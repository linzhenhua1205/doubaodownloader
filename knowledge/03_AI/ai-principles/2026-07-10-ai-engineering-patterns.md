## 核心洞察

不同方向、不同团队的 AI 应用实践，在实践中逐渐收敛到三个共通趋势（本文归纳范围以文本密集型 AI 工程为主，图像/音频等模态不必然适用）：

| # | 模式 | 一句话定义 | 对应的工程问题 |
|:-:|:-----|:-----------|:---------------|
| **1** | **📝 Markdown 化** | 所有输入输出结构化文本化，用 Markdown 作为人机共通格式 | AI 对非结构化内容（图/表/视频）理解不稳定 |
| **2** | **🧩 小模块化** | 知识/任务/提示词拆成最小独立单元，不混放、不大而全 | AI 上下文窗口有限，大而全 = 检索噪音 |
| **3** | **✅ 验证增强** | 每步 AI 输出后加入自动验证/自检/反馈闭环 | AI 输出天然不确定性，无验证 = 不能闭环 |

这三个模式**互相强化**，不是独立选择：

```text
Markdown化  --提供--->  标准化输入
     v                     v
  便于拆分 --->  小模块化  --->  精准检索/替换
     v                     v
  格式确定 --->  验证增强  --->  可自动化检查
```

## 快速自查表

> 以下自查表可在设计/审查任何 AI 系统时作为快速诊断工具，覆盖三模式的核心评估维度。

### AI 系统成熟度自查

| 维度 | 青铜级 | 银级 | 金级 |
|:-----|:-------|:-----|:-----|
| **📝 Markdown 化** | 直接喂 PDF/Word/图片给 AI | 先转为 Markdown 再处理 | 建立全链路转换→校验→修正流水线 |
| **🧩 小模块化** | 单一巨大提示词/文档 | 按模块拆分，有独立 SKILL.md 定义 | 模块可独立检索、替换、验证，有跨场景复用追踪 |
| **✅ 验证增强** | 无验证机制，直接使用 AI 输出 | 有 L1 格式验证 + L2 逻辑规则检查 | L1+L2+L3 全链路，验证结果反哺迭代 |
| **🔁 三模式协同** | 互不关联，各自独立配置 | 两两之间有配合 | 形成正向闭环（Markdown→模块→验证→反哺） |

### 常见诊断信号

| 信号 | 问题 | 对应修复 |
|:-----|:-----|:---------|
| "用 GPT 总结这篇 PDF" | 缺少 Markdown 化 | 先用 markitdown/pymupdf 转为 Markdown |
| 提示词超过 800 行 | 过度耦合 | 拆成 system/context/format/checklist 多段 |
| "它上次回答对了，这次错了" | 缺少验证 | 加 L1 格式/关键词检测 + 输入侧固化 |
| Prompt A 改一处影响多处 | 过度耦合 | 按职责拆分，每模块单一意图 |

## 模式一：📝 Markdown 化

### 现象：殊途同归

| 领域 | 实践案例 | 共同选择 |
|:-----|:---------|:---------|
| **知识库** | 全部文档 .md 存储，图片/视频/PDF → 提取为 Markdown 文本 | Markdown |
| **CodeReview** | CR 报告 .md、Prompt 模板 YAML+MD、Checklist .md | Markdown + YAML |
| **提示词工程** | 系统提示词 .md、Skill 定义 .md、分段规则 .md | Markdown |
| **Agent 工具链** | SKILL.md 作为统一接口定义、AGENT.md/USER.md/MEMORY.md/RULE.md | Markdown |
| **文档交付** | 技术报告 .md → 转 Word/PDF/PPT/Slides | Markdown 为源 |

### 为什么是 Markdown

1. **人和模型都能解析** — 没有专有格式依赖，LLM 对 Markdown 结构理解最优
2. **结构明确** — 标题层级、列表、表格、代码块，天然分段
3. **版本友好** — git diff 可读、合并冲突可解
4. **标准化管道** — 任何格式→Markdown（markitdown/unstructured）→AI处理→Markdown→任意输出
5. **嵌入方便** — 向量化时段落边界清晰，块级检索优于全文检索

### 来自现实世界的证据

**企业级「去微软化」运动** — 某公司文档转型讨论中（来源：V2EX，345天前），清晰呈现了团队在 Markdown 与 Word 之间的抉择过程：

| 团队类型 | 原来做法 | 向 Markdown 迁移的理由 |
|:---------|:---------|:----------------------|
| 硬件嵌入式 | README + ASCII 化简图 | 版本管理（git）、纯文本可搜索 |
| 软件团队 | Sphinx + javadoc | 已使用文本格式，天然兼容 |
| 系统架构 | Word + UML/Visio 截图 | 截图不可检索、版本对比困难 |
| 测试团队 | Excel→Word宏生成 | 两套模板维护成本高 |
| 用户手册 | Word 模板人工编写 | Sharepoint 版本管理不如 git |

核心诉求：**文档需完全透明，能按需检索、解析、批量处理，能用 git 做版本管理**。这正是 Markdown 化的底层驱动力。

**PDF→Markdown 转换的全链路工程化** — 在一份千问生成的 PDF 转换指南中（来源：import/doubao/），给出了极其细致的 Markdown 化工程策略：

- **6 大类 PDF 分类**：API导出型、截图生成型、扫描件型、工程型、特殊格式型（PDF/A/E/X/UA）、混合型
- **6 种内容结构**：纯文本、图文混合、表格密集型、代码型、工程型、混合型
- **差异化工具体系**：PyMuPDF（文本提取）、PDFplumber（表格提取）、PaddleOCR（截图识别）、Qwen3-8B（文本润色）、lint-md（格式校验）
- **转换后校验流水线**：提取 → 结构重建 → 内嵌图像 → AI 润色 → 格式验证 → 人工校对

这套实践的深层逻辑：**将任何格式先转为 Markdown，再喂给 AI，比直接喂原生格式稳定得多。**

### 反模式

| ❌ 反模式 | ✅ 正确做法 |
|:----------|:------------|
| 直接喂 PDF/图片给 AI | 先提取为 Markdown 文本 |
| 一段 Markdown 写 500 行 | 按标题分块，每块聚焦一个主题 |
| 表格用截图代替 | 用 Markdown 表格 + 说明文字 |
| 代码片段用纯文本 | 用代码块标注语言 |

## 模式二：🧩 小模块化

### 现象：殊途同归

| 领域 | 实践案例 | 拆分粒度 |
|:-----|:---------|:---------|
| **知识库** | 分库策略（8个子库不混放）、单文件单主题 | 目录200文件上限，同类型分库 |
| **CodeReview** | 35个独立动作模块，每动作一个 focus | 单动作单职责 |
| **Skill 系统** | 每个 Skill 独立的 SKILL.md，互不耦合 | 单 Skill 单能力 |
| **提示词** | 拆成 system/checklist/context/format 多段 | 单段单意图 |
| **告警分析** | 1000+告警→5层收敛→10-30条高价值 | 多层漏斗，每层单一过滤条件 |
| **知识页面** | 单文件单主题，关联用交叉链接 | 不堆砌不重复 |

### 为什么必须小模块

1. **上下文窗口受限** — 大而全 = 关键词稀释 = 检索命中率下降
2. **替换成本低** — 改一个模块不影响其他
3. **测试可验证** — 小模块边界清晰，输入输出可穷举
4. **复用性好** — 跨项目/跨场景可独立引用
5. **版本追踪** — git diff 精准定位变更

### 拆分的两条边界规则

```text
太细（过度拆分）          最佳粒度               太粗（大而全）
    |                       |                       |
  单函数级              单能力级               整个系统级
  失去上下文           独立可验证              检索噪音大
  管理成本高           可替换可复用            改一处动全身
```

**判断标准**：一个模块能否独立被检索到、被替换、被验证？如果可以，粒度合适。

### 来自现实世界的证据

**Skills 三层分类架构**（来源：import/doubao/「构建融合确定性与不确定性的新型软件栈架构」）—— 该文系统性地将软件栈划分为「不确定性推理层」与「确定性执行层」，其中 Skills 执行层按粒度分为三级：

| 层级 | 粒度 | 示例 | 复用范围 |
|:-----|:-----|:-----|:---------|
| **原子技能**（Atomic） | 单一职责 | SQL查询、发送邮件、图表生成 | 60%+ 跨场景复用 |
| **组合技能**（Composite） | DAG编排 | 报表生成（查询→清洗→图表→发送） | 固化的业务 SOP |
| **元技能**（Meta） | 辅助其他技能 | 技能发现、错误恢复 | 系统自适应 |

关键设计约束：每个 Skill 必须包含 `SKILL.md` 元数据文件（YAML front matter），记录名称、版本、描述、输入输出参数、权限要求，实现「自描述」——模型或 MCP 编排层可通过元数据自动识别技能的能力边界，无需额外文档。

**colleague-skill 双层架构**（来源：import/cnblogs/ 和 GitHub 开源项目 titanwings/colleague-skill）—— 该项目将个人的「数字分身」拆为两层：

```text
colleague-skill/
+-- SKILL.md                 # 技能入口
+-- prompts/
|   +-- intake.md            # 对话式信息录入
|   +-- analyzer.md          # 能力与性格特征提取
+-- tools/
|   +-- feishu_collector.py  # 多源数据采集
+-- colleagues/              # 生成的同事 Skill 包
```

- **工作能力层（Work Skill）**：技术开发规范、SOP 流程、历史项目经验 — 可标准化可复用
- **人格层（Persona）**：五级结构（硬规则→身份定位→表达风格→决策模式→人际行为）— 剥离后独立替换

运行逻辑也是模块化的四步闭环：**接到任务 → 判断态度 → 技能执行 → 语气输出**。人格层与能力层完全解耦，可独立替换和迭代。

**Skill 生态的经济验证** — 阿里 QoderWork、腾讯 WorkBuddy 等技能市场数据显示，标准化模块后的技能复用率从传统工具库（闭源 SDK/API 封装的典型复用率）的 10% 提升至 50%+——5 倍的复用效率提升直接降低了每个客户对接时的重复开发成本。某医疗 AI 技能平台（2025 年数据，华东地区）上线 3 个月，127 家医院采购技能，提供者平均月收益达 28,000 元（¥ CNY，税前分成后）。**模块化不仅解决技术问题，还有清晰的经济激励：平台对技能提供者的分润比例通常在 60-80%，即约 17,000-22,000 元月入为技能开发者的分成收入。**

**Harness Engineering 的模块化要求**（来源：import/cnblogs/「AI Agent 走出 Demo 幻觉的唯一解药」）：
> 「你的系统架构越烂，Agent 的智商就越低。……只有物理隔离边界清晰的模块，才能被安全地放入沙盒中交由 Agent 迭代。」
> 未来衡量代码质量的核心指标将从「可读性」变为「可接管性（Harnessability）」：
>
> - 状态与逻辑极度解耦（纯函数 > 隐式状态）
> - 强类型与显式契约（Rust/TypeScript > 动态语言）
> - 高内聚与微模块（物理隔离 > 牵一发而动全身）

## 模式三：✅ 验证增强

### 现象：殊途同归

| 领域 | 实践案例 | 验证方式 |
|:-----|:---------|:---------|
| **知识库** | 完整性检查脚本（链接/格式/log排序/文件位置合理性） | 自动化脚本 |
| **CodeReview** | 四阶段门禁（客户端→CI→AI汇聚→集中评审） | 工具+人工 |
| **告警分析** | 误报收集→规则固化→A/B测试 | 闭环迭代 |
| **文档质量** | doc-reviewer 逻辑谬误检查、depth-completer 深度补全 | AI+规则 |
| **论文写作** | 自检 pipeline（factual/layout/review/ethics/consistency） | 多轮自检 |
| **知识图谱** | 交叉链接有效性、索引准确性 | 定时扫描 |
| **输出规范** | 三要三不要（数据出处/格式规范/够深 | 不猜/不编/不空） | AGENT.md 硬约束 |

### 验证的三层结构

```text
L1: 格式验证 --- 自动脚本可完成
    +-- Markdown 格式、表格对齐、链接有效性
    +-- 编号规范、changelog 倒序、TOC 存在性
    +-- 文件头部约束标记检查（AUTO-GENERATED/DO NOT EDIT）

L2: 逻辑验证 --- AI + 规则
    +-- 结论是否由推理链条导出（禁止跳跃）
    +-- MECE 自检（同层互斥且穷尽）
    +-- 数据可验证（数值+单位+基线+条件）
    +-- 13条逻辑谬误清单扫描

L3: 效果验证 --- 人工 + 在线指标
    +-- A/B 测试（提示词版本对比）
    +-- 用户反馈闭环（有用/无用/改进建议）
    +-- 命中率/使用率/解决率季度追踪
    +-- 误报率/漏报率持续监控
```

### 为什么验证是闭环的关键

```text
传统 AI 使用:  输入 -> AI处理 -> 输出（不验证，直接给人）
                    v
AI 工程化:   输入 -> AI处理 -> 验证 -> 通过 -> 输出
                              v 不通过
                            重试/修正 -> 验证
                    ^___________________v
```

没有验证，AI 输出永远停留在"仅供参考"阶段，无法真正嵌入业务流水线。

### 来自现实世界的证据

**Harness Engineering：验证体系的最完整工程化范例**（来源：import/cnblogs/「AI Agent 走出 Demo 幻觉的唯一解药」）

这是当前业界对「验证增强」最系统的论述。Martin Fowler 团队（Birgitta Böckeler）与 Anthropic 团队共同提出的概念，直指核心问题：

> **大语言模型终究只是一个无状态的概率引擎。人类能完成长周期复杂工程，是因为大脑自带一套「隐式套件」。AI 必须用工程化手段重建这套套件。**

Anthropic 在实践中发现的长周期 Agent 三大失效模式——目标偏移、幻觉盲信、级联灾难——本质上都是 **「验证缺失」** 导致。他们的解法是三大核心机制：

| 机制 | 本质 | 验证方式 |
|:-----|:-----|:---------|
| **状态固化（State Pinning）** | 将模型隐空间中的状态「钉」在文件系统上 | 分离规划器与执行器，每次唤醒强制读取 JSON 状态文件 |
| **强制空间感知（Spatial Anchoring）** | 迫使 Agent 在真实环境中确认自己的位置 | 每次唤醒执行 pwd / ls / git log，端到端测试反馈 |
| **分支与回溯（Branching & Backtracking）** | 系统工程抹杀模型误差 | 高频 Git Checkpoint + 断路器（3次失败自动回滚） |

核心洞见：
> **Agent 输出的代码仅仅是「假设（Hypothesis）」，而 Harness 从物理环境中提取的运行时报错和文件状态，才是绝对的「地表真理（Ground Truth）」。**

**HDD（Harness-Driven Development）范式转移** — 从 TDD 到 HDD，核心变化：

```text
TDD:      写测试 -> 写代码 -> 测试通过   （测试 = 安全网）
HDD:      建沙盒 -> 铺传感器 -> 释放 Agent -> 迭代套件而非模型
           （测试 = 唯一视觉器官 + 方向盘）
```

关键推论：**代码的验证成本将取代代码的编写成本，成为工程界的核心矛盾。** 未来 20% 算力用于生成，80% 用于验证。

**低成本外部反馈闭环方法论**（来源：import/doubao/「低成本获取外部反馈的方法」）— 产品视角的验证循环：

- **反馈分类体系**：功能建议 / Bug 报告 / 操作体验 / 性能问题 — 四类标准化分类
- **优先级矩阵**：影响范围（广泛/局部）× 紧急程度（高/中/低）二维评估
- **分层激励**：即时奖励（小额优惠券）→ 精神激励（体验官计划）→ 社交激励（分享解锁特权）
- **闭环铁律**：24 小时响应 → 透明化处理进度 → 成果公示通知用户

这套机制的核心信条与三模式完全一致：**「低成本获取反馈的关键不是『多』，而是『快』——收集快、响应快、改进快。」**

## 跨模式实例：从 import 材料中提取的完整案例

以下三个案例分别来自 import 目录，清晰展示了三个模式如何在同一系统中协同工作。

### 案例一：Skills 生态体系（来源：构建融合确定性与不确定性的新型软件栈架构）

```text
输入（自然语言）            MCP编排层（枢纽）              Skills执行层（模块）
    |                            |                            |
    v                            v                            v
📝 Markdown化              🧩 小模块化                    ✅ 验证增强
-----------------    ---------------------          --------------------
· 用户输入通过            · MCP 将任务拆解               · 原子技能返回结果
  提示词接口层              为独立的原子调用               由 MCP 校验
  转为 JSON-RPC           · 上下文路由器                  · 错误自动重试 2 次
· 参数格式                 动态加载上下文                  · 失败触发降级策略
  由 JSON Schema          · 技能调度器                    · 全部执行完成后
  统一描述                 做 DAG 编排                    返回结构化结果
  标准化
```

### 案例二：colleague-skill 数字分身（来源：开源项目 titanwings/colleague-skill）

```text
用户发起对话 "帮我 review 这段代码"
        |
        v
📝 对话模板 intake.md (Markdown化)
        |
        v
🧩 分解为：
   +-- 人格层 Persona 选择语气（五级结构独立模块）
   +-- 工作能力层 Skill 执行代码审查（原子技能）
   +-- 知识库 RAG 检索团队规范（小模块检索）
        |
        v
✅ 输出验证
   +-- 风格一致性校验（Persona 约束）
   +-- 代码逻辑校验（Linter/类型检查）
   +-- 用户反馈闭环（纠正即时生效，版本可回滚）
```

### 案例三：HDD 开发流程（来源：Harness Engineering）

```text
需求 -> 📝 1. 将需求写为 Markdown 测试用例/验收标准
                  v
         🧩 2. 拆分子任务，每个任务有独立边界
                  v
         ✅ 3. 铺传感器（测试/Linter/类型检查）
                  v
         🤖 4. 释放 Agent 在沙盒中执行
                  v
         ✅ 5. 验证结果，失败则回滚到上一个 Checkpoint
                  v
         🔄 6. 迭代套件（Harness），不迭代模型
```

核心度量：**可接管性（Harnessability）**——代码对 AI Agent 友好的程度。状态解耦 + 强类型 + 微模块 = 高 Harnessability。

## 外部实证（v2.0 补强，2026-08-18）

三条铁律并非本系统独有归纳，而是与主流厂商实践收敛（互证而非自证）：

| 铁律 | 外部锚点 | 来源 |
|:-----|:---------|:-----|
| **Markdown 化** | Claude/ChatGPT 输出天然 Markdown；Copilot Edits 用 Markdown 差异流呈现多文件修改，人机共读 | [来源: 1] |
| **小模块化** | MCP 把"工具能力"拆成独立 server（Google Drive/Slack/GitHub/Git/Postgres/Puppeteer 各一模块），可独立增删替换 | [来源: 2] |
| **验证增强** | SWE-bench 用 2294 个真实 issue-PR 对做自动验证闭环；GitHub Project Padawan 每个任务自动"构建+测试+lint"验证后才提 PR | [来源: 3] |

**量化佐证（验证增强为什么是闭环关键）**：
- SWE-agent 从 12.47%（2024-03）→ mini-SWE-agent 65%（2025-07）——**提升的核心不是模型换了，而是验证-重试闭环成熟了**（无验证的裸生成无法达到）[来源: 3]
- 仍剩 35% 失败 → 验证闭环的覆盖缺口 = 生产可用性缺口 [来源: 3]

**第一性原理**：三条铁律都是对**同一约束**的回应——LLM 是"不确定性的概率引擎"，工程上必须用"确定性外壳"包裹：Markdown=把内容格式变成确定性可解析；小模块=把范围变成确定性可检索；验证=把结果变成确定性可接受。**三者不是风格偏好，是 LLM 工程的结构性必然**。
