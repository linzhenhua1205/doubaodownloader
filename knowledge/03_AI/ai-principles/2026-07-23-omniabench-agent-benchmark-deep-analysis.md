## 1. 概述：为什么需要 OmniaBench？

### 1.1 现有基准的根本局限

在 OmniaBench 之前，Agent 评测基准主要沿三个方向各自发展：

| 方向 | 代表基准 | 核心局限 |
|:-----|:---------|:---------|
| **函数调用/工具使用** | BFCL v3/v4, ACEBench, ToolSandbox | 场景单一，缺乏多轮交互和状态管理 |
| **交互式环境** | τ-Bench, τ²-Bench, GAIA2 | 领域数量少（≤36 个服务器/应用），覆盖窄 |
| **工作空间/计算机使用** | ClawEval, ClawMark, QwenClawBench | 专注文件系统操作，缺乏广泛领域覆盖 |

**核心矛盾**: 现实中的通用 Agent 需要跨异构应用场景工作，处理多轮交互、演化状态、工具执行和用户特定约束。而现有基准要么领域覆盖窄，要么任务形式单一。

### 1.2 OmniaBench 的定位

OmniaBench 试图回答一个根本性问题：**当前通用 Agent 的能力边界在哪里？**

它的三个设计支柱：

```text
+-----------------------------------------------------+
|                OmniaBench design pillars              |
+---------------+-------------------+------------------+
|  Scene scope  |  Diagnostics      |  Eval robustness |
|  90 L1 x 354  |  10 dims x 8 fac  |  5 model judges  |
|  L2 domains   |  precise agent    |  Fleiss k=0.573  |
|  ToC+ToB+ToE  |  weakness pinpoint|  86.3% agreement |
+---------------+-------------------+------------------+
```

> 中文说明：三大设计支柱——场景广度（90 L1×354 L2 域，覆盖 ToC/ToB/ToE）、诊断能力（10 维能力×8 难度因子精确诊断短板）、评测鲁棒性（5 模型法官交叉验证，Fleiss' κ=0.573，86.3% 一致率）。 [来源: arXiv:2607.14989]

### 3.2 四路详细说明

| 路线 | 类型 | 任务数(挑战) | 核心机制 | 评估方式 |
|:-----|:-----|:----------:|:---------|:---------|
| **DAG** | 多轮交互 | 354 | 基于工具依赖图采样可执行工具链/DAG，生成用户请求、参考轨迹和最终状态 | 多条目 Rubric（全分制） |
| **DAG-S** | 单轮 | 200 | 在 DAG 任务基础上通过 Query 精炼获得单轮用户请求 | 多条目 Rubric |
| **Solver** | 单轮优化 | 60 | 选择/调度/分配/优化场景，显式或隐式求解器引导合成 | Rubric + 约束满足检查 |
| **Program** | 单轮编程 | 30 | 分支/迭代/任务程序合成/执行调试，复杂过程推理 | VerifyCode（二值验证） |

### 3.3 挑战子集构建策略

为解决完整集（1,431 任务）的评测成本和数据污染问题，OmniaBench 设计了挑战子集：

- **DAG**: 每个 L2 域选 1 个最长参考工具链的任务 → 354 个 [来源: arXiv:2607.14989]
- **DAG-S/Solver/Program**: 排除低复杂度案例 → 290 个 [来源: arXiv:2607.14989]
- **最终**: 644 任务，保留完整场景覆盖的同时降低评测成本 [来源: arXiv:2607.14989]

## 4. 评估方法论：POMDP 形式化与多维度量

### 4.1 POMDP 形式化

OmniaBench 将通用 Agent 任务自然形式化为**部分可观测马尔可夫决策过程 (POMDP)**：

```text
P = (S, O, A, T, Ω, ρ₀)
```

其中：

- **S**: 潜在状态空间（用户信息、环境记录、工具状态、工作空间内容、中间结果）
- **O**: 观测空间（用户消息、工具响应、检索文档、文件状态、环境反馈）
- **A**: 异质动作空间，包含三子集：
  - `A_msg`: 面向用户的消息
  - `A_tool`: 外部工具调用（含工作空间和代码工具）
  - `A_final`: 任务终结动作（单轮设置中）
- **T**: 状态转移函数 `S × A → Δ(S)`
- **Ω**: 观测函数 `S × A → Δ(O)`

### 4.2 关键设计洞察

**部分可观测性**是 Agent 任务的核心难度来源：

```text
Agent sees only: o_t (observation)
Agent cannot see: s_t (full state)
Agent behavior:   a_t ~ pi_theta(. | h_t)  where h_t = (o0, a0, o1, a1, ..., o_t)
```

> 中文说明：POMDP 形式化——Agent 只能观测 o_t 而非完整状态 s_t，行为策略 πθ 基于完整历史 h_t（观测-动作序列）。 [来源: arXiv:2607.14989]

这意味着 Agent 必须：

1. 从部分观测中推断隐藏任务相关信息
2. 在不确定性下选择动作
3. 随着新证据出现更新计划

### 4.3 评估协议

| 维度 | 单轮任务 | 多轮任务 |
|:-----|:---------|:---------|
| 初始请求 | 完整用户请求 + 完整约束 | Persona 用户模拟器渐进披露 |
| 交互模式 | Agent 调用工具 → 提交最终结果 | Agent ↔ 用户模拟器 多轮对话 |
| 终止条件 | Agent 提交 `a_final` | 用户模拟器发出 `###STOP###` |
| 评分 | Rubric（加权），全分制 | Rubric（加权），全分制/VerifyCode |

**核心规则**: 每轨最多 200 工具调用步，最多 20 次环境端异常重试。

## 5. 十维能力分类法

> 不是简单地将评估结果归结为"成功/失败"，而是细分到 10 个独立能力维度

### 5.1 维度定义

| # | 能力维度 | 评估内容 | 典型检视点 |
|:--:|:---------|:---------|:----------|
| 1 | **任务理解** (Task Understanding) | 识别用户目标、隐含需求、优先级、领域约束和预期结果 | 能否正确解析模糊指令？ |
| 2 | **信息收集** (Information Gathering) | 定位、检索和整合来自环境状态、工具、文件、数据库和外部信息源的相关证据 | 能否主动搜索而非猜测？ |
| 3 | **规划与决策** (Planning & Decision Making) | 分解目标、选择执行策略、遵循依赖关系和约束、在新观测下修订计划 | 分支/长依赖下的决策质量？ |
| 4 | **状态管理** (State Management) | 跨实体、环境状态、长时间/多轮轨迹追踪中间进度并保持一致性 | 多步操作后能否回正确状态？ |
| 5 | **工具使用** (Tool Use) | 选择适当的工具、构造有效参数、解读输出、协调多个工具调用 | 工具排序/组合是否合理？ |
| 6 | **代码与编程** (Code & Programmatic) | 编写和执行用于计算、数据转换、自动化、文件操作和编程任务完成的代码 | 代码正确性和调试效率？ |
| 7 | **数据分析** (Data Analysis) | 过滤、聚合、比较、调和和推理结构化/半结构化数据 | 多源交叉验证的能力？ |
| 8 | **办公与文档** (Office & Document) | 读取、提取、编辑、合并、验证和生成文档、电子表格、演示文稿等 | 格式/结构理解是否准确？ |
| 9 | **交互协作** (Interactive Collaboration) | 请求缺失信息、澄清模糊目标、确认行动、融入用户反馈、跨轮协调 | 是否主动确认而非盲目执行？ |
| 10 | **可靠性与安全** (Reliability & Safety) | 检测和从失败中恢复、维持约束合规、避免不安全/无效操作、在不确定性下鲁棒完成任务 | 遇到错误是否能优雅恢复？ |

### 5.2 能力剖面分析

关键设计原则：**一个任务可标注多个能力维度**，这意味着能力得分基于该维度涉及的所有任务平均分计算，而非独占性分配。

这使得能力分析能揭示：

- **同分不同质**: 相同 Overall 得分的模型可能有截然不同的能力剖面
- **短板精确诊断**: 精准定位模型在哪些阶段/维度失效

## 6. 八种原子难度因子

> 能力维度描述 Agent **需要做什么**；难度因子描述该任务**为什么难**

### 6.1 因子定义

| # | 难度因子 | 实例化方式 |
|:--:|:---------|:----------|
| 1 | **模糊目标与上下文约束** | 请求不明确、间接或隐含于偏好/策略/优先级/专业约束中 |
| 2 | **工具与参数接地** | Agent 必须区分相似/冗余工具、从上下文中推断参数、或先请求缺失参数再执行 |
| 3 | **结构化信息复杂度** | 环境包含大量结构化实体、属性、关系或记录，需过滤/连接/比较/调和 |
| 4 | **长上下文与多工件证据** | 相关证据分布在长工具输出、文档、文件、附件、日志或多个异构工件中 |
| 5 | **动态多步规划** | 完成需长依赖、条件分支、中间决策或基于新观测的重新规划 |
| 6 | **多源不一致性** | 来自用户/工具/文件/环境状态的信息不完整、重复、过时或相互冲突 |
| 7 | **渐进披露与状态演化** | 关键信息或约束通过用户轮次、工具结果、审批阶段或状态转换逐步揭示 |
| 8 | **风险/可靠性与澄清** | 任务涉及不可逆操作、证据不足、指令冲突或需要明确确认/恢复处理/拒绝的操作 |

### 6.2 难度因子组合示例

```text
+----------------------------------------------------+
|  real task = combination of difficulty factors       |
+----------------------------------------------------+
|  DAG task: factor1(ambiguity) + factor5(dyn plan) + factor7(progressive) |
|  Solver task: factor3(structured) + factor6(multi-source inconsistency) |
|  Program task: factor4(long context) + factor5(branch planning) |
+----------------------------------------------------+
```

> 中文说明：实际任务由多个难度因子组合而成——如 DAG 任务含模糊性+动态规划+渐进性因子，同一能力的评测可通过不同因子组合实现难度差异化。 [来源: arXiv:2607.14989]

### 6.3 能力与难度的关系

```text
capability dim: what the agent "needs to do"
    v
difficulty factor: why the task "is hard"
    v
orthogonal: tasks evaluating same capability can differ in difficulty via factor combos
```

> 中文说明：十维能力×八难度因子的正交框架——能力维度回答"Agent 需要做什么"，难度因子回答"任务为什么难"，两者正交使评估可精细分级。 [来源: arXiv:2607.14989]

## 9. 错误模式深度剖析

### 9.1 错误分类（基于 Claude-Opus-4.7 执行分析）

```text
+-----------------------------------------------------+
|                   error distribution (100%)           |
+---------------+-------------------------------------+
|  reasoning    | 53.8%                               |
|  +- planning  | 36.7%  <- largest single class       |
|  +- constraint| 16.5%                               |
+---------------+-------------------------------------+
|  metacognition| 31.0%                               |
|  +- reflection| ~15%                                |
|  +- give up   | ~16%                                |
+---------------+-------------------------------------+
|  tool use     | ~15%                                |
|  +- format    | minor                               |
|  +- dep       | minor                               |
|  +- redundant | minor                               |
+---------------+-------------------------------------+
```

> 中文说明：错误分布（100%）——推理相关 53.8%（规划/分解 36.7% 最大单类、约束违反 16.5%）、元认知错误 31.0%（反思不足 ~15%/过早放弃 ~16%）、工具使用 ~15%。 [来源: arXiv:2607.14989]

### 9.2 三大系统性短板的根因分析

#### 🚩 短板 1: 规划 (Planning) — 36.7% 错误

> **任务**: "验证证据链完整性，发现自引用循环，然后添加新证据条目"
>
> Agent 输出: 正常找到自引用循环，但在添加新证据时使用了已被拒绝的 ID
>
> **根因**: 规划缺乏"分支恢复"能力——当主计划中一步失败时，Agent 不能自然切换到备选路径，而是机械重试 [来源: arXiv:2607.14989]

#### 🚩 短板 2: 约束维护 (Constraint Maintenance) — 16.5% 错误

> **任务**: "确保 matter 保持 stayed 状态 (不改变)"
>
> Agent 输出: 成功添加证据，但在更新时间线时无意改变了 matter 的 stayed 状态
>
> **根因**: Agent 在执行过程中"遗忘"早期约束条件。本质是**短时注意力窗口问题**——当工具调用序列拉长时，初始约束在上下文中被后续操作稀释。 [来源: arXiv:2607.14989]

#### 🚩 短板 3: 自适应纠错 (Adaptive Correction) — 元认知错误

> **工具返回**: "evidence_id EVD-005 already exists"
>
> Agent 行为: 尝试 EVD-005 第二次
>
> **根因**: Agent 不能从错误反馈中快速学习。需要多次错误输入才能切换策略。本质是**反馈-动作循环延迟**问题。 [来源: arXiv:2607.14989]

### 9.3 这三个短板为何是"系统性"的？

| 短板 | 是否可 scale 解决？ | 是否可 prompt 解决？ | 根本原因 |
|:-----|:-------------------:|:--------------------:|:---------|
| 规划 | ❌ 模型参数量越大≠规划越好 | ❌ 复杂规划无法通过指令补偿 | 当前架构缺乏可执行的世界模型和规划缓冲区 |
| 约束维护 | ❌ 上下文窗口扩大反而稀释约束 | ⚠️ 分阶段 prompt 可缓解但非消除 | Token 级别的注意力本质上是局部相关的 |
| 自适应纠错 | ❌ 更多参数不改善错误恢复 | ❌ ReAct 范式固有局限 | 反馈-动作循环延迟 + 缺乏显式错误记忆 |

**关键洞察**: 这三个短板不是因为数据不够或 prompt 不够好，而是当前 **Transformer + ReAct 范式的结构性缺陷**。

## 11. 深层原理分析：为什么规划/约束/纠错是系统性短板？

### 11.1 从第一性原理看 Transformer 在 Agent 任务上的结构性局限

#### 11.1.1 规划的挑战

> **人类规划**: 在"行动"之前在内部"推演"路径
>   - 构建内部世界模型 -> 模拟结果 -> 选择最优路径
>   - 规划缓冲区独立于执行缓冲区
>
> **Transformer Agent**: 只能在"执行"中"规划"
>   - 没有独立的世界模型
>   - 规划 = 下一个 token 预测，与执行共享同一上下文 [来源: arXiv:2607.14989]

**根本矛盾**: 规划需要前瞻性推理（proactive reasoning），而 Transformer 的"next token prediction"本质上是反应式的（reactive）。当任务需要长依赖链时，这种反应式规划不可避免地出现失误。

#### 11.1.2 约束维护的挑战

> **问题**: 为什么 Agent 容易在长序列中"忘记"约束？
>
> **数学本质**:
>   约束维护 = 在整个轨迹 h_t 上保持约束 c 有效
>
> Transformer 处理:
>   P(a_t | h_t, c) ~ attention over h_t
>
>   当 h_t 增加时:
>   - 约束 c 出现在早期位置（距当前位置远）
>   - attention 权重被后续工具返回稀释
>   - -> 约束被"软化"或遗忘 [来源: arXiv:2607.14989]

**核心**: 这不是上下文窗口长度的问题（即使 128K 上下文），而是 **注意力分配的局部性偏好** — Token 级的注意力机制天然更关注近处的信息。

#### 11.1.3 自适应纠错的挑战

> **错误模式**:
>   工具返回错误 -> Agent 重新尝试 -> 再次失败 -> 再次尝试...
>
> **原因**: ReAct 范式没有显式的"错误记忆"机制
>
>   每次错误反馈作为新的观测 o_t 加入上下文
>   Agent 需要从 h_t 中的错误模式中学习
>   -> 但这同样是 attention 问题（错误信息在长上下文中被稀释）
>   -> 且缺乏专用的"失败-恢复"回路 [来源: arXiv:2607.14989]

### 11.2 "规划三角"框架

三个短板之间存在增强循环：

```text
        planning failure
        (wrong path)
           ^v
constraint violation <----> adaptation failure
(precondition unmet)   (cannot recover from error)
```

> 中文说明：规划三角——规划失败/约束违反/自适应失败三短板相互增强形成恶性循环。 [来源: arXiv:2607.14989]

- 规划错误 → 走到不满足约束的状态 → 约束违反
- 约束违反 → 需要纠错 → 但自适应能力弱 → 陷入死循环
- 规划错误 → 需要重新规划 → 但自适应弱 → 无法切换到备选路径

### 11.3 对 Agent 架构演进方向的启示

| 方向 | 解决哪个短板 | 技术路径 |
|:-----|:----------:|:---------|
| **世界模型 + 树搜索** | 规划 | 在搜索空间中模拟轨迹后再执行 |
| **显式约束追踪** | 约束维护 | 约束作为独立的状态变量，不受 attention 稀释 |
| **错误记忆缓冲区** | 自适应纠错 | 显式记录失败模式，在下一次规划时避开 |
| **分阶段执行** | 三者兼治 | 每个阶段验证前提条件，不满足则回退 |

## 12. 对 Agent 研发的启示

### 12.1 当前 Agent 能力的真实边界

```text
Capability maturity assessment:

  reliable    --- tool use, task understanding, information gathering
  limited     --- data analysis, interaction, state mgmt, coding
  weak        --- planning, constraint maintenance, adaptive correction, safety
```

> 中文说明：能力成熟度三档——可靠（工具使用/任务理解/信息收集）、有限（数据分析/交互协作/状态管理/代码编程）、薄弱（规划/约束维护/自适应纠错/可靠性与安全）。 [来源: arXiv:2607.14989]

### 12.2 评测建议

1. **聚合分数远不足以表征 Agent 能力**: 必须报告能力剖面
2. **关注错误模式分布**: 比总体得分更能揭示模型差异
3. **多域验证**: 单一域领先不代表通用能力
4. **工具效率指标**: 不要只看最终成功，还要看成本

### 12.3 对系统设计的影响

对于部署 AI Agent 的系统架构师：

| 系统层面 | 建议 |
|:---------|:-----|
| **人机协作流程** | 在"规划/约束违反/异常"节点设置强制人工确认点 |
| **沙箱隔离** | Agent 执行应在沙箱中，异常恢复有回退策略 |
| **日志/追踪** | 记录完整轨迹，便于事后错误模式分析 |
| **约束编码** | 关键约束应编码在系统层（不可变规则）而非期望 Agent 自觉遵守 |
