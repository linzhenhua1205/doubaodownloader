    2.1KV Cache 容量公式（第一性原理）与硬件诉求

    KV 容量公式（🔶推导）

    • KV = batch × seq × 2 × L × D_eff × dtype
    • 70B (GQA 8:1, FP16)：320 KB/token
    • 128K ctx → 41.9 GB/req；1M ctx → 320 GB/req
    • 每 token：Llama2-7B MHA 512KB / Llama3-8B GQA 128KB / V3 MLA 137KB
    ⇒

    decode 全量读带宽（🔶）

    • 128K × 20 tok/s = 838 GB/s——远超 CXL(64GB/s) 与 SSD(14GB/s)
    • 仅 HBM(8TB/s) / CPU DRAM(~450GB/s) 可支撑
    • 必须依赖注意力稀疏性只读子集（OasisKV/HiSparse 技术前提）

    对整机硬件的诉求（从公式反推）

    诉求量化说明
    HBM 容量仍不足141→288 GB/卡KV 必然溢出 → 分层不可避免
    分层迁移带宽DDR 450GB/s / CXL 64GB/s / SSD 14GB/s冷热分层需带宽匹配
    SSD 小随机读512B 粒度，4K 优化盘 8× 读放大KV 层 SSD 新三围：512B IOPS + 有效 DWPD + FDP 流数
    host DRAM 容量≥ 8× GPU HBMP0 结论超节点稀疏推理短板（GB300 Grace LPDDR ~480GB ≤ GPU HBM）
    ✅KV 公式与分层依据：知识库 kv-cache 深度分析 / kv-cache-ttft-tpot-budget / HiSparse 专题；🔶decode 带宽为第一性推导

    2.2三类负载场景决定三类机型——负载形态是机型设计的第一输入

    场景 A：单请求长上下文 容量驱动

    • 典型：长文档分析、RAG、多模态
    • 核心矛盾：KV 总量 > HBM 容量（128K≈41.9GB）
    • 机型：分层存储 + CXL 池化 + 大容量内存

    场景 B：高并发短请求 吞吐驱动

    • 典型：办公助手、Agent 多轮、代码生成
    • 核心矛盾：并发 KV × decode 带宽
    • 机型：PD 分离 + 强调度 + KV 通道

    场景 C：MoE 动态路由 结构驱动

    • 典型：DeepSeek V3 类 MoE
    • 核心矛盾：专家跨节点 AllToAll
    • 机型：确定性互联 + 在网计算
  • 场景切换的含义（对整机架构）：同一 GPU 平台通过可配置外围模块（内存层容量/带宽、调度软件、互联拓扑）覆盖三类场景 = 产品线 SKU 化的第一原则
  • 架构要求：内存层与计算层解耦设计 + 软件栈支持场景感知的 KV 放置策略——这是软件研发的直接需求输入
  • 量化实证：字节 CXL 卸载实测 batch +30% / GPU 需求 -87% / prefill 利用率 ×7.5——"以存储换计算"从口号变可复现数据（✅广发证券引述）

    100sTB

    容量

    • 仅看链路/端口状态会误判"存储可用"，上层请求超时才暴露
