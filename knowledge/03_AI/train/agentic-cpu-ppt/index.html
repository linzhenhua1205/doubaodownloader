PART 01 · 论证

1.3人机双写：AI 从「对话框」进入「文档里」——工作流闭环的最后一步

过去的 AI 工具（结果放对话框）

  • AI 能写文案/分析表格/生成 PPT，但用户要自己复制 → 粘贴 → 定位 → 排版 → 检查
  • AI 与原文之间存在"最后一步距离"——高频但低价值的人工搬运
  • 本质：AI 是"提建议的人"，改不改、怎么改仍由人完成
⇒

人机双写（结果进原文件，WorkBuddy 7/30 实测）

  • 左侧 AI 对话 + 右侧可编辑文档（Word/Excel/PPT/Markdown），选中哪段 AI 改哪段
  • 错别字检查先出报告、确认后一次性同步原文；框选文字直接生成表格/配图/总结插入
  • 本质：AI 成为"坐在文档另一端的协作者"——直接动手改原文件

① 选中即改

  • 框选文字→"生成表格/配图/总结"→直接插入原文件对应位置，无需下载再排版

② 批注即指令

  • 读取文档批注并执行修改——"锁定意见 + 修改"两步合并，参与多人协作流（作者/编辑/同事）

③ 沿风格修改

  • PDF→PPT 复刻原字体/配色/版式，新插图沿用原插画风——贴合企业固定模板真实需求
  • 意义：AI 从"给建议"到"动手改"——AI 真正长进企业生产流程（智东西：入口之战已过"比功能"阶段）；也定义了办公推理形态=多轮短请求 + 长上下文 + 工具调用密集（衔接 Part 2-3 硬件需求逻辑）
  • 局限（诚实标注）：模型知识准确性仍直接影响修改结果——实测 AI 误判"SpaceXAI"公司名称为错（实际 AI 判断出错）；编辑入口更方便 ≠ 人工审核可省略
    • ✅AI应用风向标《腾讯WorkBuddy上线人机双写》2026-07-30（智东西矩阵，一手实测）；局限项来自实测原文

    1.4判断：办公 AI 将复刻编程 AI 的确定性曲线——三个共识解释"为什么是现在"

    编程 AI（已验证，2023-2026）

    • Copilot/Claude Code 从辅助→自主，代码生成已进生产流水线
    • 驱动力：任务可验证 + 反馈快 + 开发者付费意愿强
    • 结果：AI 编程成为编程的默认方式（工具覆盖率达主流）
    ⇒

    办公 AI（正在复制，2025-2027）

    • 三厂已把 AI 做进组织与产品双入口（组织整合+人机双写），AI 直接进文档动手改
    • 驱动力：任务同样可验证（文档/表格/会议即产物）+ 人群基数大 100×
    • 预判：2-3 年内办公 AI 从"尝鲜"变"默认"；IDC 预计 2030 年 95% 工作角色被重新定义→员工成为"任务架构师"

    共识 ① token 刚需场景

    • 办公=高频/高粘性/高付费意愿，是大模型 token 变现效率最高的出口（智东西/三厂共识）

    共识 ② Agent 跨越可用性门槛

    • 印奇（阶跃）：2026 模型能力跨越临界点——从连续执行数秒任务到独立工作数十小时；办公是"长程任务"最密集场景

    共识 ③ 入口争夺窗口收窄

    • OpenAI ChatGPT Work（整合 Codex）/ 微软 Copilot 超级应用年内面世——先完成内部整合者拿下一代办公入口船票
  • 对推理基础设施的含义（🔶推导）：办公 Agent 单任务 token 消耗 3-10× 单次问答、上班时间集中触发 10× 并发峰谷 → 推理算力从训练附属品变为独立主战场（低延迟/高并发/成本敏感），这是 Part 2-4 全部硬件与软件判断的需求侧起点
    • ✅三共识与 IDC 95% 预测：智东西 2026-08-03 报道（IDC×腾讯云报告）；🔶单任务 token 3-10× 与并发特征为本工作空间基于 Agent 工作流的第一性推导

    PART 02 · 背景

    2.1LLM 推理过程概述：两阶段 · 两种瓶颈

    PHASE 1 · COMPUTE-BOUND
    Prefill 预填充
    一次性处理输入上下文，计算密集
    🔶70B·seq4K·batch16≈11.5s @ 2×GPU
    吃算力（GPU 密集）
    →
    PHASE 2 · MEMORY-BOUND
    Decode 逐 token 生成
    自回归逐 token 输出，每次读全部 KV
    🔶70B KV/token≈320KB
    吃内存带宽（KV 读取为主）
    →
    AGENTIC LOOP · CPU-INTENSIVE
    多轮 Agent 循环
    路由→工具调用→检索→再推理…
    每轮含调度/解析/状态管理
    吃CPU 与 IO（GPU 空闲等待）

    KV Cache = 推理的"状态"

    • 🔶 70B：320KB/token（80层×8kv×128d×2B×2）
    • 4K 上下文≈1.3GB / 128K≈41GB / 1M≈320GB

    关键结论（✅推理冗余专题）

    • decode 瓶颈=KV 读取带宽，不是 FLOPs
    • prefill 与 decode 对硬件需求完全不同 → PD 分离

    Agentic 新变量（🔶推导）

    • 多轮循环中 GPU 大量时间空闲等待工具/检索结果
    • CPU 与 IO 成为实际瓶颈——这是 CPU 需求重构的根源
    ✅KV 数字与 PD 分离依据：知识库 `2026-07-07-kv-cache-ttft-tpot-budget`、`2026-08-05-llm-inference-single-to-multi-node`；🔶推导公式内联
    PART 02 · 核心

    2.2CPU 在 Agentic 推理中的六重角色（量化）

    ① 请求调度与编排

    • 连续批处理/PD 分离调度器在 CPU 上运行（✅Orca/vLLM）
    • Agent 任务拆解、规划、状态机——纯 CPU 逻辑

    ② KV Cache 管理

    • 显存调度/分页/前缀缓存命中（✅Intel Xeon Host CPU 文档）
    • 长上下文下 KV 分层迁移（HBM→CXL→SSD）由 CPU 驱动

    ③ 路由与工具调用

    • MoE 路由决策、工具选择、函数调用解析
    • RAG 查询路由/重排（embedding/rerank 小模型可在 CPU）

    ④ Agent 执行引擎

    • ✅AMD Venice：Helios 中 CPU 承担轻量级 Agent 推理（RAG 路由/工具选择/输出格式化）
    • ✅NVIDIA Vera：88 核 CPU 同为 AI Agent 执行核心

    ⑤ 数据通路

    • tokenization、批组装、checkpoint、压缩（✅Intel QAT/IAA 加速器）
    • GPU 越多，数据搬移越 CPU 密集（✅64→1024 GPU 负载跃迁）

    ⑥ 小模型推理

    • ✅Intel AMX：128 核≈204 TOPS(INT8)——embedding/分类/意图识别
    • 投机解码的小草稿模型、安全过滤、内容审核可在 CPU
    ✅角色①-⑥分别对应知识库 Intel Xeon Host CPU / Helios / Vera Rubin / vLLM 专题；🔶Agent 负载占比为本工作空间推导

    PART 03 · 拆解

    3.2三类 KV Cache 推理场景：负载形态决定机型

    场景 A：单请求长上下文 容量驱动

    • 🔶 128K 上下文 KV≈41GB（70B）、1M≈320GB
    • KV 放不下 HBM → KV 分层 HBM→CXL→SSD
    • CPU 驱动 KV 冷热迁移；CXL 池化是容量扩展关键（✅）
    • 机型要点：大内存带宽 + CXL 槽位 + 分层存储

    场景 B：高并发短请求 吞吐驱动

    • 办公/Agent 典型：请求短、并发高、多轮
    • PD 分离：prefill 池（算力）+ decode 池（KV 带宽）
    • 🔶 KV 4K 上下文≈1.28GB/请求，池化共享压力大
    • 机型要点：两池独立扩缩 + 调度器（CPU）强 + KV 通道

    场景 C：MoE 动态路由 结构驱动

    PART 03 · 热点

    3.3五个设计热点问题（谁回答得好，谁拿单）

    ① CPU:GPU 比例——不再是一刀切 1:8

    • 训练 1:8 够用；Agentic 推理向 1:4 甚至更高 CPU 占比演进（✅Helios 1:4、NVL72 1:2）
    • PD 分离后 decode 池对 CPU 调度/KV 管理需求更高

    ② 内存带宽 vs 核心数——谁更稀缺？

    • Venice 1.6TB/s 打的是带宽牌（KV 读取/Agent 小模型推理）
    • Vera 88 核打的是单核延迟牌（GPU 调度实时性）

    ③ CPU↔GPU 互联带宽——7× 差距的博弈

    • ⚠️AMD PCIe Gen6 x16 ≈256GB/s vs NVIDIA C2C 1.8TB/s
    • 开放生态（PCIe/CXL/UALink）vs 私有（NVLink-C2C）之争

    ④ KV 分层存储——内存层级决定推理上限

    • HBM→CXL→SSD 三级成为长上下文标配（✅）
    • CXL 池化 + 共享 KV = 集群级缓存命中（✅存储专题）

    ⑤ 故障域与恢复——推理的容错 ≠ 训练的 checkpoint

    • 🔶 72 GPU 域月故障≈4.3%（×10 节点≈×10 概率）
    • 推理要求无状态请求 + 前缀缓存重建（秒级，非分钟级）

    ⑥ scale-up 域规模——超节点的边界

    • NVLink 域 72→1,152 GPU 扩展（✅）
    • UALink 开放域 2027 目标 ≥512 GPU（✅预判）
    ✅知识库 Helios/NVLink6/跨节点推理专题；🔶故障概率为第一性推导（单 GPU 年故障 1% 假设⚠️）；🏷厂商规格

    PART 04 · 设计

    4.1算力平台 / 运维 / 固件：三件套设计要点

    算力平台（调度层）

    • 拓扑感知调度：请求→就近节点、PD 配对同域（✅跨节点专题）
    • PD 分离池化：prefill/decode 弹性扩缩，KV 走专用通道
    • 缓存感知：前缀缓存命中优先调度（✅vLLM 方向）
    • GPU 细粒度共享：Agent 小请求多 → MIG/分时
    • 厂商软件栈提速：ROCm 6 周节奏 + ROCm.AI（AI 写 kernel）+ Hyperloom +38%（✅AAI 2026）

    运维（可靠性层）

    • KV 命中率/PD 配比纳入可观测性指标（✅有效算力概念）
    • 无状态请求 + 前缀缓存重建的秒级故障恢复（🔶）
    • KV 热迁移：节点下线/负载均衡时状态搬家
    • 容量规划：按"KV 增长+并发峰谷"建模，非按峰值 FLOPs

    固件（可管理性层）

    • GPU 引导 CPU：枚举/初始化/错误处理（✅Venice/Vera 角色）
    • RAS 下沉：带外故障诊断、复位、恢复自动化（✅固件三线）
    • 固件三线节奏：BMC/GPU/互联固件版本联动管理（✅POC 管理）
    • 可观测固件：KV 分层存储健康、CXL 内存纠错上报
    ✅算力平台/运维要点：知识库 `2026-08-05-inference-single-multi-node`、`2026-08-05-redundancy`、超节点 POC 管理专题；✅固件三线为既有方法论
