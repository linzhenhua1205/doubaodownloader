## 1. AI 基础概念

### 1.1 大模型（LLM）是什么

**定义**：大语言模型（Large Language Model）是基于海量文本训练、以"预测下一个 token"为核心任务的概率模型。它不是数据库，不"存储"事实，而是**学会了语言与知识的统计规律**，推理时按概率生成。

| 特性 | 含义 | 对使用者的影响 |
|:-----|:-----|:---------------|
| 概率生成 | 每次输出可能不同 | 同一请求多次回答可能不一致 → 需要验证/基准 |
| 上下文窗口 | 一次能"看到"的 token 上限 | 长文档要分段/检索，超限会遗忘 |
| 幻觉 | 生成看似合理但不真实的内容 | 关键事实必须交叉验证，禁止直接采信 |
| 指令遵循 | 遵循提示词中的规则与约束 | 约束写得越明确，执行越可靠 |
| 上下文学习 | 从上下文中即时学习（few-shot） | 给示例比给描述更有效 |

**能力边界判断**（务实视角）：模型擅长"模式匹配/语言组织/知识回忆/代码生成"，不擅长"精确计算/事实核查/时间敏感信息/专有领域深度推理"。判断任务是否适合 AI：**是否依赖模式而非精确性？是否有明确验收标准？** [来源: 知识库 模型能力对比与使用策略]

### 1.2 提示词（Prompt）

**本质**：提示词不是"写更好的话"，而是**分级注入的认知基座设计**——按"稳定性 × 作用域"把信息切分，让高频动态信息不污染低频稳定指令 [来源: 知识库 五工程范式]。

**提示词工程的三个层次**：

| 层次 | 内容 | 示例 |
|:-----|:-----|:-----|
| 角色/人格 | 你是谁、什么风格 | "你是服务器硬件专家，用中文回答，技术术语保留原词" |
| 任务/指令 | 做什么、做到什么程度 | "分析这份 BOM 的供应风险，输出表格，标注数据来源" |
| 约束/格式 | 不做什么、输出格式 | "禁止编造数据；量化必须有来源+基线+条件；输出 Markdown" |

**实用模板（本系统实证）**：

| 要素 | 写法 |
|:-----|:-----|
| 任务 | 明确要做什么（动词开头，一次一个目标） |
| 背景 | 必要的上下文，只给相关的（不放无关历史） |
| 约束 | 必须遵守的规则，用"禁止/必须"表达 |
| 输出格式 | Markdown/表格/代码块等，明确指定 |
| 验收标准 | 怎么算完成，给出可自检的清单 |

**关键技巧**（来自 Anthropic Prompting Playbook 提炼 [来源: 知识库 提示工程方法论]）：
1. **清晰直接**：说做什么，也说做到什么程度、不做什么
2. **示例驱动**：给 1-3 个示例比长篇描述更有效（格式锚定）
3. **结构化组织**：XML 标签/分段/编号让模型更容易解析
4. **上下文管理**：长文档前置 + 分段加载，别一次塞太多
5. **迭代评估**：小评估集 + 回归，提示词也做版本管理

### 1.3 Skills（技能）

**定义**：Skill 是一组**声明式技能包**（SKILL.md + 参考文件），包含触发条件、执行步骤、产出规范，Agent 按任务相关性自动加载。它是"会做什么"的动态能力，区别于规则文件的"你是谁"的静态约束 [来源: 知识库 五工程范式 + Skills 使用方法论]。

**Skills 与规则/提示词的区别**：

| 载体 | 回答的问题 | 加载机制 | 典型内容 |
|:-----|:-----------|:---------|:---------|
| 规则文件（RULE.md/AGENTS.md） | 你是谁、必须守什么规矩 | 常驻（全量加载） | 行为准则、文件操作铁律 |
| Skills（SKILL.md） | 你会做什么、怎么做 | **按需加载**（先扫描描述，仅相关时加载详情） | 工作流步骤、质量标准、检查清单 |
| 提示词（对话中） | 这次任务怎么做 | 会话内 | 任务指令、上下文 |

**为什么按需加载重要**：Token 成本。本系统实证：技能描述裁剪收益极低，但**按需加载机制本身**是最大节约杠杆——规则全量 vs 技能按需，是 Claude Code 与 Trae 共同的设计 [来源: 知识库 五工程范式 + Token 成本实证]。

**Skill 设计四法门**（提升遵守率）[来源: 知识库 Skills 使用方法论]：
1. **重复**：关键约束多次出现，强化信号
2. **强调**：用"必做/禁做"标记优先级
3. **小型化**：要点化，降低认知负载
4. **分层**：按认知负载分级（核心/扩展/参考）

### 1.4 MCP（模型上下文协议）

**定义**：MCP（Model Context Protocol）是 Anthropic 2024 年提出的**开放标准协议**，统一了 AI 应用与外部工具/数据源的连接方式。它把"每个模型都要为每个工具写适配器"（N×M 问题）简化为"工具实现一次 MCP Server，任意 MCP Client 都能用"（N+M）[来源: 知识库 Agent 生态分析]。

**MCP 解决的核心问题**：

```text
Without MCP: each Agent x each tool = N x M adapters
With MCP:    tool writes Server once, all Agents reuse = N + M
```

**MCP 的三种角色**：
- **MCP Server**：暴露工具/数据源的标准化服务（如文件系统、数据库、GitHub）
- **MCP Client**：Agent 侧连接 Server 的客户端
- **Host**：被其他 Agent 调用的宿主（Claude Code 双角色之一）

**与 Skills/工具的关系**：Skills 定义"怎么做"（流程知识），MCP 定义"能连什么"（连接通道），内置工具是"开箱即用"（文件/终端）。三者互补：**Skills 管方法、MCP 管连接、工具管执行**。

**授权语义演进**：MCP 的授权正在 SDK 级化——approval 绑定到具体调用、hosted MCP server identity 成为安全基础 [来源: 知识库 Agent 安全周更]。

## 2. AI 在编程与办公中的使用

### 2.1 编程工具全景：Trae / CodeBuddy / Claude Code / Qoder

2026 年主流编程 Agent 呈现**四条路径** [来源: 知识库 四 Agent 对比 §12]：

| 工具 | 厂商 | 路径 | 差异化 | 适合场景 |
|:-----|:-----|:-----|:-------|:---------|
| **Claude Code** | Anthropic | 深度 Harness 路线（终端原生） | Subagent/Hooks 7 类/Background Tasks/动态工作流/MCP 双角色 | 工程师深度自动化、复杂重构 |
| **Trae** | 字节跳动 | IDE 一体化路线（AI 原生 IDE） | Builder 一键生成/TRAE Work 多端调度/多模型接入 | 开发者+低门槛 Builder、多端协作 |
| **Qoder** | 阿里云 | Spec 驱动路线 | Spec 工作流（规格驱动开发）/Repo Wiki | 规格先行的大型项目 |
| **CodeBuddy** | 腾讯云 | 全链路交付路线 | 产品构思→发布一站式/国际版多模型 | 从构思到发布的完整交付 |

**关键判断**（2026-08 窗口）：
- Claude Code 与 Trae 的差距已从"能力有无"缩小为"Harness 深度与生态"——Trae 已补齐六类 Hooks/Subagent/Skills/AGENTS.md 兼容 [来源: 知识库 五工程范式，修订 08-03 结论]
- 中国厂商从"接模型"到"建 Harness"是下一阶段胜负手
- 选型不是选"最好的"，而是选"路径匹配的"：工程师深度自动化选 Claude Code，IDE 一体化选 Trae，规格驱动选 Qoder，全流程交付选 CodeBuddy

**选择建议（本系统视角）**：团队 AI 编程工具选型看三点：①是否支持**规则分级**（AGENTS.md/CLAUDE.md 兼容）②是否支持 **Skills 按需加载**（Token 成本）③是否有 **Hooks/确认点**（安全边界）。

### 2.2 办公 AI：WorkBuddy 与五引擎

**WorkBuddy（腾讯云）**：办公场景 Agent 产品化的代表，最有价值的三个设计决策 [来源: 知识库 WorkBuddy 产品化深度分析]：

1. **Memory 只存陈述性记忆**：做事方法一律进 Skill——"知识"与"方法"分离，避免记忆污染
2. **Harness 按"前馈/反馈 × 计算型/推断型"二维组织**：不同任务用不同可靠性策略
3. **"AI 自治度上限"与"Harnessability"判定框架**：先判断任务能否交给 AI、能自治到什么程度

**五引擎迁移**：编程侧验证的五工程方法论（提示词/上下文/Router/Harness/图）可整体迁移到办公与文档场景 [来源: 知识库 五引擎办公文档应用]：

| 办公场景 | 五引擎应用 | 本系统实证 |
|:---------|:-----------|:-----------|
| 会议纪要 | 提示词模板（角色+结构）+ 上下文（只给相关材料） | 每日记忆 + 会话分析 |
| 汇报材料 | 图工程（大纲→章节→成稿三段闭环）+ 检查点 | 文档生产三段闭环 |
| 邮件/沟通 | Router（碎片化高频→模板直连） | 快捷指令/模板 |
| 周报/月报 | Loop（数据拉取→聚合→成文→检查）+ Harness（scheduler 定时） | 周报生成器 |
| 知识沉淀 | Graph（知识库三同步 = 状态机） | 知识库三件套纪律 |

**办公 AI 的黄金法则**：**输入侧治理先于输出侧优化**——先查再写（检索已有知识）比写完再改（生成后修正）成本低一个数量级 [来源: 知识库 五引擎文档 + 知识库质量方法论]。

### 2.3 Rule 与 Spec：让 AI 懂规矩

**Rule（规则文件）**：告诉 AI"你是谁、必须守什么规矩"。本系统四文件分级是工程化范例 [来源: 本系统 AGENT/USER/RULE/MEMORY]：

| 文件 | 内容 | 更新频率 |
|:-----|:-----|:---------|
| AGENT.md | 人格、交流风格、行为准则 | 季更 |
| USER.md | 用户身份、偏好、质量标准 | 年更 |
| RULE.md | 工作空间规则、存储规则、安全红线 | 低频 |
| MEMORY.md | 长期记忆索引、决策、教训 | 月更 |

**关键设计**：按"稳定性 × 作用域"分级——高频动态信息（每日记忆）不进低频稳定指令（AGENT.md），避免污染。

**Spec（规格）**：把任务规格化为人和 AI 的共同契约。三种主流形态 [来源: 知识库 五工程范式 + Qoder 分析]：

| 形态 | 代表 | 机制 |
|:-----|:-----|:-----|
| 三文档组 | Trae Spec 工作流 | spec.md（大纲）+ tasks.md（任务）+ checklist.md（验收） |
| 规格驱动 | Qoder Spec | 先规格后编码，规格即文档 |
| 系统级规格 | 本系统 spec/ | sr（需求）→std（标准）→ar（映射）→design（设计）五层流转 |

**Spec 的价值**：把"AI 的自由发挥"约束在规格边界内——任务清单防目标漂移，验收清单防"看起来完成了"，文档版本控制提供可恢复性。

### 2.4 实操清单

**编程场景**：
- [ ] 项目根目录放 AGENTS.md（或 CLAUDE.md），声明角色+约束+常用命令
- [ ] 复杂任务用 Spec/Plan 工作流，先生成计划确认再执行
- [ ] 关键决策要求 AI 给依据（文件路径/行号），不轻信"我改好了"
- [ ] 高危操作（删除/覆盖/生产改动）在 Harness 层设确认点

**办公场景**：
- [ ] 文档生成前先检索知识库（先查再写）
- [ ] 量化数据要求来源+基线+条件，禁止裸数字
- [ ] 长文档分段处理，每段独立验收
- [ ] 周报/月报等重复任务用模板+定时（Loop 化）

## 3. 编程范式：问答 / Harness / Loop / Graph

### 3.1 范式全景与确定性谱系

五种工程/范式不是并列功能，而是**五个正交视角**，按确定性谱系排列 [来源: 知识库 五工程范式]：

```text
Soft (probabilistic) ----------------------------------> Hard (deterministic)
Prompt -> Context -> Loop -> Harness -> Graph
(think)   (see)      (keep   (act      (fix flow)
                     thinking safely)
```

| 范式 | 回答的问题 | 管理对象 | 确定性 | 失效模式 |
|:-----|:-----------|:---------|:------:|:---------|
| 提示词 | 模型怎么想？ | 指令/人格/约束 | 软 | 指令漂移、上下文膨胀 |
| 上下文 | 模型看什么？ | 输入空间（窗口/记忆/检索） | 软 | 超限、遗忘、成本失控 |
| Loop | 怎么持续想？ | 推理循环（感知→规划→行动→观察） | 中 | 死循环、目标漂移、提前收工 |
| Harness | 怎么安全地做？ | 工具面/权限/持久化/事件 | 硬 | 工具滥用、状态丢失、不可审计 |
| Graph | 流程怎么固化？ | 状态/边/检查点/人工介入点 | 最硬 | 过度设计、图腐化、可恢复失败 |

### 3.2 问答范式（基础）

**本质**：单轮/多轮对话，模型直接回答。无工具、无循环、无状态管理。

- **适用**：知识问答、文案生成、思路讨论、代码片段建议
- **优势**：零门槛、快速
- **局限**：无工具执行、无记忆持久化、无验证闭环、长任务易漂移
- **最佳实践**：把问答当"思考伙伴"而非"执行者"——用问答澄清问题、探索方案，执行交给更高范式

### 3.3 Loop 工程

**本质**：所有 Agent 共享同一心脏——**感知→规划→行动→观察循环**。Loop 工程管"怎么持续想"：终止条件、想/做分离、并行化、长视界 [来源: 知识库 五工程范式]。

**演进路线**：ReAct（纯提示词维持）→ Harness（代码模板）→ Dynamic Workflow（模型生成脚本）→ Workflow Runtime（编译为可执行运行时）。

**工程要点**：
1. **显式终止条件**：任务完成/最大迭代/人类干预——没有终止条件 = 死循环或烧钱
2. **想/做分离**：Plan Mode（先只读分析出计划，批准后执行）或确认点
3. **防目标漂移**：TodoWrite/任务清单显式化
4. **长视界**：单一上下文多轮迭代（Claude Code Long Horizon 150 轮）

**本系统实证**：每日定时任务（周报/日报）就是 Loop 工程——scheduler 触发 → 数据拉取 → 聚合 → 成文 → 检查 → 推送，全自动循环 [来源: 知识库 Workflow 体系方法论]。

### 3.4 Harness 工程

**本质**：Harness = 让 Agent 更有组织地干活的**确定性外壳**——任务怎么拆、Agent 怎么调用、上下文怎么隔离、结果怎么合并、中断后怎么恢复、动作怎么授权 [来源: 知识库 五工程范式 + WorkBuddy 产品化]。

**核心组件**（以 Claude Code 为参考）：
- **工具面**：文件/终端/检索/网络等内置工具 + 权限分级（允许/询问/拒绝）
- **Hooks（7 类）**：PreToolUse/PostToolUse/UserPromptSubmit/Stop/Notification 等——把审计/拦截/通知从主循环剥离，事件驱动确定性执行
- **Subagents**：声明式子代理，独立上下文，隔离目的=防上下文污染
- **Checkpoints**：会话检查点，中断后恢复
- **MCP 双角色**：Client（接外部 server）+ Host（被调用）

**Harness 的本质价值**：把"与推理无关但必须发生的动作"（审计/拦截/通知/持久化）从主循环剥离，用代码确定性执行——**模型负责想，Harness 负责保证想的动作安全落地**。

**本系统实证**：scheduler 定时任务 + RULE.md 安全红线 + git 自动提交 = Harness 的调度/约束/审计三件套 [来源: 本系统 RULE.md + 定时任务体系]。

### 3.5 Graph 工程

**本质**：Graph 工程 = **代码约束 + 模型推理**——用图（节点/边/状态/检查点/人工介入点）把概率性隔离在节点内，让控制流恢复确定性 [来源: 知识库 Graph 工程深度分析]。

**约束五层级**（从硬到软）：状态 schema → 拓扑 → 边条件 → 运行时（重试/超时/interrupt）→ 输出校验。

**适用判据**：
- ✅ 有明确状态转换 / 需人工介入 / 需可恢复 / 需可观测 → 用图
- ✅ 窄深单一推理 → 单循环（不要为图而图）
- ❌ 为图而图是反模式——图是最后手段，不是默认架构

**两种实现路线** [来源: 知识库 五工程范式]：
- **动态生成派**（Claude Code）：模型现场生成 workflow（六模式：分类分支/并行汇聚/对抗验证/生成筛选/锦标赛/迭代验收）
- **文档驱动派**（Trae/Qoder）：spec/tasks/checklist 三文档作为人和 AI 的共同契约，人可读可编辑

**本系统实证**：知识库三同步（README/index/log 三文件职责分离 + 脚本批量刷新）就是 Graph 工程——状态 schema（三文件职责）× 拓扑（归档路径注册表）× 检查点（git 提交）× 人工介入（文件操作铁律）。

### 3.6 范式选择矩阵

| 任务特征 | 推荐范式 | 理由 |
|:---------|:---------|:-----|
| 单轮问答、思路探索 | 问答 | 零门槛，快 |
| 多步但有明确步骤 | Loop（+ 任务清单） | 持续执行 + 防漂移 |
| 需要工具/权限/审计 | Loop + Harness | 安全边界 + 可审计 |
| 需要可恢复/人工审批/合规 | Loop + Harness + Graph | 检查点 + 确认点 + 状态持久化 |
| 流程固定、重复执行 | Graph（固化） | 确定性最大化 |

**工程顺序建议** [来源: 知识库 五工程范式 §9]：先做提示词+上下文（让模型"想对、看对"）→ 再做 Harness（安全边界，防止"做错"）→ Loop 提供循环骨架 → Graph 在需要确定性/合规/可恢复的场景按需引入。

## 4. 用好 AI 的关键挑战

### 4.1 挑战总览

| # | 挑战 | 本质 | 应对层级 |
|:-:|:-----|:-----|:---------|
| 1 | 幻觉与精度 | 概率生成 ≠ 事实 | 验证方法论 + 多源交叉 |
| 2 | 上下文稀缺 | 窗口有限 + token 成本 | 上下文工程 + 成本监控 |
| 3 | 权限与越权 | Agent 工具滥用 | Harness 权限分级 + Hooks |
| 4 | 采纳与信任 | 组织拒绝或盲目信任 | 采纳方法论 + 信任链 |

### 4.2 质量挑战：幻觉与精度

**现象**：AI 生成看似合理但错误的内容——编造引用、虚构数据、自信的错误结论。

**本系统方法论（多源验证）** [来源: 知识库 知识质量方法论]：
1. **多源三角验证**：关键事实 ≥2 个独立源交叉验证；素材与验证源冲突时以验证源为准
2. **正反验证**：正向（数据→结论）+ 反向（结论回溯证据）
3. **溯源标注**：每条断言标注出处；无法溯源的内容标记为"推断"或删除
4. **禁止编造**：数据无法获取时标注缺口 + 说明尝试了哪些源 + 给出替代估算，绝不编造

**精度控制（三阶段分离协议）** [来源: spec meth-007]：
- **阶段一：方向探索**（自由宽泛）→ **阶段二：方向锁定**（刚性冻结）→ **阶段三：细节精调**（基线协议）
- 核心机制：**批准基线协议**（基线冻结后只做增量变更）+ **不可变区域声明**（哪些不能动）
- 反模式：全量重生成——每改一次全量重来 = 每次都在引入新错误

**质量检查自动化**：把质量规则脚本化（check 工具/门禁），比依赖 AI 自检可靠——"AI 自查 ≠ 人工确认"，但"规则脚本化 = 确定性地把质量标准前移" [来源: 知识库 前移后移组织动力学 + 本系统 check 体系]。

### 4.3 上下文挑战：稀缺资源管理

**本质**：上下文是稀缺资源——窗口物理极限 + token 成本。本系统实证：27 天 2.3B tokens，**缓存未命中 58% 是最大成本项** [来源: 知识库 五工程范式 + Token 成本实证]。

**上下文工程四层策略** [来源: 知识库 五工程范式 §4]：
1. **截断**：超长结果保留首尾+省略说明（纯字符串，不调 LLM）
2. **裁剪**：以完整轮为单位裁掉最早一半 + 提炼总结写记忆
3. **压缩**：每轮只留首条提问+末条回复
4. **兜底**：API 抛溢出时总结后激进截断

**成本优化杠杆**（按收益排序）[来源: 本系统 Token 成本实证]：
1. 合并 session（减少请求数）
2. 减请求（少问、问对的）
3. 缩输出（限制长度、结构化输出）
4. Prompt Caching（前缀缓存复用）

**记忆分层**：高频动态（每日记忆）→ 低频稳定（长期记忆）→ 永久事实（知识库）——按"稳定性 × 作用域"分层，避免污染与膨胀 [来源: 本系统 存储规则]。

### 4.4 安全挑战：权限与越权

**现象**：Agent 越权访问、工具滥用、提示注入（Prompt Injection）、假身份冒充。

**本系统安全实践** [来源: 知识库 Agent 安全周更 + RULE.md 安全红线]：
1. **安全红线（L1）**：绝不触碰的否定指令——"永不 rm"、"永不泄露密钥"
2. **指令优先级**：安全红线 > 工程约束 > 行为准则 > 系统默认（负面指令 > 正面指令；具体 > 模糊）
3. **权限分级**：工具调用按"允许/询问/拒绝"分级，高危操作拦截
4. **授权语义 SDK 级化**：approval 绑定具体调用，而非一次性授权
5. **敏感信息保护**：密钥/令牌永不写入记忆或文档

**提示注入防护**：外部内容（网页/文档/邮件）不可直接作为指令执行——本系统对 import 素材实施"批判性使用"约束（素材 ≠ 结论，关键数据必须交叉验证）[来源: 本系统 RULE.md]。

### 4.5 组织挑战：采纳与信任

**采纳方法论** [来源: 知识库 AI 采用方法论]：
1. **探索优先于卡收益**：收益曲线不可知，先用起来建立价值地图，再算账
2. **创造优先于验证**：查新是相似性搜索不是新颖性判定，做起来优于查起来
3. **创作优先于修补**：AI 天然滑向小修小补（边界清晰、验收容易），要用"任务重定义"引导创作
4. **adoption ≠ usage**：个人 loop → 永久交接 → 团队规范，只有第三层持久

**信任链三级** [来源: 知识库 Agent 产出信任链]：
- **可追溯**：每条产出能追溯到输入与过程
- **可审查**：关键产出有人工审查点
- **可审计**：全流程留痕，签名提交

**本系统实证**：AI 产出 = 毛利非净利——AI 自报收益不可靠（仅 31% 有测量），收益要由用户聚合统计；约束脚本化（check 工具）是最高杠杆 [来源: 知识库 AI 产出统计铁律]。

## 5. 好的工程实践（本系统 + spec 提炼）

### 5.1 本系统架构：四文件分级 + 三层记忆

本系统（Cow）是"AI × 知识管理"实证系统，运行 200+ 天，913+ commits / 2700+ 知识文件。其工程实践可提炼为可复制的模式：

**① 四文件分级（提示词工程的系统化）**：
- `AGENT.md`（人格/行为准则）→ `USER.md`（用户偏好/质量标准）→ `RULE.md`（规则/存储/红线）→ `MEMORY.md`（长期记忆索引）
- 设计原则：**按"稳定性 × 作用域"分级**——季更/年更/低频/月更，高频动态信息绝不污染低频稳定指令

**② 三层记忆（上下文工程）**：
- `MEMORY.md`（长期索引）→ `memory/YYYY-MM-DD.md`（每日事件）→ `knowledge/`（结构化知识库）
- 写入规则：按信息变化频率匹配位置（超 1 周不该放 memory/，少 1 个月不该放 MEMORY.md）

**③ 知识库三件套（Graph 工程）**：
- `README.md`（条目库）/ `index.md`（全局索引）/ `log.md`（变更日志）——三文件职责分离
- 纪律：三文件禁止 AI 直接编辑，统一走脚本（kb-log-append.py 追加 log，kb-global-index.py 刷新 index）——**把"状态管理"从人脑搬进脚本**

### 5.2 spec 体系：五层流转 + 约束注册表

本系统 spec/ 是**单一架构真相源**（41 活跃文件 ~29,160 行），五层流转 [来源: spec/README.md]：

```text
sr-xxx (req spec) -> std-xxx (eng standard) -> ar-001 (req mapping) -> design-xxx (design) -> impl (scripts/skills)
```

**五层流转的价值**：
1. **需求可追溯**：每个设计决策能回溯到原始需求（SR→AR→Design 双向追溯）
2. **标准可执行**：工程标准（std-xxx）直接约束落实层的脚本与技能
3. **一致性可检测**：spec-consistency-checker 六层检测闭环（L1 AR 映射 → L6 跨层引用）

**约束注册表（sr-003）**：`CCLRR` 编码（Category × Level × Range × RR），四层优先级（L0 安全红线 → L3 工程约束），约束冲突有解决机制，"找不到对应约束"有决策树。

**可复制要点**：小团队也可以建"轻量 spec"——一份需求清单 + 一份标准规范 + 一份设计记录，三级即可，关键是**让 AI 的工作有据可依、有迹可循**。

### 5.3 关键方法论提炼

| 方法论 | 位置 | 一句话 | 适用场景 |
|:-------|:-----|:-------|:---------|
| 三阶段分离协议 | meth-007 | 方向探索→方向锁定→细节精调，基线冻结后只增量 | AI 生成需要精度的文档/代码 |
| 八部件定义法 | meth-013 | Trigger/Planner/State/Workers/Evaluator/Loop/Stop-Resume/Repeatability | 设计 workflow/自动化任务 |
| 七 Phase 流水线 | meth-016 | 目标→地基→四文件→技能→流程→检查→迭代 | 从零搭建 AI 工作系统 |
| 多源验证 | 知识质量方法论 | 关键事实 ≥2 独立源交叉验证 | 任何涉及量化数据的产出 |
| 三层质量模型 | meth-011 | L1 产出快检（≤10%）+ L2 专业补齐 + L3 专项深修 | 文档质量管理 |
| 前后移分析 | shift-left-right | 前移把判断责任交给执行者，接纳度=能力×利益×容错÷恐惧 | 流程/责任变更决策 |
| 倒 U 投资律 | inverted-u | 投入不是越多越好，存在最优区间 | 资源分配决策 |
| 三阶段闭环 | 文档生产 | 生成时格式约束→生成后 check→批量修复 | 任何文档生产 |

### 5.4 可复制的落地清单

**团队 AI 使用规范草案（可直接采用）**：

| # | 规范 | 要点 |
|:-:|:-----|:-----|
| 1 | 规则先行 | 项目根目录建 AGENTS.md（角色+约束+常用命令），团队共享 |
| 2 | 先查再写 | AI 生成前先检索已有知识/代码，禁止重复造轮子 |
| 3 | 数据纪律 | 量化数据必须 来源+基线+条件 三要素；禁止编造 |
| 4 | 验证习惯 | 关键事实多源交叉验证；AI 自查 ≠ 人工确认 |
| 5 | 成本意识 | 长任务分段、缓存复用、上下文预算 |
| 6 | 权限分级 | 高危操作（删除/覆盖/生产改动）必须确认点 |
| 7 | 沉淀闭环 | AI 产出有价值的 → 归档知识库/代码库 + 更新索引 |
| 8 | 迭代打磨 | 一次不是终点，创建→审查→修正→再审查 |

**个人 AI 使用自检（每次任务后）**：
- [ ] 这次任务 AI 产出是否符合验收标准？
- [ ] 关键断言有出处吗？数据有基线吗？
- [ ] 有没有"看起来完成了但实际没验证"的部分？
- [ ] 这次的经验值得沉淀到知识库/规范吗？

### 5.5 团队落地路线图

| 阶段 | 时间 | 目标 | 关键动作 |
|:-----|:-----|:-----|:---------|
| 探索期 | 第 1-2 周 | 建立价值地图 | 全员用 AI 工具处理日常任务，记录收益与痛点 |
| 规范期 | 第 3-4 周 | 形成团队规范 | 落地 §5.4 清单草案，建 AGENTS.md 模板 |
| 固化期 | 第 2-3 月 | 工具化 | 高频任务脚本化（修补工具化=确定性外壳），建 check 门禁 |
| 深化期 | 第 3-6 月 | 知识资产化 | AI 产出沉淀知识库，形成团队知识飞轮 |

**关键提醒**：AI 采用是"探索优先于卡收益"——先用起来发现机会点，而不是一上来就要求 ROI 证明；收益是探索的函数不是计算的函数 [来源: 知识库 AI 采用方法论]。
