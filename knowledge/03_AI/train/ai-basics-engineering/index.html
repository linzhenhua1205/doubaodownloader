一句话主线

AI 是概率内核，工程是确定性外壳。所有 AI 使用方法的本质是同一个：把不确定性限制在模型推理边界内——越靠近模型（提示词）越软、越概率化；越靠近工程（Harness/Graph）越硬、越确定性。

好的 AI 使用者不是"会写提示词的人"，而是知道哪些该交给模型、哪些该搬进代码/流程的人。

01 · AI 基础概念

1.1大模型（LLM）是什么

基于海量文本训练、以"预测下一个 token"为核心任务的概率模型。它不是数据库，不"存储"事实，而是学会了语言与知识的统计规律，推理时按概率生成。

特性含义对使用者的影响
概率生成每次输出可能不同同一请求多次回答可能不一致 → 需要验证/基准
上下文窗口一次能"看到"的 token 上限长文档要分段/检索，超限会遗忘
幻觉生成看似合理但不真实的内容关键事实必须交叉验证，禁止直接采信
指令遵循遵循提示词中的规则与约束约束写得越明确，执行越可靠
上下文学习从上下文中即时学习（few-shot）给示例比给描述更有效

能力边界判断（务实视角）

✅ 擅长

  • 模式匹配 / 语言组织
  • 知识回忆 / 代码生成

⚠️ 不擅长

  • 精确计算 / 事实核查
  • 时间敏感信息 / 专有领域深度推理

判断任务是否适合 AI：是否依赖模式而非精确性？是否有明确验收标准？

01 · AI 基础概念

1.2提示词（Prompt）：分级注入的认知基座

提示词不是"写更好的话"，而是按稳定性 × 作用域把信息切分——让高频动态信息不污染低频稳定指令。

层次内容示例
角色/人格你是谁、什么风格"你是服务器硬件专家，用中文回答，技术术语保留原词"
任务/指令做什么、做到什么程度"分析这份 BOM 的供应风险，输出表格，标注数据来源"
约束/格式不做什么、输出格式"禁止编造数据；量化必须有来源+基线+条件；输出 Markdown"

实用模板（本系统实证）+ 关键技巧

📋 五要素模板

  • 任务：动词开头，一次一个目标
  • 背景：只给相关的，不放无关历史
  • 约束：用"禁止/必须"表达
  • 输出格式：Markdown/表格/代码块
  • 验收标准：可自检的清单

💡 五技巧

  • 清晰直接：说做什么也说做到什么程度
  • 示例驱动：1-3 个示例 > 长篇描述
  • 结构化组织：XML 标签/分段/编号
  • 上下文管理：长文档前置 + 分段加载
  • 迭代评估：小评估集 + 回归，提示词做版本管理
01 · AI 基础概念

1.3Skills（技能）：按需加载的声明式技能包

Skill = SKILL.md + 参考文件，包含触发条件、执行步骤、产出规范，Agent 按任务相关性自动加载。它是"会做什么"的动态能力，区别于规则文件的"你是谁"的静态约束。

载体回答的问题加载机制典型内容
规则文件（RULE.md/AGENTS.md）你是谁、必须守什么规矩常驻（全量加载）行为准则、文件操作铁律
Skills（SKILL.md）你会做什么、怎么做按需加载（先扫描描述，仅相关时加载详情）工作流步骤、质量标准、检查清单
提示词（对话中）这次任务怎么做会话内任务指令、上下文

💰 为什么按需加载重要

Token 成本。本系统实证：技能描述裁剪收益极低，但按需加载机制本身是最大节约杠杆——规则全量 vs 技能按需，是 Claude Code 与 Trae 共同的设计。

🔧 Skill 设计四法门（提升遵守率）

  • 重复：关键约束多次出现，强化信号
  • 强调：用"必做/禁做"标记优先级
  • 小型化：要点化，降低认知负载
  • 分层：按认知负载分级（核心/扩展/参考）
01 · AI 基础概念

1.4MCP：统一 AI 与工具/数据源的连接协议

MCP（Model Context Protocol）是 Anthropic 2024 年提出的开放标准协议——把"每个模型为每个工具写适配器"（N×M）简化为"工具实现一次 Server，任意 Client 都能用"（N+M）。

🧩 解决的核心问题

# Without MCP: each Agent x each tool = N x M adapters
Agent-A --> tool-1 adapter
Agent-A --> tool-2 adapter
Agent-B --> tool-1 adapter   # 每对都要写

# With MCP: tool writes Server once = N + M
tool-1 --> MCP Server (once)
Agent-A --> MCP Client --> Server
Agent-B --> MCP Client --> Server  # 全部复用

🎭 三种角色

  • MCP Server：暴露工具/数据源的标准化服务（文件系统/数据库/GitHub）
  • MCP Client：Agent 侧连接 Server 的客户端
  • Host：被其他 Agent 调用的宿主（Claude Code 双角色之一）

🔗 与 Skills/工具的关系

  • Skills 管方法（怎么做）· MCP 管连接（能连什么）· 工具管执行（开箱即用）

授权语义演进：MCP 授权正在 SDK 级化——approval 绑定到具体调用、hosted MCP server identity 成为安全基础。

🧠 Memory 只存陈述性记忆

做事方法一律进 Skill——"知识"与"方法"分离，避免记忆污染

"AI 自治度上限"与"Harnessability"框架——先判断能否交给 AI、能自治到什么程度

五引擎迁移到办公场景

办公场景五引擎应用本系统实证
会议纪要提示词模板（角色+结构）+ 上下文（只给相关材料）每日记忆 + 会话分析
汇报材料图工程（大纲→章节→成稿三段闭环）+ 检查点文档生产三段闭环

办公 AI 黄金法则：输入侧治理先于输出侧优化——先查再写（检索已有知识）比写完再改（生成后修正）成本低一个数量级。

2.3Rule 与 Spec：让 AI 懂规矩

📜 Rule：四文件分级（本系统范例）

文件内容更新频率
AGENT.md人格、交流风格、行为准则季更
USER.md用户身份、偏好、质量标准年更
RULE.md工作空间规则、存储规则、安全红线低频
MEMORY.md长期记忆索引、决策、教训月更

关键设计：按"稳定性 × 作用域"分级——高频动态信息（每日记忆）不进低频稳定指令（AGENT.md）

📐 Spec：任务规格化为共同契约

形态代表机制
三文档组Trae Specspec.md（大纲）+ tasks.md（任务）+ checklist.md（验收）
规格驱动Qoder Spec先规格后编码，规格即文档
系统级规格本系统 spec/sr→std→ar→design 五层流转

Spec 的价值：任务清单防目标漂移，验收清单防"看起来完成了"，版本控制提供可恢复性

一句话：Rule 管"你是谁、守什么规矩"（静态约束常驻），Spec 管"这次任务做到什么程度"（动态契约按任务建立）——两者互补，共同把 AI 的自由发挥约束在边界内。

02 · 编程与办公

2.4实操清单：今天就能用

💻 编程场景

  • 项目根目录放 AGENTS.md（或 CLAUDE.md），声明角色+约束+常用命令
  • 复杂任务用 Spec/Plan 工作流，先生成计划确认再执行
  • 关键决策要求 AI 给依据（文件路径/行号），不轻信"我改好了"
  • 高危操作（删除/覆盖/生产改动）在 Harness 层设确认点

📄 办公场景

  • 文档生成前先检索知识库（先查再写）
  • 量化数据要求来源+基线+条件，禁止裸数字
  • 长文档分段处理，每段独立验收
  • 周报/月报等重复任务用模板+定时（Loop 化）

核心原则：AI 的产出要"可验证、可追溯、可恢复"——凡是不能被这三条约束的用法，都要先补上约束再用。

03 · 编程范式

3.1范式全景与确定性谱系

五种工程/范式不是并列功能，而是五个正交视角，按确定性谱系排列：

Soft (probabilistic) ----------------------------------> Hard (deterministic)
Prompt --> Context --> Loop --> Harness --> Graph
(think)    (see)      (keep     (act       (fix flow)
                       thinking  safely)
范式回答的问题管理对象确定性失效模式
提示词模型怎么想？指令/人格/约束软指令漂移、上下文膨胀
上下文模型看什么？输入空间（窗口/记忆/检索）软超限、遗忘、成本失控
Loop怎么持续想？推理循环（感知→规划→行动→观察）中死循环、目标漂移、提前收工
Harness怎么安全地做？工具面/权限/持久化/事件硬工具滥用、状态丢失、不可审计
Graph流程怎么固化？状态/边/检查点/人工介入点最硬过度设计、图腐化、可恢复失败
03 · 编程范式

3.2问答范式 + 3.3 Loop 工程

💬 问答范式（基础）

单轮/多轮对话，模型直接回答。无工具、无循环、无状态管理。

  • 适用：知识问答、文案生成、思路讨论、代码片段建议
  • 优势：零门槛、快速
  • 局限：无工具执行、无记忆持久化、无验证闭环、长任务易漂移
  • 最佳实践：把问答当"思考伙伴"而非"执行者"——执行交给更高范式

🔄 Loop 工程（Agent 心脏）

所有 Agent 共享同一循环：感知→规划→行动→观察。管"怎么持续想"。

  • ① 显式终止条件：完成/最大迭代/人类干预——没有终止条件 = 死循环或烧钱
  • ② 想/做分离：Plan Mode（先只读分析出计划，批准后执行）
  • ③ 防目标漂移：TodoWrite/任务清单显式化
  • ④ 长视界：单一上下文多轮迭代（Claude Code Long Horizon 150 轮）

本系统实证：每日定时任务（周报/日报）就是 Loop 工程——scheduler 触发 → 数据拉取 → 聚合 → 成文 → 检查 → 推送，全自动循环。

03 · 编程范式

3.4Harness 工程：确定性外壳

Harness = 让 Agent 更有组织地干活的确定性外壳——任务怎么拆、Agent 怎么调用、上下文怎么隔离、结果怎么合并、中断后怎么恢复、动作怎么授权。

🧰 工具面

  • 文件/终端/检索/网络内置工具
  • 权限分级：允许/询问/拒绝

🪝 Hooks（7 类）

  • PreToolUse/PostToolUse/Stop 等
  • 审计/拦截/通知从主循环剥离，事件驱动确定性执行

👥 Subagents

  • 声明式子代理，独立上下文
  • 隔离目的 = 防上下文污染

💾 Checkpoints + MCP 双角色

  • 会话检查点，中断后恢复
  • Client（接外部 server）+ Host（被调用）

Harness 的本质价值：把"与推理无关但必须发生的动作"（审计/拦截/通知/持久化）从主循环剥离，用代码确定性执行——模型负责想，Harness 负责保证想的动作安全落地。

本系统实证：scheduler 定时任务 + RULE.md 安全红线 + git 自动提交 = Harness 的调度/约束/审计三件套

✅ 适用判据

🛣️ 两种实现路线

  • 文档驱动派（Trae/Qoder）：spec/tasks/checklist 三文档作为共同契约，人可读可编辑

本系统实证：知识库三同步（README/index/log 三文件职责分离 + 脚本批量刷新）= Graph 工程——状态 schema（三文件职责）× 拓扑（归档路径注册表）× 检查点（git 提交）× 人工介入（文件操作铁律）。

04 · 关键挑战

4.1挑战总览 + 4.2 质量挑战：幻觉与精度

1️⃣ 幻觉与精度

概率生成 ≠ 事实

应对：验证方法论 + 多源交叉

2️⃣ 上下文稀缺

窗口有限 + token 成本

应对：上下文工程 + 成本监控

3️⃣ 权限与越权

Agent 工具滥用

应对：Harness 权限分级 + Hooks

4️⃣ 采纳与信任

组织拒绝或盲目信任

应对：采纳方法论 + 信任链

本系统方法论：多源验证

🔍 多源三角验证

  • 关键事实 ≥2 个独立源交叉验证；素材与验证源冲突时以验证源为准
  • 正反验证：正向（数据→结论）+ 反向（结论回溯证据）

📝 溯源标注 + 禁止编造

  • 每条断言标注出处；无法溯源标记为"推断"或删除
  • 数据无法获取时：标注缺口 + 说明尝试了哪些源 + 替代估算，绝不编造

精度控制：三阶段分离协议

PHASE 1
方向探索
自由宽泛
→
PHASE 2
方向锁定
刚性冻结 + 批准基线协议
→
PHASE 3
细节精调
基线协议 + 不可变区域声明

反模式：全量重生成——每改一次全量重来 = 每次都在引入新错误。正解：质量规则脚本化（check 工具/门禁），比依赖 AI 自检可靠——"规则脚本化 = 确定性地把质量标准前移"。

04 · 关键挑战

4.3上下文挑战：稀缺资源管理

上下文是稀缺资源——窗口物理极限 + token 成本。本系统实证：27 天 2.3B tokens，缓存未命中 58% 是最大成本项。

🧰 上下文工程四层策略

策略做法
截断超长结果保留首尾+省略说明（纯字符串，不调 LLM）
裁剪以完整轮为单位裁掉最早一半 + 提炼总结写记忆
压缩每轮只留首条提问+末条回复
兜底API 抛溢出时总结后激进截断

💰 成本优化杠杆（按收益排序）

  • ① 合并 session（减少请求数）
  • ② 减请求（少问、问对的）
  • ③ 缩输出（限制长度、结构化输出）
  • ④ Prompt Caching（前缀缓存复用）

🧠 记忆分层

高频动态（每日记忆）→ 低频稳定（长期记忆）→ 永久事实（知识库）——按"稳定性 × 作用域"分层，避免污染与膨胀

04 · 关键挑战

4.4安全挑战 + 4.5 组织挑战

🔐 安全：权限与越权

现象：Agent 越权访问、工具滥用、提示注入、假身份冒充

  • 安全红线（L1）：绝不触碰的否定指令——"永不 rm"、"永不泄露密钥"
  • 指令优先级：安全红线 > 工程约束 > 行为准则 > 系统默认
  • 权限分级：工具调用按"允许/询问/拒绝"分级，高危操作拦截
  • 授权语义 SDK 级化：approval 绑定具体调用，而非一次性授权
  • 提示注入防护：外部内容（网页/文档/邮件）不可直接作为指令执行——素材 ≠ 结论，关键数据必须交叉验证

🤝 组织：采纳与信任

采纳方法论（本系统实证）

  • 探索优先于卡收益：收益曲线不可知，先用起来建立价值地图
  • 创造优先于验证：做起来优于查起来
  • 创作优先于修补：用"任务重定义"引导创作
  • adoption ≠ usage：个人 loop → 永久交接 → 团队规范，只有第三层持久

🔗 信任链三级

可追溯
产出能追溯到输入与过程
→
可审查
关键产出有人工审查点
→
可审计
全流程留痕，签名提交

本系统实证：AI 产出 = 毛利非净利——AI 自报收益不可靠（仅 31% 有测量），收益要由用户聚合统计；约束脚本化（check 工具）是最高杠杆。

05 · 工程实践

5.4可复制落地清单 + 5.5 团队路线图

📋 团队 AI 使用规范草案（8 条）

  • 1 规则先行：项目根目录建 AGENTS.md（角色+约束+常用命令），团队共享
  • 2 先查再写：AI 生成前先检索已有知识/代码，禁止重复造轮子
  • 3 数据纪律：量化数据必须 来源+基线+条件 三要素；禁止编造
  • 4 验证习惯：关键事实多源交叉验证；AI 自查 ≠ 人工确认
  • 5 成本意识：长任务分段、缓存复用、上下文预算
  • 6 权限分级：高危操作（删除/覆盖/生产改动）必须确认点
  • 7 沉淀闭环：AI 产出有价值的 → 归档知识库/代码库 + 更新索引
  • 8 迭代打磨：一次不是终点，创建→审查→修正→再审查
