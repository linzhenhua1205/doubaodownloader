## §1 背景引入：超节点定义与存储设计点

> 来源: [超节点定义深度分析](../../../02_rd/02_project/01_superpod/architecture/2026-07-28-supernode-definition-and-design-philosophy.md) §1.4 四层架构模型 + §2.2 互联网络维度

### 1.1 超节点的四层架构模型中的存储位置

```text
+-------------------------------------------------------------+
|  第四层：扩展模式                                            |
|  超节点内 Scale-Up 紧耦合 + 超节点间 Scale-Out 横向扩展       |
|  存储需求：存储网需同时支持域内（紧耦合）和域间（松耦合）流量 |
+-------------------------------------------------------------+
|  第三层：系统软件与调度（工程落地关键）                        |
|  ① 全域统一资源抽象 — 存储资源也纳入统一管理                   |
|  ② 拓扑感知调度 — 存储 placement 感知计算拓扑                 |
|  ③ 分层 RAS — 存储故障域隔离                                 |
+-------------------------------------------------------------+
|  第二层：内存架构（最核心）                                    |
|  ① 全局内存池 -> KV Cache 在超节点内全局共享                   |
|  ② 内存语义访问 -> 存储网需支持 RDMA 直通 GPU                  |
|  ⚠️ Checkpoint/训练数据不要求内存语义，但 KV Cache 需要       |
+-------------------------------------------------------------+
|  第一层：硬件互联（基础条件）                                  |
|  ① 紧耦合高速专用互联 — 计算网（NVLink/HCCS）                |
|  ② ⭐ 存储网 — 独立于计算网/管理网/同步网的第四类网络         |
|  ③ 亚微秒级域内延迟 — 存储网需求为 μs 级                     |
+-------------------------------------------------------------+
```

### 1.2 从超节点定义提炼的 8 个存储设计点

| # | 设计点 | 来源 | 技术含义 |
|:-:|:-------|:-----|:---------|
| **D1** | **统一资源抽象** | §1.4 — 第三层系统软件 | 存储资源（SSD 池、NVMe 命名空间）需被上层调度框架抽象为统一资源视图，计算节点不应感知物理存储拓扑 |
| **D2** | **存储网独立于计算网** | §2.2 — 四类流量分离 | 存储流量（Checkpoint/KV Cache/数据加载）不应与计算流量（AllReduce/AllGather）争抢同一网络带宽 |
| **D3** | **全局内存池化的存储支撑** | §2.1 — 统一内存编址 | KV Cache 的全局共享需要存储层提供跨节点的低延迟读/写能力，必须支持 RDMA GPU Direct |
| **D4** | **拓扑感知存储放置** | §1.4 — 拓扑感知调度 | KV Cache 的冷热数据需与 GPU 计算拓扑对齐，跨机架 vs 同机架拉取延迟差异需被调度感知 |
| **D5** | **分层 RAS 的存储维度** | §1.4 — 4 层故障隔离 | 存储故障（SSD 损坏、NVMe 队列挂死、DPU 故障）需要独立的故障检测和恢复路径 |
| **D6** | **Scale-Up/Out 双模存储** | §2.4 — 扩展交付 | 超节点内部存储带宽需 Scale-Up（多 GPU 并发读写单存储池），超节点间需 Scale-Out（集群级 Checkpoint 聚合） |
| **D7** | **流量优先级分离** | §2.2 — 硬件级流量整形 | 存储网内三种流量优先级：KV Cache 预取 > KV Cache 卸载 > 数据加载 > Checkpoint |
| **D8** | **与系统软件协同** | 误区 6 — 软件深度 | 存储方案不能独立设计，需与 Dynamo 等价调度框架、冷热评分、预取策略深度耦合 |

### 1.3 关键启示

> **存储不是在超节点中"加一套 NAS"**，而是与计算紧密耦合的**智能存储层**，核心特征：
>
> 1. **RDMA GPU Direct 直通** — 数据不经主机 CPU/内存直达 GPU HBM
> 2. **KV Cache 感知** — 支持 Block 级而非文件级操作，理解 KV 语义
> 3. **拓扑感知 Placement** — 冷数据放在离计算最近的存储节点
> 4. **无冗余设计** — KV Cache 的 ephemeral 属性允许去掉传统存储的 replication/RAID 开销

## §2 从系统指标到存储硬件指标：带宽·延迟·容量

### 2.1 系统级指标拆解

> 本节提供通用化的系统→存储指标映射框架。§4 将基于 KLX 512 GPU 超节点的具体参数做精细化带宽链分析。

| 系统指标 | 典型值 | 存储需求推导 |
|:---------|:-------|:------------|
| **GPU 总数** | 256~512 卡 | — |
| **KV Cache 总量**（推理场景） | ~512 GB - 2 TB（128K~1M 上下文） | 存储网需支持 **TB 级** KV Cache 读写 |
| **训练 Checkpoint** | 模型权重 ~700 GB (70B) - 10 TB (1T MoE) | Checkpoint 总容量 ~1-10 TB |
| **训练数据加载** | 每 epoch ~100 TB+ | 持续流式读取，带宽需求高 |

### 2.2 带宽需求逐项计算

#### ① 训练数据加载带宽

| 参数 | 值 | 说明 |
|:-----|:---|:------|
| 单 GPU 训练数据吞吐 | ~2-5 GB/s | 持续读取训练样本 |
| 256 GPU 总带宽 | **512-1,280 GB/s** | 线性扩展 |
| 存储网承载比例 | 50%（另一半可在本地缓存） | — |
| **训练数据加载净需求** | **~256-640 GB/s** | 持续负载 |

#### ② Checkpoint 持久化带宽

| 参数 | 值 | 说明 |
|:-----|:---|:------|
| Checkpoint 大小 (70B) | ~700 GB | 模型权重 + optimizer state |
| Checkpoint 大小 (1T MoE) | ~10 TB | — |
| 目标写入时间 | ≤60s | 业界常用要求 |
| **所需带宽 (70B)** | **~11.7 GB/s** | 700 GB / 60s |
| **所需带宽 (1T MoE)** | **~167 GB/s** | 10 TB / 60s |

#### ③ KV Cache 卸载/预取带宽

| 参数 | 值 | 说明 |
|:-----|:---|:------|
| 单 GPU KV Cache 生成速率 | ~50-200 MB/s | 持续 decode 阶段 |
| 256 GPU 总 KV 卸载带宽 | **12.8-51.2 GB/s** | 持续卸载 |
| 预取带宽（Prestaging） | 1-2× 卸载带宽 | 预取需要更高带宽 |
| **KV Cache 净需求** | **~25-100 GB/s** | 卸载 + 预取 |
| 延迟要求 | <10μs（预取），<100μs（卸载） | 对延迟敏感 |

#### ④ 总带宽需求汇总

| 流量类型 | 持续需求 | 峰值需求 | 延迟敏感度 |
|:---------|:--------|:--------|:----------:|
| 训练数据加载 | ~256-640 GB/s | ~500-1,000 GB/s | 🟡 中（可预取缓冲） |
| Checkpoint 持久化 | ~12-167 GB/s | ~35-500 GB/s | 🟢 低（可等调度） |
| KV Cache 卸载 | ~13-51 GB/s | ~25-100 GB/s | 🔴 高（影响推理延迟） |
| KV Cache 预取 | ~25-100 GB/s | ~50-200 GB/s | 🔴 极高（需提前到达） |
| **存储网总带宽需求** | **~300-950 GB/s** | **~600-1,800 GB/s** | — |

### 2.3 延迟需求

| 流量类型 | 端到端延迟要求 | 存储网贡献延迟 | 说明 |
|:---------|:-------------|:--------------|:------|
| 训练数据加载 | <100ms | <10μs | 通过预取缓冲吸收 |
| Checkpoint 写入 | <60s | <100ms | 吞吐优先，延迟可容忍 |
| KV Cache 卸载 | <100μs | <10μs | **关键路径**，影响 decode 延迟 |
| KV Cache 预取 | <50μs | <5μs | 必须在 decode 前完成 |

### 2.4 从系统指标到硬件的映射关系

```text
带宽需求: 300-1,800 GB/s
  v
网络端口数 × 端口速率 ≥ 总带宽
  v
延迟需求: 存储网 <10μs
  v
需要 RoCEv2 / InfiniBand / NVMe-oF RDMA，排除 TCP/IP + 传统 NAS
  v
容量需求: 50-500 TB
  v
JBOF 数量 × 盘数 × 单盘容量 ≥ 目标容量
```

## §3 超节点四网中的存储网架构权衡

### 3.1 超节点四网架构总览

```text
超节点内部网络架构（四网分离）

+-------------------------------------------------------------+
|  ① 计算网 (Compute Fabric)                                 |
|  GPU-GPU AllReduce/AllGather/ReduceScatter                  |
|  NVLink 5 (200GB/s per link) / HCCS / UALink               |
|  延迟~200ns, 带宽 TB/s 级                                   |
+-------------------------------------------------------------+
|  ② 存储网 (Storage Fabric)        <- 本期培训重点           |
|  GPU↔NVMe SSD 数据传输                                     |
|  训练数据加载 / Checkpoint 持久化 / KV Cache 卸载            |
|  RoCEv2 / NVMe-oF / GPUDirect Storage                      |
|  延迟~μs级, 带宽~100-1,000 GB/s                             |
+-------------------------------------------------------------+
|  ③ 管理网 (Management Fabric)                              |
|  节点状态/健康心跳/配置同步                                  |
|  1 GbE / 10 GbE, 延迟不敏感                                |
+-------------------------------------------------------------+
|  ④ 同步网 (Sync Fabric)                                    |
|  时钟同步/全局 Barrier                                      |
|  PTP / InfiniBand, 延迟~50ns                               |
+-------------------------------------------------------------+
```

### 3.2 存储网架构的核心权衡维度

#### 权衡 1：存储网与计算网的关系

| 选项 | 融合（共用计算网） | 独立（专有存储网） |
|:-----|:-----------------|:-----------------|
| **架构** | 存储流量走计算网的剩余带宽 | 独立物理网络，存储独占带宽 |
| **优点** | 节省交换机端口；布线简单 | 不干扰计算流量；可独立优化 |
| **缺点** | 存储流量与 AllReduce 竞争带宽 | 额外网络硬件成本 |
| **适用场景** | 小规模集群（≤64 GPU） | **超节点（≥256 GPU）必需** |

#### 权衡 2：存储网拓扑

| 选项 | Leaf-Spine (CLOS) | Torus |
|:-----|:-----------------|:------|
| **扩展性** | ★★★★★ 易扩展 | ★★★ 扩展需重布线 |
| **延迟** | ★★★☆ 2-3跳 | ★★★★ 1-2跳 |
| **故障域** | ★★★★ 多路径冗余 | ★★★ 局部影响 |

> **推荐**: >128 GPU 用两层 Leaf-Spine CLOS（延迟 2-3μs），≤128 GPU 可考虑 3 级 Torus

#### 权衡 3：计算侧连接方式

```text
方式 A: GPU -> PCIe Switch -> DPU -> 存储网  <- 推荐
         优点: DPU 可做卸载/加速
方式 B: GPU -> PCIe Switch -> NIC -> 存储网
         优点: 数据路径短，缺点: 无卸载能力
```

#### 权衡 4：存储侧架构

> **推荐**: **分布式 JBOF + DPU** 架构。每个存储节点（JBOF）包含 8-24 块 NVMe SSD + 2 块 BF4/IPU

### 3.3 存储网设计建议清单

```text
✅ 存储网独立于计算网（物理或逻辑）
✅ 使用 RoCEv2 / NVMe-oF RDMA 协议
✅ 计算节点通过 DPU (BF3/BF4/IPU) 接入存储网
✅ 存储侧采用分布式 JBOF 架构
✅ 支持 GPUDirect Storage (GDS) / GPU Direct RDMA
✅ 预留 1.5-2× 峰值带宽余量
✅ 流量优先级：KV Cache 预取 > KV Cache 卸载 > 数据加载 > Checkpoint
```

## §4 KLX 512 GPU 超节点存储带宽链深度分析

> ⭐ **核心新增章节**：基于 KLX 昆仑芯 512 GPU 超节点（128 节点 × 4 GPU/节点）的具体参数，对存储网络进行端到端带宽链分析。源材料：[KLX 存储带宽链分析](../../../02_rd/02_project/01_superpod/network/2026-07-01-08-klx-storage-bandwidth.md)

### 4.1 场景定义与端到端路径

#### 4.1.1 网络拓扑

```text
+-----------------------------------------------------------------------+
| KLX 128 nodes (512 GPU, 4 GPU/node) Supernode                         |
+-----------------------------------------------------------------------+
| Compute-1 (4xM300)    Compute-2 (4xM300)  ...  Compute-N (4xM300)    |
| +-----------+          +-----------+          +-----------+           |
| | 4xM300    |          | 4xM300    |          | 4xM300    |           |
| | CX7 x4   |          | CX7 x4   |          | CX7 x4   |           |
| | BF3/4    |          | BF3/4    |          | BF3/4    |           |
| | 1-2port  |          | 1-2port  |          | 1-2port  |           |
| +-----+----+          +-----+----+          +-----+----+           |
|       |                     |                       |               |
|       +---------------------+-----------------------+                |
|                           | Storage Network (RoCEv2 RDMA)           |
|                           v                                         |
|      +----------------------------------------------------+         |
|      |   Storage Network Fabric (2 Leaf × 64 ports)       |         |
|      +---------------------------+------------------------+          |
|                                  |                                    |
|                                  v                                    |
|      +----------------------------------------------------+         |
|      |   Storage Cluster (JBOF × 5-6)                     |         |
|      |   Each: 4×400G uplink, 24 × Gen5 NVMe SSD          |         |
|      +----------------------------------------------------+         |
+-----------------------------------------------------------------------+
```

#### 4.1.2 端到端数据路径

```text
GPU HBM -> PCIe -> BF DPU -> 400G NIC -> 交换机 -> 存储端NIC -> PCIe -> NVMe SSD
 ^ ^ ^ ^
 PCIe Gen5   网络端口   存储侧PCIe   NVMe SSD
(512Gbps)   (400Gbps)   (64GB/s)   (14/7 GB/s)
```

#### 4.1.3 修正后的关键假设

| 参数 | 修正值 | 说明 |
|:-----|:-------|:------|
| 节点数 | **128 节点** | 原误标 512 节点，修正为 128 节点 × 4 GPU |
| 总 GPU 数 | **512** | 不变 |
| 每节点 KV 写入 | **~4 Gbps** (4 × ~1 Gbps/GPU) | 原 ~1 Gbps |
| 每节点 Prestaging (稳态) | **~25.6 Gbps** (4 × 6.4) | 原 ~6.4 Gbps |
| 每节点 Prestaging (Burst) | **~160 Gbps** (4 × 40) | 原 ~40 Gbps |
| 每节点 Checkpoint | **~400 Gbps** (4 × 100 Gbps/GPU) | 逼近 400G 上限 |
| 集群总 KV 写入 | 512 Gbps | 总 GPU 数相同 |
| JBOF 推荐数 | **5-6 台** | 纯 KV 专用 1-2 台即可 |
| Leaf 交换机 | **2 台** | (128/64) |

### 4.2 组件规格与瓶颈预判

#### 4.2.1 BlueField-3 (BF3) DPU

| 规格项 | 数值 |
|:-------|:------|
| 以太网端口 | 2 × 400GbE |
| 单口吞吐 (有效) | ~376-384 Gbps (~47-48 GB/s) |

| 主机接口 | PCIe Gen5 ×16 (~64 GB/s / ~512 Gbps 单向) |
| KV 语义加速 | ❌ 不支持 |
| NVMe KV Ext | ❌ 不支持 |
| 典型功耗 | ~120W |

#### 4.2.2 BlueField-4 (BF4) DPU

| 规格项 | 假设值（保守） | 说明 |
|:-------|:-------------|:------|
| 以太网端口 | 1~2 × 800GbE (ConnectX-9) | BF4 = Vera CPU + ConnectX-9 SuperNIC |

| NVMe KV Ext | ✅ 原生 | — |
| GDS | ✅ cuFile 原生 | BF3 的一票否决解除 |
| 典型功耗 | ~150W+ | 含 Vera CPU + CX9 + LPDDR5X |

#### 4.2.3 NVMe SSD 与 JBOF 规格

| 规格项 | 数值 |
|:-------|:------|
| 单盘顺序读 | ~14 GB/s (峰值) / ~12 GB/s (持续) |
| 单盘顺序写 | ~7 GB/s |
| 单盘随机读 (4K) | ~3M IOPS |
| 读延迟 (QD1) | ~60-100μs |
| JBOF 盘位 | 24 × E3.S / U.2 |
| JBOF 上行 | 4 × 400G = 1,600 Gbps |
| 单 JBOF 总写带宽 | 24 × 7 GB/s = 168 GB/s = 1,344 Gbps |
| 单 JBOF 总持续读带宽 | 24 × 12 GB/s = 288 GB/s = 2,304 Gbps |

#### 4.2.4 JBOF 上行瓶颈判定

> **关键洞察**: JBOF 上行端口是读操作的瓶颈，盘写带宽是写操作的瓶颈。

**读场景**:

```text
JBOF 内部盘总读持续带宽: 24 × 12 GB/s = 288 GB/s
JBOF 上行总带宽 (4×400G): 4 × 40 GB/s (有效) = 160 GB/s
-> 上行端口只能传输内部盘 55.6% 的读能力
-> 4×400G 上行最多支撑: 160 GB/s / 12 GB/s/盘 ≈ 13.3 盘同时满速读
```

**写场景**:

```text
JBOF 内部盘总写带宽: 24 × 7 GB/s = 168 GB/s
JBOF 上行总带宽 (4×400G): 4 × ~376 Gbps = 1,504 Gbps = 188 GB/s
-> 上行端口带宽 > 盘总写带宽 ✅
-> 瓶颈在盘端
```

| 场景 | 瓶颈段 | 设计含义 |
|:-----|:-------|:---------|
| Read-heavy (Prestaging) | **JBOF uplink port** | 需更多上行端口或更少盘 |
| Write-heavy (Checkpoint) | **NVMe disk write BW** | 上行充足，需更快写盘 |

### 4.3 全链路瓶颈链逐段分析

#### 4.3.1 瓶颈链总览

```text
GPU HBM -> PCIe -> BF DPU -> NIC端口 -> 交换网络 -> 存储NIC端 -> JBOF PCIe -> NVMe SSD
 ^ ^ ^ ^ ^ ^ ^ ^
 A B C D E F G H
```

| 段 | 位置 | 典型带宽 | 瓶颈判断 |
|:--:|:-----|:---------|:---------|
| A | GPU HBM → PCIe | 取决于 GPU 配置 | ⚪ 待确认 |
| B | PCIe 链路 | BF3: 512 Gbps, BF4: 1024 Gbps | **BF3 twin-port 时瓶颈** |
| C | BF DPU 内部 datapath | BF3: 800 Gbps, BF4: ~1600 Gbps | ⚪ 一般不是瓶颈 |
| D | **NIC 端口** | 单口 400G / 双口 800G | 🟡 端口速率决定上限 |
| E | **交换网络** | 取决于 OS 比配置 | 🟡 配置不当可成瓶颈 |
| F | 存储端 NIC | 与 JBOF 上行端口数相关 | 🟡 JBOF 上行可能是瓶颈 |
| G | JBOF PCIe | 取决于 JBOF 控制器 | 🟡 需确认 |
| H | **NVMe SSD** | 单盘 14/7 GB/s | 🔴 **真实瓶颈** |

#### 4.3.2 节点级各段带宽

**BF3 单口 400G**:

| 段 | 带宽 | 瓶颈判断 |
|:---|:-----|:---------|
| BF3 PCIe Gen5 ×16 | 512 Gbps | ✅ 饱和 400G（余量 28%） |
| **400G NIC 端口** | **400 Gbps = 50 GB/s** | 🟡 节点级上限 |
| JBOF 上行 | 4×400G = 1,600 Gbps | 🟡 见匹配性分析 |

**BF3 双口 800G (Twin-port)**:

| 段 | 带宽 | 瓶颈判断 |
|:---|:-----|:---------|
| **BF3 PCIe Gen5 ×16** | **512 Gbps** | 🔴 **瓶颈**：不能饱和 800G 端口 |
| Twin-port 800G | 800 Gbps | 🟡 节点级上限 = PCIe 限制 512 Gbps |

**BF4 单口 800G**:

| 段 | 带宽 | 瓶颈判断 |
|:---|:-----|:---------|
| BF4 PCIe Gen6 ×16 | **1024 Gbps** | ✅ 饱和 800G（余量 28%） |
| **800G NIC 端口** | **800 Gbps = 100 GB/s** | 🟡 节点级上限 |

#### 4.3.3 存储后端盘带宽（集群视角）

| 场景 | 单节点需求 | 128 节点总需求 | 所需 JBOF 数 |
|:-----|:----------|:--------------|:------------|
| KV 写入（持续） | ~4 Gbps | ~0.5 Tbps | 1 台就够 |
| Prestaging（突发） | ~160 Gbps | ~20 Tbps | ~15 台（理论上限），实际 3-4 台 |
| **Checkpoint 写** | **~400 Gbps** | **~51 Tbps** | **38-39 台全并发极限**，滚动 checkpoint 3-4 台即可 |

> **JBOF 推荐**: 128 节点集群下 **5-6 台 JBOF 起步**。纯 KV Cache 专用 1-2 台即够，标准生产 3-4 台起步。

#### 4.3.4 交换网络带宽

| OS 比 | 总存储侧带宽 | 每节点平均可用 | 适用场景 |
|:------|:-----------|:-------------|:---------|
| **1:1**（无阻塞） | 51.2 Tbps | 400 Gbps | 极限场景 |
| **2:1**（标准） | 25.6 Tbps | 200 Gbps | ✅ **推荐** |
| **4:1**（经济） | 12.8 Tbps | 100 Gbps | KV Cache 专用 |

#### 4.3.5 全链路瓶颈汇总

| 场景 | 第一瓶颈 | 第二瓶颈 | 说明 |
|:-----|:---------|:---------|:------|
| **KV 写入（日常）** | 🟢 无瓶颈 | — | 流量 ~1 Gbps，链路 400 Gbps，余量 >50× |
| **KV Prestaging** | 🟢 无瓶颈（小规模） | 🟡 JBOF IOPS（大规模） | 读为主，JBOF IOPS 决定延迟 |
| **Checkpoint 写** | 🔴 **盘写带宽** | 🟡 **BF3 PCIe** | 此时 twin-port 有价值 |
| **大规模推理恢复** | 🔴 **盘读带宽** | 🟡 **JBOF 上行** | 多节点同时读可能导致拥塞 |

> 📌 **核心结论**: 对于 KLX 超节点的日常 KV Cache 场景，从 GPU HBM 到 NVMe SSD 的全链路**不存在带宽瓶颈**。最窄的链路段（400G 网络端口 = 50 GB/s）也比 KV 写入需求（~1 GB/s）大两个数量级。真正的系统瓶颈在 **IOPS 延迟**（NVMe SSD 的随机读延迟、BF3 ARM 的 KV→LBA 映射处理的软件开销），而非带宽。

### 4.4 KV Cache 带宽需求与 batch_size 敏感性

#### 4.4.1 基准场景 (batch_size=4)

| 指标 | 数值 | 400G 余量 |
|:-----|:-----|:---------|
| 每 GPU KV 写入 | ~1 Gbps | >50× |
| 每 GPU KV 读取 (Prestaging) | ~1-10 GB/s（突发） | >5× |
| Checkpoint 写 (per GPU) | ~100 Gbps（逼近 400G 上限） | ⚠️ 单口不够，需 twin-port |

#### 4.4.2 batch_size 敏感性扩展

| batch_size | 单次逐出大小 | 写入带宽 (100 tok/s) | 400G 占用率 | 余量 |
|:-----------|:-------------|:--------------------|:-----------|:-----|
| **4**（基准） | ~4 MB | ~1 Gbps | 0.25% | >50× |
| **16** | ~16 MB | ~4 Gbps | 1% | >12× |
| **64** | ~64 MB | ~16 Gbps | 4% | >3× |
| **128**（多租户） | ~128 MB | ~32 Gbps | 8% | >1.5× |
| **512**（极限） | ~512 MB | ~128 Gbps | 32% | >3× |

> **结论**: 链路带宽从不是 KV 写入的瓶颈——无论 batch_size 如何增长。

#### 4.4.3 唯一需要 twin-port 的场景

> 日常 KV 读写都不需要 twin-port。**只有 checkpoint/模型加载**这种需大带宽并发写的场景，twin-port 才有实际价值。

### 4.5 Prestaging 读取带宽模型

#### 4.5.1 三种 Prestaging 模式

| 模式 | 粒度 | 带宽需求 | 400G 占用率 |
|:-----|:-----|:---------|:-----------|
| **稳态 Sequential** | 8 MB/次, 100次/s | ~6.4 Gbps | 1.6% ✅ |
| **Burst Refill** | 20 prompt 同时回填 | ~10.2 Gbps | 2.6% ✅ |
| **128 节点全并发 Burst** | 64 节点 × 1.28 GB/s | ~656 Gbps | 2.7% 上行充裕 |

#### 4.5.2 Prestaging 关键结论

| 场景 | 瓶颈段 | 余量 |
|:-----|:-------|:----|
| 稳态 Sequential | 🟢 无瓶颈 | >50× |
| Burst Refill | 🟡 JBOF 上行端口 | ~10× |
| 128 节点全并发 Burst | 🟡 交换网络 OS 比 | ~10× |

> 🔑 **核心洞察**: Prestaging 的真正瓶颈不在带宽，在**延迟**——NVMe SSD 的顺序读延迟(~175μs) + BF3 ARM 的 KV→LBA 映射延迟(~1-3μs)。SSD 读延迟占全链路 ~95%。

### 4.6 读写混合瞬时带宽模型

#### 4.6.1 三种流量叠加

| 场景 | 流量组合 | 合计 | 400G 占用率 |
|:-----|:---------|:----|:-----------|
| 日常推理 | KV 写 + Prestaging 读 | ~12 Gbps | 3% ✅ |
| 高负载 | 大 batch + 突发读 | ~72 Gbps | 18% ✅ |
| Checkpoint + 推理 | Checkpoint + 日常 | ~58 Gbps | 14.5% ✅ |
| 全并发极限 | Checkpoint + Prestaging + KV 写 | ~142 Gbps | 35.5% ⚠️ |

#### 4.6.2 关键结论

| 流量组合 | 节点级 400G | 128 节点聚合 JBOF 上行 | 真实瓶颈 |
|:---------|:-----------|:---------------------|:---------|
| 日常推理 | ✅ 3% | ✅ 充裕 | 无 |
| 高负载 | ✅ 18% | ✅ 仍充裕 | IOPS 延迟 |
| Checkpoint + 推理 | ✅ 14.5-35% | 🔴 热点 JBOF 可能瓶颈 | JBOF 上行 + SSD 带宽 |

### 4.7 非均匀分布下的热点重评估

> "4:1 OS → 每节点平均 100 Gbps"在统计意义上正确，但在最坏情况下某台 JBOF 的上行端口可能承受预期 3-5× 的流量。

**128 节点热点场景**:

```text
条件: 5 台 JBOF, 18 节点集中到 1 台 JBOF (哈希偏斜)
每节点流量: 50 Gbps (40 checkpoint + 10 KV 日常)
JBOF 上行需求: 18 × 50 = 900 Gbps
JBOF 上行容量: 4 × 400G = 1,600 Gbps
-> 上行占用率: 56.3% ✅

虚拟节点 ×256 缓解后: 偏斜率 30% -> 8%，上行占用率降至 25-31%
-> ✅ 128 节点下热点风险从"需分流"降级为"通过虚拟节点可管理"
```

### 4.8 带宽链核心结论

**128 节点修正后全链路瓶颈排序**:

| # | 瓶颈段 | 带宽 | 128 节点判断 |
|:-:|:-------|:-----|:------------|
| 1 | 🟢 **网络端口** | 400 Gbps | 日常 **>100× 余量** |
| 2 | 🟢 **交换网络 OS** | 2:1 OS → 200 Gbps/节点 | 绰绰有余 |
| 3 | 🟢 **JBOF 上行** | 4×400G = 1,600 Gbps | 热点最坏 ~58%，虚拟节点后 25-31% |
| 4 | 🟡 **NVMe SSD 写入池** | 72-168 GB/s | checkpoint 密集需注意 |

> **最终结论**: 128 节点 × 4 GPU 规模下，KV 日常场景从节点端口到交换网络到 JBOF 上行的全网络链路**没有任何带宽瓶颈**。Leaf 交换机仅需 2 台（64×400G），2:1 OS 比绰绰有余。真正的存储端约束在 **NVMe SSD 池的聚合写入带宽**——选 3-4 台 JBOF 还是 5-6 台取决于 checkpoint 窗口要求。

## §8 延迟深度分析

### 8.1 延迟链路分解

#### 8.1.1 KV 写入路径延迟

| 延迟组件 | BF3 方案 | BF4 方案 |
|:---------|:--------|:---------|
| GPU→BF3 PCIe DMA | ~0.5-1μs | ~0.5-1μs |
| KV→LBA 映射 (BF3 ARM) | ~1-3μs | ❌ 无（硬件原生） |
| RDMA 传输 (400G/800G) | ~2-3μs (4KB~1MB) | ~1-2μs (带宽翻倍) |
| JBOF 交换网络 | ~1-2μs | ~1-2μs |
| NVMe SSD 写入 (NAND tPROG) | ~20-40μs | ~20-40μs |
| **端到端延迟 (P50)** | **~25-50μs** | **~22-45μs** |
| **端到端延迟 (P99)** | **~50-100μs** | **~45-90μs** |

> **关键发现**: 端到端延迟中 BF4 方案相比 BF3 的优势仅 **2-4μs**（占比 5-10%），NVMe SSD 的 NAND 写入延迟（~20-40μs）占全链路的 **60-80%**。**SSD 本身才是延迟瓶颈，DPU 加速解决的是那 2-4μs。**

#### 8.1.2 KV 读取/Prestaging 路径延迟

| 延迟组件 | BF3 方案 | BF4 方案 |
|:---------|:--------|:---------|
| Prestaging 调度触发 | ~0.5-1μs | ~0.5-1μs |
| BF ARM 守护进程处理 | ~1-2μs | ❌ 无（硬件触发） |
| RDMA Read (400G/800G, 2MB) | ~5-8μs | ~3-5μs |
| NVMe SSD 顺序读 (2MB) | ~150-200μs | ~150-200μs |
| **端到端延迟 (P50)** | **~160-215μs** | **~155-210μs** |
| **延迟差异占比** | **~2-4μs / ~160-215μs = 1-2%** | — |

> **核心结论**: 对 Prestaging 场景，BF3 与 BF4 的全链路延迟差异仅 **2-4μs（占比 <2%）**。SSD 顺序读延迟（~150-200μs）占全链路 **>90%**。这条数据直接削弱了"BF4 硬件加速是必须的"论证——**对 Prestaging 延迟的最终用户影响几乎为零**。

### 8.2 延迟概率分布与多节点并发建模

#### 8.2.1 各组件延迟分布函数

| 组件 | 中位延迟 | 分布类型 | 99 分位 |
|:-----|:--------|:---------|:--------|
| RDMA 传输 (400G, 2MB) | 6μs | 正态 (μ=6, σ=1) | ~8.3μs |
| NVMe SSD 顺序读 (2MB) | 175μs | 对数正态 (μ=5.16, σ=0.2) | ~260μs |
| BF3 ARM 映射处理 | 2μs | 正态 (μ=2, σ=0.5) | ~3.2μs |
| BF4 硬件处理 | 0.5μs | 退化 (确定) | 0.5μs |

### 8.3 延迟对 GPU Pipeline Efficiency 的影响

**Prestaging 时序模型**:

```text
推理步间隔: ~30-100ms (10-33 token/sec)
Prestaging 延迟: ~160-215μs
延迟占比: ~0.2-0.7% -> ✅ 无实质影响

Bubble 模型:
GPU pipeline bubble = max(0, Prestaging_delay - decode_step_interval)
-> Prestaging 延迟 ~0.2ms << 30ms decode interval -> Bubble ≈ 0
```

> **结论**: Prestaging 延迟在推理步间隔（30-100ms）中占比 <1%，无论 BF3 还是 BF4 方案都不会产生 GPU pipeline bubble。BF4 硬件加速的优势更多在于**工程可靠性**而非性能差异。

| 4 | 训练数据加载 | WRR (权重 3) | AF31 |
| 3 | Checkpoint (后台同步) | WRR (权重 2) | AF21 |
| 2 | 管理/元数据 | WRR (权重 1) | AF11 |

### 9.3 冗余与可观测性

#### 9.3.1 网络冗余架构

- **Leaf 交换机**: 2 台主备 (MLAG/VPC)

- **链路级**: 每计算节点 1-2 条 400G 链路

## §10 SPDK 栈详解

> 详细内容见原始文档 `knowledge/03_AI/train/supernode-storage-requirements-training.md` §7，此节为摘要。

### 10.1 SPDK 核心优势

```text
传统内核 NVMe 路径:
  App -> VFS -> Block Layer -> NVMe Driver -> Interrupt -> HW
  延迟: ~10-20μs

SPDK 用户态路径:
  App -> SPDK NVMe Driver (用户态轮询) -> HW
  延迟: ~1-3μs
```

### 10.2 SPDK 核心组件

| 组件 | 说明 |
|:-----|:------|
| **NVMe Driver** | 用户态轮询，无中断延迟，多队列独享核心 |
| **NVMe-oF Target** | RDMA/TCP/FC 三传输，硬件卸载支持 |
| **Bdev 框架** | NVMe/RAID/LV/Ceph RBD/Crypto/OCF 等多层堆叠 |
| **BlobFS** | 用户态文件系统，无 VFS 开销 |
| **vhost** | VM 直通 NVMe 盘，性能提升 ~2.5× |

### 10.3 SPDK vs DOCA NVMe 对比

| 特性 | SPDK | DOCA NVMe (BF4) |
|:-----|:-----|:----------------|
| NVMe-oF 卸载 | 软件 (Arm 核心) | **硬件** (专用引擎) |
| CPU 占用 | ~20-40% 单核 | <5% |
| 延迟 (4K) | ~5-8μs | ~2-3μs |
| 开源性 | ✅ BSD 开源 | ❌ 闭源 |
| KV 扩展 | 自研 | ✅ 原生 NVMe KV |
| GDS 集成 | ⚠️ 需兼容层 | ✅ 原生 |
