## 1. 引言：从对话到 Skills 的价值链

### 1.1 核心认知

对话是技能沉淀最天然的原料来源。在对话中反复出现的模式 = 需要固化的工作流。

但现实中有两个普遍痛点：

1. **对话是流水，Skills 是容器**——流水过去了，模式没有抓住
2. **知道要创建 Skill，但不知道何时、以什么方式创建最有效**

### 1.2 本工程实战背景

| 指标 | 数据 |
|:-----|:-----|
| 注册 Skills | **93 个**（12 大类） |
| 未注册 Skills（游离） | **3 个**（deep-analysis-docs-summary / knowledge-sync / spec-consistency-checker） |
| 废弃 Skills | **3 个**（计入 96 但注销） |
| Scripts 数量 | **154 个**（7 大类） |
| Skills ↔ Scripts 映射 | 三维映射框架 + 映射表 |
| 每日 Skill 调用频次 | 数十次级别（依赖会话活跃度） |
| Skill 创建工具 | `init_skill.py` + `quick_validate.py` |
| 技能治理方法 | meth-006（36 种设计模式）+ meth-009（两阶段生产法） |

### 1.3 四种路径总览

| # | 路径 | 时机 | 执行者 | 产出特征 | 本工程案例 |
|:-:|:-----|:-----|:-------|:---------|:-----------|
| ① 专项创建 | 需求明确后，一次性完成 | AI 主动 | 完整 SKILL.md + Scripts | `knowledge-doc-writer` / `server-competitor-analysis` |
| ② 有意识创建 | 执行过程中并行创建 | AI 自主 | 轻量 Skill 草稿 | 多文档分析中创建 `single-doc-parse` |
| ③ 事后模式提炼 | 对话结束后批量提取 | 批量流程 | 候选 Skill 文件 | discover 管线提取的候选 Skills |
| ④ 基于已有优化 | 发现现有 Skill 不足时 | AI 审查 | SKILL.md 增量更新 | `constraint-verifier` 迭代 / `doc-reviewer` 扩展 |

## 2. 路径一：专项创建——需求明确后系统性构建

### 2.1 适用条件

| 条件 | 判断标准 |
|:-----|:---------|
| 需求确定性 | 用户明确要求创建某个 Skill |
| 频率证据 | 对话中已出现 3+ 次同类任务 |
| 知识完整性 | knowledge/ 中有充足的参考资料 |
| 复杂度 | 涉及 5+ 步骤或需配套脚本 |

### 2.2 工作流（5 阶段）

```text
Phase 1: 需求采集
  从对话中提取用户描述：
  "帮我分析超节点存储方案" -> 目标: 存储方案设计 Skill
  "总是需要排查 BMC 故障" -> 目标: BMC 诊断 Skill
        v
Phase 2: 知识提取
  从 knowledge/ + import/ 中搜索与主题相关的已有内容
  从 conversation-log/ 中提取该任务的典型执行轨迹
        v
Phase 3: 模板生成
  运行 init_skill.py 生成 SKILL.md 框架
  或按标准模板手动创建
        v
Phase 4: 内容填充
  填充 4 个核心段：
  - description（触发/不触发条件）
  - 执行步骤（可操作动词开头）
  - 约束/红线（硬件场景必须有）
  - 输出规范
        v
Phase 5: 验证
  用全新场景测试 -> 看是否达到预期效果
  用接近边缘场景测试 -> 看触发/不触发边界是否合理
```

### 2.3 对话案例中的触发时机

在我们刚刚分析的 12 个话题中，**至少有 5 个明确触发了专项创建需求**：

| 话题 | 对话中提示创建 | 可创建 Skill | 优先级 |
|:-----|:--------------|:-------------|:-------|
| T06 文章深度提炼 | "优秀经验可做成 Skill" | `article-deep-analysis` | 🔴 P0 |
| T02 分层架构 | 描述了一整套运行流程 | `agent-layered-architecture` | 🔴 P0 |
| T07 多文档处理 | "整理一套完整工作流" | `multi-doc-analysis` | 🟡 P1 |
| T08 Skill 失效 | "整理适配 SubAgent 的下发模板" | `skill-deployment-template` | 🟡 P1 |
| T03 反偷懒提示词 | "整理标准化实验记录表" | `prompt-quality-benchmark` | 🟢 P2 |

### 2.4 本工程实战：知识文档创建 Skill 的诞生路径（六轮迭代）

以 `knowledge-doc-writer` 为例，展示从对话到成品的完整路径：

```text
对话阶段（约 7 次迭代）：
  Round 1: 用户要求深度分析服务器某一专题
  Round 2: 输出后发现缺少 TOC -> 用户要求加目录
  Round 3: 缺少交叉链接 -> 用户要求链接相关文件
  Round 4: 缺少数据出处 -> 用户要求"数值+单位+基线+条件"
  Round 5: 结论靠堆名词 -> 深度不够
  Round 6: 用户说"把我刚才提的这些要求固化到一个 Skill 里"
  Round 7: 看到效果后说"再加一些质量控制标准"

固化阶段：
  init_skill.py -> SKILL.md 框架 -> 填充 Q1-Q6 质量门禁
  -> 测试 3 个不同专题 -> 调整 description 触发边界
  -> 纳入 skills_config.json -> 每次调用生效
```

**关键教训**：这个 Skill 是 **6 轮正反馈迭代**后固化的。如果第二轮就去做，质量门禁不会到位。

### 2.5 专项创建的质量门禁

在 AGENT.md 中已定义的自检标准，对应到 Skill 创建：

```text
□ description 精准度 > 内容深度（触发偏差是最大浪费）
□ 一个 Skill 只做一类事（多职责的维护成本指数增长）
□ 破坏性操作前有确认步骤（硬件场景必加）
□ 有脚本的 Skill 比纯推理可靠 2-3×
□ 不超过 500 行（超了拆 references/）
□ 版本号 + changelog（无版本无法回滚）
```

### 2.6 本工程实战：3 个未注册 Skill 的教训

当前 `skills/` 下有 **3 个独立 SKILL.md 但不在 `skills_config.json` 中**的技能：

| Skill | 功能 | 不在配置中的原因 | 处理建议 |
|:------|:-----|:----------------|:---------|
| `deep-analysis-docs-summary` | 知识库全景摘要扫描 | 在 discover 管线中创建，未走注册流程 | 评估需求 → 注册或说明废弃 |
| `knowledge-sync` | 知识库同步与优化 | 功能与 `knowledge-health-check` + `knowledge-index-manager` 重叠 | **建议废弃**，移入 tmp |
| `spec-consistency-checker` | spec/ 文档一致性校验 | 独立的维护工具 | 如仍需 → 注册启用 |

**根源分析**：

- ① 创建时没有走标准注册流程（差一步 init_skill → 注册）
- ② 没有在创建时做重复检测（与已有 Skill 功能重叠）
- ③ 没有设置废弃标记或过期审查机制

### 2.7 本工程对话案例：server-competitor-analysis — 翻车→修复全过程

**背景**（2026-07-15）：

```text
用户说: "基于方法论文档 2026-07-15-server-competitive-analysis-methodology.md，
         生成服务器竞品分析 Skill 及配套脚本，并进行调研分析生成报告。"
```

**这是一个典型的路径①（专项创建）+ 路径④（基于已有优化）的组合案例**。

#### 第一轮：初版翻车

| 维度 | 用户原文反馈 | 具体问题 |
|:-----|:------------|:---------|
| 方法论文档引用 | "初版效果与方法论差距极大" | 引用了方法论框架但没有严格遵循其步骤 |
| 信息采集 | 未覆盖用户预期的全部来源 | 仅从知识库采集，缺少多源交叉验证 |
| 分析深度 | 仅罗列信息没有三层深度解读 | 硬件/软件/固件维度浅尝辄止 |
| 数据可信度 | 没有来源标注和置信度标识 | 用户无法判断结论可靠性 |

#### 第二轮：系统化修复

| 修复项 | v1 差在哪 | v2 怎么改 |
|:-------|:----------|:----------|
| 信息采集渠道 | 仅知识库 | **7 个来源**（知识库 + 厂商官网 + 行业报告 + 评测 + 社区 + 专利 + 论文） |
| 分析解读层次 | 单层信息 | **三层深度解读**：每维度拆解为 ①数据采集 → ②现象分析 → ③根因推断 |
| 数据标注 | 无 | 每条数据标注：来源 + 置信度（高/中/低） |
| 交叉验证 | 无 | 新增**三角交叉校验表**：每维度至少 3 个独立源交叉确认 |
| 自检机制 | 无 | 执行 **10 大陷阱自检**：确认偏见 / 幸存者偏差 / 对照组缺失 等 |
| 用户反馈采纳 | 无 | 纳入用户真实声音 |

#### 关键教训

```text
翻车根因不是"能力不足"，而是"方法论文档已被引用但未被严格执行"。

解决方法：
  ① 在 SKILL.md 中显式写出"必须严格按方法论 §X 执行"
  ② 步骤中加检查点："完成步骤 2 后，对照方法论 §3 验证覆盖率"
  ③ 输出中加 QC 报告："附：方法论遵循度自检表"
```

**对应到四路径方法**：这个案例展示了路径①（专项创建）的**典型陷阱**——即使有方法论文档，如果没有在 SKILL.md 中**显式嵌入执行检查点**，Skill 输出仍会偏离方法论。

### 2.8 本工程对话案例：discover Skill — 从管线到标准化

**背景**（2026-07-24）：

用户在与 AI 的长期协作中开发了 `discover/` 管线——一个批量化知识加工的完整管道，包含素材提取、问题生成、增强处理等多个阶段。但每次调用的执行方式不稳定：

```text
翻看多次对话记录，发现同一管线的执行方式每次都不一样：
  - 有时执行 5 步，有时跳 2 步
  - 输出格式不统一
  - 碰到的错误处理方式各异

用户决定：把这个操作流程固化为标准 Skill。
```

**Skill 化过程**：

```text
对话中采集的"最佳实践"（来自多次翻车）：
  ① 先扫描素材 -> ② 调用 enhance.py ->
  ③ 生成问题 -> ④ 输出结构化报告

历史踩坑记录：
  - 不扫描直接处理 -> 漏素材
  - enhance 参数配错 -> 输出格式错乱
  - 跳过中间 check -> 脏数据入库

固化为 SKILL.md 后的 7 步管道：
  Step 1: 素材扫描（锁定待处理文件）
  Step 2: 参数校验（检查各参数合法性）
  Step 3: 分步执行（每步完成后自动 check）
  Step 4: 中间质检（每阶段输出格式验证）
  Step 5: 结果合并
  Step 6: 最终校验
  Step 7: 日志记录
```

**对应到四路径方法**：这个案例展示了**路径③（事后提炼）+ 路径①（专项创建）**的融合。不是一次对话完成的，而是跨越多次对话、从多次"翻车"中提取的最佳实践。

### 2.9 本工程对话案例：32 个废弃 Skill 的批量生命周期终结

**背景**（2026-07-27）：

在工程的系统治理过程中，发现 `skills/` 下有大量 Skill 从未被触发，或者已被新 Skill 取代。

| 统计数据 | 数值 |
|:---------|:-----|
| 发现总数 | **32 个废弃 Skill** |
| 第一批 | 25 个 → 移入 `_archive` |
| 第二批 | 7 个 → 移入 `discover_archive_skills` |
| 节省 token | **~10-13K tokens**（系统 prompt 空间） |

**废弃原因分析**：

| 原因 | 占比 | 典型例子 |
|:-----|:----:|:---------|
| 被新 Skill 替代 | ~50% | 旧版 discover 相关 Skill → 新版统一 discover Skill |
| 逻辑已硬编码到代码 | ~20% | 自动检查类 Skill → 转为脚本化的 CI check |
| 需求不再存在 | ~15% | 临时性分析任务对应的 Skill |
| 从未被使用 | ~15% | 实验性创建后未注册 |

**废弃流程（路径③ → 生命周期终结）**：

```text
① 识别废弃 Skill
   - criteria: 最近 30 天未触发 / 已被替代 / 用户确认不用
   v
② 归档（非删除！）
   - mv 到 tmp/bak/ 或 _archive/ 目录
   - 不 rm 以便历史追溯
   v
③ 从 skills_config.json 移除
   - 确保不占用系统 prompt 空间
   v
④ 更新映射表
   - scripts/skills-scripts-mapping.md 标记为 DEPRECATED
```

**对应到四路径方法**：这个案例展示了**路径③的延伸——不是只提炼 Skill，也要识别和保护性移除废旧 Skill**。一次成功的 Skill 生态治理 = 新增 + 优化 + 废弃，三者缺一不可。

## 3. 路径二：执行中有意识创建——流水线上建容器

### 3.1 核心思想

> 不是在任务完成后才想起创建 Skill，而是在**执行一个任务的过程中，同步识别该任务可被 Skill 化的机会**。

### 3.2 判断信号（本工程实测）

| 信号 | 本工程案例 | 对应操作 |
|:-----|:----------|:---------|
| 重复操作 | 每次深度分析都要写同样的质量约束 | 创建 `depth-completer` |
| 固定流程 | 每次创建文档后要更新 index + log | `knowledge-index-manager` |
| 参数化模式 | 多文档分析中只是 URL 不同 | 参数化为 Skill 输入 |
| 多次翻车点 | 每次忘加交叉链接、数据出处 | 纳入 quality checklist |
| 需要记忆的模式 | prompt 约束模板反复写 | 固化到 `light-self-review` |

### 3.3 与偷懒机制的关系（对话 T03 的延伸）

对话 T03 中分析的**任务负载效应**与 Skill 创建的关系：

```text
多文档分析任务中 ->
  模型在多任务下偷懒 ->
    需要更强的约束指令 ->
      每次写重复约束 ->
        应该封装为 Skill -> 创建
```

**即**：偷懒现象的**存在本身就是 Skill 创建信号**——如果某类任务总是需要重复写约束才能保证质量，就说明它应该被 Skill 化。

### 3.4 本工程实战：light-self-review 的现场创建

在创建 `constraint-verifier` 的过程中，发现每次交付前都需要做同样的质量自检：

```text
创建 constraint-verifier Skill ->
  测试中发现需要检查 A-J 十类失效 ->
    发现每次都需要同样的自检流程 ->
      当场创建 light-self-review 草稿 ->
        后续完善为正式 Skill
```

这个例子完美展示了"执行过程中识别可 Skill 化机会"——不是先规划好再创建，而是**在做 A 时发现 B 的通用性**。

### 3.5 本工程对话案例：用户问题分析体系 — 从"怎么分析"到标准化 Skill

**背景**（2026-07-20）：

```text
用户说: "帮我设计用户问题分析体系——先看看现有数据，再决定怎么做。"
```

**初始状态**：此时 AI 知道 `conversation-log/user-questions/` 下有数据（176 个会话、1,424 条用户问题），但每次分析时：

- 都要先想一想"怎么分析这些问题"
- 每次分析维度不同，结果不可对比
- 用户说"看看数据"→ AI 输出一次分析；用户说"再分析"→ AI 重新构思分析框架

**执行过程中识别的可 Skill 化信号**：

| 信号 | 出现次数 | 识别时机 |
|:-----|:--------:|:---------|
| "又要思考分析框架" | 第 2 次分析时 | 发现重复构思分析维度 |
| "上次分析维度这次忘了" | 第 3 次更新时 | 发现分析视角不同，结果不可对比 |
| "能不能固定下来" | 用户第 2 次说这句话 | 用户暗示需要标准化 |
| "统计格式不统一" | 数据汇总时发现 | 格式混乱导致无法合并 |

**创建过程（有意识创建 + 事后完善）**：

```text
Step 1: 先完成本次用户要求的具体分析
  -> 扫描目录结构 -> 理解数据格式 -> 提取分析维度 -> 输出分析报告

Step 2: 分析过程中记录"哪些步骤可以固定下来"
  -> "读取 user-questions/ 目录"是重复操作
  -> "计算各维度分布"是重复操作
  -> "输出对比表格"是重复操作

Step 3: 分析完成后，立即将这些步骤封装为 Skill 草稿
  -> 创建专用 Skill: "用户问题分析模板"
  -> 创建分析脚本: "自动统计用户问题分布"

Step 4: 过程中踩坑 -> 进一步优化
  -> 字符串双引号冲突导致脚本批量修复时改错
  -> 重写关键输出部分
  -> 将踩坑经验纳入 SKILL.md 的约束提醒
```

**Key 教训——有意识创建的时间点选择**：

```text
❌ 错误做法：等用户说"帮我做个 Skill"再做
   -> 让用户替你想"什么时候需要 Skill"，增加认知负担

✅ 正确做法：第二次做同类分析时，就识别"这已经是重复工作"
   -> 用户只说了"分析数据"，AI 应该自己感知到"这活儿值得 Skill 化"
   -> 创建草稿 Skill 后立即使用 -> 效果稳定后完善 -> 注册
```

**对应到四路径方法**：这个案例是**路径②（有意识创建）的完整演示**——用户并没有说"创建 Skill"，只说了"分析数据"。AI 在第二次执行同一类任务时**自主感知**到可 Skill 化信号，主动创建，并在后续使用中持续完善。

### 3.6 轻量 Skill 草稿模板（适合执行中快速创建）

```yaml
---
name: <暂定名，后续可改>
description: "<一句话触发词
  Use when: <具体场景>
  Do NOT use: <什么场景不该用>"
---
# 草稿 (Draft)
# 来源: <对话记录/任务名/日期>

## 步骤
1. <从执行记录中提取的步骤>
2. ...
3. ...

## 关键约束
- <防止偷懒的关键约束>

## 输出格式
- <标准化输出>

## 待完善
- <需要补充的缺失信息>

## 重复检测
- 检查 skills/ 是否已有功能重叠的 Skill（grep description）
- 检查 scripts/ 是否已存在相同功能的脚本
```

### 3.8 本工程对话案例：spec-consistency-checker — 执行中"顺手"创建

**背景**（2026-07-27）：

在执行大规模 spec 系统治理任务时——修复 SR→AR 映射、清理废弃 spec 文件、建立三层流水线约束——AI 发现了一个反复出现的问题：

```text
每次修改 spec 文件后，都要手动检查：
  - 新 SR 是否映射到 AR？
  - AR 状态是否与实现一致？
  - 约束编号 CC 是否连续？
  - 引用是否有效？

这些检查每次都要手动执行，一模一样的步骤。
```

**创建过程**：

```text
训练中识别模式（第 2 次做同类检查时）：
  "等一下——我连续两次在做同一件事：检查 spec 一致性"

有意识创建动作：
  1. 先把当前检查做完（不中断用户任务）
  2. 把检查步骤记录在 tmp/spec-check-notes.md
  3. 任务完成后，立即将步骤封装为 Skill 草稿
  4. 同时创建 5 个检测脚本（L1~L4 + 编排器）

结果：
  - 一个完整的 spec 一致性检测系统 = 914 行代码 + SKILL.md
  - 可以自动化调度，不再需要手动检查
```

**然而——它成了 3 个未注册 Skill 之一**：

| 问题 | 原因 | 影响 |
|:-----|:-----|:-----|
| 草稿阶段→未注册 | 创建时没走 `init_skill.py` → 注册流程 | 系统 dispatch 引擎不识别 |
| 功能未做重复检测 | 没检查 `knowledge-index-manager` 是否覆盖 | 功能潜在重叠 |

**教训**：有意识创建的草稿 Skill 需要**在草稿→正式注册的过渡中加入"注册检查"步骤**，否则草稿永远停留在"只能用但不会被识别"的状态。

### 3.9 本工程对话案例：knowledge-sync — 功能重叠的典型教训

**背景**（2026-07-21）：

用户要求设计与 `knowledge/` 目录操作相关的配套 skills/scripts。AI 在梳理过程中，发现需要一个目录同步功能，于是创建了 `knowledge-sync` Skill。

  - 索引同步 <- 两者都有
  - 日志更新 <- knowledge-index-manager 已有

## 5. Skills 创建决策框架——什么时候创建、覆盖什么层面

### 5.1 核心问题

> 前 4 节讲了**如何创建**（四路径），但有一个更前置的问题没有回答：**什么时候应该创建 Skill？Skills 应该覆盖系统的哪些层面？**

在实践中，最容易犯的两个错误：

- **过度创建**：每个固定操作都做一个 Skill → 维护成本指数增长 → 最终废弃
- **创建不足**：反复做同一类任务但没识别到可 Skill 化 → 每次重新构思 → 效率不提升

### 5.2 什么时候应该创建 Skill

#### 5.2.1 三层决策漏斗

> 不是每个重复操作都值得 Skill 化，需要通过三层漏斗过滤。

```text
第一层：操作层面（触发频率是否够高？）
  |
  +- 每日 / 每次会话都用的操作 -> 🔴 必须 Skill 化
  |   (如：归档文档、搜索知识库、文档自检)
  |
  +- 每周 2-3 次的操作 -> 🟠 建议 Skill 化
  |   (如：生成周报、质量检测、深度分析)
  |
  +- 每月 1-2 次的操作 -> 🟡 视复杂度而定
  |   (如：竞品分析、体系结构审查)
  |
  +- 一次性 / 少于每月 1 次的操作 -> 🟢 不值得 Skill 化
      (除非流程极其复杂且有明确文档价值)
        v
第二层：复杂度层面（操作步骤是否稳定？）
  |
  +- 步骤固定（每次做同样的事）-> ✅ 适合 Skill 化
  |   (如：创建文档->更新 index->更新 log)
  |
  +- 步骤基本固定但有参数 -> ✅ 适合 Skill 化 + 参数化
  |   (如：跟踪不同主题：只是搜索词不同)
  |
  +- 步骤每次完全不同 -> ❌ 不适合 Skill 化
      (如：开放式创新 brainstorming)
        v
第三层：失败成本层面（做错了代价多大？）
  |
  +- 错误不可逆（删除文件、覆盖数据）-> 即使频率低也要 Skill 化
  |   (如：文件迁移、目录重构)
  |
  +- 错误需 30min+ 修复 -> 建议 Skill 化
  |   (如：批量格式修复、约束合规检查)
  |
  +- 错误可秒级修复 -> 不需要 Skill 化
      (如：文件名拼写错误)
```

#### 5.2.2 本工程 Skill 在三层漏斗中的分布

| 漏斗层 | 符合度 | 典型 Skill | 反例 |
|:-------|:------:|:-----------|:------|
| 频率高频 | ✅ 92% | `web-archive`（每次归档） | `mckinsey-research`（频率低但流程复杂） |
| 步骤稳定 | ✅ 85% | `knowledge-wiki`（写→更新 index/log） | `daily-news-60s`（外部 API 依赖不稳定） |
| 失败成本高 | ✅ 78% | `knowledge-index-manager`（破坏 index） | `patent-disclosure-writer`（法律风险高但无法 Skill 化止步） |

**工程数据**：93 个注册 Skill 中，约 **72 个（77%）** 满足三层漏斗全部条件，**18 个（19%）** 满足两层但不够稳定，**3 个（3%）** 属于需重新评估的边缘 Skill。

#### 5.2.3 8 种不宜创建 Skill 的场景

| # | 场景 | 本工程实例 | 正确做法 |
|:-:|:-----|:----------|:---------|
| 1 | **一次性分析任务** | `deep-analysis-docs-summary`（运行一次生成 10,000 行报告后再没用过） | ✅ 脚本化即可，不需要 Skill 包装层 |

#### 5.3.4 七层模型的跨层依赖

> Skills 不是孤立的，高层 Skill 依赖低层 Skill。这种依赖关系决定了 Skill 的**创建顺序**和**废弃风险**。

```text
依赖方向：高层 -> 低层（上层调用下层）

L0 元层 <- 无依赖（定义规则，被所有层依赖）
  ^
L1 编排 <- L0（编排必须遵守约束）
  ^
L2 领域 <- L0 + L1（知识创建受编排调度）
  ^
L3 工具 <- L0 + L2（文档生成需要领域知识指导）
  ^
L4 学术 <- L0 + L2 + L3（论文写作依赖领域知识和文档工具）
  ^

典型依赖断裂案例（本工程，已修复）：
  spec-consistency-checker (L5) 未注册 ->
    L0 元层无法感知它的存在 ->
    约束体系对它不生效 ->

  knowledge-sync (L2 + L5) 与已有 Skill 重叠 ->

```

## 6. 路径四：基于已有提示词修改优化——迭代而非从零

### 6.1 核心思想

> 大多数情况下，**不需要从零创建 Skill**。已有的提示词/工作流/约束指令中已经包含了 Skill 的大部分内容，需要的是：
>
> - **参数化**：把固定值改为变量
> - **泛化**：从单场景扩展到多场景
> - **结构化**：从自由文本转为标准格式

### 6.2 四步优化流程

```text
① 识别已有提示词
   -> 对话中反复使用的有效指令
   -> 之前写的临时 prompt
   -> 已有 Skill 中过时的内容

② 参数化
   -> 固定值 -> $变量
   -> 单场景 -> 多场景分支

③ 泛化
   -> 单模型适配 -> 多模型兼容
   -> 单文件 -> 多文件

④ 结构化
   -> 自由文本 -> YAML frontmatter + 步骤块 + 约束块
```

### 6.3 从临时提示词到 Skill 的进化（示例）

以对话中 T06 的提示词模板为例，展示四步进化：

**Step 0: 原始对话中的提示词**（对话原文）:

```text
"你需要严格仿照专业研究员分析文本的完整流程处理下文，
禁止自由简化步骤，必须依次执行以下全部规则：
1. 宏观定性...
2. 分段解析...
..."
```

**Step 1: 参数化**

```yaml
input:
  text: $ARTICLE_TEXT
  extract_type: "full" | "summary_only" | "keywords_only"
```

**Step 2: 泛化**

```yaml
input:
  texts: [$TEXT1, $TEXT2, ...]  # 支持多文本
  mode: "sequential" | "parallel"  # 串行/并行分析
  output: "comparison" | "merge" | "individual"  # 输出方式
```

**Step 3: 结构化**

```yaml
---
name: article-deep-analysis
description: "文章深度分析 — 仿人工四阶段分析流程。
  Use when: (1) 深度分析单篇长文, (2) 跨文档对比分析,
  (3) 关键字提取+关联建模。
  Do NOT use: 简单摘要任务（用 summary Skill）。"
metadata:
  requires: { bins: [] }
  emoji: 📖
---
## 执行流程

### Phase 1: 宏观定性
- 识别文章类型: 议论文/行业分析/技术文档
- 锁定核心目标
- 划分文章结构

### Phase 2: 关键词挖掘
- [x] 提取实体关键词（主体/对象/指标）
- [x] 提取逻辑关键词（转折/因果/约束/对比）
- [x] 每条关键词记录出处语句+功能标注

### Phase 3: 关联建模
- [x] 梳理关键词间因果/并列/矛盾/从属关系
- [x] 区分: 客观事实 / 作者推断 / 衍生分析
- [x] 标注: 冲突信息 / 未验证假设

### Phase 4: 输出
- [x] 结构化分析报告
- [x] 核心价值 + 漏洞 + 隐藏前提 + 适用边界

## 约束
- 禁止只输出笼统概括
- 所有解读锚定原文素材
- 遗漏逻辑关键词 = 不合格
```

### 6.4 本工程实战：constraint-verifier 的迭代演化

`constraint-verifier` 是本工程中路径四最典型的案例——它是在 `light-self-review` 的基础上演化而来：

```text
起点: light-self-review（通用自检，A-J 十类失效）
    v
发现: 用户需要更强的约束遵守度检测
    v
变化 1: 从通用自检 -> 针对约束文件的专用检测
变化 2: 从十类失效 -> 可检测断言（每个失效类对应一组可验证语句）
变化 3: 加入脚本支持 -> Python 脚本做自动化判断
    v
产出: constraint-verifier（独立 Skill，与 light-self-review 互补）
```

**关键决策**：为什么不做成 light-self-review 的扩展而是独立 Skill？

- 职责分离：self-review = 通用文本质量自检；constraint-verifier = 约束遵守度检测
- 触发条件不同：前者每次交付后触发；后者只在用户怀疑约束违规时触发
- 维护成本：合并后 SKILL.md 会 > 500 行

### 6.5 本工程对话案例：weekly-report-generator — 从碎片脚本到完整 Skill

**背景**（2026-07-29 → 多次迭代）：

`weekly-report-generator` 是本工程中**迭代次数最多**的 Skill 之一，展示了路径④的完整演化路径。

**进化历程**：

```text
v0 (2026-07-26 之前):
  +-- 碎片状态：AI 每次手动生成周报
      - 每次写不同的 prompt
      - 输出格式每次不同
      - 耗时 ~30min/次

v1 (2026-07-26):
  +-- 第一次 Skill 化：创建 SKILL.md
      - 固定周报结构（4 大分类）
      - 固定模板格式
      - 耗时降至 ~15min/次
      - 问题：缺少时间窗口定义，数据范围不统一

v2 (2026-07-29):
  +-- 时间窗口修正：
      - 发现：之前的时间窗口是 00:00-23:59 全天制
      - 实际需求：必须为 "上一日 08:00 -> 当日 08:10"
      - 原因：调研任务常在 00:00-08:00 执行，归属日期不明确
      - 修复：SKILL.md 新增时间窗口定义 + 各数据源窗口语义表

v3 (2026-07-29):
  +-- 三支柱结构定型：
      - 发现：输出混杂了调研数据、分析文档、工程变更
      - 重新设计为三支柱：
        ① 每日洞察技术要点
        ② 深度分析文档摘要
        ③ 工程 Git/Memory 变更
      - 新增配套脚本体系：
        - kb-daily-data-gather.sh（统一入口）
        - kb-daily-files.sh（文件扫描）
        - kb-daily-survey-scan.sh（调研数据扫描）

v4 (未来):
  +-- 待优化方向：
      - 链接路径自动化
      - 与 memory/ 自动关联
      - 交叉引用密度统计
```

**关键教训——什么时候应该优化 vs 重建**：

```text
每次迭代的判断依据：
  "效果差距小于 50% 的工作量" -> 优化（路径④）
  "效果差距大于 50% 的工作量" -> 重建（路径①）

weekly-report 的例子：
  v1->v2（时间窗口）：改动 SKILL.md 的 3 行定义 -> ✅ 优化
  v2->v3（三支柱）：改动整个输出结构和脚本体系 -> ⚠️ 接近重建
  但最终选择优化而非重建，因为核心工作流没变
```

## 7. Skill 全生命周期管理——从创建到废弃

### 7.1 生命周期阶段

```text
创建（专项/有意识/事后提炼/优化）
   v
注册（skills_config.json）
   v
使用（对话触发 -> 逐步优化）
   v
审查（定期评估有效性和触发准确率）
   v
✓ 继续使用
   or
✗ 废弃（移入 tmp/bak/）
```

### 7.2 本工程的三大生命周期问题

| 问题 | 表现 | 影响范围 | 根因 |
|:-----|:-----|:---------|:-----|
| **游离 Skill** | 3 个 Skill 有文件但未注册 | 不可被系统自动触发 | 创建流程缺注册步骤 |
| **功能重叠** | `knowledge-sync` 与 2 个已有 Skill 重复 | 维护成本浪费 | 创建前未做重复检测 |
| **废弃无标记** | 已失效的 Skill 仍留在 skills/ | 检索噪声 + 维护负担 | 无生命周期终点机制 |

### 7.3 解决建议

```text
创建时强制:
  1. 检查 skills/ + skills_config.json 是否有功能重叠
  2. 走 init_skill.py 确保文件规范
  3. 立即注册到 skills_config.json

使用时跟踪:
  4. 记录调用频次和成功率

定期清理:
  5. 每月审查一次废弃列表
  6. 确认废弃后移入 tmp/bak/<date>-deprecated-<skill-name>/
```

## 9. 工程质量保证体系

### 9.1 四路径通用自检清单

每个新创建/修改的 Skill，在交付前执行：

```text
□ description 清晰度
   - 能否 3 秒判断该 Skill 是否适用？
   - Do NOT use 部分是否已填？

□ 步骤可操作性
   - 每步是否以动词开头？
   - 是否有 skip/fail 条件？

□ 硬件安全红线
   - 涉及硬件操作吗？
   - 破坏性操作前有确认吗？

□ 量化约束
   - 性能断言有「数值+单位+基线+条件」吗？
   - 评估标准可验证吗？

□ 来源追溯
   - 从哪段对话/哪个任务提取的？
   - 是否标注了来源日期？

□ 版本标记
   - 有版本号吗？
   - changelog 更新了吗？

□ 重复检测（新增）
   - skills/ 中是否有功能重叠的 Skill？
   - skills_config.json 是否已有类似触发条件？

□ 注册完成
   - skills_config.json 是否已注册？
   - 是否做了 init_skill.py 的格式验证？
```

### 9.2 与 AGENT.md 自检清单的联动

AGENT.md 产出自检清单 + 本文件 4 路径方法 + 本工程已有的质量工具 → 形成了 Skill 创建的全流程质量闭环：

```text
AGENT.md 自检
  +- 断言有出处？来源可追溯？
  +- 数据: 数值+单位+基线+条件？
  +- 文档: TOC+交叉链接+changelog？
  +- 框架堆名词不深入原理？-> 不合格

本文件 4 路径方法
  +- 选择了正确的创建路径？
  +- description 足够精准？
  +- 对话模式提取完整？
  +- 已有 Skill 有没有重复？

本工程已有工具
  +- init_skill.py — 模板生成
  +- quick_validate.py — 格式验证
  +- doc-reviewer — 文档审查
  +- constraint-verifier — 约束遵守度检测
  +- meth-009 — 两阶段生产法（生成优先，维护集中）
```

### 9.3 两阶段生产法的适配（meth-009 联动）

Skill 创建也应遵循 **生成优先、维护集中** 的两阶段原则：

```text
第一阶段：生成（自由创建）
  - 只关注: SKILL.md 内容完整、步骤可执行
  - 暂不关注: skills_config.json 注册、重复检测、index 更新
  - 因为: 认知负载集中在内容质量上

  v 切换条件: SKILL.md 主体完成 + 验证通过

第二阶段：维护（集中注册）
  - 一次性完成: 注册 / 重复检测 / 更新 skills/index.md
  - 原因是: 让 AI 不要在创作时频繁切换上下文
```
