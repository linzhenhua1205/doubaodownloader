## §一 概述：本系统知识管理体系全景

本工程的 AI 知识管理不是单点工具，而是一套 **五层协同的工业级 KM 架构**：

```ascii
+-----------------------------------------------------------------+
|  Layer 5: 方法论层                                              |
|  内容引用一致性系统 · 知识容器类型学 · 团队能力量化 · 公平分配   |
|  -> 把 KM 的"怎么做"固化为可复用的方法论文档 (17 份)             |
+-----------------------------------------------------------------+
|  Layer 4: 自动化工具层                                          |
|  scripts/check/ 工具族：link-validator · ref-drift-detector ·    |
|  knowledge-normalizer · analyze-index-coverage · reformat-log   |
|  -> 把质量检查从人工变为可脚本化                                 |
+-----------------------------------------------------------------+
|  Layer 3: Skills 能力层                                         |
|  index-deep-analyzer · knowledge-health-check ·                 |
|  knowledge-doc-writer · directory-optimizer · log-reformatter   |
|  -> AI 可调用这些技能来自主维护知识库                             |
+-----------------------------------------------------------------+
|  Layer 2: 结构规范层                                            |
|  index.md + log.md 双文件制 · 英文目录 · 两位编号 · MECE 分层    |
|  bak/ 回收站 · 一句话摘要 · changelog 格式 · 交叉引用尾部列表   |
|  -> 确保所有文件遵循统一的结构契约                                |
+-----------------------------------------------------------------+
|  Layer 1: 知识内容层                                            |
|  1,592 个 .md 文件 · 10 大模块 · 19+ 子目录 · 25+ 万字内容     |
|  -> 这是知识本身                                                |
+-----------------------------------------------------------------+
```

**核心特征**：这不仅仅是"文件放在目录里"，而是一套**带有质量保证体系的知识工程系统**。

## §二 单文件变更管理与修订记录

### 2.1 当前实现

```ascii
变更操作集 (15 类):
  🆕 新增   📥 归档   🔄 rewrite   📍 移动   🔀 合并
  🧹 清理   📦 新建模块   🧭 方法论   🔧 修复   📝 更新
  🏗️ 重构   🔗 重链接   ⚡ 扩展   📊 生成   ❌ 删除(->bak)

日志体系 (三级):
  根级 log.md          -> 跨模块/顶层变更
  模块 log.md (10个)   -> 模块内部变更
  文件内 changelog     -> 单个文档版本历史

每条条目包含:
  操作类型 + 路径 + 大小/行数 + 章节覆盖 + 关键结论/量化数据
```

### 2.2 优点分析

| 维度 | 优点 | 证据/示例 |
|:-----|:-----|:----------|
| **颗粒度** | 条目级而非目录级——知道每个文件的具体变更 | `log.md` 每条含 ~30-80 字摘要 |
| **可追溯性** | 移动操作标注 `P0#1` 优先级和时刻 `(@07:40)` | 2026-07-14 批量 17 个移动全部标注 |
| **量化思维** | 每条记录含 KB/~行数/章节数，便于评估规模 | "37KB/~700行/12章" |
| **操作类型化** | 15 种标准化操作类型，一眼看懂变更性质 | emoji 前缀强化辨识度 |
| **分级废弃** | `mv` 到 `bak/` + 原因标注，非直接删除 | "bak/重复文件-2026-07-14/" |

### 2.3 待改进点

| 问题 | 严重程度 | 根因 | 建议方案 |
|:-----|:--------:|:-----|:---------|
| **日志遗漏风险** | 🔴 **高** | AI 操作日志依赖自觉性，无强制校验。14 个模块的 log 同步依赖人工触发 | 新增 `check-log-coverage.py`：每天扫描 git diff 或 mtime，检测新增/修改文件是否在对应 log.md 中有条目 |
| **版本号管理弱** | 🟡 中 | 只有少数文档有 v1.0 标记，大部分文档无显式版本号。无法区分"小幅修补"vs"重大重写" | 推行文档头部 `version:` 字段 + 语义化版本规则（MAJOR.MINOR），AI 每次修改时评估是否需升版 |
| **批量操作日志重复** | 🟡 中 | 批量移动 17 个文件时 log.md 出现 17 行相似条目（2026-07-14 可见此问题） | 批量操作归一化：同一批同类操作合并为 1 条总条目 + 附件列表或链接 |
| **删除语义不完整** | 🟢 低 | 移动到 bak 后原索引/交叉引用无自动标记"已废弃" | 新增 `bak/README.md` 格式要求：记录源路径+去向后+引用方列表 |

## §三 目录索引、log 与文件合理性

### 3.1 当前实现

```ascii
索引体系 (三层):
  Layer 1: knowledge/index.md       -> 顶层导航 (10 模块概览+统计)
  Layer 2: 模块/index.md            -> 模块内文件清单+一句话摘要
  Layer 3: 子目录/index.md          -> 子目录内文件清单

每层 index.md 包含:
  ✅ 文件统计数   ✅ 一句话摘要   ✅ 相对路径链接   ✅ 规则说明
  ✅ 目录结构概览 ✅ 交叉引用列表  ✅ 核心入口链接

文件摘要规范:
  "一句话概述" 格式 -> 30-60 字覆盖核心
  示例: "PCIe子系统深度分析：Lane划分(128 lane全映射)·Retimer vs Redriver本质差异·...·7类检查清单42项"

自动化工具体系:
  analyze-index-coverage.py (394行)   -> 扫描缺失文件
  link-validator.py (604行)           -> 校验链接有效性
  knowledge-normalizer.py (290行)     -> 规范化检查
  ref-drift-detector.py (552行)       -> 引用漂移检测
  directory-architect.py              -> 目录架构分析
```

### 3.2 优点分析

| 维度 | 优点 | 证据/示例 |
|:-----|:-----|:----------|
| **MECE 分层** | 每个 index.md 文件内按 MECE 原则分组，同层互斥 | `02_rd/index.md` 用 12 子目录+编号，每个子目录绑定文件清单 |
| **统计透明** | 每个模块在概览表中标注文件数，趋势可追踪 | `02_rd` 从 311→497→498→559 的演进可见 |
| **摘要一致性** | 所有文件统一"一句话概述"格式，目录可读性极高 | 每一行都是：`文件名 \| 一句话覆盖核心` |
| **自动化覆盖** | 5+ 个专门脚本用于索引健康度检查，不是纯人工 | `analyze-index-coverage.py` 可自动发现未纳入 index.md 的文件 |
| **数据驱动** | 索引中嵌入元数据（创建日期/版本/来源），辅助判断 | AMD Turin 分析标注来源 "豆包原始素材680+文件综合提炼" |

### 3.3 待改进点

| 问题 | 严重程度 | 根因 | 建议方案 |
|:-----|:--------:|:-----|:---------|
| **摘要信息衰减** | 🟡 中 | 一句话摘要虽然简洁，但文档被多次扩展后摘要内容可能过时 | 定期运行 `check-summary-currency.py`：将摘要与文档实际内容做向量相似度校验，偏差超阈值则触发重写 |
| **无文件成熟度标记** | 🟡 中 | 无法区分"初稿框架"vs"深度完成"vs"待审核" | index.md 新增 `状态` 列：🟢完成/🟡待审/🔴初稿/📝待扩展 |
| **跨模块导航弱** | 🟡 中 | 用户在 01_survey/ 浏览时无法感知 02_rd/ 中关联文档的存在 | 在 index.md 头部添加"关联模块"快速跳转区（自动从交叉引用反向聚合） |
| **索引更新自动化不足** | 🟡 中 | 新增文件后 index.md 仍需 AI 手动追加，偶尔遗漏 | 脚本 `sync-index.py`：扫描目录树差异 → 自动追加新文件占位摘要(使用文件名推断) → AI 手工润色 |
| **多语言目录索引** | 🟢 低 | 中文目录名优点是可读性高，但偶尔与其他工具兼容性差 | 维持现状 + 确保 URL 编码兼容（已有 `fix-index-urlencode.py`） |

## §四 跨文件调用与信息引用处理

### 4.1 当前实现

本系统采用了**三层引用策略**，从简单到复杂：

```ascii
引用类型一: Markdown 相对链接 [text](path)
  -> 用于文档内交叉引用、跳转到关联文档

引用类型二: 文档头部 "关联" 字段
  -> 显式列出依赖的关联文档，如:
    > 关联: [Turin架构深度分析](../../05_AIServer/...md) · [系统框图](35-xxx.md)

引用类型三: @ref 引用标记系统 (2026-07-16 新增)
  -> 三段式: {@ref: 源路径#段落 | 引用理由 | last-verified=日期}
  -> 配 ref-drift-detector.py 脚本 (552行)
  -> 支持三层检测: L1路径漂移/L2时间漂移/L3内容漂移(Hash)
```

**今日刚创建的 `@ref` 系统**是解决跨文件引用一致性问题的工程化方案，其核心思路是：

```ascii
副本语义(旧的):   PCIe Gen6 速率 64 GT/s   <- 从源复制后与源无关
引用语义(@ref):   {@ref: spec.md#rate}       <- 工具可追踪引用关系

三层检测:
  L1 路径漂移:  源文件被移动/删除 -> 检查路径有效性
  L2 时间漂移:  源文件已更新但引用方未更新 -> 对比 mtime
  L3 内容漂移:  源段落内容已变 -> 对比 content hash
```

### 4.2 优点分析

| 维度 | 优点 | 证据/示例 |
|:-----|:-----|:----------|
| **引用可见性** | 文档头部"关联"字段让依赖关系一览无余 | 37-serdes.md 关联 4 份文档，36-pcie.md 关联 6 份 |
| **方案升级路径** | 从基础链接→@ref 标记→自动化检测，不跳跃 | 2026-07-16 才刚刚升级到 @ref 系统，渐进演进 |
| **依赖追溯脚本** | `ref-drift-detector.py` 可输出依赖图(.dot)和 JSON | 支持全量/漂移/模块过滤三种模式 |
| **类型差异意识** | 区分路径漂移(L1)/时间漂移(L2)/内容漂移(L3)三层次 | 不同严重等级对应不同处理策略 |
| **工程化思路** | 不是靠"自觉遵守"而是靠脚本自动检测 | 编程语言的 import 机制启发 |

### 4.3 待改进点

| 问题 | 严重程度 | 根因 | 建议方案 |
|:-----|:--------:|:-----|:---------|
| **@ref 采纳门槛** | 🔴 **高** | 新规范需要逐文档手动添加 @ref 标记，1,592 个文件迁移成本极大 | 分阶段推进：① 先覆盖 P0 核心文档(~200份) ② 设计半自动扫描：脚本自动检测"引用事实数据"的段落并建议标记 ③ 在 document creation skill 中模板化 @ref |
| **反向引用不可知** | 🔴 **高** | 文档不知道"谁引用了我"——源更新后无法主动推送 | 依赖图持久化：`scripts/check/ref-graph/` 目录存储 `.dot` 文件 + 反向引用索引。源更新时脚本输出"受影响文件列表" |
| **文档版本漂移** | 🟡 中 | revision history 在 log.md 中，但文件内 changelog 有时不一致 | 统一规则：文件头部 changelog 记录本文件版本，log.md 记录目录级变更。脚本检测二者一致性 |
| **事实数据无独立标识** | 🟡 中 | "PCIe Gen5 32GT/s" 这类事实散落在各处，无法统一管理核心指标 | 核心指标表维护：将跨文档共享的量化数据（速率/损耗/功率/延迟等）抽取到 `knowledge/02_rd/00_shared/02_concepts/epistemology/core-parameters.md`，其他文档通过 @ref 引用。一份更新，全域同步 |
| **引用粒度粗** | 🟢 低 | 大多数引用是"整篇文档"级别，而非"段落/数据点"级别 | @ref 规范已支持段落锚点 `#section`，但实际使用尚未普及 |

```ascii
  2026-06-30  ⚡ 02_server/ -> 02_rd/ (全库重命名 254 处引用)
              ⚡ 04_software/ -> 04_fullstack/

  2026-07-01  ⚡ 06_solution -> 21_solution (释放06给运维)
              ⚡ 创建 06_O&M/ 运维专项目录

  2026-07-06  ⚡ 专利文档迁出 92_patent/
              ⚡ IPD/NPI/产品/项目/团队/AI 六分目录重构

  2026-07-14  ⚡ methodology/ 方法论集中 (1->16 文件)
              ⚡ 06_others 清理 (16->6 文件)
              ⚡ 批处理 17 个文件移动归位

自动化工具:

  subdir-nav-fixer.py     -> 子目录导航修复
```

### 5.2 优点分析

| 维度 | 优点 | 证据/示例 |
|:-----|:-----|:----------|
| **持续重构** | 目录不是一次性设计，而是每月调整优化 | 2026-06-26 → 07-14 间 5 次重大结构调整 |
| **参考层设计** | 按"创建日期+英文名+两位编号"模式留扩展空间 | `02_rd/` 子目录编号 00→02→03→04→05→06→08→09→21→92，预留 07/10-20/22-91 |
| **bak 机制** | 废弃文件不删除，带日期+原因保留 | `bak/重复文件-2026-07-14/` 方式保留审计追踪 |
| **增强型 index 工具** | 有专门的 directory-optimizer 技能做 MECE 分析 | 可在重建目录时做跨域耦合度分析 |
| **文件位置合理性校验** | 不是随意放置，有"文件应该在哪"的归属意识 | P0-P2 分级移动（如 "P1#5 知识质量方法论 → 05_tools/knowledge/"） |
| **引用同步** | 每次移动文件同步更新所有交叉引用（或记录引用方） | `02_server/` → `02_rd/` 批量替换 95 文件中 254 处引用 |

### 5.3 待改进点

|:-----|:--------:|:-----|:---------|
| **目录变更通知盲区** | 🔴 **高** | 目录结构调整后，引用该目录下文件的文档无法自动感知 | 结合 @ref L1 检测 + 增加 `directory-change.log` 记录每次重命名/移动，AI 创建文档时自动检查该日志 |
| **双入口问题** | 🟡 中 | 某些跨域主题的文档可能在两个目录都合理，未建立"主副本"机制 | 定义"规范位置"（canonical location）原则：每个文件只有一个规范路径，其他目录仅存放 short-link/symlink 或 @ref |
| **无文件关系图** | 🟡 中 | 缺少可视化的文件依赖关系图，新用户上手慢 | 定期从 `ref-drift-detector.py` 的 `.dot` 输出生成依赖图 HTML（类似有向无环图），纳入周报 |
| **热数据/冷数据分层** | 🟡 中 | 1,592 个文件无"活跃度"标记，难以区分高频访问和冷归档 | 引入文件最后访问时间（access time）监控，>6 个月未触碰文件自动标记"❄️冷文件"并建议归档策略 |
| **树深收敛** | 🟢 低 | 部分路径嵌套 5-6 层（如 `02_rd/03_hardware/06_superpod/hw_design/`），路径长度 >120 字符 | 考虑将 `hw_design/` 提升为 `07_hw-design/` 与 `06_superpod/` 同级（仅对通用硬件设计提升；超节点专用仍保留原路径） |

## §六 好的实践与可推广之处

### 6.1 设计哲学层面的启发

#### 🏆 最佳实践 #1：AI 作为 KM 工程师而非文件管理员

**做法**: AI 不仅读写文件，还自主执行目录重构、交叉引用修复、质量检查脚本。

**关键机制**:

```ascii
RULE.md 存储规则 -----> 自动判断信息写入位置（按频率 + 重要性）
     ^ 执行前查        v 写完后
AGENT.md 自检清单      同步更新 index.md + log.md
```

**推广价值**: 任何基于 AI 的知识库都应建立"写作→归档→索引→日志"的完整闭环，而非仅止于"把内容写进去"。

#### 🏆 最佳实践 #2：五层架构的可演进性

**做法**: 知识管理体系不是一次性构建，而是按"内容→结构→技能→工具→方法论"顺序逐步建设（甚至跨月/跨年）。

**演进证据**: 引用一致性系统 (`2026-07-16-content-ref-consistency-system.md`) 是 2026-07-16（今天！）才创建的，这已经是系统运行超过 60 天后解决第 4 层核心问题的产物。

**推广价值**: 不要试图在第一天构建完美的 KM 系统。先跑起来，再在运行中暴露痛点并针对性解决。

#### 🏆 最佳实践 #3：量化驱动的内容质量保障

**做法**: 每条 log 条目记录 KB/行数/章节数，每个 index 条目记录"一句话摘要"，每个文档记录创建版本。

**推广价值**: 量化让"知识量增长"可度量和可视化。建议扩展为自动生成的周报指标：新增文件数/行数/章节、交叉引用增长率、冷热文件比。

## §八 多人协作的挑战与解决

### 8.1 核心问题：AI 知识库不是"单用户系统"

当前本工程本质上是**单 AI Agent + 单用户**模式。扩展到多人协作时，会暴露以下根本矛盾：

```ascii
单人模式（当前）:
  用户 ↔ AI Agent -> 直接写 knowledge/
  优点: 快速、一致、无沟通开销
  缺点: 全局串行、无并行能力、依赖 AI 的上下文

多人协作模式（目标）:
  用户A ↔ AI Agent_A -+
                       +---> 共享 knowledge/
  用户B ↔ AI Agent_B -+
  问题: Agent_A 不知道 Agent_B 改了啥、Agent_B 看不到 Agent_A 的上下文
```

### 8.2 具体问题清单

#### 🔴 P0 — 上下文丢失

| 场景 | 痛点的具体表现 | 根因 |
|:-----|:-------------|:-----|
| **跨会话断点** | Agent_A 花了 2 小时归档了一批资料，做了 17 个修正。下一轮用户说"继续"，Agent 完全不知道已做过什么 | 每次会话是独立上下文，session-keeper 只能保存显式 checkpoint，无法感知"隐性进展"（如修正了某文件中的哪几处数据） |
| **多 Agent 打架** | Agent_A 在 log.md 追加了 07-16 的日志，Agent_B 写 07-16 日志时把 Agent_A 的覆盖了 | 无文件锁、无编辑冲突检测、无操作序列号 |
| **状态感知盲区** | Agent_A 在做 `02_rd/log.md` 的当日汇总，Agent_B 同时移动了 3 个文件——Agent_A 的日志条目引用路径已失效 | 无实时变更广播机制 |
| **指导原则漂移** | 用户告诉 Agent_A "文档模板改为用表格"，Agent_B 下次会话不知道，继续用旧格式 | USER.md/AGENT.md 等全局文件的更新不会自动通知所有 Agent 实例 |

#### 🟡 P1 — 流程打通

| 场景 | 痛点的具体表现 | 根因 |
|:-----|:-------------|:-----|
| **Review 流程缺失** | Agent_A 创建文档，Agent_B 想 review，但不知道怎么标记"待审/已审/需修改" | 无文档状态机。当前是 Write → Done，中间无 Review Gate |
| **合并冲突** | 两人同时编辑同一份文档的不同段落，后保存的人覆盖前一个人的修改 | 无 diff+merge 机制。Markdown 不是结构化格式，无法像代码一样做三路合并 |
| **修改通知没有** | Agent_A 修改了核心参数表，用了新数据写报告。Agent_B 不知道，还在引用旧数据 | 无订阅/通知机制。@ref 系统是 pull 模式（定期检测），不是 push 模式 |

#### 🟢 P2 — 权限与责任

| 场景 | 痛点的具体表现 | 根因 |
|:-----|:-------------|:-----|
| **操作责任追溯** | log.md 显示"新增文件 X"，但不知道是谁做的 | 当前 log 不记录操作者身份 |
| **敏感操作越权** | 任何人都可以移动目录、删除文件（到 bak） | 无角色分级（管理员/编辑者/读者） |
| **并行任务跟踪** | 多人在不同模块工作，不知道对方当前在做什么 | 无任务板/看板 |

### 8.3 解决思路

```ascii
方案一 (轻量): 文件级操作日志 + 会话头快照    <- 适合 2-3 人团队
  - log.md 每条记录追加 @who 标记（如 @lzh/@cow）
  - 每次会话开始前读取上次 log 的最后 N 条
  - 关键文件（index.md/log.md/MEMORY.md）写前先读再追加

方案二 (中量): Git 作为底层协作层            <- 适合 3-10 人团队
  - 每次操作自动 commit（AI 写 commit message）
  - Git 的 diff/merge/log/blame 天然解决冲突追踪
  - 用 branch 做 Review 流程（PR/MR 模式）
  - 示例工作流:
    main <- 稳定发布
    +-- agent-a/feature-xxx <- Agent_A 的工作分支
    +-- agent-b/fix-yyy    <- Agent_B 的工作分支

方案三 (重量): 事件总线 + 状态服务器          <- 适合 10+ 人/多 Agent
  - 每个操作发布事件（file:created / file:modified / ref:updated）
  - Agent 订阅关心的主题
  - 状态服务器维护文件锁 + 版本号 + 变更序列
  - 类似 Apache Kafka + ZooKeeper 模式，但简化为轻量服务
```

**对本工程的推荐路径**：先引入方案一的 `@who` 标记 + 方案二的 Git 底层（目前已有 `.gitignore`，但尚未启用自动 commit 流程），待规模扩展后再评估方案三。

## §九 动态信息处理与 MCP 方案

### 9.1 问题：知识库的"信息衰减"

知识库一旦创建，就进入**信息衰减曲线**：

```ascii
信息准确度
  100% +▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇ 刚创建完成
       |                          ↘
   90% +                           ▇▇▇▇▇▇▇▇ 1 周后
       |                                      ↘
   80% +                                       ▇▇▇▇▇▇ 1 个月后
       |                                                 ↘
   60% +                                                  ▇▇▇▇ 3 个月后
       |                                                        ↘
   40% +                                                         ▇▇ 6 个月后
       +-----------------------------------------------------------> 时间
```

核心原因：**知识库是静态快照，外部信息是动态流**。行业参数（如 NVIDIA GPU 规格、PCIe Gen6 速率、液冷标准）每年都在变，但文档中的数字不会自动更新。

### 9.2 当前方案：手动刷新 + 自动化检测

当前本工程的做法是"写时认真+定期自查"：

| 层 | 方法 | 示例 |
|:---|:-----|:-----|
| **创建时** | 量化数据标注来源、日期、置信度 | "NVIDIA H100: 3.35TB/s (HBM3, 来源: NVDA 官方白皮书 2024Q3)" |
| **检测时** | @ref L2/L3 检测内容漂移 | `ref-drift-detector.py` 对比 content hash |
| **刷新时** | 工具文档（如 PCIe 分析）定期更新 | 2026-07-16-36-pcie-system-deep-analysis.md v1.0(v1.0→v2.0 当日扩展) |

**局限**：纯 pull 模式——没有外部信息的自动接入，全靠 AI 或用户触发刷新。

### 9.3 MCP 方案：从 Pull 到 Push+Refresh

**MCP（Model Context Protocol）** 的核心思想是：给 AI Agent 暴露一组标准化的工具接口，Agent 可以在需要时主动调用这些工具获取实时信息，而非依赖静态副本。

#### 9.3.1 知识库场景的 MCP 架构设计

```ascii
+------------------------------------------------------------------+
|                     AI Agent（知识管理者）                         |
|   +--------------+  +--------------+  +---------------------+   |
|   | 文档创建 Skill|  | 索引维护 Skill|  | 质量检查 Skill       |   |
|   +------+-------+  +------+-------+  +---------+-----------+   |
|          |                 |                     |               |
|          +--------+--------+---------------------+               |
|                   |                                              |
|          +--------v--------+                                     |
|          |   MCP Client    |  <- Agent 通过 MCP 调用外部工具      |
|          +--------+--------+                                     |
+-------------------+----------------------------------------------+
                    |
    +---------------+---------------+
    |               |               |
+---v---+     +-----v-----+   +---v----+
|MCP Server 1| |MCP Server 2|   |MCP Server 3|
|行业数据源   | |标准规范源   |   |社区动态源  |
+-----------+ +-----------+   +----------+
```

#### 9.3.2 建议的 MCP 工具清单

| MCP 工具 | 数据源 | 更新频率 | 用途 |
|:---------|:-------|:--------:|:-----|
| **`query_parameter_db`** | 核心参数表（速率/带宽/功耗/延迟） | 事件驱动 | 文档创建/更新时自动拉取最新基线 |
| **`check_spec_update`** | 标准组织（PCI-SIG/JEDEC/IEEE/OCCP） | 每周 | 检测标准版本变化，触发关联文档刷新 |
| **`fetch_vendor_latest`** | NVIDIA/AMD/Intel 厂商官方规格 | 每周 | 检测竞品参数变化，标记过时数据 |
| **`query_dependency_graph`** | 本知识库 @ref 依赖图 | 每次调用 | 回答"这个参数被哪些文档引用" |
| **`notify_stale_doc`** | 所有 >3 个月未更新的文档 | 每月 | 主动推送冷数据告警 |
| **`auto_refresh_ref`** | @ref 标记的源文档 | 事件驱动 | 源文档已更新时，自动触发引用方文档的刷新工作流 |

#### 9.3.3 实现路线

```ascii
Phase 1 (轻量级): 脚本化 MCP <- 现阶段的可行起点
  - 不引入 MCP Server 基础设施
  - 将现有 scripts/check/ 工具族包装为可被 AI 调用的标准化接口
  - 每个脚本返回 JSON 格式结果，AI 可解析
  - 示例: `python scripts/check/ref-drift-detector.py --json`

Phase 2 (MCP 化): 轻量 MCP Server
  - 用 Python 的 FastMCP 或 Node.js 的 @modelcontextprotocol/sdk 构建轻量服务
  - 暴露 5-8 个核心工具（如上表）
  - 部署为与 AI Agent 同进程的 subprocess 或本地 socket 服务
  - 重点: 外部数据源的标准化接入接口

Phase 3 (事件驱动): 订阅-推送模式
  - 引入变更事件总线（可用 Redis Pub/Sub 或简单的文件 watch）
  - 核心参数更新 -> 自动推送通知给依赖它的文档维护任务
  - 标准版本变化 -> 自动创建"需更新"的待办项
```

### 9.4 MCP vs 本工程现有体系的关系

| 现有体系 | MCP 增强后的效果 |
|:---------|:----------------|
| @ref 标记 | MCP 的 `query_dependency_graph` 可实时查询反向引用 |
| link-validator.py 检查死链 | MCP 的 `check_spec_update` 可检测"链接活着但内容过时" |
| ref-drift-detector.py 漂移检测 | MCP 的 `auto_refresh_ref` 可实现自动触发刷新，而非仅检测 |
| log.md 记录变更历史 | MCP 的事件总线可记录"谁在什么时候改了哪个数据" |
| 人工触发周报 | MCP 的 `notify_stale_doc` 可实现主动推送 |

**关键区别**：当前是**检测到问题报告给人**，MCP 方案是**检测到问题自动触发修复流程**。

## §十 Agent 偷懒的检测与治理

### 10.1 问题的本质

Agent 在执行知识管理任务时"偷懒"——并非恶意，而是**模型的天生缺陷**在特定场景下的表现：

```ascii
Agent 偷懒的原因谱系:

① 上下文窗口耗尽 <- 最常见
   大型知识库操作时上下文被大量文件内容占据
   -> Agent "看到"任务但"看不到"全部细节
   -> 只能挑重点做，放弃非核心部分

② 成本规避 <- 隐性的
   大模型 API 按 token 计费，多步操作成本累积
   -> Agent 倾向于"用最少 token 完成任务"
   -> 跳过检查步骤，不写 log，不做交叉引用

③ 复杂度规避 <- 架构问题
   任务模板定义了 N 个步骤，但 Agent 判断 "前面几步已经够好了"
   -> 在 self-review 时放水，对明显问题视而不见

④ 工具选择懒惰 <- 路径依赖
   遇到问题直接写回复而不是调工具查证
   -> 依赖"幻觉填充"而非"工具验证"
```

### 10.2 具体偷懒模式清单

#### 🔴 P0 — 最常发生且后果严重

| 模式 | 表现 | 本工程案例 | 检测方法 |
|:-----|:-----|:----------|:---------|
| **跳过 log 记录** | 创建/修改了文件，但不在 log.md 追加条目 | 前文 §2.3 分析的"日志遗漏风险" | `check-log-coverage.py` 检测 |
| **省略交叉引用** | 创建文档时只写内容，不维护头部"关联"字段 | 部分孤立文档无任何交叉链接 | `link-validator.py` 可发现孤立文档 |
| **浅层摘要** | index.md 的一句话说"PCIe分析"而不是"PCIe子系统深度分析：Lane划分/Retimer本质/7类检查清单" | 摘要不反映文档实际深度 | `check-summary-currency.py` |
| **省略 index 更新** | 创建了新文件但不追加到对应 index.md | 上次健康检查发现 17 个文件未纳入 index | `analyze-index-coverage.py` |

#### 🟡 P1 — 中等频次

| 模式 | 表现 | 检测方法 |
|:-----|:-----|:---------|
| **质量检查走过场** | self-review 说"已检查"但实际没仔细看 | 随机抽查 + 双重 AI 复核 |
| **量化数据不标注来源** | 写了"带宽 64 GT/s"但没写"来源: PCIe 6.0 Base Spec Rev 0.7" | 正则检测量化数据行是否紧跟来源 |
| **不更新文件头部** | 文档内容已大幅修改，但 `version:`/`日期:` 未升版 | 对比文件 changelog 与文件头部 |
| **规范化不一致** | 有些文件用 `##` 做标题，有些用 `###` | `knowledge-normalizer.py` |
| **bak 移动后不更新引用** | 文件移到 bak 了，但引用它的文档链接还是旧路径 | `link-validator.py` 标记 404 |

#### 🟢 P2 — 偶尔

| 模式 | 表现 |
|:-----|:-----|
| **边界情况忽略** | 只处理正常路径，不处理异常/边界 |
| **不写修订记录** | 文件内 changelog 为空或仅写 "更新" |
| **格式不统一** | 表格不对齐、代码块无 language tag |

### 10.3 治本方案：三层避免机制

本工程已经在多个层面内置了防偷懒机制，这里系统化总结并补充缺口：

#### Layer 1：执行前——任务模板 + 检查清单强制

```ascii
现状（已有）:
  AGENT.md 产出自检清单（6 项）
  light-self-review 技能（常驻，每次任务完成后触发）
  RULE.md 存储规则（按频率匹配位置）
  pipeline-orchestrator 的 6 阶段流水线

缺口:
  ❌ 检查清单是"软约束"—AI 可以说"已检查"但实际上没做
  ✅ 方案: 把检查清单变为"硬件约束"
    - 每次创建文档后，脚本自动验证 checklist 项
    - 未通过验证 -> 阻塞归档 -> 强制补完
```

**建议增加的硬件约束**：

```python
# 强制检查清单（每次写操作后自动执行）
HARD_CHECKS = [
    ("log_record", "log.md 是否有对应条目？", check_log_coverage),
    ("index_update", "index.md 是否已追加？", check_index_coverage),
    ("head_fields", "文件头部 version/date/关联 是否完整？", check_file_head),
    ("cross_refs", "关联字段是否有效？", check_cross_ref_validity),
    ("data_sources", "所有量化数据有来源吗？", check_data_sources),
]

SOFT_CHECKS = [
    ("summary_quality", "一句话摘要是否准确反映内容？"),
    ("format_consistency", "格式是否与同级文档一致？"),
    ("depth_adequacy", "是否停留在框架堆名词？"),
]
```

#### Layer 2：执行中——中间产物检查点

```ascii
现状（已有）:
  pipeline-orchestrator 阶段 4（Ralph 验证循环）
  -> Plan -> Do -> Check -> Act
  -> 最大迭代次数（防止无限循环）
  -> Stop Hook（AI 尝试退出时自动触发验证）

缺口:
  ❌ Ralph 循环只在"整个文档完成"时触发
  ✅ 方案: 增加"中间检查点"
    - 写第 3 章后 -> 检查前 3 章的交叉引用
    - 写第 6 章后 -> 检查所有量化数据来源
    - 写完全文后 -> 最终检查
```

**建议的渐进式检查点**：

| 阶段 | 触发条件 | 检查内容 |
|:-----|:---------|:---------|
| 文档骨架完成 | 写完目录+第1章 | 头部字段完整性、目录与章节一致性 |
| 核心章节完成 | 写完方法/方案章节 | 量化数据来源标注、交叉链接有效性 |
| 全文初稿完成 | 写完所有章节 | 全文一致性、changelog 是否追加 |
| 归档前 | 准备写入 knowledge/ | index.md 更新、log.md 条目、文件格式校验 |

#### Layer 3：执行后——独立审计

```ascii
现状（已有）:
  scripts/check/ 工具族（link-validator, analyze-index-coverage, ref-drift-detector）
  knowledge-health-check 技能（健康度审计）
  周报自动生成（weekly-report-generator）

缺口:
  ❌ 这些是 pull 模式——需要人/AI 主动运行
  ✅ 方案: 改为 push 模式——定时自动执行 + 结果推送
```

**建议的自动化审计 cron 任务**：

| 频率 | 任务 | 脚本 | 输出 |
|:-----|:-----|:-----|:-----|
| **每次写后** | 强制硬件检查 | 内嵌到 write/edit 工具中 | 阻塞/通过 |
| **每日** | 基础健康扫描 | `kb-health.py` | 摘要报告 |
| **每周** | 深度审计 | `analyze-index-coverage.py` + `ref-drift-detector.py` | 完整报告 + 周报 |
| **每月** | 目录结构审计 | `directory-architect.py` | MECE 分析 + 重构建议 |

### 10.4 Agent 偷懒 vs 合理简化的边界

并非所有"不全做"都是偷懒——需要区分：

| 情形 | 是偷懒吗？ | 判断标准 |
|:-----|:---------:|:---------|
| 批量操作 17 个文件时 log 只写 1 条总条目 | ❌ 合理简化 | 批量操作归一化（见 §2.3 建议） |
| 批量操作后所有 17 个文件都做了，但 log 写成了"更新了文件" | ✅ 偷懒 | 日志太模糊，无法追踪具体变更 |
| 300 行文档写了一个 50 字的摘要 | ❌ 可接受 | 一句话摘要规范就是 30-60 字 |
| 300 行文档的摘要写成了"这是一个文档" | ✅ 偷懒 | 摘要没有信息量 |
| 文档不引用任何关联文件（因为确实没有关联） | ❌ 合理 | 孤立文档也合理（如独立方法论） |
| 引用了关联文件但"关联"字段为空 | ✅ 偷懒 | 知道关联但不写 |

**判断原则**：**可自动化验证的部分跳过了 = 偷懒；需要人类判断的部分简化了 = 合理权衡。**

### 10.5 总结：防偷懒体系现状与补全

```ascii
防偷懒能力矩阵:

                              ❌ 缺失           ✅ 已有
                              +-----+-----+-----+-----+
                          软  |     |     |     |  ★  | 自检清单
                          约  |     |     | ★★  | ★★  | pipeline 检查点
                          束  |     |     |     |     |
                              +-----+-----+-----+-----+
                          硬  |     |  ★  | ★★  | ★★  | 脚本自动化检查
                          约  |  ★  | ★★  | ★★  | ★★  | 强制阻塞检查
                          束  |     |     |     |     |
                              +-----+-----+-----+-----+
                               创建前  创建中  创建后  归档前

  注: ★ = 有覆盖  ★★ = 强覆盖
  白色 = 当前缺口 -> 增加硬件约束检查
```

**当前最大的三个缺口**：

1. **"软约束"过多**——检查清单靠自觉，AI 可以"说已检查"但实际没做
2. **检查后置**——大部分检查在"创建后"而不是"创建中"，发现问题时已经花了大量 token
3. **无自动重试机制**——检测到问题后不自动触发修复，而是报告给用户（成了用户的工作）
