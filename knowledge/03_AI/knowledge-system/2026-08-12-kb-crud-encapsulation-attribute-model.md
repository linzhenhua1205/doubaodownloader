## 核心命题

CRUD 只是最底层原子操作，知识库/域化 MoE 架构必须做**多层封装**：在原子 CRUD 之上封装知识层高阶操作（Create/Read/Update/Delete 领域化 + 六大扩展操作），并配套完整的**属性元模型**（五类正交维度）约束所有操作——数据/知识的操作与属性需要全面认知，才能支撑「可描述、可过滤、可路由、可审计」的治理体系。

## 关键洞察

### 1. 为什么裸 CRUD 会破坏分域+MoE 体系

- 裸 Update：无差别覆盖不同域的同源知识 → 跨域污染
- 裸 Delete：物理删除丢失溯源链路 → 无法回溯纠错
- 裸 Read：全表扫描绕过门控路由 → 破坏 MoE 专家路由逻辑

### 2. 第一层：CRUD 领域封装 → 知识层高阶操作

| 原子操作 | 知识层封装 |
|:---------|:-----------|
| **Create** | 域归属打标 → 数据源分级 → 置信度初始化 → 切片归一 → 实体链接 → 路由进对应 MoE 专家库，拒绝全局乱插 |
| **Read** | 禁止裸 SQL/向量全量查询；强制走网关：权限域过滤 → MoE 门控选库 → 置信度加权召回 → 冲突裁决；支持只读/可读/私有可见三种模式 |
| **Update** | 不物理覆盖，走版本链：新版本实体 → 旧版本归档冻结（只读）→ 更新图谱边权重 → 重算置信度，保留修改日志与修改人域身份 |
| **Delete** | 几乎不用物理删：逻辑归档（打废弃标记保留溯源）/ 域隔离拉黑（仅某域禁用）/ 彻底销毁（需多级域权限审批，涉密数据） |

### 3. 第二层：知识库独有六大扩展操作

- **Link**：实体关联，碎片切片绑定图谱实体，建立跨切片跨库关系
- **ConflictResolve**：冲突裁决，同源矛盾知识依域优先级+置信度自动/人工裁决
- **Reweight**：置信度重打分，依交互反馈、交叉验证动态修改权重（实现越用越聪明）
- **Migrate**：域迁移，小组域迁企业域时自动重校验权限与置信度
- **Sync**：域间同步，脱敏同步子集向上域流转，禁止原始私有数据外流
- **Audit**：审计溯源，查询一条知识所有修改记录、来源域、调用日志、命中场景

### 4. 知识实体属性元模型：五大正交维度

| 维度 | 核心字段 | 用途 |
|:-----|:---------|:-----|
| **访问权限属性** | 访问域归属、读写模式（可读写/只读/私有/域内可见）、操作主体权限、脱敏标记 | 控制 Read 权限、跨域读取脱敏 |
| **可信度与质量属性** | 静态置信度、动态置信度、证据等级（论文引用/官方/经验/主观）、冲突标记 | MoE 路由排序核心 |
| **版本与时序属性** | 创建/修订/失效时间、版本号、前驱版本、归档状态、时序衰减系数 | 解决 Update 乱覆盖、老知识自动降权 |
| **存储与路由属性** | 归属专家库 ID、向量分片 ID、图谱实体 ID、冷热存储标记 | 支撑 MoE 分专家库、冷热迁移 |
| **溯源与运维属性** | 原始来源 URL/PDF、抓取批次、修改日志 ID、修改者所属域、命中统计 | 审计、清洗、故障排查 |

### 5. 完整工作流

新素材 → 填充全套元属性（先于写库）→ 按域+领域属性走封装 Create 路由进 MoE 专家库 → 查询走封装 Read（权限校验→门控路由→置信排序）→ 修改走 Update 版本化 → 废弃走逻辑归档。

## 🔍 深度辨析报告

### 原理解析

这组对话的实质是**把数据库设计理论（事务、版本、权限、审计）完整映射到知识库场景**，核心洞察是：知识库不只是「向量检索器」，而是一个**知识 OS（操作系统）**——需要像数据库一样定义「操作语义」和「数据模型」。

- **CRUD 封装的本质**：把「无状态的数据操作」升级为「带约束的状态机操作」。Update 版本化 = 数据库的 MVCC（多版本并发控制）思想；Delete 逻辑化 = 软删除（soft delete）模式；Read 强制走网关 = 数据库的查询计划器 + 行级安全。这些在数据库领域都是成熟实践，移植到知识库是合理的「能力迁移」而非新发明。
- **六大扩展操作**：Link/ConflictResolve/Reweight/Migrate/Sync/Audit 对应知识库特有的语义（关系、冲突、信任、域、溯源），是对关系数据库 CRUD 的必要超集——因为知识实体的核心价值在于**关系与可信度**，这是传统数据库表行不具备的维度。
- **五维属性元模型**：对标 Windows 文件属性面板的分层设计（常规/详细/安全/以前的版本/共享），本质是**元数据驱动的可扩展 schema**——主表存实体 ID + 维度外键 + 扩展 JSON，避免超级宽表，这是「EAV（实体-属性-值）模型」与「宽表模型」之间的工程折中。

### 与本知识库体系的对接

- **本系统已有实践**：log.md 的「创建/修改」记录 ≈ 溯源与运维属性；RULE.md 的「改前查头部约束」≈ 访问权限属性；MEMORY.md 的「文档验收规范」≈ 质量属性。但这些都是**纪律层面**，未形成**字段级元模型**。
- **版本时序属性是本系统弱项**：当前 knowledge/ 文件用 Changelog 记录变更，但无版本号/前驱版本/归档状态字段，无法做版本回滚。
- **可落地动作**：设计知识文件头部元数据模板（domain/source_type/confidence/version/status），配合 [知识库质量方法论](2026-07-07-knowledge-quality-methodology.md) 的检查器脚本实现部分自动校验。

### 批判性评估

- ✅ **强项**：操作封装完整覆盖了「增删改查」到「治理」的全部语义；属性五维划分正交清晰，且与 Windows 类比便于理解；「先填属性再写库」的流程约束正确。
- ⚠️ **挑战 1：封装过重的成本**——每条知识入库都要走 6 步封装（打标→分级→置信→切片→链接→路由），对个人知识库高频采集场景是显著 overhead；需要「批量流水线」而非逐条操作。
- ⚠️ **挑战 2：属性完整性与可用性冲突**——五维属性全覆盖要求人工/自动填充大量字段，若自动抽取不准、人工不愿填，属性体系会退化为空壳；需要分级：核心属性（域/来源/置信）强制，边缘属性可选。
- ⚠️ **挑战 3：版本链的存储成本**——每条 Update 生成新版本，长期积累版本膨胀；需要快照合并策略（如定期折叠旧版本）。
- ❌ **未覆盖**：属性 schema 的演进管理（新增维度如何迁移存量数据）、多用户并发编辑的锁/事务协议。
