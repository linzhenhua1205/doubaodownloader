## 1. 知识质量 ：为什么需要方法论

### 1.1 知识质量的 5 个维度

知识质量不是一维的"对或错"，而是五个独立维度共同决定的特征向量：

```text
知识质量 = f(准确性, 完整性, 时效性, 一致性, 可追溯性)
```

| 维度 | 定义 | 反面 | 检查方法 |
|:-----|:-----|:-----|:---------|
| **准确性** | 断言与事实的匹配程度 | 事实错误、虚假引用、数据偏差 | 多源交叉验证、实验复现 |
| **完整性** | 是否覆盖了读者需要知道的关键信息 | 遗漏上下文、缺少基线、缺条件 | MECE 自检、读者视角审查 |
| **时效性** | 知识反映当前状态的程度 | 过时数据、已淘汰方案、旧版本 | 创建日期审查、持续跟踪 |
| **一致性** | 同一知识在本文件中不自相矛盾 | 前后说法冲突、数据单位不统一 | 维度对齐、全文扫描 |
| **可追溯性** | 断言能否追溯到原始来源 | 无从判断的"据称"，来源不可核实 | 来源链接+访问日期+原文引用 |

**各维度的代价曲线**:

| 维度 | 修复成本 | 常被忽视程度 | 出现频率 |
|:-----|:--------|:-----------|:--------|
| 准确性 | 高（需重新调研） | 极难自查 | 中等 |
| 完整性 | 中（需补充材料） | 常见 | 很高 |
| 时效性 | 中（需更新数据） | 常见 | 很高 |
| 一致性 | 低（文本编辑） | 最易忽视 | 高 |
| 可追溯性 | 低（加引用） | 非常常见 | 极高 |

> **反直觉规律**: 准确性的检查成本最高但出现频率中等；可追溯性的检查成本最低但常被忽视。**优先保证可追溯性，能大幅降低后续准确性验证的边际成本。**

### 1.2 质量不是检查出来的

**关键认识**: 知识质量不是写在文档末尾的检查清单能保证的，而是嵌入知识创建全过程的**约束条件**。

```text
传统观念:
  创建 -> 完成 -> 审查 -> 修复 -> 交付
                      ^
                质量是"事后把关"

正确观念:
  约束 -> 创建 -> 自检 -> 审查 -> 闭环
    ^                     ^
  源头质量约束         过程验证

  "质量不是检查出来的，是设计出来的。"
```

**三种质量保障模式的成本曲线**:

| 模式 | 单位缺陷修复成本 | 典型场景 |
|:-----|:---------------|:---------|
| 🔴 **事后检查** (检测→修复) | 1× (基线) | 既有知识库批量审计 |
| 🟡 **过程控制** (创建中约束) | 0.2-0.3× | 新文档创建 |
| 🟢 **源头预防** (模板+规范) | 0.05-0.1× | 系统化知识沉淀 |

> **结论**: 投入在模板设计、规范制定、自动化检查工具上的每一小时，相当于节省后续修复的 10-20 小时。

### 1.3 规模的陷阱

知识库规模增长与质量的关系不是线性的——存在**临界点效应**：

```text
知识条目数         质量特征                   风险
----------        ------------------        ----------
1-100             每条可人工审核              低
100-500           抽样审核                    中
500-2,000         仅自动化检查                高
>2,000            检查覆盖率 <10%             极高

规律: 当条目 >500 后，人工逐条审核不再可行。
      质量保障必须从"条目级"转向"系统级"——
      即保证知识库的 结构完整性 > 每条知识的准确率。
```

> CowAgent 知识库目前 1,252+ 文件，已经远超人工逐条审核的边界。质量策略必须从「每条都对」变为「每类都有保障机制」。

## 2. 多源验证

### 2.1 知识层级金字塔

不同来源的知识可信度不是同等的，必须建立层级化的优先级：

```text
                                 可信度
                                 ^
                                 |
      论文/标准原文                |  ⬛  最高 (source of truth)
      (IEEE, arXiv, JEDEC,       |  ##
       PCI-SIG, IBTA, OCP)       |  ###
                                 |  ####
      官方技术白皮书              |  #####
      (NVIDIA, Intel, AMD,       |  ######
       Arm, Samsung Datasheet)   |  #######
                                 |  ########
      一线工程报告                |  #########
      (SOSP/OSDI/ATC 论文,       |  ##########
       Backblaze, Meta 工程)     |  ###########
                                 |  ############
      主流行业分析                |  #############
      (SemiAnalysis, DIGITIMES,  |  ##############
       The Next Platform)        |  ###############
                                 |  ################
      通用知识 (Wiki, 博客,      |  #################
       教程, 新闻)               |  ##################
                                 +------------------------
                                  低              优先级
```

**使用规则**:

1. **取材时优先选高层级**: 能用论文不用博客，能用官方白皮书不用行业分析
2. **至少覆盖 2 个层级**: 单层级来源（尤其低层级）须标注为"待验证"
3. **高层覆盖底层**: 论文结论 > 官方白皮书 > 行业分析 > 通用知识
4. **底层可验证高层**: 当行业分析与论文矛盾时，以论文为准并标注冲突

### 2.2 三角验证法

单一来源不可信。最小可信知识需要 **3 个独立来源** 的支撑——这是知识质量保障的"黄金律"：

```text
                  来源 A
                 /     \
                /       \
               /    ✅    \
              /     知识    \
             /              \
            /________________\
         来源 B              来源 C
```

**三角验证的规则**:

| 条件 | 置信度 | 判定 |
|:-----|:-------|:-----|
| 3 个独立源，结论一致 | ≥95% | **可信**，可作为断言引用 |
| 2 个独立源，结论一致 | ~80% | **较可信**，标注"多源一致" |
| 1 个权威源（论文/标准） | ~70% | **可引用**，标注"单源" |
| 1 个非权威源（博客/论坛） | ~30% | **不可靠**，标注"待验证" |
| 无源 | ~5% | **不可用**，需删除或标注为推测 |

**独立源的判定**: 两个来源不能指向同一篇原始材料。例如：

- ❌ 博客 A 引用论文 X + 博客 B 引用论文 X = 1 个独立源（论文 X）
- ✅ 论文 X + 官方白皮书 Y + 工程报告 Z = 3 个独立源

### 2.3 独立源·依赖源·佐证源—三级可靠性模型

来源可分为三个可靠性层级：

| 层级 | 类型 | 说明 | 示例 |
|:-----|:-----|:------|:-----|
| **独立源** 🥇 | 自包含的第一手信息 | 不依赖其他来源，原创数据/结论 | 论文、标准、官方规格书、实测报告 |
| **依赖源** 🥈 | 基于独立源的二次加工 | 可追溯到独立源，但不保证完全忠实 | 白皮书精简版、技术博客（有引用）、行业分析 |
| **佐证源** 🥉 | 非原始、非系统的参考信息 | 提供背景但不足以作为证据 | 论坛讨论、知乎回答、新闻摘要 |

**知识创建时的标注规则**：

```text
在知识条目中标注每个关键断言的来源类型:

✅ 独立源:  [来源: IEEE 802.3ck-2023 §5.2]
✅ 依赖源: [来源: NVIDIA GTC 2025 presentation, 基于未公开内部数据]
✅ 佐证源: [来源: SemiAnalysis, "H100 Margins", 2024]
❌ 无源:   无标注 -> 需要删除或补充
```

### 2.4 源冲突的协议规则

当不同来源对同一事实给出不一致的信息时，按以下协议处理：

```text
冲突处理协议（按优先级排列）:

1️⃣ 标准 > 论文 > 白皮书 > 行业分析
   +- 如果存在正式标准 (IEEE/JEDEC/PCI-SIG) 以标准为准

2️⃣ 实测 > 仿真 > 估算
   +- 实际测量数据优先于仿真推导

3️⃣ 近期 > 远期（同类型源）
   +- 只对同一来源类型，更新近的优先

4️⃣ 第一手 > 第二手
   +- 实际参与者/厂商数据 > 第三方分析

5️⃣ 注释冲突但不掩盖
   +- 在文档中注明两个来源的差异和可能原因

冲突示例:
  "NVIDIA 官方称 H100 HBM 带宽为 3.35 TB/s,
   SemiAnalysis 分析估计实际有效带宽约 3.0 TB/s
   （差异原因: 官方标称值基于理论峰值，实际受
   ECC/地址映射/工作负载影响有 ~10% 折扣）"
```

### 2.5 溯源标注规范

每条关键断言在知识库文档中的标注格式：

```markdown
**断言内容**: H100 SXM GPU 的 HBM3 带宽为 3.35 TB/s
**来源**: [NVIDIA H100 Whitepaper, Table 1, 2023]
**类型**: 独立源 🥇（官方规格书）
**交叉验证**: [Micron HBM3 Product Brief] 确认 HBM3 3.2 Gbps/pin
   → 3.35 TB/s = 80 HBM 通道 × 3.2 Gbps × 1024 bits/cycle × 64× 累加因子
   → 第一性原理验证通过 ✅
```

**在文档中的实际呈现**: 简化为可靠来源链接 + 方法说明：

```markdown
- H100 HBM 带宽 3.35 TB/s [来源: NVIDIA H100 Whitepaper, 校验: 通过 Micron HBM3 规格书反算]
- LLaMA-3 70B 推理吞吐 ~350 tokens/s on 2×H100 [来源: vLLM 官方基准, batch=32, FP8]
```

## 3. 正反方向验证

### 3.1 正向验证：从数据到结论

正向验证（Forward Validation）是**归纳逻辑**——从具体数据点出发，看是否能推导出结论。

```text
正向验证流程:

  数据/事实 -> 逻辑推理 -> 结论
     v                     v
  可验证的基础           可证伪的断言

  核心问题: "给定这些数据，结论是合理的吗？"
```

**操作框架**:

| 步骤 | 操作 | 检查点 |
|:-----|:-----|:-------|
| 1. 收集数据 | 列出所有相关的事实和数据 | 数据来源是否可靠？数据是否完整？ |
| 2. 建立推理链 | 数据 → 中间结论 → 最终结论 | 每步推理是否有跳跃？是否有隐含假设？ |
| 3. 检查强度 | 推理是否足够支撑结论 | 结论超出数据范围了吗？ |
| 4. 标注置信度 | 给定数据的结论确定性 | 数据完整度/准确度/代表性 |

**实例**: 正向验证 KV Cache 带宽需求

```text
Data: LLaMA-3 70B, 80 layers, 8 KV heads, d=128, FP16
       -> KV_per_token = 2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 0.31 MB

Data: H100 HBM BW = 3.35 TB/s

Forward推理: T=32K, ITL下限 = (0.31 MB × 32,000) / 3.35 TB/s = ~2.96 ms

结论: ITL 约 3ms
验证: -> vLLM 实际测试 70B @ T=32K, ITL ≈ 3.0-3.5ms ✅
      -> 正向推算与实测一致，置信度很高
```

### 3.2 反向验证：从结论回溯证据

反向验证（Reverse Validation）是**演绎逻辑**——从结论出发，回溯看能否找到足够的证据支撑。

```text
反向验证流程:

  结论 -> 需要哪些证据 -> 寻找证据 -> 评估证据充足性
   v                      v
  可证伪的断言          每个断言都需要独立证据

  核心问题: "如果这个结论是真的，我应该能看到什么证据？"
```

**操作框架**:

| 步骤 | 操作 | 检查点 |
|:-----|:-----|:-------|
| 1. 提取断言 | 将结论分解为独立的可验证断言 | 每个断言是否可证伪？ |
| 2. 反问 | "如果这个断言是真的，我还应该看到什么？" | 有没有没想到的证据维度？ |
| 3. 找证据 | 寻找支撑每个断言的独立证据 | 证据来源可靠吗？有替代解释吗？ |
| 4. 查矛盾 | 有没有反向证据？"如果断言是假的会怎样？" | 被动找一个"证伪"案例 |

**实例**: 反向验证"KLX 512 存储网不满足 KV Cache 延迟 SLO"

```text
断言: KLX 512 存储网 P99.9 延迟 > 1ms 不满足 SLO

反向验证:
  "如果这个断言是真的，我应该看到什么？"
  -> KLX 存储链路有显著的延迟瓶颈
  -> 某个具体路径（PCIe/RoCE/SSD）的延迟超出预期

  "如果这个断言是假的呢？"
  -> 所有路径的延迟累加仍在 SLO 范围内
  -> 从 GPU HBM -> PCIe SW -> BF3 -> 400G NIC -> 交换机 -> JBOF SSD
    各段延迟之和 < 1ms

实际验证:
  GPU->PCIe: ~0.3 μs
  PCIe SW: ~0.5 μs
  BF3 处理: ~5 μs
  400G RoCE: ~3 μs
  交换机: ~2 μs
  JBOF SSD: ~150 μs (P99)
  合计: ~161 μs << 1ms ✅ -> 原始断言不成立

✅ 反向验证 通过: 无法找到支持该断言的关键证据
    实际延迟约 161 μs << 1ms SLO
```

### 3.3 正反闭环：严丝合缝

真正的知识质量来自**正反双向验证同时通过**——双向闭环意味着没有逻辑缝隙。

```text
正向: 数据 -> 推理 -> 结论
                        ↘
                          ✅ 双向验证通过
                        ↗
反向: 结论 -> 反向推理 -> 验证证据

当正向和反向在同一结论处重合时，称为"双向闭合"。
这是知识质量最高置信度的标志。
```

**双向闭合的 4 种状态**:

| 状态 | 正向验证 | 反向验证 | 置信度 | 操作 |
|:-----|:--------|:--------|:-------|:-----|
| ✅ **严丝合缝** | 通过 | 通过 | ≥95% | 可直接使用 |
| ⚠️ **单向支撑** | 通过 | 未通过 | ~60% | 需补充反向证据或修正结论 |
| ⚠️ **逻辑悬空** | 未通过 | 通过 | ~50% | 数据不足但结论方向对，需补数据 |
| ❌ **断裂** | 未通过 | 未通过 | <10% | 结论可疑，应删除或重写 |

### 3.4 假阳性与假阴性检测

知识质量中最危险的两种错误：

```text
假阳性 (False Positive): 接受了错误的断言 -> 知识库中有错误信息
  例子: 声称"KLX 512 存储网延迟 >1ms"但实际上只有 161 μs

假阴性 (False Negative): 拒绝了正确的断言 -> 知识库遗漏了有用信息
  例子: 因为单源而不相信"NVLink 5 带宽 1.8 TB/s"(实际是官方公布的)

检测方法:
  假阳性 -> 反向验证 + 三角交叉验证 + 证伪思维
  假阴性 -> 正向验证 + 查找替代解释
```

| 错误类型 | 代价 | 发现难度 | 优先级 |
|:---------|:-----|:---------|:-------|
| ❌ 假阳性（错误接受） | 高——错误的决策依据 | 高 | **P0** |
| ❌ 假阴性（错误拒绝） | 中——遗漏有用信息 | 低 | P1 |

> **规则**: 当知识不确定性高时，宁可标注为"待验证"（容忍假阴性），也不要贸然接受（避免假阳性）。"我不知道"比"我知道但错了"安全 100 倍。

## 4. 场景化质量方案

### 4.1 数据类型 × 质量策略矩阵

不同知识类型的最优质量保障策略不同：

| 知识类型 | 主要质量挑战 | 最有效的验证方法 | 优先级 |
|:---------|:-----------|:----------------|:-------|
| **技术规格** | 数据精确性 | 标准原文对照 + 厂商规格书比对 | P0 |
| **性能数据** | 条件完整 + 可复现 | 量化四要素 + 业界基线校准 | P0 |
| **架构分析** | 逻辑严谨 | MECE 分域 + 第一性原理 + 正反验证 | P0 |
| **行业洞察** | 时效性 + 多角度 | 多源趋势交叉 + 定期刷新 | P1 |
| **论文/研究** | 引用准确 + 结论恰当 | 双路径复现 + 原始论文核对 | P1 |
| **流程/规范** | 可执行性 | 读者走查 + 实操验证 | P2 |
| **Agent 生成** | 幻觉 + 编造引用 | 逐条溯源 + 事实核查 | P0 |

### 4.2 技术规格类

**典型内容**: 芯片参数、接口标准、协议规范、物理尺寸、电气特性

**质量方案**:

| 验证项 | 方法 | 工具/来源 |
|:-------|:-----|:----------|
| **标准原文比对** | 直接查阅标准文档（IEEE/JEDEC/PCI-SIG/IBTA） | 标准组织官网 |
| **厂商规格书对照** | 对比 2+ 厂商的官方规格书 | Datasheet、TRM |
| **第一性原理反算** | 从基本原理推算看是否自洽 | 独立计算验证 |
| **交叉产品验证** | 在不同产品维度交叉验证同一参数 | 系统级验证 |

**检查清单**:

```markdown
- [ ] 每个数值有出处（标准号/章节/页码）
- [ ] 数值与标准原文一致（不是二手/三手转述）
- [ ] 从第一性原理反算不矛盾（带宽 = 频率 × 位宽 × 通道数）
- [ ] 2 个以上独立源确认
- [ ] 区分"理论值""典型值""最小值"不同口径
```

**常见陷阱**:

- 把"典型值"当"保证值"（如 PAM4 信号下 SerDes 速率 vs 有效带宽）
- 混淆单向和双向带宽（PCIe Gen5 ×16: 64 GB/s 单向 vs 128 GB/s 双向）
- 忽略编码开销（128b/130b 编码、FEC 开销）

### 4.3 性能数据类

**典型内容**: 吞吐量、延迟、带宽利用率、加速比、能效比

**质量方案**:

| 验证项 | 方法 | 检查点 |
|:-------|:-----|:-------|
| **量化四要素** | 数值 + 单位 + 对比基线 + 测试条件 | 缺一不可 |
| **业界基线校准** | 与至少 2 个独立来源的同类数据对比 | 偏差 <30% |
| **理论极限判定** | 超过物理极限的数据必定有误 | 带宽不能超 Shannon 极限 |
| **复现性检查** | 相同条件下是否能得到相近结果 | 误差 <10% |
| **Roofline 一致性** | 性能是否在 Roofline 模型预测范围内 | 不超过天花板 |

**量化四要素的标注规范**:

```text
✅ 正确格式: "KV 读取 1.4 GB/s（fio randread, bs=32M, iodepth=16,
              单 GPU, FP16, KLX M300）"

❌ 错误格式: "KV 读取 1.4 GB/s"
  缺少: 测试工具、块大小、队列深度、并发数、精度、硬件
```

**性能数据可信度分级**:

| 级别 | 条件 | 标注 |
|:-----|:-----|:-----|
| 🥇 **基准级** | 官方 benchmark + 完整条件 + 可复现 | `[基准: vLLM v0.6, T=2K, FP8, B=1]` |
| 🥈 **参考级** | 第三方报告 + 基本条件 | `[参考: SemiAnalysis, 2025, H100推理]` |
| 🥉 **估算级** | 理论推算 + 假设条件 | `[估算: Roofline 模型, 65% 利用率假设]` |
| ❌ **推测级** | 无来源、无条件的"据称" | 不可用 |

### 4.4 架构分析类

**典型内容**: 系统架构分析、设计方案对比、技术路线评估、瓶颈分析

**质量方案**:

| 验证项 | 方法 | 检查点 |
|:-------|:-----|:-------|
| **MECE 分域** | 同层分类互斥且穷尽 | 有无遗漏类别？有无重叠？ |
| **第一性原理** | 从物理/经济/信息论根本约束推导 | 结论是否依赖隐含假设？ |
| **维度对齐** | 对比方案时统一分析维度 | 是不是 apples-to-apples？ |
| **替代方案列举** | 至少列出 3 个可选方案 | 是不是只选了"好的"？ |
| **正反验证** | 正向从数据到结论 + 反向从结论找证据 | 是否双向闭合？ |

**分析框架选择**:

```text
技术选型: 维度对齐 -> 统一量纲 -> 对比矩阵 -> 决策树
瓶颈分析: Roofline -> 分层瓶颈定位 -> 受限(计算/带宽/延迟)
趋势判断: 五看三定 -> 时间线 -> S曲线 -> 拐点识别
根因分析: 鱼骨图 -> 5Why -> 根因 -> 修复 -> 预防
```

**架构分析文档的质量标准**:

- 不罗列名词（只写"采用 PAM4 调制"不够，要写"为什么选择 PAM4，信噪比代价是多少"）
- 给出量化对比（至少 3 个方案在统一维度下的数据表格）
- 自洽（不自创分类、不使用互斥的分类标准）
- 可证伪（能设计实验验证或反驳）

### 4.5 行业洞察类

**典型内容**: 市场趋势、竞争格局、技术演进路线、厂商动态

**质量方案**:

| 验证项 | 方法 | 检查点 |
|:-------|:-----|:-------|
| **时效性检查** | 数据点的日期标注 | 是否创建/更新日期可见？ |
| **多角度确认** | 从不同利益方视角看同一事件 | 是否只采信了单一视角？ |
| **趋势模式识别** | 多个独立事件能否支持同一趋势方向 | 有没有相反方向的信号？ |
| **声明-行动一致性** | 厂商说的 vs 实际做的 | 有没有 PR 泡沫？ |
| **风险反向检查** | 如果趋势判断错了呢？ | 是否有充分的风险提示？ |

**行业洞察的特殊要求**:

```text
1. 标注判断时间: "截至 2026-07-01，据 DIGITIMES 报道..."
2. 区分事实与判断: [事实: NVIDIA 官宣 B200 2025H1 出货]
                      [判断: 预计 B200 将占据 60%+ 高端市场]
3. 跟踪连续性: 同主题连续归档，追踪判断变化
4. 冲突标注: 不同分析机构观点相左时并列表述
```

### 4.6 论文/研究类

**典型内容**: 学术论文解读、研究趋势综述、方法论应用

**质量方案**:

| 验证项 | 方法 | 检查点 |
|:-------|:-----|:-------|
| **原文提取** | 从论文原文提取结论，而非摘要/二手引用 | 摘要可能过度简化 |
| **引用保真度** | 引用中的数字是否与论文原文一致 | 数字/单位/条件不改变 |
| **结论边界** | 论文结论的适用范围 | 超范围推广是常见错误 |
| **复现性确认** | 论文方法是否可复现 | 数据集/代码开源？ |
| **发表年限** | 论文是否过时 | 3 年以上论文需补充最新进展 |
| **Peer Review 模拟** | 从审稿人角度找出弱点 | 方法缺陷/实验不充分/结论夸大体 |

**论文引用规范**:

```markdown
[作者, "标题", 会议/期刊, 年份, 链接]
[Patel et al., "Splitwise: Efficient Generative LLM Inference
 Using Phase Splitting", arXiv 2024, https://arxiv.org/abs/...]
```

### 4.7 流程/规范类

**典型内容**: SOP、Checklist、工作流程、操作指南

**质量方案**:

| 验证项 | 方法 | 检查点 |
|:-------|:-----|:-------|
| **可执行性** | 按步骤实际操作是否能完成 | 是否有遗漏步骤？ |
| **边界条件** | 异常情况如何处理 | 错误恢复路径？ |
| **角色明确** | 谁负责、谁执行、谁复核 | RACI 是否清晰？ |
| **版本关联** | 对应的工具/系统版本 | 版本变更后流程是否有效？ |
| **读者测试** | 让没参与编写的人按流程做一次 | 能否独立完成？ |

### 4.8 Agent 生成内容类

**典型内容**: AI Assistant 产出的分析、总结、方案

**质量方案**（这些是自我约束——作为 Agent 的"三不五要"规则）:

| 验证项 | 方法 | 检查点 |
|:-------|:-----|:-------|
| **不编造引用** | 每条引用有可查证来源 | URL 有效、论文可验证 |
| **不编造数字** | 每个数字标明单位和条件 | 无来源数字标注为"估算" |
| **不编造未开源工具** | 不声称不可访问的工具可用 | 仅引用可公开获取的工具 |
| **来源标注** | 关键断言标注来源层级 | 独立源/依赖源/佐证源 |
| **事实核查** | 对不确定的事实先查证 | 知识库已有内容优先 |
| **量化四要素** | 数值+单位+基线+条件 | 缺一不可 |
| **逻辑自检** | 13条逻辑谬误检查 | 不自相矛盾 |
| **边界标注** | 标注假设条件和使用范围 | 不超范围推断 |

### 5.2 逻辑谬误清单（13 条）

来自 MEMORY.md，每次交付前自检：

```markdown
# 逻辑谬误检查（每条问自己: 我犯了下面哪个错误？）

□ 1. 声明-实践不一致 —— 我声称的标准，我在实践中做到了吗？
□ 2. 先验分类 —— 是否在分析前就预设了类别？这个预设合理吗？
□ 3. 模型几何不相容 —— 我用的框架/模型能解释这个问题吗？
□ 4. 术语漂移 —— 我借用的术语是精确引用还是比喻？
□ 5. 类比当定理 —— 我用类比推导出了"必然"结论吗？
□ 6. 内部冲突 —— 我的不同章节之间有矛盾吗？
□ 7. 伪结构 —— 看起来有结构，但分类标准不统一？
□ 8. 空洞同构 —— 结构映射看似一致但实质不同？
□ 9. 维度混淆 —— 不同性质的量在同一个维度上比较？
□ 10. 诠释学循环 —— 用结论去证明同类的假设？
□ 11. 假精确 —— 看似精确的数字实际上无法操作化？
□ 12. 结论前置 —— 先下结论再凑证据？
□ 13. 二元对立 —— 只列两个极端，忽略中间连续谱？
```

### 5.3 量化四要素检查

每次遇到数据格式时，检查是否满足四要素：

```markdown
□ 数值: 明确具体的数字（不是"大约""很多"）
□ 单位: 带单位（μs/GB/s/TFLOPS 等）
□ 对比基线: 和什么比？（vs H100/vs FP16/vs 上一代）
□ 测试条件: 在什么条件下测的？（batch size, 精度, 工具, 硬件配置）

例子:
  🟢 "吞吐提升 28.9%（vs BF16, batch=32, A100-80GB, PyTorch 2.0）"
  🔴 "吞吐提升 30%" — 缺基线、缺条件、缺单位
```

## 6. 质量度量

### 6.1 条目级质量分数

每个知识条目可计算质量分数：

```text
Q_score = w_acc × Acc + w_int × Int + w_time × Time + w_cons × Cons + w_trace × Trace

权重建议:
  w_acc = 0.30  (准确性)
  w_int = 0.15  (完整性)
  w_time = 0.15 (时效性)
  w_cons = 0.10 (一致性)
  w_trace = 0.30 (可追溯性)
```

**评分操作化**:

| 维度 | 5 分 | 3 分 | 1 分 |
|:-----|:-----|:-----|:-----|
| 准确性 | ≥2 独立源验证通过 | 1 权威源确认 | 无来源或单非权威源 |
| 完整性 | MECE 覆盖关键方面 | 主要方面覆盖 | 明显遗漏关键内容 |
| 时效性 | <3 个月 | <12 个月 | >12 个月且无更新 |
| 一致性 | 全文不自相矛盾 | 小矛盾可忽略 | 严重内部冲突 |
| 可追溯性 | 每断言有出处+条件 | 主要断言有出处 | 多数断言无出处 |

## 7. 持续改进闭环

### 7.1 创建→审查→迭代 三阶段

```text
创建阶段       审查阶段       迭代阶段
--------        --------       --------
  |              |               |
  ① 多源采集    ③ 正反验证      ⑤ 修复闭环
  ② 起草文档    ④ 逻辑自检      ⑥ 交叉链接
  |              |               |
  v              v               v
[草稿] -> -> -> -> [1st 审查] -> -> [最终发布]
                 ^               |
                 |               v
               [反馈] <- <- <- [使用中的问题]
```

| 阶段 | 做什么 | 质量工具 |
|:-----|:-------|:---------|
| **创建** | 按规范模板起草；优先使用高层级来源；标注所有来源 | 知识层级金字塔、溯源标注规范 |
| **审查** | 运行自动检查；人工逻辑自检；交叉链接验证 | 13 条逻辑谬误清单、量化四要素、check_links.py |
| **迭代** | 修复审查反馈；补充遗漏来源；优化表述 | 正反验证闭环、多源验证 |

### 7.2 定期巡检与重构

| 周期 | 检查内容 | 负责人/工具 |
|:-----|:---------|:-----------|
| **每日** | 新创建文档的质量快检 | 自检（13 条谬误清单）|
| **每周** | 全库链接检查 + log 顺序 | `knowledge_health_check.py` |
| **每月** | 模块级质量报告（抽样审查） | 模块索引 + 人工抽查 10% |
| **每季** | 时效性普查（>12 月文件复审） | `find -name "*.md" -mtime +365` |
| **半年** | 大重构（目录结构、索引、交叉链接） | 目录重构 + index-rebuilder 技能 |

### 7.3 反馈驱动的知识生命周期

每条知识都应该有"生命周期"，而非"写完即永久"：

```text
                     +------ 创建 ------+
                     |                   |
                     v                   |
                  [活跃期] <- <- 使用反馈
                     |                   |
                     v                   |
                  [审查期] <- <- 定期巡检
                     |                   |
                +----+----+              |
                v         v              |
             [更新]      [归档]          |
                |         |              |
                v         v              |
              [活跃]    [bak/]           |
                     |                   |
                     +---- 重新激活 -----+
```

**知识的退出机制**:

| 操作 | 条件 | 方法 |
|:-----|:-----|:------|
| **更新** | 数据过时 3-12 月，有更准确的新数据 | 在原文件补充/修订，changelog 记录 |
| **归档** | 信息已完全过时、已被取代的技术 | `mv` 到 `tmp/bak/`（原 `knowledge/bak/`）并标注原因 |
| **删除** | 信息错误、无法修复、不再需要 | 极少发生，优先归档（`mv` 而非 `rm`） |
| **合并** | 多个文件内容重叠 | 合并为单个文件，原文件重定向到新文件 |
