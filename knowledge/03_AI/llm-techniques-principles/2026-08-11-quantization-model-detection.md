## 摘要：结论先行（领导 30 秒版）

> **一句话总结**：判断模型是否量化有**四层递进方法**——①读元数据（config.json / GGUF 头 / 张量类型，90% 情况一招制敌）→ ②看文件大小（4bit≈0.5GB/10亿参数，8bit≈1GB，16bit≈2GB）→ ③做权重统计指纹（量化=离散化，唯一值数、直方图形状、量化键名是铁证）→ ④黑盒动态行为（内存占用/输出差异/内核类型）。**底层原理只有一句话：量化把连续权重值压到有限个离散格点，信息熵锐减——凡是能观测到"离散"的信号都可以当判据**。但必须多信号交叉，因为 FP8（浮点但只有 ~240 个值）、BF16（非量化但精度低）、部分量化、剪枝、蒸馏都能骗过单一判据。

**5 条关键结论**：
1. **元数据是正道**：HF `config.json` 的 `quantization_config`、GGUF 文件头的张量类型（Q4_K_M 等）、ONNX 算子（MatMulNBits）都是**作者声明**——最快最准；权重统计是"无声明或声明可疑"时的 forensic 手段
2. **权重指纹三板斧**：①唯一值计数（int4 存储值全局 ≤16 个、int8 ≤256 个）②直方图形状（离散柱 vs 连续分布）③**量化键名指纹**（GPTQ/AWQ 的 `qweight/scales/qzeros`、BitsAndBytes 的 `quant_state` 是排他性铁证）
3. **FP8 是最大的坑**：它是浮点格式（不是整数），但 E4M3 全值域只有 ~240 个有限数——直方图呈离散柱状，**容易被误判为 int8 量化**；它本质是"窄尾数浮点"，判别要靠位模式分析而非整数化判断
4. **BF16 不是量化**：尾数 7bit 是精度截断，但数值连续、文件大小与 FP16 相同（都是 2 字节）——**唯一值计数对 BF16 无效**（值域依旧连续），只能靠行为对比或位格式检查
5. **多信号交叉是铁律**：单一判据全部可被反例绕过（§8），可靠结论 = 元数据 + 文件大小 + 权重统计 ≥2 项一致；黑盒场景（无文件、只有 API）只能靠行为特征给"疑似"结论，**无法证明**

**快速决策表**：

| 你的场景 | 推荐方法 | 置信度 |
|:---------|:---------|:------:|
| 从 HF/网盘下载的模型 | 元数据（config.json/GGUF 头） | ★★★ 确定 |
| 只有模型文件没有说明 | 文件大小 → 权重统计指纹 | ★★★ 确定 |
| 别人的私有格式/加密打包 | 动态行为（内存/速度/输出） | ★★ 疑似 |
| 只有 API 没有模型 | 行为特征（输出对比/延迟/成本） | ★ 推测 |
| 判断"是不是被偷偷量化了" | 权重统计 + 行为对比 + 内核 profile | ★★★ 确定 |

## §1 为什么需要检测（场景与目标分级）

| 场景 | 检测目标 | 失败后果 |
|:-----|:---------|:---------|
| 下载模型后确认规格 | 是否量化 + 比特数 + 方法 | 质量/性能预期错误 |
| 评估平台偷偷降质（"AI 偷懒"审计） | 线上模型是否被量化替换 | 业务质量不可控 |
| 设备兼容性判断（手机/边缘/内存受限） | 能否加载（内存预算） | 部署失败 |
| 模型资产审计/合规 | 是否合规声明一致 | 供应链风险 |
| 安全审计（后门检测前置） | 是否与声明一致 | 信任链断裂 |

> **检测目标分级**：**T1 定性**（是否量化）→ **T2 定量**（几 bit）→ **T3 归因**（什么方法：GPTQ/AWQ/GGUF/BNB/FP8）→ **T4 归位**（哪些层量化、哪些没量化）。越往后越难，但 T3/T4 在审计场景是刚需。

## §2 第一道线：元数据检查（90% 情况一招制敌）

### 2.1 HuggingFace 生态：config.json 的 `quantization_config`

```json
{
  "quantization_config": {
    "quant_method": "gptq",        // gptq / awq / gguf / bitsandbytes / fp8 / squeezellm / hqq ...
    "bits": 4,                      // 4 / 8
    "group_size": 128,              // group-wise 分组
    "desc_act": true,               // GPTQ 的 act-order
    "sym": false                    // 对称/非对称
  },
  "torch_dtype": "float16"          // 推理时反量化回 fp16
}
```

- **`quant_method` 字段 = 作者直接声明**，读到即确定
- 注意：**有些平台会删掉/不提供 config.json**（私有部署、压缩打包）→ 落到 §3/§4
- **config.json 声明 ≠ 文件实际内容**（可能声明 F16 但实际塞了量化权重）→ 高级审计需 §4 交叉

### 2.2 GGUF：文件头张量类型是硬声明（无法伪造的格式约定）

GGUF 格式本身带**每个张量的量化类型**（KV 元数据）：

```
$ llama.cpp/build/bin/gguf  dump  model.gguf        # llama.cpp 自带工具
# 输出示例：
#   tensor  token_embd.weight      : Q6_K
#   tensor  blk.0.attn_q.weight    : Q4_K
#   tensor  output.weight          : F16        ← embedding/output 常保 F16
```

- **GGUF 的量化类型是格式内强制字段**（解析器靠它决定如何解码）——读它 100% 可信
- 常见类型名：`F16 / F32 / Q4_0 / Q4_K_S / Q4_K_M / Q5_K_M / Q6_K / Q8_0 / TQ1_0/TQ2_0`（Q4_K_M 这类是**多级块量化**：256 超块内 8×32 子块，每子块独立 scale+min，见 §7.3）
- **混合类型是常态**：GGUF 允许不同张量不同精度（embedding/output 常 F16）——"部分量化"不是 bug，是设计（§8 陷阱 5）

### 2.3 ONNX：算子类型暴露量化

| 算子 | 含义 |
|:-----|:-----|
| `QLinearMatMul` / `MatMulInteger` | 动态/静态 int8 量化 |
| `DynamicQuantizeLinear` | 动态量化（运行时算 scale） |
| `MatMulNBits` | **4bit 权重量化**（GPTQ/AWQ 导出 ONNX 常见） |
| `ConvInteger` | 量化卷积（CV 模型） |

### 2.4 其他快查点

- **文件名/仓库命名**：`Q4_K_M`、`-AWQ`、`-GPTQ`、`W4A16`、`-int8`、`-bnb-4bit`——约定俗成但**可伪造/可漏标**（只作线索不作证据）
- **safetensors 头**：`safetensors` 文件头是 JSON，含每个张量的 `dtype`——`I8/I32`（量化权重）vs `F16/BF16`（原始权重）一眼可见
- **state_dict 键名**（Python 直接加载时）：见 §4.3 量化键名指纹

## §3 文件级信号：大小与熵（黑盒第一眼）

### 3.1 文件大小反推比特数（第一近似）

| 精度 | 每 10 亿参数占用 | 8B 模型参考 | 13B 模型参考 |
|:-----|:-----------------|:------------|:-------------|
| FP32 | ~4.0 GB | ~32 GB | ~52 GB |
| FP16/BF16 | ~2.0 GB | ~16 GB | ~26 GB |
| INT8 (Q8_0) | ~1.0 GB | ~8 GB | ~13 GB |
| INT4 (Q4_K_M) | ~0.5-0.6 GB | ~4.7 GB | ~7.4 GB |
| INT3 (Q3_K_S) | ~0.4 GB | ~3.5 GB | ~5.5 GB |

**公式**：`文件大小 ≈ 参数量 × bits / 8 + 常数开销`（GGUF 量化常数开销 ~0.2-0.5GB，来自 scale/min 表）

> ⚠️ **此信号只能给"嫌疑"**：文件大 ≠ 未量化（可能塞了额外词典/稀疏权重）；文件小也可能因为剪枝/蒸馏（模型更小但未量化）。**大小必须与 §4 权重统计联合使用**。

### 3.2 熵/压缩率信号（进阶）

- 量化权重的信息熵低 → 用 zstd/xz 再压缩时**压缩比显著高于 FP16**
- 快速实验：`zstd -19` 压缩模型文件，比较压缩率；量化模型（尤其 int4）压缩率通常 > 20%，FP16 通常 < 5%
- ⚠️ 陷阱：GGUF 的 int4 是**打包存储**（2 个 4bit 塞 1 字节）且本身不压缩，zstd 压缩率反而高——这个信号对 GGUF 很有效，对"已压缩打包"的文件无效

## §4 权重统计指纹：底层原理与量化类型指纹表（核心）

### 4.1 底层原理一句话

> **量化 = 把连续权重值映射到有限离散格点（Q(x)=round((x-z)/s)）→ 信息熵锐减 → 一切能观测"离散性"的统计量都是判据。**

- FP16/BF16 权重：值连续分布（唯一值数接近参数规模，直方图光滑）
- 量化权重：存储值只有 2^bits 种（int4=16 种、int8=256 种），或浮点但取值被钳在少量格点（FP8≈240 种）
- **判据强度排序**：唯一值计数（强）> 直方图形状（中）> 数值网格检测（中）> 分块 scale 结构（强，需解析）

### 4.2 量化类型指纹表（判据 → 指纹 → 结论）

| 量化方法 | 存储形态 | 判别指纹 | 检测手段 |
|:---------|:---------|:---------|:---------|
| **GPTQ** | int32 打包（8×4bit）+ `qweight/scales/qzeros` 三键 | 键名铁证 + qweight 唯一值 ≤16（int4） | state_dict 键检查 + unique |
| **AWQ** | 同 GPTQ 结构（qweight/scales/qzeros） | 键名铁证（与 GPTQ 同构，靠 config 区分） | 键检查 + config |
| **BitsAndBytes** | `bnb_Linear4bit` 层 + `quant_state` 键 | `quant_state` 键名排他性 | 键检查 |
| **GGUF (Q4_K_M 等)** | 文件头类型标注 + 打包位域 | 张量类型字段 100% 可信 | `gguf dump` |
| **NF4 (QLoRA)** | 16 个固定非均匀值（正态分位数），2 值打包 1 字节 | **直方图 = 16 根离散柱，且柱位符合正态分位数** | 直方图 + 分位数比对 |
| **FP8 (E4M3/E5M2)** | 浮点格式（1 符号+4/5 指数+3/2 尾数） | **全值域仅 ~240/256 种位模式**，直方图离散但非整数网格 | 位模式计数 + 指数分布检查 |
| **INT8 (weight-only)** | int8 或 fp16 反量化 | 存储 int8 → 唯一值 ≤256；fp16 存储 → 值 ∈ {±127}×scale 网格 | unique + 网格检测 |
| **SmoothQuant (W8A8)** | int8 权重 + 激活量化 | 权重 int8 + **激活层也有量化节点**（需跑图） | 权重检查 + 推理图检查 |

### 4.3 排他性键名指纹（GPTQ/AWQ/BNB，最铁的证据）

```python
# 加载 safetensors 键名（无需完整加载，读头即可）
KEY_SIGNATURES = {
    "gptq/awq":  ["qweight", "qzeros", "scales"],   # 三者同时出现 = GPTQ/AWQ 铁证
    "bitsandbytes": ["quant_state"],                 # bnb 4bit 专属
    "hqq": ["meta", "pack_q8", "scale"],             # HQQ 低比特
    "mlx": ["mlx.quantized"],                        # Apple MLX 量化标记
}
```

> **这是整个检测流程中最强的信号**：这些键名是量化框架在序列化时强制写入的结构，**正常 FP16 模型永远不会出现**（FP16 只有 weight/bias）。出现即定罪。

### 4.4 唯一值计数实操（无键名时的统计判别）

```python
import torch

def unique_count(t):  # t: torch.Tensor
    return torch.unique(t).numel()

# FP16 8B 模型某个 4096×4096 权重层：唯一值通常 > 400 万（接近元素数）
# int8 量化后：≤ 256
# int4 量化后（反量化回 fp16 但按 group 乘 scale）：唯一值 = 16 × group数（每个 group 有独立 scale）
# ⚠️ 关键：GPTQ/AWQ 反量化后唯一值会膨胀（group 数×16），所以：
#   - 看【存储原始值】（qweight int32 打包解包后）→ 全局 ≤ 16（int4）铁证
#   - 看【反量化后 fp16】→ 用"网格检测"（值是否落在 (整数×scale+zero) 网格上）
```

**网格检测**（反量化后权重的判别）：

```python
def grid_test(t, bits=4):
    # 1. 把 t 除以最小间隔的整数倍 → 检查余数是否接近 0
    vals = t.flatten().unique()[:1000]          # 采样即可
    diffs = torch.diff(torch.sort(vals).values) # 相邻唯一值间隔
    grid = diffs[diffs > 0].min()               # 最小格距
    residual = (vals / grid) % 1                # 非格点残留
    return residual.abs().max() < 1e-3          # True = 落在等距网格上 = 量化
```

### 4.5 直方图形状判别

```
FP16 权重分布：                       int8 量化后：
│  ▂▄▆█▇▅▃▂                        │  ▏▎▊█▉▊▎▏   （离散柱状）
│  光滑连续                            │  16/256 根柱子，柱间为空
└──────────────→ 值                    └──────────────→ 值
BF16：光滑（同 FP16 形状，尾数少但连续）   FP8 E4M3：离散柱状但柱位非整数网格
```

> **直方图局限**：多 group 反量化后柱子变密（每 group 16 个值×不同 scale → 值域铺开），直方图可能看似连续——**此时必须回看存储格式（qweight int32 打包）或做网格检测**。

## §5 动态行为判别：黑盒场景的最后手段

> 适用：无文件、只有 API/黑盒部署。**只能给"疑似"结论，无法证明**——因为所有行为特征都有非量化解释。

| 信号 | 量化模型的典型特征 | 干扰因素 |
|:-----|:-------------------|:---------|
| **内存/显存占用** | 加载后显存 ≈ 参数×bits/8（4bit 8B 模型 ~4.5GB） | 投机采样/KV cache/批大小会大幅改变占用 |
| **生成速度** | 低比特解码更快（带宽瓶颈下 4bit 比 16bit 快 ~2-3×） | 硬件、框架优化差异可能掩盖 |
| **输出精度对比** | 与 FP16 参考模型同 prompt 输出有可观测差异（ppl 略升、长尾/格式任务退化） | 采样随机性 → 需多次采样统计 |
| **内核 profile** | GPU 上出现 int4/int8 kernel（如 `dequantize_mm4`、INT8 tensor core 指令） | 需 root/权限，黑盒 API 无法用 |
| **API 成本/时延** | 低比特 → 单 token 成本/时延偏低 | 厂商定价策略干扰 |

**黑盒对照实验（相对可靠的"疑似"流程）**：
1. 固定 20-50 个敏感 prompt（数学/格式/长尾知识），API 与本地 FP16 参考各跑 3 次
2. 对比：输出一致性、错误模式、延迟分布
3. 量化模型在**格式遵循（IFEval 类）与长尾事实**上退化最明显（与 llama.cpp 量化研究结论一致：不同任务退化斜率不同）
4. 若延迟/成本显著低于同参数量 FP16 且格式任务掉点 → **强烈疑似量化**（标注为推测，非证明）

## §6 判别决策树：四层信号组合使用

```
拿到模型/服务
    │
    ├─[T] 有配置文件/GGUF头/ONNX？
    │     ├─ 是 → 读元数据 ──► 有 quantization_config/量化类型 ──► ✅ 确定（T1-T3 达成）
    │     │                        └─ 声明 F16/FP32 → 存疑 → 进 [W]
    │     └─ 否 → 进 [W]
    │
    ├─[W] 权重统计（唯一值/网格/键名/直方图）
    │     ├─ 出现 qweight/quant_state 等键名 ──► ✅ 铁证
    │     ├─ 存储 int8/int4 → 唯一值 ≤ 2^bits ──► ✅ 确定
    │     ├─ 浮点但网格检测通过 ──► ✅ 确定（量化反量化）
    │     ├─ 浮点连续（唯一值巨大） ──► ✅ 大概率未量化（再查 BF16 位格式）
    │     └─ 无文件可查 → 进 [B]
    │
    └─[B] 动态行为（黑盒）
          ├─ 内存≈bits/8×参数 + 格式任务退化 + 延迟低 ──► ⚠️ 疑似量化（T1 级推测）
          ├─ 对照实验无差异 ──► 无法判断（可能 FP16 或 BF16）
          └─ 行为与 FP16 一致但文件大小≈8GB/8B ──► ✅ 大概率未量化（大小印证）
```

> **判定铁律：≥2 个独立信号一致才算确定**。单信号（尤其文件大小、直方图）均可被 §8 反例绕过。

## §7 底层原理深潜：量化 = 离散化 = 熵减

### 7.1 量化的数学本质

```
连续权重 x ∈ ℝ（FP16 在 [-6,6] 附近连续分布，2^16 个位模式理论上亿种取值）
        │  Q(x) = clamp(round((x - zero) / scale)) × scale + zero
        ▼
离散格点 x̂ ∈ {scale×k + zero : k ∈ [0, 2^bits - 1]}   ← 有限个格点！

信息论视角：
  FP16:  H(x) ≈ 连续分布熵（每值 ~10-16 bit 信息）
  4bit:  H(x̂) ≤ 4 bit（每值最多 4 bit）→ 熵减 60-75% → 文件更小、可压缩性更高
```

**为什么唯一值计数是有效判据**：FP16 权重是连续随机变量的样本，几乎每个值都不同（唯一值 ≈ 元素数）；量化后**存储值**只有 2^bits 种可能——**熵减直接表现为唯一值数坍缩**。

### 7.2 为什么现代量化仍能保持质量（检测的难度来源）

量化本身丢精度，但现代方法**用额外结构补偿**，这让检测更复杂：
- **group-wise**：每 128 个元素一组，每组独立 scale/zero → 不同组格点不同 → 反量化后唯一值膨胀（直方图看似连续）
- **GPTQ 误差补偿**：逐层最小化输出误差，量化权重"最优逼近"原权重 → 行为差异更小
- **AWQ 激活感知**：保护对激活敏感的通道（大 scale 通道不量化）→ 混合精度（部分通道 FP16）
- **结论**：**现代量化模型行为上"几乎无感"，文件/统计上"处处留痕"**——所以检测要往存储格式和统计指纹走，不要指望行为差异

### 7.3 GGUF 多级块量化的结构（Q4_K_M 例）

```
Q4_K_M 结构（block-wise 两级）：
┌────────────────────────────────────────────────┐
│ Super-block (256 个权重)                        │
│  ├─ d (FP16 scale 超块级) + m (FP16 min)        │
│  └─ 8 × Sub-block (32 个权重)                   │
│       每 Sub-block: 1 个 FP16 scale + 32 个 4bit │
└────────────────────────────────────────────────┘
→ 存储格式自带 scale/min 表 → 文件头类型字段 Q4_K_M 100% 可信
→ 检测：gguf dump 或读取张量类型字段（无需分析数值！）
```

> **关键区分**：GGUF 的量化类型是**格式约定**（解析器依赖它），不是"声明"——**它的可信度高于 HF config.json**（后者是作者自述，可删可改）。

### 7.4 FP8 的底层特殊性（为什么是最大的坑）

```
FP8 E4M3：1 bit 符号 + 4 bit 指数（偏置 7）+ 3 bit 尾数
  有限值数 = 2^4 × 2^3 × 2 ≈ 240（扣特殊值）→ 唯一值远少于 FP16 的 65536 种位模式
  → 直方图：离散柱状（类似 int8 量化）
  → 但：它是【浮点】！值分布按指数增长（非等距整数网格）→ 网格检测会失败！

判别 FP8 的正确方法：
  1. 位模式分析：把权重按 uint8 读，统计【指数位】分布——FP8 指数位变化范围小且结构特定
  2. 或检查文件头/配置（NVIDIA FP8 模型常带 fp8_scales 或 quant_method: fp8）
  3. 或行为对比（FP8 的精度损失模式与 int4 不同：FP8 在大动态范围上更稳，小值相对误差大）
```

## §8 陷阱与反例：8 个容易误判的场景

| # | 陷阱 | 表象 | 真相 | 正确判据 |
|:-:|:-----|:-----|:-----|:---------|
| 1 | **BF16 不是量化** | 文件大小 = FP16（2 字节），直方图连续 | 精度截断但**非离散化**（指数位保留） | 位格式检查（BF16 指数 8bit vs FP16 5bit）；行为对比 |
| 2 | **FP8 是浮点量化** | 直方图离散 → 误判 int8 | 浮点格式，~240 个有限值，非整数网格 | 指数位分析 + config（quant_method: fp8） |
| 3 | **GPTQ/AWQ 反量化后直方图看似连续** | group-wise scale 使值域铺开 | 存储原始值仍是 int32 打包的 4bit | **看存储键名 qweight + 解包后 unique ≤16** |
| 4 | **部分量化（混合精度）** | 部分层看起来 FP16 | embedding/output 常保 F16（GGUF 设计如此） | 按张量逐个检查（不要抽样一层就下结论） |
| 5 | **剪枝 ≠ 量化** | 文件变小、稀疏 | 零值多但非零值**连续** | 稀疏度（零值比例）+ 非零值连续 → 剪枝；非零值离散 → 量化 |
| 6 | **蒸馏 ≠ 量化** | 行为退化、文件小 | 结构不同（更小的模型） | 参数量核对（config）+ 权重统计（连续） |
| 7 | **NF4 不是整数量化** | 值不在整数网格 | 16 个固定正态分位数（非均匀） | 直方图柱位 vs 正态分位数表比对 |
| 8 | **动态量化（激活也量化）** | 权重看似正常 | SmoothQuant 等 W8A8：激活层运行时量化 | 推理图检查（量化节点）+ 权重 int8 存储 |

> **通用反例防御**：任何单一判据都可能被反例绕过——**结论必须标注"基于哪些信号、置信度多少、可被什么推翻"**。这与知识库"断言出处+条件"的质量纪律一致。

## §9 可执行检测脚本骨架

```python
#!/usr/bin/env python3
"""模型量化检测器：四层信号（元数据→文件→权重→行为）"""
import json, sys, os
from pathlib import Path

def check_metadata(model_dir):
    """信号1：元数据"""
    cfg_path = Path(model_dir) / "config.json"
    if not cfg_path.exists():
        return None, "无 config.json"
    cfg = json.loads(cfg_path.read_text())
    qc = cfg.get("quantization_config")
    if qc:
        return qc, f"quant_method={qc.get('quant_method')}, bits={qc.get('bits')}"
    return None, f"声明 dtype={cfg.get('torch_dtype')}（未声明量化）"

def check_file_size(model_dir, n_params):
    """信号2：文件大小（n_params 单位：十亿）"""
    total = sum(f.stat().st_size for f in Path(model_dir).rglob("*") 
                if f.suffix in {".safetensors", ".bin", ".gguf"})
    per_b = total / n_params / 1e9  # GB/10亿参数
    if per_b < 0.8:   return "疑似 int4 量化"
    if per_b < 1.5:   return "疑似 int8 量化"
    if per_b < 3.0:   return "疑似 FP16/BF16"
    return "疑似 FP32"

def check_weight_signature(model_dir):
    """信号3：键名指纹（最强，读 safetensors 头即可）"""
    import struct, zlib
    hits = []
    for f in Path(model_dir).rglob("*.safetensors"):
        with open(f, "rb") as fh:
            n = struct.unpack("<Q", fh.read(8))[0]
            hdr = json.loads(fh.read(n))
            keys = " ".join(hdr.keys())
            if all(k in keys for k in ("qweight","qzeros","scales")): hits.append("GPTQ/AWQ")
            if "quant_state" in keys: hits.append("BitsAndBytes")
            if "mlx.quantized" in keys: hits.append("MLX")
    return hits or None

# 用法示例（伪代码，需按实际环境装配）
if __name__ == "__main__":
    d = sys.argv[1]
    print("元数据:", check_metadata(d))
    print("键名指纹:", check_weight_signature(d))
    # 信号4：权重统计（需 torch）——加载后对每个权重做 unique 计数/网格检测
    # 完整脚本建议封装为 scripts/tools/model-quantization-detector.py
```

> **脚本说明**：上述为可运行骨架，完整工具化（torch 权重统计 + 直方图 + 网格检测 + 报告输出）建议沉淀为 `scripts/tools/model-quantization-detector.py`，按需扩展 GGUF 解析（`gguf` Python 库）与 ONNX 检查（`onnx` 库）。
