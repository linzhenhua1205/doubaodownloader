## 1. 核心痛点

对话中提出的现实矛盾：

```text
理论构想：Skill封装标准化流程 -> 下发给SubAgent执行 -> 完成预处理/解析/提取
现实瓶颈：大量场景下Skill执行失效

最常见元凶：上下文断层、指令约束被稀释、记忆片段丢失
具象体感：字节Slate在Agent调度层面的实现缺陷突出

本工程体感（2026-07-30）：
  scheduler/tasks.json 被调度器持续覆写 next_run_at / updated_at
  -> Skill 指令"不要覆写调度时间"只在一轮有效
  -> 下一轮调度执行时 Skill 约束丢失
  -> 状态管理失控
```

## 2. 两大失效根源

### 2.1 上下文机制问题（首要因素）

#### 典型故障链路

```text
主Agent加载【文本深度解析Skill全套规则】
    -> 创建子Agent处理单篇文档
    -> 调度器为节约token，仅把待处理文章传入SubAgent
    -> Skill的分析步骤、校验标准、禁止偷懒条款没有完整下发
    -> SubAgent只收到"分析文章"简单指令
    -> 输出回归自由发挥，Skill形同虚设
```

#### 本工程实际案例：scheduler/tasks.json 被覆写（2026-07-30）

```text
问题背景:
  tasks.json 从 git 库 1dcbc7c 恢复后，
  调度器每次运行时自动覆写 next_run_at 和 updated_at 字段。

根因定位:
  ① 调度器逻辑有默认的状态更新行为（无意中的覆写）
  ② Skill 指令只在当前会话中约束 AI，调度器是独立进程
  ③ 约束指令无法穿透进程边界

症状:
  - git diff 每次都会出现 tasks.json 的日期字段变化
  - 即使修复了代码，调度器重启后又恢复覆写
  - 约束是"软性"的——无法强制调度器不覆写

对策:
  -> 需要将约束转化为调度器代码层的硬逻辑（而非 AI 提示词层的软约束）
```

#### 根本原因

| Agent 框架行为 | 后果 | 本工程体现 |
|:--------------|:-----|:-----------|
| 不自动继承全局 System Prompt | SubAgent 缺少底层执行原则 | 二次调度时约束丢失 |
| 截断规则文本以控制长度 | Skill 最关键的约束部分被裁剪 | `tasks.json` 约束被截断 |
| 只传递业务素材不传递执行规范 | 子任务运行在"裸指令"环境中 | 调度器只收到任务描述，没收到"不要覆写"约束 |
| 跨会话约束不持久化 | 约束只在当前 session 生效 | 新 session → 约束重置 |

### 2.2 框架实现缺陷（以 Slate 为例）

| # | 缺陷 | 描述 | 影响 | 本工程对应 |
|:-:|:-----|:-----|:-----|:-----------|
| 1 | Skill 缺少强绑定机制 | Skill 只是临时提示词，不是永久执行契约 | 模型几轮后"忘掉要求" | `tasks.json` 每次重启遗忘 |
| 2 | 上下文分发策略粗糙 | 要么无脑全量复制（成本暴涨）；要么过度裁剪（丢规则） | 无精细化分层分发 | 未注册的 3 个 Skill 完全无法触发 |
| 3 | 缺少执行结果校验 | 不检查产出是否符合 Skill 规范 | 模型偷懒无人发现 | 调度器覆写后无告警 |

> **通俗说**：Skill 只是一段临时提示词，不是底层执行契约，模型很容易"忘掉要求"。

### 2.3 约束验证器（constraint-verifier）视角的失效分类

本工程的 `constraint-verifier` 定义了 **A-J 十类失效模式**，应用到 Skill 失效场景：

| 失效类 | 对应 Skill 失效场景 | 可检测断言 |
|:-------|:-------------------|:-----------|
| **A 注意力衰减** | 长对话后 Skill 约束稀释 | A1: 回复是否缺少要求格式？ |
| **B 优先级错乱** | 用户催时跳过 Skill 步骤直接出结果 | B1: 是否响应最新而非最重要指令？ |
| **C 架构漂移** | 模型升级后 Skill 行为不一致 | C1: 不同模型版本 output diff |
| **D 行为绕过** | 说"已按 Skill 执行"但实际跳过关键步骤 | D1: 有执行证据还是空口说？ |
| **E 方向锁定** | Skill 只按单一模板输出，遗漏分支场景 | E1: 多分支中只深入一个？ |
| **G 知识层幻觉** | Skill 引用了不存在的数据/来源 | G1: 引用是否有真实来源？ |

## 3. 理想上下文分发策略

主Agent与SubAgent之间的信息应分为三层管理：

| 优先级 | 信息类别 | 内容 | 是否必须下发 |
|:------:|:---------|:-----|:------------:|
| ✅ **必须** | Skill 执行规范 | 分析步骤、输出格式、质量约束、校验规则 | **强制下发** |
| 🟡 **按需** | 业务上下文 | 业务背景、历史结论、前置分析 | 选择性传递 |
| ❌ **无需** | 冗余草稿 | 无关闲聊、临时中间结果、系统日志 | **禁止下发** |

### 本工程适配：三层分发 + 持久化层

```text
+---------------------------------------------------------+
|                    持久化约束层                           |
|  (RULE.md / 代码逻辑 / 脚本约束) — 跨会话/跨进程生效       |
|  例: scheduler 的 tasks.json 保护逻辑应该写在调度器代码中    |
+---------------------------------------------------------+
|  Layer 1: ⭐ Skill 执行规范（每次会话强制加载区）             |
|  - 分析步骤 / 输出格式 / 质量约束 / 校验规则                 |
|  - 不可被 token 预算裁剪                                    |
+---------------------------------------------------------+
|  Layer 2: 📦 业务上下文（按需传递）                           |
|  - 业务背景 / 历史结论 / 前置分析 / 当前素材                  |
|  - 可被裁剪，但不影响 Skill 核心流程                         |
+---------------------------------------------------------+
|  Layer 3: 🗑️ 冗余草稿（禁止下发）                             |
|  - 无关闲聊 / 临时中间结果 / 系统日志 / 调试信息               |
|  - 下发即造成 token 浪费 + 注意力稀释                       |
+---------------------------------------------------------+
```

**关键教训**：`tasks.json` 被覆写的根因是约束放在了 Layer 1（Session 级），但调度器是跨进程的，需要放在**持久化约束层**（代码级）。

## 4. 工程规避方案

### 方案1：显式内联（不依赖隐式继承）

```text
启动SubAgent时：
  ❌ 禁止只传递业务素材
  ✅ 强制把整套Skill流程+约束条件一并塞入初始Prompt
  优点：规避上下文丢失
  缺点：增加token开销

本工程应用：
  scheduler/tasks.json 修复：
  -> 在调度器代码中添加显式保护逻辑（不依赖AI提示词）
  -> 改用脚本定时检测 tasks.json 是否被意外修改
```

### 方案2：控制嵌套层级

多层Agent递归调用 → 上下文链路损耗层层放大

```text
限制规则：
  高规范要求任务（多文档深度提炼、关键词解析）
  -> 尽量控制嵌套层级
  -> 避免多次上下文中转造成约束衰减

本工程应用：
  knowledge-doc-writer 中：
  -> 避免深度 > 2 层的 Agent 嵌套
  -> 关键约束在每一层都显式声明
  -> 每层结束后做约束符合性检查
```

### 方案3：后置校验Agent（双层架构）

```text
SubAgent -> 产出初稿
                v
校验Agent -> 加载Skill标准
          -> 复核输出是否满足流程要求
          -> 不满足 -> 打回重处理
          -> 满足   -> 放行

本工程应用：
  constraint-verifier + doc-reviewer 双校验：
  -> SubAgent 产出 -> light-self-review 通用自检
  -> constraint-verifier 约束遵守度检测
  -> 不通过 -> 标记"约束失效" + 打回重做
```

### 方案4：约束持久化——从软约束到硬约束（本工程关键发现）

这是从 `tasks.json` 事件得出的最重要教训：

```text
失效链路：
  AI 提示词约束（软）-> session 终止 -> 约束丢失
  -> 下次执行无保护 -> tasks.json 被覆写

修复链路：
  识别"跨 session / 跨进程"的约束需求
  v
  将约束从 SKILL.md 移到脚本/配置文件/代码层
  v
  约束成为可检测、可恢复的硬约束

判断标准：
  ✅ 需要跨 session 生效 -> 必须硬编码到代码/脚本
  ✅ 需要跨进程生效 -> 必须硬编码到代码/脚本
  ✅ 需要持续保护（如文件不被覆写）-> 必须硬编码
  ❌ 只在当前对话生效 -> 可放在 SKILL.md 中
```

## 5. 本工程 Skill 失效案例库（2026-07 实测）

### 案例 1: scheduler/tasks.json 覆写（P0）

| 维度 | 内容 |
|:-----|:------|
| **现象** | git 恢复 tasks.json 后，调度器每次运行覆写 `next_run_at` / `updated_at` |
| **根因** | 调度器代码层有默认状态更新逻辑，Skill 约束无法穿透进程边界 |
| **失效类** | A（注意力衰减）+ D（行为绕过） |
| **解决方案** | 将"不要覆写"约束从提示词层迁移到调度器代码层 |
| **状态** | 🔴 待修复（需定位调度器代码根因） |

### 案例 2: 3 个未注册 Skill 无法触发（P1）

| 维度 | 内容 |
|:-----|:------|
| **现象** | deep-analysis-docs-summary / knowledge-sync / spec-consistency-checker 有 SKILL.md 但系统不识别 |
| **根因** | 未注册到 `skills_config.json`，dispatch 引擎不搜索磁盘 |
| **失效类** | C（架构漂移：创建流程缺少注册步骤） |
| **解决方案** | 评估后决定注册或废弃；创建流程强制加注册步骤 |
| **状态** | 🟡 待决策 |

### 案例 3: 多轮对话中约束稀释（P2）

| 维度 | 内容 |
|:-----|:------|
| **现象** | 长对话（8+ 轮）后输出的质量明显下降：缺少格式、缺少出处、结论跳跃 |
| **根因** | Skill 约束在 attention 窗口中被逐步稀释 |
| **失效类** | A（注意力衰减）+ B（优先级错乱） |
| **解决方案** | 使用 meth-007 三阶段分离协议 + 每 4 轮重新注入核心约束 |
| **状态** | ✅ 已应用（meth-007 文档已归档） |

## 6. 行业现状判断

| 评估维度 | 当前状态 | 生产级差距 |
|:---------|:---------|:-----------|
| Skill + SubAgent | 演示原型能力 | 稳定性不足，常规场景失效 |
| 上下文透传 | 粗糙/黑盒 | 缺少精细化分层策略 |
| 结果校验 | 无 | 缺少自动化符合性检查 |
| 约束持久化 | 临时提示词 | 需要永久执行契约（代码层级） |
| **约束跨进程** | **无** | **本工程实际遇到的场景（tasks.json）** |

> **落地建议**：不能单纯依赖平台原生 Agent 调度能力，必须额外增加一层自定义上下文透传 + 结果校验逻辑做兜底。**跨会话/跨进程的约束必须硬编码，不能依赖提示词软约束**。

## 7. 与分层架构的联动

→ [**T02**](2026-07-30-t02-ai-layered-architecture.md)

此前设计的架构（底层小模型/SubAgent预处理 → 顶层大模型统筹）成立需要**前置必要条件**：

```text
下层执行单元能够稳定遵循标准化Skill -> 输出规范结构化信息
```

如果下层 SubAgent 经常不按规范提炼：

- 摘要随意简化
- 丢失关键关键词
- 脏数据向上传递
- → 顶层输入素材质量崩坏
- → 整体分析质量崩盘

### 本工程实践验证

`knowledge-doc-writer` + `depth-completer` + `doc-reviewer` 的三层联动可以降低单层失效风险：

```text
Layer 1: knowledge-doc-writer（创作层）
  -> 即使失效（输出不够深），
Layer 2: depth-completer（深度补全层）
  -> 可以补救
Layer 3: doc-reviewer（审查层）
  -> 可以发现问题并打回

三层互为 fallback chain，
单层失效不会导致全链路崩塌
```

## 8. 与 meth-007 精确细节控制方法论的联动

→ `spec/meth-007-ai-detail-precision-control.md`

meth-007 提出的三阶段分离协议对 Skill 失效有直接防范作用：

```text
阶段一（方向探索）
  -> 测试 Skill 在不同场景下的行为
  -> 记录失效模式

阶段二（方向锁定）
  -> 创建批准基线 + 不可变区域
  -> Skill 的核心约束区域标记为不可变

阶段三（细节精调）
  -> 每次只改一处 + 回归检测
  -> 改完后确保已有约束未被破坏
```

**在 Skill 创建中的应用**：

```text
创建 Skill 时：
  阶段一：用 3-5 个不同场景测试 Skill 的触发边界和行为稳定性
  阶段二：锁定 SKILL.md 的 description 和核心约束段
  阶段三：逐项精调步骤，每改一次检查是否破坏了已有功能
```
