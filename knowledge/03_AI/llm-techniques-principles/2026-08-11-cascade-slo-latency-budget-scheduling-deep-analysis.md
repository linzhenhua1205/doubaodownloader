## 0. 一句话结论

> **Cascade 提出「per-request 延迟预算」概念——SLO 减去预测剩余服务时间的余量——并用这一单一信号同时协调请求调度与跨层 KV 内存管理（恢复/预取/驻留/重算）。对比仅用截止时间排序的 SLO 调度器，Cascade 把排队与数据搬移的开销**定向**给能吸收它的请求，使 SLO 达标 goodput 提升 2.4×、SLO 违规 -40%。这是推理服务可靠性度量从"吞吐"转向"SLO 达标率×吞吐"的标志性落地。**

---

## 1. 问题定义：同 SLO 不同紧迫度

### 1.1 现象

LLM 服务平台用**响应延迟 SLO** 管理服务质量——但同一服务内的请求差异可达**数量级**：

| 请求维度 | 差异来源 |
|:---------|:---------|
| 输入长度 | 短对话 vs 长文档 |
| 生成长度 | 单 token vs 长生成 |
| 执行成本 | 推理深度/工具调用链 |
| KV 缓存状态 | 命中前缀缓存 vs 冷启动 |

### 1.2 推论：紧迫度不同

**SLO 相同 ≠ 紧迫度相同**——扣除执行所需时间后：
- 有些请求**延迟余量大**（headroom 充足）——晚点调度也能达标
- 有些请求**几乎没有余量**（headroom ≈ 0）——必须立即执行

→ 把两者同等对待是浪费：余量大的请求被过度优待（提前调度），余量小的请求被饿死（SLO 违规）。

## 2. 核心概念：per-request 延迟预算

**定义**（论文原文）：

```
latency budget = SLO - predicted remaining service time
```

- **SLO**：服务目标（如 P99 延迟上限）
- **预测剩余服务时间**：从请求特征（输入/生成长度）、KV 缓存状态、当前系统负载**估算**的剩余执行时间
- **预算**：可以"挥霍"的延迟余量——排队/搬移开销可以消耗的部分

**关键洞察**：预算随系统状态**连续更新**——请求执行中，预测剩余时间变化 → 预算动态收缩/扩张。

## 3. 技术框架：单一预算联合协调调度×内存管理

### 3.1 与既有方法的本质区别

| 方法 | 用 SLO 做什么 | 局限 |
|:-----|:-------------|:-----|
| 传统 SLO 调度器 | 用**截止时间**（deadline）**仅决定请求排序** | 只控制"先服务谁"，不控制"服务时用什么资源" |
| **Cascade** | 用**单一预算**同时协调**调度**与 **KV 缓存管理** | —— |

### 3.2 两个子系统由同一预算驱动

```
         +-------------------------------------+
         |      per-request latency budget     |
         +------------------+------------------+
                            |
             +--------------+--------------+
             |                             |
             v                             v
   +-----------------+          +----------------------+
   |   Scheduler     |          |   KV Memory Manager  |
   | (priority to    |          | (per budget decide:  |
   |  low-budget req)|          |  restore/prefetch/   |
   |                 |          |  retain/recompute)   |
   +-----------------+          +----------------------+
```

## 4. 原理细节：预算如何同时驱动两个子系统

### 4.1 调度器：预算小者优先

- 预算小 = 余量不足 = **不能等** → 立即调度
- 预算大 = 余量充足 = **可以等** → 让位给紧迫请求
- 效果：**排队开销定向**给能吸收它的请求（预算大的）——公平性不牺牲（按预算而非按优先级/身份）

### 4.2 KV 内存管理器：预算决定分层动作

跨内存层级（HBM → DRAM → 持久层）管理非驻留 KV 状态时，对每个请求的 KV 数据决策：

| 预算状态 | 内存动作 | 原理 |
|:---------|:---------|:-----|
| 预算大（可等） | **重算**（recompute） | 省内存带宽，用计算换时间（GPU 算力有富余） |
| 预算中 | **驻留 HBM** | 常规路径 |
| 预算小（紧迫） | **恢复/预取**（restore/prefetch） | 从深层立即搬回，宁可花带宽也不等重算 |

**关键**：数据搬移开销（恢复/预取 vs 重算的权衡）**由同一预算信号统一裁决**——避免了调度与内存管理各自为政的次优解。

### 4.3 为什么联合比分离好

- 分离时：调度器按 deadline 排序（不知道 KV 状态），内存管理器按局部策略（不知道紧迫度）→ **两个局部最优 ≠ 全局最优**
- 联合时：紧迫请求既优先调度又优先恢复 KV → **排队等待与数据就绪同步优化**
- 本质：**把"资源就绪时间"与"调度时刻"对齐**——避免"调度到了但数据没到"（浪费 GPU 时隙）或"数据就绪但没被调度"（浪费带宽）

## 5. 与既有 SLO 调度器的本质区别

| 维度 | 传统 deadline 调度器 | Cascade |
|:-----|:--------------------|:--------|
| 信号 | 截止时间（绝对） | 延迟预算（SLO - 剩余时间，相对） |
| 控制面 | 仅排序 | 排序 + 内存分层动作 |
| 开销定向 | 无（被动接受） | 主动定向给可吸收者 |
| 数据就绪 | 与调度解耦 | 与调度联合 |
| 公平性 | 按 deadline 隐式 | 按预算显式（异质请求类间保持） |

## 6. 结果与边界

### 结果

- **goodput 提升最高 2.4×**（对比 vLLM 默认 FCFS 调度器）
- **SLO 违规 -40%**
- 三个 LLM 的生产 trace 验证（跨异质请求类保持公平）
- goodput 定义：**SLO 达标率 × 吞吐**（不是纯吞吐）——度量本身升级

## 7. 与知识库既有框架互证

### 7.1 推理调度三级升级（08-10）

知识库记录调度演进：排队器 → 编排器 → HorizonServe/TAOT/PrefixPlace。Cascade 定位：

- **与 HorizonServe 合流**：HorizonServe 关注 SLO 契约（可靠性度量升级）；Cascade 提供 SLO 契约的**调度实现机制**（预算驱动）
- **编排器级**：预算 = 全局可比较的统一信号，天然适合编排器（多请求跨设备协调）

### 7.2 四类冗余映射

| 冗余 | Cascade 的消除 |
|:-----|:--------------|
| 时间（等待） | 预算小者优先 → 减少紧迫请求排队等待 |
| I/O（搬移） | 预算决定预取/重算 → 搬移开销定向而非盲目 |
| 空间（浪费） | KV 分层决策 → 非驻留状态按需恢复 |

### 7.3 KV 四层命运论

- Cascade 的"恢复/预取/驻留/重算"决策 = **KV 四层（L0-L3）间的动态路由策略**——正是四层命运论的调度实现
- "预算大→重算"= 接受 L3 命运（checkpoint/重算成本）但换来带宽；"预算小→预取"= 抢回 L1/L0——**预算 = 决定 KV 命运的权力**

### 7.4 与 reliability-testing 追踪（FT-HSDP）

- FT-HSDP 关注训练侧（10 万 GPU 故障恢复）；Cascade 是推理侧（SLO 达标率）——**训练"暂停等恢复"vs 推理"快速失败+请求级重调度"**的推理侧深化

## 8. 产业信号解读

### 8.1 推理服务可靠性的度量变革

- **从"吞吐"到"SLO 达标率×吞吐"**：SLA 计费/质量承诺的量化基础改变
- 对云厂商：goodput 才是**可计费**吞吐（SLO 违规的请求要退款）——2.4× goodput 提升 = 直接营收提升

### 8.2 对 vLLM/SGLang 生态

- Cascade 基于 vLLM 对比验证——**调度器与 KV 管理器的联合优化**是下一代推理引擎的关键差异化
- 预算信号可跨引擎标准化（类似 prefix caching 的生态化路径）

### 8.3 对超节点推理集群

- 万卡推理集群的 KV 分层（HBM/DRAM/持久层）与调度需联合设计——Cascade 提供**单一信号的联合控制范式**
- 与 HiSparse（层级 KV 管理）互操作：HiSparse 管"分层放哪"，Cascade 管"何时调度+取回"——**分层是结构、调度是策略**

## 9. 结论与可证伪预判

### 结论

> **Cascade 用「per-request 延迟预算」统一了调度与 KV 内存管理两个子系统，把排队/搬移开销定向给能吸收它的请求。这是推理服务从"尽力而为吞吐"到"SLO 契约"的调度层落地——与 HorizonServe 合流标志着推理集群可靠性度量从吞吐转向 SLO 达标率×吞吐。**

| # | 预判 |
|:--|:-----|
| H1 | 预算驱动调度在 12 个月内进入 vLLM/SGLang 主线（或作为插件） |
