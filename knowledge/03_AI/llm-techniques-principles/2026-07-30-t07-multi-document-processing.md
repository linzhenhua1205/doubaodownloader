## 1. 核心命题

> 大篇幅/多文档直接丢给模型处理，输出质量极差——信息过载、重点丢失、逻辑破碎。
> **绝对禁止【原始长文本/多文档 → 顶层大模型】直连。**

### 1.1 本工程的切身教训

**案例：2026-07-29 每日跟踪日报的 8→1 聚合**

当日生成了 **8 个独立专题跟踪文件**（总 4,183 行/31KB），分别是：

| 专题文件 | 行数 | 内容 |
|:---------|:----:|:-----|
| `2026-07-29.md` | 274 | AI 编程工具全景（Cursor/Claude Code/Devin） |
| `2026-07-29.md` | 215 | 智算中心 |
| `2026-07-29.md` | 259 | 芯片市场 |
| `2026-07-29.md` | 362 | 云原生运维 |
| `2026-07-29.md` | 356 | 互联光通信 |
| `2026-07-29.md` | 363 | 产品管理与组织变革 |
| `2026-07-29.md` | 366 | 存储内存 |
| `2026-07-29.md`（汇总日报） | **1,988** | 聚合 8 源 + 各自调研 |
| **合计** | **4,183** | |

**处理方式**：每个专题先**独立写为跟踪文件**（底层处理）→ 日报扫描脚本 `kb-daily-survey-scan.sh` 自动收集摘要（中层聚合）→ 汇总日报只写核心发现（顶层输出）。

这恰好就是 T07 所倡导的分层架构——不是事后设计，而是实践中被迫做出的选择。相反，如果试图一次把 4,183 行/31KB 交给模型输出一份综合日报，结果必定是信息过载、泛泛而谈。

## 2. 五重根源

### 2.1 注意力带宽上限

模型的注意力算力是有限资源。海量文本涌入后：

```text
token数量: 1K -> 10K -> 100K
注意力权重: 每条信息获得权重平方级下降
关键信息被大量冗余内容稀释
远距离关联能力趋近于零
```

**本工程验证**：当尝试一次读取 10+个知识库文件（>8K tokens）做综合分析时，输出质量明显劣于把文件拆成 2-3 组分别处理后再综合。

### 2.2 偷懒机制放大

→ [**T03**](2026-07-30-t03-prompt-laziness-mechanism.md)

单次任务负载越大 → 模型倾向最低交付标准：

- 优先保证形式完成（有输出就算完成）
- 放弃深度推理、细节校验、交叉比对
- 最终输出：名词堆叠 + 框架罗列，但无原理分析

**本工程验证**：这正是 `depth-completer` Skill 要检测的「框架堆名词不深入原理」模式。一个文档是否有深度，不在于覆盖了多少模块，而在于每个关键断言是否做了原理溯源→量化支撑→边界条件分析→对比基线。

### 2.3 上下文噪声叠加

多文档间存在：

- **重复信息** → 注意力弥散（同一概念在不同文档中重复出现）
- **冲突观点** → 模型混淆（不同来源给出相反数据）
- **不同维度数据** → 无法自主对齐（A 文档用带宽指标，B 文档用延迟指标）

**没有前置分拣** → 模型信息混杂、前后矛盾、张冠李戴。

### 2.4 约束指令稀释

简短的约束指令在巨量输入文本面前权重变低：

```text
单文档：约束指令 / 总token ≈ 10% -> 约束有效
多文档：约束指令 / 总token ≈ 0.1% -> 约束被淹没
```

**本工程验证**：在 `knowledge-doc-writer` 的 Q6 质量标准中，6 条质量约束需要随每个阶段重复强调。一次性处理多份材料时，模型经常「忘记」按照 Q2（来源可溯）标注每条断言的出处——不是能力问题，是指令被稀释了。

### 2.5 进程边界隔离（工程特有）

> 多文档处理的困境不止在"同一模型上下文"维度——当处理跨 session/跨进程/跨 AI Agent 的批量任务时，**进程边界本身就是一道无法穿透的墙**。

**本工程案例：scheduler/tasks.json 被覆写事件（2026-07-30）**

```text
问题背景:
  tasks.json 从 git 库 1dcbc7c 恢复后，
  调度器每次运行时自动覆写 next_run_at 和 updated_at 字段。

根因定位:
  ① 调度器逻辑有默认的状态更新行为（无意中覆写）
  ② Skill 指令只在当前会话中约束 AI，调度器是独立进程
  ③ 约束指令无法穿透进程边界

教训:
  「不要覆写调度时间」的约束在 Skill/SKILL.md 中写得很清楚，
  但调度器是独立进程——它根本不读 SKILL.md。
  进程间共享的状态必须有硬编码的契约，不能依赖"大模型记住"。
```

**对多文档处理的启示**：如果多份文档交给不同 SubAgent/进程处理，每份文档的处理上下文是完全隔离的——A 进程不知道 B 进程提取了什么关键词。这种隔离在防干扰上是优点（每个 Agent 专注处理一份），但也意味着**跨文档的冲突检测、消重、对齐必须在汇聚层显式实现**，不能指望 SubAgent 自发完成。

## 3. 分层处理架构——三级流水线

### 3.1 架构全貌

**本工程实践标准化为三级流水线**（与 `skills/discover/` 的 L1→L2→L3 设计完全一致）：

```text
原始多篇长文档（N 份独立文件）
        v
+=======================================+
|  L1：文件级处理（单文档独立拆解）        |
|                                        |
|  每份文档  ->  独立调用  ->  结构化输出    |
|  文件 1    ->  Single-Doc-Parse  ->  摘要1|
|  文件 2    ->  Single-Doc-Parse  ->  摘要2|
|  ...                                  |
|  文件 N    ->  Single-Doc-Parse  ->  摘要N|
|                                        |
|  输出：N 份结构化摘要（每份 1/N 原始长度）|
+=======================================+
        v 结构化摘要集合
+=======================================+
|  L2：汇聚级处理（跨文档关联）            |
|                                        |
|  -> 冲突检测：标记矛盾观点与不一致数据      |
|  -> 消重合并：合并重复信息                |
|  -> 维度对齐：不同文档的同类数据对齐      |
|  -> 置信度评估：多源交叉验证              |
|                                        |
|  输出：汇聚摘要 + 冲突清单 + 置信度地图   |
+=======================================+
        v 汇聚后结构化信息
+=======================================+
|  L3：洞察级处理（顶层综合研判）          |
|                                        |
|  -> 跨域关联：打通不同专题的连接点         |
|  -> 趋势研判：从多维度数据中提取趋势       |
|  -> 决策输出：给出综合判断和建议           |
|  -> 按需下沉：存疑时调取 L1 原始摘要      |
+=======================================+
        v 最终输出
```

### 3.2 与 pipeline-orchestrator 的六阶段映射

本工程 `pipeline-orchestrator` 的六阶段流水线为三级流水线提供了更精细的分工：

| T07 三级 | pipeline-orchestrator 六阶段 | 负责 |
|:---------|:---------------------------|:------|
| **L1 文件级** | ① input-qa（输入质量门禁） | 校验每份文档完整性、来源可信度 |
| | ② multi-path（多路并行） | N 份文档分 N 路并行处理 |
| **L2 汇聚级** | ③ convergence（汇聚消解） | 冲突检测、消重合并、最优版本选择 |
| | ④ verification-loop（循环验证） | 交叉验证关键 claim，迭代直到通过 Check Gate |
| **L3 洞察级** | ⑤ constraint-enforcer（约束执行） | 质量标线检查、格式规范校验 |
| | ⑥ expert-gate（专家终审） | 人工需要判断的定性维度终审 |

### 3.3 本工程实例解读

#### 实例 A：每日跟踪的 8 个专题 → 1 份日报

```text
L1 处理（8个专题独立写）:
  每日在 8 个跟踪文件中独立产出结构化调研内容
  每个文件 200-400 行，自主完成关键词提取+核心发现

L2 汇聚:
  kb-daily-survey-scan.sh 自动扫描所有跟踪文件
  提取当日新增内容摘要 -> 按专题归类

L3 洞察:
  kb-daily-data-gather.sh 聚合调研+git+memory 三路数据
  SKILL.md 中三支柱结构确定最终输出格式
  只输出核心发现、深度文档摘要、工程变更三大块
```

#### 实例 B：豆包 24 轮对话 → 12 个独立话题文件 + 1 份交叉索引

```text
L1（12 路并行）:
  将豆包 24 轮对话拆分为 12 个独立话题
  每话题独立产出 100-200 行的深度分析文件（T01-T12）

L2 汇聚:
  每份话题文件末尾标注关联文件交叉链接
  例如 T02 引用 T03, T06, T08 -> 形成话题网络

L3 洞察:
  Skills 创建方法论文档（skills-training-hardware-domain 下）
  从 12 个话题中综合提取 4 种 Skills 创建路径
  -> 这不是任何一个单话题能产出的洞察
```

### 3.4 关键约束：L1 预处理层强制执行规则

| # | 规则 | 说明 | 违反后果 |
|:-:|:-----|:-----|:---------|
| R1 | **单文档独立拆解** | 每份文档独立完成关键词+核心论点+约束边界 | 跨文档信息混淆 |
| R2 | **信息标签化** | 客观事实/主观推论/假设条件打上标签 | 模型无法区分信源质量 |
| R3 | **跨文档初筛** | 提前标记重复/冲突/不一致点 | 顶层感知不到矛盾 |
| R4 | **禁止原文上送** | 只传结构化浓缩结果+溯源ID（典型压缩比 1:50~1:100） | 顶层上下文膨胀 |
| R5 | **输出强制标准化** | 杜绝自由随性摘要（每个字段定义明确） | 顶层无法自动化消费 |
| R6 | **进程隔离契约** | 跨进程/跨 session 的约束必须写入硬编码脚本，不依赖 LLM 记忆 | 约束穿透不了进程边界 |

#### R6 详解：进程隔离契约（新增）

当多文档处理跨 Agent/跨进程时：

```text
✅ 正确做法:
  - 将处理契约写入 JSON schema / YAML 配置文件
  - 脚本自动校验输出格式（如 check_format.py）
  - 约束双写：SKILL.md（AI 可读）+ 自动化脚本（机器可执行）

❌ 错误做法:
  - 只在 Skill 描述中说"不要覆写 next_run_at"
  - 认为子 Agent 能自动继承父 Agent 的约束
  - 假设同一约束在不同 session 中自然生效
```

## 4. 四种错误模式的工程分析

### ❌ 错误模式 A：原始长文本直灌

```text
一次性上传 4,183 行/8 个跟踪文件
一句话 Prompt: "综合所有文档，深度分析总结"
结果：信息过载、重点丢失、泛泛而谈、逻辑破碎
```

**发生原因**：误认为"模型上下文窗口大 = 能处理多文档"。

### ❌ 错误模式 B：不分文档只见清单

```text
列出所有关键词/条目清单但不标注来源
Prompt: "从这 8 份报告中提取所有芯片相关的指标"
结果：大量重复、冲突数据无法对齐、模型张冠李戴
```

**发生原因**：跳过了 L1 单文档独立拆解，直接尝试跨文档聚合。

### ❌ 错误模式 C：跨进程无契约

```text
SubAgent A 处理文档 1 -> 输出摘要
SubAgent B 处理文档 2 -> 输出摘要
收敛脚本直接将两个摘要拼接 -> 送顶层
结果：摘要格式不同、无法对齐、A 和 B 可能用了不同的关键词体系
```

**发生原因**：缺少 R5（输出标准化）和 R6（进程隔离契约）。

### ❌ 错误模式 D：质量门缺失

```text
多文档汇聚后直接产出最终报告
没有交叉验证、冲突解决、质量检查
结果：报告看似完整，但包含未解决的矛盾、未标注的不确定性
```

**发生原因**：跳过了 pipeline-convergence 和 verification-loop 两个阶段。

### ✅ 标准分步方案（推荐的工程实践）

```text
阶段 0：输入质量门 — 检查每份文档的完整性/来源可信度
         -> pipeline-input-qa

阶段 1：多路并行处理 — N 份文档 -> N 路独立处理
         -> pipeline-multi-path（四模式选择）

阶段 2：汇聚与冲突消解 — 检测矛盾/消重/维度对齐/置信度评估
         -> pipeline-convergence

阶段 3：循环验证 — 交叉验证关键 claim，不达标则迭代
         -> pipeline-verification-loop

阶段 4：约束检查 — 格式规范/质量标准/工程约束
         -> pipeline-constraint-enforcer

阶段 5：专家终审 — 人工判断定性维度
         -> pipeline-expert-gate
```

## 5. 四模式并行处理详解

**本工程 `pipeline-multi-path` 提供四种并行模式**，根据多文档任务类型选择：

### Mode A：多视角并行（最常见）

```text
场景：分析某个芯片的竞争力

路径 A -> 技术规格（性能/功耗/面积/成本）
路径 B -> 市场定位（价格/供应/生态/替代方案）
路径 C -> 时间线（演进路线/代际差距/趋势）
```

**适用**：需要从不同维度分析同一组文档的情况。

### Mode B：多模型/Agent 交叉验证

```text
场景：高价值/高风险分析（需要验证数据准确性）

路径 A -> DeepSeek 模型（强推理/长文本）
路径 B -> GPT 模型（结构化/代码）
路径 C -> Claude 模型（分析/安全）
```

**适用**：量化数据核查、关键决策支撑、风险评估。

### Mode C：多方法对比（同题异构）

```text
场景：计算系统 TCO

路径 A -> Top-down（从预算推算）
路径 B -> Bottom-up（组件加总）
路径 C -> Benchmarking（对标估算）
```

**适用**：数值计算、成本估算、性能预测。

### Mode D：多阶段流水线（嵌套）

```text
场景：大型文档集处理

输入 -> 拆分子任务
     +-- Sub-task A（独立 Agent 处理文档 1-3）
     +-- Sub-task B（独立 Agent 处理文档 4-6）
     +-- Sub-task C（独立 Agent 处理文档 7-10）
              v
     Sub-汇聚 -> 子汇聚摘要
              v
     主汇聚 -> 最终输出
```

**适用**：大规模文档集合（10+ 文件）、复杂系统拆解。

### 模式选择矩阵

| 文档集特征 | 推荐模式 | 原因 |
|:-----------|:--------:|:-----|
| 5 份以内，同主题 | Mode A 多视角 | 维度互补最大化 |
| 5-10 份，含量化数据 | Mode B 交叉验证 | 数据准确性最重要 |
| 3-5 份，需计算对比 | Mode C 多方法 | 避免单一方法偏差 |
| 10+ 份，多专题 | Mode D 多阶段 | 先分组再汇聚 |
| 含 5 种以上冲突观点 | Mode B + Mode D | 交叉验证 + 分组处理 |

## 6. 认知纠偏：大上下文窗口 ≠ 解决方法

### 6.1 常见误解 vs 事实

| 维度 | 常见误解 | 事实 |
|:-----|:---------|:-----|
| 窗口大小 | 窗口够大就能处理更多文档 | 窗口只是容器，注意力筛选能力才是瓶颈 |
| 注意力 | 更多 token→模型自动筛选 | 注意力算力有限，海量 token→注意力稀释 |
| 约束 | 约束指令持续有效 | 约束在巨量输入前权重被压低 |
| 结论 | 长上下文模型可替代预处理 | 前置结构化处理才是真正过滤器 |

### 6.2 本工程量化佐证

| 指标 | 单文档处理 | 多文档直连 | 三级流水线 |
|:-----|:----------:|:----------:|:----------:|
| 输入大小 | 1-3K tokens | 8-50K tokens | 8-50K → L1 压缩至 1-3K |
| 输出质量 | ✅ 高 | ❌ 低 | ✅ 高 |
| 注意力稀释 | 无 | 严重 | 受控（L1 过滤） |
| 冲突检测 | 不适用 | 遗漏 | L2 显式检测 |
| 约束有效性 | 有效 | 稀释 | 每层独立应用 |
| 可复现性 | 稳定 | 随机 | 标准化流程保证 |

### 6.3 一个常见的错觉纠正

> "GPT-4 有 128K 上下文，我直接把 10 份报告丢进去就行"

**现实检验**：

- "Lost in the Middle"[1] 已证实：模型对长上下文中间的 token 注意力趋近于零
- 10 份 3K 的报告 = 30K tokens，中间 6 份报告几乎不会被模型认真处理
- 前 2 份 + 后 2 份 = 占注意力的 80%+
- 中间 6 份 = 注意力黑洞

## 7. 本工程反模式案例库

### 案例 1：scheduler/tasks.json 覆写（2026-07-30，P0 级）

| 维度 | 内容 |
|:-----|:------|
| **现象** | 调度器每次运行覆写 `next_run_at` 和 `updated_at` 字段 |

### 案例 2：knowlege-doc-writer 初期 v1 输出质量差（2026-07-15）

| 维度 | 内容 |
|:-----|:------|
| **现象** | 基于多个知识库源 + 在线资料输出深度文档，初版效果极差 |
| **用户原话** | "初版效果与方法论差距极大" |
| **根本原因** | 多源材料直接送模型 → 注意力稀释 → 输出流于表面 |
| **对应模式** | 错误模式 A（原始长文本直灌） |
| **修复** | 增加 6 步工作流：每步只处理一个维度 → 逐步汇聚 |
| **教训** | 即使是"深度分析"也不能一次性处理所有源 |

### 案例 3：discover 管线初期单文件逐个处理（2026-07-24）

| 维度 | 内容 |
|:-----|:------|
| **现象** | 每次只处理 import/ 下的 1 个文件，处理完再处理下一个 |
| **根本原因** | 没有批量并行能力，全部串行 |
| **对应模式** | 错误模式 D（缺失质量门） |
| **修复** | 引入 L1→L2→L3 三级流水线，批量 + 并行 |
| **当前状态** | 3 个脚本 + 质量门禁，可批量处理数百个文件 |
| **教训** | 单文件处理可以保证质量，但无法应对规模——必须分层 |

## 8. 多文档处理的质量保障体系

### 8.1 与 doc-reviewer 五层审查的联动

多文档处理后的产出需要额外的审查维度，对应 `doc-reviewer` 的五层框架：

| 审查层 | 多文档特有检查项 | 对应工具 |
|:-------|:----------------|:---------|
| 🅰 结构层 | 交叉链接是否指向正确文件？链接深度（`../../`）是否正确？ | `link-validator.py` |
| 🅱 逻辑层 | 多个文档中是否有未解决的矛盾？结论是否偏向某一源？ | `pipeline-convergence` 冲突日志 |
| 🅲 来源层 | 每条断言是否标注了来源文件？多源验证了吗？ | Q2 来源可溯检查 |
| 🅳 知识层 | 是否混淆了不同文档中的概念？张冠李戴？ | 人工审查 |
| 🅴 输出层 | 是否过度自信地整合了不确定的信息？ | 置信度地图检查 |

### 8.2 本工程脚本工具链支撑

| 工具 | 流水线阶段 | 在多文档处理中的作用 |
|:-----|:----------|:--------------------|
| `pipeline-input-qa` | L1 前 | 校验每份文档完整性、来源可信度 |
| `pipeline-multi-path` | L1 | 多路并行处理，独立上下文隔离 |
| `pipeline-convergence` | L2 | 冲突检测、消重、维度对齐、置信度评估 |
| `pipeline-verification-loop` | L2→L3 | 迭代验证，不通过退回重做 |
| `pipeline-constraint-enforcer` | L3 | 格式规范、依赖审计 |
| `pipeline-expert-gate` | L3 后 | 专家终审，标注 AI 生成边界 |
| `knowledge-health-check` | 全流程 | 六维全景扫描（链接/表格/格式/位置） |

### 8.3 多文档处理的规模参考

| 规模等级 | 文件数 | 总行数 | 推荐处理策略 | 预期耗时 |
|:---------|:-----:|:------:|:------------|:--------:|
| 小型 | 2-5 | <1,000 | 手动读 + 综合 | 5-10 min |
| 中型 | 5-15 | 1K-5K | L1 逐文件拆解 + L2 汇聚 | 15-30 min |
| 大型 | 15-50 | 5K-20K | pipeline 六阶段 + 并行多路 | 1-2 hr |
| 超大型 | 50+ | 20K+ | 三级流水线 + 分组汇聚 + 自动脚本 | 2-8 hr |

## 9. 总结

### 核心原则

1. **分层是唯一出路** — L1（单文档处理）→ L2（汇聚消解）→ L3（综合研判）
2. **每层独立约束** — 下层约束不能假设上层会继承
3. **进程边界需要契约** — 跨 Agent/跨 session 的约束必须硬编码
4. **质量门不可跳** — input-qa 检查输入，convergence 解决冲突，verification-loop 验证输出
5. **规模决定策略** — 5 份以内可以灵活，15 份以上必须 pipeline

### 一句话总结

> 不要让大模型直接承担海量原始信息的筛选工作。信息分拣、关键词提取、初步解读交给下层标准化处理，顶层只负责跨域融合、交叉推理、判断决策。分层是唯一正确方案。进程边界需要硬编码契约。
