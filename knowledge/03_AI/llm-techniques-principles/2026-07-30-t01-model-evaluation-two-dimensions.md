## 0. 背景：为什么需要"两维度"评价框架

### 0.1 长上下文竞赛的时间线（2023→2026）

上下文窗口是 2023-2026 年大模型军备竞赛的核心战场，但**声明窗口的膨胀速度远快于有效利用能力的提升**：

| 时间 | 里程碑 | 声明窗口 | 说明 |
|:-----|:-------|:--------:|:-----|
| 2022-2023 | GPT-3.5 / LLaMA | 4K-8K | 短上下文时代，"截断"是工程常态 |
| 2023 H2 | Claude 2 / GPT-4-Turbo | 100K-128K | 窗口破 10 万，"大海捞针"测试流行 |
| 2024 | Gemini 1.5 Pro / Llama 3.1 | 1M-2M | 窗口破百万，但 RULER 实证"声明≠有效" |
| 2025-2026 | Gemini 2.5 / Claude Opus 5 / Llama 4 Scout | 1M-10M | 稀疏注意力（MSA）成为 1M+ 的关键技术变量 |

> [!INFO] **2026 实证（来源：知识库 2026-08-03 模型能力对比）**
> Artificial Analysis 新增 **AA-LCR（长上下文推理）** 子项后，1M 窗口模型的远距召回普遍打 **6-8 折**——"1M 只是入场券，有效利用才是分水岭"。这与 RULER（2024）的结论一脉相承。

### 0.2 对话原问题 → 两维度框架

豆包对话原始问题是"**输入与注意力权重对输出的影响**"。将其分解为两个正交问题：

1. **信息能不能进来？** → 上下文视野（Context Horizon）：模型能"看"多远的信息范围
2. **进来的信息能不能用上？** → 注意力利用能力（Attention Utilization）：模型能从视野内提取多少有效信息、做多远距离的关联推理

这一分解是**第一性原理**的：任何信息处理系统都遵循"**感知范围 × 处理效率**"的二分（类比人眼视野 × 视觉注意力、企业信息可达性 × 决策质量）。单一维度无法决定最终输出质量——**二者是组合关系**。

## 1. 核心命题

大模型输出质量不能仅用单一指标衡量。对话中提出**两个正交评价维度**：

- **上下文视野**（Context Horizon）：模型能"看"多远的信息范围
- **注意力利用能力**（Attention Utilization）：模型能从视野内提取多少有效信息、做多远距离的关联推理

二者是**组合关系**，单一维度无法决定最终输出质量。补充两个重要边界：

- **成本是隐含第三维度**：视野每扩大 N 倍，KV Cache 存储线性增长、注意力算力平方增长、Decode 带宽压力线性增长（详见 [§2.1.3](#213-物理成本kv-cache--算力--带宽)）。两维度评价必须结合成本才有工程意义。
- **评价是场景相关的**：同一模型在"短文本高精度提取"与"百万 token 长文档推理"两个场景下，两维度的权重完全不同（详见 [§6](#6-应用方式)）。

## 2. 维度一：上下文视野

### 2.1 声明窗口 vs 有效窗口：第一性原理

#### 2.1.1 物理上限（架构决定）

| 架构 | 典型窗口 | 有效视野比（实测/估计） | 限制因素 |
|:-----|:--------:|:------------------:|:---------|
| 传统Transformer（RoPE） | 4K-128K | ~30-60% | 位置编码衰减、注意力O(n²)算力 |
| 线性注意力（RWKV/Mamba） | 无限（理论上） | ~70-80% | 状态压缩损失、缺乏精确检索 |
| Hybrid（Transformer+SSM） | 128K-1M | ~60-75% | 路由策略、门控机制 |
| Extended RoPE（YaRN/NTK-aware） | 128K-1M | ~40-70% | 插值倍数、微调质量 |
| 稀疏注意力（MSA/Sliding Window） | 1M-10M | 取决于稀疏 mask 质量 | mask 设计、长距信息保留 |

> [!INFO] **2026 新变量**：MiniMax M3 的 **MSA 稀疏注意力**（官方称 BrowseComp 超 Claude Opus）把"长窗口的成本"从 O(N²) 拉到近线性，是 1M+ 窗口向 2M/10M 演进的关键技术变量。稀疏注意力把**注意力利用从"全量软检索"降级为"选择性硬检索"**——这改变了维度二的上限（见 [§3.2.3](#323-架构因素稀疏注意力与注意力稀释的对抗)）。

#### 2.1.2 RoPE 为什么长距离衰减（数学原理）

RoPE（Rotary Position Embedding）[3] 不把位置信息加进 token 向量，而是**旋转 Q/K 向量**：

- 位置 m 的 query 向量：`q_m = R(mθ) · q`（R 为旋转矩阵）
- 位置 n 的 key 向量：`k_n = R(nθ) · k`
- 注意力分数：`q_mᵀ k_n = Re( ⟨q, k⟩ · e^{i(m-n)θ} )`

关键洞察：

1. **分数只依赖相对距离** (m-n)，不依赖绝对位置——这是 RoPE 相对位置编码的本质。
2. **随距离增大，相位 (m-n)θ 快速旋转**。高频维度（θ = 10000^(-2i/d)，i 越小频率越高）在距离增大时先进入"相位模糊区"——内积实部在高频维度上方向不定，远距离 token 的语义相关性被**相位振荡淹没**。
3. **训练分布局限**：模型只在训练见过的距离范围（通常远小于声明窗口）内学到了"相位→语义"的映射，外推到更长距离时，未见过的相位组合产生**不可预测的噪声贡献**。
4. **YaRN/NTK-aware 的应对** [5]：缩放频率表（把高频分量"压"回已训练范围）+ 温度系数校正（补偿缩放引起的注意力锐度变化）。本质是**重新分配频率资源**——但插值本身损失分辨率，这就是"扩展后有效视野打折"的物理根源。

> **第一性原理总结**：RoPE 的位置信息容量有限（频率资源固定），窗口扩展本质是"用更粗的频率粒度覆盖更长的距离"——**声明窗口的每一次扩展，都在消耗位置编码的分辨率**。

#### 2.1.3 物理成本：KV Cache · 算力 · 带宽

窗口扩大不仅是"能不能看"的问题，更是物理成本问题（详见知识库 [`2026-07-07-kv-cache-bandwidth-latency-deep-dive.md`](2026-07-07-kv-cache-bandwidth-latency-deep-dive.md)）：

| 资源 | 复杂度 | 128K 上下文 | 1M 上下文 |
|:-----|:-------|:-----------|:----------|
| KV Cache 存储 | O(N) × 层数 × 头数 | ~数十 GB | ~数百 GB（≈1500 页 A4 文本） |
| 注意力算力（Prefill） | O(N²) | 可并行掩蔽 | 必须稀疏化或近似 |
| Decode 带宽（ITL） | O(N) | 单请求 ~毫秒级 | 单请求 ~12ms+ ITL 下限 |
| 推理时间占比 | — | — | 长上下文下 Decode 占 90%+ |

**结论**：1M 上下文不是"免费午餐"——即使注意力利用完美，**推理基础设施（显存/带宽）也会先成为瓶颈**。两维度评价必须挂在成本轴上才有工程意义。

#### 2.1.4 有效视野的量化实证

| 实证来源 | 关键数据 | 结论 |
|:---------|:---------|:-----|
| **RULER**（Hsieh et al., COLM 2024）[6] | 17 个长上下文 LM × 13 个代表性任务；vanilla NIAH 接近满分，但复杂任务下几乎全部大幅下降 | "虽然都声称 32K+ 上下文，**只有一半能在 32K 保持满意性能**" |
| **Lost in the Middle**（Liu et al., TACL 2024）[1] | 多文档 QA + KV 检索任务，改变相关信息位置 | 信息在**开头/结尾**时性能最高，**中间显著下降**，即使显式长上下文模型也如此 |
| **AA-LCR**（2026 实测，知识库 08-03） | 1M 窗口模型远距召回普遍 6-8 折 | "1M 只是入场券，有效利用才是分水岭" |

> [!WARNING] **不要被单点数据误导**："大海捞针"满分 ≠ 有效上下文好。RULER 的核心发现就是：vanilla NIAH 太简单（单针检索），**所有模型都接近满分**，但一旦加入多针检索、多跳追踪、聚合任务，性能断崖式下跌。

### 2.2 视野 ≠ 理解（机制拆解）

仅凭上下文窗口大并不保证输出质量好。三个叠加机制：

1. **注意力稀释**（Attention Dilution）：窗口扩大 N 倍后，softmax 分母项数增加——若没有显著突出的 token，注意力权重趋向均匀分布 1/N，**关键信息的平均注意力权重被摊薄**。信息论视角：注意力分布的熵 H = -Σp·log p 随窗口扩大而上升（除非模型学会聚焦），**熵升 = 检索模糊**。
2. **位置编码退化**：RoPE 在长距离上旋转角度过大（见 [§2.1.2](#212-rope-为什么长距离衰减数学原理)），远距离 token 之间相位混淆。
3. **中间信息遗忘**（Lost-in-the-Middle）[1]：大量实证表明，模型对长文本**中间部分**的召回率显著低于**开头和结尾**。机制假说：
   - **预训练位置先验**：训练语料中关键信息通常出现在文档开头/结尾，模型学到"开头结尾重要"的捷径
   - **softmax 边界效应**：序列开头有"锚定"效应（attention sink [9]），结尾有 recency bias
   - **训练长度分布**：多数训练序列短，长距离模式学习不足

### 2.3 企业类比

| 场景 | 企业中 | 模型中 |
|:-----|:-------|:-------|
| 视野窄 | 基层员工只看得到自己手头任务 | 小模型仅4K窗口，无法感知全局 |
| 视野广但无筛选能力 | 被海量信息淹没的管理者 | 长上下文模型注意力被稀释 |
| 理想状态 | 既广又精的高管 | 大窗口+高效注意力机制 |

## 3. 维度二：注意力利用能力

### 3.1 核心能力拆解

注意力利用能力至少包含以下子能力：

1. **远距离依赖捕获**（Long-range Dependency）：能否将前文的某一关键约束与后文关联起来
2. **噪声过滤**（Noise Filtering）：能否从大量无关信息中识别出真正相关的信号
3. **关键信息聚焦**（Key Information Focusing）：能否将有限的注意力算力集中在关键token上
4. **逻辑链条维持**（Logical Chain Maintenance）：在多步推理中维持因果链不断裂

> [!INFO] **第一性原理**：注意力机制本质是**可微分的软检索**（soft retrieval）——query 从 key 集合中"检索"value。注意力利用能力 = 软检索的**精确率**（检索到对的）+ **召回率**（检索到全的）。稀释、噪声、长距离衰减，都是软检索在"检索空间扩大"时的精度退化。

### 3.2 影响因素（深化）

| 因素 | 影响机制 | 量化指标 |
|:-----|:---------|:---------|
| 参数量 | 更多参数→更多注意力头→更细粒度模式识别 | 注意力头数（8-128） |
| 预训练数据 | 多样性数据→更好的长距离模式学习 | Perplexity下降曲线 |
| 对齐训练 | RLHF/DPO→抑制注意力噪声→提升聚焦能力 | 输出质量评分 |
| 推理方案 | 思维链/树搜索→显式引导注意力分配 | 推理任务准确率 |

#### 3.2.1 架构因素：GQA/MQA

多头注意力（MHA）的 KV 开销随头数线性增长，因此长上下文模型普遍采用**分组查询注意力（GQA）**：多个 query 头共享一组 key/value 头。GQA 是"**用 KV 压缩换算力/带宽效率**"——它对注意力利用的影响是间接的：共享 KV 意味着**多个 query 头必须从同一组表示中提取不同模式**，理论上限制了细粒度模式分化的上限（但实践中 8:1 分组损失很小）。

#### 3.2.2 架构因素：attention sink 与 StreamingLLM

**attention sink** 现象 [9]：训练好的模型会把大量注意力权重"倾倒"在初始 token（如 BOS 标记）上。机制：softmax 需要"无处安放的注意力"去处分——初始 token 位置稳定，成为天然的 sink。后果：

- **正面**：StreamingLLM 利用 sink 实现无限流式生成（只保留 sink + 滑动窗口）
- **负面**：sink 抢走本可用于真实信息的注意力权重——这是"开头偏好"的架构根源之一，也是注意力稀释在"位置维度"上的具体表现

#### 3.2.3 架构因素：稀疏注意力与注意力稀释的对抗

稀疏注意力（Sliding Window / MSA / Hyena）通过**强制 mask 掉大部分注意力对**来对抗稀释：注意力不再分摊给全部 token，只允许局部窗口 + 少量全局 token 参与。代价是**软检索退化为硬检索**——如果关键信息落在 mask 之外，无论注意力利用能力多强都无法访问（信息根本没进入视野）。这就是为什么稀疏注意力的"质量取决于稀疏 mask 设计"。

#### 3.2.4 推理因素：思维链的本质

CoT 不改变模型参数，但**改变注意力的分配路径**：通过"先写中间步骤"把长距离依赖分解为多个短距离步骤，每一步的注意力只需聚焦局部。本质是**用输出 token 扩充上下文，换取注意力聚焦**——把"一步远距关联"降维成"多步近距关联"。这解释了为什么 CoT 对"逻辑链条维持"（子能力 4）的提升最显著。

### 3.3 注意力利用的度量（新增）

注意力利用能力无法直接观测（注意力权重 ≠ 因果贡献），工程上通过**行为评测**间接度量：

| 度量方法 | 测什么 | 代表基准 | 局限 |
|:---------|:-------|:---------|:-----|
| 大海捞针 NIAH [8] | 单针检索（简单定位） | Kamradt 的 Needle Test | 太简单，区分度低 |
| RULER 四类任务 [6] | 多针检索 / 多跳追踪 / 聚合 / 干扰 | RULER benchmark | 合成任务，与真实场景有 gap |
| 长文档 QA | 真实场景的信息定位+综合 | LongBench [7] / ∞Bench | 覆盖真实分布，但无细粒度归因 |
| 长上下文推理 | 远距信息联合推理 | AA-LCR（2026） | 与业务场景对齐需定制 |
| 注意力熵（研究用） | 注意力分布均匀度 | — | 权重≠因果，只能佐证 |

> [!INFO] **评测分层原则**：NIAH（快筛）→ RULER（细测）→ LongBench/∞Bench（真实场景）→ 业务定制（验收）。单层评测不可靠，**四层递进**才能逼近"注意力利用能力"的真实值。

## 4. 两维度的交互矩阵

| 注意力利用 ↓ \ 上下文视野 → | 窄 | 宽 |
|:---------------------------|:---|:---|
| **低** | **类型A**：能力受限（只能处理简短任务） | **类型B**：看得远但抓不住重点（早期长上下文模型） |
| **高** | **类型C**：精于深耕（短任务上效果很好） | **类型D**：理想状态（高质量输出） |

- **类型A**：小型专用模型（如代码补全模型），只做有限上下文内的模式匹配
- **类型B**：早期长上下文模型，窗口够大但注意力未优化（典型：未经 YaRN 微调的 LLaMA 长上下文版本；RULER 实证的"半数在 32K 不达标"模型属于此类）
- **类型C**：参数小但对齐好的模型，短任务上表现出色（2026 年典型：Claude Opus 5 的短程 Agentic 任务、各类 3-8B 对齐小模型）
- **类型D**：高质量大模型，同时在视野和注意力上做足功课（2026 年典型：Gemini 2.5 Pro、Claude Opus 5、GPT-5.4 的 1M 档位）

> [!INFO] **矩阵的动态性**：类型不是固定的。2026 年的趋势是**类型B→类型D 的工程迁移**——通过 YaRN 微调、稀疏注意力、GQA、上下文工程，把"宽视野"逐步转化为"宽且精"。这也正是模型能力对比（知识库 08-03 文档）中 AA-LCR 成为核心评测项的原因。

## 5. 完整模型评测体系

延伸对话中提到的"剩下其他核心点"，一个完备的模型评价体系至少包括：

| # | 维度 | 核心问题 | 评测方法 |
|:-:|:-----|:---------|:---------|
| 1 | 上下文承载能力 | 能装入多少信息 | "大海捞针"测试、长文档QA、RULER 长度扫描 |
| 2 | 注意力有效性 | 装入的信息能用多少 | 长距离依赖测试、RULER 多跳/聚合、AA-LCR |
| 3 | 基础语言能力 | 语法、事实准确性 | MMLU、BBH |
| 4 | 逻辑推理能力 | 多步推理、因果推导 | GSM8K、MATH、HotpotQA |
| 5 | 对齐能力 | 是否遵循指令、减少幻觉 | MT-Bench、AlpacaEval |
| 6 | 泛化能力 | 陌生场景适应 | 零样本/少样本评测 |

> [!WARNING] **评测体系的三个盲区**：
> ① **单基准盲区**：NIAH 满分≠有效上下文好（RULER 核心发现）；② **平均分盲区**：长上下文评测要看"长度×任务复杂度"矩阵，不能只看平均分；③ **成本盲区**：维度 1-6 都不含成本，选型时必须叠加推理成本（每 token 价格、ITL、吞吐）做联合评估（见 [§6.1](#61-模型选型决策树)）。

## 6. 应用方式

### 6.1 模型选型：决策树

两维度框架在选型中的落地：**先定场景，再查维度，最后叠成本**。

**业务场景 → 分支判断**：

- **短文本（<4K）+ 高精度提取/API调用** → 只看注意力利用：选对齐好、推理强的模型（类型C 即可，不必为大窗口付费）
- **中长文本（4K-32K）+ 多步推理（Agent 任务）** → 两维度并重：有效视野 ≥ 输入长度 + 推理链稳定
- **长文档（32K-128K）+ 跨章节综合（合同/论文审阅）** → 视野优先：验证有效视野（RULER 长度扫描），再查远距召回（AA-LCR / LongBench）
- **超长上下文（128K-1M+）+ 全库 Agent** → 视野 + 稀疏注意力 + 成本三方权衡：1M 窗口的 KV 成本是否可承受？是否可以用 RAG/子代理隔离替代？（见 §6.3）

**2026 年实证选型锚点**（数据来源：知识库 08-03 模型能力对比）：

| 需求 | 推荐档位 | 理由 |
|:-----|:---------|:-----|
| 短任务高精度 | 对齐好的中档模型 | 类型C：短任务不需要大窗口 |
| 长文档综合 | 1M 窗口旗舰（Gemini 2.5 Pro / Claude Opus 5 / GPT-5.4） | 有效视野经 AA-LCR 验证 |
| 全库 Agent（代码库） | 10M（Llama 4 Scout）或子代理隔离 | 10M 打开"代码库全量 Agent"空间 |
| 性价比长上下文 | MiniMax M3（MSA、$0.2/M） | 稀疏注意力把长窗口成本拉低 |

### 6.2 提示词 / 上下文工程设计

两维度框架直接指导 prompt 工程——**针对模型的短板维度做补偿**：

| 模型画像 | 短板 | 补偿策略 |
|:---------|:-----|:---------|
| 窗口大但注意力弱（类型B） | 中间信息丢失、稀释 | ① **关键信息前置/后置**（避开中间区）；② **重复强调**关键约束（对抗稀释）；③ 结构化分隔（标题/编号/分段）减少中间区长度；④ 显式引导（"请重点参考第X节"） |
| 窗口小（类型A） | 信息溢出 | ① **分段输入**（分批喂+逐步综合）；② 预压缩（先让模型总结每段，再综合摘要） |
| 视野大+注意力强（类型D） | 无明显短板 | 但长任务仍需**锚定关键约束**（用户目标放开头、最终输出约束放结尾） |

> [!INFO] **底层原理**：以上策略全部可从 [§2.2](#22-视野--理解机制拆解) 的三个机制推出——前置/后置对抗 Lost-in-the-Middle，重复强调对抗注意力稀释，结构化分隔缩短"有效中间区"。**prompt 工程 = 对模型注意力分布的空间调度**（详见知识库 [`2026-07-20-prompt-signal-classification-enhancement.md`](2026-07-20-prompt-signal-classification-enhancement.md) 的信号分类体系）。

**上下文工程速查（信息放置黄金法则）**：

**输入布局（对抗 Lost-in-the-Middle）——信息放置黄金法则**：

1. **开头** → 最关键约束 / 任务目标（attention sink 效应 + 开头偏好，权重最高）
2. **中间** → 支撑材料（尽量短、结构化，缩短"有效中间区"）
3. **结尾** → 输出格式要求 / 最终检查项（recency 效应）
4. **稀释对抗** → 关键约束出现 ≥2 次（前置 + 重申）

### 6.3 Agent 场景应用：上下文预算管理

Agent 长循环任务（150+ 迭代）是两维度框架的极端考验：

| 问题 | 两维度解释 | 工程对策 |
|:-----|:-----------|:---------|
| 上下文爆炸 | 视野线性增长，注意力稀释加剧 | **子代理隔离**：每个子任务独立上下文，主控只保留摘要 |
| 历史遗忘 | 中间信息丢失（Lost-in-the-Middle） | **记忆分层**：短期记忆（原始细节）+ 长期记忆（压缩摘要） |
| 长任务漂移 | 远距依赖断裂、逻辑链断裂 | **显式状态持久化**：把中间状态写进结构化文档而非依赖上下文 |
| 检索 vs 全量 | 1M 窗口下"整库塞入"成为可能 | <1M token 全量注入；>1M 才用 RAG（2026 年边界：RAG 退守到百万级以上或实时数据场景） |

> **Agent 上下文工程的本质**：人类团队的"会议纪要+分工文档"模式——**上下文不是越长越好，而是"该在谁手里、以什么粒度、存活多久"的管理问题**。两维度框架提供了判断依据：当注意力利用（远距召回/聚焦）跟不上视野增长时，就必须靠架构手段（隔离/压缩/检索）而非单纯扩窗口。

### 6.4 评测落地：自建两维度验收矩阵

业务选型/验收时，建议用以下矩阵替代单一基准：

| 场景维度 \ 评测层 | NIAH 快筛 | RULER 细测 | 业务定制 |
|:-----------------|:----------|:-----------|:---------|
| 短任务（<4K） | 不需要 | 不需要 | 业务 QA 集 + 准确率 |
| 中长任务（4K-32K） | 全量通过 | 单/双针 + 多跳 | 真实文档子集 + 人工评估 |
| 长任务（32K-128K） | 全量通过 | 全任务类型 | 长文档 QA + 跨章节综合 |
| 超长（128K+） | 长度扫描 | 长度×复杂度矩阵 | 分批+综合链路验证 |

**验收标准示例**（可量化、可复现）：

**选型验收（以"128K 合同分析"为例）**：

1. 输入 100K+ 真实合同 → 问题集 ≥30 个（定位/综合/矛盾检测）
2. 准确率基线：≥90%（与人工标注对照）
3. 信息位置敏感性：关键条款分别放开头/中间/结尾 → 准确率差 ≤10pp
4. 成本约束：单次分析成本 ≤ X 元 / ITL ≤ Y 秒
5. 通过 1-4 才进入试点；任一不达标 → 换模型或改上下文策略
