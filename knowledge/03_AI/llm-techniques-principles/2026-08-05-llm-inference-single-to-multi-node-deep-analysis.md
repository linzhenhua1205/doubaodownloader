## 0. 一句话结论

> **推理跨节点与训练跨节点是两类问题：训练缺带宽（可预取、可异步、吞吐优先），推理缺延迟（每次通信都在关键路径上、SLO 优先）。跨节点推理的全部技术选择——TP 要低延迟域、PP 要少气泡、PD 分离要算清 KV 搬家成本、MoE 要交换结构、KV 分层要数据就近——本质上都是"用互联的某个代价换延迟预算的某个约束"；而最锋利的方案不是优化跨节点，而是用 scale-up 域（超节点）把"跨节点"变成"节点内"。单节点到跨节点的演进，不是推理被训练同化，而是互联被推理重新立法。**

## 1. 问题定义：为什么推理需要跨节点

### 1.1 单节点的三个天花板

推理要跨节点的根本原因，是单节点存在三个相互独立的硬天花板：

| 天花板 | 含义 | 典型数字（2026 基线） | 突破方式 |
|:-------|:-----|:----------------------|:---------|
| **容量天花板** | GPU 显存放不下模型权重 + KV Cache | 单 GPU HBM 288GB（B300）~ 31TB（Helios 整机 72 GPU 聚合，✅ Helios 锚点）；权重 70B FP8 ≈ 70GB、1T MoE 需数百 GB 驻留 | 模型并行（TP/PP）或 KV 分层 |
| **带宽天花板** | 单 GPU HBM 带宽有限，decode 是 memory-bound | HBM3e ~8TB/s（⚠️ 行业共识）、HBM4 单 GPU >10TB/s | 多 GPU 并行分摊 KV 读取 |
| **吞吐天花板** | 单节点算力/内存聚合量有限，并发请求数受限 | 单节点 8 GPU 聚合算力 ~5-10 PFLOPS（FP8） | 多节点复制（DP）+ PD 分离 |

**第一性原理**：三个天花板分别对应推理的三种资源——**权重占容量、KV 占带宽、请求占吞吐**。跨节点的必要性来自"单一物理节点无法同时满足三者"；而跨节点要付出通信代价，所以问题转化为：**跨节点换来的资源增量，是否大于付出的通信代价？**（5.7 决策树给出量化判据）

### 1.2 推理 vs 训练：为什么训练跨节点是常态、推理跨节点是例外

这是全篇的基石判断，必须从第一性原理讲透：

| 维度 | 训练（跨节点是常态） | 推理（跨节点是例外） |
|:-----|:---------------------|:---------------------|
| **优化目标** | 吞吐（token/s），延迟不敏感 | 延迟（TTFT/TPOT）与吞吐双约束 |
| **通信可预取性** | 梯度在固定步点产生，可流水重叠、可异步 | 激活/KV 依赖前序 token 实时产生，无法预取 |
| **通信频率** | 每步一次（秒级周期），量巨大但可压缩 | 每 token 一次（毫秒级周期），量小但**每次都在关键路径** |
| **容错语义** | checkpoint 周期重载可接受（分钟级） | 请求级重路由必须即时（无状态化请求） |
| **通信方向** | 规律的全归约（AllReduce） | 混合：TP 的 AllReduce + MoE 的 AllToAll + PD 的 KV 流 |
| **规模驱动** | 模型变大 → 必须多节点（算力不足） | 模型/并发/上下文超过单节点才需要（可回避） |

**最锋利的差异**：训练中通信与计算可以**流水线重叠**（通信隐藏），因为梯度产生时间是确定的、可调的；推理中通信发生在**自回归关键路径**上——第 n 个 token 的通信没完成，第 n+1 个 token 就不能开始。**训练可以"边算边传"，推理只能"算完再传、传完再算"。** 这正是"推理缺延迟"的本质：不是延迟数字本身大，而是延迟不可隐藏。

> 推论：把训练的经验（如"跨节点带宽要 3.6TB/s"）直接搬到推理是错误的。**推理跨节点首先算的是"多跨一层，延迟预算还够不够"；带宽只是第二约束。**

### 1.3 跨节点推理的三种驱动场景（MECE）

按"为什么非跨不可"，跨节点推理恰好三种（互斥且穷尽）：

| 场景 | 触发条件 | 典型负载 | 主导挑战 |
|:-----|:---------|:---------|:---------|
| **S1 单请求超容量** | 单请求的模型/上下文超过单节点可驻留 | 1T+ 参数 MoE、1M token 超长上下文、多模态大模型 | 延迟（TP/PP 跨节点）+ 状态（KV 分层） |
| **S2 高并发吞吐** | 单节点并发吞吐不满足 SLO，需要聚合多节点 | 在线对话、Agent 批量任务、代码生成服务 | 调度（PD 分离）+ KV 传输（状态搬家） |
| **S3 模型结构要求** | MoE 的专家数量超过单节点 GPU 数 | DeepSeek V3 类 MoE（专家跨节点放置） | 动态路由（AllToAll）+ 互联确定性 |

**场景判据（第一性原理）**：S1 是**容量驱动**（装不下），S2 是**吞吐驱动**（不够快），S3 是**结构驱动**（模型自己要求）。三者的优化重点完全不同：S1 看延迟预算、S2 看 KV 带宽与调度、S3 看互联的交换能力。**一个跨节点推理系统，通常是 S2 为主、S1/S3 兼有**——这也是为什么 PD 分离 + MoE 路由 + KV 分层成为 2026 推理平台的三大标配。

## 2. 并行范式与跨节点适配

### 2.1 TP 张量并行：通信最重、延迟最敏感

**机制**：把单层权重切成 p 份分到 p 个 GPU，每层前向需要一次 AllReduce（或 ReduceScatter/AllGather 组合）同步部分和。

**通信量（推理前向，🔶 推导）**：

- 每层每 token：约 `2 × hidden_size × 2B`（每 GPU 收发 hidden×2B 的中间结果，FP16）
- 70B（hidden=8192）：每层 32KB/token，80 层 → **2.56MB/token**
- decode 每 token 计算 ~5-15ms（70B、2 GPU、FP8）→ **带宽需求仅 ~256MB/s，远低于任何互联**

**结论（关键）**：decode 阶段 TP 跨节点的**带宽需求极小**——瓶颈不是带宽，是**每次 AllReduce 的延迟**。80 层串行 × 单次通信延迟：

- NVLink 域内（~1-2μs，✅ 库内锚点：NVLink6 HBM-to-HBM ~565ns）：80×1.5μs ≈ **120μs**，占每 token 延迟 ~1-2% → 可接受
- RDMA 跨节点（~5-20μs，⚠️ 行业共识）：80×10μs ≈ **800μs**，占 5-8% → 可接受但不免费
- 跨机架/跨交换机（~50μs）：80×50μs = **4ms**，占 20-40% → **不可接受**

**TP 跨节点的设计含义**：TP 只适合"低延迟域"（NVLink/UALink 域内），跨机架做 TP 是延迟灾难。**TP 是"域内并行"，不是"域间并行"。**

### 2.2 PP 流水线并行：气泡与跨节点延迟放大

**机制**：把层切成段分到 p 个 GPU，前向逐段传递激活。

**特点**：

- 通信量小（每段边界传 hidden×2B），远低于 TP——每层边界 16KB/token，70B 分 4 段仅 3 次传递
- 但引入**流水线气泡**（p 个 stage，微批 m 个时气泡比例 ≈ (p-1)/(m+p-1)）
- **跨节点时每个 stage 边界都是一次跨节点通信**——层间依赖串行，延迟不可隐藏

**结论**：PP 适合**模型太大装不进单节点**的场景（S1），通信少但气泡伤吞吐；跨节点 PP 的每段边界延迟直接加入关键路径，需要**深流水线 + 微批调度**稀释。PP 是"容量型并行"，不是"性能型并行"。

### 2.3 DP 复制并行：无通信但容量不增

**机制**：每节点放完整模型副本，请求按节点分发。

**特点**：节点间**零通信**（最优）、故障隔离好（单点挂了别的继续）、无延迟开销——但**不解决容量问题**（S1 无用），只解决吞吐（S2）。

**结论**：DP 是跨节点的"免费午餐"，但前提是模型能装进单节点。**一切"跨节点推理"讨论都应先问：能不能用 DP 回避？** 回避不了（S1/S3）才上 TP/PP/MoE 路由。

### 2.4 MoE 并行：跨节点推理的特有形态

**机制**：专家分布在多节点，每个 token 经 Router 选择 top-k 专家（可能跨节点）→ AllToAll 分发 → 专家计算 → AllToAll 收集。

**与 TP/PP 的本质区别**：

- TP/PP 是**静态并行**（切分方式编译期确定），MoE 是**动态路由**（每个 token 的通信伙伴运行时才确定）
- 动态路由 → **互联无法预配置路径** → 对交换结构提出确定性要求（✅ Scorpio 锚点：DeepSeek V3 推理被迫限制 token 路由到 4 个目标节点，仅因互联容量约束）
- 通信模式是 **AllToAll**（每个 GPU 与所有潜在专家通信），非 AllReduce——**交换机需要硬件级多播/重配置能力**

**结论**：MoE 是"结构型跨节点"（S3），它的跨节点是模型自己要求的，优化方向是**让互联对动态路由友好**（硬件化集合通信、交换结构），而不是消除跨节点。这正是 Scorpio Hypercast / In-Network Compute 的市场逻辑（✅ 库内锚点：GPU IO 最多降 49%、MoE AllToAll 4-6× 加速，⚠️ 厂商声称值，未独立验证）。

### 2.5 范式选择的第一性原理

四种范式按"通信粒度"排序，粒度决定跨节点的可行性：

| 范式 | 通信粒度 | 跨节点敏感性 | 适合场景 |
|:-----|:---------|:-------------|:---------|
| TP | token 级（每层都通信） | 🔴 极高（延迟敏感） | 低延迟域内、大模型单请求 |
| PP | 层段级（每段边界通信） | 🟡 中（气泡+延迟） | 超大模型、装不下单节点 |
| DP | 请求级（节点间零通信） | 🟢 无 | 并发吞吐（S2） |
| MoE 路由 | token 级动态 | 🔴 极高（需确定性互联） | MoE 结构（S3） |

**统一判据**：通信粒度越细（越接近 token 级），对延迟越敏感，越只能在低延迟域内做。**粒度 = 跨节点能力的分界线**——请求级（DP/PD 分离）可以跨数据中心，token 级（TP/MoE）只能跨低延迟域。

## 3. 跨节点推理的四大挑战

### 3.1 延迟进入关键路径

**量化**：见 2.1——80 层 TP 的串行通信延迟，NVLink 域内 120μs、RDMA 跨节点 800μs、跨机架 4ms。对照 TPOT 预算（✅ `2026-07-07-kv-cache-ttft-tpot-budget-decomposition.md`：在线对话 TPOT 通常 20-50ms，其中 KV 读取已占大头），**跨机架 4ms 直接吃掉 8-20% 的 TPOT 预算，且与 KV 读取时间叠加（通信发生在计算间隙，不是并行）**。

**深层机制**：推理的通信延迟不可隐藏（1.2 已论证）。任何"通信与计算重叠"的尝试，在 decode 阶段都受限——因为每 token 的计算本身就依赖前一次通信的结果。**延迟预算 = 跨节点可行性的第一闸门。**

### 3.2 带宽从"够用"到"瓶颈"

带宽在三种情况下成为瓶颈：

1. **prefill 阶段 TP**（🔶 推导）：seq=4K、batch=16 时 70B 每层通信 2.1GB，80 层 170GB；prefill 计算 ~11.5s → 需 ~15GB/s 持续带宽 → **>100Gbps 互联才够**（RDMA 可满足，PCIe 转发则紧张）
2. **PD 分离的 KV 传输**（见 3.3）：KV 是推理独有的"大数据搬家"
3. **MoE AllToAll**：token 分发总量大且突发，需要交换结构的高聚合带宽

**关键区分**：decode 缺延迟、prefill 缺带宽——**同一个跨节点系统，两种阶段缺的东西不同**，这直接催生 PD 分离（4.2）与"prefill 节点走带宽、decode 节点走延迟"的分工。

### 3.3 状态：KV Cache 的跨节点迁移

**推理与训练最本质的差异**：推理有**状态**——KV Cache 随请求生成，随上下文增长，是请求的"活内存"。

**KV 迁移成本（🔶 推导，70B 为例）**：

- KV/token = 2 × layers × kv_heads × head_dim × 2B = 2×80×8×128×2 = **320KB/token**
- seq=4K → 1.28GB；seq=32K → 10.2GB；seq=1M → 320GB
- 100Gbps RDMA（~12.5GB/s）传输：4K 上下文 102ms、32K 上下文 820ms

**推论**：PD 分离（prefill 节点算完 → KV 传给 decode 节点）的**状态搬家成本随上下文线性增长**。长上下文（>32K）下 KV 传输时间可与 prefill 计算同量级，直接吃掉分离收益——必须用 **KV 压缩（MLA 类）、分块流式传输、或高带宽域内 PD 分离**解决。**状态黏性（5.4）是跨节点推理独有的设计约束，训练完全没有这个问题。**

### 3.4 故障域扩大

**量化（🔶 推导）**：假设单 GPU 年故障率 ~1%（⚠️ 乐观估计，行业实践更高），则：

- 8 GPU 节点：年故障 ~7.7%，月故障 ~0.7%
- 72 GPU 域：年故障 ~51.5%，月故障 ~4.3%
- **节点数每 ×10，域内任一组件的故障概率约 ×10**（一阶近似）

**推理的故障语义**：训练可以 checkpoint 分钟级重载；推理请求是秒级交互，**故障容忍 = 即时重路由 + 前缀缓存复用**（新节点从共享 prefix 恢复，无需从头 prefill）。跨节点推理的可靠性设计是**"无状态化请求 + 有状态 KV 的快速迁移/重建"**，而不是 checkpoint。

## 4. 优化方案全景（分层 MECE）

优化方案按"干预层次"分四层，从最上游（算法）到最下游（硬件），**越上游杠杆越大、越下游越昂贵**：

### 4.1 算法层：压缩通信需求

| 方案 | 机制 | 消除的挑战 | 代价/局限 |
|:-----|:-----|:-----------|:----------|
| **KV 压缩（MLA/Delta Attention）** | 低秩投影压缩 KV，KV/token 降 5-10× | 3.3 状态迁移成本 | 精度微损、推理引擎需适配（✅ 库内锚点：`2026-08-05-llm-architecture-evolution-roadmap.md` KV 压缩三路线） |
| **注意力局部化（局部注意力/稀疏注意力）** | 每 token 只 attend 局部窗口，减少跨节点 KV 访问 | 3.2 带宽 | 长程依赖损失（非通用方案） |
| **投机解码（Speculative Decoding）** | 小模型草稿 + 大模型验证，验证失败才跨节点 | 3.1 延迟 | 草稿模型命中率决定收益 |
| **专家本地化/复制** | 高频专家复制到各节点，减少 AllToAll 出域 | 3.2 带宽 + 3.1 延迟 | 复制占容量（频率-容量权衡） |
| **量化（FP8/INT4）** | 权重/KV 更小 → 单节点可驻留更多，减少跨节点必要 | 容量天花板 | 精度权衡（已广泛采用） |

**核心思路**：算法层的统一逻辑是"**让模型不再需要跨节点**"或"**让跨节点通信变轻**"。这是杠杆最高的层——DeepSeek 用 MLA 压缩 KV，本质就是为"单机装更大模型/更省 KV 带宽"做的架构级优化。

### 4.2 系统层：PD 分离、KV 分层、拓扑感知调度

**4.2.1 PD 分离（Prefill-Decode Disaggregation）** —— 跨节点推理的"专业化分工"

- **动机**：prefill 是 compute-bound（吃算力）、decode 是 memory-bound（吃 KV 带宽），两者对硬件需求不同（✅ `2026-08-04-coding-agent-fullchain-inference-deep-analysis.md`）
- **跨节点形态**：prefill 池（大 batch、高算力）与 decode 池（KV 带宽、低延迟）分离部署，prefill 算完把 KV 传给 decode 节点
- **收益**：两池独立扩缩、prefill 不阻塞 decode、吞吐显著提升（业界已证实，⚠️ 行业共识）
- **代价**：KV 传输（3.3 量化）+ 调度复杂度
- **设计要点**：KV 传输走**专用高带宽通道**（RDMA/域内），长上下文配 KV 压缩；**同域 PD 分离**（prefill/decode 在同一 NVLink/UALink 域）可把 KV 传输延迟压到微秒级

**4.2.2 KV 分层（HBM → CXL → SSD）** —— 容量与带宽的层级交换

- **逻辑**：KV 是推理的"活内存"，复用 OS 内存层级思想（✅ 库内锚点：`2026-07-29-supernode-memory-unified-addressing-cxl-kvcache-doca-spdk.md`）
- **层级**：HBM（~8TB/s，⚠️ 行业共识）→ CXL 内存（~500GB/s 每设备，⚠️）→ NVMe SSD（~50GB/s 每盘，⚠️）→ 远端（RDMA）
- **规则**：活跃 KV 留 HBM，冷 KV 下沉；decode 读带宽需求（320KB/token × 100 token/s = 32MB/s per 请求）在 CXL/SSD 上可承受——**KV 分层把"容量天花板"变成"可管理的层级预算"**
- **跨节点关联**：KV 分层让单节点可驻留更长上下文（缓解 S1），PD 分离的 KV 传输可与分层结合（传冷 KV 用低带宽通道）

**4.2.3 拓扑感知调度** —— 把请求调度到"通信代价最小"的位置

- 请求 → 就近调度（缓存命中优先、前缀复用优先）
- MoE token 路由 → 感知互联拓扑（避免跨机架 AllToAll）
- PD 配对 → prefill 节点与 decode 节点同域
- **思路**：调度是"软件层的拓扑优化"——用调度避免通信，比用带宽扛通信便宜

### 4.3 通信层：RDMA、集合通信硬件化、计算通信重叠

| 方案 | 机制 | 适用 | 局限 |
|:-----|:-----|:-----|:-----|
| **RDMA（RoCE/IB）** | 绕过内核、零拷贝、~1-5μs 延迟（⚠️） | 跨节点 TP（勉强）、KV 传输、AllToAll | 仍比 NVLink 慢一个量级（~565ns，✅） |
| **集合通信硬件化（SHARP/Hypercast）** | 归约/多播在交换机内完成，数据在途处理 | MoE AllToAll、TP 归约 | 需专用交换芯片（✅ Scorpio 锚点：GPU IO 降 49%） |
| **计算通信重叠** | 分块通信 + 计算交错 | prefill 阶段（通信可预取） | decode 阶段受限（依赖链） |
| **Fused 通信** | 多层通信合并为一次大消息 | 减少小包延迟开销 | 破坏层间流水 |
| **多路径/负载均衡** | 多网卡多路径分摊 | 突发 AllToAll | 拥塞控制复杂度 |

**核心思路**：通信层的两个方向——**减延迟**（RDMA/硬件化）与**藏延迟**（重叠，仅 prefill 可行）。硬件化是 2026 主线（Scorpio 的 In-Network Compute、NVIDIA 的 SHARP 都属于"把通信语义下沉到交换硅片"），因为软件减延迟已逼近极限。

### 4.4 硬件层：scale-up 域扩展与超节点

**逻辑**：前三层都在"优化跨节点"，硬件层在做"消除跨节点"——用 scale-up 互联把多节点变成单逻辑节点：

| 技术 | 现状 | 推理意义 |
|:-----|:-----|:---------|
| **NVLink 6 域（NVL72/144）** | 3.6TB/s/GPU、HBM-to-HBM ~565ns（✅） | TP 跨 72 GPU 延迟近节点内 → S1 大模型"伪单机"推理 |
| **UALink 域（AMD Helios）** | scale-up 260TB/s 全铜 1-hop 全对等（✅） | 开放生态的 scale-up 域，推理 TP/PD 同域 |
| **CXL 内存池化** | 跨节点内存语义共享（✅ 库内锚点） | KV 分层延伸到池化内存，S1 超长上下文 |
| **交换式 scale-up（Scorpio）** | PCIe 6.0 fabric + Hypercast（✅） | MoE 推理的确定性互联（S3） |

**超节点 = 推理的"逻辑单机"**：当 scale-up 域大到可容纳整模型 + 足够 KV，跨节点推理的问题（延迟/状态/故障）退化为节点内问题，只剩"域间"（跨超节点）需要处理——而域间只做 DP/PD 分离这类请求级并行（3.1 粒度判据：请求级可跨域）。

## 5. 提炼思路：六个设计法则与决策树

从 1-4 章提炼六个可复用的设计法则（这是本篇的"思路提炼"，比具体方案更可迁移）：

### 5.1 法则一：数据就近

**表述**：推理的性能瓶颈是数据搬运（KV 读取、激活传递），先问"数据在哪"，再问"算多少"。
**推导来源**：decode 是 memory-bound（✅ KV 预算文档）；NVLink 565ns vs 以太网 1.8μs 的 3.2× 差距（✅）；FlashAttention"搬得少比算得少重要"（✅ 冗余消除文档）。
**应用**：KV 分层、PD 同域配对、专家复制——都是"让数据离计算更近"。

### 5.2 法则二：粒度匹配

**表述**：通信粒度必须与互联能力匹配——token 级并行只能进低延迟域，请求级并行可以跨域。
**推导来源**：2.5 范式粒度表。
**应用**：TP/MoE 路由 → NVLink/UALink 域内；DP/PD 分离 → 可跨节点/跨域；**决策顺序：先定粒度，再选互联，不颠倒**。

### 5.3 法则三：延迟预算反推

**表述**：用 SLO 反推通信预算——先算"每 token 关键路径上能容忍多少通信延迟"，再决定跨多远。
**推导来源**：TPOT 预算分解（✅）+ 3.1 量化（跨机架 4ms 吃满 20-40% 预算）。
**应用**：在线对话（TPOT 20-50ms）→ 跨机架 TP 不可行，只能域内；离线批处理（无 SLO）→ 可跨节点 TP/PP；**延迟预算决定拓扑，不是拓扑决定延迟**。

### 5.4 法则四：状态黏性

**表述**：KV 是状态，状态有搬家成本（320KB/token，🔶），且随上下文线性增长；**状态的跨节点迁移必须显式量化**。
**推导来源**：3.3 量化 + PD 分离代价。
**应用**：PD 分离要算 KV 传输账（长上下文尤其）；KV 分层把"搬家"变成"分级驻留"；**任何"状态搬家"方案（PD 分离、节点迁移、故障恢复）都必须先回答：KV 传输时间 vs 收益，谁大？**

### 5.5 法则五：故障域

**表述**：跨节点 = 跨故障域；节点数 ×10，域内故障概率 ≈ ×10（🔶）；推理的容错是无状态化 + 快速重建，不是 checkpoint。
**推导来源**：3.4。
**应用**：DP 副本天然抗故障；PD 分离的 decode 池要有热备；KV 前缀缓存让故障恢复"从缓存重启"而不是"从头 prefill"。

### 5.6 法则六：消除跨节点

**表述**：跨节点推理的最优解是"不需要跨节点"——scale-up 域把跨节点变成节点内，DP 把跨节点变成零通信。
**推导来源**：4.4 超节点 + 2.3 DP。
**应用**：先问"能不能单节点/单域解决"，再问"跨节点怎么优化"；超节点投资的本质是"用一次性的互联资本开支，换长期的延迟/状态/故障三问题消失"。

### 5.7 决策树：该不该跨节点

**第一步：模型能装进单 GPU 吗？**

- 能，且延迟敏感 → **单节点复制（DP）**，完成（最简单、零通信）
- 不能 / 并发不够 → 进入第二步

**第二步：能装进单节点（8-16 GPU）吗？**

- 能 → **节点内 TP/PP**（NVLink 域内 ~565ns），完成
- 不能 → 进入第三步

**第三步：按驱动场景分流（S1 容量 / S2 吞吐 / S3 结构）**

- **S1 容量问题**（模型/上下文超单节点）→ 有 scale-up 域吗？
  - 有 → **域内 TP/PP**（超节点 = 逻辑单机）
  - 无 → **跨节点 TP**（须先算延迟预算，见 5.3）/ **KV 分层**缓解容量
- **S2 吞吐问题**（并发不足）→ **PD 分离 + 多节点复制**（KV 传输走专用通道）
- **S3 结构问题**（MoE 专家跨节点）→ **MoE 跨节点路由**（需确定性互联/交换结构）

**决策原则**：每一步都先问"更便宜的方案能否回避跨节点"（DP → 节点内 → 域内 → 才到跨域），**跨节点是最后手段，不是默认选项**——这与训练"跨节点是默认"形成鲜明对照（1.2）。

## 6. 超节点视角：把跨节点重新定义

### 6.1 连续谱：单机到机架到超节点

跨节点不是二值的（节点内/节点外），而是**延迟连续谱**：

| 层级 | 代表 | 延迟量级（⚠️ 行业共识，✅ 库内锚点标注） |
|:-----|:-----|:------------------------------------------|
| 单 GPU | 单卡 | ~100ns（片内） |
| 单节点 | NVLink 域内 | ~0.5-2μs（✅ NVLink6 HBM-to-HBM ~565ns） |
| 机架 | UALink/域扩展 | ~1-5μs（✅ Helios 全铜 1-hop） |
| 超节点 | 全对等 scale-up | ~1-5μs（域内全对等） |
| 跨超节点 | RDMA/以太网 | ~10-50μs+ |

**关键认知**：**"跨节点"的定义正在被 scale-up 技术重写**。NVLink 6 的 565ns 让 72 GPU 的 TP 延迟与 8 GPU 单机同量级——**超节点内的"跨 GPU"在延迟语义上不是"跨节点"，而是"扩大的节点内"**。推理的"节点"概念从"物理机箱"上移到"scale-up 域"。

### 6.2 三类 scale-up 域对比

| 维度 | NVIDIA NVLink 域 | AMD UALink 域（Helios） | 交换式 fabric（Scorpio） |
|:-----|:-----------------|:------------------------|:-------------------------|
| 形态 | 私有、封闭 | 开放标准（UALink 联盟） | 开放（PCIe 6.0 生态） |
| 带宽 | 3.6TB/s/GPU（✅） | 260TB/s 域聚合（✅） | 28-28.4GB/s×4 链路（✅） |
| 延迟 | ~565ns HBM-to-HBM（✅） | 全铜 1-hop 全对等（✅） | PCIe 语义（✅） |
| 推理优势 | TP/PD 同域，延迟最优 | 开放生态 + 容错（网络单点全补偿，✅） | MoE 动态路由确定性（✅ Hypercast） |
| 主要场景 | S1 大模型单请求 | S1+S2 混合 | S3 MoE |

**判断**：三类域不是竞争关系，是**按场景分工**——NVLink 域做延迟极致（S1 在线）、UALink 域做开放生态（S1/S2 混合）、交换 fabric 做 MoE 确定性（S3）。跨节点推理的未来是"**多域分层**"：请求级跨域（DP/PD）+ token 级域内（TP/MoE）+ 状态级跨层（KV 分层）。

### 6.3 案例验证：Helios 与 Scorpio

**Helios（AMD，✅ 库内锚点）**——"用 scale-up 消除跨节点"的样本：

- 72×MI455X 聚合 2.9 EFLOPS（MXFP4）/31TB HBM4/1.7PB/s 内存带宽
- scale-up 260TB/s 全铜 1-hop 全对等 → **TP 跨 72 GPU 的通信语义近似单机**
- scale-out 43TB/s → 跨超节点走 DP/PD（请求级）
- 容错：网络单点全补偿，免 checkpoint 重载 → 呼应 5.5 法则（推理容错不是 checkpoint）
- **启示**：Helios 的架构分层（域内全对等 + 域间请求级）正是 6.2"多域分层"的工程实现

**Scorpio（Astera Labs，✅ 库内锚点）**——"用交换结构服务 MoE 跨节点"的样本：

- Hypercast 硬件集合通信（MoE AllToAll 4-6×，⚠️ 厂商值）+ In-Network Compute（GPU IO 降 49%，⚠️ 厂商值）
- 解决 DeepSeek V3 的"4 节点路由上限"（✅ 真实案例）→ 解除互联对模型结构的约束
- **启示**：当模型结构（S3）强制跨节点时，优化点是**互联的确定性与在网计算**，而不是试图回避跨节点

## 7. 数字锚点与可复算推导

### 7.1 关键数字速查表

| 数字 | 值 | 来源分级 | 出处 |
|:-----|:---|:---------|:-----|
| NVLink 6 每 GPU 带宽 | 3.6 TB/s | ✅ | 库内 `nvlink6-goodput` 专题 |
| NVLink 6 HBM-to-HBM 延迟 | ~565 ns | ✅ | 同上（vs 以太网 ~1,815ns，3.2×） |
| UALink/Helios scale-up | 260 TB/s 域聚合 | ✅ | 库内 Helios 专题（STH 一手） |
| Helios scale-out | 43 TB/s | ✅ | 同上 |
| Scorpio MoE AllToAll 加速 | 4-6×（⚠️ 厂商声称） | ⚠️ | 库内 Scorpio 专题 |
| DeepSeek V3 路由上限 | 4 目标节点 | ✅ | Scorpio 专题（Futurum 披露） |
| HBM3e 单 GPU 带宽 | ~8 TB/s | ⚠️ | 行业共识 |
| 跨节点 RDMA 延迟 | ~1-5 μs | ⚠️ | 行业共识 |
| 跨机架延迟 | ~10-50 μs | ⚠️ | 行业共识 |
| 70B KV/token | 320 KB/token | 🔶 | 本文 3.3 推导（80层×8kv×128d×2B×2） |
| 70B TP=2 每 token 通信 | 2.56 MB | 🔶 | 本文 2.1 推导（80层×32KB） |
| PD 分离 KV 传输（4K ctx） | 1.28 GB → 102ms@100Gbps | 🔶 | 本文 3.3 推导 |

### 7.2 案例 A：70B TP=2 跨节点（延迟 vs 带宽）

**前提**：LLaMA-3 70B，hidden=8192，80 层，FP16 中间激活，TP=2，decode 每 token 计算 ~10ms（2 GPU、FP8，⚠️ 量级估计）。

**带宽视角**（🔶）：

- 每层 AllReduce = 2×8192×2B = 32KB；80 层 = 2.56MB/token
- 需求 = 2.56MB / 10ms = **256 MB/s** ← 任何互联都远超（PCIe Gen6 x4 都有 28GB/s）
- **结论：带宽完全不是 decode 跨节点 TP 的瓶颈**

**延迟视角**（🔶）：

- 80 次串行 AllReduce（依赖链不可并行）
- NVLink 域内 1.5μs → 120μs（占 1.2%）✅ 可接受
- RDMA 跨节点 10μs → 800μs（占 8%）⚠️ 可接受但已显著
- 跨机架 50μs → 4ms（占 40%）❌ 不可接受
- **结论：TP 跨节点的判决量是"单次通信延迟 × 层数"，不是带宽**

**设计含义**：70B 级别模型，TP=2 跨机架不可行，TP=8 跨机架更糟（通信量更大、依赖链更长）。**70B 推理的可行选项是单机 2-4 GPU 或 NVLink/UALink 域内并行**——中间态（跨机架 TP）是工程上最差的选择。

### 7.3 案例 B：PD 分离的 KV 传输成本

**前提**：70B，KV/token=320KB（🔶），100Gbps RDMA 有效 ~12.5GB/s，prefill 计算 ~11.5s（seq=4K、batch=16、2 GPU、~400 TFLOPS 实际，🔶）。

| 上下文长度 | KV 总量 | 传输时间@100Gbps | 占 prefill 比例 | 评价 |
|:-----------|:--------|:------------------|:-----------------|:-----|
| 4K | 1.28 GB | 102 ms | ~0.9% | ✅ 可忽略 |
| 32K | 10.2 GB | 820 ms | ~7% | ⚠️ 需注意 |
| 128K | 41 GB | 3.3 s | ~29% | ❌ 吃掉大量收益 |
| 1M | 320 GB | 25.6 s | >100% | ❌ 完全不可行 |

**设计含义**：

- 短上下文（<32K）：PD 分离的 KV 传输成本可忽略 → 大胆分离
- 长上下文（>128K）：必须 **KV 压缩（MLA 类，KV/token 降 5-10×）** 或 **同域 PD 分离**（KV 走 NVLink/UALink，微秒级）+ **分块流式传输**（首块先传先算）
- **判据**：KV 传输时间 < 10% prefill 时间 → 分离划算；否则需压缩或同域

### 7.4 案例 C：MoE 跨节点 AllToAll

**前提**（✅ Scorpio 锚点 + 🔶 推导）：MoE 前向 = 分发(AllToAll) → 专家计算 → 收集(AllToAll)；DeepSeek V3 因互联约束限 4 目标节点。

**通信量（🔶）**：每 token 若路由到 E 个跨节点专家，分发+收集 ≈ 2 × E × hidden×2B。E=4 时每 token 通信 = 2×4×8192×2B = 128KB——比 TP 的 32KB/层更大，且是**突发**（token 批到达时集中爆发）。

**瓶颈本质**：MoE 跨节点的瓶颈不是平均带宽，而是**突发 AllToAll 的瞬时带宽 + 路由的确定性**。软件层面无解（路由动态、无法预配置），只能靠：

1. 交换结构硬件化（Hypercast 类，✅）
2. 专家复制/本地化（降低出域比例）
3. 模型侧约束（限制路由范围，如 DeepSeek 4 节点——但牺牲模型能力）

**设计含义**：**MoE 的跨节点能力上限由互联决定，不由模型决定**——这是"硬件为模型立法"的典型。开放生态（UALink/PCIe fabric）必须回答"动态路由确定性"问题，否则 MoE 推理只能被锁在小域内。

## 8. 对服务器研发的启示

从本分析直接导出的产品/架构决策：

| 领域 | 启示 | 优先级 |
|:-----|:-----|:-------|
| **推理服务器形态** | decode 服务器按"KV 带宽 + 低延迟互联"设计，prefill 服务器按"算力密度"设计（PD 分工） | P0 |
| **互联拓扑** | 域内（NVLink/UALink）是 TP/MoE 的家，域间只做 DP/PD；**避免"跨机架 TP"中间态**（7.2） | P0 |
| **KV 分层** | HBM→CXL→SSD 三级成为长上下文推理标配；CXL 池化延伸 KV 容量（✅ 库内 CXL 专题） | P0 |
| **MoE 互联** | 若目标负载含 MoE 推理，互联必须支持确定性动态路由（交换结构/在网计算），否则被 4 节点上限锁死 | P1 |
| **故障设计** | 推理节点按"无状态请求 + 前缀缓存重建"设计，不是 checkpoint；decode 池热备 | P1 |
| **超节点定位** | 超节点 = 推理 scale-up 域 + 训练 scale-up 复用（一鱼两吃）；Helios 架构（域内全对等 + 域间请求级）是参考样本 | P1 |
| **软件栈** | 调度器做拓扑感知（请求→就近、PD 配对、MoE 路由感知拓扑）；推理引擎与互联协同（fused 通信） | P2 |

**一句话**：**服务器厂商的推理产品设计，本质是在回答"延迟预算表"——你的互联拓扑、内存层级、故障模型，都必须能从一张 SLO 驱动的预算表推导出来。**
