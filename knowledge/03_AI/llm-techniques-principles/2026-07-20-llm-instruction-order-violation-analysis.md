## §0 术语约定

| 术语 | 含义 |
|:-----|:------|
| **顺序指令** | 提示词中明确指定内容或步骤先后关系的要求（如"先写背景再写方法"） |
| **语义自组织** | 模型基于训练数据分布，自主决定内容组织的倾向 |
| **弱信号/强信号** | 模型在冲突约束中优先遵循哪条——强信号会覆盖弱信号 |
| **结构冲突** | 用户的顺序要求与模型内部的内容组织模板之间的冲突 |
| **注意力头** | Transformer 中计算 token 间相关性的子网络，**集合操作**（所有位置两两可见） |
| **模板先验** | 模型在训练数据中见过的、对某种内容类型的默认组织方式 |

## §1 核心谜题：你明明说了顺序

### 1.1 典型场景

**场景 A — 文档生成**：

```text
用户："请生成一份技术方案，第一段写背景，第二段写方案目标，第三段写技术路线。"
AI输出："方案目标：... 技术路线：... 背景：..."（顺序错乱）
```

**场景 B — 多步骤指令**：

```text
用户："请先检查文件是否存在，如果存在则读取内容，如果不存在则创建文件。"
AI输出：[直接开始读文件，没有先检查]
```

**场景 C — 结构化输出**：

```text
用户："输出的JSON中，第一个字段是id，第二个字段是name，第三个字段是description。"
AI输出：{"name": "...", "description": "...", "id": "..."}
```

### 1.2 问题的反直觉性

对人类而言，"先A再B"是最自然的事情——我们的大脑天生就是顺序执行的：

```text
指令 -> 解析 -> 规划 -> 执行A -> 执行B -> 输出
```

但AI的工作方式完全不同：

```text
指令 -> 所有token可见 -> 计算概率分布 -> 直接输出最可能的结果
```

**没有「执行」的概念，只有「生成」**。

### 1.3 问题的普遍性

这不是某个模型的bug，而是**所有自回归Transformer的共性特征**：

| 模型类别 | 顺序遵循能力 | 说明 |
|:---------|:-----------:|:------|
| GPT-4o / Claude 3.5 | ★★★☆☆ | 短序(2-3步)还行，长序(>5步)频繁出错 |
| DeepSeek-V3 | ★★★☆☆ | 同上 |
| Llama 3 70B | ★★☆☆☆ | 更依赖训练模板先验 |
| 小模型(<7B) | ★☆☆☆☆ | 基本忽略顺序，只抓关键词 |
| 代码模型(Coder) | ★★★★☆ | 代码本身就有精确顺序，微调后明显改善 |

## §2 根因层：架构决定行为（第一性原理）

> 一切问题源自同一个架构决策：**Transformer把文本当作「集合」而非「程序」来处理**。

### 2.1 Transformer的核心矛盾

```text
人理解指令的方式：             Transformer处理指令的方式：

[1] 解析顺序 -> [2] 理解每个    [1] 所有token同时进入注意力
    步骤含义 -> [3] 按序执行        机制，两两计算相关性
                                  [2] 每个token的位置信息仅
                                      通过位置编码传递（弱信号）
                                  [3] 输出是概率生成的，不
                                      存在"执行路径"
```

### 2.2 注意力机制的「集合性」是根本原因

自注意力机制的本质公式：

```text
Attention(Q, K, V) = softmax(QK^T / √d) · V
```

**关键观察**：

1. **QK^T 矩阵计算的是所有位置对之间的注意力得分** — 位置i可以看位置j，位置j也可以看位置i，没有方向性
2. **softmax 是归一化操作** — 所有位置的权重加起来等于1，模型决定"关注哪里"而不是"先执行哪个"
3. **位置编码是加法而非乘法** — 位置信息是通过加法混入 token 嵌入的，而不是作为执行顺序的控制信号

这意味着：

```text
"先写背景，再写方案目标，最后写技术路线"

模型理解成：
    {背景, 方案目标, 技术路线}  <- 这是一个无序集合
    + 每个词有位置标签（"先"在一开始，"最后"在末尾）

而不是：
    [1] -> [2] -> [3]  <- 这是一个有序执行序列
```

### 2.3 自回归生成 ≠ 顺序执行

虽然模型是"一个token接一个token地生成"，但这**不等于顺序执行**：

```text
自回归生成（实际情况）：
  "方案目标" <- 模型认为以"方案目标"开头概率最高
     v
  "是" <- 给定"方案目标"，"是"概率最高
     v
  "..." <- 继续
     v
  "背景" <- 当已经写了方案目标，决定在前面补背景

这类似于一个人先写了第二章，再回头写第一章。
不是顺序执行，而是概率优化。
```

### 2.4 训练数据分布与模板先验

模型训练数据的组织方式决定了它的"默认模板"：

| 文档类型 | 典型组织方式 | 与用户顺序冲突的频率 |
|:---------|:-----------|:-----------------:|
| 技术方案 | 方案目标→背景→技术路线 | 高（有标准模板） |
| 论文摘要 | 背景→方法→结果→结论 | 中（IMRaD结构） |
| README | 项目介绍→安装→使用 | 高（GitHub模板） |
| API文档 | 概述→认证→端点 | 高（OpenAPI规范） |
| 周报 | 本周工作→问题→下周计划 | 中 |
| 代码 | 导入→配置→主逻辑 | 高（PEP8规范） |

当用户指定的顺序**与模板先验一致**时，遵循得好。
当用户指定的顺序**与模板先验冲突**时，95%的情况下模型优先遵循模板。

### 2.5 注意力掩码的影响

因果注意力（causal attention）的掩码机制：

```text
标准Transformer Decoder:
    位置1 位置2 位置3 位置4
P1    ✓    ✗    ✗    ✗
P2    ✓    ✓    ✗    ✗
P3    ✓    ✓    ✓    ✗
P4    ✓    ✓    ✓    ✓
```

这意味着生成位置4的token时，可以"看到"位置1、2、3。但**先看到哪个和先执行哪个是两回事**——它只是看到了所有已生成的内容，并不意味着它按你指定的顺序生成了这些内容。

## §3 具体机制：为什么「顺序」对模型是弱信号

### 3.1 七重信号衰减链

用户的顺序指令从输入到输出，经历了七重信号衰减：

```text
+-----------------------------------------------------+
|  信号衰减链                                           |
|                                                        |
|  用户写的顺序要求                                       |
|     v  ① 编码混淆：自然语言中的"先/再/最后"是语义暗示    |
|           而非控制信号，模型可能当成修辞而非指令            |
|     v  ② 位置编码弱：位置信号是加法嵌入，容易被内容淹没    |
|     v  ③ 注意力分散：长提示词中，早期位置的顺序要求        |
|           被"Lost in the Middle"效应稀释                  |
|     v  ④ 指令冲突：模板先验 vs 用户顺序                   |
|           模型用启发式决定谁胜出                           |
|     v  ⑤ 概率优势：模型按概率生成，有序版本概率可能        |
|           低于模板版本                                   |
|     v  ⑥ 连贯性优先：RLHF偏好流畅连贯的文本，              |
|           机械按顺序可能影响可读性                        |
|     v  ⑦ 训练偏差：SFT数据中顺序要求通常是非强制性的        |
|           （"可先写背景" vs "必须先写背景"差异巨大）        |
|                                                        |
|  模型输出（被大量衰减后的微弱信号）                        |
+-----------------------------------------------------+
```

### 3.2 信号强度对比

对模型而言，不同约束的信号强度不同：

| 约束类型 | 信号强度 | 示例 | 模型遵循率 |
|:---------|:-------:|:-----|:---------:|
| **格式约束**（JSON/XML） | ★★★★★ | "输出必须是JSON" | >90% |
| **内容约束**（写什么） | ★★★★☆ | "讨论GPU可靠性" | >85% |
| **长度约束**（写多长） | ★★★☆☆ | "控制在200字以内" | ~60% |
| **风格约束**（怎么写） | ★★★☆☆ | "用专业语气" | ~65% |
| **模板先验**（隐含） | ★★★☆☆ | 模型默认的文档结构 | ~80% |
| **顺序约束**（什么顺序） | ★★☆☆☆ | "先写背景再写方案" | ~40% |
| **细粒度顺序**（段落级） | ★☆☆☆☆ | "第三段写...第四段写..." | <20% |
| **交叉引用约束** | ★☆☆☆☆ | "在X节提到Y内容" | <15% |

**顺序约束是信号最弱的约束之一**——它的强度仅高于交叉引用约束。

### 3.3 "Lost in the Middle"效应对顺序的致命打击

Liu et al. (2024) 的研究证实：

```text
提示词中不同位置信息的召回率（约数）：
+-----+
| 开头 | ~70%  <- 用户通常在这里写顺序指令
+-----+
| 中间 | ~45%  <- 顺序指令可能被稀释
+-----+
| 结尾 | ~80%  <- 如果顺序指令在末尾，遵循率更高
+-----+
```

**灾难性后果**：

1. 用户习惯在提示词**开头**强调顺序（"请按以下顺序..."）
2. 但开头的顺序要求被后续大量内容稀释后，在**生成阶段**已处于"中间"位置
3. 模型生成时，最后看到的（或最近的）内容更有影响力

这意味着：

```text
用户写在最前面的顺序要求 -> 在生成时已被推到"中间"位置
-> 被后续具体内容细节淹没 -> 遵循率极低
```

## §4 为什么文件生成场景最严重

### 4.1 文件生成的特殊性

文件生成场景**集齐了所有不利条件**：

| 条件 | 描述 | 影响 |
|:-----|:-----|:-----|
| **长内容** | 文件通常 >500 tokens | Lost in Middle 严重 |
| **强模板先验** | 每种文件类型都有默认模板 | 模板冲突概率最大 |
| **多指令并行** | 同时要求顺序+内容+格式+风格 | 指令竞争加剧 |
| **一次性输出** | 不像对话可以迭代修正 | 错误无纠正机会 |
| **结构敏感性** | 顺序错了影响可读性 | 不像短回复那样容错 |
| **生成长度大** | 数千token的序列 | 早期token决定结构，后期难修正 |

### 4.2 模板先验 vs 用户顺序的冲突矩阵

以技术方案为例：

```text
模型内部的"技术方案"模板（训练数据学来的）：
  1. 项目背景
  2. 方案目标
  3. 技术路线
  4. 实施计划
  5. 预期效果

用户指定的顺序（合理但反模板）：
  1. 预期效果（先给结论，再解释）
  2. 技术路线
  3. 方案目标
  4. 项目背景
  5. 实施计划

冲突分析：
  - 第1段：用户可以写"预期效果" -> 但模型可能先写背景再写预期
  - 第2段：用户可以试图继续控制 -> 但模型已经在按模板走
  - 第3段以后：几乎完全失去控制
```

### 4.3 文件生成的"首Token决定结构"现象

对于长文本生成，**前几个token决定了整体结构**：

```text
模型生成第一个token时面临的选择：
  "方案" (背景)  vs  "预期" (效果)

概率对比（假设）：
  P("方案") ≈ 0.65  <- 模板先验占优
  P("预")  ≈ 0.15  <- 用户顺序要求的影响
  P("技")  ≈ 0.12
  P("项")  ≈ 0.08

一旦模型选择了"方案"，后面的内容自动对齐模板。
用户指定的顺序被彻底打破。
```

## §5 解一：工程层面（不改模型，改交互方式）

### 5.1 分步生成法（最有效）

将"一次生成整个文件"改成"分步生成，分段输出"：

```text
❌ 错误做法（一次下完所有指令）：
  用户："先写背景，再写方案目标，最后写技术路线"
  AI输出：[三个混在一起或顺序错乱]

✅ 正确做法（分步引导）：
  第1步：用户："写第一段：项目背景，约200字"
         AI输出：[背景段]
  第2步：用户："基于以上背景，写第二段：方案目标"
         AI输出：[方案目标段]
  第3步：用户："结合前两段，写第三段：技术路线"
         AI输出：[技术路线段]
```

**为什么有效**：

```text
原理：
  单步指令集很小（只做一件事）
  -> 模板先不被触发（没有完整文档要生成）
  -> 注意力集中在当前指令上
  -> 顺序由外部对话轮次控制，而非模型内部排序
```

**适用场景**：所有文件生成，尤其长文档（>500 tokens）

**代价**：需要多轮交互，速度变慢

### 5.2 骨架优先法

先生成文件的结构骨架（标题+章节标题），再逐段填充内容：

```text
第1轮：用户："请为技术方案生成章节骨架，按顺序：背景、方案目标、技术路线"
       AI输出：
         # 技术方案
         ## 1. 项目背景
         ## 2. 方案目标
         ## 3. 技术路线
         ## 4. 实施计划

第2轮：用户："请填充'项目背景'章节"
       AI输出：[内容]

第3轮：用户："请填充'方案目标'章节"
       AI输出：[内容]
```

**为什么有效**：

```text
骨架本身就是"顺序的物理载体"
  每个章节标题占据物理位置
  后续填充时，模型"看到"标题的顺序 -> 被迫按顺序填充
  不需要依赖模型的"顺序理解"能力
```

### 5.3 标记锚点法

在提示词中嵌入**不可见的锚点标记**，作为顺序的物理锚：

```text
请生成技术方案，严格按以下结构：
[SEQ-BEGIN]
[SEC-1] 项目背景
[SEC-2] 方案目标
[SEC-3] 技术路线
[SEQ-END]

各章节内容如下：
[SEC-1]: ...
[SEC-2]: ...
[SEC-3]: ...

输出时保持章节顺序不变。
```

**为什么有效**：

```text
标记 `[SEC-1]` `[SEC-2]` `[SEC-3]` 是离散符号
  -> 模型对离散符号的遵循率远高于自然语言描述
  -> 数字编号是强顺序信号（1<2<3明确）
  -> 标记在输出中重复出现，形成物理约束
```

### 5.4 结构化输出约束法

强制用 JSON/XML/格式化的结构化输出，利用格式本身的顺序特性：

```text
✅ 使用 JSON 约束：
用户："请按以下JSON Schema输出（字段顺序不可改变）：
       {"background": "...", "objective": "...", "approach": "..."}"

✅ 使用 Markdown 编号列表：
用户："输出格式：
       1. 背景：...
       2. 目标：...
       3. 方案：..."

✅ 使用 XML：
用户："<doc>
         <section id="1" title="背景">...</section>
         <section id="2" title="目标">...</section>
       </doc>"
```

## §6 解二：提示工程层面（让顺序从弱信号变强信号）

### 6.1 自然语言 → 编号列表（最大杠杆）

将"先A再B"的自然语言描述转换为**编号列表**，是最简单且最有效的改变：

```text
❌ 弱信号： "请先写背景，再写方案目标，最后写技术路线"
             -> 模型把"先/再/最后"当成修辞而非指令

✅ 强信号： "请严格按以下顺序输出：
              第1部分：项目背景
              第2部分：方案目标
              第3部分：技术路线"
             -> 数字编号+编号列表格式是强顺序信号
```

**原理**：

```text
编号 = 数学上非常明确的大小关系（1 < 2 < 3）
列表 = 训练数据中频繁出现的顺序结构
模型对标记的结构化顺序遵循率是自然语言的 2-3 倍
```

### 6.2 否定示例增强

给出**反例**来说明什么是不允许的：

```text
请按以下顺序输出：背景 -> 目标 -> 技术路线

注意：❌ 不允许先写目标再写背景
      ❌ 不允许将背景和目标合并在一起
      ❌ 不允许在背景段中提前讨论技术路线
```

**为什么有效**：

```text
否定示例 = 明确圈定了"错误空间"
模型在遇到信号模糊时，会回避已被告知是错误的路径
这是一种"负强化"——模型怕犯错，会主动避免
```

### 6.3 递归强调法

在提示词的不同位置多次强调顺序要求：

```text
开头："请严格按以下顺序生成：背景(第1部分)->目标(第2部分)->技术路线(第3部分)"

中间：（每个章节描述末尾）
      "注意：此内容属于第X部分，必须放在第X位置"

结尾："再次确认：你的输出必须严格按照 背景->目标->技术路线 的顺序"
```

**为什么有效**：

```text
多次出现 = 信号累积
每个位置都能"重新激活"顺序约束
减轻 Lost in the Middle 效应
```

### 6.4 输出模板嵌入

直接给出输出模板，让模型"填空"：

```text
请按以下模板输出（保持结构不变，只填充 { } 中的内容）：

## 1. 项目背景
{在此处写背景，约200字}

## 2. 方案目标
{在此处写目标，约200字}

## 3. 技术路线
{在此处写技术路线，约300字}
```

**为什么有效**：

```text
模板 = 顺序的物理载体
模型看到已写好的"## 1." "## 2." "## 3."
-> 不会自己重新组织顺序
-> 模板的物理结构比语义描述强得多
```

### 6.5 约束强度分级

不同表达方式对模型遵循率的影响：

| 表达方式 | 遵循率 | 示例 |
|:---------|:-----:|:------|
| 自然语言描述 | ~40% | "先写背景再写方案" |
| 编号列表 | ~65% | "1.背景 2.方案 3.技术" |
| 编号列表+严格指令 | ~75% | "必须严格按顺序：1)... 2)... 3)..." |
| 编号+否定示例 | ~80% | 同上 + "不允许改变顺序" |
| 输出模板 | ~90% | 给出固定的模板结构 |
| 模板+填空 | ~95% | 模板中{留空}让模型填充 |
| 多轮分步 | >99% | 一轮生成一个部分 |

## §7 解三：系统架构层面（多轮编排 + 验证循环）

### 7.1 编排器模式（本系统已实践）

将文件生成拆解为由**编排器**控制的多步流程：

```text
+--------------+
|   编排器      | <- 顺序逻辑由外部控制，不依赖模型内部
|  (Orchestrator) |
+------+-------+
        |
   +----+----+     +--------------+
   | 第1步    |----->| 生成"背景"    |
   | 指令生成 |     +------+-------+
   +----+----+            | 输出背景段
        |                 v
   +----+----+     +--------------+
   | 第2步    |----->| 生成"方案目标" |
   | 指令生成 |     +------+-------+
   +----+----+            | 输出目标段
        |                 v
   +----+----+     +--------------+
   | 第3步    |----->| 生成"技术路线" |
   | 指令生成 |     +------+-------+
   +----+----+            | 输出路线段
        |                 v
   +----+----+     +--------------+
   | 组装器    |----->| 合并为完整文档 |
   +---------+     +--------------+
```

**核心原则**：

```text
顺序控制权从模型内部 -> 外部编排器
模型只负责"写这一块"，不负责"怎么组织"
顺序的可靠性 = 外部代码的可靠性 ≈ 100%
```

### 7.2 验证循环

生成后自动检查顺序是否符合要求：

```text
第1步：生成完整文档
第2步：解析文档结构（章节标题/段落顺序）
第3步：与要求的顺序比对
第4步：如不一致，标记问题并重新生成对应部分

伪代码：
  function generate_in_order(sections):
      output = ""
      for section in sections:
          content = call_llm(f"生成{section.name}，约{section.length}字")
          output += f"## {section.name}\n{content}\n\n"
      return output
```

**本系统已实现类似模式**：Ralph 验证循环（Pipeline Stage 4）。

### 7.3 约束编码法

将顺序规则编码为可执行的模式：

```text
不是用自然语言描述顺序要求，
而是用结构化约束（如 JSON Schema / 正则 / 语法规则）：

{
  "type": "object",
  "properties": {
    "background": {"type": "string", "order": 1},
    "objective": {"type": "string", "order": 2},
    "approach": {"type": "string", "order": 3}
  },
  "required": ["background", "objective", "approach"],
  "additionalProperties": false
}
```

## §8 解四：路线图层面（未来可能根治的方案）

### 8.1 当前技术方案的能力边界

| 方案 | 当前可靠性 | 成本 | 适用规模 |
|:-----|:---------:|:----:|:--------:|
| 多轮分步 | 99%+ | 高（多轮调用） | 所有规模 |
| 骨架先填 | 95%+ | 中 | 中大规模 |
| 输出模板 | 90%+ | 低 | 中小规模 |
| 提示工程 | 40-80% | 极低 | 所有规模 |
| 结构化约束 | 85%+ | 低 | 结构化输出 |

### 8.2 近期可行改进（1-2年）

1. **指令微调强化**：在SFT数据中增加"严格按顺序生成"的样本
2. **约束解码**：在生成时通过约束解码（grammar-based sampling）强制按顺序输出
3. **顺序Token化**：将顺序信息编码为特殊的控制token，而非依赖位置编码
4. **外部记忆+规划**：模型先生成"内容规划"，再按规划执行

### 8.3 远期根治方案（3-5年）

1. **执行-生成分离架构**：将"内容生成"和"结构组织"分离为两个独立模块
2. **指令感知注意力**：设计能区分"指令"和"内容"的注意力机制，指令不参与内容生成的概率竞争
3. **神经程序合成**：将提示词编译为可执行的"程序"，模型只负责生成内容块，程序负责顺序组织
4. **面向目标的生成**：不再是逐token概率生成，而是面向目标的多步执行

### 8.4 警惕：不要追求"完美遵循"

有时候，模型的**合理变通**是有价值的：

```text
用户："先写背景再写目标"
模型认为：把目标和背景放在一起更合理

如果模型严格遵守："背景：...（20字）目标：...（20字）"
如果模型合理变通："背景与目标紧密相关，以下是综合分析..."
```

**判断标准**：

| 场景 | 是否要求严格遵循 | 原因 |
|:-----|:---------------:|:------|
| 表单/固定格式 | ✅ 必须严格 | 顺序错误导致后续处理失败 |
| 代码生成 | ✅ 必须严格 | 语法和逻辑依赖顺序 |
| API输出 | ✅ 必须严格 | 解析依赖固定字段位置 |
| 报告/文档 | ⚠️ 建议严格 | 顺序错误影响阅读但不致命 |
| 创意写作 | ❌ 可放宽 | 模型的组织可能更好 |

## §9 决策指南：场景 × 解法匹配矩阵

### 9.1 选择流程

```text
你的场景属于哪种？

1. 长度 < 200 tokens（短文本）
   +- 用提示工程（编号列表+严格指令）-> 90% 解决
   +- 若失败 -> 模板填空法

2. 长度 200-1000 tokens（中等文本）
   +- 输出模板法 -> 90% 解决
   +- 若失败 -> 骨架先填法

3. 长度 > 1000 tokens（长文本）-> 直接走骨架先填法或多轮分步
   +- 可多轮交互 -> 多轮分步法（可靠性 99%+）
   +- 需一轮生成 -> 骨架+模板联合法（可靠性 90%+）

4. 结构化为先（JSON/XML等）
   +- 结构化输出约束 -> 90% 解决
   +- 若失败 -> 多轮分步 + 验证循环

5. 需要精确控制每个段落
   +- 直接走编排器模式（外部控制顺序）
```

### 9.2 方法对比总表

| 方法 | 可靠性 | 成本 | 复杂度 | 最佳场景 | 局限性 |
|:-----|:-----:|:----:|:------:|:---------|:-------|
| **编号列表** | 65% | 零 | 极低 | 短文本 | 长文本失效 |
| **否定示例** | +10pp | 零 | 低 | 配合其他方法 | 单独使用效果有限 |
| **递归强调** | +5pp | 零 | 低 | 多指令场景 | 增加token消耗 |
| **输出模板** | 90% | 低 | 低 | 所有结构化文档 | 模板本身消耗token |
| **骨架先填** | 95% | 中 | 中 | 中长文档 | 需多轮交互 |
| **多轮分步** | 99%+ | 高 | 中 | 重要长文档 | 成本最高 |
| **结构化约束** | 85% | 低 | 低 | JSON/XML | 仅限结构化输出 |
| **验证循环** | 98%+ | 中 | 高 | 自动化工件生成 | 需编排系统 |
| **编排器** | 99%+ | 高 | 高 | 复杂多步任务 | 实现成本高 |

### 9.3 本系统（cow）的实践建议

基于已有架构（编排器+验证循环+约束编码），推荐：

```text
1. 简单文档（<500 tokens）:
   提示工程（编号列表+模板）-> 够用

2. 复杂文档（知识库文档/报告）:
   骨架先填法（编排器控制多轮分步）
   + Ralph验证循环（P4）检查结构
   + 约束编码（P5）确保格式

3. 需要精确顺序的关键任务:
   编排器（P1-P6全流程）
   每步独立调用模型
   外部组装最终输出
```

## §10 总结

### 10.1 三条核心规律

```text
规律一：架构决定行为
  Transformer 的注意力机制是集合操作而非顺序执行
  -> 顺序指令天生是弱信号
  -> 不是模型的"失误"，而是架构的"特性"

规律二：物理约束 > 语义约束
  编号列表 > 自然语言描述
  输出模板 > 顺序要求
  多次强调 > 单次强调
  -> 顺序需要"物化"而非"说明"

规律三：外部控制 > 内部依赖
  编排器的顺序 = 代码级别的可靠
  模型内部的顺序 = 概率级别的不可靠
  -> 关键场景把顺序控制权交给外部系统
```

### 10.2 一句话速记

> **要告诉AI「内容是什么」而不是「顺序是什么」。顺序用物理结构（模板/编号/分段调用）来保证，而不是用自然语言来描述。**

### 10.3 与系统架构的关系

本分析补充了 `constraint-association-limitation.md`（关联约束限制）的视角：

| 文档 | 核心问题 | 根因 | 解法 |
|:-----|:---------|:-----|:-----|
| 关联约束限制 | 多文件约束难满足 | Token限制+上下文丢失 | 编排器+显式约束 |
| **顺序不遵循** | **同文件内顺序被忽略** | **注意力集合性+模板先验** | **物理化顺序+外部控制** |

两者都指向同一个大方向：**不要依赖模型内部的"理解"来保证结构完整性，用外部系统来保证。**
