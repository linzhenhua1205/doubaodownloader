## 1. 主线 A：旋转×量化 = 低比特推理主流范式

### 1.1 第一性原理：为什么"旋转×量化"成立

```
量化误差来源：权重/激活中的离群值（outliers）占满量化范围
  → 均匀量化下小值精度被离群值压垮

旋转（Hadamard/Random Orthogonal）的作用：
  把离群值能量"扩散"到所有维度（全局能量均匀化）
  → 各维度幅值分布更均匀 → 量化误差降低
  → 代价：需要额外旋转运算（O(n²) 或 FHT O(n log n)）

组量化（group-wise）的作用：
  局部尺度（per-group scale）保留局部精度
  → 与旋转天然冲突：旋转是【全局】变换，组缩放是【局部】语义
  → 旋转破坏了组内幅值统计 → 组合失配
```

**这是 GyRot 论文的核心问题主张**：旋转与组量化的组合"often leads to accuracy degradation or hardware overhead due to a mismatch between the global nature of rotation and the localized behavior of group scaling"——**全局变换 vs 局部语义失配**，这是第一性层面的洞察，解释了为什么简单叠加两个好方法会互相破坏。

### 1.2 GyRot（2607.27694，HPCA 2026，KAIST）：算法重构派

| 组件 | 作用 |
|:-----|:-----|
| **CoRFiG**（Coarse Rotation, Fine Grouping） | 粗粒度旋转 + 细粒度分组**对齐**——让旋转粒度与组缩放语义匹配 |
| **HAP**（Harmonic-Aligned Permutation） | 谐波对齐置换——进一步协调旋转与分组的谐波结构 |
| 非对称量化重构 + 零点取整 | **全整数反量化**——去除浮点反量化硬件开销 |

**结果**：INT4 tensor PE 架构，LLaMA 家族 4-bit 精度 SOTA，3.4× 加速、3.6× 能效（vs 基线 LLM 加速器）。

### 1.3 LightRot（2607.27704，JETCAS，KAIST）：硬件适配派

| 组件 | 作用 |
|:-----|:-----|
| **GLR**（Grouped Local Rotation） | 分组局部旋转——把旋转从全局改为局部，规避全局-局部失配 |
| **ODA**（Outlier Direction Aligning） | 离群方向对齐——定向处理离群值 |
| 层级 **FHT** 旋转单元 | 快速 Hadamard 变换硬件——把旋转运算本身做成低能耗单元 |

**结果**：28nm CMOS，4-bit 推理 **27.4 TOPS/W**（超越前 SOTA）；面向 LLaMA2-13B/LLaMA3-8B + MT-Bench——**评测从"GPT-2 语言建模玩具"升级到"真实对话负载"**（论文自述 redefining benchmarks）。

### 1.4 三篇对照：范式成熟的证据链

| 维度 | OptR（08-07） | GyRot（07-30） | LightRot（07-30） |
|:-----|:-------------|:---------------|:-----------------|
| 协同方式 | 输出感知旋转（软件） | 算法重构（CoRFiG/HAP） | 硬件适配（FHT/GLR） |
| 载体 | 量化框架 | INT4 PE 加速器 | 28nm 专用芯片 |
| 解决的核心 | 旋转方向选择 | 旋转×分组失配 | 旋转运算能耗 |
| 机构 | — | **KAIST（Hoi-Jun Yoo 团队）** | **KAIST（同一团队）** |

**关键判断**：
1. **同一团队同日提交两篇** = 学术界的"范式确认"信号——团队内部两条路线并行（算法重构 vs 硬件适配），说明该方向已从单点尝试进入系统化研究
2. **旋转从"预处理技巧"升级为"第一类原语"**——三个团队独立或并行地把旋转当作低比特推理的必备组件（与量化平级），这是范式成熟的标志
3. **协同设计回归**：GyRot/LightRot/Celty 都是"算法-硬件联合设计"——2024-2025 的纯软件量化时代（GPTQ/AWQ/SmoothQuant）正在被"软件×硬件"时代取代

### 1.5 风险批判（主线 A）

- GyRot/LightRot 为**同一团队自报**（KAIST），无第三方复现；HPCA/JETCAS 发表≠大规模部署验证
- 硬件论文的 3.4×/27.4 TOPS/W 为**仿真/流片前评估**（LightRot 明确 28nm 流片，但基准对比基线选择需审）
- 旋转本身有开销：LightRot 专门解决"旋转运算能耗"，说明旋转不是免费的——**纯软件路径（OptR）与硬件路径的成本收益需在真实 serving 负载下对比**

## 2. 主线 B：推理可观测性/能耗成为一等公民

### 2.1 TELLER（2608.01975，ASE 2026）：推理 = 持续运维服务

**问题**：单请求横跨推理引擎 / Python-C++ 后端 / host CUDA API / GPU kernel / 分布式通信五层——现有 profiler 只给裸时间线，日志诊断缺跨层语义。

**方案**：
```
非侵入式采集：NVTX + CUPTI 追踪 + 服务日志
  → 重建逐请求调用链树（request → step → kernel）
  → 日志-执行步对齐
  → TPE（Trace Pair Encoding）：依赖感知因果上下文切片
     压成带 parent/depth/duration 的结构 token 序列
     → 逐步 trace 长度 -80%（适度词表）
  → 多模态根因模型：异常步预测 / 算子定位 / 自然语言解释
```

**深度判断**：
1. **"推理=持续运维服务"的语义转换**：TELLER 不是性能分析工具，而是**运维 RCA 工具**——与 08-07 期 Agentic AIOps（"从分析引擎到执行引擎"）形成闭环：AIOps 要"自动灭火"，前提是 TELLER 这类**跨层可诊断性**
2. **TPE 的工程价值**：trace 压缩 80% 意味着**可观测性数据量不再爆炸**——这是可观测性落地的关键工程门槛（本系统"可观测性三要素"方法论：采集→传输→呈现，TELLER 解决的是传输成本）
3. **与 TensorCast（今日）的呼应**：一个管张量生命周期（数据面）、一个管请求生命周期（运维面）——**推理系统正在同时长出"数据管理层"和"运维诊断层"**

### 2.2 From Tokens to Watt-hours（2607.26571，GREEN-AI@ECML-PKDD 2026）

**问题**：推理能耗直接测量需硬件遥测/功率仪器/基础设施监控——限制对比研究、早期设计、可持续性报告。

**方案**：解析结构 + 经验校准的 GPU 级能耗估计（H100 级）：
- 参数缩放 transformer FLOP 核算 + 校准的内存流量因子 + FP16/BF16 张量核/高带宽内存的能耗系数
- **显式分离 prefill 与 decode**（输入 token / 输出 token / 完整请求）
- 总能耗分解为：**计算 / 参数访问 / KV cache 写 / attention 读** 四分量
- 定位：**不替代物理测量**，提供透明可复现的近似值（模型对比/绿色编码/设计期评估）

**深度判断**：
1. **能耗从"测量"到"解析估计"**：可设计期评估 = 可持续性报告和硬件选型的必要条件——**把能耗变成可计算的工程参数**（与供电量化篇的"功耗 triage"同源：功耗作为一等公民信号）
2. **四分量分解的架构洞察**：参数访问 + KV 写/读 三分量反映**内存墙主导**——与 08-05 推理冗余消除深潜（HBM 带宽稀缺排序）严格一致：能耗模型暴露的瓶颈顺序 = 带宽 > 容量 > FLOPs
3. **与今日产业篇的 OpenCost token 级成本追踪联动**：成本（钱）与能耗（瓦时）可观测性是同一趋势的两面——**"推理的每一 token 都要可归因（成本+能耗）"**

## 3. 主线 C：预填充税——系统注入 vs 模型内在

### 3.1 预填充税的定义（第一性）

```
长上下文/个性化服务：
  每轮新请求（或多轮 agent 会话）需重新 prefill 全部上下文
  → prefill 是计算密集（并行处理所有 token）
  → 重复上下文 → 重复 prefill → "预填充税"

两条减税路线：
  系统注入（InferScale，08-01）：KV 在系统层注入/复用，模型不变
  模型内在（LiveMem，08-03）：模型内建记忆状态，计算前向推进
```

### 3.2 LiveMem（2608.02515）：模型内在路线

**核心形式化**：`state continuity under context turnover`（上下文轮换下的状态连续性）——**携带固定容量记忆状态的计算前向推进，记忆状态生命周期独立于活动上下文**。

**机制**：
```
预训练全注意力 LLM + 内在记忆状态（memory state）
  ├─ 主注意力路径：保持有界 KV 窗口（bounded KV window）
  ├─ 记忆状态：跨上下文轮换持续存在
  ├─ 记忆导向后训练（memory-oriented post-training）
  └─ 状态感知服务（state-aware serving）
     → 证据 token 释放后，记忆状态仍承载信息
```

**结果**：LongMemEval 上证据移出当前上下文仍能作答；证据-距离分析表明有用信息在活动窗口外持续存在。

### 3.3 两路线对照

| 维度 | InferScale（系统注入） | LiveMem（模型内在） |
|:-----|:----------------------|:--------------------|
| 修改面 | 系统层（KV 管理/注入） | 模型层（记忆状态+后训练） |
| 模型不变性 | ✅ 不改模型 | ❌ 需后训练 |
| 部署成本 | 低（serving 栈改造） | 高（模型+serving 双改） |
| 状态语义 | KV 语义（受限） | 可学习记忆（更丰富） |
| 上下文无关性 | 部分（KV 仍关联 token） | 完全（状态独立于 token） |
| 长期可扩展 | 受 KV 容量约束 | 固定容量状态 |

**深度判断**：
1. **这是"系统 vs 模型"范式之争在记忆领域的映射**——与 LLM 推理整体趋势一致：能力从系统层（检索/KV 注入）向模型层（内在记忆/推理能力）迁移
2. **LiveMem 若验证成功，serving 架构将被重构**：不再需要 KV 缓存管理复杂系统（TensorCast/InferScale 的问题空间），只需维护固定记忆状态——**这是对当日 TensorCast"张量管理层"叙事的潜在颠覆**（模型内在化 = 不需要系统层张量管理）
3. **但风险高**：后训练成本、记忆状态的可解释性/可审计性、长程遗忘——LongMemEval 是合成基准，真实 agent 负载未验证

## 4. 主线 D：双稀疏/低秩 serving 工程化

### 4.1 SALT（2608.03579）：子空间对齐的极致低秩 LoRA

**问题**：多租户 LoRA 服务两难——高秩适配器精度好但 PCIe 换入换出开销大；超低秩（r≤2）省内存但掉精度。

**方案**（三阶段）：
```
① 域质心联合训练 + 对齐正则化（域公共子空间）
② 用户私有数据上冻结质心微调 r≤2 任务残差
③ 推理：质心常驻 GPU，按需动态换入残差
```

**结果**：r≤2 残差恢复高秩精度（较 SOTA 压缩基线绝对精度 +18.5%）；单适配器内存 **-16×**；vLLM 集成后 PCIe 带宽压力下吞吐 +51%、VRAM 约束下 +28%（Llama-3.2-3B）。

**与今日 PLoRA 的路线对照**（两篇 multi-LoRA 服务的不同解法）：

| 维度 | PLoRA（今日归档） | SALT（本篇） |
|:-----|:------------------|:-------------|
| 解法 | 池化内存 + NDP（硬件路线） | 极致低秩 + 质心常驻（算法路线） |
| 关键 | 数据放池里算（32GB/s 饱和） | 数据压到 r≤2（-16× 内存） |
| 适用 | 1000+ 适配器超大规模 | 中规模、PCIe 受限场景 |
| 互补性 | 容量瓶颈 | 精度瓶颈 |

**判断**：**"低秩到什么程度 + 数据放哪里"是 multi-LoRA 的两维设计空间**——SALT 压缩数据、PLoRA 移动数据，两者可组合（SALT 的 r≤2 残差天然适合放池化内存）。

### 4.2 Celty（2608.01536，ICCAD 2026）：双稀疏的硬件落地

**问题**：双稀疏（非结构化权重剪枝 × 运行时激活稀疏）对单用户解码最优，但构成 GPU kernel 处理不佳的 SpMspV 工作负载。

**方案**：RLC-CSC 压缩格式（向量化加载 + 双稀疏跳过无效访存）+ 流水线 RLC 解码器 Sparse SIMT Core（免软件索引重建、寄存器文件免冲突累加）。

**结果**：kernel 较 cuBLAS 最高 2.8×、较 Flash-LLM 2.4×；加 SIMT Core 后 70% 双稀疏下达 **5.3×**。

**判断**：稀疏从"算法概念"推进到"kernel+微架构联合实现"——与主线 A 的旋转×量化同构：**算法-硬件协同设计的密集回归是本期最大主题**（GyRot/LightRot/Celty 三篇硬件协同）。

### 4.3 Prox（2607.27591）：训练无关的 FFN 激活稀疏化

**问题**：FFN 主导推理访存与计算；现有训练无关方法高稀疏度下掉质量（通道选择策略缺陷）。

**关键观察**：SwiGLU 中间状态是高效通道选择信号，但获取需昂贵稠密计算。

**方案**：两阶段训练无关框架——稀疏执行只需中间状态**诱导的通道掩码**而非完整中间值，用**近似中间通道显著性**替代稠密计算。

**判断**：与 Celty 形成"算法-硬件"配对（Prox 提供稀疏掩码信号，Celty 提供执行硬件）——**稀疏化生态正在分层**：算法（Prox/SALT）提供压缩信号，硬件（Celty/LightRot）提供执行效率。

## 5. 统一主线：推理效率的三杠杆

```
                    推理效率
                    ┌───┴───┐
           数据表示         服务形态
      （降低单 token 成本）  （降低重复成本）
       ├─ 量化：GyRot/LightRot   ├─ LoRA：SALT
       ├─ 旋转：OptR/GyRot       ├─ 状态：LiveMem
       └─ 稀疏：Prox/Celty       └─ 复用：InferScale
                                  │
            度量体系（让优化可衡量）
            ├─ 运维：TELLER（跨层 RCA）
            └─ 能耗：Watt-hours（解析估计）
```

**三层逻辑**：数据表示降单 token 成本 → 服务形态降重复/冗余成本 → 度量体系让前两者可验证、可归因、可报告。**三层同时成熟 = 推理从"跑得快"进入"跑得省、可度量、可持续"阶段**。

**与当日其他深潜的闭环**：
- TensorCast（张量管理层）↔ LiveMem（模型内在化）= **系统层 vs 模型层的两种抽象路线**，本篇首次并置
- PLoRA（池化内存）↔ SALT（极致低秩）= multi-LoRA 两维设计空间
- OpenCost/Rippling（产业成本门禁）↔ Watt-hours/TELLER（技术可观测性）= **成本可观测性的技术侧与商业侧**

## 6. 风险批判

| # | 风险 | 说明 |
|:-:|:-----|:-----|
| 1 | **卖方自报 + 同源** | GyRot/LightRot 同一团队（KAIST）；无第三方复现；HPCA/JETCAS 发表≠部署验证 |
| 2 | **硬件数据为仿真/流片前** | 3.4×/27.4 TOPS-W/5.3× 的基线选择与负载代表性需审；真实 serving 负载下未验证 |
| 3 | **LiveMem 基准局限** | LongMemEval 为合成基准；真实 agent 长运行负载、记忆可审计性未验证；后训练成本未披露 |
| 4 | **Watt-hours 是估计非实测** | 解析模型的校准依赖 H100 特定能耗系数；跨代/跨厂商迁移性未验证 |
| 5 | **范式之争未决** | 系统注入 vs 模型内在、算法重构 vs 硬件适配——两条路线都有各自代价，未到收敛点 |
| 6 | **评测升级但仍有偏** | LightRot 用 MT-Bench 是进步，但对话质量 ≠ 推理系统端到端效率 |

## 7. 对国产与决策者的启示

1. **旋转原语软件化**：旋转×量化不依赖专用硬件（OptR 是纯软件路径）→ **国产推理栈（MindIE/CANN 上层）应内置旋转算子**，在 INT4/INT8 量化前先做 Hadamard 旋转，可低成本获得精度收益
2. **能耗可观测性前置**：Watt-hours 类解析模型适合**设计期选型**（国产卡对比评测的公平标尺）——建议国产卡厂商公开能耗系数，建立"每 token 瓦时"行业指标
3. **跨层 RCA 是运维必备**：TELLER 的 TPE 思路（trace 压缩 80%）可直接借鉴到国产推理平台的 profiler 设计——可观测性数据量是可落地性的关键
4. **multi-LoRA 组合路线**：SALT（r≤2）+ PLoRA（池化）可组合——国产 CXL 池化 + 极致低秩双路并行
5. **跟踪模型内在记忆路线**：LiveMem 若在真实 agent 负载验证成功，将改变长上下文服务的整个 serving 架构（KV 管理复杂度消失）——**这是对"KV 管理工具链"投资判断的风险信号**
