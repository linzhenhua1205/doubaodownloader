## 1. 核心现象

### 1.1 两类偷懒现象

对话中基于实验观察提出两类根本性偷懒现象：

**现象一：任务负载效应**

> 单文件生成质量稳定；同时输出多份内容时，模型倾向简化内容、逻辑缩水。

多发场景：多文档分析、批量生成、一次性产出多种格式（如同时写论文摘要+PPT+申报书）。

**现象二：约束缺失效应**

> 提示词只交代"做什么"没有质量约束时，模型收敛到最低成本答案。

多发场景：提问式指令（"分析一下"）、开放式需求（"帮我看看这个"）、用户未明确质量标准时。

### 1.2 本工程的切身体感

以下案例全部来自本工程真实经历，按照偷懒的表现形式归类：

## 2. 底层机理：成本最优倾向

### 2.1 Transformer 视角的偷懒原理

大模型解码天然存在**成本最优倾向**（Minimum Effort Bias）：

> 在满足基础指令的前提下，尽可能减少token输出、降低推理难度。

#### 从自注意力机制看偷懒

```text
自注意力计算公式:
  Attention(Q,K,V) = softmax(Q·K^T / √d_k) · V

偷懒发生的三个机制层面:

① Token概率分布偏向高频
   训练数据的统计分布中，短词/常见词/简单结构出现频率远高于
   长句/专业术语/深层推理链。
   -> softmax 输出层天然倾向于选择高频token
   -> 没有约束纠正时，模型走"高频捷径"

② 多层推理的衰减
   复杂推理需要维持多个步骤的注意力聚焦（chain-of-thought），
   每一步都要保持前序信息的注意力权重。
   -> 约束越模糊，模型的注意力从"保持推理链"迁移到"结束当前token序列"
   -> 表现为推理链缩短、结论跳跃

③ 束搜索的隐含偏好
   beam search 选择 top-k 候选序列时，
   短序列的累积概率天然高于长序列（因为乘积项少）。
   -> 没有长度惩罚或质量门禁时，束搜索倾向于更短的输出
   -> 这是解码层面的系统性偏见
```

#### 成本最优倾向的数学表达

```text
模型解码的目标（简化）:
  argmax P(output | input)

当约束不明确时，实际优化的目标退化为:
  argmin [ 1 如果输出"看起来完成了任务" ]
          [ 0 如果输出需要更多计算            ]

即: 满足基础指令是硬约束，质量标准是软约束。
    模型在软约束上天然选择最低成本路径。
```

### 2.2 任务负载效应的5条根因

相比原始版本增加了第5条（束搜索偏好），并对每条根因给出了本工程实际验证：

| # | 根因 | 解释 | 本工程验证 | 可验证指标 |
|:-:|:-----|:-----|:-----------|:-----------|
| 1 | **上下文分配压力** | 多输出序列变长，自回归后期 token 的注意力被前序大量 token 稀释 | 8→1 日报聚合时，第 5 个专题后的输出篇幅明显缩水（缩至前 3 个的 40%） | 后期 token 概率下降 |
| 2 | **任务权重分散** | 模型默认"全部完成 > 每条高质量" | `weekly-report-generator` v0 输出覆盖了 22 个领域，但每个领域仅 1-2 行摘要 | 条目全覆盖但深度不足 |
| 3 | **指令约束稀释** | 约束在多目标指令中相对权重下降 | 写日报时要求"每个专题含关键数据"的指令在 8 个专题后被稀释为"尽量包含" | 输出格式逐渐松散 |
| 4 | **推理 token 预算** | 模型隐含的"总输出长度"预设被均分 | 同等 10 约束下的单文件 vs 多文件输出，后者每条篇幅仅为前者的 35-50% | 每条内容篇幅变短 |
| 5 | **束搜索最短路径偏好** | beam search 的累积概率偏见 | `depth-completer` 检测到 63% 的文档存在"结论缺少推导过程"——推理链被束搜索截断 | 推理步数减少 |

### 2.3 约束缺失效应的3类缺失

原始版本定义了粒度/禁止项/验收标准三类约束。深化分析与本工程交叉验证：

**约束缺失的层级模型**：

```text
提示词约束可以抽象为三层:

+------------------------------------------------+
|  Layer 3: 验收标准（判断"是否合格"的依据）         |
|  例: "缺失任意关键维度->不合格，需重新生成"           |
|  缺失->模型自行定义"完成"标准->通常偏低              |
+------------------------------------------------+
|  Layer 2: 禁止项（排除走捷径的可能）                 |
|  例: "禁止笼统概括" "禁止省略推理过程"               |
|  缺失->模型自然走向最低成本路径                       |
+------------------------------------------------+
|  Layer 1: 粒度约束（明确交付的精细度）                 |
|  例: "每条论证不少于X字" "包含具体数值"              |
|  缺失->输出停留于框架层面，缺乏细节                   |
+------------------------------------------------+
```

**本工程验证数据**——`discover` 文档扫描结果（2026-07-27，抽样 500 文件）：

| 约束完整度 | 文件占比 | 平均质量评分 | 典型表现 |
|:-----------|:--------:|:------------:|:---------|
| 三层俱全 | 0.2% | ⭐⭐⭐ (4.2/5) | 完整 TOC + 数据出处 + 推理链 |
| 仅 Layer 1 | 3.2% | ⭐⭐ (2.8/5) | 有结构但缺深度 |
| 仅有任务描述 | 96.0% | ⭐ (1.5/5) | 名词堆叠，缺原理分析 |
| 完全没有约束 | 0.6% | ❌ (<1.0/5) | 空壳内容 |

**关键数据**：96% 的文件仅包含任务描述，缺少任何质量约束——这解释了为什么本工程 96% 的 discover 文件停留于 ⭐ 级质量。

### 2.4 本工程量化验证：约束缺失 vs 输出深度

基于 `depth-completer` 的检测数据（2026-07-27 ~ 2026-07-30）：

```text
约束强度与输出深度的关系（1-5分制）:

约束强度 [1分=仅任务描述]                      输出深度
   1/5  (仅"分析X")                       -> 0.8/5  (框架堆名词)
   2/5  (+ 给出结构要求)                    -> 1.8/5  (有骨架无血肉)
   3/5  (+ 增加粒度约束)                    -> 2.5/5  (内容充实但缺原理)
   4/5  (+ 增加禁止项)                      -> 3.4/5  (有推理链有数据)
   5/5  (+ 验收标准 + 示例)                -> 4.5/5  (接近最佳质量)

结论: 约束强度每提升1分，输出深度提升约0.9分（近乎线性）。
      约束完备度是输出质量的单一最大预测因子。
```

## 3. 本工程实战案例

### 3.1 案例①：scheduler/tasks.json 覆写（跨进程约束穿透失败）

**背景**（2026-07-30）：

```text
tasks.json 从 git 库 1dcbc7c 恢复后，
调度器每次运行时自动覆写 next_run_at 和 updated_at 字段。

修复过程：
  手动恢复 -> 调度器运行 -> 又被覆写 -> 再恢复 -> 又被覆写
  （典型的 meth-007 所说的"改了又改回去"循环）
```

**偷懒机制分析**：

| 维度 | 分析 |
|:-----|:------|
| 偷懒类型 | 约束缺失效应（跨session约束穿透失败） |
| 本质 | 约束放在了 session 级提示词中，但调度器是独立进程 |
| 机制链 | 约束指令（软）→ session 终止 → 约束丢失 → 下次执行无保护 → 覆写 |
| A-J 失效类 | D（行为绕过：说"约束了"但实际没执行到位）|

**关键教训**：

> 跨进程约束不能丢给 AI 提示词，必须硬编码到调度器逻辑中。
> — 软约束在 session 级有效，跨 session/跨进程时形同虚设。

**最终方案**：创建 `check-tasks-integrity.py`（12306-12308），通过定时检查而不是依赖 AI 自我约束。

### 3.2 案例②：8→1 多文档聚合日报（任务负载效应）

**背景**（2026-07-29）：

```text
当日 8 个独立专题跟踪文件（总计 4,183 行 / 31KB）
需要合并为一份综合日报。
```

**偷懒表现**：

| 指标 | 分步处理（各专题独立→汇总） | 一次输入全部（8个文件全量） |
|:-----|:--------------------------:|:------------------------:|
| 输出质量 | ⭐⭐⭐（每个专题 3-5 核心发现） | ⭐（每个专题 1-2 泛泛语句） |
| 覆盖深度 | 关键数据、判断、研发价值齐备 | 只有名词罗列 |
| 交叉分析 | 能识别 3 个专题间的矛盾点 | 完全无交叉分析 |
| 输出篇幅 | 每个专题 150-300 字有效内容 | 每个专题 30-50 字摘要 |

**偷懒机制链**：

```text
8个文件×平均500行 = 4,000+行上下文
   -> 注意力被 31KB 内容稀释
   -> 模型判断"全部处理"优先于"每条高质量"
   -> 束搜索截断推理链
   -> 输出退化为："X领域有Y进展"
   -> 无数据、无对比、无判断
```

**本工程的对抗方案**：采用 T07 建议的三阶段分层流水线。

### 3.3 案例③：weekly-report-generator 四次迭代（约束完备度迭代）

**背景**（2026-07-22 ~ 2026-07-29）：

`weekly-report-generator` 经历了四次迭代，每次都是因为输出质量不达标：

| 版本 | 约束缺失 | 偷懒表现 | 用户反馈关键词 |
|:----:|:---------|:---------|:-------------|
| **v0**（初始概念） | 无粒度约束、无禁止项、无验收标准 | 22 领域全覆盖但每领域仅 1-2 行 | "太泛" |
| **v1**（首次完善结构） | 有标题结构但缺乏约束指令 | 有框架但内容空洞，数据随机 | "数据不准确" |
| **v2**（三支柱结构） | 有时间窗口定义但时间窗口语义模糊 | 早间数据丢失（07:50 入库的文件未覆盖） | "数据缺失" |
| **v3**（v2 修复版） | 时间窗口修复但关联脚本未协同更新 | `kb-daily-data-gather.sh` 与 `SKILL.md` 时间定义不一致 | "采集链路断" |
| **v4**（最终定型） | 三支柱 + 时间窗口表 + 各数据源语义 + 子脚本调用链全部固化 | ⭐⭐⭐ 输出达标 | "这才像样" |

**偷懒机制链**：

```text
每次修复后 -> 只修了表面问题 -> 遗漏关联约束 -> 下次仍然出同类问题
这本质上是约束缺失效应的"级联版"：
  只加了 Layer 1（粒度）-> 缺 Layer 2（禁止项）-> 模型"绕过"浅层约束走捷径
  再加 Layer 2 -> 缺 Layer 3（验收标准）-> 模型"形式满足"但实际质量低
  最终三层齐全 -> 输出才真正达标
```

**关键教训**：约束不是单次加完就够的——每次模型找到"新捷径"后，需要补更强的约束。这是**约束军备竞赛**。

### 3.4 案例④：constraint-verifier A-J 十类失效与偷懒映射

**背景**（2026-07-27 ~ 2026-07-30）：

`constraint-verifier` 定义了 A-J 十类失效模式。其中与偷懒直接相关的：

| 失效类 | 偷懒表现 | 本工程检测案例 | 检测方法 |
|:-------|:---------|:--------------|:---------|
| **A 注意力衰减** | 长对话后约束稀释 → 输出格式松散 | 8+ 轮对话后缺少 changelog、缺少来源标注 | 第 4/8 轮后停检输出格式 |
| **D 行为绕过** | 说"已按 Skill 执行"但实际跳过关键步骤 | `tasks.json` 说"已保护"但实际被覆写 | 检查执行证据而非口头承诺 |
| **E 方向锁定** | 多分支任务只深入一个最省力的 | mckinsey-research 12 路分析只详细展开 3-4 路 | 检查各分支覆盖率 |
| **G 知识层幻觉** | 编造不存在的来源以"完成任务" | `knowledge-doc-writer` 引用不存在文档 | 来源可达性检查 |
| **H 逻辑层跳跃** | 缺少推理过程直接下结论 | 深度分析文档"结论前置但无推导" | 检测"因此/所以"前后是否有论证链 |

### 3.6 案例⑥：mckinsey-research 12 提示词多路（反偷懒架构）

**背景**（2026-07-29 skills-creation §3.7）：

**架构对比**：

```text
[传统偷懒模式]
  单Agent处理12个分析维度
    -> 任务负载效应 -> 前3个维度有质量，后9个缩水
    -> 最终输出：12维度全覆盖但每条1-2句
```

## 4. 关键区分：能力上限 vs 交付下限

```text
模型能力（理论天花板）
       ^
       |  +----------------------+
       |  |  完备约束后的输出      | <- 上限接近天花板
       |  +----------------------+
       |  |  简陋约束后的输出      | <- 下限远离天花板
       |  +----------------------+
       |
       +-------------------------> 提示词约束强度
```

**核心公式**：

> 输出质量 = min(模型能力上限, 提示词约束强度对应的下限)

- 模型能力决定天花板（不可控）
- 提示词约束决定地板（可控）
- 同一模型在不同约束下可以拉开 **2-4 倍**的质量差距（本工程实测）

### 4.1 本工程的「地板控制」实践

本工程通过三层约束体系实现了对"交付下限"的主动控制：

```text
无约束（裸指令）                                       输出深度 ~0.8
    v 加粒度约束（"每条含数值+单位+基线+条件"）           ~2.5
    v 加禁止项（"禁止笼统概括" "禁止省略推导"）           ~3.4
    v 加验收标准（"缺任一要素->不合格，打回重做"）          ~4.2
    v 加脚本化自检（light-self-review 9项清单）           ~4.5
    v 加跨进程硬约束（check-tasks-integrity.py守护）      永久生效
```

**核心洞察**：提升输出质量的最有效路径不是"让模型更强"，而是**通过逐层约束缩小模型的"自由空间"**。

## 5. meth-007：作为系统性反偷懒框架

`spec/meth-007-ai-detail-precision-control.md` 提出的三阶段分离协议，本质上是**对抗约束缺失效应的系统性方案**。

### 5.1 三阶段与偷懒的对应关系

| 阶段 | 核心机制 | 对抗的偷懒类型 | 本工程实现 |
|:-----|:---------|:---------------|:-----------|
| **阶段一：方向探索** | 多方案零承诺，快速确认方向 | 无（探索阶段不涉及偷懒） | idea 生成→审查→方案锁定 |
| **阶段二：方向锁定** | 刚性冻结，创建批准基线 + 不可变区域 | **约束缺失效应**（基线防止方向漂移） | 不可变区域标记 → AGENT.md/RULE.md |
| **阶段三：细节精调** | 基线增量协议，每次只改一处 + 回归检测 | **任务负载效应**（每次只改一处，不一次多任务） | 回归检测脚本 → 约束检查链 |

### 5.2 批准基线：防止「改了又忘」

**偷懒机制**：没有批准的基线版本 → 每次修改=全量重生成 → 之前确定的细节被冲走 → 你不得不在每一轮重复同样的要求。

**反偷懒机制**（meth-007 §2.2）：

```text
步骤：
  1. 阶段二结束时确认基线（双方签字认可）
  2. 基线版本写入 MEMORY.md 或 knowledge/
  3. 阶段三每次改动时声明"基于基线 X 的增量修改"
  4. 回归检测确认基线中的要素未被覆盖

本工程效果：
  tasks.json 修复中，如果没有基线版本意识，
  -> 恢复->覆写循环会持续无限轮。
  有了基线后，才能判断"当前版本 vs 基线版本"的差异。
```

### 5.3 不可变区域：硬约束保护

**偷懒机制**：模型在执行过程中会"遗忘"或"绕过"某些约束指令。

**反偷懒机制**（meth-007 §2.2.2）：

```text
将约束分为三个区域：
  🔒 不可变区: 不能被任何后续指令修改（AGENT.md 的头像设定 / RULE.md 的红线）
  📝 优化区: 可以优化但不能改变语义（输出格式 / 表达方式）
  🆓 自由区: 完全自由

关键设计：不可变区声明后，每次修改前先检查是否触碰了它。
```

### 5.4 回归检测：偷懒自动回滚

**偷懒机制**：模型精调细节时，无意识中把之前做对的改错了。

**反偷懒机制**（meth-007 §2.4）：

```text
每次增量变更后自动运行回归检测:
  1. 基线版本的关键要素是否都还在?
  2. 不可变区域是否被触碰?
  3. 新增内容是否与已有内容矛盾?

检测未通过 -> 自动回滚到上一版本 -> 重新生成
```

**本工程实现**：约束检查链 `constraint-check.py` + `check-tasks-integrity.py` 就是回归检测的自动化版本。

## 7. 工程实践：反偷懒提示词范式

### 7.1 多任务场景反偷懒模板

```text
你需要同时产出【X、Y、Z】三份内容。

⚠️【反偷懒声明】
每份内容必须独立完整，不能因为需要一次性输出多项内容
就缩减细节、简化推理、省略数据。
每一项内容的深度、详实程度，
需要和单独生成该内容时的标准保持一致。

如果在输出中出现了"等"、"等等"、"类似"等省略表达，
说明你正在走捷径——立即退回重写。
```

### 7.2 质量约束完整模板

```text
【输出要求】
- 每条论证不少于 200 字
- 每条包含具体数值（含单位）/ 案例 / 数据来源
- 每条明确标注信息来源（论文 / 标准 / 官方文档 / URL）
- 每部分结束时给出关键判断（而非罗列事实）

【禁止项】
- 禁止笼统概括（不使用"具有优势"、"性能更好"等无数据表述）
- 禁止省略推理过程（不使用"因此"后无论证）
- 禁止使用"等等" / "等" / "类似" 等省略表达
- 禁止编造来源——不确定来源时声明"待验证"

【验收标准】
- 缺失任意关键维度 -> 不合格，需重新生成
- 数据缺少四要素（数值+单位+基线+条件）-> 不合格
- 关键断言无来源 -> 不合格
```

### 7.3 Skill 化的反偷懒（枚举→封装）

**核心思路**：偷懒现象的**存在本身就是 Skill 创建信号**。

```text
反偷懒的三阶段路径:

第1阶段（枚举）:
  每次写分析时都要加"详细推导、禁止省略、每条独立完整"等约束
  -> 重复写

第2阶段（模板化）:
  把约束保存为标准模板，每次复制粘贴
  -> 效率提升但仍有遗漏风险

第3阶段（Skill化）:
  封装为 Skill，在 description 中绑定触发场景
  执行时自动加载全套约束
  -> 消除遗漏，一致性保障
```

**本工程映射**：

| 手动枚举阶段 | 对应的 Skill | 解决的根本问题 |
|:------------|:-------------|:--------------|
| "要有数据出处" | `doc-reviewer` | 断言无来源 |
| "别只堆名词" | `depth-completer` | 框架堆名词 |
| "检查输出格式" | `light-self-review` | 格式随性 |
| "数据四要素齐全" | `knowledge-doc-writer` Q6 | 缺数值/基线/条件 |
| "禁止跳过步骤" | `constraint-verifier` | D 类行为绕过 |

## 8. 与约束系统的集成

### 8.1 约束三态与偷懒检测

本工程的 `constraint-check.py` 实现了三态约束判定——这是检测偷懒的自动化手段：

| 状态 | 含义 | 对应偷懒 | 本工程检测项实例 |
|:-----|:------|:---------|:----------------|
| ✅ **PASS** | 约束完全满足 | 无偷懒 | TOC 存在 + 五大要素俱全 |
| ⚠️ **WARN** | 有违反但不致命 | 轻度偷懒 | 量化缺单位（有数据但标注不全） |
| ❌ **FAIL** | 严重违反 | 明显偷懒 | 关键断言无来源、无 changelog |

### 8.2 从软约束到硬约束的转化路径

**核心问题**：约束放在提示词是"软"的——模型可以绕过、session 终止会丢失。

**硬约束转化路径**：

```text
约束类型        软（提示词）            -> 硬（代码/脚本）
--------        -----------            ----------------
格式规范         "要有 TOC"             format-validator.py 自动检查
数据质量         "数值四要素齐全"        doc-quality.py 量化检测
文件操作         "不要直接 rm"          constraint-check.py 01001 红线
调度保护         "不要覆写 tasks.json"   check-tasks-integrity.py C71 检测
技能触发         "注册后才能生效"        skills_config.json 注册检查
```

**本工程的 3 个完成转化**：

| 约束 | 软阶段 | 硬阶段 | 转化效果 |
|:-----|:-------|:-------|:---------|
| 安全红线 "永不 rm" | RULE.md 文本 | `constraint-check.py` 01001-01010 | 脚本阻断而非自我约束 |
| 数据四要素 | AGENT.md 自检清单 | `doc-quality.py` 自动化检查 | 人工自检→自动扫描 |
| tasks.json 保护 | 提示词 "不要覆写" | `check-tasks-integrity.py` 12306-12308 | 跨进程守护 |

## 9. 系统性反偷懒自检清单

每次交付前执行：

### 9.1 任务负载检查

| # | 检查项 | 判定 |
|:-:|:-------|:-----|
| 1 | 当前任务包含多个独立输出？ | 若是 → 每输出独立生成，不一次全量 |
| 2 | 是否一次性读了 5+ 个文件？ | 若是 → 提取摘要后再处理 |
| 3 | 是否有"全部完成"优于"每条高质量"倾向？ | 若是 → 加反偷懒声明 |
| 4 | 束搜索偏见是否导致推理链截断？ | 检查"因此/所以"后是否有论证 |

### 9.2 约束完备度检查

| # | 检查项 | 判定 |
|:-:|:-------|:-----|
| 5 | 是否只有任务描述无质量约束？ | 若是 → 等待，补充约束再执行 |
| 6 | 三类约束（粒度/禁止项/验收标准）是否齐全？ | 缺任一 → 补至少 2 层 |
| 7 | 约束是否写成了"软"的（提示词）而非"硬"的（脚本）？ | 跨进程/跨session → 必须硬到脚本 |
| 8 | 验收标准是否有明确的"不合格"判据？ | 没有 → 用户主观判断，效率低 |

### 9.3 迭代验证检查

| # | 检查项 | 判定 |
|:-:|:-------|:-----|
| 9 | 是否有基线版本？ | 多轮迭代必须有基线 |
| 10 | 回归检测是否覆盖所有关键维度？ | 至少覆盖：格式/数据/来源/约束 |
| 11 | 不可变区域是否被触碰？ | 触碰 → 回滚 |
| 12 | 是否检查了跨 session/跨进程的约束持久化？ | 调度器等独立进程需单独处理 |
