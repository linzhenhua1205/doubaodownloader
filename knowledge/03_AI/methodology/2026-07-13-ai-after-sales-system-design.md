## 1. 项目背景与业务痛点

### 1.1 制造业售后服务的典型困境

当前制造业的售后服务普遍面临六大痛点，其根源可以归结为 **"信息断裂"与"决策滞后"** 两大核心矛盾：

| 痛点 | 业务表现 | 根因分析 | 量化影响 |
|:-----|:---------|:---------|:---------|
| **P1 问题预警缺失** | 故障发生后被动响应，设备"坏了才修" | 历史数据未形成预测模型，缺乏实时监控告警 | 非计划停机损失：制造业平均 $260k/小时 |
| **P2 备件水位符合率低** | 备件库存要么积压要么短缺，现场维修时"有单无件" | 备件需求预测依赖人工经验，未与故障模式关联 | 水位符合率仅 60-70%，备件资金占用高 |
| **P3 响应不及时** | 从报修到工程师到达周期长，客户满意度低 | 派工依赖人工调度，未考虑工程师技能/位置/负载 | 平均响应时间 4-8h，大客户 SLA 达标率 <80% |
| **P4 SLA 解决时长超标** | 工单从创建到关闭耗时过长 | 知识库不足、故障诊断依赖个人经验、备件不到位 | MTTR (平均修复时间) 超标 30-50% |
| **P5 常规工单过多** | 技术人员 70% 时间处理简单重复问题 | 一线客户可自助解决的问题未分流，问题未分级 | 高技能工程师被低价值工单占用 |
| **P6 二次维修率高** | 同一设备短期内重复报修 | 首次维修未根除、备件错误、维修操作不规范 | 二次维修率 15-25%，增加 2× 服务成本 |

### 1.2 一天的故事：传统售后困境的具象化

> 以下场景基于制造业真实案例改编，揭示六大痛点如何在实际工作中层层叠加。

**早上 08:30 — 客户设备停机**
某制造企业 A 公司的产线核心设备（型号：XYZ-2000）出现报警停机。产线班长拨打 400 热线。

**08:35 — 客服接单**
客服小张接听电话，手动在 Excel 记录：「客户A · XYZ-2000 · 报警代码 E-47 · 产线停机」。小张翻查纸质手册 5 分钟才找到 E-47 的含义——"伺服驱动过载"。她将工单通过邮件发给售后调度。

**08:45 — 调度派工**
调度老李打开邮箱看到工单，翻看工程师名单：王工（擅长 XYZ 系列，但在城北客户现场）、赵工（有空但没修过 XYZ-2000）、刘工（在休假）。老李凭经验选了赵工先去看看，电话通知。

**09:15 — 工程师到场**
赵工驱车 30 分钟到达现场，查看设备日志，发现他不熟悉这个型号的诊断流程。他拨打王工电话远程求助，王工指导他检查伺服驱动参数。

**10:00 — 发现需要备件**
赵工判断伺服驱动模块损坏，需要更换备件。他查询备件系统发现该备件库存为 0——上个月有两台同型号设备也换了同样的驱动，但系统没做补货。赵工只能下紧急采购单。

**10:30 — 备件紧急调拨**
采购部反馈该备件标准采购周期 7 天，紧急调拨也需要 24 小时。客户 A 公司产线继续停机。

● **后果**: 产线停机持续到第二天，客户损失约 $260k（按平均 $260k/h 的停机损失估算）。赵工半天时间被低效率占据。客户的维修满意度打了 1 星。

**下午 14:00 — 同一型号另一台设备也报警了**
另一条产线的 XYZ-2000 显示同样的 E-47 报警。客服小张不知道这是今天第二个同类故障，按同样流程再走一遍。如果系统能识别「同一型号、同一故障在 24 小时内出现 2 次」，本该触发批量预警并启动 RCA（根因分析）。

📌 **这个场景揭示了六大痛点的串联效应**：预警缺失（P1）→ 备件不足（P2）→ 响应慢（P3）→ 诊断慢（P4）→ 工程师被低价值工作占用（P5）→ 因备件问题导致的二次上门（P6）。一个 AI 售后系统可以在这 6 个环节中至少切断 4 个。

### 1.4 传统数据系统的局限性

```text
+-----------------------------------------------------+
|              当前系统架构的困境                        |
|                                                       |
|  +----------+     +----------+     +----------+     |
|  | ERP系统  |     | MES系统  |     | EAM系统  |     |
|  | 标准功能  |     | 固定报表  |     | 资产管理 |     |
|  +----+-----+     +----+-----+     +----+-----+     |
|       |                |                |            |
|       v                v                v            |
|  +---------------------------------------------+     |
|  |         维护数据系统 (中台)                    |     |
|  |         功能固化 · 接口固定                    |     |
|  |           无法快速响应一线需求                  |     |
|  +-------------------+-------------------------+     |
|                      |  ❌ 定制化需求无法满足          |
|                      v                                |
|  +---------------------------------------------+     |
|  |         一线业务 (售后工程师/客服/客户)         |     |
|  |         "系统数据查不到、查不全、查得慢"         |     |
|  +---------------------------------------------+     |
+-----------------------------------------------------+
```

**核心矛盾**：后端维护数据系统（EAM/ERP/MES）承担标准化数据管理，但其 **功能固化、开发周期长、响应一线需求慢** 的天然缺陷，导致：

- 一线工程师无法快速获取所需数据
- 数据分析要靠 IT 部门出报表，排期以周/月计
- 无法灵活适配不同产品线、不同客户的定制化需求
- 大多数制造业依然用 Excel + 邮件 + 电话管理售后流程，数字化程度低

### 1.5 Why Now — 为什么现在是 AI 售后最好的时机

| 驱动力 | 三年前 (2023) | 现在 (2026) | 变化实质 |
|:-------|:-------------|:------------|:---------|
| **大模型可用性** | GPT-4 刚出，成本高昂 | Qwen3/DeepSeek 开源，本地可部署 | 成本降 10×+，隐私合规可行 |
| **RAG 技术成熟度** | 检索质量不稳定，幻觉严重 | 多路召回+重排序+BGE 模型 → 准召率 95%+ | 从"玩具"到"可用" |
| **向量数据库** | 单独部署 Milvus 运维重 | pgvector 内置在 Postgres 中 | 零额外运维 |
| **NL2SQL 精度** | 70-80%，经常出语法错误 | 92%+，配合安全沙箱可用 | 风险可控 |
| **企业 AI 意愿** | 观望为主，试点项目 | 已有一轮 POC 验证，进入规模化阶段 | 预算落地 |
| **国产替代** | 依赖海外模型，数据出境疑虑 | 国产模型(Qwen/DeepSeek)追平主流 | 合规无阻碍 |

## 2. 系统定位与核心价值

### 2.1 系统定位：数据系统与一线业务的"智能中间层"

```text
+-----------------------------------------------------+
|                  业务价值层                           |
|  +----------------------------------------------+   |
|  |  一线业务 (售后工程师/客服/备件管理/客户)     |   |
|  |  "我要快速解决问题，不需要知道底层数据在哪"     |   |
|  +--------------------+-------------------------+   |
|                       |                              |
|  +--------------------v-------------------------+   |
|  |    🎯 AI智能售后中间层 (本系统)                |   |
|  |                                               |   |
|  |  核心价值: 弥补中台系统无法满足的定制化需求      |   |
|  |  +---------+ +---------+ +---------+         |   |
|  |  |  AI能力  | | 业务编排 | | 数据桥接 |        |   |
|  |  | 自然语言 | | 工单路由 | | 多源汇聚 |        |   |
|  |  | 智能诊断 | | 智能派工 | | 实时同步 |        |   |
|  |  | 预测分析 | | SLA管控  | | 历史归档 |        |   |
|  |  +---------+ +---------+ +---------+         |   |
|  +--------------------+-------------------------+   |
|                       |                              |
|  +--------------------v-------------------------+   |
|  |   维护数据系统  (EAM/ERP/MES 等中台)           |   |
|  |    "负责标准化数据管理，不负责上层智能"          |   |
|  +----------------------------------------------+   |
+-----------------------------------------------------+
```

**一句话定位**: 做维护数据系统与一线业务之间的**智能中间层**——不替代中台，而是弥补中台无法满足的定制化需求。

**关键部署决策**:

1. **AI 推理独立部署**: LLM 推理 Pod 与业务 Pod 分离，避免 AI 推理时的高 GPU 占用影响业务响应

3. **多 AZ 部署**: 关键服务跨可用区部署，保障高可用

#### 模块02: 智能派工与调度

**核心逻辑**：

```text
输入: 工单 (故障类型·位置·优先级·客户等级)
                v
        多目标优化引擎
    +-------------------------------------+
    |  目标1: 技能匹配度 (最高) -> M1       |
    |  目标2: 响应时间最短 -> M2           |
    |  目标3: 工程师负载均衡 -> M3          |
    |  目标4: 历史维修成功率 -> M4          |
    |  目标5: 差旅成本最低 -> M5            |
    +-------------------------------------+
                v
输出: 工程师推荐列表 (带评分+理由)
```

**评分公式**:

```text
Score = w1 × skill_match + w2 × (1/eta_time) + w3 × (1 - load_factor) + w4 × history_success + w5 × (1/cost_factor)

权重建议: w1=0.35, w2=0.25, w3=0.15, w4=0.15, w5=0.10
weight ∈ [0,1], sum = 1
```

**关键规则**:

- 技能不匹配的工程师直接过滤（skill_match = 0 时不进入候选）
- 紧急工单提高 w2（响应时间）至 0.40，降低 w5（成本）至 0.05
- 白金客户工单增加客户等级系数 ×1.2
- 每 30 秒重新计算一次排队工单的派工方案

**动态安全水位算法**:

```text
safety_stock = daily_avg_consumption × lead_time_days × σ × safety_factor

其中:
- daily_avg_consumption = 近90天日均消耗量 (滚动窗口)

```

| **技术方案** | 多源关联 → 因果推理 (Granger / PCMCI) → LLM 推理链 |
| **输出** | 根因 + 置信度 + 影响列表 + 短期缓解 + 长期修复 |
| **效果指标** | RCA 准确率 ≥80%；二次维修率降至 ≤8% |

**关键设计原则**:

- **人机协同打标**: AI 答案需要人工审核确认后方可自动采纳
- **闭环反馈**: 用户对 AI 回答的"有用/无用"反馈用于优化检索排序

### 8.2 外部系统集成方式

| 外部系统 | 数据同步方向 | 同步方式 | 同步频率 | 关键数据 |
|:---------|:-----------|:---------|:---------|:---------|
| **EAM系统** | EAM → 本系统 | CDC (Debezium) / API 轮询 | 准实时 (≤5min) | 设备档案、资产台账、维修历史 |
| **ERP系统** | ERP → 本系统 / 本系统 → ERP | REST API / 消息队列 | 按需+定时 | 备件主数据、库存、采购单 |
| **MES系统** | MES → 本系统 | API / 数据库视图 | 定时 (T+1) | 设备运行参数、生产节拍 |
| **IoT平台** | IoT → 本系统 | MQTT / Kafka | 实时 | 设备运行数据、告警事件、日志 |
| **CRM系统** | CRM → 本系统 | REST API | 准实时 | 客户信息、合同、联系人 |
| **企业微信** | 双向 | 企微开放平台 API | 实时 | 通知推送、消息交互 |

### 8.3 数据同步设计要点

1. **数据不冗余原则**: 本系统不完整复刻外部系统数据，只缓存高频访问+必要字段
2. **同步失败容错**: 采用"最终一致性"策略，失败消息进入死信队列+人工补偿
3. **数据时效性分级**:
   - 实时 (<1s): 设备告警、SLA超时
   - 准实时 (<5min): 工单状态变更、备件消耗
   - 定时 (T+1): 设备档案更新、财务数据
4. **ID 映射表**: 维护外部系统ID ↔ 本系统ID 的映射关系

### 8.4 错误处理与容错策略

| 故障场景 | 影响范围 | 检测方式 | 容错策略 | 恢复手段 |
|:---------|:--------|:---------|:---------|:---------|
| **EAM 系统不可用** | 设备数据无法同步 | 健康检查超时(5s × 3次) | 使用本地缓存数据(最多缓存24h) | 恢复后增量同步补数据 |
| **ERP 接口超时** | 备件库存更新延迟 | API 超时(10s) | 进入降级模式：返回上次成功缓存数据 | 异步重试(3次)+死信队列 |
| **IoT 数据断流** | 实时监控中断 | 超过30s无数据 | 故障预测使用最近一次数据估算 | 断线重连 + 断点续传 |
| **LLM 推理超时** | AI 诊断不可用 | 推理超时(15s) | 降级到规则引擎匹配(关键词→故障模式) | 排队重试 + 通知运维 |
| **数据库主库故障** | 全系统只读 | DB 连接池耗尽 | 自动切换到从库(读) + 写操作排队 | 主库自动故障转移 |
| **消息队列积压** | 工单流转延迟 | 队列深度 > 阈值 | 丢非关键消息(如操作审计)保核心流程 | 消费者扩容 + 死信重置 |

**降级策略优先级**:

```text
核心链路（不可降级）: 工单创建/派工/闭环、SLA计时、备件出库
重要链路（可降级）: AI诊断->规则引擎、NL2Query->预定义报表
非关键链路（可丢弃）: 操作审计日志、工程师位置实时更新、页面访问统计
```

### 8.5 数据质量保障规则

| 数据实体 | 质量规则 | 检测时机 | 处理方式 |
|:---------|:---------|:---------|:---------|
| **工单故障描述** | 非空 + 最低字数≥10 | 创建时 | 触发提示要求补全 |
| **备件库存** | 库存≥0 | 每次出库/入库 | 负数自动冻结出库操作 |
| **设备型号** | 必须在设备型号字典中 | 同步时 | 未识别型号进入"待确认"队列 |
| **工程师位置** | 经纬度非空 + 在国内范围 | 每15min | 位置异常标记为"位置不可用" |
| **SLA 截止时间** | 自动计算 ≤ 合同值 | 工单创建时 | 计算异常时使用默认SLA(银级) |
| **重复工单** | 同一设备+同一故障+24h内 | 创建时 | AI 检测到重复则关联已有工单 |

**数据隔离实现 (SaaS 模式)**:

```sql
-- 所有业务表加 tenant_id
CREATE TABLE work_order (
    id BIGSERIAL,
    tenant_id BIGINT NOT NULL,  -- 租户ID
    ...其他字段,
    PRIMARY KEY (tenant_id, id)
);

-- 查询时自动注入租户过滤
-- 通过 RLS (Row Level Security) 强制实施
ALTER TABLE work_order ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON work_order
    USING (tenant_id = current_setting('app.tenant_id')::BIGINT);
```

### 9.6 扩展性设计

| 扩展维度 | 当前 | 1年后 | 3年后 | 扩展方式 |
|:---------|:-----|:------|:------|:---------|
| **工单量** | 100单/天 | 500单/天 | 2,000单/天 | 读写分离 + 分表 |
| **用户数** | 50人 | 200人 | 500人 | 无状态水平扩展 |
| **设备数** | 1,000台 | 5,000台 | 20,000台 | 时序数据分区 |
| **AI 推理并发** | 10 QPS | 50 QPS | 200 QPS | GPU Pod 水平扩展 |

| **接入外部系统** | 3个 | 6个 | 15个 | 插件化连接器架构 |

**水平扩展关键设计**:

1. **无状态应用层**: 所有业务服务无状态，通过 K8s HPA 自动扩缩
2. **数据库读写分离**: 主库写 + 从库读，从库可水平扩展

4. **缓存策略**: Redis 缓存热点数据（工单状态/备件库存/工程师状态），缓存命中率目标 ≥85%
5. **定时任务分散**: 报表生成/数据同步等定时任务分散到不同时间窗口，避免同时触发

### 10.9 前端交互状态设计

每个页面需覆盖 4 种核心状态：加载态 / 空态 / 错误态 / 边界态。以下以关键页面为例。

**全局状态约定**:

```text
Loading: Skeleton 骨架屏 (非 Spin)，避免用户感知"白屏"
Empty: 插图 + 引导文案 + 推荐操作按钮
Error: 错误信息 + 重试按钮 + 容错降级说明
Edge: 数据截断 + "查看全部"链接 / 分页 / 查看更多
```

#### 10.9.1 工单列表页状态矩阵

| 状态 | 触发条件 | 展示效果 | 用户操作 |
|:-----|:---------|:---------|:---------|
| **加载中** | 页面初始加载 / 筛选切换 | 表格行 Skeleton 占位 (6行) | 无操作，自动完成 |
| **空态** | 该筛选条件下无工单 | 插图 + "暂无工单" + 建议: [清除筛选] [新建工单] | 点击清除筛选或新建 |
| **错误态** | 后端接口超时/500 | 顶部 Alert "数据加载失败" + 表格显示上次缓存数据 + [重试]按钮 | 点击重试或查看缓存 |
| **超长列表** | 结果 > 100 条 | 分页(20条/页) + "共 N 条"统计 | 翻页或使用筛选缩小范围 |
| **实时刷新** | 新工单创建/状态变更 | 顶部 Toast "有 N 条新工单" + [刷新]按钮 | 点击刷新或忽略 |
| **多选操作** | 勾选工单后操作 | 底部浮层 "已选 N 项" + [批量派工] [批量关闭] [导出] | 点击批量操作按钮 |

#### 10.9.2 工单详情页状态矩阵

| 区域 | 加载中 | AI 不可用 | 数据缺失 | 超时刷新 |
|:-----|:-------|:----------|:---------|:---------|

| **历史工单关联** | Skeleton 行 | — | "无关联历史工单" | 无 |

#### 10.9.5 前端性能指标

| 指标 | 目标 | 说明 |
|:-----|:-----|:------|

| 首次交互 (FID) | ≤100ms | 事件处理优化 |
| 累计布局偏移 (CLS) | ≤0.1 | 避免骨架屏→内容切换偏移 |

| 页面大小 | ≤500KB | 代码分割 + 按需加载 |
| API 请求并发 | ≤6 | 请求队列管理 + 防抖/节流

```text
### 7.5 派工模拟场景推演

> 以下推演展示 AI 派工系统如何处理一次典型的紧急工单调度。

**场景**: 07:45 收到客户A的紧急报修——XYZ-2000 伺服驱动故障，产线停机。

```

Step 1: 工单创建 (07:45)
  AI 自动提取: 客户A / XYZ-2000 / 伺服故障 / 紧急
  关联历史: 同型号昨日有2次同类故障 (与 WO889, WO890 关联)
  优先级: 紧急 (SLA: 响应≤15min / 解决≤4h)

Step 2: 候选工程师池 (07:45)
  +------+-------+------+----+------+------+------+
  | 姓名  | 技能% |距离km|负载|成功率|评分  | 在途 |
  +------+-------+------+----+------+------+------+
  | 王工  |  92%  |  5   |2/3 | 95%  | 4.8  | 否   |
  | 刘工  |  85%  |  12  |1/3 | 88%  | 4.5  | 是   |
  | 陈工  |  78%  |  8   |3/3 | 90%  | 4.6  | 否   |
  | 赵工  |  60%  |  3   |0/3 | 70%  | 4.1  | 否   | → 技能不匹配,过滤
  +------+-------+------+----+------+------+------+

Step 3: 评分计算 (07:45)
  权重: 技能(0.35) + 响应(0.25) + 负载(0.15) + 成功率(0.15) + 成本(0.10)
  紧急工单调权: 响应(0.40) + 技能(0.30) + 负载(0.10) + 成功率(0.15) + 成本(0.05)

  王工: 0.30×0.92 + 0.40×(1-12/60) + 0.10×(1-2/3) + 0.15×0.95 + 0.05×1.00
       = 0.276 + 0.320 + 0.033 + 0.143 + 0.050 = 0.822  ← 最优
  刘工: 0.30×0.85 + 0.40×(1-25/60) + 0.10×(1-1/3) + 0.15×0.88 + 0.05×0.85
       = 0.255 + 0.233 + 0.067 + 0.132 + 0.043 = 0.730
  陈工: 0.30×0.78 + 0.40×(1-18/60) + 0.10×(1-3/3) + 0.15×0.90 + 0.05×0.90
       = 0.234 + 0.280 + 0.000 + 0.135 + 0.045 = 0.694

Step 4: 派工决策 (07:45)
  → 推荐王工 (评分 0.822)
  → 推送工单至王工企业微信
  → 王工接单 (07:46) → 出发前往

Step 5: AI 预诊断 (07:46-07:48)
  → 分析故障代码 E-47 + 关联历史工单 WO889
  → 92% 置信度: IGBT 模块损坏
  → 推荐备件: P-1023 (伺服驱动模块)
  → 库存检查: 当前库存 0 ❌ → 触发紧急调拨

Step 6: 抵达现场 (08:11)
  → 王工使用 AI 诊断结果直接开始维修
  → 备件紧急调拨预计 24h 到货 → 王工先做临时修复(旁路)
  → 08:45 临时修复完成 → 产线恢复运行
  → 08:47 工单标记"临时修复"状态

Step 7: 二次上门 (次日 08:00)
  → 备件已到货
  → 王工上门更换 IGBT 模块
  → 08:45 维修完成 → 09:00 客户验收

节约时间对比:

- 传统方式: 08:30-10:00 诊断(1.5h) + 调度15min + 备件24h = 25h+ 停机
