## §0 执行摘要

**一句话判断：AI 协作系统的价值不产生于"产出了多少材料"，而产生于一条闭环——需求经过论证成为可工作方案（集成取舍）、方案由 AI 生产为材料（生产）、材料在决策点被人消费并下结论（决策）、矛盾被及时裁决并回写（治理）、以上全部由一套分工机制承载（机制）、按客观规律校准投入规模（投入）。任一环断链，系统整体价值归零；矛盾环断链，系统走向崩溃。** [来源: 本文命题链推导]

用户四条直觉重构为五个可验证命题：

| # | 命题 | 对应章节 | 结论 |
|:-:|:-----|:--------|:-----|
| P1 | 需求必须经过论证：整合组件点 → 系统级可工作 | §2 | 成立：需求 = 约束集，论证 = 在组件事实约束下的可行性证明；不可工作的需求是伪需求 |
| P2 | 不看材料、不在决策点下结论 → 内容价值为零 | §3 | 成立：内容价值 = 消费 × 决策 × 执行；不被消费的内容 V=0 |
| P3 | 矛盾不处理 → 越积越大 → 崩溃 | §4 | 成立：复杂度不治理必然增长（Lehman 第2定律），越过阈值即不可维护 |
| P4 | 管理原则二选一：一个人搞定 vs 运动员+裁判 | §5 | 成立但非二选一：本质是决策权配置，推荐三层裁判分层混合 |
| P5 | 投入要符合客观规律：别人投入多少，自己投入多少 | §6 | 成立：投入规模由产出目标 × 同行/历史基线校准；AI 改变产出率斜率，不改变规律本身 |

**五个核心洞见**：

1. **价值闭环断链定理**：闭环上每一环都是必要环节。生产环断了 → 没有材料；消费环断了 → 材料归零（P2）；治理环断了 → 矛盾积累崩溃（P3）。**AI 只优化生产环，不解决其他四环**——这是"再多内容有个毛用"的原理性解释。

2. **AI 杠杆率上限定理（§6.4）**：AI 能压缩的是生产时间，压缩不了决策时间与治理时间。系统总产出 = 决策吞吐 × 决策质量；AI 把"生产"从瓶颈中移除后，**决策与治理成为新的瓶颈**。投入规划必须按"生产:决策:治理"三账户分配，而非只算 AI 生产。

3. **矛盾是熵，治理是负熵输入（§4）**：Lehman 第2定律（复杂度增长）对文档系统同样成立 [来源: Lehman 1980, Proc. IEEE]。四轮巡检实证：裁决文档与目标文档回写率仅 ~52%，靠人工自觉复发率 100% [来源: 三层治理 C1-C32 分析 §2.1，2026-08-27]。**治理必须机制化，不能依赖意志。**

4. **裁判时间是最稀缺资源（§5）**：运动员+裁判机制的成本 = 裁判时间。破解之道是分层——自动化裁判（门禁脚本，低成本高频）承接 80% 裁决，用户裁判只裁决真决策点（呼应 O2 的 3+2 分类：80% 会议时间投给 3 个真待拍板项）[来源: 三层治理分析 §3.1]。这与 08-27「约束基础设施化」同构：**把裁判自动化，让人只当终审**。

5. **投入校准回答"值不值"（§6）**：不校准投入，就无法回答"这个系统到底值不值得"。"别人投入多少，自己计划投入多少"不是攀比，而是**用可观测基线锚定投入期望**，防止两类偏差——低估投入导致产出不达标，或高估投入导致沉没成本。

### 1.2 统一框架：价值闭环

五命题不是并列的，而是一条**因果链**（与 08-27 的「共识→约束→基础设施→产出」链互补——那条链讲**产出怎么变好**，这条链讲**产出如何变现**）：

```text
Requirement (P1)          Production             Consumption (P2)
  argumentation      ->    AI output       ->    human decision
  (integrate parts,        (cheap, bulk,        (expensive, scarce:
  tradeoff, prove          unlimited)           reading + concluding)
  workability)
       |                                              |
       v                                              v
  Governance (P3)  <--  Mechanism (P4)  <--  Investment (P5)
  conflict adjudication     who does what,           calibration vs
  + writeback loop          who judges whom          objective law
```

**闭环断链判据**（可直接用于系统体检）：

| 断链位置 | 症状 | 后果 |
|:---------|:-----|:-----|
| 需求环（P1） | 需求未论证即开工；组件点未集成；无取舍记录 | 返工/技术债/伪需求 |
| 生产环 | AI 不产出或产出质量低 | 无材料可消费 |
| 消费环（P2） | 材料堆积无人读；决策点无人拍板 | **全系统价值归零**（最常见断链点） |
| 治理环（P3） | 矛盾积压；裁决不回写 | 系统崩溃（最危险的断链点） |
| 机制环（P4） | 职责不清；运动员裁判同一人且无制衡 | 质量塌方或效率塌方 |
| 投入环（P5） | 投入与产出目标不匹配 | 期望落空/资源浪费 |

> **体检结论（本系统现状）**：生产环 ✅ 超载（每日 6-8 篇深度分析 + 4 组日报）；消费环 ⚠️ 用户决策时间不足（E1-E20 待决策清单积压 [来源: 08-27 超节点扩展待决策清单]）；治理环 ⚠️ 已启动但回写率 52%（08-28 审计发现 13 项残留）[来源: 08-28 一致性审计]。**瓶颈不在生产，在消费与治理。**

## §2 需求论证：组件→系统的集成与取舍

### 2.1 需求的第一性原理：需求 = 在组件约束下可工作的系统描述

需求的经典定义是"用户要什么"，但第一性原理看，**需求是"系统在组件约束下可工作的完整描述"**：

```text
Requirement R = { Goals G (what the system must achieve)
                + Component set C (available parts: modules, docs, standards, chips)
                + Constraints K (physics, cost, schedule, compat)
                + Interface contracts I (how C parts connect, data/control semantics)
                | such that the composed system S(C, I) is provably workable }
```

- **Goals G**：要达成什么（如"13 柜超节点可训练 671B 模型"）。
- **Component set C**：已有各组件的"点"（技术方案、知识库文档、既有裁决、硬件模块）。
- **Constraints K**：物理/经济/时间/兼容性边界。
- **Interface contracts I**：组件之间如何对接——这正是 C1-C32 裁决的产物（编址公式、Rail 语义、PXE 链路承载）[来源: 三层治理 C1-C32 分析]。

**"需求不是白来的"的含义**：需求不能凭空生成，它的**可行性上限由 (C, K, I) 决定**。一个需求若无法用现有组件 + 可行接口组装出来，它就不是"需求"，而是"愿望"。

### 2.2 论证 = 集成可行性证明

论证不是"写一段需求文档"，而是完成三件事：

| 论证步骤 | 产出物 | 判据 |
|:---------|:-------|:-----|
| ① 组件盘点 | 组件能力清单（每个组件的边界、规格、已知限制） | 每个组件点有出处、有版本 |
| ② 集成设计 | 接口契约集 I（组件间连接方式、口径、语义） | 无遗漏接口；口径唯一（SSOT） |
| ③ 可行性证明 | 组装验证（数学/仿真/评审：组装后的系统满足 G 且不违反 K） | 关键量化参数闭环；矛盾清零 |

**关键认知**：**集成设计（②）是论证的主战场**。组件单个看都对，组合起来矛盾百出——这正是 C1-C32 的教训：32 项矛盾分布在 6 个域，全部是"组件点各自正确、接口口径冲突"（编址公式新旧代际、Rail 语义代际反转、功耗口径三层分离）[来源: 三层治理分析 §2.1]。**论证的本质工作 = 接口仲裁。**

### 2.3 取舍的数学本质：缺口三角

集成时必然遇到需求集合 R 与组件能力集 C 的映射缺口。设缺口 Δ = R − C（无法由现有组件直接满足的需求部分），取舍只有三条路：

```text
        R (requirements)
       /|\
      / | \  gap Delta = R - C
     /  |  \
    C (component capability)
```

| 取舍方向 | 操作 | 代价 | 适用场景 |
|:---------|:-----|:-----|:---------|
| 缩 R | 砍需求/降指标/分期 | 功能或性能损失 | 组件约束刚性（物理/成本） |
| 扩 C | 新开发/改组件/引入新组件 | 时间与成本 | 缺口小且时间充裕 |
| 改 I | 换集成方案（接口重组） | 集成复杂度 | 缺口集中在接口而非能力 |

**取舍决策的量化形式**：对每个缺口 Δᵢ，比较三方案的 (代价, 风险, 时间)，选择满足 K 约束的最小总代价组合。**没有取舍记录的需求论证 = 没有论证**——因为"全要"在物理/经济上不存在。

### 2.4 反例：未论证需求的失败模式

| 失败模式 | 表现 | 根因 |
|:---------|:-----|:-----|
| 伪需求 | 需求在组件约束下不可工作，仍被立项 | 未做可行性证明（缺②③） |
| 组件幻觉 | 方案引用了不存在/已废弃的组件能力 | 未做组件盘点（缺①） |
| 口径漂移 | 同一系统不同文档口径不一（77kW vs 82.6kW） | 未做接口契约仲裁（缺②） |
| 全要陷阱 | 无取舍，所有缺口都扩 C | 未做缺口三角分析 |
| 论证瘫痪 | 论证永不收敛，反复评审不拍板 | 论证无截止判据（见 §7） |

## §3 决策纪律：内容的价值函数

### 3.1 内容价值公式：V = 消费 × 决策 × 执行

**核心命题：AI 产出内容的价值函数是**

```text
V(content) = Consumed × Decided × Executed
```

- **Consumed** ∈ {0,1}：是否被决策者阅读/消费。未消费 → V=0。
- **Decided** ∈ {0,1}：消费后是否在决策点下结论。只看不决 → 对系统无增益。
- **Executed** ∈ {0,1}：结论是否回写为系统的确定性状态（文档/配置/代码）。只决不写 → 决策在下次对话蒸发。

三者连乘意味着：**任何一环为 0，内容价值为 0**。这解释了用户的直觉——"不花时间看 AI 输出的材料，不进行决策点下结论，再多内容有个毛用"：AI 生产环超载（Consumed 环节瓶颈），材料堆积而价值恒为 0。

### 3.2 材料 ≠ 成果：决策支持资产的性质

AI 输出的本质是**决策支持资产（decision-support asset）**，不是**成果（deliverable）**：

| 维度 | 材料（asset） | 成果（deliverable） |
|:-----|:-------------|:-------------------|
| 价值状态 | 潜在价值（待兑换） | 已实现价值（可消费） |
| 兑换条件 | 必须经过人消费+决策 | 可直接用于下游 |
| 生产方 | AI 可批量生产 | 只能由"消费+决策"产生 |
| 可替代性 | 高（可再生成） | 低（含决策权投入） |

**推论**：把"AI 产出了多少材料"当作系统 KPI，是**指标错位**——它衡量的是生产环流量，而价值在消费环兑现。正确的 KPI 是：**决策点关闭数、回写执行率、矛盾存量**（见 §8）。

### 3.3 决策点识别与下结论的量化方法

**决策点 = 材料中每个"待定/建议/可选/权衡/需确认"的语义单元**。材料生产时应在交付物中显式登记决策点清单（呼应 ADR 模式与决策登记表机制 [来源: 三层治理 O5 / 08-28 项目文件夹分析]）：

| 字段 | 内容 | 示例 |
|:-----|:-----|:-----|
| D-编号 | 唯一标识 | D1（BF3 冗余 2 卡 vs 1 卡） |
| 决策内容 | 是什么选择 | BF3 数量与冗余级别 |
| 依赖 | 依赖哪些前置决策 | D1 → D3（功耗基线） |
| 建议 | 材料方倾向 + 依据 | 建议 2 张（卡级+TOR 级冗余） |
| 代价 | 各选项的代价/风险 | 2 张：+成本与功耗 |
| 状态 | 提议/已采纳/已取代/已否决 | 提议 |

**"下结论"的量化标准（ADR 三件套）**：
1. **选择**：明确选了 A 还是 B（不写"待定"）。
2. **依据**：一条可追溯的理由（数据/约束/经验）。
3. **回退条件**：什么情况下推翻此结论（决策的可逆性声明）。

**决策质量 vs 决策速度的平衡**：不是每个决策点都要同等深度的论证。按重要度分级——关键决策（影响系统级能力/成本/安全）走完整 ADR；常规决策（口径确认）走快速确认（呼应 O2：真待拍板 vs 已定案待确认的 3+2 分类 [来源: 三层治理 §3.1]）。

### 3.4 决策积压的代价

决策点不关闭，代价随时间超线性增长：

| 代价类型 | 机制 | 参照 |
|:---------|:-----|:-----|
| 上下文折旧 | 决策所需上下文随时间丢失，重读成本↑ | org-churn 三重折旧模型（决策上下文折旧）[来源: 08-27 org-churn 分析] |
| 期权衰减 | 未决选项随时间失效（硬件交期/窗口期） | 期权时间价值衰减 |
| 连锁阻塞 | 上游未决阻塞下游决策（D1 → D3 依赖链） | 三层治理 O3 依赖拓扑 |
| 矛盾沉淀 | 未决项被后续文档当作"已定"引用，产生新矛盾 | Lehman 第2定律（§4） |

**决策积压率 = 系统健康度的先行指标**：当"新决策点产生速率 > 决策点关闭速率"时，系统必然走向崩溃（与 §4 矛盾积累同构）。

## §4 矛盾治理：不处理的动力学

### 4.1 矛盾的定义与产生机制

**矛盾 = 系统中两个以上组件/文档对同一事实给出了不一致的确定性状态**（口径、数值、语义、版本）。产生机制：

| 机制 | 示例 |
|:-----|:-----|
| 快照漂移 | 文档是"创建时刻的口径快照"，拍板在评审会，更新在会后，两者无强制闭环 → 文档间口径分叉 [来源: 三层治理 §2.2 根因分析] |
| 代际迁移 | 新裁决取代旧口径，旧口径文档未标记"被取代"（Rail 语义代际反转、CX8 残留）[来源: 08-28 一致性审计] |
| 参考混入 | 参考平台口径（dayu-klx）混入项目对象表 [来源: 三层治理 §2.2] |
| 状态脱节 | 声明（changelog 声称归一）与正文（残留旧值）不一致 [来源: 08-26 上电模型 G6 矛盾分析] |
| 错误一致性传播 | 新文档建立在对旧矛盾的引用之上，矛盾随引用扩散 | — |

### 4.2 不治理的动力学：超线性积累

**Lehman 第2定律（复杂度增长定律）：E-type 系统必须持续演化，其结构复杂度随时间增长，除非进行主动的维护/治理工作** [来源: Lehman, M.M., "Programs, Life Cycles, and Laws of Software Evolution", Proc. IEEE 68(9), 1980, 公开学术经典]。

对文档/方案系统，机制是**双重复利**：

```text
dN/dt = alpha * N(t) + beta * P(t)
   N(t): contradiction stock (accumulated unresolved conflicts)
   P(t): production rate (new docs/decisions per unit time)
   alpha: self-reinforcement rate (new docs built on old contradictions)
   beta: contamination rate (each new doc has some chance to clash with stock)
```

- 第一项 α·N：**存量矛盾自我增殖**——新文档引用旧矛盾口径 → 旧矛盾扩散到更多文档。
- 第二项 β·P：**生产速度决定新矛盾注入率**——AI 生产越快（P 大），注入的矛盾越多（这是 AI 时代的**新增治理负担**，也是"生产超载"的另一面）。
- 结论：**不治理，矛盾存量指数增长；治理速率必须 ≥ 注入速率 + 增殖速率**，否则崩溃只是时间问题。

### 4.3 崩溃路径

```text
N(t) grows -> every new decision must first arbitrate conflicts
           -> decision cost per item increases
           -> decision throughput drops
           -> decision backlog grows (P3 violation)
           -> more decisions made on stale baseline
           -> new contradictions injected (faster than resolved)
           -> N(t) accelerates -> system unmaintainable -> CRASH
```

崩溃不是突然的，而是**决策成本越过可用时间预算**的瞬间——当"仲裁存量矛盾"的成本超过决策者的时间预算时，决策者放弃仲裁直接拍板，矛盾进一步固化，系统进入不可维护状态。

### 4.4 治理的量化：频率、成本、时机

| 参数 | 规律 | 实证 |
|:-----|:-----|:-----|
| 治理时机 | 矛盾裁决越晚，回写成本越高（上下文折旧+连锁阻塞） | C17-C20 裁决后回写清单 12 处未执行 [来源: 三层治理 §2.1] |
| 治理频率 | 必须 ≥ 注入频率；周期巡检（日/周）优于事后清理 | 08-28 近 3 日审计发现 13 项残留（3 天已积累）[来源: 08-28 一致性审计] |
| 治理机制 | 靠人工自觉复发率 100% → 必须机制化（门禁/登记表/状态机） | 四轮巡检根因同构 [来源: 三层治理 §2.2] |
| 治理闭环 | 裁决 → 回写 → 验证（门禁清零）三缺一不算完成 | 回写执行率 ~52% 即半闭环 [来源: 三层治理 §2.1] |

**治理的成本结构**：治理 = 固定成本（机制建设，一次性）+ 可变成本（每次裁决+回写+验证）。固定成本摊薄到 N 次矛盾裁决，N 越大越划算——与 08-27「约束基础设施化」的固定/可变成本结构完全同构 [来源: 08-27 投入杠杆分析 §2.3]。**治理不是成本，是负熵输入，是让"生产环"产出不归零的保险。**

## §5 机制设计：一个人搞定 vs 运动员+裁判

### 5.1 两种模式的本质：决策权配置

"一个人搞定"与"运动员+裁判"不是工作量分配问题，而是**决策权配置**问题（沿用 org-churn 分析的第一性原理：组织 = 决策权分配 + 信息流路由 + 责任结构 [来源: Mintzberg 1983, 公开学术知识]）：

| 维度 | 一个人搞定（集中决策） | 运动员+裁判（分离决策） |
|:-----|:----------------------|:------------------------|
| 决策权 | 单点拥有 | 运动员生产、裁判裁决，权责分离 |
| 决策速度 | 快（无协调） | 慢（有传递+裁决延迟） |
| 决策质量 | 依赖单点能力，无制衡 | 有制衡，多视角 |
| 规模上限 | 低（单人吞吐有限） | 高（可并行扩展） |
| 制衡机制 | 无（自己裁决自己） | 有（裁判否决权） |
| 信任成本 | 低（自己信自己） | 高（裁判需投入时间理解） |
| 风险模式 | 单点失败=全盘失败；认知盲区无兜底 | 运动员偏误被裁判拦截，但裁判偏误无人拦 |

### 5.2 AI 语境下的角色映射

在 AI 协作系统中，角色有四种，可自由组合：

| 角色 | 职责 | 可选承担者 |
|:-----|:-----|:-----------|
| 运动员 | 生产材料/方案/代码 | AI（主力）、用户 |
| 裁判-自动化 | 规则化裁决（格式/门禁/一致性扫描） | 脚本、门禁、harness |
| 裁判-人工 | 决策点裁决（下结论） | 用户（主力） |
| 评审-外部 | 里程碑级把关（方案/架构/发布） | 专家、同行、委员会 |

映射到两种模式：

- **一个人搞定模式**：用户既是运动员又是裁判（AI 仅当工具）。适用：吞吐小、决策快、质量要求中等、制衡需求低。
- **运动员+裁判模式**：AI 当运动员，自动化门禁当第一裁判，用户当终审裁判。适用：吞吐大、质量要求高、需要制衡。

**关键权衡**：用户问"一个人搞定，还是运动员+裁判"的真正答案不是二选一，而是**按任务维度分层**——高频规则性裁决交给自动化裁判（零用户时间），中频决策点交给用户裁判，低频关键节点交给外部评审。

### 5.3 选择判据

| 判据 | 倾向于一个人 | 倾向于运动员+裁判 |
|:-----|:-------------|:------------------|
| 决策吞吐需求 | 低（<10 决策点/天） | 高（>50 决策点/天） |
| 决策质量要求 | 中 | 高（系统级/安全级） |
| 制衡需求 | 低 | 高（利益分离、防自欺） |
| 裁判时间预算 | — | 必须有（否则裁判形同虚设） |
| 错误代价 | 低（可逆） | 高（不可逆/连锁） |

**配套铁律**：选运动员+裁判，**必须给裁判配时间预算**——否则"裁判"形同虚设，机制退化为"运动员自娱自乐"，比一个人搞定更糟（多一层协调成本，无对应收益）。这正是 P2 的现实约束：**裁判时间 = 系统价值的物理上限**。

### 5.4 推荐：三层裁判分层

结合本系统实证（约束基础设施化 08-27 + 三层治理 08-27 + 门禁脚本体系），推荐：

```text
Layer 1  Automated judge (scripts, gates, scanners)   -- cost: ~0 user time
         catches: format errors, dead links, consistency violations,
         CI-style checks. Executes every commit / every doc.
             |
Layer 2  Human judge (user)                            -- cost: scarce, budgeted
         catches: decision points only (D-xxx list),
         tradeoff calls, direction setting.
             |
Layer 3  External review (expert / committee / peer)   -- cost: expensive, rare
         catches: architecture soundness, milestone gates,
         once per milestone.
```

**分层收益**：L1 拦截 80% 低层问题（自动裁判覆盖高频规则）；L2 只裁决真决策点（用户时间聚焦高杠杆）；L3 把关里程碑（外部视角防盲区）。三层合计 = "一个人搞定"的 1/N 时间成本 + "运动员+裁判"的质量保障。

## §6 投入规律：别人投入多少，自己投入多少

### 6.1 投入产出曲线的形状

投入产出遵循三条客观规律：

1. **规模门槛**：低于门槛投入产出≈0（材料不构成可工作系统）；超过门槛才有系统级产出。典型：一个超节点系统方案，低于"组件盘点+接口仲裁"的最低工作量，产出的只是"名词堆叠"。
2. **边际递减**：超过某点后，追加投入的边际产出递减（Brooks 定律的投入侧表述：追加资源到已超载系统反而降低产出 [来源: Brooks, "The Mythical Man-Month", 1975, 公开学术经典]）。
3. **瓶颈定律**：系统总产出 = 瓶颈环节吞吐。生产环节由 AI 承接后，瓶颈转移到决策与治理（§3/§4）——**投入若不投在瓶颈上，等于没投**。

### 6.2 校准方法：三把尺子

"别人投入多少，自己计划投入多少"的实操化 = 三把尺子交叉校准：

| 尺子 | 方法 | 示例 |
|:-----|:-----|:-----|
| ① 同行对标 | 同类任务，别人（团队/公司/开源项目）投入多少人月 | 超节点项目对标 GB200 NVL72 研发投入规模 |
| ② 复杂度估计 | 任务分解为子任务，按复杂度估算每项工时 | 组件盘点 ×N + 接口仲裁 ×M + 验证 ×K |
| ③ 历史基线 | 自己过去同类任务的实测消耗（实际人天/实际产出） | 本轮 C1-C32 裁决的实际耗时 → 外推 |

**校准产出 = 投入预算区间 [下限, 上限]**：
- 下限：能产出"可工作系统"的最小投入（规模门槛）。
- 上限：产出目标对应的合理投入（同行对标 × 自身效率系数）。
- **投入计划落在区间内 = 符合客观规律；低于下限 = 期望落空；高于上限 = 沉没成本。**

### 6.3 AI 改变斜率，不改变规律

| 环节 | 无 AI 的投入占比 | 有 AI 的投入占比 | AI 改变什么 |
|:-----|:----------------:|:----------------:|:------------|
| 生产（材料） | ~60% | ~20% | 斜率 ↑（产出率×10-50） |
| 决策（消费） | ~20% | ~40% | **不变**（人的阅读+拍板不可压缩） |
| 治理（闭环） | ~20% | ~40% | **不降反升**（生产变快 → 矛盾注入变快 §4.2） |

**关键**：AI 把生产投入压缩后，**省下的时间必须重新分配到决策与治理**，否则就是"生产 10 倍速、消费 0 倍速"——价值归零（§3）。投入规划不是"总投入减少"，而是**投入结构迁移：生产 ↓、决策 ↑、治理 ↑**。

### 6.4 杠杆率定理：AI 的上限 = 决策时间的上限

**定理：AI 协作系统的总价值 = 决策吞吐 × 决策质量 × 执行闭环率。AI 只放大生产环节；系统杠杆率的上限由决策者能投入的时间决定。**

推论：
1. 决策时间预算 T 固定 → 系统总价值有硬上限，与 AI 生产量无关。
2. 增加价值的两条路：**提高决策吞吐**（决策点分级、快速确认、自动化预判——呼应 3+2 分类）或 **提高决策质量**（决策依据标准化、外部评审）。
3. **"再多内容有个毛用"的完整表述**：当决策吞吐固定时，内容量 V 与系统价值无关——内容量不是自变量，决策量才是。

## §7 边界与反噬（极端挑剔审查）

| 反噬模式 | 机制 | 防御 |
|:---------|:-----|:-----|
| 论证过度（分析瘫痪） | 需求论证永不收敛，评审会开不完 | 论证设截止判据：组件盘点完成 + 接口仲裁闭环 + 关键量化参数对齐，三者齐即止 |
| 决策过度（决策疲劳） | 每个决策点都走完整 ADR，系统2 资源耗尽 [来源: Kahneman 双系统理论, 2011, 公开学术经典] | 分级：关键决策全流程，常规决策快速确认 |
| 治理过度（官僚化） | 为治理而治理，门禁本身成为熵源 | 治理产出与"矛盾存量/回写率"挂钩，不搞仪式性检查 |
| 机制僵化 | 运动员+裁判变成甩锅结构（运动员不负责质量，裁判不负责进度） | 责任不可分割：运动员对产出负责、裁判对结论负责、共同对系统负责 |
| 裁判虚设 | 机制上设了裁判，时间上没配预算 | 裁判时间预算是机制的硬前提（§5.3） |
| 投入误校准 | 同行对标被"别人投入很多"吓退，或"别人没投入"误导 | 对标的是**产出目标**而非别人的投入数字——投入是产出目标的反函数 |

**总边界**：本框架适用于**长期运营的系统**（知识库/项目/产品线）。一次性任务（单次问答、临时输出）不值得投入论证/治理/机制成本——这正是 08-27「低频场景 harness 化 → 沉没成本」的反噬边界在管理层的延伸 [来源: 08-27 投入杠杆分析 §6.3]。

## §8 落地清单（可直接执行）

**A. 需求论证（P1）**
- [ ] 新需求立项必须附带三件套：组件盘点表 / 接口契约集 / 集成可行性证明
- [ ] 每个缺口 Δᵢ 显式记录取舍决策（缩 R / 扩 C / 改 I）及依据
- [ ] 论证截止判据写入需求文档（§7 防御分析瘫痪）

**B. 决策纪律（P2）**
- [ ] 每次 AI 材料交付同时登记决策点清单（D-编号 + 建议 + 代价 + 依赖 + 状态）
- [ ] 决策点分级：关键决策（完整 ADR）/ 常规决策（快速确认）
- [ ] 每日检查"决策点关闭率"，关闭率 < 新产生率 → 触发降产（暂停新生产，先清积压）
- [ ] 决策采用 ADR 三件套：选择 + 依据 + 回退条件

**C. 矛盾治理（P3）**
- [ ] 每周一次一致性审计（对照 SSOT 基线登记表），输出矛盾存量报告
- [ ] 裁决 → 回写 → 门禁验证三闭环，回写率 <90% 即触发治理告警
- [ ] 治理频率 ≥ 注入频率：生产提速时同步提高审计频率（§4.2 双重复利）

**D. 机制设计（P4）**
- [ ] 三层裁判分层落地：L1 自动化门禁（脚本/扫描）→ L2 用户决策点 → L3 里程碑外部评审
- [ ] 用户裁判时间预算显式化（每周 X 小时，与生产量挂钩）
- [ ] 角色与责任写清：运动员对产出负责、裁判对结论负责

**E. 投入校准（P5）**
- [ ] 每季度用三把尺子（同行对标/复杂度估计/历史基线）校准投入预算区间
- [ ] 投入结构按"生产:决策:治理"三账户分配，AI 压缩生产后，把时间再分配到决策与治理（§6.3）
- [ ] 系统 KPI 从"产出量"切换为：决策点关闭数 / 回写执行率 / 矛盾存量（§3.2 指标错位纠正）
