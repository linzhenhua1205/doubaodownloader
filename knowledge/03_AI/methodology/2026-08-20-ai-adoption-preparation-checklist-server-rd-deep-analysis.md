## 1. 执行摘要

**一句话结论**: AI 导入研发工作是**系统工程而非工具采购**——必须按「环境 → 成本 → 工具 → 安全 → 对接」五支柱 + 「技术/组织」双维度做前置排查，缺一不可；其中**信息安全管控与 Token 成本治理是最容易被低估、且最晚补救代价最高的两项**。

**五大关键结论**:

| # | 支柱 | 核心结论 | 最常踩的坑 |
|:-:|:-----|:---------|:----------|
| 1 | 环境 | 网络隔离与数据路由是**第一决策**——先定"哪些数据能出网、哪些必须本地"，再选部署形态 | 直接全员开放外网 API，机密数据外泄 |
| 2 | 成本 | Token 成本是**架构纪律而非定价问题**——90%+ 输入 token 由架构决策决定；缓存/修剪/路由/压缩/门控五杠杆可叠加削减 | 无预算帽、无门控，Agent 失控循环烧钱 [来源: 知识库 token 优化五技术 v1.0] |
| 3 | 工具 | 按研发价值链分层选型，**防 star 通胀三重校验**（活跃度+描述+内容）；服务器研发有专用工具缺口（SI/固件/测试） | 追逐热门工具，忽略与现有工具链（PLM/配置器/BOM/CI）对接 |
| 4 | 安全 | 安全是**准入条件不是加分项**——数据分级路由 + DLP + 审计 + 制度四件套；行业已进入"企业管控期"（Cursor 封禁为标志事件） | 先跑业务后补安全，事故后一刀切封禁 |
| 5 | 对接 | 对接决定**落地深度**——AI 需嵌入 IPD 流程/工具链/组织三张网，否则沦为个人玩具 | 只买工具不改流程，AI 产出无法沉淀复用 |

**三阶段路线图**（详见第 9 章）: 试点期（1-3 月，环境+安全基线+单点验证）→ 扩展期（3-6 月，工具链打通+治理上线+成本监控）→ 规模化期（6-12 月，全流程嵌入+度量闭环）。

## 2. 总览框架：五支柱模型

### 2.1 MECE 划分依据

AI 导入研发工作，全量准备事项可按「**什么跑、花多少、用什么、安全否、接得上吗**」五个互斥且穷尽的问题划分：

```
Q -> Pillar       Tech layer                     Org layer
------------------------------------------------------------------
run?     -> 1 Env   network/compute/data/account   procurement/vendor
cost?    -> 2 Token billing/estimation/optimize    budget/quota/chargeback
tool?    -> 3 Tool  taxonomy/selection/gap         skill-base/champion
leak?    -> 4 Sec   classification/DLP/audit/priv  policy/approval/NDA
integ?   -> 5 Int   process/toolchain/datasource    org/vendor/customer
------------------------------------------------------------------
crosscut -> 6 Gov   metrics/monitoring             role/culture/roadmap
```

### 2.2 核心模型：AI 落地的投入产出函数

借鉴知识库既有框架 [来源: 知识库 2026-08-05 AI 产出经济学 毛利vs净利]:

```
NET_OUTPUT = GROSS_OUTPUT (AI-generated docs/code/analysis/plans)
           - LOSSES (drift-fix + entropy-mgmt + rework + security-incidents)
           - FIXED_COST (env + tools + token + governance)
```

- **毛利 vs 净利**: AI 产出是毛利，漂移与熵是损耗项——**治理的本质是把显性熵转成确定性约束** [来源: 知识库 gross-vs-net v1.0]
- **投入红线**: 知识库建设/AI 探索类投入 ≤40% 总投入（用户 08-14 决策），业务主线 ≥60% [来源: 用户决策 2026-08-14]
- **拐点判断**: 当治理成本增速 > 产出增速，工具从"兑现"转向"自我吞噬"，需重新评估 [来源: 知识库 gross-vs-net v1.0]

## 3. 环境问题（技术层 · 支柱一）

> **第一性原理**: 环境就绪度决定 AI 能"以什么形态、在多大数据范围内"运行。服务器研发普遍处于**隔离研发网 + 高机密数据 + 多工具链**环境，环境决策顺序应为：**数据分级 → 网络通道 → 部署形态 → 算力 → 账号/集成**。

### 3.1 网络与访问环境

| 排查项 | 关键问题 | 决策要点 |
|:-------|:---------|:---------|
| **网络隔离现状** | 研发网是否与互联网物理/逻辑隔离？是否有 DMZ？ | 隔离网需审批开通出口，走**白名单+审计代理**，禁止直连 |
| **出口通道** | 是否允许 HTTPS 出网到 AI 服务商？延迟/稳定性如何？ | 优先国内可达端点；云 API 需评估跨境链路质量 |
| **部署形态选型** | 云 API / 私有化部署 / 本地小模型 / 混合 | 决策树：数据密级 → 并发规模 → 预算 → 运维能力 |
| **代理与认证** | 是否需要统一代理、SSO 认证、IP 白名单？ | 统一入口便于审计与配额，避免个人账号满天飞 |

**部署形态决策树**（服务器研发场景）:

```
data secrecy level?
 |- TOP-SECRET (unreleased product/core algo/custom) -> local model or private deploy (never egress)
 |- CONFIDENTIAL (internal arch/competitive/BOM)     -> private deploy or controlled cloud API (after masking)
 +- INTERNAL (general knowledge/public docs/code)    -> cloud API (enterprise account + audit)
                    |
                    v
concurrency? budget? ops capacity? -> decide local compute spec or cloud plan
```

### 3.2 算力环境（本地推理）

| 方案 | 适用 | 成本量级 | 说明 |
|:-----|:-----|:---------|:-----|
| **消费级 GPU 本地跑小模型** | 个人/小组试点 | 数千元（一次性） | 已验证可行：RTX 5060 8G 跑 7B INT4 [来源: 用户 08-14 决策] |
| **企业自有 AI 服务器** | 团队级推理 | 中（复用现有产品线） | 服务器厂商自产自用——用自家 8 卡机部署 vLLM 跑开源模型 |
| **私有化集群（多卡）** | 部门级 | 高 | 需配套推理栈运维（vLLM/Ollama/KServe） |
| **云 API** | 全员轻量使用 | 按量付费 | 最低前期投入，但受网络/安全约束 |

**关键提醒**: 本地 7B INT4 与云端旗舰模型的能力差距是**数量级**的（代码生成/深度分析场景尤为明显）。合理策略是**分级路由**——简单任务本地小模型（省钱），复杂任务云端大模型（保质量），机密任务私有化。

### 3.3 数据环境

| 排查项 | 关键问题 |
|:-------|:---------|
| **知识库接入** | 企业文档/知识库（研发规范、案例库、竞品库）能否被 AI 检索？格式兼容性？ |
| **代码库接入** | 代码托管（GitLab/私有仓库）能否被 AI 索引？权限模型是否同步？ |
| **数据预处理** | 非结构化数据（PDF/图纸/PPT）是否需要解析管线（markitdown 等）？ |
| **数据新鲜度** | 知识库更新机制（每日归档/周报）是否已建立？陈旧数据会污染 AI 输出 |

### 3.4 账号与权限环境

- 企业级统一账号（SSO/Okta/企业微信/飞书），**禁止个人邮箱注册**
- 权限分级：普通成员/项目管理员/审计员——与数据分级对应
- 计费归口：按部门/项目成本中心挂账，为成本分摊打基础

### 3.5 组织层环境准备

| 事项 | 内容 |
|:-----|:-----|
| **采购流程** | 云服务/工具的采购审批链、合同评审（含数据处理条款） |
| **供应商准入** | 三重校验（活跃度+描述+内容），防 star 通胀 [来源: MEMORY.md 开源选型] |
| **IT 协同** | 与 IT 部门确认网络开通/代理/账号生命周期管理责任界面 |
| **试点授权** | 明确试点团队、试点范围（哪些项目可用）、试点期（1-3 月） |

## 4. Token 消耗问题（成本层 · 支柱二）

> **第一性原理**: Token 账单 = Σ(输入 token × 输入价 + 输出 token × 输出价)，而**输入 token 的 90%+ 是架构决策决定的**——发了什么、发了多少、发给谁、何时发——不是模型单价决定的。"成本治理是架构纪律" [来源: 知识库 token 优化五技术 v1.0]

### 4.1 计费模型与实测基线

| 计费因子 | 说明 | 实测/已知数据 |
|:---------|:-----|:--------------|
| **输入 token** | 系统提示词+上下文+工具输出回传 | 占账单大头，缓存未命中是最大成本 [来源: 08-15 实测缓存未命中 57.1%] |
| **输出 token** | 模型生成内容 | 单价通常 2-3 倍于输入 |
| **缓存命中** | 命中缓存输入大幅降价 | 缓存未命中 = 重复付费，是优化第一抓手 |
| **价格波动** | 供应商调价 | 2026-08-17 峰谷新价生效：同用量成本 +186%（flash miss 输入 1→1.5/3.0、输出 2→4.5/9.0；pro 输出 6→13.5/27.0）[来源: MEMORY.md 08-17] |

**关键教训**: 价格变动可让同用量成本翻倍以上——**预算治理必须按"用量"而非"金额"设基线**，且预留价格波动缓冲。

### 4.2 用量预估方法（按角色×任务）

| 任务类型 | 典型单次消耗（估） | 频度 | 月用量（估） |
|:---------|:------------------|:-----|:-------------|
| AI 编程（代码生成/审查） | 5-50K token/任务 | 高频（每日） | 大 |
| 深度分析/方案写作 | 30-100K token/次 | 中频（每周） | 中 |
| 文档翻译/润色 | 2-10K token/次 | 高频 | 中 |
| 信息检索/总结 | 1-5K token/次 | 高频 | 小-中 |
| 知识库沉淀/归档 | 5-20K token/次 | 中频 | 小 |

> 估算方法：**先跑 2 周试点实测，建立"单位任务 token 基线"，再外推全员用量**——不要拍脑袋定预算 [来源: 知识库 token-per-turn 审计方法]

### 4.3 五大优化杠杆（ROI 排序）

| 杠杆 | 削减幅度 | 工程成本 | 落地动作 | 落地顺序 |
|:-----|:--------:|:--------:|:---------|:--------:|
| **T1 Prompt 缓存** | -90% | 低 | 稳定 system prompt、前缀复用 [来源: Andela 框架] | ① |
| **T2 工具输出修剪** | -70~90% | 低-中 | 只回传必要字段、截断日志 [来源: Andela 框架] | ② |
| **T3 意图路由** | -50~80% | 中 | 简单任务走小模型、复杂任务走大模型 [来源: Andela 框架] | ③ |
| **T4 上下文压缩** | -30~60% | 中-高 | 摘要注入、历史裁剪（已有实证：压缩后上下文 -85% 场景）[来源: 08-17 事故复盘] | ④ |
| **T5 成本门控** | 防失控 | 中 | 执行前预算检查、循环上限、熔断 [来源: Andela cost gates] | 贯穿 |

> **门控是治理的元层**: 前四技术是"减量"，门控是"边界"——没有门控，减量技术只是让失控更慢一点。post-hoc 报告是 observability，pre-execution 门控才是 governance [来源: 知识库 token 优化五技术 v1.0]

### 4.4 监控与度量

| 监控项 | 指标 | 告警阈值建议 |
|:-------|:-----|:-------------|
| 日/月消耗 | token 总量、金额 | 超预算 80% 预警、100% 熔断 |
| 单任务成本 | token/任务 | 超基线 3 倍告警（疑失控循环） |
| 缓存命中率 | 命中/总输入 | 低于 40% 提示架构问题 |
| 单价漂移 | 实际单价 vs 预算单价 | 供应商调价即重算预算 |

### 4.5 组织层成本治理

| 机制 | 内容 |
|:-----|:-----|
| **预算帽** | 部门/项目月度 token 预算，硬上限 |
| **配额** | 按角色分级配额（工程师 > 管理者 > 试用） |
| **审批流** | 超配额申请、大任务（深度分析/批量任务）审批 |
| **成本分摊** | 按项目成本中心挂账，让项目负责人看到 AI 成本 |
| **ROI 复盘** | 月度：AI 产出毛利 vs 成本 vs 治理损耗（净利视角）[来源: 知识库 gross-vs-net] |
| **红线管理** | AI 探索/知识库建设投入 ≤40% 总投入 [来源: 用户 08-14 决策] |

## 5. 工具需求（工具层 · 支柱三）

### 5.1 服务器研发价值链 × 工具全景

按研发价值链（需求→设计→实现→验证→量产→运维）映射 AI 工具需求：

| 价值链环节 | AI 工具类型 | 代表形态 | 服务器研发典型任务 |
|:-----------|:------------|:---------|:-------------------|
| **需求/方案** | 文档助手、调研助手 | 对话式/知识库 RAG | 竞品分析、规格书起草、行业调研（已有成熟实践） |
| **设计** | 设计辅助、SI 分析辅助 | 插件/脚本 | 原理图审查、SI/PI 仿真参数建议、散热方案比对 |
| **开发** | AI 编程（IDE/CLI Agent） | Cursor 类 / Claude Code 类 | BMC 固件、BIOS、测试脚本、工具链开发 |
| **验证/测试** | 测试自动化助手 | 脚本生成/用例生成 | 测试用例生成、日志分析、故障诊断（FTA） |
| **文档/知识** | 知识库助手 | RAG + 知识库 | 研发规范沉淀、经验归档、技术报告生成（本工作空间已验证） |
| **量产** | 数据处理助手 | 脚本 | BOM 分析、配置器逻辑、DFX 评审支持 |
| **运维** | 运维助手/AIOps | 对话式+监控对接 | 集群故障定位、日志根因分析、告警降噪 |

### 5.2 选型标准（三重校验）

| 校验维度 | 检查项 | 目的 |
|:---------|:-------|:-----|
| **活跃度** | star 增长趋势、commit 频率、issue 响应 | 防"僵尸项目"（star 通胀陷阱）[来源: MEMORY.md 开源选型] |
| **描述** | README 完整性、架构文档、示例 | 防"包装精美内核空洞" |
| **内容** | 实际试用、代码质量、社区评价 | 防"表面繁荣实际难用" |

### 5.3 开源 vs 商业 vs 云服务决策

| 维度 | 开源自建 | 商业工具 | 云服务 |
|:-----|:---------|:---------|:-------|
| 前期成本 | 中（部署+运维） | 高（订阅费） | 低（按量） |
| 数据安全 | 最高（全本地） | 中（看合同条款） | 低-中（出网） |
| 能力上限 | 受限于所选模型 | 高（厂商优化） | 最高（旗舰模型） |
| 维护成本 | 高（自己养） | 低 | 零 |
| 适用 | 机密数据处理、长期投资 | 团队提效标配 | 试点/轻量场景 |

### 5.4 服务器研发专用工具缺口（需自建/定制）

通用 AI 工具覆盖不了、但服务器研发刚需的缺口：

| 缺口 | 现状 | 自建方向 |
|:-----|:-----|:---------|
| **BMC/固件代码审查** | 通用代码审查工具对固件场景（安全启动/寄存器/时序）不敏感 | 固件知识库 + 定制审查规则 |
| **SI/PI 仿真辅助** | 无成熟 AI 仿真工具 | 参数建议助手 + 经验库 |
| **原理图/PCB 审查** | 图纸理解困难（非文本） | 图纸解析管线 + 设计规则库 |
| **测试日志根因分析** | 通用 AI 不懂服务器日志格式 | 日志解析 + 故障知识库（FTA） |
| **竞品硬件情报** | 需多源交叉验证 | 调研 runner 类工具（知识库已有 v1.8 实践） |

### 5.5 组织层工具准备

| 事项 | 内容 |
|:-----|:-----|
| **技能库/提示词库** | 沉淀团队级提示词模板、Agent 技能（本工作空间已验证 skill 体系价值） |
| **AI Champion** | 每小组 1-2 名深度使用者，负责带教与反馈 |
| **培训体系** | 基础使用 → 高级技巧（上下文管理/工具链）→ 深度实践 |
| **工具准入清单** | 哪些工具可用、哪些禁用、谁来审批——与安全制度联动 |

## 6. 信息安全管控（安全层 · 支柱四）

> **行业背景**: AI 编程工具生态已进入**"企业管控期"**（2026H1）：狂热期（2025H1）→ 反思期（2025H2）→ 企业管控期（2026H1），"全面封禁 Cursor"是标志性事件（166K 阅读）[来源: 知识库 aicoding-juejin-news 2026-05]。**安全管控不是限制 AI 落地，而是让 AI 落地可持续的前提**——失控后的"一刀切封禁"代价远高于前置管控。

### 6.1 风险面识别（MECE）

| 风险类别 | 具体风险 | 典型泄露路径 |
|:---------|:---------|:-------------|
| **代码泄露** | 核心算法、固件源码、私有实现 | 开发者粘贴代码到公共 AI 服务 |
| **未发布产品泄露** | 新机型参数、Roadmap、客户定制方案 | 对话中上传技术文档/规格书 |
| **客户数据泄露** | 客户需求、NDA 信息、招标材料 | 用 AI 处理客户机密文档 |
| **供应链数据** | BOM、供应商价格、产能信息 | 分析敏感采购数据时外传 |
| **合规风险** | 数据出境、等保/密评、信创要求 | 云 API 默认数据出境 |
| **账号风险** | 个人账号使用、离职账号未回收 | 员工自带设备/个人订阅 |

### 6.2 数据分级与路由（核心机制）

| 密级 | 定义 | AI 处理策略 |
|:-----|:-----|:------------|
| **绝密** | 未发布产品、核心算法、客户定制 | **禁止**进入任何外部 AI；本地模型+断网 |
| **机密** | 内部架构、竞品分析、BOM/成本 | 私有化部署；或脱敏后走受控 API |
| **内部** | 通用研发规范、公开资料、脱敏代码 | 受控云 API（企业账号+审计） |
| **公开** | 行业公开信息、标准文档 | 任意工具 |

> **分级路由是安全与效率的平衡点**: 不是"一刀切禁用"或"一刀切放开"，而是按密级选择处理通道。分级规则须**写入制度并培训到人**，否则形同虚设。

### 6.3 技术管控手段

| 手段 | 说明 | 落地优先级 |
|:-----|:-----|:----------:|
| **DLP（数据防泄漏）** | 检测/阻断向外部 AI 服务上传敏感内容 | P0 |
| **审计日志** | 全量记录 AI 交互（谁/何时/什么数据/发给谁） | P0 |
| **网络隔离** | 敏感区物理/逻辑隔离，AI 出口白名单+代理 | P0 |
| **脱敏工具** | 自动识别并替换敏感字段（序列号/客户名/价格） | P1 |
| **沙箱环境** | 敏感代码在隔离沙箱中处理，禁止复制到外网工具 | P1 |
| **代码泄露扫描** | 定期扫描 GitHub/公共库是否出现企业代码指纹 | P1 |
| **私有化部署** | 机密数据不出内网，本地推理 | P1（与分级联动） |

### 6.4 组织与制度管控

| 制度 | 内容 |
|:-----|:-----|
| **AI 使用政策** | 明确允许/禁止行为、数据分级规则、违规后果——全员签署 |
| **审批流** | 新工具准入审批、高密级任务 AI 处理审批、异常使用审批 |
| **培训与考核** | 安全培训纳入新员工入职；违规案例定期通报 |
| **NDA 与合同** | 与 AI 服务商合同含数据处理条款（数据存储地/留存期/用途）；供应链侧保密协议覆盖 AI 场景 |
| **应急响应** | 泄露事件响应流程（发现→止损→溯源→整改→复盘） |

### 6.5 服务器研发特有安全要点

| 专项 | 要点 |
|:-----|:-----|
| **固件/芯片安全** | BMC/BIOS/芯片固件涉安全启动、密钥——**绝不外传**，AI 处理须本地 |
| **产品 Roadmap** | 未发布机型参数是股价级敏感信息，AI 对话禁用 |
| **竞品分析数据** | 竞品拆解/价格数据多为机密获取渠道——处理即违规风险 |
| **供应链谈判数据** | 供应商报价对比数据外传=丧失谈判筹码 |
| **客户 NDA** | 客户定制方案严格按客户保密协议执行 |
| **认证合规** | 等保/密评/信创场景对数据处理链路有强制要求 |

## 7. 周边对接分析（集成层 · 支柱五）

> **第一性原理**: AI 的价值 = 能力 × 嵌入深度。只买工具不接流程，AI 是"个人玩具"；嵌入 IPD 流程、工具链、组织三张网，AI 才是"生产系统"。**对接决定落地深度**。

### 7.1 与研发流程对接（IPD / TR 门）

| 阶段 | AI 介入点 | 预期收益 |
|:-----|:----------|:---------|
| **需求输入（TR1-TR2）** | 竞品分析、市场情报、需求规格初稿 | 调研提速 50%+（已有实践验证） |
| **方案设计（TR3）** | 架构方案比对、历史案例检索、风险清单 | 减少遗漏，方案质量提升 |
| **详细设计（TR4）** | 设计审查辅助、SI/散热参数建议、文档自动生成 | 评审效率提升 |
| **验证（TR5）** | 测试用例生成、日志分析、故障根因定位 | 测试覆盖提升 |
| **量产（TR6）** | BOM 分析、配置器逻辑、DFX 评审辅助 | 量产准备提速 |
| **生命周期** | 知识沉淀、经验复用、降本分析 | 组织能力沉淀 |

### 7.2 与研发工具链对接

| 工具链 | 对接内容 | 对接方式 |
|:-------|:---------|:---------|
| **代码托管/CI-CD** | 代码审查、提交信息、流水线日志 | API 集成/插件；AI 审查结果回填 |
| **缺陷管理** | 缺陷描述→根因分析→修复建议 | 插件/机器人 |
| **PLM/配置器/BOM** | 产品数据查询、变更影响分析 | 知识库 RAG 接入只读视图 |
| **文档/知识库** | 研发规范、案例库、经验沉淀 | RAG 检索（本工作空间已验证） |
| **测试系统** | 测试数据、日志、报告 | 解析管线 + 分析助手 |
| **办公套件** | 周报/日报/评审材料自动生成 | 模板 + Agent |

### 7.3 与组织对接

| 对接对象 | 事项 |
|:---------|:-----|
| **IT** | 网络开通、账号生命周期、代理/白名单、审计接口 |
| **信息安全** | 政策评审、DLP 部署、风险审批、应急联动 |
| **法务/合规** | 合同条款（数据处理）、合规评估（等保/密评） |
| **采购/财务** | 供应商准入、预算科目、成本分摊、对账 |
| **HR** | 培训、考核指标、岗位能力模型更新 |
| **管理层** | 定期汇报（效能/成本/风险），争取持续投入 |

### 7.4 与数据源对接（调研/情报侧）

| 数据源 | 对接要点 | 已有实践 |
|:-------|:---------|:---------|
| **行业标准/规范** | 标准库接入，AI 检索最新版本 | 知识库 02_rd 标准体系 |
| **竞品情报** | 多源交叉验证（防单一来源误导） | 调研 runner v1.8（39 任务分档）[来源: MEMORY.md] |
| **供应链** | 供应商资料、器件路线图 | 知识库实体库 |
| **客户** | 需求、反馈、招标信息（注意密级！） | 受限接入 |

### 7.5 对接就绪度自评（对接前必答）

- [ ] 每个 AI 产出物有明确的"落点"（进哪个库/哪份文档/哪个流程）？

## 8. 组织层面准备（治理层 · 横切）

> **核心论断**: 技术准备解决"能不能用"，组织准备解决"用不用得好、敢不敢用、持续不持续"。AI 落地的天花板在组织，不在技术 [来源: 知识库 agentic-org 系列 + 工程角色演进系列]。

### 8.1 治理框架四件套

| 件 | 内容 | 示例 |
|:---|:-----|:-----|
| **政策** | 使用边界、数据分级、行为准则 | AI 使用政策 v1.0（§6.4） |
| **角色** | 谁负责推进、谁负责审查、谁负责安全 | AI Champion / 安全评审 / 治理委员会 |
| **流程** | 准入→试点→推广→复盘闭环 | 工具准入审批流 / 月度 ROI 复盘 |
| **度量** | 效能、成本、安全、质量四维指标 | §8.2 指标体系 |

### 8.2 度量体系（四维）

| 维度 | 指标 | 说明 |
|:-----|:-----|:-----|
| **效能** | 任务耗时、吞吐、DORA 指标（部署频率/变更前置时间） | DORA 报告指出 AI 辅助开发存在"效能悖论"——感知提升≠交付提升，须用客观指标验证 [来源: 2025 DORA 报告素材] |
| **成本** | token/金额/单任务成本/缓存命中率 | §4.4 |
| **安全** | 违规次数、泄露事件、DLP 命中数 | 季度回顾 |
| **质量** | AI 产出返工率、采纳率、错误率 | 按任务类型采样评估 |

### 8.3 角色与能力建设

| 角色 | 职责 | 人数建议 |
|:-----|:-----|:---------|
| **AI 推进负责人** | 整体规划、资源协调、度量复盘 | 1 人（可兼） |
| **AI Champion** | 小组内深度使用、带教、反馈收集 | 每小组 1-2 人 |
| **安全评审** | 工具准入、政策维护、事件处置 | 安全部门兼 |
| **技能库维护** | 提示词/skill 沉淀、最佳实践文档 | Champion 轮流 |

**能力建设要点**:
- **防降智**: 判断力/第一性原理/跨域联想**不可外包**给 AI——这是用户核心原则 [来源: MEMORY.md 用户核心原则]
- **防依赖退化**: AI 辅助但不替代，核心能力（架构设计、故障判断）保持人工主导
- **知识沉淀文化**: "文档多≠懂得多"，AI 产出须经二次加工（净利视角）[来源: MEMORY.md]

### 8.4 文化与行为准则

| 准则 | 内涵 |
|:-----|:-----|
| AI 是工具非目标 | 产出=毛利需二次加工，防止为用而用 |
| 质量 > 速度 | 没有质量的输出再快也是浪费 [来源: 用户 08-17 决策] |
| 数据可验证 | AI 输出的数据必须可追溯来源（知识库质量铁律） |
| 公开透明 | AI 使用情况对管理层透明，避免"地下使用"逼出封禁 |

### 8.5 组织变革三阶段（与第 9 章联动）

```
PILOT      trust-building: small scope, quick win, low risk
  |
EXPANSION  governance: policy/quota/metrics, widen scope
  |
SCALE      culture: AI as default way of work, keep optimizing
```

## 9. 三阶段落地路线图

| 阶段 | 时间 | 目标 | 关键动作 | 验收标准 | 主要风险 |
|:-----|:-----|:-----|:---------|:---------|:---------|
| **P0 试点** | 1-3 月 | 环境就绪+安全基线+价值验证 | ①网络/账号/工具就绪；②数据分级+DLP+审计上线；③选 1-2 个小组试点（调研/文档/编程各一场景）；④建立 token 基线 | 试点场景提效可量化；安全零事故；单任务 token 基线建立 | 试点范围失控；安全漏洞；效果不明显 |
| **P1 扩展** | 3-6 月 | 工具链打通+治理上线+成本可控 | ①AI 嵌入 IPD 流程 3+ 环节；②与工具链（CI/PLM/知识库）对接；③预算帽+配额+审批上线；④技能库/培训体系建立 | 50%+ 目标团队在用；成本在预算内；产出开始沉淀复用 | 成本超支；制度僵化；员工抵触 |
| **P2 规模化** | 6-12 月 | 全流程嵌入+度量闭环+持续优化 | ①全流程 AI 化；②月度 ROI 复盘机制；③专用工具缺口补齐（固件审查/SI 辅助）；④供应商/客户侧生态协同 | ROI 为正（净利视角）；安全制度成熟；知识库持续增长 | 边际收益递减；能力退化；治理成本反超 |

**每个阶段结束做 Gate Review**: 未达验收标准不进入下一阶段——这是"质量>速度"原则在导入流程中的落地。
