## 1. 结论概要

| # | 要点 | 一句话 |
|:-:|:-----|:-------|
| 1 | **三条红线不是一个数** | 40%（AI 探索投入总上限）= 动作维度；35%（工具建设时间基准）= 动作维度子项；60%（业务产出占比）= 位置维度——三者的口径关系此前未澄清，本文给出映射 |
| 2 | **素材漏斗是净值核心** | 毛利看「产出量」，净利看「素材→知识转化率 + 存量堰塞湖」。当前历史存量 3.1 万素材 vs 月度加工 ~432，按现状需 **72 个月**清空——存量策略必须从「全加工」转向「清库淘汰」 |
| 3 | **8 月实际在好转** | import 新增 0（已停止进料）、knowledge 新增 432 > discover 新增 380（加工方向良性）、工具提交占比 21.7%（≤35% 安全）——命题「1.9 万素材 0 进 knowledge」是**历史存量现象**，8 月增量口径已健康 |
| 4 | **监控 = 指标卡 + 阈值动作 + 触发器** | 6 张指标卡（K1-K6）、绿灯/黄灯/红灯三级动作、周快照 + 月诊断 + 事件触发三级节奏 |
| 5 | **40% 红线触发即升级** | 红灯不自动处理——触发用户评审会，产出处置决策（暂停工具建设 / 清库 / 重排投入） |

**一句话总结**：监控的目标不是「看占比」，而是**守住用户定义的结构纪律——AI 探索是手段、业务沉淀是主线**。40% 红线是这条纪律的量化表达，监控机制让「手段与主线」的失衡在早期显性化，而不是等到月底复盘才发现。

## 2. 口径澄清：三条红线的映射

用户原则「AI 探索是手段、业务沉淀是主线，投入 ≤40% 红线」（MEMORY.md）与母体 §7.2 的两个判据（工具 ≤35%、业务产出 ≥60%）此前混用，本文澄清：

| 红线 | 维度 | 定义 | 来源 | 关系 |
|:-----|:-----|:-----|:-----|:-----|
| **40% AI 探索投入上限** | 动作（时间） | AI 探索类投入（工具建设 + 系统维护 + 探索性研究）占有效工作时间 ≤40% | 用户定义（MEMORY 核心原则） | **总闸门** |
| **35% 工具建设时间基准** | 动作（时间） | 工具建设（scripts/skills/spec/scheduler/templates）时间占比 ≤35% | 08-05 实证拐点判据 | 工具建设 = AI 探索的**最大子项** |
| **60% 业务产出占比** | 位置（产出） | 业务深度产出（knowledge/ 除 survey）占产出 ≥60% | 08-05 实证拐点判据 | 产出去向的镜像校验 |

**关键澄清**：
1. **40% 与 35% 不矛盾**——40% 是「AI 探索」总预算（含工具 35% + 系统维护/探索余量），35% 是其中最大的单一子项。工具占比 35% 未超，但加上维护/探索可能逼近 40%——**监控必须同时看两个数，不能只看工具**。
2. **动作维度 vs 位置维度不可混用**（kb-effort-churn-diagnosis 统计铁律 3）——40%/35% 是「时间花在哪」，60% 是「产出落哪」。「时间 35% 做工具」与「产出 8.5% 在工具目录」不矛盾（工具时间产出的是约束脚本，业务时间产出的是知识文档）。
3. **监控的完整视图 = 双维度交叉**：动作维度回答「投入健康吗」，位置维度回答「产出健康吗」，两者交叉才构成净值判断。

## 4. 素材漏斗模型：毛利/净利的量化核心

### 4.1 漏斗三层

```
        +----------------------+
        |  import (raw feed)    |  18,895 (historical imports)
        +----------+-----------+
                   | intake
        +----------v-----------+
        | discover (experiment) |  12,441 (processed/half-done)
        +----------+-----------+
                   | refine
        +----------v-----------+
        | knowledge (official)  |  2,896 (formal docs)
        +----------------------+
```

### 4.2 漏斗经济学

| 视角 | 指标 | 当前值 | 含义 |
|:-----|:-----|:------:|:-----|
| **毛利** | 月产出量（提交/新 md） | 346 / 432 | 产出旺盛，但只是毛利 |
| **转化率** | 月新增 knowledge / 月新增 import | 432/0 = ∞（好） | 8 月增量健康，但历史存量未动 |
| **存量堰塞湖** | import + discover 总文件数 | 31,336 | 每月加工 ~432 → **需 72 个月清空**（按全加工策略） |
| **净利代理** | 存量清零率 | ~1.4%/月（432/31336） | 不可持续 → 策略必须转向「清库淘汰」 |

### 4.3 存量处置策略（关键决策）

3.1 万素材不可能全加工（72 个月不现实），需要分级处置：

| 处置路径 | 适用 | 动作 |
|:---------|:-----|:-----|
| **加工沉淀** | 高价值素材（与主线主题相关、可交叉验证） | 按专题加工进 knowledge/（现有管线） |
| **索引化保留** | 中价值素材（可能未来用） | 建立素材索引（清单+来源+主题），不进正文，检索时按需提取 |
| **淘汰归档** | 低价值/重复/过时素材 | 移入 `tmp/bak/`（遵循永不 rm 铁律），保留元数据 |
| **反哺清理** | discover 试验场半成品 | 有价值的转 knowledge/，无价值的清理，控制试验场规模 |

**原则**：素材层的「存在」不等于「价值」，**素材管理的关键指标是「清零速度」而非「积累速度」**——这与知识价值链文档（ROI=利用产出/构建投入）同构：构建投入（素材积累）必须被利用产出（加工沉淀）追赶。

## 5. 监控机制：6 张指标卡

### 5.1 指标卡总览

| 卡 | 指标 | 数据源 | 频率 | 阈值（黄/红） |
|:--:|:-----|:-------|:----:|:--------------|
| K1 | 工具建设时间占比（动作维度） | git log 提交路径 + 时间加权 | 周/月 | 黄 >35% / 红 >40% |
| K2 | AI 探索总投入占比（动作维度，含维护/探索） | 人工时间记账 | 月 | 黄 >35% / 红 >40% |
| K3 | 业务相关产出占比（位置维度） | 目录快照（knowledge/ 除 survey） | 月 | 黄 <60% / 红 <50% |
| K4 | 素材转化率（月新增 knowledge / 月新增 import） | git log 路径统计 | 月 | 黄 <0.5 / 红 <0.2 |
| K5 | 存量堰塞湖（import+discover 总文件数） | 目录快照 | 周 | 黄 增长 / 红 连续 2 周增长 |
| K6 | 审查成本占比（审查小时/有效工作小时） | 人工记账 | 月 | 黄 >25% / 红 >35% |

### 5.2 指标卡详细定义

**K1 工具建设时间占比**（母体 §7.2 判据 1，沿用）
- 计算：工具侧提交（scripts/skills/spec/scheduler/templates 路径）时间加权占比
- 注意：提交数口径有局限（治理提交多而小），用时间加权交叉验证（kb-effort-churn 技能 §2 统计铁律）
- 当前：21.7%（8 月）✅ 安全

**K2 AI 探索总投入占比**（40% 红线本体，本文新增）
- 计算：工具建设时间 + 系统维护时间 + 探索性研究时间，占有效工作时间
- 数据源：**人工时间记账**（自动化只能测提交，测不了「想系统怎么改进」的时间）——这是 40% 红线无法完全自动化的原因，需用户侧提供近似值
- 触发逻辑：K1 黄灯必然先于 K2 黄灯（工具是最大子项），K2 用于捕捉「工具没超但维护/探索超」的情形

**K3 业务相关产出占比**（母体 §7.2 判据 2，沿用）
- 计算：knowledge/ 新增 md 中业务深度产出（除 01_survey/weekly-reports）占比
- 当前：8 月 knowledge 提交占 76.3% ✅ 安全

**K4 素材转化率**（本文新增，漏斗核心）
- 计算：月新增 knowledge md / 月新增 import 文件
- 8 月 = 432/0 = ∞ ✅；但需警惕「加工停止」的假象——转化率要用**存量**校验（K5）

**K5 存量堰塞湖**（本文新增）
- 计算：import + discover 文件数周快照
- 判定：不增长 ✅ / 增长 ⚠️（8 月 discover +380 → 黄灯边缘：试验层膨胀）
- 目标：通过淘汰归档（§4.3）使存量**下降**

**K6 审查成本占比**（母体 §10 沿用）
- >25% 即预警（信任损耗信号，母体 §4.3）

### 5.3 执行者分工

| 角色 | 职责 |
|:-----|:-----|
| **自动化脚本** | K1/K3/K4/K5 的 git log 与目录快照采集（可脚本化，周快照自动生成） |
| **定时任务** | 周快照入 weekly-reports（git_footstep 已有数据底座）；月诊断调用 kb-effort-churn 技能 |
| **人工记账** | K2/K6 需要时间记账（用户侧），月度评审时用户提供近似值 |
| **用户评审** | 红灯触发时决策（§6） |

## 6. 阈值动作矩阵与升级路径

### 6.1 红绿灯判定

| 状态 | 判定 | 含义 |
|:----:|:-----|:-----|
| 🟢 绿灯 | 全部 K1-K6 在阈值内 | 结构健康，维持节奏 |
| 🟡 黄灯 | 1-2 项超阈值 | 预警：观察趋势，准备处置 |
| 🔴 红灯 | ≥3 项超阈值 或 单 K2 超 40% | 失衡：触发用户评审会 |

### 6.2 红灯动作（升级路径）

> **原则：红灯不自动处理，触发用户评审会决策**（遵循用户核心原则「AI 不允许直接删除任务/替用户做准入判断」）。

```
[RED] triggered
  -> 1 generate red report: over-threshold metrics + raw stats (A/M/R/D, user aggregates)
  -> 2 user review: classify imbalance type
       |- tool-inflation (K1 over)   -> pause new tool building, prioritize business (restore K3)
       |- maintenance-drain (K2 over, K1 ok) -> audit maintenance, systemic root-cause (churn)
       |- material-accumulation (K4/K5 over) -> start backlog cleanup (sec 4.3), set zeroing target
       `- review-burnout (K6 over)   -> trust repair (mother sec 4.3 delivery paradox)
  -> 3 dispatch actions + set review date (2-4 weeks)
  -> 4 re-check: metrics recovered -> green; not recovered -> escalate
```

### 6.3 黄灯动作

- K1/K2 黄灯：记录趋势（连续 2 周上升才升级），不打断正常节奏——工具建设有合理波动（如技能迭代期）
- K4/K5 黄灯：单次 discover 增长不处理，连续增长则触发「试验场清理周」
- K6 黄灯：提高审查自动化覆盖（把人工审查项转脚本），而非立即停产出

## 7. 三级触发器与执行节奏

| 层级 | 频率 | 执行 | 产出 |
|:-----|:-----|:-----|:-----|
| **周快照** | 每周一 | 脚本自动（git log + 目录快照） | K1/K3/K4/K5 数值 + 趋势，入周报 |
| **月诊断** | 每月初 | kb-effort-churn 技能全量统计（A/M/R/D + churn 雷达） | 六卡完整报告 + 红绿灯判定 |
| **事件触发** | 按需 | 大导入（>300 文件）/ 新工具上线 / 技能批量迭代 | 即时快照 + 阈值复检 |

**事件触发的原因**：大导入提交会瞬间推高素材层（历史 6 个大导入 = 1.9 万文件的来源），新工具上线会短期推高 K1——这些事件必须即时记录基线，否则月诊断无法归因（是趋势恶化还是事件噪声）。

## 9. 批判注记

1. **40% 红线无法完全自动化**：K2（AI 探索总投入）依赖人工时间记账——提交路径只能测「动作痕迹」，测不了「思考时间」。这是监控体系的诚实缺口：红线本体的数据质量取决于用户记账的持续性。
2. **转化率 K4 的假象风险**：8 月 K4 = ∞（import 0 新增）不代表加工强劲——需 K5 存量校验。单指标看会误判。
3. **存量 72 个月估算是线性外推**：假设加工速度恒定 432/月、存量恒定 31,336。真实路径应是「淘汰为主 + 加工为辅」（存量大头不该加工），估算用于说明「全加工策略不可行」，非预测。
4. **口径仍在演进**：分类标准 v3.0 由用户定义（kb-effort-churn 技能 §1），新统计前须确认分类仍有效——本文的 K1-K6 定义随分类标准更新而更新。
5. **监控是手段不是目的**：红绿灯的产出是「决策输入」而非「自动处置」——最终判断权在用户（对应 MEMORY「不替用户做准入判断」）。
