## 1. 核心框架

### 1.1 为什么需要按工程类型区分？

AI 的"够用"不是绝对的——同一份输出，在不同工程场景中的可接受度天差地别：

```text
场景 A: 代码片段草图              -> 70% 正确即可激发灵感
场景 B: 生产环境部署脚本          -> 99.9% 正确才敢执行
场景 C: 航空级功能安全文档        -> 100% 可追溯 + 无遗漏
场景 D: PCB 信号完整性分析        -> 数值误差 < 5% + 有测量验证
```

**核心洞察**: 不是 AI 能力不够，而是**没按工程类型的可信度下限去选型/控制/验收**。

### 1.2 特性维度定义

本框架定义 **12 个独立的 AI 特性维度**，每个工程类型对其赋予不同的权重：

| 编号 | 特性维度 | 定义 | 反面案例 |
|:----:|:---------|:-----|:---------|
| C01 | **事实准确性** | 输出的事实性断言有可靠来源支撑，不编造 | 编造论文引用、虚构芯片参数 |
| C02 | **可验证性** | 每项 claim 可追溯到原始来源或推导过程 | "据行业报告显示"而无出处 |
| C03 | **逻辑一致性** | 同一上下文内不矛盾，推理链无断裂 | 前文说 A > B，后文用 B > A 推导 |
| C04 | **可复现性** | 相同输入下输出在可接受范围内一致 | 同一 prompt 两次结果矛盾 |
| C05 | **量化严谨** | 数值有单位、有对比基线、有测试条件 | "性能提升 30%" 无基线无环境 |
| C06 | **上下文记忆** | 记住项目约束、历史决策、依赖关系 | 反复忘记用户的技术选型前提 |
| C07 | **领域术语精确** | 技术名词使用准确，不混用近似概念 | "PCIe 带宽"与"PCIe 速率"混用 |
| C08 | **边界意识** | 明确知道自己不知道什么 | 对不熟悉领域给出模糊但错误的自信回答 |
| C09 | **场景覆盖完备** | 考虑正常路径 + 异常路径 + 边界条件 | 只给 happy path 不考虑错误处理 |
| C10 | **成本敏感** | 输出方案考虑实现/维护/机会成本 | 推荐方案理论上最优但落地成本不可接受 |
| C11 | **安全/合规意识** | 输出不引入安全漏洞、不违反法规 | 生成含 SQL 注入的代码 |
| C12 | **可审查性** | 输出格式/结构便于人工审查和验证 | 长篇大论无分段无要点无交叉引用 |

## 2. 通用特性要求（跨工程类型）

无论什么工程类型，以下特性是**底线的底线**，不满足则不可用于任何工程场景：

### 2.1 底线要求（P0 — 不可妥协）

| 特性 | 最低阈值 | 为什么 |
|:-----|:---------|:-------|
| **C01 事实准确性** | 不得编造可验证的事实 | 一个虚假引用即可摧毁对整份文档的信任 |
| **C07 领域术语精确** | 核心术语不得混淆 | 混用术语导致上下游工程师理解偏差，引发设计错误 |
| **C11 安全/合规意识** | 不得引入已知类别的安全风险 | 工程产出直接影响生产环境/人身安全 |

### 2.2 标准要求（P1 — 必须满足）

| 特性 | 最低阈值 | 为什么 |
|:-----|:---------|:-------|
| **C03 逻辑一致性** | 同文档内不矛盾 | 矛盾导致执行层面不知按哪条走 |
| **C08 边界意识** | 不确定时明确标注 | 假自信比无知更危险 |
| **C09 场景覆盖完备** | 至少覆盖正常+常见异常 | 只给 happy path 是工程文档的致命伤 |

### 2.3 增强要求（P2 — 区分工程质量）

| 特性 | 说明 |
|:-----|:------|
| **C02 可验证性** | 来源标注清晰度 |
| **C05 量化严谨** | 数值完整性 |
| **C12 可审查性** | 输出结构的审查友好度 |
| **C04 可复现性** | 跨 session 的一致性 |
| **C06 上下文记忆** | 是否记住项目历史 |
| **C10 成本敏感** | 方案的经济可行性 |

## 3. 软件工程

### 3.1 场景定义

代码生成、代码审查、调试排错、重构、架构设计、API 设计、测试用例生成、CI/CD 脚本

### 3.2 特性优先级

```text
P0 — 编译/运行正确:    代码能编译通过、运行时逻辑正确       (不可妥协)
P0 — 安全敏感:        不引入 OWASP Top 10 类漏洞            (不可妥协)
P0 — 渐进修改:         最小 diff 原则，不随意重构周边代码    (不可妥协)
-----------------------------------------------------
P1 — 边界覆盖:        处理空值/边界/并发/错误路径            (质量门槛)
P1 — 依赖意识:         了解使用的库版本和 API 兼容性           (质量门槛)
P1 — 测试意识:         生成的代码本身可测试、有测试            (质量门槛)
-----------------------------------------------------
P2 — 性能意识:         时间复杂度/空间复杂度不盲目            (优化)
P2 — 代码风格一致:     遵循项目既有风格和命名规范              (优化)
P2 — 文档同步:         代码变更同步更新注释/文档              (优化)
```

### 3.3 关键失效模式

| 失效模式 | 典型表现 | 后果 | 检测方式 |
|:---------|:---------|:-----|:---------|
| **幻觉 API** | 编造不存在的库函数/API 签名 | 编译失败，浪费排查时间 | 编译 + lint |
| **上下文截断** | 长文件中遗漏已有实现，重复造轮子 | 重复代码、不一致 | 人工 code review |
| **过度重构** | 改一行却重写了整个函数 | 引入新 bug，diff 难审 | git diff 审查 |
| **忽略错误处理** | try 块空 catch，不处理超时/断连 | 生产环境静默失败 | 测试覆盖率 |
| **版本幻觉** | 使用 API v2 却写 v1 的调用方式 | 运行时异常 | 编译 + 单元测试 |

### 3.4 可接受度阈值

| 使用场景 | 最低可接受 | 工具推荐 |
|:---------|:-----------|:---------|
| 代码片段灵感/原型 | 编译通过率 > 60% | Cursor/Claude Code |
| 单元测试生成 | 测试逻辑正确率 > 85% | Copilot + 人工审查 |
| 代码审查辅助 | 发现真阳性 bug > 70% | GPT-4 + 规则引擎 |
| 生产代码生成 | 逻辑正确率 > 95% + 逐行审查 | 仅辅助，禁止直接使用 |
| 重构安全关键模块 | 不改变行为 + 100% 测试通过 | 仅建议，人工实施 |

## 4. 硬件工程

### 4.1 场景定义

原理图设计、PCB 布局建议、信号完整性分析、电源完整性分析、热设计、组件选型、DFM 检查、时序分析

### 4.2 特性优先级

```text
P0 — 物理约束遵守:    遵守器件电气/机械/热特性限制           (不可妥协)
P0 — 数据表忠诚:      引用组件参数须精确匹配 Datasheet        (不可妥协)
P0 — 制造可行性:      DFM 规则不违反                        (不可妥协)
-----------------------------------------------------
P1 — 经验公式精度:     估算公式有适用范围标注                 (质量门槛)
P1 — 多域耦合意识:     知道 SI/PI/thermal 之间的相互影响      (质量门槛)
P1 — 容差分析:         考虑器件离散性与温漂                   (质量门槛)
-----------------------------------------------------
P2 — 成本敏感:         选型考虑 BOM 成本                     (优化)
P2 — 替代料意识:       提供兼容替代方案                      (优化)
P2 — 合规认证:         考虑安规/EMC/环保合规                 (优化)
```

### 4.3 关键失效模式

| 失效模式 | 典型表现 | 后果 | 检测方式 |
|:---------|:---------|:-----|:---------|
| **参数幻觉** | 虚构芯片的功耗/带宽/延迟参数 | 系统规格错误，选型失败 | 交叉验证 Datasheet |
| **忽略工艺限制** | 推荐 PCB 叠层超过工厂能力 | 无法生产 | DFM 检查 |
| **耦合盲区** | 只考虑 SI 不考虑 thermal 形变 | 高速信号失效 | 多物理场仿真 |
| **典型值陷阱** | 用典型值代替 worst-case 分析 | 量产时裕量不足 | 容差仿真 |

### 4.4 可接受度阈值

| 使用场景 | 最低可接受 | 工具推荐 |
|:---------|:-----------|:---------|
| 组件选型前期调研 | 参数不虚构 + 来源可查 | AI + 人工参考 Datasheet |
| SI/PI 快速估算 | 误差 < 20% + 标注估算条件 | AI 仅做初步扫描 |
| 设计评审辅助 | 发现明显设计缺陷 | AI 辅助 + 资深工程师终审 |
| 生产级设计输出 | 不可接受 | — (AI 不直接输出硬件设计) |

## 5. 系统架构工程

### 5.1 场景定义

技术选型对比、架构方案设计、接口协议定义、部署拓扑设计、方案权衡分析、演进路径规划

### 5.2 特性优先级

```text
P0 — MECE 分解:       对比方案在同一维度上互斥且穷尽         (不可妥协)
P0 — 约束完整声明:     方案的前提/假设/约束须完整说明         (不可妥协)
P0 — 反方论证:         主动呈现方案的弱点和风险               (不可妥协)
-----------------------------------------------------
P1 — 多维对比框架:     从功能/性能/可靠性/成本/可维护性等维度对比 (质量门槛)
P1 — 量化支持:        对比有数据支撑而非定性描述              (质量门槛)
P1 — Pareto 权衡:      识别关键约束下的 Pareto 前沿            (质量门槛)
-----------------------------------------------------
P2 — 演进路径:         方案的分阶段落地路径                   (优化)
P2 — 组织适配:         方案与团队能力/组织结构的匹配度         (优化)
P2 — 竞争参照:         对标行业主流方案的位置                 (优化)
```

### 5.3 关键失效模式

| 失效模式 | 典型表现 | 后果 | 检测方式 |
|:---------|:---------|:-----|:---------|
| **维度不完整** | 按 3 个维度对比而漏了最关键的第 4 个 | 选错方案 | MECE 自检 |
| **隐藏假设** | 未说明"假设网络不拥塞""假设无故障" | 方案在真实场景失效 | 假设清单审查 |
| **幸存者偏差** | 只列成功的参照，不提失败案例 | 风险被低估 | 反例搜索 |
| **OOS 盲区** | 方案在 10 节点好，1000 节点不可行 | 扩展性灾难 | Scale 分析 |

### 5.4 可接受度阈值

| 使用场景 | 最低可接受 | 工具推荐 |
|:---------|:-----------|:---------|
| 方案初稿/框架构思 | MECE + 约束完整 | AI 输出 + 人工完善 |
| 技术选型对比表 | 维度完整 + 数据可验证 | AI 框架 + 人工填数 |
| 架构评审准备 | 反方论证 + 量化权衡 | AI 辅助 + 架构师终审 |
| 最终架构决策 | 不可独立决策 | 人做决策，AI 提供信息 |

## 6. 数据工程

### 6.1 场景定义

数据清洗、ETL pipeline 设计、数据质量检测、特征工程、数据集构建、数据标注规范、数据隐私合规

### 6.2 特性优先级

```text
P0 — 数据质量敏感:    检测并报告数据中的异常/缺失/不一致       (不可妥协)
P0 — 可重现流程:      数据处理步骤确定且可复现                (不可妥协)
P0 — 隐私合规:         不泄露 PII，不违反数据保护法规          (不可妥协)
-----------------------------------------------------
P1 — 分布意识:         关心数据分布、偏斜、长尾               (质量门槛)
P1 — 一致性校验:       确保上下游数据语义一致                 (质量门槛)
P1 — 版本控制:         数据集的版本变更可追溯                  (质量门槛)
-----------------------------------------------------
P2 — 数据增强:         合理的数据增强策略                    (优化)
P2 — 成本效率:         存储/计算成本与数据价值匹配             (优化)
P2 — 标注质量:         标注指南清晰，质检手段完善              (优化)
```

### 6.3 关键失效模式

| 失效模式 | 典型表现 | 后果 |
|:---------|:---------|:-----|
| **分布幻觉** | 假设数据均匀分布而实际偏斜严重 | 模型对长尾失效 |
| **泄漏忽略** | 特征工程中引入未来信息 | 模型评估虚高 |
| **隐私盲区** | 未脱敏的 PII 进入数据集 | 合规风险 |

## 7. 可靠性工程

### 7.1 场景定义

FMEA、FTA、RCA 根因分析、故障模式分析、容错设计评审、可靠性建模、可用性计算

### 7.2 特性优先级

```text
P0 — 场景完备性:       不漏关键故障场景                     (不可妥协)
P0 — 因果链完整:       从故障表象到根本原因的链条完整         (不可妥协)
P0 — 概率量化:         故障率有数据源或合理估算               (不可妥协)
-----------------------------------------------------
P1 — 经验数据引用:     失效率引用有行业/厂商数据支撑          (质量门槛)
P1 — 冗余/多样性思维:   考虑单一故障点及容错方案              (质量门槛)
P1 — 共因失效敏感:     识别多个故障的共同根源                (质量门槛)
-----------------------------------------------------
P2 — 维修性分析:        MTTR/可修复性评估                   (优化)
P2 — 失效传播:         故障的级联效应分析                    (优化)
P2 — 退化模型:         考虑磨损/老化导致的渐进失效            (优化)
```

### 7.3 关键失效模式

| 失效模式 | 典型表现 | 后果 |
|:---------|:---------|:-----|
| **场景遗漏** | FMEA 漏了某类故障模式 | 设计未覆盖，量产暴露 |
| **因果跳跃** | 直接跳到结论，跳过中间推理 | 根因误判，无效修复 |
| **概率虚构** | 拍脑袋给失效率，无数据源 | 可靠性预算虚高 |
| **共因盲区** | 多个独立故障实为同一原因 | 冗余设计失效 |

## 8. 制造工程

工艺流程设计、SMT 参数建议、测试覆盖率分析、良率提升、产线布局、夹具设计、过程控制

### 8.2 特性优先级

```text
P0 — 工艺约束遵守:     不违反设备能力/材料特性限制            (不可妥协)
P0 — 统计思维:         用 CPK/SPC 说话而非"感觉"            (不可妥协)
P0 — 成本-产量敏感:    方案与量级匹配                       (不可妥协)
-----------------------------------------------------
P1 — 测试覆盖完备:     测试项覆盖关键失效模式                 (质量门槛)
P1 — 容错/调整裕量:    工艺窗口有安全裕度                    (质量门槛)
P1 — 爬坡路径:         从试产到量产的过渡计划                (质量门槛)
-----------------------------------------------------
P2 — 自动化意识:        适机自动化而非盲目自动化               (优化)
P2 — 防呆设计:         通过工装/流程防错                     (优化)
```

## 9. 运维工程

### 9.1 场景定义

部署配置、监控告警设置、日志分析、故障排障、容量规划、变更评估、Runbook 编写

### 9.2 特性优先级

```text
P0 — 变更安全:         变更影响范围完整评估                   (不可妥协)
P0 — 操作顺序精确:     步骤顺序错误即导致故障                 (不可妥协)
P0 — 回滚路径:         任何操作须有回滚方案                   (不可妥协)
-----------------------------------------------------
P1 — 日志分析深度:      从表象到根因的推理链                  (质量门槛)
P1 — 时间敏感:          关注时序关系（先A后B vs 同时）        (质量门槛)
P1 — 爆炸半径意识:      故障影响的边界评估                    (质量门槛)
-----------------------------------------------------
P2 — 自动化度评估:      判断什么该自动什么该人工               (优化)
P2 — 监控完备性:        关键指标是否被监控                    (优化)
```

### 9.3 关键失效模式

| 失效模式 | 典型表现 | 后果 |
|:---------|:---------|:-----|
| **零变更假设** | 排障时假设"什么都没变过" | 漏掉变更引入的根本原因 |
| **时序错觉** | 把相关性当因果（A 在 B 前发生 = A 导致 B） | 根因误判 |
| **回滚缺失** | 给修改意见不给回滚方案 | 改坏了无法恢复 |
| **静态假设** | 假设今天的配置与文档一致 | 实际环境与预期不符 |

## 10. 研究工程

### 10.1 场景定义

文献调研、实验设计、结果分析、baseline 对比、消融实验设计、统计显著性检验、论文写作

### 10.2 特性优先级

```text
P0 — 基线公平:         对照方法使用其最优配置而非弱化版        (不可妥协)
P0 — 统计显著性:       结论由统计检验支撑而非均值感觉          (不可妥协)
P0 — 结果不夸大:       不选择性地报告最好的结果               (不可妥协)
-----------------------------------------------------
P1 — 文献覆盖:          关键相关工作的完整覆盖                 (质量门槛)
P1 — 消融完备:          每个设计选择的贡献可隔离评估           (质量门槛)
P1 — 实验可复现:        随机种子/数据划分/超参记录完整         (质量门槛)
-----------------------------------------------------
P2 — 失败分析:          同样重视"什么没 work"                 (优化)
P2 — 局限性坦诚:        方法的使用边界和应用限制               (优化)
```

### 10.3 关键失效模式

| 失效模式 | 典型表现 | 后果 |
|:---------|:---------|:-----|
| **基线弱化** | 用默认参数跑 baseline 而自己精心调参 | 提升幅度虚高 |
| **p-hacking** | 反复试直到显著，不报告未显著的结果 | 结论不可复现 |
| **樱桃采摘** | 只报告最好的实验、最好的 epoch | 性能评估偏差 |
| **忽略负结果** | 不提什么没 work | 误导后续研究者 |

### 11.3 关键失效模式

| **结构埋没** | 关键内容淹没在长篇段落中 | 读者找不到重点 |

## 12. 安全关键工程

### 12.1 场景定义

功能安全（ISO 26262/IEC 61508）、信息安全、合规认证、故障安全设计、可靠性预算

### 12.2 特性优先级

```text
P0 — 最坏情况思维:     按 worst-case 设计而非 typical          (不可妥协)
P0 — 失效模式完备:     安全目标的失效覆盖须 100%              (不可妥协)
P0 — 独立性/多样性:     安全机制与被保护功能独立               (不可妥协)
P0 — 认证路径清晰:      清晰知道满足哪个标准/哪个 ASIL 等级    (不可妥协)
-----------------------------------------------------
P1 — 责任边界清晰:     明确 AI 建议 vs 人工决策的责任分割      (质量门槛)
P1 — 可审计/可追溯:     每项决策有完整记录和理由               (质量门槛)
P1 — 安全裕量量化:      安全裕量有数据支持                    (质量门槛)
-----------------------------------------------------
P2 — 退化路径:          系统在部分故障下的安全退化策略         (优化)
P2 — 经验数据引用:     现场故障率/保修数据的运用              (优化)
```

### 12.3 关键失效模式

| 失效模式 | 典型表现 | 后果 |
|:---------|:---------|:-----|
| **典型值陷阱** | 用典型值而非 worst-case 设计裕量 | 安全裕量不足，量产暴露 |
| **独立性忽视** | 安全机制与被保护功能共享资源 | 共因失效导致安全机制失效 |
| **责任模糊** | AI 建议被当作"已验证过的结论" | 安全责任错位 |

### 12.4 使用红线

**在任何安全关键工程中，AI 的定位只能是「辅助信息提供者」，不可作为「设计决策者」或「验证者」**。人类工程师必须对安全关键输出承担全部责任。

## 14. 工程使用的风险分级模型

### 14.1 四阶风险分级

| 级别 | 名称 | AI 使用方式 | 审查要求 | 示例场景 |
|:----:|:-----|:------------|:---------|:---------|
| **L1** 🟢 | 灵感激发 | AI 提供想法/框架/草案，人独立验证 | 快速目视检查 | 代码片段、架构草图、文献初筛 |
| **L2** 🟡 | 辅助起草 | AI 生成初稿，人逐项审查修改 | 逐项审查 + 关键数据交叉验证 | 技术文档、测试用例、设计规格 |
| **L3** 🟠 | 辅助验证 | AI 辅助检查/验证/交叉参考 | 专业领域审查 + 量化验证 | 代码审查、FMEA 交叉检查、数据质量检测 |
| **L4** 🔴 | 自动执行 | AI 自主执行，人仅确认结果 | 事前规则定义 + 事后审计 | CI/CD 流水线、自动化测试、监控告警 |

### 14.2 工程类型 × 风险等级矩阵

| 工程类型 | 允许最高级别 | 风险原因 | 绝对禁止 |
|:---------|:-----------:|:---------|:---------|
| 软件工程 | L3 | 可编译可测试，反馈快 | L4 生产代码生成 |
| 硬件工程 | L2 | 物理制造周期长，错误代价高 | L3/L4 硬件设计输出 |
| 系统架构 | L2 | 决策影响面广，反悔成本高 | L3/L4 架构决策 |
| 数据工程 | L3 | 可回滚可重算 | L4 隐私脱敏决策 |
| 可靠性工程 | L1 | 遗漏致命故障模式的后果不可逆 | L2+ FMEA 生成 |
| 制造工程 | L1 | 工艺错误影响量产 | L2+ 工艺流程设计 |
| 运维工程 | L2 | 实时系统，爆炸半径难控 | L3+ 生产变更执行 |
| 研究工程 | L3 | 实验可重复，容错空间大 | L4 结论替代 |
| 文档工程 | L2 | 内容可修订 | L3+ 无审查发布 |
| 安全关键 | **L1** | 涉及人身/财产安全 | L2+ 任何决策 |

## 15. 使用 AI 工程的最佳实践总结

### 15.1 准入三问

在将 AI 用于任何工程任务前，先回答这三个问题：

1. **如果 AI 错了，后果是什么？** → 确定风险级别
2. **这个错误能被及时发现吗？** → 确定检测窗口
3. **有回滚/修正路径吗？** → 确定兜底策略

### 15.2 不同工程类型的验收标准差异

| 工程类型 | "合格"的定义 | 验收方式 |
|:---------|:------------|:---------|
| 软件 | 编译通过 + 逻辑正确 | 自动化测试 |
| 硬件 | 物理可制造 + 仿真通过 | DFM + 仿真 |
| 架构 | MECE + 约束完整 + 反方论证 | 架构评审 |
| 数据 | 可重现 + 分布合理 + 质量检测 | 数据质量报告 |
| 可靠 | 场景完备 + 因果链完整 | FMEA 交叉检查 |
| 制造 | 工艺可行 + CPK 达标 | 试产验证 |
| 运维 | 操作可回滚 + 影响已知 | 变更评审 |
| 研究 | 基线公平 + 统计显著 + 结果不夸大 | 复现验证 |
| 文档 | 引用准确 + 术语一致 + 版本标注 | 同行审查 |
| 安全 | 最坏情况 + 失效完备 + 独立验证 | 第三方审计 |

### 15.3 一条铁律

> **AI 输出的可信度 ≠ AI 输出的事实正确性。**
>
> 可信度是"看起来多像真的"，正确性是"实际上是不是真的"。
> 工程上，永远按**最小可信度假设**使用 AI 输出——先假设它可能是错的，直到被验证。
