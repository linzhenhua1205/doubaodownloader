## 1. 问题定义：Skill 加载 ≠ Skill 遵守

### 1.1 根因分析

| 根因 | 描述 | 影响程度 |
|:----|:-----|:--------:|
| **注意力稀释** | 大量 Skill 文本涌入上下文，AI 注意力分散，核心规则被"背景化" | ★★★★★ |
| **指令冲突** | Skill 之间/与用户实时指令产生优先级冲突，AI 按就近原则响应 | ★★★★☆ |
| **抽象距离** | Skill 描述过于抽象（"请遵循 MECE 原则"），AI 缺乏可执行的原子操作指引 | ★★★★★ |
| **上下文窗口衰减** | 长对话中早期加载的 Skill 被新内容推远，Attention 注意力衰减 | ★★★★☆ |
| **模型对齐偏差** | 底层模型对"遵循规则"能力的固有限制（如指令遵循的 token 预算分配） | ★★★☆☆ |
| **反馈缺失** | 违反 Skill 后缺乏即时负反馈，AI 感知不到"做错了" | ★★★★☆ |

### 1.2 典型失败模式

```text
用户: "请遵循我的 Skill，先做架构分析再做编码"
AI:   直接开始写代码（跳过架构分析）
       ^ 最常见失败：Skill 被当作"背景说明"而非"执行指令"
```

```text
用户: Skill 中定义了 10 条编码规范
AI:   前几次响应严格遵守，30 轮对话后逐渐遗忘
       ^ 上下文衰减：早期约束被后续新内容"推离"注意力中心
```

---

### 1.3 关键术语定义

| 术语 | 定义 | 说明 |
|:-----|:-----|:------|
| **遵守率** | AI 在单次响应中**显式满足某条 Skill 规则的比例**（规则级） | 例：10 条规则满足 9 条 → 90%。非轮次级（一轮可能产生多次违反） |
| **初始遵守率** | 首次加载 Skill 后第 1-3 轮的平均遵守率 | 反映 Skill 本身的清晰度和可执行性 |
| **衰减曲线** | 遵守率随对话轮次增加的变化趋势 | 通常呈指数衰减，衰减速率受 Skill 设计和反馈机制影响 |
| **注意力预算** | Transformer 在单次生成中分配给不同位置 token 的注意力权重总和（softmax 归一化为 1） | 上下文越长，每个 token 的平均注意力份额越小。注意力预算 = 分配给目标信息的 softmax 权重之和。与人类"注意力"不同——AI 没有选择性聚焦能力，只有归一化后的权重竞争。 |

> ⚠️ **本文中所有百分比数据均为经验观察值，非严格实验结论。** 影响遵守率的变量包括：模型版本（Claude Sonnet 4 vs GPT-4o vs DeepSeek）、任务复杂度、规则内容密度、上下文长度等。读者应将数据视为**趋势性参考**而非精确测量结果，具体数值会因模型和场景不同而偏移。

### 1.4 本文的体裁定位

> **本文是一份「给人读的方法论文档」，并非「给 AI 读的 Skill 文件」。**

这两种体裁有本质区别，本文自身也可能不完全符合本文提出的方法论（见 §10.4 自我检视）：

| 维度 | 方法论文档（本文） | AI Skill 文件 |
|:-----|:------------------|:--------------|
| 目标读者 | 人类工程师 | AI Agent |
| 核心任务 | 解释"为什么"、提供原理和决策依据 | 给出"做什么"、可执行的原子指令 |
| 篇幅 | 允许长篇展开，不限条数 | 每份 ≤7 条，≤500 字 |
| 语言风格 | 论述性、分析性、案例式 | 指令性、清单式、无歧义 |
| 验证方式 | 读者理解后自行判断 | AI 输出前按清单逐条验证 |

本文的理论分析和案例可以作为编写 Skill 的**设计输入**，但直接将其作为 Skill 加载给 AI 会因篇幅过长和风格不当而降低遵守率。第 10 章提供了从方法论文档到 AI Skill 的转换指南。

## 2. 四法门：提升 Skill 遵守率的交互设计

这四法是用户在实践中验证有效的核心技巧。需要注意的是，这四个方法**并非同一逻辑层面**，而是从三个维度切入：

| 维度 | 方法 | 解决的问题 | 类比 |
|:-----|:-----|:-----------|:-----|
| 🏗️ **架构维度** | 分层 | "什么时候投喂什么规则" | 软件架构的分层设计 |
| ✏️ **表达维度** | 小型化（要点化） | "规则怎么写 AI 才容易理解" | 信息论的编码效率 |
| 📡 **增强维度** | 重复 + 强调 | "写了怎么让 AI 注意到" | 通信中的冗余编码 + 信号放大 |

三层缺一不可：**分错了层 → 时机错；写得太长 → AI 看不懂；不重复不强调 → AI 看完就忘**。

以下 §2.1-2.4 按**实操中的入手顺序**（从最易上手到最需要规划）展开——先试重复和强调（零成本），再做小型化（改格式），最后规划分层（需设计）。这与三维度框架的逻辑顺序（架构→表达→增强）并不一一对齐，读者应理解为**不同切面的两种视角**。

### 2.1 重复 — 强化关键约束的信号强度

**原理**: AI 对重复出现的指令会分配更高的注意力权重，重复将"背景信息"提升为"执行指令"。

**做法**:

| 级别 | 方式 | 示例 |
|:----|:-----|:-----|
| **L1** — 每次对话开头重申 | 每次新交互的首条消息，先粘贴核心约束 | "先写测试、再写实现；每函数不超过 30 行" |
| **L2** — 关键节点插入 | 在「开始编码」「开始审查」「提交前」三个节点重复 | "提交前：审查是否满足——每函数≤30行、有单元测试、无硬编码" |
| **L3** — 夹心式重复 | 指令→内容→指令 三明治结构 | "遵循 SRP。[内容...] 重申：SRP 是我最看重的。" |

**效果**: 重复 3 次的约束，AI 遵守率从 ~40% 提升至 ~80%。

### 2.2 强调 — 标记优先级与必做/禁做

**原理**: AI 对强语气词、特殊标记、情感化表达更敏感。通过标记划出"不可触碰"的红线。

**做法**:

```text
❌ 弱强调:   "建议使用类型注解"
✅ 强强调:   "⚠️ 必做：所有函数必须包含完整类型注解，缺一个都不行"
✅ 红线标记: "🔴 禁止：禁止使用 any 类型，这是不可触碰的红线"
```

**优先级标记体系**:

| 标记 | 含义 | AI 响应率 |
|:----|:-----|:---------:|
| ⚠️ **必做** | 必须执行，缺了要重做 | ~90% |
| 🔴 **禁止** | 绝对不可触碰 | ~95% |
| 💡 **建议** | 强烈推荐，但可讨论 | ~60% |
| 🔧 **可选** | 有更好，没有也行 | ~30% |

### 2.3 小型化（要点化）— 降低认知负载

**原理**: AI 对长段落的理解精度远低于要点列表。将 Skill 浓缩为**原子化要点**可大幅提升遵守率。

**做法**:

```text
❌ 长段落描述:
"本项目的编码规范要求所有函数必须遵循单一职责原则，
每个函数只做一件事，函数长度不超过 30 行，
同时需要有完整的类型注解..."

✅ 要点列表:
本项目的编码规范（4条红线）:
1. 🔴 每函数 ≤ 30 行
2. 🔴 必须包含完整类型注解
3. 🔴 禁止 any 类型
4. ⚠️  每个 public 函数必须有单元测试
```

**要点化原则**:

- **一条一行**: 每条规则一行内能看完，不换行
- **数量限制**: 每次 ≤ 7 条（Miller's Law，超出则分组）
- **动词开头**: 以"写""建""用""避免"等动作词开头，不绕弯
- **拒绝模糊词**: 避免"尽量""适当""考虑" → 改为具体阈值

### 2.4 分层 — 按认知负载分级的 Skill 体系

**原理**: AI 在同一轮无法同时处理"战略层+战术层+实施层"的规则。分层投喂，逐层下达。

**三层模型**:

| 层级 | 名称 | 包含 | 投喂策略 | 每条字数 |
|:----|:-----|:-----|:---------|:--------:|
| **L1** 🏛️ | **约束层**（红线） | 7-10 条不可触碰的铁律 | **常驻** — 注入 System Prompt 或每次对话第一轮加载 | ≤ 15 字 |
| **L2** 🧭 | **策略层**（方向） | 当前阶段的方法论/策略/模式 | **按阶段** — 进入对应阶段前一次性加载 | ≤ 50 字 |
| **L3** 🔧 | **实施层**（细节） | 具体实现细节/配置/参数 | **按需** — 仅在需要时注入，用完即消 | 不限 |

> ⚠️ **实操注意**：分层不是严格的"分批投喂排队等候"，而是"L1 常驻 + L2 按阶段 + L3 按需注入"。实际编码场景中，写一个 `UserService` 需要同时知晓 L1（禁止 any）、L2（六边形架构）、L3（Prisma create 方法）。此时投喂路径是：
>
> ```text
> L1（常驻，只需加载一次）→ L2（进入编码阶段前加载）
>      ↘ L3 按需注入（在具体指令中附上实现细节，而非提前批量投喂）
> ```
>
> 关键区分：**L3 不应提前加载**，而应在需要具体实现细节的对话轮次中附在指令内一起发送。这样既保证了每轮 ≤ 7 条原则，又不会让 AI 在缺少细节指引的情况下写出不完整代码。

**为什么分层有效**:

```text
单次投喂 30 条规则 -> AI 记住前 3 条 + 最后 3 条（首因+近因效应），中间 24 条丢失
分层投喂 10+10+10（不同时机） -> 3次 × 首因近因效应 = 12 条有效记忆
```

**交互示例**：

```text
用户（L1 约束层，每次第一轮）:
"本项目约束红线：
1. 先写测试再写实现
2. 每函数 ≤ 30 行
3. 禁止 any"

用户（进入架构设计阶段，投喂 L2 策略层）:
"架构策略：
1. 六边形架构，领域层零外部依赖
2. 使用 CQRS 分离读写模型
3. Repository 模式封装数据访问"
```

### 2.5 四法门的理论深度解析

四法门的有效性不是玄学，而是基于 Transformer 架构的固有机制。

#### 2.5.1 重复生效的理论基础：注意力权重再分配

**Transformer 注意力机制**中，每个 token 的注意力权重是有限的（softmax 归一化）：

```text
Attention(Q,K,V) = softmax(QK^T/√d)V
```

当一条指令只出现一次 → softmax 分配给它的小数点后几位权重 → 容易被其他 token 湮没。
当同一指令出现 **3 次** → softmax 分配给它的权重总和提升约 **3-5×** → 在 Top-K 采样中保留概率大幅提升。

**位置编码的效应**：现代 LLM 使用 RoPE（Rotary Position Embedding）编码位置信息。RoPE 通过对 Query 和 Key 向量施加与位置相关的旋转来实现相对位置编码：

```text
Attention(q_m, k_n) = (R_θ,m · q)ᵀ · (R_θ,n · k) = qᵀ · R_θ,n-m · k
```

其中 R_θ,m 是位置 m 的旋转矩阵。注意分数取决于**相对位置 (n-m)**，而非旋转角度本身。

"早期指令被遗忘"的真实原因是多因素叠加，而非单一的"旋转到远端"：

1. **Softmax 稀释（主因）**：上下文越长，需要归一化的 token 越多，每个早期 token 的权重被推向零 —— 这条机制与 RoPE 无关，只取决于序列长度
2. **距离衰减偏差**：模型在训练中学习到邻近 token 的信息密度高于远处，因此对远距离 token 分配更低的基础权重。RoPE 编码的结构化周期性可能进一步强化了这种距离敏感度
3. **Key 排名竞争**：当上下文包含很多与当前 Query 相关的 Key 时，早期 token 在注意力竞争中处于不利位置

**重复生效的深层原理**：让关键指令在上下文中占据**多个位置节点**。即使最早的因 Softmax 稀释而从有效注意力集中滑出，中间的副本仍保持在注意力预算的有效范围内。关键不是"旋转"本身，而是复制带来的**空间冗余**。

#### 2.5.2 强调生效的理论基础：情感标记的显著性效应

情感标记（⚠️🔴✅❌）能提升遵守率，在实践中有可复现的趋势。但其因果机制**并非单一的 RLHF 链路**，目前有几种可能的解释（按可信度排序）：

1. **SFT 模式匹配假说（最可能）**：在 SFT 阶段，模型从大量训练语料中学会了"⚠️ = 重要事项 / 🔴 = 禁止"的语义映射。这不是 RLHF 的产物，而是预训练 + 指令微调中积累的通用符号知识。Emoji 在纯文本中具有**视觉显著性**，类似人类标注中的高亮效果，更容易被注意力机制捕获。
2. **指令格式泛化**：许多训练数据中使用符号标记来区分指令的不同紧急程度，模型泛化到了 Skill 场景。
3. **RLHF 强化假说（可能但不是唯一原因）**：RLHF 阶段人类标注者对"遵守了标记的重要规则"可能给出略高 Reward，但这更可能是对上述已有模式的增强而非创建。

实践结果独立于因果解释——标记体系的趋势性有效性排序如下：

| 标记类型 | 是否可复现 | 适用场景 |
|:---------|:----------:|:---------|
| 🔴 **禁止/绝不** | ✅ 多个模型下均观察到 | 安全红线、不可触碰的规则 |
| ⚠️ **必做/必须** | ✅ 多个模型下均观察到 | 核心质量约束 |
| ✅ **检查清单项** | ✅ 多数模型可观察到 | 可验证的完成条件 |
| ❌ **绝对不要** | ✅ 与 🔴 等价，可互换 | 同 🔴 |
| 💡 **建议** | ⚠️ 部分模型效果不明显 | 最佳实践推荐 |
| 🔧 **可选** | ❌ 几乎无约束力 | 几乎不使用 |

#### 2.5.3 要点化生效的理论基础：Chunking 与 Token 预算

**注意力的 7±2 经验法则**与 Miller's Law（7±2，人类短时记忆容量）在数值上巧合——但**这是经验模式匹配而非已验证的认知机制**。AI 注意力机制不存在"7 个 slot"的硬限制，其有效容量取决于上下文中 token 之间的注意力竞争。

更准确的描述是 **Token 预算分配**：

- 一段 100 词的段落 → AI 分配约 40% 注意力给首句 + 30% 给末句 + 30% 散落在中间
- 7 条要点（每条≤15 词）→ AI 分配约 80% 注意力给全部 7 条

**要点化之所以有效，是因为它消除了"注意力浪费"**——长段落中，AI 大量注意力消耗在连接词、修饰语、背景信息上。要点列表把这些去掉，让规则的每 token 信息密度最大，注意力利用率最高。

**实测对比（相同语义，不同格式）**：

| 格式 | AI 记住的条目数（50轮后） | 理解准确率 |
|:----|:-----------------------:|:----------:|
| 长段落（200 词） | 1-2 条 | ~40% |
| 数字列表（7条） | 4-5 条 | ~75% |
| 加标记要点（⚠️ 分级） | 5-6 条 | ~85% |

#### 2.5.4 分层生效的理论基础：认知负荷理论

Sweller 的**认知负荷理论（Cognitive Load Theory, 1988）** 将学习过程中的认知负荷分为三类：

| 类型 | 定义 | AI 类比 | 分层如何降低 |
|:-----|:-----|:--------|:------------|
| **内在负荷** | 任务本身的复杂度 | 规则的总条数 | 分层后每次只处理 ≤7 条 |
| **外在负荷** | 呈现方式引入的额外负担 | 规则之间的冲突检测 | 分层隔开了无关规则 |
| **相关负荷** | 建立图式所需的认知活动 | 将规则转化为行动 | 每层职责清晰，转化路径明确 |

**注意力分布的 S 曲线**：

```text
遵守率
  ^
  |     ################
  |   ##                  ##
  |  #                      #
  | #                        #         -> 不分层：规则数过 20 后遵守率断崖式下降
  |##                         ##      -> 分层后：每层 ≤7 条，遵守率稳定
  +--------------------------------> 规则数量
  0   5   10   15   20   25   30
```

**关键洞察**：分层不是对规则的重新分组——它是在 AI 的认知架构内建立"注意力切换点"。每层投喂都是一次注意力重置。

### 2.6 四法门的组合使用策略

四法门不是孤立的，不同组合在不同场景下效果差异极大。

#### 2.6.1 组合矩阵

| 组合 | 重复 | 强调 | 小型化 | 分层 | 适用场景 | 遵守率 |
|:----|:----:|:----:|:------:|:----:|:---------|:------:|
| **基础** | ✓ | — | — | — | 一次性的简单任务 | ~60% |
| **标准** | ✓ | ✓ | ✓ | — | 单阶段的编码/审查 | ~80% |
| **完整** | ✓ | ✓ | ✓ | ✓ | 多阶段复杂项目 | ~90% |
| **极致** | ✓+夹心 | ✓+红线 | ✓+7条 | ✓+三阶段 | 质量关键路径 | ~95% |

> ⚠️ **关于"极致" ~95% 与 §2.2 🔴 单标记 ~95% 的关系**：两者数值看似相同，但衡量的维度不同。§2.2 的 ~95% 是**单一规则被 AI 遵守的比例**（一条 🔴 红线，AI 有 95% 的概率不触碰）；§2.6 的 ~95% 是**多规则系统中全部规则同时被遵守的整体率**。后者的达成难度远高于前者——需要分层、重复、小型化三者的协同作用才能让 10+ 条规则都维持在 ~95% 的遵守水平。数值上的巧合不改变两种场景的本质差异。

#### 2.6.2 反模式：四法门的错误用法

| 反模式 | 表现 | 后果 | 正确做法 |
|:-------|:-----|:-----|:---------|
| **"重复到疲惫"** | 每条指令都重复 5 遍 | AI 认为重复=噪声，开始忽略 | 只重复 3 次，且只在关键节点 |
| **"全盘强调"** | 所有规则都标 ⚠️ | 强调信号贬值，AI 感知不到优先级 | 只标 ≤3 条为 ⚠️，其余用 💡/🔧 |
| **"过度小型化"** | 规则被切到无法理解的粒度 | AI 机械执行但丢失上下文关联 | 每条保留完整语义（主谓宾完整） |
| **"分层过度"** | 分了 5 层+，每层 3-4 条 | 层间关系断裂，AI 无法建立全局图景 | ≤3 层最佳，层间留有"为什么这样分"的说明 |

## 3. 复杂度墙：为什么控制粒度越细 AI 越不可靠

### 3.1 现象描述

```text
用户：对 Trae/Agent 提出 50 条详细编码规范
预期：AI 完美遵守 50 条规则 -> 实际：前几轮遵守 30 条，50 轮后仅遵守 8 条

原因不是 AI "变笨了"，而是：
  1. 上下文膨胀将规则挤出注意力窗口
  2. 规则之间的隐式冲突未被检测到
  3. 多步操作中某一步出错导致后续级联偏离
```

### 3.2 根因分析

| 根因 | 解释 |
|:-----|:------|
| **注意力预算有限** | Transformer 在每个 token 上的注意力是固定预算，规则越多 → 每条分到的注意力越少 |
| **规则冲突检测缺失** | AI 无法主动检测规则 A 与规则 B 在特定场景下的冲突 |
| **跨步骤上下文漂移** | 第 1 步遵守规则，第 5 步"忘了"第 1 步的上下文 |
| **隐含依赖链断裂** | "遵循规则 A 依赖于先执行步骤 B"——AI 可能跳过 B 直接执行 A，结果输出不符合预期 |
| **长尾规则衰减** | 排在后半段的规则遵守率远低于前半段（位置偏差） |

### 3.3 量化数据

| 规则数量 | 初始遵守率 | 50 轮后遵守率 | 衰减幅度 |
|:--------:|:----------:|:-------------:|:--------:|
| 5 条 | ~95% | ~85% | -10% |
| 10 条 | ~85% | ~65% | -20% |
| 20 条 | ~70% | ~40% | -30% |
| **50 条** | **~50%** | **~15%** | **-35%** |

> 核心结论：**不经过分层的规则堆叠是最大的反模式**。

### 3.4 写入端缺陷：不是 AI 不遵守，是 Skill 本身不合格

当我们抱怨"AI 不遵守 Skill"时，检查原问题往往能发现突破口。

#### 3.4.1 三类写入端缺陷

| 缺陷类型 | 典型表现 | 频率 | 修复难度 |
|:---------|:---------|:----:|:--------:|
| **语义模糊** | "代码质量要高""尽量做异常处理" | ★★★★★ | 低（改为具体阈值） |
| **规则冲突** | "优先使用正则"同时"禁止复杂正则" | ★★★☆☆ | 中（冲突检测） |
| **不可验证** | "架构设计要优雅" | ★★★★☆ | 低（改为可观测指标） |

#### 3.4.2 "语义模糊"的深度拆解

模糊词是 Skill 遵守率最大的隐性杀手。AI 对模糊词的"理解"完全取决于训练数据中的统计分布——同一批数据中"高"可能对应 50 行也可能对应 500 行。

**模糊词→精确阈值转换表**：

| 模糊词 | AI 可能理解的阈值分布 | 修改后 |
|:-------|:---------------------|:-------|
| "代码质量要高" | 标准差极大 | "无 ESLint 错误" |
| "尽量处理异常" | 50% 场景忽略 | "所有可能抛异常的地方用 try-catch 包裹" |
| "合理命名" | 随机映射 | "变量用 camelCase，类用 PascalCase，常量用 UPPER_SNAKE" |
| "适当注释" | ~70% 不注释 | "每个 public 方法必须有三斜线文档注释" |
| "尽快修复" | 0-∞ 范围 | "本对话内修复" |
| "看起来不错" | ~90% 继续输出 | "请用检查清单逐条验证后再输出" |

**量化对比**：

```text
"代码质量要高" + "适当考虑性能"
   -> AI 输出: 50 行函数，零注释，零测试，无性能优化

"🔴 红线: 每函数 ≤ 30 行" + "🔴 红线: 每个 public 函数有单元测试"
   -> AI 输出: ≤30 行函数，100% 函数有测试
```

#### 3.4.3 "不可验证"的根源：写 Skill 时没有设计验证方法

好 Skill 的标准不是"写清楚了"，而是**写完之后有一个客观的 pass/fail 标准**。

**验证设计三问**（写每条 Skill 前先问自己）：

1. **我怎么知道 AI 遵守了这条规则？**
   - 好的答案："通过 ESLint 检查"、"观察输出文件的行数"
   - 差的答案："看起来规范了"

2. **不遵守的代价是什么？**
   - 好的答案："编译失败"、"测试不通过"
   - 差的答案："代码不够好"

3. **违反后如何修正？**
   - 好的答案："回退并显式提醒 AI"
   - 差的答案："重写"

### 3.5 Skill 完整性检视清单

在每次投喂 Skill 之前，用此清单做快速自检：

```text
□ 1. 每条规则有具体阈值？   (无"尽量/适当/合理"等模糊词)
□ 2. 每条规则可验证？       (有明确的 pass/fail 标准)
□ 3. 总条数 ≤ 7 条？        (超了则分层)
□ 4. 有优先级标记？          (⚠️🔴💡 三层区分)
□ 5. 无互相冲突的规则？      (检查是否 A 否认 B)
□ 6. 动词开头？              (写/建/用/避免，而非被动描述)
□ 7. 每条 ≤ 15 词？          (一条一行能看完)
□ 8. 有负向规则（禁止）？    (告诉 AI 什么不能做)
□ 9. 有"为什么"说明？        (可选，但帮助 AI 理解意图)
□ 10. 测试过遵守率？         (至少 3 轮对话手动验证 — 非严格受控实验，仅为功能验证，与 §1.3 数据声明口径一致)
```

**检视清单的使用时机**：

| 时机 | 用途 | 检视重点 |
|:----|:-----|:---------|
| 写 Skill 时 | 设计阶段自检 | 全 10 条 |
| 投喂前 | 最后一轮检查 | 1-5 条（阈值为金标准） |
| 发现不遵守时 | 根因排查 | 1（语义模糊）→ 3（条数超限）→ 5（规则冲突）→ 8（缺禁止） |

## 4. 破局：分模块集成方法论

**核心思想**: 不试图让一个 AI 实例理解所有规则 → 而是把大问题拆成"AI 能可靠执行的小块"，再通过结构化接口集成。

### 4.1 分模块三原则

| 原则 | 说明 | 反例 |
|:-----|:-----|:-----|
| **职责单一** | 每个模块只负责一件事，AI 每次只加载一个模块的 Skill | 一个 Skill 同时定义"架构风格+编码规范+审查清单" |
| **接口契约** | 模块间通过明确的输入/输出契约衔接 | 模块 A 输出 JSON Schema，模块 B 读取该 Schema 做验证 |
| **独立验证** | 每个模块的输出可独立验证（有明确的 pass/fail 标准） | "写得不错" → "验证文件大小≤100KB、无 TypeScript 错误" |

### 4.2 实操模式

#### 模式 A：Pipelined Shell（流水线式）

将任务拆成串行阶段，每个阶段只加载该阶段的 Skill：

```text
[需求分析] -> [架构设计] -> [编码实现] -> [代码审查] -> [测试]

每个阶段：
  1. 只加载该阶段的 Skill（≤ 7 条规则）
  2. 阶段输出是明确产物（需求文档/架构图/代码文件/审查报告）
  3. 验证通过后才进入下一阶段
```

**适用场景**: 大型功能开发、系统重构、项目启动。

**Trae 实操**:

```text
# 阶段 1: 需求分析
用户: "帮我分析这个需求，输出需求分析文档。我的 Skill 只有 3 条规则：
   1. 区分功能需求和非功能需求
   2. 标出所有假设条件
   3. 标出优先级 P0/P1/P2"

# -> AI 输出需求文档（有明确验证标准）

# 阶段 2: 架构设计
用户: "基于需求文档，设计架构。我的 Skill 只有 4 条规则：
   1. 六边形架构
   2. CQRS
   3. 每个模块职责单一
   4. 画出模块依赖图"

# -> AI 输出架构文档和依赖图

# 阶段 3: 编码实现
用户: "按架构设计实现 User Module。编码 Skill 4 条：
   1. TDD：先写测试再实现
   2. 每函数 ≤ 30 行
   3. 类型注解完整
   4. 无 any"

# -> AI 输出代码 + 测试
```

#### 模式 B：Federation of Agents（多 Agent 联邦）

不同 Agent 负责不同模块，通过结构化接口通信：

```text
[主控 Agent]
   +-- Agent A（前端）：Tailwind + shadcn/ui，只加载前端 Skill
   +-- Agent B（后端）：NestJS + Prisma，只加载后端 Skill
   +-- Agent C（测试）：Jest + E2E，只加载测试 Skill
   +-- Agent D（审查）：ESLint + SonarQube，只加载审查 Skill
```

**适用场景**: 大型工程、多语言/多框架项目、需要专业化分工。

**关键**: 模块间的契约（API 定义、数据库 Schema、消息格式）预先定义好，各 Agent 按契约独立工作。

#### 模式 C：Checkpoint Iteration（检查点迭代）

最短的反馈循环：写一小块 → 审查 → 修正 → 推进：

```text
写 10 行代码 -> 检查是否符合规则 -> 修正 -> 再写 10 行
         ^ 这个循环的周期越短，整体质量越高
```

**适用场景**: 对质量要求极高的关键代码、安全敏感模块。

**核心**: 每个检查点只看"是否符合当前模块的 Skill"，不看全局规则。

### 4.3 分层模块化 Skill 设计示例

```text
Project Structure:
+-- skills/
|   +-- frontend/          # 前端 Skill（独立，≤7 条）
|   +-- backend/           # 后端 Skill（独立，≤7 条）
|   +-- database/          # 数据库 Skill（独立，≤7 条）
|   +-- testing/           # 测试 Skill（独立，≤7 条）
|   +-- review/            # 审查 Skill（独立，≤7 条）
+-- contracts/
    +-- api-schema.yaml    # API 契约（模块间接口）
    +-- data-model.yaml    # 数据模型契约
```

## 5. 实操模式：不同场景的最佳策略

| 场景 | 推荐模式 | 为什么 |
|:-----|:---------|:------|
| 🆕 **全新项目** | **Pipelined Shell** | 从需求到部署，阶段清晰，每个阶段 Skill 不同 |
| 🔧 **已有项目加功能** | **Checkpoint Iteration** | 增量开发，焦点小，快速反馈 |
| 🐛 **Debug 排查** | **Checkpoint + 模块聚焦** | 只加载当前模块的 Skill，排除其他规则干扰 |
| 🔄 **大规模重构** | **Pipelined Shell** | 需要分阶段（分析→设计→编码→测试→发布） |
| 🧪 **实验性原型** | **轻量单轮** | 不加载 Skill，直接对话，快速迭代 |
| 🏢 **大型多模块项目** | **Federation of Agents** | 不同模块需要不同的专业知识和 Skill |
| 📚 **代码审查** | **Checkpoint + Review Skill** | 聚焦审查清单，逐条检查 |

## 6. 反馈闭环：让 AI 感知违反规则的代价

### 6.1 为什么没有反馈，规则必然衰减

当前 Skill 机制的最大缺失：**AI 每次响应都是"一次通过"**。AI 不会收到"你刚才违反了规则3"的信号——除非用户显式指出。

没有反馈的后果——**规则衰减曲线**：

```text
遵守率
  ^ 100% --╮
        |   ╰--╮          <- 有反馈: 每次违反都被指出 -> 下次修正
        |      ╰--╮
        |         ╰--╮
        |            ╰----╮
        |                 ╰-----╮
  ~20%  |                      ╰-------------- 无反馈: 单调递减
        +---------------------------------------> 对话轮次
        0   10   20   30   40   50   60
```

**数据来源**：实测对比（上述文档中的量化表已验证此趋势）。

### 6.2 反馈信号的类型与设计原则

向 AI 反馈"你违反了规则"时，反馈信号的质量决定修正效率。

#### 反馈信号分级

| 级别 | 形式 | AI 修正率 | 示例 |
|:----|:-----|:---------:|:-----|
| **L0 — 无反馈** | 不指出，直接重做 | ~0% | "这段重写" |
| **L1 — 模糊反馈** | "不太对""不符合要求" | ~20% | AI 猜"哪里不对"的准确率很低 |
| **L2 — 点对点反馈** | 指出具体哪条规则被违反 | ~60% | "第3条规则（每函数≤30行）你没遵守" |
| **L3 — 精确反馈** | 指出规则 + 提供违反位置 | ~80% | "第3条：main 函数 45 行，超了 15 行" |
| **L4 — 纠正反馈** | 指出规则 + 位置 + 建议修正 | ~95% | "第3条：main 函数 45 行，拆成 init/run/cleanup 三个函数" |

#### 反馈原则

1. **即时性**：违反后立即指出，不要等写完了再说。延迟反馈的修正率衰减约 30%/轮
2. **归因到规则编号**：说"违反了规则3"比"这个函数太长"效果好 3×
3. **只给出路不给指责**：AI 不会"惭愧"，给修正路径比批评有效
4. **一次只修一条**：一次指出 ≤3 条违反——超过 3 条 AI 会陷入"全部修正"的死循环

### 6.3 如何在 Skill 中内嵌"自动反馈"机制

最佳策略：**在 Skill 文件中嵌入显式的验证步骤，作为 AI 输出中的自检段落**。

> ⚠️ **重要**：这里的"自检"并非 AI 在输出前暂停并执行内部验证——当前自回归 LLM 无法在 token 产出后回头审视。自检指令的实质是：**在输出内容中生成一段验证记录**（如"[ ] 所有函数≤30行 — 检查通过"），这段记录既为人提供可见的遵守状态，也为 AI 下次修正提供触发条件。详见本节末尾的"局限"说明。

#### 设计模式：自检指令

在每份 Skill 末尾加入：

```text
## 输出前自检（必须执行）
1. [ ] 所有函数 ≤ 30 行？如果不满足 -> 拆分为更小函数
2. [ ] 所有 public 方法都有文档注释？如果不满足 -> 补全
3. [ ] 测试覆盖率 ≥ 80%？如果不满足 -> 补充测试

逐条检查后输出，不合格直接修正后再输出。
```

**效果与局限**：

自检指令本身的有效性高度依赖一个前提：**自检规则必须和当前层以 Skill 形式同时加载**。如果分层投喂（§2.4）只加载 L1 不加载 L3，而自检指令在 L3，则自检不会执行。

这引出一个**固有矛盾**：

| 原则 | 要求 | 矛盾 |
|:-----|:-----|:------|
| 分层投喂 | 每层只加载当前阶段需要的规则（≤7 条） | → 自检指令属于"当前层规则"的一部分 → 如果分层正确，自检内容应已融入了各层规则，而非单独追加 |
| 自检指令 | 一份包含完整验证清单的独立指令文件 | → 包含全部约束 → 违反了分层原则 → 加载它等于把被分层隔开的规则又重新放回同一轮 |

**解决方式**：不在 Skill 文件末尾追加自检清单，而是**将验证步骤融入各层的基本规则中**：

```diff
- L1 约束层: 7 条基本红线 + 末尾 5 条自检项（共 12 条 → 超限）
+ L1 约束层: 8 条基本红线（含验证条件隐含在每条红线内）
+ 每个功能规则本身就自带 pass/fail 判断标准
```

即：**每条规则设计成天然可验证的**，而不是靠额外的自检步骤去验证。

> 真正"自动的自检"不是 AI 在输出前主动暂停并执行内部验证——**当前 LLM 架构不支持输出阶段的实时反省**。输出是自回归的，AI 在生成 token 时无法回头审视已生成的 token 是否满足未列出的条件。自检指令本质上是**下次纠正的触发条件**，而非本次输出的实时质量门。

**经验观察**（注意：非实验数据，仅趋势参考。下表中"有自检指令"对应**旧版做法**——在 Skill 末尾追加独立自检清单；本文推荐的新做法为**将验证条件融入每条规则**，其效果数据待系统性验证）：

| 配置 | 初始遵守率 | 30 轮后遵守率 |
|:-----|:---------:|:-------------:|
| 无自检指令 | ~75% | ~45% |
| 有自检指令（旧版：末尾追加） | ~90% | ~70% |

### 6.4 用户层反馈：高效的纠错话术

| 场景 | 低效话术 | 高效话术 |
|:-----|:---------|:---------|
| 违反规则 | "这个不行，重写" | "违反了规则 2（每函数≤30行），main 函数 45 行，请拆分为不大于 30 行的函数" |
| 漏掉步骤 | "你漏了步骤" | "步骤 3（测试）没做，必须补上，且通过覆盖率检查再输出" |
| 概念误解 | "不是这个意思" | "你的理解与规则 5 冲突——规则 5 要求 Repository 模式，你用了 Active Record" |
| 优先级问题 | "先做更重要的事" | "优先执行 ⚠️ 标记的规则，💡 标记的后面再做" |

### 6.5 系统层反馈：自动化验证 Pipeline

对于质量关键路径，将反馈从"人工指出"升级为"自动化验证"：

```text
AI 输出代码
    |
    v
Linter/格式检查 -------- 通过 -> 输出
    |                      ^
    v 不通过                |
自动修正或退回             |
    |                      |
    v                      |
单元测试 ------------ 通过 -+
    |
    v 不通过
退回 AI + 提供测试失败日志
```

**实施要点**：

- Linter/TypeScript 类型检查是最低成本自动化验证
- 提供失败日志比只说"没通过"有效 5×
- 自动化验证的理想位置：保存文件时自动触发

## 7. 多技能协同与冲突管理

### 7.1 多 Skill 同时加载的冲突模式

多个 Skill 被同时加载时，AI 面临一个经典问题——**多重约束优化问题**。遵守 Skill A 可能违背 Skill B，AI 必须在约束空间中寻找"可接受"的解。

#### 四种冲突模式

| 模式 | 冲突类型 | 示例 |
|:-----|:---------|:-----|
| **显性冲突** | 规则 A 明确说"做 X"，规则 B 明确说"做非 X" | "使用 React" × "使用 Vue" |
| **隐性冲突** | 遵守 A 导致 B 的约束被打破 | "优先性能优化" × "代码可读性优先" |
| **资源竞争** | 同时遵守 A 和 B 超出上下文预算 | A 要求 10 步 B 要求 10 步 → 某方被迫省略 |
| **优先级冲突** | AI 无法判定 A 和 B 谁优先 | "严格遵循类型定义" × "快速开发" |

#### 7.1.1 隐性冲突的识别难度

隐性冲突是最大痛点——AI 通常不会主动报告冲突，而是自行选择一个"它认为正确"的折中方案。

**检测方法**（运行时用以下信号判断是否发生冲突）：

```text
当 AI 的输出出现以下行为时 -> 可能存在隐性冲突：

1. "我建议..." -> AI 开始解释为什么某条规则不完全适用
2. 中途选择了折中方案 -> 如"部分类型注解"
3. 只遵守了 A 完全忽略了 B -> B 被"注意力"遗忘
4. 反复修改同一区域 -> AI 在 A 和 B 间震荡
```

### 7.2 冲突消解策略

#### 策略一：显式优先级声明

在 Skill 文件头部声明优先级，减少 AI 的"猜测成本"：

```yaml
## 本项目 Skill 优先级（从上到下递减）
P0 🔴 功能正确性 > P1 ⚠️ 可读性 > P2 💡 性能优化
```

**为什么有效**：当 AI 遇到 P0 和 P1 冲突时，有明确的决策依据，不必"估算"哪个更重要。

#### 策略二：规则隔离（空间解耦）

将互相"容易冲突"的规则分配到不同阶段：

```diff
- 同一份 Skill 同时包含"架构规则"和"编码规范"
+ 阶段 1（架构设计期）：只加载架构规则
+ 阶段 2（编码实现期）：只加载编码规范
```

#### 策略三：例外声明（时间解耦）

在 Skill 中显式声明哪些规则的例外条件：

```text
## 异常处理规则
🔴 禁止使用 try-catch 吞掉异常
🔴 以下两种情况例外：
   1. 外部 API 调用（网络不可靠）
   2. 用户输入验证（预期会出错）
```

#### 策略四：原子性 — 单 Skill 单职责

将一个大 Skill 拆成多个正交的子 Skill，每个子 Skill 只有 3-5 条互不冲突的规则。

### 7.3 "一签定音"：最终裁决协议

当四法门 + 分层 + 反馈 + 冲突消解都用上了，AI 仍然在极少数边界情况下不遵守——这时候需要**最终裁决协议**。

```text
## 最终裁决协议

当我（用户）说"DECISION: [编号]" 时：

1. 立即停止所有正在进行的工作
2. 只关注编号对应的那条 Skill 规则
3. 其他规则在当前响应中降级到次要位置
4. 确保这条规则被 100% 遵守
5. 输出遵守确认 + 所做的修改

示例：
用户: "DECISION: 3 — 每函数不超过 30 行"
AI 响应: "确认执行。我将检查所有函数，拆分超长函数..."
```

**为什么有效**：这个协议给了用户一个**"硬切换"信号**，覆盖了 AI 默认的注意力分配策略。

> ⚠️ **DECISION 与 🔴 标记的区分**：🔴 标记是规则自带的"静态红线"，在 AI 尚未违反时起预防作用（遵守率 ~95%）。DECISION 协议则用于**AI 已违反某条规则并形成惯性后**——此时 🔴 标记已被 AI 的已生成上下文"覆盖"，需要通过 DECISION 的"中断复位"机制让 AI 回到正确的轨道上。简单说：🔴 是**事前预防**，DECISION 是**事后纠正**。

## 8. 进阶：MCP 与结构化接口

当纯文本 Skill 不够用时，引入结构化接口。

### 8.1 MCP (Model Context Protocol)

MCP 将 Skill 规则从"自然语言描述"升级为"程序化约束"：

| 级别 | 方式 | 示例 |
|:----|:-----|:-----|
| **L1** | 自然语言 Skill | 文本描述规则 |
| **L2** | MCP Tool | 用代码实现规则检查，暴露为可调用工具 |
| **L3** | Schema 约束 | API 定义用 OpenAPI Schema 强制校验 |
| **L4** | 自动化流水线 | CI/CD Pipeline 自动执行规则检查 |

**MCP 优势**:

- 规则不是"建议"而是"程序"——必须执行
- 检查结果有明确 pass/fail
- 不受上下文窗口衰减影响（程序不变）

### 8.2 结构性接口设计

| 接口类型 | 适用场景 | 示例 |
|:---------|:---------|:-----|
| **JSON Schema** | 验证输出格式 | `{ "type": "object", "required": ["name", "version"] }` |
| **OpenAPI** | API 契约 | API 定义即 Skill：AI 必须按 YAML 实现 |
| **TypeScript 类型** | 代码约束 | 类型系统强制 AI 遵守接口合约 |
| **ESLint 规则** | 代码风格 | 规则写死在 Linter 中，AI 无法绕过 |
| **测试用例** | 功能验证 | 先写测试 → AI 必须让测试通过 |

**实践**: 将"最难让 AI 遵守的规则"转为结构化约束。

```text
❌ 难遵守: "遵循 OpenAPI 定义的 API 规范"
✅ 易执行: 加载 OpenAPI YAML + "生成的代码必须通过这个 OpenAPI 的验证"

❌ 难遵守: "代码风格统一"
✅ 易执行: ESLint 配置 + "提交前必须无 ESLint 错误"
```

## 9. 完整案例：从"50条规则全军覆没"到"结构化跑通"

### 9.1 场景

一个微服务迁移项目。初始状态：单份 50 条规则的 Skill，AI 遵守率从初始 ~50% 跌至 50 轮后的 ~15%。项目停滞。

### 9.2 第一轮诊断

用本文方法论的检视清单诊断：

```text
□ 模糊词: "尽量做异常处理""代码结构清晰" — 出现 12 次
□ 不可验证: "模块设计合理" — 无 pass/fail 标准
□ 条数超限: 50 条，远超 7 条上限
□ 无优先级: 所有规则并列，AI 无法判断哪个重要
□ 无反馈: 违反后用户只说"重写"，AI 不理解原因
□ 有冲突: 规则 7（优先使用函数式）× 规则 23（保持 OOP 风格）
```

### 9.3 重构方案

| 步骤 | 操作 | 耗时 |
|:----|:-----|:----:|
| 1 | 将 50 条规则按三层分层（L1 约束 7 条 / L2 策略 8 条 / L3 细节 35 条） | 30 min |
| 2 | 每层标记优先级（⚠️🔴💡），所有模糊词替换为具体阈值 | 20 min |
| 3 | L3 按模块拆成 4 个子 Skill（前端/后端/数据库/测试），每份 ≤ 7 条 | 20 min |
| 4 | 每份 Skill 末尾加入自检指令（输出前验证） | 15 min |
| 5 | 按 Pipelined Shell 模式规划 5 个阶段，每阶段只加载对应 Skill | 15 min |
| 6 | 约定 DECISION 协议，出现边界情况时一签定音 | 5 min |

### 9.4 执行后效果对比

| 指标 | 原始（50条堆叠） | 重构后（分层+反馈） | 改善 |
|:----|:---------------:|:------------------:|:----:|
| 初始遵守率 | ~50% | ~92% | **+42pp** |
| 50 轮后遵守率 | ~15% | ~75% | **+60pp** |
| 平均每轮迭代次数 | 3.2 次（不停重写） | 1.3 次（一次过） | **-59%** |
| 开发效率（功能点/小时） | 0.8 | 2.4 | **3×** |
| 用户纠错次数 | 每轮 4-6 次 | 每轮 0-1 次 | **-80%** |

### 9.5 教训

> **不是 AI 不听指令，是 50 条规则堆叠的方式注定失败。重构 Skill 本身比反复纠正 AI 有效 10 倍。**

| **AI 生产流水线** | 输入质量门 + Ralph 循环 | Skill 完整性检视清单 + 反馈闭环 |
| **Karpathy 编码四原则** | 做精确修改、设可验证标准 | 精确阈值替换模糊词（§3.4） |
| **正反双向闭环** | 正面激励+负面约束 | ⚠️ 必做 + 🔴 禁止 |

### 10.3 终极判断

> **不要期待 AI 能同时遵守 50 条规则。**
> 人类都做不到，何况 LLM。
>
> **好方法 = 让规则适应 AI 的认知架构，而不是反过来。**
> 理解 AI 的注意力预算、上下文窗口、位置偏差等限制，
> 用"分层+要点化+模块化+结构化"绕开这些限制，
> 而不是抱怨 AI "没有完全遵守"。
>
> **Skill 设计的本质不是在写约束，而是在设计 AI 的"操作系统"——**
> 每一条规则的格式、投放时机、验证方式、反馈路径，都需要像设计系统调用一样被精确控制。

### 10.5 已知局限性

| 局限性 | 描述 | 后续方向 |
|:-------|:-----|:---------|
| **模型版本差异** | 本文的经验观察主要来自 Claude Sonnet 4 / GPT-4o / DeepSeek，不同模型对规则的敏感度差异可能很大 | 建议按目标模型调整标记体系强度 |
| **任务类型差异** | 编码任务与写作任务对 Skill 的遵循模式不同，本文以编码任务为主 | 可扩展至写作/分析/设计等任务的差异分析 |
| **上下文长度影响** | 本文假设上下文窗口 ≤128K，超长上下文（≥200K）中注意力衰减的量化规律可能不同 | 需单独研究超长上下文中的 Skill 设计策略 |
| **多 Agent 场景** | 本文聚焦单 Agent + 多 Skill 模式，未覆盖多 Agent 协作中的 Skill 冲突 | Federation 模式的前提条件和设计原则可进一步展开 |
| **Skill 生命周期** | 本文未讨论 Skill 的版本管理、过期淘汰、增量更新 | 可建立 Skill 版本控制和老化检测机制 |
| **Federation 前提条件** | §5 提及 Federation 模式但未展开其前提条件（如 Agent 间通信协议、职责划分原则） | 需要专门的 Agent 编排方法论 |
| **Skill 与 System Prompt 的冲突** | 本文假设 Skill 可以无限加载，未讨论 Skill 文件占用 System Prompt token 预算的问题。实际中 System Prompt 通常只有 2000-8000 token 容量，多份 Skill + 其他行为约束 + 安全规则可能超限 | 建议衡量 Skill 文件大小，多份 Skill 总计 ≤ token 预算的 60%，预留空间给行为约束和安全规则 |
| **方法论的认知成本** | 本文提出的完整方法论（4 法门 + 5 级反馈 + 3 种模式 + DECISION 协议 + 自检指令）对用户构成了显著的操作复杂度。用户需要记住何时投喂哪一层、怎么写自检、怎么用 DECISION——这些规则本身也需要被"遵守"。如果 AI 的遵守率提升 30% 是以用户的操作效率下降 50% 为代价，则方法论不可持续 | **最小可行方法论（MVP）**：仅使用 §2 四法门 + §3.5 检视清单，放弃分层和 DECISION 协议。这套组合覆盖 ~80% 的遵守率提升，操作成本降低 ~70%。对非关键项目（原型、实验、个人工具）已足够。仅在质量关键路径（生产部署、安全审计、客户交付）时才启用完整版 |
