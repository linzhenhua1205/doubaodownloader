## §0 执行摘要

**问题**：当前工程规模多大？如何从轻量级（降 token、适配低 bit 模型）到强化级（导入新 AI 技术）全谱系实施？

**核心结论**（一句话）：本工程是"**小代码、大知识、重会话**"结构——真正的资产是 3,258 个知识文件与 337 个会话（text 总量 247MB），而 2.2GB 向量库是**空转资产**（embedding 从未启用）；降 token 的下一步不是继续压缩提示词，而是**激活检索、路由与门控**三个"结构性杠杆"。

**规模体检一句话**：

| 维度 | 实测 | 判定 |
|:-----|:-----|:-----|
| 知识资产 | 3,258 文件 / 125MB / 247MB 文本 chunk | 🟢 健康（核心资产） |
| Skills | 106 个 / desc 6,680 tok（已压 33%） | 🟡 仍可再压 |
| 系统提示词 | 15,640 tok（AGENT+USER+RULE+MEMORY+固定） | 🟡 可再压至 ~9K |
| 记忆库 | 2.2GB index.db / 130,814 chunks / **embedding=0** | 🔴 空转（98% 是 FTS） |
| 会话日志 | 56MB / 591 文件 | 🟢 已导出压缩 |

**ROI 排序**（按收益/成本）：

| 优先级 | 动作 | 预估收益 | 成本 |
|:------:|:-----|:---------|:-----|
| P0 | 系统提示词再压缩（§3.1） | -40% 基础 token | 低（半天） |
| P0 | Skills 二级化落地（§3.2） | -30% desc token | 低（1 天） |
| P1 | 启用 embedding 检索（§4.1） | 高价值知识命中率 +N 倍 | 中（¥30-60 一次性） |
| P1 | 意图路由 + 工具修剪（§4.2-4.3） | -50~80% 无效 token | 中（2-3 天） |
| P2 | 成本门控 + 会话合并（§4.4） | 防失控 + -30% 重复 | 中 |
| P3 | 小模型路由 + 知识图谱（§5） | 长期架构红利 | 高（数周） |

## §1 工程规模体检（2026-08-14 实测基线）

### 1.1 五大资产盘点

```text
Project Panorama (measured 2026-08-14)
+-- knowledge/     125MB  | 3,258 .md     <- core knowledge assets (structured)
+-- skills/         42MB  | 106 skills    <- capability encapsulation (98 compressed desc)
|     +-- scripts: 263 .py
+-- scripts/        33MB  | 503 .py       <- engineering tools (check/govern/generate)
+-- memory/        2.2GB  | index.db      <- memory index (see 1.3 key finding)
|     +-- daily memory: ~30-70KB/day
+-- conversation-log/  56MB | 591 files   <- raw session logs (337 parsed/exported)
```

| 资产 | 规模 | 质量 | 说明 |
|:-----|:-----|:-----|:-----|
| 知识库 | 3,258 文件 / 125MB | 🟢 | 7 大模块，index/log 三件套治理中 |
| 技能库 | 106 个（一级 98） | 🟡 | desc 已压缩 33%，仍有二级化空间 |
| 工具脚本 | 766 个 .py | 🟢 | 503 检查类 + 263 技能内 |
| 记忆索引 | 2.2GB / 130,814 chunks | 🔴 | 文本 FTS 有效，向量空转 |
| 会话日志 | 56MB / 337+ 会话 | 🟢 | 已按月导出 + gzip 压缩 |

### 1.2 Token 消耗结构

**当前每次会话固定开销**（token-context-daily.csv 实测）：

| 组件 | Token | 占比 | 可压缩空间 |
|:-----|:-----:|:----:|:-----------|
| AGENT.md | 398 | 2.5% | 小（人格必需） |
| USER.md | 347 | 2.2% | 小 |
| RULE.md | 1,245 | 8.0% | **中（可精炼 30%）** |
| MEMORY.md | 5,650 | 36.1% | **大（已压 86%，可再精简）** |
| 固定 prompt | 8,000 | 51.1% | **大（工具定义/框架）** |
| Skills desc | 6,680 | 附加 | **中（二级化）** |
| **系统合计** | **~15,640** | 100% | **目标 ~9,000（-40%）** |

> **注**: 5,650 tok 的 MEMORY 已从 24KB 压到 3.4KB（-86%），但索引条目+待办+治理规则仍占大头；固定 8,000 tok 含系统框架与工具 schema，属"平台税"，但可借工具裁剪降 20-30%。

### 1.3 关键发现：向量索引是"空转资产"

**实测**：`memory/long-term/index.db` 2.2GB，130,814 个 chunk，但 `embedding` 字段**全为 0**——即**从未启用向量检索**，当前 2.2GB 中绝大部分是 FTS5 全文索引（trigram）与文本存储。

**含义**：
- ✅ 全文检索（keyword）一直在工作——RULE 中"检索 keyword-only"是当前实际模式
- ⚠️ 2.2GB 磁盘开销几乎全部服务于 keyword 检索，**性价比存疑**
- 🔑 高杠杆动作：**启用 embedding（¥30-60 API 成本）**，让 130,814 chunks 真正可语义检索——知识命中质量跃升
- 🔧 或反向优化：若坚持 keyword-only，可考虑精简 index.db 保留策略（重建时仅索引高价值模块）

## §2 全谱系实施框架：L0~L4 五级

```text
L0 minimal     L1 light opt      L2 arch harden    L3 smart enhance   L4 frontier
+-- min prompt +-- compress+2nd  +-- retrieval on  +-- small-model rt +-- knowledge graph
+-- zero tools  +-- memory tiers  +-- intent route  +-- KV Cache       +-- agent orchestration
+-- single mdl  +-- low-bit adapt +-- tool trim     +-- long context   +-- self-evolution
+-- basic chat  +-- cost logging  +-- cost gates    +-- multi-model    +-- meta-learning
```

| 级别 | 目标 | 核心手段 | 适用场景 | 日 token 预估 |
|:----:|:-----|:---------|:---------|:--------------|
| **L0** | 极限省 token | 精简提示词+禁用工具+单模型 | 低 bit 本地模型（7B INT4） | ~5-8K |
| **L1** | 轻量优化 | 提示词压缩+Skills 二级化+记忆分级 | 日常高频简单任务 | ~10-15K |
| **L2** | 架构强化 | 检索激活+路由+修剪+门控 | 当前主场景（当前为 L1.5） | ~15-25K |
| **L3** | 智能增强 | 小模型路由+长上下文+多模型 | 深度分析/长文档 | ~25-50K |
| **L4** | 前沿探索 | 知识图谱+Agent 编排+自进化 | 系统性知识工作 | ~50-100K |

> **现状定位**: 工程处于 **L1.5**（已有压缩、脚本治理、成本记录，但缺检索激活/路由/门控）。建议：**先落 L1 收尾（P0），再攻 L2（P1），L3-L4 按需渐进**。

## §3 L0-L1 轻量级：进一步降低 Token + 适配低 bit 模型

### 3.1 系统提示词再压缩（-40%）

**目标**: 15,640 → ~9,000 tok（省 ~6.6K/次会话，日均 30 次 ≈ 200K token/日）

**四步压缩法**：

| 步骤 | 动作 | 预估省 | 风险 |
|:----:|:-----|:------:|:-----|
| 1 | RULE.md 精炼：规则条目合并同类、去重冗长说明 | -400 | 低 |
| 2 | MEMORY.md 再瘦身：索引式（只留标题+链接，详情进 knowledge/） | -2,500 | 中（需保持检索可达） |
| 3 | 固定 prompt 工具裁剪：按场景动态加载工具定义（非全量注入） | -1,500~2,400 | 中（需 Harness 支持） |
| 4 | 技能列表改"目录+按需读"：desc 只留触发词，正文按需 read | -4,000 | 中（已部分实现） |

**关键原则**（与五技术文档一致）：
- **缓存友好优先**：system prompt 保持 prefix-stable（稳定前缀不变化），才能吃到 prompt caching -90%
- **不牺牲锚点**：身份（AGENT）、偏好（USER）、规则（RULE）是行为锚点，压缩但不可删
- **索引式记忆**：MEMORY 只放"指针"，详情全部下沉 knowledge/，检索时按需 read

### 3.2 Skills 描述瘦身与二级化

**现状**: 106 个技能 desc 共 6,680 tok（已从 17,360 压 33%）。进一步手段：

| 手段 | 做法 | 预估 |
|:-----|:-----|:-----|
| **二级化**（已建机制） | 低频技能移入 `skills/lowfreq/`，主提示只列名称，按需加载 desc | -30% desc |
| **触发词精简** | desc 只保留高区分度触发词，删冗余同义词 | -10% |
| **按域分组** | 同类技能（如 light-* 家族）合并为组技能，组内按需读 | -15% |
| **desc→YAML 化** | 用结构化字段替代长描述（name/triggers/usage） | -20% |

> 当前 `skills_config.json` 中 config desc 9,645 tok 是独立于 SKILL.md 的另一份——**两份对齐后可只留一份**，再省 ~9K。

### 3.3 上下文按需加载（记忆分级）

**核心**: 不是"把记忆全塞进上下文"，而是"按任务需要精确取用"。

```text
Memory tier loading model
+-- L0 resident: AGENT/USER/RULE/MEMORY slim (~9K)  <- every session
+-- L1 trigger:  daily memory + relevant skill body  <- by task type
+-- L2 retrieval: memory_search hit snippets         <- on-demand semantic search
+-- L3 deep read: read KB full text                  <- deep tasks only
+-- L4 full:      index-style summary (titles+links) <- rare
```

**落地**:
- 每日记忆写"摘要+关键结论"，不写全文（当前 32KB/天 偏大，目标 ≤8KB/天）
- 会话开始前**先检索再定上下文**：根据任务意图决定注入哪些记忆片段
- 长会话自动压缩：历史对话按轮压缩为结构化摘要（保留决策+结论+行动项）

### 3.4 低 bit 模型适配策略（RTX 5060 8G 跑 7B INT4）

**约束**：8GB VRAM、7B INT4（~4GB 权重）、无缓存命中（本地推理）、上下文窗口有限（通常 8-32K）。

**适配清单**：

| 维度 | 策略 | 说明 |
|:-----|:-----|:-----|
| **模型选择** | Qwen2.5-7B-Instruct INT4 / Llama-3.1-8B INT4 | 中文+工具调用均衡 |
| **量化** | GGUF Q4_K_M（~4.4GB）或 AWQ/INT4 | 8G 卡留 ~3GB 给 KV cache |
| **上下文** | 主动限制 8K（-c 8192），超长任务分段 | 7B 模型长上下文易漂移 |
| **提示词** | 用 L0 最小集（~5-8K），**禁用全部技能注入** | 本地模型吃不下 15K system |
| **工具** | 仅保留 3-5 个核心工具（read/write/bash/search） | 工具 schema 是 token 大头 |
| **知识** | 全靠 memory_search + read，不注入 index | 检索代替上下文 |
| **推理引擎** | llama.cpp / ollama / vLLM（8G 用 llama.cpp 更稳） | 支持 KV cache 量化 |
| **输出控制** | max_tokens 设上限 + 结构化输出（JSON） | 防失控循环 |

**预期效果**：本地 7B INT4 适合**高频简单任务**（问答/格式化/摘要/检索辅助），复杂深度分析仍走云端大模型——**分层路由是低 bit 落地的关键**（见 §5.1）。

## §4 L2 强化工程：架构级优化

### 4.1 检索系统激活（embedding 启用）

**现状**: 130,814 chunks 已就绪但 embedding=0，检索仅 keyword。

**实施步骤**：

| 步骤 | 动作 | 成本/收益 |
|:----:|:-----|:----------|
| 1 | 选定 embedding 模型（BGE-M3 / text-embedding-3-small） | ¥30-60 一次性 |
| 2 | 批量生成 130,814 chunks 向量（分批，约 2-4 小时） | 一次性算力 |
| 3 | 检索升级：keyword + 向量 混合（hybrid search） | 命中质量跃升 |
| 4 | 高价值模块优先（02_rd/07_industry-research 先行） | 渐进式 |

**预期收益**：
- 语义检索：不再依赖关键词精确匹配，能命中"意思相近但词不同"的知识
- 跨语言：中文 query 命中英文知识（BGE-M3 多语言）
- 记忆 recall：`memory_search` 从"猜词"升级为"理解"

### 4.2 意图路由与任务分类

**目标**: 按任务类型路由到不同处理链（小模型/大模型/脚本/直接回答），-50~80% token。

```text
意图分类器（轻量规则或小模型）
├── 简单问答   → 直接回答（不注入技能/工具）
├── 检索类     → memory_search + 摘要
├── 工具类     → 最小工具集 + 一次执行
├── 写作类     → 技能加载 + 模板
├── 分析类     → 大模型 + 深读 + 多轮
└── 维护类     → 脚本直接执行（零 LLM）
```

**落地**：
- 用规则+关键词先做（零成本），效果不足再上小分类模型
- 路由结果写入日志，用于持续优化分类边界

### 4.3 工具输出修剪与成本门控

**工具输出修剪**（-70~90%）：
- 工具返回只保留关键字段（read 截断、search 只留标题+摘要、bash 只留 tail）
- 大输出分页/摘要化：超过阈值自动截断并标注"[截断 N 行]"

**成本门控**（治理元层）：
- 单任务 token 预算：达到阈值自动暂停并报告（防失控循环）
- 单会话 token 上限：超过强制压缩上下文
- 循环检测：同一工具重复调用 N 次自动告警

### 4.4 会话管理与上下文压缩

| 手段 | 做法 | 收益 |
|:-----|:-----|:-----|
| **会话合并** | 同主题短会话合并为长会话（少次握手） | -30% 固定开销 |
| **历史压缩** | 旧轮次压缩为结构化摘要（决策+结论+待办） | 上下文 -50% |
| **断点续传** | 跨会话用 session-keeper 只传关键状态 | 避免全量重发 |
| **异步工具** | 长任务后台跑，不阻塞会话 | 减少空转 |

## §5 L3-L4 强化级：导入新 AI 技术

### 5.1 小模型路由（MoE 式分层）

**架构**：本地 7B INT4（高频简单）+ 云端大模型（深度分析）+ 专用小模型（分类/摘要/嵌入）三层路由。

| 层 | 模型 | 用途 | 成本 |
|:--:|:-----|:-----|:-----|
| L0 | 本地 7B INT4 | 问答/格式化/摘要/分类 | 零（电费） |
| L1 | 云端小模型（flash 级） | 中频任务/路由/修剪 | 低 |
| L2 | 云端大模型（pro 级） | 深度分析/长文档/规划 | 高（按需） |

**关键**：路由正确率 >95% 才划算（路由错了=大模型做小事，反而更贵）。先用规则路由，统计后调优。

### 5.2 长上下文与 KV Cache 优化

- **长上下文场景**（长文档分析/全库检索）用大窗口模型 + prompt caching
- 利用 provider 的 KV cache 折扣（DeepSeek 峰谷价：高峰 2 倍，低谷省 50%）
- 批量任务集中到低谷时段执行（定时任务已覆盖夜间窗口）

### 5.3 Agent 编排与工作流引擎

- **Pipeline 化**：多阶段任务（调研→分析→归档）用编排器串联，阶段间只传结构化中间产物
- **状态追踪**：session-keeper 持久化任务状态，断点续跑
- **并行多路**：独立子任务并行（多路同时搜索/分析），汇聚收敛

### 5.4 知识图谱与结构记忆

- **实体图谱**：人物/公司/产品/技术概念实体化，关系链接（已有 entities/ 雏形）
- **概念网络**：知识文件间交叉链接增强（已部分实现）

## §7 诚实边界与风险

1. **收益百分比为估算区间**：除系统提示词（可精确测量）外，路由/修剪/门控收益依赖实际负载分布，需落地后以 token CSV 实测校准
2. **压缩不可伤锚点**：AGENT/USER 人格与偏好是行为一致性底线，过度压缩会导致行为漂移——压缩优先动"说明性文字"而非"规则本体"
3. **低 bit 模型能力上限**：7B INT4 不适合复杂推理/长上下文/高精度任务，**路由正确性是分层架构的生命线**，正确率不达标宁可少用
4. **embedding 激活的隐藏成本**：2.2GB index.db 重建有一次性成本（API 费+算力）；且向量检索引入后需维护 embedding 版本一致性（模型换版=全量重算）
5. **L3-L4 为长期方向**：知识图谱/Agent 编排投入数周，短期 ROI 低于 L1-L2，建议在 L2 落地并稳定后再推进
