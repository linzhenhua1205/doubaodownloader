## §0 执行摘要

**一句话判断：AI 产出的质量上限由「基础投入」决定，不由「单次提问」决定；基础投入的本质是把隐性共识显性化为约束，并把约束固化为基础实施而非临时脚手架；单次提问只是这个基础设施上的一个执行器。**

用户 08-27 的表述包含五个可拆解的命题，本文逐一论证：

| # | 命题 | 对应章节 | 结论 |
|:-:|:-----|:--------|:-----|
| P1 | AI 投入也要有基础投入 | §2 | 成立：基础投入是固定成本，决定单次产出的能力上限 |
| P2 | 基础信息要达成共识并不断打磨 | §5 | 成立：共识是约束的原料，打磨是约束的演化机制 |
| P3 | 单问题 → 完美输出很难达成 | §3 | 成立：信息缺口 + 生成机制决定了单次交互的信息天花板 |
| P4 | 需要 harness 方式实现的约束支撑 | §2/§4 | 成立：约束是信道编码/先验/参考输入，harness 是载体 |
| P5 | 约束是做成基础，不是消失掉 | §4 | 成立：约束内化为系统默认行为，随每次交互继承 |

**核心洞见**：

1. **投入结构不对称**：基础投入（共识+约束+harness）是**固定成本**，单次提问是**可变成本**。固定成本可摊薄到 N 次使用，N 越大越划算——这解释了为什么「高频高质场景才值得 harness 化」。

2. **约束的三重身份**：信息论上是**信道编码**（提升信号噪声比）、贝叶斯意义上是**先验**（把后验从通用分布拉向领域最优）、控制论上是**参考输入**（让反馈环路可收敛）。三重身份都指向同一结论：没有约束，输出收敛到平均水平。

3. **「做成基础」是核心操作**：约束的寿命必须大于单次对话。prompt 是一次性的（随对话消失），约束是持久的（每次交互继承）。「不是消失掉」的三层含义：**内化**（成为默认判断标准）、**升级**（迭代而非撤销）、**增量化**（只增不减、以新代旧）。

4. **反噬边界同样来自原理**：约束过载 → 创造性下降；约束不更新 → 腐化为噪声；低频场景 harness 化 → 沉没成本。理解约束 = 理解它在什么条件下生效、什么条件下反噬 [来源: 08-18 AI Agent 模式谱系 v3.0 的「原理失效边界」方法，内部知识库]。

## §1 命题重构：从直觉到可验证命题

用户原话：「用AI投入，也是要有基础投入，对一些基础的信息要达成共识，不断进行打磨才行。只输入一个问题，就希望他能搞定，输出你想要的材料，这是很难达成的，需要背后一大堆harness方式实现的约束来支撑才行。而且是把约束做成基础来做，不是消失掉。」

将直觉表述重构为可验证命题：

**P1（投入结构命题）**：AI 使用存在两级投入——基础投入（B，一次性/低频）与单次提问投入（V，每次）。产出质量 Q 是 (B, V) 的函数，且 ∂Q/∂B ≫ ∂Q/∂V。

**P2（共识命题）**：约束的效力取决于其背后共识的质量。共识 = 对「什么是正确产出」的领域知识 + 对「什么不能发生」的历史教训 + 对「如何判断质量」的标准。无共识的约束是空转的条文。

**P3（单次交互极限命题）**：单次提问能传递的信息量（上下文 + 提示词）存在上限，而任务完成所需的信息量（领域知识 + 标准 + 历史 + 偏好）通常远超此上限。因此单次交互的产出质量存在天花板，与模型能力无关。

**P4（载体命题）**：约束必须由 harness（工程化载体）承载才能可靠生效。harness 包含：系统提示词、行为规则文件、技能库、检查脚本、门禁、记忆体系等——一切「在对话之外、对话之上」的确定性结构。

**P5（持久性命题）**：约束的价值随使用次数累积，因此必须基础设施化（持久、版本化、可继承），而非每次重新编写或随对话消失。

五个命题构成因果链：**共识（P2）→ 约束（P1/P4 的中间产物）→ 基础设施（P5）→ 高质量单次产出（P3 的天花板被抬高）**。

## §2 第一性原理：约束为什么决定产出上限

> 沿用 [AI Agent 模式全谱系](./2026-08-18-ai-agent-patterns-taxonomy-methodology-deep-analysis.md) 的六大原理透镜（信息论/博弈论/控制论/认知/经济/系统论），但视角从「模式分析」转向「投入结构」——回答「为什么基础投入在原理层面就决定了产出上限」。

### 2.1 信息论透镜：约束 = 信道编码

香农信道容量公式：C = B · log₂(1 + S/N) [来源: Shannon 1948, 信息论公开知识]。

类比映射：

| 通信系统 | AI 使用系统 |
|:---------|:------------|
| 信道带宽 B | 上下文窗口 + 模型能力 |
| 信号功率 S | 有效任务指令强度 |
| 噪声功率 N | 模糊修辞、无关上下文、目标漂移 |
| 信道编码 | **约束体系**（提示词结构化 + 规则 + 门禁） |
| 单次信道使用 | 一次提问 |

关键推论：
- **单次提问 = 一次信道使用**。你无法通过「再用力一点说」来提升信道容量，就像无法通过加大嗓门提升带宽。
- **基础投入 = 信道设计**。信道编码（约束）直接提升 S/N：把模糊的「输出想要的材料」编码为「输入/条件/处理/输出」的确定性规格，噪声大幅下降。
- 「提示词是工程，不是写作」的机理在此 [来源: 内部知识库 2026-08-07 深度分析]：描述性修辞（「极致」「优美」）是弱信号，与训练分布中的「自由度」相关；结构化指令是强信号。弱信号 = 低 S/N，强信号 = 高 S/N。

### 2.2 贝叶斯透镜：约束 = 先验，输出 = 后验

贝叶斯公式：P(θ|D) ∝ P(θ) · P(D|θ) [来源: 贝叶斯统计公开知识]。

- **模型输出 = 后验**：给定提示词（证据 D）后模型从分布中采样。
- **训练先验**：模型在互联网语料上习得的「通用平均水平」。
- **约束 = 注入的领域先验**：AGENTS.md/规则文件/技能库把「这个项目/这个人认为什么是对的」注入生成过程。

无约束时：后验主要由训练先验主导 → 输出收敛到「通用平均水平」（什么都能做、什么都不精）。
有约束时：先验被显著修正 → 后验向「领域最优」集中。

这解释了 AGENTS.md 实践中的观察：「没有显式约束时，Agent 未必会写出明显糟糕的代码……但它默认追求的是『把功能补上』，而不是『让代码回到项目认可的设计哲学里』」[来源: 《给 Code Agent 加约束：从 AGENTS.md 开始》，CareySon，博客园，2026-05]。所谓「项目认可的设计哲学」，就是领域先验。

### 2.3 经济学透镜：固定成本 vs 可变成本

| 成本类型 | 内容 | 发生频率 | 摊薄逻辑 |
|:---------|:-----|:--------|:---------|
| 固定成本（基础投入） | 共识建立、规则编写、harness 建设、打磨迭代 | 低频（建立期+维护期） | 摊薄到 N 次使用 |
| 可变成本（单次提问） | token、时间、注意力、返工 | 每次 | 随使用线性增长 |

**核心推论：基础投入的 ROI = (单次质量提升 × 使用次数) − 维护成本**。

- 高频场景（每日深度分析、代码审查、知识归档）：N 大，基础投入回报率极高。
- 低频一次性场景（问个一次性问题）：N=1，基础投入是纯沉没成本 → 直接用「裸问」更优。

这解释了一个实践现象：**为什么系统要分档投入**——对高频高质场景建设完整 harness，对低频场景保持轻量 [来源: 内部知识库 2026-08-14 工程规模评估 L0-L4 框架]。

### 2.4 控制论透镜：约束 = 参考输入

闭环控制系统需要参考输入（setpoint）才能收敛。没有 setpoint，反馈环路只能振荡或漂移 [来源: 控制论公开知识]。

对应到 AI：
- **参考输入 = 验收标准/目标约束**：什么算「完成」、什么算「达标」。
- **反馈 = 检查/门禁/评审**：输出 vs 参考输入的偏差。
- **执行器 = 模型**：根据偏差修正输出。

本系统的「深度分析铁律」就是参考输入：write + log + git commit 三缺一禁止收尾 [来源: MEMORY.md 深度分析铁律 08-17]。没有这条约束，模型会「感觉差不多了就停」（对应「偷懒/半件事陷阱」退化模式 [来源: 内部知识库 08-18 模式谱系 §1.1]）。

### 2.5 博弈论透镜：约束 = 委托代理契约

委托代理问题：委托人（用户）无法监督代理人（模型）的每一次行为，因此需要**契约**——明确定义行为边界、验收标准、失败责任 [来源: 委托代理理论公开知识]。

- 无契约：代理人按自身效用函数行事（最小努力、最快交差）。
- 有契约：代理人按契约条款行事，委托人的偏好被编码进契约。

harness 中的约束（门禁脚本、格式检查、git 纪律、独立评审）本质上是**可自动执行的契约条款**——不依赖代理人自觉，而是由外部机制强制执行。「确定的外壳」（deterministic shell）的存在意义正在于此 [来源: 内部知识库 08-18 模式谱系 §1.1 三维坐标]。

### 2.6 系统论透镜：约束 = 故障域隔离

系统论原则：通过边界隔离故障域，防止局部失效扩散为全局失效 [来源: 系统论公开知识]。

- 约束 = 系统边界：格式检查拦住格式错误、门禁拦住质量不达标、git 纪律拦住状态混乱。
- harness = 故障隔离层：模型输出的「不可预测性」被约束边界包裹，失效被限制在可修复的局部。

六透镜收敛到同一结论：**约束不是对 AI 的「限制」，而是让 AI 产出从「随机变量」变为「受控变量」的机制**。没有约束，AI 是赌博；有约束，AI 是工程。

## §3 为什么「只输入一个问题就搞定」不现实

### 3.1 信息缺口：上下文能传递的 vs 任务需要的

设任务 T 的完整信息需求为 I(T)，单次提问能传递的信息为 I(P)：

- I(T) 包含：领域知识、历史决策、踩坑记录、质量标准、输出格式、验收条件、约束边界……往往数以万计 token。
- I(P) 只有：用户当前输入 + 上下文窗口（即便长上下文，也要求用户把全部背景写进去，而这正是「基础投入不足」的表现）。

**I(P) < I(T) 是常态**。用户以为自己在提「一个问题」，实际上是在用一个提示词传递整个项目的历史共识——这是不可能完成的信息压缩。差距只能由「对话之外的基础设施」填补：AGENT.md、USER.md、RULE.md、MEMORY.md、技能库——这些是**预置的 I(T)** [来源: 本系统实证，四文件体系]。

### 3.2 生成机制：无约束收敛到平均水平

LLM 的生成机制是「从 token 分布中采样」，其条件分布由「当前上下文 + 训练先验」决定 [来源: LLM 公开知识]。

- 无约束的上下文 = 训练先验主导 = **通用平均水平**。
- 「平均水平」不是坏，而是**不知道你的领域标准**：不知道你的术语体系、你的质量观、你的历史事故、你的偏好。

正如 AGENTS.md 文章指出：「如果你不显式告诉它，它就只能根据当前上下文里最常见、最平均、最容易补全的写法继续往下写」[来源: 《给 Code Agent 加约束：从 AGENTS.md 开始》，CareySon，博客园，2026-05]。平均水平的输出也许「看起来还行」，但必然缺「你的」判断。

### 3.3 期望方差：约束压缩输出方差

从统计视角：无约束时输出分布方差大（同一任务多次生成，结果漂移大）；有约束时方差小（收敛到约定标准附近）。

| 维度 | 无约束（裸问） | 有约束（harness） |
|:-----|:--------------|:-----------------|
| 输出分布 | 宽泛、发散 | 收敛、聚焦 |
| 多次一致性 | 低（每次结果不同） | 高（结果可复现） |
| 质量下限 | 低（可能偏离目标） | 高（门禁兜底） |
| 质量上限 | 取决于模型+运气 | 取决于约束质量+模型 |

方差压缩是「约束做基础」的核心收益：**你不需要每次祈祷这次运气好，而是让每次都达到约定的下限**。

### 3.4 隐性知识不可外传

用户脑中的大量知识是**隐性知识**（tacit knowledge）：领域经验、审美判断、历史教训、权衡直觉。这些知识：
- 不在模型训练数据里（私有领域）；
- 无法通过一次提问完整表达（连用户自己都难以穷举）；
- 只能通过「显性化 → 写入约束 → 反复打磨」逐步转移。

因此，「单问题 → 完美输出」在信息论上就不成立：**你无法在一条消息里传输你十年积累的判断力**。「隐性的工程判断显性化」是 Agent 时代工程能力的核心 [来源: 《给 Code Agent 加约束：从 AGENTS.md 开始》，CareySon，博客园，2026-05]——而显性化是一个持续的基础投入过程，不是一次对话。

## §4 「约束做成基础」：基础设施化机制

### 4.1 为什么约束不能是临时的

| 载体 | 生命周期 | 继承性 | 版本化 |
|:-----|:--------|:------|:-------|
| 单次 prompt | 一次对话 | 无（下次重写） | 无 |
| 系统提示词/规则文件 | 持久 | 每次对话自动加载 | 可版本化 |
| 技能库（SKILL.md） | 持久 | 按需加载 | 可版本化 |
| 脚本/门禁 | 持久 | 自动执行 | 可版本化 |

临时约束的两个致命缺陷：
1. **不可继承**：每次对话都从零开始，基础投入无法累积——每次都是「第一次」。
2. **不可打磨**：约束无法版本化就无法迭代，「不断打磨」成为空话。

「做成基础」的本质 = **把约束从对话内部搬到对话之上**，让它先于任何一次对话存在、并在每次对话中生效。

### 4.2 约束分层架构（本系统实证）

本系统是「约束基础设施化」的完整实例，五层约束从软到硬：

```text
+--------------------------------------------------------------+
| L5 commit discipline   git add/commit + log append + push    |  HARD
+--------------------------------------------------------------+
| L4 check gates        doc-final-check / check_format /       |  HARD
|                        strategy-compliance                   |
+--------------------------------------------------------------+
| L3 skill constraints  SKILL.md workflow + Q6/Q10 standards   |  SEMI
+--------------------------------------------------------------+
| L2 behavior rules     RULE.md / AGENT.md / priority system   |  SOFT
+--------------------------------------------------------------+
| L1 memory priors      MEMORY.md + memory/ daily + KB         |  SOFT
+--------------------------------------------------------------+
```

- L1-L2 是「软约束」：塑造判断与倾向，但依赖模型遵循。
- L3 是「半硬约束」：规定了方法流程，不遵循会导致产出不达标。
- L4-L5 是「硬约束」：机器强制执行，不通过就拦截（如「未落盘 = 未完成」由门禁兜底）。

**设计要点**：约束越接近「正确产出」的验证，越应该硬化；约束越接近「偏好/风格」，越适合留在软层。全部硬化 → 僵化；全部软化 → 约束形同虚设。分层 = 在灵活性与可靠性之间做工程权衡 [来源: 本系统运行实证 + MEMORY.md 系统治理方法论]。

### 4.3 「不是消失掉」的三层含义

用户强调「把约束做成基础来做，不是消失掉」——这句话值得拆成三层：

1. **内化（不消失 = 成为默认）**：约束不应该「写完就忘」，而应该成为模型的默认判断标准。好的约束像编译器的优化：用户感觉不到它的存在，但它一直在生效。AGENTS.md 文章说「规则只能覆盖你写到的场景，原则才能延伸到你没写到的场景」[来源: 《给 Code Agent 加约束：从 AGENTS.md 开始》，CareySon，博客园，2026-05]——**原则型约束内化后，覆盖范围自动扩展**。

2. **升级（不消失 = 迭代）**：约束不是静态条文，而是随共识深化持续升级。打磨 = 每次失败都追溯一条约束的缺失/失真，然后修订它。约束的「消失」只有一种合法形式——**被更好的约束替代**。

3. **增量化（不消失 = 累积）**：约束体系总体只增不减、以新代旧。因为每条约束背后都对应一次真实教训（事故、返工、纠错），撤销约束 = 允许教训重演。本系统 log.md 记录了 2026-05 至今 1300+ 条目的迭代史 [来源: knowledge/log.md 账本，内部知识库]，本质是一部「约束累积史」。

### 4.4 基础设施化的三重收益

| 收益 | 机制 | 量化方向 |
|:-----|:-----|:---------|
| 边际成本递减 | 共识一次建立，N 次复用 | 单次有效成本 = B/N + V |
| 共识继承 | 新会话/新成员自动获得历史共识 | 冷启动成本 → 0 |
| 质量下限托底 | 门禁拦截低质产出 | 返工率下降 |

从「每问必从头」到「每问即用全部历史」，这是基础设施化与临时 prompt 的根本分野：**前者是复利，后者是单利**。

## §5 共识 → 约束 → 基础设施的转化链

### 5.1 共识的四个来源

| 来源 | 内容 | 例子 |
|:-----|:-----|:-----|
| 领域知识 | 什么是正确的（第一性原理/标准/规范） | 服务器互联拓扑、协议约束 |
| 历史事故 | 什么不能发生（失败模式） | 08-17 质量事故 → 深度分析铁律 |
| 用户偏好 | 什么算好（质量观） | 量化驱动：数值+单位+基线+条件 |
| 方法论 | 如何判断（推理框架） | MECE、第一性原理、五看三定 |

共识 = 四者的交集确认。只有领域知识没有用户偏好，产出「正确但不合口味」；只有偏好没有领域知识，产出「合口味但不正确」。**共识的质量 = 约束的质量上限** [来源: 本系统运行实证，四文件体系演进史]。

### 5.2 转化机制：失败模式 → 规则 → 机制 → 基础设施

四步转化链（本系统实证，08-17 质量事故为例）：

```text
failure mode: 4 sessions ended Done with write=0 (2026-08-17 incident)
   |  distill rule: no file on disk = not done; write+log+commit gate
   v  solidify: deep-analysis rules into RULE.md priority layer
   |  infrastructurize: agent_stream.py detects "deep-analysis" prefix
   v                -> context reset + gate scripts as backstop
```

关键点：**失败是约束的原料**。每一次真实失败都对应一条缺失的约束；约束体系的完备度 = 对失败模式覆盖的完备度。这也是「不断打磨」的精确含义：打磨 = 把新的失败模式持续转化为约束，把旧约束中失真/过时的部分修正掉 [来源: 本系统运行实证，MEMORY.md 深度分析铁律 08-17 事故记录]。

### 5.3 打磨循环：约束的迭代（本系统实证）

| 日期 | 迭代 | 触发动机 |
|:-----|:-----|:---------|
| 08-07 | 单同步纪律（三同步→只追加 log） | token 成本优化 |
| 08-14 | 01_survey 只写日期文件 | 降 token、索引脚本化 |
| 08-17 | 深度分析铁律（五条） | 质量事故 |
| 08-19 | 全库无子目录 index/log | 架构简化 |
| 08-25 | 信源配比铁律 Q10（内部≤60%） | 一致性错误传播风险 |

每条约束都有出生日期、触发事故、迭代理由 [来源: knowledge/log.md 账本 + MEMORY.md 系统治理方法论，内部知识库]。这说明：**约束基础设施与知识库一样，是活的系统，不是一次建成的一潭死水**。Harness Engineering 报告将「熵管理（对抗技术债）」列为 Harness 核心支柱之一 [来源: 《Harness Engineering：AI Agent 时代的工程范式革命》，豆包报告，import/doubao/]——约束的持续打磨就是对抗「约束体系自身的熵增」。

### 5.4 约束生命周期管理

| 阶段 | 动作 | 判据 |
|:-----|:-----|:-----|
| 创建 | 失败模式 → 规则草案 | 有真实教训支撑 |
| 验证 | 小范围试运行，观察行为变化 | 行为确实改变且方向正确 |
| 修订 | 失真/过时部分修正 | 出现反例或环境变化 |
| 退役 | 被更优约束替代 | 新约束覆盖旧约束场景 |
| 沉淀 | 写入 log/记忆，保留演进史 | 每次迭代留痕 |

生命周期管理的核心纪律：**约束的每次变更都要留痕**（为何改、何时改、替代了什么）。没有留痕的约束体系会失去「为什么」——而「为什么」正是约束对抗环境变化时的自适应依据。

## §6 边界与反噬（极端挑剔审查）

> AGENT.md 要求「极端挑剔审查：找问题比找赞同有价值」。约束基础设施化的四个反噬风险：

### 6.1 约束过载 → 僵化

- 症状：约束太多太细，模型变成「复读机」，创造性、探索性、临场判断全部丧失。
- 机理：约束压缩自由度，也压缩了意外之喜（serendipity）。AI 的「发散性」在探索性任务中是资产，在交付性任务中是负债——约束要保护后者、容忍前者。
- 缓解：按任务类型分约束档位（交付性任务全约束、探索性任务轻约束），对应「分档投入」原则 [来源: 内部知识库 2026-08-14 L0-L4 工程规模评估]。

### 6.2 约束腐化 → 不更新变成噪声

- 症状：环境变了（模型升级、流程改变、目标转移），约束没变，旧约束从「指导」变成「误导」。
- 机理：约束是对特定环境下的「正确」的编码；环境漂移后，编码失真。**约束也有技术债**。
- 缓解：定期审计约束与现实的匹配度；给约束标注「适用条件」；环境变更事件触发约束体检。Harness 报告把「熵管理」作为四大支柱之一正是为此 [来源: 《Harness Engineering：AI Agent 时代的工程范式革命》，豆包报告]。

### 6.3 沉没成本 → 低频场景不值得 harness 化

- 症状：对一次性任务也建设完整 harness，投入产出倒挂。
- 机理：ROI = (质量提升 × N) − 维护成本，N=1 时必然为负。
- 缓解：用「频率 × 质量要求 × 可标准化」三因子筛选基础设施化的对象；低频任务走「裸问 + 人工把关」的轻量路径 [来源: §2.3 经济学透镜推论]。

### 6.4 「约束消失」的误解

用户说「约束不是消失掉」，但要警惕另一种误读：**把「内化」误解为「可以删掉」**。

- 正确理解：约束从「显式条文」内化为「模型默认行为」后，用户不再需要每次重申——但约束本体必须持续存在并维护，否则默认行为会随时间/模型版本漂移回平均水平。
- 类比：编译器优化不是「不需要优化了」，而是「优化被固化进编译器」；约束内化不是「约束没了」，而是「约束进入了每次对话的默认上下文」。

### 6.5 约束冲突与优先级

- 症状：多条约束对同一场景给出矛盾指令（如「质量优先」vs「token 节约」）。
- 机理：约束体系是多重目标编码，冲突不可避免。
- 缓解：显式优先级体系。本系统设计 L1 安全红线 > L2 规则文件 > L3 人格 > L4 系统默认，负面 > 正面、具体 > 模糊 [来源: RULE.md 优先级体系，内部知识库]。**约束冲突的解决不靠删除，靠排序**——这也是「约束做基础」的组成部分：把优先级也固化为基础。

## §7 投入决策框架

### 7.1 ROI 模型

```
ROI = (dQ x N x R) - (C_build + C_maintain x T)
```

其中：**dQ** = 单次产出质量提升（有约束 vs 无约束）；**N** = 年使用次数；**R** = 质量提升的货币化系数（返工率下降/决策质量/时间节省）；**C_build** = 共识建立 + harness 建设成本；**C_maintain** = 年维护成本（打磨迭代）；**T** = 使用年限。

决策阈值：ROI > 0 则值得基础设施化；ROI < 0 则退回轻量路径。这是「基础投入」的理性边界——**不是所有 AI 使用都需要 harness，而是高频高质的才需要**。

### 7.2 什么值得基础设施化

三因子筛选：

| 因子 | 高 | 低 |
|:-----|:---|:---|
| 使用频率 N | 每日多次（深度分析、归档、审查） | 偶发（一次性问答） |
| 质量要求 | 交付级（对外输出、知识沉淀） | 参考级（了解概念） |
| 可标准化 | 流程固定、可写规则 | 探索性、无固定形态 |

三因子全高 → 建设完整 harness；全低 → 裸问；中间态 → 轻量约束（单文件规则即可）。

### 7.3 分档投入路径

| 档位 | 投入 | 适用 | 产出预期 |
|:-----|:-----|:-----|:---------|
| L0 裸问 | 0 | 一次性/探索 | 平均水平，需人工把关 |
| L1 单文件规则 | 1-2h | 高频小任务 | 行为纠偏，方差下降 |
| L2 技能封装 | 0.5-1d | 标准流程任务 | 流程可控，质量下限托底 |
| L3 完整 harness | 多天+持续维护 | 核心高频任务 | 复利效应，质量上限逼近共识上限 |

投入决策的本质：**把有限的基础投入预算，分配给 ROI 最高的任务**——这与任何资本配置决策同构 [来源: §2.3 经济学透镜 + 内部知识库 2026-08-14 工程规模评估]。

## §8 可复用清单

1. **评估任何 AI 任务先问**：这个任务需要哪些共识？（领域知识/事故/偏好/方法论）这些共识现在在模型侧、在用户脑侧、还是已写入约束？
2. **单次提问前自检**：我传递的信息量 I(P) 是否 ≥ 任务所需 I(T)？如果不是，缺什么——背景、标准、格式、边界？缺的应该补在提问里，还是应该先建基础设施？
3. **约束设计三问**：这条约束对应哪次真实教训？它应该软约束还是硬约束（门禁）？它会不会与已有约束冲突（需要优先级）？
4. **约束维护纪律**：每次失败都问「哪条约束缺失/失真了？」；每次环境变更都触发约束体检；每次约束变更都留痕（何时、为何、替代什么）。
5. **投入决策**：用「频率 × 质量要求 × 可标准化」三因子判断是否基础设施化；用 ROI 模型定档位；低频任务不建 harness，高频任务不省基础投入。
6. **「约束消失」的正确姿势**：约束内化 = 每次对话自动继承，不是删除；「感觉不到」是成功，「被遗忘」是失败。
7. **共识打磨节奏**：共识不是开会一次定死，而是随每一次失败/纠错持续演化；打磨的产出物是约束的版本史，不是一次性文档。
