## §1 结论概要

1. **五工程可整体迁移**：提示词（配方）/上下文（输入）/Router（决策）/Harness（行动）/图（固化）在办公与文档场景同样成立——因为办公/文档的本质是"把不确定性限制在模型推理边界内"的同一问题，只是约束密度更低、人工介入更频繁。
2. **本系统是最完整的实证**：四文件分级=提示词工程、memory/knowledge 分层=上下文工程、skills 触发匹配=Router 工程、scheduler+RULE 安全红线=Harness 工程、知识库三同步+pipeline=图工程——五工程在本系统全部落地且已运行 200+ 天。
3. **用户的三段闭环观点成立且可升级**：生成时格式约束（提示词）→ 生成后目标化 check（Harness）→ 批量修复（Loop）是文档生产的"最小闭环"；补上 8 个维度后升级为"五工程协同闭环"——其中**输入侧治理（先查再写）与人工介入点（AI 自查≠人工确认）是两个最关键缺口**。
4. **办公与文档的差异在 Router 层体现**：办公任务碎片化高频（邮件/纪要/汇报）→ 路由要"快"（模板+直连）；文档任务长链低频（调研/专题/论文）→ 路由要"稳"（pipeline+检查点）。同一 Router 工程，两种路由策略。
5. **图工程是总装车间**：它不是第五个孤立方法，而是把前四者的产物（规则/上下文/路由/校验）组织成空间结构——文档本身就是图的状态载体（spec/tasks/checklist 三文档组即"文档驱动派"图工程）。

## §2 定位：为什么编程五工程能迁移到办公/文档

### 2.1 底层同构：编程 = 知识工作的极端形态

| 维度 | 编程（极端形态） | 办公/文档（常态） | 同构点 |
|:-----|:----------------|:-----------------|:-------|
| 产出 | 代码（机器可执行） | 文档/决策/沟通（人可执行） | 都是"知识资产" |
| 约束密度 | 高（编译器/类型/lint） | 低（模板/规范/评审） | 都需要确定性外壳 |
| 验证方式 | 编译+测试 | check 脚本+人工评审 | 都是"生成→验证"闭环 |
| 迭代节奏 | 快（分钟级） | 中（小时/天级） | 都是 Loop |
| 失败代价 | 运行时崩溃 | 决策错误/信息失真 | 都需 Checkpoint 恢复 |

> **核心命题**：编程是知识工作的"压力测试场"——在最高约束密度下验证出的工程方法，迁移到约束更宽松的办公/文档场景时只会更有效（约束可降级，方法骨架不变）。

### 2.2 确定性谱系与办公/文档映射

```text
Certainty Spectrum (soft -> hard)
Prompt   ->  Context  ->  Router   ->  Harness  ->  Graph
how to think  what to see   whom to give  how to act safely  how to solidify
rule tiers    memory tiers  task routing  permissions+checks  flow+state
(soft)        (soft)        (mid)         (hard)             (hardest)
```

各工程在办公/文档场景的实践顺序建议（与编程侧一致）：**先做提示词+上下文（让 AI 想对、看对）→ 再做 Harness（安全边界）→ Router 提供决策骨架 → 图在最需要确定性/合规/可恢复的场景引入**（图是最后手段，不是默认架构）。

## §3 提示词工程 → 办公/文档

### 3.1 第一性：分级注入的认知基座

提示词工程不是"写更好的 prompt"，而是**按"稳定性 × 作用域"分级注入信息**：让高频动态信息不污染低频稳定指令。编程侧用 CLAUDE.md 三层分级；办公/文档侧用四类文件分级（全局人格/项目偏好/操作规则/动态记忆）。

### 3.2 办公场景应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **全局规则** | 一份"个人工作台规则"：回复格式偏好（先结论后展开/表格优先/emoji 适度）常驻 | 所有对话输出风格一致，无需每次重复 |
| **项目级指南** | 每个项目一份指南：术语表（UALink/NVLink 不翻译）、口径、关键约束 | 跨会话口径统一，防止术语漂移 |
| **模板化指令** | 高频任务封装为斜杠命令/模板：`/周报`、`/会议纪要`、`/邮件回复` | 常用操作一键触发，不重复写长 prompt |
| **技能封装** | 把"会议纪要→行动项提取→飞书推送"封装为 Skill（触发条件+步骤+产出规范） | 动态能力（会做什么）vs 静态规则（你是谁）分离 |
| **角色声明** | 会话开始时声明角色（"你是技术决策者的分析助手，先给结论再展开"） | 输出姿态稳定 |

### 3.3 文档编写应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **文档规范头部** | 强制头部元信息：日期/分类/专题编号/一句话/来源/关联 | 每篇文档自解释，索引可自动化 |
| **写作风格指南** | 全局规则声明：TOC 顶部+Changelog 底部+交叉链接+断言有出处+数据四要素 | 文档质量基线统一（本系统 Q6 标准） |
| **章节模板** | 深度文档固定骨架：结论概要→分节深挖→总矩阵→来源→Changelog | 结构 MECE，读者路径清晰 |
| **技能化写作** | SKILL.md 声明"创建文档六步工作流"（取材→溯源→量化→逻辑→链接→格式） | 每次写作自动遵循，不依赖临场发挥 |
| **@import 组装** | 大型文档拆分子文件按需引用（方法论库/数据源图谱） | 单文件不膨胀，作用域化组装 |

### 3.4 本系统实证

- **四文件分级**（提示词工程在本系统的直接体现）：`AGENT.md`（人格/行为/季更）→ `USER.md`（身份/偏好/年更）→ `RULE.md`（规则/工程约束/常驻）→ `MEMORY.md`+`memory/每日`（动态记忆）——稳定性递减、动态性递增，高频动态信息不污染低频稳定指令。
- **45+ 技能库**：每个 SKILL.md = 提示词封装（触发条件/步骤/产出规范），按需加载（先扫描描述仅相关时加载详情）——Token 节约设计。
- **知识库文档 Q6 标准**：头部注解/TOC/Changelog/交叉链接/断言出处/数据四要素——提示词工程固化为可执行规范（check_md_format 脚本强制）。

## §4 上下文工程 → 办公/文档

### 4.1 第一性：上下文是稀缺资源

上下文 = 窗口物理极限 + token 成本。上下文工程 = **预算管理**：哪些必须常驻、哪些按需加载、超限怎么办、成本如何回收（缓存）。量化锚点：本系统实测 27 天 2.3B tokens，**缓存未命中 58% 是最大成本项**——办公/文档场景同样适用（每次会话都带全量材料=最大浪费）。

### 4.2 办公场景应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **记忆分层** | 长期（个人偏好/项目结论）→ 短期（当天进展）→ 临时（会话内）三层 | 常驻只放低频稳定信息，动态信息按需取 |
| **会话预算** | 每次会话只带相关材料（项目指南+最近进展），不倾倒全量历史 | 上下文不膨胀，成本可控 |
| **检索优先** | 问"之前做过类似分析吗"→ 先检索知识库再回答，而非全量重读 | 避免重复造轮子（最贵的一步） |
| **成本意识** | 简单任务用小上下文，复杂任务才开大窗口；批量任务合并会话 | 缓存命中率提升，token 成本下降 |
| **断点恢复** | 跨会话任务保存进度（session-keeper）：当前步骤/已完成/阻塞 | 中断不丢进度，恢复成本趋零 |

### 4.3 文档编写应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **先查再写** | 写作前先 grep 知识库既有同主题文档+log.md 量化锚点 | 防重复（写入/归档前强制检查） |
| **素材分级** | import/ 素材批判性使用：关键量化数据必须独立源交叉验证 | 防止素材污染文档结论 |
| **交叉链接** | 关联文档互相链接（本文即链接编程侧姊妹篇） | 知识网络可导航，上下文按需跳转 |
| **索引引用** | 引用既有分析（数据源图谱/方法论）而非重新推导 | 上下文复用，结论可追溯 |
| **内容裁剪** | 长文档分章生成，每章独立成文再组装（避免单次超限） | 突破窗口限制，质量更高 |

### 4.4 本系统实证

- **三层记忆架构**：`MEMORY.md`（长期索引，月更）→ `memory/YYYY-MM-DD.md`（每日，日更）→ `knowledge/`（结构化知识，不定）——频率匹配原则（超 1 周不写 memory/，少 1 个月不写 MEMORY.md）。
- **每日 23:50 蒸馏**：当天讨论自动沉淀到 memory/，重要结论升级到 knowledge/——上下文"及时回收"机制。
- **知识库 2800+ 文档**：130,739 chunks 检索（keyword-only）——检索型上下文已跑通；最高杠杆=启用 embedding（¥30-60/月，待决策）。
- **27 天 2.3B tokens 教训**：缓存未命中 58% 是最大成本 → 优化优先级 = 合并 session > 减少 API 请求 > 缩短输出。

## §5 Router工程 → 办公/文档

### 5.1 第一性：路由 = 任务分诊（与 Loop 的关系）

编程底稿用 Loop 工程（循环本身），用户提出 Router 工程（路由/分诊）——**二者是同一枚硬币的两面**：

```text
Loop   = the loop itself (perceive -> plan -> act -> observe, time dimension)
Router = the decision point inside the loop (whom to hand to next, decision dimension)
```

（中文释义：Loop=循环本身，感知→规划→行动→观察，时间维度；Router=循环里的决策点，下一步交给谁，决策维度。）

在办公/文档场景，Router 比 Loop 更贴近日常直觉：**"这个任务该走哪条路？"**——用哪个模型、哪个工具、哪个技能、哪条流程。Router 是 Loop 的"岔路口"；没有 Router 的 Loop 是单行道，有 Router 的 Loop 是立交桥。

### 5.2 办公场景应用

| 场景 | 路由策略 | 效果 |
|:-----|:---------|:-----|
| **任务分诊** | 重要紧急（会议决策支持）→ 直连大模型深度分析；批量琐碎（邮件分类）→ 模板+小模型 | 资源按价值分配，不浪费大窗口 |
| **模型路由** | 简单任务用小模型（成本低），复杂推理用大模型（质量高） | 质量-成本平衡 |
| **工具路由** | 查数据→data-query 技能；查新闻→daily-news；翻译→utility；写文档→light-paper-drafting | 每个任务路由到最擅长工具 |
| **场景路由** | 定时任务（周报/日报）→ scheduler 自动触发；即时任务→ 会话直连 | 自动/人工两条通道 |
| **升级路由** | AI 不确定时路由到"人工确认点"，不擅自决策 | 不确定性问题交给人（安全兜底） |

### 5.3 文档编写应用

| 场景 | 路由策略 | 效果 |
|:-----|:---------|:-----|
| **文档类型路由** | 深度专题→pipeline（六阶段）；快速纪要→单技能直连；邮件→模板 | 任务复杂度匹配流程重量 |
| **复杂度判据** | 跨 ≥3 阶段/需交接产物 → pipeline；单阶段闭环 → 单技能 | 避免"重流程拖累轻任务" |
| **数据源路由** | 服务器硬件→STH；GPU 路线图→AMD IR；互联→UALink Consortium；存储→TrendForce（数据源图谱 §8 路由表） | 每类文档用最可信源 |
| **格式路由** | 正式报告→Q6 标准+格式门禁；内部笔记→轻量格式 | 输出规范匹配用途 |

### 5.4 本系统实证

- **skills 触发匹配**：系统每轮扫描 45+ 技能描述，命中才读取 SKILL.md（如"用户给 URL→web-archive 技能"）——这就是 Router 工程的自动路由。
- **light-orchestrator 判据**："任务跨 ≥3 阶段或需交接产物 → pipeline；改摘要/画图/查引用 → 单技能直连"——复杂度路由的显式化。
- **12 场景数据源路由表**（data-source-registry §8）：服务器硬件/GPU 路线图/互联/存储/国产化/人才趋势/大会——每类调研预置可信源。
- **42 任务调度**（scheduler）：周报 15:00/专项报告 22:00/GitHub 日报 06:50——定时任务的场景路由（全部经 feishu 通道）。

## §6 Harness工程 → 办公/文档

### 6.1 第一性：确定性外壳

Harness = 让 AI **有组织地干活**的确定性外壳：权限怎么分级、动作怎么授权、结果怎么校验、中断怎么恢复、事件怎么旁路。编程侧用 7 类 Hooks/权限分级/Checkpoints；办公/文档侧用**规则红线 + 校验门禁 + 定时调度 + 审计日志**。

### 6.2 办公场景应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **安全红线** | 破坏性操作（删除/覆盖/移动）先确认；敏感信息不写入记忆 | 防不可逆错误 |
| **定时调度** | 周报/月报/日报用 scheduler 自动触发，时间固定（周日 15:00） | 周期性任务不遗忘 |
| **通知推送** | 任务完成→飞书推送（channel_type=feishu），关键结果主动同步 | 异步任务可感知 |
| **审计日志** | 变更记录到 log.md（日期分节），可回溯 | 可审计、可恢复 |
| **会话恢复** | 中断后 session-keeper 恢复：当前步骤/已完成/阻塞风险 | 断点续跑 |

### 6.3 文档编写应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **格式门禁** | check_md_format 脚本强制 R1-R3（代码块/引用/表格格式） | 格式问题机器把关，不靠人工 |
| **链接校验** | check_links 检查交叉链接有效性 | 防死链（知识网络断裂） |
| **三同步强制** | 新文档 → README 条目 + log 变更 + INDEX 刷新（三处联动） | 索引/日志/目录不脱节 |
| **版本控制** | git 管理知识库，变更可 diff 可回滚 | 误操作可恢复 |
| **破坏性操作纪律** | 永不 rm（mv 到 tmp/bak/）；改前查文件头部约束 | 防误删关键文件 |

### 6.4 本系统实证

- **RULE.md 安全红线**（L1 优先级）：永不 rm、永不泄露密钥、破坏性操作先问——Harness 权限模型。
- **check_md_format.py**：R1-R3 全 0 才算合格（代码块纯 ASCII/引用规范/表格对齐）——目标化 check 的脚本化。
- **scheduler 42 任务**：全部经 feishu 通道，任务名=稳定锚点——调度+通知的确定性外壳。
- **knowledge/log.md 全局变更账本**：git 补齐 5 月起，日期分节——审计日志。
- **session-keeper 技能**：跨会话任务持久化（task_id/status/context/progress）——Checkpoint 机制。

## §7 图工程 → 办公/文档

### 7.1 第一性：流程固化 + 知识组织（回应"这些就是图工程"）

用户说"图工程（这些就是图工程）"——准确理解：**图工程不是第五个孤立方法，而是"总装车间"**——把前四者的产物（提示词的规则、上下文的记忆、Router 的决策、Harness 的校验）组织成**空间结构**（节点/边/状态/检查点/人工介入点），让控制流恢复确定性。

编程侧两种派别：Claude Code=动态生成派（模型现场生成工作流）；Trae=文档驱动派（spec/tasks/checklist 三文档组）。**办公/文档场景天然适合"文档驱动派"**——因为文档本身就是图的状态载体：

```text
Graph engineering in docs = document-as-graph
spec.md       = graph structure (outline/sections = nodes)
tasks.md      = execution plan (task list = actions on edges)
checklist.md  = acceptance list (completion criteria = output constraints)
confirm-point = human-in-the-loop (human intervention edge)
Changelog     = state history (checkpoint records)
```

（中文释义：spec.md=大纲/章节即节点；tasks.md=任务列表即边上的动作；checklist.md=完成标准即输出约束；确认点=人工介入边；Changelog=状态历史即检查点记录。）

### 7.2 办公场景应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **流程pipeline** | 六阶段流水线（输入QA→多路→汇聚→验证→约束→专家门） | 复杂任务结构化推进 |
| **人工介入点** | 方案生成后暂停等确认（确认点）；关键决策请用户拍板 | AI 自查≠人工确认，价值判断归人 |
| **状态机** | 任务状态显式化（待办/进行中/已完成/已取消），进度自动更新 | 可追踪、可恢复 |
| **检查点** | 阶段间强制检查点（决策点+确认点），产物台账 | 断点续跑不重来 |
| **验收清单** | checklist 显式验收条件，达标才进入下一阶段 | 防"看起来完成实则没完成" |

### 7.3 文档编写应用

| 场景 | 应用方法 | 效果 |
|:-----|:---------|:-----|
| **文档三同步** | 新文档 → README（人工条目）+ log（变更账本）+ INDEX（自动路径）三处联动 | 知识库不脱节（图的一致性） |
| **写作pipeline** | 调研→分析→归档→索引→日志五步流水线 | 每篇文档走完整生命周期 |
| **检查点恢复** | 文档中途中断 → session-keeper 保存进度，恢复后继续 | 长文档不怕断 |
| **验收门禁** | 格式 R1-R3 全 0 + 链接 0 缺失 + TOC 锚点全匹配才算合格 | 输出约束显式化 |
| **知识图谱** | 交叉链接网络（本文链接 6 篇相关专题） | 知识可导航、可复用 |

### 7.4 本系统实证

- **知识库三文件体系**：README.md（人工条目库）+ index.md（自动路径库，kb-global-index.py 生成）+ log.md（全局变更账本）——V3 架构，281 个分布式 index/log 废弃归一——图工程的知识组织落地。
- **pipeline 六阶段**（light-orchestrator）：输入质量门→多路并行→汇聚→Ralph 验证→约束执行→专家终审——图工程的流程固化。
- **research 三层架构**：tasks.json（42 任务）→ research_task_runner.py → research_topics.json（34 主题）——图工程的调度层。
- **"文档驱动派"实证**：本系统所有深度专题都走 spec 式结构（结论概要→分节→矩阵→来源→Changelog）+ 确认点（用户审阅后才定稿）——与 Trae Spec 工作流同构。

## §8 文档生产三段闭环：用户观点映射 + 8 补充维度

### 8.1 三段闭环（用户观点）

用户描述的核心机制，映射到五工程：

| 用户观点 | 本质 | 对应工程 |
|:---------|:-----|:---------|
| 生成时：提示词 + 格式约束（文件头名称/存放位置/log/摘要/联动改动信息） | 输出格式规范 + 元数据约定 | 提示词工程 + 图工程（产物规范） |
| 生成后：有目标的 check 机制（再调用一个东西让它 check） | 目标化校验（格式/链接/一致性） | Harness 工程（校验门禁） |
| 完成后：批量 check + 修复 | 批量迭代闭环（发现→修复→再验证） | Loop 工程（迭代） |

> **验证**：这三段正是本系统每天都在跑的机制——生成时按 Q6 模板写（提示词）+ 生成后跑 check_md_format（Harness）+ 批量修复格式问题（Loop）。用户从实践中提炼出的闭环与五工程方法论完全吻合。

### 8.2 8 个补充维度

| # | 补充维度 | 对应工程 | 为什么关键 |
|:-:|:---------|:---------|:-----------|
| 1 | **生成前输入治理**：先查知识库避免重复、素材分级、需求澄清 | 上下文工程 | 重复造轮子是最贵的一步，闭环应从"查"开始而非"生成"开始 |
| 2 | **任务分诊路由**：小任务直连 vs 大任务 pipeline、文档类型→模板 | Router 工程 | 没有路由，所有任务走同一条路=资源浪费 |
| 3 | **人工介入点**：AI 自查(check) ≠ 人工确认(review)——机器校验格式/链接，人判断内容/立场/取舍 | 图工程 | 价值判断不可外包，这是 AI 办公的伦理边界 |
| 4 | **再验证闭环**：批量修复后必须重跑 check 确认达标 | Loop 工程 | 防"修一个坏一个"，修复本身要验证 |
| 5 | **安全权限**：覆盖/删除/移动前确认、敏感信息防护、永不 rm | Harness 工程 | 不可逆操作的护栏 |
| 6 | **生命周期维护**：索引/交叉链接/changelog 长期维护（不止生成那一刻） | 图工程 | 文档是资产不是垃圾，需要持续治理 |
| 7 | **成本预算**：token 预算、批量合并、缓存命中率作为运营指标 | 上下文工程 | 27 天 2.3B tokens 教训：成本失控是隐形成本 |
| 8 | **断点恢复**：会话中断恢复、断点续传 | Harness 工程 | 长任务/长文档的可靠性保障 |

### 8.3 完整闭环 = 五工程协同

```text
Document Production Full Loop (Five-Engineering Synergy)
  1. Input Governance (Context)   search KB first -> no dup · grade materials -> no pollution
     v
  2. Task Routing (Router)        complexity gate -> pipeline or single-skill
     v
  3. Generation (Prompt)          template + format spec -> header meta + structure + linkage
     v
  4. Targeted Check (Harness)     check_md_format + link check + consistency
     v
  5. Batch Repair (Loop)          find issue -> fix -> re-verify (loop until pass)
     v
  6. Human Review (Graph)         AI self-check passed -> human judges content/position/tradeoff
     v
  7. Three-Sync Archive (Graph)   README entry + log change + INDEX refresh
     v
  8. Lifecycle Maintenance (Graph+Harness)  cross-links / changelog / future updates
```

各步骤说明：① 先查知识库防重复、素材分级防污染（上下文工程）；② 按复杂度判据路由到 pipeline 或单技能（Router 工程）；③ 按模板+格式规范生成，含头部元数据/结构/联动改动信息（提示词工程）；④ 目标化校验：格式/链接/一致性门禁（Harness 工程）；⑤ 批量修复后重跑 check 确认达标（Loop 迭代）；⑥ 人工评审内容深度/立场/取舍——AI 自查≠人工确认（图工程确认点）；⑦ 三同步归档：README 条目+log 变更+INDEX 刷新（图工程）；⑧ 长期维护交叉链接/changelog/后续更新（图+Harness）。
