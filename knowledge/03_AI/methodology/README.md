## 二、AI 技能遵守与复杂度管理

> **文件**: `knowledge/methodology/2026-07-14-ai-agent-skills-usage-methodology.md`（990 行）
> **核心问题**: 加载了 Skill 但 AI 并不完全遵守 → 如何确保规则被有效执行？
> **核心矛盾**: 细节控制越精细、复杂度越高，AI 能力边界越明显 → 如何突破？

### 2.1 四法门 — 提升遵守率的四大技巧

| 法门 | 原理 | 做法 | 遵守率提升 |
|:-----|:-----|:-----|:----------:|
| **🔄 重复** | 重复将"背景信息"提升为"执行指令" | 关键节点重复3次；夹心式（指令→内容→指令） | ~40% → ~80% |
| **🚨 强调** | 强语气词/标记提高注意力权重 | ⚠️必做(~90%) / 🔴禁止(~95%) / 💡建议(~60%) | ～+20pp |
| **📝 小型化** | 缩短降低认知负载，提高token利用率 | 每条≤15词；7条上限；动词开头；拒绝模糊词 | ～+30pp |
| **🏗️ 分层** | 按认知负荷分三级投喂 | L1约束(常驻) / L2策略(按阶段) / L3实施(按需) | ～+40pp |

**模糊词→精确阈值转换表**（最常见失败根因）:

| 模糊词 | 修改后 |
|:-------|:-------|
| "代码质量要高" | "无 ESLint 错误" |
| "尽量处理异常" | "所有可能抛异常的地方用 try-catch" |
| "合理命名" | "变量camelCase，类PascalCase，常量UPPER_SNAKE" |
| "适当注释" | "每个 public 方法必须有三斜线文档注释" |
| "尽快修复" | "本对话内修复" |

### 2.2 复杂度墙

| 规则数量 | 初始遵守率 | 50轮后遵守率 |
|:--------:|:----------:|:-------------:|
| 5条 | ~95% | ~85% |
| 10条 | ~85% | ~65% |
| 20条 | ~70% | ~40% |
| 50条 | ~**50%** | ~**15%** |

> **核心结论**: 不经过分层的规则堆叠是最大的反模式。

### 2.3 三种实操模式

| 模式 | 适用场景 | 核心思想 |
|:-----|:---------|:---------|
| **Pipelined Shell** | 大型功能开发 | 分阶段，每阶段只加载该阶段的 Skill（≤7条） |
| **Federation of Agents** | 大型多模块项目 | 不同 Agent 负责不同模块，通过契约通信 |
| **Checkpoint Iteration** | 高质量关键代码 | 写一小块→审查→修正→推进，周期越短质量越高 |

### 2.4 反馈闭环五级

| 级别 | 形式 | AI修正率 |
|:-----|:-----|:--------:|
| L0 无反馈 | "这段重写" | ~0% |
| L1 模糊反馈 | "不符合要求" | ~20% |
| L2 点对点 | 指出具体哪条规则被违反 | ~60% |
| L3 精确反馈 | 规则+违反位置 | ~80% |
| L4 纠正反馈 | 规则+位置+修正建议 | ~95% |

### 2.5 DECISION 协议（最终裁决）

> 当四法门+分层+反馈都用上了，仍有边界情况——DECISION 协议提供"硬切换"信号。

```text
用户说 "DECISION: 3" -> AI 立即停止所有工作，100% 遵守第3条规则
```

## 三、提示词工程与需求表达

> **核心文件**: `05_tools/ai-tools/2026-06-23-09-ai-usage-methodology.md`（53KB/1245行）· `import/md/AI反馈细节不足原因与提示词优化_0606044658.md`（162行）
> **核心问题**: 同样的 AI，不同人用效果天差地别。根本原因不是模型差异，而是**需求表达能力**的差异。

### 3.1 AI 的三层能力模型

```text
+-----------------------------------------+
|  表达层：提示词工程（Prompt Engineering）|
|  +- 把需求转译为 AI 能执行的指令         |
|  +- 最易上手，提升效果最快               |
|  +- 决定性因素：能否"问对问题"          |
+-----------------------------------------+
|  编排层：Skills / Agent / MCP            |
|  +- 把重复任务固化为可复用的工作流       |
|  +- 中级门槛，需要理解工具和工作流       |
|  +- 决定性因素：能否"抽象任务模式"       |
+-----------------------------------------+
|  模型层：Foundation Model                 |
|  +- 理解模型能力边界、原理和局限         |
|  +- 最难但最根本：决定你对 AI 的信心     |
|  +- 决定性因素：能否"批判性使用"         |
+-----------------------------------------+
```

### 3.2 提示词工程 15 维度速查

> **来源**: `05_tools/ai-tools/2026-06-23-09-ai-usage-methodology.md` §2.1

| 维度 | 做法 | 作用 |
|:-----|:-----|:------|
| **① 可衡量目标** | 定义具体、可验证的目标 | 设定终点，避免发散 |
| **② 参考样例** | 给出输入/输出示例 | 定义输出格式和风格 |
| **③ 定义角色** | 设置角色 + 背景 + 专业领域 | 激活对应知识域，提升质量 |
| **④ 定义场景** | 说明上下文和使用场景 | 避免泛化输出 |
| **⑤ 明确现状** | 给出已有条件和前置信息 | 避免 AI 从零假设 |
| **⑥ 分步拆解** | 复杂任务拆为步骤链 | 降低单步认知负载，提升可执行性 |
| **⑦ 允许多路径** | 开放多种解法/优化方向 | 保留创造性 |
| **⑧ 格式化处理** | 指定输出格式（表格/JSON/Markdown） | 便于验证和二次处理 |
| **⑨ 明确输入/输出** | 界定输入内容和输出产物 | 防止遗漏和越界 |
| **⑩ 正向约束** | 不否定（"不要X"）→ 肯定引导（"做Y"） | 避免否定指令的"反向激活" |
| **⑪ 迭代反馈** | 分层反馈→精确反馈→纠正反馈 | 修正率从 20%→95% |
| **⑫ 上下文结构** | 用分隔符清晰划分不同上下文块 | 避免上下文混淆 |
| **⑬ 示例引导** | few-shot 示例约束输出模式 | 控风格、控格式、控逻辑 |
| **⑭ 评估与测试** | 预设验证标准，让 AI 自检 | 从"单次输出"变"质量闭环" |
| **⑮ 深度角色设定** | 含价值观/禁忌/特殊偏好的角色定义 | 对齐认知，减少意外输出 |

### 3.3 提示词优化四策略（解决"深度不够"）

> **来源**: `import/md/AI反馈细节不足原因与提示词优化_0606044658.md`

| 策略 | 原理 | 反例 → 优化后 |
|:-----|:------|:-------------|
| **① 维度清单法** | 明确"必须覆盖哪些细节维度" | "解释NMS" → "请详细解释NMS：1.IOU的坐标处理逻辑；2.阈值设置的影响；3.多类别NMS的差异" |
| **② 粒度锚点法** | 给一个"多细才够"的样本 | "说明LSTM原理" → "请像这样解释：遗忘门用sigmoid的原因、细胞状态更新公式中ft的作用、梯度如何跨100步传递" |
| **③ 场景绑定法** | 绑定应用场景使细节"落地" | "讲池化层" → "在图像分割任务中，为什么用最大池化而非平均？池化步长为2时如何解决定位精度损失？" |
| **④ 结构化输出法** | 强制按格式输出，避免偷懒 | "解释BERT" → "请按结构输出：1.输入表示层（维度/位置编码）；2.MLM任务（mask比例/策略）；3.NSP任务（正负例采样）" |

**核心原则**: AI 的"细节输出能力"= 提示词的"细节引导精度"。专业细节永远是"被要求才会输出"的，而非 AI 主动"超额提供"的。

### 3.4 三层对话纪律

> **来源**: `05_tools/ai-tools/2026-06-23-09-ai-usage-methodology.md` §3

| 层级 | 纪律 | 示例 |
|:-----|:------|:------|
| **沟通纪律** | 锚定前提不跳出、抓主要矛盾、收束发散 | 不要在和 AI 聊技术方案时突然问无关问题 |
| **方法论纪律** | 结构化思考、对比分析规范、命名规范 | 对比分析必须同维度、同量纲 |
| **强制坦诚** | 让 AI 标注自己的不确定性 | 在输出末尾加"以上内容中，哪些是推论非事实？请标注置信度" |

## 四、AI 输出质检框架（12 特性维度）

> **文件**: `knowledge/methodology/industry-methodology/2026-07-13-ai-engineering-characteristics.md`（539 行）
> **核心判据**: 不同工程类型对 AI 输出的可信度下限不同，特性要求的优先级截然不同。

### 3.1 12 个特性维度速览

| 编号 | 特性 | 定义 | 反面案例 |
|:----:|:-----|:-----|:---------|
| C01 | **事实准确性** | 断言有可靠来源支撑，不编造 | 虚构芯片参数 |
| C02 | **可验证性** | 每项 claim 可追溯到原始来源 | "据行业报告"无出处 |
| C03 | **逻辑一致性** | 同上下文内不矛盾 | 前文 A＞B，后文用 B＞A |
| C04 | **可复现性** | 相同输入下输出一致 | 两次结果矛盾 |
| C05 | **量化严谨** | 数值+单位+基线+条件 | "性能提升30%"无基线 |
| C06 | **上下文记忆** | 记住项目约束和历史决策 | 反复忘记用户前提 |
| C07 | **领域术语精确** | 技术名词准确不混用 | PCIe带宽与速率混用 |
| C08 | **边界意识** | 明确知道不知道什么 | 假自信回答不熟悉领域 |
| C09 | **场景覆盖完备** | 正常+异常+边界 | 只给 happy path |
| C10 | **成本敏感** | 考虑实现/维护/机会成本 | 最优但不可落地 |
| C11 | **安全/合规意识** | 不引入安全漏洞 | 含 SQL 注入代码 |
| C12 | **可审查性** | 格式便于人工审查 | 长篇无分段无要点 |

### 3.2 工程类型×特性矩阵（部分关键摘录）

| 工程类型 | 最高优先级 | 独特要求 |
|:---------|:----------|:---------|
| **软件工程** | C01+C11+C09 | C06(上下文记忆)、C10(成本敏感) |
| **硬件工程** | C01+C05+C07 | C05(量化严谨)排第1、C12(可审查性) |
| **系统架构** | C03+C08+C06 | C10(成本敏感)排第4 |
| **数据工程** | C04+C02+C05 | C04(可复现性)排第1 |
| **安全关键** | C01+C11+C09 | 12 个维度 ALL P0 |

### 3.3 风险分级模型

| 风险等级 | 说明 | 验收标准 |
|:---------|:-----|:---------|
| **L1 参考** | 仅做灵感输入 | 任何质量都可接受 |
| **L2 辅助** | 辅助效率工具 | C01+C07+C11 通过即可 |
| **L3 决策支持** | 影响关键判断 | C01~C08 必须满足 |
| **L4 自动执行** | AI 产出直接作用生产 | 全 12 维度验证+人工复审 |

## 五、AI 生产流水线（六阶段）

> **文件**: 对应六个 Pipeline Skill 文件
> **核心思想**: 将 AI 产出视为工厂化流水线——每个阶段有独立的质量门。

```text
输入(Quality Gate)
    v
① 输入质量门 (Input QA) — 校验输入完整/来源可信/一致性/可行性
    v
② 多路并行 (Multi-Path) — 多视角独立处理，隔离上下文/Token/失败域
    v
③ 汇聚 (Convergence) — 加权来源可信度+冲突消解+跨路交叉验证
    v
④ Ralph 循环验证 (Verification Loop) — Plan->Do->Check->Act 自主迭代
    v
⑤ 约束强制 (Constraint Enforcer) — 安全红线+质量标线+工程约束+依赖审计
    v
⑥ 专家把关 (Expert Gate) — 终审：标注AI边界+判断不可自动化维度+退回路由
    v
输出
```

## 六、AI 工程熵增与约束验证

> **核心文件**: `2026-07-10-ai-engineering-entropy-and-constraint.md`（61KB/1533行）
> **工程痛点**: AI 会忽略约束条件，不断在工程中随心所欲添加文件，中间文件不删除，代码模式不加收敛，导致**工程熵增**（技术债指数级增长），最终系统不可维护。
> **核心洞察**: AI 的「高效率生成」与「低自律清理」是一体两面——AI 没有「维护成本」的概念。

### 6.1 熵增的四大根因

| 根因 | 本质 | 表现 | 后果 |
|:-----|:------|:-----|:------|
| **无维护成本意识** | AI 没有"长期维护"概念 | 生成后从不删除清理 | 文件爆炸，目录混乱 |
| **模式复制无收敛** | 倾向复制现有模式（含坏模式） | 坏模式被反复复制放大 | 架构漂移加速 |
| **无中间产物管理** | 生成大量中间文件认为"下次还用" | tmp/cache/backup 文件泛滥 | 磁盘膨胀，版本混乱 |
| **无架构一致性** | 每次生成略有不同风格 | 同一项目多种代码风格 | 维护成本指数增长 |

**量化数据**: AI 辅助生成的代码库在 **3 个月内的技术债规模是传统人工代码库的 5-8 倍**（OpenAI 内部实验数据）。

### 6.2 Harness Engineering 四层约束体系

```text
+--------------------------------------------------+
|  L4 组织约束                                     |
|  编码规范+CI/CD+CodeReview 制度化                |
+--------------------------------------------------+
|  L3 验证约束                                     |
|  自动化测试+lint+security scan 前置化             |
+--------------------------------------------------+
|  L2 架构约束（最有效）                            |
|  目录结构固化+接口契约+严格的模块边界              |
+--------------------------------------------------+
|  L1 规则约束（最弱）                              |
|  Prompt 中的"请保持简洁""不要添加多余文件"         |
+--------------------------------------------------+
```

> **关键**: 约束层级越低越可靠。L1 规则约束依赖 AI 遵守率（~50-80%），L2 架构约束通过工程边界强行阻止（~95%+）。

### 6.3 熵管理三机制

| 机制 | 做法 | 频率 |
|:-----|:------|:----:|
| **定期清理** | 自动清理中间文件、过期产物 | 每次 commit 触发 |
| **模式收敛** | 代码风格检查+架构漂移检测 | CI 阶段自动执行 |
| **债务追踪** | 用 TODO/FIXME/HACK 标记量化技术债 | 持续追踪，周报汇总 |

### 6.4 五类约束失效模式

| 模式 | 表现 | 检测方法 |
|:-----|:------|:---------|
| **未遵守约定** | 未按目录结构生成文件 | 目录结构快照对比 |
| **约束退化** | 初期遵守后期忽略 | 逐步违反的阈值监控 |
| **约束冲突** | 多条规则自相矛盾 | 规则 MECE 审查 |
| **过约束瘫痪** | 约束过多导致生成质量下降 | 约束数量 vs 质量曲线监控 |

## 七、材料可信度评估（四维框架）

> **文件**: `knowledge/methodology/industry-methodology/2026-07-13-material-credibility-matrix.md`（739 行）
> **核心洞察**: 没有天生"可信"的材料类型，只有"被验证程度"的差别。

### 5.1 可信度四维度

| 维度 | 定义 | 问法 |
|:-----|:-----|:-----|

| **方法可信度** | 过程的可追溯性 | 过程细节能否复现？ |
| **立场可信度** | 利益相关方的偏误 | 谁写的？目的是什么？ |

### 5.3 交叉验证三原则

> **最强的可信度 = 论文方法 + 第三方结果 + 量产数据（三合一）**

1. **跨类型验证**: 同一结论来自 ≥3 种不同类型的材料
2. **独立来源验证**: 同一数据来自 ≥2 个无利益关系的主体
3. **逆向验证**: 试图找证伪的证据，而不是只找证实的

## 九、AI 使用哲学与失效模式自检

> **核心来源**: `05_tools/ai-tools/2026-07-09-ai-usage-philosophy.md`（122KB/1789行）· `light-self-review` 技能 · AGENT.md 自检清单
> **核心理念**: **AI 如实验室仪器**——提供原始数据/图谱，但最终解读靠人的领域功底。

### 9.1 三个必备能力

| 能力 | 说明 | 类比 |
|:-----|:------|:------|
| **想法与路径规划** | 知道自己要什么，能拆解目标给 AI 方向 | 实验方案设计 |
| **验证能力** | 事实核查、逻辑校验、数据验算 | 实验过程监控 |
| **评判标准** | 自己的质量标尺，判断"好不好""够不够" | 实验结果判定 |

### 9.2 约束失效的三个独立维度

> **核心洞见**: AI 使用中的大部分问题不是单一根源，而是三个完全不同维度的失效叠加。

| # | 失效维度 | 本质 | 通俗表述 | 类比 | 应对策略 |
|:-:|:---------|:------|:---------|:-----|:---------|
| **I** | **约束忽略** | 该做的没做 | 说了它做不到 | 员工不遵守公司政策 | 四法门+分层+反馈闭环 |
| **II** | **方向锁定** | 不该做的做了 | 被带偏走到底 | 员工过度执着老板随口一句话 | 显式终止条件+安全词+范围限定 |
| **III** | **输入污染** | 基础就不对 | 吃垃圾吐垃圾 | 用错误数据做分析报告 | 源头验证+输入质量门+交叉检查 |

**三者 MECE**: 约束忽略是"信号衰减"、方向锁定是"信号过强"、输入污染是"信源质量"——三者原因截然不同，应对策略也截然不同。

### 9.3 五层管道 + A-J 十类失效模式自检

### 9.4 A-J 十类失效模式（自检提纲）

| 编号 | 失效模式 | 典型表现 | 检查问题 |
|:----:|:---------|:---------|:---------|
| **A** | 信源污染 | 引用不可靠来源或编造来源 | 断言有出处？来源可追溯？ |
| **B** | 注意力漂移 | 核心约束被上下文推远 | 关键规则是否在注意力窗口内？ |
| **C** | 知识幻觉 | 自信回答训练数据外的内容 | 不确定时是否标注？ |
| **D** | 推理断裂 | 前提→结论的链条缺失 | 推理步骤是否完整？ |
| **E** | 框架堆砌 | 名词堆叠但不深入原理 | 每个概念是否 >1 层解析？ |
| **F** | 数据缺失 | 结论缺少数值/基线/条件 | 有无"数值+单位+基线+条件"？ |
| **G** | 夸大结论 | 超出实验/证据可支持范围 | 结论是否 <= 证据强度？ |
| **H** | 格式混乱 | 结构无 TOC、编号跳跃、链接失效 | 文档规范性自检？ |
| **I** | 审美不一致 | 图表/风格/术语不统一 | 跨文件术语是否一致？ |
| **J** | 不可执行 | 输出缺少落地路径 | 读者能否按文档操作？ |

### 9.5 每轮输出前的自检清单

```text
□ 断言有出处？来源可追溯？
□ 数据: 数值+单位+基线+条件，缺一不可？
□ 文档: TOC+交叉链接+changelog？
□ 框架堆名词不深入原理 -> 不合格
□ 能否再迭代一轮？哪里还不够锋利？
```

### 11.1 两类用户画像

| 维度 | 主动优化型（可控增强） | 被动适配型（黑箱依赖） |
