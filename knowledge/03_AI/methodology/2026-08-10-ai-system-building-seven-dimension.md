## 摘要（TL;DR)

**核心命题**：基于 AI 的系统不是"堆模型 + 堆工具"，而是一个**七维度必须联动的整体**。任何一维单独优化都会在系统级产生瓶颈；七维的"目标一致性"决定系统成败（呼应三位一体：标准是目标的函数）。

**七个维度的本质**：
| 维度 | 一句话本质 | 关键决策 |
|:-----|:-----------|:---------|
| 1 基础设施 | 算力的**来源与形态**，不是性能而是**可用性×成本** | 云 vs 本地，按工作负载分 |
| 2 模型选取 | 能力的**供需匹配**，成本×能力×接入三角 | 按任务分档，不是选一个 |
| 3 工具与约束 | 系统能力的**边界**，知道能做什么+缺什么 | tool 层 vs skill 层分层 |
| 4 产出分类 | 输出的**价值分级**，决定投入强度 | 按价值/量级分级精雕 |
| 5 数据源与目的 | 系统**进化的燃料**，反馈闭环 | 引用关系 + 一致性治理 |
| 6 泛化处理 | 系统的**成长性**，应对复杂度与成本上升 | 架构预留 + 成本曲线 |
| 7 方向思考 | 系统的**演进方向**，封装与强化 | tools→skills 定制 |

**三个贯穿性洞察**：
1. **分模块定目标**（单一目标原则）：不同模块不同目标与标准，避免"目标混入"（56 检查器教训）；
2. **价值链分层**：采集=素材/加工=洞察/沉淀=生产/应用=学习，每层单一目标、分级标准；
3. **AI 产出=毛利非净利**：系统价值要扣除 AI 的"原料成本"看净产出（40% 红线），否则陷入认知寄生。

## 维度 1：基础设施选型与搭建

### 1.1 本质：算力的来源与形态

基础设施决策**不是性能竞赛，而是「可用性 × 成本 × 控制力」三角**。性能由模型厂商在模型侧解决，你买的是"在需要时能用到算力"。

| 决策维度 | 云 | 本地设备 |
|:---------|:---|:---------|
| 初始成本 | 低（按需）| 高（一次性）|
| 边际成本 | 持续（按量）| 低（用越多越省）|
| 可用性 | 高（供应商 SLA）| 依赖本地电源/网络/运维 |
| 控制力 | 低（数据出域风险）| 高（数据本地）|
| 弹性 | 极高（秒级扩缩）| 低（峰值需预置）|
| 适用 | 波动负载/起步/无需数据主权 | 稳定负载/数据敏感/长期高频 |

### 1.2 判定框架：按工作负载分，不搞二选一

- **起步/波动/实验** → 云（先跑起来，验证价值再固化）；
- **稳定高频/数据敏感/隐私合规** → 本地（边际成本低 + 数据主权）；
- **混合**：核心机密走本地，突发弹性走云（最常用，成本与控制的折中）。

### 1.3 关键原则

1. **按负载曲线选，不按峰值选**：峰值弹性交给云，基线负载本地扛——避免"为 1% 峰值买了 100% 容量"；
2. **可移植性优先**：接口标准化（API/容器化），云本地可迁移，防止被单一供应商锁定（vendor lock-in）；
3. **数据主权是硬约束**：敏感数据出域风险不可逆，先问"这数据能出域吗？"再谈算力；
4. **本系统实证**：本地 + 多渠道接入（feishu/web），数据全本地化，控制力最大化——适合知识库/个人皮层类系统；纯算力密集训练则云更优。

## 维度 2：模型选取与配置

### 2.1 本质：能力的供需匹配——「成本 × 能力 × 接入」三角

模型不是选一个最好的，而是**按任务分档，让能力与需求匹配**（避免大材小用烧钱，或小材大用掉链子）。

### 2.2 三种接入方式的成本-能力权衡

| 接入方式 | 成本 | 能力上限 | 控制力 | 适用 |
|:---------|:-----|:---------|:-------|:-----|
| **API（官方/三方）** | 按 token 付费 | 最强（前沿模型）| 低 | 生产主力、需最新能力 |
| **自部署（开源权重）** | 固定（算力+电费）| 中（开源上限）| 高 | 隐私/离线/长期高频 |
| **免费档/白嫖** | 近零 | 弱/限流/不稳定 | 低 | 起步验证、低频、非关键 |

**API vs Coding Plan（编程计划订阅）**：Coding Plan（如 Cursor/Claude Code 订阅）本质是"固定月费换编码场景配额"，适合**高频编码**；API 按量付费适合**全场景但低频**。判断 = 月 token 量 × 单价 对比订阅价，且考虑场景专精（Coding Plan 的编码优化 vs 通用 API 的灵活性）。

### 2.3 免费模型怎么用（务实策略）

1. **降级档位**：把免费模型放在"非关键/草稿/探索"档，关键生产用付费 API——按产出价值分档（呼应维度 4）；
2. **限流管理**：免费档有限流，用**队列/重试/缓存**消化，不用于实时关键路径；
3. **能力边界诚实**：免费档复杂约束执行差（如"零外部依赖"仍引 CDN），**硬约束任务不交给它**；
4. **作为评测基线**：免费档 = 性价比锚点，判断"值不值得为更强能力付钱"（呼应 Agent 评测方法论）。

### 2.4 配置的关键参数（选型后还要调）

| 参数 | 作用 | 权衡 |
|:-----|:-----|:-----|
| reasoning_effort | 思考深度 | 越深越准越慢越贵 |
| 上下文窗口 | 能装多少 | 越大越贵，且"装得多≠用得好" |
| 单任务最大步数 | 允许多少工具调用 | 太少截断任务，太多死循环风险 |
| 温度/采样 | 随机性 | 创作高/事实低 |

### 2.5 选型的量化依据（对接评测方法论）

选模型不该拍脑袋，用 [`Agent 评测方法论`](../agent-engineering/2026-08-10-agent-evaluation-methodology.md) 的**六维矩阵**做端到端实测，重点看：
- **成本权重**：Agent 一次任务几十次调用，**单价权重极高**（Flash 几十分之一的价格是决定性优势）；
- **稳定性 > 单次能力**：无死循环、无参数解析失败比单次高分更重要；
- **长上下文落地姿势**：懂"落盘+检索"比"装得下 1M"更有用；
- **本系统实证**：deepseek-v4-flash-ga-260731 作日常默认（性价比），复杂任务升 reasoning_effort——"分档用模型"是成本治理第一杠杆。

## 维度 3：自身工具、定义、约束

### 3.1 本质：系统能力的「边界」

工具定义了你**能做什么**；约束定义了你**不做什么**。理解工具的边界（能做什么、缺什么、哪些要补）是系统能否"正确使用 AI"的关键——不了解原理与限制，配置就是盲配。

### 3.2 原理理解 → 合理配置（第一性原理）

要真正用好，需要理解 **AI 的限制**（这是配置的基础）：
- **上下文是稀缺资源**：不是越多越好，而是"该装什么进上下文"（落盘+检索 > 全量塞入）；
- **能力不等于可依赖**：强能力也会在复杂约束下打折（零外部依赖仍引 CDN），需显式约束 + 验证；
- **幻觉与过时**：长记忆可能过时（"信任过时记忆比无记忆死 2 倍"）、文本可解≠视觉落地——配置要含真实性/时机检查；
- **token 是成本**：每次调用都有成本，工具调用次数直接反映成本（克制 vs 死循环）。

### 3.3 工具分层：tool vs skill

| 层 | 定义 | 例子 | 特性 |
|:---|:-----|:-----|:-----|
| **Tool（工具）** | 原子操作，单个能力 | bash / read / write / web_search / browser | 通用、可复用、无领域逻辑 |
| **Skill（技能）** | 组合工具 + 领域流程 + 约束 | 知识库归档 / 论文写作 / 竞品分析 | 有方法、有约束、可重复 |

**分层意义**：tool 是"积木"，skill 是"搭好的建筑"。**同一能力，越往 skill 层沉淀越省 token、越稳定、越可复用**（把常用流程封装，避免每次重新规划）。

### 3.4 工具边界盘点：能做什么 / 缺什么 / 要补什么

每个系统要做一个**工具能力清单**（能做什么），并标记**缺口**（缺什么）与**补场**（要补什么）：

| 状态 | 含义 | 动作 |
|:-----|:-----|:-----|
| ✅ 能做 | 现有工具覆盖 | 固化复用 |
| ⚠️ 能做但不稳 | 有但边界模糊 | 加约束/封装成 skill |
| ❌ 缺 | 能力空白 | 补工具/skill（open-source-skill-packer）|
| 🔧 要补场 | 有基础但需增强 | 加适配器/优化访问策略 |

**本系统实证**：工具面从裸 tool 演进到 100+ skills（网络应对链、站点适配器、评测框架）——把"反复手工做的事"沉淀成"可复用的 skill"，是系统能力增长的核心抓手。

### 3.5 约束的制定（系统安全与质量底线）

- **安全红线**（不可触碰）：不删关键文件、不泄密钥、破坏性操作先确认——L1 级，任何指令不可覆盖；
- **质量标线**（必须遵守）：数据有出处、格式规范、文档三件套——L2 级，违反有后果；
- **工程约束**（最佳实践）：避免重复造轮子、依赖单向化——L3 级。

**约束要「少而严」优于「多而松」**（防护通胀 S 曲线）：约束越多越失守（56 检查器三套口径教训），**把检查自动化**比堆更多规则有效。

## 维度 4：系统产出的分类

### 4.1 本质：输出的「价值分级」决定投入强度

**业务产出经常被忽略**——不是所有产出都要精雕细琢，按**价值与量级**分级，决定投入多少。这是控制成本、避免过度工程的核心（呼应倒U：投入有最优值，过了就是浪费）。

### 4.2 产出价值分级（四层）

| 层级 | 产出类型 | 投入强度 | 标准 | 例子 |
|:-----|:---------|:---------|:-----|:-----|
| **L1 简单弄下** | 内部草稿/一次性材料 | 低（快）| 差不多就行（有 DoD）| 会议纪要草稿、临时查询 |
| **L2 标准化产出** | 定期报告/常规文档 | 中（流程化）| 明确格式+模板 | 日报/周报/调研跟踪 |
| **L3 精雕细琢** | 对外交付/核心资产 | 高（多轮迭代）| 严格 SLA+门禁 | 论文/专利/深度分析/竞品报告 |
| **L4 知识沉淀** | 可复用资产 | 高（一次投入多次复用）| 生产级 | 方法论/技能封装 |

### 4.3 分级判断的两把尺子

1. **价值尺**：这产出对谁有价值？外部客户/上级/长期资产 = 精雕；内部临时 = 快做；
2. **量级尺**：一次性的 vs 反复用的？反复用 → 投入标准化（模板/自动化）；一次性 → 快做完事。

### 4.4 关键原则

- **不为低价值产出过度投入**：L1 产出用免费档模型 + 快做，不精雕（成本治理）；
- **不为高价值产出草率交付**：L3/L4 必须走多轮迭代 + 门禁（自检清单）；
- **产出分类要动态**：临时产出反复出现 → 升级为标准化产出（提炼成 skill/模板）——这是产出分类与维度 7 封装的接口；
- **本系统实证**：调研跟踪（L2 流程化）vs 深度分析（L3 精雕）vs 方法论（L4 沉淀）分级明确，各有对应质量门禁——避免"素材目标用万无一失标准"的错配（三位一体警示）。

## 维度 5：数据源与目的的多轮强化

### 5.1 本质：系统「进化的燃料」与「反馈闭环」

系统不是一次性搭好就完，而是靠 **数据源（输入）→ 目的（输出）** 的**多轮强化**不断进化。这包含两个关键治理：**引用关系** 与 **一致性**。

### 5.2 数据源：燃料的质量决定系统高度

| 数据源特征 | 影响 | 治理 |
|:-----------|:-----|:-----|
| 覆盖面 | 系统见过的世界 | 多源采集 |
| 质量 | 产出准确性 | 来源分级/交叉验证 |
| 时效性 | 结论是否过时 | 定期刷新 |
| 主权/合规 | 能否使用 | 隐私/版权检查 |

**数据源治理原则**：关键量化数据必须**独立源交叉验证**（官方规格/标准组织/可复现推导），多源不一致时以验证源为准并标注分歧——不编造引用/百分比（RULE 铁律）。

### 5.3 引用关系处理：知识的「追溯链」

- **每个结论可追溯来源**：文档含 Source 行、引用原始 URL、数据标注（数值+单位+基线+条件）；
- **交叉链接建图谱**：知识页互相 link（相关阅读/兄弟节点），形成可导航的知识图而非孤立文件；
- **引用即契约**：文档承诺的脚本/能力要能实现，否则降级标注或豁免——**不可承诺不兑现**。

### 5.4 一致性处理：多轮强化中防「漂移」

多轮强化（多次迭代、多 session 加工）最大的风险是**一致性漂移**：

| 一致性维度 | 风险 | 治理 |
|:-----------|:-----|:-----|
| 术语一致 | 同一概念不同叫法 | 术语表/SSOT |
| 数据一致 | 不同文档数字对不上 | 单一数据源 + 交叉引用 |
| 结论一致 | 前后判断矛盾 | 追溯链 + 版本锚定 |
| 引用一致 | 链接断裂 | link-validator 定期扫 |

**本系统实证**：link-validator 全库 67,503→0（92% 是 TOC 伪锚点）、术语/创新点表述统一（light-consistency）——一致性治理是知识系统可持续进化的前提，否则多轮强化会越积越乱。

## 维度 6：泛化处理（扩展性/复杂度/成本）

### 6.1 本质：系统的「成长性」

泛化 = 系统能否**应对复杂度增加与成本上升**而不过度膨胀、不失稳。这是"能跑起来"到"能一直跑"的分水岭。

### 6.2 应对复杂度增加

| 复杂度来源 | 表现 | 应对 |
|:-----------|:-----|:-----|
| 数据量增长 | 文件/知识爆炸 | 分层存储 + 检索优先（落盘+检索）|
| 工具增多 | 能力碎片化 | 分层（tool/skill）+ 查重防重复 |
| 流程变长 | 链路复杂 | 管线化 + 断点续传 |
| 约束增多 | 规则膨胀 | 少而严 + 检查自动化 |

**复杂度治理的核心原则**：
1. **模块化/分层**：依赖单向化，层间解耦（改动局部化）；
2. **单一目标原则**：每模块只追一个目标，避免验收模糊、投入无边界；
3. **防碎片化**：新能力先查重，能并入现有就并入（56 检查器教训）；
4. **抽象分层分治**：MECE 分解，同层互斥且穷尽。

### 6.3 应对成本上升（成本曲线治理）

成本随规模上升，关键是**理解成本曲线形态**并设最优投入点：

| 成本类型 | 曲线 | 治理 |
|:---------|:-----|:-----|
| token 成本 | 线性→随规模陡升 | 分档用模型 + 缓存 + 压缩上下文 |
| 维护成本 | 随自研脚本 O(n²)| 工具化 + 商品化迁移 |
| 存储成本 | 线性 | 分层存储 + 定期清理 |
| 约束成本 | 超线性（越多越贵）| 少而严 |

**关键认识**：
- **AI 产出=毛利非净利**：系统价值要扣 AI 的原料成本看净产出，否则投入无边界（40% 红线）；
- **倒U规律**：每个模块投入有最优值，过了就是浪费（防过度工程）；
- **工具链商品化迁移**：自研的东西被开源追上就迁移，释放维护成本；
- **成本优先降**：合并 session > 减请求 > 缩输出（token 治理实证，缓存未命中是最大成本）。

### 6.4 扩展性的架构预留

- **接口标准化**：让新工具/新模型/新渠道可插拔（换模型=纯配置）；
- **数据可移植**：不绑定单一供应商（防锁定）；
- **渐进式构建**：先跑通最小闭环，再逐步加维度（避免一上来就追求大而全）。

## 维度 7：方向的思考（tools→skills 定制封装）

### 7.1 本质：系统的「演进引擎」

方向思考 = 决定系统**往哪进化**。核心是：**把反复做的事情封装成能力，把能力强化成可复用的资产**。这是系统从"能用"走向"越用越好用"的驱动力。

### 7.2 tools → skills：定制封装（用户提出，重点展开）

**核心判断：要不要封装？** 不是所有工具都要封装，按「复用频率 × 复杂度」判定：

| 复用频率 \ 复杂度 | 简单 | 复杂 |
|:-----------------|:-----|:-----|
| **高频** | 封装（值得）| **封装（最值得，省最多）** |
| **低频** | 不封装（直接调用）| 封装（有流程价值但低优先级）|

**封装的价值**：把"每次重新规划怎么用工具"变成"直接按 skill 流程走"——**省 token、更稳定、可复用、沉淀方法论**。

### 7.3 用户举的例：web search 定制封装（展开）

把 `web_search` 从裸工具封装成 skill，内置常用网站的处理策略与访问优化：

| 现状（裸 web_search）| 封装后（定制 skill）|
|:---------------------|:-------------------|
| 每次现想搜什么、怎么解析 | 内置各站点访问策略（适配器）|
| 面对反爬/验证码手足无措 | 内置绕过策略（微信 UA/落盘检索）|
| 结果良莠不齐 | 内置来源分级（主源优先/交叉验证）|
| 每次重复踩坑 | 沉淀为可复用流程 |

**本系统实证**（web-archive v2.0 / 网络应对链）：9+ 站点适配器、微信三要素反爬绕过、降级策略链（直抓→UA→playwright）——把"访问网页"这一个裸工具封装成"带站点智能的归档 skill"，省了大量重复踩坑。这就是 tools→skills 封装的标准范式。

### 7.4 记忆的强化（用户提出）

记忆是 Agent 系统的"长期能力"，强化方向：
- **分层记忆**：长期索引（MEMORY.md）/每日记忆（memory/）/结构化知识（knowledge/）分级存储；
- **检索优先**：记忆检索 keyword-only → 启用 embedding 语义检索（更高杠杆）；
- **蒸馏与压缩**：离线整理压缩（类似 Dreaming）、技能蒸馏（把经验提炼成 skill）；
- **一致性治理**：防记忆过时（真实性/时机检查）、防认知寄生（AI 依赖萎缩）。

### 7.5 方向思考的决策框架

| 考虑 | 问自己 | 动作 |
|:-----|:-------|:-----|
| 封装 | 这事是否高频复用？| 是→封装成 skill |
| 强化 | 现有能力是否瓶颈？| 是→强化（记忆/检索/工具）|
| 扩展 | 是否该补新能力？| 按业务价值排优先级 |
| 放弃 | 是否被商品化覆盖？| 是→迁移释放维护成本 |

**方向思考的本质**：不是"多造工具"，而是**让系统沿着"越用越省力、越用越懂你"的方向进化**——把临时做法沉淀为能力，把能力沉淀为资产。

## 七维联动：一个系统的完整闭环

七维不是孤立模块，而是**一条从搭建到进化的闭环**：

```text
[1基础设施] → [2模型选取] → [3工具约束] → [4产出分类]
                                        ↓
[7方向思考] ← [6泛化处理] ← [5数据源目的多轮强化]
   ↑                                              ↑
   └────────── 沉淀/强化（进化燃料）──────────────┘
```

**闭环逻辑**：①搭好算力 → ②选对模型 → ③定义工具约束 → ④按价值分级产出 → ⑤靠数据源多轮强化并治理引用/一致性 → ⑥应对复杂度与成本成长 → ⑦沿"封装+强化"方向进化，进化成果（新 skill/更聪明的记忆）又反馈回 ①-④ 提升系统能力。

**贯穿主线：目标一致性**。七维的每一环都要服务同一个"目标"（三位一体），任何一环单独优化都可能在系统级产生瓶颈——**目标错配是系统失败第一原因**。

## 建议汇总

### 按维度落地建议
1. **基础设施**：按负载曲线分云/本地，混合最优；数据主权是硬约束；
2. **模型**：按任务分档用模型（免费档降级/生产档付费/复杂任务升 reasoning_effort）；用 Agent 评测六维矩阵做选型依据；
3. **工具约束**：tool/skill 分层，盘点能力清单（能做/缺/补场）；约束"少而严"+检查自动化；
4. **产出分类**：按价值分级定投入（L1 快做/L2 流程化/L3 精雕/L4 沉淀）；临时产出反复出现→升级标准化；
5. **数据源目的**：多源交叉验证；引用可追溯；一致性防漂移（术语/数据/结论/引用四维）；
6. **泛化**：模块化防碎片化；理解成本曲线设最优投入；接口标准化预留扩展；
7. **方向**：高频复用→封装 skill；记忆分层+检索强化；被商品化覆盖→迁移。

### 全局建议（贯穿）
- **分模块定目标**（单一目标原则），每模块独立目标与标准；
- **价值链分层**（采集=素材/加工=洞察/沉淀=生产/应用=学习），每层分级标准；
- **AI 产出=毛利非净利**：扣原料成本看净产出，设 40% 红线；
- **渐进式构建**：先最小闭环，再逐维扩展。

---

## 风险与边界

- **七维联动的前提是目标清晰**：目标模糊 → 七维各自为政 → 系统失序（先定目标再逐维落地）；
- **"封装"要克制**：封装过多 = 技能碎片化/查重负担，按复用频率判定，不盲目封装；
- **"分档用模型"需评测支撑**：不量化评测的"分档"是拍脑袋，需成本-能力数据；
- **一致性治理是持续成本**：需定期扫描（link-validator/术语检查），不是一次性；
- **本分析为方法论综合**（基于本系统实证 + 既有方法论，无在线来源需求）：核心论据来自 08-10 系列实证与 MEMORY 方法论沉淀。
