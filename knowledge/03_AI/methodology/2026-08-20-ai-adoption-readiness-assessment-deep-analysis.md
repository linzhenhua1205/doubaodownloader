## 1. 评估方法与证据体系

### 1.1 评分标尺（0-5）

| 分数 | 含义 | 判定标准 |
|:----:|:-----|:---------|
| 5 | 成熟运行 | 有制度/工具/实践，且持续运行 3 个月以上，有度量数据 |
| 4 | 基本就绪 | 核心要素齐备，小范围运行，缺系统性度量 |
| 3 | 部分就绪 | 要素部分具备，未形成闭环，靠个人经验 |
| 2 | 初步起步 | 有意识/有零星动作，无体系 |
| 1 | 空白 | 未开始或仅口头提及 |
| 0 | 负向 | 存在与目标相悖的现状（如已发生数据泄露事件） |

### 1.2 证据等级定义

| 等级 | 含义 | 示例 |
|:----:|:-----|:-----|
| 🟢 已证实 | 知识库/记忆有直接记录 | "token 缓存未命中 57.1%（08-15 实测）" |
| 🟡 推断 | 从间接信息合理推断，标注推断链 | "团队有隔离研发网" ← 服务器研发企业普遍形态 + 用户提到过配置器/BOM 等内网系统 |
| 🔴 待确认 | 无任何依据，须用户回答 | "公司是否已有 DLP 系统" |

### 1.3 评估对象分层

```
L1 PERSONAL: the user (deep AI user)            <- strongest evidence
L2 TEAM:     server R&D team (colleagues)       <- partly inferred
L3 POLICY:   corp IT/security/procurement/legal <- mostly unconfirmed
```

> **重要声明**: 本评估的 L2/L3 层分数基于"服务器整机研发企业典型形态 + 知识库间接信息"的**基线估计**，作用是暴露必须确认的问题，而非精确测量。用户按 §9 清单回答后，分数可一键修正。

### 2.2 就绪度画像：一人先行，组织未动

```
PERSONAL #################### 3.9  deep user (CowAgent mature)
```

**核心判断**: 团队 AI 导入处于典型的**"一人先行"阶段**——个人已跑通全链路（调研→分析→知识沉淀→成本治理），但组织层面（团队推广、信息安全、流程嵌入）基本空白。这带来双重含义：

1. **风险**: 个人高成熟度容易造成"AI 已落地"的错觉，实际组织就绪度仅 2.0——尤其是**信息安全 1.8 分**意味着：一旦把个人实践推广到团队，机密数据经公共 AI 服务外泄的概率会随使用人数线性上升
2. **机会**: 个人已验证的方法论（token 五技术、知识库管线、调研 runner）可直接**复制为团队基线**，无需从零探索——从 2.6 → 3.5 的路径清晰且低成本

### 3.2 深入展开：环境落地细节

**（a）部署形态矩阵（团队级建议）**

| 通道 | 承载模型 | 数据范围 | 前置条件 | 运维责任 |
|:-----|:---------|:---------|:---------|:---------|

> 关键洞察：**通道B 是服务器厂商的独特优势**——自研 8 卡 AI 服务器本身就是"私有化部署"的最优载体，既是产品验证场景又是团队 AI 基础设施，一鱼两吃。建议优先规划通道B。

- [ ] 建立账号生命周期流程（入职开通/离职回收）
- [ ] 确认供应商数据处理条款（数据存储地/留存期/训练用途）

**（c）本地算力规格建议**

| 目标模型 | 显存需求（INT4） | 建议硬件 | 备注 |
|:---------|:----------------|:---------|:-----|

## 4. 支柱二 Token 成本：就绪度 3.5/5（最强支柱）

### 4.1 逐项打分

| 排查项 | 分数 | 证据 | 依据 |
|:-------|:----:|:----:|:-----|
| 计费模型认知 | 5.0 | 🟢 | 有实测基线：缓存未命中 57.1%、08-17 涨价 +186% 均记录在案 [🟢 MEMORY] |
| 用量预估 | 4.0 | 🟢 | 有 token-per-turn 审计方法、单任务基线概念 [🟢 知识库] |
| 优化杠杆落地 | 4.5 | 🟢 | 五技术全掌握（缓存/修剪/路由/压缩/门控）+ 深度分析铁律（上下文重置、summary 注入）[🟢 知识库] |
| 监控与门控 | 3.5 | 🟢 | CowAgent 有 usage 落盘、40% 红线监控 [🟢 知识库]；团队级仪表盘缺失 |
| 团队预算机制 | 1.5 | 🔴 | 团队级预算帽/配额/成本分摊未知 |

### 4.2 深入展开：成本治理落地细节

**（a）预算治理三层机制**

```
L1 ORG:   monthly dept budget cap (amount+usage) -> 80% warn / 100% kill
L2 PROJ:  quota by cost center -> approval flow on exceed
L3 TASK:  per-task cost gate (pre-exec) -> auto-abort at 3x baseline
```

> 核心原则（来自知识库已验证结论）: 预算治理必须按**用量**设基线而非仅金额——因为供应商调价（如 08-17 +186%）可让同用量成本翻倍，金额基线会失效 [🟢 知识库 token 优化五技术]

**（b）团队推广时的成本放大模型**

```
team monthly cost = per-capita daily usage x headcount x workdays x unit price
e.g. 30 x 200K tok/day x 22d x 2 CNY/M ~ 264 CNY/mo (light)
     30 x 2M tok/day (deep) x 22d          ~ 2,640+ CNY/mo (deep)
```

> 关键洞察: 从个人（月数百元）到团队（月数千元）成本放大 10 倍量级，但**人均成本可通过路由降 50-80%**——简单任务（翻译/格式化/总结）路由到本地小模型，复杂任务（深度分析/代码生成）才用旗舰。这正是意图路由杠杆的价值 [🟢 知识库]。

**（c）个人实践 → 团队基线的直接迁移项**

| 个人已验证实践 | 迁移为团队机制 |
|:---------------|:---------------|
| 深度分析铁律（上下文重置+summary 注入） | 团队深度任务执行规范 |
| token-per-turn 审计 | 团队用量日报（按人/按项目） |
| 40% 红线监控 [🟢 08-14 决策] | 部门 AI 投入占比季度报告 |
| 缓存友好架构（稳定 system prompt） | 团队提示词模板标准化 |

## 6. 支柱四 信息安全：就绪度 1.8/5（最大短板）

### 6.1 逐项打分

| 排查项 | 分数 | 证据 | 依据 |
|:-------|:----:|:----:|:-----|
| 风险认知 | 3.0 | 🟡 | 有 AI 工具观（防降智/判断力不可外包）[🟢 MEMORY]；但无系统性风险面盘点 |
| 数据分级制度 | 1.0 | 🔴 | 公司是否有数据分级制度未知；AI 场景分级路由未建立 |
| 技术管控（DLP/审计） | 1.5 | 🔴 | 传统信息安全制度大概率存在（等保/密评要求）[🟡 服务器厂商合规常态]；AI 专项管控未知 |
| 制度与政策 | 1.5 | 🔴 | AI 使用政策是否存在未知 |
| 服务器研发专项 | 2.0 | 🟡 | 有固件安全/产品保密的行业常识 [🟡]；未体系化 |

### 6.2 深入展开：信息安全落地方案细节（本章为重点）

#### （a）数据分级 × 处理通道矩阵（落地核心）

| 密级 | 典型数据（服务器研发） | 允许通道 | 责任人 | 示例 |
|:-----|:----------------------|:---------|:-------|:-----|
| **L4 绝密** | 未发布机型 Roadmap、BMC 安全启动密钥、客户定制方案、固件源码 | 仅通道D（断网沙箱）| 项目负责人 | 新平台核心架构文档 |
| **L3 机密** | 内部架构设计、竞品拆解数据、BOM/成本、供应链报价 | 通道B/C（本地/私有化）| 部门负责人 | 竞品分析报告、成本台账 |
| **L2 内部** | 通用研发规范、脱敏代码、测试报告（去客户信息） | 通道A/B（云 API 需脱敏）| 全员 | 技术方案评审稿 |
| **L1 公开** | 行业标准、公开论文、公开规格书 | 任意 | 全员 | 标准规范检索 |

> **分级路由是第一道闸门**: 不依赖 DLP 事后拦截，而是**事前约定数据不能去哪个通道**。服务器研发最易泄露的是 L3（竞品/BOM/成本）——这些恰恰是最常被 AI 处理的数据类型（分析、对比、总结）。

#### （b）技术管控部署架构

```
ENDPOINT  IDE plugin control / clipboard monitor / sandbox
              |
NETWORK   unified proxy(whitelist) / TLS audit / egress DLP
              |
SERVICE   CASB / API gateway audit
              |
DATA      masking engine (serial/customer/price/key)
              |
AUDIT     full logs (who/when/what/channel/why)
```

| 层 | 工具/机制 | 部署要点 | 优先级 |
|:---|:---------|:---------|:------:|
| 终端 | 终端 DLP、浏览器管控 | 覆盖 IDE/浏览器/剪贴板 | P1 |
| 网络 | 出口代理+白名单 | 只放行已审批 AI 端点 | P0 |
| 服务 | CASB 或 API 网关 | 统一入口、统一审计 | P1 |
| 数据 | 脱敏引擎 | 正则+模型识别敏感字段 | P1 |
| 审计 | 日志+告警 | 敏感数据外发实时告警 | P0 |

#### （c）AI 使用政策十条红线（制度模板）

| # | 红线内容 |
|:-:|:---------|
| 1 | 严禁将 L4 绝密数据（未发布产品/密钥/客户定制）输入任何外部 AI 服务 |
| 2 | 严禁使用个人账号（非企业账号）的公共 AI 服务处理工作数据 |
| 3 | 严禁将竞品拆解数据/供应链报价输入云端 AI（含"匿名化"处理） |
| 4 | 严禁将含客户标识（名称/LOGO/NDA 条款）的文档输入云端 AI |
| 5 | 固件源码/安全相关代码仅在断网沙箱内使用 AI |
| 6 | AI 生成的对外文档须人工复核数据准确性（AI 幻觉责任在人） |
| 7 | AI 使用须走审批通道（灰名单工具/超密级任务） |
| 8 | 发现疑似泄露（含"好像发了"）24 小时内上报安全组 |
| 9 | 离职/转岗账号即时回收，AI 会话数据按密级留存 |
| 10 | 违反红线按公司信息安全制度追责，不因"AI 不懂"免责 |

#### （d）服务器研发五类专项防护

| 专项 | 风险点 | 防护措施 |
|:-----|:-------|:---------|
| **固件/芯片安全** | BMC/BIOS 源码、安全启动密钥、签名证书 | 断网沙箱处理；密钥永不进 AI 上下文 |
| **产品 Roadmap** | 未发布机型参数（股价级敏感） | 文档标密；AI 对话禁用型号/参数 |
| **竞品情报** | 拆解数据、渠道来源、价格信息 | 仅本地通道处理；来源脱敏 |
| **供应链** | 供应商报价对比、谈判策略 | 仅本地通道；谈判期 AI 使用加严 |
| **客户 NDA** | 定制方案、客户需求细节 | 按客户保密协议从严执行；默认 L4 |

#### （e）泄露应急响应四阶段

```
DETECT -> STOP -> TRACE -> FIX
  |        |        |        |
  alert/  revoke   audit   review+
  report  access   locate  policy
          notify   channel update
                   owner   all-staff
```

| 阶段 | 动作 | 时限 |
|:-----|:-----|:----:|
| 发现 | DLP 告警/人工上报/月度审计抽查 | 实时 |
| 止损 | 撤销访问、通知服务商删除（若可行）、冻结账号 | 4 小时 |
| 溯源 | 审计日志定位泄露通道/数据范围/责任人 | 24 小时 |
| 整改 | 复盘报告、制度修订、全员通报、技术补漏 | 1 周 |

> **安全 ROI 论证（给管理层的理由）**: 服务器厂商一旦发生固件/参数泄露，损失量级是研发投入的数倍至数十倍（竞品提前 6-12 个月对标）；而分级路由+DLP+审计的投入是**一次性数万至数十万 + 常态化运维**——这是保险思维，不是成本思维。

### 8.2 深入展开：治理落地要点

**（a）四维度量仪表盘（团队版）**

| 维度 | 指标 | 数据源 | 频率 |
|:-----|:-----|:-------|:----:|
| 效能 | AI 产出采纳率、任务耗时对比、DORA 指标 | 工具埋点+CI 数据 | 月度 |
