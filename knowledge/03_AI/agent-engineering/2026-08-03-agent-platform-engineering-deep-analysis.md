## 1. 引言：从 Agent 应用到 Agent 平台

### 1.1 为什么需要平台工程

Agent 从"演示能跑"到"生产可用"的鸿沟，不在模型能力，而在**平台能力**。2026 年 Agent 领域正在发生一次从"应用开发"到"平台工程"的范式迁移——就像 2013-2017 年从"容器化单体"到"K8s 云原生"的迁移 [来源: 用户素材 2026-08 汇总]。

四个信号共同指向这个判断：

| 信号 | 来源 | 核心信息 |
|:-----|:-----|:---------|
| 为 Agent 设计 API | Google Cloud（2026-08-01） | 稳定契约 + 结构化输出 + 幂等性是 Agent API 三大支柱 |
| 三大云 Agent 架构趋同 | 行业观察（2026-07-20） | AWS/微软/谷歌 Agent 平台架构收敛，事实标准形成中 |
| Agent Substrate | Google（2026） | "K8s 赢了容器十年，Agent Substrate 想赢下一个十年" |
| 沙箱观 | Perplexity（2026） | "有状态系统极难构建"——执行隔离与状态管理的根本张力 |

**核心命题**：Agent 平台工程 = 在"概率性执行者"（LLM）之上构建确定性基础设施，把不确定性限制在模型推理的边界内，而把**调度、生命周期、状态、安全、可观测性**全部平台化 [来源: 知识库 agent-os-five-paradigms]。

## 2. 执行层：沙箱与有状态系统（Perplexity 沙箱观）

### 2.1 "有状态系统极难构建"的深层含义

Perplexity 的观点直指 Agent 执行架构的第一性矛盾。展开推导：

**第一步：无状态为什么简单。** 无状态函数（输入→输出）的每个调用自包含，没有隐藏的依赖，可以随意重放、并行、水平扩展，失败即丢弃重来。

**第二步：Agent 为什么必然有状态。** Agent 的执行过程天然产生四类状态：

| 状态类型 | 内容 | 生命周期 |
|:---------|:-----|:---------|
| 会话上下文 | 对话历史、中间推理 | 任务级 |
| 记忆 | 长期偏好、历史经验 | 跨任务 |
| KV Cache | 模型推理缓存（物理状态） | 推理周期 |
| 外部副作用 | 文件写入、API 调用结果、数据库变更 | 不可控 |

**第三步：有状态的复杂性来自哪。** 一旦有状态，就出现：状态一致性（崩溃后恢复）、并发访问（多 Agent 同时改）、状态审计（谁改了什么）、状态测试（复现需要完整状态快照）。这就是分布式系统领域已经为之付出 50 年代价的复杂性 [来源: 行业通识 分布式系统理论]。

**第四步：沙箱的悖论。** 沙箱的目的恰恰是**隔离**——把执行环境做成临时的、可丢弃的、无状态的（"sandbox = 每次都是干净的"）。但 Agent 需要**持久状态**才能完成长任务。于是：

> **沙箱内无状态（执行），沙箱外有状态（持久化）——状态边界就是架构边界。**

这个边界怎么划，决定了整个平台工程的上层设计。Perplexity 强调"极难构建"的另一层含义是：**大多数人以为难在模型，实际难在状态管理** [来源: 用户素材 Perplexity 沙箱观 2026]。

### 2.2 为什么 Agent 执行必须有沙箱

沙箱不是安全洁癖，是**四个硬约束**的必然结果：

| 约束 | 无沙箱的后果 | 沙箱提供的保证 |
|:-----|:------------|:--------------|
| 不可信代码 | Agent 生成的代码可能执行任意命令 | 进程/网络/文件系统三级隔离 |
| 不可信工具副作用 | 工具调用可能破坏生产环境 | 可回滚的临时环境 |
| 不可信外部内容 | Prompt Injection 借工具扩散 | 数据面与控制面隔离 |
| 不可控资源消耗 | 失控循环耗尽 CPU/内存/网络 | 资源配额 + 强制上限 |

其中 **Prompt Injection 是 Agent 平台特有的威胁模型**：LLM 输出不可信，且可能被外部内容诱导执行恶意工具调用。沙箱 + 工具白名单 + 人审是多层防线（对应知识库 agent-os-five-paradigms 的 C1 原则"Defense Comes Outside the Model"）[来源: 知识库 agent-os-five-paradigms]。

### 2.3 沙箱技术谱系

沙箱不是单一技术，是一个**隔离强度-开销权衡谱系**：

```text
isolation weak <-------------------------------------------------> strong
process-isol   container     microVM              TEE/bare-metal
(chroot/ns)   (Docker)   (Firecracker/Cloud)   (SEV-SNP/TDX)
  low cost     light     medium cost             high cost
  weak bdry   shared k   isolated k              HW root-of-trust
```

| 技术 | 隔离粒度 | 启动延迟 | 典型场景 | 局限 |
|:-----|:---------|:---------|:---------|:-----|
| 进程隔离 | 进程 | 毫秒级 | 纯计算工具 | 共享内核，逃逸面大 |
| 容器 | 命名空间+cgroup | 百毫秒级 | 通用工具执行 | 内核共享，弱多租户 |
| microVM | 虚拟机（轻量内核） | 百毫秒~秒级 | 不可信代码沙箱 | 资源开销高于容器 |
| TEE | 硬件信任根 | 秒级 | 高敏感数据处理 | 生态/性能限制 |

**业界实践趋势**：面向 Agent 的沙箱服务（如云厂商的代码解释器/沙箱运行时）普遍采用 **microVM 或强化容器**——因为 Agent 执行的是**不可信 + 有副作用的任意代码**，不是可信任的业务容器 [来源: 行业通识 2025-2026 Agent 沙箱实践]。

**关键设计点：沙箱不是终点，而是边界。** 沙箱内部是"允许犯错"的临时空间，沙箱外是"不许出错"的生产空间。Agent 平台的价值在于管理两者之间的**状态迁移**。

### 2.4 有状态 Agent 的架构挑战

把"有状态"落到实处，Agent 平台必须解决四个工程问题：

**① 状态持久化与恢复（Checkpoint/Resume）**
长任务 Agent（分钟~小时级）随时可能中断（模型错误、超时、节点故障）。平台需提供：状态快照、增量保存、断点恢复。对应知识库 Workflow 架构的 Stop/Resume 部件 [来源: 知识库 agent-workflow-runtime-architecture]。

**② 状态一致性（会话溯源）**
最佳实践是 **Session = append-only fact log**（事件溯源模式）：Agent 不能直接改状态，只能追加事实，状态是事实流的投影。这样任何时刻可重建、可审计、可回滚 [来源: 知识库 agent-os-five-paradigms INV-S]。

**③ 状态归属（多租户隔离）**
平台化后，多个 Agent/多个用户共享同一基础设施。状态的隔离粒度必须与安全边界一致——不同租户的 KV Cache、记忆、工作目录必须物理或逻辑隔离。

**④ 状态与无状态的分层**
成熟架构把 Agent 系统拆成"无状态计算层 + 有状态存储层"：

```text
        +---------------------------------+
        |  STATELESS COMPUTE (scalable)   |
        |  Agent proc / infer / sandbox   |
        +------------------+--------------+
                           | read/write
        +------------------v--------------+
        |  STATEFUL STORE (single truth)  |
        |  Session Log / Memory / KV Cache|
        +---------------------------------+
```

计算层可以随时杀掉重建（对应"cattle not pets"），存储层保证不丢（对应 K8s 里 StatefulSet 的哲学）[来源: 行业通识 云原生架构]。

### 2.5 沙箱内外的状态管理设计模式

综合业界实践，提炼五种状态管理模式：

| 模式 | 做法 | 适用 | 代价 |
|:-----|:-----|:-----|:-----|
| **Stateless-in/Sandbox** | 沙箱内全无状态，状态全在外部存储 | 工具执行、短任务 | 大状态传输开销 |
| **Event Sourcing** | 状态 = 事实日志的投影 | 需要审计/回滚的任务 | 存储增长、投影成本 |
| **Checkpoint** | 周期性快照 + 增量 | 长任务恢复 | 快照一致性协调 |
| **Idempotent Actions** | 操作天然可重放（幂等键） | 有外部副作用的任务 | API 需支持幂等 |
| **Externalized Sidecar** | 副作用由平台代理执行并记录 | 不可信工具调用 | 控制面复杂度 |

**选择判据**：任务可逆性越高 → 越可以靠重放；外部副作用越强 → 越需要幂等 + 事件溯源。对应知识库的"不可逆度分级"（I1 原则）[来源: 知识库 agent-os-five-paradigms]。

## 3. 接口层：为 Agent 设计 API（Google Cloud 设计指南）

### 3.1 Agent 与人类消费 API 的本质差异

Google Cloud 的 Agent API 设计指南（2026-08-01）的出发点：**为 Agent 设计 API 不是为人类设计 API 的改版，而是全新的设计域** [来源: 用户素材 Google Cloud 2026-08-01]。

| 维度 | 人类消费 API | Agent 消费 API |
|:-----|:------------|:---------------|
| 错误处理 | 人类读文档、调试、变通 | Agent 自动重试，错误可能级联放大 |
| 输入质量 | 人类遵守契约 | Agent 可能生成不合法的输入（幻觉 schema） |
| 调用模式 | 低频率、有节奏 | 高频、并发、突发（工具调用风暴） |
| 反馈回路 | 人类能逐步探索 | Agent 一次失败可能带偏整个任务 |
| 契约感知 | 人类看文档理解语义 | Agent 靠 schema + 描述理解，schema 即一切 |

**核心推论**：人类 API 的失败是可恢复的（人看到了会修正），**Agent API 的失败是传染性的**（错误可能被 Agent 当作"这就是这样"继续传播）。因此 Agent API 必须把"防错"前置到契约层。

### 3.2 稳定契约：Schema 即编译期类型

**为什么稳定契约是第一支柱**：Agent 对工具的理解完全来自 API 的 schema 和描述。契约变化 = Agent 心智模型变化 = 行为漂移。对 Agent 来说，**Schema 就是它的编译期类型系统**——运行时才发现不匹配的代价远高于编译期 [来源: 用户素材 Google Cloud 2026-08-01 + 行业通识]。

稳定契约的设计要点：

| 原则 | 做法 | 反例 |
|:-----|:-----|:-----|
| 语义版本化 | 破坏性变更必须 bump major | 悄悄改字段语义 |
| 只加不减 | 新增字段默认可选，不删旧字段 | 删除/重命名现有字段 |
| 宽松输入-严格输出 | 接受合理变体，输出严格 schema | 输出字段类型漂移 |
| 描述即契约 | 参数描述写清楚边界/单位/示例 | 只有名字没有语义 |
| 枚举而非自由文本 | 能枚举的给枚举，减少幻觉 | 让模型自由填字符串 |

**关键机制：输出严格性 > 输入宽松性**。Agent 平台对模型输出的结构化校验（JSON Schema 校验）应作为**硬门**——输出不合法就重试或报错，而不是容忍 [来源: 行业通识 2025-2026 结构化输出实践]。

### 3.3 结构化输出：从解析到约束生成

结构化输出是"让概率性模型产出确定性结构"的工程化手段，技术演进有三个阶段：

```text
Stage1: free text + post-parse         (fragile: high parse-fail rate)
Stage2: prompt-JSON + post-validate    (medium: model may disobey)
Stage3: constrained decoding + schema  (reliable: valid by construction)
```

**阶段3 的原理**：在解码过程中用约束（如 JSON Schema、正则、CFG）限制 token 采样空间，使输出**在生成时就保证合法**，而非生成后再修复。这从机制上把"解析错误"从运行时问题变成不可能发生的问题 [来源: 行业通识 2025-2026 结构化输出技术]。

对 API 设计者的意义：

- **所有工具返回必须结构化**（JSON Schema 定义），让 Agent 无需猜测
- **输出校验是平台职责**，不是应用职责——平台统一校验、统一重试
- **错误也要结构化**：错误码 + 结构化错误详情，Agent 才能据此换策略（而非盲目重试）

### 3.4 幂等性：Agent 重试的语义安全

**为什么幂等性是 Agent API 的生死线**：Agent 的重试行为是**平台默认行为**（失败自动重试），而 Agent 调用的 API 往往有外部副作用（扣款、发消息、写库）。非幂等操作被重试 = 副作用重复执行 = 灾难 [来源: 用户素材 Google Cloud 2026-08-01]。

**幂等性设计模式**：

| 模式 | 机制 | 适用 |
|:-----|:-----|:-----|
| **Idempotency Key** | 客户端生成唯一键，服务端去重（Stripe 模式） | 创建/支付类操作 |
| **自然幂等** | 操作本身就是幂等的（PUT 全量覆盖、DELETE 不存在也成功） | 更新/删除类 |
| **版本号乐观锁** | 携带版本，冲突即失败（ETag/If-Match） | 并发修改 |
| **事件溯源** | 记录意图而非结果，执行可重放 | 复杂副作用链 |

**Agent 平台侧的配套**：

- **重试预算**：给 Agent 的重试设定上限（次数/时间），防止无限重试放大副作用
- **重试语义区分**：5xx 重试、4xx 不重试（4xx 重试只会重复同样的失败）
- **幂等键自动生成**：平台为每次工具调用生成 trace 级幂等键，跨重试复用

### 3.5 API 设计反模式清单

综合 Google Cloud 指南与业界实践，Agent API 设计的常见反模式 [来源: 用户素材 Google Cloud 2026-08-01 + 行业通识]：

| 反模式 | 症状 | 后果 |
|:-------|:-----|:-----|
| 返回人类友好文本 | 返回自然语言而非结构化数据 | Agent 解析失败/语义丢失 |
| 错误信息模糊 | "操作失败"无错误码 | Agent 无法换策略，只会傻重试 |
| 契约悄悄变化 | 字段语义漂移无版本 | Agent 行为漂移，难排查 |
| 忽略幂等 | 重试导致重复副作用 | 扣款两次/重复下单 |
| 巨大 schema | 一次返回 100 字段 | token 浪费 + Agent 注意力稀释 |
| 人机界面混用 | 用人类 UI 的语义设计 API | 机器消费体验灾难 |

## 4. 平台层：Agent Substrate（Google 的平台野心）

### 4.1 "K8s 赢了容器十年"的类比拆解

Google 的 Agent Substrate 叙事核心："K8s 赢了容器十年，Agent Substrate 想赢下一个十年" [来源: 用户素材 Google 2026]。这个类比值得逐项拆解——它既是野心声明，也隐含了完整的产品逻辑：

| 类比项 | 容器时代（2013-2023） | Agent 时代（2024-） |
|:-------|:---------------------|:--------------------|
| 打包单元 | 容器镜像（Docker） | Agent 定义（指令+工具+模型配置） |
| 编排平台 | Kubernetes | Agent Substrate |
| 调度对象 | Pod（容器组） | Agent 实例（会话+沙箱+模型） |
| 服务发现 | Service/DNS | 工具注册中心（MCP Registry） |
| 存储 | Volume/PVC/StatefulSet | 会话存储/记忆存储/KV Cache |
| 弹性 | HPA 水平扩缩 | Agent 实例按负载扩缩 |
| 可观测性 | Metrics/Logs/Traces | Agent 轨迹/成本/质量指标 |
| 多租户 | Namespace/RBAC | 租户隔离 + 权限治理 |

**类比的洞察**：K8s 赢不是因为容器技术最好，而是因为**它把"应用的运行方式"标准化了**——打包、调度、网络、存储、可观测性全部有统一抽象。Agent Substrate 想做的同样事情：**把"Agent 的运行方式"标准化**。

### 4.2 Agent 的"容器"是什么

类比要成立，先要回答：Agent 的可打包单元是什么？业界正在收敛到这样的定义：

```text
Agent Definition (serializable, versionable, distributable)
|-- system prompt
|-- tool manifest (MCP server refs + param schema)
|-- model config (model id, temperature, ctx length)
|-- sandbox spec (runtime, resource quota)
|-- policy (permissions, retry budget, human-review rules)
'-- initial state (seed memory / session template)
```

这个定义的三个关键属性：

1. **可序列化**：Agent 不是代码，是配置/数据 → 可以存库、版本化、回滚
2. **可组合**：Agent 可以引用其他 Agent（A2A）、挂载不同工具集
3. **可移植**：同一个 Agent 定义可以在不同模型/不同运行时上运行（如开发用小模型、生产用大模型）

**类比成立的关键**：就像镜像把"应用+依赖"打包，Agent 定义把"提示词+工具+策略"打包——运行时的复杂性被平台吸收。

### 4.3 Substrate 的职责边界

平台层要管什么？参考 K8s 的职责划分，Agent Substrate 的核心职责：

| 职责 | 具体能力 | 对应 K8s 概念 |
|:-----|:---------|:-------------|
| **调度** | 为 Agent 实例选择模型端点、沙箱节点、冷热存储 | Scheduler |
| **生命周期** | Agent 创建→运行→暂停→恢复→销毁 | Deployment/Pod 生命周期 |
| **状态管理** | 会话持久化、检查点、断点恢复 | StatefulSet + PV |
| **工具接入** | MCP 注册、健康检查、熔断 | Service + Ingress |
| **资源治理** | 算力/内存/存储/网络配额与计费 | ResourceQuota + HPA |
| **安全** | 沙箱策略、权限、审计、注入防护 | RBAC + Policy |
| **可观测性** | 轨迹、成本、质量、SLA 指标 | Metrics/Logs/Traces |

**设计要点：控制面与数据面分离**。决策（调度、策略、审批）走控制面，推理与执行（LLM 调用、工具执行）走数据面。这与 K8s 的架构同构，也是 Agent 平台能否规模化治理的关键 [来源: 行业通识 云原生架构]。

### 4.4 概念辨析：Substrate vs Harness vs Workflow Runtime

Agent 领域概念密集，先厘清层次：

| 概念 | 粒度 | 关注点 | 已有知识库对应 |
|:-----|:-----|:-------|:--------------|
| **Harness** | 单 Agent | 推理循环、上下文管理、工具路由 | agent-os-five-paradigms L 层 |
| **Workflow Runtime** | 单任务 | 把 Loop 编译成可执行脚本 | agent-workflow-runtime-architecture |
| **Substrate** | 平台 | 多 Agent 的调度、生命周期、治理 | 本专题（平台化） |
| **Agent OS** | 理论 | 概率性执行者的操作系统范式 | agent-os-five-paradigms |

**关系**：Harness 是"Agent 的进程"，Substrate 是"Agent 的操作系统"。Harness 解决"一个 Agent 怎么跑"，Substrate 解决"一万个 Agent 怎么一起跑"。两者是互补而非替代——Substrate 调度 Harness 实例，就像 K8s 调度容器运行时。

### 4.5 平台化的边界：哪些不该平台化

平台化的诱惑是"什么都管"，但过度平台化是平台工程的常见死法。**不**该平台化的：

| 不该平台化 | 原因 | 应保留在哪 |
|:-----------|:-----|:-----------|
| 任务领域逻辑 | 平台管不了业务规则 | 应用层/Agent 定义 |
| 提示词细节 | 迭代极快，平台化即僵化 | Agent 定义（版本化但自由） |
| 模型选择 | 模型市场快速变化 | 可插拔，不绑定 |
| 工具内部实现 | 工具是生态，不是平台 | 第三方 MCP 服务器 |

**边界原则**：平台管"运行方式"（生命周期/资源/安全/观测），不管"业务内容"（任务逻辑/提示词/工具实现）。K8s 的成功恰恰因为它严格不碰应用业务逻辑——Agent Substrate 要复制这个克制。

## 5. 生态层：三大云厂商 Agent 架构趋同

### 5.1 三巨头 Agent 平台定位对比

2026 年观察到的关键现象：**AWS、微软、谷歌的 Agent 平台架构正在收敛**，各自独立推出但结构高度相似 [来源: 用户素材 行业观察 2026-07-20]。

| 维度 | AWS | 微软 Azure | Google Cloud |
|:-----|:----|:-----------|:-------------|
| 平台产品 | Bedrock Agent（AgentCore） | Azure AI Foundry Agent Service | Agent Engine / Agent Substrate |
| Agent 定义 | 指令+工具+模型配置 | 指令+工具+模型配置 | 指令+工具+模型配置 |
| 工具接入 | MCP / 函数调用 | MCP / 函数调用 | MCP / 函数调用 |
| 执行沙箱 | Lambda/容器沙箱 | 容器/AKS 沙箱 | Cloud Run/沙箱运行时 |
| 会话管理 | 内置会话存储 | 内置会话存储 | 内置会话存储 |
| 可观测性 | CloudWatch+Tracing | App Insights | Cloud Monitoring+Tracing |

**注意**：以上为 2026 年中行业观察的能力定位，具体产品命名与功能细节以各厂商官方文档为准 [来源: 行业观察 2026-07-20，产品细节需官方核实]。

### 5.2 趋同的架构要素

三巨头独立演进却收敛到同一套架构要素，说明这些要素是**问题空间的必然解**而非某家的发明：

| 架构要素 | 为什么必然出现 | 三家的实现共性 |
|:---------|:--------------|:--------------|
| **Agent 定义层** | 需要可部署的单元 | 指令+工具+模型配置的声明式定义 |
| **工具注册中心** | 需要统一工具接入 | MCP 兼容成为标配 |
| **会话状态服务** | 长任务需要持久上下文 | 托管会话存储 |
| **执行沙箱** | 不可信代码需要隔离 | 云原生运行时沙箱 |
| **身份与权限** | 企业治理的底线 | 云 IAM 集成（Azure AD/IAM/Google IAM） |
| **观测与评估** | 生产运维的必需 | Trace + 成本 + 质量指标 |

**洞察**：趋同 = 行业对"Agent 平台必须提供什么"形成了共识。这正是 K8s 前的容器编排市场的状态——各家都在做同一件事，标准化的窗口已经打开。

### 5.3 事实标准的形成机制：MCP + A2A

Agent 互操作的事实标准正在由两个协议层构成 [来源: 行业通识 2025-2026 Agent 协议]：

```text
+---------------------------------------+
| A2A  Agent <-> Agent   Google -> Linux Fdn |
+---------------------------------------+
| MCP  Agent <-> Tools  Anthropic -> de-facto |
+---------------------------------------+
| LLM API Agent <-> Model  de-facto standard |
+---------------------------------------+
```

| 协议 | 定位 | 发起方 | 状态 |
|:-----|:-----|:-------|:-----|
| **MCP** | Agent 与工具/数据源的统一接入 | Anthropic（2024 末） | 生态采纳最广，事实标准 |
| **A2A** | Agent 之间的任务委派与协作 | Google（2025）→ Linux Foundation | 标准化推进中 |

**为什么协议层是终局战场**：平台层可以趋同，但**协议层的控制权决定生态话语权**。谁的标准成为事实标准，谁的生态就占据最大网络效应。MCP 先发占据工具接入，A2A 瞄准 Agent 间通信——这解释了为什么 Google 高调推 Substrate：**协议 + 平台 + 云基础设施的组合拳**。

### 5.4 趋同后的差异化维度

架构趋同不意味着竞争结束，差异化转向更深的维度：

| 差异化维度 | 内容 |
|:-----------|:-----|
| **模型能力** | 各家模型（Claude/GPT/Gemini）与 Agent 平台的深度集成 |
| **企业集成深度** | 与自家企业软件（Salesforce/M365/GCP 生态）的预置连接器 |
| **治理能力** | 审计、合规、权限的深度与自动化程度 |
| **成本结构** | 推理成本 + 平台费的定价模型 |
| **开放度** | 是否允许自带模型/自带运行时（锁定 vs 开放） |
| **开发者体验** | 调试、评测、部署的迭代速度 |

**判断**：Agent 平台竞争正在从"功能有无"进入"体验与生态"阶段——与 2016-2018 年云厂商容器服务竞争（EKS/GKE/AKS）的轨迹一致 [来源: 行业通识 云厂商竞争史]。

## 6. 综合：Agent 平台工程设计原则

### 6.1 平台工程六原则

综合四层分析，提炼六条设计原则（对应知识库 agent-os-five-paradigms 的范式体系）：

| # | 原则 | 对应层 | 理论依据 |
|:-:|:-----|:-------|:---------|
| P1 | **沙箱内无状态，沙箱外有状态**（状态边界=架构边界） | L1 | 隔离范式 + 有状态治理 |
| P2 | **契约先于实现，Schema 是编译期类型**（稳定+严格输出） | L2 | 约束空间范式 |
| P3 | **幂等是默认要求，重试有预算**（副作用语义安全） | L2 | 不可逆隔离范式 |
| P4 | **控制面与数据面分离**（决策与执行解耦） | L3 | 分布式系统对标 |
| P5 | **平台管运行方式，不管业务内容**（克制平台化） | L3 | 边界原则 |
| P6 | **协议层是终局战场，开放换取生态**（标准先行） | L4 | 网络效应 |

### 6.2 架构决策树

从"要不要自建 Agent 平台"到"选哪层"，决策树：

```text
Need an Agent platform?
|-- 1-10 agents, simple logic
|   '--> use cloud agent service (Bedrock/Azure/Vertex), no build
|-- 10-100 agents, governance/compliance needs
|   |-- accept lock-in -> single cloud platform
|   '-- need multi-cloud/OSS -> open-source orchestration + own gov
|-- 100+ agents, or Agent IS the product
|   |-- build own Substrate: sched+lifecycle+state+sandbox+obs
|   '-- tool access MUST use MCP (do not invent protocols)
'-- cross-vendor agent collaboration
    '--> protocols = MCP + A2A, platform layer stays replaceable
```

**核心建议**：无论哪个层级，**协议层（MCP）不可自创，平台层可以自建，业务层必须开放**。

### 6.3 反模式清单

Agent 平台工程的常见失败模式（综合行业实践）：

| 反模式 | 症状 | 根因 |
|:-------|:-----|:-----|
| 沙箱当堡垒 | 沙箱内也跑生产逻辑 | 混淆执行与生产边界 |
| 状态散落 | 会话/记忆/副作用各存各的 | 缺少统一状态模型 |
| 重试无预算 | Agent 无限重试放大故障 | 忽略幂等与重试语义 |
| 平台管业务 | 平台层堆业务规则 | 越界平台化 |
| 自创协议 | 自己发明工具接入协议 | 忽视 MCP 网络效应 |
| 无状态幻觉 | 把 Agent 当无状态函数设计 | 忽视长任务恢复 |

## 7. 对基础设施的启示

本专题对服务器/AI 基础设施领域的启示（与知识库 02_rd 的硬件视角衔接）：

### 7.1 沙箱资源供给

- **沙箱密度与隔离成本的权衡**：microVM 沙箱需要更多内存/CPU 开销，Agent 平台的沙箱节点选型直接决定单位 Agent 成本。大规模 Agent 平台 = 高密度轻量沙箱 + 快速冷启动（毫秒级）[来源: 行业通识 2025-2026 沙箱实践]
- **冷启动延迟是硬指标**：Agent 工具调用要求百毫秒级沙箱拉起，这推动轻量虚拟化（microVM）与快照恢复技术

### 7.2 状态持久化基础设施

- **KV Cache 成为一等存储对象**：Agent 多轮/长上下文使 KV Cache 持久化需求上升（对应知识库[推理上下文存储架构](../../02_rd/01_product/00_hardware/06_storage/kv-cache/2026-06-26-inference-context-memory-storage.md)），热/温/冷分级存储是趋势 [来源: 知识库 02_rd kv-cache]
- **会话日志是高频小对象写入**：事件溯源模式的 append-only log 对存储的写入带宽与顺序性有明确要求
- **检查点存储**：长任务 Agent 的状态快照需要低成本高可靠存储

### 7.3 可观测性基础设施

- **Agent 轨迹数据量巨大**：每次工具调用、每步推理都是结构化事件，需要高吞吐日志/追踪管道
- **成本可观测性**：Token 成本、沙箱资源成本、工具调用成本需细粒度计量——推动 GPU/算力计量到请求级

### 7.4 对服务器/数据中心产品的影响

| 影响 | 具体表现 |
|:-----|:---------|
| 推理节点规格 | Agent 工作负载混合了推理 + 沙箱执行，节点需要 CPU 密集型（沙箱）+ GPU（推理）异构配比 |
| 低延迟启动 | 沙箱冷启动与模型加载的预热技术（快照、预加载）成为性能关键 |
| 存储分层 | Agent 状态存储推动 NVMe 分层缓存（热会话/温记忆/冷归档） |
| 网络 | Agent 工具调用的高频短连接模式影响东西向流量设计 |
