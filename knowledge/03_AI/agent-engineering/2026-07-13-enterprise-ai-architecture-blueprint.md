## 一、完整架构蓝图：六大部件如何咬合

LLM 是最内核的推理引擎，外面包裹层层工程 runtime。**信息向内汇聚，控制向外掌控**：

| 环层 | 对应文章 | 职能 |
|:-----|:---------|:------|
| **LLM** | 内核 | 会推理的 CPU，不是系统，只是引擎 |
| **Prompt** | 文④ | 角色、约束、输出 schema — 仍然承重的最内环 |
| **Context** | 文④ | 决定"喂什么进模型" — 本质是减法 |
| **Harness** | 文⑤ | 工具、校验、兜底、成本 — demo 到 production 的分水岭 |
| **Loop** | 文⑥ | 驱动整个闭环持续运转 — 代码掌控控制流 |
| **Evaluation** | 文⑦ | 垂直贯穿所有层的度量柱 |
| **Relay** | 文⑧ | 人机接力外壳，让系统 7×24 连续运转 |

**关键对称**：信息从外往里流（Relay→Loop→Harness→Context→LLM），控制从里往外交（LLM 只判"这一步怎么走"，执行/循环/升级权层层外放）。

## 二、层间互兜设计

没有任何一层是完美的，但每一层都在为相邻层兜底：

- Prompt 格式没拦住 → Harness schema 校验兜住
- Harness 没拦住幻觉 → Eval 度量揪出
- Loop 收不住成本 → 预算闸踩刹车
- Agent 拿不准高风险 → Relay 交给人

**可靠性不来自完美部件，而来自层层叠叠的冗余。**

## 三、落地顺序：由内而外、先质量后规模

1. **选对场景** — 二维矩阵确认落在"高不确定×长链路×高信息密度"右上象限
2. **拆解画图** — task graph / decision points / tool points / failure points
3. **做对最内两环** — Prompt + Context 做扎实（单点质量地基）
4. **建 Harness** — 工具失败/幻觉/schema/成本四道机制
5. **上 Loop** — 终止条件/循环预算/错误恢复/状态更新四要素
6. **同步建 Eval** — 尺子从第一天就架
7. **建 Relay** — 分级自主/升级触发/交接协议

**反模式**：别一上来就多 Agent（多半只是多花 token），别一步到位全自动（能做≠该放手）。

## 四、企业自检清单（逐条对照）

### 场景与拆解

- 场景在矩阵右上象限？过治理闸？
- 四张图画出来了吗？

### Prompt 层

- 输出格式被 schema 约束？
- 手写掌控还是框架黑箱？

### Context 层

- 做减法还是硬塞？
- 防 context rot？按四种失败模式排查（污染/分心/混淆/冲突）？

### Harness 层

- 工具失败：重试/self-heal/三振升级/兜底？
- 幻觉：独立校验器（非模型自评）？
- Schema：结构化校验+带错重试？
- 成本：循环预算/成本追踪/可观测性？

### Loop 层

- 终止条件/循环预算/错误恢复/状态更新显式设计？
- 代码掌控控制流而非模型自决？

### Eval 柱

- 分清 Eval 与 Observability（看见≠评判）？
- 黄金集/量化指标/校准裁判？
- 多 Agent 流水线做了级联评估？

### Relay 壳

- 每类动作配风险相称的自主级别？
- 置信/风险/策略三类升级触发器？
- 打包上下文的交接协议？
- 自主完成率/升级准确率等运营指标？

## 五、核心洞见

> **护城河不在模型，在这张蓝图里。**

- 模型的进步是普惠的（全行业一起受益），工程体系是私有的（独有的资产沉淀）
- 把赌注押在"等更强的模型"是把命运交给别人；把功夫下在"打磨工程体系"才是攥在自己手里
- 工程沉淀有时间复利，模型红利人人均沾

> **企业 AI 化，不是"接入大模型"，而是"构建这套工程体系"。**
