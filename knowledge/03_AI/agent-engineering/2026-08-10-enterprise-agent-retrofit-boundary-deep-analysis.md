## 摘要（TL;DR)

**核心命题**：企业 Agent 化改造的本质不是重构系统，而是**在存量系统之上增加一个「代理层」（Agent layer）**——数据层原样保留、业务逻辑**封装**成工具、编排层**新增**、交互层**替换入口**。四层中只有两层真正需要动：逻辑的「接口化封装」和交互的「入口替换」，其余保持确定性。

**边界判定**（用户三个问题的回答）：
1. **确定的**：UI 交互（智能问数/问答）✅ 必须改造；页面逻辑任务化（skills 化）✅ 必须改造——但实质是**触发方式变化**（UI 事件 → 意图理解），业务逻辑本身不动；
2. **灰色地带（有观点）**：页面呈现的动态编排/编写 ⚠️ **推荐确定性为主**——动态 UI 不可审计、不稳定、有安全风险；用「UI as data」（Agent 产出结构化展示数据 + 前端模板渲染）折中；
3. **底层改造（分层判定）**：**CLI/API 化是核心杠杆**（有 API 的系统 Agent 化成本低一个数量级）；浏览器等 UI 自动化工具**仅兜底**无 API 遗留系统；**真正必须的底层改造只有两项**——可观测性（审计日志）与授权模型（Agent 最小权限）。

**落地路径**：四阶段渐进（NL 入口 → 逻辑 API 化 → 任务编排 → 深度改造），每阶段独立 ROI，不推翻任何存量。

## 一、核心命题：Agent 化 = 加代理层，不是重构

```text
before: user -> UI form/button -> page logic (hardcoded flow) -> DB
after:  user -> NL entry (smart Q&A) --+
                                       |-> Agent orchestration (goal->tool->execute->verify) -> service layer (API/CLI) -> DB
        user -> legacy UI (kept) ------+
```

**关键洞察**：存量系统的价值在**数据**（不可替代、不可重建）和**逻辑**（多年业务沉淀、已被验证）——这两者是资产不是负担。Agent 化只改变**两件事**：谁触发（人点按钮 → Agent 理解意图）和怎么触发（页面硬编码 → 工具调用）。**DB 一行不改，事务逻辑一行不改，合规链路一行不改**。

**类比**：给旧楼加电梯（Agent 层），不是拆楼重建（重构）。电梯是新增系统，楼的主体（DB）和房间（逻辑）原样保留。

## 二、四层模型：每层「不动/封装/新增/改造」判定

| 层 | 内容 | 判定 | 动作 | 工作量 |
|:---|:-----|:----:|:-----|:------:|
| **L1 数据层** | 原有 DB、数仓、主数据 | **不动** | 零改造（可选：向量化/索引增强，非必须）| 0% |
| **L2 服务层** | 业务逻辑、事务、审批、计算 | **封装** | 暴露 API/CLI 工具接口（逻辑本身不动）| 30% |
| **L3 编排层** | 任务分解、工具选择、执行验证 | **新增** | 新建 Agent 运行时 + Skills + 工具注册 | 40% |
| **L4 交互层** | UI、入口、呈现 | **替换入口** | 新增 NL 入口，保留原 UI 并行运行 | 30% |

**四层拆解的关键原则**：
- **L1 是红线**：DB 是资产，Agent 通过 L2 工具访问（Agent 直连 DB = 灾难：权限失控、SQL 注入、无审计）；
- **L2 是主要工作量**：但它是**增量封装**不是改造——每个存量逻辑加一层薄壳（参数校验 + 权限 + 日志），逻辑体不动；
- **L3 是纯新增**：不触碰任何存量，风险最低，收益最大；
- **L4 是渐进替换**：新 NL 入口与旧 UI 并行（影子模式），用户自愿迁移。

## 三、Agent 边界判定矩阵

判定「这段逻辑该不该 Agent 化」——**不是所有逻辑都适合**：

| 逻辑特征 | 判定 | 理由 |
|:---------|:----:|:-----|
| 多步决策 / 条件分支 / 需要推理 | ✅ **Agent 化** | Agent 的价值在决策链 |
| 非结构化输入（自然语言/图片/模糊需求）| ✅ **Agent 化** | 意图理解是 Agent 强项 |
| 确定性单步操作（查询/写入/计算）| ⚠️ **保持 API/工具** | 确定性操作交给确定性代码（更快更稳更省）|
| 高合规 / 高金额 / 不可逆操作 | 🛑 **HITL 人审** | Agent 建议，人批准（确定性兜底）|
| 高频低风险 | ✅ **全自动** | 自动化 + 事后审计 |
| 低频高复杂度 | ⚠️ **半自动** | Agent 执行 + 结果复核 |

**边界总原则**：
```text
agentify  = logic needing (understand + decide + multi-step execute)
deterministic = logic needing (precision + compliance + auditability)
bridge the two via HITL, not replacement
```

**反直觉要点**：Agent 化的**目的不是替代逻辑，而是替代逻辑的「触发与编排」**——把「人记流程」变成「Agent 记流程（Skills）」。逻辑本身的正确性来自存量系统多年的验证，Agent 不重写逻辑，Agent 只负责「找到并调用正确逻辑」。

## 四、确定边界 A：UI 交互（智能问数/问答）

**为什么这是最确定的 Agent 化点**：交互层是「人与系统之间」的界面，改造它**零风险触碰业务逻辑**——DB 不动、逻辑不动，只是多了一个 NL 入口。

**智能问数的本质**：NL → SQL/查询 → 结果呈现。三层结构：
```text
intent(LLM) -> query gen (controlled SQL/API) -> render (deterministic template)
     |                  |                              |
 semantic layer    controlled exec (read-only/whitelist)   presentation (chart template)
```

**关键设计约束**：
1. **只读优先**：问数先只读（SELECT），写操作（增删改）走 HITL；
2. **查询受控**：NL2SQL 必须约束（白名单表、参数化、行数上限）——防注入；
3. **结果可验证**：Agent 返回「SQL + 数据 + 图表」，用户可看 SQL 验证（透明可审计）；
4. **存量 UI 并行**：新入口与旧菜单共存，用户自由选择（影子模式，低迁移阻力）。

## 五、确定边界 B：页面逻辑任务化（skills 化）

**实质**：页面逻辑任务化**不是重写业务逻辑，而是重写「触发-编排」层**：

```text
Before: user clicks "export monthly report" -> page JS calls service.exportMonthly() -> file
After:  user says "summarize last month sales as a report" -> Agent calls exportMonthly() + format + send
```

**变化点只有两处**：
1. **触发**：UI 事件 → 意图理解（NL → 意图映射到任务）；
2. **编排**：页面内硬编码的步骤序列 → Skills（目标导向的任务定义：前置条件、步骤、工具、验收标准）。

**不变的**：`service.exportMonthly()` 本体——一行不改。

**Skills 化的价值**（为什么值得做）：
- **知识显式化**：原来藏在页面代码里的流程（谁都不知道完整步骤）→ 变成可读、可复用、可维护的 Skills 文档；
- **组合能力**：单页逻辑 → 可组合的任务单元（月报 + 分析 + 分发 = 新任务，无需新代码）；
- **沉淀复用**：页面死了，Skill 活着（业务知识不随 UI 生命周期消亡）——这正是本系统 knowledge 资产的形态。

## 六、灰色地带：页面呈现的编排与动态编写

**用户问题**：页面呈现的编排、动态编写怎么看？

**观点（明确立场）**：⚠️ **动态生成 UI 是低 ROI 高风险区，推荐「确定性为主，动态为辅」**。

| 方案 | 优点 | 风险 | 适用 |
|:-----|:-----|:-----|:-----|
| **全动态 UI**（Agent 生成 HTML/页面）| 灵活 | 不可审计、格式不稳定、渲染成本高、**prompt 注入可直达页面**（XSS）| ❌ 不推荐 |
| **UI as Data**（Agent 产出结构化展示数据 + 前端模板渲染）| 可控 + 灵活 | 模板需维护 | ✅ **推荐** |
| **确定性模板**（固定页面 + 动态数据填充）| 最稳 | 不够灵活 | ✅ 默认 |

**理由**：
1. **审计性**：企业场景页面是「证据」，动态生成 = 无法追溯「这个页面为什么长这样」；
2. **安全性**：Agent 生成 HTML 引入 prompt 注入 → XSS 攻击面（Agent 安全周更化已证实的风险序列）；
3. **成本**：动态 UI 每次生成 = token 成本 + 不稳定的渲染管线；
4. **「编排 ≠ 呈现」分离原则**：Agent 编排（L3）负责「做什么」，呈现层（L4）负责「怎么显示」——**两者解耦**：Agent 产出数据 + 组件规格（JSON），前端确定性地渲染成表单/图表/报告。

**推论**：页面动态化的正确形态不是「Agent 写页面」，而是「**Agent 写数据，模板渲染页面**」——把动态性收敛在数据层，把确定性保留在呈现层。

## 七、底层改造判定：CLI/API 化 · 浏览器工具 · 真正必须的改造

### 7.1 CLI/API 化：核心杠杆（不是必须，但决定性）

| 系统状态 | Agent 化成本 | 说明 |
|:---------|:------------:|:-----|
| 有完整 API/CLI | **低** | Agent 直接调工具，确定性接口 |
| 有部分 API | 中 | 补封装缺失逻辑 |
| 纯 UI 系统（无 API）| **高** | 只能浏览器自动化兜底 |

**结论**：**CLI/API 化是 Agent 化成本的决定性因素**——有 API 的系统 Agent 化成本低一个数量级。CLI 是 Agent 的「原生语言」：确定性输入输出、可组合、可脚本化、可审计（本系统 `agent-toolchain-cli-execution.md` 已实证：CLI 执行链是 Agent 工具化的最稳形态）。

**改造原则**：不为 Agent 造新 API，**把存量逻辑的入口「接口化」**——现有 service 方法加 CLI/HTTP 壳，就是 Agent 工具。

### 7.2 浏览器等 UI 自动化工具：仅兜底

- **用途**：无 API 的遗留系统（老 ERP/MES）——浏览器自动化是「最后的接口」；
- **代价**：脆弱（DOM 变动即失效）、慢、不可审计、无结构化返回；
- **定位**：**过渡方案**——浏览器自动化跑通流程后，推动底层开 API（浏览器只是「临时代理人」，不是长期架构）；
- **例外**：跨系统协同（Agent 同时操作多个无 API 系统）时浏览器是必要手段，但要有「截图+日志」审计。

### 7.3 真正必须的底层改造（只有两项）

```text
1) Observability: agent audit log (who called which tool, args, result, latency)
2) Authorization: least-privilege tool grants, approval flow, secret custody
```

**为什么只有这两项**：
- **没有审计 = 不敢放权**：Agent 执行不可追溯，企业不可能授权（AIOps 信任阶梯：crawl-walk-run 的前提是确定性的可观测性）；
- **没有授权模型 = 权限灾难**：Agent 以用户身份调用工具，必须工具级最小权限 + HITL 审批（组织三权回收：判断/预算/集成）；
- **其余底层（DB、中间件、网络）一律不动**——动了就是重构，违背「不推翻重来」。

## 八、落地路径（四阶段渐进）与 ROI

| 阶段 | 内容 | 周期 | ROI 信号 | 风险 |
|:-----|:-----|:----:|:---------|:-----|
| **P1 入口** | NL 入口（智能问数）+ 原 UI 并行 | 2-4 周 | 问数采纳率、SQL 正确率 | 低 |
| **P2 封装** | 高频业务逻辑 API/CLI 化 | 4-8 周 | 工具调用成功率、复用率 | 低 |
| **P3 编排** | Skills 化 + Agent 任务编排 + HITL | 8-12 周 | 端到端任务完成率、人时节省 | 中 |
| **P4 深化** | 可观测性 + 授权模型 + 复杂 Agent | 持续 | 自动化覆盖率、事故率 | 中高 |

**渐进原则**：
1. **每阶段独立 ROI**——不绑定全周期收益（防止「项目太大做不完」）;
2. **影子模式**：新能力与旧路径并行，用户自愿迁移（不强制切换）;
3. **先读后写**：先只读 Agent（问数/分析），跑稳再上写操作（审批/执行）;
4. **结晶化纪律**：Agent 探索出的稳定流程 → 固化为确定性工具/模板（progressive crystallization：探索为结晶服务）;
5. **40% 红线**：AI/Agent 投入占比设限（本系统实证：AI 投入 ≤40%，业务主线不动摇）。

## 九、案例实证：CowAgent + 行业参照

### 9.1 CowAgent（本系统，活体实证）

| 四层 | CowAgent 对应 | 证明 |
|:-----|:-------------|:-----|
| L1 数据层不动 | 2,900+ 知识文件原样保留 | 零改造 ✅ |
| L2 封装 | 脚本/工具（check_md_format、kb-log-append 等）| 逻辑封装为工具 ✅ |
| L3 新增编排 | Skills 100+（每个 = 任务定义）| 纯新增 ✅ |
| L4 入口替换 | 飞书/Web 渠道（NL 入口）| 并行 ✅ |

**CowAgent 实证结论**：一个「不推翻重来」的系统——所有知识资产、脚本、规则原样保留，只加了 Agent 层，就在原系统之上获得了 NL 交互 + 任务编排 + 工具化执行能力。

### 9.2 行业参照

- **Jira → Symphony**：从「追踪系统」升级为「编排系统」——Jira 仍是 System of Record（数据层不动），Symphony 生成 Workflow.md（编排层新增），Agent 可读而人可问责——**同一数据源，两层架构**；
- **AIOps 信任阶梯**（Dynatrace crawl-walk-run）：确定性因果 → HITL → 置信度驱动——**授权边界随信任逐级放开**；
- **GitHub Copilot 治理**：Stacked PR + 审批流——**Agent 产出 + 确定性治理**的范式（计量制催生治理制）。

## 风险与边界

- **封装层质量决定一切**：L2 工具接口若不稳定/无权限控制，Agent 层再聪明也白搭——工具是 Agent 的地基（本系统工具/脚本+git 治理经验：工具注册、版本、审计）；
- **「加代理层」的诱惑是过度封装**：别把所有逻辑都 API 化——只封装被 Agent 需要的（高频、可组合、边界清晰），其余保持原样（倒U：工具数量也有最优值）；
- **影子模式的时间窗**：新旧并行太久会资源浪费，要有明确的迁移指标（采纳率阈值）触发旧 UI 下线；
- **HITL 不是万能**：审批疲劳会导致「看一眼就批」（橡皮图章）——HITL 要有异常检测辅助（只有异常才人工介入，AIOps HOTL 思路）；
- **文化阻力**：「让被替代的人变成替代系统的主人」（前移后移分析）——Agent 化要给人新的角色（训练 Agent、审核 Agent 产出），而非直接替代。
