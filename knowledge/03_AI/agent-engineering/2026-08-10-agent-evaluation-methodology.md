## 摘要（TL;DR）

**核心命题**：Agent 评测不能停在「对话/编码基准」，而应测「模型在 Agent 链路中的端到端真实表现」。本文提炼出**六维能力矩阵 + 量化指标 + 通过判据 + 设计原则**四层评测方法，并对其内在局限（自家倾向性/无横向对比/无失败率口径）做了批判性标注。

**六维能力**：任务规划与技能调度 / 交互式编程 / 长期记忆 / 浏览器自动化 / 知识库构建 / 长上下文处理——每维对应 Agent 一个核心能力维度。

**三个关键洞察**（对选型有直接价值）：
1. **长上下文的正确姿势 =「落盘 + 检索」而非「全量塞入」**——测的不是模型能装多大，而是「知不知道何时该走工具」；
2. **记忆的价值不在存储，而在「检索 → 多记忆综合 → 产出」的推理链**（新 session 仅 2 次工具调用即完成品牌全貌整合）；
3. **复杂约束执行是低价模型的短板**（"零外部依赖"仍引 CDN）——硬约束任务需配 Pro/更高 reasoning_effort。

## 一、评测范式的根本差异：场景端到端 vs 基准对话

| 维度 | 对话/编码基准 | 场景端到端评测（本框架） |
|:-----|:-------------|:------------------------|
| 被测对象 | 模型的生成能力 | 模型 × 框架 × 工具链的**组合能力** |
| 任务形态 | 单轮问答 / 单文件 | 多步长链路（跨工具/跨 session/跨文件） |
| 核心指标 | 正确率/质量分 | 完成度 + 耗时 + 工具调用次数 + 稳定性 |
| 贴近度 | 离真实使用远 | 贴近真实使用（含反爬/登录态/落盘检索）|
| 价值 | 横向比模型强弱 | 判断"能不能当默认模型用" |

**为什么需要**：Agent 一次任务往往几十次 LLM 调用，模型单价权重高，且真实瓶颈不在"单次生成"而在"多步规划是否稳定、会不会死循环、懂不懂走工具"。基准测不出这些。

## 二、六维能力矩阵：Agent 核心能力的分解

设计原则：**每场景对应一个核心能力维度 + 任务复杂度分级**。

| 场景 | 被测能力 | 任务设计 | 复杂度 |
|:-----|:---------|:---------|:------:|
| s1 任务规划与技能调度 | 多工具/Skill 协同、长链路规划 | 调研 3 场景→8 页 PPT→沉淀知识库 | 高 |
| s2 交互式编程 | 复杂前端代码 + 视觉品味 + 约束遵守 | 单文件零依赖实时大屏 | 高 |
| s3 长期记忆 | 跨 session 检索 + 综合推理 | Setup 3 轮→新 session 写运营计划 | 中 |
| s4 浏览器自动化 | 真实站点多步操作 + 登录态 + 求助边界 | 小红书搜索→写草稿→发布 | 高 |
| s5 知识库构建 | 联网 + 文件操作 + 知识组织 | 从零构建 MCP 主题知识图谱 | 中 |
| s6 长上下文 | 长文档消化 + 大海捞针精确定位 | 《战争与和平》3.36MB 全本 | 高 |

**为什么是这六维**：它们是 Agent 区别于纯 LLM 的**六大核心能力的完备分解**——规划（决定做不做对）、编码（做出来）、记忆（记得住）、浏览器（能动真实世界）、知识库（会沉淀）、长上下文（能消化大输入）。

## 三、量化指标体系：测什么、怎么测

每一维都采集**统一量化指标**，才可横向可比、可复现：

| 指标 | 含义 | 反映什么 |
|:-----|:-----|:---------|
| **状态** | 成功 / 失败 | 完成度（硬指标）|
| **总耗时** | 端到端秒数 | 效率 |
| **工具调用次数** | 拆解成多少步 | 规划颗粒度 + 是否冗余（克制 vs 死循环）|
| **联网搜索次数** | 检索动作 | 主动信息获取 |
| **文件读写次数** | 落盘/读档 | 大任务的 IO 策略 |
| **失败率/死循环** | 批量任务口径 | **稳定性**（比单次成功更关键）|

**关键判读技巧**：
- 工具调用**克制**（35 次完成复杂任务、无冗余）= 规划稳定；反之频繁重复同一工具 = 死循环前兆；
- 模型**自加兜底动作**（主动截图回看、主动分块写入）= 稳定性强的信号，非 prompt 要求。

## 四、评测设计原则

1. **独立 session**：每场景独立运行，互不干扰（防上下文污染、可归因）；
2. **单维度聚焦**：每场景只测一个能力维度（交叉混淆时无法定位短板）；
3. **贴近真实**：用真实站点（反爬、登录态）、真实规模（3.36MB 全本）——降级到玩具任务就失去评测意义；
4. **同配置基线**：统一参数（reasoning_effort、步数上限、上下文上限、工具集）保证可比；
5. **关注边界行为**：何时该求助用户（登录/发布确认）、何时该走工具而非硬塞 context——这些"聪明的边界判断"才是 Agent 的分水岭。

## 五、通过判据与结果解读

- **通过判据**：任务完成 + 产物符合要求 + 无死循环/无参数解析失败；
- **产物验证**：不止"跑完"，要检查产物质量（PPT 排版、代码能运行、记忆与输入一致、原文引用一字不差）；
- **批量复测**：单次成功 ≠ 稳定，需批量任务口径看失败率（报告未做，属局限）；
- **维度解读**：长记忆/长上下文跑得最顺 → 适合记忆密集、长文档类任务；复杂约束执行打折 → 硬约束任务需升级配置。

## 六、本方法的内在局限与中立性

提炼时保留的**批判性标注**（评测方法自身的失败模式）：

| 局限 | 说明 | 缓解 |
|:-----|:-----|:-----|
| **自家倾向性** | CowAgent 测自己默认模型，有动机证明可用（发布即设默认）| 第三方/独立机构复测 |
| **无横向对比** | 无同场景 Claude/其他模型基线，"稳定性足够"缺参照 | 加对照组 |
| **无失败率口径** | 只有"本次都成功"，无成功率统计 | 批量 + 多次运行取分布 |
| **复杂度标注主观** | 如 s3 标"中"但推理要求高 | 明确判定规则/评分 rubrics |
| **时效窗口短** | 模型/框架快速迭代，结论易过时 | 版本锚定 + 定期复测 |

> **方法论教训**：任何评测框架都要**自带反方视角**——测"被测对象"的同时要审"评测设计本身"，否则会产出"看起来无懈可击但经不起推敲"的结论（呼应 AI 精度控制：结果夸大/不编造基线）。

## 七、可复用评测框架的沉淀路径

把单次评测升级为**标准化套件**（这是"提炼评价方法"的最终落点）：

```
agent-eval-kit/
├── scenarios/      # 六维场景模板（任务 prompt + 复杂度标注 + 通过判据）
├── metrics/        # 量化指标采集规范（耗时/工具调用/失败率/产物验证）
├── harness/        # 独立 session 运行器 + 批量复测 + 日志采集
├── baselines/      # 对照组模型跑分（横向对比）
└── report/         # 标准化报告模板（含局限性自审章节）
```

**复用场景**：Agent 框架厂商选默认模型 / 大模型评测机构 / 企业做模型选型（对应本系统"模型选取与配置"维度）——同一套六维矩阵可横向比不同模型在 Agent 链路的表现。

## 八、对本系统的映射与建议

- 本系统当前用 deepseek-v4-flash-ga-260731：本报告结论（稳定性足作默认、长上下落盘检索、复杂约束执行打折）与 MEMORY 中"V4 Flash 选择正确"判断一致；
- **长上下文「落盘+检索」** 与本系统 Token 治理（meth-015 压缩固定开销/减请求）同构，可作为长期上下文处理的默认策略固化；
- **复杂约束短板** → 本系统在硬约束任务（如"零外部依赖/禁止某依赖"）应显式提高 reasoning_effort 或用 Pro 档；
- **建议**：可将六维矩阵沉淀为本系统模型/框架选型的轻量评测清单（P1），尤其补上"失败率/批量口径"和"横向对照组"两个缺口。
