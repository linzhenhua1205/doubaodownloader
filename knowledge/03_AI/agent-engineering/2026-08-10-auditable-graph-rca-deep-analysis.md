# 🕵️ Auditable Graph-Guided RCA：可审计 RCA agent 的「证据约束 × 诚实评估」双设计——从 benchmark-coupled 到可复制的可信度框架

> **概要**: Graph Traversal Agent（arXiv:2606.08590, 06-07, cs.SE，2 作者 8 页 preprint）用「LLM 推理 + 确定性图/工具操作」构建可审计的 Kubernetes RCA agent：在 typed evidence graph 上推理，四约束（只读证据/传播感知/有界执行/独立验证）映射为四实现（typed incident graph / LangGraph 状态机 / 独立验证阶段）。ITBench 快照上固定 qwen-plus 裁判评分 F1 0.6087→0.9130（23 场景子集），但提示消融后剥离场景提示仅剩 0.6958（19 场景子集）——幸存增益集中在 ChaosMesh 注入故障场景，作者诚实标注为 benchmark-coupled 而非跨集群 RCA 证据。本文深潜：①四约束为何是 RCA agent 可审计性的「设计基线」而非「评估装饰」；②四件套轻量检查（同裁判对比/提示消融/级联源检查/遥测无泄漏）如何把「声称」变成「标记为 supported/pending/out of scope」；③0.6087→0.9130→0.6958 三层数字各自说明什么。

## 〇、结论概要

**一句话：这篇论文的最大价值不是 0.9130 的 F1，而是「把 benchmark-coupled 主动拆出来」——用消融把「提示套利」与「真实能力」分开，用四件套轻量检查把每个声称标记为 supported / pending / out of scope。这是 RCA agent 评估的可复制模板，也是「诚实标注」的教科书案例。**

1. **架构上**：RCA 可审计性 = 证据约束（只读、传播感知、有界）+ 独立验证——LLM 负责推理，确定性图/工具负责边界与检查。**LLM 的自由度被刻意限制在「证据图推理」之内**，这是可审计性的第一性来源。
2. **评估上**：0.9130 是「同一系统升级迭代」的相对增益；0.6958 是「剥离场景提示」后的幸存增益；幸存增益集中在 ChaosMesh 注入故障场景（根因实体已在证据图中）——**作者主动把结果定性为 benchmark-coupled**。
3. **诚实是稀缺品**：多数 RCA 论文报告「端到端 F1 提升」，这篇报告「提升的哪一部分是真的」。对生产决策者，这种标注比数字本身更有价值——它告诉你**别把论文数字当生产承诺**。
4. **对本地**：与 fault-diagnosis 技能（系统化故障排查）、08-07「假存活」陷阱、可观测性三要素闭环——RCA agent 的落地前提是「证据图 + 只读约束 + 独立校验」，这正是把故障诊断方法论「脚本化/约束化」的 agent 实现。

## 一、背景：RCA agent 的可信度危机

Kubernetes 事故诊断领域，LLM 驱动的 RCA 是热点，但存在系统性信任问题：

1. **benchmark-coupled 泛滥**：很多 RCA 系统在 benchmark 上表现优异，实际是因为「场景提示泄漏」——模型的增益来自对 benchmark 结构的先验（哪个组件可疑、什么故障模式常见），而非从 incident 证据中推理出来。作者原话：诊断可靠，仅当「reported gains come from incident evidence rather than scenario-specific shortcuts」。
2. **LLM 幻觉污染诊断链**：RCA 是「证据 → 假设 → 验证」链，任何一环幻觉都会把根因定位引向错误方向。纯 prompt 驱动的 RCA 无法约束这一点。
3. **验证缺失**：多数 RCA 系统没有「独立验证」阶段——模型自说自话提出根因，无人检查它是否符合证据。
4. **生产环境无法受控**：真实集群事故不可重复、无法消融，难以做受控评估——这是「benchmark-coupled 诚实标注」被逼出来的原因。

Graph Traversal Agent 的贡献在于：把「可审计性」从评估修饰变成**架构约束 + 评估方法**两个层面的第一等设计。

## 二、架构：四约束 → 四实现

| 操作约束（operational constraint） | 实现（mapping） | 作用 |
|:---|:---|:---|
| **只读证据收集**（read-only evidence collection） | typed incident graph（类型化事故图） | 证据先被收集并结构化为图，LLM 只能基于图推理，不能凭空引入外部事实 |
| **传播感知诊断**（propagation-aware diagnosis） | typed graph 的边携带传播关系 | 根因定位遵循故障传播拓扑，而不是「最可疑组件」的直觉 |
| **有界执行**（bounded execution） | LangGraph traversal state machine | 搜索步数/深度受限，避免 agent 无限探索或发散 |
| **独立验证结论**（independently validated verdicts） | 独立验证阶段（separate validation stage） | 模型提出的根因由独立阶段检查，与「提出」解耦，防止自证 |

设计精髓：**LLM 推理与确定性操作分工**——LLM 做「证据图上的假设生成与推理」，确定性图/工具做「证据收集、搜索边界、结论检查」。这既保留了 LLM 的推理灵活性，又用确定性外壳锁住可审计性。

这与本系统「约束脚本化=最高杠杆」「修补工具化=确定性外壳释放 AI」的本地判断完全同构：**LLM 负责探索与推理，确定性机制负责边界与验证**。

## 三、评估：四件套轻量检查与诚实标注

作者提出四个轻量检查，把每个声称标记为 supported / pending / out of scope：

| 检查 | 内容 | 防什么 |
|:---|:---|:---|
| **同裁判对比**（same-judge comparison） | 新旧系统用**同一个固定裁判**（qwen-plus）评分 | 裁判漂移导致假提升 |
| **提示消融**（prompt-level ablation） | 剥离场景特定提示后重测 | 场景提示泄漏（benchmark-coupled 的检测器） |
| **级联源检查**（cascade-source checking） | 检查级联故障时证据源是否真实存在 | 幻觉证据源 |
| **遥测无泄漏测试**（telemetry no-leak test） | 确认评估用的遥测数据未在训练/提示中出现 | 数据泄漏（测试集污染） |

这套方法的价值：**把「评估黑盒」变成「声称-证据对照表」**。每个结论都有对应的检查证明它「supported」（有证据支持）还是「pending」（待验证）或「out of scope」（超出范围）。

**诚实标注的三个实例**：
1. 增益集中在 ChaosMesh 场景（注入故障对象已在证据图中）→ 定性为 **benchmark-coupled**，而非跨集群 RCA 证据；
2. live-cluster trials 只是工程压力测试，alert state / trace availability 不稳定无法受控评分 → **不做生产就绪或 MTTR 声明**；
3. 范围限定 ITBench OpenTelemetry-demo snapshots → 不泛化到其他集群形态。

## 四、三层数字解读：0.6087 → 0.9130 → 0.6958

三个数字各自回答不同问题：

1. **0.6087 → 0.9130（23 场景公共子集）**：同一系统迭代升级的相对增益，证明「四约束架构 + 验证阶段」相比早期版本有效——**但这是「含提示」的全配置成绩**，不能直接当产品指标。
2. **0.6958（19 场景消融子集）**：剥离场景特定提示后的幸存增益——**这才是「跨场景泛化」的底线**。0.9130 → 0.6958 的落差（-24pp）就是「提示套利」的规模。
3. **幸存增益集中在 ChaosMesh**：即使消融后剩下的提升，也主要来自「故障对象已在证据图中」的场景——即**证据图本身给了答案**的场景。这不是贬义（证据图中找根因正是 RCA 的职责），而是界定适用范围：**当前系统擅长「证据充分的注入故障」，不等于擅长「证据稀疏的跨集群复杂故障」**。

**方法论启示**：三个数字的并置比任何一个数字都诚实。生产决策者应该要求 RCA 供应商提供「消融后的幸存增益 + 增益来源场景分布」，而不是「端到端 F1」。

## 五、与 12 类失败模式研究的对照

08-10 登记的另一篇论文（2602.09937v2, 03-04）用 OpenRCA 基准 × 5 个 LLM × 1675 次运行，把云 RCA 失败归类为 12 类陷阱，分三层：
- **intra-agent 推理层**：幻觉式数据解读、探索不完整、证据误读；
- **agent 间通信层**：多 agent 信息传递失真；
- **agent-环境交互层**：工具调用错误、状态管理失败。

关键结论：**最常见失败跨所有能力层级模型普遍存在，根因在共享 agent 架构而非单模型能力**——提示工程无法单独解决。

两篇论文互补：**12 类失败模式 = 诊断（RCA agent 为什么会错）；四约束架构 = 处方（如何让 RCA agent 错得可发现、可归因）**。Graph Traversal Agent 的只读证据 + 有界执行直接压制「幻觉式数据解读」「探索不完整」；独立验证阶段压制「自证式结论」。12 类失败模式清单可作为四约束架构的验收测试集。

## 七、批判性审视

1. **规模与泛化有限**：ITBench OpenTelemetry-demo 快照、23/19 场景、单一裁判（qwen-plus）——场景域窄，跨集群/跨应用形态的泛化未验证（作者自己也承认）。
2. **单裁判风险**：固定 qwen-plus 裁判避免了「裁判漂移」，但单裁判仍可能系统性偏好某种答案风格——「同裁判对比」防漂移不防偏差。
3. **「有界执行」的边界未量化**：搜索步数/深度如何设定、与 F1 的关系如何——摘要未给，影响「边界与质量」的权衡理解。
4. **仅 2 作者 8 页 preprint**：Peer review 状态未知，方法细节（typed graph 的 schema、验证阶段的具体检查逻辑）需读全文。
5. **「benchmark-coupled」是止损而非解决**：作者诚实标注了局限，但未提出「证据稀疏场景」的解法——这是留给后续工作的真问题，不应因诚实标注而误读为「已经解决」。

## 八、可证伪预测（P1-P4）

- **P1（2026 年内）**：RCA 论文评估将「提示消融 + 同裁判对比」设为标配——四件套轻量检查被社区采纳为 RCA 评估基准协议（类似「消融必须报」的审稿要求）。
- **P2（2027）**：至少一家云厂商 RCA 产品披露「消融后幸存增益」而非仅端到端 F1——诚实标注从学术惯例走向产品披露规范。
- **P3（2026H2）**：出现「证据稀疏场景」的 RCA 专项研究（多源证据补全、跨集群知识迁移），填补 benchmark-coupled 标注暴露的空白。
- **P4（2027）**：四约束架构（只读证据/传播感知/有界/独立验证）成为 RCA agent 平台（含开源 LangGraph 生态）的默认脚手架——「可审计 RCA」从论文特性变成平台默认。

## 九、对本系统的启示

1. **RCA 功能设计基线**：本系统若构建运维 RCA 功能，直接采用四约束架构——证据图 + 只读 + 有界 + 独立验证，LLM 只做图内推理。
2. **评估纪律**：任何 RCA 声称必须附「消融后增益 + 增益场景分布」，否则按 benchmark-coupled 对待——评估方法论直接借用四件套。
3. **与 12 类失败模式联动**：用失败模式清单做 RCA agent 的验收测试，缺什么约束补什么约束。
4. **诚实标注制度化**：本文是「标注缺口优于编造数字」的范例——与本系统「数据无法获取时标注缺口」纪律一致，可作为对外输出时的参照案例。
