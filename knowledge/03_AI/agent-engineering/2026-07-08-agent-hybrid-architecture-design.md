## 1. 背景与核心命题

### 1.1 为什么 Agent 是下一个大应用形态

**核心判断**：AI 的应用形态正从"Embedded AI"（将 AI 嵌入现有应用）转向"AI-Native Agent"（以 Agent 为核心组织交互）。这不是渐进改进，而是交互范式的切换：

| 维度 | 传统应用 | Agent 应用 |
|:-----|:---------|:-----------|
| 交互模型 | 菜单/表单/按钮 → 可视化界面 | 目标描述 → Agent 自主规划执行 |
| 用户角色 | 操作者（点按输入） | 委托者（定义目标+验收） |
| 执行路径 | 固定代码路径 | LLM 规划 + 工具调用，每次可能不同 |
| 容错方式 | 异常处理 try-catch | 反射 + 重试 + 换策略 |
| 扩展方式 | 加功能模块 | 加工具/Skill/CLI |

但关键挑战在于：**LLM 天然具有不确定性（输出的概率性、Context Window 物理上限、模型升级的行为漂移），而企业应用要求执行可靠、结果可复现、行为可审计。** 这就是混合架构存在的根本原因——**用确定性框架约束概率性主体，用 CLI/Browser 提供可靠执行边界，让 Agent 在"可控的不确定性"中发挥最大价值。**

### 1.2 问题空间的三维约束

```text
        概率性执行（LLM 输出不确定）
                ^
                |
    +-----------+-----------+
    |           |           |
    |   Agent   |           |
    |  系统设计 |           |
    |           |           |
    +-----------+-----------+
                |
                v
观测窗口硬约束 <-----------> 假设腐化
(Context Window)       (模型升级/环境变化)
```

Agent 系统设计的本质是在这三个独有约束下，组合五种驯服不确定性的范式（见 [Agent OS 五种范式](2026-06-26-agent-os-five-paradigms.md)），实现**确定性-概率性的最优融合**。

## 2. Agent 混合架构：三层融合模型

### 2.1 核心架构

```text
+--------------------------------------------------------------+
|                    用户目标（自然语言）                        |
+----------------------+---------------------------------------+
                       |
+----------------------v--------------------------------------+
|  ① LLM 任务规划层（概率性 · 负责"做什么"）                   |
|  +---------------------------------------------------------+ |
|  | · 任务拆解：目标->子任务->依赖->并行                       | |
|  | · 工具选择：判断用哪个工具/CLI/浏览器                    | |
|  | · 异常分流：失败时判断重试/换策略/升级                    | |
|  | · 结果综合：多路结果汇总/冲突消解                        | |
|  +---------------------------------------------------------+ |
+--------------------------+-----------------------------------+
                           |
        +------------------+------------------+
        v                  v                  v
+---------------+ +--------------+ +------------------+
| ② 确定性框架层| | ③ CLI 协同层 | | ④ Browser 协同层  |
| (负责"怎么走")| | (负责"执行") | | (负责"GUI操作")   |
+---------------+ +--------------+ +------------------+
| · Workflow    | | · 鉴权/校验  | | · 页面导航/点击   |
|   脚本执行    | | · 文件/系统  | | · 表单填写/截图   |
| · 状态机管理  | |   操作       | | · 登录后操作      |
| · 阶段切换/   | | · 结构化输出 | | · 动态内容获取    |
|   并行调度    | | · 预检/dry- | | · 传统 Web 兜底   |
| · Checkpoint/ | |   run       | |                   |
|   恢复        | | · 错误阶段  | |                   |
+-------+-------+ |   定位       | +------------------+
        |         +--------------+
        v
+--------------------------------------------------------------+
|                    执行结果（结构化）                         |
+--------------------------------------------------------------+
```

### 2.2 三层职责分离（核心设计原则）

| 层 | 职责 | 发生源 | 能否被替代 |
|:---|:-----|:-------|:-----------|
| **LLM 规划层** | 任务拆解、工具选择、异常分流、结果综合 | LLM 推理 | 不能→这是 Agent 的"大脑" |
| **确定性框架层** | Workflow 编排、阶段控制、状态管理、检查点 | 代码引擎 | 部分→简单任务可走纯 ReAct |
| **CLI/Browser 层** | 鉴权、参数校验、文件操作、网络请求、页面操作 | 工具/CLI/浏览器 | 部分→低风险可绕过，但失去可靠性 |

**关键原则**：

1. **LLM 规划层只做判断不做执行**——它说"调用 tool X"就行，不负责 X 的具体实现
2. **确定性框架层把 Loop 从模型搬进代码**——阶段、循环、并行、分支由代码控制，LLM 只出现在被调用的子任务中
3. **CLI/Browser 层是执行边界**——不做判断，只做鉴权、执行和结构化返回

> **一句话总结**：LLM 决定"做什么"，框架决定"怎么走"，CLI 决定"怎么做"。

### 2.3 与 ReAct 纯推理模式的对比

| 模式 | 执行路径 | 可靠性 | 可复现性 | 成本 | 适合场景 |
|:-----|:---------|:-------|:---------|:-----|:---------|
| **纯 ReAct** | LLM 全程推理每一步 | 低 | 低 | 高（强模型持续调用） | 探索性强·边界模糊·一次性 |
| **Plan + ReAct** | LLM 先规划，执行中再调整 | 中 | 中 | 中 | 常见任务·阶段相对清楚 |
| **Dynamic Workflow** | LLM 生成脚本，代码控制流程 | 高 | 高 | 低（强模型只出场一次） | 反复出现的复杂任务 |
| **Full Harness** | 七层 ETCLOVG 完整治理 | 极高 | 极高 | 初始成本高 | 企业级生产系统 |

**实验数据**（来自 PhoneHarness 工程报告）：CLI 执行成功率 ~99%，MCP ~95%，纯 GUI ~70%。路由策略的收益 > 模型能力提升的收益。

## 3. LLM 任务规划层：不确定性是第一等公民

### 3.1 规划层核心能力

规划层不是简单的"把任务拆成几步"，而是需要做出**含不确定性的决策**：

| 能力 | 输入 | 输出 | 不确定度 |
|:-----|:-----|:-----|:---------|
| **任务分解** | 用户目标 | 子任务 DAG（依赖/并行/时序） | 中 |
| **工具选择** | 子任务描述 | 工具路由（Rule/API/CLI/MCP/GUI） | 中-高 |
| **异常分流** | 执行错误详情 | 重试/换策略/升级/暂停 | 高 |
| **结果综合** | 多路子结果 | 汇总/冲突消解/质量评估 | 高 |
| **不确定性标注** | 当前信念 | 确信度 / 不确定区域 / 已知未知 | 本层产物 |

### 3.2 任务规划策略对比

| 策略 | 原理 | 适合场景 | 风险 |
|:-----|:------|:---------|:-----|
| **CoT（思维链）** | 逐步推理 | 逻辑推导、数学问题 | 长链容易漂移 |
| **ToT（思维树）** | 多路径探索 + BFS/DFS | 搜索空间大的问题 | Token 成本高 |
| **ReAct** | 推理→行动→观察→再推理 | 需要补充事实的任务 | 循环不可控 |
| **Plan-and-Execute** | 先规划→再执行→按需调整 | 结构相对稳定的任务 | 规划可能偏离实际 |
| **Self-Refine** | 生成→自我批评→修改 | 代码/写作/质量敏感 | 自我偏见 |

**推荐组合**：Plan-and-Execute 作为主策略 + ReAct 作为执行中微调手段 + Self-Refine 作为质量门。

### 3.3 信念-现实漂移检测

这是 Agent OS 中提出的重要机制——Agent 执行过程中，其内部"信念"（基于历史推断）与现实环境（实际状态）之间会产生漂移：

```text
信念（INS惯性导航）         现实（GPS 校正）
     |                         |
     +--------+------------+
              |
              v
        漂移检测
         |
         +-- 置信度 > 0.7 -> 继续
         +-- 置信度 ≤ 0.7 -> 主动 probing 验证
```

**实现方式**：

- 每条"信念"标注置信度（0~1）
- 信念年龄 > 5min 或关键操作前触发主动验证
- 验证失败 → 更新信念 + 重规划

### 3.4 规划层的关键设计陷阱

| 陷阱 | 表现 | 解决方案 |
|:-----|:------|:---------|
| **过度规划** | 花大量 Token 做精细规划，但执行中频繁偏离 | 规划粒度控制在"够用"，执行中再调整 |
| **规划幻觉** | 规划依赖不存在的工具或信息 | 规划前先验证工具可用性 |
| **不断重新规划** | 每次失败都重新开始规划，陷入"重新想"循环 | 失败后先尝试换策略，再考虑重新规划 |
| **缺乏优先级** | 子任务不分轻重，关键路径不清晰 | 规划时标注关键路径和非关键路径 |

## 4. 确定性框架层：把 Loop 从模型搬进代码

### 4.1 为什么需要确定性框架

**纯 ReAct 的核心问题**：流程全靠模型临场维持——阶段顺序、工具选择、错误恢复全部依赖 LLM 当场理解并坚持执行。结果是跑十次可能有十种不同的执行结构。

**确定性框架的核心思想**（来自 [Workflow Runtime](2026-06-26-agent-workflow-runtime-architecture.md)）：

> **"我不再给 LLM 写 Prompt 了。我有让 LLM 执行的 Loop。"** — Boris Cherny

**代码负责走路，模型负责在需要判断的位置上出手。**

### 4.2 Dynamic Workflow 机制

```text
强模型出场（一次性）：
用户目标 -> LLM 生成 Workflow Script
           +-- 阶段定义（phase -> plan -> research -> draft -> review -> finalize）
           +-- 并行控制（Promise.all）
           +-- 循环控制（for i<3: 最多回炉三次）
           +-- 分支控制（if/else）
           +-- 验收标准（assert）

弱模型执行（多次）：
Workflow Script -> Runtime 逐阶段执行
                  +-- 阶段：由代码切换
                  +-- 并行：由代码 Promise.all
                  +-- 循环：由代码 for
                  +-- LLM 只出现在 agent() 和 assert() 调用处
```

**模型只出现两类位置**：

- `agent(taskPrompt)` → **干活**（带验收标准的 worker）
- `assert(condition)` → **判断**（返回布尔信号驱动分支）

### 4.3 六种典型 Workflow 模式（来自 Claude Code Dynamic Workflows）

| 模式 | 结构 | 适合场景 |
|:-----|:------|:---------|
| **① Classify-and-Act** | 先分类→交对应Agent→可选再分类 | 工单分派（Bug/功能/咨询） |
| **② Fanout-and-Synthesize** | 拆子任务→各 Agent 独立处理→汇总合并 | 多角度调研、代码审查、批量验证 |
| **③ Adversarial Verification** | A 产出→B 验证→C 反方检查 | 安全分析、事实核查、方案评估 |
| **④ Generate-and-Filter** | 批量生成→评分/去重/筛选 | 方案筛选、命名、架构比较 |
| **⑤ Tournament** | 多方案两两比较→评审→胜出 | CLI 命名、产品方案、架构路线 |
| **⑥ Loop-Until-Done** | 持续启动直到满足停止条件 | 调试、根因分析、持续验证 |

### 4.4 状态管理设计

**Session = append-only fact log**（唯一事实源）：

```text
Session {
  id: UUID
  facts: Fact[]          // append-only，记录"发生了什么"
  tasks: Task[]          // 当前任务状态
  artifacts: Artifact[]  // 产物清单
}

Fact {
  timestamp: Time
  type: "plan" | "execute" | "error" | "verify" | "decision"
  content: any           // 具体内容
  provenance: string     // 来源标注
}
```

**派生原则**：progress.txt、状态缓存等都是从 Session facts 派生出来的，可以丢弃重建。唯一不可丢失的是 Session。

**Checkpoint 三种粒度**：

| 粒度 | 触发条件 | 恢复方式 |
|:-----|:---------|:---------|
| 全量快照 | 里程碑/人确认后 | 直接加载 |
| 增量快照 | 每步/每 N 步 | 全量 + apply deltas |
| 事件驱动快照 | 进入不可逆区域前 | 事务式恢复 |

### 4.5 Harness 五阶段执行流水线

```text
Admission -> Prepare -> Execute -> Finalize -> Persist
|           |          |          |          |
|输入校验   |装配数据源 |调用LLM   |结果校验  |写Session
|边界控制   |加载工具   |路由Tool  |证据链检查|写Audit
|Grant预检  |权限注入   |多步推进  |答案溯源  |写Trace
|预算分配   |Context组装|中间状态  |质量评估  |触发回调
```

失败时回退到最近成功阶段重试，不是从头开始。

## 5. CLI 协同层：面向 Agent 的执行边界

### 5.1 为什么 Agent 需要 CLI

**核心论点**（来自 [工具链工程化](2026-06-26-agent-toolchain-cli-execution.md)）：

> **CLI 不是 API 外壳，而是一道明确的执行边界。**

LLM 通过自然语言调用工具，但自然语言天然存在歧义。CLI 的作用是将"能明确成参数的东西"从自由文本中提取出来，让 Agent 用稳定、可检验的方式与系统交互。

| 方式 | 成功率 | 可复现性 | 错误定位 | 适合场景 |
|:-----|:-------|:---------|:---------|:---------|
| 自由文本指令 | ~60% | 低 | 模糊 | LLM 内部推理 |
| MCP 调用 | ~95% | 高 | 明确 | 标准化工具集成 |
| **CLI 调用** | **~99%** | **极高** | **精准** | **高频稳定操作** |
| 原生 API | ~100% | 极高 | 极精准 | 内部确定性逻辑 |

### 5.2 面向 Agent 的 CLI 设计规范

**原则一：参数不靠模型猜**

```bash
# ❌ 差：让 LLM 自由发挥
ai build --source ./src

# ✅ 好：参数明确，结构化
ai-build submit --type release --config ./config/release.yaml \
    --dry-run --format json
```

**原则二：输出结构化是底线**

```json
{
  "status": "success",
  "phase": "build",
  "task_id": "build-20260708-001",
  "artifacts": ["./dist/app-v2.1.0.bin"],
  "duration_ms": 34500,
  "error": null
}
```

Agent 需要的是可解析的反馈，包含：当前状态、产物路径、错误位置 + 下一步建议。

**原则三：安全设计靠 CLI 本身，不靠提示词**

```bash
# 删除/覆盖/批量写入等操作必须有：
--dry-run     # 预检模式
--confirm     # 确认机制
--format json # 结构化输出用于自动判断
```

**原则四：失败路径清晰**

```text
请求执行
  |
  +-- ✅ 参数校验通过 -> 执行中 -> 成功
  |
  +-- ❌ 失败
        |
        +-- ⚠️ 鉴权失败 -> 提示重新登录
        +-- ⚠️ 参数错误 -> 明确哪个参数和格式
        +-- ⚠️ 网络超时 -> 自动重试（有上限）
        +-- ⚠️ 资源不存在 -> 停止，返回空
        +-- ⚠️ 权限不足 -> 提示需申请权限
```

CLI 的职责是明确告诉上层失败发生在哪个阶段并给出可恢复动作，而不是丢一句模糊报错。

### 5.3 Skill ↔ CLI 分层架构演化

```text
阶段1：Skill + Scripts（早期验证）
  Skill 里塞满执行细节 -> 只能单人单 Agent 用

阶段2：Skill + CLI（稳定后）
  Skill 只负责：触发判断 + 上下文读取 + 异常分流 + 交付规范
  CLI 只负责：鉴权 + 参数校验 + 网络请求 + 文件处理 + 结构化输出
```

| 维度 | Skill + Scripts | CLI + Skill |
|:-----|:----------------|:------------|
| 适用阶段 | 早期验证、低频任务 | 团队复用、高频稳定流程 |
| 执行入口 | 脚本路径和约定 | 稳定命令和明确参数 |
| 返回结果 | 临时日志、散落文件 | JSON、状态、任务ID、产物路径 |
| 测试方式 | 依赖脚本作者习惯 | 可系统测试参数/返回值/错误码 |
| 风险控制 | 靠人工记忆 | dry-run、预检、危险操作拦截 |
| 维护成本 | 容易长成脚本堆 | 初期更重，后期更稳 |

### 5.4 优先 CLI 化的场景判断

**适合优先**：

- 文档创建/更新/素材上传/图表插入
- 审批读取/任务查询/日志检索
- 数据查询/报表生成/批处理导出
- CI 诊断/构建结果分析/发布前检查
- 工单流转/状态同步/通知分发

**暂缓**：

- 仍处探索期的流程
- 严重依赖开放式判断
- 失败模式还没看清楚
- 边界没稳定之前

## 6. Browser 协同层：AI 友好的浏览器交互

### 6.1 为什么需要 Browser Agent

**核心场景**：仍有大量企业系统和 Web 应用不提供 API/CLI——只有 GUI。在这些场景中，Browser Agent 是不可绕过的最后一公里。

| 场景 | API/CLI 可用 | 是否需要 Browser |
|:-----|:------------|:----------------|
| 内部开发系统 | ✅ 通常有 | 不需要兜底 |
| SaaS 平台 | ⚠️ 部分有 | 需要兜底 |
| 遗留系统 | ❌ 无 | **必须** |
| 第三方合作平台 | ❌ 无 | **必须** |
| 社交媒体/论坛 | ⚠️ 部分开放 | 需要兜底 |
| 监管/政府平台 | ❌ 无 | **必须** |

### 6.2 Browser 在 Agent 架构中的定位

```text
确定性优先路由（INV-R 扩展）：
Rule > API > CLI > MCP > Browser > Free-form LLM
(确定性最高)                     (概率性最高)
```

Browser 的定位是**兜底层**——当更可靠的方式不可用时才使用。这不是看不起 Browser，而是尊重工程现实：GUI 操作的成功率（~70%）显著低于 CLI（~99%）。

### 6.3 Browser Agent 架构设计

```text
Agent 规划层
    |
    v
Browser Agent 子模块
    |
    +-- 导航引擎（Navigate）
    |   +-- URL 解析 -> 页面加载 -> 等待渲染完成
    |
    +-- 元素定位引擎（Locate）
    |   +-- 文本匹配（按钮文字/标签）
    |   +-- 结构路径（CSS/XPath）
    |   +-- 视觉定位（截图+OCR）
    |   +-- 语义匹配（LLM 辅助理解页面意图）
    |
    +-- 交互引擎（Interact）
    |   +-- 点击/填入/选择/滚动
    |   +-- 表单填充（结构化数据映射）
    |   +-- 等待/确认/截图验证
    |
    +-- 提取引擎（Extract）
    |   +-- 文本抽取（get_text/snapshot）
    |   +-- 结构化数据（表格/列表->JSON）
    |   +-- 截图分析（Vision 辅助）
    |
    +-- 失败处理引擎（Fallback）
        +-- 超时 -> 截图分析，判断是加载中还是页面变化
        +-- 元素找不到 -> 截图 + LLM 辅助定位
        +-- 登录态失效 -> 触发重新登录流程
```

### 6.4 与 CLI 的协同策略

当 Agent 遇到一个操作时，按**确定性降序**尝试：

```python
def execute_operation(operation):
    # 1. 尝试 CLI（最高确定性）
    if has_cli(operation):
        return call_cli(operation)

    # 2. 尝试 MCP（次高）
    if has_mcp(operation):
        return call_mcp(operation)

    # 3. 尝试 API（需要鉴权+建连）
    if has_api(operation):
        return call_api(operation)

    # 4. 兜底：Browser（最低确定性）
    return browser_agent.execute(operation)
```

**关键原则**：路由决策不应由 LLM 做——用规则引擎。LLM 可以"建议"用什么工具，但最终路由由确定性层决定。

### 6.5 Browser Agent 的安全门控

| 操作类型 | 是否需要确认 | 原因 |
|:---------|:------------|:-----|
| 页面读取/截图 | 否 | 只读操作 |
| 表单填写 | 低风险自动 | 白名单 URL |
| 点击提交 | 高风险需确认 | 可能触发不可逆操作 |
| 删除/修改数据 | 必须确认 | 业务影响 |
| 支付/下单 | 必须确认 | 财务风险 |

## 7. 确定性-概率性路由的黄金法则

### 7.1 INV-R 扩展：完整路由排序

```text
+--------------------------------------------------------------+
|                    确定性优先路由（INV-R）                     |
+--------------------------------------------------------------+
|                                                            |
|  Rule (硬编码规则) ----- 确定性 100%                        |
|    |                                                        |
|    v                                                        |
|  API (原生接口) -------- 确定性 ~100%                        |
|    |                                                        |
|    v                                                        |
|  CLI (命令行) ---------- 确定性 ~99%                         |
|    |                                                        |
|    v                                                        |
|  MCP (协议调用) -------- 确定性 ~95%                         |
|    |                                                        |
|    v                                                        |
|  Browser (GUI) -------- 确定性 ~70%                         |
|    |                                                        |
|    v                                                        |
|  Free-form LLM (自然语言) - 确定性 ~60%                     |
|                                                            |
+--------------------------------------------------------------+
```

### 7.2 路由选择矩阵

| 任务特征 | 推荐路由 | 备选路由 | 理由 |
|:---------|:---------|:---------|:-----|
| 高频重复操作 | CLI | API | CLI 更稳定、易调试 |
| 低频复杂操作 | MCP | Browser | MCP 协议标准化 |
| 一次性的/探索性的 | Browser | Free-form LLM | 不值得建 CLI |
| 鉴权/文件操作 | CLI | API | CLI 自带 Shell 环境 |
| 跨系统协同 | MCP | — | MCP 协议标准化 |
| 登录后操作 | Browser | — | 无 API 可用 |
| 批量数据处理 | CLI | API | 管道+脚本天然适合 |
| 动态页面抓取 | Browser | — | 需要执行 JS |

### 7.3 路由演进策略

```text
时间线 ->
+----------------------------------------------------------------+
| 初始阶段：Browser + Free-form LLM（快速验证，70% 确定性）      |
|    v                                                          |
| 优化阶段：发现高频操作 -> 封装为 MCP Server（~95% 确定性）     |
|    v                                                          |
| 成熟阶段：MCP Server 进一步 CLI 化（~99% 确定性）              |
|    v                                                          |
| 固化阶段：CLI 进一步封装为 Rule 引擎（~100% 确定性）           |
+----------------------------------------------------------------+
```

**关键洞察**：每一条新的确定性路径 = 永久消除不确定性。CLI/Tool 建设是最高 ROI 的投入。

## 8. 与传统交互模式的全维度对比

### 8.1 五维模式对比

| 维度 | 传统 GUI 应用 | REST API 模式 | 基于 LLM 的 ChatBot | Agent 混合架构 |
|:-----|:-------------|:--------------|:-------------------|:--------------|
| **交互方式** | 菜单/按钮/表单 | URL+Method+Body | 对话+自然语言 | **目标驱动+自主规划** |
| **用户角色** | 操作者（每一步都手动） | 开发者（写代码调用） | 提问者（追问补充） | **委托者（定义目标+验收）** |
| **执行确定性** | 100%（代码路径固定） | 100%（接口契约） | ~60%（LLM 随机性） | **~95%（确定性框架兜底）** |
| **可观测性** | 日志+埋点 | 请求响应日志 | LLM 输出文本 | **Trace+Session 全链路** |
| **扩展性** | 加功能模块→发布新版本 | 加接口→发布新版本 | 改 Prompt/加 RAG | **加 Tool/CLI/Skill 即扩展** |
| **容错方式** | Try-Catch 异常处理 | 状态码+重试 | 重新提问 | **反射+换策略+升级+自动恢复** |
| **学习成本** | 需要学习操作方法 | 需要学习接口文档 | 自然语言（最低） | **需要理解"什么能委托"** |

### 8.2 三层交互范式的演进路径

```text
Phase 1: Copilot（副驾驶）
用户主导 -> Agent 提供建议和辅助
+-- 用户：执行操作的主体
+-- Agent：提供建议/搜索信息/辅助决策
+-- 典型：CoPilot、AI 搜索

Phase 2: Collaboration（协作）
人机分担 -> 常规任务 Agent 自主，复杂用户介入
+-- Agent：处理 Routine 操作
+-- 用户：审批异常+处理边界情况
+-- 典型：Agentic RAG、审查工作流

Phase 3: Supervision（监督）
Agent 主导 -> 用户只监督关键节点
+-- Agent：全流程自主执行
+-- 用户：看报告+干预关键决策
+-- 典型：自动运维、批量处理
```

### 8.3 确定性 vs 概率性的"最佳融合度"

```text
           纯确定性                    纯概率性
           (传统软件)                (纯 LLM 对话)
               |                          |
               +----------+--------------+
                          |
                  +-------+-------+
                  |    Agent 混合   |
                  |   (最佳融合区)   |
                  +---------------+
```

| 维度 | 确定性成分 | 概率性成分 | 融合点 |
|:-----|:----------|:----------|:------|
| **路由** | 规则引擎 | 工具选择建议 | Rule 决定最终路由 |
| **流程** | Workflow 脚本 | 任务规划 | 脚本确定结构，LLM 填充内容 |

| **安全** | Sandbox/Grant | 意图理解 | 用确定性约束兜底概率性风险 |

## 10. 企业级 Agent 落地的实战问题

### 10.1 从 Copilot 到 Autonomy 的四阶段路线

```text
          人工主导 -------------------------------> Agent 主导
              |           |           |           |
              v           v           v           v
          Phase 1    Phase 2     Phase 3     Phase 4
         Foundation   Copilot   Collaborative  Autonomy
            部署      协作模式      监督模式     完全自主
```

**各阶段关键工作**：

| 阶段 | 目标 | 关键动作 | 衡量指标 |
|:-----|:-----|:---------|:---------|
| **Phase 1** 基础建设 | 验证可行性 | 识别高价值场景 · 构建初版 Agent 原型 · 建立治理框架 | 成功率 > 80% |
| **Phase 2** 辅助模式 | 建立信任 | Agent 提建议+辅助 · 建立反馈闭环 · 收集性能基线 | 用户采纳率 > 60% |
| **Phase 3** 协作模式 | 扩大范围 | Routine 任务全自动 · 复杂任务人助 · Agent 间通信 | 自动化率 > 50% |
| **Phase 4** 监督模式 | 优化成熟 | 全流程自主 · 异常时才需要人 · 跨域能力融合 | 人工介入率 < 10% |

### 10.2 常见失败模式

| 失败模式 | 表现 | 根因 | 解决方案 |
|:---------|:------|:------|:---------|
| **Agentic Laziness** | 任务没做完就提前收工（50个问题只处理35个） | 上下文过长后自行"收工" | 动态 Workflow + 独立子 Agent |
| **Self-Preferential Bias** | Agent 偏好自己的输出，自我验证漏掉问题 | 验证和执行共享上下文 | 验证 Agent 独立（对抗式） |
| **Goal Drift** | 长任务中原始目标保持能力下降 | 上下文压缩导致信息丢失 | Checkpoint + 阶段性目标重申 |
| **Feedback Collapse** | 失败后不断重试同一路径 | 没有"换策略"机制 | 换策略触发（连续2次失败切换） |
| **Context Anxiety** | 窗口将满时焦虑，决策质量下降 | 上下文窗口物理限制 | 压缩策略 + 趋势监控 >70% 触发 |

### 10.3 安全与治理

**四道 Prompt Injection 防线**：

```text
Layer 1: 输入隔离 -> 用户输入不可信，先做注入检测
Layer 2: 输出校验 -> 结构化输出 Schema 强制
Layer 3: Capability 白名单 -> 只允许已注册的工具
Layer 4: HITL -> 高风险操作必须经过人
```

**不可逆度分级**：

```text
可逆 <--------------------------------> 不可逆
读取  写文件  发消息  API调用  支付  物理动作
(自动) (快照) (可撤?) (幂等?) (人确)  (禁止)
```

**原则**：Agent 默认操作空间 = "完全可逆"。不可逆操作按分级设置门控。

### 11.2 服务器研发场景的架构建议

```text
+--------------------------------------------------------------+

                       v
+--------------------------------------------------------------+
|  LLM 规划层                                                 |
|  · 拆解：SSH登录 -> 取日志 -> 分析 -> 对比历史 -> 生成报告    |
|  · 路由：SSH->CLI, 分析->Python, 报告->doc CLI               |
|  · 异常：SSH失败->试IPMI, 日志不全->问用户路径               |
+------------------+-------------------------------------------+
                   v
+--------------------------------------------------------------+
|  确定性框架层（Dynamic Workflow）                            |
|  phase("connect") -> phase("collect") -> phase("analyze")     |
|  -> phase("report")                                          |
|  · 并行：多台机器日志同时拉取                               |
|  · 回炉：分析不充分最多2轮                                  |
|  · 检查点：每阶段完成后存 checkpoint                       |
+------------------+-------------------------------------------+
                   v
+--------------------------------------------------------------+
|  CLI/Browser 执行层                                          |
|  · bmc-cli connect --host 10.0.0.1 (SSH/Redfish)           |
|  · bmc-cli get-sel --format json                           |
|  · bmc-cli get-sensor --format json                         |
|  · python analyze-sel.py --input sel.json --output report.md|
|  · doc-cli generate --template fault-report --data report.md|
+--------------------------------------------------------------+
```

## 12. 总结与未来演进

### 12.1 核心结论

1. **Agent 是下一代的交互范式**，但不是替代所有——**确定性优先路由**是核心设计原则，Rule/API/CLI/MCP/Browser/LLM 各有定位

2. **三层分工是架构核心**：
   - LLM 规划层：做判断（不执行）
   - 确定性框架层：管流程（LLM Loop 搬进代码）
   - CLI/Browser 层：保执行（稳定可复现）

3. **从 ReAct 到 Dynamic Workflow 是 Agent 工程的分水岭**——把 Loop 从模型上下文搬进代码，是让 Agent 从"能用"到"可靠"的关键一步

4. **CLI 不是 API 外壳**，是明确的执行边界；**Browser 不是退步**，是兜底的最后一公里

5. **Agent 工程化的成熟度不在于能力多强，而在于不确定性能被约束在可控范围内**

### 12.2 未来演进方向

| 方向 | 当前状态 | 演进目标 |
|:-----|:---------|:---------|
| **Trace→Skill 闭环** | L3 会话后复盘 | 全自动：执行→分析→沉淀→固化 |
| **Agent 间通信** | MCP/A2A 协议初始 | 标准化跨 Agent 通信 |
| **多模型路由** | 手动指定 | 自动：简单任务用轻模型，复杂用强模型 |
| **自进化** | L1-L4 手动/半自动 | L5 源代码自更新 + 安全门控 |
| **Browser Agent** | 70% 成功率 | 90%+（视觉+语义定位融合） |
| **确定性覆盖率** | ~30%（初期） | ~70%（成熟后，通过 Trace→Skill 沉淀） |

### 12.3 快速检查清单

构建 Agent 混合架构时，对照以下自我检查：

- [ ] 每个执行操作是否对照了 INV-R 路由排序？
- [ ] CLI 是否具备结构化输出（JSON）、预检（dry-run）、失败阶段定位？
- [ ] Workflow 是否把循环/并行/分支控制从 LLM 搬进了代码？
- [ ] 是否配置了 Checkpoint 以支持中断恢复？
- [ ] 是否有验证 Agent 独立于执行 Agent（对抗式验证）？
- [ ] 高风险操作是否按不可逆度分级设置了门控（HITL）？
- [ ] 是否有 Trace→Skill 的沉淀闭环？
- [ ] Browser 是否只作为兜底层使用，而不是首选？
- [ ] 每条"信念"是否标注了置信度？是否触发漂移检测？
- [ ] 是否有"换策略"机制（连续失败 2 次切换路径）？
