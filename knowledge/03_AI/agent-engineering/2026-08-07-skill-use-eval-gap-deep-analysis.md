## 1. 缺口全景：技能繁荣 × 评测滞后

### 1.1 供给端：技能生态指数级增长

SKT 论文给出的关键事实（2608.02287）：

> "Since October 2025, more than **600,000 skills** have been made publicly available, and this number continues to grow."

本地佐证（2026-08-07 GitHub 日报）：`open-kimi-ppt-skill` 单日 +713 star、Skill 商品化范式持续——技能已成为 Agent 生态的"应用商店"。

### 1.2 需求端：评测体系停留在"任务成功率"

传统评测（SkillsBench / AgentSkillOS / MolBench 等）只回答一个粗粒度问题：**任务做成了吗？** 但无法回答：

| 未回答的问题 | 对应的评测缺口 |
|:--|:--|
| 模型真的用了这个技能吗？还是靠通用推理蒙对的？ | 使用真实性缺口 |
| 技能被用到了几分？哪些约束被遵守、哪些被忽略？ | 覆盖充分性缺口 |
| 换一个 harness，技能还好用吗？ | 环境条件性缺口 |
| 第三方技能里藏了恶意逻辑，模型能识别吗？ | 信任安全缺口 |
| 模型"声明"会用的技能，实际训练/评测过吗？ | 训练供给缺口 |

**这正是"声明会用 vs 实际会用"的完整内涵**：技能生态承诺了能力，评测体系却从未验证兑现。

## 2. 核心量化：Skill-Use 把「声明 vs 实际」钉在 0.613

> 本节为上午 [Harness 实证化四篇](2026-08-07-harness-empirical-four-papers.md) 中 Skill-Use 的核心结论浓缩（2608.04828，华东师大/港科大/复旦/腾讯混元）。

**测试设计**：技能以"渐进式披露"提供——模型只看到技能**名称 + 单行描述**（即"声明"），须主动检索全文才能"实际"使用。79 技能 / 177 任务 / 9 域 / Docker 沙箱 / 8 模型 × 2 harness，三分解指标：

- **Trigger**（识别该用哪个技能）
- **Compliance**（遵循技能约束执行）
- **Boundary**（识别技能适用边界，不越界）

**量化结果**：

| 指标 | 最强配置 | 含义 |
|:--|:--:|:--|
| 综合 SU | **0.613** | 最强配置也仅 61.3% 成功率 |
| 触发后 Compliance | 0.638 | 触发是独立瓶颈，触发≠会用 |
| Boundary | 普遍 > Compliance | 守界比执行容易 |
| 换 harness | 分数与排名全变 | 使用率是 model-harness 联合属性 |

**一句话结论**：*"SU is a property of a model-harness configuration, and rankings under one harness may not transfer to another."* —— 技能使用不是模型属性，是**配置属性**。评测必须同时固定模型与 harness。

## 3. 四缺口矩阵：评测→训练→覆盖→信任

把 2026-06~08 五篇论文映射到评测价值链，缺口呈现递进结构：

```
  评测缺口（怎么测）         训练缺口（怎么补）         覆盖缺口（测到什么粒度）    信任缺口（能不能信）
  ┌──────────────┐      ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
  │ Skill-Use    │  →   │ SKT          │  →   │ Skill        │  →   │ AgentTrap    │
  │ (2608.04828) │      │ (2608.02287) │      │ Coverage     │      │ (2605.13940) │
  │ 首测 SU 0.613│      │ 验证数据训练 │      │ (2606.20659) │      │ 恶意技能识别 │
  │ 缺口被量化   │      │ 16 项全提升  │      │ 覆盖仅 38-46%│      │ 副作用被正常化│
  └──────────────┘      └──────────────┘      └──────────────┘      └──────────────┘
        ↑ 暴露缺口               ↑ 补评测缺口                ↑ 补粒度缺口            ↑ 补信任缺口
```

四个缺口的**证据链闭环**：Skill-Use 量化了"不会用"→ SKT 证明"可以训练会用"→ Skill Coverage 证明"测不到底"（覆盖率太低）→ AgentTrap 证明"会用了也可能被恶意技能带偏"。

## 4. 缺口②训练供给：SKT 验证数据合成（全文深挖）

> SKT（Skill-use Training）= 目前最完整的"技能使用训练数据"生产管线。2608.02287，2026-08-03。

### 4.1 管线设计（三阶段 + 双层验证）

```
Stage I 技能筛选     Stage II 任务合成           Stage III 轨迹合成
─────────────      ─────────────────────      ─────────────────────
技能池 2,000 个  →  模板驱动任务生成         →  4 教师 × 2 harness 求解
rubric LLM 把关  →  规则验证器（确定性）     →  规则验证器（结果+轨迹）
组合判定(k=1/2/3) →  agent 验证器（语义）    →  LLM 验证器（技能真实使用）
                  →  难度控制（p_pass<0.6）  →  失败重采样（不给反馈）
                  →  反馈引导修复（失败回炉）→  通过才入训练集
```

**关键设计决策**（与"声明 vs 实际"直接相关）：

1. **技能依赖配对测试**：同一任务做"有技能 / 无技能"两次 rollout，`r⁺ > r⁻` 才接受——**确保任务真正依赖技能**，防止模型靠通用推理蒙混过关（这正是"实际用了技能"的最低证据）。
2. **轨迹侧 LLM 验证器**：要求每个技能**在动作前被咨询、影响具体决策、且应用正确**；"仅打开/复述技能文件、事后引用、完全靠通用推理完成"均判不通过——**对"假装用了技能"的显式拦截**。
3. **难度控制**：`p_pass ≥ 0.6` 的任务判为太易，回炉修复——防止训练数据被"简单任务刷屏"。

### 4.2 数据规模

| 维度 | 数值 |
|:--|:--|
| 技能来源 | skills.sh 精选 2,000 个 |
| 任务包 | 4,000（单技能 1,520 / 双技能 1,295 / 三技能 1,185） |
| 候选配对 | 4,000 任务 × 4 教师 × 2 harness = 32,000 |
| **验证通过轨迹** | **27,164**（DeepAgents 14,277 + OpenCode 12,887） |
| 教师模型 | MiniMax-M2.5 / GLM-5 / Qwen3.5-397B-A17B / DeepSeek V4 Pro |
| 训练模型 | Qwen3.5-9B、Gemma 4 E4B-IT（全参数 SFT，1 epoch） |
| 评测基准 | SkillsBench(77) / MolBench-Bind(37) / AgentSkillOS(30) / **SkillEval(100, 留出)** |

**SkillEval 是同管线产出的留出基准**：100 任务 × 100 技能组（30 单 / 46 双 / 24 三），与训练池零重叠——"评测数据生成"与"训练数据生成"同一套管线，**评测缺口可以由同一条生产链自动补**。

### 4.3 效果：16 项对比全部提升（+3.20 ~ +18.91）

| 模型 | Harness | SkillsBench | SkillEval | MolBench | AgentSkillOS |
|:--|:--|:--:|:--:|:--:|:--:|
| Qwen3.5-9B | OpenCode | 5.80→**15.79** | 55.24→**72.48** | 33.11→**44.59** | 79.61→**84.70** |
| Qwen3.5-9B | DeepAgents | 4.94→**13.62** | 51.62→**70.53** | 31.76→**47.30** | 74.03→**79.84** |
| Gemma4-E4B | OpenCode | 7.08→**10.28** | 61.01→**72.85** | 34.46→**45.27** | 49.41→**56.74** |
| Gemma4-E4B | DeepAgents | 5.07→**9.24** | 56.14→**66.39** | 31.76→**41.89** | 42.23→**47.38** |

（0-100 尺度，4 次运行均值；全部 16 个 model-harness-benchmark 组合均提升）

### 4.4 四个机制性发现（比"有效"更重要的结论）

**① 提升的是"用外部技能"，不是"内化技能"**
技能撤销时增益仅 0.53-5.69 分，技能提供时 8.68-18.91 分——**SFT 教会模型的是"会读会用外部技能"**，而非把技能背进参数。这对"技能内化"路线（Skill0/SkillC 等）构成对照证据。

**② 数据质量是命门：未验证数据 SFT 反而有害**
未验证/未修复的原始合成数据 SFT 使四项基准**全部下降**，与 SKT 的差距达 11.91-24.61 分。→ **"声明会用"的训练数据，必须先经过"实际会用"的验证，否则训练即污染**。这直接呼应 08-05 知识库方法论"增强式占位模板（归因过验证）"。

**③ 跨 harness 迁移保留 ~50%，混合训练逼近 Specialist**
跨 harness SFT 保留匹配增益的 49.1%-58.1%；混合训练单个 checkpoint 与 Specialist 差距 ≤2.71 分（3 处甚至反超）。→ 技能使用行为**部分可迁移 + 部分 harness 特定**，与 Skill-Use 的"配置属性"结论互证。

**④ 扩展性单调 + 多技能组合是主战场**
训练技能数 100→2,000，SkillEval 55.24→72.48 单调上升；K=2 组合增益最大（3.95→20.72，**+16.77**），K≥3 也有 +8.04——**技能编排（多技能协同）正是"声明会"与"实际会"差距最大的地带**，与 Skill-Use 触发后执行瓶颈同源。

## 5. 缺口③覆盖充分性：Skill Coverage 测试度量

> 2606.20659（利物浦大学），2026-06-09。

**问题**：任务成功 ≠ 技能被充分测试。一个 80 行技能的 SKILL.md，任务做成了，但模型可能只用了其中 3 行指令。

**方案**：把技能的自然语言指令**翻译成半结构化行为约束**（"在条件 X 下应执行 Y"），逐条判定轨迹是否覆盖（Covered/Not Covered）与是否遵守（Pass/Fail）——把"测试覆盖率"思想从代码测试引入技能测试。

**量化结果**（SkillsBench leaderboard 轨迹）：

| 指标 | 数值 |
|:--|:--|
| 技能行为约束平均覆盖率 | **38.66% - 45.51%** |
| 用 Fail 约束强化技能文本（仅强调原指令）后 | 失败任务恢复率 **16.0%**（5 个模型行平均） |

**两个含义**：
1. **覆盖缺口巨大**：一半以上的技能指令在任务执行中从未被触达——现有评测的"任务成功率"掩盖了技能大部分指令是**死代码**的事实；
2. **Fail 约束是可执行信号**：覆盖率度量不只是报告，还能定位"哪条指令没被遵守"→ 强化后平均恢复 16% 失败任务——**评测结果可以直接反哺技能内容**（闭环）。

## 6. 缺口④信任安全：AgentTrap 运行时信任失败

> 2605.13940（港大等），2026-05-13。

**问题升级**：第三方技能 = Agent 的"包生态"（npm/pip 的 LLM 版）。恶意技能**不需要**让模型做明显有害动作——把有害行为伪装成常规工作流的一部分，让高权限 Agent 在少人监督下执行。

**测试**：141 任务（91 恶意 + 50 良性）× 16 安全维度，沙箱执行完整轨迹，判定四态（攻击成功 / 拦截拒绝 / 攻击未触发 / 无攻击证据）。

**中心发现**（原文）：

> "The most informative failures are not simple jailbreaks. Models often **complete the visible user task while treating unsafe side effects introduced by the skill as part of the normal workflow**."

即：模型完成了用户可见任务，同时**把技能的恶意副作用当作正常流程的一部分**——这是"声明会（用技能）vs 实际会（识别技能是否安全）"在信任维度的镜像：**会执行 ≠ 会判断**。与 Skill-Use 的 "Boundary 守界" 发现同构——技能边界识别（含安全边界）是普遍弱项。

**关联攻击面**（同主题族）：SkillMutator（2606.14154，语言-代码跨模态攻击）、SkillHarm（2606.02540，技能生命周期攻击）——技能作为"可执行声明"，正在成为供应链攻击的新载体。

## 7. 「声明 vs 实际」的统一语义框架

四篇论文看似独立，实则统一在同一个语义缺口上——**"声明"与"实际"之间隔着一层验证**：

| 层 | 声明（Claimed） | 实际（Actual） | 验证机制 | 量化缺口 |
|:--|:--|:--|:--|:--|
| **模型能力** | 模型会使用技能 | 真实 SU | Skill-Use 三分解评测 | 最强 0.613 |
| **训练数据** | 轨迹教会用技能 | 轨迹真用了技能 | SKT 双层验证器 | 未验证数据 -11.91~-24.61 |
| **技能内容** | 技能指令有效 | 指令被遵守 | Skill Coverage 约束覆盖 | 覆盖仅 38.66-45.51% |
| **技能安全** | 第三方技能可信 | 运行时无恶意 | AgentTrap 动态沙箱 | 恶意副作用被正常化 |

**第一性原理**：技能本质是"把程序性知识压缩成自然语言声明"，而 LLM 对声明的**执行**是概率性的、对声明的**验证**是缺失的。**评测缺口的根源 = 声明（确定性文本）与执行（概率性行为）之间的翻译层从未被系统度量**。SKT 的"技能依赖配对测试"和 AgentTrap 的"沙箱轨迹判定"都是对这个翻译层的显式验证——方向一致，层次不同。

## 8. 批判性审视

1. **SKT 训练模型仅 9B/4B 级**：Qwen3.5-9B、Gemma 4 E4B 是小模型，提升显著但无法外推到旗舰模型（旗舰是否同样受益未知）；
2. **评测基准同源风险**：SkillEval 与训练数据同管线生成（仅池子不同），存在"自产自销"的系统性偏差——需要第三方独立基准交叉验证；
3. **验证器依赖 LLM**：SKT 的语义验证器与 AgentTrap 的恶意判定都依赖 LLM 判断，**验证器本身的错误率未报告**，存在"用可能不可靠的裁判给数据打分"的循环；
4. **Skill Coverage 覆盖度量粒度**：半结构化约束提取本身依赖 LLM，约束集是否完备（漏掉关键指令）未验证；
5. **时间窗口**：Skill-Use/SKT 都是 08 月初 preprint，未经同行评审；AgentTrap 已过审（05-13），可信度更高；
6. **成本沉默**：SKT 27,164 条验证轨迹的合成成本（DeepSeek V4 Pro 任务合成 + 4 教师 × 2 harness rollout + 双层验证）未披露，可复制性存疑；
7. **"声明 vs 实际"的边界**：本文聚焦技能使用；但模型对用户指令的"声明理解 vs 实际执行"（如 [Reason Less, Verify More](https://arxiv.org/abs/2607.07405) 的策略违反）是同一缺口在指令域的映射，未展开。

## 9. 预测 P1-P5

- **P1（高置信）**：2027 年前出现"技能使用排行榜"（固定模型×harness 网格的 SU 排名），Skill-Use 三分解成为默认报告格式；
- **P2（中置信）**：验证数据合成（SKT 路线）成为技能训练数据的主流生产范式，"未验证合成数据不进入训练"成为默认工程约束；
- **P3（中置信）**：技能覆盖率（Skill Coverage 路线）进入主流 Agent 评测，任务成功率与覆盖率双指标报告；
- **P4（高置信）**：第三方技能供应链安全评测（AgentTrap 路线）成为 Agent 平台的发布门禁——技能市场的"应用商店审核"机制出现；
- **P5（低置信）**：多技能编排（K≥2）成为技能评测与训练的主战场，单技能评测退居基线。

## 10. 本系统启示

1. **技能触发率自检**：参照 Skill-Use Trigger 指标，为本系统 40+ 技能加"触发率"统计（哪些技能从未被触发 = 死技能），对应 [五工程×双产品](2026-08-05-five-engineering-claude-code-trae-deep-analysis.md) 的"技能描述质量=触发第一杠杆"；
2. **验证器思想落地**：SKT 的"规则验证器（确定性）+ LLM 验证器（语义）"双层结构，与知识库既有 50+ check 脚本（确定性层）一致，可补 LLM 语义层（如 doc-reviewer 已有雏形）；
3. **训练数据纪律**：任何用 LLM 生成的训练/蒸馏数据，必须先过验证再进库——对应 [MindMemOS](../../06_others/sources/2026-08-06-huawei-mindmemos-agent-memory.md) 的 Dreaming 蒸馏同样有"编造"风险（见姊妹篇记忆两极化分析）；
4. **技能内容死代码治理**：Skill Coverage 思想可迁移到本库技能审查——检查 SKILL.md 中从未被遵守的指令段；
5. **多技能协同是真实场景**：本系统日常任务多为多技能编排（读技能+搜索+写文档+索引同步），K≥2 是主战场，值得针对性评测；
6. **边界/安全评测优先**：AgentTrap 证明"会执行≠会判断"，本系统在引入第三方技能（open-source-skill-packer 封装）时应优先做安全审查——对应 skill-security-vetter 技能。
