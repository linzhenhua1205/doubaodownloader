## 〇、结论概要

**一句话：Aries 用「全栈可复现实验」证明当前 agent 服务的度量体系在度量错误的对象——token 中心指标把「模型推理成本」当成了「系统成本」的全部，而 agent 服务真正的瓶颈在非推理路径（轨迹重建、上下文管理、沙箱生命周期）上。**

1. **度量对象错误是第一性问题**：token 指标测的是「模型消耗」，但 agent 服务的成本结构是「推理 + 上下文保持 + 工具执行」三元的——后两者在传统 LLM serving 中几乎不存在，token 指标天然看不见它们。
2. **三个实证发现互为因果**：上下文保留收益递减（发现二）是因为 agent 需要持久上下文；持久上下文抬高容量占用；沙箱长空闲/短突发（发现三）是因为工具调用是稀疏的。三者共同说明：**agent 服务的单位不是「请求」，是「轨迹」**。
3. **设计愿景明确**：轨迹级指标、自适应上下文管理、弹性沙箱资源管理、最小攻击面沙箱——四个方向直接可转化为超节点软件栈的监控/调度/安全设计输入。
4. **对本地系统**：与 08-07「可观测性三要素同构」「观测层级决定论」闭环——Aries 是从「系统视角」证明「观测粒度错了，结论就错了」的又一例；同时为「约束脚本化=最高杠杆」提供反面参照（agent 服务的成本治理必须先有正确的度量面）。

## 一、背景：agentic serving 为什么不同于传统 LLM serving

传统 LLM serving 的抽象是**请求-响应**：客户端发 prompt，服务端返回 completion，一次调用即结束。工作负载特征是独立、短程、可并发的。

Agent 服务打破了这个抽象，Aries 概括为三个耦合特征：

| 特征 | 传统 LLM serving | Agent 服务 |
|:-----|:-----------------|:-----------|
| 推理调用 | 独立请求 | **重复推理**（多步循环内多次调用） |
| 上下文 | 请求内自包含 | **持久上下文**（跨步骤累积，随轨迹增长） |
| 外部效应 | 无（纯生成） | **沙箱化工具执行**（代码运行、文件操作、网络调用） |

这三个耦合特征产生三个新的成本维度：**轨迹状态**（如何跨步骤保持）、**上下文管理**（保留多少、何时压缩）、**工具生命周期**（沙箱何时建、何时挂起、何时销毁）。传统 serving 的度量体系（token 吞吐、首 token 延迟、TTFT/TTBT）对这三维几乎无感知——这正是 Aries 要证伪的对象。

## 二、Aries 框架：三要素设计

Aries 不是论文里的「建议」，而是可运行的实验框架，三要素：

1. **分离任务语义与执行配置**：同一个 agent 任务（如 SWE-bench 某 issue）可以在不同执行配置（不同 harness、不同沙箱、不同上下文策略）下运行——这是「可复现实验」的前提，把「任务」与「环境」解耦成两个可独立变化的轴。
2. **重建跨组件 agent 轨迹 + 关联系统遥测**：把 agent 生命周期（LLM 调用、工具调用、状态读写）在**组件边界**上重建为完整轨迹，并与**系统级遥测**（CPU/内存/网络/沙箱资源）时间对齐。这是「轨迹级度量」的基础设施——没有它，只能看到组件局部指标，看不到端到端行为。
3. **有状态工具执行的一致接口**：异构沙箱（Docker、Firecracker、gVisor、进程级隔离等）通过一致接口暴露 stateful tool execution——让「挂起/恢复/快照」成为可编程原语，而不是各沙箱各自为政。

实验方法上，Aries 用开放 agent harness + benchmark 做可复现实验，并辅以**商业平台的生产 traces** 交叉验证——让实验室结论有生产行为接地，避免纯合成负载偏差。

## 三、发现一：token 中心指标遗漏非推理瓶颈

**核心主张：以 token 为中心的指标（吞吐、成本/1K token、token 效率）无法捕捉 agent 服务中的非推理瓶颈。**

机理拆解：agent 轨迹中，LLM 推理只是时间线的一段。真实时间线还包括：
- **工具执行**：沙箱内代码运行、文件 I/O、网络调用——可能占 wall-clock 的显著比例；
- **状态序列化/反序列化**：上下文打包、轨迹持久化、快照保存/恢复；
- **调度与排队**：agent 请求长驻，与短请求混跑时的资源调度行为；
- **上下文搬运**：长上下文在 KV cache、CPU DRAM、磁盘间的移动。

这些瓶颈的共同特征：**与 token 数无关或弱相关**。例如快照恢复开销由「状态大小 + 沙箱冷启动」决定，不是由「本轮推理 token 数」决定。用 token 指标做容量规划、成本核算、性能调优，等价于用「油耗」衡量「载重」——相关但错位。

**与本地系统的直接映射**：MEMORY.md 记录的「跨节点判决量=单次通信延迟×层数」「KV 搬家 320KB/token 线性」等结论本质是「token 视角的推理成本」，而 Aries 提醒我们 agent 服务还要加一层「非推理成本」——后者在超节点场景（沙箱、快照、轨迹存储）可能占主导。

## 四、发现二：保留上下文的收益递减与容量代价

**核心主张：保留额外上下文带来递减的准确率收益，同时降低服务容量——上下文管理不是「多多益善」，是容量-质量权衡。**

机理拆解：
- **收益侧**：agent 在轨迹后期使用早期上下文的频率递减（多数早期状态要么已内化为当前 prompt 摘要，要么已过时）。多保留的上下文对最终准确率的边际贡献趋近于零。
- **成本侧**：每保留一份上下文，就占用一份 KV cache / 上下文窗口 / 带宽。长上下文请求的容量占用是短请求的数倍——在固定显存下，**上下文保留直接兑换为并发容量**。

两个方向叠加：多保留的收益递减、成本递增——存在**最优保留点**，超出即负收益。这为「自适应上下文管理」（按轨迹阶段动态决定保留/压缩/丢弃）提供了直接动机：不是等 KV 满了再压缩，而是按边际收益主动裁剪。

**与本地系统对照**：本系统 08-07 渠道成本实证（system prompt 118K→18K 省 85%、index 全量注入 98K→结构摘要 662 tokens 省 99.3%）正是「上下文保留收益递减」的工程实例——用结构摘要替代全量注入，是保留语义、砍掉容量占用的自适应上下文管理的本地实现。

## 五、发现三：沙箱长空闲/短突发与快照挂起成本

**核心主张：工具沙箱的工作负载呈「长空闲-短突发」交替，而当前快照式状态管理使「激进挂起」成本高昂——弹性沙箱资源管理需要新的状态模型。**

机理拆解：
- **工作负载形态**：agent 在推理时沙箱空闲，在工具调用时沙箱突发。突发可能只有毫秒-秒级，但资源需求峰值高（代码编译、数据处理）。
- **当前方案的困境**：为突发峰值常驻资源 → 空闲期浪费；挂起沙箱回收资源 → 恢复时要快照恢复（snapshot-based state management），而快照保存/恢复本身昂贵（序列化完整状态）。
- **「激进的挂起」为什么贵**：如果挂起/恢复的粒度是「完整状态快照」，那么挂起一次的成本 ≈ 状态大小 × 序列化开销；agent 轨迹中工具调用频繁交替，快照频繁触发，挂起成本累计超过保留资源成本——**两难：常驻浪费、快照更贵**。

**结论指向**：弹性沙箱需要比「快照整个状态」更细粒度的状态管理（增量快照、分层状态、惰性恢复），或让沙箱生命周期与轨迹阶段解耦。这与存储界的快照技术（增量/写时复制）同构——快照粒度决定弹性成本。

**对超节点的意义**：若 agent 服务规模化为超节点负载的一部分，沙箱资源池的调度（何时分配、何时挂起、快照放哪一级存储）将直接决定服务成本。Aries 的「长空闲/短突发」实证是设计沙箱资源池的第一手输入。

## 六、安全维度：沙箱攻击面

Aries 的补充安全分析指出：**需要减少沙箱攻击面**。agent 沙箱与普通容器不同——它运行的是「模型选定的代码」，攻击面 = 沙箱隔离强度 × 工具暴露面 × 会话持久性。状态化工具执行（长时间存活的沙箱 + 文件系统 + 网络）比无状态函数调用暴露面大得多。

这与 08-06 GitHub MCP allowlists「policies fail closed」、08-08 Agent 安全周更（越权→失控→假身份序列）构成同一主线：**agent 的工具面每扩大一维，准入控制就要收紧一档**。沙箱最小攻击面 = 默认拒绝 + 按需开放 + 轨迹级审计。

## 八、批判性审视

1. **摘要级信息密度**：三大发现均为方向性结论，未给出具体数字（如「挂起成本高」高多少、「容量降低」降多少）——需读全文获取量化数据，本分析基于摘要的机理推理。
2. **生产 traces 来源未指明**：「商业平台」是哪个平台、traces 规模/构成如何、是否与实验室基准同构——未披露，影响结论的外部有效性判断。
3. **基准覆盖有限**：「open agent harnesses and benchmarks」未列具体清单，agent 服务形态多样（单 agent/多 agent/长程/短程），发现的可迁移性待更多形态验证。
4. **「token 中心指标错位」非新观点**：SLO 研究（TTFT/TTBT 之外）、成本建模（vLLM 等）已有类似讨论；Aries 的增量在「全栈框架 + 生产 traces」的系统性，而非概念首创。
5. **沙箱挂起成本缺乏对照**：未说明「快照式挂起」与「保留常驻」的量化对比基线，两难结论的边界条件（什么规模下快照更贵）未给出。

## 九、可证伪预测（P1-P4）

- **P1（2026 年内）**：主流 agent serving 平台（vLLM/SGLang 生态或专用平台）将推出「轨迹级指标」类观测接口（轨迹 ID 贯穿推理+工具+状态，与系统遥测对齐）——若 Aries 的三发现被产业采纳，这是最直接的落地路径。
- **P2（2026H2）**：出现「自适应上下文管理」的产品化（按轨迹阶段自动压缩/摘要，而非 KV 阈值触发）——收益递减实证是它的理论依据。
- **P3（2027）**：沙箱状态管理出现增量快照/分层状态方案（借鉴存储快照技术），替代「整态快照」成为 agent 沙箱挂起的主流——若「快照比常驻贵」的实证成立，这是必然工程演化。
- **P4（2026 年内）**：至少一家国产 Agent 平台将 token 计价向「轨迹计价」或「混合计价」迁移（token + 工具执行 + 状态保持）——度量面最终会传导到商业计费面。

## 十、对本系统的启示

1. **超节点软件栈的观测设计**：agent 服务若上超节点，监控面必须包含「轨迹级遥测」——LLM 调用、工具执行、状态转换三段都要有时间对齐的遥测，否则非推理瓶颈不可见。
2. **上下文治理的量化纪律**：本系统 08-07 的 context compaction（95% 水位）+ 结构摘要注入已是「收益递减」的正确实践方向，可进一步按轨迹阶段做「保留/压缩」的边际收益决策。
3. **沙箱资源池设计输入**：长空闲/短突发的实证支持「按需分配 + 分层状态」的沙箱池设计，而非常驻容器池——对多租户 agent 服务尤其重要。
4. **安全准入与工具面同步收口**：沙箱攻击面分析与 MCP allowlists 同构——工具面每扩一维，准入控制收紧一档。
