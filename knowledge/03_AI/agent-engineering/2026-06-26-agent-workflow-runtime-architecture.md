## 核心论点

> **真正重要的不是某条神奇 Prompt，而是让 Loop 自己跑起来、稳定交付的运行时。**
> — Boris Cherny: "I don't prompt Claude anymore. I have loops running that prompt Claude."

Loop Engineering 的核心是把流程从模型临场推理中解放出来，**编译成一段可执行、可观察、可复用的 Workflow Script**。代码负责走路，模型负责在几个需要判断力的位置上出手。

---

## 一、ReAct 的软肋

- **流程全靠模型临场维持**：阶段顺序、工具选择、错误恢复、检查项 — 全部依赖模型当场理解并坚持执行
- **跑十次结构可能不同**：一次能跑通，但难以保证一致的执行结构
- **复盘困难**：执行路径在模型上下文里漂移，无法准确定位哪一步偏了

> ReAct 的成本不只是 token，真正贵的是把**整个流程交给模型的运行时自觉**。

---

## 二、Dynamic Workflow：先生成脚本，再让脚本调模型

**核心思想**：先用强模型把任务拆成一段 **Workflow Script**，脚本里写清楚阶段、并行、循环、分支、验收和日志。执行时，流程控制由代码完成，模型只在被显式调用的位置出现。

**"Dynamic" 的关键**：脚本不是工程师手写的固定 pipeline，而是模型按当前任务**现场生成**的。生成后就不再是自然语言，而是**一段普通代码**：能改、能存、能重跑。

**收益**：强模型只需要在"生成脚本"时出场一次。后续执行时可以用更便宜的模型。

> **确定的骨架归代码，不确定的判断归模型。**

---

## 三、Skill vs Workflow 对比

| 维度 | Skill | Dynamic Workflow |
|:-----|:------|:----------------|
| 结构位置 | 写在自然语言说明里，运行时由模型理解 | 写在脚本控制流里，运行时按代码执行 |
| 执行路径 | 每次可能不同，模型临场决定 | 阶段、分支、循环显式固定 |
| 对模型要求 | 高，需要持续遵守说明 | 低，模型只处理被调用的子任务 |
| 复盘方式 | 难以还原完整路径 | 日志、状态和阶段都可追踪 |
| 适合任务 | 探索性强、边界模糊、临时性任务 | 阶段清楚、有验收标准、会反复执行 |
| 成本结构 | 依赖强模型全程维持 | 强模型生成一次，普通模型执行多次 |

> 真实场景里两者会一起出现：先用 Skill 生成 Workflow，再用 Workflow 编排多个 Agent。

## 四、研究任务伪代码示例（关键机制）

```text
phase("scan")      -> 摸清问题背景
phase("plan")      -> 拆子课题（可并行）
phase("research")  -> Promise.all(并行研究)
phase("draft")     -> 合成报告
phase("review")    -> for 循环审稿+回炉（最多3轮）
phase("finalize")  -> assert 终验
```

**代码控制流（模型不需要记住的）**：

- `Promise.all` → 决定并行
- `for (let i=0; i<3; i++)` → 决定最多回炉三次
- `if (!needRewrite) break` → 决定何时跳出
- `throw new Error(...)` → 决定失败不静默吞掉

**模型只出现两类位置**：

- `agent()` → **干活**（带验收标准的 worker）
- `assert()` → **判断**（返回布尔信号驱动分支）

---

## 五、agent() 不是一次调用，是质量门

`agent(taskPrompt, verificationPrompt?)` = 带验收标准的 **worker**：

- 可以搜索、反思、重试、修正
- 通过内部验收才把结果吐给外层脚本
- **外层不必重复写 retry/score/fix 样板代码**

> 脚本层管路线，worker 层管产出质量。

## 六、可复用 Loop 的 8 个部件

| 部件 | 设计时要回答的问题 |
|:-----|:-----------------|
| **Trigger** | 用户手动、定时任务，还是外部事件？ |
| **Planner** | 大任务是否需要拆解？子任务能否并行？ |
| **State** | 中间结果放哪？变量、文件、数据库还是外部任务系统？ |
| **Workers** | 哪些部分交给 Agent？每个的输入输出是什么？ |
| **Evaluator** | 每阶段怎么判定过关？规则、测试还是 LLM-as-a-Judge？ |
| **Loop / Branch** | 哪些地方允许回炉？最多几次？失败后是否降级？ |
| **Stop / Resume** | 中途断掉怎么办？从哪步恢复？状态如何校验？ |
| **Repeatability** | 同脚本重复执行，哪些差异允许、哪些必须记录？ |

**长任务绕不过去至少需要 Trigger、Workers、Evaluator、State**。

---

## 七、可观测性不是装饰

- `phase()` → 告诉用户当前在哪个阶段
- `log()` → 记录细粒度动作
- **两类人机接口**：
  1. `askUserQuestion()` — 主动停住问人（如两个方向选一个）
  2. `drainInbox()` — 用户中途纠偏（loop 正在跑，用户发现方向不对）

> **Loop 越自动，越要给人留接口。否则它只是更有条理地犯错。**

---

## 八、什么时候不该写 Workflow

| 场景 | 理由 |
|:-----|:-----|
| 任务只做一次，边界模糊 | 先开一段对话更便宜 |
| 依赖大量临场判断 | 过早钉死流程反而限制模型发挥 |
| 验收标准写不清楚 | assert() 也救不了你，宽松裁判让错误安静通过 |

**Workflow 适合的场景**：任务会反复出现、阶段相对稳定、产出需要验收、过程需要复盘、成本需要压下来。

研究报告 · 内容生产 · 批量代码迁移 · 资料整理 · 周期性监控 · 复杂工单处理

## 九、结语要点

- ReAct 把 loop 放模型脑子里 ⇢ 灵活，但不稳
- Dynamic Workflow 把 loop 放进脚本 ⇢ 少即兴，多可复盘
- **Prompt 仍然重要，但它退到更小的边界里。外层的 loop，才是长任务能不能稳定跑完的关键**
- 当这些 loop 未来能被 Agent 自己读懂、修改、组合，Workflow 就从执行脚本升级为 **Agent Harness** 的一部分
