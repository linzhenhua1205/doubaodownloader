- 深度分析会话 3-6 turns 草草结束（vs 早间调研 14-50 turns）
- 每次 LLM 调用上下文 85K-163K tokens 高位运行，逼近 160K 上限

## 3. 证据链：五个关键事实

### 3.1 事实一：上下文严重超限，系统反复强制压缩

| 时间 | 事件 | 损失 |
|:-----|:-----|:-----|
| 12:40 | ~180801 > 160000, trimmed 4 turns | 压缩 4 turns |
| 13:54 | ~180371 > 160000, trimmed 3 turns | 压缩 3 turns |
| **18:02** | **~170543 > 160000, compressed 189→7 messages** | **85% 信息丢失** |
| 18:17 | ~161382 > 160000, trimmed 4 turns | 压缩 4 turns |
| 18:18 | ~162641 > 160000, trimmed 3 turns | 压缩 3 turns |
| 18:40 | ~176159 > 160000, trimmed 6 turns | 压缩 6 turns |

**关键机制**：feishu 渠道的 session 是长驻的，深度分析对话在同一 session 内持续累积（18:16 时已 141 messages）→ 每次新会话都在逼近 160K 上限的边缘启动 → 模型可用的"有效注意力"被历史对话稀释。

### 3.2 事实二：深度分析全部未调用 knowledge-doc-writer skill

```
18:00 后 10 个深度分析会话：knowledge-doc-writer 调用次数 = 0
对比：18:06 AI 网关会话（高质量）调用了 knowledge-doc-writer
对比：早间调研由 research_task_runner.py 脚本驱动（SKILL 内建）
```

**后果**：无格式门禁、无落盘规范、无质量检查强制。深度分析退化为"凭记忆输出 + 随手 write"。

### 3.3 事实三：turn 数骤降，多个会话"分析完就结束不落盘"

| 会话 | turn 数 | write 次数 | 结果 |
|:-----|:-------:|:----------:|:-----|
| 概念-操作双元 | **3** | **0** | ❌ 思考说"先给分析再落文档"→ 直接 Done，未落盘 |
| skills↔脚本 | **5** | **0** | ❌ 未落盘 |
| 插件 vs 配置 | **6** | **0** | ❌ 未落盘 |
| 验证重要性 | **6** | **0** | ❌ 未落盘 |
| loop 判断 | 12 | 1 | ✅ 落盘 |
| 存储 | 10 | 1 | ✅ 落盘 |
| 量化 | 6 | 1 | ✅ 落盘 |
| 原理-工程 | 5 | 1 | ✅ 落盘 |
| 开源商业 | 6 | 1 | ✅ 落盘 |
| loop 工程 | 4 | 1 | ✅ 落盘 |

**异常模式**：18:16-18:19 连续 4 个会话（概念-操作/skills↔脚本/插件-配置/验证重要性）全部 write=0 草草 Done——**这是"草草结束"的直接证据**。18:16 会话日志原文：*"我先给出分析，然后落一篇专题文档"* → 下一 turn 就是 `🏁 Done (3 turns)`，文档没写。

### 3.4 事实四：上下文规模对比——高质量 vs 劣化

```
18:06 AI 网关（50 turns 高质量）：Sending 39 messages → 41 → 43（上下文轻量）
18:16 概念-操作（3 turns 劣化）：Sending 141 messages → 143 → 145（上下文臃肿 3.5 倍）
```

**上下文越臃肿 → 有效注意力越少 → 模型越倾向"快速结束"**——这是劣化与超限的直接因果。

### 3.5 事实五：token 消耗高位运行

```
deepseek-usage.jsonl（18:40 区间）：
  prompt=163071 / 163926 / 164070（贴近 160K 上限）
  → 每次调用都在为历史对话付全量 token 费，且新会话的"思考空间"被压缩
```

## 4. 根因分析：两层结构

### 4.1 外部根因：上下文管理机制缺陷（系统层）

```
feishu session 长驻 → 上下文无限累积 → 160K 上限触发
→ 强制压缩（189→7）→ 早期关键信息（用户偏好/约束/前文分析）丢失
→ 模型在"失忆"状态下工作 → 质量下降 + 快速结束
```

- **压缩策略问题**：`turns<5` 时走"全量压成纯文本"（170K→26K），丢失了对话结构和细节，只留骨架
- **压缩时机问题**：等到 160K 才压缩（被动应对），不是主动预算管理
- **无摘要注入**：18:02 压缩后无 summary 注入（12:40/13:54 有 62-197 字符 summary，18:02 没有）→ 压缩后彻底失忆

### 4.2 内部根因：深度分析流程失守（Agent 行为层）

```
早间调研：脚本驱动（research_task_runner.py）→ 步骤固定、质量门禁内建 → 14-50 turns
深度分析：无脚本、无 skill 强制 → 全凭 Agent 自觉 → 3-6 turns 草草收尾
```

- **无格式/质量门禁**：knowledge-doc-writer skill 定义了落盘规范，但深度分析没读它 → 不落盘/裸写/无 log
- **无终止谓词**：没有"分析完成 = 文档落盘 + log + commit"的 check gate → 模型在"想清楚了"就宣布完成
- **无最小工作量约束**：深度分析没有 min_turns 要求 → 3 turns 就敢说 Done

## 5. 影响评估

| 维度 | 影响 |
|:-----|:-----|
| 输出质量 | 4 个会话无落盘（内容丢失）；有落盘的也偏浅（深度靠一次 write 顶住，无迭代打磨） |
| 知识库 | 18:16-18:19 四轮分析内容当时未归档（后经"遗留事项处理"补上，但当时产出已丢失） |
| token 成本 | 上下文臃肿 → 每次调用全量付费（163K prompt 级别）→ 实际烧钱 2-4 倍于必要 |
| 用户体验 | "几轮对话就草草结束"的直接来源 = turn 数 3-6 + 输出浅 + 有时还不落盘 |

## 6. 对策建议（按优先级）

### P0：上下文预算前置管理（治本）
1. **主动压缩**：session 上下文超 100K 即触发摘要压缩（不等 160K），压缩后**必须注入 summary**（18:02 的教训：压缩无 summary = 彻底失忆）
2. **会话分割**：深度分析话题与长驻 session 隔离，或每 topic 新开 session 上下文（AI 网关 39 messages 高质量 vs 141 messages 劣化的对照）
3. **消息裁剪**：早轮历史（超 N turns）定期折叠为摘要，而非保留全文

### P0：深度分析流程制度化（治本）
4. **深度分析必须走 knowledge-doc-writer skill**：读 SKILL.md → 按格式门禁 → 落盘 + log + commit（当前 0 调用，等于裸奔）
5. **最小工作量约束**：深度分析 ≥ 8 turns 或 ≥ 3 次工具调用（检索+读+写）才允许 Done；未落盘 = 未完成
6. **check gate**：Done 前检查"文档已 write + log 已追加 + commit 已提交"，任一缺失 → 继续

### P1：成本与质量护栏
7. **上下文预算显示**：每次调用前评估 prompt 规模，超阈值提示"本会话上下文已臃肿"
8. **质量抽样**：对 write=1 次的"一次成型"文档做二次复核（独立上下文验证）
