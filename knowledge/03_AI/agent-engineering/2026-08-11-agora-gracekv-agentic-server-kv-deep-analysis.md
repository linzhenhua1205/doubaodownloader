## 1. 一句话结论

**Agentic AI 把"服务器利用率"从 GPU 问题变成 CPU-GPU 联合问题，把"KV 管理"从局部规则变成全局分配**：Agora 用首个 hyperscaler 生产数据证明——Agentic 负载下 CPU 中位利用率仅 6-31%、GPU SM 活跃度 <55%，**碎片化执行搁置了 0.74 个服务器等效吞吐**（CPU 收割）+ **1/3 GPU 可释放**（GPU 收割），代价仅 agent 减速 <4%；GraceKV 用全局预算竞争证明——KV 压缩从"层/头/槽的局部配额"走向"同一竞争空间的全局分配"，32 设置中 24 个第一、128× 压缩仍鲁棒。**两者共享同一第一性原理：碎片化/局部化必然搁置资源，全局分配才是约束下的最优解**。

## 3. Agora 全文深读：生产架构刻画

### 3.1 研究设计：fleet 研究 + 受控研究双透镜

| 透镜 | 内容 | 目的 |
|:-----|:-----|:-----|
| **生产研究** | Azure fleet 24 小时 trace：agentic 请求时间/工具活动/CPU 指标**按软件角色归因**（scheduler/orchestrator/runner） | 规模化证据（首个） |
| **受控研究** | 4 开源框架：SWE-Agent（单 agent 顺序工具密集）/ Trae（顺序长工具链 3 模型端点）/ CORAL（4 agent 并行同构模型进化）/ Owl（异构：协调者+6 文本角色+视觉语音） | 隔离根因 + 可复现 |

**硬件**：96 核 AMD EPYC 7V12 + 8× NVIDIA A100；每角色一个 vLLM 实例；并发 1-32 任务。

### 3.2 三轴分类法（平台相关维度）

| 维度 | 选项 | 平台含义 |
|:-----|:-----|:---------|
| **Orchestration**（谁决定下一步） | Host-orchestrated（MetaGPT/MAGE）vs LLM-orchestrated（OWL/AOrchestra） | 主机控制流可见 → 可预调度/预取；LLM 编排把推理放进控制路径 → 推理需求增、可预测性降 |
| **Execution structure**（步骤时间排列） | Sequential（AlphaEvolve/Trae）vs Parallel（ReConcile/CORAL/DeLM） | 顺序=单节点活跃、延迟直接延伸关键路径；并行=并发推理+工具突发、批处理机会 |
| **Model composition**（模型族） | Homogeneous vs Heterogeneous（ToolOrchestra/AccelOpt） | 同构=共享驻留+跨 agent 批处理；异构=多模型驻留、内存压力、批处理碎片化 |

> **辨析**：分类法不是静态标签——工作流可组合/跨阶段移动。分类法捕获的是**决定服务器需求的支配行为**。这与知识库"任务形状决定范式"（窄深→单循环/宽浅→多代理）在**更高层**同构：任务形状 → 范式选择（知识库），范式 → 资源需求（Agora 分类法），两篇拼出完整因果链。

### 3.3 核心发现一：Agentic 执行是碎片化 + 异构的

**生产请求生命周期**（图 2）：单一请求跨越近 1 分钟，交替多个 LLM 调用 + agent 交接 + 3 次工具发现 + 3 次工具执行（2 种工具）。**每次 LLM 调用后主机编排解释输出推进工作流，每个工具结果必须合并进工作流状态后 agent 才能继续** → 请求反复跨越 CPU-GPU 边界，**CPU 进入关键路径**（不再是加速器的单纯前端）。

**CORAL 受控验证**（图 3）：单次运行展开为 **580 次 LLM 调用 × 552 次异构工具调用**（毫秒级文件操作到多秒编译/评估）——执行在 GPU 推理与 CPU 工具工作间**乒乓数百次**。

**Fleet 证据**（图 4）：工具执行时间重尾分布，**>27% 请求的工具时间 ≥ 推理时间**；分布极宽 → **不存在单一 CPU-GPU 时间比能刻画该工作负载**。

### 3.4 核心发现二：执行结构创造突发负载

- **Trae**（图 5）：顺序执行阶段 CPU 中位 **11%**，但推理阶段边界**多个构建/测试并行 → CPU 冲到 ~100%**
- **Owl**：只激活部分角色 → scheduler 需求低但随角色启停波动
- **CORAL**：4 agent 并行 → scheduler 需求持续高
- **Trae**：阶段式 → 工具需求在安静间隔与近饱和突发间交替（图 6）

> **静态供给悖论**：按峰值供给 → 突发间容量浪费；按均值供给 → 突发时无余量。Agentic 负载**搁置容量**（stranded capacity）：CPU/GPU 均值都低，但任一方都可能成为关键路径上的瞬时瓶颈。

### 3.5 核心发现三：模型组合制造 GPU 失衡

**Owl 高并发**（图 7）：8 个 GPU 功耗差异巨大——4 个最忙文本/视觉角色 GPU **反复逼近峰值功耗**，其余 GPU **大部分时间 ~20% 空闲**。静态角色→GPU 映射下，轻载设备保留大量未用容量。

### 3.6 核心发现四：任务/工具多样性放大异构性

- **同一框架不同任务**（图 8）：CORAL 研究类任务 CPU 99%/GPU 44%，算法类任务 CPU 31%/GPU 55%——**同一框架可压向相反资源**
- **工具类别**（图 11）：代码执行最大类 → DevOps/搜索检索/数据库/通信服务各有不同资源签名
- **每请求工具调用数**（图 12）：平均多、P99 远重、类别间行为迥异

### 3.7 三大架构错配（常规统一服务器失效模式）

| # | 错配 | 机制 | 证据 |
|:-:|:-----|:-----|:-----|
| 1 | **碎片化搁置容量** | CPU/GPU 需求交替 → 平均闲置、瞬时瓶颈 | CPU 中位 6-31%（Owl-CORAL）、GPU SM <55%、GPU 功耗 50-70% |
| 2 | **同质供给低效** | 三角色资源签名不同，单一同质核池无法匹配 | 角色级 CPU/网络/磁盘需求正交（图 9）；runner 突发 vs 控制面稳定 |
| 3 | **共享核微架构局部性损失** | 多 agent 复用共享核 → cache 行/分支预测互相驱逐 | PMU：IPC 1.2-1.6、L1-data MPKI 14-20、后端 stall 43-47%（图 10/14） |

**协调开销限制扩展**（图 15）：并发 1→32 时 SWE-Agent 非自愿上下文切换 **71→660/s**——**即使聚合 CPU 利用率低**，系统协调成本随 agent 数超线性增长，通用 OS 调度在高 agent 并发下不足。

## 4. Agora 三机制深潜与量化

### 4.1 机制一：CPU 收割（Harvesting Idle CPU Cores）

**目标**：最大化每服务器吞吐，同时保护 agentic 尾延迟。

**三工作机制**（图 16）：
1. **角色隔离**：harvester 只共享 runner 核，**永不触碰** scheduler/orchestrator 核（最直接影响 agent 延迟的部分）
2. **自适应撤退**：检测到工具突发 → 宽限窗口（grace window）内结束则 harvester 不变；持续则**逐步节流→暂停**；结束后恢复窗口再恢复（合并邻近工具调用为一次调整）
3. **编排器提示**：host-orchestrated 工作流下编排器**提前警告**突发（关闭反应式控制器的滞后窗口）；工具类型提示——计算型工具→减 harvester 配额，I/O 型（等待外部服务）→继续收割

**量化结果**（表 II）：

| 框架 | 低载 Harvest/Slow | 高载 Harvest/Slow |
|:-----|:-----------------:|:-----------------:|
| SWE-Agent | 101.5% / 2.5% | 63.6% / 1.2% |
| Trae | 100.1% / 1.4% | 73.3% / 4.3% |
| CORAL | 94.7% / 1.0% | **1.0% / 9.9%** |
| Owl | 83.6% / 6.2% | 76.9% / 0.2% |
| **平均** | **95.0% / 2.8%** | **53.7% / 3.9%** |

- 双点平均 = **0.74 server-equivalents** 额外吞吐恢复；主机 CPU 利用率 +31%，agent 延迟仅 +3.3%
- **策略权衡**（图 17）：永不撤退=吞吐最多但减速最大；总是暂停=减速最小但吞吐最少；**渐进宽限撤退**=兼顾（高载用渐进、低载用不撤退）
- **边界案例**：CORAL 高载（并行工具饱和）≈ 无闲置可收割 → 禁用收割；Owl（工具多等网络）被"全工具撤退"过度保护 → **无类型提示时仅保留 37.7% 独立吞吐，有提示时 80%（agent 减速 0.2%）**

### 4.2 机制二：GPU 收割（Harvesting Idle GPU Capacity）

**两步**：先**整合**（co-locate 多 agent 到共享 serving instance 提高每 GPU 利用）→ 再**收割**（减少 GPU 数，释放回共享池）。

**显存超订**：GPU 分配超过可同时驻留的 agent 状态；活跃 agent 常驻、其余暂存主机内存；**host-orchestrated 时编排器知道下一个 agent → 预取状态**（与当前 agent 工作重叠，隐藏 swap 延迟）。

**分类法引导共置**：共享大量状态（模型权重/缓存前缀）的 agent 高效共置（共享部分只驻留一次）；不同时活跃的 agent 可共置（顺序工作流保证）；**重载 agent 配轻载 agent**（互补而非竞争）。

**分配求解**：MILP（混合整数线性规划）基于 profiling 数据动态重算——每 agent 的 GPU 数 + 张量并行配置 + 共置选择。

**量化结果**（表 III，相对角色专属部署）：

| 工作流 | 操作 | GPU 减少 | 吞吐 | 任务/时 | 尾延迟 | 能效 | KV 命中 |
|:-------|:-----|:-------:|:----:|:-----:|:------:|:----:|:-------:|
| Owl | 整合 | – | +106% | +36% | 3.8× 改善 | +42% | +68% |
| Owl | 收割 | **33%** | +82% | +22% | 2.5× 改善 | +51% | +75% |
| CORAL | 整合 | – | +15% | +28% | 5.3× 改善 | +20% | +8% |
| CORAL | 收割 | 50% | **−71%** | −55% | 16× 恶化 | −53% | −17% |

- **Owl 收割安全（静态选择也成立）**；CORAL 收割**反噬**（并行工作流无闲置 → 收割亏损超过释放比例）→ **不应收割，只整合**（固定 GPU 预算下整合 +15% 吞吐、5.3× 尾延迟）
- **整合为何提升吞吐**：共置 agent 共享单份模型权重 → 消除角色专属部署的重复权重拷贝 → 释放内存给更大 KV 缓存 + 跨 agent 前缀复用 → **KV 命中率 +68-75%**
- **张量并行权衡**：TP8 不优于角色专属（同步-通信权衡），两个 TP4 实例反而更好

### 4.3 机制三：角色感知核池化与钉扎（Role-Aware Pooling + Pinning）

**问题**：scheduler/orchestrator（延迟关键）与 runner（突发）共享同质核池——按突发配池则空闲浪费、按常例配池则突发抢核。

**Agora 方案**：
- **角色独立池**：scheduler/orchestrator 各占小专用池（延迟关键但低稳需求）；**scheduler 面实测仅 10.3 核**、11 核池已保留 98.5% 独立吞吐（16+ 核几乎无增益）→ 池尺寸"略高于实测需求"
- **runner 池压缩**（表 IV）：工具 CPU 秒数 -25 至 -46%，serving CPU 变化 <2%，批量完成变化 <1%——**压缩把散落工具核变成干净可收割容量**
- **按任务钉扎**（表 V）：每任务（一次 assignment 的整个工具序列：编辑文件→shell→测试）钉到窄核集——**2 tasks/pool 最优：尾延迟工具时间 -12.8%、工具 CPU 秒数 -34%、批量完成 -4.7%**；完全私有核反而更差（去除吸收自身突发的松弛）；按工具类型钉扎无益（静态工具分区无法跟踪动态工具混合）

### 4.4 未来硬件三方向（V-C）

1. **调度/上下文切换硬件卸载**：专用引擎把 agent 调度+上下文切换移出 OS（硬件队列持有 agent 与状态）→ 并发变吞吐
2. **微架构结构硬件分区**：way-partitioned/agent-tagged 缓存、TLB、分支预测 → 比软件亲和性更细粒度的隔离
3. **异构/可变形核**：能效核做协调 + 高性能核做工具执行；可变形核（morphable）跟踪动态角色混合

## 5. GraceKV 全文增量与互证

### 5.1 现有分析覆盖（已归档，不重复）

方法（预算定义/曲率槽分割/原型树/值流/预算流）、数据推导、实验（24/32 第一、96.5% 保留、KV -50%）、8 项局限——见 [KV 压缩范式转移](../llm-techniques-principles/2026-08-11-kv-compression-global-allocation-gracekv-aoh-deep-analysis.md)。

### 5.2 本文增量：原文 Limitations 细节

> 原文 Limitations 段：**实现全局最优分配需搜索指数空间，难以满足在线推理的延迟要求** → GraceKV 采用全局贪心 + singleton floor 缓解非平滑增益低估，**但组合优化意义上仍无法保证全局最优**。另外**原型树构建引入一次性延迟与峰值内存开销**，可进一步通过底层/硬件特定优化降低。

**辨析**：这暴露 GraceKV 的核心张力——**"全局"与"在线"的矛盾**。全局分配的优势（跨层/头/槽流动）与贪心近似（延迟可接受）是**有意的工程妥协**，但：
- 一次性开销（原型树构建）在**长上下文在线推理**中如何摊销未量化（预填充阶段构建 vs decode 阶段使用）
- "无法保证全局最优"意味着**与 Agora 的 MILP 精确求解形成对比**——Agora 的 GPU 分配用 MILP（规模小可精确），GraceKV 用贪心（KV 原子单元规模大不可精确）——**分配问题的求解复杂度决定近似策略**，这是两篇的又一共性维度

### 5.3 与 Agora 的 KV 互证

**Agora GPU 收割的 KV 命中 +68-75%**（共享权重 + 前缀复用）与 GraceKV 的"全局分配释放内存给更高价值 KV"是**同一经济学的两端**：
- Agora：服务器侧消除重复权重 → 更多 KV 容量 → 命中率↑
- GraceKV：缓存侧全局分配 → 更高信息密度 → 相同容量下质量↑

**合流判断**：KV 优化的完整杠杆 = **容量供给（Agora 式整合/收割）+ 容量利用（GraceKV 式全局分配）**——知识库"KV 四层命运"框架的实践补充。

| **微架构级证据** | PMU 测量（IPC/MPKI/管道 stall）在生产节点上证明微架构低效——此前仅聚合利用率报告 |
| **工具类别分布** | 代码执行最大类 + DevOps/搜索/数据库/通信的类别资源签名（图 11/12）——数据中心规划的直接输入 |

### 6.2 稀缺性的边界（批判）

1. **单一 hyperscaler 单一 24h 窗口**：Azure 的负载 = 特定产品组合，24h 不覆盖周/月周期；跨 CSP 的通用性未验证
2. **受控研究仅 4 框架**：覆盖分类法代表性点但非穷尽；OWL/CORAL 的选择偏向论文作者的框架
3. **硬件单一**：96 核 EPYC + A100——AMD CPU + NVIDIA GPU 组合；Intel CPU/其他加速器（TPU/国产）下结论可能漂移
4. **A100 为上一代**：H100/B200 的 GPU 利用率/功耗特征不同（显存更大 → 超订空间更大，但 HBM 带宽/功耗密度变化）
5. **无成本模型**：收割的吞吐恢复 vs 共置工作负载的 QoS 牺牲未给经济模型——"0.74 server-equivalent"是技术收益，非 ROI

### 6.3 稀缺数据的引用规范

引用 Agora 生产数据（CPU 6-31%/GPU SM <55%/27% 工具≥推理/0.74 server-equiv/1/3 GPU 释放）时须带条件标注：**Azure 特定负载 + 2026-08 + EPYC/A100 平台**，不可泛化为"Agentic 负载普遍如此"。

## 7. 两篇的共性：全局分配的第一性原理

**第一性原理**：约束下的资源分配，局部/静态决策必然搁置资源。

| 维度 | Agora（服务器侧） | GraceKV（缓存侧） |
|:-----|:------------------|:------------------|
| 问题 | 碎片化执行搁置 CPU/GPU | 局部配额搁置高价值 KV |
| 失效 | 静态供给 vs 突发需求 | 预定义规则 vs 任务需求差异 |
| 全局解 | 收割 + 整合 + 角色池化 | 预算竞争 + 原型树 |
| 求解 | MILP（GPU，规模小→精确） | 贪心 + floor（KV，规模大→近似） |
| 自适应 | 分类法 + 负载引导 | 任务/预算引导 |

**统一洞察**：两篇都是"从局部/静态走向全局/自适应"的范式转移实例——Agora 在**空间**（服务器资源）上做全局分配，GraceKV 在**语义**（KV 信息价值）上做全局分配。**分类法（Agora）与槽分割（GraceKV）都是"把异构性结构化为可分配单元"的同一动作**。

## 8. 数据推导

### 8.1 收割的净收益模型

设服务器 CPU 总核数 C，agentic 负载 CPU 中位利用率 u（6-31%），峰值利用率 p（~100%）：

- 静态供给容量需求 = C·p（按峰值）
- 实际有效利用 = C·u
- 搁置容量 = C·(p−u)
- Agora 收割收益 = 0.74 server-equivalents（双点平均）= 收割吞吐/独立吞吐的平均
- 验证: (95% + 53.7%) / 2 = 74.35% ≈ 0.74 ✅

**第一性解读**：0.74 server-equivalent 不是"多出 74% 容量"，而是**把碎片化的时间空隙聚合成可用的连续吞吐**——与内存碎片整理同构（外部碎片 → 紧凑化 → 可用连续块）。

### 8.2 GPU 收割的盈亏边界（分类法决定）

- 收割收益 ∝ 时间上不重叠的闲置 GPU 比例（顺序/异构工作流）
- 收割亏损 ∝ 并行工作流中被移除 GPU 的活跃占比（并行/同构工作流）
- Owl（顺序激活，异构）：闲置 1/3 GPU → 收割 +82% 吞吐 ✅
- CORAL（4 agent 并行）：无闲置 → 收割 −71% 吞吐 ❌
- **决策规则**：若（闲置 GPU 时间占比）>（移除 GPU 的活跃占比）则收割，否则只整合

### 8.3 协调成本超线性增长

- SWE-Agent: 并发 1→32，上下文切换 71→660/s（9.3×），CPU 利用率仍低
- 协调成本 ≈ O(C^α)，α>1（agent 间调度/消息/状态管理随并发超线性）
- 通用 OS 调度在高 agent 并发下成为瓶颈（Agora 未来硬件方向 1 的动机）

### 8.4 KV 双杠杆合流

- KV 容量供给（Agora 整合）：权重共享 → 重复拷贝消除 → KV 缓存增大 → 命中 +68-75%
- KV 容量利用（GraceKV 分配）：全局预算 → 信息密度↑ → 128× 压缩仍鲁棒
- 综合：供给 × 利用 = 每 GB KV 内存的有效信息量最大化

## 9. 批判性审视

1. **Agora 无开源**：原型机制描述充分但无代码/复现包——"Agora improves utilization"的**可复现性受限**（对比 GraceKV 有详细方法说明）
2. **收割的 QoS 边界**：harvester（DCPerf）是合成负载，真实混合工作负载的 QoS 交互未验证
3. **MILP 的动态开销**：GPU 分配 MILP 在运行中重算——求解时延未报告，大集群（数十 GPU）下可能成为新瓶颈
4. **A100 时代数据**：显存超订/预取在 HBM 容量更大的 B200 下收益可能缩小（超订空间随显存增大）
5. **GraceKV 贪心 vs 最优的差距**：未量化贪心解与全局最优解的 gap——"24/32 第一"是相对基线，非相对最优
6. **GraceKV 一次性开销**：原型树构建的峰值内存/延迟未给绝对数值（相对 token 数？）
7. **两篇均无端到端协同**：Agora 的 KV 命中提升是"副产品"，GraceKV 的全局分配未嵌入 Agora 式收割——**两者合流是开放机会**
8. **生产数据的时效**：Agentic 框架/工具生态月级演进，2026-08 的负载结构 6 个月后可能显著不同

## 10. 本系统启示

1. **服务器选型决策框架**：Agora 的三角色模型（scheduler/orchestrator/runner）+ 分类法三轴是评估"Agentic 服务器"宣传的**检验清单**——厂商"agentic CPU"若无角色级/微架构级数据支撑，应视为营销（对照 Arm AGI CPU/AMD Agent Computers）
2. **CPU-GPU 边界认知升级**：本系统知识库此前聚焦 GPU 利用率/KV 优化，Agora 提示**CPU 是 Agentic 负载的第二瓶颈**——超节点设计需把 host CPU 资源（角色池化/收割）纳入规划
3. **KV 双杠杆**：KV 优化 = 容量供给（Agora 式整合）+ 容量利用（GraceKV 式分配）——本系统 KV 分层存储框架（HBM→DDR→NVMe）可叠加"全局分配"维度
4. **协调成本监控**：上下文切换 71→660/s 提示自建 Agent 系统需监控**协调开销随并发增长**（本系统"假存活陷阱"的又一监测点）
5. **分类法作为负载分析工具**：Agora 三轴分类法可直接用于本系统调研任务的负载形状分析（顺序/并行/同构/异构决定资源配置）
