## 一、文章概述

作者「程序员龙叔」分享了如何设计两套用于软件测试的 AI Skill——**需求评审 Skill**（`req-review` 三件套）和 **手工用例生成 Skill**（`req-test-cases`）。核心观点：SKILL 效果的好坏很大程度上取决于知识库是否完善和精准。

---

## 二、核心架构

### 2.1 两套 Skill 的目录结构

```text
.codebuddy/skills/
+-- req-review/                         # 需求评审主 Skill
|   +-- SKILL.md                        # 工作流编排（3 步）
|   +-- references/                     # 知识库（人工维护）
|       +-- association_rules.md        # 关联规则表（起步为空）
|       +-- requirement_types.md        # 需求类型识别表（起步为空）
|       +-- review_checklist_common.md  # 通用审查 checklist（核心）
|       +-- review_checklist_by_type/   # 按类型的专项 checklist（待启用）
+-- req-review-associator/SKILL.md      # 子 Skill：找关联模块 + 受影响用例
+-- req-review-challenger/SKILL.md      # 子 Skill：按 checklist 挑战 + 写报告
+-- req-test-cases/                     # 手工用例生成 Skill
    +-- SKILL.md                        # 两阶段工作流（测试点 -> 用例）
    +-- references/
        +-- feature_impact_rules.md     # 产品特性关联规则（业务规则）
```

### 2.2 工作流链路

```text
新需求 --> req-review --> <slug>-review.md (评审报告)
                |
                v
       req-test-cases --> <slug>-test-cases.md (手工用例)
```

### 2.3 主从编排模式

`req-review` 拆分为一主两子，每个单一职责：

- **req-review（主）**: 编排 + 输入理解 + 最终确认
- **req-review-associator（子）**: 只负责"找关联"（返回 md 片段，不落盘）
- **req-review-challenger（子）**: 只负责"按 checklist 挑战 + 写报告"

设计原则：单 Agent + 多 Skill 结构（比多 Agent 更省 Token）。

## 三、三个重点

### 重点一：知识库如何构建

测试 Skill 使用的知识有三个来源，缺一不可：

| 来源 | 位置 | 谁维护 | 是否重点 |
|:-----|:-----|:-------|:---------|
| ① 需求文档 | `产品需求文档/`、`docs/req-review/*-review.md` | PM 产出 + Skill 沉淀 | ✅ |
| ② 人工维护规则 | `.codebuddy/skills/*/references/*.md` | 测试人员手写 | ✅ |
| ③ 自动化用例代码 | `cases/**/*.py` | 测试人员/Skill 产出 | 辅助 |

**核心理念**: Everything in Git——知识库和测试代码一起放进 git 工程，让"知识演进"和"版本演进"绑定。

#### 来源 1：需求文档沉淀

- **关键设计**: 按模块分类切片，不堆进一个大文件
- **原因**: 渐进式披露——海量信息一次性塞给 Agent 会撑爆上下文
- **Skill 如何使用**: `req-review-associator` 用 `codebase_search` 在 `产品需求文档/` 下做语义召回，失效时降级用 `search_content` 文本召回

#### 来源 2：人工维护的规则文档

规则分为**两种，必须分开维护**：

**(A) 通用规则**——与具体业务无关的测试方法论

放在 `review_checklist_common.md`，每条规则统一结构：

```markdown
### CHK-BD-001 字符串字段的长度边界
- 类别: boundary
- 默认严重度: blocker
- 适用范围: 任何用户输入的字符串字段
- 检查问题: [结构化列表]
- 命中条件: 需求中提到"输入/名称/描述"等字段但未给出长度范围
- 建议追问: [标准追问模板]
```

设计要点：

- 每条规则结构统一（id / 类别 / 严重度 / 适用范围 / 检查问题 / 命中条件 / 建议追问），Agent 才能稳定解析
- 唯一 id（CHK-XX-NNN），便于报告追溯
- **改规则不改代码**：调整审查行为只需编辑 md，SKILL.md 不动——知识与流程解耦

**(B) 业务规则**——绑定具体产品的"踩坑经验"

放在 `feature_impact_rules.md`，编码业务专家才知道的隐式依赖：

| rule_id | trigger_module | trigger_action | must_test_features | reason |
|:--------|:---------------|:---------------|:-------------------|:-------|
| FR002 | 模型广场 | 新增支持深度思考的模型 | 标准模式-深度思考功能, 多Agent模式-深度思考功能 | 深度思考绑定模型能力 |
| FR001 | 模型广场 | 新增模型 | 标准模式-模型切换, 多Agent模式-模型切换, ... | 模型是所有应用模式的消费上游 |
| FR007 | 平台端用户权限 | 新增角色/调整权限点 | 应用导出-权限校验, 空间管理-权限校验 | 权限变更需在所有受保护入口回归 |

**为什么通用规则和业务规则要分开放？**

| 维度 | 通用规则 | 业务规则 |
|:-----|:---------|:---------|
| 内容 | 测试方法论（边界、异常、并发…） | 产品特定的依赖/踩坑 |
| 是否随产品变 | 基本不变 | 产品迭代就要更新 |
| 加载时机 | 永远加载 | 按命中加载 |
| 例子 | 字符串长度校验 | 新增模型→验证深度思考 |

#### 知识库的"分层披露"

规则一多就不能全量塞入上下文：

- **第一层（SKILL.md）**: 基本工作流 + 通用规则索引，触发即加载
- **第二层（按需 references）**: `req-review-challenger` 先读 `requirement_types.md` 判断需求类型，只加载命中类型的专项 checklist
- **第三层（用例库语义搜索）**: `req-test-cases` Phase 2 用 `codebase_search` 在 `cases/` 下搜索，读 Top 3 用例学步骤粒度和断言习惯

### 重点二：Skill 是自学习的（知识回流闭环）

**核心理念**: Skill 每跑一次，都在给知识库添砖加瓦。

```text
                    +--------------------------------------+
                    |           知识库（git 工程内）          |
                    |                                        |
                    |  需求文档     人工规则     历史用例      |
                    | 产品需求文档/ references/*.md cases/    |
                    +----^----------^----------^-------------+
                         | 沉淀      | 人工      | 沉淀
                         | 评审报告   | 提炼规则  | 新用例
                    +----+----+ +---+----+ +---+------+
                    |req-review| |<slug>- | |req-test- |
                    |(评审通过)| |review  | |cases     |
                    +---------+ |.md     | +----------+
                                +--------+
                                    | 作为下次输入
                                    v
                            <slug>-test-cases.md
```

**一句话**: 生成的需求文档和测试用例文档，都会归档到知识库，供后续需求复用。

### 重点三：工作流设计模式

#### 模式一：主从编排（单一职责拆分）

- 每个子 Skill 单一职责，上下文干净、可独立演进、可被复用

#### 模式二：人工卡点（Human Checkpoint）

`req-test-cases` 的两阶段工作流在中间设人工确认点：

```text
Phase 1: 生成测试点清单 --> 写入 <slug>-test-cases.md（status: 测试点待确认）
              |                  --> 在对话中展示，等用户确认/增删
              |
          【人工卡点】 <- 用户说"确认，生成用例" / "删掉 TP09"
              |
Phase 2: 展开手工用例 --> 覆写文件（status: 已生成）
```

**设计智慧**: 测试点是廉价的、用例是昂贵的。让用户在便宜的阶段（测试点清单）就介入调整，避免在昂贵的阶段（几十条详细用例）才发现方向错了。这是"早反馈、低成本纠偏"的典型实践。

文件里的 `status` 字段还支持**中断续跑**：用户说"继续生成用例"时，Skill 读 status 决定从哪一步恢复。

## 四、关键精彩片段

### 需求评审实战案例

以"产品增加了连接器功能"这一句话需求为例，Skill 自动分析出 6 个阻塞问题和多个信息缺失，包括：

- B1. 连接器与已有 MCP 插件的关系未定义（引用已有产品文档和用例代码）
- B2. 服务名称长度和字符集未明确
- B3. 描述字段长度和格式未明确
- I4. 审计日志格式扩展（引用已有审计日志测试用例）
- I5. 计费/用量统计口径（引用资源看板文档）
- I6. 工作流插件节点是否支持引用连接器（引用插件节点文档）

**核心洞察**: 即便需求里没写审计、计费、工作流，模型从知识库中分析出了关联性。

### 生成的用例模板

用例按 P0/P1/P2 优先级分层，包含完整的前置条件、测试步骤、预期结果，并关联已有用例代码。待澄清项（如工作流引用、鉴权方式）明确标注 status 为"待PM澄清"。

## 五、设计原则总结

1. **Everything in Git** —— 知识演进与版本演进绑定
2. **分层披露** —— 海量知识按需加载，不撑爆上下文
3. **知识与流程解耦** —— 改规则不改 SKILL.md
4. **早反馈、低成本纠偏** —— 人工卡点放在测试点阶段而非用例阶段
5. **自学习闭环** —— 每次输出都回流知识库，越用越厚
6. **主从编排** —— 单一职责拆分，上下文干净
