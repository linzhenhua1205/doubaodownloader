## 核心命题

> **把判断留给 Skill、把鉴权与执行收敛到 CLI，经验才会从文档沉淀成稳定交付链路。**

Agent 擅长判断和组织，不擅长长期背着一堆执行细节往前跑。经验沉淀的障碍不在于"知识没写下来"，而在于流程没有被收敛成**可执行边界**。

---

## 为什么经验沉淀只剩文档

| 问题 | 本质 |
|:-----|:------|
| 判断和执行混在一起 | 分不清哪些可自动化、哪些需确认 |
| 关键细节散在脚本/聊天记录中 | 换台机器就跑不动 |
| 失败只有一句报错 | 不知道卡在鉴权、参数、网络还是权限 |
| 只能单人单 Agent 用 | 无法成为团队共用入口 |

> 只写"先做 A，再做 B"远远不够——真正稳定的是输入、输出、失败方式和恢复动作。

## 核心架构：三层职责分离

```text
用户意图 ----> Skill 编排层 ----> CLI 执行层
  |                |                  |
  |    触发判断     |     鉴权        |
  |    上下文读取   |     参数校验    |
  |    前置检查     |     网络请求    |
  |    异常分流     |     文件处理    |
  |    交付规范     |     结构化输出  |
```

| 层 | 职责 | 反面 |
|:---|:-----|:------|
| **用户** | 描述目标，不负责拆命令 | — |
| **Skill** | 触发判断、上下文读取、前置检查、异常分流、交付规范 | Skill 里塞满执行细节 |
| **CLI** | 鉴权、参数校验、网络请求、文件处理、结构化输出 | CLI 只做薄薄一层命令包装 |

## 面向 Agent 的 CLI 设计要点

### 1️⃣ 参数设计 — 不让模型猜

能明确成 `--doc`、`--position`、`--anchor`、`--format json` 的，别塞进自由文本。

### 2️⃣ 输出设计 — 结构化是底线

Agent 需要可解析的反馈，包含：

- 当前状态 / 阶段名 / 任务 ID
- 产物路径或目标链接
- 出错位置 + **下一步建议**
- 长任务支持持续查询状态

### 3️⃣ 安全设计 — 别只靠提示词拦

删除、覆盖、批量写入、发布上线等操作，CLI 本身要有：

- **预检**（dry-run）
- **确认机制**（必要时强制人工确认）

> 这不是保守，而是给自动化留刹车。

## 失败路径设计：先画失败再画成功

```text
请求执行
  |
  +-- ✅ 参数校验通过 -> 执行中 -> 成功
  |
  +-- ❌ 失败
        |
        +-- ⚠️ 鉴权失败 -> 提示重新登录/更新凭证
        +-- ⚠️ 参数错误 -> 明确哪个参数、什么格式
        +-- ⚠️ 网络超时 -> 自动重试（有上限）
        +-- ⚠️ 资源不存在 -> 停止，返回空结果
        +-- ⚠️ 权限不足 -> 提示需申请权限
```

| 职责 | 要求 |
|:-----|:------|
| **CLI** | 明确告诉上层失败发生在哪个阶段 |
| **CLI** | 给出可恢复动作，而不是只丢一句模糊错误 |
| **Skill** | 决定何时自动重试、何时该问用户 |
| **Skill** | 批量操作时显式设置停止条件 |

## Skill + scripts vs CLI + Skill 对比

| 维度 | Skill + scripts | CLI + Skill |
|:-----|:----------------|:------------|
| 适用阶段 | 早期验证、低频任务、个人提效 | 团队复用、跨系统接入、高频稳定流程 |
| 执行入口 | 脚本路径和运行约定 | 稳定命令和明确参数 |
| 返回结果 | 临时日志、散落文件、自定义文本 | JSON/JSONL、状态、任务 ID、产物路径 |
| 测试方式 | 依赖脚本作者习惯 | 可系统测试参数/返回值/错误码 |
| 风险控制 | 靠人工记忆 | dry-run、预检、危险操作拦截 |
| 维护成本 | 容易长成脚本堆 | 初期更重，后期更稳 |

### 迁移到 CLI 的判断标准

- ✅ 步骤相对稳定，不需要每次从零判断
- ✅ 输入输出可以结构化描述
- ✅ 失败模式比较固定（权限/参数/外部系统）
- ✅ 需要频繁访问外部系统
- ✅ 同一件事希望 Agent 能做，人也直接能做

## 优先适合 CLI 化的场景

| 适合优先 | 暂缓（继续 Skill 即可） |
|:---------|:------------------------|
| 文档创建/更新/素材上传/图表插入 | 仍处探索期的流程 |
| 审批读取/任务查询/日志检索 | 严重依赖开放式判断 |
| 数据查询/报表生成/批处理导出 | 失败模式还没看清楚 |
| CI 诊断/构建结果分析/发布前检查 | 边界没稳定之前 |
| 工单流转/状态同步/通知分发 | — |

---

## 落地顺序（五步法）

1. **挑一个场景**：高频、边界清楚、失败成本可控
2. **整理成 Skill**：先明确触发条件、顺序和风险
3. **抽出 CLI**：找出真正稳定重复的部分
4. **补 CLI 能力**：结构化输出、预检、错误阶段、恢复提示
5. **Skill 调 CLI**：上下文读取 + 异常分流 + 交付标准补齐
6. **反推迭代**：用真实失败案例改进参数设计和错误模型

## 金句提炼

1. "只靠提示词，模型当然也能把活往前推，但越是涉及鉴权、分页、文件处理、长任务、失败恢复，纯自然语言越容易发散。"
2. "CLI 不是 API 外壳，而是一道明确的执行边界。"
3. "Skill 真正有价值的地方，不在于替 CLI 把命令写长一点，而在于它知道什么时候该做、做到哪一步该停、失败后应该怎么改道。"
4. "删除、覆盖、权限变更、批量写入、发布上线——不能把安全性寄托在'Agent 应该知道不能乱来'上。"
5. "经验不会只留在某个人的会话窗口里，失败也不会变成一团黑箱。人能直接用，Agent 也能稳定用，这种能力才算真的沉淀下来了。"
6. "先设计失败分叉与恢复动作，才能让 Agent 在真实链路里稳定续跑。"
