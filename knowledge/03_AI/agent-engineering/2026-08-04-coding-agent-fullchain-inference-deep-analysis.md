## §0 专题定位与视角声明

**为什么选编程场景**：编程 Agent（Claude Code/Cursor/Trae/Qoder 等）是 Agent 负载的**最典型代表**——同时具备长上下文（代码库）、高迭代循环（改-测-改）、密集工具交互（shell/编译/测试）、并行 subagent、check 验证闭环五大特征。它的行为模式就是推理基础设施的"压力测试负载"。

**与既有文档的关系**（三角互补，本文为第三角）：

| 文档 | 视角 | 回答的问题 |
|:-----|:-----|:-----------|
| 六层模型（静态架构） | 构成解剖 | Agent 由哪些部件组成 |
| KV Cache 物理推导 | 硬件物理 | 推理在 GPU 上怎么跑、瓶颈在哪 |
| **本文（动态时序）** | **过程流水线** | **一次任务从输入到交付，每一步碰了什么硬件、要什么硬件** |

## §1 全景：一次编程任务的推理生命周期

```text
+------------------------------------------------------------------------+
|  一次编程任务（如"修复 #42 bug 并补测试"）的推理全链路                       |
+------------------------------------------------------------------------+
|                                                                        |
|  +---------+   +---------+   +---------+   +---------+   +---------+  |
|  | 0 输入   |-->| 1 上下文 |-->| 2 拆解   |-->| 3 调度   |-->| 4 子任务  |  |
|  | 识别+规则|   | 工程    |   | 计划    |   | 执行编排 |   | 并行执行  |  |
|  +---------+   +---------+   +---------+   +---------+   +----+----+  |
|                                                                  |      |
|  +---------+   +---------+   +---------+   +---------+   +-----v----+ |
|  | 9 异常   |<--| 8 汇聚   |<--| 7 check  |<--| 6 KV    |<--| 5 执行    | |
|  | 处理    |   | 交付    |   | 纠偏    |   | Cache   |   | 沙箱     | |
|  +---------+   +---------+   +---------+   +---------+   +----------+ |
|                                                                        |
|  阶段 5->6->7->3 形成迭代循环（改-测-改），直到 check 全绿或达迭代上限        |
+------------------------------------------------------------------------+
```

**总表**（各阶段详细拆解见后文各节）：

| # | 阶段 | 主导计算类型 | 硬件访问特征 | 对硬件的核心需求 |
|:-:|:-----|:-------------|:-------------|:-----------------|
| 0 | 输入识别+规则注入 | prefill（compute-bound） | 首请求全量前向 | prefill 算力、TTFT、prefix cache 容量 |
| 1 | 上下文工程 | 检索（CPU/存储）+ prefill | 增量装载、存储 IO | 索引检索、长上下文窗口、增量命中 |
| 2 | 任务拆解与计划 | decode（memory-bound） | 长输出生成 | decode 吞吐 |
| 3 | 调度与编排 | 循环混合 | 工具回调+新一轮 prefill | 回调延迟、prefix 复用 |
| 4 | subagent 并行 | 并发推理 | N 路独立 KV cache | 并发吞吐、KV 容量线性增长 |
| 5 | 执行+沙箱 | 确定性计算（CPU） | 文件/进程/编译 | 沙箱资源、隔离、与推理解耦 |
| 6 | KV cache 交互 | 显存读写（memory-bound） | 每轮 prefix 复用 | 显存容量、HBM 带宽、命中率 |
| 7 | check 与纠偏 | 确定性+推理混合 | 测试运行+失败分析 | check 工具链、循环迭代成本 |
| 8 | 结果汇聚 | 大 prefill+长 decode | 长上下文重读 | 长序列 prefill、输出带宽 |
| 9 | 异常处理 | 混合 | 重试/恢复/压缩 | 冗余、checkpoint 存储 |

## §2 阶段0 提示词工程：输入识别与规则注入

### 2.1 主要操作

1. **请求解析**：把用户自然语言输入归一化为任务描述（意图、目标、约束、验收标准）。
2. **规则加载**：按作用域分层注入规则——`rule.md`（工作区铁律）/`AGENT.md`（人格与行为）/`USER.md`（用户偏好）/`MEMORY.md`（长期记忆）——即"四级 Prompt 分工"（既有六层模型 §2）。
3. **系统提示组装**：静态层（系统角色）+ 任务层（本次任务描述）+ 规则层（rule/记忆）+ 工具面声明（可用工具清单）。

### 2.2 数据流特征

- 系统提示是**每次请求的共享前缀**（prefix），长度稳定（几 K 到几十 K tokens）。
- 首请求 = 全量 prefill（冷启动，prefix 缓存未命中）→ 后续请求全部命中缓存。

### 2.3 硬件访问特征

- **prefill 阶段（compute-bound）**：并行处理所有输入 tokens，算术强度高，吃 GPU 算力（FLOPs），不依赖 HBM 带宽。
- TTFT（首 token 延迟）由 prefill 长度与算力决定——系统提示越长，冷启动 TTFT 越差。

### 2.4 对硬件的需求

- **prefill 算力**：冷启动 TTFT 目标（如 <2s）决定 prefill 并行度。
- **prefix cache 容量**：缓存系统提示的 KV，避免每轮重复计算（命中率是第一成本杠杆——经验：缓存未命中占推理成本 58%）。
- **规则精简是软需求**：rule 越长 → 前缀越长 → 缓存压力与 TTFT 越大（这是"裁剪 description 收益"的硬件侧解释）。

## §3 阶段1 上下文工程：获取与压缩

### 3.1 主要操作

1. **结构感知读取**：先读 `spec.md`/`README`/目录树，建立全局视图。
2. **按需检索（lazy reader）**：不一次性读入整个代码库——用语义检索/关键词检索定位相关文件，**渐进披露**（progressive disclosure）：先看结构，再按需展开具体文件。
3. **上下文压缩（compaction）**：上下文接近水位（经验 95%）时，把早期对话压缩为摘要（模型总结），腾出窗口；必要时截断低相关历史。
4. **token 预算管理**：按"当前任务相关度"分配上下文预算，代码片段 vs 分析文本的配额。

### 3.2 数据流特征

- 上下文是**增量装载**的：每读一个文件/检索结果，追加一段到上下文 → prefix 逐段增长。
- 检索本身是 CPU/存储操作（索引、文件 IO），不经过 GPU；只有"检索结果注入上下文"才触发 prefill。

### 3.3 硬件访问特征

- **存储 IO**：代码文件读取、索引查询——延迟敏感（秒级内），带宽要求低（KB~MB 级）。
- **增量 prefill**：每次注入新内容 = 对新段做 prefill，旧段命中 prefix cache（增量计算，非全量重算）。
- **压缩决策**：是"信息损失"决策（模型判断什么可压缩），压缩结果本身是一次推理。

### 3.4 对硬件的需求

- **检索基础设施**：索引存储、向量/关键词检索延迟（<100ms 量级）。
- **长上下文窗口**：窗口越大，越少压缩（少丢信息）——但显存成本线性涨。
- **prefix cache 增量命中**：增量装载模式下，缓存必须支持"前缀增长后仍命中"（增量 prefix 缓存），否则每读一个文件就全量重算。

## §4 阶段2 任务拆解与计划

### 4.1 主要操作

1. **目标分解**：把任务拆为子任务（如：定位 bug 根因 → 设计修复 → 实施修改 → 补测试 → 验证）。
2. **计划生成**：输出结构化 plan（步骤、依赖、验收条件），可能写为 plan 文件（如 `PLAN.md`）。
3. **计划回读**：后续执行阶段把 plan 作为上下文的一部分（自引用，形成"计划-执行-对照"闭环）。

### 4.2 数据流特征

- 规划是**推理密集**阶段：长 CoT（思维链）生成，输出 tokens 多（plan 文本）。
- plan 是**文本产物**，回写上下文后成为后续阶段的共享前缀一部分。

### 4.3 硬件访问特征

- **decode 阶段（memory-bound）**：逐 token 生成，算术强度低（<1 FLOP/byte 量级），**HBM 带宽决定生成速度**（ITL 下界 = 每步 KV 读取量 / HBM 带宽）。
- 规划输出长 → decode 时间长 → 用户感知"思考延迟"。

### 4.4 对硬件的需求

- **decode 吞吐**：输出 tokens/s 决定规划延迟；并发场景下 HBM 带宽竞争（多个请求同时 decode → 带宽分时）。
- **长输出稳定性**：长 plan 生成需要稳定的 decode 不中断（超时/断连管理）。

## §5 阶段3 调度与执行编排

### 5.1 主要操作

1. **执行顺序决策**：按 plan 决定下一步（模型判断"现在该做什么"）。
2. **并行决策**：判断哪些子任务可并行（spawn subagent / fan-out）。
3. **工具调用序列**：生成 tool call（读文件/跑命令/搜索），等待执行结果，再继续。
4. **循环控制**：主循环（Loop）——推理 → 行动 → 观察 → 再推理；长任务可达 **50-150 轮迭代**（既有文档锚点）。

### 5.2 数据流特征

- **工具调用往返**：模型输出 tool call → 运行时执行器（CPU 进程）执行 → 结果文本回填上下文 → **新一轮 prefill（增量）** + decode。
- 每轮往返 = 1 次"增量 prefill + decode"，prefix 全部命中缓存（只算新内容）。

### 5.3 硬件访问特征

- **回调延迟**：工具执行（读文件/shell）在 CPU/存储上完成，GPU 空闲等待 → 推理引擎的**气泡（bubble）**。
- **prefix 复用**：调度器必须支持长 prefix 命中，否则每轮全量 prefill（成本灾难）。

### 5.4 对硬件的需求

- **工具执行环境**：文件系统、进程管理、命令执行器——与推理解耦（GPU 不跑 shell）。
- **调度器延迟**：batching 时避免单个长 prefix 请求拖慢整批（chunked prefill / 抢占式调度）。
- **流式输出**：工具调用的结构化输出（JSON/XML）需要稳定的流式 decode。

## §6 阶段4 Subagent 并行执行

### 6.1 主要操作

1. **spawn child instances**：为可并行子任务创建独立子 Agent（如：并行搜索多个模块、并行分析 git 历史、并行写多文件测试）。
2. **上下文隔离**：每个 subagent 持有**独立上下文**（只装载自己需要的文件），避免主上下文膨胀。
3. **产物汇回**：subagent 输出结构化摘要/结果，写回主上下文（**只在交接点做一次摘要，防有损转述**——Graph Engineering 红线的实践形态）。

### 6.2 数据流特征

- N 个 subagent 并行 = **N 条独立 KV cache / 独立 prefix**（各有各的系统提示+任务上下文）。
- token 消耗放大：多代理范式实测 **15×**（单循环 4×）——并行省时间、烧 token。

### 6.3 硬件访问特征

- **并发推理脉冲**：subagent 同时发起请求 → GPU 并发数瞬时拉升（调度器需按显存预算排队）。
- **KV cache 容量线性增长**：N 路并行 = N 份 KV cache（共享的是模型权重，不共享 KV）。
- 每个 subagent 内部同样有"检索→计划→执行→产出"的小循环（递归结构）。

### 6.4 对硬件的需求

- **并发吞吐**：并行 decode 能力（GPU 数量 × 每卡并发 slot）。
- **显存预算管理**：并发数上限 = f(显存容量 / 每请求 KV cache 占用)——超限则排队（延迟）或 OOM（失败）。
- **优先级调度**：subagent 结果汇回主 agent 的时机需要调度器感知依赖（先完成的先回）。

## §7 阶段5 执行动作与沙箱

### 7.1 主要操作

1. **文件操作**：读/写/编辑代码文件（diff 应用、patch）。
2. **命令执行**：shell 命令、grep/rg 搜索、git 操作。
3. **编译/测试运行**：构建、跑测试套件。
4. **沙箱隔离**：动作在受控环境执行——权限受限（不能 rm 关键文件）、网络受限、资源受限（防失控）。

### 7.2 数据流特征

- 这些是**确定性计算**（非模型推理）：CPU 上执行，不碰 GPU。
- 执行结果（stdout/exit code/文件 diff）回填上下文，作为下一轮推理的观察输入。

### 7.3 硬件访问特征

- **CPU 计算**：编译/测试是计算密集（多核）；文件 IO 是延迟敏感。
- **沙箱资源隔离**：cgroup/容器限制 CPU/内存/磁盘/网络——防 Agent 失控（fork bomb、磁盘写满）。
- **与推理的时空关系**：沙箱动作与 GPU 推理**串行交替**（模型等结果，或异步预取）。

### 7.4 对硬件的需求

- **沙箱资源池**：CPU 核数、内存、临时存储（编译中间产物）、网络策略。
- **隔离性**：故障爆炸半径控制（一个任务的崩溃不影响其他任务/宿主）。
- **可观测性**：动作日志、资源用量监控（超限自动 kill）。
- **典型量化**：一次"改-编译-测"循环的编译时间直接进入迭代延迟——沙箱 CPU 速度是感知延迟的一部分。

## §8 阶段6 KV Cache 交互（贯穿全程的核心）

### 8.1 主要操作

1. **prefix 复用**：每轮迭代复用系统提示+规则+已累积上下文 的 KV（命中缓存，只计算新增部分）。
2. **增量计算**：新注入的工具结果/文件内容 → 增量 prefill → 追加 KV。
3. **缓存淘汰**：上下文超限时压缩/截断 → 被截断段的 KV 失效（不可再复用）。
4. **KV cache 感知调度**：调度器按 KV 容量分配 slot、按共享前缀聚类请求（vLLM 前缀缓存、llm-d 类 KV 感知调度）。

### 8.2 物理特征（来自 KV Cache 物理推导文档）

- **每 token KV 占用**：`2 × n_layers × n_kv_heads × head_dim × 精度字节`（2=K与V；GQA 下 n_kv_heads < n_heads 显著省钱）。
- **decode 是 memory-bound**：每步要从 HBM 读全部 KV 才能生成 1 token——算术强度 <1 FLOP/byte，**HBM 带宽决定 ITL**。
- **prefill 是 compute-bound**：并行度高，吃 FLOPs 不吃带宽。
- **长上下文 = KV 显存爆炸**：上下文 100K tokens × 每 token KV 字节数 = 单请求显存占用（可达数十 GB 量级）。

### 8.3 编程场景的 KV 特征（本专题增量）

| 特征 | 数值特征 | 硬件后果 |
|:-----|:---------|:---------|
| 多轮迭代（50-150 轮） | 每轮复用 prefix | 命中率高 → 增量计算为主 |
| 长上下文（几十~几百 K） | 上下文持续增长 | KV 显存占用持续上升，峰值在汇聚阶段 |
| 并行 subagent | N 路独立 KV | 并发 KV 容量 = N × 单路 |
| 压缩/截断 | 丢弃早期 KV | 缓存碎片化、命中率下降（损失不可逆） |

### 8.4 对硬件的需求

- **显存容量**：KV cache 是显存第一消耗（长上下文场景 > 模型权重）；容量不足 → 换入换出（性能塌方）或拒绝服务。
- **HBM 带宽**：decode 吞吐的直接上限（多路并发时带宽竞争是主瓶颈）。
- **prefix cache 命中率**：第一成本杠杆（未命中 58% 是最大成本）；需要共享前缀检测、增量缓存、缓存分代。
- **KV 分层**：显存 → 内存 → 存储 三级（G3.5 分层温存储思想）：热 KV 在显存，冷 KV 换出（牺牲命中延迟换容量）。
- **KV 压缩技术**：量化（FP8/INT4）、MLA（压缩 KV 维度）、共享块——降低每 token 字节数。

## §9 阶段7 结果 check 与纠偏

### 9.1 主要操作

1. **确定性 check**：编译通过、lint 零错误、测试全绿、diff 符合预期——这些是**代码执行验证**（非模型判断）。
2. **模型 check**：代码评审、逻辑对照、验收标准逐条核对——模型判断"改对了没有"。
3. **失败分析**：check 失败 → 模型读错误日志 → 定位原因 → 修正方案 → 再改 → 再 check（**Plan→Do→Check→Act 闭环**）。
4. **纠偏策略**：回归测试驱动（先写失败测试再修）、最小修改原则、回滚（git revert）。

### 9.2 数据流特征

- check 是**确定性计算 + 推理的混合**：测试运行走 CPU；失败分析走 GPU（新一轮推理）。
- 每次"失败→分析→修正" = 1 轮迭代 = 1 次增量 prefill + decode（prefix 复用）。

### 9.3 硬件访问特征

- **check 工具链**：编译器/测试框架吃 CPU；测试套件大 → 时间长 → 迭代延迟高。
- **失败分析的推理成本**：错误日志（长文本）注入上下文 → 上下文继续增长 → KV 显存继续涨。
- **并行 check**：多测试并行跑（CPU 多核），与 GPU 推理可重叠（异步）。

### 9.4 对硬件的需求

- **check 计算资源**：编译/测试的 CPU 核数与内存（决定迭代周期长度）。
- **循环推理预算**：迭代次数无上限会烧 token——需要上限约束（如最多 N 轮）与"已达上限"的降级路径。
- **可观测性**：每次 check 结果、耗时、资源用量的记录（审计与成本归因）。

---

## §10 阶段8 结果汇聚

### 10.1 主要操作

1. **多产物合并**：多个 subagent 的结果/多个文件修改 → 统一集成（处理文件冲突、接口一致性）。
2. **冲突消解**：并行修改同一文件的冲突解决（合并 diff、重跑相关测试）。
3. **最终交付**：总结变更、生成 commit message、输出交付报告（做了什么/为什么/验证结果）。

### 10.2 数据流特征

- 汇聚需要**重读全量上下文**（所有 subagent 产物、全部修改历史）→ 大 prefill（峰值上下文）。
- 最终报告是长 decode 输出。

### 10.3 硬件访问特征

- **峰值 KV**：汇聚阶段的上下文 = 全程最长（可能接近窗口上限）→ KV 显存峰值。
- **大 prefill + 长 decode**：一次"重读+综合" = 算力与带宽双高峰。

### 10.4 对硬件的需求

- **长序列 prefill 能力**：汇聚时的超长 prefill 需要分块处理（chunked prefill）避免单次 OOM。
- **输出带宽**：长报告生成的 decode 吞吐。
- **显存峰值预算**：设计上要预留汇聚阶段的高水位（或触发汇聚前压缩降水位）。

## §11 阶段9 异常处理

### 11.1 异常类型与处理

| 异常 | 触发 | 处理 | 硬件/资源后果 |
|:-----|:-----|:-----|:--------------|
| 工具超时 | 命令跑太久 | 超时 kill + 重试/换路径 | CPU 资源回收 |
| 工具失败 | exit≠0 | 读错误 → 修正命令重试 | 额外推理轮次 |
| 上下文溢出 | 上下文超窗口 | compaction（摘要）/截断 | KV 失效、信息损失 |
| 推理失败 | API 错误/断连 | 重试（指数退避） | 额外请求 |
| 沙箱资源超限 | CPU/内存/磁盘爆 | 自动 kill + 降级 | 资源配额管理 |
| 任务中断 | 用户打断/会话断 | checkpoint 恢复（断点续传） | 状态持久化存储 |
| 并发 OOM | subagent 超显存预算 | 排队/串行化 | 调度器降级 |

### 11.2 数据流特征

- **checkpoint**：关键节点持久化状态（上下文摘要+进度）→ 中断后可恢复，避免重跑全链路。
- **降级路径**：图/流水线设计中预置的 fallback 边（如"重试 N 次后走人工介入"）。

### 11.3 硬件访问特征

- 重试 = 额外推理（成本叠加）；压缩 = 信息损失（后续质量下降）。
- checkpoint 存储 = 磁盘写（低频、小数据量）。

### 11.4 对硬件的需求

- **失败冗余**：推理 API 的高可用（重试窗口）；沙箱的多副本。
- **checkpoint 存储**：低延迟持久化（支持断点续传的工程前提）。
- **资源配额与限额**：防单个任务耗尽共享资源（cgroup 限额、账户级预算）。

## §12 硬件需求汇总矩阵

| 硬件资源 | 编程 Agent 负载特征 | 关键量化锚点 | 需求优先级 |
|:---------|:--------------------|:-------------|:----------:|
| GPU 算力（prefill） | 阶段0/1/8 增量装载+汇聚重读 | TTFT 目标 <2s 量级 | P0 |
| HBM 带宽（decode） | 阶段2/3/7 生成+失败分析 | 每步 KV 读取量/BW = ITL | P0 |
| 显存容量（KV cache） | 长上下文×迭代×并发 | 每 token 2·L·H·d·bytes；并发 N 路线性增长 | **P0（第一瓶颈）** |
| prefix cache | 全程每轮复用 | 未命中=成本+58% | P0 |
| CPU/内存（沙箱） | 阶段5/7 编译·测试·工具 | 编译时间进入迭代延迟 | P1 |
| 存储 IO（检索/代码库） | 阶段1 文件读取/索引 | 延迟 <100ms 量级 | P1 |
| checkpoint 存储 | 阶段9 断点续传 | 低频小数据 | P2 |
| 网络（工具回调） | 阶段3 调度往返 | 回调延迟 = GPU 气泡 | P1 |

**编程 Agent 负载画像（一句话）**：**长上下文 + 高迭代 + 前缀复用 + 并发脉冲 + KV 显存主导**——是推理基础设施中"KV 压力最大、复用收益最高"的负载类型。

## §13 对推理基础设施的启示

1. **prefill/decode 分离架构**：编程 Agent 同时制造 compute-bound（装载/汇聚）与 memory-bound（生成）负载——异构调度（分离部署/分时复用）比统一处理更优。
2. **KV cache 分层是必选项**：显存→内存→存储 三级（G3.5 思想），编程场景的峰值 KV 不可能全驻显存；冷热分层 + 换出策略决定容量-延迟权衡。
3. **prefix cache 命中率是第一成本杠杆**：系统提示/规则/历史上下文高度复用 → 共享前缀检测、增量缓存、缓存分代直接决定每 token 成本。
4. **沙箱与推理解耦**：确定性工作（编译/测试/文件）不占 GPU；但沙箱 CPU 速度进入用户感知延迟——"算力≠只有 GPU"。
5. **调度器必须感知 Agent 负载**：并发脉冲（subagent spawn）、长 prefix 独占（batching 拖累）、KV 容量预算（OOM 防护）——KV cache 感知调度（llm-d 类）是下一阶段焦点。
6. **编程 Agent 是压力测试负载**：任何推理基础设施用"50-150 轮迭代 + 100K 上下文 + 并行 subagent"压测，即暴露容量/命中率/调度短板——**测试矩阵应把 Agent 负载列为一等公民**。
