## §一 问题：AI数据获取的「三层围墙」

### 1.1 现象的观察

在涉及资本市场分析、财务数据、行业研究报告等数据密集型任务时，AI工具频繁遭遇数据获取失败：

| 失败模式 | 典型错误 | 受影响的数据类型 |
|:---------|:---------|:-----------------|
| **HTTP 403 Forbidden** | 被服务器明确拒绝访问 | 财经网站（Yahoo Finance、Reuters、MarketWatch、Investing.com） |
| **HTTP 404/410 Gone** | URL已变更或不存在 | 深度链接、旧版财经页面 |
| **HTTP 429 Too Many Requests** | 被限速后封锁 | API接口、频繁访问的资讯源 |
| **连接超时/拒绝** | 服务器不响应 | 专业金融数据源（Bloomberg Terminal等） |
| **付费墙** | 需要付费阅读 | 行业报告（IDC/Gartner/Counterpoint）、新闻深度分析 |
| **重定向循环** | 无限跳转 | 部分资讯聚合站 |
| **非公开地址** | 解析到内网地址 | CDN防护下的网站 |
| **动态渲染内容** | JavaScript加载的数据 | 交互式图表、实时行情 |

### 1.2 根本原因分析

这不是AI「不够聪明」的问题，而是**技术基础设施层的结构性约束**：

```text
+---------------------------------------------+
|  第三层: 法律/商业模式层                      |
|  付费墙·订阅制·数据授权·版权保护              |
+---------------------------------------------+
|  第二层: 技术防护层                          |
|  WAF·CDN·反爬·CAPTCHA·IP封锁·User-Agent检测 |
+---------------------------------------------+
|  第一层: 协议/渲染层                         |
|  JavaScript渲染·WebSocket·SPA·动态DOM       |
|  <- web_fetch (HTTP GET) 在此层工作          |
|  <- browser (完整浏览器) 可穿透第一层         |
+---------------------------------------------+
```

**关键认知**：《web_fetch 能获取的数据 = 静态HTML页面 + 无反爬的API + 公开文档》。而绝大部分高价值商业数据，都至少跨越第一层和第二层。

## §二 围墙一：反爬机制与访问封锁

### 2.1 常见的反爬封锁信号

| 信号 | 表现 | 常见于 |
|:-----|:-----|:-------|
| 403 Forbidden | 直接拒绝请求 | Yahoo Finance、Bloomberg、大多数财经网站 |
| CAPTCHA验证 | 需要人机验证 | 知乎、新浪财经、东方财富部分页面 |
| 频率限制 | 连续访问N次后被封锁 | 大多数新闻网站 |
| IP段封锁 | 基于IP段的批量拒绝 | 金融数据聚合站 |
| 浏览器指纹检测 | 检测无正常浏览器特征 | 高价值内容网站 |

### 2.2 为什么财经数据站特别难访问

| 原因 | 说明 |
|:-----|:------|
| **高商业价值** | 实时行情/财务数据是付费产品，免费页面也有严格防护 |
| **高频更新** | 数据不断变化，防爬压力大 |
| **API数据源** | 多数页面数据来自后端API，静态抓取拿不到 |
| **法律风险** | 金融数据受严格监管，倒逼技术封锁 |

## §三 围墙二：付费墙与订阅限制

### 3.1 常见的付费墙模式

| 模式 | 行为 | 示例 |
|:-----|:------|:-----|
| **硬付费墙** | 完全不让看 | IDC/Gartner完整报告、GuruFocus高级数据 |
| **计量付费墙** | 每月N篇免费 | 部分行业新闻站 |
| **注册付费墙** | 免费注册可看基础数据 | 部分数据平台 |
| **增量付费墙** | 免费看摘要，付费看详情 | 行业报告摘要 vs 全文 |

### 3.2 付费墙的关键影响

付费墙对AI数据获取的影响不仅仅是「拿不到数据」，还有更隐蔽的风险：

| 风险 | 说明 |
|:-----|:------|
| **选择性偏差** | 免费内容 ≠ 高质量内容，只依赖免费源可能形成认知偏差 |
| **样本偏差** | 付费墙后的深度分析通常是高价值信息，错过会导致分析浅层化 |
| **时效性偏差** | 免费数据通常延迟（15min+），实时数据几乎全在付费墙后 |

## §四 围墙三：动态渲染与登录墙

### 4.1 动态渲染

现代网站大量使用SPA（单页应用）架构，页面内容由JavaScript动态加载。web_fetch 只做 HTTP GET，不会执行JS，因此：

```text
用户看到的页面（已渲染）          web_fetch 拿到的内容
+----------------------+        +----------------------+
|  <h1>股价: $398.92</h1>|        |  <div id="root">     |
|  <div>市值: 2586亿</div>|        |    <!-- JS 加载中 -->  |
|  <canvas>K线图</canvas>|        |  </div>              |
+----------------------+        +----------------------+
```

### 4.2 登录墙

部分数据（如社交媒体、企业内部数据、特定平台内容）需要登录才能访问。此时需要 **browser工具** 或用户协助登录。

## §五 替代策略体系总览

### 5.1 五层替代漏斗

当一种数据获取方式失效时，按此漏斗尝试替代方案：

```text
                    +----------------------+
                    | ① 改URL/换源         | <- 最简单，尝试不同站点
                    +----------+-----------+
                               | 失败v
                    +----------v-----------+
                    | ② 用 browser 工具    | <- 完整浏览器渲染
                    +----------+-----------+
                               | 失败v
                    +----------v-----------+
                    | ③ 间接搜索/聚合引用   | <- 从其他引用源拼凑
                    +----------+-----------+
                               | 失败v
                    +----------v-----------+
                    | ④ 基于已有数据推算    | <- 用已知参数进行工程估算
                    +----------+-----------+
                               | 失败v
                    +----------v-----------+
                    | ⑤ 向用户请求数据源    | <- 告知具体需要什么+为什么
                    +----------------------+
```

### 5.2 各策略的适用条件

| 策略 | 适用条件 | 耗时 | 精度 |
|:-----|:---------|:----:|:----:|
| ① 换源 | 存在多个数据源 | 低 | 高 |
| ② Browser | 页面有公开内容但需JS渲染 | 中 | 高 |
| ③ 间接引用 | 目标数据被其他网站引用 | 中 | 中 |
| ④ 工程推算 | 有可靠的底层参数 | 高 | 低-中 |
| ⑤ 请求用户 | 以上都不行 | — | 高 |

## §八 实操流程：发现数据获取困难时的决策树

### 8.1 标准决策树

```text
遇到数据获取失败（Error/403/付费墙/超时等）
|
+-- Error 是 403 Forbidden？
|   +-- ✅ 换源到已知白名单
|   |   +-- 美股 -> finviz.com
|   |   +-- A股 -> eastmoney.com
|   |   +-- 行业 -> IDC摘要/新闻稿
|   +-- 都失败 -> 进入⑤请求用户
|
+-- Error 是 付费墙？
|   +-- 尝试换到免费摘要/新闻引用
|   +-- 尝试用 browser 工具
|   +-- 都失败 -> 明确告知用户「需要XX具体数据，可从YY源获取」
|
+-- Error 是 连接失败/超时？
|   +-- 重试1次（网络波动）
|   +-- 换其他源
|   +-- 都失败 -> 换 browser 工具
|
+-- 页面可访问但无目标数据？
|   +-- 动态JS渲染 -> 用 browser 工具
|   +-- 需要点击/交互 -> 用 browser 工具
|   +-- 数据在API中 -> 查network请求，尝试直接调API
|
+-- 以上都失败
    +-- ⑤ 向用户清晰说明：
        1. 需要什么数据
        2. 尝试了哪些源
        3. 推荐从哪里获取
        4. 用户提供后可直接使用
```

### 8.2 在回复中处理数据缺口的策略

当某些关键数据无法获取时，回复应该：

| 要做的 | 不要做的 |
|:-------|:---------|
| ✅ 明确标注「数据缺口」 | ❌ 编造数据或比率 |
| ✅ 说明尝试了哪些源 | ❌ 假装数据没问题 |
| ✅ 给出替代推算（明确标注为估算） | ❌ 用「估计」「大约」模糊处理 |
| ✅ 建议用户可从哪里获取 | ❌ 跳过不提 |

**标注规范**：

```text
> 📌 **数据说明**: 本分析中的XX数据因[原因]未能直接获取。
> 已尝试数据源: [源1->原因], [源2->原因]
> 替代方案: 基于[底层参数]的工程推算，标注为「估算值」
> 推荐用户从[具体站点/报告]获取精确值后替换
```

## §九 向用户请求帮助的策略

### 9.1 什么时候应该请求用户

```text
+-----------------------------------------+
|  数据是否对分析结论有决定性影响？        |
|  +-- 否 -> 用估算值+标注，继续分析       |
|  +-- 是 ->                              |
|         +-- 是否有替代源可用？          |
|         |   +-- 是 -> 换替代源           |
|         |   +-- 否 ->                   |
|         |         +-- 能否合理推算？    |
|         |         |   +-- 是 -> 推算+标注 |
|         |         |   +-- 否 -> 请求用户  |
|         +--                            |
+-----------------------------------------+
```

### 9.2 请求话术模板

```text
对于 [具体数据]：

目前我尝试了以下来源获取 [数据描述]：
- [源1]：失败原因（403/付费墙等）
- [源2]：失败原因
- [源3]：数据不全/延迟

如果您能提供以下任一，分析可以继续：
1. [具体数据+来源建议]
2. [替代数据+说明]
3. 或者如果您有相关数据源API/密钥，可以配置后供我使用
```

### 9.3 配置数据源的未来可能性

对于需要API密钥的数据源，可通过 `env_config` 工具配置：

```text
env_config set BOCHA_API_KEY "xxx"   # 博查搜索
env_config set BAIDU_API_KEY "xxx"     # 百度搜索/百科
env_config set LINKAI_API_KEY "xxx"    # LinkAI平台（部分插件需要）
```

## §十 认知升级：将边界转化为优势

### 10.1 信息约束认知的价值

AI数据获取的边界，本质上是一个**信息约束认知能力**的测试：

| 认知水平 | 面对数据获取失败 |
|:---------|:-----------------|
| **L1 无认知** | 尝试2次失败 → 放弃，输出残缺分析 |
| **L2 有认知** | 知道换源，尝试3-5个源 → 输出标注了数据缺口的分析 |
| **L3 系统化** | 有备选源清单+替代策略 → 能输出完整但有标注的分析 |
| **L4 策略化** | 能判断数据缺口对结论的影响程度，主动选择最合适的策略组合 |

**目标是从L2/L3逐步提升到L3/L4。**

### 10.2 记录与迭代

每次遇到新的数据获取障碍时：

1. 记录失败的模式和原因
2. 更新白名单（成功/失败）
3. 积累替代方案数据库
4. 将常见场景的替代路径固化为操作流程
