## Part 0 写在前面——与AI协作的心态准备

在学任何操作之前，先对齐一个最重要的事情：**心态**。

### 0.1 正确的心态

```text
❌ 错误心态：
   "让AI替我做"            -> 你变成审核员，技能退化
   "AI什么都能做"          -> 过度依赖，遇到AI做不了的直接卡住
   "AI生成的代码我不敢用"   -> 拒绝工具，效率落后
   "一句话就能生成整个项目" -> 期望过高，失望越大

✅ 正确心态：
   "AI是我的初级工程师"     -> 你定方向，它干活，你把关
   "AI把80分的活干了"       -> 你把80分改到95分
   "AI让我聚焦在更有价值的事" -> CRUD交给AI，你思考架构
   "和AI协作也需要练习"     -> 和任何工具一样，越用越顺手
```

**AI红心法则**：

```text
+---------------------------------------------------------+
|                    AI Red Heart Law                       |
|                                                           |
|  ❤️ 你永远保留的权利：                                     |
|      1. 做最终决策的权利 — AI的建议不等于指令               |
|      2. 说"不"的权利 — 觉得不对就不采纳                    |
|      3. 理解的权利 — 不要用你不理解的AI输出                  |
|                                                           |
|  ⚠️ 你永远不能放弃的责任：                                 |
|      1. 对代码质量的最终责任                                |
|      2. 对安全合规的最终责任                                |
|      3. 对产品体验的最终责任                                |
+---------------------------------------------------------+
```

### 0.2 团队 AI 成熟度模型

了解你的团队在哪个阶段，不要跨阶段要求：

| 阶段 | 特征 | 典型行为 | 关键转变 | 建议重点 |
|:----|:-----|:---------|:--------|:---------|
| **L1 试探期** | 个别人在用、不敢让同事知道 | 偷偷用AI写代码、用后删聊天记录 | → 走向公开讨论 | 破除羞耻感、分享技巧 |
| **L2 工具期** | 团队公开使用、但各自为战 | 每个人用不同的方式、风格不统一 | → 建立规范 | 制定团队Rule、统一工具 |
| **L3 规范期** | 有统一的Rules/Skills | 项目规则文件纳入git、新人上手快 | → 沉淀复用 | 建立Skill库、分享最佳实践 |
| **L4 嵌入期** | AI嵌入开发流程 | CI/CD中有AI审查、智能体处理工单 | → 度量优化 | 效率度量、质量追踪 |
| **L5 原生期** | 团队组织围绕AI重新设计 | 角色重构（AI+人 = 最小交付单元） | → 持续进化 | 组织进化、文化建设 |

**评估自检表**：

```text
□ 团队中是否有人在用AI开发工具？
□ 是否有团队的AI使用规范/规则？
□ 是否有人沉淀了可复用的Skill？
□ AI输出是否纳入了Code Review流程？
□ 是否有专门的智能体处理重复性工作？
□ 团队是否有AI使用效率的度量指标？
  勾选越多 -> 成熟度越高
```

### 0.3 什么时候不该用 AI

这是培训中最容易被忽略的部分——知道「什么时候不用」和知道「什么时候用」同等重要。

```text
🚫 不要用 AI 的场景：

  一、创意与审美判断
     +-- UI/UX 设计的主视觉方向（AI可以做素材，不能定风格）
     +-- 品牌命名、Slogan（AI缺乏品牌策略理解）
     +-- 产品战略决策（AI不知道你的公司资源和市场位置）

  二、需要真实人际判断
     +-- 团队冲突调解（AI没有情感洞察）
     +-- 绩效评估（AI不了解同事的日常表现）
     +-- 客户谈判策略（AI不知道客户关系和历史）

  三、法律责任场景
     +-- 法律合同最终审核（AI不替代律师）
     +-- 合规性最终判断（AI不替代合规官）
     +-- 安全漏洞的最后确认（需要人工测试验证）

  四、高度依赖本地/私有上下文
     +-- 没有上传完整上下文时的架构设计（AI会忽略关键约束）
     +-- 涉及数百个服务调用关系的重构（AI看不到全貌）
     +-- 需要理解团队政治/历史的决策

  五、AI 特别不擅长的
     +-- 数代码行数/统计精确数量（AI"数数"很差）
     +-- 保持超长上下文的一致性（超过上下文窗口后会"失忆"）
     +-- 精确版本对比（容易搞混版本A和版本B的差异）
     +-- 不含代码/文本的纯视觉对比（标尺/精确位置判断）

  ⚠️ 五个字的判断原则：
    "AI不懂你的业务上下文"
    你懂、它不懂 -> 你来定
    你不懂、它懂 -> 可以用
    你都不懂 -> 先搞清楚再决定用不用AI
```

# 培训一 Trae Work & Coding——让AI成为你的"数字同事"

## Part 1 Trae Work 上手

### 1.1 能力边界

**核心原则**：你不是在"让AI替你做"，而是在和AI分工。

```text
+------------------------------------------------------------+
|                   人 vs AI 的分工矩阵                        |
+------------------------------------------------------------+
|                                                             |
|  你（人类）负责              AI 负责                        |
|  -------------              --------                        |
|  ✅ 定义需求方向            ✅ 写初稿                       |
|  ✅ 判断"对不对"            ✅ 大规模重复劳动              |
|  ✅ 做出最终决策            ✅ 知识检索/信息整理           |
|  ✅ 处理灰色地带            ✅ 代码脚手架/模板生成         |
|  ✅ 审美/创意/伦理判断      ✅ 文档初版/注释/测试用例      |
|  ✅ 对接真实用户             ✅ 翻译/格式转换/批量处理      |
|                                                             |
|  --------- 分界线 ---------                                 |
|                                                             |
|  Trae Work 的工作哲学：                                     |
|  它擅长「从 0 到 80 分的初稿与重活」                       |
|  你负责「最后 20 分的把关与决策」                          |
|                                                             |
|  80分 -> 你改 -> 95分 ✅                                       |
|  (不要指望AI直接出95分，这不现实)                           |
+------------------------------------------------------------+
```

**实际案例**：

| 场景 | 你做的事情 | AI做的事情 | 时间节省 |
|:-----|:-----------|:-----------|:--------:|
| 写一个 CRUD 接口 | 定义表结构+业务逻辑 | 生成 controller/service/repo 全套代码 | ~70% |
| 写代码Review | 判断逻辑正确性 | 扫出格式/命名/潜在bug | ~50% |
| 写周报 | 补充关键决策和数字 | 整理工作项 → 生成草稿 | ~60% |
| 调研技术方案 | 判断方案的可行性 | 搜索资料+罗列优缺点 | ~40% |
| 写单元测试 | 审核测试覆盖度和边界用例 | 生成测试代码+Mock数据 | ~75% |
| 数据库迁移 | 确认数据一致性和回滚方案 | 生成迁移脚本+测试数据 | ~65% |

**不同角色的分工差异**：

```text
开发者视角：
  你写：核心算法、业务逻辑、架构决策
  AI写：模板代码、CRUD、配置、测试、文档

PM视角：
  你写：需求优先级、用户故事、验收标准
  AI写：PRD初稿、竞品分析表格、会议纪要

QA视角：
  你写：测试策略、边界条件设计、风险判断
  AI写：测试用例、测试数据、自动化测试脚本

运维视角：
  你写：容量规划、故障决策、变更审批
  AI写：监控脚本、部署配置、常规告警分析
```

### 1.2 安全红线——保密文件的"防火墙"

**这是最容易被忽视也是最重要的规则**：

```text
🚨 安全铁律（写在最前面）：

  ✅ 可以上传的：
     +-- 公开代码（开源项目）
     +-- 脱敏后的代码片段（替换真实IP/密码/密钥为 xxx）
     +-- 你自己的学习笔记/草稿
     +-- 伪代码/算法逻辑（不含具体实现细节）
     +-- 脱敏后的数据样例（字段名保留、数据值替换）

  ❌ 绝对不能上传的：
     +-- 公司核心代码仓库完整代码
     +-- 数据库连接串/API密钥/Token
     +-- 客户信息/用户数据
     +-- 内部文档含敏感标题
     +-- 未公开的商业计划/财务数据
     +-- 带有公司水印/版权声明的内部文件

  ⚠️ 脱敏操作指南——三步法：
     第一步：替换真实数据（密码->"****"、域名->"example.com"）
     第二步：移除标识信息（公司名->"某某公司"、项目名->"某项目"）
     第三步：检查上下文是否暴露（文件名/路径/注释中是否有敏感信息）
```

**脱敏实战——好 vs 坏**：

```text
❌ 错误示范：
   原始代码：
     const DB_HOST = "prod-db.internal.company.com";
     const DB_PASS = "s3cur3p@ss!";
     const API_KEY = "sk-proj-xxxxxxxxxxxxxxxx";
   直接发给AI -> ❌ 数据泄露！

✅ 正确脱敏后：
     const DB_HOST = "db.example.com";
     const DB_PASS = "****";
     const API_KEY = "sk-xxxx...xxxx";
   发给AI -> ✅ 安全

❌ 你以为脱敏了但没脱干净：
   // 用户登录 - 某某银行App - 生产环境
   文件名：prod_payment_2024Q4.sql
   -> 从注释和文件名暴露了项目和环境信息
   ✅ 应改为：用户登录功能、db_migration_template.sql

❌ 另一个常见翻车：
   把整个 git 仓库拖进去 -> 包含了 .env .git/config 等敏感文件
   ✅ 应只上传必要的代码文件，检查 .gitignore 中的文件不要上传
```

**公司治理建议**：

```text
对于团队的AI使用，建议建立以下制度：

① 建立「AI可上传」和「AI不可上传」的清单
   +- 每个团队根据自己的业务特点制定
   +- 在新人入职时作为安全培训的一部分

② 设置AI脱敏检查点
   +- 在PR模板中加一项：确认上传AI的代码已脱敏
   +- 代码审查时检查是否包含不应暴露的信息

③ 定期审计
   +- 抽查团队成员的AI对话记录（在合规范围内）
   +- 发现泄露及时复盘改进

④ 技术工具辅助
   +- 推荐使用 `.env` 管理密钥
   +- 构建前的脚手架工具自动生成脱敏模板
   +- 考虑使用本地部署的AI模型处理高度敏感代码
```

### 1.3 好指令公式——BGII + 高级技巧

**为什么同样用AI，有人效率翻倍，有人觉得没用？** ——差的在"指令质量"。

**好指令公式：BGII**

```text
B --- Background（背景）     -> AI需要知道上下文
       · "我们正在做一个电商后台系统..."
       · "这是给非技术背景的老板看的..."
       · "这个需求来自客户反馈，用户最关心的是速度..."

G --- Goal（目标）           -> AI需要知道你要什么
       · "帮我生成一个用户管理模块的CRUD代码"
       · "把这个需求拆成开发任务，按优先级排序"
       · "分析这段代码的安全漏洞"

I --- Input（输入）          -> AI需要知道用什么材料
       · "以下是数据库表结构：..."
       · "以下是需求文档原文：..."
       · "这是代码片段：..."

I --- Output Requirement（产出要求）-> AI需要知道交付标准
       · "用Python + FastAPI，要有错误处理"
       · "输出 markdown 格式，中英文双语注释"
       · "不要生成测试代码，只要核心逻辑"
       · "每项分析要包含：现状->问题->建议"
```

**❌ 坏指令 vs ✅ 好指令**：

```text
❌ "帮我写个用户注册功能"
  -> AI不知道用什么语言、什么框架、要不要验证码、前端还是后端

✅ "我们正在搭建一个电商后台系统（背景），
    需要给管理员加一个注册审核功能（目标）。
    已有用户表结构：[id, name, email, role, status]（输入）。
    帮我生成：
      1. 审核列表页面的React组件（带分页+搜索）
      2. 审核通过的API接口（含权限校验）
    用 TypeScript + Ant Design，要 type-safe（产出要求）"

❌ "这段代码有什么问题"
  -> AI不知道你要找什么问题（性能？安全？风格？）

✅ "下面是一个用户登录的代码片段（输入），
    帮我检查安全性漏洞（目标），
    重点关注：SQL注入、密码存储方式、Token生成方式（产出要求）"

❌ "帮我做个PPT"
  -> 太模糊了，AI不知道给谁看、什么主题、多少页

✅ "我要给技术主管做项目汇报（背景），
    需要做一个10页的PPT（目标），
    以下是项目进展数据（输入），
    帮我列出每页的标题和要点，
    风格正式、数据驱动、每页不超过3个要点（产出要求）"
```

**不同角色的指令示例**：

```text
👨‍💻 开发者的好指令：
  "我们使用 NestJS + Prisma（背景），
  需要在订单模块中加一个根据订单状态批量更新的接口（目标）。
  已有 Order 表：id, status, updated_at（输入）。
  帮我生成：
    1. 批量更新状态的 API（PUT /orders/batch-status）
```

**高级指令技巧**：

```text
技巧一：角色设定
  在指令开头给定角色，AI会调用对应的知识体系来回答。
  "你是一个有10年后端经验的架构师..."
  "你是一个专注于安全审计的工程师..."
  "你是一个给非技术背景老板做汇报的PM..."

技巧二：Few-Shot 示例
  给1-2个输入输出的例子，AI能更准确理解你要的格式。
  "以下是我想要的输出格式示例：
    输入：订单模块
    输出：
      - 用户故事1：作为...我希望...以便...
      - 验收标准：...

    请按照这个格式分析支付模块。"

技巧三：思维链 (Chain of Thought)
  让AI展示思考过程，不只是直接给答案。
  "请先列出分析步骤，再一步一步推理，最后给出结论。"

技巧四：约束条件前置
  把最重要的约束放在指令最前面，避免AI跑偏。
  "注意以下约束条件（按优先级）：
    1. 必须兼容现有接口，不能破坏性变更
    2. 不能引入新的外部依赖
    3. 响应时间必须控制在200ms以内
  然后才开始..."

技巧五：迭代指令
  不要期望一次出完美结果，先出框架再细化。
  "先输出一个框架/大纲/目录。"
  -> AI输出后
  "展开第3节，给出具体实现。"
  -> AI输出后
  "第3.2节的方案A和B做个对比表格。"
  -> 逐步迭代到完美
```

**指令质量自查清单（每次写完指令后扫一遍）**：

```text
□ 背景是否足够？AI会不会看不懂场景？
□ 目标是否具体？是否可以用"是/否"判断完成？
□ 如果有输入材料，是否附上了？
□ 产出要求是否明确？（语言/格式/风格/粒度）
□ 有没有提防AI过度发挥的约束条件？
□ 如果涉及多步，是否拆成了迭代指令而非一步到位？
□ 如果是重要任务，是否给了角色设定？
```

### 2.2 Rule（规则）——给AI立规矩

#### 规则的作用

```text
Rule 不是「提示词技巧」，
而是「告诉AI你的团队是怎么干活的」——统一的规则 = 统一的输出。

没有 Rule 时：
  AI用自己习惯的风格写代码 -> 混合了3-4种风格 -> 代码库越来越乱
  AI用不确定的注释语言 -> 中英混杂 -> 团队其他成员看不懂
  AI不做错误处理 -> 生成看似能用实则脆弱的代码

有 Rule 后：
  所有人都问同一个AI，输出的代码像同一个人写的
  新人上手项目，AI自动按团队规范推荐
  Code Review 工作量减少 50%+
```

#### 个人规则 vs 项目规则

```text
+---------------------------------------------------------+
|                                                          |
|  个人规则（.traerules 或 Settings > AI > Rules）          |
|  --------------------------------------                   |
|  影响范围：仅你自己                                     |
|  适合放的内容：                                          |
|    +- 你的个人编码偏好（函数命名风格、空格vs Tab）        |
|    +- 你常用的技术栈偏好                                 |
|    +- 你的工作习惯（写注释的风格、错误处理偏保守还是激进）|
|                                                          |
|  示例：                                                  |
|    """                                                   |
|    ## 个人编码规则                                       |
|    - 使用 TypeScript，严格模式                            |
|    - 函数命名使用 camelCase，组件使用 PascalCase          |
|    - 所有公共函数必须写 JSDoc 注释                        |
|    - 错误处理：使用 Result 模式而非 throw                 |
|    - 缩进使用 2 空格                                     |
|    """                                                   |
|                                                          |
+---------------------------------------------------------+
|                                                          |
|  项目规则（项目根目录下的 .traerules 文件）                |
|  -------------------------------------                    |
|  影响范围：所有参与该项目的成员                           |
|  适合放的内容：                                           |
|    +- 项目技术栈和版本约定                               |
|    +- 架构规范（分层/命名/模块边界）                      |
|    +- 代码风格统一（ESLint/Prettier配置摘录）             |
|    +- 数据库命名规范                                     |
|    +- API设计规范（RESTful/GraphQL/返回格式）             |
|                                                          |
|  示例（电商后台项目）：                                    |
|    """                                                   |
|    ## 项目规则：电商后台 v2.0                             |
|                                                          |
|    ### 技术栈                                            |
```

### 2.3 Skill（技能）——封装你的超级SOP

#### 什么是 Skill

```text
Skill = 「把经常做的任务流程封装成可复用的SOP」

当你发现你经常让AI做同一类事情时
（比如"写测试用例""生成API文档""做代码审查"等），
就应该把它固化为一个 Skill。

Skill 和 Prompt 的区别：
  +-----------------------------------+
  |  Prompt：一次性指令                 |
  |  Skill：可复用的任务模板            |
  |                                    |
  |  写Prompt就像每次重新说一遍需求       |
  |  用Skill就像点外卖——选好、下单、等     |
  +-----------------------------------+
```

#### 如何创建Skill——四步法

```text
第1步：手动跑通一次
  +- 给AI发一条详细的指令（用 BGII 公式）
  +- 迭代直到输出满意
  +- 确认这个流程是可复用的

第2步：固化模板
  把跑通的流程结构化：

  skill "代码审查" {
    背景：{{project_type}} 项目的 {{language}} 代码
    目标：做全面代码审查
    输入：
      - 代码文件：{{file_path}}
      - 审查重点：{{focus_areas}}
    检查清单：
      ✅ 安全性（SQL注入/XSS/权限校验）
      ✅ 性能（不必要的查询/循环/N+1问题）
      ✅ 可维护性（命名/长度/重复代码）
      ✅ 错误处理（异常捕获/兜底逻辑）
    产出格式：
      - 问题列表（按严重程度：🔴/🟡/🟢）
      - 每个问题：位置+原因+建议修复方案
  }

第3步：按需动态加载
  在需要的时候引用Skill：
    "用「代码审查」Skill 审查 auth.service.ts，
    重点关注安全和性能"
  -> AI自动按照Skill定义的流程执行

第4步：持续迭代
  每次使用Skill后发现不足 -> 更新Skill定义
  Skill不是一次写完的，是不断完善的
```

**完整Skill模板——生成单元测试**：

```text
skill "生成单元测试" {
  背景：
    "项目使用 {{test_framework}} 框架"
    "测试的模块是 {{module_name}}"
    "已有 Mock 工具：{{mock_library}}"

  目标：
    "为以下代码生成完整的单元测试"

  输入要求：
    - 源代码文件：{{source_code}}
    - 接口定义/类型定义（可选）

  执行流程：
    1. 分析代码的结构（函数/方法/类）
    2. 识别所有分支路径（if/else/switch/异常）
    3. 生成测试用例覆盖：
       - 正常流程（Happy Path）
       - 边界条件（空值/极限值/异常参数）
       - 错误路径（异常抛出/错误返回）
       - 状态变化（如果有状态机）
    4. 生成 Mock 数据

  产出要求：
    - 每个测试函数使用 AAA（Arrange-Act-Assert）结构
    - 测试函数命名：[方法名]_[场景]_[预期结果]
    - 包含必要的 import 语句
    - 每 10 行代码至少一个测试用例
    - 运行命令：{{test_command}}

  约束条件：
    - 不要 Mock 不需要的外部依赖（过度Mock）
    - 测试之间不能有状态依赖
    - 每个测试独立可运行
}
```

#### Skill 的适用场景判断

| 场景 | 是否适合Skill | 原因 |
|:-----|:------------:|:-----|
| 新建 CRUD 模块 | ✅ 非常适合 | 流程固定，只是表结构不同 |
| 写单元测试 | ✅ 非常适合 | 框架固定，只是业务逻辑不同 |
| API 文档生成 | ✅ 非常适合 | 输入代码→输出文档，流程标准化 |
| 周报生成 | ✅ 适合 | 输入工作项→周报，格式固定 |
| 数据库迁移脚本 | ✅ 适合 | Schema变化→迁移脚本 |
| 代码审查 | ✅ 适合 | 审查维度固定 |
| Bug修复 | ❌ 不太适合 | 每个Bug根因不同，需单独分析 |
| 技术方案设计 | ❌ 不太适合 | 每个方案约束都不一样 |
| 架构重构 | ❌ 不适合 | 高度依赖项目特定上下文 |

#### Skill 的团队共享机制

```text
团队 Skill 管理流程：

① 个人沉淀 -> ② 团队评审 -> ③ 发布索引 -> ④ 使用反馈

Skill 仓库目录结构建议：

  skills/
  +-- index.md              # 所有Skill的索引
  +-- code-review.skill     # 代码审查Skill
  +-- test-generation.skill # 测试生成Skill
  +-- api-doc.skill         # API文档生成Skill
  +-- weekly-report.skill   # 周报生成Skill

每个 Skill 文件的第一段为元数据：

  ## 元数据
  - 名称：生成单元测试
  - 版本：v1.2
  - 维护者：张三
  - 最后更新：2026-07-15
  - 适用项目：所有后端项目
  - 依赖MCP：无
```

### 2.4 MCP（协议）——AI的"USB接口"

#### MCP 的本质

```text
MCP = Model Context Protocol

简单理解：
  AI模型本身只有「训练时学到的知识」——截止到某个时间点
  AI不能直接访问你的数据库、文件系统、代码仓库、API文档
  MCP 就是让AI安全地「插上」这些外部能力的接口

用USB做类比：
  USB协议        -> MCP 协议（标准化的接口协议）
  USB设备（U盘） -> MCP Server（提供具体能力的服务）
  操作系统驱动   -> MCP Client（AI IDE 端负责发现和调用）
  插上就能用     -> 配置MCP后立即获得新能力

+--------------------------------------------------------------+
|                     MCP 工作原理                              |
|                                                              |
|  [你的指令] -> [AI Model] <--> [MCP Client]                     |
|                                  |                            |
|                      +-----------+-----------+                |
|                      |    MCP Server 集合      |               |
|                      +-----------------------+                |
|                      |  Context7：实时文档检索  |               |
|                      |  Playwright：浏览器测试  |               |
|                      |  GitHub：PR/Issue管理   |               |
|                      |  Figma：设计稿解析       |               |
|                      |  File System：本地文件   |               |
|                      |  Database：数据查询      |               |
|                      +-----------------------+                |
|                                                              |
|  AI 不会直接访问外部资源 -> AI 通过 MCP 工具「问」外部资源       |
|  MCP 不会把敏感数据随意暴露 -> 受 scope 和 permission 约束      |
+--------------------------------------------------------------+
```

**MCP vs 插件 vs API**：

```text
传统方式：
  开发者手动调用 API -> 拿到结果 -> 贴给AI -> AI分析
  （开发者是"中间人"，效率低）

传统插件：
  插件封装了 API 调用 -> 通过固定接口和AI交互
  （每个插件是孤岛，互不通用）

MCP 方式：
  AI通过标准化协议发现工具 -> 自主决定什么时候用什么工具
  -> 结果回到AI的上下文中继续推理
  （标准化、AI自主发现、统一上下文）

一句话：MCP = 标准化的AI工具接口协议
  让不同工具用同一套「语言」和AI对话
  让不同AI客户端（Trae/Cursor/VS Code）能共享同一套工具
```

#### 热门 MCP 推荐

| MCP | 能力 | 适合场景 | 配置难度 | 是否免费 |
|:----|:-----|:---------|:--------:|:--------:|
| **Context7** | 实时检索第三方文档 | 写代码时查API用法 | ⭐ 低 | ✅ |
| **Playwright** | 控制浏览器自动化测试 | E2E测试/截图对比 | ⭐⭐ 中 | ✅ |
| **GitHub** | 创建PR、Review代码、管理Issue | 开发工作流自动化 | ⭐ 低 | ✅ |
| **Figma AI Bridge** | 解析设计稿、提取组件信息 | 前端还原设计稿 | ⭐⭐ 中 | 部分免费 |
| **Filesystem** | 读写项目文件 | 批量文件操作 | ⭐ 低 | ✅ |
| **Database** | 查询数据库Schema和数据 | 数据探索/排查问题 | ⭐⭐⭐ 较高 | ✅ |
| **Slack/Teams** | 发送消息到团队沟通工具 | 自动化通知 | ⭐⭐ 中 | ✅ |
| **Perplexity** | 联网搜索+引用来源 | 技术调研 | ⭐ 低 | 需API Key |
| **Stripe** | 查询支付/订单/客户信息 | 支付系统调试 | ⭐⭐ 中 | ✅ |
| **Notion** | 读写Notion页面/数据库 | 知识库管理 | ⭐⭐ 中 | ✅ |
| **Jira** | 查询/创建Issue | 项目管理/工单跟踪 | ⭐⭐ 中 | ✅ |
| **Docker** | 管理容器/镜像/日志 | 开发/调试环境 | ⭐⭐⭐ 较高 | ✅ |

#### MCP 实战指南

```text
MCP 配置方式（以 Trae IDE 为例）：

1. 打开 Settings -> AI -> MCP Servers
2. 添加 MCP Server（选择类型）：

   内置MCP（零配置）：
     +-- File System — 直接可用
     +-- Terminal — 直接可用
     +-- Search — 直接可用

   第三方MCP（需配置）：
     示例 — Context7：
       {
         "mcpServers": {
           "context7": {
             "command": "npx",
             "args": ["@context7/mcp-server"]
           }
         }
       }

   自定义MCP（自己开发）：
     用任何语言实现 MCP 协议规范
     暴露 tools / resources / prompts 三类能力

3. 验证连接成功
   在聊天窗口输入 "检查MCP连接状态"
   看是否返回可用工具列表

实战示例：
  "帮我查一下 Next.js App Router 中
   `generateStaticParams` 的最新API用法"
  -> AI通过 Context7 MCP 实时检索Next.js文档
  -> 返回最新版本API签名+示例代码
  -> 而不是依赖训练数据中的旧版本信息
```

**MCP 使用原则**：

```text
✅ 需要实时信息时用 MCP
   ("这个npm包的最新版本是多少" -> Search/NPM MCP)
   ("查一下生产环境的Redis内存使用" -> Database MCP)

✅ 需要操作外部系统时用 MCP
   ("帮我把PR的Review结果贴到Slack" -> Slack MCP)
   ("为这个设计稿生成对应的React组件" -> Figma MCP)

❌ 不需要为了用而用
   ("写一个Hello World" -> 不需要MCP，AI直接能写)
   ("解释什么是RESTful API" -> AI训练数据就有)

⚠️ 安全提醒：
   理解每个MCP能做什么、不能做什么
   不要给MCP Server不必要的高权限
   定期审查已配置的MCP列表
```

**MCP 排障指南**：

```text
常见问题与解决方法：

问题1：MCP 连接失败
  检查 MCP Server 是否已启动
  检查配置中的 command 和 args 是否正确
  检查网络是否可访问对应服务
  在终端中手动运行看是否有报错

问题2：调用超时
  确认 MCP Server 响应时间是否正常
  对耗时操作增加超时时间
  检查外部服务端的问题

问题3：返回空结果
  检查查询条件是否正确
  确认 MCP 权限范围能否访问数据
  查看 Server 日志是否有错误信息

问题4：MCP 影响了AI主任务
  有些 MCP 会"抢"AI注意力
  指令中明确：先自己回答，不确定再通过 MCP 查
  简单任务可以禁用不必要的 MCP
```

### 1.2 一句话选型

```text
🧠 一句话选型指南：

  "能画成流程图且要求每步准确"
  --> 流程编排型（工单审批/数据ETL/内容审核）

  "意图开放、用户爱问什么问什么"
  --> 对话型（知识问答/创意写作/内部搜索）

  "介于两者之间——有流程但也要对话灵活"
  --> 对话流型（客服引导/故障排查/多步骤收集）


选型决策树：

  用户输入是否可预测？
  +-- 是 -> 流程能否画出来？
  |       +-- 能 -> 流程编排型
  |       +-- 不能 -> 对话流型
  +-- 否 -> 对话型

  是否要求100%确定性？
  +-- 是 -> 流程编排型
  +-- 否 -> 对话型或对话流型

  是否涉及多轮信息收集？
  +-- 是 -> 对话流型
  +-- 否 -> 对话型


选型评分矩阵：

  需求 \ 形态          流程编排   对话流    对话型
  ----------          --------  -------  ------
  固定流程确定性        ★★★★★     ★★★★      ★★
  对话灵活性              ★★     ★★★★    ★★★★★
  快速搭建                ★★     ★★★     ★★★★★
  复杂分支处理          ★★★★★     ★★★        ★
  维护成本(低)            ★★★       ★★        ★★
  调试难度(低)          ★★★★       ★★★       ★★
```

### 1.3 渐进式演进路线

```text
不要一步到位——智能体形态应该随着业务复杂度逐步演进。

第1阶段：MVP 快速验证（1-2周）
  用「对话型」快速搭建
  目的：验证用户需求是否存在
  投入：1个Prompt + 1份知识库文档

第2阶段：体验优化（2-4周）
  从对话型升级到「对话流型」
  增加槽位填充、分支逻辑
  目的：提升回答准确率和用户体验

第3阶段：流程自动化（1-2月）
  引入「流程编排型」处理核心高频流程
  对话流型处理非结构化交互
  两者并行，互为补充

示例路径：
  内部IT支持助手：
  对话型（首版）-> 对话流型（加自助查询）-> 流程编排型（加审批流+自动派单）
```

## Part 2 五种能力组合

```text
一个智能体的能力 = 一个或多个「能力组件」的组合

以下是五种最常用的能力组件：

+--------------------------------------------------------------+
|  能力组件①：知识库检索（RAG）                                  |
|  --------------------------------                              |
|  能力：把文档/手册/FAQ喂给AI，让它基于你的知识回答问题           |
|  适用：产品FAQ助手、内部知识库、政策查询                        |
|  门槛：★☆☆☆☆（文件上传即可）                                  |
|  关键指标：检索命中率、回答准确率                                |
|                                                               |
|  实现方式：                                                    |
|    上传文档（PDF/Word/Markdown/TXT）-> AI自动分块+向量化        |
|    用户提问 -> 语义检索Top-K -> 注入Prompt -> 生成回答            |
|                                                               |
|  常见翻车：文档太老->回答过时；文档太杂->检索不到相关内容         |
|  解决方案：定期更新知识库 + 知识库分类 + 索引优化                |
|                                                               |
|  能力组件②：工具调用（Function Calling）                        |
|  --------------------------------                              |
|  能力：让AI调用外部API——查天气、查订单、发邮件、创建工单         |
|  适用：需要实时数据的场景                                       |
|  门槛：★★★☆☆（需要写API接入）                                  |
|  关键指标：调用成功率、参数匹配率                                |
|                                                               |
|  实现方式：                                                    |
|    定义工具Schema（名称+参数+返回格式）                         |
|    AI判断用户意图->选择工具->提取参数->调用->结果返回给AI生成回答    |
|                                                               |
|  常见翻车：参数提取错误->API调用失败；返回数据太复杂->AI理解错     |
|  解决方案：工具参数设计尽量简单 + 返回数据格式化                  |
|                                                               |
|  能力组件③：工作流编排                                         |
|  --------------------------------                              |
|  能力：把多步骤流程编排成自动化流水线                            |
|  适用：需要按固定流程处理的问题                                 |
|  门槛：★★★★☆（需要画流程图）                                    |
|  关键指标：流程完成率、平均处理时间                               |
|                                                               |
|  常见翻车：条件分支覆盖不全->卡在中间节点                        |
|  解决方案：每个分支加「兜底出口」 + 超时告警                     |
|                                                               |
|  能力组件④：多轮对话记忆                                       |
|  --------------------------------                              |
|  能力：记住用户说过的信息，在后续对话中复用                      |
|  适用：需要上下文理解的场景                                     |
|  门槛：★★☆☆☆（平台通常内置）                                   |
|  关键指标：上下文召回准确率、记忆长度                             |
|                                                               |
|  常见翻车：记忆混淆（A说了什么被记成B说的）；记忆超长->Token浪费   |
|  解决方案：设置记忆有效期 + 关键信息提取后再存储                  |
|                                                               |
|  能力组件⑤：人机协作（Human-in-the-Loop）                       |
|  --------------------------------                              |
|  能力：遇到AI不确定或高风险的操作时，转给人工确认                 |
|  适用：支付、审批、高风险操作                                   |
|  门槛：★★★★☆（需要审批流+通知系统）                             |
|  关键指标：人工介入率、审批通过率                                |
|                                                               |
|  常见翻车：介入率太高=失去自动化意义；介入率太低=风险暴露         |
|  解决方案：根据置信度动态调整介入阈值                             |
+--------------------------------------------------------------+

能力组合的常见模式：

  「首版智能体」推荐组合：
    知识库检索（RAG） + 多轮对话记忆
    -> 一个"能回答问题"的助手，5分钟就能搭建

  「进阶智能体」组合：
    知识库检索 + 工具调用 + 工作流编排
    -> 一个"能做事"的助手，能查数据、走流程、做操作

  「全功能智能体」组合：
    全部五项能力
    -> 一个"准同事"级别，但复杂度指数级上升

原则：从最少能力开始，逐步叠加。不要一上来就全上。
每加一个能力组件，调试复杂度翻倍。
```

## Part 3 5分钟搭建第一个智能体（实战演练）

### 3.1 创建智能体与选择形态

```text
Step 1: 进入智能体平台 -> 点击「创建智能体」

Step 2: 选择编排形态
  +-- 今天做什么？-> "内部知识问答助手"
  +-- -> 选「对话型」（因为用户问什么不确定）

Step 3: 取个有意义的名字
  ✅ "研发知识助手" — 一看就知道用途
  ❌ "智能体v1" — 3个月后没人记得这是干什么的
  ✅ "IT工单分类机器人" — 功能和场景一目了然
  ❌ "test_agent_final_v2" — 命名灾难

Step 4: 选择图标/头像（可选）
  给智能体配一个头像 -> 用户感知更亲切
  建议直接用 emoji 或平台内置图标
```

### 3.2 选择模型

```text
模型选择不是「越强越好」，而是「刚刚好」：

                    简单任务              复杂任务              专业领域
                    --------             --------             --------
  推荐模型          轻量模型               旗舰模型              领域模型
  (示例)            DeepSeek-R1-Lite      GPT-4o/Claude-4      Codex/Grok

  特点              快、便宜、够用          慢、贵、能力强        垂直领域最优
  延迟              200-500ms             1-3s                 0.5-2s
  成本/千token      ~$0.001               ~$0.01               ~$0.005-0.02

  适合场景          FAQ问答/信息查询        复杂推理/代码生成      编程/医疗/金融

选型原则：
  ① 先试轻量模型，不行再升级（90%的场景轻量模型就够了）
  ② 不同节点可以用不同模型（流程编排型中，简单节点用轻量模型）
  ③ 考虑成本和延迟——不要为90%的问题支付旗舰模型的价格
  ④ 如果用户需要实时性（客服场景），延迟是关键指标
  ⑤ 如果用户需要高准确率（医疗/法律），能力是关键指标

模型选择决策树：
  是否需要专业知识？
  +- 是 -> 领域专用模型（如 Codex 写代码、Grok 分析数据）
  +- 否 -> 是否需要复杂推理/长上下文？
       +- 是 -> 旗舰模型（GPT-4o / Claude-4）
       +- 否 -> 轻量模型（够用、便宜、快）
```

### 3.3 编写提示词

```text
提示词 = 智能体的「灵魂」——它决定了AI的行为方式

提示词四要素：

+------------------------------------------------------------+
|  角色 + 目标 + 规则 + 兜底                                    |
|                                                            |
|  「角色」——你是谁？                                          |
|    你是一个研发团队的内部知识助手                               |
|                                                            |
|  「目标」——你要做什么？                                       |
|    帮助团队成员快速找到需要的技术信息                           |
|                                                            |
|  「规则」——你怎么做事？                                       |
|    - 只回答知识库中已有的内容，不要编造                         |
|    - 如果问题涉及代码，给出示例代码片段                        |
|    - 回答要简洁，先给结论再展开                               |
|    - 引用知识库来源（文件名+行号）                            |
|                                                            |
|  「兜底」——不知道怎么办？                                     |
|    如果知识库中没有相关信息，请回答：                          |
|    "这个内容我暂时没有找到相关的知识库记录，                    |
|     你可以联系知识库管理员补充，或者尝试搜索关键词：xxx"       |
+------------------------------------------------------------+

完整示例——研发知识助手：

"""
你是一个研发团队的内部知识助手。
你的目标是帮助团队成员快速找到需要的技术信息，包括
技术方案、API文档、项目架构、最佳实践等。

### 规则
1. 基于知识库回答——只回答知识库中已有的内容
2. 如果问题涉及代码，在回答中附上代码示例
3. 回答结构：先给出最直接的回答（1-2句话），再展开细节
4. 对于有多个可行方案的场景，用对比表格展示差异
5. 如果用户问的超出知识库范围：明确指出并引导用户补充

### 回答示例
用户问：系统间怎么通信？
正确回答：
  "目前团队使用RabbitMQ作为消息中间件。

  核心配置：
  - 交换机类型：Topic Exchange
  - 序列化：Protobuf
  - 重试机制：指数退避（最大3次）

  详见知识库：系统架构设计文档 §3.2"

### 兜底
如果明确不包含所需信息，回复：
  "这个内容我暂时没有找到相关记录，
  你可以在知识库上传相关文档，我会帮你整理。"
"""

提示词进阶技巧——分版本管理：

  V1 — 基础版（能回答）
    角色 + 目标 + 基础规则
    够用：60%的场景

  V2 — 规范版（答得好）
    加入回答格式规范、示例、兜底
    够用：80%的场景

  V3 — 增强版（做得对）
    加入防幻觉机制、知识库引用规范、边界情况处理
    够用：90%+的场景

  不要一开始就写 V3 级别的提示词——先跑通再升级
```

### 3.4 配置开场白与示例问题

```text
开场白 = 用户第一次接触智能体时看到的「第一印象」

✅ 好的开场白：
  "你好！我是研发知识助手👋
  我可以帮你查找技术方案、API文档、项目架构等信息。

  试试问我：
  · 系统架构是怎样的？
  · 数据库设计规范有哪些？
  · 部署流程是什么？
  · 某个API怎么调用？"

❌ 差的开场白：
  "你好，有什么可以帮你的？"
  -> 用户不知道怎么用，可能第一个问题就问偏了

❌ 另一个差的开场白：
  "我是一个AI助手..."（用户知道你是AI，不用说）
  -> 直接说你能做什么


示例问题配置（非常重要！）：

  配置3-5个最常见的提问作为示例
  这不仅是给用户看的，也是给AI的「行为示范」

  ✅ 好的示例问题：
     · "Redis在哪些场景下使用？" -> 技术知识回答
     · "怎么创建一个新的微服务？" -> 流程指导
     · "项目的代码规范是什么？" -> 规范查询
     · "目前有哪些数据库？各自的用途是什么？" -> 对比类问题
     · "部署一个服务需要几步？" -> 步骤流程

  ❌ 差的示例问题：
     · "你好" -> 浪费了一个示例位
     · "你会什么" -> 太宽泛，不能帮助用户理解边界
```

### 3.5 调试（三类测试）

```text
调试是决定智能体能否上线的最关键步骤——千万别省略！

调试三类测试用例：

① 正例测试（测试正常功能）
   -- 预期：完全正确回答
   用例：
   - 用户问知识库内明确存在的知识 -> 应该准确回答
   - 用户问常见问题 -> 应该按预设格式回答
   - 用户问带参数的问题 -> 应该正确解析参数

② 边界测试（测试边缘情况）
   -- 预期：能合理处理
   用例：
   - 用户的问题非常模糊（只有1个词） -> 不应乱猜，应引导澄清
   - 用户的问题非常长（500字以上） -> 不应超出Token限制
   - 多轮对话中切换话题 -> 应正确处理上下文
   - 连发多条消息 -> 不应漏掉任何一条
   - 中英文混输 -> 应该正确处理

③ 反例测试（测试拒答能力）
   -- 预期：明确拒答
   用例：
   - 用户问的完全超出知识库范围 -> 应说"不知道"
   - 用户问不合规的问题（"怎么绕过权限"） -> 应拒绝回答
   - 用户诱导AI编造答案 -> 应坚持基于知识库
   - 用户问不相关的话题（"帮我写首诗"） -> 应引导回正题


调试记录表（建议在发布前填完）：

  +----------+---------------------+----------+----------+
  | 测试类型  | 输入                 | 预期输出  | 实际输出  |
  +----------+---------------------+----------+----------+
  | 正例✅   | "项目用什么数据库"    | "PostgreSQL" |  「Pass」|
  | 边界⚠️   | "。"                 | 请补充问题  |  「Pass」|
  | 反例❌   | "你怎么造出来的"      | 不回答     |  「Pass」|
  +----------+---------------------+----------+----------+

调试过程中的迭代策略：

  发现一个问题 -> 不要直接改提示词
  先问自己：
    这是Prompt问题还是知识库问题？
    是规则不够清楚还是模型本身问题？

  常见调试循环：
    问题：用户问了知识库里有但AI答错
    排查：检索没命中？-> 知识库分块问题
        命中但没用？-> Prompt中忘了强调"基于知识库"
        用了但理解错？-> 知识库内容不够清晰

  每轮调试只改一个变量
  ❌ 同时改了提示词+知识库+模型 -> 不知道哪个改动起了作用
  ✅ 只改提示词 -> 测试 -> 有效继续，无效回滚
```

### 3.6 发布与分享 + 运营

```text
发布前的检查清单：

  □ 提示词：角色+目标+规则+兜底 四要素齐全？
  □ 知识库：已上传至少一个文档并验证检索正常？
  □ 调试：三类测试用例全部通过？
  □ 开场白：能让新用户秒懂这个智能体是做什么的？
  □ 示例问题：配置了3-5个典型问题？
  □ 模型选择：复杂度匹配，没有大炮打蚊子？
  □ 权限：谁可以用？需要登录吗？需要审批吗？

发布方式：
  ① 内部使用 -> 分享链接/嵌入到内部工具台
  ② 对外使用 -> 嵌入官网/集成到公众号/小程序
  ③ 团队工具 -> 集成到飞书/企业微信/Slack


上线后的持续运营（经常被忽略！）：

  第1周：密集监控
    +- 每天看用户提问日志
    +- 标记回答不好的问题
    +- 补足知识库和边界用例

  第2-4周：稳定迭代
    +- 每周更新一次知识库
    +- 收集用户反馈（好的和不好的）
    +- 优化高频问题的回答质量

  每月：健康度检查
    +- 知识库是否需要更新？
    +- 用户量和使用次数变化趋势？
    +- 是否有新的常见问题需要纳入？
    +- 是否需要升级模型或形态？

  每季度：重新评估
    +- 这个智能体还有存在的必要吗？
    +- 是否能合并到其他智能体？
    +- 是否需要从对话型升级到对话流型？

运营指标看板建议：

  核心指标：
  +-- 日活跃用户数（DAU）
  +-- 日提问次数
  +-- 回答采纳率（用户点了"有用"的比例）
  +-- 平均对话轮数（短=高效，太长=答不清楚）
  +-- 需要转人工的次数

  质量指标：
  +-- 知识库命中率
  +-- 反例命中率（AI应该拒答的问题是否被正确拒绝）
  +-- 回答长度分布（太长=不够精准，太短=不够详细）
```

## Part 4 避坑清单

```text
⚠️ 智能体搭建常见陷阱（按频率排列）：

① 知识库没维护 -> 智能体上线时好用，1个月后回答全过时
   解决方案：
   +- 设置知识库更新提醒（每2周检查一次）
   +- 在关键文档上加「有效期」标签

② 提示词太复杂 -> AI行为反而失常
   解决方案：
   +- 提示词不超过500字（超出反而降低准确率）
   +- 能不写规则的场景就别写（越短越稳定）

③ 想让AI做它做不到的事 -> 用户期望管理失败
   解决方案：
   +- 开场白里说清楚「能做什么」和「不能做什么」
   +- 兜底回复写得越明确越好

④ 没有兜底 -> 用户按固定格式提问时AI答得还行，
   用户一问超出范围，AI就开始胡说
   解决方案：
   +- 务必写兜底规则
   +- 兜底要具体："如果你不确定，就说'这个问题我回答不了'"

⑤ 只跑正例测试 -> 看起来都过，上线后真实用户刁钻问题全翻车
   解决方案：
   +- 调试一定要包含三类测试（正例/边界/反例）
   +- 上线后前两周每天看用户提问日志，补足边界用例

⑥ 选了太贵的模型 -> 单个对话成本太高，用起来心疼
   解决方案：
   +- 简单问答用轻量模型
   +- 只有在需要推理/代码/复杂理解时才上旗舰模型

⑦ 模型幻觉没处理 -> AI回答了知识库里没有的内容
   解决方案：
   +- 在Prompt中强调"只基于给定文档回答"
   +- 加一句"如果不确定，就说不知道"

⑧ 权限开太大 -> 智能体内部人人都能改配置
   解决方案：
   +- 发布者和维护者分离
   +- 敏感功能（写库/发邮件）加人工确认

⑨ 没有度量 -> 不知道智能体好不好用、要不要优化
   解决方案：
   +- 至少跟踪3个指标：使用量/采纳率/转人工率
   +- 每两周审视一次指标，决定是否迭代

⑩ 一次性交付思维 -> 智能体不是开发完就结束了
   解决方案：
   +- 把智能体当产品来做，需要有持续运营计划
   +- 至少每两周更新一次知识库

⑪ 选了不对的形态 -> 需求变了但形态没变
   解决方案：
   +- 定期（每月）回顾：当前的形态是否还适合需求？
   +- 需要升级形态时不要犹豫

⑫ 未给AI留"人性化"余地 -> 回答太机械，用户不想用
   解决方案：
   +- 在Prompt中加入语气指导："保持友好专业的语气"
   +- 开场白设计得像「人」说话，不是说明书

陷阱自查清单（上线前逐项检查）：
  □ 是否设置了知识库更新频率？
  □ 提示词是否超过500字？（如果超过，尝试精简）
  □ 是否明确告知用户「能做什么」「不能做什么」？
  □ 是否有兜底回复？
  □ 三类测试是否全部通过？
  □ 是否有运营指标跟踪计划？
  □ 是否有持续迭代计划？
```

### A. 速查卡

**一页纸记不住的，看这里：**

```text
▸ BGII 指令公式：
  Background（背景） + Goal（目标） + Input（输入） + Output Requirement（产出要求）

▸ 铁三角速记：
  Rule -> 统一风格（让AI像你们团队的人）
  Skill -> 封装SOP（让AI记住怎么做重复的事）
  MCP -> 扩展能力（让AI能查实时数据/调用外部系统）

▸ 智能体选型：
  流程固定、每步准确 -> 流程编排型
  意图开放、自由对话 -> 对话型
  有流程但也要灵活 -> 对话流型

▸ 提示词四要素：
  角色 + 目标 + 规则 + 兜底

▸ 三类测试：
  正例（正常流程）+ 边界（边缘情况）+ 反例（应该拒绝的）

▸ 安全铁律：
  脱敏三步：替换数据 -> 移除标识 -> 检查上下文
```

```text
练习一：BGII 指令改写

  原始指令："帮我优化一下这段代码"

  （提示：明确背景、目标、输入、产出要求）

练习二：设计一个智能体

  场景：你的团队每周被重复问同样10个问题
  （"数据库密码在哪" "部署流程是什么" "谁负责XX模块"）

  请设计一个智能体来解决这个问题，包括：
  1. 选什么形态？为什么？
  2. 提示词怎么写？（角色+目标+规则+兜底）
  3. 开场白怎么设计？
  4. 需要配什么能力组件？
  5. 三类测试各写一个用例

练习三：写一个项目规则

  为你的项目写一份 .traerules 文件（至少5条规则）
  要求：
  - 覆盖技术栈/编码规范/数据库命名中的至少2个
  - 每条规则可执行可检查
  - 团队分享讨论

练习四：用AI辅助设计一个Skill

  选一个你最常做的重复性工作
  （写周报/代码审查/写测试/写API文档...）

  用 BGII 公式写一条完整指令，手动跑通一次
  然后把流程固化为 Skill 模板

练习五：智能体调试挑战

  给出一个「翻车智能体」的描述，找出问题并修复：

  场景：一个IT支持智能体，用户问"VPN怎么连"，
  AI回答："VPN是虚拟专用网络的缩写，
  它通过在公共网络上建立加密隧道...（500字原理）"
  用户想要的只是"下载客户端->输入服务器地址->点连接"。

  问题出在哪？怎么修复？
```

### C. FAQ

```text
Q: 我用AI写的代码，版权归谁？
A: 目前法律上存在争议。建议：
  - 公司内部制定AI使用政策
  - 涉及核心IP的代码，避免直接用AI生成完整代码
  - AI辅助 vs AI生成的界限要明确

Q: AI会取代程序员吗？
A: 短期（1-2年）不会。AI改变的是「怎么做」，不是「做什么」。
  - 重复性工作的需求减少
  - 架构设计/系统思考的需求增加
  - 会使用AI的程序员 -> 效率翻倍
  - 不会使用AI的程序员 -> 竞争力下降

Q: 为什么我的AI总是不按我的要求输出？
A: 最常见的原因：
  1. 指令不够具体（用BGII公式再写一遍）
  2. 没有Rule约束（AI按默认风格输出）
  3. 期望过高（80分 -> 你改到95分，不要期待AI直接出95分）
  4. 迭代不够（一次出完美是大模型目标，不是现实）

Q: 需要给所有人配置MCP吗？
A: 不必要。建议：
  - 新手：先学会用基础功能（Rule + 好指令）
  - 中级：加常用MCP（Context7 / GitHub）
  - 高级：自定义MCP
  80%的日常使用，不需要任何MCP

Q: 智能体上线后没人用怎么办？
A: 常见原因：
  1. 用户不知道有这个智能体 -> 主动推广，在团队群发
  2. 回答质量太差 -> 检查知识库和提示词
  3. 用户习惯自己查 -> 在常见场景中嵌入智能体入口
  4. 响应太慢 -> 考虑换轻量模型

Q: 提示词写越长越好吗？
A: 不是。研究表明：
  - 提示词在300-500字范围内效果最佳
  - 超过800字后，AI反而容易忽略关键信息
  - 核心规则放在最前面
  - 能精简就精简

Q: 怎么防止AI在智能体中产生幻觉？
A: 多层防护：
  1. Prompt层：强调"只基于给定知识库回答"
  2. 知识库层：分块合理、内容清晰
  3. 测试层：三类测试覆盖反例
  4. 监控层：跟踪采纳率和用户反馈
  5. 兜底层：明确告诉AI"不知道就说不知道"
```
