## 1. 能力框架总览

### 1.1 十维能力模型

AI 工具使用能力由 **10 个相互支撑的维度**构成，分为三层：

```text
                +-------------------------------------+
                |     ⑤ 输出质量验证                    |
                |     ⑥ 需求工程与表达                   |
        核心技能 |     ⑦ 批判性评估能力                   |
                |     ⑧ 人机协作模式                     |
                |     ⑨ 成本与效率意识                   |
                +---------------+-----------------------+
                               |
                +--------------+-----------------------+
                |     ② AI 原理认知                     |
        基础认知 |     ③ 数据安全与隐私                   |
                |     ④ 工具形态适配                     |
                +---------------+-----------------------+
                               |
                +--------------+-----------------------+
        根基     |     ① 领域知识                        |
                +--------------+-----------------------+
                               |
                        ⑩ 持续迭代与学习（贯穿始终）
```

### 1.2 矩阵速查

| # | 维度 | 一句话定位 | 最大风险 | 强化周期 |
|:-:|:-----|:----------|:---------|:---------|
| ① | **领域知识** | 没有领域理解，AI 输出只是"看起来专业"的废话 | 外行指挥 AI 做内行事 | 长期积累 |
| ② | **AI 原理认知** | 知道它怎么工作，才知道怎么用它、不误会它 | 幻觉当成事实 / 当成全能神 | 一次打底 + 跟踪更新 |
| ③ | **数据安全与隐私** | 能用和能用的区别——数据红线不可碰 | 机密泄露 / 合规处罚 | 持续（制度+意识） |
| ④ | **工具形态适配** | 不同场景选不同工具（Chat/API/Agent/RAG） | 用锤子找钉子 | 按需切换 |
| ⑤ | **输出质量验证** | 类似代码走读——AI 产出必须经过人工审查链路 | 盲目信任 AI 输出 | 每次使用 |
| ⑥ | **需求工程与表达** | 说不清楚需求就得不到好结果——提示词的本质是需求文档 | 需求模糊→AI 瞎猜 | 刻意训练 |
| ⑦ | **批判性评估能力** | 识别 AI 的"自信胡说"——不谄媚、不轻信、反向质疑 | 被 AI 的逻辑漏洞带偏 | 每次使用 |
| ⑧ | **人机协作模式** | 知道什么时候该用 AI、什么时候该自己做 | 过度依赖→能力退化 | 持续优化 |
| ⑨ | **成本与效率意识** | AI 不是免费的——Token/API/延迟都是资源 | 不计成本乱用 | 定期审视 |
| ⑩ | **持续迭代与学习** | AI 在变、你的用法也要变（模型升级/工具演进/生态变化） | 停留在旧模式 | 月度更新 |

## 2. 领域知识（Domain Knowledge）

### 2.1 为什么是根基

AI 的本质是一个**强大的模式匹配器**，它不真正"理解"领域。同一个 prompt 给不同领域的人用，产出质量的天壤之别来自**人的领域判断力**。领域知识决定了：

- **需求输入的质量**: 只有懂的人才能给出准确的技术约束
- **输出鉴别力**: 只有专家才能识别 AI 的"专业废话"
- **创新转化**: 只有深耕者才能把 AI 的"组合建议"变成真创新

### 2.2 强化方法

| 方法 | 描述 | 频率 | 效果 |
|:-----|:-----|:----:|:----:|
| **深度阅读** | 读标准原文（PCIe Base Spec/IEEE 802.3/ODCC 白皮书）而非二手解读 | 每周 | ⭐⭐⭐⭐⭐ |
| **动手实践** | 非 AI-assisted 地亲手完成关键任务（如亲手写一个 RDMA 通信程序） | 每月 | ⭐⭐⭐⭐⭐ |
| **一页纸总结** | 学完一个概念后用一页纸讲清楚，再交给 AI 批判 | 每次学习 | ⭐⭐⭐⭐ |
| **跨域关联** | 把自己的领域知识和 AI 原理/互联/存储做关联映射 | 持续 | ⭐⭐⭐⭐ |

### 2.3 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **领域知识图谱** | 团队共同维护领域知识库（知识点 + 交叉链接 + 权威来源），形成"可训练 AI 的语料" |
| **师徒制 + AI** | 资深者用 AI 生成案例，新手在资深者指导下评审 AI 输出——既学领域又学 AI 使用 |
| **领域校验集** | 团队建立 50-100 个领域关键问题 QA 集，定期用新模型测试，看 AI 的领域能力是否提升 |
| **反转培训** | 让领域专家教 AI，同时让 AI 反问专家——暴露专家知道但没意识到的"默认知识" |

## 3. AI 原理认知（AI Principles）

### 3.1 必须理解的 6 个核心原理

| # | 原理 | 一句话 | 对使用的影响 |
|:-:|:-----|:-------|:------------|
| 1 | **Token 机制** | AI 看的是 Token 不是字，Token 数 = 算力/成本/上下文 | 知道为什么长文本贵、为什么中英文 Token 数不同 |
| 2 | **自回归生成** | 每次只预测下一个 Token，没有"回头看" | 长文本容易出现"写到后面忘了前面"——需要显式维护上下文 |
| 3 | **上下文窗口** | 模型只能看到固定长度的历史 Token | 超出窗口的内容丢失——需要 RAG/摘要/分段策略 |
| 4 | **注意力机制** | 模型"关注"输入的每个部分但权重不同 | 关键信息放在 prompt 开头/结尾更有效 |
| 5 | **训练-推理差异** | 训练是"选择题"（有标准答案），推理是"填空题"（无标准答案） | 推理阶段可能输出训练阶段从未见过的组合——幻觉 |
| 6 | **RLHF/对齐** | 模型被训练得"讨人喜欢"——说你想听的而非真相 | AI 的"自信"不等于"正确"——必须独立验证 |

### 3.2 强化方法

| 方法 | 描述 | 效果 |
|:-----|:-----|:----:|
| **做 Tokenizer 实验** | 在 GPT Tokenizer 网站上输一段中文/英文，看 Token 切分方式 | ⭐⭐⭐⭐ 直观理解 Token |
| **对比测试** | 同一个问题用不同模型/不同 prompt 风格试，观察输出差异 | ⭐⭐⭐⭐⭐ |
| **幻觉探测** | 让 AI 生成一段技术内容，逐句验证——建立"AI 不可全信"的本能 | ⭐⭐⭐⭐⭐ |
| **读论文摘要** | 读 Attention Is All You Need / InstructGPT 等关键论文的摘要 | ⭐⭐⭐ (一次打底) |

### 3.3 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **AI 原理 101 工作坊** | 2 小时的原理讲解 + 现场交互式 demo（Tokenizer/上下文窗口/幻觉演示） |
| **"AI 原理墙"** | 团队共享空间贴一张海报：Token 怎么切 / 上下文窗口限制 / 注意力模式可视化 |
| **每周一问** | 每周抛出一个 AI 使用中遇到的问题，用原理来解释为什么 |
| **反常识清单** | 整理"AI 最容易被误解的 20 个特性"作为团队入门必读 |

## 4. 数据安全与隐私（Data Security & Privacy）

### 4.1 分级管控矩阵

| 数据级别 | 定义 | 示例 | 可用 AI 工具 | 要求 |
|:---------|:-----|:-----|:------------|:------|
| **L0 公开** | 已公开或可公开 | 公开白皮书、开源代码、规格书 | 任何工具 | 无限制 |
| **L1 内部** | 公司内部但非敏感 | 内部架构文档（不含具体参数）、培训材料 | 内部部署的 AI | 不传外部 API |
| **L2 机密** | 产品级机密 | 芯片参数、BOM 成本、未公开架构、客户信息 | 私有化部署的 AI | 数据不出公司网络 |
| **L3 绝密** | 核心商业机密 | 战略规划、专利交底书初稿、竞对分析原始数据 | 本地离线 AI（纯推理） | 完全断网 |

### 4.2 常见违规场景 + 纠正方法

| 常见违规 | 风险 | 纠正 |
|:---------|:-----|:------|
| 把内部代码段贴到 ChatGPT 公共版 | 代码进入训练数据，竞对可能"学会" | 改用 API + 不记录模式，或内部部署 |
| 在 prompt 中输入真实客户名/IP | 可追溯到具体客户 | 一律脱敏：用"客户A"/"10.0.x.x" |
| 把设计文档传给在线 AI 总结 | 架构泄露 | 使用内部部署的文档 AI |
| 用 AI 生成专利交底书时输入全部技术细节 | 过早公开 | AI 生成框架后，人补机密细节，不交给 AI |

### 4.3 强化方法

| 方法 | 描述 |
|:-----|:------|
| **脱敏本能** | 把脱敏变成肌肉记忆——每次和 AI 交互前自动检查：有客户名吗？有 IP 吗？有具体金额吗？ |
| **最小信息原则** | 只给 AI 完成任务所需的最小信息，不提供多余背景 |
| **敏感词清单** | 团队维护一份常见敏感词/模式的清单（项目代号、真实 IP 段、客户名、成本数字） |
| **"假数据"模板** | 准备一套可用于 AI 交互的脱敏版数据/文档模板 |

### 4.4 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **安全红牌制度** | 发现违规不处罚、给红牌提醒——建立"安全第一，共享经验"的文化 |
| **AI 安全 checklist** | 每次使用 AI 前/后的检查清单（贴在显示器旁） |
| **数据分级标签** | 在文档/代码库头部打标签（PUBLIC/INTERNAL/CONFIDENTIAL），AI 工具自动识别 |
| **脱敏脚本工具** | 提供一个脱敏脚本，一键替换 prompt 中的敏感信息 |

## 5. 工具形态适配（Tool Form Adaptation）

### 5.1 五大形态及适用场景

| 形态 | 延迟 | 成本 | 可控性 | 最适合 | 最不适合 |
|:-----|:----:|:----:|:------:|:-------|:---------|
| **A: 聊天对话** | 1-5s | 低-中 | 低 | 头脑风暴、快速原型、知识问答 | 批处理、高频调用 |
| **B: API 调用** | 0.5-3s | 中-高 | 高 | 嵌入产品、自动化流程、批量任务 | 探索性、交互式任务 |
| **C: Agent/技能** | 5-30s | 中 | 中 | 多步骤任务、工具链编排、知识库集成 | 简单问答（杀鸡用牛刀） |
| **D: RAG/知识库** | 2-10s | 中 | 中-高 | 事实查询、文档分析、专业知识问答 | 创造性写作、推理 |
| **E: 本地模型** | 0.5-30s | 低(硬件投) | 最高 | 敏感数据、离线场景、延迟敏感 | 顶级推理能力需求 |

### 5.2 选型决策树

```text
数据是机密？
+- 是 -> 本地模型 or 内部 API
+- 否 ->
    任务需要实时交互？
    +- 是 -> 聊天对话
    +- 否 ->
        任务是多步骤/需要自动执行？
        +- 是 ->
        |   需要查知识库？
        |   +- 是 -> Agent + RAG
        |   +- 否 -> API 调用
        +- 否 -> API 调用或聊天
```

### 5.3 强化方法

| 方法 | 描述 |
|:-----|:------|
| **形态对比实验** | 同一个任务用 3 种形态做，记录耗时/质量/成本差异 |
| **场景工具箱** | 列出自己日常 10 个高频场景，给每个场景匹配最优形态 |
| **"降维打击"检测** | 定期反问自己：是不是用了复杂的 Agent 做一件 Chat 就能搞定的事？ |

### 5.4 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **工具形态速查表** | 团队制作一页纸的形态对比+选型清单 |
| **场景-工具映射** | 团队梳理 20-30 个典型场景，给出明确的工具推荐 |
| **形态升级路径** | 新手先用聊天掌握能力→过渡到 API 自动化→进阶到 Agent 编排 |
| **成本看板** | 展示各形态的成本对比（Token 消耗/API 费用），促进理性选型 |

## 6. 输出质量验证（Output Quality Validation）

### 6.1 AI 输出的"四道质检关卡"

类似代码走读的四阶段评审：

| 关卡 | 类比 | 验证内容 | 耗时占比 |
|:-----|:-----|:---------|:--------|
| **L1: 格式合理性检查** | lint | 格式对不对？结构对不对？引用格式对不对？ | 5% |
| **L2: 逻辑一致性检查** | 单元测试 | 前后矛盾吗？数字自洽吗？因果关系成立吗？ | 20% |
| **L3: 事实准确性检查** | 代码评审 | 断言有出处吗？数据有基线/条件吗？与已知事实冲突吗？ | 50% |
| **L4: 专业判断检查** | 架构审查 | 方案可行吗？有更好的做法吗？隐含了什么假设？ | 25% |

### 6.2 每个场景的验证策略

| 场景 | L1 | L2 | L3 | L4 | 验证工具/方法 |
|:-----|:--:|:--:|:--:|:--:|:--------------|
| **写代码/脚本** | ✅ | ✅ | ✅ | ✅ | 编译+静态分析+单元测试+安全审查 |
| **写技术文档** | ✅ | ✅ | ✅ | ✅ | Markdown lint + 交叉检查 + 专家评审 |
| **写分析报告** | ✅ | ✅ | ✅ | ✅ | 来源可追溯 + 数据可验证 + 同行评审 |
| **写邮件/周报** | ✅ | ✅ | ❌ | ❌ | 快速阅读即可 |
| **头脑风暴** | ❌ | ✅ | ❌ | ✅ | 筛选+组合+批判 |
| **翻译/润色** | ✅ | ❌ | ❌ | ❌ | 双语对照 |

### 6.3 常见 AI 错误模式 + 应对

| 错误模式 | 表现 | 应对方法 |
|:---------|:-----|:---------|
| **自信编造** | 给出看似专业的假数据/假引用 | 逐项验证：所有数字要来源，所有引用要可查 |
| **中间结论漂移** | 开头说 A、结尾说 B，中间没有逻辑桥梁 | 要求 AI 输出推理链（cot），检查每一步 |
| **过度简化** | 把复杂问题压缩成"主要因为 X"的单一归因 | 要求 MECE 分解，检查是否遗漏重要因素 |
| **谄媚迎合** | 顺着用户说的方向论证，不提反对意见 | 要求 AI 先给反对意见（"列出 3 个可能出错的地方"） |
| **术语不正** | 用词看起来专业但意思不准确 | 用自己领域的术语来要求，检查关键定义 |
| **基线缺失** | 只说数值不提对比基线 | 要求每个断言附带对比条件 |

### 6.4 强化方法

| 方法 | 描述 |
|:-----|:------|
| **"找茬"训练** | 故意给 AI 一个错误前提，看它是否发现——训练不盲信的本能 |
| **交叉验证** | 同一个问题问两个不同模型，比较差异 |
| **反向验证** | 让 AI 自己给自己挑错（"指出上述回答的 3 个弱点"） |
| **验证清单** | 每次使用后快速过 5 项：出处？自洽？完整？可操作？有偏见？ |

### 6.5 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **AI 输出评审模板** | 制作标准化的 AI 输出评审模板（含 4 个关卡 + 检查项） |
| **AI 错误案例库** | 团队收集真实的 AI 犯错案例，分类整理（供新成员学习） |
| **"敢质疑"文化** | 公开表扬找出 AI 错误的人——把找 AI 问题变成团队荣誉 |
| **验证自动化** | 对常见场景（代码/文档）建立自动化的验证脚本（单元测试/格式检查/引用验证） |

## 7. 需求工程与表达（Requirement Engineering）

### 7.1 提示词的本质是需求文档

AI 没有"常识判断"——你说得越模糊，它猜得越离谱。写好 prompt 和写好需求文档是同一套能力：

```text
普通问题: "写个函数排序" -> AI 猜你用冒泡排序 -> 你不满意 -> 循环 5 轮
好的需求: "写一个对 10 万条记录按时间戳降序排序的函数，用 Timsort，内存 < 50MB"
                   -> 一次到位
```

### 7.2 "五要素"提示词框架

| 要素 | 问题 | 示例 |
|:-----|:-----|:------|
| **角色** | 让 AI 以什么身份做？ | "你是一个服务器系统架构师" |
| **任务** | 具体要做什么？ | "设计一个 KV Cache 分层存储方案" |
| **约束** | 有哪些限制条件？ | "使用 JBOF 方案，带宽 ≤400G，延迟 ≤1ms" |
| **格式** | 输出要什么格式？ | "表格对比三个方案，附推导公式和理论值" |
| **质量** | 验收标准是什么？ | "每个数值标注来源和假设条件，不自洽数据用 ❓ 标记" |

### 7.3 常见需求表达缺陷

| 缺陷 | 表现 | 改进 |
|:-----|:-----|:------|
| **模糊不清** | "分析一下这个问题" | "从成本、性能、可维护性三个维度分析" |
| **缺少约束** | "写一个数据处理的代码" | "处理 1TB JSON 数据，内存≤16GB，耗时≤30min" |
| **隐藏假设** | "用最好方案" | "最好"的定义是什么？成本最优？延迟最优？维护最优？ |
| **一次太多** | "帮我设计整个系统" | 拆分：先设计架构 → 再细化模块 → 再写代码 |
| **缺少示例** | "就用标准方式" | 给一个具体的输出示例让 AI 对齐 |

### 7.4 强化方法

| 方法 | 描述 |
|:-----|:------|
| **"一锤子"训练** | 要求自己一次写完整的 prompt，不经过 AI 反问就达到 80% 满意的效果 |
| **需求文档练习** | 把写 prompt 当成写需求文档来训练——先写草稿再发给 AI |
| **预反转** | 在 prompt 中主动加入"你可能犯的错误有：1）... 2）... 请避免" |
| **多角度表达** | 同一个需求用 3 种不同的方式表达，观察差异 |

### 7.5 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **提示词模板库** | 团队积累每个场景的标准化 prompt 模板（含五要素） |
| **Pair Prompting** | 两个人一起写 prompt——一个人提需求、一个人扮演 AI 理解需求，暴露歧义 |
| **提示词评审** | 像代码评审一样评审重要场景的 prompt |
| **A/B 测试** | 同一任务用两个不同 prompt 版本，比较输出质量 |

## 8. 批判性评估能力（Critical Evaluation）

### 8.1 "不谄媚协议"——使用 AI 的底层态度

AI 被训练得**讨人喜欢**——它会顺着你的观点说、不会主动指出你的错误、会编造看起来合理的假数据。对抗这一点的唯一方法是建立**本能性的批判态度**：

```text
✅ 正确的使用态度:
"AI 是一个知识面极广但判断力为零的实习生——
   它可以在 1 秒内读完整个互联网，
   但它需要你的判断来决定什么是正确的。"

❌ 错误的使用态度:
"AI 比我懂得多，它的输出应该是对的。"
```

### 8.2 批判性检查清单

每次看完 AI 输出，过一遍：

| 检查项 | 问题 | 高频风险 |
|:-------|:-----|:---------|
| **来源** | 数据/事实有出处吗？出处可查吗？ | 编造引用 ✅ XSS |
| **自洽** | 文内前后一致吗？数字自洽吗？ | A 段说 100，B 段说 200 |
| **边界** | 结论有适用条件吗？是否过度外推？ | "AI 将取代所有工程师" |
| **反例** | 有没有已知的反例或例外？ | 通则不适用于边缘情况 |
| **粒度** | 是否过于笼统？是否需要更细的分解？ | "提升性能"——提高了多少？哪些场景？ |
| **偏见** | 是否只呈现了一面？有没有隐藏立场？ | 只说优点不说代价 |
| **时效** | 信息是哪个时间点的？是否已过时？ | 模型知识截止日期之前的信息 |

### 8.3 强化方法

| 方法 | 描述 |
|:-----|:------|
| **"魔鬼代言人"训练** | 每次看完 AI 输出，先强制自己找出 3 个问题，再考虑优点 |
| **事实验证练习** | 随机抽取 AI 输出中的 3 个断言，用搜索引擎/知识库验证 |
| **跨模型对比** | 同一问题问两个不同模型，对比差异点，分析哪个更可信 |
| **假设挖掘** | 要求 AI 列出"我做出这个结论隐含的 5 个假设"，然后自己质疑这些假设 |

### 8.4 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **AI 输出评审制度** | 将 AI 输出纳入评审流程（代码/文档/报告），设"AI 生成"标签 |
| **批判性评估训练** | 每月一次"挑 AI 错误"比赛——用同一段 AI 输出，谁找出最多问题 |
| **"错误热力图"** | 统计团队使用 AI 中最常出现的错误类型，集中培训 |
| **信任度分级** | 建立 AI 输出可信度分级（✅ 已验证 / 🟡 待验证 / ❓ 未验证） |

## 9. 人机协作模式（Human-AI Collaboration）

### 9.1 四象限模型——什么时候该用 AI

```text
                    对准确性要求
                    高
              +-----------+-----------+
              |           |           |
        低    |  AI 主导  |  人主导    |
        复杂度|  头脑风暴  |  核心设计  |
              |  格式转换  |  关键决策  |
              |  初始草稿  |  最终审批  |
              +-----------+-----------+
              |           |           |
        高    |  AI 主力  |  人机协同  |
        复杂度|  批量处理  |  代码生成  |
              |  数据清洗  |  分析报告  |
              |  常规问答  |  架构设计  |
              +-----------+-----------+
                    低
```

| 象限 | 人机分工 | 典型场景 | AI 角色 | 人角色 |
|:-----|:---------|:---------|:--------|:-------|
| **AI 主导/低复杂低准确** | AI 全做 | 翻译/格式化/简单搜索 | 执行者 | 监督者 |
| **AI 主力/高复杂低准确** | AI 框架 + 人调优 | 文档初稿/代码框架/数据分析 | 实习生 | 导师 |
| **人主导/低复杂高准确** | 人做 + AI 辅助 | 关键决策/架构定稿/合同签署 | 助手 | 决策者 |
| **人机协同/高复杂高准确** | 人机迭代 | 架构设计/方案评审/问题诊断 | 协作者 | 负责人 |

### 9.2 常见协作反模式

| 反模式 | 表现 | 问题 | 正模式 |
|:-------|:-----|:-----|:-------|
| **甩手掌柜** | "AI 帮我全做了" | 失去判断力，AI 错了也不知道 | 自己先想框架，AI 填充细节 |
| **完美主义** | "AI 写的不够好，我自己重写" | 效率没有提升 | 用 AI 产出 80%，人优化 20% |
| **指令狂魔** | 反复修改 AI 输出直到满意 | 修改时间 > 自己写的时间 | 一次给高质量 prompt，而非反复修 |
| **过度依赖** | 每行代码都要 AI 写 | 能力退化，失去 debug 能力 | 关键/复杂逻辑自己写，常规交给 AI |

### 9.3 强化方法

| 方法 | 描述 |
|:-----|:------|
| **时间记录法** | 记录每次任务的 AI 用时 vs 纯手作用时，找到最优分工点 |
| **"不用 AI"日** | 每周固定时段强制自己手写/手算，保持基本功不退化 |
| **协作复盘** | 完成一个任务后复盘：AI 帮了什么？哪里帮了倒忙？下次怎么调整？ |
| **退化预警** | 当发现自己离开 AI 就无法完成某类基础任务时，说明已过度依赖 |

### 9.4 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **人机分工 SOP** | 每个岗位/角色定义明确的"AI 可做清单"和"人必做清单" |
| **AI 能力地图** | 团队梳理 AI 在研发各环节（需求→设计→编码→测试→部署→运维）的能力水平 |
| **任务-协作匹配** | 分类常见任务到四象限，给出标准化协作流程 |
| **基本功考核** | 定期在无 AI 辅助条件下考核核心技能（防止退化） |

## 10. 成本与效率意识（Cost & Efficiency）

### 10.1 AI 使用的成本构成

| 成本项 | 说明 | 度量单位 | 典型范围 |
|:-------|:-----|:---------|:---------|
| Token 消耗 | 输入+输出的 Token 量 | Token / 任务 | 100-100K+ |
| API 费用 | Token 消耗 × 单价 | $ / 任务 | $0.001-1+ |
| 延迟成本 | 等待 AI 响应的时间 | 秒 / 任务 | 1-30s |
| 验证成本 | 审核 AI 输出的人工时间 | 分钟 / 任务 | 1-30min |
| 试错成本 | 不合格输出的重做 | 轮次 / 任务 | 1-5 轮 |
| 集成成本 | 将 AI 接入工作流 | 人天 / 集成 | 0.5-5 天 |

### 10.2 成本优化策略

| 策略 | 说明 | 效果 |
|:-----|:------|:----:|
| **精简 prompt** | 去掉不必要的历史记录和示例，缩短输入 Token | 20-50% 成本下降 |
| **批量处理** | 多个任务合并到一个请求 | 30-60% 成本下降 |
| **模型分层** | 简单任务用小模型（如 DeepSeek-lite），复杂用大模型 | 50-90% 成本下降 |
| **缓存复用** | 对重复问题缓存 AI 输出 | 极显著 |
| **先想后问** | 先自己思考框架，只把难点/不确定的部分给 AI | 30-50% |

### 10.3 强化方法

| 方法 | 描述 |
|:-----|:------|
| **Token 意识** | 建立对不同任务 Token 消耗的直觉（一页 A4 ≈ 500 Token） |
| **成本计数器** | 使用带 Token 计数的工具，每次看到实际消耗 |
| **ROI 评估** | 完成任务后估算 AI 成本 vs 节省的时间，看是否合算 |
| **"值不值"判断** | 用 AI 前先问：这个问题值不值花这个 Token/钱？ |

### 10.4 迁移方法（团队/组织）

| 迁移方式 | 操作 |
|:---------|:-----|
| **成本看板** | 展示团队的 AI 工具使用成本趋势（按人/按场景/按模型） |
| **场景预算** | 为每个场景设 Token 预算（如"一次代码生成≤5K Token"） |
| **成本评审** | 每月回顾一次 AI 使用成本，找浪费场景 |
| **模型选型** | 每周测试新模型（本地/第三方），对比性价比 |

## 12. 综合能力成熟度模型

### 12.1 五级成熟度

| 级别 | 名称 | 特征 | 示例表现 |
|:-----|:-----|:------|:---------|
| **L1 好奇者** | 刚刚接触 | 用聊天工具偶尔问问题，输出质量不稳定 | "帮我写个 Python 脚本" |
| **L2 使用者** | 可以完成简单任务 | 能写基本 prompt，会用 1-2 种形态 | "用 API 做批量翻译" |
| **L3 实践者** | 独立完成复杂任务 | 掌握 3+ 形态，能设计 prompt、验证输出 | "用 Agent 做知识库问答" |
| **L4 赋能者** | 可以教别人 | 理解原理，能设计团队规范和工作流 | "为团队设计 AI 使用 SOP + 模板" |
| **L5 进化者** | 持续引领变革 | 跟踪前沿，能判断 AI 边界并创新使用 | "设计 AI 原生工作流，改变研发范式" |

### 12.2 十维度成熟度评估矩阵

| # | 维度 | L1 好奇者 | L3 实践者 | L5 进化者 |
|:-:|:-----|:---------|:---------|:---------|
| ① | 领域知识 | 能描述问题 | 能验证 AI 输出 | 能教 AI 领域知识 |
| ② | AI 原理 | 知道"AI 会编造" | 理解 Token/注意力/对齐 | 能预测模型行为 |
| ③ | 数据安全 | 知道不能传机密 | 自动脱敏/分级使用 | 制定安全规范 |
| ④ | 工具形态 | 只用聊天 | 3+ 形态切换 | 设计专用工具链 |
| ⑤ | 质量验证 | 凭直觉判断 | 用验证清单 | 建立自动化验证 |
| ⑥ | 需求表达 | 模糊问题 | 五要素框架 | 模板化+评审 |
| ⑦ | 批判评估 | 全信或全不信 | 识别常见错误 | 预测错误模式 |
| ⑧ | 协作模式 | AI 全做或全不做 | 四象限分工 | 人机协同设计 |
| ⑨ | 成本意识 | 不知道成本 | 知道 Token 消耗 | 成本优化体系 |
| ⑩ | 持续迭代 | 等别人教 | 主动学习 | 建立学习机制 |
