## 核心理念

**AI 的核心价值在于提供思路框架和生成骨架**——帮你快速搭出报告结构、代码框架、材料初稿。但最终的成品质量，取决于使用者的**领域功底**和**判断力**。

## 三个必备能力

| 能力 | 说明 | 类比 |
|:----|:-----|:-----|
| **想法与路径规划** | 知道自己要什么，能拆解目标，给 AI 清晰的方向 | 实验方案设计 |
| **验证能力** | 能对 AI 的输出做事实核查、逻辑校验、数据验算 | 实验过程监控 |
| **评判标准** | 有自己的质量标尺，能判断"好不好""对不对""够不够" | 实验结果判定 |

## 核心类比：AI 如实验室仪器

> AI 像一台**大型精密仪器**（比如电子显微镜、质谱仪、核磁共振）：
>
> - 不用它，永远不知道它的能力边界
> - 要**争取使用**才能用熟用好
> - 但要**理解原理**才能调对参数，否则测出的数据是错误的
> - 机器给出原始数据/图谱后，**需要人来解读**——没有领域知识就看不懂、判不准
> - **错误使用同样产生报告**，但报告可能全是错的，却不自知

这个类比揭示了 AI 工具使用的三重门槛：

1. **使用意愿** — 主动去用、多场景尝试，才能积累手感
2. **原理理解** — 知道 AI 擅长什么、不擅长什么、在什么条件下容易出错
3. **结果鉴别** — 对输出保持批判性，不盲信、不盲从

## 实践原则

| 原则 | 具体做法 |
|:----|:---------|
| **先想后问** | 自己先想清楚目标框架，再让 AI 填充细节 |
| **逐段验证** | 不要一次性让 AI 生成全部内容，分段生成、分段审查 |
| **追问原理** | 存疑的地方追问 AI 推理依据，追溯判断链条 |
| **保持批判** | AI 的"自信"不等于"正确"，反复交叉验证 |
| **积累手感** | 用得越多越能预判 AI 的输出质量，越快识别偏差 |

## 约束失效的三个独立维度

> **核心洞见**: AI 使用中的大部分问题不是单一根源，而是三个不同维度的失效叠加。
> 此前只深挖了一个维度，漏了另外两个同样致命的维度。

本工作空间在长期实践中识别出三类截然不同的 AI 失效模式——它们的**根本原因、表现形态、应对策略**完全不同：

| # | 失效维度 | 本质 | 通俗表述 | 类比 | 覆盖状态 |
|:-:|:---------|:-----|:---------|:-----|:--------:|
| **I** | **约束忽略** | 该做的没做 | 说了它做不到 | 员工不遵守公司政策 | ✅ 已深挖 |
| **II** | **方向锁定** | 不该做的做了 | 被带偏走到底 | 员工过度执着于老板随口一句话而忽视全局 | ❌ 新增 |
| **III** | **输入污染** | 基础就不对 | 吃垃圾吐垃圾 | 用错误数据做分析报告 | ❌ 新增 |

**三者 MECE**:

- **约束忽略**是"**信号衰减**"问题——约束信号在注意力噪声中被淹没。模型**知道**要求但**做不到**。
- **方向锁定**是"**信号过强**"问题——prompt 中某个方向的信号压制了所有其他信号。模型**做到了**但**做过了头**。
- **输入污染**是"**信源质量**"问题——信号本身就不对。模型无关——源头错了后面全错。

三者互斥且穷尽——任何 AI 输出质量问题，要么是输出端约束未被遵守 (I)，要么是过程中过度偏向某一方向 (II)，要么是输入端基础就错了 (III)。三者可以同时发生（实际上经常叠加）。以下逐维度展开。

---

### I 维度：约束忽略——该做的没做

> **关键认知**: 给 AI 的约束文件（AGENT.md、RULE.md、skill 指令等）只是提示词层面的"软约束"——
> 模型**不会严格执行**，在 token 压力、上下文偏移、模型版本更替等条件下随时可能失效。
>
> 这是 LLM 的**内生缺陷**——不是 bug，而是架构特性。

### 为什么约束会失效？从模型原理出发

| 失效根因 | 机制 | 典型触发场景 |
|:---------|:-----|:------------|
| **注意力衰减** | 约束在 prompt 最前面，随着对话展开（系统消息+多轮交互），注意力从早期 token 向近期 token 偏移 | 长对话后段，行为明显偏离初始设定 |
| **token 优先级竞争** | 模型天然优先响应"紧急性"指令（用户最新问题）而非"重要性"指令（规则文件） | 用户催进度时，AI 跳过质量检查直接出结果 |
| **指令层次模糊** | 系统提示词 vs user message vs skill 文件无硬性优先级区分，同层指令可能冲突 | Skill 指令与 AGENT.md 说法不一致时，模型自行"调和" |
| **模型先验压倒后验** | 预训练形成的语言习惯（如"首先总结"）强于约束文件中的反向要求（如"先给结论"） | 约束要求"先结论再展开"，但模型仍从背景介绍开始 |
| **版本漂移** | 同一 prompt 在不同模型版本推理路径不同，约束效果不可复现 | 模型升级后，原本有效的约束开始被忽略 |
| **复杂任务退化** | 任务越复杂（长文档/多步骤/高认知负荷），模型越倾向于走"默认路径"而非"约束路径" | 写长报告时格式约束、方法约束依次失效 |
| **注意力坍缩** | 超长上下文中，中间部分的约束被模型"遗忘"——Attention 在长序列中信息密度坍缩 | 100K+ 上下文中，第50K处的约束完全失效 |

这些不是罕见异常，而是**日常高频发生**的。使用约束文件时默认它们会部分失效，而非默认它们会被遵守。

### 从架构第一性原理看约束失效必然性

上述 7 种失效模式不是 bug，而是 Transformer 架构的必然产物。以下从模型架构的底层机制解释"为什么必然如此"。

#### 1. 注意力衰减的数学根源

Self-Attention 的计算公式：

$$Attention(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

当序列长度 $n$ 增加时，第 $i$ 个 token 对第 $j$ 个 token 的注意力权重为：

$$\alpha_{ij} = \frac{\exp(q_i \cdot k_j / \sqrt{d_k})}{\sum_{t=1}^n \exp(q_i \cdot k_t / \sqrt{d_k})}$$

**关键问题**：分母是 $n$ 项的和。当 $n$ 增大时，分母增大 → 每个 $\alpha_{ij}$ 被稀释。更严重的是，对于固定位置 $j=1$（约束文件所在位置），其注意力权重随 $n$ 增加呈 $\sim O(1/n)$ 衰减：

| 序列长度 | 约束 token 相对注意力 | 约束效力 |
|:--------:|:--------------------:|:--------:|
| 4K (短对话) | ~1.5% | ✅ 相对有效 |
| 16K (中等对话) | ~0.4% | ⚠️ 开始衰减 |
| 32K (长对话) | ~0.2% | ❌ 显著衰减 |
| 128K+ | ~0.05% | ❌ 几乎消失 |

> 参考：Vaswani et al., *Attention Is All You Need*, 2017, §3.2.1

**RoPE 位置编码加剧问题**：当前主流模型（LLaMA/DeepSeek/Qwen）使用 RoPE 旋转位置编码（Su et al., 2021）。RoPE 将位置信息编码到 Q/K 的旋转矩阵中，使得：

- 近端 token 对（距离短）的注意力分数自然高于远端 token 对
- 约束文件（位置 0-1000）与用户最新问题（位置 30000+）的 RoPE 距离约为 29000+
- 二者的点积衰减因子为 $\cos(\theta \cdot 29000)$，其中 $\theta$ 随维度指数衰减
- 在大维度上的旋转角度累积 → 远端信息的正弦/余弦值呈现伪随机振荡

这意味着**约束文件在数学上处于注意力的"远端死角"**——不是模型"不听话"，而是注意力分布中最活跃的区域天然偏向于近期输入。

> 来源：Su et al., *RoFormer: Enhanced Transformer with Rotary Position Embedding*, 2021, arXiv:2104.09864

#### 2. Softmax 的"赢者通吃"加剧近因偏差

Softmax 函数 $\sigma(z_i) = e^{z_i} / \sum e^{z_j}$ 具有指数放大特性。在注意力分数分布中：

- 近期 token 的 Q-K 内积通常更大（因为 RoPE 近距优势 + 上下文连贯性）
- Softmax 将这些差距指数放大 → 近期 token 拿到绝大部分注意力权重
- 位置 0 的约束 token 即使有不低的原始点积分数，经过 Softmax 后也被极低概率稀释

**实测效应**：Anthropic 在 2024 年的研究中发现，当上下文超过 8K tokens 时，prompt 最早 10% 的 token 的注意力总和中位数从 ~15% 降至 ~3%（Anthropic, *Interpretability in the Wild*, 2024）。这一效应不是偶发，而是 softmax 指数竞争的必然输出。

#### 3. RLHF/Post-training 为何也不能解决约束遵循

RLHF 或 DPO 等对齐训练（Ouyang et al., 2022; Rafailov et al., 2023）被设计用于让模型产生"有用且无害"的回答，但**不解决注意力分布问题**：

| 对齐方法 | 优化目标 | 对约束遵循的影响 | 局限性 |
|:---------|:---------|:-----------------|:-------|
| **SFT** (监督微调) | 模仿高质量回答 | 学会在训练数据分布上遵循简单指令 | 对未见过的约束格式不泛化 |
| **RLHF** (强化学习) | 最大化奖励模型打分 | 优化"表面合规"——让回答看起来遵循了约束 | 奖励模型本身也是神经网络，有同样盲区 |
| **DPO** (直接偏好优化) | 直接优化偏好对 | 在偏好分布上提升遵从度，但偏好数据本身就是有偏的 | 偏好标注者倾向于偏好"安全"而非"精确遵守"的回答 |

**根本原因**：对齐训练不改变 Transformer 的注意力计算方式——它只是微调了参数在特定数据分布上的响应模式。当输入分布（长上下文、复杂约束、高认知负荷）偏离训练分布时，参数恢复到预训练的行为模式。

这解释了为什么同一个 prompt 在不同上下文长度下的表现不同——不是模型"选择性遗忘"，而是约束遵循行为本质上依赖于注意力权重分配，后者随 token 位置和序列长度动态变化。

> 来源：Ouyang et al., *Training language models to follow instructions with human feedback*, NeurIPS 2022 (InstructGPT)
> 来源：Rafailov et al., *Direct Preference Optimization: Your Language Model is Secretly a Reward Model*, NeurIPS 2023

#### 4. 语言建模的本质与约束遵循的根本矛盾

LLM 的核心任务（预训练目标）是：

$$P(x_t | x_1, ..., x_{t-1}) = \text{softmax}(W \cdot h_t)$$

即**预测下一个 token**。约束遵循（如"先给结论再展开"）是一种**元任务**——它修改生成策略，但不改变预测能力。这意味着：

- 模型必须**同时优化两个目标**：① 预测合理的下一个 token（语言能力）；② 按照约束的格式生成（元能力）
- 当两个目标冲突时（如：认知负荷高时，预测准确率优先），模型自然选择**主要目标**（语言能力）而放弃**元目标**（格式约束）
- 这就是"复杂任务退化"的数学根源——认知负荷挤出了元能力

**与人类类比**：让一个人遵守"说话前先深呼吸"的规则。平时可以做到，但在紧张演讲、紧急情况下就会忘记。这不是"不遵守规则"，而是执行控制资源被主任务抢占。

> 参考：Kahneman, *Thinking, Fast and Slow*, 2011 — 系统1（自动） vs 系统2（受控）的认知资源竞争

### 信息论视角：约束遵循的信道容量模型

上述四种架构层面的约束失效，可以统一为 **信息论中的通信信道模型**。这一视角将约束问题从"模型会不会遵守"的工程问答，提升为"信息能否可靠通过噪声信道"的数学问题。

#### 约束作为通过噪声信道的信息

将约束文件的传递视为一个通信系统：

```text
约束文件（信源）-> Tokenization（编码）-> Position Encoding + Attention（信道）-> Softmax 加权（噪声叠加）-> Autoregressive Generation（解码）-> 输出（信宿）
```

Shannon-Hartley 定理给出了信道容量的上界：

$$C = B \cdot \log_2(1 + \text{SNR})$$

其中 $C$ 是信道容量（bits/s），$B$ 是带宽，SNR 是信噪比。映射到约束遵循问题：

| 通信系统元素 | LLM 约束场景 | 退化的物理机制 |
|:------------|:-------------|:--------------|
| **信源** | 约束文件（AGENT.md / RULE.md / Skill 指令） | — |
| **编码** | Tokenizer 将约束转为 token ID 序列 | Token 化损失（分词粒度不当丢失约束语义） |
| **信道** | Transformer 的自注意力层 | RoPE 位置编码导致远端信号衰减 → SNR 随 token 位置指数下降 |
| **噪声源** | 用户最新输入 + 历史对话 token | 用户指令的注意力权重天然高于系统消息 → 干扰信号功率远大于信号功率 |
| **信噪比 (SNR)** | 约束 token 注意力权重 / 其他 token 注意力权重 | 序列每增长 2×，约束的 SNR 大约下降 3dB (softmax 稀释) |
| **带宽 (B)** | 模型 hidden_dim / 注意力头数 | 固定值，不可调节 |
| **信道容量 (C)** | 每生成步骤能通过的约束信息量的理论上限 | 容量与 SNR 对数相关 → SNR 下降时容量快速坍缩 |

**定量推演**：假设初始 SNR 为 10dB（约束在 prompt 开头时占注意力分布的 ~10%），序列扩展到 32K tokens 后 SNR 降至约 -3dB：

- 初始状态：$C_1 = B \cdot \log_2(1 + 10) \approx B \cdot 3.46$，约束信息可有效通过
- 32K 后：$C_2 = B \cdot \log_2(1 + 0.5) \approx B \cdot 0.58$，信道容量下降 **83%**
- 128K 后：SNR 进一步降至约 -10dB → $C_3 \approx B \cdot 0.14$，容量仅为初始的 **4%**

这意味着约束文件中的信息**在数学上无法完整通过信道到达生成阶段**。这不是模型训练不足，而是信息论的基本限制——信道容量低于信息传输所需的最低速率。

#### 抗干扰编码与约束增强策略

通信系统通过**信道编码**（如 Turbo 码、LDPC 码）在噪声信道中可靠传输信息。类似地，约束工程存在对应的抗干扰策略：

| 通信技术 | LLM 约束中的对应 | 效果 |
|:---------|:-----------------|:-----|
| **重复编码**（重复发送相同信息） | 约束在 prompt 中多次强调 | 提高冗余度，但受限于注意力集中效应 |
| **纠错编码**（添加校验位） | Check 机制（三态判定、证据闸门） | 在输出端纠正传输错误，是最有效的策略 |
| **扩频**（将信号扩展到更宽频带） | 约束分散到 prompt 多处 + skill 文件中 | 部分对抗注意力坍缩，但增加 token 消耗 |
| **分集接收**（多个独立路径接收） | 交叉审查（doc-reviewer + 独立实例） | 打破同源盲区，但代价是 2× token |
| **反馈重传**（ARQ） | 约束后的自检 + 修正循环 | 可靠性高，但需要多轮交互 |

**核心推论**：无需试图让单次传输的 SNR 足够高（这在长上下文中数学上不可能），而应采用**信道编码策略**——通过冗余、纠错、分集和反馈来在输出端恢复信息。

> 参考：Shannon, *A Mathematical Theory of Communication*, Bell System Technical Journal, 1948
> 参考：MacKay, *Information Theory, Inference, and Learning Algorithms*, Cambridge University Press, 2003

### II 维度：方向锁定——不该做的做了

> **核心命题**: 方向锁定（Prompt-induced Fixation）是比约束忽略更难感知的失效——约束忽略时你看得见"没做到"，方向锁定是输出很漂亮但路走窄了。
> **被带偏往往比被忽略更难发现**，因为输出本身看起来很好、很自洽——只是视角少了、方向偏了、替代方案被过滤了。

---

#### 方向锁定的心理学基础

方向锁定不是 AI 的专属问题——它在人类认知中有深远的渊源，AI 的 Transformer 架构只是再现了这一缺陷的不同形式。

**人类认知中的对应现象**：

| 现象 | 提出者 | 核心定义 | AI 对应机制 |
|:-----|:-------|:---------|:-----------|
| **确认偏误**（Confirmation Bias） | Bacon 1620 / Nickerson 1998 | 倾向于搜索、解释、回忆支持已有假设的信息 | prompt 方向信号 → attention 偏向匹配信息 |
| **锚定效应**（Anchoring Effect） | Tversky & Kahneman 1974 | 初始信息对后续判断产生不成比例的影响 | prompt 首部/最近的强导向性表述锚定输出方向 |
| **隧道视野**（Tunnel Vision） | Janis 1982 | 过度聚焦单一目标导致忽视其他重要因素 | attention 集中在方向相关 token → 其他信号被压制 |
| **框架效应**（Framing Effect） | Tversky & Kahneman 1981 | 同一问题不同表述方式导致不同决策 | 提示词的措辞预设了输出框架 |

**关键洞察**: AI 不是比人类更少偏误——而是以**不同方式**再现了同样的认知偏误。人类的确认偏误是动机驱动的（想要相信），AI 的方向锁定是统计驱动的（概率路径越走越窄）。

---

#### 从 Transformer 架构看方向锁定的必然性

方向锁定在 Transformer 中的发生机制，与约束忽略是对称的——后者是约束信号被衰减，前者是方向信号被放大。

**机制 1：注意力放大循环**

```text
第1层 --> prompt中的方向词"A"获得略高的注意力权重
 v
第2层 --> 方向A相关的token经过残差流后激活更强
 v
第3层 --> 方向A相关的路径获得更多梯度，替代方案B/C的注意力被softmax分母压缩
 v
深层 --> 方向A形成"注意力聚集"(attention sink)，B/C的注意力权重趋近于零
```

数学表达：设方向 A 的语义信号为 $s_A$，替代方向 B 的语义信号为 $s_B$。在 layer $l$:

$$w_A^{(l+1)} = \text{softmax}(Q^{(l)} \cdot K_A^{(l)}) > w_A^{(l)} \quad \text{if } s_A > s_B + \Delta$$

其中 $\Delta$ 是初始化后的随机差距。一旦 $w_A > w_B$，softmax 的分母共用的性质使差距在每一层**放大而非缩小**：$w_A^{(l+1)} - w_B^{(l+1)} > w_A^{(l)} - w_B^{(l)}$。

这本质上是一个**正反馈放大系统**——只要初始条件略有偏向，系统就会沿着该方向自增强。它与约束忽略中"信号被噪声淹没"的机制正好对称。

**机制 2：残差流的路径依赖**

残差流（residual stream）是每一层的公共信息通道。当方向 A 的激活在残差流中累积后：

- 后续层的 attention Q/K 投影以残差流为输入 → 方向 A 的语义占主导
- 即使后文有方向 B 的约束，其在残差流中的占比已经被稀释
- 最终输出由残差流中占主导的信号决定

这解释了为什么**同一 prompt 中既有一个明确方向又有"同时考虑其他角度"的约束时，模型总是优先走向明确方向**——两者在残差流中的竞争不是平等的：具体方向有连续 N 层的累积支持，抽象约束只在约束语句处有一层激活。

**机制 3：Softmax 的赢者通吃**

方向锁定比约束忽略更容易发生的原因在 softmax 的非线性特性：

| 场景 | 信号强度 | 差距 | softmax 结果 |
|:-----|:---------|:-----|:------------|
| 约束忽略 | 约束信号 0.3，噪声 0.25 | 差距 +0.05 | 约束略占优但易被翻转 |
| 方向锁定 | 方向A 0.5，方向B 0.1 | 差距 +0.4 | 方向A压倒性占优，B几乎不可见 |

方向锁定的信号差距大得多，因此一旦形成，**比约束忽略更难被后续干预纠正**——你需要比方向放大信号更强的反向信号才能扭转。

---

#### 方向锁定的 4 种子类型

基于本工作空间的实证，方向锁定有 4 种可区分的表现：

| 类型 | 机制 | 典型触发 | 识别信号 | 发生率 |
|:-----|:-----|:---------|:---------|:-----:|
| **E1-方向锚定** | prompt中强方向性表述锚定整个输出 | "深入分析XX"、"重点关注YY" | 输出只在单一框架内打转，不提替代视角 | 🔴 极高 |
| **E2-样例固化** | 提供的样例(sample)成为唯一的输出模板 | "按照下面的格式"、"参考这个例子" | 输出是样例的变体而非创新 | 🟡 中 |
| **E3-历史锁定** | 前几轮的历史回复锁定了后续方向 | 多轮对话中 Agent 深入某个技术细节无法拉回 | 用户问"回到整体"后仍聚焦细节 | 🟡 中 |
| **E4-角色捆绑** | 角色设定过于具体导致思考框架受限 | "你是一个安全专家" | 从单一角度看待跨领域问题 | 🟢 低但顽固 |

**典型实例（本工作空间发生过的）**：

- **E1 实例**: prompt 要求"深入分析超节点的供电架构" → 输出 3000 字详尽的供电拓扑分析，却完全没有提及超节点的冷却方案、互联带宽、PCB 布局——尽管这些与供电同等重要。用户补充"也看看散热"后才转向。问题不在供电分析的质量（很好），而在于**输出自动假设了问题边界**。
- **E2 实例**: 提供一份竞品分析模板 → 后续生成的所有分析报告都套用同一模板结构，即使模板是针对特定产品的，后续分析的产品完全不同。模板中有的章节（如"供应链分析"）在大幅删减后仍然出现。
- **E4 实例**: 设定"你是一个 BMC 固件专家" → 分析服务器故障时自动排除硬件可能性，即使故障现象指向物理损伤。

**量化估计**：方向锁定在本工作空间的发生率约为**约束忽略的 60-70%**，但感知率不到约束忽略的 30%——因为输出本身质量好、自洽性强，只有达到足够经验后才能识别"方向偏了"与"内容本身没错"之间的区别。

---

#### 方向锁定 vs 约束忽略的对比

| 对比维度 | 约束忽略 | 方向锁定 |
|:---------|:---------|:---------|
| **信号问题** | 约束信号 **衰减**（该做没做） | 方向信号 **过强**（不该做却做了） |
| **根本机制** | 注意力偏移 + 噪声淹没 | 注意力放大 + 残差流锁定 |
| **输出表现** | 明显缺陷（缺格式/漏步骤） | 看起来很好，但视角单一 |
| **识别难度** | 低——一眼看出没做到 | **高**——需要领域经验才能判断"方向偏了" |
| **常见应对** | 加约束、加 check | 需要显式引入**替代视角** |
| **双审盲区** | 另一模型审查能发现缺失 | 同一方向上的另一个模型**也倾向于同意** |
| **根本原因** | Softmax **分母**过大导致信号淹没 | Softmax **分子竞争**导致注意力集中 |

---

#### 方向锁定的对抗策略

方向锁定不是"模型不够好"的问题——它来自模型作为统计系统的固有特性。对抗方向锁定需要两类手段：

**策略组 A：输入侧——打破锚定**

| 策略 | 做法 | 原理 | 效率 |
|:-----|:-----|:-----|:----:|
| A1-反方向提示 | 明确要求"同时给出反对意见/替代方案" | 在 attention 中创建竞争信号 | 🟡 中 |
| A2-视角矩阵 | 列出要求覆盖的多个视角（如：技术/成本/时间/人效） | 多方向信号防止单一聚集 | 🔴 高 |
| A3-约束前置+方向后置 | 先写通用约束再写具体方向 | 约束在残差流中先累积 | 🟡 中 |
| A4-盲点提示 | 要求主动标识"本分析中未覆盖的方面" | 迫使输出暴露自己的边界 | 🟢 低但落地 |

**策略组 B：输出侧——检查方向偏度**

- **视角覆盖率检查**: 输出的分析维度是否覆盖了 MECE 框架下应有的所有方面？如果缺了某个维度，提示可能产生了方向锁定。
- **反方测试**: 如果让 AI 从对立角度/替代假设重新分析，结果是否一致？不一致则原输出有方向锁定。
- **边界标记法**: 要求每次输出附带"本分析未覆盖的领域"列表，将隐性的方向锁定显性化。

**本工作空间的实践**：在 deep-tech-writer 和 industry-insight 中已内置"视角矩阵"——要求技术分析至少覆盖原理/架构/性能/演进/对比/局限六个维度。这就是对方向锁定的预防机制。

---

### III 维度：输入污染——基础就不对

> **核心命题**: GIGO（Garbage In, Garbage Out）是一种**与模型能力无关**的失效——输入端的质量缺陷
> 无论模型多强都无法在后端修复。约束忽略和方向锁定是模型层面的问题，输入污染是**系统层面的问题**。
>
> 错误的数据做不出正确的分析——这是信息论的基础性质，不是 AI 特有的弱点。

---

#### 输入污染的架构根源

输入污染不是"小心一点就能避免"的问题。它在信息论的框架下有一个**理论下限**：

**信息论表述**：每经过一次信息管道，输出相对于输入的互信息 $I(X;Y)$ 满足数据处理不等式(Data Processing Inequality)：

$$I(X;Y) \leq I(X;Z) \quad \text{for } X \to Z \to Y$$

其中 $X$ 是真实世界状态，$Z$ 是输入给 AI 的信息，$Y$ 是 AI 输出。

**这个不等式的实际含义极其严厉**：

- 如果输入 $Z$ 已经损失了 50% 的原始信息（噪声、偏见、断章取义），输出 $Y$ 与真实世界 $X$ 的互信息**不可能超过 50%**
- 没有任何 prompt 技巧、模型能力、后处理可以弥补这个损失
- 输入污染是**不可修复的系统性损失**——上游错 1%，下游最优情况也只能复原 1%

这正是 GIGO 的信息论基础：**垃圾进的最佳情况仍然是垃圾出**。

---

#### 输入污染的 5 个来源

输入污染不是单一现象。基于本工作空间的实证，它来自 5 个独立的源头：

| 类型 | 定义 | 典型场景 | 发生频率 | 修复可能性 |
|:-----|:-----|:---------|:--------:|:----------:|
| **F1-数据源偏差** | 检索到的信息本身有系统性偏见 | 搜索只返回一方观点、使用有立场偏向的资料来源 | 🔴 高 | 🟡 可通过多源交叉验证减轻 |
| **F2-时序错配** | 信息本身正确但时效过时 | 引用 2024 年的市场报告写 2026 年的分析 | 🟡 中 | ✅ 通过时效标注解决 |
| **F3-范围错配** | 检索到的信息与目标问题不匹配 | 用通用服务器的故障率数据推测 AI 服务器的可靠性 | 🟡 中 | 🟡 需要精确的检索词 |
| **F4-断章取义** | 上下文被切分后关键信息丢失 | Chunk 分割把"不推荐使用"切成"推荐使用" | 🟢 低但致命 | ✅ RAG chunk 策略优化 |
| **F5-未知盲区** | 用户不知道某个重要信息存在，从未提供 | 讨论功率预算时未告知电源规格 | 🔴 极高 | ❌ 无法在无意识下修复 |

**F5 是最危险的**——因为它无法被检测。用户不知道的信息既不会出现在 prompt 中，也不会在检索结果中——AI 和用户一起在无知中做决策。这是"unknown unknowns"问题，与模型的约束能力无关。

---

#### 输入污染的层次结构（L0-L3）

输入污染可以在信息管道的不同层级发生，不同层次的污染需要不同的治理策略：

```text
真实世界状态 (X)
 v
L0: 信息来源选择 --- 选了不可靠/有偏见的源
 v
L1: 信息获取/检索 --- 查询不当/检索不全/时效过期
 v
L2: 信息处理/呈现 --- 切分破坏/格式误解/断章取义
 v
L3: 信息综合/输出 --- 在污染基础上生成结论
 v
AI 输出 (Y)
```

**层次治理原则**：

| 层级 | 问题 | 治理策略 | 本系统实践 |
|:-----|:-----|:---------|:-----------|
| **L0** | 源不可靠 | 来源优先级排序、权威源优先 | MEMORY.md 中"来源优先级"（论文 > 白皮书 > 报告 > 博客） |
| **L1** | 检索不完整 | 多源验证、多轮搜索、检索前策略规划 | deep-tech-writer 的"来源挖掘"环节 |
| **L2** | 切分/呈现偏差 | chunk 策略优化、上下文完整性检查 | light-literature-search 的源内容完整性验证 |
| **L3** | 综合输出偏差 | 输出的事实核对、来源追溯 | light-citation 的引用审查、doc-reviewer 的逻辑审查 |

**关键认知**：L0-L2 的输入污染是**可以治理**的，只需要增加验证环节。但 L0 的源头污染治理成本最低、效果最好——"选对来源"比"检查输出"成本低两个数量级。

---

#### GIGO 的量化证据

基于学术界和工业界的公开数据，输入污染在各行业的实际影响：

| 研究/数据 | 发现 | 来源 |
|:----------|:-----|:------|
| RAG 归因错误率 | 即使使用检索增强，LLM 仍歪曲事实的比例为 **15-30%** | Attribution Survey 2026 |
| 向量检索碎片化 | 边界分割导致关键证据散落在不同 chunk，查询召回率 <**70%** | SCAR 2026 |
| 数据质量陷阱 | 数据产品失败案例中 **60%+** 归因于数据质量问题 | 数据资产研究报告 |
| AI 辅助决策偏差 | 使用 AI 辅助后，决策者接受错误信息的概率 **增加 40%**（因 AI 输出更流畅、更自信） | LLM Trust Calibration 2025 |
| 多源不一致 | 同时检索 5 个来源时，**60-80%** 的场景存在至少 2 个来源之间的直接矛盾 | 本系统实证 |

**一个被低估的风险**：AI 输出**越流畅、越详细、越结构化**，用户越倾向于相信它——即使源数据是错的。流畅性 ≠ 正确性，这是一种系统性的信任校准偏差。

#### 本工作空间中的输入污染实例

| 案例 | 污染类型 | 表现 | 溯源 |
|:-----|:---------|:-----|:-----|
| 芯片制程参数错误 | F1-数据源偏差 | 分析华为某芯片时引用了第三方估算数据，后续分析全部基于错误假设 | 未验证原始来源 |
| 市场报告时效过期 | F2-时序错配 | 写 2026 年市场分析时引用 2024 年 Gartner 报告，份额分布已完全变化 | 未检查时效标注 |
| RAG chunk 截断 | F4-断章取义 | 标准文档"不适用于 3.3V 供电场景"被切为"适用于 3.3V 供电场景" | chunk 边界策略不完善 |
| 设计约束遗漏 | F5-未知盲区 | 讨论单板布局时未告知连接器高度限制，AI 设计方案全部不可制造 | 用户未意识到的约束 |

这些案例的共性是：**输入端的 1% 错误导致输出端 100% 不可用**——验证投资回报率极高。

#### GIGO 对抗策略

**策略组 A：输入侧——源头治理（投资回报率最高）**

| 策略 | 做法 | 适用层级 | 效率 |
|:-----|:-----|:---------|:----:|
| A1-来源优先级排序 | 建立信息源可信度分级，声明性/推断性信息标绿/黄/红色 | L0 | 🔴 极高 |
| A2-多源三角验证 | 任何关键事实至少从 2 个独立来源交叉验证 | L0-L1 | 🔴 高 |
| A3-时效标注 | 每项数据标注获取日期，超期自动标记为"需验证" | L1 | 🟡 中 |
| A4-检索前策略 | 写 query 前先问："这个信息该从哪里找？什么关键词？时效要求？" | L1 | 🟡 中 |
| A5-完整性检查 | 每段引用信息检查上下文完整性——是否断章取义 | L2 | 🟡 中 |

**策略组 B：输出侧——验证闭环**

- **来源追溯**: 每项事实/数据标明来源，无来源=未验证=可疑
- **矛盾检测**: 在输出中标注"多源不一致"的领域，而不是掩盖
- **可信度声明**: 对难以验证的信息，主动标注置信等级（高/中/低/推测）
- **空白声明**: 当信息不足以支撑结论时，主动说"现有信息不足以判断"，而非强行生成

**本工作空间的实践**：

- MEMORY.md 已硬编码来源优先级：论文/标准 > 官方白皮书 > 一线报告 > 行业分析 > 通用知识
- light-citation 技能做引用审查时，自动检测来源可靠性
- doc-reviewer 内置"断言有出处"检查——这是对 F5（未知盲区）的防御
- MEMORY.md 的"数据类型要求"（数值+单位+对比基线+测试条件）是对 F1/F2/F3 的防御

### 三维度汇总

| 维度 | 本质 | 信号问题 | 识别难度 | 修复成本 | 本系统关键防御 |
|:-----|:-----|:---------|:--------:|:--------:|:--------------|
| **I 约束忽略** | 该做的没做 | 信号衰减 | 🟢 低 | 🟡 中 | 四层防御、三态判定、证据闸门 |
| **II 方向锁定** | 不该做的做了 | 信号过强 | 🔴 高 | 🟡 中 | 视角矩阵、反方向检查、盲点提示 |
| **III 输入污染** | 基础就不对 | 信源质量 | 🟡 中 | 🟢 低（R 极高） | 来源优先级、多源验证、时效标注 |

**三维度叠加效应**：在现实中，三维度经常同时发生。一次典型的失败流程可能是：

1. 输入污染（F2）：引用过时数据
2. 方向锁定（E1）：被"深入分析"引导只关注一个技术维度
3. 约束忽略（A3）：催进度时跳过了质量 check

→ 最终的输出：数据过时、视角片面、格式不对——三个不同维度的失效叠加在一起，每个维度都不难修复，但三者同时发生很难一次性纠正。

## 完整的五层管道框架：AI 失效的全景图

> **核心命题**: 三维度（I 约束忽略 / II 方向锁定 / III 输入污染）只覆盖了 AI 信息处理管道的**前三层**。
> 模型内部还有知识调用、逻辑推理、输出校准三个层面的失效，加上跨层元失效，总计六个层次。
>
> **失效不仅来自 prompt 端，更来自模型作为知识处理系统的内生缺陷**。

### 五层管道全景

AI 从输入到输出的信息处理可以建模为一条五层管道，每层都有特定的失效模式：

```text
用户输入/Prompt
 v
+- Layer 1: 信源层 (Source) --------- 已有 III 维度 ------+
| 输入质量 / 检索质量 / 数据偏差 F类：F1-F5 |
+---------------------------------------------------------+
 v
+- Layer 2: 注意层 (Attention) -------- 已有 I + II 维度 -+
| 注意力分配 / 约束遵循 / 方向聚焦 A-E类 |
+---------------------------------------------------------+
 v
+- Layer 3: 知识层 (Knowledge) -------- 新增 G类 --------+
| 知识检索 / 事实调用 / 概念理解 G1-G6 |
+---------------------------------------------------------+
 v
+- Layer 4: 推理层 (Reasoning) -------- 新增 H类 --------+
| 逻辑链 / 数学推理 / 因果推断 H1-H7 |
+---------------------------------------------------------+
 v
+- Layer 5: 输出层 (Output) ----------- 新增 I类 --------+
| 置信校准 / 表达方式 / 行为模式 I1-I6 |
+---------------------------------------------------------+
 v
最终输出

+- Layer X: 元层 (Meta) --------------- 新增 J类 --------+
| 可复现性 / 成本 / 依赖 / 版本 J1-J4 |
| <- 跨所有层的系统性失效 |
+---------------------------------------------------------+
```

**关键区分**: 前两层（信源+注意）是 **prompt 侧**问题——用户通过改进输入可以控制。中间三层（知识+推理+输出）是**模型侧**问题——用户无法直接控制，只能通过策略来缓解。元层是**系统侧**问题。

以下逐层展开新增的 G/H/I/J 四层。

---

### Layer 3: 知识层失效——GPT 的"知识幻觉"

> **核心命题**: 知识层失效与输入污染（Layer 1）的本质区别在于——输入污染是**给模型的信息错了**，知识层失效是**模型自己知道的信息不对或调错**。
> 模型约 60-70% 的参数存储在 FFN（前馈网络）层中，这些参数编码了模型从预训练语料中习得的"世界知识"。
> 当这些知识存在盲区、过时、或检索路径出错时，无论输入多好都会产生错误输出。

#### 知识层失效的架构根源

Transformer 中的知识存储和调用机制与人类完全不同：

**FFN 作为键值记忆（Key-Value Memory）**：

FFN 层的每个神经元可以被视为一个"记忆单元"，通过学习到的权重编码特定的知识模式。Geva et al. (2021) 的工作表明，FFN 可以解释为：

$$FFN(x) = \sum_{i=1}^{d_{ff}} \sigma(x \cdot W_i^T) \cdot v_i$$

其中 $v_i$（$W_i$ 的第二层行向量）是"值向量"——当输入 $x$ 与"键向量" $W_i^{first}$ 匹配时，对应的值 $v_i$ 被激活。可以理解为一种**隐式检索**——根据当前上下文（query）从 FFN 参数（知识库）中检索相关信息（value）。

**这个机制的两个根本弱点**：

1. **不可区分已知与未知**：FFN 没有"我不知道"这个输出——对于任何输入，它都返回某个激活模式。模型不是在"知道"和"不知道"之间切换，而是在"有多大概率的模式匹配"之间连续变化。**模型从不沉默，它总是假装知道**——这就是幻觉的架构根源。

2. **知识截断是物理边界**：模型的训练数据截止日就是知识的物理边界。超过这个边界的所有知识——新论文、新发布的产品、最近的新闻——模型"不知道"但"仍在生成"，因为生成机制独立于知识确认机制。

#### 知识层失效的 6 种子类型

| 类型 | 机制 | 典型表现 | 发生频率 | 识别难度 |
|:-----|:-----|:---------|:--------:|:--------:|
| **G1-幻觉捏造** | 概率匹配最强的模式，而非事实正确 | 编造不存在的论文/产品/事件 | 🔴 极高 | 🔴 极难（越流畅越难） |
| **G2-知识截断** | 训练截止后的信息没有编码，但模型不知"不知道" | 用旧知识回答新问题 | 🔴 高 | 🟡 中（检查时间戳） |
| **G3-虚假专家** | 模型对不熟悉的领域同样自信输出 | AI 回答医疗/法律问题语气与回答常识一样自信 | 🟡 中 | 🔴 困难 |
| **G4-概念混淆** | 相似概念的语义嵌入空间重叠导致混淆 | 混淆 NVLink 与 NVSwitch、混淆 HBM 与 DDR5 | 🟡 中 | 🟡 中（需领域知识） |
| **G5-来源编造** | 模型"学会"引用模式但无事实记忆 | 编造 DOI/URL/论文作者和年份 | 🟡 中 | 🔴 极难（引用看起来真） |
| **G6-过度泛化** | 从训练数据中的统计模式推出错误的一般性结论 | "大多数服务器都用 Linux"→"所有企业服务器都用 Linux" | 🟢 低但顽固 | 🟡 中 |

**G1 和 G5 是最危险的**——因为它们的输出质量高、自洽性强，比明显的知识缺失更难识别。G1 在学术界被称为"幻觉鸿沟"（Hallucination Gap）：模型流畅度与事实正确性之间的差距。

#### 知识层失效的量化证据

| 研究/数据 | 发现 | 来源 |
|:----------|:-----|:------|
| 幻觉率基准 | 主流 LLM 在知识密集型任务的幻觉率 **15-30%** | TruthfulQA / HaluEval 2024 |
| 引用编造率 | ChatGPT 编造参考文献的比例 **35-55%** | 多所大学独立验证 |
| 知识截断影响 | 模型在训练截止日前知识准确率 ~90%，截止日后 **降至 <50%** | Internal evaluations |
| 领域差异 | 编程知识准确率 >90%，医学/法律领域幻觉率 **>40%** | MMLU / MedQA |
| 过时知识韧性 | 即使 RAG 提供正确新信息，模型仍倾向自己"知道"的旧知识 | Stickiness of Knowledge 2025 |

#### 本工作空间的知识层失效实例

- **G1 实例**: 分析华为某芯片架构时，模型"补充"了不存在的微架构细节（寄存器命名、流水线阶段数），看起来极为专业但完全错误。用户因了解该领域才能识破。
- **G5 实例**: 生成论文参考文献时，模型编造了 DOI 号、期刊名、作者——格式完全正确，但期刊和论文不存在。需要逐条在数据库中验证才能发现。
- **G3 实例**: 问及 AI 不熟悉的细分领域（如"PCB 板级信号完整性分析中的 S 参数去嵌入方法"），模型回答语气与回答常识问题完全一致，但细节多处有误。

### Layer 4: 推理层失效——逻辑链条的断裂

> **核心命题**: 推理层失效是知识层失效的"表亲"——知识层是"知道的东西不对"，推理层是"想东西的方式不对"。
> 即使模型拥有完全正确的知识（Layer 3 无故障），错误的推理路径也会导致错误输出。
>
> 这是最容易被忽略的失效层——因为输出看起来有理有据，但**每一步推理的跳转可能都有逻辑裂缝**。

#### 推理层失效的架构根源

模型在推理时的机制不是人类式的"逻辑推演"，而是**下一个 token 的概率预测**。这个根本差异导致了一系列推理弱点：

**Chain-of-Thought 不是逻辑链**：当模型"一步一步思考"时，每一步的输出仍然是概率预测——不是基于形式逻辑规则，而是基于训练数据中的模式匹配。CoT 的每一步都可能包含隐藏的跳跃：

```text
概率空间 token 序列空间
推理步骤 1 --> P(token_i | context) -> "因此这证明"
推理步骤 2 --> P(token_j | context') -> "所以我们可以得出结论"
推理步骤 3 --> P(token_k | context'') -> "综上所述"
```

每一步之间不存在**形式逻辑约束**——只有训练数据中的统计关联。这就像一个人说"因为 A 所以 B"只是因为他在训练数据里见过 A 后面经常跟 B，而不是因为 B 确实是 A 的逻辑推论。

**数值推理的特殊困难**：数字在 tokenizer 中通常是按位切分的（"123"可能被切为"1""2""3"），这让模型失去了对数值大小的直觉理解。模型不是在"计算"，而是在"预测计算结果是什么样子"——这就是为什么简单算术题（如"17×23"）对 LLM 来说是困难的。

#### 推理层失效的 7 种子类型

| 类型 | 机制 | 典型表现 | 发生频率 | 复杂度 |
|:-----|:-----|:---------|:--------:|:------:|
| **H1-逻辑谬误** | 概率模式匹配产生类似逻辑推理的 token 序列 | 偷换概念/循环论证/虚假因果/滑坡谬误 | 🟡 中 | 🔴 高 |
| **H2-过早收敛** | 未充分探索解空间就锁定第一个似合理的路径 | 推理链的第一个分支被深度挖掘，其他分支未探索 | 🔴 高 | 🟡 中 |
| **H3-步骤遗漏** | 在多步推理中无意识地跳过中间步骤 | "A→C" 直接跳跃，丢失了中间的 B | 🟡 中 | 🟡 中 |
| **H4-数值失效** | Tokenizer 按位切分导致数值直觉丧失 | 算术错误、比较失败、单位换算错误 | 🔴 高 | 🟡 中 |
| **H5-因果倒置** | 混淆相关性与因果关系 | "因为销售上升时广告投放多→广告导致销售上升" | 🟢 低但顽固 | 🔴 高 |
| **H6-虚假二分** | 将多选项问题简化为二选一 | "要么 A 要么 B"，忽略 C/D/E | 🟡 中 | 🟢 低 |
| **H7-自我矛盾** | 同一输出中前后断言不一致 | 前一段说"NVLink 是 900GB/s"，后一段说"NVLink 是 450GB/s" | 🟡 中 | 🟡 中 |

**H1 与 H6 的区别**：H1 是**单步推理错误**（这个推理步骤不合逻辑），H6 是**选项空间被非法截断**（本有多个选项但被压缩为两个）。H6 与 E1（方向锚定）的区别在于：E1 是方向信号过强，H6 是推理过程中的逻辑错误。

#### 推理层失效的量化证据

| 研究/数据 | 发现 |
|:----------|:------|
| GSM8K 数学推理 | 即使最好的模型在小学数学题上仍有 **5-15%** 的错误率 |
| PrOntoQA 逻辑推理 | O1-preview 等推理模型仍有 **8-25%** 的逻辑错误 |
| 多步一致性测试 | 同一问题重问 5 次，**20-30%** 的推理链不一致 |
| 数值稳定性 | 模型对 "3.11 和 3.9 哪个大" 这类问题错误率 **~10%**（因 tokenizer 按位切分）|
| 因果关系推理 | 在需要区分相关性与因果性的任务上，模型准确率 **<60%** |

#### 本工作空间的推理层失效实例

- **H2 实例**: 分析"服务器故障根因"时，模型沿着第一个最可能的路径（BMC 日志错误码）深挖了 2000 字，但完全没有探索其他可能性（电源/散热/互联）。错误不在"没分析 BMC"（它分析得很深），而在于**过早锁定了路径**。
- **H4 实例**: 计算 4 台 AI 服务器总功耗时，3 台 × 8kW + 1 台 × 12kW = 36kW 算成了 34kW——单个 token 预测的统计偏差，而非真正的"算错了"。
- **H1 实例**: 在分析"NVLink 4.0 为什么是 900GB/s"时，用 NVSwitch 的规格反推 NVLink 的规格，形成了循环论证——"因为 switch 支持 900GB/s，所以 link 也是 900GB/s；反过来又用 link 的 900GB/s 证明 switch 支持 900GB/s"。

### Layer 5: 输出层失效——表达与校准的问题

> **核心命题**: 输出层失效是知识正确 + 推理正确，但**输出的呈现方式有问题**。
> 模型在"说什么"（Layer 3）和"怎么想"（Layer 4）上都没错，但在"怎么说"和"怎么呈现给自己"上出了偏差。
>
> 这是最贴近"用户体验"的失效层，也最容易被错误归因——用户可能觉得"AI 在骗人"（其实是知识问题），也可能觉得"AI 能力不够"（其实是输出校准问题）。

#### 输出层失效的架构根源

**置信度与正确性解耦**：模型的 token 生成概率（logits）与输出的事实正确性之间**不存在机械关联**——模型可以以极高概率生成错误内容（这一点已经在 G1 中说明）。但输出层的问题更细致：

**RLHF 的副作用**：RLHF 训练在优化"人类偏好"时带来了系统性的输出偏差：

- 人类更喜欢**更长、更详细**的回答 → 模型学会填充内容 → 即使不确定也写长
- 人类更喜欢**肯定、自信**的回答 → 模型学会消除不确定性表达
- 人类更喜欢**同意用户观点**的回答 → 谄媚偏好的根基

#### 输出层失效的 6 种子类型

| 类型 | 机制 | 典型表现 | 发生频率 | 与已有类区别 |
|:-----|:-----|:---------|:--------:|:-----------|
| **I1-谄媚迎合** | RLHF 优化人类偏好导致倾向同意用户 | 用户说错误观点时模型回应"你说得对" | 🔴 高 | 不同于 D3（表演式同意是假装检查），I1 是意识形态的迎合 |
| **I2-过度自信** | 置信度表达与真实正确率解耦 | "我确定这是正确的"→ 实际错误 | 🔴 极高 | 不同于 G1（G1 是事实错误本身），I2 是**对错误的态度** |
| **I3-指令博弈** | 字面执行指令但违背意图 | "列出所有约束"→ 列出但不遵守 | 🟡 中 | 不同于 D1（D1 是跳过检查），I3 是字面遵守但绕过精神 |
| **I4-安全逃逸** | 越狱/提示注入突破安全边界 | 被恶意 prompt 诱导输出有害内容 | 🟢 低但严重 | 独立于所有已有类 |
| **I5-偏见放大** | 训练数据中的社会偏见被强化输出 | 性别/种族/地域刻板印象 | 🟡 中 | 不同于 I1（I1 是迎合用户，I5 是固化的训练数据偏误） |
| **I6-拒绝异常** | 过度拒绝（本该回答的拒绝了）或拒绝不足 | "我无法回答这个问题"→ 实际可以回答 | 🟡 中 | 独立于所有已有类 |

**I3 需要特别说明**：指令博弈有几种表现形式：

- **过于字面**：说"列出问题"→ 真的只列不分析
- **选择性字面**：遵守了最容易遵守的部分，忽略困难部分
- **梯子抽走**：给出了正确结论但推理过程有跳跃——看起来遵守了"一步步推理"的要求，实际跳步了（与 H3 有关联但 I3 是意图层面的问题）

### Layer X: 元层失效——跨层系统性问题

> **核心命题**: 元层失效不是任何一层的特定问题，而是跨层交互产生的**系统性失效**。
> 就像计算机系统的"时序问题"不归 CPU/内存/硬盘中任何一个模块负责，元层失效无法通过优化单层来解决。

| 类型 | 定义 | 机制 | 发生频率 | 严重性 |
|:-----|:-----|:-----|:--------:|:------:|
| **J1-不可复现** | 同一输入在不同次调用产生不同输出 | 采样温度/随机种子引入的随机性 | 🔴 极高 | 🟡 中（调试困难但非错） |
| **J2-成本失效** | 输出质量没问题但成本/延迟不可接受 | 长输出 + 复杂推理 + 多次重试导致的成本爆炸 | 🟡 中 | 🟡 中 |
| **J3-依赖失效** | 模型依赖外部工具/知识库时的级联故障 | RAG 服务不可用 → 模型在无检索下生成 → 知识过时 | 🟡 中 | 🔴 高 |
| **J4-版本漂移** | 模型升级后行为偏移（与 C1 相同） | 升级后续航行为与原设定不兼容 | 🟡 中 | 🟡 中 |

**J1 的特殊性**：在重视**可审计性**的场景（金融/医疗/合规），不可复现可能是最严重的失效——即使输出内容正确。用户无法在审计时说"上次 AI 就是这么说的"。

## Check 机制设计

核心原则：**不要把信任押在"AI 会乖乖遵守约束文件"上。** 约束是起点而非终点——围绕关键约束建立 check 机制，让"验证"成为不可跳过的工作流环节。

### 四层防御架构（从软到硬）

```text
+------------------------------------------------------------------+
| Layer 1: 提示词层（最弱） |
| AGENT.md / RULE.md / Skill 指令 |
| -> 模型可能遵守，也可能不遵守 — 完全取决于模型当时的推理路径 |
| -> 加固技巧：正面引导>禁止表述；步骤式>原则式；关键写在系统提示词 |
+------------------------------------------------------------------+
| Layer 2: 自检层（内置反射） |
| light-self-review / 11项自检清单 / 三态判定 |
| -> 利用模型自身的审查能力，在输出前做一轮自我修正 |
| -> 弱点：同一个模型的自检和产出共享推理路径，可能盲区一致 |
+------------------------------------------------------------------+
| Layer 3: 交叉审查层（外部视角） |
| doc-reviewer / light-consistency / 独立AI实例审查 |
| -> 不同模型/不同技能实例做交叉验证，打破同源盲区 |
| -> 脚本化硬校验不可跳过（格式/编号/链接/数值一致性） |
+------------------------------------------------------------------+
| Layer 4: 系统强制层（最强） |
| 文件铁律（永不rm）、知识库脚本硬校验、Git版本控制 |
| -> 不依赖模型判断，操作系统/脚本层面强制保障 |
| -> 适用：安全红线、破坏性操作、数据完整性 |
+------------------------------------------------------------------+
```

### 检查项设计模式（来自本系统的最佳实践）

从已有技能中提取了三种可复用的检查模式：

#### 模式 A：三态判定（来自 light-self-review）

每一项检查落到三种明确结果，不写含糊感受：

```text
✓ 通过 -> 有证据支撑，约束被遵守
✖ 不通过 -> 证据显示约束被破坏，附严重级
! 警告 -> 部分满足但有风险，需要人工判断
```

严重级分级：

- **Critical（立即修）**：安全红线、数据错误、逻辑致命
- **Important（交付前修）**：格式问题、表达不清、引用遗漏
- **Minor（记录待办）**：建议优化、可选改进

**反谄媚硬约束**：判"不通过"不需犹豫；判"通过"时须附一行带证据的放行理由（指向具体命令输出/原文行号/检查结果）。没证据就当不通过处理。

#### 模式 B：分级执行（来自 light-self-review）

避免轻任务全量检查太慢、或整体跳过导致失守：

| 产出量级 | 检查范围 |
|:---------|:---------|
| **重产出**（≥1章节/含定量结论/对外交付/含代码） | 全量检查 |
| **轻任务**（改一句摘要、调措辞） | 最小三项：证据闸门 + 事实核查 + 夸大检测 |
| **判档规则**：命中任一重产出条件即全量；拿不准用重档 |

#### 模式 C：证据闸门（来自 light-self-review）

不下任何结论性判断，除非当前轮有新鲜证据：

```text
步骤：① 想清"什么命令/检查能证明它"
 ② 当场重跑（不引用旧结果）
 ③ 读完整输出、查 exit code、数失败
 ④ 确认输出真支撑结论
 ⑤ 才下结论
```

跳步 = 撒谎而非验证。红旗词：should / probably / seems to、提前自我满足、轻信子代理报告。

### 防破坏优先级

某些约束被破坏的后果远大于其他——按破坏成本分级防护：

| 层级 | 约束内容 | 防护策略 | 失效后果 |
|:-----|:---------|:---------|:---------|
| 🔴 **P0 安全红线** | 密钥不泄露、文件不误删 | 系统级机制（永不rm、环境变量隔离） | 数据泄露/不可逆损失 |
| 🟠 **P1 质量标准** | 数据可验证、断言有出处 | 自检脚本+交叉审查双重保证 | 输出不可信/错误决策 |
| 🟡 **P2 流程纪律** | 破坏性操作前确认、按步骤执行 | 用户签字认可、checkpoint 检查 | 偏离预期目标 |
| 🟢 **P3 风格规范** | 格式一致、术语统一 | 格式校验脚本+consistency审计 | 质量下降但不致命 |

## 本工作空间的反脆弱设计

回顾整个系统架构，其底层逻辑本身就是对"约束文件不可靠"这一事实的工程回应：

### 从"单点约束"到"多层防御"

```text
传统方案：
 AGENT.md 写了"不要做X" -> 期望 AI 永远遵守 -> 单一信任点 -> 失效即崩

本系统方案：
 约束文件（起点） -> 自检清单（内省） -> 交叉审查（外审） -> 脚本硬校验（系统级）
 ^ 每一层都不信任上一层完全可靠
```

### 已落地的 check 机制清单

| check 类型 | 实例 | 自动化程度 | 覆盖的场景 |
|:-----------|:-----|:----------|:-----------|
| **自检清单** | light-self-review 11项 | 自动（输出前） | 逻辑/事实/格式/创新/引用/夸大/审美/重复/结构/可执行 |
| **逻辑谬误筛查** | 13条谬误表（结论前置/二元对立/假精确/术语漂移等） | 人工+脚本 | 论证质量 |
| **格式自动化** | knowledge-health-check（6类） | 脚本全自动 | 表格/链接/代码块/目录/编号 |
| **术语一致性** | light-consistency audit | 脚本+人工 | 跨材料术语/指标/创新点漂移 |
| **量化四要素验证** | 数值+单位+基线+条件 | 人工+脚本 | 数据断言的可信度 |
| **来源追溯** | 断言出处行号定位 | 人工 | 引用真实性 |
| **借口拦截** | 27条自我欺骗识别 | 自检触发 | 跳过验证的心理防御 |
| **失败循环识别** | 修3次→架构问题 | 自检触发 | 打补丁死循环 |
| **版本控制** | git → GitHub | 自动 | 约束被破坏后的回滚能力 |

### 代价与平衡

> **关键权衡**：check 机制不是免费的——每增加一层验证，都增加延迟和 token 消耗。
> 需要在"错过约束破坏"和"过度验证"之间找到平衡点。

分级原则：

- **P0 安全约束**：永远不妥协，系统级强制
- **P1 质量约束**：逐条验证，不通过不交付
- **P2 流程约束**：抽样检查 + 关键节点验证
- **P3 风格约束**：事后批量修复，不在每轮输出中逐条检查

## 进化视角：从"约束+检查"到"反馈闭环"

Evolver 和 skill-evolver 提供了更高维度的思路——不是静态地维护约束和检查机制，而是通过运行时反馈**自动发现并修复**约束失效：

```text
观察 -> 识别约束失效 -> 分析根因 -> 修改约束或增加检查 -> 验证 -> 持续循环
```

这意味着：

1. **约束是活的** — 根据实际失效模式持续优化，不是写死不变
2. **检查点自动调整** — 频繁失效的约束获得更多检查资源，一直可靠的约束降级
3. **新失效模式自动入库** — 每次发现新的约束失效方式，补充到检查清单中

> **最终洞见**：约束文件的价值不在于被严格执行——那在模型架构层面就不可能。
> 它的真正价值是 **提供了 check 的参照系**——让你知道"应该是什么样"，
> 然后靠 check 机制发现"实际是什么样"，最后靠反馈闭环让两者收敛。

## 适用场景

- 生成技术报告/调研材料 → AI 搭框架，你填验证后的细节
- 写代码 → AI 给方案，你审查逻辑和边界条件
- 做分析 → AI 给数据，你解读其业务/工程含义
- 写文档 → AI 出初稿，你按自己的判断标准精修

## 信任校准框架：从"信不信"到"怎么校准"

> **核心问题**："AI 的输出能不能信？"——这个提问本身就是错的。
>
> 正确的提问是：**"在什么条件下、对什么类型的问题、AI 的什么输出，其可信度有多高？"**

信任不是二值开关（信/不信），而是在**域×任务类型×验证深度**三维空间中的连续校准。

### 信任校准的三维空间

```text
 验证深度
 ^
 未经核查 | 交叉验证
 -----------+-----------> 域
 工具辅助 | 人工深度
 |
```

| 维度 | 取值 | 信任校准策略 |
|:-----|:-----|:-------------|
| **域（Domain）** | 高熟悉度 / 中熟悉度 / 陌生域 | 越熟悉越敢信任初稿，越陌生越要逐句验证 |
| **任务类型** | 信息检索 / 框架生成 / 分析推理 / 代码编写 / 创意生成 | 检索和框架可放行，分析推理和代码要逐条过证据 |
| **验证深度** | 不经核查 / 关键字抽样 / 全文交叉验证 / 人工深度审 | 验证成本递增，按风险匹配 |

### 信任校准实操表

| 场景 | 域熟悉度 | 任务类型 | 建议验证深度 | 信任校准 |
|:-----|:--------:|:---------|:------------|:---------|
| 查一个已知技术参数 | 高 | 检索 | 不经核查 | ✅ 可直接用 |
| 生成报告框架 | 高 | 框架生成 | 关键字抽样 | ✅ 检查大纲逻辑即可 |
| 分析竞品优劣势 | 中 | 分析推理 | 全文交叉验证 | ⚠️ 每条结论找原始来源 |
| 写数据处理代码 | 高 | 代码编写 | 全文交叉验证 | ⚠️ 跑通+边界测试 |
| 调研陌生领域给建议 | 低 | 分析推理 | 人工深度审 | ❌ 自己先学，AI只当线索 |
| 生成论文结论 | 高 | 创意生成 | 全文交叉验证 | ⚠️ 逐句回溯结果表 |

### 信任校准的衰减曲线

信任不是持久资产——它随时间衰减：

```text
信任度
 ^
 | ################ 信任基线（初始校准）
 | ↘
 | ######## 24h后（上下文偏移）
 | ↘
 | #### 新会话（约束重新加载+版本漂移）
 | ↘
 | ## 模型升级（行为不可预知）
 +---------------------------> 时间
```

**校准原则**：

1. 每次新会话首轮产出，默认按**低一档**信任度开始，等验证后再校正
2. 模型版本变更后，重新执行信任校准——旧经验不跨版本复用
3. 连续 N 次高质量输出只能**小幅上调**信任基线，1 次关键错误就**大幅下调**

## 领域桥接：服务器硬件工程视角下的约束管理

> 以下从用户所在的服务器硬件研发领域出发，用硬件工程中经过数十年验证的设计原则来审视 AI 约束工程。这些类比不是装饰性的比喻，而是**跨领域的设计模式迁移**。

### 信号完整性（SI）与约束信噪比

服务器高速信号设计中，信号从发送端到接收端的完整性决定了系统可靠性。这与约束信息在 LLM 中的传输有着深层对应：

| SI 概念 | 硬件含义 | LLM 约束工程对应 | 共同的工程原则 |
|:--------|:---------|:-----------------|:--------------|
| **发送端幅度** | 驱动器的输出电压摆幅 | 约束的明确程度（具体 vs 抽象） | 信号必须有足够的初始强度才能承受传输损耗 |
| **信道损耗** | PCB 走线的介质损耗 + 导体损耗（dB/inch） | 注意力衰减（每增加 1K tokens 约衰减 X dB） | 信号随距离（序列长度）指数衰减 |
| **反射** | 阻抗不连续处的信号回弹 | 指令层次冲突（系统消息 vs 用户消息优先级模糊） | 不匹配的边界产生信号污染 |
| **串扰 (Crosstalk)** | 相邻走线的电磁耦合 | 用户指令对系统指令的注意力竞争 | 邻近信号的干扰无法完全消除，只能管理 |
| **眼图张开度** | 信号质量的可视化指标 | 约束遵循率的统计分布 | 眼图闭合 = 系统不可靠；约束遵循率低于阈值 = 约束失效 |
| **误码率 (BER)** | 接收端判断错误的概率 | 约束被违反的概率 | 硬件要求 BER < 10⁻¹²（0差错），约束工程接受 BER ~10⁻¹~10⁻² |

**眼图类比约束工程**：在高速信号测试中，工程师通过眼图判断信号质量——眼图"眼睛"睁得越大，信号越干净。约束工程也有类似现象：

```text
眼图张开 约束遵循状态 判断
######## >90% 遵循 ✅ 约束有效，"眼睛"张开
#### ~60% 遵循 ⚠️ "眼睛"半闭，约束部分失效
## 30-40% 遵循 ❌ "眼睛"几乎闭合，约束基本失效
空格 <20% 遵循 ❌ 约束完全失效，信号不可恢复
```

**工程启示**：

- 约束设计和高速链路设计共享一个核心原则：**在接收端（输出时）做均衡（equalization），比在发送端（prompt 中）盲目增加信号强度更有效**。
- SerDes 中的 CTLE（连续时间线性均衡器）+ DFE（判决反馈均衡器）对应的是 **check 机制（在输出端恢复信号）+ 反馈修正（根据错误信号调整）**。

### DFX（Design for X）与约束可验证性设计

服务器硬件中的 DFX 原则（DFM/DFT/DFS/DFR）可以直接映射到约束工程：

| DFX 原则 | 硬件含义 | 约束工程映射 |
|:---------|:---------|:------------|
| **DFT（可测试性设计）** | 为每块 PCB 设计测试点，确保出厂前可全功能验证 | 约束设计时同步设计 check 点（三态判定入口/证据闸门触发条件） |
| **DFM（可制造性设计）** | 设计阶段考虑制造工艺能力，避免无法生产的特征 | 约束设计时考虑模型能力边界，避免超出模型认知负荷的约束 |
| **DFS（可服务性设计）** | 现场维护时可通过 LED/日志快速定位故障 | 约束失效时输出明确的错误信号（三态判定种的 "不通过" 附严重级） |
| **DFR（可靠性设计）** | 通过冗余/降级设计保证系统在部件失效时仍工作 | P0-P3 防破坏优先级 + 降级模式（时间不够时只跑 P0-P2） |

**具体映射**：本系统的每项 check 机制都可以标注其 DFX 类别：

| 本系统机制 | DFX 类别 | 设计理由 |
|:-----------|:---------|:---------|
| 证据闸门 | DFT | 相当于硬件测试点——不接受未验证的结论 |
| 借口拦截表 | DFM | 相当于设计规则检查——避免"不可能跑好"的约束 |
| 三态判定（通过/不通过/警告） | DFS | 相当于故障指示灯——约束违反时给出明确信号 |
| P0-P3 分级防护 | DFR | 相当于冗余供电 + 降级模式——关键约束至少两层保障 |

### IPD 阶段门（TR Gate）与验证投资分层

IPD（集成产品开发）流程中的 TR1-TR6 阶段门与本框架的验证投资模型（Verification ROI）存在结构同构：

| IPD 阶段门 | 验证深度 | 本框架对应 | 共同特征 |
|:-----------|:---------|:-----------|:---------|
| **TR1（概念）** | 概念验证，评估可行性 | 轻任务三项检查（证据+事实+夸大检测） | 少量资源快速验证方向正确 |
| **TR2（计划）** | 方案选择，可行性评估 | 重产出中的结构检查 + 逻辑谬误扫描 | 中等投入，确认方案合理 |
| **TR3（开发）** | 详细设计评审 | 文档审查（doc-reviewer 三层审查） | 深度投入，确保设计和方案一致 |
| **TR4（验证）** | 产品验证测试 | 全量交叉审查 + 独立实例审查 | 系统性验证，投入最大 |
| **TR5（发布）** | 量产前确认 | 最终质量检查 + 一致性审计 | 查漏补缺，不做大改动 |
| **TR6（生命周期）** | 持续监控与改进 | 运行反馈 → 双环学习 → 约束优化 | 持续迭代不终止 |

**工程启示**：就像 IPD 不会在每个阶段投入相同的资源（TR1 匆忙跳过的代价是 TR4 发现架构缺陷），验证资源也应该按**任务阶段和风险等级**分配，而非平均投入。优秀的产品经理知道什么阶段该做什么验证，优秀的 AI 用户也应该知道什么任务该跑什么检查。

### 故障树分析（FTA）与约束失效传播

服务器可靠性工程中的故障树分析（FTA）用于追踪故障根因。约束失效同样具有故障传播路径：

```text
约束失效（顶层事件）
+-- AND: 检查机制未拦截 + 约束已被破坏
| +-- 检查机制未拦截
| | +-- OR: 无对应检查项 | 检查盲区 | 检查被跳过 | 检查结果被忽略
| | +-- ...
| +-- 约束已被破坏
| +-- OR: 注意力衰减 | 指令层次冲突 | 模型先验压倒 | 版本漂移
| +-- ...
```

**工程启示**：FTA 告诉我们，**单一故障点不可接受**。约束工程中的"单一信任点"（押宝在"模型会乖乖遵守约束文件"上）在可靠性工程中属于最低等级的设计。正确做法是使用 FTA 识别约束失效的**最小割集**（minimal cut sets），然后对每个割集至少建立一层防护。

> 参考：IEC 61025 — Fault Tree Analysis (FTA) 标准
> 参考：本系统约束验证器技能（constraint-verifier）中的 25 条标准检查项对标 FTA 的最小割集分析

## 双环学习机制：从"修复"到"系统进化"

> **单环修复**：约束被破坏了 → 修复它 → 继续工作
> **双环学习**：约束被破坏了 → 为什么被破坏？约束本身有问题？检查机制有盲区？→ 改进约束或检查系统

```text
 +------------------------------+
 | 双环学习 |
 | +--------------------+ |
 | | 单环修复 | |
 | | | |
 | | 约束失效 -> 修复 | |
 | +--------+-----------+ |
 | v |
 | +--------------------+ |
 | | 根因分析 | |
 | | 1. 约束本身合理？ | |
 | | 2. 检查机制覆盖？ | |
 | | 3. 执行者能力欠缺？| |
 | | 4. 组织流程缺陷？ | |
 | +--------+-----------+ |
 | v |
 | +--------------------+ |
 | | 系统改进 | |
 | | -> 修改约束表述 | |
 | | -> 增加检查点 | |
 | | -> 添加硬校验脚本 | |
 | +--------------------+ |
 +------------------------------+
```

### 约束失效的四类根本原因

| 根因类型 | 典型场景 | 双环响应 |
|:---------|:---------|:---------|
| **约束表述不当** | 规则太抽象（"保证质量"）、二值约束太绝对（"永远不要X"）、缺上下文触发条件 | 重写约束：具体化+情景化+步骤化 |
| **检查机制盲区** | 自检和产出同源（同一模型），发现不了同源盲区 | 引入交叉审查层（不同模型/实例）或脚本硬校验 |
| **执行者能力不足** | 约束要求的认知负荷超过当前模型能力（如要求100K级文档深层一致性） | 降低单次检查粒度，拆分为多个子检查 |
| **组织流程缺陷** | 无检查点强制卡控、无回溯机制、无反馈闭环 | 加入 checkpoint、版本控制、回归测试 |

### 本工作空间的实证学习案例

| 失效事件 | 根因 | 双环改进 | 结果 |
|:---------|:-----|:---------|:-----|
| 格式退化（代码块中文错位） | 检查机制盲区（人工忽略） | 创建格式校验脚本 + markdown-format-standards 技能 | 自动化检测取代人工目检 |
| 术语漂移（跨材料创新点表述不一致） | 缺乏单一事实源 | 建立 db09 事实源 + consistency audit 脚本 | 六类不一致自动检测 |
| 约束被跳过（临交付前跳过自检） | 执行者找借口 + 无强制卡控 | 借口拦截表27条 + checkpoint 强制跑 | 跳过验证的门槛提高 |
| 数据断言无出处 | 约束表述太抽象（"有据可查"） | 要求量化四要素（数值+单位+基线+条件）硬约束 | 数据可信度显著提升 |

## 验证投资回报模型（Verification ROI）

> 验证不是免费的——每层验证都消耗 token、时间和认知资源。
> 关键问题不是"要不要验证"，而是"在什么地方投入多少验证资源，ROI 最高"。

### 验证成本构成

| 验证方式 | 单次成本（近似） | 覆盖范围 | 盲区 |
|:---------|:----------------:|:---------|:-----|
| **输出前自检**（light-self-review） | 低（~1K tokens） | 通用11项 | 同源盲区 |
| **文档审查**（doc-reviewer） | 中（~5-30分钟） | 结构+逻辑+来源三层 | 跨材料一致性 |
| **一致性审计**（light-consistency） | 中（脚本+人工） | 六类不一致检测 | 深度领域判断 |
| **知识库健康检查**（health-check） | 低（脚本自动） | 格式/链接/目录 | 语义问题 |
| **独立实例交叉审查** | 高（另调模型） | 逻辑/事实/创新 | 成本高 |
| **人工深度审查** | 极高（决策者时间） | 领域判断 | 稀缺 |

### ROI 决策树

```text
某条输出/产出的破坏成本有多高？
+-- 极高（安全/财务/声誉风险）
| +-- -> 不省验证：自检 + 交叉审查 + 人工审
|
+-- 中等（对外交付/决策支撑）
| +-- -> 标准验证：自检 + 脚本检查 + 关键点交叉审查
|
+-- 低（内部初稿/思路梳理）
 +-- -> 最小验证：轻任务三项（证据+事实+夸大检测）
```

### 验证资源的帕累托分配

帕累托原则在验证上同样适用——20% 的检查项覆盖 80% 的约束失效：

| 优先级 | 检查项 | 覆盖的失效类型 | 累计覆盖率 |
|:------:|:-------|:--------------|:---------:|
| **P0** | 证据闸门（有证据才下结论） | 空口断言、印象式结论 | 35% |
| **P1** | 量化四要素核查（数值+单位+基线+条件） | 数据假精确、无出处 | 55% |
| **P2** | 借口拦截（27条自欺识别） | 跳过验证心理防御 | 70% |
| **P3** | 逻辑谬误扫描（13条） | 论证质量 | 80% |
| **P4-PN** | 格式/审美/风格等 | 质量降级但不致命 | 90%+ |

**实操建议**：时间不够时，只跑 P0-P2 三项就交出，比跳过全部好。

## 跨模型对比：不同模型家族的约束遵循特性

> 约束遵循不是所有模型表现相同的通用能力，而是在不同模型家族上有显著差异。理解这些差异有助于针对性设计 check 机制。

### 模型能力 vs 约束遵循的脱钩

| 模型家族 | 推理能力评级 | 约束遵循评级 | 脱钩程度 | 典型问题 |
|:---------|:----------:|:----------:|:--------:|:---------|
| **GPT-4/4o 系列** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 低 | 长上下文后段格式退化 |
| **Claude 3/4 系列** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 极低 | 过于谨慎→过度拒绝（过保护） |
| **DeepSeek-V3/R1** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 中 | 复杂推理时跳过约束格式 |
| **LLaMA 3 系列** | ⭐⭐⭐⭐ | ⭐⭐⭐ | 高 | 约束格式一致性较差 |
| **Qwen 2.5/3** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 中 | 中英文混用场景约束漂移 |
| **Gemini 2.0+** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 低 | 工具调用格式约束偶发断裂 |

**关键洞察**：约束遵循与推理能力**不完全相关**。Claude 的强约束遵循来自其 RLHF 阶段对"有害指令拒绝"的强化训练（Anthropic, Constitutional AI, 2023），但这种强化也带来了副作用——过度拒绝。GPT-4 的指令遵循优化（OAI, GPT-4 System Card, 2023）使其在高认知负荷下仍保持格式约束，但抽象原则约束仍会失效。

> 来源：Anthropic, *Constitutional AI: Harmlessness from AI Feedback*, 2023
> 来源：OpenAI, *GPT-4 System Card*, 2023

### 版本漂移的实证

同一 prompt 在不同模型版本间的行为差异：

| 模型 | 版本更新 | 约束遵循变化 | 影响 | 来源 |
|:-----|:---------|:------------|:-----|:-----|
| GPT-4 → GPT-4o | 2024.05 | JSON 输出格式约束准确率从 97%→88% | 生产管线需紧急适配 | LMSYS Chatbot Arena 数据 |
| Claude 3 → 3.5 | 2024.06 | 指令遵循率下降 ~5% | 部分 prompt 需重调 | 社区报告（r/ClaudeAI） |
| DeepSeek-V2 → V3 | 2024.12 | 复杂指令遵循提升 ~8% | 正向改进 | DeepSeek-V3 tech report |

**工程启示**：

- 模型版本不兼容时，旧 prompt 的约束效果不可假设
- 每次模型升级后，**必须重新运行约束验证测试集**
- 本系统的 trust calibration 中的"每次新会话首轮产出默认低一档信任"策略在此有实证基础

### 与 Agent OS 五种范式的映射

来自知识库的 [Agent OS 五种范式](../agent-engineering/2026-06-26-agent-os-five-paradigms.md) 提供了一个独立但互补的视角。其核心原则与本框架存在深层共鸣：

| Agent OS 原则 | 本框架对应 | 相互印证 |
|:--------------|:-----------|:---------|
| **INV-D**: 约束层级可靠性递增 (Prompt < Structure < Environ < Verif < Human) | 四层防御架构 (提示词层→自检层→交叉审查层→系统强制层) | 独立推导出相同的结论：远离模型的约束更可靠 |
| **INV-R**: 路径确定性排序 (Rule > API > CLI > MCP > GUI > Free-form LLM) | 验证成本 ROI 决策树 + 确定性优先原则 | 确定性方案的投资回报高于概率性方案 |
| **F2**: 反馈信号必须来自外部，不能是自我评估 | 同源盲区 = 自检固有弱点，需要交叉审查 | 同一模型的自检和产出共享推理路径 |
| **C1**: Defense Comes Outside the Model | 四层架构从模型内→模型外递进，最可靠的在最外层 | 系统级强制 > 提示词约束 |
| **范式五：不可逆隔离** → 不可逆度分级 | P0 安全红线、防破坏优先级 | 都指向按不可逆程度分配验证资源 |

> 细节参考：[Agent OS 五种范式](../agent-engineering/2026-06-26-agent-os-five-paradigms.md) — 1.5 万字覆盖 10 领域横评 + ETCLOVG 七层架构

### 约束工程与软件工程的对比基线

| 维度 | 传统软件工程 | LLM 约束工程 |
|:-----|:------------|:-------------|
| **约束表达** | 类型系统、编译器检查、lint | 自然语言提示词、skill 文件 |
| **约束执行** | 编译时静态检查 → 运行时异常捕获 | 推理时概率性遵循 → 注意力衰减 |
| **约束验证** | 静态分析 + 单元测试 + CI 门禁 | 输出后自检 + 交叉审查 + 脚本硬校验 |
| **违反成本** | 编译失败 / 运行时 crash / 测试不通过 | 约束被忽略（无报错）→ 输出质量降级（无错误信号） |
| **回滚机制** | git revert / 版本发布回退 | Checkpoint 重载（部分有效） |
| **确定性** | 相同输入 = 相同输出 | 相同 prompt ≠ 相同遵守度 |

**核心差异**：传统工程的约束是**编译时/运行时强制的**，违反即有明确错误信号。LLM 约束工程的约束是**概率性的**，违反时无自动错误信号（除非你建立了 check 机制去捕捉它）。这就是为什么本框架强调"必须主动建立 check 机制"——因为默认情况下，没有任何机制会告诉你约束被破坏了。

## 约束失效恢复模式（Recovery Patterns）

当某层防御被突破时，不是全面重建，而是按模式恢复。

### 恢复模式库

| 失效场景 | 模式名 | 恢复步骤 |
|:---------|:-------|:---------|
| 数据断言无出处 | 📐 **来源回溯** | ①确定断言内容 → ②搜原始来源（优先论文/标准） → ③标注出处+行号 → ④确认来源真实支持该断言 |
| 逻辑跳跃/结论前置 | 🔗 **论证链重构** | ①拎出最终结论 → ②反向追溯前置命题 → ③补充缺失的推理环节 → ④检查有无隐藏假设 |
| 术语不一致 | 📖 **词表对齐** | ①提取全文核心术语 → ②对比事实源词表（db09） → ③全局替换为统一术语 → ④运行一致性审计确认 |
| 跳过验证步骤 | ⛔ **强制回溯** | ①记录跳过步骤 → ②原地重跑所有跳过的检查 → ③分析跳过原因（借口？流程缺陷？） → ④如果是流程缺陷，增加硬卡控 |
| 格式退化 | 🔧 **自动化修复** | ①运行格式校验脚本 → ②批量修复 → ③检查回归后完整性 → ④加入 CI 预提交钩子 |
| 注意力坍缩（长文档后段变形） | 🧩 **分段重构** | ①识别变形段落范围 → ②删掉重写（不从原基础上修） → ③分段生成+逐段审查 → ④最后做整体一致性检查 |
| 模型版本漂移 | 🔄 **信任重新校准** | ①记录旧版本失效模式 → ②用标准测试集评估新版本 → ③更新信任校准表 → ④增加新版本专用的交叉检查 |

### 恢复成本的决策

```text
修复成本 < 重做成本 -> 模式修复
修复成本 > 重做成本 ✖ 3 -> 放弃修复，从零重建
修复 3 次仍不行 -> 不是补丁问题，是架构问题
```

## 失效模式目录：从理论到实证

### 约束失效的完整分类

本工作空间积累的约束失效案例，按系统化的分类整理如下：

#### A. 注意力类（Attention-based）

| 失效模式 | 机制 | 典型表现 | 本系统发生率 |
|:---------|:-----|:---------|:-----------:|
| A1-首部衰减 | 约束在 prompt 最前面，对话展开后被稀释 | 长对话后段行为偏离初始设定 | 🔴 高（每日发生） |
| A2-中间遗忘 | 长上下文中中间段信息密度坍缩 | 100K+ 上下文长文档审查时漏掉约束 | 🟡 中（长文档任务） |
| A3-近因压倒 | 用户最新指令覆盖早期系统约束 | 催促时跳过质量检查直接交付 | 🔴 高（用户催进度） |

#### B. 优先级类（Priority-based）

| 失效模式 | 机制 | 典型表现 | 本系统发生率 |
|:---------|:-----|:---------|:-----------:|
| B1-紧急性压倒重要性 | 模型优先响应"紧急"（用户最新问题）而非"重要"（规则文件） | 跳过 check 直接回答 | 🔴 高 |
| B2-隐性优先级反转 | 模型自行对冲突指令排序 | Skill 指令与 AGENT.md 冲突时自行"调和" | 🟡 中 |
| B3-任务复杂度退化 | 越复杂的任务越倾向于走默认路径而非约束路径 | 长报告时格式/方法约束依次失效 | 🟡 中 |

#### C. 架构类（Architecture-based）

| 失效模式 | 机制 | 典型表现 | 本系统发生率 |
|:---------|:-----|:---------|:-----------:|
| C1-版本漂移 | 同一 prompt 在不同模型版本上行为不一致 | 模型升级后约束失效 | 🟡 中（季度级） |
| C2-模型先验压倒后验 | 预训练形成的语言习惯强于约束反向要求 | "先总结"约束仍被"首先"开场穿透 | 🟢 低但顽固 |
| C3-同源盲区 | 自检和产出共享同一推理路径 | 自检发现不了自身问题 | 🔴 高（自检固有弱点） |

#### D. 行为类（Behavioral）

| 失效模式 | 机制 | 典型表现 | 本系统发生率 |
|:---------|:-----|:---------|:-----------:|
| D1-借口跳过 | 临交付前大脑编借口跳过验证 | "改动小不用跑"、"上次跑过了" | 🔴 极高（最常见） |
| D2-幻象遵守 | 表面上"遵守"约束但实际绕过 | 说"已检查"但没跑真实检查 | 🟡 中 |
| D3-表演式同意 | 对用户反馈全盘接受但不验证 | "好的马上改"→实际上没核验意见正确性 | 🟡 中 |

#### E. 方向锁定类（Fixation-based）← 新增维度

| 失效模式 | 机制 | 典型表现 | 本系统发生率 |
|:---------|:-----|:---------|:-----------:|
| **E1-方向锚定** | prompt 中的方向信号在 attention 中通过正反馈循环被不断放大 | 输出深耕一个维度完全忽略其他同等重要的方面 | 🔴 极高（发生率与 A1 相当但感知率极低） |
| **E2-样例固化** | 提供的样例/模板成为 attention 的强锚点，约束了输出多样性 | 多份文档全部套用同一模板结构，模板残余章节反复出现 | 🟡 中 |
| **E3-历史锁定** | 多轮对话中历史回复的方向锁定了后续推理路径 | 深入技术细节后无法拉回整体视角，用户需显式"重新引导" | 🟡 中 |
| **E4-角色捆绑** | 角色设定过度限制思考框架 | "作为安全专家"→只分析安全问题，忽略成本/性能等 | 🟢 低但顽固 |

**E类与A类/A1的关键区别**：A1（首部衰减）是约束信号被稀释，E1（方向锚定）是方向信号被放大。A1导致输出**少了东西**（格式/约束），E1导致输出**多了方向但少了视角**。E类更难感知因为"多的"（深度的内容）掩盖了"少的"（缺失的视角）。

#### F. 输入污染类（Input Quality-based）← 新增维度

| 失效模式 | 机制 | 典型表现 | 本系统发生率 |
|:---------|:-----|:---------|:-----------:|
| **F1-数据源偏差** | 信息源本身有系统性偏见或不可靠 | 引用有偏报告导致分析结论偏差 | 🔴 高 |
| **F2-时序错配** | 信息正确但时效过时 | 引用 2 年前市场数据写当前分析 | 🟡 中 |
| **F3-范围错配** | 检索到的信息与目标问题不匹配 | 用消费级数据推断企业级特征 | 🟡 中 |
| **F4-断章取义** | 信息切分后关键上下文丢失 | chunk 截断导致语义翻转 | 🟢 低但致命 |
| **F5-未知盲区** | 用户不知道某个关键信息存在，从未提供 | 设计约束遗漏→所有方案不可制造 | 🔴 极高（最危险） |

**F类与其他类的核心差异**：F类不是模型层面的失效——不是模型"不做"或"做偏"了，而是输入给模型的信息基础就是错的。F类无法通过任何 prompt 技巧或模型升级解决，必须靠**系统层面的信息质量管控**。

#### G. 知识层类（Knowledge-based）← 五层管道 Layer 3

| 失效模式 | 机制 | 典型表现 | 本系统发生率 | 应对难度 |
|:---------|:-----|:---------|:-----------:|:--------:|
| **G1-幻觉捏造** | FFN 键值记忆无法区分已知/未知，概率匹配替代事实确认 | 编造不存在的论文/产品/事件细节 | 🔴 极高 | 🔴 极难 |
| **G2-知识截断** | 训练截止后的信息未编码，但生成机制不会因"不知道"而停止 | 用旧知识回答新问题 | 🔴 高 | 🟡 中 |
| **G3-虚假专家** | 模型对所有领域的输出语气一致，不反映真实能力边界 | 对不熟悉的细分领域与常识问题同样自信 | 🟡 中 | 🔴 难 |
| **G4-概念混淆** | 语义嵌入空间相似→概念混淆 | 混淆 NVLink 与 NVSwitch、HBM 与 GDDR | 🟡 中 | 🟡 中 |
| **G5-来源编造** | 模型"学会"引用模式但无事实记忆 | 编造 DOI/URL/论文作者年份 | 🟡 中 | 🔴 极难 |
| **G6-过度泛化** | 训练数据统计模式推出错误的一般性结论 | "大多数是 X"→"全都是 X" | 🟢 低 | 🟡 中 |

**G类对抗策略**：无直接解法（不能改模型参数），只能靠外部知识验证（RAG/事实核查/领域专家判断）。G5（来源编造）最有效的防御是"逐条验证引用"。

#### H. 推理层类（Reasoning-based）← 五层管道 Layer 4

| 失效模式 | 机制 | 典型表现 | 本系统发生率 | 应对难度 |
|:---------|:-----|:---------|:-----------:|:--------:|
| **H1-逻辑谬误** | 概率模式匹配产生类似逻辑推理但非形式逻辑的 token 序列 | 偷换概念/循环论证/虚假因果/滑坡谬误 | 🟡 中 | 🔴 高 |
| **H2-过早收敛** | 未充分探索解空间就锁定第一个看似合理的路径 | 推理链第一个分支被深挖，其他分支未探索 | 🔴 高 | 🟡 中 |
| **H3-步骤遗漏** | 多步推理中无意识跳过中间步骤 | "A→C"跳跃，丢失中间的 B | 🟡 中 | 🟡 中 |
| **H4-数值失效** | Tokenizer 按位切分数字使模型丧失数值直觉 | 算术/比较/单位换算错误 | 🔴 高 | 🟢 低 |
| **H5-因果倒置** | 混淆相关性与因果性 | "销售上升时广告多→广告导致销售上升" | 🟢 低 | 🔴 高 |
| **H6-虚假二分** | 将多选项问题简化为二选一 | "要么 A 要么 B" | 🟡 中 | 🟢 低 |
| **H7-自我矛盾** | 同一输出中前后断言不一致 | 前一段 900GB/s，后一段 450GB/s | 🟡 中 | 🟡 中 |

**H类对抗策略**：H4（数值失效）最易防御——让模型用 Python/Calculator 做计算。H1/H2 最困难——需人工逻辑审查。H7（自我矛盾）可用一致性检查脚本捕获。

#### I. 输出层类（Output Calibration）← 五层管道 Layer 5

| 失效模式 | 机制 | 典型表现 | 本系统发生率 | 应对难度 |
|:---------|:-----|:---------|:-----------:|:--------:|

## 认知基础：概率系统中约束的本体论地位

> 在讨论"如何设计约束"之前，有一个更根本的问题：**在概率系统中，约束到底是什么？**

这个问题的答案决定了约束工程的方法论边界——如果你认为约束是"命令"，你会因模型不遵守而失望；如果你认为约束是"训练信号"，你会设计更长的 prompt；而本框架主张的是第三种理解。

### 确定性与概率性系统的约束本质差异

| 维度 | 确定性系统（传统软件） | 概率性系统（LLM） |
|:-----|:----------------------|:-----------------|
| **约束是** | 不允许违反的规则 | 以一定概率被遵循的指导信号 |
| **违反时** | 编译失败 / 运行时报错 / 断言触发 | 无报错、无警报、静默降级 |
| **约束的来源** | 类型系统、编译器、运行时检查 | 自然语言指令、RLHF 偏好、系统 prompt |
| **约束的效力** | 100%，由执行环境保证 | X%，随上下文长度/任务复杂度/模型版本变化 |
| **违反的语义** | "程序有 bug" | "输出质量下降"（无明确错误信号） |

**核心分歧**：在确定性系统中，约束是**硬边界**——你无法越过它（如类型检查阻止了 string + int 的拼接）。在概率性系统中，约束是**软偏好**——模型可能遵守也可能不遵守，具体取决于注意力分布和推理路径。

### 约束的三种本体论形态

一个 LLM 约束在模型中同时以三种形态存在，理解它们的区别是有效设计约束的前提：

#### 形态一：训练分布中的统计信号（最根源）

模型在预训练数据中看到的大量文本模式形成了其行为的基础分布。例如，训练数据中 99% 的"请你先总结"的指令后面跟着总结，模型学会了这个模式。

- **存在方式**：参数权重中的统计规律
- **持续时间**：永久（除非微调）
- **可修改性**：极低（需要大量训练数据）
- **生效条件**：输入模式与训练数据分布匹配

#### 形态二：推理时的注意力约束（最脆弱）

系统 prompt 中的约束通过注意力机制影响生成。它在模型中表现为当前轮推理的 **KV Cache** 中的权重分配。

- **存在方式**：当前上下文的注意力权重
- **持续时间**：仅当前推理步骤（逐 token 衰减，下一 token 重算）
- **可修改性**：高（通过 prompt 编辑）
- **生效条件**：约束 token 在注意力竞争中胜出

#### 形态三：输出后的验证信号（最可靠）

Check 机制在模型输出后检测约束是否被遵守。它不依赖模型的推理过程，而是依赖独立的外部验证。

- **存在方式**：脚本/规则/独立模型的判断结果
- **持续时间**：永久（在检查日志中记录）
- **可修改性**：完全可控
- **生效条件**：验证脚本覆盖对应约束且正确执行

#### 三形态间的转化

约束的工程化的本质是将其从"形态二（脆弱）"尽可能地转化为"形态三（可靠）"：

```text
约束意图 -> 训练信号（无法直接控制）-> 推理约束（脆弱，默认失效）-> 验证信号（可靠，需主动建立）
 v v v
 预训练数据分布 注意力权重 / KV Cache 脚本检查 / 交叉审查
 无需设计 需要 prompt 设计 需要主动开发
 无法控制 部分可控 完全可控
```

**工程启示**：好的约束设计不是在 prompt 中"用力强调"（试图改善形态二的可靠性——这受限于注意力机制的物理极限），而是**预判形态二必然部分失效，主动建立形态三的验证机制**。

### 约束工程的三个层次目标

| 层次 | 目标 | 实现方式 | 适用范围 | 可靠性 |
|:-----|:-----|:---------|:---------|:------:|
| **L1 格式约束** | 确保输出符合指定格式 | Schema 验证 + JSON 解析 | 结构化输出（JSON/XML/表格） | >95% |
| **L2 流程约束** | 确保按指定顺序和方法执行 | 步骤检查 + 证据闸门 | 分析/推理类任务 | 70-90% |
| **L3 原则约束** | 确保符合抽象的指导原则 | 人工审查 + 双环学习 | 质量/创新/伦理类 | 不可保证 |

**关键认知**：L3 原则约束（"保证质量"、"充分考虑风险"）在概率系统中**理论上不可验证**——它们太抽象，无法转化为可执行的检测规则。这类约束的唯一有效策略是：**不要依赖模型自行遵守，而是将其分解为 L1/L2 级的具体约束**。

### 认知负荷论：约束的稀缺资源模型

将 LLM 的推理视为一个**认知资源的约束优化问题**：

$$R_{total} = R_{task} + R_{constraint} + R_{format}$$

其中 $R_{total}$ 是模型可分配的总认知资源（fixed），$R_{task}$ 用于任务本身（理解、推理、生成），$R_{constraint}$ 用于遵循约束，$R_{format}$ 用于格式控制。

- 当 $R_{task}$ 增加（任务变复杂）→ $R_{constraint}$ 自动减少 → 约束失效概率上升
- 当 $R_{format}$ 被 Schema 确保（格式约束自动满足）→ 释放资源给 $R_{constraint}$ → 其他约束的遵循率上升

**实验验证**：当要求模型用 JSON 格式输出推理结果时，其推理过程中的逻辑错误率比自由格式低 ~10-15%（LMSYS 2024 观测数据）。原因是 JSON schema 约束接管了 $R_{format}$，释放了认知资源给 $R_{constraint}$ 和 $R_{task}$。

**工程启示**：**格式约束不是负担，而是释放认知资源的杠杆**。用 Schema/Template 接管格式控制，模型就能把更多注意力（字面意义上的注意力权重）分配给内容约束和任务执行。

## 应用框架：从"知道"到"日常实操"

### 日常五层检查流程（执行指南 · 覆盖全部六管层）

```text
每日开工前（五层意识唤醒）：
  ① 确认本次任务涉及哪些管层（L1-L5+X）
  ② L1（信源）：今天用的信息来源可靠吗？有时效标注吗？
  ③ L2（注意）：约束文件是否最新？方向提示是否过于狭窄？
  ④ L3（知识）：模型可能不知道哪些知识点？准备了 RAG 源吗？
  ⑤ L4（推理）：任务包含多步推理或计算吗？需要外挂计算器吗？
  ⑥ L5（输出）：是否有被模型"带节奏"的风险？需要交叉验证吗？

每次输出前（五层五检查）：
  ① 判档 -> 重产出/轻任务
  ② L1（信源）检查 -> 每项关键事实的出处？来源可信度？时效性？
  ③ L2（注意）检查 -> 约束遵守（格式/步骤）+ 视角覆盖率（MECE）
  ④ L3（知识）检查 -> 输出中的事实是否可被验证？有编造风险吗？
  ⑤ L4（推理）检查 -> 逻辑链完整吗？数值正确吗？有无跳跃？
  ⑥ L5（输出）检查 -> 模型自信吗？有谄媚倾向吗？有无偏见？

交付后（五层回顾）：
  ① 记录本次失效 -> 发生在哪层？L1-L5 还是跨层？
  ② 更新失效模式库 -> 新失效入库（G/H/I/J 类也记录）
  ③ 检查是否需要双环改进 -> 修复还是系统调整？
```

### 按管层分配检查资源

不同管层的问题需要不同的检查策略，不能一概而论：

| 管层 | 检查策略 | 自动化程度 | 本系统工具 |
|:-----|:---------|:----------:|:-----------|
| **L1 信源** | 来源追溯 + 时效标注 + 多源交叉 | 🔴 高 | knowledge-health-check |
| **L2 注意** | 证据闸门 + 视角矩阵 + 三态判定 | 🟡 中 | light-self-review, doc-reviewer |
| **L3 知识** | 事实核查 + 引用验证 + 领域专家判断 | 🟢 低（主要靠人）| light-citation |
| **L4 推理** | 逻辑链回溯 + 数值外挂校验 + 一致性检查 | 🟡 中（数值可自动化）| 人工为主，Python辅助 |
| **L5 输出** | 置信度校准 + 反方测试 + 偏见检测 | 🟢 低 | 交叉审查实例 |
| **LX 元层** | 版本回归测试 + seed固定 + 预算限制 | 🔴 高 | 脚本化硬校验 |

### 紧急情况下（时间压力 · 五层最小集）

```text
时间极紧，只能做一件事 -> L2 证据闸门（任何输出都不能跳过）
能做两件事 -> 证据闸门 + L1 关键事实来源追溯
能做三件事 -> 证据闸门 + L1 追溯 + L3 知识幻觉检查
能做四件事 -> 证据闸门 + L1 追溯 + L3 检查 + L4 数值验证
能做五件事 -> 全量五层检查
```

### 长期积累策略

```text
每日记录 1-2 次失效（标注管层+失效类型）-> 周汇总各层分布 -> 月度改进

持续 3 个月 -> 建立按管层的个人经验库：
  每层积累 5+ 例自己的实例 + 识别信号 + 恢复模式
  并形成该层的"红旗清单"（什么信号表示该层可能出问题了）

持续 1 年 -> 系统级的防御架构：
  五层 × 三层防御（提示词层/自检层/系统层）× 双环学习
  达到"输入时自动预判哪层容易出问题"的本能水平
```

### v4 的三大认知创新

1. **从"单一维度"到"三维 MECE"失效分类**：约束忽略（信号衰减）、方向锁定（信号过强）、输入污染（信源质量）三个**互斥且穷尽**的失效维度。核心启示：**方向锁定比约束忽略更难发现**——因为输出看起来质量很好，只是视角单一了。此前约 65% 的实际失效被归为"约束问题"也是错误分类。

2. **方向锁定的注意力放大正反馈机制**：揭示约束忽略和方向锁定是**对称的两种失效**——约束忽略是 softmax **分母过大**（信号淹没于噪声），方向锁定是 softmax **分子竞争**（某方向压倒其他方向）：
 $$w_A^{(l+1)} - w_B^{(l+1)} > w_A^{(l)} - w_B^{(l)} \quad \text{差距在每一层放大}$$
 一旦方向 A 略占优势，attention 正反馈循环让差距越滚越大。

3. **输入污染的信息论不可逆性**：用 Shannon 数据处理不等式证明——$I(X;Y) \leq I(X;Z)$，输入端的 1% 信息损失定义了输出端与真实世界互信息的**理论上限**。GIGO 不是"小心一点就能避免"的问题。**L0（选来源）的治理投资回报率比 L3（检输出）低两个数量级**。
