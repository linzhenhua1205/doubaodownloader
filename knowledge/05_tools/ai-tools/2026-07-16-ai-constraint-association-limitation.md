## 1. 问题现象：为什么差距这么大？

### 1.1 场景对比

| 维度 | ✅ AI擅长（单文件/低关联） | ❌ AI做不好（多文件/强约束） |
|:-----|:--------------------------|:----------------------------|
| **示例** | 写一个独立的 Python 函数、翻译一篇文章、压缩一张图片、格式化一段 JSON | 重构 15 个文件保持接口一致、实现一个需满足 8 条冲突约束的架构方案、跨模块对齐 50+ 字段定义 |
| **关联数量** | 1~3 个内部约束 | 10+ 条跨文件/跨模块约束 |
| **约束类型** | 局部语法/格式规则 | 全局一致性 + 业务逻辑 + 接口契约 + 性能约束 |
| **反馈周期** | 立即（语法验证） | 需要交叉检查才能发现（编排检查） |
| **出错代价** | 低（修复一行） | 高（接口不匹配引起连锁修复） |

### 1.2 典型翻车场景

**场景A：跨文件重构**
> 要求 AI 重命名一个公共接口，AI 正确地更新了实现文件，但忘了更新调用它的 3 个模块和对应的单元测试文件。

**场景B：多约束架构设计**
> 要求 AI 设计一个同时满足功耗<150W、延迟<5μs、成本<80 美元、兼容三代 CPU 的电路方案。AI 给出了精美的架构图，但深究后发现功耗估算用了理想值（漏算了 20% 的开关损耗），成本只算了 BOM 没算 NRE。

**场景C：一致性维护**
> 在 knowledge base 中维护 50+ 交叉链接的文档体系。AI 新增了一篇文档，更新了 index.md，但忘了更新父目录的 log.md 和 cross-reference 中的反向链接。

**场景D：矛盾约束权衡**
> 要求 AI "在保证性能的前提下降低成本"。AI 给出的方案直接降低了 CPU 主频——违反了用户隐含的"性能不可妥协，成本可以从 PCB 层数省"的优先级。

## 2. 根因分析：三层架构的先天缺陷

要理解为什么 AI 在关联约束场景下表现差，需要从大语言模型（LLM）的工作机制入手。这不是"不够智能"的问题，而是其信息处理架构与人类认知在**根本结构上不同**。

### 2.1 信息表示层：Lossy 压缩

#### 2.1.1 上下文窗口 → 物理截断

LLM 接受输入的物理上限是上下文窗口（context window）。即使窗口扩展到 1M tokens，**窗口内的信息质量也不均匀**：

```text
信息质量随位置衰减曲线：

高 |#############################
   |##########################
   |########################
   |######################
   |####################
   |###############     <- "Lost in the Middle"[1]
   |###########
   |#######
低 |##
   +------------------------------
    开头的文件    中间的关联约束    末尾的最新指令

结论：多个关联文件放在上下文中时，中间的约束信息最容易丢失。
```

[1] Liu et al., "Lost in the Middle: How Language Models Use Long Contexts", 2023.

#### 2.1.2 注意力衰减 → 跨文件关联退化

Transformer 的注意力机制虽能关注序列中任意位置，但实际效果受以下因素制约：

| 因素 | 对单文件影响 | 对多文件关联的影响 |
|:-----|:-----------|:-----------------|
| **位置编码** | 文件内位置连续，相对位置编码正常工作 | 文件边界破坏位置连续性，"跨文件跳转"的注意力路径更长 |
| **注意力稀释** | 约束密度适中，注意力集中 | 多个文件的内容混在一起，注意力分散到大量不相关的 token 上 |
| **分段效应** | 无 | AI 倾向于将注意力集中在"最近出现"或"序列开头"的信息，跨文件约束往往落在中间 |
| **表征退化** | 不受影响 | 长上下文上的 attention sink 现象——末尾 token 占有不成比例的注意力 |

#### 2.1.3 独立 Token → 无法表达结构性约束

LLM 的基本处理单元是 token，约束是一种**结构性信息**——"A 文件中的 x 必须与 B 文件中的 y 一致"——这种关系无法被压缩成 token 序列的局部模式。

```text
Token 表示:
  A.x  = 0x1234  ...  B.y  = 0x1234

AI "看到"的是:
  两个独立的数值声明

AI "看不到"的是:
  约束: A.x ≡ B.y（必须在任何修改中保持同步）
```

**本质**: LLM 没有原生机制来追踪跨 token 的约束绑定关系。

### 2.2 推理结构层：单通道规划缺失

#### 2.2.1 自回归生成 → 无全局规划阶段

人类在写多文件代码时的做法：

1. **规划阶段**: 阅读所有文件，理解关系，制定修改计划
2. **执行阶段**: 按计划依次修改
3. **验证阶段**: 检查跨文件一致性

LLM 的做法：

```text
输入所有文件 + 指令
       v
立即开始生成 token（自回归）
       v
逐 token 走向结束，没有回头路
       v
（除非外部触发重试，否则不会自发修正）
```

**关键缺陷**: AI **没有全局规划阶段**。它边生成边"想"，"想"的过程就是生成的过程。对于跨 5 个文件的修改，AI 在第 1 个文件生成到第 50 个 token 时，已经失去了对另外 4 个文件的"注意力"。

#### 2.2.2 早期承诺 → 后期无法修正

```text
时间轴 ->
文件A edit: 将接口名改为 getData()
文件B edit: 需引用文件A的新接口名 getData()
            ↳ 此时 AI 已经忘记了要把接口名改成什么

原因: 生成文件A时，AI"记住"了 getData()
      生成文件B时，注意力已被文件B的内容占据
      文件A的决策已经从工作记忆中滑出
```

自回归模型的一个根本限制是：**无法回溯修正**。一旦生成了某个 token，它就固化了。虽然外部可以做重试/重新生成，但模型内部没有"草稿-修改"机制。

#### 2.2.3 约束跟踪依赖 → 隐式概率而非显式绑定

人类跟踪约束的方式：

```text
约束清单（显式）:
1. 性能 ≥ 100 TOPS
2. 功耗 ≤ 150W
3. 成本 ≤ $80
4. 兼容 Gen3/Gen4/Gen5

-> 每次决策时显式检查清单
```

AI 跟踪约束的方式：

```text
约束被编码在 token 之间的注意力权重中

当 AI 在生成"我们选择 28nm 工艺"时：
- 它"记得"有性能约束（注意力指向开头提到的性能要求）
- 它"忘记了"有成本约束（注意力被中间内容稀释）
- 结果：28nm 性能达标但成本超了
```

**本质**: 约束是多重目标函数而非检查清单。AI 隐式地试图满足所有约束，但**缺乏显式的约束优先级和一致性检查**。

### 2.3 记忆管理层：无持久工作空间

#### 2.3.1 每次生成是全新推理

```text
多文件重构任务：

人类工作记忆：
  +- 文件A (当前编辑)
  +- 文件B (缓存状态)
  +- 文件C (修改目标)
  +- 约束清单 (主动维护)
  +- 已修改/待修改标记 (持续跟踪)

AI "工作记忆"：
  +- 当前正在生成的 token（唯一确定的内容）
  +- 注意力窗口中的 token（有优先级衰减）
  +- 暂存状态 ✗（无）
```

**人类优势**: 可以同时持有多个文件的状态，并在工作记忆中维护修改进度。AI 的"工作记忆"就是当前 token 周围的注意力窗口。

#### 2.3.2 多文件处理本质上是序列化推理

AI 处理多文件任务时，实际上是在**逐个文件**地生成内容。但系统提示和约束在**所有文件上共享**。这导致了：

```text
生成文件A时 -> 约束全部都在上下文中 -> 表现良好
生成文件B时 -> 忘记文件A中已经做了什么 -> 冲突/不一致
生成文件C时 -> 忘记文件A和B -> 进一步偏离
```

这种退化是指数级的。5 个文件的任务比 2 个文件的任务差远不止 2.5 倍。

#### 2.3.3 缺乏 "修改追踪" 概念

```text
人类修改代码时：
  "我刚刚在 file_a.py 中把 log_level 改成了 'INFO'，
   这意味着 file_b.py 中的 filter 条件也需要更新"

AI 修改时：
  "现在我要修改 file_b.py"
  -> 注意力从 file_a 转移到了 file_b
  -> log_level 的修改记录随注意力转移而丢失
  -> 除非 file_a 的修改恰好还在注意力窗口内
```

AI 没有"改了什么"这个中间状态概念。每次生成都是"从零开始的推理"，而非"基于已修改状态的增量工作"。

## 3. 失效模式分类

### 3.1 约束遗忘（最常见）

| 子类型 | 表现 | 严重程度 | 发生频率 |
|:-------|:-----|:--------:|:--------:|
| **位置遗忘** | 约束在上下文中间→生成到后半段时丢失 | ★★★ | 极高 |
| **竞争遗忘** | 多个约束互相冲突，AI 选了一个忘了另一个 | ★★★★★ | 高 |
| **隐含遗忘** | 用户没有显式说但隐含的约束（如"合理成本"中的"合理"） | ★★★★★ | 极高 |

**实际表现**:

- 开始：AI 说"根据您的 5 个要求……"
- 中间：提到了 3 个
- 结尾：只记得 1~2 个

### 3.2 局部连贯—全局矛盾

每个部分单独看都正确，合起来就矛盾：

```text
文件A: interface Port { speed: number; }
文件B: class PortImpl implements Port { speed: string; }
        ^ 类型不匹配，但 AI 生成时不知道文件A里 speed 是 number
```

**典型场景**: 数据库 schema + API 层 + 业务逻辑三层独立生成后的字段类型不一致。

### 3.3 伪约束满足

AI "声称"满足了约束，但实际上没有：

```text
用户要求: "延迟 < 5ms"

AI 回复: "我们的设计确保了低延迟，远低于 5ms 的阈值"
但是:
  1. 没有给出具体延迟数值
  2. 实际的架构设计（跨 NUMA 访问 + QPI 转发）延迟 > 8ms
  3. AI 只是"宣称"了满足，没有经过推理验证
```

**原因**: 约束满足在 AI 的生成中是一个**修辞目标**，而非**计算验证目标**。

### 3.4 优先级颠倒

多个约束存在隐性优先级时，AI 往往选错：

```text
正确优先级: 安全性 > 性能 > 成本 > 可维护性
AI 的选择: 高性能方案，安全性有后门但需要"后期修复"

问题: AI 没有理解"安全性的优先级高于性能"这一隐性约束
```

### 3.5 跨引用断裂

最典型的多文件失效模式：

```text
修改文件A -> 忘记更新文件B中对文件A的引用
修改文件B -> 忘记更新文件C中对文件B的引用
修改通用配置 -> 忘记更新所有依赖它的模块
```

**复杂度**: 随文件数量线性增长（用户感觉到），但实际是**超线性**增长（因为交叉引用会形成网络）。

## 4. 系统级改善策略

基于根因分析，问题不是"LLM 不够聪明"，而是**信息架构不匹配**。因此改善策略不是"让 AI 更聪明"，而是**改变任务组织和信息传递方式**。

### 4.1 约束显式化：将隐性关联变为显式清单

**原理**: AI 不强于隐式约束跟踪，强于遵循显式清单。把"记住"变成"对照检查"。

#### 4.1.1 约束提取模板

在启动多关联任务前，先让 AI 提取并罗列所有约束：

```text
请读我上传的这 5 个文件。在开始修改前：
1. 首先列出你识别到的所有约束（包括显性的和隐含的）
2. 给每个约束编号 C1-CN
3. 标注约束的优先级（P0=不可妥协/P1=重要/P2=可协商）
4. 标注约束之间的冲突关系
5. 列出受影响的文件范围
```

**效果**: 强制 AI 在"规划阶段"建立约束清单，而非在生成过程中被动跟踪。

#### 4.1.2 约束清单检查点

```text
单文件生成完成后，使用检查清单验证：
□ 本文件满足约束 C1-C3
□ 本文件没有引入新约束与新文件冲突
□ 本文件变更已在约束影响矩阵中记录
```

#### 4.1.3 约束冲突显式化

当约束有冲突时，不要让 AI "自己判断"：

```text
❌ 不要说: 在性能和成本间取得平衡
✅ 应要求: 列出性能和成本在此设计中的具体冲突点，
           给出 3 种权衡方案及其量化指标：
           - 方案A: 性能最优（xx TOPS），成本 xx
           - 方案B: 成本最优（$xx），性能 xx
           - 方案C: 平衡（折中指标）
```

### 4.2 编排器模式：跨文件问题降维为单文件问题

这是当前最有效的策略。核心思想：**不让 AI 在一个回合内处理多个文件，而是用外部编排器管理跨文件状态**。

#### 4.2.1 工作原理

```text
传统方式（❌）:
用户 -> AI（一次读5个文件，同时改） -> 输出（一致性差）

编排器方式（✅）:
用户 -> 编排器
         +- 1. 分析阶段: AI读所有文件 -> 输出结构化的依赖图和修改计划
         +- 2. 单文件修改: 循环每个文件
         |    每次只给 AI 一个文件 +
         |    该文件相关的约束子集 +
         |    已修改文件的变更摘要
         +- 3. 验证阶段: AI检查跨文件一致性
         +- 4. 修复阶段: 按验证结果迭代
```

#### 4.2.2 编排器关键职责

| 职责 | 为什么 AI 做不好 | 编排器怎么做 |
|:-----|:----------------|:------------|
| **状态管理** | 无持久工作记忆 | 维护"已修改文件清单+变更摘要"，在每次调用中传递给 AI |
| **约束分配** | 全部约束容易丢 | 只传给 AI 当前文件相关的约束子集 |
| **交叉验证** | 自回归无法回溯 | 完成后独立验证一致性 |
| **变更传播** | 不知道改了什么 | 跟踪变更并标记需要级联更新的文件 |
| **冲突检测** | 隐式概率满足 | 显式检查约束违反 |

#### 4.2.3 实践示例

```yaml
# 编排器的工作流程（以多文件重构为例）
步骤1: 分析依赖
  - 输入: 全部文件 + 修改需求
  - AI 产出: 依赖图 + 修改计划 + 约束清单
  - 人工审核: 计划是否合理

步骤2: 按依赖逆序修改（先改被依赖文件）
  - 对每个文件：
    输入: 该文件 + 约束子集 + 已修改文件的变更摘要
    输出: 修改后的文件
    检查: 约束违反检查

步骤3: 完整验证
  - 给 AI 全部修改后的文件
  - 要求: 检查一致性、完整性、无冲突

步骤4: 迭代修复
  - 对验证发现的问题，回到步骤2修复
```

### 4.3 验证循环：事后校验弥补事前遗忘

**原理**: AI 生成为一次性通过、事后验证可以检查跨越多个生成步骤的一致性。既然不擅长一次做对，就改为"生成→检查→修正"的循环。

#### 4.3.1 分层验证

| 验证层 | 检查内容 | 适用阶段 | 工具化可行性 |
|:-------|:---------|:---------|:-----------:|
| **L1 语法** | 代码语法、文档标记格式、JSON 合法性 | 每次生成后 | ✅ 完全自动化 |
| **L2 接口** | 跨文件接口签名一致性、类型匹配 | 多文件修改后 | ✅ 高（TypeScript/Protobuf 等） |
| **L3 语义** | 业务逻辑一致性、约束满足性 | 交付前 | ⚠️ 部分可自动化 |
| **L4 端到端** | 完整流程验证 | 交付前 | ⚠️ 需人工参与 |

#### 4.3.2 自验证提示技术

在同一个上下文中，让 AI 自己检查自己的输出：

```text
第一阶段：生成
  请完成以下文件修改：[需求]

第二阶段：自检
  现在，请以最挑剔的审稿人身份，检查你刚才的修改：
  1. 所有跨文件接口是否一致？（检查文件A、B、C中的xx接口）
  2. 是否满足初始的所有约束？（检查 C1-C8）
  3. 是否存在任何潜在的不一致？

  找出所有问题，然后给出修复方案。
```

**原理**: "自检查"与"生成"使用的是同一套推理能力，但检查阶段的注意力分布不同——从"构造"切换到"检查"，更容易发现问题。

### 4.4 分级接入：匹配任务复杂度与接入方式

不同类型的任务应该用不同的策略接入。一刀切说"AI 不好用"或"AI 全能"都不对。

#### 4.4.1 任务复杂度分类

```text
                 多
                 ^
  约束数量/      |   III类          IV类
  关联复杂度      |  (编排器模式)    (人机协作)
                 |  多文件重构      系统架构设计
                 |  跨模块对齐      多约束优化
                 |  全局一致性      矛盾权衡决策
                 |
                 |   I类           II类
                 |  (直接生成)     (单次+验证)
                 |  单文件编写     单模块边界修改
                 |  格式转换       有小量外部依赖
                 |  翻译/摘要      需参考少量约束
                 |
                 0------------------------------
                 少            文件/模块数量    多
```

| 类别 | AI 表现 | 推荐模式 | 示例 |
|:----:|:-------:|:---------|:-----|
| **I类** | 优秀 ✅ | 直接生成 | 写一个独立函数、翻译文档、格式转换 |
| **II类** | 良好 ⚠️ | 生成 + 验证 | 修改单文件但需参考 2~3 个外部约束 |
| **III类** | 差 ❌ | 编排器 + 验证循环 | 跨文件重构、接口对齐、全局一致性 |
| **IV类** | 极差 ❌❌ | 人机协作 | 系统架构决策、矛盾约束权衡、战略规划 |

#### 4.4.2 分级策略

**I类（直接生成）**：

- 一次性输入 + 输出
- 不需要验证

**II类（生成 + 验证）**：

- 在提示中明确列出约束清单
- 生成后要求 AI 自检
- 人工目视确认

**III类（编排器模式）**：

- 用外部编排器管理状态
- 分阶段处理
- 每阶段有检查点
- 多路并行 + 汇聚

**IV类（人机协作）**：

- AI 做备选方案列举 + 各方案量化对比
- 人类做决策 + 矛盾权衡
- AI 按人类选择的路径执行
- 人类做终审

### 4.5 上下文设计优化

有限上下文内的信息布局对抗注意力衰减。

#### 4.5.1 信息位置策略

基于 "Lost in the Middle" 研究，**开头和结尾的约束比中间的被更好遵循**：

```text
上下文布局优化：

❌ 低效布局:
  [约束清单] [文件A的全部内容] [文件B的全部内容] [文件C的全部内容] [指令]

✅ 高效布局:
  [指令] [约束清单（精简）] [每个文件的关键接口摘要] [文件A完整内容]
  ^ 开头       v 每个文件前加摘要
  注意力最好    ^
              "锚点"防止注意力在长内容中漂移

  如果上下文 > 32K，约束清单最好在开头+结尾各出现一次
```

#### 4.5.2 抽象层替代完整内容

不把完整文件放入上下文，而是放**抽象层**：

```text
❌ 不好的做法（上下文爆炸）:
  上下文包含: 5个完整文件 = ~20K tokens

✅ 好的做法（抽象层替换）:
  上下文包含:
    - 约束清单（显式）          ~0.5K
    - 当前要修改的文件的完整内容   ~4K
    - 其他文件的接口摘要         ~1K
    - 已修改文件的变更摘要       ~0.5K
  Total:                        ~6K（节省 70% 上下文）
```

#### 4.5.3 约束锚定

关键约束在上下文中**重复多次**，提高注意力权重：

```text
关键约束锚定示例:

[系统提示] 核心约束 C1: 所有接口必须向后兼容 Gen4
[任务描述] 请修改以下文件，注意 C1（向后兼容）
[进度提示] 正在修改文件 X，请记住 C1（向后兼容）的要求
[文件内容] ...（修改中）
[多文件检查] 最后检查：C1（向后兼容）是否在所有文件中一致
```

#### 4.5.4 摘要替代增量

对"已有 + 修改"的场景，与其给 AI 全部内容，不如给"原始内容摘要 + 已做修改的变更摘要"：

```text
非增量方式（❌）:
  每轮都重新加载全部文件和约束 -> 注意力分散

增量方式（✅）:
  第1轮: 原始文件A + 约束 -> AI 修改
  第2轮: 文件B原始内容 + 约束 + [文件A的变更摘要: 第x行改了什么]
  第3轮: 文件C原始内容 + 约束 + [文件A+B的变更摘要]
```

变更摘要是人工管理的中介状态，性质确定、内容精简。

### 4.6 人机分工：AI vs 人类各管一段

#### 4.6.1 最优分工原则

| 谁做 | 适合什么 | 不适合什么 |
|:====|:=========|:==========|
| **AI 独立做** | 单文件生成、格式转换、局部修改、海量信息筛选 | 跨文件一致性保证、矛盾权衡决策、创造性架构设计、价值判断 |
| **AI 辅助人类做** | 备选方案生成、数据提取整理、第一轮审稿、量化对比 | 终审决策、优先级裁断 |
| **人类控制** | 任务定义、约束筛选、关键决策、质量门禁 | 细节执行（应放给 AI） |

#### 4.6.2 实用分工清单

```text
在多文件/多约束场景下：

人类负责:
□ 定义"什么是对的"（价值和目标）
□ 识别并标注约束优先级（哪些是不可妥协的）
□ 在矛盾约束间做最终权衡决策
□ 审核 AI 输出中与架构/战略相关的部分
□ 验证最终结果是否满足业务目标

AI 负责:
□ 列举备选方案及量化对比
□ 按人类选定的路径执行细节修改
□ 格式、语法、拼写等局部质量保障
□ 信息检索和整理
□ 生成初稿供人类编辑
```

## 5. 服务器研发场景专项分析

### 5.1 服务器研发中常见的多约束失效场景

| 场景 | 关联复杂度 | AI 典型翻车 | 严重度 |
|:-----|:---------:|:-----------|:-----:|
| **BMC FRU 数据一致性** | 固件参数 × 数据库 × OOB 接口 × 管理平台 需要 4 方一致 | 只改了固件，忘了同步数据库 schema | ★★★★★ |
| **BIOS 选项矩阵** | Platform A/B/C 各有不同默认值，option ROM 互斥约束 | 把 platform A 的默认值沿用到了 platform B | ★★★★ |
| **PCIe 拓扑设计** | 带宽约束 × 信号完整性 × 散热 × 物理空间 × 成本 | 只算带宽满足，没检查 PCIe lane 分配是否与 Switch 可用端口匹配 | ★★★★ |
| **散热方案约束** | TDP × 风量 × 压降 × 噪音 × 成本 × 尺寸 | 给出风量满足的方案，但没考虑噪音约束 | ★★★ |
| **电源树设计** | 各 rail 电流 × 电压精度 × 效率 × 纹波 × 时序 × 热 | 算了对的功率但忽略了上电时序冲突 | ★★★★★ |
| **多平台代码复用** | 共享代码库 × 差异配置 × 版本兼容 × 编译选项 | 修改共享代码时没考虑对特殊配置的影响 | ★★★★★ |
| **验证用例覆盖** | 跨功能模块的交互场景 × 边界条件 × 组合爆炸 | 生成了单功能的完备用例，但跨功能组合场景大面积遗漏 | ★★★★ |

### 5.2 专项策略

#### 5.2.1 约束预检清单

对服务器研发场景，建立标准化的约束检查清单模板：

```text
Template: 硬件设计约束审计清单

□ 电气约束
  - 信号完整性（眼图余量 ≥ 20%）
  - 时序余量（setup/hold 余量 ≥ 10%）
  - 电源完整性（纹波 ≤ 1%）
  - 跨域信号（level shifter 是否存在？）

□ 热约束
  - 最大结温（Tj_max = 105°C）
  - 散热器高度限制（≤ 35mm）
  - 进风口温度范围（5-45°C）
  - 噪音限制（≤ 78dBA 满载）

□ 机械约束
  - PCB 层数
  - 板卡尺寸
  - 连接器高度
  - 可维护性（热插拔？）

□ 成本约束
  - BOM 目标
  - NRE 预算
  - 备选料限制

□ 兼容性约束
  - 向前兼容（Gen4/Gen5）
  - 向后兼容
  - 多 SKU 共享率
```

#### 5.2.2 领域知识库辅助

服务器研发的领域知识（信号完整性、散热、电源等）可以作为 AI 的"外部脑"：

```text
策略: 将领域知识从隐式（AI 训练数据中的概率分布）
      转化为显式（外部知识库查询）

实现:
  1. 在 AI 生成方案时，不是仅靠模型内部知识
  2. 而是查询 knowledge/ 中对应的领域文档
  3. 将领域约束作为上下文注入
  4. 生成后进行领域规则验证
```

#### 5.2.3 多阶段验证

```text
硬件设计的多阶段验证：

阶段1 - 电气规则检查（自动化工具）
  约束: 走线宽度/间距/阻抗控制
  工具: PDK 规则检查 -> 全自动

阶段2 - 架构合理性验证（AI）
  约束: 带宽是否充足、接口是否兼容
  方法: 将设计文件输入 AI，要求对照约束清单检查

阶段3 - 跨领域一致性验证（AI + 人类）
  约束: 电气方案是否与散热方案冲突
        散热方案是否与机械方案冲突
  方法: AI 逐对交叉检查，人类裁决冲突
```

## 6. 工程落地指南

### 6.1 任务难度预判表

在开始一个任务前，快速评估 AI 能完成到什么程度：

| 评估维度 | 简单（I类） | 中等（II类） | 困难（III类） | 极难（IV类） |
|:---------|:----------:|:-----------:|:------------:|:-----------:|
| **关联文件数** | 1 | 2-3 | 4-8 | 8+ |
| **显式约束数** | ≤3 | 4-7 | 8-15 | 15+ |
| **约束冲突** | 无 | 少量 | 中等 | 大量 |
| **领域专业知识** | 通用 | 通用+ | 专业 | 深度专业 |
| **判断标准** | 客观（Yes/No） | 半客观 | 半主观 | 主观（价值判断） |
| **回滚代价** | 低 | 中 | 高 | 极高 |

**评估方法**: 逐项打分后取最高等级，按对应等级选择策略。

### 6.2 不同难度对应的策略

| 难度等级 | 策略 | 期望正确率 | 人工介入程度 |
|:--------:|:------|:----------:|:-----------:|
| **I类** | 直接生成，偶尔检查 | 90%+ | 低（10% 抽查） |
| **II类** | 生成 + 自检 + 人工目视 | 80-90% | 中（50% 检查关键约束） |
| **III类** | 编排器 + 验证循环 + 分段交付 | 70-80% | 高（100% 审查计划 + 关注争议点） |
| **IV类** | AI 出方案+量化对比 → 人类决策 → AI 执行 → 人类审查 | 60-70% | 极高（人类主导） |

```text
   - 优缺点
   - 风险
3. 同时指出：如果你被要求"同时满足所有约束"，你会给出什么方案
   以及这个方案在什么条件下失效
```

### 6.4 避坑清单

| 常见错误 | 正确做法 |
|:---------|:---------|
| 一次性给 AI 太多文件 | 只给当前需要的文件 + 其他文件的摘要 |
| 期望 AI 自己记住全局约束 | 每轮都显式列出约束清单（可精简但不断） |
| 要求 AI "综合考虑" | 要求 AI 依次讨论每个因素，最后做交叉 |
| 只做一次生成就交付 | III/IV 类任务至少做"生成→自检→修复"循环 |
| 不分解任务 | 把跨 20 个文件的任务拆成 4 组 × 5 个文件 |
| 依赖 AI 做价值判断 | 把"好/坏"判断留给自己，让 AI 只做"量化和对比" |
| 混淆了"声称满足"和"实际满足" | 要求具体数值 + 计算过程 + 边界条件注释 |

## 7. AI 架构演进方向

当前 LLM 的架构限制是根本性的。以下是正在演进或有潜力的改进方向。

### 7.1 长上下文改进

| 技术 | 原理 | 对关联约束的帮助 | 成熟度 |
|:-----|:-----|:--------------:|:------:|
| **Ring Attention** | 分布式注意力计算，支持无限上下文 | 可以塞更多文件，但注意力衰减仍存在 | ✅ 已落地 |
| **Infini-Attention** | 压缩式长期记忆，而非全量保留 | 缓解注意力稀释 | ⚠️ 研究中 |
| **选择性注意力** | 只关注关键位置（如约束声明处） | 如果知道"关注什么"，有效 | ⚠️ 概念 |
| **分层注意力** | 先粗粒度定位再细粒度关注 | 接近人类"先扫再读"策略 | 🔬 前沿 |

**关键洞察**: 长上下文改进解决的是"装得下"，不是"管得了"。约束管理的瓶颈在推理结构而非信息容量。

### 7.2 推理结构改进

| 技术 | 原理 | 对关联约束的帮助 | 成熟度 |
|:-----|:-----|:--------------:|:------:|
| **Chain-of-Thought (CoT)** | 让 AI 显式展示推理过程 | 提高跟踪约束的意识 | ✅ 落地 |
| **Self-Consistency** | 多次生成 + 投票 | 提高约束满足的概率 | ✅ 落地 |
| **Graph-of-Thought** | 非线性的推理路径 | 更适合约束网络 | ⚠️ 概念 |
| **System 2 推理（o1/o3 模式）** | 内部"思考"阶段后再回答 | 显著提高多约束任务表现 | ⚠️ 部分落地 |
| **反思循环** | 生成后自我检查修正 | 最直接的改善方式 | ✅ 落地 |

**o1/o3 系列模型的区别**: 这类模型增加了内部思考 Token（reasoning tokens），在生成回答前先内在地"推理"一段时间，这对多约束任务有显著改善：

```text
传统 LLM:
  输入 -> 立即生成（约束跟踪概率化）

o1/o3 系列:
  输入 -> 内部推理（约束提取+规划）-> 生成
           ^————
           "思考"阶段，约束更可能被显式化
```

但即使 o1/o3，这种"思考"也是**隐式的**——它不产生中间检查点，没有可审计的约束管理过程。所以对于高可靠性要求的场景，**外部约束管理仍是必需的**。

### 7.3 工具增强架构

| 模式 | 原理 | 效果 | 可行性 |
|:-----|:-----|:----|:------:|
| **Agent + Tools** | AI 通过工具读取文件、搜索记忆、触发验证 | 显著扩展 AI 管理能力 | ✅ 当前可用 |
| **编排器 + 子 Agent** | 编排器分配任务，子 Agent 各管一块 | 最适合多文件场景 | ✅ 当前可用 |
| **图形数据库** | 将约束关系存在图数据库中，AI 查询而非记忆 | 避免 AI 的约束遗忘 | ⚠️ 需搭建 |
| **Vector + Document** | 用向量检索定位相关约束 | 降低上下文负担 | ✅ 当前可用 |

## 8. 总结：认知—工具—流程—期望

### 8.1 核心认知

1. **不是 AI "不够聪明"** — 而是 AI 的信息处理架构与人类根本不同。它在处理关联约束时处于信息劣势，这不是训练能解决的问题。

2. **AI 强于"检索和格式化"，弱于"跟踪和验证"** — 理解这个基本分工就理解了 90% 的使用策略。

3. **关联复杂度是 AI 能力退化的主要维度** — 文件数量和约束数量增加到一定程度后，AI 的正确率呈指数下降（不是线性）。

4. **改善的核心是"外部补偿"** — 用工具和流程补偿 AI 的先天缺陷，而非期待 AI 自己进化。

### 8.2 决策框架

```text
面对一个任务，按以下顺序决策：

Step 1: 任务属于哪一类？
  单个文件 + 少量约束 -> I类：直接做
  少量文件 + 中等约束 -> II类：生成+验证
  多个文件 + 多约束 -> III类：编排器模式
  多文件 + 矛盾约束 -> IV类：人机协作

Step 2: 选择策略策略
  I类: 直接提示 -> 输出 -> 检查
  II类: 提示+约束清单 -> 输出 -> 自检 -> 修复
  III类: 编排器 -> 分段 -> 验证循环
  IV类: AI出备选 -> 人类决策 -> AI执行 -> 人类终审

Step 3: 始终执行
  - 建立约束清单（显式化）
  - 约束锚定（关键约束重复出现）
  - 验证循环（至少自检一轮）
  - 接口/边界处加自动化验证
```

### 8.3 期望管理

| 任务类型 | 应期望什么 | 不应期望什么 |
|:---------|:----------|:-----------|
| I类 | 一次性正确率 90%+ | 100%——仍需要抽查 |
| II类 | 经自检后 85%+ | 零缺陷交付 |
| III类 | 经编排器+验证后 75-85% | 一次生成就完美 |
| IV类 | 好的备选方案集+量化对比 | AI 替你做出正确决策 |

### 8.4 最终建议

> **不要在 AI 的短板上堆更多 AI，而是用工程化手段补偿。**
>
> — 约束遗忘是架构缺陷，不是次数问题。
> — 外部编排 + 显式约束 + 验证循环，比任何提示技巧都可靠。
> — 人机分工的核心不是"谁更强"，而是"谁的架构更适合这个子问题"。

## 附录：术语对照表

| 术语 | 定义 |
|:-----|:-----|
| **自回归生成** | LLM 逐个 token 生成输出，当前 token 依赖之前所有 token |
| **注意力机制** | Transformer 中决定每个 token 需要关注序列中其他位置权重的机制 |
| **Lost in the Middle** | LLM 对长上下文中间部分的信息利用效率显著低于开头/结尾的现象 |
| **上下文窗口** | LLM 单次推理能处理的最大 token 数量 |
| **约束显式化** | 将隐式/隐含的规则和限制条件转化为明确的、可检查的清单 |
| **编排器模式** | 用外部系统管理任务的阶段、状态和跨文件一致性，AI 只负责单文件生成 |
| **验证循环** | 生成 → 检查 → 修复 → 再检查 的迭代过程 |
| **约束锚定** | 在上下文中重复关键约束以提高注意力权重 |
| **变更摘要** | 对已修改文件的精简记录（做了什么修改、影响什么），供后续步骤使用 |
| **Token** | LLM 处理文本的最小单元，中文约 1 token = 1~2 个汉字 |
| **Attention Sink** | 在长上下文生成末尾 token 时，注意力异常集中到序列开头几个 token 的现象 |
| **Reasoning Token** | o1/o3 系列模型内部生成的不可见推理步骤 |
| **抽象层** | 用接口摘要/元数据替代完整文件内容，减少上下文占用 |
| **Domain-Specific Constraint** | 领域特有的、需要通过专门知识才能识别的约束条件 |
