## 1. AI 编程理念与价值

### 1.1 核心理念

> **范式转变**：从人工编码为主 → 人机协作共创

AI 编程不是"让 AI 替代程序员"，而是**让程序员变得更强大**。核心在于：

- **利用大模型的创造能力**：AI 擅长生成代码框架、编写模板、补全逻辑，让你从重复劳动中解放
- **使用提示词进行规范化**：通过良好的提示词设计，增强 AI 输出的确定性和可控性
- **人机协同**：你做决策和评审，AI 做执行和补全 — 1+1 > 2

### 1.2 核心价值

| 价值维度 | 说明 |
|:---------|:-----|
| 🚀 **代码生成效率提升** | 编写重复代码、样板代码的速度提升 3-10 倍 |
| 📦 **缩短研发周期** | 从需求到原型的时间大幅缩短，快速验证想法 |
| 🔄 **降低重复编码工作** | CRUD、配置、测试用例等重复工作交给 AI |
| 🎯 **提升代码质量与标准化水平** | AI 辅助代码审查、规范检查，减少低级错误 |

### 1.3 应用场景

AI 编程远不止写代码这么简单：

| 场景 | 说明 | 示例 |
|:-----|:------|:-----|
| 💻 **编码开发** | 大工程开发、小工具编写 | 后端 API、前端页面、CLI 工具、数据处理脚本 |
| 🧰 **小工具开发** | 快速开发团队内部小工具，供小范围使用 | 日报生成器、数据转换工具、监控告警小工具 |
| 📝 **文档编写** | API 文档、技术方案、README、注释 | 自动生成函数注释、接口文档、变更日志 |
| 🔧 **流程搭建** | CI/CD 脚本、自动化工作流 | 构建脚本、部署流水线、测试自动化 |
| 🤖 **数字分身** | 构建特定领域的 AI 助手 | 知识库问答机器人、代码审查助手 |
| 🌈 **更多可能** | 等待你来发现和创造 | — |

> 💡 **核心思路**：凡是"有规律、可重复、确定性高"的工作，都可以考虑让 AI 来做。

### 1.4 实践路径建议

```text
第 1 步 --- 第 2 步 ------------ 第 3 步 --------
   v            v                    v
走出现状   发现可自动化的工作点    参与圈子
接触AI编码  提炼可编程场景         共同讨论进步
           构建知识库+提示词
           交给AI工具执行
```

**具体建议**：

1. **走出当前现状** — 不要观望，先动手试试。从最小的例子开始（比如让 AI 写一个贪吃蛇游戏）
2. **发现可自动化的工作点** — 审视你日常工作中的重复性任务，提炼出可以编程化的场景，构建自己的知识库和提示词模板
3. **参与圈子，共同进步** — 和同事、同行交流使用经验，互相学习提示词技巧和最佳实践

> 🎯 **一句话总结**：**让 AI 做 AI 擅长的事，你做人擅长的事。**

### 2.1 首选：TRAE CN

> 字节跳动出品，基于 VS Code 的增强 AI IDE，内置深度 AI 能力集成。

#### 2.1.1 快速上手：牛刀小试

**操作步骤**：

```text
Step 1 ---> Step 2 ------> Step 3 -----------> Step 4 -------> Step 5
   v          v              v                  v              v
打开TRAE   打开右侧      输入提示词          等待AI Builder   运行效果
新建文件夹 TRAE对话框  "用web技术生成       干活+点确认      试玩一把
                       一个贪吃蛇游戏"
```

**详细步骤**：

1. **创建工程**：文件菜单 → 选择空白文件夹作为工程路径
2. **打开 AI 对话框**：若右侧没有 TRAE 对话框，点击右上角图标打开（默认应该会有）
3. **输入提示词**：

   ```text
   使用 web 技术生成一个贪吃蛇游戏
   ```

4. **AI Builder 开始干活** — 你呢？干其他活吧 😄
   - 不过也得关注窗口，需要你干预——**点击确认**接受代码变更
5. **运行效果**：
   - 如果停止后找不到运行方法，让 AI 来帮你：在对话框中输入 `运行程序`
   - 牛人的话，自行在控制台中输入命令启动
   - **试试效果，来一把吧！** 🐍

#### 2.1.2 不要飘 🫣

成果是显著的，但有很多坑在前面等着你：

| 常见问题 | 说明 |
|:---------|:------|
| ❌ **不是我预期的功能** | AI 理解有偏差，需要你调整提示词引导 |
| ➕ **怎么在已有工程上添加新功能** | 需要把上下文告诉 AI，而不是孤立提问 |
| 💬 **怎么使用大模型来交互** | 学习提示词工程，让 AI 理解你的真实需求 |
| 📚 **怎么使用本地知识库** | 把你的技术规范和代码库喂给 AI，增强准确性 |
| 🔗 **怎么与外部系统交互** | 让 AI 调用 API、数据库，扩展其能力边界 |
| ... | 只有你想不到的坑，到时一同来克服，**做成组织的经验沉淀下来** |

#### 2.1.3 隐私模式 — 信息安全保障

建议开启隐私模式，增强信息安全：

> **位置**：TRAE 设置 → 隐私模式
> **作用**：代码数据不离开本地，使用内部部署的大模型

#### 2.1.4 Index 功能 — 让 AI 理解你的工程

启用 Index 功能，让 AI 更方便检索整个工程：

- 开启后，AI 能理解项目结构、代码依赖关系
- 在提问时能自动关联相关文件作为上下文

#### 2.1.5 工程级别设置 — Project Rules

使用 `project_rules.md` 等工程配置文件，让 AI 每次对话时自动引用约束。

**示例 project_rules.md**：

```markdown
### 1. 目录结构
- src/: 主目录，含 document_processing、dify_api、keyword_extraction、config、tools 模块
- test/: 测试套件
- docs/: 项目文档
- requirements/: 依赖目录
- .env: 环境变量
- 不在根目录下创建测试文件，需在 test/obsolete 下创建，输出放在 output 下
- 需要符合 docs/constraint.md 中的规范

### 2. 配置规范
- 配置统一在 src/config/settings.py
- Python 3.12+
- 日志 JSON 格式
- Windows 系统下搭建，尽量兼容 Linux 下使用

### 3. 日志规范
- DEBUG：开发调试，生产禁用
- INFO：系统状态，生产保留
- WARN：潜在问题，生产保留
- ERROR：功能失败，生产保留
- FATAL：系统崩溃，生产紧急响应

### 4. 异常处理
- 模块独立捕获处理
- 记录详细堆栈和上下文
- 实现优雅降级

### 5. 测试规范
- 核心业务≥80%，关键流程≥95% 覆盖率
- 测试类型：正常、边界值、异常输入、性能、功能
- 支持多方式运行

### 6. 文档规范
- API 文档：OpenAPI/Swagger 生成
- 代码文档：公共模块 docstring，Google 风格
- README.md：项目简介、快速开始、配置、使用示例

### 7. 版本控制与 CI/CD
- 依赖管理：Poetry 或 pip-tools
- 代码质量：black、ruff、mypy

### 8. 核心业务规则
- 文档处理：工厂+策略模式，长页面智能分割
- OCR 识别：双引擎，90% 一致性检查，5 次重试，大模型 fallback
- Markdown 转换：统一图片格式，OCR 结果插入图片后
- 关键字提取：支持规则和 LLM 提取，批量处理

### 9. 扩展指南
- 新增文档格式：实现 BaseParser 抽象类
- 自定义 OCR 引擎：实现 OCRProcessor 接口
- 定制关键字提取：继承 BaseExtractor 类

### 10. 最佳实践
- 模块化设计，低耦合高内聚
- 统一接口，便于扩展
- 集中配置，便于维护
- 完善日志和错误处理
```

> 这样每次对话时，TRAE 会自动引用上述约束，让 AI 输出更贴合你的工程规范。

#### 2.1.6 Linux 远程开发

配置后，可以在本地 TRAE 中像操作本地文件一样操作远程 Linux 服务器上的代码。

### 2.2 次选：Continue

> 开源 VS Code 插件，使用本地部署大模型，信息安全有保障。

#### 2.2.1 为什么有 TRAE 还要用 Continue？

不同工具各有优势，就像不同人有各自擅长的领域：

| Continue 的优势 | 说明 |
|:---------------|:------|
| 🔌 **VS Code 生态** | 与 VS Code 原生集成，大量现有插件可用 |
| 🆓 **开源方案** | 后续若要扩展和定制，是个很好的切入点 |
| 🔒 **信息安全** | 默认使用内部部署的 480B Coder 大模型，数据不出内网 |
| 👥 **使用习惯** | 团队用得比较久，积累了较多经验和配置 |
| 🔧 **可扩展性** | 开源方案，可根据需要自定义功能 |

#### 2.2.2 代码补齐

> Tab 键一键接受，享受 AI 智能补全。

**常见用法**：

- 输入部分代码 → Continue 自动生成后续 → **按 Tab 接受**
- 注意 VS Code 的设置中需要开启补齐功能
- 装注释自动生成插件：选中代码（函数）后，弹出窗中选择自动生成注释

#### 2.2.3 代码片段的解读

**语法解析功能**：

1. 选择代码 → 右键菜单 → **添加到 Continue Chat**
2. 在提示框中输入：

```text
逐行解释下本函数
```

AI 会逐行分析代码逻辑、参数含义、返回值。

**文件级别的功能阅读与优化**：

三种方式让 AI 理解整个文件：

| 方式 | 操作 | 适用场景 |
|:----|:-----|:---------|
| ① 全选+Chat | 全选整个文件 → 添加到 Chat | 一次性分析 |
| ② @file 指令 | 在 Chat 中使用 `@file` 指定文件名 | 文件内容较长时 |
| ③ 拖拽文件 | 拖拽文件到 Chat 窗口 | 快速操作 |

**常用提示词示例**：

```text
- 解读 xx 函数的功能
- 对 xx 函数进行重构
- 当前 xx 函数的输入与输出怎么样
- 对当前文件进行代码走读
```

## 3. 场景演练

> 理论千遍不如实战一回。本节通过真实案例，展示从零到一的 AI 编程全流程。

### 3.1 构建二供分析 POC 应用

> **场景**：某团队需要构建一个"二供（第二供应商）物料评估分析"的 POC 应用，评估不同供应商物料的性能、成本、风险等维度。

#### 3.1.1 业务分析先行

在写一行代码之前，**先把业务搞懂**：

| 步骤 | 做什么 | 产出 |
|:-----|:-------|:-----|
| ① 调研业务需求 | 了解背景、工作流程、目标 | 需求理解文档 |
| ② 明确评估对象 | 二供物料有哪些？评估维度是什么？ | 评估指标体系 |
| ③ 确定使用角色 | 谁用这个系统？（评估员/审批人/管理员） | 角色定义 |
| ④ 设计评估流程 | 从提报到出报告的完整流程 | 流程图 |

> 💡 **核心原则**：**一切以业务需求出发来评估。** 若只是做个小工具，who cares？若是要做一个长期运行的系统，需要部署运维甚至对外发布——那就得认真对待了。

#### 3.1.2 生成提示词

基于业务分析，编写提示词让 AI 生成应用。以下是**完整可用的提示词示例**：

````markdown
背景：
实现一套基于 web 技术栈（flask+echarts）的评估流程，并生成评估报告。主要功能点包括如下：

1）评估输入：导入待评估的二供物料清单（CSV 格式）
2）评估角色：包含评估员、审核人、管理员三种角色
3）评估流程：评估员提交评估 → 审核人审核 → 管理员终审
4）评估维度：性能指标、成本分析、供应风险、质量认证 四个维度
5）在对材料评估完成后，根据 CSV 文件 component_checklist.csv 的内容进行合规性校验
6）最终给出评估结论，评估结论需要包括以下声明：
   - 综合评估等级（A/B/C/D）
   - 各维度评分雷达图
   - 风险提示项
   - 建议行动项
7）评审流程：支持多轮审核、退回修改、终审归档

要求：
1）数据库采用 SQLite；
2）先生成 PRD.md 和业务流程图，对数据库设计提供 ER 图；
3）Web 采用 Flask + ECharts 方式，页面呈现各个二供物料的评估流程；
4）对所有二供物料的评估进展，提供汇总呈现，按各人员统计汇总；
5）所有评估过程需要记录下来，材料需要按评估单号归档，方便查找；
6）构建对应的测试用例，对功能进行验证确认；
7）CSS、JavaScript 与 HTML 分离，代码结构清晰。
````

> ⚠️ **提示词越准确，AI 可发挥的空间越小，越会按你的要求来实现。** 事先做好准备工作，需求明确，提示词合理，是成功的关键。

#### 3.1.3 迭代修正（AI 编程常态）

第一次生成的结果很少一次到位，你需要持续迭代：

| 问题 | 如何让 AI 修正 |
|:-----|:---------------|
| ❌ **无法运行** | 复制终端错误信息 → 添加到 AI 对话框 → "控制台报错如上，请修复" |
| ❌ **缺少新功能** | 描述需要的功能 → "在现有工程上增加 XX 功能" |
| ❌ **大模型评估结果没填到评估维度中** | "评估结果没有写入评估维度表，请检查数据流并修复" |
| ❌ **需要演示数据** | "生成一批假数据用于页面演示" |
| ❌ **文档需要更新** | "刷新 PRD.md 和业务流程图.md，并对整个工程进行描述" |

**示例操作**：

```text
点击发起评估后，在控制台输出错误，需要解决。
-> 选择 Terminal 中的错误信息（弹出按钮 -> 添加到对话框）
-> AI 分析错误并给出修复方案
-> 确认后自动修改代码
```

#### 3.1.4 效果呈现

经过多轮迭代后，应用效果包括：

- ✅ 二供物料导入与评估表单
- ✅ 四维度打分 + 雷达图展示
- ✅ 评估进展汇总仪表盘
- ✅ 按人员统计工作量
- ✅ PDF/HTML 评估报告导出
- ✅ 审核流程（评估 → 审核 → 归档）

#### 3.1.5 无限 BUG 如何收敛？

> **无止境的 BUG，什么是尽头？总有新的想法，怎么收敛？**

**关键是：事先准备工作没做好。**

| 收敛策略 | 说明 |
|:---------|:------|
| 🎯 **需求写进提示词** | 所有功能点、约束条件一次性明确，不要逐步追加 |
| 🧩 **分阶段实施** | 先做 MVP（最小可行产品），验证核心流程后再扩展 |
| ✅ **验收标准前置** | 在提示词中明确"什么叫做完"——测试用例通过、功能点全部实现 |
| 📝 **功能冻结** | 核心功能完成后，新想法记入 TODO，下一个版本再做 |
| 🔄 **小步快跑** | 每次修改范围尽量小，改完验证，验证后再改下一步 |

## 4. 提示词写法

> 🎯 **提示词是关键要素。要懂业务，懂技术栈，才能成为 AI 时代下的超级个体。**

### 4.1 提示词指导原则

#### 4.1.1 核心原则

| 原则 | 说明 | 反面案例 | 正面案例 |
|:-----|:------|:---------|:---------|
| **具体明确** | 尽可能详细，用结构化约束 AI 的空间 | "帮我写个页面" | "用 Flask+ECharts 生成一个二供评估仪表盘，左侧导航、右侧内容区" |
| **角色定调** | 告诉 AI 扮演什么角色 | 无角色定义 | "你是一个资深全栈工程师" |
| **约束清晰** | 告诉 AI 不能做什么 | 无限制 | "禁止使用外部 CDN，所有 JS 库本地加载" |
| **参考样例** | 给 AI 参考对标 | 凭空想象 | "参考 xx 网站的布局风格" |
| **分步递进** | 复杂任务先框架后细节 | 一次说完所有需求 | 先让 AI 出 PRD，确认后再写代码 |

#### 4.1.2 提示词结构建议

一个好的提示词通常包含以下要素：

```text
【角色定位】 ：你是谁？AI 要扮演什么专家角色？
【背景场景】 ：什么背景下的任务？解决什么问题？
【业务操作步骤】：业务流程是怎么样的？
【技术需求点】 ：页面要怎样操作？数据怎么展示？
【技术要求点】 ：用什么技术栈？要不要可维护性功能？
【限制条件】 ：不要做什么？边界在哪里？
【参考样例】 ：有没有可以参照的示例？
```

> 💡 **思路**：可大致描述需求，之后让 AI 帮你展开细化。先让 AI "理解你的意图"，再让它"执行具体任务"。


##### 7. 参考样例

```text
【参考样例】
- 参考目标：______
- 借鉴点：______
- 差异点：______
```

#### 模板使用说明

| 使用要点 | 说明 |
|:---------|:------|
| 📝 **填空原则** | 所有 `______` 占位符需替换为具体内容，描述越详细，AI 生成越精准 |
| 🔧 **灵活调整** | 轻量小工具可简化"部署要求""权限管理"等模块；企业级系统需补充"容灾备份""多租户隔离" |
| 🔄 **迭代优化** | 首次生成后，可补充"修改方向"，让 AI 基于反馈迭代 |

### 4.3 工程/产品类提示词模板

> 适用于**大型工程、多模块产品**的开发场景。

#### 核心思路

```text
结构化提示词 + 多 Agent 协作

1. 先写 PRD，明确业务需求
2. 分析已有工程，设计架构
3. 添加测试用例
4. 分模块实现

核心原则：一步步来，不要一下子吃成胖子。
```

#### 推荐流程

```text
Phase 1 ----> Phase 2 ------> Phase 3 -----> Phase 4
   v             v              v             v
 写 PRD       架构设计        分模块实现      测试验证
 明确需求      ER图/接口      各 Agent 分工   集成测试
 功能清单     数据流设计      代码生成       回归验证
```

#### 多 Agent 协作要点

| 要点 | 说明 |
|:-----|:------|
| 🧩 **定义交互规则** | 各 Agent 之间的输入/输出格式要明确 |
| 🚫 **避免信息孤岛** | 共享上下文（技术选型、命名规范、数据库 Schema） |
| 🔄 **避免重复劳动** | 明确每个 Agent 的职责边界 |
| ✅ **设置检查点** | 每个 Phase 结束后验证成果，通过后再进入下一 Phase |

> 💡 多 Agent 方案适用于大型工程，小工具直接一个提示词搞定就行。

## 5. Skills — 技能沉淀

> Skills 是团队/项目**操作流程的沉淀**，是需要定制的核心资产。

### 5.1 什么是 Skills

Skills 可以理解为 AI 的"技能包"——把**特定领域的操作流程、知识经验、提示词模板**打包成可复用的模块。

类比：**Skills 就像一本字典，用时从里面查找。**

- 部分工具可以做到 Skills 自动匹配
- TRAE 目前看上去匹配能力较弱，需要手动指定
- 使用时在提示词中说明："调用 xx 技能来完成 xx 功能"

### 5.2 Skills 分类参考

```text
Skills/
+-- 编码类/         # 代码生成、代码审查、重构
+-- 文档类/         # PRD 生成、技术方案、API 文档
+-- 测试类/         # 测试用例生成、自动化测试
+-- 流程类/         # CI/CD 流程、部署脚本
+-- 领域类/         # 各业务领域的特定知识
+-- 工具类/         # Git 操作、数据库操作、命令行
```

### 5.3 如何使用 Skills

**方式一：提示词直接引用**

```text
使用"Flask 应用开发"技能来生成这个工具的代码框架。
```

**方式二：从 GitHub 检索**

如果本地没有合适的 Skill，可以从公开仓库检索：

```text
请从 GitHub 上检索并加载 xxx 提示词来完成这个功能。
```

### 5.4 为什么 Skills 重要

| 传统方式 | Skills 方式 |
|:---------|:-----------|
| 每次重新写提示词 | 一次沉淀，反复复用 |
| 个人经验无法共享 | 团队知识可传承 |
| 新人上手周期长 | Skills 开箱即用 |
| AI 输出不稳定 | 标准化的 Skill 保证质量 |

## 6. 使用 CLI 调用大模型

> 终端党福音：直接在命令行中调用大模型，适合自动化脚本、CI/CD 集成等场景。

### 6.1 基本用法

```bash
# 调用本地部署的大模型
curl -X POST http://<model-api-url>/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "模型名称",
    "messages": [
      {"role": "user", "content": "你好，请介绍下你自己"}
    ]
  }'
```

### 6.2 常见场景

| 场景 | CLI 命令示例 | 说明 |
|:-----|:-------------|:------|
| 🔍 代码审查 | `cat main.py \| curl ... -d '{"messages": [{"role": "user", "content": "审查这段代码"}]}'` | 将代码管道传给 AI |
| 📝 生成文档 | `echo "描述某个模块功能" \| your-ai-cli --task doc-gen` | 快速生成注释/文档 |
| 🔄 批量处理 | `for f in *.py; do ai-review $f; done` | 批量代码审查 |
| 🤖 CI/CD 集成 | Pipeline 中加入 AI 审查步骤 | 提交前自动审查 |

### 6.3 工具推荐

- **curl**：最通用的方式，适合任何环境
- **httpie**：更友好的 CLI HTTP 工具
- **自定义封装**：封装成团队内部 CLI 工具，简化调用

## 7. 经验与教训

> 从实战中沉淀的宝贵经验，避免重复踩坑。

### 7.1 关键经验

| # | 经验 | 说明 |
|:-:|:-----|:------|
| 1 | 🎯 **提示词越细，效果越好** | 结构化提示词比一句话提示词好 10 倍 |
| 2 | 🔄 **迭代是常态** | 不要期待一次生成完美结果，持续迭代优化 |
| 3 | ✅ **必须人工审查** | AI 生成的代码 100% 需要人工审查后再合并 |
| 4 | 📚 **知识库是核心竞争力** | 沉淀团队知识到知识库，AI 才能更懂你的业务 |
| 5 | 🧩 **小步快跑** | 每次改一点，验证一点，不要一次改太多 |
| 6 | 📏 **规范先行** | 工程规范、命名规范、代码规范提前定好 |
| 7 | 🔒 **信息安全第一** | 敏感代码/数据绝不传给外部模型 |
| 8 | 👥 **分享才能进步** | 好用的提示词、踩过的坑，多和团队交流 |

### 7.2 常见坑与避坑指南

| 坑 | 表现 | 避坑方法 |
|:---|:-----|:---------|
| 🕳️ **需求不明确** | AI 产出的东西不是你想要的 | 写提示词前先想清楚"我要什么" |
| 🕳️ **一次给太多需求** | AI 遗漏或混淆功能点 | 分阶段给，一次聚焦 3-5 个功能点 |
| 🕳️ **不设约束** | AI 自由发挥，风格不统一 | 在提示词中明确"不要干什么" |
| 🕳️ **上下文过载** | 文件太多时 AI 精度下降 | 每次只关注相关文件，用 @file 精确指定 |
| 🕳️ **不验证就合并** | 引入隐藏 bug | AI 代码必须走 review 流程 |
| 🕳️ **一个人闷头用** | 重复造轮子、踩同样的坑 | 多分享、多交流、多沉淀 |

### 7.3 行动清单

## 8. 实践路径与常见问题

### 8.1 成长路线

```text
初学者 ------> 日常用户 ------> 高效协作 ------> 组织赋能
   v              v               v               v
 牛刀小试      辅助编码       构建知识库      沉淀最佳实践
 贪吃蛇游戏    代码走读       提示词模板      内部分享
 文档生成      日常开发       流程自动化      团队推广
```

### 8.2 常见问题

| 问题 | 解答 |
|:-----|:------|
| ❓ **AI 编程会不会让我变懒？** | 不会。AI 处理重复劳动，你专注于更高价值的架构设计、逻辑判断和创新 |
| ❓ **AI 写的代码能用吗？** | 能用，但**必须人工审查**。AI 的产出需要你验证、调整、优化 |
| ❓ **提示词怎么写才有效？** | 从"需求+约束+示例"三段式开始，逐步迭代优化 |
| ❓ **多个模型怎么选？** | Coder 系列写代码、Instruct 系列做推理、Omni 系列处理多模态，各取所长 |
| ❓ **代码安全怎么办？** | 使用内部部署的大模型，开启隐私模式，数据不出内网 |

> 🤝 **一起交流，共同进步！**

- 内部技术分享：定期组织 AI 编程经验交流
- 提示词库共享：将好用的提示词沉淀为团队资产
- 最佳实践文档：记录踩坑经验和避坑指南
