## 1. 能力边界：这套系统能做什么、不能做什么

### 1.1 能力定位：粗加工车间

> 本系统 = **粗加工车间**：把素材变成"半成品卡片"，供主 Agent / 人工精加工。
> 它不替代主 Agent 的深度分析，而是为其**预消化素材、降低上下文负担**。

### 1.2 能做（低幻觉风险，7B 本地模型可靠）

| 能力 | 说明 | 对应场景 |
|:-----|:-----|:---------|
| **提炼** | 摘要/要点/结论抽取 | 专场 1/4/5/7 |
| **标注** | 结构/术语/信息点/逻辑链标注 | 专场 3 |
| **结构化** | 段落→标题层级/要点列表 | 专场 1/3 |
| **补齐** | frontmatter/标签/缺失字段 | 专场 2/6 |
| **分类** | 内容归类/标签建议 | 专场 2/6 |
| **索引** | 文件级摘要→检索索引 | 专场 5/7 |

### 1.3 不能做（明确边界，防止误用）

| 禁区 | 原因 | 正确路径 |
|:-----|:-----|:---------|
| 跨文档综合推理 | 单文件单请求，无全局视角 | 主 Agent 云端深度分析 |
| 深度因果分析 | 7B 推理链浅 | 主 Agent / 云端大模型 |
| 创造性写作 | 易套模板、平庸 | 人工/云端 |
| **事实核查** | 本地无外部知识，会一本正经编造 | 人工/主 Agent 联网验证 |
| 英文深度翻译润色 | 7B 中英质量一般 | 云端 |

**判定法则**：该任务"基于原文重排/压缩/标注"→ 本地可做；"需要外部知识/跨文档推理"→ 不可做。

## 3. 专场 1：文章内容提炼

**目标**：把采集的文章（md/ 含对话式内容、cnblogs/ 博客、webchat/ 分享）提炼为结构化文章卡片。

**输入特征**（实测）：md/ 混合"用户提问+豆包回答"格式，需先剥离对话框架提取正文。

**处理管线**：

```
文章 → L0 清理(剥对话框架/去广告) → L2 分片提炼 → 卡片合并 → 人工抽检
```

**产物：文章卡片**

```markdown
# 📇 文章卡片：<标题>
- 来源: <原始文件路径> | 日期: <yyyy-mm-dd> | 置信度: <L1/L2>
- 摘要: 3-5 行（基于原文压缩）
- 标签: 3-5 个
## 核心信息点
- 【规格】...
- 【论断】...
- 【数据】...
## 结构
- 章节1 → 要点...
```

**质量预期**：摘要准确率 ≥90%（压缩类任务 7B 可靠）；信息点分类准确率 ~80%（有误分类需人工校正）。

## 4. 专场 2：小材料补齐

**目标**：全目录 4,158 个 ≤5KB 小文件（残缺/无头/无日期）补齐为标准化卡片——**整文件处理，不分片，吞吐最高**。

**输入特征**：平均 ≤2.5K tokens，多为无 frontmatter、无标题、无标签的零散片段。

**处理管线**：

```
小文件 → L1 单请求(整文件) → frontmatter补全 + 1行摘要 + 标签 + 分类建议
```

**产物示例**（L1 输出）：
```markdown
---
title: <从内容推断的标题>
date: <文件日期或unknown>
source: <原始路径>
tags: [<3-5个>]
category: <建议分类>
---
> 摘要: 一句话
<原文保留>
```

**质量预期**：标题推断 ~85% 可用；标签 ~80% 可用；**全程不新增事实**（frontmatter 只写原文可见信息，日期无则写 unknown）。

## 5. 专场 3：技术文档逻辑增强

**目标**：server/ 英文技术规范（实测：BMC/Redfish/dbus 等）标注术语、逻辑链、提取规格点，转成中文可读的技术卡片。

**输入特征**：英文、逻辑严谨、含大量术语（Redfish/DBus/OpenBMC）、格式规整。

**处理管线**：

```
技术文档 → L2 分片 → 术语标注(只标注不展开) + 规格点提取 + 逻辑链标注 → 技术卡片 + 术语表
```

**产物：技术卡片 + 术语表**
- 技术卡片：每章 → 要点 + 规格点表（参数/值/条件/来源）
- 术语表：`术语 | 原文 | 建议译名 | 出现章节`（标注不展开，防幻觉）
- 逻辑链：`结论 ← 前提1 + 前提2` 标注

**质量预期**：规格点提取准确率 ~85%（英文技术文本结构化程度高，适合 7B）；术语标注 recall 高但个别误标。

## 6. 专场 4：对话记录提炼

**目标**：doubao/（826 文件，平均 69KB）与 千问/（404 文件，平均 315KB）超长对话提炼为纪要。

**输入特征**：图文混排（ASCII 图）、多轮问答、主题漂移、超长（315KB ≈ 160K tokens → 需 10-15 片）。

**处理管线**：

```
对话 → L0 清理(去ASCII图噪声) → L2 分片(每片一个主题段) → 每片纪要 → 脚本合并 → 主题纪要
```

**产物：对话纪要**

```markdown
# 📋 对话纪要：<主主题>
- 来源: <路径> | 轮数: <n> | 日期: <范围>
## 主题1 <片段范围>
- 问题: ... → 结论: ...
## 主题2
- ...
## 待办/结论清单
- [ ] <行动项>
```

**质量预期**：主题分段准确率 ~80%（对话主题漂移是难点）；结论抽取 ~75%；**待办识别**是增值项（指令头显式要求）。

## 7. 专场 5：工作资料索引化

**目标**：work/ 7,401 个 112KB 大文件（828M，全库最大）建立文件级索引，解决"知道有但找不到"。

**输入特征**：大文件（平均 112KB ≈ 56K tokens → 每文件 5-7 片）。

**处理管线**：

```
work/ → L0 全量规范化 → L2 精选(按目录优先级) 分片摘要 → 文件级索引表
```

**产物：工作资料索引**

```markdown
# 📇 工作资料索引
| 文件 | 摘要(1行) | 标签 | 关键结论 | 状态 |
|:-----|:----------|:-----|:---------|:-----|
```

**策略**：先 L0 全量（脚本 10 分钟）建立文件名/目录索引；L2 摘要按目录优先级分批跑（后台，不阻塞）。

## 8. 专场 6：入库前置预处理（流程价值最高）

**目标**：所有 import 目录 素材在进入 knowledge/ 前的标准化工序，衔接知识库三件套纪律。

**处理管线**：

```
import 目录 素材 → L0 规范化 → L1 摘要+标签+分类 → 人工审核(抽检/决策) → 知识库三件套入库
```

**关键点**：
- 增强产物 = **素材加工品**（半成品），不直接视为权威知识
- 人工审核门槛：格式合规 + 无新增事实错误 → 才允许入库
- 与知识库纪律衔接：入库走 `kb-log-append.py` + 索引脚本，增强系统不直接写 knowledge/

**价值**：把"主 Agent 逐文件阅读归档"（重上下文）前置为"本地批量粗加工"（轻上下文），主 Agent 只处理审核后的候选包。

## 9. 专场 7：日报类轻归档

**目标**：github-daily-rank/（875 文件）、weekly/（63 文件）低价值但需留存，轻量摘要归档。

**处理管线**：L1 单请求 → 每文件 1-2 行摘要 → 合并索引。**不做深度增强**（成本>价值）。

## 10. 单机调度策略

| 时段 | 任务 | 模型 | 说明 |
|:-----|:-----|:-----|:-----|
| 白天（交互间隙） | L2 精选（专场 1/3） | 7B | 人工可抽查 |
| 夜间（无人值守） | L1 批量（专场 2/7） | 3B | 吞吐优先 |
| 周末 | L0 全量刷新 + L2 大文件（专场 4/5） | 脚本+7B | 长任务窗口 |
| 任意时点 | 专场 6 候选包生成 | 脚本+3B | 按需触发 |

**并行策略**：20 核 CPU 可同时跑 2-3 个 llama.cpp 实例（3B×2 或 3B+7B），显存 8G 限制下 7B 只开 1 个。

## 11. 与主 Agent 的分工（粗加工车间模型）

```
素材堆(import 目录, 1.4G)
    │  ← 本地增强系统(粗加工车间): 提炼/标注/补齐/索引
    ▼
半成品卡片库(enhanced/, ~几十M)
    │  ← 主 Agent(精加工): 审核+深度分析+证据验证+知识库三件套
    ▼
knowledge/(正式知识)
```

**分工原则**：
1. **系统做"重活"**：逐文件读取、分片、标注——主 Agent 上下文宝贵
2. **主 Agent 做"判断"**：哪些卡片值得深度分析、入库决策、交叉验证
3. **人工做"终审"**：抽检 + 关键材料放行

## 12. 落地顺序建议

1. **先跑专场 6（入库预处理）**：价值最高、与现有知识库流程无缝衔接
2. **再跑专场 1+2（提炼+补齐）**：见效快（小文件 3 天），建立用户信任
3. **然后专场 3（技术文档）**：server/ 是业务核心，卡片可直接支撑知识库建设
4. **最后专场 4/5/7**：长对话/大文件/日报，后台持续跑
