> **关键词**: 本地LLM · 32K上下文 · import增强 · 分片 · 分级处理 · Ollama · 状态机 · 幻觉防护

> **创建**: 2026-08-13 | **分类**: 工具设计 | **定位**: 与大文档拆解/高密度信息方法论配套的本地落地工具
> **硬件**: 16G RAM / 20 核 CPU / RTX5060 8G / 512G NVMe
> **数据声明**: import 目录 体量为 2026-08-13 实测；tokens 估算采用 ~500 tok/KB（中英混合保守值）

## 1. 需求与约束

**目标**：一个专门处理 import 目录文件的工具，实现"逻辑增强 + 内容补充"，在本地硬件上可运行。

**硬约束**：

| 约束 | 值 | 影响 |
|:-----|:---|:-----|
| 上下文上限 | **32K tokens** | 单请求 payload 必须 ≤16K（留输出空间） |
| 显存 | RTX5060 8G | 本地模型 ≤7B Q4 量化（4.7G 权重 + KV cache） |
| 内存 | 16G | 可 CPU offload 部分层，但速度骤降 |
| 存储 | 512G NVMe | import 目录 1.4G 占用无压力；增强产物另算 |
| CPU | 20 核 | 可并行 prompt 处理 / 多进程调度 |

**明确不做**（用户明示）：不按当前 cowagent 重方式运作——不加载 AGENT/USER/RULE/MEMORY/SKILL 全量上下文。

## 2. 第一性原理：为什么"重方式"必然失败

当前主 Agent 的上下文 = AGENT.md + USER.md + RULE.md + MEMORY.md + 技能 SKILL.md + 文件全文，轻松超过 32K：

| 组件 | 估算大小 | 问题 |
|:-----|:---------|:-----|
| 全局身份/规则文件 | 5-8K tokens | 每个请求都吃预算 |
| 技能 SKILL.md | 3-10K × N | 多技能加载直接爆 |
| 文件全文（avg 38-112KB） | 19K-56K tokens | 单文件就超 32K |
| 会话记忆 | 不可控 | 越聊越大 |

**第一性原理结论**：32K 上下文下，**任何"全局上下文 + 全文件处理"的模式都不可行**。必须反转为：

> **极简指令 + 单文件分片 + 无状态批处理 + 断点续传**

- 指令极简化：1-2K tokens 的任务定义（替代全局 rule/skills）
- 文件分片：单请求只处理 12-16K tokens 的文本（替代全文）
- 无状态：每请求独立，不依赖会话记忆（替代 MEMORY）
- 文件级状态机：处理进度落盘，断点可续

## 3. import 目录 实测体量（决策基础）

> 2026-08-13 实测（`find` + `du` + `stat`）

| 目录 | 文件数 | 大小 | 平均大小 | 小文件(≤5KB) | 优先级 |
|:-----|-------:|-----:|--------:|------------:|:------:|
| work/ | 7,401 | 828M | 112KB | 773 | ⭐ 内容最重（工作资料） |
| server/ | 3,783 | 206M | 53KB | 1,970 | ⭐ A 类（服务器专业） |
| md/ | 3,906 | 155M | 38KB | 995 | ⭐ A 类（知识采集） |
| 千问/ | 404 | 131M | 315KB | 32 | ⭐ A 类（对话长文） |
| doubao/ | 826 | 58M | 69KB | 113 | B 类 |
| cnblogs/ | 1,953 | 34M | 17KB | 203 | B 类 |
| github-daily-rank/ | 875 | 11M | 12KB | 2 | C 类（日报可弃） |
| webchat/ | 619 | 7.3M | 11KB | 66 | C 类 |
| weekly/ | 63 | 1.2M | 18KB | 4 | B 类 |
| **合计** | **19,864** | **1.4G** | **~70KB** | **4,158** | — |

**关键数字**：
- 总 tokens ≈ 1.4G × 500 tok/KB ≈ **700M tokens**（中英混合保守估算）
- 全部文件平均 70KB → 平均每文件 ~35K tokens → **单文件平均就超 32K 上限**
- 4,158 个小文件（≤5KB ≈ ≤2.5K tokens）可直接整文件处理

**决策含义**：全量深度增强 = 600+ 天（见 §9），必须分级。**小文件优先、A 类目录优先**。

## 4. 总体架构：三级处理（L0/L1/L2）

```
import 目录 (19,864 文件, 1.4G)
    │
    ├─ L0 格式规范化（纯脚本, 无 LLM）→ 全量 100%
    │    ├─ 编码修复(GBK→UTF-8) / frontmatter 补全 / 标题清洗
    │    └─ 耗时: ~10 分钟（脚本批量）
    │
    ├─ L1 轻增强（3B 模型）→ 目标 5-10% 文件 (1-2K 个)
    │    ├─ 摘要 + 标签 + 结构标记
    │    └─ 耗时: 2-4 天（后台跑）
    │
    └─ L2 深增强（7B 模型）→ 目标 1% 文件 (~200 个)
         ├─ 逻辑增强（结构/逻辑链/信息点标注）
         └─ 内容补充（术语标注/缺失字段/摘要）
         耗时: 6-7 天（只处理最高价值）
```

**增强产物独立存放，不覆盖原文**：`import 目录enhanced/<原目录>/<文件>.md`

## 5. 上下文预算管理（32K 分配表）

```
┌────────────────────────────────────────────┐
│ 32K 总预算                                  │
├────────────────────────────────────────────┤
│ 指令头（极简任务定义+输出格式）:  1-2K       │ ← 唯一"系统提示"，替代全局 rule/skills
│ 文档上下文头（标题+大纲摘要）:  1-2K         │ ← 片间一致性（分片时用）
│ 文件分片主体:                   12-16K       │ ← 被增强内容
│ 输出预留（增强结果）:           8-12K        │
│ 缓冲（分隔符/意外）:            2-4K         │
└────────────────────────────────────────────┘
```

**指令头设计**（替代 rule/skills，1-2K 内）：
```
[任务] 对给定文本做 {逻辑增强|内容补充|摘要标签}
[约束] 只基于原文，禁止引入外部事实；补充内容用【补】标记
[输出] Markdown：{按增强类型定的格式}
```
> 不是不加载规则，而是把规则**编译成单条 1-2K 的指令头**，随请求携带。

## 6. 分片策略

| 项 | 规则 |
|:---|:-----|
| 触发阈值 | 文件 >10K tokens（≈20KB 中文）才分片 |
| 分片大小 | 目标 8-12K tokens/片（留指令+输出空间） |
| 分片锚点 | 章节标题（#/##）> 空行 > 段落边界；**禁止切断句子** |
| 片间一致性 | 每片带文档上下文头（标题+前片摘要 1-2K） |
| 重叠 | 相邻片重叠 200 tokens（防边界信息丢失） |
| 整合 | 各片增强结果由脚本拼接回文件（LLM 不做整合） |

**小文件（≤5KB）**：整文件处理，不分片（4,158 个文件直接受益）。

## 7. 增强操作定义（适配小模型）

> 大模型可做"开放式增强"，32K 小模型必须**结构化、可验证、低幻觉**。

### L2 逻辑增强（7B）

| 操作 | 输入 → 输出 | 幻觉风险 |
|:-----|:-----------|:--------:|
| 结构标记 | 段落 → 标题层级 + 要点列表 | 低（只重组原文） |
| 逻辑链标注 | 文本 → 因果/转折/结论标注 | 低（标注词不新增事实） |
| 信息点标注 | 文本 → 规格/论断/数据/概念标记（衔接高密度拆解类型学） | 中（分类可能误判） |

### L2 内容补充（7B）

| 操作 | 说明 | 幻觉防护 |
|:-----|:-----|:---------|
| 术语标注 | 只标注术语位置+建议解释，不展开 | 展开易幻觉 → 标注代替解释 |
| 缺失字段补全 | frontmatter 的 date/source/tags | 只补能从原文推断的 |
| 摘要生成 | 文件头 3-5 行摘要 | 低（基于原文压缩） |

### L1 轻增强（3B）

摘要（1-3 行）+ 标签（3-5 个）+ frontmatter 标准化 —— 输出极短，吞吐高。

**明确禁止**：LLM 补充外部事实、编造数据、改写原意。补充一律【补】标记。

## 8. 模型与推理引擎选型

| 档 | 模型 | 量化 | 权重 | 显存余量 | 预期速度 | 用途 |
|:---|:-----|:-----|:----:|:--------:|:--------:|:-----|
| L1 | Qwen2.5-3B-Instruct | Q4_K_M | ~2.0G | 充足 | 100-150 tok/s | 摘要/标签/规范 |
| L2 | Qwen2.5-7B-Instruct | Q4_K_M | ~4.7G | 8G 内可控 | 40-60 tok/s | 逻辑增强/内容补充 |

- **引擎**：Ollama（`ollama run qwen2.5:7b-instruct-q4_K_M`，最简）或 llama.cpp `llama-server`（并发批处理更强）
- **20 核 CPU**：llama.cpp 可将 prompt 处理 offload CPU 并行，GPU 专注生成
- **显存告警**：7B Q4 权重 4.7G + KV cache（2K 上下文 ~0.5G）+ 运行开销 ≈ 5.5-6G，8G 显存可行但需限制 KV cache（`--ctx-size 8192`）
- **兜底**：显存不足自动降级 3B（L2 任务降级为 L1 输出）

## 9. 吞吐与成本估算（分级量化）

**硬件能力**（RTX5060 8G 实测预期）：
- L2（7B Q4）：有效吞吐 ~40 tok/s（含 prompt 摊销）
- L1（3B Q4）：有效吞吐 ~120 tok/s
- 每日有效运行 8 小时：L2 ≈ 1.15M tokens/天；L1 ≈ 3.5M tokens/天

**成本核算**：

| 场景 | tokens | 工具 | 耗时 | 可行性 |
|:-----|-------:|:-----|:-----|:------:|
| ❌ 全量深增强 | 700M | L2 | ~600 天 | 不可行 |
| ❌ 全量轻增强 | 700M | L1 | ~200 天 | 不可行 |
| ✅ L0 全量规范化 | 0（脚本） | 脚本 | 10 分钟 | 全量做 |
| ✅ L1 轻增强（A 类目录 10%） | ~60M | L1 | ~17 天 | ⚠️ 仍偏久 → 再筛小文件 |
| ✅ L1 小文件优先（≤5KB 的 4,158 个） | ~10M | L1 | ~3 天 | ✅ 可行 |
| ✅ L2 深增强（A 类 1%，~200 文件） | ~7M | L2 | ~6-7 天 | ✅ 可行（后台跑） |

**结论**：
1. **L0 全量必做**（零成本高收益：编码/frontmatter/标题）
2. **L1 做小文件优先**（≤5KB 全做 + A 类目录的 5-10KB 文件）
3. **L2 只做 A 类精选**（~200 文件，按价值排序：server/ 技术文档 > md/ 知识采集 > work/ 工作资料）
4. 总工期 ≈ **L0 即时 + L1 三天 + L2 一周**，全部后台空闲跑

## 10. 工程实现（脚本骨架）

```
scripts/import-enhancer/
├── enhancer.py           # 主入口: 扫描/分级/调度/状态机
├── chunk.py              # 分片器（锚点切分+重叠+上下文头）
├── llm_client.py         # Ollama/llama.cpp API 客户端（自动降级 3B）
├── prompts/
│   ├── L1_summary.md     # 轻增强指令头
│   └── L2_enhance.md     # 深增强指令头
├── state.json            # 文件级状态机（断点续传）
└── output/               # 增强产物（镜像目录结构，不覆盖原文）
```

**状态机**：`pending → chunking → processing → done` / `failed`（失败重试 2 次后记入 failed.log 跳过）

**核心循环（伪代码）**：
```python
for f in scan(import_dir, priority_order):
    if state[f] == "done": continue          # 断点续传
    chunks = chunk(f) if size(f) > 20KB else [f]   # 分片或整文件
    for c in chunks:
        payload = instruction_head + doc_context_head + c   # ≤16K
        result = llm(payload, model=select_model(level))
        write_enhanced(f, result)            # 独立产物
    state[f] = "done"
```

## 11. 质量保障与幻觉防护

| 机制 | 说明 |
|:-----|:-----|
| **只基于原文** | 指令头强制：禁止引入外部事实 |
| 【补】标记 | LLM 补充内容一律标记，可脚本剥离 |
| **不覆盖原文** | 增强产物独立目录，原文只读 |
| 抽样复核 | 每批抽 5% 人工检查（质量门槛：无新增事实错误） |
| 增强前后 diff | 产物 vs 原文 diff 供快速审查 |
| 状态机落盘 | 失败可重跑，不重复处理 |
| L0 先行 | 先规范化再增强，减少模型误读 |

## 12. 风险与对策

| 风险 | 对策 |
|:-----|:-----|
| 小模型幻觉（补充编造） | 指令约束 + 【补】标记 + 抽检 + 只标注不展开 |
| 分片切断上下文 | 文档上下文头 + 200 tokens 重叠 |
| 全量超时 | 三级分级 + 小文件优先 + 状态机续传 |
| 显存不足（KV cache 超限） | --ctx-size 8192 限制 + 自动降级 3B |
| 增强产物污染素材 | 独立目录 + 素材批判性使用规则（import 目录 不直接入知识库） |
| 512G 存储 | 产物约 = 原文件 10-20% 增量，无压力 |

## 13. 落地路线

1. **Day 1**：装 Ollama + 拉 qwen2.5:3b 与 qwen2.5:7b（Q4）；跑 L0 脚本全量规范化
2. **Day 1-3**：L1 小文件优先（4,158 个 ≤5KB 文件，后台跑）
3. **Day 3 起**：L2 A 类精选（先 server/ 技术文档，再 md/、work/）
4. **每周**：抽检 5% + 人工审核增强产物 → 按知识库三件套纪律入库（增强产物属素材加工品，审核后入 knowledge/）
