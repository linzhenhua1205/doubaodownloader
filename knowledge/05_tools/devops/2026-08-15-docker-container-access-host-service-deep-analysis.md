## 核心命题

容器要访问宿主机上**未容器化的服务**（如宿主机直接运行的 MySQL/Redis/系统 API），本质是解决一个网络悖论：**容器的默认网关是 docker0（172.17.0.1），而"宿主机"在容器视角里不是 127.0.0.1**。三种主流方案（`host.docker.internal` / 网关 IP / `--network host`）解决的是同一个问题——**如何让容器内的"宿主机地址"稳定可解析**——但适用平台、开销、安全边界各不相同。

> 一句话：**容器内 127.0.0.1 是容器自己；要访问宿主机，必须显式指出"宿主机的地址是什么"——这恰恰是容器网络隔离的必然结果。**

---

## 一、为什么容器内不能直接访问宿主机服务

### 1.1 网络隔离的必然推论

容器拥有独立网络命名空间：
- 容器内 `127.0.0.1` = 容器自身的 loopback，**不是宿主机**
- 容器内默认网关 = docker0 bridge IP（如 172.17.0.1）
- 宿主机真实 IP（如 192.168.1.100）对容器是"外网地址"，**可达但需要经过路由+NAT**

### 1.2 三种典型误解

| 误解 | 实际结果 |
|:-----|:---------|
| "容器里 localhost 就是宿主机" | ❌ localhost 是容器自己 |
| "用宿主机 IP 一定能通" | 多数能通，但受防火墙/多网卡/安全组影响 |
| "宿主机服务监听 127.0.0.1 容器也能访问" | ❌ 服务只监听 loopback 时容器无法访问（需监听 0.0.0.0） |

> **隐含前提**：宿主机上的目标服务必须监听 `0.0.0.0` 或至少监听 docker0 网段（172.17.x.x），否则即使容器路由正确也会连接拒绝。

## 二、三种方案原理对比

### 方案1：host.docker.internal（推荐，跨平台）

```
# Linux 需额外参数（Docker 20.10+）：
docker run --add-host=host.docker.internal:host-gateway myapp

# 容器内使用：
curl http://host.docker.internal:3306
```

**原理**：
- `host-gateway` 是 Docker 的特殊值：自动解析为**宿主机在 docker0 上的 IP**（默认 172.17.0.1），写入容器的 /etc/hosts
- `--add-host` 本质是**静态 DNS 记录注入**，不依赖网络架构，稳定可靠
- macOS/Windows（Docker Desktop）内置支持，无需额外参数；Linux 需显式 `--add-host`

**优点**：语义清晰（"宿主机"）、不依赖具体 IP、跨环境一致
**缺点**：Linux 需要记忆额外参数；只解决"宿主机"这一个地址

### 方案2：网关 IP（docker0 地址，最通用）

```
# 获取 docker0 网关 IP
ip addr show docker0    # → inet 172.17.0.1/16

# 容器内使用：
curl http://172.17.0.1:3306
```

**原理**：容器访问外网时，数据包先到默认网关（docker0），**网关 IP 就是宿主机在容器网络中的身份**。宿主机上监听 0.0.0.0 的服务，通过网关 IP 必然可达。

**优点**：零配置、任何 Docker 版本通用、可脚本化获取
**缺点**：IP 是硬编码数字，跨机器不一致；`docker0` 网段可被管理员修改（`--bip` 参数）

### 方案3：--network host（共享网络栈，性能优先）

```
docker run --network host myapp
# 容器内直接使用：
curl http://127.0.0.1:3306   # 此时 127.0.0.1 = 宿主机！
```

**原理**：容器不创建独立网络命名空间，**直接共享宿主机网络栈**——容器内 127.0.0.1 就是宿主机 loopback，没有 NAT、没有 veth、没有 docker-proxy 开销。

**优点**：性能最优（零网络翻译开销）、无端口映射烦恼（容器端口即宿主机端口）、本地回环直通
**缺点**：**失去网络隔离**（安全边界消失）；端口冲突直接作用宿主机；无法再用 `-p` 做端口收敛

## 三、方案对比与选型决策

| 维度 | host.docker.internal | 网关 IP (docker0) | --network host |
|:-----|:---------------------|:------------------|:---------------|
| 原理 | DNS 注入 /etc/hosts | 默认网关地址 | 共享网络命名空间 |
| 配置成本 | 低（加一个参数） | 零 | 零 |
| 跨平台一致性 | ✅ 高 | ⚠️ 依赖网段 | ✅ 高 |
| 网络隔离 | ✅ 保留 | ✅ 保留 | ❌ **丧失** |
| 性能开销 | 无 | 无 | 无（最优） |
| 端口映射 | 需要 | 需要 | 不需要 |
| 适用场景 | 开发环境访问宿主机 DB/缓存 | 脚本/工具类容器 | 性能敏感、需要完整网络能力 |

**决策树**：
```
容器要访问宿主机服务？
├── 开发环境 / 想语义清晰 → host.docker.internal（Linux 加 --add-host）
├── 通用脚本 / 不想记参数 → 网关 IP（docker0 172.17.0.1）
├── 性能敏感 / 需要完整端口 → --network host（接受隔离丧失）
└── 生产环境 → 尽量避免！改用"宿主机服务容器化"或独立网络
```

> **生产环境最佳实践**：不要在容器里依赖宿主机服务——正确的做法是把宿主机服务（MySQL/Redis）也容器化并加入同一自定义网络，用服务名通信（见网络报告的自定义网络 DNS 机制）。宿主机直连只保留给**监控 Agent、运维工具**等必须场景。

## 四、应用场景与排障

### 4.1 典型场景

| 场景 | 推荐方案 | 原因 |
|:-----|:---------|:-----|
| 开发容器连宿主机 MySQL | host.docker.internal | 语义清晰，团队协作一致 |
| CI 脚本容器调用宿主机构建服务 | 网关 IP | 零配置，脚本通用 |
| 网络监控容器（抓包/探测） | --network host | 需要完整网络栈能力 |
| Prometheus 容器抓宿主机指标 | 网关 IP | exporter 常监听 0.0.0.0 |

### 4.2 排障清单（容器访问宿主机不通）

1. **宿主机服务监听地址**：`ss -tlnp | grep 3306` → 确认监听 0.0.0.0（而非 127.0.0.1）
2. **防火墙**：宿主机 iptables/firewalld 是否放行 docker0 网段入站
3. **容器内路由**：`docker exec <id> ip route` → 确认默认网关是 docker0 IP
4. **DNS 注入**：`docker exec <id> cat /etc/hosts` → 确认 host.docker.internal 存在
5. **SELinux/AppArmor**：部分发行版默认阻止容器访问宿主机（如 RHEL 系需调整策略）

## 五、结论

1. **根因是隔离**：容器访问宿主机难，不是 Docker 的 bug，而是网络隔离设计的必然结果——方案的本质都是"给容器一个指向宿主机的稳定地址"
2. **选型三原则**：开发用 `host.docker.internal`（语义清晰）、脚本用网关 IP（零配置）、性能敏感才用 `--network host`（代价是隔离）
3. **生产规避**：宿主机直连是妥协方案，容器化 + 自定义网络才是生产正解
4. **安全检查点**：使用 `--network host` 前必须评估——该容器是否需要被信任为宿主机网络的一部分
