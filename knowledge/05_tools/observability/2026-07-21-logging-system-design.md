## 1. 概述与核心原则

日志系统是软件系统的"黑匣子"——既是问题排查的第一工具，也是合规审计的核心证据，更是系统可观测性的基础数据源。一份好的日志设计方案需在**完整性**与**性能开销**之间取得平衡。

### 1.1 核心设计原则

| 原则 | 说明 | 反例 |
|:-----|:-----|:------|
| **1. 结构化** | 所有日志使用统一结构化格式，机器可解析 | 自由文本日志无法被ELK索引 |
| **2. 分级控制** | 不同环境/模块可独立控制日志级别 | 生产环境打开Debug日志导致磁盘打满 |
| **3. 上下文关联** | 请求/事务必须有全局Trace ID串联 | 微服务中各组件日志无法关联定位 |
| **4. 最小权限** | 日志中不记录敏感信息，或脱敏处理 | 日志泄露用户密码/信用卡号 |
| **5. 磁盘保护** | 日志必须有滚动/压缩/限速机制 | 单进程日志撑爆/var分区 |
| **6. 可观测性优先** | 日志设计初期就考虑聚合和分析需求 | 日志格式频繁变更导致解析器失效 |
| **7. 环境差异化** | Dev/Test/Staging/Prod使用不同日志策略 | 生产环境使用全量日志导致性能暴跌 |

### 1.2 日志系统的两个角色视角

| 角色 | 关注点 | 典型日志 |
|:-----|:-------|:---------|
| **运维(Infra Ops)** | 系统稳定性、可用性、资源水位 | Docker Engine日志、系统日志、硬件诊断 |
| **开发者(App Ops)** | 代码正确性、性能、异常定位 | 应用层Debug/Error日志、事务追踪日志 |

## 2. 日志分层架构

日志系统应采用**五层架构**，自下而上覆盖从硬件到业务的全链路：

```ascii
+-------------------------------------------------+
|  第5层: 业务日志层 (Application / Business)      | <- 业务逻辑、用户操作、交易记录
+-------------------------------------------------+
|  第4层: 中间件日志层 (Middleware / Framework)     | <- 消息队列、数据库、缓存、网关
+-------------------------------------------------+
|  第3层: 容器/服务日志层 (Container / Service)     | <- Docker/容器STDOUT/STDERR、服务发现
+-------------------------------------------------+
|  第2层: OS/系统日志层 (Kernel / OS)               | <- syslog、journald、systemd、内核日志
+-------------------------------------------------+
|  第1层: 硬件诊断日志层 (Hardware / BMC)           | <- OBFL、SEL、传感器、POST Code
+-------------------------------------------------+
```

### 2.1 分层职责

| 层级 | 日志来源 | 典型内容 | 聚合方式 | 保留周期 |
|:-----|:---------|:---------|:---------|:--------:|
| L5 业务 | App代码、Web服务器 | 用户操作、交易记录、业务异常 | 结构化文件→logstash | 30~90天 |
| L4 中间件 | MQ/DB/Cache/Gateway | 慢查询、连接池、消息积压 | 日志驱动→syslog | 7~30天 |
| L3 容器 | Docker/Podman/K8s | 容器STDOUT/STDERR、健康检查 | Docker日志驱动→aggregator | 7~14天 |
| L2 OS | Kernel/systemd/syslog | 内核OOM、磁盘IO、网络错误 | journald→远端转发 | 30~90天 |
| L1 硬件 | BMC/IPMI/Sensors | 温度、电压、风扇、SEL、POST | OBFL/Redfish→平台 | 永久(设备生命周期) |

### 2.2 组织所有权映射

日志的责任归属应与团队架构对齐：

| 日志类别 | 建议所属团队 | 备注 |
|:---------|:------------|:-----|
| 硬件诊断日志(L1) | 硬件/平台团队 | BMC固件、sel日志、传感器数据 |
| OS/系统日志(L2) | 基础设施运维 | syslog、kernel日志 |
| 容器/服务日志(L3) | 基础设施运维 + 开发团队 | 共享责任 |
| 中间件日志(L4) | 中间件/平台团队 | 数据库、MQ、网关 |
| 应用业务日志(L5) | 应用开发团队 | 业务代码日志 |

## 3. 日志级别体系

### 3.1 标准日志级别

采用业界广泛使用的分级体系，从严重到详细排列：

| 级别 | 数值 | 含义 | 生产环境 | 使用场景 |
|:-----|:----:|:-----|:--------:|:---------|
| **FATAL** | 50 | 致命错误，系统将退出或不可用 | ✅启用 | 系统无法继续运行，如关键组件崩溃 |
| **ERROR** | 40 | 错误，功能不可用但系统存活 | ✅启用 | 数据库连接失败、API调用返回500 |
| **WARN** | 30 | 警告，可能表示潜在问题 | ✅启用 | 磁盘使用率>80%、重试次数超阈值 |
| **INFO** | 20 | 正常信息，记录关键流程 | ✅启用 | 服务启动、配置加载、请求完成 |
| **DEBUG** | 10 | 调试信息，便于开发排查 | ❌禁用 | 变量值、分支路径、函数入口/出口 |
| **TRACE** | 5 | 详细跟踪，包含完整数据流 | ❌禁用 | 网络包内容、SQL语句参数 |

### 3.2 环境级别映射

| 环境 | 推荐根级别 | 动态调整 | 说明 |
|:-----|:----------:|:---------|:-----|
| 开发(Dev) | DEBUG | ✅ 可临时切到TRACE | 全量日志 |
| 测试(Test) | INFO | ✅ 可临时开启DEBUG | 仅关键调试时需要 |
| 预发布(Staging) | INFO | ⚠️ 临时开启需审批 | 尽量模拟生产 |
| 生产(Prod) | WARN/INFO | ❌ 默认不可开启DEBUG | 仅通过动态开关限时启用 |

### 3.3 动态日志级别切换

生产环境必须支持无需重启的动态级别切换：

```text
# 全局切换
curl -X POST /api/log-level?level=DEBUG&duration=30m

# 按模块切换
curl -X POST /api/log-level?module=com.example.db&level=DEBUG
```

**安全约束**：

- DEBUG级别最多开启30分钟，超时自动回退
- 每次开启记录到审计日志
- 按模块粒度控制，避免全局开启

## 4. 日志格式规范

### 4.1 结构化日志格式

所有日志必须采用**JSON结构化格式**，严禁自由文本日志：

```json
{
  "timestamp": "2026-07-21T16:42:05.123+08:00",
  "level": "ERROR",
  "logger": "com.example.service.OrderService",
  "thread": "executor-3",
  "trace_id": "a1b2c3d4e5f6",
  "span_id": "span-001",
  "message": "订单创建失败",
  "fields": {
    "order_id": "ORD-20260721-0001",
    "user_id": "U12345",
    "amount": 2999.00,
    "error_code": "PAYMENT_TIMEOUT"
  },
  "exception": "java.lang.RuntimeException: Payment gateway timeout\n  at com.example...",
  "host": "app-server-01",
  "service": "order-service",
  "env": "prod"
}
```

### 4.2 必选字段定义

| 字段 | 类型 | 必填 | 说明 | 示例 |
|:-----|:-----|:----:|:-----|:-----|
| `timestamp` | ISO8601 | ✅ | 日志产生时间，含时区 | `2026-07-21T16:42:05.123+08:00` |
| `level` | string | ✅ | 日志级别大写 | `ERROR` |
| `logger` | string | ✅ | 日志来源类/模块名 | `com.example.service.OrderService` |
| `message` | string | ✅ | 人类可读的日志摘要 | `订单创建失败` |
| `trace_id` | string | ✅ | 全局追踪ID，串联全链路 | `a1b2c3d4e5f6` |
| `service` | string | ✅ | 服务/组件名 | `order-service` |
| `host` | string | ✅ | 主机名或Pod名 | `app-server-01` |
| `env` | string | ✅ | 部署环境 | `prod` |

### 4.3 可选但推荐字段

| 字段 | 类型 | 说明 | 适用级别 |
|:-----|:-----|:-----|:---------|
| `span_id` | string | 跨度ID，用于分布式追踪 | ALL |
| `fields` | object | 结构化键值对，携带业务上下文 | ALL |
| `exception` | string | 异常堆栈 | ERROR/FATAL |
| `thread` | string | 线程名 | DEBUG+ |
| `request_id` | string | HTTP请求ID | INFO+ |
| `duration_ms` | int | 操作耗时(毫秒) | INFO+ |
| `user_agent` | string | 客户端标识 | 按需 |

### 4.4 日志格式规范检查清单

```text
✅ timestamp 使用ISO8601包含时区
✅ level 为大写枚举
✅ message 为人类可读的概要描述
✅ 敏感字段在fields中必须标记为"masked"
✅ 异常信息单独放在exception字段而非拼接在message中
✅ trace_id 贯穿全链路
✅ 单条日志 < 10KB（大对象需要裁剪或拆分）
```

## 5. 日志分类体系

### 5.1 按功能分类

| 分类 | 描述 | 示例事件 | 典型保留 |
|:-----|:-----|:---------|:--------:|
| **系统日志** | OS/平台基础设施 | 启动/停止、配置加载、资源耗尽 | 90天 |
| **操作日志** | 用户操作记录 | 登录、权限变更、数据修改 | 180天 |
| **审计日志** | 安全和合规相关 | 账号创建、策略变更、特权使用 | 365天+ |
| **性能日志** | 性能统计数据 | 响应时间、吞吐量、资源使用率 | 30天 |
| **诊断日志** | 故障排查信息 | 异常堆栈、Debug信息、系统状态 | 7天 |

### 5.2 按来源分类

| 分类 | 子类 | 日志源 |
|:-----|:-----|:-------|
| **硬件层** | BMC日志、SEL、POST Code、传感器 | IPMI/Redfish/OBFL |
| **OS层** | syslog、kernel log、journald | /var/log/ |
| **容器层** | Docker Engine、容器STDIO、K8s Events | Docker logging driver |
| **应用层** | Web访问、业务逻辑、数据库查询 | App代码、Nginx、MySQL |

## 6. 日志驱动与传输

### 6.1 日志驱动的选择

以容器化场景为例，Docker支持多种日志驱动：

| 驱动 | 优点 | 缺点 | 适用场景 |
|:-----|:-----|:-----|:---------|
| **json-file** | 默认可用、docker logs支持、支持tag | 本地存储不聚合、撑爆磁盘 | 开发/测试环境 |
| **syslog** | TLS支持加密、多数OS自带 | 需HA部署syslog server | 安全敏感场景 |
| **journald** | Docker daemon日志也纳入、本地缓存不影响远端 | 二进制格式、需额外转发 | 高可靠本地缓冲 |
| **gelf** | 自带可索引字段(container_id/host/tag) | 仅支持UDP | ELK/Graylog场景 |
| **fluentd** | 多输出后端、字段丰富 | 复杂部署 | 大规模K8s集群 |
| **splunk** | 集成度好、TLS支持 | 商业授权成本 | 已部署Splunk的组织 |

### 6.2 推荐传输架构

```ascii
App Log -> stdout/stderr -> Docker json-file(本地缓冲)
                                      v
                          Fluentd/Logstash Agent(采集)
                                      v
                              Kafka(缓冲/削峰)
                                      v
                           Elasticsearch(索引)
                                      v
                              Kibana/Grafana(可视化)
```

**关键设计点**：

1. **本地缓冲优先**：使用journald或json-file做本地缓存，远端不可用时不影响应用
2. **削峰缓冲**：Kafka在高峰期做缓冲区，防止后端被突增日志冲垮
3. **Agent旁路**：Logstash/Fluentd以Sidecar或DaemonSet运行，不侵入业务进程

### 6.3 日志传输安全

| 传输环节 | 安全措施 | 说明 |
|:---------|:---------|:-----|
| DTLS/TLS加密 | TLS 1.2+ | 网络传输加密 |
| 认证机制 | mTLS或Token | 防止伪造日志注入 |
| 完整性校验 | SHA256校验和 | 防止日志篡改 |
| 传输限速 | 每源≤10MB/s | 防止日志泛洪攻击 |

## 7. 存储与生命周期

### 7.1 分层存储策略

| 存储层 | 存储介质 | 数据新鲜度 | 查询性能 | 成本 |
|:-------|:---------|:----------:|:---------|:----:|
| 热存储(Hot) | SSD/内存 | 实时~7天 | 亚秒级 | 高 |
| 温存储(Warm) | HDD | 7~30天 | 秒级 | 中 |
| 冷存储(Cold) | 对象存储(S3) | 30~365天 | 分钟级 | 低 |
| 归档(Archive) | 磁带/冷归档 | 1年+ | 小时~天 | 极低 |

### 7.2 日志轮转配置

文件日志的轮转参数：

| 参数 | 推荐值 | 说明 |
|:-----|:------:|:-----|
| 单文件大小 | 100MB~1GB | 根据IO能力调整 |
| 保留文件数 | 10~30 | 根据磁盘容量调整 |
| 压缩策略 | 轮转后gzip | 可压缩至原大小的5~15% |
| 轮转触发 | 按大小+按时间 | 大日志优先按大小 |

### 7.3 存储容量估算

```text
日志量估算公式：
  日日志量(GB) = 单条日志平均大小(KB) × 每秒TPS × 86400 / 1024 / 1024

示例：
  单条日志0.5KB × 1000 TPS × 86400 = 43,200,000条/天
  = ~41 GB/天（原始）
  = ~4 GB/天（压缩后）

保留策略：
  热存储: 41GB × 7天 = 287 GB
  温存储: 41GB × 23天 = 943 GB
  冷存储: 41GB × 335天 × 0.3(压缩) = 4.1 TB
  总计: ~5.3 TB/年
```

## 8. 安全与合规

### 8.1 日志脱敏规则

日志中绝不能记录明文敏感信息。脱敏处理规则：

| 敏感类型 | 处理方法 | 输入示例 | 脱敏后 |
|:---------|:---------|:---------|:-------|
| 密码/密钥 | 完全屏蔽 | `password=MyP@ss123` | `password=***` |
| 身份证号 | 保留前4后4 | `110101199001011234` | `110101****1234` |
| 手机号 | 保留前3后4 | `13800138000` | `138****8000` |
| 信用卡号 | 保留前6后4 | `6222021234567890` | `622202****7890` |
| 邮箱 | 保留域名 | `user@example.com` | `***@example.com` |
| 地址 | 仅保留省市 | `北京市海淀区中关村大街1号` | `北京市海淀区***` |
| Token/Cookie | 完全屏蔽 | `Bearer eyJhbGci...` | `Bearer ***` |

### 8.2 脱敏实现策略

```python
# Python示例：结构化日志自动脱敏
import re

SENSITIVE_PATTERNS = {
    'password': lambda v: '***',
    'id_card': lambda v: v[:6] + '****' + v[-4:] if len(v) == 18 else '***',
    'phone': lambda v: v[:3] + '****' + v[-4:] if len(v) == 11 else '***',
    'credit_card': lambda v: v[:6] + '****' + v[-4:] if len(v) == 16 else '***',
    'token': lambda v: '***',
}

def mask_sensitive(key, value):
    for pattern, mask_fn in SENSITIVE_PATTERNS.items():
        if pattern in key.lower():
            return mask_fn(value)
    return value

# 在日志框架中注册全局filter
class SensitiveDataFilter(logging.Filter):
    def filter(self, record):
        if hasattr(record, 'fields'):
            for k, v in record.fields.items():
                record.fields[k] = mask_sensitive(k, v)
        return True
```

## 10. 硬件诊断日志

### 10.1 硬件诊断体系

硬件诊断日志是设备级可靠性的基础，从芯片级到系统级覆盖：

| 层级 | 诊断机制 | 记录内容 | 触发方式 |
|:-----|:---------|:---------|:---------|
| 芯片级 | MBIST、LBIST | 内存/逻辑BIST结果 | 上电/post-silicon |
| 板级 | POR(Power-On Reset)、边界扫描 | 时钟、复位、JTAG状态 | 上电 |
| 模块级 | 在线诊断(GOLD) | ASIC寄存器、端口环路 | 启动/热插拔/周期性 |
| 系统级 | OBFL(Onboard Failure Logging) | 温度、电压、环境历史 | 持续监控 |
| 平台级 | IPMI SEL、Redfish Events | 传感器告警、FRU变更 | 事件驱动 |

### 10.2 Generic Online Diagnostics (GOLD) 设计

参考Cisco NX-OS GOLD框架，诊断测试分类：

| 测试类型 | 执行时机 | 是否中断业务 | 测试内容 |
|:---------|:---------|:------------:|:---------|
| **Bootup测试** | 系统启动时 | ✅ | 内存、总线、核心ASIC |
| **On-demand测试** | 运维人员触发 | ⚠️ 部分中断 | 指定模块/端口 |
| **Health Monitor** | 后台持续运行 | ❌ | 传感器、温度、电压 |
| **OIR测试** | 热插拔事件触发 | ❌ | 新插入模块完整性 |

诊断结果编码：

```text
. = Pass (通过)
F = Fail  (失败)
I = Incomplete (未完成)
U = Untested (未测试)
A = Abort  (中断)
E = Error disabled (错误禁用)
```

## 12. 安全监控与SIEM

### 12.1 SIEM与日志管理的关系

SIEM (Security Information and Event Management) 是日志系统的上层应用，负责安全事件的实时分析和告警。

```ascii
日志采集 -> 日志存储(ELK/ClickHouse) -> SIEM分析引擎 -> 告警/工单
                                              v
                                        威胁情报源
```

### 12.2 关键安全事件映射

从IT合规专家实践中总结的关键安全事件：

| 控制流程 | 关联事件ID | 重要性 | 响应方式 |
|:---------|:-----------|:------:|:---------|
| 用户登录失败 | Windows 4625/Linux sudo失败 | 🔴高 | 实时告警+工单 |
| 特权账号使用 | Windows 4672 | 🔴高 | 实时告警 |
| 账号创建/删除 | Windows 4720/4726 | 🟡中 | 日报审核 |
| 系统配置变更 | Windows 4946/4947 | 🟡中 | 日报审核 |
| 安全策略修改 | Windows 4719 | 🔴高 | 实时告警 |
| 服务启停 | Windows 7034/7036 | 🟡中 | 定期审查 |
| 文件完整性变更 | File Integrity Monitor | 🟡中 | 告警+工单 |
| 防火墙规则变更 | Windows 4949/4950 | 🟡中 | 日报审核 |

### 12.3 安全监控实施要点

1. **事件优先级**：严格区分"需实时响应"和"定期审核"的事件，避免告警疲劳
2. **前后关联**：单条日志不足以判定安全事故，需结合上下文（时间窗口、来源IP、用户行为序列）
3. **噪声过滤**：自动过滤已知的误报模式（如计划内的维护窗口、调度任务引发的登录）
4. **证据保留**：安全事件相关的原始日志应单独保留，防止被轮转覆盖
5. **响应闭环**：事件触发告警→生成工单→分配处理→记录处理结果→闭环验证

### 12.4 攻击阶段检测

| 攻击阶段 | 检测日志源 | 关键信号 | 响应优先级 |
|:---------|:-----------|:---------|:----------:|
| 侦察(Recon) | Web/Nginx日志 | 大量404、路径扫描 | 中 |
| 初始访问 | SSH/AD认证日志 | 暴力破解登录失败 | 高 |
| 权限提升 | Windows EventLog | 特权账号创建、提权操作 | 紧急 |
| 横向移动 | 网络设备日志 | 异常内网连接 | 高 |
| 数据渗出 | 防火墙/DNS日志 | 大量出站流量 | 紧急 |

## 13. 日志审计与合规检查

### 13.1 日志管理审计检查清单

参考IT审计清单和CobiT控制框架，完整的日志管理审计分为三个层面：

**管理控制(Management Controls)**

| 编号 | 检查项 | 合规标准 |
|:-----|:-------|:---------|
| MC-1 | 是否有正式发布的日志管理策略文档 | 已发布、全体员工可访问 |
| MC-2 | 日志策略是否定期审查更新 | 至少年度审查 |
| MC-3 | 是否有日志监控的SLA定义 | 定义告警响应时间 |
| MC-4 | 是否定义了日志相关角色和职责 | RACI矩阵 |
| MC-5 | 是否有日志绩效指标(KPI) | 采集率、告警响应率 |

**操作控制(Operational Controls)**

| 编号 | 检查项 | 合规标准 |
|:-----|:-------|:---------|
| OC-1 | 关键系统的日志是否启用 | 100%覆盖率 |
| OC-2 | 日志是否自动轮转和归档 | 配置检查 |
| OC-3 | 日志存储是否满足合规保留期 | 按法规要求 |
| OC-4 | 日志是否做时间同步(NTP) | 所有设备NTP同步 |
| OC-5 | 日志存储是否异地备份 | 至少一份异地副本 |

**技术控制(Technical Controls)**

| 编号 | 检查项 | 合规标准 |
|:-----|:-------|:---------|
| TC-1 | 日志是否进行完整性校验 | SHA256或数字签名 |
| TC-2 | 日志访问是否有权限控制 | RBAC最小权限 |
| TC-3 | 敏感日志是否加密存储 | AES-256 |
| TC-4 | 日志传输是否加密 | TLS 1.2+ |
| TC-5 | 是否有日志防篡改机制 | 写一次读多次(WORM) |

### 13.2 日志审计的五个阶段

```ascii
Phase 1: 审计计划
  +-- 明确审计目标和范围
  +-- 确定评估标准和框架(CobiT/ISO 27002/NIST)
  +-- 与审计团队沟通预期
Phase 2: 证据收集
  +-- 策略文档审查
  +-- 配置审计(自动化脚本)
  +-- 人员访谈
Phase 3: 控制测试
  +-- 日志完整性测试
  +-- 覆盖率验证
  +-- 告警有效性测试
Phase 4: 差距分析
  +-- 与合规基线对比
  +-- 识别缺失控制
  +-- 风险等级评估
Phase 5: 整改跟踪
  +-- 制定整改计划
  +-- 设定里程碑
  +-- 定期复查进度
```

### 13.3 常见审计发现项

| 问题 | 严重程度 | 解决方案 |
|:-----|:--------:|:---------|
| 关键系统未启用日志 | 🔴高 | 配置日志策略，启用CEF/Syslog |
| 日志时间不同步 | 🔴高 | 统一NTP服务器，配置验证 |
| 日志保留期不足 | 🔴高 | 调整轮转策略，增加冷存储 |
| 敏感信息出现在日志中 | 🔴高 | 实施脱敏过滤器 |
| 日志存储未冗余保护 | 🟡中 | 添加异地备份/复制 |
| 无日志审计流程 | 🟡中 | 建立定期审计制度 |
| 日志告警被忽略 | 🟡中 | 建立SLA和升级机制 |
