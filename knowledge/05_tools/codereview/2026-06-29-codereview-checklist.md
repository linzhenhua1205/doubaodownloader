## 一、安全漏洞检查（高危，必须拦截）

| # | 检查项 | 说明 | 示例 |
|:-:|:-------|:-----|:------|
| 1 | SQL 注入 | 用户输入未参数化直接拼接 SQL | `f"SELECT * FROM user WHERE id = {uid}"` |
| 2 | XSS 反射 | 前端直接渲染未转义的用户输入 | `innerHTML = user_input` |
| 3 | 硬编码密钥/密码 | 密钥、Token、密码直接写在代码中 | `API_KEY = "sk-xxx"` |
| 4 | 敏感信息泄露 | 日志/报错信息输出密码、手机号、身份证 | `logger.info(f"password={pwd}")` |
| 5 | 越权访问 | 接口未校验用户权限 | 未鉴权的管理后台接口 |
| 6 | SSRF | 用户可控 URL 被服务端请求 | `requests.get(user_url)` |
| 7 | 路径遍历 | 用户输入拼接文件路径 | `open(f"/data/{filename}")` |
| 8 | 反序列化漏洞 | 不可信数据直接反序列化 | `pickle.loads(user_data)` |
| 9 | 命令注入 | 用户输入拼接 shell 命令 | `os.system(f"ping {host}")` |
| 10 | CSRF 缺失 | 状态变更接口未校验 CSRF Token | POST 修改密码接口无 Token |

## 二、性能问题检查

| # | 检查项 | 说明 | 严重程度 |
|:-:|:-------|:-----|:---------|
| 1 | N+1 查询 | 循环内执行数据库查询 | ⚠️ 严重 |
| 2 | 未释放资源 | 文件句柄/网络连接/Database Cursor 未关闭 | ⚠️ 严重 |
| 3 | 循环内高开销操作 | 循环中调用远程 API、加锁、正则编译 | ⚠️ 严重 |
| 4 | 大数据量全表扫描 | 无索引查询、不走索引的 LIKE/ORDER BY | ⚠️ 严重 |
| 5 | 不必要的深拷贝 | 大对象反复深拷贝 | 🔶 一般 |
| 6 | 同步阻塞 | 异步框架中使用阻塞 I/O | ⚠️ 严重 |
| 7 | 重复计算 | 循环中重复计算不变表达式 | 🔶 一般 |
| 8 | 对象重复创建 | 高频路径中 new 对象 | 🔶 一般 |
| 9 | 未使用连接池 | 每次请求新建数据库/HTTP 连接 | ⚠️ 严重 |
| 10 | 大事务 | 事务内包含耗时的非 DB 操作 | 🔶 一般 |

## 三、代码规范与风格

| # | 检查项 | 说明 |
|:-:|:-------|:------|
| 1 | 命名规范 | 变量/函数/类/常量命名是否符合团队规范（camelCase/snake_case） |
| 2 | 注释质量 | 复杂逻辑有注释，注释与代码一致，无遗留 TODOs |
| 3 | 死代码 | 无引用变量/函数、注释掉的代码段、import 未使用 |
| 4 | 魔法数字 | 硬编码数值应定义命名常量 |
| 5 | 函数长度 | 单个函数不宜超过 50~80 行 |
| 6 | 参数数量 | 函数参数不宜超过 4~5 个 |
| 7 | 重复代码 | 相同逻辑出现多次应考虑抽取 |
| 8 | 缩进格式 | 与项目 .editorconfig / linter 配置一致 |
| 9 | 文件组织 | 一个文件专注于一个职责 |
| 10 | 异常处理 | 捕获异常时不要太宽泛（`except Exception`），区分预期/非预期异常 |

## 四、业务逻辑缺陷

| # | 检查项 | 说明 |
|:-:|:-------|:------|
| 1 | 边界条件缺失 | 空值、负数、空集合、超大值的处理 |
| 2 | 分支覆盖不足 | 缺少 else / default 分支 |
| 3 | 竞态条件 | 多线程/多进程共享变量未加锁 |
| 4 | 事务一致性 | 多个数据源操作未保证事务 |
| 5 | 状态错误 | 枚举值缺失、状态机跳转非法 |
| 6 | 类型假设 | 假设输入总是特定类型，未做类型校验 |
| 7 | 整数溢出 | 数值计算超出类型范围 |
| 8 | 精度丢失 | 浮点数比较、金额计算用 float |
| 9 | 回调未处理 | Promise/异步回调未 catch 异常 |
| 10 | 降级逻辑缺失 | 依赖服务超时/失败时无容错 |

## 五、测试相关

| # | 检查项 | 说明 |
|:-:|:-------|:------|
| 1 | 单元测试覆盖 | 新增/修改代码有对应单测 |
| 2 | 边界测试 | 覆盖空、异常、临界值场景 |
| 3 | Mock 正确性 | Mock 的返回值是否符合真实行为 |
| 4 | 测试独立 | 测试之间不依赖共享状态 |
| 5 | 断言完整性 | 测试需要断言结果，不能只"不报错" |
| 6 | 快照测试 | 复杂输出使用快照测试 |
| 7 | 性能测试 | 关键路径有性能基准（Benchmark） |

## 六、提交规范检查

| 检查项 | 推荐标准 |
|:-------|:----------|
| Commit 格式 | `type(scope): subject` 如 `feat(auth): add OAuth2 login` |
| type 标准 | feat/fix/docs/style/refactor/perf/test/chore/ci |
| Breaking Change | 在 Commit 底部标记 `BREAKING CHANGE:` |
| Issue 关联 | Commit/PR 关联 Issue 编号 |
| PR 标题 | 简洁描述变更，不超过 50 字符 |
| PR 描述 | 说明"为什么改" > "改了什么" |
| 变更范围 | 一个 PR 专注一个功能/修复，不宜过大 |

> 📌 详细 Commit 规范 → [`../git/2026-06-29-git-commit-convention-and-validation.md`](../git/2026-06-29-git-commit-convention-and-validation.md)

## 七、按语言专项检查

### Python

- 使用 with 语句管理资源（文件、数据库连接）
- 避免可变默认参数：`def f(a=[])` → `def f(a=None)`
- 避免野 `except:`，至少用 `except Exception:`

### Java

- 检查 NullPointerException 风险
- equals/hashCode 成对覆写
- 线程安全（synchronized/ConcurrentHashMap/Atomic）

### Go

- 检查 defer 中修改函数返回值
- 检查 goroutine 泄漏（channel 未关闭）
- 检查 context 传递完整性

### JavaScript/TypeScript

- `==` vs `===`（优先使用 `===`）
- async/await 的 try-catch 覆盖
- 内存泄漏（定时器、事件监听未清理）

## 八、检查结果分级

| 级别 | 颜色 | 定义 | 处理要求 |
|:-----|:-----|:------|:---------|
| 🔴 严重 (Critical) | 红 | 安全漏洞、数据丢失、业务阻断 | **必须修复**，否则阻塞合并 |
| 🟠 一般 (Warning) | 橙 | 性能隐患、代码坏味道、边界缺失 | 建议修复，讨论后可降级 |
| 🟢 建议 (Suggestion) | 绿 | 风格优化、可读性改进 | 非必须，鼓励采纳但可延期 |
