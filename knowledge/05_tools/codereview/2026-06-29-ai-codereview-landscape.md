## 一、三大主流路径概览

| 维度 | 🅰 自建平台 | 🅱 第三方 SaaS | 🅲 IDE 闭环 |
|:-----|:-----------|:--------------|:-----------|
| **代表方案** | GitLab WebHook + LLM + CodeReview Agent | Cursor Bugbot / PR-Agent / CodeAnt | Cursor + Skills + MCP |
| **触发时机** | 提交 PR/MR 后 | 提交 PR/MR 后 | 编码中 / 提交前 |
| **定位** | 平台级兜底 | 快速接入 | 开发前置 |
| **成本** | 高（开发+维护+硬件） | 中（按人头/次数收费） | **低**（复用 IDE） |
| **定制能力** | 高（完全控制） | 低（黑盒规则） | **高**（自定义 Skill） |
| **上下文理解** | 中（需自建 RAG） | 弱（云端） | **强**（本地 Codebase） |
| **人力投入** | 2~3 人长期维护 | 几乎为零 | 1 人维护规则 |
| **安全可控** | **高**（内网部署） | 低（代码外发） | **高**（本地执行） |
| **集成成本** | 高 | **低** | 中 |

## 二、路径详解

### 🅰 自建平台 — 适合大型团队/安全敏感场景

**典型架构**：

```text
GitLab WebHook -> 消息队列 -> AI CR 服务 -> LLM 推理 -> 回写 GitLab
                              v                v
                         Git 拉取上下文    Nexus 私有依赖
```

**优势**：完全掌控数据流，可深度集成团队规范，支持内网 LLM
**劣势**：投入产出比低，需自建 RAG/上下文工程，长 Diff 处理复杂

**适用条件**：

- 团队 50+ 人，有专职 DevOps 团队
- 代码不允许出内网
- 需深度定制审查规则和自动化流水线

> 📎 详细方案 → [GitLab WebHook 集成](2026-06-29-gitlab-webhook-integration.md)

---

### 🅱 第三方 SaaS — 适合快速验证/小团队

**代表工具**：

- Cursor Bugbot：内置 AI 审查
- PR-Agent：GitHub App 自动评审
- CodeAnt：全自动代码质量平台
- Amazon CodeGuru Reviewer

**优势**：零配置分钟级接入，无需维护基础设施
**劣势**：按人头收费（$20~40/人/月）、规则黑盒、上下文感知弱

**适用条件**：

- 小团队（<10人），无专职 DevOps
- 对数据安全要求不高
- 希望快速试水 AI CR

---

### 🅲 IDE 闭环（推荐）— 适合大多数研发团队

**代表方案**：Cursor + Skills + MCP

**核心理念**：将 CR 从云端"事件驱动"回归到 IDE "开发现场"

```text
旧范式：编码 -> 提交 PR -> 云端 AI 审查 -> 评论回写（反馈在 10 分钟后）
新范式：编码 -> IDE 内 AI 审查 -> 人工确认 -> 提交 PR（反馈在 10 秒内）
```

**优势**：

- ⭐ **成本极低**：复用 Cursor 订阅，零额外服务器成本
- ⭐ **上下文最强**：依托本地 Codebase，跨文件理解
- ⭐ **100% 定制**：Skill 完全贴合团队规范
- ⭐ **流程顺滑**：IDE 内闭环，不打断开发节奏
- ⭐ **持续进化**：真实 PR 数据驱动，越用越准

**落地效果（团队实测）**：

- 高频问题识别率：70% → 90%
- 单次 PR 审查耗时：15 分钟 → 5 分钟
- 人工 Review 时间减少 **60%**
- Bug 数下降 **20%**

> 📎 详细实践 → [Cursor Code Review 实践](2026-06-29-cursor-codereview-practice.md)

## 三、选型决策树

```text
团队需要 AI Code Review？
|
+- 代码不允许出内网？
|  +- 有专职 DevOps 团队？
|  |  +- 是 -> 🅰 自建平台（GitLab + LLM）
|  |  +- 否 -> 🅲 IDE 闭环（本地模型 + Cursor）
|  |
+- 团队 ≤ 10 人？
|  +- 想快速验证价值？
|  |  +- 是 -> 🅱 第三方 SaaS（PR-Agent / CodeAnt）
|  |  +- 否 -> 🅲 IDE 闭环（长期性价比最高）
|  |
+- 已有 Cursor 订阅？
|  +- 是 -> 🅲 IDE 闭环（零额外成本）
|  +- 否 -> 根据预算选 🅱 或 🅲
|
+- 资金充裕、追求完全控制？
   -> 🅲 + 🅰 双轨并行（IDE 前置 + 平台兜底）
```

## 四、各方案检查能力对比

| 检查维度 | 🅰 自建平台 | 🅱 第三方 SaaS | 🅲 IDE 闭环 |
|:---------|:-----------|:--------------|:-----------|
| 安全漏洞扫描 | ✅ 完全可定 | ✅ 内置 | ✅ Skill 定义 |
| 性能问题 | ✅ 完全可定 | ❌ 有限 | ✅ Skill 定义 |
| 代码规范 | ✅ 完全可定 | ⚠️ 部分 | ✅ Skill 定义 |
| 业务逻辑 | ⚠️ 依赖上下文 | ❌ 弱 | ✅ Codebase 感知 |
| 跨文件分析 | ⚠️ 需自建 RAG | ❌ 弱 | ✅ 本地索引 |
| 私有 SDK 感知 | ✅ 可对接 Nexus | ❌ | ⚠️ 需手动引用 |
| 架构合理性 | ⚠️ 依赖规则 | ❌ | ⚠️ 需高级 Skill |
| 审查报告格式化 | ✅ 全定制 | ⚠️ 固定格式 | ✅ Skill 定义 |
| 自动化阻断（门禁） | ✅ | ⚠️ 有限 | ❌ 仅建议 |

## 五、推荐双轨策略

对于中大型团队，推荐 **IDE 闭环 + GitLab 平台** 双轨并行：

```text
执行阶段
+- 开发阶段：🅲 Cursor IDE 闭环 — 前置拦截 80% 问题
+- 提交阶段：🅰 GitLab WebHook — MR 自动评审兜底
+- 发布阶段：专项深度审查 — 安全与架构评审
```

这一策略兼顾**效率**（IDE 即时反馈）与**安全**（平台级兜底）。
