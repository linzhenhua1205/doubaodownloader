## 一、什么是代码审查

Code Review（代码审查/代码评审）是软件开发流程中**对代码变更进行系统性检查**的质量保障活动。其核心价值在于：

- **缺陷拦截**：在代码合入主线前发现逻辑错误、安全漏洞、性能问题
- **知识传递**：让团队成员相互学习编码习惯、业务逻辑和设计思路
- **规范统一**：确保代码风格、命名、架构模式符合团队约定
- **集体所有权**：避免"只有一个人理解这段代码"的风险

> 💡 Code Review 不是找茬，而是**集体质量承诺**。

## 二、传统 CR 的七大痛点

| # | 痛点 | 表现 | 后果 |
|:-:|:-----|:-----|:------|
| 1 | **耗时费力** | 资深工程师逐行审阅，一个 PR 需数小时 | 挤占创新与架构设计时间 |
| 2 | **标准不一** | 不同审查者尺度各异，关键问题被遗漏 | 质量波动大，可重复性差 |
| 3 | **反馈滞后** | 多在 PR/MR 提审后才做，修复成本高 | 改一行可能牵连整个文件 |
| 4 | **知识断层** | 规范依赖"老师傅"口传心授 | 新人难上手，经验随员工离职流失 |
| 5 | **语言壁垒** | 审查者只精通部分语言 | 非专长语言审查流于形式 |
| 6 | **主观性强** | 轻易漏掉边界条件、竞态条件等深层问题 | 线上事故隐患 |
| 7 | **缺乏数据** | 评审效果难以量化度量 | 无法持续改进 |

## 三、CR 左移理念（核心范式转变）

**左移（Shift Left）** 是指将代码审查从**提交 MR/PR 后**提前到**编码阶段**，在 IDE 内即时完成。

### 传统流程（右偏）

```text
编码 -> 提交 -> PR/MR -> 人工评审 -> 修改 -> 合并
                            ^
                      问题在此发现，成本已高
```

### 左移流程（新范式）

```text
IDE内编码 -> AI即时审查 -> 人工确认 -> 提交PR -> 自动MR评审 -> 人工终审
    ^                          ^                ^
 问题前置拦截             责任归人           平台兜底
```

### 左移的三大优势

1. **成本更低**：编码阶段修复缺陷的成本是提测后的 1/10~1/20
2. **反馈更快**：秒级获得 AI 审查结果，不打断开发节奏
3. **质量更稳**：多项检查在提交前完成，避免"提交即污染"主线

> 📌 **核心理念**: AI 做执行，人做决策。AI 负责机械性、重复性检查，人聚焦架构与业务逻辑。

## 四、人机协同分工模型

| 角色 | 负责内容 | 职责边界 |
|:-----|:---------|:---------|
| **AI** | 格式/命名/规范、重复代码、敏感信息扫描、空指针/边界检查、简单性能问题 | 输出初步审查报告，标记置信度 |
| **开发者** | 功能自测、AI 审查结果确认、修复低级问题 | 提交前完成自我校验 |
| **Reviewer（人）** | 架构合理性、业务逻辑正确性、设计模式、AI 输出收敛、最终质量守门 | **必须终审**，安全、业务、破坏性变更强制人工 |

### 关键原则

1. **AI 不背锅**：最终质量责任始终由 Reviewer 承担
2. **AI 先行，人工把关**：AI 处理 80% 常规检查，人聚焦 20% 高价值判断
3. **持续投喂**：用真实 PR 数据持续优化 AI 审查规则，越用越准

## 五、CR 流程分级

推荐按**开发阶段**分三个层级的审查流程：

### 层级一：开发阶段（IDE 侧）

- AI 即时审查变更代码
- 提交前自动运行规则校验
- 可选：AI 自动生成修复建议

### 层级二：提交阶段（CI/CD 侧）

- WebHook 触发自动 AI 评审（MR/Push 事件）
- GitLab/GitHub 行内评论回写
- 静态工具告警 AI 提炼

### 层级三：专项审查（版本发布前）

- 全工程安全扫描
- 架构合规性审查
- 性能基线对比

## 六、常见误区

| 误区 | 纠正 |
|:-----|:------|
| "CR 就是找 Bug" | CR 是知识传递 + 设计验证 + 标准对齐，不止找 Bug |
| "AI 能完全替代人工 CR" | AI 做机械检查，人做架构判断，缺一不可 |
| "左移就只做 IDE 审查" | 左移不替代 MR 评审，而是**前置补充** |
| "CR 规则一次写完永久生效" | 规则需持续迭代：复盘误报/漏报 → 调整规则 → 沉淀规范 |
