## 一、并发

### goroutine 核心

| 特性 | 说明 |
|:-----|:------|
| 栈初始大小 | **2KB**（OS 线程默认 MB 级），按需扩容，最大可到 GB 级 |
| 线程模型 | 任何时候仅有限几个线程参与并发，通过 P 控制并发度 |
| 处理器数量 | `runtime.GOMAXPROCS` 或环境变量，默认等于 CPU 核数 |

### 多进程/线程/协程分工

| 模式 | 用途 |
|:-----|:------|
| 多进程 | 分布式负载均衡，减轻单进程 GC 压力 |
| 多线程 (LWP) | 抢夺更多处理器资源 |
| 协程 (goroutine) | 提高处理器时间片利用率 |

### 通道 (channel)

- 并发安全的队列
- **goroutine leak**：goroutine 在发送/接收阻塞且未被唤醒 → 垃圾回收器不回收 → 资源泄露

### 同步（Mutex/RWMutex）

| 建议 | 原因 |
|:-----|:------|
| Mutex 作为匿名字段时用 pointer-receiver | 避免因复制导致锁失效 |
| 锁粒度控制在最小范围 | 及早释放 |
| 避免 `defer Unlock` 在高性能场景 | defer 有额外开销 |
| 读写并发用 `RWMutex` | 性能更好 |
| 单数据读写用原子操作 | 更轻量 |

### 通道 vs 锁

- **通道**：解决逻辑层次的并发处理架构
- **锁**：保护局部范围的数据安全

## 二、测试/监控/性能调优

### 测试工具

| 命令 | 用途 |
|:-----|:------|
| `go test -cover -covermode count -coverprofile cover.out` | 代码覆盖率 |
| `go test -bench .` | 基准测试 |
| `go test -run NONE -bench . -memprofile mem.out -cpuprofile cpu.out -blockprofile block.out` | 性能监控指标 |
| `go tool pprof 文件名` | 可视化分析 profile |

| `net/http/pprof` | HTTP 封装版，`import _ "net/http/pprof"` |
| `GODEBUG=gctrace=1` | GC 监控 |

### 常用分析工具

| 工具 | 用途 |
|:-----|:------|
| **go-torch** | 生成性能火炬图 |

### 性能优化建议

| 类型 | 建议 |
|:-----|:------|
| 🧠 内存 | 小对象合并结构体一次分配；缓冲区预估大小；slice/map 创建时指定 cap；长调用栈避免频繁临时对象 |
| ⚡ 并发 | 高并发用 goroutine 池；避免高并发调用同步系统接口；避免共享对象互斥 |
| 🔧 其他 | 减少 CGO 调用；减少 `[]byte`↔`string` 转换；字符串拼接用 `bytes.Buffer` |

## 三、内存分配

### 核心策略

1. 从 OS 申请大块内存（如 1MB），减少系统调用
2. 按固定大小切分为小块，构成链表
3. 分配时从合适链表取一块，回收时归还
4. 闲置过多时归还部分给 OS

### 两种内存块

| 类型 | 说明 |
|:-----|:------|
| **span** | 多个连续页 (page) 组成的大块内存 |
| **object** | span 按特定大小切分的小块，每个可存储一个对象 |

### 三组件架构

```text
cache ---- 每个工作线程绑定一个，无锁 object 分配
   |
   v
central -- 为所有 cache 提供后备 span 资源
   |
   v
heap ----- 管理闲置 span，向 OS 申请新内存
```

### 分配流程

```text
计算规格 -> cache.alloc 找 span -> span.freelist 取 object
                                        v (空)
                                  central 取新 span
                                        v (空)
                                heap.free/freelarge -> 切分
                                        v (空)
                                  向 OS 申请新内存
```

### 释放流程

1. object 归还到 span.freelist
2. span 放回 central（可被任意 cache 复用）
3. span 的 object 全部回收 → 交还 heap 重新切分
4. 定期扫描 heap 中长时间闲置的 span，释放物理内存

### 逃逸分析

编译器在编译期构建调用图，分析局部变量是否被外部引用：

- 未被引用 → 分配在 **栈**（高性能）
- 被外部引用 → 分配在 **堆**（逃逸）

### 内存释放

sysmon 约每 **5 分钟** 检查 heap 闲置内存块：

- 遍历 free/freelarge 中所有 span
- 闲置超过阈值 → 调用 `madvise` 告知内核回收物理内存

## 四、垃圾回收

### 策略：标记-清除 (Mark and Sweep)

从 Go 1.5 起采用 **三色并发标记检测**（标记和用户逻辑并发执行）。

### 三色标记

| 颜色 | 含义 | 处理 |
|:-----|:------|:------|
| ⚪ **白色** | 待回收对象（初始全白） | 标记结束后回收 |
| 🟡 **灰色** | 处理中对象 | 放入 gcWork 高性能缓存队列 |
| ⚫ **黑色** | 活跃对象（已扫描） | 保留 |

### 流程

1. 所有对象初始为白色
2. 扫描可达对象 → 标记为灰色
3. 从队列取出灰色 → 引用对象标灰放队列 → 自身标黑
4. 写屏障监视内存修改
5. 完成扫描 → 白色回收、黑色保留

### 写屏障

解决**三色标记过程中对象引用被修改**的问题。Go 使用**混合写屏障**。

| 类型 | 说明 |
|:-----|:------|
| ❌ 插入写屏障（旧版） | 栈无 hook → 需 STW 重新扫描栈 |
| ❌ 删除写屏障 | Go 未单独实现 |
| ✅ **混合写屏障**（Go 1.8+） | 起始无需 STW 打快照；栈上新建对象均为黑色；扫描精度够用；全程无 STW |

### GC 五阶段 (Go 1.14+)

```text
GCMark (准备, 启动写屏障) -> STW
GCMark (并发标记, 写屏障开启) -> 并发
GCMarkTermination (标记终止, 停止写屏障) -> STW
GCoff (内存清扫, 写屏障关闭) -> 并发
GCoff (内存归还给 OS) -> 后台
```

## 五、并发调度

### 核心调度逻辑

- **P**：类似 CPU 核，控制并发任务数，数量默认 = CPU 核数，可用 `GOMAXPROCS` 修改
- **G**：一切以 G 方式运行（包括运行时服务和 main 函数）
- **M**：系统线程，与 P 绑定，以调度循环不停执行 G 任务

### 关键行为

| 行为 | 说明 |
|:-----|:------|
| **P 数量动态修改** | `GOMAXPROCS` 执行时修改 → `stopTheWorld` + `startTheWorld`，代价极大 |
| **sysmon 监控线程** | ①释放闲置 >5min 的 span 物理内存 ②>2min 无 GC 则强制执行 ③处理 netpoll 结果 ④抢占长时间运行的 G ⑤收回 syscall 阻塞的 P |
| **抢占调度** | 在目标 G 上设置抢占标志 → 下次函数调用时检查标志决定是否暂停 |
| **stopTheWorld** | 通过通知机制向所有 G 发出抢占调度，使其暂停在安全点 |
| **defer 延迟调用** | 非简单 CALL 指令，涉及对象分配、缓存和多次函数调用，**高性能场景避免使用** |
