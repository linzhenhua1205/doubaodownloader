## Mutex 结构

```go
type Mutex struct {
    state int32  // 互斥锁状态
    sema  uint32 // 信号量
}
```

### state 的 4 个标志位

```text
31 --------------------- 3 -- 2 -- 1 -- 0 --
|   Waiter 计数 (29 bit)  | S  | W  | L  |
+------------------------+----+----+----+
```

| 位 | 标志 | 含义 |
|:---|:-----|:------|
| 0 | **Locked** | 是否已被锁定 (0=未锁, 1=已锁) |
| 1 | **Woken** | 是否有协程已被唤醒 (0=无, 1=有) |
| 2 | **Starving** | 是否处于饥饿状态 (0=正常, 1=饥饿>1ms) |
| 3+ | **Waiter** | 阻塞等待锁的协程个数 |

> 协程抢锁的本质：争夺给 Locked 位赋值为 1 的权利

## Lock 流程

### 单协程加锁（Fast Path）

```text
CAS(&m.state, 0, mutexLocked) 成功 -> 加锁成功 ✅
```

原子操作 `atomic.CompareAndSwapInt32`，无竞争时直接获取。

### 加锁被阻塞

协程 B 尝试加锁时锁已被协程 A 持有：

1. Waiter 计数器 +1
2. 协程 B 阻塞等待 sema 信号量
3. 直到 Locked 变为 0 后被唤醒

## Unlock 流程

```go
atomic.AddInt32(&m.state, -mutexLocked)  // Locked 位置 0
```

### 无阻塞协程解锁

- Locked 位置 0 即可，不需要释放信号量

### 有阻塞协程解锁

1. Locked 位置 0
2. 看到 Waiter > 0 → 释放一个信号量，唤醒一个阻塞协程
3. 被唤醒协程把 Locked 置 1，获取锁

> ⚠️ 如果 Mutex 未加锁就 Unlock，会抛 runtime error

## 自旋 (Spinning)

### 什么是自旋

对应 CPU **PAUSE** 指令，约 30 个时钟周期的空转，不将协程转为睡眠态。

### 自旋条件（必须全部满足）

1. 自旋次数 ≤ 4
2. CPU 核数 > 1
3. P 的数量 > 1（`GOMAXPROCS` > 1）
4. 可运行队列为空

> 简单说：**不忙的时候才会启用自旋**

### 自旋的优势与问题

| 方面 | 说明 |
|:-----|:------|
| ✅ **优势** | 避免协程切换，当前协程经过短时间自旋可能直接获得锁 |
| ❌ **问题** | 自旋抢锁会导致被唤醒的阻塞协程难以获取锁 → **饥饿状态** |

## Mutex 模式

### Normal 模式（默认）

- 加锁失败不立即转入阻塞排队
- 先判断是否满足自旋条件，满足则自旋抢锁
- 适合大多数场景

### Starving 模式（Go 1.8+）

- **进入条件**：协程阻塞等待超过 **1ms**
- **行为**：不自旋！一旦释放锁，**一定唤醒一个协程并成功加锁**
- 被唤醒协程获取锁后，等待计数减 1

### Woken 状态

- 用于加锁和解锁过程中的通信
- 自旋中的协程将 Woken 置 1 → 通知解锁协程"不必释放信号量，我马上就拿到锁了"
