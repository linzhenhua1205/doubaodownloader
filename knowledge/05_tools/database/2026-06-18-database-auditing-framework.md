## 📋 全文框架

### 一、为什么数据库审计必须单独拿出来讲

数据库审计把风险识别前移到数据被真正访问的**最前沿**，而非等数据导出后才由 DLP 处理：

| 能力 | 解决什么 | 怕漏什么 |
|:-----|:---------|:---------|
| 数据分级 | 哪些数据更重要 | 没有分清重点 |
| DLP | 数据怎么流出去 | 已导出内容是否受控 |
| 数据库审计 | 数据在库里被谁动过 | 越权查询、批量导出、高危变更 |

### 二、操作分层（核心方法论）

**第一层 — 重点审计的高危操作**：

- 权限变更（GRANT/REVOKE）：钥匙被配了一把
- 数据导出（大批量 SELECT/导出到文件）：**大部分真实泄露的起点**
- 数据删除/修改（DELETE/TRUNCATE/DROP）
- 结构变更（改表/改字段/改审计配置）
- 系统级配置变更（关闭日志/改审计策略）

**第二层 — 持续观察的异常行为**：

- 非工作时间访问
- 非常规来源（陌生 IP / 跳板机以外终端）
- 越权访问（开发账号查生产敏感表）
- 访问模式突变（从几十行→几十万行）

**第三层 — 保留记录但不告警**：正常只读查询、已授权例行报表。

### 三、四类重点审计账号

DBA/超级管理员 → 应用账号（最多转发自） → 开发/测试账号（最常见越权源） → 第三方运维/外包账号（最长僵尸）

### 四、对象分级

| 层级 | 示例 | 审计重点 |
|:-----|:-----|:---------|
| 核心业务表 | 客户主表、订单、财务底账 | 所有敏感访问需留痕 |
| 关键配置表 | 权限表、策略表、审批流配置 | 变更需实时告警 |
| 普通业务表 | 中间表、缓存表 | 保留记录，低告警强度 |

### 五、最小审计字段集

用户/账号 → 来源 IP/主机 → 时间戳 → 数据库/表/对象 → 操作类型 → 执行结果 → 会话/应用标识

### 六、落地步骤

1. 打开必要审计（核心表+高危操作）
2. 集中存储与防篡改（独立日志平台）
3. 先上关键告警（3-5 条致命场景）
4. 建立处置闭环（认领→核查→处置→复盘→工单）

### 七、数据集精细化审计

- 以分类分级为基础，标记受保护数据集
- 定义逐数据集策略（如：客户表查询>1000行即告警）
- 列级敏感访问（身份证号/金额列单独审计）
- 与正常访问基线对比（全表扫/非程序账户=异常）

### 八、开源工具链（详细实操）

| 数据库 | 审计插件 | 说明 |
|:-------|:---------|:-----|
| MySQL/MariaDB | **Percona Audit Log Plugin** | 细粒度过滤，JSON/XML 输出，首选 |
| PostgreSQL | **pgAudit** | 会话级+对象级，支持绑定参数 |
| Oracle | 原生 FGA（商业） | 商业功能，直接集中采集 |
| SQL Server | 服务器审核规范 | 日志写事件日志/文件，日志采集器收集 |

**自建审计栈推荐**：ELK（Filebeat → Logstash/Elasticsearch → Kibana）+ ElastAlert 告警

**无插件替代方案**：

1. 原生查询日志解析（性能差，仅临时方案）
2. 网络层审计代理（ProxySQL / PgBouncer 记录查询）
3. 触发器辅助审计（仅 DML，兜底用）

### 九、结语核心公式
>
> 数据库审计 = 锁定高危操作 + 关键对象 + 关键账号 → 数据集级精细监控 → 开源工具链闭环

## 🤔 关键洞察

这篇最值钱的是它的**分层思维**——不是功能罗列，而是给了你一个从零开始搭建审计体系的决策顺序：

1. **先不做全量** ⇒ 先锁定高危动作和关键对象
2. **先不买商业产品** ⇒ 开源插件+ELK 足够覆盖 80% 场景
3. **先不上太多告警** ⇒ 第一轮只设 3-5 条致命规则，避免告警疲劳
4. **先跑通闭环** ⇒ 从「记下来」到「管起来」的跨越是处置工单

**"数据不是在发出去那一刻才开始泄露的，而是在库里被非法触碰的那一刻就已经开始了"** — 这是 DLP 和数据库审计的核心分工边界，对安全架构设计有指导意义。

- **`data-analysis/`**: 数据湖仓 — 数据安全治理与湖仓分级保护策略可联动
- **与 DLP/分类分级互补**：数据库审计填补的是 DLP 覆盖不到的「数据还在库里」的盲区
