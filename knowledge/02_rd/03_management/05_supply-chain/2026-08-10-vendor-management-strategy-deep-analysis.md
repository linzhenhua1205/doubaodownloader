## 1. 结论概要

| # | 场景 | 核心机制 | 一句话 |
|:-:|:-----|:---------|:-------|
| 1 | 服务体系/利益关系 | 服务地图 × 利益地图 | 供应商的行为由其**内部利益结构**决定（销售想签单、FAE 想少事、研发想免责）——看懂利益地图，就预测了行为 |
| 2 | 能力评估 | 理解能力 × 推动能力矩阵 | 两个正交能力：技术理解（会不会）与组织推动（能不能推动内部）——**推动能力比理解能力更稀缺** |
| 3 | 非常规手段 | 非正式渠道，留痕最小化 | 正式渠道拿不到的信息走非正式渠道（口头/私下/展会），**价值真实但必须划边界**：不违法、不造假、不泄我密、不伤长期关系 |
| 4 | 开发流程/release | 版本纪律 × 交付风险 | 从 release 历史看流程成熟度：版本乱、无变更说明、验证草率 = 交付风险源 |
| 5 | 上升通道 | 通道宽度 = push 上限 | 问题能否到达供应商决策层，决定了我方 push 的天花板——通道窄则必须绕道（S2.6） |
| 6 | 重要性评估 | 客户矩阵定位 | 我方在供应商客户矩阵中的位置（份额/战略/关系）决定**可动用资源的上限**——定位错则策略全错 |
| 7 | 资源投入/速度 | 历史数据验证 | 承诺履约率 + 平均解决周期是「投入」的客观度量，替代「感觉」 |
| 8-16 | 九条应对纪律 | 见 §4 | 日常攻防的操作规范：push 有术、实验有据、通信留痕、问题有格式 |

**一句话总结**：供应商管理分两半——**S1 把黑箱变灰箱**（透视组织、评估能力、定位自己），**S2 把日常变规范**（push 有术、实验有据、通信留痕、风险可控）。会管理供应商的人，不是关系硬的人，是**透视得准 + 纪律执行得严**的人。

## 2. 第一性原理：黑箱透视 × 接口纪律 × 能力判断

> **供应商是一个「部分可控的黑箱」：内部机制（利益/流程/资源）不可直接观测，但可通过接口（FAE/邮件/会议）观测信号。供应商管理的全部工作 = 透视黑箱（评估）+ 规范接口（纪律）+ 在接口上施力（push/升级）。**

三个支柱的职责划分：

| 支柱 | 回答的问题 | 对应章节 |
|:-----|:-----------|:---------|
| **黑箱透视** | 供应商内部怎么运作？能力边界在哪？我方地位如何？ | S1（七维评估） |
| **接口纪律** | 日常沟通怎么规范？怎么让信号不失真？ | S2（九条纪律） |
| **接口施力** | 供应商不配合时怎么推动？ | tactics（博弈）/ leverage（协作） |

**关键认识：供应商管理的对象不是「供应商」这个抽象实体，是「供应商内部的利益结构 + 资源调度逻辑」**。FAE 只是接口，真正决策在供应商内部——管理的本质是**通过接口影响供应商内部的资源调度**（把我的问题排到他们的高优先级）。

## 3. S1 组织架构与能力评估（七维透视）

### 3.1 S1.1 服务体系与内部利益关系

**服务地图**（供应商对外服务体系是谁、各自角色）：

```
供应商服务体系典型结构
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ 销售     │   │ FAE     │   │ 研发/产品 │   │ 质量/工厂 │
│ (KPI: 签单)│──│ (KPI: 响应)│──│ (KPI: 免责)│──│ (KPI: 良率)│
└─────────┘   └─────────┘   └─────────┘   └─────────┘
     │              │              │              │
     └──────────────┴──────┬───────┴──────────────┘
                           ▼
                   内部资源调度中心
              (谁的问题排前面，按什么排)
```

**利益地图**（每个角色的真实动机——预测行为的关键）：

| 角色 | 表面职责 | 真实 KPI | 行为预测 |
|:-----|:---------|:---------|:---------|
| 销售 | 客户关系 | 签单/份额 | 大问题会紧张（怕丢单），技术问题不关心 |
| FAE | 技术支持 | 工单响应/满意度 | 倾向「少麻烦」——能推就推（环境问题/无法复现） |
| 研发/产品 | 缺陷修复 | 版本交付/免责 | 倾向「免责」——问题归因于应用方式/环境，避免认领 |
| 质量/工厂 | 良率/交付 | 出货 | 批量性问题才触发，个案不关心 |
| 高层 | 战略 | 大客户满意度 | 只在「大客户 + 重大问题」时介入 |

**管理推论**：
1. **对 FAE 谈技术、对销售谈份额、对高层谈战略**——不同角色用不同筹码（tactics §1.1 分量等级 + 五级升级的对应关系）
2. **FAE 的「无法复现」可能是利益驱动而非事实**（免责 KPI）——这不是道德判断，是系统行为，用证据（leverage S3 SDK 复现）绕过
3. **利益的改变 = 行为的改变**：让 FAE 的 KPI 与你绑定（如把问题升级为「影响我方采购决策」→ 销售施压 FAE）

### 3.2 S1.2 能力评估：理解能力 × 推动能力

两个**正交**能力维度，构成能力矩阵：

| 维度 | 定义 | 观测点 | 低分信号 |
|:-----|:-----|:-------|:---------|
| **理解能力**（会不会） | 技术深度：能否理解问题的机制 | 首次回复是否触及机制/能否提出假设 | 复述问题/要求重复描述 |
| **推动能力**（能不能） | 组织影响力：能否调动内部资源 | 能否推动研发排期/能否给出承诺版本 | 永远「转交相关部门」 |

```
能力矩阵（FAE 个体评估）
       推动能力
       高 │  ① 全能型     ② 影响力型
          │  (理解深+推得动)  (理解浅但推得动)
       低 │  ③ 技术型     ④ 传话筒
          │  (理解深推不动)  (理解浅推不动)
          └───────────────────────
              低          高   理解能力
```

**管理策略**（按象限）：
- ① 全能型：核心依赖，重点维护（驻场/资源倾斜）
- ② 影响力型：让他拉技术资源，你补充技术深度
- ③ 技术型：技术对话找 TA，推动用升级路径（S2.6）
- ④ 传话筒：降级处理，问题直接升级或换人

**关键判断**：**推动能力比理解能力更稀缺**——理解能力可以我方补齐（我们懂技术），推动能力补不了（只有他们内部人有）。评估时优先识别「推动能力」，这是问题能否快速解决的第一变量（呼应 leverage S1 反馈质量评分，本文是「对人」的评估，leverage 是「对 action」的评估）。

### 3.3 S1.3 非常规手段：非正式渠道与边界

用户点「必要的时候，采用非常规手段，不留官方证据」——诚实分析：**它指的是通过非正式渠道获取正式渠道拿不到的信息**。

**非正式渠道的类型学**：

| 渠道 | 获取的信息 | 留痕风险 |
|:-----|:-----------|:---------|
| 口头沟通（电话/面谈） | 内部真实态度、路线图、未发布计划 | 低（但不可依赖为证据） |
| 展会/技术交流会 | 同行经验、供应商内部传闻、真实案例 | 低 |
| 熟人网络（前同事/老 FAE/行业人脉） | 供应商内部变动、真实能力、历史黑历史 | 中 |
| 私下沟通（微信/私下见面） | 模糊表态、非正式承诺 | 中 |

**价值**：正式渠道（邮件/工单）的信息经过「免责加工」（供应商会挑安全的讲），非正式渠道能拿到**未经加工的真实信息**——内部是否真的在查、问题真实优先级、供应商内部谁在卡。

**边界（必须划清，越界即反噬）**：
1. **不违法**：不窃取商业秘密、不诱导泄露他人机密
2. **不造假**：非正式信息只能作为「线索」，进入正式沟通前必须验证（拿不到证据 = 不能当证据用）
3. **不泄我密**：非正式渠道是双向的——对方也在用同样的手段了解你，注意反情报（不透露我方成本/客户/多供应商策略，呼应 leverage §9.1 保密分层）
4. **不伤长期关系**：非常规手段是「偶尔的解药」不是「日常主食」——被供应商察觉「你绕过正规流程搞小动作」会破坏信任基础（leverage §9.5 关系纪律）
5. **留痕策略的辩证**：「不留官方证据」保护了我方（不授人以柄），但也意味着这些信息**不能用于正式谈判**——非正式信息必须「转正」才有博弈价值（如通过销售渠道施压时，把非正式信息包装成「我方市场情报」）

### 3.4 S1.4 开发能力/流程/release 质量

**从 release 历史看流程成熟度**（客观、可查）：

| 观测项 | 成熟流程 | 风险流程 |
|:-------|:---------|:---------|
| 版本管理 | 语义化版本 + 变更说明（changelog） | 版本号随意 + 无变更记录 |
| 验证体系 | 发布前有明确验证矩阵（功能/性能/压力） | 「内部验证过」无证据 |
| 修复质量 | 修复带回归测试 + 影响范围说明 | 修复引入新问题（复发） |
| 交付节奏 | 承诺版本日期与兑现一致 | 频繁跳票（承诺表数据） |
| 发布公告 | 主动推送 release notes | 问题修复静默（不告知） |

**交付风险评估**（供应商 release 的「水」）：
- **新版本风险**：新 release 引入新 bug 的概率与版本间隔、变更量正相关——升级前评估「值得吗」（小修不必追新）
- **静默变更风险**：供应商悄悄改行为/参数（无公告）——我方基线测试（版本矩阵，errata §10.3）才能发现
- **验证成本风险**：每次升级我方要重跑验证——升级频率 × 验证成本 = 隐性成本，纳入「值不值得升级」决策

**管理动作**：建立供应商 release 台账（版本/日期/变更/我方验证状态），与 errata 版本矩阵联动——「供应商发版 ≠ 我方升级」，升级是决策不是跟随。

### 3.5 S1.5 问题上升通道

**通道宽度 = push 上限**：问题从 FAE 到供应商决策层（研发总监/VP）的路径越宽，我方 push 的天花板越高。

| 通道评估 | 观测方法 | 管理含义 |
|:---------|:---------|:---------|
| 通道层级 | 问题最高能到哪一级（FAE→经理→总监→VP） | 决定五级升级（tactics §3）能走多远 |
| 通道速度 | 从 FAE 到高层需要多久 | 决定紧急问题的响应上限 |
| 通道是否畅通 | 高层是否真的参与（还是走过场） | 决定「上升高层」是否有效 |
| 我方是否有直达通道 | 是否认识供应商高层/有定期高层会 | 决定性资源（QBR 是官方通道） |

**管理动作**：
- 建立供应商**关键人物地图**（谁管什么、谁能拍板、与我方谁对接）——不止 FAE，还有研发负责人、质量负责人、销售总监
- 每年至少一次**高层互访**（我方总监级 vs 供应商对应级）——为紧急问题预留直达通道（平时不用，用时必须有）
- 通道不畅的供应商（只有 FAE 一层）→ 问题多时主动走 QBR/合同渠道建立上层联系（S2.6 联动 PM/市场）

### 3.6 S1.6 重要性评估：客户矩阵定位

**我方在供应商客户矩阵中的位置 = 可动用资源的上限**。tactics §1.1 有年采购额分级（A-D 级），本文补充「非采购额维度」：

| 维度 | 高重要性信号 | 低重要性信号 |
|:-----|:-------------|:-------------|
| 采购额 | 大份额 / 快速增长 | 小额 / 萎缩 |
| 战略价值 | 联合开发 / 路线图对齐 / 首批客户 | 纯购买关系 |
| 技术影响力 | 我方是标杆案例 / 提供改进反馈 | 需求方 |
| 关系深度 | 高层互访 / 多级联系人 / 共同项目 | 单点 FAE 对接 |
| 市场影响力 | 我方品牌/渠道帮助其扩展 | 无 |

**管理推论**：
1. **定位决定策略**：重要客户 → 直接要求资源（A 级待遇）；非重要客户 → 借力（通过代理商/ODM/OEM 渠道，tactics §1.1 的 C/D 级策略）
2. **地位是动态的，可以经营**：提升重要性 = 提升采购额 OR 提升战略价值（联合开发/参与测试计划/成为 reference design）——「被重视」是可以主动经营的
3. **重要性评估要定期重估**（季度）：供应商并购/产品线调整会瞬间改变我方地位

### 3.7 S1.7 资源投入与解决速度（历史验证）

S1.1-S1.6 是结构评估，本项是**行为验证**——用历史数据检验前面的判断（承诺表 + 台账数据，leverage S1 的月度聚合）：

| 指标 | 定义 | 健康值（参考） | 数据源 |
|:-----|:-----|:--------------|:-------|
| 承诺履约率 | 承诺修复版本/日期兑现比例 | >80% | 承诺表（总纲 P2） |
| 平均首次响应 | 问题提交到首次实质响应 | <24h（紧急）/ <3 天 | 问题台账 |
| 平均解决周期 | 提交到验证关闭 | 按严重度分级（RCA 文档 §1） | 台账 |
| 反馈质量评分 | leverage S1 六维评分 | 均值 >3.5/5 | 评分记录 |
| 重复问题率 | 已修复问题复发比例 | 低（趋势下降） | 台账 + errata |

**关键**：这些数据不只是「绩效报表」，是**S1 各维度的验证器**——利益地图预测「FAE 会推责」（S1.1）→ 数据验证「推责率 60%」；重要性定位「我方是 A 级客户」（S1.6）→ 数据验证「承诺履约率是否真的 90%」。**预测与验证不一致 = 透视错了，回去重看**。

## 4. S2 供应商应对策略（九条实战纪律）

### 4.1 S2.1 FAE 管理：背景 + 主动 push

**FAE 背景摸底**（首次接触即完成）：
- 技术背景（做过什么、擅长什么）→ 判断能对话的技术深度（S1.2）
- 在公司的资历/权限 → 判断推动能力（S1.2）与通道（S1.5）
- 对接风格 → 定制沟通方式（重技术 or 重流程）

**主动 push 三原则**：

| 原则 | 操作 |
|:-----|:-----|
| **描述清楚问题** | 用八要素模板（S2.8）——模糊描述 = 给 FAE 拖延借口 |
| **罗列复现方法** | 最小触发集（总纲 P7）+ SDK 复现步骤（leverage S3）——「复现方法」是 push 的硬通货 |
| **告知复杂度与重要性** | 明示「这个问题我方 P1、影响 N 客户、计划 M 周后出货」——让 FAE 有内部上报的理由（信息要真实，虚报会透支信用） |

**问题多时的 track 纪律**：
- 一个问题一个编号，批量跟踪（承诺表，总纲 P2）——**问题多时不 track，等于把优先级决定权交给 FAE**（他们挑好解决的做）
- 每周一次批量状态刷新，而不是逐个电话催（电话 = 无留痕，见 S2.7）
- 问题一次性说清楚（含背景/已做实验/期望）——**分多次挤牙膏式提供信息 = 每次重启 FAE 的认知，等于主动拉长周期**

### 4.2 S2.2 跑火车应对：目的合理性 + 实验归档

**「跑火车」识别**：FAE 要求我方做大量实验但无明确目的（「你们再测测这个」「试试那样」）——本质是 FAE 没想清楚，把探索成本转嫁给我方。

**应对机制**：
1. **要求实验目的**：每个实验要求 FAE 先说「假设是什么、验证什么、预期结果、下一步决策」——说不清目的 = 不做
2. **实验价值排序**：多个实验时要求 FAE 排序（「哪个实验最可能定位根因？为什么？」）——让 TA 暴露优先级思维
3. **实验归档**：所有实验记录入台账（目的/条件/结果/结论）——**实验归档的三大价值**：防止重复实验、积累证据链（tactics §4）、为 DOE 提供素材（总纲 P7）
4. **拒绝无目的实验的底线话术**：「这个实验的目的是验证什么假设？如果假设不成立，我们的下一步是什么？——有明确决策价值我们立刻做」

**关键判断**：「跑火车」不全是恶意——有时 FAE 确实在摸索。区分标准是**是否有结构化思维**（假设驱动 vs 乱枪打鸟）：假设驱动的实验即使多也配合（推进认知），乱枪打鸟的实验必须拦（消耗资源）。

### 4.3 S2.3 私下实验：偶可，公开追认

**场景**：FAE 私下让我方做个实验（不经正式流程）——可能因为：流程慢、不想留痕、试探性验证。

**管理规则**：
- **偶尔可以**：非正式实验能加速探索（尤其双方互信时），且 FAE 私下请求通常意味着「TA 认为有价值但不想走流程」
- **必须公开追认**：实验有价值 → 用邮件把实验背景/结果补发正式记录（「关于 X 实验，我们已完成，结果如下……」）——**把非正式变成正式，让结果可追溯、可复用**
- **无价值的私下实验**：不做（同 S2.2 目的原则），礼貌说明「走正式流程吧，方便两边归档」

**为什么必须追认**：私下实验没有记录 = 结果不可复用 = 下次重新做；且如果实验结果是「我方有问题」，没有正式记录 = 无法要求供应商兑现相关承诺。**追认是给实验结果「上户口」**。

### 4.4 S2.4 通信纪律：即时通信 vs 邮件

| 渠道 | 适用 | 禁止 |
|:-----|:-----|:-----|
| 微信/即时通信 | 进度询问、约时间、非结论性讨论 | **结论、承诺、技术决策、问题定级** |
| 邮件 | 问题正式描述、实验请求、结论确认、承诺、升级 | 无（正式渠道） |
| 电话 | 紧急沟通、复杂讨论（先电话后邮件） | 单独作为承诺依据 |

**核心纪律**：
1. **微信不是正式渠道**——供应商在微信上说的任何结论/承诺，默认不可依赖（S2.7 电话同理）
2. **重要结论邮件化**：任何影响决策的信息（根因判断、修复承诺、时间节点、责任归属）必须邮件确认——「微信说了不算，邮件为准」
3. **即时通信的「追认」机制**：微信讨论出结论 → 发邮件总结确认（「按我们刚才的沟通，确认以下结论……」）——**在即时通信时代，主动写总结邮件的人是掌控节奏的人**
4. **我方自身纪律**：我方工程师不在微信上做任何结论性表态（对方可能截图/断章取义）——**自己不留把柄，才能要求别人留痕**

### 4.5 S2.5 供应商管控：成熟产品/风险评估/改动点确认

**供应商管控的三种场景**：

| 场景 | 管控要点 |
|:-----|:---------|
| **成熟产品** | 防「静默变更」——基线验证（版本矩阵）+ 定期 re-qualification；供应商改流程/产地/批次必须主动申报（写进合同/SQA 协议） |
| **问题风险评估** | 问题出现时快速评估三件事：影响面（哪些产品线/批次）/ 触发概率（P7）/ 修复代价——输出风险等级（errata §6 L1-L4） |
| **风险点与改动点确认** | 供应商的任何修复/改版：**先确认改动点清单**（改了哪几处、影响哪些路径）→ 评估风险 → 再决定验证范围——「改动点不确认，验证就是盲测」 |

**「改动点确认」的操作化**（防供应商「修复了 A 却悄悄改了 B」）：
```
供应商修复方案 → 要求提供:
① 改动点清单（文件/模块/参数级）
② 影响范围说明（哪些功能/配置受影响）
③ 变更原因（为什么这么改，而不是别的改法）
→ 我方据此设计验证范围（只测修复点 ≠ 只测改动点，要测改动点影响的所有路径）
```

**核心心法**：供应商管控的主动权在**验证设计**——不是我方被动接受供应商的「修复好了」，而是我方基于改动点设计针对性验证（errata §7 验证五步的输入）。

### 4.6 S2.6 无法推动：标识 + 联动 + 上升

**无法推动的识别**（客观信号，不是感觉）：
- 承诺表连续 2 次跳票 / 无承诺 / 反馈质量评分持续 C（leverage S1）
- 上升通道堵塞（S1.5 评估：FAE 无权限、上层无响应）

**三联动处理**：

| 动作 | 内容 | 角色 |
|:-----|:-----|:-----|
| **标识** | 问题打「卡死」标签（阻塞原因 + 卡在谁）——**显性化是推动第一步**（不可见的问题供应商可以永远拖） | 技术负责人 |
| **联动 PM/市场** | 借商务杠杆：PM 通过采购/合同渠道施压（扣款/份额/交期），市场通过销售渠道施压（「这影响我们下一代选型」）——**技术推不动的问题，用商务推** | PM + 采购 + 市场 |
| **上升高层** | 走高层通道（S1.5 预留的直达通道 / QBR / 联合管理层会议）——「问题上升高层」不是告状，是**把问题的决策权从执行层转移到决策层**（执行层没权限的事，决策层一句话就解决） | 我方总监级 |

**关键认知**：「无法推动」的本质是**接口层权限不足**（FAE/经理无权调动研发资源），不是供应商不合作——所以解法不是更用力地催接口层，而是**换一个更高权限的接口**（高层/商务/渠道）。催接口层 = 撞墙，换接口 = 绕墙。

### 4.7 S2.7 电话承诺无效：邮件确认

**原理**：电话/口头承诺有三重失效——无记录（无法追溯）、无约束（对方可以否认）、无细节（口头说不清版本/日期/边界）。

**纪律**：
1. **电话只用于沟通，不用于定案**——电话讨论出的结论，必须由我方（或要求对方）发邮件确认
2. **确认邮件模板**（最小有效格式）：「按今天电话沟通，确认：①根因判断/结论：___ ②承诺事项：___（版本/日期）③遗留问题：___——如无异议请回复确认」
3. **对方不回复确认邮件怎么办**：默认不生效（「未确认 = 未承诺」）——这正好是信号：不回复确认 = 不想留痕 = 承诺不可靠（S1.2 推动能力/诚信的信号）
4. **电话后 24h 内完成邮件确认**——拖久了细节失真，且对方有「我当时没这么说」的空间

### 4.8 S2.8 问题描述八要素

用户点名的规范，结构化：

| # | 要素 | 内容 | 缺失的后果 |
|:-:|:-----|:-----|:-----------|
| 1 | **项目背景** | 什么产品/项目/阶段 | 供应商无法判断相关性 |
| 2 | **拓扑** | 系统拓扑/部件连接/数据流 | 无法定位问题域 |
| 3 | **问题详细描述** | 现象/频率/影响/首次出现时间 | 无法评估严重度 |
| 4 | **逻辑清晰** | 症状→怀疑→已排除项 的推理链 | 供应商从零开始（浪费时间） |
| 5 | **复现方法** | 最小触发集 + 步骤（总纲 P7） | 供应商无法验证 |
| 6 | **日志收集** | 日志/转储/遥测 + 时间线（总纲 P8） | 无证据，靠描述 |
| 7 | **是否可在原生 SDK 上复现** | SDK 复现结果（leverage S3） | 供应商可推「环境问题」 |
| 8 | **期望** | 我方希望供应商做什么（分析/复现/修复承诺） | 供应商不知道下一步 |

**问题描述模板即第一道防线**：八要素齐全的问题描述，供应商几乎没有拖延空间（S2.1 push 的硬通货）；八要素缺失的问题描述，等于主动给供应商递「无法复现」的武器。**问题描述质量 = 我方技术能力的对外名片**（leverage §9.2 分析能力纪律的落地形式）。

### 4.9 S2.9 求助太多 = 能力不行（自省诊断）

**用户洞察**：「求助太多，本质上也是能力不行的一种表现」——这是对**我方团队**的诊断，不是供应商诊断。

**「求助太多」的信号分级**：

| 求助类型 | 判定 | 处理 |
|:---------|:-----|:-----|
| **新领域求助**（第一二次接触某技术） | 正常 | 沉淀学习（知识库） |
| **同类问题重复求助**（同一技术反复问供应商） | ⚠️ 能力缺口信号 | 内部技能建设（专项学习/文档沉淀） |
| **基础问题求助**（手册里有的/查得到答案的） | 🔴 能力不足信号 | 培训 + 知识库（先查再问） |
| **依赖型求助**（离开供应商无法工作） | 🔴 认知寄生（MEMORY: AI 依赖萎缩同构） | 独立能力建设 + 逐步去依赖 |

**诊断机制**：问题台账加「求助来源」标签（新领域/同类重复/基础/依赖）→ 月度统计 → 重复与基础求助占比高 = 团队能力缺口 → 触发内部建设。

**第一性原理**：求助的本质是**信息获取**——「求助太多」不是「问得多」的问题，是**内部知识没有沉淀为可复用资产**的问题。每次求助都应该转化为一次内部能力建设（FAQ/文档/实验模板），否则同样的求助会反复发生（与总纲 P3 关闭双门槛同构：问题解决必须沉淀）。

**边界**（避免矫枉过正）：不求助 ≠ 能力强——真正的高效是「该问就问（新领域）+ 不该问的不问（可查的）+ 问了就沉淀（转化为内部能力）」三态平衡。**问得聪明比问得少重要**。

## 5. 管理闭环：评估→策略→执行→复盘

```
季度循环：
S1 七维评估（画像卡更新）
  → 定位变化?（客户矩阵/流程成熟度/能力矩阵）

  → 问题复盘 + 策略复盘 + 画像卡修订
```

## 7. 批判注记

1. **七维评估的主观性**：利益地图/能力矩阵依赖接触样本（接触少则评估误差大）——画像卡需标注「评估置信度」，低置信度维度不用于关键决策。
2. **非常规手段的边界是「写下来容易，执行中难」**：非正式渠道获取的信息天然不可验证——建议设「非正式信息准入规则」（什么级别问题才动用、获取后必须转正验证），防止非正式渠道成为习惯性依赖。
3. **九条纪律的全面执行成本**：邮件追认/实验归档/问题八要素都是「额外动作」——落地靠模板与工具（台账字段预设），不靠自觉；建议先固化模板（问题描述八要素模板/确认邮件模板/实验记录模板），再要求执行。
4. **「求助太多=能力不行」的误判风险**：供应商 FAE 本身的水平差异大（S1.2 传话筒型），「求助多」也可能是「供应商接口太弱导致效率低」——诊断要先区分「我方能力缺口」与「供应商接口劣质」。
5. **管理密度 vs 关系温度**：九条纪律全是「留痕/确认/归档」，过度执行会让关系僵化（供应商觉得被当贼防）——**纪律用于重要事项，日常仍保持人情温度**（这是杠杆 §9.5 关系纪律的平衡点）。
6. **画像卡的时效性**：供应商并购/重组/FAE 换人会瞬间失效画像卡——重大事件即时更新，不能等季度。
