## 1. 结论概要

| # | 场景 | 核心机制 | 一句话 |
|:-:|:-----|:---------|:-------|
| 1 | action 反馈质量 | 六维评分卡 + 投入分级 | 供应商的资源投入不可见，但 **action 反馈质量是它的观测信号**——质量差 = 投入不足 = 触发升级 |
| 2 | 技术人员参与/进驻 | 协作升级阶梯 + 双向进驻机制 | 沟通升级到「技术人员面对面」是有序阶梯的最后一级，进驻前必须备好「问题包」 |
| 3 | SDK 复现 | 技术证据战 | 用供应商自己的 SDK 复现问题 = 把「我们的环境有问题」之争变成「你们的工具能复现」的事实——**承诺问题而非扯皮** |
| 4 | 日报/分析报告 | 流水与洞察分层 | 日报是流水（状态同步），分析报告是洞察（决策输入）——两者不可互相替代 |
| 5 | 环境问题 | 环境对照表 | 环境差异不是「无法复现」的借口，是**可枚举的变量清单**——列出来逐项对照 |
| 6 | 概率性问题 | 概率→确定性交接物 | 供应商无法承诺「概率」，但可以承诺「条件」——交接物是确定性触发条件，不是概率描述 |
| 7-10 | 沟通纪律 | 保密分层/技术对等/上报映射/接口人 | 一人对一供应商是默认纪律，复杂问题可分线但必须「一问题一接口」 |

**一句话总结**：供应商资源利用的本质不是「要资源」，而是**建立一套信号系统**——通过反馈质量观测投入、通过投入决定协作深度、通过协作深度决定攻关速度。会利用供应商资源的团队，不是关系好的团队，是**信号解读准的团队**。

## 2. 第一性原理：外部管道的调度与信号解读

### 2.1 供应商 = 外部攻关管道

问题管理总纲 P9 提出双管道模型（内部可见/外部不可见）。本文深化外部管道：供应商的资源投入是**我方不可直接控制、但可观测、可引导**的外部变量。

```
控制力光谱（从弱到强）：
┌─────────┬──────────┬──────────┬──────────┬──────────┐
│ 无法影响 │ 信号观测  │ 合同约束  │ 关系引导  │ 深度协作  │
│ (黑箱)  │ (反馈质量) │ (SLA/承诺)│ (升级/施压)│ (进驻/SDK)│
└─────────┴──────────┴──────────┴──────────┴──────────┘
  本文核心 ←──────────────────────────────────────────────→
```

### 2.2 投入信号链

> **供应商资源投入不可见 → 但 action 反馈质量可观测 → 反馈质量是投入的函数 → 投入是优先级与诚意的函数 → 通过反馈质量反推投入，通过投入决定下一步动作**

这是本文的**总逻辑**：S1（观测）→ S2-S6（按观测结果选择协作模式）→ §9（沟通纪律保证观测信号不失真）。

### 2.3 三个关键认识

1. **供应商不是「不愿投入」，是「在排优先级」**——他们的资源也有限，谁的问题被顶上取决于信号强度（tactics §1.1 客户分级 + 总纲 P2 承诺表）。我们的任务是**让信号变强**（反馈质量评分、升级、进驻）。
2. **协作深度是分级的**——不是所有问题都值得进驻/SDK。先评估问题价值（严重度×影响面×概率，总纲 P9），再选协作模式，避免资源错配。
3. **信号会失真**——供应商可能「反馈快但没干货」（形式投入）或「沉默但已投入」（实质投入）。评分必须看**技术内容质量**，不是看响应速度。

## 3. S1 action 反馈质量评估：投入的信号观测

### 3.1 六维评分卡

对每个供应商 action（对问题的响应/承诺/交付）按六维评分：

| 维度 | 观测点 | 满分信号 | 低分信号 |
|:-----|:-------|:---------|:---------|
| **D1 响应时效** | 首次实质响应时间 | 24h 内有技术分析，非模板回复 | 3 天无响应 / 客服话术 |
| **D2 技术深度** | 分析是否触及根因 | 给出假设 + 验证计划 + 数据需求 | 复述问题描述 / 推责 |
| **D3 可执行性** | action 是否可落地 | 明确步骤/版本/时间 | 空泛承诺（「我们会跟进」） |
| **D4 承诺明确度** | 版本号/日期是否明确 | 承诺修复版本 + 日期 | 「尽快」「下个版本」（无号） |
| **D5 主动闭环** | 是否主动回传进展 | 主动更新 + 验证结果 | 我方不问不更新 |
| **D6 知识贡献** | 是否提供增量信息 | 提供根因机制/规避知识 | 只确认「已知」 |

### 3.2 投入分级与应对

| 分级 | 评分特征 | 判定 | 应对动作 |
|:----:|:---------|:-----|:---------|
| **A 全力投入** | 六维高分，主动闭环 | 供应商已排高优先级 | 保持节奏，配合提供数据，防止我方成为瓶颈 |
| **B 常规投入** | 时效/承诺达标，深度一般 | 正常排队中 | 用承诺表（总纲 P2）跟踪，到日期未兑现升级 |
| **C 投入不足** | 时效差 / 模板回复 / 推责 | 未获重视 | 触发升级阶梯（§4）——先技术人员参与，再进驻 |

### 3.3 投入不足的识别信号（组合判断）

单条信号可能是噪声，**三条以上同时出现**才判定投入不足：

1. 响应时间持续 > 48h
2. 连续 2 次 action 无技术增量（复述已知信息）
3. 承诺版本/日期 2 次以上跳票（承诺表数据支撑）
4. 同一问题换了 3 个以上接口人（内部转手）
5. 请求提供 SDK/工具/日志分析被拖延

**关键纪律**：评分要有记录（供应商问题台账补一个「反馈质量」字段），用数据说话，不能凭印象——「感觉他们不重视」到「评分连续两轮 < 2 分」的差别，决定了升级时的底气。

## 4. S2 技术人员参与与进驻办公

### 4.1 协作升级阶梯

面对面是阶梯的**最后一级**，跳级会让资源错配（小事进驻 = 浪费双方资源，也降低我方信用）：

```
L0 邮件/工单        → 常规问题，台账跟踪
L1 电话/线上会      → 需要澄清，技术对话
L2 视频技术会       → 需要看数据/演示，FAE + 我方工程师
L3 我方赴供应商     → 需要供应商设备/环境/专家团队（最常见）
L4 供应商赴我方     → 需要我方环境/配置/数据，或问题在我方现场
```

**升级触发条件**（满足任一即考虑 L3/L4）：
- 评分 C（§3.2）且问题严重度 P1+
- 承诺表跳票 2 次且无合理解释
- SDK/工具已提供但仍无法推进（需要面对面操作指导）
- 概率性问题需要联合 DOE（§8）

### 4.2 进驻办公机制设计（L3/L4 通用）

进驻不是「去个人」，是**一次有准备的联合攻关战役**：

| 阶段 | 内容 |
|:-----|:-----|
| **进驻前（准备）** | 问题包：问题清单（按严重度排序）+ 现场数据包（日志/转储/遥测）+ 环境配置 + 已做实验清单（证明「不是没试过」）+ 期望产出（最小触发集/修复验证/根因假设） |
| **进驻中（模式）** | 面对面迭代：问题拆分 → 逐问题定「当场目标」→ 白天联合实验 → 晚上总结 action + 明日计划；**每天一个明确产出**（不能「今天在交流」） |
| **进驻后（闭环）** | 离场报告（总纲 P3 关闭双门槛的 K 部分）：根因/条件/修复承诺/遗留问题 → 进台账与专题 |

**关键设计**：
- **进驻期间每天一个产出**——防止「出差式交流」（去了但没结果）
- **期望产出先行**——进驻前双方书面确认「这次要解决什么、验收标准是什么」
- **双向进驻**——供应商问题在我方环境（L4）时，我方主导环境准备，供应商来验证；我方问题在供应商环境（L3）时，供应商提供环境与专家，我方带数据
- **驻场人员选择**：我方派「懂数据 + 能做实验」的工程师，不是「传话」的协调员

### 4.3 面对面快速解决的边界

面对面有效的前提是**信息交换密度**（看对方实验、当场迭代假设），但有两个失效条件：
1. **问题本身不需要面对面**（只是供应商流程慢）——先解决流程（升级/承诺表），进驻是浪费
2. **我方数据不足**（带去的都是「现象」没有「证据」）——进驻变成「现场找数据」，效率低；先按总纲 P8 证据保全补齐数据再去

## 5. S3 快速定位：SDK 复现与承诺问题

### 5.1 SDK 复现的三种用法

| 用法 | 场景 | 价值 |
|:-----|:-----|:-----|
| **U1 验证问题归属** | 我方怀疑部件问题，供应商推责 | 用供应商 SDK 在我方数据上复现——「你们的工具跑你们芯片出的错」 |
| **U2 剥离环境变量** | 多变量耦合，无法定位 | SDK 提供受控环境，逐个变量验证（总纲 P7 条件搜索的加速器） |
| **U3 获取供应商承诺** | 供应商要求「无法复现」 | 用 SDK 产出确定性触发条件 → 供应商无法再「无法复现」→ 必须承诺 |

### 5.2 从「描述现象」到「承诺问题」

> **核心心法：给供应商的从来不该是「问题描述」，而是「可复现的问题包」。描述引发扯皮，复现引发承诺。**

```
问题描述（扯皮触发）
  「我们的板子在某种负载下会掉盘，你们看看」← 供应商：无法复现/环境问题/正常范围
        ↓ 加工
问题包（承诺触发）
  ① 触发条件（最小集）：负载 X + 温度 Y + 固件 Z → 30 分钟内必现
  ② SDK 复现步骤：用你们的 SDK 执行这三步，日志见附件
  ③ 证据包：日志/转储/遥测时间线
        ↓
  供应商无法否认 → 必须承诺（修复版本/日期/根因分析）
```

**「承诺问题而非扯皮」的操作定义**：每轮沟通结束时，供应商必须给出**可验证的下一步承诺**（版本/日期/实验/数据交付），否则这轮沟通是失败的——用承诺表（总纲 P2）记录并跟踪。

### 5.3 与总纲 P7 的衔接

SDK 复现是 P7 条件搜索的**供应商侧加速器**：
- P7 最小触发集（我方 DOE 产出）→ 用 SDK 验证 → 供应商环境确定性复现
- 供应商提供 SDK 的质量，本身就是反馈质量评分（§3 D6 知识贡献）的观测点

## 6. S4 日报与核心信息分析报告

### 6.1 日报的强制结构（流水层）

供应商攻关期间（尤其进驻期间），日报是**双方同步的契约**：

```
攻关日报模板（供应商 + 我方每日各一份）
├─ 问题状态：open 问题清单 + 各自状态（今日变化标红）
├─ 当日进展：做了什么实验 / 分析了什么数据 / 验证了什么
├─ 阻塞点：卡在哪（数据/工具/权限/决策）——阻塞点必须点名责任人
├─ 明日计划：具体动作 + 预期产出
└─ 风险提示：承诺可能跳票 / 窗口即将关闭
```

**日报的三个作用**：
1. **进度可视化**——双方管理层都能看到进展，防止「黑洞」
2. **承诺留痕**——「明日计划」就是明天的验收标准，次日日报对照
3. **信号源**——日报的技术深度就是 S1 反馈质量的输入（连续空洞日报 = 投入不足信号）

### 6.2 流水 vs 洞察：信息分层

| 层 | 载体 | 频率 | 消费者 | 内容 |
|:---|:-----|:-----|:-------|:-----|
| **原始数据** | 台账/日志 | 实时 | 工程师 | 事件、数据、实验记录 |
| **流水** | 日报 | 日 | 双方团队 | 状态、进展、阻塞 |
| **洞察** | 分析报告 | 周/事件 | 决策层 | 根因、趋势、承诺履约、风险 |

**关键**：日报是流水，分析报告是洞察——**决策者不该看日报做决策**（信息太碎），应由技术负责人每周聚合为「核心信息分析报告」：根因假设收敛情况、承诺履约率、投入分级变化（S1）、风险升级建议。分析报告是升级（§9.3）和资源调度（S2）的输入。

### 6.3 报告节奏与升级触发

- 常规攻关：日报 + 周分析报告
- 进驻期间：日报 + 每日 5 分钟站会（面对面时代替部分日报）
- 红灯条件（任一触发升级）：连续 3 日无实质进展 / 承诺跳票 / 投入分级降至 C

## 7. S5 环境问题管理

### 7.1 环境差异类型学

「环境问题」是供应商推责的第一高频话术（tactics 套路 1）。破法不是争辩，是**把「环境」从模糊概念变成可枚举清单**：

| 环境维度 | 变量 | 对照方法 |
|:---------|:-----|:---------|
| 硬件 | 板卡版本 / 器件批次 / 走线 / 电源 | 环境对照表逐项比对 |
| 固件 | BIOS / BMC / 部件固件版本 | 版本矩阵（errata §10.3） |
| 配置 | 寄存器设置 / BIOS 选项 / 拓扑 | 配置导出比对（diff） |
| 负载 | 流量模型 / 队列深度 / 混合比 | 负载画像（现场遥测） |
| 物理 | 温度 / 电压纹波 / 震动 / 海拔 | 环境记录（总纲 P8 证据保全） |
| 网络 | 拓扑 / 线缆 / 交换机 / 背压 | 拓扑图 + 链路统计 |

### 7.2 环境对照表（Environment Baseline Matrix）

> **给供应商的每个「环境问题」说辞，用环境对照表回应：把「我们的环境和你们的不一样」变成「这 6 个维度、38 个变量，哪几个不一样、影响了什么」。**

```
环境对照表（我方 vs 供应商）
+--------+----------+----------+----------+------------------+
| 维度   | 我方环境 | 供应商EVB| 差异     | 差异影响评估      |
+--------+----------+----------+----------+------------------+
| 固件   | BIOS 1.2 | EVB 2.0  | 版本差   | 需确认是否触发点  |
| 配置   | 8CH 拓扑 | 4CH      | 通道数   | 带宽相关场景差异  |
| 负载   | 混合 7:3 | 纯顺序   | 负载模型 | 可能影响（待验）  |
+--------+----------+----------+----------+------------------+
```

### 7.3 三种可能的判定

环境差异对照后，结论只有三种，逐项排除：

| 结论 | 判定方法 | 处理 |
|:-----|:---------|:-----|
| **真环境差异** | 差异变量 → 影响评估 → 用差异变量复现成功 | 双方统一环境后再复现（或按差异归因） |
| **我方环境误判** | 差异变量与问题无因果 | 回到问题本身（可能是配置/设计问题，不是供应商问题）——**环境对照能避免冤枉供应商** |
| **供应商环境盲区** | 差异在供应商测试覆盖之外 | 我方带数据进驻（L3），要求补测——**这是「环境问题」的第三种可能：不是推责，是盲区** |

**关键**：环境问题管理的目标不是「证明我们没错」，而是**把环境差异变成可验证的变量**——这既保护我方（不被「环境问题」搪塞），也保护供应商（不被冤枉）。

## 8. S6 概率性问题的供应商协作

### 8.1 供应商对概率性问题的天然抗拒

概率性问题（总纲 P7）对供应商是**负资产**：无法复现 = 无法验证修复 = 无法承诺 = 可能背负长期责任。所以供应商的第一反应是拖延/否认。破法不是施压，是**降低他们的承诺风险**。

### 8.2 概率→确定性的交接物

> **供应商无法承诺「概率」，但可以承诺「条件」。交接物 = 确定性触发条件 + 验证方案，不是概率描述。**

```
我方输出（概率→确定性加工）：
① 现场证据包（日志/转储/遥测，总纲 P8）
② 触发条件假设（P7 分层：环境/负载/时序/配置）
③ DOE 实验结果（P7 粗筛细扫，至少收敛到 1-3 个显著变量）
④ 最小触发集（如果能做到：条件 + 步骤 → 高概率复现）
⑤ 给供应商的验证方案：用你们的 SDK/EVB 执行这组条件
```

**为什么必须我方先做 DOE**：供应商没有我们的现场数据（P8 证据保全），让供应商从零找条件 = 他们面对和 P7 一样的搜索空间，必然抗拒。**我方把搜索空间收敛到最小，供应商只需验证——抗拒消失。**

### 8.3 联合攻关模式（概率问题的进驻场景）

概率问题的进驻（L3/L4）是**性价比最高**的进驻场景：
- 面对面 + 双方环境 = DOE 加速（白天调参、当场看结果、当场改假设）
- 供应商专家在场 = 物理/芯片层假设即时验证（他们懂我们不懂的）
- 产出：最小触发集（我方带走）+ 修复承诺（供应商带走）

**边界**：进驻 3-5 天仍无收敛 → 降级为「监视清单」（总纲 P8），等现场样本积累——概率问题的攻关有统计下限（§10.4 样本量），不是面对面就能加速的。

## 9. 对外沟通技巧与关注点（五纪律）

### 9.1 保密纪律（保密要求）

| 层 | 内容 | 管理 |
|:---|:-----|:-----|
| **L1 可分享** | 问题现象、触发条件、测试数据 | 常规共享，支撑攻关 |
| **L2 受限** | 系统架构、配置细节、客户信息 | NDA 范围，按需共享，最小化原则 |
| **L3 绝密** | 我方产品规划、成本、多供应商策略、客户关系 | 绝不共享，进驻时明确边界 |

**操作纪律**：
- **进驻前签 NDA + 明确信息边界**（哪些可谈哪些不可谈，双方书面确认）
- **多供应商隔离**：A 供应商问题讨论中不透露 B 供应商信息（对比数据可匿名化：tactics「A 通过 B fail」需脱敏为「同类器件」）
- **客户信息保护**：客户名/项目名在供应商沟通中脱敏（客户 A → 「某客户」），除非合同允许
- **数据出境**：现场数据包给供应商前过一遍「最小必要」审查（只给问题相关，不给全量遥测）

### 9.2 分析能力纪律（技术对等）

- **对话的技术深度决定资源层级**：供应商对「技术对等」的对手给高投入，对「只会催进度」的客户给最低优先级——**我方工程师的分析深度（DOE 做没做、数据看不看得懂）本身就是信号**（S1 D2 技术深度的镜像）
- 我方所有沟通**用数据说话**：不带数据的抱怨 = 噪音；带数据的质疑 = 谈判筹码
- **听不懂就要求解释**：供应商术语/机制不理解时当场追问（装懂 = 信号失真）

### 9.3 问题上报纪律（内部上报 × 外部升级）

| 触发 | 内部上报 | 外部升级（tactics 五级） |
|:-----|:---------|:-------------------------|
| 常规阻塞 | 技术负责人 | L0-L1（窗口/FAE） |
| 承诺跳票 | 项目经理 | L2（经理） |
| 投入分级 C + P1 问题 | 研发总监 | L3（总监） |
| 客户受影响 / 无法解决 | 高层 | L4（VP/全球） |

**纪律**：内部上报与外部升级**同步进行**（先内部确认口径，再对外升级）——避免「对外升级了内部还没对齐」的口径混乱。

### 9.4 接口人纪律（多人跟踪 vs 避免多人跟踪）

> **核心原则：一个供应商、一个接口人；一个问题、一个 owner。复杂问题可多人参与，但对外只能有一个声音。**

| 规则 | 说明 |
|:-----|:-----|
| **单一接口人** | 我方与供应商的所有正式沟通经一个接口人（技术负责人），避免多方对接信息不一致 |
| **多人参与 ≠ 多人对接** | 复杂问题可多人分线研究（硬件/软件/测试各一条线），但各线产出汇总后由接口人统一对外 |
| **问题 owner 制** | 每个问题一个 owner，owner 对问题的闭环负责（含与供应商的沟通） |
| **轮换交接** | 接口人变更必须书面交接（历史沟通/承诺/未决项），防止「换人即失忆」 |

**为什么避免多人跟踪同一问题**：供应商收到 3 个不同人的矛盾指令时，会选择「等他们内部统一」——**多人跟踪 = 把决策权让渡给供应商**。这是对外沟通最昂贵的隐性成本。

### 9.5 关系纪律（长期视角）

- 资源利用是「共赢博弈」不是「榨取」——供应商投入有上限，**信用透支**（频繁不合理升级/小事进驻）会导致后续真实需求得不到响应
- 信息互惠（errata §4.4）：我方发现的部件问题主动反馈供应商——双向信任是长期资源池的基础

## 12. 批判注记

1. **评分卡的客观性**：六维评分仍是人工打分，存在主观偏差——建议至少两人独立评分取均值，且评分要有记录依据（邮件/日报引用）。
2. **进驻的 ROI 不保证**：进驻成本高（双方人力+差旅），§4.3 两个失效条件是经验归纳非实证——建议每次进驻后记录 ROI（问题收敛速度 vs 常规模式），积累数据校准「何时值得进驻」。
3. **「投入分级→升级」可能误伤**：供应商内部确实可能「已投入但在攻坚」（沉默投入）——分级触发升级前，先用承诺表核对「承诺是否在推进」，避免把攻坚中的供应商逼走。
4. **环境对照表的完备性假设**：38 个变量清单无法穷尽环境——对照表只能覆盖已知维度，未知维度（如电磁干扰、批次差异）仍需现场数据兜底。
5. **概率→确定性交接不总是可行**：部分概率问题的触发条件受限于物理随机性（如 ECC 位翻转），无法收敛到确定性触发集——此时交接物降级为「统计显著性证据 + 样本数据包」，供应商接受度下降。
6. **本文为协作方法论建构**：action 评分/进驻机制/日报结构均为实战经验的结构化，非行业标准流程；需结合具体供应商关系（A-D 级客户地位，tactics §1.1）裁剪使用。
