## 1. 项目目标管理 (Goals & Objectives)

### 定义

明确项目的核心定位、预期成果与量化指标，为所有后续决策提供基准参照。

### 关键活动

| 层级 | 内容 | 衡量方式 |
|:-----|:-----|:---------|
| **使命/愿景** | 项目为什么要做？解决什么业务问题？ | 一句话陈述 |
| **总体目标** | 最终要达成的核心结果（产品上线/流程优化/业绩指标） | 定性 + 定量 |
| **阶段目标** | 拆分为若干里程碑，每个里程碑有明确产出 | 时间节点 + 验收标准 |
| **关键结果 (KRs)** | 3-5 个可量化关键结果，与总体目标对齐 | 数值 + 基线 + 截止日 |

### 交付物

- 项目章程（Project Charter）
- 目标分解树（Goal Breakdown Tree）
- OKR 或 KPI 指标卡

### ⚠️ 常见陷阱

- 目标过于宏大无法衡量 → 必须分解到季度/月度可验证里程碑
- 目标与资源不匹配 → 启动前做资源对齐确认

## 2. 范围管理 (Scope Management)

### 定义

定义项目的边界——做什么、不做什么，以及范围变更的控制机制。

### 关键活动

| 活动 | 说明 | 输出 |
|:-----|:-----|:-----|
| **范围定义** | 明确包含/不包含的功能、模块、交付物 | 范围说明书 |
| **WBS 分解** | 将交付物逐层分解到可执行的工作包 | WBS 字典 (3-4层) |
| **范围确认** | 干系人正式确认范围 | 签字版范围基线 |
| **范围变更控制** | 变更请求→影响分析→CCB 审批→更新基线 | 变更日志 |

### WBS 分解原则（MECE）

- 第二层：硬件 / 软件 / 结构 / 散热 / 固件 / 测试 / 认证 / 文档
- 每个工作包：1 个责任人 + 1 个交付物 + 1 个截止日
- 所有工作包 → 每人每周不超过 5 个并行

### ⚠️ 常见陷阱

- 范围潜变（Scope Creep）：未走变更流程的微小需求累加导致失控
- WBS 过粗或过细：3-4 层为标准，过大再分，过小合并

## 3. 当前现状评估 (Current Status Assessment)

### 定义

客观反映项目当前所处的阶段、已完成工作与未完成差距。

### 关键活动

| 维度 | 内容 | 判断标准 |
|:-----|:-----|:---------|
| **阶段判定** | 启动/规划/执行/监控/收尾 | TR 门禁状态 |
| **进度偏差** | 实际 vs 计划 | 超前/正常/滞后 (±X天) |
| **质量状态** | 缺陷率/返工率/测试通过率 | 质量基线 |
| **资源消耗** | 人力/资金/物资消耗 vs 预算 | 挣值管理 (EVM) |
| **已交付物** | 文档/代码/样机/报告 | 验收签字 |
| **待完成项** | 剩余任务/问题单/变更 | 清单 + 优先级 |

### 交付物

- 项目状态报告（每周/双周）
- 燃尽图 / 燃起图

### ⚠️ 常见陷阱

- 报喜不报忧 → 必须建立「红黄绿灯」强制汇报机制
- 进度滞后但缺乏根因分析 → 滞后必有因，用鱼骨图定位

## 4. 计划管理 (Planning & Scheduling)

### 定义

将目标拆解为可执行的任务序列，明确依赖关系、时间估计和关键路径。

### 关键活动

| 活动 | 输入 | 输出 |
|:-----|:-----|:-----|
| **任务分解** | WBS 工作包 | 任务清单 (Task List) |
| **依赖分析** | FS/SS/FF/SF 关系 | 网络图 / 甘特图 |
| **工期估算** | 三点估算 / 类比 / 参数法 | 工期表 |
| **关键路径识别** | 最长路径 = 项目最短工期 | 关键路径清单 |
| **缓冲管理** | 项目缓冲 + 接驳缓冲 | 缓冲区状态 |

### 关键路径管理要点

- 关键路径上的任务每延迟 1 天 → 项目整体延迟 1 天
- 每周刷新关键路径（可能因任务完成而变化）
- 关键路径任务不安排新人、不并行削减资源
- 必要时用「赶工 (Crashing)」或「快速跟进 (Fast Tracking)」

### 交付物

- 甘特图 / 项目计划表（含里程碑）
- 依赖矩阵（Dependency Matrix）
- 资源负载图

### ⚠️ 常见陷阱

- 过度乐观的工期估算 → 必须引入安全缓冲（~20%）
- 忽略隐式依赖 → 如「设计完成」隐含「评审完成」

## 5. 实施与执行管理 (Execution & Delivery)

### 定义

按计划开展具体工作，动态协调任务、人员与资源，确保产出物按时按质交付。

### 关键活动

| 活动 | 频率 | 核心内容 |
|:-----|:-----|:---------|
| **每日站会** | 每日 | 昨日完成/今日计划/阻碍项 |
| **周例会** | 每周 | 进度回顾/风险更新/下周计划 |
| **看板管理** | 持续 | 待办→进行中→已完成 可视化 |
| **拉动式执行** | 按需 | 完成当前批次再拉取下批次 |
| **阻碍物清除** | 即时 | 责任到人 + 升级时限 |

### 执行方法论选择

| 方法 | 适用场景 | 核心特点 |
|:-----|:---------|:---------|
| **Scrum** | 软件/固件迭代开发 | 2-4 周 Sprint，固定时间盒 |
| **Kanban** | 运维/持续改进 | 无固定迭代，流动式 |
| **Waterfall** | 硬件/结构/认证 | 阶段门禁，严格顺序 |
| **Hybrid** | 服务器产品研发 | 硬件 Waterfall + 固件 Agile |

### 交付物

- 看板（物理或电子）
- Sprint Backlog / 任务板
- 阻碍项清单（Impediment List）

## 6. 质量管理 (Quality Management)

### 定义

建立质量标准和检验机制，确保交付物满足规格要求和客户期望。

### 关键活动

| 活动 | 说明 | 输出 |
|:-----|:-----|:-----|
| **质量规划** | 确定质量目标、标准、检查点 | 质量管理计划 |
| **质量保证 (QA)** | 过程审计，确保流程被执行 | 审计报告 |
| **质量控制 (QC)** | 产品检验/测试，发现缺陷 | 测试报告/缺陷清单 |
| **质量门禁** | TR 评审中的质量关卡 | 门禁通过/不通过 |

### 质量维度的量化标准

| 维度 | 服务器产品研发示例 |
|:-----|:-------------------|
| **功能正确性** | 功能测试通过率 ≥ 98% |
| **可靠性** | MTBF ≥ X 万小时，AFR ≤ Y% |
| **性能达标** | SPEC 分数 ≥ 基线 95% |
| **信号完整性** | 眼图裕量 ≥ 20%，误码率 ≤ 1e-12 |
| **散热** | 芯片结温 ≤ Tj_max - 5°C |
| **可制造性** | DFM 评审通过率 ≥ 90% |

### ⚠️ 常见陷阱

- 只测功能不测边界 → 必须包含极限/压力/异常场景
- 质量是「检验」出来的 → 实际是「设计和过程」出来的

## 7. 成本管理 (Cost Management)

### 定义

对项目全生命周期成本进行估算、预算和控制。

### 关键活动

| 活动 | 内容 | 工具/方法 |
|:-----|:-----|:----------|
| **成本估算** | 人力/物料/测试/认证/模具/物流 | 类比 + 参数 + 自下而上 |
| **预算编制** | 按阶段/WBS 分解预算 | 成本基线 (S-curve) |
| **成本控制** | 实际 vs 预算偏差分析 | 挣值管理 (EVM) |
| **变更成本影响** | 范围变更→成本更新 | CCB 审批 |

### BOM 成本核算要点

- **物料成本**: CPU/GPU/内存/SSD/NIC/PCB/被动元件/连接器
- **制造成本**: SMT/组装/测试/包装
- **非重复工程成本 (NRE)**: 模具/治具/Layout/认证
- **运营成本**: 功耗/散热/运维/退货

### 交付物

- 成本估算表（含置信度）
- 预算跟踪表（EVM 指标：PV/EV/AC/SPI/CPI）
- BOM 成本明细

### ⚠️ 常见陷阱

- 低估 NRE 成本（特别是认证和模具）
- 忽略量产后的退换货成本

## 8. 资源管理 (Resource Management)

### 定义

识别、获取、分配和管理项目所需的人力、物力、财力与技术资源。

### 关键活动

| 活动 | 内容 | 判断标准 |
|:-----|:-----|:---------|
| **资源识别** | 人力/设备/工具/场地/许可证 | 资源清单 |
| **资源估算** | 数量/技能/时间/成本 | 资源需求表 |
| **资源获取** | 调配/招聘/采购/租赁 | 到岗/到货时间 |
| **资源负载** | 每人/每设备的工作量饱和度 | 负载甘特图 |
| **资源冲突解决** | 多项目争抢同一资源 | 优先级协商/升级 |

### 人力资源规划

| 角色 | 典型配置（服务器项目） | 关键能力 |
|:-----|:----------------------|:---------|
| **项目经理** | 1 人 | IPD 流程/跨部门协调 |
| **系统架构师** | 1 人 | 全栈技术/技术决策 |
| **硬件工程师** | 3-5 人 | 原理图/Layout/调试 |
| **固件工程师** | 2-4 人 | BMC/BIOS/CPLD |
| **软件工程师** | 2-5 人 | 驱动/管理系统/测试工具 |
| **结构工程师** | 1-2 人 | 3D/散热/EMC |
| **测试工程师** | 2-4 人 | 功能/性能/可靠性/兼容性 |
| **认证工程师** | 1 人 | 安规/EMC/能效/入网 |

### ⚠️ 常见陷阱

- 资源负载超过 80% → 无缓冲应对突发任务
- 关键人员单点依赖 → 必须有备份/知识转移机制

## 9. 沟通管理 (Communication Management)

### 定义

规划项目信息的收集、分发、存储与处置，确保所有干系人获取适当的信息。

### 关键活动

| 活动 | 说明 | 输出 |
|:-----|:-----|:-----|
| **干系人沟通分析** | 谁需要什么、何时、何频率、何形式 | 沟通矩阵 |
| **RACI 矩阵** | 谁负责/执行/咨询/知情 | RACI 表 |
| **汇报机制** | 日报/周报/月报/里程碑报告 | 报告模板 |
| **升级通道** | 问题升级的层级和时限 | 升级流程图 |

### 沟通矩阵模板

| 信息类型 | 受众 | 频率 | 格式 | 责任人 |
|:---------|:-----|:-----|:-----|:-------|
| 项目状态 | PMO/管理层 | 双周 | PPT + 红黄绿灯 | PM |
| 技术评审 | 架构师/技术专家 | 里程碑 | 文档 + 评审会 | 架构师 |
| 风险更新 | 核心团队 | 每周 | 表格 | PM |
| 日常协调 | 执行团队 | 每日 | 站会 | 各组长 |
| 变更通知 | 所有受影响干系人 | 即时 | 邮件 + CCB 纪要 | PM |

### ⚠️ 常见陷阱

- 过度沟通（信息过载）→ 按角色裁剪信息量
- 问题通报不及时 → 24 小时内必须升级到决策层

## 10. 干系人管理 (Stakeholder Management)

### 定义

识别、分析、管理项目干系人的期望与影响力，获取支持、降低阻力。

### 关键活动

| 活动 | 内容 | 工具 |
|:-----|:-----|:-----|
| **干系人识别** | 列出所有受项目影响或能影响项目的人/组织 | 干系人登记册 |
| **影响力-利益分析** | 按权力/影响力 × 利益/关注度四象限分类 | 权力-利益网格 |
| **参与策略** | 每个象限的沟通/参与方式 | 参与计划 |
| **满意度跟踪** | 定期检查干系人满意度 | 调研/访谈 |

### 四象限策略

| 象限 | 特征 | 管理策略 |
|:-----|:-----|:---------|
| **高权力高利益** | 决策者/赞助人 | 重点管理，充分沟通，定期汇报 |
| **高权力低利益** | 高层领导/合规部门 | 保持满意，定期简报 |
| **低权力高利益** | 执行团队/最终用户 | 保持告知，听取反馈 |
| **低权力低利益** | 外部供应商/观察者 | 最低监控，必要告知 |

### ⚠️ 常见陷阱

- 忽略反对者或低利益干系人 → 关键节点可能被否决
- 未识别隐形干系人（如合规/法务/财务）

## 11. 采购与供应商管理 (Procurement & Vendor Management)

### 定义

管理外部产品/服务的获取过程，包括供应商选择、合同管理、交付验收。

### 关键活动

| 阶段 | 活动 | 输出 |
|:-----|:-----|:-----|
| **采购规划** | 自制/外购决策、采购策略 | 采购管理计划 |
| **供应商选择** | RFQ/RFP、技术评估、商务谈判 | 供应商评估表 |
| **合同管理** | 技术协议/商务合同/NDA | 签署合同 |
| **交付跟踪** | 交期/质量/问题跟踪 | 供应商交付看板 |
| **验收付款** | IQC 检验/性能验收/付款节点 | 验收报告 |

### 服务器项目典型采购项

| 类别 | 典型物料 | 供应商数量策略 |
|:-----|:---------|:---------------|
| **核心芯片** | CPU/GPU/DPU | 双源或三源 |
| **存储** | DRAM/SSD | 至少双源 |
| **互联** | NIC/Switch/Cable | 双源 |
| **被动元件** | MLCC/Resistor | 多源 |
| **PCB/PCBA** | 主板/背板 | 2-3 家认证 |
| **模具** | 机箱/风扇/散热器 | 单源（模具唯一） |

### ⚠️ 常见陷阱

- 单一供应商风险 → 核心物料至少双源认证
- 供应商交期与项目计划脱节 → 每周刷新关键物料交期

## 12. 变更管理 (Change Management)

### 定义

建立统一的变更请求处理流程，评估影响、获得批准、更新基线。

### 变更类型

| 类型 | 示例 | 审批层级 |
|:-----|:-----|:---------|
| **范围变更** | 新增/移除功能模块 | CCB (变更控制委员会) |
| **进度变更** | 里程碑调整 | PM + 发起人 |
| **成本变更** | 预算超支 > 10% | 发起人 + PMO |
| **技术变更** | 方案替换、器件替换 | 架构师 + PM |
| **资源变更** | 关键人员替换 | PM + 职能经理 |

### 变更控制流程

1. **提交**：变更请求及变更单
2. **影响分析**：范围/进度/成本/质量/风险 → 24h 内完成
3. **CCB 评审**：决定批准/拒绝/暂缓
4. **更新基线**：批准后更新所有受影响的管理计划
5. **通知干系人**：变更结果通报

### 交付物

- 变更请求单（Change Request Form）
- 变更日志（Change Log）
- 更新的基线文件

### ⚠️ 常见陷阱

- 微小变更未走流程但累积失控 → 定义「微小变更」阈值
- CCB 审批周期过长 → 紧急变更设 24h 快速通道

## 13. 风险管理 (Risk Management)

### 定义

识别、分析、应对项目全生命周期的不确定性，降低威胁、利用机会。

### 关键活动（五步法）

| 步骤 | 内容 | 工具/方法 |
|:-----|:-----|:----------|
| **1. 识别** | 系统性发现潜在风险事件 | 头脑风暴/检查单/假设分析/SWIFT |
| **2. 定性分析** | 概率 × 影响 → 风险等级 | 概率-影响矩阵 |
| **3. 定量分析** | 蒙特卡洛/决策树/敏感性 | 量化模型 |
| **4. 应对规划** | 规避/转移/减轻/接受 | 应对策略表 |
| **5. 监控** | 跟踪已有风险，识别新生风险 | 风险登记册 (滚动更新) |

### 风险登记册（RBS 结构化）

| 类别 | 典型风险点 | 影响等级 |
|:-----|:-----------|:---------|
| **技术风险** | 方案不可行/性能不达标/散热不足 | H/M/L |
| **进度风险** | 关键路径延迟/依赖卡顿 | H/M/L |
| **资源风险** | 关键人员离职/产能不足 | H/M/L |
| **供应商风险** | 物料缺货/交期延迟/质量不稳 | H/M/L |
| **市场风险** | 需求变化/竞品抢先/价格压力 | H/M/L |
| **合规风险** | 专利/认证/出口管制 | H/M/L |

### 应对策略

| 策略 | 说明 | 示例 |
|:-----|:-----|:-----|
| **规避** | 改变计划彻底消除风险 | 换成熟的方案 |
| **转移** | 将风险转给第三方 | 供应商质量担保 |
| **减轻** | 降低概率或影响 | 双源采购 |
| **接受** | 主动（预留缓冲）或被动 | 进度缓冲 20% |

### ⚠️ 常见陷阱

- 风险识别一次了事 → 每双周刷新风险登记册
- 只识别不应对 → 每个风险必须有应对责任人 + 截止日

## 14. 里程碑与交付物管理 (Milestones & Deliverables)

### 定义

定义项目的关键时间节点和对应的有形交付物，作为进度和质量的控制锚点。

### 关键活动

| 活动 | 内容 | 判断标准 |
|:-----|:-----|:---------|
| **里程碑定义** | 关键决策点/阶段门禁/外部依赖节点 | 时间点 + 通过标准 |
| **交付物清单** | 每阶段的输出物清单及验收标准 | 交付物登记册 |
| **里程碑评审** | TR/TM 评审 | 评审结论 (通过/有条件/不通过) |
| **交付物签收** | 干系人/客户正式签收 | 签字版验收单 |

### 服务器项目典型里程碑

| 里程碑 | 阶段 | 核心交付物 |
|:-------|:-----|:-----------|
| **TR1** | 概念 | 产品包需求/立项报告 |
| **TR2** | 计划 | 系统方案/技术规格书/项目计划 |
| **TR3** | 开发 | 详细设计/Layout/原型样机 |
| **TR4** | 验证 | EVT 样机/功能测试报告 |
| **TR5** | 验证 | DVT 报告/可靠性报告/认证报告 |
| **TR6** | 发布 | 量产批准/工艺文件/售后资料 |

### 交付物质量标准

- 每个交付物必须：有明确责任人 + 审查人 + 截止日 + 验收标准
- 文档类：模板化 + 版本号 + 变更历史
- 硬件类：BOM 释放 + 器件清单 + 测试通过
- 软件类：代码审查 + 单元测试 + 集成测试

### ⚠️ 常见陷阱

- 里程碑只有时间没有通过标准 → 必须定义 Exit Criteria
- 交付物验收流于形式 → 每次评审做 Checklist Check

## 15. 决策与评审管理 (Decision & Review Management)

### 定义

建立项目关键决策和评审的机制、流程与记录，确保决策有据可查、可追溯。

### 关键活动

| 活动 | 说明 | 输出 |
|:-----|:-----|:-----|
| **评审门禁** | TR/TM/MR 评审 | 评审结论 + 整改项 |
| **技术决策** | 架构方案/器件选型/技术取舍 | 决策记录 (ADR) |
| **问题升级决策** | 跨部门/高层决策 | 升级决策书 |
| **决策日志** | 所有决策的时间、参与人、理由 | 决策日志 (Decision Log) |

### 架构决策记录 (ADR) 模板

```text
## ADR-{编号}: {标题}

**决策时间**: YYYY-MM-DD
**提出者**: {姓名}
**参与人**: {姓名列表}

**背景**:
{决策上下文，待解决的问题}

**可选方案**:
- 方案A: {描述 + 优缺点}
- 方案B: {描述 + 优缺点}
- 方案C: {描述 + 优缺点}

**决策结果**: {选定方案}
**决策理由**: {XXX 标准/XXX 约束/XXX 数据}

**后果**:
- 正面: {...}
- 负面: {...}
- 回退方案: {...}
```

### 评审门禁执行要点

- **评审前**: 材料提前 3 天发放，与会人提前阅读
- **评审中**: 按 CheckList 逐项检查，不跳项
- **评审后**: 明确整改项 + 责任人 + 截止日
- **有条件通过**: 条件必须在下个里程碑前闭环

### ⚠️ 常见陷阱

- 评审只走形式不找问题 → 评审人必须有质疑义务
- 决策不记录理由 → 后续回溯无法理解决策逻辑
