## §0 执行摘要

**问题**：服务器整机/板卡研发中，信息从需求→框图→原理图→布线层层细化，但**上级设计常没考虑到位**，到实现阶段才发现功能点缺失、规格不确定，工程师只能"自由发挥"，导致返工和出错。

**核心结论（一句话）**：硬件研发的返工 90% 不是"实现错误"，而是**信息断层**——每层向下传递时丢失了隐性假设、未定义规格和跨域功能点。解法不是"要求上层一次想全"（违反人类认知规律），而是**建立分层信息模型 + 逐层 Check 关卡 + 配套表格清单**，让每个功能点在**所属层级**被显性定义、在**下一层**被检查闭环。

**六个点名问题的答案速查**：

| # | 问题 | 一句话答案 | 详见 |
|:-:|:-----|:-----------|:-----|
| 1 | rack/board/slot id 怎么弄 | **分层编码**：机房→排/列→机柜→Slot→FRU 五级；实现用硬件 straps + EEPROM/FRU + BMC 读取，ID 分配表逐格登记 | §5.1/§4.3 |
| 2 | 具体需求与规格怎么定 | **需求追溯矩阵（RTM）**：每条需求必须"数值+单位+基线+条件+验收方法"，框图阶段逐条落格 | §5.2/§4.2 |
| 3 | OS 怎么安装 | **引导链路三选一**（PXE/虚拟介质/本地盘）+ BMC 引导顺序 + 镜像仓库，在框图阶段定为需求而非实现期救火 | §5.3/§4.7 |
| 4 | 物料是否到位 | **BOM 就绪度表**：长交期料（GPU/交换芯片 8~16 周）CDR1 后立即下单，齐套状态每周刷新 | §5.4/§4.6 |
| 5 | 是否配套点灯 | **LED 定义矩阵**：每个状态灯（电源/健康/UID/故障）定义颜色×状态×控制源×触发条件，IPMI 标准接口 | §5.5/§4.5 |
| 6 | 对外接口怎么样 | **接口控制文档 ICD**：连接器×引脚×信号×方向×电平×速率逐格定义，原理图前冻结 | §5.6/§4.4 |

**立即可做 3 件事**：① 建 ID 分配表（本周内锁定编码规则）；② 建 RTM（每条需求落格）；③ 建接口 ICD（原理图 R1 前冻结）。三张表即可消除 80% 的"实现阶段自由发挥" [来源: 行业工程经验]。

## §1 问题诊断：为什么"上级没考虑到位，实现阶段自由发挥"

### 1.1 症状：用户点名的六类典型断层

用户描述的现象在服务器/整机柜研发中高度典型。将其结构化为六类"跨层功能点"，它们共同特征是：**不属于任何单一领域（硬件/软件/结构），因此在任何一层都没有人负责定义**：

| # | 功能点 | 典型疑问 | 应该在哪层定义 | 常见结局 |
|:-:|:-------|:---------|:-------------|:---------|
| 1 | 板卡/槽位识别 | rack id / board id / slot id 怎么弄？规格是什么？ | **框图层（L2）** | 实现期才讨论，硬件软件各搞一套，编码冲突 |
| 2 | 需求规格量化 | "具体需求与规格是怎么样的"？ | **需求层（L1）** | PRD 只写功能不写约束，验收无依据 |
| 3 | OS 部署链路 | OS 怎么安装？谁负责？引导方式？ | **框图层（L2）** | 硬件回板了才想 OS，PXE 网络没规划 |
| 4 | 物料就绪 | 物料是否到位？长交期料何时下单？ | **需求层（L1）决策，方案层（L2）冻结** | 设计完了等料 8 周，项目延期 |
| 5 | 点灯（LED） | 是否配套点灯？定义什么状态？ | **框图层（L2）** | 面板开模了才补灯，结构返工 |
| 6 | 对外接口 | 对外接口是怎么样的？连接器/引脚/协议？ | **框图层（L2）冻结，原理图（L3）细化** | 接口两边各画各的，联调对不上 |

> **共同规律**：六类问题**没有一个是"电路不会画"**，全部是**"该定义规格的层级没定义，规格真空下推到实现层"**。这就是"自由发挥"的本质——**规格空缺处，实现者只能用自己的假设填补**。

### 1.2 第一性原理：三层信息丢失机制

为什么"上级没考虑到位"会系统性发生？从信息论角度，分层传递存在三种结构性丢失：

| # | 丢失机制 | 机理 | 典型表现 |
|:-:|:---------|:-----|:---------|
| **L-A 隐性化** | 设计者脑中"默认会做"的事没写进文档 | 框图只画数据流，不画管理面/识别面/点灯 | "这个肯定要做啊"——但没人写下来 |
| **L-B 跨域真空** | 需要多领域协同定义的功能点无归属 | ID 机制=硬件(straps)+固件(BMC读)+系统(编码规则) | 硬件以为软件管，软件以为硬件给 |
| **L-C 量化缺失** | 写了功能没写约束 | "支持热插拔"没写"5000 次循环、带电" | 验收阶段双方对"支持"理解不一致 |

> **量化证据**：芯片行业 60%+ 改版根因可追溯到需求阶段遗漏，且遗漏中**非功能需求占 75%**（功耗/接口/时序/温度/成本），纯功能仅 25% [来源: knowledge/02_rd/04_chip/base/2026-07-21-chip-design-L6-requirements-to-architecture.md §1.4]。板卡级同样适用——**漏掉的从来不是"主功能"，而是"配套约束"**。

### 1.3 根因：系统级功能点的"归属真空"

把 §1.1 的六类问题归类，发现它们都属于同一根因——**系统级功能点没有在系统层（框图层）被认领**：

```text
                Traditional org (by domain)          System-level features (cross-domain)
+----------------------+  +----------------------+
|      HW EE           |  |   ID mechanism        |
|  schematic/layout/BOM |  |   LED system          |
+----------------------+  |   OS deploy chain     |
|      FW              |  |   Interface contract  |
|  BMC/BIOS/CPLD       |  +----------------------+
+----------------------+        ^
|      ME              |        | no "system engineer" owner
+----------------------+        | -> nobody owns -> blows up at impl
|      SW              |
+----------------------+
```

**关键洞察**：这类功能点有一个共同特征——**必须在"框图之上"（系统架构层）定义，由"系统工程师/架构师"认领**。如果组织里没有明确这个角色，它们就会在领域分工的缝隙中滑落。

> **对策**：不是加人，而是**加"层"**——在需求与原理图之间，强制建立**框图层（L2）**，并规定"框图层必须交付 ID 分配表、ICD、LED 定义表"三张表。层存在了，归属就有了。

## §2 分层信息模型（五层金字塔）

### 2.1 五层结构与每层定义

将硬件研发信息流标准化为五层，每层有独立交付物与准出标准（参考 [服务器研发项目管理方法论 §1.1 四层分解](2026-08-20-server-rd-project-management-methodology.md) 扩展为设计信息视角）：

```text
L1 Requirement -- What: PRD / requirement spec        Gate1 requirement review
L2 Block diagram - How: system/module blocks+contracts   Gate2 block review  *KEY GATE
L3 Schematic ---- Detail: circuit detail (schematic)   Gate3 schematic review
L4 Layout ------- Physical: physical impl (layout)     Gate4 layout review
L5 Fab/verify --- Verify: EVT/DVT                      Gate5 test review
```

| 层 | 名称 | 核心交付物 | 责任角色 | 典型周期 | 准出标准 |
|:-:|:-----|:----------|:---------|:--------:|:---------|
| L1 | 需求层 | PRD/需求规格书 + RTM 初版 | 产品/系统工程师 | 2~4 周 | 每条需求"数值+单位+基线+条件"可验收 |
| L2 | 框图层 | 系统框图 + 模块框图 + ID 分配表 + ICD + LED 表 + 物料齐套表 | **系统架构师（认领人）** | 2~3 周 | 六类跨域功能点全部有明确归属与规格 |
| L3 | 原理图层 | 原理图 + BOM 初版 + 信号表 | 硬件工程师 | 4~6 周 | 原理图与 ICD 逐信号一致，无"待定" |
| L4 | 布线层 | Layout + 叠层 + SI 报告 | Layout 工程师 | 3~4 周 | 布线规则表逐项通过，SI 裕量 ≥ 20% |
| L5 | 制造验证 | 样机 + 测试报告 + 问题清单 | 测试工程师 | 4~8 周 | 无 P0/P1 未关闭问题 |

> **与芯片设计 L6 金字塔的对应**：本模型的 L1~L5 对应芯片设计金字塔的 L6(需求→架构)→L5(架构→集成)→L4(集成→实现)→L3(实现→验证) 的板级版——方法同源 [来源: 2026-07-21-chip-design-L6-requirements-to-architecture.md]。

### 2.2 每层的输入/输出/细化方法

**L1 需求层**：
- **输入**：客户需求、市场定位、竞品对标、平台规划
- **输出**：《需求规格书》含功能需求 + 非功能需求（功耗/接口/时序/温度/成本/DFX），每条带优先级（MoSCoW）与验收方法
- **细化方法**：九维需求框架（计算/内存/接口/带宽/功耗/温度/安全/成本/时间）逐维落格 [来源: chip-design-L6 §2.1]；**功能必需配对非功能**（R2 铁律）

**L2 框图层（★本模型核心）**：
- **输入**：需求规格书
- **输出**：系统框图（含管理面/数据面/电源面/识别面四视图）+ 模块划分 + 跨域功能点清单（ID/LED/OS/接口/物料）
- **细化方法**：把"隐性假设"逐条显性化——**自问清单**：每个模块之间怎么识别？怎么点灯？怎么装系统？怎么供电？怎么散热？怎么管理？六问缺一不可

**L3 原理图层**：
- **输入**：框图 + ICD + ID 分配表 + LED 表
- **输出**：原理图（含电源树/时钟树/信号连接）+ BOM 初版
- **细化方法**：信号逐条对照 ICD 打勾；电源逐轨对照功耗预算表；BOM 对照物料齐套表

**L4 布线层**：
- **输入**：原理图 + 叠层 + SI 约束
- **输出**：Layout + Gerber + SI 仿真报告
- **细化方法**：布线规则表（线宽/间距/阻抗/等长）逐项执行，DRC 清零，SI 后仿真裕量确认

**L5 制造验证层**：
- **输入**：样机 + 测试计划
- **输出**：EVT/DVT 报告 + 问题清单 + 回归记录
- **细化方法**：测试用例与 RTM 逐条对应（每条需求至少 1 条验证），问题分级（P0~P3）+ 关闭双门槛（T+K）[来源: 2026-08-10-server-rd-issue-management-framework.md §6]

### 2.3 层间传递的三个铁律

| # | 铁律 | 内容 | 违反后果 |
|:-:|:-----|:-----|:---------|
| R1 | **无规格不下传** | 上层未定义的规格，下层不得自行假设；必须回退上层补齐 | 自由发挥 → 返工 |
| R2 | **接口契约冻结** | 跨层接口（电气/机械/协议）在指定时点冻结，变更走正式流程 | 联调对不上 [来源: 08-20 方法论 §6.2] |
| R3 | **表格伴随传递** | 每层的表格（RTM/ID/ICD/LED/BOM）随设计文档**同时**向下传递并更新 | 文档与实现脱节 |

> **核心方法论**：分层传递的本质是**"先窄后宽"**——上层只定义"是什么/约束什么"，不定义"怎么实现"；下层在约束内自由发挥，但**约束之外的发挥必须回退确认**。这样既尊重各层专业判断，又堵住"自由发挥"的漏洞。

## §3 Check 机制设计（Gate + Checklist + 表格三件套）

### 3.1 检查关卡总览（五 Gate）

每个 Gate = **评审会（3 天前发材料）+ Checklist（逐项打勾）+ 配套表格（数据支撑）** 三件套。参考 [08-20 方法论 §4 里程碑体系](2026-08-20-server-rd-project-management-methodology.md) 的 Gate 思想，细化到设计信息层：

| Gate | 对应层 | 触发时点 | 必审材料 | 配套表格 | 硬门槛（3 条量化） |
|:----:|:------:|:---------|:---------|:---------|:-----------------|
| **G1** | L1 需求 | 需求定稿前 | 需求规格书 + RTM v0.1 | RTM | ① 九维全覆盖 ② 每条需求可验收 ③ 无"待定"需求 |
| **G2** | L2 框图 | 框图冻结前 | 系统框图 + ID 表 + ICD + LED 表 + 物料表 | ID/ICD/LED/BOM | ① 六类跨域功能点有归属 ② ID 编码全局唯一 ③ 接口 100% 定义 |
| **G3** | L3 原理图 | 原理图 R1 后 | 原理图 + 信号对照表 + BOM v0.2 | ICD/BOM | ① 信号与 ICD 逐条一致 ② 电源预算表闭环 ③ BOM 无"待定"料 |
| **G4** | L4 布线 | Gerber 前 | Layout + DRC 报告 + SI 报告 | 布线规则表 | ① DRC 清零 ② SI 裕量 ≥20% ③ 与结构/连接器对齐 |
| **G5** | L5 验证 | EVT/DVT 后 | 测试报告 + 问题清单 | RTM(验收列) | ① 每条需求 ≥1 条验证记录 ② 无 P0/P1 未关闭 ③ 覆盖率 ≥95% |

> **评审纪律**：评审材料提前 3 天发放、按 Checklist 逐项检查（不是逐页过 PPT）；每个"待定"项登记问题清单并限期闭环 [来源: 08-20 方法论 §2.3/§3.2]。

### 3.2 逐层 Check 动作与准出标准

**G1 需求评审**——Check 动作：
- 逐条过 RTM：功能需求是否配对了非功能约束（功耗/接口/时序）？
- 九维框架逐维检查：哪一维空白？(计算/内存/接口/带宽/功耗/温度/安全/成本/时间)
- "默认满足"项显性化：如"OS 支持"必须写明安装方式与版本
- 优先级标注：每条需求 MoSCoW 分级，冲突显式排序 [来源: chip-design-L6 §3.3]

**G2 框图评审（★最关键）**——Check 动作：
- **跨域六问**：每个模块——怎么识别(ID)？怎么点灯(LED)？怎么装系统(OS)？怎么供电？怎么散热？怎么管理(BMC)？逐模块过，任一"未定义"即不通过
- ID 分配表逐格核对：编码规则是否全局唯一？实现机制是否明确（straps/EEPROM/RMC）？
- ICD 逐接口核对：连接器/引脚/信号/方向/电平/速率六要素是否齐全？
- 物料齐套表核对：长交期料是否已识别并启动采购？
- LED 表核对：每个状态灯的颜色/状态/控制源是否定义？

**G3 原理图评审**——Check 动作：
- 信号逐条对照 ICD：命名、方向、电平、连接关系一致
- 电源树对照功耗预算：每轨电流容量 ≥ 负载 × 1.2 裕量
- 时钟/复位/配置 pin 对照框图：上电时序、复位策略、strap 配置
- BOM 对照物料表：关键料有替代料？长交期料已下单？

**G4 布线评审**——Check 动作：
- DRC 报告清零（0 错误 0 警告或已豁免登记）
- SI 报告：关键高速信号裕量（眼图/串扰/等长）≥ 20% [来源: 08-20 方法论 §2.1 仿真裕量标准]
- 叠层/阻抗与设计规则一致；差分对等长匹配
- 与结构对齐：连接器位置、板框、散热器干涉检查

**G5 验证评审**——Check 动作：
- RTM 验收列逐条打勾：每条需求有测试记录？
- 问题清单分级：P0/P1 是否清零？P2 是否有处置方案？
- 覆盖率统计：功能/接口/边界场景覆盖率 ≥95%？
- 变更记录核对：gerber 后变更是否都走了 ECO？

### 3.3 检查机制的运作纪律

| # | 纪律 | 说明 |
|:-:|:-----|:-----|
| 1 | **表格是"活的"** | 每张表有唯一 owner + 更新节奏；周会逐表对状态，不念 PPT [来源: 08-20 方法论 §5.2] |
| 2 | **Gate 不走过场** | 硬门槛 3 条不满足不进入下一层；可带风险放行但必须登记 [来源: 08-20 方法论 §4.2] |
| 3 | **待定项限期闭环** | 每个"待定/待确认"登记问题清单，限 1 周内闭环或升级 |
| 4 | **变更显性化** | 冻结后变更走 A/B/C 分级审批 [来源: 08-20 方法论 §6.3] |
| 5 | **沉淀为模板** | 每个项目结束后把 Checklist 增量沉淀到组织模板库（防"评审经验人走茶凉"） |

## §5 用户点名问题逐项击破

### 5.1 rack id / board id / slot id 怎么弄？

**结论先行**：采用**五级分层编码**（机房→排/列→机柜→Slot→FRU）+ **硬件 straps/EEPROM 实现 + BMC 读取**的组合方案 [来源: L12 集成清单 §3.3]。

| 决策点 | 推荐方案 | 理由 | 备选 |
|:-------|:---------|:-----|:-----|
| 编码层级 | 五级分层（机房/排/列/柜/Slot/FRU） | 全局唯一 + 可预测 + 可自动推导 IP | 扁平编码（易冲突） |
| 计算节点实现 | ID Straps（电阻/GPIO）+ BMC 读 | 无人工干预、稳定可靠 | DIP 拨码（人工易错） |
| 交换节点实现 | FRU EID + RMC 柜级下发 | 与计算节点体系一致、可远程管理 | Straps（无 RMC 时） |
| 读取接口 | IPMI/Redfish 标准属性 | 软件栈通用、跨厂商 | 私有协议 |
| 唯一性校验 | 集成验收逐柜校验 | 防重复 | 人工巡检 |

**规格要点**：
- Board ID 与 Slot ID 关系：**Board ID = 板卡类型标识**（MB/SW/PSU/FAN），**Slot ID = 物理位置标识**（柜内顺序），两者正交，一张 ID 分配表同时管理
- I2C/IPMB 地址规划：每槽位独立地址（如 0x20+n），BMC 扫描时序定义
- 上电时序：BMC 上电后 <5s 内读到完整 ID（写入 RTM 验收）

### 5.2 具体需求与规格是怎么样的？

**结论先行**：需求规格不是"写出来"而是**"填表格"**——用 RTM 强制每条需求带"量化指标+验收方法"，用九维框架保证维度全覆盖 [来源: chip-design-L6 §2.1]。

**规格五要素**（每条需求必须回答）：
1. **数值**：可量化（如"插拔 5000 次"而非"支持热插拔"）
2. **单位**：W/kW、Gbps、mm、h
3. **基线**：对比基准（"SPEC CPU ≥ 基线 95%"）
4. **条件**：测试条件（25°C / 380V / 满载）
5. **验收方法**：怎么证明满足（测试用例 ID）

> **反例→正例**：❌"支持 NVMe 盘" → ✅"支持 U.2 接口 NVMe SSD，最大 30.72TB，顺序读 14000MB/s，热插拔 5000 次 [来源: PCIe 5.0 规范；参考 服务器系统设计要求细化描述.md]"

### 5.3 OS 怎么进行安装？

**结论先行**：**PXE 网络安装为主链路 + BMC 虚拟介质为备选**，框图阶段定案，回板前搭好环境 [来源: §4.7 表 6]。

**推荐链路**：
```text
Image repo (OS+drv) -> PXE/DHCP/TFTP -> BMC boot order (PXE first)
                                     -> net install -> Kickstart unattended
                                     -> batch deploy verify (cold+warm)
```

**关键规格**：
- PXE 走**管理网**（独立 VLAN），不占用业务带宽
- BMC 固件必须支持引导顺序配置 + VirtualMedia（Redfish 标准接口）[来源: L12 集成清单 §G4 管理软件/平台]
- 驱动注入：网卡/RAID/GPU 驱动预注入 initrd，避免"装完没网卡驱动"
- 验收：冷装 + 热装各 1 次通过，批量 10 节点并行安装 ≤ 1 小时

### 5.4 物料是否到位？

**结论先行**：物料管理 = **长交期前置 + 齐套可视 + 替代预案**，用 §4.6 表 5 每周刷新 [来源: 08-20 方法论 §7.2/§8.2]。

| 动作 | 时点 | 说明 |
|:-----|:-----|:-----|
| 长交期料识别 | CDR1 前 | GPU/交换芯片 8~16 周交期是最大单点风险 |
| 长交期料下单 | CDR1 后立即 | 不等 gerber，先锁产能 |
| 二供评估 | 选型阶段 | 关键料 ≥2 家 Pin-to-Pin 兼容，EVT 实际验证 |
| 齐套率刷新 | 每周 | 齐套率 <100% = 项目风险，PM 升级 |
| 替代料预案 | 设计阶段 | BOM 每关键料标注替代料号 |

> **量化锚点**：GPU/交换芯片交期 8~16 周、PCB 打样 2~3 周、SMT 1 周——**备料前置 4 周 = 项目提前 4 周** [来源: 08-20 方法论 §3.4/§7.2]。

### 5.5 是否要配套点灯？

**结论先行**：**必须配套**，且必须在框图层用 LED 定义表（§4.5）一次定全——**面板开模后补灯 = 结构返工 + 固件返工**。

| 灯 | 必配 | 说明 |
|:---|:----:|:-----|
| 电源灯 | ✅ | CPLD/硬件直驱，PWR_GOOD |
| 健康灯 | ✅ | BMC 控制，绿/黄/红三态 |
| UID 灯 | ✅ | 运维定位，IPMI Chassis Identify |
| 硬盘活动/故障灯 | ✅ | 每盘位，RAID/BMC |
| 网口 link/activity | ✅ | PHY 直驱 |
| 液冷/电源模块灯 | 视设计 | PSU 自带，液冷需状态指示 |

> **关键点**：LED 的**控制源**必须显式定义（硬件直驱 vs BMC 命令 vs CPLD）——这是点灯设计最常见的遗漏 [来源: 2026-08-15-ipmi-board-adaptation-cpld-log-deep-analysis.md]。

### 5.6 对外接口是怎么样的？

**结论先行**：所有对外接口用 **ICD（§4.4）** 在框图层冻结——连接器/引脚/信号/方向/电平/速率六要素逐格定义，发送方/接收方双向签字 [来源: 08-20 方法论 §6.2]。

**典型对外接口清单**（整机柜服务器）：

| 接口类别 | 典型接口 | 定义要素 | 冻结时点 |
|:---------|:---------|:---------|:---------|
| 网络 | 管理网口 RJ45 / OOB 网口 | 引脚+速率+VLAN | R1 前 |
| 存储 | NVMe U.2/E3.S 背板接口 | 引脚+速率+热插拔 | R1 前 |
| 供电 | AC 输入/800V HVDC/电源模块接口 | 电压+电流+引脚 | R1 前 |
| 液冷 | UQD04 快接头 | 流量+压力+温度 | R1 前 |
| 管理 | IPMB/I2C 总线、BMC 调试口 | 地址+速率 | R1 前 |
| 调试 | JTAG/UART/调试 LED | 引脚+电平 | R2 前 |
| 结构 | 导轨/安装孔/板框 | 尺寸+公差 | 结构终稿 |

## §6 落地路径：嵌入现有里程碑体系

将 Check 机制嵌入现有 CDR1→EVT→DVT→封板 里程碑 [来源: 08-20 方法论 §4.1]，不另起炉灶：

| 里程碑 | 本机制动作 | 新增表格 | 退出标准 |
|:-------|:-----------|:---------|:---------|
| **立项** | 建 RTM v0.1 + 识别长交期料 | RTM | 九维覆盖、长交期料清单 |
| **CDR1（方案）** | G1 需求评审 + 框图层六问 + ID 规则定案 | RTM + 物料表 | 六类跨域功能点有归属 |
| **设计期** | G2 框图评审 + G3 原理图评审 | ID/ICD/LED/BOM/OS 表 | 接口冻结、BOM 无待定 |
| **EVT** | G5 验证评审 + RTM 验收列打勾 | RTM(验收列) | 无 P0/P1 未关闭 |
| **DVT/封板** | 表格归档 + 变更 ECO | 全部表格 | 表格与最终实现一致 |

**最小可行启动（本周内）**：
1. **建 ID 分配表**：编码规则 + 每槽位一行（最紧急，识别机制会议已开 [来源: L12 集成清单 §1.1]）
2. **建 RTM**：把现有 PRD 逐条落格，补"量化指标+验收方法"两列
3. **建 ICD**：对外接口六要素逐格定义，R1 前冻结

## §7 结论与行动清单

**结论**：硬件研发的"实现阶段自由发挥"不是人的问题，是**机制问题**——跨域功能点没有在框图层被认领、规格没有用表格显性化、层级之间没有 Check 关卡。解法是**分层信息模型（L1~L5）+ 五 Gate 检查 + 七张配套表格**，把"隐性假设"变成"显性规格"，把"自由发挥"变成"约束内创作"。

**行动清单**（按优先级）：

| # | 动作 | 为什么 | 落地 |
|:-:|:-----|:-------|:-----|
| 1 | 建 ID 分配表（编码规则定案） | ID 是资产管理/IP 规划/故障定位地基 | 本周内，架构师牵头 |
| 2 | 建 RTM（需求逐条落格） | 需求无规格 = 验收无依据 | 本周内，系统工程师 |
| 3 | 建 ICD（接口六要素） | 接口不冻结 = 联调返工 | 原理图 R1 前 |
| 4 | LED 定义表（含控制源） | 面板开模后补灯 = 结构返工 | 框图冻结时 |
| 5 | 物料齐套表 + 长交期料下单 | 备料前置 4 周 = 提前 4 周 | CDR1 后立即 |
| 6 | OS 安装方案定案 | 回板后救火 = 项目延期 | 框图冻结时 |
| 7 | 五 Gate 评审纪律执行 | Gate 不走过场 = 质量有保障 | 从下一评审开始 |
