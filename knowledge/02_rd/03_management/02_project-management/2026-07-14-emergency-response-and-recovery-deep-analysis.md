## 1. 执行摘要

### 1.1 核心论点

> **故障不可避免，但灾难可以避免。** 逃生机制不是"出了事故怎么跑"，而是**在设计阶段就为故障预留了退出路径**。

### 1.2 辩证立场矩阵

| 断言 | 可信度等级 | 支持证据 | 反面观点 |
|:-----|:----------:|:---------|:---------|
| 逃生机制应覆盖硬件→固件→OS→应用四层 | L2（工程共识） | 云服务器架构，Google SRE 实践 | 某些嵌入式场景仅需硬件 WDT |
| 故障恢复时间与逃生机制成熟度强相关 | L2 | Netflix Chaos Monkey 数据 | "好的逃生不如好的防御" |
| 应急与设计联动的最有效形式是 post-mortem | L2 | Google SRE、Blameless Postmortem | 中国团队常跳过或形式化 |
| Chaos Engineering 对服务器硬件不适用 | L3（分析结论） | 硬件故障注入成本极高 | 华为/阿里已有成功案例 |
| 中国研发团队应急短板与管理原因 > 技术原因 | L3（分析结论） | 多团队经验观察 | 优秀团队（如华为）已有体系 |

### 1.3 核心结论

| 维度 | 结论 |
|:-----|:------|
| **最佳逃生** | 程序自己发现异常、自我清理、自我终止，不依赖外部 |
| **最佳恢复** | 恢复后用户无感知、数据零丢失、性能不降级 |
| **最佳联动** | 每次事故后都有可执行的改进项，下个版本落地 |
| **中国特色** | 管理驱动 > 技术驱动，应急偏向"人盯人"而非"系统兜底" |

## 2. 概念框架与哲学基础

### 2.1 核心概念定义

| 概念 | 定义 | 示例 |
|:-----|:-----|:-----|
| **逃生 (Escape)** | 系统在不可恢复故障前主动退出，释放资源并保存关键状态 | 内存 OOM 前的 graceful shutdown |
| **恢复 (Recovery)** | 系统从故障状态回到正常服务状态的过程 | OS 重启后加载存储中的数据继续服务 |
| **容错 (Fault Tolerance)** | 系统在部分组件故障时仍能正确提供服务 | 双路 CPU 单路故障降频运行 |
| **弹性 (Resilience)** | 系统从故障中恢复并回归正常状态的能力 | 万卡集群 NCCL 超时后自动缩减拓扑 |
| **反脆弱 (Antifragile)** | 系统因应对故障而变得更强 | 每次事故后增加了新的告警/检查项 |

### 2.2 逃生机制的三个设计原则

**原则一：故障的确定性优于不确定性**

```text
❌ "也许能继续运行" -> 不可预测的系统行为
✅ "检测到X条件，执行逃生协议Y" -> 可预测的系统行为
```

**原则二：逃生路径必须是低成本可测试的**

```text
❌ 逃生只在生产事故中触发，从未在测试中被验证
✅ 逃生路径纳入 CI/CD 回归测试，每次发布前验证
```

**原则三：逃生后的状态必须可观测**

```text
故障发生 -> 逃生执行 -> 记录日志 -> 告警通知 -> 人工介入
               v
            状态持久化（磁盘/BMC NVRAM）
               v
            恢复时可读取 -> 知道"从哪里来"
```

### 2.3 故障-逃生-恢复的时序模型

```text
正常服务 ---> 故障检测 ---> 逃生决策 ---> 逃生执行 ---> 系统退出
                  ^                              ^
            ① 检测延迟                     ② 执行时间
                                                      v
正常服务 <--- 恢复完成 <--- 恢复执行 <--- 人工介入 <--- 状态保存
                               ^                          ^
                         ③ 恢复时间                 ④ 保存时长
```

**关键优化目标**: 最小化 (① + ② + ③ + ④)的同时，保证数据的可恢复性。

### 2.4 四层逃生架构

```text
+-------------------------------------+
|           Layer 4: 应用层            | <- 主动检测、降级、graceful shutdown
+-------------------------------------+
|           Layer 3: OS 层             | <- WDT daemon、OOM killer、kdump
+-------------------------------------+
|           Layer 2: 固件/基板管理     | <- BMC watchdog、BIOS recovery
+-------------------------------------+
|           Layer 1: 硬件层            | <- HW WDT、power sequencing、AER
+-------------------------------------+
```

- **上层的逃生更智能**：知道业务上下文，能做优先级决策
- **下层的逃生更可靠**：不依赖软件栈，硬件 WDT 永远有效
- **各层独立且互补**：上层逃生失败时，下层兜底

## 3. 硬件级逃生机制

### 3.1 看门狗计时器 (Watchdog Timer, WDT)

WDT 是最基础、最可靠的逃生机制，设计上**不依赖任何软件**。

| 类型 | 位置 | 超时时间 | 触发动作 | 适用场景 |
|:-----|:-----|:--------:|:---------|:---------|
| 片内 WDT | CPU/GPU 内部 | 1-10s | 复位芯片 | CPU/GPU hang |
| 片外 WDT | CPLD/FPGA | 100ms-5s | 全板复位 | 主芯片完全死机 |
| BMC WDT | BMC 内 | 30s-5min | 重启主机/告警 | OS hang、内存泄漏 |
| 机柜 WDT | 机柜控制器 | 5-60s | 整机柜下电 | 全节点无响应 |

**设计要点**:

- **WDT 超时时间 = 正常"喂狗"间隔 × 3~5**（防止误触发）
- **WDT 必须在系统启动初期就启动**（启动阶段最脆弱）
- BMC WDT 应配置多个策略：超时→重启主机；再次超时→关闭主机电源；第三次超时→BMC 复位

### 3.2 PCIe AER (Advanced Error Reporting)

PCIe AER 是 PCIe 协议层定义的错误报告机制，**不需要 OS 以上参与**。

```text
PCIe AER 错误等级:
+-- Correctable (可纠正) -> 自动重试，记录日志
+-- Non-Fatal (非致命) -> 通知驱动，设备仍可用
+-- Fatal (致命) -> 立即触发 PCIe Hot Reset 或 Link Disable
```

**服务器逃生中的应用**:

- GPU 出现 uncorrectable ECC → 触发 PCIe AER Fatal → OS 自动重启 GPU 或触发 node draining
- NVMe SSD Fatal Error → PCIe Link Down → BMC 检测到设备丢失 → 告警

**逃生设计中的坑**:

- 某些 GPU 驱动对 PCIe AER Fatal 的响应是 kernel panic（不是逃生，是自我终结）
- 正确设计：GPU AER Fatal → OS 将该 GPU 标记为 unavailable → NCCL 自动缩减拓扑
- 参考：[NVIDIA NCCL Fault Tolerance](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/fault-tolerance.html)

### 3.3 电源管理逃生

| 故障类型 | 逃生机制 | 恢复方式 |
|:---------|:---------|:---------|
| PSU 故障 (1+1) | 自动故障切换，无中断 | 热替换 PSU |
| 整机掉电 | UPS 电池保持 → graceful shutdown | 电力恢复后自动启动 |
| 过温 | 降频 → 关机 → 熔断 | 降温后冷却复位再启 |
| 过流 | 瞬时 PSU OCP 保护 → 整机断电 | 排除短路后人工恢复 |
| 机柜过载 | PDUs 逐级卸载 → 切非关键负载 | 人工评估后恢复 |

**关键机制: PSU Hold-up Time**

- 标准要求: ≥20ms（ATX 规范）
- AI 服务器建议: ≥30ms（考虑 GPU 瞬时功耗可达 TDP 的 1.5x）
- 逃生窗口: 这 20-30ms 内，系统必须完成：
  1. 检测到 Power Good 信号丢失
  2. 通知 OS 开始紧急关机
  3. 将关键缓存写入非易失存储

### 3.4 内存/存储逃生

| 组件 | 故障模式 | 逃生机制 |
|:-----|:---------|:---------|
| DDR5 | uncorrectable ECC | MCA (Machine Check Architecture) → 杀死关联进程 → OS 置为 offline |
| HBM (GPU) | uncorrectable ECC | GPU driver 触发 page retirement → NCCL 移除该 GPU |
| NVMe SSD | Fatal Error | PCIe AER → 驱动标记故障 → 文件系统退化 (RAID降级) |
| KV Cache SSD | 单盘故障 | CMX DM 感知丢失 → 已有副本的 block 标记为 shared → 丢失的触发重新计算 |

## 4. 固件级逃生

### 4.1 UEFI/BIOS Recovery

| 场景 | 触发方式 | 恢复路径 |
|:-----|:---------|:---------|
| BIOS 启动失败的恢复 | BMC Boot Fail Count | 自动切换到 Golden Backup BIOS |
| BIOS 更新失败 | Capsule Update CRC 校验失败 | 回滚到上次可用版本 |
| NVRAM 损坏 | BIOS 启动时 CRC 校验失败 | NVRAM 重置为出厂默认值 |
| 热启动卡死 | BMC WDT 检测到 OS 无响应 | BMC 冷复位 (Cold Reset) |

**Golden BIOS 设计原则**:

- Golden Boot ROM 必须**只读**（物理保护，不能通过 FW 更新修改）
- 正常运行时更新 Secondary Region
- 启动时 Primary 校验失败 → 从 Secondary 启动
- Secondary 也失败 → 从 Golden ROM 启动（仅能亮机+修复）

### 4.2 BMC 逃生机制

BMC 是整个服务器的"最后防线"，它的可靠性决定了所有上层逃生机制是否有效。

| 功能 | 逃生价值 |
|:-----|:---------|
| **独立供电** | 主机完全掉电时 BMC 仍能工作（通过 Standby Power） |
| **WDT 兜底** | OS 死机时 BMC 可强制重启/关机 |
| **SOL (Serial Over LAN)** | 主机无网络时仍可通过 BMC 查看控制台 |
| **FRU 保存** | 记录最后一次故障的状态、时间、错误码 |
| **Auto Recovery** | BMC 自身崩溃 → HW WDT 重启 BMC（~30秒） |
| **Graceful vs Forced** | 先尝试优雅关机（发 ACPI），失败后再强制断电 |

**BMC 逃生的反直觉设计**:

- BMC 不应该太"聪明"——过度智能的 BMC 引信逻辑可能掩盖真实问题
- 最佳实践：BMC **记录但不干预**是关键约束——自动重启策略需要可配置、可关闭

### 4.3 CPLD/FPGA 级逃生

在大规模 GPU 服务器中，CPLD 负责 power sequencing 和复位管理。

```text
CPLD 逃生典型场景:
+- 过温报警 -> CPLD 逐级降频 ---> 降频无效 -> 先关闭非关键模块
+- GPU 心跳丢失 -> CPLD 触发该 GPU 的 PERST# -> 重启 GPU
+- 12V 跌落 -> CPLD 关闭非关键负载 -> 保护 CPU/GPU 供电
+- 整机柜紧急下电 -> CPLD 按优先级顺序关机
```

**关键指标**: CPLD 从检测到故障到执行保护动作的延迟通常要求在 **10μs-1ms**。

## 5. 操作系统级逃生与恢复

### 5.1 Linux Kernel 的逃生机制

| 机制 | 触发条件 | 执行动作 |
|:-----|:---------|:---------|
| panic | 不可恢复内核错误 | 打印 Oops → 同步磁盘 → 触发 kdump → 重启 |
| kdump | panic 自动触发 | 保留 crash dump → 内核 mini 启动 → 写入磁盘 |
| OOM killer | 内存耗尽 | 选择并杀死得分最高的进程 → 释放内存 |
| hung_task_detector | 任务卡住 >120s | 打印调用栈 → 可选重启 |
| lockup_detector | 软/硬锁死 | 打印调用栈 → 可选择 panic |
| MCE handler | CPU/内存硬件错误 | 标记故障页面/CPU → 杀死受影响进程 |

### 5.2 crash dump 分析体系

```text
故障发生 -> kernel panic -> kdump 启动 -> /var/crash/ 保存
                  v
         开发人员分析 vmlinux + vmcore
                  v
         找到根因 -> 修复 -> 发布新版本
```

**服务器产品中的升级版**:

- BMC 在 kdump 期间持续监控：如果 kdump 卡住 → BMC 发起硬复位
- /var/crash/ 同时写入 BMC 的持久化存储 → 即使 OS 盘损坏也可读取
- 大型集群中：crash dump 自动上传到分析服务器 → AI 辅助分析

### 5.3 systemd 故障处理链

现代 Linux 用 systemd 管理服务，提供了比 init.d 更丰富的逃生控制：

```text
Service Crash -> systemd watchdog timeout ->
    +-- Restart=on-failure (默认重试3次)
        +-- 3次失败 -> StartLimitAction=reboot-force
            +-- 仍然失败 -> 进入 emergency mode
```

**服务器调优建议**:

- 关键服务 (如 vLLM, NCCL) → Restart=no（不自动重启，让编排器决定）
- 基础设施服务 (如 sshd, rsyslog) → Restart=always
- 守护进程 (如 health check agent) → Restart=on-failure + WatchdogSec=30s

## 6. 应用与中间件级容错

### 6.1 经典容错模式

| 模式 | 原理 | 服务器场景示例 |
|:-----|:-----|:-------------|
| **超时 (Timeout)** | 超过预期时间视为失败 | NCCL AllReduce 超时 → 触发 fault tolerance |
| **重试 (Retry)** | 失败后自动重新执行 | GPU 显存申请失败 → 等待后重试 |
| **退避 (Backoff)** | 重试间隔指数增长 | NCCL 建连失败 → 100ms → 200ms → 400ms |
| **熔断 (Circuit Breaker)** | 连续失败后暂停请求 | SSD IO 连续超时 → 熔断 30 秒后恢复 |
| **舱壁 (Bulkhead)** | 隔离资源池，防止故障蔓延 | 每个 GPU 独立内存池，OOM 只影响该 GPU |
| **降级 (Graceful Degradation)** | 关闭非关键功能维持核心 | 推理降级为 batch_size=1 避免 OOM |
| **健康检查 (Health Check)** | 定期检查服务状态 | /healthz 端点 + readiness probe |
| **预热 (Warm-up)** | 预加载防止冷启动 | GPU 推理预热 → 显存预分配 |

### 6.2 Graceful Shutdown 的信号协议

```text
SIGTERM -> 进程执行清理 -> 保存状态 -> 关闭连接
    v 超时 10s
SIGQUIT -> 强制 dump 堆栈
    v 超时 5s
SIGKILL -> 强制终止（无清理）
```

**服务器场景的标准协议**:

1. K8s Pod 收到 SIGTERM → 停止接受新请求
2. 处理完进行中的请求（最大等待 30s）
3. 保存 KV Cache/模型权重到持久存储
4. 关闭 NCCL 连接
5. 通知编排器自己已下线
6. 退出

### 6.3 内存故障处理（服务器特有）

服务器 DDR5/GDDR/HBM 的内存错误率远高于消费级：

| 等级 | 处理方式 | 延迟影响 |
|:-----|:---------|:--------:|
| CE (Correctable Error) | 自动纠正，记录历史 | 无 |
| CE > 阈值 | 触发 Page Offline 请求 | 无（页面替换在后台） |
| UE (Uncorrectable Error) | POISON 机制 → 触发 MCE | 该进程被 SIGBUS 杀死 |
| 多 UE > 阈值 | 系统 panic | 恢复需要重启 |

## 7. AI 训练/推理集群特有故障恢复

### 7.1 训练故障：万卡集群的核心难题

万卡集群的平均故障间隔时间 (MTBF) 在 **数小时到数天** 级别，远低于单次训练任务所需时间（数周）。

| 故障类型 | 占比 | 典型故障源 | 逃生/恢复方式 |
|:---------|:----:|:-----------|:-------------|
| GPU 硬件 (HBM ECC) | ~40% | HBM CE 累积 → UE | GPU 置为 faulty → 拓扑缩减 |
| 网络 (NCCL) | ~25% | 链路抖动、RoCE PFC 死锁 | NCCL Fault Tolerance → 重连 |
| 存储 (Checkpoint) | ~15% | NFS/Ceph 延迟抖动 | 分布式 checkpoint → 本地 + 远端 |
| CPU/内存 | ~10% | host OS 宕机 | Pod 调度到其他节点 |
| 软件/应用 | ~10% | Python OOM、CUDA error | 容器重启 + 最近 checkpoint 恢复 |

**NCCL Fault Tolerance 机制**:

```text
训练开始 -> NCCL 建连（指定 rank 拓扑）
    +-- 正常 -> 持续训练，定期 checkpoint
    +-- GPU 故障 -> NCCL 检测到 rank 丢失
    |       +-- 拓扑缩减 (Topology Shrinking)
    |           +-- 方案 A: 移除故障 GPU，重建更小的集合
    |           +-- 方案 B: 替换到预留的热备 GPU
    |           +-- 方案 C: 通知框架从 checkpoint 恢复
    +-- 网络分区 -> NCCL 超时告警
            +-- NCCL 重试 (3次) -> 失败后通知框架
```

**Wait 和 NCCL_TIMEOUT 的关系**:

- 不是"等待越久越好"——超时时间内所有 GPU 被占用，不能做其他事
- 也不是"超时越快越好"——误判临时拥塞为永久故障
- 调优经验：NCCL_TIMEOUT = 训练一个 iteration 的时间 × 3~5

### 7.2 CMX/KV Cache 故障恢复

CMX 作为共享 KV Cache 存储，故障恢复比传统存储更特殊。

| 故障场景 | 影响 | 逃生/恢复机制 |
|:---------|:-----|:-------------|
| CMX JBOF 单 SSD 故障 | 部分 KV Block 不可读 | DOCA Memos 允许丢失 → LLM 重新计算丢失内容 |
| CMX JBOF 整机故障 | 该机所有 KV Block 丢失 | Dynamo 调度器感知 → 重建未完成的 session |
| CMX 网络延迟升高 | TTFT 抖动 | 推理节点降级为 GPU-only（跳过 CMX 查询） |
| BF4 DPU 故障 | 该 Compute DPU 连接的 GPU 失去 CMX 访问 | Dynamo 将该 GPU 移出服务池 |
| Spectrum-X 拥塞 | CMX 读写延迟异常 | DCQCN → CNP 反压 → CMX 请求降速 |

**DOCA Memos "允许丢失"原则的实际意义**:

- 不是"系统可以丢数据"，而是"LLM 可以重新计算丢失的 KV"
- 这从根本上简化了故障恢复：不需要 RAID、不需要副本
- 代价是：丢失 block 对应的请求需要额外 prefill 计算

### 7.3 推理场景的优雅降级

| 降级级别 | 条件 | 动作 | 用户体验影响 |
|:---------|:-----|:-----|:-----------|
| L0 正常 | 一切正常 | 满规格服务 | 无感知 |
| L1 降级 | CMX 不可用 | 跳过 KV Cache 查询，用 GPU HBM | TTFT 略增 |
| L2 降级 | GPU 可用显存 < 阈值 | 降低 batch_size | 吞吐下降 |
| L3 降级 | GPU 温度 > 阈值 | 降频运行 | TPOT 增加 |
| L4 熔断 | 连续请求失败 | 停止接受推理请求 | 该节点不可用 |
| L5 逃生 | 即将 OOM | graceful shutdown | 该节点下线 |

### 7.4 Checkpoint 策略

| 场景 | Checkpoint 频率 | 存储目标 | 恢复时间 |
|:-----|:--------------:|:---------|:--------:|
| 训练 (小规模 < 100 GPU) | 每 30min-1h | NFS + 本地 | 5-15 min |
| 训练 (大规模 > 1000 GPU) | 每 1-2h | 高速分布式存储 | 30-60 min |
| 推理 (大模型) | 不 checkpoint | 无（直接从模型权重加载） | - |
| 推理 (CMX KV Cache) | 异步持久化 | CMX JBOF | 无中断（丢失部分重新计算） |

**异步 checkpoint (Async Save) vs 同步 checkpoint (Sync Save)**:

- Sync: 所有 GPU 同时暂停计算 → 保存 → 继续 → **训练效率损失 5-15%**
- Async: 保存期间 GPU 继续计算 → 只复制要保存的内存 → **损失 < 3%**
- 风险: Async Save 保存的快照可能不是完全一致的 → 需要 rollback 到上一个 sync checkpoint

## 8. 数据中心级应急响应

### 8.1 供电层逃生优先级

当数据中心供电出现故障时，系统必须**按优先级有序下电**：

```text
          供电故障发生
               |
     +---------+---------+
     | UPS 切换 (0-10ms) | <- 柴油发电机启动 (10-30s)
     +---------+---------+
               |
     +---------v---------+
     | Stage 1: PSU Hold | <- 20-30ms 窗口，系统准备
     +---------+---------+
               |
     +---------v---------+
     | Stage 2: 电池持续  | <- UPS 维持 5-30 min
     | (根据容量)         |
     +---------+---------+
               |
     +---------v---------+
     | Stage 3: 优雅关机  | <- 按优先级:
     |                    |   P0: 网络/存储 -> P1: 推理 -> P2: 训练
     +---------+---------+
               |
     +---------v---------+
     | Stage 4: 柴油机就绪 | <- 恢复供电 -> 按逆序上电
     +-------------------+
```

### 8.2 散热故障逃生

| 散热故障 | 信号 | 逃生路径 |
|:---------|:-----|:---------|
| 单个风扇故障 | Tach 信号丢失 | PSU 风扇分担 → 性能降级标志 |
| 多风扇故障 (N+1 被突破) | 过温预警 | 降频运行 → 温度继续上升 → 关机 |
| CDU (液冷) 故障 | 冷却液流量/温度异常 | GPU 降频 → 紧急排液 → 整机关机 |
| 机柜级冷却故障 | 机柜入口温度 > 阈值 | 整机柜切到风冷 → 若仍有故障则逐层关机 |
| 机房空调故障 | 机房温度 > 30°C | 电源先于散热受影响 → PSU 效率下降 → 降载运行 |

**液冷系统的特别之处**:

- 液冷故障到 GPU 过温有更大的热惯性（数分钟 vs 风冷数十秒）
- 但液冷泄漏会造成二次伤害（短路、腐蚀）
- 逃生设计：泄漏检测传感器 → 通知上游 CDU 停止该支路供液 → 关机

### 8.3 网络分区逃生

| 分区类型 | 检测方式 | 逃生方案 |
|:---------|:---------|:---------|
| NCCL 通信断裂 | NCCL 超时 | 拓扑缩减 |
| CMX 存储网络不可达 | CMX API 超时 | 降级为 GPU-only 推理 |
| 管理网络断开 | BMC heartbit 丢失 | 自动重启 → 恢复管理网络 |
| 互联网断开 | 外部健康检查 | 内部服务正常，外部不可达 |

## 9. 应急处理方案体系

### 9.1 事件分级与响应时间

| 等级 | 定义 | 响应时间 | 负责人 | 通知对象 |
|:-----|:-----|:--------:|:-------|:---------|
| **P0** | 核心服务完全中断（所有推理请求不可用） | <5 min | On-call + 技术负责人 | CTO/VP |
| **P1** | 部分功能不可用或严重降级（>50% 请求受影响） | <15 min | On-call + 模块负责人 | 部门总监 |
| **P2** | 非关键功能故障或少量用户受影响（<10%） | <1h | 模块维护人员 | 团队 leader |
| **P3** | 非紧急故障，可等待下一个工作日 | <24h | 对应开发者 | 无需通知 |
| **P4** | 轻微异常，无用户影响 | 下个版本 | 产品经理排期 | 无需通知 |

Step 2: [执行动作]     <- 2 min
Step 3: [执行动作]     <- 5 min

### 恢复步骤 (故障解决后)

Step 3: [验证服务正常]

### 事后
- post-mortem 负责人: [姓名]

## 10. 应急与设计的联动——从事故到改进

### 10.1 联动的逻辑链

```text
事故发生
    |
    v
紧急修复 (止血)
    |
    v
根本原因分析 (RCA)  ------->  短期改进 (1-2周)
    |                                   |
    v                                   v
临时方案固化                       长期架构改进 (下一版本)
    |                                   |
    v                                   v
监控/告警增强 <--------------------- 设计文档更新
                                            |
                                            v
                                      知识库归档
                                            |
                                            v
                                      团队培训
```

**每条路径都是闭环**: 每个阶段都有可衡量的交付物和截止时间。

### 10.2 Post-mortem 的核心原则

**Blameless (不追责)**: 假设所有人都是在当时掌握的信息和约束下做出了最好的决策

| 坏的做法 | 好的做法 |
|:---------|:---------|
| "X 写了一段 bug 代码" | "没有 code review 覆盖这个边界条件" |
| "Y 没有及时处理告警" | "告警被淹没在 200 条日常告警中" |
| "Z 发布前没有测试" | "CI 流水线缺少该场景下的测试用例" |

**结构化的 Post-mortem 模板**:

```text
## Post-mortem: [标题]

日期: YYYY-MM-DD
影响时长: XX 分钟
影响范围: XXX

### 时间线
- 09:00 — 正常
- 09:15 — 首次告警 (XX 监控项)
- 09:17 — on-call 确认
- 09:22 — 定位到根因
- 09:35 — 执行逃生方案
- 09:40 — 服务恢复

### 根因分析 (5 Why)
1. 为什么服务挂了？
2. 为什么没有被自动恢复？
3. 为什么监控没有提前发现？
4. 为什么测试没有覆盖？
5. 为什么设计时没有考虑这个场景？

### 行动项

| # | 行动项 | 负责人 | 截止日期 | 状态 |
|:-:|:-------|:-------|:--------:|:----:|
| 1 | 修改设计增加边界检查 | A | D+7 | OPEN |
| 2 | 增加监控告警 | B | D+3 | OPEN |
| 3 | 更新 Runbook | C | D+2 | OPEN |
| 4 | 团队同步 | A | D+1 | OPEN |
```

### 10.3 Chaos Engineering 在服务器产品中的应用

**Chaos Engineering 不等于"随便搞破坏"**，而是有科学方法的故障验证。

| 层面 | 可注入的故障 | 验证目标 |
|:-----|:------------|:---------|
| GPU | HBM CE 注入、GPU hang | NCCL 容错能否正确触发 |
| 网络 | 丢包、延迟抖动、带宽限制 | RoCE 拥塞控制是否有效 |
| 存储 | NVMe 超时、写失败 | CMX 降级路径是否正确 |
| 电源 | PSU 故障注入、电压跌落 | BMC 电源管理策略是否响应 |
| 散热 | 风扇转速限制、入口温度升高 | 降频/关机阈值是否合理 |

**硬件 Chaos Engineering 的特殊性**:

- 软件可以随意注入故障（如 Chaos Mesh），硬件不行
- 硬件故障注入需要在**设计阶段预留测试接口**
  - BMC 应支持"模拟温度过高"的命令
  - CPLD 应支持"模拟 GPU 心跳丢失"的模式
  - NVMe 应支持"模拟 controller fatal"的测试模式
- 这要求在**设计阶段就考虑"如何测试逃生机制"**

### 10.4 从反脆弱到设计改进

每次事故都应该让系统更强：

```text
应急 -> 修复 -> 复盘 -> 改进 -> 验证 -> 归档
                                      |
                                      v
                           设计规范更新（预防同类问题）
                                      |
                                      v
                           下一代产品引入改进设计
```

**典型案例**:

- 某集群因 SSD 固件 bug 导致批量延迟抖动 → 增加了 NVMe Read Latency 监控 + SSD FW 版本校验（短期）→ 在下代 CMX 中引入了"慢盘自动隔离"机制（长期）
- 某集群因 NCCL 超时配置过短导致频繁误触发 → 调整超时参数（短期）→ 改为自适应超时（根据实际网络延迟动态计算，长期）

## 11. 中国研发团队特有的应急管理议题

### 11.1 组织文化差异

| 维度 | 海外 (硅谷) 典型实践 | 中国研发团队常见现状 | 优化方向 |
|:-----|:--------------------|:-------------------|:---------|
| Post-mortem | Blameless，关注系统缺陷 | 容易变成追责会 | 从"谁犯了错"转向"系统为什么允许犯错" |
| On-call 文化 | 被 on-call 视为正常职责 | 常被看作"额外负担" | on-call 计入绩效，有补偿机制 |
| 文档 | 事故记录详尽、公开 | 口头传递为主，文档遗漏 | 把文档作为事故处理的一部分 |
| 演练 | 定期 Game Day 演练 | 只在巡检前演练 | 纳入研发节奏，每年至少2次 |
| 改进落地 | 有追踪系统 (Jira/ Asana) | 会后容易不了了之 | 改进项必须有 owner + deadline |

### 11.2 特定的时间窗口

时间节奏分析文档已验证：中国研发团队应急存在特殊时间窗口。

| 时段 | 风险 | 原因 |
|:-----|:-----|:-----|
| **周五下午 16:00 后** | 发布导致周末加班 | 发布窗口必须在周四前 |
| **法定假日前一天** | 应急响应人员不足 | 提前安排假期值班表 |
| **周一上午 10:00 前** | 响应延迟 | 晨会/周会冲突 |
| **月末最后 3 天** | KPI 冲刺导致变更激进 | 锁定变更窗口，只接紧急故障 |
| **春节前 2 周** | 物流/供应商停止服务 | 提前备好备件和预案 |

### 11.3 "国庆献礼"与事故隐瞒的文化风险

- 重大节日前存在"稳定压倒一切"的压力 → 危险的故障被掩盖而非处理
- 掩盖的故障会在节后集中爆发 → 反而造成更大的事故
- **改进方向**: 建立"发现故障是功劳不是过错"的文化，用自动化检测代替人工报故障

### 11.4 国产化特殊场景的应急挑战

| 场景 | 挑战 | 应对策略 |
|:-----|:-----|:---------|
| 国产 GPU/GPGPU | 驱动不成熟，故障模式不透明 | 充分的故障注入测试，建立故障知识库 |
| 国产 SSD | 固件稳定性待验证 | 冗余设计 + 主动监控固件升级 |
| 国产交换芯片 | RoCEv2 兼容性问题 | 更保守的流控参数 + 充分的互通测试 |
| 国产 BMC (如 X-Diagnosis) | 功能不全 | 自研补充模块 + 开放的 IPMI/Redfish 适配 |

## 12. 规律总结与行动框架

### 12.1 七条普适规律

| # | 规律 | 说明 |
|:-:|:-----|:------|
| **1** | 逃生机制的可靠性与其依赖的层级数成反比 | 硬件 WDT > BMC WDT > OS WDT > 应用 timer |
| **2** | 逃生路径必须定期验证，否则等同于不存在 | 仅存在于设计文档中 = 报废 |
| **3** | 降级比熔断好，熔断比崩溃好 | 优先灰度降级，拒绝非此即彼 |
| **4** | 逃生后的状态保存决定了恢复速度 | 有序关机 + 保存最后一个 checkpoint → 秒级恢复 |
| **5** | 追责文化是应急体系最大的敌人 | 追责 → 隐瞒 → 更大事故 |
| **6** | 自动化 > Runbook > 人脑记忆 | 三级递减，70% 的故障应被自动化覆盖 |
| **7** | 应急改进的 ROI 随事故次数指数上升 | 第 3 次同类事故 ROI 是负的 → 必须从设计中根除 |
