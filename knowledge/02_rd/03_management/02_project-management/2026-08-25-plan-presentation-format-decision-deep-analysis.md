## 1. 结论概要

**一句话交付**：这不是"表格 vs 图形 vs 工具"的三选一，而是**三层分工**——**文档（表格路标）= 事实层**，承载"为什么这么排、依赖依据、风险缓冲"（知识资产，AI 可维护）；**项目管理工具 = 运行层**，承载"谁在做、做到哪、偏差多少"（可计算关键路径/浮动时间/资源负载，多人协作）；**图形化 = 呈现层**，按场景出图（甘特/里程碑/依赖网络），是汇报产物而非维护主载体。三者的关系是数据流：文档导出结构化数据 → 工具运行追踪 → 定期快照回档文档。

**5 条核心结论**：

1. **判据在"计划的活度"而非"美观度"**：计划若是一次性蓝图（对外沟通/立项评审），表格+图形足够；若是持续管控对象（151 项活动 × 14 个月 × 6 领域并行），文档表格无法支撑动态追踪，必须引入工具。超节点项目**已越过阈值**——151 项 WBS、3 条 CPM 关键路径、硬性时间门（2026-12/2027-01/2027-03）[来源: 08-25 WBS §1]，手工无法维护其网络图的浮动时间与资源冲突 [来源: PMBOK 7th CPM 方法]。

2. **工具的核心价值不是"画甘特图"，而是可计算性 + 动态性 + 协作性**：甘特图只是输出形式之一；真正不可替代的是①关键路径/浮动时间自动计算（151 项依赖网络手算不可能）、②状态每日更新（文档是静态快照）、③多人并发更新（文档是单人维护）。这三点决定"执行管控"必须工具化。

3. **文档层不可被工具替代，因为工具只记"是什么"，不记"为什么"**：现有 10+ 篇计划文档的价值在于决策依据（依赖理由/风险缓冲/口径定义/来源标注/Changelog 演进），这是知识资产，评审、审计、复盘、新人交接都要回文档。工具的定位是"运行台账"，文档的定位是"决策账本"——两层并存，互为引用。

4. **工具选型优先级：飞书项目 > ProjectLibre > MS Project**（针对本团队场景）：用户渠道为飞书，飞书项目与飞书文档/日历打通，团队协作成本最低 [来源: 飞书项目官方能力]；ProjectLibre 免费开源且兼容 .mpp，适合单人起步做专业 CPM 计算 [来源: ProjectLibre 官方]；MS Project 仅在需要对外正式交付 .mpp 文件时启用（业界标准格式）[来源: MS Project 官方]。Jira 仅当研发团队已有 Jira 基建时复用。

5. **落地最小路径：先做"关键路径 + 里程碑"轻量录入（约 50~60 项），不录全量 151 项**：录入全量 WBS 的维护成本高且易烂尾（见 §7.1）；只录入①3 条关键路径上的活动、②11 个 M 里程碑、③5 个产品节点（CDR/EVT1/EVT2/DVT/PVT）与 14 Gate、④三个硬性时间门基线，即可获得 80% 管控价值。全量 WBS 仍以文档表格为 SSOT，按需增量录入。

## 2. 问题重构：呈现决策的第一性原理

### 2.1 计划的本质：任务 × 时间 × 依赖 × 资源四元约束网络

从第一性原理看，任何项目计划都是同一个东西的实例化：

```
PLAN = f( TASK, TIME, DEP, RES )

  TASK  : deliverable activity units (WBS leaf nodes)
  TIME  : duration, start/end, milestones
  DEP   : predecessor/successor links (DAG, defines critical path)
  RES   : people / material / equipment / budget (GPU 8-16wk lead time)
```

- KLX-512 的实例：151 项 TASK [来源: 08-25 WBS §2.1]、14 个月 TIME（2026-09~2027-10）[来源: 08-20 项目总计划]、四批次交付链 + 3 条 CPM 关键路径 DEP [来源: 08-25 整合视图 §4]、GPU 8~16 周交期 + 液冷/800V 供电前置 RES [来源: 08-14 里程碑 §2.2/§6]。

**关键推论**：呈现方式之争，本质是"这个四元约束网络要编码成什么载体、服务于什么使用频率"。**使用频率是分水岭**——网络是静态的（表达一次）还是动态的（持续演进）？

### 2.2 呈现的本质：陈述式编码 vs 计算式编码

所有呈现载体可归为两种编码范式：

| 范式 | 载体 | 回答的问题 | 本质 |
|:-----|:-----|:-----------|:-----|
| **陈述式编码** | Markdown 表格、Excel、ASCII 图、Mermaid 图 | "计划长什么样？为什么这样排？" | 表达（表达既定事实） |
| **计算式编码** | ProjectLibre / MS Project / 飞书项目 / Jira | "如果 X 延迟会怎样？谁在关键路径上？资源够吗？" | 运行（推演与追踪） |

- 陈述式编码的产物是**快照**（snapshot）：某个时点计划的样子。优点：信息密度高、可审阅、可归档、AI 可生成；缺点：**不可反推**——表格里看不出"某任务浮动时间 3 周"这种二阶信息，因为二阶信息要从依赖网络算出来。
- 计算式编码的产物是**模型**（model）：计划的结构化表示。优点：可反推任意问题（what-if、关键路径、浮动时间、基线偏差）；缺点：录入维护成本高、工具依赖。

**结论**：文档表格不是"低配版甘特图"，而是与工具**不同性质**的载体。文档答"是什么/为什么"，工具答"会怎样/进行到哪"。问题不该是"哪个更好"，而是"我的使用场景需要哪种编码"。

### 2.3 关键洞察：工具的核心价值不是"画图"而是可计算性

业界常误以为"用 Project = 画专业甘特图"。这是对工具价值的最大误解。甘特图只是工具的一种输出视图，且 2026 年的文档工具（Mermaid Gantt）也能画。工具真正不可替代的三项能力：

1. **可计算性（CPM 引擎）**：151 项依赖网络，关键路径、每项活动的浮动时间（float/slack）、资源冲突检测、工期压缩（crash）分析——这些是网络图上的**算法结果**，任何静态表格/图形都无法承载。KLX-512 的三条关键路径 [来源: 08-25 整合视图 §4] 在文档里是"算好的结论"，在工具里是"随时可重算的活数据"——当 GPU 选型推迟 2 周（D0-1 未决 [来源: 08-25 WBS §1 结论4]），工具能立刻告诉你 EVT2 是否被波及、浮动时间还剩多少。

2. **动态性（状态更新 + 基线对比）**：计划是活的。每日/每周状态更新（完成/进行/延迟），工具自动生成"计划 vs 实际"偏差，基线（baseline）冻结后任何偏移可追溯。文档的 Changelog 只能记录"我改了什么"，工具能记录"实际比计划差了多少周、发生在哪条链"。

3. **协作性（多人并发 + 权限 + 通知）**：六领域（系统/硬件/固件/软件/测试/施工部署）各有负责人 [来源: 08-25 多领域 §1.3]，执行状态的更新只能由各领域 owner 自己维护，PM 汇总。文档体系下这是"6 人改一个 md 文件"的灾难；工具体系下是天然的多人在线更新。

### 2.4 文档的不可替代价值：知识资产而非展示道具

对应地，文档层有三项工具无法替代的价值，决定它必须保留：

1. **决策依据（Why 层）**：工具记录"任务 A 在 10 月 15 日、工期 3 周、前置 B"，但**不会记录**"为什么 A 排在 B 之后——因为 GPU 选型冻结是散热形态/柜施工方案/网卡型号的连锁解锁点 [来源: 08-25 WBS §1 结论4]"。这份"为什么"才是评审、争议仲裁、复盘、新人交接时的依据。
2. **可追溯性（来源 + 演进）**：文档有来源标注（[来源: xxx]）、交叉链接、Changelog；工具只有当前状态。审计场景（"这个时间点当初是谁定的、依据哪份材料"）只能回文档。
3. **持久性（不依赖工具生命周期）**：知识库是永久资产；项目管理工具可能换供应商、停服、账号失效、数据迁移丢失。文档是"永不失效的归档层"。

> **一句话**：工具是"运行台账"（现在进行时），文档是"决策账本"（完成时+原因）。两者关系不是替代，是互补——**工具数据源自文档导出，文档定期吸收工具快照**（§6.2）。

## 3. 四种呈现方式的 MECE 对比

### 3.1 四种方式定义与谱系

按"编码范式 × 载体"划分，计划呈现有四种典型方式（MECE 互斥）：

| 方式 | 载体 | 编码范式 | 典型形态 |
|:-----|:-----|:---------|:---------|
| **A 表格路标** | Markdown/Excel 表格 | 陈述式 | WBS 表（编号/任务/工期/前置/里程碑/责任域）、里程碑时间表 |
| **B 图形化呈现** | 文档内嵌图 | 陈述式 | ASCII 甘特图、时间轴图、泳道图、依赖网络图（如 08-25 整合视图 §5.3 双坐标系甘特） |
| **C 文档内甘特代码** | Mermaid/PlantUML | 陈述式（半计算） | ```mermaid gantt``` 代码块，渲染为图 |
| **D 专业项目管理工具** | ProjectLibre / MS Project / 飞书项目 / Jira | 计算式 | 动态甘特、网络图、关键路径高亮、基线对比 |

> 注：C 介于 A/B 与 D 之间——Mermaid gantt 有语法上的"依赖"声明（`after :t1`），但渲染结果仍是静态图，无法计算浮动时间，故归入陈述式。

### 3.2 八维度对比矩阵

| 维度 | A 表格路标 | B 图形化呈现 | C Mermaid 甘特 | D 专业工具 |
|:-----|:----------:|:------------:|:--------------:|:----------:|
| **信息容量**（能装多少细节） | ★★★★★ 密度最高，任意字段可加 | ★★☆ 一图胜千言但细节有限 | ★★☆ 只适合 <40 项概览 | ★★★★ 字段模型化，容量大但录入累 |
| **可计算性**（CPM/浮动/资源） | ✗ 无 | ✗ 无 | ✗ 无（仅语法级依赖） | ★★★★★ 核心价值 |
| **动态性**（状态更新支撑） | ✗ 静态快照 | ✗ 静态快照 | ✗ 静态快照 | ★★★★★ 每日更新+基线对比 |
| **协作性**（多人并发） | ✗ 单文件冲突 | ✗ 无 | ✗ 无 | ★★★★★ 多人在线+权限+通知 |
| **可追溯性**（为什么/来源/历史） | ★★★★★ 来源标注+Changelog | ★★★☆ 图内可注来源 | ★★☆ 代码块难注来源 | ★★☆ 只有状态，无"为什么" |
| **维护成本**（AI 可维护性） | ★★★★★ AI 直接生成/更新 | ★★★☆ AI 可生成 ASCII | ★★★☆ AI 可生成但渲染依赖工具 | ★★☆ 人工录入为主，AI 只能辅助导入 |
| **工具生态**（导入导出/兼容） | ★★★★ CSV/JSON 通用 | ★★☆ 图不可复用 | ★★★ 可转图导出 | ★★★★★ mpp/CSV/API |
| **场景适配** | 文档沉淀/审阅/归档/知识库 | 汇报/概览/评审讲解 | 汇报（轻量甘特） | 执行管控/周例会/团队协作 |

**读表结论**：
- A 和 D 是**两极**：A 在"信息容量/可追溯/维护成本"胜出，D 在"可计算/动态/协作"胜出——正好互补。
- B 和 C 是**辅助层**：解决"给人看"的问题，不解决"给人用"的问题。它们的正确位置是 A/D 的**输出视图**（从表格或工具生成图），而不是独立维护的载体。
- 任何试图"用表格/图形模拟工具功能"的做法（如在 Excel 里手算关键路径、在 Mermaid 里维护 151 项）都是把计算式需求硬塞进陈述式载体，必然失败。

### 3.3 各方式的典型适用场景

| 场景 | 推荐方式 | 理由 |
|:-----|:---------|:-----|
| 立项评审/方案汇报（一次性） | B + A | 图形抓眼球、表格给细节，一次性使用无需工具 |
| 知识库深度文档沉淀 | A（为主）+ B（配图） | 决策依据+可追溯，AI 可维护 |
| 周例会进度追踪 | D（工具视图） | 实时状态+偏差对比，唯一能支撑"进度 vs 计划"的载体 |
| 里程碑达成汇报 | B（里程碑图）+ D 导出 | 图形化呈现成果，数据来自工具 |
| 跨团队协作（六领域 owner 各自更新） | D | 多人并发更新的唯一可行载体 |
| 对外正式交付计划文件（.mpp） | D（MS Project） | 业界标准格式，客户/合作方可打开 |

## 4. 判定决策树：三个问题定方案

### 4.1 Q1：一次性蓝图还是持续管控对象

- **一次性蓝图**（立项、对外沟通、方案评审）：计划定完就不再变 → **A+B 足够**，工具是负担。典型：3 年技术路标 [来源: 07-29 3年路标文档]、对外方案。
- **持续管控对象**（项目执行期，状态每周变、偏差要追踪）：→ 进 Q2。

### 4.2 Q2：是否需要可计算能力

判断标准（业界经验阈值，需 PM 校准）：

| 指标 | 阈值 | 超过即需要工具 |
|:-----|:-----|:--------------|
| 活动总数 | >50 项 | 依赖网络超出人工可维护范围 |
| 依赖网络复杂度 | 存在 >3 层嵌套依赖 | 关键路径无法目测 |
| 并行领域数 | >3 个 | 跨领域协调依赖共同时间基准 |
| 硬性时间约束 | ≥2 个（客户/供应链/政策强约束） | 需要基线管理+偏差预警 |
| 资源竞争 | 存在共享稀缺资源（如 GPU 板 EDA 人力） | 需要资源负载检测 |

- KLX-512 实测：151 项 / 四批次链+3 条 CPM / 6 领域 / 3 个硬性时间门 → **五项全超**，明确需要工具。
- ≤50 项且依赖简单 → A+B 足够，工具收益<成本。

### 4.3 Q3：谁维护、是否团队协作

- **单人维护 + 不上协作平台** → **ProjectLibre**（免费开源、本地、完整 CPM、兼容 .mpp）[来源: ProjectLibre 官方]。
- **团队协作 + 公司已有办公生态** → 选与办公生态打通的工具：飞书项目（飞书生态）/ Teambition（钉钉/阿里系）/ Jira（研发流程）。
- **对外正式交付 .mpp** → MS Project（业界标准格式）。

## 5. 专业项目管理工具选型对比

### 5.1 五款工具横向对比

| 维度 | 飞书项目 | ProjectLibre | MS Project | Teambition | Jira |
|:-----|:---------|:-------------|:-----------|:-----------|:-----|
| **CPM 关键路径** | ✅ 甘特+依赖+里程碑 | ✅ 完整（网络图/浮动时间） | ✅ 业界最全 | ✅ 甘特+依赖 | ⚠️ 高级路标部分支持 |
| **资源负载检测** | ⚠️ 基础 | ✅ 完整 | ✅ 完整 | ⚠️ 基础 | ❌ 弱 |
| **协作** | ✅✅ 多人在线+@+审批 | ❌ 单机 | ⚠️ 需 Project Server/Online | ✅✅ 多人在线 | ✅✅ 研发流程集成 |
| **生态打通** | ✅✅ 飞书文档/日历/IM | ❌ 无 | ⚠️ Office 系 | ✅ 钉钉/阿里系 | ✅ 研发工具链 |
| **成本** | 免费版+付费版 | 免费开源 | 付费（订阅制） | 免费版+付费版 | 付费（按用户） |
| **格式兼容** | 导出 CSV/Excel | ✅ 读写 .mpp | ✅ .mpp 标准 | 导出 CSV | API/CSV |
| **学习成本** | 低（飞书用户零门槛） | 中（桌面软件） | 高（专业软件） | 低 | 中高 |
| **适合场景** | 团队协作 + 飞书生态 | 个人专业计算/起步 | 对外正式交付 | 阿里系团队 | 已有 Jira 的研发团队 |

**关键事实**：用户当前通过飞书渠道协作（渠道=feishu），飞书项目与飞书文档、日历、IM 原生打通，团队协作的"零迁移成本"优势显著 [来源: 飞书项目官方能力说明]。

### 5.2 选型原则与组合策略

1. **工具选型的本质是选"团队的协作基础设施"，不是选"画图软件"**：团队已在用的办公生态（飞书/钉钉/OA）决定了工具首选——协作工具的价值在"大家本来就在上面"。
2. **组合策略（推荐）**：
   - **日常运行**：飞书项目（团队协作、周例会、状态更新）
   - **专业计算**：ProjectLibre 可做补充（复杂 CPM/资源分析），或直接信任飞书项目的甘特+依赖
   - **对外交付**：必要时导出 .mpp（飞书项目可导出 Excel → 再转 .mpp 或直接出图）
3. **避免工具叠罗汉**：同时维护两套以上专业工具 = 双倍录入成本。选一套主工具，其余按需临时启用。

## 6. 超节点项目落地建议：三层分工架构

### 6.1 三层架构总览

```
+--------------------------------------------------------------+
| LAYER 3  PRESENTATION (graphics, on-demand)                   |
|   milestone chart / gantt view / dependency network           |
|   generated from L2 tool data or L1 doc tables, per scenario  |
+--------------------------------------------------------------+
| LAYER 2  RUN LEDGER (tool = Feishu Project recommended)       |
|   key-path tasks + milestones + baselines + status + owners   |
|   weekly update by domain owners, CPM auto-recalc             |
+--------------------------------------------------------------+
| LAYER 1  FACT SSOT (knowledge base docs, A+B)                 |
|   10+ deep docs: WHY / DEP reasons / risk buffers / sources   |
|   WBS 151-item table, milestone strategy, gate definitions    |
+--------------------------------------------------------------+
        DATA FLOW:  L1 docs --export CSV--> L2 tool
                    L2 tool --snapshot--> L1 docs (periodic)
```

| 层 | 载体 | 内容 | 更新频率 | 维护者 |
|:---|:-----|:-----|:---------|:-------|
| **L1 事实层** | 知识库 10+ 篇文档（表格路标为主） | 决策依据/依赖理由/风险缓冲/口径/来源 | 变更时（AI 辅助） | AI + 用户 |
| **L2 运行层** | 飞书项目（或 ProjectLibre 起步） | 关键路径活动/里程碑/基线/状态/owner | 每日（owner 更新） | 六领域 owner |
| **L3 呈现层** | 按场景出图 | 甘特/里程碑/依赖网络 | 汇报时 | PM（工具导出） |

### 6.2 数据流设计：文档 → 结构化导出 → 工具 → 快照回档

```
STEP 1  EXPORT   WBS 151-item table (08-25 WBS doc) -> CSV/JSON
                 columns: id, task, domain, duration, depends_on,
                          milestone, owner, deliverable
STEP 2  IMPORT   CSV -> Feishu Project / ProjectLibre
                 build dependency network from depends_on column
                 set milestones (M1-M11 + CDR/EVT1/EVT2/DVT/PVT)
STEP 3  RUN      weekly status updates by owners, CPM auto-recalc
                 baseline freeze, deviation alerts (hard gates)
STEP 4  SNAPSHOT monthly / per-milestone: export tool view ->
                 archive into knowledge doc (appendix or update)
                 -> keeps doc layer current even if tool is lost
```

- **防呆设计**：L2 工具数据丢失/停服时，L1 文档仍保有最近一次快照 + 全部决策依据——知识库是"永不失效的归档层"（§2.4）。
- **双写规避**：L1 文档不逐项跟踪状态（状态只活在 L2）；L2 工具不记录"为什么"（原因只活在 L1）。各写各的，不重叠。

### 6.3 最小可行录入范围：关键路径 + 里程碑

**不建议**一次录入全量 151 项（维护成本高、易烂尾，见 §7.1）。建议首批录入：

| 类别 | 内容 | 数量（约） | 数据源 |
|:-----|:-----|:----------:|:-------|
| 关键路径活动 | 3 条 CPM 路径上的活动（GPU 选型→散热→GPU 板→制板→回板 主链 + 另 2 条） | 25~30 | [08-25 整合视图 §4] |
| 里程碑 | M1~M11 + 产品节点 CDR/EVT1/EVT2/DVT/PVT | 16 | [08-25 整合视图 §5.4] |
| 硬性时间门 | 2026-12 批次1下单 / 2027-01 春节前批次3+固件 P0 / 2027-03 液冷供电就位 | 3 | [08-25 WBS §1 结论3] |
| 批次交付链 | 四批次（B1 PDB+FCB → B2 CPU → B3 SW → B4 GPU+FIO） | 4 | [08-25 单板交付 §5.2] |
| 跨领域关键交付物 | 领域 × 节点交付物矩阵中的核心项（每领域每节点 1~2 项） | 20~30 | [08-25 多领域 §3.1] |

**合计约 50~60 项**，覆盖 80% 管控价值（关键路径可算、里程碑可追踪、硬门可预警）；全量 WBS 仍以 L1 文档表格为 SSOT，需要时增量录入。

### 6.4 基线设置：三个硬性时间门

基线（baseline）冻结后，任何偏移自动预警。KLX-512 三个硬门 [来源: 08-25 WBS §1 结论3]：

| 硬门 | 时间 | 约束性质 | 失效后果 |
|:-----|:-----|:---------|:---------|
| G1 批次 1（PDB/FCB）下单 | 2026-12 前 | 供应链（春节前回板窗口） | 失去回板窗口，整体顺延 |
| G2 批次 3（SW 板）下单 + 固件 P0 冻结 | 2027-01 春节前 | 供应链+调试依赖 | 节后调试空转 |
| G3 液冷/正式供电就位 | 2027-03 前 | 设施（P4 整机集成前置） | P4 无法启动，EVT2 阻塞 |

> 工具中建议把 G1~G3 设为"里程碑+基线"，周例会首查这三项偏移（对应 [08-25 WBS §1 结论7] 的"周会三问"）。

### 6.5 同步机制：周例会双轨制

| 轨道 | 内容 | 载体 |
|:-----|:-----|:-----|
| **L2 轨道（工具）** | 各领域 owner 更新状态 → PM 看关键路径偏差/硬门预警/里程碑达成 | 飞书项目视图 |
| **L1 轨道（文档）** | 未决决策清单、风险缓冲、变更记录 → 决策依据更新 | 知识库文档 |

周例会只追三件事（[来源: 08-25 WBS §1 结论7]）：①未决决策到期（如 D0-1 GPU 选型）、②关键路径偏移（工具实时）、③Gate 通过。L1/L2 由 PM 桥接：工具暴露"偏差是什么"，文档回答"为什么偏差、怎么调"。

### 6.6 分阶段迁移路径

```
PHASE 0 (week 1)   ProjectLibre bootstrap (optional)
                   import WBS 151-item CSV, build DEP network,
                   verify CPM vs doc-stated 3 critical paths
PHASE 1 (week 2)   Feishu Project setup
                   create project, import key-path 50-60 items,
                   set M1-M11 + 5 product nodes + G1-G3 baselines
PHASE 2 (week 3+)  team onboarding
                   6 domain owners update status weekly,
                   PM reviews deviation in weekly meeting
PHASE 3 (per gate) snapshot back to docs
                   monthly / per-milestone export -> archive to KB
                   keep L1 doc layer current
```

> **为什么 Phase 0 可选**：若团队直接上飞书项目，可跳过 ProjectLibre；Phase 0 的价值是用免费工具先验证"文档里的 CPM 结论在工具里重算一致"——数据口径验证，不是必须步骤。

## 7. 反方观点与风险（诚实呈现）

### 7.1 工具烂尾风险

**风险**：项目管理工具的高失败率源于"录入一时爽、维护火葬场"——没有专职 PM 时，151 项的状态更新在 2~3 周后无人维护，工具变成僵尸数据，最终废弃。
**对策**：
- 最小录入（§6.3）只录 50~60 项关键项，把维护量压在可持续区间；
- 状态更新绑定周例会节奏（不是每日），六领域 owner 每人每周 ≤10 分钟；
- 明确"工具烂尾的止损线"：连续 2 周无更新 → 降级回 L1 文档模式，不硬撑。

### 7.2 文档与工具双写成本

**风险**：同一数据（任务/时间/状态）在两处维护，口径漂移（文档说 10 月、工具说 10 月中旬）。
**对策**：§6.2 数据流设计已划分边界——**L1 写"为什么/口径"，L2 写"状态/进度"**，唯一重叠的"时间点"以工具为准（L2 是运行时 SSOT），文档的"时间点"表述只做引用式更新（快照回档时同步）。

### 7.3 何时明确不需要工具

诚实地说，以下情况**不要**引入工具：
- 项目 <30 项活动、无并行领域、无硬性外部约束（表格完全够）；
- 项目只有决策者一人看、无团队协作（工具收益为零）；
- 团队无能力/无意愿维护工具（工具会成为负资产，比没有更糟）；
- 计划本身不稳定（还在频繁改范围阶段）——先文档，稳定后再工具化。

**对 KLX-512 的适用性**：151 项/6 领域/3 硬门/团队协作 → 明确需要工具；但**启动时机**可斟酌——若 GPU 选型（D0-1）未定、范围还在收敛，可先用 L1 文档承载，待计划相对稳定（预计 CDR 后）再工具化，避免"边改边录"的双重成本。

## 8. 结论

1. **回答原问题**：不是"图形化 vs 专业方式"、"表格 vs Project"的二选一，而是**三层分工**——表格路标（文档）= 事实层（为什么），专业工具 = 运行层（进行到哪），图形化 = 呈现层（给人看）。三者通过数据流衔接，缺一不可。

2. **判定条件已满足**：KLX-512 项目五项指标（>50 活动/深依赖/多领域/硬时间门/资源竞争）全超阈值，**需要引入专业工具**；工具选型优先飞书项目（渠道生态），ProjectLibre 作为免费验证起步，MS Project 仅对外交付用。

3. **落地最小路径**：先录关键路径 + 里程碑 + 硬门（50~60 项），不录全量 151 项；周例会双轨制（工具查偏差、文档答原因）；里程碑节点快照回档知识库——保持"工具可丢、文档永存"。

4. **启动时机建议**：GPU 选型（D0-1）未定前，计划仍在收敛期，可先维持 L1 文档模式；**CDR 后（选型冻结）再工具化**，此时依赖网络定型，录入一次到位，避免边改边录的双重成本。

5. **反方自查**：工具烂尾风险靠"最小录入 + 周会绑定 + 止损线"三道闸控制；双写成本靠"边界划分（L1 写为什么、L2 写状态）"控制；若团队最终无维护意愿，回归纯文档模式仍是可接受降级方案——文档层本就完整自洽。
