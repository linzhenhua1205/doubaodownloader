## §0 执行摘要

**问题**：需求已明确（超节点 POC 验证集群基本功能、获取 KV Cache 性能），研发活动如何组织？

**核心结论**（一句话）：研发活动管理 = **目标量化 × 分层解耦 × 依赖看板 × 同步机制 × 风险前置**——把"超节点目标"逐层翻译为"板卡/固件/软件/测试的交付契约"，用里程碑把多领域协同锁进同一节奏。

**五个关键机制**：

| # | 机制 | 一句话 |
|:-:|:-----|:-------|
| 1 | **目标量化** | POC 目标必须落到可验收数值（互联带宽、调度成功率、KV Cache tokens/s） |
| 2 | **分层解耦** | L0~L3 每层定义独立交付物+准出标准，层间只认"接口契约"不认"内部过程" |
| 3 | **依赖看板** | 6 类板卡 × 4 层组装 = 依赖矩阵，回板时间点是全局锚点 |
| 4 | **同步机制** | 固件/软件在回板前完成"虚拟联调"（模拟器/EVB/契约测试），回板即测 |
| 5 | **风险前置** | 长交期物料、bringup 延迟、互联异常三大风险在 W0 就位应对预案 |

**交付节奏**（假设 T0=2026-08-03，15 周）：W4 首板回板 → W6 单板验证 → W8 节点组装 → W10 整机柜集成 → W12 超节点互联 → W14 KV Cache 性能 → W15 POC 报告。

## §1 目标体系定义：POC 要验证什么

### 1.1 目标分层：基本功能 vs KV Cache 性能

POC 目标不是一句"验证超节点"，必须拆成**可验收的层次**：

```text
POC 目标树
+-- P0 集群基本功能（通过/不通过）
|   +-- P0.1 硬件连通性: 计算节点+交换节点+存储节点互联后拓扑正确
|   +-- P0.2 算力平台: 节点注册/资源上报/任务调度可用
|   +-- P0.3 运维平台: 固件批量上架成功、基本监控采集正常
|   +-- P0.4 整机柜管理: 电源/液冷管理生效、槽位信息识别正确
+-- P1 KV Cache 性能（量化采集）
    +-- P1.1 KV Cache 吞吐: 典型 LLM 推理场景 tokens/s
    +-- P1.2 显存/KV 容量: 可承载的最大 KV 规模（并发 × 序列长度）
    +-- P1.3 时延: TTFT / TPOT（首 token 时延 / 每 token 生成时延）
```

**关键原则**：P0 是"能跑通"，P1 是"跑多快"。P0 不过，P1 无意义；P1 是 POC 区别于"打通 demo"的价值所在（可对外量化交付）。

### 1.2 可验收的量化指标

| 指标 | 目标值（假设） | 验证方法 | 责任领域 |
|:-----|:--------------|:---------|:---------|
| 互联带宽达标率 | ≥ 90%（NCCL/ROCE 实测 vs 理论） | 带宽测试工具 | 测试 |
| 节点识别成功率 | 100%（机柜槽位→节点映射） | 运维平台界面核对 | 固件/运维 |
| 任务调度成功率 | ≥ 95%（100 次调度） | 算力平台压测 | 软件 |
| KV Cache 吞吐 | 基线值 + 对比单机 | 推理 benchmark（vLLM 等） | 软件/测试 |
| 固件批量上架成功率 | ≥ 98%（50 节点批量） | 运维平台实测 | 运维平台 |
| 电源/液冷管理 | 全部在位节点状态可读可写 | 管理面巡检 | 固件 |

> 目标值需在项目启动评审（W0）由各领域确认，**数值+基线+条件**三要素齐备才可进入执行（对齐 RULE.md 质量标准）。

## §2 系统分层架构与依赖关系

### 2.1 四层组装模型（L0~L3）

```text
L3 超节点 -------------------------------- 目标层: 集群功能 + KV Cache 性能
|   ^ 多个整机柜互联（复用已有整机柜）+
|   | 计算/交换/存储节点混合组网
|   | 算力平台调度 + 运维平台管理
+-- L2 整机柜 --------------------------- 集成层: 机柜级能力
|   ^ 节点 + 整机电源管理 + 液冷管理 +
|   | 机柜槽位信息识别（槽位->节点映射）
|   | （复用已有整机柜 -> 本层以集成验证为主）
+-- L1 节点 ----------------------------- 系统层: 节点级能力
|   ^ 计算节点（CPU板+GPU板）/ 交换节点 /
|   | 存储节点 —— 板卡装入节点机箱
+-- L0 板卡 ----------------------------- 部件层: 单板能力
    ^ CPU板 / GPU板 / 电源板 / Expander板
      / 风扇控制板 / BMC板卡
```

**每层的准出标准（交付契约）**：

| 层 | 交付物 | 准出标准（出口条件） | 主要责任领域 |
|:--:|:-------|:---------------------|:-------------|
| L0 | 单板（含固件） | bringup 通过、功能齐全、可支撑节点组装 | 硬件+固件 |
| L1 | 节点 | 单板互连正常、节点可启动、管理面可见 | 硬件+固件+测试 |
| L2 | 整机柜 | 电源/液冷/槽位识别正常、节点全部在位 | 系统集成 |
| L3 | 超节点 | 集群功能 P0 全过、KV Cache 性能 P1 采集完成 | 软件+测试 |

### 2.2 层间依赖矩阵：谁的输出是谁的输入

| 下游层 | 依赖的上游输出 | 关键时间约束 |
|:-------|:--------------|:-------------|
| L1 节点组装 | L0 各类板卡 + 对应固件 bringup 版 | **板卡回板时间点**是全局锚点 |
| L2 机柜集成 | L1 计算/交换/存储节点 | 节点验证通过后进入 |
| L3 超节点互联 | L2 整机柜 + 交换节点 + 存储节点 | 互联联调窗口 |
| 算力平台 | L2/L3 节点可被管理面发现 | 与 L2 集成并行开发，虚拟联调 |
| 运维平台 | 固件批量接口 + 节点管理接口 | 与固件开发同步定义接口契约 |

**核心洞察**：系统级项目最大的管理难点不是单板，而是**依赖的级联放大**——L0 任一板卡延迟 2 周，经 L1→L2→L3 传导可能放大为 POC 整体延迟 4~6 周。因此管理重心在"**层间契约早冻结 + 上游风险早暴露**"。

## §3 单板组成与复用矩阵

### 3.1 六类板卡清单

| 板卡 | 在系统中的作用 | 关键特性（假设） | 固件需求 |
|:-----|:--------------|:----------------|:---------|
| **CPU 板** | 计算节点主控，运行 OS/算力平台 Agent | CPU 型号、内存拓扑、PCIe 出口 | BIOS + BMC + CPLD |
| **GPU 板** | 算力核心，承载 KV Cache 推理 | 显存容量、HBM 带宽、互联口（NVLink/PCIe） | GPU VBIOS + 散热管理 |
| **电源板** | 供电（PSU→板级 VR） | 功率、效率、时序 | CPLD 时序 + PMBus 监控 |
| **Expander 板** | 存储扩展（PCIe/NVMe 扇出） | 通道数、拓扑 | CPLD + 管理 |
| **风扇控制板** | 风冷/液冷联动散热 | PWM 控制、转速反馈 | CPLD 控制逻辑 |
| **BMC 板卡** | 带外管理：监控/固件/批量接口 | Redfish/IPMI、批量上架接口 | BMC 固件 |

### 3.2 复用/新研/小改分类与决策

| 分类 | 判定标准 | 对项目管理的含义 |
|:-----|:---------|:-----------------|
| **完全复用** | 已有板卡 + 已有固件，功能满足 | 走"入库存量"路线：直接领用，只做兼容性验证 |
| **小改（固件级）** | 硬件不变/微调，仅固件适配 | 风险低，固件团队独立排期，不等硬件 |
| **小改（硬件级）** | 板卡局部改版（如电源裕量） | 走完整硬件流程，但可并行旧板 bringup |
| **新研** | 全新板卡（如新 GPU 板） | **关键路径**，需提前锁定物料+EVB 先行 |

**复用决策三问**（W0 必答）：

1. 复用板的**接口/功耗/散热**是否满足本 POC 场景？（不满足→小改/新研）
2. 复用板的**固件基线**是否覆盖本 POC 功能？（不覆盖→固件小改）
3. 复用板的**物料可获取性**？（有货→直接复用；无货→评估新研风险）

> 用户场景"复用已有的整机柜"意味着 L2 层以**集成验证**为主（槽位识别、电源液冷联动），重点转为 L0 新板卡与 L2 既有整机柜的**兼容性**验证——这是本项目最典型的复用风险点：新板卡装入旧机柜，槽位定义/电源接口/管理协议是否兼容。

## §4 固件开发三线并行

### 4.1 固件族谱（BMC/BIOS/CPLD-FPGA）

```text
固件族谱（按硬件依赖强度排序）
+-- CPLD/FPGA --- 依赖最强: 需真实硬件调时序 -> 必须随板调试
+-- BMC --------- 中等: 可 EVB/模拟器先行，回板后联调
+-- BIOS -------- 中等: 依赖 CPU 平台，可 QEMU/参考平台先行
```

**三线开发策略**：

| 固件线 | 回板前（虚拟阶段） | 回板后（实机阶段） | 关键交付物 |
|:-------|:------------------|:------------------|:-----------|
| CPLD/FPGA | 仿真验证时序逻辑 | 随板调试电源/复位/时钟 | 时序代码 + 烧录文件 |
| BMC | EVB/模拟器跑通管理栈 | 实机监控/固件升级/批量接口 | BMC 镜像 + Redfish 模型 |
| BIOS | 参考平台验证启动流程 | 实机 POST/内存/PCIe | BIOS 镜像 + 配置基线 |

### 4.2 分阶段目标：bringup → 功能齐全 → 整机验证

| 阶段 | 代号 | 核心目标 | 硬件状态 | 准出标准 |
|:-----|:-----|:---------|:---------|:---------|
| **Bringup** | B0 | 最小系统点亮、发现硬件问题 | 首版工程样片 | 电源/时钟/复位正常、Console 可见、基本内存识别 |
| **功能齐全** | T0 | 单板功能全验证、DFT 全覆盖 | EVT 样片 | 规格书功能闭环、可支撑节点组装 |
| **整机验证** | P0 | 节点→机柜→超节点逐层验证 | DVT 样片 | P0 集群功能全过、P1 性能采集完成 |

> 与单板方法论的四阶段模型（Bringup→Test→POC→Release）对齐，但本 POC 只到 **P0 级**（验证用，非量产），Release 阶段不在 POC 范围——**范围切割要明确**，避免 POC 蔓延为产品化。

### 4.3 固件-硬件同步机制（回板时间点有版本可验证）

**核心要求**："开发要在单板回板时间点有版本能进行验证"——这是本次需求的关键约束，落地机制：

```text
回板前（W-2~W0）固件准备的三个并行通道:
① 虚拟通道: 模拟器/EVB/参考平台跑通 80% 逻辑（BMC 管理栈、BIOS 启动流程）
② 契约通道: 与硬件签接口契约（GPIO/寄存器/FRU 布局/Redfish 模型），冻结变更
③ 烧录通道: 预生成回板首版镜像（含回退方案），随板卡交付清单一同下发

回板当天（W4）:
  D0: 上电安全检查（电源短路/过流）-> 最小系统点亮
  D1: Console 可见 + 基本内存识别（B0 准出）
  D3: 三线固件全部跑通基础用例 -> 输出《回板验证日报》
```

**失败模式与兜底**：若回板时固件未就绪 → 固件团队需在**回板前 2 周**发出风险预警（见 §8.3 升级机制），并准备"硬件裸调"方案（用 CPLD 最小逻辑点亮硬件，固件后续补）。

## §5 上层软件配套

### 5.1 算力平台：算力调度

| 需求 | 说明 | 依赖 | 交付时机 |
|:-----|:-----|:-----|:---------|
| 节点注册与资源上报 | 计算/交换/存储节点接入平台，上报算力/显存/存储 | BMC Redfish + OS Agent | W10（与 L2 同步） |
| 任务调度 | 推理任务下发到计算节点，含 KV Cache 场景的显存感知调度 | 调度器 + GPU 驱动 | W12（超节点联调） |
| 性能采集 | KV Cache 吞吐/时延/容量采集与报表 | 推理引擎（vLLM 等） | W14（性能阶段） |

**并行策略**：算力平台在 W0 即启动，用**模拟节点**（mock 节点注册+调度）先行验证调度逻辑，W10 实机接入——避免"等硬件才能开发软件"的串行陷阱。

### 5.2 运维平台：固件批量上架与基本监控

| 需求 | 说明 | 依赖 | 交付时机 |
|:-----|:-----|:-----|:---------|
| 固件批量上架 | 批量刷写 BMC/BIOS/CPLD，版本管理，失败重试 | BMC 批量接口（Redfish Update） | W10 |
| 基本监控 | 节点状态/电源/温度/液冷状态采集与告警 | BMC 传感器 + Redfish | W8（节点级即可） |
| 机柜视图 | 槽位信息识别展示（槽位→节点映射） | BMC FRU + 机柜拓扑 | W10 |

**接口契约先行**：运维平台与 BMC 固件在 W0~W2 冻结 Redfish 模型与批量接口契约，两边并行开发，W10 集成——这是"软件不等硬件"的关键。

## §6 端到端流程与里程碑计划

### 6.1 全流程泳道（需求→备料→加工→回板→验证→互联→报告）

```text
需求明确(W0) -> 物料备货(W1) -> 工程加工(W2-3) -> 单板回板(W4)
    v              v              v              v
 冻结PRD      长交期料锁定      PCB/结构件       bringup启动
                                              v
```

## §8 风险管理

### 8.1 系统级风险图谱（含级联放大分析）

| 风险 | 概率 | 影响 | 级联路径 | 应对策略 |
|:-----|:----:|:----:|:---------|:---------|
| **长交期物料延迟**（GPU/CPU/PMIC） | 🟠高 | 🔴致命 | L0 板卡→L1 节点→L3 超节点全链延迟 | W1 锁定长交期料+备选 BOM；复用板优先 |
| **新研板卡 bringup 延期**（硬件缺陷） | 🟠高 | 🔴致命 | 单板→节点→机柜级联放大 2~3× | B0 范围最小化；硬件问题标记不阻塞；准备 CPLD 裸调 |
| **固件-硬件不同步**（回板时固件未就绪） | 🟡中 | 🟠严重 | 回板后等待固件，浪费硬件窗口 | 回板前虚拟联调 80%；契约冻结；提前 2 周预警 |
| **新板卡装入旧机柜不兼容**（槽位/电源/管理协议） | 🟡中 | 🟠严重 | L0→L2 集成失败 | W1 复用兼容性专项验证；接口差异清单先行 |
| **互联问题**（交换/存储节点接口异常） | 🟡中 | 🟠严重 | L3 互联联调受阻 | W2 起搭建小型验证环境（2 节点先行）；协议预研 |
| **算力平台调度异常** | 🟡中 | 🟡中等 | P0 功能不过 | mock 先行；调度成功率 ≥95% 指标前移 |
| **液冷/电源集成异常** | 🟡中 | 🟠严重 | 整机柜不可用 | 复用整机柜的液冷/电源专项巡检；压力测试提前 |
| **测试资源不足**（多领域并行挤占） | 🟠高 | 🟡中等 | 验证节奏拖慢 | 测试用例按优先级分层；关键路径测试优先排期 |

### 8.2 风险应对策略矩阵

| 策略 | 应用示例 |
|:-----|:---------|
| **规避** | POC 范围切割：不做 Release/量产验证，只做 P0 验证级 |
| **减轻** | 固件虚拟联调提前 80% 逻辑；复用板兼容性专项验证前置 |
| **转移** | 认证/第三方性能基准外包（如 KV Cache 基准测试工具商） |
| **接受** | 低概率的调度性能微调问题，POC 阶段现场调优即可 |
| **备选** | 备选 BOM/备选芯片；互联异常时降级方案（单机柜先验证） |

### 8.3 里程碑风险触发与升级机制

```text
每 2 周风险复盘 + 里程碑前专项检查
  |
  +- 风险状态变化 -> 更新风险登记册（概率×影响×责任人×应对）
  |
  +- 里程碑准出未达成 -> 触发升级:
  |     L1 项目经理升级: 延期 ≤ 1 周 -> 内部协调资源
  |     L2 管理层升级: 延期 > 1 周 或 致命风险 -> 重新排期/范围决策
  |
  +- 关键预警线（提前量）:
       回板前 2 周: 固件未就绪预警
       互联前 2 周: 节点未齐套预警
       性能前 1 周: P0 功能未全过预警
```

## §11 结论与行动建议

**核心结论**：需求明确后，研发活动管理的本质是把"目标→分层→依赖→同步→风险"五个环节变成**可执行、可检查、可升级**的机制，而非依赖个人协调。

**五个立即行动**（W0 启动前）：

1. **量化目标**：把"验证集群功能 + 获取 KV Cache 性能"写成可验收数值（§1.2），全员对齐
2. **冻结契约**：W2 前完成层间接口契约（固件/软件/硬件三方），并行开发的前提
3. **锁定物料**：W1 完成长交期料下单 + 复用板确认，这是全局第一风险
4. **虚拟先行**：固件/软件/测试三条线 W0 启动，mock/模拟器先行，回板即测
5. **建风险册**：W0 建立风险登记册（含级联路径），每 2 周复盘 + 里程碑专项检查

**管理节奏总结**：周例会锁节奏、里程碑锁准出、预警线锁风险、接口契约锁并行——四把锁把多领域协同钉在同一节奏上。
