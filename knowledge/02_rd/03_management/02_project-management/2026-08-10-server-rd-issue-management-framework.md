## 1. 结论概要：9 点一句话速查

| # | 场景 | 核心机制 | 一句话 |
|:-:|:-----|:---------|:-------|
| 1 | 部件问题 | 双入口台账 + 部件问题卡 | errata 只是部件问题的一半，另一半是自身发现；一部件一卡统管 |
| 2 | 供应商多问题 | 供应商问题台账 + 承诺表 | 按供应商聚合、批量排序、一次谈判打包，把「看不到的修复队列」变成承诺表 |
| 3 | 问题→专题 | 关闭双门槛 | 技术解决 + 知识沉淀完成才允许关闭，即时通信/邮件信息必须在关闭前提取 |
| 4 | 多客户分支 | 传染性评估 | 每个问题关闭时回答「会影响哪些分支」，根因标签聚类识别共性问题 |
| 5 | 分支→主线 | 修复双写 | 客户分支的修复必须同步写回主线，否则下个版本回归 |
| 6 | 处置分类 | 四路径决策 + 平台传承清单 | 立即/规避/后续版本/下平台是「在哪+何时解决」的决策，下平台必须可回看 |
| 7 | 概率复现 | 条件搜索方法论（DOE + 最小触发集） | 条件不明不是「无法复现」，是「搜索空间太大」——分层设计实验收敛 |
| 8 | 不复现 | 证据保全金字塔 + 监视清单 | 环境破坏前按优先级抢数据；无法复现≠关闭，进监视清单回看 |
| 9 | 优先级管道 | 双管道模型 + 能见度协议 | 优先级不是重要性排序，是内部/外部双管道的分配决策；不可见管道用承诺追踪变半可见 |

**一句话总结**：问题管理的本质是在「信息不确定性」（条件不明/不复现/第三方黑箱）与「管道容量」（人力/供应商/时间窗口）双重约束下，把问题从「发现」推进到「关闭」的决策流水线。9 个场景不是 9 个独立问题，而是这条流水线在**对象、空间、认知、资源**四个维度上的难点切片。

## 2. 第一性原理：问题管理是什么

### 2.1 双重约束模型

> **问题管理 = 在信息不确定性 × 管道容量双重约束下，把问题从「发现」推进到「关闭」的决策流水线**

| 约束 | 内容 | 典型表现 | 对应场景 |
|:-----|:-----|:---------|:---------|
| **信息不确定性** | 触发条件、根因、影响范围未知 | 概率复现、不复现、供应商黑箱 | P7 / P8 / P2 / P9 |
| **管道容量** | 修复资源（人力/供应商/时间窗口）有限 | 多问题并发、优先级冲突 | P2 / P6 / P9 |

两个约束是**正交**的：一个问题可以「根因清晰但无资源修」（纯管道约束），也可以「资源充足但根因不明」（纯信息约束），大多数难问题是两者耦合（根因不明 + 供应商管道不透明 + 内部人力被占）。

**推论 1**：管理手段必须按约束类型区分——信息约束用**实验/取证**手段（DOE、证据保全），管道约束用**调度/博弈**手段（优先级、承诺表、升级）。用错手段是问题拖长的第一原因：对信息约束问题开优先级会没有用（资源给了但不知道做什么），对管道约束问题做更多实验也没有用（根因已知但没人修）。

**推论 2**：问题管理的 KPI 不是「关闭数量」，而是**约束消解速度**——信息约束被实验消解（未知→已知）、管道约束被调度消解（等待→处理中）。

### 2.2 为什么 9 个场景难以管理

| 维度 | 难点 | 本质 |
|:-----|:-----|:-----|
| 对象维度（P1/P2） | 问题挂在部件/供应商上，跨项目跨时间 | 问题有「宿主」，台账按宿主聚合才可管理 |
| 空间维度（P4/P5） | 同一问题在多个客户分支/版本间传播 | 问题的传播网络（分支矩阵）不可见 |
| 时间维度（P3/P6） | 问题要么被遗忘要么被重复发现 | 缺「关闭→沉淀→复用」的终态机制 |
| 认知维度（P7/P8） | 根因不可观测或证据丢失 | 信息不确定性是问题的本质属性 |
| 资源维度（P9） | 内部管道可见、外部管道不可见 | 优先级决策建立在不对称信息上 |

 │         │           │           │           │           └─ P3 专题沉淀
 │         │           │           │           └─ P6 处置分类（立即/规避/后续/下平台）

## 4. P1 部件问题：双入口台账与部件问题卡

### 4.1 双入口模型：部件问题 ≠ 供应商 Errata

已有 [`2026-07-13-errata-management-for-server-rd.md`](../../06_manufacturing/2026-07-13-errata-management-for-server-rd.md) 覆盖「外购部件 Errata 全生命周期」，但部件问题有**两个入口**，errata 只是其中一个：

| 入口 | 来源 | 特征 | 已有覆盖 |
|:-----|:-----|:-----|:---------|
| **主动感知** | 供应商 Errata Sheet / FAE / 社区 / CVE | 供应商已承认、有编号 | errata §4 ✅ |
| **自身发现** | 内部测试 / 产线 / 客户 RMA / 老化 | 供应商未知或未承认、无编号 | ❌ 缺口 |

自身发现的问题才是常态（客户环境触发 → 我方定位 → 反推供应商），且这类问题**在确认根因前无法确定是不是 errata**——管理机制必须从「errata 台账」升级为「部件问题台账」，errata 只是台账中的一类（状态=供应商已确认）。

### 4.2 部件问题卡（Part Issue Card）

一部件一卡，作为该部件所有问题的**单一事实源**（SSOT）：

| 字段组 | 字段 | 说明 |
|:-------|:-----|:-----|
| 部件标识 | 型号 / 批次 / 固件版本 / 兼容性矩阵链接 | 与 [`errata §10.3 兼容性矩阵`](../../06_manufacturing/2026-07-13-errata-management-for-server-rd.md) 联动 |
| 问题清单 | 全部 open 问题（含双入口来源） | 按严重度×概率排序 |
| 供应商状态 | 已知问题数 / 承诺修复版本 / 承诺日期 | 进承诺表（P2） |
| 决策历史 | 已处置问题 + 处置路径（P6） | 防重复决策 |
| 知识链接 | 专题文档链接（P3） | 关闭→沉淀 |

**关键设计**：部件问题卡是「问题聚合视图」，不是新系统——它把分散在各项目/客户的问题按部件聚合，让「这个部件到底有多少问题、供应商还欠我们什么」一眼可见。这是 P2（供应商谈判）和 P4（共性问题识别）的数据底座。

## 5. P2 供应商多问题并发：台账聚合与承诺表

### 5.1 从「单问题博弈」到「供应商问题台账」

已有 [`2026-07-08-02-problem-resolution-tactics.md`](../../05_supply-chain/2026-07-08-02-problem-resolution-tactics.md) 是「单问题怎么推动」的博弈战术（五级升级、证据链、快速决策矩阵）。但当同一供应商有多个并发问题时，单问题博弈失效——**供应商的修复管道有限**，他们内部也在排序，谁的问题被顶到前面取决于「谁在施压 + 哪个问题好修 + 哪个客户重要」。

**核心机制：供应商问题台账（Vendor Issue Register）**

| 维度 | 设计 |
|:-----|:-----|
| 聚合粒度 | 按供应商聚合所有 open 问题（跨项目/跨客户） |
| 排序字段 | 我方视角：严重度 × 影响面 × 客户压力；供应商视角：难度 × 修复版本计划 |
| 打包谈判 | 一次评审会讨论一个供应商的全部问题，而不是逐问题拉锯 |
| 承诺表 | 每个问题一行：承诺修复版本 / 承诺日期 / 实际状态 / 更新日期 |

### 5.2 承诺表：把不可见管道变半可见

供应商的 bug 修复队列对我方不可见（这是 P9「难以看到第三方情况」的核心），但可以**通过协议把它变成半可见**：

```
供应商问题台账（每月评审）
+---------+---------+----------+----------+----------+----------+
| 问题 ID | 严重度  | 承诺版本 | 承诺日期 | 当前状态 | 更新日期 |
+---------+---------+----------+----------+----------+----------+
| VND-001 | Critical| fw 2.1   | 08-15    | 开发中   | 08-08    |
| VND-002 | Major   | fw 2.1   | 08-15    | 待验证   | 08-05    |
| VND-003 | Major   | fw 2.2   | 09-30    | 未开始   | 08-01    |
+---------+---------+----------+----------+----------+----------+
```

**承诺表的三个作用**：
1. **我方优先级决策的输入**（P9）——承诺版本/日期决定「这个问题的内部投入怎么排」
2. **供应商履约的度量**——承诺日期 vs 实际状态，延迟率是供应商健康度的量化指标
3. **升级的触发器**——承诺逾期即触发升级（tactics 五级升级法的启动条件）

**打包谈判的 trade-off 空间**：多问题打包后，供应商有选择权（修最容易的、或修最重要的），我方要明确「哪些问题必须这版修、哪些可以下版」——这就是 P6 处置分类在供应商侧的镜像。

## 6. P3 问题→专题沉淀：关闭双门槛

### 6.1 问题为什么必须沉淀为专题

即时通信/邮件的问题讨论有三个致命缺陷：**不可检索**（聊天记录搜不到）、**不可复用**（下次同类问题重新踩坑）、**不可传承**（人员流动即知识流失）。用户明确要求「形成专题，而非停留在即时通信，甚至邮件上」——这是知识管理理念在问题域的落地（与 [`2026-08-05-knowledge-management-value-chain-deep-analysis.md`](../../../../07_industry-research/18_methodology-framework/2026-08-05-knowledge-management-value-chain-deep-analysis.md) 的「知识价值链」同构）。

### 6.2 关闭双门槛机制

> **一个问题的关闭必须同时满足两个门槛：技术解决（T）+ 知识沉淀（K）。只满足 T 不满足 K 的问题保持「已解决未关闭」状态。**

| 门槛 | 内容 | 检查项 |
|:-----|:-----|:-------|
| **T 技术解决** | 修复/规避已验证 | 验证报告、回归通过 |
| **K 知识沉淀** | 关键信息已入专题 | 根因、触发条件、处置历史、供应商交互、规避知识均已结构化 |

**K 门槛的强制动作**（在关闭操作前检查）：
1. 即时通信/邮件中的**关键决策与数据**已提取入台账（时间线、数据、结论）
2. 根因已打标签（进 P4 聚类）
3. 若满足专题触发条件（下节），专题已创建

### 6.3 专题触发条件与模板

| 触发条件 | 说明 |
|:---------|:-----|
| 同一根因 ≥ 3 个问题 | 症状不同但根因同 → 值得建专题 |
| 同一部件 ≥ 5 个问题 | 部件问题卡已积累足够素材（P1） |
| 供应商问题滞留 ≥ 30 天 | 博弈过程本身有复盘价值 |
| 排查过程 ≥ 2 周 | 方法/弯路值得记录（P7 概率问题的排查路径） |
| 客户环境触发 | 涉及客户沟通策略（errata §8） |

**专题模板**（问题族谱式）：症状族谱（不同症状→同一根因的映射）/ 触发条件全集（从 P7 条件搜索沉淀）/ 规避知识（workaround 及其代价）/ 供应商交互记录（承诺、升级、结果）/ 预防措施（设计/测试/流程层面）。专题归档到知识库，并在部件问题卡（P1）留链接。

## 7. P4 多客户分支：传染性评估与同步机制

### 7.1 共性问题识别的三个信号

多客户分支（产品基线 + 客户定制版本）下，同一根因会以不同症状出现在不同分支。共性问题识别不能靠「症状相似」，要靠**根因聚类**：

| 信号 | 识别方法 | 案例 |
|:-----|:---------|:-----|
| **同根因** | 每个问题关闭时打根因标签，按标签聚合 | 客户 A 掉盘 / 客户 B 性能骤降 → 同一 SSD 固件 bug |
| **同改动** | 分支 diff 矩阵——同一代码/配置被多个分支共享 | 共享 BIOS 补丁在 3 个客户分支均有影响 |
| **同部件** | 部件问题卡（P1）的跨项目视图 | 同一 Retimer 在 2 个客户环境出问题 |

### 7.2 传染性评估：每个问题的强制问题

> **每个问题在登记和关闭时必须回答：这个问题影响哪些分支/客户？——「传染性评估」**

```
传染性评估（登记时）
1. 涉及哪个部件/模块？→ 查部件问题卡（P1）→ 哪些产品线用了？
2. 涉及哪段代码/配置？→ 查分支 diff 矩阵 → 哪些分支共享？
3. 触发条件在哪些客户环境成立？→ 查客户配置矩阵 → 哪些客户满足？
4. 结论：影响分支清单 [B1, B2, B3] + 传染等级（单点/局部/全局）
```

**传染等级决定处理优先级**：全局传染的问题即使客户 A 不催，也要按 P0 处理——因为客户 B/C 随时会爆。

### 7.3 同步处理机制

| 场景 | 机制 |
|:-----|:-----|
| 修复已确认 | 修复包 → 各受影响分支分发 → 各分支独立验证（配置差异决定验证内容） |
| 分支定制多 | 「先主线后分支」——修复先合主线（P5），再从主线分发到各分支，避免逐分支重复修 |
| 客户紧急 | 「客户优先」——先出客户分支 hotfix，同时走主线（P5 修复双写） |

**同步的纪律**：每个受影响分支必须显式登记「已同步 / 已评估无需同步 / 已豁免（附理由）」三态之一——不登记=未处理。

## 8. P5 分支到主线：修复双写

### 8.1 修复的反向流动

问题在客户分支发现、修复，但**修复必须回流主线**——否则下个版本从主线拉出新分支时，问题复活（回归）。这与 [`2026-07-23-design-compatibility-board-change-control.md`](../../../01_product/00_hardware/07_dfx/2026-07-23-design-compatibility-board-change-control.md)（硬件变更控制）互补：该文档管硬件改版，本文管软件/固件问题修复流。

### 8.2 三类修复与合入规则

| 类型 | 定义 | 合入规则 |
|:-----|:-----|:---------|
| **纯 fix** | 通用修复，无客户定制耦合 | 必须合入主线，带最小复现集 + 验证结果 |
| **定制 fix** | 针对客户定制配置的修复 | 评估是否抽象为通用修复；不能则记录「定制修复 + 适用分支」，主线评估是否需同步适配 |
| **workaround** | 规避措施，非根治 | 不入主线，但登记为「已知问题 + 规避」，P6 决定根治时机 |

### 8.3 修复双写（Dual-Write）机制

> **客户分支的每次修复，必须同步写回主线（或显式豁免）。「修复双写」是防止问题跨版本复活的唯一保障。**

```
客户分支修复完成
  → ① 合入主线（cherry-pick / 手工适配）
  → ② 主线触发相关回归
  → ③ 登记：主线合入 commit / 豁免理由（二选一）
  → ④ 下个分支从主线拉取时自动携带修复
```

**检查机制**：问题关闭时（P3 双门槛）必须回答「主线已合入？豁免理由？」——未合入不关闭。

## 9. P6 处置分类：四路径决策与平台传承

### 9.1 四路径决策（用户定义的分法）

用户的分法与 errata 的应对策略矩阵（SR/WB/HW/OP/MB/AC，手段维度）正交——**四路径是「在哪解决 + 何时解决」的决策，应对策略是「用什么手段」的决策**：

| 处置路径 | 定义 | 适用条件 | 与 errata 策略的映射 |
|:---------|:-----|:---------|:---------------------|
| **立即处理** | 当前版本内解决 | P0/P1 且影响当前交付 | SR/HW（根治） |
| **规避处理** | 当前版本用 workaround，根治后置 | 修复不可行或太慢 | WB/OP/MB（缓解） |
| **后续版本处理** | 不影响当前交付，下个版本修 | P2/P3 且无交付阻塞 | SR（排期） |
| **下个平台处理** | 当前平台不值得修，下一代平台设计中规避 | 架构级 / 修复成本 > 收益 | AC（接受）+ 设计规避 |

### 9.2 处置决策单

每个问题进入处置路径时，必须记录决策（防「下平台」变成「永远不处理」）：

| 字段 | 内容 |
|:-----|:-----|
| 决策人 | 谁拍板（技术负责人） |
| 决策理由 | 为什么走这条路径（数据：修复成本/收益/风险） |
| 回看日期 | 何时重新评估（后续版本/下平台必须设） |
| 传承去向 | 下平台问题 → 平台传承清单（下节） |

### 9.3 平台传承清单（Platform Carry-over Register）

「下个平台处理」的陷阱是**平台切换时遗忘**——新平台设计团队不知道旧平台有未解决问题，于是下一代重复犯错（同一根因在新架构里重现）。

> **平台传承清单 = 旧平台未解决问题的「遗嘱」：在新平台架构评审时逐条核对是否已规避。**

| 字段 | 内容 |
|:-----|:-----|
| 源平台问题 | 问题 ID + 根因 + 触发条件 |
| 新平台对应设计点 | 哪个模块/电路/固件会重演 |
| 规避状态 | 已规避 / 设计中 / 未处理 |
| 核对人 / 日期 | 架构评审时的责任人 |

传承清单挂在新平台项目启动文档中，**架构评审的固定议程项**。

## 10. P7 概率复现：条件搜索方法论

### 10.1 核心认知转换

> 「概率复现 + 条件不明确」不是「无法复现」，而是**搜索空间太大**——问题的触发条件是「环境×负载×时序×配置」四维空间的某个（或某组）区域，未知条件 = 在这个空间里盲目试探。

errata §7.3 已给出方法论（加速测试/大批量筛选/金手指比对/故障注入/AI 异常检测）——那些是**条件已知后的验证手段**。本节的增量是：**条件完全不明时，如何系统化地找到触发条件**。

### 10.2 条件空间分层

触发条件按可探测性分层，搜索从「最易观测」到「最难观测」：

| 层 | 条件类别 | 典型变量 | 探测手段 |
|:---|:---------|:---------|:---------|
| L1 | 环境条件 | 温度 / 电压 / 湿度 / 振动 / 海拔 | 现场遥测 + 环境记录（易得） |
| L2 | 负载条件 | 流量 / 队列深度 / 并发数 / 访问模式 | 现场负载画像 + 压测（较易） |
| L3 | 时序条件 | 启动时序 / 事件顺序 / 竞态窗口 | 日志时间线分析（中等） |
| L4 | 配置条件 | 固件版本 / 寄存器设置 / 拓扑组合 | 版本对比 + 配置矩阵（需实验） |

**搜索策略**：先查现场数据（L1/L2 的遥测和负载记录往往已经存在）——**现场数据的模式识别优先于盲目复现实验**。现场数据的「异常前窗口」（事件墙法，见 [`fault-diagnosis 技能`](../../../../skills/fault-diagnosis/SKILL.md) 2.1）是触发条件的首要候选。

### 10.3 DOE 实验设计：从粗筛到细扫

条件空间太大时，不能用「一次变一个变量」的穷举（4 维 × 每维 5 水平 = 625 组合），要用析因设计：

```
阶段一：粗筛（Plackett-Burman / 部分析因）
  → 所有候选变量各测高低两个水平，识别显著变量（通常 1-3 个）
阶段二：细扫（全因子 / 响应面）
  → 对显著变量做精细扫描，定位触发区域（如温度 > 78°C 且 QD ≥ 64）
阶段三：最小化触发集（Minimal Trigger Set）
  → 在触发区域内逐步剥离条件（一次去掉一个），找到最小触发组合
  → 交付物：给供应商的「确定性触发条件」而非「无法复现」
```

**最小化触发集的价值**：它是给供应商的最强证据（tactics §4 证据链的顶点）、是修复方案的输入（修哪个条件）、也是回归测试的用例（验证修复时只需测最小触发集）。

### 10.4 低概率问题的样本量估算

触发概率极低（如 0.1%）时，需要统计支撑：设目标检出概率 95%，触发概率 p，需要样本量 n 满足 (1-p)^n ≤ 0.05，即 **n ≥ ln(0.05)/ln(1-p)**。p=0.1% → n≈2995；p=1% → n≈299。这个估算决定了「大批量筛选」（errata §7.3）的规模设计，避免盲目上量。

## 11. P8 不复现问题：证据保全金字塔与监视清单

### 11.1 环境破坏是常态，不是意外

客户现场出问题后，工程师到场前环境可能已被改变（重启、换件、恢复业务），「到现场再取证」基本不可能。**应对思路：取证前置——证据保全不是事后流程，是部署默认项。**

### 11.2 证据保全金字塔

| 优先级 | 证据类别 | 内容 | 保全手段 |
|:------:|:---------|:-----|:---------|
| **P0 内存态** | 崩溃转储 / 寄存器 / 队列状态 / 内核 panic | 最易丢失，重启即失 | 自动崩溃转储（kdump/固件转储），事故自动触发 |
| **P1 持久态** | 系统日志 / 事件记录 / 遥测快照 / BMC SEL | 重启保留但会滚转 | 环形日志 + 定期快照上传 |
| **P2 环境态** | 温度 / 电压 / 负载记录 / 现场照片 | 需要主动采集 | 带外管理（BMC/Redfish）遥测归档 |

**关键设计**：所有部署设备默认开启「事故数据自动保全」——崩溃转储自动保留、日志环形缓冲加大、遥测定时归档。**不依赖现场工程师的自觉**。

### 11.3 「环境破坏」本身是信息

现场人员的操作序列（重启了几次、换了什么、动了什么设置）本身就是**触发条件的候选集合**——操作序列与问题发生/消失的关联，就是一次「人为的对照实验」。处置流程必须包含：

1. **远端诊断优先**：现场操作前，先通过带外管理（BMC/Redfish/Serial-over-LAN）拉取所有可拉数据
2. **操作记录**：问清现场操作序列（什么时候重启、问题在重启前还是后、有没有换件）
3. **设备保留**：RMA 前完成取证清单（与客户协议化），回收设备不复位

### 11.4 无法复现 ≠ 关闭：监视清单

> **沉没问题管理：无法复现的问题进入监视清单（Known Unresolved Register），设回看周期，样本积累后重新分析——绝不用「无法复现」直接关闭。**

| 字段 | 内容 |
|:-----|:-----|
| 现场证据包 | 已保全的日志/转储/遥测链接 |
| 触发条件假设 | 从现场数据推导的候选条件（P7 分层） |
| 监视指标 | 该症状的复现计数 / 相关告警计数 |
| 回看周期 | 30 天 / 季度，样本 ≥ N 或版本升级时触发重分析 |

监视清单是 P3 专题的「待孵化」状态：满足触发条件（如同一症状再次出现）即升级为专题。

## 12. P9 优先级与管道：双管道模型与能见度协议

### 12.1 优先级是管道分配决策，不是重要性排序

已有 [`2026-07-14-server-rd-prioritization-decision.md`](../../2026-07-14-server-rd-prioritization-decision.md) 的 Eisenhower 四象限解决「内部选择过载」（该做什么）。本节的增量：**当问题依赖外部管道（供应商/第三方）时，内部优先级必须与外部管道状态联合调度**。

### 12.2 双管道模型

| 管道 | 可见性 | 资源 | 建模方式 |
|:-----|:-------|:-----|:---------|
| **内部管道** | ✅ 可见 | 人力 / 测试资源 / 时间窗口 | 精确排程（谁、何时、多久） |
| **外部管道** | ❌ 不可见 | 供应商修复队列 / FAE / 第三方（BIOS 厂商、代工厂） | 承诺表追踪（P2），半可见 |

**联合调度逻辑**：

```
问题进入
  → ① 分诊：信息约束 or 管道约束？（§2.1）
  → ② 若依赖外部管道：查承诺表 → 外部就绪度（承诺版本/日期/状态）
  → ③ 内部管道排程 = f(问题严重度, 影响面, 客户压力, 外部就绪度, 决策窗口)
  → ④ 每周重排：新问题进入 / 外部状态变化 / 决策窗口逼近
```

**关键判断**：外部管道未就绪的问题（供应商承诺 09-30 修复），内部投入不应启动（做了白做）——内部资源应该转向「外部就绪后能用」的准备工作（验证环境、回归用例）或其他问题。**把「等待外部」变成「显式调度状态」而不是「挂起黑洞」**。

### 12.3 优先级公式化与每周重排

优先级不是一个静态分数，而是随管道状态变化的动态决策：

> **P = f(严重度, 影响面, 触发概率, 客户压力, 内部就绪度, 外部就绪度, 决策窗口)**

- **决策窗口**：逼近交付节点/平台切换时，即使严重度低也可能要优先（窗口关闭后代价剧增）
- **每周重排会**（问题管理周会）：不是逐问题过，而是过「管道视图」——内部管道谁在做什么、外部管道哪些承诺要到期、哪些问题窗口要关闭

### 12.4 能见度协议（Visibility Protocol）

对供应商/第三方，通过协议把不可见管道变成半可见：

| 协议项 | 内容 |
|:-------|:-----|
| 承诺制 | 每个问题必须有承诺修复版本 + 日期（P2 承诺表） |
| 更新频率 | 承诺逾期或状态变化须主动通知（FAE 协同三要素，errata §4.4） |
| 升级触发 | 承诺逾期 X 天 / 连续两次跳票 → 升级路径（tactics 五级升级） |
| 双周同步 | 关键供应商双周技术会，确认所有 open 问题状态 |

## 15. 批判注记

1. **机制密度 vs 落地成本**：本文给出 9 套机制，全部落地会产生台账维护开销（每个问题多填几个字段）。建议分阶段（M1-M4），且台账字段克制——「够用」优于「完备」，字段膨胀是台账死亡的第一原因。
2. **统计假设**：§10.4 样本量公式假设触发概率恒定且独立，真实场景概率随环境漂移，估算为下界参考。
3. **承诺表的效力依赖博弈地位**：tactics §1.1 的 A-D 级客户分级决定了供应商是否接受承诺制——C/D 级客户需借力渠道（ODM/OEM）间接获取承诺。
4. **「修复双写」与「客户优先」的冲突**：客户紧急时先出 hotfix 再补主线，存在时间窗内主线未合入的回归风险——需在关闭门槛（P3）强制登记合入状态来兜底。
5. **监视清单的膨胀风险**：无法复现问题可能大量积累，需设「监视清单容量上限 + 定期淘汰」机制，避免变成第二个「遗留堆积」仓库（RCA 文档的库存病）。
6. **框架为理论建构**：9 点映射与双约束模型是本文的分析框架，非行业标准（ITIL 的 Incident/Problem/已知错误模型可对照，但服务器硬件研发场景的「部件/供应商/分支」维度是本文特有的）。
