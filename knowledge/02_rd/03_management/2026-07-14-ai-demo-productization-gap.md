## 1. 现象定义：AI Demo → 产品化落差

### 1.1 典型场景

```text
周一：

管理者 A（刷到一段 AI 演示视频）：
「你看这个！用 AI 自动生成报表，30 秒搞定！我们也要做！」
「我们的客户也在问这个功能，下季度必须上线！」

开发者 B 看了一眼（内心活动）：
「这个 demo 确实酷，但…它只演示了完美路径。」
「没有错误处理，没有权限控制，没有数据安全，没有配置管理…」

一周后：

管理者 A：「这个功能做得怎么样了？」
开发者 B：「我们还在做底层数据模型对接和权限设计…」
管理者 A（皱眉）：「一个报表功能需要这么久？人家 AI 30 秒就做完了。」
开发者 B（内心崩溃）：「AI 的 30 秒和产品化的 30 天是两个概念…」

一个月后：

管理者 A：「季度 OKR 定期检查，为什么这个功能延期了？」
开发者 B：「我们遇到了一些边界情况…A 部门没有开放接口权限…B 系统的数据格式不兼容…」
管理者 A（内心结论）：「开发效率确实不行。」

三个月后：

功能上线了，但：
  - 只覆盖了 60% 的报表类型
  - 权限集成只做了基础版
  - 数据准确率在边界条件下只有 85%
  - 运维文档还不全

管理者 A 的评价：「做了这么久，效果还一般。开发团队的能力有问题。」
开发团队的感受：「又来了，每次 demo 拍脑袋，落地全是坑。」
```

### 1.2 定义

**AI Demo → 产品化落差（AI Demo-to-Productization Gap）**：管理人员以 AI 工具生成的快速演示原型（demo）作为功能可行性的判断依据，低估从 demo 到生产级产品所需的工作量 10-100 倍，并将产品化过程中的正常工程困难归因为「开发效率低下」的管理认知偏差。

### 1.3 与「软文导向决策」的异同

| 维度 | 软文导向决策 | AI Demo → 产品化落差 |
|:-----|:-------------|:---------------------|
| **触发源** | 友商公关稿/新闻 | **内部/外部 AI 生成的演示视频或原型** |
| **幻觉来源** | 友商宣传的真实性 | **AI 输出到生产级的工程工作量** |
| **低估维度** | 技术难度、客户价值 | **工程复杂性、长尾问题、运维成本** |
| **归因偏差** | 「我们落后了」 | **「开发效率太低」** |
| **伤害链** | 方向频繁变更 | **方向对但预期失衡 → 团队被责备 → 士气崩塌** |
| **信息源可信度** | 低（PR 材料） | **看似高（能看到 demo 在跑）→ 更有迷惑性** |

**核心差异**: 软文导向决策的幻觉来自**外部信息失真**；AI demo 落差的幻觉来自**对工程难度的系统性低估**。后者因为「亲眼看到了 demo 在工作」而更具说服力——也是更难反驳的。

### 1.4 为什么这个现象特别危险

| 原因 | 解释 |
|:-----|:------|
| **眼见为实的错觉** | 看到 demo 在跑，管理者会认为「这已经在工作了，剩下的只是包装」 |
| **AI 的「轻松感」传染** | 生成 demo 的过程看起来太容易了（几分钟对话）→ 以为产品化也不难 |
| **归因错位** | 产品化慢被归因为团队能力问题（而非复杂度问题），导致管理者不相信开发者的估算 |
| **双向士气毁灭** | 管理者觉得「团队不行」，团队觉得「领导不懂」→ 信任破裂 |

## 2. 为什么管理者会低估 10-100 倍？—— 六层根因分析

### 2.1 认知层面：Demo 的「可用性启发」+「魔法错觉」

**可用性启发（Availability Heuristic）**：管理者「看到」了 demo 在运行——这个生动的视觉证据比抽象的工作量估算更有说服力。

**魔法错觉（"It Just Works" Illusion）**：AI 生成的 demo 看起来像魔法一样简单快速。人类大脑本能地将「看起来简单」等同于「做起来简单」——这在 AI 时代被放大了 100 倍。

```text
管理者看到的：
  Prompt -> 30秒 -> 精美功能

管理者未看到的：
  数据模型设计 -> 权限框架 -> 异常处理覆盖率 95%+
  -> 性能优化 -> 多租户隔离 -> 配置管理 -> 审计日志
  -> 监控告警 -> 文档编写 -> 回归测试 -> 兼容性测试
  -> 灰度发布 -> 回滚方案 -> 容量规划 -> SLA 保障
```

### 2.2 心理层面：完成后悔偏差 + 能力幻觉

| 心理机制 | 表现 | 放大因素 |
|:---------|:-----|:---------|
| **完成后悔偏差** | 「看起来这么简单，为什么你们要这么久？」 | AI demo 的「简单感」让这种偏差更严重 |
| **能力幻觉** | 「我能用 AI 几分钟生成 demo，说明我对这个功能理解透了」 | 实际上，Prompt 能力 ≠ 产品理解能力 |
| **幸存者偏差** | 只看到 demo 演示的成功路径，没看到失败路径的 100 倍工作 | AI demo 默认只展示完美路径 |

**关键洞察**: AI 让非技术人员第一次可以「亲手」做出一个看起来完整的功能。这种**亲身参与的幻觉**会让管理者对自己的判断力过度自信，比看别人的软文更危险——因为「是我做的」。

### 2.3 信息层面：Demo 的「信息隐藏」特性

一个工作的 AI demo 天然隐藏了以下关键信息：

| 隐藏信息 | Demo 表现 | 产品化需要 | 工作量倍率 |
|:---------|:----------|:-----------|:----------:|
| **边界条件** | 默认参数运行 | 每个输入组合测试覆盖 | 10-50× |
| **错误处理** | 只有正常路径 | 异常捕获·重试·降级·错误提示 | 5-10× |
| **安全与权限** | 无认证（本地跑） | 身份认证·RBAC·数据隔离·审计 | 5-20× |
| **性能与扩展** | 1 用户本地跑 | 1000 用户并发·P99 延迟 SLA | 10-50× |
| **数据持久化** | 内存存储/硬编码 | 数据库设计·迁移·备份·恢复 | 5-15× |
| **运维与监控** | 不需要（用完即弃） | 日志·告警·部署·升级·回滚 | 5-10× |
| **多租户隔离** | 单用户 | 数据和配置的租户级隔离 | 5-15× |
| **配置与定制** | 固定设置 | 可配置·可扩展·环境适配 | 3-10× |
| **合规与审计** | 无 | 数据隐私·合规审计·操作日志 | 5-10× |
| **文档与测试** | 无 | 功能测试·集成测试·性能测试·用户文档·运维文档 | 10-30× |

> **保守估算**: 从 AI demo 到生产级产品，工作量放大倍率在 **10-100×** 之间，取决于安全/合规/性能要求。

### 2.4 组织层面：AI 工具的个人效率 vs 团队开发效率的混淆

管理者在使用 AI 工具时的个人体验会扭曲对团队效率的认知：

```text
管理者的 AI 使用体验：
  Prompt -> 30秒 -> 代码/设计/文案 -> "太好用了"

管理者的推论：
  「我用 AI 30 秒搞定的事，开发团队应该 1 小时搞定。」

事实偏差：
  1. 管理者用的 AI 生成内容不需要经过：代码审查 × 安全审查 × 性能测试 × 兼容验证
  2. 管理者写的 Promot 直接输出，不需要：多人协作 × 版本管理 × 持续集成
  3. 管理者不需要维护：管理者不需要在 6 个月后回来修改自己 Prompt 生成的代码
```

**「一个人的 AI 加速 ≠ 一个团队的产品化加速」**——个人用 AI 产出原型和团队用工程流程产出产品是两种完全不同的活动。

### 2.5 考核层面：「可见产出」的误导性

| 考核周期 | Demo | 产品化 |
|:---------|:-----|:-------|
| **第 1 天** | ✅ 可见功能 | ❌ 架构设计（不可见） |
| **第 1 周** | (不存在了) | ❌ 数据模型 + 接口开发（部分可见） |
| **第 2 周** | — | ❌ 权限 + 错误处理（不可见） |
| **第 1 月** | — | ❌ 性能 + 兼容性（部分可见） |
| **第 2 月** | — | ✅ 功能上线（但被抱怨「为什么这么久」） |

**管理者在考核周期内看到的产出分布极不均匀**——Demo 的产出集中在前几天，而产品化的产出分布在前 80% 时间不可见、后 20% 时间突然涌现。这导致：

- 短周期考核 → 更倾向于喜欢 Demo 项目
- Demo 项目获得的认可度远高于同等实际工程量的产品化工作
- 团队产生逆向激励：「做 Demo 更划算」

### 2.6 根本原因：缺乏「工程复杂度」的认知模型

管理者（尤其非技术背景或脱离一线太久的）缺乏一个**从 Demo 到产品化的复杂度估算模型**：

```text
管理者的认知模型（过于简化）：
  Demo 工作量 × 1.2 = 产品化工作量

实际的工程模型：
  Demo 工作量 × (10~100) = 产品化工作量
  其中 90% 的工作是不可见的「地下工程」
```

**管理者需要的是一个「浮冰模型」**：

```text
　　　　　　^ 水面之上：Demo 展示的功能
　　　　　　|  o 可见的 10%
　　　　　　|  o 完美路径
　　　　　　|  o 默认参数
　　　　　　|
----------┿------------- 水面（可见/不可见分界线）
　　　　　　|
　　　　　　| 水面之下：产品化需要的 90%
　　　　　　|  o 边界条件全覆盖
　　　　　　|  o 错误处理与隔离
　　　　　　|  o 权限与安全框架
　　　　　　|  o 性能与容量规划
　　　　　　|  o 数据持久化与一致性
　　　　　　|  o 多租户与隔离
　　　　　　|  o 监控与告警
```

## 4. 归因偏差：为什么管理者会觉得「开发效率低下」

### 4.1 归因框架

管理者将产品化的「慢」归因为「开发效率低下」，本质上是**基本归因错误（Fundamental Attribution Error）**：

```text
现象：功能产品化花的时间远超预期

错误归因（基本归因错误）：
  「开发团队能力不行 / 效率太低」 <- 内部归因（人）

正确归因（系统思维）：
  「从 demo 到产品化的复杂度被严重低估了」 <- 外部归因（系统复杂度）
```

### 4.2 为什么管理者倾向「内部归因」

| 原因 | 具体表现 | 心理机制 |
|:-----|:---------|:---------|
| **可见性偏差** | 看不到代码复杂度，只看到「进度慢」 | 不可见的工作被归零 |
| **锚定效应** | Demo 的「30 秒」形成了不可动摇的锚点 | 任何超出锚点的工期都觉得长 |
| **AI 加速幻觉** | 「我 30 秒用 AI 生成的代码，你们为什么还要改 3 天？」 | 混淆了「生成代码」和「集成代码」 |
| **管理距离** | 离一线越远，越容易低估工程细节 | 信息传递中丢失了复杂度的上下文 |
| **幸存者偏差** | 只记得少数快速成功的 Demo，忘记了 90% 没落地的 | 选择性记忆 |

### 4.3 「效率低下」指控的破坏链

```text
管理者：「效率太低」
       v
团队陷入自证清白的循环：
  「我们每天工作 10 小时…」
  「边界条件有 300 多个…」
  「A 部门的接口一直没给…」
       v
管理者接受了理由，但内心没有真的相信
  （下次还会觉得效率低）
       v
团队感觉「领导不信任我们」-> 士气下降
       v
真正的效率问题（流程阻塞、跨部门协作）被掩盖
       v
管理者持续用「效率」压力驱动
       v
团队开始：
  - 砍掉不可见的工作（测试、文档）来满足工期
  - 只报喜不报忧
  - 优秀成员离职
       v
产品质量下降 -> 线上故障增多 -> 真正效率更低
```

### 4.4 真正影响「产品化速度」的因素

管理者应该区分以下三个不同性质的「慢」：

| 类型 | 原因 | 占比 | 责任归属 |
|:-----|:-----|:----:|:---------|
| **复杂度债** | 从 demo 到产品固有的 10-50× 工程放大 | **60-70%** | 架构复杂度本身，非团队的问题 |
| **流程阻塞** | 跨部门协调、审批流程、依赖 | **15-25%** | 组织级问题，需管理者解决 |
| **执行效率** | 技术能力、工具链、工作方式 | **10-20%** | 团队可优化部分 |

**如果管理者把 60-70% 的「复杂度债」误判为执行效率问题，就会做出完全错误的干预**——让团队「加速」而不是「消除流程阻塞」，导致团队压力增加但产出不增。

## 5. AI 时代的升级效应：为什么这个问题在 2024-2026 尤其严重

### 5.1 AI Demo 的「降维打击」

在 AI 之前，做一个功能的 demo 也需要相当的开发投入——所以管理者对工作量的感知与实际情况差距有限（~2-5×）。

但 AI 改变了游戏规则：

| 时代 | Demo 制作成本 | 产品化成本 | 落差倍率 |
|:-----|:------------:|:----------:|:--------:|
| 前 AI 时代（2015 前） | 数天-数周 | 数周-数月 | **2-5×** |
| 低代码时代（2018-2022） | 数小时-数天 | 数周-数月 | **5-10×** |
| AI 生成时代（2024-） | **数分钟-数小时** | 数月 | **10-100×** |

**AI 让 demo 制作成本降了 100-1000 倍，但产品化的成本几乎没有变。** 落差从「一个小山丘」变成了「马里亚纳海沟」。

### 5.2 AI 输出的「工程适配成本」

AI 生成的代码/设计面临额外的「适配成本」：

| 成本类型 | 说明 | 加权系数 |
|:---------|:-----|:---------|
| **集成成本** | AI 生成的代码需要适配现有架构、编码规范、接口约定 | 1.3-1.5× |
| **审查成本** | 人类必须审查 AI 代码的正确性、安全性和合理性 | 1.2-1.5× |
| **修正成本** | AI 代码中的「看似合理但实际错误」的修正 | 1.1-1.3× |
| **文档成本** | AI 代码缺乏现有项目的上下文文档 | 1.1-1.2× |
| **技术债成本** | AI 倾向于生成「能工作但不优雅」的解决方案 | 1.2-1.5× |
| **合计加权** | | **~1.7-3.4×** |

**讽刺的事实**: AI 生成的代码虽然加速了初稿，但在集成、审查、修正阶段的额外成本可能抵消 30-70% 的效率提升。管理者只看到了「生成加速」的 10×，没看到「适配减速」的 0.3-0.6×——净效果可能是 3-6× 而非 10×。

### 5.3 「给 ChatGPT 看 vs 给客户用」的两套标准

管理者自身使用 AI 的方式（个人→给 AI 看）和产品化（团队→给客户用）之间，存在根本性的质量要求差异：

| 维度 | 个人使用（给 AI 看） | 产品化（给客户用） |
|:-----|:-------------------|:------------------|
| **错误容忍** | 可以错，我改 Prompt | **零容忍**，直接影响业务 |
| **响应时间** | 几秒到几十秒都能接受 | **P99 < 1s**，否则客户投诉 |
| **安全性** | 不涉及客户数据 | **数据安全是底线** |
| **持续性** | 用完即弃 | **7×24 运行**，SLA 99.9%+ |
| **并发** | 单用户 · 我自己 | **1000+ 用户**同时使用 |
| **边界** | 我只用我测试过的场景 | **所有可能的输入**都要覆盖 |
| **可维护** | 不行就重写 | **6 个月后还能改** |

**管理者用第一套标准体验 AI，用第二套标准要求团队——中间的落差不是团队的效率问题，是标准本身的差距。**

### 5.4 AI 的「生产者膨胀」效应

AI 让每个管理者都成了潜在的「功能生产者」：

```text
2023 年以前：
  只有开发团队能做功能上线
  -> 管理者的冲动被「还要开发」的门槛过滤掉
  -> 只有 5% 的「这个可以做」会进入开发流程

2024 年以后：
  管理者自己能做出 Demo
  -> 「你看我都做出来了，你只需要包装一下」
  -> 80% 的「这个可以做」直接进入开发流程
  -> 需求膨胀 16×
```

**这不是开发效率的问题，是需求阀门被 AI 冲开了。** 团队接收到的「看起来合理」的需求量增长了 10×+，但团队产能没变——自然显得「效率低下」。

## 6. 真实案例解剖

### 6.1 案例一：SaaS 报表功能的 AI Demo 陷阱

```text
情境：一家 SaaS 公司的报表模块负责人
事件：管理者用 AI 生成了一段「自动报表生成 Demo」
      输入 Excel -> 输出可视化图表 -> 整个过程 30 秒
      管理者在 Demo Review 上大加赞赏，要求「一个月上线」

实际产品化过程：
  Week 1-2:  数据模型设计（8 种报表各自的数据源分布在不同系统中）
  Week 3-4:  权限集成（每个角色可见的报表不同，数据行级权限）
  Week 5-6:  性能优化（客户有 300 万行数据，AI demo 只演示了 100 行）
  Week 7-8:  边界处理（空数据、异常格式、超大数据集、特殊字符…）
  Week 9-10: 安全审查 + 合规（数据是否会泄漏？竞品数据隔离？）
  Week 11-12:灰度发布 + 用户测试 + 文档 + 培训材料

结果：上线花了 3.5 个月（超时 2.5 个月）
管理者评价：「开发效率有问题。」
复盘：AI demo 30 秒覆盖了 1% 的工作，剩下 99% 完全不可见
     投入 12 人·月，其中 8 人·月是 Demo 阶段完全没有暴露的工作
```

### 6.2 案例二：Chatbot 的「画皮」问题

```text
情境：一家金融科技公司想做 AI 客服
事件：管理者用 Claude 写了个客户意图识别的 Demo
      输入「我要查余额」-> 识别出 intent 并回复
      「这个准确率不错！一个月能上线吧？」

产品化后暴露的问题：
  - 1000+ 种问法的意图覆盖（Demo 只测试了 20 种）
  - 和现有客服系统的集成（Demo 独立运行）
  - 风险控制（客户输入敏感信息怎么办？答错造成损失谁负责？）
  - 人工兜底流程（AI 答不对时如何转到人工？）
  - 合规审查（金融场景需要监管批准）
  - 多语言支持（客户有中英文夹杂的输入）

结果：6 个月后才上线，上线后 2 周发现 37 个边界问题
管理者困惑：「Demo 上看着那么准，为什么产品化问题这么多？」
```

```text
团队的感受：「一个个人脚本被包装成了企业级产品，这本身就不合理。」
```

## 7. 系统性应对策略

### 7.1 认知层：建立「浮冰模型」

管理者需要建立从 Demo 到产品化的可视化认知模型：

```text
每个 AI Demo 都要回答：
  「这个是浮冰上面的 10%，还是全部？」

如果管理者看到 Demo 后想「要做」：
  必须由团队做一个「浮冰评估」：
  +----------------------------------------------+
  |  AI Demo -> 产品化浮冰评估模板                  |
  +----------------------------------------------+
  |  Demo 覆盖的功能点:        ______ (list)      |
  |  水下未覆盖:                                   |
  |  □ 数据模型/持久化（估: __ 人天）              |
  |  □ 权限/安全（估: __ 人天）                    |
  |  □ 错误处理/边界（估: __ 人天）               |
  |  □ 性能优化（估: __ 人天）                     |
  |  □ 运维/监控（估: __ 人天）                    |
  |  □ 测试/QA（估: __ 人天）                     |
  |  □ 文档/培训（估: __ 人天）                   |
  |  □ 集成/适配（估: __ 人天）                   |
  |  总估算: ______ 人天（Demo 的 __ 倍）          |
  +----------------------------------------------+
```

### 7.2 流程层：为 AI Demo 设立「工程放大系数」

在不同场景下，建立默认的放大系数：

| 场景 | 建议放大系数 | 说明 |
|:-----|:-----------:|:-----|
| 内部工具（单团队使用） | 5-10× | 低安全要求，可快速迭代 |
| 内部平台（多团队使用） | 15-30× | 中安全要求，需文档+支持 |
| 外部客户 Beta 版 | 20-40× | 中等质量要求，灰度可控 |
| 外部客户 GA 版 | 30-60× | 高质量要求，完整运维 |
| 企业级 SaaS（合规严） | 40-100× | 安全+合规+审计+SLA |
| 金融/医疗等强监管 | 100×+ | 严格监管合规 |

**使用方法**：

1. AI Demo 计时（从开始到生成 Demo 的时间）
2. × 放大系数 = 初步产品化工作量估算
3. 再经过团队细化评估

> 注意：系数不代表「可以做/不做」的决定，而是在决策前让管理者对量级有心理准备。如果 30 秒的 Demo × 100 倍 = 3000 秒 ≈ 1 天 → 团队细化评估可能是 2-3 个月 → 让管理者看到落差。

### 7.3 沟通层：团队的「反锚定」话术

当管理者锚定在 Demo 的「30 秒」时，团队需要结构化地破除锚点：

```text
管理者的锚点：「这个 AI 30 秒就做出来了，你们要 3 个月？」

团队的反锚定：

第一步：承认 Demo 的价值 ✅
「是的，AI 在核心功能的原型上确实很快，这个 Demo 帮我确认了方向可行。」

第二步：可视化潜水工作（不要说抽象概念，要具体） 🎯
「从 Demo 到产品，我们需要解决这些 Demo 之外的问题：
  1. 数据安全：Demo 用的是本地测试数据，产品需要对接 3 个不同的数据源，
     每个都有不同的权限设置和网络隔离 -> 预计 2 周
  2. 边界处理：Demo 只跑了我们测试的 20 个场景，实际有 300+ 种可能的输入组合，
     其中 50 种需要特殊处理 -> 预计 3 周
  3. 性能：Demo 处理 100 行数据，客户真实数据是 1000 万行 ->
     需要重新设计数据处理引擎和缓存策略 -> 预计 3 周
  ...（列出 5-8 个关键点，每个给具体的人天估算）」

第三步：用 Demo 加速部分抵消落差 💡
「好消息是，AI Demo 帮我们节省了架构探索的时间。
  如果没有 Demo，我们光需求澄清和方案讨论就要花 2 周。
  现在有 Demo 作为参考，这部分时间可以省掉。
  但剩下的工程化工作，是 Demo 覆盖不到的。」

第四步：给出可选的渐进路径 🚀
「方案一（你想要的完整版）：3 个月，覆盖所有功能
 方案二（MVP 先行版）：6 周，只支持核心场景，其余后续迭代
 方案三（实验性上线）：3 周，灰度给 10% 客户，边用边迭代
 你倾向哪个？」
```

### 7.4 组织层：建立「Demo → 产品」的分级管道

将需求和产出分为不同级别，每一级有对应的工程投入标准：

| 级别 | 名称 | 开发周期 | 质量要求 | 决策权 |
|:-----|:-----|:--------|:---------|:-------|
| **L0** | 概念验证（Spike） | 1-3 天 | 能跑即可，不求质量 | 团队自主 |
| **L1** | 内部实验（Experimental） | 1-2 周 | 可用但有缺陷，仅内部 | Tech Lead |
| **L2** | 受限 Beta | 3-6 周 | 核心功能完整，边界有损 | 产品经理 |
| **L3** | GA 发布 | 2-4 月 | 全功能，完整运维 | 管理团队 |
| **L4** | 企业级产品 | 4-8 月+ | 企业级安全/性能/合规 | 高管层 |

**核心原则**：

- **L0/L1 不需要管理层审批**（团队自主判断）
- L2+ 需要**正式评估浮冰模型后才能进入管道**
- 任何级别的**产品化成本必须在 Demo 审批阶段就明确交代**
- 允许 Kill：L0 验证方向不可行后直接放弃，不丢人

### 7.5 管理层的自我免疫

| 策略 | 具体做法 |
|:-----|:---------|
| **动手前先问「浮冰评估」** | 看到 AI Demo 后不急于喊「可以做」，而是问团队「水面之下的工作大概多少？」 |
| **建立 Demo → 产品的「成本表」** | 记录最近 5 个 AI Demo 到产品化的实际耗时 vs Demo 耗时，建立自己的量化认知 |
| **区分「AI 提示词工程」和「产品工程」** | 前者是「我能用 AI 做什么」，后者是「什么能可靠地交给客户」 |
| **用 Demo 做需求澄清，而非工期估算** | Demo 的价值在于「验证方向对不对」，不是「验证工作量多大」 |
| **接受「Demo 只覆盖 5%」作为默认假设** | 在看到确凿证据前，默认任何 AI Demo 只覆盖了产品化工作的 5% |

### 7.6 文化层：重新定义「效率」

```text
错误的效率观：
  效率 = 功能产出速度（功能数量 / 时间）
  -> 推崇快速出 Demo，惩罚「慢」的产品化

正确的效率观：
  效率 = 客户价值 / (工程投入 × 维护成本)
  -> Demo 的「客户价值」为 0（还没交付），效率为 0
  -> 产品化的效率要看长期客户价值
```

**文化的最终目标**：让团队在展示 AI Demo 时不会感到压力（怕被要求产品化），而是能自信地说：

> 「这个 Demo 验证了方向可行。但要从 Demo 到让客户放心用，还有 A、B、C、D 四个维度的工作要做，大约需要 X 人·月。要不要做？还是先做一轮用户测试再决定？」

## 8. 总结与检查清单

### 8.1 核心结论

> **AI Demo 到产品化的落差不是开发效率问题，而是「可见工作 vs 不可见工作」的认知扭曲。AI 让落差从 2-5× 急剧放大到 10-100×，但产品化的真实成本并没有变。**

| 关键认知 | 错误版本 | 正确版本 |
|:---------|:---------|:---------|
| Demo 的价值 | 「这个功能已经能跑了」 | 「这个方向值得探索了」 |
| 产品化的延迟 | 「开发效率太低」 | 「工程的固有复杂度如此」 |
| AI 的效率 | 「AI 让开发快了 100 倍」 | 「AI 让原型快了 100 倍，产品化快了 20-50%」 |
| 团队的角色 | 「团队落地太慢」 | 「团队在承受落差的所有不可见工作」 |
| 管理者的角色 | 「提出方向，催促进度」 | 「理解复杂度，排除组织阻塞」 |

### 8.2 管理者的检查清单

**每次看到 AI Demo 想「产品化」时，先回答以下问题**：

```text

□ 这个 Demo 展示的是「完美路径」还是「完整路径」？
   *完美路径：只演示了正常情况下的一种输入和输出
   *完整路径：覆盖了各种边界、异常、并发场景

□ Demo 估计覆盖了产品化工作量的百分之几？
   *主观判断后，让团队做「浮冰评估」验证

□ 放大系数估算：Demo 耗时 × 场景系数 × 安全系数？
   *内部工具 5-10×，外部 GA 版 30-60×，强监管 100×+
   *这个数字的绝对值在我的可接受范围内吗？

□ 如果要做，选择哪个交付路径？
   □ MVP / 最小产品（1-2 月）
   □ 完整版（3-6 月）
   □ 实验性上线（先灰度/有限场景）

□ 对应的资源从哪来？要砍掉什么？
   *没有资源就维持现状。新方向意味着旧方向被取消或延期。

□ 我做为管理者，能为产品化排除哪些组织阻塞？
   *跨部门沟通？审批流程？依赖资源？这些是我该解决的，不是团队的问题。

□ 如果 6 个月后回头看，不做这个功能的损失是否真的存在？
   *如果说不清楚，先放一放。
```

### 8.3 团队的检查清单

**当管理者拿着 AI Demo 过来说「做这个」时**：

```text
□ 立即做「浮冰评估」列出所有水面以下的工作
□ 每种工作给出「人天」估算（不要模糊的「需要时间」）
□ 用具体例子说明 Demo 和产品化的差距：
   *「Demo 处理了 10 行数据 / 产品要处理 1000 万行」
   *「Demo 没有登录 / 产品需要对接 SSO」
   *「Demo 本地跑 / 产品要支持 500 并发」
□ 给出至少两个可选路径（MVP vs 完整版）
□ 明确提出需要管理者解决的「组织阻塞」
□ 不要只说「这很复杂」——要说「具体哪里复杂，需要多少工作量」
```

### 8.4 一句话口诀

> **看 Demo 别上头，浮冰评估先走；说效率别甩锅，组织阻塞先破。**

#### 10.9.3 数据分析

> 按中位数估算，将工作量映射回管理者的直觉认知：

| 管理者的直觉 | 实际情况 |
|:-------------|:---------|
| 「这个功能很简单，AI 30 秒就生成了」 | 核心功能消化 = **8 人天**（让 Demo 可被重复使用） |
| 「一个月能上线吧？」 | 最简 MVP = **~80-120 人天**（F+关键S+关键Q）→ 2-3 名工程师 × 2-3 月 |
| 「一个 feature 而已」 | 完整产品化 = **~443 人天** → 3 名工程师 × 7-8 月 |
| 「为什么开发效率这么低？」 | **90%+ 的工作完全不可见**（只有第一层的 8 人天部分可见） |

#### 10.9.4 快速估算速查表

> 为管理者提供一个速查：看到不同类型的 AI Demo 时，产品化需要多人、多久。

| Demo 类型 | Demo 耗时 | 最简 MVP（3 人） | 完整版（3 人） | 企业级（4 人） |
|:----------|:---------:|:---------------:|:-------------:|:--------------:|
| **单功能工具**（一个 AI 功能点） | 30 分钟-2 小时 | 1-2 个月 | 3-5 个月 | 5-8 个月 |
| **简单 CRUD + AI**（数据输入+AI 处理+结果输出） | 2-4 小时 | 2-3 个月 | 4-6 个月 | 6-10 个月 |
| **多人协作 + AI**（含权限+工作流） | 4-8 小时 | 3-5 个月 | 6-9 个月 | 8-14 个月 |
| **AI 驱动数据面板/分析系统** | 2-6 小时 | 2-4 个月 | 5-8 个月 | 8-12 个月 |
| **AI Agent / 自动流程** | 1-4 小时 | 3-6 个月 | 6-12 个月 | 10-18 个月 |

> **使用示例**：管理者看到一段「AI 自动生成报表」的 Demo（30 分钟产出），想产品化。
> 速查：类型为「AI 驱动数据面板/分析系统」。
> → 最简 MVP：2-4 个月（3 人），完整版：5-8 个月（3 人）。
> → 管理者可据此做资源规划，而非凭「30 分钟」做直觉判断。

### 10.10 使用指引

#### 团队如何使用本清单

```text
每次收到「这个 Demo 要做成产品」的需求时：

Step 1: 确定场景系数（见 10.1）
  - 内部工具(×0.5) / 内部平台(×1.0) / 外部Beta(×1.5) / 外部GA(×2.0) / 强监管(×3.0)

Step 2: 逐层扫描清单，标记需要的项
  - 不是所有项都需要——裁剪出本项目的实际需求
  - 关键：不要只标记「要做」，要标记「现有 Demo 已经覆盖了哪些」

Step 3: 估算人天并汇总
  - 每项填入估算人天
  - 累加得到「总工作量估算」

Step 4: 可视化「浮冰报告」
  +-----------------------------------------------------+
  |  浮冰评估报告                                       |
  |                                                     |
  |  Demo 耗时: 30 分钟  ->  完成度: <5%                 |
  |                                                     |
  |  水面以上（已可见）:  8 人天  (第一层)               |
  |  水面以下（隐藏）  :  435 人天 (第二-六层 + 跨层)    |
  |  --------------------------------------------        |
  |  总工作量        :  443 人天                         |
  |  团队 3 人 × 预期工期:  ~7.5 个月                    |
  |                                                     |
  |  可选路径:                                          |
  |  □ MVP（~80人天，2-3个月）-> 覆盖核心流程无安全      |
  |  □ 完整版（~443人天，7-8个月）-> 全功能全质量       |
  +-----------------------------------------------------+

Step 5: 带着报告与管理者对话
  - 不要只给数字，用「浮冰图」展示可见 vs 不可见工作
  - 给出至少两个可选路径
  - 明确提出需要管理者解决的「组织阻塞」事项（清单中的哪些跨部门依赖）
```

#### 管理者的对照速查

| 如果管理者说 | 对应的实际工作层 | 回应策略 |
|:-------------|:----------------|:---------|
| 「这个 AI 已经能跑了」 | 涉及 F-01 到 F-06（8 人天） | 「核心逻辑可以用了，但离给客户用，还有 400+ 人天的工作」 |
| 「为什么要这么久？」 | 涉及全清单 | 「我选 5 个最大的隐藏项给你看看（如：权限 + 多租户 + 边界覆盖 + 高可用 + 合规）」 |
| 「只是个报表功能而已」 | 涉及 Q-01 到 P-08（57-166 人天） | 「报表背后有 300 种边界、1000 万行数据处理、秒级响应要求」 |
| 「不行先做个 MVP」 | 涉及 F+关键S+关键Q（~80 人天） | 「好的，MVP 覆盖核心流程，但权限是简版，安全后补，运维手动」 |
| 「安全合规必须到位」 | 涉及第四层全部（66-175 人天） | 「好，那工期要 ×1.5，这些工作量是跑不掉的」 |
