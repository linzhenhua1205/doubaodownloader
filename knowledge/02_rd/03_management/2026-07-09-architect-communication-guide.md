## 一、架构师的角色定位

在运维软件项目中，架构师不是纯技术角色，而是**技术×管理×沟通**的复合枢纽：

```text
+-------------------------------------------------------------+
|                  架构师的实际角色                             |
|                                                             |
|  +------------+  +------------+  +--------------------+   |
|  | 技术架构师   |  | 需求翻译器  |  | 跨域协调者         |   |
|  |             |  |            |  |                    |   |
|  | . 技术选型   |  | . 把业务   |  | . 产品-研发-销售    |   |
|  | . 架构设计   |  |   需求翻译 |  |   三方拉扯的缓冲层  |   |
|  | . 技术风险   |  |   成技术   |  | . 资源冲突的平衡者  |   |
|  |   识别      |  |   方案     |  | . 信息不对称的弥合者 |   |
|  +------------+  +------------+  +--------------------+   |
|                                                             |
|  核心价值: 在"技术可行性"和"业务现实性"之间找到最佳路径      |
+-------------------------------------------------------------+
```

### 1.1 架构师在本项目的关键任务

| 任务 | 说明 | 优先级 |
|:-----|:------|:------:|
| **开源选型决策** | 在 OpenBMC/Prometheus/Grafana/ELK 等开源方案中选择适合的基线 | **P0** |
| **最小功能集合定义** | 拆解哪些是"必须做"的，哪些是"等需求再说"的 | **P0** |
| **技术预研 vs 产品化边界** | 明确技术验证到什么程度算"够"，不陷入无限打磨 | **P0** |
| **与 L12 软件栈的整合点** | 识别运维软件与现有软件栈的关系（独立/嵌入/接口对接） | P1 |
| **演示中心部署架构** | 设计可部署到演示中心的轻量方案 | P1 |
| **产品材料技术部分** | 输出技术白皮书/架构说明等材料的技术内容 | P1 |

## 二、面向各角色的沟通策略

### 2.1 与管理层/产品负责人沟通（"要简洁、要结论、要安全感"）

**管理层最关心的三个问题**:

1. **要投多少钱？** → 10-15 人月，明确且可控
2. **要产出什么？** → 技术验证报告 + 最小原型 + 产品材料
3. **如果市场需求不来呢？** → 内部提效也有价值，随时可以停止

#### 沟通话术模板

```text
场景：争取管理层对项目的支持

"我想汇报一下运维软件项目的定位和推进思路。

结论：
1. **定位是技术预研，不是产品立项** — 目标是开源整合 + 内部能力建设，
   不是做商业化产品去卖
2. **投入控制在 10-15 人月** — 先做最小功能集合，满足自我部署和纳管需求
3. **验收标准明确** — 输出技术验证报告 + 最小可用原型 + 产品材料
4. **与业务节奏对齐** — 不影响固件和 AI Infra 管理软件的优先级，
   运维软件在管理层级上排在后面，只是先做技术储备
5. **如果前场一直没有需求，第一期完成后可以结项** — 不绑定长期投入

关于需求来源的问题，我的理解是：
- 短期：先满足内部提效和演示中心部署需求（这是已经存在的需求）
- 长期：通过月度同步机制持续收集前场需求
- 如果前场一直没有明确需求，第一期产出作为技术储备也是有价值的
  — 在客户有需求时我们已经有了能力，而不是从零开始

希望按'技术预研'类别立项上会，走正规流程。
需要管理层确认的是：
① 是否可以按技术预研立项？
② 10-15 人月的投入预算是否认可？
③ 第一期验收标准是否可以按我上面说的来定？
```

#### 管理层沟通原则

| 原则 | 说明 |
|:-----|:------|
| **结论先行** | 前三句话说完核心结论，再展开理由 |
| **给安全感** | 强调"可控""可停""不绑定"，降低决策负担 |
| **量化** | 人月、输出物、时间节点，全部量化 |
| **尊重流程** | 主动提出"上会立项"，展示对管理规则的尊重 |
| **给选择题** | 不要说"我们想做什么"，要说"有三个选项，我建议第二个" |

### 2.2 与销售/市场负责人沟通（"降低负担、提供武器、建立闭环"）

**销售核心痛点**: 客户已有稳定供应商，推新产品是"得罪客户关系"的苦差事

#### 沟通话术模板

```text
场景：请销售协助收集需求

"张总，关于运维软件的需求收集，我想对齐一下定位——

这个项目目前不是要做产品去卖，而是做技术储备和内部能力建设。
所以不需要销售这边花精力去推，也不影响现有的客户关系。

我这边需要销售帮忙的是——放在一个很轻的优先级上：
1. **日常聊客户时顺带问一嘴** — 不是专项调研，不问也不勉强
2. **关注这几个问题就够了**（可以给销售一张 1 页的问题清单）：
   - 客户目前用什么运维工具？
   - 有没有什么运维痛点？
   - 对 AI 集群运维有什么新需求？
3. **不需要写报告** — 月度同步会上口头说两句就行

另外，我会整理一份'AI 集群运维常见痛点清单'，
销售去客户那里聊技术话题时可以用作话题切入，
不是推销产品，是体现我们技术深度和专业性。"
```

#### 销售沟通原则

| 原则 | 说明 |
|:-----|:------|
| **降低压力** | 明确告知"不是让你去卖"，说清楚定位 |
| **提供武器** | 输出"运维痛点清单"，帮销售在客户面前体现专业度 |
| **降低门槛** | "顺带问"而不是"专门调研"，口头传达不是书面报告 |
| **给反馈** | 销售反馈的需求，在月度会给出回应，形成闭环 |

---

### 2.3 与产品洞察/市场策略沟通（"尊重判断、澄清定位、开放合作"）

**产品洞察核心关注**: 不想做"自嗨"型产品，要求价值落脚点必须是前场

#### 沟通话术模板

```text
场景：对齐项目价值判断标准

"关于运维软件项目，我想澄清一下定位，避免误解——

**这个项目不是产品立项，而是技术预研。**
这两个的区别是：
- 产品立项：承诺对外输出商业价值，需要前场需求驱动
- 技术预研：解决'我们有没有这个能力'的问题，价值在内部

第一期目标很清楚：
1. 把开源方案整合起来，形成我们的技术能力基线
2. 部署到演示中心，让客户能看到'我们有运维能力'
3. 输出产品材料的技术部分

关于价值判断，我完全认同你的观点：
- '前场没需求就不做'——对产品立项来说是对的
- 但技术预研的决策逻辑是：**我们预测这个方向未来会有需求，提前储备比临时抱佛脚好**

我建议的分工是：
- 技术预研由我这边负责，输出技术能力和架构方案
- 产品洞察负责判断'什么时候应该从技术预研升级为产品立项'
- 月度同步会上我分享技术进展，你分享前场洞察
- 当你判断有足够的需求信号时，我们再一起做产品立项

这样既不会错失技术窗口，也不会在产品化上冒进。"
```

#### 产品洞察沟通原则

| 原则 | 说明 |
|:-----|:------|
| **尊重专业判断** | 肯定"前场需求驱动产品"的逻辑是正确的 |
| **区分定位** | 清晰区分"技术预研"和"产品立项"，避免混淆 |
| **给判断权** | 把"什么时候转产品"的决定权交给产品侧 |
| **主动分享** | 定期同步技术进展，建立信任 |

### 2.4 与项目负责人/研发团队沟通（"给方向、给边界、给工具"）

**研发团队核心需求**: 明确做什么、不做什么、资源在哪里

#### 沟通话术模板

```text
场景：给研发团队开工动员

"关于运维软件项目的第一期启动，我来说一下技术层面的安排：

**做什么（范围明确）**：
1. 开源选型 -> 确定 Prometheus/Grafana/ELK/Loki 这些组件的选型
2. 最小功能集合 -> 设备纳管 + 基础监控 + 告警 + 简单 Dashboard
3. 演示中心部署 -> 设计轻量部署方案，适配演示环境
4. 产品材料输出 -> 技术白皮书 + 架构说明

**不做什么（边界明确）**：
1. ❌ 不做超节点专属功能（后延）
2. ❌ 不做完整商业产品（不是目标）
3. ❌ 不做深度诊断/根因分析（超出第一期范围）
4. ❌ 不做大规模集群管理（先验证单机/小集群）

**技术路线**：
1. 基座：OpenBMC（已有） + Prometheus + Grafana
2. 日志：Loki（轻量）或 ELK（完整）
3. 告警：AlertManager
4. 部署：容器化 + Ansible 自动化

**资源情况**：
- 演示中心设备：下周确定时间，先并行做软件设计
- 备选方案：本地服务器 + 虚拟机可以先用起来
- 人力：锁定 10-15 人月，集中在核心功能上

大家看看有什么需要对齐的？"
```

#### 研发团队沟通原则

| 原则 | 说明 |
|:-----|:------|
| **明确边界** | 说清楚做什么和不做什么，避免团队做无用功 |
| **技术路线清晰** | 给出选型方向，但留讨论空间（'大家看看'） |
| **提前说明资源约束** | 设备、人力、时间的不确定性提前告知 |
| **保护团队** | 对外由架构师挡掉不必要的需求变更 |

## 三、关键沟通场景话术

### 3.1 场景：立项评审会

```text
立项汇报结构建议:

【第一页：一页纸结论】
- 项目名称：AI 基础设施运维技术预研
- 定位：技术储备，非产品立项
- 投入：10-15 人月
- 产出：技术验证报告 + 最小原型 + 产品材料
- 验收标准：满足内部部署+纳管需求

【第二页：背景与问题】
- 为什么现在做？算力集群规模增长，运维复杂度指数上升
- 不做会怎样？客户问起来没有方案，只能回答"用开源的"
- 长期价值？AI 基础设施运维是确定性趋势

【第三页：范围与边界】
- 范围：开源整合 + 最小功能 + 演示中心部署
- 边界：不做超节点、不做商业产品、不做深度诊断

【第四页：技术方案概要】
- 架构图 + 组件选型 + 部署方案

【第五页：投入与产出】
- 人力：10-15 人月 | 周期：~6 个月
- 输出物清单：5 项具体可验收产出
- 风险与缓解：3 项主要风险 + 应对措施

【第六页：后续计划】
- 第一期完成后评估 -> 决定是否继续 / 是否转产品
- 月度同步机制：技术与前场信息对齐
```

### 3.2 场景：争取演示中心资源

```text
沟通要点:

1. **运维软件不需要 Nvidia 卡** -> 不依赖被禁用的 GPU 资源
   （降低资源调度难度）

2. **最小资源需求** -> 2 台 x86 服务器 + 1 台管理交换机
   （不是大资源需求，容易满足）

3. **承诺不占用长期资源** -> 验证完成后可释放
   （给资源协调者安全感）

4. **给对方面子** -> "理解演示中心有规划调整，我这边可以配合时间安排"
   （尊重对方的资源调度权，不施压）

话术示例:
"我理解演示中心近期规划有调整，不会催着要设备。
我的需求比较简单——2 台 x86 服务器 + 1 台交换机，
不需要 GPU，验证完成后可以释放。
等您那边规划确定后告诉我时间节点，我可以配合。"
```

### 3.3 场景：回答"前场没有需求为什么要做"

```text
回答框架:

"我理解这个质疑。我来解释一下为什么这种情况下仍然值得做——

**第一，区分'内部能力'和'外部产品'。**
- 外部产品要需求驱动，这是对的
- 但内部能力建设是'等需求来的时候我们得有'的逻辑
- 就像你不会在客户说要液冷方案的时候才开始研究液冷

**第二，这个项目的投入很小，风险可控。**
- 10-15 人月，对标 1-2 个人的半年投入
- 产出是明确的：技术验证报告 + 最小原型 + 产品材料
- 如果第一期做完发现方向不对，可以随时停

**第三，演示中心部署需求是已经存在的真实需求。**
- 客户来看演示中心，我们希望展示'我们有运维能力'
- 不是等客户要了再做，而是提前准备好

**总结一下：投入小、风险低、有产出、有内部价值。
不做商业承诺，做技术储备。
等到前场有明确需求时，我们已经准备好了能力基线。**"
```

### 3.4 场景：与产品洞察讨论"价值落脚点"

```text
沟通框架:

"关于价值落脚点的问题，我理解你的担心。
我们是否可以这样讨论——

运维软件的价值可以分为三个层次：

**第一层（现在）**：内部验证 + 能力储备
- 价值：技术团队有了运维能力基线，能回答'我们用什么做运维'
- 体现：演示中心展示了运维能力

**第二层（半年后）**：支持小规模客户部署
- 价值：如果有客户需要基础运维方案，我们能交付
- 体现：可以直接部署的开源整合方案 + 文档

**第三层（1-2 年后）**：完整 AI 运维产品
- 价值：差异化竞争力，成为销售加分项
- 体现：智能诊断、根因分析、预测性维护等

我们现在在做的是第一层——这是最基础、最没有争议的一层。
第二层和第三层需要前场需求来驱动，我不会超前投入。
这样讨论你有认同的点吗？"
```

## 四、沟通红线与注意事项

### 4.1 绝对不要说的（红线）

| 话术 | 问题 | 改为 |
|:-----|:-----|:-----|
| "这个项目很有前景，值得大力投入" | 显得冒进、不理智 | "这个方向长期有价值，但目前先做最小投入验证" |
| "销售那边不积极，不配合" | 推卸责任、制造对立 | "销售反馈了客户现状，我们需要调整预期和合作方式" |
| "管理层不懂技术，看不到价值" | 不尊重决策者 | "我理解管理层关注投入产出比，所以我们需要量化产出" |
| "先做了再说，立项慢慢来" | 违反流程，风险极大 | "我先准备立项材料，走正规流程获批后启动" |
| "这个功能很简单，几天就能搞定" | 低估复杂度，后续被动 | "这个功能第一期作为 MVP 实现，后续再迭代完善" |

### 4.2 必须说的（加分项）

| 话术 | 效果 |
|:-----|:------|
| "我建议按技术预研类别立项" | 展示对流程的尊重，降低决策风险 |
| "第一期完成后做价值评估，如果方向不对可以随时停" | 给管理层安全感 |
| "这个项目不依赖 Nvidia 卡" | 降低资源调度难度 |
| "10-15 人月，产出明确可验收" | 量化投入产出，降低决策负担 |
| "月度同步前场信息和技术进展" | 建立持续对齐机制 |

### 4.3 敏感话题处理

| 敏感话题 | 处理原则 | 话术示例 |
|:---------|:---------|:---------|
| **演示中心资源不确定** | 不追不催，表达理解，备 B 方案 | "理解规划有调整，我等您结论。这边可以先做软件设计并行推进" |
| **销售反馈"推进困难"** | 不批评、不辩论，调低预期 | "了解，所以我们不做商业化，先把技术能力建起来" |
| **管理层质疑需求** | 不辩解、不硬顶，重新定位 | "我理解您的关注点。所以这个项目的定位是技术预研，不是产品立项" |
| **产品洞察质疑价值** | 尊重专业判断，给出判断权 | "产品化时机由您判断，我先做技术储备" |
| **团队担心投入被浪费** | 给方向、给边界、给安全感 | "第一期目标很明确，做到了就是成功。做完了即使没有后续也是有价值的" |

## 五、沟通节奏与时间线

### 5.1 沟通时间线

```text
M+0 (本周)        M+1           M+2           M+3           M+4           M+5
+-------------+--------------+-------------+-------------+-------------+
| ##########  |              |             |             |             |
| 立项材料     |              |             |             |             |
| 管理层对齐   |              |             |             |             |
| 销售对齐     |              |             |             |             |
| 产品洞察对齐  |              |             |             |             |
|             | ##########   |             |             |             |
|             | 月度同步#1   | 月度同步#2   | 月度同步#3   | 月度同步#4   | 月度同步#5
|             | 资源确认     | 阶段评审     | 原型演示     | 部署验证     | 第一期评审
|             |              |             |             |             |

关键沟通动作:
M+0W1: 与管理层对结论 -> 确认立项方向
M+0W2: 与销售对齐预期 -> 降低负担、提供材料
M+0W3: 与产品洞察对齐 -> 区分技术预研 vs 产品立项
M+0W4: 与研发团队对齐 -> 明确边界、技术路线
M+1W1: 立项上会 -> 正式获批
M+1W2: 资源到位确认 -> 启动开发
M+5W2: 第一期验收评估 -> 决定下一阶段
```

### 5.2 月度同步会结构建议

```text
月度同步会 Agenda (30分钟):

1. 技术进展 (10min) — 架构师汇报
   - 做了什么、技术选型决策、遇到什么问题
   - 下一步计划

2. 前场洞察 (10min) — 销售/产品洞察汇报
   - 客户有什么新需求、竞品有什么新动向
   - 有没有值得关注的需求信号

3. 对齐与决策 (10min) — 全员讨论
   - 是否需要调整方向？
   - 是否有需求信号足以触发产品立项评估？
   - 下一阶段工作安排
```

## 六、架构师自检清单

每次重要沟通前，过一遍这个清单：

| 检查项 | 通过标准 |
|:-------|:---------|
| □ **明确本次沟通的目标** | 我要达成的具体目标是什么？（立项/资源/对齐/信息同步） |
| □ **结论先行** | 前三句话能不能说清楚核心结论？ |
| □ **量化支撑** | 每个论据是否有数据/人月/时间节点支撑？ |
| □ **预判对方立场** | 对方最关心什么？有什么担忧？ |
| □ **给出选择** | 是否提供了 2-3 个可选方案而不是单一答案？ |
| □ **留有退路** | 是否说了"可以停""可以调整""尊重您的判断"？ |
| □ **后续明确** | 是否明确了"下一步做什么、谁做、什么时候完成"？ |
| □ **没有触红线** | 有没有说任何可能被理解为不尊重/冒进/推卸责任的话？ |
