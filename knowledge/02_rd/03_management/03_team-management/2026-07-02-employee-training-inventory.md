## 1. 全景总览

### 1.1 培训体系金字塔

```text
                  +-----------------------+
                  |    培训评估与认证       |  <- 考核闭环
                  +-----------------------+
                  |   管理进阶 + 领导力     |  <- 高潜/管理梯队
                  +-----------------------+
                  |  软技能 + 综合素养      |  <- 全员必修
              +---+-----------------------+---+
              |   | 安全合规 + 质量体系     |   |  <- 底线
              |   +-----------------------+   |
  结构化培训 <-|   | 技术分享 + 复盘机制     |   |-> 日常机制
              |   +-----------------------+   |
              |   |  流程规范 + 领域知识    |   |  <- 专业纵深
              +---+-----------------------+---+
                  |  新人培训 + 导师制      |  <- 入口
                  +-----------------------+
```

### 1.2 培训分类矩阵

| 维度 | 形式 | 频次 | 面向人群 | 组织者 |
|:-----|:-----|:----|:---------|:-------|
| 新人培训 | 集中授课+在岗带教 | 按批次（每季度或每半年） | 新入职员工 | HR+用人部门 |
| 流程培训 | 授课+考试+演练 | 按需（新流程发布时） | 全员/相关角色 | 流程Owner |
| 技术分享 | 讲座+研讨+Demo | 周/双周 | 团队/跨部门 | 技术委员会/团队TL |
| 复盘 | 会议+文档沉淀 | 按事故/项目/周期 | 项目组/事件相关人 | 项目经理/技术经理 |
| 管理培训 | 外训/内训/读书会 | 月/季 | 管理者/高潜 | HR+外部机构 |
| 软技能 | 工作坊+在线课程 | 双月/季 | 全员 | HR |
| 安全合规 | 必修课+演练 | 年度+事件驱动 | 全员 | 信息安全/合规部 |

### 1.3 培训体系的核心原则

| 原则 | 说明 |
|:-----|:-----|
| **从业务中来，到业务中去** | 培训内容来自实际项目问题、事故复盘、技术瓶颈，而非纯理论 |
| **70-20-10 模型** | 70% 在岗实践 + 20% 交流反馈 + 10% 正式培训 |
| **可复用沉淀** | 每次培训和分享必须有产出物（文档/视频/案例库） |
| **考核闭环** | 培训效果必须可衡量：考试/实操/反馈/行为改变 |
| **按需分层** | 不同职级、不同角色培训内容和深度不同，拒绝"一刀切" |

## 2. 新人培训体系

### 2.1 培训阶段划分

```text
入职前 ---> 入职第1周 ---> 第2-4周 ---> 第2-3月 ---> 第4-6月
  |          |            |            |            |
  v          v            v            v            v
入职准备   集中培训    部门轮训    项目实战    独立交付
(文档预读)  (文化+制度) (技术栈)    (带教上岗)  (考核转正)
```

### 2.2 各阶段详细内容

#### 阶段一：入职前（Day -7 ~ Day 0）

| 项目 | 内容 | 形式 | 负责人 |
|:-----|:-----|:----|:-------|
| 入职手册发放 | 公司介绍、制度手册、IT使用指引 | 邮件/文档 | HR |
| 工作环境准备 | 工位、电脑、VPN、邮箱、账号开通 | 自动化+行政 | IT/行政 |
| 知识预读 | 组织架构图、产品线概览、企业文化白皮书 | PDF/在线文档 | HR |
| 导师确认 | 提前指定导师并建立联系 | 邮件/系统 | 用人部门 |

#### 阶段二：集中培训（Day 1 ~ Day 5）

**通用模块（HR主导）**：

| 序号 | 课程 | 时长 | 形式 |
|:----|:-----|:----|:----|
| 1 | 公司介绍、发展历程、组织架构 | 2h | 讲座 |
| 2 | 企业文化、价值观、行为准则 | 2h | 讲座+研讨 |
| 3 | 人事制度（薪酬/考勤/考核/晋升） | 1.5h | 讲座 |
| 4 | 财务报销流程 | 1h | 实操 |
| 5 | IT工具使用（OA/邮件/IM/代码仓库/文档平台） | 2h | 实操+演练 |
| 6 | 信息安全与合规（数据分类/密码策略/保密协议） | 1.5h | 讲座+考试 |
| 7 | 职业道德与合规红线 | 1h | 案例教学 |

**专业模块（技术部门主导）**：

| 序号 | 课程 | 时长 | 形式 |
|:----|:-----|:----|:----|
| 8 | 产品线概览：服务器产品家族与路线图 | 2h | 讲座 |
| 9 | 研发流程总览：IPD TR1-TR6 全流程 | 2h | 讲座+流程图 |
| 10 | 技术架构：整机系统架构 101 | 2h | 讲座 |
| 11 | 质量文化：缺陷管理和质量门禁 | 1.5h | 案例教学 |
| 12 | 实验室安全与操作规程 | 1h | 实操+考试 |

#### 阶段三：部门轮训（第2-4周）

| 形式 | 内容 | 产出物 |
|:-----|:-----|:-------|
| 部门串讲 | 各部门负责人介绍本部门职责、关键流程、协作接口 | 各部门核心接口人清单 |
| 岗位影子 | 跟随老员工参与日常工作，观察工作模式 | 观察笔记 |
| 技术栈扫盲 | 核心工具链、编程语言、平台、SDK 快速上手 | 环境搭建确认单 |
| 代码走读 | 了解模块代码架构、编码规范、关键路径 | 代码走读记录 |
| 文档研读 | 核心设计文档、架构文档、接口规范 | 阅读笔记+提问清单 |

#### 阶段四：项目实战（第2-3月）

| 活动 | 说明 | 检查点 |
|:-----|:-----|:-------|
| 小任务实战 | 从简单独立的任务开始（修复bug/写测试/改文档） | Code Review 通过 |
| 带教辅导 | 导师每日15分钟站会，每周1次1:1 | 周记反馈 |
| 模块Owner | 逐步Owner一个小模块/组件 | 独立完成1次完整需求 |
| 参与Code Review | 先看后审，逐步参与 | 完成≥5次CR |

#### 阶段五：独立交付（第4-6月）

| 里程碑 | 标准 | 交付物 |
|:-------|:-----|:-------|
| 独立完成1个完整需求 | 从需求评审→设计→编码→测试→发布全流程 | 设计文档+代码+测试报告 |
| 新人技术分享 | 面向部门做一次技术分享 | 分享PPT+视频录制 |
| 转正答辩 | 总结试用期工作成果与成长 | 转正述职报告+导师评价 |
| 转正考核 | 业务知识考试+实操考核+360评价 | 考核结果表 |

## 3. 流程与规范培训

### 3.1 IPD 流程培训（研发核心流程）

| 培训课程 | 面向对象 | 内容 | 考试方式 |
|:---------|:---------|:-----|:---------|
| IPD 概览 | 全员 | 流程框架、TR1-TR6 节点、关键交付物 | 在线考试 |
| 需求管理流程 | 产品经理+开发 | 需求采集→分析→分发→跟踪→验收 | 案例演练 |
| TR 评审流程 | 项目组全员 | 评审准备、评审要点、评审委员会运作 | 模拟评审 |
| 变更管理流程 | 开发+测试 | ECR/ECO 流程、变更影响分析 | 实操考核 |
| 版本发布流程 | 开发+运维 | 版本号规范、CI/CD 流水线、回滚策略 | 演练 |
| 物料/BOM 管理 | 硬件+供应链 | 层级BOM、替代料管理、版本控制 | 系统实操 |

### 3.2 工程规范培训

| 类别 | 培训内容 | 覆盖团队 |
|:-----|:---------|:---------|
| **编码规范** | 语言规范（C/Python/Go/Java）、命名规范、注释规范、代码审查Checklist | 软件团队 |
| **硬件设计规范** | 原理图规范、Layout规范、DFM/DFT/DFS 规范 | 硬件团队 |
| **接口规范** | API 设计规范、Redfish/IPMI 接口规范、RESTful 设计 | 固件+软件 |
| **文档规范** | Markdown 规范、架构图规范、文档目录结构规范 | 全员 |
| **测试规范** | 测试用例设计规范、自动化测试框架、回归测试策略 | 测试团队 |
| **安全编码规范** | 输入验证、内存安全、加密算法选择、CVE 应急流程 | 开发团队 |

### 3.3 工具链培训

| 工具类别 | 工具名称 | 培训层次 | 认证方式 |
|:---------|:---------|:---------|:---------|
| **版本控制** | Git/Gerrit/GitHub | 基础+进阶 | 实操考试 |
| **CI/CD** | Jenkins/GitLab CI/ArgoCD | 操作使用+流水线开发 | 独立搭建流水线 |
| **项目管理** | Jira/Confluence/MS Project | 操作使用 | 系统实操 |
| **文档协作** | 语雀/Wiki/Confluence | 操作使用 | 文档产出 |
| **设计工具** | Altium Designer/Cadence/EDA | 基础+进阶 | 独立完成设计 |
| **仿真工具** | SPICE/SI/PI仿真工具 | 操作使用 | 仿真报告 |
| **调试工具** | JTAG/OCP Debug Port/逻辑分析仪 | 操作使用 | 实操演示 |
| **自动化测试** | pytest/robot framework/TestNG | 框架使用+脚本开发 | 自动化脚本提交 |

### 3.4 流程培训的管理机制

| 机制 | 说明 |
|:-----|:-----|
| **流程Owner制度** | 每个核心流程指定Owner，负责培训内容维护和迭代 |
| **流程变更=培训通知** | 流程改版时必须同步更新培训材料和考试题库 |
| **流程考试年审** | 核心流程每年认证一次，不合格再培训 |
| **新员工流程必修** | 入职30天内完成6门核心流程考试 |
| **流程案例库** | 将流程违规/不合格案例沉淀为教学案例 |

## 5. 复盘机制

### 5.1 复盘类型谱系

```text
复盘类型  <- 触发条件 ->  参与者    <- 产出物
+--------+             +--------+  +-----------+
|事故复盘| <- 生产事故   |相关全员|  |RCA报告    |
+--------+             +--------+  +-----------+
|项目复盘| <- 项目结束   |项目团队|  |项目回顾    |
+--------+             +--------+  +-----------+
|阶段复盘| <- 里程碑     |核心成员|  |阶段评审    |
+--------+             +--------+  +-----------+
|周复盘   | <- 每周结束   |团队    |  |周报/改进项|
+--------+             +--------+  +-----------+
|个人复盘| <- 自驱       |个人    |  |成长日记    |
+--------+             +--------+  +-----------+
```

### 5.2 事故复盘（P0/P1/P2 事件）

#### 5.2.1 事故定级标准

| 级别 | 定义 | 响应要求 | 复盘要求 |
|:-----|:-----|:---------|:---------|
| **P0** | 核心业务完全不可用 / 数据丢失 | 立即响应，15min 内建群 | 24h 内出RCA，7天完成复盘 |
| **P1** | 核心业务部分不可用 / 严重影响用户体验 | 30min 响应 | 3天出RCA，14天完成复盘 |
| **P2** | 非核心功能受损 / 影响有限 | 2h 响应 | 14天内完成复盘 |
| **P3** | 轻微问题，可容忍 | 常规处理 | 记录在案，月会通报 |

#### 5.2.2 事故复盘流程（5W2H + 5Why）

```text
Step 1: 事实还原
  +-- 什么时间开始/结束？(When)
  +-- 什么影响范围？(What)
  +-- 哪些系统/组件涉及？(Where)
  +-- 谁参与响应？(Who)
  +-- 为什么发生？(Why) -> 5Why分析法

Step 2: 根因分析
  +-- 直接原因 -> 技术层面的错误
  +-- 间接原因 -> 流程/规范/评审缺失
  +-- 根因 -> 机制/文化/管理层面的深层原因
      +-- 至少追问到第5层"Why"

Step 3: 影响评估
  +-- 影响时长 × 影响用户数 = 严重度
  +-- MTTR (Mean Time To Recover)
  +-- 经济损失估算

Step 4: 改进措施
  +-- 短期措施（止损+预防复发）
  +-- 长期措施（根因修复+系统加固）
  +-- 如何验证措施有效？
      +-- 明确验证方法+验证人+完成日期

Step 5: 沉淀案例
  +-- 写入Case Study库
  +-- 添加监控告警规则（如果缺失）
  +-- 更新Runbook/变更Checklist
```

#### 5.2.3 事故复盘报告模板

| 章节 | 内容 |
|:-----|:-----|
| **事件概要** | 一句话描述 + 影响范围 + 级别 |
| **时间线** | 精确到分钟的关键时间节点（发现→响应→定位→恢复→复盘） |
| **故障现象** | 外部可见表现（告警/监控/用户反馈） |
| **根因分析** | 5Why分析链条 |
| **影响面** | 影响的设备数/集群/用户/业务 |
| **修复措施** | 临时止血 + 根本修复 |
| **改进项列表** | 按优先级排列，标注Owner和Deadline |
| **改进验证** | 每个改进项的可验证标准 |
| **经验教训** | 可复用到其他团队的总结 |
| **附录** | 日志片段/监控截图/代码diff |

#### 5.2.4 事故复盘的"不能做"清单

| 禁止行为 | 原因 | 替代做法 |
|:---------|:-----|:---------|
| ❌ 追责个人 | 让人不敢暴露问题 | ✅ 追责流程缺陷 |
| ❌ 归咎"粗心大意" | 无法预防 | ✅ 找系统层面缺失 |
| ❌ 仅描述现象 | 无法解决根因 | ✅ 一定要追问 Why x 5 |
| ❌ 措施无Owner | 无人负责落地 | ✅ 每条措施有Owner和截止日 |
| ❌ 措施无验收标准 | 无法确认是否解决 | ✅ 定义可验证标准 |

### 5.3 项目复盘（Retrospective）

#### 5.3.1 项目复盘四步法

| 步骤 | 方法 | 工具 |
|:-----|:-----|:-----|
| **收集数据** | 团队匿名收集做了什么、有什么问题 | 便利贴/Miro/在线白板 |
| **生成洞察** | 分类整理：做得好、做得差、值得改进 | 分类+投票 |
| **确定行动项** | 从"值得改进"中找最重要的2-3个 | SMART 目标 |
| **跟踪落地** | 下次复盘时先检视上次行动项 | 行动项看板 |

#### 5.3.2 项目复盘的常见格式

**Start / Stop / Continue 格式**：

| 类别 | 问题 | 示例 |
|:-----|:-----|:-----|
| **Start** | 应该开始做什么？ | 开始写ADC测试用例、开始做自动化回归 |
| **Stop** | 应该停止做什么？ | 停止没有设计文档就开写、停止无审批的变更 |
| **Continue** | 应该继续做什么？ | 保持每日站会、继续保持Code Review制度 |

**4L（Liked / Learned / Lacked / Longed For）格式**：

| 类别 | 说明 |
|:------|:-----|
| **Liked** | 喜欢什么？ |
| **Learned** | 学到了什么？ |
| **Lacked** | 缺了什么？ |
| **Longed For** | 渴望什么？ |

#### 5.3.3 项目复盘OKR/KPI示例

| 维度 | 指标 | 目标值 |
|:-----|:-----|:------|
| 复盘覆盖率 | 所有P0/P1事故100%复盘 | 100% |
| 措施落地率 | 复盘中识别的改进项按期完成 | ≥90% |
| 同类事故复发率 | 同一原因导致的事故不再发生 | 0% |
| 案例沉淀 | 年度Case Study数量 | 每个TL ≥3篇 |
| 复盘时效 | P0事故复盘完成时间 | ≤7天 |

### 5.4 周期复盘

| 类型 | 频次 | 形式 | 产出 |
|:-----|:-----|:-----|:-----|
| **日站会** | 每日 | 15min 立会 | 当日计划+阻塞项 |
| **周复盘** | 每周 | 30min 会议 | 本周完成+下周计划+风险 |
| **月复盘** | 每月 | 1h 会议 | 月度总结+指标趋势+改进项 |
| **季度复盘** | 每季 | 2-3h 专题会 | OKR回顾+资源调整+人才盘点 |
| **半年/年度** | 每半年 | 半天/全天 | 战略回顾+组织调整+表彰 |

### 5.5 个人复盘

| 形式 | 方法 | 频次 |
|:-----|:-----|:-----|
| **成长周记** | 本周做了什么？学到了什么？遇到了什么困难？下周计划 | 每周 |
| **KPT日记** | Keep(保持)/Problem(问题)/Try(尝试) 三栏 | 每日/每周 |
| **AAR (After Action Review)** | 目标→结果→偏差→根因→改进 | 每次重要任务完成 |
| **PDCA 个人循环** | Plan→Do→Check→Act | 持续 |

## 8. 导师制/师徒制

### 8.1 导师制运作模式

```text
                   导师（Mentor）
                  /      |      \
                 /       |       \
         技术辅导 <--- 职业指导 ---> 文化融入
          (技能)       (成长)       (价值观)
```

### 8.2 导师制设计

| 维度 | 说明 |
|:-----|:-----|
| **适用对象** | 新入职员工（必须）、实习生、转岗员工、高潜（可选） |
| **导师资格** | 工作≥3年，绩效达标，通过导师认证 |
| **匹配原则** | 同团队/同领域优先，鼓励跨团队但同方向 |
| **辅导周期** | 新人强制6个月，可延期到12个月 |
| **辅导强度** | 每周≥1次站会，每双周≥1次1:1，每月≥1次正式交流 |
| **导师激励** | 纳入绩效评定加分项，年度优秀导师奖金 |
| **退出机制** | 导师可以主动退出（需提前通知），学员可申请换导师 |

### 8.3 导师职责

| 职责 | 具体行动 |
|:-----|:---------|
| **技术带教** | 帮助理解系统架构、代码结构、工具链使用方法 |
| **流程指引** | 指导参与研发全流程，解释流程背后的Why |
| **文化传承** | 传递团队文化、工作习惯、协作方式 |
| **问题帮助** | 帮助解决技术卡点和组织流程障碍 |
| **成长反馈** | 定期给予反馈，指出改进方向 |
| **榜样示范** | 以身作则展示职业素养和工程标准 |

### 8.4 新人的责职

| 职责 | 具体行动 |
|:-----|:---------|
| **主动沟通** | 遇到问题先尝试自己解决，30分钟内无解主动问导师 |
| **定期汇报** | 至少每周同步一次工作进展 |
| **接受反馈** | 对导师的反馈保持开放心态，有异议反馈后讨论 |
| **独立成长** | 逐步从"导师带着做"到"自己做、导师审"再到"独自做" |

### 8.5 导师-学员互动模板

**1:1 每周交流模板**：

## 12. 专项与特色培训形式

### 12.1 Walk-in Clinic（技术问诊）

| 形式 | 说明 |
|:-----|:-----|
| **原理** | 固定时间（如每周四下午），开放技术咨询窗口 |
| **"坐诊专家"** | 由资深工程师/架构师轮流值班 |
| **形式** | 无需预约，Walk-in 提问，10-30分钟一对一交流 |
| **适用** | 快速答疑、设计Review、踩坑求助 |
| **产出** | 解答要点记录到FAQ库 |

### 12.2 代码大扫除（Code Clean-up Day）

| 形式 | 说明 |
|:-----|:-----|
| **频次** | 每季度一次 |
| **时长** | 半天到一天 |
| **活动内容** | 团队集中清理遗留技术债务：删除废弃代码、重构坏味道、补齐测试 |
| **指南** | 提前准备"大扫除清单"，扫除成果计入OKR |
| **输出** | 技术债务清单更新+合并的清理PR |

### 12.3 交叉培训（Cross-training）

| 形式 | 说明 |
|:-----|:-----|
| **目的** | 打破单点依赖（Bus Factor），培养T型人才 |
| **形式** | 每个工程师在相邻领域做短期轮岗（1-2周） |
| **场景** | 硬件工程师学固件、固件学测试、测试学运维 |
| **产出** | 交叉培训笔记+总结分享 |

### 12.4 故障注入日 (Chaos Day / Failure Drill)

| 形式 | 说明 |
|:-----|:-----|
| **目的** | 测试系统在故障下的行为，培训应急响应能力 |
| **形式** | 在生产环境/预生产环境注入故障（网络分区/磁盘满/进程崩溃） |
| **安全措施** | 隔离环境+回滚预案+通知相关人员 |
| **产出** | 测试报告+系统弱点清单+Runbook更新 |

### 12.5 技术辩论赛

| 形式 | 说明 |
|:-----|:-----|
| **辩题** | 技术选型争议性话题（如: 液冷vs风冷/集中式vs分布式存储） |
| **形式** | 正反方各3人，30分钟辩论+10分钟观众提问 |
| **目的** | 训练多角度思考、技术表达能力、证据驱动论证 |
| **评审** | 技术委员会评分，"赢"方观点不一定被采纳，但论证质量要最高 |

### 12.6 失败分享会 / 踩坑大会

| 形式 | 说明 |
|:-----|:-----|
| **核心理念** | 犯错不可怕，不分享才可怕 |
| **形式** | 每月一次，自愿讲述自己经历的最惨痛失败 |
| **规则** | 不追责、不批判、只讨论学到了什么、如何避免 |
| **激励** | 主动分享失败案例有积分奖励 |
| **产出** | 失败的精华=可复用的经验 |

### 12.7 AI 辅助研发培训专项

随着AI编程工具（Cursor/Copilot/Claude Code/ChatGPT等）普及，需要专门的培训模块：

| 培训主题 | 内容 | 面向 |
|:---------|:-----|:-----|
| AI编程工具入门 | 提示词工程、工具配置、基本用法 | 全员 |
| AI辅助设计 | 用AI生成设计文档、架构图、接口规范 | 全员 |
| AI Code Review | 用AI做代码审查，AI找bug | 开发团队 |
| AI测试生成 | 用AI生成测试用例、测试数据 | 测试团队 |
| AI知识管理 | 用AI做知识沉淀、问答、RAG系统 | 全员 |
| AI伦理与安全 | AI生成代码的安全风险、版权问题、幻觉识别 | 全员 |
