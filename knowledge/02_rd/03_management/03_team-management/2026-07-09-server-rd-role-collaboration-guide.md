### ⚠️ 跨角色通用红线：AI 产出的责任归属

> **原则：使用 AI 产生文档、代码、设计、数据的任何人，必须对产出的内容全权负责。**
>
> 即：AI 是工具，不是责任人。用户你使用 AI 生成了代码，那代码的 Bug 就是你的 Bug；你让 AI 写了设计文档，那文档中的错误就是你的错误。**不可因为「这是 AI 写的」而减免个人责任。**
>
> 具体含义：
>
> - **开发者**：AI 生成代码必须审查、理解、测试后才能提交。不清楚原理的代码不允许合入。
> - **架构师**：AI 协助产出的架构方案，架构师必须理解每一条 trade-off 的理由，能向团队解释「为什么这么设计」。
> - **管理者**：AI 生成的团队计划、绩效评估、项目报告，管理者必须复核事实和数据，不能直接粘贴。
> - **CTO/VP**：AI 辅助分析的战略报告，CTO 必须对结论负责，不能以「模型说的」作为决策依据。
>
> 组织层面应配套：
>
> 1. **AI 产出标记**：代码/文档中 AI 生成内容应有明显标记（注释/脚注），便于审查追溯
> 2. **审查流程不变**：AI 产出不豁免任何 Review 环节（Code Review / 技术评审 / 功能验收）
> 3. **追责不变**：线上事故因 AI 生成代码引起，开发者承担同等责任，不因来源为 AI 而减轻
> 4. **学习要求**：使用 AI 生成自己不理解的复杂逻辑，应学习理解后再提交，而不是「先合入再说」

## 1. 角色全景 — 六类角色定位

```text
+------------------------------------------------------------------+
|                    服务器产品研发组织角色谱系                        |
+------------------------------------------------------------------+
|                                                                  |
|  +----------+    +----------+    +----------+                    |
|  |  决策层   |    |  管理层   |    |  技术层   |                    |
|  | CTO/VP   |<-->|  总监/经理 |<-->|  架构师   |                    |
|  |          |    |          |    |          |                    |
|  +----+-----+    +----+-----+    +----+-----+                    |
|       |               |               |                         |
|       v               v               v                         |
|  +----------+    +----------+    +----------+                    |
|  |  骨干员工  |    |  开发/测试 |    | 实习生/新人 |                |
|  |  技术带头人 |    |  执行层    |    |  培养期    |                |
|  +----------+    +----------+    +----------+                    |
|                                                                  |
|  横向角色（跨所有层级）：                                         |
|  产品经理 ---- 连接市场与技术                                     |
|  项目经理 ---- 连接进度与资源                                     |
|  质量工程师 -- 连接标准与执行                                     |
+------------------------------------------------------------------+
```

### 1.1 六类角色的核心差异一句话

| 角色 | 核心问题 | 工作范围 | 时间视角 | 交付物特征 |
|:-----|:---------|:---------|:---------|:-----------|
| **实习生/新人** | 怎么做？ | 单模块、有 mentor 指导 | 日/周 | 学习 + 简单任务 |
| **骨干/开发** | 做什么？怎么做好？ | 单功能/模块，独立负责 | 周/月 | 可交付的代码/文档 |
| **架构师** | 为什么要这么做？ | 多模块/子系统，技术决策 | 月/季度/年 | 架构方案、技术决策 |
| **技术带头人** | 兼顾方向与落地的桥梁 | 价值域，技术 leader | 季度/半年 | 技术路标 + 团队赋能 |
| **管理者(经理/总监)** | 谁来做？资源够吗？ | 团队/部门，人员+资源+流程 | 季度/年 | 团队绩效、人才梯队 |
| **CTO/VP** | 方向对吗？值得投入吗？ | 技术战略，跨部门决策 | 年/3年 | 技术路标、组织能力 |

### 1.2 关键认知 — 角色不是职级，是 context

> **一个人的「角色」是由他当前所承担的任务 context 决定的，而非由他的职级决定的。**
>
> 一个高级工程师被分配写一个 CRUD 接口 → 他在这个任务上的角色就是「执行者」
> 一个中级工程师被指派负责某个子系统架构 → 他在这个任务上的角色就是「架构师」
>
> 关键在于：**组织中每类角色的职责定义是固定的，但谁扮演这个角色是动态的。**

## 2. 角色详解

### 2.1 实习生/新人（培养层）

#### 2.1.1 任务范围

| 维度 | 范围 | 说明 |
|:-----|:-----|:------|
| 代码任务 | 单函数/单模块/单测试用例 | 有明确输入输出，边界清晰 |
| 技术学习 | 掌握团队开发规范、工具链、业务逻辑 | 有学习计划 + 检查点 |
| 文档 | 编写自己模块的使用说明/API文档 | mentor 审核 |
| 参与范围 | 不涉及跨团队协作 | 特殊情况可在 mentor 带领下参与 |

#### 2.1.2 质量要求

| 维度 | 标准 | 验收方式 |
|:-----|:-----|:---------|
| 功能正确性 | 单元测试通过率 100% | mentor code review |
| 代码规范 | 遵循团队编码规范（无 Lint 告警） | CI 门禁 |
| 文档完整性 | 模块用途、接口、约束说明清楚 | mentor 确认 |
| 沟通 | 每日同步进度、遇到阻塞及时求助 | 日报/站会 |

#### 2.1.3 评价方式

| 维度 | 权重参考 | 评价主体 |
|:-----|:---------|:---------|
| 任务完成度 | 40% | mentor |
| 学习速度 | 30% | mentor |
| 代码质量 | 20% | 代码审查记录 |
| 团队融入 | 10% | 团队反馈 |

#### 2.1.4 质量保障措施

```text
[新人保障线]
  +- Day 1-3:  环境和工具搭建 -> checklist 逐项确认
  +- Week 1:   第一行代码（定型任务）-> mentor 当面 review
  +- Week 2-4: 第一个完整模块 -> Review + 文档检查
  +- Month 2:  独立负责小功能 -> 代码审查 + 功能验收
  +- Month 3:  掌握开发全流程 -> 可参与正常迭代
```

**核心原则**: 新人的第一个任务是「学习」而非「产出」。前2周的核心指标是环境搭建无误、开发流程理解正确。

### 2.2 骨干员工/开发工程师

#### 2.2.1 任务范围

| 维度 | 范围 | 说明 |
|:-----|:-----|:------|
| 功能开发 | 独立负责一个或多个功能模块 | 从需求理解到上线全流程 |
| Bug 修复 | 定位和修复负责模块的问题 | 含根因分析报告 |
| 代码审查 | 参与同级/新人的代码审查 |    |
| 技术方案 | 撰写所负责模块的详细设计方案 | 架构师审核 |
| 跨团队沟通 | 与自己模块相关的接口对接 | 有争议时升级 |

#### 2.2.2 质量要求

| 维度 | 标准 | 验收方式 |
|:-----|:-----|:---------|
| 功能完整 | 覆盖 PRD 中所有功能点，无遗漏 | 功能验收 |
| 测试覆盖 | 单元测试覆盖率 ≥ 80%（核心路径 100%） | CI 报告 |
| 性能 | 满足规格指标（延迟/吞吐/资源消耗） | 性能测试报告 |
| 可维护性 | 代码结构清晰、注释合理、错误处理完整 | Code Review |
| 文档 | 设计文档 + API 文档 + 自检清单 | 技术评审 |

#### 2.2.3 评价方式

| 维度 | 权重参考 | 评价主体 |
|:-----|:---------|:---------|
| 需求交付 | 30% （按时 + 完整度） | 项目经理 |
| 代码质量 | 25% （Bug率 + 代码审查反馈） | 架构师/技术主管 |
| 技术方案质量 | 20% | 架构师 |
| 团队协作 | 15% | 团队反馈 |
| 自我提升 | 10% | 技术主管 |

#### 2.2.4 质量保障措施

- **自检清单**：提交前逐项自检（功能/性能/安全/兼容性/日志）
- **双人 Review**：关键模块至少 2 人 Code Review
- **AI 辅助代码审查**：如使用 AI 生成代码，提交前必须逐行理解、自己跑通用例，不清楚原理的代码段不允许合入
- **CI 门禁**：Lint + 单元测试 + 编译 + 集成测试自动拦截
- **灰度发布**：新功能按 1%→10%→100% 逐步放量，设回滚机制

#### 2.2.5 常见误区

| ❌ 错误认知 | ✅ 正确认知 |
|:-----------|:-----------|
| "我只要把代码写完就行" | 代码写完是起点，测试覆盖、文档、可维护性都是分内事 |
| "这个 Bug 跟我无关，是别的模块的" | 即使根因在别的模块，也需要协助定位、推动修复 |
| "需求不清晰，但我先写了再说" | 需求不清晰时，第一件事是主动澄清，不做假设 |

### 2.3 架构师

#### 2.3.1 角色定位 — 架构师不是「不写代码的高级工程师」

```text
[常见误解]
  架构师 = 不写代码的资深工程师
  架构师 = 画架构图的
  架构师 = 评审别人方案的

[正确理解]
  架构师 = 通过技术决策降低系统复杂度和团队认知负担的人
  架构师 = 为系统的长期健康负责的人
  架构师 = 在「快」和「好」之间做权衡的人
```

#### 2.3.2 任务范围

| 维度 | 范围 | 非范围（不是架构师该做的） |
|:-----|:-----|:-------------------------|
| 技术选型 | 确定技术栈、框架、中间件选型 | 决定用什么编程语言版本（那是开发规范） |
| 架构设计 | 系统模块划分、接口定义、数据流设计 | 写每个模块的详细实现方案（那是开发的事） |
| 技术决策 | 关键 trade-off 决策（性能vs成本、一致性vs可用性） | 决定排期（那是 PM 的事） |
| 技术评审 | 评审各模块的方案和设计 | 替开发写代码（紧急情况可例外） |
| 技术规范 | 制定编码规范、API 规范、异常处理规范 | 逐行检查代码是否符合规范（那是 CI 做的事） |
| 风险评估 | 识别技术方案中的潜在风险、瓶颈 | 评估项目进度风险（那是 PM 的事） |
| 代码审查 | **必须亲自审查核心路径的代码** | 审查所有代码 |

#### 2.3.3 架构师的产出物

| 产出 | 频率 | 受众 | 说明 |
|:-----|:-----|:-----|:------|
| 架构设计文档 | 每次架构变更 | 开发团队 | 含背景、方案对比、决策理由、风险 |
| 技术路标 | 季度/半年 | 管理层+团队 | 技术演进方向、关键里程碑 |
| 评审意见 | 按需 | 被评审方 | 含问题、建议、风险等级 |
| 技术债务清单 | 持续维护 | 团队 | 已知问题、影响范围、计划修复时间 |
| 架构全景图 | 半年/年度 | 全员 | 系统现状、演进方向、关键依赖 |

#### 2.3.4 评价方式

| 维度 | 权重参考 | 评价主体 |
|:-----|:---------|:---------|
| 技术决策质量 | 40% | 系统长期表现（故障率、可扩展性、维护成本） |
| 团队技术能力提升 | 25% | 团队反馈、代码质量趋势 |
| 架构文档/规范质量 | 15% | 被评审方反馈 |
| 跨团队协作效果 | 10% | 协作团队反馈 |
| 技术风险预判 | 10% | 实际风险发生情况 |

> ⚠️ **架构师首先不能以「代码行数」来评价。他的价值在于：**
>
> - **避免了多少错误方向**（而非修复了多少 Bug）
> - **降低多少团队认知负担**（而非自己写了多少文档）
> - **系统长期可维护性**（而非短期交付速度）

#### 2.3.5 质量保障措施

- **决策记录（ADR）**：每个架构决策必须有 Architecture Decision Record
- **方案至少 2 个**：对比方案而非单方案决策，列出 Pros/Cons/成本/风险
- **充分征求意见**：在最终决策前，方案需在团队内充分讨论，确保无 blind spot
- **事后复盘**：每个重大决策后设 check point，6-12 个月后复盘决策质量
- **深入代码**：架构师必须深入核心模块的代码，**纯画图不写代码的架构师是纸老虎**
- **AI 辅助方案审查**：使用 AI 生成架构方案或对比分析，架构师必须理解每条 trade-off 的理由，能向团队解释「为什么这么选」，AI 生成的 ADR 草案需经本人重写/确认后生效

### 2.4 技术带头人（Tech Lead / 技术骨干层）

#### 2.4.1 定位 — 架构师与管理者的桥梁

```text
  架构师（技术方向）      管理者（人员/资源）          技术带头人（落地执行）
        |                       |                          |
        |  技术路标、规范       |  人员配置、考核          |  带领团队落地、技术细节把关
        |                       |                          |
        +-----------------------+--------------------------+
                               ^
                    技术带头人是这两个角色的「接口人」
```

#### 2.4.2 任务范围

| 维度 | 范围 | 说明 |
|:-----|:-----|:------|
| 技术落地 | 将架构方案拆解为可执行的任务 | 保证技术方案被正确实现 |
| 任务分解 | 将需求拆分为开发任务，评估工时 | 含识别依赖和风险 |
| 代码质量 | 把控团队的代码质量 | 核心代码 Review |

| 技术决策 | 模块级别的技术决策 | 升级到架构师决策 |
| 进度把控 | 跟踪任务进展，识别阻塞 | 和项目经理配合 |

#### 2.4.3 评价方式

| 维度 | 权重参考 | 评价主体 |
|:-----|:---------|:---------|
| 团队产出质量 | 35% | 管理者 + 架构师 |
| 技术方案质量 | 20% | 架构师 |
| 人员培养效果 | 20% | 下属反馈 + 成长速度 |
| 协作与沟通 | 15% | 关联团队反馈 |
| 个人技术贡献 | 10% | 架构师 |

### 2.5 管理者（总监/经理）

#### 2.5.1 角色定位 — 管理者不是「管人的」，是「对团队产出负责的」

| ❌ 错误认知 | ✅ 正确认知 |
|:-----------|:-----------|
| "管理者就是管人的" | 管人是手段，**团队持续交付高质量产出**才是目标 |
| "管理者应该技术最强" | 管理者可以技术不是最强，但要能判断技术方向、协调资源、排除障碍 |
| "管理者要管细节" | 管理者的职责是确保事情被做好，不一定自己去做。**过度管理 = 不信任** |
| "管理者只对上负责" | 管理者是连接上下级的通道：对上承接目标，对下提供资源和保障 |

#### 2.5.2 任务范围

| 维度 | 范围 | 非范围 |
|:-----|:-----|:-------|
| 目标设定 | 设定团队 OKR/KPI、明确优先级 | 替团队写技术方案 |
| 资源管理 | 人力分配、预算控制、工具/设备采购 | 自己做每个需求的技术选型 |
| 人员发展 | 招聘、晋升、培训、绩效评估 | 替下属解决技术细节问题 |
| 流程建设 | 工作流程优化、效率提升 | 写 CI/CD 脚本（那是 DevOps 的事） |
| 跨团队协调 | 与其他团队/部门沟通和问题升级处理 | 替下属参加每一个技术讨论会 |
| 风险管控 | 识别项目风险并制定应对方案 | 替团队排查线上问题（除非紧急且没人能处理） |
| 文化建设 | 建立团队文化、明确价值观期望 | 做每一件事都亲力亲为 |

#### 2.5.3 管理者的「三个不做」

```text
1. 不做下属该做的事 — 如果管理者经常在帮下属写代码/改 Bug，说明要么下属能力不足需要调整，
   要么管理者角色认知有问题。管理者的稀缺性是自己的时间。

2. 不做信息过滤 — 不替团队过滤必要的信息（包括坏消息）。团队需要了解真实情况才能做出
   正确判断。管理者要做的是帮助团队理解信息的上下文和影响。

3. 不做决策替代 — 架构决策让架构师做，技术方案让开发做。管理者负责的是「谁来做」和
   「资源够不够」，不是「这个方案好不好」（除非你同时也是架构师）。
```

#### 2.5.4 评价方式

| 维度 | 权重参考 | 评价主体 |
|:-----|:---------|:---------|
| 团队交付 | 30%（质量、按时率、客户满意度） | 上级 + 客户 |
| 人员保留与发展 | 20%（流失率、晋升率、满意度） | 人力资源 + 团队反馈 |
| 效率提升 | 15%（流程改进、工具建设、质量提升） | 上级 |
| 跨团队协作 | 15% | 协作团队反馈 |
| 团队文化 | 10% | 团队反馈 |
| 成本控制 | 10% | 财务/上级 |

#### 2.5.5 质量保障措施

- **1-on-1 制度**：与每个直接下属每周/双周 1-on-1
- **管理者自检清单**：每月自检 — 团队状态、人员风险、目标对齐度、内耗瓶颈
- **紧急上报机制**：明确什么情况下必须升级到管理者（如：严重故障、资源严重不足、项目延期风险大）
- **反向反馈**：每季度收集团队对管理者的匿名反馈
- **AI 输出复核**：管理者使用 AI 生成团队计划、绩效评估、项目报告，必须复核事实、数据、逻辑后才能发布，不得直接粘贴「AI 说的」

### 2.6 CTO / 技术 VP（决策层）

#### 2.6.1 角色定位

> CTO 不是「管技术的最大官」，而是 **「通过技术实现业务战略的掌舵人」** 。
>
> 在服务器产品研发组织中，CTO 的职责跨越技术、战略、组织、生态四个维度。

#### 2.6.2 任务范围

| 维度 | 具体内容 | 说明 |
|:-----|:---------|:------|
| 技术战略 | 制定 1-3 年技术路标、关键技术方向判断 | 如：自研芯片 vs 采购、AI 架构走向 |
| 组织建设 | 组织架构设计、关键人才引入、技术文化建设 | 如：是否成立 AI 团队、如何培养架构师 |
| 重大决策 | 技术资源投入方向、重大技术选型的最终决策 | 如：采用什么 CPU 平台、大规模架构切换 |
| 外部连接 | 客户技术交流、生态合作、行业标准参与 | 如：ODCC/OCP 标准推动、头部客户技术对话 |
| 质量与文化 | 设定组织的质量标准和技术文化基调 | 如：RAS 文化、质量红线、技术债务容忍度 |
| 投资回报 | 技术投入的 ROI 评估、研发预算分配 | 如：新项目启动/停止决策 |

#### 2.6.3 CTO 不做的事

```text
❌ 不直接管理单个项目（除非战略级项目）
❌ 不替总监做他该做的日常管理决策
❌ 不参与具体技术方案的细节讨论（除非该决策有重大战略影响）
❌ 不写代码（原型验证/ POC 可例外，但这不是常态）
❌ 不直接面试所有候选人（只面试关键岗位/高阶人才）

✅ CTO 该做的：
   - 问正确的问题，而不是给正确的答案
   - 建立决策框架，而不是替别人做决策
   - 培养其他决策者，而不是成为唯一决策者
```

#### 2.6.4 评价方式

| 维度 | 权重参考 | 评价主体 |
|:-----|:---------|:---------|
| 技术战略准确性 | 30% | 业务成果、市场反馈 |
| 组织能力建设 | 25% | 人才梯队、创新能力 |
| 技术影响力 | 15% | 行业认可度、标准参与度 |
| 跨部门/外部协作 | 15% | 业务部门/客户反馈 |
| 研发效率与成本 | 15% | 人均产出、研发 ROI |

#### 2.6.5 质量保障措施

- **技术决策复盘**：重大决策后 3-6 个月进行技术债务审计，检查决策实际效果
- **CTO 下基层**：定期参与一线技术评审、Code Review（至少每月参与一次核心模块 Review）
- **外部对标**：定期与行业同行交流，防止技术路线偏离行业主流
- **AI 战略分析复核**：AI 辅助产出的战略分析/市场判断/技术趋势报告，CTO 必须对结论负责，不能以「模型说的」作为决策依据。使用 AI 生成的技术路标草案需经架构委员会评审后方可发布

## 3. 跨角色协作矩阵

### 3.1 协作原则（四条铁律）

```text
铁律一：先对准目标，再讨论方案
  各角色在协作前，先确认共同目标是什么（用户故事/业务价值），
  避免「我理解的需求」和「你以为的需求」不匹配。

铁律二：信息透明，不搞信息垄断
  任何角色不得以「没必要知道」为由对其他角色隐瞒信息。
  特别是管理层对团队、架构师对开发。

铁律三：及时同步，不要在最后时刻暴露问题
  任何角色预计可能影响交付的，第一时间知会所有相关角色。
  「我以为你知道」是协作中最贵的一句话。

铁律四：先主动行动，再请求资源
  遇到问题先自己尝试解决，带着方案（而非问题）求助。
  但如果问题超出自己能力圈或授权范围，及时升级不拖延。
```

### 3.2 协作场景矩阵

| 协作场景 | 涉及角色 | 配合要点 | 常见失败模式 |
|:---------|:---------|:---------|:------------|
| **需求定义** | PM↔架构师↔Tech Lead | PM 说「要什么」, 架构师说「能不能做、怎么做」, Tech Lead 说「需要多久」 | PM 需求模糊 → 开发瞎做 → 返工 |
| **技术方案** | 架构师↔开发 | 架构师给框架和约束, 开发填具体实现 | 架构师太粗 → 开发自由发挥 → 偏离设计; 架构师太细 → 开发无自主权 → 低效 |
| **任务分配** | 管理者↔Tech Lead | 管理者确定优先级和资源, Tech Lead 分解任务 | 管理者跳过 Tech Lead 直接派活 → Tech Lead 失控 |
| **进度追踪** | PM↔Tech Lead↔管理者 | PM 追踪时间, Tech Lead 追踪技术风险, 管理者追踪资源 | PM 追问进度给开发者 → 影响开发效率 |
| **决策** | 架构师↔CTO↔管理者 | 架构师提供方案和对比, 管理者提供资源约束, CTO 做最终决策 | 无人决策 → 等待 → 错失时机 |
| **故障响应** | 开发↔架构师↔管理者 | 开发处理, 架构师指导, 管理者协调资源和对外沟通 | 所有人都在修故障 → 没人协调 → 混乱 |
| **技术创新** | 架构师↔CTO↔管理者 | 架构师洞察技术趋势, CTO 判断投资价值, 管理者评估团队能力 | 架构师前瞻但无落地资源 → 创新死掉 |

### 3.3 协作不得越级原则（但信息要透明）

```text
信息流动
  CTO <-----------> 管理者 <-----------> Tech Lead <-----------> 开发
     战略方向             目标/资源            任务/方案          实现

  ❌ 坏模式: CTO 直接告诉开发「你做这个」
     -> Tech Lead 和管理者都不知道 -> 计划被打乱 -> 执行混乱

  ❌ 坏模式: 开发越级向 CTO 抱怨
     -> 管理者失去控制 -> 团队信任破坏

  ✅ 好模式: 信息透明但决策走通道
     -> 所有人知道目标是什么、为什么、谁在做什么
     -> 但变更/资源/方向的决策走管理层级
```

### 3.4 关键角色接口定义

| 角色A | 角色B | 接口内容 | 同步频率 | 升级条件 |
|:------|:------|:---------|:---------|:---------|
| PM ↔ 架构师 | 需求可行性评估 | 每次需求变更 | 技术不可行 / 成本超出范围 |
| 架构师 ↔ Tech Lead | 技术路标、规范、关键选型 | 周同步 | 方案分歧 / 资源不足 |
| Tech Lead ↔ 管理者 | 团队状态、进度风险、人员问题 | 周同步 | 人员离职风险 / 严重延期 |
| 管理者 ↔ CTO | 团队产出、重大问题、资源诉求 | 双周 | 方向冲突 / 资源严重不足 |
| 开发 ↔ PM | 功能状态、变更影响 | 每日站会 | 需求变更导致延期 |

## 4. 决策机制与责任归属

### 4.1 决策分级

```text
+------------------------------------------------------------------+
|  决策分级                                                         |
+------------------------------------------------------------------+
|  Level 1: 执行决策（开发级别）                                     |
|    范围: 如何实现某个功能、用哪个 API、代码怎么写                   |
|    决策者: 开发工程师（自行决定）                                   |
|    约束: 不违反架构规范、不引入安全风险                              |
|    时间: 立即可决策                                                 |
+------------------------------------------------------------------+
|  Level 2: 模块决策（Tech Lead 级别）                               |
|    范围: 模块内接口定义、技术选型（框架/库）、模块间依赖             |
|    决策者: Tech Lead（上报架构师）                                  |
|    约束: 遵循系统整体架构顶层设计                                    |
|    时间: 1-3 天                                                     |
+------------------------------------------------------------------+
|  Level 3: 系统决策（架构师级别）                                    |
|    范围: 系统架构变更、关键技术选型、跨模块接口协议                  |
|    决策者: 架构师（上报 CTO）                                       |
|    约束: 成本、时间、团队能力的约束                                   |
|    时间: 1-2 周（含方案对比和评审）                                  |
+------------------------------------------------------------------+
|  Level 4: 战略决策（CTO/VP 级别）                                  |
|    范围: 技术方向、平台切换、架构重建、重大投资                      |
|    决策者: CTO（报 CEO/董事会）                                     |
|    约束: 业务战略、ROI、组织能力、时间窗口                             |
|    时间: 1-3 月（含调研、POC、评审）                                 |
+------------------------------------------------------------------+
```

### 4.2 决策责任矩阵（RACI）

| 决策事项 | R 执行 | A 批准 | C 咨询 | I 知会 |
|:---------|:-------|:-------|:-------|:-------|
| 功能实现方式 | 开发 | Tech Lead | 架构师 | PM |
| 模块内技术选型 | Tech Lead | 架构师 | 开发 | 管理者 |
| 系统架构变更 | 架构师 | CTO | 开发+Tech Lead | 全体 |
| 资源分配/人力调整 | 管理者 | CTO | PM+Tech Lead | 团队 |
| 项目排期 | PM | 管理者 | Tech Lead+开发 | 相关方 |
| 预算审批 | 管理者 | CTO/VP | PM+财务 | — |
| 技术规范制定 | 架构师 | CTO | Tech Lead | 全体 |
| 代码审核 | 审查者 | Tech Lead | — | 开发者 |
| 故障定级 | 故障响应人 | 管理者 | 架构师 | CTO(重大) |
| 技术方向/路标 | 架构师 | CTO | PM+管理者 | 全体 |

### 4.3 决策原则

```text
1. 最接近信息的人做决策
   - 一线开发最了解代码细节 -> 执行决策自己做
   - 架构师最了解系统全局 -> 系统决策架构师做
   - CTO 最了解战略方向 -> 战略决策 CTO 做

2. 决策速度优先于决策完美
   - 做决策等待太久比做了一个不太完美的决策代价更高
   - 如果决策代价可逆（代码重构、小范围切换），快速决策 > 完美决策
   - 如果决策代价不可逆（平台切换、架构重建），需要充分评审

3. 决策者有责任 = 决策者需承担后果
   - 谁决策、谁负责。不允许「上级拍脑袋，下级背锅」
   - 如果决策出了问题，决策者需要公开复盘、承认错误、吸取教训
   - 不允许因决策失误而惩罚执行者（除非执行者未按决策执行）

4. 决策要有记录
   - 所有 Level 3 及以上的决策必须书面记录（含背景、选项、决策理由）
   - 这是「回头可以学习」而不是「回头可以追责」的出发点
```

### 4.4 争议升级机制

当两个角色对某决策无法达成一致时：

```text
Step 1: 同级协商（目标：在各自上级介入前解决）
  双方各自陈述理由、数据、风险 -> 尝试达成一致
  时间限制: 3 个工作日内

Step 2: 共同上级裁决（目标：加速决策）
  双方各自向上级陈述 -> 上级听取双方意见后做出裁决
  时间限制: 2 个工作日内

Step 3: CTO 或 IPMT 最终裁定（目标：结束争议）
  战略级或影响巨大的争议 -> 升级到 CTO 或 IPMT
  时间限制: 1 周内

⚠️ 关键规则:
  - 争议期间，**默认按当前已有计划继续执行**，反对方案搁置讨论
  - 不允许「争议 -> 所有工作停摆等待」
  - 升级方需要带着方案（而非只有问题）升级
```

## 5. 常见内耗场景与破解

### 场景 1: 「开发说架构师没有产出」

**症状**: 开发觉得架构师天天画图不写代码，不解决实际问题

| 根因 | 解决方案 |
|:-----|:---------|
| 架构师远离一线代码 | 强制架构师参与核心模块编码/Review（每周至少1天） |
| 架构师输出物不可感知 | 架构师定期（每双周）做技术分享：架构方案思路、设计决策背后的 trade-off |
| 架构设计未落地 | 建立「架构→代码」追溯机制：每次迭代结束后，用实际代码和架构设计对比 |
| 开发不理解架构设计的价值 | 架构师做决策时让开发参与讨论，让开发理解「为什么选A不选B」 |

**一句话原则**: 架构师的产出不是文档，而是**团队因清晰架构而减少的返工时间**。这个产出需要让开发真切感受到。

---

### 场景 2: 「销售说研发不及时支持」

**症状**: 销售承诺了客户，研发说做不了或来不及做

| 根因 | 解决方案 |
|:-----|:---------|
| 销售未经技术评估就承诺 | 建立 **TTQ（技术评估响应时间）** 机制：销售提需求 -> 24h 内技术初评，72h 内详细评估 |
| 研发不知道客户的紧急程度 | 建立分级响应机制：P0（客户现场阻塞）→ 即时响应，P1（影响交付）→ 24h 响应 |
| 无 Pre-sales 技术角色 | 配备售前技术顾问（FAE/系统工程师），作为销售和研发之间的桥梁 |
| 研发资源被内部项目占满 | 设立 **客户支持缓冲区**（团队 20% 的产能预留给客户紧急需求，动态调配） |

**关键机制**: **销售承诺必须经过技术评估**。建立「销售→FAE→研发主管」的承诺审批链。未经过技术评估的承诺，研发有权不接受。但这需要 CTO 和销售 VP 先达成共识。

---

### 场景 3: 「管理者说团队效率低，团队说目标不清晰」

**症状**: 管理者觉得团队产出不够，团队觉得是目标设定有问题

| 根因 | 解决方案 |
|:-----|:---------|
| 目标只分解任务不解释价值 | 每次分配任务时，说明「为什么要做」、「做成什么样算好」 |
| 优先级频繁变动 | 设定 **迭代周期（2周为佳）**，迭代内优先级冻结，迭代间重新排 |
| 过度管理 | 管理者每周自检：我本周做了什么不该我做的事？ |
| 缺少节奏感 | 建立稳定的节奏：站会（每日）→ 计划会（双周一）→ 评审会（双周五）→ 复盘会（月底） |

---

### 场景 4: 「架构师和 Tech Lead 意见不合」

**症状**: 架构师坚持某方案，Tech Lead 觉得落地困难

| 解决方案 |
|:---------|
| 双方列出各自方案的具体数据：成本、时间、风险、团队能力匹配度 |
| 先找共同点，再聚焦分歧点（通常分歧只占 20%） |
| 如果仍无法达成一致，由管理者做裁决（基于**业务价值和资源约束**而非纯技术角度）|
| 关键约束：「先跑起来再优化」。如果两个方案差距不大，选能快速验证的 |

---

### 场景 5: 「CTO/VP 做了不切实际的承诺」

**症状**: 高层对客户承诺了过高的交付目标，研发团队认为不可能

| 根因 | 解决方案 |
|:-----|:---------|
| CTO 不了解一线实际情况 | CTO 定期参与技术评审（每月至少1次），听取真实进度的汇报 |
| 团队不敢说真话 | 建立 **「坏消息优先」文化**：最早发现的潜在风险值得表扬而非批评 |
| 评估标准不对齐 | 所有对外承诺必须经过 **Tech Lead + PM 的联合评估**，CTO 签字确认 |

## 6. 组织成熟度演进

### 6.1 不同规模的角色的职责分布

| 团队规模 | 角色合并 | 角色缺失时的风险 | 建议 |
|:---------|:---------|:----------------|:-----|
| **10-30人** | 管理者=架构师=sales engineer | 技术债务快速累积、一人离职影响巨大 | 技术负责人同时做架构和管理；核心模块双人负责 |
| **30-80人** | 出现专职 PM、专职测试 | 跨项目协调混乱、资源竞争无仲裁 | 引入项目经理、明确架构师角色 |
| **80-200人** | 架构师独立、Tech Lead 出现 | 跨团队沟通成本急剧上升 | 引入 IPD 矩阵、CBB 复用机制 |
| **200+人** | 所有角色独立、引入子领域架构师 | 组织层级过多导致决策迟缓 | 扁平化+授权、引入 TDT/TRT 技术委员会 |

### 6.2 角色成熟度自查清单

每个季度，所有角色按以下清单自查：

| 角色 | 关键问题 | 是/否 |
|:-----|:---------|:------|
| **开发者** | 我是否清楚当前 sprint 做的东西给谁用、解决了什么问题？ | ☐ |
| | 我提交代码前是否运行了所有测试？ | ☐ |
| | 我是否主动写了必要的文档（而非被要求才写）？ | ☐ |
| **架构师** | 我本季度参与了多少核心代码编写/Review？ | ☐ |
| | 我的架构方案是否有至少 2 个对比选项？ | ☐ |
| | 团队是否理解我做的技术决策的理由？ | ☐ |
| **管理者** | 我本周做了什么不该我做的事情？ | ☐ |
| | 我是否了解每个直接下属当前的困难和状态？ | ☐ |
| | 我是否为团队扫除了一个流程/资源上的障碍？ | ☐ |
| **CTO** | 我最近做的决策是基于什么数据/逻辑？ | ☐ |
| | 我是否培养了可以替代我做出好决策的人？ | ☐ |
| | 组织技术能力在提升吗？（而非只是项目在推进） | ☐ |

## 附录 B：角色职责备忘卡（可打印张贴）

### 开发工程师

```text
✅ 我负责: 功能模块设计+实现+测试+文档
✅ 我关注: 功能正确、代码规范、测试覆盖、性能达标
✅ 我协作: 与Tech Lead对齐技术方案，与PM对齐需求
❌ 我不做: 替架构师做系统决策（但有建议权）
⚠️ 卡住时: 先自己找方案(30min)，再带着方案问人
```

### 架构师

```text
✅ 我负责: 技术决策质量 + 系统长期健康
✅ 我关注: 架构合理性、技术债务、团队能力成长
✅ 我协作: 与CTO对齐方向、与Tech Lead确保落地
❌ 我不做: 不写代码纯画图

⚠️ 自检: 本周写了多少代码？做了什么技术决策？
```

### 管理者

```text
✅ 我负责: 团队产出 + 人员发展 + 资源保障
✅ 我关注: 目标对齐、效率提升、人员状态
✅ 我协作: 承接战略、提供资源、排除障碍
❌ 我不做: 替下属做技术决策/替下属写代码
⚠️ 自检: 本周做了什么不该我做的事？
```

### CTO

```text
✅ 我负责: 技术战略正确 + 组织能力持续提升
✅ 我关注: 方向对不对、人够不够好、钱花得值不值
✅ 我协作: 与CEO对齐业务战略、与团队对齐技术方向
❌ 我不做: 管具体项目、替总监做日常管理决策
⚠️ 自检: 我培养了多少个能独立做好技术决策的人？
```
