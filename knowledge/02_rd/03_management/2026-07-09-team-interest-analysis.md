## 一、利益相关方总览

```text
                 +--------------------------+
                 |     管理层/产品负责人      |
                 |   (方向控制·立项审批)      |
                 +-----------+--------------+
                             |
      +----------------------+----------------------+
      v                      v                      v
+-------------+     +---------------+     +------------------+
| 项目负责人   |     | 产品洞察/市场  |     |   销售/市场负责人  |
| (研发侧)     |<--->|   策略人员     |<--->|   (前场需求入口)   |
| ·推进执行    |     | ·价值判断      |     | ·客户沟通        |
| ·环境依赖    |     | ·需求来源质疑   |     | ·反馈"推进困难"   |
+------+------+     +-------+-------+     +--------+---------+
       |                    |                       |
       v                    v                       |
+--------------+    +---------------+               |
| 研发团队成员  |    | 技术规划人员   |               |
| ·演示部署     |    | ·技术验证导向  |               |
| ·环境适配     |    | ·内部需求满足  |               |
+------+------+    +-------+-------+               |
       |                    |                       |
       +----------+---------+                       |
                  v                                 |
       +------------------+                         |
       | 演示中心资源协调者 |<------------------------+
       |  ·资源调度        |
       |  ·规划不确定性    |
       +------------------+
```

### 1.1 角色矩阵

| 角色 | 决策权 | 利益取向 | 行动态度 | 信息完整度 |
|:-----|:------:|:---------|:---------|:----------:|
| **管理层/产品负责人** | 🔴**高** | 投入产出比 | ⏳ 等待需求明朗 | 中（全局视角） |
| **项目负责人（研发）** | 🟡中 | 项目落地执行 | 🟢**积极推动** | 高（技术细节） |
| **销售/市场负责人** | 🟡中 | 客户接受度 | 🔴**保守观望** | 高（客户一线） |
| **产品洞察/市场策略** | 🟡中 | 价值来源判断 | 🟡**审慎** | 中偏上 |
| **研发团队成员** | 🟢低 | 技术实现验证 | 🟢积极配合 | 中 |
| **技术规划人员** | 🟢低 | 技术储备验证 | 🟢支持（有边界） | 中 |
| **演示中心资源协调** | 🟡中 | 资源分配优先级 | 🟡**受限** | 高（资源现状） |

## 二、核心利益诉求对比

### 2.1 立场光谱

```text
                        研发驱动 <-------> 客户驱动
                            |                  |
  研发团队成员 --------------+                  |
  项目负责人 ----------------+                  |
  技术规划人员 --------------+                  |
  产品洞察/市场策略 ---------+------------------+
  管理层/产品 ---------------+------------------+
  销售/市场负责人 -----------+------------------+
                            |                  |
                    技术验证导向         市场需求导向
```

### 2.2 关键诉求对比表

| 维度 | 项目负责人（研发） | 销售/市场 | 管理层 | 产品洞察 | 核心矛盾 |
|:-----|:-----------------|:----------|:-------|:---------|:---------|
| **需求来源** | 尽快明确需求细化时间点 | 客户反馈"推进困难" | 什么时候会有需求？ | 前场没需求可以不做 | ⚡ **需求"有没有"vs"什么时候有"** |
| **项目范围** | 最小集合，后续演进 | 建议预研为主 | 满足纳管即可结项 | 等价值场景再立项 | ⚡ **做多少算够？** |
| **资源依赖** | 需要演示中心设备到位 | 资源可以申请支持 | 投入10-20人月 | 无明确资源诉求 | ⚡ **资源与人力的平衡** |
| **时间节奏** | 希望尽快推进 | 配合摸底预研 | 按软件节奏推进 | 定时沟通等时机 | ⚡ **快 vs 慢** |
| **立项流程** | 需要上会获批 | — | 必须上会获批 | 挖掘价值后立项 | ⚡ **先立还是先做？** |

### 2.3 隐藏诉求与未说出口的话

| 角色 | 显性诉求 | 隐性诉求 | 真实担忧 |
|:-----|:---------|:---------|:---------|
| **项目负责人** | 明确需求时间点、环境到位 | 希望项目不被砍、团队有持续工作 | 投入了人力但没产出，后续难以争取资源 |
| **销售/市场** | 客户有稳定供应商、推进困难 | 不想承诺无法交付的价值、保护客户关系 | 做出来的产品卖不出去，责任落到销售头上 |
| **管理层** | 立项流程合规、节奏有序 | 不想在没把握的方向上投入过多 | 投入打了水漂，被质疑决策质量 |
| **产品洞察** | 前场要有需求、价值落脚点 | 不想做"自嗨"型产品 | 技术储备变成了没人用的功能 |
| **技术规划** | 技术验证、内部需求满足 | 希望保留技术主动权 | 被外部需求牵着走，失去技术方向 |

## 三、利益冲突点与弥合路径

### 3.1 冲突 1：需求来源之争（最大冲突）

```text
研发侧: "我们觉得这个方向有价值，可以开始做"
  v 冲突
销售侧: "客户说已经有供应商了，不好推"
  v 冲突
管理层: "没需求就不要投入"
  v 冲突
产品侧: "需求必须来自前场，否则不做"

核心问题: 技术储备 vs 市场需求，谁先谁后？
```

**弥合路径**:

| 步骤 | 行动 | 负责人 | 时间 |
|:-----|:------|:-------|:----:|
| ① 割裂两个场景 | **内部技术验证**（确定做）vs **对外销售产品**（等需求） | 管理层决策 | 立即 |
| ② 明确第一期目标 | 满足自我部署+纳管需求，不做商业产品 | 项目负责人 | M+0W2 |
| ③ 建立需求收集渠道 | 月度同步前端洞察，不做"等需求"而是"探需求" | 销售+产品洞察 | 月度 |
| ④ 设定价值验证点 | 第一期完成后评估：是否有对外价值？是否继续投入？ | 管理层 | M+6 |

### 3.2 冲突 2：资源与时间的不确定性

```text
项目负责人: 需要演示中心设备，什么时候到位？
资源协调者: 博通项目结束可释放，但规划可能调整，下周才有结论

核心问题: 资源不可控，时间不可控，但人力安排需要提前
```

**弥合路径**:

| 措施 | 具体做法 |
|:-----|:---------|
| **并行准备** | 不等待设备到位，先做软件架构设计、开源选型、文档输出 |
| **设备方案 B** | 准备虚拟机/本地服务器作为开发环境的备选方案 |
| **提前沟通** | 下周对齐后锁定资源时间点，若延迟则启动 B 计划 |
| **最小验证** | 先用 1 台设备做核心功能验证，降低资源依赖度 |

### 3.3 冲突 3：立项 vs 启动的先后顺序

```text
管理层: 必须上会立项获批后才能开动
研发侧: 还没需求怎么立项？没立项怎么推进？

"先有鸡还是先有蛋"的问题
```

**弥合路径**:

| 选项 | 做法 | 风险 | 推荐 |
|:-----|:------|:----|:----:|
| **先做后立** | 小团队先干，边干边准备立项材料 | 🔴管理风险 | ❌ |
| **先立后做** | 用"技术预研/技术储备"类别立项 | 🟢合规 | **✅ 推荐** |
| **技术课题立项** | 以"AI 基础设施运维技术预研"名义，不做产品承诺 | 🟢低风险 | **✅ 首选** |

> **建议**: 以 **"AI 基础设施运维技术预研"** 立项，明确是技术储备项目，非商业产品，一期目标为内部提效+演示环境验证，验收标准为技术验证报告 + 最小可用原型。

## 四、共识基础与可用支点

### 4.1 已有共识

| 共识点 | 涉及方 | 对齐程度 |
|:-------|:-------|:--------:|
| ✅ 运维功能长期有价值 | 全员 | 🟢**高度一致** |
| ✅ 当前按最小集合开展 | 全员 | 🟢**高度一致** |
| ✅ 一期投入 10-20 人月 | 管理层+研发 | 🟢**明确限制** |
| ✅ 超节点/课题功能后延 | 全员 | 🟢**达成共识** |
| ✅ 开源软件基础上提炼 | 研发+技术规划 | 🟢**技术路线一致** |
| ✅ 演示中心资源可申请 | 资源协调+研发 | 🟡**有条件支持** |
| ✅ 月度同步机制 | 管理层发起 | 🟢**已定机制** |

### 4.2 可用支点（推进项目的杠杆点）

| 支点 | 利用方式 |
|:-----|:---------|
| **演示中心部署需求** | 研发团队的部署需求是"已经存在的需求"，可作为一期直接启动的理由 |
| **开源整合 + 产品材料** | 管理层认可的输出方式，产出明确、风险可控 |
| **内部提效** | 即使没有对外销售，内部运维提效也有价值（是"内部需求"） |
| **管理层"满足纳管即可结项"** | 明确了"什么是够"，可据此倒推最小功能集合 |
| **技术预研立项通道** | 可以直接绕过"市场需求"争议，走技术储备路线 |

## 五、各角色沟通策略

### 5.1 与管理层沟通

| 策略 | 具体做法 |
|:-----|:---------|
| **结论先行** | 先说"我们计划做什么、投入多少、产出什么"，再说理由 |
| **量化投入产出** | 10-15 人月，输出：技术验证报告 + 最小原型 + 产品材料 |
| **明确验收标准** | "满足内部部署+纳管即结项"，不做商业承诺 |
| **尊重立项流程** | 准备完整的立项材料，用"技术预研"类别走流程 |
| **对齐路标节奏** | 确认运维软件在固件→AI Infra 管理软件→AI 运维软件中的位置 |

### 5.2 与销售/市场沟通

| 策略 | 具体做法 |
|:-----|:---------|
| **降低预期** | 明确说明是"技术预研/内部工具"，非商业产品，不给他增加销售压力 |
| **减轻负担** | 需求收集改为"日常聊客户时顺带问一嘴"，不做专项调研 |
| **提供素材** | 输出 1 页纸的"运维痛点清单"，帮助销售在客户交流中有话题切入 |
| **建立闭环** | 月度同步时销售反馈→研发评估→反馈结果，让销售看到反馈有回应 |

### 5.3 与产品洞察沟通

| 策略 | 具体做法 |
|:-----|:---------|
| **区分"技术预研"与"产品立项"** | 澄清这不是产品立项，是技术储备，不占用产品资源 |
| **对齐价值判断标准** | 明确第一期验收后做价值评估，由产品洞察主导判断是否有产品化价值 |
| **信息共享** | 月度同步会共享研发进展和技术发现，帮助产品洞察积累判断依据 |
| **尊重质疑** | 正面回应"前场没需求"的问题，用"技术储备"定位避免"自嗨"风险 |

### 5.4 与项目负责人/研发团队沟通

| 策略 | 具体做法 |
|:-----|:---------|
| **明确边界** | 10-20 人月、最小集合、不做超节点功能、不做完整商业产品 |
| **保护研发节奏** | 在资源到位前可并行：架构设计、开源调研、文档输出 |
| **建立缓冲** | 演示中心设备不确定 → 准备本地开发替代方案 |
| **赋能团队** | 开源整合 + 产品材料输出 = 可量化的团队产出和成长 |

## 六、利益格局总结

```text
当前利益格局:

       支持推进 <-------------> 控制风险
              |                  |
   研发团队 --+                  |
   项目负责人 -+                  |
   技术规划 ---+                  |
              |                  |
   产品洞察 --+-----------------+
   管理层 ----+-----------------+
   销售 ------+-----------------+
              |                  |
        最小集合 + 技术预研定位
        是当前各方的最大公约数
```

### 6.1 最大公约数方案

| 要素 | 内容 |
|:-----|:------|
| **定位** | 技术预研项目，非商业产品 |
| **目标** | 开源整合 + 产品材料 + 演示中心部署 |
| **范围** | 最小功能集合（自我部署+纳管） |
| **投入** | 10-15 人月（在 10-20 人月范围内偏保守） |
| **节奏** | 先跑起来，月度同步，第一期完成后再评估 |
| **立项** | 技术预研类目，上会获批 |
| **验收** | 技术验证报告 + 最小可用原型 + 产品材料 |

### 6.2 风险预警

| 风险 | 概率 | 影响 | 缓解 |
|:-----|:----:|:----:|:-----|
| 演示中心资源迟迟不到位 | 🟡中 | 🔴项目搁置 | 并行做软件设计，准备 B 方案 |
| 销售一直收不到需求 | 🟡中 | 🟡缺乏立项依据 | 以"内部提效"为价值锚点，不依赖外部需求 |
| 管理层质疑"技术预研"产出 | 🟢低 | 🟡方向调整 | 明确输出物和验收标准，主动汇报进展 |
| 团队人力被其他项目抢占 | 🟡中 | 🔴进度延迟 | 锁定 10-15 人月的人力承诺 |
| 开源选型后发现不满足需求 | 🟢低 | 🟡中期返工 | 选型阶段做充分 POC 验证 |
