# 🔄 前移与后移操作：责任重分配的组织动力学与平台承载

> **版本**: v1.0 | **日期**: 2026-08-06 | **状态**: ✅ 生效中
>
> **定位**: 深度分析"前移（Shift-Left）与后移（Shift-Right）操作"的本质——**不是操作在价值链上的位置移动，而是责任、知识、能力在角色间的再分配**。回答三个问题：①前移/后移到底移的是什么？②为什么"别人"默认不接纳？③平台如何成为接纳的杠杆？以报销前移、单元测试前移、RAS 前移三个案例贯穿。
>
> **核心洞察**: 前移的本质是**把判断责任从专家转移到执行者（或系统）**。接纳与否由四个变量决定——**责任恐惧、能力补齐（工具化）、利益补偿、容错安全**。**平台是把"只转责任"变成"责任+能力+知识同时转移"的关键杠杆**：只转责任不转能力=必然抵触；责任与能力一起转（平台承载）=自然接纳。前移与后移不是对立而是互补：**前移处置高频低价值的确定性检查，后移保留低频高价值的专业复核**（80/20 原则）。

## §1 概念界定：前移/后移到底移的是什么

### 1.1 时间轴：价值链位置

**表面定义**：前移（Shift-Left）= 把操作在时间轴上**提前**（如测试从发布前移到编码时）；后移（Shift-Right）= 把操作**推迟或下放**（如容错从设计期移到运行期，审计从过程移到期末）。

```text
        +------------ value-chain timeline ------------+
        | Req -> Design -> Dev -> Test -> Release -> Ops |
        +-----------------------------------------------+
  Shift-Left  <---- move judgment/check/decision earlier
  Shift-Right ----> concentrate judgment/check/decision later
```

这层理解是对的，但**只看到了冰山一角**。

### 1.2 责任轴：判断权归属

前移/后移真正改变的是**"谁来承担判断责任"**：

| 操作 | 前移前 | 前移后 | 判断权变化 |
|:-----|:-------|:-------|:-----------|
| 报销审核 | 财务判断发票合规 | 员工自我判断 + 系统规则 | 财务 → 全员+系统 |
| 单元测试 | 测试部判断质量 | 开发自证质量 + 门禁判定 | 测试部 → 开发+CI |
| RAS 设计 | 可靠性工程师事后验证 | 设计者事前设计 + 评审把关 | 可靠性 → 设计者+评审 |

**关键洞察**：前移的本质是**判断权的下放与再分配**。表面是"操作位置移动"，实质是"责任从专家手里转移到执行者手里（或系统手里）"。这就解释了为什么前移必然遭遇阻力——**任何责任再分配都触动既得权力结构**，与操作本身是否合理无关。

### 1.3 知识轴：判断所需知识的所在地

判断权转移的同时，**判断所需的隐性知识**并没有自动转移：

- 财务的发票知识（税务规则/费用标准/发票真伪）→ 员工没有
- 测试部的测试设计知识（等价类/边界值/覆盖率）→ 开发没有（或不想用）
- 可靠性工程师的失效知识（FTA/FMEA/故障模式）→ 设计者没有

**这是接纳问题的根源**：前移若只转移责任不转移知识，被前移方必然用"我不会/我不懂/出了事谁负责"来抵抗——而且**这种抵抗是理性的**，不是态度问题。

### 1.4 第一性原理：前移=提前暴露不确定性，后移=集中处置不确定性

从系统论看（活系统：输入→状态→输出→反馈）：

- **前移**：把"错误发现点"从下游（成本高）挪到上游（成本低），本质是**用上游的额外注意力换取下游的修复成本节省**。收益 = 下游修复成本 − 上游预防成本。
- **后移**：把"不确定性"集中到少数专家/系统处置，本质是**用集中的专业能力换取分布的注意力节省**。收益 = 分布预防成本 − 集中处置成本。

两者都是经济学决策，**不是道德问题**。判断一个操作该前移还是后移，第一性原理是：

```text
shift-left  benefit > shift-left  cost (incl. resistance)  -> worthwhile
shift-right benefit > shift-right cost (incl. quality risk) -> worthwhile
```

其中**阻力成本**（组织不接受导致的推行损耗、敷衍执行、返工）常常被低估——这正是"别人会接纳吗"问题的经济实质。

## §2 三案例解剖

### 2.1 报销前移：财务审核 → 全员填报

**前移内容**：发票合规性判断、费用归属判断、报销单规范性——从财务审核环节前移到员工填报环节。

**传统流程**（后移模式）：
```text
emp submit -> finance review each (compliance/authenticity/category/limit) -> reject & refill -> pay
                    ^ knowledge sits in finance; employee just submits materials
```

**前移后**：
```text
emp fill (system realtime check: OCR invoice + rule engine + standard template) -> auto flag anomaly -> finance review only anomaly -> pay
                    ^ judgment shifted to employee (backed by system) + finance upgraded to rule-designer + anomaly-arbiter
```

**责任变化**：
- 员工：从"交材料"→"自我负责的填报"（增加了合规责任）
- 财务：从"逐单审核"→"规则设计 + 异常处理 + 审计兜底"（审核权部分让渡，但获得更高价值角色）

**阻力点**（为什么员工和财务都可能不接纳）：
- 员工：①不懂财务规则（填错被拒=浪费时间）②操作成本增加（以前扔给财务，现在要自己搞）③"报销是财务的事"的惯性认知
- 财务：①放权恐惧（员工乱填→合规风险→追责到财务）②角色焦虑（审核工作被系统替代→岗位价值感下降）③规则设计能力不足（以前审单，现在要写规则）

**平台解法**：报销平台（OCR 票据识别 + 规则引擎 + 费用标准库 + 模板 + 异常池 + 合规看板）——把财务的隐性知识**显性化到系统**，员工面对的不是"规则空白"而是"引导式填报"。

### 2.2 单元测试前移：测试部 → 开发自证

**前移内容**：单元测试用例编写与执行、覆盖率责任——从测试部（或发布前）前移到开发编码阶段。

**传统流程**：
```text
dev code -> handover -> QA design cases + execute -> defect rework -> regression
                 ^ quality verification owned by QA (backend centralized)
```

**前移后**（TDD/左移测试）：
```text
dev code (with unit tests, CI gate: coverage/pass) -> handover -> QA focus on integration/scenario/exploratory
                 ^ self-certify quality shifted to dev (CI platform gate auto-judges)
```

**责任变化**：
- 开发：从"写码"→"写码+自证质量"（增加了质量责任）
- 测试部：从"全量验证"→"测试设计/平台建设/集成与探索测试/质量门禁维护"（验证权部分让渡，角色向"质量工程"升级）

**阻力点**：
- 开发：①时间压力（交付周期不变，工作量增加）②写测试无成就感（"测试是别人的活"）③能力不足（没受过测试设计训练）
- 测试部：①岗位价值焦虑（"开发自己测了，还要我们干嘛"）②质量归因风险（线上出问题，是开发没测好还是测试没把关？）③技能转型压力（从执行用例到设计测试体系）

**平台解法**：CI/CD 平台（测试模板库 + AI 生成用例 + 覆盖率门禁 + 失败回溯 + 质量看板）——测试部的知识沉淀为**用例库/规范/门禁规则**，开发写测试时有模板可依、有门禁兜底、有数据证明。

### 2.3 RAS 前移：事后验证 → 设计阶段

**前移内容**：失效模式分析（FTA/FMEA）、可测性设计、故障诊断能力——从测试验证/运维阶段前移到产品设计阶段（RAS = Reliability, Availability, Serviceability）。

**传统流程**：
```text
design (no failure concern) -> manufacture -> test finds faults -> ops handles -> postmortem
                             ^ reliability knowledge in test/ops hands, missing at design phase
```

**前移后**（RAS by Design，参考超节点 FTA 可追溯性分析）：
```text
design phase: FTA fault tree + testability design (diagnostic points/sensors/logs) -> manufacture -> test validates design assumptions -> ops diagnoses per design
                 ^ failure knowledge shifted to designer (backed by KB + checklist + review)
```

**责任变化**：
- 设计者：从"只考虑功能性能"→"功能+失效+可测性"（增加了可靠性设计责任）
- 可靠性工程师：从"事后测试验证"→"设计咨询/评审专家/知识库建设者"（验证权部分让渡，角色向"设计伙伴"升级）

**阻力点**：
- 设计者：①FTA/FMEA 知识门槛（没受过失效分析训练）②设计周期压力（加可靠性设计=加工作量）③"失效是运维的事"的惯性认知
- 可靠性工程师：①话语权流失（设计阶段参与但"说了不算"）②验证价值被稀释（设计做得好=测试问题少=可靠性部门看起来没事干）③技能转型（从故障处理到失效模式库建设）

**平台解法**：可靠性知识平台（故障树模板库 + 历史故障库 + 设计检查清单 + AI 设计审查 + 评审流程）——把可靠性工程师几十年的失效经验**沉淀为知识库**，设计者查得到、用得上、有评审兜底。

### 2.4 三案例共性与差异

| 维度 | 报销前移 | 测试前移 | RAS 前移 |
|:-----|:---------|:---------|:---------|
| 被前移方 | 全员（非专业） | 开发（半专业） | 设计者（专业但非本行） |
| 让渡方 | 财务 | 测试部 | 可靠性工程师 |
| 判断类型 | 规则型（可规则化） | 方法型（可模板化） | 知识型（可知识库化） |
| 平台角色 | 规则引擎+OCR | CI 门禁+模板+AI | 知识库+检查清单+评审 |
| 让渡方角色升级 | 规则设计者+审计 | 测试设计者+平台主 | 设计咨询+评审专家 |
| 最大阻力 | 员工规则盲区 | 开发时间压力 | 设计知识门槛 |

**共性规律**：三者都是"判断权从专家下放到执行者"，且**让渡方都面临角色焦虑、被前移方都面临能力鸿沟**——这就是接纳问题的普遍结构。差异只在"判断的可形式化程度"：报销是规则型（最好前移）、测试是方法型（次之）、RAS 是知识型（最难，最依赖知识库）。

## §3 为什么默认不接纳：四维阻力模型

> 前置：`2026-07-20-responsibility-misplacement-brain-hands.md`（职责错位）提供认知层解释——七种归因偏差让"大脑"天然倾向"怪手"。

### 3.1 责任恐惧：判断权转移的心理成本

- **被前移方**：责任增加 → "做错了我担责"的恐惧。报销填错被拒/测试漏测线上故障/RAS 设计遗漏导致事故——**新增责任没有新增回报**，理性人必然抵触。
- **让渡方**：责任让渡 → "失控"的恐惧。财务担心乱填合规风险、测试担心质量失控、可靠性担心设计缺陷漏网——**放权意味着对不可控结果负责**。

**本质**：责任恐惧 = 责任增加 × 控制感缺失 × 后果不可逆。三者的乘积决定恐惧强度。

### 3.2 能力鸿沟：知识没有同步转移

- 判断所需的隐性知识（财务规则/测试设计/失效模式）仍留在让渡方手里
- 被前移方**被要求做"超出当前能力的事"** → 用"我不会"抵抗，或"做了但做错"
- **前移失败的典型模式**：责任已转移、知识未转移 → 被前移方"假装执行"（形式主义）→ 质量反而下降 → 让渡方说"看吧，我就说不行" → 前移失败回滚

### 3.3 利益失衡：工作量与价值的再分配

| 角色 | 前移后工作量 | 前移后价值感 | 失衡点 |
|:-----|:------------|:------------|:-------|
| 被前移方 | ↑（新增职责） | 不变或↓（视为负担） | 干了活没回报 |
| 让渡方 | ↓（部分工作被替代） | ↓（岗位价值被稀释） | 价值感被掏空 |
| 平台/系统 | ↑（建设责任） | 中立 | 建设成本谁来担 |

**利益失衡是接纳问题的经济根源**：前移让渡方"被拿走工作"（损失）、被前移方"被塞入工作"（损失）——**双方都损失，只有组织获益**，除非有补偿机制。

### 3.4 文化冲突：容错度与追责文化

- 前移要求"早期暴露错误"文化（上游敢犯错、早暴露）——但多数组织是**追责文化**（出错=考核受损）
- 被前移方理性选择：**不暴露、不主动、做表面**（隐藏错误比暴露错误更安全）
- 前移的收益建立在"上游真实暴露问题"之上——**文化不匹配则前移收益归零**

### 3.5 认知偏差的放大作用

引用职责错位综合征的七种归因偏差，前移场景下被放大：

| 偏差 | 在前移中的表现 |
|:-----|:---------------|
| 基本归因错误 | "报销乱填=员工不负责"（归人）而非"规则不可及"（归系统） |
| 知识的诅咒 | 财务觉得规则很简单，员工怎么老填错 |
| 自我服务偏差 | 测试部认为质量问题是开发写码差，开发认为是测试没测出 |
| 确认偏差 | 只看到前移失败的案例，忽视成功案例 |
| 行动者-观察者不对称 | 让渡方看被前移方"敷衍"，被前移方觉得自己"尽力了" |

**结论**：前移的阻力不是态度问题，是**结构问题**——责任恐惧×能力鸿沟×利益失衡×文化冲突，再被认知偏差放大。不理解这四维，任何前移都会以"别人不配合"收场。

### 3.6 前移 vs 后移的阻力不对称

| | 前移 | 后移 |
|:--|:-----|:-----|
| 直觉符合度 | 违背（"外行干专家的活"） | 符合（"专业的事给专业的人"） |
| 典型阻力 | 高（责任/能力/利益/文化四维全触发） | 低（但被前移方可能超载） |
| 隐性风险 | 形式主义、责任稀释 | 下游瓶颈、信息衰减、越晚越贵 |
| 典型场景 | 测试左移、报销自助、RAS by Design | 集中审计、专项治理、容错运行期兜底 |

**不对称的启示**：前移需要**主动设计接纳机制**（§4），后移则要警惕"看似合理实则低效"（§7.3）——后移的阻力小不代表后移正确，只是因为它符合直觉。

## §4 接纳模型：什么条件下前移会被接纳

### 4.1 接纳度公式

```text
acceptance = (capability-completion x benefit-compensation x fault-tolerance) / responsibility-fear
```

- **能力补齐**（0~1）：知识/工具/模板是否同步到位——化解 §3.2
- **利益补偿**（0~1）：被前移方和让渡方是否获得新价值——化解 §3.3
- **容错安全**（0~1）：失败是否有安全网、是否可逆——化解 §3.1/3.4
- **责任恐惧**（>0）：新增责任的恐惧强度——分子趋 0 则接纳趋 0

**推论**：
1. 三者中任一为 0 → 接纳度为 0（前移必然失败）
2. 责任恐惧 > 分子 → 接纳度 < 1（表面接纳，实际敷衍）
3. **平台同时提升分子三项**（能力补齐=工具态、利益补偿=角色升级、容错安全=门禁兜底），是唯一能整体抬升接纳度的杠杆

### 4.2 条件一：能力补齐（工具化）

**原则**：责任转移必须伴随"判断所需知识的形式化交付"。

| 案例 | 知识形式化方式 | 被前移方面对的 |
|:-----|:---------------|:---------------|
| 报销 | 规则引擎+OCR+标准模板+引导式表单 | 不是"空白表单"而是"被引导的填报" |
| 测试 | 用例模板库+AI 生成+覆盖率门禁 | 不是"自己发明测试"而是"按模板自证" |
| RAS | 故障树模板+历史故障库+检查清单 | 不是"从零做 FTA"而是"查库+勾选+评审" |

**要点**：能力补齐不是培训一次就完，而是**把知识固化进工作流**——人在流程中"被知识引导"，而不是"被要求懂知识"。

### 4.3 条件二：利益补偿（角色升级）

**原则**：让渡方不能"被拿走工作"，而要"升级到更高价值工作"；被前移方不能"被塞入负担"，而要"获得可度量回报"。

| 案例 | 让渡方角色升级路径 | 被前移方回报 |
|:-----|:-------------------|:-------------|
| 报销 | 逐单审核 → 规则设计者+异常裁决者+合规审计 | 报销更快（当日到账）、不再被打回 |
| 测试 | 执行用例 → 测试架构师+平台建设者+质量门禁主 | 缺陷更早发现、返工更少、交付更快 |
| RAS | 事后验证 → 设计咨询+评审专家+失效知识库主 | 设计一次通过率提升、现场问题减少 |

**要点**：利益补偿的核心是**让双方都看到"前移后自己更值钱"**——让渡方从"重复劳动"升级为"知识设计"，被前移方从"被动接活"变为"主动受益"。

### 4.4 条件三：容错安全（失败安全网）

**原则**：前移初期错误必然增多（学习曲线），必须有**分级兜底**，不能"一次出错就追责"。

- **门禁兜底**：系统级校验（报销规则/覆盖率门禁/FTA 检查清单）拦截低级错误
- **灰度试点**：先在低风险团队试点，跑通再推广（RAS 先在一个产品线试行）
- **容错期**：明确"前移过渡期 N 个月，错误不追责、只复盘"
- **例外通道**：保留专家复核通道（异常池/评审会），让被前移方"有地方求助"

### 4.5 接纳四阶段（ADKAR）

```text
A awareness (why shift-left) -> D desire (why should I comply) -> A ability (what enables me) -> R reinforcement (what do I gain)
```

| 阶段 | 关键动作 | 对应阻力 |
|:-----|:---------|:---------|
| 意识 | 讲清"前移对组织/对个人的收益"，用数据（返工成本/事故率） | 认知偏差 |
| 意愿 | 利益相关者访谈，让渡方参与设计（给话语权） | 利益失衡 |
| 能力 | 工具/模板/知识库/培训同步到位 | 能力鸿沟 |
| 强化 | 度量+激励+表彰，让成功案例可见 | 文化冲突 |

## §5 平台的作用：责任与能力的同步转移

### 5.1 平台三态：工具态/治理态/认知态

| 平台态 | 定义 | 承载内容 | 解决维度 |
|:-------|:-----|:---------|:---------|
| **工具态** | 效率放大器 | 自动化执行（OCR/CI/门禁/模板生成） | 能力补齐（做得到） |
| **治理态** | 规则执行器 | 规则引擎/检查清单/门禁/异常池 | 容错安全（做对了） |
| **认知态** | 知识载体 | 知识库/模板库/历史库/最佳实践 | 知识转移（懂不懂） |

**关键**：真正让前移被接纳的，不是工具态（效率），而是**认知态**——把专家的隐性知识变成"任何人在流程中都能获取的显性知识"。工具态解决"能做"，认知态解决"会做"，治理态解决"做对"。

### 5.2 平台如何化解四维阻力（一一对应）

| 阻力维度 | 平台化解机制 | 机制本质 |
|:---------|:-------------|:---------|
| 责任恐惧 | 门禁拦截低级错误 + 审计留痕（责任可追溯而非"背锅"） | 责任从"人扛"变"人+系统共担" |
| 能力鸿沟 | 知识库/模板/引导式流程（知识固化进工作流） | 隐性知识显性化 |
| 利益失衡 | 让渡方成为"平台主"（建设权+话语权），被前移方获得效率回报 | 权力再分配为共建 |
| 文化冲突 | 数据看板让"前移效果"可见（质量指标/效率指标） | 用数据代替指责 |

**核心洞察**：平台把"责任转移"变成"**责任+能力+知识一起转移**"。被前移方不是"被要求独立承担"，而是"在平台的支撑下承担"——**责任恐惧被系统分担，能力鸿沟被知识库填平，利益失衡被共建权补偿**。

### 5.3 平台化前移的架构六要素

1. **知识库**（认知态核心）：判断所需知识的显性化沉淀（规则库/用例库/故障库）
2. **模板与引导**（能力补齐）：让执行者"按模板做"而非"从零发明"
3. **规则引擎/门禁**（治理态）：确定性检查自动化，拦截低级错误
4. **异常池/升级通道**（容错安全）：不确定性事件集中到专家处置
5. **数据看板**（反馈闭环）：度量前移效果（通过率/返工率/事故率），驱动改进
6. **AI 增强**（认知态升级）：AI 把知识库"喂给"执行者（问答/推荐/生成），进一步拉平能力差

### 5.4 平台的风险：平台成为新瓶颈

- **平台责任虚化**：出了问题怪平台，人反而免责 → 平台成为"背锅侠"，前移责任被稀释
- **形式主义**：平台流程填表化，执行者"走形式"而非"真判断"（报销乱填但系统校验通过）
- **平台建设成本**：平台本身要人维护（规则更新/知识库维护）→ 让渡方从"审核员"变"平台维护员"，可能更累
- **过度前移**：什么都塞进平台 → 平台臃肿、规则冲突、执行者无所适从

**对策**：平台要"留例外通道"（不确定性永远有人处置）、"留人工裁决"（平台判不了的上报）、"留审计"（平台本身定期审计）。

### 6.3 自反洞察：为什么本系统的前移阻力小

本系统的前移是**单人系统**（用户既是设计者、执行者、审查者），但恰恰验证了 §4 接纳模型：

1. **能力补齐**：每个前移都有脚本/工具/知识库同步交付（不是"要求合规"而是"自动合规"）
2. **利益补偿**：前移直接减少用户的治理税（重命名 4488 次→0、断裂 83→0），利益立竿见影
3. **容错安全**：所有操作可逆（git 历史 + tmp/bak + 备份），错误可恢复
4. **责任恐惧趋零**：单人系统无"责任恐惧"维度，阻力只剩认知成本

**推论**：当系统从单人扩展为多角色组织时，前移的阻力会从"认知成本"放大为"组织成本"（§3 四维）——**本系统现在验证了前移的技术可行性，而 §2-§5 分析的是前移的组织可行性**。这也是为什么本文档强调：单人系统里"前移"是纯技术问题，多人系统里"前移"首先是组织问题。

## §7 前移与后移的辩证：最优配置

### 7.1 80/20 原则：高频确定性前移，低频专业性后移

```text
judgment-type x frequency x certainty -> placement decision

high-freq + certain   (rules/format/links)        -> shift-left (platform auto-exec)    e.g. expense rule check, format check
high-freq + uncertain (design decisions)          -> shift-left + expert support        e.g. test design, RAS design
low-freq  + certain   (compliance audit)          -> shift-right (periodic batch)       e.g. monthly audit, health check
low-freq  + uncertain (strategy/postmortem)       -> shift-right (expert deep handling) e.g. root-cause analysis, annual planning
```

**原则**：确定性越强、频率越高 → 越该前移（用系统替代人）；不确定性越强、价值越高 → 越该后移（保留人的判断）。

### 7.2 前移过度的失败模式

- **形式主义**：前移变成"填表文化"，执行者走流程不走心（报销乱填但校验通过）
- **上游瘫痪**：所有责任压到上游，上游人员超载，产出率下降
- **责任稀释**：人人负责=无人负责，出错时互相推诿（"我按平台规则做的"）
- **知识断层**：专家彻底退出流程，隐性知识无人传承（财务不审了，新员工没人教）

### 7.3 后移过度的失败模式

- **下游瓶颈**：所有判断集中到少数专家，专家成为瓶颈（报销单堆积/测试排队）
- **信息衰减**：越往后传递信息损失越大（知识诅咒：上游以为说清了，下游以为懂了）
- **越晚越贵**：错误发现点越晚修复成本越高（设计错误→测试发现→返工成本指数上升）
- **反馈滞后**：问题发现太晚，学习循环太长（前端错误到月末审计才发现）

### 7.4 操作×阶段×责任最优配置矩阵

| 操作 | 最优位置 | 执行主体 | 平台承载 | 兜底 |
|:-----|:---------|:---------|:---------|:-----|
| 格式/规范检查 | 生成时（前移） | 全员+系统 | 检查脚本 | 月度专项修复 |
| 链接/引用契约 | 提交时（前移） | 系统 | link-validator/fixer | 定期全库扫描 |
| 报销合规 | 填报时（前移） | 全员+规则引擎 | OCR+规则 | 财务异常池 |
| 单元测试 | 编码时（前移） | 开发+CI | 模板+AI+门禁 | 测试部集成验证 |
| RAS 设计 | 设计阶段（前移） | 设计者+评审 | 知识库+检查清单 | 可靠性评审会 |
| 集成测试 | 发布前（中置） | 测试部 | 测试平台 | 生产灰度 |
| 合规审计 | 期末（后移） | 审计/财务 | 审计工具 | 制度保障 |
| 事故复盘 | 事故后（后移） | 专家团队 | 复盘模板 | 改进跟踪 |

## §8 落地路线与行动建议

### 8.1 三阶模型：试点→制度化→平台化

```text
Phase 1 Pilot (1-3mo): pick a team/product-line, validate the 3 acceptance conditions
  -> goal: prove capability+benefit+tolerance, produce success-case data
Phase 2 Institutionalize (3-6mo): turn pilot experience into policy
  -> goal: define new responsibility boundaries, KPIs, upgrade path (ceding party role shift)
Phase 3 Platformize (6-12mo): settle policy into platform
  -> goal: KB/templates/gates/dashboards ready, shift-left becomes default way of working
```

**关键**：三阶段不可跳级——直接平台化（跳过试点）= 建了平台没人用；直接制度化（跳过试点）= 制度写在纸上没人执行。

### 8.2 利益相关者四象限分析

|  | 受益者 | 受损者（感知） |
|:--|:-------|:---------------|
| **让渡方** | 角色升级（规则设计/评审专家） | 工作被替代、话语权流失 |
| **被前移方** | 效率提升、质量自证 | 责任增加、能力门槛 |
| **管理层** | 成本下降、质量提升 | 变革风险、推行成本 |

**行动**：
- 让渡方：给"平台主/知识库主"头衔与建设权（利益补偿 §4.3）——**让"被替代的人"变成"替代系统的主人"**
- 被前移方：给工具+模板+容错期（能力补齐+容错安全）——**让"被要求的人"变成"被支撑的人"**
- 管理层：用数据承诺（试点 ROI 预估）——**让"变革"变成"投资"**

### 8.3 三案例行动清单

**报销前移**：
1. 梳理财务规则 → 规则引擎化（先覆盖 80% 高频规则）
2. 上线 OCR 票据识别 + 引导式填报模板
3. 财务角色转型：规则设计 + 异常池裁决 + 月度合规审计
4. 试点一个部门 → 度量（填报一次通过率、报销周期）→ 推广

**单元测试前移**：
1. 建设测试模板库（按模块/语言分类）+ CI 覆盖率门禁
2. AI 辅助生成用例（从代码/需求生成初稿，人审）
3. 测试部转型：测试架构设计 + 平台维护 + 集成/探索测试
4. 试点 1-2 个团队 → 度量（缺陷逃逸率、返工率、交付周期）→ 推广

**RAS 前移**：
1. 建设失效知识库（历史故障 → FTA/FMEA 模板，参考超节点 FTA 可追溯性实践）
2. 设计阶段嵌入"可靠性检查清单"（设计评审必过项）
3. AI 设计审查（自动识别设计中的失效风险点，人工复核）
4. 试点一个产品线 → 度量（设计评审缺陷数、现场故障率、MTTR）→ 推广

### 8.4 度量与反馈

**接纳度指标**（前移是否被真接纳）：
- 使用率：平台使用频次/覆盖率（形式主义预警：使用率高但质量没变=走形式）
- 一次通过率：填报/测试/RAS 检查的一次通过率（能力补齐是否到位）
- 返工率：被打回/返修比例（前移质量）
- 质量指标：缺陷逃逸率/故障率/事故率（前移效果）
- 投诉与求助：异常池升级量（前移是否留了出口）

**反馈闭环**：月度复盘 → 看板更新 → 规则/知识库迭代 → 下一轮（复用 meth-012 可观测方法论：目标→指标→实测→调整）。
