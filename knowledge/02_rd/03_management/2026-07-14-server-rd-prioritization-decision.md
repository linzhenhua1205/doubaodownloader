## 1. 「能做」与「应做」的永恒张力

### 1.1 服务器研发的特殊困境

服务器研发与其他软件/硬件领域相比，面临一个**三重过载**的结构性问题：

| 来源 | 典型例子 | 频率 | 不可控程度 |
|:-----|:---------|:----:|:---------:|
| **问题处理** | 线上故障·兼容性问题·芯片 errata·固件 Bug·供应链变更 | 每日 | 🔴 高（被动触发） |
| **需求规划** | 客户定制·产品路线图·竞品追赶·新场景适配 | 每周 | 🟡 中（可协商） |
| **架构优化** | 性能瓶颈·可维护性差·技术债·下一代架构演进 | 每月 | 🟢 低（自主驱动） |

**核心矛盾**：三类工作的来源互不协调，但共享同一组研发资源。当它们同时涌现时，没有任何一个天然有「更高的优先级」——每个提议者都有充分的理由。

### 1.2 「能做」的无限性

```text
工程师视角：
  "这个模块的代码太烂了，重构吧"
  "这个性能瓶颈可以优化，收益 15%"
  "这个新框架可以降低后续开发成本"
  "这个 bug 虽然不常见但确实是个隐患"
  ... -> 每一条都是事实，每一条都能做

管理者视角：
  "客户的这个定制需求下个月要交付"
  "竞争对手发布了新功能，我们需要跟上"
  "合规审计发现了 12 个需要整改的项"
  "明年的产品规划需要现在开始预研"
  ... -> 每一条都有外部压力

结果：两边加起来，可做的事远超产能 × 2
```

### 1.3 不做判断的代价

| 做法 | 短期效果 | 长期代价 |
|:-----|:---------|:---------|
| **全都要做**（不排优先级） | 人人有活干 | 每件事都做一半，没有真正完成的事 |
| **按声音大小决定** | 快速响应最吵的人 | 系统性地忽视重要但不紧急的事 |
| **按技术兴奋度决定** | 团队有激情 | 架构越来越前卫，但客户不买账 |
| **按管理者个人直觉** | 决策很快 | 方向飘忽不定，团队失去信任 |
| **拖到最后一刻才决定** | 信息最充分 | 已经来不及做了，被迫接受最低质量方案 |

### 1.4 判断的本质：识别「不需要做」和「以后再做」

> **优先级决策的核心能力不是「选出什么最重要」，而是「敢于说『这个不做』和『这个以后再做』」**

这是一个反直觉的洞察——大多数团队在「选什么」上花大量时间，在「放弃什么」上从不花时间。

## 2. 核心框架：服务器研发的四象限决策模型

### 2.1 经典 Eisenhower 矩阵的适配

Eisenhower 矩阵（紧急 × 重要）在产品研发场景需要做适配——对服务器研发而言，**「紧急」和「重要」的维度需要细化**：

```text
          紧急
        ┆
   高   ┆  I（Do First）     II（Schedule）
        ┆  线上P0/P1故障     架构演进
        ┆  客户交付deadline   核心性能优化
        ┆  安全漏洞          技术债还贷计划
        ┆  供应链紧急变更      平台化建设
        ┆
------------------------------------------- 重要性
        ┆
   低   ┆  III（Delegate）    IV（Eliminate/Delay）
        ┆  非关键告警         「还不错但不必要」
        ┆  日常运维操作       完美主义重构
        ┆  内部工具小优化      非核心场景的锦上添花
        ┆  临时数据查询       无客户验证的「灵光一现」
        ┆
        +------------------------------------
           高                低
```

### 2.2 服务器研发场景中的「紧急」再定义

在服务器研发中，「紧急」不是单一的维度，而是以下三个因素的叠加：

| 紧急因子 | 定义 | 典型例子 | 量化指标 |
|:---------|:-----|:---------|:---------|
| **时间敏感度** | 不做的话，窗口期会消失 | 客户招标截止、芯片 tape-out 冻结、合规整改期限 | 倒计时天数 |
| **影响半径** | 不做会影响多少人/设备 | P0 故障影响整个集群、单模块 Bug 影响特定配置 | 受影响节点数 |
| **连锁反应** | 不做的延迟成本 | 架构决策堵住后续功能、接口变更影响 3 个下游团队 | 阻塞的后续任务数 |

**判断「紧急」的正确问题不是「这件事急不急」，而是「如果今天不做，一周后做会产生什么额外成本？」**

### 2.3 服务器研发场景中的「重要」再定义

| 重要因子 | 定义 | 典型例子 | 量化指标 |
|:---------|:-----|:---------|:---------|
| **战略对齐度** | 是否支撑产品长期路线图 | 与产品 Roadmap 匹配、符合技术方向 | Roadmap 覆盖度 % |
| **复用杠杆** | 做完后能惠及其他多少场景 | 平台能力建设、统一管理框架 | 复用场景数 |
| **竞争壁垒** | 是否形成差异化优势 | 核心技术指标领先、独家特性 | 对比竞品的领先幅度 |
| **风险降低** | 是否消除重大隐患 | 单点故障消除、供货风险降低、合规风险消除 | 风险等级降低级数 |

### 2.4 四象限决策的细化

#### 第一象限（Do First）：紧急且重要

| 事项 | 说明 | 投入原则 |
|:-----|:-----|:---------|
| 线上 P0/P1 故障 | 影响客户业务的严重故障 | **全力投入**，但不做过度修复——先止损，再根治 |
| 客户硬性交付 | 合同约定的交付节点 | **守住底线**，但要评估是否可谈判功能范围 |
| 安全漏洞利用 | 已发现被利用痕迹的漏洞 | **立即修复**，同步排查同类问题 |
| 供应链断供 | 关键芯片/器件停产或禁运 | **立即启动替代方案**，不追求完美替代 |

**第一象限的陷阱**：

- ❌ 把「客户想要」等同于「客户deadline」——不是所有要求都是硬性交付
- ❌ 把「领导关注」等同于「紧急」——领导关注 ≠ 需要立刻动手
- ❌ 把「看起来像故障」等同于「真故障」——先确认影响范围再投入

#### 第二象限（Schedule）：重要不紧急

| 事项 | 说明 | 投入原则 |
|:-----|:-----|:---------|
| 架构演进 | 下一代架构设计、关键技术预研 | **固定时间窗口**，不受日常事务侵蚀 |
| 系统性性能优化 | 涉及架构层面的性能提升 | **设定目标**（如 P99 降低 30%），按里程碑推进 |
| 技术债还贷 | 有计划的代码/架构重构 | **19 号原则**：每月固定 10-20% 产能 |
| 平台化建设 | 可复用的基础设施 | **投资思维**：衡量 ROI 和长期收益 |
| 人才培养 | 团队技能提升、知识沉淀 | **制度化**：代码审查、技术分享、文档建设 |

**第二象限是真正的「生产力引擎」**——长期竞争力来自这块工作的质量。但这也是**最容易被第一象限和第三象限侵蚀**的区域。

**保护策略**：

- 为第二象限保留**固定的产能配额**（如 20% 时间不受干扰）
- 以「投资回报率」而非「紧迫感」衡量价值
- 允许第二象限工作「慢但持续」——不要追求短期爆发

#### 第三象限（Delegate/Rapid）：紧急不重要

| 事项 | 说明 | 处理原则 |
|:-----|:-----|:---------|
| 非关键告警处理 | 不会影响业务的告警 | **快速过滤**：自动化处理或定时批量处理 |
| 日常运维操作 | 版本升级、配置变更 | **脚本化/SOP 化**，减少手工干预 |
| 临时数据查询 | 业务方临时要的数据 | **工具化**建立自助查询平台，拒绝单次手工 |
| 非关键客户问询 | 非紧急的支持请求 | **分流**：由一线支持团队处理，研发仅做升级支持 |

**第三象限的陷阱**：

- ❌ 把「日常运维操作」做成了「必须高级工程师才能做」——文档化、脚本化后可以下放
- ❌ 每件事都小，但数量多到吃掉整个团队的产能——需要批量处理或自动化
- ❌ 让核心研发成员大量处理第三象限事务——这是最大的隐性浪费

**处理策略**：

1. **自动化**：重复性工作写脚本/工具
2. **分流**：建立明确的责任矩阵（RACI），谁负责什么
3. **批量处理**：固定时间段集中处理
4. **设定响应 SLA**：不是所有问询都需要立即回复

#### 第四象限（Eliminate/Delay）：紧急不重要（其实是「不重要」）

| 事项 | 说明 | 处理原则 |
|:-----|:-----|:---------|
| 「还不错」的功能 | 做了会有人用但不影响决策 | **明确说不** |
| 完美主义重构 | 「代码太丑了想重写」 | **定义「足够好」的标准**，不做无 ROI 的重构 |
| 无验证的创意 | 灵光一现但没有客户验证 | **先做低成本验证**，不直接投入工程资源 |
| 过时需求 | 需求提出后超过 6 个月未排期 | **主动关闭**，真需要会重新提出 |
| 竞品对标盲从 | 「他们也做了所以我们要做」 | **问为什么**——客户需要吗？差异化能建立吗？ |

**第四象限的识别标准**：

- 「如果'不做的理由'和'要做的理由'一样多，那就是不应该做」
- 「六个月内没人再提的需求，说明它不重要」
- 「只是'还好'的改进，不是'必须'的改进」

## 3. 服务器研发独有的决策约束

### 3.1 物理世界约束

软件研发的优先级决策相对简单（投入人力即可），但服务器研发涉及物理世界，额外的约束大幅改变了决策空间：

| 约束类型 | 例子 | 对优先级的影响 |
|:---------|:-----|:--------------|
| **硬件迭代周期** | PCB 改版需要 12-16 周 | 窗口期错过就要等下一版，决策有硬截止日期 |
| **供应提前期（Lead Time）** | 关键芯片采购周期 26 周+ | 优先级受物料可获得性影响，不是想做就能做 |
| **验证周期** | 信号完整性仿真 → 打样 → 测试 → 改版循环 | 每次验证至少 4-8 周，不允许多个实验并行 |
| **产线排期** | 试产线排期以月为单位 | 试产窗口错过就要等下一批 |
| **合规认证周期** | UL/CE/CCC 认证需要 4-12 周 | 认证周期不可压缩，必须提前规划 |
| **物理 BOM 变更** | 更换一个电容需要重新做 DV（Design Validation） | 看似微小的变更触发全量验证，成本巨大 |

> **软件研发可以「先上线再修复」；服务器硬件研发没有第二次机会——优先级错误意味着 3-6 个月的物理等待周期。**

### 3.2 嵌入式/固件的「三方协调」

服务器研发中，BMC/BIOS/CPLD 等固件开发面临特有的「三方约束」：

```text
硬件设计 -> 固件开发 -> 系统验证
   ^           v           v
   +-----------+-----------+
   三方必须同时就绪，缺一不可
```

| 约束 | 说明 | 决策含义 |
|:-----|:-----|:---------|
| **硬件依赖** | 固件开发需要硬件原型或仿真环境 | 固件优先级必须和硬件可用时间对齐 |
| **验证依赖** | 功能验证需要完整的硬件+固件栈 | 不能单独「先做一部分」 |
| **同步窗口** | 三方协同的窗口有限 | 错过窗口就要等下一迭代 |
| **调试困难** | 硬件问题 vs 固件问题 vs 软件问题难以隔离 | 定位成本高，优先级判断需要快速诊断 |

### 3.3 产品组合的多层次结构

服务器产品线不是单一产品，而是多层次组合：

```text
产品族（如：AI 服务器系列）
  +-- 平台（如：某代 GPU 平台）
        +-- 项目（如：客户 A 的定制方案）
              +-- 模块/组件（如：电源背板、风扇模组）
```

**不同层次的优先级天然冲突**：

| 层次 | 关注重点 | 时间视角 | 决策者 |
|:-----|:---------|:--------|:-------|
| 产品族 | 市场覆盖、技术路线 | 3-5 年 | 产品线负责人 |
| 平台 | 架构竞争力、复用率 | 2-3 年 | 架构师 |
| 项目 | 客户交付、成本、进度 | 6-18 月 | 项目经理 |
| 模块 | 功能完整性、质量 | 3-12 月 | 模块负责人 |

**冲突示例**：

- 项目层要快速交付（选成熟方案）vs 平台层要架构统一（需要时间规划）
- 模块层要做技术优化（提升指标）vs 项目层要控制成本（用更便宜的料）
- 产品族层要布局新赛道（投入预研）vs 项目层要完成现有交付（占用人力）

> **超过 70% 的优先级冲突不是「孰优孰劣」，而是「不同层次天然视角不同」。解决方法不是争对错，而是明确当前决策属于哪个层次、以该层次的权重为主。**

### 3.4 客户视角 vs 架构视角的恒久矛盾

```text
客户视角（PM/销售/客户）         架构视角（架构师/技术负责人）
       |                                |
   +---+-----------+            +-------+-------+
   | "我现在就要"  |            | "要为未来考虑" |
   | "别人都有"    |            | "不能乱加功能" |
   | "这个功能"    |            | "需统一框架"   |
   +---------------+            +---------------+
               v                        v
         定制化、快                    通用化、稳
```

这个矛盾无法消除，只能管理。关键是**建立对话机制**而非「谁赢了听谁的」。

### 3.5 「决策窗口」特性

服务器研发中，不同事项的「决策窗口」完全不同：

| 事项类型 | 决策窗口 | 含义 |
|:---------|:--------|:-----|
| 硬件量产决策 | 决定后不可更改（mask 冻结） | 必须提前冻结 |
| PCB 布局冻结 | 冻结后改版成本极高 | 在冻结前充分考虑 |
| 固件架构决策 | 中期可改但成本高 | 需要充分评审 |
| 软件架构决策 | 持续可迭代 | 可相对灵活的排序 |
| 供应商选择 | 选择后切换成本高 | 必须充分评估 |
| 功能排期 | 持续可调 | 优先级可调整 |

**决策含义**：

- 决策窗口短的优先做（硬件冻结 > 固件架构 > 软件功能）
- 不可逆决策优先投资源
- 可逆决策可以「先不决定」而不是「先决定」

## 4. 八大典型权衡场景与决策指南

### 场景一：线上故障 vs 架构重构

#### 冲突描述

```text
工程师 A："线上 P1 故障，客户数据库在凌晨 3 点出现连接失败，
影响了 12 台节点的数据写入。需要立即修复。"

工程师 B："这个故障的根因是架构层面的连接池管理设计缺陷。
我们应该停下来，花两周时间重构连接池框架，
从根源上消除这类问题。"

冲突：修故障（止血） vs 重构（根治）
```

#### 决策框架

| 决策维度 | 问题 | 倾向 Stop-Gap | 倾向根治 |
|:---------|:-----|:-------------:|:--------:|
| **影响面** | 当前故障影响多少客户/节点？ | 影响大 → 先止血 | 影响小 → 考虑根治 |
| **复发频率** | 这个故障模式多久出现一次？ | 首次出现 → 止血 | 再次出现 → 考虑根治 |
| **修复复杂度** | 止血 vs 根治各需多久？ | 止血 < 1天 & 根治 > 2周 → 先止血 | 止血难/根治快 → 直接根治 |
| **架构变更风险** | 重构引入新问题的概率？ | 风险高 → 先止血 | 风险可控 → 考虑根治 |
| **业务窗口** | 现在是业务高峰期吗？ | 是 → 止血，记录待根治 | 低谷期 → 可安排根治 |

#### 推荐策略

```text
策略：Stop-Gap First, Root-Cause Second
-----------------------------------

原则：先止血（确保业务恢复），再记录（明确根因），
然后判断是否需要根治。

判断是否根治的标准：
  □ 同类故障在 6 个月内出现 ≥2 次？ -> 必须根治
  □ 止血方案本身引入新的技术债？ -> 记录并排期
  □ 根治方案工期 > 1 周？ -> 纳入计划而非立即执行
  □ 是否有其他更紧急事项？ -> 按优先级队列排序

标准执行流程：
  Step 1: 止血修复（hotfix）-> 恢复业务
  Step 2: 根因分析（RCA）-> 明确根本原因
  Step 3: 根治决策 -> 根据复发频率 + 影响面决定
  Step 4: 选择路径：
    +- 立即根治（复发高 + 影响大 + 根治快）
    +- 纳入迭代（复发低 / 根治耗时）
    +- 记录留档（复发极低 + 影响有限）

注意：最坏的做法是「止血后忘记根治」——
  如果止血后不排期根治，下次复发成本不变。
```

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 首次发生的 P0/P1 故障 | 止血 + RCA | 先恢复再分析根因 |
| 同类型故障 3 个月内复发 | 根治优先 | 止血方案已被证明无效 |
| 止血方案引入技术债 > 5 天 | 折中：止血同时并行设计根治方案 | 避免双重成本 |
| 客户正在使用受影响版本 | 双线并行：止血给客户 + 根治团队并行 | 不能等待 |
| 故障发生在架构冻结期前 | 立即根治 | 错过窗口要等 3-6 月 |

### 场景二：客户定制 vs 平台化建设

#### 冲突描述

```text
销售："客户 A 要 200 台服务器，但需要特殊的电源背板
布局——因为他们的数据中心机架深度和我们标准的不一样。
这个定制价值 800 万。"

架构师："如果我们接了这个定制，电源背板就不再是通用设计。
后续所有平台都要维护两套背板——成本增加 15%。
我建议拒绝定制，说服客户接受标准方案。"

冲突：单客户价值 vs 平台长期竞争力
```

#### 决策框架

核心问题：**「这个定制是一次性的，还是可复用的？」**

```text
          定制可复用吗？
         ┆
    可   ┆  一次性
         ┆
   +-----+------+
   |            |
   v            v
  吸收为平台能力  评估定制成本
  (战略投资)     (商业决策)
                 |
           +-----+-----+
           |           |
       定制费覆盖成本  定制费不覆盖成本
           |           |
           v           v
         可接       建议拒绝或提价
```

#### 量化决策模板

| 评估项 | 问题 | 加权分数（1-5） |
|:-------|:-----|:--------------:|
| 定制复用潜力 | 这个定制能用于其他客户/场景吗？ | |
| 定制成本占比 | 定制成本 / 单台利润 | |
| 平台影响度 | 定制对平台通用性的破坏程度 | |
| 战略客户价值 | 这个客户的战略重要性 | |
| 竞品竞争压力 | 不接定制是否会丢失客户给竞品 | |

**决策规则**：

- **总分 > 20**（满分 25）：接受定制并吸收为平台能力
- **总分 12-20**：有条件接受（定制成本由客户部分或全部承担）
- **总分 < 12**：拒绝定制，提供标准化替代方案

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 电源/风扇/结构件等**物理外形**定制 | 平台兼容评估 → 如果影响不超过 2 个模块，可接 | 物理定制影响范围有限化 |
| **固件/管理软件**定制 | 优先通过配置实现而非改代码 | 配置化避免分支维护 |
| **接口/协议**定制 | 极谨慎——接口绑定后解耦成本极高 | 一旦支持就很难放弃 |
| 客户要求**专用测试**流程 | 可以接——成熟方案封装为服务 | 测试流程定制对平台影响最小 |
| 多个客户提出**相同**定制 | 直接吸收为平台标准功能 | 市场验证过的需求 |
| 定制需求在客户合同中**模糊** | 明确约定定制范围和费用 | 避免scope creep |

#### 分支管理策略

一旦决定接定制，必须管理分支：

```text
策略：Feature Flag > 配置化 > 插件化 > 分支

选择层级：
  1. Feature Flag（特性开关）-> 运行时控制
     ✅ 影响最小，最易维护
     ✅ 同一代码库，不影响 CI/CD
     ❌ 需要设计阶段就考虑

  2. 配置化（配置文件/数据库参数）
     ✅ 相对灵活，可动态调整
     ✅ 不需要改代码
     ❌ 配置组合爆炸时要小心

  3. 插件化（策略模式/SPI 扩展点）
     ✅ 解耦良好，可热插拔
     ✅ 允许第三方扩展
     ❌ 初期设计成本高

  4. 分支（git branch / fork）
     ❌ 最后选择——分支成本随时间指数增长
     ✅ 只有客户需求与平台完全不兼容时才用
```

> **记住：一个定制分支需要 0.5-1 人/年持续维护。如果定制收益低于维护成本，接定制是亏本买卖。**

### 场景三：技术债清理 vs 新功能开发

#### 冲突描述

```text
工程师 A："这个模块的代码已经烂到不能看了。
没有单元测试，耦合严重，每次加功能都要花 3 天
来理解代码逻辑。我们需要停下来清理。"

产品经理："客户在等这个新功能——已经答应了 Q2 交付。
如果新功能延期，客户满意度会下降。"

冲突：还债（质量） vs 借钱（功能）
```

#### 核心框架：「技术债 = 带息负债」

```text
类比金融负债：

技术债 = 以「未来开发效率下降」为利息的负债
         +------利息率-------+
         | 每次修改此模块的成本增加 20-50% |
         +------------------------------+

不是要不要还的问题——债每天都在生利息。
问题在于：**还债的时间点和方式**。
```

#### 技术债四象限分类

```text
                      债的利息率
                    ┆
               高   ┆  I（优先还）        II（计划还）
                    ┆  高频修改的烂代码     低频但关键的脆弱代码
                    ┆  阻塞新功能的技术债    影响稳定性的技术债
                    ┆  安全/合规债         架构层面的债务
                    ┆
                ----+--------------------------
                    ┆
               低   ┆  III（绑定还）       IV（容忍）
                    ┆  低频代码的轻微问题    废弃代码
                    ┆  需要时再清理         不影响功能的设计瑕疵
                    ┆                     「知道不好但暂时不管」
                    ┆
                    +---------------------------
                      低                    高
                           模块修改频率
```

#### 决策规则

| 技术债类型 | 建议 | 方式 |
|:-----------|:-----|:-----|
| **I 类**（高频修改 + 高利息） | **立即还** | 在本次修改前先重构，或者「重构+改功能」一起做—总共时间 ≤ 直接改的 2 倍就值得 |
| **II 类**（低频修改 + 高利息） | **设定还债计划** | 纳入下个迭代或技术债 Sprint |
| **III 类**（高频修改 + 低利息） | **随借随还** | 每次修改时「稍加清理」，不单独安排还债时间 |
| **IV 类**（低频修改 + 低利息） | **不动** | 直到需要修改此模块为止 |

#### 「童子军规则：每次离开时让营地比来时更干净」

```text
策略：不单独安排「还债 Sprint」，而是将还债融入日常开发

具体做法：
  每次修改一个模块时，花 10-20% 的时间清理附近的问题源。

  例如：要修改函数 A -> 顺便把函数 A 附近的变量命名规范化
        -> 顺便给函数 A 加个简单的单元测试
        -> 顺便删除一段不再使用的废弃代码

  效果：
  - 技术债不会累积——每次修改都「带走一些」
  - 没有单独的重构 Sprint（不会被视为「低产出」）
  - 长期来看，模块质量稳定提升

  限制：
  - 只适用于高频修改的模块（I 类和 III 类）
  - II 类技术债仍然需要单独安排
  - 需要团队有「稍加清理」的判断力（不加过度修改导致 scope creep）
```

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 一个模块每次修改都要 3-5 天理解逻辑 | 必须重构——且放在新功能前 | 重构后的效率提升会覆盖投入 |
| 遗留代码无测试但功能稳定 | 不主动重构——只在修改相关代码时加测试 | 没出问题就不动 |
| 依赖了一个已被废弃的第三方库 | 列为 II 类债，排期迁移 | 安全漏洞风险 |
| 新功能需要在有巨额债的模块上做 | 先还债再做功能——「先垫脚石再踩过去」 | 否则新功能会引入更多债 |
| 团队中新人有「想重写一切」的冲动 | 引导其理解分类框架 | 不是所有烂代码都需要重写 |

### 场景四：安全加固 vs 业务交付

#### 冲突描述

```text
安全团队："扫描发现 3 个高危漏洞：2 个在 BMC Web 界面，
1 个在固件更新流程中。建议立即修复并在修复完成前暂停发布。"

业务团队："这批货已经打包等待发货了——客户合同里写了交付日期。
暂停发布意味着每天 10 万的违约金。"

冲突：安全底线 vs 商业承诺
```

#### 决策框架

##### 漏洞分级与处理策略

```text
        漏洞可利用性
        ┆
    高  ┆  I（立即止损）        II（评估后行动）
        ┆  远程可利用           需要本地访问
        ┆  无需认证             需要特定权限
        ┆  影响所有产品          只影响特定配置
        ┆  PoC 已公开           仅有理论风险
        ┆
    低  ┆  III（计划修复）       IV（常规修复）
        ┆  需要物理接触          影响特定边缘场景
        ┆  需要复杂条件          需要多层绕过
        ┆                      存在补偿措施
        ┆
        +------------------------------
            高                   低
                漏洞影响面
```

#### 通用处理规则

| 场景 | 建议 | 具体操作 |
|:-----|:-----|:---------|
| **I 类**（远程可利用 + 影响面广） | **立即修复，暂停交付** | hotfix 补丁 → 验证 → 恢复交付 |
| **II 类**（远程可利用 + 影响面小） | **评估后修复** | 评估影响范围，如果≤5% 客户受影响的配置可正常交付+补丁更新 |
| **III 类**（需本地访问 + 影响面广） | **排期修复** | 纳入下个版本或补丁周期 |
| **IV 类**（需本地访问 + 影响面小） | **常规流程修复** | 纳入正常迭代 |
| **PoC 已在公开渠道传播** | **升一级处理** | PoC 公开将大幅降低利用门槛 |
| **监管/合规明确要求** | **按合规要求的时间表执行** | 合规有法律后果 |

#### 安全 vs 交付的「并行策略」

当必须同时考虑安全和交付时，不要选边站，走并行：

```text
策略：安全加固不阻塞交付，交付不跳过安全

Step 1: 快速评估漏洞的真实风险
  - 有 PoC 吗？ -> 高优先
  - 需要什么条件利用？ -> 判断难度
  - 补偿性控制措施可用吗？ -> 网络隔离/访问控制

Step 2: 如果在交付窗口内无法完成修复
  可选方案：
  +- 发布补偿性安全公告（说明受影响版本+临时缓解措施）
  +- 修复交付版 + 发布补丁给已发货版本
  +- 仅修复新版本，老版本发安全公告

Step 3: 确定修复时间线
  - I 类：7 天内修复
  - II 类：30 天内修复
  - III 类：下个版本修复
  - IV 类：迭代内修复
```

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| BMC Web 界面 RCE 漏洞（需要认证） | II 类 → 排期修复，不阻塞交付 | 需要认证降低了可利用性 |
| 固件更新签名绕过（无需认证） | I 类 → 立即修复 | 可被大规模利用 |
| 信息泄露（SSH 版本指纹） | IV 类 → 常规修复 | 可利用性低 |
| 默认密码未修改 | I 类 → 强制修改流程 | 最常见的攻击入口 |
| 证书已过期 | 取决于影响——如果服务不可用则是 P0 | 既安全又可用性问题 |
| 供应链组件漏洞（Log4j 类） | 评估实际可达性——组件被使用但不一定可被利用 | 防止过度反应 |

### 场景五：性能优化 vs 功能完善

#### 冲突描述

```text
性能工程师："当前 P99 延迟是 5ms，竞争对手是 2ms。
我需要 4 周时间优化数据路径，可以降到 2ms。"

产品经理："客户在等多租户支持——这个功能已经列入 3 个合同。
性能优化虽然好，但新的多租户功能才能签下新客户。"

冲突：更好（性能指标） vs 更多（功能覆盖）
```

#### 决策框架

```text
        性能差距
        ┆
    大  ┆  I（必须优化）         II（策略性优化）
        ┆  指标落后竞品 >50%     指标落后但不影响客户决策
        ┆  直接影响客户体验      可被其他优势弥补
        ┆  客户明确投诉延迟      无客户投诉
        ┆  是产品核心卖点        不是选型关键因素
        ┆
    小  ┆  III（条件优化）       IV（暂不优化）
        ┆  领先竞品但可更好      已经是行业领先
        ┆  优化成本低（顺手）    优化成本高
        ┆  不影响架构变动        需要大规模架构调整
        ┆
        +------------------------------
            高                   低
                功能缺失
```

#### 决策规则

| 条件 | 建议 |
|:-----|:-----|
| 性能是**行业基准对比**中的必选项（如 SPEC/P99） | 性能优化列为 P1，与功能并行 |
| 性能是**选型加分项**但非决定因素 | 设性能目标，但不以牺牲功能为代价 |
| 性能优化涉及**架构变动** | 纳入架构路线图而非功能迭代 |
| 性能优化成本 < 功能开发的 20% | 顺手优化，不设专项 |
| 客户直接反馈「慢」 | 升为 P0，用户感知即事实 |

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 竞品 P99 2ms，我们是 5ms（有客户询价） | 优化 + 客户沟通并行 | 需要优化同时也需要安抚客户 |
| 竞品 P99 2ms，我们是 3ms（无客户投诉） | 设目标但不设项目 | 设定优化目标在常规迭代中完成 |
| 功能缺失导致丢单 | 优先功能 | 有功能才能进入选型 |
| 性能优化靠改一个参数即可实现 | 顺手优化 | 零成本收益 |
| 性能优化需要换芯片 | 按架构路线图走 | 芯片级替换不是性能优化项目的范畴 |

### 场景六：工具链建设 vs 直接交付

#### 冲突描述

```text
质量工程师："我们需要搭建自动化测试平台——每次手动测试
要花 3 天，而且覆盖不全。给我 3 周可以把测试环境建好。"

项目经理："客户在这里等着验收——你现在去建测试平台，
谁来测这批货？而且测试平台建好了下一批才能用。"

冲突：投资未来效率 vs 满足当前需求
```

#### 决策框架

```text
        工具复用潜力
        ┆
    高  ┆  I（战略性投资）      II（渐进式建设）
        ┆  适用所有项目         适用于多个项目
        ┆  影响研发全流程       但定制化需求不同
        ┆  预期 ROI > 3 倍      ROI 可衡量但不确定
        ┆
    低  ┆  III（一次即可）       IV（别做）
        ┆  本次用完即弃         单次、手工就够
        ┆  手工成本 > 工具成本  手工成本 < 工具建设成本
        ┆
        +------------------------------
            高                   低
                当前交付压力
```

#### 决策规则

| 条件 | 建议 |
|:-----|:-----|
| 工具可用次数 ≥ 3 次 | 值得建 |
| 工具建一次节省的时间 > 建工具时间 × 2 | 值得建 |
| 工具建设工期 > 当前交付窗口 | 先手工跑通，**过程中记录需求**，交付后立即建 |
| 工具可以「周末搭一个」 | 应该做——边际成本极低 |

#### 「造船 vs 过河」原则

```text
核心洞察：
  不要为了省一次过河的时间去造一艘船。
  但如果这条河你每天都要过——船比游泳值。

量化判断：
  设：
    T_over = 每次过河时间（手工做一次）
    T_build = 造船时间（工具建设时间）
    N = 预计过河次数（工具使用次数）

  造船条件：T_build < T_over × (N - 1)
  即：造船投入要在 N 次使用中回本

  举例：
    手工测试一次 = 3 天
    建自动化测试平台 = 15 天
    本产品线后续测试次数 = 8 次（不同版本/配置）

    15 < 3 × (8 - 1) = 21 -> 值得建
```

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 测试平台可用于所有项目 | 战略性投资 | 长期回报显著 |
| 只为一个客户的一次需求建工具 | 不做——用手工 | 一次性的工具成本无法回收 |
| 手动部署耗时 2 天，频率每月 2 次 | 花 3-5 天建 CI/CD | 半年回本 |
| 手动处理耗时 5 分钟，频率每天 1 次 | 脚本化但不单独建平台 | 时间短建议直接写脚本 |
| 团队有强烈的「工具依赖倾向」 | 引导其先手工理解需求再建工具 | 避免过早抽象 |

### 场景七：标准合规 vs 快速迭代

#### 冲突描述

```text
合规负责人："新的 OCSP 规范要求支持带内固件更新接口。
我们需要 3 个月做适配并通过认证。合规不通过不能出货。"

研发总监："我们有 3 个客户项目在排队——每个都要固件更新功能。
等待认证意味着所有项目延期 3 个月。"

冲突：合规（市场入场券） vs 速度（市场份额）
```

#### 决策框架

```text
        合规是市场准入门槛吗？
        ┆
    是  ┆  必须做（非可选项）       战略选择
        ┆  +----------------+   +------------------+
        ┆  | Type: 强制合规  |   | Type: 差异化合规  |
        ┆  | 不做无法出货    |   | 做了有竞争优势    |
        ┆  | 优先级：P0      |   | 优先级：P1-P2     |
        ┆  | 策略：立即启动   |   | 策略：评估 ROI   |
        ┆  +----------------+   +------------------+
        ┆
    否  ┆  可协商的合规
        ┆  +------------------+
        ┆  | Type: 可选合规    |
        ┆  | 不做不影响出货    |
        ┆  | 优先级：P3        |
        ┆  | 策略：按客户需求  |
        ┆  +------------------+
        ┆
        +------------------------------
```

#### 合规管理的两个重要原则

**原则 1：「合规是最小化验收标准，不是差异化竞争力」**

```text
控制思路：

满足合规 -> 通过认证 -> 可以出货
   ^
  只投入「刚好通过」的资源
  不追求「在合规点上做到极致」

这条线上的超额投入是浪费——客户不为此付溢价。
```

**原则 2：「合规工作可以并行走」**

```text
并行路径：

路径 A（合规团队）：认证、测试、文档
路径 B（开发团队）：核心功能开发
路径 C（项目管理）：与认证机构协调、预测试

三条路径可以同时推进，不需要串行等待。

最佳实践：
  1. 合规工作尽早启动（哪怕是预研）
  2. 与认证机构保持沟通（提前了解审核重点）
  3. 并行交付窗口和合规窗口
  4. 将合规要求分解到产品设计阶段
```

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 新市场准入需要 CE/UL 认证 | 列为 P0，但可并行开发 | 没认证不能卖 |
| OCSP/Redfish 新版本合规 | 启动兼容计划但不阻塞现有交付 | 可向后兼容过渡 |
| 客户要求特定合规项（非法律强制） | 评估合同条款 — 若为硬性条款则做 | 合同约束等价于强制 |
| 合规影响架构设计 | 尽早评估——后期改造成本极高 | 架构级的合规嵌入 |
| 合规延期但产品已定型 | 评估是否可分批认证 | 核心模块先认证 |

### 场景八：短期优化 vs 长期架构演进

#### 冲突描述

```text
架构师："我们需要从当前的单 BMC 架构演进到
双 BMC 冗余架构——这是未来 3 年的架构方向。
投入 2 人年完成架构升级。"

项目经理："目前的单 BMC 架构运行没有问题。
客户也没有双 BMC 的需求——这正是节省成本的时候。"

冲突：现状够用 vs 未来布局
```

#### 决策框架

```text
        架构痛在加剧吗？
        ┆
    是  ┆  I（必须演进）         II（规划演进）
        ┆  当前架构已达瓶颈      当前架构还有余量
        ┆  未来 2 年需求会超过   但 3 年内会遇到瓶颈
        ┆  当前能力的 2 倍       演进需要时间
        ┆  不演进会影响业务      |
        ┆                        v
        +------------------  监测拐点指标
        ┆
    否  ┆  III（微调即可）       IV（不要动）
        ┆  当前架构有余量        当前架构足够
        ┆  但有一些可改进点      3-5 年内无需变动
        ┆  低成本优化可做        |
        ┆                        v
        ┆                    别动它——真的
        +------------------------------
            高                   低
                未来业务确定性
```

#### 架构演进的「拐点决策法」

```text
不是什么时候想做架构升级，而是什么时候必须做。

关键拐点指标（需要提前定义）：

  容量拐点：当前架构的极限容量 / 预期负载增长速率
    -> 当 极限容量 / 当前负载 < 3 时 -> 启动架构规划
    -> 当 极限容量 / 当前负载 < 1.5 时 -> 必须启动实施

  复杂度拐点：当前架构添加一个类似功能的成本变化
    -> 当每个新增功能成本增加 20%+ 时 -> 架构需要演进

  维护拐点：当前架构的故障恢复时间趋势
    -> 当 MTTR（平均恢复时间）逐年上升 20%+ 时 -> 架构需要演进

  生态拐点：关键技术组件是否被上游弃用
    -> 当关键依赖即将 EOL（End of Life）时 -> 架构必须演进
```

#### 典型场景速查

| 具体场景 | 建议 | 理由 |
|:---------|:-----|:------|
| 当前架构已接近容量极限 | 立即启动演进 | 业务增长不可逆 |
| 当前架构还有 3 倍余量 | 规划但不启动 | 有余量做更紧急的事 |
| 架构演进需要前置芯片/平台支持 | 取决于上游 Roadmap | 被动等待也是策略 |
| 「别人都做架构升级了」 | 回到拐点指标判断 | 不盲从 |
| 架构师有强烈的升级冲动 | 用拐点指标检验 | 热情不等于必要性 |
| 架构升级可带来 30%+ 成本降低 | 核算 ROI，如果 2 年内回本 | 效率提升也是收益 |

## 5. 策略与方法论

### 5.1 全局策略：三层过滤器

将所有「可做的事」通过三层过滤器来决定是否要进入开发管道：

```text
       所有可做的事（无限制）
              |
              v
   +---------------------+
   | 第一层：必要性过滤   | <- 不做会怎样？
   |                     |
   | “不做会死吗？”      |
   | “不做会损失 100 万？”|
   | “不做客户会走？”    |
   +--------+------------+
            |
        +---+---+
        |       |
        v       v
    必须做    可做可不做
                |
                v
   +---------------------+
   | 第二层：价值过滤     | <- 做了有什么好处？
   |                     |
   | ROI > 3?            |
   | 长期收益 > 投入？    |
   | 战略匹配？          |
   +--------+------------+
            |
        +---+---+
        |       |
        v       v
     值得做   不值得做->🗑️ 放弃
                |
                v
   +---------------------+
   | 第三层：时机过滤     | <- 什么时候做？
   |                     |
   | 现在做 vs 下季做？   |
   | 依赖条件满足了吗？   |
   | 有产能吗？          |
   +--------+------------+
            |
        +---+---+
        |       |
        v       v
     现在做   未来做->📋 放入待办池
```

### 5.2 两种核心取舍模式

#### 模式一：MECE 取舍 —— 互斥且穷尽的优先级队列

```text
做法：
  - 将所有候选事项按统一量化标准打分
  - 按分数排序形成唯一队列
  - 按产能从队列顶部取

适合：
  - 同类事项之间比较（如：都是新功能）
  - 资源分配需要透明度的场景
  - 团队对「谁更重要」有争议时

局限：
  - 不同类型的事项难以统一量化
  - 量化标准本身可能被操纵
  - 紧急情况和计划外工作难以纳入
```

#### 模式二：产能池分配 —— 为不同类型预留固定产能

```text
做法：
  - 将产能分为几个池子（故障处理 / 新功能 / 技术债 / 架构）
  - 每个池子有固定比例（如 30% / 40% / 20% / 10%）
  - 各池子内部按优先级排序
  - 紧急时可临时借用其他池

适合：
  - 工作类型多样且都有合理性的场景
  - 需要保证「重要不紧急」不被侵蚀
  - 团队需要稳定的可预测性

常见分配比例（参考）：
  +------------------------------------------------+
  |  故障处理     |  新功能    |  技术债  |  架构   |
  |  20-30%      |  40-50%   |  10-20%  |  10%    |
  +------------------------------------------------+

  注意：比例应根据产品生命周期调整
    - 早期产品：新功能 60%+，技术债 <10%
    - 成熟产品：新功能 30-40%，技术债 20%，架构 15%
    - 衰退产品：故障处理 30%，技术债 30%（准备交接）
```

### 5.3 「不做」的勇气机制

#### 机制 1：季度清零

```text
每季度末，强制性地清理待办池中超过 6 个月未被排期的需求。

做法：
  Step 1: 列出所有超过 6 个月的 open 需求
  Step 2: 逐条问「这 6 个月没人提它，真需要做吗？」
  Step 3: 决定：关闭 / 重新排期 / 标记「幽灵需求」
  Step 4: 被关闭的需求如果需要重新激活，需经过正式的
          评审流程（而非被某人一句话复活）

效果：
  - 大幅减少待办列表的「噪音」
  - 迫使团队承认「有些事就是不做也没关系」
  - 释放心理负担（「还有 200 件事没做」的焦虑）
```

#### 机制 2：加权排序砍尾

```text
做法：
  1. 所有候选事项按统一标准打分（收益 - 成本 - 风险）
  2. 按得分排序
  3. 只保留前 N 个（N = 产能可覆盖的数量）
  4. 明确砍掉后 20% 的事项
  5. 被砍的事项进入「冷冻库」
  6. 从冷冻库解冻需要经过更高一级审批

核心原则：
  「如果一个事项不值得做，把它放进待办池也不值得」

  待办池中躺着的垃圾需求会持续消耗「认知带宽」——
  每次看到它都要想一下「这个要不要做」。
  直接关闭比放着好。
```

#### 机制 3：「否定审批」——不做比做更难

```text
当决定「不做」时，需要：
  Step 1: 书面说明「不做此事的理由」
  Step 2: 预测「不做的后果」
  Step 3: 指定一个未来检查点（「如果 X 条件满足则重新评估」）
  Step 4: 发送给相关利益方确认

这比简单地「不做」要花更多时间——这恰恰是设计用意：
  你只应该对真正重要的「不做」决定花时间。
  对那些「只是觉得有点可惜」的事项——直接扔掉，不需要审批。
```

### 5.4 第二象限保护策略

> **所有团队最终都毁于「被第一象限吞噬」——除非有意识地保护第二象限。**

| 策略 | 具体做法 | 适用阶段 |
|:-----|:---------|:--------|
| **固定时间窗口** | 每周四下午 = 架构/技术债时间，不受打断 | 任何阶段 |
| **20% 规则** | 每个迭代保留 20% 产能给计划外工作和还债 | 成熟团队 |
| **专项 Sprint** | 每 4 个迭代中安排 1 个「还债/架构」Sprint | 技术债严重时 |
| **保护时间标记** | 日历上标记「不可打扰」，紧急事务需 VP 级批准才能打断 | 攻坚期 |
| **异步第二象限** | 第二象限工作以异步方式推进（文档、设计、评审），不占用同步会议时间 | 远程/混合团队 |

### 5.5 量化辅助决策工具

#### ROI 快速估算

```text
ROI = (预期收益 × 成功率) / (投入成本 × 风险系数)

其中：
  预期收益 = 客户价值 + 内部效率提升 + 风险降低
  成功率 = 技术可行性 × 市场接受度
  投入成本 = 研发投入 + 维护投入 + 机会成本
  风险系数 = 技术风险 + 时间风险 + 依赖风险

应用：
  - ROI > 5: 高优先级
  - ROI 2-5: 中等优先级，需进一步评估
  - ROI < 2: 低优先级，除非有战略意义
```

#### 加权优先级评分

```text
评分维度与权重（示例——可根据实际情况调整）：

  +------------------------+------+
  | 维度                   | 权重 |
  +------------------------+------+
  | 客户/业务影响力        | 30%  |
  | 战略匹配度             | 25%  |
  | 技术可行性/风险        | 15%  |
  | 紧急程度（时间窗口）    | 15%  |
  | 资源消耗（人月）        | 10%  |
  | 团队能力匹配度          | 5%   |
  +------------------------+------+

每项维度打分 1-5 分，加权求和得总分。

使用注意：
  - 评分不是做精确数学，而是建立**统一的讨论框架**
  - 评分过程比结果重要——强迫团队讨论关键维度
  - 定期复盘评分标准是否合理
```

## 6. 决策检查清单

### 6.1 初次评估清单（收到任何「可做的事」时）

```text
□ 这个事项有明确的需求方（客户/内部/合规）？
□ 不做会产生什么具体后果？
   -> 若无明确后果 -> 强烈建议放弃
□ 做了能带来什么具体收益？
   -> 收益可量化吗？（收入/效率/风险降低）
□ 这个事项的重要性是如何被发现的？
   -> 客户投诉？竞品发布？内部发现？灵光一现？
   -> 信息来源的可靠性如何？
□ 现在做比一个季度后做的额外收益是什么？
   -> 如果「现在做 vs 3 个月后做」收益差异 < 20% -> 放进待办池
□ 我们是否愿意砍掉另一个事项来为这个腾出产能？
   -> 如果回答「不」-> 说明它没那么重要
□ 如果只能做 20% 的工作来达到 80% 效果，那 20% 是什么？
   -> 如果这个 20% 都不可行 -> 可能需要的不是这个功能
```

### 6.2 互斥场景速查

| 非此即彼 | 决策原则 |
|:---------|:---------|
| 新功能 A vs 新功能 B | 看 ROI 和战略对齐度 |
| 性能优化 vs 新功能 | 看性能是否是选型门槛+客户是否抱怨 |
| 技术债还贷 vs 新功能 | 看债的利息率（修改频率 × 添加功能的难度）|
| 安全修复 vs 业务交付 | 看漏洞级别 + PoC 公开状态 |
| 工具建设 vs 直接交付 | 看工具复用次数 |
| 长期架构 vs 短期优化 | 看拐点指标是否触发 |
| 客户定制 vs 平台化 | 看客户战略价值 × 定制复用潜力 |
| 标准合规 vs 快速迭代 | 看合规是否是市场准入门槛 |

### 6.3 每周回顾清单

```text
□ 本周有多少时间花在了第一象限？（紧急重要）
   -> 如果 > 60% -> 团队在救火，需要加固系统
□ 本周有多少时间花在了第二象限？（重要不紧急）
   -> 如果 < 10% -> 团队在透支未来
□ 本周有哪些「紧急」但回头看不那么重要的事？
   -> 下次如何避免？
□ 本周拒绝了哪些可以做但选择不做的事？
   -> 拒绝的理由是什么？是否应该更果断？
□ 待办池清单本周关闭了多少项？（而非新增了多少）
   -> 如果只增不减 -> 说明「不做」机制失效
□ 本周有没有把第三象限的事交给适当的人（而非核心成员）？
   -> 如果不是 -> 发生了资源错配
□ 这周保护了第二象限的时间吗？
   -> 如果没有 -> 下周需要什么保护机制？
```

## 7. 团队协调与沟通

### 7.1 「不能全做」的告知策略

当管理者/客户/利益相关方要求做多个事项时，使用**替代选择法**而非直接拒绝：

```text
替代选择法模板：

❌ 错误回应：「这个做不了，资源不够。」

✅ 正确回应：
  「我们理解这三件事都很重要。
   目前团队产能可以全力做好两件，第三件只能做到 50%
   或推后到下个周期。
   您看哪两件优先级最高？第三件我们能接受什么程度的结果？」
```

### 7.2 跨团队协商框架

当两个团队/部门对优先级有冲突时：

```text
Step 1: 确认目标一致（双方都希望产品成功）
Step 2: 暴露假设（「你认为客户需要这个——依据是什么？」）
Step 3: 量化影响（「如果 A 做 3 个月，B 不做，影响是什么？」
Step 4: 寻找第三条路（「有没有办法两个都做，只是范围缩小？」）
Step 5: 争议升级（如果确实无法达成一致 -> 上级决策）

关键：在 Step 1-4 中解决 80% 的冲突，只有 20% 需要升级。
```

### 7.3 当管理者要求「全部都要做」时

这是最常见的困境。核心策略是**让管理者看到上限而不是抱怨**：

```text
策略：可视化产能约束

做法：
  +---------------------------------------------+
  |  当前迭代产能：100 人天                      |
  |                                              |
  |  已承诺：                                     |
  |  +- 客户 A 交付         40 人天 (40%)       |
  |  +- 安全修复             20 人天 (20%)       |
  |  +- 线上运维             10 人天 (10%)       |
  |  剩余：                  30 人天 (30%)       |
  |                                              |
  |  您要求的 3 个新功能：                        |
  |  +- 功能 X              30 人天              |
  |  +- 功能 Y              25 人天              |
  |  +- 功能 Z              20 人天              |
  |  合计：                  75 人天              |
  |                                              |
  |  产能缺口：              45 人天              |
  |                                              |
  |  可选方案：                                   |
  |  A. 延期现有承诺之一                          |
  |  B. 削减新功能范围（只做核心 50%）             |
  |  C. 招聘/借调资源                             |
  |  D. 分批交付（功能 X 本周期，Y/Z 下周期）      |
  +---------------------------------------------+

关键点：
  - 不要抱怨「做不完」——展示限制和选项
  - 让管理者在可选方案中做选择，而不是拒绝
  - 如果管理者选「都要做且不延期」-> 帮其理解质量/范围/时间三角
```

### 7.4 优先级决策的透明度与沟通

| 受众 | 沟通内容 | 沟通方式 |
|:-----|:---------|:---------|
| 团队 | 优先级排序结果 + 排序逻辑 | 迭代计划会 |
| 产品经理 | 功能优先级 + 待办池状态 | 周同步会 |
| 管理层 | 战略级优先级 + 资源分配 | 月度业务评审 |
| 客户 | 交付承诺（而非承诺范围） | 商务沟通 |

### 7.5 「不做清单」的发布

定期（每季度）发布团队的「不做清单」——明确宣告哪些事当前不做：

```text
XX 团队 2026 Q3 不做清单

战略性不做（本季度不投入资源）：
  □ 多数据中心部署支持（客户需求不足，预计 2027 Q1 启动）
  □ BMC Web 界面 UI 重构（不影响功能，技术债容忍）
  □ 国内合规认证（当前无国内市场需求）

条件性不做（除非触发条件否则不做）：
  □ 双 BMC 冗余架构（触发条件：单 BMC 故障 P0 事件 > 2 次/季）
  □ 第三代硬件平台（触发条件：当前平台销量 > 10K/季）

价值：
  - 让团队知道「什么不用操心」——减少心理负担
  - 让管理者知道「这些我们看到了但选择了不做」——减少事后指责
  - 让利益相关方有明确预期——「这个我们本季度不做，但下季度会评估」
```

## 8. 总结

### 8.1 核心理念

> **优先级决策的核心能力不是选出「什么最重要」——而是敢于识别「什么不需要做」和「什么可以以后再做」。**

| 错误观念 | 正确观念 |
|:---------|:---------|
| 「多做总比少做好」 | 「多做不重要的事 = 少做重要的事」 |
| 「先接需求再看资源」 | 「先看资源再接需求」 |
| 「不做会错过机会」 | 「做了不重要的事才会错过真正的机会」 |
| 「紧急就是重要」 | 「紧急和重要是正交维度」 |
| 「优先级靠争论决定」 | 「优先级靠标准和框架决定」 |
| 「待办池是安全感」 | 「待办池中 80% 是噪音」 |

### 8.2 核心框架速查

```text
面对任何「可做的事」：

三层过滤器：
  1. 必要性过滤：「不做会怎样？」-> 无明确后果 -> 放弃
  2. 价值过滤  ：ROI > 3? 战略匹配？-> 不匹配 -> 放弃/冷冻
  3. 时机过滤  ：现在做 vs 以后做？-> 以后做的成本更低 -> 推迟

四象限定位：
  紧急重要 -> 立即做
  重要不紧急 -> 保护时间做
  紧急不重要 -> 分流/自动化
  不紧急不重要 -> 放弃/冷冻

八大场景对照：
  见 §4 —— 找到你的场景，应用对应策略
```

### 8.3 一个简单的每日练习

```text
每天花 5 分钟问自己三个问题：

1. 今天做的哪件事其实可以不做？
   -> 识别「惯性做但没必要」的事项

2. 今天有没有保护第二象限的时间？
   -> 重要不紧急的事今天有进展吗？

3. 今天有没有明确地说「不」？
   -> 有没有一个「可以做但选择不做」的决策？

连续做 30 天，优先级决策能力大幅提升。
```

### 8.4 一句话口诀

> **能做不等于应做，应做不等于现在做；不做清单比待办池更有价值。**
