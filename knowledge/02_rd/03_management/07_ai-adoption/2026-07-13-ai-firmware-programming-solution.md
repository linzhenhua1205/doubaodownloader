## 1. 业务目标

### 1.1 核心目标

> **把 AI 编程深度融入 BMC/BIOS 固件开发生命周期，在信息安全约束下最大化研发效率提升。**

### 1.2 目标分解

| 维度 | 目标 | 优先级 |
|:-----|:-----|:------:|
| 🎯 **效率提升** | 固件开发端到端效率提升 ≥ 30%（从需求到合入） | P0 |
| 🔒 **安全合规** | 在信息安全约束下实现 AI 辅助，杜绝代码泄露风险 | P0 |
| 📈 **能力升级** | 从 L1 代码片段 → L3 特性级开发的全面覆盖 | P1 |
| 🔗 **流程打通** | 实现"需求→方案→编码→验证→合入"全链路 AI 介入 | P1 |
| 🧠 **知识沉淀** | 将工程知识、业务逻辑、设计模式沉淀为可复用的 AI 上下文 | P2 |

### 2.1 量化效益测算

#### 基线数据（调研估算）

| 指标 | 当前值 | 来源 |
|:-----|:------|:------|
| 固件开发人员数 | ~50-100 人 | 团队规模（典型 BMC/BIOS 团队） |
| 单特性开发周期 | 5-10 天（需求到合入） | 经验值 |
| 编码占比 | ~40% | 其余为设计/沟通/验证/等待 |
| 沟通消耗 | 30-40% 的工作时间 | 需求澄清+方案评审+问题回溯 |
| 编译等待 | 2-6 次/天 × 10-30 分钟/次 | BMC 工程规模 |
| 下板验证 | 1-3 天/轮次（含找板+准备环境） | 硬件依赖 |

#### 预期改善

| 改善项 | 当前基线 | 预期目标 | 节省量 | 测算依据 |
|:-------|:---------|:---------|:-----:|:---------|
| **编码效率** | 100% | **+40%** | 每特性节省 1-2 天 | AI 代码生成 + 自动补全 + 上下文理解 |
| **沟通成本** | 30-40% | **降至 15%** | 每特性节省 0.5-1 天 | AI 作为上下文桥梁，减少需求传递偏差 |
| **编译效率** | 2-6 次/天 | **编译首轮正确率 ↑50%** | 减少 1-2 次无效编译 | AI 预检 + 编译错误修复辅助 |
| **调试/验证** | 1-3 天/轮 | **减少 30% 验证轮次** | 每特性节省 0.5-1 天 | AI 辅助单元测试 + 边界条件分析 |
| **文档产出** | 普遍缺失 | **方案/测试用例自动化** | 每特性节省 0.5 天 | AI 自动生成 + 代码同步更新 |

#### 年度总效益测算（保守估计）

```text
基础假设:
  - 团队: 50 人
  - 人均月处理特性: 2 个（含大小特性）
  - 年处理特性总数: 50 × 2 × 12 = 1,200 个

当前总投入: 1,200 × 7 = 8,400 人天/年

效率提升 30% -> 节省: 8,400 × 30% = 2,520 人天/年
  ≈ 节省 10-12 人/年的人力投入
  ≈ 按人均成本 50-80 万/年 -> 年节省 500-960 万

工具/平台投入: ~100-200 万/年（含模型调用、工具授权、工程化）
ROI: 3-5×（首年即回本，后续持续收益）
```

## 3. 现状与问题分析

### 3.1 使用现状四层洞察

```text
AI 编程成熟度四级模型：

L4 +---------------------------------------------+
   | 需求自动拆解 -> 编码 -> 编译 -> 验证 -> 合入     |  <- 目标状态
   | 端到端自动化，人工仅做确认                    |
   +---------------------------------------------+
L3 | 特性/缺陷级开发                              |  <- 本次方案重点攻坚
   | 理解需求 -> 定位代码 -> 修改 -> 编译 -> 下板验证  |
   | AI 完成 70% 编码 + 辅助验证                  |
   +---------------------------------------------+
L2 | 小模块功能开发                               |  <- 部分团队已达
   | 单函数/单文件的完整实现                      |
   | 需要人工整合到工程                          |
   +---------------------------------------------+
L1 | 代码片段补全/生成                            |  <- 90% 人员在用
   | 复制粘贴到工程，人工整合                     |
   +---------------------------------------------+

现状: ->->->->->->->->->->->->->->->->->->->->->->->->->->->->->->->->->->-> L1 集中区
目标(12个月后): ->->->->->->->->->->->->->->->->->->->-> L2-L3 为主
```

#### 现状一：使用广泛但层次浅

| 维度 | 数据 | 分析 |
|:-----|:-----|:------|
| 使用率 | ~90% | 几乎人人都在用，说明需求真实且强烈 |
| 主要停留在 L1 | 代码片段补全/生成 | 把 AI 当"高级搜索引擎"用，未发挥 AI 的推理和上下文理解能力 |
| L2 少量 | 小模块功能开发 | 部分探索者已尝试，但效果参差不齐 |
| L3 极少 | 特性/缺陷级开发 | 工程级理解瓶颈 + 安全限制 + 验证依赖 |

**根因分解**：

- **能力断层**：知道"问 AI 写代码"但不知道怎么让 AI "理解整个工程"
- **反馈缺失**：L1 模式下即使 AI 输出有问题，影响范围小；L3 一旦错误，影响大且难以排查
- **预期管理**：把 AI 当"一次生成准确"的工具，而非"迭代辅助"的协作者

#### 现状二：支撑平台导入慢

| 工具类型 | 业界主流 | 导入状态 | 阻碍因素 |
|:---------|:---------|:---------|:---------|
| **代码补全** | GitHub Copilot, Codeium, Tabnine | ⛔ 未导入 | 信息安全（代码上传云端） |
| **代码助手** | Cursor, Windsurf, VSCode 插件 | ⚠️ 部分评估中 | 安全审核 + 网络隔离要求 |
| **工程理解** | GitNexus, DeepWiki, Sourcegraph | ✅ **验证中（GitNexus）** | 需本地部署 + 适配 |
| **大模型** | GPT-4o, Claude 4, Gemini 2.5 | ⛔ 外部模型不可用 | 信息安全红线 |
| **内部模型** | 自研/国产大模型 | ✅ 已部署但有局限 | 上下文窗口小 + 推理能力弱 |

**核心矛盾**：

- 外部最强模型（GPT-4o, Claude 4）因信息安全无法使用
- 内部模型能力弱 + 上下文小 → 难以支持 L3/L4 场景
- 国产模型在固件/C 语言场景的微调不足

#### 现状三：赋能体系已建立但难以落地

```text
已完成（问题不大）:             落地受阻（因平台限制）:
  +------------------+        +------------------+
  | AI 编程培训       | ✅     | 方案实操          | ❌
  | 提示词工程培训    | ✅     | Skills 集成测试   | ❌
  | Skills 开发方法   | ✅     | CLI 工具链集成    | ❌
  | CLI 集成实践      | ✅     | CI/CD 对接        | ❌
  +------------------+        +------------------+
```

**根因**：赋能材料与实际可用工具之间存在 **GAP** ——培训教的是"用最强模型做最好的事"，但实际面对的是"内部弱模型 + 受限环境"。

#### 现状四：内部大模型能力不足

| 对比维度 | 外部 SOTA 模型 | 内部可用模型 | 差距影响 |
|:---------|:--------------|:------------|:---------|
| **上下文窗口** | 128K-1M tokens | 4K-32K tokens | 无法理解完整工程结构 |
| **代码推理** | 强（多步推理+自检） | 弱（简单模式匹配） | 无法处理复杂逻辑 |
| **C/C++/汇编** | 充分训练 | 训练不足 | 固件场景表现差 |
| **可靠性** | 有自检机制 | 需人工全面复核 | 降低效率提升效果 |
| **指令遵循** | 严格 | 容易偏离 | 约束难以一致执行 |

### 3.2 高阶场景落地困难（L3+）

经过本地 demo 工程（知识库、运维项目）上的实践验证，L3+ 场景存在以下关键问题：

#### 问题 ①：上下文理解有限

```text
传统 AI 编程交互模式（L1-L2）:
  用户: "写一个 I2C 读写函数"
  AI:  [生成独立的 I2C 读写函数]
  用户: 复制 -> 粘贴 -> 手动适配工程接口

L3 需要的交互模式:
  用户: "在 BMC 的 IPMI FRU 模块中增加对 EEPROM 页地址的支持"
  AI:  需要先理解:
        1. 当前 FRU 模块的代码结构（哪些文件/函数）
        2. 现有的 EEPROM 读写路径（I2C 驱动层->IPMI 层->应用层）
        3. 页地址的硬件约束（不同厂商 EEPROM 的页大小/地址规则）
        4. 需要兼容哪些已有接口（不破坏现有功能）
        5. 固件的编译配置（哪些宏控制 FRU 功能）
  [分析工程 -> 找到修改位置 -> 生成适配代码 -> 检测编译 -> 生成测试用例]
```

**核心瓶颈**：AI 无法"看"到完整工程结构，只能根据用户描述零散地理解。

#### 问题 ②：难以准确理解需求与拆解

```text
需求原文: "增强 FRU 模块对多源 EEPROM 的支持"

可能的多重含义:
  解读 A: 支持更多厂商的 EEPROM 芯片（增加兼容列表）
  解读 B: 支持 EEPROM 的页地址模式（超过 256 字节需页切换）
  解读 C: 支持多个 EEPROM 设备（同一 FRU 使用多片存储）
  解读 D: 支持热插拔场景下 EEPROM 的重识别
  解读 E: 上述全部

需求拆解 -> 需要人工澄清 -> 沟通成本
AI 无法自动判定"隐含的上下文"（是哪个产品线？哪个客户？哪个项目？）
```

#### 问题 ③：约束不明确，难以一致遵守

BMC/BIOS 固件开发有大量的隐式约束：

| 约束类型 | 示例 | 来源 |
|:---------|:-----|:-----|
| **编码规范** | 命名风格、头文件顺序、注释格式 | 部门规范文档 |
| **架构约束** | 不能绕过 IPMI 层直接操作硬件寄存器 | 架构设计文档 |
| **安全约束** | 所有对外接口需做输入校验 | 安全编码规范 |
| **兼容性约束** | 不能修改已有 API 的签名 | 兼容性策略 |
| **性能约束** | ISR 中不能使用 printf/malloc | 实时性要求 |
| **历史约束** | 某些"坏味道"代码因兼容性必须保留 | 经验积累 |

AI 如果不明确知道这些约束，生成的代码很可能合规不通过。

#### 问题 ④：需要下板验证，环境依赖

```text
编码完成
    |
    v
  本地编译（虚拟环境） --- 可模拟部分场景
    |
    v
  上传到单板 --- 需要物理硬件（BMC/BIOS 硬件）
    |               |
    |           +----+----+
    |           | 板卡数量有限  |
    |           | 资源争用     |
    |           | 环境设置耗时 |
    v           +---------+
  验证结果
```

### 3.3 根因分析

```text
问题 -> 根因 -> 解决方案映射

+------------------------------------------------------------------+
|  L1 无法进阶                 工程理解不足                        |
|  v                             v                                |
|  AI 只看片段不看全局    ->   引入工程级代码理解工具               |
|                             (GitNexus/DeepWiki)                  |
+------------------------------------------------------------------+
|  L3 需求拆解困难            上下文缺失                           |
|  v                             v                                |
|  需求多义  AI 无法判定  ->  建立"需求->方案"标准化 prompt         |
|                             + 知识库辅助上下文构建               |
+------------------------------------------------------------------+
|  约束不一致                 规范未数字化                          |
|  v                             v                                |
|  隐式约束 AI 不知道     ->  约束显式化为 Rule/Skill              |
|                             编码规范 -> .cursorrules / skill 文件 |
+------------------------------------------------------------------+
|  验证依赖硬件               验证自动化的缺失                      |
|  v                             v                                |
|  每改必下板 效率低     ->  OpenBMC 模拟 + 单元测试 + CI 自动编译  |
+------------------------------------------------------------------+
|  外部模型不可用              安全限制                             |
|  v                             v                                |
|  强模型不能用  ->   内外模型协同策略 + 本地部署 + 脱敏网关       |
+------------------------------------------------------------------+
```

## 4. 总体方案架构

### 4.1 四层能力栈

```text
+------------------------------------------------------------------+
|                      应用层 (User Interface)                      |
|  +----------+  +----------+  +----------+  +----------------+  |
|  | VSCode   |  | 命令行   |  | Web UI  |  | CI/CD 集成     |  |
|  | 插件     |  | (CLI)    |  | (知识库) |  | Jenkins/GitLab |  |
|  +----+-----+  +----+-----+  +----+-----+  +-------+--------+  |
+-------+--------------+-------------+-----------------+----------+
        |              |             |                 |
+-------v--------------v-------------v-----------------v----------+
|                   能力层 (Capability Layer)                      |
|                                                                  |
|  +----------------+  +----------------+  +------------------+  |
|  | 代码生成        |  | 工程理解        |  | 验证辅助          |  |
```

### 4.3 内外模型协同策略

面对「外部模型不可用，内部模型能力弱」的核心矛盾，采用以下策略：

```text
内外模型协同决策树：

任务输入
    |
    v
+---------------------------------------------+
| 判断: 任务是否涉及 BMC/BIOS 核心代码？       |
+---------------------------------------------+
| 是 -----> 内部模型（安全第一）               |
|               |                              |
|               +--> 代码补全 -> 内部小模型      |
|               +--> 模块开发 -> 内部大模型      |
|               +--> 工程分析 -> 内部大模型      |
|                      + 提前分段/摘要策略      |
|                                              |
| 否 -----> 判断: 任务复杂度                   |
|          +- 简单 -> 内部模型                  |
|          +- 复杂 -> 外部模型（经脱敏）         |
+---------------------------------------------+

内部模型能力增强策略（弥补能力不足）:

策略 ①: 上下文压缩（Context Compression）
  问题: 内部模型上下文小 -> 无法容纳完整工程
  方案:
    · 用 GitNexus 提取"代码摘要"而非完整代码
    · 只发送函数签名+调用关系+关键注释
    · 将 10MB 工程压缩为 5-10K tokens 的"代码地图"

策略 ②: 分段处理（Chunking + Merge）
  问题: 大特性需要跨多文件修改
  方案:
    · 将大任务拆分为 N 个子任务
    · 每个子任务可用内部模型的上下文窗口
    · 最后由 AI "合并"各子任务的产出并检查冲突

策略 ③: RAG 增强（检索增强生成）
  问题: 内部模型训练数据中固件代码少
  方案:
    · 建立固件知识库（API 文档、设计文档、FAQ）
    · 每次编码时自动检索相关文档作为上下文注入
    · 用向量数据库索引历史代码修改记录

策略 ④: 外部模型辅助架构（经脱敏）
  问题: 复杂方案设计需要强推理能力
  方案:
    · 人工提取"非敏感"的需求描述
    · 使用外部模型做高层次方案设计
    · 方案经安全审核后，交给内部模型做具体编码
```

## 5. 工程级代码理解方案

L3 落地的核心前提：**AI 必须理解整个工程的上下文**，不能只看片段。

### 5.1 方案选型与对比

| 工具 | 原理 | 部署方式 | 固件工程适配度 | 推荐度 |
|:-----|:-----|:---------|:--------------|:------:|
| **GitNexus** | Tree-sitter 语法解析 → 代码知识图谱（函数/类/调用链） | **✅ 完全本地部署** | ⭐⭐⭐⭐⭐ C/C++ 原生支持 | **🔴 首选** |
| **DeepWiki** | 代码静态分析 → 结构化文档（Markdown 百科） | **✅ 完全本地部署** | ⭐⭐⭐⭐ 需要适配 | **🟡 验证中** |
| Sourcegraph Cody | 全代码索引 + AI 辅助 | ❌ 需云端服务 | ⭐⭐⭐⭐⭐ | ❌ 安全不满足 |
| 基于 LLM 的 /init | 直接用大模型分析全部代码 | 依赖大模型 | ⭐⭐ 成本高+容量限制 | ⚠️ 备选 |

### 5.2 GitNexus 集成

#### GitNexus 原理

> GitNexus 通过 Tree-sitter 语法解析器分析代码的 AST（抽象语法树），构建多维代码知识图谱，包括：函数定义/调用关系、类层次结构、文件依赖关系、符号索引。

```text
GitNexus 索引构建流程:

  BMC 固件 Git 仓库 (~500MB-2GB)
         |
         v
  +------------------------------------+
  | Tree-sitter 语法解析                 |
  | · C 语言解析器                       |
  | · C++ 解析器 (部分)                 |
  | · Makefile 解析 (编译单元)          |
  +--------------+---------------------+
                 v
  +------------------------------------+
  | 知识图谱构建                        |
  | · 实体节点: 文件/函数/类/宏/变量   |
  | · 关系边: 调用/继承/包含/定义      |
  | · 属性: 参数/返回值/行号/模块归属   |
  +--------------+---------------------+
                 v
  +------------------------------------+
  | MCP 协议暴露                        |
  | · AI Agent 通过 MCP 协议查询       |
  | · 自然语言 -> 图查询 -> 结构化返回   |
  | · 支持: find_function, get_calls,   |
  |   get_callers, get_dependencies     |
  +--------------+---------------------+
                 v
  +------------------------------------+
  | AI Agent 理解代码                   |
  | "查找 FRU 模块中 I2C 读写路径"     |
  | -> GitNexus 返回调用链              |
  | -> AI 理解代码组织和逻辑             |
  +------------------------------------+
```

#### 在 BMC/BIOS 开发中的典型使用

```text
场景: "增强 IPMI FRU 的 EEPROM 页地址支持"

开发者 -> VSCode 插件：
  prompt: "在 IPMI FRU 代码中增加 EEPROM 页地址支持"

AI Agent 内部流程:
  1. 🔍 GitNexus 查询:
     "fru_read" 函数的定义 -> 返回: fru_handler.c:284
     "fru_read" 的调用者 -> 返回: ipmi_fru_cmd.c:156, fru_main.c:42
     "i2c_read" 函数定义 -> 返回: i2c_core.c:88
     文件依赖关系 -> 返回: fru_handler.c 包含头文件列表

  2. 📚 知识库检索:
     "EEPROM 页地址规范" -> 返回: AT24C256 的页大小 64 字节
     "FRU 设计规范" -> 返回: 必须兼容 IPMI FRU v1.0 格式

  3. 🧠 内部模型处理:
     输入: GitNexus 的代码地图 + 知识库的规范
     输出: 修改方案（修改哪些文件/函数/如何实现页切换）

  4. ✅ 生成代码:
     · 修改 fru_handler.c 增加页地址参数
     · 更新 ipmi_fru_cmd.c 的协议处理
     · 生成单元测试用例
     · 更新设计文档

  5. 🔄 开发者审查:
     · 确认修改方案
     · 审查生成的代码
     · 触发自动编译
```

### 5.3 DeepWiki 方案

DeepWiki 是另一种工程理解方案，适合**文档生成和知识沉淀**场景：

```text
DeepWiki 流程:

  BMC 工程代码
      |
      v
  DeepWiki 分析引擎
      |
      +- 解析代码结构（模块/文件/函数层级）
      +- 提取文档注释（Doxygen 格式）
      +- 分析调用关系和数据流
      +- 识别设计模式（回调/状态机/工厂）
      |
      v
  生成结构化百科（Markdown 格式）
      |
      +- 📖 模块概述（做什么/为什么要这么做）
      +- 🗺️ 架构图（ASCII/时序图）
      +- 📋 关键函数目录（签名/用途/调用者）
      +- 🔗 数据流说明（全局变量/消息路径）
      +- ⚠️ 注意事项（已知问题/兼容性约束）
      |
      v
  存入知识库 -> AI 编程时作为 RAG 上下文

  与 GitNexus 的差异:
  · GitNexus: 实时查询代码结构（"谁调用了这个函数？"）
  · DeepWiki: 预先生成文档（"这个模块是做什么的？"）
  · 两者互补: GitNexus 做动态查询 + DeepWiki 做静态知识
```

### 5.4 上下文构建规范

为了在内部模型限制下最大化上下文利用，制定以下规范：

```text
上下文构建规范（按优先级注入）:

  +---------------------------------------------------------+
  | 上下文信息               | 来源              | 大小     |
  +--------------------------+------------------+---------+
  | ① 当前修改的代码片段     | 开发者选区        | <500    |
  |                         |                   | tokens  |
  | ② 相关函数签名+调用链    | GitNexus          | <2K     |
  |                         |                   | tokens  |
  | ③ 相关模块设计文档       | DeepWiki/知识库   | <3K     |
  |                         |                   | tokens  |
  | ④ 项目级 Rule/Skill     | 预定义文件        | <2K     |
  |                         |                   | tokens  |
  | ⑤ 相关历史提交示例       | Git log           | <1K     |
  |                         |                   | tokens  |
  +---------------------------------------------------------+
  总计: ~8.5K tokens
  内部模型上下文: 32K tokens (留余量给模型推理)

  超过上下文限制时的降级策略:
  · 优先丢弃 ⑤ 历史提交（相关性最低）
  · 将 ③ 设计文档替换为 摘要版
  · 将 ② 调用链限制为 1 级（不显示孙节点）
```

## 6. AI 分层能力建设

**目标**：让 90% 的开发人员从"低效搜索"升级为"高效生成"

**交付物**：

### 7.2 需求理解阶段


```text
提示词规范架构:

+----------------------------------------------------------+
```

### 8.2 Skills 固化方案

将高频可复用的编程模式固化为 Skill：

```text

  description: "增强 BMC IPMI FRU 模块功能"
  version: "1.0"

  triggers:
    - "FRU"
    - "IPMI FRU"
    - "fru_"
    - "EEPROM 页"

  context:
    gitnexus_query:
      - "fru_read"
      - "fru_write"
      - "ipmi_fru_cmd"
    knowledge_base:
      - "IPMI FRU v1.0 规范"
      - "AT24C256 EEPROM 数据手册"
      - "BMC I2C 驱动层 API 文档"

  rules:
    - "所有 FRU 数据必须遵循 IPMI FRU v1.0 格式"
    - "EEPROM 读写必须通过 I2C 驱动层，禁止直接操作寄存器"
    - "页地址切换时必须保持原 EEPROM 内容不变"
    - "新增函数必须带 Doxygen 注释"
    - "必须向后兼容已有的 FRU 读命令"

  workflow:
    - step: "工程分析"
      action: "GitNexus 查询 FRU 模块代码结构"
    - step: "方案设计"
      action: "生成修改方案，标注影响范围"
    - step: "编码实现"
      action: "按文件逐一生成修改代码"
    - step: "单元测试"
      action: "生成对应测试用例"
    - step: "文档更新"
      action: "更新设计文档和头文件注释"

  output:
    - "代码 diff"
    - "单元测试文件"
    - "设计文档更新"
    - "测试报告模板"
```

## 10. 质量保障体系

### 10.1 AI 代码审查标准

```text
AI 生成代码的审查层次:

  L0: 编译检查（自动）
  +----------------------------------------+
  | · 是否可编译通过                        |
  | · 是否有未定义的符号/类型               |
  | · 头文件引用是否完整                    |
  +----------------------------------------+

  L1: 静态分析（自动）
  +----------------------------------------+
  | · 是否符合编码规范                      |
  | · 是否有内存泄漏风险                    |
  | · 是否有空指针/越界访问                 |
  | · 是否有未初始化变量                    |
  +----------------------------------------+

  L2: 逻辑审查（AI + 人工）
  +----------------------------------------+
  | · 逻辑是否正确（边界条件）              |
  | · 是否符合设计文档                      |
  | · 是否与现有代码逻辑一致                |
  | · 异常处理是否完整                      |
  +----------------------------------------+

  L3: 架构审查（人工为主）
  +----------------------------------------+
  | · 是否符合架构设计原则                  |
  | · 是否引入不必要的依赖                  |
  | · 模块间耦合是否合理                    |
  | · 扩展性/可维护性评估                   |
  +----------------------------------------+

  AI 审查自动拦截标准:
  编译错误 -> ❌ 拦截,不进入人工审查
  内存泄漏 -> ❌ 拦截,要求 AI 修复
  空指针 -> ❌ 拦截,要求 AI 修复
  编码规范违规 -> ⚠️ 标记,人工确认
  逻辑嫌疑 -> ⚠️ 标记,人工重点审查
```

### 10.2 安全红线

```text
🚫 绝对红线（任何时候不可触碰）:

  1. 不可将 BMC/BIOS 完整工程代码上传到外部模型
  2. 不可在 AI 对话中透露敏感信息（客户名/产品代号/未公开特性）
  3. AI 生成的代码必须经过人工审查才能合入
  4. AI 不能直接修改生产分支（必须走 PR/MR 流程）
  5. 安全相关模块（加密/鉴权/安全启动）的修改必须人工审核

⚠️ 谨慎操作（需审批）:

  1. 使用外部模型辅助方案设计 -> 需脱敏 + 审批
  2. AI 生成的安全性关键代码 -> 需安全团队审查
  3. AI 对已有架构的大幅度重构 -> 需架构组评审
```

### 10.3 验证闭环机制

```text
AI 代码 -> 验证 -> 反馈 -> 迭代

  +---------------------------------------------------------+
  |  验证闭环流程:                                           |
  |                                                          |
  |  AI 生成代码                                              |
  |      |                                                    |
  |      v                                                    |
  |  ① 编译验证 ---> 失败? -> AI 自修复 -> 重试(最多3次)       |
  |      | 成功                                               |
  |      v                                                    |
  |  ② 静态分析 ---> 违规? -> AI 修复 -> 重新编译             |
  |      | 通过                                               |
  |      v                                                    |
  |  ③ 单元测试 ---> 失败? -> AI 分析+修复 -> 重新运行        |
  |      | 通过                                               |
  |      v                                                    |
  |  ④ 人工审查 ---> 发现问题? -> 人工修改+反馈给 AI          |
  |      | 通过                                               |
  |      v                                                    |
  |  ⑤ 下板验证(按需) -> 发现问题? -> 回溯到 AI 或人工        |
  |      | 通过                                               |
  |      v                                                    |
  |  ⑥ 合入                                                  |
  +---------------------------------------------------------+

  反馈闭环:
  · 每次人工修改后 -> 将修改反馈给 AI（增量学习）
  · 每次验证失败 -> 根因记录到知识库（避免重复错误）
  · 每周 -> 统计分析 AI 代码的缺陷率/修改率
```
