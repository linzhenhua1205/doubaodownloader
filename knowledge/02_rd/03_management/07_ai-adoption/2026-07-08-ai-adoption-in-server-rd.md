## 1. 总览：以 AI 为中心的组织建设

### 1.1 战略目标

| 层级 | 目标 |
|:-----|:------|
| **愿景** | 以 AI 为中心的组织建设，推进 AI 应用 & 运用到全领域 |
| **目的 1** | 解决 AI 应用过程中遇到的问题 |
| **目的 2** | 分享 Common 的 AI 应用实例 |
| **目的 3** | 端到端、上下游 AI 场景应用孵化 |

### 1.2 核心变化

传统 IT 建设与 AI 组织建设的本质区别：

| 维度 | 传统 IT 建设 | AI 组织建设 |
|:-----|:------------|:------------|
| 驱动方式 | 需求驱动（用户提需求→IT 实现） | 场景驱动（识别痛点→AI 赋能→验证推广） |
| 交付物 | 系统/平台/工具 | 能力/Skill/Agent/Automation |
| 用户角色 | 操作者（学习使用系统） | 委托者（定义目标+验收结果） |
| 迭代周期 | 月/季度 | 天/周（PoC 快速验证） |
| 成功标准 | 功能完备、流程打通 | 效率提升、痛点消除、可复制推广 |
| 推广方式 | 培训+制度强制 | 实例拉动+社区自治+价值自证 |

### 1.3 服务器研发场景的特殊性

| 特征 | 对 AI 推广的挑战 | 应对策略 |
|:-----|:----------------|:---------|
| **硬件实物研发** | 大部分设计产出是物理产物（PCB/结构件/线缆），不是代码 | AI 赋能设计过程（检查/分析/规划），而非替代实物输出 |
| **多域强耦合** | 硬件/散热/结构/测试/软件 5 大域同步迭代 | Agent 跨域协同 > 单域深度自动化 |
| **长周期高成本** | 一次 Tape-out 百万级，改版周期月级 | AI 做前期预防 > 后期纠错——"前置规避"比"事后修复"价值高 10 倍 |
| **知识密集型** | 规格书/标准/白皮书/历史经验散落在不同人脑中 | 知识库为中心的知识管理是 AI 赋能的前提 |
| **流程规范性** | 产品开发流程（IPD/NPI）有严格阶段门禁 | AI 以辅助/加速角色嵌入流程，不改变流程结构 |

## 2. 运作机制设计

### 2.1 基本思路：五阶段闭环

```text
扫场景 ---> 找痛点 ---> 跑 PoC ---> 验证 ---> 推广 ---> 迭代
   |            |           |         |        |        |
   v            v           v         v        v        v
全领域扫描  识别高频    最小可    效果量化  技能化   复盘优化
+ 热点识别  + 高痛    + 可行方   + 横向    + 文档化  + 横向
+ 竞品对标  + 切得动   案       + 对比    + 打包    + 规模化
```

### 2.2 双轨运作节奏

| 机制 | 频率 | 内容 | 输出 |
|:-----|:-----|:------|:-----|
| **即时消息群** | 随时 | 问题求助·工具推荐·快捷技巧·踩坑记录·快速对齐 | 问题-方案记录·群知识沉淀 |
| **双周例会** | 每 2 周 | **主题一**：问题讨论（当前卡点·工具选型·解决方案）<br>**主题二**：实例培训分享（具体场景怎么做·效果如何·可复制性） | 会议纪要·P0 场景更新·Skill 发布·Roadmap 刷新 |

### 2.3 双周例会议程示例

| 时间 | 环节 | 内容 | 负责人 |
|:----|:-----|:------|:-------|
| 00:00~00:10 | 开场·上周回顾 | 上次 Action 跟踪·关键进展通报 | 组织者 |
| 00:10~00:35 | **主题一：问题讨论** | 当前 1~2 个重点问题（痛点确认·技术方案·资源缺口） | 问题提出方 |
| 00:35~00:40 | 休息/自由交流 | — | — |
| 00:40~01:00 | **主题二：实例培训分享** | 1 个已跑通场景的完整分享（背景·方案·效果·教训·可复制性） | 实践者 |
| 01:00~01:15 | 开放讨论·经验交流 | 其他成员反馈·横向推广判断·后续 Action | 全体 |
| 01:15~01:30 | 总结·下期安排 | P0 场景更新·下期议题征集·资源协调 | 组织者 |

### 2.4 角色与职责

| 角色 | 职责 | 建议人选 |
|:-----|:------|:---------|
| **组织者/Facilitator** | 运作机制维护·节奏把控·议题征集·纪要输出·进度跟踪 | 1 人（全职或兼任） |
| **领域 Champion** | 每个领域 1 人，负责本域场景识别·痛点提炼·PoC 推进·效果验证 | 硬件/散热/结构/测试/软件各 1 人 |
| **AI 技术支撑** | 工具选型·架构指导·CLI/Agent 开发·疑难解决 | 1~2 人（偏技术实现） |
| **实践者/Early Adopter** | 主动尝试新技术·贡献实例·反馈改进 | 各领域 1~2 人 |
| **决策者/Sponsor** | 资源保障·瓶颈突破·推广决策 | 1 人（管理岗） |

## 3. 牵引思路展开

### 3.1 a. 现状诊断：部门当前 AI 使用情况

**评估维度**（每个领域按 1~5 分评估）：

| 维度 | 问题 | 评分参考 |
|:-----|:------|:---------|
| **感知度** | 团队是否知道当前 AI 能做什么、不能做什么？ | 1=完全不知道 → 5=人手在尝试 |
| **工具覆盖率** | 哪些环节已用上 AI 工具？ | 1=无工具 → 5=关键环节全覆盖 |
| **自动化深度** | AI 是辅助人工作还是替代了部分工作流？ | 1=全程手工 → 5=端到端自动化 |
| **知识沉淀** | AI 使用中的经验/教训/模板是否被沉淀？ | 1=人脑记忆 → 5=知识库+Skill |
| **推广程度** | 是几个人在用还是团队在用？ | 1=个别人 → 5=全员日常 |

**快速摸底方式**：在群里发一个三分钟问卷+双周会上口头过一遍，而非大张旗鼓做调研。

### 3.2 b. 场景识别：哪些业务场景需要打通 AI 应用

**核心牵引问题**（围绕"你每天花精力最多的事情是什么"展开）：

| # | 牵引问题 | 目的 | 预期类型 |
|:-:|:---------|:-----|:---------|
| 1 | **你每天花费精力最多的事情是什么？** | 找到高频场景 | 重复性工作·信息检索·沟通协调 |
| 2 | **有什么事情你希望能"一键完成"？** | 找到自动化机会 | 例行报告·数据整理·格式转换 |
| 3 | **有什么判断/决策需要翻很多资料才能做？** | 找到知识密集点 | 方案选型·规格核对·供应商评估 |
| 4 | **有什么重复性工作你认为机器完全可以替代？** | 找到低价值环节 | Check·数据录入·版本比对·文档生成 |
| 5 | **你的领域里，什么环节最容易出错/返工？** | 找到高痛环节 | 人工校验遗漏·沟通信息丢失·经验依赖 |
| 6 | **你最近一次加班是在做什么？** | 找紧急场景 | 紧急方案·紧急报告·紧急定位 |
| 7 | **如果有个 AI 助手能帮你做一件事，你最希望它做什么？** | 找到真实需求 | 各域具体场景 |

**收集方式**：

- 群内发起"三问打卡"（每天 1 个问题，持续一周）
- 双周会现场"痛点墙"（每人贴 3 个痛点，投票选出 Top 5）
- 一对一快速访谈（重点人，15 分钟/人）

### 3.3 c. P0 场景锁定：价值最高 + 最容易突破

**筛选原则**：

| 原则 | 说明 | 判断方式 |
|:-----|:------|:---------|
| **不选"颠覆性"场景** | 不要一上来就想用 AI 取代工程师核心设计工作 | 优先选"烦但简单"的非核心工作 |
| **选"切得动"的场景** | 技术可行、数据可达、干系人支持 | PoC 周期 ≤2 周 |
| **优先「高频+痛苦」** | 天天遇到 + 确实费时费力 | 落地后感受最明显，推广说服力最强 |
| **价值可量化** | 能说出"原来 2 小时 → 现在 5 分钟" | 横向对比有说服力 |

**筛选矩阵**：

```text
                   价值（效率提升 + 影响范围）
                     高 <------------> 低
                   +---------------------+
               高  |  ① P0 立即做        |  ② 值得做但排期靠后  |
                   |  （高频+高痛+易做）  |  （复杂但价值高）    |
  切得动程度       +---------------------+
               低  |  ③ 简单但价值低      |  ④ 暂时不碰          |
                   |  （有空再做）        |  （难做+价值低）     |
                   +---------------------+
```

**输出**：每个领域锁定 1~2 个 P0 场景，写在白板上、贴着不走。

### 3.4 d. 最佳实践选择：降低引入成本

**选择原则**：

| 原则 | 说明 |
|:-----|:------|
| **优先用已有工具** | 软件域已验证的 AI 代码生成、知识库 RAG 等可直接复用 |
| **CLI 优先** | 命令行工具比 Web 界面更容易被 AI Agent 调用 |
| **Skill 标准化** | 验证后的实践打包为可复用的 Skill，降低下一个使用者门槛 |
| **先抄后超** | 先学行业已有做法，再根据领域特性做定制 |

## 4. AI 推广的五层能力模型

AI 在组织中的推广不仅是工具部署，而是能力分层递进。以下五层能力逐级构建：

```text
第五层：自主演化
   +-------------------------+
   | 知识自动补全·Skill 自进化|
   | Agent 自主优化工作流     |
   +----------+--------------+
              |
第四层：智能工作流
   +----------v--------------+
   | Skills/Prompt 自动化    |
   | Agent 跨域协同·审核链   |
   +----------+--------------+
              |
第三层：Agent 辅助
   +----------v--------------+
   | 知识问答·数据查询·      |
   | 规划执行·任务 Agent     |
   +----------+--------------+
              |
第二层：工具增强
   +----------v--------------+
   | 代码生成·小工具自动生成  |
   | 文档/报告自动生成       |
   +----------+--------------+
              |
第一层：知识底座
   +----------v--------------+
   | 知识库体系（结构化沉淀） |
   | 统一索引·版本管理       |
   +-------------------------+
```

| 层级 | 核心能力 | 成熟度标志 | 典型场景 |
|:-----|:---------|:----------|:---------|
| **L1 知识底座** | 有体系的知识沉淀·统一检索·版本管理 | 每个域有知识库入口，新人能找到 80% 答案 | 规格查询·参数查表·设计方案复用 |
| **L2 工具增强** | AI 代码生成·小工具·文档生成 | 日常工作中主动使用 AI 工具 | 测试脚本生成·BOM 对比·报告生成 |
| **L3 Agent 辅助** | 知识问答 RAG·数据查询 Agent·规划执行 Agent | 日常通过 Agent 做信息检索和数据查询 | 问知识库·查实验数据·生成分析报告 |
| **L4 智能工作流** | Skills/Prompt 自动化·审核链·跨域 Agent 协同 | 复杂任务可端到端自动化执行 | 自动设计审查·自动回归测试·方案自动比较 |

### 7.3 Agent 间通信与协同

```text
                   +--------------+
                   |  用户问题/任务 |
                   +------+-------+
                          v
                   +--------------+
                   |  入口路由判断  |
                   +------+-------+
                          |
          +---------------+---------------+
          v               v               v
   +------------+  +------------+  +------------+
   | 问答 Agent  |  | 问数 Agent  |  | 规划执行    |
   | (信息查询) |  | (数据查询) |  | Agent      |
   +------+-----+  +------+-----+  | (任务执行)  |
          |               |        +------+-----+
          +-------+-------+               |
                  v                       v
           +------------+         +------------+
           | 审核 Agent  |<--------| 执行结果    |
           | (质量门)   |         | (产物/报告) |
           +------------+         +------------+
```

**协同原则**：

1. **职责单一**：每个 Agent 只负责一种能力，不叠加
2. **无状态通信**：Agent 之间通过结构化数据（Fact/Event）通信，不直接调用
3. **审核分离**：执行方和审核方独立，避免自审偏向
4. **人工介入点**：关键决策/风险操作/边界判断需人工确认

## 8. 面向软件的代码生成与小工具开发

### 8.1 定位：AI for Code 在服务器研发中的应用

| 场景 | 说明 | 示例 |
|:-----|:------|:------|
| **测试脚本生成** | 按测试用例描述自动生成自动化测试脚本 | Python 自动化测试 |
| **数据处理脚本** | 日志解析、数据格式转换、报告生成 | Log Parser、Excel 汇总 |

| **自动化工作流** | 多步骤重复性工作的自动化脚本 | 批量文件处理、版本归档 |

### 8.2 典型路径：从手工到 Skill

```text
手工操作
  |
  v
AI 辅助生成脚本（对话式：帮我写个脚本做 X）
  |
  v
脚本标准化为 CLI 工具（参数明确·输出结构化·帮助文档）
  |
  v
CLI 工具注册为 Skill（可被 Agent 自动调用）
  |
  v
Agent 编排调用（端到端自动化工作流）
```

### 8.3 代码生成实践指南

| 原则 | 说明 |
|:-----|:------|
| **先有脚本，再谈框架** | 不要一开始就"建个框架"，从解决具体问题的单脚本开始 |
| **面向 CLI 设计** | 生成的工具要参数明确、帮助完整、输出可解析（JSON/结构化文本） |
| **小工具>大系统** | 每个工具只做一件事，组合使用比大而全的系统更灵活 |
| **输入输出明确** | 明确的输入格式和输出格式，方便被其他工具/Agent 链式调用 |
| **安全第一** | 不信任用户输入、不做危险操作、敏感操作确认 |
| **文档同步** | 可维护 README + 使用示例，方便别人上手 |

## 9. Skills/Prompt 自动化工作流

### 9.1 什么是 Skills

Skills 是一组可复用的 AI 能力封装，包含：

| 组件 | 说明 |
|:-----|:------|
| **描述 (Description)** | 什么场景触发、能做什么、不能做什么 |
| **触发条件 (Triggers)** | 哪些关键词/场景下自动启用 |
| **指令文件 (SKILL.md)** | 详细的执行步骤、验证标准、输出规范 |
| **关联工具/CLI** | 执行时可调用的工具集合 |
| **自检清单** | 完成后需验证的关键项 |

### 9.2 工作流自动化层级

| 层级 | 自动化程度 | 示例 |
|:-----|:----------|:------|
| **L0 纯人工** | 0% | 完全手工 |
| **L1 Prompt 模板** | 20% | 写好的 Prompt 模板，每次粘贴修改 |
| **L2 Skill 封装** | 50% | 可复用的 Skill，输入参数→输出结果 |
| **L3 部分自动化** | 70% | 多 Skill 编排 + 条件分支 + 人工决策点 |
| **L4 端到端自动化** | 90%+ | 从输入到输出的全自动工作流，人工验收 |

### 9.3 典型自动化工作流示例

#### 示例：设计约束检查工作流

```text
输入：设计参数/布局文件
  |
  v
Step 1: 知识问答 Agent -> 查询当前项目适用的设计规范版本
  |
  v
Step 2: 检查 CLI -> 执行约束检查（走线/器件/间距等）
  |
  v
Step 3: AI 分析结果 -> 分类（pass/fail/warning/suggestion），按严重程度排序
  |
  v
Step 4: 生成报告 -> 输出检查报告文档 + 摘要
  |
  v
Step 5 (可选): 审核 Agent -> 检查报告完整性
  |
  v
输出：检查报告
```

#### 示例：周报生成工作流

```text
输入：项目名称 + 周期
  |
  v
Step 1: 问数 Agent -> 拉取各系统数据（任务进展/问题/风险/工时）
  |
  v
Step 2: AI 分析偏差 -> 识别进度偏差 + 新增风险 + 已完成里程碑
  |
  v
Step 3: 生成报告 -> 输出周报文本（关键进展 + 问题 + 下周计划）
```

## 10. 审核机制设计

### 10.1 审核的四层结构

| 层 | 名称 | 审核对象 | 频率 | 方式 |
|:-:|:-----|:---------|:----:|:-----|
| **L1** | **自检** | AI 产出的结果 | 每次 AI 输出后 | AI 自身做格式/事实/完整性检查 |
| **L2** | **工具审核** | AI 调用的工具/CLI 的执行结果 | 每次执行 | 确定性规则验证（输出格式/范�围/一致性） |
| **L3** | **Agent 交叉审核** | 重要决策/复杂任务 | 关键步骤 | A Agent 产出 → B Agent（审核Agent）验证 |
| **L4** | **人工审核** | P0 级别的决策/最终交付物 | 里程碑/门禁 | 人确认关键结论/交付物质量 |

### 10.2 适用于各域的审核清单

| 域 | L1 自检项 | L2 工具验证 | L3 交叉审核 | L4 人工介入点 |
|:----|:---------|:-----------|:-----------|:------------|
| **硬件设计** | 数据有来源·单位标注·范围校验 | DRC 工具验证 | 设计规范符合性+历史问题关联 | Tape-out 签核 |
| **测试验证** | 结果格式统一·异常标注·数据完整性 | 测试脚本语法检查 | 测试覆盖度与历史缺陷关联 | 测试报告最终确认 |
| **成本管理** | 数据来源可追溯·口径统一 | BOM 成本公式验证 | 历史成本对比+趋势偏差 | 大额采购审批 |
| **项目管理** | 状态数据一致性·时间逻辑 | 日期合法性/依赖检查 | 风险关联+资源冲突 | 关键里程碑决策 |
| **知识管理** | 格式规范·交叉链接·索引更新 | 链接有效性检查 | 内容与已有知识的一致性 | 新的核心知识入库确认 |

### 10.3 审核不通过的处理

```text
审核不通过
  |
  +-- L1 自检不通过 -> 自动修改后重新提交
  |
  +-- L2 工具验证不通过 -> 阻断执行，返回具体 error+修改建议
  |
  +-- L3 交叉审核不通过
  |     +-- 轻度偏差 -> 标注差异项，给出修改建议，退回重做
  |     +-- 重大偏差 -> 阻断，标注根因和影响范围，进入问题讨论
  |
  +-- L4 人工不通过 -> 标注具体问题，退回重做，触发复盘
```

## 11. 知识管理演进路径

### 11.1 四阶段演进

```text
第一阶段：个人笔记            第二阶段：团队知识库
+-----------------+          +---------------------+
| · 个人 Markdown  |   --->   | · 统一目录+索引      |
| · 笔记           |         | · 交叉链接+版本管理   |
| · 无统一格式     |         | · 格式规范+质量检查   |
+-----------------+         | · 多域分区结构       |
                            +---------------------+
                                    |
                                    v
第四阶段：自主演化           第三阶段：知识为中心的数据管理
+---------------------+     +------------------------------+
| · AI 自动补全知识    |  <-- | · 知识库作为唯一事实源         |
| · 知识质量自动检测    |     | · RAG 问答+Agent 使用知识库    |
| · Skill 自进化      |     | · 数据+文档+规范统一归入知识库   |
| · 知识缺口自动识别    |     | · 多源数据自动导入知识库        |
+---------------------+     +------------------------------+
```

### 11.2 第一阶段：个人笔记 → 第二阶段：团队知识库

**关键转变**：

- 从"我记我看"到"团队共建共享"
- 从"无格式"到"有规范"
- 从"人找知识"到"索引引导"

**实操方法**：

- 选定统一的知识存放位置（如 Knowledge 目录）
- 制定简单的格式模板和命名规范
- 建立索引（自动/手动）方便查找
- 开始不用追求完美，先让资料"有地方放+找得到"

### 11.3 第二阶段 → 第三阶段：以知识为中心的数据管理

**核心理念**：知识库不只是文档仓库，而是**所有 AI 能力的底层数据来源**。

| 能力 | 依赖的知识 |
|:-----|:---------|
| 知识问答 RAG | 知识库中的规范/指南/案例 |
| 问数 Agent | 知识库中的数据源描述和字段定义 |
| 规划执行 Agent | 知识库中的流程文档/操作规程 |
| 审核 Agent | 知识库中的审核规范和检查清单 |
| 代码生成 | 知识库中的代码规范/最佳实践 |

**建设要点**：

1. 结构化知识（表格/分类/标签）> 非结构化文档
2. 版本可控 + 变更可追溯
3. 检索引擎（语义+关键词）可用
4. 知识间交叉引用（链接）清晰

### 11.4 第三阶段 → 第四阶段：自主演化知识管理

| 能力 | 说明 | 成熟度标志 |
|:-----|:------|:----------|
| **自动知识补全** | AI 发现知识缺口后自动搜索补全 | 知识库覆盖率 > 90% |
| **质量自动检测** | AI 定期检查知识质量（过时/重复/矛盾/缺失） | 质量检查自动化 |
| **Skill 自进化** | 基于使用反馈自动优化 Skill | Skill 定期自动优化 |
| **知识图谱自动构建** | 从非结构化文档自动提取实体关系 | 知识关联度提升 |
| **自动索引更新** | 新知识入库后自动更新索引和交叉链接 | 索引零手工维护 |

### 11.5 知识管理的关键成功因素

| 因素 | 说明 | 常见失败原因 |
|:-----|:------|:-----------|
| **低门槛贡献** | 贡献知识的过程要简单方便 | 流程复杂→没人愿意做 |
| **质量与数量的平衡** | 先做到"有"，再改进"好" | 追求完美→效率低 |
| **搜索可用** | 找东西要快，否则宁可用群聊 | 检索质量差→用户不用 |
| **有实际价值** | 知识库确实验证了效率提升 | 没人用→变成死库 |
| **持续维护** | 定期检查+清理+更新 | 不管→库越来越旧→不再可信 |

## 12. 分享拉通机制

### 12.1 为什么要分享拉通

| 问题 | 表现 | 后果 | 分享拉通的价值 |
|:-----|:------|:------|:-------------|
| **信息孤岛** | A 域的经验 B 域不知道 | 重复踩坑·重复造轮子 | 经验横向复用 |
| **认知不统一** | 对同一工具/方法理解不同 | 效率低·协作摩擦 | 对齐认知 |
| **创新扩散慢** | 好的实践停留在少数人手中 | 整体能力提升慢 | 加速创新扩散 |
| **问题解决慢** | 遇到问题时不知道谁遇到过 | 定位时间长 | 问题快速匹配 |
| **资源浪费** | 多个团队各自摸索相同方向 | 投入分散 | 集中力量办大事 |

### 12.2 分享拉通的双轨机制

#### 日常（异步）

| 形式 | 载体 | 频率 | 内容 | 产出 |
|:-----|:-----|:-----|:------|:-----|
| **踩坑快报** | 群消息 | 随时 | 一句话+链接：今天遇到 X 问题，原因是 Y，解决方式是 Z | 群内讨论+标�记 |
| **工具推荐** | 群消息 | 随时 | "推荐一个工具做 X 特别好用" + 一句话说明 | 群内讨论 |
| **技巧分享** | 群消息 | 随时 | "今天发现一个快捷方式" + 截图/命令 | 技巧收集 |
| **问题求助** | 群消息 | 随时 | "有人遇到过 X 么？" + 上下文描述 | 群内回答+归档 |
| **周小结** | 群内帖 | 每周 | 本周关注的 1~2 个 AI 相关进展/发现/踩坑 | 存档到知识库 |

#### 定期（同步）

| 形式 | 频率 | 时长 | 内容 | 产出 |
|:-----|:-----|:----:|:------|:-----|
| **双周例会** | 每 2 周 | 1.5h | 问题讨论+实例培训分享 | 会议纪要+P0 更新 |
| **月度 Demo** | 每月 | 1h | PoC 成果展示+效果数据+可复制性评估 | Demo 记录+推广决策 |
| **季度 Review** | 每季 | 2h | 阶段总结+Roadmap 修正+资源协调 | 季度报告+下季计划 |

### 12.3 实例分享模板

每次实例分享按以下模板组织，保证信息完整且可复用：

```text
---------------------------------------
场景名称：         [场景名]
领域：             [硬件/散热/结构/测试/...]
分享人：           [姓名]
实现周期：         [从开始到验证的天数]
---------------------------------------

1. 痛点描述
  · 原来是怎么做的？
  · 痛点在哪里？（频率/耗时/易出错）
  · 为什么之前没解决？

2. 方案
  · 用了什么工具/方法？
  · 关键思路是什么？
  · 踩了哪些坑？

3. 效果
  · 原来：[具体数值]
  · 现在：[具体数值]
  · 提升：[百分比/绝对值]

4. 可复制性
  · 其他人怎么用？
  · 需要什么前置条件？
  · 有哪些限制？

5. 后续改进
  · 还有什么可以优化？
  · 还有什么新的想法？

6. 附件/链接
  · 相关文档/Skill/代码
---------------------------------------
```

### 12.4 分享拉通的运营要点

| 要点 | 说明 |
|:-----|:------|
| **不说教** | 分享不是训话，是"我知道了你知道了大家一起更快" |
| **不端着** | 即使不完美也可以分享，踩坑经验比成功经验更有价值 |
| **有记录** | 每次分享内容必须归档（知识库），方便后来人检索 |
| **低门槛** | 分享者准备时间不要超过 30 分钟 |
| **有反馈** | 分享后群里讨论 + 明确下次谁做 |
| **持续迭代** | 同一个场景的实践可以反复分享（第一次 trial → 第二次改进版） |

## 13. 关键失败模式与应对

| # | 失败模式 | 表现 | 根因 | 预防/应对 |
|:-:|:---------|:------|:-----|:----------|
| 1 | **什么都想自动** | 一开始就追求端到端全自动，结果 PoC 做不出来失去信心 | 低估了不确定性和边界情况 | 先做 80% 容易的部分，再逐步覆盖边界 |
| 2 | **只做工具不做推广** | 开发了一堆 CLI/Agent 但没人用 | 路径依赖+习惯固化 | PoC 阶段就拉上最终用户参与，解决真实痛点 |
| 3 | **只讲不落地** | 双周会开了几次但没实际场景推进 | 缺乏责任人和 Action | 每个场景指定 owner + 截止时间 |
| 4 | **一味追求最新技术** | 不断换工具换框架，实际价值没做出来 | 技术驱动而非场景驱动 | "先解决痛点，再讨论技术选型" |
| 5 | **完美主义拖延** | 总想"等 xxx 条件成熟了再开始" | 对不完美的不耐受 | 最小可行 PoC = 1~2 周，不追求完备 |
| 6 | **数据不支撑** | 想做 Agent 但发知识库/数据没有或者格式不统一 | 知识管理没跟上 | 先做数据基础设施建设（L1），再做 AI（L2+） |
| 7 | **只有 Champion 没有群众** | 1~2 个人在做，其他人观� | 推�不足 | 每次分享突出"做了的人省了多少时间" |
| 8 | **没有量化效果** | 做了但说不清好在哪 | 缺乏基准数据 | PoC 前先统计"当前基线"（花多少时间/多少次） |
| 9 | **过度依赖单一工具供应商** | 某个工具/平台/模型一旦不可用就倒退到原点 | 技术绑定 | 关键能力有替代方案（多模型/多工具） |
| 10 | **忽略安全与隐私** | 把敏感设计数据暴露给外部模型 | 安全意识不足 | 明确数据分级，敏感数据用私有化部署 |

## 14. 总结与行动清单

### 14.1 三句话总结

1. **场景锁定 > 技术炫技**：从"每天花精力最多的事"出发，选高频+痛苦的场景先切
2. **L1→L5 逐级构建**：先夯实知识底座，再做工具增强，再 Agent 辅助，再工作流自动化，再自主演化
3. **分享拉通是引擎**：双轨机制（即时群+双周会）+ 实例分享模板 + 知识沉淀 = 可持续的 AI 推广
