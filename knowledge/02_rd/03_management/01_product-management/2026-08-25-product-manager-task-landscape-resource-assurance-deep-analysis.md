## §0 执行摘要

产品经理岗位的任务域远不止"画原型、写 PRD"。在**硬件研发组织**（服务器/超节点/AI 基础设施）中，产品经理实际承担的是**从市场价值到可交付物之间的全链路衔接**，其中最容易出问题、也最容易被职责描述忽略的，是**资源获取与保障**：

- **传统职责描述**（需求/方案/项目/协同）回答"做什么、为什么做、做成什么样"；
- **资源保障职责**回答"用什么做、从哪来、什么时候到位"——缺了它，方案再好也是空中楼阁。

**核心结论**：

1. **五大任务域**（MECE）：需求与市场域、方案与决策域、资源获取与保障域、项目推进域、协同与治理域。资源保障域与其余四域同等重要，不是"顺手帮忙"。
2. **资源保障是"隐性一等职责"**：外采、领料、齐套、商务合作看似事务性，但一个关键物料缺位即可让整条研发链路停摆，其**阻塞成本远高于事务成本**（见 §4.1 量化）。
3. **方案讨论确认必须闭环书面化**：口头共识 ≠ 决策，讨论 → 确认 → 冻结 → 变更控制四步缺一不可，否则后期返工成本按数量级放大（§3.2）。
4. **齐套管理是资源保障的枢纽**：以"物料齐套率 + 缺料预警提前量"为核心指标，把外采、领料、借用、商务合作全部串起来（§4.6）。
5. **阻塞预防 > 阻塞救火**：长交期物料提前量、里程碑前置齐套检查、升级 SLA 三件套，是避免"到用的时候没物料"的系统性手段（§4.8）。

## §1 任务全景模型：五大任务域

### 1.1 为什么需要一张任务地图

产品经理岗位的常见困境：**职责边界模糊**——什么都沾边，但考核说不清；事务淹没重点——天天救火（催料、跟单、协调），真正的价值工作（需求洞察、方案质量）反而被挤压。

一张任务地图的价值：

| 用途 | 说明 |
|:-----|:-----|
| **对齐预期** | 上级/团队/产品经理三方对"这个岗位到底干什么"有一致认知 |
| **暴露盲区** | 资源保障这类隐性职责一旦显性化，就有了考核与改进抓手 |
| **精力分配** | 明确各任务域的时间配比，避免事务性工作吞噬价值性工作 |
| **能力建设** | 按任务域补齐能力短板（商务谈判、齐套管理、决策推动） |

### 1.2 五大任务域（MECE）

按**价值流 + 资源流**两条主线切分，同层互斥且穷尽：

```text
+------------------------------------------------------------------+
|                  PRODUCT MANAGER TASK DOMAINS                    |
+------------------------------------------------------------------+
|  A. DEMAND & MARKET   B. SOLUTION & DECISION   C. RESOURCE       |
|     - market insight      - solution design       ASSURANCE      |
|     - requirement mgmt    - discussion & confirm  - external buy  |
|     - prioritization      - decision freeze       - internal pull |
|     - change control      - change control        - kit complete  |
|                                                     - biz coop    |
|  D. PROJECT EXECUTION  E. COORDINATION & GOVERNANCE              |
|     - plan / milestone     - stakeholder map                     |
|     - progress / quality   - escalation ladder                   |
|     - risk management      - info synchronization                |
+------------------------------------------------------------------+
```

| 域 | 一句话定位 | 回答的问题 |
|:---|:-----------|:-----------|
| **A 需求与市场域** | 定义"做什么、为什么做" | 做对的事 |
| **B 方案与决策域** | 定义"做成什么样" | 把事做对 |
| **C 资源获取与保障域** | 解决"用什么做、何时到位" | 让事能做 |
| **D 项目推进域** | 确保"按计划交付" | 让事落地 |
| **E 协同与治理域** | 保证"多方对齐、决策通畅" | 让事推进 |

> 注：传统产品经理职责描述通常把 A/B/D/E 四域讲透，唯独 C 域（资源保障）被当作"行政事务"归给助理或采购。**本文的核心主张：在硬件研发场景中，C 域必须由产品经理亲自负责或强主导**，理由见 §4.1。

### 1.3 双主线结构：价值流 × 资源流

```text
VALUE FLOW (why & what)        RESOURCE FLOW (how & when)
----------------------         --------------------------
market need  -->  demand  -->  external buy  -->  material
requirement --> solution  -->  internal pull -->  equipment
priority    --> decision  -->  biz cooperation -> human/tech
     \                        /
      \                      /
       +-----> DELIVERABLE <-----+
              (working product)
```

两条主线在产品经理这里汇合：**价值流**决定做什么（A/B 域），**资源流**决定能不能做、何时能做（C 域），D/E 域负责把两者拧成一股绳按期交付。

## §2 需求与市场域

### 2.1 核心任务清单

| 任务 | 关键动作 | 常见失败模式 |
|:-----|:---------|:-------------|
| 市场与客户洞察 | 行业趋势跟踪、客户痛点访谈、竞品拆解 | 只看二手报告，不接触一线客户 |
| 需求收集与结构化 | 需求池维护、原始需求→产品需求转化 | 需求散落在各聊天工具，无统一台账 |
| 需求优先级排序 | RICE/WSJF 等加权打分，与战略对齐 | 按"谁嗓门大"排序，无量化依据 |
| 需求变更管理 | 变更评审、影响面分析、基线管理 | 变更不评审直接改，范围失控 |
| 竞品分析 | 竞品功能/性能/价格/生态四维对比 | 停留在参数表，缺商业模式分析 |

### 2.2 输出物与量化指标

**输出物**：需求池（结构化台账）、MRD/BRD、竞品分析报告、需求优先级列表（含评分依据）、变更记录单。

**量化指标**：

| 指标 | 定义 | 建议基线 [来源: 经验基线，行业无统一统计] |
|:-----|:-----|:-----|
| 需求命中率 | 交付需求中被客户/市场验证有效的比例 | ≥ 60% |
| 需求平均确认周期 | 从需求提出到优先级定案的天数 | ≤ 5 个工作日 |
| 变更率 | 基线后需求变更次数 / 总需求数 | ≤ 15%（超过则说明前期定义不充分） |

## §3 方案与决策域

### 3.1 方案讨论确认的闭环机制

用户特别提到"**提供对应的方案……进行方案讨论确认**"——这是产品经理的高频核心工作。方案工作不是"写一版方案发出去"，而是一个**四步闭环**：

```text
 STEP 1          STEP 2           STEP 3          STEP 4
DISCUSS  -----> CONFIRM  ------> FREEZE  ------> CHANGE CONTROL
- present       - align on       - baseline       - any change
  options         decision         versioning       goes through
- tradeoffs     - get explicit   - sign-off        review & impact
- pros/cons       agreement       - communicate     analysis
                                  - distribute
```

| 步骤 | 要点 | 失败代价 |
|:-----|:-----|:---------|
| 1 讨论 | 提供 ≥2 个可选方案，讲清权衡（成本/时间/风险/可扩展性），不预设答案 | 单方案讨论 → 决策质量差 |
| 2 确认 | 与决策者（客户/上级/跨域接口人）逐条对齐，明确"同意什么、不同意什么" | 口头认同 → 后期扯皮 |
| 3 冻结 | 方案版本化、基线化，书面签字，全员知会 | 无基线 → 版本混乱 |
| 4 变更控制 | 任何变更走评审，评估影响面（成本/进度/物料/BOM）后决策 | 随意变更 → BOM/物料连锁返工 |

### 3.2 决策确认的书面化铁律

> **铁律**：方案讨论的结论，必须在 **24 小时内**落成书面记录（会议纪要 + 决策单），包含：决策内容、决策人、决策依据、影响范围、生效版本。
>
> 理由（第一性原理）：研发链条中信息的传递损耗随环节数指数累积。口头决策经过 3 个环节后，信息保真度通常已不足 70% [来源: 知识库 08-21 复用层级分析——研发本质=信息传递非创造，信息损耗即风险]。书面化是把决策信息"固化"为可传递、可追溯、可核对的形态，是硬件研发中 BOM/物料/产线动作的前提。

**硬件场景特别提醒**：方案确认后立即触发两个下游动作，产品经理必须同步跟进：
1. **BOM 冻结** → 物料清单是否与方案一致（方案改了 BOM 没改 = 领料领错）；
2. **物料触发** → 长交期物料是否在方案确认当日就启动采购/领料流程（见 §4.4 提前量）。

### 3.3 输出物与量化指标

**输出物**：方案文档（≥2 版对比）、决策单（书面签字）、基线版本记录、变更评审记录。

**量化指标**：

| 指标 | 定义 | 建议基线 [来源: 经验基线] |
|:-----|:-----|:-----|
| 方案确认周期 | 讨论启动 → 书面确认的天数 | ≤ 7 个工作日（关键路径方案 ≤ 3） |
| 决策返工率 | 确认后因理解偏差返工的方案数 / 总方案数 | ≤ 10% |
| 变更评审及时率 | 变更在影响下游前完成评审的比例 | 100%（硬性） |

## §4 资源获取与保障域（核心）

> 本章是用户痛点的集中区：**"解决项目中需要外采的资源，内部资源需要领料处理，事先处理到位，并配合完成，避免到用的时候，没有对应的物料，形成阻塞。"**

### 4.1 为什么资源保障是一等职责

**第一性原理推导**——从阻塞成本看职责归属：

```text
BLOCKAGE COST MODEL (research pipeline)
  key material missing for T days
  -> the dependent stage stalls for T days
  -> if on critical path, project slips by T days
  -> cost = team_size x man-day cost x T + opportunity cost (late launch)

example: 20-person team, key material missing 5 days
  -> direct cost ~= 20 x 5 = 100 man-days  [Source: model estimate]
  -> if project margin target 180M CNY / 14 months (supernode scale
     [Source: 08-20 SuperPod project plan]), 1 day slip ~= 400K+ CNY
     opportunity cost
```

> 中文释义：关键物料缺位 T 天 → 环节停摆 T 天 → 若处于关键路径则项目整体延期 T 天 → 延期成本 = 团队规模 × 人天成本 × T + 机会成本。示例：20 人团队缺料 5 天 ≈ 100 人天直接成本；超节点量级项目（1.8 亿/14 个月）每延期 1 天机会成本 40+ 万元。

对比：**资源保障的事务成本**（跟单、催料、协调）每天可能只花产品经理 1-2 小时，但**阻塞成本**是数量级更高的。因此：

> **结论**：资源保障不是"事务性杂活"，而是**高杠杆的风险控制工作**——花小成本避免大损失。这正是它必须由产品经理亲自盯（或强主导）的根本原因：产品经理是唯一同时掌握"方案内容（需要什么物料）"和"项目节奏（什么时候必须到位）"两个信息源的角色，信息不对称最小。

### 4.2 资源全景五分类

资源不只"物料"，MECE 分五类：

| 类别 | 内容示例 | 获取难度 | 缺位后果 |
|:-----|:---------|:---------|:---------|
| **物料资源** | 芯片/板卡/线缆/结构件/散热件/电源 | 中-高（交期） | 无法组装、无法测试（直接阻塞） |
| **人力资源** | 研发人力/测试人力/专家支持 | 高（排期） | 任务无人做（隐性阻塞） |
| **设备资源** | 测试设备/示波器/负载仪/调试工具 | 中 | 验证做不了（隐性阻塞） |
| **技术资源** | IP/算法/认证/软件许可/参考设计 | 高 | 方案落地不了 |
| **商务资源** | 供应商关系/样片样机/价格条款/联合开发 | 高 | 无货可采、无价可谈 |

### 4.3 资源获取五通道（MECE）

| 通道 | 适用场景 | 特点 | 典型动作 |
|:-----|:---------|:-----|:---------|
| **外采** | 无库存/需采购的物料、设备 | 周期长（寻源+比价+下单+交期） | 采购申请、比价、下单、交期跟进、验收 |
| **内部领料** | 公司库存/BOM 内物料 | 流程短但受库存约束 | 领料单、BOM 对照、台账登记 |
| **借用/调拨** | 跨项目临时借用、测试设备共享 | 灵活但易失控 | 借用登记、归还跟踪、调拨单 |
| **租赁** | 高频高价设备、短期验证需求 | 成本可控、周期灵活 | 租赁协议、验收标准 |
| **商务合作/共享** | 样片样机、联合开发、资源互换、技术支持 | 杠杆最高，周期最长 | NDA、合作协议、资源互换备忘录 |

> 产品经理的关键能力：**为每类资源选对通道**。该外采的走内部领料会占用项目库存；该商务合作拿样片的走外采会花冤枉钱且周期更长。

### 4.4 外采资源管理全流程

用户痛点的第一半："**解决项目中需要外采的资源**"。完整流程八步：

```text
 NEED ---> SOURCE ---> QUOTE ---> ORDER ---> TRACK ---> RECEIVE ---> CHECK ---> CLOSE
 (spec)    (vendor)   (price)   (PO)      (delivery) (goods)     (QC)      (record)
```

| 步骤 | 产品经理关键动作 | 常见坑 |
|:-----|:-----------------|:-------|
| 1 需求定义 | 明确规格/数量/到货时间窗/质量要求，输出采购申请 | 规格不写全 → 采错 |
| 2 寻源 | 已有供应商池优先；新供应商评估资质/产能/交期 | 只找一家 → 无议价空间 |
| 3 比价议价 | ≥2 家报价对比，关注总成本（含运费/税/售后） | 只看单价 → 隐性成本漏算 |
| 4 下单 | PO 明确交期、付款、违约条款；**交期书面承诺** | 口头交期 → 无追责依据 |
| 5 交期跟进 | 每周催交期；长交期物料提前预警 | 下单后不管 → 到点没货 |
| 6 到货验收 | 数量/型号/外观/一致性核对 | 不验收 → 坏料入库 |
| 7 质量检验 | 按检验标准抽检/全检；不良品走退货换货流程 | 带病上线 → 返工 |
| 8 关闭归档 | 台账登记、价格/交期数据沉淀供复用 | 不归档 → 下次重新踩坑 |

**长交期物料提前量**（硬件研发最关键的时间管理）：

| 物料类别 | 典型交期 [来源: 服务器行业经验基线，具体以供应商确认为准] | 提前启动时机 |
|:---------|:-----|:-----|
| 通用被动件（电阻/电容/连接器） | 2-4 周 | 方案确认后立即 |
| 标准 IC（电源/接口芯片） | 6-12 周 | 方案确认当日 |
| 高端芯片（CPU/GPU/交换芯片） | 12-26 周（甚至更长） | **立项即启动商务接触** |
| 定制件（结构件/定制线缆/PCB） | 4-10 周（含开模） | 设计冻结前即预沟通 |

> **黄金法则**：长交期物料的启动时间 = 方案确认时间，不是"设计完成时间"。等设计全做完再采购，项目已经被交期绑架。

### 4.5 内部领料管理

用户痛点的第二半："**内部资源需要领料处理，事先处理到位**"。

| 环节 | 关键动作 | 失败模式 |
|:-----|:---------|:---------|
| 领料申请 | 按 BOM 核对物料编号/版本/数量，提交领料单 | 凭经验领料 → 版本不符 |
| 库存确认 | 领料前先查库存可用量，缺量提前预警 | 到库房才发现没货 → 现场阻塞 |
| 台账登记 | 领料/归还/调拨/报废全程登记，责任到人 | 无台账 → 物料去向不明 |
| 归还管理 | 借用物料到期提醒、归还检验 | 借用不还 → 他人无法使用 |
| 齐套核对 | 领料后按"打样/测试工单"核对是否齐套 | 缺 1 颗料 → 整板无法焊接 |

**内部领料的三个铁律**：
1. **领料单必须对照 BOM 版本**——方案已变更时，旧版本物料领了就是浪费+阻塞（占库存、占工位）；
2. **先查库存后开单**——把"到库房发现没货"的阻塞前置为"开单时的预警"；
3. **借用类物料必须登记归还**——公共设备/稀缺样片是多人共享资源，不登记=资源黑洞。

### 4.6 物料齐套管理

齐套管理是资源保障域的**枢纽**——它把外采、领料、借用、商务合作四个通道的产出汇总为"能不能开工"的单一判断。

**核心指标：物料齐套率**

```text
KIT COMPLETE RATE = completed-kit work orders / planned work orders x 100%
  - kit complete = all BOM materials for the order are in place & usable
  - baseline: >= 95% on start day  [Source: manufacturing experience baseline]
```

**齐套管理四步法**：

| 步骤 | 动作 | 工具 |
|:-----|:-----|:-----|
| 1 齐套清单 | 按开工节点（打样/试产/测试）生成物料齐套清单 | BOM + 工单 |
| 2 缺口扫描 | 每周扫描缺料项，输出缺料清单（物料/数量/预计到货日/影响） | 齐套台账 |
| 3 预警分级 | 缺料按影响分级：🔴 阻塞关键路径 / 🟡 影响局部 / 🟢 可替代 | 红黄绿看板 |
| 4 补救行动 | 加急采购/替代料评审/内部调拨/降级方案（四选一） | 缺料会议 |

**替代料预案**（防阻塞的重要缓冲）：
- 每类关键物料预留 1-2 个可替代型号（需提前做替代性验证）；
- 替代料验证结论写入齐套清单，缺主料时可直接切换，避免"等料"。

### 4.7 商务级合作管理

用户特别提到"**商务级别的合作**"——这是资源保障中杠杆最高、但最容易被产品经理忽视的一类。

| 合作类型 | 产品经理角色 | 关键动作 |
|:---------|:-------------|:---------|
| **样片/样机获取** | 主导 | 以技术方案换取供应商样片，签样片协议（用途/保密/归还） |
| **战略供应商关系** | 参与/主导 | 联合技术交流、优先供货、价格锁定（LTA） |
| **联合开发** | 参与 | 与供应商共担开发（定制芯片/定制散热），明确 IP 归属 |
| **资源互换** | 主导 | 用我方测试数据/市场渠道换对方技术/物料支持 |
| **技术支持协议** | 主导 | FAE 驻场、调试支持、问题升级通道 |

**商务合作的三个前置**：
1. **NDA 先行**——技术方案讨论前先签保密协议，保护我方核心设计；
2. **书面化**——口头承诺的资源支持必须落到协议/邮件确认（参照 §3.2 铁律）；
3. **时间预留**——商务谈判周期通常 2-4 周 [来源: 经验基线]，关键商务合作须提前一个里程碑启动。

### 4.8 阻塞预防机制

用户的核心诉求："**事先处理到位……避免到用的时候，没有对应的物料，形成阻塞**"。系统性预防三件套：

```text
PREVENTION TRIO
+---------------------------------------------------------+
| 1. LEAD-TIME BUFFER   2. MILESTONE GATE CHECK  3. ESCALATION SLA
|    start at confirm     2 weeks before           RED   24h report
|    written delivery     prototype / pilot        YELLOW 48h report
|    commitment           kit-rate gate check
+---------------------------------------------------------+
```

| 机制 | 具体做法 | 效果 |
|:-----|:---------|:-----|
| **提前量表** | 每类物料建立交期基线，方案确认即触发采购/领料（§4.4） | 把"到时没货"变成"提前备货" |
| **里程碑 Gate** | 打样/试产/测试节点前 2 周做齐套检查，不齐套则升级或调整计划 | 阻塞在开工前暴露 |
| **升级 SLA** | 🔴 阻塞级缺料 24 小时内上报决策层；🟡 影响级 48 小时 | 问题不沉淀、不拖延 |

**阻塞处理五步法**（万一还是阻塞了）：
1. **定性**：缺什么、影响什么、卡在哪个环节；
2. **定量**：影响工期几天、损失多少；
3. **找替代**：替代料/内部调拨/降级方案/部分交付（四选一）；
4. **升级**：超出产品经理权限 → 按 SLA 升级；
5. **复盘**：为什么没预防住 → 补进齐套清单/提前量表（防再犯）。

### 4.9 输出物与量化指标

**输出物**：资源需求清单（按五分类）、采购申请与 PO 台账、领料单与物料台账、齐套清单（含替代料预案）、缺料预警看板、商务合作协议清单、交期基线表。

**量化指标**：

| 指标 | 定义 | 建议基线 [来源: 经验基线] |
|:-----|:-----|:-----|
| 物料齐套率 | 开工日齐套工单占比 | ≥ 95% |
| 缺料阻塞时长 | 因缺料导致的停工天数/月 | ≤ 1 天（目标 0） |
| 长交期物料按时启动率 | 方案确认后 X 天内启动采购的占比 | 100%（硬性） |
| 领料差错率 | 领错料次数 / 领料总次数 | ≤ 1% |
| 商务合作转化率 | 谈成的合作 / 发起的合作 | ≥ 60% |
| 资源到位准时率 | 按时到位的资源项 / 计划资源项 | ≥ 90% |

## §5 项目推进域

### 5.1 与项目管理的边界划分

产品经理 ≠ 项目经理，但两者高度耦合。边界划分（RACI 精神 [来源: 08-20 项目管理方法论 §5.1]）：

| 维度 | 产品经理（A） | 项目经理（R 主导方） |
|:-----|:--------------|:--------------------|
| 范围与价值 | 负责（定义做什么、为什么） | 支持（拆解执行） |
| 进度计划 | 参与（提供关键节点输入） | 负责（排期、跟踪） |
| 资源保障 | **负责**（物料/商务/外部资源） | 支持（人力排期） |
| 风险管理 | 负责业务/资源风险 | 负责执行风险 |
| 质量 | 负责产品定义质量 | 负责交付过程质量 |

> 硬件研发中常见误区：产品经理只管方案，物料/齐套全甩给项目经理或采购 → 信息断层（方案细节在 PM 手里，物料责任在别人手里），这正是"到用的时候没物料"的组织根因。**资源保障责任必须归产品经理**。

### 5.2 核心任务清单

| 任务 | 关键动作 | 衔接文档 |
|:-----|:---------|:---------|
| 里程碑对齐 | 关键节点（TR 评审/打样/试产/测试/发布）与资源计划对齐 | [项目管理方法论](../02_project-management/2026-08-20-server-rd-project-management-methodology.md) |
| 进度跟踪 | 每周核对关键路径进度，识别偏差 | 同上 §5.4 |
| 风险登记 | 业务/资源/技术三类风险登记与应对 | 同上 §8 |
| 问题升级 | 按分级 SLA 升级 | 同上 §9 |
| 交付把关 | 交付物与产品定义一致（需求回溯） | [硬件分层 Check 机制](../02_project-management/2026-08-21-hardware-layered-design-check-mechanism.md) |

## §6 协同与治理域

### 6.1 利益相关者地图

产品经理要持续维护一张利益相关者地图（谁影响项目、谁被项目影响）：

| 角色 | 期望 | 产品经理动作 |
|:-----|:-----|:-------------|
| 决策层 | 及时看到风险/机会 | 定期简报、风险升级 |
| 研发团队 | 清晰的需求/方案/物料 | 需求澄清会、齐套保障 |
| 采购 | 明确规格、充足时间 | 采购申请及时、规格完整 |
| 供应商 | 明确需求、长期合作预期 | 商务对接、信息透明 |
| 客户/市场 | 需求被理解、交付符合预期 | 需求确认、进度同步 |
| 生产/测试 | 齐套物料、可生产性 | 齐套保障、问题响应 |

### 6.2 决策升级机制

```text
ESCALATION LADDER
-----------------
L1 PM self-decide   -- routine resource / minor solution tweaks, same day
L2 dept lead        -- cross-team resources, mid-size changes, within 48h
L3 project decision -- scope / budget / schedule major changes, within 1wk
L4 company level    -- strategic resources, big business deals, per rhythm
```

规则：**该升级不升级 = 隐性阻塞**。阻塞 24 小时后仍无解，必须升级（与 §4.8 SLA 一致）。

## §7 生命周期视角：五阶段任务重心

### 7.1 阶段 × 任务域重心矩阵

硬件研发五阶段，各任务域重心不同（⭐ = 该阶段主导域）：

| 阶段 | A 需求市场 | B 方案决策 | C 资源保障 | D 项目推进 | E 协同治理 |
|:-----|:----------:|:----------:|:----------:|:----------:|:----------:|
| 导入期（立项/TR1） | ⭐⭐ | ⭐ | ⭐ | ⭐ | ⭐ |
| 设计期（TR2-TR3） | ⭐ | ⭐⭐ | ⭐ | ⭐ | ⭐ |
| 打样期（TR4） | | ⭐ | **⭐⭐⭐** | ⭐ | ⭐ |
| 试产期（TR5） | ⭐ | ⭐ | **⭐⭐⭐** | ⭐⭐ | ⭐ |
| 量产/发布（TR6） | ⭐⭐ | | ⭐ | ⭐⭐ | ⭐ |

### 7.2 精力分配建议

| 阶段 | A | B | C | D | E |
|:-----|:-:|:-:|:-:|:-:|:-:|
| 导入期 | 40% | 25% | 10% | 10% | 15% |
| 设计期 | 15% | 45% | 15% | 15% | 10% |
| 打样期 | 5% | 20% | **45%** | 20% | 10% |
| 试产期 | 10% | 15% | **40%** | 25% | 10% |
| 量产期 | 35% | 10% | 20% | 20% | 15% |

> 比例依据 [来源: 经验基线]：硬件研发中打样/试产期是物料消耗与缺料风险的高峰——样板、测试物料、试产备料集中在这个窗口，产品经理 C 域投入高达 40-45%，这是正常且必须的，不是"失职去干杂活"。

|:-------|:-----|:-----|:-----:|

## §9 产品经理自检清单

**每周自检（对应五大域）**：

```text
[ ] A DEMAND : requirement pool updated? prioritization quantified?
[ ] B SOLUTION: open solutions? confirm cycle > 7 days? decision in writing?
[ ] C RESOURCE: materials ready for next week? long-lead items kicked off?
               shortage list maintained? business coop progress tracked?
[ ] D PROJECT : critical-path deviation? risk register updated?
[ ] E GOVERN  : stakeholders synced? anything stuck that should be escalated?
```

**关键节点 Gate 检查（打样/试产/测试前 2 周）**：

```text
[ ] kit complete rate >= 95%? shortage items have recovery plan?
[ ] all long-lead materials in transit or arrived?
[ ] test equipment / headcount scheduled?
[ ] business coop resources (samples / tech support) in place?
[ ] solution baseline frozen? BOM matches solution version?
```

## §10 结论与行动建议

**核心结论**：

1. 产品经理任务 = 五大任务域（需求市场/方案决策/资源保障/项目推进/协同治理），**资源保障与其余四域同等重要**；
2. 资源保障的实质是**高杠杆风险控制**——事务成本低、阻塞成本高，必须产品经理亲自盯（信息不对称最小）；
3. **阻塞预防三件套**（提前量表 + 里程碑 Gate 齐套检查 + 升级 SLA）是避免"到用没料"的系统性手段；
4. 方案确认必须**24h 内书面化**，并同步触发 BOM 冻结与物料启动，否则信息损耗传导至物料层。

**行动建议（落地优先级）**：

| 优先级 | 动作 | 周期 |
|:------:|:-----|:-----|
| P0 | 建立"长交期物料提前量表"，方案确认即触发采购/领料 | 1 周内 |
| P0 | 建立齐套清单 + 缺料预警看板（红黄绿） | 1 周内 |
| P1 | 方案决策书面化模板（决策单）并全员执行 | 2 周内 |
| P1 | 里程碑 Gate 齐套检查制度化（前 2 周） | 1 个月 |
| P2 | 商务合作清单化（样片/战略供应商/联合开发台账） | 1 个月 |
| P2 | 五大域量化指标纳入产品经理考核 | 1 个季度 |
