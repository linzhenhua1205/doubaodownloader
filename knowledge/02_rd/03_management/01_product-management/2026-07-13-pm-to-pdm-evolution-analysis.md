## 执行摘要

**核心判断**: 服务器研发企业从「项目管理」走向「产品研发管理」不是选择题，而是生存题——当GPU代际切换从18个月压缩到12个月、AI服务器营收占比超过50%时，项目管理只能保证"做完"，产品研发管理才能保证"做对"。

### 六大核心结论

| # | 结论 | 一句话 |
|:-:|:-----|:-------|
| 1️⃣ | **项目管理是"事"的维度，产品研发管理是"事×人×钱×战略"的四维** | PM关注时间/成本/范围三角，PDM在此基础上叠加产品战略、平台复用、技术路线、组织能力 |
| 2️⃣ | **服务器研发的特殊性决定了不能照搬消费电子/IPD** | 硬件BOM复杂度是手机的3-5倍、供货周期长6-12个月、客户定制化程度高、生态锁定力强 |
| 3️⃣ | **IPD是当前最适合服务器整机研发的管理体系，但需裁剪** | 完整IPD太重，建议保留核心TR评审+决策门禁，简化阶段活动 |
| 4️⃣ | **演进不是"从A到B"，而是"从A到A+B"** | 项目管理能力保留，叠加产品管理能力——两条腿走路 |
| 5️⃣ | **CBB/平台化复用是降本增效的最强杠杆** | 华为服务器CBB复用率从42%提升到68%，研发周期缩短35%，这就是产品管理的价值 |
| 6️⃣ | **度量体系的转变是关键抓手** | 从"项目按时交付率"到"产品毛利率/技术资产健康度/客户TCO领先度" |

### 演进路线概要

```text
Phase 1                Phase 2                Phase 3                Phase 4
职能型项目管理 ---> 矩阵式项目管理 ---> IPD产品开发管理 ---> 产品平台战略管理
   |                      |                      |                      |
   + 单项目管控           + 多项目并行           + 产品线运营           + 技术+产品双轮驱动
   + 职能孤岛             + 跨职能协调           + TR评审体系           + CBB平台战略
   + 项目经理制           + 弱矩阵/PCT           + 强矩阵/PDT           + 技术规划+产品规划分离
```

## 1. 命题拆解：为什么需要从PM到PDM的演进

### 1.1 两个概念的边界

| 维度 | 项目管理 (PM) | 产品研发管理 (PDM) |
|:-----|:-------------|:------------------|
| **核心对象** | 一个项目（有开始/结束） | 一条产品线（持续运营） |
| **成功标准** | 按时+在预算+达范围 | 毛利率+市场份额+技术领先+客户满意 |
| **时间跨度** | 3-12个月（单项目周期） | 3-5年（产品代际规划） |
| **组织形态** | 项目经理+职能代表 | PDT产品开发团队+IPMT投资决策 |
| **决策焦点** | 资源调度、风险缓解 | 投资取舍、平台战略、技术路线 |
| **核心能力** | WBS、甘特图、风险管理 | 需求管理、TCO分析、路标规划、CBB管理 |
| **输出物** | 项目计划、进度报告 | 产品路标、技术规划、BOM基线、版本策略 |

### 1.2 服务器研发企业为何必须演进

**驱动力一：技术复杂度指数级上升**

```text
2020年服务器: CPU(1-2种) + GPU(1-2种) + 网络(25/100G) + 风冷
                                              v 复杂度×3~5
2026年AI服务器: CPU(4种)×GPU(3家×3代)×Switch(PCIe/NVSwitch/UALink)
               ×网络(400G/800G/1.6T)×散热(风冷/冷板/浸没)
               ×国产化(信创/非信创)
```

一个项目PM无法管理这种组合爆炸——需要产品管理来定义"做什么、不做什么"。

**驱动力二：从"做产品"到"做平台"**

服务器研发已经从单机型开发演进到平台化开发：

- 同一底盘覆盖训练/推理/边缘三种场景
- 同一主板兼容NVIDIA/AMD/昇腾三路GPU
- 同一散热方案适配风冷/液冷双模式

项目管理思维无法处理这种"一鱼多吃"的复杂度。

**驱动力三：投资回报周期拉长，需要长期视角**

| 投入类型 | 回报周期 | 传统PM能否覆盖 |
|:---------|:--------:|:--------------:|
| 单机型开发 | 6-12个月 | ✅ 可以 |
| CBB模块建设 | 18-24个月 | ❌ 项目结束就被遗忘 |
| 技术预研（液冷/224G/CPO） | 24-36个月 | ❌ 没有项目立项 |
| 生态建设（认证/兼容性） | 12-36个月 | ❌ 跨多个项目 |
| 人才培养 | 24-48个月 | ❌ 超出项目范畴 |

> **结论**: 当技术预研周期超过产品开发周期时，项目管理已不能支撑战略决策。

**驱动力四：上市公司财报的技术叙事需求**

详见[研发年度规划深度报告](2026-07-13-rd-annual-planning-guide.md)，财报技术部分需要的是产品战略叙事而非项目执行叙事。

## 2. 核心差异：项目管理 vs 产品研发管理

### 2.1 十维度全景对比

| 对比维度 | 项目管理 (PM) | 产品研发管理 (PDM) | 差距影响 |
|:---------|:-------------|:------------------|:---------|
| **① 时间观** | 项目起止（短期） | 产品全生命周期（长期） | PM易陷入"做完就好"，PDM关注全生命周期TCO |
| **② 成功定义** | 铁三角（时间/成本/范围） | 市场成功+技术领先+财务回报 | 按时交付但产品不赚钱 = PM成功但PDM失败 |
| **③ 需求管理** | 接收需求→执行→交付 | 市场洞察→需求分析→路标规划→版本节奏 | PM被动接需求，PDM主动定义需求 |
| **④ 资源管理** | 按项目分配人力 | 按产品线规划人力+物料+外购 | PM导致资源碎片化，PDM实现资源复用 |
| **⑤ 风险管理** | 项目级风险（进度/质量） | 产品级风险（技术路线/竞争/供应链/地缘） | 供应链地缘风险无法在项目层面管理 |
| **⑥ 质量管理** | 项目验收标准 | 全生命周期质量（设计→制造→现网→退市） | 现网故障率是产品级指标，不是项目级 |
| **⑦ 知识管理** | 项目文档归档 | 技术资产沉淀+CBB复用+经验库 | 项目结束知识蒸发=PDM最大损失 |
| **⑧ 财务视角** | 项目预算控制 | 产品毛利率/ROI/BOM成本/服务成本 | 毛利率管理需要产品全生命周期视角 |
| **⑨ 决策模式** | 项目经理决策+向上汇报 | IPMT投资决策+PDT技术决策+分层授权 | 从"跑审批"到"被授权" |
| **⑩ 组织形态** | 临时项目组 | 常设PDT+技术委员会+产品线 | 从"临时搭班子"到"常设作战单元" |

### 2.2 核心能力差距分析

| 能力领域 | PM应具备 | PDM需新增 | 补齐途径 |
|:---------|:---------|:----------|:---------|
| **战略思维** | 项目目标对齐公司战略 | 制定产品路标、技术规划、平台策略 | 战略规划培训+SP/BP实战 |
| **商业嗅觉** | 关注项目成本 | 关注TCO/毛利率/竞争定价 | 轮岗到市场/销售 |
| **技术视野** | 理解本项目的技术方案 | 理解行业技术趋势/多方案对比 | 技术委员会参与+行业调研 |
| **跨域协调** | 协调研发内部各专业 | 协调研发+供应链+市场+服务+财务 | PDT轮值经验 |
| **投资思维** | 控制项目预算 | 评估ROI、做投资优先级排序 | IPMT评审参与 |

## 3. 四阶段演进模型

### 📊 阶段总览

```text
        复杂度/收益
            ^
  Phase 4   |  🔷 产品平台战略管理
            |    + CBB复用率>60%
            |    + 技术规划领先2代
            |    + 产品毛利率>25%
            |
  Phase 3   |    🔶 IPD产品开发管理
            |      + TR评审体系完善
            |      + PDT常设运作
            |      + 路标准时率>85%
            |
  Phase 2   |      🔶 矩阵式项目管理
            |        + PMO体系建立
            |        + 多项目并行管理
            |        + 资源池化
            |
  Phase 1   |        🔴 职能型项目管理
            |          + 单项目管控
            |          + 职能孤岛
            +--------------------------------> 时间
```

### Phase 1: 职能型项目管理

**特征**:

- 研发按职能划分（硬件部、软件部、测试部、结构部）
- 每个部门各自管项目，项目经理只是"跟单员"
- 无统一项目管理流程，各职能各自为政
- 沟通靠会议，决策靠汇报

**适用场景**: 初创期、单品研发、年营收<10亿的服务器公司

**典型问题**:

| 问题 | 表现 | 根因 |
|:-----|:-----|:-----|
| 接口扯皮 | 硬件等固件、软件等硬件 | 无统一计划和端到端owner |
| 重复劳动 | 不同项目做同样的CBB | 无CBB识别和复用机制 |
| 信息孤岛 | 采购不知道研发选型、市场不知道研发进展 | 无跨职能信息共享机制 |
| 救火文化 | 总是在赶项目deadline | 无缓冲管理和风险预警 |

**退出条件**: 同时并行项目数>3, 或年研发投入>2亿

### Phase 2: 矩阵式项目管理

**特征**:

- 建立PMO（项目管理办公室）
- 项目经理从"跟单员"升级为"项目owner"
- 推行标准项目管理流程（立项→计划→执行→验收→结项）
- 初步建立资源协调机制

**关键建设**:

| 建设项 | 内容 | 验收标准 |
|:-------|:-----|:---------|
| PMO组织 | 3-5人专职PMO，制定流程/工具/模板 | PMO运作满6个月 |
| 项目分级 | A/B/C三级管理，不同级别不同审批 | 分级规则书面化 |
| 资源池化 | 建立研发资源池，按项目优先级分配 | 资源冲突仲裁机制运作 |
| 进度可视化 | 建立项目仪表盘（里程碑/风险/资源） | 管理层每周查看 |
| 结项复盘 | 每个项目结项做复盘并沉淀经验 | 复盘报告归档率>90% |

**典型弱点**:

- PM有责无权，协调困难
- 仍以项目为单位，产品规划缺失
- TR评审流于形式

**退出条件**: 年营收>20亿, 产品线>3条, 并行项目>10个

### Phase 3: IPD产品开发管理 ⭐（推荐主流）

**特征**:

- 引入IPD（集成产品开发）流程框架
- 设立PDT（产品开发团队）常设运作
- 建立IPMT（集成组合管理团队）投资决策机制
- TR评审+决策门禁成为核心治理机制
- 产品路标正式化

**IPD核心机制**:

```text
IPMT (投资决策)              PDT (产品开发)
    |                            |
    +- 产品路标审批              +- 产品规划与需求管理
    +- 投资优先级排序            +- 技术方案决策
    +- TR1/TR5/TR6决策门禁      +- TR2/TR3/TR4技术评审
    +- 资源调配决策              +- 跨域协调
    +- 产品生命周期决策          +- 交付与质量保证

        决策分离                  执行整合
       (做什么/不做什么)         (怎么做好)
```

**PDT组织结构**：

```text
                    PDT Leader (产品经理)
                 +-------+-------+
              +----+ +----+ +----+ +----+ +----+ +----+
              | HW | | SW | | ME | | TH | | SCM| | QA |
              +----+ +----+ +----+ +----+ +----+ +----+
              (各领域代表·全职或兼职)
```

**服务器IPD的7个TR节点适配**（与业界标准IPD的差异标红）：

| IPD标准节点 | 服务器适配名 | 核心交付物 | 与消费电子IPD差异 |
|:-----------|:-----------|:-----------|:-----------------|
| CDCP (Concept) | **TR1** | 产品需求规格书(PRD)、市场评估、竞争分析 | 增加国产化替代评估、GPU生态兼容性分析 |

## 4. 服务器研发领域的十个关键关注点

### 🎯 关注点一：硬件-固件-软件的三体并行

服务器是典型的**三域并行开发**产品，这是与纯软件/纯硬件产品最大的区别。

```text
硬件 (HW)               固件 (FW/BMC)            软件 (SW/Driver)
   |                         |                         |
TR1| 架构定义                |                         |
   +--- 系统架构 ------------+---------- 软件架构 ---- |
TR2| 器件选型                |                         |
TR3| 原理图设计              |                         |
   |                         +--- BMC方案 ------------ |
TR4| Layout                  +--- 驱动开发 ------------ |
   |                         |    (需Early Silicon)    |
TR4A| PCB出带  --------------+                         |
   |                         |                         |
TR5| 样板焊接 ---------------+--- 联调 ---------------- |
   |     ^ 三体汇合          |       ^ 三域联调是最大瓶颈   |
TR6| 量产                    |                         |
```

**管理要点**:

- 三域计划必须对联（用统一WBS串联），不能独立排期
- **Early Prototyping**: 固件/软件开发不可等硬件到手——用FPGA原型/SIMICS仿真提前启动
- **联调窗口预留**: 从样板到手到TR5，至少预留6-8周（比消费电子长2倍）

### 🎯 关注点二：多平台并行的资源竞争

| 资源类型 | 典型瓶颈 | 管理方法 | 案例 |
|:---------|:---------|:---------|:-----|
| **SI/PI仿真工程师** | 高速信号仿真周期占Layout前50%时间 | 平台级仿真复用+早期介入 | 华为将仿真前移到TR2而非TR4 |
| **散热工程师** | 液冷方案每机型需2-3周CFD仿真 | 建立散热库(风冷/冷板/浸没通用模型) | SuperMicro液冷平台化，30→7天 |
| **Layout资源** | 8层以上PCB，从布线到出带8-12周 | 平台化Layout（同一布局覆盖多配置） | 浪潮NVIDIA平台统一Layout减时40% |
| **测试资源** | GPU/CPU/互联全兼容测试耗时 | 自动化测试平台+并行测试 | 联想LENOVO AI测试工厂 |

### 🎯 关注点三：供应链深度耦合

服务器研发与消费电子的根本区别——**研发决策直接锁定供应链**：

```text
CPU/GPU选型 ---> 锁定制程产能 ---> 影响12-24个月供货
      |
      +-- 散热方案 ---> CDU/冷板供应商锁定
      +-- PCB层数 ---> PCB供应商产能锁定
      +-- 连接器选型 ---> 交期锁定（AI服务器连接器交期>20周）
      +-- 电源选型 ---> 800V HVDC/PSU供应商锁定
```

**管理要点**:

- PDT中必须有SCM代表（全职或半职）
- 选型评审需含**供货风险评估**（供应商产能、地缘政治、二级物料风险）
- 建立"主供+备供"策略，备供需有实际验证而非纸面兼容

### 🎯 关注点四：客户定制化 vs 平台化平衡

服务器行业有两个看似矛盾的需求：

| 维度 | 平台化（降本） | 定制化（赢单） |
|:-----|:--------------|:--------------|
| **驱动力** | 规模效应、CBB复用、研发效率 | 客户差异化需求、赢单率 |
| **管理手段** | 产品路标、平台版本、配置矩阵 | 客户项目立项、定制开发、变更管理 |
| **冲突点** | 定制过多→CBB失效→成本上升 | 过度平台→丢失订单→份额下降 |
| **平衡策略** | **80/20法则**: 80%平台化+20%定制化接口 | 配置器管理+服务化定制 |

**实践参考**: 浪潮的"双轨策略"：

- **技术驱动轨**（平台化）: 标准化产品线，按季度发布，走IPD完整流程
- **市场驱动轨**（定制化）: 客户项目独立PDT，关键决策加速，TR合并

> 详见[全周期管理报告](02_rd/03_management/02_project-management/2026-06-04-doubao-full-cycle-management-report.md#11-技术驱动与市场驱动双轨策略)

### 🎯 关注点五：技术预研与产品开发的分离

服务器行业的最大管理陷阱——**把技术探索当产品开发管**：

| 活动 | 技术预研 | 产品开发 |
|:-----|:---------|:---------|
| **目标** | 验证技术可行性、降低风险 | 交付可量产产品 |
| **不确定性** | 高（30-70%可能失败） | 低（<10%未预期问题） |
| **管理方式** | 探索式、迭代式、无硬deadline | 计划驱动、里程碑管控 |
| **预算来源** | 研发费用中的预研预算 | 产品开发预算 |
| **结果要求** | Know-how、专利、POC原型 | 可量产BOM、SOP、认证 |
| **生命周期** | 完成预研即结束（成果转入产品线） | 持续到产品EOL |

**管理方法**: 设立**独立技术预研预算**（通常为研发总预算的10-15%），由CTO/技术委员会直接管理，不纳入PDT考核。

### 🎯 关注点六：GPU/CPU选型的生态锁定效应

CPU/GPU选型一旦锁定，影响整个产品族的软件栈、散热方案、供电方案、互联拓扑，切换成本极高：

| 锁定层次 | 切换成本 | 举例 |
|:---------|:--------:|:-----|
| **硬件接口** | 中等（重新Layout+结构适配） | NVIDIA H100→H200 同平台兼容 |
| **散热方案** | 高（TDP变化需重新CFD仿真） | H100 700W→B200 1000W 需液冷升级 |
| **供电方案** | 高（VR/PSU重新选型） | 升腾910B 310W→910C 450W |
| **固件/驱动** | 极高（BMC/BIOS/Sensor全量重适配） | NVIDIA→AMD GPU 驱动不兼容 |
| **软件生态** | 极高（CUDA→ROCm→CANN迁移） | 客户模型需重新适配优化 |
| **认证矩阵** | 高（OS/VM/Container全量重测） | 针对新GPU的所有OS兼容性测试 |

**管理要点**:

- 每个GPU/CPU选型必须做**生态锁定成本评估**（含切换成本、迁移周期）
- 主芯片选型决策应由CTO/技术委员会做，不能由单个PDT决定
- 建立芯片路线图跟踪机制，每年更新

### 🎯 关注点七：质量与成本的源头管理

服务器研发中，**80%的质量问题和成本在选型/设计阶段就已注定**：

```text
成本锁定曲线（服务器行业）:
成本锁定比例
    ^
100%|                                    ╱ 设计阶段决定80%成本
    |                                 ╱
 80%|                              ╱
    |                           ╱
 60%|                        ╱
    |                     ╱
 40%|                  ╱
    |               ╱
 20%|            ╱
    |         ╱
  0%|------╱---------------------------> 时间
    TR1  TR2  TR3  TR4  TR5  TR6  量产
```

**管理要点**:

- TR1-TR3阶段必须做**成本可行性分析**（BOM Target vs Should Cost）
- DFX评审必须前置到TR3而非TR5（DFM/DFT/DFS/DFR）
- 建立**成本基线库**：历史机型BOM成本、部件价格趋势、替代方案对比

> 详见[选型与报价关系深度分析](./2026-07-13-selection-pricing-relationship-deep-analysis.md)

### 🎯 关注点八：认证与合规的全球化管理

| 认证类型 | 覆盖市场 | 周期 | 关键点 |
|:---------|:---------|:----:|:-------|
| **3C/CCC** | 中国 | 8-12周 | 强制，新平台需重做 |
| **CE** | 欧洲 | 8-16周 | 含EMC+LVD+RED |
| **FCC** | 美国 | 8-12周 | 含Class A/B |
| **UL/ETL** | 北美 | 12-20周 | 安规+能效 |
| **CB** | 全球互认 | 12-16周 | 核心安规 |
| **信创** | 中国政企 | 8-24周 | 国产化率+安全审查 |

**管理要点**:

- 认证规划必须在**TR1**启动（需求分析阶段）
- 建立认证日历，与产品路标对齐
- 注意GPU/CPU变更可能触发认证重做
- 信创认证需提前与工信部/评测机构沟通

### 🎯 关注点九：版本管理与配置矩阵

服务器不同于消费电子的一点——**每一台机器可以有不同的配置组合**：

```text
同一机型 SKU数量 = GPU种数 × CPU种数 × 内存容量 × 存储容量 × 网络接口 × 散热方式
```

假设: 3×2×3×3×4×2 = **432种SKU**

**管理要点**:

- 建立**配置器系统**（BOM自动生成+价格自动计算+兼容性检查）
- 版本管理需覆盖：硬件版本→固件版本→驱动版本→BOM版本→配置文件版本
- 每个交付物需有**版本兼容矩阵**（哪个BMC版本配哪个BIOS版本配哪个Driver版本）
- SaaS化产品需增加软件版本管理（FW Over-The-Air更新策略）

### 🎯 关注点十：研发投入的"三段论"配比

根据[年度规划分析](2026-07-13-rd-annual-planning-guide.md)，研发预算应分三块管理：

| 预算类型 | 占比 | 管理方式 | 考核指标 |
|:---------|:----:|:---------|:---------|
| **必选研发**（已立项产品） | 60-70% | PDT预算，按项目里程碑释放 | 产品毛利率/TTM/质量 |
| **战略研发**（下一代平台/技术） | 20-30% | CTO预算，按技术路线图释放 | 技术资产积累/专利/原型 |
| **探索研发**（前沿/不确定性高） | 5-15% | 创新基金，按阶段评审释放 | Know-how/论文/人才储备 |

**演进影响**: 从PM到PDM，必须建立这三类预算的独立管理机制——项目管理只能管"必选研发"。

## 5. 研发过程管理标准全景

### 5.1 四大标准对比总览

| 标准 | 起源 | 核心哲学 | 适用阶段 | 服务器适用度 | 主要成本 |
|:-----|:-----|:---------|:---------|:-----------:|:---------|
| **IPD** | IBM→华为 | 投资组合管理+结构化流程 | 全生命周期 | ⭐⭐⭐⭐⭐ | 高（流程/组织/IT） |
| **CMMI** | 卡内基梅隆SEI | 过程成熟度+持续改进 | 研发过程 | ⭐⭐⭐⭐ | 中（文档/评审/认证） |
| **SAFe/敏捷** | 软件行业 | 迭代交付+价值驱动 | 软件/固件 | ⭐⭐⭐ | 中（培训/工具） |
| **V-Model** | 航空航天 | 验证与确认 | 质量保证 | ⭐⭐⭐ | 低（文档/测试） |

### 5.2 IPD — 集成产品开发（最推荐，已标准）

> 💡 **如果你只能选一个标准，选IPD。** 华为30年验证、服务器行业主流、覆盖全生命周期。

**核心结构**:

```text
+-----------------------------------------------------+
|                  IPMT (投资决策)                       |
|  产品路标 · 投资取舍 · 资源分配 · 生命周期决策      |
+-----------------------------------------------------+
           | 决策 ^               v 执行
+-----------------------------------------------------+
|                  PDT (产品开发)                        |
|  HW/FW/SW/ME/TH/SCM/QA + 市场/服务代表               |
+-----------------------------------------------------+
           | 输入 ^               v 输出
+-----------------------------------------------------+
|              功能部门 (能力中心)                        |
|   技术预研 · CBB开发 · 平台建设 · 人才培养           |
+-----------------------------------------------------+
```

**IPD核心流程（7个TR + 4个DCP）**:

```text
概念阶段 --> 计划阶段 --> 开发阶段 --> 验证阶段 --> 量产阶段 --> 生命周期
   |           |           |           |           |           |
  CDCP        PDCP        TR3/4       TR5         TR6        EOL DCP
 (概念决策)   (计划决策)   (技术评审)  (发布决策)  (量产决策)  (退市决策)
```

**服务器IPD的定制要点**:

1. **TR4A节点保留不变**——PCB出带是服务器研发的关键分水岭
2. **TR5需增加MLPerf/SPEC基准测试**——性能基线是客户验收的前置条件
3. **TR6需确认GPU/CPU长期供货承诺**——主芯片交期>20周
4. **EOL DCP需提前12个月启动**——备品备件+客户迁移计划

**IPD实施条件**:

| 条件 | 要求 | 说明 |
|:-----|:-----|:------|
| 年营收规模 | >20亿 | IPD固定成本需要摊薄 |
| 产品线数量 | ≥3条 | 单产品线不需要IPD |
| 组织准备度 | 高层共识+中层理解 | IPD是一把手工程 |
| IT系统支持 | PLM/ERP/配置器 | 流程不能纯手工 |
| 推行周期 | 18-24个月 | 不能急于求成 |

> 完整的IPD TR评审要素与决策门禁清单见[全周期管理报告](02_rd/03_management/02_project-management/2026-06-04-doubao-full-cycle-management-report.md#3-tr评审要素与决策门禁)

### 5.3 CMMI — 能力成熟度模型集成

**适用场景**: 需要对外展示研发管理能力（如政府/军工客户投标）、或研发过程规范性差需系统提升。

**五级成熟度**:

```text
Level 1: 初始级 ---> Level 2: 已管理 ---> Level 3: 已定义 ---> Level 4: 量化管理 ---> Level 5: 优化级
  无序           | 项目级有流程    | 组织级有标准    | 数据驱动决策   | 持续改进
  救火文化       | 需求/计划/质量  | 组织资产库      | 统计过程控制   | 根因预防
                 | 配置/供应商管理 | 培训/评审       | 量化目标管理   | 技术革新
```

**服务器企业的CMMI关键过程域**:

| 过程域 (PA) | 服务器场景价值 | 实施难度 |
|:------------|:--------------|:--------:|
| **需求开发 (RD)** | GPU/CPU需求追溯、兼容性需求 | ⭐⭐⭐ |
| **技术解决方案 (TS)** | 架构设计、CBB复用 | ⭐⭐⭐⭐ |
| **产品集成 (PI)** | 硬件-固件-软件三域联调 | ⭐⭐⭐⭐⭐ |
| **验证 (VER)** | 测试覆盖、自动化测试 | ⭐⭐⭐ |
| **确认 (VAL)** | 客户验收、场景测试、性能基线 | ⭐⭐⭐ |
| **配置管理 (CM)** | BOM/Git/版本矩阵 | ⭐⭐ |
| **供应商协议管理 (SAM)** | GPU/CPU/液冷供应商管理 | ⭐⭐⭐ |
| **度量与分析 (MA)** | 研发效能、质量度量 | ⭐⭐ |

**IPD vs CMMI vs 敏捷的关系**:

```text
          IPD（战略层）
     +----------------------+
     | 做什么/不做什么       |
     | 产品路标/投资决策     |
     +----------+-----------+
                | 流程框架
     +----------+-----------+
     |      CMMI (过程层)    |
     | 怎么做才规范/可度量    |
     +----------+-----------+
                | 执行方法
     +----------+-----------+
     | 敏捷·Scrum·SAFe(执行层)|
     | 怎么快/怎么灵活       |
     +----------------------+
```

**三者在服务器企业的部署策略**:

- **IPD框架**: 全职导入，覆盖全部产品线
- **CMMI**: 选择性认证（L2-L3），做政府/军工客户投标资质
- **敏捷**: 仅在SW/FW团队推行（Scrum + 双周迭代），HW继续按V-Model

### 5.4 SAFe/敏捷 — 规模化敏捷框架

**适用场景**: 固件/软件团队迭代开发，硬件团队需保持瀑布模型

**硬件-敏捷适配的挑战**:

| 敏捷原则 | 硬件适用性 | 原因 | 应对策略 |
|:---------|:--------:|:-----|:---------|
| 短迭代（2周） | ❌ | PCB Layout周期8-12周 | HW用"里程碑+阶段门"替代迭代 |
| 持续交付 | ❌ | 硬件不能"持续交付" | 用Engineering Build/Sample替代 |
| 自组织团队 | ⚠️ 部分适用 | 跨域协调需要明确接口 | PDT+Scrum of Scrums |
| 面对面对话 | ✅ | 硬件-固件联调需要 | Co-located PDT |
| 可工作软件 | ⚠️ 改为"可通过设计评审" | 硬件不能Demo | TR评审演示替代Sprint Review |

**推荐模式: Hybrid Agile (SAFe for Hardware)**:

- HW团队: 保持阶段门+里程碑管理，但采用Backlog管理需求和定期复盘
- FW/SW团队: Scrum + 双周Sprint
- 两团队通过**PI Planning（季度规划）** 对齐节奏

### 5.5 V-Model — 验证与确认模型

**适用场景**: 高可靠性要求的服务器产品（金融/电信级）

**V-Model结构**:

```text
需求分析 -------------------> 验收测试
   |                            ^
   |  系统设计 ---------------> 系统测试
   |     |                        ^
   |     |  概要设计 -----------> 集成测试
   |     |     |                    ^
   |     |     |  详细设计 -------> 单元测试
   +-----+-----+-----+
         (左侧: 设计)     (右侧: 验证)
```

**服务器V-Model的"加厚"**:

| V阶段 | 服务器特有活动 | 输出物 |
|:------|:--------------|:-------|
| 需求分析 | GPU/CPU兼容性需求、散热TDP需求、认证合规需求 | 需求追溯矩阵(RTM) |
| 系统设计 | 互联拓扑、散热分区、供电架构、管理架构 | HLD + 跨域评审纪要 |
| 概要设计 | 各子系统设计、DFX规划、测试策略 | 概要设计规范 |
| 详细设计 | 原理图、Layout、结构堆叠、散热CFD | 设计文件+BOM初版 |
| 单元测试 | 各部件功能验证、SI/PI仿真验证 | 仿真报告 |
| 集成测试 | HW+FW+SW三域联调 | 集成测试报告 |
| 系统测试 | 全功能+性能+可靠性+兼容性 | 系统测试报告 |
| 验收测试 | 客户场景+MLPerf/SPEC+TCO验证 | 验收报告 |

### 5.6 各标准在服务器企业的组合推荐

```text
+-----------------------------------------------------------------+

|  战略层     IPD        全产品线      IPMT投资决策                |
```

## 6. 业界主要运作模式

### 6.1 对比总览

| 维度 | 华为(IPD标杆) | 浪潮(矩阵优化) | SuperMicro(ODM模式) | Dell(集成模式) |
|:-----|:------------|:--------------|:------------------|:--------------|
| **管理框架** | IPD完整版 | 轻量IPD+双轨 | 项目制+快速迭代 | IPD企业版 |
| **组织形态** | 强矩阵(PDT常设) | 弱矩阵(PM+职能) | 项目组制 | 产品线制 |
| **产品策略** | 全栈自研 | 平台化+定制 | Building Block | 全品类覆盖 |
| **研发重心** | 芯片→系统→软件 | 系统集成+液冷 | ODM/OEM定制 | 供应链管理 |
| **IPD适配** | 原汁原味 | 裁剪至6个TR | 简化+并行 | 完整+数字化 |
| **CBB复用率** | 68%+ | 55%+ | 70%+（ODM特性） | 60%+ |
| **典型TTM** | 12-18个月 | 6-12个月 | 3-6个月 | 9-15个月 |
| **适用企业** | >100亿大型 | 20-100亿中型 | 服务型/ODM | 综合型 |

### 6.2 华为：IPD原教旨主义者

**核心特征**:

1. **IPD是组织DNA**：从1999年IBM导入至今，IPD已融入华为每一个管理毛孔
2. **IPMT+PDT双层治理**：IPMT做投资决策，PDT做产品开发，技术决策由系统架构师负责
3. **TR评审六门**：CDCP→PDCP→TR1→TR4→TR5→ADCP→EOL DCP（七节点，六门禁）
4. **技术-产品分离**：2012实验室做技术预研，产品线做产品开发

**华为IPD在服务器领域的特殊实践**:

| 实践 | 操作 | 效果 |
|:-----|:-----|:------|
| **战略KPI** | 服务器产品线考核「市场份额×毛利率×技术先进性」三维 | 避免盲目冲量 |
| **向下集成** | 服务器+存储+交换机+云平台统一管理（eSight/FusionDirector） | 提升客单价 |
| **向上锁芯** | 鲲鹏+昇腾自研芯片锁定生态 | 供应链安全+毛利提升 |
| **全球化IPD** | 欧洲/东南亚/中东各区域分PDT，匹配本地合规和认证 | 本地化响应 |

**借鉴价值**:

- ✅ IPD流程体系是业界最优实践
- ✅ 技术-产品分离机制值得学习
- ❌ 完整IPD过重，小型企业不建议照搬
- ❌ IPD流程走完需大量文档维护，需IT系统支撑

### 6.3 浪潮：轻量IPD+双轨策略

**核心特征**:

1. **IPD裁剪版**：保留IPD核心的TR评审和决策门禁，简化阶段活动和管理文档
2. **双轨策略**：技术驱动轨(平台化/标准产品) + 市场驱动轨(客户定制/快速响应)
3. **80/20平台化**：80%的模块复用+20%的差异化接口，支撑JDM/ODM定制

**浪潮双轨运作**:

```text
                        IPMT (高层决策)
                     +---------+---------+
                技术驱动轨             市场驱动轨
              (平台产品线)            (客户项目线)
                    |                      |
              PDT-主力机型           PDT-客户项目
              +----+----+           +----+----+
              |    |    |           |    |    |
            HW FE  SW   |         HW FE  SW   |
            SCM  QA    ME        SCM  QA     ME
                    |                      |
            产品路标: 季度发布       按客户需求: 定制交付
            TR评审: 完整6门                TR合并: 4门
            预算: 年度规划              预算: 项目制
```

**借鉴价值**:

- ✅ 双轨策略平衡了平台化和定制化的矛盾
- ✅ 轻量IPD适合20-100亿规模的服务器企业
- ✅ JDM模式贴近客户需求同时保持CBB复用
- ❌ 弱矩阵下PM协调能力要求高
- ❌ 双轨资源冲突需要高层持续介入

### 6.4 SuperMicro：Building Block的极致

**核心特征**:

1. **极致模块化**：主板/电源/风扇/硬盘/扩展卡全部标准化模块，像搭积木一样组合
2. **超快TTM**：新平台从概念到量产3-6个月（行业平均9-18个月）
3. **ODM/OEM双模**：既做自有品牌(Supermicro)，也为云厂商做JDM定制
4. **液冷平台化**：2024年起全系液冷天然兼容，无需额外适配

**Building Block模式解析**:

```text
Supermicro的模块库:
+--------------+  +--------------+  +--------------+
|  主板模块     |  |  电源模块     |  |  散热模块     |
| - X13/X14    |  | - 800W/1.6kW |  | - 风冷        |
| - H13/H14    |  | - 冗余/非冗余 |  | - 冷板液冷    |
| - BigTwin    |  | - 钛金/白金  |  | - 浸没液冷    |
+--------------+  +--------------+  +--------------+
+--------------+  +--------------+  +--------------+
|  网络模块     |  |  存储模块     |  |  扩展模块     |
| - 25G/100G   |  | - NVMe/U.2   |  | - PCIe槽位   |
| - OCP 3.0    |  | - E1.S/E3.S  |  | - GPU支架    |
| - 双/四口     |  | - 全闪/混闪  |  | - AIOM卡     |
+--------------+  +--------------+  +--------------+
          v 按需组合
+--------------------------------------------------+
|         93% 通过模块组合完成，无需新设计           |
|         7% 按客户需求做定制化修改                  |
+--------------------------------------------------+
```

**借鉴价值**:

- ✅ Building Block理念是CBB复用的最高境界
- ✅ 3-6个月TTM是行业标杆
- ❌ 需要极高的标准化能力和大量的模块预研投入
- ❌ 差异化空间小，高端定制化需求难以满足

### 6.5 Dell：全品类集成的数字化IPD

**核心特征**:

1. **PowerEdge旗舰管理**：Dell的PowerEdge 18代(2026)是行业最成熟的产品线管理案例
2. **数字化IPD**：IT系统深度嵌入IPD流程，PLM/ERP/配置器/CRM全链路打通
3. **供应链即研发**：Dell的供应链管理能力行业第一，研发-采购-生产一体化
4. **OpenManage生态**：从BMC到Data Center管理平台的全栈软件生态

**借鉴价值**:

- ✅ 数字化IPD降低流程管理成本（系统替代人工）
- ✅ 供应链管理+研发一体化是最好的降本手段
- ❌ 需要大量IT投入（Dell每年IT预算>10亿美元）
- ❌ 组织的供应链导向可能削弱技术创新

### 6.6 四家模式的适用性判断

| 企业特征 | 推荐模式 | 不推荐模式 |
|:---------|:---------|:-----------|
| 年营收>100亿、多产品线 | 华为IPD完整版 | SuperMicro模块化（太轻） |
| 年营收20-100亿、2-3条产品线 | 浪潮轻量IPD+双轨 | Dell数字IPD（太重） |
| ODM/JDM为主、快速响应 | SuperMicro Building Block | 华为IPD（太慢） |
| 全品类覆盖、供应链驱动 | Dell集成IPD | — |
| 初创期、单产品线 | 项目制（Phase 1-2） | 任何IPD（过早） |

## 9. 常见失败模式与反模式

### 9.1 五大失败模式

| # | 失败模式 | 表现 | 根因 | 预防措施 |
|:-:|:---------|:-----|:-----|:---------|
| **F1** | IPD僵化症 | 流程跑死业务，评审会多于干活时间 | 照搬华为IPD不裁剪 | 按企业规模裁剪TR数量，小企业4个TR足够 |
| **F2** | 有PDT无决策 | PDT Leader有责无权，IPMT形同虚设 | 高层不授权、不放权 | IPMT必须做真决策（砍项目/调资源） |
| **F3** | 度量滥造 | 堆砌指标但无数据、无行动 | 为度量而度量，不关联业务决策 | 从20个核心开始，每季度review |
| **F4** | 双轨变单轨 | 市场驱动压倒技术驱动，全部做定制 | 短期业绩压力+管理层短视 | 设置独立预研预算保护技术轨 |
| **F5** | 产品经理缺失 | PDT Leader由技术负责人兼任 | 认为"产品经理不需要" | 外招/内部培养专职产品经理 |

### 9.2 十大反模式

| # | 反模式 | 为什么错 | 正确做法 |
|:-:|:-------|:---------|:---------|
| 1 | "我们有项目经理了，不需要产品经理" | 项目经理管进度，产品经理管方向 | 两者互补，缺一不可 |
| 2 | "IPD就是多开会多评审" | IPD核心是投资决策，不是流程 | 评审不是目的，决策才是 |
| 3 | "CBB就是复制粘贴" | CBB需要专门投入维护和管理 | CBB库需要专人管理和版本控制 |
| 4 | "敏捷就是没有文档" | 硬件的敏捷是里程碑压缩，不是无文档 | 核心设计文档必须有 |
| 5 | "产品路标就是画饼" | 路标要有资源匹配和退出机制 | 每个路标项目有预算和owner |
| 6 | "TR评审走形式就行" | 评审不认真=灾难提前 | TR评审不合格可以叫停项目 |
| 7 | "先干了再补流程" | 硬件行业补流程成本极高 | 前松后紧不如前紧后松 |
| 8 | "客户定制化也可以走IPD" | 定制化项目需要加速流程 | 双轨策略：定制化走快车道 |
| 9 | "研发效能=代码行数" | 代码行数误导产出判断 | 用用户价值/毛利率/客户满意度替代 |
| 10 | "度量指标越多越好" | 20+N个指标=啥都看不清楚 | 聚焦10-15个关键指标 |

### 9.3 演进中的常见陷阱

| 陷阱 | 时间点 | 识别信号 | 化解方法 |
|:-----|:-------|:---------|:---------|
| **兴趣衰减** | 第6-9个月 | IPD会议出席率下降 | 高管站台+快速胜利宣传 |
| **流程反弹** | 第9-15个月 | "流程太麻烦"抱怨增多 | 裁剪优化+工具化降低负担 |

| **人员流失** | 第24个月+ | PDT Leader/关键角色离职 | 培养梯队+知识沉淀 |

### 10.2 董事会需要知道的五件事

1. **从PM到PDM的演进是投资决策机制的升级**：IPMT让董事会/管理层在"产品做什么/不做什么"上有真正的决策权，而非被动接受研发提报的项目

2. **前18个月只看过程不看结果**：第一年聚焦流程建设+组织调整，第二年度量开始显效，第三年才能看到毛利率/TTM/TCO的系统性改善

3. **最大风险不是新体系太慢，而是旧体系拖累**：并行运行旧+新两套体系6-9个月是正常过渡期，但超过12个月就会陷入"两不靠"

4. **CBB复用的收益是指数级的**：每提升10%的CBB复用率，研发人力投入可降低8-12%，BOM成本可降低3-5%

5. **这是"一把手工程"**：IPD/PDM推进需要CEO持续关注，不能完全授权给CTO或研发VP——投资决策本身就应该是CEO的核心职责

## 11. 标杆企业深度案例分析：浪潮信息的 IPD 演进之路

> **为什么选浪潮？** 浪潮是中国最大的服务器厂商（2025年市场份额~35%），年营收~800亿，研发投入~50亿/年，经历了从"项目制→矩阵式→轻量IPD→双轨策略"的完整演进路径，对年营收20-200亿的服务器企业最具参考价值。

### 11.1 企业背景与演进阶段

#### 时间线总览

| 时间 | 阶段 | 营收规模 | 核心变化 | 关键事件 |
|:----|:-----|:--------:|:---------|:---------|
| 2005-2010 | 职能型项目制 | < 50亿 | 研发按硬件/软件/测试划分，项目经理跟单 | 开始做服务器ODM |
| 2010-2015 | 矩阵式管理 | 50-200亿 | 建立PMO，推行项目管理流程 | 进入互联网大客户市场 |
| 2015-2020 | 轻量IPD导入 | 200-500亿 | 引入裁剪版IPD，6个TR节点，3个决策门禁 | 推出JDM模式（联合开发） |
| 2020-2025 | 双轨策略深化 | 500-800亿+ | 技术驱动轨+市场驱动轨，CBB复用率从35%→55%+ | AI服务器爆发，JDM收入占比>40% |

#### 各阶段关键数据

| 指标 | 2010 (矩阵式早期) | 2015 (PMO成熟) | 2020 (IPD导入) | 2025 (双轨运作) |
|:----|:---------------:|:--------------:|:-------------:|:--------------:|
| 年营收(¥亿) | 60 | 180 | 480 | 800+ |
| 产品线数量 | 2 | 4 | 6 | 8+ |
| 并行项目数 | 5-10 | 15-25 | 30-50 | 60+ |
| CBB复用率 | <20% | ~25% | ~35% | 55%+ |
| 研发周期(TTM) | 15-24个月 | 12-18个月 | 9-15个月 | 6-12个月 |
| 产品毛利率 | 12-15% | 15-18% | 18-22% | 20-25% |
| 项目按时交付率 | <60% | ~70% | ~80% | 85%+ |

#### 每个阶段的退出条件与决策逻辑

| 阶段 | 触发条件 | 核心决策 | 决策者 | 决策逻辑 |
|:-----|:---------|:---------|:-------|:---------|
| 职能制→矩阵式 | 并行项目>5，PM协调不过来 | 成立PMO | 研发VP | 项目数量增加导致沟通成本指数级上升 |
| 矩阵式→IPD | 营收>200亿，产品线>4条 | 引入IPD裁剪版 | CEO+CTO | 利润率被华为拉开差距(华为25%+ vs 浪潮15%) |
| IPD→双轨策略 | AI客户要求定制化快速交付 | JDM模式创新 | 产品VP | 传统IPD 12-15个月无法满足互联网客户6个月需求 |

### 11.2 浪潮 IPD 裁剪方案详解

#### 与华为完整IPD的对比

| 维度 | 华为IPD (完整版) | 浪潮IPD (裁剪版) | 裁剪原因 |
|:-----|:---------------|:----------------|:---------|
| TR节点数 | 7个(含4A) | 6个(去掉4A单独评审) | 浪潮服务器平台化程度高，4A可合并入TR4 |
| DCP门禁数 | 6个 | 3个(CDCP/PDCP/ADCP) | 减少审批层级，加速决策 |
| 阶段活动 | 每个阶段15-25个活动 | 每个阶段8-12个活动 | 行业Know-how固化到模板中，减少重复评审 |
| 文档要求 | 每个节点10-20份文档 | 每个节点5-8份文档 | 优先保留技术文档，裁剪行政性文档 |
| 评审人数量 | 7-11人/次 | 5-7人/次 | 缩小评审圈，提高效率 |
| PDT配置 | 全职6-8人 | 半职4-5人 | 浪潮PDT Leader全职，成员可兼2个项目 |
| IT系统依赖 | PLM+ERP+CRM全链路 | PLM+配置器 | 先上核心系统，其他逐步补齐 |

#### 浪潮IPD的7条核心原则

```text
1. 决策快于流程：IPMT可随时启动"快速通道"跳过非关键阶段
2. 技术评审不能省：TR1/TR3/TR5是硬门禁，不能跳过
3. 文档为决策服务：不写"归档用"的文档，每份文档有明确读者
4. CBB先于开发：项目启动前先查CBB库，能复用不复用=违规
5. 双轨平等：技术驱动轨与市场驱动轨在IPMT层面有同等话语权
6. 复盘必须改进：每个项目结项复盘必须有3条以上改进项
7. 度量透明：所有TR评审通过率/延期率对全员可见
```

### 11.3 JDM模式的运作细节

#### JDM的定义与分类

浪潮JDM (Joint Design Manufacture) 分为三个层次：

| 层次 | 名称 | 浪潮投入 | 客户投入 | 适用客户 | 占比 |
|:----|:-----|:--------|:---------|:---------|:----:|
| L1 | ODM标准化 | 全权设计 | 仅提需求 | 中小企业 | 40% |
| L2 | JDM联合开发 | 70%设计+30%按需 | 30%规格+70%验证 | 互联网中厂 | 35% |
| L3 | C2M深度定制 | 30%平台+70%定制 | 70%规格+全量测试 | 头部云厂商 | 25% |

#### JDM的PM到PDM适配

| 传统PM操作 | JDM下的PDM操作 | 差异 |
|:-----------|:---------------|:-----|
| 需求评审(被动接收) | 需求挖掘+路标对齐(主动引导) | JDM要求产品经理深入客户做技术交流 |
| 项目计划(节点管控) | 版本节奏+迭代窗口(给客户明确的交付节奏) | 浪潮每季度发布2个基线版本，JDM客户在此之上定制 |
| 变更管理(走审批) | 变更分级+快速通道(小变直接落，大变进IPMT) | 互联网客户变更频率是传统客户的3-5倍 |
| 风险预警(被动响应) | 联合风险管控(客户参与风险识别) | JDM客户的技术团队共同参与TR评审 |

#### JDM项目的实际运作流程（以某互联网大厂AI服务器为例）

```text
第1周: 客户提出技术需求框架 -> 浪潮产品经理做需求澄清+差距分析
第2周: 输出《需求差距分析报告》-> 与客户确认"平台能做 vs 需定制"清单
第3周: 评估定制工作量 -> 价格谈判 -> 签订JDM协议
第4-6周: TR1(概念评审) -> 客户参与市场分析确认
第7-12周: TR2-TR4(设计开发) -> 每双周与客户技术团队同步
第13-16周: TR5(验证) -> 客户提供测试环境+应用场景验证
第17-20周: TR6(量产) -> 客户驻厂验收
第21周+: 持续交付 -> 版本迭代维护
```

**JDM关键成功因素**: 客户接口人一对一、研发驻地(浪潮在阿里/腾讯/字节均设有驻地研发团队)、技术开放(浪潮开放BMC/Sensor API给客户做二次开发)。

### 11.4 浪潮经验的可迁移要点

| 浪潮做法 | 可迁移性 | 适配建议 |
|:---------|:--------:|:---------|
| IPD裁剪（6TR+3DCP） | ★★★★★ | 所有20-200亿级服务器企业可直接参考 |

## 13. CBB库建设方案

### 13.1 CBB的定义与分类

#### 什么是服务器领域的CBB

CBB (Common Building Block，通用构建模块) 指可在多个产品/平台间复用的硬件/软件/固件/设计资产。

#### 服务器CBB的分类维度

| 类别 | 定义 | 复用层级 | 典型例子 | 生命周期 | 经济特征 |
|:-----|:-----|:--------|:---------|:---------|:---------|
| **硬件CBB** | 可跨机型复用的硬件模块 | 平台级/产品线级 | 电源模块/风扇模组/背板/中背板 | 2-4年 | 单次开发成本高，复用后边际成本极低 |
| **固件CBB** | BMC/BIOS/CPLD的核心功能模块 | 平台级 | Sensor管理/SEL日志/IPMI命令集 | 3-5年 | 开发投入大，复用可减少80%重复开发 |
| **软件CBB** | 驱动/管理软件中间件 | 产品线级 | Redfish API/SNMP Agent/健康监控 | 3-5年 | 持续迭代，复用+持续维护 |
| **设计CBB** | 可复用的设计文件/方案 | 组织级 | PCB Layout块/散热CFD模型/结构CAD | 5-7年 | 一次投入，重复调用 |
| **知识CBB** | 测试用例/评审Checklist/经验教训 | 组织级 | GPU兼容性测试用例/EMC整改方案 | 永久 | 知识资产，需持续维护 |

### 13.2 CBB库建设四步法

#### 第一步：CBB识别（第1-3个月）

**方法: 自下而上+自上而下结合**

**自下而上（现有产品中找CBB候选）**:

1. 收集过去3年所有机型BOM，分析跨机型共用的物料
2. 统计各物料的复用频次（机箱/电源/风扇/背板等）
3. 找出现有项目中"重复造轮子"最多的模块

**自上而下（按平台规划定义CBB）**:

1. 分析3年产品路标，识别跨产品线的共性需求
2. 定义"应该复用的模块"清单（即使当前还没复用）

**CBB候选清单模板**:

```markdown
## CBB候选清单 — [领域]

| CBB名称 | 来源(现有/规划) | 复用项目数 | 当前状态 | 优先度 | 评估人 |
|:--------|:---------------|:---------:|:---------|:------|:-------|
| 2400W钛金PSU | 现有(NF5280/NF5270) | 3 | 已复用 | P0 | 电源工程师A |
| 8cm×4风扇模组 | 现有(NF5280) | 1 | 可扩展 | P1 | 散热工程师B |
| BMC健康监控模块 | 规划 | — | 需开发 | P0 | 固件Leader |
| OpenBMC基础框架 | 规划 | — | 需重构 | P1 | 软件架构师 |
```

**识别阶段交付物**: CBB候选清单 + 每个CBB的《复用效益评估表》

#### 第二步：CBB设计与开发（第4-12个月）

**CBB开发优先级排序矩阵**:

```text
                    复用效益(节省成本/缩短周期)
                         高        中       低
                     +---------------------------
             高      |   P0立即启动  P1快跟上   P2评估
  复用需求           |
  (可能复用项目数)   中|   P1快跟上   P2排期     P3观察
                     |
             低      |   P2评估     P3观察     ❌不开发
                     +---------------------------
```

**CBB开发规范**:

```markdown
## CBB开发规范

### 通用要求
1. 每个CBB须有《CBB规格书》— 定义接口/性能/环境/可靠性要求
2. CBB接口须有明确的兼容性策略（向前兼容/向后兼容/版本协商）
3. CBB须附带《集成指南》— 告诉PDT如何在自己的产品中使用

### 版本管理
- CBB版本号: V<主>.<次>.<补丁> (如 V2.1.3)
- 主版本: 接口不兼容变更
- 次版本: 接口兼容的增强
- 补丁: Bug修复

### 验收标准
- 硬件CBB: 3次以上跨产品线验证
- 固件CBB: 2个以上PDT集成并通过TR4评审
- 软件CBB: API测试覆盖率≥90% + 2个以上产品使用
- 设计CBB: 评审通过后归档到CBB库
```

## 14. 配置器系统需求文档（PRD）

### 14.1 项目背景与目标

#### 问题陈述

服务器行业SKU爆炸: 同一机型潜在SKU = GPU种数 × CPU种数 × 内存容量 × 存储容量 × 网络接口 × 散热方式 × OS配置。以典型AI服务器为例: 3(GPU)×2(CPU)×3(内存)×3(存储)×4(网络)×2(散热)×3(OS) = 1,296种SKU。

管理这些SKU的挑战:

1. BOM手动编制 → 错误率>5%，每单成百上千元的BOM错误损失
2. 价格靠人工估算 → 报价周期3-7天，客户流失
3. 兼容性靠人工验证 → 下单后才发现不兼容，返工成本高
4. 配置组合无法穷举 → 销售不敢推非标配置，丢失订单

**目标**: 建立一个配置器系统，使SKU配置从"人工3-7天"变为"系统3-5分钟"，BOM错误率从>5%降至<0.1%。

#### 预期收益

| 指标 | 当前(人工) | 目标(系统) | 改善 |
|:-----|:----------:|:----------:|:----:|
| 配置报价周期 | 3-7天 | 3-5分钟 | 50-200× |
| BOM错误率 | >5% | <0.1% | 50× |
| 配置兼容性检查 | 人工核对 | 自动校验 | 0差错 |
| 销售人员可自配率 | <30% | >85% | 3× |
| 定制化响应速度 | 7-14天 | 24小时 | 7× |

### 14.2 系统架构

```text
+-----------------------------------------------------+
|                    前端(用户界面)                      |
|  配置主页 | 3D预览 | 报价输出 | 历史配置              |
+-----------------------------------------------------+
|                    业务逻辑层                          |
|  规则引擎 | BOM引擎 | 价格计算 | 约束校验              |
+-----------------------------------------------------+
|                    数据层                              |
|  物料主数据 | 规则库 | 价格表 | 配置历史               |
+-----------------------------------------------------+
|                    集成层                              |
|  PLM系统 | ERP系统 | 报价系统                          |
+-----------------------------------------------------+
```

### 14.3 功能需求

#### FR-01: 配置主页 (P0)

用户选择产品系列→平台→机型→组件(左树+右表布局)，每个选择即时反馈价格/BOM/兼容性，不兼容选项置灰。从零到完成配置≤5分钟。

#### FR-02: 规则引擎 (P0)

| 规则类型 | 定义 | 示例 |
|:---------|:-----|:------|
| 互斥规则 | A和B不能同时选 | GPU A100 80GB与40GB互斥 |
| 依赖规则 | 选A必须选B | 选液冷必须选CDU |
| 条件规则 | 选A时B只能选某些值 | B200 GPU只能配液冷 |
| 数量规则 | A最少/最多选N个 | GPU最多8张 |
| 约束规则 | A总功耗≤B | GPU+CPU TDP≤PSU功率80% |
| 推荐规则 | 建议选A | B200推荐800G网卡 |

规则以配置化方式管理(Excel导入/界面配置)，有版本管理和生效时间控制，支持冲突检测。

#### FR-03: BOM自动生成 (P0)

完整BOM含: BOM头(客户/时间/版本/有效期)+BOM行(物料编码/描述/数量/单价/替代料)+BOM尾(总价/总功耗)。支持版本管理、变更追溯、版本对比。输出格式: HTML预览/PDF/Excel/JSON。

#### FR-04: 价格计算 (P0)

定价模型: 基础价格×批量折扣×渠道折扣。实时显示，支持分项价格和历史对比。物料价格可批量导入，即将涨价提前预警。

#### FR-05: 配置有效期 (P1)

报价30天有效，到期前7天提醒，过期可申请延期。物料EOL自动更新规则触发时间。

### 14.4 非功能需求

| ID | 类别 | 需求 | 验收标准 |
|:---|:-----|:-----|:---------|
| NFR-01 | 性能 | 页面加载≤2秒，价格重算≤1秒 | 2Gbps网络下满足 |
| NFR-02 | 可用性 | ≥99.5% | 年度停机≤43小时 |
| NFR-03 | 并发 | 100人同时在线 | 压力测试通过 |
| NFR-04 | 权限 | 角色控制(销售/售前/管理员/客户) | 各角色仅看授权内容 |
| NFR-05 | 可扩展 | 新增机型不修改代码 | 配置化扩展 |
| NFR-06 | 国际化 | 中英文 | 界面可切换 |

### 14.5 实施排期与风险

| 阶段 | 时间 | 里程碑 |
|:-----|:----:|:-------|
| 需求分析 | M1-M2 | PRD定版+UI原型 |
| 基础架构 | M3-M4 | 规则引擎MVP |
| 核心功能 | M5-M7 | BOM引擎上线(首条产品线) |
| 价格引擎 | M7-M8 | 实时报价可用 |
| 集成对接 | M9-M10 | PLM/ERP对接完成 |
| 全面推广 | M11-M12 | 全产品线上线 |

**风险**: 物料数据质量差(先清洗再开发)、规则不完备(先覆盖90%场景持续补全)、用户习惯(纳入KPI)、集成复杂度(最小可行集成起步)。
