## 核心命题

GLPI（法语"开源 IT 资产管理器"）的价值不是"又一个资产台账"，而是**把 ITIL 服务管理（ITSM）流程与资产管理整合在一个开源平台上**：资产台账（Inventory）→ 工单（Tickets）→ 变更/问题（Change/Problem）→ 知识库（Knowledge）——**从"记录资产"到"管理资产生命周期中的一切动作"**。与 Zabbix 集成的意义更在于：**监控发现问题 → 自动生成工单 → 服务台闭环跟踪**，打通"检测-响应-解决"的最后一环。

> 一句话：**GLPI 回答"资产出了事谁来处理、怎么处理、怎么沉淀"——它是资产管理的"服务层"，Zabbix 是"感知层"，CMDB 是"数据层"。**

## 一、原理深潜：GLPI 的定位与核心模型

### 1.1 与相邻系统的边界（关键认知）

| 系统 | 定位 | 核心对象 | 回答的问题 |
|:-----|:-----|:---------|:-----------|
| **CMDB** | 配置管理数据底座 | CI + 关系 | "有什么、谁依赖谁" |
| **Zabbix** | 监控感知 | 指标 + 触发器 | "现在出了什么问题" |
| **GLPI** | IT 服务管理（ITSM） | 资产 + 工单 + 流程 | "问题谁来处理、怎么闭环" |
| **ITAM** | 资产全生命周期 | 采购-部署-退役 | "资产值多少钱、在哪" |

> **GLPI 的核心竞争力是 ITSM 流程**：资产是入口，工单/变更/知识库才是价值所在——**单纯把它当资产台账用，是用错了它的定位**。

### 1.2 核心功能矩阵

| 模块 | 能力 | 价值 |
|:-----|:-----|:-----|
| 资产管理 | 硬件/软件/许可证全生命周期 | 成本优化（节省 15-30% IT 成本） |
| 服务台 | 工单/问题/变更/发布管理 | 流程规范化（ITIL） |
| 知识库 | FAQ/文档/经验沉淀 | 减少重复工单 |
| 网络发现 | 自动发现网络设备 | 减少人工录入 |
| 报表 | 多维度统计可视化 | 决策支持 |
| 插件扩展 | CMDB/合同追踪/远程维护 | 按需扩展 |

### 1.3 技术架构

- **技术栈**：PHP + MySQL/MariaDB，遵循 GNU GPL 协议
- **核心特性**：RBAC 角色权限模型（适配多分支/分布式组织）、内置报表引擎（ITIL 标准）、高度可定制（与 OA/财务系统集成）
- **适用场景**：政府机构、教育单位、中大型企业的基础运维与定制需求

## 二、部署路径（素材提炼）

### 2.1 环境要求（素材）

| 组件 | 最低版本 |
|:-----|:---------|
| Web 服务器 | Apache 2.4+ 或 Nginx 1.18+ |
| 数据库 | MySQL 8.0 或 MariaDB 10.5+ |
| PHP | 7.4+（含必要扩展） |

### 2.2 三种部署方式对比

| 方式 | 复杂度 | 适用 |
|:-----|:-------|:-----|
| **K8s + Helm**（推荐） | 低（第三方 Chart：vdiogov/glpi-conteiner） | 已有 K8s 环境 |
| 手工部署（官方文档） | 高（依赖多、易卡点） | 学习/特殊定制 |
| 源码部署 | 中（git clone + 目录权限配置） | 自定义开发 |

**关键目录权限**：`config/`（配置）、`files/`（上传文件）需要 Web 服务器可写——权限错误是部署最常见的坑。

### 2.3 初始化与配置

- Web 安装向导（数据库连接 + 管理员账号）
- 仪表盘：资产集中监控与统计分析
- 插件安装（中文包、CMDB 等）

## 三、应用场景：GLPI × Zabbix 集成（监控驱动服务闭环）

### 3.1 集成价值（素材核心）

**为什么集成**：
- ELK 解决了"日志→告警"，GLPI×Zabbix 解决"**告警→工单→闭环**"
- 消除人工干预延迟：Zabbix 异常 → 自动转 GLPI 工单

### 3.2 闭环架构

```
Zabbix 监控（发现问题）
    │  告警/触发器
    ▼
GLPI（自动生成工单）──► 服务台分配 ──► 工程师处理
    │                        │
    └── 解决后更新资产状态 ◄──┘
        + 知识库沉淀（同类问题下次自动匹配）
```

| 价值维度 | 说明 |
|:---------|:-----|
| 自动化事件处理 | 监控异常自动转工单，消除人工干预延迟 |
| 监控-服务闭环 | 问题检测（Zabbix）→ 解决跟踪（GLPI）全流程管理 |
| IT 透明度 | 统一平台展示基础设施状态 |
| 响应提速 | 缩短异常发现到工单处理的响应时间 |

### 3.3 与 CMDB 的协同（衔接上一报告）

```
CMDB（数据层）──► Zabbix（感知层）──► GLPI（服务层）
  设备状态            异常检测            工单闭环
```

**三平台协同的理想形态**：CMDB 管"设备是什么状态" → Zabbix 管"出了什么问题" → GLPI 管"谁来处理"——**数据、感知、服务三层解耦，各司其职**。这也解释了为什么 GLPI 与 Zabbix 不是"对比"关系（素材标题误导），而是**互补**关系。

## 四、GLPI vs Zabbix：纠正"对比"的认知误区

素材《GLPI vs Zabbix 软件对比分析》为**空壳文件**（无实质对比内容）。从架构原理上澄清：

| 维度 | GLPI | Zabbix | 是否可比 |
|:-----|:-----|:-------|:---------|
| 定位 | ITSM/ITAM | 监控告警 | ❌ 不同层 |
| 核心对象 | 资产/工单 | 指标/触发器 | ❌ 不同抽象 |
| 数据流 | 消费监控数据 | 产生监控数据 | 互补 |
| 集成方式 | 接收 Zabbix 告警 | 输出告警到 GLPI | 协同 |

> **正确认知**：GLPI 与 Zabbix 是**上下游关系**而非竞品——"对比分析"的提问本身源于对两者定位的混淆。竞品关系应是：GLPI vs ServiceNow/SolarWinds（ITSM 层）；Zabbix vs Prometheus/Nagios（监控层）。

## 五、结论

1. **GLPI 的核心是 ITSM 流程**：资产是入口，工单/变更/知识库是价值——不要当台账用
2. **部署首选 K8s+Helm**：官方手工部署复杂，容器化降低门槛
3. **×Zabbix 集成 = 服务闭环**：告警自动转工单，检测-响应-解决全流程自动化
4. **三层架构认知**：CMDB（数据）→ Zabbix（感知）→ GLPI（服务）——解耦协同是 IT 运维架构的正解
5. **警惕素材误区**：GLPI vs Zabbix 是伪对比，实际是互补关系
