## 1. TR1 — 概念阶段

### 1.1 阶段目标

**回答"为什么做这个机型？"** — 完成市场机会论证与需求定义。核心产出是一个有明确客户、明确场景、明确差异化定位的**产品概念**。

### 1.2 各领域活动明细表

| 领域 | 活动编号 | 具体活动 | 输入 | 输出 | 验收标准 |
|:-----|:--------:|:---------|:-----|:-----|:---------|
| **产品管理** | PM-01 | 开展目标客户访谈（≥3 家客户/5 场深度访谈） | 客户列表、访谈提纲 | 客户需求访谈纪要 | 每场访谈有录音/纪要，关键需求可追溯 |
| | PM-02 | 分析 TAM/SAM/SOM，输出市场容量数据 | IDC/Gartner 报告、券商研报 | 市场容量分析表 | TAM ≥ $10亿 且 SAM 年增 > 30% |
| | PM-03 | 输出竞品对标矩阵（3-5 款竞品按性能/价格/功耗对比） | 竞品规格书、公开报价 | 竞品对标矩阵表 | 至少覆盖 5 个对比维度 |
| | PM-04 | 撰写产品概念/需求规格书（初版），明确场景、密度、功耗、成本目标 | 访谈+竞品+市场数据 | 产品需求规格书 v0.5 | 场景定义可被架构师转化为技术指标 |
| **系统架构** | SA-01 | 评估技术可行性（关键芯片/互联/散热路线） | 芯片路线图、内部技术储备 | 技术可行性评估意见 | 识别 ≥ 3 项关键风险及其 mitigation |
| | SA-02 | 判断是否有现成模块可复用，估算复用比例 | 已有机型 BOM 与模块库 | 模块复用评估表 | 复用比例 ≥ 40% 可降低风险和 TTM |
| | SA-03 | 参与客户访谈（如客户有技术偏好），输出技术需求澄清 | 客户访谈安排 | 技术需求澄清纪要 | 客户技术需求可量化为具体技术指标 |
| **其他 12 领域** | — | **未参与**（各领域等待 TR2 通知） | — | — | — |

### 1.3 跨域交互模式

```text
交互模式: 单向传递
类型: 市场/产品 -> 系统架构

产品管理 --[需求描述]---> 系统架构
  (场景/密度/成本)       (技术可行性判断)
                           |
                           +--[可行性反馈]---> 产品管理
```

**关键特征**:

- 这是一个***轻量级***的 TR，仅 2-3 个领域参与
- 系统架构师在此阶段的作用是**可行性闸门**而非方案设计
- 如果已有 POC 验证数据，可在此阶段调用来加速决策

### 1.4 关键交付物清单

| 交付物 | 模板/格式 | 负责人 | 审核人 |
|:-------|:----------|:-------|:-------|
| 产品需求规格书 v0.5 | 按场景→密度→功耗→成本四维度定义 | PM | SA |
| 市场容量分析表 | TAM/SAM/SOM 三层，含数据来源标注 | PM | 产品线负责人 |
| 竞品对标矩阵表 | 至少 5 维度 × 5 竞品 | PM | SA |
| 技术可行性评估意见 | 含 3 项关键风险和 mitigation | SA | 研发总监 |
| 模块复用评估表 | 按子系统和可复用模块列表 | SA | 研发总监 |

### 1.5 决策检查点（TR1 评审 Gate）

| # | 检查项 | 标准 | 一票否决？ | 不通过行动 |
|:-:|:-------|:-----|:----------:|:----------|
| G1 | 市场规模是否足够？ | TAM ≥ $10亿, SAM 年增 > 30% | ✅ | 重新调研或放弃 |
| G2 | 是否有明确目标客户？ | ≥ 2 家有明确采购意向 | ✅ | 扩大客户访谈 |
| G3 | 技术是否可行？ | 无不可控红牌风险 | ✅ | 降低技术目标或等待技术成熟 |
| G4 | 差异化定位是否清晰？ | 与竞品有 ≥ 2 个差异化维度 | ❌ | 重新定位 |
| G5 | 成本目标是否可行？ | BOM 目标利润 > 15% | ❌ | 调整产品定义 |

### 1.6 典型冲突与决策场景

**场景 1: 性能 vs 成本目标冲突**

```text
产品管理: "客户要 16 卡 B200，目标价格 $80,000"
系统架构: "B200 单 GPU $25,000+，16 卡仅 GPU 就 $400,000"
解决方法: 降低配置到 8 卡 H200 + 8 卡 B200 (训练+推理分池)
```

**场景 2: 是否进入新市场**

```text
产品管理: "国产化信创市场空间大，建议做昇腾版本"
系统架构: "团队没做过昇腾方案，CAN总线/驱动适配需要 6+ 个月"
决策: 进入 TR2 做深入评估，TR2 结束再做 Go/No-Go
```

## 2. TR2 — 计划阶段

### 2.1 阶段目标

**回答"做具体什么方案？"** — 完成方案优选、可行性评估、资源授权。产出明确的**主推方案**和**备选方案**。

### 2.2 各领域活动明细表

| 领域 | 活动编号 | 具体活动 | 输入 | 输出 | 验收标准 |
|:-----|:--------:|:---------|:-----|:-----|:---------|
| **系统架构** | SA-04 | 制定 2-3 个候选方案（GPU + CPU + 互联 + 散热 + 形态的排列组合） | TR1 需求规格书、芯片路线图 | 候选方案对比表 | 方案间有明确的权衡分析 |
| | SA-05 | 完成功耗树估算（各级功耗分配 + 20% 余量） | 芯片 TDP 数据 | 功耗树估算表 | 覆盖 GPU/CPU/Switch/Retimer/风扇/泵/其他 |
| | SA-06 | 完成互联拓扑设计（GPU/CPU/网卡/Switch 拓扑关系） | 接口规格 | 互联拓扑方案图 | 标明 Lane 分配和带宽瓶颈点 |
| | SA-07 | 输出系统架构方案文档 v0.8 | 候选方案 + 权衡分析 | 系统架构方案文档 | 含方案对比、推荐方案及理由 |
| | SA-08 | 制定项目计划（WBS 分解到领域任务级） | TR1 决策 + 资源评估 | 项目开发计划 v1.0 | 里程碑清晰，关键路径标注 |
| **硬件设计** | HW-01 | 评估关键芯片可用性与交期（GPU/Switch/Retimer） | 芯片厂商报价 + 交期 | 关键芯片可用性评估表 | 主芯片交期 < 16 周 |
| | HW-02 | 初排接口规划（PCIe Lane 分配/GPI/O/管理接口） | 互联拓扑方案 | 管脚分配初版 | 至少预留 20% IO 余量 |
| | HW-03 | 评估 Retimer/Redriver 需求（基于 SerDes 速率和走线长度估算） | 224G SerDes 标准 | Retimer 需求评估表 | 明确每段高速链路的 retimer 需求 |
| | HW-04 | 初选 OAM/UBB 模块方案 | GPU 模块规格 | OAM 方案评估表 | 模块生态验证完成 |

### 2.6 典型冲突与决策场景

**场景 1: 密度 vs 散热冲突（最典型）**

```text
系统架构: "我推荐 16 卡方案，2U 密度"
散热: "16 卡 TDP 5.6kW，2U 风冷压不住"
结构: "2U 做液冷空间不够"
-> 调整方案: 4U 冷板液冷 16 卡，或者 2U 风冷 8 卡
-> 回到产品管理: 客户接受 4U 还是坚持 2U？
```

**场景 2: 国产化 vs 性能冲突**

```text
产品管理: "信创客户要求国产化率 > 70%"
系统架构: "昇腾 910B 单卡算力仅为 H200 的 60%"
硬件: "昇腾 910B 交期 4 周，优于 H200 的 12 周"
-> 决策: 做双版本 — H200 版面向训练客户，Ascend 版面向信创客户
```

**场景 3: 时间 vs 技术先进性冲突**

```text
产品管理: "要求 12 周出样机"
系统架构: "PCIe 6.0 方案芯片才刚刚有样片"
供应链: "PCIe 6.0 Retimer 交期 20 周"
-> 决策: TR2 方案选 PCIe 5.0（成熟），PCIe 6.0 列入下一代规划
```

### 3.3 跨域交互模式

```text
交互模式: 网状博弈

                系统架构（总师/仲裁者）
               ↙    v    v    v    v    v    ↘
         +---------------------------------------------+
         |             核心冲突区                       |
         |                                              |
    HW --+---> ME <----> TH <----> SI ---> PD                |
     |   |     |        |        |      |               |
     |   |     |   +----+----+   |      |               |
     |   |     |   |   FW    |   |      |               |
     |   |     |   +---------+   |      |               |
     |   |     |        |        |      |               |
     v   |     |        |        |      |               |
    SW   |     |        |        |      |               |
         |     |        |        |      |               |
         |     +--------+--------+------+               |
         |                    ^                         |
         |             SCM + MFR + QE                   |
         +---------------------------------------------+
                           ^
                    CERT + SEC + QA

交互特征:
- 不是中心辐射，而是多领域之间***相互博弈***
- 架构师角色从信息汇聚者变为冲突仲裁者
- 核心冲突集中在: HW↔ME↔TH↔SI 四角关系
- SCM 作为约束条件的提供方影响所有领域决策

关键协同机制: 每周架构仲裁会
1. 各领域提交当前未解决的冲突列表
2. 系统架构按影响范围排优先级
3. 现场决策: 能当场解决的就当场解决
4. 不能解决的升级到 TR3 评审
```

### 3.6 典型冲突与决策场景

**场景 1: GPU 安装方向冲突（HW↔ME↔TH 的经典三角）**

```text
HW: "GPU 必须水平安装（散热器贴合最优，受力均匀）"
ME: "4U 水平安装只能放 8 卡，垂直可以放 16 卡"
TH: "垂直安装 + VC 均温板可以压住 TDP，但 GPU 温度比水平高 5°C"
SA 仲裁: 评估客户场景——如果是训练（持续满载）-> 水平安装 + 4U
         如果是推理（间歇负载）-> 垂直安装 + 2U
```

**场景 2: PCB 层数 vs 成本冲突（SI↔SCM↔HW）**

```text
SI: "16 卡 PCIe 5.0 需要至少 18 层 PCB"
SCM: "18 层 PCB 成本是 14 层的 1.8 倍，超出 BOM 预算"
HW: "如果减少 2 个 PCIe Slot，可以降到 14 层"
SA 仲裁: 接受 18 层 + SCM 在其他部件上找补成本空间
```

**场景 3: 液冷 vs 维护性冲突（TH↔ME↔客户）**

```text
TH: "冷板液冷是最可靠的散热方案"
ME: "液冷管路导致 GPU 不可热插拔，更换 GPU 需要排液"
PM: "客户要求 GPU 热插拔支持"
-> 解决方案: 采用盲插快接头（Quick Disconnect）+ 液冷分支管路
-> 代价: 快接头成本 +$50/路，冷却液泄漏风险增加
```

**场景 4: 传感器位置冲突（FW↔HW↔TH）**

```text
FW: "温度传感器需要放在芯片正下方才能准确读数"
HW: "芯片正下方是 BGA 管脚区域，没有空间放传感器"
TH: "芯片边缘的温差和中心差 8-10°C，不可忽略"
-> 妥协方案: 芯片边缘放 TS（温度传感器），软件补偿 5°C 偏移量
```

**场景 5: 安全启动 vs 开发效率冲突（SEC↔FW↔HW）**

```text
SEC: "要求所有固件签名验证，从 Boot ROM 到 BMC 应用完整信任链"
FW: "签名验证增加开发调试复杂度，每次固件更新需要签名字段绕过"
HW: "TPM 芯片需要额外的 SPI 接口和 GPIO"
-> 决策: 开发阶段允许调试模式（签名绕过），量产阶段强制开启 Secure Boot
-> HW 确认增加 TPM 接口（预留 2 个 GPIO + 1 路 SPI）
```

### 4.3 核心协同机制：预布局评审

**预布局评审**是 TR4 的"压轴协同活动"，所有领域同时面对同一张 PCB 布局图，各领域标注自己的空间需求：

```text
+---------------------------------------------+
|              预布局评审会议                    |
|                                              |
|  HW: "BGA fanout 需要这个区域"                |
|  ME: "螺丝孔位置不能变"                       |
|  TH: "散热器覆盖区 — 走线别进来"               |
|  SI: "高速走线走廊 — 从这里到连接器"           |
|  PD: "大电流走线需要宽线，占 3 层"             |
|  FW: "传感器放这里"                           |
|                                              |
|  输出: 布局图 v2（标注所有领域约束）          |
|                                              |
|  迭代次数: 3-5 轮                            |
+---------------------------------------------+
```

**迭代流程**:

```text
布局图 v1 ---> 各领域标注约束 ---> 布局图 v2 ---> 冲突识别
    ^                                              |
    +---- 重新布局 <-- SA 仲裁冲突 <--- 领域间协商 --+
```

**预布局阶段各领域提交的关键约束**:

| 领域 | 约束类型 | 常见冲突 |
|:-----|:---------|:---------|
| HW | 芯片位置固定/接口朝向/关键信号走线走廊 | 与 ME 的安装孔/支撑柱冲突 |
| ME | 安装孔位置/支撑柱/导轨/面板接口 | 占 PCB 走线空间 |
| TH | 散热器覆盖区（走线禁区）/风道路径 | 与 SI 的高速走线走廊冲突 |
| SI | 高速信号走廊（带状线/差分对区域）/阻抗控制区 | 空间不足→需加层 |
| PD | 大电流走线区/VR 布局区 | 大面积铜箔影响散热 |
| FW | 传感器位置/FRU EEPROM 位置 | 空间刚好被其他器件占据 |

### 4.6 典型冲突与决策场景

**场景 1: 高速走线 vs 散热器领地之争（TR4 最经典冲突）**

```text
SI: "这个区域我要走 8 对 PCIe 6.0 差分线（≤10 英寸），不能放散热器"
TH: "散热器必须正对芯片上方，流体速度最大区域才能带走热量"
ME: "空间就这么多，你们自己协调"
HW: "芯片 TDP 1000W，散热不到->降频->性能不达标（客户不收货）"
-> 解决方案: 散热器设计异形（挖槽避开走线区域）+ PCB 增加 2 层
-> 代价: 散热器 CNC 成本 +15%, PCB 成本 +8%, 总 BOM 增幅 < 3%
-> 下一版优化: 提前在 TR3 让 SI 和 TH 对齐布局空间
```

**场景 2: 电容高度 vs 机箱厚度冲突（HW↔ME↔TH）**

```text
HW: "去耦电容必须用 1210 封装（高度 2.5mm）才能满足 PDN 阻抗"
ME: "2U 机箱 PCB 到上盖只有 3mm 空间，电容 2.5mm -> 只剩 0.5mm"
TH: "0.5mm 间隙->气流阻塞->散热恶化 3-5°C"
-> 方案 A: 换 0805 封装（1.5mm 高）-> PDN 阻抗可能不够
-> 方案 B: 增加机箱厚度到 2.5U -> 客户机柜不支持
-> 方案 C: 电容分布在 PCB 另一面 -> 需要 ME 调整支撑柱位置
-> 决策: 方案 C + PD 仿真验证新布局下 PDN 阻抗仍达标
```

**场景 3: 管理接口与 BMC 传感器冲突（FW↔HW↔TH）**

```text
FW: "需要每个 GPU 模块有独立温度传感器，BMC 才能做Smart Fan"
HW: "GPU 模块背面没有位置放额外传感器"
TH: "GPU 进气口温度和出气口温度差 15°C，进出传感器必须有"
-> 方案: 不在 GPU 模块内部放，在机箱进风口和出风口各放一个阵列式传感器
-> 代价: 多 4 个传感器 + I2C MUX + 成本 $5
-> 结果: 用 2 个传感器覆盖所有 GPU（通过进气温度+功耗估算每 GPU 温度）
```

**场景 4: PSU 位置 vs 风道设计冲突（PD↔TH↔ME）**

```text
PD: "PSU 必须放在前端，符合 800mm 机柜深度标准"
TH: "PSU 放在前端->进风温度被 PSU 加热->GPU 进风温度 35°C->散热恶化"
ME: "PSU 放后面->GPU 前插维护空间不够"
-> 方案: PSU 前置 + 独立风道（PSU 用独立风扇+导风罩直排机箱后部）
-> 验证: CFD 仿真显示 PSU 对 GPU 进风温度影响 < 2°C -> 可接受
```

**场景 5: 信号定义冲突（HW↔FW↔SI）**

```text
HW: "这个 GPIO 定义为 BMC ALERT# 中断信号"
FW: "BMC 需要用这个 GPIO 作为 POST 完成指示"
SI: "这个引脚在 BGA 扇出时和 DDR 信号邻接，有串扰风险"
-> 协调: HW 重新分配管脚，FW 确认新管脚的功能兼容性
-> SI 重新做串扰仿真确认风险消除
```

### 7.3 最高冲突领域对排名

| 🥇 | **HW ↔ SI** | BGA fanout 密度 vs PCB 层数/走线空间 | TR3-TR4 | HW 提前提供完整 pinmap, SI 预仿真 |

| 🥇 | **ME ↔ SI** | 安装孔/支撑柱 vs 走线走廊 | TR4 | ME 提前提交结构约束图 |
| 🥈 | **QA ↔ FW** | 可测试性 vs 固件实现 | TR4-TR5 | QA 在 TR3 就提交测试需求 |
| 🥈 | **SI ↔ MFR** | PCB 工艺能力 vs 设计需求 | TR4 | MFR 提前提供工艺能力文档 |
| 🥈 | **SEC ↔ FW** | 安全要求增加固件复杂度 | TR3-TR4 | SEC TR3 提交安全基线 |
| 🥉 | **TH ↔ SI** | 散热器禁区 vs 高速走线区域 | TR4 | TR3 就划定散热禁区 |
| 🥉 | **SCM ↔ HW** | 双供约束 vs 芯片选型 | TR2-TR3 | SCM 参与 HW 选型会议 |
| 🥉 | **CERT ↔ SI** | EMI 合规 vs PCB 设计自由度 | TR4-TR5 | CERT TR3 提交EMI设计指南 |

### 7.4 加速研发的 5 个关键杠杆

| # | 杠杆 | 投入 | 产出 | 典型案例 |
|:-:|:-----|:-----|:-----|:---------|
| 1 | **TR3 多领域对齐加时** | +1-2 天评审会 | TR4 减少 30%+ 返工 | 冲突案例中 SI vs TH 的空间冲突提前暴露 |
| 2 | **预布局评审全员强制参与** | 半天/迭代 × 3 轮 | 减少 2-3 轮 PCB Layout 迭代 | 安装孔+走线+散热三方一次对齐 |
| 3 | **模块复用库建设** | 版本管理 + 接口标准化 | TTM 缩短 30%+ | PCIe Switch 模块、BMC 模块跨机型复用 |
| 4 | **POC 前置高风险技术验证** | 3-4 周 POC 周期 | 降低 TR5 回退概率 | 液冷方案 POC、224G SI 验证 |
| 5 | **BMC/SW 与 HW 同步开发** | 虚拟平台/BSP 提前开发 | 样板上电即全面调试 | FW TR4 完成 BSP, SW TR4 完成驱动 |

### 7.5 常见失败模式与预防

| # | 失败模式 | 症状 | 根本原因 | 预防措施 |
|:-:|:---------|:-----|:---------|:---------|
| 1 | **"TR4 崩溃"** | 预布局迭代 8-10 轮仍无法收敛 | TR3 架构没有真正锁定, 各领域保留过多"灵活性" | TR3 评审严格把关, 不接受模糊决策 |
| 2 | **"TR5 回退"** | 样板发现架构级问题需要回 TR3 | TR3 的仿真/预验证不充分 | TR3 末做关键风险项的 POC 验证 |
| 3 | **"固件滞后"** | 样板到了 BMC 还不能点亮 | 固件开发启动太晚 | 固件在 TR3 初就启动 BSP 移植 |
| 4 | **"供应链卡脖子"** | 关键芯片交期无法满足 | TR2 的供应评估过于乐观 | SCM 在 TR2 做独立交期验证 |
| 5 | **"认证返工"** | EMC 测试失败 → PCB 改版 → 延迟 4-6 周 | 设计阶段没有考虑 EMI 设计规则 | CERT TR3 提交 EMI 设计指南, SI 做预仿真 |
