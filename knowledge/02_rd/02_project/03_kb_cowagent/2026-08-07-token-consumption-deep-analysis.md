## 摘要（TL;DR)

**实证结论**：9 天日志（07-30~08-07）共 **11,361 次 API 请求 / 569 个会话 / 估算 1.39B input tokens**（日均 ~154M）。消耗结构高度集中：**固定开销（system prompt 每轮重复发送）占 84%**——优化前 system 118K × 8,600+ 次请求 ≈ 1.14B tokens；历史消息与工具输出回读是第二大项；358 次压缩事件（73% 上下文超 100K）证明系统长期在预算边缘运行，压缩丢历史 = **质量损失的隐藏成本**。

**降 Token 核心思路**：保质量优先砍「**重复发送的固定开销**」（已完成，118K→18K 省 85%），再通过**工具输出分级截断**（当前轮 50K→20K、历史 20K→8K）、**长会话主动摘要**、**缓存命中保护**（system prompt 稳定性）、**bash 输出截断**四招砍历史/回读（保质量零损失）；轻微降质量层再用思考 token 管控、read 头部化、输出模板化（合计再省 30-40%）。

**预期**：每日 input 从 ~154M → <60M（省 60%+），压缩事件 -90%，深度文档质量回升（历史可保留不再失忆）。

## 二、Token 消耗分布（实证）

### 2.1 总览：9 天 / 11,361 请求 / 1.39B input tokens

| 指标 | 数值 |
|:-----|:-----|
| 日志时间跨度 | 2026-07-30 ~ 08-07（9 天） |
| API 请求总数 | **11,361 次** |
| 完成会话 | 569 个 |
| 每请求消息数 | 均值 **64** / 中位 45 / 最大 443 |
| 每请求轮数 | 均值 3.4 / 最大 5 |
| 估算总 input tokens | **~1.39B**（日均 ~154M） |
| 压缩事件（Context tokens exceeded） | **358 次** |
| 工具调用总数 | 12,452 次（bash 6,246 / edit 1,729 / read 1,221 / web_fetch 842 / write 461） |
| 思考事件（💭） | 8,520 次 |

**按天请求量**：08-03 起进入高峰期（1,967/2,101/2,141/1,924 vs 前期 434-1,119）——与调研/日报/深度分析任务量激增吻合。

### 2.2 消耗结构拆解：固定开销占 84%

| 消耗项 | 估算 tokens | 占比 | 性质 |
|:-------|:-----------|:----:|:-----|
| **固定开销（system 重复发送）** | ~1.14B（旧 118K × 8,660 请求） | **~82-84%** | 每轮/每步重复，纯浪费 |
| 历史消息 | ~0.22B（64 msg × 300 × 11,361） | ~16% | 必要但可压缩 |
| 工具输出回读 | 计入历史消息项（bash 可见 1.38M chars） | 内含 | 可分级截断 |
| 输出 tokens | 未计入（¥ 侧含） | — | 思考 8,520 次是主要构成 |

> ⚠️ **关键事实**：日志只记录工具输出前 200 字符（`result_str[:200]`），**真实回读量远大于日志可见**。read 一次可回读 50K chars（当前轮上限），历史 20K chars（历史上限）——工具回读是历史消息项的放大因子。

### 2.3 压缩事件：358 次，73% 超 100K

| 统计 | 数值 |
|:-----|:-----|
| 总数 | 358 次 |
| 上下文均值 | **138,950 tokens** |
| 中位 | 124,235 |
| 最大 | 345,032 |
| >100K 占比 | **73%** |
| 截断结果 | 172 次「trimmed to 3 turns」+ 压缩为纯文本（如 151→6 messages） |

**含义**：系统上下文长期在 124-345K 区间运行（远超旧预算 50K）→ 每次请求前必压缩 → 工具链被剥光（151→6 messages 样本）→ 模型失忆 → **质量差、长度上不去的直接机制**（与用户观察完全吻合）。压缩事件按天分布：08-07 达 98 次峰值（优化前 14:00-18:00 高发）。

### 2.4 会话维度：9.3% 长会话吃掉大头

| 会话长度（turns） | 数量 | 占比 |
|:------------------|:----:|:----:|
| ≤10 | 162 | 28.5% |
| 11-20 | 202 | 35.5% |
| 21-40 | 152 | 26.7% |
| 41-80 | 46 | 8.1% |
| >80 | 7 | 1.2% |

- 每会话均值 19.7 turns、中位 17、最大 176。
- **>40 turns 的 53 个会话（9.3%）** 每会话消耗 ≈ 40+ 次请求 × 118K+ 固定开销 → 单会话可达 **5-20M tokens**，是总消耗的大头（长尾集中）。
- 长会话同时是压缩重灾区：上下文随 turns 线性膨胀 → 反复压缩 → 质量与成本双输。

### 2.5 工具维度：bash 回读 1.38M chars 最大

| 工具 | 调用 | 日志可见输出总量 | 说明 |
|:-----|:----:|:----------------|:-----|
| bash | 6,246 | **1,380,031 chars** | 最大回读源；含大量 `python3 -c` 内联脚本（219 次）与 `python3 - <<'EOF'`（182 次） |
| edit | 1,729 | 416,020 chars | diff 回读 |
| read | 1,221 | 348,038 chars（日志截断后） | 实际回读更大（50K chars/次上限） |
| web_fetch | 842 | 119,685 chars | 网页正文回读 |
| write | 461 | 95,844 chars | 写文件确认 |

**高频 bash 模式**：`industry-insight/scripts/`（894 次，调研任务）、`check_md_format.py`（182 次）、`kb-global-index.py`（89 次）、`link-validator`（44 次）——**检查类命令高频重复执行**，其输出回读（即使截断）仍累积。

### 2.6 思考 token：8,520 次

- 💭 思考事件 8,520 次（占请求 75%），是输出 token 的主要构成。
- 深度任务思考是质量来源（不该砍），但**简单任务/例行任务（定时日报、检查确认）的思考**是纯成本。

### 2.7 与官方 30 天数据的交叉验证

DeepSeek 官方（06-29~07-28）：¥214.62 / 31,141 请求 / 2.345B tokens / 30 天。
- 日均 ≈ ¥7.15 / 78M tokens / 1,038 请求。
- 本 9 天日志日均 1,262 请求、154M tokens（含高峰增长）→ **数量级一致**，估算模型可信。
- 定价（¥/M）：缓存命中 0.02 / 未命中 1.00 / 输出 2.00 → **缓存未命中 + 固定开销重复 = 成本大头**（命中率低时 118K 重复发送按 ¥1.00/M 计价 = 每请求 ~¥0.12，1 万请求 ≈ ¥1,200）。

## 三、消耗热点根因（第一性原理）

| 热点 | 第一性原理 | 证据 |
|:-----|:----------|:-----|
| **固定开销 84%** | LLM API 无状态，system prompt 每请求必须完整重发；开销 = 大小 × 请求次数，**乘数效应** | system 118K × 8,660 请求 |
| **压缩-失忆循环** | 预算 < 固定开销 → available_tokens 为负 → 历史必被压缩 → 模型重读/重做 → 更多请求 → 更大上下文（正反馈） | 358 次压缩，73% 超 100K |
| **长会话失控** | turns 线性增长，上下文近线性膨胀；无中途摘要 → 到阈值一刀切压缩（丢工具链） | >40 turns 会话 53 个 |
| **工具回读放大** | 工具输出完整回传 LLM（当前轮 50K chars 上限），日志只记 200 字符 → 回读成本被低估 | 151 次历史截断到 20K |
| **缓存命中率** | 命中 ¥0.02 vs 未命中 ¥1.00（50×）；system prompt 频繁改动 → 前缀缓存失效 | 官方定价；MEMORY 记录缓存未命中 58% 最大成本 |

## 四、降 Token 方案（保质量 / 轻微降质量分层）

### 4.1 P0 已完成（本次会话）

| # | 动作 | 效果 | 质量影响 |
|:-:|:-----|:-----|:--------|
| 1 | knowledge/index.md 全量注入 → 结构摘要注入 | 98K→662 tokens（省 99.3%） | 无损失（组织结构保留，定位靠 read/memory_search） |
| 2 | skills_prompt 去 base_dir + location 相对化 | 14K→11K（省 22%） | 无损失 |
| 3 | `agent_max_steps: 200→40` | 防单任务 token 灾难 | 无损失（正常任务 <40 步） |
| 4 | `agent_max_context_tokens: 50K→110K` + `turns 20→8` | 预算 ≥ system，历史可保留 | **质量提升**（不再失忆） |
| 5 | 飞书引用回复截断 2000 字符 | 防 query 膨胀 | 轻微（引用超长时只保留头部） |

**净效果**：system 118K→18K（省 85%），历史从「必压缩」恢复「8 轮可保留」。

### 4.2 P1 保质量零损失

| # | 方案 | 机理 | 预期收益 |
|:-:|:-----|:-----|:---------|
| 1 | **工具输出分级截断**：当前轮 `MAX_CURRENT_TURN_RESULT_CHARS 50K→20K`、历史 `MAX_HISTORY_RESULT_CHARS 20K→8K` | 工具结果头部即结论，尾部多为日志细节；8K chars ≈ 3K tokens 足够保留有效信息 | 历史项 -40~60% |
| 2 | **长会话主动摘要**（中途 MemoryFlush，而非阈值一刀切）：turns ≥ 12 时主动将前段摘要化，保留工具结论链 | 避免「到阈值才压缩丢工具链」的失忆 | 长会话 tokens -30%，质量反而升 |
| 3 | **缓存命中保护**：system prompt 内容**冻结期**（如 1 周内不因小改动触发全量重发）；builder 输出 hash 校验，仅内容实质变化才重建 | 命中 ¥0.02 vs 未命中 ¥1.00，50× 差距 | 命中率 40%→70%+，总成本 -25~35% |
| 4 | **bash 输出截断**：日志/回传默认 `head -c 4000`（新增约定），大输出（如 grep 大文件、JSON 长列表）显式 `| head` | bash 输出 1.38M chars 是最大回读源 | 回读项 -50% |
| 5 | **read 头部化**：默认 read 只读前 500 行 + 文件统计（`wc -l` 预估），深度需要再全读 | 日志显示 read 常读 2000 行文档全文 | 回读项 -30~50% |

### 4.3 P2 轻微降质量（可接受损失）

| # | 方案 | 损失 | 收益 |
|:-:|:-----|:-----|:-----|
| 1 | **思考 token 管控**：例行/定时任务（日报、检查、归档确认）禁用 thinking 或限 max_thinking_tokens；深度分析保留 | 例行任务少思考深度（但例行任务本就不需要） | 输出 tokens -20~30% |
| 2 | **检查输出模板化**：doc-final-check 模式推广——所有 check 脚本默认只回传「FAIL 行 + 计数」（`--verbose` 才全量） | 丢失通过明细（无决策价值） | 回读 -80%（检查类任务） |
| 3 | **合并小工具调用为脚本**：`python3 -c`/`<<'EOF'` 高频内联（400+ 次）沉淀为 scripts 工具，一次调用替代多次 | 无实质损失 | 请求次数 -10~15% |
| 4 | **群聊 session 隔离**：`group_shared_session=False` 保持默认，多用户历史不混杂 | 无（当前已是 False） | 防未来膨胀 |

## 六、风险与边界

- **估算误差**：input tokens 为估算（±20%），方向性结论（固定开销主导）无争议；费用精确值以 DeepSeek 官方 API 用量为准。
- **工具输出截断风险**：当前轮 20K / 历史 8K 可能丢失「长 diff / 长网页全文」的中间细节 → 若发现深度任务依赖尾部信息，回调阈值（当前轮 30K / 历史 12K）。
- **思考管控风险**：例行任务的思考禁用需按任务类型白名单控制，避免误伤需要推理的定时任务。
- **缓存命中保护风险**：system 冻结期可能延迟必要更新 → 用「紧急改动绕过冻结」例外。
- **read 头部化风险**：500 行内未覆盖关键尾部（如 changelog）→ 由工具返回「文件共 N 行，尾部 X 行摘要」补偿。
