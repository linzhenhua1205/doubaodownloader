## 0. 一句话结论

> **调研追踪文档缩水的根因不在深度技能本身，而在 `research_task_runner.py` 的规则体系**——v1.7 跨组去重硬规则（08-15 新增）、token 管理「省字优先」、丰度校验只认列表项，三重约束把「轻量高频」错误套用在所有产出上。已实施 **A（产出分档）+ B（去重软化）** 组合修复：deep 档输出目标≥30KB 无上限/可读全文/多维丰度校验，track 档维持轻量；跨组去重从「剔除+大段标注」改为「一行交叉引用」，篇幅还给增量。

## 2. 三个根因（按影响排序）

> **来源**: 规则数值（15KB/20K/30 行等）引用自 runner v1.7 docstring 原文（[1]）；8 处剔除标注为 08-17 switch 文件实测（[3]）。

### 根因 1：v1.7 跨组去重硬规则（08-15 新增）——「这两天缩水」的直接元凶

**规则原文**（`research_task_runner.py` v1.7 docstring）:

> 条目已被其他组收录 → 从本组剔除，文件内**逐条诚实标注**「已由<组名>收录」，只保留本组视角增量

**实证**:
- 08-17 switch 文件 46 行中 8 处「剔除」标注（08-14 为 0），近 1/5 篇幅花在「说明我剔除了什么」，有效内容被挤掉
- 08-15 新增 → 08-16/17 立即生效，与时间感知完全吻合

### 根因 2：token 管理规则把「省 token」当成第一目标

**规则原文**（v1.7 docstring）:

> 每个搜索源最多抓取 1 次 · 读前 30 行 · 输出 ≤ 15KB · 总预算 ≤ 20K

**问题机制**:
- verify 里 `size > 15KB → WARN "检查是否过度采集"`——**反向激励压缩**，AI 会把 15KB 当硬目标而非上限（实际只写到 7-8KB）
- 源头信息摄入被「读前 30 行」限制——**想深也没素材**
- 深层矛盾：**「追踪」是产出形态标签，不是深度上限标签**——同一个任务历史上既能产 18KB 深度分析，也能产 7KB 快讯

### 根因 3：丰度校验只认列表项，惩罚段落式深度

**规则原文**（verify 实现）:

```python
finds = len(re.findall(r"^\s*[-*]\s+\*?\*?", content, re.M))  # line-start -/* only
```

**问题机制**:
- 丰度只统计行首 `-`/`*` 列表项，表格/编号不计入（08-04 教训反噬——当初为防止用表格凑数，现在反而禁止了深度分析的正常表达）
- AI 被迫把深度分析压成短列表——列表天然信息密度低、无因果展开，**这是「篇幅缩水+深度变浅」的结构性原因**
- verify 只防「写太少」（0.5KB/2 条），不促「写深」

## 3. 关键澄清：问题不在深度技能

| 层 | 是否有问题 | 说明 |
|:---|:-----------|:-----|
| deep-tech-writer / knowledge-doc-writer / industry-insight 的 SKILL.md | ❌ 无 | 三个深度技能的 SKILL.md 本身**无篇幅限制**，质量标准（Q1-Q6）反而要求深度 |
| research_task_runner.py | ✅ **有问题** | 把「轻量高频」约束**错误套用在所有产出**上；verify 只防「写太少」，不促「写深」 |

**结论**: 修复应落在执行器规则层，而非技能质量标准层。

## 4. 修复方案 A：产出分档

> **来源**: 分档阈值（15/30/60K/3 段）为本方案设计值（[1] 本次修改）；深度档判定依据为产出目录历史文件实测（[3]）。

### 4.1 设计

在 `configs/research_topics.json` 每个任务增加 `depth` 字段：

| 档位 | 字段值 | 输出 | 读取 | 总预算 | 丰度校验 |
|:-----|:-------|:-----|:-----|:-------|:---------|
| **追踪档**（默认） | `track` | ≤15KB | 前 30 行 | ≤20K | 列表项 ≥ min_finds |
| **深度档** | `deep` | ≥30KB 无上限 | 全文 | ≤60K | 列表项 + ≥3 段分析段落 + 表格多维 |

### 4.2 实现（`research_task_runner.py` v1.8）

新增两个辅助函数，各子命令按档位差异化：

```python
def depth_of(cfg) -> str:      # read cfg depth field, default track
def depth_budget(cfg) -> dict: # returns {label, out_max_kb, out_min_kb, read_lines, token_budget, target_hint}
```

| 子命令 | 改动 |
|:-------|:-----|
| `plan` | token 预算行分档：`[token 预算·深度档(deep)] 读全文 · 输出无上限KB · 总预算≤60K` |
| `guide` | ① 档位标注 + target_hint ② 读取规则分档（读全文/读前30行）③ 列表项提示分档（deep 档允许段落+表格） |
| `verify` | ① 丰度多维统计：`finds + paras + tables`，deep 档要求 `finds≥min && paras≥3` ② 大小检查分档：deep 档无上限但 `<15KB → WARN "检查是否被压缩"`（**反向激励反转**：从「太大警告」变「太小警告」） |

### 4.3 分档结果（39 任务）

- **深度档 11 个**：技术组 / 交换机与AI网络 / 互联与光通信 / 分布式OS / 超节点专题 / 服务器硬件 / 大模型动态 / 数据分析 / 可靠性测试 / 集群训练优化 / AI框架
- **追踪档 28 个**：其余（BMC/工具/云原生/政策等轻量高频主题）

**判定依据**: `knowledge/01_survey/<dir>` 存在 `*-deep-analysis*` 文件 或 历史 >15KB 深度文档。

## 5. 修复方案 B：去重规则软化

### 5.1 规则变化

| 版本 | 规则 |
|:-----|:-----|
| v1.7（08-15） | 已被其他组收录 → **剔除 + 逐条诚实标注**「已由<组名>收录」，只留本组视角增量 |
| v1.8（08-17） | 已被其他组收录 → **一行交叉引用**「（已由<组名>收录: <标题>）」，不写大段剔除说明，篇幅留给本组增量 |

### 5.2 实现（3 处）

- docstring 内建规则跨组去重段
- guide ④ 跨组去重提示（第二行）
- （保留）「禁跳过检查，写入后 verify 前再复核」——去重的**检查动作**不变，只软化**标注方式**

**效果预估**: 篇幅回血 20%+（估算来源: 08-17 switch 文件 8 处剔除标注平均每处 3-4 行 → 8 行交叉引用，按行数占比测算 [3]）。

## 7. 遗留与建议

1. **【中】深度档仍受「每源≤1次抓取」约束**：深度分析需要多轮追问/交叉验证，建议 deep 档允许「失败可重试 1 次 + 关键词 2 组变体」（与 check-gap 升级策略对齐）
2. **【中】旧文件回补**：08-14~08-17 被压缩的 switch/supernode 文件，建议按深度档标准择期回补（尤其 08-11 深度分析中断后的主题连续性）
3. **【低】表格不计入丰度是历史教训反噬**：本次 deep 档已允许多维统计，但 track 档仍只认列表项——若 track 档未来也出现「为凑列表项而拆分语义」的问题，可考虑 track 档也升级多维统计（阈值降低即可）
4. **【低】分档阈值是经验值**：deep 档 `≥30KB 目标 / ≥15KB 才算达标` 为首次设定，运行一周后按实际产出分布校准
