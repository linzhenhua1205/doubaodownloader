## 核心命题

BMC 固件升级失败的代价是"服务器变砖"（带外管理不可用），因此**双镜像（A/B 分区 + golden image）是 BMC 可恢复性的底线设计**。但"双镜像"在不同 BMC 架构下的实现哲学截然不同：**AMI（闭源）依赖硬件看门狗被动触发，OpenBMC（开源）依赖软件状态机主动判断**——这不仅是技术路线差异，更是"硬件固化 vs 软件定义"两种工程哲学在可靠性领域的对决。

> 一句话：**AMI 用"硬件强制兜底"保命（简单可靠但僵化），OpenBMC 用"软件状态管理"保命（灵活可扩展但复杂）——理解两者差异，才能理解 BMC 可靠性设计的演进方向。**

---

## 一、原理深潜：双镜像的通用机制

### 1.1 为什么需要双镜像

- BMC 固件升级中途断电/写坏 → 系统无法启动 → 服务器失去带外管理 = **变砖**
- 双镜像方案：**一个 active 分区（运行中）+ 一个备用分区（golden/待更新）**——升级写入备用分区，成功后切换 active；失败则回滚

### 1.2 通用流程

```
写入备用分区 → 设置 active 标志 → 重启
    │                               │
    ├── 启动成功 ──► 确认切换（active 永久生效）
    └── 启动失败 ──► 回滚到原 active 分区（自动恢复）
```

**核心问题**：如何检测"启动失败"？——这正是 AMI 与 OpenBMC 分道扬镳的地方。

## 二、两大架构对比（素材核心 4 维差异）

| 维度 | AMI BMC（闭源 MegaRAC） | OpenBMC（开源 Yocto） |
|:-----|:------------------------|:----------------------|
| **触发机制** | 硬件 FMC_WDT2 看门狗超时 | 软件 bootcount 计数器 + U-Boot 环境变量 |
| **回滚逻辑** | 硬件寄存器直绑（芯片级） | D-Bus 服务链（软件层） |
| **扩展能力** | 闭源固化，超时需改寄存器 | 开源可定制，Yocto meta-layer 跨平台 |
| **原子性** | 硬件级不可中断 | 软件写后验证（update_manager） |

### 2.1 触发机制：硬件看门狗 vs 软件计数器

**AMI：ASPEED AST2600 FMC_WDT2 看门狗**
- U-Boot 之前：**22 秒超时窗口**——BMC 若未完成正常启动，看门狗超时 → 硬件自动切换 golden image
- U-Boot 阶段：超时延长至 **13 分钟**
- BMC 完全启动后：关闭看门狗
- **本质**：硬件级被动触发——芯片内置看门狗寄存器，不依赖上层软件

**OpenBMC：软件定义 A/B 分区**
- U-Boot 环境变量：`active` 分区标志（记录当前活动分区）
- `bootcount` 启动计数器：每次启动递增，**超过阈值判定启动失败**
- 系统始终从已知良好分区启动；新固件后台写入另一分区
- **本质**：软件状态管理——不依赖特定硬件看门狗，通过状态机主动判断

### 2.2 回滚逻辑：硬件寄存器 vs 软件服务链

**AMI**：FMC_WDT2 超时事件直接触发芯片内镜像切换信号，**无需上层软件干预**——响应快，但灵活性受限（调超时需改硬件寄存器配置）。

**OpenBMC 软件服务链**：
```
update_manager（原子写入新固件）
    ↓
phosphor-ipmi-host（运行时监控启动状态）
    ↓
phosphor-logging（D-Bus 日志关联，记录回滚原因）
    ↓
bootcount 超阈值 → 条件回滚（如 Kernel Panic 触发）
```

**OpenBMC 的软件化优势**：
- **条件回滚**：只有特定失败（Kernel Panic、服务起不来）才回滚，普通重启不算失败
- **增量更新**：bsdiff 差分升级，只传变更部分（省带宽）
- **跨平台适配**：Yocto meta-layer 机制，不同硬件平台复用同一套回滚逻辑

### 2.3 原子性：硬件不可中断 vs 软件写后验证

- **AMI**：硬件级切换，一旦触发不可中断——简单粗暴但保证最终一致性
- **OpenBMC**：update_manager 先写入临时分区 → **校验完整（校验和/签名）→ 再标记 active**——写坏不会污染当前运行分区

## 三、工程启示：两种哲学的适用场景

| 场景 | 推荐架构 | 原因 |
|:-----|:---------|:-----|
| 成熟量产、固件稳定 | AMI 闭源 | 硬件兜底简单可靠，无软件依赖 |
| 快速迭代、频繁升级 | OpenBMC | 软件状态机灵活，支持条件回滚/增量更新 |
| 多平台复用 | OpenBMC | Yocto meta-layer 跨平台 |
| 安全合规要求高 | OpenBMC（可审计） | 开源可审计，支持安全签名链 |
| 资源受限设备 | AMI（更省资源） | 硬件逻辑不占软件资源 |

**演进判断**：OpenBMC 正在成为服务器行业主流（OCP 推动），核心驱动力是：
1. 软件定义可靠性 → 更灵活的回滚策略（不是所有失败都回滚）
2. 开源可审计 → 满足安全合规（国密/等保）
3. 可扩展 → GPU/PCIe Switch 等新硬件适配（见 BMC×PCIe Switch 报告）

> **关键认知**：双镜像只是 BMC 可靠性的一个侧面。完整可靠性体系 = 双镜像（固件级） + 看门狗（硬件级） + SEL 日志（事件级） + 冗余 BMC（系统级，部分高端平台）。

## 四、结论

1. **双镜像 = BMC 可恢复性底线**：升级失败不致命，A/B 分区 + 回滚是标准答案
2. **两大哲学**：AMI 硬件看门狗（被动、简单、僵化）vs OpenBMC 软件状态机（主动、灵活、复杂）
3. **OpenBMC 是演进方向**：条件回滚、增量更新、可审计、可扩展——符合软件定义一切的行业趋势
4. **选型看场景**：量产稳定选 AMI，快速迭代/合规要求高选 OpenBMC
5. **与服务器产品研发的关系**：BMC 双镜像设计直接决定 RMA 率与现场运维成本——**可靠性设计是 BMC 的第一优先级**
