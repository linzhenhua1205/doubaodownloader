## （一）发明名称

一种 GPU 训练任务假存活状态的功耗分诊检测方法

## （二）所属技术领域

本发明属于 AI 算力基础设施与集群训练运维技术领域，具体涉及一种基于板卡功耗多态判别的大型分布式训练任务中加速卡"假存活"（Fake Alive）状态的检测与自动恢复方法。

## （三）现有技术（背景技术）

**现有技术方案**：
1. **利用率监控方案**：通过 `utilization.gpu`（SM 活跃 warp 时间占比）监控 GPU 运行状态。该指标由 GPU 驱动周期性采样，仅反映"SM 是否有 warp 在执行"，无法区分"计算在推进"与"空转/自旋等待"。
2. **通信超时/看门狗方案**：NCCL（NVIDIA Collective Communications Library，英伟达集合通信库）提供通信超时机制与 `ncclCommWatchdog` 看门狗，检测通信对端无响应；训练框架（如 PyTorch）侧设置 loss 监控或心跳。
3. **错误码监控方案**：依赖 XID（NVIDIA 驱动错误码）与 CUDA 错误上报，出现硬错误时记录并告警。

**现有技术的客观缺陷**：
1. **利用率指标的"假存活"盲区**：在 NCCL 集合通信死锁场景（如通信算子计数不一致、对端已死但本端 spin-wait）下，GPU 的 `utilization.gpu` 仍可显示 100%——SM 一直在自旋等待标志位，但训练任务没有任何进展。生产集群实测（512-GPU 规模）中，死锁 GPU 呈现"100% 利用率 + 功耗 200-280W 冻结 + SM 时钟钉死在 1950MHz"的特征，现有利用率监控完全无法识别（实测复现：marin#7344）。
2. **超时/看门狗无法覆盖静默死锁**：NCCL 死锁时各 rank 均"存活"（无超时、无错误上报、`failures=0`），通信超时机制与看门狗不会触发——死锁被静默挂起，发现时往往已损失数小时训练时间。
3. **错误码监控只覆盖硬错误**：静默死锁不属于 XID 可上报的硬错误，无任何错误码产生。
4. **单指标判断不可靠**：仅看功耗冻结或仅看利用率 100% 均可能误判——rank 合法等待 collective、等待已死 peer 时产生完全相同的读数。

## （四）发明内容

### 1. 发明要解决的问题

本发明旨在解决现有监控技术无法识别 GPU 训练任务"假存活"（utilization 100% 但任务无进展的静默死锁）状态，导致故障发现延迟、训练时间损失的技术问题。

### 2. 解决方案、具体实施例及附图

#### 解决方案（整体方案概述）

本发明提出一种基于**板卡功耗（power.draw）多态判别**的假存活检测方法。核心思想：功耗是连续量且与实际负载耦合，而 utilization 是饱和二值量——死锁时 GPU 功耗"冻结"（多次采样完全一致），是判别假存活的最强信号。检测流程为：**周期性采集功耗与时钟 → 五态判别表分类 → 四信号合取判据确认假存活 → 触发 checkpoint 自动恢复**。

关键步骤：

1. **功耗-时钟二维特征采样**：以固定周期（如 1-5 秒）通过 GPU 管理接口（如 nvidia-smi 的 `--query-gpu=index,utilization.gpu,power.draw,clocks.sm`）采集每张卡的状态特征，至少包含：功耗值（power.draw，单位 W）、SM 时钟（clocks.sm，单位 MHz）、利用率（utilization.gpu，%）、温度（temperature.gpu）。

2. **五态功耗判别表**：建立加速卡运行状态判别表，按功耗-时钟特征将状态分类：

   | 状态 | 功耗特征 | SM 时钟特征 | 判别依据 |
   |:-----|:---------|:------------|:---------|
   | 计算（健康） | 700-1150W，波动 | 1282-1950MHz 波动 | 功耗随时间变化 = 健康 |
   | 空闲 | 200-230W | 低位 | 低功耗+低时钟 |
   | 死锁（假存活） | 200-280W，冻结 | 钉死 1950MHz | 双采样完全一致 |
   | 数据饥饿 | 中低，缓慢下降 | 低位 | 功耗单调下行 |
   | 通信 | 中高，波动 | 中高位 | 波动+利用率高 |

   其中"冻结"定义为：连续 N 次（如 2-3 次）采样功耗值完全一致（到小数点后两位），且 SM 时钟保持恒定。

3. **四信号合取判据**（单指标不足，必须合取）：判定假存活需同时满足：
   - **信号1 冻结功率**：功耗双采样完全一致到小数点后两位，且持续（如 4 分钟以上仍相同）；
   - **信号2 持续无进展**：训练 loss 或步进计数在检测窗口内无任何变化；
   - **信号3 通信计数缺口**：NCCL 层 RAS 操作计数一致性检查发现缺口（如 AllReduce 操作计数与对端不一致，`MISMATCH Communicator ranks have different AllReduce operation counts`）；
   - **信号4 全 rank 存活**：所有通信 rank 均无硬错误上报（`failures=0`）、无超时。

4. **外部 watcher 转换**：由独立于训练进程的外部监控组件（loss-progress watchdog）执行上述检测，将"静默挂起"转换为"即时拒绝"——检测到假存活即判定故障，不等框架超时。

5. **自动恢复**：确认假存活后，触发训练框架的 checkpoint 恢复流程：保存/加载最近 checkpoint，驱逐故障 rank 或整卡，重新调度训练任务。

#### 具体实施例

以 512-GPU 生产集群中一个 8 卡训练节点为例：

- **实施环境**：GB200（Blackwell 架构）节点，NCCL 2.28.x，PyTorch 分布式训练框架，nvidia-smi 可用。
- **采样配置**：监控组件每 2 秒执行一次 `nvidia-smi --query-gpu=index,utilization.gpu,power.draw,clocks.sm,temperature.gpu --format=csv,noheader`，数据落本地环形缓冲（保留最近 10 分钟）。
- **冻结判定**：连续 3 次采样（6 秒）power.draw 完全一致（如 223.00W、223.00W、223.00W）且 clocks.sm 恒定 1950MHz，标记"疑似冻结"；继续观察 4 分钟，功耗仍不变则确认"冻结"。
- **合取判据执行**：冻结确认后，检查 (a) loss 值 4 分钟无变化；(b) NCCL 日志/计数器显示 AllReduce 操作计数与对端 rank 不一致；(c) 所有 rank `ncclResult` 无错误、无超时告警。四信号全满足 → 判定假存活。
- **恢复动作**：调用训练框架 checkpoint API 保存当前状态，标记故障 GPU 从通信组驱逐，调度器将剩余 rank 重映射到健康 GPU，从最近 checkpoint 继续训练。
- **对比效果**：未采用本方案时，该故障在人工巡检中发现（数小时）；采用本方案后，检测+恢复在分钟级完成。

### 3. 发明的优点

1. **识别可靠**：以功耗双采样一致性为主信号，规避 utilization 饱和二值量的"假存活"盲区；四信号合取判据避免单指标误判（rank 合法等待、对端已死等场景）。
2. **发现及时**：故障发现从人工巡检的"小时级"缩短到自动检测的"分钟级"，减少训练时间损失（生产实证：死锁特征在 4 分钟窗口内稳定可判）。
3. **零成本可迁移**：仅依赖 nvidia-smi 标准接口，无需额外埋点或硬件改动，任何 nvidia-smi 可用的集群均可立即部署。
4. **机理明确**：功耗连续量反映 GPU 真实工作负载，冻结=既无升频也无降频的完全恒定状态，物理上不可能出现在健康计算中（健康计算功耗必然波动）。

## （五）最想保护的关键点

1. **区别于现有技术，本发明**以板卡功耗（power.draw）双采样一致性作为训练任务"假存活"检测的主判别信号，替代 utilization 单指标监控。
2. **本发明的创新点在于**：建立功耗-时钟二维五态判别表（计算/空闲/死锁/数据饥饿/通信），实现加速卡运行状态的实时分类识别。
3. **本发明的创新点在于**：采用"冻结功率 × 持续无进展 × 通信计数缺口 × 全 rank 存活"四信号合取判据确认假存活，克服单指标误判。
4. **本发明的创新点在于**：进程外 watcher 将静默挂起转换为即时拒绝，并联动 checkpoint 自动恢复的完整闭环。
5. **本发明的创新点在于**：该检测方法零成本可迁移（仅依赖标准 GPU 管理接口），适用于大规模生产集群的预防性监控。
