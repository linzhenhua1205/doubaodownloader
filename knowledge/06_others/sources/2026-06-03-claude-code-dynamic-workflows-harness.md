## 内容摘要

Claude Code 现在能针对具体任务自己写调度脚本（Dynamic Workflows），实时生成动态 Harness。文章讲清六种调度模式（分类路由/扇出合并/对抗验证/生成过滤/锦标赛/循环到完成）、六个实战场景，以及何时不需要工作流。**结尾核心洞察：Harness 可能像 prompt engineering 一样是模型发展中的中间状态——模型够强后这些编排逻辑会被内化。**

## 原文核心内容

### 背景：单 Agent 的三个已知退化模式

Claude Code 默认单 Agent（一个上下文窗口搞定规划和执行）。但长时间运行/大规模并行/需对抗性验证的任务有三个退化模式：

| 退化模式 | 表现 | 本质 |
|:---------|:-----|:-----|
| **偷懒** | 50 个检查项查到 20 个就宣布完成 | 长上下文中的行为退化，非幻觉 |
| **自我偏爱** | 评判自己的产出天然给好评 | 严格验证场景致命 |
| **目标漂移** | 上下文压缩有损，每压一次丢边缘条件 | 优化目标逐渐偏离原始任务 |

> 关键判断：这三个问题不是模型能力问题，是**单上下文窗口同时承担规划和执行的架构局限**。

### 动态 vs 静态工作流

- **静态工作流**：用 Agent SDK / `claude -p` 编排，提前写好脚本考虑边界情况，比较通用
- **动态工作流**：Claude Code 自己看任务、自己写调度脚本，针对当前任务量身定制（Opus 4.8 能力已足够）
- **体验**：已知怎么拆分的任务→静态更可控；"大概知道要做什么但不确定最优拆分"→动态更省事

### 六种调度模式（可组合）

| # | 模式 | 原理 | 解决 |
|:-:|:-----|:-----|:-----|
| 1 | **分类路由** | 分类 Agent 判断任务类型分发给处理 Agent；或最后加分类器定输出格式 | 任务分发 |
| 2 | **扇出合并** | 拆成小步各配独立 Agent，最后合并 Agent 汇总 | 上下文干净互不污染 |
| 3 | **对抗验证** | 每个生成 Agent 配独立验证 Agent 专门挑毛病 | 自我偏爱 |
| 4 | **生成过滤** | 先大量生成，再按标准筛选去重 | 质量筛选 |
| 5 | **锦标赛** | N 个 Agent 不同策略做同一事，两两比较淘汰 | 相对比较优于绝对评分 |
| 6 | **循环到完成** | 不设固定轮次，跑到满足停止条件 | 迭代收敛 |

> 组合示例：先扇出 → 分支内对抗验证 → 合并时锦标赛选最优。

### 六个实战场景

1. **大规模迁移重构**（Bun Zig→Rust 案例）：拆独立单元（调用点/失败测试/模块）→ 各派子 Agent 在独立 worktree 修 → 对抗 Review → 通过再合并。价值最大：避免上下文丢失和交叉污染。
2. **深度验证**：Agent 提取全部事实性声明 → 每个声明派子 Agent 核实 → 可再加一层验证引用源可靠性。
3. **排序**（如按 Bug 严重度排 1000 工单）：锦标赛两两比较，比较判断比绝对评分可靠。
4. **规则遵守**：一条规则一个验证 Agent，用怀疑论者视角查违规；反向：扫 session 日志找反复纠正模式→聚类验证→提炼成 CLAUDE.md 规则。
5. **根因分析**：分别从日志/文件变更/数据状态生成独立假设，每个假设配验证者和反驳者——结构性避免"认定一个假设一路追到底"。不只代码：销售数据下降/管道故障/复盘都适用。
6. **大规模分流**：分类去重→自动修复或升级。**隔离区设计**：读不可信外部内容的 Agent 不允许执行高权限操作，读和写分离防 prompt injection 越权。

### 什么时候不需要工作流

- 动态工作流 token 消耗显著更多，适合复杂高价值任务
- **判断标准**：能在 Prompt 里一句话说清 + 做完能自己快速验证 → 不需要
- 需要工作流的两个特征：①任务可拆成独立并行单元 ②验证成本高到不想一个个查

### 用法与技巧

- 触发：Prompt 里直接要求创建，或用触发词 `ultracode`
- 描述调度模式要具体（六种模式名可直接用），不要只说"用工作流"
- 可重复工作流配 `/loop`（定期执行）+ `/goal`（硬性完成条件）
- 防跑飞：加"用 10k token"限制消耗
- 运行中按 `s` 保存脚本到 `~/.claude/workflows` 或通过 Skill 分发团队

### 核心洞察（与用户独立判断同源）

> **"Harness 可能也像 prompt engineering 一样，是大模型发展过程中的一个中间状态。模型不够强的时候需要人写精巧的调度逻辑，需要多个 Agent 互相制衡才能把一件事做好；模型足够强了，这些逻辑就会被内化。今天你还在想怎么编排子 Agent，也许下一代模型根本不需要外部编排，自己就能在内部完成任务分解和对抗验证。"**（Feisky 编译文结尾）

## 批判辩证分析

- **论点强度**：强。六种模式有明确的问题-解法对应（对抗验证↔自我偏爱、锦标赛↔绝对评分失真、隔离区↔prompt injection），不是概念堆叠
- **数据可信度**：中。Bun Zig→Rust 案例、Opus 4.8 能力均为转述，无量化性能数据（无 token 成本对比、无成功率指标）
- **反方视角**：①动态工作流"自己写 Harness"仍受模型能力上限约束——模型写调度脚本本身也可能退化；②token 消耗显著更高，ROI 边界未量化；③"内化"论是推测，原文未给时间窗
- **时效性**：2026-06-03 发布，Anthropic 官方博客同源，8 月中旬归档仍具时效性

## 底层原理补充

**为什么多 Agent 制衡有效（第一性原理）**：单上下文窗口的退化（偷懒/偏爱/漂移）本质是**反馈回路闭合**——生成与验证共用同一信念状态，无法独立纠错。多 Agent 通过**独立性**打破回路闭合（验证 Agent 无生成者的立场包袱），与知识库 loop-verification"验证独立性四条件"完全同构。动态工作流的"动态"在于把**编排元逻辑**（何时拆/怎么验/如何合并）从人转移到模型——这是 Harness 内化过程的第一步实证。

## 市场机会

- **需求侧**：大规模重构/深度验证/规则治理是高价值刚需场景，动态工作流降低 Harness 使用门槛（不用人写编排）
- **落地路径**：静态→动态→内化的三阶段：动态工作流可保存为静态复用（Claude 已支持 `/workflows` 持久化）
- **风险**：token 成本失控（需预算约束）、模型自写 Harness 的质量不可控、多 Agent 的编排复杂度过高反噬
