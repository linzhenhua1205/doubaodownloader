## 1. 引言：产品研发视角的权限问题

### 1.1 问题的本质

权限问题的技术层面——RBAC、ABAC、OAuth 2.0、SELinux——已有大量理论和实现。但有一个更根本的问题被大多数人忽略：

> **当一个功能涉及权限风险时，是消灭这个功能，还是给它配上管理机制？**

选「消灭」很轻松：删代码、改文档、发公告「此功能因安全原因下线」——KPI 好看，安全审计过关。
选「管理」则痛苦：要设计配置界面、定义角色权限、写策略引擎、搭审计管道、做用户培训——成本高、周期长、还可能被吐槽「太复杂了不会用」。

但产品研发的决定性思维是：**为少数负面场景消灭一个有价值的功能，比功能本身的问题更严重。**

### 1.2 为什么这个话题发生在 AI Agent 与飞书交互的场景？

当 AI Agent（小龙猫）接入飞书平台，一个核心能力是**读取和处理用户消息**。这立即触发了权限敏感点：

```text
用户说: "帮我查一下上周的服务器故障记录"
  -> Agent 读取消息内容
  -> Agent 调用知识库 / BMC API
  -> Agent 回复结果
```

这条链路中，Agent「读了用户的消息」——这在飞书消息权限框架中是一个敏感操作。传统安全思维的第一反应是：

> ❌ 「不能让 AI 读消息，万一泄露了怎么办？」

但问题在于：**不让 AI 读消息，AI 就什么都做不了。** 这相当于为了保护轮胎不爆胎，把车拆了。

### 1.3 本文档的定位

本文档不是重复 RBAC 技术实现（见关联文档），而是解决一个**产品研发决策问题**：

| 问题 | 本文回答 |
|:-----|:---------|
| 发现权限风险时，第一反应是什么？ | 不是「消灭」，是「分析」 |
| 什么情况该消灭？什么情况该转移？ | 给出决策矩阵 |
| 权限管理应该一步到位还是分期建设？ | POC→产品化分阶段模型 |
| IT 在其中起什么角色？ | 权限架构的拥有者 |
| 针对飞书消息这个具体场景怎么做？ | 完整方案 + 管理机制清单 |

## 2. 核心矛盾：转移还是消灭？

### 2.1 三种选择

面对一个权限问题，产品研发者的工具箱里有三种选择：

```text
发现权限风险
     |
     +---> 消灭 (Eliminate)
     |     移除功能/能力，彻底消除风险
     |     例: 「不允许 AI 读取飞书消息」
     |
     +---> 转移 (Transfer)
     |     将权限控制权交给合适的角色
     |     例: 「由 IT 管理员配置 AI 可读哪些空间的消息」
     |
     +---> 管理 (Manage)
           保留能力，增加管控机制
           例: 「AI 可读消息，但处理后立即丢弃，不存储」
```

| 维度 | 消灭 🗑️ | 转移 🔄 | 管理 🛡️ |
|:-----|:-------:|:-------:|:--------:|
| **安全等级** | 最高（零风险） | 中高（可控风险） | 中（残余风险） |
| **产品价值** | 归零 | 保留 | 保留 |
| **实施成本** | 低 | 中 | 高 |
| **用户负担** | 无（但功能没了） | 依赖管理员配置 | 需理解管控规则 |
| **可逆性** | 不可逆（恢复困难） | 可逆（重配即可） | 可逆（改策略） |
| **适用场景** | 风险 > 收益 | 需要专家判断 | 可标准化管控 |

### 2.2 「消灭」是最危险的默认选项

在实际产品研发中，「消灭」往往是默认选项，因为：

1. **安全部门的 KPI**：零安全事故 = 消灭风险 = 绩效达标
2. **研发的惰性**：设计管理机制比删代码难 10 倍
3. **决策者的规避心理**：「做错了被追责」>「做对了没奖励」
4. **用户不在决策现场**：功能消灭了，用户只是「不能用」，不会当面抗议

但消灭的隐性成本极高：

```text
消灭一个功能 = 失去一个产品差异化点
             + 失去用户信任（为什么这个功能没了？）
             + 失去后续迭代的可能性
             + 打击研发团队士气（做了白做）
```

### 2.3 「转移」是最优雅的解耦

转移的本质是：**权限决策权从功能实现者转移到权限拥有者。**

```text
消灭: 研发决定「不安全 -> 删掉」
转移: IT 决定「这个场景可以开放 / 这个场景必须禁止」
管理: 研发设计机制，让 IT 的决策可执行
```

> **核心原则**: 研发不替 IT 做权限准入判断，研发只提供权限管理工具。

这正是用户提到的「由合适的人来解决，IT 有对应的权限」——IT 是权限的**所有者**，研发是权限管理**工具**的提供者。

### 2.4 转移 vs 消灭的决策树

```text
发现权限风险
     |
     v
+----------------------+
| 这个功能的核心价值    |
| 是否大于风险？        |
+------+------+--------+
       |      |
    是(继续)  否(消灭) <- 价值很低的功能可以直接消灭
       |
       v
+----------------------+
| 风险是否可以量化管控？ |
+------+------+--------+
       |      |
    是(继续)  否
       |      |
       v      v
+--------------+  +----------------------+
| 管理或转移    |  | 风险不可量化         |
| 二选一        |  | v                    |
|              |  | 能否通过架构设计      |
|              |  | 将风险控制在可量化范围？|
|              |  | v        v            |
|              |  | 能(管理)  否(消灭)     |
+--------------+  +----------------------+
```

## 3. POC→产品化的分阶段权限模型

### 3.1 核心思想：权限不能一步到位

最致命的权限设计错误是：第一天就追求「完美的权限系统」。

结果往往是：

- 花 3 个月设计权限模型 → 上线时需求已经变了
- 权限配置极其复杂 → 无人会用 → 全部默认开放 → 等于没有权限
- 安全审计要求「完善」→ 研发堆砌功能 → 臃肿不可维护

正确的做法是**分阶段演进**：

```text
Phase 0: Bootstrap    -> "裸跑，但要能看见"
Phase 1: POC          -> "宽松，但要能控制"
Phase 2: Productize   -> "标准，但要可配置"
Phase 3: Scale        -> "智能，但要可审计"
```

### 3.2 Phase 0: Bootstrap（启动期）

**目标**: 快速验证产品价值，权限问题先挂账

```text
权限状态:  ⚠️ 几乎无管控
关注点:    ✅ 功能跑通，价值验证
周期:      1-2 周
```

| 维度 | 做法 | 理由 |
|:-----|:-----|:------|
| **AI 读消息** | 允许全部读取 | 核心功能依赖，无法拆分 |
| **AI 写操作** | 全部允许（但日志记录） | 验证功能完备性 |
| **数据存储** | 临时存储，手动清理 | 不做自动生命周期管理 |
| **审计** | 输出日志到文件 | 最简单的「能看到」 |

**风险接受**: 明确告知所有参与者「这是实验阶段，数据不做持久化保护」

**退出条件**: 核心功能验证通过，价值判断成立

### 3.3 Phase 1: POC（验证期）

**目标**: 在可控范围内验证权限管理机制

```text
权限状态:  🟡 宽松但可控制
关注点:    ✅ 管理机制雏形，风险边界清晰
周期:      2-4 周
```

| 维度 | 升级 | 管理方式 |
|:-----|:------|:---------|
| **AI 读消息** | 仍允许全部读取 | 增加「消息处理记录」展示给用户 |
| **用户授权** | 用户首次使用需确认 | 飞书卡片确认「已了解消息会被 AI 处理」|
| **作用范围** | 指定空间/群组 | 管理员配置白名单空间 |
| **AI 写操作** | 关键操作需用户确认 | 重启服务器等操作弹出确认卡片 |
| **数据生命周期** | 处理后立即丢弃 | 不持久化存储消息原始内容 |
| **审计** | 结构化审计记录 | 可查询「AI 处理了哪些消息」|

**关键变化**: 从「无管控」到「有管控但很轻」

**退出条件**: 管理机制可运行、风险被理解、用户反馈积极

### 3.4 Phase 2: Productize（产品化期）

**目标**: 标准化的权限管理框架，可配置、可审计、可扩展

```text
权限状态:  ✅ 标准化管控
关注点:    ✅ 产品级权限管理，企业可用
周期:      4-8 周
```

| 维度 | 设计 | 方式 |
|:-----|:------|:------|
| **RBAC 角色定义** | 3 个默认角色 | 管理员 / 运维 / 只读用户 |
| **Scope 配置** | 管理员可配置 | 消息读取范围、API 调用范围 |
| **策略执行点** | 内置策略引擎 | YAML 策略配置，热加载 |
| **审批流程** | 高风险操作需审批 | 飞书审批流程打通 |
| **用后即丢** | 自动生命周期管理 | 消息处理后 5 分钟自动清除 |
| **审计面板** | 可视化审计日志 | 操作溯源、异常检测 |
| **用户自服务** | 用户可查看自己消息的处理记录 | 透明可控 |

**关键变化**: 从「研发说了算」到「管理员配置、用户自服务」

**退出条件**: 覆盖 80% 场景、管理员可独立配置、安全审计通过

### 3.5 Phase 3: Scale（规模化期）

**目标**: 智能化的动态权限管理，ABAC + 自动化

```text
权限状态:  🟢 精细智能管控
关注点:    ✅ 规模化、自动化、智能化
```

| 维度 | 升级 |
|:-----|:------|
| **从 RBAC 到 ABAC** | 基于环境属性动态计算权限（时间/地点/设备/风险评分） |
| **自动风险评分** | 对 AI 的每个操作进行实时风险评分 |
| **自适应管控** | 低风险自动放行，高风险触发审批 |
| **跨层权限同步** | 飞书角色 → BMC 角色 → OS 角色的自动映射 |
| **合规报告** | 自动生成 SOC2/GDPR 合规报告 |

**关键变化**: 从「静态配置」到「动态自适应」

### 3.6 阶段演进的核心原则

```text
   Phase 0       Phase 1       Phase 2       Phase 3
+----------+  +----------+  +----------+  +----------+
| 先做事    |->| 可观察    |->| 可配置    |->| 自动化    |
| 后补管理  |  | 再控制   |  | 再优化   |  | 再智能   |
+----------+  +----------+  +----------+  +----------+
     |              |             |             |
     v              v             v             v
  全开放        白名单        RBAC          ABAC
  无审计        文件级日志   结构化审计     智能审计
```

> **关键教训**: 不要在 Phase 0 尝试搭建 Phase 3 的权限系统。
> 第一天最重要的不是「权限完美」，而是「功能有价值」。
> 如果功能本身没有价值，完美的权限系统就是资源浪费。

## 4. 飞书消息权限：实战场景分析

### 4.1 消息流全景

先看一条消息从发送到处理的完整链路：

```text
用户发送消息
    |
    v
+--------------+
| 飞书服务器    |  <- 消息在飞书端已加密存储
| 消息队列      |
+------+-------+
       | Webhook / Event Callback
       v
+--------------+
| Agent 平台    |  <- 接收到消息事件
| (本工作空间)  |
+------+-------+
       | 消息明文进入 Agent 上下文
       v
+--------------+
| LLM 推理     |  <- 大模型处理消息内容
| (DeepSeek)   |
+------+-------+
       | 生成回复 + 触发工具调用
       v
+--------------+
| Agent 执行   |  <- 读知识库/写文件/调BMC API
| 工具调用     |
+------+-------+
       | 返回结果
       v
+--------------+
| 发送回复     |  <- 通过飞书 API 回复用户
| 到飞书       |
+--------------+
```

### 4.2 权限相关的四个核心问题

| # | 问题 | 涉及层面 | 风险等级 |
|:-:|:-----|:--------|:-------:|
| Q1 | **Agent 能否读取所有消息？** | 读权限 | 🔴 |
| Q2 | **Agent 读取的消息存多久？** | 数据留存 | 🟡 |
| Q3 | **Agent 能否以用户身份发消息？** | 写权限 | 🔴 |
| Q4 | **Agent 处理的消息能否被审计？** | 可追溯性 | 🟡 |

#### Q1: Agent 能否读取所有消息？

**现状**: 当前飞书机器人收到的是所在群/单聊中的消息事件

**风险分析**:

| 风险 | 概率 | 影响 | 说明 |
|:-----|:----:|:----:|:------|
| 用户发送敏感信息被 AI 处理 | 中 | 高 | 密码/密钥/商业机密 |
| AI 误解消息导致错误操作 | 低 | 中 | LLM 理解偏差 |
| 非目标用户发送消息被处理 | 低 | 低 | 群聊场景 |
| 消息被 AI 用于训练 | 低 | 高 | 隐私合规 |

**转移方案**: 由 IT 管理员配置 AI 的消息读取范围

```text
配置项: 消息读取范围
+-- 仅读取 @机器人 的消息 (最安全)
+-- 读取指定空间/群组的所有消息 (推荐)
+-- 读取用户单聊消息 (需用户授权)
+-- 读取所有消息 (仅 Phase 0/1)
```

#### Q2: Agent 读取的消息存多久？

**现状**: 消息进入 Agent 上下文处理，完成后不主动删除

**「消灭」方案**: 不让 AI 看到消息 → 功能不可用

**「管理」方案**: 用后即丢 + 生命周期管理

```text
消息处理生命周期:

  收到消息 ---> [临时上下文] ---> 处理完成 ---> [丢弃]
     |                                  |
     | 仅存于 LLM 上下文窗口             |
     | (DeepSeek 端也不持久化)           |
     |                                  |
     ^                                  ^
  可保留到日终归档 (Phase 0)          即时丢弃 (Phase 2+)
```

**实现方式**:

| 阶段 | 消息保留策略 | 依据 |
|:-----|:------------|:------|
| Phase 0 | 保留到 memory/ 日终日志 | 便于排查问题 |
| Phase 1 | 处理后标记「已处理」，保留 24h | 日活期内可追溯 |
| Phase 2 | 处理后 5 分钟自动清除 | 满足大多数企业合规 |
| Phase 3 | 按数据分类策略（敏感→即时清除，普通→按需保留） | 精细化管控 |

#### Q3: Agent 能否以用户身份发消息？

**风险**: Agent 可能冒充用户发送消息

**现状**: 机器人使用自己的身份（Tenant Token）发送，不能冒充用户

这是当前设计中的一个**天然保护**——Agent 的消息显示为「小龙猫」，用户的消息显示为用户本人，双向不可冒充。

```text
用户: "帮我发个消息给张三说下午开会"
Agent: "好的，我将以机器人身份在张三的对话中发送通知"
      v
实际效果: 张三收到「小龙猫 邀请你下午开会」
而不是: 「王五 说下午开会」
```

**转移方案**: 需要以用户名义发送时，必须由用户授权临时代理：

```text
用户请求代发消息
    |
    v
Agent 请求用户授权
    |
    v
用户通过飞书卡片确认「授权小龙猫以我名义发送此消息」
    |
    v
获取 User Access Token (Scope: im:message:send_as_user)
    |
    v
发送一次 -> Token 自动过期
```

#### Q4: Agent 处理的消息能否被审计？

**审计需求**: 企业合规要求「所有数据处理操作都有记录」

**实现方案**:

```text
审计记录格式:

{
  "timestamp": "2026-07-28T13:50:37+08:00",
  "message_id": "om_abc123",
  "user_id": "ou_xyz789",
  "action": "process_message",
  "message_type": "text",
  "message_length": 142,         <- 只记录长度，不记录内容
  "response_tokens": 856,        <- 处理耗用资源
  "tools_called": ["read", "search"],  <- 触发了哪些工具
  "processing_status": "completed",
  "trace_id": "trace_001"
}
```

> **关键设计**: 审计记录保存**操作元数据**（谁、何时、做了什么），
> 不保存**消息内容本身**（除非用户明确授权内容审计）。

### 4.3 消息权限的「消灭」场景模拟

让我们模拟一下如果在飞书消息权限上选择「消灭」会发生什么：

```text
场景: 安全部门发现「AI Agent 读取了包含客户信息的飞书消息」

消灭方案的执行链:
  1. 安全要求: 禁止 AI 读取任何飞书消息
  2. 研发实现: 关闭消息事件接收，仅保留「关键词回复」功能
  3. 业务影响:
     - ❌ 用户不能问「帮我查...」——AI 看不懂问题
     - ❌ 上下文对话能力归零——每次都是独立触发
     - ❌ 多轮交互死亡——AI 记不住上一句
     - ❌ 知识库查询必须手动触发——不能通过对话调起
  4. 最终结果: 产品倒退到「关键词回复 bot」的水平
```

**对比「管理」方案**:

```text
管理方案的执行链:
  1. 安全要求: AI 读取消息必须在可控范围内
  2. 研发实现:
     - 消息读取范围可配置（@消息/指定空间/全部）
     - 消息处理后自动丢弃（用后即丢）
     - 所有处理记录可审计
     - 敏感关键词自动脱敏/中断
  3. 业务影响:
     - ✅ 用户照常使用
     - ✅ IT 可配置控制
     - ✅ 合规可审计
     - ✅ 安全风险可控
  4. 额外收益: 积累了权限管理能力，后续功能复用
```

### 4.4 从飞书消息看普适规律

飞书消息权限的讨论，实际上揭示了权限管理的**通用范式**：

```text
任何涉及「读取用户输入」的功能，都可以用这个框架分析:

                    +--------------+
                    | 读用户输入    |
                    +------+-------+
                           |
              +------------+------------+
              |                         |
         +----v-----+             +-----v------+
         | 消灭:     |             | 管理:       |
         | 不读不碰   |             | 可控地读    |
         +----------+             | + 用后即丢  |
                                  | + 可审计    |
                                  | + 范围配置  |
                                  +------------+
```

消灭的套路永远是同一句话：**「有风险，别做了」**
管理的套路永远是同一个模式：**「可以读，但要读得清楚、用完就丢、丢了可查」**

## 5. IT 的角色：谁有权限解决问题？

### 5.1 权限责任分离矩阵

在产品研发中，权限问题涉及三个角色，各有不同的责任：

| 角色 | 负责什么 | 不负责什么 |
|:-----|:---------|:-----------|
| **研发团队** | 提供权限管理工具和机制 | **不做权限准入判断** |
| **IT 管理员** | 配置权限策略、决定开放范围 | 不决定功能有无 |
| **最终用户** | 在授权范围内使用功能 | 不设计权限规则 |

### 5.2 当前问题：研发代替 IT 做了准入判断

在目前的 AI-Feishu 平台中，存在一个**责任错位**：

```text
当前状态:
  研发团队  ->  决定 AI 能做什么 ->  实现功能 ->  交给 IT
              ^
              研发自己判断「这个功能安不安全」

理想状态:
  研发团队  ->  提供管理工具 ->  IT 管理员  ->  配置权限
                                                    v
                                              用户使用功能
```

**具体表现**:

| 场景 | 现状（研发判断） | 理想（IT 判断） |
|:-----|:----------------|:----------------|
| AI 是否能读消息？ | 研发说「可以读」 | IT 配置「哪些空间的消息可读」 |
| AI 是否能执行 bash？ | RULE.md 写「永不 rm」 | IT 配置「bash 允许哪些命令」|
| 消息保留多久？ | 研发说「保留到 memory」 | IT 配置「消息保留周期」|
| 哪些用户可用 AI？ | 飞书应用对全员开放 | IT 配置「允许的部门/人员」|

### 5.3 IT 的权限管理工具需求清单

要让 IT 真正成为权限的决策者，研发需要提供以下工具：

```text
IT 需要的权限管理能力:
+-------------------------------------+
| 1. 范围配置:                        |
|    □ AI 可读取哪些空间的消息        |
|    □ AI 可操作哪些服务器            |
|    □ 哪些 API 可被 AI 调用          |
+-------------------------------------+
| 2. 角色定义:                        |
|    □ 预定义角色 (管理员/运维/只读)  |
|    □ 自定义角色 (可配置权限组合)    |
+-------------------------------------+
| 3. 审计面板:                        |
|    □ 操作记录查询                   |
|    □ 异常行为告警                   |
|    □ 合规报告导出                   |
+-------------------------------------+
| 4. 用户自服务:                      |
|    □ 用户可查看自己的操作记录       |
|    □ 用户可管理自己的授权           |
|    □ 用户可撤回授权                 |
+-------------------------------------+
```

> **核心原则**: 研发提供「管理面板」，IT 做「管理决策」。
> 研发不替 IT 问「这个功能安不安全」，研发只回答「这个功能怎么管」。

### 5.4 「转移」给 IT 的实操路径

以飞书消息权限为例，如何把决策权「转移」给 IT：

```text
Step 1: 研发实现消息读取范围配置
  +-- 管理后台增加「消息读取范围」配置项
  +-- 可选值: [仅@消息, 指定空间, 全部]

Step 2: IT 在管理后台配置
  +-- IT 管理员选择「仅@消息」
  +-- 原因: 公司内部消息太多，不想全部被 AI 处理

Step 3: 系统按 IT 配置执行
  +-- 非@消息：不进入 AI 上下文，直接忽略
  +-- @消息：正常处理

结果: IT 做了决策，研发提供了工具，各司其职。
```

对比反面案例：

```text
Step 1: 研发自己判断
  +-- 「全部读取有风险，我们只读@消息」
  +-- 写死在代码里

Step 2: 上线后 IT 问：
  +-- 「能不能让 AI 读取全部消息？」（有些群没有@的习惯）
  +-- 研发：不行，写死了
  +-- IT：那我换方案
```

## 6. 管理机制目录：不消灭，这么管

当决定「不消灭」一个功能时，需要一套管理机制来替代。以下是**完整的机制目录**，按管控力度排序：

### 6.1 范围控制（Scope Control）

| 机制 | 说明 | 实现成本 | 用户体验影响 | 适用阶段 |
|:-----|:------|:-------:|:-----------:|:--------:|
| **白名单模式** | 仅允许指定范围 | 低 | 低 | Phase 1+ |
| **黑名单模式** | 排除指定范围 | 低 | 低 | Phase 1+ |
| **分级授权** | 不同角色不同范围 | 中 | 中 | Phase 2+ |
| **动态范围** | 基于属性计算范围 | 高 | 低 | Phase 3 |

### 6.2 数据生命周期（Data Lifecycle）

| 机制 | 说明 | 隐私保护强度 | 实现成本 |
|:-----|:------|:-----------:|:-------:|
| **用后即丢** | 处理完成立即丢弃 | 🟢 高 | 低 |
| **T+1 清理** | 次日自动清除 | 🟡 中 | 低 |
| **按策略保留** | 分类分级保留 | 🟢 高 | 高 |
| **用户自删除** | 用户可删除自己的数据 | 🟢 高 | 中 |

### 6.3 用户授权（User Consent）

| 机制 | 说明 | 合规满足 | 实现成本 |
|:-----|:------|:-------:|:-------:|
| **首次确认** | 首次使用弹出授权确认 | GDPR 基本满足 | 低 |
| **按次确认** | 每次操作前确认 | GDPR 严格满足 | 高（影响体验） |
| **按类确认** | 同类操作一次性授权 | 平衡方案 | 中 |
| **静默授权+可撤回** | 默认授权但可随时撤回 | 最佳实践 | 中 |

### 6.4 操作用户确认（Confirmation）

| 机制 | 说明 | 安全性 | 实现成本 |
|:-----|:------|:-----:|:-------:|
| **只读不确认** | 查询类不需确认 | 🟢 用户体验好 | 低 |
| **写操作确认** | 写/删/改需用户确认 | 🟢 关键保护 | 中 |
| **高危操作审批** | 重启服务器等走审批流 | 🟢 最高保护 | 高 |
| **时间窗口限制** | 仅工作时间可操作 | 🟡 附加保护 | 低 |

### 6.5 审计追踪（Audit Trail）

| 机制 | 说明 | 覆盖度 | 实现成本 |
|:-----|:------|:-----:|:-------:|
| **操作日志** | 记录操作时间和类型 | 基础 | 低 |
| **结构化审计** | 谁/何时/做了什么/结果 | 完整 | 中 |
| **实时告警** | 异常操作实时通知管理员 | 智能 | 高 |
| **合规导出** | 自动生成合规报告 | 企业级 | 高 |

### 6.6 速率控制（Rate Control）

| 机制 | 说明 | 效果 | 实现成本 |
|:-----|:------|:-----:|:-------:|
| **QPS 限制** | 每秒请求数上限 | 防止滥调用 | 低 |
| **日配额** | 每天处理消息上限 | 控制总成本 | 低 |
| **关键词限流** | 特定关键词触发频率限制 | 敏感信息防护 | 中 |

### 6.7 综合应用示例

以「AI 读取飞书消息」场景为例，组合使用多种机制：

```text
场景: AI Agent 接入飞书群聊，回答技术问题

管理机制组合:

1. 范围控制:   读取 @机器人 的消息 + 指定技术群 (IT 配置)
2. 数据生命周期: 处理后 5 分钟自动清除 (默认)
3. 用户授权:    群成员首次使用自动弹出「同意消息被 AI 处理」
4. 操作用户确认: 读取消息不需确认，写操作（创建文档等）需确认
5. 审计追踪:    记录每个消息处理的元数据
6. 速率控制:    每个群每小时最多 200 条处理
```

> **效果**: 没有消灭任何功能，但每个风险点都有对应的管控机制。
> 用户照常使用，IT 可配置，安全合规可审计。

## 7. 决策矩阵：什么情况转移？什么情况消灭？

### 7.1 四象限判断矩阵

```text
                    功能价值
                  低           高
         +-------------------------+
     高  |   消灭 🗑️        转移/管理 🔄 |
         |   (低价值高风险的       (高价值高风险的
         |    功能不值得投入)       需要管理机制)       |
风险程度   |                          |
     低  |   接受 ✅          管理 🛡️   |
         |   (低价值低风险的       (高价值低风险的
         |    无需额外投入)         加强观察即可)       |
         +-------------------------+
```

### 7.2 具体判断条件

#### 🗑️ 消灭条件（四个条件满足任意两个）

| 条件 | 判断标准 | 示例 |
|:-----|:---------|:-----|
| 功能价值低 | 使用率 <5%，且无增长趋势 | 冷门遗留功能 |
| 风险不可控 | 无法通过配置/机制降低风险 | 消息明文存储到不可信第三方 |
| 存在替代方案 | 用户可通过其他方式完成 | AI 自动发邮件（用户可手动发）|
| 合规红线 | 违反法律/行业规范 | GDPR 禁止的自动决策 |

#### 🔄 转移条件

| 条件 | 判断标准 | 示例 |
|:-----|:---------|:-----|
| 决策需领域知识 | 需要有人判断「这个场景是否安全」| IT 判断消息范围 |
| 风险边界清晰 | 可以明确「什么范围可做」| 指定空间、指定群 |
| 存在对应的角色 | 组织内有人对此负责 | IT 管理员、安全官 |

#### 🛡️ 管理条件

| 条件 | 判断标准 | 示例 |
|:-----|:---------|:-----|
| 风险可量化 | 可以用指标衡量 | 写操作次数、API 调用量 |
| 有标准化的管控方式 | 有现成的机制可用 | RBAC、白名单、审计日志 |
| 用户可理解 | 用户可以理解「为什么被限制」| 「写文档要确认」|

#### ✅ 接受条件

| 条件 | 判断标准 | 示例 |
|:-----|:---------|:-----|
| 风险极低 | 影响范围极小，危害极低 | AI 读取技术类消息 |
| 管控成本 > 风险成本 | 花 100 万管一个可能损失 100 块的风险 | —— |

### 7.3 工程实践中的典型案例

| 场景 | 功能价值 | 风险 | 决策 | 理由 |
|:-----|:-------:|:----:|:----|:------|
| AI 读取飞书消息 | 🔴 高（核心功能） | 🟡 中 | **转移/管理** | 高价值，风险可管控 |
| AI 自动重启服务器 | 🟡 中 | 🔴 高 | **转移** | 需要 IT 配置白名单服务器 |
| AI 删除知识库文件 | 🟢 低 | 🔴 高 | **消灭** | 有替代方案（标记为废弃） |
| AI 读取服务器传感器温度 | 🟡 中 | 🟢 低 | **接受** | 只读操作，无危害 |
| AI 用用户身份发消息 | 🔴 高 | 🔴 高 | **转移** | 通过 OAuth 临时代理 |
| AI 自动创建飞书文档 | 🟡 中 | 🟡 中 | **管理** | 加确认步骤 |

### 7.4 动态调整：决策不是一次性的

权限决策不是「决定就不改了」——需要随着产品演进动态调整：

```text
Phase 0: 消灭/接受为主
  +-- 功能不确定是否有价值，不投太多管理成本

Phase 1: 转移为主
  +-- 价值初步确认，引入 IT 参与决策

Phase 2: 管理为主
  +-- 价值确认，投入完整管理机制

Phase 3: 精细化
  +-- 成熟的权限体系，动态调整
```

## 8. 权限演进的「不可逆关口」

### 8.1 什么是不可逆关口？

权限演进中有一个危险时刻——当权限从「宽松」走向「收紧」时，**一旦收紧就很难再放松**。

```text
        宽松 <------------> 收紧
        Phase 0    Phase 1    Phase 2    Phase 3
        全开放     白名单     RBAC       ABAC
          |          |          |          |
          v          v          v          v
        +------+  +------+  +------+  +------+
        |自由   |  |可控   |  |标准   |  |智能   |
        +------+  +------+  +------+  +------+
                             ^
                         不可逆关口
                         一旦收紧到 RBAC，
                         退回白名单模式极其困难
```

**为什么不可逆？**

1. **用户习惯了限制**：「原来不让做这个」→ 打开后用户质疑安全性
2. **安全基线已建立**：安全审查要求保持 RBAC 级别
3. **合规要求固化**：文档写了「权限遵循 RBAC 标准」
4. **代码复杂度**：管理机制代码已嵌入，移除成本高

### 8.2 不可逆关口的影响

这意味着：**POC 阶段不要太松，产品化阶段不要太紧。**

```text
太松的 POC:
  用户习惯「什么都能用」
  -> 收紧时用户反弹
  -> 安全部门已经注意到

太紧的产品化:
  IT 配置复杂，无人会用
  -> 默认开放所有权限（等于没有）
  -> RBAC 形同虚设

平衡点:
  POC: 宽松但有基线（可观察、可审计）
  产品化: 标准但不复杂（默认角色 + 简洁配置）
```

### 8.3 跨越不可逆关口的策略

| 策略 | 说明 | 适用场景 |
|:-----|:------|:---------|
| **渐进收紧** | 每次收紧一点点，给用户适应期 | 大多数场景 |
| **新用户新政策** | 新用户直接走新权限，老用户过渡期 | 大版本升级 |
| **Opt-in 收紧** | 让用户主动选择更严格的安全模式 | 企业合规需求 |
| **可逆设计** | 权限配置保留「宽松模式」选项 | 不确定最终策略时 |

> **经验法则**: POC 阶段就要植入「权限可配置」的基因，
> 不要写死任何权限策略，始终保留向 IT 转移决策权的接口。

## 9. 设计建议与落地路径

### 9.1 三层架构建议

将飞书-AI 平台的权限管理设计为三层：

```text
+-----------------------------------------------------+
| L3: 策略执行层 (PEP)                                 |
|                                                      |
|  功能: 拦截所有 AI 操作 -> 匹配策略 -> 放行/拒绝/审批   |
|  实现: YAML 策略引擎 + 热加载                          |
|  关键: 不消灭功能，只拦截超出权限的操作                 |
+----------------------+------------------------------+
                       |
+----------------------v------------------------------+
| L2: 管理配置层 (Admin UI)                            |
|                                                      |
|  功能: IT 管理员配置权限策略                           |
|  内容:                                              |
|  - 消息读取范围配置                                   |
|  - 角色定义与分配                                    |
|  - 操作审批规则                                      |
|  - 数据保留策略                                      |
|  关键: IT 做决策，研发只做工具                         |
+----------------------+------------------------------+
                       |
+----------------------v------------------------------+
| L1: 执行审计层 (Audit)                               |
|                                                      |
|  功能: 记录全部操作，提供审计查询                      |
|  内容:                                              |
|  - 结构化操作日志                                    |
|  - 用户操作查询入口                                   |
|  - 异常行为告警                                       |
|  - 合规报告导出                                      |
|  关键: 让「可审计」成为安全部门的信心来源               |
+-----------------------------------------------------+
```

### 9.2 当前工程落地的优先级

基于本工作空间（~/cow）当前阶段，建议按以下优先级推进：

#### P0 🚨 消息处理「用后即丢」

```text
当前: 消息进入 Agent 上下文后，未主动清理
改进:
  - 每次 session 结束后清理临时上下文
  - 不在 memory/ 中存储消息原文
  - 仅存储操作元数据（谁在何时问了什么问题类型）
```

#### P1 🟠 IT 转移接口

```text
当前: 权限策略硬编码（写死在代码/RULE.md 中）
改进:
  - 将「消息读取范围」提取为配置项
  - 将「高危操作列表」提取为配置项
  - 提供简单的 YAML 或飞书文档配置方式
```

#### P2 🟡 审计可视化

```text
当前: 无系统级审计，仅 memory/ 日志
改进:
  - 为每个消息处理生成结构化审计记录
  - 审计记录不含消息原文，仅含元数据
```

### 9.3 快速验证：最小可行管理机制

如果想在 1 天内看到一个可运行版本：

```text
Step 1: 加一条配置项 (10 分钟)
  在 config.yaml 中添加:
  ```

  message_scope: "@only"    # @only | group_only | all

  ```text

Step 2: 根据配置过滤消息 (1 小时)
  ```

  if config.message_scope == "@only":
      if not is_at_me(event):
          return  # 忽略非@消息

  ```text

Step 3: 审计记录 (1 小时)
  ```

  audit_log = {
      "timestamp": now(),
      "user": event.user_id,
      "action": "process",
      "message_type": event.type,
      "message_length": len(event.text),
      "scope": config.message_scope
  }
  write_audit_log(audit_log)

  ```text

效果: 一个可配置的消息读取范围 + 基础审计
功能: IT 可配置 -> 研发不替 IT 做准入判断
```

> **这就是「转移」的精髓**: 不是消灭功能，而是把决策权交出去。

### 9.4 核心原则总结

```text
+---------------------------------------------------------+
|                                                         |
|  权限管理的产品哲学核心原则                                |
|                                                         |
|  1. 不替 IT 做准入判断                                  |
|     -> 提供管理工具，让 IT 决策                             |
|                                                         |
|  2. 不为少数负面场景消灭功能                              |
|     -> 功能存在的理由 > 被滥用的可能                       |
|                                                         |
|  3. 分阶段建设，不一步到位                               |
|     -> Phase 0 先跑通，Phase 2 再产品化                    |
|                                                         |
|  4. 「用后即丢」是最轻量有效的保护                       |
|     -> 不存储 = 不泄露 = 最安全                           |
|                                                         |
|  5. 可审计 > 不可操作                                   |
|     -> 让安全部门看到「能查到」比「不能做」更安心           |
|                                                         |
|  6. 控制权转移 ≠ 甩锅                                  |
|     -> 提供好工具，让 IT 做出更好的决策                    |
|                                                         |
+---------------------------------------------------------+
```
