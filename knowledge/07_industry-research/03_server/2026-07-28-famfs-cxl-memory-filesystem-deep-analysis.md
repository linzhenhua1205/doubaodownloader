## §1 概述：为什么要另一个文件系统？

### 1.1 动机：CXL 大内存的「文件系统缺口」

CXL (Compute Express Link) 作为缓存一致的互联协议，正在将数据中心内存从「每 CPU 本地附着」转变为「池化共享资源」。CXL Type 3 设备（内存扩展器）可以在单台服务器上提供 **2-8TB** 的额外内存，而 CXL Switch 连接的池化拓扑可达 **数十 TB** 的共享内存池。

> **核心矛盾**：CXL 提供了物理上可达的巨大内存容量，但操作系统缺少一个「让多进程/多主机高效使用这块内存」的抽象层。

当前 CXL 内存的使用方式有三种，但各有局限：

| 使用方式 | 机制 | 局限 |
|:---------|:-----|:------|
| **kmem 驱动 (NUMA node)** | 将 CXL 内存注册为新的 NUMA 节点，应用通过 `numactl` 或默认内存分配使用 | ① 无文件语义，不能跨主机共享 ② 应用必须显式 NUMA 感知 ③ 热迁移困难 |
| **block device (brd/PMEM)** | 通过 `pmem` 驱动将 CXL 内存暴露为块设备，在其上创建传统文件系统 | ① **页缓存双重拷贝** — 块设备 I/O 需要页缓存做中介，浪费 CXL 内存的字节寻址能力 ② 写入放大 |
| **DAX 直连** | 通过 `/dev/dax` 字符设备做 direct map，应用绕过内核直接 mmap | ① 无文件层级 ② 单主机独占 ③ 无法分配/回收子区域 |

**famfs 填补的正是这个缺口**：一个原生基于 **DAX (Direct Access)** 的共享文件系统，让 CXL 内存既具有文件语义（路径、权限、大小），又保留字节寻址的零拷贝访问，同时支持**跨主机共享**。

### 1.2 famfs 的定位：文件系统缝隙中的新物种

```text
传统分层:
  +--------------------------+
  |      Application         |
  +--------------------------+
  |    mmap / read/write     |
  +--------------------------+
  |   Page Cache (DRAM)      |  <- 页缓存做中介
  +--------------------------+
  |   Block Layer / VFS      |
  +--------------------------+
  |     Block Device         |
  +--------------------------+
  |   NVMe / SSD / HDD       |  <- 块语义，非字节寻址
  +--------------------------+

famfs 分层:
  +--------------------------+
  |      Application         |
  +--------------------------+
  |    mmap (DAX 直通)        |  <- 零拷贝，无需页缓存
  +--------------------------+
  |   famfs (VFS DAX)        |  <- 文件语义 + 共享
  +--------------------------+
  |   CXL Type 3 Device      |
  +--------------------------+
  |   CXL.mem (字节寻址)      |  <- 缓存一致的内存语义
  +--------------------------+
```

famfs 的设计核心：**在 VFS 层直接操作 CXL 内存的物理地址映射，不走块层、不走页缓存。**

## §2 背景材料：CXL 内存生态全景

### 2.1 CXL 内存的三种接入方式

CXL 规范定义了三种设备类型，对内存语义的支持逐级增强：

| 类型 | 功能 | 内存语义 | 适用的文件系统 |
|:-----|:------|:---------|:--------------|
| **Type 1** | CXL.io + CXL.cache | 仅缓存，无本地内存 | N/A |
| **Type 2** | CXL.io + CXL.cache + CXL.mem | 本地内存 + 加速器（如 GPU CXL 端口） | 受限 |
| **Type 3** | CXL.io + CXL.mem | **纯内存扩展器** | ✅ **famfs 目标** |

Type 3 设备是 famfs 的直接目标硬件：这些设备（如 Astera Labs Leo、Samsung CMM-D、SK hynix CMM）本质上是 **PCIe 插卡形式的 DDR5 DIMM 扩展器**，通过 CXL.mem 协议暴露字节可寻址内存。

### 2.2 从「容量补丁」到「第一级存储」

CXL 内存的认知经历了三个阶段：

**Phase 1 (2019-2023)：容量补丁**
- 核心用例：本地内存不够时的远程扩展
- 典型方案：kmem 驱动注册 NUMA node，`numactl` 手动分配
- 认知局限：CXL 内存 ≈ 慢速本地内存（补充角色）

**Phase 2 (2024-2026)：共享基础设施**
- **核心转变**：CXL 内存的价值不在于「大」，而在于「共享」
- 驱动事件：Azure CXL VM (2025-11) ✅、Beluga CXL KV Cache (2024) ✅、HyMCache 生产级推理 (2026-06) ✅
- 关键洞察：CXL 内存延迟 (150-400ns) 虽然高于本地 DDR5 (80-100ns)，但远低于 NVMe (5-100μs)。对 KV Cache、模型 weight 这类大容量、中频访问的负载，CXL 是**性价比最优的 Tier**

**Phase 3 (2027+)：计算-内存分解**
- 超节点架构下 CXL 成为 Scale-Up 域的**数据传输平面**
- GPU 原生 CXL 3.0+ 端口将 CXL 内存直接暴露给加速器
- famfs 的角色：从「文件系统」升级为「内存池化语义层」

### 2.3 内核 CXL 支持现状

截至 Linux 7.2-rc5 (2026-07)，内核 CXL 子系统已经支持：

| 组件 | 状态 | 功能 |
|:-----|:-----|:------|
| **cxl/核心** | 主线 ✅ | CXL 设备发现、枚举、Link 训练、DDT (Device DVSEC Table) |
| **cxl/pmem** | 主线 ✅ | CXL PMEM (持久内存) 的 block+DAX 双模式 |
| **cxl/mem** | 主线 ✅ | CXL Type 3 volatile 内存的 kmem 驱动 |
| **kmem 驱动** | 主线 ✅ | CXL 内存注册为 NUMA node |
| **DAX (core)** | 主线 ✅ | 包括 dev-dax (字符设备) 和 fs-dax (文件系统) |
| **ext4/xfs DAX** | 主线 ✅ | 支持 DAX 挂载的 DAX 文件系统 |
| ****famfs** ** | **讨论中** | **专为 CXL 共享内存设计的 DAX 文件系统** |
| **CXL Region** | 主线 ✅ | 内存区域的管理与分配 |
| **CXL Switch** | 主线 ✅ | CXL Switch 的发现与拓扑管理 |

## §3 技术框架：famfs 架构

### 3.1 核心设计理念

famfs 的设计可以抽象为三个核心决策：

**决策 1：DAX-first**
- 不做块设备抽象，直接在 VFS 层操作物理地址
- 文件数据 = 物理内存页的直接映射，不需要页缓存做中介
- 对上层暴露标准的 POSIX 文件接口（open/read/write/mmap）

**决策 2：共享优先**
- 默认设计为**多主机可同时访问**同一个物理内存区域
- 通过 CXL Switch 或 CXL.mem 设备的全局物理地址可见性实现
- 一致性模型：**弱一致性** — 由应用或上层库管理同步

**决策 3：轻量元数据**
- 元数据结构极简（区别于 ext4/xfs 的复杂元数据）
- 元数据存放在 CXL 内存中，与数据共存，无需额外的持久化存储
- 设计原则：**数据平面通过 DAX 零拷贝，元数据平面通过标准 VFS 调用**

### 3.2 架构全景

```text
+-----------------------------------------------------+
|                    Application                       |
|   (LLM推理引擎 / 内存数据库 / 图分析引擎 / ...)       |
+---------------------+-------------------------------+
                      |
              mmap() / read() / write()
                      |
+---------------------v-------------------------------+
|   VFS (Virtual File System)                          |
|    +----------------------------------------------+  |
|    |          famfs.ko (内核模块)                   |  |
|    |  +------------------+  +------------------+  |  |
|    |  |  famfs_inode_ops  |  |  famfs_file_ops  |  |  |
|    |  |  · create/unlink  |  |  · mmap(DAX)     |  |  |
|    |  |  · lookup/rename  |  |  · read/write    |  |  |
|    |  |  · permission     |  |  · fallocate     |  |  |
|    |  +------------------+  +------------------+  |  |
|    |  +------------------------------------------+ |  |
|    |  |  famfs_super_ops (superblock operations)  | |  |
|    |  |  · alloc_inode / destroy_inode           | |  |
|    |  |  · sync_fs / statfs                      | |  |
|    |  +------------------------------------------+ |  |
|    +----------------------------------------------+  |
+---------------------+-------------------------------+
                      |
              DAX Operations
                      |
+---------------------v-------------------------------+
|   dax_operations (内核 DAX 子系统)                    |
|   通过 dev_dax / fs_dax 获取物理页的 direct mapping    |
+---------------------+-------------------------------+
                      |
              CXL.mem protocol
                      |
+---------------------v-------------------------------+
|   CXL Type 3 Device (硬件)                           |
|   · DRAM behind CXL Controller                      |
|   · 暴露为 PCIe Function -> CXL.mem 地址空间          |
|   · 可被多个 host 访问（通过 CXL Switch）              |
+-----------------------------------------------------+
```

### 3.3 DAX 语义详解

DAX (Direct Access) 是 famfs 的基石。理解 DAX 的设计差异是理解 famfs 的关键。

**传统的存储文件系统路径**：
```
mmap(file) -> 页缓存分配 -> 缓存一致性维护 -> 回写块设备
```
- 读：缺页 → 从块设备读入页缓存 → 映射到用户空间
- 写：写入页缓存 → 脏页追踪 → 定时/同步回写块设备
- **两次拷贝**：存储介质 ↔ 页缓存 ↔ 用户空间

**DAX 文件系统路径**：
```
mmap(file) -> 直接建立物理地址 -> 用户空间虚拟地址映射
```
- 读：缺页 → 直接映射物理页（来自 CXL 内存） → 用户空间可见
- 写：直接写入 CXL 物理内存 → 无需回写（volatile 内存）
- **零拷贝**：用户空间 ←直通→ CXL 物理内存

> **为什么对 CXL 重要**：CXL Type 3 设备是 volatile（易失）内存，不像 NVDIMM 需要持久性。这意味着 DAX 的「写后不需要持久化」特性天然匹配 CXL 的 volatile 语义 — 没有 PMEM 的 flushes/fences 开销。

### 3.4 共享访问与一致性模型

famfs 的设计面对的最根本挑战是**多主机共享**：

**共享的实现机制**：
- 物理层：CXL Switch 可以在一组 host 间共享 CXL 内存设备的地址空间
- 内核层：famfs 通过 **`dax_device`** 的共享映射实现多个 namespace 对同一物理地址的访问
- 文件层：多个 host 挂载同一 famfs 实例后，看到的文件层级是全局一致的（元数据共享在 CXL 内存中）

**一致性模型：显式同步**

| 模型 | famfs | NFS | 本地文件系统 |
|:-----|:------|:----|:-----------|
| 单 host 一致性 | ✅ 保证 | ✅ 保证 | ✅ 保证 |
| 跨 host 读后读 | ✅ 保证 | ✅ 保证 | N/A |
| 跨 host 写后读 | ❌ 需显式同步 | ✅ 协议保证 | N/A |
| 跨 host 原子操作 | ❌ | ❌ | N/A |

设计选择：famfs 不提供硬件级的缓存一致性（CXL.mem 本身是缓存一致的，但文件系统层的语义一致性需要额外的 fencing）。这是**有意的架构选择** — 性能优先，一致性由上层框架管理。

## §4 技术栈：从硬件到应用

### 4.1 完整栈层级

```text
层级                | 组件                         | 职责
--------------------+------------------------------+--------------------------
L7   Application    | AI推理引擎/DB/图分析          | 通过 mmap/file 使用 CXL 内存
                    |                              |
L6   Runtime        | libc / jemalloc / tcmalloc    | 内存分配与文件访问封装
                    |                              |
L5   VFS            | famfs.ko (内核模块)           | 文件语义、权限、目录层级
                    |                              |
L4   DAX 层         | dax_ops / fs_dax              | 物理页映射管理
                    |                              |
L3   CXL Core       | cxl/mem (cxl_mem.ko)          | CXL 设备发现/初始化/DDT
                    |                              |
L2   PCIe 层        | CXL Type 3 as PCIe function  | 链路训练/配置空间/中断
                    |                              |
L1   CXL 协议       | CXL.mem @ PCIe Gen5/6/7 PHY  | 缓存一致事务/地址转换
                    |                              |
L0   物理层         | DDR5 DIMM + CXL Controller    | 实际数据存储
```

### 4.2 CXL 设备发现与初始化

famfs 的初始化流程在内核 CXL 子系统之上：

```
CXL 热插拔/启动
    |
    v
PCIe 枚举 -> 识别 CXL Type 3 Function
    |
    v
cxl/mem 驱动绑定 -> 读取 DVSEC (Designated Vendor-Specific Extended Capability)
    |
    v
初始化 CXL.mem 协议 -> 建立 HPA (Host Physical Address) 映射
    |
    v
注册 DAX 设备 (dev_dax)
    |
    v
famfs 挂载 -> 读取超级块 (在 CXL 内存中) -> 建立 VFS tree
    |
    v
应用通过文件路径 mmap -> famfs -> dax ops -> 直接映射到 CXL 物理内存
```

**关键决策点**：超级块的位置。
- famfs 将超级块（包含 inode table、目录结构等元数据）**存放在 CXL 内存的首部区域**
- 这意味着元数据本身也是 DAX 可达的，元数据操作同样是零拷贝

### 4.3 内核 VFS 集成点

famfs 在内核中需要与 VFS 的以下子系统交互：

| VFS 子系统 | 集成点 | famfs 如何实现 |
|:-----------|:-------|:--------------|
| **inode allocation** | `alloc_inode` | 直接从 CXL 内存分配 inode（DAX 映射区域） |
| **page cache** | `address_space_operations` | 绕过 page cache，通过 DAX `direct_access` 回调 |
| **dentry cache** | `dentry_operations` | 复用标准 dcache，但 inode 数据在 CXL 内存中 |
| **mmap** | `mmap` file op | 调用 `dax_iomap_fault()` 建立直接映射 |
| **write** | `write_iter` | 写入 DAX 映射页，volatile 内存无需 fsync |
| **fallocate** | `fallocate` | 在 CXL 内存位图中标记已分配区域 |

**对 iomap 的依赖**：famfs 使用内核的 `iomap` 框架来管理物理地址范围的映射，这是现代内核文件系统标准做法。

## §5 底层原理深潜

### 5.1 为什么不是现有的文件系统？

这是理解 famfs 设计动机的最关键问题。现有两种方案为什么不适用？

**方案 A：ext4 + DAX** — 复杂度过高

ext4 是为块设备设计的日志文件系统，它的元数据结构假设：
- 块编号 → 物理扇区号的间接映射
- Extent tree → 管理连续的块范围
- Journal (jbd2) → 日志事务，保证崩溃一致性

当 ext4 用 DAX 模式挂载时，这些元数据层仍然存在，带来的问题是：
- **元数据访问路径仍会经过内核的复杂代码**
- **日志是不必要的开销**（CXL volatile 内存不需要崩溃恢复）
- **inode table 的分配策略**假设存储是慢速设备，不适合 CXL 的字节寻址
- **块组的 bitmap 管理**增加了不必要的抽象

**方案 B：tmpfs** — 没有共享语义

tmpfs (基于 ramfs) 也是在内存中建立文件系统，但设计差异显著：

| 维度 | tmpfs | famfs |
|:-----|:------|:------|
| 内存来源 | **内核 slab/page allocator** (动态分配) | **CXL 设备预映射物理地址** |
| 数据路径 | 页缓存 → swap | DAX 直通 — 无页缓存 |
| 跨主机共享 | ❌ 不支持（内核内存是 per-host 的） | ✅ 通过 CXL 物理地址可达性 |
| 持久性 | 完全易失（关机丢失） | 易失（CXL Type 3 volatile） |
| 元数据位置 | 内核内存 (kmem) | CXL 内存（与数据同地址空间） |
| 容量定义 | 动态（由可用 RAM 限制） | 静态（由 CXL 设备容量定义） |

tmpfs 的设计决定了它**无法跨主机共享** — 内核地址空间是 per-instance 的，没有办法让两个不同 host 的内核 slab 分配到同一块物理地址。

### 5.2 DAX 对文件系统设计的根本影响

famfs 的架构核心是 DAX-first，这带来与传统文件系统截然不同的设计约束：

**约束 1：物理地址预先确定**
```
传统 FS:  文件 block -> FS 分配空闲块 -> 映射到逻辑块号 -> block layer 翻译到物理
famfs:    文件 -> 分配 CXL 物理页范围 -> 直接通过 DAX 做 page table 映射
```
- famfs 的文件分配是**物理地址分配**，不是逻辑块号分配
- 分配粒度：支持 4KB 页到 2MB 大页

**约束 2：无缓存一致性问题（volatile）**
- 传统 DAX（最初为 NVDIMM 设计）必须处理持久化语义：`msync()`, `fsync()`, persistent memory flushes (`CLFLUSHOPT`, `CLWB`)
- CXL volatile 内存**不需要持久化** — 关机即丢失
- 这使 famfs 比 PMEM 模式的 DAX 文件系统简单得多：
  - 不需要 `dax_flush()` 或 `pmem_flush()`
  - 不需要 write-back cache 的 fencing
  - mmap 后直接使用，无需考虑断电场景

**约束 3：共享一致性由硬件保障部分**
- CXL.mem 协议提供**硬件缓存一致性** — 多个 host 的 CPU 对同一地址的访问通过 CXL 协议自动保持 coherency
- 但文件系统级的元数据一致性（如两个 host 同时 `mkdir`）需要额外的锁机制
- famfs 的设计选择：**元数据操作通过 CAS (Compare-And-Swap) 原子操作在 CXL 内存中实现轻量锁**

### 5.3 元数据管理的设计空间

famfs 的元数据设计面临的核心问题：**元数据放在哪？**

| 方案 | 元数据位置 | 优点 | 缺点 |
|:-----|:-----------|:-----|:------|
| **A: 全部在 CXL 内存** | 与数据共享同一物理区域 | ① 统一管理 ② 所有 host 可见 ③ zero-copy | ① 元数据操作竞争 ② 需要原子原语 |
| **B: 在本地 DDR5** | 元数据在 host 本地内存 | ① 元数据快 ② 无竞争 | ① 各 host 元数据不一致 ② 无法共享目录 |
| **C: 混合** | 关键元数据在 CXL，缓存在本地 | 折中 | 复杂度高 |

**famfs 选择方案 A**：全部元数据（超级块、inode table、目录项）存放在 CXL 内存的预分配区域。这是实现「共享文件系统」语义的必要条件 — 如果元数据在本地，无法做到跨主机的文件命名空间统一。

**代价**：元数据操作的延迟由 CXL 的往返延迟决定（150-400ns），而不是本地内存的延迟（80-100ns）。

### 5.4 共享 vs 独占的架构权衡

famfs 的「共享」有多个层次，每个层次都有设计取舍：

**L1：单主机多进程共享（与本地文件系统相同）**
- 通过标准 VFS lock + inode 引用计数
- ✅ 显然是正确的

**L2：多主机共享同一 CXL 设备**
- 通过 CXL Switch 实现：多个 host 各自挂载 famfs，指向同一 CXL 内存区域
- 核心挑战：**分布式锁**
- 设计选择：**租约 (lease) 而非锁 (lock)** — 减少跨主机 RTT 开销
  - 创建文件：获取写入租约（有限时间内独占写权限）
  - 读文件：无需租约
  - 租约超时：自动释放（由 CXL 内存中的超时计数器管理）

**L3：多主机 + 故障域隔离**
- 一个 host 崩溃后如何处理其持有的租约？
- 设计选择：**租约期限 + 心跳监控** — 其他 host 看到租约过期后可回收
- 这是一个有意的「不完美一致性」选择：可能丢失少量元数据操作，但保证整体系统不阻塞

### 5.5 内核合并争议的核心问题

famfs 在 LSFMM+BPF 2024/2025/2026 连续三年讨论仍未合入主线，核心争议集中在三个问题上：

**争议 1：是否需要一个新的文件系统？（200+ 邮件讨论）**
- **反对者观点**：可以在现有 DAX 文件系统（ext4/xfs DAX mode）基础上，增加 CXL 共享扩展层
- **famfs 团队观点**：ext4/xfs 的日志、块分配、扩展属性等厚度是「不必要的税」，专有设计可以比「扩展现有 FS」简单 60%
- **当前共识**：倾向于 famfs 是独立实现，但需要在代码复用（如 DAX 基础设施）上做更好

**争议 2：共享一致性模型**
- 社区部分成员要求 famfs 提供更强的跨主机一致性保证
- famfs 团队坚持弱一致性 + 应用管理，认为强制强一致性会损失性能优势
- **争议根源**：不同的用户场景对一致性有不同要求。AI 推理可以接受弱一致性，但文件系统元数据操作需要更强保证

**争议 3：代码量与审查负担**
- famfs 实现约 3000-5000 行内核代码
- 社区部分维护者认为「每新增一个文件系统都是长期的审查负担」
- **背后的真实问题**：famfs 的设计是否足够「简单」到可以被长期维护？

**判断** 🟡：架构未完全收敛，预计还需要 1-2 个大版本周期（即 Linux 7.4-7.6 左右）才能合入。

## §6 使用场景分析

### 6.1 AI 推理：KV Cache 共享

**场景描述**：LLM 推理的 KV Cache 占用大量 HBM（单请求 1-10GB），传统方案在 HBM 不足时换出到 CPU DRAM 或 NVMe，延迟代价大。

**CXL + famfs 的解法**：
```
GPU HBM (fast, ~5TB/s, expensive)
    |
    +- 活跃 KV Cache (当前推理请求)
    |
    +--> CXL Memory (via famfs, ~64GB/s per x16, cheaper)
        <- 历史会话的 KV Cache 放在 CXL 内存中
        <- 新请求需要时通过 CXL 快速加载回 HBM
```

**为什么 famfs 是关键的**：
- 不通过 famfs，只能用 kmem 驱动将 CXL 内存暴露为 NUMA node
- 但 kmem 无法做到**文件语义的共享** — 多 GPU 进程无法通过文件名引用同一段 KV Cache
- famfs 提供路径名索引 + 权限控制 + 进程间共享的文件映射

**性能预期**：
- KV Cache 换入延迟：从 NVMe 的 5-100μs → CXL 的 0.5-1μs
- 单机推理吞吐提升：2-5×（取决于模型大小和 batch size）
- [来源: HyMCache, arXiv 2026-06] — CXL KV Cache 的端到端验证

### 6.2 AI 训练：Checkpoint/Weight 快速恢复

**场景描述**：万卡集群训练中，Checkpoint 保存/恢复是高频操作。当前方案将模型 weight 写入 NVMe/分布式存储，恢复时读回，延迟 30秒-数分钟。

**CXL + famfs 的解法**：
```
训练过程中 -> 直接将 weight snapshots 写入 famfs 的 CXL 内存文件
崩溃恢复时 -> 其他 host 通过 mmap 直接映射同一物理内存 -> 恢复时间从分钟级降至毫秒级
```

**数据**：
- Checkpoint 大小：70B 模型约 140GB，1T 模型约 2TB
- NVMe 读取：7 GB/s (Gen5) → 140GB 约 20 秒
- CXL 读取：单个 x16 链路约 64 GB/s → 140GB 约 2.2 秒；多链路聚合可达 1 秒内
- **CXL 优势**：物理上是同一个内存页面，不需要「传输」，只需要建立页表映射

### 6.3 内存数据库：跨主机大表共享

**场景描述**：Redis / Memcached / 内存数据库的 slave 节点需要从 master 同步全量数据，传统方案通过 TCP 传输。

**CXL + famfs 的解法**：
- master 将数据库写入 famfs 文件
- slave 通过 CXL Switch 直接 mmap 同一 famfs 文件
- **零拷贝数据同步**：slave 直接访问 master 写入的物理内存页面

**性能预期**：
- 100GB 数据集同步：TCP 网络 0.5-5 秒 (40-400Gbps) → CXL 共享 ~50μs（仅建立页表）
- 但需要处理**写冲突** — 不是所有数据库场景都适合

### 6.4 数据分析：图分析与内存计算

**场景描述**：图分析引擎在数 TB 的图数据上做遍历，数据需要被多个计算节点同时读取。

**CXL + famfs 的解法**：
- 图数据的一次性加载到 CXL 内存
- 多个计算节点通过 famfs mmap 共享同一地址空间
- 遍历过程中的随机访问享受 CXL.mem 的缓存一致性

**Micron 的验证**：CXL 解聚式内存 + FAMFS 在图数据库场景实现 **20× 加速**。
[来源: Micron CXL Strategy, from knowledge/02_rd/03_hardware/01_hw_core/cxl-40-hymcache-memory-pooling-ecosystem-deep-analysis.md]

### 6.5 微服务：进程间数据传递

**场景描述**：微服务架构中服务间的数据共享（如模型推理的中间结果、特征缓存）。

**CXL + famfs 的解法**：
- 服务 A 将输出写入 famfs 文件
- 服务 B 通过 mmap 读取（可在同一 host 或不同 host）
- 避免序列化/反序列化 + TCP 传输开销

**与现有 IPC 的对比**：

| IPC 方式 | 延迟 | 带宽 | 跨主机 | 零拷贝 |
|:---------|:----:|:----:|:------:|:------:|
| Unix Socket | 1-10μs | ~10Gbps | ❌ | ❌ |
| RDMA | 1-3μs | 200-400Gbps | ✅ | ✅ |
| **CXL + famfs** | **0.2-1μs** | **64-768Gbps** | **✅** | **✅** |
| 共享内存 (shm) | 0.1μs | 带宽级 | ❌ | ✅ |

famfs 在跨主机场景下提供接近本地共享内存的性能，这是其最核心的差异优势。

### 6.6 场景量化对比

| 场景 | 当前方案延迟 | famfs 预期延迟 | 延迟改善 | 关键收益 |
|:-----|:-----------:|:--------------:|:--------:|:---------|
| KV Cache 换入 | 5-100μs (NVMe) | 0.5-1μs | **10-100×** | 推理吞吐 |
| Checkpoint 恢复 | 20s (NVMe, 140GB) | 1-2s | **10-20×** | 训练有效时间 |
| 数据库全量同步 | 0.5-5s (TCP, 100GB) | 50μs | **10⁴-10⁵×** | 同步窗口 |
| 图分析遍历 | 网络延迟主导 | 本地内存级 | **10-100×** | 分析速度 |
| 微服务 IPC | 1-10μs | 0.2-1μs | **5-10×** | 服务延迟 |

## §7 性能分析

### 7.1 数据路径对比

famfs 和传统方案在数据路径上的核心差异决定了性能边界：

```
传统 CXL 块设备 + 文件系统:
  app mmap -> page cache alloc -> (缺页) CXL mem read -> page cache -> usermap
  写: app write -> page cache dirty -> 回写 CXL block
  路径: app -> VFS -> page cache -> block layer -> CXL blk -> CXL mem
  额外拷贝: 1次数据拷贝 (CXL mem -> page cache)
  额外延迟: 页缓存分配 + 缺页 + 潜在回写

famfs:
  app mmap -> (缺页) direct map -> CXL mem -> usermap (零拷贝)
  写: app write -> CXL mem (无回写)
  路径: app -> VFS -> DAX -> CXL mem
  额外拷贝: 0
  额外延迟: 仅缺页时的页表填充
```

### 7.2 延迟分解

带 famfs 的 CXL 内存访问延迟分解：

| 组件 | 延迟 (典型值) | 说明 |
|:-----|:------------:|:------|
| CXL.mem 链路往返 | ~100-350ns | 取决于 CXL 版本、重定时器、物理距离 |
| DDR5 访问 | ~30-60ns | CXL 控制器后端的 DRAM 访问 |
| **纯内存访问总延迟** | **~150-400ns** | CXL Type 3 的普遍延迟范围 |
| DAX PTE 映射 | ~20-50ns | 缺页时建立页表（首次访问） |
| VFS 路径解析 | ~100-500ns | dcache 命中时，文件路径到 inode 的查找 |
| famfs inode 查找 | ~100-300ns | inode table 在 CXL 内存中的读取 |
| **总端到端延迟** | **~400-1200ns** | 一次 mmap 后的随机读取延迟 |

**对比基线**：
| 访问方式 | 延迟 | 相对比 |
|:---------|:----:|:------:|
| 本地 DDR5 (HBM) | ~80-120ns | 1× |
| **CXL + famfs** | **~300-800ns** | **3-8×** |
| CXL + 块设备 + fs | ~500-2000ns | 5-20× (含页缓存) |
| NVMe (直通) | ~5-15μs | 50-150× |
| TCP 网络 | ~20-100μs | 200-1000× |

**关键洞察**：famfs 的延迟接近 CXL 硬件延迟的极限（额外开销仅 100-300ns），这是 DAX 直通的根本优势。

### 7.3 吞吐量特征

| 链路 | PCIe Gen | 单向带宽 (×16) | 全双工 | 聚合 (4×16) |
|:-----|:---------|:-------------:|:------:|:----------:|
| CXL 2.0 | Gen5 | 32 GB/s | 64 GB/s | 256 GB/s |
| CXL 3.0/3.1 | Gen6 | 64 GB/s | 128 GB/s | 512 GB/s |
| CXL 4.0 | Gen7 | 128 GB/s | 256 GB/s | **1.5 TB/s** |

famfs 的吞吐上限由 CXL 链路带宽决定（文件系统层额外开销 < 5%）。

**控制平面开销**：
- 元数据操作（create/delete/rename）：受单 host 持有的写入租约限制，限速在约 100K ops/s
- 数据平面（mmap 后的读写）：完全由 CXL 硬件带宽决定，无文件系统瓶颈

### 7.4 与现有方案的量化对比

**场景：140GB LLM weight 加载**

| 方案 | 延迟 | 成本/GB | 共享能力 | 大页支持 |
|:-----|:----:|:-------:|:--------:|:--------:|
| HBM(当前) | 80-120ns | $30-50/GB ❌ | ❌ | ✅ |
| CPU DDR5 | 80-100ns | $8-12/GB | ❌ | ✅ |
| **CXL + famfs** | **300-800ns** | **$3-8/GB** | **✅ 跨主机** | **✅ 2MB** |
| CXL + kmem NUMA | 300-800ns | $3-8/GB | ❌ 单主机 | ✅ |
| NVMe + VLM | 5-15μs | $0.5-2/GB | ✅ 网络 | ❌ |

**famfs 的 sweet spot**：在「中温数据」场景，延迟比 NVMe 低 10-50×，成本比 HBM 低 5-10×，同时提供跨主机共享的文件语义。

[来源: CXL 4.0 规范 (2025-11), HyMCache (arXiv 2026-06), LWN *Merging famfs?* (2026-07)]

### 8.2 未解决的设计争议

**1. kernel bypass 的程度**
- famfs 团队倾向 File system in userspace + DAX

- famfs 团队认为：volatile 内存 + 弱一致性 = 保持简单和高性能
- Linux 内核社区的部分成员希望有更强的语义保证

**3. 与现有 DAX 基础设施的代码复用**
- 维护者要求 famfs 减少重复的 DAX 基础设施代码
- famfs 团队正在做 DAX core 的抽象重构，以便 famfs 和其他未来的 DAX FS 共享
