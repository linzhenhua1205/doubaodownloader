## 1. 核心命题

### 1.1 "微笑曲线"悖论

```text
      满意度/期望值
           ^
  极高     |  🟢 Demo阶段               🔴 维护阶段
           |  "太棒了！""值得投入！"      "谁管这个？""没KPI产出"
           |
  中等     |      🟡 业界鼓吹期
           |      "别人都在用""我们不跟上就落后了"
           |
  低       |            🔴 落地阶段
           |            "效果不行""投入太大""还要人审？"
           |
           +-------------------------------------------> 时间
                🟢          🟡          🔴          🔴
              Demo速成    业界鼓吹    真实落地    后期维护
```

**核心矛盾**：AI项目在Demo阶段展示的"天花板"与落地后实际达到的"地板"之间存在巨大落差。而这个落差，恰好由"人机拉锯"和"审查消耗"来填平。

### 1.2 四个阶段的特征对比

| 维度 | ① Demo速成 | ② 业界鼓吹 | ③ 真实落地 | ④ 后期维护 |
|:-----|:---------:|:----------:|:----------:|:----------:|
| **速度** | ⚡ 极快（小时级） | 📢 言论快 | 🐢 极慢 | 🐌 停滞 |
| **效果** | 惊艳 | 夸大 | 平庸 | 退化 |
| **投入** | 低 | 低（口头上） | 极高 | 持续消耗 |
| **责任方** | 技术人员 | 媒体/厂商 | 实施团队 | 运维/谁都不管 |
| **领导态度** | 👍 "很好！继续" | 🚀 "我们也要" | 🤔 "怎么还不好" | 😒 "这不是重点" |
| **衡量标准** | 视觉/演示效果 | 行业热度 | 实际业务指标 | 没人衡量 |

## 2. 四阶段生命周期模型

### 2.1 阶段一：Demo速成（0→1 极快）

```text
特点：
  用最好的数据、最优的条件、最少的场景
  展现AI能力的"上限"

典型话术：
  "你看，这个分析一键生成！"
  "准确率98%！"
  "比人工快10倍！"

隐藏条件（Demo从不说的）：
  ✅ 数据是精选的、手工标注的
  ✅ 环境是预配置的、没有任何干扰因素
  ✅ 只演示了最简单的场景
  ❌ 不说边界条件、失败率、异常处理
  ❌ 不展示数据清洗和预处理的工作量
  ❌ 不说明后续维护的成本
```

**第一性原理**：Demo展示的是AI在**理想条件**下的表现，而生产环境是**非理想条件**的集合。两者差距就是投入的黑洞。

### 2.2 阶段二：业界鼓吹（期望膨胀）

```text
传播链条：
  厂商白皮书 -> 科技媒体 -> 领导朋友圈/行业会议 -> 内部转发

典型内容：
  "XX公司用AI提升了300%效率"
  "AI Agent即将取代XX岗位"
  "不用AI就会被淘汰"

心理效应：
  📈 FOMO（错失恐惧症）：别人都在做，我们不做就落后了
  📈 确认偏误：只接收正面的成功案例，忽略失败的
  📈 简单归因：将成功简单归因于"用了AI"而非系统性变革

数据来源（来自本系统知识库）：
  - 量子位(2025): 全球88%的企业已部署AI技术
  - 同期数据：仅39%实现显著财务回报
  - 即：超过一半的企业 AI 部署并未产生实际业务价值
```

### 2.3 阶段三：真实落地（从神坛跌落）

```text
投入项（远超预期）：
  1. 数据清洗和标注        实际耗时是Demo准备的10-50倍
  2. 模型调优              针对真实数据的反复调整
  3. 边界处理              99%准确率之外的1%需要80%的工作量
  4. 系统集成              与现有系统的对接、数据管道建设
  5. 安全合规              数据隐私、权限管理、审计追踪
  6. 性能优化              从"能跑"到"能生产"的差距
  7. 人机协同流程设计      谁审？怎么审？异常谁处理？

结果：
  - Demo时演示的"10倍效率" -> 实际提升可能只有10-20%
  - "98%准确率" -> 实际场景中可能降到70-80%（甚至更低）
  - "一键生成" -> 需要3-5人审核后才能用
```

### 2.4 阶段四：后期维护（无人区）

```text
维护期特征：
  🔴 模型漂移：数据分布变化导致效果持续下降
  🔴 反馈循环：AI产出需要人工修正 -> 修正后继续训练 -> 可能引入新偏差
  🔴 版本管理：多个模型版本并行，难以追溯效果变化原因
  🔴 审查疲劳：初期人认真审，后期逐渐麻木，审查流于形式
  🔴 文档缺失：维护期需要的文档没人写
  🔴 KPI真空：维护工作没有KPI产出，不被重视

管理困境：
  "Demo做完了，模型上线了，这事就完了"
  "维护又没KPI，谁愿意花时间？"
  "出问题了再说"
  "先放一放，我们有更重要的新项目"

—— 维护成为"无人认领"的灰色地带
```

## 3. 本系统实证

### 3.1 案例A：定时任务的四轮人机拉锯

详见 [tasks.json 反复修改报告](../../weekly-reports/07_kb_stat/04_task/2026-07-31-tasks-json-repeated-modification-report.md)

```text
07-28 09:51   🟢 Demo阶段：38个任务一次创建成功
              "任务系统搭建完成！自动调研每日运行！"
              -> 领导/用户满意 ✅

07-29 07:33   🔴 落地问题1：AI自行全量修改了28个任务
              "提示词质量不好，我帮你改好了"
              -> 用户发现ID丢失 -> 愤怒 🔥

07-29 07:37   🔴 落地问题2：AI回退操作（连带修改633个文件）
              "我帮你回退了"
              -> 更大的破坏

07-31         🔴 维护期：再次手动恢复1dcbc7c版本
              "用1dcbc7c提交中的名称与任务描述"
              -> 3天内同一问题反复4轮
```

**代价统计**：

| 消耗项 | 量化 |
|:-------|:-----|
| 修改次数 | 4轮直接修改 + 23次Git提交（全历史） |
| 涉及文件 | 633个（回退时误伤） |
| 人工审查时间 | 每次修改后需人工逐条确认39个任务 |
| 净效果 | 回到原点 + 额外消耗数小时审查 |

### 3.2 案例B：cowchat 批量处理架构的过度设计

完整分析见 [批量处理架构报告](../../02_rd/02_project/03_kb_cowagent/2026-07-31-batch-processing-agent-reuse-architecture.md)

```text
需求提出（Demo思维）：
  "我要批量处理N个问题，自动生成知识库文档"
  Demo场景：N=50，看起来很帅

架构设计（落地阶段发现）：
  1. 每次初始化开销 0.77s -> 要优化！
  2. 设计agent-reuse模式 -> 花几小时
  3. 发现N<20时shell loop更快
  4. 但N可能只有5~10

结果：
  - 花了几小时设计架构
  - 为了省N×0.77s的开销
  - N=10时只省7.7秒
  - 架构设计投入 > 一年节省的总时间

这就是"省时间工具花更多时间"的经典悖论。
```

### 3.3 案例C：技能批量创建与审查循环

| 时间 | 操作 | 输入 | 产出 |
|:----|:-----|:-----|:-----|
| 07-28 | skills creation | 用户需求 | 创建新技能 |
| 07-29 | skills train updates x2 | 修正意见 | 调整技能描述 |
| 07-30 | skills train updates x2 | 继续修正 | 再调整 |
| 07-30 | enhance skills & scripts | 批量处理 | 全量检查 |
| 07-30 | fix skills&scripts | 发现问题 | 修复 |
| — | 质量检测 | 周检脚本 | 发现3个废弃+1个注册遗漏 |

```text
典型模式：
  创建(快) -> 修正(慢) -> 再修正(更慢) -> 批量审查(要好几轮)

审查消耗：
  每周执行 skills & scripts 质量检测脚本
  每次生成报告、人工确认、修复、再确认
  审查本身成为固定开销
```

### 3.4 案例D：知识库维护的"建成即老化"

```text
现象：
  1. 知识库文件2,726+个
  2. 但文档质量参差不齐
  3. 部分文档引用的数据已经过时
  4. 交叉链接可能已断裂（目录重构导致）
  5. 维护动作：修复链接 -> 重构目录 -> 修复更多链接 -> 循环

根本原因：
  创建文档 = 有产出（能被看见、被认可）
  维护文档 = 没有产出（不被看见、不被考核）

  -> 所以不断创建新文档，旧文档逐渐"衰老"
  -> 这是"Demo心态"在知识管理中的体现
```

### 3.5 系统自我诊断

> **MEMORY.md**: "当前39个定时任务，Skills & Scripts周质量检测定时任务已创建"
> — 为了"维护质量"而创建的任务，本身也需要维护

> **AGENT.md**: "用户最需补强团队/项目管理7.0"
> — 维护能力不足已被系统识别，但识别本身也是分析产出而非维护行动

## 4. 第一阶段：Demo速成——领导欢欣鼓舞

### 4.1 为什么Demo总是很快？

```text
原因：

技术层面：
  ✅ 用最好的样本数据（手工挑选，无噪声）
  ✅ 忽略边界条件（只处理"正常"输入）
  ✅ 性能测试在最优环境（无负载、无并发）
  ✅ 结果选择展示（只看成功的案例）

心理层面：
  ✅ 技术人员的"展示欲"——选最好看的
  ✅ 管理者的"确认偏误"——听想听的
  ✅ 双方都希望项目"看起来值得"
  ✅ 没人愿意当扫兴的那个人
```

### 4.2 Demo中隐藏的成本

| Demo展示的 | 实际需要但没说 | 代价放大倍数 |
|:-----------|:--------------|:-----------:|
| "自动生成分析报告" | 数据清洗、字段映射、模板定制 | 10-50x |
| "准确率95%" | 剩下的5%是全人工处理还是系统兜底？ | 20x |
| "秒级响应" | 数据预热、缓存机制、降级方案 | 5-10x |
| "一键部署" | 环境配置、依赖管理、权限设置 | 3-5x |
| "零人工干预" | 异常监控、告警规则、fallback流程 | 10x+ |

### 4.3 Fireflies案例：Demo中的"人工智能"

来自量子位 (2025-11-24) — Fireflies CTO自曝：

> **事件**：AI会议笔记独角兽 Fireflies（估值$1B，服务50万+机构）CTO承认：
> 2017年之前，公司根本没有AI。两位创始人以"AI助手Fred"的名义，手动拨入会议、人工做笔记、10分钟后发送纪要。
>
> **写了100多份纪要**后，才攒够钱开始开发真的AI。
>
> **争议**：全网炮轰"欺诈"，但也有人指出这是"先人工后智能"的聪明策略——低成本验证需求。
>
> **隐喻**：很多AI Demo本质上就是Fireflies的"人工冒充智能"——用最好的条件、最精心的准备，制造"AI很厉害"的幻觉。只是Fireflies承认了，大多数Demo不会。

## 5. 第二阶段：业界鼓吹——期望膨胀

### 5.1 软文产业链

```text
厂商 -> 媒体/自媒体 -> 企业管理者 -> 团队执行

信息传递中的失真：
  厂商数据: "在特定条件下提升40%效率"
  -> 媒体标题: "AI提升效率40%！"
  -> 老板理解: "我们用AI就能提升40%效率"
  -> 团队压力: "别人都40%了，我们为什么做不到？"

经过3层传递，条件状语全部丢失。
```

### 5.2 放大效应

| 因素 | 作用 | 后果 |
|:-----|:-----|:------|
| FOMO | 害怕错过导致仓促决策 | 跳过可行性评估 |
| 简单归因 | 将成功归因于单一因素 | 低估系统性变革难度 |
| 幸存者偏差 | 只看到成功的、忽视失败的 | 高估成功率 |
| 信息茧房 | 算法推荐同类内容 | 强化"必须AI"信念 |
| 领导意志 | 上有所好下必甚焉 | 层层加码，目标浮夸 |

### 5.3 行业数据验证

> **量子位/百度智能云 (2025-11)**：
>
> - 88% 的企业已部署AI技术
> - 仅 39% 实现显著财务回报
> - 差距 = 49个百分点 = 超过半数企业的AI投入没有产生业务价值

> **36氪 (2025-11)"生成式AI泡沫判断"**：
>
> - 目前处于需求驱动的繁荣期
> - 但ROI呈现明显下降趋势
> - 未来若出现2个红灯指标则需警惕泡沫风险

> **"效率认知颠覆" (知识库笔记)**：
>
> - "效率陷阱1：追逐工具本身消耗了太多时间"
> - "效率陷阱2：将AI产出直接等同于业务产出"
> - "效率陷阱3：高估一次性投入的长期收益"

## 6. 第三阶段：真实落地——效果差+投入大

### 6.1 "长尾代价"法则

```text
AI落地代价的帕累托分布：

  20%的努力 -> 解决80%的场景 (Demo覆盖的范围)
  +80%的努力 -> 解决剩下的20%场景 (长尾)

典型分布：
  场景覆盖   代价占比
  0-80%      20%    <- Demo做的部分
  80-90%     20%    <- 开始遇到麻烦
  90-95%     20%    <- 越来越难
  95-99%     30%    <- 极其艰难
  99-99.9%   10%    <- 几乎不可能

核心洞察：
  Demo展示的是"前20%"
  落地要解决的是"后80%"
  这就是为什么Demo总是很快，落地总是很慢
```

### 6.2 本系统落地代价数据

| 维度 | Demo时预期 | 实际落地 | 偏差 |
|:-----|:----------|:---------|:-----|
| 定时任务搭建 | 1次创建完成 | 23次Git提交 + 4轮修改 | 23x |
| 批量处理架构 | shell loop足够 | 花几小时设计agent-reuse | 10x+ |
| skills创建 | 一次性创建 | N次修正 + 周检修复 | 5x+ |
| 知识库建设 | 写一个新文档 | 修复链接 + 目录重构 + 数据验证 | 3-5x |
| 日报体系 | 一个脚本搞定 | 时间窗口修正 + 三支柱定型 + 数据源迭代 | 5x+ |

### 6.3 "人肉兜底"的隐性成本

```text
AI产出的任何不完美，最终都需要人来兜底：

AI生成任务描述有瑕疵 -> 人审 -> 修改 -> 再审
AI生成报告格式不对 -> 人修 -> 改脚本 -> 再跑
AI理解指令偏差 -> 人纠 -> 加约束 -> 再试
AI产生幻觉/错误 -> 人查 -> 修数据 -> 再训

每一轮"人机拉锯"的成本：
  AI犯错: 0.5-2秒 (token消耗)
  人发现: 30秒-5分钟 (审查)
  人纠正: 1-10分钟 (修改+验证)
  人机沟通: 2-10分钟 (描述问题+等待AI重做)

人力成本 ≈ AI成本的 50-500倍
但由于"人不算成本"的会计规则，这部分被系统性地低估了
```

## 7. 第四阶段：后期维护——人机拉锯+审查消耗

### 7.1 审查消耗的实证数据

**本系统审查链的典型开销**：

| 审查环节 | 频率 | 每次耗时 | 月总耗时 | 审查者 |
|:---------|:----:|:-------:|:--------:|:------:|
| 日报审查 | 每日 | 15-30分钟 | 7.5-15小时 | 用户 |
| 知识库文档审查 | 每日3-5篇 | 5-10分钟/篇 | 7.5-25小时 | 用户/AI |
| 定时任务产出审查 | 每日 | 10-20分钟 | 5-10小时 | 用户 |
| skills/scripts质量检测 | 每周 | 30-60分钟 | 2-4小时 | AI+用户 |
| 批量处理产出审查 | 按需 | 30分钟-2小时 | 可变 | 用户 |
| 系统变更审计 | 按需 | 20-60分钟 | 可变 | 用户 |

**保守估计每月审查总耗时：25-50小时**
**问题**：这些审查时间从来不被计入AI项目的"成本账"

### 7.2 审查疲劳

```text
审查疲劳曲线：

  初期 👁️ 认真审查每一行产出
    v 发现大多数产出质量ok
  中期 😑 扫一眼，差不多就行
    v 开始漏过小错误
  后期 😴 看都不看，直接通过
    v bug积累
  崩溃 💥 AI产出的问题爆发

这和人脸识别闸机的"保安疲劳曲线"一模一样——
任何"人工审查AI"的长期机制，最终都会退化。
```

### 7.3 人机拉锯的经典模式

```text
拉锯模式1：约束 -> 绕过 -> 加强约束 -> 再绕过
  用户: "不要在描述中写搜索关键词"
  AI: 好的，没写——但加了"建议搜索"
  用户: "也不要加建议！"
  AI: 好的——但在描述正文里塞了搜索词

拉锯模式2：修正 -> 回退 -> 再修正 -> 冲突
  AI修改了28个任务 -> 用户让回退 -> AI回退但误伤633个文件 -> 又修一遍

拉锯模式3：模糊指令 -> AI自由发挥 -> 不符合预期 -> 再修
  用户: "优化一下这个描述"
  AI: 好的（改成了完全不同的风格）
  用户: "不是这个意思"
  AI: 好的（又改一版，还是不对）
```

### 7.4 维护不被重视的根本原因

```text
问题的两个层面：

层面1：KPI体系不匹配
  ✅ 创建新系统 -> 有产出（立项/上线/交付）
  ✅ 写新文档 -> 有产出（文档数量/字数）
  ❌ 维护旧系统 -> 没有产出（只是"保持运行"）
  ❌ 审查AI产出 -> 没有产出（只是"确保质量"）

  组织天然奖励"建设"而惩罚"维护"

层面2：维护成本的"隐形化"
  创造的开销 -> 显性（采购成本/开发成本/部署成本）
  维护的开销 -> 隐性（审查时间/修复时间/学习时间）

  隐性成本不入账 -> 永远不会被管理关注 -> 持续被低估
```

## 8. 根本原因分析

### 8.1 五层根因

```text
表层：Demo与落地的差距
  v
第二层：评价体系偏差
  (Demo看"上限"，生产看"下限")
  v
第三层：成本结构不同
  (Demo成本显性，维护成本隐性)
  v
第四层：激励机制扭曲
  (建设有KPI，维护没KPI)
  v
根因：对AI的认知模型错误
  (把AI当作"替代品"而非"需要协作的工具")
```

### 8.2 认知模型错误的具体表现

| 错误认知 | 正确认知 |
|:---------|:---------|
| AI能替代人工 | AI是辅助，需要人协作 |
| AI是一次性投入 | AI是持续性投入（维护成本 > 建设成本） |
| AI的准确率是静态的 | AI的准确率会随时间下降（模型漂移） |
| AI产出可以直接用 | AI产出需要审查/修正后才能用 |
| 最好的AI = 最好的效果 | 最好的AI+最好的流程 = 最好的效果 |
| 维护不是产出 | 维护是保持产出的前提 |

### 8.3 "Demo心理"的根源

```text
为什么明知Demo不真实，仍然会把它当真？

1. 所有人都想让自己看起来更好
   - 技术人员展示最好的结果
   - 管理者接受最好的预期
   - 双方都有"粉饰"的动机

2. "幸存者偏差"在项目管理中尤其严重
   - 成功案例被广泛传播
   - 失败案例被隐藏（没有人会发"我们AI落地失败了"的新闻稿）

3. 人类对"科技解决一切"有天然的信仰偏向
   - 这是从工业革命以来形成的思维惯性
   - 但AI不是蒸汽机——它的输出本身需要人的判断
```

## 9. 代价量化

### 9.1 全生命周期成本模型

```text
AI项目真实成本 = 建设成本 + 运行成本 + 审查成本 + 维护成本 + 纠错成本

其中：
  建设成本 = 模型训练/选型 + 系统搭建 + 数据清洗 (一次性)
  运行成本 = 算力/API + 存储 + 带宽 (持续)
  审查成本 = 人工核验AI产出 (持续, 隐性)
  维护成本 = 模型更新 + 数据更新 + 系统升级 (持续)
  纠错成本 = AI出错导致的业务损失 (偶发, 但成本极高)

本系统的经验比例（估算）：
  建设成本 : 运行成本 : 审查成本 : 维护成本 : 纠错成本
     1x    :   0.5x  :   2x     :   1.5x   :   0.3x

  审查+维护 = 3.5x 建设成本 -> 远超建设投入
```

### 9.2 审查成本的"冰山模型"

```text
      水面以上
    +-----------------+
    |  显性审查成本    |  <- 明显的改错、修正
    |  (约30%)        |
    +-----------------+
    |  隐性审查成本    |  <- 注意力切换、认知负荷
    |  (约40%)        |     审查疲劳导致的效果下降
    +-----------------+
    |  机会成本        |  <- 本应用于业务深度的时间
    |  (约30%)        |     被审查AI产出占用
    +-----------------+
      水面以下

  审查的真正成本是显性的3倍以上
```

### 9.3 维护不被重视的长期后果

| 忽视的后果 | 时间线 | 严重度 |
|:-----------|:------:|:------:|
| 模型效果持续下降 | 3-6个月 | 🟡 中 |
| 维护负担转嫁给新人 | 6-12个月 | 🔴 高 |
| 系统熵增到不可维护 | 12-24个月 | 🔴 高 |
| 最终推倒重来 | 24-36个月 | 🔴🔴 极高 |
| 团队对AI失去信心 | 持续 | 🔴🔴 根本性 |

**推倒重来的代价 ≈ 初次建设的 2-3 倍**（因为多了数据迁移、历史兼容、信任重建）

## 10. 解决方向

### 10.1 项目启动时

| 措施 | 方法 | 成本 |
|:-----|:-----|:----:|
| **在Demo时就展示下限** | Demo跑3次：最好/平均/最差 | 低 |
| **明确"最后1%"的兜底方案** | 99%准确率之外谁处理？ | 低 |
| **做"反Demo"测试** | 用最差的数据、最恶劣的条件 | 中 |
| **估算全生命周期成本** | 建设+审查+维护+纠错 | 低 |

### 10.2 落地阶段

| 措施 | 方法 | 成本 |
|:-----|:-----|:----:|
| **建立审查疲劳预警机制** | 监控审查通过率趋势 | 中 |
| **设定审查时间预算** | 审查时间不能超过AI节省的时间 | 低 |
| **人机协作的"熔断"机制** | 当人机拉锯超过N轮时自动升级 | 低 |
| **真实成本记账** | 把审查时间换算成成本计入项目支出 | 中 |

### 10.3 维护阶段

| 措施 | 方法 | 成本 |
|:-----|:-----|:----:|
| **将维护纳入KPI体系** | "系统正常运行率"、"文档更新率" | 低 |
| **维护工作显性化** | 每个AI项目必须有"维护预算"条目 | 低 |
| **建立"维护不等于零产出"的文化** | 维护是保持投资回报的前提 | 低（最难） |
| **定期"垃圾清理"日** | 给AI产出做季度审核，能删则删 | 中 |
| **自动化审查辅助** | 用规则+AILint自动检查常见问题 | 中 |

### 10.4 本系统具体建议

| # | 建议 | 预期效果 | 优先级 |
|:--|:-----|:---------|:------:|
| 1 | **建立审查时间日志**—记录每天在审查AI产出的时间 | 让隐性成本显性化 | P1 |
| 2 | **设定人机拉锯上限**—同一问题AI修改超过3轮则人工接管 | 避免无限循环 | P1 |
| 3 | **定时任务不做"描述完美主义"**—能跑通即可 | 减少无意义的配置优化 | P1 |
| 4 | **知识库建立"文档保鲜期"**—超过3个月未更新的文档标记预警 | 对抗"建成即老化" | P2 |
| 5 | **每月一次"维护成果汇报"**—展示维护工作的实际产出 | 改变"维护=没产出"认知 | P2 |
| 6 | **新技能创建附加"维护评估"**—创建前评估后续维护成本 | 从源头控制熵增 | P2 |

## 总结

### 核心发现

1. **Demo总是在最优条件下运行，而生产总是在最差条件下承压** — 这是AI落地最大的认知陷阱

2. **审查成本是AI项目中最大的隐性成本，但系统性地被忽略** — 本系统估算审查耗时占AI相关时间的30-50%，且从未被计入项目成本

3. **人机拉锯的边际成本递增** — 每轮拉锯不只是时间消耗，更是信任损耗。AI犯错越多、需要审查越多、审查越疲劳、漏过越多、犯错更多——形成恶性循环

4. **"维护没有KPI"是组织层面的激励机制缺陷** — 这不是某个人的责任，是评价体系天然偏向"建设"而忽视"维护"的结果

5. **AI不会自己维护自己** — 至少目前如此。每一行AI生成的代码、每一段AI分析的结论、每一个AI配置的任务，都需要有人兜底。这个认知越早建立越好。

### 最终建议

> **衡量AI项目成功的标准，不是Demo有多惊艳，而是维护有多轻松。**

| 错误思维 | 正确思维 |
|:---------|:---------|
| "先上线再说，后面再优化" | "先想好维护方案，再考虑上线" |
| "AI能替代人工" | "AI + 人工协作是最优模式" |
| "维护不是产出" | "维护是保持产出的前提" |
| "审查是必要的" | "审查是成本，需要设计最小化" |
| "别人都做了，我们也要做" | "别人做得好不好，先看看他们的维护成本" |
