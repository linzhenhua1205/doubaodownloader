## 1. 核心洞察

**反复修改的地方 = 系统逻辑/治理缺陷的病灶**，不是"维护投入大"的功劳簿。

| 旧视角（错误） | 新视角（正确） |
|:-----|:-----|
| 某文件被改 80 次 = 团队很勤奋 | 某文件被改 80 次 = **此处存在无约束/无检查的系统性缺陷** |
| churn 高 = 打磨投入多 | churn 高 = **治理缺失的信号**，需诊断根因 |
| 报告 = 给出符合认知的数据 | 报告 = **发现问题 + 给出解决思路** |

**推理链**：正常工作的系统，约束一旦固化（Skill + 检查脚本），同类问题不会重复出现。反复出现 = 约束缺失或检查缺失。因此 **churn 是治理雷达**：扫描高频修改文件 → 定位病灶 → 诊断根因 → 建立约束 → 验证收敛。

## 2. 病灶图谱：五大反复修改点

### 病灶 1：文件命名不规范（反复改名）

| 维度 | 内容 |
|:-----|:-----|
| **症状** | kb-rename 8/3 一次改名 **1019 文件**（YYYY-MM-DD-英文描述.md 规范化）；7/24 统一格式、7/29 redesign 亦涉及命名调整 |
| **根因** | 早期无命名规范约束 + 无自动检查 → 文件随意命名，积累到量变后被迫大规模重构 |
| **现状** | ✅ **已治理**：8/4-8/5 新增文件抽样 100% 符合 `YYYY-MM-DD-英文描述.md` 规范（deep-analysis 系列/sources 系列/01_survey 日期式） |
| **解法** | 命名规范写入 RULE.md + 新增文件生成时模板约束（knowledge-wiki 技能）；kb-rename 是补救，规范+模板是根治 |

| 维度 | 内容 |

## 3. 实证：治理前后 churn 对比（"这几天好多了"验证）

高频病灶文件的**修改次数按时间分布**（前半月=7/1-15，后半月=7/16-31，8月=8/1-5）：

| 文件 | 前半月 | 后半月 | 8月 | 趋势 |
|:-----|:------:|:------:|:---:|:-----|
| 02_rd/log.md | 58 | 22 | **1** | ✅ 收敛 |
| 07_industry-research/log.md | 18 | 42 | **1** | ✅ 爆发后收敛 |
| 07_industry-research/index.md | 20 | 38 | **0** | ✅ 收敛 |
| knowledge/index.md | 29 | 39 | **3** | ✅ 收敛 |
| spec/index.md | 0 | 22 | **3** | ✅ 收敛 |
| skills_config.json | 9 | 17 | **4** | ✅ 收敛 |
| MEMORY.md | 14 | 20 | 6 | 正常迭代 |
| **knowledge/log.md（全局）** | 15 | 34 | **18** | ⚠️ **残留热点** |

**结论**：7 个病灶中 6 个 8 月 churn 降到 ≤4（多数 0-1）——**"治理后好多了"有硬数据支撑**。但全局 log.md 8 月仍 18 次，是唯一未收敛的残留热点。

## 4. 残留热点诊断：全局 log.md

**为什么 8 月还改 18 次？**

| 假设 | 验证 |
|:-----|:-----|
| 8/3 双轨制刚建立，格式仍在磨合 | 部分成立（双轨制 = 8/3 落地，log 承载全部模块变更记录） |
| log 是"人工账本"，每笔变更都要手写追加 | **主要根因**：全局 log 目前靠人工/半自动追加，无 git 自动生成机制 |
| 内容本身反复出错 | 次要：8 月 log 记录质量总体稳定，但追加动作本身频繁 |

**本质**：全局 log.md 是**唯一靠"人肉记账"的高频文件**——其他病灶都已脚本化（index 自动生成、命名模板化、链接自动验证），唯独 log 仍是每次变更后的手工步骤。

**解法建议**：

1. **半自动生成**：从 git log 提取当日变更摘要 → 生成 log 草稿 → 人工确认（可参考 scripts/knowledge-special-reports-updater.py 模式）
2. **或降级为纯机器账本**：log.md 由脚本生成（类似 index.md 的 kb-global-index.py），人工只维护 README 条目
3. 过渡期：接受 log 高频但**内容稳定**（churn 高 ≠ 质量差，需区分"追加记账"与"返工修改"——统计 M 次数时应排除纯追加型变更）

## 5. 治理生命周期模型

所有病灶呈现同一四阶段生命周期：

**无约束发生 → churn 爆发 → 治理介入 → 收敛**

（随意命名/乱放）→（反复修）→（规范+脚本+技能）→（churn 降到 <5）

| 阶段 | 特征 | 检测信号 | 干预手段 |
|:-----|:-----|:---------|:---------|
| ① 无约束发生 | 问题零散出现 | 无 | — |
| ② churn 爆发 | 同一类问题反复出现 | **churn 骤升** | 诊断根因 |
| ③ 治理介入 | 规范+脚本+技能固化 | 治理提交（refactor/feat） | Skill 约束 + check 脚本 |
| ④ 收敛 | 问题不再复发 | **churn 骤降** | 验证 + 防复发（定时检查） |

**关键**：churn 的**时间分布**比总量更有诊断价值——总量高但已收敛 = 治理成功；总量中但持续高位 = 残留病灶（如全局 log）。

## 7. 方法论沉淀

1. **churn 是治理雷达**：扫描高频修改文件 → 定位病灶 → 诊断根因 → 建立约束 → 验证收敛
2. **报告的价值 = 发现问题 + 解决思路**，不是验证感知或给出"看起来对"的数据
3. **治理的生命周期可检测**：churn 骤升=爆发、治理提交=介入、churn 骤降=收敛——用时间分布诊断，不用总量
4. **好治理的标志**：同类问题不再复发（churn 降到 <5 且持续）；残留热点 = 下一步治理对象
5. **区分 churn 类型**：纯追加记账（log 类）与返工修改（修 bug 类）是不同性质，统计时应分离
