## §1 问题的提出：宏观化为什么值得单独成专题

### 1.1 现象：无处不在的大分类

在知识库、项目管理、汇报材料中，"研发""消化""工具建设""业务投入"这类大分类随处可见。它们把大量异构内容整合进少数几个桶里，形成一眼可读的宏观图景：

| 宏观分类（易读） | 微观事实（被掩盖） |
|:-----------------|:-------------------|
| 研发 | 产品定义 / 硬件设计 / 固件开发 / 测试验证 / 竞品分析... |
| 消化 | 文章归档 / 深度分析 / 专题报告 / 素材清洗 / 质量修复... |
| 工具建设 | scripts / skills / spec / scheduler / templates... |
| 知识库 | knowledge / import / discover / memory / conversation-log... |

宏观化最大的诱惑是**理解成本低**：一个饼图、一张表、一个百分比，决策者 30 秒就能"看懂全局"。

### 1.2 用户的洞察

> "把问题宏观化虽然容易让人理解和接纳（比如研发、消化等），但这种方式看似把关联的相关内容整合在一起，其实对细分或深度挖掘非常不友好。所以我们需要识别这个问题并进行解决，我觉得这值得形成一个专题来对待。"（用户 2026-08-06）

用户指出的核心矛盾：**宏观化的收益在"展示层"，代价却在"挖掘层"**。展示层追求的是"让人看懂"，挖掘层追求的是"让人发现真相"——两者对粒度的要求是相反的：

| 层 | 目标 | 最优粒度 | 典型场景 |
|:---|:-----|:---------|:---------|
| 展示层 | 让决策者快速理解 | 粗（3-5 个桶） | 周报/汇报/PPT |
| 挖掘层 | 发现结构、热点、异常 | 细（可下钻到文件） | 投入分析/热点诊断/短板识别 |

一个粒度不可能同时满足两层——**这就是宏观化陷阱的结构性根源**。

### 1.3 本专题的三个层次

本专题不只是一篇方法论，它同时回答三个层次的问题：

1. **认知层**：宏观化为什么会发生？为什么它如此诱人？（§2）
2. **代价层**：宏观化具体损失了什么？有没有客观的识别方法？（§3-§5）
3. **解法层**：如何设计粒度才能既"看得懂"又"挖得深"？（§6-§8）

## §2 第一性原理：聚合是有损压缩

### 2.1 认知的便利性税

宏观化的本质是**用信息保真度换取认知便利**——每一次聚合都是一次有损压缩，压缩率越高，重构原始分布的能力越差。

人类认知天然偏好压缩：认知负荷理论（Sweller, 1988）指出，工作记忆容量约 7±2 个组块，人必须把信息分块（chunking）才能处理复杂系统 [来源: 认知负荷理论, Sweller 1988]。**分类是认知的捷径，不是信息的真相**——它服务于"能处理"，不服务于"保真"。

### 2.2 信息论视角：聚合损失的是互信息

用香农信息论看，聚合操作可以建模为：

```text
Raw distribution X (N items) --f--> Aggregated Y (M buckets, M << N)

I(X; Y) = H(X) - H(X|Y)   <- mutual info preserved after aggregation
```

- 聚合后的熵 H(Y) 大幅下降（因为桶数变少）；
- 但真正关键的是**互信息 I(X; Y)**：从聚合标签 Y 能还原出多少 X 的信息；
- 每次聚合丢失的信息 = H(X|Y)——**给定桶标签后仍然不确定的细分信息**。

一个直观例子：如果把"互联/供电散热/SI/RAS"聚合成"硬件"一个桶，那么知道"某个文件属于硬件"后，你仍然不知道它是讲互联带宽还是液冷功耗——**H(X|Y) 巨大**。宏观分类越粗，H(X|Y) 越大，挖掘时的定位成本越高。

### 2.3 辛普森悖论风险

聚合还会引入统计陷阱：**辛普森悖论**——分组趋势与聚合趋势相反 [来源: Simpson, 1951]。例如：

| 视角 | 结论 |
|:-----|:-----|
| 分组（细分真相） | 供电散热 7 月新增 > 互联新增 |
| 聚合（宏观结论） | 硬件整体 7 月新增 < 8 月 |

两个结论都"正确"，但只有细分视角能指导"该往哪补投入"。宏观聚合天然隐藏分组间的此消彼长，这正是"热点识别"（用户核心需求之一）的敌人。

## §3 宏观化的四类代价（MECE）

### 3.1 分布抹平：均值掩盖 20/80

宏观聚合把分布压成均值，掩盖了**极端值结构**——而极端值恰恰是管理要抓的点（瓶颈、热点、异常）。

| 代价 | 表现 | 例子 |
|:-----|:-----|:-----|
| 分布抹平 | 聚合值掩盖内部 20/80 | "研发投入 100h"掩盖"固件 80h + 产品 15h + 竞品 5h" |
| 离群隐藏 | 异常被平均掉 | 单日 50 提交的治理总攻被月均淹没 |
| 方差丢失 | 只看均值不看波动 | 8 月 log 21 次修改的持续热点被"月度总量"掩盖 |

### 3.2 可钻取性丧失：分类树切断细分路径

一旦内容被归入宏观分类，**细分路径就从组织上消失**——不是内容不存在，而是"找不到入口"。

本工程实证（§4.2）：硬件内容分散全库（互联 1258 文件/SI 468/RAS 786/供电散热 946），但 `02_rd/03_hardware` 目录下只有 4 个文件。用户按"关注点"（P1/P2）浏览时没有聚合入口——**内容在、结构不在**。这就是宏观分类（专题式）与用户认知模型（关注点式）不匹配的典型表现。

### 3.3 决策误导：宏观数据支撑不了微观决策

宏观数据适合"判断方向"，不适合"决定动作"。但实践中宏观结论常被直接用于微观决策：

- 宏观："7 月产出主体是业务知识（86%）" → 误导性结论：应继续铺业务内容；
- 微观真相：素材层占 79.4%，knowledge 仅 9% → 真实问题是**转化率**，不是产出结构。

**决策层级必须匹配数据粒度**——用宏观数据做微观决策，等于用月均气温决定今天穿什么。

### 3.4 思维固化：分类即认知框架

分类不仅是存储方式，还是**认知框架**——它决定了"你能想到什么问题"。宏观分类会系统性屏蔽细分问题：

- 分类是"研发/消化/工具" → 你不会问"固件三线里哪条线返工最多"；
- 分类是"硬件/软件/AI" → 你不会问"互联与供电散热的耦合点在哪"。

**分类即提问范围的边界**。宏观化把边界画得太大，等于放弃了边界内所有细分的提问权。

## §4 本工程实证：宏观化陷阱的三组案例

> 以下数据均来自本工程实测（git 全量统计，详见 [`2026-08-06-kb-quality-investment-churn-insight-report.md`](../../weekly-reports/07_kb_stat/05_kbsys/2026-08-06-kb-quality-investment-churn-insight-report.md)）。

### 4.1 实证一：86:14 的宏观结论被五层流水线推翻

**宏观视角**：7 月 knowledge 新增 A=2193 vs 工具侧新增 344 → "产出主体是业务知识，约 86%:14%"。这个结论"看起来对"，也符合直觉。

**细分视角**：把工程拆成五层流水线（L0 素材 → L1 知识 → L2 工具 → L3 记忆 → L4 会话）后重统计：

| 层 | 7 月新增 A | 占比 |
|:---|:----------:|:----:|
| L0 素材（import+discover） | 19,532 | **79.4%** |
| L1 知识（knowledge） | 2,193 | 8.9% |
| L2 工具（scripts/skills/spec） | ~400 | 1.6% |
| 其他（memory/会话等） | ~2,400 | ~10% |
| 合计 | 24,598 | 100% |

[来源: v3.0 报告 §3.2，全工程 git 实测]

**结论翻转**：素材层才是投入主体（79.4%），knowledge 只有 8.9%——与宏观结论"业务是主体"完全相反。宏观化（只看 knowledge vs 工具侧）把最大的投入块（素材导入）排除在视野之外。**这是"宏观化掩盖真实结构"的最直接证据。**

### 4.2 实证二：硬件内容在、结构不在

- 按主题 grep：互联 1258 / 供电散热 946 / RAS 786 / SI 468 文件（全库分布）；
- 按目录看：`02_rd/03_hardware` 仅 4 文件。

同一批内容，**主题粒度**看到的是"内容充足"，**目录粒度**看到的是"结构缺失"。宏观的"硬件"分类（目录）与用户实际的 P1/P2 关注点（互联/供电散热/SI/RAS）不在同一维度——**分类维度与关注维度错位**是宏观化的隐蔽变体。

### 4.3 实证三：55%/30% 被反复引用

`"工具建设 55% vs 业务深度 30%"` 这个宏观定性数据，从 7 月底被反复引用 4 次以上，直到 8/5 求证报告才确认其**源头是 7/31 人工定性估算，无量化实证支撑**（[来源: `2026-08-05-ai-productivity-paradox-data-verification.md`](../04_ai/2026-08-05-ai-productivity-paradox-data-verification.md)）。

教训：**宏观定性数据（"约一半""三分之一"）一旦被写成数字，就有了虚假的精确性**。这正是用户指出的"某一天的一个投入情况被当做一个全局数据来看待"的实例。

## §5 识别宏观化陷阱的诊断清单

任何分类/聚合出现前，先过五问（任一为"是"即触发宏观化预警）：

| # | 诊断问题 | 宏观化信号 |
|:-:|:---------|:-----------|
| 1 | 聚合后能否下钻到原始数据？ | 不能，桶就是终点 |
| 2 | 分类粒度能回答"哪里是热点/短板"吗？ | 只能回答"总量多少" |
| 3 | 桶内是否存在显著 20/80 分布？ | 没统计过，凭感觉分桶 |
| 4 | 分类维度与用户的关注维度一致吗？ | 关注"互联/散热"，分类只有"硬件" |
| 5 | 结论是否被用于下一层（更细）决策？ | 是，但数据粒度不匹配 |

**核心判据**：聚合后若无法回答任何一个**下一层问题**（"具体是哪个？""差距多大？""趋势怎样？"），这个聚合就是展示用的，不应进入分析链。

## §6 解决方案：粒度设计三原则 + 三层粒度

### 6.1 保真原则：聚合是视图不是存储

**原始数据永远保留，聚合只是临时视图**。任何宏观统计都必须能回溯到文件级/提交级原始记录——这是对抗"抽样当全量"的根本手段。

| 存储层（保真） | 视图层（易读） |
|:---------------|:---------------|
| 文件级 git 记录 | 周报聚合 |
| 提交级 A/M/R/D | 月度画像 |
| 会话级原始日志 | 主题聚类 |

本工程已验证的实践：A/M/R/D 四状态×分目录×分月的**原始统计**保留在报告里，宏观结论（如 79.4%）只是对原始统计的聚合视图 [来源: v3.0 报告 §2]。

### 6.2 下钻原则：每个聚合必须有钻取路径

宏观数字旁边必须标注**下钻路径**：点击/引用可到达下一层明细。

| 聚合结论 | 下钻路径 |
|:---------|:---------|
| "7 月素材层占 79.4%" | → 分目录统计 → 素材区（导入/发现流水线）文件清单 |
| "8 月 02_rd M=2858" | → 分文件 churn Top10 → 具体提交记录 |
| "热点=知识库治理" | → 对话主题聚类 → 具体会话片段 |

本工程 8/5 建的 `link-validator`/`link-fixer` 已验证"可追溯"的价值——链接修复从 67503 → 0 问题，靠的就是每条修复可下钻到具体文件 [来源: knowledge/log.md 2026-08-05]。

### 6.3 多维原则：不依赖单一目录树

单一目录树只有一个分类维度，必然顾此失彼。引入**多维访问**：

- **主题维度**（硬件/互联/散热…）——内容归属；
- **关注点维度**（P1/P2 用户关注点）——用户视角；
- **时间维度**（日/周/月/季）——演进视角；
- **质量维度**（深度/素材/待确认）——治理视角。

已落地的实践：索引 V3 用"README 人工条目 + INDEX 自动路径 + log 全局账本"三文件职责分离，本身就是多维访问的雏形 [来源: MEMORY.md 索引V3]。

### 6.4 三层粒度：宏观/中观/微观分离

**每层只回答该层的问题，不跨层使用**：

| 层 | 粒度 | 回答的问题 | 使用场景 |
|:---|:-----|:-----------|:---------|
| 宏观 | 3-5 个桶 | "方向对不对？" | 周报/汇报/PPT |
| 中观 | 分目录×分月 | "哪块在涨/在收敛？" | 月度诊断/阶段判断 |
| 微观 | 文件/提交级 | "具体哪个文件反复改？" | 热点识别/根因分析 |

三层之间用**下钻链接**衔接（宏观→中观→微观），任何层都不得成为终点。

## §7 与 AI 的关系：AI 天然倾向宏观化

这是本专题必须单独展开的一节——因为**AI 会把宏观化从"人的认知偏好"放大为"系统性倾向"**：

| AI 行为 | 根源 | 后果 |
|:--------|:-----|:-----|
| 输出喜欢给"大结论" | 训练数据以概括性表述为主 | 细分事实被跳过 |
| 分类偏好简单方法 | 统计复现找大概率模式 | 与用户关注维度错位 |
| 引用"拍脑袋数据" | 上下文里某个数字最显眼 | 抽样当全量（55%/30% 案例） |
| 不主动暴露粒度 | 无"粒度自觉" | 用户无法判断结论可信度 |

**对策（写进约束体系）**：

1. **AI 输出强制带粒度标注**：结论必须声明"这是宏观聚合还是细分实证"；
2. **强制可下钻**：凡给出聚合数字，必须给出下钻路径或原始数据位置；
3. **强制来源+口径**：量化数据必须带"来源+基线+条件"四要素（已有 R1 检查，需扩展覆盖"粒度声明"）；
4. **发散前先查知识库细分**：AI 给点子前先检索对应细分领域，避免"跑出来才发现缺领域信息"（用户 08-06 痛点，详见 [`2026-08-06-ai-era-deep-cognition-veracity.md`](../../03_AI/methodology/2026-08-06-ai-era-deep-cognition-veracity.md) §4）。

## §8 落地建议与行动项

| 优先级 | 行动 | 说明 |
|:------:|:-----|:-----|
| **P0** | 分析链禁止宏观结论当终点 | 所有分析报告：宏观结论必须附下钻路径（§6.2） |
| **P0** | 量化断言强制带"粒度+口径" | 扩展 R1 检查：`数值+单位+基线+条件+粒度声明` |
| **P1** | 建立硬件主题聚合视图 | 按 P1/P2 关注点建导航（不移动文件），解决"内容在、结构不在" |
| **P1** | AI 输出模板增加"粒度声明"字段 | 约束技能层：结论前先声明"宏观/细分/估算" |
| **P2** | 定期跑"宏观化审计" | 对近期报告检查：有无宏观结论被用于微观决策 |
| **P2** | 分类维度与关注维度对齐检查 | 目录设计前先列"用户关注点清单"，两者映射 |

**一句话结论**：宏观化是展示层的朋友、挖掘层的敌人——**用"可下钻"对冲"易读"，用"粒度声明"对冲"AI 概括倾向"，用"原始保留"对冲"抽样当全量"**。
