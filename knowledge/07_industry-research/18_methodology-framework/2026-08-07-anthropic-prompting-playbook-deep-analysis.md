## 1. 一句话概括

> **Anthropic 官方《The Prompting Playbook》的方法论内核是「把提示词当工程文档写」：清晰直接地表达指令（而非模糊修辞）、用示例锚定输出格式（few-shot）、用 XML/角色/结构组织上下文、为长文档与工具使用设计专门的上下文策略，并通过迭代评估持续改进——与一线实践者「提示词是工程不是写作」的判断完全一致。**

官方文档的价值在于：**把零散的提示词技巧系统化为可教学、可复用的方法论框架**。

## 2. 官方 Playbook 的定位与设计哲学

**定位**：面向 Claude 开发者的提示工程官方手册——从「如何与模型对话」升级为「如何为模型构建可维护的指令系统」。

**设计哲学（推断）**：
1. **Claude 是「对话模型」**：不是指令执行器——提示工程的目标是「建立有效的协作关系」而非「下达机器指令」
2. **少即是多**：优先简洁清晰的提示，复杂机制（few-shot/结构化）按需引入
3. **可迭代**：提示词不是一次写成的，而是「写→测→改」循环的产物
4. **场景化**：不同场景（对话/工具/长文档/代码）有不同的提示策略

## 3. 核心原则重构

基于 Anthropic 公开方法论，Playbook 可重构为五条核心原则：

| # | 原则 | 核心动作 | 对应问题 |
|:--|:-----|:---------|:---------|
| 1 | 清晰直接 | 直接说「做什么/不做什么」，避免模糊 | 「模型不理解怎么办」 |
| 2 | 示例驱动 | 给 1-3 个高质量示例锚定输出 | 「输出格式不稳定」 |
| 3 | 结构化组织 | XML 标签/角色/分节组织上下文 | 「长提示词混乱」 |
| 4 | 上下文管理 | 长文档分段、工具描述精炼、渐进式加载 | 「上下文超载/遗忘」 |
| 5 | 迭代评估 | 定义评估集、对比迭代、回归测试 | 「改了这处坏了那处」 |

## 4. 原则一：清晰直接（Be clear and direct）

**核心**：把「意图」翻译成「指令」，而不是「描述」。

| ❌ 模糊 | ✅ 清晰 |
|:--------|:--------|
| 「帮我写得专业一点」 | 「把这段文字改成正式的商务邮件语气，保留所有要点」 |
| 「总结这篇文章」 | 「用 5 个要点总结这篇文章，每个要点不超过 30 字，按重要性排序」 |
| 「不要啰嗦」 | 「输出不超过 200 字；删除所有重复信息；不要添加结论之外的内容」 |

**机理**：LLM 在训练中学习到「模糊指令 → 自由发挥」的分布；清晰指令压缩了输出空间，提高遵循率。**每条指令都应回答：做什么、做到什么程度、不做什么、输出什么格式**。

**进阶技巧**：
- 负面指令同样重要：「不要解释，直接给结果」「不要添加免责声明」
- 指令粒度：大任务拆小任务（分步），每步一条清晰指令
- 约束数量：关键约束 3-7 条为宜（过多约束互相冲突）

## 5. 原则二：示例驱动（Give examples）

**核心**：few-shot 示例是最强的格式锚定手段。

```
Few-shot structure:
task description + 1-3 (input -> expected output) examples + current input
```

**为什么有效（第一性原理）**：
1. **格式锚定**：示例展示期望的输出结构（JSON 字段/标题层级/语气）
2. **隐式规则**：示例隐含「什么样的输出算对」，比文字规则更具体
3. **分布引导**：示例把模型引导到「类似示例的生成分布」

**实践要点**：
- 示例要「高质量、有代表性」——坏示例比没示例更有害
- 边界示例（反面示例）：「不要输出这样的」比「要输出那样的」更有效
- 示例数量：1-3 个通常足够，过多增加 token 成本（缓存可缓解）

## 6. 原则三：结构化组织（XML/格式/角色）

**核心**：用结构让长提示词可解析。

**XML 标签**（Anthropic 特色推荐）：
```
<task>translate the text below into English</task>
<text>original content...</text>
<rules>
  - keep proper nouns untranslated
  - use formal tone
</rules>
```

**为什么 XML 有效**：
1. **边界清晰**：模型能区分「指令」与「数据」（指令和数据混在一起是常见失败原因）
2. **可解析**：XML 结构是模型训练中常见的文档格式，遵循度高
3. **可组合**：复杂任务 = 多个标签块组合

**角色设定**（system prompt）：
- 「你是一个资深系统架构师」→ 激活领域知识分布
- 角色 + 约束 + 输出格式 → 三位一体的系统提示词

**分节组织**（Playbook 式长提示词模板）：
```
# Role (who you are)
# Context (why this task)
# Task (what to do)
# Input (where the data is)
# Constraints (what NOT to do)
# Output format (return structure)
# Examples (expected shape)
```

## 7. 原则四：上下文管理（长文档/工具使用）

**长文档场景**（Anthropic 官方强调）：
1. **文档分段**：长文档放开头（prime 效应），重要内容前置
2. **渐进式加载**：先给摘要/大纲，按需展开细节（避免一次塞满上下文）
3. **RAG 而非全文**：检索相关片段而非整篇文档（上下文长度≠理解深度）
4. **知识库文件**：把规则/背景写进文件（AGENTS.md/CLAUDE.md），按需引用

**工具使用场景**：
- 工具描述要精炼：名称 + 用途 + 参数 + 返回，避免冗余
- 工具选择要克制：暴露必要工具，减少选择混乱（呼应「flattened tools」机制）
- 工具调用策略：复杂任务分步调用，每步验证结果

## 8. 原则五：迭代与评估

**迭代循环**：
```
write prompt -> test (typical cases) -> observe failures -> revise -> regression
```

**评估方法**：
- 建立小评估集（10-50 个代表性用例）
- 每次修改跑全量回归（防止「改了这处坏了那处」）
- 记录失败模式（格式错/遗漏/幻觉/过度），针对性修复
- 版本管理（git 化提示词，可回滚）

**关键心态**：提示词没有「一次写对」，只有「迭代逼近」——**把提示词当代码：有版本、有测试、有回归**。

## 9. Claude Code 场景：从提示词到规则系统

Claude Code（Anthropic 编程 Agent）把提示工程升级为「规则系统」：

| Claude Code 机制 | 本质 | 对应原则 |
|:-----------------|:-----|:---------|
| CLAUDE.md / AGENTS.md | 项目级指令文件（角色/约束/约定） | 结构化 + 上下文管理 |
| Skills（SKILL.md） | 可复用技能封装（描述+步骤+检查清单） | 上下文管理 + 迭代 |
| Hooks | 自动化门禁（提交前检查/权限控制） | 评估 + 约束 |
| /simplify 等命令 | 代码审查（复用/质量/效率） | 迭代评估 |
| 子 Agent 委派 | 并行任务分解 | 上下文管理 |

**洞察**：Anthropic 的演进路径 = **从「提示词」到「规则系统」**——把提示工程的最佳实践固化为工具机制（文件加载/Hooks/权限），让开发者「少写提示词、多配规则」。这与本系统（AGENTS.md/RULE.md/USER.md/MEMORY.md + skills + check 脚本）的实践同构。

## 10. 与一线实践的对照（微信文章）

| 维度 | Anthropic 官方（Playbook） | 一线实践（歪斯Wise） |
|:-----|:---------------------------|:---------------------|
| 定位 | 系统化方法论 | 踩坑经验 |
| 强调 | 清晰/示例/结构/上下文/迭代 | 工程化（Git/Review）+ 模型参数 > 提示词 |
| 独特贡献 | XML/角色/长文档策略 | 编程工具链管理提示词 + 参数微调 + 重复技术 |
| 共识 | 提示词是工程 | 提示词是工程 |
| 互补 | 教你「怎么写」 | 教你「怎么管」+「何时不写」 |

**综合结论**：官方 Playbook 提供「写法」；一线实践补充「管理」与「参数」——**完整的能力 = 官方方法论（怎么写）+ 工程化实践（怎么管）+ 模型知识（何时不写提示词）**。

## 11. 深度批判：官方 Playbook 的边界

| # | 批判 | 分析 |
|:--|:-----|:-----|
| 1 | **官方方法论的适用上限** | 官方指南偏「通用对话/文档任务」；对高难推理任务（数学/代码调试）需要更专门的 CoT/工具策略 |
| 2 | **XML 的过度推荐** | XML 在部分模型上有效，但过度使用增加 token 成本与解析负担——应按任务选择 |
| 3 | **示例的隐性成本** | few-shot 示例是「可学习的权重」但也是 token 成本——长示例需配合缓存 |
| 4 | **「清晰直接」的边界** | 过度指令化可能限制模型的创造性输出（创作/头脑风暴场景需要自由度） |
| 5 | **Playbook 的版本滞后** | 模型能力快速演进（新模型指令遵循更强）→ 旧提示技巧可能过时——官方文档需持续更新 |

## 12. 可复用清单

- [ ] 提示词模板化：角色/背景/任务/输入/约束/输出格式/示例 七段式
- [ ] 每条指令自检：做什么？做到什么程度？不做什么？输出什么格式？
- [ ] 关键任务给 1-3 个高质量示例（含边界/反面示例）
- [ ] 长文档前置 + 分段 + 渐进加载（不一次塞满上下文）
- [ ] 指令与数据分离（XML 标签或分隔符）
- [ ] 建立小评估集，每次修改跑回归（提示词即代码）
- [ ] 规则系统化：把稳定约束写进 CLAUDE.md/SKILL.md/Hooks，而非每次重写
- [ ] 工具描述精炼、暴露克制（减少选择混乱）
