## 1. 一句话概括

> **提示词不是文学创作而是软件工程：第一受众是 AI 而非人类；应像代码一样定义输入输出、划分模块边界、管理版本、接受 Code Review——同时承认模型与参数的影响往往大于提示词本身。**

文章来自一线 AI 产品实践者的「踩坑总结」，核心贡献是把提示词从「写作」重新定义为「定义」（函数式思考），并引入完整软件工程工具链（Git/Diff/Plan/Code Review）管理提示词。

## 2. 文章核心内容重构

| 章节 | 核心论点 | 关键操作 |
|:-----|:---------|:---------|
| 01 提示词是工程 | 第一受众是 AI；「优美/极致/人话」是脏数据 | 当函数写：参数/条件/处理/返回格式全确定 |
| 02 高内聚低耦合 | 外部高内聚（一个节点多任务）+ 内部低耦合（子任务独立） | 角色/输入/背景/目标/行动划分边界；废话少→Token少→更稳定 |
| 03 编程工具写提示词 | 本地文件 + Git + Diff + Plan + Code Review | Claude Code/Trae 管理 .md/.json；simplify 三 Agent 审查瘦身 20% |
| 04 模型参数 > 提示词 | 跨模型不兼容；参数微调常比改提示词有效 | max_tokens/thinking/reasoning/response_format/temperature 等 |

**触发场景**：作者在 C 端 AI 产品中面临「不开深度思考（时延敏感）+ JSON 结构化输出（下游对接）+ 提示词调优不稳定」的三重约束——这正是提示词工程化的真实动机：**在模型能力固定、成本/时延受限时，提示词是唯一可调杠杆**。

## 3. 核心命题一：提示词的第一受众是 AI

> 「自然语言是创作，代码语言则是约束。当我们说『极致』和告诉模型可以自由发挥没有什么区别。」

**机理分析**：
- 人类读者从修辞中提取意图（「极致」暗示高要求）；LLM 从 token 分布中提取模式——模糊形容词在训练分布中与「自由度」相关，因此「极致」≈「放开约束」
- 提示词中的每个词都是**约束信号**（呼应知识库「提示词中的信号分类与强度控制」）：描述性修辞是弱信号，结构化指令是强信号
- 第一受众转换后，写作标准从「读起来好」变为「解析起来确定」

**函数式思考模板**：
```
INPUT:  what parameters (variables/format/source)
COND:   what to branch on (boundaries/edge cases)
PROC:   what transformation (steps/rules/forbidden)
OUTPUT: what format (schema/fields/stop condition)
```

## 4. 核心命题二：结构化演进——自然语言→Markdown→JSON

文章引用 Cloudflare 2026 年 2 月的 Markdown for Agent（把 HTML 转 Markdown，因为「大量代码是为人类的上限设计的」），提出演进链：

| 阶段 | 形态 | 特征 | 适用 |
|:-----|:-----|:-----|:-----|
| L1 | 自然语言段落 | 高歧义、低机器可解析性 | 对话/闲聊 |
| L2 | Markdown 结构化 | 标题/列表/引用表达层级，AI 可解析 | 单次任务指令 |
| L3 | JSON 格式化 | 字段/枚举/schema，下游可直接消费 | 多节点流水线/系统对接 |

**本质**：信息形态从「人类可读优先」转向「机器可解析优先」——这与「AI 才是最重要的读者」一致。**所有文档都该为 AI 重写一遍**（作者原话）。

**延伸洞察**：这解释了为什么 Agent 时代的接口是「结构化文档」（AGENTS.md/CLAUDE.md/SKILL.md/JSON schema）——LLM 的上下文窗口有限，结构化能最大化「信息密度/ token 比」，减少歧义导致的错误分支。

## 5. 核心命题三：高内聚低耦合在提示词中的适用与边界

**文章主张**：
- **外部高内聚**：一个模型节点可承担多个子任务（指代消解、意图识别、查询改写、约束补全、结构化输出放一个节点）——因为拆分节点 = 更多耗时和成本，C 端时延不可忍
- **内部低耦合**：节点内部每个子任务独立，改动一个不影响其他（角色/输入/背景/目标/行动 = 边界划分）

**第一性原理分析**：
- 为什么不拆节点？LLM 单次调用已有能力完成多任务（模型"聪明到可以一个节点处理多子任务"）；节点间通信有 token 成本和时延成本
- 为什么内部要低耦合？提示词是**可维护代码**：边界清晰 → 改一处不牵全身 → 逻辑冲突少 → 废话少 → token 少 → 稳定
- 边界在哪？当子任务需要不同模型/不同温度/不同工具时，必须拆节点；当子任务共享上下文且可单次完成时，合并节点

**一个提醒**：高内聚低耦合是软件工程原则，映射到提示词有天然差异——软件模块间有编译期类型检查，提示词子任务间只有隐式语义依赖，**耦合是隐性的**，更需要靠「命名/注释/格式」显性化。

## 6. 核心命题四：用编程工具管理提示词

这是文章最具操作性的部分，五条实践：

| 实践 | 机制 | 解决什么问题 |
|:-----|:-----|:-------------|
| ① 本地文件存储 | 提示词 → .md/.json 文件，AI 按需加载 | 上下文污染（模型记住旧逻辑乱改）、幻觉、版本对比 |
| ② Git 版本管理 | commit 轻量改动，AI 总结变更，快速回滚 | 人忘模型忘 git 不忘；变更可追溯 |
| ③ Diff 对比 | 人工审核 AI 改了什么 | 提示词是规则不能乱动；杜绝「忘了自己改过什么」 |
| ④ Plan 模式 | 先对谈理清思路再审核；思考 high 执行 medium | 从零到一写提示词 → 迭代式澄清 |
| ⑤ Code Review | simplify 三平行 Agent 审查复用/质量/效率 | 「语感不错但结构糟糕」的问题；作者提示词瘦身 20% |

**深层洞察**：这本质上是把提示词视为**一等代码资产**（AI 时代的「新源代码」）——其含义远超「写好提示词」：
- 提示词 = 行为契约（决定 AI 做什么、不做什么）
- 版本管理 = 行为审计（谁在什么时候改了什么行为）
- Code Review = 质量门禁（在进入生产前发现问题）

**与本系统对照**：本系统的 skills/*/SKILL.md + AGENTS.md + RULE.md + 规则文件，正是「本地文件存储提示词」的规模化实践——且已做到 Git 管理 + 三同步 + check 脚本验证，比文章的单人实践更进一步。

## 7. 核心命题五：模型与参数影响大于提示词

文章用两个「误区」收尾：

**误区 1：模型陷阱**
- 同一提示词跨模型复用 = 「调试惨案的开始」（Kimi 上正常，豆包上失效）
- 模型差异维度：指令遵循度（听话 vs 自由发挥）、中文理解（语法敏感 vs 英文思考）、上下文稳定性（几万 token 就开始幻觉，勿迷信 1M 上下文）
- 模型进化带来「能力溢出」→ 提示词需再调优（减重复或增负荷）

**误区 2：参数微调有大惊喜**
- 调一百遍提示词不如微调参数
- 关键参数：max_output_tokens（防过度发挥）、thinking（深度思考开关）、reasoning（思考强度）、store（会话存储）、response_format（强制格式）、stream（流式）、tools（工具/MCP）、temperature（随机性）

**机理**：提示词改变的是「输入分布」，参数改变的是「解码策略」——后者直接控制输出空间的性质（格式、长度、随机性、思考深度）。**当输出性质（格式/长度/随机性）出问题时，先查参数；当语义/边界出问题时，才改提示词。**

## 8. 重复技术的机理：为什么「重复比深度思考更高效」

作者最后的「好气又好笑」的发现：

> 把那句重要的话在开头、中间、文末重复 1 次，忽然就稳定下来了。

**机理分析（第一性原理）**：
1. **注意力加权**：Transformer 的自注意力中，关键约束在多处出现 → 在解码的多个阶段都获得注意力权重 → 被「记住」的概率显著上升（呼应知识库「注意力因果链」：输入关键词调控输出权重）
2. **上下文位置偏置**：LLM 对开头（primacy）和结尾（recency）内容遵循度最高，中间最弱——三处重复恰好覆盖三个高权重位置
3. **失忆补偿**：长上下文/复杂任务中模型会「遗忘」早期约束，重复 = 冗余编码（类似通信中的纠错码）

**代价权衡**：格式层面不干净（token 浪费 = 脏污染），但换取稳定性——**在有界场景（关键约束）下，稳定 > 优雅**。这与工程中的「冗余设计」同理：可靠性靠冗余，提示词可靠性靠重复。

## 9. 深度批判：五个值得商榷之处

| # | 文章观点 | 商榷 |
|:--|:---------|:-----|
| 1 | 「极致/优美/人话全是脏数据」 | 过度绝对：对创作类任务（营销文案/润色），风格词汇恰恰是有效信号；「脏」取决于任务类型而非词汇本身 |
| 2 | 高内聚（一个节点多任务） | 收益（省时延省成本）与风险（任务耦合→错误传染、难调试）需权衡；对高价值/高风险任务，拆节点更安全 |
| 3 | 用 Claude Code/Trae 写提示词是「版本答案」 | 是当前最佳实践，但存在工具锁定与上下文污染转移（工具本身也在读你的历史）；且非编程背景用户门槛高 |
| 4 | 「重复 1 次就稳定」 | 经验性结论，缺乏可复现实验；重复的位置/次数/内容长度对效果有非线性影响，应视为启发而非定律 |
| 5 | 模型参数 > 提示词 | 过于笼统：在「模型能力边界」内参数是杠杆；但跨模型差异本质上是**提示词适配问题**，长期看提示词工程能力仍是核心竞争力 |

## 10. 与本系统实践的对照

| 文章实践 | 本系统对应 | 差异 |
|:---------|:-----------|:-----|
| 提示词本地文件化 | skills/*/SKILL.md + AGENTS.md/RULE.md/USER.md/MEMORY.md | 本系统已四级文件化（身份/规则/记忆/技能），且按需加载 |
| Git 版本管理 | 全库 git 管理 + [AI] 前缀提交 + 三同步 | 本系统有自动提交机制，可追溯 |
| Code Review 提示词 | check_md_format / link-validator / 技能三维查重 | 本系统有自动化质量门禁脚本 |
| 高内聚低耦合 | 技能单一职责 + 编排器分层 | 本系统用「编排」而非「节点」实现组合 |
| 重复技术 | 关键约束在 AGENTS.md/RULE.md/任务描述多处重复 | 本系统无意中实践了「三处重复」原则 |

**核心共识**：提示词工程化 = 把「写提示词」升级为「构建可维护的 AI 行为系统」——这正是本系统 40+ 技能 + 约束体系存在的理由。

## 11. 可复用清单

- [ ] 写提示词前先问：第一受众是 AI 还是人？修辞词汇对任务是否必要？
- [ ] 用函数式模板组织：输入/条件/处理/输出格式
- [ ] 优先结构化：自然语言 → Markdown → JSON（下游可消费优先）
- [ ] 模块边界显性化：角色/输入/背景/目标/行动分区，改一处不牵全身
- [ ] 提示词纳入版本管理：本地文件 + Git + Diff 审核
- [ ] 遇到输出问题先分类：格式/长度/随机性 → 查参数；语义/边界 → 改提示词
- [ ] 跨模型切换时重新适配提示词（不直接复用）
- [ ] 关键约束三处重复（开头/中间/结尾），以 token 换稳定
