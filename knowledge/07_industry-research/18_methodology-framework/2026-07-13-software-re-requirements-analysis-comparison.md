## 1. 分析框架

### 1.1 十二维权衡模型

> **v2.0 扩展**: 从 4 维 → **12 维** 覆盖需求分析阶段的所有核心权衡点。12 维按角色分三组：
>
> - **产品组 (4维)** — 直接面向用户/市场的外显质量
> - **工程组 (4维)** — 决定研发过程与交付的内禀质量
> - **运营组 (4维)** — 决定长期拥有成本与生存质量的持续质量

### 1.2 十二维详细定义

#### 🎯 产品组 (Product) — 用户看到的直接价值

| 维度 | 编号 | 定义 | 核心问题 | 典型输出物 |
|:-----|:----:|:-----|:---------|:-----------|
| **🖥️ UI设计投入** | **P1** | 用户交互界面与交互流程的设计投入 | 谁用？怎么操作？什么反馈？ | 线框图、交互原型、设计系统组件 |
| **🔍 需求深度分析** | **P2** | 对业务逻辑、边界条件、异常流程的深入挖掘 | 到底要做什么？边界在哪？异常怎么处理？ | 需求规格说明书、用例图、状态机 |
| **📋 标准法规合规** | **P3** | 必须遵守的标准、行业规范、法律法规 | 哪些标准必遵守？哪些可选？不遵守风险？ | 标准覆盖矩阵、合规检查清单 |
| **💡 创新差异化** | **P4** | 产品竞争壁垒与创新点的定义与投入 | 凭什么比别人好？创新的技术可行性？ | 创新点说明书、专利分析、技术预研报告 |

#### 🔧 工程组 (Engineering) — 决定研发过程与交付质量

| 维度 | 编号 | 定义 | 核心问题 | 典型输出物 |
|:-----|:----:|:-----|:---------|:-----------|
| **♻️ 可复用点分析** | **E1** | 对已有代码、库、框架、模块复用可能性的评估 | 什么不用重写？什么可以借鉴？ | 技术选型评估、组件目录、第三方依赖清单 |
| **🔗 集成复杂度** | **E2** | 外部系统/硬件/接口的集成难度与风险 | 跟多少个系统对接？接口协议复杂不？ | 集成拓扑图、接口协议矩阵、联调计划 |
| **🧪 可测试性投入** | **E3** | 测试策略、测试工具、测试环境的定义 | 怎么验证正确性？测试环境能否搭建？ | 测试策略文档、Test Plan、自动化覆盖目标 |
| **👥 团队能力要求** | **E4** | 团队技术栈、领域知识、规模的评估 | 团队会不会做？需要招人还是外包？ | 技术栈评估、学习路线、资源需求清单 |

#### 🛡️ 运营组 (Operations) — 决定长期生存质量

| 维度 | 编号 | 定义 | 核心问题 | 典型输出物 |
|:-----|:----:|:-----|:---------|:-----------|
| **📊 系统指标定义** | **O1** | 非功能性需求的量化和目标设定 | 多快？多稳？多安全？多容易维护？ | SLA、KPI树、性能预算 |
| **🔐 安全合规投入** | **O2** | 安全架构、数据保护、隐私合规 | 数据怎么保护？攻击面多大？合规要求？ | 安全架构、威胁模型、数据流图 |
| **🔧 可维护性投入** | **O3** | 代码结构、文档、版本策略的可持续性 | 后续谁维护？改需求要多久？ | 架构文档、API规范、版本策略 |
| **🚀 运营复杂度** | **O4** | 部署、监控、告警、灾备的运营投入 | 怎么部署？怎么监控？出问题怎么办？ | 部署方案、监控方案、灾备方案、Runbook |

### 1.3 十二维分类语义

```text
产品组 (What) — 做什么、给谁用、凭什么
   P1+P2+P3+P4 = 产品价值定义

工程组 (How) — 怎么做、谁来用、怎么验证
   E1+E2+E3+E4 = 研发可行性评估

运营组 (Run) — 怎么跑、怎么活、怎么死
   O1+O2+O3+O4 = 长期可生存性

需求阶段十二维的产出, 必须回答:
   What: 我们做的是什么?          (P1+P2)
   Why: 凭什么比别人好?          (P3+P4)
   Can we: 我们做得了吗?         (E1+E2+E3+E4)
   Will it live: 它能活多久?     (O1+O2+O3+O4)
```

### 1.4 冲突矩阵：权衡决策框架

> 需求分析的核心不是单一维度最大化，而是**在冲突的维度间找到可接受的平衡点**。

| 冲突对 | 冲突本质 | 典型场景 | 决策原则 |
|:-------|:---------|:---------|:---------|
| **P1 (UI) ↔ P2 (深度)** | 表面体验 vs 逻辑完整性 | UI投入过多 → 逻辑未深挖就开工 | 根据场景定：ToC 偏向 P1 (小程序/前端)，ToB 偏向 P2 (企业软件) |
| **P4 (创新) ↔ O1 (指标)** | 新功能 vs 稳定性能 | 创新功能可能降低性能 | 创新 > 指标阈值即可，不追求极致指标 |
| **E1 (复用) ↔ P4 (创新)** | 用成熟方案 vs 自主研发 | 复用虽快但限制创新 | 复用基础上做增量创新，避免颠覆式 |
| **E1 (复用) ↔ O3 (可维护)** | 外部依赖 vs 长期可控 | 第三方库简化但产生依赖风险 | 关键路径自研，非关键路径复用 |
| **E2 (集成) ↔ P2 (深度)** | 集成复杂度 vs 业务深度 | 对接系统太多，分散深度分析精力 | 先做核心域深度，集成侧做到「接口对齐」 |
| **E3 (可测试) ↔ E4 (团队)** | 测试投入 vs 团队产出 | 测试自动化投入挤占研发资源 | 关键路径 100% 覆盖，非关键路径降低 |
| **O2 (安全) ↔ E4 (团队)** | 安全要求 vs 团队能力 | 安全要求高但团队缺安全经验 | 引入安全工具链 + 外部审查 |
| **O3 (可维护) ↔ O4 (运营)** | 代码优雅 vs 部署简便 | 过度抽象增加运营复杂度 | 优先运营简洁，再考虑架构优雅 |
| **P3 (标准) ↔ P4 (创新)** | 遵守标准 vs 突破标准 | 标准限定创新空间 | 标准覆盖核心功能，创新在扩展功能 |
| **O1 (指标) ↔ E4 (团队)** | 性能目标 vs 团队能力 | 定太高做不到，定太低无挑战 | 基线 > 竞品基准，目标设置合理 |

## 2. 七类软件场景对比总览

### 2.1 十二维投入权重总表

> **v2.0 扩展**: 从 4 维 → 12 维全面对比。数值代表该维度在需求分析阶段**占总投入的百分比**，各场景行内合计 100%。

## 3. 小程序 — 轻量级平台内应用

### 3.1 场景特征

小程序运行在微信/支付宝/抖音等宿主平台之上，核心特征是**轻量、即用即走、平台绑定**。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 宿主能力限制 | API/SDK受平台约束 | 需求必须聚焦「平台能力的子集」 |
| 即用即走 | 用户单次使用 < 30秒 | 需求必须「首屏说清价值」 |
| 病毒传播 | 社交分享是核心获客 | 需求含「分享激励/裂变机制」 |
| 审核周期 | 平台有发布审核 | 需求变更成本高，减少后续改动 |

### 3.2 四维分析

#### 🖥️ UI设计 — 🔴 重度投入 (40%)

这是小程序需求分析中**最关键的维度**。理由：

1. **首屏决定留存** — 用户在小程序上的注意力窗口极短（3-5秒），UI必须在这个窗口内传递价值
2. **宿主设计规范强制** — 微信/支付宝有严格的设计规范（WeUI/蚂蚁设计），需求分析阶段就要对齐
3. **交互路径最短** — 每多一步操作，流失率增加20%+

**需求分析中UI相关的核心工作**：

```text
UI需求分析清单 (小程序):
  □ 首页信息架构: 3秒内让用户看懂是什么
  □ 操作路径长度: 核心功能 ≤ 3次点击
  □ WeUI/蚂蚁设计规范检查: 组件/字体/间距/颜色
  □ 分享卡片设计: 标题/描述/缩略图
  □ 加载状态: Skeleton/loading/空状态/错误状态
  □ 授权页面: 手机号/位置/微信登录的触发时机
```

#### 🔍 需求深度分析 — 轻度 (15%)

- 业务逻辑本身通常不复杂（单功能点）
- 异常流程少（宿主平台兜底）
- 核心是「UI交互流程的完整性」，不是「业务逻辑的深度」

**需求深度的正确投入点**：

- 边界输入验证（超出平台限制的字符数/图片大小/访问频率）
- 网络异常时的用户体验（弱网/断网/服务器超时）

#### ♻️ 可复用点分析 — 中度 (25%)

| 可复用来源 | 复用价值 | 说明 |
|:-----------|:--------:|:------|
| 宿主组件库 | 🔴 高 | 尽量用微信原生组件（性能更好，通过审核更快） |
| 企业内部组件库 | 🟡 中 | 如果有的话，可减少50%+ UI开发量 |
| 同类小程序模板 | 🟡 中 | 电商/工具/内容模板 |
| 后端 API (已有) | 🔴 高 | 是否已有后端，决定是否要自建 |

#### 📊 系统指标定义 — 中度 (20%)

| 指标 | 目标 | 测量方式 |
|:-----|:----:|:---------|
| 首次加载时间 | < 2s | 小程序性能监控 |
| 操作响应时间 | < 500ms | AppData |
| Core Web Vitals | CLS < 0.1, LCP < 2.5s | 微信 Labs |
| 用户留存率 (次日) | 行业平均 20-40% | 平台数据分析 |
| 转化率 | 业务定义 | 漏斗分析 |

#### 权衡点扩展：小程序十二维决策要点

> **v2.0 新增**: 在原始4维基础上补充剩余8维的分析

**P3 (标准合规)** — 8% 投入

- 宿主平台审核规范是最硬的标准约束：微信/支付宝的《小程序运营规范》决定了什么能做、什么不能做
- 合规底线：**不得违反平台类目资质要求**（如金融类需牌照）
- 需求分析阶段必须完成：功能清单 → 对齐平台开放类目 → 排除不合规功能
- ❌ 常见错误：做了一半才发现功能在审核中不可见

**P4 (创新差异化)** — 7% 投入

- 小程序的创新空间**极度有限**（受宿主平台限制）
- 创新通常不在功能层面（大家都在做同样的电商/工具），而在**交互细节和裂变机制**
- 需求阶段应聚焦：分享链路的冷启动方式 > 功能新颖度

**E2 (集成复杂度)** — 13% 投入 🔴（该场景前三）

- 小程序看似轻量，但**集成复杂度不低**：
  - 微信支付/支付宝支付 → 商户号 + 证书 + 回调
  - 云开发/Serverless → 数据API对接
  - 第三方服务 → 物流/短信/地图
- 需求分析阶段：画出「外部依赖图谱」，标注每个集成的认证周期

**E3 (可测试性)** — 8%

- 小程序测试的特殊性：**宿主平台审核机制决定了测试环境不可完整模拟**
- 真机调试 vs 开发工具预览的差异——特别是支付/登录/订阅消息
- 需求含「灰度发布方案」+ 「AB测试埋点」

**E4 (团队能力)** — 4%

- 小程序技术门槛低（Vue/React 背景即可上手）
- 但**平台特有坑多**：微信 JSAPI 兼容性、分享限制、Webview 限制
- 需求阶段评估团队是否有「踩过小程序坑」的经验

**O1 (系统指标)** — 5%

- 小程序性能指标主要受**宿主平台限制**（不是团队能控制的）
- 首屏加载时间核心取决于：包大小（< 2MB） + 宿主缓存策略
- 需求分析阶段应定：包体积预算 + 首屏白屏时间目标

**O2 (安全合规)** — 3%

- 小程序安全由宿主平台兜底（微信隔离用户态和JS环境）
- 但**数据安全性需自保**：用户手机号/位置信息不得上传到非认证服务器
- 需求含：数据传输加密 + 隐私协议

**O3 (可维护性)** — 2%

- 小程序的维护投入**极低**——一次发布，宿主平台无需适配多端
- 版本管理由宿主平台控制（审核才生效）
- 需求阶段无需过度关注架构可维护性

```text
1. 业务方需求 -> 2. 对齐平台能力边界 -> 3. 输出交互原型（Axure/Figma）
   v                                              v
4. 评审: ①交互路径≤3步? ②首屏价值清晰? ③符合宿主规范?
   v
5. 输出 PRD: 页面原型 + 交互说明 + 数据埋点 + 分享策略
   v
6. 产出: 需求文档 + 设计稿 + 组件使用清单
```

## 4. 前端应用 — 用户交互型应用

### 4.1 场景特征

涵盖 Web App、移动端 App（React Native/Flutter）、桌面端（Electron）。核心特征是**跨平台、多设备适配、用户直接使用**。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 多端适配 | Web/Mobile/Tablet/Desktop | 需求须考虑「每端的行为差异」 |
| 用户体验驱动 | 直接决定产品成败 | UI/UX设计投入大 |
| 第三方依赖多 | 框架/库/CDN/API | 需求含「依赖选型分析」 |
| 版本迭代快 | CI/CD，周级/双周级发布 | 需求须「可分阶段交付」 |

### 4.2 四维分析

#### 🖥️ UI设计 — 🔴 重度投入 (35%)

**与小程序不同**：小程序的UI受平台规范强约束，前端应用的UI设计空间更大、也更需要策略投入。

```text
UI需求分析的核心粒度:

□ 设计系统 (Design System):
   - 颜色/字体/间距/阴影的 Token 化定义
   - 组件库选型: Ant Design / Material UI / shadcn/ui
   - 一致性: 全应用使用同一设计语言

□ 响应式布局:
   - 断点定义 (mobile/tablet/desktop)
   - 内容优先级: 小屏隐藏什么？折叠什么？
   - 手势操作 (移动端特有)

□ 状态覆盖:
   - Loading / Empty / Error / Success / Partial
   - 每个组件都需要定义这5种状态

□ 无障碍 (Accessibility):
   - 色彩对比度 ≥ 4.5:1
   - 键盘导航顺序
   - Screen reader 标注
```

#### 🔍 需求深度分析 — 中度 (20%)

前端应用的需求深度分析重点不是「业务逻辑」而是**「用户场景的完整覆盖」**：

- 正常路径 → 核心功能流
- 分支路径 → 用户选择/配置
- 异常路径 → 超时/失败/权限不足
- 边界路径 → 空数据/极端数据/并发操作

#### ♻️ 可复用点分析 — 中度 (20%)

| 复用层次 | 复用价值 | 典型来源 |
|:---------|:--------:|:---------|
| UI组件库 | 🔴 高 | Ant Design / shadcn/ui / 自定义设计系统 |
| 状态管理 | 🟡 中 | Redux / Zustand / Jotai 选型 |
| API层封装 | 🔴 高 | Axios / tRPC / GraphQL 客户端 |
| 工具函数 | 🟡 中 | lodash / date-fns / 自定义hooks |
| 权限体系 | 🔴 高 | 如有已有企业级权限方案 |
| 国际化方案 | 🟡 中 | i18n / react-intl 选型 |

#### 📊 系统指标定义 — 中高度 (25%)

前端应用的指标定义必须包含**体验指标**和**性能指标**两个层面：

```text
性能指标 (Lighthouse / Web Vitals):
  □ LCP (最大内容绘制) < 2.5s
  □ FID (首次输入延迟) < 100ms
  □ CLS (累计布局偏移) < 0.1
  □ TTI (可交互时间) < 3.8s
  □ 页面大小 < 500KB (首屏)
  □ API 响应时间 < 200ms (p95)

体验指标:
  □ 核心路径转化率 ≥ 85%
  □ 用户任务完成时间 ≤ 30s
  □ 错误率 < 1%
  □ 用户满意度 (CSAT/NPS)

工程指标:
  □ 构建时间 < 5min
  □ 首屏 JS 包体积 < 200KB
  □ 代码覆盖率 ≥ 80%
  □ Lighthouse 评分 ≥ 90
```

#### 权衡点扩展：前端应用十二维决策要点

> **v2.0 新增**

**P3 (标准合规)** — 5%

- 前端标准约束弱（HTML/CSS/WCAG 是无强制力的标准）
- 但**无障碍合规可能成为法律要求**：欧洲 EN 301 549、美国 Section 508
- 需求分析阶段需确认：目标市场是否有无障碍合规强制要求？

**P4 (创新差异化)** — 13% 🔴（该场景前三）

- 前端应用是**差异化展示能力最强的场景**（UI/UX决定产品印象）
- 创新点集中在：交互范式（拖拽/手势/AI对话）、可视化效果、跨端一致性
- 需求阶段应产出「交互创新白皮书」——做什么、不做什么、为什么比别人好

**E2 (集成复杂度)** — 8%

- 前端集成复杂度通常**低于企业软件**（前端是消费端，不是聚合端）
- 但多端（Web/移动端/桌面端）的适配集成是核心挑战
- 需求阶段：明确「一次开发多端运行」策略（如 Flutter/React Native）

**E3 (可测试性)** — 10%

- 前端可测试性投入常被低估——**UI测试是最难自动化的**
- 核心挑战：跨浏览器兼容测试、响应式布局验证、视觉回归
- 需求含：组件测试策略 → 每个组件 5 种状态覆盖率

**E4 (团队能力)** — 5%

- 前端团队的能力多样性要求高：CSS 精调 / 动效 / 性能优化 / 跨端 / 无障碍
- 需求阶段需评估：团队里的「CSS 高手」和「性能工程师」是否存在

**O1 (系统指标)** — 8%

- 前端性能指标的**定义比实现更难**——用户感知的性能 ≠ 技术指标
- 需求阶段的核心产出：**性能预算表**（每个核心页面的 JS 体积/图片体积/LCP 目标）

**O2 (安全合规)** — 3%

- 前端安全核心是**输入输出控制**：XSS / CSRF / 敏感数据暴露
- 需求分析阶段应完成：敏感数据分类（哪些数据不能进前端）

**O3 (可维护性)** — 4%

- 前端的可维护性取决于**组件化水平**——设计系统决定了维护成本
- 需求阶段应定义：「设计系统 Token」而不是「每个页面单独设计」

### 4.3 需求分析流程建议

```text
Phase 1 - 产品定位:
   用户画像 + 用户旅程地图 + 信息架构
   v
Phase 2 - 交互设计:
   线框图 -> 高保真原型 -> 用户测试
   v
Phase 3 - 技术选型:
   框架选型 + 组件库选型 + 状态管理 + API方案
   v
Phase 4 - 指标定义:
   Web Vitals 目标 + 包体积预算 + 性能预算
   v
Phase 5 - 分阶段规划:
   MVP (核心功能) -> 增强 (体验优化) -> 完善 (高级功能)
```

## 5. 企业软件 — 复杂业务流程系统

### 5.1 场景特征

ERP、CRM、运维管理平台、审批系统等。核心特征是**复杂业务逻辑、多角色权限、数据一致性要求高**。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 多角色系统 | 不同角色看到/操作不同 | 需求须「按角色描述」 |
| 业务流程驱动 | CRUD + 状态机 + 审批流 | 需求核心是「流程定义」 |
| 数据一致性 | 数据库事务/数据血缘 | 需求含「数据完整性约束」 |
| 合规要求 | 审计/财务/信息安全合规 | 需求须包含合规条款 |
| 长交付周期 | 3-18个月 | 需求须「版本化 + 增量交付」 |

### 5.2 四维分析

#### 🖥️ UI设计 — 中度 (20%)

企业软件的UI设计投入权重＜前端应用，但**不等于不重要**。关键区别：

- **效率优先** — 企业软件用户每天使用8小时，UI的核心目标是「操作效率」而非「视觉吸引力」
- **信息密度高** — 表格/列表/仪表盘类UI需要高信息密度设计
- **可配置性** — 用户可能想自定义字段/布局

```text
企业软件UI需求分析重点:
  □ 导航层级: 最多3级，太深就出问题
  □ 数据表格: 列排序/筛选/导出/批量操作
  □ 表单设计: 字段分组 + 表单联动 + 校验规则
  □ 操作确认: 高风险操作必须二次确认
  □ 多角色视图: 管理员/操作员/审计员看到不同界面
  □ 报表/看板: 数据可视化 -> 决策支持
```

#### 🔍 需求深度分析 — 🔴 重度投入 (35%)

**企业软件需求分析的成败决定了项目的成败**。这是所有场景中需求分析最深的一类。

```text
需求深度分析的层次:

L1 - 功能列表: 描述「要做什么」
  例: "系统支持创建采购订单"

L2 - 业务流程: 描述「怎么做」
  例: "采购员创建->部门经理审批->财务审核->供应商确认"

L3 - 状态机: 描述「所有状态和转换」
  例: 草稿->待审批->已驳回(回草稿)->待财务审核->已通过->已关闭
      每个状态的读/写/删除/操作权限

L4 - 约束规则: 描述「不能做什么」
  例: "金额 > 100万的采购单需要总经理审批"
       "已关闭的订单不可修改和删除"

L5 - 数据血缘: 描述「数据从哪里来、到哪里去」
  例: "采购订单->入库单->付款单->会计凭证->总账"

L6 - 异常场景: 描述「出错了怎么办」
  例: "审批超时24h -> 自动升级到上级审批人"
       "付款失败 -> 自动重试3次 -> 人工介入"
```

**关键产出物**：

```text
需求分析阶段必须产出的文档:
  □ 业务流程泳道图 (BPMN 2.0 / 跨职能流程图)
  □ 数据模型 (ER图 / 数据字典)
  □ 状态机图 (UML State Diagram)
  □ 角色-权限矩阵 (RABC矩阵)
  □ 用例说明书 (每个用例含: 前置条件/正常流/异常流/后置条件)
  □ 数据字段定义表 (字段名/类型/长度/必填/默认值/校验规则)
```

#### ♻️ 可复用点分析 — 中度 (20%)

| 复用层次 | 复用价值 | 典型来源 |
|:---------|:--------:|:---------|
| 权限管理模块 | 🔴 高 | RBAC / ABAC / Casbin |
| 工作流引擎 | 🔴 高 | Camunda / Flowable / Activiti |
| 报表引擎 | 🟡 中 | 已有报表系统 / JasperReports |
| 消息通知模块 | 🟡 中 | 内部消息队列 + 通知系统 |
| 用户组织管理 | 🔴 高 | LDAP / OAuth2 / SSO |
| 审批流配置 | 🟡 中 | 可提取为通用审批引擎 |
| 异常监控体系 | 🟡 中 | ELK / Prometheus / Grafana |

#### 📊 系统指标定义 — 中高度 (25%)

企业软件的指标更关注**可靠性、响应时间、数据一致性**：

| 指标 | 目标 | 说明 |
|:-----|:----:|:------|
| API响应时间 (p95) | < 500ms | 合理阈值 |
| 核心流程完成时间 | 业务定义 | 例如：审批流程 < 24h |
| 系统可用性 | 99.9%+ | 允许的停机时间 |
| 数据一致性 | 100% | 不允许脏数据 |
| 并发用户数 | 业务定义 | 同时在线用户 |
| 操作可审计 | 所有操作可追溯 | 审计日志完整性 |
| 报表生成时间 | < 30s (复杂报表) | 大数据量查询 |
| 导入导出能力 | 10000条/min+ | Excel/CSV |

#### 权衡点扩展：企业软件十二维决策要点

> **v2.0 新增**

**P3 (标准合规)** — 6%

- 行业标准约束最强：财务软件需符合会计准则、医疗软件需HIPAA、政务软件需等保
- 标准合规是**市场准入条件**——不达标则产品不可用
- 需求阶段必须产出「行业标准 → 功能需求」映射表

**P4 (创新差异化)** — 6%

- 创新在**效率提升**而非UI——自动化流程、智能决策辅助
- 最佳来源：解决业务流程中公认的痛点（审批慢、数据不对、报表耗时）
- ❌ 常见错误：加入「看起来很酷但用户不用」的功能

**E1 (复用分析)** — 7%

- 框架层复用率高但业务层极低（< 30%）
- 核心决策：工作流引擎 通用（Camunda 覆盖 80%）vs 自研（覆盖 20%特殊流程）

**E2 (集成复杂度)** — 12% 🔴（该场景前三）

- **企业软件没有孤岛**——LDAP/AD + 审批流 + 消息 + 报表 + 第三方API
- 隐藏成本：每个集成 1-2周联调 + 测试环境 + 对方不可控
- 核心产出：**集成拓扑图** + **接口协议矩阵**

**E3 (可测试性)** — 10%

- 最大难点：**数据依赖**——测试需真实数据但涉及隐私
- 核心决策：数据脱敏 vs 合成数据 vs 生产子集

**E4 (团队能力)** — 9%

- **领域知识 > 技术能力**——懂业务流程的人更难找
- 无业务专家 → 必须引入业务顾问

**O2 (安全合规)** — 5%

- 多租户隔离 + RBAC/ABAC + 操作审计 + 等保/PCI-DSS
- 必须完成：**数据分类分级** + **权限矩阵** + **审计日志规范**

**O3 (可维护性)** — 7%

- **生命周期最长**（5-15年），直接决定TCO
- 核心：模块化（独立升级）+ 可配置化（不改代码）

**O4 (运营复杂度)** — 3%

- 私有化部署：需含「部署+升级+迁移方案」
- 需确认部署模式决定投入量

### 5.3 需求分析方法论建议

```text
企业软件需求分析的标准方法:

Step 1 - 干系人分析:
   谁在用？谁在决策？谁在买单？谁在维护？

Step 2 - 业务流程挖掘:
   当前流程是什么？-> 哪里效率低？-> 目标流程设计

Step 3 - 数据建模:
   核心实体是什么？-> 实体关系 -> 数据流

Step 4 - 需求优先级:
   MoSCoW方法: Must/Should/Could/Won't

Step 5 - 产出规格说明书 (PRS):
   [附件: 业务流程泳道图 + 数据模型 + 状态机 + 权限矩阵 + 字段定义表]
```

## 6. OpenBMC/BIOS — 底层固件

### 6.1 场景特征

固件的核心特征是**硬件绑定、无OS环境、远程管理、确保持久运行**。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 硬件绑定 | BMC绑定到特定板卡、传感器、GPIO | 需求分析前提是「硬件规格已稳定」 |
| 无OS运行 | 基于u-boot/yaffs等裸机环境 | 需求含「资源预算」(Flash/RAM/CPU) |
| 7×24运行 | 固件永不重启（除非升级） | 需求含「内存泄漏检测、看门狗」 |
| 远程管理 | 人在异地通过管理网操作 | UI需求极少但「接口需求」极高 |
| 标准兼容 | IPMI/Redfish/PLDM | 需求含「标准覆盖度分析」 |
| 固件升级风险 | 升级失败=设备变砖 | 需求含「升级安全机制」 |

### 6.2 四维分析

#### 🖥️ UI设计 — 极低 (5%)

- BMC的UI限于：WebUI（可选）、SOL（串口终端）、KVM（远程桌面）
- **UI不是核心价值**，核心价值在**接口兼容性和稳定性**
- WebUI通常用现成框架（如webui-vue），需求分析中分配1-2天评审UI布局即可
- SOL/KVM是已成熟的标准功能，不需要重复设计

**UI需求分析的正确姿态**：

```text
  □ 支持哪些接口？(HTTPS/WSS/SSH/SOL/KVM)
  □ 管理页面布局是否兼容1280×720以上的分辨率？
  □ Redfish API 覆盖率如何？(不是UI覆盖率)
```

#### 🔍 需求深度分析 — 🔴 重度投入 (30%)

BMC/BIOS的需求深度核心在**「标准协议的覆盖度」和「异常场景的覆盖率」**。

```text
需求深度分析的三层:

Layer 1 - 标准覆盖:
  硬件管理接口覆盖: Redfish 2020+ / IPMI 2.0 / PLDM / MCTP
  传感器类型覆盖: 温度/电压/电流/功耗/风扇/液冷
  事件管理覆盖: SEL / PET / SNMP Trap / Redfish Event

Layer 2 - 硬件适配:
  GPIO 定义表: 哪个GPIO控制哪个硬件的哪个状态
  I2C 总线拓扑: 哪个传感器挂在哪条I2C上、地址多少
  FRU/EEPROM 布局: Product Info / Asset Tag / MAC地址
  Watchdog 配置: 超时时间、复位动作

Layer 3 - 异常场景:
  看门狗超时 -> 自动复位还是持久化后复位？
  传感器读不到 -> 默认值还是标记 NA？
  固件升级中断 -> 回滚机制、双镜像启动
  BMC 自身异常 -> 硬件看门狗复位 BMC
  Redfish 并发请求 -> 队列/拒绝/串行化？
```

#### ♻️ 可复用点分析 — 🔴 重要 (30%)

BMC/BIOS 的可复用分析是**所有场景中最关键的**之一，因为：

- OpenBMC 社区提供了大量现成组件
- 硬件平台之间有大量相似的传感器/管理逻辑
- 重新实现已验证的功能得不偿失

```text
可复用点分析清单:

Layer 1 - OpenBMC 社区组件 (直接复用):
  □ phosphor-hwmon          — 硬件监控
  □ phosphor-host-ipmid     — IPMI 协议
  □ bmcweb                  — Redfish/WebUI 服务
  □ phosphor-sel-logger     — SEL 管理
  □ phosphor-fan            — 风扇控制策略
  □ phosphor-power          — 电源控制(PGOOD/PSU)
  □ phosphor-software-manager — 固件升级

Layer 2 - ByteBMC 等厂商 BSP (合作复用):
  □ 板级支持包 (BSP): GPIO/I2C/SPI/UART 初始化
  □ 传感器适配层: 针对特定传感器的驱动
  □ CPLD 通信协议: 复用厂商提供的 CPLD 驱动

Layer 3 - 已有项目经验 (知识复用):
  □ 传感器阈值配置表 (温度/电压的告警阈值)
  □ 上电时序定义 (Power Sequence)
  □ LED 状态定义 (UID/Health/Fault)
```

#### 📊 系统指标定义 — 🔴 重中之重的投入 (35%)

**固件级指标的缺失，直接导致硬件可靠性无法保证**。这是四维中最需要投入的。

```text
固件系统指标定义:

[性能指标]
  BMC 启动时间: < 30s (到 Redfish 可用)
  Redfish API 响应: < 500ms (p95)
  SOL 延迟: < 10ms
  KVM 帧率: ≥ 15fps
  传感器采样周期: 主要传感器 1s/次
  WebUI 登录: < 3s

[可靠性指标]
  BMC 无故障运行时间: > 1年 (MTBF)
  固件升级成功率: > 99.9%
  看门狗响应时间: < 5s
  Redfish 并发连接: ≥ 32
  SEL 存储容量: ≥ 512条

[固件资源预算]
  Flash 占用: ≤ 32MB (含备份分区)
  RAM 占用: ≤ 512MB
  CPU 利用率(空闲): < 10%
  CPU 利用率(满载): < 60%

[电源管理指标]
  自身功耗: < 15W (含网口)
  上电时序误差: < 10ms
  电源状态切换: S0->S5 < 10s
  PSU 效率监控精度: ±1%

[安全指标]
  Redfish HTTPS: TLS 1.2+
  固件签名: 必须验证
  WebUI 会话超时: 15min
  登录失败锁定: 5次后 5min 锁定
```

#### 权衡点扩展：OpenBMC/BIOS 十二维决策要点

> **v2.0 新增**

**P3 (标准合规)** — 15% 🔴（该场景前三）

- 固件标准覆盖是硬门槛：Redfish 2020+ / IPMI 2.0 / PLDM / MCTP / DCMI
- 标准合规 = **可互操作**——不合规则无法被数据中心管理平台纳管
- 需求阶段必须产出：**标准覆盖矩阵**（必须/可选/不实现）

**P4 (创新差异化)** — 3%

- 固件层的创新空间极小——差异化来自**硬件适配深度**而不是功能创新
- 可做差异化：液冷传感器驱动深度、自定义诊断脚本、Redfish OEM扩展

**E1 (复用分析)** — 15% 🔴（该场景前三）

- **OpenBMC 社区已有 80%+ 的固件功能**——不做社区已有的东西
- 核心决策：哪些社区组件直接复用？哪些需修改？哪些自研？
- 复用分析步骤：OpenBMC 组件筛查 → 逐项决策 → 差异点清单

**E2 (集成复杂度)** — 5%

- 固件的集成对象是硬件（I2C/GPIO/SPI/CPLD），不是外部系统（接口相对固定）
- 集成复杂度取决于硬件成熟度：原理图定稿越晚，集成复杂度越高

**E3 (可测试性)** — 8%

- 固件测试的特殊性：**缺乏合适的测试环境模拟硬件行为**
- 核心工具：QEMU 模拟器（覆盖率有限）+ 硬件开发板（资源争抢）+ HIL（硬件在环）
- 需求含：「测试硬件资源分配计划」

**E4 (团队能力)** — 5%

- 固件团队需要：嵌入式C/C++ + 硬件知识（I2C/GPIO） + OpenBMC 框架经验
- 最稀缺的能力：**硬件调试经验**——示波器看波形、I2C 总线抓包
- 需求阶段需评估：团队是否有「硬件调试者」

**O2 (安全合规)** — 5%

- 固件安全由硬件信任根决定：TPM 2.0 / Secure Boot / 固件签名
- 需求阶段必须明确：安全启动链（BootROM→BMC→BIOS→OS 每一级的签名验证）

**O3 (可维护性)** — 5%

- 固件升级不能失败：失败=设备变砖
- 核心设计：双镜像启动（A/B Partition）+ 升级回滚 + 恢复模式
- 需求含：固件升级协议（Redfish UpdateService / 本地刷写 / 串口恢复）

**O4 (运营复杂度)** — 5%

- 固件产出是镜像文件，部署由管理平台（如 OCP 管理网关）处理
- 需求含：固件版本管理 + 批量升级 + 灰度发布 + 版本兼容性矩阵

### 6.3 需求分析流程建议

```text
固件需求分析的独特流程:

Step 0 (前置条件): 硬件原理图/Datasheet 必须已有
                    硬件寄存器地址/时序必须已定义

Step 1 - 标准覆盖分析:
  对照 Redfish Schema 2020+、IPMI 2.0、PLDM 标准
  标记: 必须实现 / 可选实现 / 不实现
  输出: 标准覆盖矩阵

Step 2 - 硬件适配分析:
  阅读硬件原理图 -> 整理 GPIO 控制表
  阅读 I2C 总线图 -> 整理 I2C 传感器清单
  阅读 FRU Layout -> 定义 EEPROM 布局
  输出: 硬件适配需求文档

Step 3 - OpenBMC 社区组件筛查:
  逐项检查: 直接复用 / 需修改 / 需自研
  关键: 不做社区已有的东西（除非有差异化理由）

Step 4 - 资源预算:
  Flash 容量计划: rootfs + app + backup
  RAM 预算: 内核 + 服务 + 用户空间
  风扇/PWM 控制策略（功耗预算）

Step 5 - 异常场景walkthrough:
  逐层推演: BMC启动异常 / 升级中断 / 传感器失效 / 看门狗触发
  输出: 异常处理规格
```

## 7. 操作系统 (OS) — 系统软件

### 7.1 场景特征

OS 的需求分析是**最抽象、最结构化**的一类。用户不是「直接交互」而是通过「系统调用 + API」使用。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 抽象接口层 | 用户态→内核态通过syscall | 需求是「接口行为定义」而非「功能列表」 |
| 资源管理 | CPU/内存/IO/中断 | 需求核心是「资源分配策略」 |
| 多任务并发 | 调度/同步/死锁 | 需求含「并发模型/调度策略」 |
| 硬件抽象 | 驱动框架/总线/设备模型 | 需求含「支持的硬件平台」 |
| 安全隔离 | 进程/内存/文件系统权限 | 需求含「安全模型」 |

### 7.2 四维分析

#### 🖥️ UI设计 — 0%

OS 的用户界面是**系统调用接口**和**API**，不是图形界面。需求分析阶段不需要任何UI设计投入。

```text
OS 的"用户界面":
  +-------------------------------------+
  | 用户态应用层                         |
  |  (应用程序/库/工具链)                |
  +------------------+------------------+
                     | 系统调用 (syscall)
  +------------------+------------------+
  | 内核层                              |
  |  VFS / 调度器 / 内存管理 / IPC       |
  +------------------+------------------+
                     | 驱动接口 / 中断
  +------------------+------------------+
  | 硬件层                              |
  +-------------------------------------+
```

#### 🔍 需求深度分析 — 中度 (20%)

OS 的需求分析更关注**「行为规范」而非「业务场景」**。重点在：

```text
OS 需求分析核心关注:

1. 系统调用接口定义:
   - 每个 syscall 的: 原型/参数范围/返回值/错误码
   - POSIX 兼容性: 哪些标准接口必须实现
   - 性能约束: 每次 syscall 开销 ≤ 200 cycles

2. 调度策略设计:
   - 调度算法: CFS/RT/Deadline
   - 优先级范围 + 调度延迟约束
   - 实时性要求: 中断响应延迟 ≤ 10μs

3. 内存管理:
   - 页大小/虚拟地址布局
   - 页面置换策略
   - OOM 行为定义

4. 安全模型:
   - 进程隔离 (MMU)
   - 文件权限 (DAC/MAC)
   - Capabilities 模型
```

#### ♻️ 可复用点分析 — 中度 (20%)

OS 的可复用点分析主要是**「基于哪个基线 /  Fork 哪个社区版本」**：

```text
OS 可复用分析的核心决策:

□ 基线选择:
   - Linux LTS (如 6.6) -> 稳定、生态好
   - RT-Linux -> 实时性要求
   - Zephyr/FreeRTOS -> 嵌入式 RTOS
   - 自研内核 -> 极少场景

□ 社区补丁筛选:
   - 架构支持补丁 (ARM64/RISC-V/x86_64)
   - 调度器增强
   - 安全补丁 (CVE)
   - 硬件特定补丁

□ 配置裁剪:
   - Kconfig 裁剪 -> 去掉不需要的功能
   - 内核模块化 -> 可加载/卸载
   - 减少攻击面
```

#### 📊 系统指标定义 — 🔴 绝对重点 (60%)

**OS 的「需求」本质上就是指标的定义**。OS 不提供具体功能，它提供性能保证。

```text
OS 系统指标定义（这基本就是 OS 的需求规格）:

[性能指标]
  上下文切换延迟: < 2μs
  中断响应延迟: < 10μs (一般) / < 5μs (RT)
  系统调用开销: < 200 cycles / call
  内存分配延迟: < 1μs (平均)
  IPC 延迟 (pipe): < 5μs
  网络协议栈延迟: < 50μs (TCP loopback)

[调度指标]
  调度粒度: 1ms (HZ=1000)
  最大进程数: ≥ 65536
  调度公平性: 同等优先级 ≤ 5% 偏差
  实时任务延迟抖动: < 100μs (p99)

[内存管理指标]
  虚拟地址空间: 48-bit (或 52-bit)
  页面错误处理: < 5μs (major fault)
  内存碎片率: < 10%
  OOM 触发响应: < 100ms

[文件系统指标]
  VFS 操作延迟: < 1μs (内存文件系统)
  最大文件大小: 取决于 FS 类型
  最大文件数: ≥ 4M (典型 ext4)
  并发 I/O: ≥ 100K IOPS

[可靠性指标]
  内核恐慌后恢复: 自动重启 < 30s
  内核内存泄漏检测: 有检测机制
  Watchdog: 支持硬件/软件 watchdog
  日志持久化: pstore / ramoops

[安全指标]
  用户/内核隔离: MMU 必须启用
  KASLR: 必须启用
  Stack Canary: 必须启用
  SELinux/AppArmor: 可选
```

#### 权衡点扩展：OS 十二维决策要点

> **v2.0 新增**

**P3 (标准合规)** — 12%

- OS 标准由 POSIX / LSB / Single UNIX Specification 定义
- 标准合规决定应用兼容性——不达标则已有应用无法运行
- 核心决策：POSIX.1-2008 覆盖度目标（100% / 90% / 80%？）

**P4 (创新差异化)** — 8%

- OS 的创新**不在内核功能，而在调度/内存/IO 策略的差异化**
- 可做方向：RT调度增强（实时性）、NUMA优化（服务器场景）、OOM 行为定制（业务感知）

**E1 (复用分析)** — 8%

- OS 基线选择决定 80% 复用率：Linux LTS 6.6 / RT-Linux / Zephyr / FreeRTOS
- 核心决策：**基线 Fork vs 模块化扩展**——Fork 短期快但长期维护难

**E2 (集成复杂度)** — 3%

- OS 的集成对象是**驱动和硬件平台**（架构支持），不是外部系统
- 集成复杂度取决于架构（x86_64 最成熟、ARM64 中等、RISC-V 高）

**E3 (可测试性)** — 15% 🔴（该场景前三）

- OS 测试最难自动化：需要大量硬件（真实物理机 + 不同外设组合）
- 核心工具：KVM 虚拟机（覆盖有限）+ LTP（Linux Test Project）+ syzkaller（fuzzing）
- 需求含：「测试集群配置 + 回归测试覆盖率目标」

**E4 (团队能力)** — 8%

- OS 内核团队是**所有软件工程中最难招聘的**——Linux 内核贡献者全球仅 ~2000 活跃
- 关键角色：架构移植工程师 + 调度算法专家 + 内存管理专家 + 安全专家

**O2 (安全合规)** — 5%

- OS 安全由内核安全机制决定：SELinux / AppArmor / Seccomp / KASLR / Stack Canary
- 等保 2.0 / 可信计算（TPM）是强制性需求
- 需求含：安全机制选型 + 默认安全策略

**O3 (可维护性)** — 3%

- OS 的内核版本升级是最大的维护挑战——API/ABI 兼容性
- 长期维护策略：LTS 版本 + 厂商 Backport

**O4 (运营复杂度)** — 3%

- OS 运营的核心是：内核热补丁（Livepatch）+ 驱动更新 + 配置更新（避免重启）
- 需求含：热补丁机制 + 无重启更新方案

### 7.3 需求分析流程建议

```text
OS 需求分析是"规格驱动"而非"场景驱动":

Step 1 - 选择基线:
   确定 Linux 版本 / RTOS / 自研
   确定架构: x86_64 / ARM64 / RISC-V

Step 2 - 定义接口规范:
   POSIX 标准覆盖度 -> 对标 POSIX.1-2008
   增加的系统调用 -> 定义原型 + 行为
   不实现的接口 -> 明确标注

Step 3 - 定义性能预算:
   每层允许的延迟预算 -> 从硬件->驱动->内核->syscall
   资源上限 -> 进程/FD/内存/网络连接

Step 4 - 定义安全边界:
   需要什么安全级别? -> 选型 LSM / SELinux
   需要什么启动安全? -> Secure Boot / TPM

Step 5 - 定义裁剪边界:
   去掉不需要的功能 -> Kconfig 裁剪清单
   模块化决策 -> 哪些编译进内核/哪些模块化
```

## 8. 驱动 — 硬件适配层

### 8.1 场景特征

驱动是连接硬件和 OS 的桥梁，核心特征是**硬件规格驱动、极端稳定性要求、内核态运行**。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 硬件Dependent | 驱动行为由硬件规格决定 | 需求 = 硬件 Datasheet 的解读 |
| 内核态运行 | 崩溃即内核恐慌 | 需求含「错误处理/容错」 |
| 并发压力大 | 多核同时访问硬件 | 需求含「锁/同步设计」 |
| 中断上下文 | 必须在极短时间内处理 | 需求含「中断延迟预算」 |
| DMA 操作 | 直接操作物理内存 | 需求含「DMA 一致性模型」 |

### 8.2 四维分析

#### 🖥️ UI设计 — 0%

驱动没有 UI。驱动的「用户」是内核上层模块，通过标准接口（file_operations / net_device_ops / gpu_sched）交互。

#### 🔍 需求深度分析 — 中度 (20%)

驱动的需求深度在于**对硬件 Datasheet 的完整解读**，而不是业务逻辑复杂性。

```text
驱动需求分析的重点:

1. 硬件寄存器映射:
   每个寄存器的地址/偏移/位域定义
   读/写/读-修改-写/清空条件
   时序要求: 两次访问的最小间隔

2. 中断处理设计:
   中断类型: MSI-X / INTx / GPIO
   中断频率: 最大每秒多少次中断
   中断共享: 是否可共享中断线
   Top half / Bottom half 划分

3. DMA 设计:
   DMA 方向: Host->Device / Device->Host / 双向
   DMA 一致性: coherent / streaming
   最大 DMA 大小
   Scatter-Gather List 格式

4. 电源管理:
   支持的 D-State (D0-D3cold)
   唤醒源定义
   省电模式延迟

5. 并发模型:
   多队列支持
   锁粒度设计
   RCU / spinlock / mutex 选型
```

#### ♻️ 可复用点分析 — 🔴 重度投入 (40%)

驱动是所有场景中**可复用点分析投入最大的**。原因是：

1. **内核驱动框架非常成熟** — Linux kernel 有完善的驱动框架
2. **同类硬件接口标准** — PCIe/USB/NVMe 等标准接口驱动逻辑高度相似
3. **已有开源驱动可参考** — 同厂商其他型号/同接口类型

```text
驱动可复用点分析:

Layer 1 - 内核驱动框架 (直接复用):
  □ PCIe 驱动框架: pci_driver / probe / remove / suspend / resume
  □ DMA API: dma_alloc_coherent / dma_map_single / dmaengine
  □ Interrupt: request_irq / threaded_irq / top-half/bottom-half
  □ IOMMU/IOVA: iommu_map / iova_alloc
  □ Power Management: dev_pm_ops / runtime PM

Layer 2 - 开源驱动参考:
  □ 同厂商其他型号驱动 -> 70-80% 可复用
  □ 同接口标准其他厂商驱动 -> 架构参考
  □ 内核主线 (kernel.org) -> 最新最佳实践

Layer 3 - 硬件抽象层 (HAL):
  □ I2C/SMBus 通信 -> i2c 子系统
  □ SPI 通信 -> spi 子系统
  □ GPIO 控制 -> gpio 子系统
  □ MDIO/MDC -> phy 子系统
```

#### 📊 系统指标定义 — 🔴 重度投入 (40%)

```text
驱动系统指标定义:

[性能指标]
  中断处理延迟: < 10μs (top half)
  DMA 传输速率: ≥ 硬件理论带宽的 90%
  IOPS (对于存储驱动): 硬件能力上限
  吞吐量: ≥ 硬件规格的 95%
  latency: 不显著高于硬件测出的原始延迟

[正确性指标]
  Data Integrity: 100%（端到端校验）
  DMA 地址无冲突
  中断丢失率: 0%（MSI-X）
  锁竞争引起的延迟: < 5% 额外

[可靠性指标]
  压力测试: 满负载运行 72h 无异常
  热插拔: 支持 1000 次热插拔循环
  内存泄漏: valgrind/kmemleak 无泄漏
  竞态条件: KCSAN/KASAN 无告警

[资源使用]
  内核内存: < 5MB
  中断占用: ≤ 1 MSI-X vector
  DMA 缓冲区: 硬件规格定义
  Lock contention: < 1% 持锁时间/CPU
```

#### 权衡点扩展：驱动十二维决策要点

> **v2.0 新增**

**P3 (标准合规)** — 12%

- 驱动标准由接口协议定义：PCIe Base Spec / NVMe Spec / USB Spec /内核Driver Model API
- 标准合规 = **可被内核纳管**——不遵守内核驱动模型规范的驱动无法合入主线
- 需求阶段必须明确：目标内核版本 + 兼容的驱动模型接口版本

**P4 (创新差异化)** — 8%

- 驱动的创新体现在：**性能优化技巧**而非功能（零拷贝、多队列、中断合并策略）
- 差异化来源：基于硬件特性的专用优化策略（不是标准框架能提供的）

**E1 (复用分析)** — 20% 🔴（该场景第一）

- 驱动是所有场景中复用率最高的（内核框架 70% + 开源参考 30% = 核心代码 90%+ 复用）
- 核心决策：基于内核哪个版本的驱动框架？(Linux 6.6 / RT 内核等)
- ❌ 常见错误：**在框架上浪费时间**——内核驱动框架已经定义了一切（probe/remove/suspend/resume），你要做的是填写硬件特定代码

**E2 (集成复杂度)** — 5%

- 驱动的集成对象是**单一硬件**（不是多个系统），集成复杂度由硬件寄存器设计决定
- 风险点：硬件Datasheet与真实行为不一致（硬件bug）→ 联调阶段的工作量

**E3 (可测试性)** — 12% 🔴（该场景前三）

- 驱动测试是**破坏性的**——测试可能产生DMA错误/中断风暴/死锁，影响整机
- 核心工具：QEMU 设备模拟 + 硬件开发板 + Kernel Sanitizer (KASAN/KCSAN/KMSAN)
- 需求含：异常注入测试方案（模拟中断丢失/DMA失败/超时场景）

**E4 (团队能力)** — 5%

- 驱动工程师需要：内核态编程 + 硬件寄存器理解 + 并发/锁模型经验
- 最稀缺：**能看懂硬件Datasheet的操作时序和读懂内核锁机制的工程师**

**O2 (安全合规)** — 3%

- 驱动的安全在于：DMA地址校验 + 用户态输入验证 + 权限检查
- 内核社区对驱动的安全审查极其严格（任何用户态触发内核崩溃 = 高危bug）

**O3 (可维护性)** — 3%

- 驱动的维护性取决于与内核版本的兼容性——每次内核API变更可能导致驱动不可用
- 长期策略：主线化（将驱动贡献到kernel.org，由社区维护）

**O4 (运营复杂度)** — 4%

- 驱动的运营是：驱动包更新 + 内核升级兼容性 + 热插拔支持

### 8.3 需求分析流程建议

```text
驱动需求分析的硬性前提: 硬件 Datasheet + 参考驱动

Step 0 - 硬件规格消化:
   精读 Datasheet -> 做寄存器映射表
   理解 DMA 引擎 -> 定义 DMA 传输模型
   理解中断机制 -> 定义中断处理策略

Step 1 - 驱动框架选型:
   基于内核哪个子系统? (PCIe/USB/NVMe/Platform)
   多队列还是单队列？
   Polling 还是 Interrupt？

Step 2 - 开源驱动调研:
   同厂商同类产品参考驱动
   内核主线相关驱动
   预计复用率评估

Step 3 - 性能预算推导:
   硬件极限带宽 -> 驱动目标 (90%+)
   ISR 最大允许延迟 -> 从硬件时序推导
   DMA 缓冲区大小 -> 从吞吐要求推导

Step 4 - 验证方案定义:
   Unit Test: 寄存器读写 / 中断触发
   Integration: 与硬件联调
   Stress: 满负载 72h
   异常注入: 中断丢失 / DMA 错误 / 超时
```

## 9. 编译器 — 工具链

### 9.1 场景特征

编译器的核心特征是**输入输出确定性、形式化程度高、优化策略复杂**。

| 特征 | 描述 | 对需求分析的影响 |
|:-----|:-----|:----------------|
| 输入是编程语言 | 语法/语义严格定义 | 需求基于「语言规范」 |
| 输出是机器码 | 架构指令集严格定义 | 需求基于「ISA 规范」 |
| 优化无上限 | 永远可以更优化 | 需求含「优化优先级和深度」 |
| 自举（Bootstrapping） | 编译器自己编译自己 | 需求含 Bootstrapping 策略 |
| 工具链集成 | 链接器/汇编器/调试器 | 需求含「工具链范围」 |

### 9.2 四维分析

#### 🖥️ UI设计 — 极低 (5%)

- 编译器的 UI 是「命令行界面」— `clang -O2 -march=... source.c -o output`
- 如果有Web IDE 可视化，那是「前端应用」场景不是「编译器」场景
- 需求分析阶段只需要定义命令行参数接口（flags/options）

#### 🔍 需求深度分析 — 🔴 重度投入 (35%)

编译器需求分析的核心不是「功能场景」而是**「语言标准覆盖 + 优化策略定义」**：

```text
编译器需求深度分析:

Layer 1 - 语言标准覆盖:
  支持的语言版本: C17/C23, C++17/C++20, Rust edition
  必须实现的特性 -> 对照标准文档逐条检查
  可选特性 -> 标记暂不支持
  扩展特性 -> 自定义 attribute / builtin

Layer 2 - 目标架构支持:
  指令集覆盖: x86-64-v3 / ARMv8.2-A / RISC-V 64G
  向量指令: AVX-512/SVE/RVV 的支持程度
  扩展指令: FMA/AES/SHA/等对性能关键指令

Layer 3 - 优化策略:
  -O0 / -O1 / -O2 / -O3 各开启哪些 pass
  链接时优化 (LTO) 策略
  配置文件引导优化 (PGO) 策略
  循环展开 / 内联 / 向量化的启发式

Layer 4 - 错误诊断:
  错误信息的格式和内容
  警告级别 (-Werror / -Wall / -Wextra)
  Static Analyzer 的检查范围
```

#### ♻️ 可复用点分析 — 中度 (20%)

编译器开发几乎都是从**已有编译器框架**开始：

```text
编译器可复用分析:

1. 框架层:
   □ LLVM 基础设施 (最成熟): IR / Pass Manager / Backend
   □ GCC 基础设施: Tree / RTL / Backend
   □ MLIR: 多级 IR 框架（适合 AI 编译器）
   □ Cranelift: 轻量级代码生成（WASM/实验）

2. 前端 (Frontend):
   □ Clang (C/C++/ObjC): 可直接复用
   □ rustc 前端: Rust 解析/类型系统
   □ 已有词法/语法解析器: 如果支持类似语法

3. 中间表示 (IR):
   □ LLVM IR: 业界标准
   □ MLIR Dialect: 自定义 + 复用标准 Dialect (TOSA/Linalg/SCF)

4. 后端 (Backend):
   □ LLVM Target: x86/ARM/RISC-V/NVPTX 后端
   □ Instruction Selection: SelectionDAG / GlobalISel
   □ Register Allocation: Greedy / PBQP

5. 优化 Pass:
   □ MLGO (ML-guided optimization): 可复用
   □ -O2/O3 Pass Pipeline: 基本固定
   □ 自定义 Pass: 差异化竞争力来源
```

#### 📊 系统指标定义 — 🔴 重度投入 (40%)

编译器的指标分成**正确性、编译速度、生成代码质量**三个维度：

```text
编译器系统指标定义:

[正确性指标]
  CVE 修复覆盖: 所有已知安全漏洞
  C/C++ 标准符合度: 99%+ (vs Standard Test Suite)
  自举验证: 新版本编译旧版本的结果一致
  Regression Test: 0 regression per PR
  Fuzzing: 持续 fuzz (OSS-Fuzz)

[编译速度指标]
  增量编译: < 1s (单文件改动)
  全量编译 (LLVM): < 1h (全项目)
  LTO 编译: < 2× 普通编译时间
  内存占用: < 8GB (普通项目编译)
  Parse 速度: > 1M lines/s

[生成代码质量指标]
  SPEC CPU 评分: ≥ 同级别编译器 95%
  生成的二进制大小: ≤ GCC 同等优化级别
  优化后代码的运行速度: > 未优化版本 5-10×
  向量化率: 符合预期的 hotspot 全部向量化
  内联决策质量: 减少热路径上的非内联调用

[工具链集成指标]
  调试信息: DWARF 4/5 完整支持
  LTO + DebugInfo 兼容
  Profile-guided optimization: 工作流完整
  LSP 支持: clangd / clang-tidy / clang-format
```

#### 权衡点扩展：编译器十二维决策要点

> **v2.0 新增**

**P3 (标准合规)** — 15% 🔴（该场景前三）

- 编译器的标准就是一切——C17/C23 / C++20/C++23 / LLVM IR / DWARF / Exception Handling ABI
- 不达标=编译结果**无声错误**（最致命：编译通过但生成错误代码）
- 需求阶段必须产出：**语言标准覆盖矩阵**（已实现/部分实现/暂不支持/不实现）

**P4 (创新差异化)** — 10%

- 编译器的差异化在于**优化策略**：自动向量化、内联启发式、循环变换、Profile Guided Optimization
- 可做差异化：AI-guided optimization（MLGO），特定领域的专用Pass

**E1 (复用分析)** — 8%

- 编译器框架复用率极高（LLVM 基础设施 70%+，Clang/GCC 前端可直接复用）
- 核心决策：**Fork LLVM 哪个版本？**——太新不稳定，太旧缺优化
- ❌ 常见错误：低估前端（词法/语法分析）的复杂度

**E2 (集成复杂度)** — 5%

- 编译器的集成对象是**工具链**（汇编器/链接器/调试器），接口标准已成熟
- 集成复杂度中等，主要是ABI一致性（调用约定/异常处理/类型信息格式）

**E3 (可测试性)** — 15% 🔴（该场景前三）

- 编译器测试是所有软件中最依赖**自动化测试套件**的：
  - 语言标准测试（C++ Test Suite ~100万+ 条）
  - 编译正确性（随机差分测试）
  - Fuzzing（OSS-Fuzz 持续运行）
- 需求含：回归测试策略 + 性能基准（SPEC CPU 评分目标）

**E4 (团队能力)** — 10%

- 编译器团队是**技术门槛最高**的——需要：编译原理 + 形式化方法 + 目标架构指令集
- 全球LLVM贡献者仅 ~1000活跃，C++标准委员会 ~300人
- 关键角色：语言前端工程师 + 优化Pass工程师 + 后端（ISel/RA）工程师

**O1 (系统指标)** — 10%

- 编译器指标的三维矛盾：**编译速度 / 生成代码质量 / 编译内存占用**
  - -O0：编译速度优先
  - -O2：平衡
  - -O3 / LTO：生成代码质量优先
- 需求阶段必须定义：每个优化级别对应的这三个指标的优先级

**O2 (安全合规)** — 2%

- 编译器安全核心：生成代码的安全属性（Stack Canary / CFI / ASAN）
- 安全特性由编译选项控制，编译器自身安全风险较低

**O3 (可维护性)** — 2%

- 编译器的维护成本在版本演化——新语言标准/新架构指令集持续加入
- 长期策略：LLVM upstream 跟进 + 定制Pass独立维护

**O4 (运营复杂度)** — 1%

- 编译器运营极简：产出物是二进制文件（可执行文件/库），分发包即可

### 9.3 需求分析流程建议

```text
编译器需求分析是"标准驱动"的:

Step 1 - 确定目标:
   新语言? -> 语言设计 / 语法 / 语义
   新架构? -> ISA 手册 / 指令集 / ABI
   新优化? -> 分析热点 pass / 优化策略

Step 2 - 选择基线:
   Fork LLVM? Fork GCC? 基于 MLIR?
   哪个版本? (LLVM 19.x / GCC 14.x)

Step 3 - 标准覆盖分析:
   对照标准文档 -> 标记: 必须/可选/不实现
   重点关注: 是否有已知兼容问题

Step 4 - 性能基线定义:
   SPEC CPU / Coremark / 应用基准
   编译时间 vs 运行时间的 Tradeoff

Step 5 - 测试策略:
   Test Suite: 语言标准测试 / 回归测试 / fuzzing
   持续集成: 每个 commit 跑完整测试
```

### 10.3 核心洞察

#### 洞察1: 需求深度 ≠ 所有场景都需要

| 场景 | 需求深度的本质 | 深度投入的ROI |
|:-----|:---------------|:-------------:|
| 企业软件 | 业务逻辑深度 | 🔴 极高 — 错就全错 |
| 编译器 | 语言标准 + 优化策略 | 🔴 极高 — 规格决定能力 |
| OpenBMC/BIOS | 硬件适配 + 异常场景 | 🔴 高 — 可靠性的基石 |
| 小程序 | 交互路径的完整性 | 🟡 低 — 迭代比深度更重要 |
| 驱动 | 硬件 Datasheet 解读 | 🟡 中 — 硬件规格已定，无需过度分析 |

**结论**: 企业软件和编译器的需求深度投入最高，小程序最低。需求深度不是「越多越好」，而是「与场景匹配」。

#### 洞察2: 系统指标定义是「隐性需求」

在前端/小程序/企业软件中，系统指标常常被业务方忽略，导致上线后才发现性能问题。而在 OS/驱动/编译器/固件中，**指标本身就是需求**。

```text
场景化建议:
  前端: 需求分析阶段就要定 Web Vitals 目标
  企业软件: 需求含响应时间/并发/可用性 SLA
  固件: 资源预算必须在需求分析阶段确定（Flash/RAM/CPU）
  OS: 延迟预算必须在需求分析阶段分配
  驱动: 性能目标必须在需求分析阶段从硬件规格推导
```

#### 洞察3: 可复用点分析投入与场景的「新写比例」成反比

| 场景 | 新写比例(估) | 可复用分析投入 | 理由 |
|:-----|:-----------:|:-------------:|:------|
| 驱动 | 20-40% | 40% | 内核框架成熟，复用率极高 |
| OpenBMC/BIOS | 30-50% | 30% | OpenBMC 社区组件丰富 |
| 编译器 | 20-60% | 20% | LLVM 基线已提供大部分 |
| 小程序 | 30-60% | 25% | 宿主组件 + 模板 |
| 前端应用 | 40-70% | 20% | 框架 + 组件库 |
| 企业软件 | 60-90% | 20% | 业务逻辑占比高，复用受限 |
| OS | 10-30% | 20% | Linux 基线已极完整 |

**洞察**: 越靠近硬件的软件，可复用率越高（因为框架/社区更成熟）。越靠近业务的软件，新写比例越高（因为业务逻辑是差异化核心）。

#### 洞察4: UI设计投入的反直觉结论

很多人以为「企业软件不需要 UI」，但这不准确：

```text
UI 设计投入的正确理解:

小程序 / 前端 -> UI 是"吸引和留住用户"的核心手段
               -> 投入在: 视觉设计/交互体验/品牌一致性

企业软件 -> UI 是"提升专业用户操作效率"的核心手段
         -> 投入在: 信息密度/导航效率/批量操作/可配置性
         -> 不是"好看"而是"好用"

固件 / OS / 驱动 -> UI 是"接口设计"(API/系统调用/命令行)
                 -> 投入在: 接口一致性/错误返回语义/可发现性
```

### 10.4 一句话总结

| 场景 | 一句话描述需求分析核心 |
|:-----|:----------------------|
| **小程序** | 页面多？交互深？路径长？——都不行。**首屏说清价值、3步完成操作**。 |
| **前端应用** | UI设计 + 5种状态覆盖（Loading/Empty/Error/Success/Partial）+ 性能预算。 |
| **企业软件** | 业务逻辑的状态机 + 数据血缘 + 权限矩阵，**错一个环节就全错**。 |
| **OpenBMC/BIOS** | 80% 在 OpenBMC 社区里，**需求的核心是"哪些要改、哪些要自研、资源预算够吗"**。 |
| **OS** | 需求 = 指标定义。**调度延迟 / 中断响应 / 内存分配开销** — 数字定死就做完了一半。 |
| **驱动** | 硬件 Datasheet 通读 + 已有驱动框架复用分析。**不要在框架上浪费时间**。 |
| **编译器** | 语言标准覆盖度 + 优化策略。**前端的复杂度 > 后端 > 中端**，但差异化在后端。 |

## 11. 实践建议：如何为不同场景制定需求分析流程

### 11.1 通用需求分析时间分配

```text
需求分析阶段的建议时间投入 (占总研发周期):

  小程序:    1-3 天 (UI原型 + 交互评审为主)
  前端应用:  1-2 周 (设计系统 + 原型 + 技术选型)
  企业软件:  2-8 周 (业务流程 + 数据模型 + 权限)
  OpenBMC:   2-4 周 (标准覆盖 + 硬件适配 + 资源预算)
  OS:        2-6 周 (基线选型 + 调度策略 + 指标定义)
  驱动:      1-3 周 (Datasheet 消化 + 框架选型 + 性能预算)
  编译器:    4-12 周 (语言标准分析 + 优化策略 + 基线选型)
```

### 11.2 需求分析阶段必须回答的关键问题

```text
通用问题 (适用所有场景):
  □ 对应的"用户"是谁？(可能是人/其他软件/硬件)
  □ 成功的标准是什么？(可测量的)
  □ 现有的东西能用什么？(复用边界)
  □ 不做会怎样？(优先级验证)

场景化特有问题:
  小程序: 宿主平台是否支持所有所需 API？
  前端: 首屏能在 3s 内加载完吗？
  企业软件: 所有业务流程的状态机画完了吗？
  OpenBMC: Redfish 标准覆盖度是否已知？
  OS: 中断延迟预算是否已经分配给各层？
  驱动: 硬件 Datasheet 中所有寄存器都理解了？
  编译器: 目标语言标准是否已覆盖？
```

### 11.3 需求分析的"危险信号"

| 信号 | 场景 | 问题 |
|:-----|:-----|:------|
| "先做，边做边改" | 企业软件 | 🔴 致命 — 业务流程定错直接返工 |
| "这个需求先记着，后面补" | 固件 | 🔴 致命 — Flash/RAM 满了加不进去 |
| "用最新框架，性能不是问题" | 前端 | 🟡 警告 — 性能预算要早定 |
| "参考 v1 版本需求" | 驱动 | 🔴 致命 — 硬件不同，驱动不同 |
| "先实现功能，优化后面做" | 编译器 | 🔴 致命 — 编译器架构决定了优化上限 |
| "复用率肯定高" | 任何 | 🟡 警告 — 复用分析要定量，不要定性 |
| "规格很清楚了" | OS | 🔴 致命 — OS 规格没有最终版，只有指标 |
