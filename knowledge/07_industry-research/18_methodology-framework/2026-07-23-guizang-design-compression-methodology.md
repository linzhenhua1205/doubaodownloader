## 1. 概述：这不是一个 PPT 模板

### 1.1 表面 vs 实质

| 层次 | 普通人看到的 | 深度分析应看到的 |
|:-----|:-------------|:----------------|
| **最表层** | 一个 PPT 开源模板，10种布局5套主题 | 又一个前端模板 |
| **中间层** | AI × 人协作做 PPT 的接口协议 | 人机协作工作流设计 |
| **最深层** | **十年审美经验的压缩算法** | **领域知识 → 可执行规则体系的蒸馏方法** |

文章作者歸藏（gui-zang）真正做的事：

> **把十年设计行业积累的隐性知识（排版、色彩、字体、节奏）蒸馏为 AI 可以逐条执行的显式规则，打包成一个 SKILL.md + checklist.md 的压缩包。**

这本质上是一个**知识工程（Knowledge Engineering）**项目——与构建专家系统的思路同源，但目标从"让机器替代人"变成了"让机器替人执行规则，人负责判断"。

### 1.2 为什么这对基础设施研发也有启发性

作为服务器 / AI 基础设施从业者，这个案例的启发性不在 PPT 本身，而在**它展示了"经验压缩"的通用方法论**：

| 你的领域 | 他的领域 | 共同的挑战 |
|:---------|:---------|:-----------|
| 十年服务器架构经验 | 十年设计经验 | 隐性知识无法传承 |
| 做竞品分析时凭直觉快速判断 | 做排版时凭直觉知道哪里不对 | 新人无法复用 |
| 如何让 AI 理解"什么叫好的可靠性设计" | 如何让 AI 理解"什么叫好看的排版" | 需要显式化 |

## 2. 核心方法论框架

### 2.1 四层模型

```text
+---------------------------------------------+
|  ① 知识压缩层                                |
|  隐性审美 -> 显式规则 -> 代码化约束             |
|  (十年经验->SKILL.md->checklist.md->CSS变量)     |
+---------------------------------------------+
|  ② 约束美学层                                |
|  少即是多：6个CSS变量、5套主题、分级字体       |
|  (限制选择=保护质量)                          |
+---------------------------------------------+
|  ③ 协作接口层                                |
|  人 × AI 的分工协议：6问前置澄清               |
|  (对齐->生成->检查的三段式管道)                   |
+---------------------------------------------+
|  ④ 节奏控制层                                |
|  时间的结构：hero/non-hero交替、密度调控       |
|  (PDF≠PPT，节奏是幻灯片的第一性原理)            |
+---------------------------------------------+
```

### 2.2 核心原则提炼

| 原则 | 原文表达 | 通用化表达 |
|:-----|:---------|:-----------|
| **约束即解放** | "约束越严，风格越稳。保护美学，比给用户自由更重要。" | 限制选择空间 = 保证输出质量的下限 |
| **分级即秩序** | "衬线→观点，非衬线→信息，等宽→元数据" | 视觉层级编码 = 信息处理成本降低 |
| **前置即效率** | "先给大纲再写代码——拦截了80%的返工" | 对齐成本在前期 vs 返工成本在后期 |
| **密度即节奏** | "连续三页以上相同主题会被判为P0错误" | 变化频率 = 注意力保持的关键 |
| **来源即底气** | "规则本来就不是我的独家，我只是把它copy到了HTML里" | 好的规则不是创造，是发现行业中已验证的模式 |

## 3. 第一层：知识压缩——隐性→显式的蒸馏过程

### 3.1 压缩的四个步骤

这是整个方法论中最有价值的部分——他**如何**把十年经验变成规则：

| 步骤 | 做什么 | 本文示例 | 通用化 |
|:-----|:-------|:---------|:-------|
| **① 识别模式** | 从大量案例中提取重复出现的有效模式 | 杂志排版的100年传统 | 你在大量项目中反复用同一方法时，说明它在底层有结构 |
| **② 把模式翻译为规则** | 用语言描述"什么情况做什么" | "大标题用衬线" | 规则必须可验证（是/否可判定） |
| **③ 把规则代码化** | 让机器可执行 | CSS变量、checklist逐条检查 | 规则必须可编程 |
| **④ 设定边界条件** | 明确什么时候这条规则不适用 | 连续三页同主题=P0错误 | 规则必须附带异常处理 |

### 3.2 他压缩了什么

| 隐性知识 | 显式规则 | 代码化 |
|:---------|:---------|:-------|
| "这个字体看起来不对" | 衬线→观点/非衬线→信息/等宽→元数据 | CSS font-family 三级定义 |
| "这个颜色太刺眼" | 底色 ≠ #FFFFFF, 字色 ≠ #000000 | 6个CSS变量约束 |
| "这页太满了" | hero页和non-hero页必须交替 | checklist 连续性检查 |
| "这张图糊了" | 单张 ≥ 1600px | 图片规则写入README |
| "这个换图太容易出错" | 新图用同名覆盖旧图，HTML不改 | 文件命名约定 |

### 3.3 关键洞察：经验压缩的"保真度"

压缩算法的关键指标是**保真度**——解压后与原始信息的接近程度。

歸藏的做法本质上是一种**有损压缩**：

- **损失了"审美直觉"**——AI 无法理解"为什么这个配色好看"，只能执行"主色=#2B4C6F, 辅色=#D4A76A"
- **保留了"审美底线"**——严格执行规则的结果不会低于某个质量阈值
- **关键判断**：他用6个CSS变量锁定风格的下限，让人类在"5选1"的有限选择中贡献上限

> **对研发的启发**：专家评审凭直觉说"这个方案不行"，背后往往有可提取的规则。把这些规则显式化，就是在压缩你的经验。

## 4. 第二层：约束美学——少即是多的工程化

### 4.1 为什么"不允许自定义 HEX"是最正确的设计决策

表面上这是"限制用户自由"，深层次上这是**保护质量基线**：

| 全自由模式 | 约束模式 |
|:-----------|:---------|
| 用户可选任意颜色 | 用户在5套预设中选择 |
| 结果是不可预测的 | 结果在可控范围内 |
| 80%的PPT配色是灾难 | 最差的结果也是"可接受的" |
| 需要专业审美才能做好 | 不需要审美也能做到70分 |

**核心机制**：约束不是"对用户的惩罚"，而是**对用户决策成本的降低**。

### 4.2 6个CSS变量的架构设计

```css
:root {
  --bg-color: #F5F2ED;      /* 底色：纸白（非纯白） */
  --text-color: #2C2C2C;    /* 字色：墨色（非纯黑） */
  --accent-color: #1A3A5C;  /* 重点色 */
  --font-heading: ...;       /* 标题字体 */
  --font-body: ...;          /* 正文字体 */
  --font-mono: ...;          /* 等宽字体 */
}
```

**架构设计思路**：

- **变量数量 = 可控自由度** — 6个变量，恰好覆盖所有视觉维度（背景/文字/强调/三级字体）
- **变量之间正交** — 改背景不影响文字，改标题字体不影响正文
- **主题 = 变量的预定义组合** — 5套主题 = 5组经过验证的变量赋值

### 4.3 三级字体分工的信息论解读

| 层级 | 字体类型 | 信息论角色 | 认知效率 |
|:-----|:---------|:-----------|:---------|
| **L1 观点** | 衬线 (Serif) | 高信噪比信号——"注意，这是重点" | 读者无需额外判断 |
| **L2 信息** | 非衬线 (Sans-serif) | 低信噪比但高带宽——正文承载 | 不干扰阅读流 |
| **L3 元数据** | 等宽 (Monospace) | 带外信息——页码、章节号、日期 | 视觉上与主内容隔离 |

**为什么有效**：大脑在处理视觉信息时有**前注意加工（pre-attentive processing）**——在意识层面"看"之前，视觉皮层已经完成了特征提取。三种字体的形态差异在前注意阶段就已经完成了分类，读者不需要"想"就知道这是标题还是附注。

> **翻译成研发术语**：这就像 PCIe 物理层用 8b/10b 编码——在数据到达协议层之前，物理层就已经完成了时钟恢复和位对齐。好的设计应该在读者"注意"之前就完成信息分类。

## 5. 第三层：协作接口——人与 AI 的分工协议

### 5.1 6问前置澄清：对齐协议的工程价值

這是整个 Skill 中最具工程思维的部分——**通过6个前置问题，在"开始生成"之前完成80%的对齐**：

| 问题 | 维度 | 为什么重要 | 如果不问 |
|:-----|:-----|:-----------|:---------|
| ① 受众和场景 | 语气/复杂度 | 决定了视觉风格和信息密度 | 学术报告做出发布会风格 |
| ② 分享时长 | 分页数量 | 决定了内容容量和节奏 | 30分钟讲10页太疏，15分钟20页太密 |
| ③ 原始素材 | 内容来源 | 决定了什么内容可用 | AI 编造数据 |
| ④ 图片来源 | 视觉素材 | 决定了图文的配合方式 | 无图空窗或图片放错位置 |
| ⑤ 主题色 | 视觉基调 | 决定了情绪传达 | 悲伤话题用了亮色调 |
| ⑥ 硬约束 | 边界条件 | 决定了不能触碰的红线 | 触犯了禁忌内容 |

**六问的架构设计**：

```text
受众 -> 决定了风格和复杂度
   v
时长 -> 决定了页数和节奏
   v
素材 + 图片 -> 决定了能填充什么内容
   v
主题色 + 约束 -> 决定了视觉边界和红线
```

这是一条**从抽象到具体、从策略到执行**的决策链——先定风格和规模（不可逆），再定内容和资源（可调整），最后定约束（防御性）。

### 5.2 三段式生产管道

```mermaid
+--------------+    +--------------+    +--------------+
|  ① 对齐阶段   | → |  ② 生成阶段   | → |  ③ 检查阶段   |
|  6问澄清      |    |  大纲→代码    |    |  checklist执行 |
|  确认大纲     |    |  HTML骨架    |    |  连续3页同主题? |
|  确认节奏表   |    |              |    |  图片分辨率?   |
+--------------+    +--------------+    +--------------+
```

**关键设计**：检查阶段从"人检查AI"变成了"AI自检 + 人抽查"。

checklist.md 里的规则是**机器可执行的**——"连续三页以上相同主题 = P0 错误"是一个布尔判定，AI 自己就能判断。

### 5.3 图片管理：接口设计思维的体现

| 设计决策 | 工程类比 | 为什么好 |
|:---------|:---------|:---------|
| 页号补零+英文语义 (01-cover.jpg) | RESTful API 的 URL 设计 | 机器可解析、人可理解 |
| 照片用JPG/截图用PNG | 数据类型的选择 | 避免不必要的格式转换 |
| 单张≥1600px | 输入验证 | 保证下游质量 |
| 同名覆盖换图 | 幂等性 | 不改HTML=不改逻辑 |

> **换图不改 HTML 是点睛之笔**——它分离了内容（图片文件）和结构（HTML），与"数据与视图分离"的 MVC 模式同源。

## 6. 第四层：节奏控制——时间的结构设计

### 6.1 Hero/Non-hero 交替

这是文章中最容易被忽略但最重要的设计原则：

```text
页1: Hero (全屏封面)      -> 密集
页2: Non-hero (正文)      -> 稀疏
页3: Non-hero (左文右图)  -> 稀疏
页4: Hero (章节幕封)      -> 密集
页5: Non-hero (数据大字报)-> 稀疏
...
```

**为什么需要交替**：

- 人类在听演讲时的注意力周期约 8-12 分钟
- 在每一页上的注意力停留时间约 30 秒
- 连续密集 → 认知过载 → 注意力流失
- 连续稀疏 → 信息密度不足 → 无聊

Hero/Non-hero 交替的本质是**在时间维度上制造"呼吸感"**——让观众的眼睛和大脑有节奏地紧→松→紧→松。

### 6.2 "连续三页同主题 = P0 错误"

| 等级 | 判定标准 | 含义 |
|:-----|:---------|:-----|
| P0 | 连续3页以上同主题 | 必须修复 |
| P1 | 非 Hero/Non-hero 交替 | 建议修复 |
| P2 | 图片分辨率不足 | 需要注意 |

这也是一条**可机器执行的规则**——AI 不需要理解"什么是好的节奏"，只需要数连续页数。

### 6.3 网格的节奏价值

7:5、6:6、8:4 几套固定网格不仅仅是视觉秩序的问题，更是**节奏的量化工具**：

- 7:5 的网格偏文字密集 → 适合论述
- 6:6 的对半分割 → 适合图文平衡
- 8:4 的不对称分割 → 适合视觉冲击

网格 = 页面的"拍子记号"（time signature），决定了这一页的"节拍"。

        +======================================+
        |    guizang-ppt-skill 的元模式        |
        |                                      |
        |  领域经验 -> 模式识别 -> 规则提炼       |

这个模式完全适用于服务器研发的知识压缩：

| 提案评审 | "这个方案风险太大" | 风险等级矩阵 + 缓解策略 |

#### 映射二：协作接口

| 歸藏的 Skill | 你的领域 |
|:-------------|:---------|
| 6问前置澄清 | 需求评审的强制模板 |
| "先给大纲再写代码" | "先出方案再动手回图" |
| checklist自动执行 | CI/CD 门禁 |
| 换图不改HTML | 用配置驱动替代代码硬编码 |

#### 映射三：节奏控制

| 歸藏的 Skill | 你的领域 |
|:-------------|:---------|
| Hero/Non-hero交替 | 设计审查时的"详→略→详→略"节奏 |
| 连续3页同主题=P0 | 连续3个DR问题未被解决=必须升级 |
| 密度即节奏 | 项目里程碑的"密集期→恢复期→密集期" |

### 7.3 最大的启示

> **经验的价值不在于你积累了多少，而在于你能压缩多少传递给他人。**

在基础设施研发中，专家退休/转岗造成的"知识断层"是组织中最大的隐性成本。歸藏的这套方法给出了一个可复用的解决方案：

1. **把经验写成规则**（SKILL.md）
2. **把规则写成检查清单**（checklist.md）
3. **让AI替人执行检查清单**
4. **人从执行者变成裁判者**

## 8. 批判性评价：这套方法的边界与局限

### 8.1 适用边界

| 适合 | 不适合 |
|:-----|:-------|
| 有明确质量标准的重复性任务 | 需要全新创造性突破的任务 |
| 审美/风格有共识的领域 | 品味高度个人化的领域 |
| 输出格式固定的场景 | 输出格式高度自由的场景 |
| 规则可以显式化的知识 | 极度依赖直觉/身体的技能（游泳/骑车） |

### 8.2 已知局限

**① 规则的质量依赖创始人的提炼能力**

歸藏做了十年设计，能把经验提炼为规则。但大部分人缺少这种**元认知能力**——知道自己知道什么，并能用语言/代码表达出来。

→ **解决方案**：需要一个"知识提取师"角色，或结构化访谈流程。

**② 规则会过时**

设计趋势会变，CSS 标准会升级，当年好看的排版 5 年后可能显得老气。

→ **解决方案**：规则需要版本管理，定期刷新"是否还有效"。

**③ 规则无法覆盖所有例外**

"连续三页同主题 = P0 错误"是一个好规则，但总会有例外——比如对比展示三页时序图。

→ **解决方案**：规则 + 豁免机制（override），人可以为特定场景标记例外。

**④ 规则的"70分效应"**

严格遵守规则的结果稳定在 70 分，但**永远不会出现 95 分的神作**。规则保障的是底线，不是上限。

→ **解决方案**：规则只锁定底线，给有经验的人保留在边界外"违规"的权利。

**⑤ AI 无法理解"为什么"**

AI 可以执行"大标题用衬线"，但不能理解"为什么大标题用衬线让人感觉这是一句该被重视的话"。这意味着当规则不适用时，AI 无法自行判断。

→ **解决方案**：这是目前 AI 能力的天花板——最终判断必须交给人。

## 9. 启示总结

### 9.1 一句话总结

> **guizang-ppt-skill 的意义不是帮人做 PPT，而是展示了一种"如何把十年经验打包成 AI 可执行的规则包"的方法论。**

### 9.2 三个即刻可用的价值提取

| 价值 | 说明 | 你的第一行动 |
|:-----|:-----|:------------|
| **① 约束即解放** | 限制选择空间不是降低自由度，而是保护质量底线 | 为你的团队定义一套"不允许自定义"的标准化模板 |
| **② 对齐前置** | 在开始之前用结构化问题完成对齐，拦截80%返工 | 为需求评审/方案评审设计你的"6问清单" |
| **③ 经验编码** | 把"直觉"变成"规则"，把"规则"变成"可执行的checklist" | 选一个你最擅长的判断，写下3条规则，让AI验证 |
