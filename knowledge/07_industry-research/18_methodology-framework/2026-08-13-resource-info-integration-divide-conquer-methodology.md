## §0 执行摘要

**核心命题**：资源信息"大 + 分散"之所以难整合，根源是**三重熵**（体量熵 O(n²) 关系爆炸、空间熵 多源异构、时间熵 持续漂移），而"分而治之"作为标准答案，其困境在于**分解必然引入接口、协调与一致性成本**——分解降低局部复杂度，却放大系统复杂度。

**方法论**：提出 **五化整合框架（N-L-I-L-V）**：

| 阶段 | 化 | 英文 | 治什么 | 核心产出 |
|:----:|:---|:-----|:-------|:---------|
| 1 | 归一化 | Normalization | 格式/命名/单位 | 统一 Schema + 解析规则 |
| 2 | 分层化 | Layering | 边界/归属 | MECE 层级 + 归属矩阵 |
| 3 | 索引化 | Indexing | 查询/发现 | 集中索引（目录+属性+语义） |
| 4 | 关联化 | Linking | 关系/导航 | 实体 ID 体系 + 显式关系边 |
| 5 | 校验化 | Verification | 可信/一致 | 交叉校验 + 血缘追踪 |

**关键论断**（数据可验证）：
1. n 个分散源的**全量关系空间是 O(n²)**，但通过"内容分散 + 索引集中"可降为 **O(n) 维护 + O(log n) 查询**——这是整合工程的杠杆点
2. 分治悖论可量化：切分把单点复杂度从 O(S) 降到 O(S/k)，但引入 k 个边界，每个边界是 O(1) 接口成本 + O(1) 一致性成本，**总成本 = S/k + 2k**，最优切分数 k* = √(S/2)（§2.1 推导）
3. 校验化是唯一随规模增长**边际成本递增**的环节——必须自动化，否则整合体系在规模越过阈值后崩塌（§8）

**落地判断**：本方法论适用于"资源信息 > 500 条目且 ≥ 3 个分散源"的场景；低于阈值时，直接物理归集更优（§4.3 给出分界线）。

## §1 问题本质：信息整合的三重熵

### 1.1 为什么"大+散"必然难整合（第一性原理）

从第一性原理看，信息整合的难度由三个不可消除的物理事实决定：

1. **组合爆炸**：n 个分散的实体，潜在关系数量是 **n(n-1)/2 = O(n²)**。体量每翻一倍，潜在关系空间翻四倍。人工维护关系必然在 n 超过 ~10² 量级后失效。
2. **异构成本**：不同来源的信息遵循不同 schema（命名、单位、粒度、精度），整合 = 翻译，翻译需要上下文，上下文本身又是信息——**归一的成本随异构度线性增长，随体量超线性增长**。
3. **漂移不可避免**：任何动态系统（生产环境、知识库、代码库）都在持续变更。整合视图与底层事实之间存在**时间差 δ**，δ 越大，视图越不可信，而消除 δ 需要持续同步成本。

这三个事实构成"整合不可能三角"的雏形：**全量、实时、低成本，三者不可兼得**。所有整合方案本质上都是在三角上选点。

### 1.2 三重熵模型：体量熵 × 空间熵 × 时间熵

| 熵类型 | 定义 | 度量指标 | 典型表现 |
|:-------|:-----|:---------|:---------|
| **体量熵** | 实体数量 n 带来的关系复杂度 | n、关系密度、索引规模 | 知识库 2700+ 篇、超节点 200+ 部件/节点 |
| **空间熵** | 来源分散与格式异构程度 | 源数量 m、schema 差异度、单位不一致率 | FRU/BMC/PMC/交换机/CMDB 五源并存 |
| **时间熵** | 变更频率与漂移速度 | 变更率 λ、视图延迟 δ | 拓扑随插拔变化、会话每日新增 |

**关键洞察**：三种熵的治理手段不同——体量熵靠**分层+索引**（空间换时间），空间熵靠**归一+关联**（翻译+建边），时间熵靠**校验+自动化**（检测+同步）。任何单一手段无法同时降三种熵，这解释了为什么"把所有信息扔进一个数据库"从来不是答案。

### 1.3 整合失败的五种典型形态

| # | 失败形态 | 症状 | 根因 |
|:-:|:---------|:-----|:-----|
| 1 | **信息孤岛** | 各源自建 schema，互不引用 | 只做了归一化，没做关联化 |
| 2 | **索引漂移** | 索引指向的文件已改名/移动 | 只做了索引化，没做校验化 |
| 3 | **归属混乱** | 同一实体出现在多处，说法不一致 | 只做了分层化，没定义归属矩阵 |
| 4 | **视图失真** | 整合视图与现场不符 | 只做了关联化，没做校验化 |
| 5 | **维护爆炸** | 每次变更需人工同步多处 | 五化缺校验化自动化，边际成本失控 |

> **经验法则**：五种失败形态中，**形态 5（维护爆炸）是其余四种的最终归宿**——任何缺乏自动校验的整合体系，都会在规模增长中逐步腐化。这与 §8 的核心论断一致。

## §2 分而治之的困境：为何"分治"本身是大问题

### 2.1 分治悖论：分解降低局部复杂度，却放大系统复杂度

"分而治之"（Divide and Conquer）是应对大规模问题的标准答案，但用户敏锐地指出"分而治之是个大问题"——这不是反对分治，而是指出**分治的代价常被低估**。

设总任务规模为 S，切分为 k 片：

```
Single-point complexity: O(S)  ->  O(S/k)      # decreases
Interface complexity:    0     ->  O(k)        # new (each slice needs >= 1 API)
Consistency cost:        0     ->  O(k)        # new (sync/verify between slices)

Total cost T(k) = S/k + 2k
Optimal: dT/dk = -S/k^2 + 2 = 0  ->  k* = sqrt(S/2)
```

**推论**：
1. 切分不是越多越好——**最优切分数 k\* = √(S/2)**。S=1000 时 k\*≈22 片；S=10000 时 k\*≈70 片。超出后，接口与一致性成本反超分解收益。
2. **小任务不应分治**：当 S < 8 时（k\*<2），分治收益为负——直接整体处理更优。这与 §4.3 的"阈值判断"一致。
3. 分治的真正价值不是"减少工作量"，而是**并行化 + 局部自治**（每片可独立演进、独立校验、独立失败），这是工程必须，但必须为它付费。

### 2.2 五种切分错误的代价

| # | 切分错误 | 描述 | 代价 | 示例 |
|:-:|:---------|:-----|:-----|:-----|
| 1 | **维度错选** | 用变更频率切分，实际应对象类型切分 | 跨片耦合，变更需多片联动 | 按"冷热"切知识库，热区又含全部类型 |
| 2 | **边界模糊** | 两片都"觉得"某个实体归自己 | 归属争议、重复建设、双写冲突 | 节点信息同时写入 node/ 和 rack/ 目录 |
| 3 | **跨层引用** | 上层直接描述底层细节 | 底层变更波及上层，破坏隔离 | 机柜描述文件内嵌各部件序列号 |
| 4 | **孤岛自治** | 每片自建 schema 不对外承诺接口 | 无法聚合，索引失效 | 各项目目录格式不统一 |
| 5 | **过度细分** | 切分数远超 k* | 接口/一致性成本爆炸 | 每个 GPU 卡单独建一个目录 |

> **本质**：切分错误 = 把"逻辑边界"错当成"物理边界"，或反之。正确做法是**逻辑分层（可多视图） + 物理归属（唯一主人）**，二者解耦——见 §5。

### 2.3 分治的 CAP 类比：一致性与可分割性的张力

分布式系统 CAP 定理（一致性/可用性/分区容忍不可三者兼得）在信息整合中有精确类比：

| CAP 项 | 信息整合类比 | 取舍示例 |
|:-------|:-------------|:---------|
| **C 一致性** | 各分片视图与底层事实一致（δ≈0） | 每次变更即时同步所有索引 |
| **A 可用性** | 任何分片独立可查、独立可写 | 离线也能查本片、写本片 |
| **P 分片性** | 必须分片（规模使然） | 规模 > 阈值必须分片 |

**结论**：规模一旦越过阈值，**P 不可放弃**，只能在 C 与 A 之间取舍：
- 偏 **C**（强一致）：变更走总线同步，查询永远准 → 代价是写入延迟与系统脆弱
- 偏 **A**（高可用）：每片自治，索引异步重建 → 代价是视图存在 δ 窗口

**工程建议**：信息整合场景**默认偏 A**（异步索引 + 定期校验），因为信息系统的 δ 容忍度远高于交易系统；但**身份与关系数据（ID 映射、归属矩阵）必须偏 C**——这是整合的锚点，不容漂移。

## §3 方法论总纲：五化整合框架（N-L-I-L-V）

### 3.1 框架全景

```
                    +-------------------------------------------------+
                    |         Unified Query View (consumption)        |
                    |   query / discovery / nav / alert / report      |
                    +------------------------+------------------------+
                                             | via index + relation edges
        +--------------+--------------+------+------+--------------+--------------+
        v              v              v             v              v              v
   +---------+   +---------+   +---------+     +---------+    +---------+    +---------+
   | 4 Link  |   | 3 Index |   | 2 Layer |     | 1 Norm  |    | 5 Verif |    |         |
   |  ID+Edges|  |  Dir+Attr|  | MECE    |     | Schema  |    | X-check |    |         |
   +----+----+   +----+----+   +----+----+     +----+----+    +----+----+    +----+----+
        |             |              |              |              |
        +-------------+------+-------+--------------+--------------+
                             v
              +---------------------------------------------+
              |          Distributed Resources (facts)       |
              |   FRU / BMC / PMC / Switch / CMDB / KB       |
              +---------------------------------------------+
```

五化不是串行流水线，而是**自底向上的五层地基**：归一化是基础（没有统一格式，上层全失效），分层化定义边界，索引化提供查询，关联化建立导航，校验化保障可信。上层依赖下层，但**校验化贯穿全部**（每一层变更都触发校验）。

### 3.2 五化之间的关系与执行顺序

| 依赖关系 | 说明 | 违反后果 |
|:---------|:-----|:---------|
| 归一化 ← 分层化 | 先定边界才知道哪些信息要归一到同一 schema | 归一半途而废 |
| 分层化 ← 索引化 | 索引按层级组织，跨层索引必乱 | 索引漂移 |
| 索引化 ← 关联化 | 关系边必须建立在可查询的索引之上 | 关系无处挂载 |
| 全部 ← 校验化 | 校验是质检，没有质检的整合是未完成品 | 腐化无人知 |

**执行顺序建议**：并非严格 1→2→3→4→5。推荐的**两轮走法**：
- **第一轮（快）**：①归一化（最小 schema）→ ②分层化（粗粒度归属）→ ③索引化（目录索引）→ ④关联化（核心 ID）→ ⑤校验化（手工+半自动）
- **第二轮（深）**：逐层加厚——补全 schema、细化层级、加属性索引、建语义索引、全自动校验

> **原则**：先跑通端到端最小闭环（哪怕粗糙），再逐层加厚。一次到位 = 一次性投入爆炸 + 长期不落地。

## §4 第一化：归一化 Normalization（治格式）

### 4.1 归一化的三个层次

| 层次 | 治什么 | 手段 | 示例 |
|:-----|:-------|:-----|:-----|
| **L1 格式归一** | 文件/记录格式 | 统一编码、统一分隔、统一模板 | 全部转 UTF-8 Markdown；CSV 统一列头 |
| **L2 语义归一** | 命名/术语/单位 | 术语表、单位换算、同义词映射 | "GPU"/"显卡"/"加速卡"→ gpu；带宽统一 GB/s |
| **L3 结构归一** | 实体结构/schema | 统一 Schema、必填字段、枚举约束 | 节点信息统一 {id, slot, type, fru_pn, bmc_ip} |

**关键原则**：**归一化只发生在"入口"（ingress），不追溯历史**。已入库的存量数据通过"迁移批次"逐步归一，而不是一次性全量重写——一次性重写 = 高风险 + 高成本 + 低收益（存量数据大多不会被回看）。

### 4.2 Schema 先行 vs Schema 后补

| 策略 | 适用 | 优点 | 风险 |
|:-----|:-----|:-----|:-----|
| **Schema 先行** | 新建系统、可控采集 | 质量高、索引稳 | 过度设计、阻碍快速落地 |
| **Schema 后补** | 存量系统、多源历史数据 | 快速覆盖、兼容真实 | 需持续迁移、初期视图粗糙 |
| **混合（推荐）** | 大多数场景 | 核心字段先行 + 扩展字段后补 | 需明确"核心字段"清单 |

**推荐做法**：定义**最小核心 schema**（10~20 个字段，覆盖身份/位置/状态/来源四类），先跑通；再按消费需求逐批扩展。判断标准：**字段是否被消费？不被消费的字段不进入 schema**（避免为归一而归一）。

### 4.3 归一化成本量化模型

设源数量 m、每源 schema 差异度 d（0~1）、记录数 n：

```
Normalization cost:  ~ m * d * n^0.5    (translation * sample-check)
Physical merge cost: ~ n                (data moving is linear)
```

**分界线判断**（实用经验值）：

| 条件 | 推荐策略 |
|:-----|:---------|
| n < 500 且 m < 3 | **物理归集**（合并到一个库/目录），不做复杂归一 |
| 500 ≤ n ≤ 5000 且 m < 5 | 逻辑归一（Schema + 视图），不搬数据 |
| n > 5000 或 m ≥ 5 | **五化框架全量实施**（内容分散 + 索引集中） |

> **为什么**：n 小时物理归集成本（线性）低于归一化成本（超线性起步）；n 大时物理归集破坏各源自治性，且搬迁本身引入错误。**本知识库（2700+ 篇、多源）明确属于第三档**。

## §5 第二化：分层化 Layering（治边界）

### 5.1 切分维度的五种选择

| 切分维度 | 定义 | 适用 | 反例（何时不用） |
|:---------|:-----|:-----|:-----------------|
| **对象类型** | 按实体类型分（节点/部件/机柜） | 大多数场景，最稳 | 对象类型会随产品演进 |
| **生命周期** | 按状态分（规划/在建/运行/退役） | 运维台账 | 单一生命周期主导时过度切分 |
| **变更频率** | 按冷热分（热数据/温数据/冷数据） | 存储分层 | 作为唯一维度（见 §2.2 #1） |
| **所有权** | 按团队/系统归属分 | 多团队协作 | 所有权变更频繁时 |
| **消费视角** | 按使用方分（研发/运维/财务） | 多角色视图 | 视角过多导致重复存储 |

**核心建议**：**以"对象类型"为主维度，其余为辅助维度**（用索引标签而非物理切分表达）。原因：对象类型是信息最稳定的内在属性，不受组织/时间影响——与 [层级实体建模规范](./2026-07-29-knowledge-engineering-hierarchical-modeling-spec.md) 的"层级隔离"原则一致。

### 5.2 切分四原则：高内聚/低耦合/稳定边界/自治演进

| 原则 | 含义 | 检验方法 |
|:-----|:-----|:---------|
| **高内聚** | 一片内的信息强相关（共同回答同一类问题） | 问："这片信息能否独立回答 80% 的同类问题？" |
| **低耦合** | 片间只通过 ID/索引引用，不内嵌内容 | 检查是否有跨层描述（见 [层级建模 §7 的 10 种违规模式](./2026-07-29-knowledge-engineering-hierarchical-modeling-spec.md)） |
| **稳定边界** | 归属矩阵长期不变 | 三个月内是否有实体跨片迁移 |
| **自治演进** | 每片可独立增删改、独立校验、独立失败 | 单片的变更是否触发其他片的手工联动 |

**归属矩阵**（落地产物）：二维矩阵，行 = 实体类型，列 = 分片，格 = 归属/引用/无关。**每个实体必须且只能有一个"主人"分片（唯一写者）**，其余分片只能引用——这是防双写冲突的关键。

### 5.3 分层自描述：每层只描述自身

- 下层（部件层）只描述部件自身属性，不描述它装在哪个节点
- 上层（机柜层）只描述机柜自身 + 通过 ID 引用下层
- **位置信息属于"关系"而非"属性"**——放在关系图层（§7），由校验化维护

> 违反示例（错误）：`rack-01.md` 内嵌 `node-03 的 GPU-7 序列号是 XXX`。
> 正确做法：`rack-01.md` 写 `包含 node-03`（ID 引用）；node-03 的 FRU 信息在 node-03 自己的文件里；"node-03 位于 rack-01 slot 5" 是关系边，由校验脚本从 BMC/PMC 数据生成。

## §6 第三化：索引化 Indexing（治查询）

### 6.1 内容分散 × 索引集中的核心设计

这是整合工程的**杠杆点**：内容保持分散（各源自治），索引集中（统一查询入口）。

```
Distributed content (facts)        Centralized index (query layer)
+------------+  collect/subscribe  +------------------------------+
| KB source A| ------------------> | Directory index (loc/struct) |
| Material B | ------------------> | Attribute index (fields/tags)|
| Session C  | ------------------> | Semantic index (vector/word) |
| CMDB D     | ------------------> | Relation index (ID->edge)    |
+------------+                    +------------------------------+
      ^                                      |
      +-------------- verify (periodic reconcile) --------------+
```

**为什么可行**：索引的规模是 O(n)（每实体一行），而全量关系空间是 O(n²)。**用 O(n) 的索引维护成本，换取 O(log n) 的查询体验，并绕开 O(n²) 的人工关系维护**——这是整个框架的经济学基础。

### 6.2 两级索引：目录索引 × 属性索引 × 语义索引

| 索引类型 | 结构 | 回答的问题 | 更新频率 |
|:---------|:-----|:-----------|:---------|
| **目录索引** | 层级树（位置→结构） | "XX 在哪" | 变更时 |
| **属性索引** | KV/倒排（字段→值） | "所有 GPU 是 H100 的节点" | 变更时 |
| **语义索引** | 向量/关键词 | "内容上相关的有哪些" | 定期批量 |

**实现建议**：
- 目录索引：目录树 + 每目录 README/index.md（本知识库已实践）
- 属性索引：front-matter 字段 → 批量脚本生成索引表
- 语义索引：embedding + 向量检索（现有 memory_search 已覆盖）

### 6.3 索引漂移防护与重建策略

**索引漂移** = 索引与内容不一致（文件改名、移动、删除未同步）。防护三件套：

1. **变更钩子**：所有写操作走统一入口（脚本/API），入口自动更新索引——本知识库的 `kb-log-append.py`、`kb-global-index.py` 即此模式
2. **定期对账**：定时全量扫描，索引 vs 实际文件 diff，自动修复 + 报告（对应 [知识库健康检查技能](../../../skills/knowledge-health-check/SKILL.md)）
3. **访问时校验**：查询命中后校验目标存在，失效则即时重建（惰性修复）

> **经验**：100% 防漂移不现实，**目标是把漂移检测延迟压到 < 1 个对账周期**，并把修复做成自动化而非人工。

## §7 第四化：关联化 Linking（治关系）

### 7.1 实体 ID 体系：全局唯一标识的设计

**ID 是整合的锚点**——没有稳定 ID，一切关系都是沙滩上建楼。

| ID 设计原则 | 说明 | 反例 |
|:------------|:-----|:-----|
| **全局唯一** | 跨源不冲突 | 两个源都用 "node-03" 指不同对象 |
| **稳定不变** | 一次分配终身不变 | 用 IP 当 ID（IP 会变） |
| **语义可读** | 人可解析（可选，可用元数据补） | 纯随机 UUID 难排查 |
| **可派生** | 可从物理特征推导（可选） | 序列号不可推导，需查表 |

**推荐方案**：**分层 ID = 类型前缀 + 域 + 序号**，如 `node:dc1-rack05-slot03`；身份（PN/SN）由 FRU 固化，位置（slot/rack）是动态属性由 BMC/PMC 解析——**身份与位置分离**（与超节点拓扑方案的"三源交叉校验"一致）。

### 7.2 关系显式化：从隐式引用到显式边

关系的三种形态（按显式程度排序）：

| 形态 | 示例 | 可查询性 | 推荐度 |
|:-----|:-----|:---------|:-------|
| 隐式（文本提及） | 文档里写了"详见 node-03" | 低（需全文检索） | 存量可容忍 |
| 半显式（链接） | Markdown 链接写法 `[node-03](node-03.md)`（示例性写法，非真实文件） | 中（可爬链接图） | 日常维护 |
| **显式（数据边）** | JSON: `{from: rack-01, rel: contains, to: node-03}` | 高（图查询/拓扑图） | **增量必用** |

**策略**：存量靠链接爬取（隐式→半显式），**新增必须写显式边**（半显式→显式）。关系数据集中到一个关系图层（如 `knowledge/` 的索引、超节点拓扑的 JSON Schema），由脚本维护。

### 7.3 关系图层独立维护：内容与关系解耦

- 内容文件描述"是什么"（自身属性）
- 关系文件描述"与谁相连"（边）
- **关系由机制生成，不由人肉维护**：超节点场景中，`contains` 关系由 BMC/PMC 上报自动生成；知识库场景中，引用关系由链接爬取自动生成

> 解耦的好处：改关系不动内容（不产生 diff 噪音）；关系可独立重建（内容不丢）；关系可独立校验（对账更简单）。

## §8 第五化：校验化 Verification（治可信）

### 8.1 三源交叉校验机制

单一来源的信息不可信——**至少两个独立源交叉验证**（对应 [知识库约束体系](./2026-07-29-knowledge-engineering-constraint-system-design-pattern.md) 与 RULE.md 的"素材批判性使用"）。

以超节点节点定位为例（三源交叉）：

| 事实 | 源 A | 源 B | 源 C | 一致 → 可信 |
|:-----|:-----|:-----|:-----|:------------|
| node 在哪个 slot | BMC strap 读取 | 交换机 LLDP | PMC 台账 | 三源一致 |
| node 的 IP | BMC DHCP option82 | MAC 规划表 | PMC 台账 | 两源一致即可 |
| 部件序列号 | FRU EEPROM | BMC 传感器 | 出厂台账 | 三源一致 |

**判定规则**：核心身份（PN/SN）要求三源一致；动态属性（位置/IP）两源一致即可；不一致时**以物理层为准**（strap > LLDP > 台账），并告警人工介入。

### 8.2 血缘追踪：数据从哪来、被谁改

每个整合后的字段记录：`{source, captured_at, transform, confidence}`。

| 血缘要素 | 内容 | 用途 |
|:---------|:-----|:-----|
| source | 原始来源（FRU/BMC/人工录入） | 争议时回溯 |
| captured_at | 采集时间戳 | 判断时效（δ 评估） |
| transform | 经历了什么转换 | 复现计算 |
| confidence | 置信度（高=三源一致/低=单源） | 消费时降权 |

**实现**：轻量级即可——在索引/关系文件中保留 `来源+时间` 字段；无需完整 Data Lineage 系统。**目的不是审计，是让"不可信信息"可被识别和降权**。

### 8.3 校验的自动化与告警

**为什么必须自动化**：校验成本随规模**线性增长**（每实体校验一次），是五化中唯一无法靠"规模经济"摊薄的环节——只能靠自动化摊薄人力。

| 校验类型 | 频率 | 手段 | 告警 |
|:---------|:-----|:-----|:-----|
| 格式校验 | 每次写入 | 脚本（lint/validator） | 写入即拦截 |
| 一致性校验 | 每日 | 对账脚本（diff 三源） | 不一致 → 工单 |
| 完整性校验 | 每周 | 全量扫描（缺字段/缺实体） | 缺口报告 |
| 血缘时效校验 | 每月 | 检查 captured_at 过期 | 过期降权 |

> **与知识库对齐**：本知识库已有 [健康检查技能](../../../skills/knowledge-health-check/SKILL.md)（完整性/链接/格式）+ [log 格式化技能](../../../skills/log-reformatter/SKILL.md)，即校验化的落地实例。

## §9 落地路线图：从现状到统一可查

### 9.1 六步实施法

```
Step1 Inventory  -> Step2 Boundaries -> Step3 Normalize  -> Step4 Index
(inventory)         (ownership mat)     (min schema)        (dir + attr)
                                        |
Step6 Deepen      <- Step5 Verify loop <- Step4.5 ID system
(iterate)           (reconcile+alert)   (anchor first)
```

| 步骤 | 输入 | 输出 | 周期（参考） |
|:-----|:-----|:-----|:-------------|
| 1 盘点 | 各源目录/接口 | 资源清单（n/m/d 三项度量） | 0.5~1 周 |
| 2 定界 | 资源清单 | 归属矩阵 + 层级图 | 0.5 周 |
| 3 归一 | 归属矩阵 | 最小 Schema + 解析脚本 | 1~2 周 |
| 4 建索引 | 归一后数据 | 目录索引 + 属性索引 | 1 周 |
| 5 校验闭环 | 索引 + 各源 | 对账脚本 + 告警 | 1 周 |
| 6 迭代加厚 | 消费需求 | 扩展 schema/语义索引/血缘 | 持续 |

> **总投入参考**：中等规模（n≈3000, m≈5）约 **4~6 人周** 跑通第一轮闭环；此后维护约 0.2~0.5 人周/月（若校验自动化到位）。

### 9.2 每步的输入输出与验收标准

| 步骤 | 验收标准（可验证） |
|:-----|:-------------------|
| 1 盘点 | 资源清单覆盖全部已知源，n/m/d 有数值 |
| 2 定界 | 每个实体有且仅有一个主人分片（归属矩阵无空行/无多主） |
| 3 归一 | 新数据 100% 通过格式校验；核心字段 95%+ 有值 |
| 4 建索引 | 抽查 20 条索引 → 目标实体 100% 可达 |
| 5 校验闭环 | 连续 2 周对账零误报；不一致 24h 内告警 |
| 6 迭代加厚 | 新增消费需求 80% 可在已有框架内满足 |

### 9.3 投入产出量化估算

**不做整合的隐性成本**（超节点 1000 节点规模参考）：
- 人工排查拓扑：每起故障定位 0.5~2 人时 × 年均 50 起 ≈ **25~100 人时/年**
- 信息不一致导致的重复采购/错配：年均 1~3 起 × 单起 5~20 万 ≈ **5~60 万/年**
- 新人上手成本：分散文档学习 2~4 周 vs 整合后 0.5 周

**做了整合的投入**：4~6 人周一次性 + 维护自动化后趋零。

> **结论**：规模越大，整合 ROI 越高；规模越小，越不该整合（§4.3）。**关键不是"要不要整合"，而是"在哪个规模点、用什么深度整合"**。

## §11 统一行动口诀与检查清单

### 行动口诀（五句话记忆）

1. **先判档，再动手**：n<500 直接归集，n>5000 才上全框架
2. **身份位置分离**：PN/SN 固化，slot/IP 动态解析
3. **每实体一个主人**：归属矩阵唯一写者，防双写冲突
4. **内容分散，索引集中**：O(n) 维护换 O(log n) 查询
5. **校验必须自动化**：不自动化的校验会随规模崩塌

### 落地检查清单

- [ ] 资源清单已建立，n/m/d 三项有数值
- [ ] 归属矩阵完成，每个实体唯一主人
- [ ] 最小 Schema 已定义并通过格式校验
- [ ] 全局 ID 体系已建立（身份位置分离）
- [ ] 索引三层（目录/属性/语义）至少前两层可用
- [ ] 关系图层独立，新增数据写显式边
- [ ] 校验三件套（写入拦截/每日对账/定期全扫）就位
- [ ] 血缘字段（source/captured_at）已写入核心数据
- [ ] 消费端有统一查询入口（而非逐源查询）
- [ ] 迭代加厚机制（消费需求 → schema 扩展）已定义

### 三句话总结

> **整合的本质不是"把信息搬到一起"，而是"建立可查询的统一视图"**——内容保持分散，索引/关系/校验集中，以 O(n) 的维护成本绕开 O(n²) 的人工关系维护。
>
> **分而治之不是万能药**：切分数存在最优值 k\*=√(S/2)，切分维度以对象类型为主，边界用归属矩阵固化。
>
> **规模越大越要校验自动化**——五化中唯一边际成本递增的环节，是整合体系长期不腐化的生死线。
