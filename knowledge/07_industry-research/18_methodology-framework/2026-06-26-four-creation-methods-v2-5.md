## 1. 第一部分：问题空间——为什么需要「创造手法」？

### 1.1 核心命题

**你面对一个「还不存在的东西」，怎么把它造出来？**

历史上对这个问题的回答同样正确但相互矛盾：

- **从零构建**：像 SQL 数据库、Transformer 架构——这是唯一路径，没有前人可抄
- **套用模板**：像 Spring Boot、Rails——99% 的业务系统都是这样
- **抄个样例**：像第一个 Kubernetes 集群、新手写的第一个 Python 脚本
- **共享演化**：像 Linux 内核、Git 协作——多人维护一个共享基础

这四种回答看似是「谁更聪明/谁更偷懒」的等级比较。**本框架的核心主张是**：它们不是等级，而是**同一创造问题在不同约束下的四种解**。每种手法解决了特定场景，同时产生了独有的代价。

**⚠️ 一个诚实的预先声明**：这个框架是**经验分类 + 事后拟合**的产物，不是从第一性原理推导出来的数学结论。它的价值在于：提供一套结构化的分析语言，让你能更清晰地描述和比较不同的创造方式。它做不到的是：预测一个新创造活动该用什么手法，或者证明「只有四种」是必然的。本文件会全程标注哪些是类比、哪些是经验观察、哪些是真正可推导的。

### 1.2 创造的根本约束

所有创造活动面临三个根本约束：

| 约束 | 含义 | 手法一 | 手法二 | 手法三 | 手法四 |
|:-----|:-----|:-------|:-------|:-------|:-------|
| **时间** | 投入多少时间能交付 | 极多 | 中等 | 极少 | 中等 |
| **认知** | 需要理解多深才能做 | 极深（原理级） | 中等（扩展点级） | 极浅（照做级） | 中等（共享边界级） |
| **风险** | 出错概率和影响范围 | 极高（每一步未知） | 中等（框架限制范围） | 极低（路径已验证） | 中等（冲突和漂移） |

**三个核心观察**（而非定理）：

1. 没有手法在所有维度上占优——时间短则认知浅或风险高，认知深则时间长；
2. 这三种约束可以看作同一个量（不确定性）在不同视角上的投影——但**这只是观察框架，不是可量化的等式**；
3. 真正的高手是能在不同场景下**灵活切换**的人——此断言是经验归纳，无实验验证。

> **P1**（经验原则——非演绎结论）：创造手法的本质不是「聪明程度」，而是**对时间·认知·风险三角的权衡**。没有手法在所有维度上最优。

### 1.3 手法的两轴定位

为缓解「四种手法看起来像等级」的问题，本版引入一个**2×2矩阵**作为显式定位框架（而非线性序）：

```text
                 观摩广度（借鉴了多少外部知识）
                低 <-------------> 高
           +------------------------+
     固定  |                        |
          |    手法一                |   手法三
    编码  |  （从零构建）           |  （样例抄袭）
    策略  |    低借鉴+高原创         |   高借鉴+低原创
          |                        |
    （上  |                        |
     层   |    手法二                |   手法四
    规    |  （模板微调）           |  （共享后COW）
    定）  |    中借鉴+中原创         |   高借鉴+中原创
          |                        |
    自适应  +------------------------+
```

**两个轴的解释**：

- **x轴—观摩广度**：创造了多少「先例知识」被借鉴。手法一最少（靠原理推导），手法三/四最多（大量借鉴）
- **y轴—编码策略**：上端是**固定编码**（手法一自己发明所有符号；手法三沿用源系统所有符号不变）；下端是**自适应编码**（手法二在模板扩展点定制；手法四在共享基础上分叉）

**⚠️ 重要说明**：

1. 这两个轴是**事后划分**——即我们已经知道四种手法存在后，找到了两个维度去区分它们。**这不是「从两轴推出手法数量为4」的推导**。要严格推导4，需要证明每个轴上只有两个取值（而非连续值），且两轴正交——这两个条件在现实中都不成立；
2. 两轴定位与线性序不矛盾——沿对角线方向（左上→右下）确实存在「控制力递减、复用效率递增」的趋势，但**这不是强制方向**，手法四在某些场景下比手法三需要更多控制力（例如管理合并冲突）；
3. 结论：四种手法是**经验上有效的分类**，背后的维度是真实但连续的。**承认它是经验分类，反而比宣称「第一性原理推导」更诚实、更稳固**。

## 2. 第二部分：理论核心——四手法的定义与基数论证

### 2.1 定义

| 手法 | 定义 | 本质操作 | 产出特征 | 认知前提 | 典型标本 |
|:-----|:-----|:---------|:---------|:---------|:---------|
| **手法一：裸构建** | 不依赖任何现成参考，从基本原理出发独立构建完整方案 | 发明 | 原创、独特、无依赖 | 深刻理解底层原理 | SQL (1974)、Transformer (2017) |
| **手法二：模板微调** | 以成熟框架/模板为骨架，在预留扩展点做定制 | 适配 | 标准骨架+定制内容 | 理解模板的架构和扩展点 | 99% Spring Boot 应用 |
| **手法三：样例抄袭** | 找到一个或多个相似的成功案例，完整模仿 | 复制 | 非原创、高度雷同 | 不需要理解原理 | 新手写的 CRUD API |
| **手法四：共享后COW** | 多人共享同一基础版本，修改时创建私有副本 | 分叉+合并 | 差异化演化、有共享基础 | 管理共享边界和分叉时机 | Linux 内核、Git 仓库 |

### 2.2 基本原则（缩减版）

> **M1**（经验分类）：四种手法是**同一创造活动在观摩广度×编码策略两轴上的四种经验投影**。数量为4是经验归纳，非数学推导。参见1.3的诚实声明。

> **M2**（手法选择）：选择手法 = 选择约束。手法一选择「自由+高负荷」，手法三选择「受限+低负荷」。**这是描述性规律，不是规范判断**。

> **M3**（手法混合）：真实产品不会只用一种手法。iPhone 的多点触控=手法一，CPU（ARM 架构）=手法四，iOS=手法二，屏幕 UI 元素=手法三。混合本身不意味着高级或低级。

> **M4**（手法变迁的观察，非定律）：经验上，同一系统随成熟度提升，主导手法会从一/三向二/四迁移（从独创或抄袭走向模板化或共享）。但**这是系统成熟度的指标，不是进化必然**——许多系统在手法三上稳定运行数十年（如传统 COBOL 系统）。

### 2.3 MECE边界诚实声明

本框架的「MECE」声明需要诚实降级：

1. **手法二 vs 手法四的重叠**：模板（手法二）和共享基础（手法四）的边界模糊。Git（文中的手法四标本）同时也是版本控制的「模板/工作流框架」（手法二）。一个标本落入两格，说明 MECE 不干净——**更准确的描述是「手法二/四构成一个连续区」，划分点是「改动能回流修改共享基础吗」**，但这不是干净的非此即彼。

2. **手法一 vs 手法二的边界**：什么算「从零构建」？手写 SQL 解析器是手法一，但「借鉴了 Codd 的关系模型论文」算不算借鉴？如果算，那手法一也有「抄袭」成分。**严格来说，没有任何创造是纯手法一的**——所有创造都站在前人肩膀上。手法一描述的是一个**程度**（很少借鉴），不是**种类**。

3. **手法三 vs 手法四的边界**：「抄一个开源项目不改」是手法三，「fork 后持续改」是手法四。但「抄了改了两个文件然后不再碰」应该算哪个？边界在「是否建立了共享-分叉的持续性关系」。

**结论**：四种手法是**原型分类（prototype categorization）** 而非**经典分类（classical categorization）**——边界模糊是正常的，工具在应用时看到的是「更像哪个」而不是「就是哪个」。承认这一点比坚持 MECE 更站得住。

### 2.4 设计模式对照矩阵（简化）

手法与设计模式不是一一对应。一种手法对应多种模式，同一模式在多种手法中扮演不同角色：

| 手法 | 最密切模式 | 说明 |
|:-----|:----------|:------|
| **手法一** | (模式的前提而非模式本身) | Abstract Factory, Builder, Singleton——但这些是定义抽象体系本身，不是「复用已有架构」 |
| **手法二** | **Template Method** | 使用者在模板预留的钩子点中定制。Strategy/Decorator/Adapter 也匹配 |
| **手法三** | **Prototype** | 复制者——复制已知成功路径。Memento 用于保存状态以便恢复（允许反悔） |
| **手法四** | **Flyweight** | 共享不可变状态以节省资源。Proxy/Composite 也匹配 |

> **D1**（观察而非推导）：设计模式不是创造手法的「元理论」，而是手法二/四在软件工程中的**具体制度体现**。绝大部分 GoF 模式解决的问题是「已有架构下如何高效复用」，而非「如何创造全新架构」。

## 3. 第三部分：双透镜——创造的信息视角与控制视角（类比声明）

> **核心命题**：信息论与控制论的概念可以作为理解四种手法的**启发式类比（heuristic analogies）**，但不是数学证明。本部分所有带「>」引用的原理，除非明确标注「可推导」，都应理解为**借用理论概念所做的类比分析**，而非将创造问题直接还原为信息论/控制论定理。

### 3.1 信息论视角：创造中的不确定性处理（类比）

#### 3.1.1 熵的概念借用

Shannon 把信息定义为「不确定性的消除」。创造一个新东西的过程，也可以看作把无限可能性空间压缩为确定产物的过程。

| 手法 | 不确定性（熵）的承担者 | 熵减方式 |
|:-----|:----------------------|:---------|
| 手法一 | 作者本人 | 逐比特手工消除——每一步都可能走错 |
| 手法二 | 框架+作者 | 框架消除骨架不确定性，作者消除扩展点不确定性 |
| 手法三 | 样例原作者 | 直接搬运已被消除的不确定性 |
| 手法四 | 平台+社区 | 共享层消除公共不确定性，分叉消除私有不确定性 |

> **IF1**（启发式类比——⚠️非热力学定律）：创造的实质可以理解为**把不确定性从「产物」转移到某个承担者**。手法一让作者承担全部不确定性，手法四把公共部分托管给平台。**「不确定性只能转移不能消灭」是借用热力学第二定律的措辞，在信息论中并不严格成立**——Shannon 熵可以通过接收信息而降低（这正是通信的意义）。本条应理解为隐喻而非定理。

> **IF2**（可观测的命名现象而非定理）：给概念命名可以看作一种压缩编码。不同手法下的命名特征不同：
>
> - 手法一：自命名——没有参考系，从零设计一套符号（高负荷低共识）
> - 手法二：沿用框架命名——压缩比被社区优化，但受限于框架词汇表
> - 手法三：映射命名——搬运源系统命名，零编码成本但跨域可能失真
> - 手法四：协议命名——`interface Reader { read() }` 是跨场景元编码，压缩比最高但抽象成本也最高

#### 3.1.2 源编码与信道编码的比喻

信息论中有两个奠基性定理，可以用作理解命名与跨域的比喻，但**应视为启发式类比而非证明**：

| 信息论定理 | 创造学类比 | ⚠️ 类比限制 |
|:-----------|:----------|:-------------|
| **香农源编码定理**：无损压缩的平均码长≥信息熵H | 命名再精妙，也不能把知识压缩到低于其「知识熵」 | 源编码定理要求随机源有定义好的概率分布。**系统知识的「概率分布」从未被定义**，因此「熵下界」是修辞而非数学断言 |
| **香农信道编码定理**：有噪信道存在可达容量C，R<C即可可靠传输 | 跨域可靠传输需要冗余，跨域代价的下界由域间「噪声」决定 | 信道编码定理讲的是容量内可达可靠传输，**并非「跨域必付冗余税」的软件意义下界**。把「认知代价=冗余」是修辞映射 |

> **IF3**（启发式类比，⚠️非下界证明）：第八部分的跨域代价（时间/空间/关卡/认知）可以从类比上对应信息论信道的四类损耗。**但这是比喻，不是推导**——软件系统中的「带宽」和「信噪比」没有物理测量单位。

#### 3.1.3 可解释性的一种比喻

> **IF4**（启发式比喻，⚠️非公式）：可以比喻性地把一个系统的「可解释性」视为**观察者从系统行为中提取因果信号的能力**。手法一因果链最短最透明（比喻为高信噪比），手法三多源拼接推理链混乱（比喻为低信噪比）。**这不是 Shannon 信噪比的实际应用**——软件系统的「噪声」不是高斯白噪声，不可解释性也远不只信噪比问题。

### 3.2 控制论视角：创造中的反馈与调节（类比）

#### 3.2.1 必要多样性定律的借用

Ashby 的必要多样性定律说：一个控制者要有效控制系统，自身的状态数必须不少于被控系统。

> **CY1**（启发式映射，⚠️非直接应用）：这个定律可以用作理解「为什么手法一认知负荷最高」的比喻——手法一要求作者内化全部「多样性」（系统的所有可能状态），手法四把多样性分散托管给平台/社区。**但 Ashby 定律在数学上讲的是**控制可能性 **，不是认知负荷**。按严格定义，分布式控制器（手法四）的总多样性更高=控制能力更强。材料把「协调成本」当缺点，但并未调和与「控制更强」的推论之间的关系（这是一个未解决的理论张力）。

#### 3.2.2 反馈回路架构

| 手法 | 反馈特征 | 比喻 |
|:-----|:---------|:------|
| 手法一 | 紧耦合直连——随时感知每一步后果 | 闭环 |
| 手法二 | 框架托管回路——标准反馈通道 | 半闭环 |
| 手法三 | 延迟/间接——靠样例反馈，常滞后 | 接近开环 |
| 手法四 | 分布式可观测回路——平台聚合反馈 | 分布式闭环 |

> **CY2**（启发式观察）：手法越是开环（手法三照搬不修正），越依赖样例的初始正确性。**但「开环/闭环」的二分在此处不干净**——抄样例失败时你会得到反馈（它崩了），只是不在抄的过程中得。开环/闭环是反馈**时机**问题，不是干净二分。

#### 3.2.3 稳态托管

> **CY3**（可观测的现象）：手法四的本质特征之一是**把维持系统属性的稳态控制从个体托管给平台**。基础设施层负责安全/可靠/可观测，业务层负责功能。这是经验观察，不是控制论定理的结果。

#### 3.2.4 良好调节器定理——手法四的双面性（未解张力，本版显式化）

Conant-Ashby 良好调节器定理：每个好的调节器，必须是它所调节系统的一个模型。

这对四种手法的映射是直观的：

- 手法一：作者脑中必须有完整系统模型（最高建模负担）
- 手法二：框架内置了模型，作者只建模扩展点
- 手法三：样例就是模型，作者几乎不建模
- 手法四：模型被分布式地编码在平台/社区中，无人持有完整模型

**⚠️ 这里有一个未解决的理论张力，本版必须显式化**：

- **CY4 （稳态托管）** ：手法四把稳态控制托管给平台 → 平台成为**好的局部调节器**（在基础设施域内）
- **CY5 （全局盲区）** ：手法四无人持有全局模型 → 按 Conant-Ashby 定理，**它不是全局的好调节器**

**化解建议（而非化解结论）** ：
手法四是**局部好调节器 + 全局非好调节器**。它在基础设施层（资源调度、安全、可观测性等）提供了强大的稳态控制，但在业务层（领域逻辑、长期演化方向）无人持有完整模型。这不是「缺点与优点并存」的模糊陈述，而是一个**结构性张力的数学根源**——分布式系统无法同时满足「局部自治」和「全局可控」。

这个张力的工程后果是：手法四系统的全局治理（架构治理、长期路线规划）**必须额外设计**，不能自然涌现。这正是 Kubernetes 社区需要 SIG Architecture、KEP 流程、TAG Review 的原因——**它们是为了对抗手法四的「全局盲区」而人工构造的模型持有机制**。

> **CY4**（可观测的趋势）：手法四的本质特征之一是**把维持局部系统属性的稳态控制从个体托管给平台**。
>
> **CY5**（结构性后果）：但按 Conant-Ashby 定理的类比，**无人持有全局模型的系统不是全局好调节器**。手法四产生「全局盲区」不是可以随手修复的 bug，而是**分布式控制架构的结构性局限**。解法是人工构造全局模型持有机制（架构评审、路线图、社区治理），而非期望自然涌现。

### 3.3 双透镜统一（诚实版）

信息论和控制论提供了两套启发式语言：

```text
信息论（熵减的比喻）         控制论（反馈的比喻）
   |                            |
   创造 ≈ 消除不确定性    <-->   创造 ≈ 建立可控反馈
   |                            |
   命名 ≈ 压缩编码             绑定 ≈ 反馈通道建立
   跨域代价 ≈ 信道限制         稳态 ≈ 基础设施托管
```

> **IF5**（统一是修辞性的）：信息论的「熵」与控制论的「多样性」在比喻层面上是同一事物的两面。但这不是数学等价——一把椅子可以既是棕色的又是木头的，「棕色」和「木头」描述的是不同属性。同样，信息论和控制论描述的是创造活动的**不同侧面**，它们的统一是分析语言的统一，不是对象的统一。

## 4. 第四部分：五维横切透镜——命名·绑定·核心·事件·系统属性

> **核心命题**：四种手法不仅是创造方式的差异，还可以从五个侧面横切透视。每个侧面揭示了手法之间更隐蔽的差异。**这部分的价值在于提供了五个独立可用的分析透镜，即使「四种手法」的分类被全部否定，这五个透镜依然独立有效。**

### 4.1 命名

| 手法 | 命名方式 | 认知负荷 | 典型 |
|:-----|:---------|:---------|:-----|
| 手法一 | 自命名——发明符号系统 | 极高——没参考系 | 变量 a/b/c，自定义函数 |
| 手法二 | 框架命名——沿用上层约定 | 低——约定俗成 | DAO/Service/Controller |
| 手法三 | 映射命名——保持源系统语义 | 中——要找到对应关系 | 抄 BloomFilter 就叫 BloomFilter |
| 手法四 | 抽象命名——消除场景依赖 | 中高——命名通用概念 | `interface Reader { read() }` |

> **N1**（可观察现象）：命名是**系统知识的压缩**（比喻意义上的）。命名体系的演化方向是从「个人编码」（手法一）走向「协议编码」（手法四）。

### 4.2 绑定

每个绑定关系由 `[源主体] —⟨绑定媒介⟩→ [目标主体]` 组成：

| 手法 | 绑定方式 | 绑定时机 | 绑定强度 |
|:-----|:---------|:---------|:---------|
| 手法一 | 原生绑定 | 编译期 | 硬绑定——不可变 |
| 手法二 | 框架绑定 | 配置期 | 软绑定——可配置 |
| 手法三 | 适配绑定 | 组装期 | 中间绑定——需适配器 |
| 手法四 | 协议绑定 | 运行时 | 松绑定——动态协商 |

> **B1**（可观察现象）：手法越高，绑定媒介越显性化、可干预、可替换。编译期绑定最稳定但最不灵活，运行时绑定最灵活但需要运行时开销。**没有一种绑定模式在所有场景下最优**。

### 4.3 核心与修饰

**核心** = 系统中**移除后就不再是它自己**的部分。**修饰** = 可独立添加/移除的部分。

随着手法从一到四，核心从具体实现迁移到抽象机制：

- 手法一：核心 = 我写的代码 → 写核心
- 手法二：核心 = 模板定义的骨架 → 在核心上写修饰
- 手法三：核心 = 借来的模块集合 → 拼核心+写修饰
- 手法四：核心 = 抽象的协议/平台层 → 重新定义核心边界

> **C1**（可操作定义）：核心界定不是理论问题而是**实践问题**——把核心部分逐行删除，看系统还剩下什么。能删的就是修饰，删了就不再是自己的就是核心。
>
> **C2**（常见模式）：把修饰混入核心是设计失灵的常见信号。修复方式：**将修饰从核心中抽离**，让核心只保留不可简化的本质逻辑。

### 4.4 事件

事件是系统在时间维度上的激活标记。在控制论类比中，事件≈反馈触发器。

事件模式的演化趋势：

```text
手法一：事件是函数调用 -> 同步，紧耦合
手法二：事件是框架回调 -> 模板预留点，可控
手法三：事件是总线广播 -> 异步通道，适配层统一
手法四：事件是声明式流 -> 事件网格，标准化契约
```

> **E1**（设计选择而非自然规律）：需要强一致性+即时反馈→偏向函数调用（手法一/二方向）；需要弹性伸缩+解耦演化→偏向事件驱动（手法三/四方向）。**两种模型不可互相替代**，这是工程事实，不是理论推导。

### 4.5 系统属性

| 属性 | 手法一 | 手法二 | 手法三 | 手法四 |
|:-----|:-------|:-------|:-------|:-------|
| **性能** | 最高 | 中等 | 中等偏低 | 中等（协议开销） |
| **安全** | 中等（全手工） | 中高（框架自带） | 低（来源复杂） | 最高（统一安全层） |
| **可靠性** | 中等（靠测试） | 中高（基础容错） | 低（边界脆弱） | 最高（自动治理） |
| **可解释性** | 最高（因果透明） | 中等 | 低（推理链混乱） | 中高（可观测基础设施） |
| **可维护性** | 低（改一处动全身） | 高（模板划定结构） | 中等 | 最高（Core/Modifier分离） |

> **Q1**（经验观察，无优劣判断）：无手法在所有属性上最优。手法一性能最高但可维护性最低，手法四可靠/安全最高但引入抽象成本。
>
> **Q2**（典型取舍，非定律）：常见权衡包括：性能↔可解释性（优化越极致代码越难懂）；安全↔性能（每层检查都是开销）；可靠↔可维护（容错越多系统越复杂）。**这些是经验上的常见模式，不是物理定律**。

### 4.6 五维总览——决策权分布

五个维度揭示的核心观点是：**手法差异在决策权分布**：

| 维度 | 手法一（全部集中）→ | → | → | 手法四（全部托管） |
|:-----|:--------------------|:--|:--|:-------------------|
| 命名 | 我定 | | | 社区协商 |
| 绑定 | 我写 | | | 系统自动发现 |
| 核心/修饰 | 我自己分 | | | 架构定好框架 |
| 事件 | 我触发 | | | 声明式注册 |
| 系统属性 | 我保证 | | | 基础设施保证 |

> **D2**（经验观察）：手法一要求创造者对一切负责——这是最大的自由也是最大的负担。手法四将决策权分散托管给基础设施/社区/平台——这是最大的效率也是最大的抽象成本。**选择手法的本质是选择自己愿意承担多少决策权**。

## 5. 第五部分：应用尺规——手法选择与切换

### 5.1 手法切换信号

> **S1**（经验规则，非可证伪定律）：每种手法都有适用的窗口期。过早切换导致挫败，过晚切换导致停滞。

| 当前手法 | 切换信号 | 目标手法 |
|:---------|:---------|:---------|
| 样例抄袭 | 抄了3个以上但发现每次改同样的地方 | 模板微调（抽象共性为模板） |
| 模板微调 | 模板限制拖慢进度，需改动模板核心 | COW（fork模板独立演化） |
| 模板微调 | 市场没有合适模板 | 从0构建（只做内核，其他复用） |
| COW | 共享版本和私有版本差异越来越大，合并成本过高 | 从0构建（分叉为独立项目） |

### 5.2 组织中不同角色的常见手法分布（⚠️ 经验观察，非规范判断）

**⚠️ 重要诚实声明**：以下表格描述的是一个**常见的经验现象**——新手通常从手法三开始，老手更能灵活运用多种手法。**但这不是能力阶梯**（不意味着手法一的人比手法三的人高级），也不应该是组织的考核标准（擅长手法三的复制者在某些场景下比擅长手法一的发明者更有价值）。

| 角色 | 常见起始手法 | 成长方向 |
|:-----|:------------|:---------|
| 初级工程师 | 手法三为主 | 从「能抄」到「能理解抄的是什么」 |
| 中级工程师 | 手法二/四 | 能使用框架（二）并参与共享库维护（四） |
| 高级工程师 | 手法四为主，辅以手法一 | 设计可共享的架构，关键决策从原理出发 |
| 架构师/CTO | 灵活运用全部四种 | 关键决策用手法一（从原理出发），日常用手法二/四 |

**注意**：和 P2（之前版本）的冲突已经在 1.3 节化解。这里描述的「成长方向」不是沿手法的线性升级，而是**对「何时用什么手法」的判断力的提升**。一个 CTO 选择手法三（例如在成熟技术栈上直接复用社区最佳实践）是源于判断力，而非能力退化。

### 5.3 辩证批判——每个手法的暗面

| 手法 | 被高估时 | 被低估时 | 自检条件 |
|:-----|:---------|:---------|:---------|
| 手法一 | 明明可以复用偏要自建（NIH 综合征） | 真正的范式突破需要这个 | 现有方案是否确实完全无法满足需求？ |
| 手法二 | 以为自己是原创，实际在框架里打转 | 好的模板适配胜过劣质的从0构建 | 模板的架构哲学和需求方向一致吗？ |
| 手法三 | 被鄙视链底端 | 所有大师都从这个阶段开始 | 是否有明确的「抄完后理解」计划？ |
| 手法四 | 以为有 Git 就解决了所有协作问题 | 大规模协作的唯一可持续方式 | 清楚自己何时该合并上游吗？ |

> **T1**（经验观察而非定律）：选择手法就是选择代价——代价不消失只转移（这是对一个经验观察的陈述，不是热力学/信息论定理）。

### 5.4 手法选择决策清单

| 决策问 | 判断依据 | 倾向手法 |
|:-------|:---------|:---------|
| ① 控制力需求：你需要决定多少？ | 需决定骨架→手法一；只需扩展点→手法二 | — |
| ② 复用效率需求：多快交付？ | 时间极紧且方案已验证→手法三 | — |
| ③ 协作规模：几人维护？ | ≤2人可手法一/二；>5人必须手法四 | — |
| ④ 场景匹配：有成熟样例/模板吗？ | 有匹配样例→手法三；有匹配框架→手法二；都没有→手法一 | — |
| ⑤ 演化预期：会长期演化吗？ | 一次性脚本→手法三；长期产品→手法四 | — |

> **DC1**（经验规则）：手法选择由「控制力×复用效率×协作规模」三轴共同决定。常见错误是只看效率（全用手法三）或只看控制力（全用手法一）。

## 6. 第六部分：实战穿透——NumPy与Git中的手法实例

> **本部分价值定位**：展示框架如何应用于真实系统（可观察、可讨论），而非验证框架的正确性。**6.5节「循环论证的优雅」被保留但标注了其逻辑谬误性质**。

### 6.1 手法一：从内存到数据结构

| API | 手法特征 |
|:----|:---------|
| `np.empty()` | 从0分配内存，不做任何初始化——容器创建和内容填充是两件独立的事 |
| `np.array()` | Python列表→C连续内存的范式跃迁 |

### 6.2 手法二：预定义形状填充

| API | 模板类型 |
|:----|:---------|
| `np.zeros()/ones()/full()` | 形状骨架+填充值（填充值可替换，类似 Template Method） |
| `np.arange()/linspace()/logspace()` | 数值区间+步进策略（步进算法可替换，类似内建 Strategy） |
| `np.eye()/diag()` | 数学结构模板（维度参数可调） |

### 6.3 手法三：复制与采样

| API | 手法特征 |
|:----|:---------|
| `np.copy()` | 最直接的 Prototype 映射——所有 ndarray 都可被克隆 |
| `np.random.rand()/randn()` | 从概率分布采样——随机生成是「抄袭自然」的过程 |

### 6.4 手法四：共享内存

| NumPy特性 | 设计模式映射 | 特征 |
|:----------|:-------------|:-----|
| 视图(view) | Proxy | 轻量代理，操作转发到原数组内存 |
| 广播(Broadcasting) | Flyweight | **零复制虚拟共享**——比 COW 更激进 |
| 布尔索引+where | Composite+Strategy | 条件驱动视图 |

> **NP1**（观察而非法则）：NumPy 选择了**显式共享**（视图）和**显式分离**（copy()）而非隐式 COW。因为：性能可预测、语义清晰、GPU 兼容。

### 6.5 ⚠️ 自反性与逻辑谬误声明

**原版内容**：NumPy 本身不是一个从0构建的：继承自 Numeric（手法三）、融合 Numarray 特性（手法二）、社区贡献演化（手法四）、ndarray 统一设计是关键创新（手法一）。用四种手法分析了 NumPy，而 NumPy 本身也是四种手法的产物。

**本版诚实评定**：**这个自指论述不构成框架的验证**。一个能描述自身工具的框架**并不因此被验证**——任何足够灵活的框架都能做到这一点（例如你也可以用马斯洛需求层次「分析」马斯洛本人写层次理论时的动机，但这不证明层次理论正确）。把一个框架用于自身产物只是**应用演示**，不是**正确性证明**。本条保留作为演示，但应明确标注其非证明性。

### 6.6 Git——COW 的教科书实现

| Git 机制 | 手法四特征 |
|:---------|:----------|
| 对象存储按内容哈希去重共享 | 共享状态（类比手法四的共享基础） |
| 工作区修改→写时复制 | 分叉触发（类比手法四的私有副本） |
| PR/rebase | 合并回流（类比手法四的差异收敛） |

> **GT1**（观察）：Git 证明了手法四在大规模协作中可持续的三个前提——①内容寻址使共享零歧义；②写时复制使分叉零破坏；③合并协议使回流有秩序。

### 7.3 演化观察（⚠️ 非定律）

> **EV1**（经验观察）：系统中存在路径依赖——「为什么这里有这个设计」的答案经常是「因为历史原因」。**这不构成诺言，只描述事实**。

> **EV2**（经验观察）：每种手法引导系统走向其局部最优。手法二的模板选定后，后续选择必须适配这个模板。**最大的选择不是选择了什么，而是选择了之后不能选什么**。

> **EV3**（经验观察）：被观测的系统会因被观测而改变行为——这不是控制论定理，而是实际工程中常见的监测效应（监控工具消耗 CPU、采样影响性能等）。

> **EV4**（经验趋势，非不可逆物理定律）：从手法一走到手法四通常比反过来容易——单体→微服务后很难回到单体，上云后很难下云。**但这只是趋势，不是物理不可逆**——以足够成本和决心，「回退」总是可能的。

### 7.4 重构四信号

| 信号 | 症状 | 建议策略 |
|:-----|:-----|:---------|
| 增量成本失速 | 加小功能改10个文件 | 参考同行更好架构（手法三） |
| 认知超载 | 新人需3个月上手 | 迁到新框架（手法二） |
| 性能悬崖 | 10×资源→1×提升 | 核心层重写（手法一） |
| 技术债利息>本金 | 维护>重写 | 架构重设计+平台升级（手法一+手法四） |

> **RG1**（经验规则）：好重构四原则——可逆性（保留回退路径）、逐步替换（Strangler Fig 模式）、保留领域知识（bug fix和边界case不能丢）、理解旧系统为何长这样（每个看似愚蠢的决定背后大概率有当时合理的理由）。
>
> **RG2**（观察）：系统不是变老了才需要重构——是**假设过时了**。最初的设计假设（数据量、用户数、团队规模）变了。

### 7.5 重构触发量化检查清单

| 检查项 | 触发阈值（示例） |
|:-------|:----------------|
| 增量改动扩散度 | 一个小功能需改 ≥10 个文件 |
| 新人上手周期 | 新成员需 ≥3 个月独立交付 |
| 资源效率比 | 加 10× 资源仅得 ≤1× 提升 |
| 维护/重写比 | 年维护成本 > 一次重写成本 |

> **RC1**（经验规则而非定理论证）：**本清单是本框架中最「可证伪」的部分**——因为它给出了具体阈值。如果你在一个系统上观察到这些信号但重构后情况更糟，说明这些阈值不适用于你的场景。这种可被事实反驳的性质，恰恰是框架其余部分所缺乏的。**讽刺的是，最可证伪的部分反而是最「科学」的**。

## 8. 第八部分：空间组织逻辑——域的涌现与跨域代价

### 8.1 域生成的四个触发器

| 触发器 | 描述 |
|:-------|:-----|
| **① 物理接近** | 空间距离近的元素天然高频通信 |
| **② 功能专化** | 做同一类事的元素自然聚合 |
| **③ 信息密度差异** | 不同区域的信息熵不同，需要翻译 |
| **④ 安全/稳定需要** | 为控制风险划定边界 |

> **DOM1**（观察而不是设计建议）：域不是人设计出来的，是上面四个触发器**推动涌现的**。即使没有显式划分域，系统运行中也会自发产生暗域。

### 8.2 四维跨域代价

| 代价维 | 本质 | 典型值 |
|:-------|:-----|:-------|
| **时间代价** | 序列化/路由/排队/心智切换 | 域内μs级→跨域ms级 |
| **空间代价** | 缓冲区/网关/数据拷贝/冗余存储 | 域内零拷贝→跨域多份 |
| **关卡代价** | 认证/审批/合规/守卫 | 域内零审批→跨域多层 |
| **认知代价** | 语言翻译/心智切换/范式转换 | 域内同一语言→跨域需翻译 |

> **DOM2**（普遍观察）：**域内亲和 > 域外亲和**。同一域内元素的通信频率、耦合度、共享度远高于跨域。跨域必有代价——这个「必有代价」是经验事实（物理接近促进高效通信），不是信息论的信道容量定理。
>
> **DOM3**（常见现象）：域的自我强化机制（共享上下文→更有效通信→更多交互→信任累积→更愿意共享）导致**域边界一旦设错，修正成本会随时间增长**。

### 8.3 跨域策略的手法国度

| 手法 | 跨域方式 | 耦合度 |
|:-----|:---------|:-------|
| 手法一：原始跨域 | 域A直接调域B实现 | 极高 |
| 手法二：模板化跨域 | 标准接口/API/RPC约定 | 中高 |
| 手法三：模式化跨域 | Observer/Mediator/Adapter/Gateway | 低 |
| 手法四：基础设施化跨域 | Service Mesh / 数据湖仓 / 统一身份 | 极低（开发者视角） |

> **DOM4**（观察）：四种跨域手法的本质是对跨域代价的不同分配——手法一双方共担，手法二设计阶段一次性标准化承担，手法三由中介承担，手法四由平台集中承担。**代价不会消失，只会转移**。

## 9. 第九部分：设计活动的本质——观摩·提炼·重现·验证

### 9.1 设计循环

```text
观摩已有系统（可干预 / 不可干预）
    v
提炼规则（抽象化、去语境化）
    v
照着运作方式复刻 -> 设计新系统 -> 验证
    v
it works ✅ 或 doesn't work ❌ -> 回到第一步
```

这是人类一切造物的底层循环。从石器打磨到现代软件工程，形式千变万化，底层结构不变。

### 9.2 观摩的两种类型

| 类型 | 规则提取 | 可靠度 |
|:-----|:---------|:-------|
| **可干预系统** | 修改变量→观察响应→因果推断 | 高 |
| **不可干预系统** | 仅能观察现象→相关性推断 | 中-低 |

### 9.3 设计三问（取代 D3a 的过度声称）

**之前版本的 D3a 说**：「设计=TDD=机器学习=逆向工程（同一循环）」——这是过度声称。它们在「都涉及输入-输出推断」的层面同构，但在**推断的性质**上本质不同：

| 活动 | 推断性质 | 差异 |
|:-----|:---------|:-----|
| TDD | 规范性——测试是人**指定**的：f 应该是什么 | 人的判断在先 |
| 机器学习 | 归纳性——f 是从数据**统计学习**的 | 概率性、数据驱动 |
| 逆向工程 | 演绎性——f 从固定制品**恢复** | 确定性的（制品已存在） |
| 设计 | 创造性——f 是**被发明**的 | 可能本不存在 |

> **D3**（修正版——缩小了的声称而不是过度的等价）：设计可以理解为**猜测已有系统中正在运行的 Function 是什么，然后在新的上下文中重现它**。这一理解的价值是提醒设计者「你总是在借鉴，区别只在于借鉴了多少和借鉴的什么层面」。但**这个「猜测-重现」循环在四种活动中实现机制不同**，不能压为同一件事。
>
> **D3a**（原版过度声称——已删除）：设计=TDD=机器学习=逆向工程（同一循环）——**此陈述已被撤回**，因为它把「指定/学习/恢复/创造」四种不同的认知活动压成了一个空洞的同构（只在「都有输入输出」层面成立，近乎无内容）。

### 9.4 四种手法的本质统一

四种手法的差异不在「是否观摩」，而在**观摩了多少系统**和**提炼到什么层级**：

```text
手法一：观摩1个（物理世界）-> 提炼不可变规律 -> 原则级
手法二：观摩1个            -> 提炼可复制模板 -> 结构级
手法三：观摩多个            -> 提炼可组合模块 -> 模块级
手法四：观摩无数个          -> 提炼可共享抽象 -> 元级
```

> **D4**（经验观察）：设计者需四种能力——阅历力（观摩）→洞察力（提炼）→判断力（复刻）→执行力（验证）。
>
> **D5**（经验观察，⚠️可能不可证伪）：模仿是理解必经的中间态。跳过模仿可能意味着跳过理解。**但此条不可证伪**：任何「无可见模仿却理解了」的情况都可以被解释为「模仿了更隐蔽的模式」。这是一条启发式建议而非可验证的命题。

### 9.5 设计四问操作指南

面对一个新设计任务时，先问：

1. **观摩过什么？** — 有没有见过类似系统 work 或不 work？
2. **可干预吗？** — 能动手修改来验证因果吗？
3. **规则可靠吗？** — 提炼的规则是因果关系还是统计巧合？
4. **跑起来了吗？** — it works 吗？

> **D6**（操作指南而非定理）：四问之后，设计方向自然浮现。设计从来不是设计出来的，而是通过这个循环**迭代出来的**。

## 12. 附录B：诚实自评——本框架知道与不知道的事

### 框架能做的事

1. **提供结构化的分析语言**——当你要比较两个系统的创造方式时，五个维度（命名/绑定/核心/事件/属性）是实用的分析透镜，即使不完美 MECE
2. **连续谱直觉**——控制-效率谱的直观理解比简单的「聪明/偷懒」等级判断更有洞察力
3. **域的涌现理论**（DOM1-3）——域非设计而是涌现，跨域必有代价，这是框架中最扎实的部分
4. **重构量化清单**（7.5）——给出了具体阈值，是最可操作、最可证伪的部分

### 框架不能做的事

1. **预测新创造活动该用什么手法**——框架是事后分析工具，不是事前预测工具
2. **证明只有四种手法**——四种是经验归纳。如果你能找到第五种独立的、无法被四手法解释的创造方式，框架就需要修改（这恰恰是它可被改进的证据）
3. **告诉你你的系统有多「好」**——框架描述手法，不评判优劣
4. **量化不确定性**——「多少熵」「多少多样性」是修辞，不是可测量的量
5. **替代实验验证**——框架的任何一个断言，如果被经验反例否定，应该修改框架而非否认事实

### 从本版学到的最重要教训

> **一个框架的解释力不等于它的正确性。** 能解释一切（包括自己）的框架恰恰因此不可证伪。本框架真正的价值不在于原则编号的数量、理论标签的硬核程度或交叉引用网的密度，而在于：当它诚实面对自己的局限时，它仍然能提供有用的分析透镜。**去伪存真之后剩下的价值，才是真正的价值。**

> **最终启示**：四种创造手法不是一本「选哪个」的说明书，而是一张**你当前在什么位置、有什么可选、选了之后会怎样**的启发式地图。**创造不是选手法的游戏，而是驾驭所有手法的能力**——以及清醒地知道每一次选择转移了哪些代价、托管给了谁。
>
> *「多少熵」「多少多样性」在正文中被替换为「哪些代价」「转移给谁」——因为前者是量化修辞，后者是框架实际能回答的问题。*
