## 文章概要

GEPA（Generative Evolutionary Prompt Architecture）是一个**基于轨迹反馈 + Pareto 前沿 + 模块合并**的 Prompt/Skill 自动优化框架。核心主张：**真正重要的不是某条神奇 Prompt，而是让 Prompt 自己变好的循环。**

---

## 一、Prompt 优化的真实瓶颈：反馈太薄

大多数 Prompt 优化方案卡在同一个地方：**评测器只给一个分数**。

| 优化方式 | 反馈形式 | 学到的东西 | 问题 |
|:---------|:---------|:-----------|:-----|
| 人工手调 | 人读 case 后总结 | 经验规则 | 成本高，难复制 |
| 标量搜索 | 单个分数 | 哪个版本分高 | 不知道为什么好 |
| 强化学习 | reward / rollout | 参数或策略偏好 | 调试成本高，样本消耗大 |
| **GEPA** | **轨迹 + 自然语言反馈** | **可读、可审计的 Prompt 规则** | 依赖评测器质量 |

GEPA 的学习介质**不是梯度，而是自然语言**。反思模型先读完整轨迹，再根据具体失败原因改写。

---

## 二、四个核心机制

### 1️⃣ Reflective Mutation：把一次失败变成可复用规则

四步工程流程：

1. 抽 minibatch → 用当前候选 Prompt 跑完整链路
2. 保存轨迹（模块输入输出、推理过程、工具调用、工具返回、最终答案）
3. 评测器给出分数 + **文字反馈**（如"定位到了风险但缺少触发路径"）
4. **反思模型**读取"旧 Prompt + 轨迹 + 反馈"，只改当前选中的模块 Prompt

> **实用细节**：反思模型可以比目标模型更强。它不直接接管线上任务，而是把诊断能力"写进"目标模型可执行的 Prompt。

### 2️⃣ 一次只动一个模块

GEPA 不会每次把整套 Prompt 一起改掉，而是**选一个模块做局部变异**。这个限制很重要——一次只动一个变量，后面才知道收益和回归来自哪里。

### 3️⃣ Pareto 前沿：不要急着扔掉"偏科生"

**GEPA 不总是保留总分最高的那一版。** 在复合任务里，总分最高的候选未必支配所有样本。

Pareto 前沿的判断标准：**只要某个候选在至少一条验证样本上是当前最好，它就有留下来的理由。**

| 候选保留策略 | 会发生什么 | 风险 |
|:-------------|:-----------|:-----|
| 只留总分最高 | 主干很干净 | 容易丢掉长尾能力 |
| 保留所有历史版本 | 信息完整 | 候选池膨胀，搜索变慢 |
| **Pareto 前沿** | 留下互补版本 | 需要稳定验证集 |

> **理解**：Pareto 前沿就是"能力档案柜"——不是收集所有旧版本，而是保留那些还有独特价值的版本。

### 4️⃣ System-Aware Merge：把分支上的好东西拼回来

合并的约束条件：

| 约束 | 含义 |
|:-----|:------|
| 共同祖先 | 只合并同一任务谱系下的候选 |
| 模块边界清楚 | 候选必须能拆成模块级 Prompt 或规则 |
| 验证无回归 | 合并后要重新跑验证集 |

GEPA 更适合**多模块系统**（Agent / RAG / 工具链 / workflow）。单个 Prompt 也能优化，但在多模块系统中模块之间经常"此消彼长"，Merge 的收益更明显。

## 三、代码评审 Agent 实战案例

使用 GEPA 优化一个两模块代码评审 Agent（L=定位风险，C=生成评论），数据分三份：轨迹集 90 / 裁判集 45 / 封存集 30。

### 演化路径

| 候选 | 高风险缺陷召回 | 评论可采纳率 | 综合 | 说明 |
|:-----|:--------------|:------------|:-----|:-----|
| S0: L0+C0 | 61% | 67% | 61% | 初始版本 |
| S1: L1+C0 | **88%** | 54% | 74% | 召回↑但太吵，互不支配，留下 |
| S2: L0+C1 | 70% | **91%** | 82% | 评论质量↑，S0 可退 |
| **S3: L1+C1** | **87%** | **89%** | **88%** | **Merge 组合** |

**最终**：封存集 86%（初始 59%），评论可直接粘到 MR 的比例从 41% 提到 76%。

> **关键教训**：S1 没有被平均分策略清掉——它当时的评论质量很差，但缺陷召回能力后来被 S3 吃到了。如果只保留 S2，系统会变得很会写评论，却继续漏掉真正危险的 diff。

## 四、主循环与停止条件

```text
采样候选 -> 运行链路 -> 保存轨迹 -> 评测 + 文字反馈 -> 反思变异 -> 更新 Pareto 前沿 -> 尝试 Merge -> 验证
```

停止条件：

- **预算耗尽**：目标模型调用次数达 max_metric_calls
- **前沿饱和**：连续 K 轮无新候选进入 Pareto 前沿
- **满分达成**：验证集指标达上限

产物是**一组可解释的文本程序**——每次改动都有轨迹、有反馈、有验证分数，能追溯是哪个模块发生了变化。

## 五、与 GRPO / RL / MIPROv2 对比

| 对比项 | GEPA | GRPO / RL | MIPROv2 |
|:-------|:-----|:-----------|:---------|
| 平均效果 | 基线约 +10 分 | 主要对照基线 | 通常低于 GEPA 10%+ |
| 样本消耗 | 通过文字反馈减少无效 rollout | rollout 最多可达 35× | 与传统搜索接近 |
| AIME-2025 | 相比 MIPROv2 约 +12% | 未作为核心项 | 基线 |
| 结果形态 | **自然语言 Prompt，可读可审计** | 策略或参数更新 | Prompt 搜索结果 |

### GEPA 的工程吸引力

| 维度 | GEPA 的处理方式 | 对工程团队的价值 |
|:-----|:---------------|:-----------------|
| 样本效率 | 从单条轨迹提炼文字规则 | 少跑很多无意义试验 |
| 可解释性 | 知识沉淀在 Prompt 里 | 能审计，也能手工修 |
| 泛化方式 | 学的是规则，不只是分布偏好 | 对长尾样本更友好 |
| 部署成本 | 不需要权重训练 | 主要消耗 API 调用和评测预算 |
| 系统适配 | 支持多模块、谱系和 Merge | 更适合 Agent / RAG / 工具链 |

## 六、从链式迭代到候选树

传统 Prompt 调优是一条线：V0 → V1 → V2 → V3（旧版本优势一旦被覆盖就丢失）。

GEPA 是一棵**可横向焊接的候选树**：

| 能力 | 含义 |
|:-----|:------|
| **回访分岔点** | 旧候选只要还有独占优势，就能继续作为父代 |
| **横向合并** | 两个分支分别学到的模块经验可以组合 |
| **并行探索** | 多个候选分支可以独立评测和反思 |

## 七、落地边界：四层工作

### 适合 vs 不适合

| 适合使用 | 不太适合 |
|:---------|:---------|
| Agent、RAG、工具链等多模块系统 | 只有二值奖励、无文字反馈的任务 |
| 评测器能解释为什么错 | 验证集太小或噪声太大 |
| 需要白盒、可审计的优化结果 | 目标模型上下文极短 |
| 没有 GPU 只能调 API | 反思模型预算很低 |
| 对 rollout 成本敏感 | 需要权重级知识注入 |

### 四层落地工作

| 层级 | 要做的事 | 代码评审场景例子 |
|:-----|:---------|:----------------|
| **L1 反馈函数** | 把错因写成自然语言，不只是给分 | "指出了并发风险，但没有说明共享对象会被两个 goroutine 同时写" |
| **L2 参数配置** | 调整 auto/use_merge/num_threads 等 | 根据验证曲线决定是否开启 Merge |
| **L3 自定义 Adapter** | 把工具调用/延迟/复诉率接进轨迹 | 同时看到 diff 片段、静态扫描结果、人工采纳状态 |
| **L4 Instruction Proposer** | 约束反思模型如何产出 Prompt | 限制长度，过滤合规风险，多模型投票后再写入 |

> **L1 最容易被低估**——评测器写得粗，GEPA 只是在粗反馈上自动绕圈。

---

## 八、核心判断

1. **GEPA 让"调 Prompt"的重心往上游挪了一截**——人更应花在评测器、轨迹可观测性和反馈粒度上，而非手工改提示词
2. 与 Claude Code 作者 Boris 那句 **"I don't prompt Claude anymore. I write loops."** 一脉相承
3. GEPA 的边界比 PE 更宽：Prompt 可以，工具描述可以，Skill 可以，workflow、路由规则、harness 里的约束也可以
4. **GEPA 不是"自动写 Prompt 的工具"，而是系统优化框架**
5. 真正稀缺的能力：**如何设计评测、如何暴露轨迹、如何让每次失败留下可复用的经验**
