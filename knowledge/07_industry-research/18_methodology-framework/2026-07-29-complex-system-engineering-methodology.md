## §0 执行摘要

复杂系统的构建（无论是算力超节点、知识库工程还是软件系统）在**底层逻辑上是统一的**。无论是硬件定义算力系统、文件目录组织索引、还是知识库质量治理，解决问题的框架都遵循一套共同范式。

**三大支柱**：

1. **搭建方法论**（§1）— 前置定义先行：目标→依赖→目录→约束→实现，5步闭环
2. **静态载体设计**（§2-3）— 文件系统5种模式 + 索引3层体系
3. **动态维护机制**（§4）— 识别知识库 vs 代码库的根本差异，针对性治理

**核心洞察**：
> 代码追求**形式化精确**，知识追求**语境下有效**。精确容易工程化，语境很难标准化。知识库比代码库更难，根源就在于此。

## §1 系统搭建方法论：前置定义先行五步法

### 1.1 核心逻辑

任何系统的搭建，**前置定义必须先行，落地执行应该后置**。完整逻辑链：

```text
定目标 -> 理依赖时序 -> 规划目录架构 -> 枚举全部约束 -> 匹配实现方案 -> 落地执行
```

这套方法论适用于：

- 算力系统（超节点、集群）的整机设计
- 知识库工程（信息分层、目录规划、约束治理）
- 软件系统（微服务、分布式架构）
- 项目管理（阶段划分、资源分配）

### 1.2 第一步：锁定核心目标

区分**业务目标**（系统要解决什么问题、交付什么价值）与**技术目标**（性能、稳定性、扩展性、运维成本等指标）

- 划定边界：明确哪些需求本期实现、哪些暂缓
- **关键：目标必须可衡量，杜绝模糊描述**

**示例**：

| 类型 | ❌ 模糊 | ✅ 可衡量 |
|:-----|:--------|:----------|
| 业务 | "提高开发效率" | "将新特性发布周期从2周缩短到3天" |
| 技术 | "提升系统性能" | "跨节点通信延迟 ≤1μs，吞吐量 ≥800GB/s" |
| 质量 | "让内容更可靠" | "AI产出内容溯源覆盖率 100%，置信标签覆盖率 100%" |

### 1.3 第二步：梳理执行先后顺序（依赖拓扑）

本质是识别依赖关系，构建有向无环图（DAG）：

| 层级 | 内容 | 示例 |
|:-----|:------|:------|
| 底层基础 | 无依赖、通用、不可缺少 | 基础设施、CI/CD流水线、测试框架 |
| 公共支撑 | 被多个上层模块依赖 | 鉴权、日志、监控、数据模型 |
| 核心业务 | 系统主要价值 | 知识加工流水线、计算调度 |
| 上层应用 | 面向用户的入口 | API、搜索、推荐 |

**纪律**：

- 依赖项未就绪前，**不启动上层开发**
- 区分**关键路径**与次要任务，优先保障主线流程打通
- 关键路径上的阻塞要及时暴露、协调资源

### 1.4 第三步：规划目录/架构分层

**目录不只是文件夹，是架构思想的具象化**。

- 按照职责划分层级（基础设施层 → 数据层 → 服务层 → 接口层 → 应用层）
- 目录规范统一：区分配置、脚本、源码、资源、文档、运维工具
- 提前约定命名规范，防止后期结构混乱

**规范原则**：

```text
领域前缀_功能描述       # 统一前缀
00_/01_/02_             # 数字前缀表达层级/优先级
raw/processed/core/meta # 信息生命周期阶段
```

### 1.5 第四步：枚举全部约束条件

约束是系统不能逾越的红线，前期遗漏会造成大规模返工。

| 约束类型 | 示例 |
|:---------|:------|
| 资源约束 | 服务器、带宽、存储容量、预算上限 |
| 性能约束 | 响应时间P99、并发量QPS、数据存储上限 |
| 合规约束 | 数据安全等级、权限模型、隐私规范 |
| 运维约束 | 监控覆盖要求、备份策略RPO、故障恢复RTO |
| 技术约束 | 选定技术栈、兼容版本、第三方组件限制 |

**检查规则**：所有实现方案必须逐一对照约束清单进行合规校验，不满足任何一条约束则方案不合格。

### 1.6 第五步：选定实现方式 + 落地执行

基于**目标+顺序+目录+约束**综合决策，不能脱离前置条件单独选型：

1. 对比多种方案，校验是否满足全部约束
2. 区分自研 vs 开源组件 vs 外购服务的取舍
3. 预估实现难度、后期维护成本、扩容成本
4. 前置信息全部对齐、文档固化后，再启动执行

### 1.7 执行纪律：调整必须重走流程

执行过程中若需要调整目标、约束、架构，**必须重新走完完整分析流程**：

```text
发现调整需求
    v
回溯到第一步：调整目标/约束
    v
重新评估依赖拓扑和架构影响
    v
验证新方案约束合规
    v
更新文档后执行变更
```

**禁止**：边做边随意改动顶层设计。这是导致90%系统返工的根本原因。

## §2 文件系统设计模式体系

文件目录不是单纯文件夹，而是系统架构的静态载体。目录结构、文件命名、内容组织、元数据管理可抽象为**5种标准化模式**。

### 2.1 模式1：分层隔离模式 🏆 [核心模式，强制优先]

按照信息生命周期/处理阶段进行目录隔离，禁止数据混杂。

```text
00_raw/          # 原始数据源，只读不可修改（事实基线，可溯源）
01_processed/    # 一次加工、脚本清洗、AI初步输出
02_construct/   # 深度整合、体系化知识、系统方案、架构设计
03_meta/        # 元数据：索引、血缘、校验记录、约束清单、变更日志
99_archive/     # 归档、废弃试验版本、历史快照
```

**约束规则**：

- raw目录任何场景禁止写入修改
- 所有跨目录流转必须附带元数据记录

### 2.2 模式2：领域垂直拆分模式

在加工层按照业务领域垂直拆分，避免文件扁平化堆积。

```text
02_construct/
+- storage/          # 存储子系统
+- interconnect/     # 互联/芯片/CPU NUMA
+- software-stack/   # 软硬件集成/驱动/调度
+- cluster/          # 超节点/集群架构
```

**规则**：一份文档只归属单一主领域，跨领域通过元数据标签关联，不复制文件。

### 2.3 模式3：主干-分支演进模式 (Git思想)

区别稳定基线/试验特性/临时验证：

```text
workspace/
+- main/             # 定型稳定方案，对外交付基准
+- feature/          # 新方案迭代、功能扩展
+- experiment/       # 短期探索、临时验证（设有过期清理策略）
```

**关键**：main只合并经过验证的成果；不同分支之间禁止硬拷贝。

### 2.4 模式4：冷热分层存储模式

依据访问频率划分存储成本：

| 层级 | 介质 | 内容类型 |
|:-----|:-----|:---------|
| 热区 (Hot) | 本地高速存储 | 频繁查阅/持续迭代 |
| 温区 (Warm) | 普通块存储 | 阶段性使用 |
| 冷区 (Cold) | 低速归档存储 | 历史归档/极少访问 |

### 2.5 模式5：统一校验入口模式

独立目录存放校验规则，所有业务目录被动引用，不重复定义约束。

```text
00_rules/
+- schema/            # 各类文档/数据强制字段规范
+- check-script/      # 批量一致性检测脚本
+- standard/          # 指标定义、系统约束基线
```

**核心价值**：约束统一单点维护，修改一处校验规则全局生效。

## §3 索引治理体系

### 3.1 索引的必要性

当知识条目体量上涨后，单纯依靠文件夹层级不足以高效检索。索引解决三个核心痛点：

1. **文件越深，逐层打开效率极低** → 索引做快捷路由
2. **树形目录单一归属 vs 知识跨领域** → 索引支持多标签
3. **跨文档关联/状态不可视** → 索引记录关系与状态

### 3.2 三层索引架构

| 层级 | 位置 | 内容 | 更新频率 |
|:-----|:------|:------|:--------:|
| 顶层 — 全局主索引 | 根目录 index.md | 领域分区索引链接、特殊分类检索 | 周更 |
| 中层 — 领域索引 | 每个子目录 index.md | 本域文件清单+摘要+状态+标签 | 随目录变化 |
| 底层 — 文档内嵌索引 | 长文档头部TOC | 章节锚点、内部跳转 | 随文档更新 |

**全局主索引模板**：

```text
# 全局索引｜[系统名称]
> 元信息：更新时间、维护人、当前主干版本

## 领域分区索引链接
- [存储子系统](../../index.md)
- [CPU/互联架构](../../index.md)

## 特殊分类检索（标签式聚合）
### 🔬 试验原型清单
### ✅ 正式定稿方案
### ⚠️ 待复核/待验证条目
### 📦 归档历史文档

## 变更大事记
```

### 3.3 实现形态：静态文件 → 结构化元数据

| 阶段 | 形式 | 适用规模 | 工具需求 |
|:-----|:------|:--------:|:---------|
| 初期 | Markdown表格索引 | ~100文件内 | 无 |
| 中期 | 表格+标签标签规范 | 100-500文件 | 轻量巡检脚本 |
| 长期 | YAML/JSON 结构化元数据 | 500+文件 | UID系统+检索脚本 |

**结构化元数据示例** (YAML):

```yaml
uid: k_00128
title: 超节点软硬件集成指标定义
file_path: ./02_construct/cluster/supernode-metric.md
domain: ["算力集群", "系统指标"]
tags: ["超节点", "软硬件集成", "验收标准"]
status: verified
confidence: high
source_ref: [raw_test_log_0715]
```

### 3.4 索引更新纪律

| 规则 | 说明 |
|:-----|:------|
| 单一事实源 | 文件本体只存一份；索引只写链接，不复制正文 |
| 索引联动 | 新增/移动/删除文档，同步更新对应层级索引 |
| 死链接禁止 | 定期巡检脚本自动校验链接有效性 |
| 增量更新 | 每次文档变更后检查索引是否需同步 |

## §4 知识库 vs 代码库：信息确定性鸿沟

### 4.1 底层基础差异对比

| 维度 | 代码库 (Code) | 知识库 (Knowledge) |
|:-----|:-------------|:------------------|
| **载体** | 代码文本 | 文本、素材、分析结论、经验判断 |
| **真值标准** | 可执行/可复现；编译器和测试有客观判定规则 | 很难全自动判定真伪/优劣/适用场景 |
| **语义边界** | 功能目标清晰定义；输入输出契约可固化 | 概念极易漂移；同术语不同时期含义不同 |
| **变更影响** | 静态分析+单元测试可划定影响范围 | 一条基础认知更新，大量衍生观点需重新校验 |
| **自我增殖** | 代码不会自己产生新代码 | AI生成/持续阅读会源源不断产生新知识 |
| **最终产出** | 确定性行为（同样输入，稳定输出） | 条件性结论（受前置约束和场景限制） |

> **一句话总结**：代码追求形式化精确；知识追求语境下有效。精确容易工程化，语境很难标准化。

### 4.2 知识库独有五大工程难题

| # | 难题 | 具体表现 | 比代码难在哪 |
|:-:|:-----|:---------|:-------------|
| 1 | **信息层级混淆** | 把个人推论当客观事实、阶段性试验结论当长期基线、碎片素材未过滤直接入库 | 代码天然分层清晰（底层→业务→应用） |
| 2 | **目录结构先天局限** | 一条知识横跨多领域，树形目录只能放一条路径 | 代码依赖显式声明（import/require） |
| 3 | **可信度溯源困难** | AI产出幻觉、片面结论、过时信息持续侵蚀质量 | 代码有单元测试/CI自动验证 |
| 4 | **时效性治理** | 硬件参数/行业方案/技术权衡会持续变化 | 代码只需外部依赖不变即可长期可用 |
| 5 | **版本演化管理** | 缺少成熟标准来隔离试验内容与稳定基线 | Git分支/主干机制成熟且行业统一 |

### 4.3 根本原因分析

```text
代码库
  +-- 载体是形式化语言
        +-- 可被编译器/解释器客观判定
              +-- 真值标准清晰（跑得对/错）
                    +-- 变更影响可计算
                          +-- 最终产出确定

知识库
  +-- 载体是自然语言/经验判断
        +-- 没有通用自动化判定器
              +-- 真值标准依赖上下文
                    +-- 隐性关联难以扫描
                          +-- 最终产出条件性
```

### 4.4 工程设计启示

| 代码库可取的方法 | 知识库需要新增的方法 |
|:-----------------|:--------------------|
| CI/CD 流水线 | 知识CI流水线 + 层级校验 |
| 静态代码分析 | 定期巡检（孤立页/重复/矛盾检测） |
| 单元测试 | 溯源校验 + 置信标签 + 人工复核 |
| Git分支管理 | 主-分支演进模式（模式3） |
| 接口契约 | 约束列表 + 校验入口（模式5） |

## §5 统一行动口诀与落地检查清单

### 统一行动口诀

```text
搭建系统先定标，目标清晰不飘摇。
依赖拓扑理清楚，底层先搭上层后。
目录就是架构图，层次分明好找路。
约束枚举要齐全，遗漏一条就返工。
方案对比讲约束，不满足的不上线。
执行纪律要守好，改顶层先走流程。
文件分层隔离好，原始数据不动摇。
索引三层架起来，搜索关联两不误。
知识代码虽然异，底层逻辑却相通。
形式精确 vs 语境有效，两者各有所长。
```

### 落地检查清单

| 阶段 | 检查项 | ✅ |
