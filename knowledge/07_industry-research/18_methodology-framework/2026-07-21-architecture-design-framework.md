## §1 架构设计的本质定义

### 1.1 什么是架构

基于 304 份架构文档的综合提炼，架构设计的本质可归纳为：

> **架构 = 结构（Structure）× 行为（Behavior）× 约束（Constraint）的三元组**

| 元组 | 定义 | 追问 |
|:-----|:-----|:------|
| **结构** | 系统的组成部分及其静态关系 | 有什么？谁连谁？ |
| **行为** | 组件间交互与运行时动态 | 怎么通信？如何协作？ |
| **约束** | 不可违背的设计边界 | 必须满足什么？绝不能做什么？ |

### 1.2 架构 VS 设计 — 关键区分

| 维度 | 架构 (Architecture) | 设计 (Design) |
|:-----|:--------------------|:--------------|
| **范围** | 全局结构、组件间关系 | 局部实现、组件内部 |
| **变更代价** | 高（重构级） | 低（重构可不影响架构） |
| **决策属性** | 战略性、约束性 | 战术性、技术性 |
| **影响面** | 跨系统、跨团队 | 单模块、单功能 |
| **来源依据** | AWS Well-Architected、Intel EA、TOGAF 等成熟框架 | |

### 1.3 架构设计的三大元目标

从 304 份源材料中提炼出的共性目标：

1. **控制复杂度** — 通过分层、分治、抽象将无穷变有限（PCIe 分层模型、AWS 五大支柱）
2. **实现质量属性** — 性能、可用性、安全性、可扩展性等非功能性需求（Oracle MAA 青铜→白金）
3. **管理变化** — 使系统在需求变化时以可预测代价演进（微服务、SOA、VMware SDDC）

## §2 全谱系架构分层模型

分析 304 份源材料，架构设计横跨 6 个层级——从最底层的芯片物理设计到最高层的企业战略架构。

### 2.1 六层架构谱系

```text
+-----------------------------------------------------+
|  L6  企业架构 (Enterprise Architecture)              |  <- Intel EA, TOGAF, 商业银行治理
|      +- IT 战略、业务对齐、治理、投资组合管理          |
+-----------------------------------------------------+
|  L5  解决方案/应用架构 (Solution/Application Arch.)    |  <- AWS Well-Architected, Oracle MAA
|      +- 云原生、微服务、SOA、数据库架构               |
+-----------------------------------------------------+
|  L4  系统软件/中间件架构 (System Software Arch.)       |  <- 鲲鹏迁移/调优、Swing MVC
|      +- OS、虚拟化、中间件、Runtime                    |
+-----------------------------------------------------+
|  L3  网络与通信架构 (Network & Communication Arch.)    |  <- 5G、Leaf-Spine、MEC、ONAP
|      +- 网络拓扑、协议栈、SDN、NFV                    |
+-----------------------------------------------------+
|  L2  硬件系统架构 (Hardware System Arch.)             |  <- PCIe、Versal ACAP、GPU、服务器
|      +- 片上系统、互连、存储、供电                    |
+-----------------------------------------------------+
|  L1  芯片/半导体架构 (Chip/Silicon Arch.)             |  <- CPU指令集(鲲鹏/MIPS)、FPGA
|      +- 微架构、流水线、内存层次、DSA                 |
+-----------------------------------------------------+
```

### 2.2 层级间的关系特征

| 特征 | 说明 |
|:-----|:------|
| **上层依赖下层** | L6 决策约束 L5，L5 约束 L4... |
| **每层有独立关注点** | 各层关心的质量属性不同（L1 关注功耗/面积，L6 关注投资回报/合规） |
| **跨层可跳过** | 并非所有项目需要全部六层（嵌入式系统只到 L2，纯 SaaS 只到 L5-L6） |
| **层间接口是关键** | 架构设计的核心工作之一是在层间定义清晰、稳定的契约 |

### 2.3 源材料在各层级分布

从 `import/work/架构/` 304 个文件的分类统计：

| 层级 | 文件数 | 典型代表 |
|:-----|:------:|:---------|
| L1 芯片/指令集 | ~25 | MIPS、鲲鹏、Loongson、FPGA/ACAP |
| L2 硬件系统 | ~35 | PCIe、GPU(Volta/Tesla)、嵌入式(ESP32)、服务器 |
| L3 网络通信 | ~45 | 5G 架构、Leaf-Spine、MEC、ONAP、SDN |
| L4 系统软件 | ~40 | 鲲鹏调优、虚拟化(vSphere)、OS、Docker 相关内容 |
| L5 应用/解决方案 | ~110 | AWS、Azure、微服务、SOA、Oracle MAA、SAS |
| L6 企业架构 | ~50 | Intel EA、银行治理、TOGAF、数字化转型 |

> **关键观察**: L5（应用/解决方案）文件数最多(~110)，L1（芯片）最少(~25)。这反映了素材的采集偏好——以企业级 IT 架构为主，服务器硬件/芯片架构为辅。

## §3 六大架构范式与设计原则

从 304 份文档中提炼出六种核心架构范式，每种有其适用场景和设计原则。

### 3.1 范式一：分层架构 (Layered Architecture)

**源材料**: PCI Express 四层模型、OSI 七层模型、Swing MVC 改良

**核心思想**: 每一层只关注一个抽象级别，层间通过明确定义的接口通信。

**设计原则**:

1. **单向依赖** — 上层依赖下层，下层不依赖上层（PCIe: 软件层→处理层→链路层→物理层）
2. **封装变化** — 每层的内部变化不影响相邻层（Swing 可拔插感官）
3. **关注点分离** — 每层解决一个正交的关注点

**适用场景**: 协议栈、OS 内核、企业应用（多数系统）

**不适用场景**: 强实时系统、对延迟极度敏感的系统（层间跳转代价高）

### 3.2 范式二：微服务/SOA (Service-Oriented)

**源材料**: 微服务分布式平台、IBM SOA 医疗集成、分布式平台演化实践

**核心思想**: 系统被拆分为多个独立部署、自治的服务，通过 API 通信。

**设计原则**:

1. **高内聚低耦合** — 服务内强相关，服务间弱依赖
2. **去中心化治理** — 每个服务可独立选型（技术多元但带来绑定风险）
3. **容错设计** — 服务故障不级联（断路器、舱壁隔离）
4. **数据主权** — 每个服务拥有自己的数据存储

**适用场景**: 大型复杂业务系统、多团队开发、持续交付

**不适用场景**: 小型简单系统（过度工程）、对数据一致性要求极高（交易系统）

### 3.3 范式三：事件驱动架构 (Event-Driven)

**源材料**: SOA ESB、MEC 架构、Splunk SVA

**核心思想**: 组件通过异步事件交互，事件生产者与消费者解耦。

**设计原则**:

1. **异步非阻塞** — 事件产生后无需等待响应
2. **幂等性** — 同事件多次处理结果一致
3. **事件溯源** — 事件日志作为事实源
4. **背压机制** — 消费者跟不上时告知生产者减速

**适用场景**: IoT 数据处理、日志分析（Splunk）、实时流处理

**不适用场景**: 请求-响应式交互为主的系统

### 3.4 范式四：主从/控制平面架构

**源材料**: 5G C/U 分离、ONAP、VMware SDDC 控制平面、Sina App Engine

**核心思想**: 控制平面集中管理策略和状态，数据平面专注高吞吐转发。

**设计原则**:

1. **控制面与数据面分离** — 控制面可慢但精准，数据面要快但简单
2. **集中控制** — 全局视图避免分布式决策一致性问题
3. **声明式 API** — 用户声明期望状态，控制面实现（K8s 模式）

**适用场景**: 网络 SDN/NFV、云平台编排、基础设施管理

**不适用场景**: 全对等 P2P 系统、自治边缘节点

### 3.5 范式五：自适应/异构计算架构

**源材料**: Xilinx Versal ACAP、AutoGAN(NAS)、鲲鹏软硬协同

**核心思想**: 利用多种计算引擎（标量+矢量+自适应）的组合实现特定领域最优效率。

**设计原则**:

1. **异构协同** — CPU (标量) + GPU/加速器 (矢量) + FPGA (自适应) 各司其职
2. **数据驱动定制** — 架构根据工作负载特征自适应（NAS 搜索最优 GAN 架构）
3. **软硬协同** — 硬件特性在软件栈暴露（鲲鹏 NEON 向量指令优化）
4. **领域特定** — DSA (Domain-Specific Architecture) 比通用 CPU 效率高 10-100x

**适用场景**: 数据中心加速、AI 推理/训练、5G 基带、自动驾驶

**不适用场景**: 通用计算、事务处理

### 3.6 范式六：参考架构/蓝图模式

**源材料**: AWS Well-Architected、Oracle MAA、Splunk SVA、Intel EA

**核心思想**: 基于最佳实践预定义一组已验证的架构模板，按场景选择。

**设计原则**:

1. **分级选择** — 提供多级方案（Oracle MAA 青铜→白金，按 RTO/RPO 选择）
2. **验证保障** — 每个模板经过测试（Splunk SVA 验证架构）
3. **可定制** — 在模板基础上按需调整而非从头设计
4. **治理配套** — 附带评估问题清单（AWS 五大支柱问题集）

**适用场景**: 企业 IT 标准化、云迁移、合规场景

**不适用场景**: 创新性项目（无现有参考可遵循）

    v              v              v              v              v
  输出:          输出:          输出:          输出:          输出:

### 4.2 第一阶段：需求与约束分析

| 活动 | 输入 | 输出 | 源材料参考 |

```text

```

**范式选择决策树**:

```text

+- 是否需独立部署/多团队开发？
|   +- 是 -> 微服务架构
|   +- 否 -> 分层 + 事件驱动混合
+- 是否需集中管控？
    +- 是 -> 控制平面架构
    +- 否 -> 参考架构/蓝图
```

### 4.5 第四阶段：实现验证

| 方法 | 内容 | 源材料参考 |
|:-----|:------|:-----------|
| **架构审查** | 对照 6 大质量属性检查 | AWS 良好架构五大支柱审查问题集 |
| **性能验证** | 负载测试、容量规划 | Splunk SVA 验证架构、VxBlock ROI |
| **可用性验证** | 故障注入、灾备演练 | Oracle MAA 各层级验证 |
| **安全审计** | 渗透测试、合规检查 | OWASP、华为云安全白皮书 |

## §5 关键设计维度与决策矩阵

### 5.1 十大设计维度

以下维度覆盖了从 L1 到 L6 所有层级共通的决策空间：

| # | 维度 | 决策连续谱 | 参考来源 |

| 1 | **耦合度** | 紧耦合 -------- 松耦合 | PCIe(紧) vs 微服务(松) |
| 2 | **抽象层次** | 物理级 --------- 业务级 | L1 寄存器级 vs L6 业务能力 |
| 3 | **一致性** | 强一致性 ---- 最终一致性 | Oracle RAC(强) vs Eventual(弱) |
| 4 | **状态管理** | 有状态 -------- 无状态 | 数据库(有) vs 微服务(无) |
| 5 | **同步性** | 同步 ---------- 异步 | REST(同步) vs 事件驱动(异步) |
| 6 | **粒度** | 粗粒度 -------- 细粒度 | 单体(粗) vs 微服务(细) |
| 7 | **集中度** | 集中式 -------- 分布式 | SDN 控制面(集中) vs P2P(分布) |
| 8 | **弹性** | 手动扩展 ------ 自动弹性 | 物理机(手动) vs 云(自动) |
| 9 | **容错性** | 单点 ---------- 冗余 | 单实例(单点) vs RAC(冗余) |
| 10 | **修改代价** | 低 ------------ 高 | 配置(低) vs 重新布线(高) |

## §6 质量属性与评估框架

### 6.1 六大质量属性

基于 AWS Well-Architected、Oracle MAA、Splunk SVA 等源材料提炼：

| 属性 | 定义 | 度量指标 | 典型权衡 |
|:-----|:-----|:---------|:---------|
| **可用性** | 系统正常运行时间比例 | 99.9%~99.9999% (RTO/RPO) | 可用性 vs 成本（每增加 9 约 2x 成本） |
| **性能** | 响应时间与吞吐量 | P50/P95/P99 Latency, TPS | 性能 vs 资源消耗 |
| **可扩展性** | 承载增长/缩减的能力 | 扩展比、弹性时间 | 可扩展 vs 复杂度 |
| **安全性** | 防入侵、数据保护 | 漏洞数、合规达标率 | 安全 vs 便利性 |
| **可维护性** | 修改与运维的易度 | MTTR、变更成功率 | 可维护 vs 性能 |
| **成本效率** | 单位产出消耗资源 | TCO、ROI | 所有属性的权衡对象 |

### 6.2 质量属性权衡模型

```text
                +-- 可用性（99.999%）
                |      ^
                |      |
  安全性 -------+------+------- 成本（TCO）
                |      |
                |      v
                +-- 性能（低延迟）
```

**关键权衡**: 不存在在所有维度都最优的架构。每次设计决策必须在质量属性间做显式权衡。

### 6.3 评估方法

| 阶段 | 评估方法 | 谁参与 | 检查点 |
|:-----|:---------|:-------|:-------|
| 概念设计 | 架构评审（ADR 审查） | 架构师团队 | 范式选择合理性 |
| 详细设计 | 维度打分（1-5 分） | 架构师+相关者 | 决策矩阵完整性 |
| 实现后 | 压力测试+演练 | QA + 运维 | 是否满足 SLO |
| 运营期 | 监控+审计 | 运维团队 | 是否偏离基线 |

## §7 常见反模式与陷阱

综合 304 份源材料中记录的问题案例，提炼十大架构反模式：

### 7.1 十大反模式速查

| # | 反模式 | 症状 | 后果 | 修复方向 | 源材料参考 |
|:-:|:-------|:-----|:-----|:---------|:-----------|
| 1 | **过度分层** | 层数 > 7，每层仅是透传 | 延迟累加，无价值 | 合并层，砍掉纯透传层 | PCIe 设计不是层越多越好 |
| 2 | **微服务过度拆解** | 服务数 > 模块数×3 | 分布式复杂度 > 单体收益 | 合并服务，按业务边界聚合 | 微服务辩证法 |
| 3 | **银弹追逐** | 新架构即翻新 | 团队永远在学新框架 | 匹配团队成熟度渐进演进 | Intel EA 演进观 |
| 4 | **忽略非功能性** | 全部精力在功能设计 | 交付即欠技术债 | 从第一天定义质量属性 | AWS 五大支柱 |
| 5 | **接口膨胀** | 接口数 > 组件数×2 | 依赖混乱难以升级 | 契约先行，严格版本管理 | SOA 集成教训 |
| 6 | **伪分层** | 层间循环依赖 | 改一处影响全局 | 强制单向依赖检查 | PCIe 层间契约 |
| 7 | **过度抽象** | 抽象层把简单变复杂 | 理解成本 > 复用收益 | 只在确实需要复用处抽象 | Swing MVC 范围控制 |
| 8 | **审查过晚** | 代码完成才做架构审查 | 返工成本 > 10x | 概念阶段即审查 | Oracle MAA |
| 9 | **忽视可观测性** | 无日志/监控/追踪 | 故障定位 > 修复×5 | 从设计第一天埋观测点 | Splunk SVA |
| 10 | **治理缺失** | 架构文档与实现不一致 | 架构漂移，技术债累积 | 建立架构合规检查 | Intel EA 治理 |

### 7.2 反模式检查清单

每次架构设计交付前，逐项检查：

- [ ] 是否存在层间循环依赖？
- [ ] 服务粒度过细（<5 个 API/服务）？
- [ ] 架构层数超过合理值（企业应用 ≤ 4 层）？
- [ ] 核心质量属性（至少 3 个）有明确量化指标？
- [ ] 每个组件有明确的责任边界描述？
- [ ] 组件间接口已定义（即使粗略）？
- [ ] 单点故障已识别并有容错方案？
- [ ] 可观测性方案已纳入？

## §8 架构文档规范

### 8.1 架构文档模板

基于 Intel EA 和 AWS 框架，推荐以下文档结构：

```text
1. 文档元信息（版本、作者、日期、审核）
2. 背景与上下文（业务目标、范围、约束）
3. 架构概述（范式选择理由、分层图）
4. 架构视图
   +- 逻辑视图（组件、关系、接口）
   +- 部署视图（物理拓扑、环境）
   +- 数据视图（模型、流程、存储）
   +- 安全视图（认证、授权、加密）
   +- 运行视图（启动、通信、故障处理）
5. 关键决策（ADR — Architecture Decision Record）
6. 质量属性评估（目标指标、当前基线、差距）
7. 演进路线图（阶段、里程碑、依赖）
8. 术语表
```

### 8.2 ADR（架构决策记录）格式

**每项重大决策必须记录**，参考格式：

```markdown
## ADR-001: 选择微服务架构

- **日期**: 2026-07-21
- **状态**: 已接受
- **上下文**: 系统需支持 10+ 团队并行开发，需求并发高
- **决策**: 采用微服务架构，按领域驱动设计拆分
- **备选方案**: 单体架构（开发效率低）、SOA（过重）
- **理由**: 团队规模 / 需求变化频率 / 独立部署需求
- **后果**: 引入分布式复杂度（已规划 API 网关 + Service Mesh 应对）
- **修订记录**: v1 (2026-07-21) 初始决策
```

### 8.3 文档质量检查标准

| 标准 | 要求 | 参考 |
|:-----|:------|:------|
| **MECE** | 分层互斥、层内穷尽 | Intel EA 方法论 |
| **可验证** | 每个断言可追溯 | AWS Well-Architected 问题集 |
| **无歧义** | 术语一致、单位统一 | 银行治理指引术语规范 |
| **可执行** | 读到文档的人知道下一步 | VMware Horizon 指南 |
| **有版本** | 变更记录齐全 | VxBlock 文档版本 |
