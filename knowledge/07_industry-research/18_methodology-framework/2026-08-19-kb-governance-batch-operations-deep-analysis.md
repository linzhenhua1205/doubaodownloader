## 1. 引言与核心判断

### 1.1 为什么现在做这次体检

知识库已进入 **3000+ 文件 / 9.3G 仓库 / 488 项 import 素材** 的规模（2026-08-19 实测）。规模增长带来的不是线性复杂度，而是**分类边界漂移、素材堆积、批量操作低效、检索退化**四类治理问题的叠加。sr-010 已有 14 个关注面（F1-F14），但**结构治理（目录）、行为治理（批量操作）、输入治理（素材导入）三个维度未被显式覆盖**——本次补齐。

### 1.2 核心判断（先给结论）

| # | 判断 | 依据 |
|:-:|:-----|:-----|
| J1 | **目录体系「形全神散」**：注册表（std-005）齐全，但实际目录树存在重号、散文件、密度不均，且无「目录健康度」量化指标 | 02_rd/03_hardware 与 03_management 重号 [来源: std-005 §8]；05_tools 顶层 2 个散文件；07_industry-research 编号跳跃 03/04/10/16/18/19/20/99 |
| J2 | **批量操作是最大治理真空**：meth-010 Loop Engineer 只覆盖「同质修复」，未覆盖「1:N 拆分、N:1 合并、N:N 素材库转化」三类结构化批量场景 | meth-010 §5.3 七类场景全部是「一批文件×同一种操作」[来源: meth-010 §5.3] |
| J3 | **素材生命周期缺失**：import/ 488 项 1.9G 无状态机（待处理/处理中/已完成/废弃），处理完不清走 → 堆积即腐化 | import/ 实测 1.9G；sr-010 F13-04「素材层归档规则」P0 未闭环 |

## 4. 目录合理性：分类清白度评估框架

### 4.1 「清清白白」的定义（MECE + 可判）

一个分类体系「清白」需要同时满足 5 个可检查维度：

| 维度 | 定义 | 检查方法 | 当前状态 |
|:-----|:-----|:---------|:---------|
| **M1 互斥** | 同层目录边界无重叠，任何文件只应属于一个目录 | 关键词交叉扫描（同主题多目录命中率） | 🟡 超节点跨 3 模块 |
| **M2 穷尽** | 顶层模块覆盖所有内容类型，无「无处安放」 | 散文件扫描（顶层非目录文件数） | 🔴 05_tools 2 个散文件 |
| **M3 编号规范** | 目录编号连续/语义化，无重号 | 编号正则校验 + 重号检测 | 🔴 03_hardware 重号 |
| **M4 密度健康** | 单目录文件数在阈值区间（如 10-100） | 密度统计 + 超阈值标记 | 🟡 01_survey 膨胀 / 02_rd 过碎 |
| **M5 操作映射** | 每个目录有明确的「什么内容放这里 + 不放这里」 | std-005 注册表条目完整性 | 🟢 注册表齐全，但 M1-M4 未量化 |

### 4.2 判定表增强：每类目录的「操作方式」

现有 std-005 §2 判定表只有「性质/用途」，缺少**负面清单**（什么不放这里）。建议每类补充两列：

| 模块 | 正面清单（放这里） | 负面清单（不放这里） |
|:-----|:-------------------|:---------------------|
| 01_survey/ | 行业动态、日跟踪、事件流 | 深度分析（→07_industry-research）、方法论（→spec/meth-*） |
| 02_rd/ | 服务器研发知识（硬件/软件/项目/管理/芯片/专利） | 行业宏观趋势（→01_survey）、AI 通用原理（→03_AI） |
| 03_AI/ | AI 架构/原理/Agent/方法论/培训 | 服务器产品实现（→02_rd）、AI 行业动态（→01_survey） |
| 05_tools/ | 工具教程、技术栈笔记 | 系统规格（→spec/）、可执行脚本（→scripts/） |
| 06_others/ | 想法暂存、外部来源归档、待分类 | 已结构化知识（→对应模块） |
| 07_industry-research/ | 深度行业专题报告（五看三定） | 日跟踪（→01_survey）、一次性统计（→weekly-reports/07_kb_stat） |

> 负面清单的价值：**「不放在这里」比「放在这里」更能约束分类漂移**——AI 归档时先排除再归属。

### 4.3 目录健康度指标（Dir-Health Index）

将 M1-M5 量化为一个可定期扫描的**目录健康度指标**：

> 评分说明（中文版）：M1 互斥=100 减跨模块重复主题数×10；M2 穷尽=100 减顶层散文件数×20（顶层不允许 md）；M3 编号=100 减重号目录×20 减编号跳跃×5；M4 密度=100 减超阈值目录×5（阈值 5-100 文件/目录）；M5 映射=注册表覆盖率×100。分级：≥90 绿 / 70-89 黄 / <70 红。

```text
DirHealth = w1*M1_mutex + w2*M2_exhaust + w3*M3_numbering
          + w4*M4_density + w5*M5_mapping        (w weights, each 0-100)

Scoring:
  M1_mutex     = 100 - 10 * (cross-module duplicate topics)   // topic hit >=2 modules
  M2_exhaust   = 100 - 20 * (top-level loose files)           // no md allowed at top
  M3_numbering = 100 - 20 * (duplicate-number dirs) - 5 * (number gaps)
  M4_density   = 100 - 5 * (dirs beyond threshold)            // threshold: 5-100 files/dir
  M5_mapping   = 100 * (registry entries / actual dirs)       // registry coverage

Grade: >=90 GREEN / 70-89 YELLOW / <70 RED
```

> 该指标可用 `kb-dir-registry.py --diff` + 增强脚本月度输出，替代「人工巡检」。

## 5. 批量操作：四关系模型与深度理解处理

### 5.1 关系模型总览

用户提出的核心洞察：**批量操作的本质是「素材（源）↔ 知识（目标）」的多对多映射**。按映射基数分四类，加上「深度理解」作为质量维度，共 5 种模式：

| 模式 | 基数 | 定义 | 典型场景 | 当前工具 | 成熟度 |
|:-----|:----:|:-----|:---------|:---------|:------:|
| **1:1** | 1源→1目标 | 单素材→单知识文档 | URL 归档、豆包链接、单文件导入 | web-archive / doubao-share / git-submodule-import | 🟢 成熟 |
| **1:N** | 1源→N目标 | 单素材拆分为多篇知识 | 同源长对话多专题拆分、长文档分章 | 无专用工具（人工拆分） | 🔴 空白 |
| **N:1** | N源→1目标 | 多素材汇聚为单篇 | 多源三角验证综述、专题报告（五看三定） | industry-insight skill | 🟡 半程（素材索引靠人工） |
| **N:N** | N源→N目标 | 素材库批量转化为知识库 | import/ 488 项消化、批量导入门禁 | discover-quality-scan（仅 discover/） | 🔴 最大真空 |
| **深度理解** | 质量维度 | 素材须「理解→提炼→重写→结构化」而非搬运 | 所有导入的最终要求 | light-file-reading + 人工 | 🟡 AI 可做、批量成本高 |

### 5.2 各模式的痛点与解决方向

#### 1:1（成熟，可固化）
- 现状：web-archive（URL→MD）、doubao-share（豆包链接→MD）、git-submodule-import（仓库→submodule）已成型
- 痛点：无「归档后质量抽查」（sr-010 F2-03）
- 解决：1:1 流程加尾部 gate——「转换保真检查清单」核对（公式/表格/图片/元数据/时间）[来源: sr-010 F2-01]

#### 1:N（空白，需建流程）
- 场景实证：同源对话（豆包导出 500+ md）中一个主题可拆出「方法论 + 技术方案 + 决策记录」多篇 [来源: MEMORY.md 同源对话可多专题拆分归档]
- 痛点：无拆分规范 → 要么整篇堆（信息密度低），要么靠人工切（效率低）
- 解决方向：**「1:N 拆分模板」**——源文档头部声明拆分意图（`> Split: topic1 → path1; topic2 → path2`），AI 按声明生成 N 篇 + 母文档留存目录导航

#### N:1（半程，需补素材索引）
- 场景实证：industry-insight 五看三定专题（22 源体系 + 3 组聚合 + 两阶段流水线）[来源: meth-004]
- 痛点：素材检索靠 grep 全库，无「专题素材池」概念——同一专题的多份素材分散在 import/ 与 knowledge/ 各处
- 解决方向：**专题素材清单**（每专题一个 `sources.md`：URL + 关键数据 + 状态），N:1 汇聚时先建池再综述

#### N:N（最大真空，需管线）
- 场景实证：import/ 488 项（work 828M / server 205M / md 157M / 千问 126M / doubao 58M）[来源: 本机实测]
- 痛点：
  1. 无**素材状态机**（见 §7.2）——不知道哪些已消化、哪些待处理
  2. 无**批量门禁脚本**——质量纪律散在记忆中（MEMORY.md 批量导入质量门禁）
  3. 无**批量执行预算**——批量 AI 处理 token 不可控
- 解决方向：**N:N 管线四段**——`登记（manifest）→ 门禁（quality-gate）→ 归类（dir-registry --suggest）→ 消化（Loop Engineer 分批）`，见 §8 方案矩阵

#### 深度理解处理（质量维度，贯穿所有模式）
- 定义：素材→知识不是「复制粘贴」，而是**理解→提炼→重写→结构化**四步
- 现状：light-file-reading（读文件学习）、depth-completer（防框架堆名词）、light-idea-critique（批判）已覆盖单文件深度，但**批量深度处理无分级**——不是所有素材都值得深度理解
- 解决方向：**「深度分级」策略**——按素材价值分三级：A 级（核心专题源）→ 深度理解 + 结构化为专题文档；B 级（有价值参考）→ 提炼要点 + 交叉链接；C 级（低价值/重复）→ 登记即弃（进 manifest 标注废弃）。避免「每个素材都做深度分析」的 token 无底洞。

### 5.3 批量权限与预算（强化 std-003 §2.3）

| 规模 | 定义 | 操作权限 | token 预算 |
|:-----|:-----|:---------|:----------|
| 单文件 | 1 个 | 直接执行 | 无限制（走正常流程） |
| 小批量 | 2-5 个 | 先执行后报告 | 样本先行（先处理 1 个评估成本） |
| 大批量 | >5 个 | **先问用户**（展示计划） | 按批预算（如每批 ≤100K token） |
| 目录级 | 整个子目录 | **先问用户**（变更计划） | 拆批 + 每批验证 |

## 7. 新工具与新素材导入：生命周期与 RAG

### 7.1 新工具导入：三查 + 三登记

**导入前三查**（防 star 通胀，MEMORY.md 开源选型纪律 [来源: MEMORY.md]）：
1. **活跃度查**：最近 commit / issue 响应 / star 增长曲线（非绝对值）
2. **描述查**：README 是否真实描述能力（防包装）
3. **内容查**：抽样代码/文档质量，评估维护成本

**导入后三登记**（进 meth-014 资产图谱的工具实例化）：
| 登记项 | 内容 | 落点 |
|:-------|:-----|:-----|
| 工具卡 | 名称/用途/版本/来源/凭证状态 | `tools-manifest.json`（或 meth-014 扩展） |
| 依赖卡 | Python/npm/系统包依赖清单（sr-010 F3-04） | 每 skill 标注 |
| 安全卡 | skill-security-vetter 审查结果 | skills/ 注册记录 |

### 7.2 素材生命周期状态机（import/ 治理核心）

```text
                  +----------------------------------------------+
                  |        Material Lifecycle State Machine       |
                  |                                              |
   +----------+   |  +---------+   +----------+   +----------+  |
   |  New     |---+> | PENDING |-->|PROCESSING|-->|   DONE   |  |
   |(URL/File)|   |  +---------+   +----------+   +----------+--+--> knowledge doc
   +----------+   |      |              |             |          |
                  |      v              v             v          |
                  |  +---------+   +----------+   +----------+  |
                  |  | SKIPPED |   | BLOCKED  |   | ARCHIVED |  |
                  |  +---------+   +----------+   +----------+  |
                  +----------------------------------------------+
```

> 状态中文释义：PENDING=待处理 / PROCESSING=处理中 / DONE=已消化（产出知识文档）/ SKIPPED=价值低登记即弃 / BLOCKED=依赖缺失或反爬失败 / ARCHIVED=已归档（移入 tmp/bak/）。

**manifest 字段**（`import/manifest.json`，纯 ASCII）：
```json
{
  "id": "import-0001",
  "source": "https://github.com/xxx/repo",
  "type": "github-repo | url | doubao | local-file",
  "status": "PENDING | PROCESSING | DONE | SKIPPED | BLOCKED | ARCHIVED",
  "priority": "A|B|C",
  "target": "knowledge/... (set when DONE)",
  "imported_at": "2026-08-19",
  "processed_at": null
}
```
> 状态含义见 §7.2 状态机；`target` 为 DONE 时的知识库落点路径（与 kb-dir-registry --suggest 输出对齐）。

**状态转换规则**：
- PENDING → PROCESSING：开始消化（人工或批量任务认领）
- PROCESSING → DONE：产出知识文档 + 交叉链接（落点记录）
- PROCESSING → BLOCKED：依赖缺失/反爬失败，记录原因
- 任何状态 → SKIPPED：价值判定低（C 级），登记即弃
- DONE/BLOCKED/SKIPPED → ARCHIVED：清理期移入 tmp/bak/（永不 rm）

### 7.3 RAG 与本地数据

**现状分层**：

| 层 | 现状 | 问题 |
|:---|:-----|:-----|
| 数据层 | knowledge/ 3386 md + index.db 2.3G 向量索引 | index.db key 曾失效（282 次 batch 失败）[来源: sr-010 F1-03] |
| 检索层 | memory_search keyword-only [来源: MEMORY.md 检索架构] | embedding 未启用（高杠杆=启用，¥30-60/月 [来源: MEMORY.md]） |
| 本地数据 | RTX 5060 8G 跑 7B INT4 [来源: MEMORY.md 战略收敛期]；浏览器书签/本地文件 | 本地算力未接检索链路；本地数据源无清单 |

**决策建议**：
1. **短期（保持）**：keyword-only + 目录导航兜底——零成本，但召回率受限
2. **中期（评估）**：启用 embedding 需三条件齐备——①key 稳定性监控（F1-03 P0）；②月度成本预算（¥30-60）；③增量重建机制（文档变更→向量增量更新）。三缺一不启用
3. **本地数据接入**：优先把「浏览器书签 + obsidian 笔记 + 本地技术文档」做清单化（来源/格式/量级），评估哪些值得进 RAG（书签→元数据索引即可，obsidian→全量导入需成本评估）
4. **本地算力定位**：RTX 5060 8G 跑 7B INT4 适合**本地小模型批处理**（摘要/分类/实体抽取），不适合大模型深度分析——批量门禁中的「机器可判」部分（格式/命名/链接）应脚本化（零 token），「需判断」部分（价值分级/深度理解）才走 AI
