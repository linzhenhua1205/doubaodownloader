## 1. 核心命题：从约束失控到约束治理

### 1.1 问题提出

> "不断添加约束，不断扩大的系统规模，自己都搞乱了有多少约束，约束是否一致，变更是否到位。需要把约束和检测信息进行充分排查修复下，轻装上阵。"

这是任何持续演化的知识库系统都会面临的**约束退化问题**：

```text
阶段1: 少量约束（口头约定）-> 有效
阶段2: 约束增多（零散记录）-> 开始重复
阶段3: 约束膨胀（多处不统一）-> 冲突出现
阶段4: 约束失控（无法追溯）-> 依靠人工记忆
```

### 1.2 三类核心风险

| 风险类型 | 具体表现 | 后果 |
|:---------|:---------|:-----|
| **规则重复、表述不一** | 同一条约束在不同 Prompt/文档里措辞不同 | AI执行口径分裂 |
| **隐性冲突** | 规则A要求X，另一处允许少量X例外 | 边界模糊、决策混乱 |
| **变更无追溯** | 修改一条约束，无法批量同步到对应脚本/Prompt | 约束体系解体 |

## 2. 约束膨胀的三种风险模式

### 2.1 重复膨胀

```text
同一含义的约束，出现在 N 个位置：
- 对话记录中说过一次（口头）
- 某个README中写了一段（文本）
- Skill的SKILL.md中又有一条（规范）
- CI脚本中隐含假设（代码）

-> N个版本，可能不一致
-> 改了一处，其他N-1处依然保持旧约束
```

### 2.2 隐性冲突

约束在独立撰写时不会冲突，但在组合场景下矛盾：

- 规则A："上层只靠关系引用底层Log"
- 规则B："排查问题时可以在上层简要描述日志路径"
- 冲突边界：什么是"简要描述"？何时适用规则A，何时适用规则B？

### 2.3 变更雪崩

```text
改一条约束 -> 影响：
  - N个实体的描述文件（需重写）
  - M条Prompt（需更新）
  - K个自动化脚本（需修改）
  - L个模板文件（需调整）

-> 没有依赖图谱 -> 靠人脑不可能全覆盖
```

## 3. 约束法典中心化

### 3.1 根治方案

> **约束法典中心化 + 约束可检测化 + 变更版本化 + 自动化卡点兜底**

一次性地：**全集梳理、去重、对账、冲突排查、最终收敛为4大模块**。

### 3.2 约束4大模块

| 模块 | 覆盖范围 | 检测方式 |
|:-----|:---------|:---------|
| **层级隔离规则** | 跨层描述、信息下沉、实体边界 | 正则扫描实体描述文件 |
| **Index规范规则** | Index内容、格式、必填字段 | 结构化校验 |
| **图谱关系规则** | 关系格式、语义、完整性 | JSON Schema校验 |
| **文档质量规则** | 语言规范、粒度、一致性 | 文本分析+人工抽样 |

### 3.3 法典的版本管理

```text
约束法典需要：
- 唯一的版本号（SemVer）
- 每条约束有唯一编号（R001, R002, ...）
- 变更记录（什么版本增加了什么、修改了什么、废弃了什么）
- 依赖关系（哪些约束是互相引用的）
```

## 4. 约束可检测化：从自然语言到机器判定

### 4.1 四步转化范式

**任何自然语言约束都可以通过以下4步转化为机器可判定的校验规则：**

#### 步骤1：拆解三要素

| 要素 | 问题 | 示例 |
|:-----|:-----|:-----|
| **作用对象（Scope）** | 哪些文件/目录/字段生效？ | `knowledge/**/*.md` |
| **禁止/允许行为（Action）** | 不能出现什么/必须包含什么？ | 禁止出现"转发到"正文描述 |
| **例外白名单（Whitelist）** | 哪些路径不受约束？ | `knowledge/concepts/` 目录例外 |

#### 步骤2：选定技术载体

| 规则类型 | 技术方案 | 覆盖率 | 复杂度 |
|:---------|:---------|:------:|:------:|
| 文本关键词/违禁短语 | 正则表达式 Regex | 90% | 低 |
| Markdown结构/标题层级 | 文本解析+字符串匹配 | 5% | 中 |
| JSON/YAML Schema | Schema校验库 | 3% | 中 |
| 目录结构/命名 | 路径正则+ls校验 | 2% | 低 |

#### 步骤3：编写判定逻辑

```python
# 示例: 检查实体描述中是否有跨层引用
def check_cross_layer_reference(filepath, content):
    """检查实体文件是否违规内嵌了下游资源信息"""
    violations = []
    # 关键词检测
    cross_layer_patterns = [
        r"转发到\s+\S+",
        r"依赖\s+\S+",
        r"日志存储于\s+\S+",
        r"运行于\s+\S+",
    ]
    for pattern in cross_layer_patterns:
        matches = re.finditer(pattern, content)
        for m in matches:
            violations.append({
                "file": filepath,
                "line": content[:m.start()].count('\n') + 1,
                "rule": "R-CROSS-001",
                "violation": m.group(),
            })
    return violations
```

#### 步骤4：接入CI

```yaml
# GitHub Actions Workflow
on: [pull_request]
jobs:
  constraint-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Run constraint checks
        run: python3 scripts/constraint-checker.py
```

### 4.2 阻断级别

| 级别 | 含义 | CI行为 |
|:-----|:-----|:-------|
| **BLOCK** | 违反红线，必须修复 | 阻断合并 |
| **WARN** | 建议优化，不强制 | 仅提示 |

### 4.3 约束→检测 对应示例

| 约束原文 | 转化后检测逻辑 | 技术手段 |
|:---------|:---------------|:---------|
| "实体不跨层描述底层信息" | 检测实体文件中是否出现底层实体关键词（Linux/log path） | 正则 |
| "Index不记录关系" | 检测Index中是否出现"依赖/转发/引用"等关系描述词 | 正则 |
| "实体-关系解耦" | 检测实体描述中是否包含[依赖/转发/调用]等关系字眼 | 正则 |
| "Ingress只描述自身" | 检测Ingress实体文件中是否出现"转发到XXX" | 正则 |

## 5. 使用价值导向建库方法论

### 5.1 核心理念转向

> **知识库重点不在于建，而在于用好。建为用服务。**

从「建设导向」彻底转向「使用价值导向」：

```text
❌ 传统顺向思维：
先建库 -> 再想怎么用 -> 发现很多内容用不上

✅ 本方案逆向思维：
先穷尽消费场景 -> 拆解每个场景需要什么数据 ->
反向定义知识库结构、约束规范、内容颗粒度 ->
最后才开始录入内容
```

### 5.2 三大使用场景

| 场景层级 | 描述 | 核心价值 | 对知识库的倒逼 |
|:---------|:-----|:---------|:---------------|
| **L1: 基础交互** | 检索+问答+RAG | 保底能力，非核心 | 单条知识点完整文本 |
| **L2: 程序化调用** | MCP/API/接口输出 | **核心高价值** | 可解析Schema+结构化数据 |
| **L3: 场景工程化** | 故障定位/文档生成/配置生成 | **最高价值** | 完整实体关系+约束合规 |

### 5.3 建为用服务的落地原则

1. **先定义消费场景的数据需求** — 每类场景需要什么数据格式、什么粒度、什么关系
2. **反向约束内容录入规则** — 不满足消费场景需求的内容不录入
3. **对外输出先行** — 先定义API/MCP接口规格，再定义库内结构
4. **持续验证闭环** — 每新增一个使用场景，验证现有结构是否能满足

## 6. 四层质量保障防线

### 6.1 防线总览

```text
第1层: 事前约束 ---- 入库标准
第2层: 自动化检测 -- CI拦截
第3层: 人工复核 ---- 定期抽检
第4层: 使用反馈 ---- 迭代优化
```

### 6.2 各层详解

#### 第1层：事前预防（入库前）

| 措施 | 说明 |
|:-----|:-----|
| 统一内容本体规范 | 写入法典，强制所有内容创作者遵守 |
| 最小粒度原则 | 一条只讲一个概念，避免大杂烩文档 |
| 实体边界明确 | 指定实体类型、属性字段、关系类型 |

#### 第2层：自动化检测（入库CI）

| 检测项 | 频率 | 阻断级别 |
|:-------|:----:|:---------|
| 层级违规（跨层描述） | 每次PR | BLOCK |
| Index格式合规 | 每次PR | BLOCK |
| 关系JSON Schema校验 | 每次PR | BLOCK |
| 命名规范 | 每次PR | WARN |
| 链接有效性 | 每日 | WARN |

#### 第3层：人工复核（定期抽样）

| 维度 | 抽样比例 | 复核人 |
|:-----|:--------:|:-------|
| 知识准确性 | 10% | 领域专家 |
| 描述完整性 | 5% | 质量控制 |
| 粒度合理性 | 5% | 架构师 |

#### 第4层：使用反馈（持续迭代）

| 反馈源 | 采集方式 | 处理周期 |
|:-------|:---------|:---------|
| MCP调用失败率 | 自动监控 | 实时 |
| QA回答质量评分 | 用户反馈 | 每周 |
| 故障定位成功率 | 事后统计 | 每月 |

## 7. 内容质量评估体系

### 7.1 评估框架

```text
质量评估 = 结构化合规质量（自动化） + 业务可用质量（人工+实测）
```

### 7.2 维度1：结构化合规质量（自动评分）

| 指标 | 权重 | 评分方式 |
|:-----|:----:|:---------|
| 层级合规率 | 30% | 违规文件占比 |
| Index覆盖率 | 20% | 有Index的文件占比 |
| 关系完整性 | 25% | 孤立实体占比 |
| 命名规范率 | 15% | 违规命名占比 |
| 链接有效性 | 10% | 死链接占比 |

### 7.3 维度2：业务可用质量（人工+实测）

| 指标 | 权重 | 评分方式 |
|:-----|:----:|:---------|
| 知识准确性 | 30% | 人工抽样评估 |
| 描述清晰度 | 20% | 人工评分 |
| 粒度合理性 | 15% | 架构审查 |
| 场景覆盖度 | 20% | 实测场景验证 |
| 接口可用性 | 15% | MCP/API调用成功率 |

### 7.4 分级标准

| 等级 | 结构化得分 | 业务可用得分 | 措施 |
|:-----|:----------:|:------------:|:-----|
| A+ | ≥95 | ≥90 | 标杆，可对外输出 |
| A | ≥85 | ≥80 | 良好，持续优化 |
| B | ≥70 | ≥60 | 需整改，指定责任人 |
| C | <70 | <60 | 冻结，全面重写 |

## 8. 变更版本化与自动化卡点

### 8.1 版本化体系

```text
约束法典版本: v1.0.0 -> v1.1.0（新增规则）-> v2.0.0（兼容性破坏）
检测脚本版本: 绑定约束法典版本
Prompt版本: 注明依赖的约束版本
```

### 8.2 CI卡点流程

```text
开发 -> PR -> 自动化约束检测
    +-- BLOCK违规 -> 阻止合并，输出报告
    +-- WARN违规 -> 提示，不阻止合并
    +-- 全部通过 -> 自动合并 -> 更新版本号
```

### 8.3 变更同步机制

```text
修改约束法典 -> 自动触发：
  1. 更新版本号
  2. 刷新检测脚本
  3. 通知所有依赖的Prompt/Workflow更新
  4. 输出变更说明
```
