## 1. 一句话概括

> **CPT（Cost Per Token，每 token 成本）是 AI 推理成本计量的核心指标：它把「模型调用」还原为「token 吞吐 × 单价」两个变量，使成本从「黑盒 API 费用」变成「可分解、可优化、可预测」的工程量——是连接模型能力、算力投入与商业定价的枢纽指标。**

AI 成本计算的关键不是「总花了多少钱」，而是**「每个 token 花了多少钱 + 每个 token 创造了多少价值」**——CPT 解决前者，Token 经济模型解决后者。

## 2. CPT 的定义与定位

**定义**：CPT = 处理一个 token（输入或输出）的平均成本。

**基本公式**：
```
CPT = total cost / total tokens
    = (compute + storage + serving) / (input tokens + output tokens)
```

**与相关指标的关系**：

| 指标 | 含义 | 与 CPT 的关系 |
|:-----|:-----|:-------------|
| CPT（每 token 成本） | 成本/token | 基准指标 |
| Token/s（吞吐） | token/秒 | 决定单位时间内能服务多少请求 |
| Token/Watt（能效） | token/瓦 | 决定电力成本占比 |
| TTFT/TPOT（延迟） | 首 token/每 token 时间 | 决定体验，间接影响容量规划 |
| 利用率（GPU Util） | 算力使用率 | 决定硬件成本摊薄 |

**定位判断**：CPT 是**成本侧**的枢纽指标——上游连接「算力成本」（GPU/电力/摊销），下游连接「产品定价」（每请求成本）与「优化决策」（缓存/量化/路由）。

## 3. Token 成本的三层结构

```
Three-layer token cost structure
+-----------------------------------------------+
| L1 API bill (explicit)                        |
|    input price x input + output price x output |
|    + cache-hit price x cached tokens           |
+-----------------------------------------------+
| L2 serving cost (semi-explicit)               |
|    inference servers (GPU) x hours + storage   |
+-----------------------------------------------+
| L3 infra cost (hidden, self-hosted)           |
|    hardware/amort + power + DC + ops + dev    |
+-----------------------------------------------+
```

**关键点**：
- API 模式（L1）：CPT 直接由厂商定价决定——但厂商定价背后是 L2/L3
- 自建模式（L2/L3）：CPT 必须自己算——**自建推理的真实 CPT = 硬件摊销 + 电力 + 运维 + 研发 / 有效 token 产出**（利用率是关键分母）
- 知识库锚点：缓存未命中是最大成本项（Token 成本：缓存未命中 58% 最大成本）——**CPT 优化首先要算清缓存命中的节省**

## 4. 为什么 CPT 是关键指标

1. **可分解**：CPT 可拆为「硬件成本/利用率/token 吞吐/单价」——每个因子都可独立优化（第一性原理：成本不是黑盒）
2. **可预测**：给定 QPS（每秒查询数）+ 平均 token 数 → 预测月度成本；成本随规模线性可算
3. **可比价**：跨模型、跨厂商、跨部署模式（API vs 自建）用 CPT 直接对比
4. **可优化**：CPT 的每个分量都有已知优化杠杆（见 §8）
5. **连接商业**：产品定价 = CPT × 单请求 token 数 × 毛利率——**CPT 决定产品能不能赚钱**
6. **统一语言**：从模型训练（每 token 训练成本）到推理（每 token 推理成本）到业务（每 token 收入）——token 是 AI 经济学的统一计量单位

## 5. CPT 的计算模型

### 5.1 API 模式
```
CPT_api = (P_in × T_in + P_out × T_out + P_cache × T_cache) / T_total
```
- P_in/P_out/P_cache：输入/输出/缓存命中单价（厂商定价，输出通常 3-5 倍于输入）
- T_in/T_out/T_cache：对应 token 量

### 5.2 自建模式（第一性原理）
```
CPT_self = C_hw / T_lifetime + C_elec / T_period + C_ops + C_dev
          -----------------------------------------------------
                      T_effective

C_hw       = hardware cost (GPU servers + network + storage)
T_lifetime = total tokens over depreciation (= util x peak tp x time)
C_elec     = power cost (= wattage x rate x hours)
C_ops      = operations (staff/monitoring/DC)
C_dev      = R&D (deploy/optimize/maintain)
T_effective= effective tokens (= peak tp x util x valid-rate)
```

**关键分母洞察**：
- **利用率**：GPU 利用率 30% vs 90%，CPT 差 3 倍——利用率是自建 CPT 的第一杠杆
- **有效率**：生成被丢弃/重试的 token 是浪费——重试率直接推高 CPT
- **吞吐随并发**：batching 规模决定吞吐——continuous batching 是 CPT 杀手锏

## 6. 从 CPT 到总拥有成本（TCO）

| 维度 | CPT 覆盖 | TCO 补充 |
|:-----|:---------|:---------|
| 单位成本 | 每 token | 每功能/每用户/每业务价值 |
| 时间维度 | 运行期 | 全生命周期（选型→部署→运维→退役） |
| 隐性成本 | 部分 | 集成/迁移/人才/失败重做 |
| 机会成本 | 无 | 模型能力差异导致的业务损失 |

**决策框架**：CPT 用于「运行期优化」；TCO 用于「平台选型/自建 vs API 决策」。**CPT 低但 TCO 高的方案（如自建但利用率长期 20%）不是好方案**。

## 7. 影响 CPT 的关键因素

| 因素 | 影响机制 | 敏感性 |
|:-----|:---------|:-------|
| 模型规模（参数） | 参数×计算量→吞吐↓→CPT↑ | 高（大模型 CPT 可差 10-100×） |
| 输入/输出比例 | 输出单价高（3-5×） | 中 |
| 上下文长度 | 长上下文→prefill 计算↑ | 高 |
| 缓存命中率 | 命中成本仅为全算的 ~10% | 高（58% 成本项） |
| 并发/批处理 | batching 提升吞吐 | 高（continuous batching 数倍） |
| 硬件代际 | 新一代 GPU 每 token 能效更高 | 中 |
| 利用率 | 摊薄硬件成本 | 高（30%→90% 差 3×） |
| 量化/蒸馏 | 降低单 token 计算量 | 中 |

## 8. 优化杠杆：降低 CPT 的七条路径

| # | 杠杆 | 机制 | 效果 |
|:--|:-----|:-----|:-----|
| 1 | **Prompt Cache（缓存）** | 复用公共前缀（system prompt/工具定义） | 缓存命中成本 ~10%，可降 CPT 30-50% |
| 2 | **Continuous Batching** | 动态合并请求，提高 GPU 利用率 | 吞吐提升 2-4×（vLLM 实证） |
| 3 | **模型路由** | 简单任务用小模型，复杂任务用大模型 | 平均 CPT 降 50%+ |
| 4 | **量化**（INT8/FP8/INT4） | 降低单 token 计算/显存 | CPT 降 30-70%（精度权衡） |
| 5 | **蒸馏** | 大模型蒸馏小模型 | 长期 CPT 结构性下降 |
| 6 | **上下文压缩/精简** | 减少输入 token（无关内容裁剪） | 直接降输入成本 |
| 7 | **批处理/异步** | 非实时任务排队合并 | 提高利用率 |

**优先级判断**（知识库共识）：缓存 > batching > 路由 > 量化——**先消除浪费（缓存/重试），再提利用率（batching），再降单 token 成本（量化/蒸馏）**。

## 9. CPT 与产品定价模式

| 定价模式 | 与 CPT 的关系 | 风险 |
|:---------|:--------------|:-----|
| 按 token 计费 | 直接映射 CPT | 用户难预估成本，体验差 |
| 按请求/次数 | CPT × 平均 token 数 | 长上下文请求亏损 |
| 订阅制 | CPT × 平均用量 < 订阅价 | 重度用户亏损 |
| 按价值/结果 | 与 CPT 脱钩 | 需保证毛利率 |

**定价本质**：定价 = CPT × 用量 × (1 + 毛利)。**CPT 是定价的地板**——所有定价模式最终都要覆盖 CPT + 合理毛利；CPT 越透明，定价越科学。

## 10. 深度批判：CPT 的盲区与误用

| # | 盲区/误用 | 分析 |
|:--|:----------|:-----|
| 1 | **只看 CPT 忽略质量** | 便宜模型 CPT 低但错误率高→重试/修复成本吞噬节省——应看「有效 CPT」（含失败成本） |
| 2 | **输入/输出价格不对称** | 输出 token 贵 3-5 倍，但很多应用输出占比高——只看总 token 数会低估成本 |
| 3 | **缓存成本被低估** | 缓存不是免费的（存储+查表），长前缀缓存命中率低时收益有限 |
| 4 | **CPT 静态化** | 模型降价/硬件换代频繁，CPT 需持续重新测算（2026 年模型价格战使 CPT 快速变化） |
| 5 | **忽略隐性成本** | 集成/运维/人才/治理成本往往超过 token 费用本身——CPT 只是显性成本 |
| 6 | **「CPT 越低越好」误区** | 过度优化 CPT（如过度量化）可能损害质量/体验——CPT 应在质量约束下优化 |

**核心修正**：真正关键的是 **「单位价值成本」**（CPV = 成本/业务价值），CPT 只是中间指标。**先问「每个 token 创造多少价值」，再优化「每个 token 花多少钱」**——否则会陷入「为省 token 牺牲质量」的局部最优（呼应 AI 产出经济学：毛利 vs 净利）。

## 11. 对算力/服务器产业的启示

1. **CPT 是算力需求的商业语言**：客户买算力本质是买「更低的 CPT」——服务器厂商的竞争维度是「每 token 的系统成本」（硬件 + 电力 + 利用率），而不仅是 FLOPS
2. **利用率是服务器设计的隐藏变量**：CPT 分母 = 利用率 × 吞吐——服务器架构（Scale-Up/Scale-Out）的选择最终影响利用率→影响 CPT（呼应超节点 Token/s + Token/Watt 指标体系）
3. **KV Cache 硬件化降 CPT**：专用 KV 存储（CMX/HBF）减少 HBM 占用→提高可用 token 吞吐→降低有效 CPT（呼应知识库存储专题）
4. **电力成本成为 CPT 大头**：GPU 功耗上升→电力占比上升——液冷/能效优化直接降 CPT（Token/Watt）
5. **Agent 时代的 CPT 新维度**：Agent 单任务消耗 10-100× token（推理/工具调用/多轮）——Agent 应用的 CPT 是传统对话的 10-100×，成本治理更关键（OpenCost×llm-d per-token FinOps 趋势）

## 12. 计算示例（参数显式，可复算）

**示例：自建推理 CPT 估算**

```
Assume: 8xH100 node, $300K, 3-yr depreciation, 70% util
     peak tp (7B model, batch=256): 40,000 tok/s
     power: 10kW x 24h x 365d x $0.1/kWh ~ $8.8K/yr
     ops+dev: $30K/yr
     valid-rate: 95% (5% retry/discard)

yearly tokens = 40,000 x 0.7 x 31,536,000 x 0.95 ~ 8.4e11
yearly cost   = $300K/3 + $8.8K + $30K ~ $138.8K
CPT           ~ $138.8K / 8.4e11 ~ $1.65 / 1M tokens
```

**对照**：同模型走 API 输出定价约 $15/百万 token——**自建 CPT 约为 API 的 1/10（利用率 70% 时）**；若利用率降到 30%，自建 CPT 升至 $3.9/百万——优势缩小到 4×。**结论：利用率决定自建是否划算**。
