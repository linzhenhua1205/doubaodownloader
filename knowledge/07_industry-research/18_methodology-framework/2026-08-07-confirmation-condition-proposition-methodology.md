## 1. 引言：一次「能不能」的三种回答

上一条交付是「超节点计算节点 CPU 异常/重启场景下的 scale-out/scale-up 网络可靠性完整设计方案」。用户在追问之前，实际问的是一个问题：

> **「CPU 单板异常或重启的情况下，scale out / scale up 网络还能正常工作吗？」**

同一个问题，可以给出三种截然不同的回答：

| 回答形态 | 示例 | 可靠性的来源 | 可决策性 |
|:---------|:-----|:-------------|:---------|
| **结果型（断言）** | 「能，硬件上不经过 CPU」 | 发言者的可信度 | 高，但可能是错的 |
| **经验型（类比）** | 「类似平台我们做过，没问题」 | 案例相似度 | 中，案例可能不适用 |
| **原理型（条件命题）** | 「数据面可保持，控制面会中断，**取决于 10 项依赖条件，其中 2 项待厂商验证**」 | 证据链强度 | 低但可靠，可直接排期 |

三种回答对应三种认知模式。本文要论证的核心命题是：

> **工程上「目标可达成」从来不是一个布尔值，而是一张依赖条件状态表。**
> 「能不能」的正确回答形式是「在 X、Y、Z 满足的前提下，可达到 A 级目标；若 W 不满足，只能达到 B 级」。

**为什么部分人希望直接给结果，而这类评估必须走「原理分析 → 设计确认 → 部分实现 → 验证」的闭环？** 因为前者的需求是**决策输入**，后者的产出是**可交付的确定性**——两者在时间轴上天然错位：决策者要的确定性在当下不存在，只能靠过程制造出来。

## 2. 两种确认形态：结论确认 vs 条件确认

先解剖认知差异本身。面对同一个「能不能」，两种确认者的大脑运行方式完全不同：

| 维度 | 结论确认者 | 条件确认者 |
|:-----|:-----------|:-----------|
| **目标** | 得到一个「能/不能」的**决策输入** | 得到一条**证据链** + 依赖清单 |
| **时间偏好** | 尽早确定（排期/成本/风险需要数字） | 允许不确定性存在，直到被验证消除 |
| **对「不能」的态度** | 立刻转向替代方案或追问「那怎么办」 | 追问「在什么条件下能」 |
| **对「待验证」的态度** | 视为**未完成**（给不了结论） | 视为**正常状态**（确定性本来就要制造） |
| **本质动作** | **表决**（对目标投赞成/反对票） | **审计**（盘点达成目标的必要条件） |
| **错误代价** | 结论错误 → 决策错误 | 清单遗漏 → 验证闭环缺口 → 交付期返工 |
| **典型角色** | 产品/项目/管理者 | 架构/设计/验证工程师 |

关键认知：**两者没有对错，是时间轴上的分工**。结论确认者站在「决策点」上（必须现在拍板），条件确认者站在「交付链」上（确定性还没制造完）。矛盾的本质是——**决策点早于确定性制造完成点**。

> 这正是 [AI 产出经济学](../../03_AI/methodology/2026-08-05-ai-output-gross-vs-net-entropy.md) 里「确定性是存量资产」的推论：结论确认者想直接**提取**确定性，条件确认者知道确定性必须**先生产**，而生产需要原理分析 + 实现 + 验证的时间成本。

## 3. 结论的类型学：断言 / 论证 / 条件命题

要把「能不能」说清楚，先给结论分个类。任何结论按证据链强度可分为三型：

| 结论形态 | 特征 | 可靠性来源 | 例 |
|:---------|:-----|:-----------|:---|
| **断言** (Assertion) | 无证据链或证据链不可审计 | 发言者可信度 × 领域权威 | 「能保持，我做过类似项目」 |
| **论证** (Argument) | 有证据链，但链条是静态的 | 证据强度 × 推理严密性 | 「数据面不经过 CPU，原理上可保持」 |
| **条件命题** (Conditional) | 证据链 + 依赖清单 + 每项状态 | 清单完备性 × 状态真实性 | 「供电域隔离已设计；CX7 固件待验证；验证通过则 A 级可达」 |

**工程中的「目标可达成」天然是条件命题**，原因有二：

1. **系统复杂度 > 任何人的心智模型**：单一断言无法承载「电源域 × 复位域 × 时钟 × 驱动 × 控制面 × 厂商固件」的联合约束，必须分解为可逐项审计的清单。
2. **验证成本决定了置信度上限**：未验证的设计约束（如 CX7/PEX89104 在 CPU 掉电后的链路保持行为）只能标注「待验证」，无法用任何论证替代——论证证明「理论上可能」，验证证明「实际上可行」。

> 与 [材料可信度矩阵](2026-07-13-material-credibility-matrix.md) 同构：材料的可信度取决于来源层级；结论的可信度取决于证据链形态。断言 ≈ 低可信度材料，条件命题 ≈ 可交叉验证的权威来源。

## 4. 为什么「能不能」不是布尔问题：第一性原理拆解

用 CPU 案例做第一性原理拆解，看「目标可达成」如何从布尔问题展开成依赖清单。

**目标陈述**：CPU 单板异常/重启时，scale-out/scale-up 网络仍能正常工作。

**第一性原理追问**：网络「正常工作」需要什么？逐层剥离：

| 必要条件 | 是否依赖 CPU | CPU 异常时状态 |
|:---------|:------------:|:---------------|
| 供电（V_MAIN / V_GPU / V_STBY） | 部分 | 取决于电源域隔离设计（已设计：三域独立） |
| 时钟（网络器件参考时钟） | 否（独立时钟源） | 可保持 |
| 复位（PERST# 分组） | 部分 | 取决于复位分组设计（已设计：五分组互锁） |
| 链路训练（CX7 / PEX89104 上游端口） | 是（上游 = CPU/IOH） | **待厂商验证** |
| 驱动 / 固件（NCCL / QP / 路由表） | **完全依赖** | 中断，需重建 |
| 管理面（BMC 独立 V_STBY） | 否 | 始终存活 |

**关键发现**：目标本身是**分层的**——「网络正常工作」可以拆成：
- **A 级**：数据面完全保持（含跨组 GPU P2P）→ 需要 CPU IOD 中转路径也存活 → 依赖 CX7 固件行为（**待验证**）
- **B 级**：数据面保持（同组 P2P + Scale-Out）+ 控制面 30s 内重建 → 依赖 BMC 处置策略（**需实现**）+ OS 快速恢复（**需实现**）
- **C 级**：管理面始终存活，节点可被远程管理 → 已具备（V_STBY 独立）

于是「能不能达成」从一个布尔问题，展开为：

> **「达成 A 级需要 10 项依赖，其中 4 项已设计、6 项需实现、2 项待验证；在 8 项满足时 B 级可达，A 级待 2 项验证结果。」**

这就是 [可行性分析方法](../../02_rd/00_shared/01_architecture/2026-07-13-feasibility-analysis-methodology.md) 的落点：可行性不是一次判断，是一个**必要条件集的可达性审计**。

## 5. 确定性是被制造的：确认的过程论

为什么不能直接给「能」？因为**在早期，能级的确定性在物理上不存在**。

### 5.1 确定性的时序曲线

```
confidence
 100% |                                  +-- verification closed
      |                            +-----+
  80% |                      +-----+     |
      |                +-----+           |
  50% |          +-----+                 |
      |    +-----+                       |
  20% |----+                             |
      +-------------------------------------> time
       concept  principle  design  impl  verify  delivery
```

- **概念期**：置信度 20-30%，此时任何「能/不能」都是**猜测**（即使是资深专家，也只是置信度更高的猜测）
- **原理分析期**：置信度 50-70%（论证型结论，静态证据链）
- **设计期**：置信度 70-85%（约束落实为方案，可审查）
- **实现+验证期**：置信度 90-99%（注入测试证明实际行为）

**结论确认者想要的「确定性」在概念期不存在**——他们要么接受一个高置信度的猜测（风险自担），要么等待验证闭环（时间成本）。这两者之间的矛盾只能通过**明确标注置信度**来调和，而不是假装早期就能确定。

### 5.2 验证是唯一把「可能性」变成「确定性」的操作

论证说「理论上可能」，验证说「实际上可行」。两者缺一不可：

| 阶段 | 回答的问题 | 消除的不确定性 |
|:-----|:-----------|:---------------|
| 原理分析 | 必要条件是什么？ | 目标分解的完备性 |
| 设计确认 | 约束能否落实为方案？ | 方案的可行性 |
| 部分实现 | 方案能否真的跑起来？ | 实现的正确性 |
| 注入验证 | 故障发生时行为是否符合预期？ | 场景覆盖的完整性 |

> 类比医学诊断：医生不会只看症状就断言「是 X 病」——先做检查（原理分析），再按检查结果排除/确认（验证闭环）。诊断报告的本质不是结论，而是**证据 + 依赖条件**（「满足 A、B、C 三项指标，可确诊」）。直接给结论的医生叫「拍脑袋」，直接给结论的工程师叫「背书」。

## 6. 为什么有人偏好「直接给结果」：五种动机与边界

理解对方的动机，才能设计正确的沟通协议。偏好「直接给结果」的五种动机：

| 动机 | 内在逻辑 | 合理的回应 |
|:-----|:---------|:-----------|
| **① 决策压力** | 排期/成本/资源分配需要数字，不确定性无法入计划 | 给**带风险的分层结论**：最佳/基线/最差三档 + 每档概率 |
| **② 认知负荷** | 条件命题难消化，需要可执行的单一结论 | 结论置顶，依赖清单折叠为附录 |
| **③ 责任转移** | 要专家背书，出了事「是专家说能的」 | 明确标注：结论 = 条件命题，条件变化则结论失效 |
| **④ 时间成本** | 验证很贵，等不起 | 给出「验证的最短路径 + 成本」，让决策者权衡 |
| **⑤ 文化惯性** | 「专家就该拍板」的权威叙事 | 用「分层结论 + 置信度」重塑权威：可靠的专家给的是条件，不是口号 |

### 6.1 什么时候可以直接给结果（边界矩阵）

直接给布尔结论**是允许的**，当且仅当满足以下条件之一：

| 条件 | 例子 | 依据 |
|:-----|:-----|:-----|
| **低风险** | 结论错误代价可忽略 | 试错成本 < 验证成本 |
| **高可逆** | 结论错误可以回滚 | 决策可逆，无需精确 |
| **已验证过** | 同类平台/场景已验证 | 经验 = 已完成的验证闭环 |
| **时间紧急** | 验证来不及且必须拍板 | 接受高置信度猜测 + 标注风险 |

**反之**：高风险 + 不可逆 + 未验证 + 时间充裕 → **必须走完整闭环**。CPU 网络可靠性正属于这一类——训练中断一次的成本（checkpoint 重训 + 集群空转）远超验证成本，因此必须给条件命题。

> 与 [AI 采用与创新引导方法论](../../03_AI/methodology/2026-08-06-ai-adoption-creation-methodology.md) 的「伪精确陷阱」一致：用已知成本评估未知收益分布是伪精确；同样，用早期置信度冒充最终确定性也是伪精确。

## 7. 完整路径示范：CPU 故障网络可靠性案例走一遍

把方法论落到真实案例，展示每个阶段的产出形态。

### 阶段 1：原理分析（回答「必要条件是什么」）
- **产出**：通信路径分类表（数据面/控制面/管理面 × 是否经过 CPU）
- **关键动作**：第一性原理剥离「网络正常工作」的必要条件（供电/时钟/复位/链路/驱动/管理面）
- **遗留问题**：CX7/PEX89104 上游掉链行为——**原理上无法确定**，必须验证

### 阶段 2：设计确认（回答「约束能否落实为方案」）
- **产出**：三层设计（硬件电源域隔离 + 复位互锁 / 固件事件分类引擎 + WDT 策略重设计 / 软件快速恢复 + 调度器状态机）
- **关键动作**：把「不经过 CPU 的路径」设计为可独立存活（PERST# 五分组、电源三域、独立时钟）
- **遗留问题**：BMC 处置策略需实现；OS 网络栈 30s 恢复需实现

### 阶段 3：部分实现与验证（回答「方案能否真的跑起来」）
- **产出**：7 项注入测试清单（sysrq panic / WDT 停心跳 / 温复位 / CPU VR 掉电 / 维护重启 / 恢复计时 / 连续失败 degraded）+ 验收标准
- **关键动作**：向 NVIDIA/Broadcom 索取 CX7/PEX89104 保持行为数据（2 项待验证的闭环路径）

### 阶段 4：最终交付（条件命题形态）

| 目标级 | 定义 | 依赖状态 | 可承诺性 |
|:------|:-----|:---------|:---------|
| **A 级** | 数据面全保持 + 跨组 GPU P2P | 10 项依赖：8 满足，2 待验证 | CX7/PEX89104 固件行为验证通过后可承诺 |
| **B 级** | 数据面保持 + 控制面 30s 重建 | 8 项依赖 | 需 BMC 事件分类 + OS 快速恢复实现后承诺 |
| **C 级** | 管理面存活（远程可管理） | 已具备（V_STBY 独立） | 可承诺 |

> **置信度**：B 级 85%（设计级）→ 实现+验证后 95%；**剩余风险**：厂商固件行为（2 项）+ 跨组 P2P 硬件演进（下一代）

这个交付物**既是结论，也是审计报告**——决策者可以拿着它排期（B 级先承诺）、定风险（2 项待验证）、规划资源（向厂商索取数据）。

## 8. 确认的本质：审计依赖条件

把以上收敛为一句话方法论：

> **确认 = 审计达成目标的必要条件集；结论 = 依赖条件状态的函数。**

| 动作 | 本质 | 输出 |
|:-----|:-----|:-----|
| **深度分析** | 把隐含依赖显性化（第一性原理倒推必要条件） | 依赖清单 |
| **设计确认** | 把显性依赖落实为方案（约束 → 设计决策） | 设计方案 |
| **实现验证** | 把方案依赖状态化（满足 / 未满足 / 待验证） | 状态表 |
| **结论** | 依赖状态的函数 f(依赖₁..依赖ₙ) | 分层结论：全部满足→承诺 / 部分满足→降级或补依赖 / 关键缺失→不可达（止损） |

三个推论：

1. **「深度分析」的价值 = 发现隐含依赖的数量**。大多数人问「能不能」时，脑中的依赖清单是空的或残缺的（「硬件不经过 CPU 应该就能」）——深度分析填补的就是这张清单。清单越完整，后续实现/验证越少返工。
2. **「部分实现与验证」的价值 = 把「待验证」降为「已验证」**。依赖清单上每一项「待验证」，都是一个未消除的风险项；验证闭环是唯一能消除它的操作。
3. **「不能」也是有效结论**——当审计发现关键依赖缺失且无法补齐（如跨组 P2P 硬件上不经过 CPU 且无直连），诚实的结论是「A 级不可达，B 级可达」。**这比「能」更有价值**，因为它把资源从不可能的目标上释放出来。

> 与 [观测认知塑造](2026-08-07-observability-cognition-shaping-framework.md) 闭环：观测决定了你看到哪些指标（依赖清单的完备性），确认决定了你能否据此决策（依赖状态的真实性）。观测是采集层，确认是验证层。

## 9. 对 AI 协作与团队沟通的启示

这个方法论直接回答了用户观察到的现象——「有人要确认时希望给结果，而评估其实需要深度分析 + 实现验证」。落到协作协议上：

### 9.1 AI/工程师的默认动作：给条件命题，不给裸断言

| 用户问「能不能」 | AI/工程师的默认回答结构 |
|:-----------------|:------------------------|
| ❌ 裸断言 | 「能」/「不能」 |
| ✅ 分层结论 | 结论置顶：A/B/C 级目标分别能否达成 |
| ✅ 依赖清单 | 达成每级目标需要哪些条件，每项状态（已设计/需实现/待验证） |
| ✅ 置信度标注 | 每个结论的置信度 + 依据（原理/设计/已验证） |
| ✅ 验证路径 | 待验证项如何闭环（注入测试/厂商数据/成本估算） |

### 9.2 双向协议：明确要「决策输入」还是「完整论证」

- **确认者**（要决策输入）：明确说「我要的是带风险的分层结论 + 时间线」，分析师给「最佳/基线/最差三档 + 验证最短路径」
- **确认者**（要理解过程）：明确说「我要看论证链」，分析师展开依赖清单推导
- **最差的沟通**：确认者要决策输入，分析师给完整论证（信息过载）；或确认者要论证链，分析师给裸结论（无法信任）

### 9.3 判断力 > 执行力的再确认

> 与 [判断价值](../../05_tools/ai-tools/2026-07-20-ai-execution-free-judgment-valuable.md) 一致：AI 时代执行趋于免费，判断决定价值。而判断的原材料正是**条件命题**——能拆出依赖条件的判断才是有依据的判断；裸断言只是转述。

### 9.4 对本系统的自反

本系统的知识库实践正是条件命题的产物：每个深度分析都带「来源 + 基线 + 条件」，每个数据点都标注可验证性；log.md 链接化让每次交付可追溯（审计路径）。**「结论=依赖状态函数」是本系统自带的默认输出协议**——这也是为什么用户与 AI 的协作中，AI 的默认动作是给分层结论 + 依赖清单，而非裸断言。

## 10. 可证伪预测与落地清单

### 可证伪预测

| # | 预测 | 证伪方式 |
|:--|:-----|:---------|
| P1 | CPU 案例中「CX7/PEX89104 上游掉链保持行为」若验证为「不保持」，A 级目标将降为 B 级，且跨组 P2P 需引入硬件直连 | 厂商验证数据显示「保持」→ 预测失败 |
| P2 | 若 B 级承诺（数据面保持 + 控制面 30s 重建）未做注入验证即上线，首次真实 CPU 故障的恢复时间将显著超过 30s | 现网故障恢复记录 < 30s 且无返工 → 预测失败 |
| P3 | 团队中「要结果型确认者」占比越高，未经验证就承诺「能」的结论越多，交付期返工率越高 | 若返工率与确认风格无相关性 → 预测失败 |

### 落地清单（下次评估「能不能」时）

- [ ] 把目标拆成**分级目标**（A/B/C），不要问「能不能」，问「每级能不能」
- [ ] 用第一性原理列出**必要条件集**（供电/时钟/复位/链路/驱动/控制面/管理面…）
- [ ] 给每项依赖标状态：`已设计 / 需实现 / 待验证`
- [ ] 结论形态 = 分层结论 + 依赖清单 + 置信度 + 验证路径（**禁止裸断言**）
- [ ] 判断是否可直接给结果：风险 × 可逆性 × 已验证 × 时间（4 因子矩阵）
- [ ] 待验证项必须有**闭环动作**（注入测试/厂商数据/替代方案），不能挂着
- [ ] 交付时明确接收方要「决策输入」还是「完整论证」，避免信息过载或信任缺失
