## 1. 框架概览

### 1.1 为什么要一个可验证的架构分析框架

架构决策是技术领域**成本最高、影响最持久、纠错代价最大**的决策类型。一个错误的架构决策：

- 在编码阶段发现：损失 1×
- 在测试阶段发现：损失 10×
- 在上线后发现：损失 100×
- 在架构固化后发现：损失 1000×（系统重写/迁移成本）

然而现实中，大量架构评审依赖"架构师直觉"或"行业共识"，缺少**可验证的推理链条**。本框架的目标是将架构评审从**意见分歧**升级为**事实分歧**——我们争论的不是"谁对"，而是"哪个数据来源更可靠、哪个推理步骤是否缺失"。

### 1.2 六模块一矩阵架构

本框架由 **6 个独立模块 + 1 个集成矩阵** 组成，逐个覆盖架构分析的完整推理链：

```text
输入: 架构方案
    |
    +--> [A] 数据合理性验证     <- 所有量化断言必须通过此关
    +--> [B] 技术与现实可行性   <- 从物理/经济/时间三维验证
    +--> [C] 假设合理性论证     <- 显式化所有隐藏前提
    +--> [D] 依赖条件与复用验证 <- 复用的基础能否站住脚
    +--> [E] 工作量估计         <- 从分解到交叉验证
    +--> [F] 多维度最优性分析   <- 在给定约束下是否最优
         |
         v
    [集成评判矩阵] -> 最终决策
```

**核心原则**: 6 个模块**顺序执行**，前一个模块的结论是后一个模块的输入。若某个模块未通过（红灯），**停止后续分析**，先解决当前问题。

### 1.3 输出三色信号

每个模块的输出以三色信号表达判断结论：

| 信号 | 含义 | 后续行动 |
|:----:|:-----|:---------|
| 🟢 **通过** | 该维度验证通过 | 进入下一模块 |
| 🟡 **存疑** | 有风险但可接受，需标注风险缓解措施 | 记录风险条目后进入下一模块 |
| 🔴 **否决** | 该维度通不过，方案不可行 | 停止，返回修改 |

## 2. 第一性原理：架构决策的本质约束

在进入具体模块之前，先明确架构决策背后的**根本约束**。任何架构方案都受到以下三层约束的边界限制，超出即不可行。

### 2.1 物理层约束（不可突破）

源自物理学基本定律，任何架构方案都**不能违反**：

| 约束类型 | 具体内容 | 在服务器架构中的体现 |
|:---------|:---------|:---------------------|
| **信息论** | 信道容量 ≤ Shannon 极限 | 信号完整性：PCIe/NVLink 眼图裕量、BER 下限、信号速率与信道损耗的权衡 |
| **热力学** | 热量必须排出，COP ≤ 理论最大值 | 散热设计：TDP 与冷却能力的匹配、液冷系统的最低功耗 |
| **电磁学** | 信号速度 ≤ c，串扰随频率升高 | SI 设计：走线长度限制、阻抗匹配、串扰隔离 |
| **材料科学** | 热膨胀系数、介电常数、导电率 | PCB 材料选择、焊点可靠性、connector 承载电流上限 |
| **量子力学** | 隧穿效应限制最小线宽 | 制程工艺的物理极限 |

**自检方法**: 对于方案中每个声称的性能指标，问："这个指标是否违反了已知的物理定律？如果是，需要怎样的前提条件才能接近？"

### 2.2 经济层约束（不可持续则不可行）

| 约束类型 | 具体内容 |
|:---------|:---------|
| **规模经济** | 单位成本随产量增加而降低，反之小众方案单价高 |
| **技术成熟度曲线** | 新技术初期成本高、可靠性低，大规模采用需要时间 |
| **TCO 边界** | 采购 + 运维 + 淘汰的总成本不能超过业务收益 |
| **机会成本** | 选 A 方案意味着放弃在 B 方案上投入的可能收益 |

### 2.3 工程层约束（可协商但有代价）

| 约束类型 | 具体内容 |
|:---------|:---------|
| **时间窗口** | 市场窗口不等人，架构方案必须在可用时间内交付 |
| **团队能力** | 团队的技能集决定了能做什么、不能做什么 |
| **生态兼容** | 必须与上下游生态兼容，否则集成成本过高 |
| **合规/安全** | 法律法规不可违反 |

## 3. 模块A：数据合理性验证

> **核心问题**: 架构方案中引用的所有数据——性能指标、容量、延迟、带宽、成本——是否可信？

这是最容易被忽视但最关键的环节。**没有经过验证的数据，后续所有推理都是空中楼阁。**

### 3.1 数据三角验证法则

每个关键数据需要**至少三种独立来源**交叉验证：

```text
        +--------------+
        |  官方规格书   |  (厂商 datasheet、标准规范)
        +--------------+
        |  独立实测     |  (第三方评测、内部 POC 数据)
        +--------------+
        |  理论推导     |  (从第一性原理计算最大值/上限)
        +--------------+
```

**优先级与可信度排序**:

| 来源类型 | 可信度 | 说明 | 典型陷阱 |
|:---------|:------:|:-----|:---------|
| 标准组织规范 | ⭐⭐⭐⭐⭐ | JEDEC/IEEE/PCI-SIG/OCP 官方文档 | 标准 = 理论最大值，实际实现打折扣 |
| 厂商官方规格书 | ⭐⭐⭐⭐ | Datasheet 中 Test Conditions 明确的数据 | 选"最佳工况"数据而非"最差工况" |
| 第三方独立评测 | ⭐⭐⭐⭐ | 正规测试机构、学术论文 | 注意测试条件与自己的场景是否一致 |
| 第一性原理推导 | ⭐⭐⭐ | 从基本定律算出理论上界 | 忽略实际工程折损因子 |
| 行业分析报告 | ⭐⭐ | IDC/Gartner/券商研报 | 作者立场、方法论不透明 |
| 技术博客/社区 | ⭐ | 个人经验分享 | 场景差异大、无复现条件 |
| 口头承诺/PPT | ⭐ | 售前演示、内部会议 | 无任何验证，视为噪声 |

### 3.2 数据合理性检查清单

对每一条量化断言，逐项检查：

**3.2.1 完整性（四要素）**

一条完整的量化断言必须包含四个要素，缺少任何一个即不合格：

| 要素 | 含义 | 反例 | 正例 |
|:-----|:-----|:-----|:-----|
| **数值** | 具体数字 | "吞吐量大幅提升" | "吞吐量 2.3 GB/s" |
| **单位** | 度量衡 | "延迟 5" | "延迟 5 μs" |
| **对比基线** | 和什么比 | "性能提升 50%" | "性能提升 50%（vs PCIe Gen5 x16, 128B payload）" |
| **测试条件** | 什么环境下测得 | "带宽 32 GB/s" | "带宽 32 GB/s（PCIe Gen5 x16, 单方向, 25°C）" |

**自检查询**: 随机挑 3 条量化断言，用 `web_fetch` 从独立源验证数值。

**3.2.2 时效性**

| 数据类型 | 可接受时效 | 说明 |
|:---------|:----------:|:-----|
| 半导体制程/性能 | ±6 个月 | 迭代极快，1 年前的数据已过时 |
| 服务器系统规格 | ±12 个月 | 产品周期约 18-24 个月 |
| 市场价格 | ±3 个月 | 波动大，须标注来源日期 |
| 标准规范 | 以最新版为准 | 引用时必须注明版本号 |
| 行业趋势 | ±18 个月 | 大趋势相对稳定 |

**3.2.3 场景匹配度**

- 这个数据是在**我的场景**下测得的，还是不同场景？
- 如果来源场景与我的场景不同，差异在哪？差异的影响方向（偏大还是偏小）？
- **致命错误**: 拿实验室理想环境的数据直接套用生产环境

**3.2.4 量纲转换验证**

- 单位换算是否正确？（1 GB = 10^9 bytes？还是 2^30 bytes？——网络世界用 10 进制，存储用 2 进制）
- 方向性是否正确？（双向带宽 = 2× 单方向带宽？还是全双工本身就双向？）
- 时序推演是否一致？（峰值 × 持续时间 ≤ 缓存容量？）

### 3.3 偏差校准公式

当只能拿到近似数据时，使用偏差校准：

```text
校准值 = 来源值 × 场景因子 × 工程折损因子
```

**工程折损因子经验值**（服务器领域）：

| 数据类型 | 典型折损 | 说明 |
|:---------|:--------:|:-----|
| 厂商宣称带宽 | × 0.7~0.85 | 扣除协议开销、链路训练、重传 |
| 实验室峰值性能 | × 0.6~0.8 | 扣除实际工作负载损耗 |
| 模拟仿真结果 | × 0.5~0.7 | 扣除边界条件未覆盖的部分 |
| 理论计算上限 | × 0.3~0.5 | 实际工程实现的典型效率 |

### 3.4 来源可追溯要求

每条被用于关键决策的数据，必须标注**可验证的来源引用**，格式：

```text
[数据断言] -> 来源: [文档名称/链接], 报告日期: [YYYY-MM-DD], 测试条件: [条件], 数据有效期: [日期]
```

**不可接受**: "行业普遍认为……"、"据可靠消息……"、"大家都知道……"

## 4. 模块B：技术与现实可行性

> **核心问题**: 这个架构在技术上是否可工程实现？在现实环境中是否可部署、可运维？

### 4.1 技术可行性四层检验

从底层到顶层逐层检验：

**第1层：物理可行性**

| 检查项 | 具体内容 | 判断标准 |
|:-------|:---------|:---------|
| 信号完整性 | 信号速率 × 走线长度 ≤ 信道能力 | 眼图裕量 ≥ 厂商要求的最小值 |
| 功耗密度 | 单位面积功耗 ≤ 散热能力 | 是否超过当前冷却技术极限 |
| 空间约束 | 组件物理尺寸 ≤ 可用空间 | 是否存在物理干涉 |
| 供电能力 | 峰值功耗 ≤ PSU + VR 总容量 | 是否考虑启动浪涌、动态响应 |

**第2层：工程可行性**

| 检查项 | 具体内容 |
|:-------|:---------|
| 关键器件可获得性 | Lead time？独家供应风险？EOL 风险？ |
| 工艺能力 | PCB 层数/线宽/过孔是否在制造商能力范围内 |
| 测试覆盖 | 关键路径是否有测试点？测试覆盖率目标？ |
| DFX 验证 | DFM/DFT/DFS 是否已做，是否有 issue 未关闭 |

**第3层：系统可行性**

| 检查项 | 具体内容 |
|:-------|:---------|
| 子系统兼容 | 所有子系统（计算/存储/网络/散热/供电）是否匹配工作 |
| 软件生态 | OS/Driver/FW/BMC 是否支持硬件特性 |
| 性能线性度 | 资源扩展时性能是否线性增长（或至少可预测） |
| 可靠性预算 | 各组件 MTBF 是否满足系统整体可靠性目标 |

**第4层：运维可行性**

| 检查项 | 具体内容 |
|:-------|:---------|
| 部署便利性 | 上架、布线、配置是否需要特殊工具或培训 |
| 可维护性 | FRU 替换难度、MTTR 是否达标 |
| 监控告警 | 关键指标是否可监控、阈值是否合理 |
| 故障隔离 | 单点故障会不会扩散为系统级故障 |
| 版本管理 | FW/Bios/Driver 升级路径是否清晰 |

### 4.2 现实可行性：外部约束检查

| 约束维度 | 检查项 | 验证方法 |
|:---------|:-------|:---------|
| **供应链** | 关键器件 ≥ 2 家供应商可选？ | 查询供应商 lead time 和 allocation 状态 |
| **法规合规** | 3C/CE/FCC/RoHS/WEEE？ | 对照目标市场的法规清单 |
| **时间窗口** | 方案能否在市场窗口关闭前交付？ | 倒排工期、识别关键路径和瓶颈 |
| **人力** | 团队是否有相关经验？ | 技能矩阵对齐、识别培训需求 |
| **预算** | NRE + 量产成本是否在预算内？ | BOM 核算 + NRE 分拆 |
| **客户接受度** | 客户是否接受新技术架构？ | 客户调研、POC 验证 |

### 4.3 POC 验证的要求

当技术可行性存在不确定性时，**必须**做 POC（概念验证）。POC 的设计要求：

| 要素 | 要求 |
|:-----|:------|
| **验证目标** | 每次 POC 只验证一个假设，明确定义通过/不通过的量化标准 |
| **最小可验证范围** | 用最小的系统/接口/场景验证最大风险点 |
| **对照组** | 必须有对比基线（当前方案或业界参考） |
| **时长** | 足够覆盖典型工作模式（含启动、稳态、高峰、异常恢复） |
| **失败预案** | 假如 POC 不通过，明确下一步方案（B 计划是啥） |

## 5. 模块C：假设合理性论证

> **核心问题**: 架构方案中做了哪些不成立的假设？这些假设是否合理？

每个架构方案都基于一组**显式和隐式假设**。识别并验证这些假设，是架构评审最重要的价值之一。

### 5.1 假设显式化四象限

将所有假设按 **可验证性** 和 **重要性** 分类：

```text
                  重要性
                  高
            +-----------+-----------+
            |   致命盲区  |   核心假设  |
    可验证  |  (立刻验证) |  (必须验证) |
    性 低   +-----------+-----------+
            |   次要假设  |   背景假设  |
            |  (接受风险) |  (有感知)   |
            +-----------+-----------+
                  低
```

| 象限 | 特征 | 处理方式 |
|:-----|:-----|:---------|
| **核心假设**（高重要×高可验证） | "NVLink 带宽足够承载训练通信" | 必须用数据验证，否则不准往下走 |
| **致命盲区**（高重要×低可验证） | "国产替代芯片性能与 NVIDIA 相当" | 是最危险的地方，需专门设计 POC 验证 |
| **背景假设**（低重要×低可验证） | "未来 3 年流量年增长 50%" | 有感知即可，做敏感性分析 |
| **次要假设**（低重要×高可验证） | "机柜功率密度 40kW" | 快速验证，不过高成本 |

### 5.2 假设验证清单

针对每个识别出的假设，按以下维度验证：

**5.2.1 假设的可操作化**

把模糊假设转化为可测量的断言：

| 模糊假设 | 可操作化后的断言 | 验证方法 |
|:---------|:-----------------|:---------|
| "这个方案性能好" | "在 SPECrate 2017 上得分 ≥ 200" | 找已发布的 benchmark 结果 |
| "用户会接受" | "70% 的调研用户表示愿意迁移" | 做客户调研 |
| "扩展性足够" | "从 4 节点扩展到 16 节点时加速比 ≥ 14" | 做扩展性测试 |
| "新接口是未来趋势" | "2027 年市场份额 ≥ 30%" | 查行业分析师预测 |

**5.2.2 假设的敏感度**

变化 10% 会不会改变结论？

| 敏感度级别 | 定义 | 处理方式 |
|:-----------|:-----|:---------|
| **高敏感** | 假设值变化 ±10%，结论完全反转 | 必须精确验证，加安全边界 |
| **中敏感** | 假设值变化 ±30%，结论开始松动 | 取合理保守值 |
| **低敏感** | 假设值变化 ±50%，结论基本不变 | 可用估算值 |

**5.2.3 假设的共变关系**

多个假设之间是否独立？如果 A 假设不成立，B 假设会如何？

> **典型反模式**: 同时假设"流量高速增长"和"单位成本大幅下降"——这两个假设往往不是独立的，流量增长会摊薄固定成本，但也可能增加运维成本。

### 5.3 假设退路检查

对每个核心假设，问：

- 如果这个假设不成立，有退路吗？
- 架构设计是否预留了调整空间？
- 假设失效后回到原点的成本是多少？

**自检话术**: 「如果这个假设错得离谱，这个架构还能活吗？」

## 6. 模块D：依赖条件与复用基础验证

> **核心问题**: 架构所依赖的外部条件是否成立？声称的"复用"基础是否真实存在？

### 6.1 依赖条件六维检查

架构方案依赖的外部条件按以下六维逐项检查：

**D1: 技术依赖**

| 检查项 | 验证方法 |
|:-------|:---------|
| 关键技术是否已存在（而非在研）？ | 查成熟度等级（TRL ≥ 7 为可用） |
| 依赖的版本/规格是否已冻结？ | 查 spec 版本号、变更频率 |
| 是否有替代方案如果主依赖失败？ | 技术选型时考虑 Plan B |
| 技术依赖的 Roadmap 是否与项目对齐？ | 对比两方时间线 |

**D2: 供应商依赖**

| 检查项 | 验证方法 |
|:-------|:---------|
| 是单供应商还是多供应商？ | 查询市场供应格局 |
| 供应商的历史交付可靠性？ | 历史项目评价 |
| 供应商是否可能被收购/EOL 该产品线？ | 供应商财报/产品策略分析 |
| 关键器件是否有 allocation 风险？ | 查询供应状态 |

**D3: 标准/协议依赖**

| 检查项 | 验证方法 |
|:-------|:---------|
| 所依赖的标准是否已正式发布？ | 查标准组织官网 |
| 不同厂商实现之间的互操作性验证过吗？ | 查互操作性测试报告 |
| 是否存在专利/许可壁垒？ | 专利检索 |

**D4: 工具链依赖**

| 检查项 | 验证方法 |
|:-------|:---------|
| 开发/测试/部署工具是否就绪？ | 工具清单和状态跟踪 |
| 工具版本是否兼容上下游？ | 版本矩阵验证 |
| 是否需要新的工具链？学习成本？ | 培训计划和学习曲线评估 |

**D5: 数据/基础设施依赖**

| 检查项 | 验证方法 |
|:-------|:---------|
| 训练/测试数据的质量和规模是否满足？ | 数据质量报告 |
| 测试环境是否具备（硬件/网络/存储）？ | 环境清单 |
| 生产环境的容量规划是否考虑新架构？ | 容量规划文档 |

**D6: 组织/人才依赖**

| 检查项 | 验证方法 |
|:-------|:---------|
| 团队是否有维护该架构的能力？ | 技能矩阵对比 |
| 关键人员是否有离职风险？ | 人力资源风险评估 |
| 是否需要外部顾问/原厂支持？ | 支持合同/预算 |

### 6.2 复用基础验证

"复用"是最常见的架构假设陷阱。声称"可以复用现有模块/组件/代码"时，必须验证：

**6.2.1 复用条件验证框架**

| 验证维度 | 检查项 | 不通过的风险 |
|:---------|:-------|:------------|
| **功能匹配** | 被复用组件的功能是否 100% 覆盖新需求？ | 缺功能 → 加适配层 → 越加越复杂 |
| **接口兼容** | 接口协议/数据格式/语义是否完全一致？ | 接口适配成本可能超过重写 |
| **性能余量** | 被复用组件在当前负载下是否还有余量？ | 全系统性能瓶颈 |
| **质量状态** | 被复用组件是否有已知 Bug/技术债务？ | 带病复用，累积风险 |
| **维护状态** | 被复用组件是否还有人维护？ | 无人维护 → 技术债务加速累积 |
| **文档完整性** | 设计文档/API 文档/测试文档是否完整？ | 无人能理解该组件的完整行为 |

**6.2.2 复用 vs 重写的决策规则**

```text
收益 = 新需求开发成本 - 复用适配成本 - 复用引入的风险成本
如果收益 < 0 -> 重写
如果收益 > 0 且 风险可控 -> 复用
```

**6.2.3 "复用幻觉"常见形态**

| 形态 | 症状 | 破解方法 |
|:-----|:-----|:---------|
| **拿过来就能用** | 声称 XX 模块改改配置就行 | 穿行测试：实际走一遍适配流程 |
| **接口差不多** | "接口大部分兼容" | 列完整接口差异表 |
| **性能足够** | "负载不大，够用" | 用实际数据做容量推演 |
| **没人动过** | "代码一直好好的" | 检查已知 Bug 列表、代码覆盖率 |
| **就是旧了点** | "十几年的代码，稳定" | 评估技术债务和框架迁移成本 |

## 7. 模块E：工作量估计

> **核心问题**: 完成这个架构需要多少时间、多少人、多少资源？估计是否靠谱？

### 7.1 工作量分解结构（WBS）

将架构实现分解到**可独立估计的最小任务单元**（通常 ≤ 5 人天），然后从下往上汇总。

**分解维度**:

- 按子系统（计算/存储/网络/管理/散热/供电）
- 按阶段（设计/开发/集成/测试/部署/验收）
- 按工种（硬件/软件/FW/结构/测试/认证）

### 7.2 三重估计法

对每个 WBS 单元，给出三个估计值：

```text
乐观估计(O): 一切顺利，无阻碍
最可能估计(M): 正常情况，有预期阻碍
悲观估计(P): 多灾多难，最坏情况

期望工期 = (O + 4×M + P) / 6
标准差 = (P - O) / 6
```

**汇总原则**:

- 关键路径上的工期**不可直接相加**——串行任务的总工期 = 各任务期望工期之和
- 并行任务的工期 = 最长路径工期（而非平均）
- 考虑**依赖延迟**：上游延误 + 排队等待时间

### 7.3 工作量校准因子

原始估计需按以下因子校准：

| 因子 | 校准范围 | 说明 |
|:-----|:---------|:-----|
| **沟通开销** | × 1.1~1.4 | 团队越大，沟通开销越高 |
| **学习曲线** | × 1.2~2.0 | 新技术/新领域 ≥ 1.5 |
| **集成测试** | × 1.2~1.5 | 子系统越多，集成工作量越大 |
| **文档/合规** | × 1.1~1.2 | 交付物要求 |
| **管理层审查** | × 1.05~1.15 | 内部审批/汇报循环 |
| **不可预见事件** | × 1.15~1.25 | 按项目复杂度和历史数据 |

**实际工作量 = 原始估计 × ∏(校准因子)**

### 7.4 工作量交叉验证

| 验证方法 | 说明 | 适用阶段 |
|:---------|:-----|:---------|
| **类比法** | 和过去的类似项目对比 | 早期 |
| **参数法** | 用历史产能数据 × 工作量因子 | 需求明确后 |
| **三点估算法** | 上述 PERT 方式 | 分解完成后 |
| **Delphi 法** | 多人独立估计后取一致性 | 任何阶段 |
| **业内基准** | 查同行业类似项目的实际工时 | 任何阶段 |

**自检话术**: 「如果工作量翻倍，项目还在预算和时间范围内吗？如果减半，能完成吗？」

### 7.5 工作量常见陷阱

| 陷阱 | 症状 | 预防 |
|:-----|:-----|:-----|
| **乐观偏差** | 只考虑"正常路径"，忽略异常 | 强制用三点法，P 取最坏情况 |
| **集成低估** | 只算各子系统的独立开发，忽略集成测试 | 集成工作量 = 子系统数 × 子系统接口数 × 因子 |
| **平滑忽略** | 假设所有资源随时可用 | 加入资源争抢排队模型 |
| **分工幻觉** | 认为多人并行工作等于人数叠加效率 | Brooks 定律：人月不可互换 |
| **隐藏假设** | 假设"不会有需求变更" | 预留 20-30% 缓冲 |

## 8. 模块F：多维度最优性分析

> **核心问题**: 在给定的约束条件下，这个方案是否**真的**最优？还是"看起来不错"？

### 8.1 最优性的正确理解

"最优"不是绝对概念，而是**在给定条件下的相对概念**：

```text
在约束集 C 下，方案 X 是 "最优" 的表达 =
  ∀Y ≠ X: f(X) ≥ f(Y)
  其中 f 是评价函数，C 是约束条件集
```

因此多维度最优性分析的核心是：**明确约束集 C 和评价函数 f**。

### 8.2 约束集显式化

在比较方案之前，先列出所有约束条件并区分类型：

| 约束类型 | 特征 | 示例 | 处理方式 |
|:---------|:-----|:-----|:---------|
| **硬约束** | 违反即方案不可行 | 机柜高度 ≤ 42U、功耗 ≤ 机柜供电容量 | 方案筛选的截止条件 |
| **软约束** | 违反会扣分但方案仍可行 | 成本预算偏好 ±20% | 加权评分中体现 |
| **偏好约束** | 主观倾向，无硬性标准 | "优先使用国产器件" | 可用加权偏置表达 |

### 8.3 评价维度

至少从以下维度评价方案（可根据领域调整权重）：

**P0 维度（必须评估）**:

| 维度 | 评价指标 | 量化方式 |
|:-----|:---------|:---------|
| **性能** | 吞吐量/延迟/容量 | 基准测试值（标注条件） |
| **成本** | BOM/NRE/运维/全生命周期 TCO | 按 3-5 年折旧核算 |
| **可靠性** | MTBF/可用性/年均故障数 | FTA/FMEA 分析结果 |
| **可扩展性** | 扩展上限/线性度/扩展代价 | 扩展测试数据 |
| **时间** | TTM（上市时间） | 从立项到量产的时间线 |

**P1 维度（强烈建议评估）**:

| 维度 | 评价指标 | 量化方式 |
|:-----|:---------|:---------|
| **功耗效率** | 性能/瓦 | SPECpower 或等效指标 |
| **空间效率** | 性能/U | 单位机柜空间产出 |
| **可维护性** | MTTR/FRU 数量/替换复杂度 | 维护演练测试 |
| **兼容性** | 与现有基础设施的匹配度 | 接口/协议/物理兼容清单 |
| **供应链风险** | 关键器件供应商数/lead time | 供应商风险评估 |

**P2 维度（可选，视场景评估）**:

| 维度 | 说明 |
|:-----|:------|
| 技术成熟度 | TRL 等级、工程经验 |
| 生态丰富度 | 配套工具链、社区支持、人才市场 |
| 安全特性 | 硬件安全模块、固件签名、可信根 |
| 可观测性 | 监控/日志/调试能力 |
| 环境适应性 | 温度/湿度/振动/海拔范围 |

### 8.4 方案空间扫描：避免二元对立

**反模式**: 只考虑两个方案（方案 A 和方案 B），然后强行二选一。

**正确做法**: 扫描方案空间的全貌，包括：

| 方案类型 | 说明 |
|:---------|:------|
| **极端方案** | 纯方案 A、纯方案 B |
| **混合方案** | A 和 B 的组合（A 做计算、B 做存储） |
| **分层方案** | 先跑 A 在某些场景，逐步过渡到 B |
| **最小可行方案** | 先做最核心功能的"骨架" |
| **分阶段方案** | 版本 1 用 A、版本 2 切到 B |
| **不做的方案** | 什么都不做 = 保留现状，作为基准参考 |

### 8.5 加权评分矩阵

| 维度 | 权重 | 方案A | 方案B | 方案C | 不做的 |
|:-----|:----:|:-----:|:-----:|:-----:|:------:|
| 性能 | 25% | 9(2.25) | 7(1.75) | 6(1.50) | 3(0.75) |
| 成本 | 20% | 5(1.00) | 8(1.60) | 7(1.40) | 10(2.00) |
| 可靠性 | 20% | 8(1.60) | 6(1.20) | 7(1.40) | 9(1.80) |
| 可扩展性 | 15% | 9(1.35) | 5(0.75) | 7(1.05) | 2(0.30) |
| 时间 | 10% | 4(0.40) | 7(0.70) | 8(0.80) | 10(1.00) |
| 功耗效率 | 10% | 7(0.70) | 6(0.60) | 8(0.80) | 5(0.50) |
| **总分** | **100%** | **7.30** | **6.60** | **6.95** | **6.35** |

**重要规则**:

1. 权重和评分数值必须**有依据**（来源或推理），不能凭感觉
2. 评分必须**有明确的分档定义**（如 1-3=不可接受, 4-6=可接受, 7-9=优秀, 10=完美）
3. "不做"方案（现状）必须始终作为参考基线
4. 如果两个方案总分差 < 0.5，说明无显著差异，需考虑非量化因素

### 8.6 敏感性分析

对权重分配做敏感性测试：

```text
权重 ±20%，方案排名是否变化？
如果变化 -> 结论对权重敏感，需谨慎
如果不变化 -> 结论稳健
```

### 8.7 最优性证明方法

| 方法 | 适用场景 | 做法 |
|:-----|:---------|:-----|
| **优势论证** | 方案 A 在所有维度都优于 B | 简单，但现实中很少见 |
| **帕累托前沿** | 多目标优化，无法同时最优 | 画出帕累托前沿，确认方案在前沿上 |
| **权衡分析** | 方案有取舍 | 量化每个取舍点的收益/损失比 |
| **决策树** | 有不确定性分支 | 各分支的概率 × 收益，选期望值最高的 |
| **博弈分析** | 需考虑对手/市场反应 | 各参与方的收益矩阵 |

## 9. 集成评判矩阵与决策流程

### 9.1 集成评判矩阵

把 6 个模块的结论汇总为一个决策表：

| 模块 | 结论 | 关键发现 | 风险等级 |
|:-----|:----:|:---------|:--------:|
| [A] 数据合理性 | 🟢/🟡/🔴 | 最弱的数据是？偏差最大的数据是？ | 高/中/低 |
| [B] 可行性 | 🟢/🟡/🔴 | 最大的技术风险是？最大的外部风险是？ | 高/中/低 |
| [C] 假设合理性 | 🟢/🟡/🔴 | 最危险的假设是？敏感度最高的假设是？ | 高/中/低 |
| [D] 依赖/复用 | 🟢/🟡/🔴 | 最脆弱的依赖是？"复用幻觉"的风险？ | 高/中/低 |
| [E] 工作量 | 🟢/🟡/🔴 | 工作量估算可信区间？最不确定的 WBS 单元？ | 高/中/低 |
| [F] 最优性 | 🟢/🟡/🔴 | 方案是否在帕累托前沿上？ | 高/中/低 |

### 9.2 决策规则

| 综合信号 | 决策 | 后续行动 |
|:---------|:-----|:---------|
| **全 🟢** | **批准** | 进入详细设计阶段 |
| **最多1个 🟡** | **有条件批准** | 标注风险点，制定缓解措施，设定 check gate |
| **≥2个 🟡** | **返回修改** | 列出需补充的分析项，指定再评审时间 |
| **≥1个 🔴** | **否决** | 退回重新设计，明确否决的原因和方向建议 |

### 9.3 架构评审会议流程

```text
Step 1: 架构师陈述方案（不超过15分钟）
Step 2: 评审员按模块逐项质询（自下而上，单项不过即停止）
Step 3: 填集成评判矩阵
Step 4: 决策（通过/条件通过/打回/否决）
Step 5: 输出会议纪要（含否决理由+改进建议+责任人）
```

## 10. 常见失效模式与反模式

### 10.1 模块A 失效模式

| 模式 | 症状 | 预防 |
|:-----|:-----|:------|
| **数据移植** | 拿别人场景的数据当自己的 | 每次引用数据前问"什么条件下测得" |
| **数据修饰** | 只报最好不报最差 | 强制要求提供 P10/P50/P90 数据 |
| **占位符数据** | "这个后面再测" | 不接受无数据的断言 |
| **精度幻觉** | 三位有效数字的精度保证 | 标注误差范围 |

### 10.2 模块B 失效模式

| 模式 | 症状 | 预防 |
|:-----|:-----|:------|
| **过度承诺** | "理论可行"当"工程可行" | 要求展示工程折损因子 |
| **演示陷阱** | Demo 环境不等于生产环境 | POC 必须在近似生产条件下跑 |
| **忽略集成** | 各子系统单独测都通，合起来不通 | 强制做集成测试计划 |
| **运维遗忘** | 只考虑开发不考虑运维 | 做运维 Checkist |

### 10.3 模块C 失效模式

| 模式 | 症状 | 预防 |
|:-----|:-----|:------|
| **假设潜藏** | 没说出来的假设最多也最危险 | 强迫列假设清单 |
| **乐观偏移** | 所有假设都是正面 | 让评审员扮演"魔鬼代言人" |
| **假设固化** | 项目中期假设变了但没人发现 | 在里程碑时重新验证假设 |
| **互赖忽视** | 假设 A 和 B 相互依赖但未识别 | 列假设关系矩阵 |

### 10.4 模块D 失效模式

| 模式 | 症状 | 预防 |
|:-----|:-----|:------|
| **复用幻觉** | "改改就能用" → 改了大量代码 | 穿行测试验证 |
| **黑盒依赖** | 依赖的内部机制不了解 | 要求提供依赖组件的核心原理 |
| **供应商绑定** | 被单一供应商锁定 | 评估迁移成本，设计解耦层 |
| **标准浮躁** | "支持 XX 标准"但未验证互操作性 | 查互操作性认证 |

### 10.5 模块E 失效模式

| 模式 | 症状 | 预防 |
|:-----|:-----|:------|
| **计划谬误** | 系统性地低估工作量 | 参考历史项目的实际完成时间 |
| **学生综合症** | 所有任务压到最后一刻 | 设中间里程碑 |
| **帕金森定律** | 给多少时间花多少时间 | 设紧凑时间盒 |
| **范围蔓延** | 需求不断扩展 | 用变更控制流程 |

### 10.6 模块F 失效模式

| 模式 | 症状 | 预防 |
|:-----|:-----|:------|
| **二元对立** | 只考虑两个极端方案 | 列出至少 5 个候选方案 |
| **锚定效应** | 第一个被提出的方案占便宜 | 方案陈述顺序随机化 |
| **光环效应** | 某方面优秀就认为它整体好 | 各维度独立评分 |
| **确认偏差** | 只找支持预设结论的证据 | 强制列出每个方案的风险 |
