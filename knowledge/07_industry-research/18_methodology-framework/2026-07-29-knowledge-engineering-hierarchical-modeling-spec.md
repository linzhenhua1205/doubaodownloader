## 1. 核心命题：层级隔离是分布式知识库的前提

### 1.1 问题起源

> "Linux 跟 log 要放在最底层的那个文件里面。上一层的描述文件就描述文件，描述文件夹就行。不要跨层描述底层的信息，这样就方便分布式的一个处理。"

这句话点出了知识库设计的**核心架构决策**：

- **层级隔离 = 分布式处理的前提**
- 跨层描述 = 制造耦合 = 破坏分布式能力
- 每一层只描述自身 = 支持并行读取、增量处理、局部更新

### 1.2 类比：软件工程中的分层架构

| 软件分层 | 知识库层级 |
|:---------|:-----------|
| 上层调用下层接口，不关心下层实现 | 上层实体只通过关系边引用下层，不内嵌下层详情 |
| 层间通过API通信 | 层间通过图谱关系连接 |
| 修改下层不波及上层 | 更新底层不影响上层实体描述 |

## 2. 层级实体建模的核心约束

### 2.1 总则

> **当前层级实体，只描述本层级载体对应的对象。**

- 如果本层级存在**文件**：描述文件属性、路径、权限、内容特征
- 如果本层级只有**文件夹**：仅描述目录属性、挂载规则、目录用途
- **严禁**在实体描述中内嵌其他层级的信息

### 2.2 层级信息填写准则

| 实体层级 | 可以写 | 禁止写 |
|:---------|:-------|:-------|
| 顶层（业务域/集群） | 业务范围、集群规模、拓扑架构 | 底层OS参数、日志存储路径、内核配置 |
| 中层（服务/中间件） | 服务配置、端口、依赖关系 | inode数量、日志轮转策略 |
| 底层（OS/Log） | 内核参数、日志目录结构 | 上层业务逻辑（用关系引用） |

## 3. Linux与日志的底层归属原则

### 3.1 核心规则

**Linux系统、日志（log）统一归属最底层实体**，在知识库中作为独立的底层节点：

```text
上层：业务服务、中间件、应用模块、集群、业务域
    v 通过关系边引用
底层：宿主机OS (Linux) / 日志文件目录 (log)
```

### 3.2 正确做法 vs 错误做法

**❌ 错误示例**（上层实体跨层描述底层信息）：

```yaml
# 业务服务A的描述
name: order-service
description: 订单处理服务，日志存储于/var/log/order/
            日志轮转策略为每天rotate一次，保留30天
            使用ext4文件系统，inode数量充足
```

**✅ 正确示例**（上层只建立关联边，不内嵌底层详情）：

```yaml
# 业务服务A的描述
name: order-service
description: 订单处理服务
relations:
  - type: 日志写入
    target: log/order-service-log
  - type: 运行于
    target: os/linux-prod-node-01
```

### 3.3 为什么这是分布式处理的前提

```text
❌ 跨层描述方式：
业务A.md 包含了 { 业务信息 + OS信息 + 日志信息 + 文件系统信息 }
    ↕ 修改OS参数 -> 需要更新业务A.md -> 同步困难

✅ 层级隔离方式：
业务A.md = 只描述业务
os.md = 只描述OS
log.md = 只描述日志
关系图 = 独立维护连接
    ↕ 修改OS参数 -> 只更新os.md -> 增量、独立
```

## 4. 信息与关系彻底解耦

### 4.1 核心设计决策

> **实体正文 = 静态属性（本层自有配置、参数、规格、当前对象定义）**
> **图谱边（关系库）= 对象之间的连接逻辑**

**绝不把"关联谁"写进实体描述文本里。**

### 4.2 解耦后的职责边界

| 维度 | 实体文件本身 | 关系图独立维护 |
|:-----|:------------|:---------------|
| 内容 | 自身静态属性 | 实体间的连接逻辑 |
| 示例 | 路径、参数、规格、配置 | 依赖、引用、调用、转发 |
| 变更影响 | 只影响自身 | 影响两端实体 |
| 维护方式 | 各自独立更新 | 关系层统一管理 |

### 4.3 违反解耦的典型症状

- 实体描述中出现"转发到XXX"、"依赖YYY"、"由ZZZ管理"
- 修改一个实体的名称时，需要搜索所有其他实体的描述文本
- 删除一个实体时，不确定哪些文件的描述中包含对它的引用

## 5. Ingress专项约束

### 5.1 问题

Ingress作为流量入口，**最容易出现跨层/跨文件夹描述下游资源信息的违规写法**。

### 5.2 约束

> **Ingress实体只描述自身配置，不跨文件夹描述下游资源。**

**❌ 错误写法**（在Ingress实体描述中内嵌下游资源信息）：

```yaml
# Ingress配置实体
name: api-ingress
description: |
  路由规则：
  - 匹配 /api → 转发至service-a（端口8080）
  - 匹配 /admin → 转发至service-b（需认证）
  依赖 service-a 和 service-b
```

**✅ 正确写法**（只描述Ingress自身，关系交给关系图层）：

```yaml
# Ingress配置实体
name: api-ingress
description: |
  负责/api和/admin路径的路由转发
  配置的TLS证书、域名、限流规则...
relations:
  - type: 转发到
    target: service/service-a
  - type: 转发到
    target: service/service-b
```

## 6. Index标准化规范

### 6.1 核心铁律（最高优先级，不可突破）

1. **Index 严禁记录文件/目录之间的关联关系** — 所有关系剥离到独立图谱关系库
2. Index 只承载三类信息：
   - ① 当前文件/目录**自身定位**：作用、用途、职责边界
   - ② 当前目录内**资产统计**：直接包含的文件/子目录清单
   - ③ **变更历史**：重要修改记录、版本变更要点

> **设计目标**: Index = 目录/文件的**本地档案卡片**，只对内自描述，不向外建立连接。

### 6.2 两种Index类型

#### 文件Index（文件头部）

```markdown
# 文件名
> 作用: ... | 所属目录: ... | 上次变更: YYYY-MM-DD
```

#### 目录Index（目录的index.md）

```markdown
# 目录名 — 说明

> 本目录文件清单

## 📄 文件清单

| 文件 | 说明 |
|:-----|:-----|

<!-- 变更历史 -->
## Changelog
```

### 6.3 Index写入规范

| 字段 | 说明 | 必须 |
|:-----|:-----|:----:|
| 文件/目录名称 | 自描述名称 | ✅ |
| 作用/用途 | 一句话说明 | ✅ |
| 包含资产 | 直接子文件/子目录列表 | ✅ |
| 变更历史 | 重要变更+日期 | ✅ |
| 交叉链接 | 到相关实体的链接 | ✅（外部链接，非关系定义） |
| 关系定义 | **禁止** | ❌ |

### 6.4 设计原理

```text
Index = 自身档案卡片（本地自描述）
关系库 = 实体间连接（全局图谱）

Index 不记录关系 -> 两大好处：
1. 支持分布式分片处理（任意Index可独立读取）
2. 支持增量并行更新（改关系不影响Index）
```

## 7. 跨层描述的10种违规模式

| # | 违规模式 | 示例 | 正确替代 |
|:-:|:---------|:-----|:---------|
| 1 | 上层描述下层OS参数 | 业务服务描述inode数量 | 通过关系引用OS实体 |
| 2 | 实体内嵌转发目标 | Ingress描述转发到哪个Service | 关系图层单独维护 |
| 3 | 文件描述跨文件夹引用 | A目录文件描述B目录文件内容 | 只描述A目录自身 |
| 4 | 依赖关系写在描述里 | "依赖XXX服务"写进正文 | 用`depends_on`关系边 |
| 5 | 日志路径写在上层 | 业务服务描述日志存储路径 | 日志路径属于log实体 |
| 6 | 配置参数下沉 | 上层实体写底层内核参数 | 配置属于OS或配置实体 |
| 7 | 跨层比较 | 上层描述"性能高于底层Y" | 性能数据属于各层自有 |
| 8 | 级联影响描述 | "如果X故障会导致Y" | 关系库维护故障传播链 |
| 9 | 历史信息泛滥 | 描述中包含非本层变更记录 | 变更属于对应层级 |
| 10 | 冗余兜底描述 | "详细信息请参考XXX" | 用关系边建立引用 |

## 8. 关系图层的独立维护

### 8.1 关系库设计原则

```text
关系库 -> 只存放"边"（实体之间的连接）
每个关系 = [源实体, 关系类型, 目标实体, 属性(可选)]
```

### 8.2 关系库数据格式

```json
{
  "relations": [
    {
      "source": "service/order-service",
      "type": "日志写入",
      "target": "log/order-service-log",
      "properties": {
        "log_path": "/var/log/order/",
        "level": "INFO"
      }
    },
    {
      "source": "service/order-service",
      "type": "运行于",
      "target": "os/prod-node-01"
    }
  ]
}
```

### 8.3 关系层的优势

| 维度 | 关系嵌入实体 | 关系独立维护 |
|:-----|:------------|:------------|
| 更新关系需修改 | N个实体的描述文件 | 1个关系文件 |
| 图谱查询效率 | 需全文扫描 | 直接查询关系库 |
| 分布式支持 | 不支持 | ✅ 天然支持 |
| 增量更新 | 整个文件重写 | ✅ 单条关系更新 |
| 冲突检测 | 手动检查 | ✅ 自动校验 |

## 9. 设计哲学：从分布式分片到本地自描述

### 9.1 设计原则总结

```text
三个"只描述自身"原则：
1. 实体文件 -> 只描述本层自有静态属性
2. Index文件 -> 只描述本地资产统计和变更
3. 关系图层 -> 单独维护，不嵌入任何实体描述
```

### 9.2 类比：微服务架构 vs 单体架构

| 知识库设计 | 软件架构对应 |
|:-----------|:-------------|
| 层级隔离 | 微服务（独立部署/独立变更） |
| 跨层描述 | 单体（耦合/变更互相影响） |
| 关系解耦 | 服务注册中心（独立维护调用关系） |
| 本地自描述 | 每个服务有自己的README |

### 9.3 核心结论

> **层级隔离 + 信息关系解耦 = 分布式知识库的架构基础。**

这套设计范式解决了传统知识库最常见的两个问题：

1. **耦合膨胀** — 单个文件修改导致连锁更新
2. **分布式困难** — 无法并发读取，无法增量处理
