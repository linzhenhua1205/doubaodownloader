## 1. 方法论总纲

### 1.1 设计方法论的八步框架

设计方法论遵循**八步递进框架**，每个步骤产出文档/评审物，通过决策门后进入下一步：

```text
+----------------------------------------------------------------------+
|         指标体系驱动的系统设计——八步框架                                |
|                                                                      |
|  Step 1                    Step 5                                    |
|  +==========+             +==============+                           |
|  | 业务需求  |---> Step 2 | 组件实现决策  |---> Step 6                 |
|  | +KPI定义 |    v      | (自研/外采)   |    v                      |
|  +==========+   +==============+       +==============+              |
|                 | 架构描述     |       | 指标->开发    |              |
|                 | +组件识别    |       | 可操作分解   |              |
|                 +==============+       +==============+              |
|                      v                         v                     |
|                 +==============+       +==============+              |
|                 | 指标定义     |       | 整合组装     |              |
|                 | +层层分解    |       | +集成验证    |              |
|                 +==============+       +==============+              |
|                      v                         v                     |
|                 +==============+       +==============+              |
|                 | 复用识别     |       | 回归验证     |---> 交付       |
|                 | +改动点标记  |       | (指标闭环)   |              |
|                 +==============+       +==============+              |
|                                                                      |
|  +==================================================================+ |
|  |                    贯穿全程：过程管理+异常拉通                      | |
|  |  决策门 | 里程碑 | 风险监控 | 跨域协同 | 外采管理 | 变更控制       | |
|  +==================================================================+ |
+----------------------------------------------------------------------+
```

**八步框架的各步简述**：

| 步骤 | 活动 | 核心产出 | 决策门 | 负责角色 |
|:-----|:-----|:---------|:-------|:---------|
| **1** | 业务需求+KPI定义 | 需求规格书/业务KPI树 | TR1 | PM+系统工程师 |
| **2** | 架构描述+组件识别 | 系统架构图/组件清单 | TR2 | 架构师 |
| **3** | 指标定义+层层分解 | 指标体系文档（类似06/07） | TR2 | 系统工程师 |
| **4** | 复用识别+改动点标记 | 复用分析表/改动影响矩阵 | TR3 | 架构师+各SE |
| **5** | 组件实现决策(自研/外采) | 选型决策矩阵 | TR3 | 架构师+采购 |
| **6** | 指标→开发可操作分解 | 硬件Spec/软件Spec/结构Spec/测试用例 | TR4 | 各领域工程师 |
| **7** | 整合组装+集成验证 | 集成计划/接口协议/合规验证报告 | TR5 | 系统工程师 |
| **8** | 回归验证(指标闭环) | 指标达成度报告/偏差分析 | TR6 | 测试+系统工程师 |

### 1.2 三视角协同模型（PM/Arch/PLM）

每一项设计活动需要从**三个视角**同步审视：

```text
                              +---------+
                              |  项目    |
                              |  管理    |
                              |  (PM)    |
                              +---------+
                              | 时间/成本|
                              | 资源/风险|
                              | 交付物   |
                              +----+----+
                                   | 拉通
              +--------------------+--------------------+
              |                    |                     |
              v                    v                     v
       +----------+        +----------+        +----------+
       |  架构    | 协同    |  产品    | 协同    |  各子   |
       |  设计    | <---->   |  生命    | <---->   |  领域   |
       |  (Arch)  |        |  周期    |        |  (Sub)   |
       +----------+        +----------+        +----------+
       | 技术方案 |        | TR1-TR6  |        | HW/SW/SI |
       | 接口定义 |        | 阶段评审  |        | RAS/散热 |
       | 系统整合 |        | 变更控制  |        | 结构/供  |
       +----------+        +----------+        +----------+

```

| 视角 | 关注点 | 核心问题 | 输出物 |
|:-----|:-------|:---------|:-------|
| **PM（项目管理）** | 时间/成本/资源/风险 | 进度是否按计划？资源是否到位？风险是否可控？ | 项目计划/WBS/风险登记册 |
| **Arch（架构设计）** | 技术方案/接口/权衡 | 方案是否最优？接口是否清晰？技术风险是否识别？ | 架构文档/接口协议/技术评审报告 |
| **PLM（产品生命周期）** | 阶段完整性/质量 | 当前阶段交付物是否齐全？是否满足进入下一阶段条件？ | 阶段评审报告/质量门报告 |

### 1.3 设计决策的四个层级

设计的决策按影响范围分四个层级，越往上拉通范围越大：

| 层级 | 决策类型 | 影响范围 | 决策者 | 拉通会议 | 实例 |
|:-----|:---------|:---------|:-------|:---------|:-----|
| **L1** | 战略级 | 全产品线/平台 | CTO/产品线负责人 | 产品委员会 | 确定采用BF3还是BF4 |
| **L2** | 架构级 | 系统/子系统间 | 系统架构师 | 架构评审会 | 确定存储网OS比=2:1 |
| **L3** | 方案级 | 子系统内 | 子系统SE | 子系统方案评审 | JBOF选4×400G还是8×100G |
| **L4** | 实现级 | 模块/组件内 | 开发工程师 | 设计审查 | NVMe SSD顺序读延迟≤175μs |

**异常拉通**: 当L4发现影响L2/L1的约束时，必须逐级上报拉通。

### 1.4 与IPD TR1-TR6的映射

| IPD阶段 | 八步框架 | 指标维度的关键活动 |
|:--------|:---------|:------------------|
| **TR1 需求评审** | Step 1→2 | 业务KPI确定，顶层指标分解启动 |
| **TR2 概念评审** | Step 2→3 | 架构确定，指标体系初版（类似06/07初版） |
| **TR3 计划评审** | Step 4→5→6 | 复用决策，组件选型冻结，指标→规格分解 |
| **TR4 开发评审** | Step 6执行 | 各领域规格落实，PCBA/FPGA/FW开发 |
| **TR4A 模块验证** | Step 6→7 | 单模块测试，接口验证，指标初步达成 |
| **TR5 系统验证** | Step 7→8 | 系统集成，全链路指标验证，回归测试 |
| **TR6 确认评审** | Step 8闭环 | 指标达成度100%，偏差消解，交付 |

## 2. 指标定义与层层分解

### 2.1 从业务KPI到系统指标的分解链

**核心主张**: 指标不是事后度量，是**设计的前置约束**。从业务KPI出发，逐层分解到系统/子系统/组件级规格，形成指标树。

```text
KPI层级              KLX 512实例                         分解方法
--------------------------------------------------------------------
L0 业务KPI          Token/s | Token/$ | Goodput          用户定义
   |                  |           |          |
L1 系统指标         MFU | 吞吐   | 利用率  | 成本        KPI->系统指标映射
   |                  |           |          |
L2 子系统指标     计算吞吐|网络BW|存储BW|延迟|功耗       系统指标->子系统分解
   |                  |           |          |
L3 组件规格       GPU HBM|CX7 BW|SSD IOPS|BF4功耗        子系统->组件分配
   |                  |           |          |
L4 实现参数       SERDES速率|PCIe Gen|lane数|DCDC       组件->实现参数
```

### 2.2 指标分解的MECE模板（以存储网为例）

指标分解遵循MECE原则，使用**五维×三层×N场景**矩阵模板：

```text
                           +-- 带宽链 (Throughput) --+
                           |  延迟 (Latency)           |
        每项指标按         |  容量/利用率 (Capacity)    |
       +--- 五维 --->       |  经济性 (Economics)       |
       |                   |  可靠性 (Reliability)     |
       |                   +--------------------------+
       |
 指标 --+                   +-- L1 节点级 (单组件)
  模板  |                   |  L2 超节点级 (子系统)
       |  每项指标按         |  L3 跨域级 (系统)
       +--- 三层 --->       |
                           +--------------------------+

        每项指标按           +-- KV日常 (稳态)
       +--- N场景 --->       |  Prestaging (突发读)
                           |  Checkpoint (大块写)
                           +-- 模型加载/数据训练
```

**实例：存储网的"带宽链"指标MECE分解表**（出自06文档§2）：

| 一级 | 二级(3层×N场景) | 目的 | 度量方法 | 理论值 | 负责领域 |
|:-----|:----------------|:-----|:---------|:-------|:---------|
| **带宽链** | 节点级·KV日常 | 验证400G链路够用 | `fio --rw=write` | ~4Gbps,余量>50× | 系统测试 |
| | 节点级·CKPT | 验证端口压力 | `fio`大块写 | ~400Gbps接近上限 | 系统测试 |
| | 集群级·聚合 | 确定JBOF数量 | 总需求÷单JBOF能力 | 5-6台推荐 | 架构师 |
| | 交换网络·OS比 | 阻塞程度 | 下行÷上行 | 2:1推荐 | 网络SE |
| | JBOF上行·读 | 上行-盘匹配 | `iostat`+`ethtool` | 上行压制55.6% | 存储SE |

### 2.3 指标到硬件/软件/结构的映射

每个底层指标必须映射到具体开发领域的**可操作参数**：

```text
                        指标（如：Prestaging读延迟P99≤500μs）
                                |
          +---------------------+---------------------+
          |                     |                      |
          v                     v                      v
   +--------------+   +--------------+   +--------------+
   |    硬件      |   |    软件       |   |    结构/散热  |
   +--------------+   +--------------+   +--------------+
   |NVMe Gen5 SSD |   |BF3 KVSvc延迟 |   |JBOF风道设计  |
   |顺序读≤175μs  |   |KV->LBA≤3μs    |   |连续读温升≤15℃|
   |              |   |              |   |              |
   |CX7 SERDES    |   |RoCEv2拥塞    |   |光模块布局    |
   |端口≤10⁻¹² BER|   |DCQCN可接受   |   |散热风量≥XCFM |
   |              |   |PFC<100/s     |   |              |
   |PCIe Gen5 ×16 |   |NCCL调度     |   |PCBA层叠    |
   |实际BW≥90%    |   |overlap≥60%   |   |SI阻抗控制    |
   +--------------+   +--------------+   +--------------+
```

**映射表模板**（以读出延迟为例）：

| 指标 | 硬件约束 | 软件约束 | 结构约束 | 协同检查项 |
|:-----|:---------|:---------|:---------|:----------|
| Prestaging P50≤180μs | SSD读≤175μs(中位) | KVSvc处理≤3μs | — | 软件+硬件合计≤178μs |
| Prestaging P99≤500μs | SSD P99≤300μs | KVSvc P99≤10μs | 散热导致SSD限速≤10% | 300+10+hotspot≤500 |
| CKPT全集群≤3min | JBOF写≥840GB/s | 异步CKPT实现 | JBOF部署≤Δ10m | BW+软件+距离合计 |

### 2.4 指标可行性判定（理论极限 vs 工程上限）

每个指标在发布前必须做**可行性判定**，区分理论极限和工程上限：

| 判定结果 | 含义 | 处理方式 |
|:---------|:-----|:---------|
| ✅ **理论可行** | 物理极限≥指标，已存在商用案例 | 进入开发 |
| ⚠️ **需Pre-Research** | 物理极限≥指标但无成熟案例 | 设立PR项目验证 |
| 🔴 **理论不可行** | 指标超过当前物理极限 | 必须降低指标 |

**实例**（存储网延迟指标）：

| 指标 | 物理极限 | 工程上限 | 可行性 | 依据 |
|:-----|:---------|:---------|:------|:------|
| SSD顺序读P50 | ~150μs(NAND tR) | ~175μs(含控制器) | ✅ | 已有Gen5商用SSD |
| 全路径P50 | ~150μs | ~184μs(BF3) | ✅ | 08文档§9.1 |
| 全路径P99.9<500μs | — | ~600-750μs | ⚠️ **需热点缓解** | 08文档§9.3.2 |
| 跨Leaf AllReduce<10ms | ~5μs/跳 | ~15.3ms(512GPU) | ⚠️ **需分层优化** | 07文档§3.2.2 |
| KV日常<10μs | ~0.1μs(SSD) | ~24-49μs(BF3写入) | ❌ **不可达** | 写入含NAND tPROG~20μs |

## 3. 架构描述与组件识别

### 3.1 架构描述规范（五视图法）

每一层架构必须从**五个视图**描述，避免单一视角的盲区：

| 视图 | 回答的问题 | 描述的侧重点 | KLX存储网实例 | 产出物 |
|:-----|:----------|:------------|:-------------|:-------|
| **V1 拓扑视图** | 连了什么？怎么连的？ | 物理连接/拓扑/端口 | Spine-Leaf-JBOF拓扑图 | 网络拓扑图 |
| **V2 流量视图** | 数据怎么流？ | 数据路径/协议/带宽 | GPU→PCIe→BF→JBOF→SSD路径 | 数据流图 |

### 4.1 自研 vs 外采决策框架（四维评估）

每个组件的实现方式从**四个维度**评估：

| 维度 | 权重 | 自研评分1-5 | 外采评分1-5 | 决策依据 |
|:-----|:----:|:-----------|:-----------|:---------|

| **D3 时间窗口** | 25% | 开发周期是否满足 | 供应周期是否满足 | Deadline优先 |
| **D4 风险控制** | 15% | 技术风险+质量风险 | 供应风险+锁定风险 | 风险最小化 |

```text
半系统 -> 全系统: 64节点指标≥90%, 扩展性问题已解决
全系统 -> 交付: 128节点全部指标≥95%, 偏差有降级方案, 问题已闭环
```

### 7.1 RAS子领域串联方法

RAS（可靠性·可用性·可服务性）是**横向串联**各子领域的抓手：

```text
              +---------------------------------------------+
              |            RAS 需求/场景                      |
              |  (硬件故障/软件挂死/链路中断/散热异常)        |
              +----------------+----------------------------+
                               | 串联
         +---------------------+---------------------+
         |                     |                      |
         v                     v                      v
   +----------+         +----------+          +----------+
   |  硬件    |         |  软件    |          |  系统    |
   |  RAS     |         |  RAS     |          |  RAS     |
   +----------+         +----------+          +----------+
   |.FRU设计  |         |.Watchdog |          |.故障隔离 |
   |.热插拔   |         |.健康检查  |          |.降级策略 |
   |.温度感知 |         |.错误日志  |          |.Graceful |
   |.电压监控 |         |.自动恢复  |          |  Shutdown|
   +----------+         +----------+          +----------+
```

**RAS场景驱动法**（以存储网为例）：

| RAS场景 | 硬件动作 | 软件动作 | 系统动作 | 验证方法 |
|:--------|:---------|:---------|:---------|:---------|
| NVMe SSD故障 | FRU指示灯亮/热插拔 | 错误上报+日志 | 降级(损失1/24盘) | 热插拔测试 |
| JBOF上行断链 | 链路告警 | 路径切换 | 降速(减少1/4上行) | 拔纤测试 |

| 节点掉电 | PWR_GOOD信号 | Graceful Shutdown | 不影响其他节点 | 模拟掉电 |

### 7.5 跨领域冲突检测与消解

当两个子领域的设计要求产生冲突时，使用以下方法检测和消解：

```text
冲突实例: 400G端口位置
--------------------------------------------
散热要求: OSFP cage靠近风扇 -> 便于散热
SI 要求: OSFP cage靠近背板 -> 缩短走线
结构要求: OSFP cage在前板 -> 方便维护

冲突检测: 联合评审 -> 3个位置方案各有取舍
冲突消解: 以SI达标为首要约束(bottleneck),
          散热通过增加导流罩补偿,
          结构接受后部维护(前后维护兼容)

记录: 设计决策记录(ADR) — 记录冲突+方案+理由
```

**冲突消解优先级**: 功能正确→信号完整→散热安全→可维护→成本

## 8. 过程管理与异常处理

### 8.1 决策门（Gate Review）制度

每个设计阶段设置决策门，未通过不得进入下一阶段：

| 决策门 | 时间点 | 评审重点 | 参与角色 | 交付物要求 | 退出标准 |
|:-------|:-------|:---------|:---------|:-----------|:---------|
| **TR1** | 需求明确后 | 业务KPI可行性 | PM+Arch+客户 | 需求规格书 | KPI合理,商业可行 |
| **TR2** | 方案设计后 | 架构合理性 | Arch+各SE | 架构文档+指标体系 | 方案可行,接口清晰 |
| **TR3** | 详细设计后 | 规格可落地性 | 各领域SE | 规格Spec+选型矩阵 | 分解到开发可操作 |
| **TR4** | 开发完成 | 功能完整性 | 测试+开发 | 单元测试报告 | 功能完整,BAT通过 |
| **TR5** | 系统验证后 | 指标达成度 | 测试+Arch | 系统验证报告 | 关键指标≥90% |
| **TR6** | 交付前 | 可交付性 | PM+质量+生产 | 全量验证报告 | 指标≥95%,问题闭环 |

**决策门判定规范**：

```text
  ✅ GO: 所有退出标准满足, 风险已识别并有缓解方案
  🟡 CONDITIONAL: 主要标准满足, 次要问题有缓解方案, 有条件放行
  🔴 NO-GO: 核心标准不满足, 或关键风险无缓解方案, 退回上一阶段

  CONDITIONAL放行条件:
    1. 问题有明确Owner和完成日期
    2. 不影响下阶段核心工作
    3. 问题不阻碍其他子领域并行推进
```

### 8.3 异常拉通机制

当发现设计风险/实测偏差/进度延迟时，按**三级拉通机制**处理：

```text
异常等级定义:
------------------------------------------------------------
L1: 影响量产的重大问题 (如: GDS不兼容->BF3方案一票否决)
    -> CTO/产品线负责人 48h内决策
    -> 跨领域拉通会议 + 新方案评估 + 进度影响评估

L2: 影响核心指标的严重问题 (如: Prestage P99超SLO)
    -> 系统架构师 1周内给出缓解方案
    -> 子系统SE + 相关领域SE联合攻关
    -> 影响TR评审决策

L3: 可内部消解的非关键问题 (如: SSD延迟比理论高5%)
    -> 子领域SE自行解决
    -> 记录到问题跟踪系统
    -> TR评审时更新进展

拉通流程:
  [问题发现] -> [分级评估] -> [指定Owner] ->
  [根因分析] -> [方案确定] -> [跟踪闭环] -> [复盘归档]
```

**异常拉通会议模板**：

```text
异常拉通会议通知
--------------------------------
标题: [异常拉通] Prestage读延迟P99=520μs超SLO 500μs
等级: L2
发起人: 存储SE
参与人: 系统Arch/网络SE/软件SE/测试SE
时间: 当天内

问题描述:
  128节点全系统集成测试中, Prestaging读延迟P99=520μs,
  超出SLO (≤500μs) 约4%偏差。

根因分析(初步):
  1. 一致性哈希偏斜导致1台JBOF上行~58%占用
  2. 热点JBOF排队延迟增加~20μs

方案讨论:
  方案A: 虚拟节点×256 (减少偏斜)   -> 预计改善~15μs ✅
  方案B: 增加1台JBOF (从5台->6台)  -> 预计改善~25μs
  方案C: 放宽P99 SLO到550μs        -> 需确认推理SLO是否满足

决策: 采用方案A + 方案B并行推进, 1周后验证
Owner: 存储SE
跟踪: 2026-08-XX 验证结果
--------------------------------
```
