## 1. 核心问题：目录 ≠ 文件集合

一个目录如果包含了强关联的文件集合，那么它的质量**不是各文件质量的加和**，而是**各文件之间关联关系的完整性**。

```text
错误认知:
  目录质量 = Σ(文件i的质量)

正确认知:
  目录质量 = Σ(文件i的质量) + Σ(关联(文件i, 文件j)的完整性)
                                       ^ 这部分最容易被人和AI忽略
```

### 1.1 目录质量的退化模式

强关联目录在没有主动治理的情况下会**自然退化**，退化的方向有规律可循：

| 退化模式 | 表现 | 根因 | 渐进程度 |
|:---------|:-----|:-----|:--------:|
| **关联退化** | 交叉链接失效、术语不一致、接口签名不一致 | 每次只改了一个文件，忘了同步关联文件 | 渐进 |
| **冗余堆积** | 多个文件重复描述同一概念，说法相互矛盾 | 新增文件时不检查是否已存在类似内容 | 渐进 |
| **结构崩塌** | 目录从"精心设计"退化为"塞进去拉倒" | 缺乏目录级别的准入标准和编码规范 | 突发（在达到临界点后） |
| **信息过时** | 引用的外部链接404、指标数据过期 | 没有定期刷新机制 | 渐进 |
| **碎片化** | 一个完整主题被拆散在多个文件中，丢失整体图 | 分文件创建时的逻辑拆分在后继修改中丢失 | 渐进 |
| **边界模糊** | 文件A的内容渗透到了应属于文件B的范畴 | 缺乏清晰的scope定义和review机制 | 渐进 |

### 1.2 为什么强关联目录的质量更难管

强关联目录退化快，有三个根本原因：

**原因1：修改的传播代价 > 创建代价**

```text
创建一个新文件 -> 只需理解自己的scope
修改一个已有文件 -> 需要理解与N个关联文件的交互

当 N 增大时，修改的认知负载远超创建。
人（和AI）天生倾向于"新增"而不是"修改+同步"。
```

**原因2：关联是隐式的**

```text
文件A 中引用了 "IBRS (Indirect Branch Restricted Speculation)"
文件B 中引用了 "IBRS 机制"
文件C 中引用了 "分支预测隔离"

三个文件在说同一件事，但 AI 不会"知道"它们之间的关联关系，
因为关联不是显式声明的，而是隐式存在于语义中的。
```

**原因3：质量退化的检测需要全局视野**

```text
局部检查（单个文件）:
  ✅ 拼写正确
  ✅ 格式规范
  ✅ 链接有效

全局检查（跨目录）:
  ❌ 文件A的"IBRS"在文件B中是"ibrs"——大小写不一致
  ❌ 文件A的接口定义 x=0x1234，文件B的实现用了 x=0x1235——值不同
  ❌ 文件A引用了文件C中的概念，但文件C已被删除——悬空引用
```

这些全局问题只有**目录级扫描**才能发现。

### 1.3 案例：一次典型的目录质量恶化过程

```text
时间线: knowledge/02_rd/03_hardware/ 目录的半年质量退化

第1月: 创建目录
  - 精心设计了子目录结构（cpu/memory/storage/interconnect/）
  - 每个子目录有 index.md + 统一的文件模板
  - 交叉链接完整

第2月: 新增3个文件
  - 接口定义开始不一致（x0.1 vs x0.1a）
  - 但整体可控

第3月: 新增5个文件 + 修改2个已有文件
  - 新文件忘了在 index.md 中注册
  - 一个修改导致 cross-ref 断裂
  - "no one notices"

第4月: 积压
  - index.md 已有 5 个文件未注册
  - 交叉链接断裂 3 处
  - 出现 2 组重复内容（同一概念的两个不同表述）

第6月: 临界点
  - index.md 过时率 > 30%
  - 没人敢碰这个目录——"改了A可能影响B和C，但没人知道B和C在哪里"
  - 质量崩盘
```

这不是管理不善的问题——这是**系统性缺陷**。目录缺乏"质量管家"角色。

## 2. 方法论框架：目录即系统

### 2.1 核心隐喻

把目录看作一个**软件系统**，而不是一个文件容器：

```text
文件系统视角（❌）:
  目录 = 文件夹
  文件 = 独立文档
  质量 = 单个文档的好坏

软件系统视角（✅）:
  目录 = 微服务集群
  文件 = 服务实例
  关联 = 服务间API调用
  质量 = 服务集群的健康度（包括服务内+服务间）
```

这个隐喻转换的意义：**软件系统有架构设计、接口规范、依赖管理、监控告警、变更流程——目录治理也应该有。**

### 2.2 四层治理模型

```text
+-------------------------------------------------------------+
|                    预防层（Change Protocol）                    |
|  新增审核 · 修改门禁 · 审计制度 · 变更通报                     |
+-------------------------------------------------------------+
|                    修复层（重构手术刀）                          |
|  反模式检测 · 去重合并 · 结构重组 · 索引重建                   |
+-------------------------------------------------------------+
|                    探测层（质量雷达）                            |
|  自动检查 · 健康评分 · 退化预警 · 趋势跟踪                     |
+-------------------------------------------------------------+
|                    拓扑层（依赖图）                              |
|  依赖提取 · 耦合分析 · 影响范围 · 变更传播                      |
+-------------------------------------------------------------+
|                    契约层（目录合约）                            |
|  Index · Schema · Scope · 命名规范                             |
+-------------------------------------------------------------+
```

各层依赖关系：**下层是上层的基础**，不能跳过下层直接建上层。

### 2.3 质量维度定义

目录级质量从六个维度评估：

| 维度 | 定义 | 测量方式 | 权重 |
|:-----|:-----|:---------|:----:|
| **完整性** | 所有文件都被纳入索引管理，没有"孤儿文件" | 索引覆盖率 = 已注册/实际文件数 | 20% |
| **一致性** | 跨文件的术语、定义、接口、数值一致 | 抽样比对 + 自动化接口检查 | 25% |
| **连通性** | 交叉链接有效，无404、无悬空引用 | 链接有效性检测 | 15% |
| **简洁性** | 无冗余内容、无重复覆盖 | 语义相似度检测 | 15% |
| **时效性** | 内容不过时，数据有日期 | 文件最后修改日期 + 内容中日期标记 | 15% |
| **规范性** | 格式统一、命名规范、模板一致 | 格式检查脚本 | 10% |

## 3. 契约层：目录合约（Index + Schema）

### 3.1 目录合约四要素

每个强关联目录都应有一份"合约"，明确定义：

```text
目录合约（示例：knowledge/02_rd/03_hardware/）

1. Scope（边界）
   本目录存放硬件设计相关的技术文档。
   不包括: 软件/固件/生产制造/市场分析

2. Schema（文件模板）
   每个文件必须包含:
     - 标题行（# 开头）
     - 一句话简介（> 引言块）
     - 目录（## 📑 目录）
     - 主体内容
     - 元数据（创建日期、关联文档、changelog）

3. Naming Convention（命名规范）
   - 英文小写，下划线分隔
   - 编号前缀: 00_ 用于 index, 10/20/30 用于分类
   - 非编号文件按主题命名

4. Index Protocol（索引协议）
   - 新增/删除文件 -> 即时更新 index.md
   - 修改内容 -> 即时更新 log.md
```

### 3.2 Index.md 的角色升级

在强关联目录治理中，index.md 的角色从"文件列表"升级为"治理中心"。

**Level 1 - 基础版（仅列表）**:

```markdown
# 硬件设计文档

- [file_a.md](file_a.md) — 主题A
- [file_b.md](file_b.md) — 主题B
```

**Level 2 - 结构化版（带元数据）**:

```markdown
| 文件名 | 创建日期 | 核心内容 | 关联文件 |
|:-------|:--------:|:---------|:---------|
| file_a.md | 2026-01 | 主题A | file_b.md, file_c.md |
| file_b.md | 2026-02 | 主题B | file_a.md |
```

**Level 3 - 治理版（我们的目标）**:

```markdown
## 📄 文件清单

| 文件名 | 创建 | 最后修改 | 核心内容 | 关联文件 | 状态 |
|:-------|:----:|:--------:|:---------|:---------|:----:|
| file_a.md | 2026-01 | 2026-06 | 主题A | B(§3), C(§2) | ✅ 活跃 |
| file_b.md | 2026-02 | 2026-05 | 主题B | A(§4) | ⚠️ 需更新 |

## 🔗 交叉引用地图

文件间的引用关系（方向性）:
- file_a → file_b: §3 中引用 file_b 的接口定义
- file_b → file_a: §4 中引用 file_a 的架构图
- file_c → file_a: 全文件依赖 file_a 的概念基础

## 🔍 最近检查
- 上次完整性检查: 2026-06-15 ✅
- 链接有效: 所有 cross-ref 有效
- 一致性问题: file_b 需同步 file_a 的更新（2026-06）
```

**关键升级**: index.md 要记录**文件间的关联关系**，而不仅是文件本身。

## 4. 拓扑层：依赖图管理

契约定义了"应该怎样"，拓扑回答"实际怎样"。

### 4.1 目录内依赖类型

| 依赖类型 | 示例 | 强度 | 检测难度 |
|:---------|:-----|:----:|:--------:|
| **显式链接** | `See file_b` | 直接引用 | 易（正则提取） |
| **接口依赖** | 文件A定义了一个接口签名，文件B实现了它 | 强绑定 | 中（需语义分析） |
| **术语依赖** | 两个文件使用同一术语，定义必须在某处一致 | 弱但广 | 难（需术语提取+比对） |
| **概念依赖** | 文件B假设读者已读过文件A中的概念 | 隐含 | 极难 |
| **数值一致性** | 两个文件引用了同一规格参数，数值必须一致 | 硬约束 | 中（需模式匹配数值） |
| **时序依赖** | 文件B的内容必须在文件A之后阅读 | 弱 | 难 |
| **包含依赖** | 文件B是文件A的子主题，后者应引用前者 | 弱 | 难 |

### 4.2 依赖图构建方法

**方法A：正则提取（自动，浅层）**

```python
# 通过正则提取 markdown 中的显式链接
import re

def extract_markdown_links(content, current_file):
    """提取 markdown 文件中的内部链接"""
    links = []
    # [text](path.md) 模式
    pattern = r'\[([^\]]+)\]\(([^)]+\.md)\)'
    for match in re.finditer(pattern, content):
        text, target = match.groups()
        links.append({
            'source': current_file,
            'target': target,
            'type': 'explicit_link',
            'context': text
        })
    return links
```

**方法B：语义匹配（自动，较深）**

```python
# 通过术语提取+跨文件匹配检测语义依赖
def detect_term_dependencies(files, domain_terms):
    """
    提取每个文件中的领域术语使用情况，
    构建"术语-文件"矩阵，检测术语定义与使用的一致性。
    """
    term_usage = {}
    for fname, content in files.items():
        used_terms = extract_terms(content, domain_terms)
        for term in used_terms:
            if term not in term_usage:
                term_usage[term] = []
            term_usage[term].append(fname)
    return term_usage
```

**方法C：人工标注（最准确，但成本高）**

在 index.md 的交叉引用地图中人工维护依赖关系（见 3.2 的 Level 3 示例）。

**推荐**: 组合使用 A（自动提取显式链接）+ C（人工在 index.md 中标注关键依赖），B 作为辅助检测。

### 4.3 依赖耦合度指标

量化目录内文件间的耦合程度：

```text
目录耦合度 = 平均每个文件的外部引用数 / 目录中总文件数

分类:
  < 0.3: 松散耦合（文件间独立性强）
  0.3-1.0: 适度耦合（正常互引）
  1.0-2.0: 紧耦合（高度互依）
  > 2.0: 过度耦合（重构信号）

示例:
  10个文件，总引用数 8 -> 耦合度 = 8/10 = 0.8（适度耦合）
  10个文件，总引用数 25 -> 耦合度 = 25/10 = 2.5（过度耦合，需拆分目录）
```

**耦合度故障模式**:

- **太低 (<0.1)**: 文件之间完全独立，说明它们可能不应在同一目录中
- **太高 (>2.0)**: 文件过度互依，说明目录边界不合理或主题粒度太细

## 5. 探测层：质量雷达系统

### 5.1 自动化检查清单

| 检查项 | 方法 | 工具化 | 对应退化模式 |
|:-------|:-----|:------:|:-----------|
| **索引覆盖率** | 扫描实际文件 vs index.md 中的文件列表 | ✅ 易 | 结构崩塌 |
| **链接有效性** | 检测所有内部链接目标是否存在 | ✅ 易 | 关联退化 |
| **反向链接缺失** | 文件A引用文件B，但文件B未回链 | ✅ 易 | 关联退化 |
| **日志完整性** | log.md 中记录了近期所有变更？ | ✅ 中 | 结构崩塌 |
| **命名规范符合** | 文件名是否符合目录合约中的约定 | ✅ 易 | 规范性 |
| **冗余内容** | 跨文件的语义相似度检测（标题相似/TF-IDF） | ⚠️ 中 | 冗余堆积 |
| **术语一致性** | 同一术语在不同文件中的写法是否一致 | ⚠️ 中 | 一致性 |
| **数值一致性** | 关键数值在不同文件中是否一致 | ⚠️ 中 | 一致性 |
| **过期内容** | 文件最后修改日期 > 阈值（如 6个月） | ✅ 易 | 信息过时 |
| **Index 格式完整** | index.md 是否包含指定字段 | ✅ 易 | 规范性 |
| **交叉引用完整** | 文件间的预期关联是否都存在（基于依赖图） | ⚠️ 难 | 连通性 |

### 5.2 质量雷达图

定期（如每月）对每个强关联目录扫描并生成雷达图：

```text
                     完整性
                       ^
                      ╱▔▔▔╲
                     ╱  85% ╲
                    ╱          ╲
           规范性  <╱    90%    ╲> 一致性
                 ╱                ╲
                ╱  70%     60%     ╲
               ╱                    ╲
         时效性 <╱▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁╲> 连通性
                        80%
                      简洁性

结论: 一致性和用时性最低，是下次治理的重点。
```

**趋势跟踪（更重要）**:

```text
----------+------+------+------+------+
完整性     | 90%   | 85%   | 82%   | 85%   | <- 波动（新文件未更新索引）
一致性     | 75%   | 70%   | 65%   | 60%   | <- 📉 持续恶化！重点关注
连通性     | 88%   | 85%   | 80%   | 80%   | <- ⚠️ 需修复断裂链接
简洁性     | 85%   | 82%   | 80%   | 78%   | <- 📉 冗余在增加
时效性     | 80%   | 75%   | 65%   | 55%   | <- 📉 恶化最快，需更新一批文件
规范性     | 95%   | 90%   | 88%   | 88%   | <- 较稳定
----------+------+------+------+------+
综合评分   | 85.5% | 81.2% | 76.7% | 74.3% | <- 📉 连续3个月下降，需介入
```

### 5.3 健康度评分模型

```text
基础公式:
  健康度 = Σ(维度i得分 × 维度i权重)

报警阈值:
  ≥ 90%: 健康     -> 维持现有制度
  75-89%: 亚健康  -> 安排计划性治理
  60-74%: 危险    -> 需要紧急治理
  < 60%: 崩溃     -> 建议冻结变更 + 一次性大治理

退化速度关注:
  如果单一维度月度下降 > 5%，或总评分月度下降 > 3%，
  即使仍在"健康"区间，也应触发预警。
```

## 6. 修复层：重构手术刀

### 6.1 六种反模式与修复策略

| 反模式 | 症状 | 修复策略 | 复杂度 |
|:-------|:-----|:---------|:------:|
| **索引泄漏** | index.md 中的文件列表与实际不符 | 重建索引（扫描实际文件 → 生成新 index） | 低 |
| **孤立文件** | 文件存在但未被任何其他文件引用 | 1) 确认是否必要 2) 必要则加交叉链接 3) 不必要则移到 bak | 中 |
| **悬挂引用** | 文件A引用文件B，但文件B已被删除 | 1) 检查文件B内容是否已合并到其他文件 2) 更新引用 | 中 |
| **重复覆盖** | 文件A和文件B描述相同概念 | 1) 选择一个作为"主文件" 2) 合并内容 3) 另一个改为重定向或删除 | 高 |
| **术语漂移** | 同一术语在不同文件中写法/含义不一致 | 1) 统一术语表 2) 全目录批量替换 3) 非规范处加注释 | 高 |
| **范围渗透** | 文件A的内容溢出到文件B的 scope | 1) 重新界定 scope 2) 提取溢出内容归入正确文件 3) 加交叉链接 | 高 |

### 6.2 目录重构流程

```text
触发条件:
  - 雷达图综合评分 < 75% 且持续下降
  - 耦合度 > 2.0（目录需要拆分）
  - 单个子目录文件数 > 阈值（建议 50 为预警线，80 为上限）

重构流程:

Step 1: 盘点（know what we have）
  - 扫描所有文件，建立完整文件清单（含元数据）
  - 提取依赖图
  - 评估当前质量

Step 2: 分析（know what's wrong）
  - 对照质量维度找出最短板
  - 识别反模式
  - 确定根因（退化的根本原因，而非表面症状）

Step 3: 规划（know what to do）
  - 制定修复计划（按影响面排序，优先修复一致性问题和悬挂引用）
  - 如果需要拆分目录，定义新目录结构
  - 评估风险（哪些改动会影响外部依赖者）

Step 4: 执行（do it）
  - 分阶段执行：
    Phase 1: 修复断裂链接 + 更新 index（低风险高回报）
    Phase 2: 去重 + 合并重复内容（中风险）
    Phase 3: 目录拆分/重组（高风险，需冻结变更期间执行）
  - 每阶段后做质量雷达扫描验证效果

Step 5: 验证（verify it's done）
  - 质量雷达扫描验证（目标：综合评分 > 85%）
  - 依赖图重新构建确认
  - 更新目录合约（如果范围/规范有变化）
```

### 6.3 注入 vs 抽取：两种核心操作

在修复过程中，有两种对立的操作模式：

**注入模式**：给每个文件增加缺少的信息

```text
适用场景: 文件缺少元数据、交叉引用、模板字段
操作: 向每个文件追加缺失信息
风险: 文件膨胀、信息冗余
示例: 给一个目录所有文件加上 changelog 尾部
```

**抽取模式**：从多个文件中提取共同信息到共享文件

```text
适用场景: 多个文件重复相同内容（常见描述、引用、定义）
操作: 提取公共内容到 dedicated 文件，原处改为引用
风险: 过度解耦、阅读时需要跳转
示例: 目录中 5 个文件都引用了同一标准规范 ->
       提取到 _references.md，各文件改为 [详见 _references]
```

**决策原则**: 先抽取后注入。删除冗余先于添加缺失。

## 7. 预防层：变更协议（Change Protocol）

### 7.1 新增文件的 Four-Step

每次向强关联目录添加新文件，强制执行四步：

```text
Step 1: 检查（Check）
  是否已有文件覆盖相同或类似内容？
  -> 是：不新增，而是补充到已有文件
  -> 否：继续

Step 2: 声明（Declare）
  在 index.md 中注册：
  - 文件名、创建日期、核心内容
  - 已知的关联文件列表
  - 依赖的外部文件/概念

Step 3: 链接（Link）
  建立必要的交叉引用：
  - 在新文件中引用关联文件
  - 在关联文件中补充对新文件的引用（反向链接）

Step 4: 验证（Verify）
  全量扫描确认：
  - 索引覆盖率达标
  - 链接有效
  - 术语一致
  - 合规
```

### 7.2 修改文件的验证门禁

每次修改一个文件，强制检查受影响的关联：

```text
修改文件A -> 检查:
  □ 文件A自身的质量（格式、链接、术语）
  □ 文件A的修改是否影响关联文件B、C、D
  □ 如果是: 同步更新B、C、D中的相关内容
  □ 更新 index.md (如果修改了核心描述)
  □ 更新 log.md
  □ 全量扫描: 修改后的目录质量未下降
```

### 7.3 目录质量审计制度

```text
审计频率（按目录等级）:
  - P0（核心目录，如 knowledge/02_rd/）: 每月全量审计
  - P1（重要目录）: 每季度全量审计
  - P2（一般目录）: 每半年审计

审计内容:
  1. 全量质量雷达扫描（自动化）
  2. 抽样人工审查（10% 文件，关注一致性+时效性）
  3. 依赖图验证（抽取的依赖是否仍然准确）
  4. 趋势分析（对比上次审计的雷达图）
  5. 改进计划（针对下降维度制定修复方案）

审计报告模板:
  +---------------------------------
  | 目录质量审计报告
  +---------------------------------
  | 目录: knowledge/02_rd/03_hardware/
  | 审计日期: 2026-07-16
  | 上次审计: 2026-06-15
  |
  | 综合评分: 74.3%（上次 76.7%, -2.4%）
  |
  | 退化维度（需关注）:
  |   - 一致性: 60%（-5%）📉 严重
  |   - 时效性: 55%（-10%）📉 严重
  |
  | 修复建议:
  |   1. 紧急: 统一 PCIe Gen5 相关术语
  |   2. 计划: 更新 5 个 >6月未更新的文件
  |   3. 常规: 无
  |
  | 风险等级: ⚠️ 亚健康 - 需安排治理
  +---------------------------------
```

```text
                    循环周期
                  +--------------+
                  |              |
                  v              |
           +--------------+     |

           |  (Change)     |     |
           +------+-------+     |
                  |             |
                  v             |
           +--------------+     |
           |  周期检查     |<----+ 每周/每月自动扫描

                  |             |
```

## 9. 在 AI 工作流中的落地

### 9.1 AI 负责什么、人类负责什么

基于前文对 AI 关联约束局限性的分析，在目录治理中：

| 任务 | 负责方 | 原因 |
|:-----|:------|:-----|
| **契约初始化**（定义 scope/schema/naming） | **人类** | 需要领域知识+价值判断，AI 只能辅助建议 |
| **依赖图构建**（自动提取显式链接） | **AI** | 正则提取是机械任务，AI 擅长 |
| **质量雷达扫描**（运行检查脚本） | **AI** | 自动化脚本，AI 可执行 |
| **雷达解读**（分析退化原因） | **AI + 人类** | AI 发现趋势模式，人类判断深层原因 |
| **反模式识别**（找重复/范围渗透） | **AI** | 语义比较是 AI 强项 |
| **修复方案制定** | **人类主导** | 需要领域理解+权衡，AI 辅助建议 |
| **修复执行**（自动修复已知问题） | **AI** | 批量替换、重建索引、修复链接 |
| **变更协议检查**（新增文件时四步检查） | **AI** | 规则驱动，AI 擅长遵循清单 |

**核心分工模式**:

- AI 做**检测和统计**（扫描 + 报告生成 + 批量修复）
- 人类做**定义和决策**（契约制定 + 优先级排序 + 复杂权衡）

### 9.2 AI 编排器与目录质量门禁的集成

参考前文的"编排器模式"，AI 在编排器控制下按阶段处理目录治理：

```text
编排器 -> 目录治理 Pipeline:

Phase 1: 扫描（纯AI，全自动）
  输入: 目标目录路径
  输出: 质量雷达图 + 反模式清单 + 依赖图
  工具: read(扫描文件) -> bash(运行检查脚本)

Phase 2: 分析（AI + 人类决策点）
  输入: Phase 1 的输出
  流程:
    1. AI 生成分析报告（退化趋势 + 修复建议）
    2. AI 生成优先级排序（急vs缓）
    3. 人类确认优先级（关键决策点 <- 人工介入）
    4. 人类指定还需补充什么检查

Phase 3: 修复执行（AI，分阶段）
  按人类确认的优先级，每阶段：
    1. AI 执行修复
    2. AI 运行验证（质量雷达扫描）
    3. AI 输出验证结果
    4. 如果质量未达标 -> 自动迭代
    5. 如果质量达标 -> 进入下一阶段

Phase 4: 收尾（AI + 人类审核）
  1. AI 生成最终质量雷达图（对比前后）
  2. AI 生成变更摘要
  3. AI 更新 index.md 和 log.md
  4. 人类抽查 10-20% 的关键文件（终审）
```

## 11. 总结：四层模型速查表

```text
遇到"目录质量差"问题 -> 按此排查：

+-----------------------------------------------------+
|  Symptom                  ->  Layer to Check          |
+-----------------------------------------------------+
| 找不到文件、文件乱放        -> 契约层（index缺失/过时） |
| 改了A忘了B、接口不一致      -> 拓扑层（缺依赖图）      |
| 不确定哪有问题             -> 探测层（缺质量雷达）     |
| 重复内容多、结构混乱        -> 修复层（需重构）        |
| 每次新增都制造新问题        -> 预防层（缺变更协议）     |
+-----------------------------------------------------+

治理成熟度:

Level 0: 混沌 — 没有 index，文件随意堆积
   -> 第一步: 建立目录合约

Level 1: 有序 — 有 index，文件按规范存放
   -> 第二步: 建立质量雷达（探测退化）

Level 2: 可控 — 每周检查，退化能被发现
   -> 第三步: 建立修复/预防制度（阻断退化）

Level 3: 健康 — 退化在萌芽阶段就被发现和处理
   -> 第四步: 趋势分析 + 前瞻性治理

Level 4: 自适应 — 系统能自动发现、修复、预防退化
   -> 最终目标：AI 编排器 + 目录质量门禁的闭环
```
