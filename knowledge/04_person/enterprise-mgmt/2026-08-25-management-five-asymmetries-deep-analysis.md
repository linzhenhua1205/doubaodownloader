## 1. 引言：五条思考实为一个问题

### 1.1 问题全景

技术决策者在实际推进工作中反复遭遇的五类困境，表面各自独立，实则共享同一深层结构：

| # | 用户思考 | 表层问题 | 深层结构 | 核心不对称 |
|:-:|:---------|:---------|:---------|:-----------|
| 1 | 不了解业务怎么开展、如何避免出问题 | 认知不足 vs 行动必要 | 信息获取是被动的、暴露度是主动的 | **信息不对称** |
| 2 | 没要求是最大的要求，细节靠执行、出问题都是执行的问题 | 隐性期望 vs 显性追责 | 要求≠文字，要求=意图 | **期望不对称** |
| 3 | 特殊时期的不合规行事遗留，系统越来越复杂、无人敢动 | 短期正确 vs 长期成本 | 复杂度=决策上下文丢失的累积 | **时间不对称** |
| 4 | 尽量简化，但修改代价多大、谁来承担风险 | 简化收益 vs 改造风险 | 收益归系统、成本归个人 | **责任不对称** |
| 5 | 有现成方案≠能集成落地，不能拿能力当结果 | 能力存量 vs 结果产出 | 价值=能力×适配×验证，默认达成=把后两项当1 | **结果不对称** |

### 1.2 统一视角：管理即消解不对称性

这五条思考可以统一到一个视角：**技术决策者面对的从来不是"技术问题"，而是"不对称性问题"**——信息、期望、时间、责任、结果，五种不对称性在组织+技术系统里无处不在。

不对称性的共同特征：**隐性的那一侧无法被讨论、无法被决策、无法被追责**。

- 你不知道的业务知识 → 无法被讨论（你都不知道自己不知道什么）
- 对方没说出口的要求 → 无法被决策（验收时才发现标准是隐性的）
- 历史遗留的权宜债 → 无法被追责（没有人"拥有"它）
- 简化的隐性风险 → 无法被定价（没人敢拍板）
- 集成差距的隐性工作量 → 无法被规划（默认"拿来就能用"）

因此统一解法只有一句话：**显性化——把隐性的知识、要求、债务、风险、差距，变成显性的地图、清单、台账、定价、标准。** 系统里每一件事都可以被讨论、被决策、被追责，系统才可控。

### 1.3 本文结构

每条思考按统一结构展开：**现象 → 深层结构（为什么）→ 第一性原理 → 应对机制（可操作）→ 反面坑**。最后给出综合框架与决策者实操清单。

## 2. 信息不对称：不了解业务怎么开展、如何避免出问题

### 2.1 现象与两难

管理者/技术负责人空降新领域、接手不熟的模块，面对一个基本两难：

```
learn first (safe, slow)        act first (fast, risky)
      |                              |
      +-------+----------+-----------+
              |          |
              v          v
        miss window   break things
```

- **先学后干**：安全但慢，可能错过时机，且"学完"没有终点——业务知识是无穷的，等学完=永远不动。
- **边干边干学**：快但有风险，不了解就动手，可能把系统改坏、把决策做错。

### 2.2 深层结构：风险 = 不确定性 × 暴露度

第一性原理拆解：不了解业务时，风险模型是

```
risk = uncertainty (what you don't know)
     × exposure     (how much damage a wrong move causes)
```

这个模型的关键洞察：**两个变量中，不确定性是被动的（你只能慢慢学），暴露度是主动的（你可以立刻控制）**。所以"如何避免出问题"的答案不是"先学完"，而是"**把暴露度压到当前认知水平可承受的范围内**"——行动策略应该优先控制暴露度，而不是试图消除不确定性。

进一步拆解"不了解"的构成——真正危险的不是已知的空白，而是未知的未知（unknown unknowns）：

| 认知层级 | 含义 | 行动策略 |
|:---------|:-----|:---------|
| 我确定知道的 | 已验证的事实 | 可以在其上行动 |
| 我怀疑的 | 有线索但未验证 | 行动前先验证 |
| 我不知道的 | 明确知道有盲区 | 找锚点人物补 |
| **我不知道自己不知道的** | 盲区中的盲区 | **只能靠探测机制暴露** |

### 2.3 应对机制：五条可操作原则

**① 建"业务地图"而非"业务知识库"**
不需要掌握所有细节，但要建立四张地图：
- **人图**：谁是干这个的（锚点人物）、谁拍板、谁背锅
- **物图**：什么数据/系统承载了业务（事实源，而不是听二手转述）
- **流程图**：业务怎么流转、决策链怎么走
- **历史图**：现在这个形态是怎么演进来的、为什么是现在这样

**② 用问题清单代替学习计划**
不从头学，带着关键问题去问（"这个模块为什么存在""上次为什么这么改""最怕出什么故障"）。问题清单比学习计划更聚焦、更省时。

**③ 可逆行动原则（two-way door）**
第一个动作选"错了也能回滚"的。区分两类决策：
- **单门（one-way door）**：不可逆（删数据、改合同、裁员）→ 必须充分了解后再动
- **双门（two-way door）**：可逆（试点、灰度、加注释、只读重构）→ 可以立即行动，错了回滚成本低

Bezos 的经典原则：双门决策要快、要分散授权；单门决策要慢、要充分论证。不了解业务时，**优先只做双门动作**。

**④ 确认闭环（复述式沟通）**
每次理解都复述给对方确认："我理解的是 X，对吗？"把隐性理解变成显性确认，避免"我以为你懂"的错位。这也是 08-19 文档 RIDE 模型"信息闭环"要素的进入期版本。

**⑤ 风险对冲：决策背书**
重要决策前找至少一个"老业务人"背书——不是让他负责，而是用他的判断校准你的盲区。背书人的价值不在技术，在于**他知道你不知道的坑**。

### 2.4 反面坑

| 坑 | 表现 | 后果 |
|:---|:-----|:-----|
| 假装懂 | 不懂装懂、不敢问 | 决策基于错误前提，翻车后信用受损 |
| 学完再动 | 无限学习、永不行动 | 错过窗口，被评价为"没产出" |
| 上来就动 | 不建地图直接改 | 改错方向，暴露度失控 |
| 只问不做 | 一直问、从不产出 | 失去信任，被当"问问题的" |

**结论**：不了解业务的正确姿势 = 建地图（被动降低不确定性）× 控暴露（主动降低风险敞口）× 双门快动（保持产出节奏）。三者缺一不可。

## 3. 期望不对称：没要求是最大的要求

### 3.1 现象：一句"你看着办"是最难办的要求

"没要求是最大的要求"是管理者与执行者之间的经典张力：上级/客户说"你看着办"，事后验收时却说"这不符合我的预期"。而"出问题都是执行人员的问题"——这句话在组织里几乎是无敌的追责逻辑。

### 3.2 深层结构："没要求"的三种真相

"没要求"不是一个状态，而是三种截然不同的状态：

| 真相 | 要求方的心理 | 执行方的正确应对 |
|:-----|:------------|:----------------|
| **委托判断权** | "我信任你，你来定" | 主动显性化方案，让他确认（委托≠放任） |
| **视为理所当然** | "这是行业常识，不用我说" | 补全行业默认项，但超出常规的假设要上报 |
| **懒得多说/甩锅** | "说了我负责，不说你负责" | 书面留痕，风险提示到位 |

区分这三种真相的方法：**主动输出需求理解清单，看对方反应**——清单一出来，是真委托（会认真看）、是默认（会说"这还用说"）、是甩锅（会含糊其辞），立即现形。

### 3.3 深层结构：要求 = 意图 + 约束 + 验收标准

第一性原理拆解"要求"：

```
requirement = intent (why)   <- the real problem to solve
            + constraint     <- boundaries / limits / taboos
            + acceptance     <- how to know it is done well
```

"没要求"= 三要素全部缺失。执行方此时只有两个选择：
- **赌博式执行**：猜意图、猜约束、猜验收 → 猜对概率低，出问题全责
- **契约式执行**：自己补全三要素并请对方确认 → 把隐性要求变成显性契约

### 3.4 为什么"出问题都是执行人员的问题"——责任转移的结构性分析

这句话逻辑自洽，但揭示了一个隐蔽的组织结构问题：

```
requirement-maker side: you did not ask = you should know; you did not say = default; bad result = your fault
executor side:          you did not clarify = not responsible; blaming later = passing the buck
```

双方逻辑都自洽 → 冲突根源是**隐性契约**：要求方以为"没要求=没责任"，执行方以为"没要求=没标准"。而"没要求"实际意味着**决策权也一并下放了**——此时执行方不仅是执行者，还是半个决策者。出问题追责执行方，本质是"**委托了决策却不承认委托**"——这是组织上最隐蔽、也最不公平的责任转移。

对执行者而言，这个结构的现实含义是：**"没要求"时的责任不是变小了，而是变大了**——因为你同时承担了决策者和执行者两份责任。防守的唯一方式是显性化。

### 3.5 应对机制：把隐性期望变成显性契约

**① 需求理解清单（RUL - Requirement Understanding List）**
开工前主动输出："我理解你要的是 A、B、C，其中 C 我建议这样做，可以吗？"清单一出，隐性期望显性化，验收标准前置。

**② 假设台账**
每个未经确认的假设都是潜在事故。假设要编号、要记录、要请对方确认。格式示例：

```
ASM-001: assume legacy data needs no migration (pending confirm, +3 person-days)
ASM-002: assume RBAC model stays as-is (pending confirm, affects security review)
```

**③ 风险提示留痕**
发现风险时书面提示（邮件/记录），提示了就是尽责，没提示就是失职。留痕不是甩锅，是让决策信息完整——对方知情后仍决定，责任自然转移。

**④ 专业补全的边界管理**
区分两类细节：行业默认项（该做，做不好是失职）与超出常规的假设项（要上报，不报是失职）。边界不清时，一律按"要上报"处理——多报不亏，少报翻车。

### 3.6 反面坑

| 坑 | 表现 | 后果 |
|:---|:-----|:-----|
| 闷头干 | 不问不报，做完才发现理解错了 | 返工+失信，最贵的学习方式 |
| 过度确认 | 每个细节都问，烦人 | 失去自主性评价，被当"没主见" |
| 口头确认 | 问了但没留痕 | 对方事后不认账，白问 |
| 把"没要求"当"没标准" | 自由发挥，验收时被否 | 全责追讨 |

**结论**：没要求≠没标准。执行方要用"需求理解清单+假设台账+留痕"把隐性契约变成显性契约——**显性化是对自己的保护，也是唯一能让"没要求"变成"有据可依"的手段**。

## 4. 时间不对称：不合规遗留与系统熵增

### 4.1 现象：特殊时期的权宜，变成永久的包袱

特殊时期（赶进度、救火、上线压力）走的捷径，当时有充分理由；事后没人清理，系统越来越复杂，最后"没人去动了，难以改动"。这是几乎所有长期系统的宿命。

### 4.2 深层结构：为什么权宜会遗留、且无人敢动

**为什么遗留（四重原因叠加）**：

| 原因 | 机制 |
|:-----|:-----|
| 理由遗忘 | 特殊时期决策都有当时的理由（时间/资源/风险），事后理由被遗忘，只留下"不合规"标签 |
| 激励缺失 | 清理=纯成本无直接收益；不清理=风险在将来，由"未来的别人"承担 |
| 风险不对称 | 改动=可能引入新故障；不动=现状至少是"已知的坏"。维护者期望 E[改]=P(好)×0+P(坏)×(-1)<0 → 永不改 |
| 责任模糊 | 遗留物是历史的，没人"拥有"它，也就没人敢对它负责 |

**为什么"没人去动了"（熵增的组织学解释）**：
系统复杂度每增加一分，能完全理解它的人就少一分。当复杂度超过任何单一维护者的理解能力时，系统进入"不可理解"状态——不可理解的系统 = 不可改动的系统。此时连"评估改动影响"都做不到，改动的期望风险趋近无穷大。

### 4.3 第一性原理：复杂度 = 决策上下文丢失的累积

```
system complexity = accumulated lost decision context
```

每个特殊时期的权宜决策，都在系统里压缩了一段上下文——"当时在什么约束下、为什么选这条路"。当上下文丢失（人走了、文档缺了、理由忘了），系统对后来者就是一团"不可理解的怪"，于是：

- 不可理解 → 不敢动
- 不敢动 → 继续叠加新权宜
- 叠加 → 更不可理解

**恶性循环的起点不是"走了捷径"，而是"走了捷径却没记录理由"**。因此防熵增的第一手段不是减少权宜（特殊时期该权宜还得权宜），而是**权宜必须留痕**——把当时的理由固化下来，让未来的改动者能读懂历史。

### 4.4 应对机制：债务显性化四件套

**① 债务台账（Technical Debt Ledger）**
给每笔债建立记录：谁引入、何时、为什么（当时的理由）、代价估算、还债触发条件。债务台账本身就能阻止"不断加债"——每笔债都有了名字和记账人，加债就有了心理成本。

**② 还债预算（固定额度）**
不是"有空再还"，而是**每次改造预留 20%~30% 的还债额度**（经验建议值，按团队承受力调整）。还债和做新功能一样要有预算——没有预算的还债=永远不还。

**③ 赦免机制（Amnesty）**
对历史决策明确表态："当时是对的，现在条件变了。"解除"动了=否定前任"的心理负担。没有赦免机制，任何人动历史遗留物都在政治风险，于是没人动——赦免是"敢动"的前提。

**④ Strangler Fig 替代（绞杀藤模式）**
不修改旧系统，在旁边建新系统，逐步迁移流量，旧系统自然萎缩退役。相比"修改旧系统"，替代模式的改动风险低一个数量级，特别适合"难以改动"的历史系统。参考 Martin Fowler 的 Strangler Fig 模式。

**⑤ ADR（Architecture Decision Records）——从今天起记录决策上下文**
每个重要决策记录：上下文（当时约束）→ 备选方案 → 决策 → 理由。让未来的维护者"读懂历史"。ADR 是防熵增的第一道防线，成本极低（每次 0.5~1 人天），收益是让系统永远"可被理解"。

### 4.5 反面坑

| 坑 | 表现 | 后果 |
|:---|:-----|:-----|
| 全面清算 | 一次性重构所有历史债 | 风险爆炸，大概率失败并失去信任 |
| 只记不还 | 台账建了但永远不排期 | 台账变成装饰，债继续滚 |
| 动而不赦 | 改造了但不说"历史免责" | 政治风险让改造者寒心，下不为例 |
| 反对权宜 | 禁止任何特殊时期捷径 | 教条主义，关键时刻僵化误事 |

**结论**：历史债不可怕，可怕的是**无记录的债**。核心动作是把"特殊时期的理由"固化成文（ADR+台账），把"还债"变成有预算、有赦免的常规机制——系统才能从"越来越复杂"转向"可理解、可演化"。

## 5. 责任不对称：尽量简化，但代价多大、谁来承担风险

### 5.1 现象：所有人都同意简化，但没人动手

"尽量简化"是共识，"修改的代价多大、谁来承担风险"是死结。简化的建议人人会提，简化的执行没人敢接——因为**收益归系统，成本归个人**。

### 5.2 深层结构：简化悖论

```
simplification benefit: long-term, dispersed, belongs to the system
  - lower maintenance cost (every month)
  - fewer failures (every year)
  - faster delivery (every release)
  -> NO ONE's KPI

simplification cost: short-term, concentrated, belongs to the actor
  - person-days spent (immediately)
  - breakage risk (immediately)
  - opportunity cost (forgone features)
  -> ALL on the actor
```

为什么简化总是排不上优先级：
- 新功能有**可见产出**（上线、卖钱、汇报），简化没有可见产出
- 风险不对称：新功能失败=功能问题；简化失败=**系统问题**（更严重）
- 归因不对称：简化成功=理所当然（"本来就该简单"）；简化失败="谁让你动的"

### 5.3 第一性原理：改造 = 风险转移交易，必须定价、签约、履约

```
refactoring = trade: now one-time risk  <->  future continuous cost saving
```

这笔交易要成立，需要三个要素，缺一不可：

| 要素 | 含义 | 缺失后果 |
|:-----|:-----|:---------|
| **定价** | 量化 ROI（省多少 vs 花多少+风险期望） | 无法比较优先级 → 永远被新功能挤掉 |
| **签约** | 谁批准、谁背书（决策者签字） | 责任悬空 → 个人赌博 → 没人敢动 |
| **履约保证** | 回滚预案 + 责任条款（按预案执行不追责） | 出事全责 → 期望值恒负 → 永不改 |

### 5.4 应对机制：算账→分层→共担→可见化

**① 先算账（定价）**
简化必须量化。示例（示意算法，非实证数据）：

```
module X now:   1 person-day per change, 20 changes/yr = 20 person-days/yr
after simplify: 0.2 person-day per change, 20 changes/yr = 4 person-days/yr
annual saving:  16 person-days
investment:     10 person-days (refactor) + 1 person-day risk (P=5% x 20 fix)
ROI = 16 / 11 = 1.45 -> worth doing, competes with other demands
```

**② 风险分层（确定自己能干多少）**

| 风险等级 | 动作示例 | 决策方式 |
|:---------|:---------|:---------|
| 低 | 只读重构、加注释、提取公共函数、删死代码 | 直接做，无需审批 |
| 中 | 合并模块、统一接口内部实现 | 团队评审后做 |
| 高 | 改对外接口、删功能、换架构 | 立项+审批+回滚预案+灰度 |

**③ 责任共担（签约）**
立项时明确："只要按预案执行，出问题不追责个人。"——这句条款的效力取决于组织文化，但必须写进立项书。**决策者签字 = 风险由决策者背书，执行者按预案免责**，这是让"敢动"成为组织能力的关键机制。

**④ 收益可见化（给简化记账）**
简化完成要记录"省了多少"（人天/故障/交付周期），让简化有产出记录——否则简化永远是无名英雄，下个简化项目依然排不上队。

### 5.5 反面坑

| 坑 | 表现 | 后果 |
|:---|:-----|:-----|
| 不算账 | 凭感觉简化 | 无法论证，被"先做别的"一句话顶回 |
| 一刀切 | 高风险改造也直接干 | 翻车全责，从此再不敢简化 |
| 集体背锅 | 人人有责=无人负责 | 决策稀释，简化流产 |
| 简化无记录 | 做完不度量 | 成果不可见，激励链条断裂 |

**结论**：简化不是技术问题，是**交易结构问题**。把简化的收益和成本都显性化（定价），把批准权和风险都显性化（签约），简化才能从"谁都不敢动的共识"变成"有预算、有背书、有预案的常规工程"。

## 6. 结果不对称：有现成方案≠能集成落地，不能拿能力当结果

### 6.1 现象：能力幻觉与默认达成

很多时候有现成方案——开源项目、供应商方案、别人的成功经验。管理者容易默认"拿来就能用"，结果集成是持久战，甚至不了了之。"不能拿能力当结果，默认就达成了"——这是对**计划谬误**（planning fallacy，人系统性低估任务耗时）最清醒的警惕。

### 6.2 深层结构：为什么"有现成的"不等于"能落地"

**① 现成方案是为别人的场景设计的**
别人的约束（规模、网络拓扑、权限体系、合规要求、运维习惯、团队能力）≠ 你的约束。方案是"别人的答案"，你的问题未必是同一个问题。

**② 集成成本在边界，不在核心**
方案核心功能可能 90% 适配，但 10% 的边界才是消耗战：接口、数据格式、权限对接、性能调优、监控集成、安全加固、故障处理。边界问题最琐碎、最不可预测、最耗人天（Conway's Law 的另一面：方案的边界由方案方的组织结构决定，天然与你的结构不匹配）。

**③ 验证成本被系统性低估**
集成≠完成，验证=符合预期。验证需要测试环境、用例、数据、时间——每一项都是投入。且验证不足=上线风险。

**④ 组织协同成本**
集成往往跨团队（方案方、平台方、业务方、运维方），协同成本（沟通、对齐、等待）常被忽略，却常占总工期的 30%+（经验值）。

**⑤ 三个心理机制**
- **能力幻觉**：看到 demo 就以为问题解决了（demo ≠ production）
- **乐观偏差**：默认集成顺利（计划谬误在集成场景尤其严重）
- **责任稀释**：方案是"现成的"，出问题可以怪方案方——责任转移的幻觉，掩盖了"我们自己没投入"的事实

### 6.3 第一性原理：价值 = 能力 × 适配 × 验证

```
value = capability (what the solution offers)
      × fit         (how well it matches OUR constraints)
      × verification(how thoroughly we confirm it works for us)
```

三个乘数，缺一不可。**"拿能力当结果"的本质是把 fit 和 verification 都当成了 1**——而实际它们通常远小于 1。一旦 fit<1 且 verification<1，价值快速趋近于 0，无论能力多强。

推论：**能力再强的方案，只要适配和验证不投入，结果就是 0。管理者必须为 fit 和 verification 显式分配资源**——这是"默认达成"的反面：把达成当项目做。

### 6.4 用户给出的五步链条（深化版）

用户原话拆解："首先要提出问题，之后要能确认是否是问题，并找资源来集成，并验证集成成果是否符合预期。都是工作量。"

```
step 1: raise the question   -> what problem exactly? (problem definition is work)
step 2: confirm it's a real  -> is it worth solving? (true/pseudo/low-value problems)
step 3: find resources       -> budget + people + schedule (integration is a project)
step 4: integrate            -> adapt to OUR constraints (boundary work)
step 5: verify the result    -> acceptance against pre-defined metrics
(step 6: maintain            -> hidden ongoing cost, almost always forgotten)
```

每步都是工作量，且第 2 步最反直觉：**确认"是否真是问题"本身就是工作**——不是所有痛点都值得解决，区分真问题/伪问题/低价值问题需要调研和判断，这一步不做，后续全部白做。

### 6.5 应对机制：把"集成"当独立项目

**① 集成=独立项目**
有立项、预算、工期、负责人，挂在"顺便做"上的集成必然失败。

**② Spike 先行（集成可行性验证）**
先花 **5%** 的资源（经验建议值）打通最小闭环：方案能否接入、数据能否打通、性能能否达标。Spike 通过再全量投入，Spike 失败则换方案——**用 5% 的钱避免 100% 的沉没**。

**③ 差距清单（显式化 fit）**
集成前列出显式差距表：

```
| 维度 | 方案提供什么 | 我们还需要投入什么 | 差距等级 |
|:-----|:------------|:------------------|:---------|
| 核心功能 | 覆盖 90% | 无 | 低 |
| 接口对接 | 标准 REST | 定制适配层 5 人天 | 中 |
| 权限体系 | 自建 RBAC | 对接统一认证 3 人天 | 中 |
| 性能 | 单机达标 | 集群规模压测 4 人天 | 高 |
| 监控运维 | 自带面板 | 接入现有监控 2 人天 | 中 |
```

**④ 验收标准前置**
集成启动前定义"符合预期"的可度量标准（性能指标、功能覆盖、稳定性、故障恢复），验收标准不前置=验收时吵架。

### 6.6 反面坑

| 坑 | 表现 | 后果 |
|:---|:-----|:-----|
| 拿来就用 | 跳过 Spike 直接全量集成 | 边界问题集中爆发，工期失控 |
| 默认达成 | 不立项不派人不排期 | 最后不了了之，责任模糊 |
| 只验功能 | 只测核心功能不测边界 | 上线后边界问题连环爆 |
| 怪方案方 | 集成失败归咎于"方案不行" | 掩盖"我们自己没投入"的事实，下次重蹈 |

**结论**：现成方案的价值是真实的，但**集成差距是独立的工程量**。把"提出问题→确认问题→找资源→集成→验证"当项目立项，用 Spike 控风险、用差距清单显式化 fit、用验收标准前置兜底——"拿能力当结果"才能变成"拿结果当结果"。

## 7. 综合框架：管理即显性化

### 7.1 五机制总表

| # | 不对称 | 显性化对象 | 显性化产物 | 对应机制 | 关键动作 |
|:-:|:-------|:-----------|:-----------|:---------|:---------|
| 1 | 信息 | 认知边界 | 业务地图+盲区清单 | **学习机制** | 锚点人物+双门快动+确认闭环 |
| 2 | 期望 | 隐性要求 | 需求理解清单+假设台账 | **契约机制** | 补全意图/约束/验收+留痕 |
| 3 | 时间 | 历史债务 | 债务台账+ADR | **债务机制** | 还债预算+赦免+Strangler Fig |
| 4 | 责任 | 风险定价 | ROI计算+责任条款 | **风险机制** | 算账+分层+决策者背书 |
| 5 | 结果 | 集成差距 | 差距清单+验收标准 | **验证机制** | 集成立项+Spike+验收前置 |

### 7.2 深层统一：五条思考的演进逻辑

这五条不是孤立的清单，而是管理者在系统中的**完整生命周期视角**：

```
        (t0)              (daily)           (past->now)        (now->future)        (boundary)
  enter the system    execute inside    inherit history    actively change     interact with outside
        |                  |                 |                  |                    |
  [1] info           [2] expectation   [3] time debt     [4] responsibility   [5] result
  unknown business   no requirement    legacy shortcuts  simplify vs risk    capability vs result
```

- 第 1 条：进入系统（时间起点）——认知门槛
- 第 2 条：系统内日常执行——隐性契约
- 第 3 条：系统的历史累积——存量包袱
- 第 4 条：系统的主动改造——演进决策
- 第 5 条：系统与外部世界交互——集成边界

一个管理者要管好系统，五个位置都要站住：进得来（1）、干得对（2）、接得住历史（3）、改得动（4）、接得上外部（5）。

### 7.3 一句话总结

> **管理的本质是消解不对称性——把隐性的知识、要求、债务、风险、差距，变成显性的地图、清单、台账、定价、标准，让系统里每一件事都可以被讨论、被决策、被追责。**

对称的系统=透明的系统=可控的系统。不对称的系统=黑盒的系统=靠运气和个别人扛的系统。
