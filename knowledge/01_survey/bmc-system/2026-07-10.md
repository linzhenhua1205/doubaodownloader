### 1️⃣ bmcweb: 修复 session 持久化 JSON 上限导致的丢失 bug 🆕🟡

| 属性 | 值 |
|:-----|:---|
| **来源** | 🔧 `openbmc/bmcweb` commit [`93ec859f`](https://github.com/openbmc/bmcweb/commit/93ec859f5d20eef343ddc3f003cc2d36ec9dcb08) |
| **日期** | 2026-07-06（author）/ 2026-07-09（merged） |
| **作者** | Rick Yazwinski (Meta) |
| **版本** | master branch (2.19-dev) |
| **重要性** | 🟡 **中** |

**概要**：
`parseStringAsJson()` 通过 `BmcwebSaxParse` 硬编码了 500 个 JSON value 的上限（原意为防御恶意外部 HTTP 请求 body）。实际后果是：当持久化 session 累积到约 50 个时（每个 session ~11 个 JSON values），文件超过上限被当作损坏（malformed），**bmcweb 重启后丢失所有持久化 session**。Meta 内部集成测试和 openbmc-test-automation robot suite 均已命中此问题。

**解决方案**：
- 将 JSON value 上限提高到约 200 个 session 的容量
- 放弃了原先的「无限制 trusted reader」方案（安全风险不理想）
- 远期规划：将每个 session 重构为独立的 JSON 文件（当前代码即将重构，此 patch 仅为过渡方案）

**影响**：
- 影响所有使用 bmcweb session 持久化的生产部署
- 特别是在大型集群管理场景中，50 个 session 是很容易达到的量级
- Meta、NVIDIA 等大规模部署方已实际踩坑

### 2️⃣ bmcweb: 默认 TLS 密码套件升级至 Mozilla modern，禁用 TLS 1.2 🔒🟡

| 属性 | 值 |
|:-----|:---|
| **来源** | 🔧 `openbmc/bmcweb` commit [`37b599b8`](https://github.com/openbmc/bmcweb/commit/37b599b8) (主提交) + [`917fbad4`](https://github.com/openbmc/bmcweb/commit/917fbad4) (tls-profile meson option) |
| **日期** | 2026-06-12（author）/ 2026-07-07（merged） |
| **作者** | Ed Tanous (NVIDIA) |
| **版本** | master branch (2.19-dev) |
| **重要性** | 🟡 **中** |

**概要**：
将 bmcweb 默认 TLS 配置从 Mozilla intermediate（兼容 TLS 1.2）升级为 **Mozilla modern**：
- 禁用 TLS 1.2，仅保留 TLS 1.3
- 使用现代密码套件（Forward Secrecy 优先）
- 保留 Mozilla intermediate 作为编译时回退选项（`tls-profile` meson option）

**配套提交** `917fbad4`（2026-07-02 merged）：
- 新增 `tls-profile` meson 构建选项，支持选择 intermediate / modern
- 通过 testssl.sh 验证密码套件正确生效

**影响**：
- ✅ 安全增强：消除 TLS 1.2 已知漏洞（如 POODLE、BEAST 等攻击面）
- ⚠️ 向后兼容：需要启用了 TLS 1.3 的现代客户端（主流 OS 均已支持，参见 [caniuse.com/tls1-3](https://caniuse.com/tls1-3)）
- 对老旧 IPMI / in-band 管理工具可能有兼容性影响

## 📊 趋势观察

- **bmcweb session 管理成瓶颈**：JSON value 硬上限导致的 session 丢失是典型的「安全防御过度反噬可用性」案例。bmcweb 正计划将 session 从聚合 JSON 文件重构为每个 session 独立文件，这是架构级的改进方向。
- **TLS 安全持续收紧**：继 TLS 1.3-only profile 后，bmcweb 进一步禁用 TLS 1.2 并切换至 Mozilla modern。对新一代 BMC 部署是合理的安全增强，但对依赖老旧管理工具的客户需要过渡方案。
- **BMC 内核安全同步加快**：ASPEED + Nuvoton 两周内从 v6.18.36 到 v6.18.38 连续升级，反映 OpenBMC 社区对内核安全的重视程度提升。
- **AMI 加速 OpenBMC 贡献**：phosphor-state-manager 多项代码质量修复来自 AMI，传统 IPMI BMC 厂商正向 OpenBMC 栈转型。
- **Redfish 2026.2 在途**：Cable 资源中的 SparePartNumber 占位表明 DMTF 正在推进下一版规范，预计 2026 H2 发布。
