### Facebook Rainier: SMBIOS MDR 启用以获取主机 SMBIOS 数据

| 字段 | 值 |
|:-----|:----|
| Commit | [`1da07a0da0`](https://github.com/openbmc/openbmc/commit/1da07a0da0) |
| Author | Frank Tsao (quantatw) → amithash (Meta) merged |
| 标题 | `meta-facebook: rainier: enable SMBIOS MDR` |
| 说明 | 在 Facebook Rainier 平台启用 SMBIOS MDR（Memory Data Register）功能。通过 MDR 通道解析 Host SMBIOS 数据，导出至 D-Bus 供上层管理服务（如 Redfish BIOS 枚举/资产管理）消费。 |

> 💡 Rainier 是 Facebook 上一代 OCP 整机柜平台。SMBIOS MDR 是用 MCTP/PLDM 协议从 Host 获取 SMBIOS 信息的标准机制，此前已在 Yosemite4/5 平台启用。Rainier 补齐此功能后，所有 Facebook 主流平台均可通过统一方式获取主机 BIOS/FRU 信息。

## 🔧 动态 ② — bmcweb: asio resolver 回归修复

- **来源**: [bmcweb/commits](https://github.com/openbmc/bmcweb/commits/master)
- **提交日期**: 2026-07-15
- **版本**: master @ `a72a21df`

| 字段 | 值 |
|:-----|:----|
| Commit | [`a72a21df`](https://github.com/openbmc/bmcweb/commit/a72a21df) |
| Author | Ed Tanous (NVIDIA, 自提交) |
| 标题 | `Fix bug in asio resolver` |
| 说明 | 修复了 bmcweb 编译选项 `resolver=asio` 的回归问题。当 bypass 选项（跳过某些地址解析）被添加时，asio resolver 未能正确构建 `results` 对象，代码无法编译。修复后使用 ASIO 内置类型替代 `std::vector` 构建解析结果。 |

> 💡 bmcweb 支持两种 DNS 解析后端：c-ares（默认）和 asio。此次修复确保 asio 后端**再次可用**，对嵌入式平台（ASPEED AST2600/AST2700）上不带 c-ares 依赖的轻量级构建场景有用。

## 🏭 动态 ③ — Dell iDRAC OEM Redfish Schema: DeviceManagementService + RackInventory

- **来源**: [dell/DellRedfishSchemas](https://github.com/dell/DellRedfishSchemas)
- **提交日期**: 2026-07-15
- **版本**: commit [`bf05064b9e`](https://github.com/dell/DellRedfishSchemas/commit/bf05064b9e)

### 新增 OEM Schema 扩展

```
Added new OEM DeviceManagementService feature to ServiceRoot and
RackInventory feature to Manager's schema
```

**Dell iDRAC OEM 扩展解读：**

| OEM 扩展 | 挂载点 | 功能推测 |
|:---------|:-------|:---------|
| **DeviceManagementService** | `ServiceRoot` | 设备全生命周期管理服务入口，可能涵盖固件合规/基线管理/批量设备注册等功能 |
| **RackInventory** | `Manager` (BMC) | 机架级硬件清单管理，超越单个服务器范围，延伸至机架拓扑、资产定位、电源/网络连接关系 |

> 💡 Dell 在 iDRAC 中增加这两个 OEM 扩展，方向明确：**BMC 管理范畴从单机向机架/数据中心级延伸**。`RackInventory` 尤为值得关注，它暗示 iDRAC 开始承担机架级拓扑感知能力——与 OCP 的 Rack Scale Management 思路一致。
