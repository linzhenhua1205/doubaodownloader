## 二、Apache Flink：2.3.0 大版本 + 原生 S3 文件系统

### 2.1 Flink 2.3.0 发布（2026-06-25）

Apache Flink PMC 于 2026-06-25 发布 Flink 2.3.0，实现 15 个 FLIP（Flink Improvement Proposals）的全量或核心功能，是 Flink 2.x 系列中 SQL 能力扩张幅度最大的一次。核心变更可分为 **SQL 能力、运行时、运维面** 三个维度：

**① SQL 层：changelog 算子落地与物化表对齐**

- **FROM_CHANGELOG / TO_CHANGELOG（FLIP-564）**：将 DataStream API 早已具备的 changelog 流能力下沉到 SQL。FROM_CHANGELOG 把携带操作列（op column）的 append-only 流转换为动态表，可配置 op_mapping 对接自定义 CDC 格式；TO_CHANGELOG 则是反向操作——首次在 SQL 层把 retract/upsert 流物化为 append-only 形式，直接服务于归档、审计、append-only sink 对接等场景。2.3 版本覆盖基础用例，PARTITION BY、invalid_op_handling 等扩展留待后续版本。
- **物化表（Materialized Table）DDL 对齐（FLIP-550/557）**：CREATE MATERIALIZED TABLE 现支持显式列定义（含 watermark、主键），ALTER 支持 ADD/MODIFY/DROP/RENAME；新增 START_MODE 子句控制查询变更后的数据重处理起点，可尝试从上一作业实例的精确 source offset 恢复——避免"改查询就全量重跑"的历史成本。仅当查询优化器生成全新物理计划时才需全量重处理，而加 nullable 列等兼容演进可零重放。
- **SinkUpsertMaterializer 显式冲突处理（FLIP-558）**：当 upsert key ≠ 目标表主键时（多级变换/投影/join 场景），旧实现靠保存主键全量更新历史导致无界状态增长。2.3 改为**默认规划期报错**，强制用 `ON CONFLICT DO NOTHING / DO ERROR / DO DEDUPLICATE` 显式声明冲突策略，把隐性行为变成显式决策。
- **PTF 增强（FLIP-565）**：Process Table Function 新增 late data 处理（SQL 层自定义迟到策略）与 ORDER BY 有序表参数；state 访问与 broadcast state 留待后续。
- **ARTIFACT 关键字（FLIP-559）**：CREATE FUNCTION ... USING ARTIFACT 作为 JAR 的前瞻替代语法，为 Python wheel 等生态资产预留语法空间。
- **关键 bug 修复（FLINK-35661）**：MiniBatchGroupAggFunction 在 ONE_PHASE 聚合策略下，当某 key 的 mini-batch 只含 retraction 且无既有 state 时会提前 return，静默丢弃 bundle 中其余 key——这是数据正确性级别的严重 bug，2.3 已修复。

**② 运行时：自适应与弹性**

- **自适应分区选择（FLIP-339）**：Rebalance/Rescale 分区器按下游任务负载动态分配数据，`taskmanager.network.adaptive-partitioner.enabled`（默认 false）+ `max-traverse-size`（默认 4）两个开关控制，缓解偏斜导致的背压。
- **AdaptiveScheduler rescale 历史 + Web UI（FLIP-487/495）**：流作业记录完整 rescale 事件历史（并行度变化、slot 分配、状态迁移、终止原因），通过 REST 端点暴露并在 Web UI 新增 "Rescales" 页签展示事件计数、时间线、分位数耗时统计。
- **Watermark alignment 重设计（FLINK-37399）**：修复对齐逻辑中 announcement delay 导致的背压处理限速——旧实现下 30s max drift + ~1s 更新周期等于把积压处理速度锁死在 30:1（事件时间:真实时间）；2.3 引入对齐缓冲区（默认 3 个更新周期）解耦，代价是窗口/时间算子 state 轻微增大，可用 `pipeline.watermark-alignment.buffer-size: 0` 恢复 2.2 行为。
- **恢复期检查点（FLIP-547）**：允许作业在 unaligned checkpoint 恢复过程中就触发新检查点，避免"in-flight state 大时数小时无法完成检查点、重启/扩容被迫重做恢复"的恶性循环；两个开关均默认关闭，推荐大 unaligned 状态 + 频繁 rescale 作业开启。

**③ 运维面：应用概念 + OTel 健壮性**

- **应用级生命周期管理（FLIP-549/560）**：cluster-job 模型升级为 cluster-application-job 三级层次，Web UI 新增 Applications 页签，作业回溯到所属应用——多租户生产的"作业归属"问题首次一等公民化。
- **OTel 指标导出健壮性（FLIP-553）**：metrics.reporter.otel.exporter.compression（gzip）与 metrics.reporter.otel.batch.size（分批）两个开关解决大作业指标 payload 被 gRPC 后端拒绝丢数据的问题。
- **文档重构（FLIP-561）**：SQL 独立成章、流式关系概念（changelog/动态表/state）升为顶层 Concepts、Python 文档并入各 API 章节。

**分析段落 A — Flink 2.3 的定位转向：从"流引擎"到"湖仓统一计算层"**：Flink 2.3 的 FLIP 清单呈现一条清晰主线——把过去只能在 DataStream API 或外部系统完成的能力**系统性下沉到 SQL 层**（changelog 算子、物化表 DDL、PTF late data、ON CONFLICT）。这不是零散功能堆叠，而是对"流批一体"承诺的兑现：此前 Flink SQL 处理 CDC/upsert 场景时要么依赖 DataStream API 绕行，要么忍受 SinkUpsertMaterializer 的无界 state 增长；2.3 用 TO_CHANGELOG + ON CONFLICT 把这两种绕行路径都收编进 SQL 语法面。其直接竞争对象是 Spark Structured Streaming 的物化视图能力与 Iceberg 生态的增量处理——Flink 正在以"SQL 一等公民"的姿态争夺湖仓上"持续处理"这一层的默认引擎位置。

### 2.2 Flink Native S3 文件系统：Hadoop 依赖的终结（2026-06-26）

Flink 官方博客宣布 flink-s3-fs-native：一个**零 Hadoop 依赖、基于 AWS SDK v2 异步 I/O 从零构建**的 S3 文件系统插件（FLIP-555），随 Flink 2.3 以实验性 opt-in 插件形式发布。

**背景：S3 插件的历史困局**：Flink 长期提供两个互斥注册 s3:// scheme 的插件——Hadoop 插件（flink-s3-fs-hadoop）支持 RecoverableWriter/精确一次 sink，但拖入完整 hadoop-common 依赖树 + AWS SDK v1；Presto 插件（flink-s3-fs-presto）读路径快、适合检查点，但不支持 RecoverableWriter（精确一次 sink 不可用）且存在目录删除 bug。用户被迫在"精确一次"与"快检查点"之间二选一，还要持续为 hadoop-common 传递依赖树做 CVE 排查。

**性能基准（EKS ap-south-1，Flink 2.1.1，1 JM + 2 TM，并行度 8，20GB RocksDB 状态，60s 全量检查点 EXACTLY_ONCE，约 77 分钟）**：

| 指标 | flink-s3-fs-presto | flink-s3-fs-native | 提升 |
|:--|:--|:--|:--:|
| 平均吞吐 | ~92 MB/s | ~200 MB/s | **2.17×** |
| 平均检查点耗时 | 90.1 s | 48.8 s | 1.85× 快 |
| P90 检查点耗时 | 155.0 s | 72.5 s | 2.14× 快 |
| P99 检查点耗时 | 165.3 s | 76.7 s | 2.15× 快 |
| 同窗口完成检查点数 | 40 | 78 | 1.95× |
| 每检查点存储 | 415 MB | 312 MB | 小 25% |

吞吐按 state 规模分档，小状态收益最大、大状态收益稳定 >2×：

| State 规模 | presto | native | 加速比 |
|:--|:--|:--|:--:|
| 0–2 GB | 79 MB/s | 362 MB/s | 4.58× |
| 2–4 GB | 85 MB/s | 285 MB/s | 3.35× |
| 4–6 GB | 84 MB/s | 173 MB/s | 2.06× |
| 6–8 GB | 86 MB/s | 165 MB/s | 1.92× |
| 8–10 GB | 91 MB/s | 180 MB/s | 1.98× |
| 10–12 GB | 93 MB/s | 193 MB/s | 2.08× |
| 12–14 GB | 93 MB/s | 198 MB/s | 2.13× |
| 14–16 GB | 94 MB/s | 203 MB/s | 2.16× |

**设计要点**：

- **异步优先 I/O**：基于 AWS SDK v2 S3TransferManager + Netty NIO 多路复用连接，规避 thread-per-request 瓶颈；批量 state 恢复走连接池感知的并发传输（官方称可替代 s5cmd 外部工具）。
- **精确一次可恢复写**：NativeS3RecoverableWriter 用 S3 multipart upload 提供 sink 与检查点元数据的 exactly-once 语义，上传失败可从中断 part 恢复。
- **SSE-KMS 加密上下文**：三插件均支持 SSE-S3/KMS，native 额外支持加密上下文（KMS 操作的 key-value 元数据，用于细粒度 IAM 策略条件）。
- **熵注入**：检查点路径可配置随机子串替换，打散 S3 内部分区热键，规避高频检查点节流。
- **JAR 体积**：~13 MB vs Hadoop ~30 MB vs Presto ~93 MB；无 Jackson/Guava/protobuf/Jetty/Kerberos/Zookeeper 等 hadoop-common 传递依赖，CVE 排查面大幅收窄。
- **配置命名空间**：统一 `s3.*`（s3.region / s3.endpoint / s3.upload.min.part.size / s3.async.enabled 等），不再需要 fs.s3a.* 镜像键。

**迁移与路线图**：迁移是纯部署操作（换 JAR + 改配置 + 重启），新旧插件数据双向读写兼容，可并行共存并通过优先级开关灰度切换。Flink 2.4 计划：per-bucket 配置（s3.bucket.<name>.*）、AWS CRT client（S3CrtAsyncClient，HTTP/2 + multipart 优化）、S3 指标可观测性、stream 化读写。三阶段路线：Phase 1 实验特性（当前）→ Phase 2 成为推荐默认（需一个完整发布周期无 Blocker/Critical JIRA + 生产采纳信号）→ Phase 3 正式弃用 Hadoop/Presto 插件。

**分析段落 B — Native S3 的因果链：AWS SDK v1 EOL 是压垮旧插件的最后一根稻草**：两个旧 S3 插件共享的底座是"把 Hadoop FileSystem 适配成 Flink FileSystem"的适配层 + AWS SDK v1。AWS SDK for Java 1.x 于 2024-07-31 进入维护模式、2025-12-31 停止支持（不再有功能与安全修复），意味着 Flink 的 S3 路径事实上站在一个**已 EOL 的 SDK 之上**——这不是性能问题而是合规与技术债的持续累积。Flink 社区的选择不是修补适配层（那会继续绑定 Hadoop 配置模型与 SDK 生命周期），而是推翻重来：以 AWS SDK v2 为底座写一个 Flink 原生的实现，顺带把 4.5× 的小状态吞吐、25% 的存储缩减、7× 的 JAR 瘦身作为副产品收割。这一决策逻辑与 Iceberg 社区 1.11 中"移除 Hadoop 2 依赖"（1.9.0 起）是同一趋势的两面：**湖仓生态正在系统性摆脱 Hadoop 时代的依赖包袱，向云原生 SDK 原生实现迁移**。

**1.11.0 关键能力解读**：

- **Manifest list 加密（#7770）**：作为"清单列表"（manifest list）层级的加密能力，配合此前 1.10 引入的表元数据加密键（table metadata keys for encryption #12927）、REST spec 加密键（#12987），Iceberg 的加密体系从单文件级（Parquet 列加密）扩展到**元数据面**——这直接回应了云对象存储上"数据加密但元数据明文"的合规痛点。1.11 还同步"bring back added-rows in snapshot fields"（#14048），为 row lineage 提供快照级行数证据。
- **Variant 类型生态成型**：Variant（半结构化类型，对标 Snowflake/Delta 的 variant）从 1.9 API 初入 → 1.10 读写器实现 → 1.11 的 Parquet Metrics 过滤修复（#14081）、sanitizing（#13137）、timestamp_ns/time/UUID 子类型（#12682）——一个"JSON 超集但可进列式引擎"的类型在 Iceberg 中完成了从规范到工程的闭环。
- **Spark 4.0 深度集成**：PartitionStatistics Files 支持（RewriteTablePath 流程 #13956）、procedure 参数化重构（ProcedureInput #13913）、迁移动作 format-version 传递（#14163）——Iceberg 与 Spark 4.x 的集成从"能用"走向"原生"。

**分析段落 C — Iceberg 的技术路线：加密、AI 类型、多引擎三线并进**：对照 1.9→1.11 的 changelog 可看出 Iceberg 的工程优先级在 2026 年发生明显转向：1.9 时代的主线是 deletion vectors + Variant 引入（解决"湖上的更新与半结构化"两大历史短板），1.10 完成删除向量全链路 + Flink 2.0 集成，1.11 则把重心移到**元数据加密 + row lineage + 多引擎版本矩阵维护**。row lineage（行级血缘）尤其值得注意——它从 spec 层（1.10 #12982）到实现层（1.10 Spark MERGE/UPDATE #12736）再到 1.11 的快照字段补充（#14048），配合 1.11 的 CountNull 聚合（#13981）与 manifest list 加密，Iceberg 正在为"受监管、可审计、可追溯"的企业级湖仓补齐事务语义的最后几块拼图。这与 Flink 2.3 的 ON CONFLICT 显式化、以及 arXiv 侧 PVDM proof-gated 发布协议（见 4.1）形成共振：**湖仓的下一场竞争不在吞吐，而在正确性与治理**。

### 5.1 事务正确性与发布协议

- **Proof-Gated Publication（PVDM）**（arXiv:2608.14643，2026-07-29，cs.DB）：针对 serverless data-mesh 湖仓中"写者退出码决定发布"的正确性漏洞——Iceberg/Delta 保证提交原子性与快照隔离，但不保证"落库行 = 作业意图行"（静默丢分区、重试截断文件、重复 chunk 都会产生合法但错误的快照）。提出四阶段协议：Physical（写可回滚 staging）→ Verify（独立 notary 存的 keyed multiset 证明，区分缺失/重复/损坏）→ Durable（serverless 重试间重放已完 chunk）→ Metadata（证明通过才提交 catalog）。验证：八千注入故障全部拦截（100 万行内无误拦）；Spark 4.0 + Iceberg 1.11 端到端跑 1 亿行，门控发布成本 ~17ms 与表大小无关，验证开销约为写入的 1/5。URL: https://arxiv.org/abs/2608.14643
- **GitLake：agent 优先湖仓的 Git-for-data**（arXiv:2607.08319，2026-07-09，DASHSys@VLDB 2026）：把单表 Iceberg 快照提升为湖仓级 commit/branch/merge，agent 在隔离分支上工作、人类审查后发布；流水线跑临时分支、最终 merge 原子发布（全见或全不见）；用 Alloy 模型验证核心抽象并暴露事务分支可见性的反例。URL: https://arxiv.org/abs/2607.08319
- **Correct-by-Design Lakehouse（Bauplan）**（arXiv:2602.02335，2026-02-02）：代码优先湖仓，三个流水线级正确性机制——typed table contracts（类型化表契约）、Git-like 版本、事务化 run（整条流水线原子发布）；Alloy 轻量模型验证直觉并发现分支可见性反例——"正确性不是事后补丁，而是限制编程模型使非法状态不可表示"。URL: https://arxiv.org/abs/2602.02335
- **Data contracts as types**（arXiv:2607.13339，2026-07-14，CDMS@VLDB 2026）：Bauplan 基于一年数百万作业运营经验，把数据契约作为跨语言/引擎的多语言湖仓类型系统——用户/agent 用 schema 对象注解输入输出表（列类型、约束、文档、血缘），执行生命周期不同节点解释注解。URL: https://arxiv.org/abs/2607.13339
- **AuditWeave：AI 辅助与数据转换工作流的防篡改证据层**（arXiv:2607.09682，2026-06-14）：轻量 Python 库（零运行时依赖），把 RAG 流水线与表格/湖仓转换的步骤记录进 append-only 哈希链账本，任何修改/重排/插入/删除均可被链校验检出；事件级完整性成本数十微秒，2000 次随机变异测试全检出。URL: https://arxiv.org/abs/2607.09682

### 5.2 查询性能与存储优化

- **Smart Compaction：从元数据预测压缩效用**（arXiv:2608.08639，2026-08-09，cs.AI）：开放表格式小文件累积损害查询性能，但"何时值得压缩"长期是阈值驱动。该工作生成 2,376 张 Iceberg 表（文件大小跨三个数量级），**不读数据**仅从 manifest 提取 17 个元数据特征，XGBoost 预测文件缩减比 R²=0.998/RMSE=0.013；但二值压缩决策其实被单个分区级阈值 max_files_per_partition>4 平凡可分——不需学习模型；96 张 TPC-H 表跨 schema 验证 R²=0.976；查询基准显示压缩利好元数据重查询、却可能因降低任务并行度拖慢全表扫描聚合。URL: https://arxiv.org/abs/2608.08639
- **Oasis：SmartNIC 把 Parquet 解码卸载进网络数据路径**（arXiv:2608.02268，2026-08-03，ETH）：生产数仓工作负载中扫描（含存储往返）约占查询运行时一半，湖仓因每查询解码压缩列式格式放大该瓶颈；存储/网络带宽增速持续超过 CPU 性价比，解码 CPU 周期侵蚀云成本效率。Oasis 是在网络数据路径上卸载 Parquet 解码的定制 SmartNIC，含硬件解码器 + 软件抽象层 + DuckDB 端到端集成，最佳情况下 DuckDB 查询吞吐近乎翻倍。URL: https://arxiv.org/abs/2608.02268
- **Filtered Vector Search in Disaggregated Lakehouse**（arXiv:2608.05441，2026-08-05）：把 IVF 索引内嵌进每个 Parquet 文件 footer，不发明新过滤算法，而是**组合**引擎既有文件剪枝（分区剪枝/zone-maps/bitmap）与 per-file ANN——规划器先按谓词剪文件，再对幸存者跑 IVF。11.5M×768 表 warm IVF 比暴力扫描快 ~32×（recall@10≥0.90，谓词剪掉 444 文件中的 355 个）；5M IBM Granite 真实 embedding 上 join 过滤四分之三分区后快 ~94×（14.7s→157ms）。适用条件：过滤列需文件级局部性，剩余谓词只在纯分区列上可安全下推（排序列不可）。URL: https://arxiv.org/abs/2608.05441
- **Query Performance Prediction 的运行时方差实证**（arXiv:2606.03464，2026-06-02，IEEE CLOUD）：K8s 部署 × 三公有云 + 一私有云 × 多库规模 × 三分析基准，**同一查询重复执行运行时几乎差 2 倍**；因子分析定位数据局部性/租户负载/缓存效应；消除关键方差源可使 SOTA QPP 预测误差降 80%；对低碳调度等依赖预测的负载管理有直接下游影响。URL: https://arxiv.org/abs/2606.03464
- **三湖仓加载/存储效率对比**（arXiv:2604.21449，2026-04-23）：Spark 上 Hudi vs Iceberg vs Delta 处理结构化（CSV）与半结构化（JSON）数据至 7GB，四段 ETL 流程评估加载时间与表体积：Delta 加载最快（任何规模），Iceberg 在稳定性与磁盘节省上最优，Hudi 在加载/存储评估中不占优但可能适合增量更新与流处理场景。URL: https://arxiv.org/abs/2604.21449

### 5.3 AI × Lakehouse

- **"Skill Issues"：数据为中心的湖仓 agent 优化**（arXiv:2606.01185，2026-05-31，ADS@VLDB 2026）：编码 agent 正在成为数据基础设施的用户，其成败不只取决于模型质量，还取决于教 agent 使用系统的 skills/environment 文件。在分支型湖仓 Bauplan 上，agent 生成的流水线代码会诱导具体、可检查的湖仓状态变更——把 agent 评估从输出匹配问题变成状态验证问题。数据为中心的优化管线生成 task-verifier 对、沙箱执行候选 skill、用轨迹信号 + 湖仓状态程序化检查打分，数百任务上优化 skill 使 held-out reward 提升最高 28.6%。URL: https://arxiv.org/abs/2606.01185
- **A Query Engine for the Agents（Hyperparam）**（arXiv:2605.27785，2026-05-26）：生产增长最快的非结构化数据是 agent 轨迹/聊天日志/推理链/模型输出，"agent 在哪里困惑了"这类问题 SQL 答不了（文本无模型不可查询）。针对 Claude Code/Cursor 等客户端 agent 运行时，构建 JS 原生湖仓读路径：Hyparquet/Squirreling/Icebird 三库合计 <70KB，直接从对象存储读 Parquet/Iceberg；per-cell 异步 SQL 执行让昂贵单元仅在下游算子需要时触发。LLM 形态异步 UDF 在过滤型查询上比 DuckDB-WASM 快 300×（排序型 192×），十任务 agent 分析师套件成本低三分之二。URL: https://arxiv.org/abs/2605.27785
- **BatteryLake：agentic、物理约束的数据湖仓策展**（arXiv:2607.09762，2026-07-06）：LLM agent 提取元数据并合成数据集专属转换器（逐字证据落地、无证据即弃权），26 条 schema/统计/物理合理性规则门禁人工复核；发布 41 数据集（25+ 机构）标准化 SOH/RUL 基准。URL: https://arxiv.org/abs/2607.09762
- **事件驱动云原生可穿戴分析框架**（arXiv:2608.11402，2026-08-11）：medallion lakehouse 架构支撑穿戴设备高频生命体征的流处理 → ML 全生命周期；FHIR 最小化方案降存储开销；50 请求/秒摄入、中位响应 <8ms。URL: https://arxiv.org/abs/2608.11402
- **Template-as-Ontology：制造域 AI 验证的合成数据基础设施**（arXiv:2605.11259，2026-05-11）：单 Python 配置模块同时作为时序制造模拟器规范与分析工具运行时 schema（对齐由构造保证而非集成），五层流水线（sim→PostgreSQL→CDC/Iceberg 湖仓→星型→12 个参数化 AI 工具）生成 66 实体类型的 MES 形态数据；72 次工具调用实验中约束参数化把工具参数编造率从 43% 降到 0%（Fisher p<10⁻¹²）。URL: https://arxiv.org/abs/2605.11259

### 5.4 架构与治理

- **What Went Wrong with Data Lakes? 15 年现实检查**（arXiv:2606.08266，2026-06-06）：James Dixon 2010 年提出 Data Lake（存原始、延后 schema、省前期转换），15 年后承诺大多落空。作者读 64 份资料 + 15 年在摩洛哥/西非金融服务与电信业近 500 个现实检查案例，归纳 **Data Lake 七大死罪**与"治理债"（Governance Debt）解释框架，并提出"治理引力"（governance gravity）——治理变难时组织会漂回仓库式结构；给出 Data Swamp 可度量定义与治理债评估模型；结论：湖仓与数据网格技术前进了，但组织记录几乎没有移动。URL: https://arxiv.org/abs/2606.08266
- **Beyond the Data Mesh Illusion**（arXiv:2605.27131，2026-05-26）：数据网格的纯实现经常欠佳——团队承担新职责却缺乏平台成熟度/工具/协调机制。提出 AI 增强的 hub-and-spoke 模型：中央 hub（CoE）提供共享平台服务、策略自动化、AI 治理（自动标准化数据产品、生成质量规则、起草数据契约、回归审查），领域 spoke 拥有业务语义与本地迭代节奏并随成熟度渐进承接；用数据产品采纳率、time-to-find、time-to-insight 三个业务价值指标评估。URL: https://arxiv.org/abs/2605.27131
- **DATER：数据架构及其技术要求**（arXiv:2606.08811，2026-06-07）：概念框架系统描述与评估六种现代架构（数仓、语义数据湖、数据湖仓、数据编织、数据网格），按历史语境、定义特征、DATER 维度符合度逐一分析——帮助从业者理清范式重叠与边界。URL: https://arxiv.org/abs/2606.08811
- **AI-Ready 数据库架构选择框架**（arXiv:2606.08317，2026-06-06）：跨范式评估框架（9 个架构维度 + 工作负载刻画 + 约束过滤 + 兼容性评分），对 13 种数据库范式做结构化对比，揭示三大演进规律：存储与计算解耦、工作负载驱动特化、向集成 AI 就绪平台收敛；最终给出集成湖仓存储 + 特征处理 + 语义检索层的 AI-ready 参考架构。URL: https://arxiv.org/abs/2606.08317
- **Enterprise Data Science Platform（EDSP）**（arXiv:2512.03401，2025-12-02，WS-D2ET@IEEE BigData 2025）：湖仓架构 + Write-Once Read-Anywhere 原则实现多查询引擎联邦访问，四层架构消除数据复制与厂商锁定；n 数据集 × m 环境本可产生 n×m 副本，EDSP 实现跨引擎直接查询，操作步骤减少 33–44%，查询延迟最多 2.6× 但端到端仍在秒级。URL: https://arxiv.org/abs/2512.03401
- **Supervaluationism for the Agentic Lakehouse**（arXiv:2603.13380，2026-03-10）：agentic 分析把湖仓变成多版本系统——(人/AI) 生产者在数据分支中物化竞争流水线，消费者不知数据生命周期却要答案。原型跨分支回答查询（supervaluationary 语义），开源 demo 作为 OLAP 多分支查询的基线。URL: https://arxiv.org/abs/2603.13380
- **LeJOT：Databricks 作业成本编排**（arXiv:2512.18266，2025-12-20）：ML 执行时间预测 + solver 优化实时资源分配，替代静态配置/反应式调整；真实 Databricks 工作负载平均降云成本 20%（分钟级调度窗口）。URL: https://arxiv.org/abs/2512.18266

### 5.5 行业应用

- **OpenHealth Lake**（arXiv:2605.19922，2026-05-19）：基于湖仓 + 数据联邦 + FAIR 原则的健康数据管理平台原型（开源工具栈，Python/R 双包，用户研究验证可用性）。URL: https://arxiv.org/abs/2605.19922
- **Observation Lakehouses**（arXiv:2512.02795，2025-12-27）：面向软件行为的活档案——Sequence Sheets/SRM/SRC 结构使观察数据可离线分析、可复用，解决代码生成 LLM 训练于静态制品、内化 bug 代码的问题。URL: https://arxiv.org/abs/2512.02795

**分析段落 E — arXiv 湖仓研究的三条张力线**：把这 24 篇论文放在一起，能看到 2026 年湖仓研究的三条核心张力。**第一是"正确性 vs 吞吐"**：PVDM 的 proof-gated 发布（每写入 1/5 开销换 fail-closed 证明）、Bauplan 的 typed contracts、GitLake 的 branch/merge、AuditWeave 的哈希链，与 Smart Compaction / Oasis SmartNIC / filtered-ANN 的性能路线形成鲜明对照——正确性侧论文 2026 年显著增多，且多出自同一批作者（Tagliabue 团队在 Bauplan/GitLake/data-contracts 连续产出），说明"湖仓作为多人多 agent 共享基础设施"的新假设正在催生一批新的系统原语。**第二是"AI 是湖仓的用户还是被管理者"**：Skill Issues 把 agent 当作湖仓的一等用户（优化 skill 文件而非模型）、Hyperparam 把湖仓读路径搬进 JS 运行时服务 agent 客户端，而 BatteryLake / Template-as-Ontology 则把 LLM 当作数据策展与合成的工具——两条路线在"agent 化数据工程"这一点上汇合。**第三是"架构反思回归"**：DATER、15 年现实检查、Beyond Data Mesh Illusion 三篇都在做元层面的范式审视，且结论一致地指向"组织与治理比技术更稀缺"——这为上面所有系统论文提供了为什么需要它们的背景板。

## 六、跨源趋势研判

### 6.1 引擎三巨头 2026 年的共同动作：拥抱云原生，摆脱 Hadoop 阴影

| 动作 | Flink | Iceberg | Spark |
|:--|:--|:--|:--|
| 去 Hadoop 依赖 | Native S3 零 Hadoop（~13MB JAR） | 1.9.0 移除 Hadoop 2、1.10 移除 Hadoop 3.3 支持 | 4.x 时代 native 实现持续剥离（历史趋势） |
| 云对象存储一等公民 | AWS SDK v2 异步 I/O | Manifest list 加密 + REST catalog 深化 | 对象存储读路径持续优化 |
| AI/Agent 对接 | (路线图) agent 应用管理 | Variant 类型 + row lineage | (生态) Spark Connect 多语言客户端 |
| 正确性强化 | ON CONFLICT 显式化 | 元数据加密 + 行级血缘 | — |

三者在 2026 年不约而同地把"去掉 Hadoop 时代的历史包袱"与"为 AI/Agent 时代重构"作为主线。对基础设施决策者而言，这意味着：**选型评估基线正在变化**——"兼容 Hadoop 生态"不再是加分项而是历史遗留，云厂商 SDK 原生实现（AWS SDK v2 / Azure SDK / GCP）成为新的默认评估维度；同时 Flink 2.3 的 ON CONFLICT 与 Iceberg 的 row lineage 表明，**数据正确性语义正在从"引擎实现细节"上升为"SQL/spec 层的一等公民"**，这与 5.1 的学术动向完全一致。

### 6.2 对 AI 算力基础设施的映射（本库视角）

数据分析/湖仓生态的演进对服务器/AI 基础设施侧有可迁移的观察：

- **存储吞吐瓶颈的硬件化解耦**：Oasis（SmartNIC 卸载 Parquet 解码）与 504-GPU 集群 checkpoint 带宽瓶颈（见硬件组日报）是同一物理约束的两面——**解码与序列化的 CPU 成本正在追平甚至超过传输成本**。SmartNIC/DPU 上做数据面加速（解码、压缩、哈希）从"研究实验"走向"架构必选项"，与光互连、800V 供电一样进入超节点设计的约束清单。
- **检查点/快照 I/O 成为第一性瓶颈**：Flink Native S3 的 2× 检查点加速、PVDM 的 17ms 门控成本、恢复期检查点（FLIP-547）——三者都在回答同一问题：**大规模状态系统的持久化路径如何不再成为故障恢复的瓶颈**。这与集群训练侧 checkpoint 带宽预算（加载 21.5% 读带宽）是同构问题，湖仓生态的"异步 I/O + 并行传输 + 证明式校验"组合值得训练侧借鉴。
- **Agent 基础设施的"状态可检查性"**：GitLake / Bauplan / Skill Issues 共同揭示——当 AI agent 成为数据流水线的生产者时，"agent 干了什么"必须是**可检查的湖仓状态变更**而非黑盒输出。这为 AI 集群的运维可观测性（agent 作业追踪、血缘、回滚）提供了数据基础设施侧的设计蓝本。

### 6.3 风险与缺口

- **数据缺口**：Spark 4.2.0 具体新特性（release notes 未抓取，仅确认版本与节奏）；Iceberg 1.11 的 Flink 2.1 支持细节、Flink 2.3 的 FROM_CHANGELOG 性能基准均未公开量化数据——如需可后续补抓官方 release notes。
- **时效注意**：arXiv 论文均为 2026-05 至 08 提交，部分（如 LeJOT、EDSP）为 2025 年末预印本，引用时注意"提交时间 ≠ 会议录用"。
- **验证限制**：Flink 2.3.0 发布公告中 15 个 FLIP 的编号与描述以官方公告为准；Native S3 基准数据仅反映其声明的测试环境（EKS ap-south-1、20GB RocksDB），不构成普遍性结论。
