## 1. 🏗️ 数据架构演进 — 新范式涌现

### 1.1 Databricks — Decision Execution Platforms（DEP）— 超越 BI 的第四类企业分析

> **来源**: [Databricks Blog — Beyond Dashboards](https://www.databricks.com/blog/beyond-dashboards-introducing-decision-execution-platforms)（Jul 1, 2026）
> **作者**: Marc Solomon, Marcello Pedersen (Databricks FDE)

**核心论点**: BI（$34.8B/2025）只改进了决策的输入，决策流程本身仍然是手动、碎片化、缓慢的——信号在 dashboard，理由在会议，决策在 deck，执行在 spreadsheet，度量在另一处。

**DEP 新范式** — 将执行决策拆为 4 个可计算阶段，闭环运行在统一治理平面上：

| 阶段 | 描述 | 自动化程度 |
|:-----|:-----|:-----------|
| **Signal** | 实时检测 KPI 偏离 | 自动检测 |
| **Decision** | Agent 推荐+预计影响+替代方案 | Agent 计算 |
| **Execution** | 一键推送到系统+编排 Agent 执行 | 自动编排 |
| **Outcome** | 记录预测 vs 实际影响 → 训练系统 | 闭环反馈 |

**三层架构**:

```
Layer 3 — Executive Surface (行业范式: 保险/医疗/能源/金融/零售)
Layer 2 — FDE SDK (Genie Ontology · Action Types · Decision Log · Scenarios · Omnigent Harness)
Layer 1 — Foundation (Lakebase实时状态 · Genie NL · Unity Catalog · Lakehouse分析 · Agent Bricks · MLflow)
```

**架构信号**:
- 数据平台的演进方向从「看到发生了什么」→「决定怎么做 → 执行 → 衡量是否有效」
- **Fortune 100 零售客户**部署的 fulfillment optimization DEP：4 周完成 MVP，评估的单点缺口价值 $100M+/year
- DEP 运行在客户自己的 Databricks workspace 上，数据/IP 不离开客户治理面

### 1.2 Databricks — dbt Query Tags Public Preview — 细粒度使用归因

> **来源**: [Databricks — Granular Usage Attribution for dbt Pipelines](https://www.databricks.com/blog/granular-usage-attribution-dbt-pipelines-query-tags)（Jul 1, 2026）

**核心能力**:
- 自动注入标签（`@@dbt_model_name`、`@@dbt_materialized`、`@@dbt_core_version`）
- 自定义标签（team / cost_center / project_name / env）
- 标签记录在 `system.query.history`，可通过纯 SQL 查询成本归因
- Genie 支持自然语言查询

**架构意义**: dbt 从「ETL 编排层」进化到「可观测 + 可治理」的数据工程平台。每个模型执行具备完整的财务归因和性能跟踪链。

**最佳实践**:
- 组织级标签在 profile 定义，模型级标签仅用于异常覆盖
- 区分 `local-dev` / `dev` / `prod` 环境以分离 ad-hoc 与生产查询
- 一个仓库内多 dbt 项目通过 `project_name` 区分

### 1.3 arXiv — DATER：六种数据架构的系统化评估框架

> **来源**: [arXiv 2606.08811](https://arxiv.org/abs/2606.08811) — Sayed Hoseini 等（Jun 7, 2026）

**DATER 框架** — Data Architectures and their Technical Requirements。系统评估六种现代架构：

| 架构 | 核心特征 | 适用场景 |
|:-----|:---------|:---------|
| **Data Warehouse** | 结构化历史分析 | BI/报表成熟场景 |
| **Semantic Data Lake** | 语义标注 + 原始存储 | 探索性分析 |
| **Data Lakehouse** | ACID + 开放格式 + ML | 统一分析/AI |
| **Data Fabric** | 虚拟化 + 分布式查询 | 异构数据集成 |
| **Data Mesh** | 去中心化域拥有 | 大型组织数据民主化 |

**架构信号**: 研究界开始系统化框架化数据架构选择，而非叙事驱动。DATER 提供了维度对齐的客观评估桥梁。

### 1.4 arXiv — AI-Ready Data Platforms：9 维度选择框架与 AI 就绪参考架构

> **来源**: [arXiv 2606.08317](https://arxiv.org/abs/2606.08317) — Mohit Srivastava（Jun 6, 2026）

**9 个架构维度**: 存储-计算耦合度、工作负载专化度、AI 集成层、事务语义、查询接口、数据格式开放度、治理成熟度、弹性伸缩模式、跨范式兼容性

**13 个数据库范式分析**（从 OLTP 到向量数据库到湖仓），识别出三个重复进化模式：

3. **收敛到 AI 就绪平台** — 湖仓存储 + 特征处理 + 语义检索 作为统一基座

+-------------------------------------------+

### 1.5 arXiv — Beyond the Data Mesh Illusion：AI 增强 Hub-and-Spoke 湖仓

> **来源**: [arXiv 2605.27131](https://arxiv.org/abs/2605.27131) — Angélil, Migon（May 26, 2026）

**核心论点**: 纯数据网格实现经常不达标 — 团队继承职责但缺少平台成熟度、工具和协调机制。

**AI 增强方案**:
- **Central Hub (CoE)**：共享平台服务 + 策略自动化 + AI 治理
  - LLM 自动标准化数据产品、生成质量规则、起草数据合约、审查回归
- **Domain Spokes**：拥有业务语义、产品 backlog、迭代节奏
  - 随着成熟度提升逐步承担更多职责

**三个结果指标**: 数据产品采用率 × 查找时间 × 获取洞察时间

**架构信号**: 纯数据网格 → AI 增强的中心辐射式湖仓是实际落地方向。LLM 既自动治理又降低领域团队的技术门槛。

### 1.6 arXiv — 三大 Lakehouse 效率对比：Delta Lake vs Iceberg vs Hudi

> **来源**: [arXiv 2604.21449](https://arxiv.org/abs/2604.21449) — Borodii, Osukhivska（Apr 23, 2026）

首次基于 Apache Spark 对三大湖仓系统进行的结构化效率对比：

| 维度 | Delta Lake | Apache Iceberg | Apache Hudi |
|:-----|:-----------|:---------------|:------------|
| **数据加载速度 (CSV/JSON 至 7GB)** | **🏆 最优** | 中等 | 弱 |
| **磁盘空间效率** | 中等 | **🏆 最优** | 高（但加载代价大） |
| **最佳场景** | 加载速度优先的系统 | 稳定性和空间节约 | 增量更新/流处理 |

**工程建议**:
- 追求加载速度 + Delta API 生态 → **Delta Lake**
- 追求稳定性 + 空间节约 + 多引擎互操作 → **Iceberg**
- 增量更新 / CDC 流式场景 → **Hudi**（但批加载不推荐）

## 2. 🤖 Text-to-SQL 突破 — RL 深化与系统化

### 2.1 GradeSQL：ORM 验证器超越执行启发式

> **来源**: [arXiv 2606.30851](https://arxiv.org/abs/2606.30851) — Tritto 等（Jun 29, 2026）
> **归属**: SURGeLLM Workshop @ ACL 2026

**核心贡献**: 将 Outcome Reward Models (ORM) 引入 Text-to-SQL 测试时验证。

**方法**:
- 自动候选生成 + 执行标注（无需人工标注）
- ORM 作为学习到的语义评分函数，比执行成功/频率启发式更精细化

**结果**:
- 优于执行式 Best-of-N 和 Majority Voting
- BIRD: **+4.33%** · Spider: **+2.10%**
- ORM 随候选集扩大有效扩展，在复杂查询上收益更大

**架构信号**: Text-to-SQL 的推理时策略从启发式（执行/频率）转向学习式语义评分——ORMs 作为验证器是 test-time compute scaling 的结构化推理版本。

---

### 2.2 TAHOE：Hint Bank 驱动的提示优化系统

> **来源**: [arXiv 2606.12387](https://arxiv.org/abs/2606.12387) — Chen 等（Jun 10, 2026）

**核心创新**: 将 Text-to-SQL 的提示优化重新定义为**数据管理问题**。

**TAHOE 架构**:
1. **Hint Bank** — 结构化的调试跟踪知识库
   - Syntax Hints: 编译器反馈蒸馏的方言规则
   - Semantic Hints: 执行/用户反馈转化的 schema 和用户逻辑
2. **Strategy Layer** — 建模冲突用户意图为竞争策略
3. **推理管线**: Hint 检索 → Logic Planning → SQL Synthesis

**结果** (Spider 2.0-Snow, GPT-5.5):
| 指标 | 基线 | TAHOE | 提升 |
|:-----|:----|:------|:-----|
| Pass Rate | 61.95% | **79.42%** | +17.47pp |
| Pass@4 | 72.57% | **87.61%** | +15.04pp |
| Snowflake 语法通过 | — | **100%** | — |
| 平均编译反馈轮次 | 2.79 | **0.12** | 23.3× 降低 |

Hint Bank 对弱 backbone 也有效：Doubao-2.0-lite pass rate +19.7pp。

### 2.3 SQLConductor：MCTS 搜索→策略学习的 Text-to-SQL 编排

> **来源**: [arXiv 2606.23537](https://arxiv.org/abs/2606.23537) — Zhu 等（Jun 22, 2026）

**核心区别与突破**:
- 典型编排: plan-then-execute（先定完整流程，再执行）
- SQLConductor: **step-wise orchestration**（每一步基于中间产物和反馈选下一动作）

**方法**:
1. **MCTS** 探索候选工作流
2. 稳定性估计识别高质量编排模式
3. Stability-weighted SFT + Curriculum RL 训练策略模型

**结果**:
- BIRD-Dev: **73.2% EX**（编排小型策略模型协调冻结大型 action 模型）
- 超越直接训练大模型 backbone 的方法
- 策略适应多样化查询需求

---

### 2.4 Larch：语义谓词的 Learned Query Optimization

> **来源**: [arXiv 2606.07923](https://arxiv.org/abs/2606.07923) — Zhao 等（Jun 5, 2026）

**核心问题**: AI SQL（含 `AI_FILTER` 语义谓词）的查询优化—语义操作高延迟 + 高成本，计划不当放大代价。

**Larch 两个变体**:
| 变体 | 方法 | 适用 |
|:-----|:-----|:-----|
| Larch-A2C | GNN 编码谓词树 + Markov 决策策略 | 任意谓词树 |
| Larch-Sel | 监督学习预测选择率 + DP 找最优序 | 固定模式场景 |

**结果**: 比 Palimpzest/Quest 减少 **3×-19× token 成本**。

**架构信号**: 随着 AI SQL (semantic operators) 在数据库中普及，传统的 CBO（基于统计信息/代价模型）不够用——需要 learned optimization 专门处理语义谓词。

---

### 2.5 ProSPy：SQL-Python 双语言 Agent 框架

> **来源**: [arXiv 2606.05836](https://arxiv.org/abs/2606.05836) — Yang 等（Jun 4, 2026）

**核心设计**: 针对企业级大数据库的 SQL + Python 双语言协作框架。

**四阶段**: 自动 Profiling → 渐进 Schema 裁剪 → SQL 中间视图 → Python 灵活分析

**结果**: Spider 2.0-Lite **60.15%** · Spider 2.0-Snow **60.51%**（Claude-4.5-Opus, 无 majority voting）

**架构信号**: 复杂企业查询「一道 SQL 解决不了」→ SQL 做高效扫描 + Python 做灵活分析 是螺旋上升的趋势。

---

### 2.6 arXiv — UniQL：16 种 SQL 方言的统一跨方言基准

> **来源**: [arXiv 2606.08018](https://arxiv.org/abs/2606.08018) — Gao 等（Jun 6, 2026）

| 属性 | 值 |
|:-----|:---|
| 自然语言问题数 | 1,534 |
| SQL 方言数 | **16**（MySQL/Postgres/Snowflake/BigQuery/DuckDB 等） |
| 总查询数 | 24,544 |
| 构建方式 | 混合：数据库迁移 + SQL 翻译 + 执行验证 + 规则汇总 + 人工校验 |

**核心发现**: 当前模型远未达到方言通用的程度。SQLite 上的成功不能迁移到其他方言。需要方言感知的 Text-to-SQL 方法。

## 3. 🔧 平台可靠性 — GPU 健康检查架构

### 3.1 Databricks gpu-monitor：GPU 可靠性全生命周期

> **来源**: [Databricks Blog — How We Keep GPUs Reliable](https://www.databricks.com/blog/how-we-keep-gpus-reliable-across-databricks-ai)（Jul 1, 2026）
> **作者**: Steven Chen, Feng Wang 等（Databricks AI）

**假设**: 单 GPU 年失效率 ~1%。256 GPU × 30 天 → ~19% 故障概率。1,024 GPU → **57%**。大规模下故障不是异常而是预期。

**三类故障**:
| 类别 | 表现 | 诊断难度 |
|:-----|:-----|:---------|
| Crashed Jobs | NCCL watchdog timeout | 易发现，但根因难追踪（需跨硬件/网络/软件层排查） |
| Silent Slowdowns | 吞吐量瓶颈在最低 GPU | 中 — 需 DCGM 信号（HW_SLOWDOWN/THERMAL） |
| Numerical Corruption | NaN / 收敛异常 / 质量退化 | 高 — ECC 纠正后仍可能传播未纠错 |

**三层健康检查架构**:

| 层级 | 时机 | 检查内容 | 检出类型 |
|:-----|:-----|:---------|:---------|
| **Active Bootstrap** | 节点上线 + 每次清理后 | GPU compute burn-in、NVLink 全对连通、NCCL all-reduce 正确性、RDMA NIC bandwidth、ECC/HBM health、PCIe topology、NVIDIA DCGM diag L2 | 确定性故障 |
| **Passive Continuous** | 运行中持续 | NVLink lane status、GPU clock throttle、RDMA port down（累积停机时）、XID errors、PCIe AER、thermal gradient、NVSwitch errors | 非确定性故障 |
| **Periodic Multi-Node** | 空闲节点轮询 | NCCL collective bandwidth（8B → 2GiB sweep）、跨节点 fabric 健康 | 跨节点故障 |

**NCCL 调优洞察**: `NCCL_IB_TIMEOUT` 默认 ~7s（含重试），比 PyTorch watchdog（~10min）短得多。一次长时间端口停摆（即使仅一次）就能杀死训练。Databricks 已调优默认值并在端口瞬断时从 checkpoint 快速恢复。

## 4. 🏢 平台能力扩展 — Databricks / Snowflake

### 4.1 Databricks — 视频智能：VLM 驱动的湖仓级视频分析

> **来源**: [Databricks — Video Intelligence Pipeline](https://www.databricks.com/blog/how-databricks-turning-video-searchable-actionable-intelligence)（Jun 26, 2026）

**架构方案**: 将视频分析作为数据工程问题处理：
- 上传 → Lakeflow 触发 → Serverless GPU + SAM3 分割 + VLM 摘要
- 26min 视频 → 1min55s 相关片段 + AI 摘要
- 模型无关（可换 YOLO / YOLO + 自定义模型）
- 文件/事件驱动 → 横扩展到 20 视频并发

---

### 4.2 Snowflake — Cortex Sense：未建模数据的 Grounded Context

> **来源**: Snowflake Blog（Jun 30, 2026）

直接在**未建模数据**（JSON、非结构化文本）上提供 grounded context，无需预先定义 schema/模型。

**架构信号**: 数据平台的下一个前沿——从建模结构化数据到为未建模数据提供即时查询能力，减少分析延迟。

---

### 4.3 Snowflake — Postgres ML Feature Store：毫秒级特征服务

> **来源**: Snowflake Blog（Jun 22, 2026）

**架构**: 计算在 Snowflake 平台（SQL 转换+特征工程），服务在 Snowflake Postgres（毫秒级推理时特征检索）。

**架构信号**: 湖仓 + 特征平台 + 推理服务三个功能层的分离与集成，湖仓负责批量特征计算，PG 负责实时特征服务。
