## 1. 🔧 Delta Lake 4.3.1 发布（Jul 8, 2026）— 今天刚出

> **来源**: [Delta Lake 4.3.1 Release Notes](https://github.com/delta-io/delta/releases/tag/v4.3.1)
> **作者**: Daniel Wang, Murali Ramanujam, Zheng Hu 等
> **状态**: ✅ GA

**定位**: 基于 4.3.0 的补丁版本，修复 3 个生产级问题，无新功能。

| 修复模块 | 问题 | 影响 |
|:---------|:-----|:-----|
| **Delta REST Catalog OAuth** | `CaseInsensitiveStringMap.entrySet()` 将 camelCase OAuth key（如 `oauth.clientId`）转为小写，破坏认证 | **所有使用 OAuth 的 REST Catalog 连接** |
| **S3A Fast Listing** | OSS UnityCatalog(>=0.4.1) 引入 `CredScopedFileSystem` 包装 S3AFileSystem，类型转换失败 | **UC + S3 联合部署** 的快速文件列举 |
| **UC 托管表元数据** | `is_managed_location` 保留字段泄露到已提交的 `Metadata.configuration` | **表创建时元数据膨胀**，DSv2 与托管表元数据一致性 |

**构建基线**: Delta Spark 4.3.1 基于 **Spark 4.1.0 / 4.0.1**，双版本 Maven 构件。

**架构信号**: Delta 4.3.x 系列是当前**推荐生产版本**（4.3.0 于 Jun 18 发布）。4.3.1 的 OAuth 修复对统一目录集成场景至关重要。

## 2. 🏗️ Databricks Omnigent Contextual Policies（Jul 7, 2026）

> **来源**: [Databricks — Contextual Policies in Omnigent Blog](https://www.databricks.com/blog/contextual-policies-omnigent-using-session-state-better-govern-ai-agents)（Jul 7, 2026）
> **状态**: 发布中

**关键人物**: **Matei Zaharia**（Spark 创始人）直接参与此项目。

**核心创新**: Agent 治理从静态规则 → **会话上下文感知的动态策略**。

| 策略类型 | 能力 |
|:---------|:-----|
| **Google Drive Policy** | 基于会话上下文判定 Drive 文件访问权限 |
| **Risk Score** | 实时风险评分，动态调整 Agent 操作边界 |
| **Cost Budget** | 会话级预算追踪与控制 |
| **Intent-Based Authorization** | 基于自然语言意图而非 API 粒度的鉴权 |

**架构意义**: 这标志着 Agent 平台从"功能交付"进入"企业级治理"阶段。Omnigent 是 Databricks 的 AI Agent 平台，Contextual Policies 是其治理层的核心升级。

## 3. 🧠 Spider 2.0-AIFunc — Text-to-SQL 扩展到 AI-Native SQL（Jul 7）

> **来源**: arXiv:2607.06229 — *Spider 2.0-AIFunc: Extending Real-World Text-to-SQL to AI-Native SQL Workflows*
> **作者**: Tianyang Liu, Canwen Xu, Fangyu Lei 等（8 位作者）
> **日期**: 2026-07-07

**核心贡献**: 首次将 Text-to-SQL 基准扩展到**云平台原生 AI 函数**调用场景。

**背景**: 主流云数据平台（Snowflake/BigQuery/Databricks）现已将 LLM 能力暴露为 Native SQL 函数——分类、过滤、情感分析、抽取、相似度搜索、聚合——但现有 Text-to-SQL 基准只评估传统 SQL。

**AIFunc 基准**:

| 维度 | 数据 |
|:-----|:-----|
| 实例数 | **465** 条（每个多轮验证通过） |
| 数据库 | **125** 个真实企业数据库 |
| AI 函数类型 | 6 种（分类/过滤/情感/抽取/相似度/聚合） |
| 平台 | Snowflake |
| 验证协议 | 多轮重复执行（跨时间窗口随机验证结果稳定性） |

**模型表现**:

| 层级 | 模型 | Execution Accuracy |
|:-----|:-----|:-----------------:|
| 🥇 最强闭源 | 最优闭源模型 | **67–70%** |
| 🥈 最佳开源 | 最佳开源模型 | **58.1%** |
| 📉 差距分析 | 主要失败模式 | 谓词指定 · Schema 接地 · AI 函数参数化 |

**关键发现**: 为传统 Text-to-SQL 设计的 Agent 框架（schema 检索、表选择策略）**不能有效迁移到 AI-native SQL**。最简单的 Agent setup 反而一致匹配或超越更复杂的方案。

## 4. ⚡ Eiger — 运行时自适应的 GPU 数据分析库（Jul 5）

> **来源**: arXiv:2607.04489 — *Eiger: An Efficient Library for GPU-based Data Analytics*
> **作者**: Bowen Wu, Marko Kabić, Sven Hepkema, Vasilis Mageirakos, Christos Kozyrakis, Gustavo Alonso（ETH Zurich + 工业界）
> **日期**: 2026-07-05

**核心问题**: cuDF 虽功能丰富，但对大多数运算符采用**单一静态实现**，不使用运行时数据信息，在多样工作负载和 GPU 架构上性能受限。

**Eiger 方案**: 运行时工作负载自适应的 GPU 分析库，两大原则：

| 原则 | 实践 |
|:-----|:-----|
| **① 多实现变体** | 每个运算符提供多个实现 + 可调 knob，不仅 join/group-by，还包括 **表达式求值、字符串处理、多键排序**（之前被忽视的热点） |
| **② 运行时自适应** | 使用轻量级统计（值范围、HyperLogLog++ sketch）在线选择实现、调 knob、压缩数据 |

**性能**: TPC-H（Scale Factor 100）

| 对比 | 提升 |
|:-----|:----:|
| 全部 22 个查询（总运行时间） | **最高 1.8×** 优于 cuDF |
| 单查询最佳 | **最高 6.1×** |

**架构意义**: "快速互联时代，查询处理而非数据移动成为瓶颈"——这是 GPU 分析优化的范式转变信号。Eiger 的自适应策略直接挑战 cuDF 的静态实现霸权。

## 6. 🔍 CADENZA — 语义查询的 Intent-Dependent 优化（VLDB 2026）

> **来源**: arXiv:2607.01468 — *CADENZA in Action: Breaking the Monolith with Intent-Dependent Plan Spaces for Semantic Queries*
> **作者**: Jaehyun Ha, Yongjoo Park, Wook-Shin Han（POSTECH）
> **状态**: VLDB 2026 Demo

**核心创新**: 语义查询优化器将自然语言 intent 编译为分解步骤，为每个步骤选择物理实现，在用户指定的质量/延迟/成本偏好下调优参数。

**传统问题**: 现有优化器将语义运算符（LLM、embedding 模型）当作**整体实现**，强制在昂贵的模型调用和无法捕获语义的廉价替代方案之间做取舍。

**CADENZA 方案**:

```
Intent（用户查询）
  v 编译
分解步骤（子操作序列）
  v 物理选择
实现方案（LLM vs 规则 vs 向量搜索等）
  v 参数调优
                     <- 用户偏好（质量/延迟/成本）
  v
最优执行方案
```

**架构意义**: 这是**语义查询处理的优化器从 monolith 向 plan-space 演进**的标志性工作。与之前 DATER/DIA 的架构研究一脉相承——系统化地处理 AI-native 查询优化。

## 7. 🔬 DA-Studio — 端到端数据分析 Agent 系统（VLDB 2026 Demo）

> **来源**: arXiv:2606.31423 — *DA-Studio: An Agentic System for End-to-End Data Analysis*
> **作者**: Yizhe Liu, Shaolei Zhang, Ju Fan
> **状态**: VLDB 2026 Demo

**架构**:

```
用户: 自然语言 + 原始文件
  v
DA-Studio Backend: 动作结构化的分析流程
  +- 迭代动作生成
  +- 代码执行（沙箱化）
  +- 反馈循环
  v
产出: 可执行分析步骤 + 中间结果 + 最终报告
  v
用户: 浏览器界面（流式动作追踪/产物预览/代码编辑重跑/报告导出）
```

**三个设计原则**: **Autonomous**（自动编排多步工作流）、**Sandboxed**（安全执行代码）、**Inspectable**（可见的动作轨迹和中间产物）。

## 8. ✅ GradeSQL — ORM 验证器提升 Text-to-SQL（ACL 2026 Workshop）

> **来源**: arXiv:2606.30851 — *Test-Time Verification for Text-to-SQL via Outcome Reward Models*
> **作者**: Mattia Tritto 等（IBM Research）
> **状态**: ACL 2026 SURGeLLM Workshop

**核心贡献**: Outcome Reward Models（ORM）作为 Text-to-SQL 的测试时语义评分函数。

| 方法 | BIRD Dev | Spider |
|:-----|:--------:|:------:|
| Execution Best-of-N | 基线 | 基线 |
| Majority Voting | 基线 | 基线 |
| **GradeSQL (ORM-based)** | **+4.33%** | **+2.10%** |

**关键发现**: ORM 在大候选集下效果更好，复杂查询提升更显著。
