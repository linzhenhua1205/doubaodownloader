## 1. 🚀 Apache Spark 4.2 正式发布（Jul 16）

> **来源**: [Databricks Blog — Introducing Apache Spark 4.2](https://www.databricks.com/blog/introducing-apache-spark-42)（Jul 16, 2026）
> **作者**: Wenchen Fan, Andreas Neumann, Serge Rielau 等 11 人
> **版本**: 🔖 **Apache Spark 4.2**（1,900+ commits, 260+ 贡献者）
> **状态**: ✅ **GA** · 同步进入 **Databricks Runtime 19 Beta**

### 架构变更全景

Spark 4.2 将现代数据与 AI 栈直接"下沉"到引擎内部的四个核心方向：

#### A. Metric Views — 语义层原生内置

| 能力 | 说明 |
|:-----|:------|
| **Metric Views** | Spark SQL 原生语义层，维度和度量为 First-class 对象 |
| **非可加度量** | 比率/去重计数/留存率等，引擎自动保持聚合语义一致性 |
| **AI 一致性** | Agent 与 Dashboard 使用同一治理度量定义，消除"不同分组不同结果"问题 |

> **意义**: 此前语义层在 Spark 外由 Looker/dbt 等工具实现，Spark 4.2 将其下沉到引擎的 Catalog 层面，SQL/BI/Agent 共用同一治理定义。

#### B. AI-Native SQL 原语

| 特性 | 说明 |
|:-----|:------|
| **Vector 函数** | 向量距离/相似度/归一化/聚合 |
| **NEAREST BY** | Top-K 排序 Join，基于距离匹配的检索/推荐/实体解析 |
| **GEOMETRY/GEOGRAPHY** | 原生空间类型 + ST_* 函数 + Parquet/WKT/WKB/SRID 支持 |
| **SYSTEM.BUILTIN** | 完全限定内置函数名，防止注入和歧义 |
| **SET PATH** | SQL 搜索路径，跨命名空间解析表/函数/变量 |
| **Cursor** | DECLARE/OPEN/FETCH/CLOSE，行级结果集控制 |
| **Top-K** | max_by/min_by + QUALIFY + IGNORE/RESPECT NULLS |
| **Tuple Sketches** | 元组草图 + time_bucket 时间序列分析 |

> **意义**: 向量检索原语直接内置到 SQL 引擎，不再需要独立向量数据库做预处理；空间类型减少外部扩展依赖。

#### C. Spark Connect & PySpark — "从任何地方调用 Spark"

| 特性 | 说明 |
|:-----|:------|
| **gRPC+Arrow 协议** | 客户端构建逻辑计划，服务端分析+执行，结果以 Arrow Batch 返回 |
| **兼容性提升** | RDD API 兼容、DataFrame inputs、YARN cluster-mode |
| **Arrow UDF 默认启用** | 存量 UDF 自动走列式加速，无需代码改造 |
| **Pandas 3 支持** | 环境升级更平滑 |
| **Arrow C Data Interface** | Spark ↔ Polars/DuckDB 零拷贝互操作 |
| **Python Data Source** | Python 编写 batch/streaming reader/writer，注册为标准 Data Source |

> **意义**: Arrow 零拷贝互操作使 Spark 成为 Python AI 生态的"规模化计算后盾"，不再需要在 Spark 和 Pandas/Polars 之间反复序列化。

#### D. Auto CDC & Real-Time Mode — 安全处理变化数据

| 特性 | 说明 |
|:-----|:------|
| **Auto CDC (SDP)** | Spark Declarative Pipelines 内建 SCD Type 1 变更数据捕获 |
| **CHANGES 子句** | DSv2 Connector 暴露变更流，SQL/DataFrame/PySpark 统一查询 |
| **DSv2 CDC 标准化** | 所有 DSv2 Connector 统一接口暴露变更流 |
| **RTM PySpark 支持** | Real-Time Mode 扩展至 PySpark（stateless queries） |
| **RTM 性能数据** | P95 < 0.5ms, P99 = 1ms, 69,713 rows/sec（4 worker i3.xlarge） |
| **Stateful RTM** | 规划中（SPARK-54699），含 streaming shuffle + 并发 stage scheduling |

> **意义**: Spark 4.2 将 CDC 和实时流处理拉平到同一引擎。RTM 的 PySpark 支持标志着 Spark 开始用单一栈覆盖 analytical（秒级）和 operational（毫秒级）两类负载。

#### E. 其他平台改进

| 改进项 | 说明 |
|:-------|:------|
| **Web UI** | Bootstrap 5 + Dark Mode + SQL plan 可视化 + 服务端分页 |
| **K8s** | Heterogeneous executor 管理 + 稳定的 Resource Manager API |
| **JDK 25** | 支持最新 JDK |
| **依赖升级** | Scala, Parquet, ORC, Arrow, Netty, Hadoop |

## 2. 🧠 Apache Flink Agents 0.3.0（Jun 19）

> **来源**: [Apache Flink Blog — Flink Agents 0.3.0 Release Announcement](https://flink.apache.org/2026/06/19/apache-flink-agents-0.3.0-release-announcement/)（Jun 19, 2026）
> **作者**: Wenjin Xie
> **版本**: 🔖 **Apache Flink Agents 0.3.0**（预览版）
> **状态**: ⚠️ **Preview**（0.4 做 API 打磨，之后 1.0）

### 架构定位：流式 Agent OS

Flink Agents 定位为 **Streaming Agent OS**——在 Flink 流处理管道中将 AI Agent 作为一等公民算子运行。与传统的"Human-in-the-loop" Agent 不同：

| 特征 | Flink Agents | 传统 Agent 框架（LangChain/AutoGen） |
|:-----|:------------|:-------------------------------------|
| 触发方式 | 事件驱动（system events） | 人类提示触发 |
| 执行引擎 | Flink 分布式流处理 | 单节点+API Server |
| 一致性 | Flink 的 exactly-once | 无强一致性保证 |
| 容错 | 分布式 checkpoint + 自愈 | 手动重试/无状态 |
| 状态管理 | Flink State + Fluss/Kafka | 内存/外部数据库 |
| 规模 | 每秒百万级事件 | 取决于 API Server 吞吐 |

**三类典型场景**: AIOps（日志/指标/告警流→即时异常检测诊断）· 实时风控（毫秒级交易审批）· IoT（设备流→自主决策）· 实时多模态（音视频流→即时理解响应）

### 0.3.0 关键新特性

#### Agent 原语

| 特性 | 说明 |
|:-----|:------|
| **Agent Skills** | 将 prompt/tools/resources 封装为自包含能力单元，按需加载（Python + Java API） |
| **Mem0 长期记忆** | 替换 v0.2 的 vector-store 实现，提供更强的语义检索/摘要/隔离能力 |

#### 编程模型

| 特性 | 说明 |
|:-----|:------|
| **YAML API** | 声明式 YAML 定义 Agent 资源（chat model connections/prompts/tools/vector stores），逻辑层用 Python/Java 代码引用 YAML 中的 function pointer |
| **跨语言 Action** | 一个语言的 Action 可在另一个语言的 Agent 内运行（Python→Java 互调）|
| **JSON Schema** | 随 YAML API 发布，IDE 校验+自动补全+LLM 辅助创作 |

#### 可靠性 & 可观测性

| 特性 | 说明 |
|:-----|:------|
| **Durable Reconciler** | Durable execution 内的 side effect 在故障恢复时 reconciler 自动调和 |
| **Fluss Action State Store** | 新增 Apache Fluss（Incubating）作为 Action State 后端 |
| **EventLog** | Flink WebUI 默认显示；支持 per-event-type 日志级别配置 |
| **Metrics** | 模型维度和 Action 维度的 key-value metric groups + chat-model retry metrics |

#### 生态集成扩展

- **Chat Models**: Amazon Bedrock, Azure OpenAI, OpenAI Responses API
- **Embedding Models**: Amazon Bedrock, Tongyi
- **Vector Stores**: Amazon OpenSearch, Amazon S3 Vectors, Milvus, Mem0

## 3. 🛡️ GRID: Grammar-Railed Decoding for Enterprise SQL（arXiv Jul 11）

> **来源**: [arXiv:2607.11951](https://arxiv.org/abs/2607.11951) — Mohsen Arjmandi（Jul 11, 2026）
> **版本**: KDD 2027 审稿中
> **状态**: 📄 论文 + 开源（arXiv）

### 核心贡献

GRID 是面向企业 T2S 部署的语法约束解码引擎，核心创新：**以 LALR(1) 解析器状态为 Key 计算 Next-Token Mask**（而非 Token 序列）。

| 指标 | 数值 |
|:-----|:----:|
| **Per-token Mask** | **3.6–6.7 μs**（Rust 内核，领先 llguidance 的 p50 & p90） |
| **执行精度提升** | +13 pp（0.5B 模型，Spider 基准） |
| **7B + Checker-guided Repair** | 94.5% 可执行 |
| **RBAC 编译进语法** | Role projection 子集化 grammar productions + schema lexicons 限制 identifier terminals → Forbidden verbs/identifiers 在 Mask 层级不可生成 |
| **审计追踪** | Hash-chained per-token，100% 篡改检测，bit-identical replay |
| **Token 开销** | Position-flat at n=16,000 |

### 四大形式化保证

1. **Soundness**: Mask 拒绝所有无效 token → 输出语义有效
2. **Completeness**: Mask 允许所有语法正确的 token
3. **Termination**: 解码总能在有限步数内完成
4. **Cost**: Per-token cost 近乎常数（不随序列长度增长）

### 已知局限（作者明确说明）

- ❌ Distribution faithfulness（mask 不保证概率分布保真）
- ❌ Column-level RBAC（mask 层无法覆盖列级权限 → 需要 PCC-SQL 等互补方案）
- ❌ Non-LALR(1) languages

> **与 PCC-SQL（arXiv Jul 14）的关系**: GRID 解决**表级**语法约束（Schema/RBAC），PCC-SQL 解决**列级**访问控制（三分类+确定性 Mask）。二者结合可获得 T2S 安全部署的全栈覆盖。

## 4. 🔄 Double Ratchet: 自进化评估指标与 T2S Agent（arXiv Jul 14）

> **来源**: [arXiv:2607.12790](https://arxiv.org/abs/2607.12790) — Xing Zhang, Guanghui Wang 等（Jul 14, 2026）
> **状态**: 📄 论文（arXiv）

### 核心问题

自进化 Agent 通过创建/修订/淘汰自己的 Skills 来提升，但这一切依赖一个前提假设：**已经存在可靠的评估指标**。在真实企业场景中，Ground Truth 往往不存在。

### Double Ratchet 架构

**双重棘轮**: Metric 进化 + Skill 进化 协同驱动：

| 棘轮 | 机制 | 产出 |
|:----|:-----|:-----|
| **Metric Ratchet** | 搜索小缺陷检测器的组合 → 进化生命周期 → 10-item anchor reference 训练 → consensus over unlabeled outputs → held-out anchor 审计 | 透明、可检视的评估指标 |
| **Skill Ratchet** | 生命周期管理的 skill 创建/修订/淘汰循环 | 持续改进的执行技能 |

### 关键结果

| 场景 | 表现 |
|:-----|:------|
| **Spider 2.0-Snow**（Enterprise T2S） | 保留 88–110% Ground Truth 提升量 |
| **Code Gen（MBPP+）** | 同类结果 |
| **无参考报告生成** | 同类结果 |

### 安全机制

- **Anchor Guard**: 移除此守卫 → Metric 坍缩为空检测器（而移除 Lifecycle 不会）
- **外部审计**: Skill Game 报告 rubric → 独立 Judge 捕获 → Detector 修复
- **Task-aware Judge**: 修复后 77% 的 dicide pairs 倾向进化后输出

> **意义**: Double Ratchet 提出"预期失败"（Failure-expecting）架构——在没有可靠自动验证器的场景下，Metric 和 Skill 必须协同进化，且必须有外部审计作为安全垫。

## 5. 📊 Delta Lake vs Iceberg vs Hudi 基准实验（arXiv Apr 23）

> **来源**: [arXiv:2604.21449](https://arxiv.org/abs/2604.21449) — Ivan Borodii, Halyna Osukhivska（Apr 23, 2026）
> **状态**: 📄 论文（已发表：Information Technology journal）

### 实验设计

- **平台**: Apache Spark
- **数据**: 结构化（CSV）+ 半结构化（JSON），最大 7GB
- **流程**: 4 个顺序 ETL（read → transform → load）
- **评价维度**: (1) 加载时间 (2) 存储空间

### 三格式对比结论

| 维度 | Delta Lake 🥇 | Apache Iceberg 🥇 | Apache Hudi |
|:-----|:-------------|:------------------|:------------|
| **加载速度** | ✅ **最快**（任意数据量） | ❌ 较慢 | ❌ 最慢 |
| **存储效率** | 中等 | ✅ **最优**（磁盘空间节省） | 较差 |
| **稳定性** | 良好 | ✅ **最稳定** | 一般 |
| **增量/流式** | 一般 | 一般 | ✅ **潜在优势**（实验未充分验证） |
| **适宜场景** | 加载性能优先的系统 | 存储稳定性和空间节省优先的系统 | 增量更新 + 流式处理场景 |

> **建议**: 架构选型应根据负载特征——**重加载轻存储选 Delta Lake，重存储轻加载选 Iceberg，增量流式优先选 Hudi**。没有"最优秀"，只有"最匹配"。
