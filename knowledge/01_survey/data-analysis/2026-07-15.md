## 1. 🏗️ UC Managed Tables 外部引擎访问 Public Preview（Databricks Jul 13）

> **来源**: [Databricks Blog — How Unity Catalog managed tables bring interoperability, performance, and unified governance](https://www.databricks.com/blog/how-unity-catalog-managed-tables-bring-interoperability-performance-and-unified-governance)（Jul 13, 2026）
> **作者**: Alex Jiang, Tathagata "TD" Das
> **状态**: ✅ **Public Preview**

### 核心变更

UC Managed Delta Tables 此前不支持外部引擎写入——引擎只能用 External Tables（缺性能优化和治理保证）。现在：

| 能力 | 说明 |
|:-----|:------|
| **多引擎 CRUD** | Apache Spark（批量+流式）、Apache Flink、Starburst、**DuckDB**、StreamNative 均可创建/读写 |
| **Catalog Commits（GA）** | UC 作为提交协调器，外部客户端不再直接对云存储提交 |
| **Predictive Optimization** | 自动清理/统计收集/液氮聚类（Liquid Clustering） |
| **升级路径** | `ALTER TABLE SET MANAGED` 就地升级，不重写数据 |
| **外部基线** | 基于 UC OSS 开放 API（Metadata + Credential Vending + Commit） |

### 支持引擎对比

| 引擎 | 能力 | 底层技术 |
|:----|:----|:---------|
| **Apache Spark** | 批量 + Streaming CRUD | Delta Lake 4.3 + UC Client 0.5.1 |
| **Apache Flink** | 流写入（Kernel 连接器） | Delta Kernel 新 Flink 连接器（实验性 → GA 中） |
| **Starburst** | CRUD | UC OSS Delta API |
| **DuckDB** | CRUD | Delta Kernel 扩展（v1.5.1） |
| **StreamNative** | 流式 | Pulsar → Delta 管道 |

### 💡 架构意义

这是 Lakehouse 走向**湖仓原生互操作**的关键里程碑：

```
以前：External Table（缺优化）    vs    Managed Table（独占）
     +-- 被迫在「性能」和「开放性」间二选一

现在：UC Managed Table（优化 + 治理 + 多引擎）
     +-- 一个治理层，统一掌控多种引擎的读写
```

**核心对手对标**：Iceberg 的 Catalog 模型天然支持多引擎——Delta 用 UC Delta API 等效对齐，关键在于 Delta Kernel + UC OSS 让引擎接入成本从「重写协议」降至「调用 Kernel 库」。

## 2. ⚡ GRID — 语法约束解码引擎（arXiv Jul 11）

> **来源**: [arXiv:2607.11951 — GRID: Grammar-Railed Decoding for Enterprise SQL Generation](https://arxiv.org/abs/2607.11951)（Jul 11, 2026）
> **作者**: Mohsen Arjmandi
> **状态**: 扩展版，KDD 2027 审稿中

### 架构概要

GRID 是一个 Rust 内核的语法约束解码引擎，核心设计：

| 组件 | 设计选择 | 性能 |
|:-----|:--------|:----:|
| **Mask 键** | Parser 配置（lexer scan state × LALR(1) stack）而非 Token 序列 | 缓存命中率不随长度衰减 |
| **Viable Prefix Oracle** | 直接用增量 LALR(1) 解析器本身 | 不需要预计算 |
| **Token ←→ Grammar 桥接** | byte-level trie walk + CI/CD split | Cache-key soundness 由构造保证 |
| **RBAC 编译进语法** | Role 投影子集 Grammar Production + Schema Lexicon 限制标识符 | 禁止的动词/标识符在 Mask 层不可达 |

### 性能数据

| 指标 | 数值 | 对比 |
|:----|:----:|:----:|
| **Per-token Mask 中位数** | **3.6–6.7 μs** | 领先 llguidance（p50 和 p90） |
| **False Rejects** | **0** | 无虚假拒绝 |
| **位置平坦性（n=16,000）** | ✅ | 位置无关的常数开销 |
| **Spider +13 执行精度** | 0.5B 模型 | 约束解码 vs 无约束 |
| **7B 可达 94.5% 可执行** | 一次 Checker-guided Repair | 补列级政策的残留不可执行部分 |
| **审计链** | Hash-chained per-token | 100% 篡改检测，位一致回放 |

### 四项正式保证

| 保证 | 前置条件 | 验证方式 |
|:-----|:--------|:--------:|
| **Soundness** | Grammar 覆盖目标语言 | ✅ Benchmark |
| **Completeness** | 不缩窄 Grammar | ✅ Benchmark |
| **Termination** | 有限 Token 空间 | ✅ Formal |
| **近常数 Per-token 成本** | 缓存命中 | ✅ 位置平坦性测试 |

### 💡 工程含义

GRID 是 **Text-to-SQL 从「实验场景」走向「企业部署」所需的关键基础设施**：

- 语法有效 + 权限合规 + 审计可追溯 + 常数延迟 → 缺一不可
- Rust 内核的 3.6μs 意味着在生产中几乎**零额外延迟**
- 「编译 RBAC 进语法」使**违反权限的 SQL 在 Token 级别不可能生成**——无需后过滤

## 4. 🛡️ PCC-SQL — 列级访问控制的约束解码（arXiv Jul 14）

> **来源**: [arXiv:2607.12341 — Policy-Conditioned Constrained Decoding for Column-Level Access Control in Text-to-SQL](https://arxiv.org/abs/2607.12341)（Jul 14, 2026）
> **作者**: Ryoto Miyamoto, Xin Fan, Hayato Yamana

### 问题与解法

| 维度 | 现有方法 | PCC-SQL |
|:-----|:--------|:--------|
| **策略判定依据** | 查询提及的列名 | 列的**语义用途**（output/filter/aggregation 角色） |
| **执行方式** | 随机（stochastic）拒绝 | **确定性**单次解码 Mask |
| **覆盖** | 可能遗漏变通写法 | 支持 SQL 片段的**0% Leakage Rate** |
| **额外 Token** | — | **< +10%** |

### 方法

```
策略定义：列用途三分类（输出 / 过滤条件 / 聚合参数）
    v
Grammar Productions 对齐：每个角色与解码器跟踪的语法产生式绑定
    v
Per-token Logits Mask：确定性消除单条查询的列用途违规
```

### 效果

| 指标 | 数值 |
|:-----|:----:|
| **Leakage Rate** | **0%**（确定性保证） |
| **Coverage** | **88.7%**（Spider-CU） |
| **额外 Token 开销** | < +10% |
| **模型** | 3 种开源模型验证 |

### 💡 与 GRID 互补

PCC-SQL 解决的是 GRID 声称「Mask 无法处理」的**列级 RBAC**：GRID 明确承认 Column-level Policy 是「provably mask-unenforceable residue」，需要用 repair pass 补救。PCC-SQL 通过**将列用途语义编入 Grammar Production** 来实现 mask 级别的列级控制。二者结合可获得更完整的约束覆盖。

## 5. 🔄 Double Ratchet — 自进化 T2S 评估指标的演进（arXiv Jul 14）

> **来源**: [arXiv:2607.12790 — Who Grades the Grader? Co-Evolving Evaluation Metrics and Skills for Self-Improving LLM Agents](https://arxiv.org/abs/2607.12790)（Jul 14, 2026）
> **作者**: Xing Zhang, Guanghui Wang, Yanwei Cui et al.

### 核心问题

自进化 Agent 系统依赖一个隐藏假设：存在可靠的评估指标。在 Spider 2.0-Snow 等真实企业 T2S 场景中，**这个假设不成立**——没有可用的 Ground Truth 指标。

### Double Ratchet 架构

```
Metric Loop（指标进化）               Skill Loop（技能进化）
    v                                       v
搜索小缺陷检测器的组合 <--> 锚点参考集     创建/修改/退役技能
    v                                       v
未标注输出上的共识正则化                  执行 -> 评估
    v                                       v
外部审计 vs 保留锚点                      <- Metric 提供评分 ->
```

### 关键发现

| 维度 | 结果 |
|:-----|:-----|
| **Co-Evolution 有效性** | 在 Spider 2.0-Snow 保留 Ground Truth 驱动的 **88–110%** 提升 |
| **Metric 退化防护** | 移除锚点守卫 → Metric 崩塌为空检测器；移除生命周期则不会 |
| **安全防护** | 技能作弊 → 独立 Judge 发现 + 修复器修补 |
| **人类偏好** | 77% 的已决对偏好进化后输出 > 进化前基线 |

### 💡 含义

当企业 T2S 系统部署后，**Ground Truth 不可得**（没有标准 SQL），Double Ratchet 提供了一种**可自持的提升回路**——指标和技能共同进化，且有空检测器防护机制。
