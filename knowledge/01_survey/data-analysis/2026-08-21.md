## 一、TL;DR 速览

- **架构反思成为主旋律**：DATER 论文（2606.08811）提出六架构技术需求评估框架；《What Went Wrong with Data Lakes?》（2606.08266）基于 15 年 500 条实地记录总结"七大反模式"，提出**治理债务（Governance Debt）**与**治理引力（Governance Gravity）**两个新概念——湖仓/数据网格技术前进、组织治理记录几乎未动。
- **开放表格式进入实证对比阶段**：2604.21449 首次系统对比 Hudi/Iceberg/Delta Lake 在 Spark 下的加载与存储效率（CSV/JSON、最高 7GB 文件），结论 Delta Lake 加载最快、Iceberg 稳定省空间、Hudi 适合增量流场景；2508.13396 在汽车遥测场景给出差异化结论——Delta Parquet 强在 ML 就绪与治理、Iceberg 强在批分析云原生、Hudi 强在实时摄入。
- **AI×湖仓从概念走向工程化**：BatteryLake（2607.09762）用 LLM agent + 26 条规则门控构建电池老化数据湖仓基准（41 数据集/25 机构）；Bauplan 团队提出"proof-carrying agents"（2510.09567）让不可信 AI agent 在数据湖仓上安全运行；数据库在 GenAI 中的角色被系统化分类（2503.04847）。
- **事务正确性仍是开放表格式短板**：LakeVilla（2504.20768）为 Iceberg/Delta 补充多表事务与隔离，性能开销仅 2% YCSB 写入 / 2.5% TPC-DS 读——说明 OTF 元数据设计"天然缺事务"的论断被再次验证，且修补成本可控。
- **成本与调度成为云湖仓新战场**：LeJOT（2512.18266）在 Databricks 上以 ML 预测 + 求解器编排实现平均 20% 云成本下降；Snowpark（2508.05904）披露其安全沙箱与 Python 包缓存架构（ICDCS 2025 论文）。
- **跨组织数据共享的联邦化路径**：EDSP（2512.03401）以 Write-Once Read-Anywhere 原则减少 33-44% 操作步骤（代价是查询延迟最高 2.6×，端到端仍为秒级）。

## 二、架构范式反思：DATER 框架与"数据湖的七宗罪"

### 2.1 DATER：六种现代数据架构的技术需求评估框架

- **来源/标题**: *Data Architectures and their Technical Requirements (DATER)*（arXiv 2606.08811，2026-06-07，Sayed Hoseini / Christoph Quix / Stefan Decker）
- **URL**: https://arxiv.org/abs/2606.08811
- **要点**: 提出 DATER 概念框架，系统描述并评估六种现代数据架构——数据仓库（Data Warehouse）、（语义）数据湖（Data Lake）、**数据湖仓（Data Lakehouse）**、数据编织（Data Fabric）、数据网格（Data Mesh）。每种架构按**历史背景、定义特征、DATER 维度符合度**三维分析。研究价值在于帮助研究者与实践者在架构范式丛林中导航、澄清重叠、明确各自优势/局限/适用场景。
- **要点**: 该框架把"技术需求"作为第一性评估维度——即脱离厂商营销话术，从数据集成方式、治理能力、分析就绪度、实时性、扩展模式等技术特征出发横向比较，而非按"谁更先进"排序。
- **要点**: 六架构被置于同一坐标系，意味着湖仓不再是"数据湖的升级版"这一线性叙事，而是与数据编织/数据网格并列的**并行范式**——各自解决不同治理-弹性组合问题。

**分析段落 A — 为什么需要"架构评估框架"而非"架构选型清单"**：2022-2025 年间，湖仓（Lakehouse）从 Databricks 的营销概念演变为 Iceberg/Delta/Hudi 三足鼎立的工程事实，但行业对"何时该用湖仓、何时该用数据编织"的决策仍高度依赖厂商叙事。DATER 的价值在于把评估从"名字崇拜"拉回"技术需求符合度"：它承认六种架构各有适用域，湖仓的 ACID + 开放格式组合在"批分析 + BI + ML"场景最优，但数据网格在"跨域自治"场景、数据编织在"虚拟化集成"场景仍有不可替代性。这一框架与 2026 年行业从"上湖仓"转向"按场景组合架构"的趋势一致——企业不再追求单一架构通吃，而是以湖仓为底座、以编织/网格做边缘扩展。

**分析段落 B — 从 DATER 看湖仓的边界条件**：DATER 把湖仓定义为"数据湖的存储弹性 + 数据仓库的治理/分析能力"的组合体，这隐含两个边界条件：其一，湖仓的治理能力依赖开放表格式（OTF）的元数据层，当多表事务、跨目录一致性需求出现时（见第五章 LakeVilla），OTF 原生的单表设计会成为瓶颈；其二，湖仓的"分析就绪"以批处理/近实时为默认，对毫秒级交互查询仍需外接 OLAP 引擎。DATER 提醒实践者：湖仓是"治理与弹性"的折中解，不是"所有问题"的最终解。

### 2.2 《数据湖哪里出了问题？》——15 年现实检查与治理债务理论

- **来源/标题**: *What Went Wrong with Data Lakes? A 15-Year Reality Check from the Field*（arXiv 2606.08266，2026-06-06，Youssef Gahi）
- **URL**: https://arxiv.org/abs/2606.08266
- **要点**: James Dixon 于 2010 年提出 Data Lake 概念——"原始存储、推迟 schema、削减前期转换"，承诺灵活性与易分析性。**15 年后该承诺基本落空**：多份调查持续报告大数据项目/数据湖/数据科学项目的高失败率。论文阅读 64 份资料（学术 + 分析师报告 + 实践者记录），提炼出**七大反模式（Seven Deadly Sins of Data Lakes）**。
- **要点**: 提出核心解释机制——**治理债务（Governance Debt）**：组织不断推迟的治理决策以复利方式累积成本。第二个自发现模式：当治理变难时，组织会漂移回结构化、仓库式方法，作者命名为**治理引力（Governance Gravity）**。
- **要点**: 为业界滥用词"数据沼泽（Data Swamp）"给出可测量定义与指标，并提供**治理债务评估模型（Governance Debt Assessment Model）**定性量表用于早期捕获衰退。
- **要点**: 论文基石不仅是分析文献，还包含**作者 15 年间在摩洛哥与西非金融/电信行业构建与拯救企业数据湖的近 500 条实地记录**——独立于文献汇编，结论收敛到相同反模式，且补充了两个文献低估的维度：**运维债务（operational debt）与工程纪律债务（engineering-discipline debt）**，并从新兴市场视角重读问题。
- **要点**: 对湖仓/数据网格的追问结论尖锐：**技术前进了，组织记录几乎没动**（"the technology advanced, the organizational record barely moved"）。为实践者提供两个工具：现实检查框架（Reality Check Framework）与阶段化干预矩阵（Stage-Based Intervention Matrix）。

**分析段落 C — 治理债务的因果链：为什么"先存后治"必然失败**：数据湖的原始承诺建立在"推迟 schema = 推迟成本"的假设上，但该假设忽略了治理决策的时间不对称性：**schema 决策推迟一天，未来每个消费方都要多付一次解释成本；而解释成本不会随时间消失，只会随数据规模与消费方数量复利增长**。这正是"治理债务"与金融债务的类比成立之处——利息（解释/修复成本）持续累积，最终债务违约（项目失败/数据沼泽化）。七大反模式（无元数据、无所有权、无质量门禁、复制蔓延等）本质上是"推迟治理"在不同环节的具体投影。论文将其根因定性为**组织性远多于技术性**，与数据湖行业"重平台轻治理"的普遍实践互为印证。

**分析段落 D — 治理引力与湖仓的"结构化回归"宿命**："治理引力"描述了数据湖实践中的一个吊诡现象：当治理变难时，团队不是补治理，而是**逃回仓库式结构**（建模先行、schema-on-write、ETL 强约束）。这一现象在湖仓时代并未消失——Iceberg/Delta 的 schema enforcement 本质上是"治理引力"的技术化实现：把约束从组织流程转移到表格式强制。但论文指出：湖仓只是把"治理债务"从存储层挪到元数据层，**组织层面的数据所有权与消费契约问题依旧悬而未决**。这对数据中心/AI 基础设施的启示是：湖仓平台建设必须配套数据治理组织设计，否则技术升级只是延迟了"治理引力"的回归时刻。

| 维度 | 数据湖(2010 承诺) | 现实检查(2026 实测) | 湖仓/数据网格是否解决 |
|:--|:--|:--|:--|
| 存储灵活性 | 原始存储、schema 后置 | ✅ 兑现，但代价是解释成本复利 | 部分（schema enforcement 强制） |
| 分析易用性 | 即存即分析 | ❌ 高失败率，数据沼泽普遍 | 部分（ACID + 分析就绪） |
| 治理成本 | 推迟 = 节省 | ❌ 治理债务复利累积 | 未解决（组织层债务仍在） |
| 组织适配 | 技术问题 | 根因是组织/流程问题 | **基本未动** |
| 典型失败模式 | — | 七大反模式 | 部分反模式被格式约束，组织类未解 |

**分析段落 E — 新兴市场视角的独特增量**：论文的 500 条实地记录来自摩洛哥与西非——这一视角在数据湖文献中稀缺。新兴市场场景（资源受限、人才稀缺、网络不稳定）放大了两类文献低估的债务：**运维债务**（管道运行成本、集群维护、网络带宽约束下的数据搬运）与**工程纪律债务**（团队缺乏统一工程规范导致的质量漂移）。这对国内企业数据平台建设有直接借鉴：在"降本增效"与"信创替代"双重压力下，运维债务与工程纪律债务往往比元数据治理更早压垮平台——平台建设优先级应从"能力堆叠"转向"债务最小化"。

## 三、开放表格式工程对比：两篇独立实证

### 3.1 Spark 加载/存储效率：Hudi vs Iceberg vs Delta Lake

- **来源/标题**: *Research on the efficiency of data loading and storage in Data Lakehouse architectures for the formation of analytical data systems*（arXiv 2604.21449，2026-04-23，Ivan Borodii / Halyna Osukhivska）
- **URL**: https://arxiv.org/abs/2604.21449
- **要点**: 首次系统对比三大湖仓系统（Apache Hudi / Apache Iceberg / Delta Lake）在 Apache Spark 分布式处理下的**数据加载与存储效率**。测试覆盖结构化（CSV）与半结构化（JSON）数据、多种规模（最高 7GB 文件），四个顺序 ETL 流程（读取→转换→加载→成表）。
- **要点**: 评估双准则：**数据加载时间**与**文件系统中成表体积**。实验结论：**Delta Lake 是"加载速度优先"场景的最优架构（任意数据量）**；**Apache Iceberg 适合"稳定性 + 磁盘空间节省"优先**；**Apache Hudi 在加载/存储评估中表现不佳，但可能在增量更新与流处理场景有效**。
- **要点**: 该研究发表于《Information Technology: Computer Science, Software Engineering and Cyber Security》No.4 (2025)，DOI: 10.32782/IT/2025-4-4。

| 评估维度 | Delta Lake | Apache Iceberg | Apache Hudi |
|:--|:--:|:--:|:--:|
| 加载速度（任意规模） | 🥇 最优 | 中等 | 偏慢 |
| 磁盘空间节省 | 中等 | 🥇 最优 | 偏大 |
| 稳定性 | 良好 | 🥇 最优 | 一般 |
| 增量更新/流处理 | 支持 | 支持 | 🥇 潜在最优 |

**分析段落 F — 为什么"加载最快"与"存储最省"不能兼得**：三格式的本质差异在写入路径的元数据开销结构。Delta Lake 的 transaction log（JSON 格式 _delta_log）写入轻量、对单分区追加友好，因此加载最快；Iceberg 的 manifest 分层（metadata → manifest list → manifest file → data file）提供更强的文件裁剪与统计信息，代价是**写入路径多一层元数据序列化**，换取的是更优的查询剪枝与空间复用（快照隔离下可安全删除孤儿文件）；Hudi 的 timeline + record-level index 设计面向"行级更新/增量拉取"，其 MOR（读时合并）与索引维护在纯批量加载场景成为净开销。**选择本质是"写路径成本"与"读路径收益"的权衡**——这与 2508.13396 汽车场景结论（Delta 强 ML 就绪、Iceberg 强批分析、Hudi 强实时摄入）完全互洽。

### 3.2 汽车行业时序遥测：Delta Parquet vs Iceberg vs Hudi

- **来源/标题**: *A Comparative Study of Delta Parquet, Iceberg, and Hudi for Automotive Data Engineering Use Cases*（arXiv 2508.13396，2025-08-18，Dinesh Eswararaj / Ajay Babu Nellipudi / Vandana Kollati，SSRG IJCSE July 2025）
- **URL**: https://arxiv.org/abs/2508.13396
- **要点**: 用真实车联网时序遥测数据（车辆 ID、时间戳、位置、事件指标字段）对比三种格式，评估维度：建模策略、分区、CDC 支持、查询性能、扩展性、数据一致性、生态成熟度。
- **要点**: 结论：**Delta Parquet 提供强 ML 就绪性与治理能力**；**Iceberg 在批分析与云原生工作负载上高性能**；**Hudi 面向实时摄入与增量处理优化**。三格式在查询效率、时间旅行（time-travel）、更新语义上各有取舍。
- **要点**: 场景应用指向：车队管理、预测性维护、路线优化的数据管道与 ML 模型集成。

**分析段落 G — 两篇实证的互补性：领域差异如何改变格式排序**：2604.21449 与 2508.13396 表面结论相似（三格式各有定位），但细节差异值得注意：前者在通用分析系统场景将 Hudi 评为"加载/存储不理想"，后者在汽车遥测场景强调 Hudi 的**实时摄入**价值——差异源于数据特征：遥测数据是**高基数、持续追加、带时间序**的流式形态，正是 Hudi record-level upsert 的用武之地；而通用分析负载是批量、面向全量扫描，Hudi 的索引维护反成负担。**这验证了湖仓选型的领域依赖性：格式没有绝对优劣，只有与工作负载的匹配度**。对国内智能汽车/车联网数据平台，参考路径是：实时遥测入湖用 Hudi/MOR，批分析用 Iceberg，ML 特征库用 Delta——多格式共存已成为 2026 年湖仓工程的主流形态。

## 四、AI×湖仓：从概念验证到治理工程化

### 4.1 BatteryLake：Agentic + 物理约束的电池老化数据湖仓

- **来源/标题**: *BatteryLake: Agentic, Physics-Grounded Curation of Heterogeneous Battery Aging Data and Benchmarking*（arXiv 2607.09762，2026-07-06，Tianwen Zhu / Hao Wang / Yonggang Wen）
- **URL**: https://arxiv.org/abs/2607.09762
- **要点**: 电池老化公开数据集是健康管理的关键资产，但受限于格式不一致、schema 不清、元数据分散。BatteryLake 构建**治理型数据湖仓**，以 agentic + 物理约束策展框架把原始数据转为 benchmark 就绪资产。
- **要点**: 三大贡献：① **LLM agents 提取元数据并合成数据集专属转换器**，每个输出锚定在逐字证据上，无证据支持则弃权（abstain）；② **人机协同验证**：将验证框架化为选择性预测（selective prediction），通过 **26 条 schema/统计/物理合理性规则**门控数据入库；③ 发布**开放基准：41 个数据集、25+ 机构**，标准化 SOH（健康状态）与 RUL（剩余寿命）任务、三种划分协议、八类基线模型族。
- **URL**: 平台/基准/协议开源：https://tianwen1209.github.io/batterylake/

**分析段落 H — "证据锚定 + 弃权"为何是 agentic 数据治理的关键设计**：BatteryLake 的两个设计决策直击 LLM 数据工程的两大失败模式：幻觉与过度自信。**证据锚定**（每个元数据/转换器输出必须引用原始数据中的逐字证据）把 LLM 从"自由生成者"降级为"证据标注者"，从机制上阻断无中生有；**弃权机制**（无证据支持则不输出值）把"宁可错过不可编造"编码进系统行为。这与 2510.09567（proof-carrying agents）的"正确性证明携带"哲学同构——**2026 年 AI×湖仓的核心命题不是"让 agent 做更多"，而是"让 agent 的错误可被证明、可被拦截"**。26 条规则中的"物理合理性"尤其值得注意：对电池电化学时序数据，电压/容量曲线违反物理规律即可判定异常——**领域物理先验成为比统计规则更强的校验器**。

### 4.2 Proof-Carrying AI Agents：不可信 agent 的安全运行范式

- **来源/标题**: *Safe, Untrusted, "Proof-Carrying" AI Agents: toward the agentic lakehouse*（arXiv 2510.09567，2025-10-10，Jacopo Tagliabue / Ciro Greco，IEEE Big Data Workshop on Secure and Safe AI Agents）
- **URL**: https://arxiv.org/abs/2510.09567
- **要点**: 数据湖仓运行敏感工作负载，AI 自动化引发信任/正确性/治理担忧。作者论证：**API-first、可编程的湖仓为安全默认的 agentic 工作流提供正确抽象**。以 Bauplan 为案例，展示**数据分支（data branching）与声明式环境**如何自然扩展到 agent——在获得可复现性与可观测性的同时缩减攻击面。
- **要点**: 概念验证中，agent 用**受 proof-carrying code 启发的正确性检查修复数据管道**；原型证明不可信 AI agent 可在生产数据上安全运行，勾勒通往"完全 agentic 湖仓"的路径。

**分析段落 I — 为什么"数据分支"是 agent 安全的天然隔离机制**：传统 agent 执行数据管道时，权限边界难以界定——agent 需要读写生产数据，又不能在出错时污染生产。Bauplan 的答案是把**版本控制中分支的思想移植到数据**：agent 在数据分支（branch）上执行，验证通过后合并（merge）回主分支，与 Git 工作流同构。这带来三重安全收益：① **失败隔离**——agent 的破坏性操作只影响分支，不触及生产快照；② **可复现性**——每次 agent 执行对应确定的数据版本，审计可回溯；③ **最小权限**——agent 只获得对分支的写权限，生产主分支仅经人类审查合并。该模式与 08-17 系统中"git 回滚 + tmp/bak + log"的强保护策略在哲学上一致——**用版本化隔离替代信任假设，是 agent 时代数据安全的第一性方案**。

### 4.3 数据库在 GenAI 应用中的角色分类

- **来源/标题**: *Role of Databases in GenAI Applications*（arXiv 2503.04847，2025-03-05，Santosh Bhupathi）
- **URL**: https://arxiv.org/abs/2503.04847
- **要点**: 将数据库在 GenAI 工作流中的角色按上下文类型三分：**会话上下文**（key-value/文档数据库）、**情境上下文**（关系数据库/数据湖仓）、**语义上下文**（向量数据库）——各司其职地丰富 AI 生成响应。强调实时查询处理、向量语义检索、数据库选型对模型效率与扩展性的影响。
- **要点**: 多数据库组合策略让 GenAI 应用实现更上下文感知、个性化、高性能的响应。

**分析段落 J — 湖仓在 GenAI 中的定位：情境上下文的中枢**：该分类明确了湖仓不是 GenAI 的"数据仓库替代品"，而是**情境上下文（situational context）的供给层**——即 RAG/微调所需的、带有治理与血缘的业务数据。会话上下文（对话历史）与语义上下文（向量索引）本质上都是情境上下文的派生形态：向量库从湖仓数据嵌入而来，对话记录最终也归档于湖仓。这意味着**湖仓是 GenAI 数据链路的"源系统"与"归档层"**，其治理能力（血缘、版本、权限）直接决定 RAG 质量的上限。对数据中心/AI 基础设施的启示：向量数据库采购不应替代湖仓建设，两者是"派生"与"源"的关系。

## 五、事务正确性与性能工程

### 5.1 LakeVilla：为开放表格式补齐多表事务

- **来源/标题**: *LakeVilla: A Modular and Non-Invasive Toolbox for Lakehouse Transactions*（arXiv 2504.20768，2025-10-17 更新，Tobias Götz / Daniel Ritter / Jana Giceva，26 页 14 图 4 表）
- **URL**: https://arxiv.org/abs/2504.20768
- **要点**: 数据湖仓的核心是开放表格式（OTF），但 OTF 元数据设计天然缺失多表事务与 abort 恢复——并发多查询工作负载下可导致不可重复读、脏数据、云环境高成本。LakeVilla 以**模块化、非侵入**工具箱为 Iceberg/Delta Lake 引入**恢复、复杂事务、事务隔离**。
- **要点**: 性能影响极小：**YCSB 写入 2% 开销、TPC-DS 读取 2.5% 开销**，支持任意长事务下多读写方并发控制。

**分析段落 K — 2% 开销背后的工程判断：为什么"非侵入"比"性能极致"更重要**：LakeVilla 的核心设计约束是**非侵入（non-invasive）**——不修改 OTF 存储格式，只在元数据操作层加事务协调层。这一约束的意义远超兼容性：① **可插拔**——Iceberg/Delta 用户无需迁移数据即可获得多表事务；② **可演进**——OTF 格式版本升级不受事务层绑定；③ **生态友好**——Spark/Flink/Trino 等查询引擎无感。2%/2.5% 的极低开销说明事务协调成本可通过精心设计（锁粒度、日志合并）压缩到可忽略水平。该结论的行业含义是：**OTF 的"单表设计"缺陷不是不可修复的架构原罪，而是可通过中间层补齐的工程缺口**——这也解释了为何商业湖仓（Databricks/Onehouse）把多表事务作为差异化卖点，而开源侧正以 LakeVilla 这类方案追赶。

### 5.2 LeJOT：Databricks 上的智能作业成本编排

- **来源/标题**: *LeJOT: An Intelligent Job Cost Orchestration Solution for Databricks Platform*（arXiv 2512.18266，2025-12-20，Lizhi Ma / Yi-Xiang Hu 等，The 11th International Conference on Big Data Computing and Communications）
- **URL**: https://arxiv.org/abs/2512.18266
- **要点**: 湖仓平台作业成本管理挑战：现有方案静态配置或反应式调整，无法适配动态负载。LeJOT 用 **ML 执行时间预测 + 求解器优化模型**做实时资源分配——主动预测负载、动态分配算力、在满足性能前提下最小化成本。
- **要点**: 真实 Databricks 工作负载实验：**分钟级调度时间窗内平均降低 20% 云计算成本**，优于传统静态分配策略。

**分析段落 L — 从"反应式调优"到"预测式编排"的成本杠杆**：LeJOT 的 20% 降本来源于范式转变：传统 auto-scaling 是**反应式**（负载上升→扩容→滞后于峰值），LeJOT 是**预测式**（ML 预测作业执行时间→求解器提前决策资源→消除滞后与过度供给）。其技术栈组合（ML 预测 + 运筹求解）反映了云成本优化的成熟路线：**预测解决不确定性，求解器解决组合优化**——两者缺一不可。对国内算力平台（尤其万卡集群训练）的启示：作业级成本编排的思路可平移至"训练任务资源预留"场景，预测式调度比当前普遍的人工静态预留更贴合 GPU 稀缺但峰谷分明的现实。

### 5.3 Snowpark：Snowflake 的数据工程与 AI/ML 统一运行时

- **来源/标题**: *Snowpark: Performant, Secure, User-Friendly Data Engineering and AI/ML Next To Your Data*（arXiv 2508.05904，2025-08-07，Brandon Baker / Elliott Brossard 等 20 人，ICDCS 2025 录用）
- **URL**: https://arxiv.org/abs/2508.05904
- **要点**: Snowflake 以计算存储解耦弹性架构支持数据湖/仓库/湖仓/网格多种架构，Snowpark 是其中支撑 Python 等语言数据工程与 AI/ML 负载的**托管开箱方案**。核心架构：**安全沙箱隔离 Snowflake SQL 工作负载与 Snowpark 执行**、利用控制平面做分布式计算。
- **要点**: 性能创新：**Python 包缓存降低查询初始化延迟**、定制化工作负载调度、**高效行重分配（row redistribution）应对数据偏斜**。真实案例验证大规模数据工程与 AI/ML 任务的效率与有效性。

**分析段落 M — "数据旁计算"架构对湖仓性能范式的启示**：Snowpark 的关键卖点是 **"next to your data"**——把 Python 数据工程/ML 代码推送到数据所在的计算层执行，避免数据搬运。这本质上是湖仓领域对"存储计算分离"的再平衡：存储计算分离解决了弹性，却引入了**数据搬运的隐形成本**（网络、序列化、安全边界）。Snowpark 的安全沙箱 + 控制平面调度的组合说明：**分离与聚合不是二选一，而是分层——存储与弹性分离、计算与数据就近聚合**。这一设计对国内智算中心"算力池 + 对象存储"架构有直接参考：训练/推理数据应尽量在存储侧就近处理，避免反复拉取。

### 5.4 Eudoxia：可组合湖仓的 FaaS 调度模拟器

- **来源/标题**: *Eudoxia: a FaaS scheduling simulator for the composable lakehouse*（arXiv 2505.13750，2025-05-19，Tapan Srivastava / Jacopo Tagliabue / Ciro Greco）

### 6.2 EDSP：跨平台联邦访问的企业数据科学平台

- **来源/标题**: *Enterprise Data Science Platform: A Unified Architecture for Federated Data Access*（arXiv 2512.03401，2025-12-03，Ryoto Miyamoto / Akira Kasuga，WS-D2ET @ IEEE BigData 2025）
