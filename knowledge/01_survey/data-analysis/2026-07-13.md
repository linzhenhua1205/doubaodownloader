## 1. 🏆 PExA — Parallel Exploration Agent: Spider 2.0 SOTA 70.2%（ACL 2026）

> **来源**: [arXiv:2604.22934 — PExA: Parallel Exploration Agent for Complex Text-to-SQL](https://arxiv.org/abs/2604.22934)（Apr 24, 2026 / 被 ACL 2026 接收）
> **作者**: Tanmay Parekh, Ella Hofmann-Coyle, Shuyi Wang et al.
> **状态**: ✅ **ACL 2026 已接收**，Spider 2.0 **新 SOTA 70.2%**

### 核心创新：Test Coverage 范式

PExA 将 Text-to-SQL 生成重新表述为 **软件测试覆盖（Test Coverage）** 问题：

```
复杂用户查询
    v
分解 -> 一组原子/简单子查询（Test Cases）
    v
并行执行所有 sub-SQL（覆盖不同维度）
    v
收集执行结果 -> 覆盖信息聚合
    v
基于已验证信息生成最终 SQL
```

**关键设计**:
- **Test Case 分解**: 原始查询被拆分为一组更简单、原子的子 SQL，每个子 SQL 覆盖查询的一个语义维度（如 WHERE 过滤、JOIN 路径、聚合方式）
- **全并行执行**: 所有子 SQL 可以并行执行（而非顺序迭代），大幅降低延迟
- **覆盖驱动**: 基于已执行的子 SQL 结果来 Grounding 最终 SQL 生成，而非依赖 LLM 推断

### 效果对比

| 基准 | PExA（Spider 2.0） | 之前 SOTA | 提升 |
|:-----|:------------------:|:---------:|:----:|
| **Spider 2.0 Execution Accuracy** | **70.2%** | — | **新 SOTA** |

**架构意义**: PExA 验证了**并行测试覆盖优于串行迭代**——这是 Text-to-SQL Agent 设计的原则性转变。传统 Agent 逐个工具调用遍历搜索空间（慢+顺序），PExA 用一组精心设计的并行 SQL 覆盖语义空间（快+并行）。💡 **核心启示**: 正确设计的并行探索比贪心顺序迭代更高效。

## 2. 🏆 R³-SQL — Ranking + Resampling: BIRD-dev SOTA 75.03%（ACL 2026 Findings）

> **来源**: [arXiv:2604.25325 — R³-SQL: Ranking Reward and Resampling for Text-to-SQL](https://arxiv.org/abs/2604.25325)（Apr 28, 2026 / 被 ACL 2026 Findings 接收）
> **作者**: Hojae Han, Yeonseok Jeong, Seung-won Hwang et al.
> **状态**: ✅ **ACL 2026 Findings**，BIRD-dev 新 SOTA **75.03%**

### 核心创新

传统 Text-to-SQL 两阶段（生成 N 候选 → 排序选最优）有两个固有问题：
1. **排序不一致**: 功能等价的 SQL 因表面形式不同得分不同
2. **候选缺失**: 正确 SQL 根本不在候选池中时，排序无力回天

**R³-SQL 的解决方案**:

```
生成 N 个候选 SQL
    v
Step 1️⃣: 按执行结果分组（Group by Execution Result）
    v
Step 2️⃣: Group-wise Ranking（Pairwise Preference across groups + Pointwise Utility）
    +-- Pairwise: 组间两两偏好比较
    +-- Pointwise: 最佳组的 rank 和 size 决定最终得分
    v
Step 3️⃣: 评估候选池质量
    v
Step 4️⃣: 如果正确 SQL 很可能不在池中 -> Agentic Resampling（智能补充新候选）
```

### 效果对比

| 基准 | R³-SQL | 说明 |
|:-----|:------:|:-----|
| **BIRD-dev Execution Accuracy** | **75.03%** | **新 SOTA**（限定模型大小可公开的方法中） |
| Spider / BIRD / Kaggle DBQA | 一致性提升 | 5 个基准一致改善 |

**架构意义**: R³-SQL 的核心创新在「候选池不完整时重新采样」——这是 Agent 自我评估能力。之前所有方法只能在已有候选池中排序，R³-SQL 第一次能**判断候选池是否足够**并**主动补充**。

## 3. 📄 Semantic Layers — 4KB 业务文档胜过模型选择（+17–23pp）

> **来源**: [arXiv:2604.25149 — Semantic Layers for Reliable LLM-Powered Data Analytics](https://arxiv.org/abs/2604.25149)（Apr 27, 2026）
> **作者**: Michael Rumiantsau, Ivan Fokeev
> **状态**: ✅ Pair基准实验，结果显著

### 核心发现（极具实践价值）

这是一个**极度简洁但结论震撼**的实验设计：

```
实验: 100 个自然语言问题 × ClickHouse × Contoso Retail 数据集
变量控制:
  +- 条件 A: 仅给 Schema（45.5–50.5%）
  +- 条件 B: Schema + 4KB 手写业务语义文档（67.7–68.7%）
  +- 模型: Claude Opus 4.7 / Claude Sonnet 4.6 / GPT-5.4
```

### 关键结果

| 指标 | 仅 Schema | Schema + 4KB 文档 | 提升 |
|:-----|:---------:|:-----------------:|:----:|
| Claude Opus 4.7 | ~50.5% | ~68.7% | **+18.2 pp** |
| Claude Sonnet 4.6 | ~47.5% | ~67.7% | **+20.2 pp** |
| GPT-5.4 | ~45.5% | ~68.2% | **+22.7 pp** |
| 模型间差异（同条件） | ❌ 不显著 | ❌ 不显著 | — |

**统计显著性**: 所有跨条件对比 p < 0.01；同条件跨模型对比 p > 0.05（不显著）

### 核心结论

> **Semantic Layer 的存在几乎解释了所有显著方差，模型在 Tier 内的选择无关紧要。**
> 显式的业务语义并不让模型更聪明——它改变了模型被要求做的事情。

**架构意义**:
- 对于企业部署 Text-to-SQL，投资 **Semantic Layer（度量/约定/歧义消除文档）** 的 ROI 远高于升级模型
- 4KB 的精心编写文档可以让 Opus→Sonnet 级别的降级变得中性
- **Semantic Layer ≠ Schema Comment，而是独立的业务知识文档**，包含：度量定义、命名约定、歧义规则、常见反直觉行为

## 4. 🏗️ SEMA-SQL — Hybrid Relational Algebra：SQL + LLM UDF 统一查询（arXiv, May 2026）

> **来源**: [arXiv:2604.23477 — SEMA-SQL: Beyond Traditional Relational Querying with LLMs](https://arxiv.org/abs/2604.23477)（Apr 25, 2026 / v2: May 14, 2026）
> **作者**: Yin Lin, Tianjing Zeng et al.（Alibaba Group + UIUC）
> **状态**: ✅ 论文

### 核心创新：Hybrid Relational Algebra（HRA）

SEMA-SQL 提出 **HRA（Hybrid Relational Algebra）**，将传统关系代数和 LLM User-Defined Functions（UDFs）纳入统一声明式抽象：

```sql
-- HRA 示例: 将 LLM 语义匹配作为代数操作符
SELECT company_name, revenue
FROM companies
WHERE SEMANTIC_MATCH(company_name, 'enterprise software firms in California')
  -- 这不是标准 SQL，而是 HRA 中的 LLM UDF
```

### 三层系统架构

```
用户自然语言查询
    v
① Query Generation（In-Context Learning -> HRA 查询）
    +-- 自动为 LLM UDF 生成精确的自然语言规格说明
    v
② Query Optimization（基于代价的优化器）
    +-- 传统操作符 -> 标准代价估计
    +-- LLM UDF -> LLM 调用代价估计
    +-- UDF Rewriting: 将语义 JOIN 改写为批处理
    v
③ Efficient Execution
    +-- 语义 JOIN 中通过智能批处理降低 **93% LLM 调用次数**
```

### 效果与意义

| 指标 | 值 |
|:-----|:--:|
| LLM 调用减少 | **avg 93%**（语义 JOIN 批处理） |
| 查询能力 | 覆盖传统 SQL 无法表达的语义匹配/文本提取/价值判断 |

**架构意义**: SEMA-SQL 回答了一个根本问题——**LLM 在数据查询中的角色不是替代 SQL，而是作为 SQL 代数中的 UDF 操作符**。HRA 统一了关系代数和 LLM 语义能力，让优化器可以同时代价优化两类操作。

## 5. 🏗️ Databricks Synapse → Lakehouse 迁移实战指南（Jul 8, 2026）

> **来源**: [Databricks Blog — Navigating a Synapse Migration to Databricks](https://www.databricks.com/blog/navigating-synapse-migration-databricks)（Jul 8, 2026）
> **作者**: Olga Romanova, Johannes Oehler（Databricks FDE Team）
> **状态**: ✅ 实战指南

### 迁移架构概览

Synapse 是三个不同计算模型的缝合物（Dedicated SQL + Serverless SQL + Spark Pools + ADF），Databricks 提供统一方案。

### 分阶段迁移方法论

```
Phase 1️⃣ Discovery
  +- Lakebridge Profiler -> 扫描 Synapse 资产（配置+资源+查询模式）
Phase 2️⃣ Assessment
  +- Lakebridge Analyzer -> 代码复杂度分类 + 不支持结构标记 + 依赖映射
Phase 3️⃣ Design
  +- Hybrid 策略: 自动化工具->80-90% 代码转换+增量现代化
  +- BI-first 顺序: 先搬数据市集->Genie 自服务分析->后搬复杂 ETL
Phase 4️⃣ Pilot
  +- 选取一个 Lighthouse 用例完整端到端验证
Phase 5️⃣ Wave Migration（四并行走）
  +-- Ingestion: ADF -> Lakeflow Connect
  +-- Transformation: T-SQL Stored Procedure -> Databricks SQL
  +-- Orchestration: Synapse Pipelines -> Databricks Workflows
  +-- Consumption: BI 工具重定向到 Databricks SQL Warehouses
```

### 关键技术差异

| 维度 | Synapse 方式 | Databricks 方式 |
|:-----|:------------|:---------------|
| **物理优化** | HASH/ROUND_ROBIN/REPLICATE distribution + Clustered Columnstore Index | 自动（Predictive Optimization + Liquid Clustering + CLUSTER BY AUTO） |
| **字符串比较** | Case-insensitive（默认） | Case-sensitive（需 LOWER()/UPPER() 显式处理） |
| **存储优化** | 手动 Index/Partition 管理 | Delta 自动文件压缩 + Statistics + VACUUM |
| **SCD Type 2** | 自定义 Stored Proc | Delta ACID 事务两步法（过期旧记录→插入新版本） |
| **代码转换** | — | Lakebridge 自动 80-90%，剩余 10-20%（Cursor+Dynamic SQL+复杂错误处理）需要人工判断 |

### 架构启示

迁移不仅是技术项目，更应利用机会**简化架构**：
- 不要用 Delta 分区列模拟 Synapse HASH Distribution Key（高基数列不适合分区）
- **BI-first**: 先搬 Data Mart → Genie NL 分析 → 业务看见价值 → 再搬复杂 ETL
- 保留旧环境一段时间（Compute 可 Pause）作为回滚保障
- Casey's 迁移后交付时间从 8h → 4h；Italgas 移除 Synapse + Azure Analysis Services 后成本降 **73%**

## 6. 📄 LEAF-SQL / FlexSQL / FINER-SQL — 三篇工程化 T2S 突破（May–Jul 2026）

### 6.1 LEAF-SQL — 粗到细树搜索，BIRD 71.6%（ACL 2026 层次）

> **来源**: [arXiv:2605.09295 — LEAF-SQL: Level-wise Exploration with Adaptive Fine-graining](https://arxiv.org/abs/2605.09295)（May 9, 2026）

**核心**: 将 SQL Skeleton 预测转化为**粗到细的树搜索过程**，三层 Skeleton 层次：
- Level 1: 粗结构（SELECT/FROM/WHERE 存在性）
- Level 2: 中间粒度（JOIN 路径 + 聚合类型）
- Level 3: 细粒度（具体列 + 条件值）

| 指标 | 值 |
|:-----|:--:|
| **BIRD 隐藏测试集 Execution Accuracy** | **71.6%** | 超越现有搜索式和 Skeleton 方法 |

### 6.2 FlexSQL — 灵活探索+执行，Spider2-Snow 65.4%

> **来源**: [arXiv:2605.02815 — FlexSQL: Flexible Exploration and Execution Make Better Text-to-SQL Agents](https://arxiv.org/abs/2605.02815)（May 4, 2026）

**核心原则**: 在推理过程中**随时可以**探索 Schema、检查数据值、运行验证查询。不是一次性提取 Schema，而是交互式迭代。

**关键架构**:
```
用户查询
    v
多样化 Execution Plan（覆盖多种查询解释）
    v
Plan -> SQL or Python（根据任务选）
    v
两层修复: SQL 级错误 -> 可回溯到 Plan 级修订
```

| 指标 | 值 |
|:-----|:--:|
| **Spider2-Snow** | **65.4%**（gpt-oss-120b） |
| Claude Code Skill 集成 | 相对提升 **>10%** |

### 6.3 FINER-SQL — 3B SLM 匹配大模型，BIRD 67.73%（ACL 2026 接收）

> **来源**: [arXiv:2605.03465 — FINER-SQL: Boosting Small Language Models for Text-to-SQL](https://arxiv.org/abs/2605.03465)（May 5, 2026）

**核心**: 基于 GRPO 的细粒度执行反馈，替代传统的稀疏二进制奖励（0/1）：

| 奖励设计 | 说明 |
|:---------|:-----|
| **Memory Reward** | 将推理与已验证的轨迹对齐 → 语义稳定性 |
| **Atomic Reward** | 操作级重叠测量 → 对结构正确但不完整的 SQL 给部分分 |

| 指标 | 值 | 对比 |
|:-----|:--:|:----:|
| **BIRD Execution Accuracy（3B 模型）** | **67.73%** | 匹配更大 LLM |
| **Spider Execution Accuracy（3B 模型）** | **85%** | 匹配更大 LLM |
| 推理延迟 | **5.57s/sample** | 适合 on-premise 部署 |
