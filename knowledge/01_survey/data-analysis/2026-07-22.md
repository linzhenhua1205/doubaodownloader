## 1️⃣ 🏗️ TreeCat — 独立目录引擎：为大数据系统重新思考 Catalog

**来源**: [arXiv:2503.02956](https://arxiv.org/abs/2503.02956) | Mar 4, 2025 (v2: Aug 8, 2025) · **VLDB 2025 (PVLDB Vol.18)**
**作者**: Keonwoo Oh, Pooja Nilangekar, Amol Deshpande (University of Maryland)

### 核心论点

> 现有湖仓表格式（Delta Lake / Iceberg）的 Catalog 功能有**根本性局限**，需要一个**专用的数据库引擎来担当 Catalog**。

TreeCat 不是又一个表格式，而是一个**完全专用化的 Catalog 数据库引擎**，定位对标 Hive Metastore / Delta Catalog / Iceberg REST Catalog。

### 架构设计

```
                    +---------------+
                    |  TreeCat Engine|  <- 专用 Catalog 数据库
                    |  (路径式查询)  |
                    +-------+-------+
                            | MVOCC (串行化隔离)
          +-----------------+-----------------+
          |                 |                 |
    +-----v-----+   +------v------+   +------v------+
    | Spark     |   | Flink      |   | Trino       |
    | (Iceberg) |   | (Delta)    |   | (Hudi)      |
    +-----------+   +------------+   +-------------+
```

| 组件 | 设计 |
|:----|:-----|
| **数据模型** | 层次化数据模型 + **路径式查询语言**（类似文件系统路径语义） |
| **存储格式** | 针对**范围查询**和**版本化**优化，不同于通用 OLTP 的 B-tree |
| **扫描优化** | **Correlated Scan** — 多个相关查询共享扫描结果，加速批量元数据读取 |
| **并发控制** | **MVOCC** (Multi-Versioned Optimistic Concurrency Control) — 保证 **Serializable 隔离**，同时支持多客户端高并发读写 |
| **一致性** | 严格可串行化，不比 Delta Lake 的乐观并发弱，但吞吐更高 |

### 与现有方案的性能对比

| 维度 | Hive Metastore | Delta Lake | Iceberg | TreeCat |
|:----|:-------------:|:----------:|:-------:|:-------:|
| 专用引擎 | ❌ (RDBMS 通用) | ❌ (文件级) | ❌ (文件级) | ✅ **专用引擎** |
| Serializable 隔离 | ❌ | ✅ (有限) | ✅ (有限) | ✅ **全量** |
| 路径式查询 | ❌ | ❌ | ❌ | ✅ |
| 多引擎共享 | ✅ | ✅ | ✅ | ✅ **原生设计** |
| Correlated Scan | ❌ | ❌ | ❌ | ✅ |

### 架构意义

- **Catalog 正在从附属组件 → 一级引擎**。TreeCat 论证了：当数据系统的规模和多引擎需求达到一定程度，通用目录（HMS）和表格式内建目录（Delta/Iceberg）都不够，需要一个**专门优化的 Catalog 数据库**
- 与 [GitLake (arXiv:2607.08319)](https://arxiv.org/abs/2607.08319) 的 Iceberg 跨表分支形成互补：GitLake 管数据版本的分支/合并，TreeCat 管元数据的并发/隔离
- 趋势信号：**数据架构正在从"引擎+文件"两层的简单模式 → "引擎+专用Catalog+存储"三层精细化架构**演进

## 2️⃣ 🔀 跨引擎查询优化器 — 多任务学习自动路由 SQL 到最佳引擎

**来源**: [arXiv:2506.02802](https://arxiv.org/abs/2506.02802) | Jun 3, 2025
**作者**: András Strausz, Niels Pardon, Ioana Giurgiu (IBM Research Europe)

### 核心问题

Lakehouse 中同一份数据可以被多个引擎查询（Spark SQL / Presto / Trino / DuckDB），但用户需要先验知识才能决定哪个引擎跑得最快 → 选错引擎导致效率损失。

### 架构设计：跨引擎优化器

```
                    SQL Query
                       |
                       v
               +---------------+
               |  Query Plan   |  <- 带 Hint 优化的逻辑计划
               |  (optimized)  |
               +-------+-------+
                       |
               +-------v-------+
               | Learned Cost  |  <- 多任务学习模型
               |   Predictor   |    多个 Predictor Heads
               +-------+-------+     (引擎1/引擎2/...)
                       |
                成本矩阵输出
                       |
               +-------v-------+
               |  Query Router |  -> 路由到成本最低的引擎
               +---------------+
```

| 组件 | 设计 |
|:----|:-----|
| **模型架构** | **多任务学习** — 单一模型 + 多个 Predictor Heads (每个引擎/配置一个 head) |
| **输入** | 经 Hint 优化的逻辑查询计划（比未优化计划 Q-error **低 12.6%**） |
| **输出** | 各引擎的执行成本预测 → 路由到最低成本引擎 |
| **扩展性** | 新增引擎只需**微调一个新 head**，无需重新训练整个模型 |
| **支持场景** | Zero-shot (无历史数据) → Few-shot (少量训练) 平滑过渡 |

### Benchmark 结果

| 场景 | 总运行时间减少 |
|:----|:------------:|
| Zero-shot (无历史训练) | **最多 25.2%** |
| Few-shot (少量训练) | **最多 30.4%** |
| Q-error 改进 | **比未优化计划低 12.6%** |

### 架构意义

- **多引擎路由从规则驱动 → 学习驱动**：不再是 DBA 写规则（"这个查询走 Presto，那个走 Spark"），而是 ML 模型自主决策
- **多任务架构是关键设计**：共享底层特征编码 + 独立 head → 新引擎接入成本极低
- 与 `AutoSLO`（arXiv:2607.11770）和 `LeJOT`（arXiv:2512.18266）形成**三层优化体系**：跨引擎路由(查询级) → 扩缩容(分/秒级) → 成本编排(分钟级)
- **对 Lakehouse 架构的启示**：引擎多样性是优势也是负担 → 智能路由成为架构刚需组件
