## 2. 🔄 Apache Flink 2.3.0 详解 — SQL 层重大变革（Jun 25, 2026）

> **来源**: [Apache Flink 2.3.0 Release Announcement](https://flink.apache.org/2026/06/25/apache-flink-2.3.0-release-announcement/)（Jun 25, 2026）
> **版本**: Flink 2.3.0（功能版本）
> **状态**: ✅ GA，15 个 FLIP 实现

### 2.1 🏗️ SQL Changelog 操作符：FROM_CHANGELOG / TO_CHANGELOG

Flink 2.3 首次在 SQL 层提供 changelog 转换能力，之前只有 DataStream API 有 `toChangelogStream()` / `fromChangelogStream()`。

```sql
-- Append-only → Dynamic Table
SELECT * FROM FROM_CHANGELOG(
  TABLE cdc_events,
  op_mapping => 'c=INSERT, u=UPDATE_BEFORE, ...'
);

-- Dynamic Table → Append-only（归档/审计用）
SELECT * FROM TO_CHANGELOG(TABLE retract_table);
```

**架构意义**: 
- TO_CHANGELOG 是 **Flink SQL 第一个将 retract/upsert 流转为 append 形式的操作符**——极端重要但之前只能通过 DataStream API 实现
- FROM_CHANGELOG 支持自定义 `op_mapping`，可接入任意 CDC 格式（Debezium/Canal 等）
- **局限**: 2.3 覆盖有限 Basic Use Cases，`PARTITION BY`、`invalid_op_handling`、`produces_full_deletes` 等扩展在后续版本

### 2.2 🏗️ Materialized Table DDL 对等 + 刷新控制

Flink 2.3 将 Materialized Table 推到与普通表 **DDL 对等**：

```sql
-- 支持显式列定义（含 Watermark/PK），与普通表一致
CREATE MATERIALIZED TABLE enriched_orders (
  order_id BIGINT,
  event_time TIMESTAMP(3) METADATA,
  WATERMARK FOR event_time AS event_time - INTERVAL '5' SECONDS,
  PRIMARY KEY (order_id) NOT ENFORCED
) AS SELECT ...;

-- 细粒度刷新控制（START_MODE）
ALTER MATERIALIZED TABLE mt SET (
  'refresh.start_mode' = 'resume'  -- 从上一次 source offset 继续
);
```

**架构意义**:
- 以前改 Materialized Table 定义 → Drop & Recreate → 全量重刷
- 现在 `ADD/MODIFY/DROP` 列 + RENAME + `START_MODE` 可避免不必要的历史重处理
- 仅当查询优化器生成完全不同的物理计划时才会全量重刷

### 2.3 🏗️ SinkUpsertMaterializer 重构 — 显式冲突策略

这是 Flink SQL 写入 Upsert 场景的 **长期痛点修复**。当流中的 upsert key 与目标表 primary key 不同时，Flink 需要 SinkUpsertMaterializer 做中间状态维护。

**2.3 以前**: 自动执行 deduplicate → 无界状态增长 → OOM，不可控。

**2.3 变更**:
```sql
INSERT INTO target_table
SELECT * FROM source
ON CONFLICT DO NOTHING   -- 静默跳过
-- ON CONFLICT DO ERROR      -- 作业失败
-- ON CONFLICT DO DEDUPLICATE -- 显式去重（2.2 的隐式行为）
```

加上 Watermark-based compaction：
- `table.exec.sink.upserts.compaction-mode`（默认 `WATERMARK`）
- `table.exec.sink.upserts.compaction-interval`

**架构意义**: 从**隐式+不可控** → **显式+可选择**，是 Flink SQL 写入层的一次架构完善。

### 2.4 Adaptive Partition Selection — 负载自适应数据分发

基于下游任务负载动态平衡数据分布：

```
RebalancePartitioner / RescalePartitioner
       v
Adaptive Partition Selection（默认关闭）
       v
taskmanager.network.adaptive-partitioner.enabled = true
taskmanager.network.adaptive-partitioner.max-traverse-size = 4
```

**架构意义**: 传统 Hash/Rebalance 无法感知下游负载差异 → 慢任务拖慢整个作业。自适应分区基于即时 backlog 信息选择最小负载 target。

### 2.5 Native S3 FileSystem 性能要点

同期[发布的 Benchmark](https://flink.apache.org/2026/06/26/announcing-native-s3-fs/) 数据：

| 对比项 | flink-s3-fs-native | flink-s3-fs-presto | 优势 |
|:-------|:------------------:|:------------------:|:----:|
| 依赖大小 | ~13 MB JAR | 30–93 MB JAR | 瘦身 70–86% |
| Hadoop 依赖 | ❌ 零依赖 | ✅ 依赖 | CVE 面减少 |
| AWS SDK | v2（非阻塞 I/O） | v1（已 EOL） | 安全合规 |
| RecoverableWriter | ✅ 内置 | ❌ 无 | Exactly-once Sink |

**架构意义**: 既解决性能问题（非阻塞 I/O），又解决运维痛点（零 Hadoop 依赖消除 CVE 负担），还解决合规问题（AWS SDK v1 → v2）。

## 3. ❄️ Snowflake CoCo + Streamlit — 长周期规划的 Agent 化（Jul 8, 2026）

> **来源**: [Snowflake Blog — How We Use CoCo and Streamlit to Make Long-Range Planning Conversational](https://www.snowflake.com/blog/how-we-use-coco-and-streamlit-to-make-long-range-planning-conversational/)（Jul 8, 2026）
> **作者**: Brad Floering
> **状态**: ✅ 实际部署

**核心创新**: Snowflake 自己的规划团队用 CoCo（工程师编码 Agent）+ Streamlit 做了一个「对话式长期规划」工具。

### 架构

```
用户（以中文提问）
  v
Streamlit Chat UI
  v
CoCo（Agent）：读取规划数据 + 执行计算 + 更新路线图
  v
Snowflake Warehouse（源数据）
```

**关键实现细节**:
- **意图理解**: CoCo 将自然语言规划问题转为结构化查询和数据操作
- **多轮规划**: 不是单次 QA，而是迭代式规划修正
- **数据驱动**: 所有规划建议基于 Snowflake 中的实际数据（资源消耗、进度追踪）
- **不可逆操作保护**: CoCo 在执行可能破坏性操作前要求用户确认

**架构意义**: 展示了 **Agent 从「查数据」走向「干预数据」**——CoCo 不只是读仓库，而是写仓库（更新规划路线图）。这是数据 Agent 从 Read-only 到 Read-write 的典型实践。

## 5. 📄 arXiv: DBCC — 数据库上下文压缩，真实大库 T2S 输入缩至 1.3%（Jun 26, 2026）

> **来源**: [arXiv:2606.28601 — Database Context Compression for Text-to-SQL](https://arxiv.org/abs/2606.28601)（Jun 26, 2026）
> **作者**: Liu et al.
> **状态**: ✅ 已开源

**核心洞察**: 当前 Text-to-SQL 的真正瓶颈已不是推理能力，而是**数据库表示**。真实企业库有上千表、重复列、不透明标识符、冗长的数据字典。

### SGCF 原则（Support-Gain Component Factorization）

- **Repeated Column Extraction**: 提取重复审计列（如 `create_time`, `update_time`, `is_deleted`），统一表示
- **Isomorphic Table Templating**: 结构相似的表（如 `order_2024_01`, `order_2024_02`）模板化
- **Semantic Componentization**: 将列名/注释/DDL 描述合并为紧凑语义单元
- **Evidence Purification**: 在线阶段仅保留查询相关的上下文

### 效果数据

| 指标 | 压缩前 | 压缩后 | 提升 |
|:-----|:------:|:------:|:----:|
| **输入 Token（最大子集）** | 2,600,000 | ~34,700 | **缩至 1.3%** |
| **Schema-linking Strict Recall（DeepSeek-V3.2）** | 0% | **56.5%** | 从不可用到可用 |
| **Schema-linking Strict Recall（Claude Opus 4.7）** | — | **63.1%** | — |
| **End-to-End Execution Accuracy** | — | +1.8–1.9% | 模型无关提升 |

### 关键结论

DBCC 是一个 **查询无关的数据库侧中间件**，可插入任意 Text-to-SQL Pipeline。代码已开源：[SchemaCompression](https://github.com/MrBlankness/SchemaCompression)。在 Spider 2.0-Snow 上从 2.6M → 34.7K Token 是**极令人印象深刻的压缩率**。

## 6. 📄 arXiv: Schema-First Retrieval — Catalog 元数据检索层（Jun 22, 2026）

> **来源**: [arXiv:2606.28387 — Schema-First Retrieval: Embedding Catalogs for NL Analytics](https://arxiv.org/abs/2606.28387)（Jun 22, 2026）
> **作者**: Agrawal, Indukuri
> **状态**: ✅ 可复现

**核心创新**: 把 Schema 检索视为**一流的检索问题**，而非提示词格式细节。嵌入 Catalog 元数据（表/列/度量/关系/查询历史）而非 Warehouse 行数据。

### 架构

```
User Query
    v
并行 Vector Search（5 类 Catalog 对象）
    +-- Tables（表名+描述模板化嵌入）
    +-- Columns（列名+类型+注释）
    +-- Metrics（业务度量定义）
    +-- Relationships（外键+Join 约定）
    +-- Query History（已执行查询+用法）
    v
Lineage Expansion（找到关联的表/列）
    v
Cross-encoder Reranking（精排 Top-K）
    v
Workload Memory（记住用户之前的查询偏好）
    v
Access-control Gates（权限过滤）
    v
SQL Generation
```

### 效果数据

| 指标 | 值 | 对比 |
|:-----|:--:|:----:|
| CRUSH4SQL Table Recall@20 | **96.4%** | BM25 基线 +32.8 pp |
| Cross-encoder Column Recall@10 | +11.1 pp | 显著提升 |
| SEDE Table Recall@5（加 Query History） | **92.3%** | 无 Query History: 52.1% |
| BIRD SQL 执行错误减少 | **2.5×**（15.6%→6.2%） | — |

### 关键结论

- **Query History 是 Recall 跃升的核心**: SEDE 上 Recall@5 从 52.1% → 92.3%（+40.2 pp）
- **Catalog Selection 与 Text-to-SQL 解耦**: 应为独立的一流检索问题，不应是提示词细节
- **Schema-First 比 Row-First 更高效**: 索引 Metadata 而非数据本身

## 7. 📄 arXiv: DecoSearch — 复杂度感知路由 + DAG 级计划修复（Jun 16, 2026）

> **来源**: [arXiv:2606.17821 — DecoSearch: Complexity-Aware Routing and Plan-Level Repair for Text-to-SQL](https://arxiv.org/abs/2606.17821)（Jun 16, 2026）
> **作者**: Schafir et al.
> **状态**: ✅ Training-free

**核心创新**: 不靠更大的模型，而靠**复杂度感知路由**——简单 SQL 直接生成，复杂查询走 DAG 分解。

### 架构

```
User Query
    v
Schema Selector（轻量级，裁剪 Schema）
    v
LLM Judger（判断复杂度）
    +-- 简单 -> 直接生成 -> SQL
    +-- 复杂 -> DAG 的原子子问题
                  v
            各子问题分别 SQL 生成
                  v
            Topology Refiner（执行失败时重构 DAG）
                  v
            合并 -> SQL
```

**关键设计**:
- **DAG 分解**: 复杂查询拆成 DAG 的原子子问题，每个子问题独立 SQL 生成
- **Topology Refiner**: 当执行失败信号表明是分解错误（而非 SQL 语法错误）时，重构 DAG
- **RAG 示例**: 用语义相似的训练示例 grounding 分解器

### 效果

| 指标 | DecoSearch | 对比 |
|:-----|:----------:|:----:|
| **BIRD Execution Accuracy** | **70.53%** | 无需训练的基线中最佳 |
| **Spider Execution Accuracy** | **88.31%** | — |
| Token 消耗 | 一个数量级更低 | vs 竞争方法 |
| **模型无关** | ✅ 可作为 Wrapper 提升已微调模型 | — |

**架构意义**: DecoSearch 验证了一个关键假设——复杂 Text-to-SQL 的问题核心在「分解」而非「生成」。DAG 级计划修复比 SQL 级修复更有效。以 DeepSeek 为 backbone 达 70.53% BIRD 是当前 training-free 方法中的 SOTA。

## 8. 📄 arXiv: SQuaD-SQL — SLM 知识蒸馏逼近 LLM T2S 水平（Jul 9, 2026）

> **来源**: [arXiv:2607.08161 — SQuaD-SQL: Efficient Text-to-SQL with Small Language Models via LLM-Guided Knowledge Distillation](https://arxiv.org/abs/2607.08161)（Jul 9, 2026）
> **作者**: Wu et al.
> **状态**: ✅ 已被 IEEE SMC 2026 接收

**核心创新**: 用 LLM 引导的知识蒸馏 + 合成数据生成，让 SLM（Small Language Model）在单消费级 GPU 上接近 LLM 的 Text-to-SQL 性能。

### 技术方案

1. **LLM-based Synthetic Data Generation**: 精心设计的 prompt 策略，从 LLM 提取结构化知识
2. **Parameter-Efficient Fine-Tuning**: LoRA 等 PEFT 方法，单消费级 GPU 可训练
3. **Domain-Adaptive Fine-Tuning**: 领域特定合成数据进一步提升

### 效果

| 指标 | SQuaD-SQL（SLM） | LLM 基线 |
|:-----|:----------------:|:--------:|
| **WikiSQL Execution Accuracy** | **86.9%** | 接近 LLM |
| 推理速度 | ✅ 更快 | ❌ 更慢 |
| 内存占用 | ✅ 更低 | ❌ 更高 |

**架构意义**: 对于无法使用 cloud API（数据隐私/合规要求）或预算受限的团队，SLM 蒸馏是一条可行路径。86.9% 的 WikiSQL 精度在资源受限场景下足够实用。
