## 1️⃣ 🔀 Databricks Lakebase 分支 CI/CD — 数据库像代码一样分支

**来源**: [Databricks Blog — Branching databases like code: a CI/CD pattern for Lakebase](https://www.databricks.com/blog/branching-databases-code-cicd-pattern-lakebase-production-glaspoort) | Jul 20, 2026
**产品**: Databricks Lakebase (serverless Postgres OLTP, 与 Lakehouse 同平面运行)

### 架构设计：Glaspoort 生产案例

荷兰光纤运营商 Glaspoort 将 **Lakebase** 作为应用数据库，与 Lakehouse 分析数据共生：

```
Lakehouse (curated data) --sync---> Lakebase Production Branch
                                          +-- Read-only app schema
                                          +-- App write schema (state)
```

### 核心模式：永远从 Production 分支

| 传统拓扑 (陷阱) | Glaspoort 拓扑 (正确) |
|:--------------|:-------------------|
| Dev ← Production | Dev ← Production |
| Acceptance ← Dev | Acceptance ← Production |
| Feature ← Dev | Feature ← Production (per-PR ephemeral) |
| ❌ 重置 Dev 必须先删所有子分支 | ✅ Dev/Acceptance 互不依赖，重置即刷新 |

**"Reset-from-Parent Trap"**：传统堆叠拓扑中，刷新 Dev 环境需要级联删除→重新创建→重新授权，成本过高导致团队放弃刷新 → 环境漂移。Glaspoort 的解法：所有长期环境直接分支自 Production，重置时无需删除任何子分支。

### 每 PR 的 CI/CD 流程

| 步骤 | 操作 |
|:----|:-----|
| 1 | 开发者开 PR, CI 从 Production 切出临时 `pr-xxxx` 分支 (TTL=1h) |
| 2 | CI 重放 Migration 到新分支 |
| 3 | CI 部署新应用镜像到 staging slot，指向迁移后的分支，运行全套测试 |
| 4 | Merge 后 **再次** 从 Production 切分支+重放+测试（因为世界可能已变化） |
| 5 | Migration 通过 → 应用到 Dev → 手动门禁 → Acceptance → Production |

**核心原则**：分支永不回合并，**Migration 本身是 Schema 的单一事实来源**。

### 架构意义

- **Lakebase 定位**：Serverless Postgres OLTP 与 Lakehouse 同平面运行，不再需要独立 RDS
- **数据架构演进**：Lakehouse + Lakebase → 分析库+事务库统一平台，**OLTP/OLAP 边界模糊化**
- **对 Agent 的启示**：GitLake (arXiv:2607.08319) 的 Iceberg 分支 + Lakebase 的 Postgres 分支 → 数据操作的 Git 化正在成为事实标准

## 3️⃣ 🧪 Spider 2.0-AIFunc — AI-Native SQL 基准测试扩展到 Snowflake AI 函数

**来源**: [arXiv:2607.06229](https://arxiv.org/abs/2607.06229) | Jul 7, 2026
**作者**: Tianyang Liu, Canwen Xu, Fangyu Lei 等

### 核心贡献

Spider 2.0-AIFunc: **465 个验证实例** × **125 个真实数据库** × **6 类 AI 函数**

| AI 函数类型 | 示例 |
|:----------|:-----|
| 分类 (CLASSIFICATION) | `SNOWFLAKE.CORTEX.CLASSIFY(text, categories)` |
| 过滤 (FILTER) | `WHERE SNOWFLAKE.CORTEX.SENTIMENT(text) = 'positive'` |
| 情感分析 | `SNOWFLAKE.CORTEX.SENTIMENT(review)` |
| 提取 (EXTRACTION) | `SNOWFLAKE.CORTEX.EXTRACT(text, 'entities')` |
| 相似度搜索 | `ORDER BY SNOWFLAKE.CORTEX.SIMILARITY(emb, query_emb)` |
| 聚合 (AGGREGATION) | `SNOWFLAKE.CORTEX.SUMMARIZE(text)` |

### 关键发现

| 模型 | Execution Accuracy | 备注 |
|:----|:-----------------:|:-----|
| 最强闭源模型 | 67-70% | 主要在谓词/AI函数参数化出错 |
| 最佳开源模型 | 58.1% | 差距达~10pp |
| Agent 框架 | ❌ 不提升 | 传统 schema retrieval 策略在 AI-Native SQL 中失效 |

**架构信号**：传统 Text-to-SQL Agent 框架（多轮 schema 检索+表格选择）在 AI Native SQL 上**比不上最小 Agent 配置** → 说明当前 Agent 策略是为传统 SQL 优化的，AI 函数引入后 Schema 交互范式需要重设计。

## 4️⃣ 🛡️ GRID — Grammar-Railed Decoding：企业 SQL 的可证明合规生成

**来源**: [arXiv:2607.11951](https://arxiv.org/abs/2607.11951) | Jul 11, 2026
**作者**: Mohsen Arjmandi

### 核心架构

GRID (Grammar-Railed Decoding) 基于 LALR(1) 解析器状态驱动 Token Mask：

```
LLM -> Token Logits
       v
LALR(1) Parser State (lexer scan state × stack)
       v 逐 token mask <- 语法 + 角色权限 + Schema 白名单
       v
仅合法的 token 被允许 -> 确保 4 Guarantees
```

### 四大保证

| Guarantee | 含义 |
|:----------|:-----|
| **Soundness** | 生成的 SQL 100% 语法有效 |
| **Completeness** | 不会漏掉任何合法 SQL |
| **Termination** | 生成的序列一定终止 |
| **Near-Constant Cost** | 每 token 的 mask 开销恒定（~3.6-6.7μs, n=16,000 时仍平坦） |

### Benchmark 结果

| 配置 | 提升 |
|:----|:----:|
| 0.5B 模型 + GRID (Spider) | **+13 执行准确率点** |
| 7B 模型 + GRID + 1次修复 | **94.5% Executable** |
| RBAC 编译入语法 | 禁止的动词/标识符在 mask 层不可达 |

### 与 PCC-SQL (arXiv:2607.12341) 的对比

- PCC-SQL: 列级访问控制，0% Leakage Rate，Coverage ~88.7%
- GRID: 通用语法约束引擎，Token Mask 速度更快（3.6-6.7μs vs LLGuidance at p50/p90）
- 两者可互补：GRID 管语法+表级，PCC-SQL 管列级语义使用

### 架构意义

**"编译期安全"取代"运行时过滤"**：这代表企业级 T2S 的核心范式切换——不再依赖 LLM 生成后再检查，而是让禁用的 SQL 结构在生成阶段就不可达。

## 5️⃣ 🎯 EXPO-SQL — 子句级奖励的 T2S 强化学习

**来源**: [arXiv:2606.23693](https://arxiv.org/abs/2606.23693) | Apr 29 · ACL 2026 Findings
**作者**: Jaehoon Lee, CheolWon Na 等

### 核心创新

现有 RL-based T2S 方法给整条 SQL 分配**查询级统一奖励** → 错误子句得到正奖励、正确子句被负奖励连带。EXPO-SQL 的解法：

```
传统: REWARD(SQL) = 1 或 0 (整个查询)
EXPO: REWARD(SELECT) = 1, REWARD(FROM) = 1, REWARD(WHERE) = -1
      通过错误信息 + 子句增量执行 定位出错子句
```

### 效果

- **显著超越** SFT + Prompting + 传统 RL 方法
- 子句级奖励信号更密集、更准确

## 6️⃣ 📊 LeJOT — Databricks 智能作业成本编排

**来源**: [arXiv:2512.18266](https://arxiv.org/abs/2512.18266) | Dec 2025 · BigDataCom 2025

### 核心架构

| 层 | 机制 | 时间尺度 |
|:--|:-----|:---------|
| 预测层 | ML 模型预测作业执行时间 | 秒级 |
| 优化层 | 求解器实时分配资源 | 分/秒级 |
| 调度层 | 动态调整集群配置 | 分钟级 |

### 效果

- **云计算成本降低 20%**
- 分钟级调度窗口
- 在真实 Databricks 工作负载上验证

### 架构意义

企业 Databricks 成本管理正从静态配置 → ML 驱动的动态优化。与 AutoSLO (arXiv:2607.11770) 形成"成本优化+SLO保障"互补方案。
