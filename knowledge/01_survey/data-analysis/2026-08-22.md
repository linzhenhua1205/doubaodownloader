## 二、查询执行优化：从黑盒代理到可解释执行 + 硬件卸载

### 2.1 Carnot：深度研究查询的可解释交互执行引擎

- **来源/标题**: *Carnot: Interpretable, Interactive, and Optimized Execution of Deep Research Queries*（arXiv 2608.09532，2026-08-10，Matthew Russo / Yash Agarwal / Tianyu Li / Zhuohan Gu / Michael Cafarella / Omar Khattab / Tim Kraska / Samuel Madden —— MIT+Stanford+Google 团队，含 Madden/Kraska 两位数据库泰斗）
- **URL**: https://arxiv.org/abs/2608.09532
- **要点**: 企业日益倾向用自然语言查询数据湖（语义算子或深度研究 agent），但两类工具各有致命缺陷：**深度研究 agent 是黑盒**——隐藏中间推理与数据检索步骤，无法控制 API 成本与执行延迟；**语义算子对企业级数据湖成本过高**。分析人员因此无法拦截幻觉前提、验证中间结果、纠正系统轨迹。
- **要点**: Carnot 把自然语言请求**编译为物理执行图（physical execution graphs）**，通过交互式 notebook 界面呈现。用户可批判执行计划、逐步执行算子、检查中间数据、直接编辑底层代码或语义算子指令；查询优化器按用户给定的成本/延迟约束优化。
- **要点**: 定位是"演示/原型"（demo），工作负载来自真实企业用例——说明该方向仍处早期，但 MIT/Stanford 数据库顶级团队入场标志着"AI 分析可解释性"成为主流数据库研究议程。

**分析段落 A — 为什么"可解释执行图"是 AI 分析从玩具走向企业的必经之路**：Carnot 的洞察在于把"深度研究"从**黑盒 agent 调用**降级为**数据库查询计划**——这正是 70 年关系数据库成功的核心经验：查询优化器把声明式请求编译为可检查、可调优、可复现的执行计划。LLM 时代的问题在于：agent 的"计划"藏在提示词与工具调用轨迹里，既不可检查也不可优化。Carnot 把这一层重新显式化（物理执行图 + notebook 交互 + 成本约束优化），本质是**把数据库的"计划-执行-调优"循环移植到 AI 分析**。对数据平台研发的启示：AI 数据分析工具若想在企业落地，必须提供"人类可干预的中间层"——纯黑盒 agent 再聪明也无法通过数据治理审计（呼应 08-21 收录的 proof-carrying agents 2510.09567：agent 正确性必须可证明）。

### 2.2 Oasis 与 SmartNIC 路线：把 Parquet 解码藏进网络数据通路

- **来源/标题**: *Oasis: Hiding the Cost of Querying Parquet Files in the Datapath*（arXiv 2608.02268，2026-08-03，Jonas Dann / Luca Tagliavini / Gustavo Alonso，ETH Zurich Systems Group）
- **URL**: https://arxiv.org/abs/2608.02268
- **要点**: 云原生数据库系统通过存储计算解耦获得弹性，但生产数据仓库负载实测**扫描（含往返存储）约占查询总运行时的 50%**；数据湖/湖仓因每次查询都要解码存储优化的压缩文件格式（Parquet）而放大此瓶颈。存储与网络带宽增速持续超过 CPU 性价比，**解码耗掉的 CPU 周期正在侵蚀云成本效率承诺**。
- **要点**: Oasis 是**数据处理的 SmartNIC**——把 Parquet 解码卸载到网络数据通路（datapath），作为自定义硬件加速器。包含硬件解码器架构、软件抽象层、与 DuckDB 的端到端集成。评测显示：**Oasis 把 Parquet 解码成本隐藏在网络数据通路之后，扫描与查询执行其余部分重叠，最佳情况 DuckDB 查询吞吐几乎翻倍**。
- **要点**: 与同团队 2602.18775（*Should I Hide My Duck in the Lake?*，2026-02-21，URL: https://arxiv.org/abs/2602.18775）是连续叙事——后者是愿景论文：数据湖查询执行中 **TPC-H 直接查 Parquet 时解码占运行时的 46%**，提出 SmartNIC 卸载解码与下推算子、直接操作预过滤数据；Oasis 是落地实现。

**分析段落 B — 解码瓶颈的因果链：为什么"压缩格式"成为云数据湖的新瓶颈**：Parquet 的列式压缩（字典编码+RLE+位打包）是数据湖存储效率的基石，但其代价是**每次查询都必须完整解码**——存储压缩率越高、解码开销越大，形成"存储省了、计算贵了"的剪刀差。随着 SSD/网络带宽每代翻倍而 CPU 单核性能增速放缓（Amdahl 的另一面），**解码这个固定成本在总成本中的占比持续上升**（46% 解码占比正是这一趋势的量化证据）。Oasis 的解法是**在数据移动路径上就近解码**：数据从存储到 CPU 的路上经过 SmartNIC 时完成解码/过滤，CPU 拿到的是"半成品"。这与 08-21 收录的 Snowpark"next to your data"（2508.05904）哲学一致——**数据搬运途中处理，比搬完再处理省一个数量级**。对智算中心/湖仓平台选型的启示：若云厂商提供 SmartNIC/DPU 卸载能力，Parquet/ORC 解码这类"固定成本型"算子应优先卸载，比加 CPU 核数更经济。

### 2.3 QOaaS：查询优化器即服务——微软的湖仓统一实验

- **来源/标题**: *Towards Query Optimizer as a Service (QOaaS) in a Unified LakeHouse Ecosystem: Can One QO Rule Them All?*（arXiv 2411.13704，2024-11-20，微软数据团队，CIDR 2025 投稿方向）
- **URL**: https://arxiv.org/abs/2411.13704
- **要点**: 客户需求、监管压力与工程效率驱动行业从"孤岛式引擎"转向高度集成方案——开放格式、共享组件库的广泛采用与 Microsoft Fabric 等集成湖仓体验的成功印证此趋势。论文研究该趋势对查询优化器（QO）的影响，汇报**把 Calcite 与 Cascades 扩展为 SQL Server、Fabric DW、SCOPE 的 QO 组件**的实践经验。
- **要点**: 论证激进方向转换的利弊：从定制 QO 或库共享（à la Calcite）**重写 QO 栈、全面拥抱 QOaaS**。收益包括：集中式工作负载级优化、多引擎联邦、加速功能创建；挑战同样严峻（跨引擎语义差异、代价模型不统一）。原型兼容 Fabric DW 与 Spark。
- **要点**: 核心问题"**一个优化器能否统治所有引擎**"开放给社区辩论——反映统一湖仓生态下查询优化层正从"各引擎私有"走向"共享服务"。

**分析段落 C — 优化器统一化的经济逻辑与工程代价**：QOaaS 的动机本质是**消除 N 引擎 × M 优化器的重复投资**：湖仓生态中 Spark/Flink/Trino/DuckDB/Fabric 各自维护优化器，而开放表格式（Iceberg/Delta）已统一存储层，优化器成为最后一个"重复造轮子"的组件。微软的实践（Calcite→Cascades→QOaaS）揭示统一的三重收益：**工作负载级优化**（跨引擎共享统计信息与执行经验）、**多引擎联邦**（一条查询跨引擎执行时统一优化）、**功能加速**（新特性只写一次）。但挑战在于：优化器与执行器深度耦合（代价模型依赖物理算子），强行统一要么牺牲各引擎特长（如 DuckDB 的向量化、Spark 的 shuffle 优化），要么退化为"最小公分母"。**这与开放表格式的演进路径同构**：先统一存储格式（Iceberg/Delta 已成），再统一目录/事务（LakeVilla 类方案），最后才轮到优化层——QOaaS 是湖仓统一进程的"最后一公里"。

## 三、表发现与检索：2026 年数据湖研究的主战场

> 本节收录 9 篇表发现/检索论文——占本次新增的 38%。这是数据湖规模爆炸（企业湖仓表数以万计）与 LLM 数据代理需求（自动找表→分析）交汇的必然结果。按技术路线分三组：**图/结构匹配**（GRAFT、HyperJoin）、**值级语义**（MosaicJoin）、**生成式/端到端**（GenTUS、UniDisc、Octopus）+ 专门任务（Table-Centric TUS、NTS、LakeHopper）。

### 3.1 GRAFT：把表检索变成图匹配问题

- **来源/标题**: *GRAFT: Graph-Matched Retrieval and Fusion of Tables in Data Lakes*（arXiv 2607.12717，2026-07-14，Daomin Ji / Hui Luo / Zhifeng Bao / Shane Culpepper / Shazia Sadiq，RMIT+墨尔本大学）
- **URL**: https://arxiv.org/abs/2607.12717
- **要点**: 自主数据代理（autonomous data agents）通过检索表数据湖中的证据来解答分析查询，但现有方法**独立对每个表打分，忽略表间的可连接性（joinability）与可联合性（unionability）**，返回碎片化证据，下游 agent 无法集成。
- **要点**: 两个核心贡献：① 把表检索建模为**查询意图图与异构数据湖图之间的图匹配**，提出 IGMS（log-determinant 奖励）耦合语义相关、结构兼容、证据多样性三目标；② 把子图生成重构为 **MDP + 隐式 Q-learning**，用压缩算子反转同态生成自训练轨迹；三阶段在线管线（锚点可达性/谓词可纳性/奖励单调性剪枝）大幅缩减候选空间。
- **要点**: 在改编为表数据湖设定的 Spider 与 BIRD 上，GRAFT 在 Recall/Precision/F1/Sufficiency 全面最优，**F1 相对最强基线 +7.8%、Sufficiency +10.6%**，同时保持高搜索效率。

### 3.2 MosaicJoin：零训练的值级语义 Join 发现

- **来源/标题**: *MosaicJoin: Compact Semantic Sketches for Value-Level Join Discovery*（arXiv 2607.21781，2026-07-23，Grace Fan / Eden Wu / Majid Daliri / Juliana Freire，NYU）
- **URL**: https://arxiv.org/abs/2607.21781
- **要点**: Join 发现是数据集搜索的核心任务。数据湖/开放数据仓库中，两列常指向同一实体但语法表示不同（如 "NYC" vs "New York"），早期等值 join 方法失效；近期语义 join 方法面临根本权衡：**值级比较准确但高基数下不可扩展，列级单嵌入高效但丢失细粒度值对齐**。
- **要点**: MosaicJoin 用**新颖 sketching 策略**在无需比较全部值的情况下逼近列对的可连接性：查询时以 sketch 大小为界的代价给每个候选打分；查询子采样算子带**可证明的准确率保证**。**无需训练/微调**，可扩展到 57K 值的查询列与 1M 值的数据湖列。
- **要点**: 实验全面超越已有方法，**比其它值级方法快最多 66 倍**——把值级语义 join 从"不可扩展"拉到"生产可用"。

### 3.3 GenTUS：生成式检索重构 Table Union Search

- **来源/标题**: *Generative Retrieval for Table Union Search*（arXiv 2607.00833，2026-07-01，Shulun Zhang / Linting Wang / Yuwei Xu / Yingli Zhou / Chenhao Ma，香港城市大学）
- **URL**: https://arxiv.org/abs/2607.00833
- **要点**: 表 union 搜索（TUS）检索可与查询表可靠合并的表，支持数据发现/丰富/下游分析。学习式方法仍走"编码-搜索-精排"流水线（候选池检索→匹配/重排），质量依赖候选池召回率，且随湖规模增长延迟与存储成本上升。
- **要点**: GenTUS 把 TUS **重构为离散语义表标识符上的约束生成问题**：为候选表分配紧凑的 unionability-aware 标识符，训练生成器直接从查询产生可 union 表的标识符；查询时约束解码保证生成的标识符对应湖中真实表。
- **要点**: 7 个公开 TUS 基准上整体检索质量最优：**平均排名 1.05 vs 最强基线 2.57**，同时大幅降低在线延迟、检索产物存储与增量更新成本。

**分析段落 D — 三路线竞争的本质：表发现是"检索"还是"推理"**：GRAFT（图匹配）、MosaicJoin（值语义）、GenTUS（生成式）分别对应信息检索三大范式：**结构化匹配**（图同态=显式建模表间关系）、**语义近邻**（值级嵌入=局部语义对齐）、**生成式检索**（标识符生成=端到端记忆）。各自的代价-收益结构不同：GRAFT 强在"证据完整性"（sufficiency 维度领先），适合下游要集成多表的 agent 场景，但依赖图构建的离线成本；MosaicJoin 强在"零训练+可证明保证"，适合无标注冷启动，但语义理解深度受 sketch 容量限制；GenTUS 强在"延迟与增量成本"，适合表量巨大的生产湖，但标识符分配依赖离线聚类质量。**三条路线尚未收敛，说明表发现的"正确表示"仍是开放问题**——这与中国数据要素市场（政务/金融数据目录检索）的需求高度吻合，是国产湖仓产品可差异化发力的点。

### 3.4 表发现全景：其余六篇的定位与增量

- **来源/标题**: *Octopus: A Lightweight Entity-Aware System for Multi-Table Data Discovery and Cell-Level Retrieval*（arXiv 2601.02304，2026-01-05，Wen-Zhi Li / Sainyam Galhotra，Cornell）
- **URL**: https://arxiv.org/abs/2601.02304
- **要点**: 现有数据发现系统假设"一个问题可由单表回答"，且依赖昂贵的离线预处理（模型训练/大规模内容索引）。Octopus 面向**需要跨多表（独立或 join）回答的问题**与**cell 级取值检索**，主打轻量（无重型离线索引）——反映真实分析需求从"给表"到"给答案"的迁移。
- **来源/标题**: *HyperJoin: LLM-augmented Hypergraph Link Prediction for Joinable Table Discovery*（arXiv 2601.01015，2026-01-03，Shiyuan Liu / Jianwei Wang / Xuemin Lin / Lu Qin / Wenjie Zhang / Ying Zhang，悉尼科技大学+阿德莱德大学）
- **URL**: https://arxiv.org/abs/2601.01015
- **要点**: 现有 LM 方法把表建模为孤立/成对列，忽略**表间与表内结构交互**；在线仅按查询-候选相似度排序，忽略候选间结构。HyperJoin 用**超图链接预测**显式建模多表结构，LLM 增强特征——与 GRAFT 同属"结构感知"阵营，但用链接预测替代图匹配。
- **来源/标题**: *UniDisc: Unified Data Discovery across Query Modalities and User Intents*（arXiv 2604.27252，2026-04-29，Tingting Wang / Shixun Huang / Zhifeng Bao / J. Shane Culpepper / Shazia Sadiq / Volkan Dedeoglu）
- **URL**: https://arxiv.org/abs/2604.27252
- **要点**: 数据发现须同时支持**多种查询模态**（自然语言语句/表）与**多种用户意图**（开放式丰富/任务驱动推理如 table QA、事实核验）。现有方法多为单一模态+单一意图设计，泛化受限。UniDisc 提出统一框架——反映企业数据目录"一套入口、多种用法"的现实需求。
- **来源/标题**: *Efficient and Effective Table-Centric Table Union Search in Data Lakes*（arXiv 2603.17298，2026-03-18，Yongkang Sun / Zhihao Ding / Huiqiang Wang / Reynold Cheng / Jieming Shi，香港大学）
- **URL**: https://arxiv.org/abs/2603.17298
- **要点**: 现有 union 搜索以**列为中心**（列嵌入建模列 unionability），忽略**表级整体语义**导致次优排序与低效。提出表中心（table-centric）方法——与 GenTUS 的"标识符级"、GRAFT 的"图级"共同构成对"列中心"范式的集体修正。
- **来源/标题**: *Novel Table Search*（arXiv 2603.07235，2026-03-07，Besat Kassaie / Renée J. Miller，Northeastern University）
- **URL**: https://arxiv.org/abs/2603.07235
- **要点**: 查询结果去冗余在关系数据库/IR 中研究充分，但对数据湖几乎空白。NTS 形式化定义"**相对查询表贡献新信息的可 union 表**"问题，给出评分函数应满足的两个性质——**这是"信息增量"视角首次进入表搜索**，直接服务"别给我重复的表"的真实需求。
- **来源/标题**: *LakeHopper: Cross Data Lakes Column Type Annotation through Model Adaptation*（arXiv 2602.08793，2026-02-09，Yushi Sun / Xujia Li / Nan Tang / Quanqing Xu / Chuanhui Yang / Lei Chen，HKUST+华为）
- **URL**: https://arxiv.org/abs/2602.08793
- **要点**: 列类型标注（column type annotation）是数据清洗/集成/可视化的基础。已有方案依赖在"源数据湖"标注列上微调的资源密集型 LM。LakeHopper 研究**如何把预训练模型适配到新数据湖**以最小化新湖标注需求——解决"每个湖都要重新标"的成本问题，涉及源-目标知识鸿沟、信息性目标数据选择、微调不失共享知识三大挑战。

**分析段落 E — 表发现的五大维度全景：从"找到表"到"用好表"**：汇总 9 篇论文可提炼表发现任务的完整维度空间：① **检索对象**（整表→列→cell 值，Octopus 推至 cell 级）；② **关系类型**（union→join→schema 匹配，MosaicJoin/GenTUS 覆盖 join/union，PiLLar 覆盖 pivot schema）；③ **查询形式**（表→NL→多模态，UniDisc 统一）；④ **目标函数**（相似度→信息增量，NTS 引入 novelty）；⑤ **部署约束**（离线成本/跨湖迁移，Octopus 轻量、LakeHopper 适配）。**行业含义**：企业数据目录产品（如阿里 DataWorks、华为 DAYU、Snowflake Marketplace）当前多为"关键词搜索+血缘"，而学术前沿已把"语义 join 发现/信息增量排序/多模态查询"全部问题化——**未来 2-3 年数据目录将从"导航器"升级为"数据代理"，这是国产数据治理产品的确定性升级窗口**。

## 四、LLM×Agentic 数据治理与集成

### 4.1 AgenticER：实体解析的范式革命

- **来源/标题**: *AgenticER: the next frontier in Entity Resolution*（arXiv 2607.27435，2026-07-29，George Papadakis / Panos Korovesis / Manolis Koubarakis / Themis Palpanas，雅典大学+巴黎城市大学）
- **URL**: https://arxiv.org/abs/2607.27435
- **要点**: 实体解析（ER）是数据管理的基础问题（数据清洗/知识图谱构建）。现有方法从规则到深度学习到 LLM，但都属"**被动范式**"——通过静态一次性相似度计算检测重复。这在数据湖场景（流式内容、CSV/JSON/RDF/自由文本异构格式）下失效：消解歧义需要**迭代取证、跨源推理、选择性人工介入**。
- **要点**: 主张从被动到 **Agentic ER 的范式转移**：把 ER 框架化为**自主代理执行的顺序决策过程**——主动规划 ER 策略、获取外部证据、决定何时查询额外源或人类、在**准确率/成本/延迟间优化权衡**。
- **要点**: 形式化为决策论问题，给出参考架构、核心研究挑战与面向 agent 行为的新评测维度——旨在建立数据管理与智能代理交叉的新研究方向。

**分析段落 F — 为什么实体解析是 Agentic 数据管理的最佳试验场**：实体解析具有 agent 化的天然结构：**不确定性**（同一实体多种表示）、**迭代性**（一个证据不足需更多证据）、**成本权衡**（问人最准但贵，查库便宜但可能不准）、**多源性**（需要跨 CSV/JSON/知识图谱取证）。这与对话式 QA 的"思考-行动-观察"循环高度同构，但比通用 agent 更可控、更可评测——**ER 有明确的 ground truth（重复对标签）**。AgenticER 的"决策论框架"（准确率/成本/延迟三维权衡）也直接呼应 08-21 收录的 proof-carrying agents（2510.09567）"可验证性优先"哲学：**在可评测任务上先验证 agent 范式，再向更开放任务扩散**，是 Agentic 数据管理最务实的路径。

### 4.2 Metadata Reasoner：Google 的 Agentic 元数据推理

- **来源/标题**: *An Agentic Approach to Metadata Reasoning*（arXiv 2604.20144，2026-04-22，Jiani Zhang / Sercan O. Arik / Cosmin Arad / Fatma Ozcan / Alon Halevy，Google Cloud AI + Google Research）
- **URL**: https://arxiv.org/abs/2604.20144
- **要点**: LLM 驱动的自主代理执行复杂多步任务需集成多数据集，**发现相关数据源成为关键瓶颈**——不仅因数据源数量庞大，更因数据语义极其微妙，需考虑数据多方面特性。
- **要点**: 提出 **Metadata Reasoner**：agentic 元数据推理方法，为给定分析任务识别**既充分又最小**的数据源集。利用表搜索引擎检索候选表，然后**自主查阅各种元数据方面**判断候选是否匹配任务需求。
- **要点**: 真实 KramaBench 数据集选择评测：**平均 F1 83.16%**，超最强基线 3.3 个百分点、弱基线 38 个百分点；基于 BIRD 数据源的新合成基准上，**对冗余/低质量表高度鲁棒：平均 F1 85.5%，99% 成功率避开低质量数据**。

### 4.3 SANA：数据湖 QA Agent 的失败诊断框架

- **来源/标题**: *SANA: What Matters for QA Agents over Massive Data Lakes?*（arXiv 2606.13904，2026-06-11，Austin Senna Wijaya / Jiaxiang Liu / Haonan Wang / Eugene Wu，Columbia University）
- **URL**: https://arxiv.org/abs/2606.13904
- **要点**: 数据湖探索式问答（EQA）需要 LLM agent **发现相关源、分析检索数据、基于中间结果调整行动**。端到端准确率无法区分失败发生在**搜索/规划/数据分析/行动策略**哪个环节。
- **要点**: SANA 是**诊断性消融框架**：把 EQA 任务转化为含"黄金源序列、清洗后子问题、执行记录"的运行时画像，据此构造理想化搜索/规划/数据分析工具逐一消融；残余差距即策略失败的诊断证据。
- **要点**: 适配 LakeQA 与 KramaBench 两基准评测轻/中型 agent：**数据分析是普遍瓶颈、规划问题较小；搜索在 LakeQA 大湖场景是主要限制，在较小规模 KramaBench 则否**——首次把端到端准确率解构为可定位的环节诊断。

**分析段落 G — SANA 的诊断结论与"湖越大搜索越难"的规模效应**：SANA 最有价值的产出是"**搜索瓶颈随数据湖规模非线性恶化**"的实证：LakeQA 的大湖场景（大量表）中搜索成为主要失败点，而小湖 KramaBench 中数据分析才是瓶颈。其因果机制可解释：**候选表数量增长 → 检索召回率下降 → agent 拿到的证据集不完整 → 后续分析再强也基于错误前提**——这形成"规模诅咒"：数据湖越大，LLM 代理的端到端质量越受制于检索而非推理。对工程的含义非常直接：**给 LLM 代理配数据湖时，检索层（第 3 节表发现技术）的投资回报高于换更大模型**。这也解释了为什么 2026 年表发现研究爆发（第三节 9 篇）——它们是 agent 时代数据湖的"基础设施"。

### 4.4 EcoTable：自然语言查询驱动的表集成

- **来源/标题**: *EcoTable: Cost-effective Table Integration in Data Lakes for Natural Language Queries*（arXiv 2606.26613，2026-06-25，Yuhui Wang / Jinqi Liu / Chengliang Chai / Hangyu Zhao / Yuhao Deng / Yuyu Luo / Xin Tang / Ye Yuan，北航）
- **URL**: https://arxiv.org/abs/2606.26613
- **要点**: 数据湖中 CSV/Parquet 格式多样，传统 ETL 依赖数据工程师预定义目标 schema 并构建复杂集成管道；且**预定义 schema 往往无法支撑未预见的分析需求**（表格式或 join 关系不匹配）。
- **要点**: EcoTable 是**首个基于自然语言的表集成框架**：给定用户 NL 查询集合，自动把表集成为可支撑对应 SQL 查询的形态。用图表示搜索空间（节点=表，边权重=轻量深度学习模型给出的 join 可能性），三组件：① 基于用户查询的两阶段 schema linking 表识别；② 把 join 路径发现建模为 **Steiner tree 搜索**的图验证层；③ LLM 生成变换代码实现 join 的表变换层。
- **要点**: 4 个真实世界基准数据集、200+ 查询：**准确率超 SOTA 基线 30%+，LLM 调用成本降低 5 倍**——"图剪枝+LLM 生成"组合有效遏制了 LLM 昂贵推理的规模/成本问题。

### 4.5 其余两篇：PiLLar 与概念 Schema 推断

- **来源/标题**: *PiLLar: Matching for Pivot Table Schema via LLM-guided Monte-Carlo Tree Search*（arXiv 2604.26356，2026-04-29，Yunjun Gao / Chuangyu Ouyang / Congcong Ge / Yifan Zhu，浙江大学）
- **URL**: https://arxiv.org/abs/2604.26356
- **要点**: Pivot 表在现代数据湖生态中普遍存在，其 schema 匹配（联合 schema-值匹配任务）是数据集成关键前提：正确匹配须 schema 层语义一致 + 值层兼容。实际中**匿名化数据盛行**（数据敏感性）带来显著挑战——LLM 引导的蒙特卡洛树搜索（MCTS）用于探索匹配空间。
- **来源/标题**: *Conceptual Schema Inference for Tabular Datasets using Large Language Models*（arXiv 2605.23105，2026-05-21，Zhenyu Wu / Jiaoyan Chen / Norman W. Paton，曼彻斯特大学）
- **URL**: https://arxiv.org/abs/2605.23105
- **要点**: 数据湖/Web 表/开放数据门户的大规模表格数据来源异构、表示不一致，理解与组织仓库是重大挑战。已有工作聚焦数据集发现与探索，本文处理互补问题：**概念 schema 推断**——直接从原始表自动推导捕获实体类型、属性、类型间关系的概念 schema，基于 LLM 的两种方法。

## 五、评测体系与嵌入基准：表学习进入"度量衡"时代

- **来源/标题**: *TEmBed-T: A Multi-Dimensional Benchmark for Table-Level Embeddings*（arXiv 2607.24130，2026-07-27，Ayeen Poostforoushan / Liane Vogel / Carsten Binnig，TU Darmstadt）
- **URL**: https://arxiv.org/abs/2607.24130
- **要点**: 表格数据是主导的结构化数据模态，表级嵌入支撑表检索/数据湖发现/表分类等应用。但**不同嵌入方法跨任务的行为缺乏系统理解**。TEmBed-T 提供系统评测，捕获下游任务所需的多个互补属性（多维度）——为表嵌入选型提供度量衡。
- **来源/标题**: *TRL-Bench: Standardizing Cross-Paradigm Representation-Level Evaluation of Tabular Encoders*（arXiv 2606.09323，2026-06-08，Wei Pang / Xiangru Jian / Hehan Li / Zhixuan Yu / Alex Xue / Jinyang Li，UC Berkeley）
- **URL**: https://arxiv.org/abs/2606.09323
- **要点**: 表格编码器通常在任务特定端到端管道内评测，**不同训练范式的模型难以直接比较**。TRL-Bench 标准化跨范式的表示级评测：各编码器经 wrapper 导出行/列/表嵌入，共享轻量 probe 头跨三个套件评测——TRL-CTbench（列/表）、TRL-Rbench（行）、TRL-DLTE（组合式 Data-Lake 表嵌入任务）。
- **来源/标题**: *Create Benchmarks for Data Lakes*（arXiv 2601.19176，2026-01-27，Yi Lyu / Pei-Chieh Lo / Natan Lidukhover）
- **URL**: https://arxiv.org/abs/2601.19176
- **要点**: 数据湖已广泛采用，但**缺乏标准化、全面的性能基准**：现有基准主要面向传统数仓与结构化 SQL 工作负载，无法覆盖数据湖的多样化工作负载与访问模式（结构化/半结构化/非结构化）。提出新型基准框架——呼应 2026 年湖仓评估从"TPC-DS 式"走向"湖原生"的缺口。

**分析段落 H — 评测基准扎堆出现说明表学习进入"工程成熟期"**：三篇基准论文（TEmBed-T/TRL-Bench/Data Lake Benchmarks）的密集出现，是领域成熟度的典型信号：**方法数量爆发后，社区开始需要统一度量衡来对比与选型**。这与 CV 领域 ImageNet、NLP 领域 GLUE 出现的时间点逻辑一致——基准不是研究终点，而是下一轮竞争的起跑线。TRL-Bench 的"跨范式表示级评测"（剥离任务管道、只评嵌入质量）尤为关键：它把"表嵌入好不好"从下游任务性能中解耦，让表发现/检索研究（第三节）可以独立优化表示层。**对国产数据平台的含义**：表嵌入/表检索是数据目录智能化的核心技术，中国团队（北航 EcoTable、浙大 PiLLar、HKUST LakeHopper、港大 TUS）已密集入场，但统一评测体系（对标 TRL-Bench）仍是空白——先立标准者有定义权。

## 六、数据湖基础设施新形态：科学化、向量化、模型化

### 6.1 Science Data Lake：2.93 亿论文的统一开放基础设施

- **来源/标题**: *The Science Data Lake: A Unified Open Infrastructure Integrating 293 Million Papers Across Eight Scholarly Sources with Embedding-Based Ontology Alignment*（arXiv 2603.03126，2026-03-03，Jonas Wilinski，单作者）
- **URL**: https://arxiv.org/abs/2603.03126
- **要点**: 学术数据碎片化于孤岛数据库，元数据分歧且缺乏关联。Science Data Lake 基于 **DuckDB + 简单 Parquet 文件**的可本地部署基础设施，通过 DOI 归一化统一 8 个开放源（Semantic Scholar、OpenAlex、SciSciNet、Papers with Code、Retraction Watch、Reliance on Science、预印本-正式发表映射、Crossref），同时保留源级 schema。
- **要点**: 约 **960GB Parquet、~2.93 亿篇唯一可识别论文、~22 个 schema、~153 个 SQL 视图**。基于 BGE-large 句嵌入的本体对齐把 4516 个 OpenAlex 主题映射到 13 个科学本体（~130 万术语），产出 16,150 个映射覆盖 99.8% 主题（≥0.65 阈值），**F1=0.77**（推荐 ≥0.85 操作点），优于 TF-IDF/BM25/Jaro-Winkler 基线（300 对金标准评测）。
- **要点**: 10 项自动检查、跨源引用一致性分析（成对 Pearson r=0.76-0.87）、分层人工标注验证；四个 vignette 展示单库无法实现的跨源分析。开源、单盘可部署或 HuggingFace 远程查询，含适合 LLM 研究代理的结构化文档。

**分析段落 I — "DuckDB 湖"的启示：轻量湖仓基础设施正在挑战重型平台**：Science Data Lake 用 DuckDB+Parquet 实现 2.93 亿篇论文的统一查询，验证了一条被低估的路径：**单机嵌入式数据库 + 开放列式格式 = 可查询的 PB 级数据湖**（在合理压缩下）。其方法论增量是"**保留源级 schema 的 DOI 归一化**"——不做大一统 schema，而是靠主键映射+视图层统一，与 08-21 收录的 EDSP"Write-Once Read-Anywhere"（2512.03401）异曲同工：**先统一访问语义，再谈数据迁移**。对数据中心/AI 基础设施的含义：科研/治理类数据资产的"轻量湖仓"路线（DuckDB/Parquet，无需 Hadoop 集群）在 2026 年已完全可行，重平台仅在有并发多写/复杂治理需求时才必要。

### 6.2 LiveVectorLake：实时版本化向量知识库

- **来源/标题**: *LiveVectorLake: A Real-Time Versioned Knowledge Base Architecture for Streaming Vector Updates and Temporal Retrieval*（arXiv 2601.05270，2025-11-24，Tarun Prajapati，单作者）
- **URL**: https://arxiv.org/abs/2601.05270
- **要点**: RAG 系统面临根本架构张力：**向量索引优化查询延迟但难以持续更新，数据湖擅长版本化但查询延迟惩罚明显**。LiveVectorLake 提出双层级时态知识库架构：当前知识上实时语义搜索 + 完整版本历史（合规/审计/时点检索）。
- **要点**: 三大架构贡献：① **内容寻址的 chunk 级同步**（SHA-256 哈希确定性变更检测，无需外部状态跟踪）；② **双层级存储**（热层向量索引 Milvus+HNSW，冷层列式版本化 Delta Lake+Parquet），查询延迟与存储成本独立优化；③ **时态查询路由**（delta 版本化 + 跨层 ACID 一致性）。
- **要点**: 100 文档语料 5 个时点版本实测：**增量更新仅重处理 10-15% 内容**（对比全量重索引 100%）；当前知识检索 <100ms；时态查询 <2s；热/冷分层存储成本优化（仅当前 chunk 在昂贵向量索引中）。开源：https://github.com/praj-tarun/LiveVectorLake

**分析段落 J — 向量库与湖仓的"婚姻"：LiveVectorLake 回答 RAG 的版本化难题**：LiveVectorLake 的价值在于直面 RAG 生产化的隐藏痛点：**知识更新时向量索引怎么办**。全量重索引的 100% 成本在百万级文档下不可接受；增量更新又面临"如何知道哪些 chunk 变了"的难题。其解法（SHA-256 内容寻址 + 双层存储）本质是把 Git 的"内容寻址+增量"思想搬到向量领域：**只重索引内容变化的 chunk（10-15%），版本历史存冷层**。这与 08-21 收录的 2503.04847（数据库在 GenAI 中的角色：湖仓=情境上下文供给层）形成互补：**湖仓是 RAG 的"源系统"，向量库是"派生层"——LiveVectorLake 证明两者可以共享同一份版本化数据，而非各自维护副本**。对国产 RAG 平台架构选型：热冷分层+内容寻址应成为标配，避免"为了向量化牺牲版本化"或反之。
