## 一、湖仓正确性与数据治理（8 月主线）

- **Proof-Gated Publication: Verify-Before-Commit（PVDM）**（07-29 提交，cs.DB）: 针对 serverless data-mesh 场景，Open Table Format（Iceberg/Delta）只保证提交原子与快照隔离，**不保证落盘行=作业意图写出的行**——serverless 作业静默丢分区、重试截断文件、重复 chunk 仍会产生「合法且错误」的快照。PVDM 提出四阶段协议（Physical→Verify→Durable→Metadata），用 keyed incremental multiset hash 做内容校验，元数据最后提交、证明不过则消费者不可见。端到端在 Apache Spark 4.0 + Apache Iceberg 1.11 上跑至 1 亿行，8000/8000 注入故障全拦截、零误拦，门控发布成本 ~17ms 且与表大小无关，验证开销约为写入的 1/5。参考实现 Apache-2.0 开源（github.com/vaquarkhan/Proof-gated-publication-PVDM）。https://arxiv.org/abs/2608.14643

- **Specification-delta-driven data governance**（08-20 提交，cs.AI/cs.PL）: 把 OpenSpec 的「spec-delta」思想从软件工程搬到湖仓数据平台——主张湖仓中大量变更本质是契约性的（新数据集、SLA、指标语义、访问策略）而非纯代码变更。论文给出数据平台变更的分类法（按「是否适合增量规格化」排序），并设计受控实验对比 spec-delta 工作流 vs 传统 PR 工作流，响应变量为发现到部署时间、到达 Silver/Gold 层的缺陷密度、跨工具指标发散、审阅者认知负荷（NASA TLX）。明确把「实例化到真实湖仓」留给演示/实验章节，宣称贡献是可复现证据 + 规避 upfront over-specification 反模式的应用指南。https://arxiv.org/abs/2608.19838

- **Not Your Usual Type(s): Data contracts as types**（07-14 提交，CDMS @ VLDB 2026，Bauplan）: 基于 Bauplan 生产环境年运行数百万作业的经验，把数据契约建模为跨语言/跨引擎的「类型」：用户在输入输出表上标注 schema 对象（列类型、约束、文档、血缘），Bauplan 在执行生命周期不同节点解释这些注解。目标是把「弱规格的管线节点边界」（schema 检查晚、跨语言执行不一致、与业务语义脱节）变为编译期可检查的强类型边界。https://arxiv.org/abs/2607.13339

- **AuditWeave: Tamper-Evident Evidence Layer**（06-14 提交，cs.LG/cs.SE）: 面向受监管领域（审计/金融/医疗）的「AI 辅助 + 数据转换」工作流审计层。轻量 Python 库（零运行时依赖），把 RAG 管线与表格/湖仓转换事件写入 append-only、hash-chained 账本；事件词汇表同时覆盖 RAG 与湖仓转换，可端到端追溯一条结论的证据链。链上任何修改/重排/插入/删除均可通过链验证检出；开销为每事件数十微秒，2000 次随机试验中 4 类变异全部检出。https://arxiv.org/abs/2607.09682

- **GitLake: Git-for-data for the agentic lakehouse**（07-09 提交，DASHSys @ VLDB 2026）: 把单表 Iceberg snapshot 提升为湖仓级 commit/branch/merge，让 agent 在隔离分支上工作、人类 review 后发布；管线在临时分支运行、最终 merge 发布，全部输出原子可见或全不可见。附带生产经验教训 + Alloy 模型对核心抽象的正确性初步验证。https://arxiv.org/abs/2607.08319

- **Beyond the Data Mesh Illusion: AI-augmented lakehouses**（05-26 提交）: 论证纯 data mesh 经常「欠交付」——团队继承了责任却没有平台成熟度/工具/协调机制。提出 hub-and-spoke 模型：中心 hub（Center of Excellence）提供共享平台服务、策略自动化、AI 治理（自动标准化数据产品、生成质量规则、草拟数据契约、审查变更回归），域 spoke 拥有业务语义与迭代节奏并随成熟度渐进接管。用数据产品采用率、time-to-find、time-to-insight 三个业务结果指标评估，而非内部活动指标。https://arxiv.org/abs/2605.27131

> **分析①：为什么「提交即正确」成为湖仓新战场——正确性问题的因果链**
>
> 湖仓的原子性承诺（Iceberg/Delta 的 commit 语义）解决的是「读侧隔离」，而 PVDM 指出的缺口是「写侧意图」：分布式作业的 exit status 不等于数据正确性。这条因果链在传统 warehouse 时代被 ETL 工具的强同步校验掩盖；而 serverless 数据网格把「谁写的、怎么写、写错了谁知道」三个问题同时放大——domain 团队拥有写权限、无服务器环境重试语义不可控、数据产品消费者默认信任快照。叠加 GitLake 与 Bauplan 的「分支 + 契约」路线，可以看到行业对正确性的解决策略从「事后补丁」（数据质量监控、SLA 报警）转向「构造性约束」（不合法状态不可表示）。这与软件开发从「测试驱动」到「类型驱动」的演进同构，是 lakehouse 成熟度第二阶段（多写者、agent 参与写入）的必然产物。

> **分析②：治理层的「规格化」竞赛——spec-delta vs data contracts vs 审计链**
>
> 三条技术路线并行：spec-delta（把变更本身规格化为可 review 的增量单元）、data contracts as types（把契约变成编译期类型，Bauplan）、AuditWeave（事后可证明的审计账本）。三者差异在「约束施加点」：spec-delta 约束在流程（变更必须先规格化再实施），contracts 约束在边界（表之间交换必须类型安全），AuditWeave 约束在证据（事后可重建且不可篡改）。对基础设施的启示是：**它们都假设「湖仓变更越来越像软件变更」**——这直接推高了对版本控制原语（branch/merge/diff）、schema 演化和变更审计日志的工程要求，而这些能力最终要落到 catalog 层（如 Iceberg REST Catalog 的扩展）与存储层（对象版本化）的硬件/系统配合上。

## 二、湖仓性能优化：决策外溢与硬件卸载

- **Smart Compaction: 从元数据预测压缩效用**（08-09 提交，cs.AI）: 开放湖仓表格式随时间积累小文件、损害查询性能，但「何时值得压缩」长期依赖阈值启发式。论文构建开放仿真框架生成 2,376 张 Apache Iceberg 表（文件大小跨越 3 个数量级），**不读数据**仅从 manifest 提取 17 个元数据特征训练 XGBoost 预测连续文件缩减比（R²=0.998，RMSE=0.013）；但二分压缩决策竟可被单一分区级阈值 max_files_per_partition>4 平凡可分，无需学习模型。96 张 TPC-H 表跨 schema 验证泛化（R²=0.976）。查询基准揭示：压缩有利于 metadata-heavy 查询，但可能因降低任务并行度拖慢全扫描聚合。https://arxiv.org/abs/2608.08639

- **Oasis: SmartNIC 在数据通路隐藏 Parquet 解码成本**（08-03 提交，cs.DB/cs.AR, ETH）: 生产数仓负载研究中扫描（含存储往返）约占查询运行时一半，湖仓因每次查询重新解码压缩列存格式（Parquet）放大该瓶颈；存储/网络带宽增长快于 CPU 性价比，解码 CPU 周期侵蚀云成本效率。Oasis 是数据通路上的 SmartNIC 硬件加速器：硬件解码器 + 软件抽象层 + DuckDB 端到端集成，把 Parquet 解码重叠在查询执行剩余部分之后，最佳情况 DuckDB 查询吞吐几乎翻倍。https://arxiv.org/abs/2608.02268

- **Filtered Vector Search in a Disaggregated Lakehouse**（08-05 提交，cs.DB）: 提出「过滤 + 向量检索」不必新建专用索引——把 IVF 索引就地嵌入每个 Parquet 文件 footer，复用表既有的文件剪枝栈（分区剪枝、zone-maps、位图索引）：规划器先用谓词剪枝数据文件，再只对幸存文件跑 IVF。索引分布式构建且非破坏性（metadata-only Iceberg replace，其他引擎仍可读）。11.5M×768 表 warm IVF 比暴力 ~32x（recall@10≥0.90，选择性谓词先剪掉 444 个文件中的 355 个）；5M 真实 IBM Granite embeddings 上，跨 join 到达的过滤谓词剪掉 5 个区域分区中的 4 个，物化到分区布局后比查询时 join 快约 94x（14.7s→157ms）。适用条件：过滤列需具备文件级局部性，且残差谓词只能安全下推进纯（分区）列而非仅排序列——并报告了把 ANN 硬接湖仓引擎的失败模式。https://arxiv.org/abs/2608.05441

- **Predicting Lakehouse Performance in Clouds: 查询运行时方差**（06-02 提交，IEEE CLOUD 2026）: 首次系统量化分布式湖仓查询的 run-to-run 运行时方差：K8s 部署跨 3 个公有云 + 1 个私有云、多数据库规模、3 个分析基准，**同一查询重复执行运行时差异接近 2 倍**。因子分析定位方差来源（数据局部性、租户负载、缓存效应）；对 SOTA 查询性能预测（QPP）模型，处理关键方差源可把预测误差降低最多 80%；下游低碳调度（依赖性能预测的工作负载管理）也因此显著降低碳成本。https://arxiv.org/abs/2606.03464

- **Data Lakehouse 加载/存储效率实测：Hudi vs Iceberg vs Delta**（04-23 提交，cs.DC/cs.DB）: 以 Apache Spark 为分布式处理平台，对三种主流湖仓格式跑 4 个顺序 ETL 流程（读→转换→写），处理结构化 CSV 与半结构化 JSON、最大 7GB 文件，用「加载时间 + 落盘体积」双准则评估：**Delta Lake 在任意规模下加载速度最优**；**Apache Iceberg 在稳定性与磁盘节省上最优**；**Apache Hudi 在加载/存储评估中表现最弱**，但其增量更新与流式处理场景可能发挥价值。https://arxiv.org/abs/2604.21449

- **LeJOT: Databricks 平台智能作业成本编排**（2025-12-20 提交，BigDataCom 2026）: ML 执行时间预测 + solver 优化模型的实时资源分配，替代静态配置/反应式调整；真实 Databricks 工作负载下平均降低云计算成本 20%，分钟级调度时间窗。https://arxiv.org/abs/2512.18266

> **分析③：性能优化的「决策点前移」——元数据即杠杆**
>
> Smart Compaction 最有价值的发现不是 R²=0.998 的模型，而是**「二分决策可由单阈值平凡解决，连续效用预测才需要学习」**——这揭示了湖仓运维优化的结构：离散决策（做不做）通常有低维支配特征，连续决策（做多少/何时做）才需要多特征建模。其另一发现（压缩拖慢全扫描聚合）说明优化存在**反噬面**：文件越少 → 任务并行度越低 → 扫描型负载反而变慢。这与 MoE 推理里「专家复制过度反噬显存」是同一类 trade-off 结构。对运维系统的启示：压缩策略应感知负载类型（metadata-heavy vs scan-heavy），而非全局阈值。

> **分析④：算力从「通用 CPU 池」流向「存储路径」——与服务器架构的强共振**
>
> Oasis（SmartNIC 卸载 Parquet 解码）与 Filtered Vector Search（索引进文件 footer）方向相反但目标一致：**把数据就近处理，避免把字节搬回通用计算**。Oasis 的因果逻辑是：网络/存储带宽增速 > CPU 性价比增速 → 解码这类确定性的、带宽密集的、无状态的计算，是 DPU/SmartNIC 的天然候选（与 RDMA、NVMe-oF 卸载同源）。向量检索进 footer 则把「搜索下推」做到文件格式层，让剪枝栈（已为 SQL 谓词优化多年）免费为 ANN 服务。两者共同验证：**湖仓性能下个增量在存储-网络路径上的专用计算**，这正是服务器侧 SmartNIC/DPU 与对象存储协议演进（如 S3 Express、NVMe-oF）的接口机会。

## 三、Agentic Lakehouse：agent 成为数据平台一等公民

- **"Skill Issues": Data-Centric Optimization of Lakehouse Agents**（05-31 v1 / 07-16 v2，ADS @ VLDB 2026，Bauplan）: 编码 agent 正在成为数据基础设施的用户，其成功率不仅取决于模型质量，还取决于教会 agent 用系统的 skills/环境文件。核心观察：**分支型湖仓把 agent 评估从「输出匹配」问题变成「状态验证」问题**——agent 生成的管线代码会诱导具体、可检查的湖仓状态变化。据此构建数据驱动的优化管线：生成 task-verifier 对、隔离沙箱执行候选 skills、用 trace 级信号 + 湖仓状态程序化检查打分。数百任务初步评估：优化后的 skills 使 held-out reward 提升最多 28.6%。https://arxiv.org/abs/2606.01185

- **A Query Engine for the Agents (Hyperparam)**（05-26 提交）: 生产增长最快的数据是 agent traces/chat logs/推理链/模型输出等非结构化文本，「show me where the agent got confused」这类问题无法纯 SQL 回答，文本查询必须把模型放进查询路径。面向客户端 AI 应用（Claude Code/Cursor/浏览器内 agent）提出三个 JS 开源库（Hyparquet/Squirreling/Icebird，合计 <70KB），直接从对象存储读 Parquet 和 Iceberg；per-cell async SQL 执行使 LLM 形态的 async UDF 在 filter-bounded 查询上比 DuckDB-WASM 快 300x（sort-bounded 192x），10 任务 agent 分析套件成本低 2/3。https://arxiv.org/abs/2605.27785

- **Building a Correct-by-Design Lakehouse（Bauplan）**（02-02 提交）: 湖仓在并发不可信变更下脆弱：schema 不匹配运行期才暴露、开发与生产易发散、多表管线失败后暴露部分结果。Bauplan 用三类机制从构造上消除：typed table contracts（转换边界可检查）、Git-like data versioning（可复现协作与 review）、transactional runs（整条管线执行原子发布）。Alloy 模型验证核心直觉并暴露分支可见性反例；主张「正确性最好靠限制编程模型使非法状态不可表示，而非事后修补」。https://arxiv.org/abs/2602.02335

- **Querying Everything Everywhere All at Once: Supervaluationism**（03-10 提交）: agentic analytics 把湖仓变成多版本系统：producer 群在数据分支物化竞争性管线，consumer 需要答案却不知道底层数据生命周期。原型在 supervaluationary 语义下跨分支查询（在无主流 OLAP 可比能力下开源 demo 作为 OLAP 社区基线）。https://arxiv.org/abs/2603.13380

> **分析⑤：agent 写入倒逼「数据平台 = 版本控制系统」——三条路线分殊**
>
> GitLake（Bauplan 团队）、Bauplan Correct-by-Design、Hyperparam 是 agent 化湖仓的三条路线：GitLake 把 Iceberg snapshot 提升为湖仓级分支/合并（沿用 git 心智模型）；Bauplan 用契约+事务把正确性前置（编程模型约束）；Hyperparam 走 JS 原生 + 轻量引擎路线（把引擎塞进 agent 运行时的冷启动沙箱）。分殊的根源在目标运行时不同：GitLake/Bauplan 服务「数据工程师 + agent 协作」（人审 agent 改），Hyperparam 服务「agent 独占的分析」（模型在查询路径里）。但共同前提一致：**agent 的产出必须可验证、可回滚、可审计**——Skill Issues 的「状态验证优于输出匹配」正是这一前提的方法论化：agent 代码是否正确，看它造成的湖仓状态是否与声明一致，而非看它输出的字符串像不像。这对评估体系的启示是：agent 数据任务的评估要从「LLM 裁判打分」转向「程序化检查状态不变量」，后者更便宜、更客观、可离线回放。

## 四、架构范式与行业反思

- **DATER: Data Architectures and their Technical Requirements**（06-07 提交）: 提出概念框架系统描述/评估数据架构，覆盖 6 种现代架构（数据仓库、语义数据湖、湖仓、数据编织、数据网格），从历史语境、定义特征、DATER 维度符合度三维分析，帮助厘清重叠、优势/局限与适用场景。https://arxiv.org/abs/2606.08811

- **AI-Ready 数据库架构选择框架**（06-06 提交）: 九个架构维度 + 多阶段选择流程（负载刻画→约束过滤→兼容性打分），对 13 种数据库范式做结构化对比，归纳三个演化规律：**存储与计算解耦、工作负载驱动专业化、向集成 AI-ready 平台收敛**；最终给出集成湖仓存储、特征处理、语义检索层的 AI-ready 参考架构。https://arxiv.org/abs/2606.08317

- **What Went Wrong with Data Lakes? 15 年现实检验**（06-06 提交，cs.ET）: 阅读 64 份文献 + 15 年摩洛哥/西非金融电信企业湖仓建设/救援的近 500 条现场记录，归纳数据湖七大反模式（Seven Deadly Sins），核心解释是 **Governance Debt（治理债务）**——组织不断推迟的治理决策的复利成本；并提出「治理引力」：治理变难时组织漂回结构化数仓路线。给 Data Swamp 可测量定义 + 治理债务评估模型；结论：湖仓/数据网格技术前进，组织层面记录几乎未动——根因是组织性而非技术性。https://arxiv.org/abs/2606.08266

- **OpenHealth Lake: 健康应用湖仓平台设计**（05-19 提交）: 开源工具构建的湖仓 + 数据联邦 + FAIR 原则原型，含网站、开放 API、Python/R 包，用户研究（不同技术背景参与者）验证可用性与实用性；面向全球卫生协作的可定制、可自托管（云或本地）方案。https://arxiv.org/abs/2605.19922

- **Enterprise Data Science Platform (EDSP)**（2025-12-20 提交）: n 数据集 × m 环境可产生 n*m 副本、推高不一致与成本；基于湖仓 + Write-Once Read-Anywhere 原则，多查询引擎联邦访问同一数据源，消除重复与厂商锁定，面向秒到分钟响应、周期性更新的数据科学负载。https://arxiv.org/abs/2512.03401

- **BatteryLake: Agentic 电池老化数据治理湖仓**（07-06 提交）: LLM agent 提取元数据 + 合成数据集专属转换器，输出以逐字证据为锚、无证据则弃权；HITL 以选择性预测框架把关，26 条 schema/统计/物理合理性规则门禁；发布 25+ 机构 41 数据集开放基准（SOH/RUL 任务、3 种划分协议、8 个基线模型族）。https://arxiv.org/abs/2607.09762

- **Template-as-Ontology: 制造 AI 合成数据基础设施**（05-11 提交）: 单一 Python 配置模块（700-770 行、45 个校验导出）同时作为时序制造仿真器规格与 AI 分析工具运行时域 schema，「构造即对齐」；五层管线（仿真→PostgreSQL→CDC/Iceberg 湖仓→星型模型→12 个参数化 AI 工具）生成跨 4 个运营域 66 实体类型的 MES 形态数据。受控幻觉实验（72 次工具调用，Qwen3-32B）：本体约束参数把工具参数编造率从 43% 降到 0%（Fisher 精确检验 p<10⁻¹²）。https://arxiv.org/abs/2605.11259

> **分析⑥：架构反思的两极化——「治理债务」与「AI-ready 收敛」**
>
> 2026 年上半年的架构论述呈现清晰两极：一端是 What Went Wrong with Data Lakes 的十五年反思（治理债务 + 治理引力，组织根因论），另一端是 AI-Ready 架构的收敛叙事（存储计算解耦、工作负载专业化、集成 AI-ready 平台）。两者并非矛盾而是同一枚硬币：**治理债务说明「架构图不能替代治理机制」，AI-ready 收敛说明「技术栈收敛是治理简化的前提」**。DATER 框架与 AI-Ready 选择框架都在做同一件事——把架构选型从「工程直觉」变成「维度化比较」，这与企业级 AI 平台建设（用户背景）中「选型必须可论证」的方法论需求同构。

> **分析⑦：领域湖仓（battery/health/manufacturing）——lakehouse 作为「数据治理基座」的扩散**
>
> BatteryLake、OpenHealth Lake、Template-as-Ontology 三个领域案例显示湖仓从「分析平台」演化为「治理基座」：BatteryLake 的 agent 弃权机制（无证据不输出）与 Template-as-Ontology 的本体约束（0% vs 43% 幻觉率）都是**把 LLM 的不确定性用数据工程手段驯化**——前者约束在「生成时验证」，后者约束在「schema 构造时对齐」。对通用基础设施的启示：合成数据 + 契约 + 门禁的组合正在成为「AI 数据管线」的标准配方，这为湖仓 catalog/质检层的产品化（自动 schema 校验、约束引擎）提供了明确的场景清单。

## 五、对 AI 基础设施/服务器侧的启示

1. **存储路径计算成为湖仓性能新前线**：Oasis（SmartNIC 解码）与向量检索进 footer 共同指向「字节不搬家、计算就近做」。对服务器架构的直接含义是：DPU/SmartNIC 的卸载范围应从网络（RDMA/NVMe-oF）扩展到**列存格式解码与索引维护**；未来对象存储网关/SDS 节点可能需要原生 Parquet/Iceberg 感知能力——这是 SmartNIC 厂商（NVIDIA BlueField、Intel IPU、AMD Pensando）与存储厂商的交叉机会带。

2. **正确性语义上移要求更强的「提交/审计」原语**：PVDM/GitLake/AuditWeave 的工程落地依赖 catalog 层（快照、分支、审计日志）与存储层（原子替换、版本化、WORM 语义）的配合。若「verify-before-commit」成为标配，对象存储需要支持**可验证的写入回执**（写入后可对内容做哈希校验），SSD/存储控制器侧的端到端校验（类似 T10-PI）会从块层扩展到对象/表文件层。

3. **agent 数据工作负载是「小包高频」IO 的新来源**：Hyperparam 描述的场景（agent 沙箱内冷启动查 Parquet）意味着海量小对象读取 + 短生命周期计算，这对对象存储的 GET 时延（P99）、catalog 元数据缓存的命中率提出新要求，也可能推动「引擎内置缓存/数据本地化」的存储层级设计（与 08-19 存储专题的 S3 Express/NVMe-oF 信号同频）。

4. **运行时方差量化（近 2 倍）为弹性调度提供新维度**：Lakehouse 查询跨云/私有云的近 2 倍运行时方差说明：性能预测与弹性调度的前提是「方差建模」而非「均值建模」；低碳调度（carbon-aware）与成本调度（LeJOT 的 20% 降本）都需要把方差纳入优化目标——这对应数据中心调度器（如 K8s 资源框架）的预测式扩缩容能力升级。

## 六、技术原理深挖（第一性原理展开）

### 6.1 PVDM 的 multiset hash 证明：为什么「可证明写入」不贵

PVDM 的验证原语是 **keyed incremental multiset hash**（带密钥的增量多重集哈希），其原理值得展开：普通哈希（如 SHA-256）对「内容序列」敏感——交换两行或重复一行都会改变哈希；但 multiset hash 对「集合」敏感而对「顺序」不敏感——它把每行（identity 投影 + content 投影）哈希后按可交换运算聚合，使得「哪些行在、每行几份」成为可证明量，同时天然区分「缺失行」与「重复行」（这正是普通哈希做不到的：缺一行和加一行都可能碰巧同哈希，而 multiset 计数结构可以）。

关键工程点在于 **incremental（增量）**：验证器不需要重读全部数据，而是在写入过程中增量维护证明，因此门控开销恒定 ~17ms 且与表大小无关——这解释了「验证开销≈写入 1/5」的量级：它不是在写完后全表扫描校验，而是把校验摊进写入流水线。对基础设施的启示：**「可证明正确」的成本结构由增量性决定**，只要验证可以随写入流式维护，正确性保证就可以从「昂贵的事后审计」变成「廉价的提交前门禁」。

### 6.2 IVF-in-footer：为什么「复用剪枝栈」胜过「新建索引」

Filtered Vector Search 的直觉是：湖仓引擎已经为 SQL 谓词打磨了 20 年的文件剪枝栈（分区剪枝→zone-maps→位图索引），而「过滤 + 向量检索」的本质是**先过滤后检索**——如果过滤能把候选文件从 444 个剪到 89 个（355/444 ≈ 80% 剪枝率），那么向量检索只需要在幸存文件上做，索引本身可以退化为「每文件内的小型 IVF」。这比「全局向量索引 + 过滤后置」更优的原因有二：

1. **索引维护成本**：全局 ANN 索引对写入敏感（插入/删除要重建或走增量结构），而 per-file footer 索引随文件一起写、随 compaction 一起消亡，天然与文件生命周期对齐，无需跨文件一致性协议；
2. **剪枝先行降低召回压力**：过滤后剩余数据量小，IVF 的 nprobe 可以更激进，同等 recall 约束下搜索更快。

论文同时给出适用性边界（过滤列需文件级局部性、残差谓词只能下推进纯分区列），并报告了失败模式——这说明「组合式优化」的价值在于**明确其失效条件**，而不是宣称万能。这正是工程上「组合优于发明」的一个干净案例。

### 6.3 Smart Compaction 的「双速」结论：阈值 vs 模型

Smart Compaction 的 R²=0.998（连续文件缩减比预测）与「二分决策可用单阈值平凡解决」并存，看似矛盾实则统一：**连续量的预测需要模型，离散决策往往被少数支配特征决定**。max_files_per_partition>4 这一阈值背后是物理直觉——每个分区内文件数超过某个量级，查询的计划开销/IO 数量就必然劣化；而「压缩能减多少文件」则依赖文件大小分布、重叠键范围、表更新模式等多个特征（论文提取了 17 个 manifest 元数据特征）。对湖仓运维的启示：**不要把「是否做」和「做到什么程度」混为一谈**——前者可以用可解释的启发式（可审计、可调参），后者才值得上 ML。这避免了「为简单问题引入复杂模型」的过度工程，也符合「模型复杂度应与问题内在复杂度匹配」的第一性原理。

### 6.4 Governance Debt：为什么「推迟决策」会复利

What Went Wrong with Data Lakes 把数据湖失败归因于 Governance Debt——每次「先存起来以后再说」的决策，都在为未来积累需要一次性偿还的治理成本：schema 未定义 → 消费端各自猜测 → 口径分歧 → 数据产品信任崩塌 → 平台被弃用。复利机制在于**债务以「已有数据的规模」为基数计息**：1TB 未治理数据与 100TB 未治理数据的清理成本不是线性关系（后者的血缘/语义已经不可恢复地丢失）。「治理引力」则解释了为何组织最终漂回数仓：数仓的强 schema 约束本质上是一种「预先支付的治理」，在治理能力弱的组织里，预付费模式反而比后付费更可靠。这条因果链对湖仓产品设计的方向性启示是：**治理机制必须在写入路径上默认开启**（schema-on-write 的契约层），而不是依赖事后治理工具——与 6.1 的「提交前门禁」、Bauplan 的「非法状态不可表示」形成完整闭环。
