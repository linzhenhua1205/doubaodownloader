## 1. ⚡ Flink Native S3 FileSystem 深度解析 — Hadoop-free 时代的 Checkpoint 性能革命

> **来源**: [Apache Flink Blog — Introducing Flink's Native S3 FileSystem](https://flink.apache.org/2026/06/26/announcing-native-s3-fs/)（Jun 26, 2026）
> **作者**: Gabor Somogyi, Samrat Deb（Apache Flink PMC）
> **关联版本**: Flink 2.3.0（Jun 25 GA，该博客深入技术细节）

### 1.1 背景：两个插件，一个文件系统，没有好答案

历史痛点——Flink 同时提供两个 S3 插件，**只有一个能激活**，且各自有不可调和的取舍：

| 插件 | 优点 | 致命缺陷 |
|:-----|:-----|:---------|
| **flink-s3-fs-hadoop** | ✅ RecoverableWriter（exactly-once sink） | ❌ Hadoop 全依赖树 + AWS SDK v1（已 EOL 2025-12-31） |
| **flink-s3-fs-presto** | ✅ 快读取路径（checkpoint 友好） | ❌ 无 RecoverableWriter，exactly-once sink 不可用，目录删除已知 bug |

**核心矛盾**: exactly-once sink **或** 轻量取证路径，但从不兼得。而 AWS SDK v1 已于 2025-12-31 结束支持。

### 1.2 Native S3 FS 架构设计

**`flink-s3-fs-native`** — 从头构建的、**零 Hadoop 依赖**的 S3 文件系统：

- **不在两者中选，而是消除取舍** — 统一提供 FileSystem + RecoverableWriter
- **AWS SDK v2** — 异步优先 I/O（S3TransferManager），底层 Netty NIO 复用连接，避免 thread-per-request 瓶颈
- **JAR 大小对比**: 原生 ~13 MB vs Hadoop ~30 MB vs Presto ~93 MB（7× 减轻）
- **配置命名空间**: 简洁 `s3.*` 前缀，不再需要 `fs.s3a.*` 或 `presto.s3.*` 兼容层
- **安全性**: 免去 hadoop-common 传递依赖的 CVE 排查负担（Jackson/Guava/Protobuf/Jetty/Kerberos/ZK 等）

### 1.3 性能基准 — 2× 提速 + 25% 存储节约

**测试环境**: Amazon EKS (ap-south-1) · Flink 2.1.1 · 1 JM + 2 TM · 20 GB RocksDB state · 全量 non-incremental checkpoint / 60s · EXACTLY_ONCE 模式 · 77 分钟运行时长

| 指标 | Presto 插件 | 原生插件 | 提升 |
|:-----|:-----------|:---------|:-----|
| 平均吞吐 | ~92 MB/s | **~200 MB/s** | **2.17×** |
| 平均 checkpoint 时长 | 90.1 s | **48.8 s** | **1.85×** |
| P90 checkpoint 时长 | 155.0 s | **72.5 s** | **2.14×** |
| P99 checkpoint 时长 | 165.3 s | **76.7 s** | **2.15×** |
| 同窗口内完成数 | 40 | **78** | **1.95×** |
| 平均存储/checkpoint | 415 MB | **312 MB** | **25% 更少** |

**吞吐量-状态大小分布**:

| 状态大小区间 | Presto | 原生 | 加速比 |
|:------------|:------|:----|:------|
| 0–2 GB | 79 MB/s | **362 MB/s** | **4.58×** |
| 2–4 GB | 85 MB/s | **285 MB/s** | **3.35×** |
| 4–6 GB | 84 MB/s | **173 MB/s** | 2.06× |
| 6–8 GB | 86 MB/s | **165 MB/s** | 1.92× |
| 8–10 GB | 91 MB/s | **180 MB/s** | 1.98× |
| 10–12 GB | 93 MB/s | **193 MB/s** | 2.08× |
| 12–14 GB | 93 MB/s | **198 MB/s** | 2.13× |
| 14–16 GB | 94 MB/s | **203 MB/s** | 2.16× |

加速比在**小状态 (0–4 GB) 段高达 3–4.5×**，大状态段稳定在 2× 以上。

### 1.4 运维影响

- **更短 checkpoint 窗口** → 少 CPU 被状态序列化消耗，释放给实际数据处理
- **更紧凑恢复窗口** → 故障后少 replay 数据，直接改善恢复 SLA
- **更高 checkpoint 频率** → 不牺牲吞吐量，减少故障回放量
- **更少依赖安全审查** → 无 Hadoop 传递依赖的 CVE 摸排负担

### 1.5 路线图

| 版本 | 状态 | 内容 |
|:-----|:-----|:-----|
| **Flink 2.3** | 实验性 opt-in（本版本） | feature-complete，已在大客户生产验证 |
| **Flink 2.4** | 规划中 | per-bucket 配置 · AWS CRT 支持（HTTP/2 优化）· S3 指标暴露（Flink metric system 集成）· stream-based 读写 |
| **Phase 2** | 社区决定 | 成为推荐默认 |
| **Phase 3** | 社区投票 | 正式弃用 Hadoop/Presto 插件 |

**迁移代价**: 零代码改动，仅部署级操作——`rm` 旧插件 JAR + `mkdir` 新插件 + 清理 `fs.s3a.*`/`presto.s3.*` 配置 + 重启集群。向后兼容已有 checkpoint/savepoint。支持两插件共存，优先级可配置，回滚只需翻转优先级。

## 2. 🧠 Text-to-SQL 新突破 — 零样本 SOTA、Schema 检索、双重自适应

### 2.1 ZAS-SQL: 零样本 Text-to-SQL 新 SOTA — 87.2% Spider（首次超越多数少样本方法）

> **来源**: [arXiv 2606.08245](https://arxiv.org/abs/2606.08245) — Zheng 等（Jun 6, 2026）

**核心观察**: LLM 在零样本 Text-to-SQL 中的失败不是随机的，而是**系统性的、可模式化的**。

**ZAS-SQL 三模块架构**:

| 模块 | 功能 |
|:-----|:------|
| **知识增强 Schema 表示** | 在 DDL（Data Definition Language）中补充缺失语义信息 |
| **规则驱动结构化推理框架** | 从失败案例蒸馏核心生成规则 → Map-Reduce 规则蒸馏 pipeline → 抑制结构化偏离 |
| **执行引导早停（EG-ES）** | 低代价自纠正，在 SQL 执行成功时提前终止 |

**结果**:

| 基准 | 准确率 | 对比 |
|:-----|:------|:-----|
| Spider Dev | **87.2%** | 超越 GPT-4/4o 的 few-shot + fine-tuning 方法 |
| Spider Test | **88.6%** | 零样本新 SOTA |
| UrbanPlan（领域特定） | **81.3%** | 规则蒸馏跨域泛化 |

**关键信号**: 当配备 **4B 参数模型**时，ZAS-SQL 框架超越闭源大模型的零样本基线。证明**规则蒸馏**而非模型缩放是零样本 Text-to-SQL 的核心杠杆。

**与 ZAS-SQL 互补的零样本工作 — GATE**:

> **来源**: [arXiv 2606.05634](https://arxiv.org/abs/2606.05634) — Lee 等（Jun 3, 2026）

GATE（Grounding After Test from Execution）从执行反馈中自举缺失的语义层 grounding：保持假设开放 → 执行已 grounding 部分获取观察 → 仅将观察支持的假设 grounding 为 memory entry。跨基准一致超过强基线。

### 2.2 Schema-First Retrieval: 将 Catalog 选择定义为一等检索问题

> **来源**: [arXiv 2606.28387](https://arxiv.org/abs/2606.28387) — Agrawal, Indukuri（Jun 22, 2026）

**核心论点**: 企业 Text-to-SQL 在 SQL 生成之前就已经失败——模型收到了**错误的 Schema 上下文**。

**方法 — Schema-First Retrieval**:

嵌入 **Catalog 元数据**而非仓库行数据。索引 5 类 typed catalog 对象：

| 索引对象 | 查询时处理 |
|:---------|:----------|
| Tables | 并行向量搜索 |
| Columns | Lineage 扩展 |
| Metrics | 交叉编码器重排序 |
| Relationships | Workload memory |
| Query History | 确定性权限门控 |

**结果**:

| 基准 | 指标 | 数据 |
|:-----|:-----|:-----|
| CRUSH4SQL (1,534 Q) | Table Recall@20 | **96.4%** |
| CRUSH4SQL | Column Recall@10（交叉编码重排序后） | +11.1 pp |
| SEDE (857 Q) | Table Recall@5（query history 加入后） | 52.1% → **92.3%** |
| BIRD (96 Q) | SQL 执行错误减少 | 15.6% → **6.2% (2.5×)** |

**架构信号**: Schema 选择从 prompt 格式化细节升级为**一等检索问题**。Catalog 嵌入 + 向量搜索 + 交叉编码重排序 + lineage 扩展 + 权限门控 形成企业级 schema 检索管线。

### 2.3 Progress-SQL: 多轮 Text-to-SQL 的渐进奖励

> **来源**: [arXiv 2606.06825](https://arxiv.org/abs/2606.06825) — Zhang 等（Jun 4, 2026）

**核心创新**: 现有 RL 方法定义单轮一次性奖励 → Progress-SQL 引入**多轮渐进奖励**。

**方法**:
- **Oracle-guided Diagnostic Tree (ODT)**: 将 SQL 抽象为 clause 级结构画像，产生诊断反馈用于下一轮改进
- **渐进奖励**: 组合 ODT 结构对齐 + 词法对齐 + 进度延迟奖励（越早正确越好）+ 执行状态奖励（从无效 SQL 恢复）

### 2.4 ACE-SQL: Retriever + Generator 的联合自适应优化

> **来源**: [arXiv 2606.05906](https://arxiv.org/abs/2606.05906) — Chen 等（Jun 4, 2026）

**核心问题**: 现有 RL 方法各自优化 schema 检索和 SQL 生成，但检索目标（静态 gold-column 监督）对当前生成器策略可能是次优的。

**ACE-SQL 方案**:
- 从生成器 rollout 中构建**在线 column-set pool**
- 从执行正确的 rollout 中提取最频繁关联的 column set 作为**自适应 on-policy 检索目标**
- 双向自适应：
  - **Retriever → Generator**: 检索器选择生成器能正确执行的 column set
  - **Generator → Retriever**: 生成器适应检索器在执行反馈下的 evolving schema 选择

**结果**: BIRD Dev **65.3%** 贪心执行准确率，仅 **0.93k** 输出 tokens/query，约 3k 合成 RL 训练对。

### 2.5 CoTE-SQL: 结构化 CoT 推理 + 自我增强 + 执行纠错

> **来源**: [arXiv 2606.15598](https://arxiv.org/abs/2606.15598) — Lyu 等（Jun 14, 2026）

**三项创新**:
1. **自我增强推理链**: 从 LLM 蒸馏无需人工标注
2. **结构化 CoT 提示**: 模块化分解 + 示例检索
3. **错误感知修正**: 基于 SQL 执行反馈

**结果**:

| 基准 | 指标 | 数值 |
|:-----|:-----|:-----|
| BIRD | EX | **53.39%**（开源同规模新 SOTA） |
| BIRD | VES | **59.02%** |
| Spider | EX | **79.60%** |

### 2.6 TACO: 开放式领域 Text-to-SQL 基准 — 模糊+跨库查询

> **来源**: [arXiv 2606.14201](https://arxiv.org/abs/2606.14201) — Deng 等（Jun 12, 2026）

**现存基准局限**: 聚焦封闭领域，预设 schema 和明确问题 → 无法评估模糊查询、未指定数据库、跨库查询等开放域挑战。

**TACO 基准**:

| 属性 | 值 |
|:-----|:----|
| 真实示例 | 1,500（基于智慧城市数据服务） |
| 合成示例 | 13,000（基于开放数据门户，覆盖交通/医疗/金融） |
| 构造方式 | 保持真实查询复杂度的数据合成 pipeline |

**基线 TACO-SQL**: 问题重写 → 表链接 → 查询规划。实验表明当前方法与人写 SQL 仍有显著差距。

## 3. 🏛️ 数据架构与系统研究

### 3.1 SemCEB: 语义算子的基数估计基准

> **来源**: [arXiv 2606.23081](https://arxiv.org/abs/2606.23081) — Zimmerer 等（Jun 22, 2026）

**核心问题**: 现代数据库引入语义算子（LLM 驱动的 filter/join，谓词是自然语言指令），但查询优化仍基于传统基数估计方案——语义算子的高逐行成本使坏计划代价被放大**数量级**。

**SemCEB 基准**: 基于真实 (半) 结构化文本+图像数据集，102 条手工精选查询，覆盖广泛选择率范围。

**关键发现**:
| 方法 | 优势 | 局限 |
|:-----|:-----|:------|
| 采样 | 跨谓词类别鲁棒 | 不扩展，高成本 |
| Semantic Histograms | 轻量 | 适用性受限，对谓词类别敏感 |

**架构信号**: 语义算子普及后，传统 CBO 的基数估计方法不适用——需要新的、语义感知的估计方案。SemCEB 是首个面向此问题的基准。

### 3.2 Data Intelligence Agents (DIA): ACA 一阶抽象的企业数据查询

> **来源**: [arXiv 2606.19319](https://arxiv.org/abs/2606.19319) — Vyas 等（Jun 17, 2026）

**核心创新**: 将 Autonomous Coding Agents (ACAs) 作为**一阶抽象**——Agent 生成、执行、验证、修复具体产物（而非发出文本）。

**DIA 三 Agent 架构**:
1. **Data Interpreter**: 数据理解和语义发现
2. **Schema Creator**: 结构化 Schema 构建
3. **Query Generator**: SQL 生成

**关键特性**:
- **Shared Memory**: 经验复用，而非每次从头推理
- **执行驱动**: 每个 Agent 生成具体产物 → 执行验证 → 自动修复
- **领域专家审查**: 每次产物都暴露给领域专家审核

**结果**: 完全自主模式下，7 个 SQL 基准（4 种任务 × 4 种方言）**匹配或超越最佳已发表结果**。只通过自然语言指令跨数据智能任务泛化。
