## 1. 🆕 Spider 2.0-AIFunc — AI-Native SQL 新基准（arXiv Jul 7）

> **来源**: [arXiv:2607.06229 — Spider 2.0-AIFunc: Extending Real-World Text-to-SQL to AI-Native SQL Workflows](https://arxiv.org/abs/2607.06229)（Jul 7, 2026）
> **作者**: Tianyang Liu, Canwen Xu, Fangyu Lei et al.（AWS AI + 耶鲁大学 + UIUC）

### 核心贡献

现代云数据平台（Snowflake/BigQuery/Databricks）已将 LLM 能力暴露为原生 SQL 函数（`ai_classify()`、`ai_extract()`、`ai_sentiment()`、`ai_similarity_search()` 等），但现有 T2S 基准**只评测传统 SQL**，无法反映模型能否生成 AI-Native SQL。

Spider 2.0-AIFunc 基于企业级 Spider 2.0 基准构建：

| 维度 | 数据 |
|:-----|:----:|
| **实例数** | 465 个已验证 |
| **数据库数** | 125 个真实企业数据库 |
| **AI 函数类型** | 6 类（分类/过滤/情感/提取/相似度搜索/聚合） |
| **平台** | Snowflake（`ai_classify` 等内置函数） |
| **验证协议** | 多轮跨时间窗口重复执行确认结果稳定性 |

### 模型表现

| 模型类型 | 模型 | Execution Accuracy |
|:--------|:----|:------------------:|
| 🥇 最强闭源 | Claude Opus 4.7 / GPT-5.x | **67–70%** |
| 🥈 最佳开源 | Qwen3 / LLaMA 系列 | **58.1%** |
| 📉 差距源 | — | 谓词规格化 / Schema Grounding / AI 函数参数化错误 |

### 💡 关键发现

**Agent 框架在 AI-Native SQL 中越复杂效果越差**：为传统 T2S 设计的复杂多阶段 Agent 方案（Schema Retrieval + Relevant Table Selection）并不能迁移到 AI-Native 场景。**最简 Agent 设置（直接生成）一致匹配或优于复杂方案。**

> **含义**: AI-Native SQL（`ai_*` 函数嵌入 SQL）是 T2S 的下一个范式，模型问题不是「如何找表」而是「如何正确参数化 AI 函数」。

## 2. 📦 Databricks Feature Views — 托管 ML 特征管理 Public Preview（Jul 10）

> **来源**: [Databricks Blog — Introducing Feature Views](https://www.databricks.com/blog/introducing-feature-views)（Jul 10, 2026）
> **作者**: Nick Joung, Ian Ackerman, Julia Powell

### 架构概要

```
Feature View（一次定义）
    +-- -> 训练阶段：Point-in-Time 历史数据（批量/离线）
    +-- -> 推理阶段：实时特征服务（批量/流式/在线）
                +-- Batch Features -> Lakebase / Model Serving
                +-- Streaming Features -> Kafka -> Spark Realtime Mode -> Lakebase（200ms p99）
```

**Feature View** 是 Unity Catalog 的一级对象，一个定义同时服务离线训练和在线推理：

| 能力 | 说明 |
|:-----|:------|
| **一次定义，无 Train-Serving Skew** | 平台自动按相同定义计算训练值和在线推理值 |
| **Genie Code 集成** | 自然语言描述 → 自动生成 Feature 代码 + 构建训练集 |
| **Streaming 200ms p99** | Spark Realtime Mode 逐事件处理 + Lakebase 最小化写入放大 |
| **RollingWindow 毫秒级精度** | 每个事件的 "last 10分钟交易合计" 实时可用 |
| **Unity Catalog 治理** | Features 作为一等 UC 对象，全谱系追踪，MLflow 自动记录依赖 |

### 团队使用模式

| 场景 | 案例 |
|:-----|:------|
| 金融风控 | RollingWindow 流式特征 → 毫秒级交易信号 |
| 个性化推荐 | 同一定义同时服务在线 session 意图 + 离线模型训练 |
| 平台工程 | 合并碎片化 Feature 管道 → 治理的 UC 对象，消除自管 Online Store |

### 与竞争对手对比

| 维度 | Databricks Feature Views | SageMaker Feature Store | Tecton |
|:-----|:------------------------:|:----------------------:|:------:|
| **Train-Serving 统一** | 同一 Definition（默认） | 手动映射 | 同一 Definition |
| **流式延迟** | 200ms p99（内建） | 需自建 | ~100-300ms |
| **治理集成** | Unity Catalog 一等公民 | 独立 | 需额外配置 |
| **Genie 自然语言定义** | ✅ 已集成 | ❌ | ❌ |

## 4. 🏗️ Databricks Lakebase 生态加速器 — 40+ SI 方案（Jul 14）

> **来源**: [Databricks Blog — Foundational context: Cross-industry & function-specific accelerators for Lakebase](https://www.databricks.com/blog/foundational-context-cross-industry-function-specific-accelerators-lakebase)（Jul 14, 2026）

### 核心架构定位

Lakebase（托管 Postgres）在 Lakehouse 架构中的角色进化：

```
Legacy:      OLTP <- ETL -> Lakehouse（分析）
                ^ 两套系统 ^ 治理碎片化

Lakebase:    Lakebase（Postgres OLTP） <-自动同步-> Delta Lake（分析）
                 Unity Catalog 统一治理
                 v
                 AI Agents / Genie / 实时应用
```

### 关键方案模式

| 模式 | 代表方案 | 说明 |
|:-----|:---------|:------|
| **Agent 工作记忆** | Cognizant Stateful Agent Stack、Celebal Agent Garage | Lakebase 作为 Agent 持久记忆 + 工作流状态管理 |
| **迁移控制面** | Blueprint Informatica、CT Visa 迁移平台 | Lakebase 管理迁移项目元数据、AI 评估结果、验证状态 |
| **实时特征服务** | Tredence T-Discovery | Lakebase Online Feature Store + Spark Realtime Mode |
| **因果 AI 操作化** | Celebal CausalX | Zero-copy 分支实现反事实 What-if，事务决策日志审计 |
| **成本管理** | T1A LakeSentry | 归一化跨工作区成本可见性，AI 异常检测 |

### 💡 趋势信号

Lakebase 正在填补 Lakehouse 的**操作型工作负载**空白。40+ SI 方案覆盖了 **Agent Memory、实时特征服务、数据迁移控制面、实时 MDM、因果 AI 操作化** 等多个高频模式。这将 Lakehouse 从纯分析平台推向**统一 OLTP/OLAP 的操作型数据平台**（即 LTAP——Lake Transactional Analytical Processing）。

## 5. 🧪 arXiv Text-to-SQL 四篇

### 5.1 正确性预测与选择性验证（arXiv Jul 7）

> **来源**: [arXiv:2607.06799 — What Predicts Correctness in Text-to-SQL? A Selective-Prediction Study](https://arxiv.org/abs/2607.06799)

| 方法 | AUROC | 说明 |
|:-----|:-----:|:------|
| String Self-Consistency | **0.675** | 黑盒信号最强 |
| Log-Probability | 0.67 | 白盒基线 |
| **LLM Judge（单）** | **0.72–0.78** | GPT-4o-mini 到 Claude |
| **LLM Judge（双供应商 Ensemble）** | **0.82** | 两个不同供应商的 Judge 组合，校准 ECE 0.03 |
| Fine-tuned Verifier（In-Distribution） | 0.77–0.79 | 跨 Schema 降至 ~0.66 |

**核心发现**:
- 交叉 Schema 泛化瓶颈不在微调，**在模型推理能力**——7B 模型、Schema 多样性、蒸馏均无法缩小跨 Schema 差距
- 有意义的规避策略：**回答 27% 的问题时，选择性风险仅 24%**（Self-Consistency 无法提供有效低风险子集）

### 5.2 Constrained Decoding — 扩散模型 T2S 首次约束解码（arXiv Jul 8）

> **来源**: [arXiv:2607.07026 — Constrained Decoding for Diffusion Language Models](https://arxiv.org/abs/2607.07026)
> **方法**: 将有限自动机视为图形模型，精确约束扩散模型的均场后验分布

| 任务 | Dream-7B（贪心） | Dream-7B（随机采样） |
|:----|:---------------:|:-------------------:|
| BFCL-Live（未约束） | 63.9% | **22.3%**（崩塌） |
| BFCL-Live（约束解码） | **71.5%** | **69.0%**（稳定） |
| Spider（Text-to-SQL） | 🟢 显著提升 | 🟢 显著提升 |
| 额外开销 | < 5% 墙钟时间 | < 5% 墙钟时间 |

> **意义**: 首次将约束解码推广到扩散语言模型，且开销极小。对 T2S 意味着**无需额外微调即可强制 SQL 语法合规**

### 5.3 On-Prem Open LLMs — 跨族跨代诚实基准（arXiv Jun 28）

> **来源**: [arXiv:2606.29733 — How Far Do On-Prem Open LLMs Get on Text-to-SQL? A Cross-Family Size × Technique Frontier on BIRD](https://arxiv.org/abs/2606.29733)

| 发现 | 结论 | 统计显著性 |
|:-----|:------|:----------:|
| **模型代际 > 参数规模** | Qwen2.5-Coder 7B（39.1%）> CodeLlama 34B（~高个位数） | ✅ McNemar |
| **Self-Correction 稳健有效** | 在所有族内有效 | ✅ 三族显著 |
| **Schema Linking 没用** | 96.5% gold-table recall 仍无效果 | ✅ 排除弱基线问题 |
| **Self-Consistency 不划算** | +0.13pp / ~5× token | ❌ 不显著 |

> **工程意义**: 部署决策应优先选择**现代模型 + Self-Correction**，而非大参数旧模型或 Schema Linking 管线

### 5.4 ProgramTab — 表推理的程序式范式（arXiv Jul 13）

> **来源**: [arXiv:2607.11207 — ProgramTab: Boosting Table Reasoning of LLMs via Programmatic Paradigm](https://arxiv.org/abs/2607.11207)
> **核心**: 对大表格，T2S 方式提取关键信息 → Python 做数据清洗和数学逻辑操作 → 再加行列提取和 SQL 生成
> **适合场景**: 缺乏 Schema 一致性的 Web Table 推理
