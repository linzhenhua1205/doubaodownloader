## 1. 🏗️ Databricks Feature Views — 受管 ML Feature 框架（Jul 10, Public Preview）

> **来源**: [Databricks Blog — Introducing Feature Views](https://www.databricks.com/blog/introducing-feature-views)（Jul 10, 2026）
> **作者**: Nick Joung, Ian Ackerman, Julia Powell
> **状态**: ✅ Public Preview

**核心创新**: 定义一个 Feature View（特征视图），同一份定义同时服务「历史数据→训练」和「实时数据→推理」，消除 Train-Serving Skew。

### 架构设计

```
Feature View（单一定义）
       |
       +---> 实验/训练: 自动产出具 Point-in-Time 准确性的历史数据集
       |
       +---> 生产推理: 受管 Pipeline 写入 Online + Offline Store
                  |
                  +-- Batch Source -> 批量 Materialize
                  +-- Streaming Source (Kafka) -> 200ms p99 端到端延迟
                           |
                           +-- Spark Realtime Mode 连续处理 + Lakebase Online Store
```

### 关键技术细节

| 维度 | 详情 |
|:-----|:------|
| **Online Store** | Lakebase（流优化低写入放大）做 Online Store，替代自管 Redis/DynamoDB |
| **Streaming** | Spark Realtime Mode 基于 Event 粒度逐条更新 Rolling Aggregate，非 Microbatch |
| **延迟保证** | Streaming Feature 端到端 p99 **200ms**（Event→Online Feature 可查询） |
| **服务集成** | Model Serving 自动从 MLflow Model 注册的 Feature 依赖查找并注入特征 |
| **治理** | Unity Catalog 一级对象（可发现 / 权限控制 / 血缘追踪） |
| **Genie Code** | 自然语言在 Notebook 中定义 Feature，一键 Materialize 上线 |
| **Backfill** | 大时间跨度回填 Online Store 内建支持（Corner Case 开箱处理） |

### 行业引用

> "Feature Views cut our feature code dramatically — our data scientists go faster and focus on what drives traveler value, not how to compute it."
> — Jules Marshall, Sr. Director of Data, Skyscanner

### 工程意义

Feature Views 是一个关键的 **Feature 生产化接口统一**——将特征定义、训练数据准备、生产 Pipeline 部署、特征服务、治理——**五件事合为一件**。对比现有方案：
- 传统: Notebook 写 Feature → 数据工程重写 Batch Pipeline → 再写 Streaming Pipeline → 自管 Online Store → 自写 Feature Lookup 代码 → 碎片化
- Feature Views: 定义一次 → 平台处理剩余一切

## 2. 🎯 LinkedIn Text-to-SQL: Enterprise 部署的实践基准（arXiv:2507.14372）

> **来源**: [arXiv:2507.14372 — Text-to-SQL for Enterprise Data Analytics](https://arxiv.org/abs/2507.14372)（Jul 2025, KDD 2025 Workshop on Agentic AI for Enterprise）
> **作者**: Albert Chen 等（LinkedIn）
> **状态**: 📄 已发表 Workshop 论文

**核心发现**: 构建企业级 Text-to-SQL 的核心杠杆不在模型，在于**知识图谱**。Schema-only 配置准确率仅 9%，而完整知识图谱达 48%——相差 **5.3×**。

### 系统架构

```
用户提问
   |
   v
Intent Classifier
   +---> Query Writer Agent
   +---> Data Finder Agent
   +---> Query Fixer Agent
   +---> Question Answering Agent
              |
              v
        Knowledge Graph
        +-- 表/列索引 (DataHub, EBR)
        +-- 使用索引 (Query Log 解析, 流行度, 关联 Join)
        +-- 表聚类索引 (ICA + 访问模式聚类)
        +-- 示例查询索引 (Wiki + 代码库)
        +-- 领域知识索引 (用户标注 + 内部行话)
        +-- 产品区域 -> 用户 -> 表聚类映射
              |
              v
        Context Retrieval + Ranking -> Query Writing -> Fix Loop
                               ^
                        Researcher Agent
                        (gpt-4o-mini 搜索 + gpt-4o Self-Reflection)
```

### 核心实验结果

| 配置 | 表 Recall | 列 Recall | Score 4+ | 成功编译 | 无幻觉 |
|:---------|:----------|:----------|:---------|:---------|:-------|
| 完整系统 | 78% | 56% | **48%** | 96% | 99% |
| A.5 - 无流行度/关联Join | 77% | 53% | 42% | 95% | 98% |
| A.4 - 无领域知识/行话 | 76% | 52% | 49% | 96% | 99% |
| **A.3 - 无示例查询** | **60%** | **38%** | **24%** | 98% | 100% |
| A.2 - 无表/列属性 | 56% | 30% | 11% | 93% | 99% |
| **A.1 - 仅 Schema** | **45%** | **24%** | **9%** | 88% | 99% |
| B.1 - 仅 EBR + Writer | 67% | 50% | 46% | 66% | 77% |
| 最简(C.1: 仅 Schema + EBR+Writer) | 37% | 23% | 16% | 67% | 81% |

### 关键洞察

1. **知识图谱 >>> 建模改进**: 从仅 Schema（9%）到完整知识图谱（48%），知识组件带来的提升远大于模型组件（48%→47% 无 Researcher Agent）
2. **示例查询是最重要的单一组件**: 移除示例查询，Score 4+ 从 49% 跌至 24%（-25pp），大于移除任何其他单个组件
3. **领域知识反而略降**: 可能因为无关领域知识产生了噪声混淆
4. **表聚类是次重要组件**: 提供用户/团队级别的个性化候选表集合
5. **多意图路由**: 除 Text-to-SQL 外，用户需要 Data Finding / Query Fixing / General QA，单一 Agent 不够
6. **架构指导**: 系统运行在 Trino SQL / 知识库基于 DataHub / 模型 Azure OpenAI gpt-4o / 300+ 周活跃用户 / 33% 对话最终粘贴到 SQL 编辑器

## 3. 🧩 Databricks Genie Hackathon: Ask·Build·Compose 三模式（Jul 9, 2026）

> **来源**: [Databricks Blog — Ask, build, compose: What our 5th Genie Hackathon taught us](https://www.databricks.com/blog/ask-build-compose-what-our-5th-genie-hackathon-taught-us-about-databricks-genie)（Jul 9, 2026）
> **作者**: Shruti Prasanna, Rob Bajra
> **状态**: ✅ 总结性发布

### Genie 三模式架构

```
Genie 产品家族
  |
  +-- 🗣️ Genie Agents: 业务用户->自然语言问数据
  |     +-- 基于 Unity Catalog 治理的数据域
  |     +-- ≤30 张表/Agent 保证精度
  |     +-- Genie Ontology: 语义层（度量视图 + 业务词汇）
  |     +-- 示例: OneTrust 190 表 -> 多 Agent Shard + 路由层
  |
  +-- 🔨 Genie Code: 分析师/Builder -> AI 辅助开发
  |     +-- 自然语言 -> Metric Views / UC Functions / Pipeline / Dashboard
  |     +-- UC 集成: 理解真实 Schema，选正确 Join
  |     +-- 示例: 治理智能平台（Flag 废弃报告 + 聚类重复 + AI 就绪度评分）
  |
  +-- 🔗 Compose Genie: 工程师->嵌入 Agent 系统
        +-- Genie Conversation API + Managed MCP Server
        +-- 成为 Agent 的可治理数据查询工具
        +-- OAuth + UC + MLflow Tracing
        +-- 示例: ShipBob 11PM Ops Brief（Supervisor + Genie + 17 Feeds）

底层一致: Unity Catalog 治理 + Genie Ontology 语义理解
```

### 关键工程信号

| 项目 | 技术点 |
|:-----|:-------|
| **OneTrust** | 190 表 + 300+ 视图 → 多 Agent Shard 层，用户无感 |
| **ShipBob** | Supervisor-coordinated Agent 架构，Genie 查仓 + 17 实时外部 Feeds → 自动 Ops Brief（含 $192K 风险金额，Human-in-loop 审批） |
| **Fanatics** | 用 Genie 质疑自己的 Churn Model，发现仅 2 个历史特征贡献大部分 Signal |
| **Ripple KYC** | Genie 内部 CRM 上下文 + External Sanctions → 3-4 小时→ <1 分钟，完整审计溯源 |
| **Procore** | ai_extract() 分类评分 Listing → Dashboard + Genie Agent 组合 → 数天而非数周 |
