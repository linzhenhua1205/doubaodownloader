## 1. 🏗️ Databricks 湖仓产品三箭齐发（Jul 6, 2026）

### 1.1 Auto Upgrades — Lakehouse 表的自动最佳实践 Feature 更新

> **来源**: [Databricks — Automatic Upgrades Blog](https://www.databricks.com/blog/automatic-upgrades-best-practice-features-your-lakehouse-tables)（Jul 6, 2026）
> **作者**: Elizabeth Bowman, Tom van Bussel
> **状态**: Gated Public Preview

**核心问题**: 开放表格式快速迭代，但新功能采用需要：识别合格表 → 验证客户端兼容性 → 在数千张表上跑 `ALTER TABLE`。大多数团队没时间做，因此错过了性能/成本优化。

**Auto Upgrades 方案 — 行业首个湖仓自动升级能力**:

| 步骤 | 机制 |
|:-----|:------|
| **① Observe** | 观察每张 UC 托管表的客户端访问模式（100 天滚动窗口） |
| **② Verify** | 对每项功能检查：所有客户端 DR 版本支持 + 表活跃 + 无外部客户端（当前范围） |
| **③ Upgrade** | 对合格表通过轻量级后台 job 执行 `ALTER TABLE` |
| **④ Schema Default** | 表全部兼容后，将功能设为 Schema 默认值，新表自动继承 |

**可启用功能列表**:

| 功能 | 收益 |
|:-----|:------|
| **Automatic Liquid Clustering** | 按实际查询优化数据布局，无需 ZORDER/手动 clustering key |
| **Deletion Vectors** | 标记行删除/更新，无需重写整个数据文件 |
| **Column Mapping** | 列改名/删除即时生效，无数据重写 |
| **Parquet V2** | 更高压缩比，降低存储成本，加速扫描 |
| **Catalog Commits** | UC 成为跨引擎协调点，支持外引擎写入 UC 托管表 + ABAC 策略 + 多表多语句事务 |
| **Row Tracking** | 行级唯一标识符 → Auto CDF / Vector Search / Lakebase / 物化视图增量刷新 |
| **Checkpoint V2** | 可扩展元数据格式，高并发写入下减少 commit 失败 |

**安全性设计**:
- 仅启用 **GA** 且无性能/成本回归的功能
- **100 天观察窗口**捕获月/季度 Job
- 已验证所有客户端兼容 → 跳过外部/OSS 客户端表
- 每张表可禁用/回滚；一次禁用后不再重启用
- `DESCRIBE HISTORY` 可区分用户行为与 Auto Upgrades 行为

**架构信号**: UC 托管表正在从"用户全权负责表 feature 升级"转向"平台自动安全推进"。100 天观察窗口是高确定性安全网。这是湖仓平台层治理能力的关键演进。

### 1.2 Vibe Data Modeling — 用自然语言描述业务，小时级获得 Silver 层数据模型

> **来源**: [Databricks — Vibe Data Modeling Blog](https://www.databricks.com/blog/reimagining-data-modeling-lakehouse-introducing-vibe-data-modeling)（Jul 6, 2026）
> **作者**: Amr Ali, Cary Moore, Roberto Bruno Martins, Abhijit Tilak

**核心论断**: Silver 层是每个分析栈的成败关键。传统通路：从头构建 6–36 个月，或买行业模板（Acord/FHIR/ARTS/TM Forum）再花 9–12 月裁剪 → 只有 20–40% 相关，且不是为特定业务建的。

**Vibe Data Modeling 方案** — LLM Agent 驱动的数据模型生成器：

| 组件 | 细节 |
|:-----|:------|
| **输入** | 自然语言业务描述 |
| **输出** | 完整、可治理、可部署的 Silver 层数据模型 |
| **时间** | MVM（Minimum Viable Model）< 2 小时，ECM（Expanded Coverage Model）一个下午 |
| **部署** | 原生 Unity Catalog：Schema → Tables → Foreign Keys → Classification Tags → Metric Views → RDFS Ontology → DBML 图 → 样本数据 |

**模型结构 — 六层层次**:

```
Organization
 +-- Divisions (Operations · Business · Corporate)
 |    +-- Domains (有界上下文)
 |         +-- Subdomains
 |              +-- Products (真实业务概念，如 Invoice/Order)
 |                   +-- Attributes（必须有存在理由）
```

**251 条可执行规则**（20 组），确定性门控 + 静态分析：
- 单源真理：一个概念只有一个 owning product
- DAG 外键方向：child → parent，无循环
- 冗余列归一化：当 key 落地时消除

**Agent 架构 — 多模型集成**:
| 模型角色 | 职责 |
|:---------|:------|
| Thinker（大模型） | 推理 + 审查 |
| Worker（大模型） | 高量 Product/Attribute 生成 |
| Smaller models | 域建模、标记、样本数据 |
| Judge | 统一评分竞争式提案 |

**Agentic 循环**: 生成 → 确定性验证 → 失败则换策略重试（非简单重复）→ 单调守护防止退化

**验证机制**:
- 每次 vibe 请求被解析为结构化 VREQs（可检查指令）
- 沙箱化 mutator 独立应用并验证（确定性门控读真实 model + UC，不用 LLM 判断）
- Domain Architect + Global Architect 两级架构审查 — 自动应用、跟踪、最多 8 轮直到干净

**已有 40+ 开源参考模型**（电信/航空/零售/医疗等），完全开源。

**架构信号**: 这是 Databricks 首次将 LLM Agent 嵌入到数据建模核心流程中。银层建模从"6–36 月手工项目"变为"小时级 → 自然语言迭代"。251 条确定性规则 + 两级架构审查 + Agent 循环 的组合保证了 LLM 产出的可靠性。

### 1.3 Contextual Policies in Omnigent — 会话状态的 Agent 安全治理

> **来源**: [Databricks — Contextual Policies Blog](https://www.databricks.com/blog/contextual-policies-omnigent-using-session-state-better-govern-ai-agents)（Jul 6, 2026）
> **作者**: Matei Zaharia, David Nasi, Xiangrui Meng, Kecheng Cao, Tomu Hirata

**核心问题**: 现有 Agent 框架只有简单的 allow/deny 控制，无法应对"同个操作在不同上下文下风险不同"的场景（如 push GitHub 在正常功能开发时安全，在读到不信任网页后则危险）。

**Omnigent Contextual Policies** — 跟踪会话状态进行决策：

| 内置策略 | 机制 | 场景 |
|:---------|:------|:------|
| **Google Drive Policy** | 写操作限制为此会话创建的文档；读机密文档后实施 "no write-down" | 防止 prompt injection 后数据泄露 |
| **Risk Score Policy** | 累计风险分数，越线后 ASK 而非 ALLOW | 同一封邮件，在低风险时自动发，高风险时用户审批 |
| **Cost Policy** | 软阈值警告 + 硬阈值降级（切到低成本模型） | 单会话/单用户预算管控 |
| **Intent-Based Authorization** | 根据用户初始 prompt 锁定权限集（最小权限原则） | 即使 prompt-injected 也无法越权 |

**架构特性**:
- **Meta-harness**: 可包裹 Claude Code、Codex、OpenAI Agents SDK 等任何 Agent harness
- **会话状态持久化**: 策略 handler 接收旧状态和当前事件，返回新状态和决策
- **累积状态**: 跨越多个 tool call，不是单次判断

**架构信号**: Agent 治理从静态规则转向**会话上下文感知**是必然方向。Matei Zaharia（Spark 创始人）亲自参与此项目，说明这是 Databricks 战略级的 Agent 基础设施。

## 2. 🖇️ 数据架构系统性反思

### 2.1 What Went Wrong with Data Lakes？— 15 年实地检查

> **来源**: [arXiv 2606.08266](https://arxiv.org/abs/2606.08266) — Youssef Gahi（Jun 6, 2026）

**核心论点**: James Dixon 2010 年提出 Data Lake 理念，15 年后承诺大部分未被兑现。调查 64 个来源 + 15 年北非/西非金融电信领域近 500 条实地记录。

**七宗罪（Seven Deadly Sins of Data Lakes）**:

| 罪 | 表现 |
|:---|:------|
| 1. No Governance | Schema-on-read 变成"永远不考虑 governance" |
| 2. No Metadata | 数据进入后缺乏目录，无法 discover |
| 3. No Quality | "存原始数据" = "存脏数据" |
| 4. Ownership Gap | 业务方和技术方谁也不负责 |
| 5. False Economy | 看起来便宜（廉价对象存储），实际治理成本爆炸 |
| 6. Skill Mismatch | 需要同时具备数据工程 + 领域知识的人才 |
| 7. Tooling Fragmentation | 各团队各自选工具，形成新的孤岛 |

**根因**: **Governance Debt** — 团队不断推迟的治理决策的累积成本。当治理变难，组织自然漂回结构化的 warehouse 方式 → 称为 **Governance Gravity**。

**对 Lakehouse/Data Mesh 的观察**: 技术层进步了，**组织层几乎没有改变**。给实践者提供 Reality Check Framework + Stage-Based Intervention Matrix。

**架构信号**: 这证实了我们一直以来的认知——湖仓成功最大障碍不是技术而是治理/组织。Lakehouse 解决了技术层（ACID 事务/Schema 演进/开放格式），但组织层仍可能重复 Data Lake 的失败模式。

### 2.2 Bauplan — 正确性内置的 Lakehouse

> **来源**: [arXiv 2602.02335](https://arxiv.org/abs/2602.02335) — Sheng 等（Feb 2, 2026）

**核心问题**: Lakehouse 在并发/不可信变更下仍然脆弱 — Schema 不匹配运行时才暴露、开发与生产容易漂移、多表 pipeline 在故障后暴露部分结果。

**Bauplan 三层正确性机制**:

| 机制 | 解决什么问题 |
|:------|:-------------|
| **Typed Table Contracts** | 使转换边界可检查—Schema 在生产前被验证 |
| **Git-like Data Versioning** | 可复现协作+审查—每个 pipeline 版本可回溯 |
| **Transactional Runs** | 保证整个 pipeline 原子发布—无部分结果 |

**核心设计原则**: 与其事后修补失败，不如**限制编程模型**使非法状态不可表示。早先用 Alloy 模型验证了关键直觉并暴露了事务性分支可见性的微妙反例。

**架构信号**: 与 Auto Upgrades (1.1) 互补——Auto Upgrades 解决"表级别 feature 自动推进"，Bauplan 解决"pipeline 级别正确性保证"。

## 3. 🔬 Text-to-SQL 新论文 — 测试时效率 / 脆弱性发现 / 时空域

### 3.1 Knowing When to Stop — Text-to-SQL 的收敛预测

> **来源**: [arXiv 2607.03991](https://arxiv.org/abs/2607.03991) — Anavi 等（Jul 4, 2026）

**核心问题**: 重复 LLM 调用是评估 Text-to-SQL 结果可信度的标准做法，但何时停止？

**方法**: 轻量级 1-D 模型观察运行一致性轨迹，在每步判断继续是否不会显著改变结果。对比 Beta-Bernoulli 停止规则和学习型 run-count 基线。

**关键发现**: 在 BIRD + 两个生产客户数据集上：
- 方法自适应调整停止点（一致收敛早则早停，晚则继续）
- 运行间的弱序列相关性允许 shuffle 顺序作为训练增强
- 即使注入噪声模拟不完美 judge，仍能可靠预测收敛

**架构信号**: 这是 Text-to-SQL 从"每条查询固定调用次数"转向"自适应成本"的关键一步。推理时成本优化的基础组件。

---

### 3.2 SAGE — 自动化发现 Text-to-SQL 潜在脆弱性

> **来源**: [arXiv 2607.03833](https://arxiv.org/abs/2607.03833) — Wang 等（Jul 4, 2026）
> **状态**: **ACL 2026 Findings 接收**

**核心问题**: 当前诊断方法依赖静态、专家定义的规则，缺乏系统化自动探索能力。

**SAGE 框架**:
1. 为给定样本生成脆弱性假设
2. 引用持续演化的 **Vulnerability Codex**
3. 设计定向扰动，迭代验证和记录潜在缺陷

**关键发现**:
- 在最新开源 LLM 上发现了大量失败案例 — 当前模型显著脆弱
- **Vulnerability Codex 跨模型可迁移** — 发现的模式代表广义的结构性弱点
- 初步修复实验：在生成样本上轻量 fine-tuning 显示出有希望的改进

**架构信号**: 与 ZAS-SQL（Jul 6 报告）的"系统性失败范式"互补——SAGE 自动化发现这些范式，ZAS-SQL 用规则蒸馏压制它们。

---

### 3.3 STRATOS — 气象数据域时空 Text-to-SQL

> **来源**: [arXiv 2607.03501](https://arxiv.org/abs/2607.03501) — Zhang 等（Jul 3, 2026）

**核心问题**: Copernicus 等地球观测计划产生 PB 级数据，但需要 NetCDF/GRIB 专业格式知识。通用 Text-to-SQL 因 **Symbolic-to-Numeric 鸿沟**失败。

**STRATOS 框架**:

| 模块 | 功能 |
|:-----|:------|
| **Spatio-Temporal Resolution Agent** | 在 SQL 生成前解析模糊概念 → 本地化本体 → 外部知识库解析空间实体 |
| **复杂度感知查询重写器** | 重写昂贵空间谓词 → 执行时间从小时级降到秒级 |
| **STRATOS Evaluation Workload** | 7,520 个复杂查询对，由领域专家设计 |

**架构信号**: Text-to-SQL 正在从通用基准扩展到**专业化领域**。气象/时空域需要特殊的 symbol-to-numeric 桥接和谓词优化。
