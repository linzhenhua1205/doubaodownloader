## 二、核心发现

### 2.1 流式窗口归因：从「闭式解」到「可部署运行时」

- **来源/标题**: Closed-Form Predicate-Level Shapley Attribution for Sliding-Window Aggregates（arXiv:2608.23087，2026-08-24 提交，Khani & Assent，IEEE Access 在投）— 流式引擎实时报告滑动窗口聚合值，却无法解释**为什么**聚合取当前值。本文证明对 SUM、COUNT、AVG、总体/样本方差四类聚合，**精确的谓词级 Shapley 归因存在闭式解**：每个谓词只需维护 3 个可加性摘要（count、sum、sum of squares），系数仅依赖两个运行调和数，归因退化为每次滑动 O(1) 摘要更新、零 coalition 枚举；重叠/组合谓词通过原子签名细化精确回答。数学刻画：**每个矩多项式（moment-polynomial）聚合都有此形式，而 MAX/MIN/分位数在任意固定矩阶上可证不存在**。实验：超 10,000 个窗口与暴力 Shapley 浮点精度级匹配，N=10⁶ 时每次滑动约 2μs（比逐窗口重算同公式快 3200×），在 2.9M NYC 出租车行程上以约 1.8M 次摘要更新/秒解释夜间费用尖峰。URL: https://arxiv.org/abs/2608.23087
- **来源/标题**: Incremental Delta-Shapley: A Standalone Runtime for Predicate Attribution on Sliding Windows（arXiv:2608.26930，2026-08-27 提交，Khani & Assent）— 前者的**工程落地篇**：闭式解解决了数学，但运行时还需回答「如何跨滑动维护摘要、如何暴露归因 API、如何回答未注册谓词、如何摊销重复 ad hoc 查询」。IDS（Incremental Delta-Shapley）是单节点独立运行时：消费窗口维护增量 → 更新 global/marginal/atom 三级摘要 → 常量时间求值任意闭式；重叠谓词走原子细化；受限 SQL 风格 API 将归因及其逐滑动变化暴露为一等算子；未注册谓词由保留态扫描/倒排索引/带集中保证的摊销滑窗采样回答，频繁谓词通过重建细化升级。实验：合成/对抗/NEXMark 风格/NYC 出租车四类负载上与穷举 Shapley 浮点精度匹配；**增量维护在 N 上平坦，比同形式逐窗口扫描快至 4.3×10⁵ 倍**；自适应提升在 Zipfian 追踪上削减 ad hoc 成本至 9.2×。URL: https://arxiv.org/abs/2608.26930

**两条发现构成一个完整叙事**：2608.23087 给出「为什么可以」（数学闭式），2608.26930 给出「如何部署」（运行时工程）。对生产流式分析（Kafka + Flink/Spark Structured Streaming 的滑动窗口场景）而言，归因从「指数级不可能」变为「与窗口本身同阶的成本」，这直接改变实时报表「为何涨/为何跌」类问题的实现方式——不再需要事后回放重算或采样近似。

### 2.2 企业 NL2SQL：上下文约束、确定性中间件与 Schema 表示

- **来源/标题**: DRL: A Deterministic Relational Middleware Layer for Transaction-Safe Enterprise NL2SQL Under Schema-Graph Scaling（arXiv:2608.26172，2026-07-23 提交，Mishra/Chukkapalli/Naik）— 企业 OLTP 目录上部署自然语言接口在 schema 图扩展时会压垮语义解析器（上下文膨胀超过 LLM 稳定注意力预算）。DRL 是在前端与 SQL 后端之间插入的**确定性安全管道**：动态上下文剪枝 + 关系 AST 类型化 + 事务安全校验（EXPLAIN 门控与 NULL 守卫），以限定上下文并标记操作性静默分歧（SDop）。在 PostgreSQL/MySQL 上评估，贡献 (i) OLTP schema 图扩展模型、(ii) 1000 对工作负载验证套件、(iii) B0-B3 基线、(iv) 企业 NL2SQL 失败分类学。量化结果：schema 链接提示（B1）较朴素全目录提示（B0）上下文减少 **76%**；DRL 动态路由器（B2）达 **92%** 削减（剪枝 p95=0.58ms、中间件 p95=4.6ms）；GPT-4o / Claude Sonnet 4.5 / Gemini 2.5 Flash 在修正后的评测 harness 下执行匹配 52.9% / 52.8% / 52.1%；SDop 标记 89~100% 假阳性 EX-passing 查询。GPT-4o 失败由语义/过滤错误主导（254/471），列幻觉仅 47/471。**关键方法论发现**：评测后处理器中单个 regex 缺陷曾静默压低准确率并制造虚假的 4~10% 跨厂商差距，修正后消失——基准代码应获得与所评测模型同等的审视。URL: https://arxiv.org/abs/2608.26172
- **来源/标题**: Disentangling Structure and Semantics: How Schema Representation Affects LLM-Based SQL Generation（arXiv:2608.20356，2026-06-17 提交，Su 等，work in progress）— LLM Text-to-SQL 以文本形式读 schema，其中结构线索（表/键/关系）与语义线索（表名/列名）此前只被孤立研究。本文用**受控 6×3 因子设计**（结构层级 L1-L6：从反规范化宽表到带外键与显式连接路径的 3NF；语义层级 S1-S3：匿名/缩写/描述性标识符）在 397 条修正 BIRD 问题（gold query 全程一致）上评估，并为 9 个 BIRD 库物化 1NF/2NF 变体以支撑最低结构层级。9 个模型（0.5B 到旗舰规模）上发现**两轴间的不对称替代**：有意义的命名可补偿缺失的结构，但更丰富的结构元数据在名称模糊时无法恢复性能（8/9 数据库复现，且随模型规模出现，3B 以下可忽略）。结构轴内主导杠杆是**规范化本身**，而非叠加在 3NF 之上的元数据——对当前 LLM Text-to-SQL 而言，实际瓶颈是语义接地（semantic grounding）而非关系暴露（relational exposure）。URL: https://arxiv.org/abs/2608.20356

**两条发现互补**：DRL 回答「企业系统如何约束 LLM 的输入上下文与输出正确性」（系统工程视角），Schema 表示研究回答「给定上下文预算，哪些 schema 信息最值得保留」（信息论视角）。后者为前者的剪枝策略提供了理论依据——DRL 的 92% 上下文削减之所以能维持执行匹配，正是因为它优先保留了语义载荷高的命名信息；两者共同指向企业 NL2SQL 的「上下文预算分配」问题本质。

### 2.3 语义数据处理的成本架构：LLM 调用成为新的优化边界

- **来源/标题**: Compositional Online Learning for Semantic Data Processing Systems（arXiv:2608.27244，2026-08-27 提交，Liskowski/Zhao/Han/Datta/Tsirogiannis）— 语义数据处理系统中一次 LLM 调用贵到主导查询成本（生产中 LLM 计算占查询成本 **80~90%**），又慢到能在其往返延迟内隐藏 CPU 侧学习器的更新（单次 LLM 调用成本是关系谓词的 **10⁵~10⁷ 倍**）。该延迟窗口**倒置了经典自适应查询处理的设计约束**——传统上在线学习器必须保持轻量以免主导其所优化的谓词；在 LLM 延迟下，逐调用梯度步与逐批次阈值求解都能塞进往返延迟。本文提出 LLM 调用边界的组合式在线学习框架：组件在决策粒度 × 学习器更新节奏两轴上组合，共享「将每个训练步藏在下一个 LLM 往返内」的单一学习模式。Cortex AISQL 生产案例组合三个组件：记忆化层、在线逐调用过滤顺序学习器、在线逐批次级联路由学习器；条件成本分解将每个学习组件指派到逐行 LLM 成本的独立因子。独立性假设下两学习组件乘法组合对代表性合取过滤负载达 **11.4×** 上界；级联边界自选择、样本预算收缩、选择性估计漂移将其修正至接近现实的 **8×**。URL: https://arxiv.org/abs/2608.27244

**核心启示**：语义数据处理（如 AISQL 这类将 LLM 算子嵌入 SQL 的系统）的成本模型与传统数据库完全不同——谓词求值是「免费的」，LLM 调用是「昂贵的」。因此优化杠杆从「减少磁盘/CPU 代价」转向「减少 LLM 调用次数」，而在线学习（过滤顺序、级联路由）恰好能把「省调用」的决策实时学出来。这解释了为何 2026 年语义算子系统的性能优化会大规模采用记忆化 + 路由 + 级联的「省钱」结构。

### 2.4 LLM 数据处理的验证与溯源：BLIP 的可验证溯源

- **来源/标题**: Bolt-on, Verifiable Provenance for LLM-Powered Data Processing（arXiv:2608.25210，2026-08-25 提交，Lin/Zeighami/Parameswaran）— LLM 是强大的数据处理工具，但作为黑箱返回答案时不提供「答案从哪来、是否可信」。既有启发式（嵌入相似度、直接问 LLM）对答案来源只有提示、无保证且常出错。本文提出**可验证溯源（verifiable provenance）**：识别输入文本的一个子集，它能在完整文本上复现相同（或等价）答案；并提出**最小性**——溯源尽可能小。朴素解需检查源数据的所有子集，代价不可行。BLIP 是螺栓式（bolt-on）框架：为任意 LLM 数据处理任务高效推断小体积可验证溯源，内置 **8 种策略**（每种都保证找到最小可验证溯源）+ 组合各策略优势的自适应策略，并扩展为产出多个最小溯源。7 数据集实验：BLIP 生成的溯源**总能复现答案**，在可比溯源体积下精度超最优基线 **30%+**；成本低至与原查询相当。URL: https://arxiv.org/abs/2608.25210

**价值定位**：这是 LLM 数据处理「可信化」基础设施的一环，与 08-27 收录的「Never the Number: Structural Abstention」（结构性弃权，NLIDB 可靠性）方向互补——前者在问题层面决定「哪些不回答」，BLIP 在答案层面决定「答案依赖哪些输入」。对监管场景（金融/医疗的数据分析报告）而言，「答案 → 最小证据子集」的可追溯链路是落地的硬需求。

## 三、深度分析

### 3.1 因果链：为什么滑窗归因在 2026 年 8 月迎来「闭式解 + 运行时」双落地？

Shapley 归因从「指数级不可能」到「O(1) 滑动维护」不是孤立的理论突破，而是三条因果线交汇的结果：

**① 流式分析从「监控」走向「归因」，需求侧先行。** 实时报表（异常检测、运营大盘、交易监控）长期停留在「报数」层面——告诉用户指标涨了 12%，却不解释哪个维度（地区/品类/时段）贡献了涨幅。传统解决方案（事后回放重算、按维度下钻）要么成本随窗口历史线性膨胀，要么在窗口滑过后丢失归因窗口。需求侧的空白早已存在，缺的是供给侧的数学工具。

**② 聚合函数的可加性结构被重新发现。** 闭式解的关键洞察是：SUM/COUNT/AVG/方差的谓词级 Shapley 值只依赖 count/sum/sumsq 三个可加性摘要。这并非偶然——这类聚合都属于**矩多项式（moment polynomial）**族，而作者证明了「矩多项式聚合 ⟺ 存在闭式归因」，同时证伪了 MAX/MIN/分位数的同类可能性。这给出了一个干净的边界：能流式维护的（可加性）聚合才能流式归因，硬地把不可加聚合的归因需求与可加聚合的数学工具区分开。**这是「第一性原理」式的工作——先回到聚合的代数结构，再导出算法。**

**③ 运行时工程把数学变成产品。** IDS 的贡献在于回答了闭式解不回答的工程问题：未注册谓词怎么答（保留态扫描/倒排索引/摊销采样三种机制 + 带浓度保证）、高频谓词怎么升级（重建细化）、API 怎么暴露（受限 SQL 风格的一等算子）。**4.3×10⁵ 倍的增量维护加速**和 **9.2× 的 ad hoc 摊销**表明：数学上的 O(1) 只有在运行时维护设计正确时才真正兑现。这也解释了为何两篇论文同一团队（Khani & Assent）间隔 3 天相继提交——数学与工程是同一个研究议程的两半。

**对产业的含义**：任何跑滑动窗口聚合的引擎（Flink SQL、Spark Structured Streaming、Druid、ClickHouse 的 window 函数）理论上都能以「3 个附加摘要/谓词」的成本获得精确归因。这会把「归因分析」从 BI 层的二次计算下沉为流引擎的原生算子——与昨日收录的 DAGSmith（管道级重写）一样，属于「把智能下沉到系统层」的 2026 主线。

### 3.2 对比：企业 NL2SQL 的「执行匹配」光谱——DRL 52.9% vs SPC 97.4% 的启示

将本周可见的 NL2SQL 系统量化结果放在同一光谱上，能看出明显的方法论分层：

| 系统 | 数据集/场景 | 量化结果 | 方法本质 | 出处 |
|:--|:--|:--|:--|:--|
| SPC（Bounded Semantic Planning） | ACME 保险（38 问，3 runs/问） | 97.4% 逐 run 判定正确（vs 基线 55.3%） | 语义路径编译：规划在代码中确定性执行，LLM 只做短语接地 | 2608.16663（08-17） |
| DexterSQL | BIRD-Dev | 67.6%（开源 120B）/ 71.6%~72.2%（GPT-4o/GPT-5.2） | 深度 schema 探查 + 库无关规则挖掘 + 多路径生成 | 2608.11889（08-12） |
| DRL | 企业 OLTP（PostgreSQL/MySQL，1000 对） | 52.9%/52.8%/52.1%（三模型执行匹配） | 确定性中间件：上下文剪枝 + AST 类型化 + EXPLAIN 门控 | 2608.26172（07-23） |
| MIRA | BIRD + ScienceBenchmark（1785 查询） | 执行准确率 +16.53% / +8.78% | 证据验证的修复记忆复用 | 2608.06950（08-07） |

**三个关键观察**：

**① 场景复杂度与准确率呈反比，数字不可直接比较。** SPC 的 97.4% 建立在受控企业 schema（38 问）与「规划在代码中确定性执行」的强约束下；DRL 的 52.9% 面对的是 OLTP schema 图扩展（数百表、图状外键）与 1000 对工作负载——**两者的分母不同**。把 SPC 的 97.4% 与 DRL 的 52.9% 直接对比是「拿选择题分数比应用题分数」。真正可比的启示是：**确定性组件占比越高，准确率越稳定**——SPC 把 SQL 构造与检查全部下沉到代码，DRL 把上下文剪枝与 EXPLAIN 门控下沉到中间件，两者的成功都来自「LLM 只做它擅长的（语义接地），系统做它必须做对的（语法/事务/上下文）」。

**② 「执行匹配」不等于「语义正确」。** DRL 的 SDop 标记揭示：89~100% 的 EX-passing 查询（执行通过）实际上是语义静默分歧——SQL 能跑但回答错了问题。这意味着所有以 execution accuracy 为指标的基准（包括 BIRD）都在系统性高估系统质量。这与昨日收录的 EXPLAIN Yourself!（规划器停滞构成 DoS 向量）形成呼应：**2026 年的可靠性研究开始把「能执行」与「执行得对」拆开**。

**③ 基准代码本身是误差源。** DRL 论文中最具方法论冲击力的是：评测后处理器的单个 regex 缺陷曾制造虚假的 4~10% 跨厂商差距。这是对「LLM 排行榜文化」的直接警示——当模型分数差落在 1~5% 区间时，评测 harness 的 bug 可能比模型差异更大。**对技术选型的启示**：跨模型对比（尤其商业模型）时，必须要求评测代码开源、可复现，且把「评测管线自身的单测」纳入验收。

### 3.3 原理：LLM 调用成本如何翻转自适应查询处理的设计约束

Compositional Online Learning 的核心洞察可以形式化为一个量级对比：

- **LLM 调用成本 ≈ 10⁵~10⁷ × 关系谓词成本**，且占语义查询总成本 80~90%；
- **LLM 调用延迟 ≈ 数百 ms~数 s**，而 CPU 侧一次梯度步/阈值求解 ≈ μs~ms 级。

经典自适应查询处理（如 Eddies、在线 selectivity 估计）的设计约束是「学习器必须比被优化的算子便宜几个数量级，否则学习本身成为开销」。这一约束在 LLM 延迟下**自动失效**：学习器执行 1ms 与 LLM 往返 500ms 相比可忽略，因此可以大胆地把逐调用梯度步、逐批次阈值求解放进往返窗口。**成本结构翻转导致优化目标翻转**：

| 维度 | 经典数据库 | 语义数据处理（LLM 算子） |
|:--|:--|:--|
| 昂贵资源 | 磁盘 I/O、CPU 计算 | LLM 调用（token 计费） |
| 优化杠杆 | 索引、物化、join 顺序 | 记忆化、级联路由、过滤顺序 |
| 学习器约束 | 必须极轻量 | 可重度（藏在 LLM 往返内） |
| 成本模型 | 代价 = f(行数, 选择性) | 代价 = f(LLM 调用次数) |
| 缓存对象 | 页/物化视图 | 语义答案（memoization） |

**为什么乘法组合能到 11.4×？** 条件成本分解把逐行 LLM 成本写成各学习组件对应因子的乘积：过滤顺序学习器削减「每行是否值得调用 LLM」的判定成本，级联路由学习器削减「调用哪个/是否级联」的路径成本，记忆化层削减「已答问题是否重答」的重复成本。**三个组件优化的是逐行成本的三个独立因子，所以效果相乘而非相加**——这是「组合式（compositional）」一词的含义，也是 8×（现实修正后）相对单组件优化（通常 2~3×）的放大来源。对 80~90% 成本占比的 LLM 调用而言，8× 意味着总查询成本下降约 7 倍量级，这在 2026 年 token 计费主导的语义分析场景中是决定性的性价比差异。

### 3.4 结构 vs 语义：Schema 表示的不对称替代律与「接地瓶颈」

Schema 表示研究（2608.20356）的 6×3 因子设计提供了 Text-to-SQL 领域罕见的**受控实验证据**，其不对称替代律值得展开：

**「有意义命名 → 补偿结构缺失」**：把 3NF schema 压成反规范化宽表，只要列名仍然描述性（S3），准确率损失有限；**「丰富结构 → 无法补偿语义模糊」**：把列名换成缩写/匿名（S1），即使保留完整外键与连接路径，准确率也无法恢复。且该效应（a）在 8/9 数据库中复现，（b）随模型规模涌现（3B 以下不可见）。

**机制解释（第一性原理）**：LLM 生成 SQL 的过程本质是「把自然语言问题中的实体/属性/关系，锚定到 schema 中的对应元素」。语义命名（列名=业务词）直接服务于这个锚定过程；结构元数据（外键、连接路径）服务于「锚定之后如何组装」的次要环节。当锚定失败（名称模糊）时，再完善的结构也无法补救——因为组装的对象根本不存在。**而 3B 以下模型看不到该效应，暗示小模型的失败更多来自 SQL 语法/组装能力本身而非接地**——这解释了为何小模型 + 丰富结构（S1 变体）依然差：它们连「组装」都做不好，结构冗余自然无感。

**工程启示**：Text-to-SQL 系统的 prompt 设计（上下文预算分配）应把 token 优先给**语义载荷**（描述性命名、列注释、业务术语映射），而非机械地塞入全部 DDL 元数据。DRL 的 92% 上下文削减与此一致——剪枝策略若按「语义载荷密度」而非「结构完整性」排序，将与本文结论天然吻合。**对数据工程侧的启示更直接**：数据湖仓的表/列命名规范（而非索引/分区设计）可能是 LLM 时代分析可用性的第一生产力——「语义接地」已成为比「关系暴露」更硬的瓶颈。

### 3.5 从「查询性能」到「可信成本」：2026 年 8 月最后一周的数据分析研究议程重定位

把本周（08-21 ~ 08-28）两份日报合并观察，可以画出一条清晰的研究议程迁移轨迹。08-27 的增量重心在「**让系统更快**」：JetStream 生成查询加速器（833×）、DataKernelBench 让 LLM 写 GPU 内核（2.11×）、DAGSmith 重写管道（-67.7% 成本）——优化对象是**执行计划与内核**。08-28 的增量重心在「**让系统可信、让成本可解释**」：流式归因回答「为什么是这个值」（O(1) 闭式解）、BLIP 回答「答案来自哪」（可验证溯源）、DRL 回答「该给 LLM 看什么、如何确认它答对了」（上下文剪枝 + EXPLAIN 门控）、Compositional Online Learning 回答「如何少调用 LLM」（11.4× 成本上界）。

**这不是巧合，而是同一因果链的下一环**：一旦 LLM 生成/优化系统被证明「能快」（08-27 的结论），紧接着的问题必然是「快之外，结果可信吗、成本可控吗」——因为生产采纳的门槛从来不是峰值性能，而是可归责性（accountability）与总拥有成本。**性能是入场券，可信与成本是生死线**。对于服务器/AI 基础设施侧的决策者，这一信号的含义是：2026 年下半年的数据分析栈选型，应把「LLM 算子的可观测性（归因/溯源/门控）」与「LLM 调用成本模型」列为与吞吐/延迟同等权重的一等评价维度——只测 QPS 的基准将系统性误判新一代语义分析系统的价值。

### 3.6 对本地算力与推理成本的技术含义

Compositional Online Learning（8× 成本修正值）与 DRL（92% 上下文削减）的组合，对中小团队还有一层现实意义：**上下文压缩与调用削减是「软件层面的降本」，与硬件（本地 RTX 5060 8G 跑 7B INT4）路线正交且互补**。记忆化层在「同语义问题重答」场景的命中，意味着自建语义分析系统可以把相当比例的热查询从「每次全量 LLM 推理」降为「缓存查找 + 增量验证」；DRL 式剪枝把单次调用的 prompt 从全目录（可能数万 token）压到相关子图（数千 token），直接降低 token 计费与 KV 缓存占用。**在本地小模型上，这两个机制同时缓解显存带宽与上下文窗口两个瓶颈**——这与 08-14 战略收敛期「本地算力 + 数据源质量」的投入方向完全自洽：成本工程让 8G 显存跑 7B 模型的方案在语义分析场景变得更可行，而非更不可行。
