## 1️⃣ GitLake — Agent-first Lakehouse 的 Git-for-data 设计

| 字段 | 内容 |
|:-----|:------|
| **来源** | arXiv:2607.08319 (cs.DB, cs.AI) |
| **发布时间** | 2026-07-09 |
| **会议** | DASHSys @ VLDB 2026, Boston |
| **作者** | Weiming Sheng, Jinlang Wang, Manuel Barros, Aldrin Montana, Jacopo Tagliabue, Luca Bigon |
| **关联系统** | **Bauplan**（code-first lakehouse） |

### 架构要点

将 Iceberg 单表快照提升为 **Lakehouse 级别的 commit / branch / merge**：

| 构件 | 说明 |
|:-----|:------|
| **Lakehouse-wide commit** | 跨多表的一次原子提交，而非 Iceberg 原生的单表快照 |
| **数据分支** | Agent 在隔离分支上操作，人类 review + publish |
| **事务化 pipeline** | Pipeline 跑在临时分支上，最终 merge 后原子可见（all-or-nothing） |
| **Alloy 形式化验证** | 核心抽象已用 Alloy 建模，暴露分支可见性的反例 |

### 设计动机

- Agent 并发写 = 湖仓的多版本问题
- 传统的单表 snapshot 粒度的隔离不足以支撑 multi-table pipeline 的原子性
- "Correct-by-construction"：通过限制编程模型使非法状态不可表示

## 2️⃣ Hyperparam — JS 原生 Iceberg 查询引擎

| 字段 | 内容 |
|:-----|:------|
| **来源** | arXiv:2605.27785 (cs.AI, cs.DB) |
| **发布时间** | 2026-05-26 |
| **作者** | Kenny Daniel |
| **总大小** | **< 70 KB**（三个 JS 库之和） |

### 架构详情

| 组件 | 功能 |
|:-----|:------|
| **Hyparquet** | 浏览器端读取 Parquet |
| **Squirreling** | LLM-shaped async UDF 引擎 |
| **Icebird** | 从对象存储直接读取 Apache Iceberg |

### 关键性能数据

| 对比项 | 数值 |
|:-------|:-----|
| vs DuckDB-WASM (filter-bounded) | **300x 更快** |
| vs DuckDB-WASM (sort-bounded) | **192x 更快** |
| 10-task agent analyst suite | **成本降低 2/3** |
| Bundle size | 3 个库合计 < 70 KB |

### 设计意义

- 面向 **AI-native 客户端应用**（Claude Code, Cursor, Claude Desktop, 浏览器内 Agent）
- 传统湖仓读路径依赖 Spark / Trino / Managed Warehouse → 无法嵌入 JS runtime
- 异步逐 cell 执行：仅当下游 operator 需要时才触发计算（类似 lazy evaluation）
- 标志着数据工程需要为 AI-native 客户端和 agent 更新基础设施

## 3️⃣ Delta Lake vs Apache Iceberg vs Apache Hudi — Spark 性能对比

| 字段 | 内容 |
|:-----|:------|
| **来源** | arXiv:2604.21449 (cs.DC, cs.DB) |
| **发布时间** | 2026-04-23 |
| **平台** | Apache Spark（分布式处理） |
| **数据规模** | CSV + JSON，最大 7 GB |

### 核心结论

| 指标 | Delta Lake | Apache Iceberg | Apache Hudi |
|:-----|:----------:|:--------------:|:-----------:|
| **加载速度（优先级）** | 🏆 **最优** | 适中 | 最慢 |
| **存储效率** | 适中 | 🏆 **最优**（节省磁盘） | 较差 |
| **场景推荐** | 任何数据量下加载速度优先 | 稳定性 + 磁盘空间敏感 | ❌ 批处理不推荐 |
| **适用场景** | 通用批处理 ETL | 批量分析、云原生 | 增量更新、流处理 |

### 实验设计

- 4 个顺序 ETL 步骤：读 → 转 → 写 → 各自格式
- 评估维度：**加载时间** + **存储体积**
- Hudi 在批处理加载和存储方面表现弱，但在增量更新和流处理场景可能有优势

## 数据架构演进趋势（综合）

从 2026 年上半年 arXiv 湖仓论文可看出三个清晰方向：

1. **Agent-first Lakehouse**：Bauplan 系列 5 篇论文（VLDB'26 + AAAI'26）系统性地将湖仓从"人用"改造为"Agent 用"——分支隔离、事务化 pipeline、数据合约、形式化验证
2. **JS/Client-side 查询引擎**：Hyperparam 以 <70KB 在浏览器端读 Iceberg，比 DuckDB-WASM 快两个数量级，满足 AI 客户端应用需求
3. **跨引擎统一治理**：Snowpark 论文（arXiv:2508.05904）展示 Snowflake 的弹性架构和沙箱隔离；EDSP（arXiv:2512.03401）实现 Write-Once Read-Anywhere 减少 33-44% 操作步骤；Learned cost model（arXiv:2506.02802）自动路由 SQL 到最优引擎
