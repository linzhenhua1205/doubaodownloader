## 1️⃣ 🏗️ Delta Lake 4.3 — Catalog-Managed Tables 深化 + UniForm 跨引擎共享

**来源**: [Delta Lake Blog](https://delta.io/blog/) · Jul 2026 · Alex Jiang

### 架构变化

Delta Lake 4.3 在 4.0 引入的 Catalog-Managed Tables 基础上继续深化，核心改动：

| 维度 | 变更 | 架构意义 |
|:----|:-----|:---------|
| **Unity Catalog Delta API 集成** | 事务协调从文件系统完全迁移到 UC | Catalog 成为表状态的唯一事实源（SSOT） |
| **UniForm 支持增强** | Delta ↔ Iceberg ↔ Hudi 格式兼容 | Spark / DuckDB / Flink 共享同一套表，无需格式转换 |
| **Streaming 改进** | catalog-managed 表上的流式读写 | 实时管道一致性问题解决 |
| **Rust Delta Kernel → ClickHouse** | ClickHouse 直接用 Kernel 做一致性接口 | 分析引擎可以直接读写 Delta，不用维护自家解析器 |

### UniForm 架构示意

```
+------------+  +------------+  +------------+  +------------+
|   Spark    |  |   DuckDB   |  |   Flink    |  | ClickHouse |
+-----+------+  +-----+------+  +-----+------+  +-----+------+
      |               |               |               |
      +---------------+------+--------+---------------+
                             |
                    +--------+--------+
                    |  UniForm Layer  |  <- Delta ↔ Iceberg ↔ Hudi 自动转换
                    +--------+--------+
                             |
                    +--------+--------+
                    |  Delta Lake 4.3 |  <- Catalog-Managed (Unity Catalog SSOT)
                    +-----------------+
```

### 💡 信号

**Delta Lake 正在从"表格式"演变为"表格式平台"**：通过 Kernel（Rust 实现进 ClickHouse）+ UniForm（格式自适应）+ Catalog-Managed（UC 事务协调），Delta 正在成为跨引擎数据共享的事实标准。这不是"Spark 的表格式"了，是所有引擎的表格式。

## 2️⃣ 🦆 DuckDB Delta / Unity Catalog Extensions GA

**来源**: [Delta Lake Blog](https://delta.io/blog/) · Jul 2026 · Ben Fleis

### 变更

DuckDB 的 Delta Extension + Unity Catalog Extension 正式移除 "experimental" 标签，三项核心能力可投入生产：

1. **写入支持（Writes）** — DuckDB 可以直接 `INSERT` / `UPDATE` / `DELETE` / `MERGE INTO` Delta 表
2. **Unity Catalog 集成** — DuckDB 通过 UC Extension 直接读取 UC 中注册的 Delta 表，复用权限模型
3. **Time Travel** — DuckDB 支持 Delta 表时间旅行查询，`FOR SYSTEM_TIME AS OF` / snapshot 版本

### 架构意义

```
+---------------------------------------------------------+
|     DuckDB (单机 OLAP)                                   |
|  +----------------------------------------------------+ |
|  | Delta Extension (Writes + Time Travel)             | |
|  | Unity Catalog Extension (权限+元数据发现)           | |
|  | -> 直接对 Delta 表做 ETL / 分析 / 物化               | |
|  +----------------------------------------------------+ |
+----------------------+----------------------------------+
                       |
              +--------+--------+
              |  Delta Lake     |  <- 统一的开放表格式
              +-----------------+
```

### 💡 信号

DuckDB 的 "嵌入式 OLAP" + Delta 的 "开放湖仓表格式" 正在形成一种 **轻量级数据分析新范式**：不需要 Spark 集群就能做 Lakehouse 分析。这对数据工程师和数据分析师的工作流影响深远。

## 3️⃣ ⚡ Flink 2.3 Native S3 FS — 性能基准深度解析

**来源**: [Apache Flink Blog](https://flink.apache.org/blog/) · Jun 26, 2026 · Gabor Somogyi & Samrat Deb

### 基准测试结果

Flink 2.3 引入的 `flink-s3-fs-native` 对比旧 Hadoop/Presto 插件的核心性能提升：

| 场景 | flink-s3-fs-presto (旧) | flink-s3-fs-native (新) | 提升 |
|:----|:----------------------:|:----------------------:|:----:|
| Checkpoint 写入 (1GB) | 基线 | ~2× 更快 | **~100%** |
| 小文件读取 (1MB × 1000) | 基线 | 非阻塞 I/O 显著减少延迟 | 显著 |
| 大文件读取 (100MB+) | 基线 | 异步预取消除等待 | 30-50% |
| 启动时间 | 需加载 Hadoop 类库 | 零外部依赖 | 大幅缩短 |

### 架构对比

```
旧架构 (Flink < 2.3):
+------------------------------+
|  flink-s3-fs-presto          |
|  +------------------------+  |
|  | Hadoop S3A 实现        |  | <- 大量依赖，配置复杂
|  | AWS SDK v1 (阻塞 I/O)  |  |
|  +------------------------+  |
+------------------------------+

新架构 (Flink 2.3+):
+------------------------------+
|  flink-s3-fs-native          |
|  +------------------------+  |
|  | AWS SDK v2 (异步 I/O)  |  | <- 零 Hadoop 依赖
|  | IRSA / 现代凭证链      |  |
|  | FileSystem +            |  | <- 单一插件提供 FS + RW
|  | RecoverableWriter       |  |
|  | 统一 s3:// / s3a://    |  |
|  +------------------------+  |
+------------------------------+
```

### 配置示例

```yaml
# flink-conf.yaml
s3.region: us-west-2
s3.async.enabled: true
s3.upload.min.part.size: 5MB
s3.upload.max.concurrent.uploads: 4
s3.read.buffer.size: 64KB
s3.bulk-copy.enabled: true
```

### 💡 信号

Flink 的 S3 原生实现是 **去 Hadoop 依赖的又一关键步骤**（Flink 2.0 删 DataSet API，2.1 去 Scala，2.3 去 S3 Hadoop 插件）。这使 Flink 成为真正 K8s-native 的流计算引擎——不依赖 HDFS/Namenode 生态。

## 4️⃣ 🛡️ PCC-SQL — 文本到 SQL 的列级访问控制：确定性策略执行

**来源**: [arXiv:2607.12341](https://arxiv.org/abs/2607.12341) · Jul 14, 2026 · Miyamoto, Fan & Yamana

### 问题

企业 T2S 需要跨信任边界部署：数据提供者（拥有权限策略）vs 数据用户（提交 NL 查询）。现有方案基于 "查询提到了哪些列" 来拒绝，且是 **随机性执行**（stochastic）——无法确定性排除违规。

### PCC-SQL 方案

```
NL Question -> LLM Decoder -> per-token Logits Mask
                                   v
                     +-------------------------+
                     | Grammar Productions     |
                     |  - OUTPUT columns        |
                     |  - FILTER columns        |
                     |  - AGGREGATE columns     |
                     +-------------------------+
                                   v
                     策略（角色投影 + Schema Lexicon）
                     -> 禁止列 = LALR(1) 不可达
```

### 核心成果

| 指标 | 值 |
|:----|:---:|
| **Leakage Rate（泄露率）** | **0%** — 确定性保证 |
| Coverage（覆盖） | 最高 **88.7%**（Spider-CU） |
| Token Overhead | 仅 **+10%** tokens |
| 实现 | 单次解码 Pass 完成（无多次推理） |

### 💡 信号

T2S 正在从"生成准确 SQL"进入"生成合规 SQL"阶段。PCC-SQL 的 **确定性策略执行** 是第一个可证明的列级 RBAC 方案，所有禁止列在语法层面就不可达——这比任何后过滤都强。

## 5️⃣ 🔍 Schema-First Retrieval — 把目录检索作为 T2S 的一等公民

**来源**: [arXiv:2606.28387](https://arxiv.org/abs/2606.28387) · Jun 23, 2026 · Agrawal & Indukuri

### 核心洞察

> "企业文本到 SQL 系统在生成 SQL 之前就已经失败了：模型收到了错误的 Schema 上下文。"

现代数据仓库有成千上万张表、缩写的列名、隐式 Join 约定和权限边界——这些根本不在原始表名里。

### 架构

```
NL Question
     v
+---------------------------------------------+
|  Schema-First Retrieval Layer               |
|  +----------+ +----------+ +------------+  |
|  | 5种目录   | |  向量搜索  | | Cross-    |  |
|  | 对象索引  | | (并行)    | | Encoder   |  |
|  | Tables   | |          | | Reranking |  |
|  | Columns  | |          | |           |  |
|  | Metrics  | |          | |           |  |
|  | Relations| |          | |           |  |
|  | Queries  | |          | |           |  |
|  +----------+ +----------+ +------------+  |
|         -> 访问控制门 -> 上下文组装 -> SQL 生成  |
+---------------------------------------------+
```

### 成果

| 基准 | 指标 | 结果 |
|:----|:-----|:----:|
| CRUSH4SQL (1,534 问) | table recall@20 | **96.4%** |
| CRUSH4SQL | column recall@10 (+cross-encoder) | **+11.1 点** |
| 对比 BM25 基线 | table recall@5 | **+32.8 点**（vec 胜出） |
| SEDE (857 问) | +query history → table recall@5 | 52.1% **→ 92.3%** |
| BIRD (96 问) | SQL execution errors | **15.6% → 6.2% (2.5× 降)** |

### 💡 信号

**Schema 检索不是 Prompt 格式化的细节，而是一等检索问题。** 在万表级数据仓库中，Schema-First Retrieval 的正确性直接决定了 T2S 的天花板。

## 6️⃣ 🎯 SQLConductor — 搜索到策略的逐步 T2S 编排学习

**来源**: [arXiv:2606.23537](https://arxiv.org/abs/2606.23537) · Jun 22, 2026 · Zhu, Peng, Li & Luo

### 核心问题

现有 T2S 多阶段管道采用固定顺序（Schema Linking → SQL Gen → Self-Correction → ...），缺乏对查询需求的适应性。

### SQLConductor 方案

```
Monte Carlo Tree Search (离线)
  -> 探索候选工作流
  -> 稳定性估计 -> 稳健监督信号
  -> Stability-weighted SFT + Curriculum RL
     v
Policy Model (在线推理)
  -> 基于中间产物的逐步决策：
     "下一步做什么？"
     [Schema Probe] [SQL Gen] [Execute] [Debug] ...
```

### 成果

| 基准 | 准确率 |
|:----|:------:|
| **BIRD-Dev** | **73.2% EX** |
| OOD 数据集 | 强泛化 |

> "用一个紧凑的编排策略 + 冻结的大模型行动器，超过了直接训练同等或更大 T2S 主干的现有方法。"

### 💡 信号

**T2S 的下一步不是更大更强的模型，而是更聪明的编排。** SQLConductor 的工作流自适应学习代表着 T2S 从"单次生成"到"自适应多步推理"的范式转变。
