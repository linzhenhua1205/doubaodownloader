## 核心发现

### arXiv 学术增量（LLM serving 扩缩容粒度 / SLO 修复 agent 控制面 / 无 sidecar 网格）

- **OpScale: Operator 级扩缩容——LLM serving 扩缩容单元之争**（arXiv:2608.13499, 08-13）: 现有 LLM serving 扩缩容把"整个模型"当单一单元，粒度太粗——突发流量下 SLO 违规或 GPU 利用率低二选一；OpScale 以算子（attention/FFN 等）为扩缩单元，细粒度捕捉推理工作负载动态，同时满足 time-to-first-token 等严格 SLO 与成本效率——扩缩容粒度从"模型级"下沉到"算子级"，与 08-12 归档的 AFD-Ledger 注意力-FFN 解耦部署同向（算子级资源管理成为 LLM 推理平台新范式）。https://arxiv.org/abs/2608.13499
- **ARBITER v2: SLO 导向 Kubernetes 修复的受控 agent 控制面**（arXiv:2607.19182v2, 07-21 v2 更新）: 自愈平台的关键设计——不受约束的 agentic 操作者不能安全改生产集群；ARBITER 构建 OTel 原生因果资源图 + 有界 DiagnosisContext + 有限类型化动作接口，规划与执行分离；安全底座=确定性 schema 检查/策略门/资源与中断预算/审批/有界执行；DeathStarBench（4 节点，Social Network + Online Boutique）实测：坏镜像部署回归 10/10 次选 rollback_canary，而 HPA 要么扩了错误镜像要么不触发；下游关键路径故障时 trace 证据正确定位 home-timeline-service（HPA/资源型控制永不命中）；开源 controller/replay corpus/harness。https://arxiv.org/abs/2607.19182
- **Meshlib: Cilium 之上的无 sidecar 服务网格**（arXiv:2608.13107, 08-13）: sidecar 代理每次请求重复应用层解析带来延迟与资源开销；Meshlib 以 Cilium 为控制面扩展 + 应用内库进程内执行 L7 策略，传输层身份/路由交给 eBPF 数据面——职责分离去掉 sidecar 延迟且保持网格安全语义；TrainTicket 基准（37 服务 126 安全策略）对比 Istio/Linkerd/纯 Cilium 取得最低端到端延迟，资源开销相当，且与未修改服务完全互操作可增量落地。https://arxiv.org/abs/2608.13107

### CNCF 云原生运维动态（自愈升级 / LLMOps 所有权 / 策略可观测 / 双栈冲突）

- **Eleven minutes, zero humans: Kairos 自愈 K8s 控制面升级管道**（CNCF Blog, 2026-08-14）: Kairos Hadron 不可变 Linux（A/B 分区升级 + cosign 签名镜像，不原地打补丁而写新分区）；3 控制平面节点 K3s HA + Cilium CNI + OpenTofu 全代码引导；实测控制面升级 11 分钟零人工——CVE 频发时代"可信任的自动化升级"成为运维平台必备能力，与 08-11 归档的不可变基础设施主线呼应。https://www.cncf.io/blog/2026/08/14/eleven-minutes-zero-humans-building-a-self-healing-kubernetes-upgrade-pipeline-on-kairos/
- **LLMOps and platform engineering: AI 管道所有权之争**（CNCF Blog/Syntasso, 2026-08-13）: LLMOps 是 MLOps 的专门子集（数据管理/prompt 工程/部署服务/监控评估/安全治理），差异在规模与评估——LLM 微调与推理成本更高、输出比 accuracy 数字难评分得多（须安全+可信）；LLMOps 叠加在 MLOps/DevOps 之上与平台工程争夺同一管道所有权——所有权模型搞错会重造 shadow-IT（用 prompts 代替 Jenkinsfiles）；平台团队从"跑管道"转向"定义 AI 应用的操作契约"。https://www.cncf.io/blog/2026/08/13/llmops-and-platform-engineering-who-should-own-the-ai-pipeline/
- **Observable policy as code: 可观测策略护栏**（CNCF Blog/VictoriaMetrics+Kyverno, 2026-08-12）: PaC 定义应用如何运行/访问哪些资源/如何保持合规，是平台工程护栏；结合 OTel 遥测让"策略效果"可度量——护栏不止约束行为，还要证明约束有效；Kyverno（K8s 原生策略引擎）与 VictoriaMetrics 视角联合，策略即代码从合规工具走向平台可观测性的一等公民。https://www.cncf.io/blog/2026/08/12/good-apps-arent-born-theyre-guided-building-observable-policy-as-code/
- **Mesh observability 的 0+0=2 陷阱**（CNCF Blog/Coralogix+VictoriaMetrics, 2026-08-11）: Istio+Kiali+Prometheus 开箱即得请求率/延迟/错误率（免改代码）；但"全都要"——同时上 OTel 零代码插桩后 trace 断裂、span 对不上号（双 telemetry 栈产生重复/分裂）——"零代码插桩"承诺与网格自带指标叠加时数据一致性先崩；实践指南给出合并/去重/关联策略，网格观测栈选型进入"单一数据面 vs 双栈融合"的工程权衡期。https://www.cncf.io/blog/2026/08/11/a-practical-guide-to-solving-when-zerozerotwo-in-mesh-observability/
- **Lightweight Dragonfly: P2P 镜像分发去数据库化**（CNCF Blog, 2026-08-13）: Dragonfly（云原生镜像/制品 P2P 分发）提供去掉数据库栈的轻量部署——大规模集群镜像拉取风暴场景（发布/扩缩容）的运维负担进一步降低；P2P 分发链路的轻量化是规模化集群运维的隐性刚需。https://www.cncf.io/blog/2026/08/13/lightweight-dragonfly-deployment-p2p-distribution-without-the-database-stack/

## 趋势研判

- **LLM serving 扩缩容进入"算子级"细粒度时代**: OpScale（算子级扩缩）与昨日 AFD-Ledger（注意力-FFN 解耦部署）同向——整模型视为黑盒的时代结束，推理平台资源管理粒度下沉到算子/模块级，运维平台需适配"非模型级"扩缩容语义。
- **自愈自动化从"能自动化"走向"受控自动化"**: ARBITER 用"有界动作接口+预算+审批+有界执行"约束 agent 改生产集群（坏镜像回归 10/10 选对动作 vs HPA 扩错镜像），Kairos 用不可变 A/B 分区让升级"11 分钟零人工"——安全边界与不可变基座是自愈平台落地的双前提，与 08-17 Safety-Gated Autoscaling/Progressive Crystallization 主线连续。
- **运维所有权之争浮出水面**: LLMOps vs 平台工程（AI 管道归谁管）成为显性议题——运维平台在 LLM 时代的职责边界（操作契约 vs 跑管道）正在重新定义，警惕 prompts 版 shadow-IT。
- **可观测性进入"合并去重"阶段**: mesh 双栈 0+0=2 陷阱说明观测栈叠加不再免费——单一数据面 vs 多源融合的工程权衡（对应 08-17 OTel 基数治理主线），平台选型期需主动设计遥测数据一致性。
