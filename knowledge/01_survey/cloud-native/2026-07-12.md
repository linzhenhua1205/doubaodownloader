## 一、🔴 AI Agent 基础设施 — 运行时新范式

### 1.1 agent-substrate: 超越 sandbox 的 Agent 高效运行时

CNCF Blog, Jul 7, 2026 | Lin Sun (Solo.io, CNCF Ambassador)

> 核心论点: **Sandboxing your agents is necessary, but not sufficient.**

**两个项目的差异化定位**:

| 维度 | agent-sandbox (SIG Apps) | agent-substrate (独立项目) |
|:-----|:------------------------|:---------------------------|
| 核心关注 | 安全 + 隔离 + 生命周期管理 | 密度 + 效率 + 操作可扩展性 |
| 运行模式 | Pod 持续运行 | 按需唤醒、执行中 suspend、恢复 |
| 资源效率 | 低（空闲 Pod 空转） | 高（共享 Worker Pool，agent 无状态化） |
| 扩缩粒度 | 每 agent 独立 Pod | Worker Pool 水平扩缩，agent 密度远大于 Pod 数 |
| 运行环境 | 标准 K8s Pod | gVisor / Kata 轻量 sandbox |

**关键机制**: agent-substrate 将 agent "actor" 生命周期与 Worker Pod 解耦:
- Agent 不在 Worker Pod 中持续运行
- 短突发执行 → 挂起 → 在任意可用 Worker 上恢复
- Worker Pool 通过 kagent 统一管理

**Lin Sun 的实践**: 6 个 AIRE agent 映射到 6 个 actor template，仅需 1 个 Worker Pod 并发执行；并发增加时水平扩展 Worker Pool 即可

**我的评估**: 对 AI 集群的 Agent 部署有重要参考价值。万卡集群的运维 Agent（故障诊断/巡检/调度优化）如果每个都独立 Pod 运行，资源浪费巨大。agent-substrate 模式值得关注。

- **来源**: https://www.cncf.io/blog/2026/07/07/why-sandboxing-your-agent-is-not-enough/

## 二、🔴 Dapr v1.18 GA — Workflow 安全与 MCP Server

Dapr Blog, Jun 10, 2026 | Dapr Maintainers

> 版本主题: **安全 + 持久化 + 规模化**，核心是 Workflows 模块

### 2.1 Workflow 安全三层防御

| 安全层 | 机制 | 说明 |
|:-------|:-----|:------|
| **WorkflowAccessPolicy (CRD)** | 纯 allow-list | 控制哪些 appID 可以调用哪些 WF/Activity；跨 trust domain 默认 deny |
| **历史签名防篡改** | Ed25519 链式签名 | 每步事件 batch 签名并链式链接，状态加载时全链路验证 |
| **跨 App 证明** | ChildCompletion/Activity 签名证明 | 子 WF 返回值经签名，父 WF 验证后才接收入口 |

**防篡改链**: Event Batch → Signature(prevDigest + events_digest) → 链式链接 → 状态加载全验证。验证失败触发 `DAPR_WORKFLOW_HISTORY_TAMPERED` 错误，保留原始状态供取证。

### 2.2 MCP Server 资源 — 内置 WF 编排引擎

- 新 CRD: `MCPServer`，将 MCP (Model Context Protocol) Server 工具暴露为 Durable Workflow
- 应用代码无需导入 MCP SDK、管理连接或凭证
- 支持传输: `streamable_http` / `sse` / `stdio`
- 认证: 静态 header/OAuth2/SPIFFE JWT SVID
- Lifecycle hooks: beforeCallTool / afterCallTool 等
- **价值**: 将 AI 工具调用编排为**有状态、可恢复的 Durable Workflow**，而非无状态 HTTP 调用

### 2.3 其他重要更新

| 特性 | 状态 | 说明 |
|:-----|:-----|:------|
| Jobs API | **Stable** | 性能回归测试已加入 CI |
| HotReload | **GA + 默认开启** | Component/Subscription/MCPServer/Configuration 等 7 种资源热重载 |
| 工作流并发限制 | 全局 + 按 name | 精确控制 WF/Activity 并发数 |
| 超限 Payload 优雅挂起 | 95% body-size 预警 | 不 tear down 整个 stream |
| Placement: Coalesce Window | Optional | 100+ replica scale-up 时减少 O(N) 轮次 |
| Sentry: Ed25519 密钥 | 默认 | 不能回退到 1.17.7 以下 |
| Sidecar Probe 调优 | 生产级 | Liveness ~230s, Readiness ~3~5s |

- **来源**: https://blog.dapr.io/posts/2026/06/10/dapr-v1.18-is-now-available/

## 三、🟡 OpenTelemetry 生态更新

### 3.1 Don't Wrap OpenTelemetry — OTel API 最佳实践警告

OTel Blog, Jun 24, 2026

- **问题模式**: 团队在 OTel API 外再包一层抽象 (IMetric/ITracer)，本意是简化使用
- **严重后果**:
  - 丢失上下文传播能力 (W3C TraceContext)
  - 丢失自动 instrumentation 兼容性
  - 更难升级/迁移 → vendor lock-in
  - 团队内部抽象与生态标准脱节
- **反模式三要素**: 泛化(Too Generic)/泄露(API Leak)/隔离(Isolation)
- **正确做法**: 直接用 OTel API，通过配置层 (OTel SDK 配置/Collector pipeline) 解决定制需求
- **来源**: https://opentelemetry.io/blog/2026/06/24/dont-wrap-opentelemetry/ (404，需确认)

### 3.2 OpenCensus 兼容正式退役
