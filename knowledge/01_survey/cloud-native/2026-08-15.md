## 主线：AI 时代供应链信任——从"扫描"到"签名+准入"

- **TNS/你的容器镜像没有签名——AI 时代这是一颗滴答作响的定时炸弹**（2026-08-14, Uma Sridharan, AWS ECR 团队, AWS Marketplace 赞助）: 核心论点=**扫描是反应式的（"镜像里有什么漏洞"），签名是主动的（"谁构建的、离开构建系统后是否被改过"），二者互补不可替代**。AI 时代紧迫性三层：①**模型权重/训练数据集/推理运行时/agent 工具日益以 OCI artifact 分发**，而 pickled PyTorch checkpoint 没有 CVE 可匹配——"没有为训练好的权重准备的漏洞数据库"，safetensors 消除代码执行路径但不回答"谁生产的"；②实证攻击链：2024-02 JFrog 发现 Hugging Face 恶意模型（pickle `__reduce__` hook 在 `torch.load()` 时执行任意代码开 reverse shell），Hub 上约 **100 个模型携带真实恶意载荷**；HF 用 ClamAV+pickle 静态扫描后，2025-02 ReversingLabs 描述 **nullifAI 两个模型绕过 picklescan**（用 7z 而非 ZIP 压缩 + 载荷运行后立即破坏 pickle 流使静态分析报错）——"模式匹配扫描器是一条不断移动的线"；③**爆炸半径变化**："被篡改的应用镜像毁掉一个页面，被篡改的 AI 模型 artifact 在规模上污染预测"，agentic 场景=生产中的 API 调用/工具调用/支出。**为什么 Registry 是对的位置**：每个镜像必经 registry；当前实践是"验证地址不是验证来源"（admission 策略允许某 registry 账号 ≠ 能区分好镜像坏镜像）；digest pinning 只证明"拿到了你要的字节"不证明"那是该要的字节"。方案=**Amazon ECR Managed Signing**：registry 级签名配置（最多 10 条规则=签名 profile×repository filters），匹配的 push 自动签名；**AWS Signer 保管私钥**（密钥永不在 repo/runner/build log），默认有效期 135 个月，撤销=revoke profile 让全集群立即停止信任；签名对象是 Notary payload 的 image manifest（media type/digest/size，content-addressed）而非镜像字节本身；签名作为 detached OCI artifact 存入同 repository（`application/vnd.cncf.notary.signature`），**异步签名**（push 提交后调 SignPayload，同步调用会把 Signer 抖动变成开发者 push 失败）。验证链=resolve digest→OCI Referrers API 取签名→证书链验证→trust store 根→trustedIdentities 比对→revocation 检查；EKS 上经 Gatekeeper+Ratify 或 Kyverno（均用 AWS Signer plugin）。运维含义=**签名三步骤 Sign/Verify/Enforce 中 Enforce 是关键**（"没有强制执行的签名什么都没改变"），准入控制器阻断未签名镜像；注册表托管签名把"签名成本"从每个团队数周项目（Notation CLI/Cosign+密钥托管+轮换）降为"push 的属性"——AWS 立场是"加密从来不是难点，让它成为阻力最小的路径才是"。https://thenewstack.io/unsigned-container-images-ai/

- **诚实标注/赞助说明**: 上文为 AWS Marketplace 赞助文章（ECR Managed Signing 产品推广），量化数据与供应链事实链（JFrog 2024-02、ReversingLabs 2025-02、safetensors 机制）属真实可查，产品主张按厂商视角采信；与 08-10 EKS 镜像拉取、08-07 npm provenance 攻击（TNS）同属供应链信任主题链

## 主线：可观测性治理——"全栈 OTel"不等于 trace 统一

- **CNCF Blog/mesh 可观测性实用指南：为什么 zero+zero=two**（2026-08-11, Israel Blancas, Coralogix & Jose Gomez-Selles, VictoriaMetrics）: 问题场景=应用 OTel SDK 埋点（Jaeger 看完整端到端 trace）+ Istio/Kiali sidecar 注入（metrics/logs 正常）→**同一请求出现两棵互不相交的 trace 树**（Jaeger 里 `checkout` 与 `checkout.otel-demo` 两个同名服务）。根因=**传播（propagation）不统一**：Envoy 内置 OTel tracer 对每个请求新建 root span，**从不读入站的 W3C traceparent 头**；应用 SDK 独立继续自己的 traceparent——两条 trace 流永不汇合。修复三步：①**Envoy 改用 Zipkin tracer**（Envoy 的 Zipkin tracer 会提取入站 B3 trace context 并在既有 trace 下建子 span；讽刺点=以为用 otel-tracing provider 是终极零埋点方案，实际内置 OTel tracer 恰恰是断链元凶）；②**应用端加 B3 传播**（`OTEL_PROPAGATORS=tracecontext,baggage,b3multi`，同时保留 W3C 标准头并额外发 B3 供 Envoy 续接）；③**OTel Collector 作为格式归一化中心**（同一 Collector 用 OTLP receiver 4317 + Zipkin receiver 9411 收两端数据，归一化后进同一 backend）。效果=checkout 服务从 ~14/2 spans 两簇 → **51-75 spans 单 trace 完整串联**（应用业务 span + proxy 网络 span 同 trace ID）。通用模式=Collector 可做语义约定变更/采样/基数控制/span metrics 生成/信息脱敏/多 backend 导出——**"生产中每个系统版本/默认值不同，一处依赖配置不一致 trace 就断"**；Istio 开箱即用的可观测性到"能调试单条请求"之间隔着传播格式一致性这道隐藏沟壑。https://www.cncf.io/blog/2026/08/11/a-practical-guide-to-solving-when-zerozerotwo-in-mesh-observability/

## 侧线：升级自动化的"策略闭环"——Kairos 实操（tech 组已收录，本组补运维视角）

- **CNCF Blog/Kairos：11 分钟零人工的自愈 Kubernetes 升级管道**（2026-08-14, Olivier Calzi, CNCF Golden Kubestronaut）: 【跨组标注：tech 组已收录本条目，此处仅保留本组运维视角增量】。**架构=六工具单职责**：Gitea（自托管 git+Actions runner 跑 CI）/ Renovate（watch quay.io 新 tag→自动开 PR 改两行：image tag + CR metadata.name）/ Kyverno（ClusterPolicy 准入：拒绝 image 不匹配 `quay.io/kairos/hadron:*` 的 upgrade CR，防错配与 typosquatting）/ Cosign（验签：不只"是不是对的 tag"而是"真实 CI pipeline 确实产出了这个 artifact"，对 GitHub Actions OIDC identity）/ ArgoCD（GitOps：检测 PR merge 为 drift 自动 apply，无人工 kubectl）/ kairos-operator（执行：watch NodeOpUpgrade CR→cordon 单节点→拉镜像→写 A/B slot→重启→等 rejoin→下一节点）。**不可变 OS 基础**：Kairos Hadron 不原地 patch，写新 OS 镜像到非活动分区后重启，回滚=重启回旧分区（A/B 分区是回滚的物理保障）。实测时间线（7/7 升 v0.4.0）：11:42:00 PR merge→11:42:37 ArgoCD Synced→11:43:09 镜像拉完（324MB/25.5s）→11:43:11 cordon→~11:47 节点0 Ready→~11:51:36 全部完成，**总墙钟 11 分钟、merge 后零人工、etcd quorum 从未破坏、工作负载零中断**。**两个运维教训**：①`concurrency: 0` 的语义=**"全部节点同时"而非"一次一个"**（作者原以为是一次一个，三控制面节点同时重启、etcd quorum 纯靠运气存活）→ 改为 `concurrency: 1`；②NodeOpUpgrade 是一次性 CR，**patch spec.image 无效**（operator 视为已完成），必须同时改 metadata.name 强制 ArgoCD delete+create 新 CR 才触发；Renovate 自定义 regex manager 的 `extractVersionTemplate` 字段在其 schema 中不存在、**静默无效**（只升 image 没升 name → 管道"看似坏了实则半执行"），改 `currentValueTemplate` 修复——"人类审查仍存在的原因：抓自动化安静地做错事却看起来像做对了的地方"。后续=gateway cluster 接入同一 GitOps loop；计划加 CI dry-run（merge 前跑 `kairos-agent upgrade --recovery`）。https://www.cncf.io/blog/2026/08/14/eleven-minutes-zero-humans-building-a-self-healing-kubernetes-upgrade-pipeline-on-kairos/

## 本期观察线

1. **供应链信任从"扫描"转向"签名+准入"，AI artifact 是关键驱动力**：模型权重/agent 工具无 CVE 可比对（safetensors 解决执行路径但非来源），nullifAI 证明静态扫描可被绕过——签名从"最佳实践"升级为"准入强制"，注册表层托管（密钥不落地、异步、可撤销）把运维税从团队级降到平台级；与 08-07 npm provenance、08-10 EKS 镜像拉取、08-14 shadow LLMOps 治理同链——**AI 时代的可信边界正在从"内容检查"迁移到"来源证明"**
2. **可观测性统一是传播协议问题，不是工具数量问题**：Envoy 内置 OTel tracer 新建 root span 的坑说明"全栈 OTel"≠trace 统一——W3C/B3 双传播 + Collector 格式归一化才是落地关键；与 08-13 平台工程"golden path"叙事一致：**治理发生在约定的边界（协议/collector），不在每个团队的自由发挥里**
3. **升级自动化进入"策略闭环"形态**：Kairos 把准入（Kyverno）+ 签名（Cosign）+ 执行（operator）+ 回滚（A/B 分区）拼成完整闭环，`concurrency: 0` 与 Renovate 字段两个坑揭示 **operator CRD 默认值与工具 schema 是隐性故障面**——自动化越深，对"静默做错事"的审查越不可省略
