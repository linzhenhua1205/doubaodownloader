## 一、🔴 FinOps 核心增量：OpenCost × llm-d 推理成本追踪（CNCF 8/5）⭐

- **OpenCost 1.121.0：Kubernetes 首个推理成本追踪（08-05, IBM Research × OpenCost Maintainer）**: 将 OpenCost（CNCF Incubating）与 llm-d（CNCF Sandbox，分布式 LLM 推理）集成——**把基础设施成本连接到 vLLM 的 token 流**，回答"每个 token 到底花多少钱"。核心指标来自 vLLM（`vllm:prompt_tokens_total` / `vllm:generation_tokens_total`），**非 llm-d 用户也可直接用 vLLM 指标获益**。PoC 在 109 GPU / 30 个 AI 模型集群上验证。
  https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/

- **两种成本、两个问题（方法论核心）**: ① **Allocation-based（分配型）成本** = 模型可用成本（权重占 VRAM + 活跃推理计算 + 共享基础设施 gateway/KV cache 分摊），与基础设施账单对账，回答"**这个模型花了我多少钱**"；② **Usage-based（使用型）成本** = 仅活跃推理期间消耗，按实际处理的 token 归因（含 KV cache 命中节省），回答"**这个模型的实际工作花了多少钱**"。两者差距 = 保持模型 warm 的固定成本。**警告：低流量模型可能 95% 时间处于 "warm but idle" 状态——权重占着 VRAM 烧钱却产出零 token**。

- **利用率公式 + build-vs-buy 陷阱（可直接复用）**: **Utilization = usage-based $/M tokens ÷ allocation-based $/M tokens**（例：$1.00 ÷ $4.00 = 25%）。**常见错误**：用 usage-based cost 证明自托管比 SaaS 便宜——自托管 25% 利用率时真实成本是 $4.00/M tokens 而非 $1.00；与外部 API 价格（$2.00）对比，**外部 API 更便宜；自托管在 ~50% 利用率以上才有竞争力**。同时给出优化靶点：提高利用率（smarter routing / 模型共享 / 流量整合）直接降低 allocation-based 单 token 成本。

- **新指标与 labels**: `llm_total_hourly_cost`（每模型每小时成本）+ `llm_cost_per_million_tokens`（混合每百万 token 成本），labels 含 model_name / model_version / namespace / cost_basis（usage vs allocation）/ workload_type。**input 与 output token 成本分开报告**（prefill vs decode 计算负载不同；disaggregated serving 下 prefill/decode 跑在不同硬件，此区分对准确归因至关重要），reasoning tokens 纳入 input 成本。KV cache 命中影响 input token 处理成本，已计入。

- **完整成本 ≠ 只有 GPU**: 一个 llm-d 模型还包含——Inference Scheduler (EPP，CPU-only 但高吞吐下有真实成本)、gateway proxy、**KV cache 存储（tiered-cache 部署可达 18TB 持久存储）**、Workload Variant Autoscaler。llm-d 组件通过 **SharedLabels 机制**在部署时打标，OpenCost 共享成本分摊逻辑处理归因——**保持两项目解耦**（OpenCost 无需理解 llm-d 内部架构）。共享成本计入 allocation-based、排除出 usage-based。

- **4×4 成本诊断矩阵**: Allocation High + Usage Low = 保持可用成本高但推理高效 → 利用率问题（考虑模型共享/流量整合）；High + High = 托管贵运行也贵 → 评估模型选型；Low + Low = 部署良好；Low + High = 托管便宜但推理贵 → 评估模型大小/量化/硬件匹配。**FinOps 团队可识别低利用率模型并量化 right-sizing 收益；llm-d 正在开发的 smart router 可把 per-token 成本纳入路由决策**（与延迟/吞吐并列）。路线图：wasted GPU 容量测量、LLM 特定 idle-GPU 检测、UI 集成。

## 二、🟠 CNCF 项目动态：K8gb → Incubating（8/5）

- **K8gb 成为 CNCF incubating 项目（08-05, Staff Post）**: Kubernetes Global Balancer——**云原生 GSLB（全局服务器负载均衡）**，解决多集群/多地域应用可用性与容灾：基于标准 K8s API + CoreDNS + ExternalDNS 自动化流量管理与无缝故障切换。2021年3月进 Sandbox，5年后晋升 Incubating。**组件**：GSLB Custom Resource（声明式 API）+ K8gb Operator（健康检查/流量策略）+ K8s 原生健康检查（直接复用 pod liveness/readiness probe 做路由决策）。
  https://www.cncf.io/blog/2026/08/05/k8gb-becomes-a-cncf-incubating-project/

- **K8gb 生态数据与路线图**: LFX Health Score **72/100**；**239 contributors（73% 季度持续贡献）、105 个贡献组织、1197 GitHub stars、149 forks（+71% YoY）、软件估值 $2M+**；案例——葡萄牙最大私有银行 Millennium bcp 用其实现 **99.99% 服务可用性**并大幅缩短恢复时间。集成面：Ingress + Gateway API（控制器无关）、嵌入式 CoreDNS、ExternalDNS、**Crossplane 全局控制面**（声明式多集群基础设施供给）。路线图：多区域复杂流量路由、GSLB 可观测性/指标、服务网格深度支持。→ 对多集群容灾架构：K8s 原生 GSLB 补上了"跨集群流量编排"这块拼图。
