## 1️⃣ 🔴 Kubeflow × Cilium 实战：K8s GPU 利用率 60% 闲置的根因定位

**来源**: [CNCF Blog Jul 23 | When Kubeflow meets Cilium: Debugging 60% idle GPUs in Kubernetes](https://www.cncf.io/blog/2026/07/23/when-kubeflow-meets-cilium-debugging-60-idle-gpus-in-kubernetes/) · Ramkumar Nagaraj & Bingi Narasimha Karthik (Adobe, Golden Kubestronaut)
**状态**: 实战级 K8s GPU 排障案例，量化数据完整

### 症状

> 分布式训练作业调度正常，Pod 全部 Running，无 Crash/OOMKill，dashboard 正常 → 但 GPU 利用率仅 **40%**（60% 闲置）

### 排障全过程 — 五层检查

| 排查层 | 做了什么 | 发现 |
|:-------|:---------|:------|
| **1. GPU 直接诊断** | `nvidia-smi` + DCGM 指标 → 逐 GPU 看利用率 | 所有 GPU 利用率均匀偏低，非单卡瓶颈 |
| **2. 网络吞吐检查** | Cilium `cilium connectivity test` + Hubble 流量观测 | 发现部分 Pod 间通信**丢包 + 高重传率** |
| **3. 存储 IO 检查** | Kubeflow Pipeline 中每步的 IO wait | 无异常（训练数据已本地缓存） |
| **4. 调度拓扑检查** | K8s `topologySpreadConstraints` + GPU 亲和性 | 跨 Node 通信路径过长导致 NCCL all-reduce 等待 |
| **5. **根因锁定位**** | Hubble 流分析 + Cilium NetworkPolicy 日志 | **Cilium NetworkPolicy 规则过于严格**，拦截了部分 NCCL AllReduce 的 side-channel 通信 |

### 根因

| 因素 | 说明 |
|:-----|:------|
| **直接原因** | Kubeflow 命名空间下 Cilium NetworkPolicy 未允许 NCCL 使用的动态端口范围（NCCL 协议动态协商端口，部分 high-port 被策略拦截） |
| **根本原因** | 策略安全团队与训练团队未同步 NCCL 通信的端口范围需求 |
| **放大器** | 跨 Node GPU 通信依赖 NCCL AllReduce（带宽敏感），丢失的 side-channel 包导致梯度同步延迟膨胀 |

### 对 AI 集群运维的价值

| 结论 | 直接可用的方案 |
|:-----|:--------------|
| **GPU 闲置不一定在 GPU 侧** | 先用 `dcgm-exporter` → 确认利用率低 → 转查网络/策略层 |
| **Cilium NetworkPolicy 可导致 NCCL 通信降级** | 训练命名空间的 NetworkPolicy 需显式允许 NCCL 动态端口（建议 `protocol: TCP, portRange: 50000-51000`） |
| **Hubble 是 GPU 集群网络排障的标准工具** | `hubble observe --namespace kubeflow --drop` 快速定位丢包根因 |
| **拓扑感知调度** | `topologySpreadConstraints` + nodeAffinity 确保 GPU 通信在最短路径内 |

## 2️⃣ 🟡 OpenTelemetry 贡献者队列实战 — Bloomberg × CNCF 的 10 周模型

**来源**: [CNCF Blog Jul 23 | Sustaining OpenTelemetry: What a 10-week contributor cohort actually looks like](https://www.cncf.io/blog/2026/07/23/sustaining-opentelemetry-what-a-10-week-contributor-cohort-actually-looks-like/) · Alyssa Wright (Bloomberg)
**状态**: OTel 项目可持续性维护的量化报告，有复用价值

### 背景
- **问题**: OTel 作为第 4 大 CNCF 项目（119篇博客），维护者 burnout + contributor pipeline 稀疏
- **方案**: Bloomberg × CNCF 联合发起 10 周 Contributor Cohort Program
- **目的**: 从「dependency management→stewardship」转变，系统性培养贡献者

### 10 周模型

| 阶段 | 周次 | 内容 |
|:-----|:----:|:------|
| **Onboarding** | 1-2 | 项目架构、SIG 介绍、Git Workflow、社区文化 |
| **Guided Contribution** | 3-6 | 分配 mentor + 具体 issue（由易到难） |
| **Independent** | 7-9 | 自主认领 issue、提 PR、参与 review |
| **Graduation** | 10 | 提交最后 PR + 社区分享 + 决定是否继续贡献 |

### 关键数据

| 指标 | 数据 |
|:-----|:-----|
| **参与者** | 共 24 人（Bloomberg 内部 + 外部社区） |
| **PR 产出** | 89 个合并 PR（47% 来自初次贡献者） |
| **留存率** | 项目结束后 6 周，58% 参与者仍在贡献 |
| **Reviewer pipeline** | 8 人成为 OTel 正式 reviewer |
| **覆盖组件** | Collector / SDK（Go/Java/Python） / Operator |

### 对我方的价值
- OTel 的可持续性模型可复用于超节点生态中的**社区项目维护**（如 Redfish Operator、BMC exporter）
- 10 周 cohort 模式有完整 SOP，可直接套用
