## 一、CNCF 项目里程碑

### 1.1 HAMi → CNCF Incubating (2026-07-15)

**来源**: [CNCF Blog](https://www.cncf.io/blog/2026/07/15/hami-becomes-a-cncf-incubating-project/)

HAMi（异构AI计算虚拟化中间件）正式晋级 CNCF Incubating 项目。核心能力：

- **GPU 虚拟化/分片**: 将物理 GPU/NPU/DCU/MLU 按内存/核心/设备数量切片
- **硬隔离**: 共享 workload 之间强制运行时隔离
- **多调度策略**: binpack、spread、topology-aware 的 pod 调度
- **多厂商统一接口**: 非绑定单一厂商设备插件生态

**关键数据**: 550+ 组织贡献者 · 2,687 total contributors (YoY +43%) · 3,500+ GitHub stars · 16 releases (v2.9.0 current) · 10,000+ GPUs 部署 (DaoCloud 中国10+数据中心)

**生态集成**: Volcano（批处理调度）、Koordinator（GPU共享）、Kueue（规划集成）
**方向**: gang-scheduling、preemption、autoscaling、DRA consumable monitoring、AMD Mi Series/PPU

### 1.2 Confidential Containers → CNCF Incubating (2026-07-22)

**来源**: [CNCF Blog](https://www.cncf.io/blog/2026/07/22/confidential-containers-becomes-a-cncf-incubating-project/)

## 二、Kubernetes v1.36 核心特性

**来源**: [Kubernetes Blog - v1.36 系列文章](https://kubernetes.io/blog/)

K8s v1.36 "Haru"（春）于 2026年6月发布，以下为关键特性分类解析：

### 2.1 AI/ML Workload 增强

| 特性 | 阶段 | 说明 |
|:-----|:----:|:-----|
| **Pod-Level Resource Managers** | **Alpha** | 首次支持在 Pod 级别管理资源（非容器级别），适配 GPU/NPU 整卡分配场景 |
| **In-Place Vertical Scaling for Pod-Level Resources** | **Beta** | Pod 级别资源原地垂直扩缩容，推理服务弹性伸缩关键能力 |
| **Workload-Aware Scheduling** | GA | 调度器识别 workload 模式，优化 GPU/加速器放置 |
| **DRA (Dynamic Resource Allocation) 增强** | GA+ | 更多驱动支持、新特性，走向下一代设备管理 |
| **PSI Metrics for K8s** | GA | Pressure Stall Information 原生暴露，识别 CPU/IO/内存资源压力 |

### 2.2 存储/持久化

| 特性 | 阶段 | 说明 |
|:-----|:----:|:-----|
| **Volume Group Snapshots** | GA | 卷组快照生产就绪 |
| **Declarative Validation** | GA | 声明式校验正式 GA |
| **Tiered Memory Protection with Memory QoS** | 新 | 分层内存保护 + 内存 QoS |

### 2.3 安全/多租户

| 特性 | 阶段 | 说明 |
|:-----|:----:|:-----|
| **User Namespaces GA** | GA | 用户命名空间正式 GA，增强多租户安全隔离 |
| **Admission Policies That Can't Be Deleted** | 新 | 不可删除的准入策略，防误操作/恶意删除 |
| **Fine-Grained Kubelet API Authorization** | GA | 细粒度 Kubelet API 鉴权 |
| **Mixed Version Proxy** | Beta | 混合版本代理，支持集群升级期间的 API 兼容 |
| **SELinux Volume Label Changes** | GA | SELinux 卷标签变更（v1.37 可能有影响） |

### 2.4 可观测/运维

| 特性 | 阶段 | 说明 |
|:-----|:----:|:-----|
| **Server-Side Sharded List and Watch** | 新 | 服务端分片 List/Watch，etcd 负载均摊 |
| **Staleness Mitigation and Observability for Controllers** | 新 | Controller 过时数据缓解 + 可观测性 |
| **New Metric: Route Sync in CCM** | 新 | Cloud Controller Manager 路由同步新指标 |
| **Mutable Pod Resources for Suspended Jobs** | Beta | 挂起 Job 的资源可变，批处理更灵活 |
| **ExternalIPs 废弃** | Deprecation | Service ExternalIPs 正式进入废弃流程 |

### 2.5 即将到来: v1.37

- **Code Freeze**: 2026-07-22 截止
- **SIG Storage Spotlight**: 持续演进中
- **WG Device Management**: 硬件管理加速器（GPU/TPU/NPU）管理标准化

## 三、K8s AI/ML 特性与 AI 基础设施

### 3.1 NVIDIA K8s 深度投入：DRA + KAI Scheduler + AI Conformance

**来源**: [CNCF Blog - NVIDIA 官方](https://www.cncf.io/blog/2026/07/23/the-future-of-ai-is-community-driven-and-open/)

NVIDIA 发布重大社区承诺：

- **$400万/3年** 资助 CNCF 项目 CI 在真实 GPU 上运行测试
- **加入 CNCF Governing Board**
- **GPU DRA Driver**: 上游贡献至 SIG-Node，作为 DRA API 参考实现
  - 实时按需 GPU 分配取代调度时静态分配
  - MIG 设备共享（Alpha）
  - ComputeDomains: GPU 通过 Multi-Node NVLink 跨节点安全共享内存
- **KAI Scheduler**: CNCF Sandbox 准入
  - Gang scheduling + pre-scheduling simulation
  - Hierarchical queues + Dominant Resource Fairness
  - Asynchronous binding（已验证 10,000+ GPU 集群）
- **AI Conformance Program**: 18→31 认证平台，v1.35 新增 agentic workflow + in-place pod resizing 要求

### 3.2 Kagent / Agent-substrate: Pod 还是执行单元？

**来源**: [CNCF Blog - Solo.io Lin Sun](https://www.cncf.io/blog/2026/07/14/is-a-pod-the-right-deployment-unit-for-an-ai-agent/)

核心论点：**AI Agent ≠ 传统微服务**，Pod 作为执行环境（execution worker）而非部署模型（deployment model）。
引入 **agent-substrate** 抽象层：

- **WorkerPool** → NodePool，**Worker** → Node，**ActorTemplate** → PodTemplate
- Actor（逻辑 Agent）可动态调度到 Worker，Worker 保持长运行 Pod
- 支持短生命周期、突发执行、动态子 Agent 创建
- 延续 K8s 基础设施优势（网络/安全/调度）+ 新增 Agent 级生命周期管理

> **关键问题**: 身份/安全策略/多租户/可观测性是否应提升到 Actor 级别而非 Pod 级别？

### 3.3 自托管 LLM in K8s: vLLM + LINSTOR 实践

**来源**: [CNCF Blog - LINBIT](https://www.cncf.io/blog/2026/07/16/running-a-self-hosted-llm-in-kubernetes-with-vllm/)

实操指南：在 K8s 上用 vLLM + LINSTOR（DRBD 复制块存储）部署自托管 LLM。

- OpenAI 兼容 API → 任何已有工具链可指向本地
- PersistentVolume 缓存模型权重（重启不需要重新下载）
- 混合策略：高流量/敏感数据用本地，低流量用托管 API
- `llm-d` 项目作为推理请求路由器（K8s 原生）

### 3.4 GPU 60% 空闲: Kuebeflow + Cilium 拓扑问题

**来源**: [CNCF Blog - Adobe Kubestronaut](https://www.cncf.io/blog/2026/07/23/when-kubeflow-meets-cilium-debugging-60-idle-gpus-in-kubernetes/)

典型案例：Kubeflow 训练 + CiliumNetworkPolicy 导致 GPU 集群 60% 空闲。

**根因**: K8s 调度器拓扑无关 × Cilium 拓扑感知网络策略 = 正确系统集体犯错
**三种表现**: 硬阻断（训练不启动）、跨区延迟（吞吐下降30-60%）、跨AZ流量费
**修复**: `nodeAffinity` + `topologySpreadConstraints` + tolerations → GPU 利用率 40%→85%

> **启示**: CNI 对拓扑的认知 K8s 调度器看不到——这是故障的静默来源。该模式通用化：任何拓扑感知 CNI + 分布式 ML 框架都可能遇到。

### 3.5 LLM Serving: Goodput > Throughput

**来源**: [CNCF Blog - Akamas](https://www.cncf.io/blog/2026/07/20/why-goodput-matters-more-than-throughput-for-llm-serving/)

vLLM 调优实证：优化三个参数（`gpu_memory_utilization` / `max_num_batched_tokens` / `max_num_seqs`）

**核心结论**:
- 相同 TTFT 下，p95 TPOT 可相差 10×（50ms vs 494ms）
- 无 SLO 的 throughput = 营销数字，非工程指标
- 最优配置靠自动搜索而非手动猜测
- 配置需随流量/模型/提示变化持续重跑

## 五、服务网格与多集群 (Service Mesh)

### 5.1 Linkerd 联邦多集群: 三种模式共存的实战指南

**来源**: [CNCF Blog - Dominik Táskai, Linkerd Contributor](https://www.cncf.io/blog/2026/07/27/federating-clusters-for-zero-downtime-kubernetes/)

Linkerd multicluster 三种模式对比及其在多区域 GKE 上的实战：

| 模式 | Label | 网络要求 | 使用场景 |
|:-----|:------|:---------|:---------|
| **Gateway (层级)** | `exported=true` | 仅需 Gateway IP 可达 | 无扁平网络时使用 |
| **Flat (P2P)** | `exported=remote-discovery` | 扁平网络(pod IP 路由) | 客户端需指定集群 |
| **Federated** | `federated=member` | 扁平网络 | 自动负载均衡+故障转移 |

**混沌测试结论**: 杀死一个集群后，federated 服务自动重平衡（零错误），mirrored 服务友好降级（503/502）。联邦模式是默认推荐，镜像模式适合客户端明确需要指定集群的场景。

**配置陷阱**: VPC peering 需`--export-custom-routes` / 单集群 pin 到单zone 控成本 / CIDR 不可重叠 / 每个消费集群需独立 controller
