## 一、K8s 控制面运维：v1.36 运维向特性补全（AI 调度之外的另一半）

- **Kubernetes v1.36 Server-Side Sharded List and Watch**（K8s 官方, 2026-05-06）: API 服务器读路径优化——List/Watch 请求按资源分片分布到多实例，缓解 etcd 热点；对万级节点集群，watch 风暴是控制面雪崩首因，与 v1.33 Streaming List 一脉相承——**控制面水平扩展的最后一公里是「读路径去单点」**，watch 语义对客户端透明，无需改 client 即可扩容。https://kubernetes.io/blog/2026/05/06/kubernetes-v1-36-server-side-sharded-list-and-watch/
- **Kubernetes v1.36 Staleness Mitigation and Observability for Controllers**（K8s 官方, 2026-04-28）: 控制器数据陈旧问题的检测与可视化——新增 staleness 指标（控制器缓存/队列落后于 API 实际状态的程度），让「控制器卡死但不报错」的静默故障可发现；**运维价值=控制器健康度从黑盒变可观测指标**，配合同期 Declarative Validation GA 降低控制面「静默漂移」风险。https://kubernetes.io/blog/2026/04/28/kubernetes-v1-36-staleness-mitigation-for-controllers/
- **Kubernetes v1.36 Mixed Version Proxy 转 Beta**（K8s 官方, 2026-05-15）: 控制面滚动升级兼容层——旧版 API server 可把请求代理给新版，实现「先升 API server、再升其它组件」；**大规模集群=把「一次升级整个控制面」拆成可回滚多步操作**，升级韧性体系一环。https://kubernetes.io/blog/2026/05/15/kubernetes-1-36-feature-mixed-version-proxy-beta/
- **Introducing the Checkpoint/Restore Working Group**（K8s 官方, 2026-01-21）: 新官方工作组——容器级 checkpoint/restore（进程+内存快照），把 CRIU 类能力做成 K8s 原生原语；**运维含义=「慢启动 Pod 预热迁移」「故障现场冻结取证」「有状态负载快速恢复」三条赛道**，与 v1.26 Forensic checkpointing 形成从「功能」到「工作组」的演进信号。https://kubernetes.io/blog/2026/01/21/introducing-checkpoint-restore-wg/
- **Announcing Ingress2Gateway 1.0**（K8s 官方, 2026-03-20）: Ingress → Gateway API 的官方迁移工具发布 1.0——自动转换 Ingress 资源为 Gateway API 配置，覆盖 annotation/ingress class/rewrite 等常见映射，降低存量集群向 Gateway API 迁移的改造成本；**配合 Gateway API v1.6（TCPRoute/UDPRoute GA，tech 组已收），「Ingress 十年遗产」的退出路径正式工具化**。https://kubernetes.io/blog/2026/03/20/ingress2gateway-1-0-release/

## 二、可观测性进入 AI 数据时代：trace 即应用数据，治理从「采」转向「管」

- **Observability has a data problem. AI is about to make it worse.**（The New Stack, 2026-08-26）: 可观测性根本矛盾=遥测增速持续超过存储/分析预算，AI 负载（训练/推理代理/agent 循环）是新爆炸源——agent 每次决策产生多轮工具调用 trace，高基数标签（tool/agent/session）推高索引成本；**与昨日 Omdia 调研（59% 因成本终止 agentic AI、遥测预期 9.5X）互相印证：2026 可观测性主战场从「采集」转向「数据治理」**（采样/路由/保留/成本归属）。https://thenewstack.io/opentelemetry-observability-telemetry-storage/
- **When AI agent traces become application data**（The New Stack, 2026-08-26）: agent trace（工具调用链/模型选择/重试路径）从「排障临时数据」升级为「应用数据」——agent 行为=业务逻辑，trace 是还原「agent 为什么这么做」的唯一记录；**运维含义=agent trace 需像业务数据一样治理（保留期/合规/访问控制），而非日志式采完即弃**；与 08-25「AI 决策 receipt」同链：决策证据从审计要求变成数据资产。https://thenewstack.io/agent-traces-application-data/
- **After becoming cloud computing's telemetry standard, OpenTelemetry graduates into the AI infrastructure era**（The New Stack, 2026-05-21）: OTel 成可观测性事实标准（CNCF 毕业、采用率超 90%）后重心转向 AI 基础设施——GenAI 语义约定（model/request/token 维度）、agent 与 LLM 调用的 tracing 规范（SemConv GenAI）；**与 tech 组 OTel shift-left（08-25）互补：一个扩标准、一个降门槛，AI 可观测性正被 OTel 标准化**。https://thenewstack.io/opentelemetry-hits-general-availability/
- **OpenTelemetry roadmap: Sampling rates and collector improvements ahead**（The New Stack, 2026-02-24）: OTel 2026 路线图——采样（sampling）策略升级（基于命中的 tail sampling、成本感知采样）与 Collector 性能/可扩展性改进是两大主线；**回应上述「数据治理」需求：采样从「随机丢弃」走向「按价值保留」（保留失败/慢/高成本 trace）**，Collector 作为「遥测网关」承接路由/富化/脱敏职责。https://thenewstack.io/opentelemetry-roadmap-sampling-rates-and-collector-improvements-ahead/
- **A practical guide to solving when zero+zero=two in mesh observability**（CNCF, 2026-08-11, Coralogix/VictoriaMetrics）: Service Mesh（Istio）+ Kiali 可观测性陷阱——「两个系统各报 0、加总变 2」：sidecar 与 Kiali 重复计数根源（重试/双面统计/采样不一致）与解法（规范化指标命名、统一采样边界、去重）；**运维价值=网格可观测性数据质量工程（防重/防漏/防漂移）是生产级 mesh 的隐性必修课**。https://www.cncf.io/blog/2026/08/11/a-practical-guide-to-solving-when-zerozerotwo-in-mesh-observability/
- **Good apps aren't born, they're guided: Building observable policy as code**（CNCF, 2026-08-12, VictoriaMetrics/Kyverno）: 「可观测的策略即代码」——把策略（Kyverno 类 admission policy）做成可观测对象：策略命中率、拒绝原因分布、策略变更对工作负载的影响度都作为指标暴露；**把「策略」从安全静态配置升级为「可度量、可调优的运行时行为」**，与 08-19 Kyverno 定位（见下）同主题双文。https://www.cncf.io/blog/2026/08/12/good-apps-arent-born-theyre-guided-building-observable-policy-as-code/
- **LitmusChaos Q1-Q2 2026 更新**（CNCF, 2026-08-06）: 混沌工程平台进展——社区/贡献者增长与实验库扩充，继续作为「在生产环境主动制造故障验证韧性」的标准工具；与 08-25 已收的 Flipkart 混沌工程案例同链：**2026 混沌工程从「演练」走向「常态化韧性验证」**。https://www.cncf.io/blog/2026/08/06/litmuschaos-q1-q2-2026-update-community-contributions-and-project-progress/

## 三、平台工程×AI：Agent 运维的「新岗位」与「新归属」

- **Microsoft Agent Lightning v1.0：平台工程师的新抓手**（The New Stack, 2026-08-26）: 微软发布 Agent Lightning v1.0——面向平台工程师的 agent 编排/harness 框架，把 agent 运行时（沙箱/工具权限/遥测/审批流）标准化为平台能力；**与 08-25 已收「harness engineering puts humans on the loop」同链：agent 时代平台工程=构建 harness 而非写死流程**，微软押注 agent harness 标准化。https://thenewstack.io/microsoft-agent-lightning-harness/
- **LLMOps and platform engineering: Who should own the AI pipeline?**（CNCF, 2026-08-13, Syntasso）: LLM 流水线（模型微调/评估/部署/监控）的归属之争——LLMOps 是 DevOps 的延伸还是平台工程的子集？作者论证：**模型生命周期的「平台化」（多团队共享的评估、灰度、回滚、成本治理设施）应归平台工程，业务侧 prompt/模型选择归业务团队**——「AI 流水线不是某个团队的专属，而是需要平台层提供共享原语」；呼应本库 08-13 已收的「CI/CD fails LLMs」：AI 交付需要新的 release gate 与平台抽象。https://www.cncf.io/blog/2026/08/13/llmops-and-platform-engineering-who-should-own-the-ai-pipeline/
- **Kyverno is a platform primitive, not a security tool**（CNCF, 2026-08-19, CNCF Ambassador）: Kyverno 的重新定位——多数企业把 Kyverno 划给安全团队预算，但作者论证它是「平台原语」：策略即代码承载的是平台治理（合规基线、资源规范、多租户边界），安全只是其中一类消费者；**运维视角=策略引擎应作为平台层能力建设（平台团队拥有），而非安全孤岛**，否则策略与工作负载演进脱节。https://www.cncf.io/blog/2026/08/19/kyverno-is-a-platform-primitive-not-a-security-tool/
- **Cloud Native platform sovereignty through multi-plane architecture**（CNCF, 2026-08-18, WSO2）: 云原生平台主权（sovereignty）的多平面架构——数据面/控制面/管理面分离 + 每个平面可独立选择「在本地 or 在云」的部署位置，实现「数据不出境但享受云原生能力」；**对政企/跨国企业=主权需求从「选 region」升级为「架构级可拆分」**，平台工程团队需要把合规边界设计进平面划分而非事后打补丁。https://www.cncf.io/blog/2026/08/18/cloud-native-platform-sovereignty-through-multi-plane-architecture/

## 六、今日小结

- **v1.36 的「另一半」是控制面运维韧性**：tech 组收的 v1.36 全是 AI 调度向（DRA/Pod-Level/PSI），本篇补齐运维向四件套——Sharded List/Watch（读路径水平扩展）、Staleness Mitigation（静默故障可观测）、Mixed Version Proxy（分阶段升级）、Checkpoint/Restore WG（快照恢复原语化）——**「AI 原生调度 + 控制面运维韧性」才是 v1.36/v1.37 完整拼图**，对万卡集群尤其关键。
- **可观测性 2026 转折点：数据治理 > 数据采集**。Omdia（59% 因成本终止部署）+ TNS 分析（AI 让遥测爆炸更糟）+ OTel 路线图（采样升级/Collector 网关化）三线合流：**观测栈的价值从「看得见」转向「花得值、留得住、查得清」**；agent trace 升格为应用数据后，保留策略/合规/成本归属成为平台工程的硬需求。
- **AI 流水线的「所有权」问题浮出水面**：LLMOps vs 平台工程（Syntasso）、Kyverno 重新定位（平台原语非安全工具）、Agent Lightning（harness 标准化）——**AI 时代的运维组织设计共识正在形成：共享治理原语归平台，业务决策归业务线**；CNCF 72 项目治理审查则给「依赖治理成熟度」提供了官方判据。
