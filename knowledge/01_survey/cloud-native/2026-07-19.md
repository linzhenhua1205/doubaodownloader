## 1️⃣ 🔴 DRA 深度实操指南 — 四个 GPU 分配场景全覆盖

**来源**: [CNCF Blog Jul 1 | 理解 K8s DRA](https://www.cncf.io/blog/2026/07/01/understanding-dynamic-resource-allocation-in-kubernetes/) · CNCF Ambassador ChengHao Yang
**状态**: 实操级长文，完整覆盖 DRA v1 GA 后的四个生产场景

### 核心内容：DRA 四场景实操 vs 传统 Device Plugin

| 场景 | 传统 Device Plugin | DRA 方案 | 关键差异 |
|:-----|:------------------|:---------|:---------|
| 🅰️ 两容器共享一 GPU | 需额外 hack | ResourceClaim + 两个容器同时引用 | 更简洁清晰 |
| 🅱️ 品牌优先+异构回退 | 不可能 | `firstAvailable` + CEL selector (`productName == "NVIDIA RTX A5000"` → 回退 T10) | **首创性能力** |
| 🅲 显存容量约束(>20Gi) | 需 nodeSelector/Affinity | `device.capacity["gpu.nvidia.com"].memory.isGreaterThan(quantity("20Gi"))` | **声明式精确控制** |
| 🅳 GPU Time Slicing | 静态配置 | DRA Config 声明 `strategy: TimeSlicing` + 4 Pod 共享单 GPU | 统一配置入口 |

### 关键技术细节

- **NVIDIA DRA Driver GPU v25.12.0** 已进 K8s SIGs, 文档去除 Beta 标签
- **DeviceClass**: `gpu.nvidia.com` / `mig.nvidia.com` / `vfio.gpu.nvidia.com`
- **ResourceSlice**: 每节点自动发现，128 device 上限后自动 split Pool, `pool.generation`+`resourceSliceCount` 保障调度器拿到完整视图
- **K8s v1.36+** device health reporting → Pod 不再是 Error，可区分设备故障 vs 应用故障
- **未来**: Cluster Autoscaler 可基于 GPU 短缺自动扩容节点

### 与 HAMi 的关系（参见 07-16 报告）

- **DRA**: 原生标准化资源分配，OS 层资源发现（本报告）
- **HAMi**: 实用主义 GPU 虚拟化中间件，多厂商兼容
- → **互补并存**，各自解决不同层级的问题

## 2️⃣ 🔴 Platform Engineering 2.0 — AI-Native 平台工程框架

**来源**: [CNCF Blog Jul 6 | Evolving platform engineering for AI-native workloads](https://www.cncf.io/blog/2026/07/06/evolving-platform-engineering-for-ai-native-workloads/) · VMware by Broadcom Pankaj Gupta

### Platform Engineering 1.0 → 2.0 演进

| 维度 | 1.0（当前） | 2.0（演进） | 运维影响 |
|:-----|:-----------|:-----------|:---------|
| **服务对象** | 开发者 | 开发者 + ML/DS + FinOps + 安全 + **AI Agent** | 平台需治理 Agent |
| **GPU 管理** | 手工/脚本 | 一等公民：GPU/TPU 分配 + 模型 serving + MCP Gateway | K8s DRA + vLLM 集成 |
| **FinOps** | 事后报表 | 预部署成本门禁 + 实时成本归因 | 预算管控前置 |
| **安全** | Shift-Left | 运行时下沉 + **Shadow AI 治理** | 模型投毒/推理泄露 |
| **架构** | 单体平台 | 模块化可组合 (CNCF 200+ 项目) | 灵活替换组件 |

### 五项核心原则

1. **AI-Native Platform**: GPU/TPU 一级支持, MCP 网关, Agentic Guardrails
2. **Multi-Persona**: 非人类消费者(AI Agent)的访问/作用域/治理
3. **Embedded FinOps**: 预部署成本门禁, 实时成本归因, 人人成本感知
4. **Security Shifts Down**: Shadow AI 治理, 提示注入防护, 推理审计
5. **Composable by Design**: API-first 可互换构件

## 3️⃣ 🟡 DRA+CEL Selector — GPU 精细化调度的可编程未来

**来源**: （同 DRA 实操指南）
**状态**: 与 HAMi/DRA 互补形成三条路线

DRA CEL 表达式支持的完整能力集：
- `.attributes["gpu.nvidia.com"].productName` — 按品牌/型号选
- `.capacity["gpu.nvidia.com"].memory.isGreaterThan(quantity("20Gi"))` — 按显存容量
- `.attributes["gpu.nvidia.com"].cudaComputeCapability` — 按 CUDA 算力
- `firstAvailable` — 有序优先级（首选→回退）
- `exactly` / `count` — 精确数量

> **信号**: CEL 选择器使 GPU 调度从「黑盒」走向「可编程」，DRA 的 GPU 场景价值远大于其他设备类型

## 4️⃣ 🟡 AI 工作负载主权部署框架

**来源**: [CNCF Blog Jul 10 | Where should AI workloads run? A sovereign and sensible approach](https://www.cncf.io/blog/2026/07/10/where-should-ai-workloads-run-a-sovereign-and-sensible-approach/) · KubeOps

### 五个主权要素

| 要素 | 含义 | AI 场景特别关注 |
|:-----|:-----|:-------------|
| **Operational Autonomy** | 全面控制运维 | AI 训练中断/恢复的自主控制 |
| **Compliance** | 法律确定性 | 训练数据的地域限制 |
| **Auditability** | 可验证安全 | 模型推理审计日志 |
| **Portability** | 避免锁定 | 模型+数据跨云迁移能力 |
| **Resilience** | 冗余+恢复 | 训练检查点/故障切换 |

### AI Readiness Check（部署前必做）
- 加速器容量 / 存储性能 / 数据 locality / 网络隔离 / 身份集成
- 监控 / 备份 / 恢复 / 软件供应链 / 漏洞管理 / 策略执行

> **信号**: "不要猜测完美目的地，但要避免建造死胡同" — 可移植性 + 可复现性 + 成本可见性

## 5️⃣ 🟡 Don't Wrap OpenTelemetry — OTel 採用的关键反模式

**来源**: [OTel Blog Jun 24 | Don't Wrap OpenTelemetry](https://opentelemetry.io/blog/2026/dont-wrap-opentelemetry/)
**状态**: 官方强烈建议

### 核心论点
- 团队常因"让事情更简单"而构建 OTel API 抽象层
- 但抽象层导致：丢失语义约定、破坏标准集成、增加维护债务
- OTel API 本身就是抽象层 — "在抽象之上加抽象没有意义"
- **例外**: 仅限跨语言 SDK 切换场景（但极少需要）
