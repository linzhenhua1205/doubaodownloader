## 🟢 三、AI × 云原生（K8s Infra for AI）

### 3.1 Cilium × Kubeflow — GPU 60% 空闲的根因

> **症状**：训练作业 Pod 全部 Running，健康检查全绿，但 GPU 利用率仅 ~40%，训练从未实际开始

**本质**：K8s 调度器**拓扑无关** ↔ CiliumNetworkPolicy **拓扑感知** → 协调者在 A 区，Worker 在 B 区，网络策略静默阻断

**三种表现形式**：

| 类型 | 表现 | 发现时间 |
|:-----|:-----|:--------:|
| 硬阻断 | 跨 Zone 网络策略直接拒绝 | 秒级 |
| 跨区延迟 | NCCL AllReduce 跨 AZ 支付 RTT，吞吐降 30-60% | 小时级 |
| 跨 AZ 成本 | 云账单上出现大量跨 AZ 数据传输费 | 天级 |

**修复**：无需改 Cilium 或 K8s — 仅需在 workload spec 增加：
- `nodeAffinity` → 绑定 GPU 专用 Zone
- `topologySpreadConstraints` → 协调者与 Worker 同 Zone
- `tolerations` → 协调者能调度到 GPU 节点

**效果**：GPU 利用率 **~40% → ~85%**

### 3.2 Goodput > Throughput — LLM 服务指标转型

> **核心论点**：Throughput（请求/秒）可以持续上升，但服务质量可能变差

**关键实验**（vLLM + Qwen2.5-7B on A10G）：

| 指标 | 含义 | 实验发现 |
|:-----|:-----|:---------|
| **Throughput** | 总请求/秒 | 可增长但掩盖问题 |
| **Goodput** | 满足 SLO 的请求/秒 | 真正应优化的指标 |
| **TTFT** | Time To First Token | 受 prefill 阶段控制 |
| **TPOT** | Time Per Output Token | 受 decode 阶段批量大小影响 |

**关键发现**：
- 相同 TTFT 下，不同配置的 **TPOT 可差 10 倍**（50ms vs 494ms）
- 推理负载不同（Chatbot/Reasoning/Agentic），最优配置不同
- **建议**：先用数据驱动搜索找到 best goodput 配置，而非手工猜测

### 3.3 Kubeflow v2 SDK — Spark + LLM Finetuning 一体化

- 原生 Spark Connect 支持：无需写基础设施配置即能在 K8s 上运行 Spark 作业
- LLM 微调蓝图内置

## 🔵 四、运维自动化关键实践

### 4.1 Scale-to-Zero 的真正敌人 — 健康检查唤醒 🆕

**KubeElasti ProbeResponse**：

| 问题 | Scale-to-zero 后负载均衡器持续健康检查 → 触发重新扩容 |
|:-----|:-------------------------------------------------------|
| **三种来源** | ① 云负载均衡器（ALB/GCP LB/Azure GW）② K8s Liveness/Readiness ③ 服务网格/可观测平台 |
| **解决方案** | 在 Resolver 层设置 ProbeResponse 规则：匹配到健康检查请求时直接回复 200，不触发扩容 |
| **配置示例** | `method: GET, path: /healthz → response: 200` |
| **架构优势** | 仅在 Proxy 模式生效，服务运行时零开销；仅拦截合成流量，真实请求正常唤醒 |
| **最大受益** | GPU 负载 / 授权软件 / 内部服务 / 东西向流量 |

### 4.2 Linkerd 多集群联邦 — 三种模式共存实战 🆕

**三模式对比**：

| 模式 | Label | 网络要求 | 行为 | 适用场景 |
|:-----|:------|:---------|:-----|:---------|
| **Gateway (层级)** | `exported=true` | Gateway IP 可达 | 服务镜像为 `<svc>-<cluster>`，经 Gatway 路由 | 无扁平网络 |
| **Flat (点对点)** | `exported=remote-discovery` | Pod IP 可路由 | 服务镜像为 `<svc>-<cluster>`，直连远端 Pod | 需要客户端指定后端 |
| **Federated** | `federated=member` | Pod IP 可路由 | 所有同名服务合并为 `<svc>-federated`，跨集群 LB | 自动故障转移 |

**实战验证**（3 个 GKE 集群 × 3 个 Demo Service）：
- 全量集群故障模拟：Federated 服务自动重平衡（33% → 50/50），**零错误**
- Gateway/Flat 镜像服务：目标集群宕机后 503/502 正确返回
- 三种模式在同一组集群 + 同一组链接上**共存**

**生产建议**：
- Federation 作为默认（自动故障转移）
- Mirror 用于需要客户端感知集群的场景（数据本地性）

### 4.3 平台工程演进 — Agentic Enterprise 🆕

**WSO2 OpenChoreo**（CNCF Sandbox）展示的下一代 IDP：

| 演进维度 | 传统 IDP | 下一代 IDP |
|:---------|:---------|:-----------|
| **消费者** | 人类开发者 | 人类 + AI Agent |
| **管理对象** | Applications | Applications + Resources + AI Agents |
| **核心能力** | 部署自动化 | 上下文感知 + 关系治理 |
| **接口** | Portal / CLI | Portal / CLI / MCP Server |

**关键洞察**：
- AI Agent 成为平台**第一类消费者**，需独立身份 + 范围化权限 + 审计轨迹
- **Context 成为平台核心能力**：连接 Applications × Resources × AI Agents 的依赖关系
- 可复用 Skills + 内置 Agents（SRE/Security/FinOps）共享同一上下文模型
