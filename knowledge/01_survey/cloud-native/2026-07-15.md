### 1. 「Agent 不是 Pod」— kagent agent-substrate 架构深度解析

> 📄 CNCF Blog, Jul 14 · Lin Sun (Solo.io, CNCF Ambassador)

**核心命题：Pod 是 AI Agent 正确的部署单元吗？**

kagent 团队从「1 Agent = 1 Pod」出发，逐步发现了根本性问题：

**Agent 与微服务的本质差异：**
| 维度 | 传统微服务 | AI Agent |
|:-----|:----------|:---------|
| 可用性 | 持续在线 | **按需唤醒**，执行秒/分钟即 idle |
| 生命周期 | 天/月 | 秒/分钟 |
| 并行性 | 固定副本数 | 动态创建子 Agent 并行任务 |
| 身份 | Pod IP绑定 | 独立于执行环境的逻辑身份 |
| 状态 | 连接态 | 执行—暂停—恢复（等待人工审批） |

**Agent-substrate 的解法：三层抽象**

```
WorkerPool (≈ NodePool) -> Workers (≈ Nodes) -> Actors (≈ 逻辑 Agent)
                                        v
                              Kubernetes Pods (执行载体)
```

- **WorkerPool**: 定义执行 Worker 的集合，如 3 副本部署
- **Worker**: 映射到唯一一个 K8s Pod，长期运行
- **Actor**: 逻辑实体（**非 K8s CRD**），轻量，可按需 suspend/resume 在 Worker 上

**关键架构决策：**
- 6 个 Actor 可共享 1 个 Worker Pod（而非 6 Pod）
- **gVisor sandbox** 为每个 Actor 提供独立隔离（runsc 配置在 ActorTemplate 中定义）
- Actor 无状态化：STATUS_SUSPENDED 状态，无 Worker 时仅存元数据
- Actor 由 agent-substrate 控制面管理，K8s 只看到 WorkerPods

**遗留问题（正在探索）：**
- **Agent Identity**: 不绑定 Pod，应绑定 ActorTemplate × namespace × tenant × version
- **Security/Policy**: 应该在 ActorTemplate 级别表达，而非 Pod/ServiceAccount
- **Multi-tenancy**: Actor 的归属/配额/计费/生命周期管理
- **Observability**: Actor 在多个 Worker 间迁移时，trace/log 需跟随逻辑 Agent

> **Impact**: ⭐⭐⭐⭐⭐ — 对 AI Agent 在 K8s 上的部署模型提出了根本性挑战。**Agent 无状态化 + 共享 Worker Pool** = 比 1 Pod/Agent 高效数倍。结合 agent-sandbox（安全沙箱）和 agent-substrate（效率调度）形成完整方案。对我们设计 AI 集群 Agent 部署架构有直接的架构参考价值

### 2. OTel Spring Boot 声明式配置 — 从 env var 到 application.yaml

> 📄 OTel Blog, Jul 14 · The Voyage of a Small Environment Variable

**背景**：OTel Spring Boot Starter v2.26.0 起支持声明式配置（YAML schema），嵌入 application.yaml

**演进路径**：
1. 早期：`OTEL_SERVICE_NAME=my-service` 环境变量
2. 当前：Java Agent + application.yaml 声明式配置，与 Spring Boot 配置层级自然融合
3. 意义：降低 OTel 接入心智负担，开发者无需理解 OTel SDK 配置细节

**技术要点**：
- 与 Java Agent 自 2025 年末引入的 YAML schema 保持一致
- 通过 Spring Boot 的 `application.yaml` 集中管理 OTel 配置
- 对 Spring Boot 微服务可观测性标准化有积极推动作用

### 4. CNCF Data Storage in Cloud Native AI 白皮书发布

> 📄 CNCF Blog, Jul 8 · TAG Infrastructure

**三阶段 AI 存储模型：**

| 阶段 | 数据特征 | 存储需求 | 推荐技术 |
|:-----|:---------|:---------|:---------|
| **训练** | PB级数据集，高吞吐顺序读 | 并行文件系统，数据缓存 | Fluid + JuiceFS |
| **推理** | KB级请求，低延迟随机读 | 高性能缓存，模型分片 | CSI + 本地SSD |
| **Agentic AI** | 多轮上下文，KV Cache 动态 | 近存缓存，跨节点共享 | CMX/CDK |

**技术支柱**：Fluid（数据编排） + CSI（容器存储接口） + CDK（缓存分发）
