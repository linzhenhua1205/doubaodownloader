## 一、🔴 GPU 共享生态：DRA 与 HAMi 的"合流"（CNCF 8/7 全文深潜）⭐ 主线

- **核心命题：DRA 是否取代 HAMi？——短答"否"，完整答"取决于 HAMi 的哪一半工作"（08-07, Mesut Oezdil, HAMi 贡献者）**: 传统 device plugin API 只会"数数"（`nvidia.com/gpu: 1` = 一整张卡，要么全要要么不要）。HAMi（**7/15/2026 成为 CNCF Incubating 项目**）用 extended resources + mutating webhook + scheduler extender + annotation 绕过了这个窄 API，表达"给这个 pod 8,000 MiB 显存 + 10% 算力，且限额必须生效"。**DRA 吸收的是"编码分数请求、让调度器看得见"这一半；"容器内 CUDA 调用粒度强制"另一半 DRA 从未被设计去做**。HAMi 的回应是拆分：保留强制（HAMi-core），把编码重建在 DRA 之上（跨 3 个仓库）。
>  https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

- **DRA 演进时间线（做规划的关键）**: 核心 DRA **v1.34 GA、v1.35 起默认启用**；扩展特性各自毕业——prioritized device lists（先要大卡、回退两张小卡）v1.36 stable，**partitionable devices + consumable capacity（可消耗容量）v1.36 仍为 beta 未 stable**。Consumable capacity 才是映射到 HAMi 模型的那块：驱动可标记 `allowMultipleAllocations`（不同 namespace 的独立 claim 可同时落同一设备），claim 可携带 capacity request（按名数量请求，而非整卡）。调度器从此为 GPU 显存做**记账**（bookkeeping）——像为节点内存做的那样，保证授予容量总和不超过设备公告值。
>  https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

- **强制层：DRA 管不到的"运行时肌肉"（HAMi-core, libvgpu.so）**: DRA（含 consumable capacity）本质是**承诺跟踪器**——保证调度器不超额承诺，但不管容器在运行时违约（CUDA 不认 ResourceClaim，一个贪婪的 `cudaMalloc()` 循环会吃掉邻居的显存）。HAMi-core 是预加载进容器的 C 库，拦截 CUDA/NVML 调用并在用户空间施加限额：**2 个 pod 各授权 8,000 MiB，其中一个故意超限分配，会在精确的 8,000 MiB 边界拿到 CUDA OOM，邻居不受影响**——按容器隔离的配额，正是多团队共享集群需要的。诚实的上限：这是库拦截的软件强制，可被绕过（静态链接驱动/CUDA_DISABLE_CONTROL/容器套容器）；对抗性多租户需要硬件分区（MIG，HAMi 也能动态调度 MIG），合作团队共享则拦截粒度胜出（1 MiB/1% 步进 vs MIG 固定 profile）。
>  https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

- **HAMi 的 DRA 三仓库布局（每仓库解决不同运维问题）**: ① **k8s-dra-driver**——首个支持 consumable capacity 的 NVIDIA 开源 DRA 驱动，发布 GPU 显存/算力为 ResourceSlices、跑 kubelet 插件、经 CDI 接线容器并挂上 HAMi-core 强制；② **HAMi-DRA**——mutating admission webhook，把存量 `nvidia.com/gpu` 清单在准入时改写成等价 ResourceClaim，**无需改任何 manifest**，资源名可配置，v2.9 起生产就绪（v0.2.1）；③ **HAMi-core**——强制层不变。**深层收益：HAMi-DRA 不注入自己的 scheduler extender，因此能无补丁地落进 Volcano / KAI Scheduler 等任何 DRA-aware 调度器**——DRA 把"请求是对象"这一点标准化，HAMi 不再需要改上游。
>  https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

- **代价与边界（诚实清单）**: HAMi-DRA 不带自己的调度器 → **做不了拓扑感知放置**（如 NVLink 相连的 GPU 对，请求 2 卡应优先高速互联对，webhook 只能给调度器一个数量+容量，无法表达拓扑约束）——带宽敏感负载要么留在建模拓扑的调度器上，要么接受带宽盲放置。**硬约束：DRA 模式与传统 device-plugin 模式绝不能在同一集群并存**（两套记账者各自认为独占同一块 VRAM，互不可见）。前置门槛：K8s v1.34+ 且 v1.34/1.35 需手动开 `DRAConsumableCapacity` feature gate（托管集群若不暴露 API server flags 则被卡住，**v1.36 默认开启悄然移除了最大采用障碍**）+ CDI 能力运行时 + 对应硅片的 DRA 驱动。
>  https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

- **选型决策树（2026 年中，作者作为传统模式运维者的判断）**: 托管 K8s 无 feature-gate 访问或版本 <v1.34 → **传统模式**（16 个 release、DaoCloud 10,000+ GPU/10+ DC 生产验证、独立案例 3x 利用率提升）；混合厂商加速器机群 → **传统模式**（HAMi 传统模式覆盖 12+ 设备家族：寒武纪/沐曦/天数/摩尔线程/昆仑芯/AWS Neuron 等，DRA 驱动面最小，是 HAMi 最宽的护城河）；NVIDIA 集群 + v1.34+ 可控控制面、或 v1.36 → **立即在 staging 起 DRA 模式**，先挂 HAMi-DRA webhook 让 manifest 零改动，用 `kubectl get resourceclaim` 观察真实负载后定生产时间线。**三处诚实保留**：consumable capacity 未 stable、k8s-dra-driver 的 Helm chart 仍标 WIP、DRA 侧厂商覆盖是传统模式的零头。**方向已定：HAMi 2026 roadmap 把"完整 DRA 标准适配"列为目标——请求、调度、强制第一次讲同一种语言（ResourceClaim 取代私有 annotation 方言）**。
>  https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/

## 二、🟠 供应链安全：npm 来源证明被"伪装化" + Shadow AI 威胁建模（8/7 双源）

- **npm 供应链攻击：>400 个包受影响，provenance attestations（来源证明）被攻击者用作伪装（08-07, Amanda Caswell）**: 安全研究者本周披露的 npm 供应链攻击波及 400+ 包，含 Keyv 相关项目。**核心杀伤力：本意是供应链信任机制的 provenance attestations（SLSA 来源证明）被攻击者反向利用为"伪装"——攻击者让自己的恶意包"看起来有来源证明"，安全信号本身被武器化**。与 08-05 记忆库"伪装深度分析"（信号经济学：伪装者利用接收方对信号的信赖）直接互证；对运维启示：**供应链信任层不能只验证"有没有证明"，还要验证"证明的签发链与内容是否自洽"**（与 08-07 记忆库"约束验证/链路审计"同逻辑）。
>  https://thenewstack.io/npm-supply-chain-worm-attack/

- **Shadow AI in CI/CD：从开发者笔记本到 K8s 的威胁建模（08-07, Matteo Bisi, ReeVo SpA）**: 定义 Shadow AI = **任何在成为安全架构一部分之前就被日常使用的 AI 工具/模型/agent/扩展/集成**——AI 正在成为软件交付的日常部分，往往先于安全架构。文章对"开发者笔记本上的 AI 工具 → CI/CD 管道 → K8s 集群"全路径做威胁建模。**对平台团队：AI 工具链（含自建 coding agent/IDE 扩展）是新的影子 IT 面，需要纳入资产清单与准入控制**——与 08-04 记忆库"Agent 安全周更化（Rogue agents 创建假身份）"同一威胁面。
>  https://www.cncf.io/blog/2026/08/07/shadow-ai-in-ci-cd-threat-modeling-the-path-from-developer-laptop-to-kubernetes/

## 三、🟡 AI 运维与平台工程（TNS 8/7）

- **"AI kill switch" 的前提谬误：假设你知道你在关掉什么（08-07, Robin Tatam）**: "AI kill switch"进入公共对话是因为它给了复杂恐惧一个简单表达——但**从基础设施视角它站不住：你未必知道 agent 实例在哪里运行、状态存在哪、依赖哪些外部服务**。没有运行时清单（哪个 agent 跑在哪个集群/容器、持有哪些凭证、正在调用什么），"一键关停"无从谈起。**运维含义：kill switch 的前提是"可观测 + 可定位"——先有运行时资产清单与依赖图，才谈得上紧急关停**（与 08-05 记忆库"带内+带外双轨遥测"、Agent 可观测性三支柱直接相关）。
>  https://thenewstack.io/ai-kill-switch-infrastructure/

- **Coinbase / Shopify / Ramp 各自自建 coding agent，三家仍付费 Anthropic（08-07, Janakiram MSV）**: 企业工程团队在 AI 辅助开发上收敛到共同架构：**自建 agent 编排/harness 层（对齐自家代码库与规范），但底层模型仍外购（Anthropic）**——"工具自建、模型外购"的分层成为企业默认。**与 08-06 记忆库"编程 Agent 差异化在 Harness 深度"一致：模型商品化后，企业护城河在 harness/上下文工程而非模型本身**。
>  https://thenewstack.io/enterprise-ai-agent-harness/

- **OpenAI 放缓 Astra：内部测试显示模型可能越过"无 AI 达到过"的网络安全线（08-07, Amanda Caswell）**: OpenAI 因内部测试暗示 Astra 可能触及网络安全红线而放缓发布——**与 08-07 记忆库"UK AISI 第三方评估 GPT-5.6/Claude Mythos 5 有害行为"、Agent 安全周更化同一叙事：前沿模型安全评估正在从"事后发现"走向"发布前拦截"**；对 Infra 决策者，模型能力边界的不确定性意味着基础设施层仍须假设"模型可能被滥用"来设计护栏。
>  https://thenewstack.io/openai-astra-cybersecurity-delay/

## 📊 本期观察

- **GPU 共享进入"原生化"拐点**: DRA consumable capacity 在 v1.36 默认开启，是"K8s 原生支持 GPU 分片"的实质落地——昨日（08-07）TNS 讲 DRA 概念，今日 CNCF 给出 HAMi 视角的完整技术对照（请求/调度/强制三层分离）。**对超节点/智算平台：GPU 虚拟化选型从"私有方言生态"（HAMi 传统模式、各厂商独立 annotation）走向"标准 API + 强制层组合"**；多厂商混合集群短期仍依赖 HAMi 传统模式（12+ 设备家族护城河），NVIDIA 单栈 + v1.36 可先行 DRA。三点现实约束（consumable capacity 未 stable / 拓扑感知缺失 / 双模式不可并存）决定迁移节奏要稳。
- **供应链信任机制进入"攻防螺旋"**: npm 来源证明被伪装化，是继 08-04"npm provenance 取证攻击"后供应链安全的最新升级——**信任机制本身成为攻击面，验证逻辑必须"证明可信 ≠ 内容可信"**；配合 Shadow AI 威胁建模（AI 工具先于安全架构进入交付链），运维侧需要把"AI 工具链"纳入供应链治理范围。
- **AI 运维的"关停权"前提是可观测性**: kill switch 讨论揭示 AI 运维的深层缺口——不知道 agent 在哪、状态在哪，就无法执行任何"关停"语义；这与 Agent 可观测性三支柱（traces/costs/audit）、运行时资产清单形成闭环：**先可观测，才可关停**。
- **企业 AI 开发架构收敛为"自建 harness + 外购模型"**: Coinbase/Shopify/Ramp 三案例与 08-06 记忆库"编程 Agent 差异化在 Harness 深度"互证——模型层商品化加速，企业投入重心转向 harness/上下文工程，对平台团队是"做工具链资产"的信号。
