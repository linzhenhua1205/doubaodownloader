### 2. K8s 原生 Agent 部署模式讨论 — 「Pod 不是 Agent 的正确答案」

> 📄 CNCF Blog, Jul 14 · Lin Sun (Solo.io, CNCF Ambassador)

**kagent 架构反思**：将每个 Agent 运行在独立 Pod/Service/ServiceAccount 中 → 过于重型。

**结论**：Agent 应作为轻量级运行时内部执行单元，而非独立 K8s 资源。

**架构对比**：

| 维度 | 每个 Agent = Pod | Agent → kagent Runtime |
|:-----|:----------------|:-----------------------|
| 启动开销 | 完整 Pod 启动（秒级） | 运行时内执行（毫秒级） |
| 资源密度 | 低（Pod 级隔离冗余） | 高（共享运行时） |
| 可观测性 | Pod 级 Metrics/Logs | Agent 级粒度的 OTel 插装 |
| 安全隔离 | Pod 级网络策略 | Runtime 级沙箱隔离 |
| 更新/回滚 | 重建 Pod | Runtime 热更新 |

**信号**：AI Agent 在 K8s 上的部署架构仍在快速迭代中，kagent 的 "Agent-as-substrate" 模式值得关注。与 HAMi 的 GPU 虚拟化一起，构成 **Agent 运行时基础设施的轻量化趋势**

### 3. OTel Go 编译期插装 v1.0 正式发布

> 📄 OTel Blog, Jul 16

**痛点**：Java/Python/Node.js/.NET 均支持无代码 Agent 插装，Go 因编译为二进制一直是例外。

**方案**：编译期插装（Compile-Time Instrumentation）— 在 Go 编译时通过代码生成注入 OTel 调用，不修改源代码。

**关键能力**：
| 能力 | 说明 |
|:-----|:------|
| 零运行时代理 | 编译时注入，运行时无额外 Agent 进程 |
| 自动 trace | 自动追踪 HTTP/gRPC 调用 |
| 适用版本 | Go 1.24+ |
| 成熟度 | v1.0 正式版（此前 Beta） |

**Impact**: Go 是 K8s/NVIDIA 驱动/Dragonfly/etcd 等基础设施核心语言。编译期插装 v1.0 = **Go 生态终于获得与 Java Agent 对等的自动插装能力**。对 AI 集群中 Go 编写的组件（NVIDIA device plugin、CNI、CSI driver 等）的可观测性增强有直接价值

### 5. etcd v3.7.0 发布 — RangeStream 长请求里程碑

> 📄 K8s Blog, Jul 8 · SIG Etcd

**对 AI 集群的关联**：
- etcd 作为 K8s 控制面存储，RangeStream 改善大规模集群的 watch/list 性能
- 对万卡 AI 集群控制面可扩展性有间接正向影响
