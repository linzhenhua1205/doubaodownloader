## 1️⃣ 🔴 Confidential Containers → CNCF Incubating — 数据在使用中的保护标准化

**来源**: [CNCF Blog Jul 22 | Confidential Containers becomes a CNCF incubating project](https://www.cncf.io/blog/2026/07/22/confidential-containers-becomes-a-cncf-incubating-project/) · CNCF Staff
**状态**: CNCF TOC 投票通过，从 Sandbox 晋升 Incubating

### 项目定位与价值

| 维度 | 说明 |
|:-----|:------|
| **要解决的问题** | 云原生环境中**数据在使用中（data-in-use）的保护**——加密存储→加密传输→但运行时数据明文暴露给宿主机 |
| **技术路线** | 基于硬件 TEE（Trusted Execution Environment）的容器运行时保护：**TDX（Intel）· SEV-SNP（AMD）· TEE（ARM）** |
| **核心组件** | CoCo Operator（自动化 Operator） + KBS（密钥代理服务） + 各类 TEE 的 K8s 集成层 |
| **架构模式** | 加密容器镜像 → TEE 内解密运行 → 宿主机不可见内部内存/数据 |

### 与已有项目的差异

| 对比项 | Confidential Containers | 传统容器安全 | Kata Containers |
|:-------|:----------------------|:-------------|:---------------|
| **保护目标** | 运行时内存保护 | 进程隔离 | 虚拟机级隔离 |
| **硬件依赖** | 必须 TEE CPU | 无 | 轻量级 VM |
| **攻击面** | 防宿主机 Root/BIOS 级攻击 | 防容器逃逸 | 防容器逃逸 |
| **密钥管理** | KBS 中心化 | 无 | 无 |
| **性能损耗** | TEE 切换开销（~3-8%） | ~0% | VM 启动开销 |

### 生态现状

- 主要贡献者：Intel、AMD、IBM、Microsoft、Red Hat、SUSE
- 硬件支持：Intel TDX（Xeon 5/6 代）· AMD SEV-SNP（EPYC Genoa+）· ARM CCA
- 实测场景：金融/医疗/联邦学习的敏感数据保护、**多租户 GPU 集群中防止租户间互窥**
- **对 AI 集群的价值**：多租户 GPU 训练中，TEE 保障用户代码和数据不被其他租户/管理员看到

### 对我方价值
- **超节点多租户场景**：GPU 训练数据保护可用 CoCo + TDX/SEV-SNP
- 与 HAMi（GPU 隔离虚拟化）互补：HAMi 做资源隔离，CoCo 做内存/数据保护

## 2️⃣ 🟡 Kyverno 生产模拟测试 — 让策略引擎以为自己「在生产中」

**来源**: [CNCF Blog Jul 22 | I made a policy engine think it was in production](https://www.cncf.io/blog/2026/07/22/i-made-a-policy-engine-think-it-was-in-production/) · Sargam Puram (Kyverno Maintainer)
**状态**: Kyverno 策略测试方法论，有实战价值

### 核心问题

- Kyverno 策略引擎在生产中 mutate/validate/generate 资源，一旦策略有 bug → 直接影响生产负载
- 开发者面临的两难：完全脱离集群测试（策略真实行为无法验证） vs 直接压生产（高损风险）
- **需要一种方式，让 K8s 策略引擎以为自己在生产中，但实际不产生副作用**

### 实现方法：Kyverno 的测试框架

| 组件 | 用途 |
|:-----|:------|
| **Kyverno CLI test** | 本地运行 YAML 策略测试（轻量级单元测试） |
| **`kyverno-test.yaml`** | 定义测试用例：输入资源 + 期望策略行为（pass/fail/skip） |
| **静默集群（Silent Cluster）** | 复刻生产集群资源（不含业务流量），运行策略但不产生实际 mutation |
| **审计模式（Audit Mode）** | 策略以 `background: true` + `validationFailureAction: Audit` 部署，仅报告不阻断 |

### 关键实践

| 维度 | 做法 |
|:-----|:------|
| **CI 集成** | 每个策略 PR 触发 `kyverno test` 自动跑所有已有测试用例 |
| **生产回放** | 从生产集群导出真实资源（不含敏感数据），加载到测试集群跑 Audit 模式 |
| **突变预览** | Kyverno `generate` 策略产生的变更在 dry-run 模式预览，人工审核后再部署 |
| **覆盖率** | 每条策略至少覆盖：正常 pass 用例 + 预期 fail 用例 + 边界条件 |

### 对我方价值
- 超节点集群安全策略（SBOM 准入/镜像签名/GitOps compliance）可采用 Kyverno 测试框架
- 运维 Agent 自动生成策略测试用例：Agent 提策略 → CI 自动跑测试 → 审计模式验证 → 人工审核上线

## 3️⃣ 🟡 Multi-Cluster 数据库在 K8s 上的架构模式

**来源**: [CNCF Blog Jul 22 | Multi-Cluster databases on Kubernetes: Architecture and deployment](https://www.cncf.io/blog/2026/07/22/multi-cluster-databases-on-kubernetes-architecture-and-deployment/) · Edith Puclla & Ivan Groenewold (Percona)
**状态**: 跨集群数据库架构设计指南，与 CNCF TAG Infrastructure 发布的 Data Storage White Paper（Jul 8）呼应

### 核心挑战

| 问题 | 说明 |
|:-----|:------|
| **跨集群数据同步** | 数据库在 K8s 上运行已成熟，但跨集群（区域故障/控制面损坏/网络割接）仍无标准答案 |
| **故障隔离** | 一个集群的控制面损坏不应影响数据库可用性 |
| **网络延迟** | 跨集群同步的延迟与带宽瓶颈 |
| **一致性与可用性权衡** | 跨数据中心场景的 CAP 选择 |

### 架构模式

- **Active-Passive**：主集群读写，备集群只读备份。主故障时切换。简单但切换时间~分钟级
- **Active-Active**：多集群写。复杂（冲突解决）但 RTO ~0
- **完全独立+应用层路由**：每个集群独立数据库，应用层做读写分离/路由。最灵活但应用复杂度高

### 关键组件
- **Percona Operator for MongoDB** 作为实战案例，支持跨 K8s 集群的复制集
- **Kuberhealthy + Prometheus** 做跨集群健康检查
- **服务网格（Istio/Linkerd）** 处理跨集群流量管理

### 对我方价值
- 超节点的**集群间数据同步**（BMC 资产/监控/training checkpoint）可参考这些模式
- Active-Passive + K8s Operator 是最可行的起点
