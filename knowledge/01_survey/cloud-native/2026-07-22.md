## 1️⃣ 🔴 平台工程进入 "Agent 企业" 时代 — Applications + Resources + AI Agents 三位一体

**来源**: [CNCF Blog Jul 21 | Platform engineering for the agentic enterprise](https://www.cncf.io/blog/2026/07/21/platform-engineering-for-the-agentic-enterprise-managing-applications-resources-and-ai-agents/) · Lakmal Warusawithana (WSO2)
**状态**: 平台工程演进的纲领性文章，提出 Agent 时代的平台架构框架

### 核心论点：平台工程的三次跃迁

| 阶段 | 重心 | 消费者 | 管理对象 |
|:-----|:-----|:-------|:---------|
| **1.0 基础设施抽象** | 简化 IaC/CI/CD | 人类开发者 | 基础设施 |
| **2.0 IDP（当前）** | 黄金路径/自服务/治理 | 人类开发者+SRE | 应用（Application） |
| **3.0 Agent 企业**（目标） | 上下文驱动/多角色/AI协作 | 人类 + AI Agents | **Application + Resource + AI Agent** |

### 关键变革点

| 维度 | 旧模式 | Agent 时代 |
|:-----|:-------|:-----------|
| **平台消费者** | 仅人类开发者在 portal/CLI 操作 | 人类 + AI Agent 通过 MCP/API/Portal 并存 |
| **管理对象** | 应用是唯一一等公民 | **应用、资源、AI Agent** 三个一等公民 |
| **资源模型** | 数据库/消息/存储视为基础设施 | 资源有独立生命周期、所有权、治理、安全策略 |
| **上下文的角色** | 从可观测性平台获取（事后） | **上下文成为一等平台能力**（实时共享模型） |
| **接口** | Portal/CLI/GitOps | 增加 MCP Server，AI Agent 通过 MCP 访问同一模型 |

### 三个一等公民的关系

```
Applications --消费-->  Resources (DB/消息/存储/API/模型/Secret)
     |                      |
     |                      |
     v                      v
 AI Agents ----消费/管理--> Both
```

- **Applications**：实现业务逻辑的核心软件制品
- **Resources**：数据库/消息队列/对象存储/AI模型/Secret/SaaS等 → 从 "基础设施依赖" 提升为 "一等平台对象"
- **AI Agents**：推理上下文、调用工具、协作人类 → 像人类工程师一样与 Applications 和 Resources 交互

### OpenChoreo — 实际落地方案
- **状态**: CNCF Sandbox 项目
- 核心设计：在 K8s 基础上提供 Applications + Resources + AI Agents 的统一平台模型
- AI Agent 通过 MCP Server 接入，人类通过 Portal/CLI/GitOps 接入
- **可扩展架构**：通过 ecosystem 模块扩展，不修改核心
- 内置能力：Agent Manager、AI Gateway、沙箱、策略执行、评估框架

### 对我方的价值
- **资源作为一等公民** → 超节点中的 BMC/GPU/存储网络/供电散热等模块可映射为 platform Resources
- **MCP Server 接入模式** → 运维 Agent 的标准对外接口
- **Context 作为一等能力** → 与知识库愿景高度一致（平台即上下文）

## 2️⃣ 🟡 Agent 中 Knowledge Base 工具的真实价值 — 1,192 次对话分析

**来源**: [CNCF Blog Jul 21 | Why your agent needs access to your documentation](https://www.cncf.io/blog/2026/07/21/why-your-agent-needs-access-to-your-documentation/) · Finn Bauer (kapa.ai)
**状态**: 有量化数据的 Agent 工具使用模式分析

### 核心发现：文档搜索是最被低估的 Agent 工具

| 发现 | 占比 | 说明 |
|:-----|:----:|:------|
| **#1 文档作为 fallback** | 32.1% | Agent 原生工具无法回答时，文档搜索兜底 |
| **#2 文档提供上下文** | ~7% | 原生工具回答 "是什么"，文档回答 "为什么"和"意味着什么" |
| **#3 文档帮助 Agent 使用工具本身** | 最有趣 | Agent 不确定用什么原生工具时，先查文档再决策 → 文档在做**规划工作** |

### 关键数据
- Agent 有 **30 个原生工具**（search_conversations, display_chart 等），仅 **1 个** `search_knowledge_base` 工具
- `search_knowledge_base` 的使用量 **几乎等于所有原生工具之和**
- Agent 查文档不是为了回答用户，而是为了**弄明白自己该做什么**

### 示例：用户问 "找负面情绪的对话"
- 原生工具 → 产品没有 sentiment filter，无法回答
- Agent 查文档 → 发现负面信号由 downvotes 和 feedback comments 捕获
- 调用正确的原生工具 + 过滤参数 → 给出答案
- **文档不是在回答问题，而是在做 Agent 的 briefing**

### 对云原生社区的延伸
- K8s/Prometheus/Envoy/Argo/OTel 等项目的文档庞大且快速变化
- 为这些项目构建 Agent 时，**文档搜索是最关键的工具**
- 对知识库建设的反向要求：高结构化的 FAQ/code examples/API ref 对 Agent 能力提升最显著
