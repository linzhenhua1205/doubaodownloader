### 2. Self-Hosting LLM on K8s with vLLM — 实战指南

> 📄 CNCF Blog, Jul 16 · Matt Kereczman (LINBIT)

**要点**：
- LINBIT 发布 **vLLM on Kubernetes 完整部署指南**
- vLLM = 高性能推理引擎（PagedAttention + 连续批处理 + Tensor Parallel）
- K8s 部署的关键考量：GPU 分配（NVIDIA Device Plugin / DRA）、持久卷（模型存储）、HPA（推理负载自动扩缩）

**技术架构**：
```
用户请求 -> K8s Service -> vLLM Pod(s) [GPU] -> Model (PV/NFS)
                           ^
                   ConfigMap (模型参数、采样配置)
```

**运维要点**：
- GPU 共享与隔离：单节点多模型部署时需避免显存争用
- 模型版本管理：PV 挂载 vs 初始容器下载（首次启动延迟权衡）
- 推理冷却：低负载时自动缩容至 0（需 GPU 感知的 HPA）

### 3. 构建自定义 Metrics Exporter — K8s 可观测性扩展

> 📄 K8s Blog, Jul 14 · Victor David Effiok

**核心观点**：
- K8s 内置 CPU/内存指标不足覆盖真实扩缩容决策
- 需要自定义指标：**队列深度/批处理耗时/每秒请求延迟分位数/GPU 利用率/模型推理延迟**
- 提供从零构建 Custom Metrics Exporter 的分步教程（Prometheus HTTP handler → 注册 metrics → ServiceMonitor CRD）

**技术要点**：

| 组件 | 作用 |
|:-----|:------|
| Prometheus Client (Go/Python) | 暴露 `/metrics` 端点 |
| ServiceMonitor/PodMonitor | Prometheus Operator CRD，自动发现 |
| HPA with custom/external metrics | 基于业务指标扩缩容器 |
| KEDA ScaledObject | 事件驱动扩缩（队列长度、消息积压） |

**关联性**：配合 **KEDA（CNCF Incubating）** 可完全替代内置 HPA，支持 50+ 事件源

### 4. Operating OpenTelemetry at Scale with OpAMP

> 📄 CNCF Blog, Jul 13 · Dotan Horovits (CNCF Ambassador)

**OpAMP (Open Agent Management Protocol)** — OTel Collector 集群管理标准：

**关键挑战**：
- 大规模 OTel 部署：多 Collector 实例在异构环境下的一致性管理
- 配置更新：不停机热更新 Collector pipeline
- 健康监控：Collector 的内存/CPU/吞吐量远程可见

**OpAMP 核心能力**：

| 能力 | 说明 |
|:-----|:------|
| 远程配置管理 | 集中下发 OTel Collector 配置（接收器/处理器/导出器） |
| 健康报告 | Collector 定期上报自身状态（内存、CPU、吞吐量） |
| 远程控制 | 重启、升级 Collector 无需 SSH |
| 包管理 | Collector 插件热安装/更新 |

**对 AI 集群的价值**：大规模集群中 OTel Collector 作为可观测性数据管道的第一跳，集中管理避免配置漂移 + 监控 Collector 自身健康
