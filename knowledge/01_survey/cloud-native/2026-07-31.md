## 🟡 三、Kubernetes 生态深度内容

### 3.1 🆕 Controller-runtime Cache 原理（7/29 K8s Blog）

**核心论点**：`controller-runtime` 的 Cache 层使得每个控制器持有一个**本地化的 API 对象缓存**，这是控制器不会压垮 API Server 的根本原因。

| 机制 | 说明 |
|:-----|:------|
| **Informer-based** | 每个 GVK 对应一个 sharedInformer，监听 watch events |
| **Transform 函数** | 可在缓存层做字段剥离/脱敏，减少内存 |
| **Index 机制** | 自定义索引字段，提升 List 效率 |
| **Cache 复用** | 同一 Manager 的所有 Controller 共享 Cache |
| **与 API Server 的解耦** | 读走缓存，写直接走 API Server |

**实际陷阱**：Cache 的一致性窗口问题 — 写后不一定立刻读到。`uncached reads` 直接走 API Server。

## 🟠 四、深度技术分析

### 4.1 🆕 KubeElasti ProbeResponse — Scale-to-Zero 健康检查修复（7/29 Deep Dive）

#### 问题本质

```
健康检查循环锁：LB 每 30s 检查健康 -> Resolver 收到请求 -> 触发 Scale-up -> Pod 启动 -> 从未真正 idle
```

**三种表现形式**：

| 类型 | 触发源 | 检查频率 |
|:-----|:-------|:--------:|
| 云负载均衡器 | AWS ALB / GCP LB / Azure App Gateway | 每 30s |
| K8s Liveness/Readiness | Ingress 层复制 | 可配置 |
| 平台监控 | Istio / Prometheus Blackbox / Datadog Synthetic | 持续 |

#### 解决方案

**ProbeResponse**：在 Resolver 层添加匹配规则，匹配到的健康检查请求由 Resolver **自主回复 200 OK**，不触发 Scale-up。

```yaml
probeResponse:
- method: GET
  path:
    type: PathPrefix
    value: /healthz
  response:
    status: 200
    body: '{"ok":true}'
- method: HEAD
  path:
    type: Exact
    value: /ready
  response:
    status: 204
    body: '{}'
```

**架构优势**：
- 服务运行时 **零开销**（Resolver 不在请求路径中）
- 仅在 proxy mode（0 replica）时生效
- 真实流量仍正常触发 Scale-up

**三大获益场景**：
- **GPU 负载**：IDLE GPU 从不可能变为可行
- **授权软件**：按实例收费的软件在无真实流量时保持关闭
- **内部服务**：CI 预览环境 / 内部仪表盘在健康检查中保持 0 副本

### 4.2 🆕 Cilium × Kubeflow — 60% GPU 空闲调试（7/23 Adobe KubeCon India）

#### 根因：两个正确系统，组合出错

```
Kubernetes Scheduler（拓扑无关）-> 随意放置 Pod
CiliumNetworkPolicy（拓扑感知）-> 划 Zone 边界封锁流量
                                        v
Coordinator 落在 Zone A，GPU Worker 落在 Zone B -> 网络策略静默阻断 NCCL 通信
```

**三种表现形态**：

| 形态 | 表现 | 发现时间 |
|:-----|:-----|:--------:|
| **Hard Block** | 直接拒绝，Training 不启动 | 秒级 |
| **Cross-Zone Latency** | NCCL AllReduce 跨 Zone，吞吐下降 30-60% | 小时级 |
| **Cross-AZ Egress Cost** | 跨 AZ 流量产生的 Cloud 账单 | 天级 |

#### 修复：几行 YAML

```yaml
# nodeAffinity 将训练组固定在 GPU Zone
# topologySpreadConstraints 将 Coordinator 与 Workers 共置
# toleration 让 Coordinator 能落在 GPU taint 节点
```

- **GPU 利用率**：~40% → **~85%**
- **关键启示**：CNI 的拓扑意见对 Scheduler 不可见 — 这个 silence 就是故障所在

### 4.3 🆕 Goodput > Throughput — LLM Serving 的真正指标（7/20 Akamas）

#### 实验设置

| 参数 | 值 |
|:-----|:----|
| 模型 | Qwen2.5-7B |
| 引擎 | vLLM |
| GPU | NVIDIA A10G (24GB) |
| 集群 | EKS |
| 指标 | Prometheus + DCGM Exporter |
| 开源 | [github.com/graz-dev/vllm-benchmark](https://github.com/graz-dev/vllm-benchmark) |

#### 核心发现

| 实验 | GPU Mem Util | max_num_batched_tokens | max_num_seqs | TTFT avg | Prefill tput | Decode tput | **p95 TPOT** |
|:----:|:------------:|:----------------------:|:------------:|:--------:|:------------:|:-----------:|:------------:|
| Exp 1 | 0.89 | 416 | 2 | 1.40s | 1925 tok/s | 478 tok/s | **50 ms** |
| Exp 20 🔥 | 0.87 | 215 | 27 | 1.40s | 2934 tok/s | 690 tok/s | **494 ms** |

- 相同 TTFT，TPOT 差 **10×**（50ms vs 494ms）
- **三种负载**（Chatbot / Reasoning / Agentic）最优配置不同
- 配置空间存在**微小悬崖** — 手工猜测不可靠，必须自动搜索

**核心教训**：没有 SLO 的 throughput 是营销不是工程。真正的目标是 **Goodput** = 满足延迟目标的请求/秒。

## 🟤 五、多集群 & 服务网格

### 5.1 🆕 Linkerd 多集群联邦 — 三模式共存实战（7/27）

#### 三种模式对比

| 模式 | 标签 | 网络要求 | 行为 |
|:-----|:-----|:---------|:-----|
| **Hierarchical (Gateway)** | `mirror.linkerd.io/exported=true` | Gateway IP 可达 | 服务 mirror 为 `<svc>-<cluster>`，经 Gateway 路由 |
| **Flat (Pod-to-Pod)** | `mirror.linkerd.io/exported=remote-discovery` | Flat 网络 (Pod IP 可路由) | 直连远端 Pod |
| **Federated** | `mirror.linkerd.io/federated=member` | Flat 网络 | 同名服务合并为 `<svc>-federated`，自动负载均衡 |

#### 三区域 GKE 架构

- **3 集群**：west (us-central1) / east (us-east1) / north (europe-west1)
- **全互联拓扑**：每对方向各一条 Link（共 6 条）
- **3 种示范服务**：frontend (federated) / api (flat) / analytics (gateway)

#### 混沌测试结果

| 事件 | 效果 |
|:-----|:------|
| **east 集群宕机** | Federated 自动重平衡 33%→50%/50% (零错误) |
| **api-east 宕机** | 503（预期 — 客户端指定了 remote） |
| **analytics-east-gw 宕机** | 502（Gateway 不可达） |
| **恢复 east** | 15-30s 内三模式全部恢复 |

**关键洞察**：标签决定行为，三种模式在同一个 mesh 中**自由共存**。

#### 7 大注意事项（实操经验）

1. VPC Peering 必须导出+导入自定义路由
2. Regional 集群默认 3× 节点数（单 Zone fix）
3. Pod CIDR 不可重叠（否则路由静默失效）
4. 每个 consuming cluster 需要一个 controller per link
5. Federated 服务命名固定 `<svc>-federated`
6. Gateway 和 Flat 不能用同一条 Link
7. 测试故障转移要**真杀集群**而非只杀 Pod
