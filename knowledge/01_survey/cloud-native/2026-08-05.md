## 一、🔴 AI Agent 可观测性（核心增量，CNCF 8/4）

- **Observability for AI Agents（08-04, epower · CNCF Member Post）**: 核心论断——**传统 APM 无法回答 Agent 监控问题**：为什么任务成本异常高？为什么 agent 重复调用同一工具？agent 是否真的做了它说的事？哪个模型最适合该任务？**Agent 不会带 stack trace 崩溃——它们 loop、hallucinate、烧 token、产出看似合理但微妙错误的输出**。Prometheus 计数器 + Grafana 面板单独无法回答这些问题。
  https://www.cncf.io/blog/2026/08/04/you-cant-debug-what-you-cant-see-observability-for-ai-agents/

- **三支柱之一：Traces（Session 时间线）**: 每个 agent session 产出 **agent trace**（非通用 APM trace）——捕获完整决策历史：每次模型调用、工具调用、sub-agent 委托，**附 timing 与 cost**。实践：Langfuse 作 trace backend，每个 LLM 调用/工具执行/委托都是一个 span，sub-agent 工作作为父 trace 的子节点嵌套。**trace 投递必须非阻塞**——工具执行绝不等待同步 HTTP POST，用 batch exporter 管道内存缓冲周期 flush，shutdown 时优雅 drain；trace backend 短暂不可达时损失的是遥测而非可用性。

- **三支柱之二：Costs（单位经济学）**: token 成本是 agent 的**单位经济学**。两级可见性：per session（总成本/token 分解/哪个模型做了什么）+ per agent 随时间（每日 burn rate/session 数/成本趋势）。**loop agent 几何级烧 token**——反复调用同一工具无法进展，无成本监控时你会在发票到达时才发现。**主动 guardrail 优于被动告警**：硬迭代上限（hard iteration caps）、per-tool 调用预算、**loop detection 阻断相同连续调用**都是 pre-flight 断路器——并行 agent 的紧循环可在 webhook 触发前几秒内烧光预算。告警阈值设计：单 session 成本超过该 agent 滚动平均的倍数。

- **三支柱之三：Audit（不可变记录）**: 每次工具调用、治理决策、内存操作记录到 **append-only 结构化日志**（带时间戳、可搜索）；含敏感数据的工具输出**先 sanitize 再记录**。配套实践：**doctor 式诊断命令**（brew doctor 风格）一键检查 agent 依赖健康（模型连通性/向量库可达性/待批 approvals/内存计数/trace backend 状态/集成健康），免翻五个 dashboard；**自动化 session 审查**——agent 每天跑数百 session 无法人工全看，自动分析 traces（duration/cost/tool count/loop detection/token efficiency）标记异常 session 供人工复查。

- **Metrics vs Traces 分工 + cardinality 警告**: 实时 dashboard/告警导出**有界 metrics** 到 Prometheus（tool 成功率/每 agent session 成本/approval 延迟直方图/分类计数），与 traces 互补不替代。**关键警告：Prometheus labels 必须低基数**——tool 名/agent 名安全（有界值），**绝不把 session ID 等唯一标识放进 labels**——每天数千 session 会产生 cardinality explosion 直接 crash metrics server。监控信号优先级：session cost vs 滚动平均（抓 loop）> 相同连续工具调用（loop detection）> approval 延迟 > model error rate > 向量库/集成健康（静默依赖故障）> 每日 token burn vs 预算 > audit log 增长率。

- **经验教训（可直接复用）**: ① **Cost is your canary**——成本突增几乎总意味着 bug（loop/模型路由错误/上下文无界累积），先告警成本后调试；② **traces 用于调试、metrics 用于告警**——别用 traces 告警（太细）也别用 metrics 调试（太聚合）；③ **audit 的 PII-redaction 不可妥协**——审计轨迹会在事故复盘时被查询，含凭据/PII 的可观测工具会变成责任；④ 构建诊断命令 > 任何 dashboard；⑤ 自动化 trace 分析，人只审异常标记。

## 二、🟠 安全运维：CSPM 采用激增但工单未减（TNS 8/4）

- **CSPM adoption jumped 60%. Tickets stayed open.（08-04, Megan Carnegie · IOmergent 赞助）**: **CSPM（云安全态势管理）采用率一年内激增 60%+**，**65%+ 组织**现使用某种 CSPM；市场预计 **2030 年达 $11.75B**。核心矛盾——**"Detection is easy. Execution is the hard part"**：工具与发现不短缺，缺的是**时间与操作容量**；安全扫描器持续产出 findings，但同一批 tickets 一周周保持 open。
  https://thenewstack.io/cloud-security-triage-cadence/

- **真正的缺口是 triage 而非检测**: 安全发现要产生价值需三层判断——是否真实可利用、暴露严重度、是否影响业务关键依赖；sense-check 一个问题时背后又涌入几十个 alerts。**解决方案不是更多工具而是"节奏"（cadence）**：短周期反复 check-in（周/月度）+ 明确 owner + 业务上下文，四个问题驱动——"What's new? Does it matter? What's still open? What's blocking it? Who owns the next step?"；快速赢今天修，长项进 roadmap。CISO 观点：AI 与更熟练攻击者使漏洞发现/利用速度加快，**零星审查是坏赌注**——云安全问责必须成为每日运营常态。
  ⚠️ 注：IOmergent 为赞助商（托管云安全服务商），方法论可借鉴但立场需留意——"需要外部托管团队"是隐含推销。

## 三、🟢 数据库运维：Agent 引发的数据库增殖（TNS 8/4）

- **YugabyteDB AMP：Agentic Multitenant Postgres（08-04, Carly Page · Yugabyte 赞助）**: 下一轮数据库扩展问题不是"单库能多大"而是"**企业突然要跑多少个库**"——公司可能运行数百上千个 AI agents，每个都产生独立数据层需求；"**规模的维度在转移：不只是大数据库，更是数据库的增殖**"（co-founder Karthik Ranganathan）。AMP 用 serverless 多租户 + Enhanced Colocation 把数百 workload 打包到共享基础设施，**每个 agent 获得隔离的 PostgreSQL 数据库**；闲置 scale-to-zero，运行时按 **CPU 分钟计费**（实验 agent 猛跑几分钟→闲置数天→任务完成即销毁的典型生命周期）。
  https://thenewstack.io/yugabytedb-agentic-postgres-scaling/

- **用 4 个 agent 管理数据库群（"more agents" 解法）**: AMP 内置四 agent——**Architect**（建库/供给，保留组织上下文与规则）、**Voyager**（迁移/现代化，算 sizing 与改造）、**Perf Advisor**（运行期性能/根因分析，预警查询问题于生产前）、**Nexus**（连接数仓/数据流/KMS 等生态）。**"guarded freedom"（受守卫的自由）**：可丢弃的开发库让 agent 自主干活不问权限；生产系统（金融数据）走 **dry-run 模式**——"告诉你想做什么，我在这些类别操作上先征求许可"。所有 agent 决策留**可重建轨迹**（Meko 记录：人说了什么/上下文说了什么/我推断了什么/我做了什么），支持事后"what the hell was that"审计。⚠️ 赞助内容，产品处于早期（内部使用+精选合作伙伴）。
  ⚠️ 判断：Yugabyte 案例的价值不在产品本身，而在**揭示"数据库蔓延"将随 Agent 普及成为真实运维问题**——与 08-03 报告"平台工程服务 Agent 速度"同向：基础设施层必须为海量短期、隔离、可销毁的 Agent 工作负载重新设计（serverless + scale-to-zero + 自动化治理）。
