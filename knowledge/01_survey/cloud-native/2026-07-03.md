## 1️⃣ 🔴 K8s WG Device Management Spotlight — GPU/TPU 设备管理全景

- **来源**: [Kubernetes Blog — Spotlight on WG Device Management](https://kubernetes.io/blog/2026/06/24/spotlight-on-wg-device-management/) (2026-06-24)
- **作者**: Natalie Fisher
- **热度**: 🔴 直接影响 GPU 调度路线图

**核心内容**:

AI/Edge/Telecom 工作负载对 K8s 的硬件管理需求正在超过传统 CPU+Memory 范畴：

| 硬件类型 | K8s 管理手段 | 当前状态 |
|:---------|:------------|:--------|
| GPU | DRA + Device Plugin + Node Feature Discovery | GA (v1.35) |
| TPU/NPU | DRA Resource Class / CEL selectors | Beta |
| FPGA | DRA + Device Plugin | Alpha |
| NIC/DPU | DRA + SR-IOV + DPDK | Alpha/Beta |
| 加密加速器 | DRA Resource Pool | Alpha |

**关键讨论方向**:
1. **Node Feature Discovery 标准化** — 硬件能力自动发现，避免人工标注
2. **Device Health Reporting** (v1.36 引入) — 设备故障透传至调度层
3. **DRA Resource Class 语义扩展** — 不仅管"有多少 GPU"，还能管"哪个型号/拓扑位置"
4. **跨集群设备编排** — Edge/Fog 场景下的离散 GPU 管理

**🔗 关联**: K8s v1.35 DRA GA (7/02 已记录) + NVIDIA DRA Driver 移入 SIGs

## 2️⃣ 🟡 K8s AI 政策深度解析 — Open Source Maintainership in the Age of AI

- **来源**: [Kubernetes Blog](https://kubernetes.io/blog/2026/06/26/open-source-maintainership-in-the-age-of-ai/) (2026-06-26)
- **作者**: Kevin Hannon (Red Hat)
- **热度**: 🟡 影响所有 K8s 贡献者，已于 7/02 记录，今日补充深度解读

**3 层政策框架**:

```
+-----------------------------------------+
|  ① 披露要求 (Disclosure Required)        |
|  - PR 描述/Template/Commit 中声明 AI     |
|    辅助范围                              |
+-----------------------------------------+
|  ② 禁止事项 (Forbidden)                  |
|  - AI 列为合著者/Co-Author                |
|  - "assisted-by" / "co-developed" trailer |
|  - 将 LLM 工具署名                        |
+-----------------------------------------+
|  ③ 审阅标准 (Review Standards)           |
|  - AI 生成代码同样需人工审阅              |
|  - Maintainer 有权要求重写 AI 部分        |
|  - 安全关键代码 (CVE fix) 需逐行确认      |
+-----------------------------------------+
```

**核心问题**: AI 让生成代码变快了，但维护代码库的效率没有相应提升。维护者面临"更多 PR → 更多 Review → 更不可靠"的压力三角。

**7/02 记录结论更新**: CNCF 生态首个明确 AI 辅助开发政策，将影响所有云原生企业内 CI/CD 流程。

## 3️⃣ 🟡 kpt 重新引入：你的基础设施自动化工具链

- **来源**: [CNCF Blog — (re)introducing kpt](https://www.cncf.io/blog/2026/07/02/reintroducing-kpt-your-toolchain-for-infrastructure-automation/) (2026-07-02)
- **作者**: Ciaran Johnston (Ericsson)
- **热度**: 🟡 基础设施即代码工具

**背景**: kpt 最初是 Google 在 2019 年推出的 KRM 配置管理工具，后捐赠给 CNCF。2024 年后转入低活跃期。本次 Ericsson 基于最新 KRM 生态重新设计。

**kpt 设计哲学**:

| 特性 | 说明 |
|:-----|:-----|
| Package-based | 配置以 KRM package 为单位分发/组合 |
| WYSIWYG | 可视化配置编排，所见即所得 |
| Automation Chain | CI/CD 管道中可编程调用 |
| KRM-native | 原生支持 K8s Resource Model |

**目标**: 替代原始 YAML 手写/Helm Chart 管理，走向声明式 Package 管理。

## 4️⃣ 🟡 OTel 启动 Dart 和 Flutter SDK

- **来源**: [OTel Blog — CfC: OpenTelemetry for Dart and Flutter](https://opentelemetry.io/blog/2026/cfc-dart-flutter/) (2026-06-29)
- **热度**: 🟡 可观测性覆盖面扩展

**要点**:
- Flutter 占 App Store 提交量的 20%+，但缺乏原生 OTel 支持
- Dart 是 Flutter 语言，也是全栈语言（服务端 + 客户端）
- 需社区贡献，现在 CfC（Call for Contributors）阶段
- 目标：Mobile Observability + Server-side Dart 可观测性

**🔗 关联**: GenAI 可观测性已覆盖 VS Code Copilot/Claude Code，移动端可观测性是下一增长点。
