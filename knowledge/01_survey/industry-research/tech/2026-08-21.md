## MoE→硬件影响

- **华为昇腾 910 上部署 MoE 大模型的现场研究：非 GPU 加速器的真实工程代价**（arXiv:2607.08215，2026-07-09）：在 16 设备 Ascend 910 集群上用 CANN + vLLM-Ascend 部署两套工作负载——W8A8 MoE judge 模型（DeepSeek-V4-Flash 的安全与对齐评测管线）和多模态医疗视觉-语言基准（DeepSeek-V4-Flash-Vision 跑 MMMU/MMMU-Pro）。为使负载可靠运行，需打 12 个厂商推理插件的源码级补丁、禁用多项高吞吐特性以保数值正确、并为周期性设备级故障增加运维防护。作者将平台限制归纳为 8 类：算子与特性支持不完整、并行机制脆弱、底层内核数值错误、图编译不成熟、高级特性不稳定、扩展性有限、可观测性弱、生态碎片化。URL: https://arxiv.org/abs/2607.08215
- **ViBE：硬件变异性感知的 MoE 专家放置（背景项，已由 08-19 收录）**（arXiv:2606.00735，2026-05-30）：制造差异/功耗限制/热条件使标称相同的 GPU 存在执行时间差异，MoE 的 token 路由负载不均 × 硬件不对称交互产生持续 straggler。ViBE 用每 GPU 性能建模 + 专家激活画像，把高负载专家放快设备，SLO 达标率 +14%、P90 TTFT 最高 -45%——**硬件变异性随规模放大**。URL: https://arxiv.org/abs/2606.00735
- **ROMER：模拟 CIM 噪声下的 MoE 鲁棒化（背景项，已由 08-19 收录）**（arXiv:2605.11800，2026-05-12）：模拟存算系统硬件噪声会破坏专家负载均衡、使干净训练的路由决策持续次优；ROMER 通过专家替换 + 路由器分位归一化校准，在真实芯片噪声下困惑度 -58.6%~-59.8%。URL: https://arxiv.org/abs/2605.11800
- **AxMoE：近似乘法器 × MoE 拓扑敏感性（昨日已收录，一行引用）**（arXiv:2605.04754）：近似计算与 MoE 的交互首研，Hard MoE 在激进近似下反超 Dense。URL: https://arxiv.org/abs/2605.04754

**分析段落 1 — MoE×硬件的三层问题空间**：将本周 arXiv 的 MoE×硬件研究并排看，恰好覆盖三层问题：AxMoE 在**算术单元层**（近似乘法器）、ROMER 在**存储介质层**（模拟 CIM 噪声）、ViBE 在**系统调度层**（GPU 硬件变异性）。三层共同指向同一结论——MoE 的稀疏激活把「硬件非理想性」从可容忍的模拟误差放大为**路由决策的系统性偏差**：专家选择是离散的，硬件噪声一旦扰动 logits 排序，就会成块地改变激活路径，而不是像稠密模型那样只是平滑劣化。这是 MoE 区别于稠密架构的第一性差异：**对硬件非理想性的敏感度由路由的离散性决定，而非参数规模**。

**分析段落 2 — 昇腾现场研究的行业信号**：2607.08215 是罕见的非 GPU 加速器大规模推理公开工程报告，价值在于量化了「脱离 CUDA」的真实成本：12 个源码级补丁、禁用高吞吐特性保正确性、8 类平台限制。对国产算力生态而言，这既是坏消息（工程成熟度仍落后）也是好消息（**问题已从「能不能跑」进入「要打几个补丁才能可靠跑」的可度量阶段**）——与 DeepSeek-V4 在 Ascend 上 34.22% MFU 的基线（昨日收录）互相印证，国产加速器在 MoE 场景的适配已进入工程攻坚期而非原理验证期。

**分析段落 3 — 硬件变异性正在成为 MoE 服务的新约束**：ViBE 的核心数据（变异性影响随规模放大）与 AgentSysBench（见分布式OS专题，异构资源亲和任务延迟差 32×）形成共振：当集群从 8 卡扩展到万卡，「同构假设」彻底失效。MoE 服务在万卡规模的真实瓶颈不是总带宽，而是**最慢 GPU 的层延迟**——同步执行下 straggler 决定一切。硬件感知专家放置（ViBE）与通信感知放置（AgentSysBench）代表了同一趋势的两翼：调度器必须把硬件状态作为一等输入。

## 云原生AI基础设施

- **Does Kubernetes DRA Replace HAMi?**（CNCF Blog，2026-08-07，Mesut Oezdil/Project Maintainer）：设备插件接口的词汇表只有「数卡」（nvidia.com/gpu: 1），想共享 GPU 的项目只能绕过 API 而非使用 API。文章系统对比 DRA（Dynamic Resource Allocation）与 HAMi：DRA 是标准化的资源管理原语（v1.34 GA），HAMi 是 GPU 共享的具体实现（切分/调度/显存隔离），两者不是替代关系——DRA 提供控制面语义，HAMi 提供数据面能力，未来 HAMi 可作为 DRA 的 driver 形态存在。URL: https://www.cncf.io/blog/
- **OpenCost 1.121.0：首个 Kubernetes 推理成本追踪**（CNCF Blog，2026-08-05，IBM Research + OpenCost Maintainer）：GPU 账单在涨、模型在服务数十亿 token，但「每个 token 到底花多少钱」无解。OpenCost 1.121.0 把 token 级成本追踪引入 CNCF 项目，按模型/命名空间/工作负载维度分摊 GPU 成本——平台团队首次获得可审计的推理成本视图。URL: https://www.cncf.io/blog/
- **LLMOps 与平台工程：AI 流水线归谁所有？**（CNCF Blog，2026-08-13，Daniel Bryant/Syntasso）：LLM 打破「数据科学家训练→DevOps 部署」的旧分工：提示词版本化、评测集管理、影子流量、回滚策略横跨多个团队。文章主张平台工程团队接管「AI 流水线平台」的所有权，数据科学家聚焦模型本身——组织归属之争（与昨日 Kyverno 归属之争同构）。URL: https://www.cncf.io/blog/
- **Gateway API v1.6.0：TCPRoute / UDPRoute 转正**（Kubernetes Blog，2026-08-03，SIG Network）：v1.6 于 6 月 30 日发布，TCPRoute 与 UDPRoute 从 Experimental 升入 Standard，Gateway API 覆盖从 L7 HTTP 到 L4 传输层的完整南北向流量语义。URL: https://kubernetes.io/blog/
- **etcd v3.7.0 发布：RangeStream 长请求功能**（Kubernetes Blog，2026-07-08，SIG Etcd）：最新 minor release 引入长期诉求的 RangeStream（流式范围请求），对大规模 Watch/List 场景的 API server 压力缓解有直接影响。URL: https://kubernetes.io/blog/
- **Kubernetes v1.37 Sneak Peek**（Kubernetes Blog，2026-07-31）：预告 v1.37 计划变更，含 SELinux 卷标签变更 GA 的影响提示等——K8s 主版本节奏与 AI 工作负载特性（DRA/设备管理 WG 持续活跃）同步演进。URL: https://kubernetes.io/blog/

**分析段落 1 — DRA 与 HAMi 的关系是「控制面 vs 数据面」**：这个问题在 GPU 共享场景被反复问起，答案值得展开：DRA（v1.34 GA）定义的是**资源如何被声明、分配、挂载、健康上报**的 API 语义；HAMi 解决的是**GPU 如何被切分、显存如何隔离、调度器如何感知拓扑**的执行细节。类比网络栈：DRA 是 CNI 接口规范，HAMi 是具体 CNI 插件。生态演进方向（文章明确提示）是 HAMi 转写为 DRA driver，让共享能力暴露为标准 API——这正是 K8s 一贯的「先实现后标准化」路径（类似 Ingress→Gateway API）。

**分析段落 2 — 云原生 AI 成本治理进入 token 粒度**：OpenCost 的 token 级成本追踪是「AI 运营化」的第二块拼图（第一块是资源分配 DRA）。第一性问题：推理成本的核算粒度必须匹配**计费粒度**——按 token 卖就按 token 算成本。但 token 成本 ≠ GPU 成本 ÷ token 数：KV cache 复用、prefill/decode 段差异、批大小波动使真实成本是强非线性的。OpenCost 先给「分摊视图」（模型×命名空间×工作负载），精确的边际成本仍需专用 profiling——这为平台团队留出了工具空白。

**分析段落 3 — 平台工程接管 AI 流水线的组织信号**：LLMOps 归属之争（Bryant）、Kyverno 定位之争（Oksay）、AI 流水线所有权（昨日）三篇同周出现，说明平台工程团队正在集体争取「AI 时代新增运维职责」的所有权：模型网关、提示词版本、评测管道、影子流量。这是有商业含义的组织变革——**平台工程正在从「容器平台」升级为「AI 运行时平台」**，谁掌握这个位置，谁就掌握企业 AI 落地的基础设施入口。

- **504 GPU 预训练集群运维实录：63 节点 B200 的故障与恢复数据**（arXiv:2605.09370，2026-05-10，SKT/Upstage/Lablup/NVIDIA Korea/VAST Data）：55 天 Prometheus（751 项指标）+ 73 天运维日志（224 次多节点训练会话）的跨组织分析。四大发现：①没有单一指标能主导所有故障类型（10 个 XID 故障）→ 需要多信号检测；②523 次 checkpoint 事件显示重启加载达最大读带宽 21.5%（700GB/s）、保存突发 16.0% 最大写带宽（250GB/s），NFS/RPC 排队与传输层积压同步上升——**checkpoint I/O 是训练稳定性的隐藏瓶颈**；③节点排除高度集中：63 节点中 top-3 占 >50%；④自动重试链成功率 33.3%（12 链 73 次尝试），是手动重试 12.5% 的 2.7 倍，重试中位间隔 11 分钟。URL: https://arxiv.org/abs/2605.09370

**分析段落 1 — Agent 负载正在改写 serving 系统的假设**：AgentSysBench 是本季度最重要的系统论文之一，因为它系统性地证明了 serving 系统为「孤立模型推理」设计的假设在 agent 场景全部失效：非 LLM 组件主导延迟（5/10 应用）、资源亲和异构（32× 延迟差）、空闲会话占资源、控制面税挤占计算。第一性解释：agent 工作负载的本质是**「推理 + 状态 + 工具执行」的长事务**，而传统 serving 优化的是**无状态短请求的吞吐**——两者优化目标根本冲突。四个设计探索（任务感知/通信感知/状态卸载/结果缓存）给出的收益（-40% 延迟、-4.6× 内存）说明：agent serving 的优化空间远大于传统推理的边际优化，是系统研究的蓝海。

**分析段落 2 — checkpoint I/O 是万卡训练被低估的稳定性瓶颈**：504 GPU 报告的 21.5%/16.0% 带宽峰值数据揭示了被「网络瓶颈」叙事遮蔽的事实：**训练稳定性瓶颈正在从通信转移到存储**。checkpoint 频率×模型规模的增长快于存储带宽增长：万亿参数模型单次 checkpoint 数 TB，在 700GB/s 读带宽下重启加载就需数分钟，且 NFS 排队与传输积压会反向拖累训练（I/O 抖动传染计算）。五方跨组织共享监控管线的模式本身也是亮点——单一团队无法隔离 60 节点规模的存储 I/O 瓶颈，**跨组织可观测性是规模化故障诊断的前提**（与「60 节点测试无瓶颈、生产才暴露」的规模效应一致）。

## 分布式OS

- **TopoClaw：以人为本、拓扑感知的 Agent 操作系统**（arXiv:2605.15556，2026-05-14）：Agent OS 作为「内核层」（生命周期/内存/调度/访问控制）正在形成共识，但多数设计是 agent 中心、单宿主。TopoClaw 把人机生态建模为两个耦合结构——物理设备拓扑（异构表面）+ 社会关系拓扑（共享空间/团队/委派角色），三大贡献：①跨设备动作放置（意图与执行解耦）；②跨用户身份归因（agent 作为「数字孪生」在多用户空间协调）；③跨上下文权限治理（分布式策略执行）。开源参考架构。URL: https://arxiv.org/abs/2605.15556
- **VUDA：打破 CUDA-Vulkan 隔离，同 GPU 空间共享计算与图形**（arXiv:2605.01352，2026-05-02，上海交大 IPADS）：具身 AI 模拟环境在单设备上交错执行物理仿真（CUDA）与真实感渲染（Vulkan），但 CUDA/Vulkan 独立上下文导致时间片互斥。VUDA 通过 channel 重定向 + 页表嫁接统一地址空间，实现空间并行，吞吐最高 +85%（对比时间共享基线）——**GPU 执行隔离是多工作负载共存的最后壁垒**。URL: https://arxiv.org/abs/2605.01352
- **AEG：异构加速器的裸金属 AI 运行时**（arXiv:2604.09565，2026-02-15）：无 RTOS/通用 OS 的裸金属运行时，「Control as Data」范式把 ADF 图控制逻辑扁平化为可执行 RCB（Runtime Control Blocks）。ResNet-18 实测：单 AIE tile 计算效率比 Linux+Vitis AI 高 9.2×、数据搬运开销 -3~7×、延迟方差 CV=0.03%，28 个 AIE tile 达 68.78% Top-1——**去掉 OS 层是极致效率路径之一**。URL: https://arxiv.org/abs/2604.09565
- **Energy Calculus：能量组合代数**（arXiv:2607.11087，2026-07-13，Michigan Mosharaf Chowdhury 组）：能量是 AI 扩展的硬约束但缺乏形式化。energy elements（时间/静态动态能量/硬件工作点/不确定度）+ 顺序/同设备并行/跨设备并行三算子 + 七公理；顺序组合仅在上下文无关时交换、不分配于并行——能量度量的组合性质与其他资源根本不同，Reduction Theorem 允许测量不确定度主导时回退到简单代数。URL: https://arxiv.org/abs/2607.11087

**分析段落 1 — Agent OS 从「单宿主内核」走向「分布式权限系统」**：TopoClaw 的价值不在技术实现而在问题框架：它把 agent OS 的核心矛盾从「怎么管理 agent 内部推理」重构为「agent 的行动如何与人机拓扑/权限边界对齐」。这与昨日 Science Earth（已撤回）的「能力互连协议」、VUDA 的「跨 API 域共享」形成谱系——**分布式 AI 基础设施的 OS 层正在从资源编排（调度/内存）扩展到信任编排（身份/权限/归因）**。第一性看，agent 数量的指数增长必然要求「动作可归因、权限可委派、越权可审计」，这是 OS 语义在新计算范式下的回归。

**分析段落 2 — 裸金属 vs 通用 OS：效率极端的两条路线**：AEG（去掉 OS，9.2× 效率）与 Energy Calculus（在 OS 层做能量形式化）代表了边缘 AI 效率的两个方向：**减法**（去 OS 层换确定性）与**加法**（在 OS 层做精细能量调度）。两者的适用边界清晰：AEG 适合固定工作负载的确定性部署（推理/仿真），Energy Calculus 适合动态混合负载（云/集群）。对服务器行业的意义在于：**「OS 层开销」在 AI 时代的每一层都在被重新审视**——从裸金属运行时到 agent 编排层，「谁的抽象值得保留」是贯穿性的设计问题。

**分析段落 1 — PCIe Gen6 SSD 量产的里程碑意义**：Samsung PM1763 量产 + Kioxia CM10 发布标志 PCIe Gen6 SSD 进入规模交付元年。第一性看，AI 存储的瓶颈从「接口带宽」转向「介质与控制器」：Gen6 单盘 ~14GB/s 读带宽已接近 NVMe 控制器的 PCIe x4 物理极限，下一步竞争在**介质层（QLC/PLC 密度）与控制器层（多队列/卸载）**。512TB 单盘（DapuStor）与 10M IOPS（Kioxia GP1）分别代表容量与 IOPS 两个极端——存储厂商正在用「容量型/IOPS 型」分化应对 AI 负载的两类需求（训练大文件流式 vs 推理小对象随机读）。

**分析段落 2 — KV cache 外置化与 JBOF 的早期信号**：AIC 的 KV-cache JBOF 与昨日硬件组互连专题的 CXL 内存池是同问题的两种路径：**推理 KV cache 的内存墙如何打破**。JBOF（NVMe over Fabric 键值语义）押注「闪存随机读够快」，CXL 内存池押注「内存级延迟」，两者的分界点是延迟敏感度：KV cache 命中延迟差一个数量级就影响 TTFT。当前 JBOF 是成本解，CXL 是性能解，最终形态取决于「KV cache 命中率 × 延迟预算」的工程权衡。

## 运维平台与AIOps

- **ES Guardian Agent：自治 AI SRE，六九可用性（99.9999%）**（arXiv:2604.03933，2026-04-04，IEEE CNSM 2026 投稿）：11 阶段全生命周期自治运维（Evaluate/Optimize/Deploy/Calibrate/Stabilize/Alert/Predict/Heal/Learn/Upgrade）+ 多源预测性故障引擎（指标趋势/应用日志/内核遥测：dmesg、NVMe SMART、NIC bond 统计、热传感器）。生产评估：300 次自主调查-修复循环、从 18 小时跨系统故障恢复、诊断所有宿主机 NIC 硬件故障。关键结论：**每分片数据量（非调参）是查询性能的首要决定因素，延迟以 0.26ms/MB·shard 线性增长**。URL: https://arxiv.org/abs/2604.03933

**分析段落 1 — AIOps 从「告警辅助」走向「全生命周期自治」**：ES Guardian Agent 的 11 阶段框架与 300 次自主循环，把 AIOps 的边界从「异常检测 + 告警」扩展到「部署→调优→预测→自愈→升级」全生命周期。第一性判断：运维自动化的价值密度取决于**故障预测的提前量**——Guardian 的多源遥测（内核级 dmesg/SMART/NIC/热传感器）目标是把「事后修复」变成「事前规避」；NVMe SMART 等带外/内核信号进入预测模型，与 BMC 遥测（见 BMC 专题）形成呼应：**底层硬件信号是 AIOps 的上游燃料**。

**分析段落 2 — Agent 可观测性成为新运维品类**：传统 APM（请求指标）对 agent 系统失灵的根因是**观测粒度假设错误**：agent 的一次「用户请求」内部包含数十次 LLM 调用/工具调用/上下文重写，失败模式是「多问了三次」「上下文污染」「工具链死循环」——这些在请求级指标里不可见。Agent 可观测性需要记录决策轨迹（decision trace），这与 AgentSysBench 的「控制面税」测量互补：**既要看到 token 花在哪（成本），也要看到推理走到哪（质量）**。对运维平台厂商而言，agent 可观测性是确定的新品类窗口。
