## MoE→硬件影响

- **FreeToken：边缘原生 MoE 服务系统（2608.16157）**（08-17，arXiv）：把个人电脑当作统一弹性推理平台，持续将计算/模型状态映射到实际可用资源；支持 20+ MoE 模型，8GB 笔记本 GPU 跑 35B、游戏台式机跑 284B、单工作站 GPU 跑 753B GLM-5.2，已在 flashml.ai 开源。https://arxiv.org/abs/2608.16157
- **高带宽闪存（HBF）双路径专家投递架构（2608.14333）**（08-14，arXiv）：探索 HBF→GPU 直连 + HBF→HBM base die→GPU 中继双路并发传输，整专家按路由分配、早专家判定隐藏 HBF 读延迟；代表负载下吞吐 1.94x、端到端 1.90x vs 纯 HBM 中继方案。https://arxiv.org/abs/2608.14333
- **DA-MoE：分布感知 fused-MoE kernel 动态派发（2607.23099）**（07-27，arXiv）：用 Effective Experts 指标 + Dirichlet 逆建模生成可控路由分布，GPU 端按实时路由直方图选近最优 kernel（免 CPU-GPU 同步）；HumanEval-X 上 DeepSeek-V3 提速 1.16x、Kimi K2 提速 1.29x，峰值 1.40x/1.56x。https://arxiv.org/abs/2607.23099
- **Sieve：动态专家感知 PIM 加速（2605.11277）**（05-11，arXiv，Stanford）：现代 MoE 专家激活呈双峰分布（少数专家吃大量 token、长尾专家只接 1-2 个），算术强度差异使静态 PIM 卸载失效；Sieve 按运行时路由分布将专家在 GPU/PIM 间分区并重叠计算与通信，Qwen3.5-397B-A17B 吞吐/交互性 1.3x、GPT-OSS-120B 1.3x、Qwen3-30B-A3B 1.6x。https://arxiv.org/abs/2605.11277
- **EEP：宽 EP 推理的部分秩故障存活（2605.10670）**（05-11，arXiv，清华）：把「成员关系」从初始化固定配置改为显式可变运行时状态，单秩故障从整实例停机变为两次有界中断（11s 恢复 + 8s 重入），52s 内吞吐恢复到故障前 95%，而固定成员全重启基线 348s 不可用；与 SGLang 集成。https://arxiv.org/abs/2605.10670
- **FluxMoE：专家分页解耦常驻内存（2604.02715）**（04-30，arXiv）：把专家权重视为流式瞬态资源，按需物化、用后即逐出，GPU 内存优先给 KV cache；vLLM 上内存紧张场景吞吐最高 3.0x。https://arxiv.org/abs/2604.02715
- **CRAFT：细粒度成本感知专家复制（2603.28768）**（MLSys 2026）：现有复制方案普遍过度复制，复制体占用显存反噬吞吐；按层估计复制收益、在显存预算下最大化负载均衡，百亿~万亿参数规模端到端吞吐 +1.14x（最高 1.2x）。https://arxiv.org/abs/2603.28768
- **PROBE：实时预测预取的算通协同（2602.00509）**（02-03，arXiv）：Gate 初始化前瞻预测器蒸馏 router 预测下一层专家激活，硬件感知均衡规划器联合优化动态复制与 token 分配，相位锁定协同调度用分相传输把带宽密集的专家迁移藏进计算；prefill 延迟降 1.32x、decode 吞吐 +1.26x。https://arxiv.org/abs/2602.00509
- **MixServe：TP-EP 混合并行的 fused AR-A2A 通信（2601.08800）**（01-13，arXiv，ICDCS 2026 投稿）：自动评估各并行策略通信开销后选择最优，重叠节点内 AR 与节点间 A2A；DeepSeek-R1/Qwen3 上 TTFT 加速 1.08~3.80x、ITL 1.03~1.66x、吞吐 +5.2%~50.3%。https://arxiv.org/abs/2601.08800
- **Tarragon：注意力/专家分离域的弹性 MoE 推理（2601.01310）**（01-05，arXiv）：注意力 worker 与专家 worker 作为独立故障域，异步增量 KV checkpoint + 影子专家，故障 stall 较 MegaScale-Infer 降 160-213x（~64s→0.3-0.4s）。https://arxiv.org/abs/2601.01310
- **Temporally Extended MoE：选项框架降低专家切换率（2604.20156）**（04-21，arXiv）：控制器学习「何时切换专家集、加载哪些」，gpt-oss-20b 上切换率从 >50% 降至 <5%，MATH/MMLU/MMMLU 保留 90% 精度——直接缓解专家权重换入换出对 HBM 带宽的冲击。https://arxiv.org/abs/2604.20156
- **InfiniLoRA：解耦多 LoRA 服务（2604.07173）**（04-08，arXiv）：MoE 架构使 LoRA 显存成本剧增，InfiniLoRA 把 LoRA 执行与基座推理解耦为共享 LoRA Server，SLO 严格约束下可服务请求率平均 +3.05x。https://arxiv.org/abs/2604.07173
- （已收录 08-20/21/22）：ViBE 硬件感知专家放置（2606.00735）、ROMER 模拟 CIM 噪声校准（2605.11800）、AxMoE 近似乘法器（2605.04754）、MoP agent 预取器（2608.13027）、SLAI T-Rex 昇腾 MoE 后训练（2607.20145）、PithTrain agent-native MoE 训练（2605.31463）、AIConfigurator（2601.06288）

> **分析：2026H2 MoE 服务优化的三条收敛主线**
>
> **① 从「均衡路由」到「异构感知」**。08-20 收录的 ViBE 提出硬件感知专家放置（P90 TTFT −45%），本日 DA-MoE/Sieve 从 kernel 派发与 PIM 分区两个层面深化同一命题：MoE 执行时间不平衡 = 路由偏斜 × 硬件异构的联合函数，只优化 token 均衡而忽略设备差异（制造偏差/功耗/热）必然留下硬件侧 straggler。三者共同指向的结论是：**MoE 推理优化的下一增量不在路由算法本身，而在「路由分布 × 硬件状态」的联合建模**——这要求运行时具备每 GPU 性能画像与每专家激活画像的双重可观测性，对服务器 BMC/遥测数据的细粒度提出了新需求（见 BMC 专题）。
>
> **② 显存约束下的「专家流动性」共识**。FluxMoE（专家分页、3.0x）、CRAFT（复制体预算化、1.14x）、PROBE（预测预取、1.32x/1.26x）、Temporally Extended MoE（切换率 50%→5%）从四个方向围攻同一矛盾：MoE 权重越大，静态常驻越浪费——KV cache 与专家权重在 HBM 内是零和博弈。HBF（高带宽闪存）论文更给出架构级答案：与其在 HBM 内腾挪，不如让专家权重走「闪存直连 GPU」的第二条路（1.94x）。这预示 **CXL/闪存级专家存储 + 细粒度权重流式化** 将成 2026H2-2027 推理服务器硬件差异化重点（与存储专题 CMX/NAND 涨价信号共振）。
>
> **③ 故障弹性从「整机重启」走向「秩级存活」**。EEP（11s 恢复）与 Tarragon（0.3s 级 stall）表明：EP 宽度越大，固定成员模型的恢复代价越高，成员关系必须变成可变的运行时状态。对万卡集群的工程含义是：推理服务的 MTTR 优化点从「重建通信子层」下移到「只修复被失效状态污染的成员元数据」——这与集群训练专题 ETC 的免检查点迁移（2.33-6.37x）是同一思想的训练/推理两面。

> **分析：K8s AI 化的「API 层」与「成本层」双突破**
>
> DRA 与 HAMi 之争的本质是**设备抽象范式切换**：device plugin 把 GPU 当作「可计数的匿名资源」，DRA 把设备建模为「带属性、可参数化、可健康上报的资源对象」。v1.34 GA、v1.36 扩展驱动、v1.37 继续演进，说明上游已把 DRA 当作 AI 工作负载的事实标准推进；而 HAMi 类项目（GPU 共享/MIG 编排）解决的是 DRA 尚未覆盖的共享语义——结论不是谁替代谁，而是 **DRA 定义资源模型、HAMi 层补充共享策略** 的上下分层。对服务器厂商：DRA 使 GPU 设备的健康/容量/分区属性成为调度输入，意味着 K8s 生态将直接消费 BMC/驱动上报的设备级遥测，BMC 的 Redfish/DRA 桥接能力成为云原生 AI 基础设施的隐藏接口。
>
> OpenCost 推理成本追踪与「AI Gateway Working Group」并行出现，标志云原生 AI 从「跑起来」进入「算得清账、控得住流」阶段：token 级成本核算 + 网关层 LLM 流量治理，是把推理服务变成可计量内部产品的两个前置条件。这与 CNCF 近期 LLMOps/平台工程责任讨论（08-13）同向——**成本与治理正在成为云原生 AI 的第二增长曲线**。

>

## AI最新技术业界观点

- **MoE 服务是否正从「数据中心假设」走向「边缘原生」**：正方（FreeToken, arXiv 2608.16157；FastTTS, ASPLOS 2026）——「个人电脑=统一弹性推理平台」在 8GB 笔记本跑 35B、单工作站跑 753B GLM-5.2，边缘/本地设备 + 高效 TTS 使本地 agent 匹配云级精度，隐私与离线刚需推动本地化；反方/风险（数据中心服务商视角）——本地单机算力与 KV cache 容量天花板仍在（753B 也仅存于工作站级），企业级多租/高并发服务仍需集群，且本地模型版本更新/评测负担转移给终端用户，规模经济弱于云；辨析：边缘 MoE 解决的是「隐私敏感 + 单用户 + 可接受延迟」的长尾场景，不会替代数据中心推理，但会分流一部分实时/隐私请求，使数据中心负载结构向「重 prefill + 批处理」集中。
- **K8s DRA 会否终结 HAMi 类 GPU 共享项目**：正方（CNCF Project Maintainer, https://www.cncf.io/blog/）——DRA 提供结构化资源模型与可编程分配，device plugin「只能数数」的抽象已被取代，GPU 共享语义应建在 DRA 之上；反方/风险（HAMi 生态用户）——DRA 定义的是资源发现与分配 API，共享/切分/调度策略仍需项目层实现，存量集群迁移成本高，且 DRA 设备健康/容量上报成熟度尚需验证；辨析：两者是「API 层 vs 策略层」的关系而非替代关系，未来最可能形态是 HAMi 类项目适配 DRA 资源模型（该文章本身即为双方对话信号）。
- **AI 算力供给是否必须「可信任化 + 弹性化」**：正方（TDX 去中心化计算 2607.21865；GridPilot 2605.26384 已收录）——加密 CVM 使未托管硬件可参与可信算力市场，毫秒级功率控制使 AI 集群成为电网柔性负载，算力供给从「集中自建」走向「可信众包 + 电网协同」；反方/风险（数据中心运营商）——去中心化节点的网络/安全/监管一致性难以保证，电网响应牺牲的是训练吞吐的可预测性，商业模式成熟度低；辨析：去中心化可信算力更适合推理/微调等中低敏感负载，训练仍留在集中集群；但「功率可调度」正从绿色叙事变成并网硬约束，弹性化落地概率更高。
