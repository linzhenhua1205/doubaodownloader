## §1 研发效能度量 — 增量更新

### ① "认知债务(Cognitive Debt)"概念正式结构化

> **来源**: [Margaret-Anne Storey — "How Generative and Agentic AI Shift Concern from Technical Debt to Cognitive Debt"](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/) (2026-02-09)
> **信号强度**: ⭐⭐⭐⭐⭐

**核心概念革命**:

| 维度 | 技术债务 (Technical Debt) | 认知债务 (Cognitive Debt) |
|:-----|:--------------------------|:-------------------------|
| **债务载体** | 代码本身（属性） | 开发者的头脑（理解） |
| **本质** | 设计/实现选择的累积 | 共享理论的消失 |
| **检测方式** | 代码质量分析工具 | 团队犹豫不敢改代码/依赖部落知识 |
| **AI影响** | AI可能降低技术债（生成规范代码） | **AI显著增加认知债**（代码理解跟不上生成速度） |
| **偿还方式** | 重构/重写 | 配对编程/代码审查/知识分享/文档化 |
| **厄运循环** | 代码变糟→难改→更多技术债 | **不再理解→害怕修改→整个系统变黑盒** |

**Storey核心论点**:
- Peter Naur几十年前就提醒：程序不是源代码——程序是存在于开发者头脑中的**理论(Theory)**，描述程序做什么、开发者的意图如何实现、程序如何改变
- AI/Agent时代：这个理论碎片化或消失的速度远超技术债务的积累速度
- 学生团队在第7-8周撞墙的案例：**认知债务先于技术债务瘫痪了团队**

**团队应对策略**:
1. 每项AI生成变更至少有一人**完全理解**后才能发布
2. 不仅记录"改了啥"，还要记录**"为什么这样改"**
3. 通过代码审查/回顾/知识分享会议**定期重建共享理解**
4. 警示信号：团队成员**犹豫改代码**、依赖"部落知识"（只有1-2人懂）、系统成为黑盒

> **关联**: 这一概念与 MEMORY.md 中"AI依赖萎缩效应"和"认知寄生"概念高度一致——AI工具让代码生产加速，但人类对系统的理解却在下降。认知债务可能是2026-2027研发管理最被低估的风险。

### ③ METR 2026年2月实验更新 — 结构性"无AI不工作"效应确认

> **来源**: [METR — "We are Changing our Developer Productivity Experiment Design"](https://metr.org/blog/2026-02-24-uplift-update/) (2026-02-24)
> **信号强度**: ⭐⭐⭐⭐⭐

**实验困境**:

| 问题 | 表现 | 影响 |
|:----|:-----|:-----|
| **招募失败** | 开发者拒绝参与"工作时不能使用AI"的实验组 | 2026年无法招募到愿意无AI工作的开发者样本 |
| **任务选择偏倚** | 30-50%开发者选择不提交某些任务，因为不想做这些任务时不能用AI | 高AI增值任务被系统性地排除 |
| **多Agent并行** | 开发者同时跑多个Agent，无法准确报告单任务耗时 | 时间测量不可靠 |
| **质量差异** | AI允许 vs 禁止条件下的产出质量/测试/文档显著不同 | 时间差值≠价值差值 |
| **完成率偏倚** | 分配到AI禁止条件后任务完成率下降——有人直接一个任务都没完成 | 样本自选偏倚 |

**原始数据变化**:

| 时间段 | 速度效应 | 置信区间 | 说明 |
|:-------|:---------|:---------|:-----|
| 2025年初（原研究） | **-19%**（慢19%） | +2%~+39% | AI拖慢开发者 |
| 2025末（原参与者的子集） | **+18%**（快18%） | -38%~+9% | 翻转但置信区间宽 |
| 2025末（新招募开发者） | **+4%**（快4%） | -15%~+9% | 几乎为零 |

**开发者原话**:
> *"我实际上严重偏倚采样的问题……我避免那些AI可以在2小时内完成、但我却要花20小时的任务。如果被分配到AI禁止组，我会非常痛苦。"*
>
> *"我的头要炸了——当我习惯了用Uber，再让我在城里走路就根本没法忍受。"*

**METR方法论转向计划**:
1. **更密集的实验**：高收入+短期，提高合规率
2. **观测数据**：Claude Code约占4%的GitHub提交，可做被动分析
3. **问卷调查**：尽管自评有偏倚，精心设计仍有价值
4. **固定任务实验**：回归传统设计（给定相同任务，比较AI允许/禁止完成时间）
5. **开发者级随机化**：而非任务级（每个参与者全部用AI或全部不用）
6. **基准评测**：继续构建自主完成任务能力的评估

> **启示**: "无AI不工作"效应已经不是假设，而是实验层面的结构性障碍。对于研发管理者，这意味着AI依赖已是**不可逆的组织状态**，管理制度必须围绕"AI是默认选项"来设计，而非"AI是补充选项"。

### ④ DORA 2024反常发现 — 个体感知≠系统指标

> **来源**: [Redmonk — "Development Productivity, Not Developer Productivity"](https://redmonk.com/rstephens/2025/09/25/development-productivity/) (2025-09-25)
> 引用的DORA 2024数据：Google Cloud Accelerate State of DevOps Report 2024
> **信号强度**: ⭐⭐⭐⭐⭐

**DORA 2024 反直觉数据**:

| 指标 | 发现 |
|:----|:-----|
| AI使用率 | ~75%开发者报告使用AI |
| 个体感知 | 开发者"感觉"AI让自己更高效 |
| 但：AI采用增加25% → **有价值工作时间减少2.6%** | 系统层面产出不升反降 |
| AI采用增加25% → **交付吞吐率下降1.5%** | 更多代码≠更快交付 |
| AI采用增加25% → **交付稳定性下降7.2%** | 质量显著恶化 |

**分析（Redmonk Rachel Stephens）**:
> *"蛇吞下老鼠只花了几秒钟，但消化老鼠需要很长时间。现在有一块老鼠形状的肿块在蛇体内缓慢移动。"*
>
> *"个体开发者甚至团队变快，不必然让系统变快。我们的系统以复杂方式交互。"*

**核心概念: "Development Productivity, Not Developer Productivity"**:
- **开发者生产率(Developer Productivity)**：个体能写多少代码——AI擅长这个
- **开发生产率(Development Productivity)**：系统能交付多少价值——涉及审查/测试/部署/运维
- AI编码工具再快，若审查/测试/部署不变，系统产出不增长

> **关联**: 这与前日文档中的"编排鸿沟"(Orchestration Gap)概念一致——DX×Atlassian研究也发现AI使用量+65%但速度仅+10-15%。Redmonk的贡献在于用"蛇吃老鼠"提供了形象的因果模型。

## §3 研发流程优化 — 增量更新

### ① 蛇吃老鼠 — 生成速率与消化速率的断层

> **来源**: Redmonk (详见§1-④) + 独立验证

**核心流程图**:
```
当前状态（问题）:
AI Code Gen ---> 开发者理解 ---> Code Review ---> CI/CD ---> 部署 ---> 运维
    ^4倍速度      ↔ 相同       ↔ 81%^        ↔ 相同      ↔ 相同   ↔ 相同
    |                                                                
    +------------------- 「蛇吃老鼠」瓶颈 ----------------------------+
    生成快了4倍，但从审查到运维的"消化系统"还以相同速度运转
```

**问题本质**:
- AI 代码生成速率提升 2-4×（Cursor/Claude Code等）
- 但代码审查效率未同步提升，甚至**下降**（AI代码需要更仔细审查）
- 测试/部署/运维管道容量不变
- → **瓶颈从"写代码"转移到"审查+理解+测试"**

**对研发管理者的具体建议**:
1. **审查能力扩容**：Code Review需要成为关注度投资的第一优先级
2. **自动化审查分层**：AI自动审查(格式/安全/模式) + 人类审查(架构/逻辑/决策)
3. **认知债务跟踪**：每个AI生成的PR需要标注"理解风险等级"
4. **审查 KPI 更新**：从"PR合并时间"转向"PR被充分理解后合并时间"

### ② "认知债务会计系统"提案 — 流程治理新思路

> **来源**: [HN讨论 — "Tell HN: We need an accounting system for cognitive debt"](https://news.ycombinator.com/item?id=48760460) (2026-07-02)
> 引用 Margaret Storey 认知债务概念
> **信号强度**: ⭐⭐⭐⭐

**提案：将认知债务纳入工程治理**

| 组件 | 描述 |
|:-----|:------|
| **认知债务账本** | 代码库跟随的"理解事实表"——每个文件/模块需要标注谁理解了、什么层次、谁验证的 |
| **Microcertification** | 小型理解认证，绑定具体代码区域。"开发者X已展示对此区域的理解，Y层次，由Z权威验证" |
| **验证方式** | AI-resistant验证：领域专家/技术负责人/配对编程 |
| **度量单位** | **代码行数（LOC）**——AI生成的每一行都是债务，直到被认证为"已理解" |
| **激励机制** | 更多AI代码 = 更多认知债务 → 强制理解 → 平衡生成速率和理解速率 |

**对研发流程的影响**:
- 代码审查不仅检查正确性，还检查**理解度**
- 每个Agent生成的代码块需经过"理解认证"才能进入主干
- 认知债务账本**持续对账**——代码变更会作废旧理解认证

> **关联性**: 这与我们知识库中 meth-005 系统审查方法论中的"可追溯性要求"一致。提案虽然激进且实际推广有难度，但抓住了AI时代研发流程的核心痛点——理解跟不上生成。
