## 🆕 本期新增（arXiv，2 篇，全部经 curl HTTP 200 验证）

### 1. Bounded-State Restoration：把"恢复工作集"从存储容量中解耦出来

- **Bounded-State Restoration: Decoupling Local Restore Capacity from External LLM State**（[arXiv:2608.17826](https://arxiv.org/abs/2608.17826)，08-18，作者 Zixuan Li）: 分层 KV cache 系统（如 LMCache）能把长上下文执行状态驻留在 GPU 之外的存储层级，但**"能保留多少状态"与"恢复执行需要多少本地内存"是两个独立的资源维度**——本文把后者命名为**恢复工作集（Restoration Working Set, RWS）**：恢复过程中生命周期重叠的峰值本地暂存状态。测量显示，在 pinned upstream LMCache 全路径下，1.956 / 7.823 / 15.646 GiB/rank 的外部状态分别要到 2 / 8 / 16 GiB 的 L1 层（rung）才首次全量复用成功，且成功时 L1 峰值几乎等于状态本身（1.956 / 7.824 / 15.648 GiB/rank）——**"状态多大，恢复就需要多大本地内存"是朴素实现的天花板**。论文提出 **BSR**：把"完整发现"与"本地驻留"分离——先用探针在 L1 中物化最小的可复用前缀（不落整个 hit），确认后通过**至多 W 个 chunk 的可复用窗口**安装状态。在有界辅助状态下，峰值恢复容量降至 **O(W)**，而总传输+安装工作量保持 **Θ(|S|)**（与状态大小线性）。由于可复用状态横跨异构 allocator 组与 TP rank，BSR 采用**请求级提交规则**：部分安装绝不暴露为有效复用前缀；失败时使已公告前缀失效、回退到更低有效档或确定性重算。实测：DeepSeek-V4-Flash + TP=2 双 DGX Spark 节点，干净 no-resume 扫描把外部状态从 1.956 增长到 31.277 GiB/rank，而 W=32 时实测 L1 RWS **恒定 500.75 MiB/rank**——**63.959x 的"外部状态/活暂存"比**；第二次全新 524K-token 运行重复验证最大状态接受结果。对 tier 与 rank 非对称故障的评测显示：要么完整复用、要么零外部复用后回退（无中间态泄漏）。配套 SSD 优化把 512K restore TTFT 从 **43.1 降到 17.6 秒**（-59%）且不改变 RWS。

### 2. 在线 KV-cache 调度的紧竞争比下界：理论上的"不可优化"定理

- **A Tight Linear Deterministic Competitive Ratio for Fully Online KV-Cache Scheduling**（[arXiv:2608.16944](https://arxiv.org/abs/2608.16944)，08-14，作者 Ian D'Ambrosio）: 针对 Jaillet et al. 提出的完全在线 LLM 批调度模型（不可抢占请求 + 增长中的 KV-cache 内存约束），此前已知：任意确定性算法的总端到端延迟竞争比为 **Omega(√n)**（下界），而朴素顺序策略给出平凡的 n 上界。本文**闭合该间隙**：设 R_det(n,M) 为恰好 n 个请求、内存 M 下的最优确定性竞争比，R_det(n)=sup_M R_det(n,M)，则对任意 n≥2 证明 **(n-1)/12 ≤ R_det(n) ≤ n**，即 **R_det(n)=Θ(n)**——完全在线场景下不存在亚线性竞争比的确定性调度器。下界构造：先释放一个填满内存的长请求、观察其确定性开始时间，再在长请求运行中途释放 n-1 个宽单 token 请求——短请求无法与长请求重叠，而事后最优调度在有价值时以相反顺序执行两组。硬实例使用显式固定内存 M=2(n-1)n。上界由统一因果串行策略实现。**精确模型、因果性论证、两个比较分支与量词顺序全部在 Lean 4 中机器验证**，并附精确有限控制与回放命令。这是推理调度领域少见的"定理级"结果——不是又一个启发式，而是给启发式的天花板画了条线。

## 📊 深度分析（本组视角，6 段）

### 分析一：KV 生命周期管理的"时间维度"——BSR 把恢复成本变成一等资源，与昨日四条路线合成完整治理框架

昨日（08-19）本组归纳了 KV cache 治理的四条路线：vToken（空间解耦：逻辑 token 活性与物理块放置分离）、GraniKV（结构适配：共享前缀连续 + 请求后缀细粒度）、Pallas（空间移动：跨节点预取迁移）、KV-Rescue（模型级补偿：信息缺口用 helper 补回）。**BSR 补上了第五条——时间维度：恢复（restoration）本身需要本地暂存资源，且这个成本与"保留容量"不成正比**。这是一个容易被忽略的第一性事实：分层 KV 系统把状态推向外层存储时，工程师习惯用"能保留多少 GiB"衡量系统能力，但"把状态取回来执行"需要一段生命周期重叠的本地 staging——朴素实现下恢复峰值等于状态本身（1.956 GiB 状态 → 2 GiB L1 才能恢复），这意味着**外部存储扩容并不自动转化为可恢复容量的增长**。BSR 的贡献在于把"发现"与"驻留"分离：探针物化最小前缀确认可复用性，然后通过 W 窗口流式安装——代价是恢复过程变成"多阶段确认"，收益是 63.959x 的外部/活暂存比与 W 有界的峰值恢复容量。**与 Pallas 对照可看出完整闭环正在形成**：Pallas 解决"状态如何跨节点移动"（迁移协议），BSR 解决"状态如何从慢层取回执行"（恢复协议）——两者共享同一个前提假设（KV 是跨层级、跨节点的可移动资产），也共享同一个安全原则（**部分状态不得对外可见**：Pallas 用切换时两段组装、BSR 用请求级提交规则与失败回退）。对超节点集群的工程含义很直接：**KV 分层系统的调度器不能只看"命中率/容量"，必须把"恢复延迟 + 恢复暂存峰值"纳入成本模型**——512K restore TTFT 43.1→17.6s 的 SSD 优化说明恢复路径的调优空间与推理路径同级。框架侧信号：LMCache（vLLM 生态的 KV 分层标准件）成为 BSR 的实验载体，说明 **KV 分层正从"缓存工具"升格为"有协议约束的分布式状态系统"**——这与 08-13 期 Mooncake/KV connector 生态观察同向。

### 分析二：调度理论的负面结果恰恰为工程方向背书——"不可优化"定理告诉我们应该优化什么

2608.16944 是一个罕见的"定理级负面结果"：完全在线（无先验、不可抢占、内存受限）的批调度下，**任何确定性算法的竞争比都是 Θ(n)**——n 个请求的最坏情况延迟劣化与请求数线性相关，不存在常数或对数竞争比的确定性策略。这个结果的工程价值不在"证明贪心不好"（这在直觉上不新鲜），而在**它划定了"无假设调度的理论天花板"，从而反证了工程上所有有效调度都必须引入结构假设**。回头看昨日收录的工程论文，三者恰好各自引入一类假设：P-PAS 引入"压力可观测"（按 prefill/decode 并发动态调 MBT 预算）、TEMPO 引入"成本结构可建模"（max-affine 双 regime 相位图）、Multi-Tier SLA 引入"SLA 谱系可表达"（4 层优先级最优）。**竞争比定理与这三篇的关系是"不可能性 ↔ 可能性"的镜像**：没有假设 → 线性不可救；有可观测/可建模的假设 → 可以做到跨负载最优。这给推理系统架构一个明确的取舍准则：**调度器的设计预算应该花在"获取高质量假设"（遥测、成本模型、负载画像）上，而不是花在"更聪明的无假设启发式"上**——后者的理论收益是零（Θ(n) 下界），前者的收益在昨日论文中已量化到 1.3~8.3x。另一个值得注意的元信号是 **Lean 4 机器验证**：一个调度定理连同"因果性论证、比较分支、量词顺序"被形式化验证——与 08-19 期 Integer Alibi 的 kernel 级验证、vLLM 的 dtype 匹配保护同属"正确性验证下沉"趋势，只不过这次下沉到了**算法理论层**：推理系统的基础设施论文开始具备可机器检查的证明，这正在改变"调度算法论文"的证据标准。

### 分析三：四框架同步空窗 = 8 月中旬大版本潮后的"消化期"确认，但空窗的性质不同

本期最显著的工程信号是**四框架（vLLM / TRT-LLM / PyTorch / SGLang）同时无新版**，且 vLLM 主分支 08-19 的 15 条 commit 全是 bugfix / CI / 量化修复，无一条新功能。这与 08-19 期判断的"静默窗口"（学术侧密集提交 vs 工程侧消化）完全互证——只是现在可以把"消化期"刻画得更精确：**v0.27.0（08-10）与 rc24（08-12）两周前同时落地了 Kimi K3 全栈 + DSv4 优化序列 + PyTorch 2.13/FA4 SM100 三件大事，之后框架团队进入的是"修 bug、补测试、回滚风险内核"的收敛阶段**，而不是"准备下一个大功能"的积累阶段。三个证据：① Gemma-4 FA4 FP8 kernel 被 revert——说明 08-10 大版本合入时带进来的内核在集成测试中不达标，回滚比修补更优先（正确性 > 性能）；② OCP MX MoE 的 mxfp6 QDQ"静默跳过"修复——量化路径的错误是"不报错但算错"，这类 bug 的优先级在维护期会被提到最高；③ ROCm 侧一天 5 条测试/修复 commit——**并行平台（AMD）的测试覆盖在补课**，这与 v0.27.0 同时支持 sm_107/ROCm/XPU 的"多硬件同日落地"压力直接相关：功能扩张速度超过了验证能力，维护期正是验证补课期。对下游用户的操作含义：**未来 2~3 周升级框架需谨慎**——v0.28.0（预计 9 月初）之前的版本处于"修复但未发布"状态，主分支已修的问题要等下一个 release 才拿到；而 9 月初的 v0.28.0 大概率携带大量 kernel/量化修复，届时评估"是否值得升级"时应把 08-10~08-19 期间暴露的正确性风险（FA4 FP8 revert、MX QDQ、混合 dtype）列为重点回归项。

### 分析四：内核质量控制成为框架竞争的新前线——"快速合入 + 快速回滚"模式的代价与收益

把本期两个看似孤立的信号放在一起——vLLM 主分支 revert Gemma-4 FA4 FP8 内核（#52987）、以及 08-19 期 Integer Alibi 证明"同接口内核输出不可 bit 对齐"——可以读出一个结构性事实：**推理框架的内核开发已经从"慎重合入"转向"快速合入、验证后回滚"的 DevOps 模式，代价是正确性风险后置到集成阶段**。收益是明显的：v0.27.0 能在模型发布两周内全栈落地 Kimi K3（内核/前端/量化/投机解码），这种速度在"每个内核都经过完整验证再合入"的模式下不可想象；代价则是 FA4 FP8 这类"合入时看起来对、集成时暴露问题"的回归会不定期出现，且**用户侧的故障表现往往是静默的**（MX QDQ 跳过不报错、mixed-dtype 输出 `!!!!!`、INT8 内核间分歧）。这对依赖框架的生产系统意味着三层防御：① 版本锁定 + 发布说明回归清单（vLLM 的 revert 记录是最好的回归清单来源）；② 量化/内核敏感负载的**黄金样本对比测试**（同一模型同一输入，新旧版本输出逐 token 比对）；③ 关注框架的"revert/静默修复"commit 而不只是 feature commit——**正确性 commit 是质量信号，feature commit 是能力信号，生产选型两者都要看**。从 08-18 期到本期的连续观察看，vLLM 正在用"commit 透明性"承担内核质量风险的管理职能——对用户这是好事，但前提是用户端有机制把这些信号转化为自己的回归测试计划。

### 分析五：BSR 的"恢复工作集"概念在分布式系统理论中的坐标——检查点/日志/提交规则的经典回归

把 BSR 放在分布式系统四十年的恢复理论谱系里看，会发现它的三个核心机制都有经典原型，但被重新组合到了一个新场景。① **探针物化最小前缀 = 检查点验证（checkpoint validation）**：数据库恢复在 redo 前先验证检查点的可读性/完整性，BSR 用探针确认"可复用前缀"而非盲目全量恢复——区别在于验证对象从"磁盘页"变成"KV 前缀的 allocator 组 × TP rank 组合"，验证粒度细化到跨 rank 一致；② **W 窗口流式安装 = 日志先行（write-ahead）+ 有界重放窗口**：BSR 的"至多 W 个 chunk"上限对应日志恢复中的"重放窗口有界"原则——恢复成本不随总状态线性增长（Θ(|S|) 的总工作量仍在，但**峰值**暂存被压到 O(W)），这正是把"恢复的空间复杂度"从"恢复的时间复杂度"中分离出来的系统级表达；③ **请求级提交规则 = 两阶段提交的可见性语义**：部分安装不暴露为有效前缀、失败回退到低档或重算，等价于事务恢复中"部分提交不可见、失败回滚到安全点"的原子性要求。**BSR 的原创性不在发明这些机制，而在证明它们可以套到"KV cache 恢复"这个新资源上，并把收益量化到 63.959x**。这个坐标定位对框架选型有意义：KV 分层系统（LMCache/Mooncake 系）正在经历分布式数据库 80 年代经历的"从缓存到状态管理"的成熟过程，**"恢复协议"将成为 KV 分层的标配能力**——下一个可预期的新增是"恢复优先级"（哪些前缀值得快速恢复、哪些可接受重算），这与 08-19 期 KV-Rescue 的"信息缺口 vs 能力缺口"判断形成调度层的镜像。

### 分析六：vLLM 发布节奏的定量画像——9 天空窗在全年 24 个 release 中的位置

用 GitHub API 拉取 vLLM 2026 年全部 24 个 release 做节奏画像：**全年平均约 9 天一个 release**（含 patch），major/minor 级版本（v0.14→v0.27）平均间隔 **11.8 天**，patch 级（v0.14.1/v0.15.1 等）平均间隔 **7.2 天**。几个结构特征：① **大版本 + 立即补丁模式**是常态——v0.25.0→v0.25.1 间隔 3 天、v0.27.0→v0.27.1 仅 1 天，说明"大版本发布后 1~3 天内打补丁"是 vLLM 的固定节奏，当前 v0.27.1 后 9 天无任何 release，**已经超过 patch 平均间隔**，说明团队在有意收敛（不再发 patch，直接等 v0.28.0）；② **major/minor 间隔的分布**：最短 3 天（v0.18.1→v0.19.0，09-31~04-03 的快速推进期）、最长 21 天（v0.15.1→v0.16.0，02 月春节效应？），历史 75 分位约 14 天——**当前 v0.27.0（08-10）已 10 天，若按 75 分位节奏，v0.28.0 的窗口是 08-20~08-31，即未来 1~2 周内随时可能发布**，这比此前"9 月初"的估计更紧；③ 与模型发布耦合的版本（v0.27.0 对齐 Kimi K3）通常伴随 500+ commits 的大版本，而维护期版本（如当前）则以 patch/修复为主——**commit 量的波峰波谷比 release 日期更能反映框架的生命周期相位**。对运维的量化含义：vLLM 用户若保持"跟随最新 major"策略，平均每 12 天就要评估一次升级（含回归测试），这在 8 月中旬的大版本潮后应该放缓到"评估 v0.28.0 一次"——与 08-19 期"每两周一个大版本需持续跟进"的判断互相印证，但本期数据给出了更精确的节奏基线。

## 🎯 对基础设施团队的落地建议（本期增量映射）

1. **KV 分层容量规划要加"恢复视角"**：BSR 证明"能存多少"≠"能恢复多少"——如果集群用 LMCache/Mooncake 类分层 KV，规划外部存储容量时必须同时规划恢复路径的本地暂存与恢复延迟预算；朴素实现下 15.6 GiB 状态需要 16 GiB L1 才能恢复，BSR 类方案可压到 500 MiB 量级（63.959x）。**选型清单新增一项：分层 KV 方案必须说明恢复暂存峰值与恢复延迟的可控性**（探针/窗口/提交规则），否则长上下文会话的"换出再换入"会成为隐性延迟炸弹
2. **调度器选型先问"假设是什么"**：16944 的 Θ(n) 下界意味着——无先验的确定性调度在理论上不可优化，任何声称"普适最优"的调度器都不成立；有效调度的价值全部来自结构假设（负载压力可观测 / 成本模型可建模 / SLA 谱系可表达）。**评估调度方案时把"它利用了哪个可观测信号"作为第一问**，而不是比较 benchmark 数字——TEMPO 的相位图主张（预测何时会赢）应成为评估标准
3. **升级节奏与框架相位对齐**：vLLM 平均 11.8 天一个 major，但 8 月中旬大版本潮（v0.27.0/rc24）后进入"正确性收敛期"（主分支 15 条 commit 全是 bugfix/CI/ROCm + FA4 FP8 内核 revert）——**建议把 v0.28.0 作为下一评估节点（窗口 08-20~08-31）**，回归重点：FA4 FP8 revert 是否回归、MX QDQ 静默跳过修复、ROCm 测试补课；在 v0.28.0 发布前不追主分支（修复未发布）
4. **把框架的 revert/静默修复 commit 纳入质量雷达**：vLLM 的"内核快速合入 + 验证后回滚"模式使正确性风险后置——生产团队应订阅框架 commit 流中 `[Bugfix]` `Revert` `[Quantization]` 前缀条目，作为升级决策与黄金样本回归的输入（正确性 commit 是质量信号，feature commit 是能力信号）
