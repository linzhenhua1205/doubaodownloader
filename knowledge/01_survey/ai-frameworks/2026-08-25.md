## 🆕 本期核心事件一：vLLM Blog 08-23 发布 AMD 投机解码全景长文

### 1. 发布概况——五种投机方法 × 九模型 × AMD 双平台的首个系统性对照

- **来源/标题**: Exploring Speculative Decoding in vLLM on AMD GPUs（[vLLM Blog](https://blog.vllm.ai/blog/2026-08-23-speculative-decoding-amd-gpus)，2026-08-23，242 min read）
- **要点**: vLLM 团队与 AMD 合作，在 **AMD Instinct MI300X 与 MI355X（ROCm 平台）** 上对五种投机解码方法——**Native MTP、Gemma 4 MTP、EAGLE-3、DFlash、DSpark**——做了首个系统性的任务级基准对照。覆盖 9 个目标模型家族（Gemma 4 E2B/E4B/12B/26B-A4B/31B、Qwen3-8B、Qwen3.5-27B/-122B-A10B、Qwen3.6-27B/-35B-A3B、Kimi-K2.5、MiniMax-M3-MXFP8），用任务基准（GSM8K/MATH500/HumanEval/MBPP）而非随机 token 序列评估接受行为
- **方法差异核心（原文第一性原理）**: 五种方法的分野在于**草稿组件如何从目标模型获取信息、候选 token 是顺序生成还是并行生成**——Native MTP 用模型自带的多 token 预测头顺序生成；Gemma 4 MTP 是 Google 训练的 MTP 头（对 Gemma 4 系列）；EAGLE-3 用训练时测试（TTT）微调特征映射顺序生成；DFlash 用块扩散并行生成整块草稿；DSpark 用置信度调度验证预算（半自回归分块 draft + 按置信度定 verify 窗口）。文章指出投机解码不改变目标模型输出分布——draft 只是候选，目标模型验证后才 commit

### 2.5 五种投机方法的工程细节与调优方法论（文章第 4/8/9 节展开）

- **五种方法的信息流与生成方式对比**:

| 方法 | draft 信息来源 | 候选生成方式 | 内存特征 | 供给方 |
|:--|:--|:--|:--|:--|
| Native MTP | 目标模型自带 MTP 头 | 顺序 | 无独立 checkpoint，可与目标共享 embedding/输出头 | 模型内建（Qwen3.5/3.6 等） |
| Gemma 4 MTP | Google 训练的 MTP 头 | 顺序 | 加载额外 draft 权重 | Google（Gemma 4 E2B~31B） |
| EAGLE-3 | 训练时测试（TTT）微调特征映射 | 顺序 | 加载额外 draft 权重 | LightSeek / Red Hat / DeepSeek / Inferact |
| DFlash | 块扩散 | 并行（整块草稿） | 加载额外 draft 权重 | Z-Lab / Red Hat / DeepSeek |
| DSpark | 半自回归分块 + 置信度 | 混合（并行预测 + 轻量顺序校正） | 加载额外 draft 权重 | Red Hat / DeepSeek / Inferact |

- **内存考量**: Native MTP 不加载独立 draft checkpoint（可与目标模型共享 embedding 表或输出头）；其余四种需预留额外 GPU 内存，实际开销取决于 draft 组件大小、数值精度、TP 配置与运行时 buffer
- **调优核心结论——投机解码是运行时优化而非固定配置**: 最优 `num_speculative_tokens` 取决于"被接受 token 数"与"draft+verify 开销"的权衡。观测信号四件套：**吞吐、平均接受长度（MAL）、总体接受率、逐位接受率（per-position AR）**。逐位接受率是调提案长度的关键——若前几位高频接受而后几位贡献极低，缩小提案窗口可避免无效 draft 工作
- **N sweep 实测规律**: 数学基准（GSM8K/MATH500）常在中深提案长度达峰——Qwen3.5-122B-A10B native MTP 吞吐增至 N=7，DFlash 高频出现在 N=7 或 N=11；代码基准（HumanEval/MBPP）偏好中等长度——代码有可预测局部结构，但格式/标识符/实现选择会使看似合理的延续发散（第 9 节原文）。**跨负载最优 N 不守恒，必须按负载 sweep**
- **speculator 训练工作流**（面向新目标模型的完整链路）: ① 用**目标模型本身**生成代表性 prompts 的响应（tokenizer/chat template/thinking mode/生成配置须与部署一致——"对既有响应套目标模型 tokenizer 不会使其 target-specific"，原文明确否定此捷径）；② 选 hidden-state 获取模式——**Online**（vLLM server 即时生成、用完即弃，省磁盘但需目标推理+训练同时占资源）/ **Offline**（先存盘再训练，训练期 GPU 全释放但需大存储）/ **Hybrid**（首 epoch 生成并缓存、后续复用）；③ 训练后以 accepted length / acceptance rate / draft latency / GPU 内存 / 端到端吞吐为验收指标——**"training loss 不足以评判结果"**；④ 同一目标模型、同一生成模式、同一代表负载复测

### 2.1 KV cache 量化：从"离线平均验证"走向"运行时逐请求证明"（WitCert）

- **来源/标题**: WitCert: Sound Runtime Risk Observability and Gating for KV-Cache Quantization（[arXiv 2607.28699](https://arxiv.org/abs/2607.28699)，2026-07-30）
- **要点**: 现状是 KV cache 量化只用离线 benchmark 平均分验证——**部署中的系统无法判断压缩此刻正在损害哪个请求**。WitCert 给出可证明健全的运行时仪表（"DTrace for KV quantization"）：对每 (layer, head, step) 计算精确与压缩注意力的总变差（TV）上界。两层仪表：① 确定性 band-norm-witness 界——对任意 cache-preserving 黑盒量化器、任意查询健全（worst-case Cauchy–Schwarz + RoPE band-unitarity）；② 更紧的概率证书——针对受控 subtractive-dithered INT8 量化器，在显式请求级失败预算下成立（核心定理 Lean 4 机器验证）
- **实测效果**: 仪表通过 env-guarded patch 进入 **SGLang 在线 serving**；meter-driven gating（witness 饱和处按风险排序、可证明处给证书）在 benchmark 规模恢复质量底线——**raw-cast FP8 在 hard RULER 任务从 22.8 恢复到 79.7**（与未压缩差距显著缩小）
- **信号解读**: 这是"KV 量化安全护栏"从学术原型到框架集成的落地案例。因果链：离线平均 → 无法定位受损请求 → 逐请求 TV 上界 → 风险分级 gating → **量化深度从"静态选择"变成"运行时自适应"**。对生产部署的意义：KV 量化（尤其 FP8/INT4）的省显存收益可以保留，同时把"损害不可见"风险转为"逐请求可观测"

### 2.2 稀疏 serving 的安全反面：激活稀疏性成为 token 提取侧信道（SparSEEty）

- **来源/标题**: SparSEEty: Extracting Tokens from Sparsity-Exploiting LLM Serving Systems via Deterministic Side Channels（[arXiv 2608.02995](https://arxiv.org/abs/2608.02995)，2026-08-04）
- **要点**: 现代 LLM 的激活稀疏性让 serving 系统跳过非激活神经元的权重访问与计算——但**这种优化创造了输入依赖的权重访问模式，可经侧信道泄露**。SparSEEty 是首个端到端 token 提取攻击：① 用权重访问侧信道构造神经元激活 oracle；② 反演激活轨迹重建输入 token。攻击在 **Intel TDX 机密虚拟机内的 LLM serving** 上实例化，解决三个挑战：CVM 暴露侧信道的 oracle 构造、激活监控的推理期开销抑制（隐蔽性）、部分二值激活轨迹的精确反演
- **信号解读**: 与 08-10 期收录的 "Governing the KV Cache: Preventing Timing Side-Channel Leakage"（2608.09225）同属 serving 安全主线，但攻击面不同：前者是 KV cache 时序侧信道，后者是**激活稀疏权重访问侧信道**。稀疏性优化（MoE 路由跳过、ReLU 稀疏）在性能与安全之间制造了新张力——**"省算力的特性"同时也是"泄露的通道"**。对机密计算（TDX/SNP/CVM）内跑稀疏 serving 的部署是直接风险提示

### 2.3 能源感知 serving：证据门控 + 功率调节旋钮（TokenPowerSandbox / Smoothing the Ramp）

- **来源/标题**: TokenPowerSandbox: Evidence-Gated CPU-First Screening for Energy-Aware LLM Serving（[arXiv 2608.18149](https://arxiv.org/abs/2608.18149)，2026-08-11）
- **要点**: 能源感知 serving 需要对比真实请求形态下的配置，但目标 GPU 全量 profiling 昂贵，而廉价预测器在测量范围外可能"危险地自信"。TokenPowerSandbox 是证据门控工作流：**可解释 CPU 驻留投影器 + 短目标 GPU 探针 + 全负载验证 + freeze-before-measurement 防篡改溯源**。H100 80GB 上 vLLM 服务 Qwen2.5-7B-Instruct：3 次锚定重复 + 6 个开发负载标定，盲测 holdout + 预声明 no-refit 共 51 次 freeze 后运行——**Energy MAPE 6.23%/7.35%，Spearman 秩相关 0.976/0.933**。关键反面教训：预声明 TTFT gate 在并发 4 通过（9.27% MAPE）但在并发 <4 触发弃权（64.80%）——**能源准确率不能认证延迟**，两类指标须分开验证
- **来源/标题**: Smoothing the Ramp, Not the Peak: Scheduling-Induced Power Dynamics of LLM Inference and Their Grid-Scale Consequences（[arXiv 2608.01250](https://arxiv.org/abs/2608.01250)，2026-08-02）
- **要点**: 用真实 GPU 功率轨迹证明 **chunked prefill（生产 LLM serving 默认部署的延迟优化技术）是可控的功率爬坡速率调节旋钮**：峰值功率基本不变，但平均 ramp rate 显著下降，且该收益随系统饱和单调增长——并发从轻载 7.0% 到重载 **34.6%** 的 mean-ramp 降幅；长提示（"whale"）请求占比高时达 **42.6%**。进一步把单 GPU 机制翻译为电网级运营量——regulation-reserve 采购，用 model-free bootstrap 直接重采样实测功率数据求解机会约束问题
- **信号解读（两条合看）**: 能源 serving 正在从"事后测量"走向"事前可证"——TokenPowerSandbox 解决"如何可信地比较配置"，Smoothing the Ramp 发现"调度策略本身就是功率整形工具"。对数据中心规划者的含义：**LLM 推理负载的功率动态可由 serving 层调度（chunked prefill）整形**，无需额外硬件——这为 08-25 期 power-architecture 组的供电设计讨论提供了软件侧调控维度

### 2.4 其他补漏：trace 诊断 / AMD kernel 汇编级优化 / VLA token 压缩

- **来源/标题**: Diagnose Before You Compress: Prediction-Independent Bottleneck Witness Refinement for LLM Serving Traces（[arXiv 2608.00423](https://arxiv.org/abs/2608.00423)，2026-08-01）
- **要点**: 生产 LLM serving 的 trace 重放随配置组合指数变贵，现有 trace 缩减只保 workload 分布或代表性请求，但**瓶颈暴露型负载可能稀有且不具代表性**；且"用预测瓶颈当真值"会造成循环评估。提出 Bottleneck-Preserving Witnessing（BPW）：响应盲 workload 特征提名候选（覆盖 scheduler/prefill/decode/KV-cache 瓶颈）→ 覆盖率优先的序列构造（超边组织多组件提案）→ 独立瓶颈真值验证。**服务于 serving 配置比较的诊断基础设施**
- **来源/标题**: AsmEvo: Agentic Assembly-Level Optimization of AMD GPU Kernels with Functional Equivalence Verification（[arXiv 2608.20711](https://arxiv.org/abs/2608.20711)，2026-08-21）
- **要点**: 现有 LLM kernel 优化器/autotuner 都作用于 CUDA/Triton/HIP 源码，AsmEvo 针对**更严格的设定：已编译的 AMDGPU code object**——部署二进制是唯一行为 oracle。流程：重构可重汇编表示 → 长视界 agent 提出低层编辑 → 重建 ABI 保持的优化对象 → 与 K0 在相同 launch 下差分验证才接受。MI308X 上 **29/30 个 KernelBench kernels 改善，1.35× 几何平均、3.88× 最大加速**。汇编级优化 + 差分验证 = 无源码场景的性能回收路径
- **来源/标题**: Just Noticeable Difference Modeling for Token Compression in Vision-Language-Action Models（[arXiv 2608.21247](https://arxiv.org/abs/2608.21247)，2026-08-21）
- **要点**: 现有 VLA token 压缩（token pruning / KV-cache reuse）用冗余度或重要性线索（视觉相似度/注意力分数/显著性）引导，但这些**只是安全压缩关键因素的间接度量**——"一个 token 变化多少才会导致下游动作不可接受偏差"。提出 Action-JND：把人类视觉系统的 JND（最小可觉差）概念推广到具身感知，以语言条件化 VLA 策略的动作响应定义可觉性。token 压缩从"启发式重要性"走向"接收者依赖的容差建模"

## 🧠 分析段落（因果链 / 对比 / 原理）

### 分析一：投机解码生态的"草稿供给"分化——框架竞争从内核延伸到模型供给层

08-23 的 vLLM AMD 长文最值得注意的不是性能数字本身，而是其附录呈现的**草稿模型供给生态**：Google 官方 MTP checkpoints、LightSeek 的 Kimi EAGLE-3、Red Hat AI 的跨家族三方法集合、Z-Lab 的 DFlash、DeepSeek 的 DeepSpec 三方法集合、Inferact 的 MiniMax/Kimi 草稿——六个独立组织在为一个"框架特性"生产模型。这是投机解码从"框架内置工具"走向"独立模型品类"的标志：草稿 checkpoint 的训练（hidden-state 提取、目标层选择、draft 网络深度）已经复杂到需要专门供给方。对框架选型的含义：**投机解码的竞争力 = 内核实现 × 草稿模型覆盖面**，vLLM 通过开放 Speculators 训练工具链（08-28 期已收录）把"覆盖"变成生态竞赛，而 SGLang 侧 DSpark 由 LMSYS 自己推进、TRT-LLM 侧 MTP 由 NVIDIA 模型侧内建——三种供给模式（开放生态/自研/模型内建）并行，后续期次值得跟踪哪种模式在草稿模型丰富度上胜出。

### 分析二：KV 量化与稀疏优化的"可证明性拐点"——serving 优化的安全与信任约束

本期补漏的两篇（WitCert 的逐请求 TV 上界、SparSEEty 的激活侧信道攻击）指向同一拐点：**serving 层激进优化（KV 压缩、稀疏跳过）在性能收益兑现后，正在被安全/可靠性约束重新审视**。因果链：KV 量化省 2-4× 显存 → 离线平均分验证无法定位受损请求 → WitCert 提供逐 (layer, head, step) 的 TV 上界与 Lean 4 机器验证证书 → 量化从"静态深度选择"变为"运行时门控"。稀疏侧同理：激活稀疏跳过省算力 → 输入依赖的权重访问成为侧信道 → TDX 机密计算内的 token 提取攻击成为现实威胁。**这两条线合流的判断是：2026 下半年 serving 优化的验收标准将从"吞吐/延迟"扩展为"吞吐/延迟 × 可证明性/机密性"**，与 08-10 期收录的 KV cache 时序侧信道（2608.09225）共同构成框架安全面的完整拼图。框架侧落地信号：WitCert 已通过 env-guarded patch 进入 SGLang——"安全仪表"正在成为框架特性而非论文概念。

### 分析三：能源感知 serving 的"软件整形"范式——调度策略作为功率基础设施

Smoothing the Ramp 给出了一个反直觉但可验证的结论：**chunked prefill（为延迟而生的调度技术）同时是功率爬坡的调节旋钮**——峰值功率不变、ramp rate 降 7.0%→34.6%（随并发饱和）乃至 42.6%（whale 负载），且收益单调随饱和增长。原理层面：长提示的 prefill 计算被切成小 chunk 后，GPU 功耗的上升沿被"摊薄"到多个小台阶，峰值由计算总量决定、爬坡速率由调度粒度决定。对数据中心的意义：**LLM 推理负载的功率动态可以由 serving 层软件整形，无需 PSU/储能硬件投入**——这与 power-architecture 组同日讨论的供电设计形成软件/硬件互补。TokenPowerSandbox 则补上了方法论缺口：如何可信地比较配置（CPU 投影 + 短探针 + freeze 溯源，Energy MAPE 6.23%），并给出关键边界——**能源指标不能认证延迟指标**（TTFT gate 在低并发触发弃权），能源优化不能以牺牲 SLO 可证性为代价。

### 分析四：AMD 双平台验证的扩散——"性能优化不分 ISA"成为框架基线

综合本期 vLLM AMD 长文与近期多期信号（08-13 vLLM ROCm gfx1250 使能、07-13 EAGLE3 on AMD、08-24 SGLang K3 在 MI35x 验证、08-22 期 AsmEvo 同批 AMD kernel 汇编优化），可以确认：**AMD ROCm 已从"可运行"进入"性能等价"阶段**。投机解码 2.87×（DFlash/MATH500）与 NVIDIA 侧的 SOTA 处于同一量级，且 MI308X 汇编级优化（AsmEvo 1.35× 几何平均）证明无源码内核仍有显著性能空间。对框架选型的含义：**双平台（NVIDIA+AMD）性能一致性正在成为头部框架的默认承诺**，单一 ISA 优化的竞争力窗口在收窄；对用户的含义：AMD 部署不再需要"性能打折"预期，但需按负载实测（投机增益随模型规模/负载形态波动大，Qwen3-8B 仅 1.08~1.63× vs Gemma-26B 2.6~2.9×）。
