### 1. FlashPrefill V2：稀疏 prefill 从"算法原型"走向"生产级注意力后端"

- **FlashPrefill V2: Block-Sparse Prefill Attention for Long-Context LLM Serving**（[arXiv:2608.19758](https://arxiv.org/abs/2608.19758)，08-20，作者 Qihang Fan / Huaibo Huang / Zhiying Wu / Bingning Wang / Ran He）: 长上下文建模的注意力二次复杂度瓶颈集中在**计算密集的 prefill 阶段**。V1（FlashPrefill）用"瞬时模式发现 + max 动态阈值"做稀疏化，但只是算法原型。**V2 沿三个维度产品化**：① 引入**均值校正项**（mean correction term）抑制近似误差，极端稀疏度下性能退化仍可控；② 用 **PackGQA 内存访问 + warp specialization + pingpong pipelining** 重设计稀疏注意力算子，**完全对齐 FlashAttention-3/4 实现**，并支持 FP8 推理；③ **原生支持 paged KV cache 与 continuous batching**，可作现代推理框架（如 SGLang）的注意力后端。NVIDIA H20 GPU 评测（最广泛部署的推理加速器之一）：128K 上下文长度下相对 FlashAttention-2，FP8 精度最高 **47.26x**、BF16 最高 **27.19x** 加速；FP8 下相对 FA3/4 对齐的稠密基线仍有 **30.49x** 加速。**这是稀疏 prefill 首次具备"生产部署形态"的完整能力集（paged KV + 连续批处理 + FP8 + 框架集成）**

### 2. CacheRoute：规划式前缀亲和路由——把缓存命中率从 64% 拉到 93%

- **CacheRoute: Planned Prefix-Affinity Routing for Large-Scale LLM Serving**（[arXiv:2608.19677](https://arxiv.org/abs/2608.19677)，08-20，作者 Huang Cheng）: 前缀缓存**只在重复请求回到仍持有该前缀 KV 的服务器时**才避免 prefill。缓存无感知的负载均衡（cache-blind balancing）打散复用流量；固定亲和（fixed affinity）保住复用但会压垮单机。**CacheRoute 用周期性路由计划**化解两难：高请求率 key 进入稳定的 warm set，按期望负载放置分配；热 key 可多目的地（本实验全部单目的地）。**Llama-3.3-70B fp8 × 60 H100** 实测：3.5s p99 SLO 下维持 **176±11 QPS**，是 5 个基线中最强者（2.3x）；KV cache 命中率从 cache-blind balancing 的 **64.1±1.3% 升至 93.2±0.5%**。两个 32B 工作负载提供反例：亲和恢复的 KV 工作量太少时，残余负载偏斜会削减甚至抹掉增益——因此作者建议**任何部署先做 shadow replay 门控，不要仅凭工作负载统计直接启用亲和路由**

### 3. ReCache：tool-augmented agent 的 KV 表示复用——TTFT 提速 3.65x、KV 内存 -92.4%

- **ReCache: Efficient KV Cache Reuse and Compression for Tool-Augmented LLM Agents**（[arXiv:2608.19662](https://arxiv.org/abs/2608.19662)，08-20，作者 Yichu Fang / Sitong Wei / Haozhe Hu / Xiaoyu Shen）: agentic 模型在请求间反复编码**工具与技能 schema**，但组合顺序不同，标准前缀缓存无法复用其 KV 状态。**ReCache 把资源表示独立缓存**：① **resource-wise attention** 移除跨资源交互、分配资源局部位置，产生**组合不变（composition-invariant）的 KV 块**；② 用贡献度选择把资源可见性限制到 layer-KV-head-group 路由；③ 结构化 + 语义剪枝只保留调用关键字段。7 个公开 tool/skill 数据集基准：resource-wise attention 与稠密调用性能持平（**82.3% vs 82.4% Inv-F1**），同时 TTFT 提速 **3.655x**；完整框架减少 **92.43%** 的 KV tensor 内存分配，attention 加速 **1.423x**。代码开源：https://github.com/EIT-NLP/ReCache。**核心洞察：把"可复用的 schema 编码"与"选择性的资源访问"分离，是 agentic 推理降本的关键结构手段**

### 4. FleetSieve：决策关键型 profiling——为 SLO 感知的集群配置省掉 6.9% 测量

- **FleetSieve: Decision-Critical Profiling for SLO-Aware LLM Fleet Configuration**（[arXiv:2608.19659](https://arxiv.org/abs/2608.19659)，08-20，作者 Huang Cheng / Scott Zhang / Aubert Li）: 为 LLM 服务集群选 TP 度（tensor-parallel degree）与副本数很难：**性能对 TP 不单调、可行选择随负载漂移**。穷举 profiling 能解决不确定性但测了大量不影响最终资源分配的配置。**FleetSieve 按测量对"资源耦合的 SLO 感知决策"的期望影响选测量点**：联合建模容量与尾部延迟、比较保守/激进分配、决策差距低于容差即停。31B 开源模型 + 固定 H100 测量网格：**22,200 GPU-seconds** 达 oracle 聚合决策，比均匀随机 profiling 少 **6.9%**；200 个随机 reveal 顺序下平均省 **5.4%**（95% bootstrap CI: 3.5-7.2%）；Chat 场景固定比较省 21.5%。联合容量/尾部建模还避免了选中一个 **46.4 秒 p99 违约 30 秒 SLO** 的配置。16-GPU 分配下错误稀疏 profile 决策最多损失 1.93 req/s 与 12.4 个百分点的 max-min 满足率

### 5. Axon DSL：write-once run-everywhere——一套模型定义编译到 vLLM/PyTorch/JAX/MLX

- **Write Once, Run Everywhere: The Axon DSL for Shape-Safe and Framework-Agnostic LLM Architectures**（[arXiv:2608.19889](https://arxiv.org/abs/2608.19889)，08-20，作者 Jacob Nielsen / Danial Namazifard / Lukas Galke Poech / Peter Schneider-Kamp）: 开源 LLM 生态"事实上依赖单一平台"（PyTorch/Transformers）。Axon 是**强类型、Haskell 式语法的领域特定语言**：以语言规范而非某框架愿景为协作基础，模型定义可自动编译为 PyTorch、PyTorch+Triton、JAX、MLX、**vLLM** 的独立实现。135M~32B 模型 467 个推理基准实验：相对 Transformers 参考实现，median 加速 **PyTorch +7% / PyTorch+Triton +12% / JAX +91% / MLX +107%**；作为**原生 vLLM 架构（PagedAttention + KV-cache）部署时 median 加速 58%**。**价值不在"又一个 DSL"，而在把 vLLM 纳入"编译目标"阵营——推理框架开始拥有独立于训练框架的模型前端**

### 6. Learning how to Forget：用微调让模型与稀疏 KV 策略共适应

- **Learning how to Forget: Fine-tuning for Long-Context Sparse Attention**（[arXiv:2608.19920](https://arxiv.org/abs/2608.19920)，08-20，作者 Matthias Seeger / Zeyu Zhang / Vihang Patil / Konstantinos Benidis / Sebastian Schelter，Amazon/AWS）: 大量工作用稀疏注意力做 KV cache 选择/压缩以支持长上下文推理，但策略（如 H2O）通常**强加在已训练模型上**，模型未与策略共适应。本文给出**适用于任意 KV cache 策略的稀疏注意力微调方法**：单块 **A100 40GB** 即可运行（中等硬件预算），让模型与策略 co-adapt，**常优于用精确注意力（序列并行）训练的模型**。配套实现：H2O 稀疏注意力的高效实现 + 专用 scaled dot product attention kernel；发布开源库 **KeysAndValues**（https://github.com/awslabs/keys_values）覆盖长上下文推理与微调。**方向意义：稀疏化从"推理期补救"上移到"训练期联合优化"——模型权重开始为特定 KV 策略而生**

### 7. FIBER：线程-寄存器解耦的 GPU 执行模型——Ampere 端到端 2.25x

- **A Thread-Register Decoupled GPU Execution Model for Efficient Tensor Computation**（[arXiv:2608.19628](https://arxiv.org/abs/2608.19628)，08-20，作者 Zihan Liu / Jingwen Leng / Yangjie Zhou 等，上海交大团队）: 现代 GPU 的 Tensor Core 吞吐持续增长（操作数供给从 Ampere 的寄存器制演进到 Hopper/Blackwell 的**去冗余、内存制**），但完整 tensor 计算流水线的编排仍受两大瓶颈制约：**固定并行度**与**粗粒度调度**——由"GEMM 与非 GEMM 操作交错"的现代 AI 负载暴露。**FIBER** 扩展 GPU SIMT 模型：基本执行实例 **fiber** 与私有寄存器所有权解耦，只携带最小控制状态、通过共享视图访问 SM 寄存器——实现动态并行度缩放、细粒度寄存器级数据流调度、矩阵操作数供给的去冗余替代。扩展 ISA、微架构与编译器实现共享寄存器寻址、无冲突操作数投递、fiber 程序映射。混合精度 LLM serving 场景：**Ampere 端到端 2.25x**（原始 FP16 计算 1.15x）、Hopper 1.8x、Blackwell 2.09x，kernel 级最高 2.49x。**这是执行模型层面的"调度单位"变革——与算子调度/内核融合形成互补的第三优化维度**

### 8. HYDRA：异构 chiplet 设计空间探索——Transformer-Mamba 混合 LLM 的架构-运行时协同

- **HYDRA: A Heterogeneous Chiplet DSE Framework for Serving Dynamic Hybrid LLM Workloads**（[arXiv:2608.19395](https://arxiv.org/abs/2608.19395)，08-19，作者 Jiahao Lin / Alish Kanani / Sangwan Lee / Jaehyun Park / Umit Ogras）: 混合 Transformer-Mamba LLM 增强长上下文效率，但其异构计算/通信模式让硬件加速复杂；chiplet 架构提供集成专用计算与存储单元的扩展路径，但**静态架构配置 × 动态运行时策略的设计空间爆炸**。HYDRA 联合探索 chiplet 组成、放置、片间带宽供给、动态批处理与运行时调度：集成**通信感知放置、动态批处理、弹性任务调度、快速 Markov 性能估计器**（捕获多租户运行时动态）。全负载平均 **1.55x 吞吐、TTFT 降低 43.7%**，吞吐增益最高 2.3x（相对 SOTA 基线）。**结论：架构与运行时策略的协同设计（co-design）是大规模异构 chiplet LLM 服务的效率关键——纯架构或纯调度的单边优化都不够**

### 9. Edge RAG 自适应压缩（弱相关，简要收录）

- **From Retrieved Context to Runtime Control: Adaptive Compression for Edge-based RAG**（[arXiv:2608.19535](https://arxiv.org/abs/2608.19535)，08-20，作者 Zlatan Feric / Amir Taherin / Yanzhi Wang / David Kaeli）: 检索上下文拉长 prompt，增大 prefill 工作量、KV cache 足迹、内存流量、延迟与能耗；压缩（如 LLMLingua-2）可缓解，但**压缩器本身也在边缘 SoC 上跑，其延迟/能耗会抵消生成侧节省**。NVIDIA Jetson AGX Thor + Llama/Qwen 生成器 + Natural Questions/HotpotQA 实测：7B-8B 生成器下 generation 占单查询延迟约 90%、GPU 能耗 91%；**中等压缩率可将 GPU 能耗降 53.2%、SoC 能耗降 48.2%，且质量损失可忽略**——但压缩率需运行时策略动态管理（基于工作负载特征 + 边缘遥测）。对本组的边缘侧框架叙事是补充性信号，非核心

## 📊 深度分析（本组视角，5 段）

### 分析一：FlashPrefill V2 把"稀疏 prefill"推进到生产门槛——H20 评测与 SGLang 集成的双重信号

FlashPrefill V2 的意义不在稀疏算法本身（模式发现 + 动态阈值 V1 已有），而在**生产化三件套的补齐**：FA3/4 对齐的算子实现（warp specialization + pingpong pipelining）、FP8 量化支持、paged KV + continuous batching 的框架集成接口。这三个能力正是"算法原型 → 生产后端"的分水岭——之前的稀疏注意力工作（如 08-21 期收录的 WhiteMatter 等）都停留在架构/算法层，而 FlashPrefill V2 选择把自己做成**可插拔后端**，直接回应推理框架的集成需求。两个细节值得注意：① 评测卡选 **H20** 而非 H100——H20 是中国市场与全球推理部署的主力卡，说明该工作明确面向"推理性价比优先"的现实集群，而非榜单展示；② 明确以 SGLang 为集成对象而非 vLLM，与 08-19 期收录的 MAPLE（SGLang 集成 MoE 分配）形成同向信号——**SGLang 正在成为稀疏/优化内核的"开放试验场"**，vLLM 的规模化优势与 SGLang 的架构灵活性形成分工。对本库判断：稀疏 prefill 的落地路径已从"论文→框架重写"变为"论文→后端 PR→框架合入"，内核贡献的标准化接口（paged KV/FP8）是这条路径的使能器。

### 分析二：KV cache 复用出现"路由层 / 表示层 / 训练层"三层分工——agent 工作负载是共同推手

本期三篇 KV 相关论文恰好覆盖三层：**CacheRoute**（路由层——决定请求去哪台服务器，命中率 64.1%→93.2%）、**ReCache**（表示层——让 KV 块对组合顺序不变，TTFT 3.655x、KV 内存 -92.4%）、**Learning how to Forget**（训练层——让模型权重主动适配 H2O 等驱逐策略）。三层的共同推手都是 **agent 工作负载**：CacheRoute 的前缀重复来自 agent 的系统提示词/tool schema，ReCache 直接针对 tool/skill 复用，稀疏微调的价值在长上下文 agent 推理中最大。第一性视角：KV cache 的本质是"过去 token 的压缩表示"，任何复用优化都在回答同一问题——**哪些表示是"请求无关"（可跨请求复用）的？** 路由层假设"前缀相同"，表示层假设"资源相同、组合无关"，训练层假设"策略已知、权重可调"——三层假设从粗到细，覆盖了 agent 流量的三种典型重复模式。工程启示：规模化 agent 推理的 KV 成本控制不是单点优化，而是**路由亲和 + 表示复用 + 策略共适应**的叠加，未来框架（vLLM/SGLang）需要同时暴露这三类钩子。

### 分析三：Axon DSL 与"框架无关"叙事——vLLM 升格为编译目标，模型前端开始独立于训练框架

Axon 的价值主张是"write once, run everywhere"：模型定义写一次，编译到 PyTorch/JAX/MLX/vLLM 各自的原生实现，且 vLLM 路径（PagedAttention + KV cache 原生架构）拿到 58% median 加速。这背后是 LLM 软件栈的一个结构性变化：**模型定义层（DSL/规范）与执行层（训练/推理框架）开始解耦**。类比编程语言史：硬件无关的中间表示（如 LLVM IR）出现的前提是"存在多个后端且迁移成本高"——LLM 生态正处在"训练用 PyTorch、推理用 vLLM/SGLang/TensorRT-LLM、边缘用 MLX"的多后端局面，DSL 层自然成为降低迁移成本的中间表示。对 vLLM 而言这既是机会也是挑战：机会在于成为"编译目标"意味着获得 DSL 生态的模型供给；挑战在于"原生 vLLM 架构"要求 vLLM 的模型实现足够规范（shape-safe、kernel 选择可预测），否则 DSL 编译产物无法吃到 PagedAttention 的红利。**对本库的跟踪含义：框架竞争的战场正在从"内核性能"延伸到"模型前端的可编程性"**——谁能提供最友好的架构定义接口，谁就能捕获上游模型生态。

### 分析四：FleetSieve + HYDRA——配置/架构层面的"决策智能化"双样本，SLO 成为第一性约束

FleetSieve（软件侧：TP 度 + 副本数选择）与 HYDRA（硬件侧：chiplet 组成 + 调度策略）表面是不同问题，底层共享同一方法论：**在爆炸的设计空间中，用"决策关键性"而非"穷举"来引导搜索**。FleetSieve 只测量"会影响最终分配决策"的配置（省 6.9% 测量量），HYDRA 用 Markov 性能估计器替代全模拟（1.55x 吞吐 + TTFT -43.7%）。两者都把 **SLO（尤其 p99 尾部延迟）作为第一性约束**：FleetSieve 明确演示"46.4s p99 vs 30s SLO"的违约风险，HYDRA 把 TTFT 纳入优化目标。第一性视角：推理服务的资源分配本质是"**在尾部延迟约束下最小化成本**"的优化问题，而性能对配置的非单调性（TP 越高通信越重）让经验公式失效——这就是为什么 profiling 与 DSE 需要"智能采样"而非查表。对超节点/服务器厂商的启示：当 GPU 资源池足够大（百卡级以上），**配置选择本身成为可优化的系统组件**，类似 FleetSieve 的工具应嵌入推理平台的 capacity planner，而非靠工程师手工调参。
