## 二、arXiv 新论文精选

### 2.1 KV Cache 管理与长上下文（7篇）

**① LOCKS — Page-Local Compact Key Summaries（vLLM drop-in 插件）**
> **来源**: https://arxiv.org/abs/2607.24555 · Jul 27, 2026

- 每 page 维护自身谱摘要（约 cache 1/10 大小），以 log-sum-exp 估计各 page 注意力质量，**只 attend top pages，选择本身不读任何候选 key/value**
- 2048-token budget 下在 **100K+ context 匹配 FullKV 聚合质量**，仅 attend ~2% tokens
- 1M tokens 时 **per-token decode 延迟减半（2.0×）**；以 unmodified vLLM 的 drop-in plugin 交付，batch decode 运行于完整 CUDA graphs
- 洞察: 注意力 key 局部低秩但全局高秩 → page 专属谱基优于共享低秩基

**② SmartGen — PD 分离下选择性 KV Cache 传输**
> **来源**: https://arxiv.org/abs/2607.28150 · Jul 30, 2026

- 面向 rented cloud 场景：PD 分离节点间全量 KV 传输易打满有限带宽 → **选择性传输关键 KV**
- 三条传输路径：profile-based 主动推送（prefill 阶段识别）+ 并行 on-demand 拉取 + speculative 兜底
- **time-to-second-token 最高降 4.3×**，后续 decode 性能与精度相当

**③ DualDecoder — 投机预测驱动的 KV 预取**
> **来源**: https://arxiv.org/abs/2607.26475 · Jul 29, 2026

- 关键洞察：**下一 token 所需的关键 KV 可由前一 speculated token 预测** → KV 检索预取与 decode 计算重叠，消除 GPU 侧辅助状态
- 双 token 解码流水线 + layer-aware 传输调度 + layer-scoped 内存管理
- **decode 吞吐最高 2.62× over SOTA**（对比对象包括现有稀疏 KV offload 系统），延迟与质量不变

**④ ReTopK — 相似度引导的 Top-K 稀疏注意力复用**
> **来源**: https://arxiv.org/abs/2607.27692 · Jul 30, 2026

- 问题: Top-K 稀疏注意力的 selector 仍需对全 KV 打分，选择器成本随上下文线性增长
- 洞察: 相似 query 的 attention support 高度重叠 → 缓存历史 query-support 对，只对紧凑候选集重排
- 128K context、K=512 时 **attention 计算加速 3.07×**，perplexity 仅增 0.50%；16K-128K 全范围 PG19/LongBench 领先

**⑤ Back from the Future — Counter-Causal Surprise KV 驱逐**
> **来源**: https://arxiv.org/abs/2607.27600 · Jul 30, 2026

- 新驱逐原则：**能被更近 token 良好预测的旧 token 是冗余的** → 用 counter-causal attention mask（每位置只看未来上下文）打分驱逐
- 与 cache 实际内容直接挂钩、训练无关；单层近似将刷新成本降到边际
- 多开源 LLM 上优于或持平 SOTA 驱逐方法（代码: metacognitionai/counter_causal）

**⑥ SemPIC — 语义位置无关 KV Cache 学习**
> **来源**: https://arxiv.org/abs/2607.28069 · Jul 30, 2026

- 长上下文/agentic 负载反复复用同一批文档 → prefix caching 无法利用，位置无关缓存（PIC）不可靠
- LoRA Writer 通过行为蒸馏编译 native per-layer 文档 KV，预训练 decoder 保持为不变的 Reader；仅离线 cache 构建期适配，保留标准 KV 接口
- 引入 **KV Gradient Checkpointing** 降低峰值训练内存
- 3 模型 4 任务：mean micro-F1 从 KV Packet 的 0.53 → **0.60**（Full Recompute 0.62）

**⑦ DynaCalKV — Head 分组 + 自适应秩分配的 KV 压缩**
> **来源**: https://arxiv.org/abs/2607.24331 · Jul 27, 2026

- Key/Value 区别对待：Key cache 按 **CKA 相似度动态分组 head** 并预算内自适应分配秩；Value cache 复用 ReCalKV 离线校准低秩分解
- 显著减少 Key cache 参数量；**对 MHA 特别有效，GQA 长上下文下应更保守使用**

### 2.2 推理服务系统（2篇）

**⑧ InferScale — GPU 原生 KV 注入（经 vLLM KV-connector 接口）**
> **来源**: https://arxiv.org/abs/2607.27090 · Jul 29, 2026

- 问题: Mem0/MemGPT/Zep 等记忆系统反复将检索内容注入 prompt → 引擎重复 prefill 同一内容，TTFT 随检索预算增长
- 方案: 预计算每条记忆事实的 KV + 语义 embedding 存 GPU，serving 时检索并**直接注入 vLLM paged cache**
- **Chunked RoPE**: 先存旋转前 key，注入时按 serving 位置旋转；Context-Window Encoding 弥补独立编码丢失的跨事实上下文
- 经 vLLM KV-connector 接口实现，**无需改引擎、无需微调**；k=50 时 TTFT 降 **72-79%（3.6-4.8×）**，并发吞吐 3.7-4.5×，质量 60.3% vs Mem0 63.3%（免 serving 重算）

**⑨ Kalypso — 关系型 LLM Serving（query-aware 调度）**
> **来源**: https://arxiv.org/abs/2607.23815 · Jul 26, 2026

- 新抽象: LLM 作为语义算子（filter/extract/rank/join）执行语义查询计划 → **跨算子流水线执行时 KV-cache state 复用而非重算**
- 新的在线调度问题：pipelined operator 执行与 GPU 内存压力管理耦合（在驱逐前复用 KV state）
- 调度器连续调整内存分配，平衡上游并行度/下游进度/GPU 利用率
- **query 完成时间最高提速 4.57× over request-centric serving**

### 2.3 投机解码（2篇）

**⑩ Functional MLA — MHA/GQA→MLA 的功能重构（非缓存压缩）**
> **来源**: https://arxiv.org/abs/2607.27269 · Jul 29, 2026

- 发现: 直接 MHA/GQA→MLA 转换中，低秩分解 + RoPE 处理引入的 attention 函数误差**大幅降低投机解码 draft-token 接受率**
- 方案: 将 MLA draft 构建视为**功能重构**——优化转换后 MLA 模块以复现原 MHA/GQA 的 post-output-projection 响应（calibration hidden states），converter-agnostic，无需 verifier 监督
- 192 配置（4 Llama/Qwen draft-target 对 × TransMLA/MHA2MLA × HF/vLLM × 4 任务）：**37/64 单元显著改善接受率**，26 基本不变，仅 1 下降

**⑪ SparseSpec-L — 训练无关自投机解码（长上下文）**
> **来源**: https://arxiv.org/abs/2607.27735 · Jul 30, 2026

- 统一效率分析: **当边际接受概率低于相对 drafting 成本时，延长投机视野反而降低加速比**（关键理论贡献）
- 训练无关: 目标模型自身用动态稀疏化 + 可召回 KV cache 生成轻量 draft；复用 full-context 验证期的 per-head 注意力统计作为无额外前向的重要性信号
- 在线熵控制器按期望 step-wise 效率自适应选择投机长度

### 2.4 Agent 推理（1篇）

**⑫ Self-Speculating Agent — 联合 Agent-Speculator RL**
> **来源**: https://arxiv.org/abs/2607.25816 · Jul 28, 2026

- 问题: 现有 tool-call speculator 用独立 draft 模型或缓存 trace，与部署 agent 行为不对齐（speculator-agent gap）
- 方案: **同一模型双模式**——agent 模式解题 + speculator 模式从部分轨迹预测下一 tool call，完全复用 prefix KV cache；RL 从自身 rollout 导出投机目标，交替更新
- agentic search QA + 对话工具任务: next tool-call Hit@1 从 **44.1 → 61.2**（Qwen3-4B）、**48.9 → 66.3**（Qwen3.5-4B），agent 任务成功率不降

## 三、综合观察

1. **长上下文 KV cache 管理进入"零辅助状态"竞赛**: LOCKS（无候选读取选择）/ DualDecoder（无 GPU 辅助状态）/ ReTopK（缓存历史决策）三个独立工作共同攻击同一瓶颈——稀疏 KV 选择器自身的线性成本，方向收敛于"让选择本身变便宜"。
2. **PD 分离从架构共识走向传输优化**: SmartGen 针对 rented cloud 带宽瓶颈，Kalypso 针对算子级 KV 复用，InferScale 针对个性化 KV 注入——三段不同层次都在榨取 KV state 的可复用性。
3. **vLLM 成为学术系统落地的默认平台**: LOCKS（drop-in plugin）/ InferScale（KV-connector 接口）均以 vLLM 为交付目标且零引擎修改，vLLM 的插件接口设计开始兑现生态红利。
4. **投机解码精细化**: Functional MLA 证明"转换后仍需功能重构"、SparseSpec-L 给出投机视野的自适应理论边界、Self-Speculating Agent 把投机对象从 token 扩展到 tool call——投机解码从"加速技巧"演化为"系统设计维度"。
5. **安全债偿还**: vLLM v0.26.0 一次消除 pickle 反序列化 + 修复 CVE 绕过 + 4 项 DoS 防护，框架竞争进入"功能×安全"双线。
