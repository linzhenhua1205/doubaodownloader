## 二、arXiv 论文动态（2026-08-21 ~ 08-26，推理框架方向）

### 2.1 多智能体 / Agent 推理 serving（本周最热方向）

- **arXiv:2608.25523「TOPAS: Workflow-Aware Prefix-State Scheduling for Multi-Agent LLM Serving」**（2026-08-26）: 多智能体 serving 中 prefix caching 存在根本权衡——保留长 system-prompt KV cache 加速后续调用，却挤压并发 batching 的 GPU 显存。TOPAS 以任务级最长剩余服务路径为优化目标，联合决策「保留哪些 agent prefix + 调度哪些请求」，并加入任务级 aging 防饿死；**在 SGLang 框架内实现**，三类合成 DAG + MetaGPT 双工作流上 mean/p99 JCT 最高降 **39.8%/49.4%**（MetaGPT-TL: 22.0%/26.6%）。https://arxiv.org/abs/2608.25523
- **arXiv:2608.25683「psRL: Efficient Training for Agentic AI via Training-Time Prefix Sharing」**（2026-08-26）: Agentic RL 训练中系统瓶颈从 rollout 转向 update——树状/逐步采样使训练样本量激增而 rollout 边际成本低。psRL 利用 update 阶段的全局可见性与数据不可变性，实现前缀共享：新 KV cache manager 支持自适应 block-size 分配与动态 KV caching，**吞吐较现有系统最高提升 5.2x**。https://arxiv.org/abs/2608.25683
- **arXiv:2608.24004「AgentSpec: Speculative Decoding for Batch Inference of LLM Agents」**（2026-08-25, EMNLP 2026）: 系统分析 agent 场景投机解码的两大退化主因——投机 token 高拒绝率、动态 token 预算利用不足。AgentSpec 以 structure-isolated drafting（约束投机到语义连贯片段，拒绝率极低）+ redundancy-aware budget allocation（利用 agent 级信息），**在 vLLM 上覆盖 4 个模型族/5 类工作负载**，全面超越 SOTA。https://arxiv.org/abs/2608.24004

### 2.2 KV cache 压缩与管理（数量最多的子方向）

- **arXiv:2608.23843「PuzzleKV: Page-Wise Low-Rank Decomposition for KV Cache Compression」**（2026-08-24）: 发现每个 head 的 KV cache 按固定长度逻辑页切分后，**页内存在显著低秩结构**。以页为独立压缩单元做低秩分解（训练/校准-free），60% 存储下保留 96%+ Full KV 性能；叠加量化后 **18.7% 存储仍保留 93%+ 性能**。https://arxiv.org/abs/2608.23843
- **arXiv:2608.23834「Minima-KV: Retention-Preserving KV Cache Compression with Mixed-Format Paged Attention」**（2026-08-24, Minima AI）: 保留型分层压缩——近期/Anchor 页保持 FP8，更老的非 Anchor 页转 packed TQ3，通过全局归一化 online-softmax merge 直接异构 decode，**无 cache 级 dense shadow**。Qwen3.6-27B 单卡（96GB RTX PRO 6000 Blackwell）实测 18.3 KiB/活 token（BF16 的 3.50x、FP8 的 1.75x 压缩）；LongBench v2 503 题 16K/32K/64K 仅 -0.80/-0.60/-0.40pp；59,008-token 直接 decode 对实测 3.625x active-KV 压缩、0.9821x 吞吐。https://arxiv.org/abs/2608.23834
- **arXiv:2608.23658「Elastic KV Cache for LLM Serving: A Working Reclamation Mechanism, and Why Chunked Prefill Already Closes the Gap」**（2026-08-24）: 把启动时预留给 worst-case prefill 的显存储备在 decode 阶段借给 KV pool、prefill 前归还（纯 userspace CUDA virtual-memory 路径，两个 physical handle 映射进同一 contiguous virtual range，无需驱动补丁）。**但论文诚实报告负面结果**：小 chunked-prefill 对 TTFT 惩罚仅 ~1%（8192 vs 32768 chunk），因为 prefill 是 compute-bound 而 decode 每步每序列只吃一个 token——调低 `max_num_batched_tokens` 就能回收更多 KV；储备在 TP 下还会稀释（TP1 16% → TP4 2.7%）。https://arxiv.org/abs/2608.23658
- **arXiv:2608.25230「Trust the Mass: Forced Weights in KV-Cache Eviction」**（2026-08-24）: 枚举 168,192 条 attention 行的最优子集证明「保留最大权重」已近最优（最优子集仅补上 2~5% 的 gap），因此各 eviction 方法的差距来自**内存记账口径**而非选择质量——最强 query-agnostic 方法靠 mask 存全量 cache，只有 ragged per-head 存储才真正省内存；名义预算下固定选择损失 14~62 基准分；ContourKV（training-free，基于 dropped-mass 统计）在 160 对对比中赢 93 输 22。https://arxiv.org/abs/2608.25230
- **arXiv:2608.21541「Beyond Sparse Weights: When Is Attention Compressible?」**（2026-08-21）: 大权重多≠可压缩——遗漏值的加权和（missing statistic）才是精确指标。CertKV（training-free）每 head 保留 1 个 tail-summary slot，其余按 value dispersion 分配；**LongBench-v2 9 项设置中 7 项 top-2**，128K RULER 保持领先压缩层，packed Llama 原型实现 10 倍 cache 预算。https://arxiv.org/abs/2608.21541
- **arXiv:2608.23296「Sigmoid Attention as a Better Substrate for Learned KV Cache Eviction」**（2026-08-24, ICML 2026 AdaptFM Workshop）: 学习式 eviction 的 soft-to-hard 失配——训练时 differentiable gate 只是衰减，推理时要物理删除才省内存。GPT-2 规模受控 2×2×2 对比发现 **sigmoid attention 是更好的硬删除基底**：sigmoid-gated 模型删 KV 项 PPL 几乎不变，而 softmax gates 无法一致超越 H₂O/KeyDiff 等事后方法。https://arxiv.org/abs/2608.23296
- **arXiv:2608.24063「VisCache: Visual KV Cache Pruning for Efficient Vision LLM Inference」**（2026-08-25）: 视觉 KV cache 剪枝两段式——轻量 VLM 先滤时序冗余（关键帧选择），再以 PruneKV 抛物线逐层预算分配 + 非对称更新（剪 keys 融 values）；**仅 19~28% KV 保留实现最高 2.35x 加速**，建立 VLLM 长上下文效率新 Pareto 前沿。https://arxiv.org/abs/2608.24063
- **arXiv:2608.22704「WnW: Waxing-and-Waning KV Cache for Long-Form Speech LLMs」**（2026-08-24, EMNLP 2026）: 长语音输入下 KV cache 成主导内存成本。发现 prefill attention 集中于音频起始（attention-sink），decode 时则广泛分布、两者排序重叠弱——纯 prefill 压缩会误删。WnW 把 KV heads 分为 anchor/tidal/fixed 三类：anchor 留 GPU 当重要性观测器，tidal 在 CPU 留副本按 chunk 召回；**仅 20% 音频 token 在 GPU 上即保持近 Full-Cache 精度**（LibriSpeech-Long，Voxtral-mini-3b / Qwen2.5-Omni-3B）。https://arxiv.org/abs/2608.22704
- **arXiv:2608.22753「Beyond Factual Knowledge: Benchmarking and Learning Step-Level Procedural Rule Reasoning」**（2026-08-24, EMNLP 2026 Findings）: DynaRule 把外部规则注入 KV cache，用 Stacked Step-Level Attention Training + `<search>` token 让检索成为可学习的分步内化过程；10K 规则池 Recall@1 >85%，QA 准确率最高 +19 分。https://arxiv.org/abs/2608.22753

### 2.3 Serving 系统与调度

- **arXiv:2608.21719「PowerSlider: Exploiting Phase Asymmetry for LLM Serving under Demand Response」**（2026-08-22）: AI 推理集群开始被**瞬时功率**约束（电网需求响应、功率上限随时间变化），而非仅能耗。核心洞察是流水线相位不对称：compute-bound prefill 随 GPU 频率近乎线性掉吞吐，memory-bound decode 在 0.57x 频率下仍可维持，reasoning thinking 阶段把 KV 容量与调度耦合。PowerSlider 用 Flex SLO 契约 + prefill-think-answer 解耦 + KKT 在线求解器（每次 cap 变化 7.7ms 内重解）；**SGLang 上 30% cap 削减时在线 goodput 78.3% vs 基线最优 47.6%（1.64x）**，CAISO 电网紧急日回放中 92% 平均 goodput（谷底 54%，所有基线 <7%）。https://arxiv.org/abs/2608.21719
- **arXiv:2608.24650「Simthesizer: An Agent-Driven Simulation Framework for LLM Serving Systems」**（2026-08-25）: LLM serving 演进快于人类驱动的模拟器开发——agentic 工作流、disaggregated serving 都不再适配单体模拟管线。Simthesizer 用可组合模拟器基础设施 + Synthesizer agent（带护栏的编码 agent）把自然语言特性请求直接降到统一动态图抽象；**与 vLLM 真实系统对比平均吞吐误差仅 2.51%**（现有模拟器 6.03%），比 LLMServingSim2.0 / Vidur 快 284.96x / 23.19x。https://arxiv.org/abs/2608.24650
- **arXiv:2608.25431「GIFT: Enforcing User Data Isolation in LLM Serving via GPU Information Flow Tracking」**（2026-08-26）: 共享推理基础设施上用户数据隔离问题。两个关键洞察：① CPU 侧只编排数据流不做内容操作 → **加密即隔离**（per-user 加密无需改 serving 逻辑）；② GPU kernel 信息流有限且可预测 → 静态流分析预计算规则，解耦流追踪零插桩零 GPU stall。在 **vLLM 与 DistServe 上实现**，4-10.7% 吞吐开销、延迟不变；GIFT-CC 扩展机密计算对抗不可信 OS/虚拟化层。https://arxiv.org/abs/2608.25431

### 2.4 MoE 推理优化

- **arXiv:2608.24938「ExFold: Unified Expert Folding for Training-Free MoE Prefill-Decode Acceleration」**（2026-08-24）: MoE 两阶段瓶颈本质不同——prefill 是 token-wise 专家计算主导，decode 是 batch-wise 激活专家集的内存流量主导；现有训练-free 方法只优化单一资源代理。ExFold 把两阶段统一为「有预算的输出近似问题」：执行相位特定约束专家集，用校准的标量投影矩阵把预算外专家贡献折叠进保留专家。**vLLM 插件实现（轻量 expert-folding CUDA kernel），TTFT 最高 1.41x、TPOT 最高 2.45x 加速，质量保留 ~99%**。https://arxiv.org/abs/2608.24938
- **arXiv:2608.21693「MoEXBench: Benchmarking Composable Compression Techniques in Mixture-of-Experts LLMs」**（2026-08-22）: 系统化基准 10 个 MoE 模型（30B~235B）上 20~50% expert pruning + 1~16 bit 量化 + 多档 KV cache 精度**组合使用**的交互效应。发现：组合压缩无法从独立技术预测、压缩率不能可靠预测质量损失/运行时收益、**expert pruning 是主导质量劣化源**、平均质量会掩盖 workload/架构特定失败。https://arxiv.org/abs/2608.21693

### 2.5 成本 / 能耗分析

- **arXiv:2608.23962「More GPUs or a Smaller Cache? Tensor Parallelism versus KV Compression for Memory-Bound LLM Serving」**（2026-08-25）: 把张量并行（degree 1~8）与 KV 压缩（16/8/4-bit、keep-ratio 0.25）放到同一成本轴（每百万 token 成本 vs 延迟，A100/A40/H100 校准模拟器）。**结论：没有成本等价交叉点——压缩全面更便宜 1.20x~2.00x**；决策边界是模型规模相对设备显存，80GB 卡约 36B 参数分水岭：以下压缩占优（加 GPU 是浪费），以上 TP 从选择变入场券（Llama-2-70B 单 A100 任何 KV 设置都不可行，因为瓶颈是权重）。压缩只放大每美元容量（16.5x vs 1.21x），TP 是唯一改善延迟的杠杆（压缩因 batching 争用使每 token 延迟恶化 8~93%）。https://arxiv.org/abs/2608.23962
- **arXiv:2608.25096「Understanding the Energy Scaling of Large Language Model Inference Across Context Lengths and Attention Architectures」**（2026-08-25）: 系统性实测 decode 阶段能耗（NVIDIA 硬件计数器）。**注意力机制是 decode 能耗随上下文扩展的主因**：MHA 能耗增速远陡于 GQA，GQA+SWA 几乎恒定；模型规模决定绝对能耗；batching 使每 token 能耗与延迟最高降 **87%**。https://arxiv.org/abs/2608.25096

### 2.6 框架安全与多租户隔离（新维度）

- **arXiv:2608.25697「LMSM: LLM Security Framework Inspired by Linux Security Modules」**（2026-08-26）: 把 LSM 的分离思想搬到 LLM serving——安全后端暴露校准证据、版本化策略评估规则、独立 gate 授权缓冲输出释放，后端/规则/调度可独立更换。原型同时跑在 **HuggingFace Transformers 与连续 batching vLLM** 上；Qwen3-4B 上 HarmBench ASR 从 39.20% 降到 3.32%，XSTest 误拒从 2.40% 升到 4.40%，32 active sequences 下保留 98.14% 吞吐。https://arxiv.org/abs/2608.25697
- **arXiv:2608.23962 补充视角**: 多租户成本经济学——同卡多租户的 KV 内存分配策略直接影响每美元容量（见 2.5）。https://arxiv.org/abs/2608.23962

### 2.7 CPU 推理与 embedding 服务（边缘参照系）

- **arXiv:2608.23841「Pipeline-Native Transformers: Co-Designing Model Architecture and CPU Inference for Bandwidth-Efficient Autoregressive Decode」**（2026-08-24, 77 页）: CPU 单 token 自回归解码被内存带宽绑定（现代 CPU ~1 TFLOP/s 算力 vs ~50 GB/s 主存带宽，每 token 必须流式读全部活跃权重）。cflow（CPU-first streaming 引擎）+ pipeline-native 架构：权重按 L2 尺寸 tile 存储、MoE 只读 top-k experts、投影融合、delay-aware 调度。30.9B MoE 在 32-vCPU Ice Lake 上 **5.94 tok/s**，对比 llama.cpp 4.75、**vLLM CPU backend 1.65**；专家延迟窗口用磁盘异步 I/O 重叠再获 1.68x。论文诚实报告 8 项设计声明中 1 项被证伪、1 项无结论。https://arxiv.org/abs/2608.23841
- **arXiv:2608.23806「Giga-Embeddings: Mixture-of-Experts Encoders for High-Throughput Text Embeddings」**（2026-08-24）: 10B 稀疏 MoE embedding 编码器（~1.8B active params/token），**vLLM 基准 1024-token 输入 114.5k tokens/s**（比 dense 3B 高 25%，比外部系统高 1.56~2.65x）；配套 dense 3B 与蒸馏 480M（俄语 MTEB 70.98 分，超 FRIDA 且少 42% 参数）。https://arxiv.org/abs/2608.23806

## 三、分析段落（深度展开）

### 分析段落 1 — vLLM v0.28.0 释放的信号：框架竞争从「模型功能支持」切换到「推理深度优化」

把 v0.26.0 → v0.27.0 → v0.28.0 三个版本连起来看，vLLM 的版本节奏已经从「发布周期追新模型」切换到「为特定旗舰模型做跨栈性能攻坚」：v0.26.0 是 Inkling 全栈支持、v0.27.0 是 Kimi K3 全栈落地、v0.28.0 是 Kimi-K3 的深度优化（DCP、fused FlashKDA、GEMM-RS、shared-expert sharding 每 GPU 省 17 GiB、自适应投机预算 DSpark TTFT 提升 60%）。这个模式的因果链很清晰：**当模型架构（MoE/MLA/混合注意力）进入成熟期，新模型带来的边际收益下降，而推理成本成为规模化部署的主矛盾**——厂商（月之暗面 Kimi-K3、DeepSeek V4）与框架（vLLM）形成深度协同，把优化下沉到 kernel 级（FlashKDA fused decode/prefill）与调度级（DCP、async scheduling）。对服务器/AI 基础设施决策者的含义：vLLM 的 `max_num_batched_tokens` 默认 8192→16384 和 Blackwell CUDA graph capture 默认 1024，意味着**默认配置就在为「大 batch + 高并发」调优**——采购与容量规划时应以 vLLM 新默认值为基准重新评估吞吐模型，而非沿用旧版本的压测数据。另一个值得注意的信号是 TensorRT-LLM 的 AutoDeploy 弃用：NVIDIA 正在用 agentic 方式（Minimax M3 一周内支持）替代手工移植流程，说明**模型支持速度正在成为框架竞争的第二战场**，而这恰好是 vLLM 生态（Python 优先 + 社区驱动）的传统优势区。

### 分析段落 2 — KV cache 从「压缩算法竞赛」转向「系统级工程问题」，且出现难得的负面结果诚实报告

本周 arXiv 的 KV cache 论文密度是近期最高，但更重要的是方法论层面的转向。第一层是**内存记账口径问题**（Trust the Mass）：论文枚举证明保留最大权重已近最优，各 eviction 方法的差距主要来自「用 mask 存全量 cache 还是 ragged 存储」的记账差异——这解释了为什么过去一年大量 KV 压缩论文的宣称收益无法在生产中复现，**评估协议（per-head ragged vs dense mask、byte budget vs ratio budget）比算法本身更决定论文数字**。第二层是**保留型压缩 vs 驱逐型压缩的分野**：Minima-KV（FP8 + TQ3 混合格式、无 dense shadow）、CertKV（tail-summary slot）代表「不驱逐活请求页、只降精度」的路线，与 WnW（CPU 副本召回）共同指向**分层存储**（GPU 高精度 + CPU/磁盘低精度 + 按需召回）作为生产形态——这与 vLLM v0.28.0 的 Tiered KV cache offloading 体系（disk offloading、二级 tier manager、canonical CPU layout）形成论文-工程的双向印证。第三层是难得的**负面结果**：Elastic KV cache 论文诚实报告「chunked prefill 已经基本抹平了储备回收的收益」——调低 `max_num_batched_tokens` 就能回收更多 KV 且延迟几乎不变，储备在 TP 下还会稀释（TP1 16% → TP4 2.7%）。这类「机制可行但前提不成立」的诚实负面结论，对工程选型的价值远高于又一篇「+30% 加速」的乐观论文，因为它直接否定了「弹性 KV 池」作为高优先级投资方向。综合判断：**KV cache 的下一轮竞争不在算法而在内存分层架构 + 计费/记账口径标准化**，这与 More GPUs or a Smaller Cache 的成本轴分析（压缩 1.2~2.0x 更便宜、36B/80GB 分水岭）相互印证——对显存规划者的直接指导是：80GB 级设备上 36B 以下模型优先 KV 压缩而非加卡，36B 以上必须上 TP（那是权重瓶颈，压缩碰不到）。

### 分析段落 3 — 多智能体推理成为 serving 新战场：prefix caching 的语义从「加速」变成「多智能体调度的核心变量」

本周三篇论文（TOPAS、psRL、AgentSpec）从不同角度指向同一结论：**多智能体/Agentic 工作负载正在重塑 LLM serving 的优化目标**。TOPAS 揭示了最深的矛盾：多智能体系统依赖长 system prompt 的 prefix reuse（每个 agent 的 system prompt 可能数十 KB），但保留这些 prefix KV cache 会挤压并发 batching 的显存——这不再是「缓存命中率 vs 显存」的经典权衡，而是「多智能体任务级完成时间（JCT）」的调度问题，需要把 prefix 保留决策放进调度器（SGLang 实现）与请求调度联合优化。psRL 则从训练侧提供镜像视角：Agentic RL 的树状采样让 update 阶段成为瓶颈，prefix 冗余从「服务端优化对象」变成「训练端优化对象」，5.2x 吞吐提升说明冗余规模之大。AgentSpec 处理的是 agent 推理的延迟问题：投机解码在 batch 场景下因拒绝率高而失效，需要按 agent 工作流的语义结构（tool call、chain-of-thought 等片段）约束投机。三篇合起来可以画出一条因果链：**Agent 应用爆发 → 长 system prompt 与高并发共存 → prefix cache 预算成为稀缺资源 → 调度器/训练器必须感知任务级语义（agent 工作流、JCT、token 预算）**。对 vLLM/SGLang 等框架的工程含义：prefix caching 的接口需要从「LRU 式自动缓存」演进为「显式的、可被调度器控制的 cache 预算管理」（类似 vLLM v0.28.0 的 tiered offloading + `module_path` 可插拔管理器），而 Agent 专用推理引擎（状态管理、工具 schema 压缩、跨请求冗余缓存）将成为未来 1-2 年 serving 框架的主要差异化战场——这与 tech 组今日收录的 AgentSysBench（control-plane tax、28GB/session 状态、35.2% 跨请求冗余）结论完全互证。

### 分析段落 4 — 框架安全与多租户隔离成为新维度，且与国产加速器生态形成对照

LMSM（LSM 思想搬到 LLM serving）与 GIFT（GPU 信息流追踪 + 加密即隔离）同周出现不是巧合：**当推理规模化到多租户共享集群，用户数据隔离与安全策略执行从「合规问题」变成「架构问题」**。LMSM 的价值在于把安全控制从「每个新 artifact 耦合一段校准/策略/干预代码」重构为「后端-策略-门禁」三层分离（LSM 模式），这与操作系统 30 年验证过的模块化安全架构一脉相承——对 vLLM 这类框架的启示是安全策略需要成为一等公民 API 而非插件补丁。GIFT 的「加密即隔离」洞察更深：CPU 侧只编排数据流不做内容操作，所以 per-user 加密就能在不改 serving 逻辑的前提下实现隔离，4-10.7% 的吞吐开销在合规场景下是值得的。这个维度对国产加速器（昇腾等）尤其有对照意义：tech 组今日收录的昇腾 16 设备场测（2607.08215）显示平台级限制（数值错误、并行脆弱、生态碎片化）需要 12 个 vendor 插件源码级补丁——当多租户隔离、安全策略、可观测性成为推理框架的默认能力时，**生态成熟度（而不是单点性能）会成为国产加速器部署的瓶颈**，这与 GIFT/LMSM 所依赖的 kernel 信息流可预测性、标准安全 API 生态互为条件。
