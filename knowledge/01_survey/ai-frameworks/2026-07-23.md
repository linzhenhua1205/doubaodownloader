## 1. 推理调度：Gimbal — 跨层协调 MoE 推理调度

> **来源**: arXiv 2606.15177 · 2026-06-13 | **实验**: 多 GPU MoE 部署 | **对比**: vLLM

### 问题

MoE LLM serving 中，动态请求负载与稀疏专家路由相互作用，产生两个层次的不平衡：
- **DP engine 间不平衡**：前端调度基于粗粒度请求计数器，忽略后端引擎的真实压力
- **Expert 热点**：后端负载均衡基于聚合 expert 激活计数，忽略 source-DP 到 expert 的流量模式

### 方法：跨层协调调度

**Gimbal** 在三层做联合优化：

| 层级 | 方法 | 信号来源 |
|:-----|:-----|:---------|
| **DP-engine 调度器** | 细粒度在线压力信号 → 将请求路由远离过载引擎 | KV cache 用量·剩余 prefill 量·队列压力·MoE expert 压力 |
| **Engine 内排序** | 轻量 prefill-aware 队列排序 + aging → 减少 HOL blocking | 无需输出长度预测 |
| **Expert 放置** | 基于 MINLP 启发式的在线 source-DP→expert 路由统计 + 迁移稳定性约束 | 专家负载·source-aware 通信成本·迁移稳定性 |

### 性能数据

| 指标 | 改进 vs vLLM | 条件 |
|:-----|:------------:|:------|
| **TTFT (Time to First Token)** | **-42.9%** | 平均，混合 MoE 负载 |
| **TPOT (Time Per Output Token)** | **-33.3%** | 平均 |
| **高负载请求吞吐** | **+3.0%** | 高并发场景 |

### 影响判断 🟢

Gimbal 的贡献在于**将前端调度、engine 内排队、expert 放置三个解耦的决策统一建模**——这是一个方法论上的进步。但在高负载下吞吐提升仅 3%，说明瓶颈可能不在调度侧而在 compute/memory 侧。

## 2. 推理调度：Load-Aware Prefill Deflection — 解耦推理 P95 TTFT -81%

> **来源**: arXiv 2607.02043 · 2026-07-02 | **实验**: A100 2P2D 生产 trace | **模型**: DeepSeek-V2-Lite

### 问题

解耦推理 (PD-disaggregated) 中，bursty heavy-tailed 负载下 prefill 节点饱和而 decode 节点计算未充分利用。

关键发现：P95 TTFT 中 **prefill 执行仅占 2-23%**，剩余来自排队的**节点间 GPU-GPU KV cache 传输**。

### 方法：主动 Prefill Deflection

将排队请求的 prefill 阶段**偏转到 decode 节点执行**（chunked prefill 与 in-flight decode batch 交错），消除节点间 KV 传输。

| 组件 | 功能 |
|:-----|:------|
| 路径选择 | 对每个排队请求估计 prefill 节点 TTFT + 每个 decode 节点的最大可插入 chunk 大小 |
| 约束检查 | 确保 deflected prefill 不破坏 in-flight decode 的 TBT SLO |
| 零额外传输 | deflected prefill 直接在 decode 节点上完成→KV 传输被消除 |

### 性能数据

| 指标 | 改进 vs SOTA 解耦调度器 | 条件 |
|:-----|:-----------------------:|:------|
| **P95 TTFT** | **最高 -81%** | 生产级 trace，burst 负载 |
| **SLO 达标率** | **最高 +79%** | 同上 |
| 每请求路由开销 | <1ms | 在线决策 |

### 影响判断 🔥

**"KV 传输即瓶颈"** 的实证是关键贡献——prefill 执行本身只占 2-23% 的尾延迟。这个发现直接挑战了解耦推理的假设前提（prefill 和 decode 应该严格分离），暗示**在中等规模部署中，解耦可能不如混合执行**。

## 3. KV 缓存：UltraQuant — 4-bit KV 缓存面向上下文重 Agent

> **来源**: arXiv 2606.20474 · 2026-06-18 | **模型**: 未指定 | **硬件**: AMD CDNA4 GPU

### 背景

上下文重的 Agent 场景对 KV cache 压力极大：长 prefix 在多个短 turn 间复用，同时并发决定了 GPU 利用率。

### 方法：4-bit KV Cache 实践路线

- TurboQuant 风格旋转 + 码本量化作为精度锚点
- vLLM FP8 KV cache 作为部署锚点
- **FP4 近似路径**：FP8 query × FP4 KV × UE8M0 group scale + native scaled-MFMA (CDNA4)

### 关键设计决策

| 决策 | 方向 | 理由 |
|:-----|:-----|:------|
| K/V 非对称处理 | ✅ 分别量化 | K 对量化更敏感 |
| Walsh-Hadamard 旋转 | ✅ 保留 | 均衡 outlier |
| QJL 移除 | ✅ 移除 | 精度无改善时降低复杂度 |
| Block-scale 变体 | ✅ 探索 | 优于 per-tensor |

### 性能数据 (Agent 多轮负载)

| 指标 | 改进 vs FP8 KV 基线 | 场景 |
|:-----|:-------------------:|:------|
| **P50 TTFT (cache 压力后期)** | **3.47× 降低** | 长上下文多轮 Agent |
| **P50 TTFT (全轮平均)** | **2.3× 降低** | 同上 |
| **输出吞吐** | **1.63× 提升** | 同上 |

### 影响判断 🟢

Agent 场景的 KV cache 优化从"压缩"转向"感知多轮生命周期"——UltraQuant 是首个在该设定下端到端验证 4-bit 的工作。AMD CDNA4 原生 scaled-MFMA 支持使得 FP4 路径更具吸引力。

## 4. 推理架构：MiniPIC — 位置无关缓存在 <100 LOC

> **来源**: arXiv 2606.13126 · 2026-06-11 | **实现**: vLLM (<100 行核心修改) | **基准**: 2WikiMultihopQA

### 问题

RAG 和 Agent 负载反复预填充重复的结构化输入（文档、代码文件等），但 vLLM 的 prefix caching 无法复用**非前缀对齐**的 KV 条目。

Position-Independent Caching (PIC) 的现有实现要么需要大量 server 代码修改，要么将 KV 状态保留在 server 外部引入 H2D 传输开销。

### 方法：极简主义 PIC

MiniPIC 仅靠两个组件实现：

1. **无位置编码的 KV cache**：存储未旋转的 K 向量，在 attention 内按每请求逻辑位置应用 RoPE
2. **三个用户级 token 原语**：
   - `block-aligned padding`：对齐块边界
   - `SSep (Span Separator)`：修改 hashing 行为
   - `PDep (Prompt Depend)`：修改块级因果 attention 结构

<img width="1"> 完全兼容 PagedAttention 和 CPU offload

### 性能数据

| 指标 | 改进 vs vLLM baseline | 条件 |
|:-----|:---------------------:|:------|
| **Prefill 吞吐** | **+49%** | interleaved 调度 |
| **缓存 span 的 TTFT** | **最高两个数量级提升** | 重复 span 命中时 |
| **未缓存 span 的 prefill 缩放** | 保持线性 | 无退化的保障 |
| 最坏情况开销 | **仅 5.7%** | 所有场景 |

### 影响判断 🔥

**100 LOC 实现完整 PIC**——这是实用性的胜利。三个 token 原语的设计优雅且可组合，理论上可统一 Block-Attention/EPIC/Prompt Cache 等多种 PIC 方案在一个框架内。

## 5. 推理架构：SwiftCache — 异构模型间 KV 缓存共享

> **来源**: arXiv 2606.16135 · 2026-06-14 | **实现**: vLLM / SGLang 对比

### 问题

多轮对话中历史 token 持续累积，GPU HBM 不足迫使 KV cache offload 到 CPU/SSD，导致 reload 延迟随上下文增长而恶化。

### 方法：跨模型 GPU 内存共享

| 组件 | 功能 |
|:-----|:------|
| **捐赠池** | KV cache 需求低的模型将空闲 GPU 内存借给高需求模型 |
| **NVLink 传输** | 避免慢速 PCIe 传输 |
| **活跃层缓存** | 仅保留当前活跃层的 KV cache 在本地 GPU (sliding window into layers) |

### 性能数据

| 指标 | 改进 vs vLLM/SGLang | 条件 |
|:-----|:-------------------:|:------|
| **P99 TTFT** | **最高 -69%** | 多模型同 server 部署 |
| **最大上下文长度** | **最高 3.98×** | 显存池化后 |
| 对同驻模型干扰 | **极小** | 跨 NVLink 无损共享 |

### 影响判断 🟢

不同于大多数 KV cache 研究关注"压缩一个模型的 cache"，SwiftCache 在**节点级多模型共享**维度发力。在 GPU server 中，空闲 GPU 内存是真实存在的浪费——这一角度很有实际价值。

## 6. 推理路由：ELDR — MoE 解耦推理的专家局部性感知路由

> **来源**: arXiv 2607.00466 · 2026-07-01 | **实验**: vLLM 实现·最大 40 GPU | **模型**: DeepSeek-V2/V3, Qwen MoE

### 问题

PD-disaggregated MoE serving 中：现有 decode 路由器只均衡负载，但相同负载的 worker 在 latency 上可以相差很大——因为每个 decode step 需要加载请求所激活的所有 expert 的权重。

### 方法

| 步骤 | 方法 |
|:-----|:------|
| **专家签名** | 从 prefill 阶段的 expert 激活模式构建预测签名 |
| **离线分区** | Balanced K-means 将签名空间分区到 decode worker |
| **在线路由** | locality-band 路由：请求发送到签名匹配的 worker 中负载最低者 |
| **签名缓存** | 与 KV cache 共索引（KV-block 粒度）→ prefix caching 下签名保持精确 |

### 性能数据

| 指标 | 改进 vs 最优负载均衡基线 | 条件 |
|:-----|:-----------------------:|:------|
| **TPOT 中位数** | **5.9-13.9% 降低** | 3 个 MoE 模型 × 2 种负载 |
| 模型输出 | 不变 | 无损路由 |

### 影响判断 🟢

ELDR 揭示了 MoE PD-disaggregated 中被忽视的问题：**expert locality ≠ load balancing**。签名空间聚类是一个优雅的思路，5.9-13.9% 的 TPOT 提升是"免费的"——不改变模型、不增加硬件。

## 7. 模型优化：YouZhi-LLM — GQA→MLA 自适应过渡 (Ascend 验证)

> **来源**: arXiv 2606.05868 · 2026-06-04 | **硬件**: Huawei Ascend NPU | **框架**: vLLM-Ascend

### 方法

| 组件 | 功能 |
|:-----|:------|
| **层自适应 GQA→MLA 过渡** | 动态分配每层 FreqFold 大小：FreqFold → MLA 的关键压缩维度 |
| **知识蒸馏** | 通用知识蒸馏 + 金融 SFT |

### 影响判断 🟢

GQA→MLA 过渡方向上从"统一替换"到"层自适应分配"的改进。Ascend 生态验证对国产化部署有参考价值。但这一方向依赖于训练后转换，部署灵活性有限。

## 8. 编译器/硬件：eNPU (MICRO'26) — NPU 细粒度 DVFS 节能 25.8-35.2%

> **来源**: arXiv 2607.16473 · MICRO'26 接收 | **硬件**: TPUv4 类 NPU | **负载**: LLM serving

### 核心发现

LLM 中的 tensor operator 在 NPU 不同组件间表现出不同的瓶颈特征 → 每个组件独立配置 V/f 可最大化能效。

### 方法：eNPU

| 组件 | 实现 |
|:-----|:------|
| 硬件 | NPU 核流水线重构 → 组件级独立 V/f 域 |
| 同步 | 轻量跨域通信机制减少同步开销 |
| ISA 扩展 | 子微秒级 DVFS 控制指令 |
| 编译器 | 两级贪心搜索：指令调度 + 每组件 V/f 选择，满足 SLO |

### 性能数据

| 指标 | 数值 | 条件 |
|:-----|:----:|:------|
| **能耗降低** | **25.8-35.2%** | 生产 trace，各种 LLM |
| 面积开销 | **3.45%** (TPUv4) | — |
| SLO 保障 | **严格满足** | — |

### 影响判断 🟢

MICRO'26 的硬件架构工作。核心洞察——LLM tensor 在不同 NPU 组件上的瓶颈有显著差异——是正确的。但从软件角度，DVFS 的粒度从芯片级→组件级后，编译器决策空间的复杂度大幅上升，两阶段贪心搜索的有效性有待更大规模验证。

## 9. 编译器：Transition-Aware Backend Dispatch — 边缘推理 17.4% 延迟优化

> **来源**: arXiv 2607.17415 · 2026-07-21 | **硬件**: NVIDIA Jetson | **后端**: PyTorch eager CPU/CUDA / ONNX Runtime CPU

### 方法

| 组件 | 功能 |
|:-----|:------|
| **Transition-aware 调度** | 结合当前 operator 特征 + 前一个选择的 backend |
| **成本模型** | 实测 operator 成本 + backend 切换成本 |
| **留一法验证** | 7 个模型中 6/6/7 个改进延迟/能耗/EDP |

### 性能数据

| 指标 | 改进 vs 最佳静态策略 | 条件 |
|:-----|:-------------------:|:------|
| **延迟** | **-17.4%** | 平均，9,584 个有序 operator 实例 |
| **能耗** | **-14.4%** | 平均 |
| **能耗-延迟积** | **-28.5%** | 平均 |

### 影响判断 🟢

边缘推理场景中不同 backend 间的切换成本是一个被忽视的问题。切换感知调度在 Jetson 上展示了明确的收益。

## 10. 趋势判断

### 🔥 本期核心信号

| 趋势 | 证据 | 判断 |
|:-----|:------|:----:|
| **解耦推理的边界条件清晰化** | Load-Aware Prefill Deflection 揭示 2-23% 的 prefill 执行占比 → 小集群不适合严格解耦 | 高置信度 🔥 |
| **MoE 推理调度三面受压** | Gimbal (DP-engine)·ELDR (expert-locality)·Gimbal (expert-placement) 三篇同期出现，问题空间开始收敛 | 高置信度 🔥 |

| **编译器: 后端切换纳入优化空间** | Transition-Aware Dispatch 在边缘端被验证 | 早期信号 |

### 需跟踪的问题

- Gimbal 的吞吐提升仅 3%，是 MoE 调度优化的天花板还是实现局限？
- Load-Aware Deflection 的有效性取决于 prefill:decode 资源比——最优比值是多少？
- MiniPIC 的 3 个原语能否标准化为 vLLM 社区接受的扩展接口？
