## 一、ML 编译器与符号优化

### 1.1 Prism — 张量程序符号式超级优化器（4.9× vs 编译器）

> **来源**: arXiv:2604.15272 · cs.LG · Apr 16, 2026 · **作者**: Wu, Jiang, Padon, Jia (CMU)

**核心思想**: 首个张量程序**符号式超级优化器**。核心抽象 `sGraph` —— 以符号化表示部分执行参数（如 tile size、loop order）来紧凑编码大规模程序族的层次化表示。

**两级搜索架构**:
1. **符号图构建层**: 构造符号化程序族，使用符号推理（算子语义 + 代数恒等式 + 硬件约束）**结构性剪枝**确定性次优区域
2. **参数实例化层**: 通过 auto-tuning 从符号族实例化出具体实现

**关键技术**:
- 高效的符号图生成算法
- 基于 e-graph 重写的等价性验证
- 通过 auto-tuning 的参数实例化

**性能数据**:

| 对比对象 | 加速比 |
|:---------|:------|
| vs 最佳超级优化器 | **up to 2.2×** |
| vs 最优编译器方案 | **up to 4.9×** |
| 优化时间减少 | **up to 3.4×** |

**验证负载**: 5 个常用 LLM 工作负载

**意义**: 将超级优化的**穷举搜索彻底性**与编译器方法的**可扩展性**做了以前被认为不可能的桥接。`sGraph` 的符号化程序族编码方式提供了比 e-graph 更高效的等价类探索——这是编译优化工具箱的重要补充。

### 1.2 GPUOS — GPU 操作系统原语：透明算子融合（15.3×）

> **来源**: arXiv:2604.17861 · cs.DC · Apr 20, 2026

**问题**: 现代深度学习工作负载含大量小张量操作（推理/attention/micro-batch训练），kernel launch 开销可超过实际计算时间。

**方案**: GPUOS——基于 **持久 kernel 架构** + **运行时算子注入**的 GPU JIT 系统。
- 单支长期存在的 GPU kernel 持续从 host 管理的工作队列消费任务
- 使用 NVIDIA NVRTC 运行时 JIT 编译算子并通过 **device function pointer table** 注入运行中 kernel
- **双槽别名方案**确保并发安全地进行算子更新

**与 PyTorch 集成**:
- 通过 TorchDispatch 透明拦截，将 micro-operation 批量为统一提交

**性能数据**:

| 场景 | 加速比 |
|:-----|:------|
| 小操作主导的推理/attention 模式 | **up to 15.3×** over standard PyTorch |
| 任意 tensor shapes/strides/dtypes | 通用抽象兼容 |

**意义**: 持久 kernel + JIT 注入的组合攻击了 GPU 编程中一个被长期忽视的瓶颈——kernel launch 开销。如果这项技术能进入 PyTorch 主线，将直接改善 micro-batch 训练和小算子密集型推理的性能特征。

### 1.3 LLVM -O3 优化流水线实证研究（84,750 次测量）

> **来源**: arXiv:2606.31238 · cs.PL · Jun 30, 2026 · Bruzzone, Cazzola

**问题**: LLVM 作为 C/C++/Rust/MLIR 的标准后端，优化 pass 之间的交互、测量噪声和流水线规模使得量化每个 pass 的边际影响极其困难。

**实验设计**: 对 LLVM -O3 流水线的 113 个累计前缀进行 **84,750 次测量**（30 PolyBench/C kernel × 113 prefixes × 25 repeats），覆盖执行时间、编译时间、二进制大小、硬件计数器和 RAPL 能耗。

**核心发现**:

| 发现 | 数据 |
|:-----|:-----|
| 流水线非单调 | **6.6-9.7%** 的过渡导致性能退化 |
| 性能增益严重尾加载 | 中位数需要 **84.8%** 的流水线才能获得 80% 加速 |
| 最终 -O3 非 Pareto 最优 | 对 30 个 kernel 中的 **29 个**，在(大小, 加速)上是被支配解 |
| IR 指令数不可靠 | 不是运行时间的可靠预测器 |
| 运行时优化天然节能 | 30-60% 能源节省 |
| 相位干扰的上界 | 无搜索理想加性上界为 46.35% |

**意义**: 为 pass 剪枝、成本模型校准和自动调优提供了系统的实验基础。`84.8% 的 pass 才获得 80% 收益` 和 `-O3 对 29/30 核不被 Pareto 支配` 这两个发现对编译器设计有直接指导价值。

### 1.4 Neptune — 高级算子融合编译器（3.32× on AMD）

> **来源**: arXiv:2510.08726 · cs.PL · Oct 2025 (Updated Apr 2026) · Zhao et al. (UIUC)

**问题**: 现有张量编译器难以融合涉及**循环携带依赖**的复杂规约计算（如 attention 机制）。

**方案**: Neptune——高级算子融合的**故意打破依赖 + 代数校正表达式**方法。在正确性保证下主动打破某些现有依赖，再用代数校正表达式补偿计算结果。

**关键能力**: 对普通 attention 代码应用 Neptune 的融合 → 自动生成等价于 FlashAttention 和 FlashDecoding 的算子。

**性能数据**:

| 对比 | 加速比 |
|:-----|:------|
| 10 个 attention benchmark 平均 | **1.35×** over next best (Triton/TVM/FlexAttention) |
| NVIDIA GPU 最高 | **up to 2.65×** |
| AMD GPU 最高 | **up to 3.32×** |
| 跨架构验证 | NVIDIA H100/A100 + AMD MI250/MI300 |

**意义**: 无需手写 FlashAttention kernel，从 plain attention 代码 + 高级调度模板出发，自动生成匹敌乃至超越手调 kernel 性能的融合算子。`故意打破依赖` 这个设计模式可能成为 tensor 编译器的新范式。

## 二、GPU Kernel 自动生成

### 2.1 DRTriton — 大规模合成数据驱动的 RL Triton 生成

> **来源**: arXiv:2603.21465 · cs.LG · Mar 2026 (Updated May 2026) · Guo, Lin, Yang

**问题**: LLM 直接将 PyTorch 代码转成高性能 CUDA kernel 仍然困难——GPT-5.2 和 Claude-Sonnet-4.5 表现都不佳。

**方案**: DRTriton——可扩展的 RL 学习框架，将 PyTorch 程序转为优化 Triton kernel 再编译为 CUDA。

**三大组件**:
1. **CSP-DAG** 数据合成算法：保证算子空间全覆盖 + 无偏均匀采样 + 可控难度
2. **解耦奖励的课程 RL**：联合优化 conversion 成功率和执行速度
3. **Test-time search**：进一步提高生成 Triton kernel 的执行速度

**性能数据**:

| 模型 | KernelBench Level 2 超越 PyTorch 比例 |
|:-----|:--------------------------------------|
| DRTriton-7B | **92%** |
| GPT-5.2 | 23% ❌ |
| Claude-Sonnet-4.5 | 19% ❌ |

**意义**: 7B 参数通过 RL 超越 10 倍以上参数的前沿 LLM——证明**针对性的 RL post-training 比模型规模更重要**。CSP-DAG 的合成数据生成方法可复用。

### 2.2 KernelSmith — 进化式 Kernel 优化框架（KernelBench SOTA）

> **来源**: arXiv:2603.28342 · cs.LG · Mar 2026 (Updated Apr 2026) · Du et al. (Kai Chen group)

**方案**: 双组件系统——
- **Agent 侧**: 进化式 agent 维护可执行候选项种群，使用**性能/多样性归档** + 结构化执行反馈（编译/正确性/加速比）迭代改进
- **训练侧**: 将长 horizon 进化轨迹转为 step-centric 监督/RL 信号

**多平台验证**: NVIDIA Triton 和 MetaX MACA 双后端

**性能数据**:

| 配置 | 成绩 |
|:-----|:------|
| KernelSmith-235B-RL (NVIDIA) | **KernelBench SOTA**，超越 Gemini-3.0-pro 和 Claude-4.6-opus |
| KernelSmith-MACA-30B (MetaX) | 超越 DeepSeek-V3.2-think 和 Qwen3-235B-2507-think |
| 生产贡献 | 已为 SGLang 和 LMDeploy 提交上游优化 |

**意义**: 证明 LLM 驱动 kernel 优化可以从基准测试转移到**生产部署**——进化轨迹转化为训练信号的管线设计值得借鉴。

### 2.3 TritorX — MTIA 全算子后端自动生成（481 ATen ops）

> **来源**: arXiv:2512.10977 · cs.LG · Dec 2025 · **Meta (MTIA team)**

**方案**: 用于新兴加速器平台的 agentic AI 系统，自动生成功能正确的 PyTorch ATen kernel。集成开源 LLM + 自定义 linter + JIT 编译 + PyTorch OpInfo 测试框架。

**关键特性**:
- 覆盖 vs 性能的取舍：优先全算子覆盖
- 兼容 Meta Training and Inference Accelerator (MTIA) 真片与模拟环境

**性能数据**:

| 指标 | 数值 |
|:-----|:------|
| 成功生成的 ATen 算子 | **481 个**（通过全部对应 OpInfo 测试） |
| 总测试数 | **20,000+** |

**意义**: `overnight generation of complete PyTorch ATen backends`——对于新硬件平台的软件栈建设，这是一个**范式级的提速**。传统需要数月的手工算子移植，agentic pipeline 可能做到隔夜完成。

### 2.4 Astra — 多智能体 GPU Kernel 性能优化（1.32× on SGLang）

> **来源**: arXiv:2509.07506 · cs.LG · Sep 2025 (Updated Dec 2025) · Wei et al. (Stanford)

**方案**: 首个 LLM 驱动的多智能体 GPU kernel 优化系统。专业 LLM agent 通过**迭代代码生成→测试→profiling→规划**循环协作。

**与已有工作的关键区别**: 从 SGLang 中提取的现有 CUDA 实现出发，而非从 PyTorch 模块做规格。

**性能数据**:

| 设置 | 成绩 |
|:-----|:------|
| Zero-shot (OpenAI o4-mini) | **平均 1.32×** 加速 on SGLang kernels |
| 典型案例 | 自动应用 loop 变换/内存访问优化/CUDA intrinsics/fast math |

**意义**: 验证了 LLM 多智能体协作在**已知正确但未优化**的 kernel 上做迭代优化是可行路线。与 DRTriton/KernelSmith 的从零生成互补。

## 三、推理框架新进展

### 3.1 AngelSpec — 统一投机解码训练框架（1.98-2.40×）

> **来源**: arXiv:2607.25852 · cs.CL · Jul 28, 2026

**问题**: 不同工作负载下最优 draft 结构不同——自回归 MTP 对高熵开放对话好，block-parallel diffusion 对代码/数学的长可预测延续好。

**方案**: 三层次统一框架——

| 层次 | 设计 | 效果 |
|:-----|:-----|:------|
| **训练层**: 协同特化 | MTP drafter 训练于多样化对话数据，block-diffusion 训练于代码/数学数据 | 结构-数据配对优化 |
| **架构层**: DFly | 混合目标条件 backbone + 前驱条件自回归 head | 提高目标特征利用 + intra-block 依赖建模，保持生成并行性 |
| **推理层**: 自适应验证 | verification 视为共享 batch 级资源，预期效用 + profiling 成本模型在线调整 | 高置信前缀优先分配计算 |

**性能数据**（Hy3 系列）:

| 指标 | 数值 |
|:-----|:------|
| DFly 平均接受长度提升 | **~30%** |
| 吞吐加速 vs 自回归解码 | **1.98-2.40×** |
| 吞吐 vs DFlash | **+10.5-11.8%** |
| 并发 4-64 全部覆盖 | 所有测试并发下最高吞吐 |

**意义**: 统一了 MTP 和 block-diffusion 两种投机解码路线的训练框架。`co-specialization` 思路（不同 drafter 有不同的训练数据配置）是原创贡献。

---

### 3.2 PopPy — Compound AI 应用自动并行化（6.4×）

> **来源**: arXiv:2605.18697 · cs.PL · May 18, 2026 · Mell et al. (UPenn)

**问题**: Compound AI 应用中执行时间由外部组件（ML 模型调用）主导，传统优化编译器无法处理。

**方案**: 结合 AOT 编译器 + runtime 的系统，自动发现 Python 应用中的并行化机会。
- 支持表达力丰富的 Python 子集，最小化开发者输入
- 解决三个核心挑战: 语言复杂性、动态分发、变量变更

**性能数据**:
- **最高 6.4×** 端到端加速（真实 Compound AI 应用）
- 保持顺序程序语义不变

**意义**: 填补了`外部组件主导执行`场景下的并行化空白——不是优化循环/内存，而是识别哪些外部调用可以并行。

---

### 3.3 stratum — Agentic Pipeline 搜索基础设施（16.6×）

> **来源**: arXiv:2603.03589 · cs.DC · Mar 2026 (Updated Mar 2026)

**问题**: LLM agent 执行 agentic pipeline search 时产生数千个 ML pipeline 执行，现有 Python ML 生态（Pandas/scikit-learn）不适合大规模并行执行。

**方案**: stratum——解耦 pipeline 执行与规划/推理的统一基础设施。
- 无缝集成现有 Python 库
- 将 pipeline 批量编译为优化执行图
- 跨异构后端高效执行（含 Rust-based runtime）

**性能数据**:
- **最高 16.6×** 加速 agentic pipeline search
- 保持与 Python ML 生态的完整兼容性

**意义**: 解决`AI agent 自己写代码跑实验`这种大规模工作负载的系统瓶颈。与 PopPy 不同，stratum 关注的是 pipeline 批量编译而非函数调用并行化。

## 四、训练框架

### 4.1 BluTrain — 从第一性原理构建的 C++/CUDA 训练框架

> **来源**: arXiv:2606.24780 · cs.LG · Jul 6, 2026

**方案**: 完全用标准 C++ 和核心 CUDA 编程模型从头构建的训练框架。每个层原生实现：
- 带反传自动微分的类型化 tensor 模块
- 线性代数库 + 缓存分配器 + 多模式分布式执行模块
- MLIR 深度学习编译器

**性能数据**（GPT-2 124M, FP32, 8×6000 Ada）:

| 对比对象 | Tokens/s | 显存占用 |
|:---------|:--------:|:--------:|
| **BluTrain** | **407K** | **-22%** |
| PyTorch | 395K | 基线 |

**意义**: 证明了`避开框架膨胀`可以在不牺牲数值精度和收敛质量的前提下提升性能和内存效率。性能提升虽不大（~3%），但 22% 的内存节省和完全可控的实现是有价值的工程参考。

### 4.2 PyTorch 博客：Monarch on AMD GPU（2026-07-06）

> **来源**: PyTorch Blog · AMD + Meta

**内容**: PyTorch Monarch（单控制器分布式训练）扩展到 AMD ROCm GPU。Monarch 的分布式策略现在在 AMD GPU 上得到原生支持。

**关键细节**:
- 单控制器范式：一个进程管理所有 GPU（通过 CUDA-like 抽象）
- 原生集成 ROCm 的 backend 支持
- 目标：降低多 GPU 训练的运维复杂性

**意义**: 标志着 PyTorch 多平台战略的持续推进——分布式训练框架不再仅优化 NVIDIA 平台。

### 4.3 PyTorch 博客：Towards Free Normalization（2026-07-10）

> **来源**: PyTorch Blog · Jul 10, 2026 · Jacky Zhou, Hongtao Yu et al.

**内容**: 将 Normalization 层融合到 GEMM 和 Attention kernel 中的新型 kernel 融合技术。

**核心创新**:
- LayerNorm / RMSNorm 在 GEMM 输出阶段**零额外内存往返**完成
- Attention 后 normalization 整合到 flash-decoding 的最终归约阶段
- 无需额外的 kernel launch 或中间显存读写

**性能数据**（文中未提供硬数字，方向性结果）:
- GEMM + Layernorm **fused kernel** 明显减少 launch 开销和显存带宽占用
- Attention + Normalization **fused** 在长序列场景收益显著

**实现方式**: Triton 和 CuTe DSL 双路径实现

**意义**: 在 `LLM 推理中的 normalization 开销占总延迟约 5-15%` 的背景下，融合到 GEMM/Attention 中可使 normalization 变成 `近乎免费` 的操作。这是 PyTorch 编译器团队`推理性能优化的微观层面`信号。

## 五、安全与系统

### 5.1 Quantamination — 动态量化跨批次数据泄露

> **来源**: arXiv:2604.26505 · cs.CR · Apr 29, 2026 · Foerster et al.

**问题**: 动态量化虽然是最广泛推荐的 ML serving 优化手段之一，但在实现不当时会创建 side channel，暴露同一 batch 中其他用户的数据。

**核心发现**:
- 至少 **4 个主流 ML 框架**（含 ML 编译器和推理引擎）默认或可配置使用有漏洞的量化配置
- 攻击者可**部分甚至完全恢复**同批次中其他用户的输入数据
- 动态量化本应提升效率，但不当实现导致**严重隐私风险**

**影响**: 当前被广泛推荐为`ML serving 第一步优化`的动态量化在安全审计视角下需要重新评估。

**意义**: 对于生产环境部署 ML serving 的用户，这是一个需要立即关注的安全告警——建议进行量化策略的安全审计，特别是多租户场景。

---

## 六、综合观察

### 架构趋势

1. **GPU Kernel 自动生成进入第二波**: 从 `LLM 单次生成` → DRTriton/KernelSmith 的 `进化/RL 迭代` → Astra 的 `多智能体协作`。KernelBench 已是事实标准，7B 模型已验证可通过 RL 超越 GPT-5.2（92% vs 23%）

2. **符号推理回归编译器工具箱**: Prism 的 sGraph 符号编码 + e-graph 等价性验证，证明符号方法在处理大规模搜索空间时比纯枚举式超级优化更有效——这是对 e-graph 热潮后`一切皆重写`的适度回调

3. **持久 kernel 架构崛起**: GPUOS 的持续 kernel + JIT 注入（15.3×）、Neptune 的`依赖打破+代数校正`、Syncopate 的 chunk 级通信重叠——三种不同的方法都在攻击 kernel launch 和中间内存带宽瓶颈

4. **安全与性能的权衡重新打开**: Quantamination 揭示动态量化可能暴露用户数据，四项 26 年流行框架受影响——隐私面被低估了

5. **LLVM 基线假设被实证测试**: -O3 对 29/30 核不是 Pareto 最优，84.8% 流水线才获 80% 收益——编译器的默认策略可能需要硬件/工作负载感知的定制

### 关注/跟进

- **Prism 的 sGraph 实现**——是否开源，能否与 Triton 编译器集成
- **GPUOS 的 TorchDispatch 拦截**——是否可能进入 PyTorch 主线
- **Astra / DRTriton / KernelSmith 三者的生产化进展**——谁先落地到 vLLM/SGLang 上游
- **Quantamination 的 CVE 编号和修复状态**——当前部署的 ML serving 是否受影响
- **Neptune 的跨架构稳定性**——attention 之外的更通用场景验证
