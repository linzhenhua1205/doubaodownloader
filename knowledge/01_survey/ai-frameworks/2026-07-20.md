## 1. 编译器优化：Triton 3.7 Plugin Extensions + TLX

> **来源**: PyTorch Blog · 2026-07-15 | **相关**: 编译器生态

### 核心发布：Triton Plugin Extensions 系统

PyTorch-Triton 3.7 引入了**通用插件扩展系统**，允许在运行时动态加载自定义编译器 pass、方言（含其 ops）和 DSL 扩展，**无需 fork 或重新编译 Triton**。插件以 `.so` 共享库形式分发，通过 `TRITON_PLUGIN_PATHS` 环境变量在运行时发现和加载。

### 插件能力

| 能力层级 | 描述 |
|:---------|:-----|
| 自定义转换 pass | 在管线任意点插入单个 pass，无需关联方言 |
| 自定义 MLIR 方言和转换 pass | 独立编译的方言加载到 Triton，含标准 IR→方言 rewrite |
| 自定义顶层 DSL ops | 新 Python 级语法和语义，不修改 Triton 自身 |

### TLX (Triton Language Extensions) 现为内置

Meta 开发的 TLX 专注显式内存管理和异步计算/加载流水线，此前只能用 Meta 的 Triton fork。现在以 `utlx` 包（PyPI: `triton-utlx`）发布，可在**未经修改的上游 Triton** 上运行。

#### 关键 TLX 操作

| 操作 | 描述 |
|:-----|:------|
| `tlx.local_alloc` | 分配共享内存缓冲用于软件流水线 |
| `tlx.async_load/commit/wait` | 异步全局→共享内存加载流水线 |
| `tlx.async_dot/wait` | 异步矩阵乘法累加 |
| `tlx.local_store/local_load` | 共享内存↔寄存器 |

### 影响判断 🔥

Triton Plugin Extensions 是**编译器生态的范式转变**——不再需要维护 Triton fork 来获得硬件特定性能。这意味着：
1. TLX 等扩展的核心能力现可供**所有 Triton 用户**开箱使用
2. 自定义 backend（Intel/CPU）、分布式原语（`triton-distributed`）、性能分析工具可全部插件化
3. **同 kernel 代码同时跑 H100 和 MI350** 且超越各自厂商库（cuBLAS/rocBLAS）

## 2. 训练框架：Towards Free Normalization (Meta·B200)

> **来源**: PyTorch Blog · 2026-07-10 | **DSL**: TLX + Helion | **硬件**: NVIDIA B200 (750W PL)

### 问题

- LayerNorm/RMSNorm 占 Meta Kunlun 训练延迟 **~20%**、LLM 推理 **~10%**
- 内存密集型：无 TensorCore 利用率
- 融合挑战：norm 按行归约 vs GEMM 双维 tile，tiling 不匹配

### 三阶段融合技术

#### ① Lazy Pre-Norm（Prologue Fusion）

**核心洞察**: 无仿射 RMSNorm 的行乘 `rstd` 是逐行操作，满足 `(A * rstd) @ B = (A @ B) * rstd`

这意味着 rstd 归约与 GEMM 并行计算，逐元素应用延迟到 K 循环结束后——成为 epilogue。

```
def GEMM_norm_fusion_kernel(A, B, C):
    square_sum += (tile_A²).sum(-1)  <- 与 GEMM 并行
    rstd = rsqrt(square_sum / ...)
    acc *= rstd[:, None]             <- K 循环后延迟执行
```

| 形状 (K/N) | 64 | 128 | 256 | 512 | 1024 |
|:-----------|:--:|:---:|:---:|:---:|:----:|
| LayerNorm 延迟节省 | **32%** | **17%** | 6% | −5% | −18% |

- 小 N 有效（17–32%），大 N 因 tile 偏差导致回归
- **局限**: 不支持仿射/不支持 LayerNorm

#### ② Multi-CTA Norm Fusion（Epilogue Fusion）

利用 Blackwell CTA 集群 + 分布式共享内存（DSMEM），将大 N 拆给集群内多 CTA：

```
acc = multi_cta_norm(acc)  <- CTA 间 DSMEM 通信完成归约
```

- 每 CTA 上限 ~512 → 集群 ×8 → N 上限 **4096**
- 限制：相邻 CTA 必须共享相同 m_tile| 配对 CTA matmul 困难

> M=256K, K=O(512), N=O(512) 形状：norm 延迟**几乎完全隐藏**

#### ③ FlashNormAttention（Megakernel）

将 GDPA 注意力的前后**两个 norm + 两个残差连接**全部融合到一个 kernel：

- SMEM/TMEM 复用：TMEM accum 实现 `ln_q + p@v` 零额外开销
- TMA_REDUCE_ADD 处理外残差
- 寄存器 sub-tiling 防 spill

**性能**:

| 配置 | Head dim=128, KV=128, Q sparsity=0.5, BS=768 |
|:-----|:---------------------------------------------|
| **Forward** | 最高 **35%** kernel 延迟降低 |
| **Backward** | 对应加速（epilogue 融合避免 prologue 退化） |
| **关键** | Backward 通过"融合重组"（forward 与不同 linear 融合）使 backward 也是 epilogue 融合 |

### 影响判断

FlashNormAttention 是一种**模式性优化**——适用任何"norm→dense→norm→residual"模式的运算链。对于 LLM 和 RecSys 场景，norm 延迟从 10–20% 降至**接近 0 开销**。

## 3. 推理优化：Dustin 稀疏验证推测解码 (ICML'26)

> **来源**: arXiv 2606.24957 · ICML'26 接收 | **模型**: Qwen2.5-72B | **数据**: PG-19, LongBench

### 问题

推测解码的 verification 阶段 KV cache 加载成为瓶颈（长上下文场景）。现有 KV 压缩在 verification 路径上不可用：静态 eviction 精度损失，动态选择开销过大。

### 方法

Dustin 利用 draft 模型的 lookahead 信号 + target 模型的历史注意力识别关键 token，对 attention head 做最小子集稀疏估计。验证时只计算关键 token 的 attention。

### 性能数据

| 指标 | 加速 | 条件 |
|:----|:----:|:-----|
| self-attention | **27.85×** | 32k 序列 |
| **端到端解码** | **9.17×** | 32k 序列 |
| 精度 | 可忽略损失 | PG-19 / LongBench |

### 影响判断

在**长上下文推测解码**场景下，Dustin 提供了目前最强的端到端加速。其验证稀疏化方法不依赖特定 KV 压缩，可与主流缓存方案叠加。

## 4. 通信优化：TokenWeave AllReduce-RMSNorm 融合 (MLSys'26)

> **来源**: arXiv 2505.11329 · MLSys'26 接收 | **硬件**: 8×H100 DGX | **来源**: Microsoft Research

### 问题

分布式推理的 tensor parallelism 即使在 NVLink 上也有 **20%+** 通信开销。现有分解计算→重叠通信的技术在 token 数 <1024 时反而更差，因为通信占用过多 SM。

### 方法

TokenWeave 识别 RMSNorm（之前被忽视）作为关键操作，实现**融合 AllReduce-RMSNorm kernel**，利用 NVSHARP/Multimem（Hopper/Blackwell）仅用 **2–8 个 SM** 完成通信+norm。

### 性能数据

| 指标 | 加速 |
|:----|:----:|
| **Latency** | **1.28×** (基线÷ours) |
| **Throughput** | **1.19×** (ours÷基线) |
| 多模型设置 | 部分优于**零通信理想情况** |

### 影响判断

TokenWeave 是**首个实现在 TP token=1024 时高效通信重叠**的系统。融合 AllReduce-RMSNorm 的设计简洁有效，已开源（`github.com/microsoft/tokenweave`）。

## 5. 推理架构：HMA-Serve 跨厂商解耦推理

> **来源**: arXiv 2606.29986

### 核心思路

- **Prefill**（计算密集）→ GDDR 加速器（低 $/TFLOP）
- **Decode**（内存密集）→ HBM GPU（高带宽）
- 跨厂商意味着 KV 格式不匹配 + 软件栈不同 → 需解决格式转换和传输

### 三大组件

1. **Phase-wise quantization**: prefill 用厂商原生低精度 → decode 用 BF16
2. **Compute-transfer pipeline**: 每层的 KV transfer 与下一层 prefill 重叠
3. **Deferred dequantization**: 传输量化字节，在 decode GPU 上延迟重建

### 性能数据

| 模型 | Goodput | Goodput-per-dollar |
|:----|:-------:|:------------------:|
| Qwen3 4B–32B (×4模型) | **3.2×** vs State-of-the-art | **4.8×** |
| 生成质量损失 | **零可测损失** | — |

## 6. KV 调度：PEEK 预测性队列感知管理

> **来源**: arXiv 2607.02525 | **引擎验证**: SGLang + vLLM | **硬件**: 4×H100 (DP=2×TP=2)

### 方法

PEEK 维护挂起队列的增量 radix tree，暴露前缀共享集群。双步遍历匹配 tree vs 引擎 prefix cache → 返回每个等待请求的最长前缀匹配 → 优先准入集群先锋 → 协同 eviction 保护祖先块 → 多道 stride 调度限制饥饿。

### 性能数据 (vs 各引擎最强基线)

| 指标 | SGLang | vLLM |
|:----|:------:|:----:|
| **Cache Hit** | **3.0×** | **2.6×** |
| **TTFT** | **7.9×** | **7.1×** |
| **E2E 延迟** | **6.7×** | **5.5×** |
| **Throughput** | **3.6×** | **4.5×** |

无前缀结构的工作负载上匹配基线（无回归）。

## 7. KV 压缩：SeKV 分辨率自适应语义缓存

> **来源**: arXiv 2606.31145 | **上下文**: 128K | **GPU**: GPU-CPU 层次

### 方法

将上下文组织为熵引导的语义 span，按 GPU-CPU 层次存储：GPU 存轻量摘要向量用于粗路由，CPU 存低秩 SVD 基用于按需 token 级重建。训练好的 zoom-in 机制在解码时选择性展开查询相关 span。

## 9. KV 存储：Fractal KV-Cache 无损符号归档

> **来源**: arXiv 2607.07144

### 核心

用 contractive iterated-map codes 将量化 KV 符号流序列化为低维实向量，形成天然存档格式：

- **无损**、线性时间、O(1) 随机访问、O(1) 均摊 append
- **同时是搜索索引**：近似子串查询直接在存储向量上执行

### 性能数据

| 方法 | 压缩比 | 困惑度代价 |
|:-----|:------:|:----------:|
| 逐头残差 VQ | **36–54×** | 11–15% |
| 关键发现 | Key 量化损伤 ≈ Value 的 **4×** | → 混合位分配 |

### 影响判断

Fractal KV-Cache 的**符号存档即搜索索引**设计具有突破性——不再需要传统 KV cache 管理（eviction/offloading），而是"存了就能搜"。但当前仅验证 GPT-2。

## 10. 自适应推理：HARD-KV 头自适应正则化压缩

> **来源**: arXiv 2606.28831 · ICML'26 poster | **引擎**: vLLM 兼容

### 方法

解决**动态选择 vs 静态内存布局**的矛盾——Top-p 级别的 head 自适应压缩精度更高但内存波动，vLLM 的 PagedAttention/CUDA Graphs 要求静态内存。

- **Cascade Cache 层次**: dense → sparse → condensed 三级 token 生命周期管理
- **Logits Calibration**: 不同 head 的 importance metric 归一化为统一概率空间
- **动态转静态**: 碎片化动态索引 → 连续物理布局适配 vLLM

### 性能数据

| 指标 | 加速 | 场景 |
|:----|:----:|:-----|
| **Throughput** | **2×** | vs 静态基线 |
| 精度 | 保持 | AIME, U-Math, 10K+ token |

## 11. 趋势判断

1. **Triton Plugin Extensions 标志着编译器生态的「去 fork 化」** 🔥
   - 不再需要维护 Triton fork 获得硬件特定性能
   - TLX 跨 H100（+2~4% vs cuBLAS）和 MI350（+12~15% vs rocBLAS）均超厂商库
   - 为自定义 backend、分布式原语、性能分析工具的全插件化铺平道路

2. **Normalization「免费化」成为训练/推理的共同目标**
   - Lazy Pre-Norm（H100）+ FlashNormAttention（B200）将 norm 从 10–20% 延迟降至接近零
   - 与 TokenWeave（通信侧融合 RMSNorm）形成互补：计算侧+通信侧双向消除 norm 开销

3. **KV 压缩走向存算一体（compute-capable storage）**
   - Fractal KV-Cache 的"存档即索引"是最激进的设计——不再需要 eviction 决策
   - SeKV 的 GPU-CPU 层次 + 按需重建也走向类似方向

4. **推测解码在长上下文场景实现 9×+ 端到端加速**
   - Dustin (ICML'26) 在 32K 序列上自注意力 27.85×、端到端 9.17×
   - 稀疏验证方法不依赖特定 KV 压缩方案，可叠加
