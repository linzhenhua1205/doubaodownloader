## 一、arXiv 新论文精选（2026-07-15 新列表）

### 🥇 Kv Cache 压缩：Query Visibility 改变排名（cs.LG, Jul 11）

> arXiv:2607.11942 · 144,300 paired evaluations on RULER-8192; 40,800 on LongBench; 50,000-resample bootstrap

**核心发现**：KV cache 压缩方法的评测长期使用 query-aware 协议（压缩前 query 已附在 context 中），但实际复用场景是 query-agnostic（压缩一次，回答多个 query）。

**性能数据**：

| 方法 | Query-aware vs Query-agnostic 变化（Δ） | 在 agnostic 下的表现 |
|:-----|:--------------------------------------|:-------------------|
| **SnapKV**（最广泛部署） | Δ = +0.198（**最大下降**） | **输给** "keep start + recent window" baseline（-0.066） |
| **KeyDiff** | Δ = +0.011（**最小退化**） | 唯一**一致胜出**所有 trivial baseline 的方法（31 of 36 cells） |
| 其他 4 种方法 | Δ 介于两者之间 | 均无法在所有配置下击败基线 |

**启示**：
- SnapKV 的评分信号天然依赖 query（64-token observation window），在 query-agnostic 下失效
- KeyDiff 的评分不含 query 项，因此两种协议下几乎无差异
- **如果要部署 KV cache 压缩用于长期缓存复用，必须用 query-agnostic 协议重评**

### 🥇 LiteTopK: 融合 Indexer-TopK Kernel（cs.LG, Jul 13）

> arXiv:2607.11976 · 用于 long-context sparse attention

**问题**：Indexer-TopK（DSA 的核心操作）在 GPU 上存在全局内存流量过大、同步开销高、内存开销大的问题。

**创新**：利用高维空间的"维度诅咒"（向量距离集中在窄范围内），先采样小部分数据估算 score 范围，然后在线分区候选结果，只回写有希望的 candidates。

**性能**：

| 场景 | 加速 | 内存 |
|:-----|:-----|:------|
| **GLM 5.2 prefill stage** | **1.2× speedup** | 更低 |
| **Top-k 精确性** | 保持 exact（无损） | — |

**意义**：直接改进 DSA 效率，影响 DeepSeek-V4/GLM-5 等使用 sparse attention 的模型推理。

### 🥇 N:M Sparse Transformer — Kernel + 稀疏搜索协同设计（cs.AR, Jul 14）

> arXiv:2607.12505 · Accepted at Euro-Par 2026

**问题**：N:M 半结构化稀疏的理论加速难以转化为实际端到端加速，因为稀疏下的调度不规律性抵消了算力节省。

**方案**：
- **硬件**：MD-SpMM kernel — 将稀疏 GEMM 重排为 micro-dense、TensorCore 对齐的数据流，使用 inference-aware 自适应并行
- **软件**：三层启发式搜索（constraint relaxation）分配逐层稀疏度，以显式端到端延迟预算为目标

**性能**：

| 对比对象 | 加速比 |
|:---------|:-------|
| 端到端稀疏 ViT 推理 | **>2.2× latency speedup** |
| 同等延迟下精度 | 优于非稀疏方法 |

---

### 🥇 HeteroMosaic: Edge LLM 异构推理调度（cs.DC/cs.AR, Jul 14）

> arXiv:2607.12839 · AMD Ryzen AI 平台实现

**问题**：Edge SoC 有 CPU/iGPU/NPU，但现有推理运行时只做粗粒度设备决策，浪费异构资源。

**方案**：HeteroMosaic — 异构 roofline model + dependency-preserving micro-batches + trace-guided 调度和设备分配协同优化（考虑 memory contention / DVFS / device variation / NPU runtime overhead）

**性能**（balanced platform）：

| 对比 baseline | 加速 | 能效 |
|:-------------|:----|:-----|
| vs iGPU 基线 | **1.73×** | — |
| vs NPU 基线 | **1.78×** | — |
| vs 现有框架（如 llama.cpp） | **2.05×** | **-45.3% energy** |
| vs 异构 edge AI 方案 | **2.35×** | — |

## 二、推理框架更新

### 2.1 vLLM v0.25.1 Patch（Jul 14）

已报道于 v0.25.0（Jul 11）基础上的补丁版本。两项关键修复：

#### 修复 1：FFmpeg 缺失导致模型加载阻塞
- `import torchcodec` 在没有 FFmpeg 的系统上抛出 `RuntimeError`
- 导致 `vllm serve Qwen/Qwen3-VL-2B-Instruct` 启动失败
- 修复：将错误推迟到运行时，仅在实际使用 TorchCodec 时触发

#### 修复 2：混合 dtype 下 allreduce RMSNorm quant 融合 bug
- **场景**：BF16 residual stream + FP32 RMSNorm weight（NVFP4 模型）
- **表现**：隐藏状态损坏 → 输出全是 `!!!!!` 重复 token
- **根因**：FlashInfer allreduce + RMSNorm + static-quantization 融合模式匹配时，未校验激活和权重 dtype 是否一致
- **修复**：添加 dtype-match guard，不匹配时路由到安全路径
