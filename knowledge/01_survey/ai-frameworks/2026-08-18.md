- **The Integer Alibi: Localizing Cross-Kernel Divergence in INT8-Quantized LLM Inference**（[arXiv:2608.13756](https://arxiv.org/abs/2608.13756)，08-13，companion: 2608.11693）: 固定 checkpoint/提示/硬件/引擎/解码/量化配置，仅在 vLLM 内互换 INT8 GEMM kernel（CUTLASS ↔ Triton），**端到端任何序列都无法 bit 级对齐（0/8、0/16、0/64）**；但喂给两个 kernel 完全相同的操作数（Qwen3-1.7B/8B 共 196/252 层），在 2 的幂 scale 下输出 bit 一致（预注册预测 196/196、252/252 全中）——由于 INT32 点积在无溢出下精确且与顺序无关，累加器被排除为分歧源，**分歧被精确定位到 scale 应用与输出舍入（至多 1 个 bfloat16 spacing）**；同一干预作为探针 checkpoint 恢复端到端 bit 级一致（8/8、16/16）。跨实现 FP8 GEMM 显示不同签名：分歧普遍性与幅度随 reduction depth 增长，而 INT8 分歧在 64x K 范围保持 ppm 级且 ≤1 spacing。对推理框架的启示：**kernel 互换性不是默认属性，INT8 的"整数不在场证明"把正确性验证从黑盒对比变成可预测的分层定位**（预注册 + 逐层预测 + kernel 证据清单）。
- **Multi-tenant Kubernetes Use Cases for AI, Secure Computing and Data Services**（[arXiv:2608.00742](https://arxiv.org/abs/2608.00742)，08-01，ACM/IEEE 会议收录 DOI:10.1145/3837730.3837733）: HPE Cray EX 超算（Isambard-AI，Slingshot 互联）上评估 Kubernetes 多租户部署：① Trusted Research Environment（医疗健康机密计算）；② **KubeRay + Ray + vLLM 组合提供分布式、沙箱化、持久化的多租户 AI 模型托管服务**（面向机密计算）。论文明确 Kubernetes 不是 MPI 批调度的替代品而是补充——"national AI Research Resource"的一等公民服务。对框架层意义：**vLLM 作为超算级多租户推理服务组件首次出现在 HPE Cray EX 生态的官方评估中**，裸金属 + Slingshot + K8s 的组合是超算中心向 AI 服务转型的部署模板。

## 📊 本期观察（本组视角）

### 分析一：kernel 互换性不是默认属性——"整数不在场证明"把正确性验收从黑盒推向分层可预测

The Integer Alibi 的价值不在"发现两个 kernel 输出不同"（这早已被 08-14 Spec Sheets 审计的 INT8 栈级撤退所预告），而在**方法论**：INT8 的数学结构（INT32 累加器在无溢出下精确且与顺序无关）天然排除了累加器作为分歧源，从而把差异**精确定位**到 scale 应用与输出舍入这两个"后处理"环节——这是量化推理正确性验证从"黑盒端到端对比"走向"可预测的分层定位"的范式证据。更深一层，该文与 08-15 期"AI 生产链正确性验收"主线（正确性由预计算保证）形成闭环：**预注册预测列表（196/196 全中）+ 逐层 kernel 证据清单 + 探针干预恢复位级一致**，正是把"验收"从一次性的端到端跑分变成可持续的回归护栏。而 FP8 与 INT8 的分歧签名差异（FP8 随 reduction depth 增长、INT8 保持 ppm 级）说明：**不同量化格式的"分歧物理"不同**——FP8 的指数位有限导致舍入误差随归约深度累积，INT8 的误差只来自单点 scale/舍入。对框架工程团队的实操含义：① 多 kernel 后端（CUTLASS/Triton/FlashInfer 等）并存时，跨后端一致性测试必须纳入 CI 门禁，且应按"先验可预测层 → 后验黑盒层"两阶段设计；② 部署 INT8 模型时"同接口互换 kernel"的假设需要显式验证，且验证协议应预注册（pre-registration）以避免事后选择性报告。

### 分析二：开源推理框架进入"PR 洪流时代"——21x 吞吐增长背后的跟进成本重估

Engineering Signals 提供了罕见的仓库级纵向证据：vLLM/SGLang 的 PR 吞吐从 2023/2024 到 2026 年增长 21x/17.9x，且增长几乎全由人类贡献（bot PR <0.2%）、评论密度 +4.2x/+3.8x、月度作者持续增长——这是一个"产能爆炸但未自动化"的混合信号。结合 v0.27.0 单版本 561 commits/242 贡献者的数据，**vLLM 已稳定处于"每月数千 PR"的节奏**（18,290 PR / 41 个月 ≈ 446 PR/月，且仍在加速）。对框架跟进策略的含义有三层：① **API/行为变更风险**：如此高的变更速率意味着框架行为（调度、KV cache、量化路径）可能在 patch 版本间漂移——08-13 起知识库已记录多起"同版本不同 kernel 输出不同"案例，跟进方必须 pin 版本 + 记录 commit hash；② **上游审阅带宽成为瓶颈**：P90 cycle time 16.8 天说明大量 PR 需要等待，功能落地节奏 ≠ 代码合并节奏，企业采用框架时应关注"已合并未发布"功能与"已发布未稳定"功能的区分；③ **人机协作的产能结构**：bot 评论仅占增量 15-20%、bot PR <0.2%，说明当前 AI 辅助开发主要是"加速人类审阅与写作"而非"替代人类提交"——但这一比例是动态的，建议将"bot 参与率"作为框架健康度的持续观测指标（若未来 bot PR 占比快速上升，框架的治理与安全审查模型需同步升级）。该文同时给出 SGLang 中位 cycle time 0.62 天 < vLLM 1.04 天的对比——SGLang 以更小 PR 规模（14,938 vs 18,290）实现了更快合并节奏，两框架"吞吐 vs 速度"的工程文化差异值得单独追踪。
