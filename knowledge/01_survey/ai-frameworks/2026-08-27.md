### 2. Kimi-K3 优化栈——从 kernel 到调度器的全栈穿透

Kimi-K3 是 2.8T 参数 LatentMoE（896 experts / top-16 / 3584 维潜在空间路由，69 层 KDA 线性注意力 + 24 层 MLA 交错），其推理难点在于**长上下文（1M token）下的线性注意力内核效率、解码并行度与 MoE 大专家内存**。v0.28.0 的优化清单直指这三处：

| 优化项 | 机制 | 量化收益（官方数据） |
|:--|:--|:--|
| Decode Context Parallel (DCP) | 解码阶段上下文并行切分 | 长上下文解码跨节点扩展（#50484） |
| Fused FlashKDA decode/prefill kernels | KDA 线性注意力融合内核 | decode+prefill 双阶段提速（#50654/#51311/#52458） |
| SiTU activation for MegaMoE | MoE 激活函数内核支持 | 大专家 MoE 前向提速（#50510） |
| GEMM-RS for sequence parallelism | 序列并行下 GEMM 归约散射融合 | 序列并行通信削减（#52079） |
| Combined all-gathers | 合并多次 all-gather 为一次 | **kernel 级 1.5~3× 提速**（#51070） |
| Adaptive speculative token budget | 按置信度动态调整投机 token 预算 | **DSpark TTFT 改善 ~60%**（#51725） |
| Shared-expert sharding | 共享专家可选切分 | **每 GPU 省 ~17 GiB 内存**（#50912） |
| ROCm V2 runner | 模型运行器 v2 上 ROCm 支持 | 多平台覆盖（#51653） |

**解读**: ① GEMM-RS + combined all-gathers 反映 Kimi-K3 这类**深 MoE + 长上下文**模型在序列/张量并行下通信占比高，vLLM 正在把"通信削减"做成一级优化维度；② adaptive speculative token budget（~60% TTFT 改善）说明投机解码从"固定 draft 长度"转向"置信度驱动"——与 SGLang v0.5.16 的 DSpark confidence-driven 验证是同一方向（见核心事件四）；③ shared-expert sharding 省 17 GiB/GPU 对 896 专家模型是实打实的部署成本下降。

## 🆕 本期核心事件二：TensorRT-LLM 宣布移除 TensorRT backend——推理框架的"改名"时刻

### 1. 事件原文——v1.3.0rc20 的最后通牒

- **来源/标题**: TensorRT-LLM v1.3.0rc20 Release Notes（https://github.com/NVIDIA/TensorRT-LLM/releases/tag/v1.3.0rc20，2026-06-30）: **"This RC version will be the last one supporting the TensorRT backend, in the next version the TensorRT backend will be removed!"**
- **背景**: TensorRT-LLM 自 2023 年诞生起即绑定 TensorRT（NVIDIA 的推理优化引擎），PyTorch backend 自 2024 年底开始作为替代路径并行发展。rc20 的这一行声明等于**官方承认 PyTorch backend 已全面接管**——产品名里的 "TensorRT" 正在变成历史名词
- **配套动作（rc21，07-15）**: AutoDeploy backend 弃用，官方明确"earlier model support 是关键优先级"，转向 agentic 方法缩短 PyTorch backend 的模型支持时间；**首个成果：Minimax M3 在模型发布一周内获得功能支持**（#15292 同期 T5/BART 加入 PyTorch backend）

### 2. 为什么移除——第一性原理分析

**TensorRT backend 的痛点**: ① 模型支持滞后——每新架构需手工构建 TRT engine，LLM 架构迭代速度（周级新模型）远超 TRT 编译管线（月级适配）；② 编译链复杂——graph optimization 与动态 shape/连续批处理/投机解码等新特性叠加后工程爆炸；③ 与 PyTorch 生态割裂——无法直接复用 HF transformers 权重加载、无法与 torch.compile 生态协同。

**PyTorch backend 的替代逻辑**: 直接吃 PyTorch 生态的模型定义（HF 权重零转换），eager 模式优先保证"能跑"，再以 torch.compile / CUDA graphs 逐层加速。rc22-rc24 的 known issues 暴露了过渡期代价：**torch.compile 与 CUDA graphs 组合在初始化/推理时崩溃**（rc24）、多 GPU 精度路径在 remove_copy pass 报 KeyError（rc22）、DeepSeek-V4-Pro 在 GB300 分解部署上挂起（rc23）——这些都是 PyTorch backend 尚未完全消化的工程债。

### 3. 对用户/生态的含义

| 维度 | 影响 |
|:--|:--|
| 存量用户 | v1.3.0rc20 是 TensorRT backend 的"最后一个安全版本"；后续升级需迁移 PyTorch backend |
| 模型适配速度 | PyTorch backend + agentic 方法将新模型支持压缩到"发布后一周内"（Minimax M3 先例） |
| 竞争格局 | vLLM/SGLang 的"开箱即用模型支持"优势被 TRT-LLM 以转换执行路径的方式追赶；TRT-LLM 的差异化回归到**闭源优化深度**（NVIDIA 自家 kernel 库、GB200/GB300 平台调优） |
| 战略判断 | 推理框架的胜负手已从"编译优化器"转移到"模型适配速度 + 平台深度调优"——**TensorRT 的退出是编译型推理框架时代的尾声信号** |

## 🆕 本期核心事件三：PyTorch 2.13.0 亮点——编译后端多元化 + 分布式通信底座重写

### 1. 发布概况

- **来源/标题**: PyTorch 2.13.0 Release Notes（https://github.com/pytorch/pytorch/releases/tag/v2.13.0，2026-07-08；2.12.1 补丁 06-18）
- **七大 Highlights 逐条解析**:

| Highlight | 内容 | 意义 |
|:--|:--|:--|
| FlexAttention → Apple Silicon (MPS) | 稀疏模式较 SDPA **~12× 加速**；CUDA 侧新增确定性 backward | 注意力优化 API 跨硬件落地；可复现训练 |
| CuTeDSL "Native DSL" backend | Inductor 第二条高性能代码路径（与 Triton 并列），编译更快（Prototype） | **编译后端去 Triton 单点依赖**，CUTLASS 生态接入 torch.compile |
| `nn.LinearCrossEntropyLoss` | 融合最后预测与损失计算，大词表 LM 训练**峰值显存降 ~4×** | 直接利好 LLM 预训练显存瓶颈 |
| **torchcomms** | PyTorch Distributed 新通信后端，改善大规模集群训练的容错/扩展性/可调试性 | **分布式通信底座重写**——对大集群训练是地基级变化 |
| FSDP2 通信重叠 | reduce-scatter 与 all-gather 经专用进程组重叠（opt-in） | 分布式训练吞吐提升 |
| Python 3.15 wheel | Linux 支持 free-threaded 3.15t | 紧跟 CPython 节奏 |
| 平台扩展 | ROCm AOTriton 0.12b（native HIP CMake）、Armv9-A torch.compile 目标、Intel XPU telemetry API | 多平台覆盖继续 |

- **2.12.1 补丁（06-18）重点**: 修复 B200 上 FLASH_ATTN 的 test_batch_invariance 非确定性输出（Triton 3.7.1，#181248/#186814）、Triton 非法内存访问——**Blackwell 平台确定性问题是 2.12 的已知回归**
- **2.13 已知回归**: ROCm wheel 在无 GPU 环境（`torch.cuda.is_available()==False`）跑 CPU 路径 `torch.compile` 报 "Can't detect vectorized ISA for CPU"（#189194）——ROCm builder 镜像依赖
- **破坏性变更**: 停止 cp313t wheel（free-threaded 用户需迁 3.14t）；移除 Bazel build（Bazel 6 过时、生态已迁 Bazel 9）；裸 `PyObject` schema 拒绝

### 2. 解读——PyTorch 的"平台化"转向

2.13 的三个信号值得单独拎出：**CuTeDSL 让 Inductor 摆脱"Triton 单引擎"**——Triton 编译慢、调试难一直被社区诟病，CUTLASS 系的 CuTeDSL 作为第二条路径意味着 torch.compile 的代码生成开始"多引擎化"，与 vLLM 的"多后端"（CUDA/ROCm/CPU/XPU）策略同构；**torchcomms 是通信层的"新一代"**——NCCL 之外的容错/可调试通信底座，直接服务万卡训练；**nn.LinearCrossEntropyLoss 显存 -4×** 表明 PyTorch 团队仍在为大词表 LLM 训练做"显存抠细节"。整体判断：PyTorch 2.13 是"编译器多元化 + 分布式底座重构"的版本，为 2026 下半年万卡集群训练做准备。

## 📚 arXiv 推理系统新论文（08-20 ~ 08-26 提交）

### A. KV cache 压缩与内存专题——六路线并行，两个"冷水"研究

- **VisCache: 视觉 KV cache 粗到细剪枝**（https://arxiv.org/abs/2608.24063，2026-08-25）: VLLM 长上下文推理的视觉 KV 占大头，两阶段无训练剪枝——轻量 VLM 过滤时间冗余关键帧 + PruneKV 抛物线逐层预算分配 + 非对称更新（剪 key 融 value）；**2.35× 加速、仅保留 19-28% KV 仍保竞争性能**，在效率-性能帕累托前沿上超越现有基线（代码: github.com/Wlklk/VisCache）
- **PuzzleKV: 页级低秩分解 KV 压缩**（https://arxiv.org/abs/2608.23843，2026-08-24）: 发现每 head KV cache 的固定长度逻辑页内存在显著低秩结构，逐页独立压缩（训练/校准无关），注意力直接在 dense 与 factorized 页上计算；**~60% 存储下保持 >96% Full KV 性能**；叠加量化后 **18.7% 存储保持 >93% 性能**（RULER 上超 Global SVD、LongBench 竞争）
- **Minima-KV: 混合格式分页注意力**（https://arxiv.org/abs/2608.23834，2026-08-24, Minima AI）: 近期+受保护的 Anchor 页留 FP8，旧非 Anchor 页转 packed TQ3，在线 softmax 合并实现异构 decode（无 dense 影子）；RTX PRO 6000 Blackwell 上 Qwen3.6-27B 每 live token **18.3 KiB 注意力 KV（=BF16 的 3.50×、FP8 的 1.75× 压缩）**；16K RULER 与 dense 控制持平，LongBench v2 损失 -0.4~-0.8pt
- **CertKV: 全局分数缺口驱动的无训练压缩**（https://arxiv.org/abs/2608.21541，2026-08-21）: 论证"注意力图稀疏"不足以证明可压缩（大权重可能不含多数质量、被省略值可抵消）——**Global score gaps 而非阈值计数决定需保留 token 数**；每 head 保留 1 个 tail-summary 槽、按值离散度分配其余；LongBench-v2 9 个设置中 7 个 top-2，128K RULER 保持领先压缩层
- **Elastic KV Cache: 可回收 prefill 保留区，附诚实负面结果**（https://arxiv.org/abs/2608.23658，2026-08-24）: 启动时为最坏 prefill 激活预留的显存在 decode 阶段闲置——机制上可借给 KV 池再归还（纯用户态 CUDA VMM，毫秒级 decommit/几十毫秒 recommit，兼容 CUDA graphs/prefix caching，永不 OOM）；但**对照实验得出负面结论：chunked prefill 已基本抹平差距**（TTFT 中位数在 chunk 8192 vs 32768 间仅差 ~1%，因 prefill 计算受限而 decode 每步仅 1 token/序列），且 TP 下保留区从 TP1 的 16% 稀释到 TP4 的 2.7%——**"保留区回收"多数场景不划算，机制仍作为可复用 VMM 分配器开源**
- **More GPUs or a Smaller Cache? TP vs KV 压缩的成本等价分析**（https://arxiv.org/abs/2608.23962，2026-08-25）: 把 TP（1~8 卡）与 KV 压缩（16/8/4-bit、keep-ratio 0.25）放到同一成本归一化轴（每百万 token 成本 vs 延迟，A100/A40/H100 校准模拟器）——**结论: 不存在交叉点，压缩全程便宜 1.20-2.00×**；分界墙在 ~36B 参数/80GB 卡——低于此墙压缩主导（加 GPU 是浪费），高于此墙 TP 是"入场券"（权重绑定，KV 压缩碰不到）；压缩使容量/美元乘 16.5×（vs 8 倍 GPU 花费仅 1.21×），但压缩使 per-token 延迟差 8-93%（batching 争用）
- **Learning how to Forget: 稀疏注意力微调 + KeysAndValues 开源库**（https://arxiv.org/abs/2608.19920，2026-08-20, AWS）: 任何 KV cache policy 均可微调共适应（单张 A100 40GB 即可），常优于 exact attention 训练；实现 H2O 稀疏注意力的专用 SDPA kernel；开源 github.com/awslabs/keys_values（长上下文推理+微调库）
- **DynaRule: 规则注入 KV cache 的步级推理**（https://arxiv.org/abs/2608.22753，2026-08-24, EMNLP 2026 Findings）: 把外部程序规则注入 KV cache、检索变为内部可学习步进过程（Stacked Step-Level Attention Training + `<search>` token）；10K 规则下 Recall@1 >85%，QA 精度最高 +19pt——KV cache 从"记忆"变成"可检索规则库"

**KV 压缩专题分析一：六条路线收敛于"页/块级粒度 + 混合精度 + 训练无关"，但评估口径开始分裂**。PuzzleKV（页级低秩）、Minima-KV（页级混合格式）、CertKV（head 级 tail-summary）、VisCache（帧级过滤+层预算）虽机制各异，共同点是**都放弃"全局 SVD/全局阈值"而转向局部结构利用**——这印证了长上下文下 KV 的局部低秩/局部重要性不均假设。但注意评估差异：PuzzleKV 报"60% 存储 96% 性能"、Minima-KV 报"18.3 KiB/token 3.5× 压缩"、CertKV 报"top-2 in 7/9"——存储口径（原始字节 vs 压缩后）与基准集（RULER vs LongBench v2）不统一，**跨论文直接对比不可行**，需要 MoEXBench（昨日收录）式的统一评测框架来消歧。

**KV 压缩专题分析二：两个"冷水"研究标志学界自我纠偏**。Elastic KV Cache 的诚实负面结果（机制成立但收益被 chunked prefill 抹平）与 More GPUs or a Smaller Cache 的"压缩在延迟上反而更差（+8~93%）"共同指向：**KV 压缩的真实价值是"容量/美元"而非"延迟"**——容量受限场景（长上下文并发）压缩是唯一杠杆，延迟敏感场景（单请求）则相反。这对工程选型的指导是：**压缩策略应按"内存瓶颈 vs 延迟瓶颈"分流部署**，而非一刀切。另一个边界洞察（~36B/80GB 分界墙）直接回答"该加卡还是该压缩"——这是部署决策少见的量化判据。

### B. Serving 系统、解码优化与工具链

- **Simthesizer (Borg): Agent 驱动的 LLM Serving 模拟器**（https://arxiv.org/abs/2608.24650，2026-08-25）: 现有模拟器跟不上 serving 系统演进（agentic 工作流、分解式 serving 等新机制需侵入式重写）——Borg 用统一动态图表达完整 serving 流程，合成 agent 在护栏+保真校验下把自然语言特性请求落到抽象上；**基于 vLLM 的真实系统扩展吞吐误差 2.51% vs 现有模拟器 6.03%**，同负载下比 LLMServingSim2.0 快 284.96×、比 Vidur 快 23.19×
- **AgentSpec: LLM Agent 批量推理的投机解码**（https://arxiv.org/abs/2608.24004，2026-08-25, EMNLP 2026）: 指出 SOTA 投机解码在大 batch 下显著降速的两大主因——投机 token 高拒绝率 + 动态 token 预算未充分利用；结构隔离 draft（限定在 agent 工作流的语义连贯段）+ 冗余感知预算分配；**vLLM 实现，5 工作负载 × 4 模型族均超 SOTA**
- **FlashPrefill V2: 块稀疏 prefill 注意力**（https://arxiv.org/abs/2608.19758，2026-08-20）: 从算法原型走向生产——均值校正项抑制稀疏化误差；PackGQA 内存访问 + warp specialization + pingpong pipelining 对齐 FlashAttention-3/4；**原生支持 paged KV cache 与连续批处理，可作 SGLang 注意力后端**；NVIDIA H20 128K 上下文 FP8 下较 FA2 **47.26×**、BF16 27.19×、FP8 下较 FA3/4 对齐 dense 基线 30.49×
- **CacheRoute: 大规模 LLM Serving 的规划式前缀亲和路由**（https://arxiv.org/abs/2608.19677，2026-08-20）: prefix caching 仅在重复请求回到仍持有前缀 KV 的服务器时才避免 prefill——cache-blind 均衡分散复用、固定亲和易过载；CacheRoute 用周期性规划路由化解（论文全文待展开）
- **Axon DSL: 形状安全、框架无关的 LLM 架构 DSL**（https://arxiv.org/abs/2608.19889，2026-08-20）: 针对"开源生态依赖单一平台"的锁死风险，Haskell 风格强类型 DSL 一次编写、自动编译到 PyTorch/Triton/JAX/MLX/vLLM；467 次推理基准（135M-32B）median 加速 PyTorch 7% / Triton 12% / JAX 91% / MLX 107%；**作为 vLLM 原生架构（PagedAttention+KV cache）部署时较 Transformers 实现 median 加速 58%**
- **AsmEvo: AMD GPU 汇编级 agentic 优化**（https://arxiv.org/abs/2608.20711，2026-08-21）: 对已编译 AMDGPU code object 做汇编级编辑（代码对象恢复→元数据感知重建→差分验证），MI308X 上 29/30 KernelBench kernel 改进（geomean 1.35×/max 3.88×）；**vLLM/SGLang Triton 汇编 kernel 亦获 1.09×/1.31×（MI300X 生产负载）**——AMD 生态 kernel 优化从源码级下沉到汇编级
- **XKV: 异构 LLM 间双缓存潜在空间通信**（https://arxiv.org/abs/2608.20617，2026-08-20）: 多智能体系统跨模型传递上下文——learned-query attention 池化双缓存 + 层映射协调不同深度 + 共享位置解码器；两模型可异族/异深/异 KV 几何/异 tokenizer；45 个数据集-模型对设置中最高 macro score，ROPES 上较 LCF-X 高 4.6 EM/4.2 F1，**翻译 10.3× 快（5.8 vs 59.9ms）、端到端 26% 快于 LCF-X、6.8× 快于文本通信**，训练参数少 76%
- **TreeWY: Gated DeltaNet 混合模型的树形投机验证**（https://arxiv.org/abs/2608.20961，2026-08-21）: 混合模型（线性注意力 GDN 层 + 小固定循环状态）的投机解码需在每 draft 位置快照循环状态、树分支无法共享——用树结构 WY 变换以单次三角求解计算所有 draft 节点输出，仅提交时重建被接受状态；Qwen3.5 35B/397B 上削减投机循环状态内存与 KV 压力，内存受限处转为更高吞吐与更低 TTFT
- **cflow: Pipeline-Native Transformers 的 CPU 推理**（https://arxiv.org/abs/2608.23841，2026-08-24）: 单 token 自回归 decode 在 CPU 上受内存带宽（~50 GB/s）而非算力（~1 TFLOP/s）约束——模型架构与推理运行时协同设计（L2 尺寸 tile 存储、MoE 只读 top-k 专家、延迟感知调度）；30.9B MoE 在 32 vCPU Ice Lake 上 **5.94 tok/s，超 llama.cpp 4.75 与 vLLM CPU backend 1.65**；诚实报告 8 项设计主张中 1 项被证伪、1 项不确定
- **Giga-Embeddings: MoE 编码器的高吞吐服务**（https://arxiv.org/abs/2608.23806，2026-08-24）: 10B 稀疏 MoE 嵌入模型（1.8B 激活）在 **vLLM 基准 1024-token 输入达 114.5k tok/s**，较 dense 3B 高 25%、较外部系统高 1.56-2.65×——vLLM 覆盖面从生成扩展到嵌入服务
- **昨日已收录（仅交叉引用）**: WnW 语音 LLM KV cache（2608.22704）/ PowerSlider 功耗感知 serving（2608.21719，SGLang 上）/ MoEXBench MoE 组合压缩基准（2608.21693）/ SSM 扩散 LM 结构化后缀（2608.23167）——详见 knowledge/01_survey/ai-frameworks/2026-08-26.md

**分析三：投机解码成为跨框架的"调度器级能力"，且正在 agent 场景重构**。vLLM 的 DSpark confidence-scheduled verification + adaptive token budget（TTFT -60%）与 SGLang 的 DSpark 383.7 tok/s 是同一算法在两个引擎的独立实现；AgentSpec 揭示了大 batch 下投机解码失效的两个根因（拒绝率、预算利用），与 TreeWY 解决混合架构的树分支内存问题——**投机解码的下一战场是"大 batch + agent 长链 + 混合架构"的组合场景**，单序列小 batch 的收益已接近天花板。

**分析四：推理框架竞争已进入"全生命周期 + 多硬件 + 模拟验证"三维战场**。全生命周期：vLLM 的 RL 权重同步（RDT，昨日）、启动加速（SGLang overlap staging）、权重卸载与分级 KV（vLLM MRv2）——冷启动与权重更新成为新竞争点；多硬件：vLLM ROCm gfx11/gfx950 + CPU + XPU、PyTorch Armv9-A + ROCm AOTriton、TRT-LLM 的 GB300 平台调优——AMD/ARM 不再是"能跑"而是"要调优"；模拟验证：Simthesizer 把 serving 系统研究拉到 agent 驱动的模拟器（2.51% 吞吐误差），CacheRoute 用规划路由解决 prefix 亲和——系统研究方法论本身在 agentic 化。**判断：推理框架的护城河正从"内核数量"转向"模型适配速度（day-0）+ 调度器原生能力（投机/卸载/路由）+ 多平台调优深度"**，这与 08-26 硬件组 Hot Chips 观察（推理延迟成下一代集群竞争焦点）互为印证。
