### 框架与系统

- **DARTree：扩散草稿树 + 自回归校正头的训练免费推测解码**（[arXiv:2608.13524](https://arxiv.org/abs/2608.13524)，08-13）: 推测解码用并行验证多个草稿 token 无损加速自回归模型；扩散式 drafter 可一次并行预测整块 token 块，但其位置分布是边际分布而非沿草稿路径逐 token 条件化——现有递归校正只沿单一草稿链引入因果信息，扩散式建树虽拓宽候选覆盖却不沿分支校正；DARTree 把预训练 AR correction head 从链扩展到树：先批量扩展+评分固定宽度候选树（每层全节点一次前向），再用 best-first 剪枝选验证树，将 AR head 推理与顺序堆操作解耦；7 项 math/code/chat 基准全部 4 种温度配置下取得最高平均接受长度与加速：每轮最多接受 12.97 tokens（比 DFlash 多 98.6%、比 Domino 多 27.9%），无损加速最高 9.73×。URL: https://arxiv.org/abs/2608.13524 ⭐

- **OpScale：LLM Serving 的 operator 级供给与自动扩缩容**（[arXiv:2608.13499](https://arxiv.org/abs/2608.13499)，08-13）: 云 GPU 集群服务 LLM 时满足 TTFT 等 SLO 与成本效率的平衡是根本挑战，而"扩缩容单位是什么"这一基础设计问题尚未解决——现有方案把整个模型当单体扩缩单位，无法捕捉推理负载细粒度动态，导致突发流量下 SLO 违约或 GPU 严重欠载；OpScale 以 operator 级弹性为扩缩容原语，提供 profiling/provisioning/placement/runtime serving 完整框架，并专门设计应对 operator 粒度带来的高复杂度与空间爆炸；生产 traces 上最多 40×A100 与 24×GB200 验证：满足 SLO 前提下 GPU 数减少 36.3%、功耗降低 28%，固定成本预算下吞吐提升 44%。URL: https://arxiv.org/abs/2608.13499 ⭐

- **vLLM 自适应验证：DSpark 置信度调度的草稿验证**（[vLLM Blog](https://blog.vllm.ai/blog/2026-08-14-dspark-adaptive-verification)，08-14）: 传统推测解码对每个草稿 token 都验证，验证预算与请求实际需求无关；vLLM 引入按每请求置信度调度 DSpark 草稿验证预算——低置信请求投更多验证、高置信请求少验证，单一配置即可保持 batch size 1 到 256 的吞吐/延迟前沿，无需按负载调参。URL: https://blog.vllm.ai/blog/2026-08-14-dspark-adaptive-verification ⭐

- **vLLM Decode Context Parallelism：长上下文解码的 KV 序列维切分**（[vLLM Blog](https://blog.vllm.ai/blog/2026-08-07-decode-context-parallelism)，08-07）: vLLM DCP 按序列维度把 KV cache 切分到多 GPU，与按层/头的张量并行正交；长上下文 agentic 工作负载下吞吐比标准张量并行高 3×（配合 08-14 期前 SGLang 侧 DCP 首落地，vLLM 侧同日窗口正式化并给出量化收益）。URL: https://blog.vllm.ai/blog/2026-08-07-decode-context-parallelism ⭐

- **vLLM 达 Qwen3.5 25K total TPS/GPU**（[vLLM Blog](https://blog.vllm.ai/blog/2026-08-06-qwen35-25k-tps)，08-06）: GB200 NVL72 分离式（disaggregated）serving 下 Qwen3.5-397B-A17B-NVFP4 单 GPU 总吞吐达 25K tokens/s；技术组合：Blackwell GDN kernels、HMA cache transfer（KV 跨 GPU 直传）、async scheduling 修复、srt-slurm recipes。URL: https://blog.vllm.ai/blog/2026-08-06-qwen35-25k-tps ⭐

## 核心趋势

1. **推测解码从"算法"走向"系统调度"**：DARTree（树状校正）解决草稿质量上限问题，vLLM DSpark Adaptive Verification（置信度调度）解决验证预算分配问题——两者同日窗口出现，标志推测解码优化重心从 drafter 架构转移到验证侧系统策略
2. **扩缩容粒度细化：模型级 → operator 级**：OpScale 提出 operator 级弹性原语（GPU -36.3% / 功耗 -28% / 吞吐 +44%），与 vLLM 侧 DCP（序列维切分）、elastic EP（专家级弹性）同向——serving 弹性正从"整模型复制"走向"更细粒度资源切分"
3. **vLLM 生态进入"性能冲刺 + Day-0 全覆盖"双轨**：25K TPS/GPU（GB200 NVL72 分离式）与 2.4T Qwen3.8 / Nemotron 3.5 Lightning 同日窗口 Day-0 支持，表明框架竞争从功能对齐转向规模化性能标杆与最新模型即时支持
