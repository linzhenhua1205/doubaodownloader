### 5. PyTorch 2.13.0 功能细节 + 2.12.1 修复（07-08 发布，历史期次未展开）

- **PyTorch 2.13.0**（[GitHub Release](https://github.com/pytorch/pytorch/releases/tag/v2.13.0)，07-08）: ① **FlexAttention 登陆 Apple Silicon (MPS)**——稀疏模式相对 SDPA 最高 **~12x 加速**，CUDA 侧补确定性 backward 路径；② **CuTeDSL "Native DSL" 后端**——Inductor 第二条高性能代码路径（与 Triton 并列），编译更快（Prototype）；③ **nn.LinearCrossEntropyLoss**——合并最终预测与 loss 计算，大词表 LM 训练峰值显存**最多降 4x**；④ **torchcomms**——PyTorch Distributed 新通信后端，改善大规模集群训练的容错/可扩展/可调试性；⑤ **FSDP2** reduce-scatter 与 all-gather 通信重叠（opt-in 独立进程组）；⑥ **Python 3.15 wheel** 支持（Linux pytorch 索引）
- **PyTorch 2.12.1**（[GitHub Release](https://github.com/pytorch/pytorch/releases/tag/v2.12.1)，06-18）: 修复 B200 FLASH_ATTN 非确定性输出、B100/B200 (sm100) Triton conv2d_bwd_weight 非法内存访问（均通过升 Triton 3.7.1）、byte-dtype misaligned fill_——**与 vLLM v0.27.0 同步升 Triton 3.7.1 呼应**，说明 Triton 3.7.1 是 sm100 时代的稳定基线
- **对本组的含义**：FlexAttention MPS 与 CuTeDSL 显示 PyTorch 在"编译路径多元化"（Triton + CuTeDSL + MPS）上加速，而 vLLM v0.27.0 已同步升级 PyTorch 2.13——**推理框架对 PyTorch 大版本的跟随周期正在缩短**（v0.27.0 距 2.13.0 发布仅 33 天）

## 🧭 深度分析（本组视角，6 段）

### 分析一：SGLang v0.5.18 的"模型矩阵扩张"——空窗打破不是节奏变化，而是发布模式的切换

08-21 期基于"13 天无新版"判断 SGLang 工程侧静默，本期 710 PR 直接证伪。但更准确的解读不是"节奏变了"，而是**SGLang 的发布模式从"低频大包"切向"半月一包"**：v0.5.16（07-25）→ v0.5.17（08-08，14 天）→ v0.5.18（08-22，14 天），间隔稳定在两周。与 vLLM 的月度大版本（v0.27.0 08-10 → v0.28.0 预计 08 月末）形成错峰——**SGLang 用更高的发布频率换取"day-0 覆盖"的敏捷性**。8 个新模型里 5 个是 diffusion，说明 SGLang-Diffusion 已从"实验特性"升级为"主干能力"：视频生成（SANA-Video / LTX-2.5 / Cosmos3）与统一 serving（文本 + 视频 + 音频同栈）正在成为框架竞争的新维度——vLLM 本期只有 Qwen3.5 EVS 视频 token 剪枝（模型侧），SGLang 则以"视频生成全家桶"在 diffusion serving 上建立先发。第一性视角：**推理框架的差异化正在从"同一模型的吞吐"转向"新模型类型的覆盖速度"**——当 AR 模型的 kernel 优化趋同（FA4/MX/投机解码已普及），谁能最先 serve 新一代模型（diffusion 视频、世界模型、线性注意力混合）谁就定义下一轮基准。对本库的跟踪含义：**把"新模型类型（diffusion/视频/世界模型）的 day-0 覆盖"列入框架对比的第二指标**（第一指标仍是吞吐/TTFT）。

### 分析二：Kimi K3 双框架 day-0——"头部模型牵引框架"格局正式成型

SGLang v0.5.17（08-08）与 vLLM v0.27.0（08-10）**两天内先后完成 Kimi K3 的 day-0 支持**：SGLang 端是 DCP + DSpark + KDA-aware 前缀缓存 + HiCache L2，vLLM 端是 AttnRes kernels + DeepGEMM + compressed-tensors MXFP4 + DSpark AR fusion + Rust 前端。这不是巧合，而是**模型厂商-框架厂商"联合发布"机制成熟**的标志——K3 的 2.8T 参数 / 69 KDA + 24 MLA 混合架构 / MXFP4 原生量化，任何一个特性单靠框架侧逆向都需数月，day-0 只能来自模型侧深度合作（Moonshot 直接参与 PR）。对本组的三个判断：① **K3 的 69 KDA 线性注意力层意味着"KV cache 不再是唯一内存大头"**——线性注意力的循环状态（recurrent state）管理（08-19 期 DeltaLog 方向）将成为下一个框架内竞争点，SGLang 的 KDA-aware 前缀缓存与 vLLM 的 AttnRes 是两种不同路线（前者复用、后者压缩）；② MXFP4 原生 checkpoint 让"4-bit 推理"从"后量化"变为"出厂即 4-bit"——框架只需信任格式，无需精度恢复（与 08-22 期"MX 从存储格式升级为计算格式"判断闭环）；③ **K3 的 day-0 验证平台含 AMD MI35x（SGLang）与 ROCm gfx1250（vLLM）**——国产头部模型 + AMD 平台的组合正在成为框架"必须支持"的组合，这对超节点异构集群（NVIDIA + AMD 混布）的框架选型有直接意义。

### 分析三：DSV4 优化集在 vLLM v0.27.0 的"打包兑现"——连续跟踪线的验证

本组从 08-17 起连续跟踪 vLLM 的 [DSV4] 前缀 commit（prefill 预取优化、CuMemAllocator.discard()、共享专家 MegaMoE 融合），v0.27.0 一次性打包了 9 项 DSV4 优化（见表格 2）：序列并行、~2x kernel（空 c128 跳过）、TTFT -3.4%（topk/router）+ -3.9%（workspace）+ -1.0%（adaptive topk）、1.88x kernel、448 MiB 内存、MXFP4 indexer KV cache、sparse-MLA q-head padding 移除。**这些优化呈"内存分配 → kernel 执行 → 调度决策"的全链形态**，说明 vLLM 对 DSV4 的优化已从单点打补丁进入系统性重写（与 08-21 期"DSV4 优化链形成"判断一致）。跨框架对照：TRT-LLM rc23 同期加载 DSV4 NVFP4 混合精度 checkpoint、SGLang 的 DSpark 在 DSV4-Pro 上 383.7 tok/s——**DSV4 是 2026H2 唯一被三大框架同时深度优化的国产模型**。对服务器厂商的含义：DSV4 的推理性价比（尤其 NVFP4/MXFP4 低比特路径）已成为框架 benchmark 的默认叙事，**国产模型集群的选型不再只看"能不能跑"，而要看框架对该模型的优化深度（kernel 级 + 调度级 + 量化级三层）**——建议把 vLLM v0.28.0 的 DSV4 PR 密度作为下一评估窗口（08-21 期下期清单第 1 项）。

### 分析四：PyTorch 2.13 的"编译器 + 通信"双升级——推理框架底层基座的连锁反应

PyTorch 2.13.0 的六大 highlight 中，与本组最相关的是 CuTeDSL Native DSL 与 torchcomms：前者给 Inductor 第二条代码路径（Triton 之外），后者重构 Distributed 通信栈（容错/可调试）。连锁反应已经发生：vLLM v0.27.0 在 2.13.0 发布 33 天后即整体升级（含 Triton 3.7.1），TRT-LLM 的 known issues 里 torch.compile 相关崩溃（rc24 第一条）正是跨框架升级期的共性阵痛。第一性视角：**推理框架的性能上限由 kernel 决定，但 kernel 的供给速度由编译器决定**——CuTeDSL 的意义在于打破 Triton 单点（若 Triton 某算子不生成最优代码，CuTeDSL 是备选路径），这与 08-22 期 FIBER（执行模型层）、TileSight（tile 级分析）形成"编译器-内核-分析"三层的生态补位。对本库的跟踪含义：**PyTorch 大版本升级已成为推理框架 release 的隐性前置依赖**（vLLM v0.27.0 与 PyTorch 2.13 强绑定），跟踪 PyTorch 2.14 时间表（预计 9~10 月）即可预判下一轮框架升级窗口；2.12.1 的 B200/sm100 修复与 vLLM 同步升 Triton 3.7.1 也验证了"sm100 时代稳定基线 = Triton 3.7.1"这一事实。
