## 三、分析性段落（因果链 / 原理展开 / 对比）

### 3.1 为什么"周一的今天"反而没有新论文：arXiv 公告时差的两级延迟机制

今天的日期是 2026-08-24（北京周一），直觉上"周一 = 工作日 = 应该有新论文"，但实际命中 0 条新论文。这不是通道失效，而是 arXiv 公告机制的两级时差叠加。**第一级：美东 vs 北京时间差**。TRACKING.md 执行基线（08-10 沉淀）明确记录"arXiv 公告时差 +24h = 北京日"——cs.DC recent 页面按美东日期列示，美东发布日 +24h 才是北京对应日。**第二级：周末批次并入周一**。美东周六/周日提交的论文不单独发布，而是并入**美东周一 20:00 的公告批次**。今天北京 22:33 = 美东周一 10:33，距周一公告批次（美东 20:00 = 北京周二 08:00）还有约 9.5 小时——**今天执行的查询命中窗口，实际上仍处于"周末无公告"的尾段**：最近 1 个月内的新论文（Belayer 08-18 更新、PHOENIX 07-06 更新等）早在 08-20~22 三个工作日被密集收录完毕，而周末两天提交的论文要等到**明天（北京 08-25 周二 08:00）**才进入 arXiv 的搜索索引与 API 返回。这构成一个精确可预期的因果链：**周一白天（北京）执行追踪 → 命中窗口 = 上周已收录存量 + 周末未发布论文 → 0 新论文 → 周二 08:00 周一公告批次发布 → 周二执行才见周末增量**。对追踪任务的操作含义：周一的正确动作不是"期待新论文"，而是"确认存量版本 + 锁定周二 08:00 为首个高概率新论文窗口"——这正是本日文件的定位。

### 3.2 版本时间戳 vs 收录时间戳的双基线核对：为什么"无增量"需要被证明而不是被假设

今天的核心工作是对 7 条核心论文做版本核对。这里有一个方法论细节：**"收录时已是某版本"需要证据链，而不是凭印象**。以 Belayer 为例：08-20 收录时 URL 为 https://arxiv.org/abs/2608.14635（无版本号），今日 API 返回 2608.14635**v2**，v2 更新时间为 2026-08-18——早于 08-20 收录日 2 天，因此可判定"08-20 收录时已是 v2"，今日无增量。PHOENIX 同理：v2 更新 2026-07-06，早于 08-20 收录日，收录即 v2。这个"版本时间戳 < 收录时间戳 → 收录即最新版"的判定规则，是版本追踪的可靠基线——它把"无增量"从主观印象变成可复核的时间比较。反之，如果某天 API 返回的版本时间戳**晚于**收录日（例如明天发现 Belayer v3 更新于 08-25），那就是必须深挖的版本增量信号。这套双基线核对（API 版本时间戳 vs 本地收录时间戳）应沉淀为追踪任务的固定校验步骤，其价值在于：**追踪系统必须能区分"该领域沉寂了"与"我们没去查"**——版本时间戳是客观的活性信号，收录时间戳是主观的检查覆盖，两者对齐才能避免假阴性。

### 3.3 源1 查询语法修正验证：分类限定如何替代失效的三元 AND（08-23 建议的实战落地）
