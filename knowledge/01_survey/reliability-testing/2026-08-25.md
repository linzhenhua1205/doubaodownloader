### 3.3 SPARe 版本登记误差：为什么"无增量"判定依赖登记准确性

今日版本轮询暴露了一个此前未被注意的登记误差：SPARe 在 08-22 收录描述中明确写"2026-05-27 更新"，但 08-23/08-24 的量化表格将其版本登记为 v1。这个误差的机理值得拆解：08-22 收录时 URL 使用无版本号形式（https://arxiv.org/abs/2603.00357），描述虽提到"2026-05-27 更新"但未显式标注版本号；08-23/24 表格的"版本"列填 v1 时**未回查 API 版本时间戳**，而是按"提交日期 02-27 → 默认 v1"的直觉填写。这与 08-24 第 3.2 节建立的"版本时间戳 vs 收录时间戳双基线核对"规则形成对照：**规则只在"检查时"生效，若登记环节本身不核对 API，误差会悄悄进入基线**。今日 API 返回 v3（upd=2026-05-27）与 08-22 描述互相印证，误差得以修复，且修复后"无增量"结论不变（v3 早于收录日）。**方法论教训**：① 版本登记必须回查 API 版本时间戳，不能凭提交日期直觉；② "无增量"结论的可靠性上限 = 登记准确性，登记误差会污染平台期判断（若 SPARe 实际是 v3 而登记 v1，后续发现 v3 会误判为增量）；③ 修复路径已沉淀为校验动作——**核心论文版本列每次轮询回查 id_list API**（今日已验证该通道效率：单次请求 4 个 ID 全部返回版本+时间戳）。今日起，08-20 以来收录的全部论文版本登记将与 id_list 轮询绑定，杜绝第二例 SPARe。

### 3.4 关键词面盲区：为什么 "restoration/recovery" 语义逃逸了现有查询面

BSR（Bounded-State Restoration）的发现过程暴露了查询面设计的盲区：该论文 08-18 已提交（早于本组 08-20 建立的三查询面），但 08-20~24 五次执行（源1 fault tolerance+checkpoint、源3 GPU fault、搜索页多词）均未命中——因为它**不在摘要中同时使用 "fault tolerance" 与 "checkpoint" 字面词**，而用 "restoration / restore capacity / reusable prefix / commit rule" 描述恢复语义。这揭示关键词查询的根本局限：**容错领域的概念迁移（fault tolerance → resilience → restoration → recovery → self-healing）导致同一主题在不同论文中有完全不同的词面**。SPARe（fault-tolerant）、Lazarus（resilient）、ReCoVer（recovery）、Concordia（checkpointing）、BSR（restoration）——五个概念高度重叠的论文用了五套词面。现有查询面只覆盖前两类（fault tolerance/checkpoint），"resilience" 靠源1 的 25 条召回间接覆盖（Lazarus 在册），但 "restoration/recovery/self-healing" 是系统性盲区。**应对方案**：① 源1 查询扩展为 `abs:"fault tolerance" OR abs:"checkpoint" OR abs:"resilien*" AND cat:cs.LG`（需验证 OR 与 AND 的优先级，arXiv API 默认 AND 优先，需括号显式分组）；② 增加"窗口内全量扫描 + 关键词过滤"通道（今日已验证有效，捕捉到 BSR/Lazy Pod）；③ 对高价值边缘候选（如 BSR）做方向判定后决定收录或排除——**盲区补强不是无限扩面，而是让查询面覆盖"语义簇"而非"字面词"**。

### 3.5 Lazy Pod 的失败语义表征：部署侧可靠性为何值得一行收录

Lazy Pod 与训练侧容错主线不重合（K8s 镜像交付 vs 训练 checkpoint），但其核心贡献——**表征 eager 拉取结构性不存在的失败模式**——与本组"可靠性测试"专题的底层逻辑同构：可靠性的本质是"对失败模式的穷举与表征"。懒加载的失败模式链条值得展开：冷启动优化（16.9~17.6s vs 24.5~573.0s）把 I/O 代价从"启动期一次性"推迟到"运行期按需"，而**按需读取依赖节点级缓存卷的容量**——持续合法读取下缓存耗尽，运行中 pod 开始读文件失败。这是一个典型的**时间-空间权衡的可靠性陷阱**：优化启动时延（时间维度）的代价是引入运行期缓存耗尽（空间维度）这一新失败模式，且该模式在 eager 路径上结构性不存在（eager 一次拉全量，无按需读取阶段）。对万卡集群的启示：模型交付链路的"优化"必须伴随"失败语义增量"审查——任何把代价从启动期推迟到运行期的优化（懒拉取、懒 checkpoint、按需分页）都在把失败面从"可控的启动失败"推向"运行中不可预测的失败"。这正是 08-24 第 3.3 节"从时间驱动到内容驱动"范式判断的部署侧镜像——**"推迟"不是消除，而是失败模式的时空迁移**。

### 3.6 失败面时空迁移的对称性：训练侧与部署侧为何指向同一规律

把今日 Lazy Pod 与 08-20 收录的训练侧方案放在同一张坐标系下，能看到一个此前未显式点明的对称结构。**训练侧**：PHOENIX 把 checkpoint 移到 off-critical-path（零开销热插拔）、Belayer 用 shadow worker 延迟恢复代价、BitSnap 用稀疏化减少 checkpoint I/O——三者共同策略是"把恢复/保存代价从关键路径上挪走"，代价是引入**运行期空间冗余**（内存 checkpoint 空间、shadow worker 资源、稀疏重建计算）；**部署侧**：Lazy Pod 把镜像拉取代价从启动期推迟到运行期，代价是引入**运行期缓存耗尽的失败模式**；**推理侧**（08-24 tech 组信号）：EEP/Tarragon 用秩级存活把恢复粒度从节点降到部分秩，代价是**运行期存活检测与弹性调度的复杂度**。三侧的共同规律：**可靠性优化的本质是"失败代价的时空重分配"，而非"失败代价的消除"**——任何把代价移出关键路径/启动期的优化，都会在运行期某个维度（空间/检测/调度）产生新的代价载体，而这个新载体本身就是新失败模式的来源。对可靠性工程的方法论含义：**优化方案的验收不能只看"代价少了多少"，还要审计"代价搬去了哪里、新载体何时会饱和"**——Lazy Pod 的缓存耗尽（空间饱和）、PHOENIX 的内存 checkpoint（容量饱和）、Belayer 的 shadow worker（资源竞争饱和）都是同一审计问题的不同实例。这条规律可作为本组与 tech 组后续跨组合并的候选专题框架（见 4.5 表）。

### 3.7 平台期判定的证据链完整性：为什么"零新增"不等于"零信号"

今日文件同时报告"平台期确认（第二数据点）"与"1 条边缘增量 + 1 处登记修正 + 1 个盲区识别"，表面上看似矛盾（既说平台期又说有发现），实则需要厘清"平台期"的精确语义：**平台期指的是"训练侧容错/checkpoint 主线的论文供给进入低频"，而非"本专题无任何可追踪信号"**。证据链拆解：① 主线供给端——周一公告批次（最高概率窗口）零新论文，且 08-20 以来 21+ 条已收录论文全部版本无增量（SPARe 修正后仍无增量），主线论文供给确实进入平台期；② 信号端——Lazy Pod（部署侧）、BSR（推理侧）、SPARe 登记误差（体系自检）分别代表三个**非主线但相关**的活跃信号，说明"可靠性"作为一个跨层主题并未沉寂，只是主战场从"训练容错论文"迁移到"部署/推理侧失败语义"与"体系自我修正"；③ 方法论端——盲区识别（restoration 语义）与登记误差修复（id_list 轮询绑定）本身是追踪体系的活性证据，**一个能持续自我修正的追踪体系，其"零新增"报告比"天天有新论文"的体系更可信**。因此"平台期确认"与"今日有产出"不矛盾：前者是领域供给侧的判断，后者是追踪体系侧的判断——两者分属不同对象，并行成立。这个区分对追踪任务的管理意义在于：平台期观察模式（低频轮询）针对的是供给端，而体系维护（查询面补强、登记校验）不应随供给端降频——**供给平台期反而是体系升级的最佳窗口期**。
