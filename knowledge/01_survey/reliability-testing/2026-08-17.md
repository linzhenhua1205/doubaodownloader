## 一、checkpoint 架构演进：从"单层落盘"到"分级/稀疏/内存态/选择性"

- **PHOENIX: 零开销热替换 checkpoint（2607.01646, 07-06）**: 通过 off-critical-path 内存态 checkpoint 提供空间冗余 + communicator reconstruction 协议在运行时用备用节点替换故障节点——**不终止整个任务**。实测 512×A100 训练 ≤65B 模型：失败路径外零 checkpoint 开销、热替换恢复 <40 秒。这是"任务级重启"向"节点级热插拔"的范式切换，为"故障不打断训练"提供了首个规模化证据。https://arxiv.org/abs/2607.01646
- **TierCheck: 三层分级 checkpoint（2605.17821, 05-17）**: 本地+对等节点内存保存轻量差分 checkpoint（快速局部恢复），异步迁移重型基 checkpoint 到远程持久存储——存储放置与故障异质性对齐（局部小故障→内存恢复，集群级灾难→远端恢复）。40B 参数下端到端 checkpoint <10 秒，支持高频 checkpoint，跨层严格全局一致性且不暂停训练。https://arxiv.org/abs/2605.17821
- **LLMTailor: 层粒度选择性 checkpoint 工具（2602.22158, PDSW'25）**: 观察 LLM 各层更新高度非均匀（部分层稳定甚至不变）→ 只 checkpoint 显著更新的层，再跨 checkpoint 过滤组装成复合 checkpoint。Llama3.1-8B 体积 -4.3×、Qwen2.5-7B 时间 -2.8×，保持模型质量。https://arxiv.org/abs/2602.22158
- **BitSnap: checkpoint 稀疏化+量化（2511.12376, 11-15）**: 自适应训练阶段与模型架构：bitmask 稀疏化 16× 压缩无损，cluster 量化 2× 近无损——对损失/无损压缩技术的系统比较后给出的自适应方案。https://arxiv.org/abs/2511.12376
- **Inshrinkerator: 动态量化 checkpoint 压缩（2306.11800, 06-20）**: 非均匀量化（不同权重敏感度不同）+ 高效搜索最优量化配置 + 量化感知 delta 压缩（重排权重最小化 checkpoint 差异）。压缩比最高 39×，承受 10 次恢复精度影响可忽略。https://arxiv.org/abs/2306.11800
- **FastPersist: NVMe 加速持久 checkpoint（2406.13768, 06-19）**: NVMe 写入优化 + 利用训练环境多 SSD 的写并行 + checkpoint 与独立训练计算重叠。持久存储 checkpoint 比基线快 116×，支持近零开销的 per-iteration checkpointing。https://arxiv.org/abs/2406.13768
- **分布式内存态 checkpoint（2310.12670, 10-19）**: 混合并行（HP）场景内存 checkpoint 与训练的资源竞争问题——三级异步 on-device 调度（保存阶段与训练并行）+ intra-node 冗余（节点内冗余保护，无需跨节点通信，不阻塞训练）。Frontier 上 Llama-2-34B @ 256 MI250X（512 GPU）实现零内存态保存开销，分布式加载绕过 NFS 读瓶颈。https://arxiv.org/abs/2310.12670

### checkpoint 技术路线对比

| 技术路线 | 代表系统 | 机制 | 关键数字 | 适用场景 |
|:--|:--|:--|:--|:--|
| 单层持久落盘 | 基线（NFS/并行FS） | 全量权重+优化器状态周期落盘 | 恢复分钟~小时级 | 小规模/容忍停机 |
| 分级存储 | TierCheck | 内存差分 + 远端基 checkpoint 异步迁移 | E2E <10s（40B） | 故障异质性明显的集群 |
| 选择性/稀疏 | LLMTailor / BitSnap / Inshrinkerator | 只存高更新层 / 稀疏+量化 / 动态量化+delta | 4.3×/16×/39× 压缩 | 层更新非均匀 / 存储受限 |
| 内存态+冗余 | 分布式 in-memory (2310.12670) / PHOENIX | on-device 快照 + 节点内/跨节点冗余 | 零保存开销；恢复 <40s | 混合并行、恢复速度优先 |
| MoE 专家子集 | MoC-System / MoEvement | 部分专家 checkpoint / 稀疏增量快照 | -98.9% 开销 / -4×、-31× | MoE 大总参、专家利用非均匀 |

## 二、容错范式外扩：集合通信韧性、计算冗余与热替换

- **ReCoVer: 容错集合通信保持训练轨迹（2605.11215, 05-21）**: 核心不变式——每次迭代 microbatch 数恒定，保证每迭代梯度与无故障运行随机等价。三层解耦协议：(1) 容错集合通信隔离故障跨副本传播；(2) in-step 细粒度恢复保留迭代内进度、防梯度损坏；(3) versatile-workload 策略在幸存者间动态再分配 microbatch 配额。**并行无关**，可直接集成 3D 并行与 HSDP。512 GPU 端到端预训练中累计丢失 256 GPU 仍保持无故障训练轨迹；vs checkpoint-restart 基线有效吞吐 2.23×，234 GPU-hours 内多处理 74.9% tokens。https://arxiv.org/abs/2605.11215
- **R²CCL: 容错集合通信库（2512.25059, 12-31）**: 网络故障浪费 10~15% GPU hours（慢恢复导致超时终止任务→checkpoint 回滚/请求重处理）。利用多 NIC 硬件：快速连接迁移 + 带宽感知负载再分配 + 弹性集合算法。2×8-GPU H100 InfiniBand 实测 + 数百 GPU 多样化故障模式仿真：训练开销 <1%、推理 <3%；优于 AdapCC 12.18×、DejaVu 47×。https://arxiv.org/abs/2512.25059
- **SPARe: 计算冗余掩蔽节点故障（2603.00357, ICML 2026）**: 面向 restart 主导 regime（100k+ GPU 时故障是常态、重启成本主导墙钟时间）——梯度同步期间跨并行组堆叠冗余数据分片，近似复制的可用性但仅 2~3× 近恒定计算开销（传统复制随冗余线性膨胀）。给出端耐久故障数与开销的闭式表达式，SimGrid 离散事件仿真验证；600k GPU 推演下比传统复制减 40~50% 训练时间。https://arxiv.org/abs/2603.00357
- **ATTNChecker: attention 的 ABFT 容错（2410.11720, 10-15）**: 系统故障注入实验揭示 INF/NaN/near-INF 值在 LLM 训练中的传播模式（触发不可训练状态→强制从 checkpoint 加载）。首个针对 attention 的 Algorithm-Based Fault Tolerance：平均 7% 训练开销检测并纠正全部极端错误；vs SOTA checkpoint/restore 恢复开销 -49×。https://arxiv.org/abs/2410.11720
- **AuroraRL: 商品网络上的容错 RL 训练（2602.11456, 02-11）**: RL 微调每步更新稀疏（~1% 参数元素变化）→ 每步稀疏 delta checkpoint：delta 提取与多流传输流水化、与 rollout 生成重叠、租约式容错协调异构 worker。Qwen3 8B 权重传输 -79×，吞吐 1.3~9.5×（vs PrimeRL-Full 等 dense-broadcast 基线），端到端距理想 RDMA 单数据中心基线 8.91%，tokens/dollar 1.21~1.59×——**容错机制同时是带宽优化手段**。https://arxiv.org/abs/2602.11456
- **ECRM: 推荐模型训练的纠删码容错（2104.01981, 04-07）**: DLRM 因大嵌入表跨数百服务器分布，服务器故障常见——用纠删码替代复制降低冗余存储开销（嵌入表分片级 EC）。https://arxiv.org/abs/2104.01981
- **PLINIUS: SGX 安全训练 + 持久内存容错（2104.02987, 04-07）**: 加密镜像模型驻留 PM + 字节可寻址加密训练数据，系统失败后近瞬时恢复；真实 PM 硬件上比磁盘 checkpoint 保存 3.2×、恢复 3.7× 更快——安全与容错合一的边角案例。https://arxiv.org/abs/2104.02987
- **TRAININGCXL: CXL 持久内存池化容错（2301.07492, 01-14）**: Type-2 CXL 将 PMEM 放入 GPU 内存层级（cache-coherent 域，GPU 无软件干预直接访问），checkpoint 计算/持久化逻辑置于 CXL 控制器旁；推荐模型特性让 checkpoint 移出关键路径，并松弛批间参数更新顺序。5.2× 训练性能提升、76% 节能。https://arxiv.org/abs/2301.07492

### 容错范式对比（故障假设与恢复语义）

| 范式 | 代表系统 | 故障假设 | 恢复粒度 | error-free 开销 | 恢复速度 |
|:--|:--|:--|:--|:--|:--|
| checkpoint-restart | 基线 | 永久/瞬时故障 | 作业级重启 | 周期落盘开销 | 分钟~小时 |
| 分级 checkpoint | TierCheck | 局部 vs 集群级异质 | 局部/全量 | 低（异步迁移） | <10s（40B） |
| 内存态+热替换 | PHOENIX | 永久节点故障+备用池 | 节点级替换，任务不中断 | 零 | <40s |
| 容错集合通信 | R²CCL / ReCoVer | 网络/NIC 故障为主 | 通信级透明 failover / 迭代级 | <1% / 低 | 亚秒~秒级 |
| 计算冗余 | SPARe | 任意节点故障 | 梯度同步期掩蔽 | 2~3×（近恒定） | 无恢复动作 |
| 应用层 ABFT | ATTNChecker | 计算错误（INF/NaN） | 算子级纠正 | 7% | 无需 checkpoint |

## 三、MoE 容错：为什么专家稀疏性改变了 checkpoint 经济学

- **MoC-System: 部分专家 checkpointing（2408.04307, ASPLOS 2025）**: PEC 机制（算法-系统协同）战略保存选中的专家子集，把 MoE checkpoint 降到与 dense 模型同级；全分片 checkpoint 均匀分布负载；两级管理异步处理内存快照与持久化。Megatron-DeepSpeed + ZeRO-2 数据并行/专家并行实测：每次 checkpoint 开销 -98.9%，下游任务平均精度 +1.08%。https://arxiv.org/abs/2408.04307
- **MoEvement: MoE 专用分布式内存 checkpoint（2412.15411, NSDI'26）**: (1) 稀疏 checkpoint 跨迭代增量快照专家子集；(2) 稀疏→密集 checkpoint 增量转换，一致性稠密 checkpoint 逐步重建；(3) pipeline 阶段边界激活/梯度上游日志，实现不重跑未受影响 worker 的局部恢复。≤64 专家模型：checkpoint 开销 -4×、恢复开销 -31×；MTBF 低至 10 分钟仍保持 ETTR≥0.94；总体训练加速最高 8×，不牺牲同步训练语义。https://arxiv.org/abs/2412.15411
- **Lazarus: MoE 弹性容错训练（2407.04656, 07-05）**: 针对 spot 实例频繁抢占（本质是常态化故障）——自适应分配专家副本解决专家负载不均，可证明最优的专家放置算法最大化恢复概率；故障后利用全部可用节点（无 GPU 闲置）。频繁节点故障 5.7×、真实 spot 实例轨迹 3.4× 优于现有 MoE 训练系统。https://arxiv.org/abs/2407.04656
- **AMD Full-Stack MoE 预训练（2511.17127, 11-21）**: 首个纯 AMD 大规模 MoE 预训练（MI300X + Pollara 网络），ZAYA1（760M active / 8.3B total MoE）。training stack 描述中明确将 fault-tolerance 与 checkpoint-reshaping 列为"常被忽略但关键的实用工具"——容错已成为全栈（硬件/网络/软件）成熟度叙事的一部分。https://arxiv.org/abs/2511.17127

### MoE checkpoint 的经济学（第一性原理）

| 维度 | Dense 模型 | MoE 模型 | 含义 |
|:--|:--|:--|:--|
| 总参数 vs 激活参数 | 相同 | 8.3B total / 760M active（ZAYA1） | 全量 checkpoint 存的是"不活跃"的冗余 |
| 专家利用率 | — | 高度非均匀（负载不均） | 高/低频专家可差异化处理 |
| checkpoint 语义 | 全量一致 | 稀疏快照需增量转稠密 | MoEvement 的 sparse→dense 转换层 |
| 恢复语义 | 全量重载 | 局部专家恢复即可继续 | ETTR≥0.94 @ MTBF 10min（MoEvement） |

## 四、故障检测与根因分析：训练侧延伸到推理侧

- **TELLER: LLM 推理跨层根因分析（2608.01975, 08-03, ASE 2026）**: 单个请求跨越推理引擎、Python/C++ 后端、CUDA API、GPU kernel 与分布式通信，现有 profiler 只给原始时间线、日志诊断缺跨层语义。TELLER 无侵入收集 NVTX/CUPTI traces + 服务日志 → 重建 per-request 调用链树 → dependency-aware causal-context slice（保父子结构/时序/通信关系）→ Trace Pair Encoding tokenizer 压缩为结构 token 序列（parent/depth/duration 属性）→ 多模态根因模型联合定位异常步、可疑算子并生成自然语言解释。适度 TPE 词表下每步 trace 长度 -80%+ 且横/纵视图性能最佳——**trace 压缩与诊断质量的权衡曲线**是论文核心方法论贡献。https://arxiv.org/abs/2608.01975
- **TENT: 声明式数据移动弹性引擎（2604.00368, 03-31）**: 推理/RL 场景 KVCache 成一级可迁移资产，imperative 早绑定路径选择导致状态盲 striping（无视拥塞与灰故障）→ 带宽搁浅 + 运维脆弱。TENT 将互联抽象为统一资源池、路径解析延迟到 slice 级晚绑定：按实时遥测+预测成本模型在 rails 间"喷洒"细粒度 slices，消除 head-of-line blocking，<50ms 透明自愈（绕开故障/降级路径，无需应用介入）。生产数据平面（Moonshot 系集群）：SGLang HiCache 推理吞吐 +1.36×、P90 TTFT -26%；RL 管线 Moonshot Checkpoint Engine 参数更新 +20-26%。https://arxiv.org/abs/2604.00368
- **RAPID-LLM: 韧性感知的分布式 LLM 性能建模（2512.19606, 12-22）**: DeepFlow 前端（硬件感知、算子级 Chakra traces）耦合 Astra-Sim 后端（显式多维网络拓扑 + 拥塞感知路由 + 降级/故障链路支持）。A100 验证：Llama 推理 step 延迟与 GPT 规模训练每 batch 时间预测相对误差 10.4%，代表性通信负载与 ns-3 匹配 8% 内——**软链路故障对训练/推理性能的敏感性首次可在仿真中系统性扫描**。https://arxiv.org/abs/2512.19606
- **TRANSOM: 训练任务全生命周期容错（2310.10046, 10-16）**: TOL（训练 pipeline 自动容错恢复与重启）+ TEE（多维指标自动异常检测）+ TCE（异步 checkpoint 自动容错恢复）。TEE 检测异常上报 TOL → 自动剔除异常节点并重启任务。GPT3-175B 预训练时间 -28%，checkpoint 保存/加载性能 20×。https://arxiv.org/abs/2310.10046

### 训练侧 vs 推理侧可靠性需求对比

| 维度 | 训练侧 | 推理侧 |
|:--|:--|:--|
| 故障后果 | 状态丢失（需 checkpoint 重放） | 服务质量退化（延迟/错误/断流） |
| 关键指标 | MTTR、有效吞吐、ETTR | P90 TTFT、吞吐、自愈时间 |
| 容错手段 | checkpoint/冗余/热替换 | 路径重路由、连接迁移、SLA 感知 |
| 故障语义边界 | 节点/GPU/通信 | 跨层请求链（引擎→kernel→网络） |
| 观测手段 | 指标+日志 | 分布式 trace（NVTX/CUPTI）+日志对齐 |

## 分析段落

### ① 因果链：checkpoint 架构为何五年内从"单层落盘"演进到"热替换"？

推理链条的起点是**模型规模与集群规模的指数增长**。LLM 从 8B 到 65B（PHOENIX）、再到 MoE 的 8.3B 总参（ZAYA1），全量 checkpoint 包含权重+优化器状态，体积随参数线性膨胀；同时万卡集群使硬件故障从"偶发"变成"统计必然"（SPARe 直言 100k+ GPU 下 restart 成本主导墙钟时间，ReCoVer 说"hardware faults routine rather than rare"）。这两股力量把 checkpoint-restart 推到临界点：**周期全量落盘的 IO/存储成本（快照时）与恢复时的重放成本（重算步数×吞吐损失）同时恶化**。于是优化目标从"减少存储占用"迁移到"减少失败路径的总时间（MTTR + 重放代价）"——这正是 TierCheck 用"内存差分快照（快恢复）+远端异步迁移（持久兜底）"替代单一后端的直接动机，也是 PHOENIX 把 checkpoint 从"持久化动作"变成"内存态空间冗余"的原因：只有让恢复路径不经过存储介质、且恢复时不需要重放计算（保留内存状态），才可能把 MTTR 压到 40 秒量级。因果链的末端是**任务语义层的变化**：传统 checkpoint-restart 恢复的是"作业"（重启整个任务），热替换恢复的是"节点"（备用节点接管，任务不中断）——恢复粒度从作业级下沉到节点级，是 2026 年容错设计最重要的结构性变化。

### ② 对比：三种"不重启任务"的容错范式如何权衡失败路径与正常路径？

除 checkpoint-restart 外，本批论文呈现三种不中断任务的范式，它们在**正常路径开销、故障路径代价、故障假设**三维度上构成互补而非替代：(1) **容错集合通信**（R²CCL/ReCoVer）在通信层做文章——R²CCL 靠多 NIC 连接迁移把 NIC 故障对上层透明化（正常路径开销 <1%），ReCoVer 靠保持 microbatch 数不变式把故障隔离在迭代内（正常路径开销低，但要求每次迭代语义可重放）；(2) **计算冗余**（SPARe）在梯度同步期堆叠冗余分片——正常路径开销 2~3×（近恒定，不随冗余线性膨胀），但故障路径代价为零（无需恢复动作，靠冗余直接掩蔽），适合故障频率极高的 restart 主导 regime；(3) **热替换**（PHOENIX）在调度层做——正常路径零开销（off-critical-path checkpoint），故障路径代价是有备用节点池（空间冗余成本转移为节点储备）。三者本质是**把"恢复成本"转化为"正常路径开销或储备成本"的不同比例**：通信层转化最少（1% 级），计算冗余转化最多（2~3×），热替换介于其间（零执行开销+节点储备）。集群故障率越高，越值得把成本前置到正常路径（SPARe 的 600k GPU 推演 -40~50% 训练时间即此逻辑）；故障率可控时，通信层透明 failover 的性价比最高（网络故障浪费 10~15% GPU hours 是最大单一浪费源，R²CCL 数据）。

### ③ 原理：为什么 MoE 是 checkpoint 问题的"放大镜"？

MoE 把 dense 模型的 checkpoint 矛盾放大了两个数量级：**总参数（决定 checkpoint 体积）与激活参数（决定计算量）分离**——ZAYA1 的 8.3B total / 760M active 意味着若按 dense 方式全量 checkpoint，存储的是 91% 本次迭代根本没参与计算的参数。第一性原理看，checkpoint 的本质是"保存可恢复训练状态的最小充分集合"，MoE 下该集合不是全量权重，而是**(a) 高频变化专家（MoC-System 的 PEC 只存部分专家）+ (b) 稀疏增量（MoEvement 跨迭代快照专家子集）+ (c) 恢复时的局部性（pipeline 边界日志让未受影响 worker 不重跑）**。三个系统给出同一结论的不同切面：MoC-System 证明"MoE checkpoint 可以降到 dense 同级"（-98.9% 开销），MoEvement 证明"低 MTBF 下仍可维持训练进度"（ETTR≥0.94 @ MTBF 10 分钟），Lazarus 则从负载侧证明"专家复本分配同时优化吞吐与恢复概率"。这与 dense 路线的逻辑一致性在于：**所有方案都在利用"训练状态的冗余度"**——dense 用层更新非均匀（LLMTailor），MoE 用专家利用非均匀（PEC），RL 用参数更新稀疏（AuroraRL 的 ~1% 变化率）。三层证据链说明"选择性持久化"已成为容错设计的第一性原理，而非权宜之计。

### ④ 分层视角：容错职责应该放在哪一层？

本批论文给出一个清晰的**分层分工图谱**：NIC/链路故障→通信层（R²CCL 连接迁移，故障对应用透明）；节点/GPU 故障→调度/任务层（PHOENIX 热替换、SPARe 冗余掩蔽）；计算错误（INF/NaN）→应用层算法容错（ATTNChecker ABFT）；跨层因果定位→观测/分析层（TELLER 的 trace+日志对齐）。分层依据是**故障语义边界与检测成本**：越靠下的故障越频繁但越容易在本地检测（链路超时），越靠上的故障越罕见但影响越大（训练发散）。R²CCL 的 10~15% GPU hours 浪费数据说明最便宜的修复在通信层；而 TELLER 揭示的跨层根因困难（单请求跨引擎/后端/CUDA/kernel/网络五层）说明一旦故障跨越语义边界，缺统一因果模型的分析层必然成为瓶颈。对超节点/万卡集群工程的意义：**容错不是单点组件而是分层职责的联合设计**——通信层透明 failover 处理高频小故障，调度层热替换/冗余处理中频节点故障，应用层 ABFT 兜底计算错误，观测层提供跨层因果链支撑决策。任何一层缺失都会把故障成本上抛给成本最高的一层（作业级重启）。

### ⑤ 推理侧可靠性：从"任务连续性"到"服务质量"的范式迁移

TELLER（ASE 2026）与 TENT 标志可靠性研究正式进入推理侧，且与训练侧有本质区别：训练侧故障的后果是**状态丢失**（重放可恢复，成本可量化），推理侧故障的后果是**服务质量违约**（延迟尖峰、TTFT 恶化、请求失败——直接影响 SLO 与收入）。TENT 的 <50ms 自愈（vs 训练侧分钟级 MTTR）体现了两侧时间尺度的差异：推理的故障窗口以 100ms 计，恢复动作必须早绑定解除、路径级热切换。RAPID-LLM 则提供了把"韧性"纳入设计期的能力——在仿真里系统性扫描软链路故障/拥塞对性能的影响，无需真机故障注入。三者的共同技术底座是**遥测与因果建模**：TELLER 的 TPE tokenizer（trace 长度 -80% 仍保诊断质量）、TENT 的实时遥测+预测成本模型、RAPID-LLM 的 Chakra 标准化执行轨迹——可靠性从"事后恢复"转向"实时感知+预测性调度"，这与训练侧"故障预测（GPU fault prediction）"的方向汇合，是 2026 年可靠性的主线叙事。

## 五、全球分布式与异构生态：容错的"边界条件"样本

- **INTELLECT-1: 跨洲 10B 模型容错训练（2412.01152, 12-02）**: 首个 10B 参数全球协作训练（1T tokens，3 大洲 14 并发节点、30 个独立算力提供方动态加入/离开，compute 利用率 83-96%）。PRIME 框架三件套：ElasticDeviceMesh（管理动态全局进程组，跨互联网容错通信 + 节点内本地进程组）、live checkpoint recovery kernels、hybrid DiLoCo-FSDP2；配合 int8 all-reduce 比传统数据并行通信带宽 -400×。**"节点随时可能消失"被当作第一公民约束设计**，是容错假设最极端的生产样本。https://arxiv.org/abs/2412.01152
- **A Survey of LLM × DATA（2505.18458, 05-23）**: DATA4LLM 存储章节将 fault-tolerant checkpointing 列为数据存储层的正式研究主题（与 KV-cache 管理、分布式异构存储层级并列）——容错 checkpoint 已从"训练系统内部机制"上升为"数据管理学科"的公共议题。https://arxiv.org/abs/2505.18458
- **Flotilla: 联邦学习容错框架（2507.02295, 07-03）**: stateless client + 服务端会话状态分离，周期性/增量 checkpoint；200+ client 快速 failover（秒级）、1000+ client 扩展性优于 Flower——边缘/联邦场景的容错设计样本（资源异质、故障频繁、异步聚合）。https://arxiv.org/abs/2507.02295

## 六、对可靠性测试工作的工程启示

### 故障模型与测试矩阵设计

本批论文的故障假设可归纳为四类，对应可靠性测试的不同注入维度：

| 故障类别 | 论文证据 | 测试注入方式 | 验收指标 |
|:--|:--|:--|:--|
| 永久节点/GPU 故障 | PHOENIX/ReCoVer/SPARe | 节点 kill/下电 | 热替换/冗余掩蔽时间、轨迹保持 |
| 瞬时/软故障（INF/NaN） | ATTNChecker | 计算结果位翻转注入 | 检出率、纠正开销 |
| 网络/NIC 故障与链路劣化 | R²CCL/RAPID-LLM | 链路 down/限速/抖动注入 | 透明 failover 时间、吞吐衰减 |
| 灰故障/性能降级 | TENT/RAPID-LLM | 拥塞/带宽搁浅仿真 | 自愈时间、P90 TTFT |

### 关键量化基线（可直接用于对标）

- 网络故障浪费 **10~15% GPU hours**（R²CCL）→ 通信层容错 ROI 的量化起点
- 通信层透明 failover 开销 **<1% 训练 / <3% 推理**（R²CCL）→ 容错开销的验收上限参考
- 热替换恢复 **<40s**、分级 checkpoint **<10s（40B）**（PHOENIX/TierCheck）→ 恢复时间目标区间
- MoE 场景 checkpoint 开销可降 **98.9%**（MoC-System）→ 稀疏化收益上限
- 计算冗余 2~3× 近恒定开销换 **-40~50% 训练时间**（SPARe @ 600k GPU）→ 冗余策略的收益模型

### 与万卡集群 RAS 主线的衔接

ReCoVer 的"迭代级语义保持"（microbatch 不变式）与 SPARe 的"故障数闭式表达式"（端耐久故障数/开销）为可靠性测试提供了**可计算的验收标准**——不再依赖"跑通即通过"的经验判断，而是给出"丢失 N 个节点后训练轨迹与无故障运行的等价性"这种可量化断言。结合 tech 组已收录的 504 GPU 运维分析（checkpoint 读占 21.5% 带宽），可靠性测试应从"单点故障恢复演练"升级为"故障注入 + 轨迹等价性 + 资源成本"三维验收体系。

### ⑥ 规模效应：故障预算的量化推理与 100k GPU 转折点

把本批论文的规模数据排成序列可得到一条清晰的数量级曲线：单节点（分钟级重试）→ 512 GPU（PHOENIX/ReCoVer 实测，热替换 <40s、轨迹保持可验证）→ 100k+ GPU（SPARe 断言 restart 主导 regime）→ 600k GPU（SPARe 推演 -40~50% 训练时间）。转折点的物理含义可以用故障预算推导：若单 GPU 年故障率（AFR）为 ~1%（数据中心级 HBM/焊点典型量级），万卡集群的日期望故障数 ≈ 10000 × 0.01/365 ≈ 0.27 次/天，即平均每 3~4 天一次全集群可见故障；10 万卡则每天 ~2.7 次。与此同时 checkpoint 恢复成本随模型规模线性膨胀（65B 全量状态可达 TB 级，落盘+重放小时级）——**故障频率上升与恢复成本上升相乘，使"每故障几小时停机"的数学期望在 10 万卡规模达到不可接受**。这正是 SPARe 论证"restart 主导"的量化基础，也解释了为什么 2026 年的论文集体放弃"少故障+慢恢复"假设，转向"故障是常态+恢复要亚分钟级"。对可靠性测试的含义：**验收标准必须随规模缩放**——512 GPU 上"40 秒恢复"的指标，到 10 万卡要除以故障频率的增量（恢复时间 × 故障率 = 停机占比），测试设计应围绕"停机占比 < 某阈值"而非单一 MTTR 数字。
