## 0. 执行摘要

**核心判断**：大规模 AI 训练的可靠性机制正处于**「检查点(Checkpoint)单一支柱 → 多机制协同」**的范式切换期。本日窗口（arXiv 提交 2026-04 ~ 2026-08）涌现的 22 篇增量工作显示，可靠性工程的三条技术路线同时成熟：

1. **容错架构从「保存-重启」走向「热替换-收缩-重接入」**：PHOENIX（零开销 in-memory checkpoint + hot-swap 40s 恢复）、ReCoVer（容错集合通信 + 不变量保持，2.23× 有效吞吐）、Belayer（Agentic RL 影子 worker + KV 前缀重建，42× 恢复加速）分别从节点级、集合级、worker 级三个粒度重构恢复路径。
2. **检查点从「整模型快照」走向「语义化稀疏/分层」**：MoEvement（专家子集稀疏 checkpoint，4× 开销降低 / 31× 恢复加速）、LLMTailor（按层更新率选择性 checkpoint，4.3× 体积缩减）、BitSnap（bitmask 稀疏 + 量化 16× 压缩）、TierCheck（三级存储分层，端到端 <10s）——共识是**训练状态的非均匀性（层间/专家间/时间上）成为压缩杠杆**。
3. **故障特征从「黑盒假设」走向「硬件接地(RTL)特征化」**：LLM-PRISM（RTL 级 GPU 故障模拟 + 7,664 次训练运行，量化 SDC 对训练的破坏路径）、VCCL（生产集群通信库，primary-backup QP 容错）、R²CCL（多网卡连接迁移 <1% 开销）——可靠性测试正从「故障注入演练」升级为「故障模型驱动的系统设计」。

**对国内万卡集群的直接启示**：① 故障时间不可预测（tech 组 HeaRank 结论）→ 可靠性投入应聚焦「恢复速度 × 恢复粒度」而非「预测概率」；② SDC（静默数据损坏）是比显式故障更危险的失效模式，需要 RTL 级特征化 + 训练轨迹监控双管齐下；③ 通信库（VCCL 已开源、R²CCL）成为容错的新战场，国产通信库应在 QP 级容错与可观测性上对标。

## 1. 主线一：LLM 训练容错系统——恢复路径的三粒度重构

### 1.1 节点级：热替换（Hot-Swap）替代整任务重启

- **PHOENIX: Resilient LLM Training with Hot-Swapping via Zero-Overhead Checkpoint**（https://arxiv.org/abs/2607.01646，2026-07-06，NVIDIA 系团队）：双机制组合——① off-critical-path in-memory checkpointing（空间冗余，与计算重叠实现**零故障外开销**）；② communicator reconstruction protocol（运行时用备用节点替换故障节点，不终止整任务）。评估：512× A100、65B 参数，**热替换恢复 <40s**，错误外执行零开销。
- **SPARe: Stacked Parallelism with Adaptive Reordering**（https://arxiv.org/abs/2603.00357，2026-05-27，ICML 2026）：面向 100k+ GPU 的「重启主导」场景，在梯度同步期间通过堆叠冗余数据分片 + 自适应重排序**掩盖节点故障**，开销恒定 2~3×（传统复制随冗余线性膨胀）。600k GPU 极端规模下比传统复制**时间-训练缩短 40~50%**；给出可承受故障数/开销的闭式表达式，SimGrid 验证 + 冗余与检查点联合优化。
- **TRANSOM: An Efficient Fault-Tolerant System for Training LLMs**（https://arxiv.org/abs/2310.10046，2023-10）：更早的综合框架（TOL 生命周期 + TEE 异常检测 + TCE 异步检查点），GPT3-175B 预训练时间 -28%、检查点存取 +20×——本组工作的「先声」，验证了「自动检测→节点剔除→异步恢复」闭环的可行性。

**分析一：为什么 hot-swap 是 100k GPU 时代的必然**。传统 checkpoint-restart 的恢复延迟 = 检测时间 + 全局同步 + 全量加载，在 100k GPU 规模下重启成本可主导墙钟时间（SPARe 明确以「重启主导区」为设计前提）。PHOENIX 的零开销 in-memory checkpoint 解决了「故障外开销 vs 恢复延迟」的 Pareto 权衡——把检查点放在 off-critical-path 的内存冗余而非持久化存储，用**空间换时间**；SPARe 则更进一步，用**冗余计算换同步时间**（堆叠分片使梯度同步在部分节点失效时仍可完成）。两者共同揭示：可靠性设计的本质约束从「存储带宽」转向「并行度冗余成本」，当 GPU 数量超过某个阈值（约 10k+），冗余分片/热备的成本低于重启损失的算力成本——这正是万卡集群可靠性经济模型的拐点。

### 1.2 集合级：容错通信 + 梯度语义不变量

- **ReCoVer: Resilient LLM Pre-Training System via Fault-Tolerant Collective and Versatile Workload**（https://arxiv.org/abs/2605.11215，2026-05-11，ANL 系 + Zheng Zhang 团队）：三层解耦协议——① 容错集合（fault-tolerant collectives）隔离故障跨副本传播；② in-step 细粒度恢复保留迭代内进度、防梯度损坏；③ 灵活负载策略在幸存者间动态重分配 microbatch 配额。**核心不变量：每迭代 microbatch 数恒定 → 梯度与无故障运行随机等价**。512 GPU 端到端预训练，即使 256 GPU 中途丢失仍保持无故障参考轨迹；对比 checkpoint-restart 基线**有效吞吐 2.23× 更高**（234 GPU 小时多处理 74.9% token）。
- **AuroraRL: Fast, Fault-Tolerant, and Cost-Efficient RL over Decentralized Network**（https://arxiv.org/abs/2602.11456，2026-02-12，蚂蚁系）：面向以太网/WAN 松散耦合 GPU 的 RL 后训练——利用「RL 每步更新仅 ~1% 参数变化」的稀疏性，每步存稀疏 delta checkpoint，管线化多流传输 + 与 rollout 生成重叠；lease-based 容错。Qwen3-8B 权重传输 **79× 缩减**、吞吐 1.3~9.5×、端到端达到理想 RDMA 单数据中心基线的 **91.1%**，容错透明且精度无损；按 token/美元计比预留 RDMA 集群高 **1.21~1.59×**。
- **R²CCL: Reliable and Resilient Collective Communication Library for LLM Training and Serving**（https://arxiv.org/abs/2512.25059，2025-12-31，UIUC 系）：多网卡硬件上的无损耗低开销故障切换——快速连接迁移 + 带宽感知负载再分配 + 弹性集合算法。网络故障浪费 10~15% GPU 小时（慢恢复导致）；R²CCL 对 NIC 故障训练开销 <1%、推理 <3%，**优于 AdapCC 12.18×、DejaVu 47×**。

**分析二：ReCoVer 的「梯度不变量」是容错从工程走向科学的标志**。传统容错只保证「能恢复」，不保证「恢复后训练轨迹与无故障一致」——这正是为什么故障后模型质量波动难以归因。ReCoVer 把「每迭代 microbatch 数恒定」设为系统不变量，从数学上保证恢复后的梯度序列与无故障运行随机等价，使**容错从「尽力而为」升级为「可证明正确」**。这一思路与 08-17 知识库沉淀的「故障注入测试必须定义恢复正确性判据」一脉相承：恢复正确性不是「loss 继续下降」，而是「轨迹偏差有界」。AuroraRL 的稀疏 delta checkpoint 则是同一思想在带宽受限场景的极致化——把「全量状态同步」降为「变化量同步」，其 1% 稀疏性洞察与 LLMTailor 的层更新非均匀性互为印证（见 2.1）。

### 1.3 Worker 级：Agentic RL 的故障域细化

- **Belayer: Efficient Fault Tolerance for LLM Agentic RL Training**（https://arxiv.org/abs/2608.14635，2026-08-18，上海 AI Lab 系）：首个面向 LLM Agentic RL 的容错系统——Agentic RL 把 GPU rollout 引擎与**有状态环境容器**（文件编辑/命令执行/依赖安装的可见副作用）耦合，单轨迹跨多轮生成+环境交互，组件故障会丢弃已完成工作或使环境状态与 LLM 上下文不一致。Belayer 双机制：① 影子 worker 选择性 GPU 状态复用（所有权/健康检查后保留独立权重与 KV-arena 原始分配，从日志 token 前缀重建 request 特定 KV）；② 环境失败用完整 checkpoint/restore 联合捕获容器文件系统与运行时状态，并与 LLM 上下文协调保持前缀一致性。自适应策略将全状态 checkpoint 与 LLM 推理气泡重叠。**故障外开销低；worker 恢复比引擎冷启动快 42×；环境故障恢复快 1.5~3.5×**。

**分析三：Agentic RL 暴露了传统容错假设的盲区**。传统训练容错假设「状态=权重+优化器+数据」，而 Agentic RL 引入「环境状态」这一第三类状态——容器内文件系统、已执行命令的副作用、agent 的 KV 上下文与环境的因果一致性。Belayer 的贡献在于**把 KV 前缀与容器状态联合建模为可恢复单元**，其「从日志 token 前缀重建 KV」本质上是对「可重放性（replayability）」原则的工程化——与 SCOUT（tech 组收录）的现场重放理念同构。对万卡集群的启示：随着 RLVR/Agentic 工作负载占比上升，可靠性测试必须覆盖「环境状态一致性」这一新维度，传统的「权重快照 + 重启」测试矩阵已不充分。

**容错系统横向对比（三粒度 × 关键指标）**：

| 系统 | 粒度 | 恢复机制 | 故障外开销 | 恢复/加速指标 | 适用场景 |
|:--|:--|:--|:--|:--|:--|
| PHOENIX | 节点级 | in-memory checkpoint + hot-swap | 零 | <40s 热替换 | 永久节点故障 |
| SPARe | 并行组级 | 冗余分片堆叠 + 自适应重排 | 2~3× 恒定 | 600k GPU 下 time-to-train -40~50% | 100k+ GPU 重启主导区 |
| ReCoVer | 集合级 | 容错集合 + microbatch 不变量 | 低（未量化） | 有效吞吐 2.23× | 3D 并行/HSDP 通用 |
| Belayer | worker 级 | 影子 worker + KV 前缀重建 | 低（未量化） | 恢复快 42×（vs 冷启动） | Agentic RL 训练 |
| AuroraRL | 通信级 | 稀疏 delta + lease 容错 | 低（未量化） | 传输 -79×，吞吐 1.3~9.5× | 以太网/WAN 松散集群 |
| TRANSOM | 任务级 | 检测+剔除+异步检查点 | 低 | 预训练 -28%，存取 +20× | 传统集群（较早） |

**因果链推演：从「故障外开销」到「恢复粒度」的设计权衡**。六套系统在「故障外开销（failure-free overhead）→ 恢复粒度（recovery granularity）」二维空间中形成 Pareto 前沿：PHOENIX 用 off-critical-path 内存冗余实现零开销但恢复粒度最粗（节点级，需备用节点）；ReCoVer 用集合级协议实现细粒度恢复但引入协议开销；Belayer 的 KV 前缀重建介于两者之间——它保留「热」状态（权重/KV-arena）只重建「冷」状态（request 特定 KV），本质是**按状态温度分层决定恢复策略**。这个「状态温度」视角可推广为可靠性测试的设计原则：先按访问频率/重建成本给训练状态分级，再为每级选择恢复机制，避免「一刀切全量 checkpoint」的成本浪费。

## 2. 主线二：检查点优化——从「全量快照」到「语义化稀疏」

### 2.1 稀疏/分层检查点：利用训练状态的非均匀性

- **MoEvement: Sparse Checkpointing for Fast and Reliable MoE Training**（https://arxiv.org/abs/2412.15411，2024-12，NSDI'26 Camera-Ready，Stanford Kozyrakis 组）：面向 MoE 的三机制——① 稀疏检查点（跨迭代增量快照专家子集）；② 稀疏→稠密转换（增量重建一致稠密检查点）；③ 流水线阶段边界激活/梯度上游日志（局部恢复，不重执行未受影响 worker）。64 专家 MoE：**检查点开销降低至 1/4、恢复开销降低 31×**；MTBF 低至 10 分钟仍维持 ETTR ≥0.94；最高 8× 整体训练加速，不牺牲同步训练语义。
- **LLMTailor: Layer-wise Tailoring Tool for Efficient Checkpointing**（https://arxiv.org/abs/2602.22158，2026-02-25，PDSW'25）：利用「LLM 层间更新高度非均匀」——部分层变化显著、部分稳定甚至不变——选择性仅对显著更新层做检查点。checkpoint 体积 **4.3× 更小**（Llama3.1-8B）、checkpoint 时间 **2.8× 更快**（Qwen2.5-7B），模型质量保持。
- **BitSnap: Checkpoint Sparsification and Quantization**（https://arxiv.org/abs/2511.12376，2025-11-15，清华系）：bitmask 稀疏化 + 聚类量化的自适应组合——**16× 压缩比不损精度**，聚类量化再 2× 微损；随训练阶段/架构动态调节压缩比-速度-精度三角。
- **Inshrinkerator: Compressing Training Checkpoints via Dynamic Quantization**（https://arxiv.org/abs/2306.11800，2023-06，Gatech 系）：动态量化 + 量化感知 delta 压缩，**压缩比最高 39×**，容错训练可承受 10 次恢复精度影响可忽略；非均匀量化利用「权重对压缩的敏感性随训练变化」。
- **TierCheck: Tiered Checkpointing for Fault Tolerance in LLM Training**（https://arxiv.org/abs/2605.17821，2026-05-18，港中文 Lee 组）：三级存储对齐故障异质性——轻量差分检查点存本地/对等内存（快速局部恢复），重量级基检查点异步迁移远端持久存储；跨层严格全局一致性不阻塞训练。40B 模型端到端检查点 **<10s**，支持高频检查点。
- **FastPersist: Accelerating Model Checkpointing in DL**（https://arxiv.org/abs/2406.13768，2024-06，微软）：NVMe 优化 + SSD 写并行 + 与计算重叠——**持久化检查点创建最快 116× 加速**，支持近每迭代检查点。

### 2.2 MoE 弹性与混合并行容错

- **Lazarus: Resilient and Elastic Training of MoE Models**（https://arxiv.org/abs/2407.04656，2024-07，UC Berkeley 系）：自适应专家副本分配（专家负载天然不均衡）+ 可证明最优的专家放置（最大化故障恢复概率）+ 弹性 token 分发器（故障后全节点利用、无 GPU 空闲）。频繁节点故障下比现有 MoE 系统 **5.7×**，真实 spot instance 轨迹 **3.4×**。
- **MoC-System: Efficient Fault Tolerance for Sparse MoE Training**（https://arxiv.org/abs/2408.04307，2024-08，ASPLOS 2025）：Partial Experts Checkpointing（PEC）——只保存专家子集，将 MoE 检查点体积降到与稠密模型相当；全分片检查点均匀分配负载；两级异步快照+持久化。基于 Megatron-DeepSpeed，**每次检查点开销最多降低 98.9%**（ZeRO-2 + 专家并行），平均下游任务精度 +1.08%。
- **Fault-Tolerant Hybrid-Parallel Training with Reliable In-memory Checkpointing**（https://arxiv.org/abs/2310.12670，2023-10，港中文/科大）：层级异步快照协调（三层异步设备调度，快照与训练并行）+ 混合内存检查点保护（节点内冗余防硬件故障，无跨节点通信阻塞）。Llama-2-34B / 256 MI250X（512 GPU）**零内存检查点保存开销**（Frontier）。

**分析四：检查点压缩的「非均匀性」共识与物理根源**。五篇独立工作（MoEvement/LLMTailor/BitSnap/Inshrinkerator/MoC-System）不约而同利用训练状态的非均匀性，这不是巧合而是物理必然：① **层间非均匀**——深层/近输出层梯度更大、更新更频繁（LLMTailor 实证）；② **专家间非均匀**——MoE 中热专家被路由更多 token、状态变化快（MoEvement/MoC-System 实证）；③ **时间非均匀**——训练早期权重变化大、后期收敛变化小（Inshrinkerator 的动态量化依据）。三轴非均匀性叠加使「全量等权快照」的信息效率极低——保守估计 90%+ 的检查点字节从未被恢复利用。可靠性测试的新命题随之而来：**如何验证「稀疏检查点恢复后的轨迹等价性」**？MoEvement 的稀疏→稠密转换一致性、ReCoVer 的 microbatch 不变量、BitSnap 的精度影响量化，是三种可操作的验证判据。

### 2.3 持久内存与算法级容错（补充）

- **TRAININGCXL: Failure Tolerant Training with Persistent Memory Disaggregation over CXL**（https://arxiv.org/abs/2301.07492，2023-01，首尔国立大学）：把持久内存（PMEM）以 Type-2 方式纳入 GPU 缓存一致性域——GPU 无软件干预直访 PMEM，CXL 控制器旁放置计算与检查点逻辑实现「主动持久化」；利用推荐模型特性把检查点开销移出训练关键路径；放松跨 batch 的参数/嵌入更新序列。对比现代 PMEM 推荐系统：**训练性能 5.2×、能耗 -76%**。这条线的意义在于：CXL 内存池化（本库 power-architecture/supernode 常跟踪）为「检查点即内存层次的一部分」提供了硬件底座——检查点不再需要单独 I/O 路径，而是内存系统的持久化视图。
- **ATTNChecker: Highly-Optimized Fault Tolerant Attention for LLM Training**（https://arxiv.org/abs/2410.11720，2024-10，ANL 系）：首个面向 attention 的算法级容错（ABFT）——系统化故障注入实验刻画 INF/NaN/近-INF 在 LLM 中的传播模式（可触发不可训练态、迫使从检查点加载），再据传播模式设计轻量保护。四模型评估：**平均 7% 训练开销下检测并纠正全部极端错误**；对比 SOTA checkpoint/restore 恢复开销**最多降低 49×**。ABFT 的价值在于「预防性纠错」——在错误扩散前就地纠正，而非事后恢复，与 SDC 特征化（主线四）互补：PRISM 回答「哪些故障危险」，ATTNChecker 回答「如何在传播路径上拦截」。

**检查点方案横向对比（压缩/加速 vs 代价）**：

| 方案 | 压缩/加速机制 | 指标 | 代价/限制 | 状态 |
|:--|:--|:--|:--|:--|
| MoEvement | 专家子集稀疏 + 稀疏→稠密转换 | 开销 -4×，恢复 -31×，ETTR≥0.94（MTBF 10min） | 仅 MoE；需一致性转换 | NSDI'26 |
| LLMTailor | 按层更新率选择性保存 | 体积 -4.3×，时间 -2.8× | 需层更新率 profiling | PDSW'25 |
| BitSnap | bitmask 稀疏 + 聚类量化 | 压缩 16×（无损精度）+2×（微损） | 量化精度影响需监控 | 预印本 |
| Inshrinkerator | 动态量化 + 量化感知 delta | 压缩最高 39×，10 次恢复无损 | 压缩率-精度权衡随训练变化 | 预印本 |
| MoC-System | Partial Experts Checkpointing | 检查点开销 -98.9% | 仅 MoE；ZeRO-2 + EP | ASPLOS'25 |
| TierCheck | 三级存储分层（本地/peer/远端） | 端到端 <10s，支持高频 | 需跨层一致性协议 | 预印本 |
| FastPersist | NVMe 优化 + SSD 写并行 | 持久化创建最快 +116× | 依赖本地 SSD 资源 | 预印本（微软） |

**从「存储分层」到「状态温度」的统一视角**。将主线一的分析三与主线二的 TierCheck 放在一起看，出现一个有趣的收敛：Belayer 按「重建成本」给 worker 状态分层，TierCheck 按「故障频率」给存储分层（本地/peer 内存应对高频小故障，远端持久化应对低频大故障），ReCoVer 按「梯度语义」给恢复分层。三者的共同结构是：**可靠性机制正在从「单一存储/单一恢复策略」走向「异构分层 + 自适应选择」**——这与存储行业的 HBM/CXL/SSD 三级内存架构（tech 组已收录）形成同构。这提示可靠性测试的基准设计也应分层：小故障频繁注入（本地恢复路径）与大故障低频注入（远端恢复路径）应分开测试，且验证「层间切换」的正确性（TierCheck 的跨层全局一致性是这类测试的标尺）。

## 3. 主线三：通信层容错——NCCL 之外的可靠性底座

- **VCCL: Efficient, Reliable and Observable Collective Communication Library**（https://arxiv.org/abs/2510.00991，2025-10，Infrawaves/清华/智谱/联通，**已开源**）：生产集群经验驱动的 NCCL 替代——① 去掉耗 SM 的 P2P kernel（节点内数据搬运与流依赖迁移到 CPU 线程与 GPU copy engine）；② **primary-backup QP 机制**容忍频繁 NIC 端口故障；③ window-based monitor 以 **O(μs) 级**观测网络瞬态异常。生产部署数月：训练吞吐比 NCCL **最高 +5.28%**，通过运行时容错与细粒度监控减少大量 GPU 资源浪费。
- **R²CCL**（见 1.2，https://arxiv.org/abs/2512.25059）：多 NIC 连接迁移 + 弹性集合算法，NIC 故障训练开销 <1%。
- **Fault-Tolerant Hybrid-Parallel Training**（https://arxiv.org/abs/2310.12670）：节点内冗余替代跨节点通信的检查点保护，避免 HP 下通信阻塞（见 2.2）。

**分析五：通信层成为可靠性的「最后一公里」**。数据表明网络故障浪费 10~15% GPU 小时（R²CCL），NIC 端口故障是生产集群最高频硬件故障之一（VCCL 的 primary-backup QP 直接针对此）。两条技术路线分野清晰：**VCCL 代表「生产级工程韧性」**（简单可靠的 QP 主备 + 可观测性，宁要 5% 吞吐提升不要复杂算法），**R²CCL 代表「研究级算法弹性」**（连接迁移 + 负载再分配的自动化）。对国内通信库研发（如国产 NCCL 替代）的启示：① 故障模型应来自生产遥测而非假设——VCCL 的 O(μs) window monitor 正是为了「先看见再容错」；② QP 级主备比 TCP 级重传更适合 RDMA 集群（恢复延迟差 2~3 个数量级）；③ 可靠性测试必须包含**网络故障注入矩阵**（NIC 端口故障/链路抖动/交换机重启），且与训练轨迹可观测性联动（呼应 tech 组 SCOUT 的带外观察器）。

## 4. 主线四：GPU 故障特征化与 SDC——从故障注入演练到硬件接地

- **LLM-PRISM: Characterizing Silent Data Corruption from Permanent GPU Faults in LLM Training**（https://arxiv.org/abs/2604.10390，2026-04-12，Rochester/NVIDIA 系）：**首个硬件接地（RTL 级）的 LLM 预训练 SDC 弹性特征化**——RTL 级 GPU 故障模拟 + 嵌入 Megatron-LM 的随机注入引擎；7,664 次训练运行覆盖 FP16/BF16/FP8 三精度域，分析故障类型/速率/数值格式如何决定弹性。发现：① LLM 抵抗低频故障；② 影响高度非均匀——**关键数据通路与特定精度格式在中度故障率即可引发灾难性发散**；③ 提供 SDC 弹性的首个硬件接地预训练特征化。
- **Characterization-Guided GPU Fault Resilience in NVIDIA MPS**（https://arxiv.org/abs/2605.26461，2026-05-26，Rice 系）：MPS 弱故障弹性（一进程故障终止所有协程进程）→ 系统性 GPU 故障特征化 + 端到端处理流水线分析后双机制：① 主要内存相关故障在开源 GPU 驱动内核模块内软件隔离；② 专有软件内故障用虚拟内存 GPU 驻留状态共享实现快速恢复。多 GPU/负载验证开销最小。
- **Deep4ge: DNN Training Trajectories for Fault Detection and Diagnosis**（https://arxiv.org/abs/2607.12868，2026-07-14，ICSME Data & Tool Track 2026）：**公开基准数据集**——14,227 次训练运行（59 个 Stack Overflow 改编 TensorFlow/Keras DNN 程序 × 27 种源码变换 × 7 类故障），9,845 故障运行 + 4,382 正确基线；每 epoch 记录 4 个评估指标 + 26 个特征（权重/梯度/激活/精度损失趋势/学习率/硬件使用）。支持二分类故障检测、多分类故障诊断、部分训练轨迹的早期故障预测。数据集与注入框架开源（Zenodo 10.5281/zenodo.20337241）。

**分析六：SDC 是比显式故障更危险的失效模式，且无法用传统手段测出**。显式故障（崩溃/挂起）有明确信号可检测；SDC 则静默污染梯度/参数，训练「正常」继续但模型质量劣化，恢复时从污染 checkpoint 重启会**放大而非消除**损坏（SCOUT 的干净重放认证正是为此）。LLM-PRISM 的 RTL 接地方法学价值在于：把「故障注入」从随机位翻转的粗粒度演练升级为**制造逃逸(manufacturing escape)/硅老化(aging)驱动的真实缺陷模型**，并量化精度格式（FP8 尤甚）作为 SDC 敏感性的放大器。对可靠性测试体系的启示：① 测试矩阵应包含「精度格式 × 故障速率 × 数据通路」三维组合（LLM-PRISM 已证非均匀性，抽样测试会漏掉关键发散区）；② 训练轨迹监控（Deep4ge 的 26 特征）可作为 SDC 的廉价在线探针——权重/梯度/激活的趋势异常是 SDC 的指纹；③ MPS 类多租户共享场景需要故障隔离测试，不能假设租户间故障透明。

**GPU 故障研究路线对比（预测/特征化/隔离）**：

| 工作 | 路线 | 方法 | 关键指标 | 与训练系统关系 |
|:--|:--|:--|:--|:--|
| LLM-PRISM | 特征化 | RTL 模拟 + Megatron 注入 | 7,664 runs；FP8 高敏感 | 设计期预防 |
| HeaRank* | 预测/排序 | 生产遥测 + 风险排序 | AUC 0.83，top5% 捕 64% | 运维期调度 |
| SCOUT* | 定位 | 共识 + 现场重放 | 11s 恢复；SDC 认证 | 故障后恢复 |
| Deep4ge | 检测基准 | 26 特征训练轨迹 | 14,227 runs 开源 | 监控探针 |
| MPS Resilience | 隔离 | 驱动层隔离 + 状态共享 | 最小开销 | 多租户隔离 |
| VCCL/R²CCL | 容错 | QP 主备 / 连接迁移 | <1~3% 开销 | 通信层防护 |

（* 由 tech 组收录，此处仅对比引用）

**分析七：可靠性测试方法学的三段演进——从「事后复盘」到「设计内建」**。将本组 22 篇工作按时间轴排序，可清晰看到可靠性测试方法的演进：**第一代（2023-2024，TRANSOM/FastPersist/Lazarus/MoC-System）**——「快照-重启」范式内优化，测试重点是「恢复多快」；**第二代（2024-2025，MoEvement/Inshrinkerator/ATTNChecker/R²CCL）**——「稀疏/压缩/算法级容错」，测试重点是「恢复后质量损失多少」；**第三代（2026，LLM-PRISM/ReCoVer/Belayer/SCOUT/VCCL）**——「故障模型驱动设计」，测试重点是「故障如何建模 + 恢复如何证明正确」。驱动演进的根因是规模：万卡集群上故障从「异常事件」变成「统计必然」，迫使可靠性从「事后保险」升级为「设计约束」。这一演进对国内集群建设的直接含义：可靠性测试预算应向前移至**设计阶段**（RTL 模拟、故障注入矩阵、恢复正确性证明），而非仅靠生产环境的故障演练——后者在万卡规模下的成本（一次全集群重启 ≈ 数百万 GPU 小时）已不可承受。

## 6. 方法学总结：可靠性测试追踪的增量框架

**本组增量价值**：区别于 tech 组的「集群训练故障处理」（偏系统设计）与 cluster-training 组的「训练优化」（偏性能），本组聚焦**可靠性「测试/追踪/验证」维度**，从 22 篇增量工作中提炼出三层测试框架：

| 层级 | 测试对象 | 代表工作 | 验证判据 |
|:--|:--|:--|:--|
| L1 恢复正确性 | checkpoint/容错系统 | ReCoVer（梯度不变量）、MoEvement（稀疏→稠密一致性）、SCOUT*（干净重放认证） | 轨迹等价性（非「loss 不涨」） |
| L2 故障模型 | 硬件/通信故障 | LLM-PRISM（RTL 接地 SDC）、VCCL（QP 主备）、R²CCL（NIC 迁移） | 故障注入矩阵 × 精度格式 × 数据通路 |
| L3 在线监控 | 训练轨迹异常 | Deep4ge（26 特征基准）、VCCL（O(μs) monitor） | 早期预测 / 瞬态异常可见 |

**待验证判断（开放问题）**：① 稀疏检查点的「轨迹等价性」缺乏统一形式化定义——ReCoVer 的 microbatch 不变量是否可推广为通用判据？② LLM-PRISM 的 RTL 模拟与真实硅片故障（field data）的差距多大——制造逃逸分布是否与模拟注入分布一致？③ VCCL 的开源是否引发国产通信库（如华为 HCCL、阿里 ACCL）的 QP 级容错对标？建议后续跟踪 VCCL 的 GitHub 活跃度与国内厂商采用情况。

## 7. 生产实践参考与搜索局限说明

### 7.1 生产系统实践：全栈 AMD 平台的大规模 MoE 预训练

- **Training Foundation Models on a Full-Stack AMD Platform**（https://arxiv.org/abs/2511.17127，2025-11-21，Zyphra 团队）：首个纯 AMD 硬件（MI300X + Pollara 网络）的大规模 MoE 预训练报告，其中「often-ignored utilities」一节明确把 **fault-tolerance 与 checkpoint-reshaping** 列为训练栈的核心组成而非附属品——与主流「性能优先、可靠性补丁」的工程叙事形成对比。ZAYA1-base（760M active / 8.3B total MoE）在推理/数学/编程基准上匹敌 Qwen3-4B、Gemma3-12B，超越 Llama-3-8B——证明容错开销并未拖累最终模型质量。

**实践要点提取**：① 容错与检查点重塑（checkpoint-reshaping）在生产栈中「常被忽略却必不可少」，应在系统设计初期预留；② AMD 生态（ROCm）的容错成熟度随规模化验证提升，国产加速卡生态可对标此路径——**可靠性不是发布后的补丁，而是规模化训练的前置条件**。
