- **Contract-Grade Verifier: LLM 生成 GPU kernel 的契约级验证器（cross cs.LG）**（arXiv:2608.12700, 08-13）: 反驳「LLM 生成 GPU kernel 正确率高」的行业共识——现有正确率来自单一松测试（固定形状随机输入+近似比较），一个 kernel 可通过该测试仍静默错误（NaN/Inf 被当成普通数、逐次运行不一致、形状变化即坏、fp16 累积）。作者构建 **12 个对抗门的契约级验证器**（多个门容差无关、无法用阈值糊弄），审计 2638 个已被公开系统自带 harness 接受的机器生成 kernel：**39.5% 坏到任何容差论证都无法挽救，62.1% 至少携带 1 个违规**；标准测试接受了验证器拒绝的 1487 个 kernel（反向仅 14 个）。四重独立辩护：7/7 阳性对照、阈值校准扫描、98.5% 与参考基准正确性代码一致、分层人工审计。对 AI 辅助开发的启示：**「报告的正确性信号远弱于数字所示」——LLM 生成代码的验收必须升级为容差无关的契约级验证，而非随机输入近似比对**。https://arxiv.org/abs/2608.12700
- **Validation-Centric AI-Assisted GPU Porting: 25 万行遗留天气代码的验证中心移植**（arXiv:2608.13122, 08-14）: CReSS 遗留 Fortran 天气仿真（250K+ 行）AI 辅助 GPU 移植案例——工作流=AI agent 抽取 OpenMP 区域→从物理意义仿真状态生成 dump 基准 kernel→应用 OpenACC 变换→**逐元素与 dump 参考数据比对+应用级验证**。真实台风仿真验证了 **162 个目标 kernel 的数值正确性，应用级 5.1x 加速**，并检出 5 个 kernel 的数值差异（浮点/内在函数差异、阈值敏感分支发散、抵消效应），反馈给应用开发者。结论：**AI 辅助 GPU 移植不仅是代码生成，必须设计验证中心工作流**（会话跨度上下文管理、运行时状态重建、静态分析遗漏的恢复成本是实际障碍）。与 2608.12700 同属「LLM 辅助代码可靠性验证」主题线——移植/生成的每个环节都要显式验证。https://arxiv.org/abs/2608.13122
- **vToken: token 级虚拟化实现可回收 KV 缓存（cross cs.AI）**（arXiv:2608.13263, 08-14）: KV 缓存可靠性主线的**回收维度**——PagedAttention 固定块管理与 token 粒度驱逐算法不匹配，造成块内碎片（intra-block fragmentation），大量已分配 KV 内存不可回收。vToken 用 token 表间接层解耦逻辑 token 存活与物理块放置，异步 repacking 回收存活 token。量化：相比 Naive-Evict 基线，每请求保留 KV 块 **-27.2%~72.3%**，SLA 约束吞吐 **+1.37x**，受限 active-KV 预算下最大并发 **2x**，且集成足迹从 500+ 行降到 50 行内。KV 主线第五日：HiSparse（分层，08-10）→ OasisKV（预取，08-11）→ ImpactHO（交接迁移，08-12）→ vToken（碎片回收，08-14）——KV 状态生命周期从「驻留/流动」延伸到「内存物理可回收性」，是 serving 内存可靠性的边界问题。https://arxiv.org/abs/2608.13263
