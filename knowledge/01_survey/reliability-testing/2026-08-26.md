### 3.2 scarHW 的因果链分析：为什么"容错"正在硬件化？

scarHW 的核心主张值得展开：将共识协议（POPUC）实现进 FPGA smartNIC，让"mostly-synchronous"的硬件行为替代软件层的 mostly-asynchronous 协调（Paxos 及其变体）。从第一性原理看，这条技术路线的因果链是：**数据中心一致性复制的根本矛盾 = 同步假设（性能来源）与异步现实（正确性要求）之间的张力**。Paxos 类协议选择 mostly-asynchronous 以容忍网络异步，但代价是协调开销随副本数增长；scarHW 观察到可编程网络设备在数据中心内实际呈现"mostly synchronous"行为（时延有界、时钟近似同步），因此将同步假设固化为硬件语义，用硬件加速的协同决策换取吞吐数量级提升。这解释了为什么是 smartNIC 而非通用 CPU 承载共识——**容错逻辑的时延敏感部分下沉到数据路径（data plane），控制路径只保留决策协调**，这与 NVIDIA 在 NCCL 中引入 Primary-Backup QP（VCCL 采用）的容错硬件化思路同构。

对万卡集群的启示：训练侧容错（FT-HSDP 的 FTAR、VCCL 的 primary-backup QP）已经在集合通信库层做硬件辅助化，而 scarHW 展示了**通用数据中心复制**同样可硬件化的证据。两者的共同方向是"容错从软件重试向硬件状态机迁移"——这暗示未来的容错训练可能进一步下沉到 NIC/交换芯片层面（如网内聚合 SHARP 的容错扩展）。但需注意边界：scarHW 的零停机保证仅针对"少数副本失败"（minority of replicas），且是复制场景（状态副本冗余），与训练场景的"计算状态无冗余"有本质差异——训练容错无法简单借用复制冗余，只能靠 checkpoint/重算，这是 scarHW 无法直接迁移到训练侧的结构性原因。

### 3.3 AVID 的"恢复复杂度"与 checkpoint 恢复的概念交叉

AVID（异步可验证信息分散）表面上属拜占庭容错的分布式存储协议，但其核心优化目标——**恢复（recovery）路径的复杂度**——与训练侧 checkpoint 恢复有值得记录的概念交叉。经典信息分散（如 Rabin 的 IDA）优化的是写入/读取复杂度，恢复常作为次要考量；AVID 的两维矩阵编码 + 定制分散算法，使节点恢复（recovery）不再需要全量重构数据，而是利用矩阵结构做局部解码。这与 checkpoint 领域的**部分专家检查点（MoC-System 的 PEC）**、**增量 checkpoint（BitSnap 的稀疏化）**共享同一思想：**恢复代价应与故障范围而非数据总量成正比**。

更广义地看，AVID 与 08-25 收录的 BSR（有界状态恢复，LMCache 生态）构成了"恢复语义"在存储/推理两端的样本——这再次印证 08-25 识别出的查询面盲区：现有三个关键词面（fault tolerance/checkpoint/GPU fault）覆盖不了 "recovery/restoration/dispersal" 语义，而这些语义恰恰是恢复类工作的常见表达。**方法论结论**：reliability-testing 专题的查询面应从"容错/检查点"扩展为"容错/检查点/恢复/分散"，或在计划层将 recent 全量扫描固化为标准步骤——今日 3 条边缘候选全部依赖后者才被发现，这就是补充通道连续两日产出增量而关键词面零新增的直接证据。

### 3.4 源2 移除决策的完整证据链：七数据点收官

arXiv 搜索页（arxiv.org/search）作为计划源2 的失效判定，今日完成第七个数据点：08-20 起连续七日多词 AND 查询（fault tolerance + checkpoint + AI training）全部返回 "no results"。从方法论角度，这个案例的教训不在于"某个源失效"，而在于**失效判定的证据积累节奏**：第一数据点（08-20）只能算"疑点"（可能查询写法问题）；第三数据点（08-22）可判"趋势"（多词 AND 在 arXiv 搜索页的 OR/AND 组合语义异常）；第五数据点（08-24）已够"定案"（并发验证了 API 通道同时段正常返回 16-25 条，排除 arXiv 整体故障）；第七数据点（今日）则是"收官"——按 08-25 建议，该源应从计划层正式移除，由 recent 全量扫描替代。**移除决策的关键支撑不是失败天数本身，而是对照实验**：同一查询在 API 通道（export.arxiv.org/api/query）正常返回，证明问题定位在搜索页前端（其多词查询的布尔语义实现缺陷），而非 arXiv 检索后端。这个"同查询双通道对照"的方法可推广为所有搜索类源的失效判定标准。

### 3.5 边缘增量与主线的关系：专题边界的稳态管理

连续两日（08-25/26）的产出结构呈现同一模式：主线零新增 + 边缘 1-3 条增量。这引发专题边界的管理问题：**reliability-testing 专题的收录边界应划在哪？** 当前收录原则（TRACKING.md 质量门槛）是"具体可靠性提升数据"优先，方向上以训练侧容错/checkpoint/GPU 可靠性为主线。今日 3 条边缘增量分别落在数据中心复制（scarHW）、分布式存储（AVID）、新型硬件（Trust-but-Verify）三个相邻域，共同点是"可靠性工程的具体量化数据"（零停机/恢复复杂度/扩展效率），但均非训练侧主线。**边界管理建议**：① 边缘增量维持"一行收录 + 方向标注"的轻量格式，不展开大段分析（避免专题漂移）；② 当某边缘域（如硬件化容错）连续出现 2+ 篇增量时，升级为独立子主题跟踪（在 TRACKING.md 追加子主题）；③ 边缘增量同时写入交叉引用，供 cluster-training/（容错↔训练效率）与 distributed-os/（集合通信容错）专题引用。今日 scarHW（硬件化容错）与 VCCL 的 primary-backup QP 形成第一个"硬件化容错"子主题的雏形，值得下个窗口观察是否形成聚集。

### 3.6 30 天窗口在册论文的量化基线回顾：平台期的"存量"视角

平台期判定关注的是"增量"，但存量在册论文的量化数据本身构成了该方向的基线谱系，值得在平台期做一次系统性回顾——这既是追踪的深度要求，也为后续新增论文提供对比锚点。从 08-22~26 收录的在册核心论文中提取关键量化指标：**恢复时延维度**，PHOENIX 在 512×A100/65B 规模实现热插拔恢复 <40s 且失败无关路径零开销（in-memory checkpoint 与计算重叠），Belayer 将 agentic RL 训练的 worker 恢复时延较引擎冷启动降低 42×（环境故障恢复 1.5-3.5×）；**吞吐/效率维度**，VCCL 以 primary-backup QP 容错机制换来 NCCL 对比下训练吞吐提升最高 5.28%，FT-HSDP 在 O(100K) GPU 将故障恢复 stall 从 10 分钟降至 3 分钟、有效训练时间从 44% 提升至 80%，SPARe 在 600K GPU 极端规模下较传统复制减少 time-to-train 40-50%（计算开销仅 2-3×）；**checkpoint 压缩维度**，BitSnap 实现 16× 无损压缩 + 2× 量化压缩，MoC-System 将 MoE checkpoint 开销降低 98.9%（PEC 部分专家检查点），R²CCL 网络故障转移开销 <1% 训练 / <3% 推理且较 AdapCC/DejaVu 提升 12.18×/47×。

将这些数据放在一起看，可以识别出该方向的**技术收敛特征**：① 容错方案的评估主轴已从"能否恢复"转向"恢复多快 + 失败无关路径多低开销"——PHOENIX 的零开销、R²CCL 的 <1%、SPARe 的 2-3× 常数开销都在量化这个权衡空间；② 故障语义正在细分——从节点故障（FT-HSDP/SPARe）到网络故障（R²CCL/VCCL）到环境故障（Belayer）到静默数据损坏 SDC（LLM-PRISM/SCOUT），每个故障类都有对应方案；③ checkpoint 与冗余两条技术路线的边界逐渐清晰——checkpoint 侧以压缩（BitSnap/MoC/Inshrinkerator）控制存储开销，冗余侧以堆叠（SPARe/FT-HSDP 副本）控制恢复时延，两者的联合优化（SPARe 的 redundancy+checkpoint 联合最小化 time-to-train）成为顶会（ICML/ASPLOS）认可的范式。这个存量基线为下周一公告批次的对比提供了现成参照系：任何新论文若不能在某维度上刷新上述量化记录（如恢复时延 <40s 或有效训练时间 >80%），则属渐进式改进而非范式突破。

### 3.7 硬件化容错趋势：今日三个边缘样本的汇聚证据

今日 3 条边缘增量看似分散（数据中心复制/分布式存储/新型硬件），但放到一起可以识别出一条跨域趋势：**容错机制正从软件层向硬件/设备层下沉**。scarHW 将共识协议固化进 FPGA smartNIC（POPUC 协同共识，Redis/ZK 吞吐提升 2 个数量级、少数副本失败零停机）；VCCL（在册）将 primary-backup QP 容错放进集合通信库的硬件路径（NIC 端口故障容忍，吞吐 +5.28%）；Trust-but-Verify 则观察 Cerebras WSE（880,000 处理器）的 best-effort 容错容忍（稀疏异步采样容忍硬件故障）——三个样本分别覆盖"smartNIC 承载容错""NIC 硬件路径容错""晶圆级处理器故障容忍"，共同指向**设备层容错能力成为系统可靠性的新前沿**。

从因果链看，这个趋势的驱动力是可量化的：① 训练/服务集群的故障主体已从"节点级崩溃"（软件可处理）转向"器件级劣化"（SDC/链路抖动/热漂移，软件难检测）——LLM-PRISM 的 7,664 次运行表征和 VCCL 的链路故障观察都是证据；② 软件层容错的时延粒度过粗（秒级检测 + 分钟级恢复），而硬件路径可提供微秒级观测（VCCL 的 O(μs) 窗口监控）与亚秒级转移（scarHW 零停机）；③ 可编程网络设备（smartNIC/DPU）的算力密度已足以承载共识/监控逻辑而不干扰数据路径。这个趋势对万卡集群的工程启示是：**容错设计应在系统架构早期把设备层能力（NIC QP 冗余、网内聚合、晶圆级冗余）纳入方案空间**，而非事后在软件栈上打补丁。需要标注的边界：三个样本均非训练侧 LLM 容错的直接证据（scarHW 是复制场景、Trust-but-Verify 是数字进化场景、VCCL 才是训练侧），因此该趋势目前是"相邻域汇聚"而非"训练侧确认"——若下个窗口在 cs.LG/cs.DC 出现训练侧硬件化容错论文（如网内 checkpoint 或 NIC 级梯度冗余），则趋势升级为训练侧主线信号。

### 3.8 查询面演进方法论：从关键词 AND 到语义扫描的通道迁移

08-25 与 08-26 连续两日，新增有效发现全部来自 recent 全量扫描（Lazy Pod/BSR/scarHW/AVID/Trust-but-Verify 共 5 条边缘增量），而关键词 AND 查询（源1/源3）连续两日零新增。这个对照实验给出了明确的通道迁移信号：**在方向平台期，关键词 AND 查询的边际产出趋近于零，recent 全量语义扫描成为唯一有效的发现通道**。其方法论解释是：平台期的论文供给以边缘/交叉主题为主（如硬件化容错、恢复语义、失败语义），这些论文的摘要用词分散（scarHW 用 "consensus"、AVID 用 "dispersal/recovery"、Trust-but-Verify 用 "best-effort"），任何固定关键词集合都无法覆盖；而全量扫描依赖的是人工语义判断，不受词面限制。**执行层结论**：① 下个窗口起，计划源顺序应调整为 recent 扫描优先、关键词 API 降为版本轮询辅助；② 关键词查询面仍需扩展（recovery/restoration/dispersal/consensus），用于部分自动化；③ 全量扫描的 token 成本需纳入预算（60 条×2 域 ≈ 100KB 原文），深度档预算内可承受，若转轻量档则需裁剪至标题级扫描。
