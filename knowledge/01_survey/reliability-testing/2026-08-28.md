## 0. 执行摘要

**核心判断**：本日窗口（arXiv 提交 2026-08-24 ~ 08-28）的可靠性信号从「训练侧容错」明显转向**「Agent 化负载的可靠性语义」**与**「故障预测的时间序列方法」**两个新战场。昨日（08-27）22 篇增量确立了「检查点单一支柱 → 多机制协同」的范式切换，今日的增量进一步暴露该范式的**边界盲区**：

1. **Agent 委托（delegation）正在击穿服务网格的三大可靠性原语**。Agent Mesh（2608.26225，08-26 提交）对生产 agentic 软件交付平台的 147 起事故做了逐案归因，量化证明 retry / timeout / error-rate circuit breaking 三个原语的假设全部失效：54 次连续成功工具调用的循环让错误率熔断器「看不见」、构造性恒定的 progress signal 保证误触发、21 个累积事件让正确幂等组件「不可获胜」。这不是工程瑕疵而是**语义层缺陷**——传统可靠性原语以「消息」为执行单元，而 Agent 的可靠性必须以「委托（delegation）」为单元。
2. **复制容错（replication）作为 checkpoint 的替代路线重新浮出**。FTHP-MPI（2504.09989）在无容错支持的原生 MPI 库上叠加复制，论证高故障率区间（MTBF < 1h）复制比 checkpoint/restart 更高效——这与昨日 SPARe「100k+ GPU 重启主导区」的判断在 HPC 侧形成独立印证。
3. **故障预测进入「多维时间序列深度学习」路线**。Time-Series Learning（2505.20705）用 GRU+attention 从性能指标序列预测故障，与 LLM-PRISM（RTL 特征化）、Deep4ge（训练轨迹 26 特征）、HeaRank（风险排序）共同构成故障预测方法谱系的第四极。

**对国内万卡集群的直接启示**：① Agentic RL / Agent 工作负载的可靠性测试必须引入**「委托级」故障注入与身份/证据充分性验证**，传统消息级熔断/重试矩阵不适用；② 高故障率区间（MTBF 小时级）应评估**复制容错**与 checkpoint 的组合策略，而不是无条件增加 checkpoint 频率；③ 故障预测应从「单点日志规则」升级为「多维指标时间序列 + 注意力聚焦」，但需警惕预测模型自身的训练/部署成本（下一节展开）。

## 1. 主线一：Agent 委托可靠性——服务网格原语的语义失效与「双充分性」判据

### 1.1 Agent Mesh：147 起生产事故的逐案归因

- **Agent Mesh: Reliability Primitives for Non-Idempotent Agent Delegation - Identity Adequacy and Evidence Adequacy**（https://arxiv.org/abs/2608.26225，2026-08-26 提交，Mazhar Shaikh 等）：对生产 agentic 软件交付平台做失效研究——**147 起编号事故 / 81 次运行**，每起事故记录实测成本、多数附 mutation proof（可复现失败的变异证明）。核心论点：服务网格（service mesh）的 retry / timeout / error-rate circuit breaking 三原语所依赖的假设在 Agent 场景**全部被违反**，并量化了后果：
  - **54 次连续成功工具调用的循环**——错误率熔断器按定义看不见（错误率 ≈ 0），但该循环是死循环，消耗无限预算；
  - **progress signal 构造性恒定**——信号与「是否真正进展」无关，保证第三次修复轮（repair round）误触发熔断，把一次运行从 6/6 组件成功打到 3 组件；
  - **21 个事件跨 6 次委托调用累积**——对「正确且幂等」的组件形成不可能赢的局面（unwinnable），因为每次重试的判定证据都被前序事件的残留污染；
  - **误路由故障唤醒 5 个组件**（实际仅 2 组件故障）——3 个旁观者（bystander）因此回退（regress）了正常工作的代码；
  - **12 起事故中 enforcement 层（熔断/超时执行器）阻止了正确工作**，最贵的一起浪费 **107 个 agent turns、0 次被接受的写入**。
  - 归因出一个跨切原因及其对偶：**identity adequacy（身份充分性）**——5 个子系统中身份无法区分（failed to discriminate）导致「自信的错误答案」，其中 2 个子系统独立推导出了纠正规则；**evidence adequacy（证据充分性）**——可靠性决策只能基于「能移动的（capable of moving）、可归因于其所测对象的（attributable to what it measures）、在相同条件下确定性的（deterministic under identical conditions）」的证据。据此推导出 **7 条可靠性原语**，其执行单元是**委托（delegation）**而非消息。

**分析一：为什么服务网格原语在 Agent 场景必然失效——从「可观测信号」到「语义信号」的断裂**。服务网格的 retry/timeout/circuit-breaking 建立在两个隐含假设上：① 故障可以被**错误率/延迟等传输级信号**表征；② 重试是**幂等安全**的（同一条消息重发不改变系统状态）。Agent 委托（delegation）同时打破两条：Agent 执行的是**有副作用的工具调用序列**（改文件、执行命令、写数据库），重放不满足幂等；而「进展」是**任务级语义属性**，与传输级信号之间不存在可计算映射——一个 54 次成功的工具循环在错误率上是「完美健康」，在语义上是「死锁」。Agent Mesh 的贡献在于把「双充分性」提升为判据：可靠性机制必须先问「我拿到的证据能否区分正常/异常」（identity adequacy），再问「这个证据是否可归因、可复现、能推动决策」（evidence adequacy）。这本质上把可靠性测试从「信号触发」升级为「**证据链验证**」——与昨日 Belayer 的「KV 前缀重建」共享同一个底层关切：Agent 场景下「状态」与「证据」必须能跨组件、跨轮次地**追踪归属**，否则任何自动恢复机制都会在错误的证据上做出自信的错误决策。对可靠性测试的启示：Agent 集群的故障注入矩阵应包含**「伪健康故障」（health-looking failures）**——进程不崩溃、错误率不升高、但任务语义停滞或侧向损坏，这类故障是传统探针的盲区。

**分析二：Agent Mesh 与昨日 Belayer 的互补——「环境状态」与「委托语义」构成 Agent 可靠性的两个正交维度**。昨日收录的 Belayer（2608.14635）解决「Agentic RL 训练中环境状态（容器文件系统/命令副作用）与 LLM 上下文的一致性恢复」，其单元是 worker 级状态；今日 Agent Mesh 解决「Agent 委托执行中决策证据的充分性」，其单元是委托级语义。两者拼出 Agent 可靠性测试的完整坐标系：**状态轴（训练侧：权重/KV/环境状态；服务侧：KV cache/会话状态）× 语义轴（委托是否进展/证据是否充分）**。目前工业界 Agent 平台（LangGraph/AutoGen 类编排器）的可靠性配置几乎全部停留在消息级重试与超时，两篇工作共同表明：这个层级已经不够——可靠性测试必须上移到「委托边界」，验证的是「一次委托的完成证明」而非「一条消息的送达确认」。这与软件工程中「恰好一次（exactly-once）语义」从消息队列向分布式事务的演进同构，但 Agent 场景的难点在于**「完成」本身需要语义判定**——这正是 mutation proof（变异证明）方法的价值：把「这次失败可复现吗」变成测试的硬性判据。

**Agent 可靠性原语与传统原语对比**：

| 维度 | 服务网格（消息级） | Agent Mesh（委托级） |
|:--|:--|:--|
| 执行单元 | 消息（message） | 委托（delegation） |
| 健康信号 | 错误率 / 延迟 / 超时 | 进展证据 / 身份区分度 |
| 重试语义 | 假设幂等 | 需证据充分性验证后才可重试 |
| 熔断触发 | 错误率阈值 | 证据不足或身份混淆 |
| 故障注入重点 | 崩溃 / 超时 / 抖动 | 伪健康循环 / 证据污染 / 误归因 |
| 恢复正确性判据 | 请求完成 | 委托的完成证明（含副作用一致性） |

**因果链推演：从「147 起事故」到「7 条原语」的方法学意义**。Agent Mesh 的价值不止于结论，更在于**方法学**：对每起事故记录「实测成本 + 可复现证明」，使「可靠性论断」从轶事升级为可审计证据——这直接呼应本库 08-17 沉淀的「故障注入测试必须定义恢复正确性判据」铁律。147 起事故中 12 起「enforcement 层阻止正确工作」的数据特别值得注意：它量化了**过度防御的代价**（最贵 107 turns + 0 写入），说明 Agent 可靠性测试必须同时度量「漏报代价（fault escaped）」与「误报代价（false trip）」，单纯提高熔断灵敏度不是答案——这与 08-27 分析中「故障不可预测 → 聚焦恢复速度而非预测概率」的判断一致：在语义不可观测的区间，任何启发式触发器都会在「看不见故障」与「误杀正常」之间摆动，真正稳健的设计是**让证据可判定**而非**让阈值更聪明**。

### 1.2 Agent 可靠性测试的落地路径（本组增量建议）

基于 Agent Mesh 的 7 原语与 Belayer 的状态建模，对 Agent 化工作负载（Agentic RL 训练 / Agent 服务）的可靠性测试提出三条可执行建议：

- **① 委托级故障注入矩阵**：在现有「崩溃/超时/网络分区」注入之外，增加「伪健康死循环」「进度信号恒定但语义停滞」「跨委托证据残留污染」三类语义故障；每类注入必须带 mutation proof（可复现）并记录「漏报/误报/正确处置」三分统计。
- **② 双充分性检查清单**：每次自动恢复动作（重试/熔断/回退）执行前，检查 identity adequacy（触发证据能否区分本次故障与正常变体？）与 evidence adequacy（证据是否可归因于被测对象、在相同条件下是否确定性复现？）——不满足则降级为人工介入，避免「自信的错误自动处置」。
- **③ 委托预算与完成证明**：为每次委托设置「证据预算」（如最大 turns × 每 turn 证据权重），并要求完成证明（含副作用一致性校验）才能关闭委托——对齐 Agent Mesh 的「107 turns + 0 写入」教训，防止无限预算消耗在不可获胜的委托上。

## 2. 主线二：复制容错 vs 检查点——FTHP-MPI 与高故障率区间的策略选择

### 2.1 FTHP-MPI：在无容错原生 MPI 上叠加复制

- **FTHP-MPI: Towards Providing Replication-based Fault Tolerance in a Fault-Intolerant Native MPI Library**（https://arxiv.org/abs/2504.09989，2025-04-14，Sarthak Joshi / Sathish Vadhiyar，IISc）：在**不支持容错的原生 MPI 库**上实现复制（replication）容错——动机：exascale 时代故障率上升，checkpoint/restart 需要以更高频率建检查点导致不可持续；复制（进程冗余）可通过「丢弃故障进程、用副本继续」实现快速恢复。创新点：① 不修改原生 MPI 库即可获得容错，保留针对平台调优的高效通信协议；② 实现副本间的高效并行通信技术；③ 处理 checkpoint + 部分复制（partial replication）集成的独特挑战。实验：HPCG / PIC / CloverLeaf 三个应用，**故障间隔 < 1 小时的大规模系统上复制比 checkpoint 方案效率更高**；无故障时复制开销可忽略。

**分析三：复制与 checkpoint 的经济学——为什么「高故障率区间」是复制的甜区**。设 MTBF = τ、checkpoint 周期 = T、checkpoint 成本 = C_cp、重启成本 = C_restart、复制冗余度 = r。checkpoint/restart 的总开销随 1/τ 增长（故障越频繁开销越大），而复制的开销主要是**常驻冗余成本**（r× 资源占用），与 τ 弱相关。因此存在阈值 τ*：当 MTBF 低于 τ*（故障足够频繁），复制从「昂贵的保险」变成「合算的投资」。FTHP-MPI 给出 τ* ≈ 1h 的实证判断（三个 HPC 应用），而昨日 SPARe 从训练侧给出同构结论（100k+ GPU 时「重启主导区」出现，冗余分片 2~3× 恒定成本优于线性复制）——两条独立路线（HPC 科学计算 / LLM 训练）收敛到同一经济模型：**「冗余 vs 重算」的切换阈值由「故障率 × 重启成本 / 冗余成本」决定**。对万卡集群的启示：当节点级 MTBF 降到小时级（万卡规模下 GPU 故障是统计必然），纯 checkpoint 策略的资源浪费（高频建检查点 + 频繁重启）会超过热备/复制的常驻成本——可靠性预算应从「存储带宽」转向「冗余度规划」，这与 08-27 分析一「可靠性设计的本质约束从存储带宽转向并行度冗余成本」完全一致。FTHP-MPI 的「原生 MPI 不修改」特性对国产通信栈（HCCL/ACCL）同样有参考价值：容错不应绑定在重写通信库上，而应作为**透明叠加层**提供。

**复制容错三方案对比（本组历史 × 今日增量）**：

| 方案 | 领域 | 复制方式 | 关键指标 | 与 checkpoint 关系 | 收录状态 |
|:--|:--|:--|:--|:--|:--|
| FTHP-MPI（2504.09989） | HPC 科学计算 | MPI 进程复制（透明叠加） | MTBF<1h 时优于 C/R；无故障开销可忽略 | 复制+checkpoint 混合 | ✅ 今日新增 |
| SPARe*（2603.00357） | LLM 训练 100k+ GPU | 堆叠冗余分片 + 自适应重排 | 2~3× 恒定开销；time-to-train -40~50% | 冗余与 checkpoint 联合优化 | 已收录（08-27） |
| PHOENIX*（2607.01646） | LLM 训练 | in-memory checkpoint + 热替换节点 | 零故障外开销；恢复 <40s | 空间冗余替代持久化 | 已收录（08-27） |

（* 昨日已收录，此处对比引用）

**分析四：复制容错的「正确性语义」是推广的隐性障碍**。复制方案看似简单（丢故障进程、用副本继续），但存在两个深层问题：① **副本一致性**——非确定性操作（随机数、时间戳、浮点约减顺序）会导致副本间状态漂移，必须约束为确定性重放（deterministic replay）或同步屏障，否则「用副本继续」会静默产生与无故障不同的轨迹；② **复制度 vs 故障相关性**——机架级故障（电源/网络）会同时杀死主副本与备份，复制对**相关故障**（correlated failures）无效，必须与跨故障域放置（rack-aware placement）配合。FTHP-MPI 未在摘要中展开这两点，但这是评估复制方案时必须补上的测试维度：复制容错的测试矩阵应包含「非确定性注入（检验副本发散）」「机架级故障注入（检验跨域放置）」「故障风暴（检验恢复风暴与级联）」三类用例。这也解释了为什么复制在 LLM 训练侧（SPARe）比在通用计算侧走得更快——训练前向传播是确定性的（同权重同数据同结果），副本天然一致，复制成本可控；而通用 HPC/Agent 负载的非确定性让复制的正确性成本陡增。

## 3. 主线三：故障预测的时间序列深度学习——方法谱系的第四极

### 3.1 GRU+Attention 的预测路线

- **Time-Series Learning for Proactive Fault Prediction in Distributed Systems with Deep Neural Structures**（https://arxiv.org/abs/2505.20705，2025-05-27，Yang Wang 等）：面向分布式系统故障预测与延迟响应的智能预测方法——输入多维性能指标序列；**GRU 建模系统状态随时间演化**；**attention 机制增强关键时间段**（聚焦异常前兆段）；前馈网络做最终分类，输出故障早期预警。实验：真实大规模云系统数据，Accuracy / F1-Score / AUC 优于主流时间序列模型，消融实验验证各组件贡献，loss 收敛曲线证明训练稳定性。

**分析五：故障预测方法谱系——四极并立与各自的前提假设**。将本库已收录的故障预测工作放在一起，可以看清四条路线的适用边界：

| 路线 | 代表工作 | 输入信号 | 输出 | 前提假设 | 局限 |
|:--|:--|:--|:--|:--|:--|
| RTL 特征化 | LLM-PRISM*（2604.10390） | RTL 级故障模拟 | 故障→训练影响的映射 | 故障模型可知、可模拟 | 不预测「何时」，只回答「多危险」 |
| 生产遥测排序 | HeaRank*（2607.15115） | 生产监控指标 | 节点风险排序 | 风险可排序 | 故障时间不可预测（当日已证） |
| 训练轨迹监控 | Deep4ge*（2607.12868） | 权重/梯度/激活 26 特征 | 故障检测/诊断/早期预测 | 故障在训练轨迹留痕 | 限 DNN 训练场景 |
| 时序指标预测 | Time-Series（2505.20705） | 多维性能指标序列 | 故障早期预警分类 | 故障前有指标前兆 | 泛化依赖数据/特征选择 |

（* 已收录，此处对比引用）

**分析六：时间序列预测的「前兆可观测性」假设与工业落地的三重门槛**。GRU+attention 的路线成立的前提是「故障前存在可学习的指标前兆（precursor）」——这个假设对**慢变故障**（内存泄漏、散热退化、带宽渐衰）成立，对**快变故障**（瞬时电源跌落、突发链路中断）不成立（前兆窗口小于采样周期）。这是所有预测路线的共性天花板，也解释了为什么昨日 HeaRank 得出结论「故障时间不可预测 → 聚焦恢复速度」——预测与恢复不是二选一，而是**按故障的时间常数分层**：慢故障（分钟~小时级前兆）用时序预测提前处置；快故障（秒级以下）只能靠容错/恢复兜底。工业落地还有三重门槛：① **标注数据**——故障样本天然稀缺（类不平衡），需要主动故障注入补充；② **特征选择**——多维指标的相关性与冗余（GRU 的消融实验正是回答哪些维贡献）；③ **预测决策闭环**——预警后的处置动作（隔离/降频/迁移）必须与预测置信度联动，否则「狼来了」效应会削弱运维信任。对万卡集群的建议：把时序预测作为**慢故障的早期预警层**（与 VCCL 的 O(μs) 瞬态监测互补——一个管分钟级趋势、一个管微秒级瞬态），两层时间尺度各司其职，避免在单一时间粒度上过度投资。

**分析七：从「故障预测」到「可靠性测试」——预测模型的测试本身就是可靠性测试的一部分**。一个值得本组跟踪的元问题：**预测模型自身的可靠性如何测试**？GRU+attention 模型可能产生误报（打断正常训练）或漏报（错过故障），其行为随训练数据分布漂移而变化。Agent Mesh 的「证据充分性」判据在此同样适用：预测模型的告警必须「可归因」（能说明是哪个指标窗口触发的）、「可复现」（同输入同输出）、「可审计」（置信度可校准）——否则运维无法判断该信还是该忽略。建议将「预测器健康度」纳入集群可靠性指标体系：监控预测模型的在线校准误差（calibration error）与误报率，作为二级可靠性探针。

**5.1 Serving 容错三件套的增量视角（不重复技术细节，仅补今日完整摘要带来的新视角）**：

- **Concordia**（https://arxiv.org/abs/2606.23521，交叉引用 tech 07-30 / 本组 08-20）：其完整摘要揭示了此前收录未强调的架构主张——**容错需要 GPU-resident 执行上下文**：checkpoint hooks 必须在设备同步点运行、观察框架实际执行的二进制内核（PTX/SASS 级插桩）、恢复路径不经过 host CPU 关键路径；JIT 编译专门的 delta-checkpoint handler（KV-block scanner / adapter-page scanner / recovery applier）并热插拔进持久内核的算子表；lock-free ring buffer 承载 compute/checkpoint/append-log/recovery 任务，脏页检测→delta 暂存→追加日志到 CXL 内存或 host DRAM。
- **增量分析**：Concordia / LUMEN / GhostServe 三篇独立工作（2026-03~06 提交）在 08-20 已被并置分析，今日补一个此前未点明的视角——**三篇对「恢复时谁在关键路径上」给出三个不同答案**：GhostServe 把 parity 放 host 内存（恢复时 host 参与校验、重建 KV）；LUMEN 把决策放调度器（协调层决定谁恢复、谁承接，GPU worker 专注 reload）；Concordia 把执行放 GPU 持久内核（host CPU 完全退出关键路径）。这个差异本质上是**「恢复控制的放置（placement of recovery control）」设计空间**的三次采样：host 侧（校验/纠删码）、控制面侧（调度协调）、设备侧（GPU-resident）。对可靠性测试的含义：恢复路径的测试必须覆盖「控制面在哪个域执行」——设备侧恢复最难测试（需持久内核插桩工具链），但也最彻底（不依赖 host 可用性）。国产推理栈（vLLM 系）目前几乎全部是 host/控制面侧恢复，GPU-resident 恢复是值得跟踪的下一代方向。
