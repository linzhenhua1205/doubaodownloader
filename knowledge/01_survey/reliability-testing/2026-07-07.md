## 1️⃣ 🚨 SDCHunter + AEGIS：大规模 LLM 训练中的 SDC 检测双引擎

> **来源**: OSDI'26 · Training Reliability and Silent Errors session
> **SDCHunter**: Wenxin Zheng 等 (上海交通大学 + ByteDance Seed)
> **AEGIS**: Kinman Lei 等 (清华大学 + ByteDance)

### SDCHunter — 生产级 SDC 缺陷 GPU 诊断

**方法**:
SDCHunter 针对 LLM 训练中的 Silent Data Corruption (SDC) 问题。核心发现是**工业界通用的合成微基准测试会遗漏超过 60% 的缺陷设备**。研究团队从生产集群收集了 23 块 SDC 缺陷 GPU，进行了全面表征。三个关键洞察：

1. **SDC 不仅出现在新硬件上**——老化也会导致 SDC（非早期失效率模型）
2. **SDC 高度数据依赖且单元特定**——通过通用压力测试的设备，在特定训练输入数据下会失效
3. **标准 ECC 和热保护无法捕获这些逻辑级位翻转**

解决方案 SDCHunter 采用**精确训练负载执行回放**来检测 SDC，而非依赖通用基准测试。

**实验数据**：

| 指标 | 数值 |
|:-----|:----:|
| 生产 SDC 事件数 | **40 起**成功缓解 |
| 通用基准测试遗漏率 | **>60%** 缺陷设备 |
| 缺陷 GPU 样本量 | 23 块（实际生产环境） |
| 部署环境 | ByteDance 大规模训练集群 |
| SDC 根源定位 | 逻辑级位翻转，ECC/热保护不捕获 |

### AEGIS — 在线 SDC 检测（3.5×10⁷ GPU小时）

**方法**:
AEGIS 提出一个两阶段 **cSensor-cVerifier** 抽象，将 SDC 检测解耦为轻量级腐败感知（sensing）和确定性腐败验证（verification）。基于此抽象，AEGIS 协同设计了新的检测技术，整合 LLM 训练的**固有特征**与 GPU 特性，实现实用在线 SDC 检测。

**实验数据**：

| 指标 | 数值 |
|:-----|:----:|
| 部署规模 | **35,000,000 GPU-hours** |
| 发现真实 SDC 事件 | **18 起** |
| 发现缺陷 GPU | **13 块** |
| 性能开销 | 仅 **0.86%** |
| 检测策略 | cSensor(轻量感知) → cVerifier(确定性验证) |

**相关性 ⭐⭐⭐⭐⭐**：
SDCHunter + AEGIS 构成生产 SDC 检测的完整组合——一个解决**「收到异常后如何精确定位故障 GPU」**（诊断侧），另一个解决**「如何在无异常信号时主动发现 SDC」**（检测侧）。二者来自同一家公司的产学合作（ByteDance Seed），展示了业界在大规模 LLM 训练可靠性上的最新实践。

## 2️⃣ 🛡️ OpGuard: 位对齐精确调试生产 LLM 训练

> **来源**: OSDI'26 · Training Reliability and Silent Errors session
> **作者**: Ziming Zhou 等 (University of Michigan + ByteDance Seed)

**方法**:
大规模 LLM 训练在快速演进的软件栈上运行数周。Bug 或硬件故障会**静默破坏计算**，等到明显时才被发现——「大海捞针般的调试」。开发者通常用另一个训练运行对比 loss/gradient norm，但这些聚合信号在数百万操作中被稀释，对定位根因帮助甚微。

OpGuard 引入**位对齐（bitwise alignment）**作为正确性神谕（oracle）和调试原语。关键思想：
1. 发现跨异构训练栈的**语义稳定算子边界**
2. 对这些操作包裹轻量**指纹生成**
3. 通过**调度容忍映射器**计算两次执行产生位级一致张量的最长前缀
4. **第一个不匹配点**成为调试的支点

通过精细控制良性非确定性，OpGuard 使第一个不匹配点成为错误的**强证据**。

**实验数据**：

| 指标 | 数值 |
|:-----|:----:|
| 发现生产问题 | **20+ 起** |
| 问题类型 | 精微 kernel 竞态 + SDC（被现有检查遗漏） |
| 调试时间缩减 | **从天到分钟** |
| 覆盖范围 | 预训练 + 后训练 |
| 部署环境 | ByteDance 生产集群 |
| 核心技术 | 位对齐指纹 + 调度容忍映射器 |

**相关性 ⭐⭐⭐⭐⭐**：
OpGuard 解决了 LLM 训练调试中一个长期存在的根本问题——除了数值偏差，如何真正证明「这次训练跑错了」。位对齐方法将调试范式从「看 loss 曲线是否一致」（模糊信号）升级为「第一个 bit 差异在哪里」（精确定位）。与 SDCHunter 的诊断互补——SDCHunter 回答「哪个 GPU 坏了」，OpGuard 回答「哪个算子/哪一步出了第一个错误」。

## 3️⃣ 🚂 TrainMover: 弹性恢复运行时—20秒搞定 GPU 中断恢复

> **来源**: OSDI'26 · Serverless Plus Resilience session (Wednesday)
> **作者**: ChonLam Lao 等 (Harvard University + Alibaba Group)

**方法**:
大规模 ML 训练作业频繁被硬件/软件异常、故障和管理事件中断。现有方案（检查点重启、运行时重配置）存在长停机时间和性能降级。

TrainMover 利用**弹性备用机器**处理中断，实现三个目标：
1. **最小停机时间**：接管时间约 20 秒
2. **零内存开销**：无额外内存占用
3. **通用备用设计**：任何角色故障均可恢复

三项关键技术：
- **两阶段、基于增量的通信组建立**（delta-based communication group setup）
- **无通信沙箱预热**（communication-free sandboxed warmup）
- **通用备用设计**（general standby design）

**实验数据**：

| 指标 | 数值 |
|:-----|:----:|
| 测试规模 | **1024 GPU** |
| 中断恢复时间 | **~20 秒** |
| 间歇中断处理 | 恒定 ~20 秒 |
| GPU 小时节省（对比最优方案） | **55%** |
| 64K-GPU 周节省 | **140万 GPU-hours/周** |
| 内存开销 | **零** |
| 恢复角色 | 任意角色（通用备用设计） |

**相关性 ⭐⭐⭐⭐⭐**：
TrainMover 是 OSDI'26 上 LLM 训练中断恢复的里程碑式突破。20 秒的恢复时间比 DeadPool (<40 秒) 更快，且不需要特殊的 off-critical-path 内存复制。两者互补：
- **DeadPool**：通过内存检查点实现**热插拔**
- **TrainMover**：通过弹性备用机器实现**快速接管**

在更大规模 (64K GPU) 下，TrainMover 的周节省 140 万 GPU 小时是具说服力的生产级收益。

**与知识库已有条目的关系**：
- 补充 [DeadPool](./2026-07-06.md)（零开销检查点）→ TrainMover 采用不同的弹性备用路线，恢复更快（20s vs 40s）
- 补充 [MeCeFO](./2026-06-07.md)（算法级容错）→ TrainMover 是系统级弹性方案
- 补充 [ReCycle](./2026-06-29.md)（pipeline 适应）→ TrainMover 是通用弹性运行时框架
