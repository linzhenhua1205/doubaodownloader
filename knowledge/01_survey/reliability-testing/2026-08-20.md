## 二、核心发现（列表项）

### 2.1 训练侧容错（本窗口新增）

- **Belayer: Efficient Fault Tolerance for LLM Agentic RL Training**（arXiv 2608.14635，2026-08-18，https://arxiv.org/abs/2608.14635）：首个面向 **LLM Agentic RL 训练**的容错系统。Agentic RL 将 GPU 密集的 rollout 引擎与有状态环境容器耦合（文件编辑/命令执行/依赖安装等副作用），单条轨迹跨多轮生成与环境交互，组件故障会丢弃已完成工作或让模型面对与上下文不一致的环境状态。Belayer 双管齐下：**scoped worker-local rollout 故障**采用 shadow worker + selective GPU-state reuse 协议（通过 owner 与 GPU 健康检查后保留独立持有的权重和原始 KV-arena 分配，重初始化 worker-local 状态，从日志 token 前缀重建请求级 KV）；**环境故障**采用 full checkpoint + full restore 联合捕获/恢复容器文件系统与运行时状态，并协调恢复后的环境与 LLM 上下文保持前缀一致性。自适应策略在预测间隔足够长时，将全状态 checkpoint 与 LLM 推理的自然 bubble 重叠。量化结果：无故障运行开销低，worker 恢复时间比完整引擎冷启动**快最多 42 倍**，环境故障恢复**快 1.5~3.5 倍**。

- **PHOENIX: Resilient LLM Training with Hot-Swapping via Zero-Overhead Checkpoint**（arXiv 2607.01646，2026-07-06，https://arxiv.org/abs/2607.01646）：同时优化两个通常互斥的目标——无故障运行开销与恢复延迟，**零开销 checkpoint + 40 秒内热插拔恢复**。核心两招：① off-critical-path 内存 checkpoint 机制做空间冗余（与计算重叠，误差路径零开销）；② communicator reconstruction 协议，在运行时用备用节点替换故障节点而**不终止整个 job**。512 A100 GPU、65B 参数规模验证：错误路径零 checkpoint 开销，永久节点故障下热插拔恢复 <40 秒。

- **AuroraRL**（arXiv 2602.11456v2，2026-08-04 更新，https://arxiv.org/abs/2602.11456）：面向**弱网/跨地域松散 GPU 集群**的 RL 训练系统，核心观察是 RL 微调每步更新高度稀疏（仅 ~1% 参数元素变化）。将每步表示为 **sparse delta checkpoint**，delta 提取与多流传输流水线化，传输与 rollout 生成重叠，并用 throughput/bandwidth 感知调度 + **lease-based fault tolerance** 协调异构 worker。Qwen3 4B-14B、最多 4 地域：每步权重传输缩减 **79 倍**（Qwen3-8B），吞吐比 dense-broadcast 基线高 **1.3~9.5 倍**，端到端训练距理想 RDMA 单数据中心基线仅差 8.91%，可比吞吐下 tokens/美元高 1.21~1.59 倍。容错语义是"透明容忍常见故障且不损精度"。

- **Concordia: JIT-Compiled Persistent-Kernel Checkpointing for Fault-Tolerant LLM Inference**（arXiv 2606.23521，2026-06-22，https://arxiv.org/abs/2606.23521）：论证 LLM 推理容错需要 **GPU-resident 执行上下文**——checkpoint 钩子必须在设备同步点运行、观察框架/库实际执行的二进制 kernel、且恢复不把 host CPU 放在关键路径。Concordia 用 device-resident persistent kernel 作为基底，拦截 GPU 模块加载，支持 PTX/SASS 级插桩，在框架代码与库边界之下插入 checkpoint/pause 钩子；对每个注册的 LLM 状态区域 JIT 编译专用 delta-checkpoint handler（KV-block scanner、adapter-page scanner、recovery applier 等）热插拔进 persistent kernel 的 operator 表。持久 kernel 消费 lock-free ring buffer 的计算/checkpoint/append-log/恢复任务，同一个常驻执行器触发脏页检测、stage delta、把已提交记录追加到 CXL 内存或 host DRAM 的 CPU 可见日志。价值：长运行 LLM agent 的 KV cache/调度器/通信状态不再因单 GPU 故障丢失数分钟到数小时的工作。

- **LUMEN: Coordinated Failure Recovery for Distributed LLM Serving**（arXiv 2606.17787，2026-06-16，https://arxiv.org/abs/2606.17787）：把分布式 LLM serving 的故障恢复视为**负载感知的协调问题**，覆盖三个决策点：① 故障前 checkpoint 放置；② 故障时中断请求的分布；③ 模型 reload 期间的服务容量恢复。动机：worker 故障时集群同时失去故障 worker 的 GPU 驻留 KV cache 与服务容量，幸存 worker 吸收重定向流量并从零重跑中断请求；现有方案（从头重跑 / 从固定邻居 worker 的 checkpoint 恢复 KV）都不考虑当前集群负载，且 reload 期间恢复 worker 空转。LUMEN 用原型实验 + 大规模仿真验证 serving 与恢复时间的显著改善。作者团队与 TierCheck/ReCoVer 有重合（Patrick P. C. Lee 等，港中文/香港城市大学系），反映一个成体系的容错研究方向。

- **TierCheck: Tiered Checkpointing for Fault Tolerance in LLM Training**（arXiv 2605.17821，2026-05-18，https://arxiv.org/abs/2605.17821）：针对"异构故障谱系"（从常见 GPU 崩溃到灾难性集群级中断）提出**集群感知的分层 checkpoint**：本地/peer 内存中维护轻量差分 checkpoint 支持快速局部恢复，同时异步把重量级 base checkpoint 迁移到远程持久存储；三层间严格全局一致且不 stall 训练。40B 参数规模评估：训练开销低，端到端 checkpoint 时间 <10 秒，支持高频 checkpoint，在"低开销持久化"与"快速恢复"之间取得平衡。设计哲学与 MoC-System（ASPLOS 2025）的"内存快照 + 持久化两级异步"一脉相承，但按故障频率分层而非按模型结构分层。

- **ReCoVer: Resilient LLM Pre-Training via Fault-Tolerant Collective and Versatile Workload**（arXiv 2605.11215，2026-05-22，https://arxiv.org/abs/2605.11215）：坚持单一不变量——**每个迭代 microbatch 数量恒定**，保证每迭代梯度与无故障运行随机等价。三层解耦协议：① fault-tolerant collectives 隔离故障跨副本传播；② in-step 细粒度恢复保留迭代内进度、防梯度损坏；③ versatile-workload 策略把 microbatch 配额动态再分配给幸存者。与 3D parallelism 和 HSDP 直接集成（drop-in substrate），512 GPU 端到端预训练、运行中累计丢失 256 GPU：成功保持与无故障参考一致的训练轨迹；对比 checkpoint-and-restart 基线，连续故障后有效吞吐**高 2.23 倍**，234 GPU-hours 内多处理 **74.9% tokens**，且优势随训练延长而扩大。

### 2.2 通信层容错（生产级）

- **FT-HSDP: Training LLMs with Fault Tolerant HSDP on 100,000 GPUs**（arXiv 2602.00277，2026-01-30，https://arxiv.org/abs/2602.00277）：**Meta 在 O(100K) GPU 上的生产经验**——同步训练要求所有 GPU 同时健康，导致频繁故障 + 长恢复下的低效率。FT-HSDP 以**数据并行副本为容错单元**：故障时仅将含故障 GPU/服务器的单个 DP 副本下线重启，其他副本继续训练。两项关键机制：① **FTAR（Fault Tolerant All Reduce）**协议做跨副本梯度交换——CPU 驱动添加/移除参与者的复杂控制逻辑，GPU 只做数据传输以获得最佳性能；② **非阻塞 catch-up 协议**，让恢复中的副本以最小 stall 重新加入训练。O(100K) GPU 下与全同步训练相比，故障恢复 stall 从 **10 分钟降至 3 分钟**，有效训练时间从 **44% 提升到 80%**，且异步恢复不带来模型精度损失。这是本窗口最接近"万卡集群"场景的第一手工业界数据（作者名单几乎覆盖 Meta 训练基础设施团队）。

- **VCCL: An Efficient, Reliable and Observable Collective Communication Library**（arXiv 2510.00991v2，2026-06-01 更新，https://arxiv.org/abs/2510.00991）：Infrawaves/上海 AI 创新机构/清华/智谱/联通研究院联合的**开源生产级集合通信库**，针对 NCCL 在生产中的三个短板：① SM 竞争（计算与通信抢 SM）——把节点内数据传输与流依赖约束移出 SM，改由 CPU 线程 + GPU copy engine 承担；② 链路故障下昂贵的重启成本——引入 **primary-backup QP 机制**容忍频繁 NIC 端口故障；③ 瞬态集合通信异常观测不足——设计 **window-based monitor** 在 O(μs) 级观测网络异常。与 NCCL 相比吞吐最高提升 **5.28%**，通过运行时容错与细粒度监控减少大量 GPU 资源浪费。已开源并在生产集群部署数月。对万卡集群的价值：集合通信库层面的故障切换比作业级重启代价低几个数量级。

- **R²CCL: Reliable and Resilient Collective Communication Library for LLM Training and Serving**（arXiv 2512.25059，2025-12-31，https://arxiv.org/abs/2512.25059）：量化了网络故障的真实代价——**网络故障浪费 10~15% GPU 小时**（恢复缓慢所致），常见网络错误/链路抖动触发超时，常导致整个 job 终止、训练 checkpoint 回滚或推理请求重处理。R²CCL 利用多 NIC 硬件做无损低开销故障切换：快速连接迁移、带宽感知负载再分配、弹性集合算法。8-GPU H100 IB 服务器 + 大规模 ML 仿真（数百 GPU 多样故障模式）验证：对 NIC 故障高度鲁棒，训练开销 <1%、推理开销 <3%，优于基线 AdapCC 12.18 倍、DejaVu 47 倍。

### 2.4 补充观测（本窗口 API 全量结果中的相关性条目）

- **Grounded autonomous research**（arXiv 2607.02329，2026-07-02，https://arxiv.org/abs/2607.02329）：容错 LLM 科研流水线（ICML 2026 AI for Science Workshop）——从 11,083 篇凝聚态物理 arXiv 论文端到端到可发表稿件，跨 47 个 fresh-context session、6 阶段、2,162 次文献咨询。其容错观是 **fresh-context isolation + distributed grounding + adversarial review** 的多重冗余：单 session 会漏，冗余结构兜住。对训练系统容错的隐喻价值在于"上下文隔离即故障隔离"——与 Belayer 的 shadow worker 隔离哲学同构。
- **LLMTailor**（arXiv 2602.22158，PDSW'25，https://arxiv.org/abs/2602.22158）：**层间选择性 checkpoint**——观察 LLM 各层更新高度非均匀（部分层稳定甚至不变），只对显著更新的层做 checkpoint，从不同 checkpoint 过滤/组装成复合 checkpoint。Llama3.1-8B 体积减 4.3 倍、Qwen2.5-7B checkpoint 时间快 2.8 倍。与 AuroraRL"更新稀疏"洞察互为印证，共同支撑"信息熵感知 checkpoint"趋势。
- **BitSnap**（arXiv 2511.12376，2025-11-18，https://arxiv.org/abs/2511.12376）：checkpoint **稀疏化 + 量化**组合——bitmask 稀疏化 16 倍压缩不损精度，cluster-based 量化 2 倍压缩微损精度；对现有 lossy/lossless 压缩技术做了系统分析。表明 checkpoint 体积优化已从"存储层压缩"进入"训练语义层裁剪"。
- **MoFa**（arXiv 2511.09837，2025-11-13，https://arxiv.org/abs/2511.09837）：预训练性能建模框架首次把**容错开销（checkpoint 恢复）纳入成本模型**，基于历史集群可靠性数据建模故障，用于预训练系统设计与瓶颈探索——容错从"运行时特性"变成"规划期参数"，是 TCO 建模视角的进步。

### 2.3 本窗口外的关键演进（支撑深度分析）

- **GhostServe**（arXiv 2605.00831，MLSys 2026，https://arxiv.org/abs/2605.00831）：用**纠删码（erasure coding）**在 host 内存中生成/存储 KV cache 的 parity shards，设备故障时快速重建丢失的 KV cache，免去全量重算或状态复制。checkpoint 延迟降低最多 2.7 倍、恢复延迟 2.1 倍。
- **SPARe**（arXiv 2603.00357v3，ICML 2026，https://arxiv.org/abs/2603.00357）：面向 **100K+ GPU 重启主导时代**，跨并行组堆叠冗余数据分片 + 自适应重排序，把节点故障在梯度同步阶段屏蔽。计算开销恒定 2~3 倍（传统复制在高冗余下线性膨胀），600K GPU 极端规模下 time-to-train 比传统复制**减少 40~50%**。给出可耐故障数与计算开销的闭式表达式，SimGrid 离散事件仿真验证，联合优化冗余与 checkpoint 最小化训练总时长。
- **ATTNChecker**（arXiv 2410.11720v3，https://arxiv.org/abs/2410.11720）：首个面向 attention 的 **ABFT（算法级容错）**技术，基于 INF/NaN/近 INF 的故障传播模式，平均 7% 训练开销内检测并纠正所有极端错误，比 checkpoint/restore 恢复开销低最多 **49 倍**——证明"算法级在线容错"可替代部分 checkpoint 频率。
- **MoC-System**（arXiv 2408.04307v3，ASPLOS 2025，https://arxiv.org/abs/2408.04307）：MoE 的 Partial Experts Checkpointing（PEC）——只存选定的专家子集，把 MoE checkpoint 降到稠密模型量级；两级 checkpoint 管理（内存快照异步 + 持久化），Megatron-DeepSpeed 上单次 checkpoint 开销降 **98.9%**。
- **Lazarus**（arXiv 2407.04656v2，https://arxiv.org/abs/2407.04656）：MoE 弹性训练——专家副本自适应分配 + 可证明最优的专家放置算法最大化恢复概率，spot 实例轨迹上比现有 MoE 系统快最多 5.7 倍（云上 spot 抢占本质是高频故障，弹性即容错）。
- **TRANSOM**（arXiv 2310.10046v3，https://arxiv.org/abs/2310.10046）：全链路容错三件套（TOL 任务生命周期 + TEE 多维异常检测 + TCE 异步 checkpoint），GPT3-175B 预训练时间减 28%、checkpoint 存取性能提升 20 倍——异常检测与容错一体化的早期范本。

## 三、深度分析

### 分析一：容错范式迁移——从 checkpoint-restart 到"在线恢复"，再到"热插拔 + 分层冗余"

把 2025~2026 年的容错论文按恢复机制排序，可以清晰看到一条**因果链驱动的范式迁移**：集群规模每上一个数量级，checkpoint-restart 的边际成本就恶化一个数量级，于是研究重心逐级下移。

**第一代：checkpoint-restart 的优化**。TRANSOM（2023）和 MoC-System（ASPLOS 2025）的出发点都是"checkpoint 必然发生，如何让它更快"——异步化、两级化、按结构裁剪（MoE 只存部分专家）。其隐含假设是：**故障是低频事件，恢复 = 回滚 + 重算**。这一代把单次 checkpoint 的开销从分钟级压到秒级（TierCheck <10s、MoC 降 98.9%），但在 100K GPU 规模下，即便单次 checkpoint 只要几秒，MTBF 下降导致的重启频率使"重启总时间"仍占 wall-clock 的 56%（FT-HSDP 数据：全同步 100K GPU 有效训练时间仅 44%）。**因果链的断点在于：优化单次成本不能改变"恢复时必须全体停摆"的结构性缺陷。**

**第二代：并行度级别的在线恢复**。ReCoVer（2026-05）与 FT-HSDP（2026-01）的共性洞察是：**故障的影响范围应该被限制在故障单元内部**。FT-HSDP 把容错单元定义为 DP 副本——故障只下线一个副本，其余继续训练（有效训练时间 44%→80%）；ReCoVer 更进一步，通过恒定 microbatch 不变量保证恢复后的梯度与无故障运行随机等价（256/512 GPU 丢失后仍保持训练轨迹）。这代的代价是显式的：要么需要冗余副本（FT-HSDP 依赖 DP 规模），要么需要细粒度状态协议（ReCoVer 的 in-step 恢复复杂度随并行度上升）。**其因果逻辑是：把"全体同步"的恢复模型改成"局部异步 + 全局一致性协议"，用控制面复杂度换取训练面可用性。**

**第三代：热插拔 + 空间冗余，目标"零开销 + 秒级恢复"**。PHOENIX（2026-07）把两条线合流：off-critical-path 内存 checkpoint 做空间冗余（误差路径零开销），communicator reconstruction 协议在运行时换入备用节点（<40 秒恢复、不终止 job）。Belayer（2026-08）把同一思想推进到 Agentic RL：shadow worker 保留权重与 KV-arena 分配，恢复比冷启动快 42 倍。SPARe（ICML 2026）则给出理论边界：冗余分片 + 自适应重排序把计算开销恒定在 2~3 倍，600K GPU 时 time-to-train 减 40~50%。**这代的关键转变是：容错从"事故处理"变成"架构属性"——冗余不是事后补救，而是训练拓扑设计的一部分。** 对万卡集群的直接含义：未来集群规划必须把"备用节点池 + 内存级冗余预算"当作第一公民资源来设计，而非事后扩容。

### 分析二：通信层容错三方案对比——FTAR / VCCL / R²CCL 的原理分野

网络/通信故障是万卡集群的第一大故障源（R²CCL 量化：网络故障浪费 10~15% GPU 小时）。三个方案代表了三种不同的设计取向，用"故障检测 → 故障隔离 → 恢复路径"三段式对比最清晰：

| 维度 | FTAR（Meta, FT-HSDP） | VCCL（Infrawaves 开源） | R²CCL |
|:--|:--|:--|:--|
| 容错粒度 | DP 副本级（梯度 AllReduce 参与者动态增删） | NIC 端口级（主备 QP 切换） | NIC/连接级（连接迁移 + 负载再分配） |
| 控制面 | CPU 驱动复杂控制逻辑，GPU 只做数据传输 | CPU 线程 + GPU copy engine 接管节点内数据移动 | 多 NIC 硬件冗余，协议层快速迁移 |
| 故障检测 | 副本健康检查（训练框架层） | window-based monitor（O(μs) 级） | 连接超时 + 链路状态监测 |
| 恢复代价 | 副本重启（分钟级，3 分钟） | QP 切换（微秒~毫秒级） | 连接迁移（毫秒级） |
| 适用场景 | O(100K) GPU 同步训练 | 生产集群 NCCL 替换 | IB 多 NIC 训练/推理 |
| 性能数据 | 有效训练时间 44%→80% | 吞吐 +5.28% vs NCCL | 训练开销 <1%、推理 <3%；优于 AdapCC 12.18x、DejaVu 47x |

**原理分析**：三者其实是容错分层中不同层级的解——FTAR 在"集合通信语义"层做容错（把参与者集合变成动态集合，本质是拓扑重配置），VCCL 在"传输连接"层做容错（主备 QP 是传输层的 active-standby 冗余），R²CCL 在"路径/资源"层做容错（多 NIC 是路径冗余，迁移是资源再分配）。**越往下层做容错，恢复越快但可覆盖的故障类型越窄；越往上，覆盖广但恢复代价越大。** 一个自洽的万卡集群容错栈应当是三层叠加：VCCL 式微秒级 NIC 故障切换兜住最常见的端口抖动（占网络故障的大头）→ R²CCL 式连接迁移兜住链路级故障 → FTAR 式副本级重配置兜住节点/服务器级故障。VCCL 论文明确说"运行时容错 + 细粒度监控减少大量 GPU 资源浪费"，正是这个意思——**90% 的网络故障其实不该惊动训练框架**。

### 分析三：工作负载边界扩展——Agentic RL / 长上下文推理带来的容错新约束

本窗口最有信号意义的变化是容错研究从"训练"扩展到"训练 + 推理 + Agent 执行"三线并行：

**训练侧的新约束来自 RL 的交互性**。AuroraRL 观察 RL 微调每步更新仅 ~1% 参数变化，于是 delta checkpoint 成为天然选择——这揭示了**容错成本与工作负载的信息熵直接相关**：更新稀疏 → checkpoint 可以稀疏。Belayer 则面对更棘手的挑战：Agentic RL 的环境容器有**外部副作用**（文件编辑、命令执行），恢复不能只回滚模型权重，还必须恢复环境状态并与 LLM 上下文保持前缀一致——**这本质上是分布式事务的"状态一致性"问题被搬进了 RL 训练**。Crab（arXiv 2604.28138，https://arxiv.org/abs/2604.28138，eBPF 分类每轮 OS 效应、75% 的 agent 轮次无恢复相关状态、checkpoint 流量降 87%）与之呼应：agent 沙箱的 checkpoint 需要"语义感知"，不是全量拍快照。

**推理侧的新约束来自状态驻留**。长上下文/agent 化应用让 KV cache 成为 GPU 上的宝贵易失状态（GhostServe：millions-token 级任务 + 流式 KV cache）。Concordia 与 LUMEN 从两个方向回答"推理服务如何容错"：Concordia 从运行时/二进制层做透明 checkpoint（persistent kernel + PTX/SASS 插桩），LUMEN 从系统调度层做负载感知恢复。**推理容错与训练容错的根本差异在于：训练可以接受确定性回滚（模型状态是数学可逆的），推理必须考虑"用户体验连续性"（KV cache 状态是上下文语义，丢了用户就断线）**——这解释了为什么推理侧方案偏向"重建/纠删码/影子副本"而非"回滚重算"。

**对 RAS 体系的意义**：容错研究边界从"训练作业"扩展到"训练 + 服务 + Agent 执行"意味着，集群 RAS 的故障模型要从"硬件故障为主"升级为"硬件故障 + 软件状态故障 + 语义一致性故障"三模型并重。这也是 08 月窗口期多个系统（Belayer、Crab、Concordia）几乎同时出现的结构性原因：**agentic 工作负载的爆发把"状态恢复"从可选项变成必选项。**

### 分析四：对万卡集群 RAS 与训练调度的启示（结合本库 P1 关注）

把本窗口成果映射到万卡集群落地视角，可提炼三条可执行结论：

**① MTTR 预算应下探到"秒级"，集群架构要为热插拔预留资源**。PHOENIX <40s、Belayer 42x 加速、FT-HSDP 3min，都在挑战"分钟级恢复"的行业默认值。实现秒级恢复的前提是：备用节点池常驻（通信拓扑可动态重构）、内存级 checkpoint 有容量预算（KV/权重副本驻留）、控制面协议支持运行时成员变更。这三点都应写进集群规划阶段的资源预算（如预留 2~3% 节点做热备池），而非故障后再救火。

**② 通信层容错应优先于作业层容错部署**。VCCL 的 μs 级监控 + QP 切换、R²CCL 的 <1% 开销，说明**多数网络故障可以在不惊动训练框架的前提下被通信库吸收**。部署顺序建议：先通信库层（VCCL/R²CCL 类，覆盖频率最高的端口/链路故障）→ 再并行度层（FT-HSDP/ReCoVer 类，覆盖节点故障）→ 最后 checkpoint 层（TierCheck 类，兜底灾难性故障）。每往上一层，故障频率指数下降、恢复代价指数上升，形成自然的分层预算。

**③ checkpoint 分层化与"信息熵感知"是降本主线**。TierCheck（按故障频率分层）、AuroraRL（按更新稀疏度分层）、MoC-System（按模型结构分层）、GhostServe（纠删码而非复制）四者合流指向同一结论：**统一单层 checkpoint 已过时，未来是"存储层级 × 模型结构 × 更新频率"三维裁剪的差异化 checkpoint 体系**。万卡集群的 checkpoint 存储预算（NVMe/内存/CXL 的配比）应据此重估——CXL 内存被 Concordia、TierCheck 反复提及为"低成本快速 checkpoint 介质"，是值得跟踪的硬件投入方向。

### 分析五：评估方法论批判——仿真、小规模原型与生产数据的可信度分层

对 2026 年这批容错论文做证据质量审计，能发现评估方法论存在明显的**可信度梯度**，这直接决定结论可外推的程度：

**最高档：生产规模一手数据**。只有 FT-HSDP（Meta，O(100K) GPU，44%→80% 有效训练时间）与 VCCL（Infrawaves，生产集群部署数月，+5.28% 吞吐）是真实生产环境的因果证据。FT-HSDP 的价值不仅在于数字本身，更在于它揭示了全同步训练的"效率天花板"（100K GPU 下有效训练仅 44%）——这是小规模实验永远测不出的结构性事实。**生产数据的不可替代性在于：故障率/故障分布是规模与运行时长的函数，仿真只能注入你预先建模的故障。**

**中档：大规模原型 + 受控故障注入**。PHOENIX（512 A100/65B）、ReCoVer（512 GPU/256 GPU 丢失）、TierCheck（40B）、MoC-System（98.9% 开销降幅）等属于此类。它们具备真实训练栈与真实故障注入，但集群规模仍比生产低 1~2 个数量级，且故障模型是"研究者认为典型"的故障。需要注意：**这类论文报告的改善倍数（42x、2.23x、49x）对"恢复路径"成立，但对"故障频率"不做承诺**——恢复再快，如果故障检测延迟或误判率高，端到端收益会大打折扣，而多数论文对检测环节着墨最少。

**低档：纯仿真/建模**。SPARe（SimGrid 离散事件仿真）、MoFa（成本模型）、LUMEN（原型 + 大规模仿真）属于此类。仿真对"设计空间探索"（SPARe 的闭式表达式、冗余 vs checkpoint 联合优化）有价值，但仿真结论的外推边界取决于故障模型与真实集群的拟合度。**一个方法论陷阱值得警惕：多篇论文报告"相对基线 X 倍改善"，但基线选择不统一（checkpoint-restart、AdapCC、DejaVu、PrimeRL-Full……），且各论文的故障注入频率不同——跨论文比较绝对数字必须回到原始条件，这正是本库"数值 + 基线 + 条件"质量标准的适用场景。**

**对决策的含义**：万卡集群容错选型时，证据权重应按"生产 > 大规模原型 > 仿真"排序；仿真结果只能用于排除选项，不能用于论证收益。FT-HSDP 与 VCCL 是当前唯二可直接引用到生产决策的数据点。

## 五、趋势总结

1. **范式迁移确认**：容错从"checkpoint-restart 的优化"转向"在线恢复 + 冗余架构"，PHOENIX 的"零开销 + 秒级热插拔"与 SPARe 的"恒定 2~3x 计算开销"标志着第三代（架构级容错）已形成论文簇，不再是孤例。
2. **工作负载边界扩张**：容错研究同时覆盖训练（RL/预训练）、推理服务（KV cache）与 Agent 执行（沙箱状态），"状态一致性"取代"数据可回滚"成为新难点。
3. **通信层是性价比最高的容错投资**：VCCL/R²CCL 证明大部分网络故障可在通信库内被吸收，开销 <1~3%，远低于作业级重启；Meta FT-HSDP 提供 100K GPU 的第一手量化基线（44%→80% 有效训练时间）。
4. **checkpoint 体系三维差异化**：存储层级（TierCheck）× 模型结构（PEC）× 更新密度（AuroraRL）的组合裁剪是降本主线，CXL 内存作为快速 checkpoint 介质被多个系统独立提及。
5. **对 RAS 的启示**：集群 RAS 的故障模型应从"硬件故障为主"扩展为"硬件 + 软件状态 + 语义一致性"三模型；MTTR 预算应从分钟级下探到秒级，集群规划需预留热备节点池与内存级冗余预算。
