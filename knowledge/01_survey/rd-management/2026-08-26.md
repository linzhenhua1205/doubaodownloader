## 核心发现

- **LLM 生产评估三层标准：先定产品决策再碰模型，指标分层不可互换**（08-25 GitHub Blog, AI & ML, Mariko Wakabayashi(Principal Applied Scientist, Microsoft) & Zixiao Chen(Senior Applied Scientist)）: 评估一个用于减少 GitHub secret scanning 误报的 LLM 系统时，明确三层组织：**①Primary outcome**（用户收益=误报降低/Precision 提升）→ **②Safety constraint**（安全约束=Recall 必须守在预定义护栏内，任何实验仅在 recall 降幅可接受时才可推进）→ **③Operational guardrails**（延迟/成本/可靠性/生产兼容性）。关键原则原文：**"We did not treat precision and recall as equally interchangeable metrics"**——在 secret scanning 里错误压制真实凭证比让开发者多看一条 alert 后果更重，故 recall 是"否决项"而非可交换指标。文中给出对照示例：实验 A 精度大幅提升但 recall 跌破护栏→不推进；实验 B 精度中等提升但 recall 在护栏内→继续测试。治理迁移：任何 AI 功能(代码审查/安全检查/文档)立项时先写"产品决策+护栏清单"，防"单指标优化"掩盖风险。URL: https://github.blog/ai-and-ml/how-to-evaluate-llms-before-production/

- **离线评估=集成测试：一次一变量 + 全量版本化 + 管道贴近生产**（08-25 同文）: ①**变更即重跑**——每次改 prompt/模型/输入构造/系统逻辑都重跑离线评估，与端到端集成测试同待遇，且每次记录 prompt/model/dataset/系统配置版本，保证可比基线；②**一次只改一个主要变量**——prompt 修订与模型升级分开测（小 prompt 改动也会移模型行为，模型升级同时影响质量/成本/延迟/输出一致性），prompt 与评估配置"当代码管"：版本化、记录变更、可回滚；③**模型升级定期测**——prompt 可能承载了本应由模型承担的理解复杂度，更强模型+更简 prompt 常优于旧模型+重度调优，但升级必须过评估；④**离线贴近生产**——保留候选值、周边上下文、支撑信息、输入格式、系统逻辑，小差异即歪曲结果（示例：变量名 example_token 因"看起来更安全"吸引模型注意力，导致评估目标 candidate_value 被忽略——干净数据集会漏掉这类干扰）。治理迁移：AI 评估不是一次性验收，是随变更反复跑的 CI 环节。URL: https://github.blog/ai-and-ml/how-to-evaluate-llms-before-production/

- **生产标签≠ground truth：错误分析六归因 + LLM-as-judge 分流人工审查**（08-25 同文）: ①生产数据里 dismissed/resolved 的 secret alert **不代表误报**——可能是凭证已轮换/风险被接受/为解锁工作流而清掉/被错误分类，用前先问"标签怎么来的、是否匹配评估问题、不同工作流结果是否被归入同类"；②**错误分析找聚合指标藏的东西**——每个失败归因到 model/prompt/input/pipeline/dataset/label 六类之一，把"质量模糊问题"转成具体工程任务（示例：推理错对象→prompt/输入框架问题；缺证据→上下文构造问题；标签错→数据清理问题）；③**LLM-as-judge 只做 triage 不做裁决**——judge 输出也是预测而非 ground truth：自动处理明确低风险案例、低置信/冲突/高影响路由给人工、定期抽样高置信防系统性错误、跟踪 judge/被评系统/人三方分歧、judge prompt 同版本化评估；④**成果量化**: 经反复评估+定向错误分析，离线数据集**误报降 95%**、recall 守护栏——但结论诚实声明"离线评估不证明生产行为，只提供足够结构化证据支持带风险理解地进入线上实验"。URL: https://github.blog/ai-and-ml/how-to-evaluate-llms-before-production/

## 趋势判断（研发管理视角）

- **「AI 质量治理」主线闭环：从规则设计 → 规则运行 → 规则成本 → 规则权威 → 入生产评估**。08-24 alt text（prove/suspect 分层+默认值分离）、08-23 AutoGPT（CI 是墙+门禁可解释）、08-20 Code Quality（按 committer 计费）、08-21 AI credits 预算分层，构成"检查器治理"四维；本次补上第五环——**「AI 系统凭什么被允许进生产」的评估证据链**：产品决策先行（指标分层不可互换）、评估当集成测试（版本化+一次一变量）、贴近生产（保真度）、标签批判（信号≠真理）、错误归因（把模糊质量问题工程化）。任何要把 LLM 放进研发流水线的团队，这五环都是立项清单。
- **"评估的工程化"是 AI 研发治理的下一主战场**：本文把评估从"选模型的 benchmark 对比"升级为"持续工程实践"（变更即重跑、当代码版本化、judge 分流人工），与昨天"离线评分 harness 与 CI 同 prompt"互证——**评估资产(prompt/数据集/基线)本身成为需要治理的一等代码资产**。研发平台若提供"评估即服务"（数据集版本管理+基线库+一次一变量实验追踪），将是高价值基建方向。
- **AI 进入安全关键流程的护栏模式可复用**：Precision 作主目标、Recall 作否决护栏、运营指标作兼容性约束——"主指标+否决项+运营约束"三层结构，适用于一切"AI 帮人做决策但错误代价不对称"的场景（安全扫描/代码审查/告警分诊）；错误代价不对称的方向必须设否决护栏，这是 08-24"宁可漏报不误报"的量化版表述。
