## ① Agent Plugins 1.0 在 VS Code / Copilot CLI / Copilot app 全面可用：技能供应链标准化 🔥🔥

- **来源/标题**: GitHub Changelog《Agent Plugins 1.0 in VS Code, Copilot CLI, and the Copilot app》（Aug 12, 2026, Release）— https://github.blog/changelog/2026-08-12-agent-plugins-1-0-in-vs-code-copilot-cli-and-the-copilot-app
- **要点**: Agent Plugins 1.0 开放标准于 **8 月 6 日**发布（AWS、Anysphere、Microsoft、OpenAI、Vercel 联合，Google 同日加入核心维护者），将 **agent skills + MCP servers 打包为单一可安装插件**，独立于任何单一厂商治理。8 月 12 日起 VS Code、Copilot CLI、GitHub Copilot SDK、GitHub Copilot app **全平台 GA**（所有 Copilot 套餐）
- **要点**: 一次构建、跨客户端复用——插件可同时捆绑 skill（如部署 runbook）与其 MCP 工具集成，消除逐客户端维护 manifest/目录布局的重复成本；`com.github.copilot/` 命名空间目录承载 Copilot 专属能力（自定义 agents/commands/rules/hooks），其他客户端忽略该目录以保持可移植性；现有 Copilot 插件无需迁移
- **要点**: 分发入口 Awesome Copilot marketplace 默认内置（VS Code/Copilot CLI/Copilot app）；**组织治理复用现有 enterprise managed settings**：`enabledPlugins`（自动安装/屏蔽）、`extraKnownMarketplaces`（增补市场）、`strictKnownMarketplaces`（限制仅受管市场），企业值=基线、团队级覆盖可叠加；插件携带 MCP server 配置 → 与 MCP allowlists（按 URL/命令/名称批准或屏蔽）配合使用
- **信号解读**: **agent 技能进入"应用商店化"阶段**——技能的分发、安装、屏蔽第一次有了跨厂商标准包装格式 + 组织级治理面，研发管理从"管模型"扩展到"管技能包生态"；Google 加入核心维护者意味着 skill 生态**不锁定单一厂商**，组织投资 AGENTS.md/skill 资产的锁定风险下降
- **研发管理含义**: 建议评估将内部 runbook/规范沉淀为 Agent Plugin（skill+MCP 打包）并在受管 marketplace 分发；用 strictKnownMarketplaces 收敛安装源、MCP allowlists 控制工具接入，形成"插件=技能分发单元"的治理基线

## ③ "Your contributors are AI-first now. Is your project?"：AI 贡献者治理模式库 🔥🔥

- **来源/标题**: GitHub Blog《Your contributors are AI-first now. Is your project?》（Aug 12, 2026, Maintainers, Andrea Griffiths）— https://github.blog/news-insights/maintainers/your-contributors-are-ai-first-now-is-your-project/
- **要点**: AutoGPT（180k+ stars、~150 个 open PR、~800 贡献者）维护者 Nicholas Tindle 实践：**AI 贡献者已占 PR 队列大头**（Copilot/OpenClaw/自研工具等），态度从"关闭大门"转向"让 token 替你付算力——只要进门的路只有一条"；核心观点"**你的文档没问题，发现（discovery）才是问题**"：agents 不会主动读 docs，只读所在目录级别的指令文件
- **要点**: 落地模式——CLAUDE.md 先行（commit trailer 自报家门）→ Copilot/Codex 不读 Claude 文件 → 收敛到标准 **AGENTS.md**（放代码旁边，目录作用域；skill 可目录外动态发现，如前端 Storybook 测试 skill 用描述触发词自动加载、后端 80% 覆盖率门禁）；**门禁设计**：PR 模板不符自动关闭（实际规则先改变了 agent 行为，人反而被宽容对待）、模板中"testing the PR"措辞触发 test PR skill（自动装 agent browser、跑 app、执行变更）、Codecov 阈值设为 required check（CI=墙不是建议）、**CLA 作人类探测器**（浏览器+GitHub OAuth 跨域流，agent 目前做不了）、**review thread 必须附 commit SHA 才能 resolve**（pr-address skill 声明 fix→commit→push→reply→resolve 唯一合法序列，SHA 取自 git rev-parse HEAD 防复用旧提交）
- **要点**: 主动关掉的门禁——CI 失败 agent 自动评论（噪声大于价值，"restraint"原则：保留降低维护负担的，关掉变噪声的）；**四个坑**：坏 AGENTS.md 比没有更糟（污染 context）、GraphQL API 会 rate limit（改用 GitHub App 认证 CLI）、重审查工具成本高（8-agent 并行测试 rig 只跑极小/极大 PR）、**审计 authorized apps**（Secure Open Source Fund 教训：每个试过又弃用的工具都留了个授权，弃用即移除）
- **要点**: 不是所有东西都是门禁——**不必接受每个 PR**（合并他人 LLM 输出是不对称交易：维护成本永远在你），关闭 PR/限制 issue/仅收 bug 报告（SQLite 模式）都是合法边界；关闭要自己重建的 PR 时把贡献者加为 co-author
- **信号解读**: 官方（GitHub 平台能力：AGENTS.md 生态、rulesets、Copilot）与社区（AutoGPT 实践）**双向验证同一方向**——"把判断放进代码旁边"：指令文件+门禁矩阵+工具审计构成 AI-first 贡献治理三件套；05 月 Maintainer Month 采访沉淀为 8 月正式文章，说明该问题已成为维护者社区的普遍焦虑
- **研发管理含义**: 企业内部可复制该模式库：AGENTS.md 治理规范（模板+CI 门禁+人工回环点）+ 授权审计制度（季度清理 GitHub Apps/OAuth）+ "合并 LLM 输出=永久维护负债"的取舍原则；对内部代码库，CLAUDE.md/AGENTS.md 标准化是 AI 协作质量的低成本杠杆

## ④ GitHub 7 月可用性报告：自动化变更为主要事故源 ⭐⭐

- **来源/标题**: GitHub Blog《GitHub availability report: July 2026》（Aug 12, 2026, Company news, Jakub Oleksy）— https://github.blog/news-insights/company-news/github-availability-report-july-2026/
- **要点**: 7 月 8 起事故（较 6 月 6 起上升）；**8/6 Actions 事故被官方定性"unacceptable"**——完整 RCA 将在 8 月报告（9 月发布），已宣布**加速 Actions 迁往 Azure**（launch service 因异步+可排队而未优先迁移，级联失败拖长恢复）；目标 CY2026 年底 dotcom 生产流量全部迁出自有数据中心
- **要点**: 7 月事故明细——7/8 数据驻留环境 5xx（峰值 96% 错误率、84% 活跃租户受影响、7h4m，根因：自动化 metadata 变更绕过了运行中 VM 的保护、破坏服务发现）；7/9 Actions runner 供应（9h18m，8% 工作流延迟>5min、2% 启动失败）；7/16 MCP Server web_search 上游提供商劣化（峰值 82% 错误）；7/19 DNS 两次（内部 DNS 控制面数据库问题→自动重配破坏服务发现，峰值区域 5xx 9.9%、webhook 中断 40min；同日 Actions runner 证书过期 5h10m，78.99% larger-hosted jobs 延迟）；7/21 SSH RSA key 认证回归（12.2%→15.7% 失败）；7/24 PR 创建故障（Vitess backfill 取消执行了误解的 codepath 导致丢表，113,930 次创建尝试受影响、50,904 用户）；7/25 Actions Redis 维护后跨区不一致（25%→60% 运行基础设施错误）
- **要点**: 架构迁移里程碑——monolith 读流量 Azure Central US 峰值 **52.75%**（7/28 首破 50%）、Git 流量 47%（6 月 43%）、29% 仓库有第二副本；认证首表迁出共享数据库（专用用户服务峰值卸载 >1M QPS）、PR 服务认证读 99.87% 与 monolith 对齐；7 月 5xx 事故主因集中在**自动化变更/证书手动部署/误解工具行为**三类
- **信号解读**: **"变更自动化"本身成为最大事故源**（metadata 自动变更、DNS 自动重配、证书依赖手动部署）——平台工程新风险面：需要"安全自动化"（配置 immutability、last-known-good 保留、read-only 回退、pre-flight validation）；官方原则"availability, then capacity, then features" + 度量转向**工作流健康**（PR 创建等关键工作流而非仅基础设施）
- **研发管理含义**: 对自建 AI 基础设施平台（万卡集群/RAS）同构：变更系统化（自动化变更必须自带保护与回退）、证书/密钥生命周期自动化、关键工作流健康度量——8 起事故中 3 起与"自动化过程引入的变更"直接相关，是 SRE 预算投入的实证依据
