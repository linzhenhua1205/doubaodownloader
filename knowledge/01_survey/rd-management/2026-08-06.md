## ① Stacked PR：把巨型 AI 变更拆成可审查的依赖链 🔥

- **来源/标题**: GitHub Blog《Turn one giant AI-generated pull request to a reviewable stack》（Aug 4, 2026）— https://github.blog/engineering/turn-one-giant-ai-generated-pull-request-to-a-reviewable-stack/
- **要点**: 针对 coding agent 默认产出 1,000+ 行巨型 PR（数据模型+API+UI+错误态一锅端、审查者流失、质量下滑、合并且慢）的痛点，GitHub 给出原生解法——**stacked pull requests 将功能拆成逻辑分层、各自独立可审查的依赖链**
- **能力细节**: 通过 `gh stack init/add/push/submit/rebase/sync` CLI 管理；新增 `gh-stack` skill（`gh skill install github/gh-stack` 或 `npx skills add`），让 agent 学会"以栈的方式提交工作"；PR 顶部有 **stack map 一键导航**；审查路径固定为"自上而下读上下文、自下而上逐层审"
- **分层示例**: 商品搜索功能拆 4 层——L1 数据模型（Data modeler agent）/ L2 搜索 API（Backend agent）/ L3 聊天接 API（Frontend agent）/ L4 UI 引文（Frontend agent），每层可由不同领域 owner 审查（数据 owner 审数据、UX owner 审 UI）
- **注意点**: Web 端一键 Rebase 在 GitHub 服务器执行会重置 committer 且提交不签名（破坏签名提交约束）→ 推荐 `gh stack rebase` 本地执行；栈中下层分支被修改后 GitHub 会标记 "branches have diverged" 并阻止合并，`gh stack sync` 一条命令级联同步
- **信号解读**:
  - 这是**"AI 产出治理"从事后约束转向交付结构原生支持**的标志——不再靠人工拆 PR，而是让 agent 从提交起就遵循可审查粒度
  - 与昨日"Copilot code review 工具化"（迁移到 Unix 风格代码探索工具）呼应：**审查友好性成为 AI 协作平台的核心竞争力**
  - Gartner 预测引述：coding agents 到 2028 年驱动每个 SDLC 阶段 50% 生产率提升——生产率越高的工具越需要"可审查性"兜底

## ④ IntelliJ IDEA 语言智能走向开放：LSP 落地 VS Code/Cursor/Agentic Flows

- **来源/标题**: JetBrains Blog《IntelliJ IDEA Goes LSP: Java and Kotlin Intelligence Comes to VS Code, Cursor, and Agentic Flows》（2026-07 底，主页列表可见）— https://blog.jetbrains.com/
- **要点**: JetBrains 将其 Java/Kotlin 语言智能通过 **LSP（Language Server Protocol）** 开放给 VS Code、Cursor 及 agentic flows——IDEA 的核心语言能力不再绑定自家 IDE
- **信号解读**:
  - 背景：agent 承担实现工作后，开发者手动编辑场景变窄，可能只需要"窄而基础"的 IDE 能力 → JetBrains 被迫把语言智能商品化/开放化，**IDE 的护城河从"编辑器体验"迁移到"语言服务器+agent 工具链"**
  - 与昨日记录的 Copilot"代码审查迁移到共享 Unix 式代码探索工具"同构：**AI 时代，工具能力走向标准化协议开放，垂直集成让位于横向协议兼容**（LSP/MCP 双标准再获一例）
