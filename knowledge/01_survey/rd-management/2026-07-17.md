## ① 🆕 Claude Code v2.1.212 — runaway 防护体系（Jul 17）

> 来源：https://docs.anthropic.com/en/docs/claude-code/changelog

### 三大 session 级硬上限

**这是 Claude Code 首次引入会话级的资源消耗硬上限**——标志着 agent 从"信任优先"转向"安全兜底"：

| 上限 | 默认值 | 配置项 | 行为 |
|:----|:------|:-------|:-----|
| WebSearch 调用次数 | 200次/会话 | `CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` | 防止搜索循环失控 |
| Subagent 派生次数 | 200次/会话 | `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION` | 防止委托循环爆炸；`/clear` 重置预算 |
| MCP tool 自动后台阈值 | 2 min | `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` | 超长 MCP 调用自动移入后台，保持界面可用 |

### /fork 的语义升级

`/fork` 现在**把当前对话复制到一个新的后台 session**（在 claude agents 中独立一行），同时主会话继续工作。之前 `/fork` 启动的是 in-session subagent，现在改为 `/subtask`。

### 关键修复

- **plan mode 自动运行破坏性命令**（`touch`/`rm`）不弹权限确认 — 已修复
- **worktree symlink 逃逸**：`.claude/worktrees` 处仓库提交的 symlink 可能导致文件创建到仓库外部 — 已修复
- **`continue:false` hook 的 halt 被丢弃**：当 tool 失败或流中断时 hook 的拦截失效 — 已修复
- **SIGTERM 导致 Bash 进程孤儿化**：print/SDK 模式下 kill 无法终止整个进程树 — 已修复
- **Windows Group Policy 阻塞 PowerShell 5.1** → daemon 改用 PowerShell 7
- **OTel HTTP export 被 Azure Monitor 拒绝**（chunked transfer encoding）— 已修复
- **大量图片会话误报 "Request too large"** — 已修复，错误信息改进

### 企业安全强化延续

- `forceLoginMethod` 现在同时适用于 **VS Code extension、SDK、setup-token、install-github-app**，不限于 terminal

## ② Atlassian：Teamwork Graph 的量化价值（Jul 15）

> 来源：https://www.atlassian.com/blog/company/how-were-evolving-jira-for-ai-native-software-development
> 作者：Dave Meyer，2026-07-15

### 关键发现：AI 使用量 +65%，研发速度仅 +15%

Atlassian 与 DX 联合进行了一项**纵向工程团队研究**，结果发人深省：

> "AI usage has increased by 65%, but overall developer velocity did not. It topped out at a 15% increase, with many organizations seeing gains averaging 10%."

这个 **AI 生产力差距**（productivity gap）不是模型写代码不行了——而是软件开发从来不仅仅是写代码。真正的瓶颈在**上下文传递**和**组织协调**。

### Teamwork Graph 的量化效果

Atlassian 内部基准测试显示，Agent + Teamwork Graph 的组合效果：

| 指标 | 无 Teamwork Graph | + Teamwork Graph | 改善 |
|:----|:-----------------|:-----------------|:-----|
| 结果准确率 | 基准 | **44% 更准确** | ↑ 44% |
| Token 消耗 | 基准 | **48% 更少 token** | ↓ 48% |

> "Agents enriched by Teamwork Graph showed 44% more accurate results while using 48% fewer tokens than agents operating without that context."

### Jira AI-native 产品发布清单

Atlassian 在 **2026-07-15** 发布了整套 AI-native 产品能力：

| 能力 | 说明 |
|:----|:------|
| **Jira Planner** | 从代码库、Jira、Confluence 历史拉取上下文，生成人机可读的技术 spec（Confluence 页面） |
| **Jira for Slack** | `@Jira` 创建任务、捕获 thread 上下文、分配 agent；Microsoft Teams 即将支持 |
| **Loom 视频转指令** | 录屏 + 语音说明 → 自动生成可执行的 agent 任务 |

| **Agent Sessions 视图** | 查看哪些 coding agent **卡住**、哪些等审查、哪些已完成，统一视图 |
| **Coding Agent Automations** | Jira enterprise 自动化规则：bug fix/漏洞修复/测试生成/文档更新→自动路由给 agent |
| **DX AI Cost Management** | 统一管理 Claude/Cursor/Copilot/Jira 的 spend + token 数据，**估算每个 PR 的成本** |

## ③ GitHub Copilot Code Review：工具指令重塑 PR 审查工作流（Jul 10）

> 来源：https://github.blog/ai-ml/better-tools-made-copilot-code-review-worse-heres-how-we-actually-improved-it/
> 作者：Napalys Klicius, GitHub Software Engineer

### 核心论点：给 agent 更好的工具 ≠ 更好的结果

GitHub 将 Copilot code review 的代码探索工具从自研实现迁移到**共享的 Copilot CLI 工具集**（grep/glob/view），预期是一次干净的升级。

**结果适得其反**：审查成本上升、有效评论数下降。

### 根因分析：agent 在"浏览"而非"审查"

旧的代码审查工具在设计上倾向于包裹额外上下文（返回匹配行 + 周围代码），这是为了适配早期模型调用少、需自动拉上下文的特性。

迁移到共享 CLI 工具后，agent 的行为变成了：

1. 广泛搜索（browse）
2. 猜测路径（guess）
3. 广泛读取（read broadly）
4. 发现更多可搜索的东西（widen the search）
5. 携带额外上下文前进

**这不是审查者的工作流**。一个真正的审查者从 diff 开始，提出**针对性的问题**：

- 这个函数在哪里被调用？
- 这个配置键在其他地方被用到吗？
- 最小的相关代码范围是什么？

### 解决方案：为审查重写工具指令

关键的改动是**改写工具的指令**（不是工具本身），让 agent 的行为从"浏览→读→再搜索"变为"提问→缩小→读→判断"：

| 旧行为 | 新行为 |
|:-------|:-------|
| 广泛搜索，猜测路径 | 从 diff 开始，形成具体的审查问题 |
| 交替搜索和读取 | **批量搜索**（grep/glob）→ **精确读取**（view） |
| 搜索失败后继续猜附近路径 | 搜索失败→**简化的转义搜索**；路径不对→**glob**，不猜 |
| 携带无关上下文前进 | **最小化上下文**，只携带回答问题所需的证据 |

### 结果：~20% 更低审查成本

> "In production, the tuned behavior showed roughly 20% lower average review cost compared with the control. Importantly, it did not show a quality signal that could block shipping."

### 反例验证：同套指令对 CLI 无效

相同的聚焦式工具指令在 Copilot CLI（交互式 coding 助手）中**没有产生同样的效果**——因为 CLI 的任务没有固定的 diff 锚点，用户在多个 turn 中改变方向。验证了：

> **共享工具可以扩展，但工具指令必须匹配任务场景。**

### 方法论意义

对于 agent 来说，**工具表面就是产品体验的一部分**。工具描述和系统指令类似于 API 文档——模糊的 API 文档让开发者困惑，模糊的工具指令让 agent 低效。

## ④ GitHub Agentic Workflows：跨仓库文档自动化实战（Jul 8）

> 来源：https://github.blog/ai-ml/automating-cross-repo-documentation-with-github-agentic-workflows/
> 作者：David Pine & Peli de Halleux, Microsoft Aspire 团队

### 背景：文档生产的"逆向工程税"

产品代码在 `microsoft/aspire`，文档网站在 `microsoft/aspire.dev`（不同 repo、不同部署目标、不同审查链）。

传统流程：工程师发版→文档写手数周后注意到→审查 diff→ping 工程师确认→文档拖到发布后。

### GitHub Agentic Workflows 方案

Agentic Workflows = GitHub Actions + model 作为工作项处理器 + **安全输出约束**。核心架构：

```yaml
# 工作流文件 (.github/workflows/pr-docs-check.md)
# YAML frontmatter + 英文 prompt

tools:
  github:
    toolsets: [repos, issues, pull_requests]
    min-integrity: approved
    allowed-repos:
      - microsoft/*
    github-app:
      app-id: ${{ secrets.ASPIRE_BOT_APP_ID }}
      # 只授权两个 repo
      repositories: ["aspire.dev", "aspire"]
  safe-outputs:
    create-pull-request:
      title-prefix: "[docs] "
      labels: [docs-from-code]
      draft: true  # 人肉审，永不自动合并
      allowed-base-branches: [main, release/*]
      target-repo: "microsoft/aspire.dev"
      protected-files: blocked  # AGENTS.md/manifests/安全配置 = 免碰
      fallback-as-issue: true
```

**关键安全设计**：agent 不能直接写 GitHub — 它输出意图（JSON blob），由单独严格 scope 的 safe-outputs handler 物化。

### 量化结果（30 天窗口：May 3 - Jun 2, 2026）

| 指标 | 数据 |
|:----|:-----|
| 产品 PR 合并数（microsoft/aspire） | 396（338 main / 50 release/13.3 / 8 release/13.2） |
| 自动文档 PR 创建数 | **82** |
| 合并率 | **100%**（0 个未合并关闭，0 个仍在 open） |
| 中位文档发布时间（PR merge ~ docs PR） | **44.8 小时** |
| 24h 内合并 | 38% |
| 7 天内合并 | 96% |
| 触发→判定"无需文档" | 396-82=314 次（78%）← 这是 feature，不是 bug |

### 还有什么效果？

- 连 CI 改动、测试修复、内部重构都不生成文档（agent 判"no docs needed"的能力是特意训练的）
- 阅审人是**特性 PR 的 SME**（谁批准了代码，就由谁批准文档）
- agent 永不合并，永远 draft

### 其他 4 个工作流

| 工作流 | 频率 | 功能 |
|:-------|:-----|:-----|
| milestone-changelog.md | 每 2 小时 | 获取最新合并的 PR，维护 changelog wiki 页 |
| release-update-support-mdx.md | 稳定版本发布 | 更新 support policy 页面（提升新版本、降级旧版本） |
| update-integration-data.md | 每天 | pnpm update:all → NuGet metadata + GitHub stats |
| repo-pulse.md | 滚动 3 天 | repo dashboard 钉在单个 issue 上，原地更新 |

## ⑤ Cursor v3.11: Side Chats + Conversation Search（Jul 10）

> 来源：https://changelog.cursor.com/

### Side Chats（侧边对话）

- 用 `/side`、`/btw` 或聊天面板 "+" 按钮启动侧边对话
- **不打断主 agent 对话**，独立持久化、可后续跟进
- 默认聚焦于 **读/搜/答**（read/search/answer）——用来问澄清问题、调研替代方案、做决策 sanity check
- 侧边对话可通过 `@-mention` 拉回主线程

### Conversation Search（对话搜索）

- 在 Agents Window 中可搜索**数千条历史对话的 transcript**
- Cmd+K 全局搜索 → 本地搜索索引，性能"snappy"
- 对话内 Cmd+F 支持跳转匹配、计数、滚动搜索

### 新的 Cloud Agent Hooks（agent 对话层 Hook）

之前的 cloud agent hooks 围绕 tool 执行和文件/shell 操作。新增 hook 覆盖 agent **对话层**：

| Hook | 触发时机 | 用途 |
|:-----|:---------|:-----|
| `beforeSubmitPrompt` | 提交 prompt 前 | 观察/修改输入 |
| `afterAgentResponse` | agent 回复后 | 检查输出质量 |
| `afterAgentThought` | agent 推理后 | 观察推理过程 |
| `stop` | 停止时 | 中断控制 |
| `subagentStart` | subagent 启动时 | 子 agent 管控 |
| compaction 相关 | 上下文压缩时 | 监控 context 管理 |

支持构建**自纠错循环**（self-correcting loops）。
