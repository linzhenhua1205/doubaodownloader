**核心论点**: 面向企业管理员/组织 Owner 的新 Copilot 度量仪表盘，**从"谁在用"升级为"怎么用、多深地用"**。基于 usage metrics API 的 `ai_adoption_phase` 分类（28 天滚动窗口），将用户划分为 4 个采用阶段群组：

| 群组 | 定义 |
|:-----|:-----|
| **Phase 1 (Code-first)** | 以代码补全/生成式为主 |
| **Phase 2 (Agent-first)** | 以 Agent 交互为主 |
| **Phase 3 (Multi-agent / Copilot app)** | 多 Agent / Copilot App 深度使用 |
| **Passive** | 已授权但未活跃使用 |

**每个群组卡片展示的指标**：
- 人均每月合并 PR 数（throughput）
- 中位 PR 合并速度（merge velocity）
- 群组用户数及占比
- 人均每日代码行数

**核心创新 — Adoption Multiplier（采用倍率）**：直接对比 **Passive 群 vs 活跃 Copilot 用户的平均吞吐/速度**，用"底部线"方式呈现采用 ROI。另有 6 个月群组增长与 PR 吞吐趋势图，以及**可执行的下一步建议**（引导用户进入更深采用阶段）。

> 这是**研发效能度量方法论的里程碑事件**。DORA 2024 已证明"AI 采用率"作为单一指标有误导性（采用+25% → 吞吐反而 -1.5%），GitHub 这次的答案是用**行为阶段而非开关状态**来度量采用：Code-first → Agent-first → Multi-agent 的阶梯本身就是能力深化的路径。对企业的启示：**度量"采用深度"比度量"采用率"更能指导 enablement 投入**。配套信号（Jul 28：Copilot app usage metrics 扩展到报告汇总；Jul 17：仓库级用量指标 GA；Jul 07：usage API 新增 review cycles 与 time-to-adoption 字段）显示 GitHub 正在系统性补全"AI 研发效能度量"的指标体系。

## ② Tame Dependabot — 依赖更新噪音治理的可复制最佳实践

| 维度 | 内容 |
|:-----|:-----|
| **来源** | GitHub Blog, Jul 29, 2026 |
| **标题** | Tame Dependabot: Group your updates, slow the cadence, keep security fast |
| **作者** | Bruno Borges (Principal PM) |
| **链接** | https://github.blog/enterprise-software/automation/tame-dependabot-group-your-updates-slow-the-cadence-keep-security-fast/ |
| **标签** | `研发流程优化` `Dependabot` `依赖管理` `噪音治理` |

**核心论点**: Dependabot 的默认配置会产生"更新噪音"，让重要更新被淹没。微软 GCToolkit 项目的数据触目惊心：**578 个 commit 中 92 个（约 1/6）是 Dependabot 版本 bump，过去 12 个月就有 61 个，有时一天多个**——大量 review/merge/CI 周期消耗在例行维护上。

### 三改法（十几行 YAML 解决）

| 改动 | 操作 | 效果 |
|:----:|:-----|:-----|
| ① **分组** | `groups: monthly-batch: patterns: ["*"]` | 10 个单依赖 PR → 1 个批量 PR（1 分支/1 CI/1 review） |
| ② **降频** | `schedule.interval: daily → monthly` | 从"随时来"到"按月可规划" |
| ③ **全覆盖** | 补上遗漏的 ecosystem（maven 等） | 只配置 github-actions 导致应用依赖无版本更新 |

**安全网设计（关键）**：分组与调度**只影响版本更新，不影响安全更新**——安全更新仍由漏洞披露即时触发，独立于 schedule。另有默认 **3 天 cooldown**（新版本发布 3 天后才开 PR），抵御供应链攻击（刚发布即被利用的版本）。2026-02 起支持**跨目录分组**（monorepo 场景，`group-by: dependency-name` 把同一依赖的多个 bump 合并为 1 个 PR）。

### 信号解读

> 这是**研发流程优化的教科书级实操案例**：噪音治理 = 分组 + 降频 + 覆盖完整性 + 安全旁路。核心原则对任何自动化流水线都适用：**例行工作要"安静且批量"，紧急工作要"仍然穿透"**。对研发管理者的启示：审查队列的信噪比本身就是一种管理资产——当 1/6 的 commit 是噪音时，重要更新被忽略是必然结果。配套信号（Jul 23：Dependabot 默认 3 天 cooldown 落地）说明平台正在把"防噪音"内置为默认行为。
