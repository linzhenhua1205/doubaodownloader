## 一、平台调度研究前沿（arXiv 2026-08 最新）

- **arXiv/OpScale (2608.13499, 08-13)**: LLM serving 自动扩缩容的"单元粒度"之问——现有方案把整个模型当单一缩放单元（monolithic），无法捕捉推理负载的细粒度动态；OpScale 把供给与自动扩缩容下沉到 **operator 级**（每算子独立扩缩），直指"粗粒度扩缩容造成 GPU 过度供给/供给不足并存"的成本-延迟失衡。与昨日 SliceScheduler（容器→算子级调度）构成同向双证据：**扩缩容与调度两个维度都在从模型/请求级下钻到算子级**。https://arxiv.org/abs/2608.13499
- **arXiv/ElastiCo (2608.07971, 08-08)**: GPU 集群"训练+离线推理共置"弹性框架——训练作业整卡预留却周期空闲、离线推理按突发峰值过度供给，两类负载都被现有调度器当作隔离静态资源；ElastiCo 让训练与推理安全共享 GPU（弹性配置 + 干扰感知编排），针对多云厂商"训练/推理池分离"导致的显著容量浪费。https://arxiv.org/abs/2608.07971
- **arXiv/HorizonServe (2608.01785, 08-03)**: Omni-model（文本/语音/图像/多模态统一后端）暴露新调度问题——不同输出模态请求共享多模态 backbone、后发散到下游生成阶段，同一 GPU 上出现异构首响指标与 SLO 目标；现有 LLM/多模态 serving 只优化 token 进度或输入侧处理，HorizonServe 首次**联合控制请求调度与 GPU 共享**。平台调度从"单一文本 LLM"扩展到多模态混合负载。https://arxiv.org/abs/2608.01785
- **arXiv/Beyond the Limits (2608.09308, 08-10)**: 云集群调度两大缺陷——(1) SLO 过度严格执行导致资源利用率低与能效差；(2) 共享资源缺拥塞感知。提出弹性 SLO 执行 + 拥塞感知调度，把"死守 SLO"转为"按负载压力动态让步"，与 Multi-Tier SLA（昨日已收）同向：**SLA/SLO 语义正从硬约束变成可弹性协商的调度输入**。https://arxiv.org/abs/2608.09308
- **arXiv/Aries (2607.29069, 07-31)**: Agentic serving 的 AI 云基础设施全栈实验框架——Agent 负载=重复推理+持久上下文+沙箱工具执行，与常规 LLM serving 根本不同；Aries 分离任务语义与执行配置、重建跨组件 Agent 轨迹（关联系统遥测）、在异构沙箱基座上统一暴露有状态工具执行接口。为"算力平台如何服务 Agent 负载"提供可复现评估底座（延续 SAGA/DriftSched 的 Agent 语义调度主线）。https://arxiv.org/abs/2607.29069

## 四、追踪结论（趋势线）

- **调度/扩缩容双线下钻到算子级**: 昨日 SliceScheduler（容器→算子级调度）+ 今日 OpScale（整模型→算子级扩缩容）——LLM serving 的资源管理单元正在经历"模型级→请求级→算子级"的第三次下钻，直接回应多租户 LLM 服务的碎片化 GPU 利用与成本-延迟失衡。
- **SLA 语义从硬约束走向弹性协商**: Multi-Tier SLA（4 层分级最优）+ Beyond the Limits（弹性 SLO+拥塞感知）——平台 QoS 契约从"死守单点"转向"按层级/拥塞动态让步"，为多档位差异化定价（OpenCost token 级计费，已收）铺路。
- **负载谱系从文本 LLM 扩展到 Omni-model 与 Agent**: HorizonServe（多模态统一后端的调度难题）+ Aries（Agentic serving 全栈实验框架）——算力平台要服务的负载已不再是单一文本生成，调度语义必须感知输出模态分化与 Agent 工具执行链路。
- **国产算力平台进入"万卡交付+共建运营"阶段**: 昆仑芯 P800 万卡集群多批次交付、壁仞开发者云"运营商+设备商+芯片商"共建普惠算力底座——国产算力从芯片供给走向平台运营化，与海外 AI 工厂承购模式（PORTS-Pike 8 IT-GW，08-18 已收）形成两条平行商业化路径。
