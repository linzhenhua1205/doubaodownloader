## 一、平台调度研究前沿（arXiv）

- **arXiv/Pod-Deployability PSPACE-Complete (2608.19822, 08-20, Giallorenzo/Mauro/Zavattaro)**: 把 K8s 调度的核心问题「pod-deployability」（给定初始集群+pod 类型+目标节点，是否存在合法部署/删除序列覆盖目标）做计算复杂性定界，三个结果：①动态约束无 affinity（仅 anti-affinity）→ 多项式时间可判定；②required affinity + required anti-affinity → PSPACE-complete；③仅 required affinity 就足以 PSPACE-complete（单节点、单标量容量即触发）。下界分别编码 1-safe Petri-net coverability 与 bounded black pebbling，把调度状态空间复杂性的两个独立来源（逻辑互斥 + 资源受限前提管理）分离出来。https://arxiv.org/abs/2608.19822
- **本组解读（required vs preferred 是复杂度阶变）**: 该结果的平台工程含义比论文标题更锋利——K8s 中 `requiredDuringScheduling` 与 `preferredDuringScheduling` 在 API 层面只是「硬/软」语义差异，理论上却是 PSPACE-complete 与多项式时间的**复杂度阶变**：required affinity 使可行性判定本身不可精确求解（大规模集群上只能启发式逼近），而 preferred affinity 把问题拉回可判定域。这为「平台默认用 soft 约束、hard 约束仅限关键反亲和」的工程实践提供了第一性原理背书，也解释了为何生产调度器（Volcano/Kueue/HAMi-DRA）普遍把亲和建模为打分项而非硬约束。https://arxiv.org/abs/2608.19822
- **交叉引用（tech 组今日已收录）**: CacheRoute 前缀亲和路由（2608.19677）与 FleetSieve SLO 感知集群配置（2608.19659）——亲和/配置决策从「静态规则」走向「规划化路由+决策关键画像」，详见 tech 组 08-24 日报与 cluster-training 组。

## 四、追踪结论（趋势线）

- **调度理论从「优化」走向「可行性边界」**: 08-21/22 收录的 RLTune/DriftSched/Beyond the Limits 回答「怎么排最优」，今日 PSPACE 回答「排不排得出来」——调度研究开始给平台工程划理论边界：required affinity 的可行性判定 PSPACE-complete 意味着**大规模精确求解不可行是数学事实而非工程妥协**，启发式/软约束不是降级而是唯一理性选择；对平台 API 设计者的直接启示：把约束按「硬可行性约束（资源容量/反亲和互斥）」与「软偏好目标（亲和打分）」分层建模，是复杂度可控的前提。
- **亲和语义成为新的第一性分水岭**: K8s 的 required/preferred 之分、调度器的 scoring vs hard-filter 之分，在复杂度理论上被证明是「可判定 vs 不可精确求解」的分界——这一观察可与今日 tech 组 DRA 条目互证：DRA 以 ResourceClaim 声明式表达设备语义，同样把「精确保证」让渡给「账本式记账+调度器启发式」，云原生调度整体向「声明软约束+启发式求解」收敛。
- **跨组共振：调度器的三个新约束维度**: 综合今日各组合集——tech 组专家流动性（FluxMoE 分页/CRAFT 复制预算化/PROBE 预取，显存零和博弈）、软 SLO 受控超卖（08-22 Beyond the Limits/ElastiCo）、今日 PSPACE 可行性边界——2026H2 的 GPU 调度器设计面从「单目标（利用率/延迟）」扩展为「可行性 + 确定性 + 弹性」三维约束空间，平台层 SLA 承诺方式随之从「绝对保证」转向「违约概率可控」。
- **源体系缺口成追踪档最大风险**: 连续 3 日 Baidu/Bing/爱集微全线失败，国产算力平台动态（政策/集采/芯片平台适配）系统性漏报——国际侧（arXiv/CNCF）增量充足、国产侧持续空白的不对称，正在扭曲算力平台追踪的覆盖均衡，建议优先修复国产信源通道。
