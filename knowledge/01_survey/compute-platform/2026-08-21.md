## 一、平台调度研究前沿（arXiv GPU Scheduling 最新）

- **arXiv/LOCAL (2608.15241, 08-15)**: 首个"单 GPU 端侧 Agent 连续学习"运行时——端侧 LLM Agent 反复与用户交互产生私有轨迹，理想应边推理边学习，但现有推理运行时假设权重稳定、RL 系统假设资源分离。LOCAL 让合作式调度器、版本感知 KV 缓存管理器、多 Agent 模型运行时三方共享状态，解决"adapter 更新使旧版本 KV 缓存失效"的耦合问题。7B 模型/24GB GPU 实测：前台排队等待 p95 较 FIFO 降 3.1x、TTFT p95 较不可抢占训练降 1.55x、发布后首命中 prefill p99 降 25.6%、跨 Agent TTFT p99 降 21.9%，且在紧 KV 预算下后台学习持续推进。https://arxiv.org/abs/2608.15241
- **arXiv/SAGA (2605.00528v2, 06-19)**: "程序级调度"宣言——AI Agent 每个任务执行数十到数百次链式 LLM 调用，现有 GPU 调度器却把每次调用当独立请求，丢弃步骤间 GB 级中间状态，端到端延迟膨胀 3-8x。SAGA 以整个 Agent 工作流为调度单元（Agent Execution Graph 预测跨工具调用边界的 KV 缓存复用，达 Bélády 最优离线策略的 1.31x 内），64-GPU 集群跑 SWE-bench 编码 Agent 与 WebArena 浏览器任务：任务完成时间较 vLLM v0.15.1（prefix caching+affinity routing）降 1.64x（几何均值，p<0.001）、GPU 内存利用率提升 1.22x、多租户干扰下 99.2% SLO 达成；代价是峰值吞吐降约 30%——面向延迟敏感的交互式 Agent 部署的明确取舍。https://arxiv.org/abs/2605.00528
- **arXiv/DriftSched (2606.02982v2, 06-19)**: 多租户 LLM 推理的 QoS 感知调度——准入时的工作负载估计常偏离实际执行（token 漂移），导致误分类、队列失衡、尾延迟恶化。DriftSched 组合工作负载分类+token 预算估计+租户感知队列+在线反馈校准：估计误差平均降 38.8%（MAE）/40.5%（RMSE）；对比 FIFO/Priority/Weighted/SJF/Aging 五策略，SJF 综合最优（中位端到端延迟 -42%、p99 -16%）；结论：**调度策略选择对延迟的影响大于运行时校准本身**，准确的负载刻画可消除系统性估计漂移。https://arxiv.org/abs/2606.02982
- **arXiv/Vitamin-E (2603.15042v4, 08-05)**: 保持确定性的 GPU 空间共享——观察到现代 GPU 调度把"逻辑结构"与"物理宽度"解耦（一个不修改的 launch 可通过 block 放置与 wave 数变化覆盖一族宽度），据此提出 parallel-structure invariant：保持每次 launch 不可变则输出位与物理宽度无关。Vitamin-E 把不可变 launch 晚绑定到池化物理上下文，保证跨分配的逐位相等（零温贪心解码下 token 不变）：LLM 训练聚合吞吐最高 3.50x、推理 p99 延迟降 62.5%、后台训练吞吐 1.43x；同机制 TPOT-First 策略把 TPOT SLO 违例较吞吐导向策略降 46.1%。https://arxiv.org/abs/2603.15042
- **arXiv/Hummingbird (2601.04071v2, 02-10)**: 闭源 GPU 上的微秒级抢占——空间/时间共享都难同时保证 SLO 与效率，根因是闭源 GPU 缺乏细粒度任务调度。Hummingbird 通过抢占+空闲时间片收割：高优任务 SLO 达成率较 SOTA 空间共享提升 9.7x、较时间共享提升 3.5x；与独占执行相比，共置低优任务时高优任务 SLO 达成率仅降 <1%；低优任务吞吐较时间共享方案高 2.4x。https://arxiv.org/abs/2601.04071
- **arXiv/RLTune (2512.10271, 2025-12-11)**: 异构 GPU 集群的应用无关 RL 调度——现有调度器依赖离线 profiling 或应用特定假设，在异构集群上失效。RLTune 用 RL 驱动优先级 + MILP 做作业-节点映射，在 Microsoft Philly/Helios/Alibaba 生产 trace 上训练：GPU 利用率最高 +20%、排队延迟最高 -81%、作业完成时间（JCT）最高 -70%，且无需逐作业 profiling 即可跨负载泛化——云厂商规模化部署的实用路径。https://arxiv.org/abs/2512.10271

## 四、追踪结论（趋势线）

- **调度单元从"请求"升维到"工作流"**: SAGA（程序级调度，中间状态跨调用复用）+ LOCAL（端侧 Agent 连续学习，adapter 版本×KV 缓存协同）——延续昨日 Aries（Agentic serving 实验底座），Agent 负载迫使调度器放弃"每次调用独立"的抽象，中间状态生命周期与 KV 缓存复用成为一等调度输入；SAGA 明确量化代价（吞吐 -30% 换端到端 -1.64x），"延迟敏感优先"成为 Agent 场景默认取舍。
- **GPU 共享的第三个约束浮出：确定性**: 传统共享优化利用率（空间/时间），Vitamin-E 加"输出逐位不变"（并行结构不变量）、Hummingbird 加"微秒级抢占"（SLO 达成 9.7x）——确定性保证与抢占粒度成为共享技术能否落地的判据，直接服务"多租户 GPU 集群如何承诺 QoS"的平台级问题。
- **调度决策从规则/启发式走向学习与校准**: RLTune（RL+MILP，-81% 排队延迟）+ DriftSched（在线校准，估计误差 -38.8%）——生产 trace 训练 + 运行时反馈闭环取代静态优先级，与 Kubernetes 侧 DRA 的"声明式+账本式"路线互补：前者解决"怎么排最优"，后者解决"排了怎么算数"。
- **DRA 标准收敛确立：控制面标准化、数据面保留**: HAMi 转写为 DRA driver 是 K8s"先实现后标准化"的又一实例（Ingress→Gateway API 同构）；落地门槛（K8s ≥1.36 默认开启 + CDI + 驱动 440+）已大幅降低，但**拓扑感知放置缺口**（HAMi-DRA 无自有调度器）是显性工程欠账——NVLink 拓扑感知与 DRA 标准的融合是下一阶段看点。
- **国产算力调度栈开始融入国际标准体系**: HAMi 孵化 + 昇腾/燧原/海光 DRA driver 在途——国产芯片的"平台化"路径从自建调度栈转向"兼容国际标准 + 保留硬件差异化"，与昨日昆仑芯万卡交付（爱集微）形成"硬件供给+软件标准"双线。
