## 📡 本期核心信号

- **供电控制从"攻击面识别"走向"合规可证明"**：上期 Bit2Watt 证明负载→电网攻击面，本期 SolVRT 用形式化方法（STL 规范语言）综合出 correct-by-construction 的电压穿越（VRT）控制器，不可满足时还能定位"冲突前沿"并计算最小硬件/负载改动量——数据中心供电侧从"事后监控"进入"设计期可证明合规"，与 800V HVDC/供电主题直接衔接
- **推理调度器目标函数新增两个显式预算维度**：Cascade 把"剩余 SLO 预算"作为单一信号联合协调请求调度与跨层 KV 管理（goodput 最高 +2.4×、SLO 违规 -40%）；Routing to Cleanest Grid 用 MOER 边际碳排放信号做实时跨区域路由（主配置 GPU 碳排放 -50.9%）——延迟预算与碳预算成为与吞吐/公平并列的一等公民
- **DRA 正式接管 GPU 共享的"编码层"，HAMi 职责拆分重构**：DRA 在 K8s v1.34 GA、v1.35 默认启用，consumable capacity 让 pod 原生请求设备内存切片；HAMi（7/15 进 CNCF incubating）保留容器内 CUDA 粒度执行、把分数请求编码迁到 DRA 之上（拆 3 repo）——上期预告的 KubeCon China DRA vs HAMi 辩论已提前在社区落地
- **B300 代际实操一手信号**：首份公开的 16×B300 两节点全参微调现场报告——NCCL 挂起时 utilization% 仍读 100%（"假存活"陷阱在 B300 复现）、以板卡瓦数为分诊依据优于利用率、epoch-end 死锁用 2.7 秒运行前不变量门+外部 watcher 把"数小时静默失败"转为"即时拒绝"

## 📄 arXiv 论文（cs.DC · 8/6-8/7 提交，2608 批次）

- **SolVRT: Synthesizing Voltage Ride-Through Controllers for Data Centers（2608.07289，8/7）**: 电网故障时数据中心需满足 VRT 电网规范（保持并网一段时间、维持有功功率下限、恢复期限内恢复负载），但系统化设计与认证耦合的时序+运行约束一直缺失；SolVRT 用 STL（信号时序逻辑）表达规范+数据中心功率拓扑模型，编码为控制器综合问题——可解则输出 correct-by-construction 控制器、不可解则给出证明；后者提供诊断：追踪设施"冲突前沿"、隔离违规条款、计算实现合规的最小硬件/负载改动；200MW 数据中心+140 总线输电系统闭环仿真验证——供电侧"设计期可证明合规"范式，与 08-10 Bit2Watt 攻击面互补为攻防闭环。https://arxiv.org/abs/2608.07289
- **Cascade: Exploiting SLO-Aware latency budget for fair and high goodput LLM inference serving（2608.06557，8/6）**: 同一 SLO 下的请求执行成本差数量级（输入/生成长度、可复用 KV 状态），"剩余 SLO 预算"（SLO−预测剩余服务时间）各不相同；Cascade 用单一 per-request 预算联合协调调度+跨层 KV 管理——调度器优先剩余预算小的请求，内存管理器用同一预算决定非驻留 KV 状态是恢复/预取/驻留 HBM/重算；把排队与数据搬运开销导向能吸收的请求，三模型生产 trace 下 goodput 最高 +2.4×、SLO 违规较 vLLM FCFS 降低 40%——推理可靠性从"调度序"走向"预算驱动的调度×KV 联合控制"，呼应 08-10 记忆线的 Cascade×HorizonServe 合流判断。https://arxiv.org/abs/2608.06557
- **Routing LLM Inference to the Cleanest Grid in Real Time（2608.06188，8/6）**: 推理是快速增长的电力负载，跨区域/跨时段边际碳强度差 >10×，请求放置成为无重训/无硬件改动的减排杠杆；用 NVIDIA DCGM 遥测+实测并发曲线做 per-request 能耗归因（非铭牌 TDP），MOER 信号驱动的跨区域推理路由实况验证无调度失败；回放 CONUS 全美车队 12 个月小时级 MOER，主配置下 GPU 归因运营碳排放较 round-robin 降 50.9%（95% CI 48.5-53.3%），其中时段路由贡献约 40%；实践观察：跨区域比较应按绝对 MOER 而非各区域归一化百分位排序——"调度器×电网"交叉新维度，为算力平台碳预算调度提供落地基线。https://arxiv.org/abs/2608.06188
- **Operating Multi-Node Full Fine-Tuning on NVIDIA B300（2608.05944，8/6，现场报告）**: 16×B300（两节点，FSDP/ZeRO-3）全参微调 Qwen3-32B，首批公开现场报告，四件套：①B300 校准板卡瓦数分诊表——区分计算/通信/数据饥饿/checkpoint-死锁/空闲（NCCL hang 时 utilization% 读 100%，利用率指标失效）；②诚实负结果——每步 NFS 读取与预分词本地缓存持平（~53k tok/s，语料在页缓存、任务 compute-bound），此前"吞吐崩塌"实为 NFS/CPU 争用而非存储介质限制；③4/8/16-GPU 强扩展与 GPU 小时数校准数据（近线性）；④epoch-end NCCL 死锁（per-rank token 打包不平衡）→2.7 秒运行前不变量门+外部 watcher 把数小时静默失败转为即时拒绝——传递性结论：数据依赖型 DP 任务要看功率而非利用率、运行前验证不变量（smoke test 通过≠安全全量运行）。https://arxiv.org/abs/2608.05944
- **TensorCast: The Missing Tensor Management Layer in LLM Infrastructure（2608.06007，8/6）**: LLM 基础设施中张量不仅是计算数据、更是跨分布式组件共享的持久状态；现有系统把权重加载/KV 管理/checkpoint 同步各自深度耦合进执行引擎、网络或存储后端，形成孤立 silo，阻碍策略复用与组合；TensorCast 提出张量生命周期管理作为缺失的抽象层——控制面/数据面分离范式在"张量移动"上的落地（上期 08-10 已记录其控制面/数据面分离第三次落地信号），为权重/KV/checkpoint 统一管理与新硬件适配提供解耦点。https://arxiv.org/abs/2608.06007
- **HiSparse: Scaling Sparse-Attention Decoding with Hierarchical KV Cache Management（2608.07009，8/7）**: Top-k 稀疏注意力使长上下文 decode 计算廉价（每步只读数千个 KV），但服务系统仍把整条 KV 留在 HBM 以保证任意位置可选——请求内存账单随全上下文增长，decode 在算力耗尽前先撞容量墙；HiSparse 提出精确、索引器无关的分层 KV：分层保留各位置可选择性（L0 HBM 热层→深层分层存储），实现 KV 四层命运的工程化（互证 08-10 记忆线的 KV 四层命运论），让稀疏注意力"计算便宜"真正转化为"内存便宜"。https://arxiv.org/abs/2608.07009
- **OPSche: A Kubernetes Scheduler Plugin for Cluster-Wide Placement Optimisation（2608.06987，8/7）**: 默认 K8s 调度器做快速本地决策导致资源碎片化、集群利用率下降与过度供给；外部求解器可算全局放置计划但上游集群强制执行难（无原生跨节点抢占、并发调度不一致、替换默认调度器脱离上游演进）；OPSche 作为 Scheduling Framework 插件提供集群级全局放置优化而不脱离上游——算力平台调度"本地贪心 vs 全局最优"张力的工程化中间解，与 08-07 记录的多租户公平调度问题互补。https://arxiv.org/abs/2608.06987
- **G-Power: Architecture-level GPU Power Modeling with Aggregated Knowledge Foundations（2608.06870，8/7）**: 架构级 GPU 功耗模型（如 AccelWattch）因功率标签采集耗时仅用简单 microbenchmark 训练导致精度不足；G-Power 聚合已知 GPU 的知识基础（aggregated knowledge foundation）做迁移/预训练，以架构参数快速估算功耗——供电/散热设计早期的功耗快速评估工具，为算力平台功耗预算与 PUE 优化提供模型侧支撑。https://arxiv.org/abs/2608.06870

## ☸️ CNCF / K8s 生态（8/3-8/7 窗口，与上期 4 条不重复）

- **Does Kubernetes DRA Replace HAMi?（8/7，Mesut Oezdil）**: 官方定调 GPU 共享的 API 演进——旧 device plugin 词汇只有 `nvidia.com/gpu: 1`（整卡，take it or leave it）；HAMi（7/15 CNCF TOC 接受进 incubating）用 mutating webhook+scheduler extender+注解+容器内执行表达"8000 MiB+10% GPU 且限制生效"；DRA v1.34 GA、v1.35 默认启用，consumable capacity 让 pod 原生向调度器请求设备内存切片；结论：DRA 吸收"分数请求编码"（scheduler 可见），HAMi 保留"容器内 CUDA 调用粒度执行"（DRA 从未设计做）；HAMi 已按此拆分在 DRA 之上重建编码（跨 3 repo）——KubeCon China（9/7-9 上海）DRA vs HAMi 议题的前置答案。https://www.cncf.io/blog/2026/08/07/does-kubernetes-dra-replace-hami/
- **OpenCost 1.121.0: First-of-a-kind Kubernetes inference cost tracking（8/5）**: 平台团队"看不清 AI 推理成本"（只见基础设施支出+token 吞吐，两者无连接）——自建 vs SaaS、模型性价比、哪个团队 Agent 负载吃预算均无数据；OpenCost（incubating）集成 llm-d（sandbox，K8s 分布式 LLM 推理），从实际资源消耗推导 per-model/per-token 成本；并强调 Cost ≠ Price（SaaS 定价可能低于成本抢份额或高于成本收溢价，企业真实成本是供应商价格）——算力平台的"成本可观测性"补位，回应执行层对 AI ROI 问责。https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/
- **When Kubeflow meets Cilium: Debugging 60% idle GPUs in Kubernetes（7/23，Adobe 两位 Golden Kubestronaut）**: 分布式训练"全绿但半死不活"静默故障模式——所有 pod 健康、无崩溃/OOMKill/日志异常，但 60%+ GPU 空闲且训练从未开始；根因是训练协调器与 worker 间网络策略（Cilium）误阻断（类比：满场乐手就位但指挥被防火门锁在另一侧）；健康检查全绿≠在计算——与 B300 报告的"utilization% 100% 但 hang"互为镜像，算力平台监控须验证"命令完成率/实际计算"而非表面状态。https://www.cncf.io/blog/2026/07/23/when-kubeflow-meets-cilium-debugging-60-idle-gpus-in-kubernetes/
- **Kubeflow SDK evolution: One million downloads and counting（8/3）**: Kubeflow SDK 演进达 100 万下载里程碑——ML 平台 SDK 生态成熟度信号，云原生 ML 工作流从"实验脚本"走向"工程化 SDK 接口"，为算力平台的用户侧接入层提供生态基准。https://www.cncf.io/blog/2026/08/03/kubeflow-sdk-evolution-one-million-downloads-and-counting/
