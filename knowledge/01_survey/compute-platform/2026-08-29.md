## 一、平台调度研究前沿（arXiv：08-27 提交可见，索引延迟确认恢复）

- **VPP: Virtual Pipeline Parallelism for Efficient Chunked Prefill in Long-Context LLM Inference**（https://arxiv.org/abs/2608.26523, 08-27 新提交）: 等尺寸 chunk 的 chunked prefill 流水线存在**延迟失衡**——后段 chunk 要 attend 更长前缀 KV cache、注意力成本更高，产生流水线气泡；现有动态 chunk 缩放（DCPP）以调度开销换均衡。VPP 用虚拟流水线并行化解。平台视角：**长上下文成为主流负载后，prefill 阶段均衡成为推理平台调度新维度**（与 08-28 本组 OpScale 算子级扩缩容同向：调度粒度继续细化）。
- **Benchmarking Confidential Computing Performance on NVIDIA Blackwell GPUs**（https://arxiv.org/abs/2608.26575, 08-27 新提交）: 在 B200 上用 Intel TDX 机密 VM + NVIDIA Confidential Computing 配对测量 LLM 推理/训练在 TEE 内的性能开销。平台视角：**多租户算力平台的机密计算（TEE）能力正在从"安全选项"变为"平台一等公民"**——Blackwell 的 CC 栈 + TDX 组合是首个可量产的 GPU TEE 基准，多租户隔离与性能损失的权衡将被量化。
- **Distributed Training using an Intelligent Network**（https://arxiv.org/abs/2608.26453, 08-26）: WAN 分布式训练中网络带宽/延迟/拓扑不均制约参数交换；提出让**网络成为训练的主动参与者**——multicast 复制出站流量 + 线内 FPGA 聚合。平台视角：**"网络即计算参与者"从数据面升级到训练语义面**，与 hardware 组 08-28 的 CPO/scale-up 互联主题互补（硬件侧互联提速 vs 软件侧网络参与计算）；对多地域智算协同（东数西算场景）有直接参考。
- **FLINT: High Bandwidth Flash for Capacity-Scalable LLM Inference**（https://arxiv.org/abs/2608.25062, 08-25）: 单加速器/小节点推理被加速器内存容量锁死；HBF（3D 堆叠 NAND，多 TB 近加速器容量）作为 HBM 的容量扩展层。与 tech 组 08-29 已收录 Beyond Capacity（HBF 双路专家投递，2608.14333）互证：**HBF 闪存层是"加速器内存容量危机"的共识解法**——本组补平台视角：容量可扩展性决定单节点可部署模型规格，智算平台选型需把 HBF 纳入存储层次设计（HBM→HBF→远端）。
- **Token Management in Multi-Tenant AI Inference Platforms**（https://arxiv.org/abs/2603.00356, 02-27）: 提出 **token pools 控制面抽象**——用 token 池代表推理容量配额，替代"专用端点闲置 + rate limit 忽略异构成本"的旧模式。与 08-27 本组"Token 经济"直接互证：**token 作为计量/配额/计费统一语义正在从商业叙事走向学术控制面抽象**——平台侧应把 token 配额机制（而非 QPS/实例数）作为多租户控制面的一等抽象。
- **Characterization-Guided GPU Fault Resilience in NVIDIA MPS**（https://arxiv.org/abs/2605.26461, 05-26）: MPS 让多进程并发共享单 GPU，但**故障韧性弱：一个进程故障可终止所有共运行进程**，阻碍多租户 GPU 集群采用。平台视角：**GPU 共享技术（MIG/MPS）的故障隔离是平台级 RAS 盲点**——共享越细、爆炸半径越大；与 08-28 本组 Slasher/电力灵活性"平台能力维度扩展"呼应，容错能力需要下沉到共享原语层。
- **WarmServe: Enabling One-for-Many GPU Prewarming for Multi-LLM Serving**（https://arxiv.org/abs/2512.09472, 2025-12-10）: 共享 GPU 集群多模型部署提升利用率但牺牲 TTFT；WarmServe 用对未来负载特征的感知做 GPU 预热（one-for-many）。**与今日 CNCF Adobe 预测性扩缩容文章形成"预热-扩容"双胞胎**：服务侧预热权重 vs 平台侧预热节点，同一"提前就绪"思想在两层落地（详见第二节）。
- **Execution Envelopes: A Shared Admission Contract for Backend AI Execution**（https://arxiv.org/abs/2605.08267, 05-08）: 企业 AI 后端请求异构化（部署/推理/评测/数据移动/agent 工作流），各服务请求形态不一导致难以挂接统一准入行为（日志/治理/资源记账/授权策略）。提出共享准入契约。平台视角：**agent 工作流时代的平台准入控制面需要"统一契约 + 异构执行"**——与 2608.26453 智能网络同属"AI 负载形态变化倒逼平台抽象升级"主线。

## 二、云原生算力平台动态（CNCF：08-28 两篇新文章已由 tech 组收录，本组补平台视角增量）

- **交叉引用（tech 组已收录）**: 「Scale before the spike: Predictive autoscaling for GPU workloads on Kubernetes」（https://www.cncf.io/blog/2026/08/28/scale-before-the-spike-predictive-autoscaling-for-gpu-workloads-on-kubernetes/, 08-28, Adobe Golden Kubestronaut）。本组平台视角四条增量：**① 物理根源量化**——GPU 节点供给比 CPU 慢 3-5 倍（固件加载/驱动初始化/CUDA 就绪），反应式 HPA"等需求出现再下单"对 GPU 是灾难（06:00 尖峰→06:45 才跑起来，尖峰已过）；**② Predict-Provision-Absorb 三件套**——Bi-LSTM（2 层 64→32 units）控制器内嵌 TensorFlow Lite 推理（无外部 ML 平台/无 CRD）、滚动 std 自适应突发检测兜底、渐变扩容限速 20 pods/min（防 etcd thrash + thundering herd），目标利用率 70% 留余量；**③ 验证数据**——shadow 模式 500+ 小时，T+10min 预测精度 85% 落在 ±10% 内，突发检测 9/10 捕获 + 2 误报，23/23 校验通过，模拟尖峰提前 11 分钟预测；**④ 作者自省**——"well-tuned ARIMA 大概用 10% 基础设施拿到 80% 效果"，复杂度不是特性——**平台工程"够用即用"的务实信号**，与 08-27 本组"利用率优先"主线互证：扩缩容从反应式走向预测式是 GPU 供给物理的必然。
- **交叉引用（tech 组已收录）**: 「Your Kubernetes platform is ready for containers. Is it ready for AI?」（https://www.cncf.io/blog/2026/08/28/your-kubernetes-platform-is-ready-for-containers-is-it-ready-for-ai/, 08-28, Vultr Member Post）。本组平台视角增量：**① 就绪度差距量化**——CNCF 2025 年度调查：66% 组织用 K8s 承载部分/全部 genAI 推理负载，但仅 7% 组织每日部署 AI 模型；2025 State of AI in Platform Engineering：35% 平台团队仍不编排 AI 工作负载——**"跑在 K8s 上"≠"平台就绪"，66% vs 7% 的落差即平台能力缺口**；**② 五件要事清单**——资源模型扩展（DRA 声明式请求异构加速器）、CI/CD 扩展到模型生命周期（Code+model+config → evaluate → deploy → observe → update）、观测从集群下沉到工作负载（加速器利用率/调度排队/推理延迟/模型加载时间）、golden path 自我服务、AI 作为普通生产工作负载；**③ 对国产平台含义**——平台就绪度（而非硬件规格）正成为评测标准，国产智算平台的自服务/可观测性/模型生命周期管理是下一竞争面。

## 五、追踪结论（趋势线）

- **"预测式扩缩容"成为平台层新共识（第 3 个互证点）**: Adobe 生产实践（GPU 供给慢 3-5 倍→预测式扩容）+ WarmServe（权重预热）+ ElastiCo（弹性配置）+ OpScale（算子级扩缩容）——**学术与产业两侧同周收敛于"提前就绪"**：GPU 供给物理（分钟级）与需求到达（秒级）的时间差决定了反应式扩容必然失效，预测式（shadow 验证 + 渐变限速 + 目标利用率 70%）是平台侧通用解法。
- **token 作为计量/配额统一语义完成"商业→学术"闭环**: 08-27 Token 经济（商业叙事）+ 08-29 token pools 控制面抽象（学术方案）+ 08-28 CNCF AI factory（GPU-seconds/OpenCost 计量）——**三种计量语义（token/GPU-seconds/实例）并存，平台计量层设计成为多租户平台的分水岭**。
- **平台就绪度（而非硬件规格）成为评测主轴**: Vultr 文章 66% vs 7% 数据 + "GPU 利用率 60% 闲置"（KubeCon India 议题）——**平台能力（调度/观测/自我服务/模型生命周期）正取代硬件指标成为算力平台竞争的评判标准**；对国产平台：池化、计量、预测式扩缩容、TEE、RAS 故障隔离是五大软件能力抓手。
- **GPU 共享的 RAS 盲点浮现**: MPS 故障级联（一损俱损）论文揭示共享粒度与故障隔离的矛盾——**共享越细、爆炸半径越大**，多租户平台需在共享原语层内建容错（而非集群层事后恢复）。
