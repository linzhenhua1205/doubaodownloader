## 1️⃣ 👁️ ARGUS — 万卡级生产集群 always-on 追踪与性能诊断

**来源**: arXiv:2606.20374 (2026-06-18, v2 2026-07-08)
**链接**: https://arxiv.org/abs/2606.20374

### 问题

大规模LLM训练需要**always-on、细粒度的可观测性**才能做有效的性能诊断。粗粒度的资源监视器无法定位根因，细粒度的剖析器（profilers）开销高达 **5%-30%** 且产生海量追踪数据，在大型生产集群中无法常开部署。

### 核心设计

ARGUS 沿**训练调用层次**分解观察：

| 层次 | 观察内容 |
|:-----|:---------|
| CPU call stacks | 主机侧调用栈 |
| Framework semantics | 框架语义（如 PyTorch 算子） |
| GPU kernel execution | GPU kernel 执行细节 |

关键技术：

- **3,700× 压缩**：原始 kernel 事件从 **10 MB 压缩至 2.7 KB** per rank per step
- **渐进式诊断框架**：自动隔离异常窗口 → straggler rank → 退化 kernel，分三级迭代
- **生产部署验证**：在 **10,000+ GPU** 生产集群上运行超 **6 个月**

### 覆盖的异常类型

| 异常类型 | 说明 |
|:---------|:------|
| Compute stragglers | 计算慢节点 |
| **Link degradation** | 🔥 **链路降级**——与 NCCL 层通信性能直接相关 |
| Pipeline-bubble amplification | 流水线气泡放大 |
| FlashAttention JIT stalls | JIT 编译停顿 |
| Compute stragglers masked by communication | **被通信症状掩盖的计算慢节点**——最难诊断的类别 |

### 性能数据

| 指标 | 数值 |
|:-----|:------|
| Always-on 开销 | **< 2%** 综合开销 |
| 数据压缩比 | **~3,700×** (10 MB → 2.7 KB/rank/step) |
| 部署时长 | **6+ 个月** 持续运行 |
| 集群规模 | **10,000+ GPU** 生产集群 |
| 诊断模式 | 三级渐进: iteration-time → phase-level → kernel-level |

### 意义

- **与 StageFrontier (07-15) 互补**：StageFrontier 是轻量 always-on 信号（<0.2%开销，定位"哪里慢了"），ARGUS 是更完整的生产级 always-on 追踪系统（<2%开销，定位"什么 kernel 慢了"）——两者可部署在不同抽象层
- **与 Guard (07-15) 互补**：Guard 从节点健康角度检测 fail-slow，ARGUS 从 kernel 执行角度检测链路降级和 JIT stall
- **link degradation 检测** 直接服务于 NCCL/RDMA 互联诊断，对万卡集群运维极具价值

## 2️⃣ 🤖 CUCo — Agent自动计算-通信协同设计的CUDA Kernel框架

**来源**: arXiv:2603.02376 (2026-03-02, v2 2026-06-03)
**链接**: https://arxiv.org/abs/2603.02376

### 问题

分布式 LLM 训练和推理中的**计算和通信传统上被孤立优化**。专家手工制作的系统（DeepEP、FLUX、TokenWeave）虽然展示了协同设计的潜力，但**需要深厚的系统专业知识和硬件特定调优**。

### 核心方案

**CUCo** 是一个自动化计算-通信协同设计的 **Agentic 框架**，核心包含：

| 组件 | 角色 | 说明 |
|:-----|:------|:------|
| 结构化的设计空间形式化 | 基础层 | 将协同设计问题转化为可搜索空间 |
| **Fast-path agent** (正确性优先) | 快速生成可靠基线 | 快速迭代保证正确性的参考实现 |
| **Slow-path agent** (进化驱动) | 探索高性能策略 | 基于进化算法搜索最佳策略 |

### 发现

在 DeepSeek-V3 MoE 层上，CUCo **自主发现了一种两流重叠策略**——将 dispatch 通信隐藏在本地计算之后——这在之前需要 DeepEP 等专业系统专家手工优化。

### 性能数据

| 指标 | 数据 |
|:-----|:------|
| 速度提升 | **最高 1.57×** (四个多GPU工作负载) |
| 单工作负载成本 | **< $10** LLM推理成本 |
| 发现策略 | 两流重叠策略 (dispatch behind local compute) |
| 自动化程度 | 全自动，无需人工系统专家介入 |

### 意义

- **AI Agent 设计 AI 通信库的开始**：用 AI 自动探索计算-通信协同设计空间，替代人类专家手工调优
- **低成本高收益**：低于 $10 即可发现一种有价值的策略——这使得自动化 Kernel Co-design 变得经济可行
- 与 [DITRON (07-02)](2026-07-02.md) 互补——DITRON 从编译器角度做分布式 tile 级优化，CUCo 从 agent 角度做 kernel 级协同设计

## 3️⃣ 🌐 ScaleAcross Explorer — Meta跨数据中心AI训练通信优化

**来源**: arXiv:2605.24326 (2026-05-22) | Minghao Li et al. (Meta)
**链接**: https://arxiv.org/abs/2605.24326

### 背景

LLM 训练的快速扩展需要将 GPU 资源分布到**多个数据中心建筑甚至多个区域**（称为 **"scale-across" 训练**）。Meta 基于跨数百个数据中心、数十万 GPU 的生产经验，提出了这个跨数据中心训练的系统设计方案探索框架。

### 三大关键设计维度

| 维度 | 关注点 | 说明 |
|:-----|:--------|:------|
| **① Parallelism placement** | 并行策略放置 | 如何将模型划分到跨数据中心的 GPU |
| **② Parallelism scheduling** | 并行调度 | 跨域通信的时序优化 |
| **③ Network layer technologies** | 网络层技术 | 数据中心间的互联技术选择 |

### 核心产出：ScaleAcross Explorer

一个考虑三个设计维度**相互作用**、整体优化跨数据中心训练的优化器。

### 性能数据

| 对比方案 | 加速比 |
|:---------|:------|
| 对比 Meta 生产配置 | **最高 64.62% 训练加速** |
| 对比 SOTA 基线 | **最高 37.59% 训练加速** |
| 覆盖场景 | 跨多种设计点的广泛测试 |

### 意义

- **从 Meta 生产一线来的视角**：跨数据中心训练不再是理论问题，而是 Meta 等超大规模 AI 公司已必须面对的现实
- **与 [BACE-Pipe (07-07)](2026-07-07.md) 互补**：BACE-Pipe 关注跨区域场景下的 PP 编排调度（JCT降低 27.9%-64.7%），ScaleAcross Explorer 给出更三维度的设计空间全局视图
- **与 [CCCL (06-29)](2026-06-29.md) 互补**：CCCL 用 CXL 替代 RDMA 做跨节点通信，ScaleAcross 在生产中面对现实网络分层做选择
