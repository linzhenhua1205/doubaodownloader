## 1. 📏 NVIDIA NVbandwidth — GPU互联带宽测量官方工具正式发布

- **来源**: [NVIDIA Technical Blog](https://developer.nvidia.com/blog/nvidia-nvbandwidth-your-essential-tool-for-measuring-gpu-interconnect-and-memory-performance/) (2026-04-14)
- **作者**: Eva Sitaridi, Banajit Goswami (NVIDIA CUDA Performance团队)
- **GitHub**: [NVIDIA/nvbandwidth](https://github.com/NVIDIA/nvbandwidth)（开源）

### 核心能力

NVbandwidth 是一个 **CUDA-based GPU互联带宽/延迟基准测试工具**，填补了NCCL-tests专注于collective性能、cuda-samples P2P测试功能单一的中间空白。

### 测试能力矩阵

| 测试类别 | 子类型 | 说明 |
|:---------|:-------|:------|
| **单方向** | H2D / D2H / D2D | CPU↔GPU、GPU↔GPU |
| **双方向** | Host↔Device / Device↔Device | 同时双向带宽 |
| **多GPU** | A2O / O2A / A2H / H2A | All-to-One, One-to-All等 |
| **多节点** | P2P跨节点 | 需MPI + IMEX服务 |
| **延迟** | Host↔Device / Device↔Device | 精确到微秒级 |

### 两种拷贝方法

| 方法 | 机制 | 特点 |
|:-----|:-----|:------|
| **Copy Engine (CE)** | 使用CUDA异步memcpy函数 | 反映硬件DMA实际能力 |
| **Streaming Multiprocessor (SM)** | 使用自定义CUDA kernel | 反映SM实际可达到的搬运带宽 |

### 性能数据示例（多节点NVLink系统）

8-GPU MNNVL 系统 P2P Read CE 带宽：

```
GPU(row) -> GPU(col) 带宽 (GB/s):
   0      1      2      3      4      5      6      7
0  N/A  397.4  397.4  397.6  397.5  397.5  397.7  397.6
1 397.7   N/A  397.4  397.5  397.5  397.5  397.5  397.6
...
```

**每对GPU间稳定在 ~397.5 GB/s**，说明NVLink全带宽可达。

### 工程意义

1. **开源 + 官方维护**: 首次提供官方统一互联测量工具，替代社区拼凑方案
2. **拓扑无关设计**: 自动发现GPU拓扑，无需用户手动指定
3. **JSON输出**: `-j` 参数直接输出JSON，便于自动化测试流水线
4. **生产部署验证**: 支持HPG（硬件性能保证）验收测试

## 2. 🔄 MoE-Prefill (AsyncEP) — 用权重AllGather替代激活AlltoAll，MoE预填充通信范式转换

- **来源**: [arXiv:2605.02960](https://arxiv.org/abs/2605.02960) (2026-05-02, v1)
- **作者**: Zhaoyuan Su, Olatunji Ruwase, Karthik Ganesan, Aurick Qiao, Samyam Rajbhandari, Juncheng Yang, Yue Cheng, Yuxiong He (Microsoft + 高校)

### 核心洞察

**关键观察**: MoE预填充（prefill）的单层前向传播时间较长（大batch），足够**在后台把专家权重流式传输过来**。

现有方案的痛点：每层都需要一次 **activation AlltoAll**，将token路由到对应的专家GPU上。当全连接操作变为通信瓶颈时，AlltoAll延迟直接拖慢整个预填充。

**AsyncEP的核心反转**: 不把token送给专家，**把专家权重送给token** —— 用异步权重 AllGather 替换 Activation AlltoAll，与计算完全重叠。

### 设计方案

| 维度 | 传统EP (AlltoAll) | AsyncEP (权重AllGather) |
|:-----|:-----------------|:------------------------|
| 通信内容 | 激活张量（token数据） | 专家权重参数 |
| 通信模式 | AlltoAll（全对全） | AllGather（一对多广播） |
| 与计算关系 | 串行，前向需等AlltoAll完成 | 异步，权重加载可与计算完全重叠 |
| 依赖条件 | 硬件拓扑感知路由 | 预填充大窗口（≥4K tokens） |
| 适用场景 | 训练+推理解码 | 预填充推理 |

### 性能数据

| 对比基线 | 吞吐提升 | 模型 | 配置 |
|:---------|:---------|:------|:------|
| vs 最强分布式基线 | **1.35-1.37×** | Qwen3-235B-A22B | 4种硬件/精度配置 |
| vs 最强基线（长上下文） | **高达1.59×** | Qwen3-235B-A22B | 长上下文合成负载 |
| Per-GPU MFU | **29.8-36.2%** | — | 预填充效率大幅提升 |

**附加机制**:
- **prefix-aware routing**: 结合物理推导的饱和阈值，避免过度路由
- **true-FLOPs负载跟踪**: 实时感知各GPU实际计算负载，而非token数量

### 工程意义

1. **范式等级发现**: 揭示了一个被忽视的基本事实——预填充的计算窗口足够大，不需要低延迟路由，需要的只是带宽
2. **对网络架构的影响**: 如果MoE推理普及AsyncEP，**AlltoAll优化优先级下降**，AllGather和Broadcast带宽将成为新瓶颈
3. **与vLLM/TensorRT-LLM集成路径**: 论文未展示集成，但前缀感知路由+AsyncEP的组合对生产推理系统有直接吸引力

## 3. 🧩 BrownoutMoE — 结构感知专家分组，RL优化的MoE推理效率

- **来源**: [arXiv:2607.04164](https://arxiv.org/abs/2607.04164) (2026-07-05)
- **作者**: Yi Ding, Minxian Xu, Zhengxin Fang, Kejiang Ye, Chengzhong Xu

### 核心洞察

MoE推理中，**热专家和冷专家的访问极不平衡**：少数热专家处理大部分路由token，而冷专家几乎闲置。现有方案专注于运行时调度（overlap/kernel fusion），但**未触及专家结构的根本问题**。

BrownoutMoE引入服务计算中的"brownout"（限电）概念——**选择性关闭冷专家，将token重组到剩余专家组中**。

### 设计方案

| 组件 | 方法 |
|:-----|:------|
| **专家分组** | RL强化学习发现最优分组策略，最小化精度损失 |
| **蒸馏补偿** | grouping-consistent distillation，生成可直接部署的模型 |
| **兼容性** | 与标准推理管线完全兼容（不修改推理引擎） |

### 性能数据

| 指标 | 数值 |
|:-----|:------|
| 精度退化减少 | **降低高达71.4%**（vs直接分组基线） |
| 吞吐提升 | **最高2.24×** |
| 方法 | RL发现分组策略 + 蒸馏补偿 |
| 兼容性 | 兼容标准推理管线，无需修改引擎 |

### 工程意义

1. **与ELDR（arXiv:2607.00466, 7-12报告）互补**: ELDR优化路由均衡，BrownoutMoE重组专家结构——两个层面均可独立实施
2. **对硬件的影响**: 如果推理时实际活跃专家数可显著减少，**单节点可承载的MoE模型规模增大**，减少跨节点通信
3. **对生产运维的影响**: 动态分组+蒸馏，意味着MoE模型可以**按负载特征做结构适配**，不同场景部署不同专家组
