## 1️⃣ 🌐 Agora: 互联网级集体预训练 — Protocol Learning宣言 (arXiv:2607.13332) 🔥

- **来源**: arXiv:2607.13332, "Agora: Collective and Permissionless Internet-Scale Pretraining of Large Language Models" (2026-07-14)
- **作者**: Gil Avraham, Violetta Shevchenko, Hadi Mohaghegh Dolatabadi 等 (11人)
- **标签**: `Protocol Learning` · `Internet-scale Training` · `Permissionless` · `Fault-tolerant` · `Pipeline Parallel` · `Decentralized`

### 背景与核心问题

千亿至万亿参数大模型训练被限定在数据中心：DP/MP 假设同构加速器、高速互联、单一编排实体。前沿模型开发高度集中于少数能组装此类集群的机构。

与此同时，大量计算资源被闲置——异构、可回收、个人持有的消费级/专业级 GPU，仅通过互联网连接。

> **Agora 的命题**: 能否让这些 **"野生"GPU** 高效参与前沿模型训练？

### Agora 系统设计

#### 核心机制: Protocol Learning

Agora 提出 **Protocol Learning** 概念：

| 维度 | 方案 | 与传统区别 |
|:-----|:-----|:----------|
| **模型分片** | 带宽高效 PP（Pipeline Parallel）跨互联网链路 | 每个参与者只持有模型的一个 stage |
| **所有权** | 无单一实体持有完整权重 | 区别于 centralized training |
| **训练产出** | 集体训练、集体拥有的模型 | 经济可持续的开源前沿模型 |

#### 三大技术支柱

| 支柱 | 具体方案 | 应对挑战 |
|:-----|:---------|:---------|
| ① **通信高效并行** | Bandwidth-efficient PP over internet-grade links | 互联网带宽远低于数据中心内网 |
| ② **异步优化** | 去中心化梯度异步更新，容忍延迟和丢包 | 参与者动态加入/离开 |
| ③ **容错集体操作** | Multi-party fault-tolerant collective ops | 节点随时可能掉线 |

### 实战验证: Pluralis-8B

Agora 的第一次端到端实证——**Pluralis-8B**：

| 指标 | 数据 |
|:-----|:------|
| **模型规模** | **8.6B 参数** |
| **训练数据** | 500B tokens FineWeb-Edu |
| **训练时长** | **40 天** |
| **贡献节点** | **330 个**（主要是消费级 GPU，互联网连接） |
| **节点行为** | 动态加入和离开 |
| **吞吐** | **~170k tokens/s** |
| **效率** | **4.2 tokens/TFLOP**（= 中心化 H100 基线 **63%**） |
| **收敛质量** | 与中心化参考运行**差距极小** |

### 意义与影响

1. **⚡ 范式级跃迁**: 从"谁有集群谁训练"到"谁有 GPU 谁参与"——协议级集体所有权
2. **💰 经济模型**: 首次证明 permissionless 训练的经济可持续性（脱离巨头垄断）
3. **🔗 集合通信新维度**: 互联网级容错 collective operations 不再是理论探讨，而是生产实践
4. **🆚 与 ScaleAcross Explorer (07-16)互补**: ScaleAcross 是 Meta 跨**数据中心**训练，Agora 是跨**任意互联网节点**训练

## 2️⃣ ⚙️ Piper: 可编程分布式训练系统 — 策略与运行时解耦 (arXiv:2606.11169)

- **来源**: arXiv:2606.11169, "Piper: A Programmable Distributed Training System" (2026-06-09)
- **作者**: Megan Frisella, Shubham Tiwari, Andy Ruan, Yi Pan, Parker Gustafson, Mat Jacob, Gilbert Bernstein, Stephanie Wang
- **标签**: `Programmable Training` · `IR` · `Strategy-Runtime Decoupling` · `DualPipe` · `Pipeline Parallelism`

### 背景与核心问题

当前部署系统面临两难：

| 路径 | 优点 | 缺点 |
|:-----|:-----|:------|
| **手工专家调优**（如 Megatron-LM） | 性能好 | 难以适配新策略 |
| **通用框架**（如 FlexFlow） | 灵活 | 仍绑定固定策略集，集成前沿 strategy 困难 |

**问题根因**: 并行策略（strategy）与运行时实现（runtime implementation）**高度耦合**。

### Piper 设计

#### 核心理念: 策略在 IR 层声明，运行时无关

```
用户声明 (annotations + scheduling directives)
    v
Piper IR (统一全局训练 DAG——包含所有计算和通信)
    v
编译器 -> 每设备执行计划
    v
分布式运行时 (strategy-agnostic)
```

| 组件 | 功能 |
|:-----|:------|
| **Model annotations** | 标注模型的计算图边界 |
| **Scheduling directives** | 声明并行策略（DP/PP/EP/ZeRO） |
| **Piper IR** | 统一全局 DAG：表示所有计算**和通信** |
| **编译器** | 从 IR 编译到每设备执行计划 |
| **Distributed runtime** | 策略无关的分布式执行引擎 |

#### 核心创新

1. **IR 级别的算通联合调度**: 通信不是后加的东西——Piper IR 从设计上就把通信作为一等公民
2. **策略即变换**: 每条 scheduling directive 对 IR 应用一种转换（transformation）
3. **运行时不感知策略**: 只执行编译后的每设备计划

### 性能验证

| 测试场景 | 结果 |
|:---------|:------|
| **ZeRO-3（标准策略）** | **性能持平**现有系统 |
| **DeepSeek-V3 DualPipe** | **额外性能和内存效率提升**（通过 IR 级算通联合调度） |

> DualPipe 是 DeepSeek-V3 创新的计算-通信重叠流水线策略，用 Piper IR 表示后可自动获得优于手工实现的调度效果。

### 意义

1. **🗺️ 策略创新加速**: 新并行策略只需在 IR 层声明 transformation，无需重写运行时
2. **🔄 与 DITRON (07-02) 互补**: DITRON 是编译器**自动搜索**最优策略（6-30%加速），Piper 让用户**可编程声明**策略——两者可组合
3. **🔧 与 DualPipe 的关系**: 第一次在通用框架中复现 DeepSeek-V3 核心创新之一的 DualPipe，验证了 IR 方案的表现力

## 3️⃣ ⚡ ASAP: 全异步解耦 MoE Prefill — CloudMatrix384 验证 (arXiv:2606.22541)

- **来源**: arXiv:2606.22541, "ASAP: A Disaggregated and Asynchronous Inference System for MoE Prefill" (2026-06-21)
- **作者**: Weiwei Chen, Shuang Chen, Lele Li, Qiang Hu, Han Li, Xin Ye, Ming Yan, Zhibin Yu
- **标签**: `MoE Inference` · `Disaggregated` · `Asynchronous` · `CloudMatrix384` · `Prefill` · `Expert Parallelism`

### 背景与核心问题

MoE 模型的在线推理系统通常采用**混合并行策略**：

| 阶段 | 并行策略 | 通信模式 |
|:-----|:---------|:---------|
| Attention | Data Parallelism (DP) | AllReduce（组内同步） |
| MoE FFN | Expert Parallelism (EP) | All-to-All（跨组通信） |

**问题**: DP 组与 EP 组之间需要**频繁的全局同步屏障**。在线推理场景下，请求到达率和序列长度的方差导致 DP 组间负载严重不均衡，**同步屏障阻塞 → TTFT 劣化 → 吞吐下降**。

### ASAP 设计

#### 核心理念: 彻底拆除同步屏障——Attention 和 MoE 阶段全异步执行

| 组件 | 方案 |
|:-----|:------|
| **架构** | 解耦 Attention + MoE 为独立阶段 |
| **执行模式** | **完全异步 pipeline** |
| **通信基元** | 专用异步通信原语（取代同步 collective） |
| **四大优化** | 请求调度 + 模型执行 四个协同优化 |

#### 与 DisagMoE (07-08 报告) 的关系

| 系统 | DisagMoE (训练) | ASAP (推理) |
|:-----|:----------------|:------------|
| 场景 | MoE **训练** | MoE **推理 prefill** |
| 解耦方式 | Attention 和 FFN 分到独立 GPU 组 | Attention 和 MoE 阶段异步 pipeline |
| 调度 | 多级 pipeline + uni-directional many-to-many | 全异步 + 专用原语 |
| 优化目标 | 训练吞吐（1.8×） | SLO-compliant 推理吞吐 |

### 性能数据

| 指标 | 数据 |
|:-----|:------|
| **硬件** | **CloudMatrix384 超节点**（华为） |
| **对比基线** | 最先进的同步推理方案 |
| **SLO合规吞吐提升** | **+90%** |
| **核心机制** | 拆除全局同步屏障 + 异步通信原语 + 请求调度协同优化 |

### 意义

1. **🧱 CloudMatrix384 实战**: 首次在华为超节点上验证 MoE 推理全异步方案
2. **🔧 DP 瓶颈终结**: 证明 MoE 推理的同步屏障可以被彻底拆除——Request drift 不再影响 TTFT
3. **🆚 与 AsyncEP 的区别**: AsyncEP 关注 DP 组内异步 AllReduce（07-14 报告），ASAP 关注 Attention↔MoE 间的全局同步消除——两个层面可叠加
