## 1️⃣ 🔐 NCCLbpf: 验证的NCCL插件策略执行 — 27% AllReduce提升 (arXiv:2603.11438 v2)

- **来源**: arXiv:2603.11438, "NCCLbpf: Verified, Composable Policy Execution for GPU Collective Communication" (2026-03-12, v2 2026-05-04)
- **作者**: Yusheng Zheng
- **标签**: `eBPF` · `NCCL Plugin` · `Verified Execution` · `Hot-Reload` · `B300` · `AllReduce`
- **录用**: 未标注会议

### 问题背景

NCCL插件在NCCL地址空间内以**未验证原生代码**执行，风险极高：
- Job崩溃 / 静默状态损坏 / 策略更新需要停机重启
- 当前无任何加载时验证机制可阻止恶意或有bug的插件

### NCCLbpf 设计

受内核可扩展性模型（eBPF）启发，将**用户态eBPF运行时**直接嵌入NCCL现有插件接口，**不修改NCCL本身**。

| 核心能力 | 技术细节 |
|:---------|:---------|
| **加载时静态验证** | 阻止不安全插件载入，所有通过的插件可保证不会导致NCCL崩溃或状态损坏 |
| **结构化跨插件映射** | 多插件可组合策略 + 闭环自适应调度 |
| **原子策略热更新** | 策略切换无需停机重启，零中断时间 |
| **禁用系统调用** | eBPF verifier 保证插件不执行危险系统调用 |

**与NCCL现有Tuner Plugin接口关系**: 直接嵌入`ncclTuner_v7_t`等接口，作为NCCL plugin的eBPF backend。

### 性能数据 📊

| 指标 | 数值 |
|:-----|:------|
| **每次Tuner决策开销** | **80-130 ns**（< 0.03% 集合延迟） |
| **安全验证覆盖** | 阻止所有测试的不安全插件行为（加载时） |
| **AllReduce吞吐提升** | **最高27%**（4-128 MiB消息范围 @ 8×B300 NVLink） |
| **策略热更新** | 原子替换，零中断 |
| **验证平台** | 8× NVIDIA B300 GPU，NVLink互联 |

**eBPF策略示例**: Message-size-aware eBPF策略在4-128 MiB范围内动态调整NCCL算法选择，相比NCCL默认策略提升27%吞吐。

### 意义与影响

1. **NCCL安全防线**: 提供了NCCL运行时的**Load-time Verification**机制——这是NCCL生态中首个"验证执行"方案
2. **生产级可组合策略**: 多个eBPF插件可通过cross-plugin maps组合（如拓扑感知+带宽感知+故障感知），形成闭环自适应调度
3. **与NCCL Plugin体系的关系**: NCCLbpf不是替代而是增强——它将未验证的native plugin升级为验证的eBPF plugin，保留了NCCL Plugin的可扩展性，消除了安全风险
4. **B300实测**: 在最新B300 GPU上的验证数据意味着对下一代硬件的直接适用性

### 可复用资源

- 首个在NCCL中嵌入eBPF的开源实现方案
- 非侵入式设计（不修改NCCL），可直接集成到现有NCCL部署

## 2️⃣ 🎯 Move the Query, Not the Cache: 跨实例MLA注意力的RDMA拓扑感知最优路由 (arXiv:2606.01502)

- **来源**: arXiv:2606.01502, "Move the Query, Not the Cache: Characterizing Cross-Instance Latent Attention Redistribution Across GPU Fabrics" (2026-05-31)
- **作者**: Bole Ma, Jan Eitzinger, Harald Köstler, Gerhard Wellein (FAU Erlangen-Nürnberg)
- **标签**: `MLA` · `Cross-Instance Attention` · `RDMA` · `Topology-Aware` · `H100` · `IBGDA` · `DeepSeek` · `KV Cache`
- **录用**: 未标注会议

### 核心洞察

跨实例KV cache系统传统采用 **"Move Cache"** 策略：将attention选中的KV块拉到请求GPU。但当使用**Multi-head Latent Attention (MLA)** 时，数学运算被翻转：每个token的K/V压缩为窄向量，**路由的query行仅~1 KB**，比它要attend的chunk还小。此时 **"Move Query"** 通常比"Move Cache"更便宜。

### 拓扑感知成本模型

**五阶段流水线**: Probe → Transfer → Compute → Return → Merge

| 阶段 | 成本组成 |
|:-----|:---------|
| **Probe** | 探测远端GPU延迟（选fabrics by latency，非峰值带宽） |
| **Transfer** | 传输query行（~1 KB MLA compressed） |
| **Compute** | 在远端GPU执行attention计算 |
| **Return** | 返回结果 |
| **Merge** | 合并回主GPU上下文 |

**核心成果**:
- **封闭式路由/取回/本地谓词**（closed-form route/fetch/local predicate）
- 在真实IBGDA（InfiniBand GPUDirect Async）上测量，模型追踪batched round-trip到 **~7%精度**

### 关键数据

| 场景 | Move Query | Move Cache |
|:-----|:-----------|:-----------|
| Decode阶段 | **数十微秒** round-trip | ~3 ms re-adaptation splice |
| 消息大小 | ~1 KB (MLA query) | 数十MB～GB级 (KV cache块) |
| 选fabrics依据 | Probe延迟 | 峰值带宽 |

### 普适性

**不限于MLA**: 凡是压缩或稀疏选择将attention缩成小chunk的架构都适用（DeepSeek-V3.2、V4、GLM-5.1）。扩展到新架构只需测两个系数：路由载荷大小和取回cache成本。

### 意义

1. **RDMA拓扑感知的新维度**: 不再仅以带宽选路径，而是以**Probe延迟**决定路由策略——这对GPU-initiated RDMA的设计产生直接影响
2. **深挖GIN/Device API的意义**: 实测IBGDA（即GIN的InfiniBand backend），证明了device-initiated RDMA的per-request nano-scale延迟优势
3. **跨实例attention的经济性**: 在Agentic Workloads场景下（多个sub-agent查询同一个大代码库，复用同一组KV块），每个请求都涉及跨实例路由，Move Query优势会被放大多个数量级
4. **对推理框架启示**: 未来vLLM/TensorRT-LLM的跨实例attention策略可能需要从带宽导向转向延迟+带宽双导向

### 补充数据

模型在H100多节点集群上实测验证，使用真实IBGDA配置。

## 3️⃣ ⚡ SparrowRL: 商品网络上的RL训练 — 79×传输缩减，8.91%理想RDMA差距 (arXiv:2602.11456)

- **来源**: arXiv:2602.11456, "RL over Commodity Networks: Overcoming the Bandwidth Barrier with Lossless Sparse Deltas" (2026-02-11)
- **作者**: Chaoyi Ruan, Geng Luo, Xinyi Wan et al. (15位作者)
- **标签**: `RL` · `Commodity Networks` · `Sparse Delta` · `RDMA` · `Lossless` · `WAN` · `Qwen3` · `Cost-Efficient`
- **录用**: 未标注会议

### 问题背景

LLM post-training with RL需要频繁在trainer和distributed rollout actors间同步大模型参数。当前依赖**专用RDMA HPC集群**，成本极高。使用标准Ethernet/WAN链路却无法承受全权重复发：同步8B模型在带宽受限链路需100+秒。

### 核心洞察

RL fine-tuning产生**高度稀疏的逐步骤更新（每步仅~1%参数变化）**。利用这一特性，SparrowRL以**无损稀疏Delta**替代全权重广播，保持bit-exact updates，不丢弃或量化信息。

### 架构设计

| 组件 | 功能 |
|:-----|:------|
| **Sparse Delta Checkpoint** | 每步表示为仅含变化参数的稀疏checkpoint，减少传输量 |
| **Pipelined Delta Extraction** | Delta提取与多流传输管道化 |
| **Overlap with Rollout** | 传输与rollout生成重叠，隐藏通信延迟 |
| **Throughput- & BW-Aware Scheduling** | 吞吐量与带宽感知调度，协调异构worker |
| **Lease-Based Fault Tolerance** | 基于租约的容错机制，处理worker故障 |

### 性能数据 📊

| 场景 | 加速比 / 缩减 | 对比基线 |
|:-----|:-------------|:---------|
| **Qwen3-8B** | **79× per-step transfer payload缩减** | vs full-weight broadcast |
| **Throughput (WAN)** | **2.4-9.5×** 提升 | vs full-weight broadcast |
| **理想RDMA差距** | **内缩至8.91%** | vs ideal RDMA single-DC |
| **Tokens/$(成本)** | **1.21-1.59×** 更高 | vs reserved RDMA clusters |
| **测试模型** | Qwen3 4B-14B | — |
| **部署拓扑** | 最多4个地理区域 | WAN跨域部署 |

### 意义与影响

1. **RL训练的去RDMA化**: SparrowRL证明RL post-training可以在标准Ethernet/WAN上达到~91%的专用RDMA集群性能
2. **稀疏Delta应用的扩展**: 从梯度稀疏化扩展到**参数级稀疏Delta**——RL fine-tuning的每步更新只有~1%参数变化，利用此特性实现79×传输缩减
3. **成本结构转变**: 从"买RDMA集群"变成"按需租用跨云GPU"，1.21-1.59×更高的tokens/$
4. **对RoCE的间接意义**: 说明当应用层做好稀疏化后，底层的RoCE/InfiniBand需求可以被大幅缓解——但这反过来要求集合通信库（NCCL/UCX）支持高效的稀疏Delta传输

### 可复用资源

- 稀疏Delta Checkpoint算法
- 吞吐+带宽感知的异构worker调度策略
- 基于租约的容错机制
