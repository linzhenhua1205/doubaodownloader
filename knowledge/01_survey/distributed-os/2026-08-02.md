## §1 集合通信优化（GPU集群OS核心层）

- **Every Microsecond Matters: Achieving Near Speed-of-Light Latency in GPU Collectives**（arXiv:2607.16100, 2026-07-17, ETH/Torsten Hoefler 组）: GPU 集合通信长期为带宽优化，而长上下文 decode-heavy LLM 推理中大量小集合通信位于 token 生成关键路径。本文识别近最优设计三原则：**无 barrier 同步、对称内存高效利用、多播**；基于 NCCL device-side API 构建低延迟自定义 collective kernel 并在 NCCL 中实现新对称 collectives。中小消息开销降至绝对 SoL 下限的 **7% 以内**；集成后改善 LLM 推理 inter-token 延迟与吞吐，并加速 cuSOLVERMp。**意义**: 推理场景下集合通信优化范式从带宽转向延迟，硬件 SoL 成为可逼近的工程目标。URL: http://arxiv.org/abs/2607.16100

- **Pici: Adaptive Space-efficient Collectives for Dynamic and Unstructured Sparsity**（arXiv:2607.04676, 2026-07-06, SC 2026）: NCCL 等 SOTA 库仅针对稠密数据优化，稀疏数据通信仍发送全量。本文提出 bitvector 格式 Pici（低开销、中稀疏度下快速压缩/解压），为 all-gather / reduce-scatter / all-reduce 设计稀疏感知算法，并在集合过程中**自适应调整数据表示**。99% 输入稀疏度下较 NCCL 提升：all-gather **5.25×**、reduce-scatter **2.5×**、all-reduce **2.66×**。**意义**: MoE 稀疏激活/梯度稀疏场景中"不发零"成为下一带宽杠杆。URL: http://arxiv.org/abs/2607.04676

- **CTA-Pipelining: Latency-Oriented Spatial Scaling for Multi-GPU Systems**（arXiv:2607.07862, 2026-07-08）: 多 GPU 系统已演化为紧密集成共享内存结构，但软件仍将其当高速网络对待。CTA-pipelining 在 **Cooperative Thread Array 级**利用依赖，实现跨 GPU 依赖 kernel 的并发执行，作为与 TP 正交的缩放维度。2 层 GEMM（MLP 代表）在 8-GPU H200/B200 上较 micro-batching 延迟降 **31.8%**、较 TP 降 **29.6%**，可与 TP 组合进一步推低延迟边界。**意义**: 共享内存多 GPU 上软件需从"网络心智"转向"共享内存心智"。URL: http://arxiv.org/abs/2607.07862

## §2 RDMA 与内存解聚（分布式系统架构）

- **Tiara: A Programmable Line-Rate ISA for Remote Memory Access**（arXiv:2606.13708, 2026-06-10）: RDMA one-sided 需客户端提供精确远端地址，当目标地址依赖先读取的数据时（Indirection Wall）1-RTT 性能崩溃——图遍历逐跳指针、多级页表、分布式协调、分页 KV Cache block-table 查找均属此类。Tiara 在**内存侧 NIC** 上执行预注册的可静态验证程序（类比内核 eBPF），本地解析间接寻址，将多 RTT 依赖链折叠为单 RTT。FPGA 原型：10 跳图遍历延迟降 **2.85×** 且吞吐 3.4×、页表遍历延迟 -62%、分布式锁延迟 -2.9×、8KB block 的 PagedAttention 吞吐 2.8×、32 experts MoE 聚合延迟 1.88×。**意义**: 内存侧计算（Memory-Side Processing）从学术走向可编程线速原语。URL: http://arxiv.org/abs/2606.13708

- **Lotus: Two-sided RDMA Striking Back for Disaggregated Memory Databases**（arXiv:2607.26227, 2026-07-28）: 内存解聚数据库中 one-sided RDMA 因绕过远端 CPU 而 API 受限——无法表达饥饿预防、优先级调度、抢占等并发控制关键功能，且索引需多网络 RTT 造成放大。Lotus 重访 two-sided 路线，以轻量缓存 + 高效批处理解决内存服务器 CPU 瓶颈。YCSB 下较 SOTA one-sided 方案吞吐 **8.2×**、p999 尾延迟低 **42.9×**。**意义**: "one-sided 永远更优"的共识被打破——受限 CPU 的智能利用可转化为优势。URL: http://arxiv.org/abs/2607.26227

- **MemExchange: Utility-Driven Distributed Memory Reallocation**（arXiv:2607.11579, 2026-07-14）: 云厂商按峰值过配内存导致跨集群大量闲置，而内存受限租户缓存命中率受损。MemExchange 基于在线 Miss Ratio Curve 估计的边际效用分配，经 RDMA 在物理节点间动态重分配闲置内存，将分散缓存池聚为逻辑聚合池；MTC 协议支持 one-sided RDMA 免远端 CPU。100 节点 CloudLab：远程访问开销较 TCP 低 **2.3×**、机架级内存利用率 +13%、偏斜负载下受限租户 miss rate 降 **63%**。**意义**: 内存成为集群 OS 可动态重配的第一级资源。URL: http://arxiv.org/abs/2607.11579

- **OpenURMA: Clean-Room Open Implementation of Huawei Unified Bus (UB)**（arXiv:2605.28717, 2026-05-27）: 数据中心 RDMA 瓶颈在网卡而非线缆——RoCE/IB 为每 (应用, 远端) 对维护连接状态（1024 应用扇出即数百 MB），且 64B 操作需四次 PCIe 往返。华为 UB（2025 公开规范）解耦每应用端点状态与每主机传输状态、排序可选、经片内总线控制器以原生 load/store 触达远端内存（已用于 Ascend 950）。OpenURMA 以三档实现（Alveo U50 可综合 RTL / SystemC 双节点 / gem5 脚手架）对照 OpenRoCE：64B 远端取数 UB load/store 路径 ~500ns 端到端，较匹配基线（2186ns）低 **4.37×**、吞吐 2.80×，仅占 U50 LUT 14%。**意义**: 华为 UB 生态开源化推进，国产互联软件栈获得可验证参考实现。URL: http://arxiv.org/abs/2605.28717

## §3 调度与容错（资源调度与隔离）

- **OptCC: Don't Let a Few Network Failures Slow the Entire AllReduce**（arXiv:2606.01680, 2026-06-01）: 网络故障是大规模 GPU 集群最常见硬件故障之一。NCCL 现有缓解方式（同机幸存 NIC 重路由）使降级服务器留在 ring 关键路径上拖慢全局。本文首次给出**非对称带宽下 AllReduce 完成时间信息论下界**：straggler 保留 ≥50% 原带宽时，相对无故障最优的不可避免开销仅 O(1/p)。四阶段流水线算法 OptCC 逼近该下界：50% 带宽损失下 AllReduce 仅比 NCCL 无故障 ring 慢 **2-6%**，而 SOTA 高达 57% 开销。**意义**: 容错集合通信从启发式走向有理论下界的算法设计。URL: http://arxiv.org/abs/2606.01680

- **Rain: RDMA-assisted In-Network Scheduling for Microsecond-scale Workloads**（arXiv:2606.03352, 2026-06-02, CoNEXT2）: 微秒级服务严格尾延迟下，软件调度器难平衡吞吐/延迟，交换机方案缺全局协调或依赖包重循环。Rain 基于可编程交换机维护集中队列并约束 worker 本地队列：双向 on-switch 排队直接在交换机内缓冲匹配任务与 token；交换机驱动 RDMA 引擎以 one-sided WRITE 多播预写任意大任务；切片感知调度降低队头阻塞。并发现反直觉结论——**更浅的 worker 队列不一定改善尾延迟**，故运行时自适应调整队列深度。RocksDB 实测较 SOTA 吞吐 **1.75×** 且满足同等尾延迟。URL: http://arxiv.org/abs/2606.03352

- **StageFrontier: Synchronization-Aware Stage Accounting for Distributed ML Training**（arXiv:2606.06751, 2026-06-04）: 分布式训练变慢时同步机制掩盖根因——单 rank 数据延迟可表现为整个 group 的"时间倒退"。StageFrontier 让每 rank 只上报短的有序 stage 时长向量（data/forward/backward），取最领先 rank 的累计时间构成 frontier，精确归因暴露时间来自哪个 stage/rank，且不依赖同步时钟与内核追踪。PyTorch 实现 128 ranks（Gloo/NCCL）开销 <0.2%；从 **0.11 MB 摘要**复现 PyTorch Profiler/HTA/Nsight 的 top-stage 定位（对照 15.81 GB trace）。**意义**: 恒开型轻量诊断信号补齐"重 profiler 不可常开、均值仪表误导"的运维鸿沟。URL: http://arxiv.org/abs/2606.06751

## §4 推理服务 OS 编排（AI集群OS编排）

- **NELSSA: GPU-PNM Heterogeneous System for Mixed-Length LLM Serving**（arXiv:2607.26633, 2026-07-29, MICRO 2026）: agentic 应用使数百 token 至数十万 token 的混合长度请求交织于同一服务窗口，GPU-centric 架构因依赖大而受限的 batch 而失效。NELSSA 集成真实 Processing-near-Memory (PNM) 加速器：**长度感知请求放置**（短上下文→GPU，长上下文→PNM tier）+ 运行时迁移适应动态上下文增长（免重算），经 CXL 基础设施 + RPC/RDMA 编排跨 tier 内存移动。混合长度负载下 decode 吞吐提升 **5.5×**（tokens/sec）、P99 延迟降 **15×**。**意义**: CXL 解聚使 GPU+PNM 异构服务成为可扩展 LLM 基础设施范式。URL: http://arxiv.org/abs/2607.26633

- **ForeMoE: Routing Foresight for Micro-step-level MoE Load Balancing in RL Post-training**（arXiv:2606.11867, 2026-06-10）: MoE RL 后训练中 step 级负载稳定但微步 batch 极小导致高频剧烈波动，现有基于历史统计的预训练负载均衡方法失效。ForeMoE 利用 RL 多阶段管线（rollout→recompute→policy update）中 **rollout 阶段的可预见路由信息**主动引导后续阶段负载均衡；层级规划器分解 NP-hard 问题 + 传输引擎经 CPU-assisted/GPU-direct 双路径重叠专家迁移。64 GPU 上较 SOTA RL 后训练系统加速 **1.45×**。**意义**: 调度信号从"历史统计"转向"管线前瞻"，RL 训练成为 MoE 调度新战场。URL: http://arxiv.org/abs/2606.11867

- **Move the Query, Not the Cache: Cross-Instance Latent Attention Redistribution**（arXiv:2606.01502, 2026-05-31）: 前沿 LLM 以稀疏注意力索引器每查询选取少量 KV block，agentic 工作负载大量子 agent 复用同一语料块；当语料跨 GPU 实例分区时查询与其选中的 block 常在不同 GPU。传统跨实例 KV 方案"移缓存"，而 MLA（多头潜在注意力）将每 token K/V 压缩为窄向量，路由查询行仅 ~1KB——**"移查询"常比"移缓存"更便宜**。在真实多节点 H100 + IBGDA 上提炼拓扑感知成本模型与 closed-form 路由判定（探测/传输/计算/返回/合并），模型对批量 RTT 跟踪误差 ~7%；decode 时路由查询把 ~3ms 缓存重适配换为数十微秒 RTT。非 MLA 专用，DeepSeek-V3.2/V4、GLM-5.1 适用。**意义**: 稀疏选择 + 压缩让注意力原语从"移数据"转向"移计算"。URL: http://arxiv.org/abs/2606.01502

## 🧠 趋势判断

1. **集合通信双线并进：带宽上限（稀疏）与延迟下限（SoL）** — Pici 证明"不发零"在稀疏场景可再获 5×；Every Microseconds 证明延迟可逼近硬件 SoL 7% 以内。两者共同要求 collective 库从黑盒原语走向**可定制 kernel 层抽象**
2. **内存侧智能成为新 OS 层** — Tiara（可编程内存侧 NIC）与 Lotus（two-sided RDMA 复兴）殊途同归：远端 CPU/内存的有限智能若被正确暴露与利用，可突破 one-sided RDMA 的 API 天花板
3. **调度信号革命：前瞻性替代历史统计** — ForeMoE 用管线前瞻路由信息、Rain 用交换机内实时匹配、OptCC 用信息论下界，共同指向"调度决策依据从过去数据转向未来信息+理论边界"
4. **华为 UB 开源生态成形** — OpenURMA 提供可验证参考实现（4.37× 延迟优势），国产互联（UB/Ascend 950）软件栈正从闭源走向可研究、可复现
