## §1 Agent Workflow调度（新架构爆发——Agent OS雏形）

> **核心趋势**: Agent workload从"请求级"→"Workflow级"→"会话级"调度演进，这本质是分布式OS的调度抽象升级。

### 1.1 ⭐ SAGA: Workflow-Atomic Scheduling for AI Agent Inference (arXiv:2605.00528)

- **信号强度**: ⭐⭐⭐⭐⭐
- **来源**: [arXiv:2605.00528](https://arxiv.org/abs/2605.00528) (May 2026)
- **核心发现**:
  - AI Agent每任务执行10-100+个LLM调用链，但现有GPU调度器把每个调用当独立请求
  - 跨步KV Cache被丢弃，端到端延迟膨胀3-8×
  - **提出**: 将整个Agent Workflow（非单个推理调用）作为一级调度单元
  - **三个机制**: (1) Agent Execution Graphs预测跨工具边界的KV Cache复用，达到Bélády最优离线策略的1.31×内 (2) session-affinity batching + work stealing (3) Agent Fair Share——任务完成时间公平性度量（有界偏差保证）
  - **结果**: 64-GPU集群，1.64×任务完成时间(geomean, p<0.001)，GPU内存利用1.22×，99.2% SLO达标率
  - **代价**: ~30%更低峰值吞吐——适合延迟敏感型交互式部署
- **意义**: 这是分布式OS调度抽象升级的关键信号——**请求级→程序级**，与K8s的Pod→Job演进类似但粒度更细

### 1.2 ⭐ SpecBox: Speculative Sandbox Scheduling for MCP Agents (arXiv:2607.23933)

- **信号强度**: ⭐⭐⭐⭐⭐
- **来源**: [arXiv:2607.23933](https://arxiv.org/abs/2607.23933) (Jul 2026, latest)
- **核心发现**:
  - MCP (Model Context Protocol) 使Agent调用隔离sandbox，sandbox冷启动成新瓶颈
  - **SpecBox**: keyword matching + streaming semantic embedding实现intent-driven sandbox预预热
  - 在LLM token生成中识别即将执行的tool调用，将sandbox启动与模型推理重叠
  - 上下文感知随机预取 + 语义结果缓存 + 零拷贝共享内存传输层
  - **结果**: P99延迟降2.9×，峰值内存降45.9%
- **意义**: Agent OS需要**推测执行**能力——类似CPU分支预测的OS级等价物

### 1.3 SMetric: Session-Centric Scheduling for Agent Serving (arXiv:2607.08565)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2607.08565](https://arxiv.org/abs/2607.08565) (Jul 2026)
- **核心发现**:
  - Agent workload中KV$复用超80%（chat仅54-62%），但现有调度器过度追求cache locality导致负载不均
  - **核心洞察**: 只用负载均衡一小部分请求（每个Agent session的首个请求）即可平衡集群
  - SMetric: session turn信息作为调度度量——仅从用户输入就能高效准确获取，调度器保持无状态
  - **结果**: 集群TPS提升10-16%（prefill-decode colocation），prefill TPS提升2-34%（解耦场景）
- **意义**: Agent session结构本身携带调度信号——Agent OS可以利用应用层语义

### 1.4 SwarmX: Neural Predictor-based Agentic Scheduling (arXiv:2606.21401)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2606.21401](https://arxiv.org/abs/2606.21401) (Jun 2026)
- **核心发现**:
  - Agent的inference时间和model-call结构依赖于prompt语义——传统调度方法失效
  - SwarmX: 专用neural predictor捕捉prompt/device/runtime/target-model特征
  - 分布预测暴露给router和scaler实现tail-aware决策
  - 生产部署近千GPU + 百万CPU核
  - **结果**: tail latency降61.5%，同SLO下吞吐2×生产调度器
- **意义**: **调度本身需要ML**——分布式OS从"规则调度"向"预测调度"演进

### 1.5 Maestro: Cross-Cluster Multi-Agent Scheduling (arXiv:2606.12950, ICDCS 2026)

- **意义**: 多Agent系统的调度需要**跨集群协同**和**workflow感知**

### 1.7 Scepsy: Aggregate LLM Pipeline for Agent Serving (arXiv:2604.15186)

## §2 解耦推理架构（从P/D分离到算子级解耦）

> **核心趋势**: Prefill-Decode分离已成标配，但正在被更细粒度的operator-level disaggregation超越。

### 2.1 ⭐ DOPS: Dynamic Operator Scheduling beyond PD Disaggregation (arXiv:2607.25498, MICRO 2026)

- **信号强度**: ⭐⭐⭐⭐⭐
- **来源**: [arXiv:2607.25498](https://arxiv.org/abs/2607.25498) (Jul 2026, MICRO 2026 acceptance)
- **核心发现**:
  - PD分离和roofline-based调度的不足：端到端延迟还依赖workload形状、设备争用、weight布局
  - DOPS: 硬件感知闭环框架，联合优化算子调度 + blockwise weight布局
  - 两组件: Bifocal scheduler(动态算子到设备放置) + Weight Layout Arbiter(内存约束下选高效weight布局)
  - NPU+PIM异构系统: Bifocal 1.20-2.23×加速，WLA额外1.28-1.33×
- **意义**: 从P/D分离→算子级解耦——**算子级调度是下一代AI OS的核心抽象**。MICRO 2026接收标志学术认可

### 2.2 FlexNPU: 昇腾NPU透明虚拟化 (arXiv:2606.04415)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2606.04415](https://arxiv.org/abs/2606.04415) (Jun 2026)
- **核心发现**:
  - 用户空间虚拟化层接入AscendCL API，无需修改模型/framework/驱动
  - 支持动态PD co-location——根据互补资源特征自适应调度
  - 384卡Ascend 910C + DeepSeek-R1: 吞吐比静态PD分离提升5.15%/26.33%
  - Qwen2.5-7B: TTFT降92%+，TPOT几乎不变
- **意义**: **NPU虚拟化是国产AI OS的关键基础设施**——华为昇腾生态的OS层能力

### 2.3 NetKV: Network-Aware Decode Selection (arXiv:2606.03910)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2606.03910](https://arxiv.org/abs/2606.03910) (Jun 2026)
- **核心发现**:
  - KV Cache必须在DC网络中传输后才开始decode → transfer time进入TTFT预算
  - 当前调度器忽略拓扑距离和动态拥塞
  - 证明: 忽略网络项使cache-only调度随context增长任意次优
  - NetKV: 贪心oracle消费→64 GPU fat-tree模拟中TTFT降21.2%
- **意义**: **网络拓扑作为调度的一级输入**——分布式OS必须感知物理网络

### 2.4 ⭐ ConServe: 会话级解耦调度 (arXiv:2606.01839)

- **信号强度**: ⭐⭐⭐⭐⭐
- **来源**: [arXiv:2606.01839](https://arxiv.org/abs/2606.01839) (Jun 2026)
- **核心发现**:
  - Agent workload的多轮依赖使turn-level调度依赖不可靠预测
  - **将调度单元从turn提升到conversation**→turn级波动变为稳定的两阶段结构：(1) compute-bound turn-1 prefill (2) 长memory-bound tail
  - 放置只需读取first-turn输入长度和per-decoder KV occupancy——**两者均直接可观测，无需预测**
  - **结果**: P95 TTFT降51.08%，能效提升7.51%；异构GPU再额外22.75%
- **意义**: **调度抽象粒度升级消除预测需求**——这是分布式OS的"接口即契约"思想的实例

### 2.5 AMPD: Multi-Round LLM Inference over Disaggregated Serving (arXiv:2602.14516, ICML 2026)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2602.14516](https://arxiv.org/abs/2602.14516) (ICML 2026, Feb 2026)
- **核心发现**:
  - 多轮workflow（Agent/iterative retrieval）的interleaved prefill-decode模式被现系统忽略
  - AMPD: 根据实时workload自适应决定prefill在哪里执行、如何调度
  - 规划算法推导最优资源分配和并行策略
- **意义**: ICML接收标志"解耦调度进入ML系统主流"

### 2.6 AFD: Attention-FFN Disaggregation Design Space (arXiv:2605.28302)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2605.28302](https://arxiv.org/abs/2605.28302) (May 2026)
- **核心发现**:
  - MoE推理中，memory-bound attention + compute-intensive FFN + dispatch/combine通信各有不同资源需求
  - 三层解耦全景对比: chunked-prefill → P/D分离 → Attention-FFN分离(AFD)
  - 在严格TTFT/TPOT SLO下，AFD在DeepSeek-V3.2上维持~4k tokens/s——非AFD部署不可行
  - 给出如何根据workload和模型架构partition attention/FFN的设计原则
- **意义**: **算子级解耦的设计空间系统化**——为下一代AI OS提供架构参考

### 2.7 Frontier: LLM Inference Simulator (arXiv:2605.21312)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2605.21312](https://arxiv.org/abs/2605.21312) (May/Jun 2026)
- **核心发现**:
  - 覆盖PD分离 + AFD + CUDA Graphs + speculative decoding的离散事件模拟器
  - 16-H800: 吞吐误差<4%，端到端延迟误差6.4%(co-location)/2.6%(disaggregation)
  - 扩展至1K+ GPU，支持SLA Pareto前沿探索、Agent推理调度验证、RL post-training重配置
- **意义**: **模拟器是分布式OS设计的加速器**——可大规模试验调度策略

### 2.8 RTP-LLM: 阿里生产级推理引擎 (arXiv:2605.29639)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2605.29639](https://arxiv.org/abs/2605.29639) (May 2026)
- **核心发现**:
  - 服务阿里100M+用户，支持8B-235B模型
  - PD分离 + 层次化multi-tier KV Cache管理 + modular speculative decoding
  - 对比vLLM/SGLang: 模型加载4.7-6.3×加速, TTFT P95降35-37%, 推理吞吐1.12-2.48×(speculative)/1.86-2.52×(多模态)
- **意义**: **中国最大规模的LLM serving OS实践**

## §3 分布式训练运行时OS

> **核心趋势**: 训练从"静态资源分配"向"弹性、跨阶段协同、跨数据中心的OS级编排"演进。

### 3.1 ScaleAcross Explorer: Meta跨数据中心训练优化 (arXiv:2605.24326)

- **信号强度**: ⭐⭐⭐⭐⭐
- **来源**: [arXiv:2605.24326](https://arxiv.org/abs/2605.24326) (May 2026, Meta)
- **核心发现**:
  - "Scale-Across"训练：跨多数据中心building和region分布GPU资源

- **信号强度**: ⭐⭐⭐⭐⭐
- **来源**: [arXiv:2604.21428](https://arxiv.org/abs/2604.21428) (Apr 2026, Google/DeepMind)
- **核心发现**:
  - SPMD要求跨加速器紧耦合→任何瞬态slowdown/故障阻塞全计算

  - 灵感来自"混沌工程"：**零全局停机**，百万模拟chip测试
- **意义**: **彻底打破SPMD紧耦合范式**——这是分布式训练OS的架构范式转移

### 3.3 FoMoE: Federated MoE Training (arXiv:2606.19025)

### 3.4 Asteria: 二阶优化运行时系统 (arXiv:2605.16184)

- **意义**: **训练OS的runtime层决定优化器的可行性**——这是OS-算法协同设计的典范

### 3.5 BiDiRL: 双向资源调度 for 异步RL (arXiv:2607.09207)

### 3.6 ROSE: 利用Serving GPU做RL Rollout (arXiv:2605.06534)

## §4 故障容错与Checkpoint OS

> **核心趋势**: 从"保存→恢复"到"差异化、层级化、无停顿的容错"演进。

### 4.1 ⭐ TierCheck: 三层差异化Checkpoint (arXiv:2605.17821)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2605.17821](https://arxiv.org/abs/2605.17821) (May 2026)
- **核心发现**:
  - LLM训练被异构故障谱打断——从GPU crash到集群级outage
  - TierCheck三层设计: (1) 本地/peer内存轻量diff checkpoint→快速局部恢复 (2) 异步迁移base checkpoint到远程持久存储 (3) 集群感知恢复
  - 严格全局一致性，不stall训练
  - **结果**: 40B参数模型端到端checkpointing <10s
- **意义**: **容错OS必须了解故障的异构性**——差异化策略比"一刀切"高效

### 4.2 BatchWeave: 对象存储原生训练数据平面 (arXiv:2605.09994)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2605.09994](https://arxiv.org/abs/2605.09994) (May 2026)
- **核心发现**:
  - LFM训练的数据pipeline从静态ingestion变为动态组件
  - Transactional Global Batch + versioned-manifest ACID存储语义
  - Decentralized Adaptive Commit算法：manifest增长时维持稳定吞吐
  - **结果**: 64 GPU，超越colocated dataloader吞吐 + 完全故障隔离，超越Kafka吞吐
- **意义**: **数据平面也是OS的一部分**——checkpoint/CKPT要原生集成到存储层

### 4.3 MoEvement: MoE稀疏Checkpointing (arXiv:2412.15411, NSDI'26)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2412.15411](https://arxiv.org/abs/2412.15411) (NSDI 2026)
- **核心发现**:
  - MoE模型训练状态大→checkpoint开销剧增
  - **稀疏checkpointing**: 在迭代间逐步snapshot expert子集
  - sparse→dense转换 + upstream activation logging
  - **结果**: checkpoint开销降4×，恢复开销降31×，ETTR≥0.94（MTBF低至10分钟）
  - 整体训练加速8×
- **意义**: **MoE模型需要专用容错OS**——通用checkpoint方案浪费巨大

### 4.4 R²CCL: 弹性容错集合通信 (arXiv:2512.25059)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2512.25059](https://arxiv.org/abs/2512.25059) (Dec 2025)
- **核心发现**:
  - 网络故障浪费10-15% GPU小时（因慢恢复）
  - R²CCL: 利用multi-NIC硬件做连接快速迁移 + 带宽感知负载重分布 + 弹性collective算法
  - **结果**: 训练开销<1%，推理开销<3%，吞吐优于AdapCC 12.18×/DejaVu 47×
- **意义**: **通信库是分布式OS的内核模块**——容错必须嵌入通信层

## §5 集群调度元OS

> **核心趋势**: 调度从"集中式/启发式"向"去中心化/ML驱动/生命周期感知"演进。

### 5.1 Laminar: Probe-First调度范式 (arXiv:2602.13789)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2602.13789](https://arxiv.org/abs/2602.13789) (Feb 2026)
- **核心发现**:
  - 刚性拓扑作业在GPU集群留下碎片生态：长驻workload vs 高度瞬态任务竞争不稳定余量
  - Laminar: 去中心化probe-first, execute-later范式
  - Zone级概率流分裂 + bounded probing + 节点级仲裁 → 控制面近O(1)
  - **Airlock**: bounded node-local runtime-survival层——将内存压力转为有序策略(暂停/原地恢复/重寻址/回收)
  - 生命周期感知调度：保护高价值长驻工作，逼近物理饱和
- **意义**: **调度不终止于执行开始**——运行时存活性是OS的新职责

### 5.2 SWARM+: 去中心化多Agent共识调度 (arXiv:2603.19431)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2603.19431](https://arxiv.org/abs/2603.19431) (Mar/Jul 2026)
- **核心发现**:
  - 分层多Agent共识协调workload放置，不需要中心化orchestrator
  - 数据感知调度策略：资源可用性+DTN连通性+数据局部性
  - 990分布agent: ~1s/作业选择(110 agents)
  - **97%+ job completion**（分布式故障下），mean ~95%（关联站点outage）
  - 选择延迟和调度延迟降97-98% (vs prior SWARM)
- **意义**: **去中心化共识在1000节点规模可行**——这打开了调度OS的架构新方向

### 5.3 Mixture-of-Schedulers (arXiv:2511.11628)

- **信号强度**: ⭐⭐⭐
- **来源**: [arXiv:2511.11628](https://arxiv.org/abs/2511.11628) (Nov 2025)
- **核心发现**:
  - "one-policy-fits-all"调度器在不同workload下表现差异巨大
  - 从专家调度器组合中动态选择：Adaptive Scheduling Agent
  - 离线训练hardware-agnostic ML模型→运行时time-weighted probability voting识别workload
  - 通过Linux sched_ext框架切换调度器
  - **结果**: 86.4%场景优于EEVDF，78.6%在前三
- **意义**: **调度策略本身成为可组合的专家系统**——OS调度正在走MoE路子

### 5.4 Descriptive HPC Execution with Agents (arXiv:2607.10081)

- **信号强度**: ⭐⭐⭐⭐
- **来源**: [arXiv:2607.10081](https://arxiv.org/abs/2607.10081) (Jul 2026)
- **核心发现**:
  - Agentic框架执行HPC应用：从人类代码→描述性prose
  - 三项任务: (1) scaling study (2) Slurm↔Flux作业转换（高精度，processor-affinity最常见错误）(3) bioscience workflow重建（18/19 runs完全一致）
  - 用agent自动完成多集群设置和调度
- **意义**: **Agent本身就是HPC集群OS的新用户界面**

### 5.5 AGMARL-DKS: GNN增强多Agent K8s调度 (arXiv:2603.12031)

- **信号强度**: ⭐⭐⭐
- **来源**: [arXiv:2603.12031](https://arxiv.org/abs/2603.12031) (Mar/May 2026)
- **核心发现**:
  - 每个集群节点作为agent → 集中训练+去中心化执行
  - GNN构建全局集群上下文状态表示
  - stress-aware lexicographical ordering替代静态线性加权
  - Google GKE验证: 优于默认调度器（fault/utilisation/cost）
- **意义**: **GNN+MARL是K8s调度演进方向**——但离生产还有距离

## 💡 关键判断

### 六大趋势判断

1. **Agent OS是分布式OS的新分支**（与K8s的核心差异）
   - K8s调度以Pod/Container为单位，Agent OS以**Workflow/Session**为单位
   - K8s关心资源利用率，Agent OS关心**端到端任务完成时间**
   - K8s网络模型基于IP，Agent OS需要**语义路由+能力发现**
   - SAGA/SMetric/SpecBox构成Agent OS调度的三要素: workfow-atomic + session-centric + speculative

2. **解耦从P/D分离走向算子级解耦**
   - DOPS (MICRO 2026)开创了**动态算子调度**范式
   - AFD将Attention和FFN分别放置到不同GPU组
   - ConServe证明**会话级抽象消除预测需求**
   - 趋势: Disaggregation粒度从服务级→请求级→算子级→数据流级

3. **训练和推理的OS边界正在消失**
   - ROSE让serving GPU做RL rollout
   - MARLaaS做RL-as-a-Service多租户调度
   - BiDiRL让rollout/training资源双向借用
   - → **统一训练推理OS**是下一代集群OS的核心能力

4. **网络拓扑成为调度的一级约束**
   - NetKV证明忽略网络项使调度任意次优
   - ScaleAcross Explorer明确网络层为三大维度之一
   - 调度器从"compute-aware"→"network-aware"→"topology-aware"

5. **容错OS从"重置"向"差异化恢复"演进**
   - TierCheck三层差异化 (局部→peer→remote)
   - MoEvement稀疏checkpoint
   - Decoupled DiLoCo异步学习+故障屏蔽
   - R²CCL通信层内嵌容错

6. **去中心化调度正在替代集中式**
   - SWARM+在990 agent规模验证可行性
   - Laminar的O(1)控制面probe-first范式
   - AGMARL-DKS的GNN+MARL方法
