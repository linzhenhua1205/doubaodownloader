## 1️⃣ 🏆 NCCL EP: NVIDIA 原生 MoE 专家并行通信库 (arXiv:2603.13606)

- **来源**: arXiv:2603.13606, "NCCL EP: Towards a Unified Expert Parallel Communication API for NCCL" (2026-03-13, v3 2026-04-02)
- **作者**: Amos Goldman, Nimrod Boker 等 **18位 NVIDIA 作者**
- **标签**: `NCCL` · `MoE` · `Expert Parallelism` · `Device API` · `GIN` · `LL/HT` · `vLLM`

### 背景与动机

前有 DeepEP、Hybrid-EP 等第三方 GPU-initiated 通信库证明 MoE 通信的性能潜力，但碎片化严重——每个库独立实现dispatch/combine、各自管理GPU通信资源，缺乏统一支撑。NCCL EP 的目标：**将 MoE 通信原语内建于 NCCL，提供受支持的官方路径**。

### 架构设计

**核心 API**: `ncclEpDispatch` + `ncclEpCombine`，C/Python 双接口

**双模式设计**:

| 模式 | 目标场景 | Batch Size | 通信策略 |
|:-----|:---------|:-----------|:---------|
| **Low-Latency (LL)** | Inference Decoding | 1-128 tokens | 全连接 All-to-All RDMA+NVLink mesh，Double-buffered 重叠 dispatch 与 combine 阶段 |
| **High-Throughput (HT)** | Training / Inference Prefill | 4096+ tokens | 层次化：NVLink 域内聚合 → 域间 RDMA 传输 |

**关键实现细节**:
- 完全基于 NCCL Device API 构建（而非第三方 GIN 库）
- 内/节点间通信统一使用 Device API，利用拓扑感知路由
- 两种模式的所有通信路径均通过 GPU-initiated RDMA

### 性能数据

| 场景 | 结果 |
|:-----|:------|
| LL 模式 kernel 性能 | 与 DeepEP 等专业库 **性能竞争**（在多节点 H100 集群上验证）|
| vLLM 端到端集成 | 已集成 vLLM，展示完整推理流程 |
| 跨节点配置 | H100 cluser，多节点验证双模式可行性 |

### 意义

- NCCL EP 的发布意味着 NVIDIA 正式将 MoE 通信的**标准化路径**纳入 NCCL 体系
- 对 AI infra 影响：未来 MoE 模型的 dispatch/combine 无需依赖第三方库，直接通过 NCCL API 实现
- 双模式策略（LL All-to-All mesh vs HT 层次化聚合）可作为设计参考

## 2️⃣ 🔒 R²CCL: 面向 LLM 训练/推理的可靠弹性集合通信库 (arXiv:2512.25059)

- **来源**: arXiv:2512.25059, "Reliable and Resilient Collective Communication Library for LLM Training and Serving" (2025-12-31)
- **作者**: Wei Wang, Nengneng Yu, Sixian Xiong, Zaoxing Liu
- **标签**: `Fault Tolerance` · `NIC Failover` · `Connection Migration` · `Load Redistribution`

### 背景与动机

网络故障可浪费 **10-15% 的 GPU 小时**（因恢复缓慢）。常见的网络错误和链路波动触发超时，通常导致整个 job 终止，训练需要昂贵的 checkpoint 回滚，推理需要请求重处理。

### 核心机制

R²CCL 通过利用**多 NIC 硬件**实现无损低开销故障转移：

| 机制 | 技术详情 |
|:-----|:---------|
| **Rapid Connection Migration** | 故障时快速迁移活跃连接到备用 NIC，不中断通信 |
| **Bandwidth-Aware Load Redistribution** | 感知可用带宽的负载重新分配，避免过载 |
| **Resilient Collective Algorithms** | 改容错集合算法，适配带宽降级场景下保持最优性能 |

### 性能数据

| 指标 | 数值 |
|:-----|:------|
| 训练开销 | **<1%**（与 NCCL 无故障时对比） |
| 推理开销 | **<3%** |
| vs AdapCC | **12.18×** 提升 |
| vs DejaVu | **47×** 提升 |
| 评估硬件 | 2× 8-GPU H100 InfiniBand 服务器 + 大规模 ML 仿真器（数百GPU）|

### 意义

- 与 VCCL（10/2025，主备 QP）和 OptCC（6/2026，容错 AllReduce 算法）互补：VCCL 侧重 QP 级冗余，OptCC 侧重算法级理论最优，R²CCL 侧重连接迁移+弹性算法三合一
- **<1% 开销意味着容错机制可以被默认启用**，这是走向生产级可靠性的关键指标
- 47× 超越 DejaVu 说明在连接迁移而非单纯重新建立连接的策略上取得了突破

## 3️⃣ ⚡ CoCoDiff: Diffusion Transformer 分布式推理 All-to-All 优化 (arXiv:2604.14561)

- **来源**: arXiv:2604.14561, "CoCoDiff: Optimizing Collective Communications for Distributed Diffusion Transformer Inference Under Ulysses Sequence Parallelism" (2026-04-15, v2 2026-04-21)
- **作者**: Bin Ma, Xingjian Ding, Tekin Bicer, Pengfei Su, Dong Li
- **机构**: 文中工作单位为 Argonne National Laboratory 等
- **标签**: `Diffusion Transformer` · `All-to-All` · `Ulysses SP` · `Aurora` · `Intel GPU`

### 背景与动机

Diffusion Transformers (DiTs) 在科学计算中日益普及，模型增大+分辨率提高使多 GPU 推理成为必须。Ulysses 序列并行可扩展 DiT 推理，但引入频繁的 All-to-All 集合通信，由于其严格的数据依赖、大消息体积和不对称互连带宽，与计算重叠极为困难。

### 核心发现与机制

**两个关键观察**:
1. **V 仅需线性投影**，而 Q/K 需要额外的 normalization + RoPE → V 的通信可与 Q/K 计算重叠
2. **相邻去噪步的 tensor 相似** → 存在时间冗余

**三个机制**:

| 机制 | 技术详情 |
|:-----|:---------|
| **TAPA: Tile-Aware Parallel All-to-all** | 将 All-to-All 分解为拓扑对齐的 phase，匹配底层硬件拓扑 |
| **V-First Scheduling** | 将 V 的通信隐藏在 Q/K 计算之后 |
| **V-Major Selective Communication** | 在慢速互连上仅传输激活的 projection，减少通信量 |

### 性能数据

| 场景 | 加速比 |
|:-----|:-------|
| 平均加速 (4 DiT 模型, 1-8 节点) | **3.6×** |
| 峰值加速 | **8.4×** |
| 平台 | Aurora 超算, 最多 96 Intel GPU tiles |
| 模型 | 4种不同规模的 DiT 模型 |

### 意义

- 这是首个系统性地针对 Diffusion Transformer 推理的集合通信优化工作
- **All-to-All 作为 DiT 推理的瓶颈已被确认**，且可以通过计算-通信重叠大幅缓解
- TAPA 的"拓扑对齐 Phase 分解"思路可推广到其他需要 All-to-All 的场景（如 MoE dispatch）
- V-First 的"利用操作不对称性"思路与 6/30 的 Perseus（反向——megakernel 的隐藏序列化）形成镜像对照

## 4️⃣ 🛡️ RobustRL: 基于角色的 LLM RL 后训练容错系统 (arXiv:2512.22492)

- **来源**: arXiv:2512.22492, "Role-Based Fault Tolerance System for LLM RL Post-Training" (2025-12-27)
- **作者**: Zhenqian Chen, Baoquan Zhong, Xiang Li, Qing Dai, Xinkui Zhao, Miao Ye, Ren Cheng, Lufei Zhang, Jianwei Yin
- **标签**: `RL Post-Training` · `Fault Tolerance` · `UCX` · `Dynamic P2P` · `Role Isolation`

### 背景与动机

RL 后训练（reasoning 增强、工具使用等）交叉运行训练和推理工作负载，暴露在双端故障风险中。现有容错框架 target 训练或 inference 单一场景，未能利用 RL 异步执行的优化空间。

### 核心洞察：基于角色的故障隔离

关键洞察：**角色级故障隔离**——一台机器的故障不影响其他角色。将 trainer、rollout 和其他管理角色视为独立的分布式子任务：

- 不重启整个 RL 任务（如 ByteRobust）
- 仅恢复故障角色并重新连接到存活角色
- 消除全重启开销（rollout 重放 + 初始化延迟）

### 三阶段设计

| 阶段 | 方法 | 技术细节 |
|:-----|:------|:---------|
| **Detect** | 角色感知监控 | 区分实际故障与角色特定行为，避免误报和延迟检测 |
| **Restart** | 非破坏性恢复 | Trainer: rollout 状态持续 + 快速通过 rollout warm standby 恢复；Rollout: 隔离机器替换，不中断 RL 任务 |
| **Reconnect** | UCX 动态 P2P | **替换静态集合通信为基于 UCX 的动态 point-to-point**，故障角色恢复后立即权重同步 |

### 性能数据

| 指标 | RobustRL | ByteRobust |
|:-----|:---------|:-----------|
| ETTR (Effective Training Time Ratio) | **>80%** | ~60% |
| 端到端训练时间加速 | **8.4%-17.4%** | — |
| 测试配置 | 256-GPU, Qwen3-8B-Math, 10% 故障注入 |

### 意义

- **UCX 在容错场景中的首次系统级应用**：用动态 P2P 替代静态 collective，使故障恢复后的权重同步成为可能
- 角色级隔离的设计思路可推广到更一般的混合工作负载场景（不仅 RL）
- 对于 RL 后训练这个快速增长的需求，RobustRL 提供了首个端到端容错方案

## 5️⃣ 🌐 BACE-Pipe: 跨地域 LLM 训练的带宽感知成本优化流水线调度 (arXiv:2605.25375)

- **来源**: arXiv:2605.25375, "Bandwidth-Aware and Cost-Efficient Pipeline Parallel Scheduling in Geo-Distributed LLM Training" (2026-05-25)
- **作者**: Han Zhang, Jianchun Liu, Hongli Xu (中国科学技术大学)
- **标签**: `Geo-Distributed` · `Pipeline Parallelism` · `Scheduling` · `Cost Optimization`

### 背景与动机

单云区域 GPU 短缺迫使跨地域分布式训练。在此场景下，Pipeline Parallelism (PP) 通信量小，但跨地域异构带宽和不同电价下的调度极为困难。现有方案要么延迟优先（高电费），要么成本优先（JCT 延长），且多租户场景下长作业导致 HoL blocking。

### 三组件设计

| 组件 | 功能 |
|:-----|:------|
| **Dynamic Job Prioritization** | 综合考虑 job 特征（计算时间）+ 实时网络利用率优化执行顺序 |
| **Bandwidth-Aware Pathfinder** | 识别满足通信约束的可行跨区域 pipeline 路径，防止通信 stall pipeline |
| **Cost-Minimizing Allocator** | 在所有可行路径中，优先分配到低电价区域的 GPU 资源 |

### 性能数据

| 指标 | 提升幅度 |
|:-----|:---------|
| 平均 JCT 降低 | **27.9% — 64.7%** |
| 总电费降低 | **12.6% — 30.6%** |
| 方法 | 大规模仿真验证 |

### 意义

- **跨 DC 训练**正从试验走向实用，BACE-Pipe 提供了首个联合优化延迟+成本的调度框架
- 与 6/29 的 ScaleAcross Explorer（Meta 跨建筑训练）互补：ScaleAcross 侧重并行策略（PP/TP/DP）+网络拓扑联合优化，BACE-Pipe 侧重多作业调度+电价成本
- 带宽感知 pathfinder 的思路可应用到多数据中心 AI 基础设施规划

## 6️⃣ 🏗️ HetCCL (v2): 混合厂商异构集群集合通信 (arXiv:2605.31000, May 2026)

- **来源**: arXiv:2605.31000, "HetCCL: Enabling Collective Communication For Mixed-Vendor Heterogeneous Clusters" (2026-05-29)
- **作者**: Yuejie Wang, Tao Chang 等 13 位作者（多家中国机构）
- **标签**: `Heterogeneous` · `Mixed-Vendor` · `Border-Communicator` · `Hierarchical Topology`

### 与 1月 HetCCL 的区别

| 维度 | HetCCL (Jan 2026, arXiv:2601.22585, 韩版) | HetCCL (May 2026, arXiv:2605.31000, 中版) |
|:-----|:------------------------------------------|:------------------------------------------|
| 机构 | 韩国（Samsung/LG/학계）| 中国（多家机构）|
| 核心思路 | RDMA-based, 统一 vendor backend | **border-communicator** 机制利用 vendor 库自身 reduce |
| 硬件支持 | NVIDIA + AMD | **4个不同厂商** |
| 性能对比 | 匹配 NCCL/RCCL 单厂商性能 | **17-19× vs Gloo** |
| 场景 | 同厂商扩展 | **跨厂商混合集群** |

### 核心设计

| 组件 | 技术详情 |
|:-----|:---------|
| **Efficient P2P Transport** | 跨异构设备的直接 P2P，消除 host-device 内存拷贝，控制 offload 到 CPU |
| **Border-Communicator** | 利用 vendor CCL 库自身的 reduction 操作实现厂商无关的组合——不依赖任何厂商的私有 reduction 路径 |
| **Hierarchical Topology Abstraction** | 将集群解构为 cluster-level primitives，保证最优跨集群数据传输量和带宽利用率 |

### 性能数据

| 场景 | 结果 |
|:-----|:------|
| 异构通信带宽 vs Gloo | **17-19×** |
| 端到端训练加速 | **16.9% per-step-time** |
| 厂商支持 | 4个不同厂商 |
| 评估设置 | 4种异构配置，包含 benchmark 和 end-to-end LLM 训练 |

### 意义

- 随着厂商多元化（NVIDIA → AMD/Intel/中科曙光等），HetCCL 的推出时机非常关键
- Border-communicator 的设计哲学——"利用 vendor 自己的 reduction 而非重新实现"——是务实的跨厂商策略
- 与 7/01 的 HetCCL（韩版）形成互补：前者聚焦**统一接口暴露 RDMA**，后者聚焦**利用现有库**实现跨厂商
