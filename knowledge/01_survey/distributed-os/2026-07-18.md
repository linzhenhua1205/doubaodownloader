## 1️⃣ 🔄 LiveR: 细粒度弹性训练实时重配置 — 14-23× 超越 checkpoint/restart

**来源**: arXiv:2605.22014 (2026-05-21) · 作者: Haoyuan Liu, Kairui Zhou 等 7 位 (Shizhen Zhao, Wei Zhang 团队)
**链接**: https://arxiv.org/abs/2605.22014

### 问题

训练规模越大，**利用低价波动性 GPU 资源**（spot instance、可回收资源）的经济动力越强。但这类资源只给很短**预警窗口**（分钟级）——现有弹性训练系统在 resize 时做 **stop-and-restart**：

```
checkpoint 存储 -> 重建分布式运行时 -> 新拓扑 CUDA init -> communicator setup -> 重启训练
```

每个 resize 事件产生大量停机时间（I/O + 进程重启 + 通信域建立），使得短暂预警窗口内无法完成弹性适配。

### 核心方案 — LiveR

LiveR 用 **live bounded-memory handoff**（有界内存热移交）替代存储回退重启：

| 组件 | 功能 |
|:-----|:------|
| **目标世界异步准备** | 当前世界继续训练的同时，异步准备好目标世界 |
| **新Worker隔离引导** | 新增 worker 在隔离环境中做 CUDA init 等重型操作，不阻塞主路径 |
| **在线状态流式重分布** | 模型状态经高速互联直接流式传输，在线重塑 TP/PP/DP 维度 |
| **轻量 commit** | 目标世界就绪后，执行轻量 commit 切换训练配置 |

> **关键**: 不是"停-存-搬-启"，而是"边跑边备、备完即切"。

### 性能数据

| 指标 | 数据 |
|:-----|:------|
| 重配置速度 | 对比 checkpoint/restart 基线 **14×-23× 加速** |
| 停机时间 | 从**分钟级缩短到秒级** |
| 稳态开销 | **极小**（几乎不影响正常训练） |
| Goodput | **高达 99%**（波动性资源条件下） |
| 实现 | 基于 Megatron-LM + PyTorch |
| 适用配置 | 支持跨 TP/PP/DP 维度的在线重塑 |

### 意义

- **与 [NVIDIA NTP (07-17)](2026-07-17.md) 互补**: NTP 在 TP 域内做动态降/升 TP degree，LiveR 在**完整并行策略空间**（TP×PP×DP）做热切换
- **与 [BACE-Pipe (07-07)](2026-07-07.md) 互补**: BACE-Pipe 是跨区域 PP 编排调度，LiveR 是弹性训练场景下的拓扑动态适配
- 核心价值：**让波动性 GPU 资源真正可用于 LLM 训练**——不再需要漫长的 checkpoint/restart

## 2️⃣ 🔮 OrchestrRL + RFabric: 解耦RL动态计算与光电路网络编排 — 1.42× 吞吐

**来源**: arXiv:2601.01209 (2026-01-03, v2 2026-03-12) · 作者: Xin Tan, Yicheng Feng 等 (香港中文大学 + 字节跳动)
**链接**: https://arxiv.org/abs/2601.01209

### 问题

LLM 后训练阶段日益采用**解耦 RL 架构**（generation 与 training 分离），但面临两大挑战：

1. **Generation 成为瓶颈**: 动态 workload 偏移 + 严重执行不均衡
2. **网络流量失控**: 解耦阶段产生多样化、动态化的流量模式，**传统静态 Fabric 难以应对**（generation 需高带宽 All-to-All，training 需规则 AllReduce，weight sync 需突发高吞吐）

### 核心方案

#### ① 自适应计算调度器
- 在 generation 步内和步间动态调整并行配置以匹配变化的工作负载特征
- 解决阶段间及阶段内的执行不均衡

#### ② RFabric — 可重构光电混合网络
采用 **光电路交换机**（Optical Circuit Switches）动态重构汇聚层和核心层拓扑：

| 阶段 | 流量模式 | RFabric 适配 |
|:-----|:---------|:-------------|
| Generation | 高带宽 All-to-All | 光电路接通直达路径 |
| Training | 规则 AllReduce | 优化拓扑减少跳数 |
| Weight sync | 突发高吞吐 | 动态带宽分配 |

### 性能数据

| 指标 | 数据 |
|:-----|:------|
| 吞吐提升 (64-H800 实测) | **1.42×** vs 静态基线 |
| 光电路重构粒度 | per-phase / per-step |
| 仿真大规模验证 | RFabric 性能-成本效率 > 静态 Fat-Tree |

### 意义

- **与 [Harvest (07-14)](2026-07-14.md) 互补**: Harvest 关注光电路交换在集合通信算法层面的调度，OrchestrRL 关注在**解耦RL端到端工作流**中光电路的动态编排
- **首次将光电路交换应用于解耦 RL 场景**——证明光网络在 AI 训练-推理混合工作负载中的价值
- 与传统的"固定拓扑、静态网络"范式形成鲜明对比

## 3️⃣ ⚙️ Resource-aware Computation-Communication Overlap — 25.5% 执行时间减少 / 零库修改

**来源**: arXiv:2606.09200 (2026-06-08) · **ISC 2026 Workshop (AI on HPC)** · 作者: Minyu Cui, Miquel Pericas
**链接**: https://arxiv.org/abs/2606.09200

### 问题

多 GPU 训练中**算通重叠**虽然理论上被广泛支持，但在实际中往往效果有限。原因是通信 kernel 需要 **on-chip 资源**（SM/GPU 核心）才能推进，而计算 kernel 在调度器层面占用了大部分 on-chip 资源——两个问题叠加：

1. 计算 kernel 的 **occupancy 过高**，通信 kernel 无资源可执行
2. 通信 stream 的**调度优先级不足**，计算 kernel 不主动让出资源

### 核心方案 — 两个运行时控制

不修改 vendor 库（NCCL/cuBLAS 不动），仅用**两个 portable 运行时控制**：

| 技术 | 机制 | 效果 |
|:-----|:------|:------|
| **① Shared-memory occupancy shaping** | 通过 per-block 共享内存分配**调控计算 kernel 的 residency**，为通信 kernel 留出 on-chip 资源 | 通信 kernel 得以并行执行 |
| **② Elevated scheduling priority** | 给通信 stream 分配**更高的调度优先级** | 一旦资源可用，通信 kernel 优先获取执行权 |

### 覆盖 GPU 代际

| GPU | 架构 | 效果 |
|:----|:-----|:------|
| NVIDIA A40 | Ampere | ✅ 有效 |
| NVIDIA A100 | Ampere | ✅ 有效 |
| NVIDIA H100 | Hopper | ✅ 有效 |
| AMD MI250X | CDNA 2 | ✅ 有效 |
| **共 4 代 x 2 厂商** | A/H 全系列 + AMD | **最高 25.5% 执行时间减少** |

### 性能数据

| 指标 | 数据 |
|:-----|:------|
| 执行时间减少 | **最高 25.5%** |
| 修改量 | **零** — 不修改 vendor 库/kernel |
| 覆盖 GPU | A40, A100, H100, MI250X |
| 可移植性 | 通用 CUDA runtime API |

### 洞察

> **关键**: 算通重叠的问题往往不是"算法设计"问题，而是**GPU 内部资源调度**问题。在计算 kernel 持续用满所有 SM 时，即使通信 kernel 被正确发射也无法执行。调节 occupancy 和优先级——两个运行时控制的巧妙组合——在不需要修改 NCCL 或任何 kernel 代码的前提下实现了大幅重叠。
>
> 这为集群运维提供了一个**零侵入、可快速部署**的优化手段——适用于无法随意升级 NCCL 版本的生产环境。
