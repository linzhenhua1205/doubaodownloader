## 1️⃣ 🔧 DITRON: 分布式多级Tiling编译器 — 已部署生产，节省50万GPU小时/月 (arXiv:2605.02953)

- **来源**: arXiv:2605.02953, "DITRON: Distributed Multi-level Tiling Compiler for Parallel Tensor Programs" (2026-05-02)
- **作者**: Size Zheng et al. (18位作者，共13个机构，含NVIDIA/Microsoft?)
- **标签**: `Compiler` · `Tiling` · `NCCL` · `Distributed Kernel` · `Production` · `MFU`
- **录用**: 未标注会议

### 核心思想

当前分布式编程的"刚性"瓶颈——CuBLAS/NCCL性能优但缺乏灵活性，现有tensor compiler又无法有效处理分布式集群的多级内存层次。

**DITRON 三层抽象**:

| 层级 | 抽象 | 功能 |
|:-----|:------|:------|
| **Core** | 核心级 | 单运算单元调度 |
| **Device** | 设备级 | 跨GPU/SM的局部通信与同步 |
| **Task** | 任务级 | 跨节点通信（直接操作NCCL collective） |

**关键特性**:
- 自动将NCCL collective集成到编译流程，非手动调库
- 支持NVIDIA + AMD双平台
- 企业级部署，training + inference双场景

### 性能数据

| 场景 | 加速比 |
|:-----|:-------|
| 单kernel vs 专家手写CUDA | **6%-30%** |
| vLLM端到端推理 | **5%-30%** |
| 训练MFU提升 | **>10%** |
| 推理端到端 | **>20%** |
| GPU小时节省 | **~500,000 GPU小时/月** |
| 应用场景 | 云服务推理 + 边缘推理 |

### 意义

- DITRON是首个**将NCCL collective作为编译器原语**的tensor compiler——让编译器自动决策通信方案，无需开发者手动优化
- 企业级部署验证了"编译器驱动分布式通信"的现实可行性
- 10%+ MFU提升意味着每10000-GPU集群每月节省约**150万GPU小时**

## 2️⃣ 🩺 CCL-D: 集合通信慢/挂异常高精度诊断 — 6分钟定位 (PPoPP'26, arXiv:2605.04478)

- **来源**: arXiv:2605.04478, "CCL-D: A High-Precision Diagnostic System for Slow and Hang Anomalies in Large-Scale Model Training" (2026-05-06)
- **作者**: Yida Gu et al. (20位作者)
- **录用**: **PPoPP 2026**
- **标签**: `Diagnostics` · `Slow/Hang` · `4000-GPU` · `Production`

### 问题

CXL库异常是分布式训练中最频繁、最耗时的诊断类别——传统方法**数小时甚至数天**才能根因分析。

### CCL-D 设计

**Rank-level real-time probe + Intelligent decision analyzer**:

1. **轻量分布式trace框架**：监控跨层异常指标（通信流量维度）
2. **智能决策分析器**：自动异常检测 + 根因定位，精确识别**故障GPU rank**

### 部署验证

| 指标 | CCL-D |
|:-----|:-------|
| 部署规模 | **4000-GPU** 集群 |
| 部署时长 | **超过1年** |
| 已知异常覆盖 | **近乎全覆盖** |
| 定位时间 | **6分钟内**精确定位受影响rank |
| 对比传统方法 | "传统方法需要数小时甚至数天" |

### 意义

- 继ARGUS(System, ASPLOS'26)之后，CCL-D是**集合通信层面的生产级诊断系统**的里程碑
- ARGUS定位"万卡追踪"(高性能trace)，CCL-D定位"慢/挂诊断"(高精度根因)
- 6分钟定位 = 故障MTTR从小时级降至分钟级——对万卡集群训练可靠性至关重要

## 3️⃣ ⚙️ CAIS: 计算感知In-Switch计算 — 超越NVLink SHARP 1.38× (HPCA 2026, arXiv:2605.05628)

- **来源**: arXiv:2605.05628, "Towards Compute-Aware In-Switch Computing for LLMs Tensor-Parallelism on Multi-GPU Systems" (2026-05-07)
- **作者**: Chen Zhang et al. (北京大学/上海交大)
- **录用**: **HPCA 2026**
- **标签**: `In-Switch Computing` · `NVLink SHARP` · `TP` · `Compute-Aware`

### 问题

NVLink SHARP (NVLS) 加速collective通信，但其**通信中心设计**与LLM计算的**内存语义需求**不匹配——计算和通信阶段隔离，资源利用率低。

### CAIS 三技术

| 技术 | 作用 |
|:-----|:------|
| **Compute-aware ISA + microarchitecture** | 使交换机感知计算的内存语义需求，实现通信模式对齐 |
| **Merge-aware TB Coordination** | 提高时间对齐，高效请求合并 |
| **Graph-level dataflow optimizer** | 实现紧密的跨kernel重叠（GPU compute + switch compute并行） |

### 性能数据

| 对比项 | 加速比 |
|:-------|:-------|
| vs SOTA NVLS-enabled solution | **1.38×** 端到端训练 |
| vs T3 (SOTA overlap方案，未用NVLS) | **1.61×** |
| 适用场景 | LLM Tensor Parallelism |

### 意义

- 首次提出**"计算感知"in-switch computing**方向——交换机不再只是"加速collective"，而是**参与计算**
- 与NVLS形成互补：NVLS减少冗余传输，CAIS进一步对齐计算语义
- 对超节点tensor parallelism场景有直接价值

## 4️⃣ 📦 ZipCCL: 无损压缩集合通信 — 1.35×通信加速 (arXiv:2604.27844)

- **来源**: arXiv:2604.27844, "ZipCCL: Efficient Lossless Data Compression of Communication Collectives for Accelerating LLM Training" (2026-04-30)
- **作者**: Wenxiang Lin, Xinglin Pan, Ruibo Fan, Shaohuai Shi, Xiaowen Chu (香港理工大学/香港科技大学广州)
- **标签**: `Lossless Compression` · `Gaussian Distribution` · `Exponent Coding` · `MoE`

### 核心观察

LLM训练通信数据（activation/gradient/parameter）遵循**近高斯分布**——这为无损压缩提供了理论基础。

### ZipCCL 三技术

1. **Exponent coding**：基于LLM张量高斯分布的理论保障加速压缩，**无需在线统计**（即插即用）
2. **GPU-optimized compress/decompress kernel**：通信感知数据布局 + 内存访问模式优化 + pipeline
3. **Adaptive communication strategy**：根据工作负载和系统特征动态切换collective操作

### 性能数据 (64-GPU集群)

| 指标 | 提升 |
|:-----|:------|
| 通信时间缩减 | **最高1.35×** |
| 端到端训练加速 | **最高1.18×** |
| 模型精度影响 | **完全无损** |
| 适用模型 | MoE + Dense Transformer |

### 对比其他压缩方案

| 方案 | 类型 | 精度影响 | 加速 |
|:-----|:------|:---------|:-----|
| DynamiQ (7/01调研) | 有损量化 | 99.9% BF16 | 34.2% |
| NCCLZ (6/27调研) | 解耦量化+熵编码 | 可调精度 | — |
| **ZipCCL** | **无损压缩** | **完全无损** | **1.18× end2end** |

ZipCCL与DynamiQ、NCCLZ形成互补：无损场景用ZipCCL，可容忍精度损失场景用有损方案追求更高加速。

## 5️⃣ ⏱️ CommFuse: P2P分解消除尾延迟 — 替代RS/AG (arXiv:2604.24013)

- **来源**: arXiv:2604.24013, "CommFuse: Hiding Tail Latency via Communication Decomposition and Fusion for Distributed LLM Training" (2026-04-27)
- **作者**: Rezaul Karim, Austin Wen, Wang Zongzuo, Weiwei Zhang, Yang Liu, Walid Ahmed
- **标签**: `Tail Latency` · `P2P` · `Reduce-Scatter` · `All-Gather` · `Overlap`

### 核心思想

将传统collective操作（reduce-scatter / all-gather）**分解为P2P通信**，然后调度分块计算实现细粒度重叠。这一方案**彻底消除尾延迟**（tail latency），这是现有data-slicing overlap方案无法解决的痛点。

### 方法

| 组件 | 传统方案 | CommFuse |
|:------|:---------|:----------|
| 通信原语 | Reduce-Scatter / All-Gather | **P2P decomposed** |
| 重叠粒度 | coarse-grained | **fine-grained** |
| 尾延迟 | 存在（data-slicing通病） | **消除** |
| 兼容性 | — | DP + TPSP + UP |

### 性能数据

CommFuse在延迟、MFU和吞吐三个维度**一致优于**现有方案（但论文未提供如"3.5×"等具体数字，以"consistently achieves lower latency, superior MFU, and high throughput"描述）。

### 意义

- 与Lagom (7/01) 互补：Lagom通过cost model调优overlap参数，CommFuse通过**重构通信模式**从根源消除尾延迟
- P2P分解替代collective的思路与NIMBLE (multi-path balancing) 形成技术共鸣

## 6️⃣ 🚄 RRFP: 就绪驱动流水线运行时 — 最高2.77×加速 (arXiv:2605.18750)

- **来源**: arXiv:2605.18750, "A Readiness-Driven Runtime for Pipeline-Parallel Training under Runtime Variability" (2026-05-18)
- **作者**: Ruitao Liu, Xinyang Tian, Shuo Chen et al. (清华大学/Scitix AI)
- **标签**: `Pipeline Parallelism` · `Readiness-Driven` · `Megatron` · `128 GPUs`

### 问题

现有pipeline系统使用**静态/预提交schedule**。当运行时任务就绪度偏离预期顺序时，stage等待**未就绪的任务**而不可执行的工作被闲置——stage misalignment + idle bubble。

### RRFP 核心

将schedule从"序列约束"改为**"非绑定提示排序"** —— 只用来排序当前就绪的工作，而非必须遵循的执行顺序。

**三组件**:
1. **Message-driven asynchronous communication** — 消息驱动的异步通信
2. **Lightweight tensor-parallel coordination** — 轻量TP一致性协调
3. **Ready-set arbitration** — 低开销就绪组调度

### 性能数据 (最高128 GPU)

| 场景 | 加速 vs 固定顺序baseline |
|:-----|:--------------------------|
| 纯语言模型 (BFW hint) | **最高1.77×** |
| 多模态 (BFW hint) | **最高2.77×** |
| 跨框架对比 (BF hint, vs最快外部系统) | **最高1.84×** |
| 训练正确性 | **全程保持** |

### 意义

- 从"schedule驱动"到"readiness驱动"的**流水线范式转变**
- 对pipeline bubble的消除效果显著——尤其多模态场景（计算特征差异大）达2.77×
- 与TawPipe (6/30, 拓扑感知权重流水线) 形成互补：TawPipe解决通信拓扑，RRFP解决运行时调度

## 7️⃣ 🖥️ RATrain: 带宽约束异构超算LLM训练运行时 — 1.35×, 97%效率 (arXiv:2606.10415)

- **来源**: arXiv:2606.10415, "RATrain: A Resource-Aware Training Runtime for Large Language Models on Bandwidth-Constrained Heterogeneous Supercomputing Platforms" (2026-06-09)
- **作者**: Yao Lu, Shiqing Ma, Zhongzhi Luan et al. (北京航空航天大学)
- **标签**: `Heterogeneous` · `MT-3000` · `Bandwidth-Constrained` · `1F1B` · `Scaling`

### 背景

国产MT-3000超算平台：**显式内存层次结构 + 有限可用DDR（20GB/cluster）+ 约束的集群间通信**，GPU优化运行时无法直接适配。

### RATrain 设计

将标准1F1B训练形式化为**training-state lifecycle调度问题**，在layer-level和stage-local粒度调度：

| 调度项 | 描述 |
|:-------|:------|
| 梯度同步 | 异步 + 压缩 |
| 参数更新 | 紧耦合调度 |
| Parameter-view prefetching | 参数视角预取 |
| 激活值恢复 | 重计算调度 |

**MT-3000-aware执行后端**：高效可预测FP16 GEMM、Attention Backward、显式数据搬移

### 性能数据

| 指标 | RATrain |
|:-----|:---------|
| vs MT-3000适配GPU策略 | **1.35×** end-to-end |
| LLaMA-2-7B扩展 | **1024 cluster, 112,790 tokens/s** |
| Scaling效率 | **97.0%** |
| Loss轨迹偏差 | **0.081%** (1.028B token验证) |
| 可用DDR约束 | 20GB/cluster下可行配置自动选择 |

### 意义

- 国产超算生态的关键软件栈突破——让标准LLM在**非GPU架构**上高效运行
- "Resource-aware planning"思路可推广到**一切带宽约束的混合集群**
- 与HetCCL (7/01, 混合厂商) 构成异构计算的一体两面：HetCCL解决厂商间通信，RATrain解决单厂商条件下的资源适配

## 8️⃣ 📉 When Scaling Fails: 网络和互联对分布式训练失效的实证研究 (arXiv:2603.04424)

- **来源**: arXiv:2603.04424, "When Scaling Fails: Network and Fabric Effects on Distributed GPU Training Performance" (2026-02-16)
- **作者**: Dinesh Gopalan, Ratul Ali
- **标签**: `Scaling` · `Network Topology` · `Congestion` · `Fabric` · `Empirical Study`

### 核心论点

**相同模型+相同软件栈在不同互联设计下呈截然不同的扩展特征**。超出小规模后，网络拓扑、拥塞动力学、collective同步行为和GPU locality主导端到端训练性能。

### 三大失效模式

| 失效模式 | 描述 |
|:---------|:------|
| **Synchronization amplification** | collective同步放大延迟，少量慢节点拖累整体 |
| **Topology-induced contention** | 拓扑设计引发的资源竞争 |
| **Locality-driven performance variance** | GPU位置差异导致的性能方差 |

### 关键发现

- 这些效应**对标准profiling工具不可见** → 常被误诊为框架/模型层问题
- 经验法则：一旦跨节点训练，**网络/互联就是第一因**

### 意义

- 为前5期调研的所有集合通信优化工作提供了**理论背景**——为什么需要这些优化
- 对系统构建者提出"诊断先行"原则：在优化之前，先**正确诊断scaling失效的根因**
- 与CCL-D (本期间)、ARGUS (6/29) 形成诊断三件套：ARGUS(追踪) → CCL-D(诊断) → WS-Fails(实证)
