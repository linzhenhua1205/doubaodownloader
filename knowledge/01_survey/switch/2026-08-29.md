### 1.2 草案间的关系网（从引用关系看设计意图）

- **LQ Telemetry** 自称是 FANN 问题陈述（draft-ietf-rtgwg-net-notif-ps，即被 WG 采纳前的编号）所呼吁的"信息模型"的**拥塞场景实现**——问题陈述 §5.1 要求定义通知承载的信息，LQ Telemetry 的 YANG 结构直接作答。
- **LQ Telemetry** 在 FANN Framework 的术语体系里定位清晰：helper node = 通知源（spine），load-balancer node = 消费者（leaf），link-local scoping = 框架的"通知域隔离"实例。
- **FARE（draft-xu-idr-fare，BGP Path Bandwidth）** 与 LQ Telemetry 构成**双平面**：FARE 传静态容量（秒级），LQ 传动态拥塞（毫秒级），两者在 leaf 上融合为加权 ECMP 权重。
- **LSN（draft-camarillo-rtgwg-lsn，Lightspeed Notification Protocol）** 与 LQ Telemetry 是**竞争/对照关系**：LSN 是硬件加速转发面信令（sub-100μs 收敛、硬件 veto 剪枝拥塞路径），LQ Telemetry 是厂商无关 YANG 模型 + 渐进式 256 级质量分——草案作者明言"与 LSN 的融合或分化将是 FANN 的关键讨论"。
- **UEC CSIG**（带内逐跳拥塞标记 + 接收 NIC 反射）与 LQ Telemetry 被定位为**互补**：CSIG 以 RTT 时标指导端主机传输，LQ Telemetry 以带外 switch-to-switch 通知指导交换机级加权 ECMP。

## 二、Fast CNP with Proxy 深度解析（draft-xiao-fann-fast-cnp-with-proxy-02）

> 来源：IETF Datatracker 草案全文（08-29 抓取）。URL: https://datatracker.ietf.org/doc/draft-xiao-fann-fast-cnp-with-proxy/
> 作者：Xiao Min（ZTE）/ Kan Zhang（中国移动）/ Zehua Hu（中国电信）；前身 draft-xiao-rtgwg-proxy-congestion-notification（rtgwg→fann 转移，印证 FANN 承接拥塞控制主战场）；Intended status: Standards Track；2026-08-07 更新至 -02

### 2.1 四种拥塞通知机制的演进谱系

草案将拥塞通知机制系统梳理为四代，Fast CNP with Proxy 是第四代：

| 世代 | 机制 | 通知路径 | 代表 |
|:--|:--|:--|:--|
| ① | 经典无专用包 | 拥塞点 ECN 标记 → 接收者 TCP 标记 → 发送者降速 | RFC 3168 |
| ② | 经典专用包 | 拥塞点 ECN 标记 → 接收者发专用 CNP → 发送者 | IBTA RoCEv2 CNP |
| ③ | Fast CNP 无代理 | 拥塞点**直接**发专用 CNP → 发送者 | draft-xiao-fann-fast-cnp（07-26） |
| ④ | **Fast CNP with Proxy** | 拥塞点 → **代理节点**（翻译）→ 发送者 | 本文档（08-07） |

**设计动机（草案 §1 原文逻辑）**：拥塞节点直接通知发送者的前提是"拥塞节点知道每个发送者支持哪种通知格式"——这在两种场景下不成立：① **VPN P 路由器**与 CE 处于不同路由域，无法直发；② 发送者**只支持标准 RoCEv2 CNP** 时，拥塞节点难以构造标准 CNP（需深度解析）。代理节点的引入解耦了"拥塞检测"与"格式翻译"两个职责。

### 2.2 代理节点选择三规则

- 代理节点**必须知道**发送者支持的拥塞通知格式（如标准 RoCEv2 CNP 或 UEC BTS）。
- 代理节点与拥塞节点**必须处于同一路由域**。
- RoCEv2 场景下，代理节点**必须位于正反向流量都经过的位置**——因为需要通过数据流量学习 Source QP ↔ Destination QP 映射表（代理不解析 payload 就无法建立 QP 映射）。
- 位置建议：**尽量贴近发送者**（如数据中心 leaf switch）；具体选择是部署相关，超出本文档范围。

### 2.3 两种通知包格式（从场景反推协议设计）

| 维度 | Option 1（数据中心） | Option 2（VPN WAN） |
|:--|:--|:--|
| 适用场景 | 拥塞节点 = DC 内 spine switch | 拥塞节点 = VPN P 路由器 |
| UDP 载荷 | IP 五元组 + TC/ToS + **Destination QP（24bit）** | IP 五元组 + TC/ToS + **NRP Selector ID** |
| 翻译依据 | QP 映射表（正反向流量学习） | NRP Selector ↔ Source QP 映射 + VPN ID 映射 |
| 深度解析需求 | 需解析 IP 五元组 | P 路由器不做深度解析（五元组在 VPN 封装下） |
| 第二跳通知 | 标准 RoCEv2 CNP 或 UEC BTS | 同左（经 PE 翻译） |

**设计亮点**：两种格式用"是否做深度包解析"区分——数据中心 spine 有 ASIC 解析能力（Option 1 带 QP 细粒度），VPN P 路由器只转发不解析（Option 2 用 NRP Selector ID 间接标识流）。UDP 目的端口 TBD1/TBD2 申请 IANA 系统端口段，为**硬件卸载**预留了标准锚点。

### 2.4 代理能力通告（PNC）：控制面三平面

- **IS-IS**：Prefix Attribute Flags 新增 PNC Flag（Bit 7，仿 RFC 9088 ELC E-flag）；跨 level 传播必须保留。
- **OSPFv2/v3**：Prefix Extended Flags 新增 PNC Flag（Bit 2，仿 RFC 9089 ELC）；ABR 跨区域分发必须保留。
- **BGP**：Next Hop Dependent Characteristic Codes 新注册 PNC TLV（code TBD3，载荷为代理节点 IP）——复用 draft-ietf-idr-nhc 框架。
- **语义**：PNC 是"节点属性 + 前缀绑定"——代理节点为其身后发送者的前缀通告"我是这些发送者的拥塞通知代理"，拥塞节点据此建立"发送者 → 代理"地址映射表。

### 2.5 安全设计

- 限速：生成/接收拥塞通知消息必须限速（防 DoS）。
- 边界过滤：域内部署，进出口必须丢弃域外拥塞通知。
- 默认关闭：代理功能默认禁用，需显式配置启用。

**技术评价**：这是一个典型的"兼容性桥接"设计——不要求升级全网设备，只要求拥塞点（spine/P 路由器）+ 代理点（leaf/PE）支持，发送者侧零改动（仍收标准 RoCEv2 CNP）。对存量 RoCEv2 部署（中国互联网大厂 + 运营商云）是**低门槛升级路径**，且显式对接 UEC BTS——**把 UEC 生态纳入 RoCEv2 兼容面**，是标准面争夺 AI 网络拥塞控制话语权的关键落子。

## 三、LQ Telemetry 深度解析（draft-praveen-fann-lq-telemetry-info-00）

> 来源：IETF Datatracker 草案全文（08-29 抓取）。URL: https://datatracker.ietf.org/doc/draft-praveen-fann-lq-telemetry-info/
> 作者：S. Praveen K. Pasalapudi / Vishnu Pavan Beeram（均为 HPE）；Intended status: Standards Track；2026-07-21 发布；**2026-08-28 通过 IETF 官方 YANG 验证（xym/pyang/yanglint 三工具 0 errors 0 warnings）**

### 3.1 要解决的问题：拥塞可见性缺口（Congestion Visibility Gap）

3-stage CLOS 中，源 leaf（L1）发往远端 leaf（L4）有多条等价路径（经 spine S1/S2）。**DLB（动态负载均衡）只监视本地上行链路质量，看不到远端链路（spine→L4）质量**——若 S2→L4 严重拥塞而 L1→S2 健康，L1 继续向 S2 灌流量，S2 排队或丢包。三个断层：
1. L1 对 S2→L4 链路质量**无可见性**；
2. S2 没有标准方式告诉 L1 拥塞；
3. 即使能告诉，L1 也没有标准方式消费该数据做转发决策。

**这是 AI 训练网络自适应路由（adaptive routing）缺失的"下一跳可见性"（NNH visibility）**——AI 工作负载的同步突发流量产生毫秒级瞬时拥塞，等 RTT 级反馈（ECN/DCQCN）已经晚了。

### 3.2 双平面架构：慢平面定容量，快平面定拥塞

```
weight(path_i) = f( FARE_capacity(i), LQ_quality(i) )
```

| 平面 | 机制 | 时标 | 决定 |
|:--|:--|:--|:--|
| 慢平面 | BGP/FARE（Path Bandwidth） | 秒级 | 哪些路径存在、最大容量 |
| 快平面 | LQ Telemetry（本草案） | 毫秒级（硬件加速亚 100μs） | 每条路径当前可用多少 |

路径资格判定 = 慢平面允许（BGP 路由安装）**AND** 快平面健康（LQS > 0）。在 3-stage CLOS：spine = helper（生成通告），leaf = load-balancer（消费通告计算加权 ECMP）；5-stage CLOS：spine 为 dual 角色（对 super-spine 是 load-balancer，对 leaf 是 helper）。

### 3.3 数据模型三层设计

| 层 | 字段 | 强制性 | 用途 |
|:--|:--|:--|:--|
| Tier 1 Core | LQS（0-255）、CL（0-7）、可用带宽（Gbps）、远端节点 ID、链路 ID、远端 AS | 必须 | 仅凭 Tier 1 即可做转发决策 |
| Tier 2 Metadata | 节点 ID、AS、序列号、时间戳、信令模式 | 必须 | 校验与新鲜度 |
| Tier 3 Diagnostics | 队列深度、ECN 标记率、PFC pause 占比、丢包指示、链路容量 | 可选 | 排障/分析，禁止用于转发决策 |

**LQS 语义**（0=不可用，255=完全可用）：255 无拥塞 / 192-254 健康 / 128-191 中等负载 / 64-127 显著拥塞 / 1-63 严重拥塞 / 0 失效。**CL 语义**（0-7）：0 无 → 4 显著（ECN/DCQCN 激活）→ 5 高（PFC 激活）→ 6 严重（背压传播）→ 7 危急（丢包或不可用）。

**互操作约束的精妙之处**：LQS 计算方式实现自定义，但**必须是各拥塞指标的单调函数**（任一指标恶化 → LQS 不增）；同一 ECMP 组内建议使用同一计算实现（附录 A 提供推荐检测管线：硬件信号 → 派生指标 → 非对称 EWMA 平滑 → LQS 计算 → CL 映射 → 滞回状态机）。默认通告间隔 **T_notify = 20ms**，周期 + 触发双模式。

### 3.4 UDP 传输绑定：亚 100μs 的硬件路径

配套草案（draft-praveen-fann-lq-telemetry-udp）定义紧凑固定偏移二进制编码——**能在转发面（ASIC）直接生成和消费**，亚 100μs 通知延迟，同时保留 UDP/IP 的可路由性、可管理性与载荷丰富性；还提供 Router-Info 载体（借用其认证与刷新率协商）。**数据模型与传输解耦**——未来可加 gRPC/gNMI 绑定而无需改模型（RFC 8791 structure 是规范核心，模型层稳定）。

### 3.5 与 UEC CSIG 的互补性（草案原文立场）

UEC CSIG 是带内逐跳机制：拥塞状态在转发面逐跳更新，由接收 NIC 反射给发送者做速率控制与路径选择——**以 RTT 时标指导端主机传输**。LQ Telemetry 是带外 switch-to-switch：给负载均衡交换机 NNH 可见性，**以毫秒时标指导交换机级加权 ECMP**。两者可共存于同一 fabric：带内信号指挥端主机传输，LQ Telemetry 指挥交换机转发。

## 五、分析段落

### 分析①：FANN 从"问题定义"到"解决方案族"——IETF 标准面反攻的组织化信号

把 08-28 与 08-29 两日数据并置，AI 网络快速通知的竞争格局出现**第二次质变**：08-28 是"IETF 成立专门工作组"（组织化起点），08-29 是"工作组内七条技术线齐备"（组织化成型）。五周内（07-03~08-07）提交的 10 份 individual I-D + 1 份 WG Document 构成了完整的技术栈：**检测（Fast CNP）→ 翻译（Proxy）→ 控制（SRv6-CC）→ 遥测（LQ Telemetry）→ 框架（Framework）→ 建模（YANG）→ 通告（Router-Info）→ 跨域（PFC/FGFC）**。

从第一性原理看，这对应 NVIDIA 私有方案的**每一层都出现了标准面对位**：NVIDIA MRC 的微秒级检测 ↔ Fast CNP 标准扩展；NVIDIA 私有遥测的"租户噪声隔离" ↔ LQ Telemetry 的厂商无关质量分；NVIDIA Multiplane 的拓扑冗余 + 私有 TE ↔ FARE×LQ 双平面加权 ECMP；NVIDIA 的 2.68ms/100ms 演示口径 ↔ LSN 的 sub-100μs 目标。更关键的是**参与方结构**：华为、ZTE、中国移动/电信/联通、腾讯、HPE、Cisco、Futurewei——中美欧运营商与设备商全线入场，这不是单一厂商的游说，而是**产业联盟级的标准竞争**。对交换机厂商的含义：2027 年新品若要在"故障响应"维度有竞争力，标准面（FANN）与私有面（NVIDIA）两条路线都必须跟踪，且**标准面落地的速度正在加速**——FANN 从 BOF 到 11 份文档仅用约两个月，远超 IETF 平均节奏。

### 分析②：Fast CNP with Proxy——中国主导的"存量兼容"路线与 UEC 桥接

这份草案的产业意义被低估了。表面看它只是拥塞通知的格式翻译器，但拆解后有三层战略含义：

**第一层（兼容性）**：它不要求全网升级——拥塞点（spine/P 路由器）+ 代理点（leaf/PE）支持即可，发送者（GPU 服务器 NIC）零改动继续收标准 RoCEv2 CNP。这对中国互联网大厂与运营商云的海量存量 RoCEv2 部署是**最低摩擦的升级路径**。对比 NVIDIA 的 MRC（要求 NIC 与交换机同时升级到私有栈），标准面的"渐进兼容"策略直击私有方案的最大软肋——**全栈替换成本**。

**第二层（生态桥接）**：代理节点翻译的目标格式显式包含 **UEC BTS（Back To Sender）**——这意味着 UEC 生态（Broadcom Thor、Arista、微软等）的拥塞通知机制可以反向兼容 RoCEv2 存量网络。UEC 作为"非 NVIDIA 以太网联盟"，其 BTS 协议与 RoCEv2 CNP 的桥接正是其生态扩张的关键一步，而这份草案由 ZTE+中国移动+中国电信主导，**把中国运营商的网络话语权嵌入了 UEC 生态扩展路径**。

**第三层（硬件锚点）**：TBD1/TBD2 UDP 端口 + IS-IS/OSPF/BGP PNC 通告 + QP/NRP 映射表——全部设计为**可硬件卸载**的固定格式。对交换芯片厂商（Broadcom/Cisco Silicon One/国产芯片）而言，这意味着拥塞通知代理可以做成 ASIC 原生功能，而非 CPU 慢路径处理。**谁先在芯片里实现 PNC + QP 映射加速，谁就拿到了 AI 网络拥塞控制标准化的先发生态位**。

### 分析③：LQ Telemetry 双平面——自适应路由标准化的关键拼图

LQ Telemetry 的价值在于它回答了 FANN 问题陈述留下的一个悬而未决的问题：**通知到达后，消费方（交换机）拿它做什么？** 答案从草案的架构设计中可以读出——**加权 ECMP**。

这里有一个值得注意的设计判断：草案明确**禁止接收方用 Tier 3 诊断指标做转发决策**（"These metrics are NOT interoperability fields. Receivers MUST NOT use them for forwarding decisions"）——只有 Tier 1（LQS/CL/带宽）可入转发路径。这是对"遥测泛滥"的克制：**转发决策只需要一个单调、可比较、跨厂商一致的质量标量，而不是一堆原始计数器**。LQS 的"实现自定义 + 单调性约束 + 推荐管线"三元组设计，在"厂商差异化"与"跨厂商可比性"之间取了精妙的平衡——这比 NVIDIA 的私有遥测体系（全栈自家闭环）对多厂商数据中心明显更友好。

与 UEC CSIG 的互补定位同样关键：**带内逐跳（CSIG）指挥端主机，带外 switch-to-switch（LQ）指挥交换机**——这是两个不同控制回路，时标不同（RTT vs 毫秒）、作用对象不同（NIC vs 交换机），可以共存。这暗示标准面的共识方向：**AI 网络的拥塞控制不是单一机制，而是"端到端 + 逐跳 + 交换机级"的多层协同**。对交换机厂商的产品启示：未来 AI 数据中心交换机的差异化竞争点将从"转发性能"（已趋同）转向"**拥塞遥测的精度与消费能力**"——能否亚毫秒级生成/消费 LQ 通告、能否把 LQS 实时映射进加权 ECMP，将成为新一代 AI 交换机的规格表新条目。

### 分析④：私有 vs 开放——AI 网络的两条时间线

将今日标准面进展与本库既有的 NVIDIA 产品线跟踪（08-25/26 详录）对照，两条路线的时间线逐渐清晰：

- **NVIDIA 私有线（2026 兑现）**：Spectrum-6（102.4T，07-21 发布）→ Multiplane 拓扑（512k GPU，Hot Chips 08-25）→ MRC 传输（05-06）→ NVLink Fusion/DSX（Hot Chips）——**全部是"发布即就绪"的产品叙事**，但依赖全栈替换。
- **IETF 标准线（2027+ 兑现）**：FANN WG 成立（08-27）→ 解决方案族齐备（08-29 今日）→ WG Last Call → RFC——**标准流程通常 12-24 个月**，但受益于多厂商生态与渐进兼容。

判断：2026H2-2027H1，NVIDIA 私有方案在"可用性"上领先（已量产）；2027-2028，标准面（FANN/UEC）的**多厂商生态 + 存量兼容**优势将开始兑现。两条路线并非零和——**LQ Telemetry 与 CSIG 互补、Fast CNP Proxy 与 UEC BTS 桥接的设计，说明标准面正在主动与私有/联盟方案共存**。最终格局大概率是：NVIDIA 生态（全栈私有）与开放生态（UEC/FANN 多厂商）在超大规模 AI 工厂并行，而**中间地带（运营商云、政企智算、国产替代）将是标准面渐进兼容路线的主场**——这与中国厂商（华为/ZTE/三大运营商）在 FANN 的主导地位互相印证。
