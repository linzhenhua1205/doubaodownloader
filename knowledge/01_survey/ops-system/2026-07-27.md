## 1️⃣ 🔴 OpenTelemetry 毕业后的四大运维演进方向

**来源**: [CNCF Blog Jul 24 | OpenTelemetry has graduated… Now what?](https://www.cncf.io/blog/2026/07/24/opentelemetry-has-graduated-now-what/) · CNCF

**状态**: OTel 作为可观测性事实标准毕业后的 roadmap，直接影响运维架构决策

### 四个运维影响方向

| 方向 | 运维影响 | 时间线 |
|:-----|:---------|:------:|
| **声明式配置稳定化** | OTel Collector 配置从 Alpha → Stable，减少"配置漂移"类运维事故；可纳入 GitOps 管线 | Alpha→Beta |
| **Profiling Alpha** | 补齐可观测性第四支柱（M+T+L+P），生产性能分析的标准化信号，摆脱 perf/pprof 碎片化 | Alpha |
| **CI-CD 可观测性** | 将 OTel 嵌入 CI/CD 管线——从部署到构建的全链路可观测；CI 失败 = 可观测性事件 | 早期 |
| **Agent 追踪** | Agent 化基础设施的可观测性——追踪 Agent 决策链路而非仅服务调用 | 早期 |

### 对运维团队的实际动作

> 1. **声明式配置** — 评估 OTel Collector 声明式配置与现有 GitOps 管线的集成方式，计划 Beta 后尝试
> 2. **Profiling** — 当前 Profiling 仍在 Alpha，不适合生产首选；但建议在实验室环境试用，为生产化做准备
> 3. **CI-CD OTel** — 如果当前 CI 失败率较高，CI-CD 可观测性是最快获得 ROI 的方向
> 4. **Agent 追踪** — Agent 追踪目前最早期，仅适合 PoC 层探索

### 风险提示

> OTel 标准化 → 厂商锁定风险。主流 APM 厂商已内置 OTel 支持，但差异化功能（如 Datadog APM 的标签体系、New Relic 的 NRQL）可能将标准数据引向专有分析路径。运维团队应优先选择**不依赖商业 SaaS 的分析栈**（如 Prometheus + Grafana + Jaeger + Pyroscope）来保持 OTel 数据路径的中立性。

## 2️⃣ 🟡 Broadcom Platinum 对运维工具链的潜在影响

**来源**: [CNCF Announcements Jul 16 | Broadcom as Platinum Member for AI-Ready Cloud Native Infrastructure](https://www.cncf.io/announcements/2026/07/16/cncf-strengthens-partnership-with-broadcom-as-a-platinum-member-to-advance-ai-ready-cloud-native-infrastructure/)

**状态**: 厂商战略动作，运维影响需跟踪

### 潜在叙事转变

| 维度 | 对运维的影响 |
|:-----|:------------|
| **VMware Tanzu** | Broadcom 加速 K8s 原生化，vSphere-based 运维模式向 K8s-Native 迁移 |
| **AI-Ready 基础设施** | Broadcom 的运维工具重心从「数据中心虚拟化管理」转向「K8s AI 工作负载编排」 |
| **OEM/ODM 关系** | Broadcom 在 CNCF 的 Platinum 地位 → 可能推动与其合作的服务器厂商深度集成 K8s 运维栈 |
