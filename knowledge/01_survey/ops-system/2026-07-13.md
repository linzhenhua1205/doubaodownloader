## 🔴 核心动态

### 1. SRE 4-Body Problem：自治运维的上下文瓶颈与知识图谱解法

> 📄 CNCF Blog, Jul 6 · Sanjeev Sharma (StackGen Field CTO)

**核心框架：任何 SRE 决策都需要同时推理四个领域的信息**

| 领域 | 工具/系统 | 现状问题 |
|:-----|:----------|:---------|
| **Code** | Git / PR / Build | 版本和配置变更历史 |
| **Infrastructure State** | Terraform / K8s / IAM | 期望状态与实际状态的偏差 |
| **Runtime Signals** | Metrics / Logs / Traces / SLO | 系统此刻在做什么，何时开始异常 |
| **Operational Knowledge** | 事后复盘 / ADR / Runbook / Slack | "2022年试过这个，把region搞挂了" |

**关键洞察：**
- 每个领域单独看已基本解决，但**任何真实的运维决策都在四者交叉处**，这里历史上没有系统
- 四者交叉 = 少数资深工程师的大脑（昂贵、稀缺、每两年换一波）
- 目前靠 "people putty"（部落知识）维系——Runbook在上一次Infra变更后就过时了

**解法路径：**
1. **先建知识图谱再放 Agent** — Code × Infra × Runtime × OpsKnowledge 的统一实时图，**价值在边**（提交→Terraform→K8s deploy→OTel延迟→Prometheus SLO burn→半年前的类似incident）
2. **决策轨迹追踪** — 每个Agent动作记录：输入快照 + 生效策略 + 模型版本 + 考虑的假设 + 动作 + 结果
3. **AI在路径中而非事后** — 不是"人做，AI写post-mortem"，而是AI嵌入四领域的连续循环

> **Impact**: ⭐⭐⭐⭐⭐ — 深度契合我们的CodeReview工程化、约束体系、AI生产流水线方法论。与我们的设计思想高度一致

### 2. OTel Don't Wrap — 抽象层导致运维上下文断裂

> 📄 OTel Blog, Jun 24

**警告模式**：团队为了让"使用更简单"而封装 OTel API（`IMetricService` / `ITraceService` / `ILogService`），导致：
- **丢失上下文** - 包装层丢失 Baggage / Span Links / 上下文传播
- **丢失自动检测** - 包装层覆盖了 OTel SDK 的自动插装能力
- **升级困难** - 包装层成为升级瓶颈
- **Vendor Lock** - 包装层往往隐含对特定后端的假设

**正确做法**：
- 直接暴露 OTel SDK API，通过配置切换后端
- 用 Instrumentation Libraries 而非自包装
- 保留 OTel 的[上下文传播](https://opentelemetry.io/docs/concepts/context-propagation/)完整链路

> **Impact**: ⭐⭐⭐⭐⭐ — 直接影响 OTel 落地架构决策，对运维可观测性链路完整性至关重要

### 3. Kepler 重架构深度分析 — 脱离 eBPF 回归 /proc

> 📄 CNCF Blog, Jun 30 · Niki Manoledaki (Grafana Labs) / Sunyanan Choochotkaew (IBM)

**架构变更**：
- 旧：eBPF kprobe + tracepoint → 需 CAP_BPF/SYSADMIN
- 新：`/proc` + `/sys` + RAPL + `powercap` → 无特权要求
- 消除了 multi-kW 的测量尖峰，**归因差距 ≈ 0W**（通过实际功耗验证）
- GPU 电源监控：实验性支持（通过 NVIDIA DCGM 或 GPU metrics exporter）

**部署影响**：
- 生产环境不再需要特权容器（CAP_BPF/SYSADMIN 被安全团队拒的常见原因）
- 多架构一致性：ARM64 同样支持
- 对 AI 集群：容器级 GPU 能耗追踪成为可能

### 7. LWN: LLM 辅助内核补丁的接受度分化

> 📄 LWN.net, Jul 2 · corbet

- Kernel MM 维护者收到两个大型 LLM 辅助补丁集（均来自**成熟、受尊敬**的开发者）
- 与新人提交的 LLM 补丁（被拒）形成鲜明对比
- 关键差异不在于代码质量，而在于：
  - 提交者是否有能力解释代码的正确性和设计理由
  - 是否参与过后续的 review 讨论
  - **审查标准不应因 LLM 参与而放松**
- 信号：LLM 辅助可帮助成熟开发者提高产出，但不会降低提交门槛
