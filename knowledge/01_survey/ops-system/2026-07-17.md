## 🔴 核心动态

### 1. Sched-ext 推进子调度器 + Proxy-Execution 支持

> 📄 LWN.net, Jul 16 · corbet

**extensible scheduler class (sched_ext)** 的进化里程碑：

**当前进展**：
- **子调度器层级（Sub-scheduler hierarchy）** 接近完成 — 可设置多层调度器树状结构
- **Proxy Execution 兼容性** — 长期存在的兼容性问题即将解决

**技术原理**：
- sched_ext 允许通过 BPF 程序安装自定义 CPU 调度器
- 子调度器 = 不同 workload（AI 训练/推理/数据库/Web）可使用不同调度策略
- Proxy Execution = 允许一个线程代表另一个线程执行调度操作（关键：解决调度死锁）

**对 AI 集群运维的关联**：
| 场景 | 当前 | 子调度器后 |
|:-----|:-----|:-----------|
| AI 训练（长时计算） | 默认 CFS | 专用 GPU-aware 调度策略 |
| 推理服务（延迟敏感） | 与训练竞争 | 独立 RT 调度域 |
| 数据预处理 I/O | 共享调度 | 专属带宽调度 |
| 控制面组件（etcd） | 重要性标记 | 优先级调度域隔离 |

**现状**：代码接近内核主线合并，kernel 8.x 可能正式包含

### 2. BPF 实现内核漏洞实时屏蔽 — Cisco 生产实践

> 📄 LWN.net, Jul 13 · daroc · LSFMM+BPF Summit

**问题**：Cisco 运行大量自定义内核设备，安全补丁部署周期长（硬件认证等约束）。

**方案**：在 BPF 中实现漏洞屏蔽逻辑，运行时加载到目标内核。

**核心逻辑**：
```
内核漏洞披露 -> BPF 程序检测攻击面 -> 加载运行时修复 -> 正式补丁后方可卸载
```

**当前限制**：
- 需要更多内核 hook 点才能覆盖全部攻击面
- 但对已知有限攻击面的 CVE 已可有效防护

**运维启示**：BPF 安全屏蔽 = 「热补丁」的新替代方案。对 AI 集群中无法快速重启的 GPU 节点尤其有价值

### 3. BPF 绕过用户态 Agent — Tetragon 内核内直接发包

> 📄 LWN.net, Jul 14 · daroc · LSFMM+BPF Summit

**Tetragon**（Cisco 的 BPF 安全监控工具）探索去除用户态 Agent 依赖：
- 当前：BPF 采集数据 → 用户态 Agent 转发 → 中心监控
- 问题：用户态 Agent 可能被攻击者杀死，导致监控盲区
- 方案：BPF 程序直接通过网络栈发送事件到中心端

**安全价值**：移除用户态 Agent = 消除整个攻击面层。对 AI 集群安全的架构参考意义

### 5. K8s v1.36 User Namespaces GA — 非 Root 容器里程碑

> 📄 K8s Blog, 7月

**User Namespaces GA** 是 K8s 安全性最重要的里程碑之一：
- 容器内进程映射为非 root 用户（即使镜像要求 root）
- 大幅降低容器逃逸攻击面
- 对 AI 集群中多租户 GPU 共享场景的安全增强

**运维注意**：
- 升级前检查镜像兼容性（部分镜像明确要求 UID 0）
- 与 HAMi/Kata Containers/gVisor 的嵌套兼容性需验证

### 7. OTel Go Compile-Time Instrumentation v1.0 — 监控部署影响

> 📄 OTel Blog, Jul 16

从运维视角看此发布：

**运维价值**：
- Go 组件（K8s 核心、CNI、CSI、NVIDIA Device Plugin）可自动 trace

## 🎯 本期核心信号

1. **Sched-ext 子调度器 = 真正的 AI-Aware 内核调度** — 当不同 AI workload（训练 vs 推理 vs 数据处理）可在同一主机上使用独立调度策略时，**GPU 利用率预期可提升 15-30%**。8.x 内核值得关注

2. **BPF 安全屏蔽（Cisco 模式）对 AI 集群尤其有价值** — AI 集群节点 GPU 驱动/NCCL 复杂栈无法频繁重启打补丁。BPF 运行时修复 = 绕过硬件认证限制的关键路径

3. **Tetragon 去掉用户态 Agent 的尝试** — 消除了 Agent 被杀死的监控盲区。对高安全要求的 AI 集群监控架构有参考意义

4. **K8s v1.36 User Namespaces GA 是安全基线的关键推进** — 配合 Pod-Level Resource Managers Alpha，多租户 AI 集群的隔离安全性显著提升。升级规划中应纳入此项变更
