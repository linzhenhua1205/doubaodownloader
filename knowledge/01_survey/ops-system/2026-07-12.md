## 一、🔴 AI 运维 — SRE 的 4-Body Problem

### 1.1 AI 自治运维的真正瓶颈不是模型，是上下文

CNCF Blog, Jul 6, 2026 | Sanjeev Sharma (StackGen Field CTO)

> 核心诊断: "You can't put an agent on top of four siloed, mutually-suspicious systems and expect reliability."

**SRE 的四体问题 — 每次运维决策需要跨四个域推理**:

```
+---------------------------------------------------------+
|                   运维决策 = 四体交叉                     |
+----------+----------+----------+----------+--------------+
|  ① Code  |  ② Infra  |  ③ Runtime |  ④ Ops    | 交叉点(无系统)|
|          |  State   |  Signals |  Knowledge|              |
+----------+----------+----------+----------+--------------+
| Git      | Terraform| OTel/    | Post-    | 断层 ->       |
| commit   | 状态     | Prometheus| mortems  | "people putty"|
| PR/branch| IAM策略  | SLO/错误  | Runbook  | = 2-3人脑中的|
| 版本     | 网络/K8s | 预算     | ADR文档  | 部落知识     |
|          | 集群/DB  | 告警     | Slack记录|              |
+----------+----------+----------+----------+--------------+
```

**核心问题**: 每个域在孤立地看已基本解决，但真实决策在四体的交集中。传统靠资深工程师的「人肉 Putty」拼凑，但这些人离职后断层。

**AI Agent 的信任阶梯**:

| 阶段 | 模式 | 信任度 | 关键依赖 |
|:-----|:------|:------:|:---------|
| Copilot | 人做→AI 写事后分析 | 低 | 无 |
| 辅助决策 | AI 提假设→人确认 | 中 | 上下文完整 |
| 自主 RCA | AI 给出 SLO 锚定的根因假设 | 中高 | 统一知识图谱 |
| 全自动 | AI 决策+执行+审计 | 高 | 决策轨迹 + 策略围栏 |

**核心结论**:
1. **Substrate 优于 Agent**: 先建统一知识图谱(四体+边)再放 agent
2. **决策轨迹不可妥协**: 每次 agent 决策需记录: 输入快照/生效策略/模型版本/考虑过的假设/执行动作/结果
3. **信任由可审计性赢得**, 非模型能力

- **来源**: https://www.cncf.io/blog/2026/07/06/the-4-body-problem-of-sre-why-autonomous-operations-depend-on-context/

## 二、🔴 可观测性 — OpenTelemetry 生态(二)

### 2.1 Don't Wrap OpenTelemetry

OTel Blog, Jun 24, 2026

**问题模式**: 团队在 OTel API 外包自己的抽象层 (IMetric/ITracer)

**四大危害**:

| 危害 | 说明 | 案例 |
|:-----|:------|:------|
| 上下文丢失 | W3C TraceContext 传播被包、丢失 | 跨服务 trace 断裂 |
| 自动检测失效 | Auto-instrumentation 只识别原生 OTel API | JVM agent 找不到埋点 |
| 升级困难 | 内部抽象与 OTel 版本耦合 | 升级 OTel = 改大量内部代码 |
| Vendor Lock-in | 内部抽象掩盖了迁移路径 | 换 backend = 重写抽象层 |

**正确实践**: 直接使用 OTel API，通过配置层（SDK 配置/Collector pipeline/环境变量）解决定制需求

### 3.2 Uncached I/O — 容器内存指标语义澄清

Prometheus Blog, Mar 5, 2026 | Ayoub Mrini

**问题**: 用户常混淆 `container_memory_usage_bytes` vs `container_memory_working_set_bytes` vs `container_memory_rss`
- 根源: Page Cache 语义 — 对某些容器，page cache 占内存很大部分，但实际可回收
- 9 年之久的 K8s issue 持续困扰用户
- 推荐: 使用 `container_memory_working_set_bytes` 做 OOM 相关容量规划

**对 AI 集群的意义**: GPU 服务器容器内存监控同样面临此问题，训练 Pod 的 page cache 使用可能导致误判内存压力
