## 一、🔴 可观测性 — OpenTelemetry 生态

### 1.1 OTel-Arrow Phase 2: 从高效传输到高效流水线

OTel Blog, Jun 12, 2026

- **Phase 1** (已交付): OTAP (OpenTelemetry Arrow Protocol) — 基于 Apache Arrow 列式内存格式的高效传输协议
- **Phase 2** 新内容:
  - 不仅传输高效，处理流水线本身也采用 Arrow 列式架构
  - 端到端减少序列化/反序列化开销 40%+（预计）
  - 与 OTel Collector pipeline 深度集成，transform/process 阶段直接在 Arrow 列存上操作
- **影响**: 对大规模 telemetry ingestion 具有显著成本效益，尤其适应 AI 集群的海量指标采集场景
- **来源**: https://opentelemetry.io/blog/2026/06/12/otel-arrow-phase-2/

### 1.2 OTel Blueprints & Reference Implementations

OTel Blog, May 12, 2026

- 解决痛点: 用户反复问"OTel 为什么这么复杂"——缺少参考架构
- Blueprints: 基于真实场景的标准化部署方案（K8s 部署/边缘收集/混合云等）
- 帮助团队跳过试错阶段，直接采用经过验证的 OTel 架构

### 1.3 GenAI Observability with OpenTelemetry

OTel Blog, May 14, 2026

- **核心能力**: 对 LLM 调用的端到端跟踪
  - 模型调用链: user request → tool calls → LLM calls → token exchanges → response
  - 每次 LLM 调用背后有多轮内部调用（retry loops / fallback / function calling）
  - 45 秒的延迟可能是模型问题、tool call 慢、或 retry 循环
- **OTel 方案**: spans 记录每次 LLM 调用的持续时间、token 消耗、模型名称、temperature 等属性
- **与 AI 集群运维强相关**: inference serving 的可观测性可以直接复用这套模型

### 1.4 Don't Wrap OpenTelemetry

OTel Blog, Jun 24, 2026

- 常见错误: 团队在 OTel API 上再包一层抽象（IMetric、ITrace 接口）
- 问题: 丢失语义、限制能力、增加维护负担、妨碍标准工具兼容
- 最佳实践: 直接使用 OTel API，利用标准 exporter/sampler 框架

### 1.5 Ecosystem Explorer Project & OTel for Dart/Flutter

## 二、🔴 集群可观测性 — Kepler / Prometheus / 能耗

### 2.1 Kepler 重架构深度解析

CNCF Blog, Jun 30, 2026 | Grafana Labs + IBM + Red Hat

> **核心变更**: 脱离 eBPF，回归 /proc + /sys！这是 Kepler 项目自 2023 年进 CNCF Sandbox 以来最大的架构变更

**为什么放弃 eBPF**:
1. **权限瓶颈**: 要求 CAP_BPF + CAP_SYSADMIN，生产环境难以满足
2. **精度问题**: eBPF 跟踪细粒度进程时有误差，导致能耗估算模型不准确
3. **复杂度**: eBPF 层的抽象使代码难以扩展和维护，学习曲线陡峭

**新架构**:
- 信号采集: 只读访问 `/proc` 和 `/sys`（无需特权、通用可用）
- 功率探测: **动态发现**主机电源拓扑（而非之前硬编码 RAPL core/DRAM/other）
- 一句话安装: Helm 单命令部署

**精度验证 — 两项实验**:

| 实验 | 方法 | 结果 |
|:----|:-----|:-----|
| **实验1: pre/post 对比** | 新旧 Kepler 同时部署在同一 bare-metal node，IPMI BMC 做 ground truth | 新 Kepler 消除旧版本的 multi-kW 尖峰(超出 IPMI), 跟踪 IPMI 曲线紧贴 |
| **实验2: 归因差距** | stress-ng 渐进负载，对比 Node 总功率 vs 进程归因功率 | **归因差距 ≈ 0 Watts**，仅几 mW 偏差 |

**90% 测试覆盖率** — 集成测试 + 单元测试

**下一步优先级**:
1. **GPU 电源监控 (实验)** — 需要 AI/ML 用户测试验证
2. **VM 功率建模** — 重训练虚拟化环境功耗估算模型
3. **空闲功率归因** — 重写后仅归因活跃 CPU 使用，空闲功耗待补

**来源**: https://www.cncf.io/blog/2026/06/30/kepler-re-architected-improved-power-accuracy-and-a-community-call-to-action/

## 三、🟡 容器安全运维 — Security Profiles

### 3.1 Security Profiles Operator v1 GA (运维视角)

CNCF Blog, Jun 26, 2026 — 与 3.2 联动看

**运维影响**:
- seccomp/SELinux/AppArmor 三种安全配置文件统一声明式管理
- 配置文件录制: 从真实 workload 自动生成安全策略（audit log + eBPF → 自动化）
- 分布: OCI 注册表分发 + kubelet 原生拉取（KEP 6061）
- 零宕机迁移: 转换 webhook 透明处理旧 API 版本

**与 AI 集群的关系**: AI 训练 workload 常需要 seccomp/SELinux 宽松配置，SPO 提供精确的最小权限策略生成能力

### 3.2 PSI Metrics for K8s Graduates to GA

K8s Blog, v1.36 (2026 May)

- PSI (Pressure Stall Information) — 容器级 CPU / Memory / IO 压力信号标准化为 K8s 指标
- 从 Beta 到 GA: 可用于基于压力的自动调度决策
- 与 Kepler 能耗指标+PSI 压力指标协同 → 运维人员获得全面的"资源压力 + 能耗 + 性能"三维视图
