## 1️⃣ 🔴 AI 让角色「变大」而非「变小」— Teamwork Lab 最新研究

**来源**: [New research reveals how AI is making jobs bigger — Atlassian Blog / AI at Work](https://www.atlassian.com/blog/ai-at-work/new-research-reveals-how-ai-is-making-jobs-bigger) (2026-07-06)
**作者**: Halina Mader, Conor Donegan — Atlassian Teamwork Lab
**方法论**: 1,000 名美国知识工作者双盲调查 (2026-05-27 ~ 06-09)
**核心主张**: AI 不是取代工作，而是**扩张工作**——角色变宽、变深，但跨功能连接变弱。

### 1.1 关键量化数据

| 指标 | 数值 | 含义 |
|:-----|:----:|:-----|
| 过去一年角色超出原 JD 范围 | **92%** | 角色扩张是普遍现象，但 AI 用户分化最明显 |
| 非 AI 用户岗位不变 | **7×** 更可能 | 与重度 AI 用户对比，AI 使用是角色是否变化的最强信号 |
| 重度 AI 用户跨职能工作 | **+72%** | 远超非用户，边界模糊化 |
| 重度 AI 用户自主处理专业任务 | **2×** 更可能 | 不依赖专家就能完成 |
| AI 用户「与同事连接」时间排名 | **垫底** | 非用户排名第 3；用户最不花时间在同事身上 |

### 1.2 三大核心发现

**① 角色扩张不只是「更多同类工作」**

> 「The expansion isn't simply more of the same work, faster.」

重度 AI 用户在做**本质不同的工作**——以前需要专家或属于其他团队的任务。

- 营销：重度用户中 >50% 同时扩展到创意与技术工作
- IT/工程：扩展到沟通与跨职能协调——传统上属于其他团队的领域

**② 从「执行」到「领导」的角色爬升**

| 用户类型 | 时间分配特征 |
|:---------|:-------------|
| 非 AI 用户 | 更多低头执行时间 (heads-down execution) |
| 重度 AI 用户 | 更多监督、管理、指导工作 (oversight / management / direction) |

> 「AI shifts your job from doing to leading.」— 这种模式跨资历层级成立，说明是 AI 使用本身驱动而非职业阶段。

**③ 连接鸿沟 (Connection Gap)**

| 维度 | AI 用户 | 非用户 |
|:-----|:-------|:-------|
| 跨功能协作可能性 | +72% | 基线 |
| 「与同事连接」时间排名 | **第 10 位 (垫底)** | 第 3 位 |

> 自相矛盾：AI 让用户跨越更多团队边界工作，但**人际关系反而更弱**——跨功能工作缺少了连接的组织「结缔组织」。

### 1.3 与跟踪链的交叉

> 🔗 关联 [07-07 AI 诚实悖论](2026-07-07.md) — 两篇同为 Teamwork Lab 2026 年 5-6 月调研周期的产出。诚实悖论说「用 AI 被罚 10× 懒」，本篇说「用 AI 角色变大但连接变弱」——**合在一起看：AI 用户在隐藏使用（诚实悖论）的同时承担更宽的角色（角色扩张），还面临更弱的人际连接（连接鸿沟）。三重张力。**

> 🔗 关联 [07-06 Speed Paradox](2026-07-06.md) — 「个人快≠组织快」与「跨职能多≠连接强」是同一底层问题：**AI 加速了执行与覆盖范围，但协调与连接的「基础设施」没有跟上。**

### 1.4 给管理者的建议

1. **让 AI 使用可见、被重视、正常化** — 否则角色扩张在隐藏中无法持续
2. **不要让角色扩张变成孤军奋战** — 轻量级的咨询关系（短对接会议 + 优秀案例 + 快速问答渠道）比正式培训有效

## 2️⃣ 🟡 新瓶颈从数字层到物理层 — AI 时代的办公室设计框架

**来源**: [AI made your people faster. But it's your office that's slowing them down. — Atlassian Blog / AI at Work](https://www.atlassian.com/blog/ai-at-work/ai-made-your-people-faster-but-its-your-office-thats-slowing-them-down) (2026-07-01)
**作者**: Gina Creegan (Head of Workplace) + Atlassian Teamwork Lab
**方法论**: 12,000 知识工作者 + 172 Fortune 1000 高管调研 (State of Teams 2026) + 办公室行为研究 + 高管访谈
**核心主张**: AI 压缩执行后，新瓶颈在协调——但办公室仍按「执行为瓶颈」设计，需要重新设计。

### 2.1 关键数据

| 指标 | 数值 | 来源 |
|:-----|:----:|:-----|
| F500 碎片化税 (Fragmentation Tax) | **$1.61B/年** | Atlassian 调研 |
| 知识工作者「没有协调时间/容量」 | **87%** | State of Teams 2026 (12K 调研) |
| 员工完全信任 AI 比例 | 仅 **1/3** | 同一调研 |
| 员工不希望他人知道 AI 辅助 | **37%** | 同一调研 |

### 2.2 核心框架：AI 时代的三种工作流状态

传统办公室围绕「专注」和「开会」两模式设计。AI 时代需要新框架：

```
传统办公室           ->    AI 时代的办公室
-------------------------------------------
Focus (专注)         ->    Ideate (构想)
Collaborate (协作)   ->    Calibrate (校准)
Connect (连接)       ->    Regulate (调节)
```

| 状态 | 解决的问题 | 空间设计 |
|:-----|:----------|:---------|
| **Ideate** 构想 | AI 能生成一切，但「做什么值得做」是稀缺资源 | 可写墙面、非正式座位、低监视环境 — 让半成品想法敢于说出口 |
| **Calibrate** 校准 | 执行成本消失后瓶颈在「和他人对齐什么是对/好/可发版」 | 共享显示屏对比选项、15 分钟决策空间、非 1 小时状态会议的配置 |
| **Regulate** 调节 | AI 加速一切后需要有保护的思考时间与人际连接 | 安静室、户外区、无屏幕社交空间 — 对抗「认知让步」(cognitive surrender) |

### 2.3 AI 物理存在的演进路线

| 阶段 | 现在 | 下一步 | 未来 |
|:-----|:-----|:------|:-----|
| AI 存在 | 不可见 (屏幕内) | 语音激活 (麦克风/扬声器/隔音舱) | 空间感知 (光/声/自适应环境) |
| 协作模式 | 嵌入式助手 | 主动协作者 | 环境级队友 |
| 物理表达 | 无空间变化 | 语音优先环境 + 校准室 | AI 嵌入环境，响应式空间 |

> 关键洞察：**当 AI 从打字提示转向语音对话，声学策略、封闭/开放空间比例、AV 配置都需重新规划。**

### 2.4 六大设计原则

1. **明确标示 AI 在哪里 — 或不在**。AI 免费区的显式信号建立信任
2. **设计无缝的流程邻接**。Ideate ↔ Calibrate ↔ Regulate 的切换应无摩擦
3. **语音优先而非键盘优先**。声学规划必须跟上
4. **将健康视为性能基础设施**。Off-state 是 AI 加速的平衡器
5. **实验优于完美**。用明确假设和成功指标试点模块
6. **规划灵活性**。模块化基础设施可随 AI 能力演进

### 2.5 与跟踪链的交叉

> 🔗 本篇与 [07-06 Speed Paradox](2026-07-06.md) 是同一问题的**物理层表达**。Speed Paradox 论述了「个人快≠组织快」的机制；本篇提供了物理空间设计方案来解决协调瓶颈。两者构成：**问题诊断 (Speed Paradox) → 物理治疗方案 (AI 办公室框架)**。

> 🔗 关联 [07-07 AI Collaboration Framework](2026-07-07.md) — 数字层的 Human-First / Collaboration / AI-First 三区 + 物理层的 Ideate / Calibrate / Regulate 三状态 = **数字+物理双层的 AI 工作流锚定设计**。

### 3.2 Agent 全状态可见性: Jira 中管理所有 Agent

**来源**: [Every agent. Every state. Full visibility in Jira. — Atlassian Blog / Development](https://www.atlassian.com/blog/development/) (2026年7月·最新发布)
**工具**: Jira Agent 管理面板
**方法论**: 将所有 Agent（Claude / Cursor / Codex / 自研）的状态统一展示在 Jira 中
**核心主张**: 当 Agent 数量增长后，可见性 (observability) 成为关键制约——你无法管理看不见的 Agent。

**关键能力**:

| 能力 | 作用 |
|:-----|:------|
| 所有 Agent 统一状态面板 | 正在工作 / 待命 / 失败 / 需人工介入 |
| 按 Agent 类型筛选 | 区分 Claude / Cursor / Codex / Automation |
| 工作量统计 | 每个 Agent 每小时处理的任务数 |
| 人工介入队列 | Agent 未能解决 → 自动升级到工程师 |

> 🔗 **这是自然演进的下一步**：当 Agent 从 1 个（06-26 Claude Agent）→ 2 个（07-02 +Cursor）→ 多厂商（07-08 +Codex）后，**Agent 编排的下层问题从「能力」变成了「可见性」**。Jira 的 Agent Dashboard 是 Agent 编排的运维基础。

### 3.4 @Jira: 从 Slack 对话直接创建 Jira 工作项

**来源**: [Introducing @Jira: create work items from any Slack conversation — Atlassian Blog / Jira](https://www.atlassian.com/blog/jira/) (2026年7月·最新发布)
**工具**: Jira Cloud for Slack App (已在 Slack Top 5 App 中)
**方法论**: Slack 对话中 @Jira → 自动创建 Agent-ready Jira work item，无需离开 Slack
**核心主张**: 「你已经在 Slack 里讨论工作了，为什么还要离开才能创建 Jira？」— 将所有输入渠道统一到 Jira

| 能力 | 说明 |
|:-----|:------|
| 触发 | Slack 对话中 @Jira |
| 输出 | 自动创建包含完整对话上下文的 Jira Issue (agent-ready) |
| 上下文继承 | 对话历史 + 参与者 + 链接自动带入 Issue |
| Agent 就绪 | 创建后的 Issue 可直接 Assign 给 Claude/Cursor Agent |

> 🔗 **Slack → Jira → Agent 的三跳路径**: @Jira (Slack 入口) → Jira Issue (结构化上下文) → Agent (自动执行) — 这是 07-02「Agent 编排入口从 Jira 前移到 Slack」的实际产品落地。

### 3.5 Code Reviewer 增加 PR Context

**来源**: [Improving Code Reviewer with Atlassian PR Context — Atlassian Blog / Development](https://www.atlassian.com/blog/development/) (2026年7月·最新发布)
**工具**: Rovo Dev Code Reviewer + PR Context
**方法论**: Code Reviewer 此前已经知道「规则」(lint/风格/模式)，现在增加了「历史」(PR 历史/代码演进/关联 Issue)
**核心主张**: Code Review 不能只看当前 diff，需要理解代码的演进背景和设计决策。

| 维度 | 之前 | 之后 |
|:-----|:-----|:-----|
| Code Reviewer 输入 | 规则 (代码风格/安全模式/常见 bug) | 规则 + 历史 (PR 历史/代码演化/关联 Issue) |
| 覆盖范围 | 当前 diff | 当前 diff + 上下文 + 设计决策轨迹 |

### 📈 本期关键推论

**1. 跟踪链从「工具层→组织层→文化层」继续上到「角色层+物理层」**

| 层次 | 前期跟踪 | 本期新增 |

| 工具层 | Coding Sessions, Claude Agent, MCP | Agent 全状态可见, Codex 集成, @Jira Slack |

| 物理层 | — | AI 办公室 Ideate/Calibrate/Regulate |

**2. 「角色扩张 + 连接鸿沟」= 2026 年 AI 工作研究的核心矛盾**

诚实悖论 (用 AI 被罚) + 角色扩张 (用 AI 责任变大) + 连接鸿沟 (用 AI 联系变弱) 三者构成了 **2026 年 AI 时代知识工作的结构性矛盾**：

```
AI 使用 -> 角色扩张 (责任^)
        -> 连接鸿沟 (关系v)
        -> 隐藏使用 (诚实悖论)
        = 个体承担更多、联系更少、还要隐藏怎么做
```

**3. Context 的量化 ROI 公式**

LangChain +0.38%/1% 的弹性系数看似小，但考虑：
- Agent 上下文质量通常以 **10-50%** 幅度提升（通过 MCP/TG CLI/Skills）
- 10% 上下文改进 → 3.8% 输出质量提升
- 这相当于 **AI-native 团队 1-2 个月的效率增益差**

| 层 | 产品/能力 | 覆盖 |
|:---|:----------|:-----|

| 编排 | Jira Agent Assignments | Issue → Agent 分配 |
