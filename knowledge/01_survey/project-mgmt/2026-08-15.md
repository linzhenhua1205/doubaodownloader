## 1️⃣ 🔴 How we built Linear Agent——"边界内自主"的 Agent 工程方法论（08-10，全库首次）

- **来源**: [How we built Linear Agent](https://linear.app/blog/how-we-built-linear-agent)（Linear Blog / From the team, **2026-08-10**, Matthijs Wolting, 全库 grep 零匹配首次归档; 08-13 changelog 发布 Team initiatives 后 Linear 进入新一轮产品+工程叙事期）
- **核心设计哲学——用边界替代路径**: 传统工程=收缩结果空间直到同一动作稳定产出同一结果; AI 反转该逻辑——Linear Agent 价值恰在"做未预料的活、走未显式定义的路"。**工程对象从"固定路径"转为"自主性边界"**（system prompt + 工具设计 + 产品模型 + run 范围 + 自建 harness 五层边界）
- **System prompt 四要素（高层方向+留白）**: ① 沟通风格——自然清晰、随运行表面自适应（Slack 更口语化、Loop 更正式, 甚至可在 Slack 接梗）② 硬边界——敏感话题不表态、**不擅自扩大用户请求范围**（超范围动作须先确认）③ Linear 特有概念解释（taxonomy 理解才能正确行动）④ 功能使用的默认观点——prompt 极短时"推断意图 vs 追问澄清"的默认判断。核心: 方向给足、行为留白
- **工具设计即约束（prompt 之外的第二层）**: 把约束**编码进工具设计**而非写进 prompt 文本——参数易理解、非法动作难以执行（"类同好代码抽象/好 UI 设计"）; 且动作空间不过度脚本化→模型升级时工具可灵活组合、能力自动增长
- **🔴 Agent 的产品模型——与 coding agent 形状相反**: coding agent=少量深工具（read_file/write_file/run_command）+ 代码与 shell 在训练数据中强表示→陌生场景也有好直觉; Linear Agent=**大量浅工具**（每个绑定一个产品操作）+ 产品概念在训练数据中弱表示→启用任何产品区域需要三件套: 读写工具 + 该数据是什么/如何关联产品的解释 + 功能使用基本原则（如 Customer Requests skill: 聚合跨客户请求模式起草项目 spec 的最佳实践）
- **🔴 System skills——渐进披露的组成单元**: 每个 system skill = 元数据 + system prompt 片段 + 一组工具, **按需加载**（run 前根据 prompt+上下文推断预加载, 如从 Slack/项目页调用预载 'projects' skill; 运行中任务展开再动态补载, 如起草项目更新时中途加载 issues/PRs 相关 skill）——每线程上下文聚焦、全产品能力可扩展、**不因能力增长而膨胀每次交互的 prompt/toolset**
- **🔴 自建 harness 的三大编排需求（不用现成库的理由）**:
  - **动态工具注入**: skill 加载后须在工具调用解析完成**立即**提供新工具（子调用完成前可再调新工具）; 且须**保留 provider 前缀缓存**——朴素实现会重算既有上下文推高成本（与 08-11 期 Long Horizon"分层 prompt+前缀缓存"同构）
  - **条件工具审批**: 现成库=仅按工具名+参数做粗粒度审批; Linear 要**上下文敏感审批**——会话内自己创建的删除可免批、删既有 issue 须确认; 多数评论线程可直发、**同步到公开仓库的帖子须暂停确认**
  - **异步子代理执行**: 子代理运行数十秒期间父代理应**挂起 turn（不耗服务端资源）**, 对父表现为同步工具调用, 完成后恢复线程——须 mid-tool-call 挂起/异步执行/续跑三态
- **架构取舍——产品级工具而非底层 API**: 曾考虑直连 Linear SDK+编码环境/CLI/GraphQL——底层模型动作面大、UI 概念需解释后才能映射, 长尾请求易"越来越投机地试错"; **放弃广度换可预测性**: 偶尔拒绝无法安全完成的任务, 但出错面大幅收窄
- **信号意义**: ① **"五机制"公共设计语言再获独立实证**——system skills 渐进披露 = Long Horizon flattened tools/progressive disclosure、前缀缓存保留、异步子代理 = child instances, 跨厂商（Atlassian/Linear）方法论收敛 📌 ② **"工具设计即约束"是 agent 安全性的工程化答案**——比 prompt 层约束更可执行, 呼应 08-14 MCP Okta"agent 权限=人类权限投影"的治理主线（本层管"动作可执行性", 身份层管"动作授权"）③ **产品型 agent（浅工具多量）vs 编码型 agent（深工具少量）的分野**——前者考验产品知识结构化（SKILL 化）, 后者考验基础模型代码直觉, 对自建 agent 平台有直接选型参考价值 📌
