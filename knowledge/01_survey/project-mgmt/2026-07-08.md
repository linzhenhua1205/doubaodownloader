## 1️⃣ 🔴 Linear 正式闭环：Coding Sessions — Agent 从规划到写代码一步完成

**来源**: [Coding sessions in Linear — Linear Changelog](https://linear.app/blog) (2026-06-10/11)
**工具**: Linear Agent + Claude Code / Codex
**方法论**: 端到端 Agent SDLC — Issue → Code → Diff → Review → Merge，全部在 Linear 内完成
**核心主张**: 「你可以在 Linear 内 triage、plan、review、ship」— 不需离开 Linear 做任何事。

### 1.1 关键能力 — 三模式覆盖

| 模式 | 触发方式 | 工作流 | 适用场景 |
|:-----|:---------|:-------|:---------|
| **Assign to Linear** | 将 Issue assign 给 Linear Agent | Issue → Code → Diff → Review | 从零开始的开发任务 |
| **Chat/Slack trigger** | 在 chat / comment / Slack 中提问 | 自然语言 → Code → Diff | 修改变更、原型验证 |
| **Auto-triage** | 新 Issue 报告→ Agent 自动调查+修复 | Bug → Investigation → Fix → Draft PR | 第 1 遍自动处理 |

**环境**: Coding sessions run in the cloud — 不需要本地开发环境，Team 全员可触发。

### 1.2 🔴 最关键的内部数据

> 「Linear uses this workflow internally to resolve **roughly 30% of incoming bug reports**, mostly on the first pass.」

| 指标 | 数据 | 含义 |
|:-----|:----:|:-----|
| 自动修复 bug 比例 | **~30%** 首遍通过 | Agent 已能处理约 1/3 的 bug 提交 |
| 场景 | 新 Issue 触发 → 工具链(MCP→Sentry/Datadog) → 代码库分析 → 根因定位 → 修复 | 全链路自主 |
| 模式 | Auto-triage: Agent 在到达工程师之前完成第一遍 | 减少人工负载 |

> 🔗 **与跟踪链的关系**: 此前 06-26 记录 Linear Agent 启动（03-24 "Issue tracking is dead"宣言），07-07 记录 At 的 Jira Agent 80% chores 自动化。**现在 Linear 完成了同水平的实证——30% bugs 自动修复。** 两个平台在同时间点（Jun 2026）交出了各自的 Agent 效率第一波实测数据。

### 1.3 架构选择：云上执行 vs 本地 IDE

| 维度 | Linear Coding Sessions | Atlassian Claude Agent for Jira |
|:-----|:----------------------|:-------------------------------|
| 执行环境 | Linear Cloud（云上） | Anthropic Sandbox（云上） |
| 开发环境要求 | 0（不需要 IDE） | 0（不需要 IDE） |
| 代码规模 | 远程 clone + 分析 | 远程 clone + 分析 |
| 输出 | Linear Diff → Review → Merge | Draft PR → GitHub Review |
| Agent 后端 | Claude Code / Codex | Claude (Anthropic Managed Agents) |

**趋势**: 两大平台**都选择了云上执行而非本地 IDE**。这意味着 Agent 不依赖开发者的本地环境——非工程师（PM/Support）也可以触发 Coding Session。

### 1.4 Linear 并行发布的关键支撑组件

| 日期 | 组件 | 作用 |
|:----:|:-----|:-----|
| 05-14 | **Code Intelligence** | Agent 可以读代码库（public beta），理解产品「实际怎么工作的」 |
| 05-28 | **Linear Diffs** | 原生代码审查 — Guided Reviews，Review Inbox，代理代审 |
| 06-03 | **Team Documents** | 每 Team 独立知识空间，Agent 的静态数据源 |
| 06-04 | **Shared Skills** | 个人工作流 → 团队标准化流程的固化与共享 |
| 06-17 | **Agent Assisted Project Updates** | Agent 自动写项目更新（分析 Issue / document / Slack 生成 draft） |
| 06-30 | **Initiative Properties** | 高级 Initiative 管理（状态/优先级/标签），roadmap 治理 |
| 07-02 | **Enterprise MCP (Okta)** | 企业级 MCP 授权管理 |

> 🔗 **分层依赖**: Code Intelligence (上下文) → Diffs (审查) → Coding Sessions (执行) — 这是 3 个月内从零到完整 Agent SDLC 的构建速度。**Linear 在 Mar-Jun 的 4 次发布构成了一个完整的产品闭环。**

## 2️⃣ 🔴 Claude Agent for Jira + Cursor in Jira — Jira 双 Agent 编排实证

**来源**: 
- [Introducing Claude Agent for Jira — Atlassian Blog / Company News](https://www.atlassian.com/blog/company-news/claude-agent-for-jira) (2026-06-18)
- [Introducing Cursor in Jira — Atlassian Blog / Company News](https://www.atlassian.com/blog/company-news/cursor-in-jira) (2026-05-20)
- [Introducing new MCP capabilities — Atlassian Blog / Company News](https://www.atlassian.com/blog/company-news/) (2026-06)

**方法论**: Jira 作为多 Agent 编排总线 — 对每个 Agent 厂商平等开放集成
**核心主张**: 工程组织应在 Jira 中完成从规划到部署的完整工作，而不切换工具。

### 2.1 Claude Agent for Jira — 关键细节（06-18 发布，本期深度捕获）

| 维度 | 详情 |
|:-----|:------|
| **架构** | 基于 Anthropic Claude Managed Agents 基础设施 |
| **执行** | Anthropic 隔离沙箱中 clone repo → 分析代码 → 实现变更 → Draft PR |
| **触发方式** | 3 种：@Claude comment、Assignee 下拉选 Claude、自动化规则自动分配 |
| **输入上下文** | Issue 描述 + 验收标准 + 目标仓库 + 设计/工程规范（AC 属性自动读取） |
| **输出** | Draft PR → GitHub → Jira Issue 实时状态同步 |
| **人力保留** | 代码审查、验证、最终合并完全由工程师控制 |
| **可用性** | Jira Cloud Standard/Premium/Enterprise + Rovo 启用 |

### 2.2 Cursor in Jira — 关键细节（05-20 发布，本期深度捕获）

| 维度 | 详情 |
|:-----|:------|
| **引用数据** | 「DX 多年研究发现开发者效率提升跟不上模型能力进步，因为 Agent 缺少上下文——上下切换、规划、对齐、bug 分流、审查是 IDE 外的主要摩擦点。」 |
| **路径** | Jira Issue → @Cursor → 云 Agent → Code → Draft PR → 回链 Jira |
| **Teamwork Graph CLI 量化** | 使用 ATG 上下文的 Agent → **回答质量提升 44% + 减少 48% Token 消耗** |
| **Spec-Driven Dev 流** | Confluence specs ↔ Jira 自动同步 → Agent 可消费的结构化 Spec |
| **可用性** | 所有付费 Jira 订阅 |

### 2.3 两枚 Agent 的分工与互补

| 对比项 | Claude Agent for Jira | Cursor in Jira |
|:-------|:---------------------|:---------------|
| **发布日期** | 06-18 (最新) | 05-20 (先发) |
| **执行后端** | Anthropic 托管基础设施 | Cursor 自己 |
| **触发方式** | 3 种（assign/mention/automation） | assign 与 mention |
| **交付形式** | Draft PR via GitHub | Draft PR / 更新 Jira |
| **上下文来源** | Jira Issue + Acceptance Criteria + Rovo | Cursor context + Teamwork Graph CLI |
| **Token 效率** | 未公开 | —44% 更好的回答 / —48% 更少 Token |
| **核心优势** | 管理式全托管，低配置成本 | 与 Cursor IDE 深度集成 |

> **Atlassian 选择「不是选一个 Agent」而是「Agent Marketplace」路线**。在 Jun 2026 的一个月内同时支持 Claude Agent 和 Cursor——这与 07-02 的判断一致：**Jira 作为 Agent 编排平台，覆盖从 Slack 入口 → Code 执行 → Bitbucket CI/CD 的完整编排总线**。

## 3️⃣ 🟡 Ramp: 内部 Coding Agent 贡献 60% 合并 PRs

**来源**: [The coding agent behind 60% of Ramp's merged PRs — Linear Blog / Customer Story](https://linear.app/blog) (2026-04-27)
**工具**: Ramp Internal Agent + Linear (structured product context)
**方法论**: Linear 作为底层结构化上下文层 → Agent 获取 Issue 的完整产品上下文后独立开发
**核心主张**: 当 Agent 能获取 Issue 的完整上下文后，可自主处理 60%+ 的合并 PR。

### 3.1 关键数据

| 指标 | 数值 | 解释 |
|:-----|:----:|:-----|
| Agent 贡献合并 PR 比例 | **60%+** | 所有合入代码的 >60% 来自 Agent |
| 上下文来源 | Linear | Issue + 依赖 + 历史 + 产品决策树作为 Agent 的「结构化输入」 |
| 方法论 | Agent 从 Issue 获取完整上下文后自主开发 | 工程师 Review 与 Merge 阶段介入 |

### 3.2 与跟踪链的关系

| 此前跟踪 | 连接点 |
|:---------|:-------|
| 06-26 「10-15% 天花板」 | Ramp 60% 说明**特定条件下**（结构化上下文 → Agent 自主开发）效率飞跃可远超平均值 |
| 06-29 Context Wrangler | Agent 需要的「结构化上下文」= PM/Context Wrangler 的核心产出 |
| 07-06 Speed Paradox / 瓶颈迁移 | Ramp 的 PM 配比和 Agent 设计本质上实现了「组织瓶颈后移到 Agent 层」 |
| 07-07 Jira 80% chores | Ramp 60% 不是 chores 是**新功能开发合并 PRs**，表明 Agent 在新功能开发中的效率同样大幅提升 |

> **重要区别**: Atlassian 80% chores 自动化针对的是**维护性杂务**。Ramp 的 **60% merged PRs** 包含了新功能开发代码。两者合在一起说明 Agent 在**维护性工作（80% 节省）和新功能开发（60% 合并 PRs）** 两个方向都已经有规模化实证。

### 📈 本期关键推论

**1. Agent 执行层已齐备，下一步竞争在编排层**

Linear 和 Atlassian 在 Jun 2026 都交出了 Agent 自主写代码的产品版本——**Agent 的「写代码」问题已不是差异点，差异在于编排环境的质量**：
- Linear: 全闭环（规划→代码→审查→部署，全部在 Linear 内）
- Atlassian: 开放编排（Jira 编排 + MCP 协议 + 多 Agent 厂商 + 多工具集成）

**2. 实测数据（30% / 60% / 80%）已涵盖三类场景**

| 场景 | 来源 | 数据 | 含义 |
|:-----|:-----|:----:|:-----|
| 维护性杂务 | At 80% chores (07-07) | **~80%** 节省 | 重复性工作大幅缩减 |
| Bug 自动修复 | Linear 30% (本期) | **~30%** 首遍通过 | Agent 已能处理约 1/3 报告 |
| 新功能开发 | Ramp 60% (本期) | **60%+** merged PRs | 新功能开发同样可大幅由 Agent 承担 |

**3. 组织 ROI 可验证性问题 → 下一个范式缺口**

Atlassian 的最新调研（89% 说快 / 6% 能验证 ROI）是**系列跟踪自然收敛到的顶层问题**：
- 07-02：「+19% PRs → 2-3 小时/周」— 个人层效率提升已可量化
- 07-06：「Speed Paradox — 个人快≠组织快」— 解释了损耗机制
- 07-07：「诚实悖论 — 披露被罚 10×」— 发现了社会文化层的损耗
- **本期：「6% 能验证组织 ROI」— 是前三个阶段的必然结果**

> **关于「6%」的谨慎说明**: 这个数字来自调研摘要（89% faster / 6% ROI），因未获取到完整调研报告，不清楚其精确方法学和定义（ROI 如何界定的？样本构成是什么？）。但即使实际数字在 10-20% 区间，结论方向不变：**绝大多数组织无法验证 AI 投资的顶层回报。**
