## 1️⃣ 🔴 Linear Loops: 团队级循环 Agent 工作流 — 从个人效率到团队运营自动化

**来源**: [Introducing Loops](https://linear.app/blog/introducing-loops) — Linear Blog / Product Launch (2026-07-20)
**作者**: Nan Yu
**工具**: Linear Agent × Loops × Coding Sessions × MCP
**方法论**: Loop Engineering — 用自然语言定义定时或事件驱动的 Agent 工作流，跨团队共享可见

### 1.1 关键创新

在此之前 AI 编程 Agent 的 "loop" 能力（Claude Code / Codex 的 `/loop`）仅限于**单个开发者工作流**。Linear 将其扩展到**整个产品团队**。

| 维度 | 传统 Agent Loop | Linear Loops |
|:-----|:----------------|:-------------|
| 范围 | 个人终端 | Team + Workspace 级别 |
| 定义方式 | 代码命令 (`/loop`) | **自然语言描述反复性工作** |
| 触发方式 | 手动 | **定时器或事件驱动** |
| 可见性 | 终端可见 | 团队共享可见、可审查、可追溯 |
| 判断能力 | 固定规则 | AI 驱动的上下文判断、异常处理、歧义导航 |

### 1.2 典型用例与数据

| 用例 | 工作机制 | 价值主张 |
|:-----|:---------|:---------|
| **Bug 诊断与分派** | Loop 审查 Issue 描述+评论+代码库 → 推荐下一步 → 清晰时启动 Coding Session 修复 | 从人工 Triage 到 AI Triage + Auto-Fix |
| **跨平台需求生成** | 新 Feature Request → Loop 判断 iOS/Android/Web 是否需要分别改动 → 创建对应 Issue → 分派给对应团队 | 手动分派 → 自动路由 |
| **发布计划自动同步** | 每日 Loop 扫描活跃 Projects/Initiatives 对照发布计划 → 发现时间/范围变更 → 自动更新文档并记录原因 | 人力维护文档 → AI 主动维护 |

### 1.3 跨期对比: Linear Agent 能力演进

| 日期 | 能力 | 跟踪期 |
|:----:|:-----|:-------|
| 05-14 | Code Intelligence (读代码库) | 07-17 |
| 05-28 | Diffs (代码审查) | 07-17 |
| 06-10 | Coding Sessions (Agent 写代码) | 07-17 |
| 06-12 | Auto-fix bugs (自修复, ~30%) | 07-17 |
| 06-30 | Initiative Properties (目标量化) | 07-20 |
| **07-20** | **Loops (循环工作流, 团队级)** | **本期** |

**推论**: Linear 在 2 个月内完成了从「单 Agent 能力」→「多 Agent 协同」→「团队级运营自动化」的三级跳。Loops 是最后一块拼图——让 Agent 从「工具」变为「团队成员」。

## 2️⃣ 🔴 Jira: 从追踪工作到委派工作 — SDLC 列级 Agent 编排实验

**来源**: [The future of Jira isn't just tracking work. It's delegating it.](https://www.atlassian.com/blog/ai-at-work/the-future-of-jira-isnt-just-tracking-work-its-delegating-it) — Atlassian Blog / AI at Work (2026-07-20)
**作者**: Reign Nelson
**工具**: Jira × Rovo Studio (Agent Builder) × Rovo MCP × Teamwork Graph
**方法论**: Column-as-Delegation layer — 将 Jira 看板列映射到 SDLC 阶段，每列绑定一个专用 Agent

### 2.1 核心实验: 一个功能, 四个 Agent

作者亲手用 **Launchpad (Forge app)** 构建了一个真实功能，流程如下:

```
Research Agent ---> Planning Agent ---> Implementation Agent ---> QA Agent
   (收集上下文)      (制定实现计划)       (编码实现)             (审查输出)
```

| 列 | 工作产物 | 关键能力 |
|:---|:---------|:---------|
| **Research** | 组织上下文: 相关 Jira Issue/Confluence 页面/实现模式/已知阻塞/相关人 | 自动探索 Teamwork Graph |
| **Planning** | 结构化实现计划, 含架构决策和 tradeoffs | 基于 Research 输出推理 |
| **Implementation** | 编码实现 | 从批准的 Plan 直接输出代码 |
| **QA** | 审查结果 | AI 驱动审查 |

### 2.2 关键发现

1. **"The board determined ownership. The Jira issue preserved context. And I decided when the work was ready to move forward."**
   — 看板成为委托层, Issue 成为上下文载体, 人类负责裁决过渡点

2. **"每阶段的输出自动保存为 Issue 评论 → 成为下一个 Agent 的共享上下文"**
   — 上下文在 Agent 之间自动传递，无需人工同步

3. **启动建议:**
   > "Start with one column. Pick the stage of your workflow that costs you the most time or context."

   **四步入门:**
   - ① 在 Jira Board 添加一列代表该阶段
   - ② 在 Rovo Studio 创建一个专用 Agent (只做一件事)
   - ③ 将该 Agent 绑定到列 (Issue 移入列时自动委派)
   - ④ 跑一个真实 Issue, 审查输出, 迭代 Agent 指令

4. **规模化路径:**
   > "The workflow you build for your own bottleneck today can become the workflow your teammates run tomorrow, or the pattern a partner ships to thousands of customers next quarter."

### 2.3 与跟踪链的交叉验证

| 信号 | 来源 | 关联 |
|:-----|:-----|:-----|
| Jira Agent Sessions (07-15) | Agent 统一状态面板 | 底层可见性 |
| Jira Planner (07-15) | Spec-Driven Dev | 上游意图输入 |
| **本期: Column-as-Delegation** | Agent 绑定到 Jira 列 | **"委派层"的实操验证** |
| Deeplink to AI coding tool from Jira (本期相关) | 一键从 Jira 委派给本地 Coding Agent | 另一种委派路径 |

**推论**: Jira 的 "委派层" 策略有两条路径并行:
- **路径 A (本期):** Agent 入住 Jira 列 → 看板自动委派 (重型编排)
- **路径 B:** Deeplink → 一键递给本地 IDE Agent (轻量级)

### 3.2 五问题框架

| # | 问题 | 核心答案 |

## 4️⃣ 🟡 Teamwork Lab 研究: AI 正让"工作变大"——92% 角色扩张

**来源**: [New research reveals how AI is making jobs bigger](https://www.atlassian.com/blog/ai-at-work/new-research-reveals-how-ai-is-making-jobs-bigger) — Atlassian Blog / AI at Work (2026-07-06)
**工具**: Teamwork Lab 双盲调查 (1,000 US 知识工作者)
**方法论**: 按 AI 使用深度分组 → 对比角色范围、时间分配、跨职能度

### 4.1 核心数据

| 发现 | 数据 |
|:-----|:-----|
| 角色过去一年扩张 | **92%** |
| 非 AI 用户角色不变的比例 | **7×** 高于重度 AI 用户 |
| 重度 AI 用户跨界工作比例 | **近 2×** |
| 重度 AI 用户自主处理专业任务 | **2×** 无需请教专家 |
| 跨职能工作增加 | **72%** 高于非用户 |
| 与同事连接排名 | AI 用户 **倒数第一**, 非用户 **第三** |

### 4.2 职能分布差异

| 职能 | 扩张方向 |
|:-----|:---------|
| **市场营销** | 创意工作 + 技术工作的双重扩张 (>50%) |
| **IT/工程** | 沟通 + 跨职能协调方向扩张 |

### 4.3 核心矛盾

> "Role expansion without connection is fragile."

**72% 更多跨职能工作 + 连接排名倒数第一** = AI 让工作变宽但关系变浅。这对项目管理工具意味着: 连接/对齐功能将成为新的刚需。

| 源 | Superuser 数据 | 跟踪期 |
