## 1️⃣ 🔴 Jira AI-native 转型正式发布 — 从「追踪工作」到「编排人类与 Agent 协同」

**来源**: [How we're evolving Jira for AI-native software development](https://www.atlassian.com/blog/company-news/how-were-evolving-jira-for-ai-native-software-development) — Atlassian Blog / Company News (2026-07-15)
**作者**: Dave Meyer (Jira Product Lead)
**工具**: Jira × Teamwork Graph × Jira Coding Agent × Jira Planner × DX AI Cost Management
**方法论**: 三层 AI-native SDLC 设计原则 — ① 意图结构化 (intent structured) ② 选择 Agent 不分叉流程 (runtime-agnostic) ③ 自主性全程可观测 (autonomy observable)

> **关键背景**: 本篇是 07-17 明确标注「下次关注 — Team '26 发布的完整文章，需跟进获取」的正式回应。Atlassian 在 Team '26 之后，首次系统地阐述了 Jira 在 AI-native 时代的定位。

### 1.1 核心数据 — AI 生产力差距 (Productivity Gap) 首次量化

| 指标 | 数值 | 来源/方法 |
|:-----|:----:|:----------|
| AI 使用增长 (同比) | **+65%** | DX 纵向研究, 跨专业工程团队 |
| 开发者速度增长 | **+10-15%**, 多数组织 ~10% | 同上 (与 07-13 捕获的 400 组织研究一致) |
| 差距原因 | "软件开发从来不只是写代码" | 意图→上下文→治理 三环断裂 |
| Teamwork Graph 提升准确率 | **+44%** | Atlassian 内部基准测试 |
| Teamwork Graph 降低 Token | **-48%** | 同上 |

**关键论断**: "In a longitudinal study we ran with DX across professional engineering teams, AI usage has increased by 65%, but overall developer velocity did not. It topped out at a 15% increase, with many organizations seeing gains averaging 10%."

**与其他跟踪的交叉验证**:
- 07-13 捕获的 "400 工程组织纵向研究 → 仅 10-15% 增益" → 本篇确认同一结论，并**首次公开 DX 为数据源**
- 07-17 捕获的 Teamwork Graph +44%/-48% → 本篇从 "内测" 升级为 "内部基准测试" 并写入正式发布

### 1.2 AI-native SDLC 三层设计原则

| 原则 | 问题 | Atlassian 方案 |
|:-----|:-----|:--------------|
| **① Intent structured** | Agent 需要比 prompt 更丰富的上下文 | Jira Planner: Confluence spec 双读 (人类+Agent) |
| **② Runtime-agnostic** | 每个 Agent 厂商各自流程分叉 | Jira 统一编排层: Claude / Cursor / Copilot / Jira Coding Agent |
| **③ Autonomy observable** | Agent 会话消失在终端/tab | Agent Sessions: 统一状态面板 + 可追溯 |

### 1.3 新能力发布矩阵

| 能力 | 定位 | 关键特性 |
|:-----|:-----|:---------|
| **Jira Planner** | 复杂项目的 Spec-Driven Dev | 从代码库+Jira+Confluence 历史拉取上下文 → 生成结构化技术 Spec (人类+Agent 双读) |
| **Jira for Slack** | 对话→Agent-ready Issue | @Jira 创建 Issue + 继承对话上下文 |
| **Loom Video Prompts** | 语音+屏幕→结构指令 | 录屏 → 生成 action plan → 创建 Agent-ready Jira Issue |
| **Agents in Jira** | 分配 ↔ 执行 | Claude/Cursor/Copilot 直接 Assign + Codex Coming Soon |
| **Jira Coding Agent** | 内置 Agent (每人) | 每个付费 Jira 计划自带。取 Issue → Teamwork Graph 上下文 → Code Intelligence → 返回 PR |
| **Agent Sessions** | 全 Agent 可见性 | 统一面板: 谁 stuck / 谁 waiting review / 谁 completed |
| **Coding Agent Automations** | 规则驱动 | Jira Automation 规则 → 自动分派 Bug/Vulnerability/Test/文档 |
| **Agentic Engineering Template** | 分钟级项目搭建 | 预配 workflow/status/tracking/integration |
| **DX AI Cost Management** | Agent 经济学 | 统一 Claude/Cursor/Copilot/Jira 的 spend + token 数据 → 团队/项目映射 → Cost per PR |

### 1.4 Reddit 合作信号

> "The bottleneck in AI-native development isn't agent capability, it's coordination at scale to keep our engineers in the flow. We're partnering with Atlassian to solve that: one place where every agent action is visible, governed, and tied to a business outcome."
> — **Sean Joerg, Deputy CISO & Head of Corporate Engineering, Reddit**

**意义**: 头部科技公司 (Reddit) 将 Jira 定位为 Agent 编排中心——coordination at scale 被明确列为最大瓶颈。

### 1.5 跨期分析 — Jira AI-native 演进时间线 (2026 Q2-Q3)

| 日期 | 里程碑 | 覆盖期 |
|:----:|:-------|:-------|
| 05-20 | Cursor in Jira (首个 Agent 厂商入驻) | 07-17 |
| 06-18 | Claude Agent for Jira | 07-13 |
| 06-18 | Agent as First-Class Teammate (assignee 字段) | 07-17 |
| 07-01 | MCP 5M+/day + Governance | 07-10 |
| 07-10 | Agent Dashboard / Codex / @Jira Slack | 07-10 |
| **07-15** | **Jira Planner / Jira Coding Agent / Agent Sessions / DX Cost Mgmt** | **本期** |

> **关键推论**: Jira 在 2 个月内完成了从「Agent 入驻」→「Agent 编排」→「Agent 治理+经济」的完整拼图。07-15 是 Jira 作为 Agent 编排平台的理论+产品双重成熟的标志。

## 2️⃣ 🟡 Boom Supersonic × Linear: 硬件制造借用软件工程交付节奏

**来源**: [Boom Supersonic builds as fast as it flies](https://linear.app/blog/boom-supersonic-builds-as-fast-as-it-flies) — Linear Blog / Customer Story (2026-07-15)
**工具**: Linear (项目管理) + Agent (编码) — 硬件工程团队使用纯软件工程节奏
**方法论**: "Building in short cycles and getting real parts in hand as quickly as they can" — 将软件敏捷节奏映射到物理制造

### 2.1 核心主张

Boom Supersonic 正在本十年末将超音速飞行带回。为实现这种速度，其工程师**借用了软件项目的习惯**：

- 短周期迭代 (short cycles)
- 快速拿到实物零件 (real parts in hand)
- Linear 作为项目节奏的核心载体

### 2.2 与跟踪链的关联

| 维度 | 意义 |
|:-----|:------|
| **硬件×软件 交付节奏趋同** | 继 Cars24 (二手车电商)、Ramp (金融科技)、Coinbase/Base (Web3) 后，**制造业也开始采用 Linear 的纯软件节奏** |
| **AI 时代的项目管理工具** | 制造业使用 Linear 管理硬件交付 — 表明 AI 项目管理工具不仅仅服务于软件团队，也在向更广泛的工程领域渗透 |
| **与 Atlassian 的对比** | Linear 在垂直深度的策略 (单工具全流程) vs Atlassian 水平广度 (300 工具集成) — Boom Supersonic 选择 Linear 表明在制造场景中「极简+深度」胜过「全量集成」 |

### 2.3 补充数据: Coinbase/Base 的 Agent-first 开发

同期 Linear 客户故事 (03-26) 提到:

> "In January 2026, Chintan asked his entire engineering organisation to delete their IDEs and write zero lines of code. For two weeks, every engineer at Base would have to do their job without touching a code editor."

**意义**: 当交付速度足够快，硬件工程 (Boom Supersonic) 可以借用软件节奏；当编码本身被 Agent 覆盖，软件工程 (Base) 可以借用非编码工作流。
