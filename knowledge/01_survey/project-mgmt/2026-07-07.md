## 1️⃣ AI 诚实悖论：94% 使用但披露被罚 10× 懒

**来源**: [New research shows honesty about AI use at work is backfiring — Atlassian Blog / AI at Work](https://www.atlassian.com/blog/ai-at-work/new-research-shows-honesty-about-ai-use-at-work-is-backfiring) (2026-06-10)
**作者**: Conor Donegan + Halina Mader, Atlassian Teamwork Lab
**方法论**: 961 位美国知识工作者控制实验 (03-30~04-07) + 1,006 人脉冲调研 (04-24~05-06)
**核心主张**: AI 采用已接近普适，但文化接受远未跟上，披露 AI 使用带来显著的职业惩罚。

### 1.1 关键量化数据

| 指标 | 数值 | 方法论 |
|:-----|:----:|:-------|
| 美国知识工作者上月使用 AI | **94%** | 1,006 人脉冲调研 |
| 对经理/同事透明披露 | **~80%** (约3/4) | 同上 |
| 披露 AI 使用→评为更懒 | **10×** | 961 人控制实验 |
| 不推荐参与高可见度项目 | **-24 百分点** | 同上 |
| 「团队导向」框架→评分提升 | +11 分(努力) / +8 分(推荐) | 框架对比实验 |
| 未披露 AI 使用 | 最高评分(SOTA) | 控制组 |
| AI 庆祝文化→惩罚消失 | 几乎完全消失 | 实验条件控制 |

### 1.2 核心洞察：这是一个文化问题，不是技术问题

> 「Companies are telling the workforce to use AI, but employees are penalizing each other for being honest about it. Until leaders change the culture, you don't have an AI strategy; you have an AI contradiction.」— Molly Sands, Head of Teamwork Lab

**反直觉推论**：94% 的采用率意味着采用问题已经解决。**新问题是文化后果**——惩罚披露AI使用的诚实行为。当工人学会诚实=被贴懒人标签时，理性反应是**停止谈论AI使用**→ AI 使用转入地下 → 组织失去从中学习、规模化有效做法、发现问题的能力。

**框架效应**：描述为「为团队/客户」而非「为自己省时间」有边际改善（+11/+8分），但仍远低于不提及 AI 的基线。

### 1.3 跨来源交叉验证

> 🔗 关联 [07-06 Speed Paradox](2026-07-06.md) (组织瓶颈) + [06-26 10-15% ceiling](2026-06-26.md) (生产力天花板)
>
> **新发现**：此前跟踪链聚焦「AI 生产力的组织损耗」，但忽略了**社会损耗**——即使技术效率提升到了组织层面，**文化规范不匹配会系统性抑制 AI 的正向循环**。诚实悖论解释了为什么许多组织的 AI ROI 不能线性放大：管理者无法观察到团队的真实 AI 使用模式，无法规模化「什么有效」，也无法捕捉「什么无效」。

## 2️⃣ AI 创造力扁平原化 & 认知让步 — AI Collaboration Framework

**来源**: [Is AI flattening your team's creativity? Here's how to tell. — Atlassian Blog / AI at Work](https://www.atlassian.com/blog/ai-at-work/is-ai-flattening-your-teams-creativity-heres-how-to-tell) (2026-05-20)
**作者**: Dr. Molly Sands, Head of Atlassian Teamwork Lab
**核心主张**: AI 加速个体创造性但使群体输出趋同→「认知让步」(Cognitive Surrender) → 团队需要明确的 AI Collaboration Framework 来保护人的判断。

### 2.1 三大证据化陷阱

| 陷阱 | 证据 | 来源 |
|:-----|:-----|:------|
| **1. AI 诱导的群体思维** | AI 辅助的个体更「有创意」，但群体输出收窄、聚类于模型建议模式 | HCI 研究 |
| **2. 认知让步** | AI 用户应对复杂任务时神经活动减弱、Quoting 自己作品准确性下降、无AI后也持续偏低 | MIT 研究 + Wharton lab |
| | 访问 AI 膨胀了用户对准确性的自信（即使错了） | Wharton: "cognitive surrender" |
| | 81,000 全球 AI 用户调查：认知萎缩是第四大担忧 | Anthropic 调查 |
| | 工程师原话：「遇到 AI 处理不了的复杂问题→'好久没干这个了，感觉更难了'」 | Atlassian Teamwork Lab 定性研究 |
| **3. 空心化自身价值** | 用户获得表面理解 (illusion of explanatory depth) → 成为「可信答案的转发者」而非推理的拥有者 | 认知科学 |

### 2.2 AI Collaboration Framework

Teamwork Lab 发布用于团队决策的框架，核心是**显式选择 AI 的参与模式**：

```
高                   +---------------------------------+
                    |     Human-First Zone              |
            模糊性/  |  (Strategy / Risk / Design)       |
            高价值  |  Think -> Capture -> AI 协助         |
                    +---------------------------------+
                    |     Collaboration Zone             |
                    |  (Draft -> Review -> Refine)        |
                    +---------------------------------+
                    |     AI-First Zone                  |
            低     |  (Quick answers / Templates)       |
                    +---------------------------------+
                    低 <- 输出可被判断 -> 高
```

**给团队的 4 个实操指导**:
1. **建立 AI Working Agreements**: 团队的动态使用准则，定期更新
2. **让人的思考先于 AI**: 高模糊性/高价值任务，先写自己的思路再交给 AI
3. **保护深度工作时间**: 如果每件事都是冲刺，satisficing 是唯一理性策略
4. **运行 AI Retros**: 里程碑后用10分钟评估 AI 加速/锚定/扁平化的效果

### 2.3 State of Teams 2026 引用的补充数据

## 3️⃣ 工程实证：Jira Agent 自动化 80% 工程杂务

**来源**: [How We Cut up to 80% of Engineering "Chores" Using AI Agents in Jira — Atlassian Blog / Development](https://www.atlassian.com/blog/development/ai-agents-jira-engineering-maintenance) (2026-06-01)
**作者**: Arnaud Moret (Principal Engineer, Jira) + WaiYee Loo (Senior Engineer, Jira)
**核心主张**: 将已知的重复性工程工作的模式编码为 Jira 工作项 + Agent 指令 + Agent Skills，用 Jira 作为 Agent 编排层。

### 3.1 关键量化数据

| 场景 | 之前 | 之后 | 节省 |
|:-----|:----|:----|:----:|
| **Flaky Tests** | 2 小时/次, ~1次/天 | Agent 自动第一遍诊断+修复 | **~80% 工程小时数** |
| | 每月约 1 人周 | | **每月节省约 1 人周** |
| **Stale Feature Flags** | 手动+高风险 | Agent 自动识别+提 PR | **500+ PRs / 70 天** |
| | | 日 cron 扫描→创建Jira→分配Agent→Draft PR | |

### 3.2 方法论：Jira 作为 Agent 编排层

```
Cron扫描 -> Jira Work Item (含: flag名/类型/仓库/code引用/目标状态)
         -> Agent 匹配 Repository-Specific Skill
         -> Agent 第一遍诊断/修复
         -> Draft PR + Jira Comment
         -> 工程师 Review -> Merge
```

**三个关键设计**:

| 设计 | 作用 |
|:-----|:------|
| **Repository-Specific Skills** | 每种测试类型一个专用 Agent Skill（Unit/Integration/Visual Regression）+ 针对每个仓库的定制的特征 flag 清理流程 |
| **Work Item as Prompt** | Jira Issue 不仅是跟踪记录，同时是给 Agent 的完整上下文（flag 名、类型、仓库路径、目标状态） |
| **Human-in-the-Loop** | Agent 只做第一遍 → Draft PR → 工程师 Review & Merge，确保代码质量 |

### 3.3 关键洞察：「反直觉的复用」

> 「Our team has spent years fixing these exact categories of issues. That pattern recognition is what makes delegation to agents possible.」

**不是 AI 自己学会修 bug，而是团队多年的**模式识别经验 **先编码成 Agent Skills，然后 Agent 按规则执行第一遍。**这套方法可迁移到所有具有重复模式的工程杂务：漏洞修复、可访问性问题、长尾 bug——只要团队能定义「什么样子算修好了」。

### 3.4 与跟踪链的交叉

> 🔗 这是一篇**工程实操报告**，与 06-22/06-26/06-29 的理论框架（Jira as Agent Orchestration Layer）构成了 **Implementation → Evidence 闭环**。**80% 不再是理论数字，而是 Jira 自家工程团队的实测结果。**

> 🔗 关联 07-02 的「AI-native SDLC +19% PRs」— 这里的 80% 节省针对的是**特定类别的 KTLO 工作**（非新功能开发），说明 AI 在维护性工作中的节省幅度远高于新功能开发。
