## Linear Agent：从"定义路径"转向"划定边界"（架构方法论主线）

- **AI 反转传统软件设计逻辑：以边界代替固定路径**（Linear Blog, 2026-08-10, Matthijs Wolting）：传统工程=缩小可能结果空间直到同一动作稳定产生同一结果；Linear Agent 的价值恰在于做未被预定义的工作，因此不编写固定执行路径，而是划定边界让 agent 自主探索；四层边界=system prompt（交流风格/敏感话题硬边界/产品概念解释/默认使用意见）、工具设计（约束编入工具参数形状而非 prompt 文本，使无效动作难以执行）、agent 对产品的模型（与 coding agent 形状相反——coding agent 是少量深工具+模型训练强先验，Linear Agent 是大量浅工具+产品语义需系统技能补齐）、单次运行范围（https://linear.app/blog/how-we-built-linear-agent）
- **System skills 渐进式披露：上下文聚焦 + 能力可扩展**（同上, 2026-08-10）：每个系统技能=元数据+prompt 片段+工具集，运行前按用户 prompt 与调用语境推断预载（Slack/项目页调用预载 projects 技能），运行中按需加载（草拟项目更新时自行加载 issues/PRs 技能）；避免全量 prompt+工具集膨胀，且与用户自建 skills（复用指令）区分（https://linear.app/blog/how-we-built-linear-agent）
- **自建 harness 支撑三种运行中编排模式**（同上, 2026-08-10）：动态工具注入（技能加载后立即可用且保护 provider prefix cache，naive 实现会重算已有上下文推高成本）、条件工具调用审批（上下文感知而非按工具名粗粒度规则：会话内自建可删、删除既有 issue 需确认；多数评论线程免审批、同步公开仓库的线程需暂停确认）、异步子 agent 执行（父 agent 挂起不耗服务端资源，对父表现为同步工具调用）；选择自建而非现成 harness 库，因库对执行流有强观点、无法支持运行中编排（https://linear.app/blog/how-we-built-linear-agent）
- **明确权衡：用广度换可预测性**（同上, 2026-08-10）：agent 可能偶尔拒绝无法安全完成的任务，但犯错空间大幅受限；随模型能力提升，未过度脚本化的动作空间可自然组合更复杂任务（https://linear.app/blog/how-we-built-linear-agent）

## Loops：团队级循环 agent 工作流

- **Loop engineering 从个人扩展到整个产品团队**（Linear Blog, 2026-07-20, Nan Yu）：Claude Code/Codex 的 /loop 已把重复任务交给个人 agent，Loops 让整个团队共享该模式；plain language 描述任务 + 选择 schedule（定时）或 event（事件）触发，运行时从 workspace、连接代码库、MCP servers、历史运行记录取上下文（https://linear.app/blog/introducing-loops）
- **三类典型用例**（同上, 2026-07-20）：triage 诊断分派（issue 进入 triage 时审查描述/评论/代码库，路径清晰则直接启动 coding session 修复）、feature request 拆平台任务（自动创建 iOS/Android/Web 各平台 issue 并路由团队）、文档保鲜（每日对照中央发布计划审查项目/initiative 变更，更新文档并留注释说明原因）（https://linear.app/blog/introducing-loops）
- **共享可见性与治理**（同上+changelog, 2026-07-20）：Loops 在 team/workspace 级运行，任何人可审查指令、配置与每次运行记录；Business/Enterprise 计划 + AI credits 计费，发布期 $20/seat 促销 credits（2026-08-20 过期）（https://linear.app/blog/introducing-loops）

## Coding Sessions 深化与透明定价

- **Coding sessions 三升级：环境配置/浏览器测试/透明定价**（Linear Changelog, 2026-08-20）：可配置环境=自动检测并安装 toolchain 与依赖（开箱支持 Python/Ruby/Go 等），团队可 pin 运行时版本、加 setup scripts 与环境变量；浏览器测试=agent 打开应用走用户流程验证实现、捕捉前后截图（能发现代码审查漏掉的交互/视觉回归，发现问题自修自测后返回）；定价两段式=模型 token 按 provider 公布价零 markup + sandbox 运行时 $0.25/20 分钟块，用量仪表盘分模型展示 token 与成本（https://linear.app/changelog）
- **花费控制下放给团队**（同上, 2026-08-20）：admin 可设 workspace-wide 与 per-user spend limits（日/周/月重置），达限暂停 AI credits 使用直到重置或 admin 调额（https://linear.app/changelog）
- **量化锚点：Linear 内部约 30% incoming bug reports 由 agent 自动解决，多数首轮通过**（Linear Changelog, 2026-06-11）：triage 自动化=新 issue 上报时 Linear Agent 先调查并尝试修复再触达工程师；遵循团队指引、经 MCP 从 Sentry/Datadog 取证、检查代码库溯源根因后产出修复；该流程是 coding sessions 系列的基线数据（https://linear.app/changelog）

## 观察小结

- **主线信号**：Linear 本周进入"AI 项目管理平台成熟化"阶段——功能发布期（Loops/Coding Sessions）之后开始输出三层方法论：架构层（边界设计/渐进式技能披露/自定义 harness 三大编排模式）、治理层（initiative 责任归属、Okta 托管 MCP 授权、花费限额）、经济层（零 markup token + $0.25/20min sandbox 的透明定价）
- **与 Atlassian 对照（08-24 已收录）**：两大项目管理平台同向收敛——AI 从工具升维为可编排、可治理的执行层；差异在路径：Atlassian 主推"work factory"结构化知识工作流程，Linear 主推"agent 自治边界 + 运行中编排"工程实践，前者重流程封装、后者重执行可控
- **量化锚点**：30% bug 自动解决（多数首轮）、$0.25/20min sandbox 成本、模型 token 零 markup——agent 化研发的经济模型开始透明化，可作为自建 agent 平台成本测算参照
- **方法论外溢**：Linear Agent 的"system skills 渐进式披露 + 保护 prefix cache"与"约束编入工具设计而非 prompt"两条工程原则，对服务器知识库的 AI 工具层设计（技能按需加载、工具约束内建）有直接借鉴价值
- **来源说明**：4 条 URL（blog 两篇 + changelog + 列表页）均经 curl HTTP 200 逐条验证；changelog 条目为单页应用无独立 URL，以 https://linear.app/changelog 为统一来源并标注日期；08-17/08-11/08-18 三篇取自列表页标题+摘要，slug 未收录于 sitemap 无法独立验证，故标注列表页来源；AI usage patterns 与 Coinbase 两篇正文未抓取（slug 推断 404 止损），待下轮深读
