## 1️⃣ Copilot Code Review: 工具链迁移后发现「更好用的工具反而更差了」，然后通过重写指令降本20% 🔍

- **来源**: [GitHub Blog Engineering](https://github.blog/engineering/better-tools-made-copilot-code-review-worse-heres-how-we-actually-improved-it/) · Jul 10, 2026
- **工具**: **GitHub Copilot Code Review**
- **作者**: Napalys Klicius (GitHub, Agentic Systems)

### 背景：工具替换引发质量倒退

Copilot Code Review 原本使用自有的代码探索工具（`list_dir` / `search_file` / `search_dir` / `read_code`）。团队希望统一到 Copilot CLI 体系共享的 Unix 风格工具集（`grep` / `glob` / `view`），以减少重复维护，让一处改进惠及多个产品。

> 表面看只是简单的映射替换：
> - `list_dir` → `glob`
> - `search_file` / `search_dir` → `grep`
> - `read_code` → `view`

结果出乎意料：**成本上升，有效评论数下降**。

### 根因：通用工具的 Agent 行为模式不适合 Code Review

Internal benchmark 的 trace 显示：Agent 拿到 grep/glob/view 后，行为模式变成了「**浏览仓库**」而非「**审查 PR**」——

```
旧模式（通用工具）：
  搜索广泛 -> 猜测路径 -> 大量读取 -> 找到更多可搜索项 -> 上下文膨胀

预期模式（Review 导向）：
  从 diff 出发 -> 形成具体审查问题 -> grep 定位 -> glob 确认路径 -> view 精确读取
```

区别在于：通用编码助手需要「理解整个仓库再改」，而 Code Review 需要「从 diff 出发，找最小相关代码做判断」。

### 解法：为 Review 场景重写工具指令

核心原则：
1. **从 diff 出发**：形成具体审查问题后再搜索
2. **先窄后读**：grep/glob 做发现，只有确定文件+行号后才 view
3. **批量发现再批量读取**：避免搜索→读取→再搜索的交替循环
4. **优雅降级**：grep 失败时重试简化转义搜索，路径错误时用 glob 而非猜临近路径

### 结果：成本降 ~20%，质量不变

| 指标 | 变化 |
|:-----|:----|
| 平均审查成本 | **↓ ~20%** |
| 审查质量信号 | 无退化（可安全上线） |
| 工具调用次数 | 持平，但更多花费在相关证据上 |
| 上下文膨胀 | 显著减少 |

### 关键经验（对我们有直接参考价值）

> **给 Agent 更好的工具，不等于它会有更好的表现——工具的描述和指令才是决定性的。**
>
> 工具描述和系统指令 ≈ API 文档。不清晰的 API 文档让开发者困惑，不清晰的工具 prompting 也让 LLM 困惑。**一个小措辞变化就能影响成本、质量和 Agent 的注意力分配方式。**

**同样的工具，换到 CLI 场景就没这个效果**——因为 CLI 需要更广泛的探索。这验证了：**共享工具可以，但指令必须匹配场景。**

**价值说明**: 这篇博客对我们设计 AI 工具链有直接参考意义——工具共享是好的工程实践，但**每个场景的 Agent instruction 必须独立设计**。我们在工作中使用 Copilot / Cursor / Claude Code 时，如果感觉「工具多了反而变慢」，很可能就是指令与场景不匹配的问题。同理，为团队内部分配 Agent 时，**工具的暴露范围（哪些 MCP 可见）+ 指令风格（探索型 vs 验证型）需要按任务类型做差异化配置，而非一刀切**。

## 2️⃣ GitHub Agentic Workflows 实战：Aspire 团队跨仓库文档自动化 📝

- **来源**: [GitHub Blog Engineering](https://github.blog/engineering/automating-cross-repo-documentation-with-github-agentic-workflows/) · Jul 8, 2026
- **工具**: **GitHub Agentic Workflows**（GitHub Next 团队出品）
- **作者**: David Pine & Peli de Halleux (Microsoft Aspire 团队)

### 背景与痛点

Microsoft Aspire 团队（~10 人）的产品代码在 `microsoft/aspire`，文档在 `microsoft/aspire.dev`——**跨仓库**。传统流程：

```
工程师合并功能 PR（aspire）
   v 数周后
文档作者注意到变更
   v 反向工程 diff
工程师已投入下一个功能，模糊回忆
   v 
文档发布时可能已落后于版本
```

这就是 **"反向工程税"**。

### 方案：pr-docs-check 工作流

基于 GitHub Agentic Workflows 构建，核心设计：

1. **触发**：`pull_request: closed` + `merged == true`
2. **Pre-agent 确定性步骤**：用 bash 解析里程碑 → 确定文档目标分支
   - PR milestone 标题（如 `13.4`）→ `release/13.4` on aspire.dev
   - 回退到 `main`
3. **Agent 判断**：读 diff + linked issues → 判断是否需文档 → 如需则起草内容
4. **安全写操作**（safe-outputs）：Agent 不直接写 GitHub，而是 emit 意图 JSON
   - 一个极简的 verifiable pipeline 处理写入
   - token 权限限制两个 repo，仅允许 `main` / `release/*` 分支
   - 永远 draft PR + SME 作为 reviewer
   - `protected-files: blocked`——Agent 不能触及 AGENTS.md / 依赖清单 / 安全配置

### 结果：硬数据

| 指标 | 值 |
|:-----|:---|
| 产品 PR 合并数（30天） | **396** |
| 工作流运行次数 | **396**（每次合并都触发） |
| 创建的文档 draft PR | **82**（其余判定为不需要文档→正常） |
| 文档 PR 合并率 | **100%**（0 关闭、0 未合并） |
| 中位数合并时间 | **44.8 小时** |
| 24h 内合并率 | **38%** |
| 7天内合并率 | **96%** |

> 注意：50%+ 的 PR 被 Agent 判定为「不需要文档」（内部重构/CI 修改/测试修复），**这不是缺陷而是特性**。

### 架构亮点

```
+----------------------------------------------+
|  pr-docs-check.md (aspire repo)              |
|                                                |
|  1. bash: 里程碑->目标分支解析                  |
|  2. Agent: 读 diff + 判断 + 起草文档内容       |
|  3. safe-outputs: emit create_pull_request     |
|     +- title: "[docs] ..."                     |
|     +- draft: true                             |
|     +- reviewer: PR 审批者 (SME)               |
|     +- target: microsoft/aspire.dev            |
|  4. 源 PR 上自动评论：文旦 PR 链接             |
+----------------------------------------------+
```

**关键安全设计**: Agent 的 GitHub App Token 只安装到两个仓库。写操作通过 safe-outputs handler 的 allow-list 过滤。**Agent 的推理是模糊的，但操作表面不是。**

### 其他工作流

Aspire 团队还有 4 个 Agentic Workflows 在生产运行：
- **milestone-changelog.md**: 每 2h 运行，维护版本的 ChangeLog wiki 页面（346 runs）
- **release-update-support-mdx.md**: 稳定版发布后更新 support 页面
- **update-integration-data.md**: 每日更新 NuGet 元数据 + GitHub stats
- **repo-pulse.md**: 滚动 3 天仓库仪表盘（固定 issue，原地更新）

**价值说明**: 这是目前为止最完整、有硬数据的 **Agentic Workflows 生产落地案例**。核心经验：
- **跨仓库自动化**的安全约束反而是设计质量的保证（限制越多越可靠）
- **Agent ≠ 替代人**——draft + SME review 模式是最好的分工
- **Pre-agent 确定性步骤**极大降低 token 消耗，这是我们在自己工作流中也应该采用的模式
- 对团队也有直接启发：**文档自动化不必一步到位**，从单个 `pr-docs-check` 起步，效果可衡量的同时风险可控

## 3️⃣ GitHub Agentic Workflows Token 效率优化：62% Token 节约的实操方法论 ⚡

- **来源**: [GitHub Blog Engineering](https://github.blog/engineering/improving-token-efficiency-in-github-agentic-workflows/) · May 7, 2026 *(Updated May 13)*
- **工具**: **GitHub Agentic Workflows**（自身优化）
- **作者**: Landon Cox & Mara Kiefer (Microsoft Research)

> 📅 注：本文虽发布于 5 月，之前报告未覆盖，且其**方法论价值极高**，特此补录。

### 核心挑战

CI 中的 Agentic Workflows 自动触发、重复运行，token 消耗容易被忽视。GitHub 在 2026年4月 开始系统性地优化自家产线中的 Agentic Workflows token 消耗。

### 优化方法论

#### Step 1: 可观测性先行

利用 Agentic Workflows 的 API proxy 架构（Agent 不直接访问凭据），统一采集所有调用日志：
- 每个 workflow 输出 `token-usage.jsonl`——input/output/cache tokens、model、provider、timestamp
- 统一格式，跨 Agent framework（Claude CLI / Copilot CLI / Codex CLI）

#### Step 2: Workflows 优化 Workflows（自举）

建了两个优化工作流：

**Daily Token Usage Auditor**
- 聚合 token 消耗，按 workflow 分组
- 标记异常：通常 4 轮 LLM 的工作流突然跑了 18 轮

**Daily Token Optimizer**
- 被 Auditor 标记后，读 workflow 源代码+日志
- 自动创建 Issue 描述具体低效点并给出优化建议

#### Step 3: 三大优化手段

**① 裁剪未使用的 MCP 工具**（最直接的优化）
- GitHub MCP server 有 ~40 个工具，schema 占用 10-15KB/turn
- Agent 实际只用到其中 2-3 个
- 裁剪后每次调用节省 **8-12 KB** 上下文

**② 用 GitHub CLI 替代 MCP 的纯数据获取**
- MCP 调用 = **一个完整 LLM 推理回合**——决定调用→构造参数→收到响应→处理上下文
- `gh pr diff` = **一次确定性 HTTP 请求**——无 LLM 开销
- 两种模式：
  - **Pre-agent 下载**: Agent 启动前 `gh` 命令下载固定数据（diff / 文件列表）
  - **In-agent CLI 代理**: Agent 运行时动态 `gh` 调用，通过透明代理路由

**③ 模型降级**
- Haiku 比 Sonnet token 成本 ~4× 低

#### Step 4: 有效 Token（ET）度量

解决「不同模型混用」和「工作量波动」两大干扰因素：

```
ET = m × (1.0 × I + 0.1 × C + 4.0 × O)
```
- `m`: 模型倍数（Haiku=0.25, Sonnet=1.0, Opus=5.0）
- `C`: cache-read tokens（0.1×）→ 缓存读取成本极低
- `O`: output tokens（4×）→ 最贵的 token 类型

### 实测结果

| 工作流 | ET 降幅 | 运行频率 | 说明 |
|:-------|:-------:|:--------:|:-----|
| Auto-Triage Issues | **-62%** | 日均 6.8 次 | 预读取 issue 元数据/标签，移出 LLM 推理环 |
| Security Guard | **-43%** | 高频（每 PR） | 不触碰安全文件的 PR 直接跳过 LLM |
| Smoke Claude | **-59%** | 高频 | MCP 工具裁剪+模型降级到 Haiku |
| Daily Community Attribution | **-37%** | 中频 | 8 个 MCP 工具 0 次调用→全裁剪 |
| Daily Compiler Quality | **-19%** | 日级 | 适中 |

### 关键教训

> **最便宜的 LLM 调用，是你不做的那一次。**
> - **确定性数据获取**（gh CLI / pre-agent steps）应该完全移出 LLM 推理环
> - **未使用的 MCP 工具是纯 overhead**，每个 tool schema 都是永久的上下文负担
> - **一条错误的 allow-list 配置**就能让 Agent 陷入 64 轮 fallback 循环——配置即性能

**价值说明**: 这篇方法论对我们有两层意义：
- **直接可用**：在自己的 Agent 工作流中也应该用 pre-agent CLI 步骤+裁剪 MCP 工具+模型分层
- **度量思路**：ET 公式和「LLM turns/run 不变但 tokens/call 下降=真优化」的判定逻辑可以直接复用
- **警示**：Agent 的「鲁莽搜索循环」现象在 Copilot Code Review 和 Agentic Workflows 中都出现了——这是通用 agent + 宽泛指令的通病，必须在 prompt 设计层面约束
