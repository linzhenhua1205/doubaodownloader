## 1️⃣ Cursor v3.11 (Jul 10) — Side Chats + 对话搜索 + 重做项目/仓库选择器 🗣️🔍

- **来源**: [Cursor Changelog](https://www.cursor.com/changelog)
- **工具**: Cursor
- **标签**: `cursor` `ai-ide` `side-chat` `conversation-search` `cloud-agent` `hooks`
- **发布时间**: 2026-07-10

**概览**: v3.11 是 Cursor 在三位一体（本地+云端+移动）布局后的首个**体验优化**版本——不堆新大模块，而是打磨 Agent 工作流中的上下文管理、信息检索和导航效率。

---

### 🔹 Side Chats：不打断主 Agent 的轻量并行对话

| 功能 | 说明 |
|:-----|:------|
| **触发方式** | `/side`、`/btw` 或 Chat 面板顶部 + 按钮 |
| **上下文继承** | Side Chat 自动继承主 Chat 的上下文，可引用 / @ 拉回主线程 |
| **默认聚焦** | 只读模式（reading/searching/answering），不会修改代码 |
| **持久化** | 每次 Side Chat 是完整的 agent 对话，可后续回看、追问 |
| **典型场景** | 用主 Agent 写代码，Side Chat 查资料/验证方案/讨论替代方案，互不阻塞 |

> **价值**: 过去「查个资料 → 切到新 Chat → 丢失上下文」或「在同一个 Chat 里问杂乱问题 → Agent 上下文膨胀」。Side Chat 让**主 Agent 持续运行**的同时，并行做调查/求证/备选方案评估，完成后可用 @ 把结论带回主线。这是 Agent IDE 对「多线程工作流」的首次原生支持。

### 🔹 对话搜索 (Conversation Search)

| 能力 | 说明 |
|:-----|:------|
| **搜索范围** | 全部历史 Agent 对话的 transcripts（不仅是名字和 PR 号） |
| **入口** | Cmd+K → 搜索对话内容 |
| **索引引擎** | 本地构建搜索索引，支持数千条对话的毫秒级响应 |
| **对话内搜索** | 单条对话内 Cmd+F，支持匹配计数 + 跳转 |

> **价值**: 随着 Cursor Agent 对话数破百/千，找到「上次那个 Agent 怎么说 X 问题」成为刚需。对话内容全文搜索而非只能搜标题，让知识复用成为可能——尤其对于 Cloud Agent 跑了一堆长任务后，结果散落在大量历史对话中。

### 🔹 重新设计的项目/仓库选择器

| 改进 | 说明 |
|:-----|:------|
| **分类分组** | No Repo / On This Computer / Cloud 三大类 |
| **Run on 选择器** | 先选运行环境（Cloud / This Computer / Remote Machines）→ 再选具体环境 |
| **分支选择器** | 默认显示 default branch + 最近使用分支，搜全量 |
| **远程合并** | 自己的机器 + Team Pools + 远程 workspace 合并为「Remote Machines」统一入口 |
| **多仓库** | 多 repo / 多 root 选择用 Select Multiple toggle，不再需要独立的 Set Up Workspace |
| **云仓库** | 如果仓库仅存在于云端，选择器建议 clone 到本地 |
| **简化** | 搜索移到顶部、去掉 Home 概念、去掉分支列表中的 Current 标签、一行移除 Recent |

> **价值**: 之前 Cursor 的项目选择器在 Cloud Agent / Local / Remote 三个入口间切换成本高、找文件路径长。新版把「在哪里跑」和「跑什么」做了清晰分层。对于多项目/多仓库/混用环境的用户来说操作效率显著提升。

### 🔹 新的 Cloud Agent Hooks

新增 hooks 让开发者可以**观察和控制 Agent 对话本身**（相较于之前只支持 tool execution / file / shell 类 hooks）：

| Hook | 触发时机 |
|:-----|:---------|
| `beforeSubmitPrompt` | Agent 提交 prompt 前 |
| `afterAgentResponse` | Agent 回复完成后 |
| `afterAgentThought` | Agent 内部思考步骤后 |
| `subagentStart` | 子 Agent 启动时 |
| `stop` | Agent 停止时 |

> **价值**: 这些 hooks 使开发者可以构建**自纠错循环**——监控 Agent 的推理过程、约束子 Agent 的行为、在 Agent 输出后进行校验/修正。对于需要自定义 Agent 工作流的企业团队来说，这是从「黑盒使用」到「可观测可干预」的关键一步。

---

**总结**: v3.11 是「体验版本」，但几个功能点值得关注：
- **Side Chat** 是 Agent IDE 对「并行工作流」的首次原生实现，解决了长任务中「查一下却打断主流程」的核心矛盾
- **对话搜索** 让 Cursor 从「写代码工具」向「工作记忆系统」进化——过去的 Agent 对话不再是「用完即弃」，而是可检索的知识资产
- **Cloud Agent Hooks 升级** 让有工程能力的团队可以构建自己的 Agent 质量门

## 2️⃣ GitHub Copilot Code Review 深度复盘：换工具不如改指令 🧠📉

- **来源**: [GitHub Blog Engineering (Jul 10, 2026)](https://github.blog/engineering/better-tools-made-copilot-code-review-worse-heres-how-we-actually-improved-it/)
- **工具**: GitHub Copilot Code Review
- **文章**: Napalys Klicius (GitHub Software Engineer)
- **标签**: `github` `copilot` `code-review` `agent-workflow` `prompt-engineering` `tool-design`

### 🔹 核心发现

| 维度 | 结论 |
|:-----|:------|
| **问题** | 把 Copilot Code Review 换到共享的 Unix 风格工具（grep/glob/view）后，**成本更高了、捕获的问题更少了** |
| **根因** | 不是工具的问题，是 **Agent 的指令（instructions）不对**。工具被当作「通用编程助手」而非「代码审查者」来使用 |
| **解法** | 重写 tool instructions，让 Agent 像审稿人而非浏览者一样工作 |
| **结果** | 平均审查成本 **降低约 20%**，审查质量保持不变 |

### 🔹 问题重现：Agent 在「浏览仓库」而非「审查 PR」

换用共享工具后，Agent 的行为模式变成了：

```
搜索（broadly）-> 猜路径 -> 读文件 -> 发现更多搜索点 -> 再搜索
```

这在「理解整个仓库」的场景下没问题，但审稿人不应该这样工作。一个真实审稿人的流程是：

```
从 diff 出发 -> 问具体问题（这个函数在哪里被调用？这个配置键还有别的用途吗？）
-> 用 grep 精准搜索 -> 用 glob 定位文件 -> 用 view 读取最小上下文
-> 判断是否有风险
```

### 🔹 关键改进：重写 tool instructions

| 指令维度 | 通用 Agent 风格 | 审查 Agent 风格 |
|:---------|:----------------|:-----------------|
| **出发点** | 理解仓库 | 从 diff 出发，形成审查问题 |
| **搜索策略** | 先读一大片再找 | 先用 grep/glob 精准搜索，再用 view 读取最小上下文 |
| **失败恢复** | 猜邻近路径继续读 | grep 失败→用更简单的转义搜索重试；路径猜错→glob 而非继续猜 |
| **批处理** | 搜索与读交替 | 批量搜索→批量读取→判断 |
| **上下文控制** | 可能携带大量无关文件进上下文 | 只保留回答问题所需的最小上下文 |

### 🔹 技术洞察：工具结果≠可丢弃的打印件

> "Extra file contents can be carried forward into later reasoning, increasing cost and sometimes making the review less focused. A tool result is not a disposable printout; for an agent, it's extra tokens that stay in the context window."

这一点是关键：**在 Agent 系统中，工具输出不是可丢弃的中间结果，而是会留在上下文窗口中的 token 成本**。因此「多给点上下文以防万一」的策略在 Agent 场景中会适得其反——消耗了 token 却没有提高质量。

### 🔹 验证方法：Benchmark 提供行为级可见性

团队使用内部 benchmark 不只是看最终分数，而是**追踪 Agent 的工具调用路径**：

- Agent 是先缩小搜索范围，还是先广泛阅读？
- 是否批量执行独立搜索？
- 调用 view 时是否有明确理由？
- 失败恢复路径是否收敛？

这种**行为级别的调试能力**（而非只看最终指标）是快速迭代指令质量的关键基础设施。

### 🔹 反例验证：同样指令在 CLI 上无效

有趣的是，同样的「聚焦审查」指令在 Copilot CLI（互动式编程助手）上没有产生同样效果。原因很清楚：

| 场景 | 审查 | CLI 交互 |
|:-----|:-----|:---------|
| **起点** | 固定 diff | 用户自由提问 |
| **任务边界** | 有限（判断风险） | 开放（理解/规划/修改/探索） |
| **上下文需求** | 最小化 | 随任务变化 |

> **关键教训**: 共享工具可以重复使用，但**围绕工具的指令必须适配产品场景**。同一套 grep/glob/view 工具，在审查场景和编程助手场景下需要完全不同的 workflow 设计。

### 🔹 对 AI 工具设计者的启示

| 维度 | 启示 |
|:-----|:------|
| **工具即 API 文档** | 对 Agent 来说，tool descriptions + instructions 就是 API 文档——写清楚了 Agent 才能正确使用 |
| **指令比工具更重要** | 换工具不一定见效，改指令可能产生更大影响 |
| **行为跟踪>最终分数** | Benchmark 要能看 Agent 的行为路径，而不仅仅是最终指标 |
| **不跨场景复用指令** | 同一套工具在不同产品场景下需要不同的 instructions |
| **工具结果有隐形成本** | 每次工具调用结果都在上下文窗口里，不是「免费的」 |

## 📊 趋势观察

| 趋势 | 说明 | 关键信号 |

| **Agent 工作流精细化** | AI 编程工具从「能用」到「用得高效」，关注点从「能不能生成代码」转向「怎么引导 Agent 做正确的事」 | GitHub 这篇文章是最好的例证——指导 Agent「如何工作」比换更好的工具更重要 |

| **Agent 并行工作流** | Side Chat 支持在 Agent 主任务运行的同时做轻量级调查，让开发者可以「多线程」与 Agent 协作 | Cursor v3.11 Side Chats |
| **Agent 可观测性** | 工具调用轨迹、推理步骤 hooks、行为级 benchmark——AI 工具正在从「黑盒」走向「可观测、可调试、可干预」 | GitHub Benchmark 行为跟踪、Cursor Cloud Agent Hooks |
