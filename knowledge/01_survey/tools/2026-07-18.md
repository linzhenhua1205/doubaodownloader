## 1️⃣ GitHub Blog Engineering: "说"是"的成本变了" — AI 时代如何决策什么才是真正的"小改动" 🧠

| 来源 | GitHub Blog Engineering |
|:-----|:-----------------------|
| 日期 | 2026-07-17 |
| 链接 | [The cost of saying yes has changed](https://github.blog/engineering/the-cost-of-saying-yes-has-changed/) |
| 作者 | Dalia Abuadas（GitHub Copilot Agent Control Plane 团队） |

**核心论点**：AI 时代，写代码的成本降了，但**拥有代码的成本没降**。因此决策方式需要改变。

### 关键洞察

| 维度 | 传统直觉 | AI 时代新做法 |
|:-----|:---------|:--------------|
| **争议处理** | 花 40 分钟讨论"这个改动大不大" | 让 Agent 30 分钟出一版 probe patch，看真实 diff |
| **评估方式** | 凭感觉说"这涉及范围蔓延" | 从产出物审：改了几个文件？可测试吗？破坏了抽象吗？ |
| **决策时机** | 实现之前做范围管理 | 把部分范围管理移到** review 阶段** |
| **成本构成** | 写代码最贵 → 所以保护实现时间 | **理解+审查+拥有**最贵 → 代码只是探针 |

### 框架：三类改动的判别标准

```
      便宜（可以试试）    ⇔   贵（无论代码多小都慎重）
  +-----------------+         +-----------------+
  | 已有字段加展示   |         | 改授权行为       |
  | 改好测试的 helper |         | 改数据保留语义   |
  | 加只读信息展示   |         | 碰隐私/计费/合规  |
  | 加 feature flag  |         | 改产品契约       |
  | 已有抽象框架内   |         | 创建新支持负担   |
  +-----------------+         +-----------------+
```

**让 Agent 产出 probe patch 的四条约束**：
1. 最小可能 patch
2. 保持在已有 feature flag 后面
3. 不改 public contract
4. 加/更新测试 + 列出所有改动文件 + 标记风险点

### 价值说明

一篇**实操性极强的工程管理框架文章**，作者从 Copilot Agent 控制面团队视角提出：
- **AI 时代工程师的新关键技能**不是"是/否"，而是"快速定价不确定性"
- 给出了可操作的决策流程：**先发 probe patch → 从证据而非直觉判断 → 再决定是否合入**
- 与用户（技术决策者）每日面对的 scope creep / feature request 决策高度相关

## 2️⃣ Cursor in Slack: 多仓库环境 + 跨频道工作流 + 执行前分享计划 🔗

| 来源 | Cursor Changelog |
|:-----|:-----------------|
| 日期 | 2026-07-17 |
| 链接 | [Cursor Changelog](https://www.cursor.com/changelog) |
| 版本 | —（7月17日更新） |

### 新增功能

| 功能 | 说明 |
|:----|:-----|
| **计划先行** | Cursor 在 Slack 中先输出计划再执行，用户在早期可介入/调整方向 |
| **状态更新** | 执行过程中实时更新状态，每个步骤可见 |
| **多仓库环境** | 可从 Slack 指定 multi-repo 环境（前后端+共享库），Cursor 自动选择正确的仓库上下文 |
| **仓库切换** | 中途需要不同仓库时，弹出"Switch repository"按钮，切换后断点续传 |
| **跨频道工作流** | 可在多个 Slack 频道/线程中读取上下文，把结果发回原始频道 |
| **UI 精简** | 内联按钮→紧凑 footer 链接，PR/artifacts/表格渲染更干净 |

### 价值说明

Cursor 从 IDE 插件→**团队协作层**的跃迁信号：
- **多仓库环境**是实际工程组织中的刚需（前端/后端/共享库分离），Cursor 这是第一次原生支持
- **跨频道工作流**意味着 Agent 可以嵌入团队日常沟通流，不只是单用户交互
- "show plan first"模式与 GitHub Blog 的 probe-first 思路同构——先暴露信息再执行，降低协作摩擦
- 对于管理多人、多仓库团队的架构/研发 Leader，这一更新意义重大：**团队协作 Agent 不再是独立工具，而是 Slack 中的一等公民**

## 3️⃣ GitHub Copilot Code Review 定制化 + Code Scanning AI 检测上 PR 🔐

### 3a. Copilot Code Review 定制化（Jul 17）

| 来源 | GitHub Changelog |
|:-----|:-----------------|
| 日期 | 2026-07-17 |
| 链接 | [Copilot code review: Customization and configurability improvements](https://github.blog/changelog/) |

**功能**：Copilot Code Review 新增可定制化和可配置能力，允许团队调整 review 的严格程度/聚焦方向。

**价值**：与上周 (Jul 10) "Better tools made Copilot code review worse" 文章形成闭环——工具指令需要匹配场景，新的定制化能力让团队可以按项目风险级别设置 review 策略。

### 3b. Code Scanning AI 安全检测 + Agentic Autofix（Jul 10-14）

| 来源 | GitHub Changelog |
|:-----|:-----------------|
| 日期 | 2026-07-14 (release) + 2026-07-10 (public preview) |
| 链接 | [Agentic autofix for code scanning alerts in public preview](https://github.blog/changelog/2026/07/10/agentic-autofix-for-code-scanning-alerts-in-public-preview/) + [Code scanning shows AI security detections](https://github.blog/changelog/2026/07/14/code-scanning-shows-ai-security-detections-on-pull-requests/) |

**功能链完整时间线**：
1. **Jul 10**: Agentic Autofix 进入 public preview — Code Scanning 发现的告警可由 Agent 自动生成修复
2. **Jul 10**: CodeQL 2.26.0 新增 Kotlin 2.4.0 支持和 AI prompt injection 检测
3. **Jul 14**: AI 安全检测结果直接显示在 PR 上（code scanning shows AI security detections on pull requests）

**价值**：
- **从 detect → fix → review 的闭环打通**：以前只在 CI 中扫出告警，现在 Agent 可自动修复，修复结果在 PR 上可见
- 对于服务器固件/嵌入式等安全敏感场景，DevSecOps 自动化程度显著提升
- AI prompt injection 检测新增（CodeQL 2.26.0）说明安全检测面在扩大
