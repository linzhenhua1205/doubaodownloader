## 1. 🏗️ 大规模分布式训练并行策略

### 1.1 Mpipe: 多模态 LLM 训练的调度代数系统（重点 ⭐⭐）

- **作者**: Chong Li, Zhengdao Yu, Nelson Lossing, Thibaut Tachon, Pierre Leca, Etienne Filhol, Yujie Yuan, Chong Bao, Teng Su
- **来源**: arXiv:2607.03229 (cs.DC), 提交 2026-07-03（Tue 新刊区）
- **核心问题**: 多模态大模型(MLLM)训练相比纯 decoder-only LLM 训练 MFU 显著更低——异构的模态编码器（视觉/音频等）在 pipeline 调度中难以与 LLM backbone 高效交错
- **核心技术: HyperParallel-Mpipe**:
  1. **Schedule algebra**: 从紧凑的 schedule 规范推导具体的运行时行为——允许系统化搜索最优 schedule
  2. **Transpose**: 一种多模态感知的异构并行 schedule——将模态编码器计算映射到 pipeline 中本应空闲的区域（即"转置"了计算的时间槽）
- **关键数据**（Ascend 910C NPU 集群）:
  - 小规模环境: **2.70×** 加速
  - 512 卡大规模环境: **1.21×** 加速
- **意义**: MLLM 训练正成为超节点集群上的主要工作负载之一（从文本到多模态的转变）。Mpipe 的 **"schedule algebra"** 提供了一个形式化框架来描述和搜索多模态训练的最优 pipeline schedule——这与 MoP（07-07 跟踪）的"人工编排并行策略"形成对比，后者偏重静态设计，前者追求形式化搜索。Ascend 910C 的实现表明其与国产 AI 芯片生态的兼容性

## 2. 🧠 Speculative Decoding

### 2.1 SPORK: 自推测分叉加速 Agent 推理（重点 ⭐⭐🔥）

- **作者**: Huajun Bai, Weiwei Lv, Huichuan Zheng, Youyou Lu, Jiwu Shu
- **来源**: arXiv:2607.03333 (cs.DC, cs.AI, cs.LG), 提交 2026-07-03（Tue 新刊）
- **核心问题**: LLM Agent 的 Thought-Action-Observation 循环中，模型推理后发出 tool call，然后 GPU 空闲等待结果返回——这个等待占 **16-37%** 的 wall time（本文实测）或 **35-61%**（先前报道）
- **关键洞察**: 模型本身可以作为预测器——在生成开始时 fork 的 probe 可预测 Qwen3-32B 即将调用的 tool 名，准确率达 **74.6-99.6%**
- **核心技术: SPORK**:
  1. **Prefix-cache fork**: 复用前缀缓存降低 probe 开销
  2. **Confidence gate**: 过滤误预测
  3. **Partial-token accept**: 被拒绝的 probe 退化为 speculative decoding drafts
  4. **Cost model**: 推测何时 break-even
  5. **拒绝时退回串行执行**，零正确性损失
- **关键数据**:
  - GAIA P95 **降低 18%**（131.9→108.1 秒）
  - 模型大小 4B-32B、dense/MoE 均有效
  - 任务精度在基线 **1pp 以内**或更优
  - 部署为薄控制器，**无需重训练/辅助模型/离线 trace**
- **意义**: **SPORK 是 Speculative Decoding 在 Agent 场景的自然演化**。传统 SD 做"token 级推测"——用草稿模型预测未来 token；SPORK 做"function call 级推测"——用主模型自身预测未来 tool call。这种"self-speculation"思路与 Lynx（07-07 跟踪）的"自推测 KV 传输"形成更广泛的范式：**自推测的核心模式是"用模型自身的一部分作为预言机"**。开源代码的提供加速了落地

## 4. 💾 KV Cache 优化

### 4.1 PEEK: 队列感知预取 KV Cache 管理（重点 ⭐⭐🔥）

- **作者**: Bing Xie, Zhipeng Wang, Masahiro Tanaka, Zheng Zhen
- **来源**: arXiv:2607.02525 (cs.DC, cs.AI), 提交 2026-05-10（Tue 新刊区曝光）
- **核心问题**: 现有 KV Cache 管理系统只考虑**在服务中的请求**，忽略了 pending 队列中等待请求的 KV 共享潜力。pending 请求之间有大量前缀共享模式，但现有引擎不暴露这一信息
- **核心技术: PEEK**:
  1. **增量 radix tree**: 在 pending 队列上维护，暴露**前缀共享簇**
  2. **双遍历匹配**: 将树与引擎的前缀缓存匹配，为每个等待请求生成最长前缀匹配
  3. **簇先驱优先准入**: 让共享簇的第一个请求先执行，兄弟请求继承缓存的前缀
  4. **协同设计 eviction hook**: 保护队列中请求的祖先 block 不被驱逐
  5. **多车道 stride 调度器**: 防止饥饿
- **关键数据**（SGLang 和 vLLM，5 个 workload，4×H100 DP=2 TP=2）:
  - Cache hit: SGLang **3.0×** / vLLM **2.6×**
  - TTFT: **7.9× / 7.1×**
  - 端到端: **6.7× / 5.5×**
  - 吞吐: **3.6× / 4.5×**
  - 无前缀共享结构时，噪声水平匹敌基线
- **意义**: **PEEK 的核心创新在于"将 KV Cache 管理的视野从当前请求扩展到 pending 队列"**。之前的工作（如 SGLang 的 radix attention）只在引擎内部做已到达请求的前缀缓存，而 PEEK 在更早的阶段（pending 队列）就识别并利用前缀共享。这种"跨请求的协同缓存准入"思路与之前所有 cache eviction 工作正交

### 4.2 KVpop: 预测型在线 KV 剪枝（重点 ⭐⭐）

- **作者**: Lukas Hauzenberger, Niklas Schmidinger, Anamaria-Roberta Hartl, David Stap, Thomas Schmied, Sebastian Böck, Günter Klambauer, Sepp Hochreiter
- **来源**: arXiv:2607.05061 (cs.LG), 提交 2026-07-06（Mon 新刊）
- **核心问题**: 现有 KV eviction 方法依赖静态启发式或代理分数，难跟踪未来 token 效用变化，导致脆弱的驱逐决策
- **核心技术: KVpop**:
  1. **Future-attention 监督训练**: 训练 scorer 直接对 keep-or-drop 做二分类，监督信号是**未来注意力**（高效计算，不物化完整 attention map）
  2. **延迟记忆型 scorer**: 延迟固定步数再评分——利用近未来上下文做出更明智决策——这是 learned eviction 中的独特设计
- **关键数据**（AIME/HMMT 数学推理）:
  - Qwen3-4B @75% KV 压缩: **保留 98%** full-attention 性能
  - @88% 压缩: **保留 97%**
  - Qwen3-8B 结果更强，接近 full-attention 性能
  - 一致优于 established eviction baselines
- **意义**: KVpop 的 **"future-attention as supervision"** 是对现有 heuristic- and proxy-based eviction 的范式级替代。其"延迟评判"设计（推迟固定步数再打分）对在线推理场景具有实用价值。与 PEEK（4.1）形成对比：PEEK 从 pending 队列角度优化 KV 缓存准入，KVpop 从 eviction 角度优化 KV 缓存驱逐

### 4.3 KV Cache 管理全景综述——四轴分类 30+ 系统（重点 ⭐）

- **作者**: Jie Li, Tongyang Wang, Yong Chen
- **来源**: arXiv:2607.02574 (cs.DC, cs.AI, cs.LG), 提交 2026-06-30
- **核心贡献**:
  1. **四轴分类**: locality（本地/远程）、lifetime（请求内/跨请求）、ownership（独占/共享）、substrate（DRAM/NVM/CXL/网络）
  2. **五种架构原型**: local-paged、disaggregated-pipeline、shared-store、memory-pool、hybrid-tier
  3. **核心发现**: 在 workload 和硬件固定后，**ownership 解释了分布式系统间的大部分设计差异**
  4. **七个缺失的 KV 度量**: 与开放问题（容错、隔离、分层 eviction、Speculative Decoding、MoE 服务、共享缓存语义）对应
- **意义**: 这是第一个系统化覆盖 **30+ KV Cache 管理系统**的综述。虽然我们跟踪已覆盖其中大部分，但其四轴分类法和"缺失度量"清单对判断未来 KV Cache 研究的空白领域提供了结构化参考

## 5. 🔄 通信调度

### 5.1 Pici: 自适应空间高效稀疏集合通信（重点 ⭐⭐🔥 — SC 2026）

- **作者**: Lannie Dalton Hough, Emir Gencer, Hoffmann Muki, Abhinav Bhatele
- **来源**: arXiv:2607.04676 (cs.DC), 提交 2026-07-06（Mon 新刊），**SC 2026**
- **核心问题**: NCCL 等主流通信库只优化密集数据。稀疏数据下发送零值是浪费带宽，但显式处理稀疏引入格式转换开销和 reduction 期间密化的挑战
- **核心技术: Pici**:
  1. **Pici bitvector 格式**: 专为低开销、快压缩设计，在中等稀疏度下高效
  2. **自适应表示转换**: 集合操作过程中根据数据稀疏度动态切换表示形式（密集↔稀疏）
  3. **覆盖三个 collectives**: all-gather, reduce-scatter, all-reduce
- **关键数据**（@99% 稀疏度 vs NCCL）:
  - all-gather: **5.25×**
  - reduce-scatter: **2.5×**
  - all-reduce: **2.66×**
- **意义**: **SC 2026 接收确认了其高性能计算社区的贡献**。稀疏通信在 ML 训练中越来越重要（梯度稀疏化、MoE 路由、稀疏注意力）。Pici 与 SCAPE（07-07 跟踪）形成互补——SCAPE 是从优化器层面做梯度稀疏化来减少通信量，Pici 是从通信库层面做集合操作时利用稀疏性加速

### 5.2 CAP: 通信感知放置与剪枝——MoE 推理通信优化（重点 ⭐⭐）

- **作者**: Xiao Shi, Yingying Sun, Jiangsu Du, Zhiguang Chen, Yutong Lu
- **来源**: arXiv:2607.05116 (cs.DC), 提交 2026-07-06（Mon 新刊）
- **核心问题**: MoE 模型扩展到数百 expert 后，放置和剪枝决策会直接影响通信量，影响跨 GPU/节点推理性能
- **核心技术: CAP**:
  1. **共激活驱动放置**: 将频繁共激活的 expert 分组到同一设备——减少跨设备/节点通信
  2. **通信-计算权衡调整**: 生成不同计算负载和通信量的放置方案
  3. **通信感知 expert 剪枝**: 选择性移除路由目标以减少通信，精度损失有限
- **关键数据**:
  - 单节点/多节点实验中，吞吐提升 **1.23-1.86×** vs DeepSeek EPLB 和 vLLM 顺序放置
  - 在相同目标加速下保留更好的模型精度
- **意义**: CAP 与 ELDR（07-02 跟踪）形成有趣的对照——ELDR 是从路由角度（将请求路由到专家缓存最近的 worker），CAP 是从放置角度（将共激活 expert 就近放置）。**两者共同指向 MoE 推理的核心问题不是计算而是通信**

## 6. 📦 Checkpoint 容错 / 弹性训练

### 6.1 ETC: 无检查点的直接模型状态迁移——弹性训练（重点 ⭐⭐🔥）

- **作者**: Weijian Liu, Mingzhen Li, Rui Kang, Chen Sun, Guangming Tan, Weile Jia
- **来源**: arXiv:2607.04749 (cs.DC), 提交 2026-07-06（Mon 新刊）
- **核心问题**: LLM 训练需要适应集群动态资源变化（被动抢占、主动缩放）。改变混合并行配置时需要跨设备集迁移状态。现有方案依赖 checkpoint 持久化→恢复——需要所有 GPU 在迁移期间停止，且涉及多层内存层次的数据移动
- **核心技术: ETC（Elastic Training with Checkpoint-free migration）**:
  1. **状态局部性利用**: 最小化跨 GPU 数据移动——**P2P 直传替代存储持久化**
  2. **通信合并消除节点碎片**
- **关键数据**（集成 Megatron-LM）:
  - 迁移开销降低 **2.33-6.37×** vs checkpoint 方案
  - 覆盖多种并行配置
- **意义**: **ETC 与 DeadPool（07-07 跟踪）形成了"故障恢复"和"弹性训练"的完整组合**。DeadPool 解决的是"节点故障→热插拔恢复"（零开销+<40s），ETC 解决的是"资源配置改变→无缝迁移"（无 checkpoint 直传 2.33-6.37×）。两者都体现了**"不要停所有 GPU 来做迁移/恢复"**的共同设计哲学。对万卡集群而言，弹性训练（ETC 的分配变更）和故障容错（DeadPool 的永久故障）是两大关键操作
