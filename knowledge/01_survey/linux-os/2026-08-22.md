## CXL 与内存管理（服务器基线重点）

- **LWN/What's brewing in CXL**（05-19，Jonathan Corbet，LSFMM+BPF 2026 报告）: Dan Williams 开场直言 CXL "has been making memory-management problems worse since 2021"。核心现状：① CXL 内存延迟劣于远端 NUMA、高度可配置（interleave 可改善性能）；② 内核与系统固件争夺 CXL 内存控制权；③ 热插拔特性导致"部分系统 RAM 可随时消失"；④ 内核按 ACPI "code-first" 策略跟踪厂商偏离标准的硬件并文档化，向厂商喊话"有人这样搞坏了，请你也这样搞"；⑤ **错误处理**：CXL 协议错误经 PCIe 内部错误上报但走旁路通道，且 CXL 代码在错误处理路径主动引入 kernel panic（固件反正会 panic 整机）；⑥ **加速器支持（memory-to-memory 压缩等）接近落地**；⑦ vfio-cxl 可把 CXL 加速器导出给虚拟机；⑧ 动态容量（dynamic capacity）：买 DIMM 拉线共享内存给多主机，内核计划用 **device DAX** 作为用户态接口，需与 guest_memfd 集成；⑨ 明确无解/未做：**错误隔离**（CXL host bridge 丢失→TB 级内存消失，系统难以幸存）、**peer-to-peer 操作**尚无工作。来源: https://lwn.net/Articles/1072858/ 📎 raw: tmp/raw/2026-08-22/lwn-cxl-1072858.md
- **LWN/128-Bit page tables for Arm**（08-13）: Arm 128 位页表方案进入 LWN 报道视野（索引页收录），面向超大规模内存寻址——与 CXL 大内存池化、万卡集群内存容量扩展需求直接相关。来源: https://lwn.net/Articles/1088125/（403 订阅墙，索引页验证）
- **LWN/Automatic mTHP creation in 7.2**（06-11）: 7.2 内核引入自动多尺寸 THP（mTHP）创建——匿名页大页化自动策略，服务器内存密集负载（数据库/缓存）受益面扩大。来源: https://lwn.net/Articles/1077208/
- **LWN/Two LLM-assisted memory-management patch sets**（07-02）: 两套 LLM 辅助的内存管理补丁集进入内核社区讨论——LLM 开始参与内核内存子系统开发（与 07-21 "LLM in kernel community" 讨论呼应）。来源: https://lwn.net/Articles/1080162/

## 追踪信号小结

- **内核 7.x 时代版本节奏稳定**: 7.2 于 08-16 发布、7.3 merge window 08-20 开启，约 2.5 个月/版本；LTS 六线（6.18/6.12/6.6/6.1/5.15/5.10）08-19 同步批量更新——服务器 OS 基线选择面完整（7.x 新特性 + 6.12 LTS 保守线双轨并行，与 08-21 判断一致）
- **CXL 内存进入"工程现实期"**: Dan Williams LSFMM 报告勾勒出 CXL 从"卖点"到"内核负担"的真实状态——错误处理靠 panic、动态容量接口未定型（device DAX + guest_memfd 集成中）、错误隔离无解（host bridge 丢失即 TB 级内存消失）。对服务器厂商：CXL 内存池化方案的 RAS 设计（错误域划分、热插拔预案）必须前置，不能等内核"完全成熟"
- **K8s 1.37 发布延迟信号**: 按 3 次/年节奏 8 月下旬应为 1.37 发布窗口，但官方 releases 页仍标 upcoming——叠加 08-21 SUSE 容器栈安全修复密集，K8s 侧"发布静默期 + 安全维护期"并行的状态延续，升级规划应锚定 1.36.x 而非等待 1.37
- **LLM 进入内核开发流程**: "LLM-assisted memory-management patch sets"（07-02）与 "LLM in kernel community" 讨论（07-21）——LLM 辅助内核补丁从试验走向社区议题，与 tech 组 Agent 主线呼应，可作为 Linux 生态"AI 化开发"观察点
