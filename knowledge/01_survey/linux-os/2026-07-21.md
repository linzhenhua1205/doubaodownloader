## 🔥 内核社区重磅

### 1️⃣ 🆕 **Linus Torvalds：LLM 在内核开发中的角色"强烈争议"** 🔥

- **来源**: LWN.net (Jul 21 13:48 UTC, corbet) — *[$] Debating the role of large language models in the kernel community*
- **版本/状态**: **内核社区正在激烈辩论** — Linus Torvalds 本周发出措辞强硬的信函
- **核心议题**:

| 维度 | 说明 |
|:-----|:------|
| 🔴 **LLM 署名要求** | 补丁中是否必须标注 `Assisted-by: LLM`？上周 7.1.4 中已出现多种标注格式（`LOLLM`、`Codex:gpt-5.5`、`Antigravity:gemini-3.5-flash` 等），标准尚未统一 |
| 🔴 **代码审查工具** | LLM 生成的代码如何审查？社区担心「AI 幻觉代码」逃避人类审查 |
| 🔴 **专有工具依赖** | Linus 强烈反对内核开发**依赖专有 LLM 工具**— 这与内核的 GPL/开源精神冲突 |
| 🟡 **伦理考量** | LLM 训练数据的版权问题、开发工作是否应归功于人类 |
| 🟡 **社区分化** | 部分维护者积极使用（如 Darrick J. Wong 用 LOLLM 找 XFS bug），部分强烈反对 |

- **背景**: 本周 7.1.4 的中已出现多个 `Assisted-by: <LLM名>` 标注，其中 **LOLLM（专门找 bug 的 LLM 工具）** 被 Darrick J. Wong 用于 XFS 代码审计找到 12+ 个真实 bug，但也引发了「AI 辅助工作是否应同等待遇」的争议
- **对服务器团队**: 🟡 **值得关注**
  - 内核 LLM 政策将影响服务器厂商的长期内核维护策略
  - 如果内核社区要求 `Assisted-by: LLM` 强制标注，Linux 发行版维护者可能需要建立新的合规流程
  - Linus 对**专有 LLM 工具**的态度可能影响 NVIDIA/AMD 等厂商的 GPU 驱动开发工具链

> 💡 **核心矛盾**: Linus 不反对 LLM 辅助开发，但**坚决反对内核依赖专有 LLM 工具**。这与内核社区「来自社区、回馈社区」的开源精神一致，但意味着依赖 GPT/Claude API 的辅助开发工具可能面临「不被认可」的风险。

### 5️⃣ 🆕 **Red Hat OpenShift AI MaaS 治理：双门访问控制模型** 🔐

- **来源**: Red Hat Blog (Jul 21) — *Models-as-a-Service (MaaS) governance*
- **核心设计**: Red Hat OpenShift AI 的 MaaS（模型即服务）引入双门访问控制：

```
请求 -> MaaS API Gateway -> [1. MaaSAuthPolicy: 准入] -> [2. MaaSSubscription: 配额] -> 推理服务器
```

- **关键概念**:
  - **MaaSSubscription**: 定义用户/组在时间窗口内的 Token 配额上限
  - **MaaSAuthPolicy**: 定义用户/组可调用的模型白名单
  - **双门分离设计**: 配额和准入独立演变，修改策略不影响配额配置
- **典型场景**: 数据科学团队持有 Premium 订阅（大配额）但仅限访问部分模型；ML 工程团队同一订阅但不同模型范围
- **对服务器团队**: 🟡 **趋势信号** — AI 推理服务治理正在向云原生模式演进，配额/策略/审计三大支柱逐渐标准化

## 🛠️ 容器安全

### 6️⃣ 🆕 **Red Hat AI：AI Agent 6 层安全框架** 🏗️

- **来源**: Red Hat Blog (Jul 21) — *Why prompt-level guardrails aren't enough: The platform security layers production agents need*
- **作者**: Richard Naszcyniec, Joshua Wilson
- **核心论点**: Prompt 级防护（Instruct/System Prompt）**不能作为安全边界** — 攻击者可通过 Prompt Injection 绕过
- **6 层安全框架**:

| 层 | 技术 | 解决什么问题 |
|:---|:-----|:-------------|
| 1️⃣ **身份** | **SPIFFE/SPIRE** 密码学身份 | 每个 Agent 拥有独立的短期 x509/JWT 身份凭证，消除共享凭据 |
| 2️⃣ **沙箱** | **Kata Containers**（独立内核隔离） | Agent 被攻破后无法逃逸到宿主机 |
| 3️⃣ **细粒度网络** | **OpenShell** 每进程网络策略 | 各进程仅能访问指定外部服务 |
| 4️⃣ **工具访问** | **MCP Gateway** OAuth2 代理 | 工具权限由基础设施控制，不依赖 Agent 推理 |
| 5️⃣ **推理边界** | **NVIDIA NeMo Guardrails + Trusty AI** | 在模型输出变成行为前拦截幻觉/不合规输出 |
| 6️⃣ **预生产扫描** | **NVIDIA Garak** 对抗性漏洞扫描 | CI/CD 管道中自动红队测试 Agent |

- **关键发现**: Garak 测试表明，仅沙箱隔离就能将凭据泄露从 **67% 成功率降至 0** 🔴
- **对服务器团队**: 🟡 **趋势信号** — AI Agent 安全分层方案对服务器基础设施提出新的隔离和安全要求
