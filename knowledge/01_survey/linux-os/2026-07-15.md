### 2️⃣ 🆕 Two-node OpenShift with fencing — 边缘高可用深度方案 🔄

- **来源**: Red Hat Blog (Jul 15, Fröhlich/Lancaster)
- **版本**: OpenShift 4.22 中 **GA**
- **架构**: 真正 2 节点方案（非 2+1 arbiter），仅支持 x86 裸金属
- **核心机制**: Corosync + Pacemaker + BMC RedFish API 实现 fencing
- **流程图**:
  - 节点故障 → etcd 失去 quorum → API 不可用 → Corosync 声明失败
  - **Fencing**: Pacemaker 通过 BMC 调用 RedFish `ForceRestart` → 强制重启故障节点
  - 幸存节点 200 OK 确认后 → 重配 etcd 为单节点 → 恢复 quorum → 重启工作负载
  - 故障节点恢复上线 → etcd learner 阶段重新同步 → 恢复 2 节点集群
- **极端条件**: 双节点同时掉电需人工干预 SSH
- **存储伙伴**: LINBIT(DRBD), Arctera InfoScale, IBM Storage Fusion(Ceph)
- **磁盘要求**: SSD 及以上（etc learner 阶段 I/O 密集）
- **对服务器团队**:
  - 🟢 **参考价值** — 如果你有数据中心内 2 节点 HA 集群需求，fencing+RedFish 方案可借鉴
  - OpenShift 的 BMC 集成思路对服务器 BMC 团队有参考意义

## 🔐 安全事件

### 5️⃣ 🆕 🔴 严重: 大量旧版 shim 仍被 Secure Boot 接受 — 持续安全风险 🛡️⚠️

- **来源**: LWN.net (Jul 15, corbet) — CMU CERT 公告
- **公告方**: CMU CERT Coordination Center (CERT/CC)
- **问题**: 大量存在漏洞的 **shim** 版本从未被添加到 SBAT 吊销列表
- **攻击场景**:
  - 攻击者获得管理员权限或能修改启动过程
  - 使用漏洞 shim 引导加载器 **绕过 Secure Boot** 保护
  - 在 OS 加载前执行任意代码 → 持久化平台入侵
  - 可加载未签名/恶意内核组件 → 重启后仍存活，甚至重装系统后依然存在
- **影响范围**: 所有使用 shim 的 Linux 发行版（几乎所有主流发行版）
- **缓解**: 最新更新已通过 **LVFS** 和 Windows Update 开始部署吊销
- **对服务器团队**:
  - 🔴 **需跟进** — 服务器 Secure Boot 合规环境需确认是否已应用最新 SBAT 吊销列表
  - 建议: 检查 `/sys/firmware/efi/efivars/SbatLevel-*` 确认 SBAT 版本
  - 关注各发行版安全公告中的 shim 更新
