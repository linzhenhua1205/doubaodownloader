### 9.1 🟢 AIC F2032-01-G6 JBOF — 面向Vera Rubin CMX的KV Cache专用服务器（ServeTheHome, 2026-07-11）

**URL**: https://www.servethehome.com/aic-gets-flashy-with-32-ssd-bay-jbof-server-for-key-value-caching/

**核心内容**: AIC发布F2032-01-G6，**2U 32盘位全闪PCIe Gen6 JBOF**，专为NVIDIA Vera Rubin **CMX (Context Memory Storage)** KV缓存平台设计。这是AI推理集群中一种**新服务器形态**——不再是通用存储服务器，而是KV Cache专用加速存储节点。

| 关键指标 | 数值 |
|:---------|:-----|
| 外形 | **2U** JBOF |
| SSD数量/规格 | **32× E3.S/E3.L** (PCIe Gen6) |

| PCIe交换芯片 | Broadcom **PEX90144** (144 lanes, PCIe Gen6) |

| SSD连线拓扑 | **x2 lanes/SSD** (PCIe Gen6带宽弥补通道数不足) |
| 高可用 | 双节点独立PSU，任一DPU故障不宕机 |
| 形态定位 | KV Cache → Vera Rubin 推理加速 |

**关键洞察**:
- **KV Cache专用JBOF是AI推理集群的新标准组件**——NV CMX平台将其定义为Vera Rubin rack标配

**行业意义**: ⭐⭐⭐⭐⭐ — 证明AI推理正从"算力瓶颈"转向"**KV Cache存储瓶颈**"，催生专用的JBOF服务器新形态。NV蓝图的CMX将成为超节点标配

### 11.2 🟢 arXiv — BrownoutMoE: 结构感知Expert分组优化Web服务推理（2607.04164, 2026-07-05）

**来源**: arXiv:2607.04164, 2026-07-05
**作者**: Yi Ding, Minxian Xu, Zhengxin Fang, Kejiang Ye, Chengzhong Xu
**URL**: https://arxiv.org/abs/2607.04164

**核心方法**: 提出**BrownoutMoE**框架，解决MoE推理中hot/cold expert高度不均衡的问题。核心洞察——现有优化（调度、通信重叠、kernel fusion）保留原始expert组织，不解决**结构性低效**。BrownoutMoE将expert分组（Grouping）形式化为RL学习问题，自动发现最小化精度损失的grouping策略，并通过grouping-consistent distillation产出可直接部署的模型。

**关键发现**:
- MoE推理中少数hot experts处理大多数路由token，大量cold experts几乎不激活 → GPU并行度浪费
- RL自动发现的grouping策略具有跨任务可迁移性
- Grouping-consistent distillation确保兼容标准推理管线

**性能数据**:
- **精度损失降低 71.4%**（vs 同等压缩baseline）
- **吞吐提升 2.24×**
- 在bursty web服务负载下有效

**硬件影响**: ⭐⭐⭐⭐ 证明**expert组织结构本身是系统瓶颈**——即使用最先进runtime优化，保留原始expert组织的部署方式在结构上是低效的。对GPU显存局部性和expert调度策略有新的设计启示——未来GPU/SmartNIC应在硬件层支持灵活的expert分组模式

### 11.3 🟢 arXiv — MAESTRO: 马尔可夫链驱动的跨层Expert剪枝（2607.08601, 2026-07-09）

**来源**: arXiv:2607.08601, 2026-07-09
**作者**: Palaash Goel, Ayush Maheshwari, Tanmoy Chakraborty
**URL**: https://arxiv.org/abs/2607.08601

**核心方法**: 提出**MAESTRO**（Markov-chain Approximated Expert Sparsification via Transition-based ROuting），将自回归expert激活轨迹建模为**遍历马尔可夫链**，其平稳分布编码**跨层依赖**，从而获得全局感知的expert重要性评估。与现有基于局部启发式（如activation count、gate score）的剪枝方法不同，MAESTRO首次在剪枝决策中显式建模了**层间路由依赖性**——一个专家在某层的"重要性"应被其他层中与其激活序列耦合的专家影响。

**关键发现**:
- 现有基于局部启发式的剪枝方法"盲目"于MoE路由的相互依赖性（interdependent nature）
- 跨层依赖建模使剪枝后的模型在异构任务上泛化更一致

**性能数据**:
- **50%严格压缩率**下，平均性能保持比SOTA基线高 **10.61%**
- 跨任务方差显著低于SOTA基线
- 在**Safety、Bias、Ethics**等五个不同领域验证

**硬件影响**: ⭐⭐⭐⭐ 提出全新视角：**Expert剪枝不仅是模型压缩问题，更是路由拓扑结构优化问题**——这暗示硬件在支持剪枝后的dynamic expert activation时应考虑跨层路由的拓扑特性。为稀疏MoE在边缘部署提供理论基础

### 11.4 🟢 arXiv — ELDR: PD分离MoE服务中的Expert局部感知路由（2607.00466, 2026-07-01）

**来源**: arXiv:2607.00466, 2026-07-01
**作者**: Sangjin Choi, Sukmin Cho, Yifan Xiong, Ziyue Yang, Youngjin Kwon, Peng Cheng
**URL**: https://arxiv.org/abs/2607.00466

**核心方法**: 提出**ELDR**（Expert-Locality-Aware Decode Routing），专门解决PD（Prefill-Decode）分离架构中MoE模型的decode路由问题。现有路由只平衡负载，但MoE中同等负载的worker可能因batch激活的expert集合不同而延迟差异巨大。ELDR从request的prefill expert激活构建**expert签名**预测decode阶段的激活模式，离线用Balanced K-means将签名空间分区，在线用**局部性波段路由**（locality-band routing）将request发送到与其签名最匹配的least-loaded worker。

**创新组件**：
- Expert签名 + 签名缓存（与KV cache共同索引）
- 离线balanced K-means分区
- 在线locality-band路由

**性能数据**:
- 在vLLM实现中，跨3个MoE模型+2个工作负载，**中位数TPOT降低 5.9%~13.9%**
- 在**40 GPU**部署中验证
- 模型输出不变（路由仅为placement决策）

**硬件影响**: ⭐⭐⭐⭐ 揭示MoE推理中一个被忽视的瓶颈来源——**同一负载下不同expert组合导致不等效延迟**。对PD分离架构中decode worker的异构性管理有直接指导意义：宽EP部署时，即使是均匀负载也会因expert locality差异而产生高延迟抖动

### 11.5 🟢 arXiv — Gimbal: MoE LLM服务中的协同跨层调度（2606.15177, 2026-06-13）

**来源**: arXiv:2606.15177, 2026-06-13
**作者**: Yifan Sun, Zhexiang Zhang, Jiantong Jiang, Gholamreza Haffari, Minxian Xu, Feng Liu, Rajkumar Buyya, Adel N. Toosi
**URL**: https://arxiv.org/abs/2606.15177

**核心方法**: 提出**Gimbal**协同跨层调度系统。现有MoE服务系统将前端调度和后端expert平衡隔离决策——前端用粗粒度request计数器路由，后端用aggregate expert activation计数平衡。Gimbal统一两者：

1. **前端细粒度DP-engine调度器**：使用在线backend压力信号（KV cache使用量、剩余prefill工作量、队列压力、MoE expert压力）将request分流远离过载engine
2. **engine内prefill感知队列排序策略**（带aging机制）减少HOL blocking
3. **后端expert负载均衡**：基于MINLP启发式，联合考虑expert负载、source感知通信和迁移稳定性

**性能数据**:
- **TTFT降低 42.9%** · **TPOT降低 33.3%**（vs vLLM）
- 高负载request吞吐提升 **3.0%**
- 跨不同MoE模型验证

**硬件影响**: ⭐⭐⭐⭐ 证明**MoE服务系统的前端调度与后端expert放置必须协同设计**——独立的expert负载均衡不足以解决MoE推理的性能抖动。硬件层面的fabric调度器应考虑将MoE的路由局部性信号暴露给上层调度

### 11.6 🟢 arXiv — Does Mixture-of-Experts Actually Help Inference on Consumer and Edge Hardware?（2606.21428, 2026-06-19, v3更新2026-07-09）

**来源**: arXiv:2606.21428, 2026-06-19（v3: 2026-07-09）
**作者**: Alfarizy Alfarizy, Hung Truong Thanh Nguyen, René Richard, Roozbeh Razavi-Far, Hung Cao
**URL**: https://arxiv.org/abs/2606.21428

**核心方法**: 实证研究——MoE在消费级和边缘硬件上是否真的比dense模型更快更便宜？在Apple M2 Pro和NVIDIA Jetson Orin Nano 8GB上对比OLMoE-1B-7B（1.3B active/6.9B total）与三个dense基线。通过patch llama.cpp进行逐节点解码图计时。

**关键发现**:
- MoE的active-parameter FLOP优势**在现实中部分丧失**：
  - 笔记本（M2 Pro）：**~10%落后**于同active参数的Llama-3.2-1B
  - 边缘设备（Jetson Orin Nano）：**~31%落后**，每token能耗 **2.1×**
  - 峰值内存接近8GB天花板
- 逐节点计时显示：**路由只占MoE block计算的<9%**（clean edge backend上）
- 性能差距的根本原因是**总参数内存占用**+**expert dispatch**+**KV cache压力**，而非路由本身

**核心结论**: 在带宽受限的硬件上，**推理成本追踪的是总参数而非活跃参数**——稀疏激活不能买回带宽限制设备的短板

**性能数据**:
| 指标 | MoE (OLMoE-1B-7B) vs Llama-3.2-1B (同active参数量) |
|:-----|:--------------------------------------------------|
| M2 Pro吞吐 | **~10%** lower |
| Jetson Orin Nano吞吐 | **~31%** lower |
| 每token能耗(Jetson) | **2.1×** higher |
| 峰值内存 | 8GB ceiling hit |
| 路由开销占比 | <9% of MoE block |

**硬件影响**: ⭐⭐⭐⭐⭐ **对MoE部署假说的关键纠偏**——"MoE适合资源受限设备"的常识需要修正：在带宽受限硬件上，**总参数量决定实际性能**而非活跃参数量。这对未来边缘AI芯片的架构选择有直接影响——如果目标是边缘部署，设计专用dense模型可能比MoE更优

## §12 附录：Speculative Decoding专题

### 12.1 🟢 arXiv — DeLS-Spec: Decoupled Long-Short Contexts for Parallel Speculative Drafting（2607.07409, 2026-07-08）

**来源**: arXiv:2607.07409, 2026-07-08
**作者**: Hong-Kai Zheng, Piji Li
**URL**: https://arxiv.org/abs/2607.07409

**核心方法**: 提出**DeLS-Spec**，将并行block推测解码中的长/短上下文解耦。现有block-parallel方法（如DFlash）位置级预测缺乏块内因果条件化，而Domino/DSpark引入因果性但需从头训练drafter。DeLS-Spec将固定DFlash模型作为**长上下文专家**，引入轻量级local head作为**短上下文专家**——local head可独立用标准NTP目标训练，不需与target model或DFlash骨干联合训练。

**核心优势**:
- **极低训练成本**（language head级别，非完整drafter）
- **模块化**：local head不绑定特定DFlash checkpoint
- **即插即用**：可组合不同long-context专家

**性能数据**:
- 在Qwen3模型上（dense + MoE），**一致优于DFlash**的速度提升和平均接受长度
- 在math/code/dialogue三个benchmark上验证

**硬件影响**: ⭐⭐⭐ 模块化解耦long/short上下文推测解码——与之前tracked的EVICT（MoE-SD的自适应验证裁剪）互补，表明SD的模块化趋势

| 转换路径 | 适用场景 | 支持者 | 关键权衡 |
|:---------|:---------|:-------|:---------|
| 800V→48V→12V/1V | 侧车过渡期，兼容48V生态 | ST (Di Franco) | 最少架构颠覆，多一级转换 |

- AI加速器TDP冲向多kW级，TDC达**8,000A**，sub-1V核心电压

### 14.1 🟢 Cursor 3.11 — Side Chats + Conversation Search（Cursor Changelog, 2026-07-10）

**URL**: https://www.cursor.com/changelog

**核心功能发布**:
- **Side Chats**（边聊窗口）: 通过 `/side`、`/btw` 或 `+` 按钮打开侧边对话，可提问、探索想法、调查分支方向，**不影响主agent会话**。每个Side Chat是持久的完整agent会话，支持后续跟进和`@-mention`拉回主线程。默认只读模式（reading/searching/answering），适合做决策前的快速验证
- **Conversation Search**（会话搜索）: 在Agents Window中支持搜索agent transcript内容（Cmd+K），建立**本地搜索索引**，可扩展到数千条会话。单个会话内支持Cmd+F搜索，带匹配计数器和跳转
- **Redesigned Pickers**: 项目和仓库选择器重新设计——搜索按作用域（This Computer/Cloud/Remote Machine）区分，支持创建一个项目并同时绑定GitHub/GitLab/Azure DevOps无需离开选择器
- **Cloud Agent Hooks扩展**: 新增 `beforeSubmitPrompt`, `afterAgentResponse`, `afterAgentThought`, `stop`, `subagentStart` 等hooks，支持观察agent输出、控制subagent、构建自纠错循环

**行业意义**: ⭐⭐⭐ 产品精细化迭代——Side Chats解决"agent运行时不能查别的事"的痛点；Conversation Search解决了agent transcript不可检索的系统性缺陷

### 16.1 🔴 arXiv — "Who Needs DRAM? We Have Fiber"：光纤内存架构（2026-07-09）

**来源**: arXiv:2607.08407 (cs.AR) · 2026-07-09
**作者**: Hannah Atmer, Thiemo Voigt, Yuan Yao, Stefanos Kaxiras
**URL**: https://arxiv.org/abs/2607.08407

**核心概念**: 提出 **Fiber Memory** 架构——将超大规模数据中心中已有的光纤网络改造为**有源循环延迟线内存**，专门用于存储不可变数据（如LLM权重）。

**技术方案**: 数据并行光广播延迟线内存架构，整合以下技术：
- **空分复用多芯光纤 (MCF)**
- **无源光抽头放大接口 (passive optical tap-and-amplify)**
- **共封装光学 (CPO)** — 直接在GPU/加速器封装内连接光纤
- **区域全光中继 (regional all-optical regeneration)**

**关键性能数据**:

| 指标 | Fiber Memory | vs HBM3e 基线 |
|:----|:------------|:--------------|
| **冗余权重存储** | **消除**跨10,000个AI加速器的重复存储 | 每加速器各自存储 → 大量冗余 |
| **权重交付能耗** | 降低 **>70%** | HBM3e基线下为100% |
| **物理介质** | 已部署的多芯光纤 | 专用HBM DRAM |
| **应用场景** | LLM推理权重分发 | 通用HBM用途 |

**核心洞察**: LLM权重在推理过程中是**只读的（immutable）**，无需随机访问——这恰好匹配光延迟线的**只读+顺序+高带宽**特性。利用CPO将光信号直接从光纤接入加速器封装内，可取代大量的HBM DRAM用于权重存储。

**硬件影响**: ⭐⭐⭐⭐⭐ 如果这一架构能落地，将从根本上改变AI集群的内存层级：
1. **CPO从"网络互连"延伸到"内存层级"** — 光不仅是连接介质，更是存储介质
2. **HBM需求可能分化**：一部分被光纤内存替代（权重），高端HBM集中用于KV Cache和激活值
3. **对交换机CPO的启示**：CPO既然可以接光纤内存，就不只是网络连接功能

### 16.2 🟢 arXiv — CPO热漂移的软件预测调度层（2026-05-18）

**来源**: arXiv:2605.18612 (cs.AR) · 2026-05-18（v2: 2026-05-23）
**作者**: Chi Fei Chung
**URL**: https://arxiv.org/abs/2605.18612
**标题**: *Predictive Software Scheduling as an Early-Warning Hint Layer for Optical Engine Thermal Drift in Heterogeneous SoIC Packaging*

**背景**: 随着半导体工艺推进到 **A16 / 2nm节点**，TSMC **COUPE (Co-Packaged Optics Ultra Engine)** 架构中的CPO集成面临严峻的**热-光耦合**挑战。

**核心问题**: 

| 敏感参数 | 数值 | 后果 |
|:---------|:-----|:-----|
| MRM谐振波长偏差 | **±1.7nm** | 可量测的BER退化 |
| 温度波动范围 | 芯片级异构集成中的典型值 | 波长漂移超过容限 |
| PIC层位置 | SoIC封装中紧邻计算die | 受计算负载热量直接影响 |

**解决方案**: 
- 提出**预测性软件调度层**作为**早期预警提示层 (Early-Warning Hint Layer)**
- 在OS/调度器层面预判计算任务产生的热量分布
- 将热敏感的光学引擎操作**避开**大功率计算时段
- 将热预测提示传递给光学引擎做**预补偿**

**关键创新**:
1. 首次将CPO热漂移问题从**硬件补偿（加热器/TEC）**扩展到**软件调度协同**
2. 不需要额外硬件开销，纯软件层（调度器提示）
3. 与TSMC COUPE架构兼容——**面向量产CPO的热管理方案**

**硬件影响**: ⭐⭐⭐⭐ CPO从实验室到量产的关键瓶颈之一是**可靠性**——热漂移被系统性地指出并给出软件协同方案。这意味着：
1. CPO的可靠性问题**有可操作的解决路径**（不完全是硬件天花板）
2. 软件+硬件协同热管理将成为**CPO系统级设计标配**
3. TSMC COUPE客户的**系统集成壁垒**增加——需要OS/调度器层面的适配
