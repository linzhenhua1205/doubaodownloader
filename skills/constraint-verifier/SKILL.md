# 约束验证器（Constraint Verifier）

> **核心理念**：给 AI 的约束文件只是提示词层面的"软约束"——模型 **不会严格执行**，在注意力衰减、上下文偏移、模型版本变更等条件下随时可能失效。
>
> **五层融合**：基于 [AI 使用哲学文档](knowledge/04_person/ai-usage-philosophy.md) 的五层管道框架，
> 将 A-J 十类失效模式全部纳入可检测断言体系。本技能的核心任务是**将约束偏离定位到具体的失效类**，
> 以便精准修复和双环改进。

## 概述

对一份或多份 AI 产出（输出文本、代码、文档），检查其是否偏离了约定约束（AGENT.md、RULE.md、MEMORY.md、USER.md、skill 指令等），并按 A-J 十类失效模式归类。

```
输入：AI 产出 + 目标约束文件列表
 ↓
检测阶段1：逐条约束断言 vs 产出行为（原有三层架构）
检测阶段2：按五层管道和A-J分类归类偏离
检测阶段3：元层检查（可复现/成本/依赖/版本漂移）
 ↓
输出：验证报告（通过/不通过/警告 + 失效类别标签 + 修复建议）
```

## 约束检测的三层架构（扩展为五层全管道的失效分类）

### 失效分类与检测断言体系

每一条约束偏离都被归类到一个具体的失效类（A-J）。检测时从三个维度定位：

```
约束偏离证据
    ↓
定位到管层：L1信源 / L2注意 / L3知识 / L4推理 / L5输出 / LX元层
    ↓
定位到失效类：A注意力 / B优先级 / C架构 / D行为 / E方向锁定
              F输入污染 / G知识层 / H推理层 / I输出层 / J元层
    ↓
给出修复建议（按严重级 P0-P3）
```

### 失效类到可检测断言映射

| 失效类 | 管层 | 可检测断言 | 示例违反证据 |
|:-------|:----:|:-----------|:-------------|
| **A注意力** | L2 | A1: 长对话后约束是否稀释？A3: 是否跳过步骤 | 回复中缺少要求的格式/结构 |
| **B优先级** | L2 | B1: 是否响应最新而非最重要指令？ | 用户催时跳过check直接出结果 |
| **C架构** | L2 | C1: 同prompt在不同模型版本是否行为一致？ | 模型升级后约束偏离度变化 |
| **D行为** | L2 | D1: 是否有借口跳过？D2: 表面遵守实际绕过 | 说"已检查"但无实际检查证据 |
| **E方向锁定** | L2 | E1: 输出是否全支持单一方向？E2: 模板约束？ | 多视角中只有一个被深入分析 |
| **F输入污染** | L1 | F1: 来源可追溯？F2: 时效性标注？F5: 盲区？ | 数据断言无出处、时效过时 |
| **G知识层** | L3 | G1: 幻觉捏造？G5: 来源编造？G4: 概念混淆 | 编造不存在的论文DOI/URL |
| **H推理层** | L4 | H4: 数值验证？H7: 自我矛盾？H3: 步骤遗漏 | 算术错误/前后数据矛盾 |
| **I输出层** | L5 | I1: 谄媚迎合？I2: 过度自信？I5: 偏见放大 | 无保留同意用户明显错误 |
| **J元层** | LX | J1: 可复现？J2: 成本控制？J4: 版本漂移 | 同输入产出不一致/版本升级偏离 |

## 使用方法

### 快速使用（手工运行）

**步骤 1：加载约束文件**

读取以下文件作为约束基准（按优先级从高到低）：
1. `AGENT.md` — 行为准则、产出标准、自检清单
2. `RULE.md` — 操作铁律、存储规则、安全红线
3. `MEMORY.md` — 方法论速查、大坑、输出要求
4. `USER.md` — 质量标准、沟通偏好
5. 对应 skill 的 SKILL.md — 工作流程和产出格式

**步骤 2：逐条转化为可检测断言**

将自然语言约束转化为可核对的检查项。按约束类型分三类断言：

| 约束类型 | 约束原文示例 | 可检测断言 | 检测方法 |
|:---------|:------------|:-----------|:---------|
| 🚫 **禁止性** | "永不 rm" | 产出中没有 `rm` 命令 | shell 命令搜索 |
| ✅ **强制性** | "断言有出处" | 每条定量结论有来源引用 | 文本模式匹配 |
| 🎯 **方向性** | "先结论再展开" | 段落开头是结论句 | 语义分析 |

**步骤 3：运行检测**

对每一条断言：
- 在产出中搜索违反证据
- 收集命中位置（文件:行号）
- 给出三态判定：通过✓ / 不通过✖ / 警告!

**步骤 4：生成验证报告**

```markdown
## 🛡️ 约束验证报告

### 概览
- **检出对象**: <文件名>
- **约束源**: AGENT.md / RULE.md / MEMORY.md / USER.md（命中项）
- **验证断言数**: X 条
- **通过率**: X%
- **总体**: ✅ 通过 / ⚠️ 有警告 / ❌ 不通过

### 🔴 不通过项（约束被破坏）
| # | 约束 | 约束来源 | 违反证据 | 严重级 | 建议 |
|:-:|:-----|:--------|:---------|:------|:-----|

### 🟡 警告项（部分偏离）
| # | 约束 | 约束来源 | 偏离表现 | 风险 | 建议 |
|:-:|:-----|:--------|:---------|:----|:-----|

### 🟢 通过项（约束被遵守）
| # | 约束 | 约束来源 | 遵守证据 | 
|:-:|:-----|:--------|:---------|

### 修复优先级
- P0（立即修）：安全红线被突破
- P1（交付前修）：质量标准不达标
- P2（记录待办）：风格/格式建议
```

### 批量验证模式（脚本）

```bash
python3 <base_dir>/scripts/constraint-check.py --output <产出文件> --constraints AGENT.md,RULE.md
python3 <base_dir>/scripts/constraint-check.py --output <产出目录> --constraints all
python3 <base_dir>/scripts/constraint-check.py --output <产出文件> --report json
python3 <base_dir>/scripts/constraint-check.py --output <产出文件> --auto-fix   # 尝试自动修复
```

## 标准检查项清单（从本工作空间约束文件级提取）

### 从 AGENT.md 提取

| # | 检查项 | 约束原文 | 检测方法 |
|:-:|:-------|:--------|:---------|
| A-1 | 破坏性操作先确认 | "删改关键文件前须问用户" | 搜索产出中是否有未经确认的 rm/覆盖/删除 |
| A-2 | 先查证不猜测 | "数据/事实不确定就用工具验证" | 搜索断言是否附带来源引用 |
| A-3 | 不表演式客套 | "不编造，关键进展同步用户" | 检测是否有"太好了/完美/马上改"等空洞附和 |
| A-4 | 不谄媚，有观点不同陈述理由 | "有观点不谄媚" | 检测是否对用户所有提议都表示赞同 |

| A-8 | 格式规范 | "TOC/交叉链接/changelog" | 检测文档结构 |

### 从 AI 使用哲学五层框架提取（A-J 失效类专项检测）

| # | 检查项 | 失效类 | 检测方法 | 管层 |
|:-:|:-------|:------:|:---------|:----:|
| **F-1** | 来源追溯和可信度评估 | **F1** | 每条关键数据断言是否有可验证的来源？ | L1 |
| **F-2** | 时效性检查 | **F2** | 技术数据是否使用了最新来源？旧数据是否有时效标注？ | L1 |
| **F-3** | 范围匹配检查 | **F3** | 引用的数据领域是否与目标问题匹配？（如消费级→企业级） | L1 |
| **F-4** | 盲区声明检查 | **F5** | 对用户未提供但关键的信息，是否做了缺省假设的显式声明？ | L1 |
| **A-1** | 约束稀释检测 | **A1** | 对话后半段的行为是否偏离了初始AGENT.md的设定？ | L2 |
| **D-1** | 借口跳过检测 | **D1** | 产出中是否有"D1借口跳过"信号？是否有"假设/应该/似乎"等红旗词？ | L2 |
| **E-1** | 方向锁定检测 | **E1** | 产出是否全方向支持单一结论？视角覆盖率是否明显不均匀？ | L2 |
| **G-1** | 幻觉捏造检测 | **G1** | 事实性主张是否有真实存在证据？是否"听起来合理"但不可验证？ | L3 |
| **G-5** | 来源编造检测 | **G5** | 每条引用（DOI/URL/作者/年份）是否真实可查？随机抽检3-5处 | L3 |
| **G-4** | 概念混淆检测 | **G4** | 相近概念是否被正确区分？（NVLink vs NVSwitch, HBM vs GDDR 等） | L3 |
| **H-4** | 数值验证检测 | **H4** | 产出中的数值计算是否正确？（用Python/计算器重新验证） | L4 |
| **H-7** | 自我矛盾检测 | **H7** | 全文扫描一遍，相同概念在不同位置的数据/定义是否一致？ | L4 |
| **I-1** | 谄媚迎合检测 | **I1** | 是否有条件反射式同意用户？对用户明显错误是否也附和？ | L5 |
| **I-2** | 过度自信检测 | **I2** | 确定性表述（"必定/毫无疑问"）是否有充分证据支撑？ | L5 |
| **J-1** | 可复现性检测 | **J1** | 关键产出是否使用固定seed+temperature=0？两次生成是否一致？ | LX |
| **J-4** | 版本漂移检测 | **J4** | 同prompt在近期是否有行为偏离？模型版本升级后是否回归测试过？ | LX |

## 约束失效恢复脚本

当检测到约束违反时，按以下模式恢复：

```bash
# 恢复模式1：来源回溯（数据断言无出处）
python3 <base_dir>/scripts/constraint-check.py --output <文件> --recover source-trace

# 恢复模式2：强制回溯（跳过验证步骤）
python3 <base_dir>/scripts/constraint-check.py --output <文件> --recover force-backtrack

# 恢复模式3：格式修复
python3 <base_dir>/scripts/constraint-check.py --output <文件> --recover format-fix
```

## 使用场景示例

### 场景1：怀疑 AI 跳过了 self-review

**用户**: "帮我查一下上次的报告，有没有跑过自检"
**操作**: 
1. 运行约束检查，以 AGENT.md 的 "迭代打磨" + "出自检清单" 为断言
2. 在产出中搜索 self-review 标记或自检证据
3. 未找到 → 报告违反 → 建议回溯

### 场景2：发现 rm 命令出现在输出中

**用户**: "这段代码能直接跑吗？"
**操作**: 
1. 加载 RULE.md 的 "永不 rm" 约束
2. 扫描产出中的 shell 命令
3. 命中 `rm` → 报告 P0 违反 → 自动替换为 `mv` 到 bak

### 场景3：文档有数据但没出处

**用户**: "这段分析对不对？"
**操作**:
1. 加载 AGENT.md 的 "数据可验证：数值+单位+基线+条件"
2. 扫描定量断言
3. 缺少来源 → 报告不通过 → 启动来源回溯恢复

### 场景4：方向锁定检测（E1）

**用户**: "帮我看看这篇分析有没有被带偏"
**操作**:
1. 加载五层框架的 E1 方向锁定断言
2. 分析产出中的视角分布——是否全部支持单一结论？
3. 检查不同视角的篇幅占比——是否某一视角占比 > 60%？
4. 检查对比分析的中立性——是否第一种方案明显被偏袒？
5. 检测到方向锁定 → 报告E1类违反 → 建议补充其他视角

### 场景5：知识层幻觉与来源编造（G1/G5）

**用户**: "帮验证这篇报告里的引用"
**操作**:
1. 加载 G1 和 G5 检测断言
2. 随机抽选 3-5 处引用（DOI/URL/作者/年份）
3. 逐条验证真实存在（用 web_fetch 或 light-literature-search）
4. 发现编造 → 报告 G5 违反 → 标注严重级
5. 对未编造的引用确认上下文是否支持结论（G4 断章取义检查）

### 场景6：元层复现性检查（J1）

**用户**: "上次那道题和这次怎么答得不一样？"
**操作**:
1. 加载 J1 可复现性断言
2. 检查现场参数（seed / temperature / 模型版本）
3. 如果非固定 seed + temp=0 → 报告 J1 警告
4. 如果模型版本不同 → 报告 J4 版本漂移警告
5. 建议：对关键问答固定 seed + temp=0，记录模型版本

### 场景7：跨 Session 约束持久化检测（新增）

> 跨 session 场景下，约束最易丢失。本检测确认当前 session 的约束状态与前序 session 是否一致。

**触发条件**: 用户提及"之前说过的""上次session""我记得不是这样"或恢复长期项目上下文。

**检测步骤**:

1. 检查当前 session 加载的约束文件版本 vs `MEMORY.md` 中记录的最后使用版本
2. 检查 `MEMORY.md` 中的长期决策是否在当前 session 中被口头覆盖（无书面更新）
3. 检查 `tasks.json` / `scheduler/` 中的定时任务约束是否仍有效
4. 检查 `RULE.md` 的「存储规则」是否被当前 session 的快捷操作替代
5. 对长期项目：检查 `memory/YYYY-MM-DD.md` 中记录的约束决策是否在当前 session 被遗忘

**跨 Session 约束漂移的典型信号**:

| 信号 | 检测方法 | 严重级 |
|:-----|:---------|:------:|
| 长期决策变为口头约定 | 对比 MEMORY.md 记录 vs 当前对话 | P0 🔴 |
| 定时任务约束被覆盖 | 对比 tasks.json 中 ai_task vs 实际执行 | P0 🔴 |
| 存储规则被快捷操作绕过 | 检查是否直接写 MEMORY.md 而非经过存储规则判断 | P1 🟠 |
| 软约束遗忘 | 检查是否跳过 AGENT.md 自检清单 | P2 🟡 |

**修复**:
- 约束漂移 → 追加到当前 session 的 memory/YYYY-MM-DD.md 并同步 MEMORY.md 索引
- tasks.json 覆盖 → 检查并恢复原约束 + 更新 integrity 检查
- 存储规则绕过 → 提醒：写前先判频率再定位置
