# 自动反思与自我审查

> **理论基础**：[AI 使用哲学文档](knowledge/04_person/ai-usage-philosophy.md) 的五层管道框架（L1信源→L2注意→L3知识→L4推理→L5输出+LX元层），
> 覆盖 A-J 十类约束失效模式。自检的核心任务是**在各层定位失效信号**，并分类到对应失效类别进行修复。

## 五层管道自检框架

```
输入 → L1信源层 → L2注意层 → L3知识层 → L4推理层 → L5输出层 → 输出
         ↓          ↓           ↓           ↓           ↓
       F类失效    A-E类失效    G类失效     H类失效     I类失效
                                                      + LX元层 J类失效
```

每层自检回答三问：
1. **这层出问题了吗？** → 对应失效类型的信号出现
2. **问题源头在哪层？** → 方便定位修复（输出表现差可能根因在信源层）
3. **当前产出是否在某一层停留到抑制其他层？** → 方向锁定检测（E类）

### 失效类型快速自查表

| 管层 | 失效类 | 核心信号 | 检出难度 |
|:-----|:------:|:---------|:--------:|
| L1信源 | **F** | 来源不可靠/时效过时/范围错配/F5未知盲区 | 🟡 中 |
| L2注意 | **A/B/C/D/E** | 约束被稀释(A)/优先级反转(B)/借口跳过(D)/方向锁定(E) | 🟢 低~🔴极高 |
| L3知识 | **G** | 幻觉捏造(G1)/知识截断(G2)/虚假专家(G3)/来源编造(G5) | 🔴 高 |
| L4推理 | **H** | 逻辑谬误(H1)/过早收敛(H2)/数值失效(H4)/自我矛盾(H7) | 🔴 高 |
| L5输出 | **I** | 谄媚迎合(I1)/过度自信(I2)/偏见放大(I5) | 🟡 中 |
| LX元层 | **J** | 不可复现(J1)/成本失效(J2)/依赖失效(J3)/版本漂移(J4) | 🟡 中 |

**关键原则**：自检的固有弱点是**同源盲区（C3）**——自检和产出共享同一推理路径，发现不了自身问题。
因此自检永远不能作为唯一防线，必须配合交叉审查（doc-reviewer）和脚本硬校验。

## 工作方式（常驻，输出前必跑）
任何技能产出在交付前，先过一遍自检清单，发现问题就**先修后交**，不把粗糙结果直接抛给用户。重大产出可迭代多轮。

**证据闸门（借 verification-before-completion）**：不下「完成/通过/修好了」之类结论，除非当前轮就有新鲜证据。五步——①想清「什么命令/检查能证明它」②当场重跑(不引用旧结果) ③读完整输出、查 exit code、数失败 ④确认输出真支撑结论 ⑤才下结论。跳步=撒谎而非验证。红旗词：should/probably/seems to、提前自我满足、轻信子代理报告。
- 测试通过 = 有 0 失败的测试输出；构建成功 = exit 0（光过 lint 不够）；bug 修复 = 原始症状被测且通过；需求满足 = 逐条核对清单。
- **借口拦截**：临交付前大脑最会编借口跳过验证。「改动小不用跑/应该能过/上次跑过/先交了再说/审稿人不会注意」等都是借口而非判断，命中即回到证据闸门重跑。完整 27 条 excuse→reality 见 `references/excuse_intercept.md`。

**三态判定**：自检每一项都落到 通过✓ / 不通过✖ / 警告! 的明确判定（同 Deepchecks 的 check+condition、安全工具的 HIGH/MED/LOW/SAFE），不写含糊感受。不通过项附严重级 Critical(立即修)/Important(交付前修)/Minor(记录待办)。
- **假阳校准**：凡判「非问题/可放行」（✓ 或把疑似问题降级为非问题），必须附一行带证据的放行理由（指向具体命令输出/原文行号/检查结果），不许凭印象放行——没证据就当不通过处理。

## 分级执行档（先判档再跑，避免轻任务全跑或整体跳过）
全量 11 项对轻任务（改一句摘要、调个措辞）= 要么慢、要么干脆整体跳过导致失守。按产出量级择档：

- **重产出全量档**：跑下方 11 项全清单。**判据（命中任一即全量）**：产出 ≥1 个完整章节/小节；含数字结论或定量主张；对外交付（投稿/提交/客户/公开）；新增或修改代码/脚本；涉及引用、合规、伦理。
- **轻任务最小三项**：其余轻改动至少跑——① **证据**（结论是否有当轮新鲜证据，过证据闸门，不下未验证的"改好了"）；② **事实**（改动引入的数据/声称是否真实可核，无臆造 CONVENTIONS §4）；③ **夸大**（措辞是否超出证据，慎用 novel/significantly）。三项任一不通过即就地修。

判档本身要显式（心里点一下命中哪条判据）；拿不准用重档。orchestrator 阶段间检查点按此档调用本技能（见 `light-orchestrator/references/checkpoints.md`）。

## 五层通用自检清单

> 基于 AI 使用哲学的五层管道框架，每层的检查项对应特定失效类型。
> 每项的最小 通过✓/不通过✖ 反例对照见 `references/self_check_contrasts.md`；可勾选清单见 `assets/self_review_checklist.md`。

### L1 信源层检查（F类失效）

□ **F1 来源可靠**：每条关键事实是否标注来源？来源可信度是否经过评估（论文/标准 > 白皮书 > 博客 > 公众号）？
□ **F2 时效性**：信息的时效是否与任务匹配？技术数据是否采用最新来源？
□ **F3 范围匹配**：引用数据是否来自与目标问题匹配的领域/场景？有无范围错配？
□ **F4 上下文完整**：引用时是否保留了关键上下文？有无断章取义风险？
□ **F5 未知盲区**：是否有可预见的、用户未提供但重要的信息缺失？是否做了缺省假设的显式声明？

### L2 注意层检查（A/B/C/D/E类失效）

□ **A1-A3 约束遵循**：产出是否遵守了所有适用的约束（格式/步骤/质量要求）？有无注意力衰减症状？
□ **B1 优先级正确**：响应的是用户"最重要的"需求还是"最新说的"需求？
□ **C3 同源盲区认知**：本次自检是否能发现产出中的深层问题？是否需要交叉审查？
□ **D1 借口跳过**：是否在找借口跳过某些检查或步骤？（命中借口拦截表立即停止）
□ **E1/E3 方向锁定**：是否在某一方向上过深而忽略了其他同等重要的视角？当前产出中"多的"（深度）是否掩盖了"少的"（广度）？
□ **E2 样例固化**：是否被提供的样例/模板过度约束了输出的多样性？

### L3 知识层检查（G类失效）

□ **G1 幻觉捏造**：输出中有无可能不存在的论文/产品/事件/数字？"听起来合理"不等于真实存在
□ **G2 知识截断**：涉及最新事件/技术进展时，是否考虑了模型知识截止日期？
□ **G3 虚假专家**：对不熟悉领域的语气是否与常识问题一样自信？有没有虚张声势？
□ **G4 概念混淆**：相近概念是否被正确区分？（如 NVLink vs NVSwitch, HBM vs GDDR）
□ **G5 来源编造**：引用的 DOI/URL/作者/年份是否真实可查？每一处引用能否验证？
□ **G6 过度泛化**：是否有"所有/总是/从来不"类表述？是否应该加上限定词？

### L4 推理层检查（H类失效）

□ **H1 逻辑谬误**：论证链有无断点、跳跃、循环论证、虚假因果？（可联动 doc-reviewer 13条谬误表）
□ **H2 过早收敛**：是否只探索了第一个看似合理的路径而未考虑其他可能性？
□ **H3 步骤遗漏**：多步推理中的中间步骤是否都显式出现？有无"跳步"？
□ **H4 数值失效**：数值计算是否用外挂工具验证过（Python/计算器）？单位换算是否正确？
□ **H5 因果倒置**：是否混淆了相关性与因果性？
□ **H6 虚假二分**：是否将多选项问题简化为了二选一？是否有中间方案？
□ **H7 自我矛盾**：全文扫描一遍，相同概念在不同位置的数据/定义是否一致？

### L5 输出层检查（I类失效）

□ **I1 谄媚迎合**：是否有条件反射式同意用户？对用户有疑问/不同意的内容是否也说了"正确"？
□ **I2 过度自信**：确定性表述（"必定/肯定/确定无疑"）是否有足够证据支撑？模型自信语气≠内容正确
□ **I3 指令博弈**：是否字面执行了指令但违背了用户真实意图？
□ **I5 偏见放大**：输出中是否存在未经审视的假设或刻板印象？
□ **I6 拒绝校准**：是否有不合理的拒绝（能回答但不回答）或过度配合（越狱风险）？

### LX 元层检查（J类失效）

□ **J1 可复现性**：关键输出是否使用固定 seed + temperature=0 来保证可复现？
□ **J2 成本控制**：输出长度是否合理？有无不必要的冗余推高 token 消耗？
□ **J3 依赖检查**：本次输出依赖的外部资源（知识库/RAG/工具）是否健康可用？
□ **J4 版本一致性**：如果模型有版本变更，当前行为是否与历史一致？

## 按产出类型补充（五层框架指引）

### 各产出类型的层重点

| 产出类型 | P0 必检层 | 核心风险 | 配套技能 |
|:---------|:---------:|:---------|:---------|
| **技术文档** | L1+L2+L3 | F1（来源不可靠）+ G1/G5（幻觉/编造） | doc-reviewer, light-citation |
| **代码/脚本** | L4+H4 | H4（数值失效）+ I3（指令博弈字面执行） | light-backend-coding |
| **数据分析** | L1+L4+H4 | F类数据质量 + H4 数值错误 | light-result-analysis |
| **论文/综述** | L3+L4+L5 | G1幻觉 + H1逻辑 + I2过度自信 | light-paper-drafting |
| **汇报/PPT** | L2+L5+E1 | E1方向锁定 + I2夸大 | light-slides |
| **实验方案** | L4+L2 | H2过早收敛 + A类约束遗漏 | light-research-plan |
| **技能/SKILL** | L2+LX+J3 | A类约束衰减 + J3依赖失效 | skill-creator |

### 各类型详细自检

- **代码**：能否运行、有无测试、安全隐患(联动 a03)。回归测试走红-绿循环（撤掉修复必失败、恢复后通过）；新功能/改 bug 走 TDD。依赖安全按 SCA/能力分析自查（装包脚本、网络/shell 访问、混淆、typosquatting；CLI 可借 snyk/Socket `sfw`）；产出本身是 skill/MCP 则按 prompt injection/数据外泄/含糊触发/跨技能重叠等维度自查，「无发现≠无威胁」仍需人工复核（工具命令见 references.md）。
  - **L4 专项**：运行逻辑是否在第一个合理路径上停止探索了（H2 过早收敛）？有无隐藏数值错误（H4）？
- **论文/材料**：用同行评审维度自审——原创性、方法学、**结论逐句回溯结果**(最经典失败点：不止口头确认"被支撑"，而是把每条主张逐句拎出，指出结果中支撑它的那句原话并带行号/表号/图号定位；找不到对应支撑句的主张即判 ✖ 删除或降级)、文献根基、贡献、格式合规(联动 m14)；科学主张过批判性思维（独立 verify 源头、相关≠因果、可证伪、举证责任在提出方）。
  - **L3 专项**：引用的每篇论文/标准是否真实存在（G5 来源编造）？是否混淆了相近概念（G4）？
  - **L5 专项**：结论是否被模型自信语气放大（I2 过度自信）？有无谄媚迎合用户倾向（I1）？
  - **核心撞车终检（交付前最后一道闸）**：定稿前用核心结论/方法当关键词再检索（至少 2 库），找"最像的那一篇"。三态：✖ 撞车且未承认前作=Critical，回 m08/m04 重定位（承认前作、改打广度/严谨/负结果牌，绝不假装首创）；! 已承认并讲清 delta=警告，确认 framing 收到证据撑得住；✓ 无撞车且阴性证据充分。并预演审稿人拒稿 top-3。与 m03/m04 撞车检查同源，是输出端兜底。
- **数据/结果**：统计是否站得住(联动 m06)。对照/样本/漂移可借 Deepchecks/Evidently 检查清单逐项核（套件用法见 references.md）。
  - **L4 专项**：计算是否正确（H4）？有无混淆相关与因果（H5）？
- **合规**：伦理/版权/隐私风险(联动 a10)，当带证据逐条核查：定范围→三态判定→不通过附修复建议与来源位置。
- **自评打分(对抗式批判)**：按 5 维打分——可操作性、具体性、论证、是否给解法、语气专业；致命问题排在格式问题前，别陷入只挑表述的表面陷阱。
  - **L5 专项**：评委分是否向某一维度过度倾斜（E1方向锁定）？是否只看到"好"而忽略了"偏"？
- **开场即上强度(grill 规则)**：**仅重产出全量档**适用——自审**首句就直接列三个最致命弱点**，禁客套开场与缓冲句（对自己的产出缓冲就是放水），三个弱点按严重度排序、先于任何肯定表述。轻任务最小三项档不强制三弱点开场，按其三项就地修即可。

### 方向锁定检测（E类失效专项）

方向锁定是最容易被忽略的失效类型——"多的"（深度内容）掩盖了"少的"（缺失视角）。

**检测方法**：
```
① 列出产出覆盖的"视角集合"（性能/成本/可靠性/安全/可维护性...）
② 估算每个视角的篇幅占比
③ 追问"同等重要但没覆盖的视角是什么？"
④ 检查源 prompt 是否有无意中锁定方向的语言
⑤ 做反方自检：若结论全支持A，尝试为¬A构建最强论证
```

**红旗信号**：
- 产出全部排他性支持某一结论（应有部分数据不支持）
- 多节篇幅分布极度不均（某节 > 60%，与重要度不匹配）
- 对比分析中第一种方案明显"更好"（先验偏向）
- 对己方视角"优势"极详细，对缺点/代价一笔带过
- 用户没指定方向，但输出天然倾向某一视角

**缓解策略**：
- 回复前主动问"这个问题是否还需要从××视角看？"
- 主动添加"反方视角"或"其他可能性"小节
- 对每个优点列一个代价/前提条件

## 失败循环识别
同一问题修两次仍不对，停止打补丁、诊断根因、换思路（systematic-debugging：细读报错→稳定复现→查最近改动→边界埋点定位→源头修不在症状处修；一次只改一个变量）。**修≥3 次仍不行=架构问题**：停手质疑架构（信号：每修一处暴露新耦合/按下葫芦浮起瓢），与用户讨论后再动。四阶段全文见 `light-backend-coding/references/debug_protocol.md`。

## 接收外部意见（借 receiving-code-review）
对评审/反馈不「表演式同意」、不「盲目实现」：先核验意见技术上是否成立、是否清晰，对可疑处提质疑或要澄清，只在理解+验证后才改；反驳要给代码/测试/技术理由，不空驳。
- **禁表演式同意**：「你说得太对了/马上改/好的好的」等空附和一律禁用，同意必须带证据，反驳也必须带证据。
- **不清楚就全停**：对意见含义/范围/目标有任何不确定，停下要澄清，不用猜测继续往下做。
- **范围纪律 + YAGNI**：只改被指出的问题，不借机重构无关代码；不为「将来可能用到」加抽象/配置/防御代码。
- 禁用措辞清单、标准流程、问题分级见 `references/receiving_feedback.md`。

## 产出
默认静默自检并直接交付修正后的结果；若发现无法自行解决的重大问题，明确告知用户问题与建议，不隐瞒。
