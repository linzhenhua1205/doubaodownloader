# 专利交底书撰写技能

## ⚠️ 重要声明

本技能产出为**专利交底书草稿**（技术交底书，提交给专利代理师/专利工程师的原始材料），不构成正式法律文件。最终权利要求书、说明书、附图须由**专业专利代理师**审核定稿。技术内容须真实、可实现，不得虚构数据或夸大效果。

## 工作流总览

生成一份专利交底书需经过 **4 个阶段**：

```
Phase 1: 信息萃取 ← 从已有专利点子/技术文档提取核心要素
Phase 2: 查新检索  ← 验证新颖性，确保无在先公开
Phase 3: 交底书撰写 ← 按五段式格式组织
Phase 4: 质量审查  ← 逻辑谬误扫查 + 数据可验证性 + 格式规范
```

## 一、专利交底书格式规范（硬标准）

每份交底书必须严格按以下 **5 段结构** 组织，段落编号不能少、顺序不能乱：

---

### （一）发明名称

- **字数**: ≤25 个中文字
- **要求**: 简单明了，反映技术内容是产品/装置/方法
- **格式**: 一般用「一种……方法/系统/装置/模块」
- **示例**: ❌ 一种基于 BMC 的高效智能问答交互方法及系统（18字）✅

### （二）所属技术领域

- **说明**: 发明所属或直接应用的技术领域
- **格式**: 一句话，如「本发明属于服务器带外管理技术领域，具体涉及一种嵌入式轻量级智能问答方法」

### （三）现有技术（背景技术）

- **内容**:
  1. 现有技术方案/产品是什么（结合本发明领域）
  2. 现有技术的客观缺陷（针对性，避免贬损性措辞）
- **要求**: 列出 1-2 个最接近的现有方案（含对比文件号或出处）；缺陷须是本发明能解决的，不能无关

### （四）发明内容

#### 1. 发明要解决的问题

- 一句话，直接对应背景技术缺陷
- **格式**: 「本发明旨在解决……的技术问题」

#### 2. 解决方案、具体实施例及附图

**解决方案**（核心，必须使本领域技术人员可实现）：
- 整体方案概述（1-2 段）
- 关键步骤/模块/结构（逐条列出，软件类给数据流、模块交互、关键算法/伪代码）
- **电气连接关系**（硬件类）：各元件的连接方式、信号流向、控制关系
- **方法步骤**（方法类）：每一步的具体操作，包括静态关系（结构组成）+ 动态关系（时序/流程）

**具体实施例**（至少 1 个）：
- 实施环境/参数取值（具体数值、硬件型号、版本号等）
- 完整流程描述
- 举例说明：用「例如」「假设」「以……为例」展开一个完整的实施场景

**英文缩写说明**：
- 首次出现英文缩写时，必须写全称 + 中文含义
- 如：BMC（Baseboard Management Controller，基板管理控制器）、Redfish（一种基于 RESTful 接口的数据中心管理标准）

**附图说明**（若有）：
- 图1：xxx（流程图/结构图/模块交互图）
- 补充：本交底书暂以文字描述为主，正式申请时由代理师决定是否配图

#### 3. 发明的优点

- 与「要解决的技术问题」「技术方案」一一对应
- 尽量量化：精度/速度/能耗/成本/可用性提升百分比等
- 或给出机理解释：为什么本方案能带来这个效果
- **禁止** 使用「极大」「显著」等无数据修饰词
- 科学分析/试验数据是最有力的证据

### （五）最想保护的关键点

- 概括写明最具创新性的内容（3-5 条）
- 这是代理师撰写权利要求书的直接输入
- **格式**: 每条一句话，用「区别于现有技术，本发明……」「本发明的创新点在于……」

---

## 二、查新检索与新颖性验证

每份交底书在撰写前必须做初步查新检索（至少检索中文专利 + 中文技术文献）：

### 检索方法

1. **中文专利检索**（优先）：
   - 访问中国专利公布公告网站 http://epub.sipo.gov.cn/ 或者 Google Patents（https://patents.google.com）
   - 用核心关键词组合搜索，如 `BMC AND 智能 AND 问答`、`BIOS AND 散热 AND 自适应`
   - 每份交底书至少记录 3-5 篇对比文献号，简要说明与本发明差异

2. **补充检索**：
   - 如果技能 `light-ip-application` 可用，读取其 `patent_search.py` 脚本辅助检索
   - 万方/知网查学术论文是否存在类似公开

3. **检索结果记录格式**：
   ```
   | 对比文献 | 相似度 | 核心差异 |
   |:---------|:------|:---------|
   | CNxxxxxxA（一种xxx方法） | 中 | 本文通过xxx实现，该文献采用xxx |
   ```

### 新颖性判断

- 如果找到完全相同或高度相似的方案 → 标记「新颖性风险：高」，建议修改独立权利要求范围
- 如果找不到相同方案 → 标记「新颖性初步判断：无风险」

## 三、质量审查（交付前必做）

### 3.1 逻辑谬误扫查

使用 MEMORY.md 中的 13 条逻辑谬误清单自检，重点关注：

| 谬误类型 | 在本场景常见表现 | 检查方法 |
|:---------|:----------------|:---------|
| 术语漂移 | 同一概念在不同章节用不同术语 | 全文搜索核心术语一致性 |
| 结论前置 | 在解决方案之前先下结论 | 检查「发明内容→优点」是否与技术方案对应 |
| 假精确 | 编造无来源的数据百分比 | 所有数据必须有出处或计算依据 |
| 二元对立 | 只有 A 方案和本方案对比 | 确保现有技术分析真实、非贬损 |
| 声明-实践不一致 | 声称可量化但实际没数据 | 每个「提升/降低」后面检查是否有基准值 |

### 3.2 数据正确性

- **数值**: 所有数值必须有单位（ms/s、MB/GB、% 等）
- **比较**: 所有「提升/降低」必须有对比基线
- **来源**: 关键数据标注来源（测试报告编号/标准文档号/实验日志）
- **条件**: 标注测试条件（温度/负载/配置等）

### 3.3 格式规范

- 发明名称 ≤25 字
- 英文缩写首次出现须写全称+中文
- 五段式结构完整，没有缺漏
- 语言正式、客观，不使用营销化表达

## 四、输出物规范

每份交底书输出为一个 Markdown 文件，命名规则：

```
knowledge/02_rd/00_rd-management/patent-disclosure-<序号>-<英文slug>.md
```

或按用户指定路径。

每次生成后，同步更新 `knowledge/02_rd/log.md`。

文件头部须包含：
```markdown
> **专利交底书草稿 v1.0**
> **生成日期**: YYYY-MM-DD
> **来源点子**: 《专利点子报告》第X.X节
> **状态**: 草稿·待代理师审核
```
