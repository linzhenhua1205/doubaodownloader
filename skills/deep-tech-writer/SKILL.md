# 深度技术文档创建技能 (Deep Tech Writer)

## 概述

本技能提供一套**六步工作流**，用于创建符合高标准的质量技术文档。每次使用前先运行自检脚本确保质量达标。

遵循的六大质量标准（来自用户长期使用中沉淀的规则）：

| # | 原则 | 含义 |
|:-:|:-----|:------|
| 1 | **原理深度** | 深入到协议/芯片/物理层次，不罗列名词，不流于形式 |
| 2 | **来源标注** | 每条关键断言必须有出处（论文/标准/白皮书/报告） |
| 3 | **强逻辑** | 论点→论据→数据→结论，不自相矛盾，不自造分类 |
| 4 | **取材优先** | 论文/标准原文 > 官方白皮书 > 一线工程报告 > 主流行业分析 > 通用知识 |
| 5 | **外部链接优先** | 通用背景知识压缩为外部链接一句话带过 |
| 6 | **审查闭环** | 写完后必须自检，必要时外部评审→处理意见→重新优化 |

## 六步工作流

### 第0步：先查知识库已有内容（深度分析启动必做）

> 🚀 **2026-08-25 新增**：深度分析动笔前**必须先查 `knowledge/log.md` 全局账本**
> （全库路径+摘要密度最高的单文件索引，1316 条目/2026-05 至今），避免重复造文档、
> 并快速定位可引用的既有深度报告。工具化检索避免全量 read log.md 浪费 token。

```bash
# ① log.md 第一线索源：关键字检索 → 日期+路径+摘要（命中路径自动验证/兜底）
python3 scripts/tools/kb-log-search.py --keyword "<主题>" [--keyword "词2"] [--since 2026-08-01] [--limit 15]
python3 scripts/tools/kb-log-search.py --keyword "<主题>" --path-only   # 只看有效路径

# ② 命中候选后 read 评估；判断「已有覆盖 vs 增量 vs 全新」
# ③ 补充：index.md 摘要 + grep 文件内容（参照 knowledge-doc-writer 1a 流程）
```

**自检**：当前主题在 log.md 中检索过吗？已有文档覆盖了哪些角度？本次增量是什么？
（避免重复建文档：已有覆盖 → 走增量升级而非新建，参考 knowledge-doc-writer 查重结论）

### 第1步：搜集权威源

按优先级顺序，**至少覆盖 2 个层级**：

| 层级 | 来源类型 | 示例 |
|:-----|:---------|:-----|
| 🥇 **论文/标准原文** | IEEE/ACM/arXiv、JEDEC/PCI-SIG/IBTA/OCP 规范 | 论文PDF、标准文档 |
| 🥇 **官方技术白皮书** | NVIDIA/Intel/AMD/Arm/Samsung 官方文档 | 架构白皮书、TRM、Datasheet |
| 🥈 **一线工程报告** | 实测数据、实验报告、Backblaze/GCP/Facebook 工程论文 | Sosp/ATC/OSDI 论文、故障分析 |
| 🥉 **主流行业分析** | SemiAnalysis/DIGITIMES/The Next Platform/AnandTech | 深度行业分析、拆解报告 |
| 📄 **通用知识** | Wikipedia、博客、教程 | 一句话带过 + 外部链接 |

**自检**：当前分析的每条关键断言，追溯到哪个层级？有无来源？是否可以升一级？

### 第2步：协议/机制原理深潜

> ⚠️ **常见陷阱**: 罗列名词但不讲原理（如只说"使用了PAM4调制"不说为什么选择PAM4、信噪比代价是多少）

**深度标准**：
- ✅ 解释为什么 —— 设计选择背后的物理/经济/逻辑原因
- ✅ 量化对比 —— 多个方案间用数据比较（延迟/带宽/面积/功耗/成本）
- ✅ 给出值 —— 关键参数给出具体数值和范围
- ✅ 时序/流程 —— 解释信号/数据/状态的完整流转过程
- ❌ 仅罗列名词 —— "支持PAM4、RS-FEC、CTLE、DFE……" 没有解释

### 第3步：强逻辑结构编排

**逻辑框架选择指南**：

| 文档类型 | 推荐结构 |
|:---------|:---------|
| 技术综述/全景 | 分层展开（L5→L0），每层先原理再实现 |
| 方案对比/选型 | 维度对齐→统一量纲→对比矩阵→决策树 |
| 原理深潜 | 基础→机制→实现差异→性能影响→趋势 |
| 故障分析 | 事件→鱼骨图→5Why→根因→修复→预防 |

**逻辑自检**：用 MECE 原则检查章节划分——同层是否互斥且穷尽？

### 第4步：量化数据 + 来源标注

**量化四要素**：
```
📊 吞吐提升 28.9%（vs BF16, batch=32, A100-80GB, PyTorch 2.0）
```

每条关键数据必须包含：**数值 + 单位 + 对比基线 + 测试条件**

**来源标注规范**：
```
[来源: 论文/标准编号/报告/URL]
```

**系统化数据标注**：
- 每条断言前问：「这句话有出处吗？」「出处是第一手还是第二手？」
- 没有出处的断言放在「✅ 已标注」列，否则放进「❌ 待补充」列
- 两个独立来源的交叉验证更可靠

### 第5步：外审迭代

1. **自审** — 对照本技能的「质量自检脚本」逐项检查
2. **外部视角** — 自问三个问题：
   - 如果领域专家看到这篇文档，会在哪里提出质疑？
   - 是否有遗漏的重要替代方案？
   - 文档中的每个断言是否都能被证伪？
3. **处理反馈** — 收到评审意见后：逐条评估→标记接受/拒绝→修改→重新优化

### 第6步：格式打磨

**文档结构规范**（已固化到 `check_md_format.py` 的 R2 规则）：

| 规则 | 要求 | 检查工具 |
|:-----|:------|:---------|
| ✅ changelog 在底部 | >200行文件必须有底部 changelog，条目化、时间倒序、附带链接 | `check_md_format.py` R2 |
| ✅ TOC 在顶部 | >100行文件必须有目录 | `check_md_format.py` R2 |
| ✅ 交叉链接 | 覆盖 knowledge/ 下已有相关文件 | 手动检查 |
| ✅ 代码块纯ASCII | 图表用纯英文ASCII，中文说明在外 | `check_md_format.py` R1 |
| ✅ 通用知识外链化 | 背景知识用一句话+外部链接 | 手动检查 |
| ✅ 出处标注 | 技术文档必须有参考来源 | `check_md_format.py` R2 |
| ✅ 强逻辑 | 论点→论据→数据→结论，不跳跃 | 手动检查 |

## 脚本使用

```bash
# 在创建/更新文档后运行质量自检
python3 <base_dir>/scripts/check_tech_doc_quality.py <文档路径>

# 示例
python3 <base_dir>/scripts/check_tech_doc_quality.py knowledge/server-hardware/xxxx.md
```

## 常见错误预防

| # | 错误类型 | 症状 | 预防 |
|:-:|:---------|:-----|:-----|
| 1 | **结论前置** | 先摆结论再堆证据，而非从数据推结论 | 核心结论移至文档末尾 |
| 2 | **二元对立** | 只列两个极端方案，忽略中间连续谱 | 至少列出3个方案的参数对比 |
| 3 | **假精确** | 用量化语言但无操作化度量 | 追问数值的单位和计算方式 |
| 4 | **类比当定理** | 用类比得出结论，用"必然"措辞表述 | 检查每个"定理/必然"能否严格推出来 |
| 5 | **术语漂移** | 借用其他学科术语包装论证 | 术语溯源：是精确引用还是比喻？ |

## 📐 架构决策记录（ADR）模板

> **参考来源**: ECC-main/agents/architect.md 的 ADR 模板，适配技术文档场景

当进行重大技术决策时（如架构选型、方案对比、标准制定），创建 ADR 记录决策过程：

```markdown
# ADR-XXX: <决策标题>

## 背景（Context）
- 需要解决的问题或决策背景
- 技术约束和业务需求
- 当前现状分析

## 决策（Decision）
- 最终选择的技术方案
- 核心设计要点

## 理由（Rationale）
- **为什么选择该方案**（第一性原理推导）
- **物理/经济/逻辑依据**
- **量化对比数据**

## 影响（Consequences）

### 正向影响
- 性能提升数据（如延迟降低 30%）
- 成本节约（如功耗降低 15%）
- 可维护性改善

### 负向影响
- 技术债务（如需要重构 XX）
- 风险点（如供应商依赖）
- 额外成本（如需新增设备）

### 替代方案（Alternatives）
| 方案 | 优势 | 劣势 | 放弃原因 |
|:-----|:-----|:-----|:---------|
| 方案A | ... | ... | 第一性原理推导不支持 |
| 方案B | ... | ... | 成本过高（ROI < 1） |
| 方案C | ... | ... | 技术风险不可控 |

## 状态（Status）
提议 / 已批准 / 已实施 / 已废弃

## 日期（Date）
YYYY-MM-DD

## 参考（References）
- 论文/标准编号
- 白皮书链接
- 工程报告链接
```

### ADR 创建时机

- **必须创建**: 涉及架构选型、技术路线决策、标准制定
- **建议创建**: 涉及性能优化方案、成本敏感决策、高风险方案
- **可选创建**: 小的技术调整、常规迭代

## 🔄 会话持久化命令（参考 ECC ck skill）

> **核心价值**: 长文档创建过程可能跨多个会话，需要持久化记录进度、决策和待办事项

### `/dtw:init` — 初始化技术文档项目

```bash
# 在文档目录创建持久化记录
python3 <base_dir>/scripts/tools/session-manager.py init doc:<文档名> --context path=<文档路径>
```

输出 JSON 记录：
```json
{
  "docPath": "...",
  "title": "...",
  "stack": ["硬件架构", "服务器", "AI"],
  "goal": "创建深度技术分析文档",
  "constraints": ["必须有量化数据", "必须有来源标注"],
  "createdAt": "2026-06-27T10:00:00Z"
}
```

### `/dtw:save` — 保存会话进度

**需要 LLM 分析当前对话**：
- `summary`: 本次会话完成的内容（一句话）
- `leftOff`: 当前正在处理的具体章节/技术点
- `nextSteps`: 下一步工作清单（优先级排序）
- `decisions`: 本次做出的技术决策（`{what, why, ADR编号}`）
- `blockers`: 当前阻塞点（数据缺失、来源未找到等）

```bash
echo '<json>' | python3 <base_dir>/scripts/tools/session-manager.py save doc:<文档名>
```

### `/dtw:resume` — 恢复上次进度

```bash
python3 <base_dir>/scripts/tools/session-manager.py resume doc:<文档名>
```

输出上次会话记录，提示："继续从这里？还是有新的变化？"

## 🤖 LLM 深度分析模块

> **参考来源**: user_indent.md 第十章的 LLM 深度解析框架

在技术文档创建完成后，使用 LLM 进行语义级深度分析：

### 分析维度

| # | 分析维度 | 方法 | 输出 |
|:-:|:---------|:-----|:-----|
| 1 | **技术关注演化** | 从关键词频次推断技术栈演进路径 | 技术栈关注优先级排序 |
| 2 | **决策模式洞察** | 从指令模式推断工作习惯 | 核心工作模式描述 |
| 3 | **隐性洞察** | 发现统计数据背后的隐性规律 | 深层特征描述 |
| 4 | **趋势判断** | 基于文档内容推断未来演进方向 | 技术趋势预测 |

### 分析输出格式

```markdown
## 🤖 LLM 深度分析

### 技术关注演化
- **最高频关注**: XX（占比XX%）
- **演化路径**: 从 A → B → C 的技术视野扩展
- **隐性特征**: 用户本质是知识建构者，兼具XX和XX能力

### 决策模式洞察
- **核心指令模式**: XX（占比XX%）
- **工作习惯**: 偏好"XX"而非"XX"
- **决策路径**: 创建→迭代→打磨三元闭环

### 技术栈关注优先级
硬件架构（si）> 系统互联（interconnect）> 单点技术（memory）
```

## 📊 质量评分体系

> **参考来源**: ECC architect agent 的系统设计 checklist

技术文档完成后，按以下维度评分：

| # | 评分维度 | 检查项 | 权重 |
|:-:|:---------|:-------|:-----|
| 1 | **原理深度** | 是否深入到协议/芯片/物理层次？是否解释"为什么"？ | 30% |
| 2 | **量化支撑** | 是否有3+处数值+单位+基线的数据？是否可追溯？ | 25% |
| 3 | **来源质量** | 是否引用论文/标准/白皮书？是否交叉验证？ | 20% |
| 4 | **逻辑严密** | 是否有逻辑谬误？是否自相矛盾？ | 15% |
| 5 | **格式规范** | 是否符合 changelog/TOC/代码块ASCII 规则？ | 10% |

**评分等级**：
- **优（85+）**: 可直接发布，无需修改
- **良（70-84）**: 可发布，建议小修
- **需改进（50-69）**: 需重大修改后发布
- **不合格（<50）**: 需重写
