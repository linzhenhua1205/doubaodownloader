# 方法论分析与固化技能 (Method Analysis)

## 概述

本技能用于**方法论框架的创建、验证、固化与迭代优化**。将隐性方法论转化为显性、可复用的结构化知识。

**核心价值**（来自 user_indent.md 第九章）：
- **P1 优先级**: 方法论制定是核心驱动力
- **高频需求**: 用户频繁提出方法论制定需求（MECE、第一性原理等）
- **固化必要性**: 方法论需要从对话沉淀到知识库，避免每次重复讨论

## 方法论框架库

> **参考来源**: MEMORY.md 的方法论速查清单 + RULE.md 的方法论框架

### 🅰 分析类方法论

| 框架 | 一句话描述 | 适用场景 | 关键约束 |
|:-----|:-----------|:---------|:---------|
| **五看三定** | 360°扫完宏观→市场→竞争→自身→机会，再收拢到方向→目标→路径 | 市场调研、战略规划、竞品分析 | 每看 ≥ 3 条有效信息，结论来自数据而非直觉 |
| **MECE 拆解** | 至上而下分层，同层互斥且穷尽 | 任何结构化分析的开场 | 自检：有重叠→违ME；有遗漏→违CE |
| **鱼骨图 + 5W** | 人机料法环测六维排查，每条因果链追问 5 次 Why 到底 | 故障根因、性能瓶颈、异常数据 | 必须触及物理极限/设计原点/管理根源/外部约束才停 |
| **维度对齐** | 比较前先问：同一维度？能力还是方案？事实、假设还是期望？ | 任何分析的开场自检 | 三问缺一问，结论不可靠 |
| **对比分析** | 先做完维度对齐，再统一量纲/条件 | 产品对比、技术选型 | 深入到架构哲学/技术权衡/商业模式，不罗列参数 |
| **BOM 核算** | 按实际指标算，区分全生命周期，验证充分性 | 成本分析、物料选型 | 供应链动态因素必须纳入，不低估"小项"累积效应 |
| **架构五工具** | 需求总表→约束矩阵→四维评估→权衡矩阵→Checklist 五步闭环 | 系统设计、方案评审 | 所有决策必须有量化数据支撑，禁止主观判断 |
| **深度技术分析工作流** | 搜集权威源→协议/机制原理深潜→强逻辑结构编排→量化数据+来源标注→外审迭代→格式打磨 | 创建技术专题文档、深度调研报告 | ①不罗列名词要讲原理 ②每条断言标注来源 ③通用知识压缩为外链 ④写完自检「流于形式？」 |

### 🅱 思维类方法论

| 框架 | 一句话描述 | 落地检查 |
|:-----|:-----------|:---------|
| **第一性原理** | 不盲从"大家都这么说"，回到物理/经济/逻辑的基本规律 | 我的结论能否用基本原理推导出来？ |
| **抽象·分层·分治·演化** | 只看该看的→划分层级→横向拆解→持续进化 | 当前正在用哪种思维？下一步该用哪种？ |
| **架构制图四要素** | 每张图必须有：元素 + 关系 + 属性（接口/职责）+ 原理（为什么这么设计） | 这张图能让外人看懂设计意图吗？ |
| **人机协作** | 人类负责品味和判断，AI 负责重复劳动 | 我是在做判断还是在做执行？ |

### 🅲 产出类方法论

| 规范 | 要求 | 自检 |
|:-----|:-----|:-----|
| **量化四要素** | 每条数据必须有：数值 + 单位 + 对比基线 + 测试条件 | `吞吐提升 28.9%（vs BF16, A100, batch=32）` |
| **来源标注** | 关键数据/判断必须附带来源，禁止无来源断言 | 这句话的来源我能说出来吗？ |
| **交叉验证** | 关键结论至少经 2 个独立来源验证 | 换一个渠道查同样的数据，结果一致吗？ |
| **深度五步法** | 信息聚合→逻辑拆解→推理论证→方案沉淀→迭代复盘 | 我是直接转述，还是真正推演过？ |
| **数据时效性** | 科技类数据优先引用 **2025-2026 年**的最新信息 | 这条数据的年份？是否有更新的来源可替换？ |
| **调研材料质量标准** | 论文/标准/规范原文 > 官方技术白皮书 > 一线工程报告 > 主流行业分析 > 通用知识 | 这条结论能追溯到论文/标准原文吗？没有来源的断言是否删掉了？通用知识是否被压缩为外链？ |
| **文档结构规范** | changelog在底、TOC在顶、交叉链接覆盖、代码块纯ASCII、通用知识外链化、出处标注、强逻辑 | 文档底部有 changelog 吗？代码块内有中文吗？每条断言都能追踪到出处吗？ |

### 🅴 逻辑谬误与预防

> **来源**: 从方法论使用中提炼的常见谬误（已固化到 doc-reviewer skill）

| # | 谬误 | 症状 | 预防方法 | 自检话术 |
|:-:|:-----|:-----|:---------|:---------|
| 1 | **声明-实践不一致** | 宣称A但全文按¬A运作 | 穿行测试 | 「凡是我喊得最响的那句声明，全文是否真的按它走？」 |
| 2 | **先验分类** | 先假定分类数再事后拟合理论 | 溯源追问 | 「这个数字是推出来的还是定下来的？」 |
| 3 | **模型几何不相容** | 多个模型描述同一事物但结构冲突 | 画空间结构 | 「我的模型们摆在一起，在几何上矛盾吗？」 |
| 4 | **术语漂移** | 借用其他学科术语包装论证 | 术语溯源 | 「这个术语，我是在用它本来的意思，还是借它的光环？」 |
| 5 | **类比当定理** | 用类比得出结论却用"定理"措辞表述 | 措辞诚实化 | 「这个是真正推出来的，还是说起来像那么回事？」 |
| 6 | **内部冲突未检视** | 同一框架对同一对象给出相反判定 | 集中陈列法 | 「我把这些结论放在同一页，它们打架吗？」 |
| 7 | **伪结构/假密度** | 同一内容在不同章节重复，编号制造"很多节点"假象 | 合并测试 | 「这两条换了个说法，说的是一件事还是两件事？」 |
| 8 | **空洞同构** | 找共同点然后声称"本质上一样"，但共同点太宽泛 | 差异优先法 | 「除了像的地方，不像的地方是什么？」 |
| 9 | **维度混淆** | 两个不同维度的东西塞到同一概念框架的同一格 | 再分类法 | 「这里面的'同一个概念'，换了个上下文意义还一样吗？」 |
| 10 | **诠释学循环** | 框架能事后解释任何现象，但从未做有风险的预测 | 证伪性自检 | 「如果我的框架是错的，什么证据会让我发现？」 |
| 11 | **假精确** | 使用量化语言但无任何操作化度量 | 单位追问 | 「这个数值能算吗？单位是什么？」 |
| 12 | **结论前置** | 结论表放在文档开头，后续论证变成给预设找支持 | 论证优先 | 「先看了结论再看论证，还是在论证最后才揭示结论？」 |
| 13 | **二元对立** | 只列两个极端方案，忽略中间方案空间 | 多元方案表 | 「真的只有这两个选项吗？中间有没有更平衡的方案？」 |

## 方法论固化工作流

### 第1步：识别方法论需求

**触发条件**：
- 用户提出方法论名称（MECE、第一性原理、五看三定等）
- 用户描述分析框架（"我要做XX分析"、"XX框架"）
- 用户要求制定标准（"制定XX标准"、"固化XX框架"）

**识别方法**：
```bash
# 使用关键词扫描识别方法论需求
python3 <base_dir>/scripts/identify_method.py --input <用户输入文本>  # ⚠️ 设计承诺（方法论识别（语义判断），当前由 LLM 完成）
```

输出：
```json
{
  "methodName": "MECE拆解",
  "category": "分析类",
  "triggerKeywords": ["MECE", "互斥", "穷尽", "结构化分析"],
  "suggestedFramework": "MECE拆解框架"
}
```

### 第2步：选择或创建方法论框架

**选择现有框架**（优先）：
- 从方法论框架库中选择匹配的框架
- 适配到当前具体场景

**创建新框架**（必要时）：
- 从第一性原理推导
- 确保框架有明确约束和自检方法
- 验证框架的可操作性

### 第3步：方法论验证

**验证维度**：

| # | 验证项 | 检查方法 | 通过标准 |
|:-:|:-------|:---------|:---------|
| 1 | **可操作性** | 是否有明确的执行步骤？ | 步骤清晰、可执行 |
| 2 | **自检方法** | 是否有明确的自检话术？ | 每个约束有对应的自检问题 |
| 3 | **证伪性** | 是否有明确的证伪条件？ | 框架有明确的失败条件 |
| 4 | **适用边界** | 是否明确适用场景？ | 适用场景清晰描述 |
| 5 | **第一性原理支撑** | 是否从基本原理推导？ | 有明确的原理推导路径 |

**验证输出**：
```markdown
## 方法论验证报告: <方法论名称>

### 验证结果
- **可操作性**: ✅/⚠️/❌
- **自检方法**: ✅/⚠️/❌
- **证伪性**: ✅/⚠️/❌
- **适用边界**: ✅/⚠️/❌
- **第一性原理支撑**: ✅/⚠️/❌

### 🔴 必须修正
1. [验证项] → 建议修正内容

### 🟡 建议修正
1. [验证项] → 建议修正内容

### 方法论质量评级
- **可用（85+）**: 框架完整、可操作、有自检
- **待完善（70-84）**: 框架基本完整，建议补充自检
- **需重构（<70）**: 框架不完整，需重新设计
```

### 第4步：固化到知识库

**固化路径**：
```
knowledge/methodology/<方法论名称>.md
```

**固化内容**：
1. **框架描述**: 一句话描述、适用场景、关键约束
2. **执行步骤**: 分步骤的执行指南
3. **自检方法**: 每个约束的自检话术
4. **示例应用**: 典型应用场景的示例
5. **与其他框架的关系**: 交叉引用到相关方法论

**固化后更新**：
- 更新 `knowledge/methodology/index.md`（方法论索引）
- 更新 `knowledge/log.md`（操作日志）
- 更新 `MEMORY.md`（如果方法论被频繁使用）

## 🔄 会话持久化命令

> **核心价值**: 方法论制定过程可能跨多个会话，需要记录讨论过程、决策点、验证结果

### `/ma:init` — 初始化方法论制定项目

```bash
python3 <base_dir>/scripts/tools/session-manager.py init method:<方法论名称>
```

输出：
```json
{
  "methodName": "...",
  "category": "分析类/思维类/产出类",
  "status": "draft",
  "createdAt": "2026-06-27T10:00:00Z"
}
```

### `/ma:save` — 保存方法论制定进度

**需要 LLM 分析当前制定状态**：
- `summary`: 本次会话完成的制定内容
- `framework`: 当前框架的版本和内容
- `decisions`: 方法论设计决策（`{what, why, 第一性原理依据}`）
- `validation`: 验证结果
- `nextSteps`: 下一步制定计划

### `/ma:resume` — 恢复上次制定进度

```bash
python3 <base_dir>/scripts/tools/session-manager.py resume method:<方法论名称>
```

输出上次制定记录，提示："上次讨论到XX，当前框架验证结果是XX。继续完善？"

## 🤖 LLM 深度分析模块

> **参考来源**: user_indent.md 第十章的 LLM 深度解析框架，适配方法论场景

在方法论制定完成后，使用 LLM 进行语义级深度分析：

### 分析维度

| # | 分析维度 | 方法 | 输出 |
|:-:|:---------|:-----|:-----|
| 1 | **隐性约束发现** | 从方法论描述中发现未显式表达的约束 | 隐性约束清单 |
| 2 | **适用边界扩展** | 推断方法论可能适用的其他场景 | 适用场景扩展建议 |
| 3 | **与其他框架的关系** | 发现方法论与其他框架的关联关系 | 交叉引用建议 |
| 4 | **证伪性增强** | 发现框架的潜在失败条件 | 证伪条件补充 |

### LLM 深度分析输出格式

```markdown
## 🤖 LLM 深度分析（方法论）

### 隐性约束发现
- 发现 X 个隐性约束（方法论未显式表达但实际依赖的约束）
- **约束1**: [具体描述] → 建议显式表达

### 适用边界扩展
- 当前适用场景: [原适用场景]
- **可扩展场景**: [扩展场景1、扩展场景2]
- **扩展依据**: [第一性原理推导]

### 框架关联发现
- **关联框架**: [相关框架1、相关框架2]
- **关联方式**: [互补关系、包含关系、对立关系]
- **交叉引用建议**: 在文档中添加交叉链接

### 证伪性增强
- **当前证伪条件**: [原证伪条件]
- **补充证伪条件**: [新增证伪条件]
- **证伪依据**: [失败案例或反例]
```

## 方法论质量评分体系

| # | 评分维度 | 检查项 | 权重 |
|:-:|:---------|:-------|:-----|
| 1 | **可操作性** | 步骤清晰、可执行、有工具支撑 | 25% |
| 2 | **自检方法** | 每个约束有自检话术、有自动化脚本 | 25% |
| 3 | **证伪性** | 有明确的失败条件、可验证 | 20% |
| 4 | **第一性原理支撑** | 从基本原理推导、有逻辑依据 | 15% |
| 5 | **适用边界** | 适用场景清晰、有边界约束 | 15% |

**评分等级**：
- **可用（85+）**: 方法论完整，可直接应用
- **待完善（70-84）**: 方法论基本完整，建议补充自检
- **需重构（<70）**: 方法论不完整，需重新设计
