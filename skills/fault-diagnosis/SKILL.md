# 故障排查方法论

## 概述

本技能提供一套系统化的故障排查方法论体系，覆盖从「发现问题」到「根因确认」到「修复验证」的完整链路。核心原则：

1. **先定位再修复** — 不要跳过诊断直接动系统
2. **先查变化再查异常** — 多数故障由变更触发
3. **先还原场景再分析数据** — 没有上下文的数据没有意义
4. **分层隔离法** — 从外到内逐层排除，不跳层

---

## 一、总体排查工作流

遇到任何故障时，按下述**六步法**推进，每一步完成后再进入下一步：

```
Step 1: 场景还原
  → 发生了什么？什么时候？影响范围多大？最近变更了什么？

Step 2: 数据收集
  → 指标 / 日志 / Trace / 事件 四类数据汇聚到同一时间线

Step 3: 假设生成
  → 基于数据提出 1-3 个最可能的根因假设

Step 4: 假设验证
  → 用额外数据/实验逐条验证或排除假设

Step 5: 根因确认
  → 找到触发条件和根因机制，形成完整因果链

Step 6: 修复 + 复盘
  → 执行修复，确认恢复，记录教训，更新知识库
```

> **切忌**: 跳过 Step 1-2 直接猜根因。大多数排障慢的原因不是"不知道怎么看"，而是"不看变化就开始查指标"。

## 二、核心方法论

### 2.1 事件墙法（推荐首选）

**核心思想**: 根因定位不是查指标异常，而是找到"异常前后发生了什么变化"。

**操作步骤**:
1. 确定故障时间窗口（精确到秒级）
2. 收集该时间段内的**全部事件**（不限于系统指标）
3. 将事件按时间线排列，看哪些与异常时间点重合

**四类事件**:

| 事件类型 | 典型内容 | 来源 |
|:---------|:---------|:-----|
| **变更事件** | 发布、回滚、配置变更、灰度开关、限流策略、路由调整、DB变更、证书变更 | CI/CD 平台、配置中心、Git 日志 |
| **运行时事件** | Pod 重启、节点 NotReady、Deployment 滚动更新、OOM、磁盘挂载、主备切换 | K8s Events、云平台事件 |
| **告警事件** | 监控告警、业务告警、云平台告警 | 监控系统、告警平台 |
| **运营事件** | 大促开始、渠道投放、批量推送、业务规则切换 | 运营日历、发布平台 |

**关键技巧**: 告警之间的先后顺序本身就是排障线索。比如：Redis 连接数告警 → 订单接口超时 → 支付成功率下降，这条时间线本身就指向了根因传播路径。

> 🎯 **使用时机**: 几乎所有系统故障都可以先用事件墙法。快速回答"刚才变了什么"是最快的排障路径。

---

### 2.2 鱼骨图 + 5Why 深度根因分析

**核心思想**: 故障往往是多因素耦合的结果，鱼骨图帮你穷尽可能性，5Why 帮你追到真正的根因。

**操作步骤**:
1. **鱼骨图展开** — 从**人机料法环测**六个维度穷尽可能的故障因素
   - **人**（操作失误、误配置、权限问题）
   - **机**（硬件故障、固件问题、性能瓶颈）
   - **料**（数据异常、缓存失效、配置错误）
   - **法**（流程缺陷、设计缺陷、规范缺失）
   - **环**（环境变化、依赖服务、网络波动）
   - **测**（监控缺失、告警阈值、测试盲区）
2. **5Why 追问** — 对最可能的因素，连续追问 5 次 Why，直到触及：
   - 物理极限（如带宽/容量/散热物理上限）
   - 设计原点（如架构假设被打破）
   - 管理根源（如流程/组织/规范缺失）
   - 外部约束（如供应商/合规/预算限制）

**停止检查**: 如果 5Why 追问后答案仍然停留在"操作层面"（如"某人改错了配置"），说明还没到底——继续追问"为什么允许他改？""为什么没有审批流程？""为什么没有自动化校验？"

---

### 2.3 五层诊断架构

**核心思想**: 从物理信号到业务影响，系统性逐层排查，禁止跳跃。

```
五层架构（从底向上）:

Layer 1: 物理层 / 芯片层
  → 信号完整性、电压/温度/时钟、物理损坏、错误率原始数据
  → 工具: SMART、EDAC、温度传感器、BMC 传感器

Layer 2: 固件层 / 驱动层
  → 固件版本、驱动参数、寄存器配置、FTL 行为
  → 工具: nvme-cli、smartctl、lspci -vvv、ethtool

Layer 3: 系统层 / OS 层
  → 内核日志、资源使用、文件系统、网络协议栈
  → 工具: dmesg、top/htop、iostat、netstat、strace、perf

Layer 4: 应用层 / 中间件层
  → 应用日志、配置、连接池、GC、依赖服务状态
  → 工具: 应用日志、APM、JMX、admin endpoints

Layer 5: 业务层
  → 业务指标、用户影响、SLA/SLO 达成、流量模式
  → 工具: 业务监控面板、用户反馈、A/B 实验看板
```

**分层排查原则**:
- 永远从 Layer 5 开始（先确认业务影响范围），再逐层向下到确切根因
- 某一层全部正常才能跳到下一层——不要越层排查
- 如果 Layer 1-2 都正常，大概率是软件/配置/流程问题

> 🎯 **使用时机**: 硬件类故障（服务器关机、磁盘异常、网络不通）、性能类故障（IO 延迟、吞吐下降）、系统级问题（内核panic、驱动崩溃）

### 2.4 四类数据联动排查法

**核心思想**: 故障现场有四类独立数据源，单个数据源最多只能给出线索，多个数据源交叉验证才能锁定根因。

| 数据 | 回答的问题 | 典型工具 |
|:-----|:----------|:---------|
| **指标 (Metrics)** | 状态有没有变化？何时变的？ | Prometheus、Grafana、BMC Sensors |
| **日志 (Logs)** | 程序/请求里发生了什么？ | ELK、Loki、journalctl、dmesg |
| **链路 (Trace)** | 请求经过了哪些服务？哪一步慢了/错了？ | Jaeger、Zipkin、OpenTelemetry |
| **事件 (Events)** | 系统环境发生了什么变化？ | K8s Events、发布平台、告警系统 |

**交叉验证三原则**:
1. **时间对齐** — 所有数据源先对齐到同一时间轴（UTC 统一）
2. **范围收敛** — 时间对齐后，用不同数据源指认同一故障域
3. **因果排序** — 事件→指标异常→日志报错→Trace 慢调用，形成因果链

**例子**: Pod CrashLoopBackOff
- 指标: 内存使用率在 T0 时刻突然跳升到 95%+（状态变化）
- 事件: T0-5min 有新的配置发布（环境变化）
- 日志: OOM Killer 在 T0+2s 杀掉了进程（程序发生了什么）
- Trace: 新配置导致单个请求的内存申请量增加了 3×（根本原因）

---

### 2.5 变更回溯法

**核心思想**: 多数线上事故和变更有关。指标异常一旦和变更时间重合，就应该优先验证。

**必须检查的变更来源**:
1. **代码发布 / 配置变更** — 最近一次发布是什么？谁做的？多长时间？
2. **基础设施变更** — 网络策略、安全组、K8s 资源配额、存储扩容
3. **依赖服务变更** — 上游/下游服务接口变化、第三方 API 版本更新
4. **数据变更** — 离线数据导入、缓存预热、数据库迁移
5. **容量变更** — 扩缩容、限流阈值调整、连接池大小

**追问技巧**:
- "最近有没有人改过什么？" → 问所有人，不只是运维
- "和上次正常的版本比，变了什么？" → diff 对比是黄金方法
- "这个变更在其他环境先上线了吗？" → 环境差异是常见盲区

---

### 2.6 对比排除法

**核心思想**: 通过对比正常和异常的差异来缩小根因范围。

**三种对比模式**:

| 模式 | 做法 | 适合场景 |
|:-----|:-----|:---------|
| **时间对比** | 故障时刻 vs 正常时刻的同类数据对比 | 突增突降类故障 |
| **空间对比** | 故障节点 vs 正常节点的同类数据对比 | 局部故障、节点差异 |
| **版本对比** | 故障版本 vs 上一版本的配置/代码 diff | 发布导致的问题 |

**操作步骤**:
1. 找一个「正常参照物」（时间上/空间上/版本上的）
2. 列出故障场景和正常场景的所有差异点
3. 逐条验证每个差异点是否是根因
4. 确认后修复并验证

---

### 2.7 AIOPS 自动化排障模式（Event-Driven + ReAct）

**核心思想**: 可重复的故障类型应该自动化排障，不可重复的才走人工深度分析。

**适用于自动化排障的场景**:
- Pod CrashLoopBackOff / OOM / 频繁重启
- 磁盘空间不足 / IO 延迟超标
- 数据库连接池耗尽 / 慢查询
- 证书过期 / DNS 解析失败
- 内存泄漏 / CPU 飙高

**自动化链路**:
```
告警事件 → 事件总线(Queue) → Agent 接收
  → ReAct 推理（Thought → Action → Observation）
  → 调用诊断工具（query_pod_status / query_logs / check_config）
  → 生成诊断结论 → 自动修复 / 通知人工接手
```

**关键设计**:
- **幂等性**: 所有自动修复操作必须是幂等的（可以重复执行）
- **熔断**: 同一故障自动修复 3 次不成功 → 转人工
- **审计**: 所有自动执行的操作必须有日志和回滚方案

## 三、典型故障场景排查速查

### 3.1 服务器硬件类

| 现象 | 优先排查路径 | 关键工具 |
|:-----|:------------|:---------|
| 服务器不开机/重启 | BMC 日志 → 电源状态 → 温度传感器 → POST 码 → 内存报错 | BMC Web、SOL、dmesg |
| 磁盘 IO 高延迟 | iostat await → SMART 指标 → 磁盘类型(SSD/HDD) → 分区 IO 分布 | iostat、smartctl、fio |
| 网络丢包/延迟 | ethtool 统计 → 网卡温度 → 光模块信号 → 交换机端口 | ethtool -S、mii-tool、iperf3 |
| GPU 异常 | nvidia-smi → Xid 错误 → PCIe 链路 → 温度/功耗 → 驱动版本 | nvidia-smi、dmesg、nvidia-persistenced |

### 3.2 软件/系统类

| 现象 | 优先排查路径 | 关键工具 |
|:-----|:------------|:---------|
| 进程异常退出 | dmesg(OOM?) → 应用日志(panic?) → ulimit → cgroup 限制 | dmesg、journalctl、coredumpctl |
| 内存泄漏 | top RES 趋势 → /proc/meminfo → pmap → heap dump | top、pmap、jmap(Java)、valgrind |
| CPU 飙高 | top → perf top → /proc/softirqs → 内核线程/用户态 | top、perf、htop、mpstat |
| 磁盘空间满 | df -h → du 逐层定位 → lsof 查未释放 fd → logrotate 配置 | df、du、lsof、ncdu |

### 3.3 分布式/集群类

| 现象 | 优先排查路径 | 关键工具 |
|:-----|:------------|:---------|
| 服务超时 | Trace 看哪一跳慢 → 依赖服务状态 → 连接池 → GC 暂停 | Jaeger、K8s Events、metrics |
| 数据不一致 | 副本对比 → 同步延迟 → 事务日志 → 一致性协议日志 | diff、mysqldump、etcdctl |
| 负载均衡异常 | 后端健康检查 → 会话保持 → 权重配置 → 后端容量 | curl、健康检查接口、监控面板 |

## 四、排障通用原则

### 4.1 始终验证假设

每个假设必须有对应的**验证方法**和**预期结果**。验证前先自问：
- 如果这个假设是对的，我会看到什么数据？
- 如果这个假设是错的，我应该看到什么？
- 如果两种数据都能看到，那我需要新的假设

### 4.2 一次只改一个变量

修复时一次只改一个配置/参数，验证后再改下一个。多变量同时改会导致无法判断哪个修改起了作用。

### 4.3 留下线索

- 每一步排查的命令和结果记录下来
- 错误信息不要只看最后一屏，看全日志
- 截图/保存快照供后续复盘

### 4.4 时间和范围优先

先回答两个问题再深入：
1. **影响范围**: 影响一个用户/一个节点/整个集群？
2. **时间窗口**: 什么时候开始？持续多久了？

这两个问题的答案决定了排查的紧急程度和方向。
