# 文档审查技能 (Doc Reviewer)

> **理论基础**：[AI 使用哲学文档](knowledge/04_person/ai-usage-philosophy.md) 的五层管道框架
> (L1信源→L2注意→L3知识→L4推理→L5输出+LX元层，A-J十类失效模式)。
>
> 新五层审查将原有的**三层审查（结构→逻辑→来源）**映射到五层管道，并扩展出知识层/推理层/输出层
> 三个原本缺失的审查维度。

## 概述

对技术文档执行 **五层审查**，覆盖 L1-L5 全管道 + LX 元层检查。输出结构化的审查报告和处理建议。

审查层次与映射：

```
原有的三层审查                 新增（基于AI使用哲学）
┌──────────────────────┐     ┌──────────────────────────────┐
│  🅰 结构层 (10s)      │     │  L2注意层 + A类约束遵循检查     │
│  TOC/changelog/交叉链接 │ ←──│  AGENT.md/RULE.md/MEMORY.md   │
├──────────────────────┤     ├──────────────────────────────┤
│  🅱 逻辑层 (5-30min)  │     │  L4推理层 + H类推理失效检测     │
│  13条逻辑谬误/MECE/    │ ←──│  H1/H2/H3/H7 + 方向锁定E类    │
│  声明-实践一致         │     │                              │
├──────────────────────┤     ├──────────────────────────────┤
│  🅲 来源层 (10-60min) │     │  L1信源层 + F类输入污染检查     │
│  取材优先级/交叉验证/   │ ←──│  F1-F5 + 时效/范围/盲区        │
│  量化四要素/时效性     │     │                              │
└──────────────────────┘     └──────────────────────────────┘

                              全新审查维度（覆盖防御薄弱区）
                              ┌──────────────────────────────┐
                              │  🅳 知识层 (10-30min)          │
                              │  L3 + G类幻觉/编造/概念混淆     │
                              ├──────────────────────────────┤
                              │  🅴 输出层 (5-15min)           │
                              │  L5 + I类谄媚/过度自信/偏见    │
                              └──────────────────────────────┘

                              LX 元层检查贯穿所有层：
                              可复现性(J1) + 成本(J2) + 依赖(J3) + 版本(J4)
```

### 五层 vs 原有三层：映射关系

| 原有层 | 新层编号 | 管道层 | 对应失效类 | 说明 |
|:-------|:--------:|:-------|:-----------|:-----|
| 🅰 结构层 | L2检查 | 注意层 | A类（约束遵循） | 约束文件规定的格式/结构是否遵守 |
| 🅱 逻辑层 | L4检查 | 推理层 | H类（推理失效） | 论证链完整性 + E类方向锁定 |
| 🅲 来源层 | L1检查 | 信源层 | F类（输入污染） | 来源优先级+量化四要素+交叉验证 |
| **🅳 新增** | L3检查 | 知识层 | **G类（知识失效）** | 幻觉捏造/来源编造/概念混淆 |
| **🅴 新增** | L5检查 | 输出层 | **I类（输出失效）** | 谄媚迎合/过度自信/偏见放大 |
| **🅵 贯穿** | LX | 元层 | **J类（跨层失效）** | 可复现/成本/依赖/版本漂移 |

## 使用方法

### 快速审查

```bash
python3 <base_dir>/scripts/review_doc.py <文件路径>
python3 <base_dir>/scripts/review_doc.py <文件路径> --output <报告路径>
python3 <base_dir>/scripts/review_doc.py <目录>          # 批量审查
```

### 完整审查流程

#### 🅰 第1层：结构审查（~10秒，可自动化）

先运行自动化脚本检查：

```bash
python3 <base_dir>/scripts/review_doc.py <文件路径>
```

自动检查的项：

| # | 检查项 | 规则 | 严重度 |
|:-:|:-------|:-----|:------|
| 1 | **TOC 存在性** | >100行必须有目录 | 🔴 必过 |
| 2 | **Changelog 底部** | >200行必须有底部变更日志 | 🔴 必过 |
| 3 | **代码块纯ASCII** | 代码块内不能有中文 | 🔴 必过 |
| 4 | **来源标注** | 必须有参考文献/来源引用 | 🔴 必过 |
| 5 | **交叉链接** | 推荐链接到 knowledge/ 下已有文件 | 🟡 推荐 |
| 6 | **量化数据** | 至少3处数值+单位+基线的数据 | 🔴 必过 |

#### 🅱 第2层：逻辑审查（5-30分钟，人工+工具）

逐项检查 **13 条逻辑谬误**。优先检查高频出现的问题：

**高频 5 条**（每次必查）：

| # | 谬误 | 症状 | 自检方法 |
|:-:|:-----|:-----|:---------|
| 1 | **声明-实践不一致** | 宣称A但全文按¬A运作 | 穿行测试：核心原则全文搜索，逐段自检 |
| 2 | **先验分类** | 先假定分类数再事后拟合，却宣称从第一性原理推出 | 追问：数字是推出来的还是定下来的？ |
| 3 | **术语漂移** | 借用其他学科术语包装论证（如"熵"当信息论定理） | 术语溯源：精确引用还是比喻？ |
| 4 | **类比当定理** | 用类比得出结论却用"必然"措辞表述 | 每个"定理/必然"能严格推出来吗？ |
| 5 | **结论前置** | 结论表放在文档开头，后续论证变成给预设找支持 | 核心结论是否在末尾才自然揭示？ |

**中频 5 条**（发现上述问题时连带检查）：

| # | 谬误 | 自检 |
|:-:|:-----|:------|
| 6 | **二元对立** | 真的只有两个选项吗？中间有没有更平衡的方案？ |
| 7 | **假精确** | 每个量化表述，单位是什么？怎么算出来的？ |
| 8 | **空洞同构** | 找到共同点后，追问差异在哪里 |
| 9 | **维度混淆** | 同一个概念在不同语境下含义不同吗？ |
| 10 | **内部冲突未检视** | 把一个对象的所有结论集中在一起，它们打架吗？ |

**低频 3 条**（整体性评估时使用）：

| # | 谬误 | 自检 |
|:-:|:-----|:------|
| 11 | **伪结构/假密度** | 这两条可互相推导或互为特例？合并试 |
| 12 | **诠释学循环** | 框架有证伪性吗？什么证据能让你觉得自己错了？ |
| 13 | **模型几何不相容** | 多个模型的空间结构（顺序/平面/树/网络）能共存吗？ |

#### 🅲 第3层：来源审查（10-60分钟，人工）

| # | 检查项 | 标准 | 严重度 |
|:-:|:-------|:-----|:------|
| 1 | **取材优先级** | 论文/标准 > 白皮书 > 工程报告 > 行业分析 > 通用知识 | 🔴 |
| 2 | **交叉验证** | 关键结论至少 2 个独立来源 | 🔴 |
| 3 | **量化四要素** | 每条数据：数值 + 单位 + 对比基线 + 测试条件 | 🟡 |
| 4 | **时效性** | 科技数据优先 2025-2026 | 🟡 |
| 5 | **上下文的引文** | 引用是否断章取义？原文语境是否支持当前结论？ | 🟡 |

## 与 deep-tech-writer 协作

### 使用场景

```
用户: "创建一篇 NVLink 深度分析"
→ deep-tech-writer: 六步工作流产出文档
→ doc-reviewer: 审查并输出报告
→ 用户或 LLM: 处理审查意见
→ deep-tech-writer: 迭代优化
```

### 审查前置检查

在进行审查前，先运行自动化合规检查，确保基础格式和策略匹配：

```bash
# 策略合规检查（文件是否在正确目录、符合对应策略要求）
python3 scripts/check/strategy-compliance.py <文档路径（相对 knowledge/）>

# 格式合规检查（T1-T7 格式是否通过）
python3 scripts/check/format-validator.py <文档路径（相对 knowledge/）>
```

合规分数 >= 80% 再进入人工审查；< 60% 提示创建者先修正。

### 🅳 第4层：知识审查（L3 知识层 · G类失效）

> **新增审查层**。原有三层覆盖 L1（信源）、L2（注意）、L4（推理），缺少对模型内部知识错误的专门审查。
> 本层专门审查 G1-G6 六类知识层失效。

**依赖**：高度依赖审查员自身的领域知识。脚本仅做辅助标记，判断需人工。

| # | 检查项 | 失效类 | 审查方法 | 严重度 |
|:-:|:-------|:------:|:---------|:------|
| 1 | **幻觉捏造** | G1 | 逐条检查关键事实性主张——"听起来合理"不等于真实存在 | 🔴 |
| 2 | **来源编造** | G5 | 随机抽选 3-5 处引用（DOI/URL/作者/年份），验证是否真实可查 | 🔴 |
| 3 | **概念混淆** | G4 | 检查相近概念是否被正确区分（如 NVLink vs NVSwitch, HBM vs GDDR） | 🔴 |
| 4 | **知识截断** | G2 | 涉及最新事件/技术的数据，检查模型是否使用了截止日期之后的"预知" | 🟡 |
| 5 | **虚假专家** | G3 | 对不熟悉领域的语气是否异常自信？是否给出了超出知识边界的断言？ | 🟡 |
| 6 | **过度泛化** | G6 | 是否有"所有/总是/从来不"类无限定词表述？ | 🟡 |

**知识层审查的对抗式技巧**：

| 场景 | 审查技巧 |
|:-----|:---------|
| 怀疑某篇论文不存在 | 复制论文标题+作者 → 用 light-literature-search 验证 |
| 怀疑引用被编造 | 截取引文片段验证 → 看原始上下文是否支持结论 |
| 怀疑数据被美化 | 找同主题的权威数据交叉对比 → 差距 > 30% 标记为红旗 |
| 对"A优于B"类断言 | 问"是谁做的测试？条件是什么？有没有第三方验证？" |

### 🅴 第5层：输出校准审查（L5 输出层 · I类失效）

> **新增审查层**。检查输出的表述是否经过了适当校准——是否过度自信、谄媚迎合、偏见放大。

| # | 检查项 | 失效类 | 审查方法 | 严重度 |
|:-:|:-------|:------:|:---------|:------|
| 1 | **谄媚迎合** | I1 | 检查是否有条件反射式同意用户的情况；对用户可能的错误是否明确指出 | 🔴 |
| 2 | **过度自信** | I2 | 确定性表述（"必定/毫无疑问/确定无疑"）是否有充足证据？语气 ≠ 正确率 | 🔴 |
| 3 | **指令博弈** | I3 | 是否字面执行了指令但违背了真实意图？ | 🟡 |
| 4 | **偏见放大** | I5 | 输出中的分类/判断是否存在未经审视的假设？ | 🟡 |
| 5 | **拒绝校准** | I6 | 是否有不合理的拒绝或过度配合？ | 🟡 |

**输出层校准信号**：
- 模型中关于"我"或"我确定"的主观表述密度过高 → 可能是自信膨胀的预兆
- 对用户所有观点都无异议 → 警惕谄媚
- 在不确定性高的领域使用绝对措辞 → 过度自信

### 🅵 贯穿层：元层审查（LX · J类失效）

贯穿所有审查层，每层输出后附加元检查：

| # | 检查项 | 失效类 | 检查方法 |
|:-:|:-------|:------:|:---------|
| 1 | **可复现性** | J1 | 关键输出是否条件固定（seed/temperature）？行为是否可重复？ |
| 2 | **成本控制** | J2 | 文档长度是否合理？有无不必要的冗余？ |
| 3 | **依赖检查** | J3 | 引用的外部资源/工具/知识库项是否可访问？ |
| 4 | **版本漂移** | J4 | 如果模型有升级，行为是否有偏离？ |

## 审查工作流完整版（五层）

```
🅰 结构层（L2注意层） ─→ 🅱 逻辑层（L4推理层） ─→ 🅲 来源层（L1信源层）
    ↓                        ↓                        ↓
 运行脚本                13条谬误+E类方向锁定       F1-F5+量化四要素
    ↓                        ↓                        ↓
🅳 知识层（L3新增） ─→ 🅴 输出层（L5新增） ─→ 🅵 元层贯穿（LX）
    ↓                        ↓                        ↓
 G类幻觉/编造审查        I类谄媚/自信校准        J类跨层系统性检查
    ↓                        ↓                        ↓
                     评分输出与审查报告
```

**审查优先级**（按时间预算选择）：
- **快速审查 5min**：🅰 结构层 → 🅲 来源层快速扫描 → 🅵 元层关键项
- **标准审查 15min**：🅰 → 🅲 → 🅱 → 🅵（覆盖原三层 + 元层）
- **深度审查 30-60min**：🅰 → 🅲 → 🅱 → **🅳 知识层** → **🅴 输出层** → 🅵（五层全量）

## 常见场景处理

### 场景1：用户说"确认其合理性"
1. 运行结构审查 → 自动修复格式问题
2. 执行逻辑审查（重点：声践一致、先验分类、二元对立）
3. 输出：审查报告 + 标记的问题行

### 场景2：用户说"解决评审意见"
1. 运行快速结构审查排除低级问题
2. 定位用户提出的具体问题在 13 条中的归属
3. 提出修复方案并执行
4. 重新审查确保闭环

### 场景3：用户说"格式错乱"
1. 优先运行 `check_md_format.py` 修复代码块对齐
2. 再运行 `review_doc.py` 检查其余结构问题
3. 输出修复后的对比

## 📐 ADR（架构决策记录）审查模块

> **参考来源**: ECC-main/agents/architect.md 的 ADR 模板，适配审查场景

### ADR 审查时机

- **必须审查**: 文档包含架构选型、技术路线决策、标准制定内容
- **建议审查**: 文档包含性能优化方案、成本敏感决策、高风险方案
- **快速检查**: 扫描关键词（"决策"、"方案选型"、"架构"、"标准制定"）

### ADR 完整性检查清单

| # | 检查项 | 严重度 | 检查方法 |
|:-:|:-------|:------:|:---------|
| 1 | **背景描述** | 🔴 | 是否清晰描述决策背景、技术约束、业务需求？ |
| 2 | **决策明确** | 🔴 | 是否明确写出最终选择的技术方案？ |
| 3 | **理由充分** | 🔴 | 是否包含"为什么"（第一性原理推导）？是否包含物理/经济/逻辑依据？ |
| 4 | **量化数据** | 🟡 | 是否有性能提升/成本节约的量化数据？ |
| 5 | **正向影响** | 🟡 | 是否列出至少2个正向影响？ |
| 6 | **负向影响** | 🔴 | 是否诚实列出至少1个负向影响（技术债务/风险/成本）？ |
| 7 | **替代方案** | 🔴 | 是否列出至少2个替代方案及其放弃原因？ |
| 8 | **状态标记** | 🟡 | 是否标记状态（提议/已批准/已实施/已废弃）？ |
| 9 | **参考链接** | 🟡 | 是否附带论文/标准/白皮书链接？ |

### ADR 逻辑谬误专项检查

| # | 谬误类型 | ADR 中的表现 | 检查方法 |
|:-:|:---------|:-------------|:---------|
| 1 | **二元对立** | 只列出2个方案，忽略中间方案 | 替代方案表至少包含3个方案 |
| 2 | **先验分类** | 先定方案再找理由支撑 | 检查"理由"是否从数据推导而非预设 |
| 3 | **结论前置** | 决策写在开头，理由变成"找支持" | 决策应在"理由"之后自然浮现 |
| 4 | **假精确** | 量化数据无来源或无单位 | 检查每条数据的"数值+单位+来源" |
| 5 | **空洞同构** | 方案间差异未清晰说明 | 替代方案表必须包含"放弃原因"列 |

### ADR 审查输出模板

```markdown
## 📋 ADR 审查报告: ADR-XXX

### 完整性检查
- **总分**: 完整/基本完整/不完整
- **通过项**: X / 9
- **缺失项**: ...

### 🔴 必须补充
1. [缺失项] → 建议补充内容

### 🟡 建议补充
1. [缺失项] → 建议补充内容

### 逻辑谬误检查
- **发现谬误**: X 条
- **谬误类型**: ...
- **修复建议**: ...

### ADR 质量评级
- **优（85+）**: ADR完整、逻辑严密、量化充分
- **良（70-84）**: ADR基本完整，建议补充细节
- **需改进（50-69）**: ADR不完整，需重大补充
- **不合格（<50）**: 缺少核心要素，需重写
```

## 🔄 会话持久化命令（审查过程）

> **核心价值**: 审查过程可能跨多个会话，需要记录审查进度、发现的问题、已修复项

### `/dr:init` — 初始化审查项目

```bash
python3 <base_dir>/scripts/tools/session-manager.py init review:<文件名> --context path=<文件路径>
```

输出审查计划：
```json
{
  "filePath": "...",
  "totalLines": XXX,
  "reviewPlan": {
    "structureLayer": true,
    "logicLayer": true,
    "sourceLayer": true,
    "adrReview": false
  },
  "createdAt": "2026-06-27T10:00:00Z"
}
```

### `/dr:save` — 保存审查进度

**需要 LLM 分析当前审查状态**：
- `summary`: 本次审查完成的内容
- `foundIssues`: 发现的问题清单（按严重度排序）
- `fixedIssues`: 已修复的问题清单
- `pendingIssues`: 待处理的问题清单
- `adrCheck`: ADR 审查结果（如果有）
- `blockers`: 当前阻塞点（需要用户确认的问题）

### `/dr:resume` — 恢复上次审查进度

```bash
python3 <base_dir>/scripts/tools/session-manager.py resume review:<文件名>
```

输出上次审查记录，提示："上次审查发现了 X 个问题，已修复 Y 个。继续审查剩余问题？"

## 🤖 LLM 深度分析模块（审查增强）

> **参考来源**: user_indent.md 第十章的 LLM 深度解析框架

在审查完成后，使用 LLM 进行语义级深度分析，发现脚本无法检测的隐性问题：

### 分析维度

| # | 分析维度 | 方法 | 输出 |
|:-:|:---------|:-----|:-----|
| 1 | **隐性逻辑谬误** | 结合上下文语义分析发现深层逻辑矛盾 | 逻辑谬误清单（补充脚本检测结果） |
| 2 | **声明-实践一致性** | 检查文档声明与实际操作是否一致 | 一致性问题清单 |
| 3 | **维度对齐检查** | 检查对比分析是否在同一维度上 | 维度不对齐问题清单 |
| 4 | **术语漂移检测** | 检查术语是否在不同语境下含义漂移 | 术语漂移问题清单 |
| 5 | **诠释学循环检测** | 检查框架是否有证伪性 | 框架可证伪性评估 |

### LLM 深度分析输出格式

```markdown
## 🤖 LLM 深度分析（审查增强）

### 隐性逻辑谬误
- 发现 X 条脚本无法检测的逻辑谬误
- **声明-实践不一致**: [具体描述]
- **维度不对齐**: [具体描述]
- **术语漂移**: [具体描述]

### 框架可证伪性评估
- 当前框架是否可证伪？如果框架是错的，什么证据会让你发现？
- **诠释学循环风险**: 高/中/低

### 审查建议优先级
- **P0（必须修复）**: 声明-实践不一致、维度不对齐
- **P1（建议修复）**: 术语漂移、隐性谬误
- **P2（可选修复）**: 格式优化
```

## 📊 审查评分体系增强

> **参考来源**: deep-tech-writer 的质量评分体系，适配审查场景

| # | 评分维度 | 审查检查项 | 权重 |
|:-:|:---------|:-----------|:-----|
| 1 | **结构合规** | TOC/changelog/代码块ASCII/来源标注/交叉链接 | 10% |
| 2 | **逻辑严密** | 13条逻辑谬误+ADR谬误+声明-实践一致 | 35% |
| 3 | **来源质量** | 取材优先级/交叉验证/量化四要素/时效性 | 25% |
| 4 | **ADR完整性** | 9项完整性检查+逻辑谬误专项检查 | 15% |
| 5 | **隐性问题** | LLM深度分析发现的语义级问题 | 15% |

**评分等级**（更新）：
- **优（90+）**: 无严重问题，可直接发布
- **良（75-89）**: 有少量建议修改项，可发布
- **需改进（60-74）**: 有必须修改项，修改后发布
- **不合格（<60）**: 有严重问题，需重大修改或重写

## 审查工作流完整版

```
🅰 结构层（自动化） ─→ 🅱 逻辑层（13条谬误） ─→ 🅲 来源层 ─→ 🅳 ADR审查 ─→ 🅴 LLM深度分析 ─→ 🅵 评分输出
    ↓                    ↓                       ↓           ↓             ↓                ↓
运行脚本             人工+工具检查           人工检查      专项检查      语义级分析      生成报告
```

**审查优先级**：
- **快速审查**: 🅰 结构层 → 输出评分（<1分钟）
- **标准审查**: 🅰 → 🅱 → 🅲 → 🅵 输出评分（5-30分钟）
- **深度审查**: 🅰 → 🅱 → 🅲 → 🅳 → 🅴 → 🅵 输出评分（10-60分钟）
