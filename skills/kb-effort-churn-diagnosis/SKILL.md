# 知识库投入统计与治理诊断（kb-effort-churn-diagnosis）

> 由 2026-08-05 用户四轮纠正沉淀。**分类标准、统计铁律、诊断方法均为用户定义，视为 SSOT**——任何占比/投入/治理统计前先读本技能，避免重犯分类错误。

## 1. 分类标准 v3.0（用户定义，SSOT）

统计"工具建设 vs 业务投入"等占比前，**必须先按此分类归集，不得自行发明分类**。分类不对，分析没有意义。

| 大类 | 目录 | 说明 |
|:-----|:-----|:-----|
| **工具** | 根目录 `scripts/`（scraper/KeySQL/Specter）、`spec/`、`skills/`、`scheduler/`、`templates/`、`weekly-reports/` | 工具本体 + Reporter（对系统的定期审视也算工具） |
| **业务深度调研** | `knowledge/` 除 `01_survey`、`weekly-reports` 外**全部** | 人工花精力产生的深度产出 |
| **数据导入** | `conversation-log/`、`import/`、`discover/` | 对话/素材/试验场 |
| **定期调研** | `knowledge/01_survey/` | 每日增量库 |
| **待确认** | `websites/`（用户提到的 "WebRootPath"，knowledge/ 下无此目录） | 向用户确认指向后再归类，勿臆断 |

**注意**：用户会继续微调此分类。新统计前先向用户确认分类是否仍有效；用户给出新定义时以用户最新定义为准，并回写本表。

## 2. 统计铁律（用户三令五申，违反即返工）

1. **不做二分/三分法拟合用户感知**。直接给 A/M/R/D 四状态 × 分目录 × 分月的**原始统计表**，由用户按自己的框架聚合。不要"把数据拟合到用户的 30/40/30"。
2. **不要过度拟合用户的数据与分类**。拆得越细越好，越能说明问题。
3. **双维度不可混用**：①位置维度（产出去向=文件落在哪个目录）②动作维度（时间投入）。用户感知的是动作维度，位置数据不能直接验证动作感知。维度混用必然失真（历史教训：52.6% 误报 = 位置分类错误 + 计权偏差双重产物）。
4. **时间范围拉满**：不能只看一天/一月，从**工程创建至今**全程观察——目录变化、文件改动、格式演变，都是问题高发区。
5. **先摸清实际目录结构再跑统计**，避免分类错位（历史教训：ai-storage 13 篇实际在 03_AI/train/ 而非 07 调研；01_survey 是定期调研库）。
6. 提交数 ≠ 工作量：大导入提交（单提交塞 300+ 文件）会虚增；先识别并单独标注口径。

## 3. 测量指标（A/M/R/D + 体积）

| 维度 | 指标 | 回答的问题 |
|:-----|:-----|:-----------|
| 产出量 | **A** 新增文件数（分目录/分月） | 产出了多少 |
| 维护投入 | **M** 修改次数（churn） | 打磨/维护花了多少 |
| 重构投入 | **R** 重命名数 | 整理/重构工作量 |
| 清理 | **D** 删除数 | 淘汰清理 |
| 规模 | 文件数快照 | 规模扩张（如 6/30 1065 → 8/5 2699 md） |

**git 数据源要点**：
- `git log --numstat --diff-filter=A/M/R/D` 逐条解析；awk 解析注意**含空格路径的引号问题**（会归错类）。
- 识别大导入提交：单提交 A>300 文件即标注"大导入"，单独排除并注明口径（历史：6 个大导入提交约 1.9 万文件全进 import/discover、0 进 knowledge/）。
- 高频修改 Top 榜 = churn 雷达输入。

## 4. churn 诊断方法论（报告的核心价值）

**核心认知（用户定义）**：反反复复修改的点，背后是系统逻辑搭建或治理存在大问题——无固定 Skill 约束、无对应检查机制、文件目录乱放、命名格式不对。**报告的价值 = 发现问题 + 给出解决思路（洞察），不是给一个符合认知的数据。**

| 旧视角（错误） | 新视角（正确） |
|:-----|:-----|
| 某文件被改 80 次 = 很勤奋/维护投入大 | churn 高 = **治理缺失的信号**，需诊断根因 |
| 报告 = 给出符合认知的数据 | 报告 = **发现问题 + 解决思路** |

**五大病灶类型**（诊断时对照）：
1. 文件命名不规范（如 kb-rename 一次改 1019 文件）→ 根因=无命名规范+无检查 → 解法=规范入 RULE + 模板约束
2. 文件存放目录不当（反复迁移）→ 根因=目录架构早期未定型 → 解法=归档前先查归属
3. index/log 反复维护（常占高频修改 Top10 的大头）→ 根因=多套格式并存/人肉记账 → 解法=双轨制 + 自动化
4. 链接失效反复修 → 根因=TOC 脚本/移动路径/无自动验证 → 解法=validator 入定时任务
5. 技能/工具配置反复改 → 根因=注册流程初期未固化 → 解法=固定注册步骤 + check 脚本

**治理生命周期模型**（可检测）：
```
无约束发生 → churn 爆发 → 治理介入 → 收敛
```
- churn **骤升** = 爆发信号 → 诊断根因
- 治理提交（refactor/feat）= 介入
- churn **骤降** = 收敛验证
- **用时间分布诊断，不用总量**：总量高但已收敛 = 治理成功；持续高位 = 残留病灶（如全局 log.md 仍高频 = 人肉记账残留）。

## 5. 全程透视视角（三阶段识别）

从工程创建至今看投入阶段特征：
- **建立导入期**：素材铺量（IMPORT 新增占全月 80%+）
- **扩张加工期**：批量加工 + 业务打磨（discover 修改数巨大、业务修改数达前月 4-5 倍）
- **收敛治理期**：铺量停止 → 治理接管（业务新增骤降、重命名/整理税集中）

阶段判断让"规模扩张阶段快速撑大体积"这类用户判断有数据支撑。

## 6. AI 自动优化三级流水线（质量提升）

用户已明确"文件质量是下一重点，让 AI 自动优化，通过辩证方法提升质量"：

```
L1 脚本检测（50+ check 已就位）→ 输出问题清单
L2 AI 批处理 → 机械修复（如标题层级跳跃）+ 内容增强 + 辩证质检（多视角交叉）
L3 人工抽验（5-10% + 关键文档全审）
```

落地五步：全库基线扫描 → 机械修复（先备份到 tmp/bak/）→ 子目录内容增强试点 → check 入 commit 门禁 → 月度质量趋势扫描。

## 7. 产出与报告规范

- 诊断报告归档 `knowledge/07_industry-research/`（治理类 → `19_governance-permissions/` 或 `04_ai/`），单同步（kb-log-append.py 追加 log.md；README/index 脚本批量）。
- 报告结构：分类定稿 → 全程时间线 → A/M/R/D 全景 → 问题高发区（churn 雷达 + 病灶图谱）→ 可执行解法。
- 关键量化数据多源交叉验证，无法获取时标注缺口（遵循 RULE.md）。
- 过程失误主动披露（如 log 编辑吞条目当场修复），不掩盖。
