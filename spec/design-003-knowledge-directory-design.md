## 1. 设计总纲


> **实现 AR**: `AR-P3-011`（Index+Log 自动维护）
### 1.1 系统定位

knowledge/ 是 Cow 工程的核心知识库，当前 **2,549 个 .md 文件，~56MB 纯文本**（2026-07 快照；2026-08 已持续增长，实际数以 `knowledge/index.md` 为准），覆盖服务器/AI 基础设施全场景。它不是简单的文件堆叠，而是一个**有生命的、自组织、自演进的认知体**。

### 1.2 三层设计哲学

> **SSOT 参照**: 三论的完整定义见 `sr-001-knowledge-system-requirements.md §1.2` C5。

```text
┌──────────────────────────────────────────────────────┐
│                    第一性原理                          │
│  知识库的本质是什么？                                  │
│  → 信息的最小冗余 + 最大检索效率 + 最高可信度           │
├──────────────────────────────────────────────────────┤
│                     MECE 分层                         │
│  目录分类怎么做到互斥且穷尽？                            │
│  → 每层分类在语义上不重叠，全部覆盖领域知识              │
├──────────────────────────────────────────────────────┤
│                    约束辩证法                          │
│  规范 vs 灵活如何平衡？                                │
│  → SSOT 适度原则：25% 松弛空间 + bak 回收站            │
│                                                      │
│  【正式定义】: "约束辩证法" = 在 SSOT 规范统一（75%）   │
│  与弹性空间（25%）之间保持动态平衡，通过 bak 回收站      │
│  机制实现可逆变更。既避免过度约束导致僵化（无辩证），     │
│  也避免过度灵活导致混乱（无约束）。                     │
└──────────────────────────────────────────────────────┘
```

### 1.3 设计目标优先级

| 优先级 | 目标 | 度量方式 | 当前状态 |
|:------:|:-----|:---------|:--------:|
| **P0** | 文件可定位 — 每个文件有唯一明确的归属目录 | 文件→目录的确定性映射 | ✅ 基础分类 |
| **P0** | 索引完整 — 每个模块有 index.md + log.md | 覆盖率审计 | 🚧 部分模块 | 
| **P0** | 引用有效 — 交叉链接不指向不存在文件 | 链接有效性检查 | ✅ 定期检查 |
| **P1** | 分类 MECE — 同层互斥且穷尽 | 目录 MECE 审计 | ✅ 7 大模块 |
| **P1** | 路径稳定 — 目录结构变更频率可控，且有完整迁移计划 | 结构变更记录 | ✅ 有 bak 机制 |
| **P2** | 语义丰富 — 从目录结构可推断领域关系 | 新文件分类准确率 ~85% | 🚧 |

### 1.4 工程特点：编程 + AI 双引擎维系知识库

#### 1.4.1 双引擎架构

本知识库不是纯手工维护（如 Wiki），也不是纯 AI 生成（如 RAG 知识库），而是 **编程脚本（Scripts）与 AI 技能（Skills）双引擎协同** 的混合架构：

```text
                       知识库维系体系
                     ┌──────────────────┐
                     │    人的判断       │
                     │  (策略/决策/终审)  │
                     └────────┬─────────┘
                              │ 指令 & 确认
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
     ┌────────────────┐ ┌────────────────┐ ┌────────────────┐
     │  Scripts 引擎   │ │  Skills 引擎    │ │  人工操作       │
     │  (编程脚本)     │ │  (AI 技能)      │ │  (手动编辑)     │
     │                 │ │                 │ │                 │
     │ 批量/确定/可重复 │ │ 智能/上下文/创造 │ │ 决策/修复/终审  │
     │ 无 token 可用   │ │ 需 token 消耗   │ │ 无需 token      │
     └───────┬─────────┘ └───────┬─────────┘ └────────┬────────┘
             │                   │                    │
             └─────────┬─────────┴────────┬───────────┘
                       │                  │
                       ▼                  ▼
              ┌──────────────────────────────────────┐
              │            knowledge/                 │
              │     2,549 个文件 · ~56MB 纯文本        │
              └──────────────────────────────────────┘
```

> 📌 **备注（2026-08-19，第四轮）**: 图中「2,549 个文件 · ~56MB 纯文本」为 2026-07 快照——2026-08 知识库已持续增长，实际数以根 `knowledge/index.md` 为准；三层引擎分工（Scripts 确定性 / Skills 智能 / 人工决策）仍然有效。

#### 1.4.2 分工边界

| 维度 | Scripts 引擎（编程） | Skills 引擎（AI） | 人工 |
|:-----|:-------------------|:-----------------|:-----|
| **核心能力** | 确定性操作、批量扫描、语法校验、路径检测 | 语义理解、内容生成、深度分析、质量审查 | 策略决策、异常处理、终审确认 |
| **运行条件** | 零 token 成本，依赖 Python 环境 | 需 token 消耗，依赖 LLM 调用 | 不依赖任何系统资源 |
| **典型操作** | `link-validator.py` 扫全库链接、`md-format.py` 格式检查、`reformat-log.py` 批量格式化 | `deep-tech-writer` 写深度分析、`doc-reviewer` 逻辑审查、`knowledge-doc-writer` 专题报告 | 目录重组决策、大规模迁移确认、无法自动修复的异常处理 |
| **输出性质** | 结构化报告（JSON/Markdown 表格） | 自然语言文档（Markdown 长文） | 操作指令 |
| **错误模式** | 假阳性/假阴性（规则误判） | 幻觉/框架堆名词/来源编造 | 人为失误 |
| **谁写代码** | AI 辅助生成，但运行时不依赖 AI | AI 运行时执行，但流程由人设计 | 直接操作 |

#### 1.4.3 四层协同模式

编程与 AI 不是二选一，而是在**四个层次**上协同运作：

```text
┌──────────────────────────────────────────────────────────────────┐
│  Layer 4: 战略层（人工）                                           │
│  目录重组决策、模块新增/合并、大规模迁移、规则修改                     │
│  ↑ 人做出判断，AI 提供数据支撑                                      │
├──────────────────────────────────────────────────────────────────┤
│  Layer 3: 决策层（AI + 编程数据）                                   │
│  AI 分析编程脚本产出的结构化数据（链接失效报告/健康扫描报告），        │
│  给出修复优先级和建议策略，人确认后执行                               │
│  ↑ 编程提供"事实"，AI 提供"判断"                                    │
├──────────────────────────────────────────────────────────────────┤
│  Layer 2: 自动层（编程定时触发）                                     │
│  定时脚本扫描全库、生成健康报告、发现异常链式触发 AI 深度分析           │
│  脚本是"哨兵"，AI 是"分析师"                                        │
│  ↑ 编程发现异常，AI 理解异常                                        │
├──────────────────────────────────────────────────────────────────┤
│  Layer 1: 执行层（编程 + AI 各自独立）                               │
│  • 编程独立：`check_links.py`、`md-format.py` 零 token 批量执行    │
│  • AI 独立：`deep-tech-writer` 写技术文档、`web-archive` 归档 URL   │
│  • 编程给 AI 铺路：`link-validator.py` 输出失效清单 → AI 逐个分析   │
│  • AI 生成编程材料：AI 写文档后 → `md-format.py` 验证格式           │
└──────────────────────────────────────────────────────────────────┘
```

#### 1.4.4 协同模式实例

| 场景 | 编程脚本干的事 | AI 技能干的事 | 协同效果 |
|:-----|:-------------|:-------------|:---------|
| **批量导入素材** | `autokb/pipeline.py` 扫描文件、去重、写入 | —（全自动脚本） | 零 token 完成 7,400+ 文件处理 |
| **链接失效修复** | `link-validator.py` 扫描全部链接 → 分类报告 | `doc-reviewer` 分析失效原因，给出修复策略 | 编程定位问题，AI 理解上下文 |
| **周报生成** | `weekly-report-generator` Skill 触发知识库扫描 | AI 分析知识库一周变更 + 联网搜索行业动态 | 定时触发 + 智能分析 |
| **文档质量审查** | `md-format.py` 检查格式规范 | AI 做三层审查（结构/逻辑/来源） | 编程做确定的格式检查，AI 做模糊的质量判断 |
| **内容深度补充** | `depth-completer` Skill 检测"框架堆名词"模式 | AI 补充第一性原理分析 | 编程检测模式，AI 补充深度 |
| **变更引用跟踪** | `track-knowledge-refs.py` 扫描所有引用 | —（全自动脚本，生成失效清单给人/AI 确认） | 零 token 确保引用完整性 |
| **健康快照** | `knowledge-normalizer.py` 5 阶段全库扫描 | AI 解读健康报告，生成优化建议 | 编程出数据，AI 出洞察 |
| **Token 断供时** | `check/link-validator.py`、`md-format.py`、`reformat-log.py` 等仍可运行 | AI 不可用 | 核心维护不依赖 AI |

#### 1.4.5 关键设计决策

| 决策 | 理由 | 影响 |
|:-----|:------|:-----|
| **脚本独立可运行** | 每个脚本有 `argparse` CLI，不依赖 AI 能力 | Token 断供时基础维护不停摆 |
| **AI 产出有脚本校验** | `deep-tech-writer` 产出 → `md-format.py` + `doc-reviewer` 验证 | 质量门禁不是纯粹靠 AI 自觉 |
| **脚本输出结构化** | `link-validator.py --json` 供 AI 或人后续分析 | 编程数据可被 AI 消费 |
| **Skills 编排脚本** | Skill 的 SKILL.md 中定义工作流，内部调用脚本执行 | 复杂流程靠 AI 编排，确定步骤靠脚本执行 |
| **不做大规模纯 AI 目录重组** | 目录结构决策由人 + 数据支撑完成 | 避免 AI 幻觉导致灾难性结构变更 |
| **保留手工操作入口** | `edit`/`write`/`mv` 等基础工具始终可用 | 人可以做任何操作，不受 AI 可用性约束 |

#### 1.4.6 与纯编程方案 / 纯 AI 方案的对比

| 维度 | 纯编程方案（传统 Wiki） | 纯 AI 方案（RAG 知识库） | **本方案（编程+AI 双引擎）** |
|:-----|:----------------------|:---------------------|:--------------------------|
| 内容创建成本 | 高（人工写） | 低（AI 生成） | **中低**（AI 写 + 脚本校验） |
| 维护可靠性 | 高（规则驱动） | 低（AI 幻觉风险） | **高**（编程兜底 + AI 增强） |
| 扩展灵活性 | 低（规则写死） | 高（AI 语义理解） | **高**（脚本可扩 + AI 灵活） |
| 知识深度 | 取决于写的人 | 取决于 prompt | **高**（AI 深度 + 脚本审计） |
| Token 依赖 | **零依赖** | 完全依赖 | **部分依赖**（基础维护不依赖） |
| 一致性保障 | 强（规则检查） | 弱（AI 风格不固定） | **强**（脚本强制格式 + AI 理解语义） |
| 异常处理 | 规则误判 | AI 幻觉编造 | **三者互补**（规则/AI/人工接力） |

**核心结论**: 编程脚本提供**确定性**和**可靠性**，AI 技能提供**理解力**和**创造力**，人工提供**判断力**和**终审权**。三者互补，缺一不可。

## 2. 目录设计原则


> **实现 AR**: `AR-P3-011`（Index+Log 自动维护）→ `AR-SYS-007`（SSOT 治理）
> **需求 SR**: `SR-005`（import 目录管理）→ `SR-007`（discover 输出目录）
### 2.1 MECE 分层模型

knowledge/ 采用**三级 MECE 分层**：

```text
D1: 顶层模块         (7 大模块 + 4 特殊模块)
    │  互斥原则: 每个顶层模块有唯一的领域边界
    │  穷尽原则: 所有可能的服务器/AI 知识都能归入某一模块
    │
    ├── D2: 功能子目录   (每个模块下的子分类)
    │      互斥原则: 子目录间功能不重叠
    │      穷尽原则: 模块下的知识都有明确归属
    │
    └── D3: 文件层面     (独立 .md 文件)
           归属原则: 每个文件属于唯一子目录
           例外原则: 跨领域文件使用 <模块>-<主题>.md 命名
```

**自检方法** — 判断目录是否符合 MECE：

```text
问: "一个新来的知识点，能否唯一确定它属于哪个目录？"
是 → 目录设计合格
否 → 存在分类重叠或遗漏，需要重构

问: "两个子目录之间，是否存在边界模糊的文件？"
有 → 边界不清晰，需要调整目录定义或文件归属
无 → 子目录间互斥合格
```

### 2.2 编号预留原则

顶层模块使用 **两位数字编号** 预留扩展空间：

```text
01_*      02_*      03_*      04_*      05_*      06_*      07_*
 │         │         │         │         │         │         │
 ├─ 01     ├─ 00     ├─ 03     ├─ 04     ├─ 05     ├─ 06     ├─ 07
 ├─ 02     ├─ 01     ├─ ...    ├─ ...    ├─ ...    └─ others └─ 09_vr
 ├─ ...    ├─ ...    └─ ...    └─ ...    └─ ...    └─ ...
 └─ ...    └─ 08_incr_ir
```

| 编号 | 名称 | 说明 | 扩展空间 |
|:----:|:-----|:-----|:--------:|
| 01_ | 调研跟踪 | 行业动态追踪 | 01_~09_ 可用（当前占用 02_） | 
| 02_ | 研发 | 服务器研发全链路 | 00_~92_ 可用（当前占用 10 个） |
| 03_ | AI 技术原理 | AI 核心技术 | 预留 03_~09_ |
| 04_ | 个人 | 个人发展 | 预留 04_~09_ |
| 05_ | 工具与行业 | 工具/方法论 | 预留 05_~09_ |
| 06_ | 其他归档 | 历史档案 | 预留 06_~09_ |
| 07_ | 行业调研跟踪 | 行业研究报告 | 07_~09_ + 编号日期目录 |

**设计决策**: 预留跳跃编号（非连续 01-07）是为了**避免日后重新编号的大规模重构**。例如从 01_ 直接到 03_，中间的 02_ 留给未来可能分裂出的模块。

### 2.3 子目录深度约束（🔵 提示级）

> ⚠️ **当前级别**: 以下约束为**提示级别（L3）**，暂不强制要求调整到位。实际违反时优先评估影响范围，不阻塞业务操作。对应约束注册表编码 **02305-02307**，详见 `sr-004-workspace-dir-req.md §3.2`。

| 规则 | 说明 | 违规示例 | 正确做法 |
|:-----|:------|:---------|:---------|
| 目录深度 ≤ 3 级 | `knowledge/<模块>/<子目录>/<文件>` 为最长路径 | `02_rd/03_hardware/thermal/power/case.md` | 归入更粗粒度子目录或文件名加前缀 |
| 单目录文件数 ≤ 200 | 超出应拆分子目录 | `01_survey/` 下 802 个文件 | 已拆分为 22 个子目录 |
| 同层子目录数 ≤ 15 | 超出意味着分类粒度过细 | `02_rd/` 下有 10+ 子目录 | 当前 14 个可接受，接近上限 |

### 2.4 命名规范

| 类型 | 命名规则 | 示例 |
|:-----|:---------|:------|
| 顶层模块 | `NN_英文名`（NN 两位数字） | `01_survey/`, `02_rd/` |
| 子目录 | `NN_英文名` 或 `英文名` | `00_rd-management/`, `agent-engineering/` |
| **文件（全局模块，2026-08-03 起强制）** | **`YYYY-MM-DD-英文描述-使用-连接.md`** | `2026-07-03-knowledge-scale-law.md` |
| 特殊文件 | `index.md` / `log.md` / `index.md` / `README.md` | 固定名称 |
| 周报 | `weekly-report-YYYY-MM-DD.md` | `weekly-report-2026-07-20.md` |
| 对话归档 | `YYYY-MM-DD.md` | `2026-07-21.md` |
| 行业报告 | `YYYYMMDD_主题-slug.md` | `20260720_supernode-market-critique.md` |

**文件命名规范细则（design-003 v1.2，2026-08-03 全库实施）**：
- **格式**: `YYYY-MM-DD-英文描述.md`；描述用英文小写，单词以 `-` 连接（如 `knowledge-scale-law`）
- **日期来源优先级**: ① 文件头部元信息（`Date:`/`更新日期:` 等）→ ② 头部 30 行内独立日期行 → ③ **git 最早提交时间**（`--follow` 追溯重命名链，反映真实归档日）→ ④ mtime（最后兜底）
- **描述生成**: 已有英文文件名提取 slug；中文文件名翻译为英文 slug（内置映射表）
- **重复消歧**: 内容完全相同或新名冲突的文件，保留最早日期原件，其余加 `-dupN` 后缀（不删除，清理另议）
- **适用范围**: 全局模块（`02_rd`/`03_AI`/`04_person`/`05_tools`/`06_others`/`07_industry-research`）活跃 .md 文件；**排除** `01_survey/`、`weekly-reports/`（保留分布式机制）、`index.md`/`log.md`/`README.md`/`index.md`（管理文件）、`oldbak/`、`*-bak/`（废弃归档区）
- **配套工具**: `scripts/tools/kb-rename-normalize.py`（批量规范化，dry-run 生成映射表→apply 执行 git mv + 全库引用更新）；`scripts/check/kb-index-check.py` **C8** 文件名规范检查

**禁止的命名模式**:
- ❌ 中文文件名（链接编码问题）
- ❌ 空格或特殊字符（` ` `（）` `，`）
- ❌ 大写字母开头（除非是固定缩写如 `AI`, `BMC`）
- ❌ `.md` 以外的扩展名
- ❌ 过长的文件名（>60 字符）
- ❌ 无日期前缀的文件名（全局模块）

## 4. 目录演变史

记录 directory/ 设计的重大变更，便于定期反思时追溯设计决策。

### 4.1 阶段一：单层扁平（~2026-03）

```text
knowledge/
├── survey/               # 调研跟踪 — 单目录 500+ 文件
```

**问题**: 单目录文件数快速膨胀，检索困难；模块边界模糊。

### 4.2 阶段二：两层分类（~2026-05）

```text
│   └── ...
```

**改进**: 引入编号预留 + 子目录分类，文件可定位性大幅提升。

### 4.3 阶段三：7+4 模块 + 三层审计（当前，~2026-07）

- 7 大内容模块 + 4 特殊模块（concepts/methodology/sources/weekly-reports）
- 每个模块独立 index.md + log.md
- 链接有效性/格式规范/目录架构定期审计

- 文件数从 300+ 增长到 2,549

### 4.4 演变教训总结

| 维度 | 教训 | 当前做法 |
|:-----|:------|:---------|
| 编号 | 连续编号导致重构时需改多个目录名 | 跳跃编号（01→03，中间预留） |

| 单目录文件 | 500+ 文件时几乎无法手动检索 | 单目录 ≤ 200，超出立即拆分子目录 |
| 引用 | 无约束导致大量失效链接 | 每次变更检查引用完整性 |
| 归档 | 无回收站导致误删无法恢复 | mv 到 bak/ + 日期标记 |

## 5. 文件变更管理

> 📌 **备注（2026-08-19）**: 本节为**历史完整流程**（v1.2 原文，未删除）。其中 §5.2 涉及模块级 `index.md`/`log.md` 同步的步骤**已被单轨制取代**——2026-08-19 起全库统一：索引=根 `knowledge/index.md`（`kb-global-index.py` 刷新，禁手编）、日志=根 `knowledge/log.md`（`kb-log-append.py` 追加）；不写任何子目录 index/log（含 01_survey/weekly-reports）。**仍在用的规则**：五种变更操作分类（新增/修改/移动/删除/重命名）、bak 回收站规则（永不 rm，mv 到 `tmp/bak/<原因>-<日期>/`）、批量改名流程、变更约束矩阵。


> **实现 AR**: `AR-P3-011`（Index+Log 自动维护）→ `AR-P3-010`（多层质量门禁）
### 5.1 五种文件变更操作

| 操作 | 触发 | 执行者 | 约束 |
|:-----|:------|:-------|:-----|
| **CREATE** | 新知识点产生 | Agent/Skills/手动 | index.md + log.md 同步更新 |
| **UPDATE** | 内容修正/补充 | Agent/手动 | 修改前检查头部约束标记 |
| **MOVE** | 目录重构/分类调整 | Agent/手动 | 源文件 mv，更新所有引用 |
| **DELETE** (→bak) | 内容废弃/重复 | Agent/手动 | mv 到 bak/，**永不 rm** |
| **RENAME** | 文件名规范化 | Agent/手动 | 更新所有交叉引用 |

### 5.2 详细操作流程

#### 5.2.1 CREATE — 创建文件

```text
[触发] 新知识点/外部来源/对话产出
   │
   ├─ 1. 判定归属模块（见 §3.2 判定矩阵）
   │
   ├─ 2. 生成 slug 文件名
   │     规则(全局模块): YYYY-MM-DD-英文描述.md（日期取当日; 描述英文小写-连接, ≤60字符）
   │     反例: "关于超节点散热设计的一些思考.md" ❌ / "thermal-design.md" ❌(无日期)
   │     正例: "2026-08-03-supernode-thermal-design.md" ✅
   │
   ├─ 3. 写入文件内容
   │     长文档(>200行): TOC + 交叉链接 + Changelog
   │     量化数据: 数值+单位+基线+条件
   │     来源: 文件头部 > Source: 标记
   │
   ├─ 4. 更新 README.md 条目库（全局模块, 见 design-010）
   │
   ├─ 5. 更新 log.md（模块级）
   │     格式: | YYYY-MM-DD | add | 文件名 | 说明 |
   │
   └─ 6. 检查是否需要更新顶层 index.md
         新模块→更新顶层索引
         已有模块→跳过
```

#### 5.2.2 UPDATE — 修改文件

```text
[触发] 内容修正/补充
   │
   ├─ 1. 检查文件头部约束标记（前 10 行）
   │     ⚠️ AUTO-GENERATED → 通过生成工具修改
   │     🚫 DO NOT EDIT / MANAGED_BY → 不手动修改
   │     无标记 → 直接编辑
   │
   ├─ 2. 执行修改
   │     使用 edit 工具（精确替换）而非 write（全量覆盖）
   │
   ├─ 3. 更新交叉引用
   │     如果修改了章节标题，检查其他文件的链接是否失效
   │
   └─ 4. 更新 log.md
         格式: | YYYY-MM-DD | update | 文件名 | 变更说明 |
```

#### 5.2.2b 批量改名（RENAME 全库规范化 — 2026-08-03 新增）

> 全局模块文件命名规范升级为 `YYYY-MM-DD-英文描述.md` 后，全库批量改名的标准操作流程。

```text
[触发] 文件名不合规批量修复 / 新命名规范实施
   │
   ├─ 1. DRY-RUN 审查（推荐先执行）
   │     python3 scripts/tools/kb-rename-normalize.py --dry-run
   │     → 生成 tmp/kb-rename-mapping.csv 映射表
   │     → 审查: 日期来源(git优先) / 描述slug / dup消歧
   │
   ├─ 2. APPLY 执行
   │     python3 scripts/tools/kb-rename-normalize.py --apply
   │     → git mv 保留历史（禁用裸 mv）
   │     → 自动更新全库引用（排除 log.md/weekly-reports 历史快照）
   │
   ├─ 3. 三同步收尾
   │     ① 刷新 index.md: python3 scripts/tools/kb-global-index.py
   │     ② 更新 README.md 条目库文件名（脚本已同步处理）
   │     ③ log.md 当日分节追加更名记录（含映射表路径）
   │
   ├─ 4. 复核
   │     python3 scripts/check/kb-index-check.py   # C8 文件名规范应 PASS
   │     残留旧名检查: grep -rn "旧文件名" knowledge/（排除 log.md/weekly-reports）
   │
   └─ 5. 提交
         git add -A && git commit（映射表随变更提交, 便于追溯）
```

**RENAME 单文件纪律**: `git mv` 改名 → 全库替换旧名引用（独立文件名匹配, 防子串误替换）→ 刷新 index.md → log.md 记录。**禁止**直接 `mv`（丢失 git 历史）。

#### 5.2.3 MOVE — 移动文件（目录重构）

```text
[触发] 目录重构/分类调整
   │
   ├─ 1. USE CASE 判断
   │     单文件移动 → 直接处理
   │     批量移动 → 先确认用户（破坏性操作）
   │
   ├─ 2. 扫描所有引用
   │     脚本: track-knowledge-refs.py — 找出所有指向此文件的链接
   │     范围: knowledge/ 内所有 .md + skills/*/SKILL.md + scripts/*.py
   │
   ├─ 3. 执行 mv
   │     mv knowledge/<旧路径> knowledge/<新路径>
   │     保持文件名不变（除非需要 renaming）
   │
   ├─ 4. 更新所有引用
   │     自动更新: 路径变更的修正
   │     人工确认: 内容关联性改变时的引用策略调整
   │
   ├─ 5. 更新 index.md + log.md（源模块和目标模块都更新）
   │     源模块 index: 删除条目
   │     目标模块 index: 添加条目
   │
   └─ 6. 更新依赖此文件的所有 skill/script 的映射
```

#### 5.2.4 DELETE / ARCHIVE — 废弃文件

```text
[触发] 内容废弃/重复/过时
   │
   ├─ 1. 确认: 是否真的不再需要？
   │     - 被更优文档替代？→ 在 bak/ 中标注替代文档
   │     - 数据过时？→ 在 bak/ 中标注过期日期
   │     - 错误内容？→ 在 bak/ 中标注错误原因
   │
   ├─ 2. 扫描引用
   │     确认没有活跃的链接指向此文件
   │     有链接 → 先更新引用，再归档
   │
   ├─ 3. mv 到 bak/
   │     mv knowledge/<path> tmp/bak/<原因>-<日期>/（原 knowledge/bak/，2026-07-24迁址）
   │     原因使用短标签: cleanup / superseded-by-xxx / outdated / duplicate
   │
   ├─ 4. 更新 index.md → 删除条目
   │
   └─ 5. 更新 log.md
         格式: | YYYY-MM-DD | archive | 文件名 | 原因 |
```

#### 5.2.5 RENAME — 重命名文件

```text
[触发] 文件名规范化/主题变更
   │
   ├─ 1. 判断规模
   │     单文件 → 走下方纪律
   │     批量(全库规范化) → 走 §5.2.2b 流程
   │
   ├─ 2. 单文件 RENAME 纪律
   │     ① git mv 旧名 新名（禁止裸 mv, 保留历史）
   │     ② 全库替换旧名引用（独立文件名匹配, 排除 log.md/weekly-reports 历史快照）
   │     ③ 刷新 index.md: python3 scripts/tools/kb-global-index.py
   │     ④ README.md 条目库文件名同步 + log.md 追加记录
   │
   └─ 3. 命名规范校验（C8）: python3 scripts/check/kb-index-check.py
```

| **索引完整性** | index.md 覆盖率 | 有 index 的模块 / 总模块数 | 100% | ~85% | `analyze-index-coverage.py` |
| **链接有效性** | 失效链接占比 | 失效链接 / 总链接数 | < 1% | ~2% | `link-validator.py` |
| **格式规范性** | 格式错误文件占比 | 格式问题文件 / 总文件数 | < 5% | ~8% | `md-format.py` |
| **日志一致性** | log.md 格式统一 | 标准格式条目 / 总条目 | 100% | ~90% | `reformat-log.py` |
| **位置合理性** | 文件归属正确率 | 抽查匹配率 | > 90% | ~85% | `kb-health.py` |
| **引用新鲜度** | 超 6 个月未更新文件占比 | 未更新文件 / 总文件数 | < 20% | ~30% | `kb-health.py` |

### 9.2 健康度等级

| 等级 | 综合得分 | 含义 | 应对措施 |
|:----:|:--------:|:-----|:---------|
| 🟢 **优秀** | ≥ 90% | 知识库健康，维护良好 | 正常维护 |
| 🟡 **良好** | 80-89% | 有少量问题但不影响使用 | 安排修复 |
| 🟠 **需关注** | 70-79% | 存在明显问题 | 安排集中修复 |
| 🔴 **危险** | < 70% | 需要紧急处理 | 立即修复，暂停新内容写入 |

### 9.3 健康审计调度

| 审计类型 | 频率 | 脚本 | 目标 |
|:---------|:----:|:-----|:------|
| 全库健康快照 | 每周 | `knowledge-normalizer.py` | 5 阶段一站式检查 |
| 链接专项 | 每月 | `link-validator.py --classify` | 分类检测失效原因 |
| 索引覆盖率 | 每月 | `analyze-index-coverage.py` | 补全缺失的 index.md |
| 格式专项 | 文档写入时 | `md-format.py` | 确保新建文档格式规范 |
| 目录 MECE 审计 | 每季度 | `directory-architect.py` | 发现分类缺陷 |
| 深度健康报告 | 每季度 | `kb-health.py --json --report` | 季度趋势分析 |
