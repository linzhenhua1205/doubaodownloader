## 1. 六步法总览

### 1.1 六步流程定义

```text
┌─────────────────────────────────────────────────────────────────┐
│                    六步架构法（闭环）                              │
│                                                                   │
│  ① 定目标       ② 理依赖时序    ③ 规划目录架构                  │
│  ┌─────────┐    ┌───────────┐   ┌─────────────┐                 │
│  │ 做什么？│ →  │ 依赖谁？  │ → │ 放哪里？    │                 │
│  │ 为什么？│    │ 谁依赖它？│   │ 怎么组织？  │                 │
│  └─────────┘    └───────────┘   └─────────────┘                 │
│       │              │                │                          │
│       ↓              ↓                ↓                          │
│  ④ 枚举全部约束  ⑤ 匹配实现方案  ⑥ 落地执行                    │
│  ┌───────────┐   ┌────────────┐   ┌───────────┐                │
│  │ 限制什么？│ → │ 用什么做？│ → │ 怎么做？  │                │
│  │ 边界在哪？│   │ 谁来验证？│   │ 何时做完？│                │
│  └───────────┘   └────────────┘   └───────────┘                │
│       │              │                │                          │
│       └──────────────┴────────────────┘                          │
│                         ↑                                        │
│                   反馈闭环（实际执行反馈修正目标）                  │
└─────────────────────────────────────────────────────────────────┘
```

| 步骤 | 核心问题 | 产出物 | 典型耗时 |
|:----:|:---------|:-------|:--------:|
| **① 定目标** | 这个架构想解决什么问题？价值主张是什么？ | 目标陈述 + 成功标准 | 20% |
| **② 理依赖时序** | 它依赖哪些前置条件？哪些下游依赖它？ | 依赖图谱 + 拓扑排序 | 15% |
| **③ 规划目录架构** | 信息/模块如何组织？归属谁？ | 目录结构 + 归属矩阵 | 15% |
| **④ 枚举全部约束** | 有哪些限制条件？边界在哪里？ | 约束清单 + 冲突消解 | 20% |
| **⑤ 匹配实现方案** | 用什么工具/技术实现？如何验证？ | 方案映射 + 实现矩阵 | 20% |
| **⑥ 落地执行** | 谁在什么时候做什么？ | 路线图 + 任务清单 + 验收 | 10% |

### 1.2 六步法在各架构层的应用矩阵

架构描述不是单一层次的——它在六个不同抽象层上展开。六步法在不同层的侧重不同：

| 架构层 | 六步法侧重 | 典型产出 | 对应 spec 文件 |
|:-------|:-----------|:---------|:---------------|
| **L1: 理念层** — 为什么做？ | ①定目标 > ④约束 | 三论指导、设计哲学 | `design-001` §1, `design-003` §1 |
| **L2: 系统层** — 整体怎么搭？ | ③目录规划 > ②依赖时序 | 四层架构、四阶段数据流 | `design-001` §2-3, `sr-004` |
| **L3: 模块层** — 各模块怎么做？ | ①定目标 > ⑤实现方案 | Skills/Scripts 设计、知识策略 | `design-007`, `design-004`, `design-003` |
| **L4: 规范层** — 规则是什么？ | ④枚举约束 > ⑥落地执行 | 约束注册表、开发规范、格式规范 | `sr-003`, `std-001`, `std-002` |
| **L5: 优化层** — 如何改进？ | ②依赖时序 > ⑥落地执行 | Token 优化、调度可靠性、任务优化 | `design-005`, `design-006`, `sr-006` |
| **L6: 需求层** — 要什么？ | ①定目标（需求侧） | SR/AR 需求清单 | `sr-001`, `ar-001` |

**当前问题**: 现有 spec 文件多数只覆盖 2-3 步——如 `design-001` 侧重①+③但缺④约束枚举和⑥落地路径；`sr-006` 侧重④+⑥但缺②依赖时序和③目录规划。本文以六步法统一视角补全各缺失环节。

### 1.3 六步法的内在逻辑

六步法不是串行瀑布——而是**螺旋递进**的：

```text
循环1（粗粒度）:  目标(宏观) → 依赖(粗) → 目录(顶层) → 约束(关键) → 方案(初选) → 落地(试点)
                                                                                      ↓
循环2（中粒度）:  目标(收敛) → 依赖(精) → 目录(细化) → 约束(完整) → 方案(确定) → 落地(推广)
                                                                                      ↓
循环3（细粒度）:  目标(验证) → 依赖(审计) → 目录(优化) → 约束(固化) → 方案(迭代) → 落地(运维)
```

| 循环 | 粒度 | 典型周期 | 适用场景 |
|:----:|:-----|:--------:|:---------|
| 粗粒度 | 模块级 | 月 | 新模块引入、架构重构 |
| 中粒度 | 文件级 | 周 | 规范制定、策略设计 |
| 细粒度 | 操作级 | 天 | 日常修正、增量优化 |

**核心原则**: 不追求一步到位——允许并鼓励在后续循环中补全前序步骤遗漏的细节。

## 6. 匹配实现方案

### 6.1 四层实现方案映射

六步法第⑤步：对每类约束/需求，匹配具体的实现方案。当前 Cow 体系中有四类实现途径：

```text
① 需求/约束 (What)
   │
   ├─▶ ② Skills (AI处理引擎): 通过 SKILL.md 描述行为 → AI 运行时执行
   │
   ├─▶ ③ Scripts (确定性引擎): 通过 Python/bash 脚本 → 命令行执行
   │
   ├─▶ ④ Spec文件 (规范/设计): 通过 .md 文档 → 人类阅读 + 审计
   │
   └─▶ ⑤ 配置/模板 (数据驱动): 通过 YAML/JSON/模板 → 参数化执行
```

| 实现途径 | 优势 | 劣势 | 适用场景 |
|:---------|:-----|:-----|:---------|
| **② Skills** | 灵活、创造性、上下文感知 | Token 成本高、非确定性 | 内容创作、深度分析、研究 |
| **③ Scripts** | 确定、可控、可自动化、低成本 | 僵化、无上下文 | 批量处理、格式检查、数据提取 |
| **④ Spec** | 全局可见、系统化、可审计 | 不主动执行、维护成本 | 架构规范、质量标准、设计原则 |
| **⑤ 配置** | 零代码、参数化、易调整 | 表达能力有限 | 路径映射、模板、任务调度 |

```text
│
├─ 需要频率 > 1次/天？
│   ├─ 是 → Scripts（低成本可调度）
│   └─ 否 → Skills（灵活但 token 高）
│
├─ 需要确定性输出（格式/数值校验）？
│   ├─ 是 → Scripts（可验证）
│   └─ 否 → Skills（可解释）
│
├─ 需要全局一致性（所有写入行为统一）？
│   ├─ 是 → Spec 规范 + Scripts 检查
│   └─ 否 → Skills 各自处理
│
└─ 需要参数化/频繁调整？
    ├─ 是 → 配置/模板
    └─ 否 → 硬编码到 Scripts/Skills
```

**当前的应用案例**:

| 需求 | 裁决过程 | 最终方案 | 理由 |
|:-----|:---------|:---------|:------|
| 约束合规检查 | 确定性 + 高频 → Scripts | `constraint-check.py` | 不需要创造，需要精确 |
| 深度技术分析 | 上下文理解 + 创造性 → Skills | `deep-tech-writer` | 需要原理级理解和结构化输出 |
| 文件写入归属判定 | 全局一致性 + 低频率 → Spec + Scripts | `std-003` 决策树 + 检查脚本 | 统一规则优于 AI 灵活判断 |
| 定时任务调度 | 确定性 + 高频 → Scripts | scheduler | 纯工程机制，不需要 AI |
| 内容格式修复 | 确定性 + 低频 × 创造性边缘 → Scripts 主 + Skills 辅 | Scripts 自动修复（格式）+ Skills 手动处理（语义） | 格式问题确定性，语义问题需 AI |

### 8.1 design-001：系统架构（四层架构描述的六步法重构）

**当前 §2 的描述**:

```text
### ⑤ 实现方案
```
